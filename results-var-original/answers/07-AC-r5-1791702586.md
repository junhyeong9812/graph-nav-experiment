# 즉시 구매 처리 흐름 분석

경로 표기: `B` = `src/main/java/com/fream/back/domain/`

## 1. 진입 API, 처리 단계, 동기/비동기, 응답 ID

**API**: `POST /order-bids/instant` (`OrderBidCommandController`, base path `/order-bids`).
- `B order/controller/command/OrderBidCommandController.java:22` (`@RequestMapping("/order-bids")`)
- `B order/controller/command/OrderBidCommandController.java:89-90` (`@PostMapping("/instant")`, `createInstantOrderBid`)
- 요청 본문: `saleBidId`, `addressId`, `warehouseStorage`, `paymentRequest` — `B order/dto/InstantOrderRequestDto.java:20-29`

**처리 단계 (모두 한 요청 스레드, 하나의 트랜잭션에서 동기 처리)**
1. 컨트롤러가 이메일을 추출하고(`OrderBidCommandController.java:92`) 결제 요청에 `userEmail`을 넣고 `orderId=null`로 초기화한다 (`:97-98`, `:119-123`).
2. `OrderBidCommandService#createInstantOrderBid` 호출 (`:101`). 이 메서드가 `@Transactional`이다 — `B order/service/command/OrderBidCommandService.java:118-119`.
   1. 입력 검증 (`OrderBidCommandService.java:123`, `:154-167`)
   2. 구매자 조회 (`:126`)
   3. SaleBid 조회 및 Sale 연결 검증 (`:129-130`, `:172-184`)
   4. `OrderCommandService#createInstantOrder` 호출 (`:133-139`)
   5. `OrderBid` 생성 (`:142`, `:189-207`)
3. `createInstantOrder` 내부 (`B order/service/command/OrderCommandService.java:219-319`) 순서:
   1. 주소 조회 `addressQueryService.getAddress` (`:238`)
   2. `Order` 생성·저장 (`:241-247`), 결제 요청에 orderId 주입 (`:250`)
   3. `OrderItem` 생성 (`:255-256`)
   4. `OrderShipment` 생성 (`:264-271`)
   5. SaleBid 매칭 + `flush` (`:279-283`)
   6. 판매자 창고 상태 갱신 (조건부, `:291-293`)
   7. 결제 처리 `paymentCommandService.processPayment` (`:305`)
4. `processPayment` (`B payment/service/command/PaymentCommandService.java:57-107`): 검증 → 결제 유형별 엔티티 생성 → `notifyUsersAndUpdateSaleStatus` (알림 + Sale `SOLD`, `:83`).

**동기/비동기**: 동기이다. 이 경로에는 Kafka 발행이 없다. 같은 `orders` 아래의 `POST /orders/{orderId}/process-payment-shipment`만 Kafka 비동기(202 Accepted)이며 (`B order/controller/command/OrderCommandController.java:42-69`), 즉시 구매는 그 경로를 타지 않는다. 컨트롤러 호출은 `orderBidCommandService`뿐이다 (`OrderBidCommandController.java:28`, `:101`). 응답은 200 OK이고 결제까지 끝난 뒤 돌아온다 (`:109`).

**응답 ID**: 반환 값은 `Long`이고 메시지는 "생성된 주문 ID"로 적혀 있지만, 실제로는 **`OrderBid`의 ID**이다.
- `orderBidCommandService.createInstantOrderBid(...)`는 `OrderBid`를 반환하고 (`OrderBidCommandService.java:119`, `:142-144`), 컨트롤러가 `.getId()`를 호출한다 (`OrderBidCommandController.java:101-107`).
- 변수명은 `orderId`이지만 값은 OrderBid PK이다 (`:101`, `:109`). Order PK가 아니다.
- Javadoc(`:80-82`)도 "생성된 주문 ID"라 적혀 있어 실제 동작과 다르다.

| 3 | `OrderShipment` 생성 | `OrderCommandService.java:264-271`, `B shipment/service/command/OrderShipmentCommandService.java:61-68` | `ShipmentStatus.PENDING` |

| 5 | (판매자가 창고 보관 판매인 경우만) `WarehouseStorage.status` 갱신 | `OrderCommandService.java:291-293`, `B warehouseStorage/service/command/WarehouseStorageCommandService.java:117-133` | `WarehouseStatus.ASSOCIATED_WITH_ORDER` (새 엔티티 아님, 기존 변경) |

| 8 | `OrderBid` 생성·저장 | `OrderBidCommandService.java:192-206` | `OrderBid.status = MATCHED`, `isInstantPurchase = true`, `order`/`sale` 연결 |

세부 사항:
- 4단계에서 `Order`는 아직 `PENDING_PAYMENT`이다. 즉시 구매 경로에서는 `order.updateStatus(...)` 호출이 없다 (`OrderCommandService.java:219-319` 전체).
- 7단계: 결제 시점에 `order.getOrderBid()`가 null이다. OrderBid는 이 뒤(8단계)에 만들어지기 때문이다 (`PaymentCommandService.java:388-389`). 그래서 `saleBidQueryService.findByOrderId`로 SaleBid를 찾아 Sale을 얻는다 (`:391-397`, `B sale/service/query/SaleBidQueryService.java:26-28`). 4단계의 `flush`가 이 조회를 가능하게 한다. 이어서 알림 후 `sale.updateStatus(SaleStatus.SOLD)` (`PaymentCommandService.java:403-405`).
- `Sale`의 `SaleStatus` 상태 전이 검증(`canTransitionTo`)은 이 경로에서 호출되지 않는다. `updateStatus`가 무조건 대입한다 (`B sale/entity/Sale.java:142-144`).
- `OrderBid.assignOrder`는 `status`를 `MATCHED`로 바꾼다 (`B order/entity/OrderBid.java:253-275`). 빌더에서도 `MATCHED`로 지정한다 (`OrderBidCommandService.java:196`).
- 즉시 구매 경로에서 `order.assignPayment`는 호출되지 않는다 (`processPayment` 반환값을 버림, `OrderCommandService.java:305`). `Payment.order` 쪽만 설정된다 (`B payment/entity/Payment.java:47-50`).

## 3. 결제 수단별 결과

`PaymentRequestDto`는 `paymentType`(CARD/ACCOUNT/GENERAL)으로 하위 DTO를 역직렬화한다 (`B payment/dto/PaymentRequestDto.java:20-25`). 공통 검증은 `PaymentCommandService.java:117-146`이다 (orderId 일치, userEmail 일치, `paidAmount > 0`).

| 수단 | 처리 | `Payment.status` | `isSuccess` | 근거 |
|---|---|---|---|---|
| CARD | PortOne `processCardPayment` 호출 후 `CardPayment` 저장 | 응답 `status`가 문자열 `"success"`이면 `PAID`, 아니면 기본값 `PENDING` | 응답 성공 시 `updateSuccessStatus(true)`. 단 생성자의 `setPaidAmount`가 이미 `isSuccess = paidAmount > 0`으로 만든다 | `PaymentCommandService.java:157-208`, `B payment/entity/CardPayment.java:60`, `Payment.java:60-63` |
| ACCOUNT | 은행명 검증(`Bank` enum) 후 `AccountPayment` 저장. 외부 호출 없음, 입금 확인 없음 | `PENDING` | `setPaidAmount`로 true (금액>0) | `PaymentCommandService.java:236-262`, `:470-488`, `B payment/entity/AccountPayment.java:28` |
| GENERAL | `impUid` 필수 검증 후 `GeneralPayment` 저장. 외부 검증 호출 없이 클라이언트가 준 값을 신뢰 | `PAID` | true | `PaymentCommandService.java:290-316` |

**즉시 구매가 끝까지 성공하는가**: 세 수단 모두 예외 없이 끝까지 진행되어 HTTP 200이 나가고, 알림과 `Sale = SOLD`까지 진행된다. 결제 완료 여부와 무관하다.
- ACCOUNT는 `PENDING`인 채로 구매가 확정된다. 이후 입금 확인 로직이 이 경로에는 없다. `Payment.updateStatus`는 `PENDING → PAID`만 허용한다 (`B payment/entity/PaymentStatus.java:12-13`).
- 알림 전송과 Sale `SOLD` 처리는 `payment.getStatus()`를 확인하지 않는다 (`PaymentCommandService.java:83`, `:383-420`).
- 결제 금액(`paidAmount`)을 `saleBid.bidPrice`나 `order.totalAmount`와 비교하는 코드가 없다 (`:117-146`, `OrderCommandService.java:241-251`).

**카드 결제를 PG(결제 대행사)가 실패로 응답하면** — 두 경우로 갈린다.
1. **PortOne 응답이 `code != 0` 또는 HTTP != 200인 경우**: `PortOneApiClient#processCardPayment`가 `PaymentProcessingException`을 던진다 (`B payment/portone/PortOneApiClient.java:270-275`).
   - `createCardPayment`와 `processPayment`가 그대로 전파한다 (`PaymentCommandService.java:179-185`, `:218-219`, `:89-94`).
   - `createInstantOrder`가 `OrderPaymentProcessingFailedException`으로 감싸 던진다 (`OrderCommandService.java:304-309`).
   - `OrderBidCommandService`가 `OrderException`을 그대로 재던지고 (`:145-146`, `:212-215`), 외부 `@Transactional`(`:118`)이 롤백한다. Order, OrderItem, OrderShipment, SaleBid 매칭, 창고 상태 변경이 모두 취소된다.
   - 결과: 에러 응답이 나가고 OrderBid는 만들어지지 않는다. `GlobalExceptionHandler#handleOrderException`이 처리한다 (`B ../global/exception/GlobalExceptionHandler.java:325`).
   - `@Retryable`은 선언돼 있지만(`PortOneApiClient.java:224-228`) `@EnableRetry`가 프로젝트에 없어 재시도는 일어나지 않는다 (`grep -rn EnableRetry src` 결과 없음). 또 대상이 `PaymentApiException`이고 이 실패는 `PaymentProcessingException`이라 어차피 대상이 아니다.
2. **HTTP 200 + `code == 0`이지만 `response.status`가 `"success"`가 아닌 경우** (예: PG 승인 거절이 `status: failed`로 오는 경우): 예외가 없다.
   - `CardPayment`가 `status = PENDING`으로 저장되고 (`PaymentCommandService.java:203-208`), 롤백이 일어나지 않는다.
   - 생성자의 `setPaidAmount`로 `isSuccess`는 이미 `true`이다 (`CardPayment.java:60`, `Payment.java:60-63`).
   - 이후 흐름이 그대로 진행되어 구매자·판매자 알림이 나가고 Sale이 `SOLD`가 된다. 즉시 구매는 성공으로 응답된다.
   - 추가 참고(코드 밖 지식에 의한 추정): 코드는 성공을 `"success"`로 비교하는데, PortOne(아임포트) 결제 성공 값은 일반적으로 `"paid"`이다. 그렇다면 정상 승인도 `PENDING`으로 남는다. 이 부분은 PortOne 응답 명세에 근거한 추정이며 저장소에서 확인되지 않는다.

## 4. 알림 대상, 시점, 전달 방식

**대상과 내용** — `PaymentCommandService#sendNotifications` (`:434-462`):
- **구매자**: `"결제가 완료되었습니다. 주문 ID: {orderId}"` (`:438-443`)
- **판매자** (`sale.getSeller()`): `"구매자가 결제를 완료하였습니다. 판매 ID: {saleId}"` (`:447-454`)
- 둘 다 `NotificationCategory.SHOPPING`, `NotificationType.BID`이다.

**시점**: 결제 엔티티 저장 직후, 같은 요청·같은 트랜잭션 안에서 동기로 전송된다 (`PaymentCommandService.java:83`). Sale `SOLD` 변경 직전에 호출된다 (`:403-404`). 결제 상태가 `PENDING`(계좌이체, 카드 미확정)이어도 "결제가 완료되었습니다"가 나간다. 알림 실패는 로그만 남기고 삼킨다 (`:457-461`, `:421-425`).

**방식** — `B notification/service/command/NotificationCommandService.java`:
1. DB에 `Notification` 저장 (`createNotification`, `:44-54`).
2. 실시간 전송: Redis에 `WebSocket:User:{email}` 키가 있을 때만 STOMP `convertAndSendToUser(email, "/queue/notifications", dto)`로 푸시한다 (`:303-313`, 상수 `:37-38`). 연결이 없으면 DB에만 남는다 (`:320-322`).
3. 이 경로에서 Kafka 알림 발행은 없다.

**알림이 나가지 않는 것**: 즉시 구매 경로에서는 `OrderShipmentCommandService`의 알림(배송 시작·완료)이 호출되지 않는다. `createOrderShipment`는 알림을 보내지 않는다 (`OrderShipmentCommandService.java:56-75`). 배송 완료·주문 완료 알림은 이후 배치(`ShipmentItemProcessor`)가 송장번호 있는 배송을 처리할 때 나간다 (`B shipment/config/ShipmentItemProcessor.java:106-117`, `UpdateShipmentStatusesJobConfig.java:95`).

## 5. 최종 주문 상태와 창고 보관 선택 시 차이

**최종 `Order.status` = `PENDING_PAYMENT`** (요청 처리가 끝난 시점).
- `createInstantOrder`에서 `Order`는 `PENDING_PAYMENT`로 만들어진 뒤 (`OrderCommandService.java:244`) 이 흐름에서 `updateStatus`가 호출되지 않는다 (`:219-319`).
- `OrderBidCommandService`(`:118-149`)와 `PaymentCommandService`(`:57-107`, `:383-426`)에도 Order 상태 변경이 없다.
- `PAYMENT_COMPLETED → PREPARING`으로 바꾸는 로직은 다른 경로(`processPaymentAndShipment`, `OrderCommandService.java:163-177`, Kafka `OrderEventConsumer.java:192-217`)에만 있다. 즉시 구매는 두 경로 모두 타지 않는다.
- 이름·메시지는 "즉시 구매가 성공적으로 처리되었습니다"이다 (`OrderBidCommandController.java:109`)이지만 주문은 결제대기 상태로 남는다.
- 이후 상태 변화: 배송이 `IN_TRANSIT`/`OUT_FOR_DELIVERY`가 되고 송장번호가 생겨 배치가 `DELIVERED`를 확인하면 `completeOrder`가 `COMPLETED`로 바꾼다 (`OrderShipmentCommandService.java:191-205`). `PENDING_PAYMENT → COMPLETED`는 전이표상 허용된다 (`B order/entity/OrderStatus.java:157`). 그 전까지는 `PENDING_PAYMENT`이다.

**그 밖의 최종 상태 요약**

| 엔티티 | 최종 값 |
|---|---|
| `Order.status` | `PENDING_PAYMENT` |
| `OrderShipment.status` | `PENDING` |
| `SaleBid.status` (sale 패키지) | `MATCHED` |
| `OrderBid.status` | `MATCHED`, `isInstantPurchase = true` |
| `Sale.status` | `SOLD` |
| `Payment.status` | CARD: 보통 `PENDING` 또는 `PAID` (3번 참조), ACCOUNT: `PENDING`, GENERAL: `PAID` |
| `WarehouseStorage.status` | 판매자 Sale이 창고 보관이면 `ASSOCIATED_WITH_ORDER`, 아니면 변경 없음 |

**구매자가 "창고 보관"(`warehouseStorage=true`)을 선택한 경우: 달라지는 것이 없다.**
- 컨트롤러가 값을 서비스로 넘기지만 (`OrderBidCommandController.java:105`, `OrderBidCommandService.java:119-138`), `createInstantOrder`는 `isWarehouseStorage` 인자를 읽지 않는다. 본문에서 이 인자를 사용하는 곳이 없다 (`OrderCommandService.java:220-319`, 파라미터는 `:221`에서만 등장).
- 창고 관련 분기는 **판매자의** `sale.isWarehouseStorage()`뿐이다 (`:291-293`). 이 값이 true일 때 판매자의 기존 `WarehouseStorage`를 `ASSOCIATED_WITH_ORDER`로 바꾼다. 구매자 선택과 무관하다.
- 구매자 창고 보관을 처리하는 코드는 `processPaymentAndShipment`에만 있다 (`OrderCommandService.java:163-172`: `PAYMENT_COMPLETED → PREPARING → IN_WAREHOUSE`, `warehouseStorageCommandService.createOrderStorage`, 이어서 `COMPLETED`). 즉시 구매 경로에서는 호출되지 않는다.
- 결과적으로 `IN_WAREHOUSE`/`COMPLETED`로의 전이도, 주문용 `WarehouseStorage` 생성도 일어나지 않는다. 배송지(`addressId`)로 `OrderShipment`가 그대로 만들어진다 (`OrderCommandService.java:264-271`).
- 판매자 Sale이 창고 보관인데 해당 `WarehouseStorage`를 찾지 못하면 `WarehouseStorageNotFoundException`이 나고 (`B warehouseStorage/service/query/WarehouseStorageQueryService.java:30-32`) `OrderWarehouseStorageProcessingFailedException`으로 감싸져 전체가 롤백된다 (`OrderCommandService.java:295-301`).
