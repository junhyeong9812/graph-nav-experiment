# 구매자 배송: 운송장 등록 → 배송 완료

경로 접두사: `src/main/java/com/fream/back/` (이하 `B/`로 표기)

## 요약

- 운송장 등록(`PATCH /shipments/order/{id}/status`)은 의도된 흐름대로라면 Shipment → Order → (OrderBid/SaleBid) 순으로 상태가 바뀌고 구매자·판매자에게 알림이 간다. 그러나 **실배송 일반 구매 입찰 주문은 Order가 `PREPARING`이라 `IN_TRANSIT` 전이가 막혀 항상 실패**한다(404 `S001`, 전부 롤백).
- 배송 완료 감지는 **Spring Batch 잡이 6시간마다** 돌며, 실제 처리 코드는 `ShipmentItemProcessor`다. `OrderShipmentCommandService.updateShipmentStatuses()`와 `UpdateShipmentStatusesJobConfig.shipmentItemProcessor()`는 실행되지 않는다.
- 배송 완료 판정 후 처리(`completeOrder`)는 **즉시 구매 주문(b)에서만 끝까지 간다.** 일반 구매 입찰 주문(a)은 `PREPARING → COMPLETED` 전이가 막혀 실패한다.

## 1. 운송장 등록 요청

### 1-1. 진입 API
1. `PATCH /shipments/order/{shipmentId}/status`, body `OrderShipmentRequestDto`(courier, trackingNumber) — `B/domain/shipment/controller/command/OrderShipmentCommandController.java:20,33-45`. 컨트롤러가 `orderShipmentCommandService.updateTrackingInfo(...)`를 호출한다(`:41`).
2. (참고) 같은 컨트롤러의 `POST /{shipmentId}/check-status`(`:58`)는 운송장 저장과 동시에 택배사를 즉시 조회하는 별도 API다 → `OrderShipmentCommandService.updateAndCheckShipmentStatus` (`B/domain/shipment/service/command/OrderShipmentCommandService.java:452`).

### 1-2. 코드가 짜 놓은 상태 변경 순서와 알림 (`OrderShipmentCommandService.updateTrackingInfo`, `:239-303`)
1. courier/trackingNumber가 비어 있으면 `TRACKING_INFO_REQUIRED`(S004, 400) — `:243-246`, `ShipmentErrorCode.java:15`.
2. `OrderShipment` 조회 후 `shipment.updateTrackingInfo()` → 택배사·운송장 저장, 상태 **`IN_TRANSIT`**으로 설정 — `:256`, `B/domain/shipment/entity/OrderShipment.java:41-45`. 이 메서드는 전이 검증 없이 대입한다.
3. **Order** `order.updateStatus(OrderStatus.IN_TRANSIT)` — `:259-260`. `Order.updateStatus`는 `canTransitionTo`로 검증하고 불가하면 `InvalidOrderStatusException`을 던진다 — `B/domain/order/entity/Order.java:113-120`.
4. **구매자 알림** "상품이 출발하였습니다. 주문 ID: …" (SHOPPING/BID) — `:263-269`.
5. `updateSaleStatusToSold(orderId)` — `:276`. 내부(`:112-183`)에서 SaleBid가 있으면 Sale을 `SOLD`로 바꾸고 창고 상태 갱신, **판매자 알림** "상품이 성공적으로 판매 완료되었습니다"(`:116-137`). OrderBid 쪽 Sale도 같은 방식으로 SOLD + 판매자 알림(`:150-171`).
6. SaleBid의 Sale이 창고 보관이면 창고 상태 SOLD — `:279-286`.
7. `updateOrderAndSaleBidStatusToCompleted` — `:289`, `:413-440`. OrderBid가 `MATCHED`면 `COMPLETED`, SaleBid가 `MATCHED`면 `COMPLETED`. 내부 예외는 로그만 남기고 삼킨다(`:436-439`).

즉, 의도상 운송장 등록 시점에 이미 Order `IN_TRANSIT`, Sale `SOLD`, 입찰 `COMPLETED`까지 가도록 되어 있다(이름과 달리 "배송 중"에 "판매 완료"까지 처리).

### 1-3. 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문 — 끝까지 성공하지 못한다
**실패 지점: 3단계 `order.updateStatus(IN_TRANSIT)` (`OrderShipmentCommandService.java:260`).**

근거(주문이 이 시점에 가진 상태):
1. 일반 구매 입찰 주문은 `PENDING_PAYMENT`로 생성된다 — `B/domain/order/service/command/OrderCommandService.java:81`.
2. `processPaymentAndShipment`의 "실제 배송" 분기는 `PAYMENT_COMPLETED → PREPARING`까지만 올린다 — `OrderCommandService.java:174-177`. (Kafka 소비자 경로도 동일하게 `PREPARING`에서 멈춘다 — `B/domain/order/service/kafka/OrderEventConsumer.java:215-218`.) 이 결제 과정에서 `OrderShipment`는 `PENDING`으로 생성된다(`OrderShipmentCommandService.java:42`).
3. 허용 전이표에서 `PREPARING`은 `IN_WAREHOUSE`, `SHIPMENT_STARTED`만 갈 수 있고(`B/domain/order/entity/OrderStatus.java:26`), `IN_TRANSIT`은 `SHIPMENT_STARTED`에서만 갈 수 있다(`:28-29`). `PREPARING → IN_TRANSIT`은 불가.
4. 코드 어디에도 `SHIPMENT_STARTED`로 올리는 곳이 없다(전체 `OrderStatus.` 사용처 확인: OrderCommandService, OrderEventConsumer, OrderShipmentCommandService뿐).

실패 시 동작:
- `Order.updateStatus`가 `InvalidOrderStatusException`("상태 전환이 허용되지 않습니다: PREPARING -> IN_TRANSIT") 발생 — `Order.java:116-119`.
- `updateTrackingInfo`의 `catch (Exception e)`가 잡아 `ShipmentException(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")`로 감싸 던진다 — `OrderShipmentCommandService.java:293-302` (`ShipmentErrorCode.java:12`).
- **저장되는 것: 없음.** 메서드가 `@Transactional`(`:238`)이고 런타임 예외가 밖으로 나가므로 롤백된다. 2단계에서 바꾼 shipment의 courier/trackingNumber/`IN_TRANSIT`도 DB에 남지 않고 shipment는 `PENDING`, 운송장 null 그대로다. 4단계 알림은 3단계 뒤에 있으므로 생성되지도 않는다.
- **응답:** `GlobalExceptionHandler.handleShipmentException`(`B/global/exception/GlobalExceptionHandler.java:459-473`)이 HTTP **404**, body `ErrorResponse{code:"S001", message:"배송 정보를 찾을 수 없습니다.", status:404, path:"/shipments/order/{id}/status"}`를 돌려준다. 예외 메시지가 아니라 ErrorCode의 고정 메시지가 body에 들어간다(`:467-471`). 컨트롤러의 "업데이트 완료" 로그와 200 응답(`Controller:47-48`)에는 도달하지 못한다.
- 추가로, 3단계가 통과했더라도 5단계의 `saleBidQueryService.findByOrderId`는 SaleBid가 없으면 `null`이 아니라 `IllegalArgumentException`을 던진다(`B/domain/sale/service/query/SaleBidQueryService.java:26-28`). 일반 입찰 주문엔 SaleBid가 연결되지 않으므로(`SaleBid.assignOrder`는 즉시 구매 경로에서만 호출됨 — `OrderCommandService.java:279`) `updateSaleStatusToSold` 첫 줄(`OrderShipmentCommandService.java:116`)에서도 어차피 실패한다. `if (saleBid != null)` 방어 코드(`:117`)는 사실상 도달 불가.

## 2. 배송 완료 감지

### 2-1. 누가·언제·어떻게
- **스케줄러:** `ShipmentBatchScheduler.scheduleShipmentStatusJob()` — `B/global/config/ShipmentBatchScheduler.java:34-44`.
- **주기:** `@Scheduled(cron = "0 0 */6 * * *")` → 매일 00:00, 06:00, 12:00, 18:00(서버 타임존 기준), 6시간마다 — `:34`. 실행마다 `timestamp` 파라미터를 달리해 `jobLauncher.run(updateShipmentStatusesJob, …)`(`:37-40`). 실패는 `printStackTrace`만 한다(`:41-43`).
- **잡 구성:** `UpdateShipmentStatusesJobConfig` — Job `updateShipmentStatusesJob`(`:54-60`), Step 청크 크기 50(`:51,67`), faultTolerant + `skip(Exception.class)` + `skipLimit(50)`(`:75-77`).

### 2-2. 조회 대상
- Reader `JpaPagingItemReader`: `SELECT s FROM OrderShipment s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL`, pageSize 50 — `UpdateShipmentStatusesJobConfig.java:87-97`.
- 즉 `PENDING`/`DELIVERED` 등은 조회되지 않는다. (1-3에서 보듯 운송장 등록 API가 일반 주문에서 롤백되므로 해당 shipment는 `PENDING`으로 남아 대상이 되지 않는다. 대상이 되려면 `check-status` API 등으로 `IN_TRANSIT`이 커밋돼 있어야 한다 — 4절 참고.)

### 2-3. 실제로 실행되는 처리 코드
- Step이 `.processor(new ShipmentItemProcessor(playwrightBrowserManager(), notificationService, orderService))`를 사용 — `UpdateShipmentStatusesJobConfig.java:69-73`. **실제 실행 코드는 `B/domain/shipment/config/ShipmentItemProcessor.java:57-` (`process`)**이다.
- 같은 파일 안의 `@Bean @StepScope shipmentItemProcessor()`(`UpdateShipmentStatusesJobConfig.java:104-177`)와 `parseCjLogisticsStatus`(`:186-220`)는 Step에 연결되지 않아 **실행되지 않는다**(Step은 빈이 아니라 `new`로 만든 프로세서를 쓴다).
- `OrderShipmentCommandService.updateShipmentStatuses()`(`:308-366`)는 호출하는 곳이 없다(프로젝트 전체 검색 결과 정의부만 존재) → 미사용.
- `ShipmentItemProcessor.process` 흐름: 운송장 null/blank → `TRACKING_NUMBER_INVALID`(`:59-64`) → `browserManager.newPage()`로 Playwright 페이지 생성 → `https://trace.cjlogistics.com/next/tracking.html?wblNo=<번호>` 이동 → `tbody#statusDetail tr` 대기 → HTML 파싱, **마지막 행의 5번째 td 텍스트**를 상태로 사용(`:167-185`, 마지막 행 `:181`) → 현재 상태와 같으면 변경 없이 반환(`:100-105`) → 분기 처리(`:108-127`).
- (참고) 즉시 조회 API `updateAndCheckShipmentStatus`는 `CjTrackingPlaywright.getCurrentTrackingStatus`(`B/global/utils/CjTrackingPlaywright.java:32`)를 쓴다.

### 2-4. 택배사 상태 문자열 → 내부 상태
`ShipmentItemProcessor.mapToShipmentStatus` — `ShipmentItemProcessor.java:220-226`:
- `"배송완료"` → `ShipmentStatus.DELIVERED`
- `"배송출발"` → `ShipmentStatus.OUT_FOR_DELIVERY`
- 그 외 모든 문자열(null이 아닌 한) → `ShipmentStatus.IN_TRANSIT` (default)
- (null이면 `switch`에서 NPE.) 같은 매핑이 `OrderShipmentCommandService.java:399-405`에도 복제돼 있다.
- 분기: DELIVERED → 3절 처리, OUT_FOR_DELIVERY → `shipment.updateStatus(OUT_FOR_DELIVERY)`(`:119-121`), 그 외 → `updateStatus(IN_TRANSIT)`(`:123-125`). `OrderShipment.updateStatus`는 `ShipmentStatus.canTransitionTo`로 검증한다(`OrderShipment.java:47-55`). `DELIVERED`가 가능한 직전 상태는 `IN_TRANSIT`, `OUT_FOR_DELIVERY`(`ShipmentStatus.java:15-16,21-22`); `OUT_FOR_DELIVERY → IN_TRANSIT`은 불가라 택배사 문구가 "배송출발"에서 다른 문구로 돌아가면 `IllegalStateException`이 난다(`ShipmentStatus.java:21-23`).

## 3. 배송 완료 판정 이후 (`ShipmentItemProcessor.java:108-117`)

순서:
1. **OrderShipment** → `DELIVERED` (`orderShipment.updateStatus(DELIVERED)`, `:113`). 메모리상 변경이며 청크 Writer(`JpaItemWriter`, `UpdateShipmentStatusesJobConfig.java:239-246`)가 저장.
2. `orderService.completeOrder(orderId)` (`:116`) → `OrderShipmentCommandService.completeOrder` (`:191-229`):
   1. `orderBidQueryService.findByOrderId`로 OrderBid 조회, 없으면 `IllegalArgumentException`(`:196-197`).
   2. **Order** → `COMPLETED` (`:204`).
   3. `updateSaleStatusToSold(orderId)` (`:208`): SaleBid → Sale `SOLD` + 판매자 알림, OrderBid.sale → `SOLD` + 판매자 알림 (각 조건: `Sale.status.canTransitionTo(SOLD)` — `SaleStatus.java:21-22`는 `ON_AUCTION`/`SELLING`에서만 허용, 이미 `SOLD`면 건너뜀).
   4. **구매자 알림** "[completeOrder] 주문이 완료 처리되었습니다. 주문 ID: …" (`:211-216`).
   5. 어떤 예외든 `ShipmentException(ORDER_NOT_FOUND_FOR_SHIPMENT)`로 감싸 던짐(`:220-228`).
3. `notificationService.notifyShipmentCompleted(order)` (`:117`) → **구매자 알림** "[배송 완료] 상품이 배송 완료되었습니다. 주문 ID: …" (`B/domain/notification/service/command/NotificationCommandService.java:219-234`).
4. `shipment` 반환 → Writer가 저장.

알림 수:
- **구매자: 2건** ("[completeOrder] 주문이 완료 처리되었습니다" + "[배송 완료] 상품이 배송 완료되었습니다").
- **판매자: 0~2건.** `updateSaleStatusToSold`에서 Sale이 아직 `SOLD`가 아니고 전이 가능할 때만 발송. 즉시 구매 주문에서는 결제 시점에 이미 `SOLD`라(`PaymentCommandService.java:404`) 0건이다(4절).

주문 입찰·판매 입찰 상태:
- 배송 완료 처리 경로(`completeOrder`)는 `updateOrderAndSaleBidStatusToCompleted`를 **호출하지 않는다**(그 메서드는 운송장 등록 경로 `:289`에서만 호출). 따라서 OrderBid·SaleBid의 `status`는 **변경되지 않는다**(`MATCHED` 그대로, `COMPLETED`로 안 감). 이름("주문 완료")과 달리 입찰 상태는 건드리지 않는다.
- 바뀌는 것은 Sale 상태(`SOLD`, 조건부)와 Order(`COMPLETED`)뿐이다.

## 4. 주문 종류별 차이

### (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문 — **끝까지 진행되지 않는다**
- 상태: Order `PREPARING`(`OrderCommandService.java:175-176`), OrderBid `MATCHED`(`OrderBid.assignOrder`가 생성 직후 MATCHED로 만듦 — `OrderBid.java:60-76`), 연결된 SaleBid 없음, Sale은 판매자 매칭 전이면 null.
- `completeOrder`의 `order.updateStatus(COMPLETED)`(`OrderShipmentCommandService.java:204`)가 `PREPARING → COMPLETED` 불가(`OrderStatus.java:26`)라 `InvalidOrderStatusException` → `ShipmentException(ORDER_NOT_FOUND_FOR_SHIPMENT)`(`:220-228`)로 실패한다. 이 시점에는 어떤 알림도 아직 만들어지지 않았다(알림 발송은 `:208` 이후).
- 도달 경로 자체도 제한적이다: 운송장 등록 API는 롤백되므로 shipment가 배치 대상이 되려면 `check-status` API가 `IN_TRANSIT`을 커밋해야 한다. 그 API(`:452-516`)는 shipment만 `IN_TRANSIT`으로 두고 Order는 건드리지 않는다(`:473`). 그 뒤 배치에서 "배송완료"가 나오면 위 실패가 발생한다.
  - `check-status` 단계에서 바로 "배송완료"가 나오면 `shipment.updateStatus(DELIVERED)`(`:486`) 후 `completeOrder`(`:489`)가 같은 이유로 실패 → 롤백 → 컨트롤러가 `ShipmentException`을 잡아 본문 없이 상태코드만 반환(`Controller:80-86`, code 404).
- 결과: shipment는 `IN_TRANSIT`(또는 `OUT_FOR_DELIVERY`)에 영구히 남고, Order `PREPARING`, OrderBid `MATCHED`, 알림 0건. 배치는 6시간마다 같은 건을 다시 조회해 같은 실패(skip)를 반복한다.

### (b) 즉시 구매로 만들어진 주문 — **배송 완료 처리(3절)가 끝까지 진행된다**
- 생성: `createInstantOrder`가 Order를 `PENDING_PAYMENT`로 만들고(`OrderCommandService.java:244`), 배송 정보 `PENDING` 생성, `saleBid.assignOrder(order)`로 SaleBid `MATCHED`(`:279-281`), 결제 처리(`:305`). 결제 서비스는 OrderBid가 아직 없어 SaleBid로 Sale을 찾아 `SOLD`로 바꾸고 구매자/판매자에게 "결제 완료" 알림(`PaymentCommandService.java:388-407,434-458`). 이후 `OrderBidCommandService.createInstantOrderBid`가 OrderBid(`MATCHED`, sale 연결, 즉시구매 플래그)를 만든다(`OrderBidCommandService.java:133,189-206`). 이 흐름은 Order를 `PENDING_PAYMENT`에서 올리지 않는다.
- `completeOrder`: OrderBid 존재 ✔ → `PENDING_PAYMENT → COMPLETED`는 허용(`OrderStatus.java:24`) ✔ → `updateSaleStatusToSold`: SaleBid 있음, Sale은 이미 `SOLD`라 `canTransitionTo(SOLD)`가 false(`SaleStatus.java:23`) → 판매자 알림·상태 변경 없음 → 구매자 알림 발송.
- 결과: OrderShipment `DELIVERED`, Order `COMPLETED`, Sale `SOLD`(결제 때 이미), 구매자 알림 2건, 판매자 알림 0건, OrderBid/SaleBid는 `MATCHED` 유지(`COMPLETED` 아님).
- 단, 배치 대상이 되려면 shipment가 `IN_TRANSIT`/`OUT_FOR_DELIVERY`여야 한다. 운송장 등록 API는 (b)에서도 `PENDING_PAYMENT → IN_TRANSIT`이 `OrderStatus.java:24`에 없어 같은 방식으로 실패(404 S001, 롤백)한다. 즉 (b)도 `check-status` API로 shipment가 `IN_TRANSIT`이 된 경우에만 3절이 실행된다.

| 구분 | Order | Shipment | OrderBid / SaleBid | 구매자 알림 | 판매자 알림 |
|---|---|---|---|---|---|
| (a) 일반 입찰 | `PREPARING` 유지 (COMPLETED 전이 실패) | `IN_TRANSIT` 유지 (롤백/skip) | `MATCHED` / 없음 | 0 | 0 |
| (b) 즉시 구매 | `COMPLETED` | `DELIVERED` | `MATCHED` / `MATCHED` | 2 | 0 |

## 5. 실패 처리 (주기 처리 중 한 건 실패)

실행 중인 쪽은 Spring Batch Step이다(`updateShipmentStatuses()`의 try/catch-continue 방식 `OrderShipmentCommandService.java:322-362`은 쓰이지 않음).

1. `process`의 예외는 `ShipmentException`으로 통일(`ShipmentItemProcessor.java:129-139` 비-ShipmentException은 `EXTERNAL_TRACKING_SERVICE_ERROR`로 래핑)해 던진다. Playwright 페이지는 `finally`에서 닫는다(`:146-155`).
2. Step이 `faultTolerant().skip(Exception.class).skipLimit(50)`이므로(`UpdateShipmentStatusesJobConfig.java:75-77`) 처리 중 예외가 난 건은 **skip**되고 잡은 계속된다. 청크(50건) 트랜잭션이 롤백된 뒤 아이템이 하나씩 다시 처리되며, 실패 건만 건너뛰고 나머지는 정상 처리·저장된다.
3. skip된 건은 `SkipListener.onSkipInProcess`가 에러 로그만 남기고(`:251-266`) DB에는 아무 변경도 반영되지 않는다. 롤백되었으므로 shipment 상태/운송장 그대로이며 다음 주기(6시간 후)에 다시 조회 대상이 된다.
4. `completeOrder` 내부 예외(a의 경우)도 같은 방식으로 skip된다. 단, `completeOrder`가 `@Transactional`로 같은 트랜잭션에 참여해 rollback-only가 되므로 그 청크 전체가 롤백되고 재처리 과정에서 개별 처리된다.
5. skip이 50건을 초과하면 Step이 `SkipLimitExceededException`으로 실패하고 잡이 중단되어, 이후 청크는 해당 실행에서 처리되지 않는다. 스케줄러는 예외를 `printStackTrace`로만 처리하며(`ShipmentBatchScheduler.java:41-43`) 다음 6시간 주기를 기다린다.
6. 알림 생성 자체 실패는 `notifyShipmentCompleted`가 내부에서 로그만 남기고 삼킨다(`NotificationCommandService.java:230-233`).
