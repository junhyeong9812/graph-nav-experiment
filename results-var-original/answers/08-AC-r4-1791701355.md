# 구매자 배송: 운송장 등록 ~ 배송 완료 처리 분석

경로 약어 (모두 `src/main/java/com/fream/back/` 아래):
- `SVC` = `domain/shipment/service/command/OrderShipmentCommandService.java`
- `CTRL` = `domain/shipment/controller/command/OrderShipmentCommandController.java`
- `PROC` = `domain/shipment/config/ShipmentItemProcessor.java`
- `JOB` = `domain/shipment/config/UpdateShipmentStatusesJobConfig.java`
- `SCHED` = `global/config/ShipmentBatchScheduler.java`
- 상태 전이 규칙: `domain/order/entity/OrderStatus.java`, `domain/shipment/entity/ShipmentStatus.java`, `domain/sale/entity/SaleStatus.java`

## 사전: 결제·배송 처리 후 Order·Shipment 상태 (이후 모든 답의 전제)

- 결제·배송 정보 입력 API는 `POST /orders/{orderId}/process-payment-shipment`이며 Kafka 이벤트를 발행한다 (`domain/order/controller/command/OrderCommandController.java:43`, `:54`). 컨슈머가 `processCompleteOrder`에서 `OrderShipment`를 `PENDING`으로 만든다 (`domain/order/service/kafka/OrderEventConsumer.java:181`, `SVC:67`).
- 실배송(비창고)이면 Order는 `PAYMENT_COMPLETED` → `PREPARING`에서 멈춘다 (`OrderEventConsumer.java:195`, `:216-217`). 동기 버전도 같다 (`domain/order/service/command/OrderCommandService.java:175-176`).
- `OrderStatus.SHIPMENT_STARTED`를 세팅하는 코드는 어디에도 없다. grep 결과 `OrderQueryController.java:207`의 표시용 문자열뿐이다.
- 즉시 구매 주문(`createInstantOrder`)은 Order를 `PENDING_PAYMENT`로 만들고(`OrderCommandService.java:244`) 그 뒤로 상태를 바꾸지 않는다. `OrderShipment`(PENDING)는 이때 바로 생성된다 (`OrderCommandService.java:264-271`).
- 즉시 구매에서만 `SaleBid.order`가 연결된다 (`OrderCommandService.java:279` `saleBid.assignOrder(order)`).
- 즉시 구매 `OrderBid`는 `MATCHED`, `sale`을 가지며 `isInstantPurchase=true`이다 (`domain/order/service/command/OrderBidCommandService.java:137-146`).
- 일반 구매 입찰의 `OrderBid`는 `Order`와 연결될 때 `MATCHED`가 되고 `SaleBid`와는 연결되지 않는다 (`OrderBid.java` `assignOrder`).

## 1. 운송장 등록 요청

### 1-1. 어느 API인가
- `PATCH /shipments/order/{shipmentId}/status`, 본문 `OrderShipmentRequestDto`(courier, trackingNumber). `CTRL:20`, `CTRL:33-49`.
- 컨트롤러는 `OrderShipmentCommandService#updateTrackingInfo`(`SVC:239`)를 호출한다.
- 컨트롤러에 권한 검사 코드는 없다.
- 같은 서비스를 쓰는 즉시 조회형 API도 있다: `POST /shipments/order/{id}/check-status`, `/check-status-string` (`CTRL:58`, `CTRL:103`). 이 둘은 `updateAndCheckShipmentStatus`(`SVC:452`)를 호출하며 아래 1-2의 경로와 별개이다.

### 1-2. 어떤 엔티티가 어떤 순서로 바뀌도록 짜여 있나 (설계 의도)
`SVC:239-303` 순서:
1. courier/trackingNumber가 비어 있으면 `TRACKING_INFO_REQUIRED` (`SVC:243-246`).
2. `OrderShipment` 조회 후 `updateTrackingInfo(courier, trackingNumber)` 호출. 택배사·운송장을 세팅하고 상태를 전이 검사 없이 `IN_TRANSIT`으로 직접 대입한다 (`SVC:256`, `domain/shipment/entity/OrderShipment.java:41-44`).
3. `Order.updateStatus(OrderStatus.IN_TRANSIT)` (`SVC:260`). 이 메서드는 전이 규칙을 검사한다 (`domain/order/entity/Order.java:113-121`).
4. 구매자에게 알림 "상품이 출발하였습니다. 주문 ID: …" (`SVC:266-271`).
5. `updateSaleStatusToSold(orderId)` (`SVC:276`):
   - `Sale` → `SOLD` (`SVC:123`, `:160`). 배송 출발 시점에 판매 완료로 바꾸는 설계이다.
   - 창고 보관 Sale이면 `WarehouseStorage` → `SOLD` (`SVC:126-129`).
   - 판매자에게 알림 "상품이 성공적으로 판매 완료되었습니다…" (`SVC:133-138`, `:164-169`).
6. 창고 보관 Sale이면 `updateWarehouseStatusToSold`를 한 번 더 호출한다 (`SVC:279-286`).
7. `updateOrderAndSaleBidStatusToCompleted` (`SVC:289`, `SVC:413-440`): `OrderBid` MATCHED→COMPLETED, `SaleBid` MATCHED→COMPLETED. 이 메서드의 예외는 삼키고 로그만 남긴다 (`SVC:436-439`).

의도된 순서를 요약하면 OrderShipment(IN_TRANSIT) → Order(IN_TRANSIT) → 구매자 알림 → Sale(SOLD)/창고(SOLD) → 판매자 알림 → OrderBid/SaleBid(COMPLETED)이다.
- 이름은 "운송장 등록"이지만 실제로는 판매 완료와 입찰 완료까지 한 번에 처리한다.
- 배송 완료가 아닌 출발 시점에 OrderBid와 SaleBid가 COMPLETED가 된다.

### 1-3. 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문에서 끝까지 성공하나
**성공하지 않는다.** `SVC:260`에서 실패한다.

- 이 주문의 Order 상태는 `PREPARING`이다 (사전 항목 참고).
- `PREPARING`에서 허용되는 다음 상태는 `IN_WAREHOUSE`, `SHIPMENT_STARTED`뿐이다 (`OrderStatus.java:26`). `IN_TRANSIT`은 `SHIPMENT_STARTED`에서만 갈 수 있다 (`OrderStatus.java:28`).
- `Order.updateStatus`가 `InvalidOrderStatusException("상태 전환이 허용되지 않습니다: PREPARING -> IN_TRANSIT")`을 던진다 (`Order.java:113-121`).
- `SVC:295`의 `catch (Exception e)`가 이를 받아 `ShipmentException(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")`로 감싸 던진다 (`SVC:295-301`). 이 코드는 `ShipmentException`만 그대로 통과시키므로(`SVC:293`) 래핑된다.

**무엇이 저장되나: 아무것도 저장되지 않는다.**
- 메서드 전체가 `@Transactional`(`SVC:238`)이고 런타임 예외가 밖으로 나가므로 롤백된다.
- 2단계에서 메모리상 바꾼 courier/trackingNumber/`IN_TRANSIT`도 DB에 반영되지 않는다. 배송은 `PENDING`에 운송장 없음 그대로이다.
- 4단계(구매자 알림)는 3단계 뒤라서 실행조차 되지 않는다. 알림 서비스는 같은 트랜잭션에 참여하는 `@Transactional` 클래스라(`domain/notification/service/command/NotificationCommandService.java:27`) 별도로 커밋되지도 않는다.

**응답:**
- `GlobalExceptionHandler#handleShipmentException` (`global/exception/GlobalExceptionHandler.java:459-473`)가 처리한다.
- HTTP **404**, `ErrorResponse`(code `S001`, message "배송 정보를 찾을 수 없습니다.", status 404, 요청 URI)이다 (`domain/shipment/exception/ShipmentErrorCode.java` `SHIPMENT_NOT_FOUND`).
- 응답 메시지는 에러코드의 고정 메시지이다. 실제 원인(상태 전환 불가)은 응답에 나오지 않고 로그에만 남는다. 에러 코드 이름도 실제 원인과 맞지 않는다.

덧붙임:
- (b)의 즉시 구매 주문도 Order가 `PENDING_PAYMENT`이고 `PENDING_PAYMENT`→`IN_TRANSIT`은 허용되지 않아(`OrderStatus.java:24`) 같은 지점에서 실패한다.
- 설령 Order 전이가 통과해도 `SaleBidQueryService#findByOrderId`는 없으면 null이 아니라 `IllegalArgumentException`을 던진다 (`domain/sale/service/query/SaleBidQueryService.java:26-28`). 따라서 SaleBid가 order에 연결되지 않은 주문은 `SVC:116`에서 실패한다. 이 호출은 try 밖이라 `SVC:295`에서 마찬가지로 래핑된다.
- 창고 보관 Sale이면 `SVC:128`과 `SVC:284`에서 창고 SOLD 처리를 두 번 하는데, 두 번째는 `SOLD`에서 `InvalidStatusTransitionException`이 날 수 있는 구조이다 (`WarehouseStorageCommandService#updateWarehouseStatusToSold`의 `SOLD` 검사).
- 결과적으로 `SHIPMENT_STARTED`가 세팅되지 않는 한 이 PATCH API는 정상 경로로는 성공할 수 없다.

## 2. 배송 완료 감지

### 2-1. 누가, 언제, 어떻게
- **누가:** Spring Batch 잡 `updateShipmentStatusesJob`을 스케줄러가 돌린다. `SCHED:34-40`에서 `jobLauncher.run(updateShipmentStatusesJob, …)`을 호출한다 (`JOB:54-60`).
- **어떻게:** 운송장 번호로 CJ대한통운 추적 페이지(`https://trace.cjlogistics.com/next/tracking.html?wblNo=…`)를 Playwright로 열어 `tbody#statusDetail tr`의 마지막 행 5번째 `td` 텍스트를 읽는다 (`PROC:94`, 파싱 `PROC:167-190`).
- 사용자 API로 즉시 조회하는 경로(`check-status`)는 별도로 있다 (1-1 참고).

### 2-2. 주기, 대상, 실제 실행 코드
- **주기:** `@Scheduled(cron = "0 0 */6 * * *")` = 매일 00·06·12·18시 정각, 6시간마다 (`SCHED:34`).
  - 잡 파라미터에 현재 시각을 넣어 매번 새 JobInstance로 실행한다 (`SCHED:37-39`).
  - 예외는 `printStackTrace`만 한다 (`SCHED:41-43`).
- **대상:** `SELECT s FROM OrderShipment s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL` (`JOB:95`). 청크 크기와 pageSize는 50 (`JOB:51`, `JOB:67`).
- **실제로 실행되는 처리 코드는 `ShipmentItemProcessor`(`PROC`)이다.** 근거: `JOB:69-73`의 `.processor(new ShipmentItemProcessor(playwrightBrowserManager(), notificationService, orderService))`.
- 비슷하지만 실행되지 않는 코드:
  1. `JOB:106`의 `@Bean shipmentItemProcessor()`(람다, `CjTrackingPlaywright` 사용)는 Step에 연결되지 않는다. Step은 `shipmentItemProcessor()`를 호출하지 않는다.
  2. `SVC:309`의 `updateShipmentStatuses()`는 프로젝트 전체에서 호출하는 곳이 없다 (grep). 이 메서드는 DELIVERED일 때 `order.updateStatus(COMPLETED)`를 직접 하는 또 다른 구현이다.
  3. `JOB:186`의 `parseCjLogisticsStatus`(Jsoup 직접 연결)는 private이고 사용처가 없다.
- 브라우저는 Step 시작/종료 때 `BrowserManageStepListener`가 열고 닫는다 (`JOB:80`, `domain/shipment/config/BrowserManageStepListener.java:14-25`).

### 2-3. 택배사 상태 문자열 → 내부 상태
`PROC:220-226` `mapToShipmentStatus`:
- `"배송완료"` → `DELIVERED`
- `"배송출발"` → `OUT_FOR_DELIVERY`
- 그 외 모든 문자열(null이 아닌 것) → `IN_TRANSIT` (`default`)

정확히 일치(equals)하는 문자열만 매핑되고 trim은 파서에서 한다 (`PROC:181`). 매핑 결과가 현재 상태와 같으면 변경 없이 그대로 반환한다 (`PROC:101-105`).

주의: 현재 `OUT_FOR_DELIVERY`인데 택배사가 다른 문자열을 주면 `IN_TRANSIT`으로 매핑된다. `OUT_FOR_DELIVERY`→`IN_TRANSIT`은 허용되지 않아(`ShipmentStatus.java:23-26`) `IllegalStateException`이 나고, 이는 `EXTERNAL_TRACKING_SERVICE_ERROR`로 감싸져 해당 건이 skip된다 (`PROC:133-148`).

## 3. 배송 완료 판정 이후 (실제 실행 경로 `PROC`)

`PROC:110-118`, newStatus가 `DELIVERED`일 때:
1. `OrderShipment.updateStatus(DELIVERED)` (`PROC:113`). `IN_TRANSIT`과 `OUT_FOR_DELIVERY`에서는 허용된다 (`ShipmentStatus.java:16-22`).
2. `OrderShipmentCommandService#completeOrder(orderId)` (`PROC:116`, `SVC:191-229`):
   - `OrderBid`를 `orderId`로 조회하고 없으면 예외 (`SVC:196-197`).
   - `Order.updateStatus(COMPLETED)` (`SVC:204`).
   - `updateSaleStatusToSold(orderId)` (`SVC:208`):
     - SaleBid의 Sale이 `SOLD`로 전이 가능하면 Sale → `SOLD`, 창고 Sale이면 창고도 `SOLD`로 바꾸고 판매자에게 알림을 보낸다 (`SVC:116-141`).
     - 이어서 OrderBid의 Sale에 대해 같은 처리를 한다 (`SVC:150-176`). 이미 SOLD이면 `canTransitionTo`가 false이므로 중복 알림은 없다 (`SaleStatus.java:23`).
   - 구매자 알림 "[completeOrder] 주문이 완료 처리되었습니다. 주문 ID: …" (`SVC:212-217`).
3. `NotificationCommandService#notifyShipmentCompleted(order)`로 구매자에게 "[배송 완료] 상품이 배송 완료되었습니다. 주문 ID: …" 알림 (`PROC:117`, `NotificationCommandService.java:219-230`). 이 메서드는 예외를 삼킨다.
4. 청크 종료 시 `JpaItemWriter`가 OrderShipment를 반영한다 (`JOB:243-245`).

### 상태 변경 순서
OrderShipment `DELIVERED`(메모리) → Order `COMPLETED` → Sale `SOLD`(전이 가능할 때) → (창고 Sale이면) WarehouseStorage `SOLD` → 알림들 → 청크 커밋 시 OrderShipment 저장.

### 알림 건수
- **구매자: 2건.** "[completeOrder] 주문이 완료 처리되었습니다"(`SVC:212`)와 "[배송 완료] …"(`PROC:117`).
- **판매자: 0 또는 1건.** Sale이 `SOLD`로 전이 가능할 때만 1건이다 (`SVC:119-138`). Sale은 생성 시 `PENDING_SHIPMENT`이고(`domain/sale/service/command/SaleCommandService.java:108`), `SOLD`는 `ON_AUCTION`·`SELLING`에서만 갈 수 있다 (`SaleStatus.java:21-22`). 그 외 상태면 아무 알림 없이 `log.debug`만 남기고 넘어간다 (`SVC:142-144`).

### 주문 입찰·판매 입찰의 상태
- **변하지 않는다.** 배치 경로(`completeOrder`)는 `updateOrderAndSaleBidStatusToCompleted`를 호출하지 않는다 (`SVC:191-229`에 호출 없음. 호출처는 `SVC:289`의 `updateTrackingInfo`뿐이다).
- 따라서 `OrderBid`와 `SaleBid`는 `MATCHED`로 남는다.
- 이름("completeOrder")과 달리 입찰은 COMPLETED가 되지 않는다. 입찰 COMPLETED 처리는 1-2의 PATCH 경로에만 있고 그 경로는 1-3에서 보듯 실패한다.

## 4. 주문 종류별 차이

### (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문: 끝까지 진행되지 않는다
- Order가 `PREPARING`이다. 배치가 이 배송을 읽으려면 배송이 `IN_TRANSIT`/`OUT_FOR_DELIVERY`여야 하는데, 그 상태는 `check-status` API가 운송장을 세팅할 때 얻는다 (`OrderShipment.java:41-44`). 이 경로는 Order 상태를 건드리지 않는다.
- 택배사가 "배송완료"를 주면 `PROC:113`에서 배송이 `DELIVERED`가 된 뒤 `completeOrder`가 `SVC:204`의 `Order.updateStatus(COMPLETED)`에서 막힌다. `PREPARING`→`COMPLETED`는 허용되지 않는다 (`OrderStatus.java:26`).
- `InvalidOrderStatusException`은 `SVC:221-228`에서 `ShipmentException(ORDER_NOT_FOUND_FOR_SHIPMENT)`으로 감싸져 나가고, 그 앞에서 Order에 한 일은 없다. 이 시점까지 알림은 하나도 만들어지지 않았다.
- 결과: 청크 트랜잭션이 롤백되고 그 건은 skip된다. OrderShipment는 DB에서 `IN_TRANSIT`/`OUT_FOR_DELIVERY` 그대로, Order는 `PREPARING`, 알림 0건, OrderBid/SaleBid 변화 없음이다. 6시간 뒤 같은 건이 다시 조회되고 다시 실패한다.
- 부가: Order 전이가 통과하더라도 일반 구매 입찰은 SaleBid가 order에 연결되지 않으면 `SVC:116`에서 `IllegalArgumentException`("해당 Order에 연결된 SaleBid가 없습니다")이 발생한다 (`SaleBidQueryService.java:26-28`).
- `check-status` API로 "배송완료"가 즉시 조회되는 경우도 같은 `completeOrder`(`SVC:489`)에서 같은 예외가 나고 롤백된다. 컨트롤러는 404를 빈 본문으로 돌려준다 (`CTRL:80-86`).

### (b) 즉시 구매로 만들어진 주문: 끝까지 진행된다
- Order가 `PENDING_PAYMENT`이고 `PENDING_PAYMENT`→`COMPLETED`가 허용된다 (`OrderStatus.java:24`). 그래서 `SVC:204`를 통과한다.
- `SaleBid.order`가 연결되어 있어 `findByOrderId`가 성공하고 (`OrderCommandService.java:279`), `OrderBid`도 order와 연결되어 있다 (`OrderBidCommandService.java:137-146`).
- 결과: OrderShipment `DELIVERED`, Order `COMPLETED`, 구매자 알림 2건, Sale이 `SELLING`/`ON_AUCTION`이면 `SOLD`(+판매자 알림 1건). OrderBid/SaleBid는 `MATCHED` 그대로이다.
- 의미상으로는 결제 단계(`PAYMENT_COMPLETED`/`PREPARING`)를 거치지 않은 채 `PENDING_PAYMENT`에서 바로 `COMPLETED`로 점프하는 것이다. 이는 전이 맵이 허용해서 통과할 뿐이다.
- 이 주문이 이 지점에 오려면 배송이 `IN_TRANSIT`이어야 하는데, 이는 1-3에서 설명했듯 `check-status` API를 통해서만 얻을 수 있다 (PATCH 경로는 `PENDING_PAYMENT`→`IN_TRANSIT`이 막혀 실패한다).

## 5. 실패 처리 (주기 처리 중 한 건이 실패할 때)

실제 실행 경로(Spring Batch Step) 기준:
- Step은 `.faultTolerant().skip(Exception.class).skipLimit(50)`이다 (`JOB:75-77`). 청크 크기는 50 (`JOB:67`).
- processor가 던진 예외(`ShipmentException` 등)는 skip 대상이다.
  - 청크 트랜잭션이 롤백된 뒤, Spring Batch가 해당 청크를 항목 단위로 다시 처리하며 실패한 항목만 건너뛴다. 이는 `faultTolerant` 청크 처리의 기본 동작이다.
  - 실패 건은 `SkipListener#onSkipInProcess`가 로그만 남긴다 (`JOB:255-264`).
  - 나머지 건은 정상 처리되어 커밋된다.
- 실패한 건은 상태가 바뀌지 않고 `IN_TRANSIT`/`OUT_FOR_DELIVERY`로 남아 다음 주기(6시간 후)에 다시 조회된다. 재시도 큐나 실패 상태는 없다.
- 운송장 번호가 비어 있거나(`PROC:61-64`), 페이지 생성 실패(`PROC:74`), 파싱 실패, 조회 오류, 상태 전이 위반은 모두 `ShipmentException`으로 던져져 같은 방식으로 skip된다 (`PROC:133-148`).
- 한도: skip이 Step 실행당 50건을 넘으면 잡 전체가 실패하고 남은 건은 그 실행에서 처리되지 않는다. 예를 들어 (a) 유형이 50건 넘게 쌓이면 이 문제가 생긴다.
- 알림 생성 실패는 `notifyShipmentCompleted`가 삼키므로 배송 완료 처리 자체는 계속된다 (`NotificationCommandService.java:219-230`). `completeOrder` 안의 `createNotification`은 삼키지 않아 실패하면 `completeOrder`가 실패한다 (`SVC:221-228`).

참고(실행되지 않는 `SVC#updateShipmentStatuses`): 건별 try/catch로 실패를 세고 계속 진행하는 구조이다 (`SVC:322-388`). 그러나 호출되는 곳이 없어 실제 동작과는 무관하다.
