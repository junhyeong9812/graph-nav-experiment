# 즉시 구매 처리 흐름 (구매자 → 판매 입찰 즉시 구매)

경로 표기: `D` = `src/main/java/com/fream/back/domain`

## 1. 진입 API, 처리 단계, 동기/비동기, 응답 ID

**진입점**: `POST /order-bids/instant` (`@RequestMapping("/order-bids")` + `@PostMapping("/instant")`).
- `D/order/controller/command/OrderBidCommandController.java:89-90`
- 요청 DTO `InstantOrderRequestDto`: saleBidId, addressId, warehouseStorage, paymentRequest — `D/order/dto/InstantOrderRequestDto.java:20-29`

**처리 단계 (전부 한 요청 스레드, 한 트랜잭션 안에서 동기 처리)**

1. 컨트롤러: 이메일 추출 후 결제 요청에 `userEmail` 설정, `orderId=null` 로 초기화 — `OrderBidCommandController.java:92, 98, 119-123`
2. `OrderBidCommandService#createInstantOrderBid` (`@Transactional`) — `D/order/service/command/OrderBidCommandService.java:118-149`
   - 입력값 검증(이메일/saleBidId/addressId/paymentRequest null 체크) — `:154-167`, `:123`
   - 구매자 조회 — `:126`
   - SaleBid 조회, 연결된 Sale 존재 검증 — `:129-130`, `:172-184`
3. `OrderCommandService#createInstantOrder` (`@Transactional`) — `D/order/service/command/OrderCommandService.java:219-319`
   - 주소 조회 `:238` → Order 저장 `:241-247` → `paymentRequest.setOrderId(order.getId())` `:250` → OrderItem `:255-256` → OrderShipment `:264-271` → SaleBid 매칭 + `flush` `:279-283` → (판매자 창고) 창고 상태 변경 `:290-301` → 결제 `:305`
4. 결제 `PaymentCommandService#processPayment` — `D/payment/service/command/PaymentCommandService.java:57-107` (결제 수단별 생성 → 알림/Sale 상태 변경 `:83`)
5. 다시 `OrderBidCommandService` 에서 OrderBid(구매 입찰) 를 만들어 저장 — `OrderBidCommandService.java:142`, `:189-207`

**동기 처리다.** Kafka 발행이 없다. `OrderEventProducer` 는 `/orders` 경로(`OrderCommandController.java:6, 30`)에서만 쓰인다. 즉시 구매 경로는 `OrderEventProducer`/`KafkaTemplate`을 부르지 않는다(위 3~5 호출 사슬 참조). 알림도 같은 스레드에서 DB 저장 + WebSocket 전송한다(4번 항목 참조).

**응답으로 돌려주는 ID는 Order ID 가 아니라 OrderBid ID 다.**
- 서비스가 `OrderBid` 를 반환하고(`OrderBidCommandService.java:119, 142-144`), 컨트롤러가 그 `.getId()` 를 `orderId` 변수에 담아 응답한다 — `OrderBidCommandController.java:101-107`.
- 응답 본문은 `ResponseDto.success(orderId, "즉시 구매가 성공적으로 처리되었습니다.")` — `:109`. 변수명·Javadoc("생성된 주문 ID", `:83`)과 달리 실제 값은 OrderBid PK 다.

## 2. 새로 생기는 엔티티와 상태 변화 순서 (각 단계 직후 값)

사전 상태: 판매자가 `POST /sale-bids` 로 만든 SaleBid `status=PENDING` (`D/sale/service/command/SaleBidCommandService.java:41-47`), 연결된 Sale `status=PENDING_SHIPMENT` (`D/sale/service/command/SaleCommandService.java:101-109`).

| 순서 | 동작 | 직후 상태 | 근거 |
|---|---|---|---|
| ① | **Order 생성·저장** (totalAmount = saleBid.bidPrice) | `Order.status = PENDING_PAYMENT` | `OrderCommandService.java:241-247` |
| ② | **OrderItem 생성** (수량 1, 가격 = bidPrice) | — | `:255-256`, `D/order/service/command/OrderItemCommandService.java:45-52` |
| ③ | **OrderShipment 생성** (주소는 addressId 로 조회한 값) | `OrderShipment.status = PENDING` | `OrderCommandService.java:264-271`, `D/shipment/service/command/OrderShipmentCommandService.java:61-68` |
| ④ | **SaleBid 매칭**: `saleBid.assignOrder(order)` 후 `updateStatus(MATCHED)`, `flush` | `SaleBid.status = MATCHED`, `SaleBid.order = order` | `OrderCommandService.java:279-283`, `D/sale/entity/SaleBid.java:58-61` |
| ⑤ | (Sale.isWarehouseStorage=true 일 때만) 창고 상태를 `ASSOCIATED_WITH_ORDER` 로 변경 시도 | 아래 5번 참조 — 실제로는 예외 | `OrderCommandService.java:290-301` |
| ⑥ | **Payment 생성** (CardPayment / AccountPayment / GeneralPayment) | 수단별로 다름(3번 참조) | `PaymentCommandService.java:157-333` |
| ⑦ | **Sale 판매 완료 처리** + 알림 | `Sale.status = SOLD` | `PaymentCommandService.java:383-420` (SaleBid 경로 `:391-405`) |
| ⑧ | **OrderBid 생성·저장** (구매자, 사이즈, bidPrice=saleBid 가격, order, sale 연결) | `OrderBid.status = MATCHED`, `isInstantPurchase = true` | `OrderBidCommandService.java:189-207` |

세부 사항:
- ⑦ 시점에 `order.getOrderBid()` 는 아직 null 이다(OrderBid 는 ⑧ 에서 생성). 그래서 `saleBidQueryService.findByOrderId(order.getId())` 경로로 SaleBid → Sale 을 찾고 `sale.updateStatus(SOLD)` 한다 — `PaymentCommandService.java:388-405`. ④의 `flush` 덕에 이 조회가 성공한다. `findByOrderId` 는 없으면 `IllegalArgumentException` — `D/sale/service/query/SaleBidQueryService.java:26-28`(이 예외도 `:421-425` 에서 삼켜져 Sale 상태·알림이 조용히 생략됨).
- `Sale.updateStatus` 는 `SaleStatus.canTransitionTo` 검증 없이 값을 덮어쓴다 — `D/sale/entity/Sale.java:73-75`. `PENDING_SHIPMENT → SOLD` 는 규칙상 불허지만(`D/sale/entity/SaleStatus.java:17`) 우회된다. 이 때문에 이후 판매자 발송 등록(`SOLD → IN_TRANSIT`)은 `SaleCommandService#updateSaleStatus` 검증(`:155-157`, `SaleStatus.java:23`)에서 `IllegalStateException` 이 날 수 있다.
- SaleBid 가 아직 `PENDING` 인지 검증하지 않는다. `getSaleBidAndValidate` 는 null/Sale 연결만 확인한다 — `OrderBidCommandService.java:172-184`. 이미 MATCHED 인 입찰도 다시 구매가 가능하다.
- 결제 금액은 서버가 Order 금액으로 대체하지 않고 요청의 `paidAmount`(>0 이면 통과)를 쓴다 — `PaymentCommandService.java:142-145`, `:193`, `:255`, `:308`. Order.totalAmount(`OrderCommandService.java:243`)와 비교하는 로직은 없다.
- Order 에 `assignPayment` 는 호출되지 않는다(Payment 쪽 FK 만 설정: `PaymentCommandService.java:200`, `:258`, `:311`).

## 3. 결제 수단별 결과, 끝까지 성공하는지, 카드사(PG) 실패 응답

수단은 JSON 의 `paymentType` (CARD/ACCOUNT/GENERAL) 으로 정해지고 `getResolvedPaymentType()` 이 분기한다 — `D/payment/dto/PaymentRequestDto.java:20-25, 74-87`, `PaymentCommandService.java:67-80`. 결제 전 검증: orderId 일치(`:131`), 이메일 일치(`:136`), 금액 > 0(`:142`).

| 수단 | Payment 최종 상태 | 외부 호출 | 근거 |
|---|---|---|---|
| **카드(CARD)** | PG 응답 `status=="success"` 일 때만 `PAID`+`isSuccess=true`. 그 외엔 기본값 `PENDING`, `isSuccess=false` 로 **그대로 저장됨** | PortOne `processCardPayment` 호출 | `PaymentCommandService.java:179, 203-208`, 기본값 `D/payment/entity/Payment.java:39, 44` |
| **계좌이체(ACCOUNT)** | 항상 `PENDING` (입금/확인 로직 없음). 은행명만 검증 | 없음 | `PaymentCommandService.java:244, 260-262` |
| **일반(GENERAL)** | 항상 즉시 `PAID`, `isSuccess=true` (impUid 비어있지 않은지만 확인, PG 검증 없음) | 없음 | `PaymentCommandService.java:297-299, 313-314` |

**끝까지 성공하는가**: 세 수단 모두 예외가 없으면 요청은 HTTP 200 "성공" 으로 끝난다. 그러나 "결제 완료"가 보장되지는 않는다.
- 계좌이체는 `PENDING` 인 채로 ⑦ 이 실행되어 Sale 이 `SOLD` 가 되고 "결제가 완료되었습니다" 알림이 나간다 — `PaymentCommandService.java:83, 383-420, 438-443`. 결제 상태와 무관하게 `notifyUsersAndUpdateSaleStatus` 가 무조건 호출된다.
- Order 는 어느 수단이든 `PENDING_PAYMENT` 에서 바뀌지 않는다(5번 참조).

**카드 결제 실패 시 (두 갈래)**
1. **PG 가 최상위 `code != 0`(또는 HTTP != 200) 으로 실패 응답** → `PaymentProcessingException` (`D/payment/portone/PortOneApiClient.java:270-274`) → `PaymentCommandService.java:218-219, 89-94` 로 전파 → `OrderCommandService.java:306-309` 에서 `OrderPaymentProcessingFailedException` 으로 감싸짐 → `:312-314` 재던짐 → `OrderBidCommandService.java:145-146, 212-215` 재던짐. 한 `@Transactional` 이므로 Order/OrderItem/OrderShipment/SaleBid 매칭이 **전부 롤백**되고 클라이언트는 에러 응답을 받는다. 알림·Sale SOLD·OrderBid 는 생성되지 않는다(예외가 그 앞에서 발생).
   - HTTP 오류·통신 오류는 `RestClientException` → `PaymentApiException` (`PortOneApiClient.java:288-290`). `@Retryable(maxAttempts=3)` 이 붙어 있지만(`:224-228`) `@EnableRetry` 선언이 소스 어디에도 없어 재시도는 동작하지 않는다(소스 전체 grep 결과 없음).
2. **PG 가 `code == 0` 이지만 `response.status` 가 "success" 가 아닌 경우(예: failed)** → 예외가 없다. `PaymentCommandService.java:203-206` 의 if 를 건너뛰어 CardPayment 가 `PENDING`/`isSuccess=false` 로 저장된다(`PaymentStatus.FAILED` 로 바뀌지 않음). 이어서 `:83` 알림·`Sale=SOLD` 가 실행되고, OrderBid 가 MATCHED 로 생성되며 응답은 200 "즉시 구매가 성공적으로 처리되었습니다" 이다. 즉 **카드 실패인데 구매가 성사된 것처럼 처리**된다.

## 4. 알림 수신자, 시점, 전달 방식

**수신자 2명, 둘 다 `notifyUsersAndUpdateSaleStatus → sendNotifications` 에서 발송**:
- 구매자(`order.getUser()`): "결제가 완료되었습니다. 주문 ID: {orderId}" — `PaymentCommandService.java:436-443`
- 판매자(`sale.getSeller()`): "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}" — `:447-453`
- 둘 다 `NotificationCategory.SHOPPING`, `NotificationType.BID`.

**시점**: 결제 수단 처리 직후, Sale 을 SOLD 로 바꾸기 직전 — `:83`, `:403`/`:416`. 결제 수단이 PENDING 이어도(계좌이체, 카드 비성공) 발송된다. 카드 결제가 예외로 실패하면 발송되지 않는다.

**방식 (동기, 같은 트랜잭션)**:
1. `NotificationCommandService#createNotification` 이 Notification 을 DB 에 저장 — `D/notification/service/command/NotificationCommandService.java:44-53`
2. 이어서 `sendRealTimeNotification` — Redis 키 `WebSocket:User:{email}` 가 있을 때만 `SimpMessagingTemplate.convertAndSendToUser(email, "/queue/notifications", dto)` 로 WebSocket 푸시 — `:57`, `:303-310`, 상수 `:37-38`. 연결이 없으면 DB 저장만 되고 푸시는 생략(`:316-321`).
3. 전송 실패는 로그만 남기고 삼킨다 — `:311-315`, `PaymentCommandService.java:457-461`. 발송 전체가 try/catch 로 감싸져 예외가 호출자로 전파되지 않는다(`:421-425`).
- Kafka `notification-topic` 은 쓰이지 않는다(그 발행은 `D/order/service/kafka/OrderEventConsumer.java:318, 364` 뿐).
- 이 경로에서 SaleCommandService 의 "구매 입찰에 판매자가 등록되었습니다"(`SaleCommandService.java:82-89`)는 **즉시 판매**(`/sale-bids/instant`) 쪽 알림이므로 해당하지 않는다.

## 5. 최종 주문 상태, 창고 보관 선택 시

**최종 상태 (정상 종료 시)**

| 엔티티 | 최종 값 | 근거 |
|---|---|---|
| Order | **`PENDING_PAYMENT` 그대로** | 즉시 구매 경로 어디서도 `order.updateStatus` 를 호출하지 않음: `OrderCommandService.java:241-245` 이후 `:219-319` 에 호출 없음. 상태를 `PAYMENT_COMPLETED → PREPARING` 으로 올리는 코드는 별도 메서드 `processPaymentAndShipment` (`:112-176`) 이고 이 흐름에서 호출되지 않음 |
| OrderBid | `MATCHED`, `isInstantPurchase=true` | `OrderBidCommandService.java:196, 205` |
| SaleBid | `MATCHED` (order 연결) | `OrderCommandService.java:279-280` |
| Sale | `SOLD` | `PaymentCommandService.java:404/419` |
| OrderShipment | `PENDING` | `OrderShipmentCommandService.java:67` |
| Payment | 카드 성공·일반: `PAID`, 계좌이체·카드 비성공: `PENDING` | 3번 참조 |

메서드명·Javadoc 은 "즉시 구매가 성공적으로 처리"라고 하지만, 주문은 결제가 `PAID` 여도 `PENDING_PAYMENT` 로 남는다.

**"창고 보관" 선택(`warehouseStorage=true`) 시**
- 구매자가 보낸 `warehouseStorage` 값은 컨트롤러 → `OrderBidCommandService` → `createInstantOrder` 파라미터 `isWarehouseStorage` 까지 전달되지만(`OrderBidCommandController.java:105`, `OrderBidCommandService.java:137`, `OrderCommandService.java:220`) **메서드 본문 어디에서도 읽히지 않는다**(`:221-319`). 그래서 구매자 선택은 아무 효과가 없다: 구매자용 `WarehouseStorage` 가 생성되지 않고(`createOrderStorage` 는 `:170`, `OrderEventConsumer.java:199` 에서만 호출), `IN_WAREHOUSE`/`COMPLETED` 로의 주문 상태 변경도 없다. `PAYMENT_COMPLETED → PREPARING → IN_WAREHOUSE → COMPLETED` 시퀀스는 `processPaymentAndShipment` 에만 있다(`OrderCommandService.java:163-172`).
- 실제로 동작에 영향을 주는 것은 **판매자가 입찰 때 지정한 `Sale.isWarehouseStorage`** 뿐이다 — `OrderCommandService.java:291-293`. 이 값이 true 면 `warehouseStorageCommandService.updateWarehouseStatus(sale, ASSOCIATED_WITH_ORDER)` 를 호출한다.
  - 그런데 `updateWarehouseStatus` 는 `findBySale` 로 기존 창고 레코드를 찾고, 없으면 `WarehouseStorageNotFoundException` 을 던진다 — `D/warehouseStorage/service/command/WarehouseStorageCommandService.java:127`, `D/warehouseStorage/service/query/WarehouseStorageQueryService.java:30-32`.
  - 판매 입찰 생성(`SaleCommandService#createSale`, `:95-133`)은 창고 레코드를 만들지 않고, 만드는 메서드 `createSellerStorage`(`WarehouseStorageCommandService.java:74`)는 소스에서 호출하는 곳이 없다.
  - 따라서 판매자가 창고 보관을 선택한 입찰을 즉시 구매하면 `OrderWarehouseStorageProcessingFailedException` 이 발생해(`OrderCommandService.java:295-301`) 결제 이전 단계에서 전체가 롤백된다(결제·알림 없음, 에러 응답).
  - (레코드가 있었다면 `IN_STORAGE → ASSOCIATED_WITH_ORDER` 는 허용 전환이다 — `WarehouseStorageCommandService.java:239-242`.)
- 판매자가 창고 보관을 선택하지 않은 입찰이라면 창고 관련 변화는 전혀 없고, 구매자의 `warehouseStorage=true` 요청도 일반 요청과 결과가 같다.
