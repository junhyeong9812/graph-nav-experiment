# 즉시 구매 처리 흐름 분석

경로 약어: `D` = `src/main/java/com/fream/back/domain`, `G` = `src/main/java/com/fream/back/global`

## 결론 요약

- 즉시 구매는 `POST /order-bids/instant` 하나로 들어와 **동기**로, 한 트랜잭션 안에서 끝까지 처리된다. Kafka 비동기 경로(`/orders/{id}/process-payment-shipment`)는 타지 않는다.
- 응답으로 돌려주는 ID는 변수명(`orderId`)과 달리 **OrderBid 의 ID** 이다. Order ID 가 아니다.
- 처리가 끝난 뒤 Order 상태는 **`PENDING_PAYMENT` 그대로**이다. 결제가 성공해도 `PAYMENT_COMPLETED` 로 바뀌지 않는다.
- 구매자가 보낸 "창고 보관" 플래그는 서버에서 **사용되지 않는다** (로그에만 찍힌다).
- 알림 문구는 "결제가 완료되었습니다"이지만 계좌이체(PENDING)이거나 카드 응답 status 가 success 가 아니어도 똑같이 나간다.

## 1. 진입 API, 처리 단계, 동기/비동기, 응답 ID

**API**
- 클래스 매핑 `@RequestMapping("/order-bids")` — `D/order/controller/command/OrderBidCommandController.java:22`
- `@PostMapping("/instant")` `createInstantOrderBid(@RequestBody @Valid InstantOrderRequestDto)` — `OrderBidCommandController.java:89-90`
- 요청 DTO: `saleBidId`, `addressId`, `warehouseStorage`, `paymentRequest` — `D/order/dto/InstantOrderRequestDto.java:20-29`

**처리 단계 (모두 같은 스레드, 같은 트랜잭션)**
1. 컨트롤러: 이메일 추출(`OrderBidCommandController.java:92`) → 결제 정보 보강. `enrichPaymentRequest` 가 `userEmail` 설정, `orderId=null` 로 초기화 (`:98`, `:119-123`).
2. `OrderBidCommandService.createInstantOrderBid` — `@Transactional` (`D/order/service/command/OrderBidCommandService.java:118-120`).
   - 입력 검증 (`:123`, `:154-167`) → 구매자 조회 (`:126`) → SaleBid/Sale 조회·검증 (`:129-130`, `:172-184`).
3. `OrderCommandService.createInstantOrder` 호출 (`OrderBidCommandService.java:133-139`), 내부 순서 (`D/order/service/command/OrderCommandService.java:219-319`):
   1. 배송지 조회 `addressQueryService.getAddress` (`:238`)
   2. Order 생성·저장, `PENDING_PAYMENT` (`:241-247`)
   3. `paymentRequest.setOrderId(order.getId())` (`:250`)
   4. OrderItem 생성 (`:255-256`)
   5. OrderShipment 생성 (`:264-271`)
   6. SaleBid 매칭 (`:279-283`)
   7. 판매 측 창고 보관이면 창고 상태 변경 (`:291-293`)
   8. 결제 처리 `paymentCommandService.processPayment` (`:305`)
   9. Order 반환 (`:311`)
4. `OrderBidCommandService.createInstantOrderBid(order, saleBid, sale)` 로 OrderBid 를 만들어 저장 (`:142`, `:189-207`).
5. 컨트롤러가 `OrderBid` 의 `getId()` 를 응답에 담아 `200 OK` 로 반환 (`OrderBidCommandController.java:101-109`).

**동기/비동기**
- `Kafka`/`@Async` 호출이 없다. 결제 대행사 호출(`PortOneApiClient.processCardPayment`, `D/payment/service/command/PaymentCommandService.java:179`)도 요청 스레드에서 블로킹으로 실행된다.
- 비동기(Kafka, 202 Accepted)는 별도 API 인 `OrderCommandController.processPaymentAndShipment` (`D/order/controller/command/OrderCommandController.java:42-69`) 이며, 즉시 구매에서는 호출되지 않는다. `createInstantOrder`/`createInstantOrderBid` 의 호출처는 위 컨트롤러 하나뿐이다.
- 주의: 주석/메시지는 "즉시 구매가 성공적으로 처리되었습니다"(`OrderBidCommandController.java:109`)라고 하지만 아래 3번처럼 결제가 실제로 완료되지 않은 채 성공 응답이 나갈 수 있다.

**응답 ID 가 무엇의 ID 인가**
- `Long orderId = orderBidCommandService.createInstantOrderBid(...).getId();` — 반환 타입이 `OrderBid` 이므로 `getId()` 는 **OrderBid ID** (`OrderBidCommandController.java:101-107`, 서비스 반환 `OrderBidCommandService.java:119,142-144`).
- 변수명만 `orderId` 일 뿐 실제 Order ID 는 응답에 없다. 일반 입찰 `createOrderBid` 응답도 OrderBid ID 다 (`:54`).

## 2. 새로 만들어지는 엔티티와 상태 변화 순서

**새로 생성되는 엔티티** (순서대로)

| # | 엔티티 | 생성 위치 | 생성 직후 상태 |
|---|---|---|---|
| 1 | Order | `OrderCommandService.java:241-247` | `OrderStatus.PENDING_PAYMENT` |
| 2 | OrderItem (수량 1, 가격 = SaleBid 입찰가) | `OrderCommandService.java:255`, `D/order/service/command/OrderItemCommandService.java:45-52` | (상태 없음) |
| 3 | OrderShipment | `OrderCommandService.java:264`, `D/shipment/service/command/OrderShipmentCommandService.java:61-68` | `ShipmentStatus.PENDING` |
| 4 | Payment (카드/계좌/일반 중 하나) | `PaymentCommandService.java:187`, `:250`, `:302` | 결제 수단별 상이 (3번 참고) |
| 5 | Notification 2건 (구매자·판매자) | `PaymentCommandService.java:438`, `:449` → `D/notification/service/command/NotificationCommandService.java:52-53` | 저장됨 (미읽음) |
| 6 | OrderBid | `OrderBidCommandService.java:192-206` | `order.BidStatus.MATCHED`, `isInstantPurchase=true` |

**기존 엔티티 상태 변경 순서와 직후 값**

1. **SaleBid**: `PENDING` → `MATCHED`. `saleBid.assignOrder(order)` 가 order 를 연결하고 상태를 MATCHED 로 설정(`D/sale/entity/SaleBid.java:58-61`), 이어서 `updateStatus(MATCHED)` 한 번 더 (`OrderCommandService.java:279-280`), `entityManager.flush()` (`:283`).
2. **WarehouseStorage** (판매자 Sale 이 창고 보관인 경우만): 현재 상태 → `ASSOCIATED_WITH_ORDER` (`OrderCommandService.java:292-293`, `D/warehouseStorage/service/command/WarehouseStorageCommandService.java:117-133`, 값 정의 `D/warehouseStorage/entity/WarehouseStatus.java:5`). `Sale.isWarehouseStorage` 가 false 면 이 단계는 건너뜀 (`D/sale/entity/Sale.java:43`).
3. **Payment 생성** — 3번 참고.
4. **Sale**: 결제 서비스 안에서 `SaleStatus.SOLD` 로 변경 (`PaymentCommandService.java:404`).
   - 이 시점엔 Order 에 OrderBid 가 아직 없다(OrderBid 는 결제 이후에 생성). 그래서 `order.getOrderBid()==null` 분기로 들어가 `saleBidQueryService.findByOrderId` 로 SaleBid → Sale 을 찾는다 (`PaymentCommandService.java:388-404`). 1번에서 flush 했기 때문에 조회된다.
   - `Sale.updateStatus` 는 전이 검증 없이 값을 대입한다 (`D/sale/entity/Sale.java:73-75`).
5. **OrderBid** 생성: `assignOrder` 가 상태를 `MATCHED` 로 만들고 Order 의 `orderBid` 도 연결 (`D/order/entity/OrderBid.java:60-82`), `markAsInstantPurchase()` (`:97-99`).

**상태가 바뀌지 않는 것 (주의)**
- `createInstantOrder` 전체에서 `order.updateStatus(...)` 는 한 번도 호출되지 않는다 (`OrderCommandService.java:219-319`). `PAYMENT_COMPLETED`/`PREPARING` 으로 올리는 코드는 비동기 경로(`OrderCommandService.java:165-176`, `D/order/service/kafka/OrderEventConsumer.java:192-217`)에만 있다.
- 따라서 Order 는 `PENDING_PAYMENT` 로 남는다 (5번 참고).

## 3. 결제 수단별 결과

결제 수단은 DTO 타입으로 분기한다 (`D/payment/dto/PaymentRequestDto.java:74-87`, `PaymentCommandService.java:67-80`). 공통 검증: orderId·이메일 일치, `paidAmount > 0` (`PaymentCommandService.java:117-146`). `paidAmount` 가 SaleBid 입찰가와 같은지는 검증하지 않는다.

| 수단 | 처리 | Payment 상태 | isSuccess |
|---|---|---|---|
| 카드 (CARD) | PortOne 호출 (`:179`) 후 응답의 `status` 가 `"success"` 일 때만 PAID (`:203-206`) | 응답 status 가 success 면 `PAID`, 아니면 기본값 `PENDING` (`D/payment/entity/Payment.java:44`) | success 면 true, 아니면 false (`Payment.java:39`) |
| 계좌이체 (ACCOUNT) | 은행명만 검증(`:243-248`), 외부 호출 없음, 명시적으로 `PENDING` (`:260`) | `PENDING` | false |
| 일반 (GENERAL) | `impUid` 필수 확인(`:297`), **외부 검증 없이** 바로 PAID (`:313-314`) | `PAID` | true |

**즉시 구매가 끝까지 성공하는가**
- 계좌이체: 결제는 `PENDING` 인데도 예외가 없으므로 즉시 구매 트랜잭션은 그대로 커밋되고 HTTP 200 이 나간다. 입금 확인을 기다리는 단계가 없다. 그럼에도 SaleBid `MATCHED`, Sale `SOLD`, 구매/판매 알림이 모두 발생한다 (`PaymentCommandService.java:83`, `:383-425`). 알림·SOLD 처리는 결제 성공 여부와 무관하게 `processPayment` 가 무조건 호출한다.
- 일반: PAID 로 커밋.
- 카드: 아래 "카드 실패" 참고.
- 결과적으로 어떤 수단이든 Order 는 `PENDING_PAYMENT` 로 남는다 (2번).

**결제 대행사가 카드 결제를 실패로 응답하면** — 실패 응답의 형태에 따라 두 갈래다.
1. **HTTP 비200 이거나 응답 `code != 0`** (일반적인 PortOne 실패):
   - `PortOneApiClient` 가 `PaymentProcessingException("카드 결제 요청 실패: ...")` 을 던진다 (`D/payment/portone/PortOneApiClient.java:270-275`). `PaymentApiException` 만 재시도 대상이라(`:224-228`) 이 경우 재시도 없이 즉시 전파 (`:286-287`).
   - `PaymentProcessingException` 은 `PaymentException` 의 하위 클래스 (`D/payment/exception/PaymentProcessingException.java:6`) → `createCardPayment` 가 그대로 재던짐 (`PaymentCommandService.java:218-219`), `processPayment` 도 재던짐 (`:89-94`).
   - `OrderCommandService` 가 `OrderPaymentProcessingFailedException` 으로 감싸 던지고 (`:306-309`), 바깥 catch 가 `OrderException` 은 그대로 전파 (`:312-314`), `OrderBidCommandService` 도 그대로 전파 (`:145-148`, `:212-218`).
   - `GlobalException` 이 `RuntimeException` 이므로 (`G/exception/GlobalException.java:10`) `OrderBidCommandService` 의 `@Transactional` (`:118`) 이 **롤백**된다: Order/OrderItem/OrderShipment, SaleBid MATCHED 변경, 창고 상태 변경, OrderBid 모두 취소. 알림·Sale SOLD 단계(`:83`) 에는 도달하지 못한다. 클라이언트는 에러 응답을 받는다.
   - 통신 오류(`RestClientException`)는 `PaymentApiException` 이 되어 최대 3회, 1초 간격 재시도 후 실패 (`PortOneApiClient.java:224-228`, `:288-290`) → 위와 동일하게 롤백.
2. **HTTP 200, `code == 0` 이지만 `response.status` 가 `"success"` 가 아님** (예: failed 등):
   - 예외가 없다. CardPayment 는 `PENDING`, `isSuccess=false` 로 저장된다 (`PaymentCommandService.java:187-208`, 기본값 `Payment.java:39,44`). `FAILED` 로 바꾸는 코드도 없다.
   - 이후 정상 경로와 똑같이 알림 발송, Sale `SOLD`, OrderBid 생성, `200 OK "즉시 구매가 성공적으로 처리되었습니다"` 가 나간다. 즉 결제는 실패했는데 판매 완료로 처리되는 결함이 있다.

## 4. 알림: 누가, 언제, 어떤 방식으로

**수신자와 문구** — `PaymentCommandService.sendNotifications` (`:434-461`)
- 구매자: 카테고리 `SHOPPING`, 타입 `BID`, "결제가 완료되었습니다. 주문 ID: {orderId}" (`:438-443`)
- 판매자(`sale.getSeller()`): `SHOPPING`/`BID`, "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}" (`:449-454`)
- 판매자·구매자 외에 다른 알림은 없다. 즉시 구매 흐름에서 환불 알림은 호출되지 않는다.

**시점**
- 카드/계좌/일반 결제 레코드 저장 직후, `processPayment` 안에서 동기 실행 (`PaymentCommandService.java:83`). 순서: 구매자 → 판매자 → 그 다음 Sale `SOLD` (`:403-404`).
- 결제 성공 여부와 관계없이(계좌이체 PENDING, 카드 PENDING 포함) 호출된다. 카드 `code != 0` 실패일 때만 예외로 인해 호출되지 않는다.
- 알림 생성은 트랜잭션 안에서 이루어진다. 이후 OrderBid 저장 단계(`OrderBidCommandService.java:206`)에서 예외가 나면 알림 DB 행은 롤백되지만 WebSocket 으로 이미 나간 메시지는 회수되지 않는다.

**방식**
1. DB 저장: `notificationRepository.save` (`NotificationCommandService.java:52-53`).
2. 실시간 WebSocket: Redis 키 `WebSocket:User:{email}` 가 존재할 때만 `/queue/notifications` 로 `convertAndSendToUser` 전송 (`NotificationCommandService.java:37-39`, `:303-313`). 접속 중이 아니면 저장만 하고 전송은 생략 (`:320-322`). Kafka·이메일·푸시는 사용하지 않는다.
3. 알림 생성/전송 중 예외는 모두 삼켜서(로그만) 구매 처리 자체를 실패시키지 않는다 (`PaymentCommandService.java:457-461`, `:421-425`; 실시간 전송 실패 `NotificationCommandService.java:315-319`).

## 5. 최종 주문 상태와 창고 보관 선택 시 차이

**최종 상태**
- Order: **`PENDING_PAYMENT`** (생성 시 설정 `OrderCommandService.java:244`, 이후 즉시 구매 경로에서 변경 없음 — 2번). 허용 전이 정의는 `D/order/entity/OrderStatus.java:24`.
- OrderBid: `MATCHED`, `isInstantPurchase=true` (`OrderBidCommandService.java:196,205`).
- SaleBid: `MATCHED`, Sale: `SOLD` (`OrderCommandService.java:280`, `PaymentCommandService.java:404`).
- OrderShipment: `PENDING` (`OrderShipmentCommandService.java:67`).
- Payment: 카드 성공/일반 `PAID`, 계좌이체·카드 비성공 응답 `PENDING`.
- 이후 Order 가 `COMPLETED` 로 가는 경로는 배송 배치(6시간 주기 cron, `G/config/ShipmentBatchScheduler.java:34`)가 DELIVERED 처리할 때 (`OrderShipmentCommandService.java:204`, `:355`) 뿐이다. 이 요청 안에서는 일어나지 않는다. (Order 의 `PENDING_PAYMENT → COMPLETED` 전이는 허용돼 있다, `OrderStatus.java:24`.)

**구매자가 "창고 보관"을 선택한 경우**
- 달라지는 것이 **없다.**
  - `warehouseStorage` 값은 컨트롤러 로그에만 쓰인다 (`OrderBidCommandController.java:94-95`).
  - 서비스에 `isWarehouseStorage` 로 전달되지만 (`OrderBidCommandService.java:137`) `createInstantOrder` 안에서 파라미터로만 존재하고 읽는 곳이 없다 (`OrderCommandService.java:219-319`; `isWarehouseStorage` 를 읽는 곳은 판매자의 `sale.isWarehouseStorage()` 하나, `:292`).
  - 구매자 창고 보관용 `warehouseStorageCommandService.createOrderStorage`, `IN_WAREHOUSE` 전이, `COMPLETED` 처리는 비동기 경로 `OrderCommandService.processPaymentAndShipment` (`:163-172`) 와 `OrderEventConsumer` (`:197-210`) 에만 있고, 즉시 구매는 호출하지 않는다. 따라서 `WarehouseStorage` 가 Order 에 생성·연결되지 않고 Order 도 `IN_WAREHOUSE` 로 가지 않으며 `OrderShipment` 도 그대로 만들어진다.
- 창고와 관련해 실제로 일어나는 것은 **판매자 쪽** 뿐이다: 판매 입찰의 Sale 이 창고 보관 상품(`sale.isWarehouseStorage()==true`)이면 해당 WarehouseStorage 가 `ASSOCIATED_WITH_ORDER` 로 바뀐다 (`OrderCommandService.java:291-293`). 창고 정보가 없으면 `WarehouseStorageNotFoundException` (`D/warehouseStorage/service/query/WarehouseStorageQueryService.java:30-33`) 이 `OrderWarehouseStorageProcessingFailedException` 으로 감싸져 (`OrderCommandService.java:295-300`) 전체가 롤백된다. `SOLD` 로의 전환은 이후 배송 완료 처리에서 수행된다 (`OrderShipmentCommandService.java:128`, `:284`).
