# 즉시 구매 처리 흐름 분석

경로 약어: `D` = `src/main/java/com/fream/back/domain`

## 1. 진입 API, 처리 단계, 동기/비동기, 응답 ID

- 진입점은 `POST /order-bids/instant` 이다. (`D/order/controller/command/OrderBidCommandController.java:22` `@RequestMapping("/order-bids")`, `:89` `@PostMapping("/instant")`)
- 요청 본문은 `InstantOrderRequestDto` 이다. 필드는 `saleBidId`, `addressId`, `warehouseStorage`, `paymentRequest` 이다. (`D/order/dto/InstantOrderRequestDto.java:20-29`)
- 처리 단계 (모두 하나의 요청 스레드, 하나의 `@Transactional` 안에서 진행):
  1. 컨트롤러가 이메일을 꺼내고 `paymentRequest` 에 `userEmail` 을 넣고 `orderId=null` 로 둔다. (`OrderBidCommandController.java:92`, `:98`, `:119-122`)
  2. `OrderBidCommandService.createInstantOrderBid` (`D/order/service/command/OrderBidCommandService.java:118-149`)
     - 입력 검증 (`:123`, `:154-167`)
     - 구매자 조회 (`:126`)
     - SaleBid 조회 및 Sale 존재 검증 (`:129`, `:172-184`). 이때 SaleBid 가 이미 매칭됐는지는 검사하지 않는다.
  3. `OrderCommandService.createInstantOrder` (`D/order/service/command/OrderCommandService.java:219-319`)
     - 주소 조회 (`:238`)
     - Order 저장 (`:241-247`)
     - OrderItem 생성 (`:255`)
     - OrderShipment 생성 (`:264-271`)
     - SaleBid 매칭 및 flush (`:279-283`)
     - 창고 상태 갱신 (`:290-301`)
     - 결제 처리 (`:305`)
  4. 결제 처리 중 `PaymentCommandService.processPayment` 가 결제를 만들고 알림을 보내며 Sale 을 SOLD 로 바꾼다. (`D/payment/service/command/PaymentCommandService.java:57-88`, `:383-426`)
  5. 마지막으로 즉시 구매용 OrderBid 를 만들어 저장한다. (`OrderBidCommandService.java:142`, `:189-207`)
- **동기 처리**이다. 이 경로에는 Kafka 가 관여하지 않는다.
  - 컨트롤러가 서비스를 직접 호출하고(`OrderBidCommandController.java:101`) 완료 후 `200 OK` 를 돌려준다. (`:109`)
  - Kafka 비동기 경로는 `POST /orders/{orderId}/process-payment-shipment` (202 Accepted, `D/order/controller/command/OrderCommandController.java:42-69`) 이며, 즉시 구매는 거치지 않는다.
- 응답으로 돌려주는 ID 는 **OrderBid(주문 입찰)의 ID** 이다. 주문(Order) ID 가 아니다.
  - 서비스는 `OrderBid` 를 반환하고 (`OrderBidCommandService.java:144`), 컨트롤러는 그 `.getId()` 를 `orderId` 라는 변수에 담아 응답한다. (`OrderBidCommandController.java:101-107`)
  - 변수명은 `orderId` 이지만 값은 OrderBid 자신의 PK 이다. (`OrderBidCommandService.java:192-206`)
  - 컨트롤러 Javadoc 의 "생성된 주문 ID" (`OrderBidCommandController.java:83`) 는 코드의 실제 동작과 다르다.

## 2. 새로 생성되는 엔티티와 상태 변화 순서

생성 순서와 직후 상태는 다음과 같다.

| 순서 | 동작 | 직후 상태 | 근거 |
|---|---|---|---|
| 1 | **Order** 생성/저장 | `OrderStatus.PENDING_PAYMENT`, `totalAmount = saleBid.bidPrice` | `OrderCommandService.java:241-247` |
| 2 | **OrderItem** 생성 후 Order 에 추가 | (상태 필드 없음) | `OrderCommandService.java:255-256` |
| 3 | **OrderShipment** 생성 | `ShipmentStatus.PENDING`. 배송지는 `addressId` 로 조회한 주소로 채운다. | `OrderCommandService.java:264-271`, `D/shipment/service/command/OrderShipmentCommandService.java:56-68` |
| 4 | 기존 **SaleBid** 갱신: `assignOrder(order)` 후 `updateStatus(MATCHED)` | `SaleBid.status = MATCHED` (PENDING → MATCHED), `order` 연결, 즉시 flush | `OrderCommandService.java:279-283`, `D/sale/entity/SaleBid.java:58-61`, `:66-68` |
| 5 | (판매자가 창고 보관으로 올린 Sale 일 때만) 기존 **WarehouseStorage** 갱신 | `WarehouseStatus.ASSOCIATED_WITH_ORDER` | `OrderCommandService.java:291-293`, `D/warehouseStorage/service/command/WarehouseStorageCommandService.java:117-133` |
| 6 | **Payment** 생성 (카드/계좌/일반 중 하나) | 결제 수단별로 다름 (3번 참조) | `PaymentCommandService.java:67-80` |
| 7 | 알림 전송 + 기존 **Sale** 갱신 | `Sale.status`: 생성 시 `PENDING_SHIPMENT` → `SOLD` | `PaymentCommandService.java:83`, `:403-405`, `:416-419`, `D/sale/service/command/SaleCommandService.java:108` |
| 8 | **OrderBid** 생성/저장 | `BidStatus.MATCHED`, `isInstantPurchase = true`, `order` 와 `sale` 연결 | `OrderBidCommandService.java:192-206`, `D/order/entity/OrderBid.java:97-99` |

- SaleBid 의 초기값은 `PENDING` 이다. (`D/sale/service/command/SaleBidCommandService.java:45`, `D/sale/entity/SaleBid.java:35-37`)
- 5번에서 `findBySale` 이 보관 정보를 못 찾으면 예외가 나고 전체가 롤백된다. (`WarehouseStorageCommandService.java:127`, `OrderCommandService.java:295-300`)
- 7번에서 Order 가 아직 OrderBid 와 연결되기 전이다. 따라서 `order.getOrderBid()` 가 null 이어서 `saleBidQueryService.findByOrderId` 분기로 들어가고, 4번의 flush 덕분에 SaleBid 를 찾는다. (`PaymentCommandService.java:388-406`, `OrderCommandService.java:283`)
- **Order 의 상태는 이후 어디서도 바뀌지 않는다.** 이 경로에는 `order.updateStatus(...)` 호출이 없다. (`OrderCommandService.java:219-319` 전체)

## 3. 결제 수단별 결과, 성공 여부, 카드 결제 실패 시 동작

공통 사항:

- `paymentType` 으로 분기한다. (`PaymentCommandService.java:67-80`, `D/payment/dto/PaymentRequestDto.java:20-25`)
- 공통 검증은 다음과 같다. (`PaymentCommandService.java:117-146`)
  - 주문 ID 와 이메일이 일치해야 한다.
  - 결제 금액이 0 보다 커야 한다.
  - `paidAmount` 가 SaleBid 가격과 같은지는 확인하지 않는다.
- `Payment` 기본값은 `status=PENDING`, `isSuccess=false` 이다. (`D/payment/entity/Payment.java:38-44`)

| 수단 | 결과 Payment 상태 | 근거 |
|---|---|---|
| **CARD** | PortOne 응답의 `status` 가 `"success"` 일 때만 `PAID` + `isSuccess=true`. 그 외에는 `PENDING`, `isSuccess=false` 로 **저장만 되고 예외는 없다.** | `PaymentCommandService.java:179`, `:187-208` |
| **ACCOUNT** (계좌이체) | 은행명만 검증하고 항상 `PENDING` 으로 저장한다. 입금 확인이 없다. `isSuccess=false`, `paymentDate` 없음. | `PaymentCommandService.java:244`, `:250-262` |
| **GENERAL** (일반 결제) | `impUid` 가 있으면 PG 검증 없이 곧바로 `isSuccess=true`, `PAID` 로 저장한다. | `PaymentCommandService.java:297-316` |

- **즉시 구매가 끝까지 성공하는가?**
  - 컨트롤러는 어떤 결제 수단이든 예외가 없으면 "즉시 구매가 성공적으로 처리되었습니다." 로 200 응답한다. (`OrderBidCommandController.java:109`)
  - 하지만 완전히 성공(결제 완료 + 주문 확정)하는 경우는 사실상 없다.
    - `Order` 가 `PENDING_PAYMENT` 에서 바뀌지 않는다. (2번 참조)
    - 계좌이체는 `PENDING` 으로 남는다. 카드와 일반 결제만 `PAID` 가 될 수 있다.
  - 결제 상태와 무관하게 알림과 Sale `SOLD` 처리가 실행된다. (`PaymentCommandService.java:83`)
    - `processPayment` 는 `payment.isSuccess()` 를 검사하지 않는다.
    - 이 호출부는 반환된 Payment 의 성공 여부도 확인하지 않는다. (`OrderCommandService.java:305`)
    - Kafka 경로 쪽 `OrderEventConsumer.java:174-176` 에만 그 검사가 있다.
- **카드 결제를 PortOne 이 실패로 응답하면?** 실패 형태에 따라 두 갈래로 나뉜다.
  1. 실패가 HTTP 비정상이거나 `code != 0` 인 경우 (`PortOneApiClient.java:270-275`):
     - `PaymentProcessingException` 이 발생하고, `createCardPayment` → `processPayment` 를 거쳐 `OrderPaymentProcessingFailedException` 으로 감싸져 전파된다. (`PaymentCommandService.java:180-181`, `:89-94`, `OrderCommandService.java:306-309`)
     - 하나의 트랜잭션이 롤백되므로 Order, OrderShipment, OrderBid, Payment 가 모두 없어지고 SaleBid 는 `PENDING` 으로 남는다. 클라이언트는 오류 응답을 받는다.
     - 통신 오류(`RestClientException`)는 `PaymentApiException` 이 되어 최대 3회 재시도된다. (`PortOneApiClient.java:224-228`, `:288-290`)
  2. 응답이 HTTP 200 + `code == 0` 이지만 `response.status` 가 `"success"` 가 아닌 경우:
     - 예외가 없다. CardPayment 가 `PENDING`/`isSuccess=false` 로 저장된다. (`PaymentCommandService.java:203-208`)
     - `FAILED` 상태는 설정되지 않고 환불도 호출되지 않는다.
     - 이어서 구매자/판매자 알림이 나가고 Sale 은 `SOLD` 가 되며 SaleBid 는 `MATCHED` 가 된다.
     - Order 는 `PENDING_PAYMENT` 로 남고 OrderBid 도 생성되며, 클라이언트는 200 "성공" 을 받는다.

## 4. 알림: 수신자, 시점, 전달 방식

- 수신자는 구매자와 판매자 두 명이다. (`PaymentCommandService.java:434-456`)
  - 구매자: "결제가 완료되었습니다. 주문 ID: {orderId}"
  - 판매자: "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}"
  - 둘 다 `NotificationCategory.SHOPPING` / `NotificationType.BID` 로 보낸다.
- 시점은 결제 처리(Payment 저장) 직후, 요청 처리 중 동기적으로 보낸다. (`PaymentCommandService.java:83`, `:403`, `:416`)
  - 결제가 `PENDING` 이거나 카드 결제가 실패로 응답돼도 "결제가 완료되었습니다" 문구로 나간다. (3번 참조)
  - `OrderBid` 생성은 그 이후이다.
  - 알림 실패는 예외를 삼키고 로그만 남긴다. (`PaymentCommandService.java:421-425`, `:457-461`)
- 전달 방식은 두 가지이다. (`D/notification/service/command/NotificationCommandService.java:44-57`, `:303-323`)
  1. DB 에 `Notification` 을 저장한다. 호출자 트랜잭션에 참여하므로 롤백되면 같이 사라진다.
  2. 사용자가 WebSocket 연결 중일 때만(Redis 키 `WebSocket:User:{email}` 존재) `/user/{email}/queue/notifications` 로 실시간 푸시한다. 연결이 없으면 저장만 된다.
- 즉시 구매 경로에서는 `OrderEventConsumer` 가 보내는 `/topic/order/{id}` WebSocket 알림과 `notification-topic` Kafka 발행이 일어나지 않는다. 이들은 Kafka 경로 전용이다. (`D/order/service/kafka/OrderEventConsumer.java:287-318`)

## 5. 최종 주문 상태와 창고 보관 선택 시 차이

- **최종 주문 상태는 `PENDING_PAYMENT` (결제 대기) 이다.**
  - Order 는 `PENDING_PAYMENT` 로 생성되고 (`OrderCommandService.java:244`) 이후 상태 변경 호출이 없다.
  - 카드/일반 결제가 `PAID` 여도 `PAYMENT_COMPLETED`, `PREPARING` 등으로 이행되지 않는다.
  - 주석이나 응답 메시지의 "처리되었습니다" 와 달리 주문은 확정되지 않은 채 남는다.
  - 결제 완료 후 `PAYMENT_COMPLETED → PREPARING (→ IN_WAREHOUSE → COMPLETED)` 로 가는 전이 코드는 Kafka 경로(`OrderEventConsumer.java:192-220`)와 `processPaymentAndShipment` (`OrderCommandService.java:163-177`)에만 있고, 즉시 구매는 호출하지 않는다.
- **구매자가 "창고 보관" 을 선택해도 달라지는 것이 없다.**
  - `createInstantOrder` 는 `isWarehouseStorage` 인자를 받지만 본문에서 한 번도 사용하지 않는다. (`OrderCommandService.java:220-221`, 본문 `:222-318`)
  - 구매자용 `WarehouseStorage` 는 생성되지 않는다. `createOrderStorage` 호출이 없다.
  - 주문 상태가 `IN_WAREHOUSE`/`COMPLETED` 로 바뀌지도 않는다.
  - 배송 정보(OrderShipment, `PENDING`)는 구매자 플래그와 무관하게 항상 만들어진다. (`OrderCommandService.java:264-271`)
  - 창고 관련 분기는 **판매자 쪽 `Sale.isWarehouseStorage`** 뿐이다. 이 값이 true 이면 기존 판매자 보관품의 상태만 `ASSOCIATED_WITH_ORDER` 로 바뀐다. (`OrderCommandService.java:291-293`)
  - 요청 DTO 의 `warehouseStorage` 는 `OrderBidCommandService` 까지 전달되지만 이후 아무 효과가 없다. (`OrderBidCommandController.java:105`, `OrderBidCommandService.java:136`)
