경로 약칭: `S` = `src/main/java/com/fream/back/domain/shipment/service/command/OrderShipmentCommandService.java`,

## 사전 사실: 결제·배송 처리 직후의 상태

- 결제 후 배송 정보(`OrderShipment`)는 `PENDING` 으로 생성된다. (`S:61-68`, 호출 `OC:148-155`)
- 일반 구매 입찰 주문(`createOrderFromBid`)은 `PENDING_PAYMENT` 로 시작한다. (`OC:76-82`)
- `processPaymentAndShipment` 에서 실배송(`isWarehouseStorage()==false`)이면 `PAYMENT_COMPLETED → PREPARING` 까지만 간다. 즉 **Order 는 `PREPARING`** 이다. (`OC:174-177`)
- Order 상태 전이표: `PREPARING → {IN_WAREHOUSE, SHIPMENT_STARTED}` 만 허용, `IN_TRANSIT → {COMPLETED}`, `PENDING_PAYMENT → {PAYMENT_COMPLETED, COMPLETED, IN_WAREHOUSE}` (`src/main/java/com/fream/back/domain/order/entity/OrderStatus.java:24-29`). 허용되지 않으면 `Order.updateStatus` 가 `InvalidOrderStatusException` 을 던진다. (`src/main/java/com/fream/back/domain/order/entity/Order.java:113-121`)

## 1. 운송장 등록 요청

### 1-1. 진입 API
- `PATCH /shipments/order/{shipmentId}/status`, body 는 `OrderShipmentRequestDto`(courier, trackingNumber). (`C:20`, `C:33-37`)
- 컨트롤러는 `orderShipmentCommandService.updateTrackingInfo(shipmentId, courier, trackingNumber)` 를 호출한다. (`C:41-45`)
- (참고) 같은 컨트롤러의 `POST /{shipmentId}/check-status` 는 운송장 등록과 동시에 택배사 조회까지 하는 별개 경로다. (`C:58-70`, `S:452-516`)

### 1-2. 의도된 처리 순서 (`S:238-303`, `updateTrackingInfo`)
1. courier/trackingNumber 공백 검사 → `TRACKING_INFO_REQUIRED`. (`S:243-246`)
2. `OrderShipment` 조회 후 `shipment.updateTrackingInfo` : courier, trackingNumber 저장 + 배송 상태를 전이 검사 없이 `IN_TRANSIT` 으로 직접 대입. (`S:249-256`, `src/main/java/com/fream/back/domain/shipment/entity/OrderShipment.java:41-45`)
3. `Order.updateStatus(IN_TRANSIT)`. (`S:259-260`)
4. 구매자에게 알림 "상품이 출발하였습니다. 주문 ID: …" 1건. (`S:265-271`)
5. `updateSaleStatusToSold(orderId)` : Sale 을 `SOLD`로 바꾸고 판매자에게 "상품이 성공적으로 판매 완료되었습니다" 알림. (`S:276`, `S:111-183`)
6. 창고 보관 Sale 이면 창고 상태를 sold 로. (`S:279-286`)
7. `updateOrderAndSaleBidStatusToCompleted` : OrderBid/SaleBid 가 `MATCHED` 이면 `COMPLETED` 로. (`S:289`, `S:412-440`)

즉 의도는 "운송장 등록 시점에 배송 `IN_TRANSIT`, 주문 `IN_TRANSIT`, 판매 `SOLD`, 입찰 `COMPLETED`" 까지 한 번에 가는 것이지만, 아래처럼 실제로는 3단계에서 막힌다.

### 1-3. 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문(즉시 구매 아님): 끝까지 성공하지 않는다
- 이 주문의 Order 상태는 `PREPARING` 이다 (`OC:175-176`). `PREPARING → IN_TRANSIT` 은 전이표에 없다 (`OrderStatus.java:26`).
- 따라서 `S:260` 의 `order.updateStatus(OrderStatus.IN_TRANSIT)` 에서 `InvalidOrderStatusException`("상태 전환이 허용되지 않습니다: PREPARING -> IN_TRANSIT") 발생. (`Order.java:117-119`)
- 이 예외는 `ShipmentException` 이 아니므로 `S:295` 의 `catch (Exception e)` 에 잡혀 `ShipmentException(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")` 로 **잘못된 에러코드로 재포장**되어 던져진다. (`S:295-301`)
- 저장되는 것: **없음**. `ShipmentException` 은 `GlobalException extends RuntimeException` (`src/main/java/com/fream/back/global/exception/GlobalException.java:10`)이므로 `@Transactional`(`S:238`)이 롤백한다. 2단계에서 메모리상으로 바꾼 courier/trackingNumber/`IN_TRANSIT` 은 DB에 반영되지 않고 배송은 `PENDING`, 운송장 필드는 null 로 남는다. 4단계 알림도 3단계 뒤라서 생성되지 않는다 (구매자 "출발" 알림 0건, 판매자 알림 0건, Sale/입찰 상태 변경 없음).
- 응답: `GlobalExceptionHandler.handleGlobalException` 이 에러코드 기준으로 응답 → **HTTP 404**, body `ErrorResponse(code="S001", message="배송 정보를 찾을 수 없습니다.", status=404, path=요청 URI)`. 상세 메시지(상태 전환 불가)는 응답에 안 담기고 로그에만 남는다. (`src/main/java/com/fream/back/global/exception/GlobalExceptionHandler.java:49-63`, `src/main/java/com/fream/back/domain/shipment/exception/ShipmentErrorCode.java:12`)
- 요약: 배송이 존재하는데도 "배송 정보를 찾을 수 없습니다(404)"가 나가고 아무것도 저장되지 않는다. 같은 이유로 즉시 구매 주문(`PENDING_PAYMENT`, 전이표에 `IN_TRANSIT` 없음)도 이 API 로는 실패한다.

## 2. 배송 완료 감지

### 2-1. 누가/언제/어떻게
- 주체: Spring `@Scheduled` 가 Spring Batch Job 을 실행. `ShipmentBatchScheduler.scheduleShipmentStatusJob` 가 `jobLauncher.run(updateShipmentStatusesJob, …)` 호출. (`src/main/java/com/fream/back/global/config/ShipmentBatchScheduler.java:34-40`)
- 주기: `cron = "0 0 */6 * * *"` → **6시간마다**(00:00, 06:00, 12:00, 18:00 정각). (`ShipmentBatchScheduler.java:34`)
- 예외는 `e.printStackTrace()` 만 하고 삼킨다. (`ShipmentBatchScheduler.java:41-43`)

### 2-2. 조회 대상
- Reader: `SELECT s FROM OrderShipment s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL`, 페이지 크기 50. (`J:95`, `J:51`)
- 즉 운송장이 등록되고 `IN_TRANSIT`/`OUT_FOR_DELIVERY` 인 배송만 대상이다. `PENDING` 은 대상 아님.

### 2-3. 실제로 실행되는 처리 코드 (비슷한 코드가 3벌 있음)
| 후보 | 실행 여부 | 근거 |
|---|---|---|
| **`ShipmentItemProcessor.process`** (Playwright `PlaywrightBrowserManager` 로 CJ 페이지 조회, `completeOrder` + `notifyShipmentCompleted`) | **실제 실행됨** | Step 에 `.processor(new ShipmentItemProcessor(...))` 로 연결 (`J:69-73`) |
| `UpdateShipmentStatusesJobConfig.shipmentItemProcessor()` @Bean (`cjTrackingPlaywright` 사용) | 미사용. Step 이 이 빈을 참조하지 않음 | 정의 `J:106`, Step 은 `J:66-77` |
| `OrderShipmentCommandService.updateShipmentStatuses()` (`@Transactional` 루프) | 미사용. 호출하는 곳 없음(정의만 존재) | `S:308-391`, 저장소 전체 grep 결과 호출부 없음 |
| `JobConfig.parseCjLogisticsStatus` (Jsoup) | 미사용 private 메서드 | `J` 내 정의만 있고 호출 없음 |

실행되는 Step 구성: chunk 50, `faultTolerant().skip(Exception.class).skipLimit(50)`, writer `JpaItemWriter`. (`J:51-52`, `J:67`, `J:74-77`, `J:241`)

### 2-4. 택배사 상태 문자열 → 내부 상태
- CJ 페이지 `tbody#statusDetail tr` 의 **마지막 행 5번째 td** 텍스트를 trim 하여 사용. (`P:181`)
- 변환(`mapToShipmentStatus`, 완전 일치): `"배송완료"` → `DELIVERED`, `"배송출발"` → `OUT_FOR_DELIVERY`, 그 외 모든 문자열 → `IN_TRANSIT`. (`P:220-225`)
- 처리 분기: 현재 상태와 같으면 변경 없이 반환(`P:101`); `DELIVERED` 면 배송 상태 DELIVERED + `completeOrder` + `notifyShipmentCompleted` (`P:113-117`); `OUT_FOR_DELIVERY` (`P:121`); 그 외 `IN_TRANSIT` (`P:125`).
- 주의: 현재 `OUT_FOR_DELIVERY` 인 배송에 대해 다른 문자열이 오면 `IN_TRANSIT` 으로 매핑되고, `OUT_FOR_DELIVERY → IN_TRANSIT` 은 `ShipmentStatus` 전이표에 없어 `IllegalStateException` → 스킵된다. (`src/main/java/com/fream/back/domain/shipment/entity/ShipmentStatus.java:79-84`, `OrderShipment.java:47-55`)

## 3. 배송 완료 판정 이후 (`DELIVERED` 감지 시 `P:113-117`)

### 3-1. 상태 변경 순서 (성공 경로)
1. `OrderShipment.status = DELIVERED` (`IN_TRANSIT`/`OUT_FOR_DELIVERY → DELIVERED` 허용, `ShipmentStatus.java:75-76`, `82`). (`P:113`)
2. `completeOrder(orderId)` (`P:116` → `S:190-229`):
   1. OrderBid 조회 (없으면 `IllegalArgumentException`→ 아래 catch 에서 `ShipmentException`). (`S:196-197`)
   2. `Order.updateStatus(COMPLETED)`. (`S:204`)
   3. `updateSaleStatusToSold(orderId)` : SaleBid 조회 → Sale 이 `canTransitionTo(SOLD)` 일 때만 `SOLD` + (창고면 창고 상태) + 판매자 알림. 이어서 OrderBid 의 Sale 도 같은 방식. (`S:208`, `S:111-183`)
   4. 구매자 알림 "[completeOrder] 주문이 완료 처리되었습니다. 주문 ID: …". (`S:211-217`)
   5. 어떤 예외든 `ShipmentException(ORDER_NOT_FOUND_FOR_SHIPMENT)` 로 재포장. (`S:221-228`)
3. `notifyShipmentCompleted(order)` : 구매자 알림 "[배송 완료] 상품이 배송 완료되었습니다. 주문 ID: …" (`P:117`, `src/main/java/com/fream/back/domain/notification/service/command/NotificationCommandService.java:219-234`)
4. Writer 가 `OrderShipment` 를 저장. (`J:74`, `J:241`)

### 3-2. 알림 (성공 경로: Sale 이 아직 `SOLD` 가 아니었던 경우)
- 구매자: 2건 ("[completeOrder] …" `S:212-217`, "[배송 완료] …" `NotificationCommandService.java:224-229`).
- 판매자: 1건 ("상품이 성공적으로 판매 완료되었습니다. 판매 ID: …" `S:133-138`; 같은 Sale 은 첫 블록에서 `SOLD` 가 되어 OrderBid 블록 `S:156` 의 `canTransitionTo(SOLD)` 가 false 라 중복 안 됨).
- 단 즉시 구매 주문은 아래 4-(b) 처럼 Sale 이 이미 `SOLD` 라 판매자 알림이 0건이다.

### 3-3. 주문 입찰·판매 입찰 상태
- `completeOrder` / 배치 경로에는 OrderBid/SaleBid 를 `COMPLETED` 로 바꾸는 코드가 **없다**. 그 코드(`updateOrderAndSaleBidStatusToCompleted`, `S:412-440`)는 `updateTrackingInfo`(`S:289`)에서만 호출되고, 1-3 에서 보았듯 그 경로는 실패한다. 따라서 OrderBid(`order.BidStatus`)와 SaleBid(`sale.BidStatus`)는 **`MATCHED` 그대로** 남는다.
- (참고) 해당 메서드는 `private` 에 `@Transactional` 이 붙어 있어 프록시 적용 대상이 아니며(`S:412-413`), 내부 예외도 로그만 남기고 삼킨다(`S:436-439`).

## 4. 주문 종류별 차이

### (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문 → 끝까지 진행되지 않음
- 이 주문은 1-3 의 이유로 `updateTrackingInfo` 가 롤백되므로, 이 API 로는 배송이 `IN_TRANSIT` 이 되지 않는다. 배송이 `IN_TRANSIT` 이 되려면 `check-status` 경로(`S:473`, `updateTrackingInfo` 를 엔티티 메서드로 직접 호출)를 거쳐야 하며, 그 경우 Order 는 여전히 `PREPARING` 이다.
- 그 상태에서 택배사가 "배송완료"를 주면 `P:113` 에서 배송이 `DELIVERED` 로 메모리상 바뀐 뒤 `completeOrder` → `S:204` `Order.updateStatus(COMPLETED)` 가 `PREPARING → COMPLETED`(전이표에 없음, `OrderStatus.java:26`)로 `InvalidOrderStatusException` → `S:221-228` 에서 `ShipmentException(ORDER_NOT_FOUND_FOR_SHIPMENT)` 로 재포장.
- 결과: 배치에서는 해당 아이템 skip(`J:75-76`, 스킵 리스너 로그 `J:255`). 알림 0건(구매자 알림 `S:212` 와 `P:117` 이 예외 이후라 실행 안 됨). 배송은 `IN_TRANSIT`/`OUT_FOR_DELIVERY` 로, Order 는 `PREPARING` 으로, 입찰들은 `MATCHED` 로 남는다. 다음 주기(6시간 후)에 같은 건이 다시 조회·실패한다(반복 실패).
- `check-status` API 에서는 `shipment.updateStatus(DELIVERED)` 후 `completeOrder` 예외가 `ShipmentException` 이라 그대로 전파(`S:505-506`) → `@Transactional` 롤백, 컨트롤러가 `ORDER_NOT_FOUND_FOR_SHIPMENT` 의 상태(404)를 빈 body 로 반환(`C:79-86` 계열, `status(e.getErrorCode().getStatus())`).

### (b) 즉시 구매로 만들어진 주문 → 끝까지 진행됨
- 즉시 구매 주문은 `PENDING_PAYMENT` 로 생성되고(`OC:241-245`) `createInstantOrder` 안에서 상태가 바뀌지 않는다(결제 `OC:305`는 Order 상태를 건드리지 않음, `PC` 에 `OrderStatus` 변경 없음). 배송은 `PENDING` (`OC:264-271`).
- `PENDING_PAYMENT → COMPLETED` 는 전이표에서 허용(`OrderStatus.java:24`) → `S:204` 성공.
- Sale 은 결제 시점에 이미 `SOLD` 가 된다: `createInstantOrder` 의 결제 시점엔 OrderBid 가 아직 없어(`OrderBidCommandService.java:133` 이후 `142` 에서 생성) `order.getOrderBid()==null` → SaleBid 경로에서 `sale.updateStatus(SOLD)`. (`PC:388-405`; 결제 시 구매자·판매자 알림은 `PC` `sendNotifications`)
- 따라서 `S:119` / `S:156` 의 `canTransitionTo(SOLD)`(`SaleStatus.SOLD → false`, `src/main/java/com/fream/back/domain/sale/entity/SaleStatus.java:38`) 가 false → 판매자 알림·창고 갱신 없음.
- 결과: 배송 `DELIVERED`, Order `COMPLETED`, 구매자 알림 2건("[completeOrder]…", "[배송 완료]…"), 판매자 알림 0건, Sale `SOLD`(결제 시점부터), OrderBid/SaleBid 는 `MATCHED` 유지.
- 단 배송이 `IN_TRANSIT` 이 되려면 운송장 등록 API(`PATCH …/status`)는 `PENDING_PAYMENT → IN_TRANSIT` 불가로 실패하므로(1-3 끝), `check-status` API 로 운송장을 등록·조회하는 경로가 필요하다. 이후 배치 또는 `check-status` 호출이 위 처리를 완료시킨다.

### 비교 요약
| | (a) 실배송 일반 구매 입찰 | (b) 즉시 구매 |
|---|---|---|
| 배송 완료 시점 Order 상태 | `PREPARING` | `PENDING_PAYMENT` |

## 5. 실패 처리 (주기 처리 중 한 건 실패)

- 실제 실행되는 Spring Batch Step 은 `faultTolerant().skip(Exception.class).skipLimit(50)` (`J:74-77`). 한 건의 processor 예외(조회 실패, 파싱 실패, 상태 전이 실패, `completeOrder` 실패)는 **그 건만 skip** 되고 나머지는 계속 처리된다.
- processor 는 모든 예외를 `ShipmentException` 으로 재포장해 던진다. (`P:132-146`; 운송장 없음 `P:61-64`, 테이블 비어 있음/파싱 실패 `P:173-208`)
- 실패 건은 skip 리스너가 error 로그만 남긴다(`J:78`, `J:252-264`). 실패 건의 DB 변경은 없다(writer 로 가지 않고, `completeOrder` 의 `@Transactional` 이 chunk 트랜잭션에 참여해 롤백 마킹 → chunk 롤백 후 Spring Batch 가 skip 건을 제외하고 나머지 아이템을 재처리). 해당 배송은 계속 `IN_TRANSIT`/`OUT_FOR_DELIVERY` 이므로 **다음 주기(6시간 후)에 다시 대상**이 된다.
- skip 한도 50건을 넘으면 Step 이 실패하고 남은 건은 그 실행에서 처리되지 않는다. (`J:77`) 스케줄러는 예외를 `printStackTrace` 로만 삼킨다. (`ShipmentBatchScheduler.java:41-43`)
- (참고) 실행되지 않는 `OrderShipmentCommandService.updateShipmentStatuses` 는 건별 try/catch 로 에러 카운트만 올리고 계속하는 구조(`S:322-388`)지만 호출되지 않으므로 실제 동작과 무관하다.
