# 구매자 배송: 운송장 등록 → 배송 완료

경로 약어: `S` = `src/main/java/com/fream/back/domain/shipment`, `O` = `src/main/java/com/fream/back/domain/order`, `G` = `src/main/java/com/fream/back/global`

## 사전 사실: 결제·배송 처리 후 주문/배송 상태

- 결제·배송 처리 요청(`POST /orders/{orderId}/process-payment-shipment`)은 Kafka 이벤트만 발행하고 202를 돌려준다. `O/controller/command/OrderCommandController.java:43-60`
- 이벤트 소비 측(`processCompleteOrder`)이 `OrderShipment`를 만든다. `O/service/kafka/OrderEventConsumer.java:181`
  - 생성 시 상태는 `PENDING`. `S/service/command/OrderShipmentCommandService.java:67`
  - 실배송(창고 보관 아님)이면 주문은 `PAYMENT_COMPLETED` → `PREPARING`에서 멈춘다. `OrderEventConsumer.java:195`, `OrderEventConsumer.java:214-218`
  - 동기 경로 `processPaymentAndShipment`도 같다. `O/service/command/OrderCommandService.java:175-176`
- `OrderStatus.SHIPMENT_STARTED`로 바꾸는 코드는 어디에도 없다. grep으로 `OrderStatus.SHIPMENT_STARTED`를 설정하는 곳이 없음을 확인했다.
- 즉시 구매(`createInstantOrder`)는 주문을 `PENDING_PAYMENT`로 만들고 결제 후에도 주문 상태를 바꾸지 않는다. `OrderCommandService.java:244`, `OrderCommandService.java:305`
- 주문 상태 전이표. `O/entity/OrderStatus.java:24-31`
  - `PENDING_PAYMENT` → {`PAYMENT_COMPLETED`, `COMPLETED`, `IN_WAREHOUSE`}
  - `PREPARING` → {`IN_WAREHOUSE`, `SHIPMENT_STARTED`}
  - `IN_TRANSIT` → {`COMPLETED`}
- `Order#updateStatus`는 전이표에 없으면 `InvalidOrderStatusException`을 던진다. `O/entity/Order.java:113-121`
- 반면 `OrderShipment#updateTrackingInfo`는 전이 검사 없이 상태를 바로 `IN_TRANSIT`으로 바꾼다. `S/entity/OrderShipment.java:102-106`

## 1. 운송장 등록 요청

### 1-1. 진입 API

- `PATCH /shipments/order/{shipmentId}/status`, 본문 `OrderShipmentRequestDto`(courier, trackingNumber). `S/controller/command/OrderShipmentCommandController.java:33-47`
- 호출 대상은 `OrderShipmentCommandService#updateTrackingInfo`. `OrderShipmentCommandController.java:40-44`
- 예외 처리 없이 `ResponseEntity.ok()`를 반환하므로, 예외는 `GlobalExceptionHandler`가 처리한다.
- 별도로 `POST /shipments/order/{shipmentId}/check-status`, `/check-status-string`도 운송장을 등록하는 경로다. 이 경로는 `updateAndCheckShipmentStatus`를 호출한다(아래 4번 참고). `OrderShipmentCommandController.java:62-100`
- 보안 설정상 `/shipments/**`에 별도 role 제한은 보이지 않는다. 인증된 사용자 전체에 열려 있다. `G/config/security/SecurityConfig.java:52`

### 1-2. 의도된 상태 변경 순서와 알림 (`updateTrackingInfo`)

`S/service/command/OrderShipmentCommandService.java:238-303` 기준.

1. courier/trackingNumber가 비어 있으면 `TRACKING_INFO_REQUIRED`. `:243-246`
2. `OrderShipment`를 조회하고 `updateTrackingInfo(courier, trackingNumber)`를 호출한다. 운송장을 채우고 shipment 상태를 `IN_TRANSIT`으로 바꾼다. `:249-256`, `OrderShipment.java:102-106`
3. `order.updateStatus(OrderStatus.IN_TRANSIT)`. `:259-260`
4. 구매자에게 알림 1건: "상품이 출발하였습니다. 주문 ID: …". `:265-271`
5. `updateSaleStatusToSold(orderId)`. `:276`
   - SaleBid의 Sale을 `SOLD`로 바꾸고 창고 보관이면 창고 상태도 `SOLD`로 바꾼다. 판매자에게 알림 "상품이 성공적으로 판매 완료되었습니다". `:116-143`
   - OrderBid의 Sale도 `SOLD`로 바꾸고 판매자에게 알림을 한 번 더 보낸다. `:150-172`
6. 창고 보관 Sale이면 창고 상태를 다시 `SOLD`로 바꾼다. `:279-286`
7. `updateOrderAndSaleBidStatusToCompleted`. OrderBid와 SaleBid가 `MATCHED`이면 `COMPLETED`로 바꾼다. `:289`, `:413-432`
   - 이 메서드는 `private`에 `@Transactional`이 붙어 있어 프록시 효과가 없다. 예외는 삼키고 로그만 남긴다. `:412-439`
   - 즉 운송장 "등록" 시점에 입찰을 이미 `COMPLETED`로 만들도록 짜여 있다. 이름과 주석("배송 완료")과 다르게 배송 완료 시점이 아니다.

즉 의도된 순서는 shipment `IN_TRANSIT` → order `IN_TRANSIT` → 구매자 알림 → Sale `SOLD`(판매자 알림) → 창고 → OrderBid/SaleBid `COMPLETED`이다. 알림 수신자는 구매자 1건과 판매자(SaleBid/OrderBid 경로별로 최대 2건)다.

### 1-3. 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문: 끝까지 성공하지 못한다

- 이 주문은 `PREPARING` 상태다(사전 사실 참고). 3번 단계 `order.updateStatus(IN_TRANSIT)`에서 `PREPARING → IN_TRANSIT`은 전이표에 없다.
  - 전이표: `OrderStatus.java:26`(PREPARING은 IN_WAREHOUSE/SHIPMENT_STARTED만 허용)
  - `Order#updateStatus`가 `InvalidOrderStatusException("상태 전환이 허용되지 않습니다: PREPARING -> IN_TRANSIT")`을 던진다. `Order.java:113-120`
- 이 예외는 `OrderException`(GlobalException, RuntimeException)이고 `ShipmentException`이 아니다. `updateTrackingInfo`의 `catch (Exception e)`가 받아 `ShipmentException(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")`으로 감싸 던진다. `OrderShipmentCommandService.java:295-301`
- 트랜잭션이 롤백된다. 저장되는 것은 없다.
  - shipment의 courier/trackingNumber/`IN_TRANSIT` 변경은 메모리 변경이라 반영되지 않는다. shipment는 `PENDING`, 운송장 `null`로 남는다.
  - 알림은 3번 뒤(4번)에 만들기 때문에 구매자·판매자 알림이 모두 생성되지 않는다. `:260` 대 `:266`
  - Sale/OrderBid/SaleBid 상태도 건드리지 않는다.
- 응답: `GlobalExceptionHandler`가 `GlobalException`을 `errorCode.getStatus()`로 응답한다. 본문은 `ErrorResponse`(code `S001`, message "배송 정보를 찾을 수 없습니다.", status 404)다. `G/exception/GlobalExceptionHandler.java:49-63`, `S/exception/ShipmentErrorCode.java:12`
  - 실제 원인과 다른 "배송 정보 없음" 404로 응답된다. 에러 코드가 잘못 매핑돼 있다.
- 설령 주문 상태 전이를 통과해도, 일반 구매 입찰 주문에는 SaleBid가 연결돼 있지 않다.
  - `SaleBidQueryService#findByOrderId`는 없으면 null이 아니라 `IllegalArgumentException`을 던진다. `sale/service/query/SaleBidQueryService.java:26-29`
  - 이 호출은 `updateSaleStatusToSold`에서 try 밖이다(`OrderShipmentCommandService.java:116`). 따라서 이 경로로도 실패한다.
- 즉시 구매 주문도 `PENDING_PAYMENT → IN_TRANSIT`이 전이표에 없어(`OrderStatus.java:24`) 같은 이유로 실패한다.

## 2. 배송 완료 감지

### 2-1. 누가·언제·어떻게

- 주체는 스프링 스케줄러 `ShipmentBatchScheduler#scheduleShipmentStatusJob`이다. `@Scheduled(cron = "0 0 */6 * * *")`로 6시간마다(매일 00·06·12·18시 정각) 실행한다. `G/config/ShipmentBatchScheduler.java:34-44`
- `JobLauncher`로 `updateShipmentStatusesJob`을 실행한다. 매번 `timestamp` 파라미터를 붙인다. `ShipmentBatchScheduler.java:37-40`
- 운영자가 호출하는 `check-status` API는 즉시 조회용 수동 경로로, 주기 처리와 별개다.

### 2-2. 조회 대상

- `shipmentItemReader`(JpaPagingItemReader, pageSize 50)가 다음 쿼리로 읽는다. `S/config/UpdateShipmentStatusesJobConfig.java:87-97`
  ```
  SELECT s FROM OrderShipment s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL
  ```
- 청크 50건, `faultTolerant().skip(Exception.class).skipLimit(50)`. `UpdateShipmentStatusesJobConfig.java:51-52`, `UpdateShipmentStatusesJobConfig.java:66-78`

### 2-3. 실제 실행되는 처리 코드

- 실제로 실행되는 것은 `ShipmentItemProcessor`(`S/config/ShipmentItemProcessor.java`)다. step이 `new ShipmentItemProcessor(playwrightBrowserManager(), notificationService, orderService)`를 processor로 직접 등록한다. `UpdateShipmentStatusesJobConfig.java:69-73`
- 처리 흐름은 다음과 같다. `ShipmentItemProcessor.java:57-157`
  1. Playwright 페이지로 CJ 조회 URL에 접속한다.
  2. HTML에서 `tbody#statusDetail tr`의 마지막 행 5번째 td 텍스트를 파싱한다.
  3. `mapToShipmentStatus`로 변환한다.
- 실행되지 않는 유사 코드는 다음과 같다.
  - 같은 설정 클래스의 `@Bean @StepScope shipmentItemProcessor()`(`UpdateShipmentStatusesJobConfig.java:104-177`)와 `parseCjLogisticsStatus`(`:186`). step이 참조하지 않는 죽은 코드다.
  - `OrderShipmentCommandService#updateShipmentStatuses`(`OrderShipmentCommandService.java:308-391`). 호출하는 곳이 없다. 이 메서드의 DELIVERED 분기는 `completeOrder`를 쓰지 않고 구매자 알림만 직접 생성한다. 이 점도 `ShipmentItemProcessor`와 다르다.
  - `CjTrackingPlaywright#getCurrentTrackingStatus`는 `check-status` API 경로에서만 쓰인다.

### 2-4. 택배사 문자열 → 내부 상태

`ShipmentItemProcessor#mapToShipmentStatus`(`ShipmentItemProcessor.java:220-226`):

| 택배사 문자열 | 내부 상태 |
|---|---|
| `"배송완료"` | `DELIVERED` |
| `"배송출발"` | `OUT_FOR_DELIVERY` |
| 그 외 전부 | `IN_TRANSIT` |

- 정확 일치(equals)라서 "배송중", "집화처리" 등은 모두 `IN_TRANSIT`이 된다.
- 현재 상태와 같은 상태로 매핑되면 아무 것도 하지 않고 반환한다. `ShipmentItemProcessor.java:101-105`
- `OUT_FOR_DELIVERY` 건이 `IN_TRANSIT`으로 매핑되면 `updateStatus(IN_TRANSIT)`이 전이표 위반이라 `IllegalStateException`이 난다. 이 건은 skip 처리된다. `ShipmentItemProcessor.java:123-126`, `ShipmentStatus.java:23-27`, `OrderShipment.java:108-115`

## 3. 배송 완료 판정 이후 (`ShipmentItemProcessor`, DELIVERED 분기)

`ShipmentItemProcessor.java:108-117`. 정상 진행되는 경우의 순서다.

1. `orderShipment.updateStatus(DELIVERED)`. `IN_TRANSIT`/`OUT_FOR_DELIVERY` → `DELIVERED`는 허용된다. `ShipmentStatus.java:19-26`
2. `orderService.completeOrder(orderId)`. `OrderShipmentCommandService.java:190-229`
   - OrderBid를 `findByOrderId`로 조회한다. 없으면 `IllegalArgumentException`. `:196-197`
   - `order.updateStatus(COMPLETED)`. `:204`
   - `updateSaleStatusToSold`. `:208`
   - 구매자 알림 "[completeOrder] 주문이 완료 처리되었습니다". `:211-217`
3. `notificationService.notifyShipmentCompleted(order)`. 구매자에게 "[배송 완료] 상품이 배송 완료되었습니다". `ShipmentItemProcessor.java:117`, `notification/service/command/NotificationCommandService.java:219-229`
4. 청크 writer(`JpaItemWriter`)가 shipment를 저장한다. `UpdateShipmentStatusesJobConfig.java:239-246`

엔티티 상태 변경 순서는 Shipment `DELIVERED` → Order `COMPLETED` → Sale `SOLD`(조건부)다.

알림은 다음과 같다.

- 구매자: 2건("[completeOrder]…", "[배송 완료]…").
- 판매자: `updateSaleStatusToSold`에서 Sale이 `SOLD`로 전이 가능한 경우에만 받는다.
  - SaleBid 경로와 OrderBid 경로가 각각 알림을 만들 수 있다. `OrderShipmentCommandService.java:133-138`, `:164-169`
  - Sale이 이미 `SOLD`면 `canTransitionTo`가 false라 알림이 없다. `SaleStatus.java:83`

입찰 상태는 다음과 같다.

- 주기 처리 경로는 `updateOrderAndSaleBidStatusToCompleted`를 호출하지 않는다. 호출하는 곳은 `updateTrackingInfo`(`:289`)뿐이다.
- 따라서 배송 완료 시점에 OrderBid와 SaleBid의 상태(`MATCHED`)는 바뀌지 않는다. `COMPLETED`는 운송장 등록 시점에만 설정하도록 짜여 있고, 1-3에서 보듯 그 경로는 이 주문에서 실패한다.

## 4. 주문 종류별 차이

### (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문: 끝까지 진행되지 않는다

- 전제: 배송 상태가 `IN_TRANSIT`이어야 배치 대상이 된다. 1-3에서 `updateTrackingInfo`는 실패하므로 이 경로로는 대상이 되지 않는다.
- 대상이 되는 방법은 `check-status` API뿐이다. 이 API는 shipment만 `IN_TRANSIT`으로 만들고 주문은 건드리지 않는다. `OrderShipmentCommandService.java:473`, `OrderShipment.java:102-106`
- 이 상태에서 배치가 "배송완료"를 읽으면 `completeOrder`가 실패한다.
  - 주문은 `PREPARING`이다. `order.updateStatus(COMPLETED)`는 `PREPARING → COMPLETED`가 전이표에 없어 `InvalidOrderStatusException`을 던진다. `OrderStatus.java:26`, `Order.java:113-120`
  - `completeOrder`의 `catch (Exception)`이 `ShipmentException(ORDER_NOT_FOUND_FOR_SHIPMENT)`으로 감싸 던진다. `OrderShipmentCommandService.java:221-228`
  - 이 시점에 Sale 처리, 구매자 알림, "[배송 완료]" 알림은 실행되지 않는다. 모두 `:204` 이후라 도달하지 못한다.
- 결과는 다음과 같다.
  - 청크 트랜잭션이 롤백된다. shipment는 `IN_TRANSIT`, order는 `PREPARING`, 알림은 0건이다.
  - 건은 skip 처리된다. 다음 6시간 주기에 같은 건을 다시 읽고 다시 실패한다.
  - 그 사이 `updateSaleStatusToSold`의 `SaleBid` 조회도 SaleBid가 없어 실패할 구조다(1-3).
- `check-status` API로 즉시 조회해도 같은 이유로 `completeOrder`가 실패한다. 서비스는 `ShipmentException`을 던지고, 컨트롤러는 `ORDER_NOT_FOUND_FOR_SHIPMENT`의 404 상태와 빈 본문을 돌려준다. `OrderShipmentCommandService.java:489`, `OrderShipmentCommandController.java:80-85`

### (b) 즉시 구매로 만들어진 주문: 끝까지 진행된다

- 주문 상태는 `PENDING_PAYMENT`다. `PENDING_PAYMENT → COMPLETED`는 전이표에 있다. `OrderStatus.java:24`
- OrderBid가 있다(MATCHED, `order` 연결). `O/service/command/OrderBidCommandService.java:189-206`
- SaleBid가 주문에 연결돼 있다. `saleBid.assignOrder(order)`. `OrderCommandService.java:279`
- 따라서 `completeOrder`가 통과한다. 결과는 다음과 같다.
  - Shipment `DELIVERED`, Order `COMPLETED`.
  - 구매자 알림 2건("[completeOrder]", "[배송 완료]").
  - 판매자 알림 0건. 결제 처리 때 `notifyUsersAndUpdateSaleStatus`가 이미 Sale을 `SOLD`로 만들어 둔다. `payment/service/command/PaymentCommandService.java:389-405`
  - 그래서 `updateSaleStatusToSold`에서 `canTransitionTo(SOLD)`가 false다(`SaleStatus.java:83`). 판매자 알림과 창고 상태 갱신이 모두 건너뛰어진다. `OrderShipmentCommandService.java:119`, `:156`
  - OrderBid/SaleBid는 `MATCHED` 그대로다.
- 단, shipment가 `IN_TRANSIT`이 되는 경로가 문제다. 즉시 구매 주문은 주문이 `PENDING_PAYMENT`라서 `updateTrackingInfo`가 `PENDING_PAYMENT → IN_TRANSIT`에서 실패한다(1-3). `check-status` API로 운송장을 등록해야만 배치 대상이 된다.
- 요약하면 (a)는 `PREPARING → COMPLETED`가 막혀 배송 완료 처리 전체가 롤백된다. (b)는 `PENDING_PAYMENT → COMPLETED`가 허용돼 완료까지 가지만 판매자 알림은 없고 입찰 상태는 갱신되지 않는다.

## 5. 실패 처리 (주기 처리)

- `ShipmentItemProcessor`는 모든 예외를 `ShipmentException`으로 감싸(`EXTERNAL_TRACKING_SERVICE_ERROR` 등) 던진다. `ShipmentItemProcessor.java:133-145`
- step은 `faultTolerant().skip(Exception.class).skipLimit(50)`이다. `UpdateShipmentStatusesJobConfig.java:75-77`
- 실패한 한 건은 skip된다.
  - 해당 건의 변경(shipment 상태, `completeOrder`가 건드린 Order/Sale/알림)은 청크 롤백으로 반영되지 않는다.
  - `shipmentSkipListener`가 `[Skip]` 로그만 남긴다. `UpdateShipmentStatusesJobConfig.java:251-286`
  - shipment는 여전히 `IN_TRANSIT`/`OUT_FOR_DELIVERY`라 6시간 뒤에 다시 조회 대상이 된다.
- 나머지 건은 계속 처리된다. Spring Batch의 fault-tolerant 청크는 롤백 후 해당 건을 제외하고 다시 처리해 저장한다.
- 단, skip이 50건을 넘으면 step 자체가 실패한다. 이후 건은 처리되지 않는다. `UpdateShipmentStatusesJobConfig.java:52`
- 스케줄러는 `jobLauncher.run`의 예외를 `printStackTrace`만 하고 삼킨다. `ShipmentBatchScheduler.java:41-43`
- (참고) 실행되지 않는 `OrderShipmentCommandService#updateShipmentStatuses`는 건별 try/catch로 계속 진행하는 방식이다. `OrderShipmentCommandService.java:322-388`
