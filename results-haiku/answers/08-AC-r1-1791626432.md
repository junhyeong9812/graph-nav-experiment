# 구매자 배송: 운송장 등록부터 배송 완료까지

요약: 운송장 등록 API는 코드상 의도한 순서대로 끝까지 가지 못한다. `Order`가 `IN_TRANSIT`으로 갈 수 있는 전이가 없어서, 실배송 일반 구매 주문(a)과 즉시 구매 주문(b) 모두 PATCH 등록에서 실패하고 롤백된다. 그래서 배치의 배송 완료 처리는 정상 흐름에서 시작되지 않는다. 아래는 코드 기준 상세다. 경로는 `src/main/java/com/fream/back/` 아래 파일이다.

---

## 1. 운송장 등록 요청

**진입점**
- `PATCH /shipments/order/{shipmentId}/status`, body `{courier, trackingNumber}` — `domain/shipment/controller/command/OrderShipmentCommandController.java:33-48`
- 서비스 `OrderShipmentCommandService.updateTrackingInfo` — `domain/shipment/service/command/OrderShipmentCommandService.java:238-303`
- 같은 기능을 하는 우회 경로가 하나 더 있다: `POST /shipments/order/{shipmentId}/check-status` → `updateAndCheckShipmentStatus` (`OrderShipmentCommandController.java:58-`, `OrderShipmentCommandService.java:452-516`). 이 경로도 송장 번호를 저장한다(2번 참조).

**의도된 상태 변경 순서 (코드 순서 그대로)**
1. 택배사/운송장 공백 검사 → `TRACKING_INFO_REQUIRED` (`OrderShipmentCommandService.java:243-246`)
2. `OrderShipment` 조회 (`:249-253`)
3. `shipment.updateTrackingInfo(courier, trackingNumber)` — 택배사·운송장 저장 후 `status = IN_TRANSIT`을 직접 대입 (`domain/shipment/entity/OrderShipment.java:41-45`). `ShipmentStatus.canTransitionTo`를 거치지 않는다. 원래 `PENDING`에서 `IN_TRANSIT`은 허용되지 않는다 (`domain/shipment/entity/ShipmentStatus.java:4-9`).
4. `order.updateStatus(OrderStatus.IN_TRANSIT)` (`OrderShipmentCommandService.java:259-260`). `Order.updateStatus`는 `OrderStatus` 전이표로 검사하고 실패하면 `InvalidOrderStatusException`을 던진다 (`domain/order/entity/Order.java:113-121`).
5. 구매자에게 "상품이 출발하였습니다" 알림 1건 (`OrderShipmentCommandService.java:265-271`)
6. `updateSaleStatusToSold(orderId)` (`:276`) — SaleBid가 있으면 Sale을 `SOLD`로 바꾸고 판매자에게 알림 1건 (`:112-141`), OrderBid에 Sale이 있으면 같은 처리 (`:154-169`)
7. 창고 보관이면 창고 상태 갱신 (`:279-286`)
8. `updateOrderAndSaleBidStatusToCompleted` (`:289`) — OrderBid·SaleBid가 `MATCHED`면 `COMPLETED`로 변경. 이 메서드는 예외를 삼킨다 (`:413-440`).
9. 응답 `200 OK` (`OrderShipmentCommandController.java:48`)

**실제 동작: 4단계에서 항상 실패한다**
- `OrderStatus`에서 `IN_TRANSIT`으로 들어오는 전이는 `SHIPMENT_STARTED → IN_TRANSIT` 하나뿐이다 (`domain/order/entity/OrderStatus.java:28`).
- `SHIPMENT_STARTED`를 설정하는 코드는 저장소 어디에도 없다. `OrderStatus.java:13`, `:26-27`, 그리고 조회 표시 `domain/order/controller/query/OrderQueryController.java:207`뿐이다.
- 따라서 `IN_TRANSIT`은 어떤 주문 상태에서도 도달할 수 없다. 전이 규칙상 `null`일 때만 통과한다 (`Order.java:114`).

**(a) 실배송 일반 구매 입찰 주문**
- 생성: `OrderBidCommandService.createOrderBid` → `createOrderFromBid`가 Order를 `PENDING_PAYMENT`로 만든다 (`domain/order/service/command/OrderCommandService.java:81`). OrderBid는 `PENDING`이고 Sale에 연결되지 않는다 (`domain/order/service/command/OrderBidCommandService.java:95`).
- 결제·배송: 컨트롤러는 Kafka 이벤트만 발행한다 (`domain/order/controller/command/OrderCommandController.java:54`). 소비자 `OrderEventConsumer.processCompleteOrder`가 실배송이면 Order를 `PREPARING`으로 바꾸고 끝낸다 (`domain/order/service/kafka/OrderEventConsumer.java:166-230`, 특히 `:216-217`). OrderBid는 건드리지 않는다. 같은 일을 하는 동기 버전 `OrderCommandService.processPaymentAndShipment`(`:112-202`)는 컨트롤러에서 호출되지 않는다(`OrderCommandController.java:91-101` 주석 처리).
- PATCH: 주문이 `PREPARING`이다. `PREPARING`의 허용 전이는 `{IN_WAREHOUSE, SHIPMENT_STARTED}`뿐이다 (`OrderStatus.java:26`). `order.updateStatus(IN_TRANSIT)`가 `InvalidOrderStatusException`을 던진다 (`Order.java:117`).
- 서비스의 `catch (Exception e)`가 이를 `ShipmentException(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: ...")`로 감싸서 던진다 (`OrderShipmentCommandService.java:293-301`). 메서드가 `@Transactional`이므로 롤백된다.
- **저장되는 것: 없음.** 택배사·운송장·`IN_TRANSIT`(`:256`)은 롤백되고, 알림(`:266`)은 4단계 뒤라서 나가지 않는다.
- **응답: HTTP 404, 코드 `S001`** (`domain/shipment/exception/ShipmentErrorCode.java:12`의 상태값, `global/exception/GlobalExceptionHandler.java:459-470`).

**(b) 즉시 구매 주문**
- 생성: `OrderBidCommandService.createInstantOrderBid` → `OrderCommandService.createInstantOrder` (`OrderCommandService.java:220-319`). Order는 `PENDING_PAYMENT`(`:244`), 결제는 `paymentCommandService.processPayment`(`:304-309`)로 동기 처리되지만 **Order 상태는 바뀌지 않는다**. `domain/payment`에는 Order 상태 변경 코드가 없다.
- OrderBid는 `MATCHED`, Sale 연결, 즉시 구매 표시 (`OrderBidCommandService.java:189-207`, 특히 `:196`, `:198`). SaleBid도 `MATCHED` (`OrderCommandService.java:279-280`).
- PATCH: `PENDING_PAYMENT`에서 `IN_TRANSIT`은 허용 목록(`{PAYMENT_COMPLETED, COMPLETED, IN_WAREHOUSE}`, `OrderStatus.java:24`)에 없으므로 (a)와 같은 경로로 실패한다.
- 저장되는 것: 없음. 응답: 404, `S001`.

## 2. 배송 완료 감지

**누가·언제**: 사람이나 외부 호출이 아니라 스케줄러가 한다.
- `ShipmentBatchScheduler.scheduleShipmentStatusJob`, `@Scheduled(cron = "0 0 */6 * * *")` — `global/config/ShipmentBatchScheduler.java:34-44`. **6시간마다** 00:00, 06:00, 12:00, 18:00 (서버 시간대)에 실행된다.
- 실행 Job: `updateShipmentStatusesJob` (`domain/shipment/config/UpdateShipmentStatusesJobConfig.java:55-60`), 스텝 `updateShipmentStatusesStep` (`:63-82`).

**대상 조회**: `UpdateShipmentStatusesJobConfig.java:89-96`
- `SELECT s FROM OrderShipment s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL`, 페이지 크기 50 (`CHUNK_SIZE`, `:51`).

**실제로 실행되는 처리 코드**
- 스텝은 `new ShipmentItemProcessor(...)`를 쓴다 (`UpdateShipmentStatusesJobConfig.java:69-73`) → `domain/shipment/config/ShipmentItemProcessor.java:57-157`.
- 쓰이지 않는 비슷한 코드:
  - `shipmentItemProcessor()` 빈 (`UpdateShipmentStatusesJobConfig.java:104-177`) — 스텝에 연결되지 않았다. 이 빈은 `CjTrackingPlaywright`를 쓴다.
  - `parseCjLogisticsStatus` (`:186-220`, Jsoup) — 호출자가 없다.
  - `OrderShipmentCommandService.updateShipmentStatuses()` (`OrderShipmentCommandService.java:309-391`) — 호출자가 없다.
- 조회 방식: 헤드리스 Chromium(`PlaywrightBrowserManager`). 스텝 시작 시 열고 종료 시 닫는다 (`domain/shipment/config/BrowserManageStepListener.java:14-25`). 각 건마다 새 페이지를 열고 `tbody#statusDetail tr`을 기다린다 (`ShipmentItemProcessor.java:72-87`).

**택배사 상태 문자열 → 내부 상태**
- 마지막 `tr`의 5번째 `td` 텍스트를 쓴다 (`ShipmentItemProcessor.java:181`).
- `mapToShipmentStatus` (`ShipmentItemProcessor.java:220-226`):
  - `"배송완료"` → `DELIVERED`
  - `"배송출발"` → `OUT_FOR_DELIVERY`
  - 그 밖의 모든 값(빈 값 검사 전 포함) → `IN_TRANSIT`
- 현재 상태와 같으면 아무것도 하지 않는다 (`ShipmentItemProcessor.java:101-105`).

## 3. 배송 완료 판정 이후

배치 경로 기준 (`ShipmentItemProcessor.java:108-117`):
1. `OrderShipment` → `DELIVERED` (`:113`). `IN_TRANSIT`, `OUT_FOR_DELIVERY`에서 허용된다 (`domain/shipment/entity/ShipmentStatus.java:16-28`).
2. `orderService.completeOrder(orderId)` (`:116`, `OrderShipmentCommandService.java:191-229`).
   - `Order` → `COMPLETED` (`:204`). `PENDING_PAYMENT`, `IN_WAREHOUSE`, `IN_TRANSIT`에서 허용되고 `PREPARING`에서는 허용되지 않는다 (`OrderStatus.java:24-27`).
   - `updateSaleStatusToSold` (`:208`): Sale이 `SOLD`로 바뀔 수 있으면 `SOLD`로 바꾸고 판매자 알림 1건 (`:119-138`). OrderBid의 Sale도 같은 방식이다 (`:154-169`). `SaleStatus.canTransitionTo`는 `ON_AUCTION`, `SELLING`에서만 `SOLD`를 허용한다 (`domain/sale/entity/SaleStatus.java:15-22`).
   - 구매자에게 `"[completeOrder] 주문이 완료 처리되었습니다"` 알림 1건 (`OrderShipmentCommandService.java:211-217`).
3. `notificationService.notifyShipmentCompleted(order)` (`:117`) → 구매자에게 `"[배송 완료] ..."` 알림 1건 (`domain/notification/service/command/NotificationCommandService.java:219-231`).
4. 저장은 `JpaItemWriter`가 한다 (`UpdateShipmentStatusesJobConfig.java:241-246`).

**결과**
- Order: `COMPLETED`. Shipment: `DELIVERED`.
- 알림: **구매자 2건** (`completeOrder`의 "[completeOrder]", `notifyShipmentCompleted`의 "[배송 완료]"). **판매자 1건**은 SaleBid가 있고 Sale이 `SOLD`로 전이 가능할 때만 (`OrderShipmentCommandService.java:132-138`).
- **OrderBid·SaleBid는 바뀌지 않는다.** `COMPLETED` 전환은 `updateOrderAndSaleBidStatusToCompleted`(`:289`, 정의 `:413-440`)에만 있는데, 호출은 `updateTrackingInfo`뿐이고 그 경로는 1번에서 실패한다. 배치 경로와 check-status 경로(`:483-489`)는 이 메서드를 호출하지 않는다.

## 4. 주문 종류별 차이

**(a) 실배송 일반 구매 입찰 주문: 끝까지 가지 못한다**
- 1번에서 PATCH가 실패하므로 Shipment는 `IN_TRANSIT`이 되지 않고 배치 조회(`UpdateShipmentStatusesJobConfig.java:95`)에 잡히지 않는다. 3번 처리는 시작되지 않는다.
- 우회 경로(check-status)로 송장을 넣어 `IN_TRANSIT`을 만든 뒤 CJ가 "배송완료"를 돌려줘도 실패한다. 이 경로는 Order를 건드리지 않고 `shipment.updateStatus(DELIVERED)`(`OrderShipmentCommandService.java:486`) 후 `completeOrder`를 호출한다. `completeOrder`의 `PREPARING → COMPLETED`가 `InvalidOrderStatusException`을 던지고(`OrderStatus.java:26`), 이는 `ShipmentException`으로 감싸져 `:505-506`에서 다시 던져진다. 메서드 전체가 롤백된다.
- 결과: 주문 `PREPARING` 유지, 배송 `IN_TRANSIT` 유지(또는 롤백), 알림 0건, OrderBid `PENDING` 유지, SaleBid 없음.

**(b) 즉시 구매 주문: 주문·판매는 완료되지만 PATCH 경로로는 못 들어온다**
- PATCH는 (a)와 같이 실패한다. 배치에 들어가려면 우회 경로가 필요하다.
- check-status 경로에서 CJ가 "배송출발"을 주면 `OUT_FOR_DELIVERY`로 저장되고(`OrderShipmentCommandService.java:491-493`, `IN_TRANSIT → OUT_FOR_DELIVERY` 허용) 배치 대상이 된다. 이후 CJ가 "배송완료"를 주면 `completeOrder`가 성공한다. `PENDING_PAYMENT → COMPLETED`가 허용되기 때문이다(`OrderStatus.java:24`). Sale이 `ON_AUCTION` 또는 `SELLING`이면 `SOLD`가 된다.
- 결과: Order `COMPLETED`, Shipment `DELIVERED`, Sale `SOLD`(조건부), 구매자 알림 2건, 판매자 알림 1건(조건부). **OrderBid와 SaleBid는 `MATCHED`로 남는다.**

**차이 요약**: (a)는 `completeOrder`에서 `PREPARING → COMPLETED`가 막혀 롤백된다. (b)는 `PENDING_PAYMENT → COMPLETED`가 허용되어 주문과 판매가 완료된다. 둘 다 입찰 상태는 완료로 바뀌지 않는다.

## 5. 실패 처리

- 스텝 설정: `.chunk(50)`, `.faultTolerant().skip(Exception.class).skipLimit(50)` (`UpdateShipmentStatusesJobConfig.java:66-78`).
- **건 단위:** 처리 중 예외가 나면 그 건은 쓰기에서 빠지고 `SkipListener.onSkipInProcess`가 로그를 남긴다 (`:252-266`). 그 건의 DB 상태는 바뀌지 않는다. 다음 실행(6시간 뒤)에 다시 조회된다.
- **나머지 건:** Spring Batch의 기본 동작으로 보인다(프레임워크 동작이라 코드만으로는 확정할 수 없다). 처리 예외가 나면 청크 트랜잭션을 롤백하고 건별로 다시 처리한다. 같은 청크의 다른 건은 각자 트랜잭션으로 정상 처리된다. `completeOrder`는 `@Transactional` 참여 메서드라서 예외 시 트랜잭션을 rollback-only로 표시하는데, 이것도 청크 전체 롤백의 원인이 된다.
- **스킵 한도 초과:** 스킵 누적이 50을 넘으면 스텝이 실패하고 Job이 중단된다. 남은 건은 다음 실행까지 처리되지 않는다.
- **반복 실패가 생기는 대표 경우:** 스킵이 누적된다.
  - 상태가 `OUT_FOR_DELIVERY`인데 CJ 텍스트가 "배송완료"·"배송출발"이 아니면 `updateStatus(IN_TRANSIT)`가 `IllegalStateException`을 던진다 (`ShipmentItemProcessor.java:123-126`, `ShipmentStatus.java:23-28`). 매번 스킵된다.
  - `IN_TRANSIT` 건을 check-status로 다시 조회할 때도 `updateStatus(IN_TRANSIT)`가 같은 이유로 실패한다 (`OrderShipmentCommandService.java:473`, `:497`). 송장 등록 직후 in-memory 상태가 이미 `IN_TRANSIT`이기 때문이다.
  - 구매자 주문이 `PREPARING`인 건은 DELIVERED 처리 때 `completeOrder`가 실패해 매번 스킵된다.
- **페이징 문제 (추정):** 리더는 오프셋 페이징이고 `ORDER BY`가 없다 (`UpdateShipmentStatusesJobConfig.java:89-96`). 같은 실행 중 `DELIVERED`가 된 건은 WHERE 결과에서 빠져서, 다음 페이지 오프셋이 그만큼 밀린다. 해당 건들이 이번 실행에서 건너뛰어질 수 있다.

## 코드 의도와 실제 동작이 다른 곳

- `OrderShipment.updateTrackingInfo`는 송장 저장만 할 것 같지만 `IN_TRANSIT`을 전이 검사 없이 설정한다 (`OrderShipment.java:44`).
- `OrderShipmentCommandService.updateTrackingInfo`의 주석 "배송 상태가 변경되었으므로 주문 상태도 업데이트"(`:258`)와 달리, 그 주문 상태 전이(`IN_TRANSIT`)는 어떤 경로에서도 허용되지 않는다.
- `updateOrderAndSaleBidStatusToCompleted`는 예외를 로그만 남기고 삼킨다(`:436-439`). 그래서 실패해도 호출자는 모른다. 실제로는 1번 실패가 먼저 발생하므로 이 메서드는 도달하지 않는다.
- `mapToShipmentStatus`는 모르는 텍스트를 전부 `IN_TRANSIT`으로 취급한다 (`ShipmentItemProcessor.java:224`). "배송출발"이나 "배송완료"가 아닌 CJ 텍스트가 `OUT_FOR_DELIVERY` 건을 실패시키는 이유다.
- 배치 주석 "DELIVERY 완료 시 알림, Order 상태 완료 등도 여기서 처리 가능"(`UpdateShipmentStatusesJobConfig.java:101-102`)과 달리, 실제로 실행되는 처리는 `ShipmentItemProcessor`이고 `shipmentItemProcessor()` 빈은 죽은 코드다.
- `OrderShipmentCommandService.updateShipmentStatuses()`(`:306-308`)는 "전체 배송 상태 업데이트"라고 하지만 호출되지 않는다.
- `completeOrder`의 알림 문구에 `"[completeOrder]"` 디버그 접두어가 그대로 들어 있다 (`OrderShipmentCommandService.java:216`). 같은 완료 상황에 구매자 알림이 두 건 나가는 것도 의도와 다르다고 볼 수 있다.

## 확인하지 못한 것

- CJ 페이지의 실제 상태 문구(예: "배송중", "도착" 등)는 외부 사이트라서 확인하지 못했다. 3번 "IN_TRANSIT으로 떨어지는 텍스트"와 4번 check-status 경로의 성공 여부는 이 문구에 따라 달라진다.
- 페이징 누락과 청크 롤백 동작은 Spring Batch 프레임워크 동작에 기대는 추정이다. 실제 실행 로그나 테스트로 확인하지 않았다.
- 코드는 수정하지 않았고, 실행하거나 테스트하지도 않았다.
