## 1. 진입점과 처리 방식

- 진입점: `POST /order-bids/instant` (`C:89-110`). 요청 DTO는 `InstantOrderRequestDto` (`src/main/java/com/fream/back/domain/order/dto/InstantOrderRequestDto.java:20-29`): `saleBidId`, `addressId`, `warehouseStorage`, `paymentRequest`.
- 처리 단계:
  1. 로그인 이메일 추출 (`C:92`), 결제 요청에 이메일 설정 및 `orderId=null` 초기화 (`C:98`, `C:119-123`).
  2. `OrderBidCommandService.createInstantOrderBid` (`S:118-149`, `@Transactional`):
     1. 입력값 검증 (`S:123`, `S:154-167`)
     2. 구매자 조회 (`S:126`)
     3. 판매 입찰 및 판매 조회 (`S:129`, `S:172-184`). 입찰/판매 상태는 검사하지 않는다.
     4. `OrderCommandService.createInstantOrder` 호출 (`S:133`, `O:219-319`): 주문, 주문 항목, 배송, 판매 입찰 매칭, 창고 상태, 결제까지 처리
     5. `OrderBid` 생성 및 저장 (`S:142`, `S:189-207`)
- 동기 처리다. 이 경로에는 Kafka 발행이 없다 (`OrderEventProducer`, `PaymentEventProducer`는 다른 경로에서만 쓰인다). 주문, PG 결제 호출, 알림이 모두 같은 HTTP 요청과 같은 트랜잭션 안에서 끝난다.
- 응답 ID: `C:101-107`은 `createInstantOrderBid(...).getId()`를 반환한다. 따라서 응답의 ID는 **Order ID가 아니라 OrderBid의 ID**다. 컨트롤러 Javadoc(`C:83`)은 "생성된 주문 ID"라고 적지만 실제 값은 OrderBid ID다. 성공 메시지는 "즉시 구매가 성공적으로 처리되었습니다."(`C:109`).

## 3. 결제 수단별 결과와 즉시 구매의 성공 여부

공통 검증: `validatePaymentRequest`는 주문 ID, 이메일 일치와 `paidAmount > 0`만 확인한다 (`P:117-146`, 금액 검사는 `P:142-145`). 판매 가격(`saleBid.bidPrice`)과 요청 금액(`paidAmount`)을 비교하지 않는다. 카드 경로는 요청의 `paidAmount`를 그대로 PG에 청구한다 (`P:179`). 결제 요청 DTO의 `@NotNull`/`@Min(100)`도 실행되지 않는다. `C:90`의 `@Valid`는 최상위 DTO에만 걸려 있고 `paymentRequest` 필드(`DTO:28-29`)에는 `@Valid`가 없어 중첩 검증이 cascade되지 않는다.

결제 유형 분기: `P:67-80` (`CARD`, `ACCOUNT`, `GENERAL`, 그 외는 예외).

**(a) 카드 (`createCardPayment`, `P:157-225`)**
- `paymentInfoId`로 결제 정보를 조회한 뒤 PortOne 카드 결제를 호출한다 (`P:166`, `P:179` → `PG:229-295`).
- PG 응답이 HTTP 200이고 `body.code == 0`이면 정상 응답으로 받는다 (`PG:270-277`). 그다음 `response.status == "success"`일 때만 `PAID`로 바꾸고 `isSuccess = true`로 설정한다 (`P:203-206`). 그 외에는 `PENDING`으로 저장하고 예외 없이 계속 진행한다.
- PG가 실패로 응답한 경우 (두 가지로 나뉜다):
  - **HTTP 오류 또는 `code != 0`**: `PG:270-275`가 `PaymentProcessingException`을 던진다. 이 예외는 `P:218-219` → `P:89-94` → `O:312-318`(`OrderPaymentProcessingFailedException`으로 감쌈) → `S:145-146` → `S:212-218`을 거쳐 그대로 전파된다. `RuntimeException`이므로(`global/exception/GlobalException.java:10`) `@Transactional`이 롤백한다. 롤백되는 것은 Order, OrderItem, OrderShipment, SaleBid 상태, 창고 상태, Payment이다. Sale은 SOLD가 되지 않고 알림도 나가지 않는다. 응답은 `GlobalExceptionHandler`의 `OrderException` 핸들러가 만든다 (`src/main/java/com/fream/back/global/exception/GlobalExceptionHandler.java:325-332`). 이때 PG 측 취소 호출은 하지 않는다.
  - **`code == 0`이지만 `status != "success"`인 경우**: 예외가 없다. `CardPayment`가 `PENDING`으로 저장되고 (`P:203-208`), 알림이 나가고 (`P:83`), Sale이 SOLD가 되고 (`P:404`/`P:419`), OrderBid가 만들어지고, 응답은 성공이다. 즉 **카드 결제가 실패인데 즉시 구매가 성공으로 끝나는 경로가 있다.** PG의 `status` 값 체계(`"failed"` 등)는 저장소 밖이라 확인하지 못했다. 코드상 이 분기에 대한 처리는 없다.
- PG 호출 중 네트워크 예외(`RestClientException`)는 `PaymentApiException`이 되어 같은 방식으로 롤백된다 (`PG:286-294`).
- `PG:224-228`의 `@Retryable(maxAttempts=3)`은 실제로 동작하지 않는다. 저장소 어디에도 `@EnableRetry`가 없다. 재시도는 일어나지 않는다.
- 즉시 구매 경로에는 PG 취소 호출이 없다. `handleRefundIfNecessary`(`P:341-375`)는 `private`이고 호출처가 없다. `cancelPayment`는 다른 환불 경로(`P:564`)에서만 쓰인다.

**(b) 계좌이체 (`createAccountPayment`, `P:236-279`)**
- 은행명만 검증한다 (`P:243-248`). PG는 호출하지 않는다.
- `AccountPayment`를 `PENDING`, `isSuccess=false`로 저장한다 (`P:258-262`).
- 예외 없이 끝난다. 즉 응답은 성공이지만 **결제는 미확정 상태(PENDING)다.** 주문은 `PENDING_PAYMENT`, 판매 입찰은 `MATCHED`, 판매는 `SOLD`가 된다. 입금 확인이나 이를 완료로 바꾸는 경로는 이 흐름에 없다.

**(c) 일반 결제 (`createGeneralPayment`, `P:290-333`)**
- 클라이언트가 보낸 `impUid`가 비어 있지 않은지만 확인한다 (`P:297-300`). PortOne에 조회하거나 검증하지 않는다.
- 저장 시 바로 `isSuccess=true`, `PAID`로 설정한다 (`P:313-314`). 클라이언트 값을 신뢰하는 구조다.
- 예외 없이 끝나므로 응답은 성공이다.

**즉시 구매가 끝까지 성공하는 경우**
- 카드 승인(`status == "success"`) 경우: 결제 확정, 응답 성공. 주문 상태는 여전히 `PENDING_PAYMENT`다 (6번 참조).
- 카드 HTTP/`code` 실패: 전체 롤백, 실패 응답.
- 카드 `code==0`이지만 `status!="success"`: 결제 PENDING인데 성공 응답 (버그 가능성 높음).
- 계좌이체: 결제 PENDING인데 성공 응답.
- 일반 결제: 검증 없이 PAID, 성공 응답.

## 4. 알림 수신자, 시점, 방식

- 수신자 2명 (`P:434-456`):
  - 구매자: `NotificationType.BID`, `NotificationCategory.SHOPPING`, 메시지 "결제가 완료되었습니다. 주문 ID: {orderId}" (`P:438-443`).
  - 판매자: 같은 타입/카테고리, 메시지 "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}" (`P:449-454`).
- 시점: `processPayment` 안에서 결제 저장 직후, 같은 트랜잭션 안에서 실행된다 (`P:83` → `P:383-403` → `P:416`). 결제 상태(PENDING/PAID)와 관계없이 발송된다. 따라서 계좌이체(PENDING)와 `code==0 && status!="success"` 카드도 "결제가 완료되었습니다"를 받는다.
- 방식:
  - 알림은 DB에 저장된다 (`N:52-53`).
  - 저장 후 `sendRealTimeNotification`이 실행된다 (`N:56-57`). Redis에 해당 이메일의 연결 키가 있을 때만 STOMP WebSocket으로 `convertAndSendToUser`로 보낸다 (`N:303-313`). 연결이 없으면 DB에만 남는다 (`N:320-322`).
  - 이메일이나 푸시는 이 경로에서 보내지 않는다.
- 주의: WebSocket 전송은 트랜잭션 커밋 전에 일어난다. 이후 `OrderBid` 저장 등에서 실패해 롤백되면 DB 알림 행은 사라지지만 이미 보낸 WebSocket 메시지는 취소할 수 없다.
- 알림과 Sale 상태 변경은 `try/catch`로 감싸져 있어 실패해도 결제는 실패하지 않는다 (`P:421-425`, `P:457-461`).

## 5. 처리 완료 후 주문의 최종 상태와 창고 보관

처리가 정상 종료되었을 때 (카드 승인 또는 계좌/일반 결제):

| 대상 | 최종 상태 | 근거 |
|---|---|---|
| `Order.status` | `PENDING_PAYMENT` (변화 없음) | `O:244`. 즉시 구매 경로에 전이 없음 |
| `Payment` | 카드 승인: `PAID` / 계좌: `PENDING` / 일반: `PAID` | `P:203-206`, `P:260`, `P:314` |
| `OrderShipment.status` | `PENDING` | `OrderShipmentCommandService:67` |
| `SaleBid.status` | `MATCHED` | `O:279-280`, `SaleBid.java:58-60` |
| `OrderBid` | `status=MATCHED`, `isInstantPurchase=true` | `S:196`, `S:205`, `OrderBid.java:97-99` |
| `Sale.status` | `SOLD` | `P:404`, `P:419` |

`PAYMENT_COMPLETED`, `PREPARING` 등으로 바뀌는 전이는 `processPaymentAndShipment`(`O:112`, `O:165-176`)와 Kafka 소비자 `OrderEventConsumer`(`src/main/java/com/fream/back/domain/order/service/kafka/OrderEventConsumer.java:192-217`)에만 있다. 즉시 구매는 이를 호출하지 않는다.

**창고 보관 선택 시**
- 요청의 `warehouseStorage` 값은 `C:105`를 거쳐 `O:createInstantOrder`의 `isWarehouseStorage` 인자로 전달되지만 **본문에서 쓰이지 않는다** (`O:221`, 본문 `O:224-311`에서 참조 없음).
- 실제로 창고 상태를 바꾸는 조건은 판매자 쪽 `sale.isWarehouseStorage()` 하나다 (`O:292-293`). 그 결과:
  - 판매 설정이 true이면 구매자가 false를 골라도 `WarehouseStorage`가 `ASSOCIATED_WITH_ORDER`로 바뀐다.
  - 판매 설정이 false이면 구매자가 true를 골라도 아무 변화가 없다.
- `Order.warehouseStorage`에 연결하는 코드(`order.assignWarehouseStorage`)도 이 경로에는 없다 (`O:171`은 다른 경로, `OrderEventConsumer:200`도 Kafka 경로).
- 비교: 일반 주문 경로(`O:163`)는 `requestDto.isWarehouseStorage()`를 실제로 사용한다. 즉시 구매만 구매자 선택을 무시한다.

## 주석/메서드 이름과 실제 동작이 다른 부분 (실제 동작 기준)

1. 응답 ID: Javadoc은 "주문 ID"라고 하지만 실제로는 OrderBid ID다 (`C:83`, `C:101-107`).
2. `createInstantOrder`의 `isWarehouseStorage` 인자는 무시된다 (`O:221`). 창고 보관 여부는 판매 설정만 본다.
3. "결제가 완료되었습니다" 알림과 `SOLD` 처리는 실제 결제가 확정되지 않은 계좌이체, PG 실패 상태 응답 카드에도 나간다 (`P:83`, `P:383-426`).
4. 카드 실패 처리는 `code`로만 판단하고 `status`는 PAID 여부에만 쓰인다 (`P:203-206`, `PG:270`). `status != success`는 실패로 취급되지 않는다.
5. `@Retryable`은 선언만 있고 `@EnableRetry`가 없어 재시도가 없다 (`PG:224-228`).
6. 결제 금액이 판매가와 같은지 확인하지 않는다 (`P:142-145`, `P:179`). 중첩 DTO의 `@Min(100)`도 적용되지 않는다 (`DTO:28-29`, `C:90`).
7. 판매 입찰 및 판매의 상태를 검사하지 않는다 (`S:172-184`). 이미 `MATCHED`/`SOLD`인 입찰도 조건 검사 없이 다시 매칭된다. 중복 구매를 막는 DB 제약은 이 조사에서 확인하지 않았다.
