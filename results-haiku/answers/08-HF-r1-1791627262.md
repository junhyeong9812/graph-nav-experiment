# 답변: 구매자 배송의 운송장 등록부터 배송 완료까지

조사 방식: 정적 코드 읽기만 수행했다. 앱을 실행하거나 DB/Kafka에 붙지 않았다. 경로는 저장소 루트 기준이며, `C` = `src/main/java/com/fream/back` 이다.

## 요약

- **운송장 등록은 현재 코드에서 어떤 주문도 성공하지 못한다.** `Order` 가 `IN_TRANSIT` 으로 가려면 `SHIPMENT_STARTED` 를 거쳐야 하는데, 이 상태를 세팅하는 코드가 없다.
- **실제로 도는 배송 완료 감지는 6시간마다의 Spring Batch 잡이다.** 실행 처리는 `ShipmentItemProcessor` (Playwright) 이다. Jsoup 기반 `shipmentItemProcessor()` 빈과 `updateShipmentStatuses()` 는 실행되지 않는다.
- **(a) 실배송 일반 구매 입찰 주문은 배송 완료 처리까지 가지 못한다.** 주문이 `PREPARING` 에서 `COMPLETED` 로 갈 수 없다.
- **(b) 즉시 구매 주문은** `check-status` 엔드포인트로 `DELIVERED` 까지는 갈 수 있다. 다만 입찰(`OrderBid`/`SaleBid`) 이 `COMPLETED` 로 바뀌지 않는다.
- 참고로 `nav/domain/shipment/README.md` 의 "배송 완료 시 입찰 COMPLETED" 와 "운송장 등록 정상 동작" 설명은 코드와 다르다. 아래는 코드 기준이다.

## 1. 운송장 등록 요청

**API**: `PATCH /shipments/order/{shipmentId}/status`, 본문 `OrderShipmentRequestDto`(courier, trackingNumber). `C/domain/shipment/controller/command/OrderShipmentCommandController.java:33-49`

**설계된 흐름 (성공을 가정할 때)** — `C/domain/shipment/service/command/OrderShipmentCommandService.java:239-303`

1. 빈 값 검사 (`:243-246`).
2. `OrderShipment` 에 택배사·송장을 넣고 `status = IN_TRANSIT` 을 **직접 대입**한다. 이 메서드는 `canTransitionTo` 검사를 하지 않는다. `C/domain/shipment/entity/OrderShipment.java:41-45`. 상태 `PENDING → IN_TRANSIT`.
3. `Order` 를 `IN_TRANSIT` 으로 전이한다 (`OrderShipmentCommandService.java:260`).
4. 구매자에게 알림 1건: "상품이 출발하였습니다" (`:266-271`).
5. `updateSaleStatusToSold` 호출 (`:276`). 판매가 `SOLD` 로 바뀌고 판매자에게 알림이 갈 수 있다 (`:112-183`). 등록 시점에 판매 완료가 처리되도록 짜여 있다.
6. 창고 보관 상태 갱신 (`:279-286`).
7. `OrderBid`/`SaleBid` 를 `MATCHED → COMPLETED` (`:289`, `:413-440`). 등록 시점에 입찰이 완료되도록 짜여 있다.

**실제 동작: (a), (b) 모두 실패한다.**

- **실패 지점**: `:260` 의 `order.updateStatus(OrderStatus.IN_TRANSIT)` → `C/domain/order/entity/Order.java:113-121` 에서 `canTransitionTo` 검사 실패 → `InvalidOrderStatusException`.
  - `C/domain/order/entity/OrderStatus.java:26` — `PREPARING` 의 다음 허용 상태는 `IN_WAREHOUSE`, `SHIPMENT_STARTED` 뿐이다.
  - `C/domain/order/entity/OrderStatus.java:28` — `IN_TRANSIT` 으로 갈 수 있는 상태는 `SHIPMENT_STARTED` 뿐이다.
  - `SHIPMENT_STARTED` 를 세팅하는 코드는 없다. 전체 소스 검색 결과 열거형 정의와 전이 규칙에만 나온다.
- **(a) 주문 상태가 `PREPARING` 인 근거**: 결제·배송 처리 API 는 Kafka 로만 발행한다 (`C/domain/order/controller/command/OrderCommandController.java:54`, `C/domain/order/service/kafka/OrderEventProducer.java:43`). 소비자 `C/domain/order/service/kafka/OrderEventConsumer.java:195` 가 `PAYMENT_COMPLETED` 로, `:216-218` 이 `PREPARING` 으로 바꾼다. 동기 경로 `C/domain/order/service/command/OrderCommandService.java:175-176` 도 같다.
- **(b) 즉시 구매 주문 상태가 `PENDING_PAYMENT` 인 근거**: `C/domain/order/service/command/OrderCommandService.java:244` 에서 `PENDING_PAYMENT` 로 생성하고, `:305` 에서 결제만 처리한다. 이 메서드 어디에도 주문 상태 전이가 없다. `OrderStatus.java:24` 에서 `PENDING_PAYMENT → IN_TRANSIT` 은 허용되지 않는다.
- **저장되는 것: 없다.** 예외가 `@Transactional` 서비스 밖으로 나가 롤백된다. 메모리에서 바꾼 송장·`IN_TRANSIT` 도 롤백된다. 알림은 `:260` 뒤에 있어 만들어지지 않는다.
- **응답**: `:295-301` 의 `catch (Exception e)` 가 모든 예외를 `ShipmentException(SHIPMENT_NOT_FOUND)` 로 감싼다. `C/domain/shipment/exception/ShipmentErrorCode.java:12`. `C/global/exception/GlobalExceptionHandler.java:459-473` 이 이를 **HTTP 404, 코드 `S001`, 메시지 "배송 정보를 찾을 수 없습니다."** 로 응답한다. 실제 원인은 `:296` 의 로그에만 남는다. 컨트롤러에는 try/catch 가 없다 (`OrderShipmentCommandController.java:41-48`).

## 2. 배송 완료 감지

**누가, 언제, 어떻게**: 사람이 하지 않는다. 스케줄러가 한다.

- **주기**: `C/global/config/ShipmentBatchScheduler.java:34-44`, `@Scheduled(cron = "0 0 */6 * * *")`. 매 6시간, 0·6·12·18시 정각(서버 타임존). `@EnableScheduling` 은 `C/domain/weather/config/WeatherDataScheduler.java:16` 등에서 켜져 있어 전역 적용된다.
- **대상**: `C/domain/shipment/config/UpdateShipmentStatusesJobConfig.java:87-97`. JPQL `status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND trackingNumber IS NOT NULL`, 페이지·청크 크기 50 (`:51`, `:94`).
- **실제로 실행되는 스텝**: `UpdateShipmentStatusesJobConfig.java:62-81`. 프로세서로 `new ShipmentItemProcessor(...)` 를 넣는다 (`:69-73`). 쓰기는 `JpaItemWriter` (`:239-245`).
- **실제로 실행되는 처리 코드**: `C/domain/shipment/config/ShipmentItemProcessor.java:57-156` 의 `process`.
  - Playwright 페이지로 `https://trace.cjlogistics.com/next/tracking.html?wblNo=<송장>` 을 연다 (`:81-87`).
  - `tbody#statusDetail tr` 의 마지막 행 5번째 `td` 를 읽는다 (`:181`).
- **실행되지 않는 비슷한 코드**
  - `UpdateShipmentStatusesJobConfig.java:104-177` 의 `shipmentItemProcessor()` 빈. 스텝에 연결되지 않는다. 내부의 `parseCjLogisticsStatus` (`:186-220`, Jsoup 직접 조회)도 호출처가 없다.
  - `C/domain/shipment/service/command/OrderShipmentCommandService.java:309-391` 의 `updateShipmentStatuses()`. 호출처가 없다.
  - `CjTrackingPlaywright` 는 `check-status` 경로(`OrderShipmentCommandService.java:477`)에서만 쓰인다.

**택배사 문자열 → 내부 상태**: `ShipmentItemProcessor.java:220-226`.

- `"배송완료"` → `DELIVERED`
- `"배송출발"` → `OUT_FOR_DELIVERY`
- 그 밖의 모든 문자열 → `IN_TRANSIT`

현재 상태와 같으면 건너뛴다 (`:101-104`). 전이가 허용되지 않으면 엔티티가 `IllegalStateException` 을 던진다 (`C/domain/shipment/entity/OrderShipment.java:47-55`).

## 3. 배송 완료 판정 이후

`ShipmentItemProcessor.java:108-117` 의 `DELIVERED` 분기 순서:

1. `OrderShipment.updateStatus(DELIVERED)` (`:113`). `IN_TRANSIT` 과 `OUT_FOR_DELIVERY` 에서 `DELIVERED` 로 가는 것은 허용된다. `C/domain/shipment/entity/ShipmentStatus.java:72-90`.
2. `orderService.completeOrder(orderId)` (`:116`) → `OrderShipmentCommandService.java:191-229`.
   - `OrderBid` 조회 (`:196`). 없으면 예외.
   - `Order.updateStatus(COMPLETED)` (`:204`). 허용 여부는 아래 4번 참조.
   - `updateSaleStatusToSold` (`:208`). `SaleBid.getSale()` 이 `SOLD` 로 전이 가능하면(`SELLING`, `ON_AUCTION`) `Sale` 을 `SOLD` 로 바꾸고 창고 상태를 갱신한 뒤 판매자에게 알림을 보낸다 (`:119-138`). 같은 `Sale` 이면 두 번째 분기(`:156`)에서는 이미 `SOLD` 라서 알림이 중복되지 않는다. `C/domain/sale/entity/SaleStatus.java:21-22`.
   - 구매자에게 "[completeOrder] 주문이 완료 처리되었습니다" (`:211-217`).
3. 프로세서에서 `notifyShipmentCompleted(order)` (`:117`, `C/domain/notification/service/command/NotificationCommandService.java:219-233`). 구매자에게 "[배송 완료]..." 알림. 이 메서드의 예외는 삼켜진다.

**알림 건수**

- 구매자: 배치 경로에서는 **2건**. `check-status` 경로에서는 `completeOrder` 의 1건만 간다 (`OrderShipmentCommandService.java:483-489`).
- 판매자: `Sale` 이 `SELLING` 또는 `ON_AUCTION` 일 때만 **1건**. 그 밖에는 0건.

**입찰 상태**

- `OrderBid`/`SaleBid` 를 `COMPLETED` 로 바꾸는 코드는 배송 완료 경로(`completeOrder`, 프로세서)에 없다.
- 호출처는 `updateTrackingInfo` 의 `:289` 하나뿐이다.
- 따라서 배송이 완료돼도 입찰은 `MATCHED` 로 남는다.

## 4. 주문 종류별 차이

**(a) 실배송 일반 구매 입찰 주문: 끝까지 가지 못한다.**

- 1번에서 보았듯 운송장 등록이 실패하므로 `IN_TRANSIT` 이 되지 않아 배치 대상이 아니다.
- 우회 경로: `POST /shipments/order/{id}/check-status` (`OrderShipmentCommandController.java:58-94`)는 CJ 상태가 `배송출발` 이면 `updateAndCheckShipmentStatus` 가 `OUT_FOR_DELIVERY` 를 **커밋**한다. 주문 상태는 확인하지 않는다 (`OrderShipmentCommandService.java:491-493`, `:503`). 이후 배치가 이 건을 집어 `DELIVERED` 를 시도한다.
- `DELIVERED` 시도: `completeOrder` 의 `Order.updateStatus(COMPLETED)` (`:204`)에서 `PREPARING → COMPLETED` 가 막힌다 (`OrderStatus.java:26`). 예외는 `:221-227` 에서 `ShipmentException(ORDER_NOT_FOUND_FOR_SHIPMENT)` 로 감싸진다. 응답은 **404 `S102`** (`ShipmentErrorCode.java:20`).
  - 배치라면 프로세서의 `catch` 에서 스킵된다 (`ShipmentItemProcessor.java:133-145`). 건은 `OUT_FOR_DELIVERY` 에 머물고, 주문은 `PREPARING` 그대로다.
  - `check-status` 라면 트랜잭션이 롤백되어 `DELIVERED` 도 저장되지 않는다 (`OrderShipmentCommandService.java:483-489`).
- 결과: 주문 `PREPARING` 유지. 알림 0건. 입찰 `MATCHED` 유지. 판매 상태 변화 없음.

**(b) 즉시 구매로 만들어진 주문: 주문 완료까지는 가지만 입찰 완료가 빠진다.**

- 주문은 `PENDING_PAYMENT` 로 생성된다 (`OrderCommandService.java:244`). `PENDING_PAYMENT → COMPLETED` 는 허용된다 (`OrderStatus.java:24`). 그래서 `completeOrder` 의 `:204` 를 통과한다.
- 진입 경로별 결과
  - 운송장 등록(PATCH): 1번에서 보았듯 실패한다.
  - `check-status`, CJ 상태 `배송완료`: 메모리의 `IN_TRANSIT`(`OrderShipmentCommandService.java:473`)에서 `DELIVERED`(`:486`)로 가고 `completeOrder`(`:489`)가 실행된다. **끝까지 진행된다.** 구매자 알림 1건, 판매자 알림 1건(조건부), 주문 `COMPLETED`, 판매 `SOLD`.
  - 배치: 먼저 `check-status` 로 `OUT_FOR_DELIVERY` 가 커밋되어 있어야 대상이 된다. 그 뒤 `DELIVERED` 처리는 위와 같다. 구매자 알림 2건.
- 두 경우 모두 입찰은 `MATCHED` 로 남는다. 3번에서 보았듯 입찰 완료 처리가 없기 때문이다.
- 참고 1: `check-status` 에서 CJ 상태가 `배송완료`/`배송출발` 이 아닌 일반 "배송 중" 류 문자열이면 `:495-497` 에서 `IN_TRANSIT → IN_TRANSIT` 전이 실패(`ShipmentStatus.java:72-78`) → `EXTERNAL_TRACKING_SERVICE_ERROR`(503, `ShipmentErrorCode.java:30`) → 롤백. 즉 이 경로는 중간 상태 조회에서 항상 실패한다.
- 참고 2: `createInstantOrder` 는 결제 후 주문 상태를 `PAYMENT_COMPLETED`/`PREPARING` 으로 바꾸지 않는다 (`OrderCommandService.java:244-305`). 결제는 완료됐는데 주문은 `PENDING_PAYMENT` 로 남는다.

## 5. 실패 처리 (주기 처리 중 한 건 실패)

설정: `UpdateShipmentStatusesJobConfig.java:75-77` — `faultTolerant().skip(Exception.class).skipLimit(50)`. 건너뛴 건은 `:251-268` 의 리스너가 로그로 남긴다.

**실패한 건**

- 그 건의 청크 트랜잭션이 롤백된다. 상태 변경, `completeOrder` 로 만든 주문·판매 변경, 알림 DB 행이 모두 되돌아간다.
- 스킵된다. 건은 `IN_TRANSIT`/`OUT_FOR_DELIVERY` 로 남아 다음 6시간 주기에 다시 대상이 된다.
- 예외: 알림 실시간 푸시는 트랜잭션 밖에서 즉시 나간다 (`NotificationCommandService.java:57`, `:303`). 그래서 롤백된 알림이 WebSocket 으로 먼저 전달될 수 있다.

**나머지 건**

- 청크가 롤백된 뒤 Spring Batch 가 청크를 한 건씩 다시 처리한다(scan 모드). 정상 건은 각자 트랜잭션으로 커밋된다. 이미 한 번 조회한 Playwright 페이지는 다시 조회된다. 이 동작은 Spring Batch 의 fault-tolerant 기본 동작에 근거한 것이며, 실행해 확인하지는 않았다.

**스킵이 50건을 넘으면**

- 스텝이 실패하고 잡이 종료된다. 남은 건은 이번 주기에 처리되지 않고 다음 주기로 넘어간다.

**추가로 확인된 문제 (실행으로 검증하지 않음)**

- `JpaPagingItemReader` 는 오프셋 페이지 방식이고 `ORDER BY` 가 없다 (`UpdateShipmentStatusesJobConfig.java:87-97`). 청크가 쓰이면서 `DELIVERED` 가 된 건은 조회 조건에서 빠진다. 그러면 다음 페이지의 오프셋이 밀려 일부 건이 이번 실행에서 건너뛰어질 수 있다.
- `OUT_FOR_DELIVERY` 건에서 CJ 상태가 `배송출발`/`배송완료` 가 아니면 `OUT_FOR_DELIVERY → IN_TRANSIT` 이 막혀 매번 스킵된다 (`ShipmentItemProcessor.java:123-126`, `ShipmentStatus.java:79-84`).

## 확인하지 못한 것 / 한계

- 정적 읽기만 했다. 실제 DB, Kafka, CJ 페이지, Playwright 는 실행하지 않았다.
- "`SHIPMENT_STARTED` 를 세팅하는 코드가 없다"는 주장은 저장소 전체 텍스트 검색 기준이다. DB에 직접 넣는 경우는 배제하지 못했다.
- 배치 reader 의 JPQL 이 열거형 필드를 문자열 리터럴(`'IN_TRANSIT'`)과 비교하는데, Hibernate 에서 이것이 실제로 파싱·실행되는지는 확인하지 못했다. 이 부분은 실행해 봐야 한다.
