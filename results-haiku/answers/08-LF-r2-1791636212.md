# 답: 구매자 배송은 운송장 등록부터 배송 완료까지 어떻게 처리되나

코드는 읽기만 했고 수정하지 않았다. 앱 실행과 테스트는 하지 않았고, 모든 판단은 정적으로 읽은 코드에 근거한다. 근거 경로는 `src/main/java/com/fream/back/` 기준 상대 경로로 적었다(줄 번호는 해당 파일 기준).

요약: **정상 운송장 등록(PATCH)은 실배송 일반 입찰 주문과 즉시 구매 주문 모두에서 실패한다.** 실패 지점은 같은 곳(`Order.updateStatus(IN_TRANSIT)`)이고, 응답은 404 `S001`이며 DB에는 아무것도 남지 않는다. 그래서 배치의 배송 완료 처리는 운영상 정상 송장 등록 흐름으로는 도달하지 않고, 수동 `check-status`로 `OUT_FOR_DELIVERY`가 된 건에서만 실행된다.

---

## 1. 운송장 등록 요청

**진입 API**: `PATCH /shipments/order/{shipmentId}/status` (body: `courier`, `trackingNumber`)
- `src/main/java/com/fream/back/domain/shipment/controller/command/OrderShipmentCommandController.java:33-41` → `OrderShipmentCommandService.updateTrackingInfo`
- 컨트롤러와 서비스 어디에도 관리자/소유자 검사가 없다(인증만 필요).

**의도된 처리 순서** (`src/main/java/com/fream/back/domain/shipment/service/command/OrderShipmentCommandService.java:238-301`, 한 트랜잭션)
1. `courier`/`trackingNumber` 공백 검사 → `S004`(400): `:243-246`
2. `OrderShipment` 조회, 없으면 `S001`: `:249-253`
3. `OrderShipment.updateTrackingInfo` → 택배사·송장 저장, `status=IN_TRANSIT`. **상태 전이 검증 없음**: `src/main/java/com/fream/back/domain/shipment/entity/OrderShipment.java:41-45`, 호출 `:256`
4. `Order.updateStatus(IN_TRANSIT)`: `:260`
5. 구매자 알림 "상품이 출발하였습니다": `:266-271`
6. `updateSaleStatusToSold(orderId)` → Sale `SOLD`, 창고 보관 시 창고 `SOLD`, 판매자 알림: `:276`, 본문 `:112-183`
7. 창고 보관 건이면 창고 `SOLD`: `:279-286`
8. `OrderBid`/`SaleBid` → `COMPLETED`: `:289`, 본문 `:413-440`

**의도된 상태 변화**: OrderShipment `PENDING → IN_TRANSIT`, Order → `IN_TRANSIT`, Sale → `SOLD`, OrderBid/SaleBid `MATCHED → COMPLETED`. 알림은 구매자 1건.

**(a) 실배송 일반 구매 입찰 주문: 끝까지 실패한다**

주문이 만들어지고 결제·배송 처리되는 과정:
- 입찰 생성: `OrderBidCommandService.java:60`(주문 생성), `:100`(`orderBid.assignOrder` → `OrderBid.java:60-78`, 여기서 `MATCHED`). 주문 상태는 `PENDING_PAYMENT`(`OrderCommandService.java:81`).
- 결제·배송 Kafka 소비: `src/main/java/com/fream/back/domain/order/service/kafka/OrderEventConsumer.java:166-230`. 결제 처리 `:171`, `OrderShipment` PENDING 생성 `:181`, `PAYMENT_COMPLETED` `:195`, 실배송 분기 `PREPARING` `:216-218`.
- 따라서 등록 시점 상태: Order `PREPARING`, OrderShipment `PENDING`(송장 없음), OrderBid `MATCHED`.

실패 과정:
1. `OrderShipmentCommandService.java:260` → `Order.updateStatus(IN_TRANSIT)`: `src/main/java/com/fream/back/domain/order/entity/Order.java:113-121`에서 `canTransitionTo` 실패 → `InvalidOrderStatusException`(`:117`).
2. 전이표상 `PREPARING`은 `{IN_WAREHOUSE, SHIPMENT_STARTED}`만 허용(`src/main/java/com/fream/back/domain/order/entity/OrderStatus.java:26`). `IN_TRANSIT`은 `SHIPMENT_STARTED`에서만 올 수 있고, `SHIPMENT_STARTED`를 설정하는 코드는 없다(`grep` 확인).
3. 예외는 `OrderException → GlobalException → RuntimeException`이며 `ShipmentException`이 아니므로 `:293`의 `catch (ShipmentException)`을 통과하고 `:295`의 `catch (Exception)`에서 `ShipmentException(SHIPMENT_NOT_FOUND)`으로 감싸진다(`:297-301`).
4. 예외가 트랜잭션 밖으로 나가 **전체 롤백**. 앞서 바꾼 엔티티 값도 저장되지 않는다.
5. `GlobalExceptionHandler`의 `ShipmentException` 핸들러(`src/main/java/com/fream/back/global/exception/GlobalExceptionHandler.java:459-470`)가 응답한다. `S001`의 HTTP 상태는 404(`src/main/java/com/fream/back/domain/shipment/exception/ShipmentErrorCode.java:12`).

**응답**: HTTP 404, body `{code:"S001", message:"배송 정보를 찾을 수 없습니다."}`. 메시지는 enum 기본 문구이고 실제 원인(상태 전이 불가)은 숨는다.

**저장되는 것**: 없음. 송장·택배사는 null 그대로, OrderShipment `PENDING`, Order `PREPARING`, OrderBid `MATCHED`. 알림도 없다(알림은 `:266`이 `:260` 뒤에 있어 도달하지 않음).

보조 실패 지점: 설령 `:260`을 통과해도 `:276` → `updateSaleStatusToSold`의 `:116`(`saleBidQueryService.findByOrderId`, try 밖)이 SaleBid가 없는 일반 입찰 주문에서 `IllegalArgumentException`을 던진다(`src/main/java/com/fream/back/domain/sale/service/query/SaleBidQueryService.java:26-29`). SaleBid는 판매자가 구매 입찰에 즉시 판매할 때만 연결된다(`src/main/java/com/fream/back/domain/sale/service/command/SaleBidCommandService.java:70-83`). 이 경우도 `S001`로 끝난다.

## 2. 배송 완료 감지

**누가/언제/어떻게**: 시스템이 주기 배치로 감지한다. 사람이 호출하는 수동 경로도 있다.

- **주기**: `src/main/java/com/fream/back/global/config/ShipmentBatchScheduler.java:34` `@Scheduled(cron = "0 0 */6 * * *")` → 6시간마다, 매일 0·6·12·18시 정각(서버 기본 타임존). 실행 예외는 `printStackTrace`로만 남는다(`:41-42`).
- **대상**: `status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND trackingNumber IS NOT NULL` (`src/main/java/com/fream/back/domain/shipment/config/UpdateShipmentStatusesJobConfig.java:95`). 주문 상태는 조건이 아니다. 페이지 크기는 청크 크기 50(`:94`), 정렬(ORDER BY)은 없다.
- **실제로 실행되는 처리 코드**: Step이 `new ShipmentItemProcessor(...)`를 쓴다(`UpdateShipmentStatusesJobConfig.java:69-75`) → `src/main/java/com/fream/back/domain/shipment/config/ShipmentItemProcessor.java:57` `process()`.
  - 브라우저: `BrowserManageStepListener.java:15-17`에서 Step 시작 시 열고 `afterStep`에서 닫는 공유 Playwright 브라우저. 건마다 페이지를 열어 `ShipmentItemProcessor.java:28`의 `https://trace.cjlogistics.com/next/tracking.html?wblNo=` + 운송장으로 이동(`:72`, `:87` 셀렉터 대기).
  - 파싱: `tbody#statusDetail tr`의 마지막 행, 5번째 `td` 텍스트(`:181`, trim).
- **실행되지 않는 비슷한 코드**(구분 필요):
  - `OrderShipmentCommandService.updateShipmentStatuses()`(`OrderShipmentCommandService.java:309`): 호출처 없음.
  - `UpdateShipmentStatusesJobConfig.shipmentItemProcessor()`(`:106`): 호출처 없음. 주석은 이 빈이 배송 완료 처리를 한다고 하지만 Step은 다른 processor를 쓴다.
  - `UpdateShipmentStatusesJobConfig.parseCjLogisticsStatus()`(`:186`): private, 미사용(Jsoup 방식).
  - `CjTrackingPlaywright.getCurrentTrackingStatus()`: 배치가 아니라 수동 `check-status`(`OrderShipmentCommandService.java:477`)에서만 사용된다.
- **수동 경로**: `POST /shipments/order/{id}/check-status`(및 `-string`), `src/main/java/com/fream/back/domain/shipment/controller/command/OrderShipmentCommandController.java:58-94` → `updateAndCheckShipmentStatus`(`OrderShipmentCommandService.java:452-516`). 이 경로는 `:473`에서 송장을 넣으며 `IN_TRANSIT`으로 만들고, **주문 상태는 건드리지 않는다**.
  - CJ 결과가 "배송중"(기본값)이면 `:497`의 `updateStatus(IN_TRANSIT)`가 이미 `IN_TRANSIT`인 엔티티에 대해 호출되어 `IllegalStateException` → `S302`(503)로 실패하고 롤백된다. 즉 "배송중"은 항상 실패한다.
  - "배송출발"이면 `OUT_FOR_DELIVERY`로 저장되어 커밋된다(`:491-493`). 이 상태가 배치 대상이 된다.
  - "배송완료"면 `:486` → `completeOrder`(`:489`) 경로로 간다.

**택배사 문자열 → 내부 상태**: `ShipmentItemProcessor.java:220-226`
- `"배송완료"` → `DELIVERED`
- `"배송출발"` → `OUT_FOR_DELIVERY`
- 그 외 모두 → `IN_TRANSIT` (정확 일치 비교, 알 수 없는 문자열도 `IN_TRANSIT`)

**배치 처리의 상태 분기**: 같은 상태면 조기 반환(`ShipmentItemProcessor.java:101-104`). `DELIVERED`면 `:112-117`. `OUT_FOR_DELIVERY`면 전이 후 저장. 그 외는 `updateStatus(IN_TRANSIT)`. 예: DB가 `OUT_FOR_DELIVERY`인데 CJ 문자열이 알 수 없는 값이면 `OUT_FOR_DELIVERY → IN_TRANSIT`이 `ShipmentStatus`상 불허되어 예외(`ShipmentStatus.java:23-28`).

## 3. 배송 완료 판정 이후

배치 경로(`ShipmentItemProcessor.java:112-117`) 기준. 순서는 다음과 같다.

1. **OrderShipment**: `updateStatus(DELIVERED)`(`ShipmentItemProcessor.java:113`). `IN_TRANSIT`과 `OUT_FOR_DELIVERY` 모두 `DELIVERED` 전이 허용(`ShipmentStatus.java:16-28`).
2. **completeOrder**(`OrderShipmentCommandService.java:191-229`, `ShipmentItemProcessor.java:116`):
   - OrderBid 조회(`:196`, 없으면 예외).
   - **Order → `COMPLETED`**(`:204`). 허용 전이는 `PENDING_PAYMENT`, `IN_WAREHOUSE`, `IN_TRANSIT` 등에서만 가능(`OrderStatus.java:24-29`). `PREPARING`에서는 불허.
   - `updateSaleStatusToSold(orderId)`(`:208`):
     - Sale → `SOLD`는 `SaleStatus.canTransitionTo`가 허용할 때만(`SaleStatus.java:15-25`: `ON_AUCTION`, `SELLING`에서만 가능). `PENDING_SHIPMENT`, `IN_TRANSIT`, 이미 `SOLD`인 경우는 가드에 걸려 아무것도 안 한다(`OrderShipmentCommandService.java:119`).
     - 창고 `SOLD` 갱신과 판매자 알림(`:126-138`)은 이 가드 안에 있어 같이 생략된다.
   - 구매자 알림 "[completeOrder] 주문이 완료 처리되었습니다"(`:212-217`).
3. **notifyShipmentCompleted**(`ShipmentItemProcessor.java:117`, `src/main/java/com/fream/back/domain/notification/service/command/NotificationCommandService.java:219-232`): 구매자 알림 "[배송 완료] …" 1건.

**엔티티 상태 순서**: OrderShipment `→DELIVERED` → Order `→COMPLETED` → (Sale `→SOLD`는 가드 조건부).

**알림**
- 배치 경로에서 **구매자 2건**(`:212-217` + `NotificationCommandService.java:224`). 판매자는 Sale 가드 때문에 보통 0건.
- 수동 `check-status`의 DELIVERED 경로는 `completeOrder`만 호출하므로 **구매자 1건**, `notifyShipmentCompleted`는 호출되지 않는다(`OrderShipmentCommandService.java:489`).

**주문 입찰·판매 입찰 상태**: 두 경로 모두 **`MATCHED`로 남는다.** `COMPLETED`로 바꾸는 곳은 `updateOrderAndSaleBidStatusToCompleted`(`OrderShipmentCommandService.java:413-440`, 설정은 `:424`, `:431`)뿐이고, 호출처는 `updateTrackingInfo`의 `:289`뿐이다. 배송 완료 경로에서는 호출되지 않는다.

## 4. 주문 종류별 차이

**(a) 실배송 일반 구매 입찰 주문**
- 정상 송장 등록(1번)이 실패하므로 `IN_TRANSIT`/`OUT_FOR_DELIVERY`가 되지 않는다. 배치 대상이 되지 않는다.
- 수동 `check-status`로 "배송출발"을 받아 `OUT_FOR_DELIVERY`가 된 경우를 가정하면, 배치의 "배송완료" 처리에서:
  - `:113` 배송 `DELIVERED` 설정 → `:116` `completeOrder` → `:204` Order `PREPARING → COMPLETED` **불허** → `InvalidOrderStatusException`.
  - `completeOrder`의 `catch (Exception)`(`OrderShipmentCommandService.java:221-227`)이 `ShipmentException(ORDER_NOT_FOUND_FOR_SHIPMENT, S102)`로 감싸고, `ShipmentItemProcessor.java:145`에서 그대로 다시 던진다.
  - 결과: 주문 `PREPARING` 유지, 알림 없음, 입찰 `MATCHED` 유지. 이 건은 청크에서 skip된다(5번 참고).
- 결론: **(a)는 배송 완료 처리까지 끝까지 가지 못한다.**

**(b) 즉시 구매로 만들어진 주문**
- 생성: `OrderBidCommandService.java:119-143` → `OrderCommandService.createInstantOrder`(`:220`). Order는 `PENDING_PAYMENT`(`:244`)로 만들어지고, 결제(`:305`)는 Order 상태를 바꾸지 않는다. SaleBid는 `:279-280`에서 주문에 연결·`MATCHED`. 결제 시 `PaymentCommandService.java:404`(또는 `:419`)에서 **Sale이 `SOLD`**로 바뀐다.
- 정상 송장 등록(1번)은 `PENDING_PAYMENT → IN_TRANSIT`이 `Order.java`/`OrderStatus.java:24`상 허용되지 않으므로 (a)와 똑같이 실패(404, `S001`, 롤백).
- 배송 완료 처리는 가능하다. 수동 `check-status`로 "배송완료"가 나오거나(`:486-489`), "배송출발" 후 배치가 완료를 감지하면:
  - Order `PENDING_PAYMENT → COMPLETED` **허용**(`OrderStatus.java:24`) → 주문 `COMPLETED`.
  - `updateSaleStatusToSold`: Sale이 이미 `SOLD`라서 가드에서 생략(`:119`). 판매자 알림 없음. 창고 보관 건이면 창고 `SOLD` 갱신도 생략됨(`:126-129`가 같은 가드 안).
  - 구매자 알림: 수동 경로 1건, 배치 경로 2건.
  - OrderBid/SaleBid는 `MATCHED` 유지.
- 결론: **(b)는 주문 `COMPLETED`까지 간다**, 그러나 입찰은 `MATCHED`로 남고, 판매자 알림은 없으며, 창고 상태는 갱신되지 않는다. 정상 송장 등록 경로로는 (a)와 마찬가지로 도달하지 못한다.

## 5. 실패 처리 (배치 한 건 실패)

- Step 설정: 청크 50, `faultTolerant().skip(Exception.class).skipLimit(50)`(`UpdateShipmentStatusesJobConfig.java:67-77`), `SkipListener`(`:78`, 정의 `:252`)는 로그만 남긴다.
- **실패한 한 건**: processor 예외 → 청크 트랜잭션 롤백 → skip. 그 건은 DB 변경이 없고 상태가 그대로 남아, 다음 주기(6시간 뒤)에 다시 조회된다. (Spring Batch의 청크 재처리 방식은 프레임워크 동작이며 이 저장소 코드 밖의 내용이다. 실행으로 확인하지 않았다.)
- **나머지 건**: 청크 안의 다른 건은 재처리되어 정상이면 커밋된다. 즉 한 건 실패가 같은 청크 나머지를 막지는 않는다.
- **skip 누적 50건 초과**: skip 한도(`skipLimit`)를 넘으면 Step이 실패하고 Job이 중단된다. 남은 건은 다음 주기까지 처리되지 않는다. 스케줄러는 예외를 `printStackTrace`만 한다(`ShipmentBatchScheduler.java:41-42`).
- **Step 수준 실패**: `BrowserManageStepListener.beforeStep`의 브라우저 초기화 실패는 `S303`이고 Step 자체가 실패한다(`src/main/java/com/fream/back/global/utils/PlaywrightBrowserManager.java` 초기화 예외 처리).

**코드에서 확인된 문제 2건 (실제 동작)**
1. **재처리 시 메모리 상태가 DB에 쓰일 수 있음(가능성 높음, 실행 미검증)**: `ShipmentItemProcessor.java:113`에서 엔티티를 `DELIVERED`로 바꾼 뒤 `:116`에서 예외가 나면, 청크 재처리에서 같은 객체가 다시 processor에 들어올 때 `:101-104`의 조기 반환(`status == newStatus`)에 걸려 `completeOrder` 없이 writer가 `DELIVERED`를 저장할 수 있다. 그러면 배송은 `DELIVERED`, 주문은 `PREPARING`, 알림은 없는 상태가 된다. Spring Batch가 같은 인스턴스를 재사용하는지 확인하지 못했다.
2. **페이징 누락(추론)**: `UpdateShipmentStatusesJobConfig.java:94-95`는 조건 컬럼(`status`)을 바꾸면서 OFFSET 페이징을 한다. 정렬(ORDER BY)도 없다. 같은 청크에서 `DELIVERED`가 된 건만큼 다음 페이지 OFFSET이 밀려, 같은 실행에서 일부 건이 조회되지 않고 다음 주기로 넘어간다.

## 주석·메서드 이름과 실제 동작이 다른 곳
- `OrderShipmentCommandService.updateTrackingInfo` 주석 "배송 상태가 변경되었으므로 주문 상태도 업데이트"(`:258`): 실제로는 `PREPARING`/`PENDING_PAYMENT`에서 `IN_TRANSIT` 전이가 불허되어 항상 실패한다(1번).
- `updateSaleStatusToSold` 주석 "OrderBid가 없는 경우 예외로 중단하지 않고 진행"(`:179`): OrderBid 조회만 예외를 삼키고, SaleBid 조회(`:116`)는 try 밖이라 없으면 예외로 중단한다.
- `updateOrderAndSaleBidStatusToCompleted` 주석 "상태 변경 실패는 로그만 남기고 진행"(`:436-438`): 예외를 삼키므로 입찰이 `MATCHED`로 남아도 드러나지 않는다. 이 메서드는 `private` + `@Transactional`이라 프록시 트랜잭션도 적용되지 않는다.
- `UpdateShipmentStatusesJobConfig.shipmentItemProcessor()` 주석 "DELIVERY 완료 시 알림, Order 상태 완료 등도 여기서 처리": 이 빈은 Step에서 쓰이지 않는다. 실제 처리는 `ShipmentItemProcessor`.
- `OrderShipmentCommandService.updateShipmentStatuses()` "전체 배송 상태 업데이트": 호출처 없음.

## 확인하지 않은 것
- 앱 실행·테스트는 하지 않았다(정적 읽기만).
- Spring Batch의 fault-tolerant 재처리가 같은 객체를 재사용하는지(위 5번 문제 1)는 실행으로 확인하지 않았다.
- `CjTrackingPlaywright` 내부 파싱은 호출부만 확인했다.
- `DataInitializer`의 시드 데이터에 `IN_TRANSIT`/`OUT_FOR_DELIVERY` 배송이 있는지는 확인하지 않았다.
