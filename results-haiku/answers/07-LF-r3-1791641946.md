# 즉시 구매 처리 흐름

경로는 저장소 루트 기준이다. `src/main/java/com/fream/back/`는 `main/…`로 줄여 쓴다.
(예: `main/domain/order/...` = `src/main/java/com/fream/back/domain/order/...`)

## 1. 진입점, 처리 방식, 응답 ID

- 진입점은 `POST /order-bids/instant`다. `main/domain/order/controller/command/OrderBidCommandController.java:89-90`에서 `@RequestBody @Valid InstantOrderRequestDto`를 받는다.
- 요청 DTO는 `saleBidId`, `addressId`, `warehouseStorage`, `paymentRequest`를 가진다(`main/domain/order/dto/InstantOrderRequestDto.java:18-30`). `saleBidId`, `addressId`, `paymentRequest`는 `@NotNull`이다.
- 컨트롤러는 로그인 이메일을 꺼내(`OrderBidCommandController.java:92`), 결제 요청에 `userEmail`을 넣고 `orderId`를 null로 만든다(`OrderBidCommandController.java:98`, `:120-121`). 그다음 `OrderBidCommandService#createInstantOrderBid`를 호출한다(`OrderBidCommandController.java:101-107`).
- **동기 처리다.** Kafka 발행은 없다. 한 HTTP 요청 안에서 주문 생성, 결제 API 호출, 판매 상태 변경, 알림까지 모두 끝난다. 이 경로에 `OrderEventProducer`나 `PaymentEventProducer` 호출은 없다.
- 서비스 메서드는 `@Transactional`이다(`main/domain/order/service/command/OrderBidCommandService.java:118-119`). 입력 검증(`:123`, 검증 메서드 `:154`), 구매자 조회(`:126`), `SaleBid` 조회 및 검증(`:129`, `:172-185`), `OrderCommandService#createInstantOrder` 호출(`:133`), `OrderBid` 생성(`:142`, `:189-207`) 순서다.
- **응답의 ID는 `OrderBid`의 ID다.** 컨트롤러가 `OrderBidCommandService#createInstantOrderBid(...).getId()`를 `orderId`라는 변수에 담아 반환한다(`OrderBidCommandController.java:101-109`). 반환되는 객체는 `OrderBid`(`OrderBidCommandService.java:142`, `:206`)이고 `Order`의 ID가 아니다. 결제 ID도 아니다. 응답은 `ResponseDto.success(orderId, "즉시 구매가 성공적으로 처리되었습니다.")`다(`:109`).
- 검증 로직에 어긋나는 부분이 있다. `getSaleBidAndValidate`는 `saleBid == null`을 확인하지만(`OrderBidCommandService.java:174-175`), 실제 `SaleBidQueryService#findById`는 없으면 `IllegalArgumentException`을 던진다(`main/domain/sale/service/query/SaleBidQueryService.java:21-24`). 그래서 이 null 검사는 실행되지 않는다. 예외는 `handleOrderBidCreationException`에서 `OrderBidCreationFailedException`으로 감싸진다(`OrderBidCommandService.java:146`, `:212-217`).
- `SaleBid`의 상태(이미 `MATCHED`나 `COMPLETED`인지)를 확인하는 코드는 보이지 않는다. `getSaleBidAndValidate`는 null 여부와 `sale` 연결 여부만 본다(`OrderBidCommandService.java:172-185`). 그래서 같은 판매 입찰에 두 번 즉시 구매가 들어와도 막는 코드가 없다. `SaleBid#assignOrder`가 `order`를 덮어쓴다(`main/domain/sale/entity/SaleBid.java:58-61`). 이 부분은 읽기만 했고 실행해 보지는 않았다.

## 2. 생성되는 엔티티와 상태 변화 순서

모두 한 트랜잭션 안에서 일어난다(`OrderBidCommandService.java:118`, `OrderCommandService.java:219`). 아래 상태는 각 단계 직후 값이다. 중간에 예외가 나면 트랜잭션 전체가 롤백되므로 뒤 단계가 실패하면 앞 단계 결과도 남지 않는다(3번 참고).

| 순서 | 동작 | 근거 | 직후 상태 |
|---|---|---|---|
| a | `Order` 생성 후 저장. `totalAmount = saleBid.getBidPrice()` | `main/domain/order/service/command/OrderCommandService.java:238-247` (주소 조회 `:238`), totalAmount `:243` | `Order.status = PENDING_PAYMENT` (`:244`) |
| b | `OrderItem` 생성 | `OrderCommandService.java:255` | — |
| c | `OrderShipment` 생성, 주소록 값을 스냅샷으로 복사 | `OrderCommandService.java:264-271`, `main/domain/shipment/service/command/OrderShipmentCommandService.java:56-70` | `OrderShipment.status = PENDING` |
| d | `SaleBid`에 `order` 연결, 상태 `MATCHED`, `flush` | `OrderCommandService.java:279-283`, `main/domain/sale/entity/SaleBid.java:58-61` | `SaleBid.status = MATCHED`, `SaleBid.order = order` |
| e | 판매자 보관(`Sale.isWarehouseStorage()`)이면 창고 상태 변경 | `OrderCommandService.java:292-293`, `main/domain/warehouseStorage/service/command/WarehouseStorageCommandService.java:117-` | 창고 `ASSOCIATED_WITH_ORDER` |
| f | `PaymentCommandService#processPayment` 호출. 결제 엔티티 생성·저장 | `OrderCommandService.java:305`, `main/domain/payment/service/command/PaymentCommandService.java:57-83` | 결제 엔티티 `status = PENDING` 기본값, 카드 성공 시 `PAID`(3번) |
| g | 알림 발송 후 `Sale` 상태를 `SOLD`로 변경 | `PaymentCommandService.java:83`, `:383-426` (`SOLD` 설정 `:404`, `:419`) | `Sale.status = SOLD` |
| h | `OrderBid` 생성. `MATCHED`, `isInstantPurchase = true`, `order`·`sale` 연결, 저장 | `OrderBidCommandService.java:142`, `:189-206` (`MATCHED` `:196`, `markAsInstantPurchase` `:205`) | `OrderBid.status = MATCHED` |

단계 f와 g의 순서에 주의해야 한다. `notifyUsersAndUpdateSaleStatus`는 `order.getOrderBid()`를 먼저 보는데(`PaymentCommandService.java:388`), 이 시점에는 `OrderBid`가 아직 없으므로 `null`이다. 그래서 `saleBidQueryService.findByOrderId`로 `SaleBid`를 찾아서 `Sale`을 `SOLD`로 만든다(`PaymentCommandService.java:391-404`). `SaleBid`에 `order`가 이미 연결되어 있고 `flush`(`OrderCommandService.java:283`)도 되어 있으므로 이 조회는 성공한다.

**성공 시 최종 상태**

- `Order`: `PENDING_PAYMENT`에서 바뀌지 않는다. 이 경로에서 `Order.updateStatus`나 `Order.assignPayment`를 호출하지 않는다. 일반 주문 경로(`OrderEventConsumer`)에서 하는 `PAYMENT_COMPLETED`/`PREPARING` 전이가 없다.
- `OrderBid`: `MATCHED`, `isInstantPurchase = true`.
- `SaleBid`: `MATCHED`, `order` 연결됨.
- `Sale`: `SOLD`.
- `OrderShipment`: `PENDING`.
- 결제 엔티티: 카드는 `PAID`일 때만 `isSuccess = true`(3번 참고), 일반 결제는 `PAID`.

## 3. 결제 수단별 결과, 실패 처리

결제 실행은 `PaymentCommandService#processPayment`에서 `getResolvedPaymentType()`으로 분기한다(`main/domain/payment/service/command/PaymentCommandService.java:67-80`).

**공통 검증**: `validatePaymentRequest`는 주문 ID 일치(`:131-134`), 이메일 일치(`:136-139`), `paidAmount > 0`(`:142-145`)만 본다. **결제 금액이 입찰 가격(`saleBid.getBidPrice()`)과 같은지 확인하지 않는다.** 카드는 클라이언트가 보낸 `paidAmount`를 그대로 PortOne에 청구한다(`:179`, `main/domain/payment/portone/PortOneApiClient.java:229`). 주문 금액은 입찰 가격으로 저장되지만(`OrderCommandService.java:243`), 실제 청구액과 연결되지 않는다.

**CARD (`createCardPayment`, `PaymentCommandService.java:157-225`)**
- 저장된 카드(`PaymentInfo`)를 조회해 PortOne `processCardPayment`를 호출한다(`:166`, `:179`).
- 성공 판정: PortOne 응답 `status`가 문자열 `"success"`일 때만 `PAID`와 `isSuccess = true`가 된다(`:203-206`). 그 외에는 `status`가 기본값 `PENDING`, `isSuccess = false`로 저장된다(`main/domain/payment/entity/Payment.java:39`, `:44`). 다만 PortOne 문서상 결제 완료 상태 값이 `"paid"`로 알려져 있다. 이 코드만으로는 확정할 수 없으므로 실제 응답 샘플로 확인해야 한다. 맞다면 정상 카드 결제도 `PENDING`으로 남는다.
- **PortOne이 실패를 응답하는 경우(HTTP가 200이 아니거나 `code != 0`)**: `PortOneApiClient.java:270-275`가 `PaymentProcessingException`을 던진다. `createCardPayment`(`PaymentCommandService.java:218-219`)와 `processPayment`(`:89-94`)는 그대로 다시 던진다. `OrderCommandService#createInstantOrder`는 이를 `OrderPaymentProcessingFailedException`으로 감싸서 던진다(`OrderCommandService.java:305-308`, 바깥 catch `:315-317`). `OrderBidCommandService`는 `OrderException`을 그대로 다시 던진다(`OrderBidCommandService.java:212-215`). `@Transactional` 메서드 밖으로 RuntimeException이 나가므로 **트랜잭션 전체가 롤백된다.** `Order`, `OrderItem`, `OrderShipment`, `SaleBid`의 `MATCHED` 변경, 창고 상태 변경이 모두 되돌려진다. 클라이언트는 `GlobalExceptionHandler`가 만든 에러 응답을 받는다(`main/global/exception/GlobalExceptionHandler.java:49-57`). 주문은 남지 않는다. 참고로 `nav/flow-trade.md`의 "Order는 PENDING_PAYMENT 유지"는 이 즉시 구매 경로에는 맞지 않다. 여기서는 Order가 아예 저장되지 않는다.
- **PortOne이 `code = 0`으로 응답하면서 `status`가 `"success"`가 아닌 경우**: 예외가 없다. `CardPayment`가 `PENDING`, `isSuccess = false`로 저장된다(`PaymentCommandService.java:203-208`). 그런데 바로 이어서 `notifyUsersAndUpdateSaleStatus`가 실행되어 **구매자와 판매자에게 "결제가 완료되었습니다" 알림을 보내고 `Sale`을 `SOLD`로 바꾼다**(`:83`, `:391-404`, `:434-456`). 결제 상태를 확인하지 않는다. 트랜잭션은 커밋된다. 결과는 `Sale=SOLD`, `OrderBid=MATCHED`, `Order=PENDING_PAYMENT`, `Payment=PENDING`이다. 실제로 돈이 빠지지 않았는데도 거래가 완료된 것처럼 보인다.
- `PortOneApiClient`의 `@Retryable`(`PortOneApiClient.java:224-228`)은 동작하지 않는다. 저장소 어디에도 `@EnableRetry`가 없다(`grep` 확인). 설령 있더라도 `PaymentApiException`만 재시도 대상이다.

**ACCOUNT (`createAccountPayment`, `PaymentCommandService.java:236-279`)**
- 은행명 검증(`:243-248`) 후 `AccountPayment`를 만든다. 기본 상태는 `PENDING`이다. 그다음 `accountPayment.updateStatus(PaymentStatus.PENDING)`을 호출한다(`:260`).
- `Payment.updateStatus`는 `PENDING → PENDING` 전이를 허용하지 않으므로(`main/domain/payment/entity/Payment.java:70-75`, `main/domain/payment/entity/PaymentStatus.java:10-14`) `IllegalStateException`이 난다. 일반 catch에서 `PaymentProcessingException`으로 바뀐다(`PaymentCommandService.java:274-277`).
- **계좌이체는 즉시 구매에서 항상 실패한다.** 이후 흐름은 카드 실패와 같다(롤백). 실패 원인 설명은 `nav/flow-trade.md`와 일치한다.

**GENERAL (`createGeneralPayment`, `PaymentCommandService.java:290-333`)**
- `impUid`가 비어 있지 않은지만 확인한다(`:297-300`). PortOne을 호출해서 검증하지 않는다. 클라이언트가 준 `impUid`를 그대로 믿는다.
- `isSuccess = true`, `status = PAID`로 저장한다(`:313-314`). 그래서 **일반 결제는 항상 성공으로 처리된다.** 금액도 `paidAmount > 0`만 확인하고 입찰 가격과 비교하지 않는다.

**즉시 구매가 끝까지 성공하는 경우**: CARD에서 PortOne이 `code = 0`과 `status = "success"`를 준 경우, 또는 GENERAL인 경우다. ACCOUNT는 실패한다. CARD가 PortOne에서 실패로 응답하면 주문, 배송, 판매 상태 변경이 모두 롤백되고 에러가 반환된다. 다만 `code = 0`이면서 `status`가 `"success"`가 아닌 경우는 예외 없이 "성공"처럼 끝난다.

## 4. 알림 수신자, 시점, 방식

발송은 `PaymentCommandService#notifyUsersAndUpdateSaleStatus` → `sendNotifications`에서 한다(`main/domain/payment/service/command/PaymentCommandService.java:383-462`). 결제 엔티티가 만들어진 뒤, `Sale` 상태를 바꾸기 전에 실행된다(`:83`, `:416`). 즉시 구매 컨트롤러와 서비스에서는 따로 알림을 보내지 않는다.

- **구매자**(`order.getUser()`): `SHOPPING` / `BID` 카테고리, "결제가 완료되었습니다. 주문 ID: …"(`PaymentCommandService.java:436-443`).
- **판매자**(`sale.getSeller()`): `SHOPPING` / `BID` 카테고리, "구매자가 결제를 완료하였습니다. 판매 ID: …"(`:447-454`).

전달 방식은 두 단계다. `NotificationCommandService#createNotification`이 알림을 DB에 저장한다(`main/domain/notification/service/command/NotificationCommandService.java:44-59`). 그다음 `sendRealTimeNotification`이 Redis 키(`REDIS_KEY_PREFIX + email`)가 있을 때만 WebSocket으로 `/user/{email}/queue/notifications`에 보낸다(`NotificationCommandService.java:303-313`). 연결이 없으면 DB 저장만 남는다. 둘 다 동기 호출이고 같은 트랜잭션 안에서 실행된다. Kafka `notification-topic`은 이 경로에서 쓰지 않는다. `sendNotifications`는 예외를 삼키므로(`PaymentCommandService.java:457-461`) 알림 실패가 결제를 막지는 않는다.

시점 문제 두 가지:
- 알림은 `Sale` 상태 변경과 함께 `processPayment` 안에서 나간다. 이후 `OrderBid` 저장(`OrderBidCommandService.java:206`)이 실패해 트랜잭션이 롤백되어도, WebSocket으로 나간 push는 되돌릴 수 없다.
- 2번 3번에서 본 대로, PortOne 응답이 `"success"`가 아니어도 "결제가 완료되었습니다" 알림이 나간다.

## 5. 처리 끝난 뒤 주문의 최종 상태, 창고 보관 선택 시 차이

**성공 시 주문 최종 상태**: `Order.status`는 `PENDING_PAYMENT`로 남는다(`OrderCommandService.java:244`, 이후 변경 없음). `OrderShipment`는 `PENDING`이다. 연결된 `OrderBid`는 `MATCHED`이고 `Sale`은 `SOLD`다. 이후 송장 등록(`PATCH /shipments/order/{shipmentId}/status` → `OrderShipment#updateTrackingInfo`) 등은 별도 API다(`nav/flow-trade.md` 5번, 이번 질문 범위 밖이라 검증하지 않음).

**구매자가 "창고 보관"을 선택했을 때: 아무것도 달라지지 않는다.**
- 요청의 `warehouseStorage` 값은 `InstantOrderRequestDto.java:26`에서 받고, `OrderBidCommandController.java:105`와 `OrderBidCommandService.java:137`을 거쳐 `OrderCommandService#createInstantOrder`의 `isWarehouseStorage` 파라미터로 들어간다(`OrderCommandService.java:221`).
- 그런데 `createInstantOrder` 본문은 이 파라미터를 **읽지 않는다**(`OrderCommandService.java:220-318`에서 참조 없음). 창고 여부는 `sale.isWarehouseStorage()`, 즉 **판매자 쪽 설정**만 본다(`OrderCommandService.java:292-293`).
- 구매자 창고 보관용 `WarehouseStorageCommandService#createOrderStorage`는 즉시 구매 경로에서 호출되지 않는다. 호출되는 곳은 `OrderEventConsumer.java:197-200`과 `OrderCommandService.java:163-171`(비즉시 경로)뿐이다. 그러므로 `Order.warehouseStorage`는 `null`로 남고 `WarehouseStorage` 행도 새로 생기지 않는다.
- 배송 정보(`OrderShipment`)는 창고 여부와 관계없이 항상 생성된다(`OrderCommandService.java:264-271`). 창고 보관을 골라도 주소로 배송된다고 기록된다.

요약하면, 구매자 창고 옵션은 즉시 구매 경로에서 무시된다. 판매자가 보관 중인 상품(`Sale.isWarehouseStorage()`)이면 그 창고 기록만 `ASSOCIATED_WITH_ORDER`로 바뀐다.

## 코드와 이름·주석이 다른 부분 (실제 동작 기준)

- `createInstantOrder`의 `isWarehouseStorage` 파라미터는 선언만 있고 쓰이지 않는다(`OrderCommandService.java:221`).
- `getSaleBidAndValidate`의 `SaleBidNotFoundException` 분기는 실행되지 않는다. `findById`가 `IllegalArgumentException`을 던진다(`SaleBidQueryService.java:21-24`). 결과적으로 `OrderBidCreationFailedException`(500계열)으로 바뀐다.
- `PaymentCommandService#processPayment`는 실패를 검증한다고 적혀 있지만, 결제 상태(`PENDING`, `isSuccess = false`)를 보지 않고 판매를 `SOLD`로 바꾼다(`PaymentCommandService.java:83`, `:404`).
- `PortOneApiClient`의 `@Retryable`은 재시도한다고 적혀 있으나 `@EnableRetry`가 없어 동작하지 않는다(`PortOneApiClient.java:224`).
- `nav/flow-trade.md`는 "실패 시 Order는 PENDING_PAYMENT 유지"라고 하지만, 즉시 구매는 실패하면 Order가 롤백되어 남지 않는다.
