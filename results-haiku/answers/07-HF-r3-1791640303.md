# 질문: 즉시 구매는 어떻게 처리되나

모든 경로는 저장소 루트 기준이다. 근거는 코드만으로 확인했다(`nav/` 상세 문서는 열지 않았다). 코드는 수정하지 않았고 실행·재현도 하지 않았다.

---

## 1. 진입점, 처리 방식, 응답 ID

- **진입점**: `POST /order-bids/instant`. 클래스 매핑 `src/main/java/com/fream/back/domain/order/controller/command/OrderBidCommandController.java:22`, 메서드 매핑 `:89-90`.
- **요청 본문**: `src/main/java/com/fream/back/domain/order/dto/InstantOrderRequestDto.java:20-29` (`saleBidId`, `addressId`, `warehouseStorage`, `paymentRequest`).
- **처리 단계** (전부 한 스레드, 한 트랜잭션):
  1. 컨트롤러가 토큰에서 이메일을 꺼낸다 (`OrderBidCommandController.java:92`). 결제 요청에 이메일을 넣고 `orderId`를 null로 둔다 (`:98`, `:119-121`).
  2. `OrderBidCommandService.createInstantOrderBid` 호출. `@Transactional`이 붙어 있다 (`src/main/java/com/fream/back/domain/order/service/command/OrderBidCommandService.java:118-119`). 입력 검증 `:123`, `:154-167`. 구매자 조회 `:126`. SaleBid 조회 `:129`, `:172-184`.
  3. `OrderCommandService.createInstantOrder` 호출 (`src/main/java/com/fream/back/domain/order/service/command/OrderCommandService.java:219-221`). 주소 조회, Order·OrderItem·OrderShipment 생성, SaleBid 매칭, 창고 처리, 결제 순으로 진행한다 (자세한 내용은 2번).
  4. 3번이 끝난 뒤 `OrderBidCommandService`로 돌아와 OrderBid를 만들고 저장한다 (`OrderBidCommandService.java:142`, `:189-207`).
- **동기 처리다.** 이 경로에는 Kafka 발행이 없다. 비동기(Kafka) 처리는 `OrderCommandController.java:34` 주석이 말하는 다른 엔드포인트(결제·배송 처리)에만 해당한다.
- **응답 ID는 OrderBid의 ID다.** 컨트롤러는 `createInstantOrderBid(...).getId()`를 `Long orderId`라는 변수에 담아 응답한다 (`OrderBidCommandController.java:101-109`). 반환 객체는 OrderBid다 (`OrderBidCommandService.java:142`, `:206`). Order의 ID가 아니다. 컨트롤러 주석 `OrderBidCommandController.java:84`는 "생성된 주문 ID"라고 적고 있어 주석과 실제가 다르다.

## 3. 결제 수단별 결과와 실패 시 동작

결제 분기는 `PaymentCommandService.java:67-80`에서 일어난다. 공통적으로 확인하는 것은 `paidAmount > 0`뿐이다 (`:142-145`). 클라이언트가 보낸 `paidAmount`를 입찰가와 비교하는 코드는 없다. `paidAmount`는 PG 요청에 그대로 쓰인다 (`:179`). `@Min(100)`은 `PaymentRequestDto.java:50-52`에 있지만, `InstantOrderRequestDto.paymentRequest`에 `@Valid`가 없어 실행되지 않는다 (`InstantOrderRequestDto.java:28-29`).

**카드 (`CARD`)** — `PaymentCommandService.java:157-225`
- 저장된 카드 정보(`paymentInfoId`)로 PortOne 카드 결제를 호출한다 (`:166`, `:179`).
- 응답 `code`가 0이 아니면 `PaymentProcessingException`을 던진다 (`src/main/java/com/fream/back/domain/payment/portone/PortOneApiClient.java:270-275`).
- 응답 `status`가 `"success"`이면 `PAID`, 아니면 `Payment` 기본값인 `PENDING`으로 저장된다 (`PaymentCommandService.java:203-206`, `src/main/java/com/fream/back/domain/payment/entity/Payment.java:44`). 이 경우에도 예외는 없고 주문은 끝까지 진행된다. PortOne이 성공을 어떤 `status` 문자열로 돌려주는지는 이 저장소만으로 확인할 수 없다.

**카드 결제가 실패로 응답하면** (`code != 0`, HTTP 오류, `RestClientException` 모두 포함)
- 예외가 호출 스택을 타고 올라간다: `PaymentCommandService.java:88-94` → `OrderCommandService.java:304-309` (`OrderPaymentProcessingFailedException`으로 감쌈) → `:312-314` 재던짐 → `OrderBidCommandService.java:145-147` 재던짐.
- `GlobalException`이 `RuntimeException`이므로 (`src/main/java/com/fream/back/global/exception/GlobalException.java:10`) `OrderBidCommandService.java:118`의 트랜잭션은 롤백된다.
- 결과: Order, OrderItem, OrderShipment, SaleBid 변경, WarehouseStorage 변경이 모두 롤백된다. 주문은 생성되지 않고, 알림도 나가지 않고, Sale도 SOLD가 되지 않는다. 응답은 `GlobalExceptionHandler`가 만든다. HTTP 상태 코드는 확인하지 않았다.
- 주의: PG가 승인한 뒤 같은 트랜잭션의 나중 단계가 실패하면 DB만 롤백되고 PG 결제는 취소되지 않는다. 환불 코드 `PaymentCommandService.java:341-375` (`handleRefundIfNecessary`)는 `private`이고 호출처가 없다.

**계좌이체 (`ACCOUNT`)** — `PaymentCommandService.java:236-279`
- PG를 호출하지 않는다. 은행명 검증만 한다 (`:244`).
- `Payment.status`는 `PENDING`으로 저장된다 (`:260`).
- 그래도 주문, SaleBid 매칭, OrderBid 생성, Sale SOLD, 구매자·판매자 알림이 모두 성공 처리되고, 응답은 "즉시 구매가 성공적으로 처리되었습니다"다 (`OrderBidCommandController.java:109`).
- PENDING을 PAID로 바꾸는 코드(`PaymentCommandService.java:498` `updatePaymentStatus`)는 저장소 안에 호출처가 없다.

**일반 결제 (`GENERAL`)** — `PaymentCommandService.java:290-333`
- 클라이언트가 보낸 `impUid`, `pgProvider`, `receiptUrl`, `paidAmount`를 그대로 저장하고 `PAID`로 바꾼다 (`:302-314`).
- PG에 검증 요청을 보내지 않는다. PortOne 호출은 카드 결제(`:179`)와 환불(`:351`) 두 곳뿐이다.
- 따라서 `impUid`만 채워 보내면 실제 결제 없이 성공한다.

**요약**: 즉시 구매가 끝까지 성공하는 경우는 세 가지다. 카드는 PG 응답이 성공일 때, 계좌는 `PENDING` 상태인데도 성공 처리될 때, 일반 결제는 검증 없이 성공할 때다. 카드 결제가 실패하면 트랜잭션 전체가 롤백되고 에러 응답이 나간다.

## 4. 누가 어떤 알림을 받나

- **구매자** (`PaymentCommandService.java:438-445`): 카테고리 `SHOPPING`, 타입 `BID`, 메시지 "결제가 완료되었습니다. 주문 ID: {orderId}" (`:442-443`).
- **판매자** (`PaymentCommandService.java:449-456`): 같은 카테고리·타입, 메시지 "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}" (`:453-454`).
- **언제**: `processPayment` 안에서 결제 레코드를 만든 직후 동기로 보낸다 (`PaymentCommandService.java:83` → `:383-416`). 결제 수단과 무관하게 항상 보내므로, 계좌이체(`PENDING`)에도 "결제가 완료되었습니다"가 나간다.
- **어떻게**: `NotificationCommandService.createNotification` (`src/main/java/com/fream/back/domain/notification/service/command/NotificationCommandService.java:44-67`).
  - DB에 저장한다 (`:53`).
  - Redis 키 `WebSocket:User:{email}`이 있으면 `/queue/notifications`로 WebSocket 전송한다 (`:303-309`). 없으면 저장만 한다 (`:320-321`).
  - 이메일·Kafka 전송은 없다.
- **트랜잭션과의 관계**: `NotificationCommandService`는 클래스 전체가 `@Transactional`이다 (`:27`). 따라서 WebSocket 전송은 커밋 전에 나간다. 이후에 롤백이 일어나면 이미 나간 실시간 메시지는 되돌릴 수 없다. 롤백은 알림 전송 뒤의 실패(예: OrderBid 저장 실패) 때만 생긴다.
- **실패 처리**: 알림 전송 실패는 예외를 던지지 않고 로그만 남긴다 (`PaymentCommandService.java:457-461`, 바깥 감싸기 `:421-425`).

## 5. 처리 완료 후 주문의 최종 상태, 창고 보관 선택 시 차이

**최종 상태 (성공 경로 기준)**
- **Order.status = `PENDING_PAYMENT`.** 결제가 PAID여도 주문 상태는 결제 대기 그대로다 (`OrderCommandService.java:244`). 이 경로에서는 상태를 바꾸지 않는다. `PAYMENT_COMPLETED`로 바꾸는 코드는 `processPaymentAndShipment`(`OrderCommandService.java:165`, `:175`)와 Kafka 컨슈머(`src/main/java/com/fream/back/domain/order/service/kafka/OrderEventConsumer.java:192-195`)에만 있고, 즉시 구매 경로는 둘 다 거치지 않는다.
- Payment: 카드 성공·일반은 `PAID`, 계좌·카드 비성공 응답은 `PENDING`.
- OrderShipment: `PENDING`.
- OrderBid: `MATCHED`, `isInstantPurchase = true`.
- SaleBid: `MATCHED`, order 연결됨.
- Sale: `SOLD`.

**창고 보관을 선택한 경우**
- 요청의 `warehouseStorage` 값은 컨트롤러 로그(`OrderBidCommandController.java:94-95`)와 `createInstantOrder`의 파라미터(`OrderCommandService.java:221`)에만 들어간다. 파라미터는 메서드 안에서 쓰이지 않는다.
- 실제 분기는 **Sale의 플래그**로 한다: `sale.isWarehouseStorage()` (`OrderCommandService.java:291-292`, 필드는 `src/main/java/com/fream/back/domain/sale/entity/Sale.java:43`). 구매자의 선택과는 무관하다.
  - Sale 플래그가 true이면 구매자가 false를 보내도 기존 WarehouseStorage의 상태가 `ASSOCIATED_WITH_ORDER`로 바뀐다 (`OrderCommandService.java:293`). WarehouseStorage가 없으면 `findBySale`이 예외를 던져 주문 전체가 실패한다 (`src/main/java/com/fream/back/domain/warehouseStorage/service/query/WarehouseStorageQueryService.java:30-33`).
  - Sale 플래그가 false이면 구매자가 true를 보내도 창고 쪽에는 아무 변화가 없다.
- 두 경우 모두 `WarehouseStorage.assignOrder`(`src/main/java/com/fream/back/domain/warehouseStorage/entity/WarehouseStorage.java:48`)는 호출되지 않는다. 그래서 창고 보관과 Order 사이에 연결이 생기지 않고, `Order.warehouseStorage`도 설정되지 않는다.
- 창고 주문 완료 흐름(`PAYMENT_COMPLETED → PREPARING → IN_WAREHOUSE → COMPLETED`, `OrderCommandService.java:161-172`)은 이 경로에서 실행되지 않는다. 그래서 구매자가 "창고 보관"을 골라도 Order는 `PENDING_PAYMENT`로 남는다.

## 주석·메서드 이름과 실제 동작이 다른 곳

1. **응답 ID**: 컨트롤러 주석(`OrderBidCommandController.java:84`)과 변수명 `orderId`는 주문 ID를 가리키지만, 실제 값은 OrderBid ID다 (`:101-109`, `OrderBidCommandService.java:142`).
2. **`isWarehouseStorage` 파라미터**: `createInstantOrder`의 파라미터(`OrderCommandService.java:221`, 주석 `:210`)는 쓰이지 않는다. 실제 판단은 Sale 플래그로 한다 (`:292`).
3. **판매 입찰이 없을 때**: 메서드 주석(`OrderBidCommandService.java:115`)은 `SaleBidNotFoundException`을 말하지만, `SaleBidQueryService.findById`는 `IllegalArgumentException`을 던진다 (`src/main/java/com/fream/back/domain/sale/service/query/SaleBidQueryService.java:21-24`). 이 예외는 `OrderBidCreationFailedException`으로 감싸진다 (`OrderBidCommandService.java:212-218`). 바로 아래의 null 검사(`:173-176`)는 도달하지 않는다.
4. **결제 금액 기준**: `PaymentRequestDto`의 주석은 "0보다 커야 함"(`:46-49`)이고 어노테이션은 "100원 이상"(`:50-52`)이다. 실제로 서버는 `> 0`만 확인하고 (`PaymentCommandService.java:142`), 어노테이션은 `@Valid` 누락으로 실행되지 않는다 (`InstantOrderRequestDto.java:28-29`).
5. **결제 완료 알림**: 계좌이체가 `PENDING`인데도 "결제가 완료되었습니다"를 보낸다 (`PaymentCommandService.java:442-443`).
6. **카드 성공 판정**: 실패는 PortOne `code`로 판정하는데 (`PortOneApiClient.java:270`), 성공 표시는 `status == "success"`로 한다 (`PaymentCommandService.java:203`). `code`가 0이고 `status`가 다르면 Payment는 PENDING인데 주문은 성공 처리된다.

## 이 답에서 가려지지 않은 문제 (코드 기준 추론, 재현하지 않음)

- **같은 SaleBid를 두 번 구매할 수 있어 보인다.** 이 경로에는 SaleBid·Sale의 상태를 확인하는 코드가 없다 (`OrderBidCommandService.java:172-184`, `OrderCommandService.java:224-235`). 두 번째 요청은 `saleBid.assignOrder`로 order를 새 주문으로 바꾸고 새 OrderBid를 만든다 (`OrderCommandService.java:279`, `SaleBid.java:58-61`).
- **결제 금액을 검증하지 않는다.** 카드 결제 금액은 클라이언트의 `paidAmount`를 그대로 PG에 보낸다 (`PaymentCommandService.java:179`). Order의 `totalAmount`는 입찰가다 (`OrderCommandService.java:243`). 두 값이 달라도 막는 코드가 없다.

## 확인하지 않은 것

- `nav/` 상세 문서는 열지 않았다. 모든 답은 `src/` 코드에서 확인했다.
- HTTP 상태 코드(`GlobalExceptionHandler`), PortOne 응답 스펙, 실제 실행 결과는 확인하지 않았다.
