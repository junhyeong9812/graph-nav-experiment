# 즉시 구매 처리 흐름

경로 표기: `src/main/java/com/fream/back/domain/...` 를 `domain/...` 로 줄여 적는다. 예: `domain/order/controller/command/OrderBidCommandController.java:89`. 코드는 수정하지 않았다.

## 1. 진입점과 처리 방식

- **API**: `POST /order-bids/instant` — `domain/order/controller/command/OrderBidCommandController.java:89-90`
- **요청 본문**: `InstantOrderRequestDto` (saleBidId, addressId, warehouseStorage, paymentRequest) — `domain/order/dto/InstantOrderRequestDto.java:154-163`
- **처리 단계** (`OrderBidCommandController.java:98-107`)
  1. 이메일을 보안 컨텍스트에서 꺼내고, `enrichPaymentRequest`가 결제 요청의 `userEmail`을 로그인 사용자로 덮어쓰고 `orderId`를 null로 만든다 (`:119-123`).
  2. `OrderBidCommandService.createInstantOrderBid` (`domain/order/service/command/OrderBidCommandService.java:119-149`)
     - 입력 검증 (`:154-167`)
     - 구매자 조회, `getSaleBidAndValidate` (`:172-184`)
     - `OrderCommandService.createInstantOrder` (`domain/order/service/command/OrderCommandService.java:219-319`): Order·OrderItem·OrderShipment·SaleBid 갱신·결제
     - OrderBid 생성·저장 (`OrderBidCommandService.java:189-207`)
- **동기 처리**: Kafka를 쓰지 않는다. PortOne 카드 결제 HTTP 호출까지 같은 HTTP 요청, 같은 DB 트랜잭션 안에서 끝난다 (`OrderBidCommandService.java:118`, `OrderCommandService.java:219`, `PaymentCommandService.java:37`). Kafka 비동기 흐름은 별도 엔드포인트 `/orders/{id}/process-payment-shipment`이며 이 경로와 무관하다 (`domain/order/controller/command/OrderCommandController.java:42-54`).
- **응답**: HTTP 200, `ResponseDto.success(orderId, "즉시 구매가 성공적으로 처리되었습니다.")` (`OrderBidCommandController.java:101-109`).
- **응답 ID의 주인**: **OrderBid(주문 입찰)의 id**다. `createInstantOrderBid(...)`의 반환값 `OrderBid`에 `.getId()`를 호출한다 (`OrderBidCommandController.java:101-107`). Order의 id가 아니다. 주석 "생성된 주문 ID"(`:83`)와 변수명 `orderId`(`:101`)는 실제와 다르다.
- **검증 공백**
  - `InstantOrderRequestDto.paymentRequest`에 `@Valid`가 없다 (`InstantOrderRequestDto.java:162-163`). 그래서 `PaymentRequestDto`의 제약(`paidAmount` `@Min(100)` 등, `domain/payment/dto/PaymentRequestDto.java:50-51`)이 이 경로에서 실행되지 않는다.
  - `getSaleBidAndValidate`는 null 여부만 본다 (`OrderBidCommandService.java:172-184`). SaleBid나 Sale의 상태(이미 MATCHED/SOLD인지)를 확인하지 않는다.

## 2. 생성되는 엔티티와 상태 변화 (순서대로, 단계 직후 상태)

모든 단계는 한 트랜잭션 안에서 일어난다.

| 순서 | 동작 | 단계 직후 상태 | 근거 |
|---|---|---|---|
| 1 | Order INSERT | `Order.status = PENDING_PAYMENT`, `totalAmount = saleBid.bidPrice`, 할인·포인트 0 | `domain/order/service/command/OrderCommandService.java:241-247` |
| 2 | OrderItem 생성·추가 | (OrderItem 상태 필드 없음) | `OrderCommandService.java:254-260` |
| 3 | OrderShipment 생성 | 구매자 주소로 생성 (창고 여부와 무관) | `OrderCommandService.java:263-275` |
| 4 | SaleBid 갱신 | `assignOrder` → `status = MATCHED`, 이어서 `updateStatus(MATCHED)`, `flush()` | `OrderCommandService.java:279-283`, `domain/sale/entity/SaleBid.java:58-61`. 등록 시 초기값은 PENDING (`domain/sale/service/command/SaleBidCommandService.java:45`) |
| 5 | 창고 보관 상태 (판매가 창고 보관일 때만) | 기존 `WarehouseStorage.status = ASSOCIATED_WITH_ORDER` | `OrderCommandService.java:289-301`, `domain/warehouseStorage/service/command/WarehouseStorageCommandService.java:117-140` |
| 6 | 결제 처리 (`processPayment`) | Payment INSERT (3번 답 참조). 이어서 Sale `status = SOLD` | `OrderCommandService.java:305`; `domain/payment/service/command/PaymentCommandService.java:83, 391-404`. 이 시점에는 OrderBid가 아직 없어서 `order.getOrderBid()`가 null이고, SaleBid 경로로 Sale을 찾는다 |
| 7 | OrderBid INSERT | `status = MATCHED`, `isInstantPurchase = true`, `order`·`sale` 연결 | `OrderBidCommandService.java:189-206`; `domain/order/entity/OrderBid.java:60-75, 97-99` |
| 8 | 커밋, 응답 | 위 상태 확정 | `OrderBidCommandController.java:109` |

- **Order 최종 상태는 `PENDING_PAYMENT`이다.** 이 경로에서 Order의 `updateStatus`를 호출하는 곳이 없다 (`OrderCommandService.java:219-319` 안에 Order 상태 변경 없음). `PAYMENT_COMPLETED`, `PREPARING` 등 전이는 `processPaymentAndShipment`(`OrderCommandService.java:163-177`)와 Kafka 소비자(`domain/order/service/kafka/OrderEventConsumer.java:192-217`)에만 있다.
- Payment는 `order` 쪽에서 `payment` 필드를 세팅하지 않는다. 연결은 Payment 쪽 `order`로 이루어진다 (`PaymentCommandService.java:200, 258`, `domain/payment/entity/Payment.java:47-50`).

## 3. 결제 수단별 결과

공통: `PaymentCommandService.processPayment`(`domain/payment/service/command/PaymentCommandService.java:57-107`)의 금액 검증은 `paidAmount > 0`뿐이다 (`:142-145`). 청구 금액은 요청의 `paidAmount`이며 판매 입찰 가격과 비교하지 않는다 (`:179`에서 그대로 PortOne에 전달).

### CARD (`PaymentCommandService.java:157-225`)

저장된 카드 정보로 PortOne 결제를 요청한다 (`:179`, `domain/payment/portone/PortOneApiClient.java:229-295`).

- **실패 A: PortOne이 오류 코드로 응답 (HTTP ≠ 200 또는 `code ≠ 0`)**
  - `PortOneApiClient.java:270-275`에서 `PaymentProcessingException`을 던지고, 통신 예외는 `:288-290`에서 `PaymentApiException`으로 바뀐다.
  - `PaymentCommandService.java:180-181, 218-219, 89-94`에서 그대로 전파된다.
  - `OrderCommandService.java:304-309`가 `OrderPaymentProcessingFailedException`으로 감싸고, `:312-314`가 다시 던진다.
  - `OrderBidCommandService.java:145-147, 212-218`을 거쳐 예외가 밖으로 나간다. `GlobalException`이 `RuntimeException`이므로 (`src/main/java/com/fream/back/global/exception/GlobalException.java:10`) 트랜잭션이 롤백된다.
  - 결과: Order, OrderItem, Shipment, SaleBid 변경, Payment, 알림, Sale 상태가 모두 취소되고 에러 응답이 나간다.
  - 단, 보상 처리는 없다. 환불 헬퍼 `handleRefundIfNecessary`(`PaymentCommandService.java:341-375`)는 호출처가 없다. PortOne이 청구한 뒤 같은 트랜잭션에서 뒤쪽 단계가 실패하면 청구는 남는다.
- **실패 B: PortOne이 `code = 0`으로 응답하고 `response.status`가 `"success"`가 아님**
  - `PaymentCommandService.java:203-206`의 조건이 거짓이 되어 예외 없이 지나간다.
  - CardPayment는 `status = PENDING`으로 저장된다 (`domain/payment/entity/Payment.java:44`). 그런데 `isSuccess`는 `true`가 된다. 빌더가 `setPaidAmount`를 호출하고, 그 안에서 `isSuccess = paidAmount > 0`이기 때문이다 (`domain/payment/entity/CardPayment.java:38`, `Payment.java:60-62`).
  - `processPayment`가 정상 반환하고 알림 전송, Sale SOLD, OrderBid MATCHED, HTTP 200까지 전부 진행된다.
  - **결제 실패인데 즉시 구매가 성공한다.** `PaymentStatus.FAILED`는 어디에서도 설정되지 않는다. 비교만 있다 (`domain/payment/dto/kafka/PaymentCompletedEvent.java:111`).
  - 주의: `"success"`라는 문자열이 PortOne 실제 응답 값과 맞는지는 저장소만으로 확인할 수 없다.
- **성공**: `status = PAID`, `isSuccess = true`, `paymentDate` 설정 (`PaymentCommandService.java:203-208`, `Payment.java:64-69`). 이후 나머지 흐름은 실패 B와 같다.

### ACCOUNT (`PaymentCommandService.java:236-279`)

- 은행명 검증 후 PortOne을 호출하지 않는다 (`:243-248`).
- AccountPayment를 `status = PENDING`으로 저장한다 (`:260`).
- 예외 없이 끝까지 진행된다. 주문 생성, SaleBid·OrderBid MATCHED, Sale SOLD, 구매자 "결제가 완료되었습니다" 알림까지 나간다.
- 그런데 PENDING을 PAID로 바꾸는 코드가 없다. `updatePaymentStatus`(`PaymentCommandService.java:498`)는 호출처가 없고, 입금 확인 콜백이나 웹훅 컨트롤러도 저장소에 없다. 계좌이체 결제는 영구히 PENDING이다.

### GENERAL (`PaymentCommandService.java:290-333`)

- 클라이언트가 보낸 `impUid`, `pgProvider` 등을 그대로 저장하고, PortOne 조회 없이 `updateSuccessStatus(true)`, `updateStatus(PAID)`를 호출한다 (`:313-314`).
- 검증 없이 성공한다. 나머지 흐름은 카드 성공과 같다.

### 결제 대행사가 카드 결제를 실패로 응답하면

- 명시적 오류 응답(실패 A)이면 **전체 롤백, 에러 응답**이다.
- 성공 코드로 돌아오지만 상태가 실패인 경우(실패 B)에는 **실패가 성공으로 처리된다**.

### 즉시 구매가 끝까지 성공하는지

예외가 발생하지 않는 한 CARD(성공 또는 실패 B), ACCOUNT, GENERAL 모두 HTTP 200으로 끝난다. 이때 Order는 `PENDING_PAYMENT`에 머무른다.

## 4. 알림

- **받는 사람**
  - 구매자: `PaymentCommandService.java:436-445`. 카테고리 SHOPPING, 타입 BID, 메시지 "결제가 완료되었습니다. 주문 ID: …" (`:442`).
  - 판매자: `:447-454`. 메시지 "구매자가 결제를 완료하였습니다. 판매 ID: …" (`:453`).
- **시점**: `processPayment` 안에서 동기로 보낸다. 결제 직후, OrderBid 저장과 커밋 이전이다 (`PaymentCommandService.java:83, 403, 416`).
- **방식**: DB에 먼저 저장한 뒤 실시간 전송을 시도한다 (`domain/notification/service/command/NotificationCommandService.java:44-67`, 전송 호출 `:57`).
  - 실시간 전송은 Redis 키 `WebSocket:User:<email>`가 있을 때만, STOMP `/queue/notifications`로 보낸다 (`NotificationCommandService.java:37-38, 303-309`).
  - 커밋 전에 push가 나가므로, 이후 롤백되어도 push는 회수되지 않는다.
  - 알림 실패는 예외 없이 로그만 남긴다 (`PaymentCommandService.java:457-461`).
- **결제 상태와 무관하게 나간다**: 계좌이체 PENDING, 카드 실패 B에서도 "결제가 완료되었습니다"가 나간다.
- 이 경로에는 이메일 등 외부 채널이 없다.

## 5. 처리 완료 시 최종 상태와 창고 보관

정상 완료 시 최종 상태:

- **Order**: `PENDING_PAYMENT` (변경 없음). OrderItem과 OrderShipment는 생성되어 있다.
- **Payment**: 카드 성공 PAID / 카드 실패 B PENDING(`isSuccess = true`) / 계좌이체 PENDING / 일반 PAID.
- **SaleBid**: MATCHED, order 연결 (`OrderCommandService.java:279-280`).
- **Sale**: SOLD (`PaymentCommandService.java:404` 또는 `:419`).
- **OrderBid**: MATCHED, `isInstantPurchase = true`, sale·order 연결 (`OrderBidCommandService.java:196-205`).

**구매자가 "창고 보관"을 선택한 경우 달라지는 것은 없다.**

- 요청의 `warehouseStorage` 값은 쓰이지 않는다. `createInstantOrder`의 `isWarehouseStorage` 파라미터(`OrderCommandService.java:221`)는 본문에서 참조되지 않는다.
- 분기 조건은 판매(Sale)의 `isWarehouseStorage()`이며, 판매자가 정한 값이다 (`OrderCommandService.java:292`).
- 판매가 창고 보관 대상이면 기존 WarehouseStorage의 상태만 `ASSOCIATED_WITH_ORDER`로 바뀐다 (`OrderCommandService.java:293`, `WarehouseStorageCommandService.java:117-140`). 조회는 Sale 기준이며 없으면 예외다 (`domain/warehouseStorage/service/query/WarehouseStorageQueryService.java:30-33`).
- WarehouseStorage를 새로 만들지 않고 Order에 연결하지 않는다. `createOrderStorage`와 `assignWarehouseStorage`는 이 경로에서 호출되지 않는다.
- Order는 `COMPLETED`가 되지 않는다. 창고 보관 흐름의 `IN_WAREHOUSE → COMPLETED` 전이(`OrderCommandService.java:163-172`)는 `processPaymentAndShipment`에만 있다. 즉시 구매 경로에는 없다.

## 의도(주석·이름)와 실제 동작이 다른 곳

- **응답 ID**: "생성된 주문 ID"라고 적혀 있지만 실제로는 OrderBid의 ID다 (`OrderBidCommandController.java:83, 101-107`).
- **"즉시 구매가 성공적으로 처리되었습니다"**: Order는 `PENDING_PAYMENT`에 머문다. 결제 완료 전이가 없다.
- **창고 보관 선택**: 구매자 플래그는 무시되고, 판매자의 Sale 플래그만 본다 (`OrderCommandService.java:221, 292`).
- **결제 실패 B**: 실패가 성공 흐름으로 들어간다 (`PaymentCommandService.java:203-206`).
- **계좌이체**: PENDING인데 "결제가 완료되었습니다" 알림이 나간다 (`PaymentCommandService.java:438-443`).
- **금액 검증**: `PaymentRequestDto`의 "100원 이상" 제약은 `@Valid` 누락으로 이 경로에서 적용되지 않는다 (`InstantOrderRequestDto.java:162-163`).
- **알림·Sale 갱신**: "핵심 기능이 아니므로 예외를 던지지 않는다"는 주석대로 실패를 삼킨다 (`PaymentCommandService.java:421-425`). 결제 상태가 PENDING이어도 Sale은 SOLD가 된다.

## 저장소만으로 확인하지 못한 것

- PortOne 응답의 실제 `status` 값과 실패 시 `code` 값. 외부 API라 실제 응답 형식은 확인할 수 없다.
- 같은 SaleBid에 즉시 구매를 두 번 요청하는 경우. 상태 검사가 없어(`OrderBidCommandService.java:172-184`) 코드상 막는 곳이 없다. 실행해 보지는 않았다.
- `getAddress`의 주소 소유권 검사 내부. 확인하지 않았다.
