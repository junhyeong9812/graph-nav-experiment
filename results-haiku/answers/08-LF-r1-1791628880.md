# 답: 구매자 배송 — 운송장 등록부터 배송 완료까지

> 경로는 `src/main/java/com/fream/back/` 기준 상대경로(`domain/...`)로 줄여 쓰지 않고 저장소 기준 전체 경로로 적었다.
> 코드는 수정하지 않았고, 정적 추적으로만 확인했다(DB·Playwright·CJ 연동은 실행하지 않음).

**요약**
- 운송장 등록(`PATCH /shipments/order/{shipmentId}/status`)은 (a) 실배송 일반 입찰 주문, (b) 즉시 구매 주문 모두 **실패**한다. 주문을 `IN_TRANSIT`으로 바꿀 수 없어서다. 실패 응답은 404 / `S001`이고, 이 요청으로 저장되는 것은 없다.
- 배송 완료 감지는 6시간 주기 배치이며, 실제로 실행되는 처리는 `ShipmentItemProcessor`다.
- (a)는 어떤 경로로도 `COMPLETED`에 도달하지 못한다. (b)는 `check-status` 우회 경로로 `COMPLETED`까지 갈 수 있지만, 입찰 상태가 `COMPLETED`로 바뀌지 않는다.

## 1. 운송장 등록 요청

**API**
- `PATCH /shipments/order/{shipmentId}/status` → `OrderShipmentCommandController#updateTrackingInfo` → `OrderShipmentCommandService#updateTrackingInfo`
  - `src/main/java/com/fream/back/domain/shipment/controller/command/OrderShipmentCommandController.java:20, 33-45`
  - `src/main/java/com/fream/back/domain/shipment/service/command/OrderShipmentCommandService.java:238-303`
- 같은 `courier`/`trackingNumber`를 받는 `POST /shipments/order/{id}/check-status`(및 `-string`)도 송장을 저장한다. (3·4절에서 다룸) `OrderShipmentCommandController.java:58-103`

**의도된 상태 변화 순서 (`updateTrackingInfo`)**
1. `OrderShipment`: 택배사·송장 저장, `status = IN_TRANSIT` (`src/main/java/com/fream/back/domain/shipment/entity/OrderShipment.java:41-45`, 전이 검증 없음; 호출 `OrderShipmentCommandService.java:256`)
2. `Order`: `order.updateStatus(IN_TRANSIT)` (`OrderShipmentCommandService.java:259-260`)
3. 구매자 알림 1건 "상품이 출발하였습니다" (`:265-271`)
4. `updateSaleStatusToSold` (`:276`) → 허용될 때만 `Sale → SOLD` + 판매자 알림 1건 (`:112-148`, 검사 `:119`)
5. 창고 보관 상품이면 창고 상태 SOLD (`:279-286`)
6. `OrderBid`/`SaleBid`: `MATCHED → COMPLETED` (`:289`, 메서드 `:413-440`, 예외는 로그만 남기고 삼킴)

알림 push는 `NotificationCommandService#createNotification` → Redis 키(`WebSocket:User:{email}`)가 있을 때만 WebSocket 전송 (`src/main/java/com/fream/back/domain/notification/service/command/NotificationCommandService.java:57`).

**(a) 실배송 일반 구매 입찰 주문 — 실패**
- 결제 후 상태: `OrderEventConsumer#processCompleteOrder`가 `PAYMENT_COMPLETED`(`src/main/java/com/fream/back/domain/order/service/kafka/OrderEventConsumer.java:195`) 후 `PREPARING`으로 저장(`:216-218`).
- 전이표: `PREPARING → {IN_WAREHOUSE, SHIPMENT_STARTED}`만 허용(`src/main/java/com/fream/back/domain/order/entity/OrderStatus.java:26`). `IN_TRANSIT`은 `SHIPMENT_STARTED`에서만 가능(`:28`). `SHIPMENT_STARTED`를 설정하는 코드는 없다(전체 검색 결과, 화면 표시 문구만 있음 `OrderQueryController.java:207`).
- 따라서 `OrderShipmentCommandService.java:260`의 `order.updateStatus(IN_TRANSIT)`에서 `Order.java:113-121`이 `InvalidOrderStatusException`을 던진다.
- 이 예외는 `:293-301`의 `catch (Exception e)`에서 `ShipmentException(SHIPMENT_NOT_FOUND)`(S001)로 감싸져 다시 던져지고, `@Transactional`이 롤백한다.
- **응답**: 컨트롤러는 예외를 잡지 않는다. `GlobalExceptionHandler.handleShipmentException`(`src/main/java/com/fream/back/global/exception/GlobalExceptionHandler.java:459-471`)이 처리해서 **HTTP 404**, 본문 `ErrorResponse`의 `code = "S001"`, `message = "배송 정보를 찾을 수 없습니다."`(enum 기본 문구)를 돌려준다(`ShipmentErrorCode.java:12`). 실제 원인은 로그에만 남는다.
- **저장되는 것: 없음.** `OrderShipment`는 `PENDING`에 송장 없음 그대로, `Order`는 `PREPARING`, 알림도 없다.
- 참고: 전이 검사를 통과하더라도 다음 단계 `:276` → `:116`의 `SaleBidQueryService#findByOrderId`가 `SaleBid`가 없으면 `IllegalArgumentException`을 던진다(`src/main/java/com/fream/back/domain/sale/service/query/SaleBidQueryService.java:26-29`). 일반 입찰은 `SaleBid`와 연결되지 않으며, 판매자가 `POST /sale-bids/instant`로 즉시 판매를 해야 연결된다(`src/main/java/com/fream/back/domain/sale/service/command/SaleBidCommandService.java:78, 83`). 즉 두 번째 장애물도 같은 S001로 실패한다.

**(b) 즉시 구매 주문 — 실패**
- `OrderCommandService#createInstantOrder`(`src/main/java/com/fream/back/domain/order/service/command/OrderCommandService.java:219-319`):
  - `Order` 생성, 상태 `PENDING_PAYMENT`(`:244`)
  - `OrderShipment` 생성, 상태 `PENDING`(`:264-271`)
  - `SaleBid`를 주문에 연결(`:279-283`)
  - 결제 실행(`:305`). 이때 `Order`는 `PENDING_PAYMENT`에 그대로 남는다.
- 등록 시 `:260`의 `PENDING_PAYMENT → IN_TRANSIT`은 전이표에 없다(`OrderStatus.java:24`는 `PAYMENT_COMPLETED`, `COMPLETED`, `IN_WAREHOUSE`만 허용). 따라서 (a)와 같은 경로로 **404 / S001**, 롤백.
- 이미 저장된 것(등록 실패와 무관): 결제, 주문·입찰 연결, `OrderBid`(MATCHED, `OrderBidCommandService.java:189-207`, `OrderBid.java:74-75`).
  - 결제 시점에 `Sale`이 바로 `SOLD`가 된다(`PaymentCommandService.java:404`, 해당 분기에서 검증 없이 `updateStatus`). 결제 알림도 이때 나간다(구매자 `:442`, 판매자 `:453`).

## 2. 배송 완료 감지

- **누가/언제/어떻게**
  - 자동: `ShipmentBatchScheduler#scheduleShipmentStatusJob`, cron `0 0 */6 * * *` → 6시간마다(0·6·12·18시 정각, 서버 시간대) `updateShipmentStatusesJob` 실행 (`src/main/java/com/fream/back/global/config/ShipmentBatchScheduler.java:34-40`).
  - 수동: `POST /shipments/order/{id}/check-status`(`OrderShipmentCommandService#updateAndCheckShipmentStatus`, `:451-516`).
  - `@EnableScheduling`은 다른 스케줄러에 이미 있어 전역으로 켜져 있다(`src/main/java/com/fream/back/domain/event/scheduler/EventStatusScheduler.java:22`). `@EnableBatchProcessing`은 `src/main/java/com/fream/back/global/config/BatchInfraConfig.java:15`.
  - `spring.batch.job.enabled` 설정이 없으므로(리소스 전체 확인) Spring Boot 기본값대로 기동 시에도 Job이 한 번 실행된다고 보는 것이 맞다(프레임워크 동작에 근거한 추론).
- **대상 배송**: reader `shipmentItemReader()`의 쿼리 — `status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND trackingNumber IS NOT NULL`, 페이지 50 (`src/main/java/com/fream/back/domain/shipment/config/UpdateShipmentStatusesJobConfig.java:87-97`). 주문 종류 구분은 없다.
- **Step 구성**: chunk 50, `faultTolerant().skip(Exception.class).skipLimit(50)` (`:63-82`).
- **실제로 실행되는 처리 코드**: `:69-73`의 `new ShipmentItemProcessor(...)` → `ShipmentItemProcessor#process` (`src/main/java/com/fream/back/domain/shipment/config/ShipmentItemProcessor.java:57-157`).
  - 비슷하지만 실행되지 않는 코드:
    - `UpdateShipmentStatusesJobConfig#shipmentItemProcessor()` 람다 (`:104-177`): Step이 참조하지 않는다. Javadoc은 `parseCjLogisticsStatus`를 말하지만 그 메서드(`:186-220`)도 호출되지 않는다.
    - `OrderShipmentCommandService#updateShipmentStatuses` (`OrderShipmentCommandService.java:309-391`): 호출처가 없다.
    - `CjTrackingPlaywright#getCurrentTrackingStatus`(`src/main/java/com/fream/back/global/utils/CjTrackingPlaywright.java:33-115`): 수동 `check-status`에서만 쓰이며, 호출마다 새 Chromium을 띄운다.
- **조회 방법**: 공유 브라우저에서 새 페이지 열기(`ShipmentItemProcessor.java:72`) → `https://trace.cjlogistics.com/next/tracking.html?wblNo={운송장번호}` 접속(`:81-83`) → `tbody#statusDetail tr` 대기(`:87`) → 마지막 행의 5번째 `td` 텍스트 파싱(`:167-191`).
- **택배사 문자열 → 내부 상태** (`ShipmentItemProcessor.java:220-226`)
  - `"배송완료"` → `DELIVERED`
  - `"배송출발"` → `OUT_FOR_DELIVERY`
  - 그 밖의 모든 문자열 → `IN_TRANSIT`
  - 현재 상태와 같으면 아무것도 하지 않는다(`:101-105`).

## 3. 배송 완료 판정 이후 (DELIVERED 판정, 배치 경로)

순서:
1. `OrderShipment` → `DELIVERED` (`ShipmentItemProcessor.java:108-113`, `OrderShipment.java:47-55`; `IN_TRANSIT`·`OUT_FOR_DELIVERY`에서 전이 허용, `ShipmentStatus.java:16-28`)
2. `OrderShipmentCommandService#completeOrder` 호출 (`ShipmentItemProcessor.java:116`, 본문 `OrderShipmentCommandService.java:190-229`)
   - a. `Order` → `COMPLETED` (`:204`). 전이표상 `PENDING_PAYMENT`, `IN_WAREHOUSE`, `IN_TRANSIT`에서만 가능(`OrderStatus.java:24, 27, 29`). `PREPARING`에서는 불가.
   - b. `updateSaleStatusToSold` (`:208`): `Sale → SOLD`는 `canTransitionTo(SOLD)`일 때만. 허용 출발 상태는 `ON_AUCTION`, `SELLING`뿐이며(`SaleStatus.java` 해당 분기), 이 상태들은 거래 흐름에서 설정되지 않는다. 따라서 `PENDING_SHIPMENT`·`IN_TRANSIT` 판매는 `SOLD`가 되지 않는다. 이미 `SOLD`이면 건너뛴다.
   - c. 구매자 알림 "[completeOrder] 주문이 완료 처리되었습니다" (`:212-217`)
   - `OrderBid`/`SaleBid`는 바뀌지 않는다. 입찰 `COMPLETED` 전환은 `updateTrackingInfo` 안에서만 일어난다(`:289`).
3. `NotificationCommandService#notifyShipmentCompleted` (`ShipmentItemProcessor.java:117` → `NotificationCommandService.java:219-234`): 구매자 알림 "[배송 완료] …" 1건
4. chunk 커밋 시 `JpaItemWriter`가 반영 (`UpdateShipmentStatusesJobConfig.java:239-246`)

**알림 요약**: 구매자 2건(`[completeOrder]`, `[배송 완료]`), 판매자 0건(판매 상태가 `SOLD`로 전이되지 않는 한).
- `check-status`의 DELIVERED 분기(`OrderShipmentCommandService.java:483-489`)는 `completeOrder`만 호출하고 `notifyShipmentCompleted`는 호출하지 않으므로, 구매자 알림은 1건이다.
- 알림 push는 트랜잭션 커밋 전에 나간다(`NotificationCommandService.java:57`). 뒤에 롤백되어도 WebSocket 알림은 이미 전송된다.

**입찰 상태**: 배치 경로의 DELIVERED 처리에서는 `OrderBid`·`SaleBid` 상태가 바뀌지 않는다. 등록 단계(`:289`)에서 이미 `COMPLETED`가 되어 있어야 하지만, (a)·(b) 모두 등록이 실패하므로 `MATCHED` 그대로다.

## 4. 주문 종류별 차이

**(a) 실배송 일반 구매 입찰**
- 정상 등록 경로: 1단계에서 실패하므로 3단계에 도달하지 않는다.
- 우회 경로 ① — `check-status`에 CJ "배송완료"가 올 때: `completeOrder`의 `PREPARING → COMPLETED`가 불가하다(`OrderShipmentCommandService.java:204`, `OrderStatus.java:26`). `ShipmentException(ORDER_NOT_FOUND_FOR_SHIPMENT, S102)`(`:221-227`, 코드 `ShipmentErrorCode.java:20`)로 롤백된다. 응답은 `S102`의 상태 404이고 본문은 없다(`OrderShipmentCommandController.java:80-86`).
- 우회 경로 ② — `check-status`에 CJ "배송출발"이 올 때: 예외 없이 **커밋된다**. `OrderShipment`는 `OUT_FOR_DELIVERY` + 택배사·송장 저장(`OrderShipmentCommandService.java:473, 491-493`), `Order`는 `PREPARING` 그대로, 응답은 200 `OUT_FOR_DELIVERY`. 이후 배치 reader가 이 건을 집어 가고, 매 실행마다 DELIVERED → `completeOrder` 실패 → skip이 반복된다.
- 최종 상태: `Order`는 `PREPARING`에 머문다. `PREPARING`에서 나갈 수 있는 상태는 `IN_WAREHOUSE`, `SHIPMENT_STARTED`뿐이고 후자는 설정되지 않으므로, **`COMPLETED`에 도달하는 코드 경로가 없다.** `OrderBid`는 `MATCHED`에 남는다.

**(b) 즉시 구매 주문**
- 정상 등록 경로: (a)와 같이 1단계에서 실패하므로 3단계에 도달하지 않는다.
- `check-status`에 CJ "배송완료"가 올 때 — 완료된다:
  1. `updateAndCheckShipmentStatus`: 방금 `IN_TRANSIT`으로 설정한 송장이 `DELIVERED`로 전이(`OrderShipmentCommandService.java:473, 483-486`)
  2. `completeOrder`: `Order`가 `PENDING_PAYMENT → COMPLETED`로 전이된다. 이 전이는 허용된다(`OrderStatus.java:24`). (a)와 달리 여기서 막히지 않는다.
  3. `updateSaleStatusToSold`: `Sale`은 결제 때 이미 `SOLD`이므로 건너뛴다. `SaleBid`·`OrderBid` 경로 모두 예외 없이 지나간다.
  4. 구매자 알림 1건 `[completeOrder]`, 커밋. 응답 200 `DELIVERED`.
  - 결과: `OrderShipment` DELIVERED, `Order` COMPLETED, `Sale` SOLD(결제 시점). **`OrderBid`·`SaleBid`는 `MATCHED` 그대로**(입찰 COMPLETED 전환 없음), 「배송 완료」 알림 없음.
- `check-status`로 "배송출발"을 받은 뒤 배치가 DELIVERED를 판정하는 경우: 3절과 같은 경로로 완료되지만(구매자 알림 2건), 입찰 상태는 여전히 `MATCHED`다.

| 구분 | (a) 일반 입찰 | (b) 즉시 구매 |
|---|---|---|
| 정상 등록 | 실패 (404 S001, 저장 없음) | 실패 (404 S001, 저장 없음) |
| 실패 지점 | `OrderShipmentCommandService.java:260`, `PREPARING→IN_TRANSIT` 불가 | 같은 줄, `PENDING_PAYMENT→IN_TRANSIT` 불가 |
| 우회 경로로 완료 | 불가 (`PREPARING→COMPLETED` 불가) | 가능 (`PENDING_PAYMENT→COMPLETED` 허용) |
| 완료 시 판매 상태 | 판매 없음(SOLD 되지 않음) | 이미 SOLD (결제 시점) |
| 입찰 상태 | `MATCHED` 유지 | `MATCHED` 유지 |

## 5. 실패 처리 (배치 한 건 실패 시)

- **그 건**: `ShipmentItemProcessor`가 예외를 던지면 Step의 `faultTolerant().skip(Exception.class)`(`UpdateShipmentStatusesJobConfig.java:75-77`)가 그 건만 skip한다. `shipmentSkipListener`가 로그를 남긴다(`:252-287`). 그 건은 DB 상태(`IN_TRANSIT`/`OUT_FOR_DELIVERY`) 그대로 남고, 다음 6시간 실행에서 다시 시도된다.
- **나머지 건**: 같은 Step에서 계속 처리된다. 단, 아래 롤백 주의가 있다.
  - `completeOrder`는 `@Transactional`(REQUIRED 기본값)이라 청크 트랜잭션에 참여하고, 실패 시 `RuntimeException`을 던진다(`OrderShipmentCommandService.java:190, 221-227`). 그러면 공유 트랜잭션이 rollback-only로 표시된다. 청크 커밋이 실패할 수 있고, 그 경우 Spring Batch가 청크를 건별로 다시 처리하며 같은 청크의 성공 건도 재처리된다고 보는 것이 맞다. **실행해서 확인하지는 않았다.**
  - 처리 도중 `orderShipment.updateStatus(DELIVERED)`는 메모리에서 먼저 바뀌므로, 롤백에 의존해 DB에 남지 않아야 한다.
- **한도 초과**: `skipLimit` 50은 한 Step 실행 안의 skip 건수 기준이다. 넘으면 Step과 Job이 실패하고 남은 건은 다음 실행까지 처리되지 않는다(Spring Batch 기본 동작).

**코드에서 확인한 잠재 문제 (실행 확인 안 함)**
- OUT_FOR_DELIVERY인 건에 CJ가 "배송완료"/"배송출발" 외의 문자열을 주면 `IN_TRANSIT`으로 매핑되고, `OUT_FOR_DELIVERY → IN_TRANSIT`은 허용되지 않으므로 `IllegalStateException`이 난다(`ShipmentItemProcessor.java:123-126`, `ShipmentStatus.java:23-28`, `OrderShipment.java:47-55`). 매 실행마다 skip된다.
- reader는 오프셋 페이징(페이지 50)이고 ORDER BY가 없다. 처리 중에 상태가 바뀌어 결과 집합이 줄어들면 다음 페이지에서 일부 건이 빠질 수 있다(코드상 추론).

## 주석·메서드명과 실제 동작이 다른 곳 (실제 동작 기준으로 답함)
- `OrderShipment.updateTrackingInfo`: "정보 갱신"이라는 이름이지만 검증 없이 `IN_TRANSIT`을 설정한다(`OrderShipment.java:41-45`).
- `updateTrackingInfo`의 주석 "배송 상태가 변경되었으므로 주문 상태도 업데이트"(`OrderShipmentCommandService.java:258`)는 실제로 `PREPARING`·`PENDING_PAYMENT`에서 항상 실패한다.
- `UpdateShipmentStatusesJobConfig`의 Javadoc "parseCjLogisticsStatus를 통해 파싱"은 맞지 않는다. 실제 파싱은 `ShipmentItemProcessor`가 한다.
- `updateOrderAndSaleBidStatusToCompleted`는 실패를 전부 로그로 삼키므로(`OrderShipmentCommandService.java:436-439`), 입찰 상태가 바뀌지 않아도 호출자는 알 수 없다.

## 검증 범위
- 실행하지 않았다. DB, Playwright, CJ 연동 없이 정적 추적만 했다.
- 실행 없이 추론한 것: Spring Batch의 청크 롤백 후 건별 재처리, Spring Boot의 기동 시 Job 자동 실행, reader 오프셋 누락 가능성.
- 줄 번호는 현재 파일 기준으로 확인했다.
