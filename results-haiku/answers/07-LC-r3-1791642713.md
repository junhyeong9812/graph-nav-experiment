# 즉시 구매는 어떻게 처리되나

경로는 저장소 루트 기준이다. `D/` = `src/main/java/com/fream/back/domain/`.

## 1. 진입점, 처리 단계, 동기/비동기, 응답 ID

- 진입점: `POST /order-bids/instant` → `D/order/controller/command/OrderBidCommandController.java:89-90`
- 요청 본문 `InstantOrderRequestDto`: `saleBidId`, `addressId`, `warehouseStorage`, `paymentRequest` (`D/order/dto/InstantOrderRequestDto.java:20-29`). `paymentRequest`에는 `@NotNull`만 있고 `@Valid`가 없어서 내부 제약(`paymentType` `@NotBlank`, `paidAmount` `@Min(100)` 등)은 검사되지 않는다.
- 처리 순서:
  1. 컨트롤러가 이메일을 꺼내고(`OrderBidCommandController.java:92`), 결제 요청의 `userEmail`을 로그인 사용자로, `orderId`를 `null`로 덮어쓴다(`:98`, `:119-123`).
  2. `OrderBidCommandService#createInstantOrderBid` (`D/order/service/command/OrderBidCommandService.java:118-149`, `@Transactional`): 구매자 조회(`:126`), `SaleBid` 조회(`:129`).
  3. `OrderCommandService#createInstantOrder` (`D/order/service/command/OrderCommandService.java:220-319`): 주소 조회, Order/OrderItem/OrderShipment 생성, SaleBid 매칭, 창고 상태 갱신, 결제 처리.
  4. 다시 `OrderBidCommandService`로 돌아와 OrderBid를 저장(`OrderBidCommandService.java:142`).
- **동기 처리**다. 같은 HTTP 요청 스레드에서 PortOne 호출(`D/payment/service/command/PaymentCommandService.java:179`)까지 끝내고 응답한다. 이 경로에는 Kafka 발행이 없다(일반 주문의 `process-payment-shipment`가 202를 주는 것과 다르다). PortOne 호출이 DB 트랜잭션 안에서 일어난다.
- **응답 ID는 OrderBid의 ID다.** 컨트롤러 변수는 `Long orderId`라고 되어 있지만 실제로는 `createInstantOrderBid(...).getId()`, 즉 OrderBid ID다(`OrderBidCommandController.java:101-109`). Order ID가 아니다.

## 2. 생성되는 엔티티와 상태 변화 순서

처음 상태: 판매 입찰이 등록될 때 이미 SaleBid가 MATCHED다. `SaleBidCommandService.java:53` → `Sale.java:59-61` → `SaleBid.java:53-56`. Sale은 PENDING_SHIPMENT다(`D/sale/service/command/SaleCommandService.java:62`). 따라서 즉시 구매가 SaleBid 상태를 바꾸지 않는다. 한 트랜잭션 안에서 아래 순서로 진행된다.

| 순서 | 대상 | 동작 (근거) | 직후 상태 |
|---|---|---|---|
| 1 | Address | 구매자 이메일과 addressId로 배송지 조회 (`OrderCommandService.java:238`) | 변화 없음 |
| 2 | Order (신규) | `PENDING_PAYMENT`, `totalAmount = saleBid.bidPrice` 로 INSERT (`:241-247`) | Order=PENDING_PAYMENT |
| 3 | OrderItem (신규) | 상품 사이즈와 bidPrice로 생성 후 연결 (`:254-256`) | — |
| 4 | OrderShipment (신규) | 배송지 정보로 생성, `ShipmentStatus.PENDING` (`:264-271`, `D/shipment/service/command/OrderShipmentCommandService.java:67`) | OrderShipment=PENDING |
| 5 | SaleBid | `assignOrder(order)` → `status=MATCHED`, 이후 `flush` (`:279-283`, `D/sale/entity/SaleBid.java:58-61`) | SaleBid=MATCHED, order 연결 |
| 6 | WarehouseStorage (기존, Sale 기준) | `sale.isWarehouseStorage()`가 true일 때만 `IN_STORAGE → ASSOCIATED_WITH_ORDER` (`:292-294`, `D/warehouseStorage/service/command/WarehouseStorageCommandService.java:117-140`) | 창고 보관이면 ASSOCIATED_WITH_ORDER |
| 7 | Payment (신규) | `processPayment` 실행 (`:305`). 결제 유형별 결과는 3번 참고 | CARD: CardPayment, GENERAL: PAID, ACCOUNT: 실패 |
| 8 | Sale | `notifyUsersAndUpdateSaleStatus`에서 `sale.updateStatus(SOLD)` (`PaymentCommandService.java:404`, `:419`) | Sale=SOLD |
| 9 | Notification (신규) | 구매자, 판매자 알림 저장 (`PaymentCommandService.java:438`, `:449`) | — |
| 10 | OrderBid (신규) | `status=MATCHED`, `isInstantPurchase=true`, `order`, `sale`, `user=buyer` 로 INSERT, `order.orderBid` 연결 (`OrderBidCommandService.java:189-207`, `D/order/entity/OrderBid.java:60-82`) | OrderBid=MATCHED |
| 11 | 커밋 | 여기까지 예외가 없으면 커밋 | — |

마지막 상태:
- Order: **`PENDING_PAYMENT`에서 바뀌지 않는다.** `Order.assignPayment`도 호출되지 않는다. `assignPayment`는 `processPaymentAndShipment`(`OrderCommandService.java:140`)에서만 호출된다.
- OrderShipment: PENDING, SaleBid: MATCHED, OrderBid: MATCHED, Sale: SOLD.
- Payment: CARD는 PG 응답에 따라 PAID 또는 PENDING, GENERAL은 PAID, ACCOUNT는 저장되지 않는다.

## 3. 결제 수단별 결과와 카드 실패 처리

`PaymentCommandService#processPayment` (`D/payment/service/command/PaymentCommandService.java:57-107`)에서 `switch`로 나뉜다.

**금액 검증이 없다 (공통).** `validatePaymentRequest`는 `paidAmount > 0`만 확인한다(`:142-145`). 상품 가격(`saleBid.bidPrice`)과 비교하지 않는다. `paymentRequest`에 `@Valid`가 없어 `@Min(100)`도 적용되지 않는다(`InstantOrderRequestDto.java:28-29`). 그래서 **구매자가 보낸 `paidAmount`가 그대로 PortOne 카드 결제 금액이 된다**(`:179`, `PortOneApiClient.java:250`).

**CARD**
- PortOne 호출 → `processCardPayment` (`D/payment/portone/PortOneApiClient.java:229`).
- PG가 거절하면 응답 `code != 0`이고 `PaymentProcessingException`이 던져진다(`PortOneApiClient.java:270-275`).
- `createCardPayment`는 이를 그대로 전파하고(`PaymentCommandService.java:179-184`, `:218-219`), `createInstantOrder`가 `OrderPaymentProcessingFailedException`으로 감싼다(`OrderCommandService.java:304-309`).
- `OrderException`은 `RuntimeException`의 하위라 트랜잭션이 롤백된다(`global/exception/GlobalException.java:10`, `D/order/exception/OrderException.java:10`). Order, OrderItem, OrderShipment, SaleBid 매칭, 창고 상태, 알림 모두 되돌아간다.
- 응답: HTTP 500, 코드 `ORD005`. ErrorResponse 메시지는 enum 기본 문구인 "주문 결제 처리에 실패했습니다."이고 PG 사유는 응답에 나가지 않는다(`D/order/exception/OrderErrorCode.java:44`, `global/exception/GlobalExceptionHandler.java:325-337`). PG 사유는 로그에만 남는다(`PaymentCommandService.java:90-94`).
- `@Retryable`이 `processCardPayment`에 붙어 있지만 저장소에 `@EnableRetry`가 없어서 재시도는 일어나지 않는다(`PortOneApiClient.java:224-228`).
- 성공 판정: PG 응답 `status`가 문자열 `"success"`일 때만 `PAID`와 `isSuccess=true`로 바꾼다(`PaymentCommandService.java:203-206`). 그 외에는 `Payment` 기본값인 `PENDING`, `isSuccess=false`로 저장된다(`D/payment/entity/Payment.java:39`, `:44`). 예외가 없으므로 흐름은 계속되어 **Sale은 SOLD, 알림은 "결제가 완료되었습니다"로 나간다.** `"success"` 리터럴이 PortOne 실제 응답 값과 맞는지는 저장소만으로는 확인할 수 없다.

**ACCOUNT**
- 계좌이체는 항상 실패한다. `AccountPayment` 생성자는 status를 세팅하지 않아 `PENDING`이 되고(`D/payment/entity/AccountPayment.java:21-28`), 이어서 `updateStatus(PENDING)`(`PaymentCommandService.java:260`)을 호출한다. `PaymentStatus.canTransitionTo`는 PENDING→PAID만 허용하므로(`D/payment/entity/PaymentStatus.java:10-20`) `Payment.updateStatus`가 `IllegalStateException`을 던진다(`Payment.java:70-75`). 이것이 `PaymentProcessingException`으로 바뀌어 롤백된다(`PaymentCommandService.java:274-277`).

**GENERAL**
- `impUid`를 클라이언트 값 그대로 믿고 `PAID`로 저장한다(`PaymentCommandService.java:297-314`). PortOne 검증 호출이 없다. 성공 흐름을 탄다.

**즉시 구매가 끝까지 성공하는가**
- 결제 단계는 CARD(PG 승인 시)와 GENERAL에서 성공한다. ACCOUNT는 항상 실패한다.
- 성공해도 주문은 `PENDING_PAYMENT`로 남는다(2번 참고). 주문이 "끝까지" 진행된 상태는 아니다.

**카드 결제 실패 응답의 문제점**
- PG 거절 자체는 PortOne에서 승인이 안 났으므로 환불이 필요 없다.
- 하지만 PortOne 승인 후 같은 트랜잭션에서 예외가 나면(예: `OrderBidCommandService.java:142` 저장 또는 커밋 실패) DB는 롤백되고 PG 승인 금액만 남는다. 환불 경로가 없다. `refundPayment(Long)`(`PaymentCommandService.java:543`)과 `handleRefundIfNecessary`(`:341`, private)는 호출처가 없다. `PortOneApiClient.refundPayment`(`:308`)도 `:376`, `:386`에서만 불린다.

## 4. 알림 수신자, 시점, 방식

수신자와 내용 (`PaymentCommandService.java:434-462`, `:438`, `:449`):
- 구매자(`order.getUser()`): `SHOPPING`/`BID`, "결제가 완료되었습니다. 주문 ID: {orderId}"
- 판매자(`sale.getSeller()`): `SHOPPING`/`BID`, "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}"

시점과 방식:
- `processPayment` 안에서 동기로 호출된다(`PaymentCommandService.java:83`, `:403`, `:416`). 결제 성공 직후이고 OrderBid 저장과 커밋 전이다.
- `NotificationCommandService#createNotification`(`D/notification/service/command/NotificationCommandService.java:44-57`)이 DB에 행을 저장한다. 클래스가 `@Transactional`이라(`:27`) 외부 트랜잭션에 참여한다.
- 실시간 전송은 Redis 키 `WebSocket:User:{email}`이 있을 때만 시도한다(`:37`, `:303-307`). 있으면 STOMP `convertAndSendToUser(email, "/queue/notifications", …)`로 보낸다(`:38`, `:309`). Kafka는 쓰지 않는다. 연결이 없으면 DB에만 남는다.
- 알림 실패는 삼킨다. `createNotification`과 `sendNotifications` 모두 예외를 로그로만 남긴다(`PaymentCommandService.java:457-461`). 알림 전송 후 같은 트랜잭션이 롤백되면 이미 보낸 실시간 알림과 DB가 어긋난다.
- 결제가 실패하면 알림은 나가지 않는다.

## 5. 처리 완료 후 주문 상태와 창고 보관 선택

- 주문 최종 상태: **`PENDING_PAYMENT`.** 즉시 구매 경로에서 Order 상태를 바꾸는 코드가 없다(`OrderCommandService.java:241-245`에서 설정된 뒤 변경 없음). `Order.updateStatus`는 `OrderStatus.java:24-27`의 전이 표를 따르는데 `PENDING_PAYMENT`에서 `IN_TRANSIT`은 허용되지 않는다(`D/order/entity/Order.java:113-121`). 송장 등록 경로(`D/shipment/service/command/OrderShipmentCommandService.java:260`)는 이 상태에서 실패한다.
- 구매자의 `warehouseStorage` 선택은 **무시된다.** `createInstantOrder`의 `isWarehouseStorage` 파라미터(`OrderCommandService.java:221`)는 본문에서 쓰이지 않는다. 창고 분기는 `sale.isWarehouseStorage()`(`:292`)만 본다. 그러므로 구매자가 "창고 보관"을 골라도:
  - Order에 `WarehouseStorage`가 생성되지 않는다(`createOrderStorage` 호출 없음).
  - Order는 `IN_WAREHOUSE`나 `COMPLETED`로 가지 않고 `PENDING_PAYMENT`에 머문다.
  - 판매자 쪽 창고 보관(Sale 플래그)이 있을 때만 그 `WarehouseStorage`가 `ASSOCIATED_WITH_ORDER`로 바뀐다(`:292-294`).
- 대조: 일반 주문 경로 `processPaymentAndShipment`는 `requestDto.isWarehouseStorage()`를 실제로 보고 창고 분기에서 `COMPLETED`까지 간다(`OrderCommandService.java:163-172`). 즉시 구매만 이 값을 버린다.

## 코드 동작이 이름·주석과 다른 곳

1. 컨트롤러의 `Long orderId`는 OrderBid ID다(`OrderBidCommandController.java:101`).
2. `createInstantOrder`의 `isWarehouseStorage` 인자는 사용되지 않는다(`OrderCommandService.java:221`, `:292`).
3. `validateInstantOrderBidInput`과 `getSaleBidAndValidate`는 검증처럼 보이지만 SaleBid/Sale의 상태를 확인하지 않는다(`OrderBidCommandService.java:154-184`). 같은 판매 입찰을 두 번 즉시 구매할 수 있고, 판매자 본인 구매도 막지 않는다. 동시 요청을 막는 락도 없다.
4. `SaleBidQueryService.findById`는 없을 때 `SaleBidNotFoundException`이 아니라 `IllegalArgumentException`을 던진다(`D/sale/service/query/SaleBidQueryService.java:21-24`). 그래서 `OrderBidCommandService.java:174-176`의 null 검사는 실행되지 않고, 오류는 `ORD102`(`OrderBidCreationFailedException`)로 감싸진다.
5. "결제가 완료되었습니다"라는 알림은 PG 응답이 `"success"`가 아니어도 나간다(3번 참고).
6. `PortOneApiClient`의 `@Retryable`은 `@EnableRetry`가 없어 동작하지 않는다(저장소 전체에 `EnableRetry`와 spring-retry 설정이 없다).
7. `notifyUsersAndUpdateSaleStatus`의 "알림 및 상태 업데이트 실패 시 예외 미발생" 주석대로, Sale을 SOLD로 바꾸는 중 실패해도 결제 자체는 성공으로 남는다(`PaymentCommandService.java:421-425`).

## 확인하지 못한 것

- PortOne이 실제로 `"success"` 또는 다른 `status` 값을 주는지는 이 저장소만으로 알 수 없다.
- 실제 DB 동작(격리 수준, 커밋 순서)과 WebSocket 전달 여부는 실행하지 않고 코드로만 확인했다.
