# 답: 구매자 배송의 운송장 등록 → 배송 완료 처리

확인 범위: 코드 읽기만 수행했다. 실행과 DB 검증은 하지 않았다. Spring Batch의 스킵·재처리 동작은 프레임워크 규칙에 따른 판단이며 해당 부분에 표시했다. 경로는 모두 `src/main/java/com/fream/back/` 기준이다.

---

## 1. 운송장 등록 요청

**API**: `PATCH /shipments/order/{shipmentId}/status`, 본문 `{courier, trackingNumber}`
(`domain/shipment/controller/command/OrderShipmentCommandController.java:20, 33-41`). 이 컨트롤러에는 권한 어노테이션이 없다.
→ 서비스 `OrderShipmentCommandService.updateTrackingInfo` (`domain/shipment/service/command/OrderShipmentCommandService.java:238-303`).

**코드가 의도한 처리 순서**
1. courier, trackingNumber 공백 검사 (`OrderShipmentCommandService.java:243-246`)
2. OrderShipment 조회 후 송장 정보 설정 (`:249-256`). `OrderShipment.updateTrackingInfo`는 상태를 `IN_TRANSIT`으로 직접 대입하며 전이 검사를 하지 않는다 (`domain/shipment/entity/OrderShipment.java:41-45`).
3. Order를 `IN_TRANSIT`으로 변경 (`OrderShipmentCommandService.java:260`)
4. 구매자 알림 "상품이 출발하였습니다" 1건 (`:266-271`)
5. `updateSaleStatusToSold` 호출 (`:276`). Sale이 SOLD로 전이 가능할 때만 판매자 알림 1건 (`:111-138`)
6. 창고 보관 상품이면 창고 상태 갱신 (`:279-286`)
7. OrderBid, SaleBid를 MATCHED → COMPLETED (`:289`, 구현 `:412-440`)

상태 기계와 어긋나는 지점: Order가 `IN_TRANSIT`에 가려면 `SHIPMENT_STARTED`를 거쳐야 하고 (`domain/order/entity/OrderStatus.java:28-29`), 배송도 `SHIPPED`를 거쳐야 한다 (`domain/shipment/entity/ShipmentStatus.java:7, 13`). 코드는 둘 다 건너뛴다.

**결론: 두 주문 모두 끝까지 성공하지 못한다.**

**(a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문**
- 결제·배송 처리 후 Order 상태는 `PREPARING`이다. Kafka 소비자 `processCompleteOrder`가 `PAYMENT_COMPLETED` → `PREPARING`으로 바꾼다 (`domain/order/service/kafka/OrderEventConsumer.java:195, 217`). 동기 경로 `OrderCommandService.java:175-176`도 같은 상태가 된다.
- 실패 지점 1: `:260` `order.updateStatus(IN_TRANSIT)`. `PREPARING`에서 허용되는 전이는 `IN_WAREHOUSE`, `SHIPMENT_STARTED`뿐이다 (`OrderStatus.java:26`). `Order.updateStatus`가 `InvalidOrderStatusException`을 던진다 (`domain/order/entity/Order.java:113-121`).
- `:295-301`의 catch-all이 이를 `ShipmentException(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")`으로 감싸 다시 던진다.
- 실패 지점 2 (잠재): 실패 지점 1을 우회하더라도 `:116` `saleBidQueryService.findByOrderId`에서 막힌다. 일반 구매 입찰에는 SaleBid가 없고, 판매는 `OrderBid.assignSale`로만 연결된다 (`domain/sale/service/command/SaleCommandService.java:79`). `SaleBidQueryService.findByOrderId`는 없으면 `null`이 아니라 `IllegalArgumentException`을 던진다 (`domain/sale/service/query/SaleBidQueryService.java:26-28`).
- **저장되는 것: 없음.** 예외가 RuntimeException으로 빠져나가 `@Transactional`이 롤백한다. 메모리상의 shipment 변경(courier, trackingNumber, IN_TRANSIT)도 DB에 반영되지 않는다. 구매자 알림은 `:266` 이전에 실패하므로 만들어지지 않는다.
- **응답: HTTP 404**, `ErrorResponse`, code `S001`, 고정 메시지 "배송 정보를 찾을 수 없습니다." (`global/exception/GlobalExceptionHandler.java:459-470`, `domain/shipment/exception/ShipmentErrorCode.java:12`). 실제 원인은 로그에만 남는다. 컨트롤러에는 try/catch가 없다 (`OrderShipmentCommandController.java:34-49`). 상태 전이 오류가 "배송 정보 없음"으로 보이는 것도 문제다.

**(b) 즉시 구매로 만들어진 주문**
- `createInstantOrder`가 Order를 `PENDING_PAYMENT`로 만든다 (`domain/order/service/command/OrderCommandService.java:244`). 결제(`PaymentCommandService.processPayment`, `domain/payment/service/command/PaymentCommandService.java:57`)에는 Order 상태를 바꾸는 코드가 없다. 즉시 구매는 Kafka 경로도 타지 않는다.
- `PENDING_PAYMENT`에서 `IN_TRANSIT`은 허용되지 않는다 (`OrderStatus.java:24`). `:260`에서 실패하며, 저장 결과와 응답은 (a)와 같다 (롤백, 404 `S001`).

## 2. 배송 완료 감지

- **누가, 어떻게**: 서버가 주기적으로 CJ 추적 페이지를 조회하는 폴링 방식이다. 택배사의 푸시나 웹훅은 없다.
- **주기**: `global/config/ShipmentBatchScheduler.java:34` `@Scheduled(cron = "0 0 */6 * * *")`, 즉 매일 00·06·12·18시 정각이다. 실행은 `:40` `jobLauncher.run`이고, 예외는 `printStackTrace`만 한다 (`:41-43`). 스케줄링은 `EventStatusScheduler.java:22` 등에서 `@EnableScheduling`으로 활성화되어 있다.
- **대상**: `domain/shipment/config/UpdateShipmentStatusesJobConfig.java:95`의 쿼리 `status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND trackingNumber IS NOT NULL`, 페이지 크기 50 (`:51-52`, `:87-97`).
- **실제로 실행되는 처리 코드**: 스텝 (`:62-82`)은 `new ShipmentItemProcessor(...)`를 쓴다 (`:69-73`). 그 `process()` (`domain/shipment/config/ShipmentItemProcessor.java:57-157`)가 건마다 Playwright 페이지를 열고 (`:72`) 이동하고 (`:83`) `tbody#statusDetail tr`의 마지막 행 5번째 `td`를 읽는다 (`:87-94`, 파싱 `:167-212`, 상태 칸 `:181`).
- **실행되지 않는 비슷한 코드**
  - `UpdateShipmentStatusesJobConfig.shipmentItemProcessor()` (`:104-177`): 빈 정의만 있고 스텝에서 쓰지 않는다.
  - `parseCjLogisticsStatus` (`:186-220`): Jsoup 방식이며 호출처가 없다.
  - `OrderShipmentCommandService.updateShipmentStatuses()` (`:308-391`): 호출처가 없는 죽은 코드다.
  - `CjTrackingPlaywright.getCurrentTrackingStatus` (`global/utils/CjTrackingPlaywright.java:33`): 배치 스텝에서 호출되지 않는다. 단건 조회 API(`OrderShipmentCommandService.java:477`)에서만 쓰인다.
- **택배사 상태 문자열 → 내부 상태** (`ShipmentItemProcessor.java:220-226`): 정확히 `"배송완료"`는 DELIVERED, `"배송출발"`은 OUT_FOR_DELIVERY, 그 밖의 모든 문자열은 IN_TRANSIT이다. 앞뒤 공백은 trim한다 (`:181`).
- **분기** (`:101-126`): 현재 상태와 같으면 아무것도 하지 않는다. DELIVERED면 배송을 DELIVERED로 바꾸고 `completeOrder`와 알림을 호출한다 (`:108-117`). OUT_FOR_DELIVERY면 그 상태로 바꾼다 (`:119-121`). 그 밖에는 IN_TRANSIT으로 바꾼다 (`:123-125`).
- **버그**: 현재 상태가 OUT_FOR_DELIVERY인데 CJ 상태 문자열이 "배송출발"도 "배송완료"도 아니면 IN_TRANSIT 전이를 시도한다. 그러나 OUT_FOR_DELIVERY에서 IN_TRANSIT은 허용되지 않는다 (`ShipmentStatus.java:26`). `OrderShipment.updateStatus`가 `IllegalStateException`을 던지고 (`OrderShipment.java:47-55`), 이것이 ShipmentException으로 감싸여 매 주기 스킵된다 (`ShipmentItemProcessor.java:133-145`).

## 3. 배송 완료 판정 이후 (DELIVERED 분기, `ShipmentItemProcessor.java:108-117`)

**엔티티 상태가 바뀌는 순서**
1. OrderShipment → DELIVERED (`ShipmentItemProcessor.java:113`). 청크 커밋 때 DB에 기록된다 (`UpdateShipmentStatusesJobConfig.java:239-246`).
2. `OrderShipmentCommandService.completeOrder(orderId)` (`OrderShipmentCommandService.java:190-229`)
   - OrderBid를 orderId로 조회 (`:196-197`).
   - Order → COMPLETED (`:204`).
   - `updateSaleStatusToSold` (`:208`): SaleBid 조회 (`:116`). Sale이 SOLD로 전이 가능할 때만 판매자 알림 (`:119-138`). OrderBid 경로는 Sale이 이미 SOLD라 아무것도 하지 않는다 (`:151-175`).
   - 구매자 알림 "[completeOrder] 주문이 완료 처리되었습니다" (`:211-217`).
3. `notificationService.notifyShipmentCompleted(order)` (`ShipmentItemProcessor.java:117` → `domain/notification/service/command/NotificationCommandService.java:219-232`): 구매자 알림 "[배송 완료] …".

**알림**: 구매자가 2건을 받는다 (`OrderShipmentCommandService.java:212`, `NotificationCommandService.java:219-232`). 판매자는 이 경로에서 0건이다. 판매 SOLD 전이와 판매자 알림은 보통 결제 시점에 이미 끝나 있다 (`PaymentCommandService.java:383-428`, SOLD 전이 `:404`, `:419`).

**입찰 상태**: OrderBid와 SaleBid는 바뀌지 않는다. `updateOrderAndSaleBidStatusToCompleted` (`OrderShipmentCommandService.java:412-440`)는 송장 등록 경로 `:289`에서만 호출된다. 배치 경로에서는 MATCHED로 남는다.

## 4. 주문 종류별 차이

**(a) 일반 구매 입찰 실배송 주문: 끝까지 진행되지 않는다.**
- 정상 등록 경로로는 shipment가 IN_TRANSIT이 될 수 없으므로 (1번 참고) 배치 대상이 되지 않는다.
- 다른 경로로 IN_TRANSIT이 된 경우를 가정하면: 단건 조회 API `POST /shipments/order/{id}/check-status`는 Order 상태를 검사하지 않고 shipment를 IN_TRANSIT/OUT_FOR_DELIVERY로 저장한다 (`OrderShipmentCommandService.java:473, 493-497`). 이 상태에서 배송이 완료되면 `completeOrder`의 Order `PREPARING → COMPLETED` 전이가 허용되지 않아 실패한다 (`OrderStatus.java:26`, `OrderShipmentCommandService.java:204`). 예외는 `:221-227`에서 ShipmentException으로 감싸지고, 처리기가 다시 던져 (`ShipmentItemProcessor.java:138-145`) 스킵된다.
- Order가 IN_TRANSIT이었더라도 `:116`에서 SaleBid가 없어 실패한다.
- 저장 결과: 없음. 알림: 0건. 입찰 상태: 변화 없음.

**(b) 즉시 구매 주문: 완료까지 진행된다.**
- Order는 `PENDING_PAYMENT → COMPLETED` 전이가 허용되므로 (`OrderStatus.java:24`) 통과한다.
- OrderBid가 존재하고 (`domain/order/service/command/OrderBidCommandService.java:189-204`), SaleBid가 Order에 연결되어 있으며 (`OrderCommandService.java:279`), Sale은 결제 시점에 이미 SOLD다 (`PaymentCommandService.java:391-405`).
- 따라서 `completeOrder`는 Order를 COMPLETED로 바꾸고, 판매 전이가 없으므로 판매자 알림은 0건이다. 구매자 알림은 2건이다. OrderBid와 SaleBid는 MATCHED로 남는다.
- 다만 (b)도 송장 등록 API로는 IN_TRANSIT에 도달하지 못한다 (1번). 단건 조회 API에서 CJ가 "배송완료"를 반환하면 위와 같이 완료된다 (`OrderShipmentCommandService.java:483-489`).

**차이 요약**: (a)는 Order가 PREPARING이라 COMPLETED 전이에서 막히고, 막히지 않더라도 SaleBid가 없어 실패한다. (b)는 전이와 조회가 모두 통과해 완료되지만, 입찰 상태는 COMPLETED가 되지 않는다.

## 5. 실패 처리

- **건별**: `faultTolerant().skip(Exception.class).skipLimit(50)` (`UpdateShipmentStatusesJobConfig.java:75-77`). 처리기에서 예외가 나면 그 건은 쓰지 않고 스킵한다. 스킵 리스너가 로그를 남긴다 (`:251-287`). 그 건은 이전 상태로 남고, 다음 주기(최대 6시간 뒤)에 다시 시도된다.
- **같은 청크의 나머지 건**: Spring Batch의 fault-tolerant 청크 규칙상 처리 중 예외가 나면 청크를 롤백하고 항목을 하나씩 다시 처리하므로, 정상 건은 개별 트랜잭션으로 커밋된다. 이 부분은 프레임워크 동작에 근거한 판단이며, 저장소 코드만으로는 확인되지 않는다.
- **스킵 한도**: 한 번의 실행에서 스킵이 50건을 넘으면 스텝이 실패하고 그 실행의 남은 건은 처리되지 않는다. 다음 주기까지 기다린다.
- **주의 1**: 영구 실패 건이 매 주기 스킵 한도를 소모한다. 잘못된 운송장 번호는 파싱 실패로 `ShipmentItemProcessor.java:174-177`에서 예외가 나고, (a)처럼 상태 전이가 불가능한 건도 매번 실패한다. 이런 건이 50건을 넘으면 뒤쪽 건 전체가 막힌다.
- **주의 2 (추정)**: 리더는 `ORDER BY` 없는 JPQL을 offset 방식으로 페이징한다 (`UpdateShipmentStatusesJobConfig.java:87-97`). 처리 결과로 상태가 바뀌어 조건에서 빠진 건만큼 다음 페이지의 offset이 밀려서, 같은 실행에서 일부 건이 읽히지 않을 수 있다. 다음 주기에 다시 잡히므로 영구 누락이 아니라 지연이다. 실행으로 검증하지는 않았다.
- 처리기는 브라우저 페이지를 `finally`에서 닫는다 (`ShipmentItemProcessor.java:146-156`).

## 부가: 주석·메서드명과 실제 동작이 다른 곳

- `updateTrackingInfo`의 주석 "배송 상태가 변경되었으므로 주문 상태도 업데이트" (`OrderShipmentCommandService.java:258`): 실제로는 전이 규칙 위반으로 실패한다.
- `completeOrder`는 실패 원인과 무관하게 모든 예외를 `ORDER_NOT_FOUND_FOR_SHIPMENT`로 감싼다 (`:221-227`). 원인 구분이 되지 않는다.
- `updateOrderAndSaleBidStatusToCompleted`는 `private`인데 `@Transactional`이 붙어 있어 프록시를 타지 않는다. 예외는 삼킨다 (`:436-439`).
- `SaleBidQueryService.findByOrderId`는 연결이 없으면 `null`을 기대하는 호출부가 있다 (`PaymentCommandService.java:391-394`, `OrderShipmentCommandService.java:116, 279`). 실제로는 예외를 던진다.
- 단건 조회 API `check-status`는 IN_TRANSIT 상태에서 `updateStatus(IN_TRANSIT)`을 호출한다 (`OrderShipmentCommandService.java:497`). IN_TRANSIT → IN_TRANSIT은 허용되지 않으므로 (`ShipmentStatus.java:16-22`) 항상 실패한다. 아직 배송 중인 건은 이 API로 조회할 수 없고, 컨트롤러는 `S302`의 503을 빈 본문으로 돌려준다 (`OrderShipmentCommandController.java:80-86`, `ShipmentErrorCode.java:30`).
- `OrderCommandService.processPaymentAndShipment`는 OrderBid를 `findById(orderId)`로 조회한다 (`OrderCommandService.java:188`). 주문 ID를 입찰 PK로 쓰는 잘못된 키다. 실사용 경로인 Kafka 소비자는 이 메서드를 호출하지 않는다.
