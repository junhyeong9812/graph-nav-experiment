# 구매자 배송: 운송장 등록부터 배송 완료까지

요약: **현재 코드로는 운송장 등록이 어떤 주문에서도 성공하지 않는다.** 등록 API는 주문을 `IN_TRANSIT`으로 바꾸려 하는데, 그 전이를 허용하는 상태(`SHIPMENT_STARTED`)를 설정하는 코드가 없다. 그래서 배송이 `IN_TRANSIT`이 되지 못하고, 배치의 배송 완료 처리 대상에도 들어가지 않는다. 아래 3·4번의 "성공 경로"는 운송장 등록이 (어떤 방식으로든) 성공해서 배송이 `IN_TRANSIT`이 되었다고 가정한 설계상·실행상 동작이다.

경로 표기: 모든 경로는 저장소 루트 기준이다.
- `OCS`=`src/main/java/com/fream/back/domain/order/service/command/OrderCommandService.java`
- `SVC`=`src/main/java/com/fream/back/domain/shipment/service/command/OrderShipmentCommandService.java`

## 1. 운송장 등록 요청

**API**
- `PATCH /shipments/order/{shipmentId}/status`, 본문 `{courier, trackingNumber}` (`src/main/java/com/fream/back/domain/shipment/controller/command/OrderShipmentCommandController.java:20, 33-34, 41`). 성공 시 200, 빈 본문(`:48`).
- 소유자 검사도 관리자 검사도 없다. shipment 도메인 어디에도 `checkAdminRole`이나 `SecurityUtils` 호출이 없으므로, 인증된 아무 사용자나 호출할 수 있다.

**설계된 처리 순서** (`SVC:239-298`, `updateTrackingInfo`, `@Transactional`)
1. 빈 값 검사 → `TRACKING_INFO_REQUIRED` (`SVC:245`).
2. `OrderShipment`에 택배사·운송장 번호를 쓰고 status를 `IN_TRANSIT`으로 설정 (`SVC:256` → `src/main/java/com/fream/back/domain/shipment/entity/OrderShipment.java:41-45`). 이 메서드는 전이 검사를 하지 않는다.
3. `Order`를 `IN_TRANSIT`으로 전이 (`SVC:260`). 의도는 `PREPARING → IN_TRANSIT`이다.
4. 구매자에게 알림 1건, "상품이 출발하였습니다" (`SVC:266-271`).
5. `updateSaleStatusToSold(orderId)` (`SVC:276`): Sale을 `SOLD`로 바꾸고 판매자에게 알림 (`SVC:112-141`, `:116` SaleBid 조회, `:119` 전이 검사, `:123` 상태 변경, `:133` 알림).
6. 창고 보관 건이면 창고 상태를 SOLD로 (`SVC:279-286`).
7. `updateOrderAndSaleBidStatusToCompleted` (`SVC:289`, 정의 `:413`): OrderBid·SaleBid를 `MATCHED → COMPLETED`로 바꾼다. 이 메서드는 내부에서 모든 예외를 삼키고, 자기 호출이라 `private`의 `@Transactional`도 적용되지 않는다.

**알림 수신자:** 구매자 1건(`:266`). 판매자 알림(`:133`)은 Sale이 아직 `SOLD`가 아닐 때만 생기는데, 결제 시점에 이미 `SOLD`가 되므로 실제로는 생기지 않는다 (아래 참고).

**결제 시점에 이미 일어나는 일** (운송장 등록 전)
- 일반 구매 입찰(a)과 즉시 구매(b) 모두 결제 때 `PaymentCommandService.processPayment` → `notifyUsersAndUpdateSaleStatus`가 호출된다 (`src/main/java/com/fream/back/domain/payment/service/command/PaymentCommandService.java:83, 383`).
- 여기서 Sale을 `SOLD`로 바꾸고(`PCS:404`, `:419`), 구매자 1건("결제가 완료되었습니다", `:438`)과 판매자 1건("구매자가 결제를 완료하였습니다", `:449`)에게 알림을 보낸다.
- 따라서 운송장 등록 때 Sale 전이는 이미 끝나 있어서 no-op이다.

**실패: 일반 구매 입찰 주문(a), 결제·배송 처리 완료 후**
- 결제·배송 처리: `OrderEventConsumer`의 `processCompleteOrder`가 결제(`src/main/java/com/fream/back/domain/order/service/kafka/OrderEventConsumer.java:171`), 배송 생성(`:181`), `PAYMENT_COMPLETED`(`:195`), 창고가 아니면 `PREPARING`(`:216-217`)까지 한 트랜잭션으로 수행한다. 이때 주문 상태는 `PREPARING`이다.
- 실패 지점: `SVC:260` `order.updateStatus(IN_TRANSIT)`. `PREPARING`에서 허용되는 다음 상태는 `IN_WAREHOUSE`, `SHIPMENT_STARTED`뿐이다 (`src/main/java/com/fream/back/domain/order/entity/OrderStatus.java:26`). `IN_TRANSIT`은 없다.
- 전이 검사는 `src/main/java/com/fream/back/domain/order/entity/Order.java:113-119`에서 `InvalidOrderStatusException`을 던진다.
- `SHIPMENT_STARTED`는 `OrderStatus` 맵(`OST:28`) 외에 설정하는 코드가 없다. `IN_TRANSIT`으로 갈 수 있는 상태가 현재 도달 불가다.
- 예외 처리: `SVC:295-301`의 `catch (Exception)`이 `ShipmentException(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생")`으로 감싸 다시 던진다. `GlobalException`은 `RuntimeException`이므로(`src/main/java/com/fream/back/global/exception/GlobalException.java:10`) 트랜잭션은 롤백된다.
- **저장되는 것: 아무것도 없다.** 운송장 번호, 택배사, shipment의 `IN_TRANSIT`, order 변경이 모두 롤백된다. 구매자 알림은 `:266`에 도달하기 전에 실패하므로 생기지 않는다. 결제·주문 생성은 이전 트랜잭션에서 이미 커밋되어 있다.
- **응답:** `GlobalExceptionHandler.handleShipmentException` (`src/main/java/com/fream/back/global/exception/GlobalExceptionHandler.java:459-471`) → HTTP **404**, 본문 `ErrorResponse` (code `S001`, message `"배송 정보를 찾을 수 없습니다."`, status 404, path). 배송 정보는 실제로 존재하므로 메시지가 틀리다. `ShipmentErrorCode.java:12`.
- 설령 `:260`을 통과하더라도 두 번째 실패가 기다린다. `SVC:276` → `updateSaleStatusToSold` → `SVC:116`의 `saleBidQueryService.findByOrderId`는 연결된 SaleBid가 없으면 `IllegalArgumentException`을 던지고(`src/main/java/com/fream/back/domain/sale/service/query/SaleBidQueryService.java:26-28`), 이 예외는 `updateSaleStatusToSold`에서 잡히지 않는다. 일반 구매 입찰 주문에는 SaleBid가 order에 연결되지 않는다. `SaleBid.assignOrder`는 즉시 구매 경로에서만 호출된다 (`OCS:279`, `src/main/java/com/fream/back/domain/sale/service/command/SaleBidCommandService.java:83`).

**실패: 즉시 구매 주문(b)**
- 즉시 구매 흐름 `OCS.createInstantOrder` (`OCS:220`)은 주문을 `PENDING_PAYMENT`로 만들고(`OCS:244`), 결제(`OCS:305`)를 한 뒤, 주문 상태를 바꾸지 않는다. 주문은 계속 `PENDING_PAYMENT`다.
- `PENDING_PAYMENT`에서 허용되는 상태는 `PAYMENT_COMPLETED`, `COMPLETED`, `IN_WAREHOUSE`뿐이다 (`OST:24`). `IN_TRANSIT`은 없으므로 같은 `SVC:260`에서 실패한다.
- 저장되는 것과 응답은 (a)와 같다: 아무것도 저장되지 않고, 404 `S001`.

## 2. 배송 완료 감지

**누가, 언제, 어떻게**
- 사람이 아니라 스케줄러가 한다. `src/main/java/com/fream/back/global/config/ShipmentBatchScheduler.java:34-40`의 `@Scheduled(cron = "0 0 */6 * * *")`로 6시간마다 00·06·12·18시 정각(서버 시간대)에 `updateShipmentStatusesJob`을 실행한다.
- 대상 조회: `src/main/java/com/fream/back/domain/shipment/config/UpdateShipmentStatusesJobConfig.java:87-97`. JPQL `status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND trackingNumber IS NOT NULL`, 페이지 50, **ORDER BY 없음**.
- 청크 크기 50 (`UJC:63-67`).
- 조회: CJ 추적 페이지를 Playwright 헤드리스 브라우저로 열고 `tbody#statusDetail tr`이 나타날 때까지 기다린 뒤 마지막 행의 5번째 `td` 텍스트를 읽는다. `src/main/java/com/fream/back/domain/shipment/config/ShipmentItemProcessor.java:57-94, 181`. URL은 `https://trace.cjlogistics.com/next/tracking.html?wblNo=` + 운송장 번호(`SIP:28, 81`).

**실제로 실행되는 처리 코드와 비슷한 코드 구분**
- 실제 실행: `UJC:69-73`의 `new ShipmentItemProcessor(...)` → `ShipmentItemProcessor.process` (`SIP:57-157`).
- 실행되지 않음 1: `UJC:104-177`의 `@Bean shipmentItemProcessor()`. Step에 연결되지 않는다. 안에 있는 Jsoup 기반 `parseCjLogisticsStatus`(`UJC:186-220`)도 호출되는 곳이 없다.
- 실행되지 않음 2: `SVC:309`의 `updateShipmentStatuses()`. 호출하는 곳이 없다. 이 메서드는 `CjTrackingPlaywright`를 쓴다.
- `CjTrackingPlaywright`(`src/main/java/com/fream/back/global/utils/CjTrackingPlaywright.java:33`)은 수동 확인 API `POST /shipments/order/{id}/check-status`(`SVC:452` `updateAndCheckShipmentStatus`, `:477`에서 호출)에서만 쓰인다. 이 경로도 DELIVERED면 `completeOrder`(`SVC:489`)를 호출한다.
- 브라우저 수명: `BrowserManageStepListener`가 `beforeStep`에서 열고 `afterStep`에서 닫는다 (`src/main/java/com/fream/back/domain/shipment/config/BrowserManageStepListener.java:14-25`).

**택배사 상태 문자열 → 내부 상태** (`SIP:220-226`)
- `"배송완료"` → `DELIVERED`
- `"배송출발"` → `OUT_FOR_DELIVERY`
- 그 밖의 모든 문자열(빈 문자열 제외) → `IN_TRANSIT`. `default` 분기라서 알 수 없는 문구도 `IN_TRANSIT`이 된다.
- 빈 문자열은 `SIP:183-188`에서 `TRACKING_HTML_PARSE_ERROR`로 실패한다.
- 현재 상태와 같으면 아무것도 하지 않는다 (`SIP:101-105`).
- 상태 전이 자체는 `ShipmentStatus.canTransitionTo`가 검사한다 (`src/main/java/com/fream/back/domain/shipment/entity/ShipmentStatus.java`). `OUT_FOR_DELIVERY`에서 `IN_TRANSIT`으로는 갈 수 없다 (`:80-83`).
- 그래서 `OUT_FOR_DELIVERY` 건에서 CJ 문구가 `"배송완료"`도 `"배송출발"`도 아니면 `else` 분기(`SIP:123-125`)의 `updateStatus(IN_TRANSIT)`가 `IllegalStateException`을 던지고, 그 건은 매번 실패한다.

## 3. 배송 완료 판정 이후 (`SIP:108-117`, 성공 가정)

순서:
1. `orderShipment.updateStatus(DELIVERED)` (`SIP:113`). 메모리에서만 바뀌고 쓰기는 청크 끝에 된다. `IN_TRANSIT`과 `OUT_FOR_DELIVERY`에서 `DELIVERED`로 가는 것은 허용된다 (`ShipmentStatus.java:75-76, 82`).
2. `completeOrder(orderId)` (`SIP:116` → `SVC:191`). 이 메서드는 processor 트랜잭션에 참여한다.
   - `SVC:197` OrderBid 조회 (없으면 예외).
   - `SVC:204` `order.updateStatus(COMPLETED)`. 허용되는 시작 상태는 `PENDING_PAYMENT`, `IN_WAREHOUSE`, `IN_TRANSIT`뿐이다 (`OST:24, 27, 29`).
   - `SVC:208` `updateSaleStatusToSold`. Sale은 이미 `SOLD`라서 `SaleStatus.canTransitionTo(SOLD)`가 false(`src/main/java/com/fream/back/domain/sale/entity/SaleStatus.java:23`)이므로 상태도 판매자 알림도 바뀌지 않는다.
   - `SVC:212-216` 구매자 알림 1건 `"[completeOrder] 주문이 완료 처리되었습니다."`.
   - 이 메서드는 `updateOrderAndSaleBidStatusToCompleted`를 호출하지 않는다. 그 호출은 운송장 등록 경로(`SVC:289`)에만 있다.
   - 어떤 예외든 `SVC:221-226`에서 `ShipmentException(ORDER_NOT_FOUND_FOR_SHIPMENT)`으로 바뀐다.
3. `notifyShipmentCompleted(order)` (`SIP:117` → `src/main/java/com/fream/back/domain/notification/service/command/NotificationCommandService.java:219-234`). 구매자 알림 1건 `"[배송 완료] ..."`(`NCS:224-229`).
4. 청크 writer(`UJC:239-246`)가 `OrderShipment`를 `DELIVERED`로 저장하고 커밋한다.

**결과**
- Shipment: `DELIVERED`.
- Order: `COMPLETED`.
- Sale: 변화 없음. 결제 때 이미 `SOLD`.
- OrderBid, SaleBid: 변화 없음. 배치는 이 둘을 `COMPLETED`로 바꾸지 않는다. 결제·매칭 때의 `MATCHED`로 남는다. `COMPLETED`는 운송장 등록 경로에서만 설정되는데, 그 경로는 성공하지 않는다.
- 알림: **구매자 2건**(`SVC:212-216`의 completeOrder 알림 + `NCS:224-229`의 배송 완료 알림), **판매자 0건**.
- 각 알림은 DB 저장 직후 WebSocket 실시간 전송을 한다 (`NCS:57, 303-`). 즉 커밋 전에 푸시가 나간다.

## 4. 주문 종류별 차이

| | (a) 일반 구매 입찰 (`PREPARING`) | (b) 즉시 구매 (`PENDING_PAYMENT`) |
|---|---|---|
| 정상 경로(운송장 등록)로 `IN_TRANSIT`에 도달 | 불가 (`SVC:260`, `OST:26`) | 불가 (`SVC:260`, `OST:24`) |
| 배치 대상(`IN_TRANSIT`) 진입 | 등록이 성공하지 않으므로 정상 경로로는 불가 | 같은 이유로 불가 |
| 가정: 배치에서 DELIVERED 판정 시 `completeOrder` 주문 단계 | `SVC:204`에서 `PREPARING → COMPLETED` 불가 → 실패 | `PENDING_PAYMENT → COMPLETED` 허용 → 통과 |
| 가정: `updateSaleStatusToSold` 단계 | (주문이 `IN_TRANSIT`이었다고 가정해도) `SVC:116` SaleBid 없음 → `IllegalArgumentException` → 실패 | SaleBid 있음, Sale 이미 `SOLD` → 상태 변화 없음, 판매자 알림 없음 |
| 끝까지 진행 | **아니오** (두 지점 모두에서 실패) | **예** (구매자 알림 2건) |
| 결과 저장 | Shipment `IN_TRANSIT` 유지, Order `PREPARING` 유지, 알림 없음 (청크 롤백, 해당 건 skip) | Shipment `DELIVERED`, Order `COMPLETED`, Sale `SOLD`(변화 없음), OrderBid·SaleBid `MATCHED` 유지 |

(b)는 결제 시점에 주문 상태가 `PENDING_PAYMENT`에 머문다 (`OCS:244`, 결제 후 갱신 없음). 그래서 배송 완료 처리에서 `COMPLETED`로 바로 갈 수 있지만, 그 이전인 운송장 등록 단계가 막혀 있어서 이 경로는 실제로 시작되지 않는다.

## 5. 실패 처리 (주기 처리 중 한 건 실패)

설정: `UJC:75-77`의 `faultTolerant().skip(Exception.class).skipLimit(50)`. 로그용 `SkipListener`는 `UJC:252-266`.

한 건이 실패하면(예: (a)의 `completeOrder` 실패, CJ 조회 실패, 파싱 실패, `OUT_FOR_DELIVERY`에서의 잘못된 전이):
- **그 건**: processor 예외 → 청크 트랜잭션 롤백 → 그 건은 skip되어 쓰기가 없다. 그 건의 DB 상태는 실패 전 그대로(`IN_TRANSIT`/`OUT_FOR_DELIVERY`)다. SkipListener는 로그만 남긴다. 다음 6시간 실행에서 다시 대상이 된다.
- **같은 청크의 나머지 건**: Spring Batch의 fault-tolerant 청크 처리는 롤백 후 건별로 다시 처리한다(프레임워크 동작, 이 저장소 코드 밖). 정상 건은 개별로 저장된다.
  - 단, 롤백되지 않는 부작용은 중복될 수 있다. 실패 전에 DELIVERED로 처리된 건의 알림 푸시(`NCS:57`는 커밋 전 즉시 전송)와 브라우저 조회는 재처리 때 다시 일어난다. 알림 행은 롤백되어 DB에는 한 번만 남지만, 실시간 푸시는 두 번 갈 수 있다.
- **skip 누적 50건 초과**: `SkipLimitExceededException`으로 step이 실패하고 job이 실패한다. 남은 건은 이번 실행에서 처리되지 않고 다음 주기에 다시 시도된다. `BrowserManageStepListener`가 `afterStep`에서 브라우저를 닫는다.
- **페이징 문제**: 리더에 ORDER BY가 없고 페이지마다 쿼리를 다시 실행한다. 처리 중 DELIVERED로 커밋된 건이 필터에서 빠지면 다음 페이지 offset이 밀려 같은 실행에서 일부 건을 건너뛸 수 있다. 현재 코드에서 DELIVERED가 커밋되는 것은 (b)형 건이 가정된 경우뿐이다.
- **상태 전이 실패가 반복되는 건**: `OUT_FOR_DELIVERY`인데 CJ 문구가 `"배송완료"`/`"배송출발"`이 아니면 매 실행마다 `IllegalStateException` → skip이다. skip 카운트가 쌓여 50을 넘기면 다른 정상 건까지 같은 실행에서 멈춘다.

## 코드와 이름·주석이 다른 부분 (실제 동작 기준)

- `updateTrackingInfo`(`SVC:239`)는 "배송 상태 변경과 주문 상태 업데이트"처럼 읽히지만, 실제로는 `SVC:260`에서 항상 실패하므로 아무 상태도 저장되지 않는다.
- `updateSaleStatusToSold`(`SVC:112`)의 "주문 완료에 따라 SOLD" 주석과 달리, 결제 시점에 이미 SOLD가 되어 있어서 이 메서드는 사실상 no-op이다 (`PCS:404, 419`).
- `ShipmentItemProcessor`의 `default -> IN_TRANSIT` 매핑(`SIP:224`)은 알 수 없는 문구를 모두 "배송 중"으로 바꾼다.
- `updateOrderAndSaleBidStatusToCompleted`(`SVC:413`)는 `@Transactional`이 붙어 있지만 `private` + 자기 호출이라 프록시를 타지 않는다. 또 예외를 삼키므로 실패해도 흔적이 없다.
- `UJC:104-177`의 `@Bean shipmentItemProcessor()`와 `parseCjLogisticsStatus`는 "배치 처리"처럼 보이지만 Step에 연결되지 않는다.
- `updateShipmentStatuses()`(`SVC:309`)는 배치 대체 버전처럼 보이지만 호출처가 없다.

## 기타 확인 사항 (질문 범위 밖, 근거 있음)

- 권한: `domain/shipment` 컨트롤러 어디에도 관리자·소유자 검사가 없다. 인증만 되면 누구나 운송장을 바꾸거나 `check-status`를 호출할 수 있다.
- 빈 이름 충돌 가능성(정적 판단, 실행으로 확인하지 않음): `PlaywrightBrowserManager`는 `@Component`(`src/main/java/com/fream/back/global/utils/PlaywrightBrowserManager.java:18-19`)이고, `UJC:292-296`에도 같은 이름 `playwrightBrowserManager`의 `@Bean`이 있다. yml에 bean overriding 허용 설정이 보이지 않으므로(`src/main/resources/application*.yml` 검색 결과 없음) 기동 시 `BeanDefinitionOverrideException`이 날 가능성이 높다. 기동 시험으로 확인하지는 않았다.

## 확인하지 못한 것

- 실제 CJ 추적 페이지의 문구(`"배송완료"`, `"배송출발"`)와 DOM 구조는 외부 사이트라 코드로 확인할 수 없다.
- 실행이나 테스트는 하지 않았다. 위 동작은 코드 읽기로 추적한 결과다.
- 청크 롤백 후 건별 재처리 동작은 Spring Batch의 일반 동작을 근거로 한 것이다.
