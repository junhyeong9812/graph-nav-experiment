# 즉시 구매는 어떻게 처리되나

요약: 즉시 구매는 `POST /order-bids/instant` 한 번의 HTTP 요청 안에서 **동기적으로**, 하나의 DB 트랜잭션으로 처리된다. Kafka는 이 경로에 없다. 결제 수단과 무관하게 결제 API가 실패가 아니라고 응답하면 주문은 완료된 것으로 처리되며, 주문 상태(`Order.status`)는 끝까지 `PENDING_PAYMENT`로 남는다. 아래 근거의 경로는 모두 `src/main/java/com/fream/back/domain/` 기준이다.

---

## 1. 요청 진입점과 처리 단계

- **API**: `POST /order-bids/instant` → `order/controller/command/OrderBidCommandController.java:89-90` (`createInstantOrderBid`).
- **요청 DTO**: `order/dto/InstantOrderRequestDto.java:143-152` — `saleBidId`, `addressId`, `warehouseStorage`, `paymentRequest`.
- **처리 흐름** (전부 동기, HTTP 스레드 안에서 실행)
  1. 컨트롤러가 로그인 이메일을 꺼내고 결제 요청에 구매자 이메일을 넣는다, `orderId`는 null로 둔다 (`OrderBidCommandController.java:92-98`, `119-123`).
  2. `OrderBidCommandService.createInstantOrderBid` 진입, `@Transactional` (`order/service/command/OrderBidCommandService.java:118-120`).
  3. 입력 검증 (`:154-166`), 구매자 조회 (`:126`), 판매 입찰 조회 (`:129`, `:172-184`).
  4. `OrderCommandService.createInstantOrder`로 주문 생성 + 배송지 + 판매 입찰 매칭 + 결제 (`order/service/command/OrderCommandService.java:220-311`, 결제 호출은 `:305`).
  5. `OrderBid` 생성·저장 (`OrderBidCommandService.java:142`, `:189-206`).
  6. 컨트롤러가 **`OrderBid`의 ID**를 응답 (`OrderBidCommandController.java:101-109`).
- **반환 ID는 `OrderBid`의 ID다.** 컨트롤러는 `createInstantOrderBid(...).getId()`를 `orderId`라는 변수에 담아 `ResponseDto.success(orderId, ...)`로 보낸다 (`OrderBidCommandController.java:101-109`). Javadoc(`:82`)과 변수명은 "주문 ID"라고 하지만 실제 값은 주문 입찰 ID다. `Order` ID는 응답에 없다.

## 2. 생성되는 엔티티와 상태 변화 순서

모두 한 트랜잭션 안이고, 아래 번호 순서대로 실행된다. 각 단계 직후의 상태 값을 적었다.

| 단계 | 동작 | 근거 | 직후 상태 |
|---|---|---|---|
| ① | `Order` 생성·저장 | `OrderCommandService.java:241-247` | `Order.status = PENDING_PAYMENT`, `totalAmount = saleBid.bidPrice` |
| ② | `Order.id`를 결제 요청에 설정 | `OrderCommandService.java:250` | 결제 요청의 `orderId` 채워짐 |
| ③ | `OrderItem` 생성·추가 | `OrderCommandService.java:255-256` | `OrderItem` 1개 |
| ④ | `OrderShipment` 생성 (배송지 스냅샷) | `OrderCommandService.java:238`, `:264-271` | 주소 조회는 `addressId`로 하고 소유자는 이메일로 검증 |
| ⑤ | `SaleBid`에 `Order` 연결, 상태 변경 후 flush | `OrderCommandService.java:279-283`, `SaleBid.java:58-61` | `SaleBid.status = MATCHED` |
| ⑥ | `Sale`에 창고 보관이 있으면 `WarehouseStorage` 상태 변경 | `OrderCommandService.java:290-293` | `WarehouseStorage.status = ASSOCIATED_WITH_ORDER` (아래 5번 참고) |
| ⑦ | 결제 처리 → `Payment` 생성 (`Payment.order`만 설정) | `OrderCommandService.java:305`, `PaymentCommandService.java:57-107` | `Payment.status`는 결제 수단별로 다름 (3번) |
| ⑧ | 결제 성공 후 알림 저장 + `Sale` 상태 변경 | `PaymentCommandService.java:83`, `:391-404` | `Sale.status = SOLD` |
| ⑨ | `OrderBid` 생성·저장 | `OrderBidCommandService.java:189-206` | `OrderBid.status = MATCHED`, `isInstantPurchase = true`, `order`·`sale` 연결 |
| ⑩ | 커밋 후 응답 | `OrderBidCommandController.java:109` | `Order.status`는 여전히 `PENDING_PAYMENT` |

주의할 점:
- **`Order` 상태는 한 번도 바뀌지 않는다.** `updateStatus`를 호출하는 곳이 이 경로에 없다 (`OrderCommandService.java:220-311` 전체). `PENDING_PAYMENT → PAYMENT_COMPLETED` 전이 규칙은 `order/entity/OrderStatus.java`에 있지만 즉시 구매는 사용하지 않는다.
- **`Order.payment`는 설정되지 않는다.** `order.assignPayment(...)`는 일반 주문 경로(`OrderCommandService.java:139-140`)에만 있다. 즉시 구매에서는 `Payment` 쪽에만 `order`가 연결된다 (`payment/entity/Payment.java:47-50`).
- **`OrderBid`는 가장 마지막에 만들어진다.** 따라서 결제 알림을 만드는 시점에는 `order.getOrderBid()`가 null이고, `PaymentCommandService.java:391`의 `findByOrderId` 분기로 `SaleBid`를 찾는다.
- **판매 입찰 상태 검사가 없다.** `getSaleBidAndValidate`는 null과 `sale` 연결만 본다 (`OrderBidCommandService.java:172-184`). `SaleBid`나 `Sale`이 이미 `MATCHED`/`SOLD`여도 막지 않는다. 락도 보이지 않는다.

## 3. 결제 수단별 결과와 전체 성공 여부

결제 수단은 `requestDto.getResolvedPaymentType()`로 고른다 (`PaymentCommandService.java:67-80`).

**공통**
- 결제 검증은 주문 ID 일치(`:131-134`), 이메일 일치(`:136-139`), 금액 `> 0`(`:142-145`)만 한다.
- **요청에 들어온 `paidAmount`를 주문 금액(`Order.totalAmount`, 즉 판매 입찰 가격)과 비교하지 않는다.** `totalAmount`는 `OrderCommandService.java:243`에서 입찰 가격으로 정해지지만 결제 쪽 코드에서는 읽지 않는다.

**카드 (`CARD`)** — `PaymentCommandService.java:157-225`
- 저장된 결제 정보로 PortOne 카드 결제를 호출하고 요청 금액은 **클라이언트가 보낸 `paidAmount`** 다 (`:179`).
- 응답의 `status`가 정확히 `"success"`일 때만 `PAID`이고, 그 밖의 경우 `PENDING`으로 저장되며 **예외가 나지 않는다** (`:203-206`, `:208`). 이후 알림·`SOLD` 처리가 그대로 진행되어 성공 응답이 나간다. PortOne 응답 스펙은 이 저장소만으로 확인할 수 없다.
- **대행사가 실패로 응답한 경우** (HTTP 상태가 200이 아니거나 `code != 0`): `PortOneApiClient.java:274`에서 `PaymentProcessingException`을 던진다.
  - `PaymentCommandService.java:180-181`, `:218-219`, `:89-94`에서 그대로 전파된다.
  - `OrderCommandService.java:306-309`에서 `OrderPaymentProcessingFailedException`으로 감싼다.
  - `OrderBidCommandService.java:145-147`, `:213-215`에서 `OrderException`이라 그대로 다시 던진다.
  - `GlobalException`이 `RuntimeException`이라 트랜잭션이 롤백된다 (`global/exception/GlobalException.java:10`).
  - 결과: `Order`, `OrderItem`, `OrderShipment`, `SaleBid` 매칭, `Sale` `SOLD`, 알림, 창고 상태가 모두 되돌아가고, 카드 결제 기록도 저장되지 않는다. 요청은 실패한다.

**계좌이체 (`ACCOUNT`)** — `PaymentCommandService.java:236-279`
- 은행명만 검증한다 (`:243-248`). PG 호출은 없다.
- `Payment`는 `PENDING`으로 저장된다 (`:260`, `:262`).
- 예외가 없으므로 알림과 `SOLD` 처리까지 진행되고 **성공 응답**이 나간다. 이 경로에는 입금 확인 로직이 없다. 최종 `PAID` 전이도 여기서는 일어나지 않는다.

**일반 결제 (`GENERAL`)** — `PaymentCommandService.java:290-333`
- `impUid`가 비어 있지 않은지만 확인한다 (`:297-300`).
- **PortOne에 조회·검증하지 않는다.** 클라이언트가 보낸 `impUid`, `paidAmount`를 그대로 믿고 바로 `PAID`로 저장한다 (`:313-314`, `:316`).
- 성공 응답으로 끝난다.

**즉시 구매가 "끝까지 성공"하는 경우**: 검증을 통과하고 `OrderBid` 저장까지 끝나야 하며, 결제 수단이 `GENERAL`이거나 카드가 `status == "success"`일 때 `Payment`가 `PAID`가 된다. 계좌이체는 `PENDING`으로 끝난다. 어느 경우든 `Order.status`는 `PENDING_PAYMENT`다.

**결제 후 DB 단계가 실패하는 경우 (주의)**: 결제는 `OrderBid` 생성(`OrderBidCommandService.java:142`)보다 먼저 실행된다. 카드 결제가 PortOne에서 이미 승인된 뒤 `OrderBid` 저장 등에서 예외가 나면 DB는 롤백되지만 **카드 승인은 취소되지 않는다.** 이 경로에는 보상 로직이 없다. `PaymentCommandService.java:341`의 `handleRefundIfNecessary`는 호출되는 곳이 없다 (`grep` 결과 정의만 있음).

## 4. 알림 수신자와 전달 방식

- **수신자 2명**: 구매자와 판매자 (`PaymentCommandService.java:434-460`).
  - 구매자 (`:438`): "결제가 완료되었습니다. 주문 ID: ..."
  - 판매자 (`:449`): "구매자가 결제를 완료하였습니다. 판매 ID: ..."
  - 둘 다 `NotificationCategory.SHOPPING`, `NotificationType.BID`.
- **언제**: `processPayment`가 끝난 직후, 결제 수단과 상관없이 호출된다 (`PaymentCommandService.java:83`). 따라서 `PENDING`(계좌, 카드 비성공)에도 "결제가 완료되었습니다"가 나간다.
- **방식**: 동기 처리다.
  - DB 저장은 같은 트랜잭션 안에서 이뤄진다 (`NotificationCommandService.java:44-53`).
  - 실시간 전송은 `NotificationCommandService.java:57` → `sendRealTimeNotification` (`:303-`)에서 하며, Redis에 `WebSocket:User:{email}` 키가 있을 때만 WebSocket으로 보낸다 (`:37`, `:307-313`).
  - WebSocket 푸시는 커밋 전에 나가므로, 이후 트랜잭션이 롤백되면 DB에서는 알림이 사라지는데 사용자 화면에는 이미 보인 상태가 될 수 있다.
  - 알림 실패는 `sendNotifications`(`PaymentCommandService.java:459`)와 `notifyUsersAndUpdateSaleStatus`(`:423`)의 catch에서 삼켜지므로 주문 실패로 이어지지 않는다.
- **Kafka 경로 아님**: 즉시 구매 경로에는 Kafka producer 호출이 없다. Kafka를 쓰는 주문 처리는 `OrderCommandController.processPaymentAndShipment`가 `202 ACCEPTED`를 돌려주는 별도 경로이며 (`order/controller/command/OrderCommandController.java:43-68`), 즉시 구매와는 다른 경로다.

## 5. 처리 완료 후 주문의 최종 상태, 창고 보관 선택 시

**성공 시 최종 상태**

| 엔티티 | 최종 상태 | 근거 |
|---|---|---|
| `Order` | `PENDING_PAYMENT` (전이 없음) | `OrderCommandService.java:244` |
| `Payment` | `GENERAL`=`PAID`, `CARD`=`PAID` 또는 `PENDING`, `ACCOUNT`=`PENDING` | `PaymentCommandService.java:203-206`, `:260`, `:314` |
| `OrderBid` | `MATCHED`, `isInstantPurchase=true` | `OrderBidCommandService.java:196`, `:205` |
| `SaleBid` | `MATCHED`, `order` 연결 | `OrderCommandService.java:280`, `SaleBid.java:58-61` |
| `Sale` | `SOLD` | `PaymentCommandService.java:404` |
| `OrderShipment` | 생성됨 (배송지 스냅샷) | `OrderCommandService.java:264-271` |

**창고 보관 선택(`warehouseStorage = true`) 시**
- **구매자의 선택은 아무 효과가 없다.** `createInstantOrder`의 `isWarehouseStorage` 파라미터는 메서드 본문에서 쓰이지 않는다 (`OrderCommandService.java:221`). 컨트롤러와 서비스가 값을 넘기기만 한다 (`OrderBidCommandController.java:105`, `OrderBidCommandService.java:120`, `:137`).
- 실제 분기는 **판매자가 등록한 `Sale.isWarehouseStorage`** 로만 한다 (`OrderCommandService.java:292`). 값이 true면 기존 `WarehouseStorage`를 찾아 `ASSOCIATED_WITH_ORDER`로 바꾼다 (`:293`, `WarehouseStorageCommandService.java:117-` 의 `findBySale` 호출 `:127`). 해당 보관 기록이 없으면 예외가 나고 전체가 롤백된다.
- 일반 주문 흐름과 비교하면 차이가 크다. 일반 흐름은 `WarehouseStorage`를 새로 만들고 `Order`를 `IN_WAREHOUSE`를 거쳐 `COMPLETED`로 보낸다 (`OrderCommandService.java:161-172`). 즉시 구매는 `Order`에 `WarehouseStorage`를 연결하지 않고 `Order` 상태도 바꾸지 않는다.

## 주석·메서드 이름과 실제 동작이 다른 곳

1. **반환 ID**: 컨트롤러 Javadoc과 변수명은 "주문 ID"인데 실제 값은 `OrderBid` ID다 (`OrderBidCommandController.java:82`, `:101-109`).
2. **"즉시 구매는 바로 매칭 상태"** (`OrderBidCommandService.java:196`): `OrderBid`만 `MATCHED`이고 `Order`는 `PENDING_PAYMENT`다. 응답 메시지 "즉시 구매가 성공적으로 처리되었습니다" (`OrderBidCommandController.java:109`)도 `Order`가 완료되었다는 뜻이 아니다.
3. **"셀러 정보 추가"** (`OrderBidCommandService.java:198`): 실제로는 `Sale`을 넣는다.
4. **`isWarehouseStorage` 파라미터**: 세 계층 모두 받지만 `OrderCommandService.createInstantOrder`에서는 쓰지 않는다 (`:221`). 창고 여부는 `Sale` 플래그로 결정된다 (`:292`).
5. **`@throws SaleBidNotFoundException`** (`OrderBidCommandService.java:115`): 실제로는 `sale/service/query/SaleBidQueryService.java:21-24`의 `findById`가 `IllegalArgumentException`을 던진다. 이것이 `OrderBidCreationFailedException`으로 감싸진다 (`OrderBidCommandService.java:212-217`). 그래서 `OrderBidCommandService.java:174-176`의 null 검사는 실행되지 않는다.
6. **"결제 처리" (`processPayment`)**: 이름과 달리 알림 전송과 `Sale` 상태 변경까지 한다 (`PaymentCommandService.java:83`, `:391-404`). 그래서 결제 수단 호출 뒤에 `OrderBid`가 만들어지기 전에 알림이 나간다.
7. **카드 `status` 검사**: `"success"`가 아니면 `PENDING`으로 저장하면서도 예외 없이 성공 응답을 준다 (`PaymentCommandService.java:203-206`). 실패로 보고 응답하는 것과 다르다.
8. **`handleRefundIfNecessary`** (`PaymentCommandService.java:341`): 환불 보상 로직으로 보이지만 호출되지 않는다.

## 이 경로에서 보이는 위험 (질문 밖이지만 근거 있음)

- 결제 금액 무결성: 카드·일반 결제 모두 클라이언트 `paidAmount`를 주문 금액과 대조하지 않는다 (`PaymentCommandService.java:142-145`, `:179`, `:193`). 결제 금액을 낮춰도 검증에 걸리지 않는다.
- 일반 결제 위조 가능성: `impUid`를 PortOne에 확인하지 않고 바로 `PAID`로 저장한다 (`:297-314`).
- 중복 구매: 판매 입찰·판매의 상태를 검사하지 않고 락도 보이지 않는다 (`OrderBidCommandService.java:172-184`). 동일 판매 입찰이 두 번 구매되는지는 이 코드만으로는 확인할 수 없고, 확인되지 않았다는 점만 기록한다.
- 보상 없음: 카드 승인 후 DB 단계에서 실패하면 승인 취소가 없다 (위 3번).
