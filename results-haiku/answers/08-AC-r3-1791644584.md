# 구매자 배송: 운송장 등록부터 배송 완료까지

## 요약

- 운송장 등록 API(`PATCH /shipments/order/{shipmentId}/status`)는 (a) 실배송 일반 구매 입찰 주문, (b) 즉시 구매 주문 모두에서 **실패**한다. 주문 상태 전이 규칙에 막혀 `IN_TRANSIT`으로 바뀌지 못하고, 요청 전체가 롤백된다.
- 그래서 배송 상태 조회 배치(6시간 주기)가 대상으로 삼는 `IN_TRANSIT` 배송이 정상 경로로는 생기지 않는다. 배치 경로의 "배송 완료" 처리는 코드상 존재하지만 운영 흐름에서는 도달하지 않는다.
- 배치 경로가 실제로 도달하더라도 입찰(OrderBid/SaleBid)은 `COMPLETED`로 바뀌지 않고, 구매자는 알림을 2건 받는다.

## 1. 운송장 등록 요청

### 1-1. 들어오는 API

- `PATCH /shipments/order/{shipmentId}/status`, body는 `courier`, `trackingNumber`
  - `src/main/java/com/fream/back/domain/shipment/controller/command/OrderShipmentCommandController.java:20` (base path `/shipments/order`)
  - `src/main/java/com/fream/back/domain/shipment/controller/command/OrderShipmentCommandController.java:33-34` (PATCH 매핑)
  - `src/main/java/com/fream/back/domain/shipment/controller/command/OrderShipmentCommandController.java:41-45` (서비스 호출, 이 메서드에는 try/catch가 없음)
- 같은 목적의 우회 경로로 `POST /shipments/order/{shipmentId}/check-status`, `.../check-status-string`이 있다. 이 경로는 운송장을 기록한 뒤 CJ 조회 결과로 상태를 정한다 (`OrderShipmentCommandController.java:58-94`, `:103-138`).

### 1-2. 코드가 의도한 상태 변화와 알림 (성공 경로 기준, 실행 순서)

`OrderShipmentCommandService.updateTrackingInfo` (`src/main/java/com/fream/back/domain/shipment/service/command/OrderShipmentCommandService.java:238-303`)

1. 입력 공백 검사 (`:243-246`)
2. `OrderShipment`: `courier`, `trackingNumber` 저장, `status`를 `PENDING` → `IN_TRANSIT`으로 직접 대입. 전이 규칙 검사를 거치지 않는다 (`src/main/java/com/fream/back/domain/shipment/entity/OrderShipment.java:41-45`, 생성 시 `PENDING`은 `OrderShipmentCommandService.java:67`)
3. `Order`: `IN_TRANSIT`으로 변경 (`OrderShipmentCommandService.java:260`)
4. 구매자 알림 1건: "상품이 출발하였습니다" (`:266-271`)
5. `updateSaleStatusToSold(orderId)` 호출 → `Sale`을 `SOLD`로, 판매자 알림 1건 (`:276`, 본체 `:112-183`, 판매자 알림 `:133-138`)
6. 창고 보관 상품이면 창고 상태 갱신 (`:279-286`)
7. `OrderBid`, `SaleBid`를 `MATCHED` → `COMPLETED` (`:289`, 본체 `:413-440`)

주의: 5번의 `updateSaleStatusToSold`는 첫 줄에서 `SaleBid`를 조회하는데, 없으면 `IllegalArgumentException`을 던진다 (`OrderShipmentCommandService.java:116`, `src/main/java/com/fream/back/domain/sale/service/query/SaleBidQueryService.java:26-29`). `SaleBid`가 없는 주문은 주문 상태 문제를 고쳐도 여기서 실패한다.

### 1-3. (a) 실배송 일반 구매 입찰 주문: 끝까지 성공하지 않는다

결제·배송 처리 후 상태 (Kafka 경로):

- 결제·배송 처리 요청은 `POST /orders/{orderId}/process-payment-shipment`가 Kafka에 발행하고 바로 응답한다 (`src/main/java/com/fream/back/domain/order/controller/command/OrderCommandController.java:42-54`, `src/main/java/com/fream/back/domain/order/service/kafka/OrderEventProducer.java:34-43`).
- 컨슈머 `processCompleteOrder`가 결제 → 배송 생성 → `PAYMENT_COMPLETED` → `PREPARING` 순서로 처리하고 저장한다 (`src/main/java/com/fream/back/domain/order/service/kafka/OrderEventConsumer.java:166-230`, 상태 전이 `:195`, `:216-218`).
- 실배송이므로 주문은 `PREPARING`에 머문다. `OrderShipment`는 `PENDING`으로 만들어진다 (`OrderEventConsumer.java:181-188`).

운송장 등록 시 실패 지점:

- `shipment.updateTrackingInfo`가 메모리에서 `IN_TRANSIT`을 설정한다 (`OrderShipmentCommandService.java:256`).
- `order.updateStatus(IN_TRANSIT)`에서 실패한다 (`OrderShipmentCommandService.java:260`). `PREPARING`에서 허용되는 다음 상태는 `IN_WAREHOUSE`, `SHIPMENT_STARTED`뿐이다 (`src/main/java/com/fream/back/domain/order/entity/OrderStatus.java:26`). `IN_TRANSIT`으로는 바로 갈 수 없다. 전이 검사는 `src/main/java/com/fream/back/domain/order/entity/Order.java:113-118`에서 `InvalidOrderStatusException`을 던진다.
- 예외는 `updateTrackingInfo`의 `catch (Exception e)`로 들어가 `ShipmentException(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: 상태 전환이 허용되지 않습니다: PREPARING -> IN_TRANSIT")`로 감싸진다 (`OrderShipmentCommandService.java:295-301`).
- 메서드가 `@Transactional`이고 `RuntimeException`이므로 롤백된다. `ShipmentException`은 `RuntimeException` 하위다 (`src/main/java/com/fream/back/global/exception/GlobalException.java:10`, `src/main/java/com/fream/back/domain/shipment/exception/ShipmentException.java:9`).

결과:

- **저장되는 것**: 이 요청으로는 아무것도 저장되지 않는다. 배송의 `courier`, `trackingNumber`, `IN_TRANSIT`과 주문의 `IN_TRANSIT`, 알림, `SOLD`, `COMPLETED` 변경이 모두 롤백된다. 결제·배송 처리 결과(결제, 주문 `PREPARING`, 배송 `PENDING`)는 그대로 남는다.
- **알림**: 발송되지 않는다 (`:266`은 도달하지 않음).
- **응답**: 컨트롤러에 catch가 없으므로 `GlobalExceptionHandler.handleShipmentException`이 처리한다 (`src/main/java/com/fream/back/global/exception/GlobalExceptionHandler.java:459-473`). 에러 코드가 `SHIPMENT_NOT_FOUND`(`src/main/java/com/fream/back/domain/shipment/exception/ShipmentErrorCode.java:12`)이므로 **HTTP 404, 코드 S001, 메시지 "배송 정보를 찾을 수 없습니다."**가 응답된다. 실제 원인 메시지는 응답 본문에 없고 로그에만 남는다. 배송 정보는 존재하므로 이 응답은 오해를 부른다.

### 1-4. (b) 즉시 구매 주문: 역시 실패하며, 이유가 다르다

- 생성: `createInstantOrder`가 주문을 `PENDING_PAYMENT`로 만들고 배송을 `PENDING`으로 만든다 (`src/main/java/com/fream/back/domain/order/service/command/OrderCommandService.java:241-245`, `:264-271`). 이후 `processPayment`가 있지만 주문 상태를 바꾸지 않는다 (`:305`, `src/main/java/com/fream/back/domain/payment/service/command/PaymentCommandService.java:57-83`). 즉 `PAYMENT_COMPLETED`, `PREPARING`을 거치지 않는다.
- 운송장 등록: `PENDING_PAYMENT`에서 `IN_TRANSIT`은 허용되지 않는다 (`src/main/java/com/fream/back/domain/order/entity/OrderStatus.java:24`, 허용 집합은 `PAYMENT_COMPLETED`, `COMPLETED`, `IN_WAREHOUSE`). 따라서 1-3과 같은 경로로 롤백되고 같은 404 응답이 나온다 (`OrderShipmentCommandService.java:260`, `:295-301`).
- 결과: 저장되는 것은 결제 기록, `PENDING_PAYMENT` 주문, `PENDING` 배송, 결제 시점의 `Sale` `SOLD` 전이와 알림(`PaymentCommandService.java:383-425`, 판매 상태 `:404`)이다. 입찰 생성 시 `OrderBid`는 `MATCHED`로 만들어진다 (`src/main/java/com/fream/back/domain/order/service/command/OrderBidCommandService.java:189-207`, 상태 `:196`).

## 2. 배송 완료 감지

### 2-1. 누가, 언제, 어떻게

- 외부 콜백이나 사람이 감지하지 않는다. 서버 주기 실행이 CJ 대한통운 추적 페이지를 조회한다.
- 주기: `@Scheduled(cron = "0 0 */6 * * *")`, 즉 매일 00·06·12·18시 정각 (`src/main/java/com/fream/back/global/config/ShipmentBatchScheduler.java:34`). 실행 시 `jobLauncher.run(updateShipmentStatusesJob, ...)`를 호출하고, 예외는 `printStackTrace`만 한다 (`ShipmentBatchScheduler.java:36-43`). `@EnableScheduling`은 다른 스케줄러 클래스에 선언돼 있다 (`src/main/java/com/fream/back/domain/weather/config/WeatherDataScheduler.java:16`).
- Spring Batch 잡 `updateShipmentStatusesJob`: 청크 크기 50, 스킵 한도 50 (`src/main/java/com/fream/back/domain/shipment/config/UpdateShipmentStatusesJobConfig.java:97-98`, `:101-106`, `:109-128`).

### 2-2. 대상 배송

- Reader: `SELECT s FROM OrderShipment s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL` (`UpdateShipmentStatusesJobConfig.java:133-143`, 쿼리 `:141`).
- 운송장을 등록한 배송만 대상이다. 1절에서 보았듯 정상 등록 경로가 막혀 있으므로 실제로는 대상이 거의 없다.

### 2-3. 실제로 실행되는 처리 코드

- 스텝은 `new ShipmentItemProcessor(playwrightBrowserManager(), notificationService, orderService)`를 쓴다 (`UpdateShipmentStatusesJobConfig.java:115-119`). 실행되는 코드는 `src/main/java/com/fream/back/domain/shipment/config/ShipmentItemProcessor.java`의 `process`(`:57-157`)다.
- 비슷한 코드 중 실행되지 않는 것:
  - `UpdateShipmentStatusesJobConfig.shipmentItemProcessor()` `@Bean` (`UpdateShipmentStatusesJobConfig.java:150-223`). 스텝에 연결되지 않았다. Jsoup 기반 `parseCjLogisticsStatus`(`:232-266`)와 `mapToShipmentStatus`(`:274-280`)도 쓰이지 않는다.
  - `OrderShipmentCommandService.updateShipmentStatuses()` (`OrderShipmentCommandService.java:309-391`). 호출처가 없다. 이 메서드는 DELIVERED일 때 `completeOrder`를 부르지 않고 `Order`를 직접 `COMPLETED`로 바꾼다. 실행되지 않는 쪽이라 무시해도 되지만 동작이 다르다.
- 실행 흐름: 브라우저 열기(`BrowserManageStepListener.beforeStep`, `src/main/java/com/fream/back/domain/shipment/config/BrowserManageStepListener.java:240-244`), 항목마다 새 페이지로 `trace.cjlogistics.com` 이동(`ShipmentItemProcessor.java:72-83`), `tbody#statusDetail tr` 대기(`:87`), 마지막 행의 5번째 `td` 텍스트를 trim해서 읽음 (`:94`, `:181`), 페이지 닫기(`:146-156`).

### 2-4. 택배사 상태 문자열 → 내부 상태

`ShipmentItemProcessor.java:220-226`

- `"배송완료"` → `DELIVERED`
- `"배송출발"` → `OUT_FOR_DELIVERY`
- 그 외 모든 문자열 → `IN_TRANSIT`

이 매핑 때문에 `OUT_FOR_DELIVERY` 배송이 "배송출발"이 아닌 다른 문자열을 받으면 `else` 분기(`ShipmentItemProcessor.java:123-125`)의 `orderShipment.updateStatus(IN_TRANSIT)`가 `OUT_FOR_DELIVERY → IN_TRANSIT` 전이 위반으로 `IllegalStateException`을 던진다 (`src/main/java/com/fream/back/domain/shipment/entity/OrderShipment.java:47-55`, `ShipmentStatus.java:79-84`). 이 항목은 매번 실패해 스킵된다.

## 3. 배송 완료 판정 이후 (`DELIVERED`, 배치 경로)

`ShipmentItemProcessor.java:108-117`

1. 배송: `IN_TRANSIT` 또는 `OUT_FOR_DELIVERY` → `DELIVERED` (`:113`, 허용 전이는 `ShipmentStatus.java:72-84`). 쓰기는 청크 끝의 `JpaItemWriter`에서 커밋된다 (`UpdateShipmentStatusesJobConfig.java:287-292`).
2. `orderService.completeOrder(orderId)` (`:116`, 본체 `OrderShipmentCommandService.java:191-229`)
   - 주문 입찰 조회 후 `Order` → `COMPLETED` (`:196-204`). 허용 전이는 `IN_TRANSIT`, `IN_WAREHOUSE`, `PENDING_PAYMENT`에서 `COMPLETED`로 가는 것 (`OrderStatus.java:24`, `:27`, `:29`).
   - `updateSaleStatusToSold(orderId)` (`:208`) → `Sale`이 `SOLD`로 바뀔 수 있으면 판매자 알림 1건 (`:116-138`, `:151-172`).
   - 구매자 알림 1건, 접두어 "[completeOrder]" (`:211-217`).
3. `notificationService.notifyShipmentCompleted(order)` (`ShipmentItemProcessor.java:117`, 본체 `src/main/java/com/fream/back/domain/notification/service/command/NotificationCommandService.java:219-234`): 구매자 알림 1건, 접두어 "[배송 완료]".

답:

- **상태 변경 순서**: `OrderShipment` → `DELIVERED`, `Order` → `COMPLETED`, `Sale` → `SOLD`(전이 가능할 때만). 창고 보관 상품이면 창고 상태도 바뀐다 (`OrderShipmentCommandService.java:126-129`, 이 배치 경로에서는 `completeOrder`가 `updateSaleStatusToSold`를 통해 호출).
- **구매자 알림: 2건** (`[completeOrder]`, `[배송 완료]`). 같은 내용을 두 번 보낸다.
- **판매자 알림: 0건 또는 1건.** `Sale`이 이미 `SOLD`면 `canTransitionTo(SOLD)`가 false라 보내지 않는다 (`OrderShipmentCommandService.java:119`, `SaleStatus.java`의 `SOLD`는 전이 불가). 결제 시점에 이미 `SOLD`로 바뀌므로 (`PaymentCommandService.java:404`, `:419`) 보통 0건이다. 전이가 아직 가능한 경우에만 1건이다.
- **주문 입찰·판매 입찰: `MATCHED`에서 바뀌지 않는다.** `COMPLETED`로 바꾸는 `updateOrderAndSaleBidStatusToCompleted`(`OrderShipmentCommandService.java:413-440`)는 `updateTrackingInfo`의 `:289`에서만 호출되고, 배치 경로에서는 호출되지 않는다. 주석이 말하는 "배송 완료 시 입찰 완료"가 배치에서는 실행되지 않는다.

## 4. 주문 종류별 차이

### (a) 실배송 일반 구매 입찰 주문

- 1절에서 운송장 등록이 실패하므로 `IN_TRANSIT`이 되지 않는다. 배치 대상이 되지 않아 3의 처리는 도달하지 않는다.
- 가정으로 주문이 `IN_TRANSIT`이었다고 해도 `completeOrder`는 실패한다. 실제 주문 상태는 `PREPARING`이고, `PREPARING → COMPLETED`는 허용되지 않는다 (`OrderStatus.java:26`). `OrderShipmentCommandService.java:204`에서 `InvalidOrderStatusException`이 나오고 `:221-227`에서 `ShipmentException`으로 감싸져 해당 건이 스킵된다.
- `SaleBid`가 없는 경우에는 `:116`에서 먼저 실패한다 (`SaleBidQueryService.java:26-29`). `SaleBid`는 `createInstantSaleBid`로 판매자가 즉시 판매할 때만 생긴다 (`src/main/java/com/fream/back/domain/sale/service/command/SaleBidCommandService.java:59-91`).

### (b) 즉시 구매로 만들어진 주문

- 1절과 같이 운송장 등록이 실패하므로 배치에 도달하지 않는다.
- 가정으로 `IN_TRANSIT` + 운송장이 있었다면 3의 처리는 끝까지 진행된다. `PENDING_PAYMENT → COMPLETED`는 허용되고 (`OrderStatus.java:24`), `SaleBid`가 있으며 (`OrderCommandService.java:279`), `Sale`은 결제 시점에 이미 `SOLD`다 (`PaymentCommandService.java:404`). 따라서 판매자 알림은 0건, 구매자 알림은 2건이다. `OrderBid`, `SaleBid`는 여전히 `MATCHED`다.

### 차이 요약

| 구분 | (a) 일반 구매 입찰 | (b) 즉시 구매 |
|---|---|---|
| 결제 후 주문 상태 | `PREPARING` (`OrderEventConsumer.java:216-218`) | `PENDING_PAYMENT` (`OrderCommandService.java:244`) |
| 운송장 등록 | 실패 (`PREPARING → IN_TRANSIT` 불가) | 실패 (`PENDING_PAYMENT → IN_TRANSIT` 불가) |
| 배치 도달 | 불가 | 불가 |
| 가정 시 `completeOrder` | 실패 (`PREPARING → COMPLETED` 불가) | 성공 |
| 가정 시 구매자 알림 | 없음 | 2건 |

## 5. 실패 처리

- 배치 처리 중 한 건이 실패하면 `ShipmentItemProcessor.process`가 예외를 던진다 (`ShipmentItemProcessor.java:133-145`). 스텝은 `.faultTolerant().skip(Exception.class).skipLimit(50)`이므로 해당 건은 스킵되고 로그가 남는다 (`UpdateShipmentStatusesJobConfig.java:121-124`, 리스너 `:298-333`).
- 실패한 건의 DB 변경은 남지 않는다. 청크 트랜잭션이 롤백되고, 해당 건의 `status`는 `IN_TRANSIT`/`OUT_FOR_DELIVERY`로 그대로다. 다음 실행(6시간 뒤)에 다시 대상이 된다.
- 같은 청크의 다른 건: 프레임워크 표준 동작에 따르면 청크가 롤백된 뒤 항목을 하나씩 다시 처리해 실패한 건만 건너뛰고 나머지는 개별 트랜잭션으로 커밋된다. 이는 Spring Batch의 표준 동작에 근거한 설명이며, 이 저장소 코드에 명시돼 있지는 않고 실행으로 확인하지 않았다.
- 스킵 한도(50) 초과 시 스텝이 실패하고 잡이 `FAILED`가 되며, 그 실행에서 남은 건은 처리되지 않는다. 스케줄러는 예외를 로그로만 남기고 재시도하지 않는다 (`ShipmentBatchScheduler.java:41-43`).
- 브라우저 쪽: `waitForSelector`는 30초 타임아웃이다 (`ShipmentItemProcessor.java:78`, `:87`). 페이지 로드 실패나 행이 없는 경우도 `TRACKING_HTML_PARSE_ERROR`로 스킵된다 (`:167-212`).

## 부가 발견

- 운송장 등록의 `check-status` 경로(`OrderShipmentCommandService.java:473-497`)는 `updateTrackingInfo`로 `IN_TRANSIT`을 먼저 설정한 뒤 `IN_TRANSIT` 상태에 `updateStatus(IN_TRANSIT)`를 호출한다 (`:497`). 전이 규칙상 `IN_TRANSIT → IN_TRANSIT`은 허용되지 않아 `IllegalStateException`이 나고 `EXTERNAL_TRACKING_SERVICE_ERROR`로 롤백된다 (`OrderShipment.java:47-55`).
- Reader JPQL은 enum 필드에 문자열 리터럴(`'IN_TRANSIT'`)을 쓴다 (`UpdateShipmentStatusesJobConfig.java:141`). Spring Boot 3.4.1 / Hibernate 6에서 이 쿼리가 그대로 동작하는지는 코드만으로 확정하지 못했다. 실행 검증이 필요하다.

## 확인하지 못한 것

- 이 답은 코드 읽기에 근거한다. 테스트나 실행은 하지 않았다. 코드는 수정하지 않았다.
- 실행 시 외부 CJ 페이지, Kafka, DB 상태에 따라 결과가 달라질 수 있다.
