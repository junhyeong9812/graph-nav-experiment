# 구매자 배송: 운송장 등록부터 배송 완료까지

코드를 읽어서 확인한 결과다. 실행이나 테스트는 하지 않았고, 코드는 수정하지 않았다.
경로는 저장소 루트 기준이며, 축약 없이 `src/main/java/com/fream/back/...` 로 쓴다.
Spring Batch 재처리·페이징 동작에 대한 판단은 프레임워크 지식에 근거하므로 해당 문장에 표시했다.

## 요약

- 운송장 등록 API(`PATCH /shipments/order/{id}/status`)는 (a), (b) 두 주문 모두 **실패**한다. 주문 상태 `PREPARING`/`PENDING_PAYMENT` 에서 `IN_TRANSIT` 으로 가는 전이가 허용되지 않는다.
- 6시간 주기 배치는 운송장 번호가 저장되고 `IN_TRANSIT`/`OUT_FOR_DELIVERY` 인 배송만 본다. 이런 상태를 만드는 길은 `check-status` 엔드포인트뿐이다.
- 그 길로 들어간 뒤 결과는 (a)는 실패, (b)는 성공이다. (a)는 주문을 `COMPLETED`로 못 바꾸고, (b)는 주문 `COMPLETED`, 배송 `DELIVERED`까지 간다. 입찰은 두 경우 모두 `MATCHED` 로 남는다.

## 1. 운송장 등록 요청

### 1-1. 진입점
- `PATCH /shipments/order/{shipmentId}/status`, 본문 `{courier, trackingNumber}`
  - `src/main/java/com/fream/back/domain/shipment/controller/command/OrderShipmentCommandController.java:20`, `:33-47`
  - DTO: `src/main/java/com/fream/back/domain/shipment/dto/OrderShipmentRequestDto.java:10-12`
- 서비스: `OrderShipmentCommandService.updateTrackingInfo` (`src/main/java/com/fream/back/domain/shipment/service/command/OrderShipmentCommandService.java:238-303`, `@Transactional`)

### 1-2. 코드가 의도한 변경 순서
1. `courier`, `trackingNumber` 공백 검사 (`OrderShipmentCommandService.java:243-246`)
2. `OrderShipment` 로드 (`:249-253`)
3. `OrderShipment` 에 택배사·운송장 저장 후 `status = IN_TRANSIT` 을 **상태 전이 검사 없이** 직접 대입 (`src/main/java/com/fream/back/domain/shipment/entity/OrderShipment.java:41-45`). 규칙상 `PENDING` 에서는 `SHIPPED`/`CANCELED` 만 가능하다 (`src/main/java/com/fream/back/domain/shipment/entity/ShipmentStatus.java:6-8`). 이 규칙을 우회한다.
4. `Order` → `IN_TRANSIT` (`OrderShipmentCommandService.java:259-260`)
5. 구매자에게 알림 1건 "상품이 출발하였습니다." (`:266-271`)
6. `updateSaleStatusToSold` 호출 (`:276`): 판매가 `ON_AUCTION`/`SELLING` 이면 `SOLD`로 바꾸고 판매자에게 알림 1건 (`:112-183`, 조건은 `SaleStatus.java:21-22`)
7. 창고 보관 건이면 창고 상태를 `SOLD` (`:279-286`)
8. `OrderBid`/`SaleBid` → `COMPLETED` (`:289`, 구현 `:413-440`). 이 블록의 예외는 모두 삼켜진다 (`:436-439`).

### 1-3. (a) 실배송 일반 구매 입찰 주문: 실패
- **도달 시점의 주문 상태는 `PREPARING`이다.**
  - 실제 결제·배송 처리는 HTTP에서 Kafka로 넘어간다. `OrderCommandController.java:43-54` 는 `sendOrderProcessingEvent` 후 202를 돌려준다.
  - 소비자 `OrderEventConsumer.java:55-93` → `processCompleteOrder` (`:166~`) 가 `PAYMENT_COMPLETED` (`:195`), 실배송이면 `PREPARING` (`:216-217`) 으로 바꾼다.
  - 동기 경로 `OrderCommandService.processPaymentAndShipment` (`src/main/java/com/fream/back/domain/order/service/command/OrderCommandService.java:175-176`)도 같은 상태로 만들지만, 컨트롤러에서는 호출하지 않는다.
- **`PREPARING` 에서 허용되는 다음 상태는 `IN_WAREHOUSE`, `SHIPMENT_STARTED` 뿐이다** (`src/main/java/com/fream/back/domain/order/entity/OrderStatus.java:26`).
- `IN_TRANSIT` 은 `SHIPMENT_STARTED` 에서만 들어갈 수 있다 (`OrderStatus.java:28`). 그런데 `SHIPMENT_STARTED` 로 바꾸는 코드가 없다. 이 상수는 전이 맵과 표시용 switch(`src/main/java/com/fream/back/domain/order/controller/query/OrderQueryController.java:207`)에만 나온다.
- 따라서 `OrderShipmentCommandService.java:260` 의 `order.updateStatus(IN_TRANSIT)` 가 항상 `InvalidOrderStatusException` 을 던진다 (`src/main/java/com/fream/back/domain/order/entity/Order.java:113-121`, `:117`).
- 그 예외는 `OrderShipmentCommandService.java:295-301` 의 `catch (Exception)` 에서 `ShipmentException(SHIPMENT_NOT_FOUND, ...)` 으로 감싸져 다시 던져진다.
- `GlobalException` 이 `RuntimeException` 이므로 (`src/main/java/com/fream/back/global/exception/GlobalException.java:10`) 트랜잭션이 롤백된다.
- **저장되는 것: 없다.** 택배사, 운송장 번호, 배송 상태는 롤백된다. 주문은 `PREPARING` 그대로다. 알림은 `:266` 에 도달하지 못해 0건이다. Sale·Bid 도 바뀌지 않는다.
- **응답:** `src/main/java/com/fream/back/global/exception/GlobalExceptionHandler.java:459-470` 가 `ShipmentErrorCode.SHIPMENT_NOT_FOUND` 의 값을 쓴다. 결과는 HTTP **404**, 본문 코드 `S001`, 메시지 "배송 정보를 찾을 수 없습니다."다 (`src/main/java/com/fream/back/domain/shipment/exception/ShipmentErrorCode.java:12`). 실제 원인인 상태 전이 실패는 로그에만 남는다.

### 1-4. (b) 즉시 구매 주문: 역시 실패
- 즉시 구매 주문은 `PENDING_PAYMENT` 로 만들어진다 (`src/main/java/com/fream/back/domain/order/service/command/OrderCommandService.java:244`).
- 결제 처리(`PaymentCommandService`)는 Order 상태를 바꾸지 않는다.
- `PENDING_PAYMENT` 에서 허용되는 전이는 `PAYMENT_COMPLETED`, `COMPLETED`, `IN_WAREHOUSE` 뿐이다 (`OrderStatus.java:24`). `IN_TRANSIT` 은 안 된다.
- 따라서 (a)와 같은 예외, 같은 롤백, 같은 404/S001 응답이 된다.

### 1-5. 같은 상태를 바꾸는 다른 경로: `check-status`
- `POST /shipments/order/{id}/check-status` (`OrderShipmentCommandController.java:58`) 와 `/check-status-string` (`:103`) 는 `updateAndCheckShipmentStatus` 를 호출한다 (`OrderShipmentCommandService.java:452-516`).
- 이 메서드는 주문 상태를 건드리지 않고 택배사·운송장 번호를 저장한다 (`:473`, 이때 shipment는 `IN_TRANSIT` 이 된다, `OrderShipment.java:44`). 그 뒤 CJ 조회 결과에 따라 갈린다.
  - **"배송출발"**: `OUT_FOR_DELIVERY` 로 갱신 (`:491-493`). `IN_TRANSIT → OUT_FOR_DELIVERY` 는 허용된다 (`ShipmentStatus.java:17-27`). 커밋되고 주문 상태는 그대로다. 이후 배치 대상이 된다.
  - **"배송완료"**: 4번 참조 (`:483-489`).
  - **그 밖의 문자열**: `:497` 의 `shipment.updateStatus(IN_TRANSIT)` 가 `IN_TRANSIT → IN_TRANSIT` 이라 `IllegalStateException` (`OrderShipment.java:47-55`). `EXTERNAL_TRACKING_SERVICE_ERROR`(S302, 503)로 감싸져 롤백된다 (`:505-514`). 컨트롤러는 상태 코드만 돌려준다 (`OrderShipmentCommandController.java:80-86`).

## 2. 배송 완료 감지

### 2-1. 누가, 언제, 어떻게
- 사람이나 이벤트가 아니라 스케줄러가 한다.
- `src/main/java/com/fream/back/global/config/ShipmentBatchScheduler.java:34` 의 `@Scheduled(cron = "0 0 */6 * * *")` 가 서버 시간대 기준 **매일 00:00, 06:00, 12:00, 18:00**(6시간 주기)에 실행된다.
- 잡 파라미터 `timestamp` 를 붙여 `updateShipmentStatusesJob` 을 실행한다 (`ShipmentBatchScheduler.java:37-40`).
- 배치 인프라는 `@EnableBatchProcessing` (`src/main/java/com/fream/back/global/config/BatchInfraConfig.java:15`). 스케줄링 활성화는 `@EnableScheduling` 이 붙은 다른 컴포넌트(`src/main/java/com/fream/back/domain/event/scheduler/EventStatusScheduler.java:22`)에 기대는 것으로 보인다.

### 2-2. 대상 배송
- reader 쿼리 (`src/main/java/com/fream/back/domain/shipment/config/UpdateShipmentStatusesJobConfig.java:89-97`):
  `SELECT s FROM OrderShipment s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL`
- 페이지·청크 크기는 50 (`UpdateShipmentStatusesJobConfig.java:51`, `:67`, `:94`).

### 2-3. 실제로 실행되는 처리 코드
- 스텝은 `new ShipmentItemProcessor(...)` 를 쓴다 (`UpdateShipmentStatusesJobConfig.java:69-73`).
  → `src/main/java/com/fream/back/domain/shipment/config/ShipmentItemProcessor.java:56-157`.
  Playwright로 `https://trace.cjlogistics.com/next/tracking.html?wblNo=...` 을 열고 `tbody#statusDetail tr` 마지막 행의 5번째 `td` 를 읽는다 (`ShipmentItemProcessor.java:72-94`, `:181`).
- 실행되지 않는 비슷한 코드:
  - `UpdateShipmentStatusesJobConfig.shipmentItemProcessor()` (`:104-177`). 어디서도 호출되지 않는다.
  - `UpdateShipmentStatusesJobConfig.parseCjLogisticsStatus` (`:186`). Jsoup 방식이며 호출되지 않는다.
  - `OrderShipmentCommandService.updateShipmentStatuses()` (`OrderShipmentCommandService.java:309-391`). 호출처가 없다. 이 쪽은 `CjTrackingPlaywright` 를 쓴다 (`:335`).

### 2-4. 택배사 상태 문자열 → 내부 상태
- `ShipmentItemProcessor.java:220-226`:
  - `"배송완료"` → `DELIVERED`
  - `"배송출발"` → `OUT_FOR_DELIVERY`
  - 그 밖의 모든 문자열 → `IN_TRANSIT` (`default`)
- 마지막 행 텍스트가 비면 `TRACKING_HTML_PARSE_ERROR` 예외 (`ShipmentItemProcessor.java:183-188`). 행이 없어도 예외다 (`:172-177`).
- 주의: 한 번 `OUT_FOR_DELIVERY` 가 된 뒤 CJ가 "배송출발"이 아닌 중간 문자열을 보이면 `IN_TRANSIT` 으로 매핑된다. `OUT_FOR_DELIVERY → IN_TRANSIT` 은 허용되지 않으므로 (`ShipmentStatus.java:23-27`) `IllegalStateException` 이 나고, 그 건은 실행마다 skip된다 (`OrderShipment.java:47-55`).

## 3. 배송 완료 판정 이후 (배치 경로)

### 3-1. 엔티티 상태 변경 순서
`ShipmentItemProcessor.java:108-117`:
1. `OrderShipment` → `DELIVERED` (`:113`). `IN_TRANSIT`, `OUT_FOR_DELIVERY` 에서 허용된다 (`ShipmentStatus.java:16-27`). 메모리 상의 변경이다.
2. `completeOrder(orderId)` (`:116`, 구현 `OrderShipmentCommandService.java:191-229`):
   - `OrderBid` 조회 (`:196-197`). 없으면 예외.
   - `Order` → `COMPLETED` (`:204`). `IN_WAREHOUSE`, `IN_TRANSIT`, `PENDING_PAYMENT` 에서 허용된다 (`OrderStatus.java:24`, `:27`, `:29`).
   - `updateSaleStatusToSold` (`:208`, 구현 `:112-183`):
     - `SaleBid` 조회 (`:116`). 없으면 `IllegalArgumentException` 이고 이 호출은 try로 감싸여 있지 않다 (`src/main/java/com/fream/back/domain/sale/service/query/SaleBidQueryService.java:26-29`).
     - `Sale` 이 `ON_AUCTION`/`SELLING` 일 때만 `SOLD` (`:119-123`, `SaleStatus.java:21-22`). 이때 창고 상태도 `SOLD` (`:126-129`) 이고 판매자에게 알림 1건 (`:133-138`).
     - 두 번째 블록 (`:151-175`)은 이미 `SOLD` 면 아무것도 하지 않으므로 판매자 알림은 최대 1건이다 (`:156`).
   - 구매자 알림 "[completeOrder] 주문이 완료 처리되었습니다." (`:211-217`).
3. 구매자 배송 완료 알림 "[배송 완료] ..." (`ShipmentItemProcessor.java:117` → `src/main/java/com/fream/back/domain/notification/service/command/NotificationCommandService.java:219-232`).
4. 청크 끝에서 `JpaItemWriter` 가 저장한다 (`UpdateShipmentStatusesJobConfig.java:241-246`).

### 3-2. 알림
- **구매자: 2건.** `completeOrder` 의 "[completeOrder]..." 1건과 `notifyShipmentCompleted` 의 "[배송 완료]..." 1건이다.
- **판매자: 보통 0건.** 판매 상태는 결제 시점에 이미 `SOLD` 가 되어 있을 수 있다. 결제 처리의 `notifyUsersAndUpdateSaleStatus` 가 `SOLD` 로 바꾸고 판매자에게 "구매자가 결제를 완료하였습니다" 알림을 보낸다 (`src/main/java/com/fream/back/domain/payment/service/command/PaymentCommandService.java:383-420`, `:434-460`). 판매 입찰이 연결된 경우에 해당한다. 그래서 배송 완료 시점에는 `SOLD` 전이가 일어나지 않는다.

### 3-3. 입찰 상태
- `OrderBid` 와 `SaleBid` 는 **`MATCHED` 로 남는다.** `COMPLETED` 가 되지 않는다.
- 입찰은 생성 시점에 이미 `MATCHED` 다 (`src/main/java/com/fream/back/domain/order/entity/OrderBid.java:75`, `src/main/java/com/fream/back/domain/order/service/command/OrderBidCommandService.java:91-100`).
- `COMPLETED` 로 바꾸는 `updateOrderAndSaleBidStatusToCompleted` (`OrderShipmentCommandService.java:413-440`)는 `private` 이고 `updateTrackingInfo` (`:289`)에서만 호출된다. 그 경로는 1번에서 실패하므로 도달하지 않는다.
- 배치 경로의 `completeOrder` 에는 입찰 상태 변경이 없다.

## 4. 주문 종류별 차이

### (a) 실배송 일반 구매 입찰 주문: 끝까지 가지 못한다
- 1번의 PATCH 경로에서는 2단계 전에 실패한다. 배치 대상이 되는 길은 `check-status` 의 "배송출발"뿐이다 (1-5).
- 배치가 CJ "배송완료"를 판정하면 (`ShipmentItemProcessor.java:108-117`):
  1. shipment는 `DELIVERED` 가 된다 (메모리).
  2. `completeOrder`: `OrderBid` 는 찾는다 (`MATCHED`). 그런데 `Order` 가 `PREPARING` 이라 `COMPLETED` 로 갈 수 없다 (`OrderStatus.java:26`). 여기서 `InvalidOrderStatusException` (`Order.java:117`) 이 난다. `OrderShipmentCommandService.java:204`.
  3. `:221-228` 에서 `ShipmentException(ORDER_NOT_FOUND_FOR_SHIPMENT, S102)` 로 감싸진다.
  4. 처리기가 다시 던지고 (`ShipmentItemProcessor.java:133-145`), 그 건은 skip된다.
- 결과: 배송은 롤백되어 `OUT_FOR_DELIVERY` 로 남고, 주문은 `PREPARING` 그대로다. 알림은 0건이고 입찰은 `MATCHED` 다. 다음 6시간 배치에서 같은 실패가 반복된다.
- `check-status` 로 CJ "배송완료"를 직접 받아도 같은 지점(`:204`)에서 실패한다. 응답은 `S102` 에 해당하는 404다 (`OrderShipmentCommandController.java:80-86`, `OrderShipmentCommandService.java:505-506`).

### (b) 즉시 구매로 만들어진 주문: 끝까지 간다
- 즉시 구매는 `createInstantOrder` 에서 `Order`(`PENDING_PAYMENT`) 와 `SaleBid`(`MATCHED`, `order` 연결)를 만든다 (`OrderCommandService.java:244`, `:279-280`). 그다음 결제를 처리한다 (`:305`).
- 결제 처리 시점에 `order.getOrderBid()` 가 아직 없으므로 `SaleBid` 경로로 들어가고, `Sale` 이 `SOLD` 가 되며 알림 2건이 간다 (`PaymentCommandService.java:387-405`, `:434-460`). 즉시 구매 `OrderBid` 는 그 뒤에 만들어진다 (`OrderBidCommandService.java:142`, `:189-205`, `isInstantPurchase=true`).
- PATCH 경로: 1-4에서 실패한다 (`PENDING_PAYMENT → IN_TRANSIT` 불가).
- `check-status` 로 CJ "배송완료"를 받는 경우 (`OrderShipmentCommandService.java:483-489`):
  - shipment `DELIVERED` (`IN_TRANSIT → DELIVERED` 허용).
  - `completeOrder`: 즉시 구매 `OrderBid` 가 있다. `PENDING_PAYMENT → COMPLETED` 는 허용된다 (`OrderStatus.java:24`).
  - `updateSaleStatusToSold`: `SaleBid` 가 있다. `Sale` 은 이미 `SOLD` 라서 상태 변경도 판매자 알림도 없다.
  - 구매자 알림 1건 (`completeOrder`). `notifyShipmentCompleted` 는 이 경로에서 호출되지 않는다.
  - 트랜잭션이 커밋되고 응답은 200, 상태 `DELIVERED` 다.
- 배치 경로: "배송출발"로 `OUT_FOR_DELIVERY` 를 저장한 뒤 배치가 "배송완료"를 판정하면 같은 로직으로 성공한다. 이때 구매자 알림은 2건이다.
- **결과 요약:** 주문 `COMPLETED`, 배송 `DELIVERED`, 판매 `SOLD`(결제 시점), 구매자 알림 1~2건, 판매자 알림 0건(배송 시점), 주문 입찰·판매 입찰은 `MATCHED` 유지.

## 5. 실패 처리 (주기 처리 중 한 건 실패)

- 설정: `UpdateShipmentStatusesJobConfig.java:75-78`: `.faultTolerant().skip(Exception.class).skipLimit(50)`.
- **실패한 건:**
  - 처리기 예외 → 그 건은 skip된다. `SkipListener` 가 로그를 남긴다 (`:252-266`).
  - 그 건의 DB 변경은 청크 트랜잭션 롤백으로 되돌아간다. `completeOrder` 는 `@Transactional` 로 같은 트랜잭션에 참여하므로 주문·판매·알림 변경도 함께 롤백된다.
  - 건은 이전 상태(`IN_TRANSIT` 또는 `OUT_FOR_DELIVERY`)로 남고, 다음 실행(6시간 뒤)에 다시 선택된다.
- **같은 청크의 나머지 건 (프레임워크 동작에 근거한 판단):** Spring Batch의 fault-tolerant 처리는 청크 롤백 후 건별로 다시 처리한다. 그래서 정상 건은 처리되어 저장되고 실패 건만 skip된다. 이 저장소에서 실행해 확인하지는 않았다.
- **skip 한도:** 한 실행에서 51번째 skip이 나면 `SkipLimitExceeded` 로 스텝이 실패한다. 남은 건은 그 실행에서 처리되지 않는다 (프레임워크 동작).
- **페이징 주의 (코드 구조에서 나온 추정):** reader는 `JpaPagingItemReader` 로 offset 페이징을 한다. 처리 중 `DELIVERED` 가 된 건은 쿼리에서 빠지므로 다음 페이지 offset이 밀린다. 그래서 일부 건이 그 실행에서 건너뛰어질 수 있다. 다음 실행에서 잡힌다.
- 대조: 호출되지 않는 `OrderShipmentCommandService.updateShipmentStatuses()` (`:309-391`) 는 건별 `try/catch` 로 계속 진행하는 구조이지만 실제로는 실행되지 않는다.

## 주석·이름과 실제 동작이 다른 곳

1. `OrderShipment.updateTrackingInfo` (`OrderShipment.java:41-45`) 는 상태 전이 규칙을 우회해 `IN_TRANSIT` 을 직접 대입한다.
2. `updateTrackingInfo` 의 주석 "배송 상태가 변경되었으므로 주문 상태도 업데이트" (`OrderShipmentCommandService.java:258`) 는 실제로는 항상 실패한다 (1-3, 1-4).
3. `updateTrackingInfo` 는 모든 예외를 `SHIPMENT_NOT_FOUND`(404, S001)로 감싼다 (`:297-300`). 원인과 무관한 코드다.
4. `completeOrder` 는 "주문을 완료 상태로 변경하고 관련된 후속 작업" (`:185-189`)이라고 하지만 입찰을 `COMPLETED` 로 바꾸지 않는다 (`:191-229`).
5. `UpdateShipmentStatusesJobConfig.shipmentItemProcessor()` 의 주석 "DELIVERY 완료 시 알림, Order 상태 완료 등도 여기서 처리" (`:101-103`) 는 실행되지 않는 코드에 대한 설명이다.
6. `OrderShipmentCommandService.updateShipmentStatuses()` 의 "전체 배송 상태를 주기적으로 업데이트" (`:305-307`) 는 호출처가 없다.
7. 배송 완료 알림은 배치 경로에서 구매자에게 2건 나간다 (`completeOrder` 1건 + `notifyShipmentCompleted` 1건). `check-status` 경로에서는 1건이다.
8. `updateOrderAndSaleBidStatusToCompleted` 는 `private` 이라 메서드 프록시가 적용되지 않고, 예외를 모두 삼킨다 (`:436-439`). 이 경로는 도달하지 않는다.

## 기타 확인 사항

- `/shipments` 경로의 역할 제한은 찾지 못했다. `src/main/java/com/fream/back/global/config/security/SecurityConfig.java` 를 포함해 소스 어디에도 `/shipments` 규칙이 없다. 운영자 전용 접근 제한은 코드에서 확인되지 않는다.

## 근거의 한계

- 실행이나 테스트는 하지 않았다. 모든 판단은 정적 읽기에 근거한다.
- Spring Batch의 fault-tolerant 재처리(3·5번)와 offset 페이징 밀림(5번)은 프레임워크 동작에 대한 판단이다. 실제 실행으로 확인하지 않았다.
