# 즉시 구매는 어떻게 처리되나

근거 경로는 `src/main/java/com/fream/back/` 아래 상대경로로 적었다 (예: `domain/order/...`는 `src/main/java/com/fream/back/domain/order/...`).

## 1. 진입점, 처리 방식, 응답 ID

- **API**: `POST /order-bids/instant` (`src/main/java/com/fream/back/domain/order/controller/command/OrderBidCommandController.java:89-90`). 요청 본문은 `InstantOrderRequestDto`(`saleBidId`, `addressId`, `warehouseStorage`, `paymentRequest`).
- **처리 단계** (컨트롤러 `:92-107`):
  1. 토큰에서 이메일 추출 (`:92`)
  2. `paymentRequest`에 `userEmail`(토큰 값)을 넣고 `orderId`를 `null`로 설정 (`:98`, `:119-123`)
  3. `OrderBidCommandService.createInstantOrderBid(...)` 호출 (`:101-107`)
- **서비스 단계** (`order/service/command/OrderBidCommandService.java:118-149`, `@Transactional`):
  1. 입력 null 검사 (`:123`, `:154-167`)
  2. 구매자 조회 (`:126`)
  3. 판매 입찰 조회·검증 (`:129`, `:172-184`)
  4. `OrderCommandService.createInstantOrder(...)`로 주문 생성·결제 (`:133-139`)
  5. `OrderBid` 생성·저장 (`:142`, `:189-207`)
- **동기/비동기**: 동기다. 이 경로에는 Kafka 발행이 없다 (`OrderCommandService.createInstantOrder`에 producer 호출 없음). 기존 `OrderCommandController`의 Kafka 비동기 처리(`:34`)는 즉시 구매 경로가 아니다. 결제 대행사 호출(카드)과 STOMP 푸시도 요청 스레드 안에서, DB 트랜잭션이 끝나기 전에 실행된다.
- **응답 ID는 `OrderBid`의 ID다.** 컨트롤러가 `createInstantOrderBid(...).getId()`를 반환한다 (`OrderBidCommandController.java:101-107`). 변수명은 `orderId`이고 javadoc은 "생성된 주문 ID"라고 적었지만(`:83`), 실제로는 `OrderBid` ID다. `Order` ID는 응답에 없다. 구매자 알림 본문에만 `Order` ID가 들어간다 (`payment/service/command/PaymentCommandService.java:438-445`).
- **주석/이름과 실제 동작이 다른 곳**
  - 판매 입찰이 없을 때 javadoc은 `SaleBidNotFoundException`을 말하지만(`OrderBidCommandService.java:115`), 실제로는 `SaleBidQueryService.findById`가 `IllegalArgumentException`을 던지고(`sale/service/query/SaleBidQueryService.java:21-23`), 서비스의 `catch (Exception)`이 이를 `OrderBidCreationFailedException`으로 감싼다 (`OrderBidCommandService.java:145-148`, `:212-218`). 그래서 `getSaleBidAndValidate`의 null 검사(`:174-176`)는 도달하지 않는 코드다.
  - `createInstantOrder`의 `isWarehouseStorage` 파라미터는 본문에서 쓰이지 않는다 (`OrderCommandService.java:221`, 사용처는 `:289-293`의 판매 쪽 플래그뿐).

## 2. 생성되는 엔티티와 상태 변화 순서

| 순서 | 동작 | 근거 | 직후 상태 |
|---|---|---|---|
| 1 | `Order` 생성·저장 | `order/service/command/OrderCommandService.java:241-247` | `Order.status = PENDING_PAYMENT`, `totalAmount = saleBid.bidPrice` |
| 2 | `paymentRequest.orderId` 설정 | `OrderCommandService.java:250` | — |
| 3 | `OrderItem` 추가 | `OrderCommandService.java:255-256` | Order는 여전히 `PENDING_PAYMENT` |
| 4 | `OrderShipment` 생성 (구매자 배송지 스냅샷) | `OrderCommandService.java:264-271` | Order는 여전히 `PENDING_PAYMENT` |
| 5 | `SaleBid` 연결 및 `entityManager.flush()` | `OrderCommandService.java:279-283`, `sale/entity/SaleBid.java:58-61` | `SaleBid.status = MATCHED`, `SaleBid.order = order` |
| 6 | 판매 쪽 `Sale.isWarehouseStorage`가 true일 때만 창고 상태 변경 | `OrderCommandService.java:291-301` | `WarehouseStorage.status = ASSOCIATED_WITH_ORDER` (이 경우에만) |
| 7 | `paymentCommandService.processPayment(...)` | `OrderCommandService.java:305` | `Payment` 생성 (아래 3번). 그 뒤 `Sale.status = SOLD` (`payment/service/command/PaymentCommandService.java:404`) |
| 8 | `OrderBid` 생성·저장 | `OrderBidCommandService.java:189-206` | `OrderBid.status = MATCHED`, `isInstantPurchase = true`, `order`·`sale`·`user` 설정 |

- 7단계에서 `Order.orderBid`는 아직 `null`이다. `OrderBid`는 8단계에서야 만들어지기 때문이다. 그래서 `notifyUsersAndUpdateSaleStatus`는 `order.getOrderBid()==null` 분기(`PaymentCommandService.java:389-`)로 빠지고, `saleBidQueryService.findByOrderId`로 판매 입찰을 찾아 `Sale`을 `SOLD`로 바꾼다 (`:404`).
- `Order`는 이 경로 어디에서도 `PAYMENT_COMPLETED` 이상으로 바뀌지 않는다. `PAYMENT_COMPLETED`를 설정하는 곳은 Kafka 소비자(`order/service/kafka/OrderEventConsumer.java:195`)와 기존 `processPaymentAndShipment`(`OrderCommandService.java:165-175`)뿐이다.
- 입찰·판매 상태에 대한 검사가 없다. `getSaleBidAndValidate`는 `SaleBid`의 `status`나 `Sale`의 `status`를 보지 않는다 (`OrderBidCommandService.java:172-184`). 그래서 이미 `MATCHED`/`SOLD`인 판매 입찰도 그대로 통과한다 (아래 3번의 중복 결제 주의점 참고).

## 3. 결제 수단별 결과, 성공 여부, 카드 실패 응답

`PaymentCommandService.processPayment`(`payment/service/command/PaymentCommandService.java:57`)는 `paymentType`(JSON `CARD`/`ACCOUNT`/`GENERAL`)으로 분기한다 (`payment/dto/PaymentRequestDto.java`의 `@JsonSubTypes`).

공통 검증 (`PaymentCommandService.java:117-145`): 주문 ID 일치, 이메일 일치, `paidAmount > 0`만 확인한다. **결제 금액을 판매 입찰 가격(`order.totalAmount`)과 비교하지 않는다.** 또 `InstantOrderRequestDto.paymentRequest` 필드에 `@Valid`가 없어서 `PaymentRequestDto`의 `@Min(100)`(`PaymentRequestDto.java:51`)도 적용되지 않는다. 1원 결제도 검증을 통과한다.

- **CARD** (`createCardPayment`, `PaymentCommandService.java:157-`)
  - 결제 정보 조회 후 PortOne 호출: `portOneApiClient.processCardPayment(paymentInfo, requestDto.getPaidAmount())` (`:179`). 청구 금액은 클라이언트가 보낸 `paidAmount`다.
  - PortOne 응답의 `code`가 0이 아니면 `PaymentProcessingException`을 던진다 (`payment/portone/PortOneApiClient.java:270-274`).
  - 응답의 `status`가 문자열 `"success"`일 때만 `PAID`·성공으로 표시한다 (`PaymentCommandService.java:203-206`). 그 외에는 `Payment` 기본값 `PENDING`(`payment/entity/Payment.java:44`), 성공 아님으로 저장된다.
  - **결과**: `code==0`이고 `status!="success"`이면 예외 없이 진행한다. `Payment`는 `PENDING`으로 저장되는데, 알림 전송과 `Sale.SOLD` 처리가 그대로 실행되고 응답은 성공이다.
- **ACCOUNT** (`createAccountPayment`, `:236-`)
  - 은행명 검증 후 `AccountPayment`를 `PENDING`으로 저장한다 (`:260-262`). 외부 호출은 없다.
  - 그 뒤 같은 `notifyUsersAndUpdateSaleStatus`가 실행되어 `Sale`이 `SOLD`가 되고, 구매자에게 "결제가 완료되었습니다" 알림이 간다. 입금 확인은 이 경로에 없다.
- **GENERAL** (`createGeneralPayment`, `:290-`)
  - `impUid`가 비어 있지 않은지만 확인하고 (`:297-300`), 외부 검증 없이 `PAID`, `successStatus=true`로 저장한다 (`:314-316`). 클라이언트가 보낸 `impUid`를 PG에 조회하지 않는다.
- **카드 결제 실패 응답 시 (PortOne이 `code != 0`)**
  1. `PortOneApiClient.java:274`의 `PaymentProcessingException` (`PaymentException`의 하위, `payment/exception/PaymentProcessingException.java:6`)
  2. `processPayment` → `OrderCommandService.createInstantOrder`의 `catch`가 `OrderPaymentProcessingFailedException`으로 감싼다 (`OrderCommandService.java:305-309`, `:312-317`)
  3. `OrderBidCommandService`의 `catch`를 거쳐 `OrderException`으로 그대로 다시 던져진다 (`OrderBidCommandService.java:145-148`, `:212-215`)
  4. 두 `@Transactional` 경계에서 `RuntimeException`이 나와 **트랜잭션 전체가 롤백된다.** `Order`, `OrderItem`, `OrderShipment`, `SaleBid` 상태 변경(`MATCHED`→`PENDING`), 창고 상태 변경, `Payment`가 모두 취소된다. 알림도 보내지 않는다 (알림은 `processPayment` 뒤에 있음).
  5. 응답은 `GlobalExceptionHandler`의 `OrderException` 핸들러(`global/exception/GlobalExceptionHandler.java:325`)로 나간다. 상태는 `ORD005`의 500, 메시지는 enum 고정 문구 "주문 결제 처리에 실패했습니다."다 (`order/exception/OrderErrorCode.java:44`). PG 실제 실패 메시지는 응답에 나가지 않고 로그에만 남는다.
  - 주의: DB 롤백은 PG 쪽 요청을 되돌리지 않는다. PG에서 승인된 뒤 DB 쓰기가 실패하는 경우에 대한 보상(취소) 로직은 이 경로에 없다.

**즉시 구매가 끝까지 성공하는가?** HTTP 레벨에서는 세 결제 수단 모두 성공 응답(`"즉시 구매가 성공적으로 처리되었습니다."`)을 줄 수 있다. 하지만 주문은 끝까지 `PENDING_PAYMENT`로 남는다 (4번 참고). 카드는 `status != "success"`인 경우 결제 미확정인데도 성공 응답이 나가고, 계좌 이체는 입금 전에 성공 응답이 나간다. 판매 입찰 중복 구매도 막히지 않는다. 같은 `SaleBid`에 대해 두 요청이 들어오면 둘 다 PG 결제까지 진행할 수 있다. 그 뒤 `OrderBid`의 `sale_id` 유니크 제약(`@OneToOne`)에 걸리면 DB 쪽에서 롤백되지만, 카드 승인은 이미 일어난 뒤다. 이 부분은 DDL 유니크 제약 생성을 실제로 확인하지 못했으므로 추정이다.

## 4. 알림 수신자, 시점, 방식

`sendNotifications` (`PaymentCommandService.java:434-`)가 두 명에게 `NotificationCategory.SHOPPING` / `NotificationType.BID`로 알림을 만든다.

- **구매자**: "결제가 완료되었습니다. 주문 ID: {orderId}" (`:438-445`)
- **판매자**: "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}" (`:449-`)

시점은 `processPayment` 성공 직후다. 즉 `OrderBid` 저장과 트랜잭션 커밋보다 앞이다. 결제 유형과 무관하게 보내며, 계좌 이체(`PENDING`)와 `status!="success"`인 카드도 포함된다.

방식은 두 단계다 (`notification/service/command/NotificationCommandService.java`).
1. `createNotification`(`:44`)이 DB에 저장한다 (`:53`).
2. 저장 직후 `sendRealTimeNotification`(`:57`, 정의 `:303-`)이 Redis 키(접속 여부)를 확인하고, 접속 중이면 STOMP로 `/user/{email}/queue/notifications`에 보낸다 (`WEBSOCKET_DESTINATION = "/queue/notifications"`, `:38`). 접속 중이 아니면 DB에만 남는다.

두 단계 모두 같은 트랜잭션 안에서(`NotificationCommandService`는 클래스 레벨 `@Transactional`, `:27`) 실행된다. STOMP 푸시는 커밋 전에 나가므로, 이후 `OrderBid` 저장이 실패해 롤백되더라도 접속 중인 사용자는 이미 알림을 받은 상태가 된다. 알림 호출 예외는 `sendNotifications`가 삼켜서 결제 흐름을 멈추지 않는다 (`PaymentCommandService.java`의 `sendNotifications` catch).

## 5. 처리 완료 후 최종 상태, 창고 보관 선택 시

성공 경로의 최종 상태 (카드 `PAID`/계좌 `PENDING`/일반 `PAID` 기준):

| 엔티티 | 최종 상태 | 근거 |
|---|---|---|
| `Order` | `PENDING_PAYMENT` (바뀌지 않음) | `OrderCommandService.java:244-247`, 이 경로에 `updateStatus` 없음 |
| `OrderBid` | `MATCHED`, `isInstantPurchase=true`, `order`·`sale` 연결 | `OrderBidCommandService.java:196`, `:205-206` |
| `SaleBid` | `MATCHED`, `order` 연결 | `OrderCommandService.java:279-280`, `sale/entity/SaleBid.java:58-61` |
| `Sale` | `SOLD` | `PaymentCommandService.java:404` |
| `Payment` | `PAID`(카드 `success`, 일반) / `PENDING`(계좌, 카드 `status!="success"`) | `PaymentCommandService.java:203-206`, `:260`, `:314` |
| `OrderShipment` | 생성됨 (구매자 배송지) | `OrderCommandService.java:264-271` |

**창고 보관을 선택한 경우**: 구매자의 `warehouseStorage` 값은 어디에서도 쓰이지 않는다. 컨트롤러 로그 (`OrderBidCommandController.java:94-95`)와 서비스 호출 인자(`:105`)에만 있고, `createInstantOrder` 안의 분기는 판매 쪽 `sale.isWarehouseStorage()`(`OrderCommandService.java:292`)만 본다. 그래서 구매자가 창고 보관을 골라도 달라지는 것은 다음과 같다.
- 판매자가 이미 창고 보관으로 올린 `Sale`(`SaleCommandService.java:96-107`)이라면 `WarehouseStorage`가 `ASSOCIATED_WITH_ORDER`가 된다 (`OrderCommandService.java:293`).
- 구매자 선택과 상관없이 `OrderShipment`는 항상 생성되고 (`:264-271`), `Order`는 `IN_WAREHOUSE`로 바뀌지 않으며, `Order.warehouseStorage`에도 연결되지 않는다 (`Order.assignWarehouseStorage`는 다른 경로에서만 호출된다: `OrderCommandService.java:171`, `OrderEventConsumer.java:200`).
- 즉 구매자가 창고 보관을 선택해도 주문은 배송 주문으로 남고, 판매자가 창고 보관으로 올린 경우에는 창고 상태만 바뀌고 주문과 연결되지 않는 불일치가 생긴다.
