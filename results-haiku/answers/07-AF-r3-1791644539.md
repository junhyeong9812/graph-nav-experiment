# 즉시 구매는 어떻게 처리되나

모든 경로는 저장소 루트 기준이다. `src/main/java/com/fream/back/` 아래 파일은 `domain/...`, `global/...`으로 줄여 적지 않고 전체 경로로 적는다.
코드는 읽기만 했고 실행하거나 테스트하지 않았다. 외부 PortOne 응답 스펙은 저장소에 없으므로 그 부분은 코드가 기대하는 동작만 근거로 쓴다.

---

## 1. 요청 진입점, 처리 단계, 동기/비동기, 응답 ID

**진입점:** `POST /order-bids/instant` → `OrderBidCommandController#createInstantOrderBid`
- `src/main/java/com/fream/back/domain/order/controller/command/OrderBidCommandController.java:89-90`
- 구매자 이메일은 보안 컨텍스트에서 꺼낸다 (`:92`).
- 결제 요청에 `userEmail`을 덮어쓰고 `orderId`를 `null`로 만든다 (`:98`, `:119-123`).

**처리 단계 (모두 같은 HTTP 요청 스레드에서 동기 실행):**
1. `OrderBidCommandService#createInstantOrderBid`가 `@Transactional`로 시작한다 (`src/main/java/com/fream/back/domain/order/service/command/OrderBidCommandService.java:118-119`).
2. 입력 검증: 이메일, `saleBidId`, `addressId`, `paymentRequest` null 여부만 본다 (`OrderBidCommandService.java:154-167`).
3. 구매자 조회: `userQueryService.findByEmail` (`:126`).
4. 판매 입찰 조회: `getSaleBidAndValidate` (`:129`, `:172-184`).
5. `OrderCommandService#createInstantOrder` 호출 (`:133-139`). 여기서 주문, 주문 항목, 배송, 판매 입찰 매칭, 창고 상태, 결제를 처리한다 (상세는 2, 3번).
6. `OrderBid` 생성·저장 (`:142`, `:189-207`).
7. `ResponseDto.success(orderId, "즉시 구매가 성공적으로 처리되었습니다.")`를 200으로 반환 (`OrderBidCommandController.java:109`).

**동기/비동기:** 동기다.
- 이 경로에는 Kafka 발행이 없다. 비동기 결제는 별도 엔드포인트 `POST /orders/{orderId}/process-payment-shipment`의 `OrderCommandController.java:54`에서만 `sendOrderProcessingEvent`를 호출한다.
- 주문 생성, 결제, 알림, 판매 상태 변경이 하나의 DB 트랜잭션 안에서 처리된다 (`OrderBidCommandService.java:118`, `OrderCommandService.java:219`, `PaymentCommandService.java:37` 클래스 레벨 `@Transactional`이 합류한다).
- PortOne HTTP 호출도 이 트랜잭션 안에서 일어난다 (`PaymentCommandService.java:179`).

**응답 ID는 `OrderBid`의 ID다. 주문(`Order`)의 ID가 아니다.**
- `createInstantOrderBid`의 반환 타입이 `OrderBid`다 (`OrderBidCommandService.java:119`).
- 컨트롤러는 그 객체의 `.getId()`를 `orderId`라는 변수에 담아 반환한다 (`OrderBidCommandController.java:101-107`).
- 컨트롤러 Javadoc은 "생성된 주문 ID"라고 적었다 (`OrderBidCommandController.java:83`). 실제 값과 다르다.

## 3. 결제 수단별 결과, 끝까지 성공 여부, 카드 실패 응답 처리

결제 분기는 `PaymentCommandService.java:67-80`의 `switch`다. 타입은 `PaymentRequestDto#getResolvedPaymentType`이 정한다 (`src/main/java/com/fream/back/domain/payment/dto/PaymentRequestDto.java:74-87`).

**공통 검증** (`PaymentCommandService.java:117-146`)
- `order.getId()`와 `requestDto.orderId` 일치 (`:131`).
- 사용자 이메일 일치 (`:136`).
- `paidAmount > 0`만 확인한다 (`:142`).
- **결제 금액이 판매 입찰가와 같은지는 확인하지 않는다.** 주문 금액은 `saleBid.getBidPrice()`(`OrderCommandService.java:243`)인데, 실제 청구 금액은 클라이언트가 보낸 `paidAmount`를 그대로 쓴다 (`PaymentCommandService.java:179`).
- `PaymentRequestDto`의 `@Min(100)`, `@NotBlank`는 적용되지 않는다. `InstantOrderRequestDto.java:28-29`의 `paymentRequest`에 `@Valid`가 없어서 중첩 검증이 돌지 않는다.

**CARD (카드)** — `createCardPayment`, `PaymentCommandService.java:157-225`
- 결제 정보는 구매자 본인 것만 조회한다 (`:166` → `PaymentInfoQueryService.getPaymentInfoEntity`, `src/main/java/com/fream/back/domain/payment/service/query/PaymentInfoQueryService.java:129`).
- PortOne 원타임 결제 호출 (`src/main/java/com/fream/back/domain/payment/portone/PortOneApiClient.java:229`, 호출 `:266`).
- 응답 본문 `code != 0`이거나 HTTP가 200이 아니면 `PaymentProcessingException`을 던진다 (`PortOneApiClient.java:270-275`).
- 응답 `status == "success"`일 때만 `PAID`로 바꾸고 `isSuccess = true`로 한다 (`PaymentCommandService.java:203-206`). 그 외에는 생성 시 기본값 `PENDING`을 유지하며 `isSuccess = false`다 (`src/main/java/com/fream/back/domain/payment/entity/Payment.java:39, 44`). **예외는 던지지 않는다.**
- 끝까지 성공하는 경우: PG가 `code 0`과 `status "success"`를 줄 때다. 그 뒤 주문 상태는 여전히 `PENDING_PAYMENT`다 (2번 참조).

**ACCOUNT (계좌이체)** — `createAccountPayment`, `PaymentCommandService.java:236-279`
- 은행명 검증 후 `AccountPayment`를 만든다 (`:244`, `:250-256`).
- **`accountPayment.updateStatus(PaymentStatus.PENDING)` (`:260`)에서 항상 실패한다.** 생성 시 상태는 이미 `PENDING`인데 `Payment#updateStatus`는 `this.status.canTransitionTo(newStatus)`를 검사한다 (`Payment.java:70-76`). `PaymentStatus.canTransitionTo`는 `PENDING → PAID`만 허용한다 (`src/main/java/com/fream/back/domain/payment/entity/PaymentStatus.java:10-21`). 따라서 `PENDING → PENDING`은 `IllegalStateException`이고, `catch (Exception)`(`PaymentCommandService.java:274-277`)이 `PaymentProcessingException`으로 바꾼다.
- 결과: **계좌이체 즉시 구매는 항상 실패하고 전체가 롤백된다.**

**GENERAL (일반 결제)** — `createGeneralPayment`, `PaymentCommandService.java:290-333`
- 클라이언트가 보낸 `impUid`가 비어 있지 않은지만 확인한다 (`:297-300`).
- 상태를 바로 `PAID`, `isSuccess = true`로 만든다 (`:313-314`).
- **PortOne에 `impUid`를 조회해 검증하는 호출이 없다.** `PortOneApiClient`의 public 메서드는 `getAccessToken`, `requestTestPayment`, `processCardPayment`, `refundPayment`, `cancelTestPayment`, `cancelPayment`뿐이다.
- 결과: 클라이언트가 주장하는 `impUid`와 `paidAmount`를 그대로 믿는다. 끝까지 성공한다.

**카드 결제를 대행사가 실패로 응답하면**
- (a) HTTP 비정상, `code != 0`: `PortOneApiClient.java:270-275`에서 `PaymentProcessingException` → `PaymentCommandService.java:179-184`, `:89-94` 재던짐 → `OrderCommandService.java:307-308`이 `OrderPaymentProcessingFailedException`으로 감쌈 → `OrderBidCommandService.java:145-146`이 `OrderException`은 그대로 재던짐 → `GlobalExceptionHandler.java:49-56`이 `ErrorCode`의 상태 코드로 응답한다.
  - 모든 예외는 `RuntimeException` 하위이므로 `@Transactional`이 롤백한다 (`global/exception/GlobalException.java:10`).
  - 주문, 주문 항목, 배송, `SaleBid` 매칭, `Sale` 상태, 알림은 모두 저장되지 않는다. 알림은 결제 뒤에 실행되므로 아예 보내지지 않는다.
- (b) 네트워크 또는 HTTP 클라이언트 예외 (`RestClientException`): `PortOneApiClient.java:288-290`에서 `PaymentApiException`으로 바뀌어 (a)와 같이 롤백된다.
- **재시도는 없다.** `@Retryable`(`PortOneApiClient.java:224-228`)은 붙어 있지만 `@EnableRetry`가 프로젝트 어디에도 없어서 동작하지 않는다 (`src/main` 전체 검색).
- (c) `code 0`인데 `status != "success"`: 예외 없이 `PENDING` 결제가 저장되고 트랜잭션이 커밋된다. 그 뒤 `notifyUsersAndUpdateSaleStatus`가 결제 상태와 관계없이 알림을 보내고 `Sale`을 `SOLD`로 바꾼다 (`PaymentCommandService.java:83`, `:404`). 주문은 `PENDING_PAYMENT`이고 결제는 `PENDING`인데 판매는 `SOLD`인 불일치가 생긴다. 코드가 기대하는 문자열은 `"success"`뿐이다. 실제 PortOne이 이 문자열을 주는지는 저장소만으로 확인할 수 없다.
- (d) 카드 승인 뒤 같은 트랜잭션의 나중 단계가 실패하면, 카드는 이미 승인됐는데 DB는 롤백된다. 보상 환불을 하는 `handleRefundIfNecessary`(`PaymentCommandService.java:341-375`)는 어디서도 호출되지 않는다 (`src/main` 전체 검색). 나중 단계는 `OrderBid` 저장(`OrderBidCommandService.java:206`)과 커밋이다.

**요약:** 즉시 구매가 끝까지 성공하는 경우는 카드(PG 응답이 `success`일 때)와 일반 결제뿐이다. 계좌이체는 항상 실패한다. 그리고 성공해도 주문 상태는 `PENDING_PAYMENT`로 남는다.

## 4. 알림 수신자, 시점, 방식

**수신자 2명**
- 구매자: `order.getUser()`, 본문 "결제가 완료되었습니다. 주문 ID: …" (`PaymentCommandService.java:436-443`).
- 판매자: `sale.getSeller()`, 본문 "구매자가 결제를 완료하였습니다. 판매 ID: …" (`:447-454`).
- 두 알림 모두 카테고리 `SHOPPING`, 타입 `BID` (`:440-441`, `:451-452`, `src/main/java/com/fream/back/domain/notification/entity/NotificationType.java`에서 `BID(NotificationCategory.SHOPPING, …)`).

**시점**
- 결제가 성공 분기를 지나 `notifyUsersAndUpdateSaleStatus`에 도달했을 때만 보낸다 (`PaymentCommandService.java:83`). 결제 실패로 예외가 나면 보내지 않는다.
- 카드 (c) 경우처럼 `PENDING` 결제여도 보낸다.
- 계좌이체는 결제 단계에서 실패하므로 보내지 않는다.
- 같은 트랜잭션 안에서, `OrderBid` 저장과 커밋 전에 보낸다 (`PaymentCommandService.java:391-404`, 2번 참조).

**방식**
- 비동기 메시지 큐나 이메일, SMS는 쓰지 않는다. 이 경로에 Kafka나 `@Async`가 없다.
- `Notification` 행을 DB에 저장한다 (`NotificationCommandService.java:52-53`).
- 실시간 전송은 Redis에 해당 사용자 키가 있을 때만 WebSocket(STOMP `convertAndSendToUser`)으로 보낸다 (`NotificationCommandService.java:57`, `:303-323`).
- 알림 저장이나 전송이 실패해도 결제는 막히지 않는다. `sendNotifications`와 `notifyUsersAndUpdateSaleStatus`가 예외를 삼킨다 (`PaymentCommandService.java:421-425`, `:457-461`).

## 5. 처리 완료 후 주문의 최종 상태, 창고 보관 선택 시 차이

**성공 분기의 최종 상태 (카드 success 또는 일반 결제 기준)**

| 대상 | 최종 상태 | 근거 |
|---|---|---|
| `Order.status` | **`PENDING_PAYMENT`** (결제가 완료됐는데도) | `OrderCommandService.java:244`, `createInstantOrder` 안에 상태 변경 없음 |
| `Payment` | `PAID` (카드는 PG success일 때, 일반은 항상) | `PaymentCommandService.java:204`, `:314` |
| `OrderShipment` | `PENDING` | `OrderShipmentCommandService.java:67` |
| `SaleBid` | `MATCHED`, `order` 연결 | `SaleBid.java:58-61` |
| `Sale` | `SOLD` | `PaymentCommandService.java:404` |
| `OrderBid` | `MATCHED`, `isInstantPurchase = true`, `order`·`sale` 연결 | `OrderBid.java:75`, `:97-99`, `OrderBidCommandService.java:196-205` |
| 알림 | 구매자 1건, 판매자 1건 | `PaymentCommandService.java:438`, `:449` |

**창고 보관을 선택했을 때**
- 요청 DTO의 `warehouseStorage`는 `OrderBidCommandController`에서 `OrderBidCommandService`로 넘어가고 (`OrderBidCommandController.java:104-106`, `OrderBidCommandService.java:120`), 다시 `OrderCommandService.createInstantOrder`로 넘어간다 (`OrderBidCommandService.java:133-138`).
- **그러나 `createInstantOrder`는 그 매개변수 `isWarehouseStorage`(`OrderCommandService.java:221`)를 본문에서 사용하지 않는다.** 구매자의 선택은 즉시 구매 흐름에서 무시된다.
- `isWarehouseStorage`를 읽는 곳은 `processPaymentAndShipment`뿐이다 (`OrderCommandService.java:163-172`). 이 경로는 주문 상태를 `PAYMENT_COMPLETED → PREPARING → IN_WAREHOUSE → COMPLETED`로 바꾸고 `WarehouseStorage`를 새로 만든다. 즉시 구매 경로에서는 이런 처리가 없다.
- 즉시 구매에서 창고 관련으로 바뀌는 것은 **판매자 쪽 `Sale.isWarehouseStorage`** 값뿐이다 (`OrderCommandService.java:291-293`). 이 값이 true이면 기존 `WarehouseStorage`의 상태만 `ASSOCIATED_WITH_ORDER`로 바뀌고, 주문과의 연결(`WarehouseStorage.order`)은 설정되지 않는다. `WarehouseStorage.assignOrder`(`WarehouseStorage.java:48-52`)는 이 경로에서 호출되지 않는다. 해당 `WarehouseStorage`가 없으면 예외가 나서 주문 전체가 롤백된다 (`WarehouseStorageQueryService.java:30-33`, `WarehouseStorageCommandService.java:127`).
- 따라서 구매자가 "창고 보관"을 선택해도 주문 상태, 주문과 창고의 연결, 배송 정보 어느 것도 달라지지 않는다. 배송 정보(`OrderShipment`)는 항상 생성된다 (`OrderCommandService.java:264-271`).

## 메서드 이름, 주석과 실제 동작이 다른 곳

1. `OrderBidCommandController.java:83` Javadoc과 `:101` 변수명 `orderId`: "주문 ID"라고 하지만 실제 값은 `OrderBid` ID다.
2. `OrderCommandService.java:221`: `isWarehouseStorage` 매개변수가 있으나 본문에서 쓰지 않는다.
3. `PaymentCommandService.java:82`: "알림 전송 및 Sale 상태 업데이트"는 결제 상태가 `PENDING`이어도 실행된다.

## 검증 한계

- 정적 코드 읽기로만 답했다. 테스트나 실행은 하지 않았다.
- PortOne 응답 형식(`status` 값, `code` 타입)은 저장소 밖 정보라서 코드가 기대하는 값만 기준으로 삼았다.
- 중복 구매와 금액 불일치는 코드 경로에서 검사가 없다는 사실만 확인했다. 실제 악용 가능성은 실행으로 검증하지 않았다.
