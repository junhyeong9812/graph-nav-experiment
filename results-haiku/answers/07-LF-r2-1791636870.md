# 질문: 즉시 구매는 어떻게 처리되나

조사 방법: `NAV.md` → `nav/flow-trade.md`, `nav/order.md`, `nav/sale.md`, `nav/payment.md`, `nav/notification.md`로 큰 흐름을 잡은 뒤, 각 단계와 줄 번호를 실제 코드에서 다시 확인했다. 코드는 수정하지 않았다. 아래 경로는 저장소 루트 기준이며 `src/main/java/com/fream/back/`는 `main/`으로 줄여 쓰지 않고 그대로 적었다.

---

## 1. 진입점, 처리 방식, 응답 ID

- **진입점**: `POST /order-bids/instant`. 클래스 매핑 `@RequestMapping("/order-bids")`(`src/main/java/com/fream/back/domain/order/controller/command/OrderBidCommandController.java:22`), 메서드 `@PostMapping("/instant")`(`OrderBidCommandController.java:89-90`). 본문은 `@Valid InstantOrderRequestDto`(`OrderBidCommandController.java:90`)이고, 필드는 `saleBidId`, `addressId`, `warehouseStorage`, `paymentRequest`다(`src/main/java/com/fream/back/domain/order/dto/InstantOrderRequestDto.java:18-29`).
- **처리 단계**
  1. 컨트롤러: 이메일을 SecurityContext에서 추출하고(`OrderBidCommandController.java:92-93`), `enrichPaymentRequest`로 `userEmail`을 설정하며 `orderId`는 null로 둔다(`OrderBidCommandController.java:119-123`). 그다음 서비스를 호출한다(`OrderBidCommandController.java:101-106`).
  2. `OrderBidCommandService.createInstantOrderBid`(`src/main/java/com/fream/back/domain/order/service/command/OrderBidCommandService.java:118-119`, `@Transactional`은 118행): 입력 검증(`OrderBidCommandService.java:123`, `:154-167`), 구매자 조회, SaleBid 조회·검증(`OrderBidCommandService.java:172-184`).
  3. `OrderCommandService.createInstantOrder`(`src/main/java/com/fream/back/domain/order/service/command/OrderCommandService.java:219-220`, `@Transactional`은 219행): 주소 조회 → Order 생성 → OrderItem → OrderShipment → SaleBid 매칭 → 창고 상태 변경 → 결제. 모두 같은 트랜잭션이다.
  4. `OrderBidCommandService.createInstantOrderBid(order, saleBid, sale)`(private, `OrderBidCommandService.java:189-207`): OrderBid 생성·저장(`OrderBidCommandService.java:206`).
- **동기 / 비동기**: **동기**다. HTTP 요청 스레드 안에서 PortOne 외부 호출까지 끝낸 뒤 응답한다. Kafka는 쓰지 않는다. 대조적으로 일반 입찰의 결제 요청 `POST /orders/{orderId}/process-payment-shipment`는 Kafka 발행 후 202를 돌려준다(`src/main/java/com/fream/back/domain/order/controller/command/OrderCommandController.java:42`). 즉시 구매는 외부 HTTP 호출을 DB 트랜잭션 안에서 수행하는 구조다.
- **응답 ID**: **OrderBid의 ID**다. 컨트롤러 변수명은 `orderId`지만(`OrderBidCommandController.java:101-106`), 실제 값은 `createInstantOrderBid(...).getId()`, 즉 OrderBid ID다. Order ID는 응답에 없다. 응답은 `ResponseDto.success(orderId, ...)`로 HTTP 200이다(`OrderBidCommandController.java:109`).

## 3. 결제 수단별 결과, 최종 성공 여부, 카드 결제 실패 시

결제 진입점은 `PaymentCommandService.processPayment`(`src/main/java/com/fream/back/domain/payment/service/command/PaymentCommandService.java:57`)이다. 검증은 `orderId` 일치, 이메일 일치, `paidAmount > 0`뿐이다(`PaymentCommandService.java:117-145`, 금액 검사는 `:142`).

**[중요] 결제 금액을 상품 가격과 대조하지 않는다.**
- 실제 결제 금액은 클라이언트가 보낸 `paidAmount`를 그대로 쓴다(`PaymentCommandService.java:179` 카드 호출, `:193`/`:255`/`:308` 저장).
- payment 도메인 어디에도 `bidPrice`나 `order.totalAmount`과 비교하는 코드가 없다(검색 결과 없음).
- `@Min(100)`(`src/main/java/com/fream/back/domain/payment/dto/PaymentRequestDto.java:51-52`)은 `InstantOrderRequestDto.paymentRequest`에 `@Valid`가 없어서(`InstantOrderRequestDto.java:28-29`) 중첩 검증이 실행되지 않는다. 그래서 1원도 통과할 수 있다.

**결제 수단별**

- **CARD** (`PaymentCommandService.java:157`, PortOne 호출 `:179`)
  - PortOne이 실패로 응답하는 경우: HTTP가 200이 아니거나 `code != 0`이면 `PortOneApiClient.java:270-274`에서 `PaymentProcessingException`을 던진다. 이것이 `processPayment` → `OrderCommandService.java:305-308`의 `OrderPaymentProcessingFailedException` → `OrderBidCommandService.java:145-147`, `:212-218`을 거쳐 그대로 전파된다. `GlobalException`은 `RuntimeException`이므로(`src/main/java/com/fream/back/global/exception/GlobalException.java:10`) `@Transactional`이 롤백한다. 결과적으로 Order, OrderItem, OrderShipment, SaleBid 매칭, 창고 상태 변경, 알림, Sale SOLD가 모두 취소된다. 응답은 `GlobalExceptionHandler.handleOrderException`(`src/main/java/com/fream/back/global/exception/GlobalExceptionHandler.java:326`)이 만든다.
  - **허점**: `code == 0`인데 `status != "success"`인 경우에는 실패로 처리되지 않는다. `PaymentCommandService.java:203`은 `"success".equals(status)`일 때만 `PAID`로 바꾸고, 그 외에는 `CardPayment`를 `PENDING`으로 저장한다(`Payment.java:44`). 그런데 `isSuccess`는 생성 시점에 금액이 0보다 크면 true가 된다(`Payment.java:60-63`, `CardPayment.java:38`). 그러면 `processPayment`가 정상 반환하고, Sale SOLD, 알림, OrderBid 생성이 모두 커밋되어 HTTP 200이 된다.
  - 검증 한계: PortOne 응답의 실제 성공 `status` 값이 `"success"`인지는 이 저장소만으로 확인할 수 없다. 외부 지식으로는 PortOne v1이 결제 완료를 `paid`로 돌려주는 것으로 알고 있으니 실제 응답으로 확인이 필요하다. 그 값이 `paid`라면 카드 결제는 항상 `PENDING`으로 남고 `isSuccess`만 true가 된다.
- **ACCOUNT** (`PaymentCommandService.java:236`)
  - `AccountPayment`의 기본 상태는 `PENDING`인데(`Payment.java:44`), `PaymentCommandService.java:260`에서 `updateStatus(PENDING)`을 호출한다. `PaymentStatus`는 PENDING에서 PAID로만 전이할 수 있으므로(`src/main/java/com/fream/back/domain/payment/entity/PaymentStatus.java`, PENDING case) `IllegalStateException`이 나고, `:277`에서 `PaymentProcessingException`으로 감싸져 전체 롤백된다. **계좌이체 즉시 구매는 항상 실패한다.**
- **GENERAL** (`PaymentCommandService.java:290`)
  - `impUid`가 필수이고(`PaymentCommandService.java:298-299`), PortOne 검증 호출 없이 `updateStatus(PAID)`(`:314`)와 `isSuccess`를 설정한다. 클라이언트가 보낸 `impUid`를 그대로 신뢰한다. 이 경로는 끝까지 성공한다.

**즉시 구매가 "끝까지" 성공하는가**
- 결제 단계까지는 CARD(`code == 0`)와 GENERAL이 성공해서 HTTP 200과 OrderBid ID를 돌려준다.
- 그러나 **Order는 `PENDING_PAYMENT`에 머문다.** 이후 배송 단계가 막힌다. 구매자 송장 등록은 `OrderShipmentCommandService.updateTrackingInfo`(`src/main/java/com/fream/back/domain/shipment/service/command/OrderShipmentCommandService.java:239`)에서 `order.updateStatus(IN_TRANSIT)`(`OrderShipmentCommandService.java:260`)를 호출한다. 그런데 `PENDING_PAYMENT`에서 허용된 전이는 `PAYMENT_COMPLETED`, `COMPLETED`, `IN_WAREHOUSE`뿐이라(`src/main/java/com/fream/back/domain/order/entity/OrderStatus.java:24`) `IN_TRANSIT`은 거부된다. 즉시 구매 주문은 배송 등록 단계에서 실패하며, 주문 흐름이 끝나지 않는다.

## 4. 누가 어떤 알림을 받나, 언제, 어떻게

- **수신자와 내용** (`PaymentCommandService.java:434-460`, 모두 `SHOPPING / BID`)
  - 구매자(`order.getUser()`): "결제가 완료되었습니다. 주문 ID: …" (`PaymentCommandService.java:442`)
  - 판매자(`sale.getSeller()`): "구매자가 결제를 완료하였습니다. 판매 ID: …" (`PaymentCommandService.java:453`)
- **시점**: `processPayment` 안에서 결제 저장 직후 `notifyUsersAndUpdateSaleStatus`(`PaymentCommandService.java:383`, 호출 `:83`)가 실행된다. 같은 트랜잭션이라 커밋 전에 저장된다. 카드 상태가 `PENDING`이어도 "결제가 완료되었습니다"가 나간다.
- **방식**: `NotificationCommandService.createNotification`(`src/main/java/com/fream/back/domain/notification/service/command/NotificationCommandService.java:44-59`)이 DB에 저장하고 `sendRealTimeNotification`(`NotificationCommandService.java:303-307`)을 호출한다. 이 함수는 Redis 키 `WebSocket:User:{email}`이 있을 때만 STOMP `/user/{email}/queue/notifications`로 보낸다.
- **실시간 푸시는 실제로 나가지 않을 가능성이 높다.** 이 키를 쓰는 곳은 `WebSocketAuthInterceptor.afterHandshake` 한 곳뿐이다(`src/main/java/com/fream/back/global/config/websocket/WebSocketAuthInterceptor.java:128-137`). 이 메서드는 servlet request attribute `"attributes"`를 읽는데, 저장소 안에 그 attribute를 설정하는 코드가 없다(`setAttribute` 검색 결과 없음). 그래서 키가 생기지 않고 `sendRealTimeNotification`은 전송을 건너뛴다. 런타임 확인은 필요하다. 그 전까지 구매자와 판매자는 DB에 쌓인 알림을 `GET /notifications/...`와 `GET /notifications/count/unread`로 조회해야 안다.
- **실패 처리**: `sendNotifications`의 catch(`PaymentCommandService.java:455-460`)가 알림 실패를 삼켜서 로그만 남긴다.
- 즉시 구매 경로에서는 `notification-topic` Kafka나 `OrderEventConsumer`의 Map 푸시를 쓰지 않는다.

## 5. 처리가 끝났을 때 주문 최종 상태, 창고 보관 선택 시 차이

**최종 Order 상태: `PENDING_PAYMENT`.** 성공 경로에서도 바뀌지 않으며, 3번에서 본 대로 배송 등록에서 막힌다.

**"창고 보관"을 선택했을 때**

- **구매자 선택은 무시된다.** 요청의 `warehouseStorage`는 `OrderBidCommandService.createInstantOrderBid`의 `isWarehouseStorage`(`OrderBidCommandService.java:120`)로 전달되고(`OrderBidCommandService.java:137`), `createInstantOrder`의 `isWarehouseStorage` 파라미터(`OrderCommandService.java:221`)는 본문에서 사용되지 않는다. 실제 분기는 `sale.isWarehouseStorage()`(`OrderCommandService.java:292`)이며, 이 값은 판매자가 판매 입찰을 만들 때 정한 값이다(`src/main/java/com/fream/back/domain/sale/service/command/SaleCommandService.java:107`).
- **판매 측 플래그가 true인 경우**: 창고 상태가 `IN_STORAGE → ASSOCIATED_WITH_ORDER`로 바뀐다(`OrderCommandService.java:293`, 전이 허용은 `src/main/java/com/fream/back/domain/warehouseStorage/service/command/WarehouseStorageCommandService.java:240-241`).
- **창고 행이 있어야 한다.** `WarehouseStorageQueryService.findBySale`(`src/main/java/com/fream/back/domain/warehouseStorage/service/query/WarehouseStorageQueryService.java:30-32`)은 행이 없으면 `WarehouseStorageNotFoundException`을 던지고, 전체가 롤백된다. 창고 행은 판매자 발송 때만 만들어진다(`src/main/java/com/fream/back/domain/shipment/service/command/SellerShipmentCommandService.java:79`).
- **기본 발송 경로로는 창고 행이 남지 않는다.** `POST /sales/{saleId}/shipment`는 `SellerShipmentCommandService`가 창고 행을 만들고 Sale을 `IN_STORAGE`로 바꾼 뒤(`SellerShipmentCommandService.java:79-82`), `SaleCommandService.createSellerShipment`가 `IN_TRANSIT`으로 바꾸려 한다. `IN_STORAGE → IN_TRANSIT`은 허용되지 않으므로(`src/main/java/com/fream/back/domain/sale/entity/SaleStatus.java:20`) 예외가 나고 전체가 롤백된다. 창고 판매는 `POST /shipments/seller`(`src/main/java/com/fream/back/domain/shipment/controller/command/SellerShipmentCommandController.java:31-38`)로만 창고 행과 `IN_STORAGE`를 남길 수 있다. 이 컨트롤러는 Sale 상태 서비스를 호출하지 않는다.
- **구매자 측 창고 행은 즉시 구매에서 만들지 않는다.** `createOrderStorage` 호출은 `OrderEventConsumer.java:199`(Kafka 경로)와 미사용 `processPaymentAndShipment`(`OrderCommandService.java:170`)에만 있다. 따라서 즉시 구매 주문은 `IN_WAREHOUSE`에 도달하지 않고 `PENDING_PAYMENT`에 머문다.

## 코드 동작과 이름·주석이 다른 부분 (정리)

1. `createInstantOrderBid` 응답의 변수명 `orderId`는 실제로 OrderBid ID다(`OrderBidCommandController.java:101-106`).
2. `createInstantOrder`의 `isWarehouseStorage` 파라미터는 선언만 되고 쓰이지 않는다(`OrderCommandService.java:221`).
3. `createCardPayment`의 `"success"` 판정과 `updateSuccessStatus(true)`는 결제 "성공"을 뜻하는 것처럼 보이지만, `isSuccess`는 금액 기준으로 생성 때 이미 true다(`Payment.java:60-63`). 실패 응답도 `isSuccess = true`가 될 수 있다(`PaymentCommandService.java:203`).
4. `notifyUsersAndUpdateSaleStatus`는 주석에서 "핵심 기능이 아니므로" 예외를 던지지 않는다고 적는다(`PaymentCommandService.java:421-423`). 그래서 Sale SOLD 처리가 실패해도 주문은 성공으로 커밋된다. 이것은 핵심 상태 변경을 삼키는 구조다.
5. `PaymentRequestDto`의 `@Min(100)`은 중첩 검증이 없어서 실제로는 적용되지 않는다(`PaymentRequestDto.java:51`, `InstantOrderRequestDto.java:28-29`).

## 추가 관찰 (이번 질문 범위 밖, 참고용)

- 즉시 구매 주문은 `PENDING_PAYMENT`로 남는다. `OrderEventConsumer`의 중복 처리 판정은 `order.getStatus() != PENDING_PAYMENT`일 때만 "이미 처리됨"으로 본다(`src/main/java/com/fream/back/domain/order/service/kafka/OrderEventConsumer.java:72`, `:235-243`). 따라서 같은 Order ID로 `/orders/{id}/process-payment-shipment`가 다시 호출되면 중복 판정을 통과하고 결제가 다시 시도될 수 있다. 실제 재현은 하지 않았다.
