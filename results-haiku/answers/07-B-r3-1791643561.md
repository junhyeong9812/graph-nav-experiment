# 즉시 구매는 어떻게 처리되나

모든 근거 경로는 저장소 루트 기준이다. 경로 앞부분 `src/main/java/com/fream/back/domain/`은 아래에서 그대로 적었다. 코드를 읽어서 확인한 내용이며, 실행해 보지는 않았다.

---

## 1. 진입 API, 처리 단계, 동기/비동기, 응답 ID

- **진입점**: `POST /order-bids/instant`
  `src/main/java/com/fream/back/domain/order/controller/command/OrderBidCommandController.java:89-90`
- **요청 본문**: `InstantOrderRequestDto` (`saleBidId`, `addressId`, `warehouseStorage`, `paymentRequest`)
  `src/main/java/com/fream/back/domain/order/dto/InstantOrderRequestDto.java:152-163`
- **처리 단계**
  1. 컨트롤러가 SecurityContext에서 구매자 이메일을 꺼낸다 (`OrderBidCommandController.java:92`).
  2. `paymentRequest`에 구매자 이메일을 넣고 `orderId`를 null로 둔다 (`OrderBidCommandController.java:98`, `:119-123`).
  3. `OrderBidCommandService.createInstantOrderBid`를 호출한다 (`src/main/java/com/fream/back/domain/order/service/command/OrderBidCommandService.java:119-149`, `@Transactional`).
  4. 서비스 안에서 입력 검증 (`OrderBidCommandService.java:123`, `:154-167`), 구매자 조회 (`:126`), 판매 입찰 조회 (`:129`, `:172-184`)를 한다.
  5. `OrderCommandService.createInstantOrder`로 주문, 주문 항목, 배송, 판매 입찰 상태, 결제를 처리한다 (`OrderBidCommandService.java:133`).
  6. 마지막으로 `OrderBid`를 만들고 저장한다 (`OrderBidCommandService.java:142`, `:189-207`).
- **동기/비동기**: **동기**다. 한 HTTP 요청 안에서 하나의 DB 트랜잭션으로 끝까지 처리하고, PG 호출도 그 안에서 한다 (`src/main/java/com/fream/back/domain/payment/service/command/PaymentCommandService.java:179`). Kafka를 쓰지 않는다. Kafka를 쓰는 것은 별도 경로인 `POST /orders/{orderId}/process-payment-shipment`이다 (`src/main/java/com/fream/back/domain/order/controller/command/OrderCommandController.java:54`). 즉시 구매는 이 경로를 타지 않는다.
- **응답 ID**: **`OrderBid`의 ID**이며 주문(`Order`) ID가 아니다.
  - `createInstantOrderBid`의 반환 타입은 `OrderBid`이고 (`OrderBidCommandService.java:119`), 컨트롤러는 `.getId()`를 응답으로 준다 (`OrderBidCommandController.java:101-109`).
  - 컨트롤러의 Javadoc은 "생성된 주문 ID"라고 적고 (`OrderBidCommandController.java:83`), 변수명도 `orderId`다 (`:101`). 주석과 실제 값이 다르다.
  - HTTP 상태는 성공 시 200이다. 응답 메시지는 "즉시 구매가 성공적으로 처리되었습니다."다 (`:109`).

중요한 점:

- **판매 입찰 상태를 검사하지 않는다.** `SaleBidQueryService.findById`는 상태와 무관하게 조회만 한다 (`src/main/java/com/fream/back/domain/sale/service/query/SaleBidQueryService.java:21-24`). `getSaleBidAndValidate`도 `sale` null 여부만 본다 (`OrderBidCommandService.java:172-184`). 그래서 이미 `MATCHED`나 `SOLD`인 판매 입찰도 다시 "즉시 구매"할 수 있다. 자기 판매 입찰을 사는 것을 막는 검사도 없다. DB의 unique 제약 여부는 코드만으로 알 수 없다.
- `Sale.updateStatus(SOLD)`는 전이 규칙을 확인하지 않고 바로 덮어쓴다 (`Sale.java:73-75`). `SaleStatus.canTransitionTo`를 쓰지 않는다 (`src/main/java/com/fream/back/domain/sale/entity/SaleStatus.java`).
- 결제 실패 시 위의 모든 변경은 롤백된다. 3번 문항을 보라.

## 3. 결제 수단별 결과, 끝까지 성공하는가, PG 실패 시

공통 분기는 `PaymentCommandService.processPayment`다 (`src/main/java/com/fream/back/domain/payment/service/command/PaymentCommandService.java:57-80`).

**금액 검증**: `validatePaymentRequest`는 `paidAmount > 0`만 확인한다 (`PaymentCommandService.java:142-145`). 주문 금액(`totalAmount`)과 비교하지 않는다. 카드 결제는 클라이언트가 보낸 `paidAmount`를 그대로 결제한다 (`:179`, `:193`). `PaymentRequestDto`의 `@Min(100)`도 적용되지 않는데, `paymentRequest` 필드에 `@Valid`가 없어서 중첩 검증이 실행되지 않기 때문이다 (`InstantOrderRequestDto.java:162-163`, `src/main/java/com/fream/back/domain/payment/dto/PaymentRequestDto.java:51`).

### 카드 (CARD)

- 구매자의 `PaymentInfo`를 `user+id`로 조회한다 (`PaymentCommandService.java:166`).
- PG 호출: `PortOneApiClient.processCardPayment` (`src/main/java/com/fream/back/domain/payment/portone/PortOneApiClient.java:229`).
- **PG가 성공**: PortOne 응답의 `code == 0`이고 `status == "success"`일 때만 `PAID`, `isSuccess=true`가 된다 (`PaymentCommandService.java:203-206`). 코드가 `PAID`로 바꾸는 조건은 이 한 가지뿐이다. 그 밖에 어떤 값을 받는지는 저장소 밖의 PortOne 응답에 달려 있다.
- **PG가 실패로 응답 (HTTP 200이 아니거나 `code != 0`)**: `PaymentProcessingException`을 던진다 (`PortOneApiClient.java:270-275`). 예외는 `createCardPayment` → `processPayment`로 그대로 올라간다 (`PaymentCommandService.java:180-181`, `:89-94`, `:218-219`). `createInstantOrder`에서 `OrderPaymentProcessingFailedException`(ORD005, HTTP 500)으로 감싼다 (`OrderCommandService.java:305-308`, `src/main/java/com/fream/back/domain/order/exception/OrderErrorCode.java:44`). 이 예외는 `OrderBidCommandService`에서 다시 던져지고 (`OrderBidCommandService.java:213-214`) `@Transactional`에 의해 **전체 롤백**된다. 주문, 주문 항목, 배송, `SaleBid` 매칭, 창고 상태가 모두 원래대로 돌아간다. 응답은 `GlobalExceptionHandler.handleOrderException`이 만든다 (`src/main/java/com/fream/back/global/exception/GlobalExceptionHandler.java:325-338`).
- **PG 네트워크 오류 (`RestClientException`)**: `PaymentApiException`을 던지며 위와 같이 롤백된다 (`PortOneApiClient.java:288-291`).
- **PG가 `code=0`으로 응답했지만 `status != "success"`인 경우**: 예외가 없다. `CardPayment`는 `PENDING`, `isSuccess=false`로 저장된다 (`Payment.java:39`, `:44`). 그런데 흐름은 그대로 계속 진행된다. 판매는 `SOLD`가 되고, 알림이 나가고, `OrderBid`가 만들어지고, 응답은 200 "즉시 구매가 성공적으로 처리되었습니다."다. 즉 **결제가 확정되지 않았는데 성공으로 응답한다.**

### 계좌이체 (ACCOUNT)

- 은행명만 검증한다 (`validateBank`, `PaymentCommandService.java:243-248`, `:470-488`). PG를 호출하지 않는다.
- `AccountPayment`를 `PENDING`으로 저장한다 (`PaymentCommandService.java:260-262`).
- 예외가 없으므로 흐름이 끝까지 간다. 판매는 `SOLD`, 알림은 발송, 응답은 200 성공이다. 그런데 결제는 `PENDING`이다.
- 입금 확인 후 `PAID`로 바꾸는 코드가 없다. `PaymentCommandService.updatePaymentStatus` (`:498`)는 호출하는 곳이 없다. 따라서 **계좌이체 즉시 구매는 입금 전에 판매 완료와 "결제가 완료되었습니다" 알림이 나간다.**

### 일반 결제 (GENERAL)

- PG 호출이 없다. 클라이언트가 보낸 `impUid`, `pgProvider`, `receiptUrl`, `paidAmount`를 그대로 저장한다 (`PaymentCommandService.java:297-309`). `impUid`가 비어 있는지만 확인한다 (`:297-300`).
- 바로 `PAID`, `isSuccess=true`로 만든다 (`:313-314`).
- 서버에서 `impUid`나 금액을 PG에 대조하지 않는다. **가짜 `impUid`로도 즉시 구매가 성공한다.** 보안상 가장 큰 문제다.

### 끝까지 성공하는가

- **카드**: PG가 성공하면 끝까지 성공한다. PG가 예외로 실패하면 롤백되어 실패한다. PG가 `code=0`이면서 `status`가 `"success"`가 아니면 성공 응답이 나가지만 결제는 `PENDING`이다.
- **계좌이체**: 성공 응답이 나가지만 결제는 `PENDING`이다.
- **일반 결제**: 검증 없이 성공한다.

## 4. 누가 어떤 알림을 받나, 언제, 어떻게

알림은 `PaymentCommandService.processPayment`의 `notifyUsersAndUpdateSaleStatus` 안에서 나간다 (`PaymentCommandService.java:83`, `:383-426`, 호출은 결제 유형과 관계없이 항상 실행된다).

- **구매자** (`order.getUser()`): 카테고리 `SHOPPING`, 타입 `BID`, 내용 "결제가 완료되었습니다. 주문 ID: {orderId}" (`PaymentCommandService.java:436-443`).
- **판매자** (`sale.getSeller()`): 같은 카테고리와 타입, 내용 "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}" (`PaymentCommandService.java:447-454`).
- **시점**: `processPayment` 안에서, 즉 DB 트랜잭션이 커밋되기 전에 동기적으로 나간다. 결제 상태가 `PENDING`이어도(계좌이체, 카드 `code=0` 비성공) 나간다.
- **방식**: `NotificationCommandService.createNotification`이 알림 행을 DB에 저장하고 (`src/main/java/com/fream/back/domain/notification/service/command/NotificationCommandService.java:44-67`, `:53`), 이어서 `sendRealTimeNotification`으로 WebSocket 메시지를 보낸다 (`:57`, `:303-`). 이 메시지는 Redis에 해당 사용자의 연결 키가 있을 때만 보낸다. 이메일, SMS, 푸시는 없다.
- **롤백 주의**: 알림 WebSocket 메시지는 트랜잭션 커밋 전에 나간다. 이후 `OrderBid` 저장 (`OrderBidCommandService.java:206`)에서 실패하면 DB의 알림 행은 롤백되지만 WebSocket 메시지는 이미 나간 뒤다.
- `notifyUsersAndUpdateSaleStatus`는 예외를 모두 삼킨다 (`PaymentCommandService.java:421-425`). 알림이나 판매 상태 변경이 실패해도 구매는 성공으로 처리된다.
- `@Async`, `@TransactionalEventListener`, `@EventListener`는 이 경로에 없다. 코드에서 확인했다.

## 5. 처리가 끝난 뒤 주문의 최종 상태, 창고 보관을 고르면 달라지는 것

### 최종 상태

- `Order.status` = **`PENDING_PAYMENT`** (`OrderCommandService.java:244`). 이 경로는 주문 상태를 바꾸지 않는다. 결제가 `PAID`여도 주문은 `PENDING_PAYMENT`로 남는다.
- `Payment.status`: 일반 결제와 카드 PG 성공은 `PAID`. 계좌이체와 카드 `code=0` 비성공은 `PENDING`.
- `OrderShipment.status` = `PENDING` (`OrderShipmentCommandService.java:67`).
- `OrderBid.status` = `MATCHED`, `isInstantPurchase = true` (`OrderBidCommandService.java:196`, `:205`).
- `SaleBid.status` = `MATCHED`, `SaleBid.order` = 새 주문 (`OrderCommandService.java:279-280`).
- `Sale.status` = `SOLD` (`PaymentCommandService.java:404` 또는 `:419`).

### 창고 보관을 선택한 경우

- 구매자가 보낸 `warehouseStorage` 값은 **이 경로에서 아무 효과가 없다.**
  - 컨트롤러는 로그에만 찍는다 (`OrderBidCommandController.java:95`).
  - 서비스로 넘어가지만 (`:105`, `OrderBidCommandService.java:119`, `:137`), `OrderCommandService.createInstantOrder`의 `isWarehouseStorage` 매개변수(`OrderCommandService.java:221`)는 본문에서 한 번도 읽지 않는다.
- 그래서 구매자 보관 선택 때문에 달라지는 것은 없다.
  - 구매자용 `WarehouseStorage`를 만들지 않는다.
  - `Order`를 `IN_WAREHOUSE`나 `COMPLETED`로 바꾸지 않는다.
  - 배송 정보는 그대로 만들어진다 (`OrderCommandService.java:264-275`).
- 창고 상태에 영향을 주는 것은 **판매자의 `Sale.isWarehouseStorage`** 하나뿐이다 (`OrderCommandService.java:291-294`). 이 값이 true이면 기존 `WarehouseStorage`를 `ASSOCIATED_WITH_ORDER`로 바꾼다. 해당 `WarehouseStorage`가 없으면 예외가 나고 롤백된다 (`WarehouseStorageQueryService.java:30-33`).
- 비교: `processPaymentAndShipment`의 창고 보관 분기는 `IN_WAREHOUSE`를 거쳐 `COMPLETED`로 만들고 `WarehouseStorage`를 새로 만든다 (`OrderCommandService.java:163-172`). 이 분기는 즉시 구매 경로가 아니다.

## 주석/이름과 실제 동작이 다른 곳 (요약)

1. 응답 ID: 주석은 "주문 ID", 변수는 `orderId`, 실제 값은 `OrderBid` ID다 (`OrderBidCommandController.java:83`, `:101-109`).
2. `notifyUsersAndUpdateSaleStatus`는 "결제 완료 알림"이라고 하지만, 결제가 `PENDING`이어도 호출되고 판매를 `SOLD`로 바꾼다 (`PaymentCommandService.java:378-383`).
3. 즉시 구매 응답 메시지 "성공적으로 처리되었습니다"는 계좌이체와 카드 `code=0` 비성공에도 나간다 (`OrderBidCommandController.java:109`).
4. `isWarehouseStorage` 매개변수는 받지만 쓰지 않는다 (`OrderCommandService.java:221`).
5. Javadoc의 `@throws SaleBidNotFoundException`과 `saleBid == null` 검사(`OrderBidCommandService.java:174`)는 실제로 닿지 않는다. `findById`는 없을 때 `null`이 아니라 `IllegalArgumentException`을 던지고 (`SaleBidQueryService.java:23`), 이것은 `OrderBidCreationFailedException`으로 감싸진다 (`OrderBidCommandService.java:217`).
6. `InstantOrderRequestDto.paymentRequest`의 검증 어노테이션은 `@NotNull` 하나뿐이고 `@Valid`가 없어서 결제 금액 최소값(100원)과 결제 유형 검증이 실행되지 않는다 (`InstantOrderRequestDto.java:162-163`).

## 한계

- PortOne의 실제 응답 값(`status` 등)은 저장소 밖에 있다. 카드 `code=0` 비성공 경우가 실제로 얼마나 일어나는지는 확인하지 못했다.
- DB 제약(unique 등)과 실제 설정(프로파일)은 확인하지 않았다.
- 실행하지 않고 코드만 읽었다.
