# 즉시 구매는 어떻게 처리되나

경로 약어: `D` = `src/main/java/com/fream/back/domain`

## 1. 진입점, 처리 단계, 동기/비동기, 응답 ID

- 진입점: `POST /order-bids/instant` → `OrderBidCommandController.createInstantOrderBid` (`D/order/controller/command/OrderBidCommandController.java:22`, `:89-90`).
- 처리 순서 (모두 한 HTTP 요청, 한 DB 트랜잭션 안에서 동기 실행):
  1. 로그인 이메일 추출 (`:92`), 결제 정보에 이메일 주입·`orderId=null` 설정 (`:98`, `:119-123`).
  2. `OrderBidCommandService.createInstantOrderBid` 호출 (`D/order/service/command/OrderBidCommandService.java:118-120`, `@Transactional`).
  3. 입력값 검증 (`OrderBidCommandService.java:123`, `:154-167`). 배송지 ID와 결제 정보가 null이면 실패.
  4. 구매자 조회 (`:126`), 판매 입찰 조회 (`:129`, `:172-184`).
  5. `OrderCommandService.createInstantOrder` 호출 (`:133`, 정의는 `D/order/service/command/OrderCommandService.java:219-319`): 주소 조회 → Order 저장 → OrderItem → 배송정보 → 판매 입찰 매칭 → 창고 상태 → 결제 처리.
  6. `OrderBid` 생성·저장 (`OrderBidCommandService.java:142`, `:189-207`).
- 비동기 구간은 없다. 이 경로에는 Kafka 프로듀서 호출이 없다. Kafka를 쓰는 `OrderEventProducer`는 `OrderCommandController.java:54`(다른 엔드포인트)에만 있다.
- 응답 ID는 **OrderBid의 ID**다. `createInstantOrderBid(...).getId()`를 반환한다 (`OrderBidCommandController.java:101-109`). Order ID가 아니다. 같은 메서드 주석은 "생성된 주문 ID"라고 적혀 있어 주석과 다르다 (`OrderBidCommandController.java:83`).
- 응답 메시지 "즉시 구매가 성공적으로 처리되었습니다"는 결제 상태와 무관하게 항상 나간다 (`:109`). 계좌이체·실패 카드 케이스도 포함된다 (3번 참고).

## 2. 생성되는 엔티티와 상태 변화 순서

한 트랜잭션 안에서 아래 순서로 일어난다. 각 단계 직후 상태를 적었다.

| 순서 | 엔티티 | 동작 | 직후 상태 | 근거 |
|---|---|---|---|---|
| 1 | Order | INSERT | `status=PENDING_PAYMENT`, `totalAmount=saleBid.bidPrice` | `D/order/service/command/OrderCommandService.java:241-247` |
| 2 | OrderItem | INSERT (productSize, price=bidPrice) | - | `OrderCommandService.java:255`, `D/order/service/command/OrderItemCommandService.java:34-` |
| 3 | OrderShipment | INSERT (주소는 `AddressQueryService` 결과) | `status=PENDING` | `OrderCommandService.java:238`, `:264-271`; `D/shipment/service/command/OrderShipmentCommandService.java:61-68` |
| 4 | SaleBid | `assignOrder(order)` + `updateStatus(MATCHED)`, `entityManager.flush()` | `order=새 Order`, `status=MATCHED` | `OrderCommandService.java:279-283`; `D/sale/entity/SaleBid.java:166-169` |
| 5 | WarehouseStorage (Sale.isWarehouseStorage일 때만) | 기존 행의 status 변경 | `status=ASSOCIATED_WITH_ORDER` | `OrderCommandService.java:291-293`; `D/warehouseStorage/service/command/WarehouseStorageCommandService.java:117-140` (`:132`) |
| 6 | Payment (CardPayment / AccountPayment / GeneralPayment) | INSERT | 아래 3번 참고 | `D/payment/service/command/PaymentCommandService.java:57-107` |
| 7 | Notification ×2 | INSERT + WebSocket 푸시 | - | 아래 4번 참고 |
| 8 | Sale | `updateStatus(SOLD)` | `status=SOLD` | `PaymentCommandService.java:404`, `:419` |
| 9 | OrderBid | INSERT (user=구매자, sale=판매, `isInstantPurchase=true`, order 연결) | `status=MATCHED` | `OrderBidCommandService.java:192-206`; `D/order/entity/OrderBid.java:97-99` |

- 6~8 단계는 `OrderCommandService.java:305`의 `processPayment` 안에서 일어난다. 8단계 시점에는 9단계 OrderBid가 아직 없다. 그래서 `PaymentCommandService.java:388-391`은 `order.getOrderBid()`가 null이라 `saleBidQueryService.findByOrderId`로 SaleBid를 찾는다.
- 이 경로에서 **Order의 상태는 `PENDING_PAYMENT`에서 바뀌지 않는다.** 결제가 PAID여도 Order.status는 그대로다. `processPayment`도 Order 상태를 바꾸지 않고, `order.assignPayment`도 호출하지 않는다 (`OrderCommandService.java:305`에서 반환값을 버림). Payment 행은 `payment.order`로 Order와 연결된다 (`D/payment/entity/Payment.java:47-50`의 `assignOrder`).

## 3. 결제 수단별 결과, 끝까지 성공하는지, 카드 실패 응답 처리

결제 라우팅은 JSON `paymentType` (`D/payment/dto/PaymentRequestDto.java:20-25`, `:74-87`)으로 CARD / ACCOUNT / GENERAL 중 하나를 고르는 것이다 (`PaymentCommandService.java:67-80`).

공통 검증 (`PaymentCommandService.java:117-146`): `paidAmount > 0`만 확인한다 (`:142-145`). **Order.totalAmount나 bidPrice와 금액을 비교하지 않는다.** 카드 결제는 클라이언트가 보낸 `paidAmount`를 그대로 PG에 청구한다 (`:179`, `:193`).

- **카드(CARD)**
  - 결제 정보를 사용자 이메일로 조회 (`:166`), PortOne 카드 결제 호출 (`:179`).
  - `PortOneApiClient.processCardPayment`는 HTTP가 200이 아니거나 응답 `code != 0`이면 `PaymentProcessingException`을 던진다 (`D/payment/portone/PortOneApiClient.java:270-275`).
  - 정상 응답이면 `response.status == "success"`일 때만 `PAID`로 바꾸고 `updateSuccessStatus(true)` 한다 (`PaymentCommandService.java:203-206`). 그 외에는 엔티티 기본값 `PENDING`으로 저장된다 (`D/payment/entity/Payment.java:44`, 저장 `:208`).
  - **케이스 A: PG가 `code != 0`으로 실패를 던짐.** 예외가 `PaymentException`으로 그대로 전파된다 (`:218-219`, `:89-94`). `OrderCommandService.java:305-309`가 `OrderPaymentProcessingFailedException`(ORD005, `D/order/exception/OrderErrorCode.java:44`)으로 감싸 다시 던진다. 이 예외는 `RuntimeException`이라 `createInstantOrderBid`의 `@Transactional`이 롤백한다. 그 결과 Order, OrderItem, 배송정보, SaleBid 매칭, 창고 상태 변경이 모두 되돌아가고, Sale은 SOLD가 되지 않으며, 알림도 남지 않는다. 응답은 `src/main/java/com/fream/back/global/exception/GlobalExceptionHandler.java:325`의 `OrderException` 핸들러로 나간다. 즉 이 경우에만 "실패"로 끝난다.
  - **케이스 B: `code == 0`인데 `status != "success"`(예: 결제 실패 상태).** 예외가 없다. Payment는 `PENDING`으로 저장되고 (`:203` 조건 불충족), 이후 알림 전송, Sale `SOLD`, OrderBid `MATCHED`가 모두 진행된다. 응답은 "성공"이다. 즉 실패한 카드 결제가 즉시 구매 성공으로 기록된다. PortOne이 실패를 `code 0 + status failed`로 주는지는 저장소만으로는 확인할 수 없다. 다만 코드는 `status`를 검사하지 않고 `code`만 본다 (`PortOneApiClient.java:270`).
  - **케이스 C: PG 결제는 성공했지만 뒤 단계에서 예외 발생.** 트랜잭션은 롤백되는데 PG 결제는 취소되지 않는다. `handleRefundIfNecessary`(`PaymentCommandService.java:341`)가 정의만 되어 있고 호출되는 곳이 없다.
- **계좌이체(ACCOUNT)**
  - 은행명 검증 후 `AccountPayment`를 `PENDING`으로 저장한다 (`:243-260`). PG 호출이 없다.
  - 예외가 없으므로 **끝까지 성공한다.** Sale SOLD, OrderBid MATCHED, 성공 응답이 나가지만 입금은 아직 확인되지 않았다. 구매자 알림은 "결제가 완료되었습니다"라고 보낸다 (`:441-442`).
- **일반 결제(GENERAL)**
  - `impUid`가 비어 있지 않은지만 본다 (`:297-300`). PortOne을 호출해 검증하지 않는다. 금액도 검증하지 않는다.
  - `updateSuccessStatus(true)`, `updateStatus(PAID)`로 바로 PAID 처리한다 (`:313-314`).
  - 예외가 없으므로 **끝까지 성공한다.** 클라이언트가 보낸 임의의 `impUid`로 PAID 결제가 만들어진다.
- 판정 요약: 카드 정상 = 성공 / 카드 PG 예외 = 전체 롤백 후 실패 / 카드 `code 0`·비성공 status = 실패인데 성공 처리 / 계좌이체 = 성공(입금 대기) / 일반 결제 = 검증 없이 성공.

## 4. 알림 수신자, 시점, 방식

- 알림은 `PaymentCommandService.processPayment` 중간(`:83` → `notifyUsersAndUpdateSaleStatus`, `:383-426`) 안에서 `sendNotifications`(`:434-461`)로 보낸다.
- 수신자와 내용
  - 구매자: `"결제가 완료되었습니다. 주문 ID: ..."` (`:438-443`)
  - 판매자(`sale.getSeller()`): `"구매자가 결제를 완료하였습니다. 판매 ID: ..."` (`:449-454`)
  - 둘 다 `NotificationCategory.SHOPPING`, `NotificationType.BID` (`:440-441`, `:451-452`).
- 방식: `NotificationCommandService.createNotification` (`D/notification/service/command/NotificationCommandService.java:44-67`)가 알림을 DB에 저장한 뒤 (`:53`), Redis에 연결 키가 있는 사용자에게만 `convertAndSendToUser`로 WebSocket 푸시한다 (`:303-321`, 키 확인 `:307`, 전송 `:309`).
- 시점: 요청 처리 중, **트랜잭션 커밋 전**에 보낸다. 나중에 롤백돼도 WebSocket 푸시는 이미 나간 뒤다. 알림 전송이 실패해도 예외를 던지지 않는다 (`PaymentCommandService.java:457-460`).
- 알림이 가는 것은 `processPayment`가 알림 단계까지 도달했을 때뿐이다. 케이스 A(카드 PG 예외)에서는 알림이 나가지 않는다.

## 5. 처리 완료 후 주문의 최종 상태

정상 완료(카드 성공 또는 계좌이체·일반 결제)일 때 DB 상태는 다음과 같다.

- Order: `status = PENDING_PAYMENT` (변경 없음, `OrderCommandService.java:244`). 결제 완료 후속 전이가 이 경로에 없다.
- Payment: 카드 성공 `PAID`, 계좌이체 `PENDING`, 일반 `PAID`, 카드 `code 0` 비성공 `PENDING`.
- OrderShipment: `PENDING`.
- SaleBid: `MATCHED`, `order` 연결됨.
- Sale: `SOLD`.
- OrderBid: `MATCHED`, `isInstantPurchase=true`.

**"창고 보관"을 선택한 경우 (`warehouseStorage=true`):** 요청 값은 바뀌는 것이 없다.
- 요청의 `isWarehouseStorage`는 `OrderBidCommandService.java:137`을 거쳐 `createInstantOrder`에 전달되지만, 메서드 본문에서 한 번도 쓰이지 않는다 (`OrderCommandService.java:220-221`, 본문 `:219-319`).
- 창고 관련 로직은 판매자 쪽 설정인 `sale.isWarehouseStorage()`만 본다 (`:291-293`). 이 경우 기존 WarehouseStorage의 상태만 `ASSOCIATED_WITH_ORDER`로 바뀐다 (`WarehouseStorageCommandService.java:132`). Order와의 연결(`WarehouseStorage.assignOrder`, `D/warehouseStorage/entity/WarehouseStorage.java:48-53`)은 호출되지 않는다.
- 주문 상태는 `IN_WAREHOUSE` / `COMPLETED`로 가지 않는다. 그런 전이는 `processPaymentAndShipment`의 `OrderCommandService.java:163-172`에만 있고, 즉시 구매 경로는 그 메서드를 쓰지 않는다.
- 배송정보(OrderShipment)는 구매자 선택과 무관하게 생성된다 (`:264-271`).
- 로그(`OrderBidCommandController.java:94-95`)에는 구매자가 선택한 `창고 보관 여부`가 찍히지만, 실제 처리와는 무관하다.

## 주석·이름과 실제 동작이 다른 곳 (요약)

1. 응답 ID: 주석은 "주문 ID"(`OrderBidCommandController.java:83`), 실제는 OrderBid ID (`:101-107`).
2. 창고 보관 플래그: 전달만 되고 처리되지 않는다 (`OrderCommandService.java:220-221`).
3. 판매 입찰 조회: `SaleBidQueryService.findById`는 없으면 `null`이 아니라 `IllegalArgumentException`을 던진다 (`D/sale/service/query/SaleBidQueryService.java:21-24`). 그래서 `OrderBidCommandService.java:174-176`의 null 검사는 실행되지 않는다. 대신 `handleOrderBidCreationException`(`:145-147`, `:212-218`)이 `OrderBidCreationFailedException`으로 감싼다.
4. 판매 상태 검사 없음: `getSaleBidAndValidate`(`OrderBidCommandService.java:172-184`)는 null 여부만 본다. SaleBid나 Sale의 상태(`MATCHED`, `SOLD`)를 확인하지 않는다. `SaleBidRepository`에도 잠금이 없다(`@Lock` 없음). 같은 판매 입찰에 대한 중복 구매를 코드가 막지 않는다. DB 제약으로 막히는지는 스키마를 보지 않아 확인하지 못했다.
5. 결제 금액: 주문 금액(`bidPrice`)과 결제 금액(`paidAmount`) 비교가 없다 (`PaymentCommandService.java:142-145`). 카드 청구 금액도 클라이언트 값이다 (`:179`).
6. 알림 문구: 계좌이체·카드 `code 0` 비성공에서도 "결제가 완료되었습니다"라고 보낸다 (`:441-442`).
