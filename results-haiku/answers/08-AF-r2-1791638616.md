# 답: 구매자 배송의 운송장 등록부터 배송 완료까지

코드만 읽었다(빌드·실행·테스트 없음). 경로는 저장소 루트 기준이다.

## 요약

- **운송장 등록(PATCH)은 실배송 일반 구매 입찰 주문에서 항상 실패한다.** 주문이 `PREPARING`인데 `IN_TRANSIT` 전이가 허용되지 않는다. 결과는 404(`S001`)이고 전부 롤백된다. 즉시 구매 주문도 `PENDING_PAYMENT`라서 같은 지점에서 실패한다.
- 배송 완료 자동 감지는 6시간 주기 Spring Batch(`ShipmentItemProcessor` 경로)다. 대상은 `IN_TRANSIT`/`OUT_FOR_DELIVERY` 건이다. 등록이 막혀 있어 일반 구매 주문은 자동 완료되지 않는다. 즉시 구매 주문만 완료될 수 있는데, 그것도 `check-status` 경로로 배송 상태를 먼저 세팅해야 한다.
- 완료 처리에서 `OrderBid`·`SaleBid`는 `COMPLETED`로 바뀌지 않고 `MATCHED`로 남는다.
- 판매자 알림은 배송 완료 시점에는 나가지 않는다. `Sale`은 결제 시점에 이미 `SOLD`가 되기 때문이다.

## 1. 운송장 등록 요청

### 1-1. 들어오는 API

- `PATCH /shipments/order/{shipmentId}/status`, 본문 `{courier, trackingNumber}`
  - 컨트롤러: `src/main/java/com/fream/back/domain/shipment/controller/command/OrderShipmentCommandController.java:33-49`
  - 서비스: `src/main/java/com/fream/back/domain/shipment/service/command/OrderShipmentCommandService.java:238-303` (`updateTrackingInfo`)
  - DTO: `src/main/java/com/fream/back/domain/shipment/dto/OrderShipmentRequestDto.java:10-13`

### 1-2. 코드가 의도한 상태 변화 순서

1. `OrderShipment`에 택배사·운송장 번호를 저장하고 `status = IN_TRANSIT`로 둔다. 전이 검사 없이 직접 대입한다 (`src/main/java/com/fream/back/domain/shipment/entity/OrderShipment.java:41-45`).
2. `Order` → `IN_TRANSIT` (`OrderShipmentCommandService.java:259-260`).
3. 구매자에게 "상품이 출발하였습니다" 알림 1건 (`OrderShipmentCommandService.java:265-271`).
4. `updateSaleStatusToSold` 호출: `Sale` → `SOLD`, 판매자 알림, 창고 보관 시 창고 상태 변경 (`OrderShipmentCommandService.java:276`, `116-138`).
5. `OrderBid`·`SaleBid` → `COMPLETED` (`OrderShipmentCommandService.java:289`, `413-440`).

### 1-3. 실배송 일반 구매 입찰 주문 (a): 실패

전제: 결제·배송 처리가 끝나 주문이 `PREPARING`이고, 판매자 매칭으로 `OrderBid.sale`이 연결되어 있다.

- 주문 상태 경로: Kafka 컨슈머가 결제 후 `PAYMENT_COMPLETED`를 거쳐 `PREPARING`으로 만든다 (`src/main/java/com/fream/back/domain/order/service/kafka/OrderEventConsumer.java:171`, `181`, `195`, `216-218`). 컨트롤러는 `OrderCommandController.java:42-54`에서 이 이벤트를 발행한다.

**실패 지점 ① (먼저 발생):** `OrderShipmentCommandService.java:260`의 `order.updateStatus(IN_TRANSIT)`.
- `Order.updateStatus`는 `canTransitionTo`가 false면 `InvalidOrderStatusException`을 던진다 (`src/main/java/com/fream/back/domain/order/entity/Order.java:113-121`).
- `OrderStatus`에서 `PREPARING`의 허용 전이는 `{IN_WAREHOUSE, SHIPMENT_STARTED}`뿐이다 (`src/main/java/com/fream/back/domain/order/entity/OrderStatus.java:26`).
- `IN_TRANSIT`로 가는 전이는 `SHIPMENT_STARTED`에서만 허용된다 (`OrderStatus.java:28`). 그런데 `SHIPMENT_STARTED`를 주문에 대입하는 코드가 없다. `OrderQueryController.java:207`의 문자열 매핑뿐이다.
- 예외는 `OrderShipmentCommandService.java:295-301`의 `catch (Exception e)`에서 `ShipmentException(SHIPMENT_NOT_FOUND)`로 감싸진다.

**실패 지점 ② (①을 고쳐도 남는 문제):** `OrderShipmentCommandService.java:276` → `updateSaleStatusToSold` → `:116`의 `saleBidQueryService.findByOrderId(orderId)`.
- `SaleBidQueryService.findByOrderId`는 없으면 `null`이 아니라 `IllegalArgumentException`을 던진다 (`src/main/java/com/fream/back/domain/sale/service/query/SaleBidQueryService.java:26-29`).
- 일반 구매 입찰 주문에는 `SaleBid`가 연결되지 않는다. `SaleBid.order`를 설정하는 곳은 즉시 구매 경로뿐이다 (`src/main/java/com/fream/back/domain/sale/service/command/SaleBidCommandService.java:78`, `83`; `src/main/java/com/fream/back/domain/order/service/command/OrderCommandService.java:279`).
- `:116`은 try로 감싸지 않아 그대로 전파되고 `:295`에서 잡힌다.

**저장되는 것:** 트랜잭션이 롤백되므로 택배사·운송장 번호·`IN_TRANSIT`(shipment), `Order` 상태 변경, 구매자 알림이 모두 저장되지 않는다. 결제 단계에서 이미 저장된 것(Payment, `Order`의 `PREPARING`, `Sale`의 `SOLD`)은 그대로 남는다. `Sale` `SOLD`는 `src/main/java/com/fream/back/domain/payment/service/command/PaymentCommandService.java:419`에서 결제 시점에 설정된다.

**응답:** HTTP 404, 본문 `{code: "S001", message: "배송 정보를 찾을 수 없습니다.", status: 404, path}`.
- `src/main/java/com/fream/back/global/exception/GlobalExceptionHandler.java:49-63`에서 `errorCode.getStatus()`와 `errorCode.getMessage()`를 쓴다.
- `src/main/java/com/fream/back/domain/shipment/exception/ShipmentErrorCode.java:12`.
- 응답 메시지는 실제 원인(상태 전이 불가)을 말하지 않는다. 원인은 로그에만 남는다.

### 1-4. 즉시 구매 주문 (b): 같은 지점에서 실패

- 즉시 구매 주문은 `PENDING_PAYMENT`로 생성된다 (`OrderCommandService.java:244`).
- 결제 후에도 주문 상태를 바꾸는 코드가 없다 (`createInstantOrder` 219-319, `PaymentCommandService.processPayment` 57-88).
- `OrderStatus.java:24`의 `PENDING_PAYMENT` 허용 집합에 `IN_TRANSIT`가 없다.
- 따라서 `OrderShipmentCommandService.java:260`에서 `InvalidOrderStatusException` → 404 `S001`, 롤백. 결과는 (a)와 같다.

## 2. 배송 완료 감지

### 2-1. 누가, 언제, 어떻게

- **자동(주기 배치):** `ShipmentBatchScheduler.scheduleShipmentStatusJob()`이 `@Scheduled(cron = "0 0 */6 * * *")`로 6시간마다 실행된다. 0시·6시·12시·18시 정각(서버 시간대 기준)이다 (`src/main/java/com/fream/back/global/config/ShipmentBatchScheduler.java:34-35`). 매번 `timestamp` 파라미터로 Job을 시작한다 (`:36-40`). 예외는 `printStackTrace`만 하고 재시도하지 않는다 (`:41-42`).
- **기동 시 실행(추론):** `application.yml`에 `spring.batch.job` 설정이 없다. Spring Boot 기본값이면 기동 시에도 Job이 한 번 실행될 수 있다. 실행 여부는 확인하지 못했다.
- **수동 즉시 조회:** `POST /shipments/order/{shipmentId}/check-status` 및 `/check-status-string` → `OrderShipmentCommandService.updateAndCheckShipmentStatus` (`OrderShipmentCommandController.java:58-59`, `103-104`; `OrderShipmentCommandService.java:452-516`).

### 2-2. 대상 건

- reader 쿼리: `SELECT s FROM OrderShipment s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL`, 페이지 크기 50 (`src/main/java/com/fream/back/domain/shipment/config/UpdateShipmentStatusesJobConfig.java:87-97`, 쿼리는 `:95`). `ORDER BY`가 없다.

### 2-3. 실제로 실행되는 코드

- step은 `new ShipmentItemProcessor(...)`를 쓴다 (`UpdateShipmentStatusesJobConfig.java:69-73`). 실제 처리 본체는 `src/main/java/com/fream/back/domain/shipment/config/ShipmentItemProcessor.java:57-157`의 `process`다.
- **실행되지 않는 비슷한 코드:**
  - `UpdateShipmentStatusesJobConfig.java:104-177`의 `@Bean shipmentItemProcessor()`. step에 연결되지 않고 호출자도 없다.
  - `UpdateShipmentStatusesJobConfig.java:186-220`의 `parseCjLogisticsStatus`(Jsoup). 호출자가 없다.
  - `OrderShipmentCommandService.java:309-391`의 `updateShipmentStatuses()`. 호출자가 없다.
- 브라우저: step 시작 전 열고 끝나면 닫는다 (`src/main/java/com/fream/back/domain/shipment/config/BrowserManageStepListener.java:15-25`). 건마다 `newPage()`로 페이지를 만든다 (`ShipmentItemProcessor.java:72`). 이동·대기·파싱은 `:83`, `:87`, `:94`이다. 파싱은 `tbody#statusDetail tr`의 마지막 행 5번째 `td`를 읽는다 (`:167-212`, 특히 `:181`).
- 수동 경로는 `CjTrackingPlaywright.getCurrentTrackingStatus`를 쓴다 (`src/main/java/com/fream/back/global/utils/CjTrackingPlaywright.java:33`). 호출마다 Playwright와 Chromium을 새로 띄운다 (`:48-56`).

### 2-4. 택배사 상태 문자열 → 내부 상태

`ShipmentItemProcessor.java:220-226`:
- `"배송완료"` → `DELIVERED`
- `"배송출발"` → `OUT_FOR_DELIVERY`
- 그 외 전부 → `IN_TRANSIT`

같은 매핑이 `OrderShipmentCommandService.java:399-405`에도 있다. 완전 일치 비교다.

## 3. 배송 완료 판정 이후

### 3-1. 배치 경로의 상태 변화 순서 (`ShipmentItemProcessor.java:108-117`)

1. `OrderShipment`: `IN_TRANSIT` 또는 `OUT_FOR_DELIVERY` → `DELIVERED` (`:113`; 허용 여부는 `src/main/java/com/fream/back/domain/shipment/entity/ShipmentStatus.java:16-34`).
2. `completeOrder(orderId)` (`:116`, `OrderShipmentCommandService.java:190-229`):
   - `Order` → `COMPLETED` (`:204`)
   - `updateSaleStatusToSold` (`:208`)
   - 구매자 알림 "[completeOrder] 주문이 완료 처리되었습니다..." (`:212-217`)
3. `notifyShipmentCompleted(order)` (`:117`, `src/main/java/com/fream/back/domain/notification/service/command/NotificationCommandService.java:219-234`): 구매자 알림 "[배송 완료] ..." 1건.
4. 청크 커밋 시 `JpaItemWriter`가 `OrderShipment`를 저장한다 (`UpdateShipmentStatusesJobConfig.java:239-246`).

- `OrderBid`·`SaleBid`: 변경 없음, `MATCHED`로 남는다. `completeOrder`에는 입찰 상태 변경이 없다. `updateOrderAndSaleBidStatusToCompleted`는 `updateTrackingInfo`(`:289`)에서만 호출되며, 그 경로는 1-3에서 이미 실패한다.
- `Sale`: `updateSaleStatusToSold`는 `canTransitionTo(SOLD)`가 true일 때만 바꾼다 (`OrderShipmentCommandService.java:119`). `ON_AUCTION`·`SELLING`에서만 허용된다 (`src/main/java/com/fream/back/domain/sale/entity/SaleStatus.java:20-22`). 결제 시점에 이미 `SOLD`이므로 전이가 일어나지 않고 판매자 알림도 나가지 않는다 (`SaleStatus.java:23`).

### 3-2. 알림 건수

- 구매자: 배치 완료 경로에서 2건 (`OrderShipmentCommandService.java:212-217`, `ShipmentItemProcessor.java:117`).
- 판매자: 0건 (위 Sale 설명).

### 3-3. check-status 경로 (`OrderShipmentCommandService.java:452-516`)

- `"배송완료"`: `shipment.updateStatus(DELIVERED)` 후 `completeOrder` 호출 (`:483-489`). `notifyShipmentCompleted`는 호출하지 않으므로 구매자 알림은 1건이다.
- `"배송출발"`: `shipment` → `OUT_FOR_DELIVERY` (`:491-493`). 주문은 건드리지 않고 알림도 없다.
- 그 외(예: `"배송중"`): 1-2의 `updateTrackingInfo`가 이미 `IN_TRANSIT`으로 만들어 둔 상태에서 `updateStatus(IN_TRANSIT)`를 호출한다. `IN_TRANSIT → IN_TRANSIT`은 불가이므로 `IllegalStateException`이 나고, `:507-514`에서 `EXTERNAL_TRACKING_SERVICE_ERROR`(S302, 503)로 롤백된다 (`ShipmentStatus.java:16-22`, `OrderShipment.java:47-55`).

## 4. 주문 종류별 차이

| 항목 | (a) 실배송 일반 구매 입찰 | (b) 즉시 구매 |
|---|---|---|
| 주문 상태 | `PREPARING` (`OrderEventConsumer.java:216-218`) | `PENDING_PAYMENT` (`OrderCommandService.java:244`) |
| PATCH 등록 | 실패: `PREPARING → IN_TRANSIT` 불가 (`OrderStatus.java:26`), 이후 SaleBid 없음으로도 실패. 404 `S001` | 실패: `PENDING_PAYMENT → IN_TRANSIT` 불가 (`OrderStatus.java:24`). 404 `S001` |
| check-status `"배송완료"` | 실패: `PREPARING → COMPLETED` 불가 (`OrderStatus.java:26`). `completeOrder`가 `S102`(404)를 던져 롤백 (`OrderShipmentCommandService.java:221-227`, `505-506`) | 성공: `PENDING_PAYMENT → COMPLETED` 허용 (`OrderStatus.java:24`). `SaleBid` 존재 (`OrderCommandService.java:279`). 200 `DELIVERED`, 구매자 알림 1건 |
| 배치 `DELIVERED` 처리 | 실패: `completeOrder`가 `S102` 던짐 → 해당 건 skip (5장) | 성공: 주문 `COMPLETED`, 구매자 알림 2건, 판매자 알림 0건 |
| `Sale` | 결제 시점 `SOLD` (`PaymentCommandService.java:419`) | 결제 시점 `SOLD` (`PaymentCommandService.java:404`, `SaleBid` 경로) |
| `OrderBid`/`SaleBid` | `MATCHED` 유지 | `MATCHED` 유지 |

- (b)가 배치 대상이 되려면 `IN_TRANSIT`/`OUT_FOR_DELIVERY` 상태와 운송장 번호가 있어야 한다. PATCH는 막히므로, `check-status`의 `"배송출발"`(→ `OUT_FOR_DELIVERY`)로 먼저 세팅해야 한다.
- (a)는 `check-status`의 `"배송출발"`로 `OUT_FOR_DELIVERY`가 될 수 있다. 주문은 `PREPARING`에 남는다. 이 상태로 배치에 들어가면 `DELIVERED` 처리에서 매번 실패하고 skip된다.

## 5. 실패 처리 (주기 처리 중 한 건 실패 시)

설정: `faultTolerant().skip(Exception.class).skipLimit(50)`, retry 없음 (`UpdateShipmentStatusesJobConfig.java:75-77`). 청크 크기 50 (`:51`, `:67`).

- **실패한 건:** 해당 건은 skip된다. 처리 단계의 예외(CJ 조회 실패, 브라우저 생성 실패 `PlaywrightBrowserManager.java:117-125`, 상태 전이 실패, `completeOrder` 실패)와 쓰기 예외 모두 대상이다. skip 리스너는 로그만 남긴다 (`UpdateShipmentStatusesJobConfig.java:252-287`). 그 건의 변경(상태·알림)은 롤백되어 저장되지 않는다. 조회 조건은 그대로이므로 다음 6시간 주기에 다시 시도된다.
- **같은 청크의 나머지 건(추론, Spring Batch 장애 허용 동작 기준):** 청크 트랜잭션이 롤백되고 건별로 다시 처리(scan)된다. 나머지 건은 각자 트랜잭션에서 정상 처리되어 커밋된다. 그 과정에서 이미 처리됐던 건도 CJ 조회와 알림 생성을 다시 수행한다.
- **스킵 한도:** 한 실행에서 50건을 넘게 스킵되면 step이 실패하고, 남은 건은 이번 실행에서 처리되지 않는다. 스케줄러는 예외를 `printStackTrace`만 하므로 재시도나 알림이 없다 (`ShipmentBatchScheduler.java:41-42`).
- **페이지 밀림(코드상 추론, 실행 검증 안 함):** reader 쿼리에 `ORDER BY`가 없다 (`UpdateShipmentStatusesJobConfig.java:95`). 처리 중 `DELIVERED`가 된 건은 조회 조건에서 빠진다. 그래서 다음 페이지의 offset이 밀려, 같은 실행에서 아직 처리하지 않은 건이 건너뛰어질 수 있다. 건너뛴 건은 다음 주기에 처리된다.

## 의도(주석·메서드명)와 실제 동작이 다른 곳

- `updateSaleStatusToSold`: 주석은 "`OrderBid`가 없는 경우 예외로 중단하지 않고 진행"이라고 하고(`OrderShipmentCommandService.java:179`), `if (saleBid != null)` 검사(`:117`)가 있다. 그러나 `findByOrderId`는 `null`이 아니라 예외를 던진다 (`SaleBidQueryService.java:26-29`). 일반 구매 입찰에서는 이 예외가 그대로 전파되어 처리를 중단시킨다.
- `completeOrder`: "주문을 완료 상태로 변경하고 관련된 후속 작업을 처리"라고 하지만 `OrderBid`·`SaleBid`는 완료 처리하지 않는다 (`OrderShipmentCommandService.java:190-229`).
- `updateOrderAndSaleBidStatusToCompleted`: `COMPLETED` 전환 메서드지만 `updateTrackingInfo`에서만 호출되고, 그 경로는 앞에서 실패하므로 사실상 실행되지 않는다 (`:289`, `:413-440`).
- `UpdateShipmentStatusesJobConfig.java:99-103` 주석: "배송 완료 시 알림, Order 상태 완료 등도 여기서 처리 가능"이라고 하지만, 이 설정이 만든 processor 빈은 실행되지 않는다 (`:104-177`).
- 구매자 알림 문구에 디버그 접두사 `[completeOrder]`가 그대로 노출된다 (`OrderShipmentCommandService.java:216`).
- `OrderShipment.updateTrackingInfo`는 전이 검사 없이 `IN_TRANSIT`을 세팅한다 (`OrderShipment.java:41-45`). 이후 `updateStatus(IN_TRANSIT)`와 충돌해 `"배송중"` 응답에서 check-status가 항상 실패한다 (3-3).
- PATCH 실패 응답의 메시지는 "배송 정보를 찾을 수 없습니다."인데, 실제 원인은 주문 상태 전이 불가다 (1-3).

## 확인하지 못한 것

- 실행·테스트는 하지 않았다. 위 동작은 모두 코드 읽기에 근거한다.
- 기동 시 배치 실행 여부(spring.batch.job 기본값)는 설정 파일만 보고 추론했다.
- Spring Batch의 청크 롤백·건별 재처리와 페이지 밀림은 프레임워크 동작을 근거로 한 추론이다.
