# 질문: 즉시 구매는 어떻게 처리되나

## 1. 진입 API, 처리 단계, 동기/비동기, 응답 ID

- **진입 API**: `POST /order-bids/instant` → `OrderBidCommandController#createInstantOrderBid`
  (`src/main/java/com/fream/back/domain/order/controller/command/OrderBidCommandController.java:89-90`).
  요청 DTO `InstantOrderRequestDto`는 `saleBidId`, `addressId`, `warehouseStorage`, `paymentRequest`를 가진다
  (`src/main/java/com/fream/back/domain/order/dto/InstantOrderRequestDto.java:20-29`).
- **컨트롤러 단계**: JWT에서 이메일을 꺼내고(`OrderBidCommandController.java:92`), `enrichPaymentRequest`로 결제 요청의 `userEmail`은 인증 사용자 이메일로 덮어쓰고 `orderId`는 `null`로 초기화한다
  (`OrderBidCommandController.java:98`, `:119-123`).
- **서비스 단계**: `OrderBidCommandService#createInstantOrderBid`
  (`src/main/java/com/fream/back/domain/order/service/command/OrderBidCommandService.java:118-119`, `@Transactional`).
  1) 입력 null 검사 (`:154-167`), 2) 구매자 조회, 3) `SaleBid` 조회·검증 (`:172-184`),
  4) `OrderCommandService#createInstantOrder` 호출 (`:133-139`), 5) `OrderBid` 생성·저장 (`:142`, `:189-207`).
- **동기 처리**: HTTP 요청 하나 안에서 끝나는 동기 처리다. 하나의 트랜잭션에서 주문, 결제, 알림, 판매 상태 변경이 모두 실행된다.
  Kafka를 쓰지 않는다. 컨트롤러 `createInstantOrderBid`는 `OrderEventProducer`를 호출하지 않는다.
  Kafka 기반 비동기 파이프라인(`order-processing-topic`)은 `processPaymentAndShipment` 경로(`OrderCommandController`)에만 있다.
- **응답 ID**: `OrderBid`의 ID다. Order ID가 아니다.
  `createInstantOrderBid(...).getId()`를 `orderId` 변수에 담아 `ResponseDto.success(orderId, ...)`로 돌려준다
  (`OrderBidCommandController.java:101-109`, 반환 객체는 `OrderBid`, `OrderBidCommandService.java:206`).
  Javadoc의 `@return 생성된 주문 ID`(`OrderBidCommandController.java:83`)와 실제 동작이 다르다. 주문 ID는 응답에 없으므로 클라이언트는 별도 조회가 필요하다.

## 2. 생성되는 엔티티와 상태 변화 순서

`OrderCommandService#createInstantOrder`(`src/main/java/com/fream/back/domain/order/service/command/OrderCommandService.java:219-317`)가 대부분을 처리하고, 마지막에 `OrderBid`가 만들어진다.

| 순서 | 동작 | 근거 | 직후 상태 |
|---|---|---|---|
| 1 | 구매자 주소 조회 (이메일 + addressId로 조회, 소유자 확인 포함) | `OrderCommandService.java:238` | 변화 없음 |
| 2 | `Order` 생성·저장 | `OrderCommandService.java:241-247` | `Order.status = PENDING_PAYMENT`, `totalAmount = saleBid.bidPrice`, `user = 구매자` |
| 3 | `OrderItem` 생성, `order.addOrderItem` | `OrderCommandService.java:255-256` | `OrderItem` 1건 (`order` 연결) |
| 4 | `OrderShipment` 생성 (수령인·주소 스냅샷) | `OrderCommandService.java:264-271` | `OrderShipment.status = PENDING` |
| 5 | `SaleBid.assignOrder(order)`, `updateStatus(MATCHED)`, `entityManager.flush()` | `OrderCommandService.java:279-283` | `SaleBid.order = 신규 Order`, `SaleBid.status = MATCHED` |
| 6 | 판매(`Sale`)가 창고 보관 상품이면 판매자 창고 레코드를 `ASSOCIATED_WITH_ORDER`로 변경 | `OrderCommandService.java:292-293` | `WarehouseStorage.status = ASSOCIATED_WITH_ORDER` (해당 레코드 없으면 예외) |
| 7 | 결제 처리 `PaymentCommandService#processPayment` | `OrderCommandService.java:305` | `Payment` 1건 생성 (3번 참고) |
| 8 | 알림 전송, 판매 상태 변경 | `PaymentCommandService.java:383-420` | `Sale.status = SOLD` |
| 9 | `OrderBid` 생성·저장 (`user`, `productSize`, `bidPrice`, `order`, `sale` 설정) | `OrderBidCommandService.java:142`, `:189-207` | `OrderBid.status = MATCHED`, `isInstantPurchase = true` |
| 10 | 트랜잭션 커밋 | `OrderBidCommandService.java:118` | — |

- 9번에서 `orderBid.assignOrder(order)`가 `order.assignOrderBid(this)`를 호출해 양방향 연결을 맞춘다
  (`src/main/java/com/fream/back/domain/order/entity/OrderBid.java:60-82`).
- `Order.status`는 이 경로 전체에서 `PENDING_PAYMENT`로 남는다. `Order.updateStatus(PAYMENT_COMPLETED)` 등은 `processPaymentAndShipment`(`OrderCommandService.java:165-176`)와 Kafka 소비자(`OrderEventConsumer.java:192-217`)에만 있고, 즉시 구매 경로는 둘 다 호출하지 않는다.
- **입력 검증의 한계**: `getSaleBidAndValidate`는 `SaleBid`가 null인지, `Sale`이 null인지만 본다(`OrderBidCommandService.java:172-184`).
  `SaleBid.status`(이미 매칭됐는지)나 `Sale.status`(판매 중인지)는 검사하지 않는다. 그래서 같은 판매 입찰을 두 번 구매하는 것을 애플리케이션 코드에서 막지 않는다.
  `SaleBidQueryService#findById`는 없을 때 null이 아니라 `IllegalArgumentException`을 던지므로(`src/main/java/com/fream/back/domain/sale/service/query/SaleBidQueryService.java:21-24`), `OrderBidCommandService.java:174`의 null 검사는 실행되지 않는다. 이 예외는 `OrderBidCreationFailedException`으로 감싸진다(`OrderBidCommandService.java:212-218`).

## 3. 결제 수단별 결과, 끝까지 성공하는가, 카드 실패 시

결제 분기는 `PaymentCommandService#processPayment`의 `switch`다(`src/main/java/com/fream/back/domain/payment/service/command/PaymentCommandService.java:57-104`).
검증(`validatePaymentRequest`, `:117-146`)은 주문 ID 일치, 이메일 일치, `paidAmount > 0`만 확인한다. **결제 금액을 판매 가격(`totalAmount`)과 비교하지 않는다** (`:142-145`).

- **카드(CARD)** — `createCardPayment` (`:157-215`)
  - PaymentInfo를 조회한 뒤 PortOne에 `processCardPayment(paymentInfo, requestDto.getPaidAmount())`를 호출한다 (`:179`). 청구 금액은 클라이언트가 보낸 `paidAmount`다.
  - 응답의 `status`가 정확히 `"success"`일 때만 `CardPayment`를 `PAID`로 만들고 성공 플래그를 켠다 (`:203-206`). 그 외에는 엔티티 기본값 `PENDING`으로 저장되지만(`src/main/java/com/fream/back/domain/payment/entity/Payment.java:44`) 예외는 나지 않는다. 그러면 주문은 성공으로 진행된다.
  - **대행사가 실패로 응답한 경우** (PortOne 응답 `code != 0`): `PortOneApiClient.processCardPayment`가 `PaymentProcessingException`을 던진다 (`src/main/java/com/fream/back/domain/payment/portone/PortOneApiClient.java:270-274`).
    이 예외는 `createCardPayment`의 `catch (PaymentException)`에서 그대로 전파되고(`PaymentCommandService.java:180-181`), `processPayment`(`:89-100`)를 거쳐 `createInstantOrder`에서 `OrderPaymentProcessingFailedException`으로 바뀐다(`OrderCommandService.java:305-308`).
    `createInstantOrder`의 바깥 `catch`가 `OrderException`을 다시 던지고(`:312-317`), `OrderBidCommandService`의 `handleOrderBidCreationException`도 그대로 다시 던진다(`OrderBidCommandService.java:145-147`, `:212-215`).
    `@Transactional`은 `RuntimeException`에서 롤백하므로(`src/main/java/com/fream/back/global/exception/GlobalException.java:10`에서 `GlobalException extends RuntimeException`), 주문, 주문 항목, 배송, `SaleBid` 변경, 창고 상태 변경, `Sale` 상태 변경이 전부 되돌아간다. 응답은 `GlobalExceptionHandler`의 `GlobalException` 핸들러가 만든다 (`src/main/java/com/fream/back/global/exception/GlobalExceptionHandler.java:49-`).
  - **주의: PG 승인 후 롤백되면 결제가 취소되지 않는다.** PG 호출(`PaymentCommandService.java:179`)이 트랜잭션 안에서 DB 작업들 사이에 있고, 이후에도 `OrderBid` 저장(`OrderBidCommandService.java:142`, `:206`)과 커밋이 남아 있다. 이 구간에서 실패하면 PG에는 결제가 남고 DB에는 기록이 없다.
    `PaymentCommandService`에는 `handleRefundIfNecessary`(`:341-`)가 있지만 호출하는 곳이 없다.
- **계좌이체(ACCOUNT)** — `createAccountPayment` (`:236-288`)
  - PG 호출 없이 은행명만 검증하고(`:244`) `AccountPayment`를 `PENDING`으로 저장한다 (`:260`).
  - 예외가 없으므로 주문, `OrderBid` 생성, 알림, 판매 `SOLD`까지 전부 진행된다. 주문은 성공으로 응답하지만 결제는 `PENDING`이다.
- **일반 결제(GENERAL)** — `createGeneralPayment` (`:290-`)
  - `impUid`가 비어 있지 않은지만 확인한다 (`:296-299`). 이후 클라이언트가 보낸 `impUid`, `paidAmount`로 `GeneralPayment`를 만들고 바로 `PAID`로 설정한다 (`:314`).
  - PortOne 조회·검증 호출이 없어서, 실제 결제 여부를 확인하지 않고 클라이언트 값을 그대로 믿는다.

**즉시 구매가 끝까지 성공하는가**: 카드는 PG 응답이 `"success"`인 경우에 한해 끝까지 성공한다. 계좌이체는 결제가 `PENDING`인 채로 성공 처리된다. 일반 결제는 검증 없이 `PAID`가 된다. 카드 PG 실패는 전체 롤백이다. 카드 PG가 `code == 0`이면서 `status`가 `"success"`가 아니면 결제는 `PENDING`인데 주문은 성공 처리된다.

## 4. 알림의 수신자, 시점, 방식

- **구매자**: `"결제가 완료되었습니다. 주문 ID: …"` (`src/main/java/com/fream/back/domain/payment/service/command/PaymentCommandService.java:442`), 카테고리 `SHOPPING`, 타입 `BID`.
- **판매자**(`sale.getSeller()`가 null이 아닐 때): `"구매자가 결제를 완료하였습니다. 판매 ID: …"` (`PaymentCommandService.java:453`), 같은 카테고리와 타입.
- **시점**: `processPayment` 안에서 결제 레코드를 만든 직후 동기로 실행된다 (`PaymentCommandService.java:83` → `:383-420` → `sendNotifications` `:434-`). 같은 HTTP 요청, 같은 트랜잭션, **커밋 전**이다.
- **방식**: `NotificationCommandService#createNotification`(`src/main/java/com/fream/back/domain/notification/service/command/NotificationCommandService.java:44-`)이 `Notification` 행을 저장한 뒤, Redis에 `WebSocket:User:<이메일>` 키가 있으면 STOMP `/queue/notifications`로 실시간 전송한다 (`NotificationCommandService.java:37-38`, `:303-309`). 연결이 없으면 DB에만 남는다.
- **주의**:
  - 카드 PG 실패 시에는 예외로 빠지므로 알림이 가지 않는다.
  - 계좌이체는 결제가 `PENDING`인데도 `"결제가 완료되었습니다"`를 보낸다.
  - 알림 실패는 `sendNotifications`에서 삼킨다(`PaymentCommandService.java:457-460`).
  - 커밋 전에 실시간 전송이 나가므로, 이후 롤백되면 전송된 알림과 DB 상태가 어긋날 수 있다.
  - 즉시 구매 경로에서는 `notification-topic` Kafka를 쓰지 않는다.

## 5. 최종 상태와 "창고 보관" 선택 시 차이

성공 경로(카드, PG `"success"`) 기준 최종 상태:

- `Order`: `status = PENDING_PAYMENT`(변경 없음), `totalAmount` = 판매 입찰 가격, `user` = 구매자, `orderBid` 연결됨, `orderShipment` = `PENDING`, `warehouseStorage` = `null`.
- `Payment`(CardPayment): `PAID`(계좌이체면 `PENDING`, 일반 결제면 `PAID`), `order` 연결.
- `OrderBid`: `MATCHED`, `isInstantPurchase = true`, `order`·`sale` 연결.
- `SaleBid`: `MATCHED`, `order` 연결.
- `Sale`: `SOLD`.
- 알림: 구매자·판매자 각 1건.

**"창고 보관"을 선택한 경우**:

- 요청의 `warehouseStorage` 값은 이 경로에서 쓰이지 않는다. `createInstantOrder`의 `isWarehouseStorage` 매개변수는 선언(`OrderCommandService.java:221`) 말고 본문에서 사용되지 않는다.
- 실제 분기는 판매 쪽 플래그 `sale.isWarehouseStorage()`다(`OrderCommandService.java:292`). 판매자가 창고 보관으로 등록한 상품일 때만 판매자 창고 레코드(`src/main/java/com/fream/back/domain/shipment/service/command/SellerShipmentCommandService.java:75-79`에서 생성)를 `IN_STORAGE` → `ASSOCIATED_WITH_ORDER`로 바꾼다 (`WarehouseStorageCommandService#updateWarehouseStatus`).
  이 전이는 `validateStatusTransition`으로 검사하며, `ON_AUCTION`이나 `SOLD` 상태에서는 실패해 전체가 롤백된다 (`src/main/java/com/fream/back/domain/warehouseStorage/service/command/WarehouseStorageCommandService.java`의 `validateStatusTransition`).
- 구매자용 창고 레코드는 만들어지지 않는다. `createOrderStorage`는 이 경로에서 호출되지 않는다. 비교: 일반 주문 경로는 `requestDto.isWarehouseStorage()`일 때 `createOrderStorage`를 호출한다 (`OrderCommandService.java:163-170`).
- `order.warehouseStorage`는 설정되지 않으므로 주문 상세 응답에 창고 정보가 나오지 않는다 (`src/main/java/com/fream/back/domain/order/controller/query/OrderQueryController.java:85`).
- `Order.status`는 여전히 `PENDING_PAYMENT`다.

결과적으로 구매자의 "창고 보관" 선택은 이 경로에서 아무 효과가 없다. 실제로 바뀌는 것은 판매 쪽 창고 레코드의 상태뿐이다.

## 부가 발견 (질문 외, 근거 포함)

- 결제 금액 미검증: `paidAmount`는 클라이언트 값이며 `Order.totalAmount`(판매가)와 비교되지 않는다 (`PaymentCommandService.java:142-145`, 청구는 `:179`). 카드는 클라이언트가 보낸 금액으로 청구된다.
- 같은 판매 입찰의 중복 구매를 막는 검사가 없다 (`OrderBidCommandService.java:172-184`, `OrderCommandService.java:219-238`). 동시성 제어(락)도 보이지 않는다.
- `enrichPaymentRequest`의 주석 "이후 Order 생성 후 업데이트 가능"(`OrderBidCommandController.java:121`)과 달리, 실제 `orderId` 설정은 `createInstantOrder`의 `paymentRequest.setOrderId(order.getId())`(`OrderCommandService.java:250`)에서 이루어진다. 동작은 맞지만 주석 위치가 다르다.
