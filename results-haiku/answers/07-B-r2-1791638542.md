# 즉시 구매는 어떻게 처리되나

정적 코드 리뷰 결과입니다. 실행이나 테스트는 하지 않았고, 아래 내용은 코드를 읽어서 확인한 동작입니다. 경로는 저장소 루트 기준입니다.

---

## 1. 진입 API와 처리 단계, 동기/비동기, 반환 ID

**진입점**: `POST /order-bids/instant` (`src/main/java/com/fream/back/domain/order/controller/command/OrderBidCommandController.java:22` 클래스 매핑 `/order-bids`, `:89` `@PostMapping("/instant")`, `:90` 메서드).

**처리 단계** (모두 같은 HTTP 요청 안에서 동기로 실행됨):

1. 컨트롤러가 토큰에서 이메일을 꺼내 검증한다 (`OrderBidCommandController.java:92`).
2. 결제 정보에 사용자 이메일을 넣고 `orderId`를 `null`로 초기화한다 (`:98`, `:119-122`).
3. `OrderBidCommandService.createInstantOrderBid(...)`를 호출한다 (`src/main/java/com/fream/back/domain/order/service/command/OrderBidCommandService.java:118` `@Transactional`, `:119-120`).
   - 입력값 검증 (`OrderBidCommandService.java:123`, `:154-167`).
   - 구매자 조회 (`:126`).
   - 판매 입찰 조회 (`:129`, `:172-184`).
   - `OrderCommandService.createInstantOrder(...)`로 주문 생성 및 결제 (`:133-139`).
   - `OrderBid` 생성 및 저장 (`:142`, `:189-207`).
4. 컨트롤러는 HTTP 200으로 응답한다 (`OrderBidCommandController.java:101-109`).

**동기/비동기**: 동기 처리입니다. 카드 결제 시 PG(PortOne) HTTP 호출도 DB 트랜잭션 안에서 동기로 일어납니다 (`src/main/java/com/fream/back/domain/payment/portone/PortOneApiClient.java:266`). Kafka를 쓰는 `OrderEventProducer` 경로는 이 엔드포인트에서 쓰지 않습니다. Kafka 경로는 별도 엔드포인트 `POST /orders/{orderId}/process-payment-shipment`이며 202를 반환합니다 (`src/main/java/com/fream/back/domain/order/controller/command/OrderCommandController.java:165-202`).

**응답 ID**: 반환되는 ID는 **`OrderBid`의 ID**입니다. `Order`의 ID가 아닙니다. 컨트롤러가 `createInstantOrderBid(...).getId()`를 쓰고 (`OrderBidCommandController.java:101-107`), 서비스 메서드 반환 타입이 `OrderBid`입니다 (`OrderBidCommandService.java:119-120`). 그런데 Javadoc에는 "생성된 주문 ID"라고 적혀 있습니다 (`OrderBidCommandController.java:83`). **주석과 실제 동작이 다릅니다.** 실제 값은 `OrderBid` ID입니다.

## 2. 생성되는 엔티티와 상태 변화 순서

`OrderCommandService.createInstantOrder` (`src/main/java/com/fream/back/domain/order/service/command/OrderCommandService.java:219-319`, `@Transactional`) 안에서 아래 순서로 진행됩니다. `OrderBid`는 이 메서드가 끝난 뒤 만들어집니다.

| 순서 | 동작 | 근거 | 직후 상태 |
|---|---|---|---|
| a | `Order` 생성 및 저장 | `OrderCommandService.java:241-247` | `Order.status = PENDING_PAYMENT`, `totalAmount = saleBid.bidPrice` |

| c | `OrderItem` 생성 및 Order에 추가 | `OrderCommandService.java:254-260` | — |
| d | `OrderShipment` 생성 (주소 조회 결과 사용) | `OrderCommandService.java:238`, `:263-275` | Shipment 생성, Order에 연결 |
| e | `SaleBid` 매칭: `assignOrder` 후 `updateStatus(MATCHED)`, `flush()` | `OrderCommandService.java:279-283`, `src/main/java/com/fream/back/domain/sale/entity/SaleBid.java:58-61` | `SaleBid.status = MATCHED`, `SaleBid.order = Order` |
| f | `Sale.isWarehouseStorage`가 true면 창고 보관 상태 변경 | `OrderCommandService.java:291-294` | `WarehouseStorage.status = ASSOCIATED_WITH_ORDER` (false면 아무 일 없음) |

**정리**:

- 새로 만들어지는 엔티티: `Order`, `OrderItem`, `OrderShipment`, `Payment`(카드/계좌/일반 중 하나), `OrderBid`, 알림(구매자/판매자 각 1건).
- 기존 엔티티 상태 변화: `SaleBid` PENDING → MATCHED, `Sale` → SOLD, 창고 보관이 켜진 판매라면 `WarehouseStorage` → ASSOCIATED_WITH_ORDER.
- `Order.status`는 `PENDING_PAYMENT`에서 바뀌지 않습니다. `createInstantOrder` 안에 `order.updateStatus(...)` 호출이 없습니다 (`OrderCommandService.java:219-319`). 결제가 `PAID`가 되어도 주문 상태는 그대로입니다.
- 주의: `SaleBid`의 구매 전 상태(PENDING인지)와 `Sale`의 구매 전 상태(SELLING 등)를 확인하는 코드가 없습니다. `getSaleBidAndValidate`는 null 검사만 합니다 (`OrderBidCommandService.java:172-184`). 그래서 이미 MATCHED나 SOLD인 입찰도 다시 구매할 수 있습니다. 이 경우 `SaleBid.order`가 새 주문으로 덮어써집니다 (`SaleBid.java:58-61`). 락도 없습니다 (`src/main/java/com/fream/back/domain/sale/repository/SaleBidRepository.java:9`는 일반 `findById`).

## 3. 결제 수단별 결과와 성공 여부

결제 수단은 `paymentType` 필드로 정해집니다 (`src/main/java/com/fream/back/domain/payment/dto/PaymentRequestDto.java:20-25`). 분기는 `PaymentCommandService.processPayment`의 switch입니다 (`src/main/java/com/fream/back/domain/payment/service/command/PaymentCommandService.java:67-80`).

**공통 검증**: 주문 ID와 이메일이 일치하는지 확인하고 (`PaymentCommandService.java:131-139`), 금액은 **0보다 큰지만** 봅니다 (`:142-145`). 결제 요청 금액(`paidAmount`)은 클라이언트가 보낸 값이고, 판매 입찰 가격(`Order.totalAmount`)과 비교하는 코드가 없습니다.

**카드 (CARD)** (`PaymentCommandService.java:157-225`):

- 결제 정보 ID로 `PaymentInfo`를 조회하고 (`:166`), PortOne에 요청 금액을 그대로 보냅니다 (`:179`).
- PortOne 응답의 `code`가 0이 아니면 `PortOneApiClient.processCardPayment`가 `PaymentProcessingException`을 던집니다 (`src/main/java/com/fream/back/domain/payment/portone/PortOneApiClient.java:270-275`).
  - 이 예외는 `PaymentCommandService`에서 그대로 전파됩니다 (`:180-181`, `:89-94`).
  - `OrderCommandService`가 이를 `OrderPaymentProcessingFailedException`으로 감싸 던집니다 (`OrderCommandService.java:304-309`).
  - `GlobalException`은 `RuntimeException`입니다 (`src/main/java/com/fream/back/global/exception/GlobalException.java:10`). 따라서 `@Transactional`이 **전체 롤백**합니다. Order, OrderItem, Shipment, SaleBid 매칭, Sale 상태 변경이 모두 되돌아갑니다. 실패한 `Payment` 행도 저장되지 않습니다. `PaymentStatus.FAILED`는 이 경로에서 쓰이지 않습니다.
  - 응답은 `OrderException` 핸들러가 `ErrorCode`의 상태 코드로 돌려줍니다 (`src/main/java/com/fream/back/global/exception/GlobalExceptionHandler.java:325-332`).
- PG 응답 `code`가 0이면 성공 경로로 가지만, `CardPayment`는 `response.status`가 문자열 `"success"`일 때만 `PAID`가 됩니다 (`PaymentCommandService.java:203-206`). 그 외에는 기본값 `PENDING`(`src/main/java/com/fream/back/domain/payment/entity/Payment.java:44`)으로 저장되고, **실패로 처리되지 않습니다**. 그래도 주문, 판매 SOLD, 알림(결제 완료 문구)은 모두 진행됩니다.

**계좌이체 (ACCOUNT)** (`PaymentCommandService.java:236-279`):

- PG를 호출하지 않습니다. 은행명이 `Bank` enum에 있는지만 확인합니다 (`:242-248`, `:470-488`).
- `Payment`는 `PENDING`으로 저장됩니다 (`:260`). 입금 확인 절차는 이 경로에 없습니다.
- 주문, 매칭, Sale SOLD, 알림까지 모두 진행되고 응답은 성공입니다. 돈은 아직 들어오지 않은 상태입니다.

**일반 결제 (GENERAL)** (`PaymentCommandService.java:290-333`):

- `impUid`가 비어 있지 않은지만 확인합니다 (`:297-300`). PortOne을 호출해 검증하지 않습니다.
- 바로 `PAID`로 저장합니다 (`:313-314`). 금액과 `impUid`는 전부 클라이언트 값입니다.

**즉시 구매가 끝까지 성공하는지**: 예외 없이 끝나면 HTTP 200과 `OrderBid` ID를 돌려줍니다. 하지만 "성공"이라고 해서 주문이 완료된 것은 아닙니다. 주문 상태는 여전히 `PENDING_PAYMENT`이고 (2번 참고), 계좌이체는 입금 전이며, 일반 결제는 검증 없이 `PAID`입니다.

**결제 대행사가 카드 결제를 실패로 응답하면**: 위 카드 항목과 같습니다. 예외가 전파되어 **전체 롤백**되고, 주문이 만들어지지 않습니다. 실패 결제 기록도 남지 않습니다. 사용자에게는 `OrderException`에 대응하는 에러 응답이 갑니다.

**주의 (롤백 후 돈이 빠져나간 경우)**: PG 호출이 트랜잭션 안에서 일어나므로, 카드 승인이 끝난 뒤 같은 트랜잭션의 뒷부분이 실패하면 DB만 롤백되고 PG 취소는 호출되지 않습니다. 예를 들어 `createInstantOrderBid`가 `OrderBid`를 저장하다 실패하면 (`OrderBidCommandService.java:142`) 카드 승인은 남습니다. 이 경로에는 `cancelPayment` 호출이 없습니다 (환불 로직은 `PaymentCommandService.java:341-375`, `:543-596`에 있지만 즉시 구매에서 호출되지 않습니다).

## 4. 알림 수신자, 시점, 방식

**호출 위치**: 알림은 `PaymentCommandService.processPayment`가 결제를 마친 뒤 `notifyUsersAndUpdateSaleStatus`에서 보냅니다 (`PaymentCommandService.java:83`, `:383-426`). 즉시 구매에서는 `OrderBid`가 아직 없으므로 `order.getOrderBid()`가 `null`입니다 (`:388-389`). 그래서 `saleBidQueryService.findByOrderId`로 판매 입찰을 찾습니다 (`:391`). `flush()` 덕분에 이 조회가 성공합니다 (`OrderCommandService.java:283`).

**수신자와 내용** (`PaymentCommandService.java:434-462`):

- 구매자: 카테고리 `SHOPPING`, 타입 `BID`, 메시지 "결제가 완료되었습니다. 주문 ID: {orderId}" (`:438-443`).
- 판매자: 카테고리 `SHOPPING`, 타입 `BID`, 메시지 "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}" (`:449-454`).

**방식**:

- 알림은 DB에 저장됩니다 (`src/main/java/com/fream/back/domain/notification/service/command/NotificationCommandService.java:44-67`).
- 실시간 전달은 WebSocket으로 하는데, Redis에 해당 사용자 키가 있을 때만 보냅니다 (`NotificationCommandService.java:303-323`, 키 확인은 `:307`). 연결이 없으면 저장만 되고 나중에 조회됩니다.
- 전송 시점은 요청 처리 중이며, **DB 트랜잭션 커밋 전**입니다. 그래서 뒤에서 롤백되면 WebSocket 푸시는 이미 나갔는데 DB 알림 행은 사라지는 불일치가 생깁니다. `OrderBid` 생성 실패가 그 예입니다.
- 알림 실패는 로그만 남기고 무시합니다 (`PaymentCommandService.java:421-425`, `:457-461`).

**주의**: 알림 문구는 결제 상태를 확인하지 않고 보냅니다. 계좌이체(`PENDING`)나 카드에서 `status`가 `"success"`가 아닌 경우에도 "결제가 완료되었습니다"가 나갑니다.

## 5. 처리 후 주문 최종 상태와 "창고 보관" 선택의 영향

**최종 주문 상태**: `PENDING_PAYMENT`입니다 (`OrderCommandService.java:244`, 이후 변경 없음). 결제 상태(`Payment.status`)는 수단에 따라 `PAID`, `PENDING`일 수 있지만, 주문 상태에는 반영되지 않습니다. 결제 후 주문 상태를 `PAYMENT_COMPLETED`→`PREPARING`으로 바꾸는 로직은 다른 경로인 `OrderCommandService.processPaymentAndShipment` (`OrderCommandService.java:161-177`)에만 있고, 즉시 구매는 이 경로를 쓰지 않습니다.

**최종 상태 요약 (성공 경로)**:

- `Order`: `PENDING_PAYMENT`, `OrderItem`/`OrderShipment` 연결됨. `Order.payment`는 설정되지 않고 `Payment.order`만 설정됩니다 (`OrderCommandService.java:250` 주변, `Payment.java:47-50`).
- `Payment`: 카드는 `PAID` 또는 `PENDING`, 계좌는 `PENDING`, 일반은 `PAID`.
- `SaleBid`: `MATCHED`, `order` 연결.
- `Sale`: `SOLD`.
- `OrderBid`: `MATCHED`, `isInstantPurchase = true`, `order`와 `sale` 연결 (`OrderBid.java:97-99`).

**"창고 보관"을 선택한 경우**:

- 요청의 `warehouseStorage` 값은 `createInstantOrder`에 전달되지만 **본문에서 사용되지 않습니다**. 파라미터 `isWarehouseStorage`는 시그니처에만 있습니다 (`OrderCommandService.java:221`). 컨트롤러 로그에 "창고 보관 여부"가 찍히지만 (`OrderBidCommandController.java:94-95`), 실제 결정에는 쓰이지 않습니다.
- 창고 여부는 판매 쪽 플래그 `Sale.isWarehouseStorage`가 정합니다 (`OrderCommandService.java:292`, `src/main/java/com/fream/back/domain/sale/entity/Sale.java:43`). 판매자가 등록할 때 정해진 값입니다. 구매자가 고르는 것과 무관합니다.
- 판매의 창고 플래그가 true이면 `WarehouseStorage` 상태만 `ASSOCIATED_WITH_ORDER`로 바뀝니다 (`OrderCommandService.java:293`, `WarehouseStorageCommandService.java:117-140`). 이때 `findBySale`로 창고 정보를 찾는데, 없으면 `WarehouseStorageNotFoundException`이 나고 주문 전체가 롤백됩니다 (`WarehouseStorageQueryService.java:30-33`, `OrderCommandService.java:295-297`).
- 창고 보관 주문에 대해 `Order`에 `WarehouseStorage`를 연결하거나 `IN_WAREHOUSE`/`COMPLETED`로 바꾸는 처리는 이 경로에 없습니다. 그런 처리는 `processPaymentAndShipment`의 창고 분기에만 있습니다 (`OrderCommandService.java:163-172`).
- 결론: 즉시 구매에서 구매자가 "창고 보관"을 체크해도 주문 상태와 배송 정보에는 차이가 없습니다. 창고 여부는 판매 플래그에 따라 `WarehouseStorage`가 `ASSOCIATED_WITH_ORDER`가 되느냐만 달라집니다.

## 코드와 이름/주석이 다른 부분 (요약)

1. **응답 ID**: Javadoc은 "주문 ID"라고 하지만 실제로는 `OrderBid` ID를 반환합니다 (`OrderBidCommandController.java:83`, `:107`).
2. **창고 보관 플래그**: 요청 값은 무시되고 `Sale.isWarehouseStorage`로 결정됩니다 (`OrderCommandService.java:221`, `:292`).
3. **SaleBidNotFoundException**: Javadoc에는 "판매 입찰을 찾을 수 없으면 `SaleBidNotFoundException`"이라고 되어 있습니다 (`OrderBidCommandController.java:86`). 실제로는 `SaleBidQueryService.findById`가 `IllegalArgumentException`을 던집니다 (`src/main/java/com/fream/back/domain/sale/service/query/SaleBidQueryService.java:21-24`). 그 결과 `OrderBidCommandService`의 null 검사(`:173-176`)는 도달하지 않고, 예외는 `OrderBidCreationFailedException`으로 감싸집니다 (`OrderBidCommandService.java:145-147`, `:212-218`).
4. **주문 상태**: 결제 완료 후에도 `PENDING_PAYMENT`로 남습니다 (2번, 5번 참고).
5. **"결제 완료" 알림**: 결제 상태와 무관하게 발송됩니다 (4번 참고).

## 이 코드에서 보이는 위험 (질문 밖, 참고용)

- **중복 구매 방지 없음**: 판매 입찰과 판매의 상태를 확인하지 않고, 락도 없습니다 (`OrderBidCommandService.java:172-184`). 같은 판매 입찰에 대해 두 구매자가 동시에 요청하면 둘 다 통과할 수 있습니다. 이 경우 `SaleBid.order`가 마지막 주문으로 덮어써집니다 (`SaleBid.java:58-61`). 이것은 코드 읽기로 추론한 결과이며 재현하지는 않았습니다.
- **결제 금액 검증 없음**: `paidAmount`는 클라이언트 값이고 입찰 가격과 비교하지 않습니다 (`PaymentCommandService.java:142-145`, `:179`, `:193`). 카드는 요청 금액 그대로 승인됩니다. 일반 결제는 `impUid`도 검증하지 않습니다 (`:297-314`). 금액 위조가 가능하다는 뜻입니다.
- **PG 호출과 DB 트랜잭션이 묶여 있음**: 위 3번 주의 사항 참고.
