## 1. 운송장 등록 요청

**API**
- `PATCH /shipments/order/{shipmentId}/status`, body `OrderShipmentRequestDto(courier, trackingNumber)`
  - 컨트롤러: `P/domain/shipment/controller/command/OrderShipmentCommandController.java:20, 33-41`
  - DTO: `P/domain/shipment/dto/OrderShipmentRequestDto.java:10-13`
  - 서비스: `P/domain/shipment/service/command/OrderShipmentCommandService.java:239` (`updateTrackingInfo`)
  - 소유자 검증 없음: `OrderShipmentCommandService.java:249` 에서 `shipmentId`로 바로 조회한다.

**설계된 처리 순서** (`OrderShipmentCommandService.java:239-303`, `@Transactional`)
1. 입력 검증: 택배사·운송장이 비면 `TRACKING_INFO_REQUIRED`(S004) (`:243-246`)
2. `OrderShipment` 조회, 없으면 `SHIPMENT_NOT_FOUND` (`:249-253`)
3. `OrderShipment.updateTrackingInfo` → courier/trackingNumber 저장, status `PENDING → IN_TRANSIT`. 전이 검증 없이 대입한다 (`P/domain/shipment/entity/OrderShipment.java:41-45`).
4. `Order.updateStatus(IN_TRANSIT)` (`:260`). 전이표상 `IN_TRANSIT`은 `SHIPMENT_STARTED`에서만 허용된다 (`P/domain/order/entity/OrderStatus.java:28-29`). `Order.updateStatus`는 불가능한 전이를 `InvalidOrderStatusException`으로 막는다 (`P/domain/order/entity/Order.java:113-121`).
5. 구매자 알림 1건: "상품이 출발하였습니다" (`:266-271`). `createNotification`은 저장 후 실시간 전송한다 (`P/domain/notification/service/command/NotificationCommandService.java:44-66`).
6. `updateSaleStatusToSold(orderId)` (`:276`, 본체 `:112-183`): 연결된 Sale을 `SOLD`로 바꾸고 판매자에게 알림 1건 (`:119-138`, `:156-169`). 두 번째 블록은 Sale이 이미 `SOLD`라 알림을 보내지 않는다.
7. 창고 보관 건이면 창고 상태를 `SOLD`로 바꾼다 (`:279-286`).
8. `OrderBid`/`SaleBid`를 `MATCHED → COMPLETED`로 바꾼다 (`:289`, 헬퍼 `:413-440`). 헬퍼는 예외를 로그만 남기고 삼킨다.

**(a) 실배송 일반 구매 입찰 주문: 끝까지 성공하지 않는다**

결제·배송 처리(Kafka)까지는 정상이다.
- 주문 생성: `OrderBidCommandService.java:90-103`이 `PENDING`으로 만든 뒤 `assignOrder`로 `MATCHED`가 된다 (`P/domain/order/entity/OrderBid.java:75`). Order는 `PENDING_PAYMENT` (`P/domain/order/service/command/OrderCommandService.java:81`).
- 컨슈머 `P/domain/order/service/kafka/OrderEventConsumer.java:166-230`: 결제 → `OrderShipment` 생성 (`:181-188`, 상태 `PENDING`, `OrderShipmentCommandService.java:56-75`) → `PAYMENT_COMPLETED` (`:195`) → 실배송이면 `PREPARING` (`:216-218`) → 저장 (`:223`).

따라서 주문은 `PREPARING`, 배송은 `PENDING`(운송장 없음), 입찰은 `MATCHED` 상태다.

등록 요청은 **`:260`에서 실패한다.**
- 이유: `PREPARING → IN_TRANSIT` 전이는 허용되지 않는다. `PREPARING`의 허용 전이는 `IN_WAREHOUSE`, `SHIPMENT_STARTED`뿐이다 (`P/domain/order/entity/OrderStatus.java:26`). `SHIPMENT_STARTED`를 설정하는 코드는 없다(전체 검색 결과 `OrderStatus.java:13,26-28`만 존재).
- 예외: `InvalidOrderStatusException` (ORD008, `P/domain/order/exception/InvalidOrderStatusException.java`).
- 래핑: `catch (Exception e)`가 이를 `ShipmentException(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: ...")`로 바꾼다 (`OrderShipmentCommandService.java:293-301`).

**저장되는 것**: 이 요청에서 저장되는 것은 없다. `ShipmentException`은 `RuntimeException`(`P/global/exception/GlobalException.java:10`)이라 `@Transactional`이 롤백한다. 운송장·`IN_TRANSIT` 변경은 취소되고 알림도 `:266` 이전에 실패하므로 나가지 않는다. 남는 상태는 위와 같다(주문 `PREPARING`, 배송 `PENDING`, 입찰 `MATCHED`).

**응답**: HTTP `404`, body `ErrorResponse`: `code="S001"`, `message="배송 정보를 찾을 수 없습니다."`, path.
- 전역 핸들러가 `errorCode.getMessage()`(enum 기본 문구)를 쓴다 (`P/global/exception/GlobalExceptionHandler.java:459-470`).
- 코드: `P/domain/shipment/exception/ShipmentErrorCode.java:12` (`SHIPMENT_NOT_FOUND`, 404).
- 실제 원인 메시지는 응답에 나오지 않는다.

**참고(잠재 실패)**: `:260`을 통과하더라도 `:276` → `updateSaleStatusToSold` → `:116` `SaleBidQueryService.findByOrderId`가 연결된 `SaleBid`가 없으면 `IllegalArgumentException`을 던진다 (`P/domain/sale/service/query/SaleBidQueryService.java:26-28`). 이 블록은 try 밖이다. `SaleBid`는 즉시 판매 경로(`P/domain/sale/service/command/SaleBidCommandService.java:83`)에서만 주문과 연결되므로, 연결이 없는 일반 주문은 여기서도 실패한다.

## 2. 배송 완료 감지

**누가 / 언제 / 어떻게**: 사람이 아니라 서버 스케줄러가 감지한다.
- 주기: `@Scheduled(cron = "0 0 */6 * * *")` → 매일 0·6·12·18시(Spring 스케줄러 타임존 기준). `P/global/config/ShipmentBatchScheduler.java:34-40`. `JobLauncher`로 `updateShipmentStatusesJob`을 실행하며 `timestamp` 파라미터를 붙인다 (`:37-40`). 컨텍스트에는 `@EnableScheduling`이 이미 있다(`P/domain/event/scheduler/EventStatusScheduler.java:22`).
- Job/Step: `P/domain/shipment/config/UpdateShipmentStatusesJobConfig.java:54-82`. chunk 50, `faultTolerant().skip(Exception.class).skipLimit(50)` (`:66-77`).
- 대상(Reader): `SELECT s FROM OrderShipment s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL`, 페이지 50 (`UpdateShipmentStatusesJobConfig.java:87-97`, 쿼리 `:95`). 판매자 발송(`SellerShipment`)은 대상이 아니다.
- 브라우저: Step 시작 때 열고 끝나면 닫는다 (`P/domain/shipment/config/BrowserManageStepListener.java:14-25`).

**실제로 실행되는 처리 코드**: `ShipmentItemProcessor.process` (`P/domain/shipment/config/ShipmentItemProcessor.java:57-157`).
- Step이 `new ShipmentItemProcessor(...)`를 직접 생성한다 (`UpdateShipmentStatusesJobConfig.java:69-73`).
- 흐름: 페이지 열기 (`:72`) → CJ 추적 URL 이동 (`:81-83`) → `tbody#statusDetail tr` 대기 (`:87`) → HTML 파싱 (`:94`, `:167-212`) → 매핑 (`:95`) → 분기.

**실행되지 않는 비슷한 코드** (혼동 주의)
- `UpdateShipmentStatusesJobConfig.java:104-177`의 `@Bean shipmentItemProcessor()`: Step에서 참조하지 않는다.
- `UpdateShipmentStatusesJobConfig.java:186-220`의 `parseCjLogisticsStatus`(Jsoup 직접 요청): 호출처 없음.

- `CjTrackingPlaywright`: 수동 확인 API(`updateAndCheckShipmentStatus`, `OrderShipmentCommandService.java:452`)에서만 쓴다.

**택배사 상태 문자열 → 내부 상태**
- 값: 마지막 `tbody#statusDetail tr`의 5번째 `td`, `trim` (`ShipmentItemProcessor.java:181`).
- 매핑 (`:220-226`): `"배송완료"` → `DELIVERED`, `"배송출발"` → `OUT_FOR_DELIVERY`, 그 외 전부 → `IN_TRANSIT`.
- 분기 (`:101-126`): 현재 상태와 같으면 종료 (`:101-105`); `DELIVERED`면 완료 처리 (`:108-117`); `OUT_FOR_DELIVERY`면 상태만 변경 (`:119-121`); 그 외는 `IN_TRANSIT` (`:123-126`).

## 4. 주문 종류별 차이

**(a) 실배송 일반 구매 입찰 주문: 3이 진행되지 않는다**
- 등록 요청이 `:260`에서 실패한다 (1번 참고). 배송 완료 쪽은 실행되지 않는다.
- 배치 Reader는 `trackingNumber IS NOT NULL`인 건만 읽는다 (`UpdateShipmentStatusesJobConfig.java:95`). 운송장이 없으므로 이 주문은 배치 대상이 되지 않는다.
- 결과: 알림 0건, 주문 `PREPARING`, 배송 `PENDING`, 입찰 `MATCHED`, 판매 상태 변경 없음.

**(b) 즉시 구매 주문: 3이 진행되지 않는다. 실패 지점은 같지만 이유와 저장 결과가 다르다**
- 생성: `OrderCommandService.createInstantOrder` (`P/domain/order/service/command/OrderCommandService.java:218-`). Order는 `PENDING_PAYMENT`로 만들어진다 (`:244`). 결제는 동기로 호출되고 (`:305`), `saleBid.assignOrder(order)`로 연결된다 (`:279`).
- 결제 시점: `PaymentCommandService.notifyUsersAndUpdateSaleStatus` (`P/domain/payment/service/command/PaymentCommandService.java:383-410`)가 알림을 보내고 Sale을 `SOLD`로 바꾼다. 이 변경은 요청 안에서 이미 커밋된다.
- 즉시 구매 `OrderBid`는 생성 시점부터 `MATCHED`다 (`P/domain/order/service/command/OrderBidCommandService.java:189-205`, `:196`).
- 등록 요청: `OrderStatus` 전이표에서 `PENDING_PAYMENT`는 `PAYMENT_COMPLETED`, `COMPLETED`, `IN_WAREHOUSE`로만 간다(`OrderStatus.java:24`). 따라서 `IN_TRANSIT` 전이는 `:260`에서 실패하고 404 `S001`이 나온다. 3에 도달하지 않는다.
- 차이:
  - 실패 이유: (a)는 `PREPARING`에서, (b)는 `PENDING_PAYMENT`에서 전이를 시도해서 실패한다.
  - 저장된 것: (b)는 결제·판매 SOLD·알림이 이미 결제 요청에서 확정되어 있다. (a)는 결제·배송 생성까지만 있다.
  - 입찰: (a)와 (b) 모두 `MATCHED`에 머문다.
  - 주문 상태: (b)는 끝까지 `PENDING_PAYMENT`다. Kafka 경로가 아니라 동기 결제이므로 `PAYMENT_COMPLETED`를 거치지 않는다.

## 5. 실패 처리 (주기 처리 중 한 건 실패 시)

설정: chunk 50, `faultTolerant().skip(Exception.class).skipLimit(50)` (`UpdateShipmentStatusesJobConfig.java:51-52, 66-77`). 스킵 리스너는 로그만 남긴다 (`:251-287`).

**그 건**
- 처리 중 예외가 나면 writer로 넘어가지 않아 DB에 반영되지 않는다. 스킵 로그만 남는다.
- 대표 실패 원인:
  - CJ 페이지 대기 타임아웃 30초 (`ShipmentItemProcessor.java:30, 78, 87`) → `EXTERNAL_TRACKING_SERVICE_ERROR`로 래핑 (`:139-144`).
  - 파싱 실패 (`:174-177`, `:185-188`).
  - 상태 전이 불가. 예: `OUT_FOR_DELIVERY` 건이 `"배송완료"`/`"배송출발"`이 아닌 문자열을 받으면 매핑이 `IN_TRANSIT`이 된다. `OUT_FOR_DELIVERY → IN_TRANSIT`은 허용되지 않아 `IllegalStateException`이 나고 (`P/domain/shipment/entity/ShipmentStatus.java:23-28`, `P/domain/shipment/entity/OrderShipment.java:47-55`), 래핑되어 스킵된다 (`ShipmentItemProcessor.java:123-126, 133-145`). 이런 건은 `DELIVERED`가 될 때까지 매 주기마다 스킵된다.
- 배송 완료 처리 중 실패: `completeOrder`(`OrderShipmentCommandService.java:190-229`)가 `ShipmentException`을 던진다. `completeOrder`는 `@Transactional`(REQUIRED)이라 청크 트랜잭션에 참여하며, 예외가 전파되면 그 트랜잭션은 rollback-only가 된다(Spring 표준 동작). 따라서 그 건의 `Order COMPLETED`·`Sale SOLD`·알림 DB 변경은 남지 않는다.

**나머지 건**
- 같은 청크의 나머지 건은 청크 롤백 후 개별 재처리되어 처리될 것으로 보인다. 이 세부 동작은 Spring Batch 내부 구현에 의존하며, 이 코드만으로는 확정하지 못했다.
- 스킵 누적이 50건을 넘으면 Step이 실패하고 Job이 실패한다. 남은 건은 다음 주기(최대 6시간 뒤)까지 처리되지 않는다. 스케줄러는 `jobLauncher.run`의 예외만 잡는다 (`P/global/config/ShipmentBatchScheduler.java:41-43`).

**추가 위험 (분석, 실행으로 검증하지 않음)**: Reader는 상태 필터 + 페이지 오프셋 방식이다 (`UpdateShipmentStatusesJobConfig.java:89-96`). 처리 중 `DELIVERED`가 된 행은 결과 집합에서 빠지므로, 다음 페이지의 오프셋이 그만큼 어긋나 일부 `IN_TRANSIT` 건이 이번 실행에서 읽히지 않고 다음 주기로 밀릴 수 있다.

## 코드 의도 vs 실제 동작 차이

- 메서드명 `updateSaleStatusToSold`·`completeOrder`는 배송 완료 시점의 SOLD를 떠올리게 하지만, 실제로 Sale이 `SOLD`가 되는 시점은 **운송장 등록 시점**이다 (`OrderShipmentCommandService.java:276`, 설계상). 정상 경로에서 배송 완료 시점에는 SOLD 변경이 없다.
- `updateTrackingInfo`의 주석 "배송 상태가 변경되었으므로 주문 상태도 업데이트"(`:258`)와 달리, 일반 구매 주문에서는 주문 상태 갱신이 `:260`에서 항상 실패한다.
- 오류 응답의 메시지는 실제 원인이 아니라 enum 기본 문구이고, 코드는 `S001`이며 `ShipmentErrorCode`의 `S001`은 `SaleErrorCode`와도 충돌한다.
- `updateOrderAndSaleBidStatusToCompleted`는 `private`인데 `@Transactional`이 붙어 있다. 프록시 없이 내부 호출되므로 어노테이션은 효과가 없고, 예외를 삼켜 실패해도 등록은 성공으로 끝난다(`OrderShipmentCommandService.java:413-440`).
- 배치 Step은 `shipmentItemProcessor` `@Bean`을 쓰지 않고 `new ShipmentItemProcessor`를 쓴다. 빈 정의와 실제 구현이 따로 있다.

## 확인하지 못한 것

- 실제 실행 (DB, Kafka, PortOne, CJ 조회, Playwright 브라우저) 은 하지 않았다. 모든 결론은 코드 읽기에 근거한다.
- Spring Batch의 faultTolerant 청크 재처리 세부 동작은 코드 밖이라 확정하지 못했다(5번 "나머지 건").
