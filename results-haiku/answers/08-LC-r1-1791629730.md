# 구매자 배송: 운송장 등록 → 배송 완료 (코드 기준 답)

> 조사 방법: 소스 코드만 읽었다. DB·CJ 대한통운 연결·Playwright 실행은 하지 않았다. 아래 "추론"으로 표시한 부분은 코드 구조에서 도출한 것이고 실행으로 확인하지 않았다.
> 근거 경로는 저장소 루트 기준 전체 경로(`src/main/java/com/fream/back/...`)로 적었다.

## 요약

- **운송장 등록 API는 어떤 주문이든 성공하지 못한다.** 주문을 `IN_TRANSIT`으로 바꾸는 전이는 `SHIPMENT_STARTED`에서만 허용되는데, `SHIPMENT_STARTED`를 설정하는 코드가 없다.
- 배송 완료 감지 배치(6시간 주기)가 실제로 실행하는 처리는 `ShipmentItemProcessor.process`다. 등록 API가 막혀 있으므로 배치 대상 건은 운영자 `check-status` 호출로 `OUT_FOR_DELIVERY`까지 간 건뿐이다(코드 경로상).
- (a) 일반 구매 입찰 주문: 등록 실패. 설령 배송 완료가 감지돼도 주문이 `PREPARING → COMPLETED` 전이 불가라서 실패한다.
- (b) 즉시 구매 주문: 등록 실패(`PENDING_PAYMENT → IN_TRANSIT` 불가). 다만 `check-status`로 배송 완료가 감지되면 주문 `COMPLETED`까지 성공한다. 입찰은 `MATCHED`로 남는다.

## 1. 운송장 등록 요청

### 1-1. 진입점
- `PATCH /shipments/order/{shipmentId}/status`, 본문 `{courier, trackingNumber}`.
  - `src/main/java/com/fream/back/domain/shipment/controller/command/OrderShipmentCommandController.java:20` (`/shipments/order`), `:33-34` (PATCH 메서드), `:41` (서비스 호출), `:48` (성공 시 200, 빈 본문).
  - 요청 DTO: `src/main/java/com/fream/back/domain/shipment/dto/OrderShipmentRequestDto.java:10-12`.
- 이 컨트롤러는 예외를 잡지 않는다. 서비스 예외는 전역 핸들러로 간다.

### 1-2. 설계된 상태 변경 순서
`OrderShipmentCommandService.updateTrackingInfo` (`src/main/java/com/fream/back/domain/shipment/service/command/OrderShipmentCommandService.java:239-303`, `@Transactional`):

1. `courier`/`trackingNumber` 공백 검사 → `TRACKING_INFO_REQUIRED` (`:243-246`).
2. `OrderShipment` 조회 (`:249`).
3. `OrderShipment.updateTrackingInfo` → 택배사·송장번호 저장, `status = IN_TRANSIT` (`src/main/java/com/fream/back/domain/shipment/entity/OrderShipment.java:41-45`). **상태 전이 검사 없음.** `PENDING → SHIPPED → IN_TRANSIT` 표를 우회한다.
4. `Order.updateStatus(IN_TRANSIT)` (`:259-260`). 이 줄에서 `OrderStatus` 전이 규칙을 검사한다 (`src/main/java/com/fream/back/domain/order/entity/Order.java:113-121`).
5. 구매자 알림 "상품이 출발하였습니다" 1건 (`:265-271`).
6. `updateSaleStatusToSold(orderId)` (`:276`):
   - SaleBid 경로: `Sale`을 `SOLD`로 바꾸고 판매자 알림 1건 (`:116-138`). 창고 보관이면 창고 상태도 `SOLD`.
   - OrderBid 경로: 같은 전이를 한 번 더 시도하지만 이미 `SOLD`이면 건너뛴다 (`:151-176`).
7. 창고 보관이면 `updateWarehouseStatusToSold`를 한 번 더 호출 (`:279-286`). 6번 안에서 이미 호출했으므로 중복이다.
8. `updateOrderAndSaleBidStatusToCompleted` (`:289`) → `OrderBid`·`SaleBid`를 `MATCHED → COMPLETED` (`:413-432`). 이 메서드의 예외는 모두 삼킨다 (`:436-439`).

설계상 알림: 구매자 1건 + 판매자 최대 1건.
주의할 점: 판매 `SOLD` 전환과 입찰 `COMPLETED`가 **배송 완료가 아니라 운송장 등록 시점**에 일어나도록 짜여 있다 (`:276`, `:289`).

### 1-3. 실제 동작: 실배송 일반 구매 입찰 주문 (a)

**주문 생성·결제 단계 (등록 전 상태 확인):**
- 입찰 주문 생성: `Order`는 `PENDING_PAYMENT` (`src/main/java/com/fream/back/domain/order/service/command/OrderCommandService.java:81`). `OrderBid`는 `OrderBidCommandService` 에서 만든다 (`src/main/java/com/fream/back/domain/order/service/command/OrderBidCommandService.java:100`).
- 결제·배송 처리 (`OrderCommandService.processPaymentAndShipment`, `:112-`): 결제 `:139`. 실배송(창고 아님) 분기에서 `PAYMENT_COMPLETED → PREPARING` (`:175-176`). 같은 로직이 Kafka 소비자에도 있다 (`src/main/java/com/fream/back/domain/order/service/kafka/OrderEventConsumer.java:171`, `:195`, `:216-217`).
- `OrderBid`는 `MATCHED` (`src/main/java/com/fream/back/domain/order/service/command/OrderCommandService.java:189`).
- 결제 후 판매 상태: `src/main/java/com/fream/back/domain/payment/service/command/PaymentCommandService.java:83`이 `notifyUsersAndUpdateSaleStatus`를 호출하고, 연결된 `Sale`을 **결제 시점에** `SOLD`로 바꾼다 (`src/main/java/com/fream/back/domain/payment/service/command/PaymentCommandService.java:419`). 전이 가능 여부를 검사하지 않는다. 즉 Sale은 운송장 등록 전에 이미 `SOLD`다.

**운송장 등록 (PATCH) 실제 동작:**
- 메모리에서 `shipment.updateTrackingInfo`까지는 실행된다 (`src/main/java/com/fream/back/domain/shipment/service/command/OrderShipmentCommandService.java:256`).
- `order.updateStatus(IN_TRANSIT)`에서 실패한다 (`:260`). 현재 상태 `PREPARING`에서 `IN_TRANSIT`은 허용 목록에 없다 (`src/main/java/com/fream/back/domain/order/entity/OrderStatus.java:26`: `PREPARING → {IN_WAREHOUSE, SHIPMENT_STARTED}`; `:28`: `SHIPMENT_STARTED → IN_TRANSIT`만 허용). `Order.updateStatus`가 `InvalidOrderStatusException`을 던진다 (`src/main/java/com/fream/back/domain/order/entity/Order.java:117`).
- `:293-302`의 `catch (Exception e)`가 이를 잡아 `ShipmentException(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: ...")`로 감싼다 (`:297-301`).
- **저장되는 것: 없다.** 예외가 `RuntimeException`(`GlobalException` 계열)으로 메서드 밖으로 나가므로 트랜잭션이 롤백된다. 송장 번호, 배송 상태, 구매자 알림(`:266` 이전에 실패) 모두 남지 않는다.
- **응답:** `GlobalExceptionHandler.handleShipmentException` (`src/main/java/com/fream/back/global/exception/GlobalExceptionHandler.java:459-471`)이 처리한다.
  - HTTP **404**, 코드 **S001**, 메시지는 enum 기본 문구 `"배송 정보를 찾을 수 없습니다."` (`src/main/java/com/fream/back/domain/shipment/exception/ShipmentErrorCode.java:12`).
  - 상세 메시지("운송장 정보 업데이트 중 오류 발생 ...")는 응답에 나가지 않는다. 로그에만 남는다.

**원인 요약 (이 실패는 모든 주문에서 일어난다):**
- `IN_TRANSIT`으로 들어가는 전이는 `SHIPMENT_STARTED → IN_TRANSIT` 하나뿐이다 (`src/main/java/com/fream/back/domain/order/entity/OrderStatus.java:28`).
- `SHIPMENT_STARTED`는 어디서도 설정되지 않는다. 전역 검색 결과 `src/main/java/com/fream/back/domain/order/entity/OrderStatus.java`의 정의·전이 표와 `src/main/java/com/fream/back/domain/order/controller/query/OrderQueryController.java:207`(표시 문구)에만 있다.
- 따라서 `Order`가 `IN_TRANSIT`이 될 수 없고, 운송장 등록 PATCH는 항상 404 S001로 끝난다.
- 엣지: `Order.status`가 `null`이면 전이 검사를 건너뛴다 (`src/main/java/com/fream/back/domain/order/entity/Order.java:114`). 정상 데이터에는 해당하지 않는다.

## 2. 배송 완료 감지

### 2-1. 누가·언제·어떻게
- **주기 배치**가 감지한다. 사람이 하는 것이 아니다.
- 스케줄러: `src/main/java/com/fream/back/global/config/ShipmentBatchScheduler.java:34` `@Scheduled(cron = "0 0 */6 * * *")` → **6시간마다** (0·6·12·18시 정각). `:36-40`에서 `JobLauncher.run(updateShipmentStatusesJob, timestamp)`. 예외는 `printStackTrace` 후 삼킨다 (`:41-43`).
- 운영자 수동 확인: `check-status` API (`src/main/java/com/fream/back/domain/shipment/controller/command/OrderShipmentCommandController.java:58-94`, `:103-138`)도 배송 완료를 감지해 같은 완료 처리를 한다.

### 2-2. 대상과 실제 실행 코드
- Job/Step: `src/main/java/com/fream/back/domain/shipment/config/UpdateShipmentStatusesJobConfig.java:55-60`, `:63-82`. chunk 50 (`:51`, `:67`).
- Reader 대상: `src/main/java/com/fream/back/domain/shipment/config/UpdateShipmentStatusesJobConfig.java:95` → `status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND trackingNumber IS NOT NULL`, 페이지 50 (`:91-94`).

- **실행되지 않는 비슷한 코드 (무시할 것):**

- 배치 처리 흐름 요약: `process` 안에서 `DELIVERED`를 만나면 `completeOrder`까지 같은 청크 트랜잭션에서 실행된다 (`src/main/java/com/fream/back/domain/shipment/config/ShipmentItemProcessor.java:108-117`).

### 2-3. 택배사 상태 문자열 → 내부 상태
`src/main/java/com/fream/back/domain/shipment/config/ShipmentItemProcessor.java:220-226`:

- `"배송출발"` → `OUT_FOR_DELIVERY`
- 그 외 모든 문자열 → `IN_TRANSIT`
- 텍스트가 없으면 파싱 단계에서 `TRACKING_HTML_PARSE_ERROR`(S301)로 실패한다 (`:183-189`).

처리 분기 (`:101-105`, `:108-126`):

- `OUT_FOR_DELIVERY` / 그 외 → `updateStatus`. 단, `OUT_FOR_DELIVERY → IN_TRANSIT`은 `src/main/java/com/fream/back/domain/shipment/entity/ShipmentStatus.java:23-27`에서 허용되지 않아 `IllegalStateException`이 나고 그 건은 skip된다.

## 3. 배송 완료 판정 이후

### 3-1. 배치 경로 (`src/main/java/com/fream/back/domain/shipment/config/ShipmentItemProcessor.java:108-117`)
순서:
1. `OrderShipment.status = DELIVERED` (`:113`). `IN_TRANSIT`·`OUT_FOR_DELIVERY`에서 허용 (`src/main/java/com/fream/back/domain/shipment/entity/ShipmentStatus.java:17-27`).
2. `orderService.completeOrder(orderId)` (`:116` → `src/main/java/com/fream/back/domain/shipment/service/command/OrderShipmentCommandService.java:191-229`, `@Transactional`):
   - `OrderBid` 조회, 없으면 예외 (`:196-197`).
   - `Order.updateStatus(COMPLETED)` (`:204`).
   - `updateSaleStatusToSold` (`:208`): 판매 상태가 전이 가능할 때만 `SOLD` + 판매자 알림 (`:119-138`). 결제 시 이미 `SOLD`였다면 아무 일도 없다 (`:419`).
   - 구매자 알림 `"[completeOrder] 주문이 완료 처리되었습니다. ..."` 1건 (`:211-217`). 알림 텍스트에 디버그용 `[completeOrder]` 문자열이 그대로 노출된다.
   - 예외는 `ShipmentException(ORDER_NOT_FOUND_FOR_SHIPMENT, S102)`로 감싼다 (`:221-227`).
3. `notifyShipmentCompleted(order)` (`:117`, 본체 `src/main/java/com/fream/back/domain/notification/service/command/NotificationCommandService.java:219-234`) → 구매자 알림 `"[배송 완료] ..."` 1건.

정리:
- **엔티티:** `OrderShipment` → `DELIVERED`, `Order` → `COMPLETED`, `Sale` → `SOLD` (이미 결제 시 `SOLD`였을 가능성이 높음).
- **알림:** 구매자 **2건** (`[completeOrder]` + `[배송 완료]`). 판매자는 **0건**이거나 **1건**. 판매자 알림은 SaleBid 경로이면서 `Sale`이 `ON_AUCTION`/`SELLING`일 때만 생긴다 (`src/main/java/com/fream/back/domain/sale/entity/SaleStatus.java:91-101`: `SOLD`로 갈 수 있는 상태가 이 둘뿐이다).
- **입찰:** `OrderBid`·`SaleBid`는 **`MATCHED` 그대로**다. 배치의 `completeOrder`는 입찰을 `COMPLETED`로 바꾸지 않는다. 입찰 완료는 `updateTrackingInfo`(`:289`)에만 있다.
- 알림 푸시는 커밋 전에 나간다. `createNotification`이 트랜잭션 안에서 바로 STOMP 전송한다 (`src/main/java/com/fream/back/domain/notification/service/command/NotificationCommandService.java:57`).

### 3-2. `check-status` 경로 (참고)
`updateAndCheckShipmentStatus` (`src/main/java/com/fream/back/domain/shipment/service/command/OrderShipmentCommandService.java:452-516`):
- `DELIVERED`이면 `shipment.updateStatus(DELIVERED)` → `completeOrder` (`:483-489`). 같은 완료 처리를 하지만 `notifyShipmentCompleted`는 호출하지 않는다. 구매자 알림은 1건이다.
- 응답은 `ShipmentStatusResponse`(`200`, `{status: DELIVERED}`).

## 4. 주문 종류별 차이

| 항목 | (a) 실배송 일반 구매 입찰 | (b) 즉시 구매 |
|---|---|---|
| 결제 후 주문 상태 | `PREPARING` (`src/main/java/com/fream/back/domain/order/service/command/OrderCommandService.java:175-176`) | **`PENDING_PAYMENT` 그대로.** 즉시 구매 생성(`src/main/java/com/fream/back/domain/order/service/command/OrderCommandService.java:244`) 과정과 `processPayment`(`:305`) 어디에서도 `Order` 상태를 바꾸지 않는다. `PaymentCommandService`에도 `order.updateStatus`가 없다. |

| `check-status`가 DELIVERED 감지 시 | **실패** — `PREPARING → COMPLETED` 불가 (`src/main/java/com/fream/back/domain/shipment/service/command/OrderShipmentCommandService.java:204`) → `ShipmentException(S102)` (`:223-227`), 롤백, 404 | **성공** — `PENDING_PAYMENT → COMPLETED` 허용 (`src/main/java/com/fream/back/domain/order/entity/OrderStatus.java:24`). 배송 `DELIVERED`, 주문 `COMPLETED`, 구매자 알림 1건 |

| 배치로 들어왔을 때 | `OUT_FOR_DELIVERY`에 머문 채 매 6시간 재시도 후 skip (아래 5번) | 배치 경로로는 완료 가능. 판매자 알림 없음 (이미 `SOLD`) |

추가로 확인한 점:
- (a)는 `OrderBid`에 `Sale`이 연결돼 있어도 `SaleBid`가 없다 (일반 입찰 판매 연결은 `src/main/java/com/fream/back/domain/sale/service/command/SaleCommandService.java:79`에서 `OrderBid.assignSale`만 한다. `SaleBid`에 주문을 붙이는 곳은 즉시 구매 `src/main/java/com/fream/back/domain/order/service/command/OrderCommandService.java:279-280`과 즉시 판매 `src/main/java/com/fream/back/domain/sale/service/command/SaleBidCommandService.java:82-83` 두 곳뿐이다). `updateSaleStatusToSold`의 `saleBidQueryService.findByOrderId`는 없으면 `null`이 아니라 `IllegalArgumentException`을 던진다 (`src/main/java/com/fream/back/domain/sale/service/query/SaleBidQueryService.java:26-30`, `src/main/java/com/fream/back/domain/shipment/service/command/OrderShipmentCommandService.java:116`). 그래서 `if (saleBid != null)` 분기는 실행되지 않는다. 지금은 `:204`에서 먼저 실패하므로 드러나지 않지만, 주문 상태 전이가 통과했다면 여기서 실패했을 것이다.

## 5. 실패 처리 (주기 처리 중 한 건 실패)

설정:
- 청크 50 (`src/main/java/com/fream/back/domain/shipment/config/UpdateShipmentStatusesJobConfig.java:51`, `:67`), `faultTolerant().skip(Exception.class).skipLimit(50)` (`:75-77`), SkipListener가 로그만 남긴다 (`:78`, `:251-287`).
- 스케줄러는 Job 실행 예외를 삼킨다 (`src/main/java/com/fream/back/global/config/ShipmentBatchScheduler.java:41-43`).

실패한 건:
- 발생 지점은 여러 곳이다. CJ 조회 실패·파싱 실패(`src/main/java/com/fream/back/domain/shipment/config/ShipmentItemProcessor.java:138-145`, `:183-189`), `OUT_FOR_DELIVERY → IN_TRANSIT` 전이 불가(`:125`), `completeOrder` 실패(`:116`, `src/main/java/com/fream/back/domain/shipment/service/command/OrderShipmentCommandService.java:221-227`).
- 이 건은 writer까지 가지 않는다. 처리 중 바꾼 엔티티 상태는 청크 트랜잭션이 롤백되면 DB에 반영되지 않는다.
- 상태는 이전 값(`IN_TRANSIT` 또는 `OUT_FOR_DELIVERY`)으로 남고, 다음 6시간 실행에서 다시 대상이 된다.
- (a)처럼 완료가 구조적으로 불가능한 건은 매 실행마다 같은 실패를 반복한다.

같은 청크의 나머지 건:
- `completeOrder`는 `@Transactional`이므로 processor 안에서 호출하면 청크 트랜잭션에 참여한다 (`src/main/java/com/fream/back/domain/shipment/service/command/OrderShipmentCommandService.java:190-191`). 그 안에서 `RuntimeException`이 나가면 공유 트랜잭션이 롤백 전용으로 표시된다. 즉 같은 청크에서 먼저 처리된 건들도 커밋 시점에 함께 날아갈 수 있다.
- Spring Batch 5.2의 fault-tolerant 처리에서는 청크가 롤백된 뒤 건별로 다시 처리되어 실패 건만 skip되고 나머지는 저장되는 것이 예상되는 동작이다 (추론: 실행으로 검증하지 않음). 이 경우 실패 건은 skip 카운트를 1 올리고, skip이 50을 넘으면 Step이 실패한다.

추가 관찰 (추론):
- Reader는 상태 필터 + 오프셋 페이징이고 정렬이 없다 (`src/main/java/com/fream/back/domain/shipment/config/UpdateShipmentStatusesJobConfig.java:91-96`). 청크 안에서 `DELIVERED`로 바뀌어 필터에서 빠진 건이 생기면 다음 페이지의 오프셋이 밀려 같은 실행에서 일부 건을 건너뛸 수 있다. 다음 6시간 실행에서 처리된다.
