# 질문: 즉시 구매는 어떻게 처리되나

> 근거 경로는 `src/main/java/com/fream/back/` 생략. 모든 내용은 코드 읽기로 확인했고, 실행·테스트는 하지 않았다.
> NAV.md와 `nav/flow-trade.md`, `nav/order.md`, `nav/payment.md`를 먼저 읽고 요약을 얻은 뒤 해당 코드를 직접 대조했다. 요약과 어긋나는 부분은 아래에 따로 표시했다.

## 1. 요청 진입점, 처리 방식, 반환 ID

- **API**: `POST /order-bids/instant` — `domain/order/controller/command/OrderBidCommandController.java:89-90`
- **요청 본문**: `InstantOrderRequestDto`(`saleBidId`, `addressId`, `warehouseStorage`, `paymentRequest`) — `domain/order/dto/InstantOrderRequestDto.java`
- **컨트롤러 전처리**: 이메일은 SecurityContext에서 꺼내 `paymentRequest.userEmail`을 덮어쓰고, `orderId`는 null로 비운다 — `OrderBidCommandController.java:98`, `:120-121`
- **처리 흐름**: 컨트롤러 → `OrderBidCommandService#createInstantOrderBid`(`@Transactional`, `domain/order/service/command/OrderBidCommandService.java:118-149`) → `OrderCommandService#createInstantOrder`(`@Transactional`, `OrderCommandService.java:219-220`) → `PaymentCommandService#processPayment`(동기 호출). 결제 PortOne 호출까지 요청 스레드 안에서 **하나의 DB 트랜잭션**으로 실행된다.
- **동기/비동기**: **동기**. Kafka를 쓰지 않는다. 일반 구매 입찰의 `process-payment-shipment`(202 Accepted, Kafka)와 다르다.
- **응답 ID**: **OrderBid의 ID**다. 컨트롤러 변수명은 `orderId`지만 실제로는 `createInstantOrderBid(...)`가 반환한 OrderBid의 `getId()`다 — `OrderBidCommandController.java:101-107`, 응답 `:109`. Order ID는 응답에 없다.
- **참고(요약 문서와 다름 없음)**: 입력 검증은 null 여부만 본다 — `OrderBidCommandService.java:154-167`.

## 2. 생성되는 엔티티와 상태 변화 순서

같은 트랜잭션 안에서 아래 순서로 진행된다. 각 단계 직후 상태를 적었다.

| 순서 | 동작 | 근거 | 직후 상태 |
|---|---|---|---|
| 0 | 구매자 조회, SaleBid 조회(`findById`), Sale 참조 | `OrderBidCommandService.java:126-130`, `domain/sale/service/query/SaleBidQueryService.java:21-24` | 변경 없음 |
| 1 | 주소 조회 후 **Order 신규 생성·저장** (`user`=구매자, `totalAmount`=판매 입찰 가격) | `OrderCommandService.java:238-247` | **Order = PENDING_PAYMENT** |
| 2 | `paymentRequest.orderId = order.getId()` 설정 | `OrderCommandService.java:250` | Order 변화 없음 |
| 3 | **OrderItem 신규 생성**(수량 1, 가격=판매 입찰 가격) 후 Order에 추가 | `OrderCommandService.java:255-256` | Order = PENDING_PAYMENT |
| 4 | **OrderShipment 신규 생성**(주소록 값 스냅샷) 후 Order에 연결 | `OrderCommandService.java:264-271`, `domain/shipment/service/command/OrderShipmentCommandService.java:56-74` | OrderShipment = **PENDING** (`:67`) |
| 5 | **SaleBid 매칭**: `assignOrder(order)` + `updateStatus(MATCHED)`, `entityManager.flush()` | `OrderCommandService.java:279-283`, `domain/sale/entity/SaleBid.java:58-61, 66-68` | **SaleBid = MATCHED**, SaleBid.order = 새 Order |
| 6 | Sale이 창고 보관이면 기존 WarehouseStorage를 `ASSOCIATED_WITH_ORDER`로 변경 | `OrderCommandService.java:291-293`, `domain/warehouseStorage/service/command/WarehouseStorageCommandService.java:117-140` | WarehouseStorage = ASSOCIATED_WITH_ORDER (창고 보관인 경우만) |
| 7 | `processPayment` 호출 — 결제 생성(3번 참고) | `OrderCommandService.java:305` | Payment 신규 생성. **Order는 그대로 PENDING_PAYMENT** |
| 7-a | 결제 성공 후 알림 발송, **Sale → SOLD** | `PaymentCommandService.java:383-404` | **Sale = SOLD** (Sale 상태 전이 검증 없음, `domain/sale/entity/Sale.java:73-75`) |
| 8 | **OrderBid 신규 생성**: `status=MATCHED`, `order`, `sale`, `isInstantPurchase=true` 후 저장 | `OrderBidCommandService.java:189-207` (MATCHED `:196`, markAsInstantPurchase `:205`) | **OrderBid = MATCHED** |

- 새로 생기는 엔티티: Order, OrderItem, OrderShipment, Payment(CARD/GENERAL 성공 시), OrderBid.
- 기존 엔티티 변경: SaleBid(→MATCHED), Sale(→SOLD), WarehouseStorage(→ASSOCIATED_WITH_ORDER, 창고 보관인 경우만).
- **`OrderStatus`는 끝까지 PENDING_PAYMENT다.** 이 경로에서는 `order.assignPayment`도 호출하지 않는다 (`OrderCommandService.java:220-311`에 해당 호출 없음). `nav/order.md`의 "즉시 구매 경로에서 Order는 PENDING_PAYMENT로 남음" 설명과 일치한다.

## 3. 결제 수단별 결과, 끝까지 성공하는지, 카드 실패 시

결제 실행은 `PaymentCommandService#processPayment`(`PaymentCommandService.java:57-107`) 한 곳이다. 먼저 `validatePaymentRequest`에서 `order.id == requestDto.orderId`, 구매자 이메일 일치, 금액 > 0을 검사한다(`:131-145`). 그 뒤 타입별로 분기한다(`:67-80`).

### 3-1. CARD
- 저장된 카드(`paymentInfoId`)를 조회·복호화하고(`PaymentCommandService.java:166`), `PortOneApiClient#processCardPayment`(`domain/payment/portone/PortOneApiClient.java:229`)를 호출한다.
- 성공 판정은 `"success".equals(response.get("status"))` 한 줄이다 (`PaymentCommandService.java:203-206`). 맞으면 `PAID` + `updateSuccessStatus(true)`.
- **주의**: `CardPayment` 빌더 생성자가 `setPaidAmount(paidAmount)`를 호출하고, 이 메서드는 금액 > 0이면 `isSuccess = true`로 만든다 (`domain/payment/entity/CardPayment.java:38`, `domain/payment/entity/Payment.java:60-63`). 따라서 `status`가 `"success"`가 아니어도 `isSuccess`는 이미 true다. 이 값으로 성공을 판정하는 곳은 Kafka 주문 경로의 `OrderEventConsumer.java:174`이고, 즉시 구매 경로에는 이 검사가 없다.
- 이 저장소만으로는 PortOne이 실제로 보내는 `status` 값을 확인할 수 없다.

### 3-2. ACCOUNT (계좌이체)
- 은행명 검증 후 `AccountPayment`를 만들고, 기본값 PENDING 상태에서 `updateStatus(PENDING)`을 호출한다 (`PaymentCommandService.java:244`, `:260`).
- `PaymentStatus.canTransitionTo`는 PENDING → PAID만 허용하므로(`domain/payment/entity/PaymentStatus.java:12-13`), PENDING → PENDING은 `IllegalStateException`이 된다 (`domain/payment/entity/Payment.java:70-76`).
- 예외는 `PaymentProcessingException`으로 감싸져 전파되고(`PaymentCommandService.java:272-277`), 트랜잭션이 롤백된다.
- **결론: 계좌이체 즉시 구매는 항상 실패한다.**

### 3-3. GENERAL (일반 결제)
- `impUid`가 비어 있지 않은지만 확인한다 (`PaymentCommandService.java:297-300`). PortOne에 검증 요청을 보내지 않는다.
- 바로 `updateSuccessStatus(true)` + `PAID` (`:313-314`). 클라이언트가 보낸 impUid와 금액을 그대로 믿는다.
- 나머지 흐름은 성공으로 끝난다.

### 3-4. 즉시 구매가 끝까지 성공하는 경우
- **CARD(PortOne 응답이 성공 처리되는 경우)와 GENERAL만** 끝까지 성공한다. ACCOUNT는 항상 실패한다.
- 성공 시 응답은 200과 OrderBid ID다 (`OrderBidCommandController.java:109`). 하지만 Order는 PENDING_PAYMENT로 남는다(2번 참고).

### 3-5. 결제 대행사(PortOne)가 카드 결제를 실패로 응답하는 경우
세 가지로 나뉜다.

- **(a) 응답 code ≠ 0** (비즈니스 실패): `PortOneApiClient.java:270-275`에서 `PaymentProcessingException` → `PaymentCommandService.java:180-181`, `:89-94`에서 그대로 재던짐 → `OrderCommandService.java:305-308`에서 `OrderPaymentProcessingFailedException`으로 감싸짐 → `OrderBidCommandService`에서 재던짐 → **트랜잭션 롤백**.
- **(b) HTTP/통신 오류**: `PortOneApiClient.java:288-290`에서 `PaymentApiException` → (a)와 같은 경로로 **롤백**.
- **(c) code = 0이지만 `status != "success"`**: 예외가 발생하지 않는다. `CardPayment`는 PENDING 상태로 저장되고 `isSuccess`는 true다(3-1 참고). 이어서 알림이 나가고 **Sale은 SOLD**가 되며, OrderBid가 만들어지고 **200 성공 응답**을 반환한다. Order는 PENDING_PAYMENT, 결제는 PAID가 아니다. 실패가 사용자에게 알려지지 않는 경로이므로 가장 중요한 문제다.
- 롤백 시 결과: Order, OrderItem, OrderShipment, Payment, OrderBid, SaleBid 변경, Sale SOLD, WarehouseStorage 변경이 모두 없던 일이 된다. 알림도 DB 저장이 같은 트랜잭션이므로 사라진다(단, 아래 4번의 실시간 푸시는 예외). 응답은 `GlobalExceptionHandler.handleOrderException`(`global/exception/GlobalExceptionHandler.java:325-`)이 OrderException의 `errorCode` HTTP 상태로 만든다.

## 4. 알림 수신자, 시점, 방식

- **수신자 2명**, 둘 다 `NotificationCategory.SHOPPING`, `NotificationType.BID`:
  - **구매자**(`order.getUser()`): "결제가 완료되었습니다. 주문 ID: {orderId}" (`PaymentCommandService.java:436-443`)
  - **판매자**(`sale.getSeller()`): "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}" (`PaymentCommandService.java:447-454`)
- **시점**: `processPayment`가 결제를 만든 직후, 같은 트랜잭션 안에서 `notifyUsersAndUpdateSaleStatus` → `sendNotifications` 순으로 실행된다 (`PaymentCommandService.java:83`, `:403`, `:416`). 결제 실패 경로에서는 실행되지 않는다.
- **방식**: `NotificationCommandService#createNotification`이 알림을 DB에 저장한 뒤(`domain/notification/service/command/NotificationCommandService.java:44-67`), Redis에 해당 사용자 키가 있을 때만 `messagingTemplate.convertAndSendToUser(email, ...)`로 WebSocket(STOMP) 푸시를 한다 (`:303-317`, Redis 확인 `:307`). Kafka `notification-topic`은 이 경로에서 사용하지 않는다.
- **주의(트랜잭션)**: 푸시는 커밋 전에 나간다. 이후 `OrderBid` 저장 등이 실패해 롤백되면 DB에는 알림이 없지만 클라이언트에는 이미 푸시가 도착한 상태가 된다.
- 알림 생성 자체가 실패해도 예외를 던지지 않고 로그만 남긴다 (`PaymentCommandService.java:457-461`). 같은 방식으로 `notifyUsersAndUpdateSaleStatus` 전체도 예외를 삼킨다 (`:421-425`). 즉 알림이나 Sale SOLD 갱신이 실패해도 즉시 구매는 성공으로 끝날 수 있다.
- 주문 입찰 생성 자체는 알림을 보내지 않는다 (`OrderBidCommandService`, `OrderCommandService`에 알림 호출 없음).

## 5. 처리 후 최종 상태, 창고 보관 선택 시

### 5-1. 정상 완료(CARD 또는 GENERAL) 후 최종 상태

| 대상 | 최종 상태 | 근거 |
|---|---|---|
| Order | **PENDING_PAYMENT** (변경 없음, 결제 연결도 Order 쪽은 없음) | 2번 표 7 행, `OrderCommandService.java:220-311` |
| OrderBid | MATCHED, `isInstantPurchase=true`, `sale`·`order` 연결 | `OrderBidCommandService.java:196-205` |
| SaleBid | MATCHED, `order` 연결 (COMPLETED 아님) | `OrderCommandService.java:279-280` |
| Sale | **SOLD** | `PaymentCommandService.java:404` |
| Payment | CARD 또는 GENERAL = PAID, `isSuccess=true`, `order_id` 연결 | `PaymentCommandService.java:203-206`, `:313-314` |
| OrderShipment | PENDING | `OrderShipmentCommandService.java:67` |

- 배송 추적·구매 확정 단계는 이 경로에 없다. 구매자의 송장 등록 경로(`OrderShipmentCommandService#updateTrackingInfo`)에서 SaleBid/OrderBid가 COMPLETED가 된다 (`nav/flow-trade.md` 5절, 이 답에서는 코드 대조 안 함).

### 5-2. 구매자가 "창고 보관"을 선택한 경우
- **요청의 `warehouseStorage` 값은 즉시 구매 처리에 쓰이지 않는다.** `OrderBidCommandService`가 `isWarehouseStorage`를 넘기지만(`OrderBidCommandService.java:119-137`), `OrderCommandService#createInstantOrder`의 `isWarehouseStorage` 매개변수(`OrderCommandService.java:221`)는 본문 어디에서도 사용되지 않는다.
- 실제 분기는 **판매자가 등록한 `Sale.isWarehouseStorage`**(`domain/sale/entity/Sale.java:43`)로만 한다 (`OrderCommandService.java:291-293`). 참이면 판매 측 기존 WarehouseStorage를 `ASSOCIATED_WITH_ORDER`로 바꾸고, 거짓이면 아무 일도 없다.
- 그래서 구매자가 창고 보관을 선택해도 결과가 달라지지 않는다. 판매자가 창고 보관으로 등록했다면 구매자가 선택하지 않아도 같은 상태 전이가 일어난다.
- 구매자 쪽 창고 보관 엔티티는 만들어지지 않는다. `createOrderStorage` 호출처는 Kafka 소비자 `OrderEventConsumer.java:199`와 사용되지 않는 `OrderCommandService.java:170`, 시드 데이터 `DataInitializer.java:551`뿐이다. 따라서 Order가 `IN_WAREHOUSE`로 바뀌지도 않는다.

## 6. 기타 확인된 문제 (질문 외 관찰)

- **이미 매칭된 판매 입찰을 또 살 수 있다**: `getSaleBidAndValidate`(`OrderBidCommandService.java:172-184`)는 null 여부만 확인하고 상태(MATCHED/COMPLETED)를 보지 않는다. `SaleBidQueryService.findById`도 상태 조건이 없다(`SaleBidQueryService.java:21-24`). 잠금도 없다(`domain/sale/repository/` 에 Lock 없음). 동시에 두 번 요청하면 같은 SaleBid에 Order가 두 개 생길 수 있다.
- **메서드 이름과 실제 동작의 차이**: `getSaleBidAndValidate`는 "validate"라는 이름이지만 검증은 null 체크뿐이다.
- **PaymentStatus 값과 성공 판정의 불일치**: 3-1에서 설명한 것처럼 `isSuccess`는 생성 시점에 true이고, 상태 값은 문자열 `"success"` 비교로만 바뀐다.
- **포인트 미사용**: 즉시 구매는 포인트를 차감하지 않는다(`usedPoints` 0 고정, 호출 없음).

## 확인하지 못한 것
- PortOne이 실제로 응답하는 `status` 값(3-1, 3-5의 (c)). 이 저장소에는 PortOne 명세가 없다.
- 실제 DB 격리 수준과 동시 요청 동작. 코드만 읽었고 실행하지 않았다.
- 프런트엔드의 호출 방식(어떤 `paymentRequest` 필드를 보내는지)은 이 저장소에서 확인하지 않았다.
