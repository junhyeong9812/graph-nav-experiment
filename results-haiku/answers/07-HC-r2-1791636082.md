# 즉시 구매는 어떻게 처리되나

모든 경로는 저장소 루트 기준이다. 접두사 `D/`는 `src/main/java/com/fream/back/domain/`을 줄인 것이다.

대상 API는 구매자가 판매 입찰(`saleBidId`)을 골라 호출하는 `POST /order-bids/instant`이다. 판매자가 올린 입찰을 대상으로 하는 `POST /sale-bids/instant`(`D/sale/controller/command/SaleBidCommandController.java:43`)는 판매자 쪽 흐름이라 이 질문의 대상이 아니다.

---

## 1. 요청 진입과 처리 단계

- 진입점: `D/order/controller/command/OrderBidCommandController.java:89-90` `@PostMapping("/instant")`, 요청 본문은 `InstantOrderRequestDto`(`D/order/dto/InstantOrderRequestDto.java:67-78`)이다. 필드는 `saleBidId`, `addressId`, `warehouseStorage`, `paymentRequest`다.
- 처리 순서:
  1. 컨트롤러가 인증 이메일을 꺼낸다(`OrderBidCommandController.java:92`).
  2. 결제 요청에 구매자 이메일을 넣는다(`enrichPaymentRequest`, `OrderBidCommandController.java:120-123`).
  3. `OrderBidCommandService.createInstantOrderBid`를 호출한다(`D/order/service/command/OrderBidCommandService.java:119-149`).
  4. 서비스는 입력값을 검증하고(`:154-167`), 구매자를 조회하고(`:126`), `saleBid`와 `sale`을 조회한다(`:128-130`, `:172-184`).
  5. `OrderCommandService.createInstantOrder`로 주문을 만든다(`D/order/service/command/OrderCommandService.java:220-317`).
  6. `OrderBid`를 만들고 저장한다(`OrderBidCommandService.java:142`, `:189-207`).
  7. 성공하면 HTTP 200과 `"즉시 구매가 성공적으로 처리되었습니다."` 메시지를 돌려준다(`OrderBidCommandController.java:109`).
- 동기/비동기: 전부 동기다. 한 HTTP 요청 안에서 DB 트랜잭션, PortOne 결제 API 호출, 알림 저장과 WebSocket 발송이 모두 일어난다. 이 경로에는 Kafka가 없다. `OrderBidCommandService`, `OrderCommandService.createInstantOrder`, `PaymentCommandService`에는 Kafka producer 호출이 없다(Kafka producer는 `D/order/controller/command/OrderCommandController.java:54`의 일반 주문 처리 경로에서만 쓰인다).
- 트랜잭션: `OrderBidCommandService.createInstantOrderBid`(`:118`), `OrderCommandService.createInstantOrder`(`:219`), `PaymentCommandService` 클래스 전체(`D/payment/service/command/PaymentCommandService.java:37`)가 모두 `@Transactional`이다. 결제는 같은 트랜잭션 안에서 실행된다. 예외는 `GlobalException`을 거쳐 `RuntimeException`이므로(`global/exception/GlobalException.java:10`) 예외가 나면 전체가 롤백된다.
- 응답 ID: `orderId`라는 변수에 담기는 값은 **주문(Order) ID가 아니라 `OrderBid`의 ID**다. `createInstantOrderBid(...).getId()`를 쓰기 때문이다(`OrderBidCommandController.java:101-107`). 이 메서드의 반환형은 `OrderBid`다(`OrderBidCommandService.java:119`).

## 3. 결제 수단별 결과와 실패 처리

결제는 `PaymentCommandService.processPayment`에서 `paymentType`(`CARD`, `ACCOUNT`, `GENERAL`)으로 갈린다(`PaymentCommandService.java:67-80`). 공통 검증은 `:117-146`이다. 주문 ID 일치, 이메일 일치, 금액 양수를 확인한다. `paymentType`은 `PaymentRequestDto`의 `@JsonSubTypes`로 정해진다(`D/payment/dto/PaymentRequestDto.java:20-25`).

**카드(CARD)** (`PaymentCommandService.java:157-225`)
- 저장된 결제 정보로 PortOne 카드 결제를 호출한다(`:179`, 구현은 `D/payment/portone/PortOneApiClient.java:229`).
- PortOne 응답의 `code`가 0이 아니면 `PaymentProcessingException`을 던진다(`PortOneApiClient.java:270-275`). 이 예외는 `PaymentCommandService`와 `OrderCommandService`에서 감싸져 다시 던져지고(`OrderCommandService.java:304-309`), `OrderBidCommandService`의 `handleOrderBidCreationException`을 거쳐 전파된다(`OrderBidCommandService.java:145-147`, `:212-218`). 결과적으로 **트랜잭션 전체가 롤백되고 요청은 실패한다.** 주문, 주문 항목, 배송지, `SaleBid` 매칭, `Sale`의 SOLD 변경, 알림은 모두 저장되지 않는다. 이 실패 응답을 만드는 전역 예외 처리기는 `global/exception/GlobalExceptionHandler.java`에 있지만, 본문은 확인하지 않았다.
- 응답 `code`가 0인데 `response.status`가 `"success"`가 아니면 예외가 나지 않는다. 결제는 `PENDING`, `isSuccess = false`로 저장된다(`PaymentCommandService.java:203-208`, 기본값은 `Payment.java:39`, `:44`). 그 뒤 판매는 SOLD, 알림은 발송, `OrderBid`는 MATCHED가 되고 요청은 **성공 응답**을 준다. 단, PortOne이 이런 응답 형식을 실제로 보내는지는 외부 계약이라 저장소만으로는 알 수 없다.
- 참고: 코드는 `"success"` 문자열만 `PAID`로 인정한다(`:203`). PortOne 응답의 상태 문자열이 다르면 정상 결제도 `PENDING`으로 남는다. 이것도 외부 계약에 따라 달라진다.
- 카드 결제가 PortOne에서 이미 성공한 뒤 같은 트랜잭션의 뒤쪽 단계(`createInstantOrderBid` 저장 등)가 실패하면, DB는 롤백되지만 PortOne 결제는 취소되지 않는다. 환불 처리 `handleRefundIfNecessary`(`PaymentCommandService.java:341`)는 정의만 있고 호출되는 곳이 없다.

**계좌이체(ACCOUNT)** (`PaymentCommandService.java:236-279`)
- PortOne을 호출하지 않는다. 은행명 유효성만 검사하고(`:243-248`), `Payment`를 `PENDING`으로 저장한다(`:260`, `:262`).
- `processPayment`는 결제 상태와 관계없이 `notifyUsersAndUpdateSaleStatus`를 호출한다(`:83`). 따라서 아직 입금되지 않은 계좌이체인데도 판매는 SOLD가 되고, 구매자는 "결제가 완료되었습니다" 알림을 받는다. 이 동작은 주석의 의도와 다르다.

**일반 결제(GENERAL)** (`PaymentCommandService.java:290-333`)
- 클라이언트가 보낸 `impUid`가 비어 있는지만 확인한다(`:297-300`). PortOne에 실제 결제 여부를 조회하지 않는다. 저장과 동시에 `PAID`, `isSuccess = true`로 기록한다(`:313-314`).
- 따라서 클라이언트가 보낸 `impUid`만으로 결제 완료가 된다. 이 경로에서 검증은 없다.

**즉시 구매가 끝까지 성공하는가**
- 카드 결제가 PortOne에서 실패 코드(`code != 0`)로 응답하면 **실패하고 전부 롤백된다.**
- 카드 결제가 `code == 0`이지만 상태가 `"success"`가 아니면 **요청은 성공하지만 결제는 PENDING이다.** 판매는 SOLD, 주문은 `PENDING_PAYMENT`로 남는다.
- 계좌이체는 **요청이 성공하고** 판매는 SOLD가 되지만, 결제는 PENDING이고 주문은 `PENDING_PAYMENT`다.
- 일반 결제는 `impUid`만 있으면 **요청이 성공하고** 결제는 PAID다. 주문은 여전히 `PENDING_PAYMENT`다.
- 결제 성공 여부와 무관하게 주문은 완료 상태가 되지 않는다(5번 참고).

**카드 결제 실패 응답 요약**: PortOne이 실패 코드를 주면 `PaymentProcessingException`이 던져지고, 트랜잭션은 롤백되며, HTTP 응답은 전역 예외 처리기가 만든다. 주문, 판매, 입찰 상태는 모두 바뀌지 않는다. 다만 `code == 0` + 비성공 상태라는 별도의 경로가 있어, "실패 응답이면 아무것도 안 남는다"는 가정은 맞지 않는다.

## 4. 알림 수신자, 시점, 방식

`PaymentCommandService.notifyUsersAndUpdateSaleStatus`(`PaymentCommandService.java:383-426`)에서 `sendNotifications`(`:434-462`)를 호출한다. 결제 수단과 무관하게 `processPayment`가 성공해 반환하기 직전에 한 번 실행된다.

- **구매자**(`order.getUser()`): `NotificationCategory.SHOPPING`, `NotificationType.BID`, 메시지 `"결제가 완료되었습니다. 주문 ID: {orderId}"`(`PaymentCommandService.java:436-445`).
- **판매자**(`sale.getSeller()`): 같은 카테고리와 타입, 메시지 `"구매자가 결제를 완료하였습니다. 판매 ID: {saleId}"`(`:447-456`).
- 방식: `NotificationCommandService.createNotification`(`D/notification/service/command/NotificationCommandService.java:44-62`)이 `Notification`을 DB에 저장하고(`:53`), 이어서 `sendRealTimeNotification`(`:57`)을 호출한다. 이 함수는 Redis 키 `WebSocket:User:{email}`이 있을 때만 STOMP `/queue/notifications`로 WebSocket 발송한다(`:303-322`). 키가 없으면 DB 저장만 한다.
- 시점: 결제 처리 중 **트랜잭션이 커밋되기 전에** 실행된다. WebSocket 발송은 커밋 전에 나가므로, 이후 트랜잭션이 롤백되면 사용자는 존재하지 않는 주문에 대한 실시간 알림을 받을 수 있다.
- 실패 처리: `sendNotifications`와 `notifyUsersAndUpdateSaleStatus`는 예외를 모두 잡아 로그만 남긴다(`:421-425`, `:457-461`). 알림 실패가 결제를 막지 않는다.
- Kafka나 이메일은 사용하지 않는다.

## 5. 처리가 끝났을 때의 최종 상태

성공 경로의 최종 상태는 다음과 같다.

- `Order.status` = **`PENDING_PAYMENT`**. 이 경로에서 바뀌지 않는다(`OrderCommandService.java:244`에서 설정된 값 그대로). 결제 여부와 무관하다.
- `Order.payment`는 null이다. `processPayment`의 반환값을 `assignPayment`에 넘기지 않기 때문이다(`OrderCommandService.java:305`). `Payment` 행은 저장되지만 주문과 연결되지 않은 상태다. 다만 `Payment.assignOrder`는 `paymentRequest`의 `orderId`를 통해 이루어진 결제 생성 과정에서 호출된다(`PaymentCommandService.java:200`, `:258`, `:311`).
- `OrderShipment`는 생성되어 주문에 연결된다(`OrderCommandService.java:271`).
- `OrderBid.status` = `MATCHED`, `isInstantPurchase = true`, `sale` 연결(`OrderBidCommandService.java:196-205`).
- `SaleBid.status` = `MATCHED`, `order` 연결(`OrderCommandService.java:279-280`).
- `Sale.status` = `SOLD`(`PaymentCommandService.java:404` 또는 `:419`). 결제가 PENDING이어도 SOLD가 된다(3번 참고).

**창고 보관(`warehouseStorage`)을 선택한 경우**

구매자가 보낸 `warehouseStorage` 값은 이 흐름에서 무시된다.

- `OrderCommandService.createInstantOrder`는 `isWarehouseStorage` 파라미터를 받지만(`OrderCommandService.java:221`) 본문 어디에서도 쓰지 않는다. 대신 판매 쪽 플래그 `sale.isWarehouseStorage()`를 본다(`:292`). 즉 주문 시점의 구매자 선택이 아니라 판매자가 등록할 때 정한 값으로 동작한다.
- 판매 플래그가 true이면 `updateWarehouseStatus(sale, ASSOCIATED_WITH_ORDER)`가 호출된다(`OrderCommandService.java:292-293`). 이 메서드는 기존 `WarehouseStorage`를 `findBySale`로 찾아야 한다(`D/warehouseStorage/service/command/WarehouseStorageCommandService.java:117-140`). 그 레코드는 판매자가 창고로 보낼 때 `createSellerStorage`로 만들어진다(`D/shipment/service/command/SellerShipmentCommandService.java:79`). 판매자 발송 전이라 레코드가 없으면 `WarehouseStorageNotFoundException`이 발생하고 주문 전체가 롤백된다.
- 성공하면 `WarehouseStorage.status`는 `IN_STORAGE`에서 `ASSOCIATED_WITH_ORDER`로 바뀐다. `Order`에는 `WarehouseStorage`가 연결되지 않는다. 주문 쪽에서는 `createOrderStorage`가 호출되지 않고(`assignWarehouseStorage`도 호출되지 않는다), 주문 상태는 `COMPLETED`가 되지 않는다.
- 일반 주문 경로(`OrderCommandService.processPaymentAndShipment`, `:161-177`)에서 창고 보관은 `PAYMENT_COMPLETED → PREPARING → IN_WAREHOUSE → COMPLETED`로 진행되지만, 즉시 구매 경로에는 이 흐름이 없다.

**요약**: 즉시 구매가 성공해도 주문은 `PENDING_PAYMENT`에 머문다. 주문 상태를 `PAYMENT_COMPLETED`나 `PREPARING`으로 올리는 코드가 이 경로에 없다. 주석이나 메서드 이름이 말하는 "즉시 구매 완료"와 실제 동작이 다르다.

## 주석/이름과 실제 동작이 다른 곳 (정리)

1. 응답의 `orderId`는 주문 ID가 아니라 `OrderBid` ID다(`OrderBidCommandController.java:101-109`).
2. 구매자의 `warehouseStorage` 선택은 무시되고 판매 플래그가 쓰인다(`OrderCommandService.java:221` vs `:292`).
3. 주문 상태는 결제 성공과 무관하게 `PENDING_PAYMENT`로 남는다(`OrderCommandService.java:244`). 즉시 구매 완료라는 이름과 맞지 않는다.
4. 카드 결제가 `code == 0`인데 비성공 상태면 예외 없이 성공 응답과 SOLD 처리가 된다(`PaymentCommandService.java:203-208`, `:419`).
5. 계좌이체가 PENDING이어도 판매는 SOLD가 되고 "결제가 완료되었습니다" 알림이 간다(`PaymentCommandService.java:83`, `:436-445`).
6. 일반 결제는 클라이언트가 보낸 `impUid`만으로 PAID가 된다(`PaymentCommandService.java:297-314`).
7. `OrderBid` 생성은 결제 이후에 있다(`OrderBidCommandService.java:142`). 그 전에 WebSocket 알림이 나가므로(`NotificationCommandService.java:57`, `:303-322`), 이후 롤백되어도 알림은 남는다.
8. 결제 성공 후 뒤쪽 단계가 실패하면 PortOne 결제는 취소되지 않는다. 환불 헬퍼 `handleRefundIfNecessary`는 호출되지 않는다(`PaymentCommandService.java:341`).
