# 질문: 즉시 구매는 어떻게 처리되나

> 모든 경로는 저장소 루트 기준이다. 코드는 읽기만 했고 수정·실행하지 않았다.
> 기본 경로: `src/main/java/com/fream/back/domain/` (아래에서는 `domain/`으로 줄여 쓴다)

---

## 1. 진입 API, 처리 단계, 동기/비동기, 응답 ID

- **진입점**: `POST /order-bids/instant`
  - 클래스 매핑 `domain/order/controller/command/OrderBidCommandController.java:22`, 메서드 `:89-90`
  - 요청 본문 `InstantOrderRequestDto`: `saleBidId`, `addressId`, `warehouseStorage`, `paymentRequest` (`domain/order/dto/InstantOrderRequestDto.java:20-29`)
- **처리 단계**
  1. 컨트롤러가 인증 이메일을 꺼낸다 (`OrderBidCommandController.java:92`).
  2. 결제 요청에 `userEmail`을 넣고 `orderId`를 `null`로 초기화한다 (`:98`, `:119-123`).
  3. `OrderBidCommandService.createInstantOrderBid(...)`를 호출한다 (`:101-107`). 이 메서드는 `@Transactional`이다 (`domain/order/service/command/OrderBidCommandService.java:118`).
  4. 입력값 검증 (`OrderBidCommandService.java:123`, `:154-167`)
  5. 구매자 조회 (`:126`), 판매 입찰 조회 및 검증 (`:129`, `:172-184`)
  6. `OrderCommandService.createInstantOrder(...)` 호출 (`OrderBidCommandService.java:133-139`). 여기서 주문 생성, 배송지 조회(`domain/order/service/command/OrderCommandService.java:238`), 판매 입찰 매칭, 창고 상태 변경, 결제 처리가 모두 일어난다 (`:219-319`).
  7. 돌아와서 `OrderBid`를 생성·저장한다 (`OrderBidCommandService.java:142`, `:189-206`).
- **동기 처리다.** 이 경로에는 Kafka가 없다. `OrderEventProducer`는 일반 주문 경로인 `OrderCommandController.java:54`에서만 쓰인다.
- 주의: 카드 결제의 PortOne HTTP 호출(`domain/payment/service/command/PaymentCommandService.java:179`)이 DB 트랜잭션 안에서 실행된다. 외부 호출이 끝난 뒤에 나머지 DB 작업이 실패하면 DB만 롤백되고 실제 승인된 결제는 취소되지 않는다. 환불 메서드 `handleRefundIfNecessary`(`PaymentCommandService.java:341`)는 정의만 있고 호출처가 없다.
- **응답 ID는 `OrderBid`의 ID다.** 컨트롤러 `OrderBidCommandController.java:101-107`에서 `createInstantOrderBid(...).getId()`를 쓰는데, 반환 객체는 `OrderBid`(`OrderBidCommandService.java:142`)다. 주문(`Order`) ID는 응답에 없다. 컨트롤러 주석(`:83`)은 "생성된 주문 ID"라고 적혀 있어 실제 동작과 다르다.

## 3. 결제 수단별 결과와 실패 처리

**공통 검증** (`PaymentCommandService.java:117-146`)
- `order.id == requestDto.orderId`, `user.email == requestDto.userEmail`, `paidAmount > 0`만 확인한다.
- **결제 금액과 주문 금액(`bidPrice`)을 비교하지 않는다.**
- 결제 수단은 `paymentType` 속성으로 나뉜다 (`domain/payment/dto/PaymentRequestDto.java:20-25`).

**(가) 카드 (`CARD`)** — `PaymentCommandService.java:157-225`
- PortOne에 요청하는 금액은 클라이언트가 보낸 `paidAmount`다 (`:179` → `domain/payment/portone/PortOneApiClient.java:250`). 주문 금액과 다른 금액으로 승인될 수 있다.
- 응답 `status`가 문자열 `"success"`일 때만 `PAID`가 되고 `isSuccess = true`가 된다 (`:203-206`). 그 밖의 경우 엔티티 기본값 `PENDING`이 남는다 (`domain/payment/entity/Payment.java:44`). 그래도 예외 없이 흐름은 성공으로 이어진다.
- **PortOne이 실패로 응답하면** (`PortOneApiClient.java:270-275`에서 `code != 0`이거나 HTTP 상태가 200이 아니면 `PaymentProcessingException`을 던진다):
  1. 예외가 `createCardPayment`(`PaymentCommandService.java:180-181`, `:218-219`)와 `processPayment`(`:88-94`)를 거쳐 전파된다.
  2. `createInstantOrder`에서 `OrderPaymentProcessingFailedException`으로 감싸져 던져진다 (`OrderCommandService.java:304-309`). 이 예외는 `OrderException`이므로 그대로 다시 던져진다 (`:312-314`).
  3. `OrderBidCommandService`에서 `handleOrderBidCreationException`을 거쳐 다시 던져진다 (`OrderBidCommandService.java:145-147`, `:212-215`).
  4. `GlobalException`이 `RuntimeException`을 상속하므로 (`global/exception/GlobalException.java:10`) 트랜잭션이 **롤백된다**.
  5. 응답은 `GlobalExceptionHandler.java:49-60`에서 에러 코드의 HTTP 상태로 나간다.
  - 결과: 주문, 주문 항목, 배송 정보, 판매 입찰 매칭, 판매 상태 변경이 모두 남지 않는다. 알림도 보내지 않는다(알림 단계에 도달하지 않음).

**(나) 계좌이체 (`ACCOUNT`)** — `PaymentCommandService.java:236-279`
- 은행명 검증만 한다 (`:243-248`, `:470-487`). 실패하면 예외로 롤백된다.
- 성공하면 `AccountPayment`가 `PENDING`으로 저장된다 (`:260`).
- 예외가 없으므로 트랜잭션이 **커밋**되고, 알림과 `Sale.SOLD`가 반영되며, 응답은 "즉시 구매가 성공적으로 처리되었습니다"다. 결제가 완료되지 않은 상태다.
- `PENDING → PAID`로 바꾸는 `updatePaymentStatus`(`PaymentCommandService.java:498`)는 호출하는 곳이 코드에 없다. 계좌 결제는 끝까지 `PENDING`으로 남는다.

**(다) 일반 결제 (`GENERAL`)** — `PaymentCommandService.java:290-333`
- `impUid`를 클라이언트가 보낸 그대로 믿는다. PortOne에 조회하거나 검증하지 않는다 (`:297-300`, `:302-309`).
- 바로 `PAID`로 저장된다 (`:313-314`). 금액도 클라이언트 값(`paidAmount`)이고 주문 금액과 비교하지 않는다.

**즉시 구매가 끝까지 성공하는 경우**: 카드 결제에서 PortOne 응답의 `code`가 0이고 `status`가 `"success"`일 때만 `Payment`가 `PAID`가 된다. 계좌는 예외 없이 끝나지만 결제는 `PENDING`이다. 일반 결제는 검증 없이 `PAID`가 된다. 세 경우 모두 API 응답은 같은 성공 메시지다.

## 4. 알림 수신자, 시점, 방식

- **수신자와 내용** (`PaymentCommandService.java:434-456`)
  - 구매자: 카테고리 `SHOPPING`, 타입 `BID`, "결제가 완료되었습니다. 주문 ID: …" (`:438-443`)
  - 판매자: 카테고리 `SHOPPING`, 타입 `BID`, "구매자가 결제를 완료하였습니다. 판매 ID: …" (`:449-454`)
- **시점**: `processPayment`가 끝난 직후 같은 트랜잭션 안에서 동기로 보낸다 (`PaymentCommandService.java:83`, `:403`, `:416`). 결제 상태(`PENDING`, `FAILED` 등)를 확인하지 않고 항상 보낸다 (`:383-426`). 따라서 계좌 결제(`PENDING`)와 `PENDING`으로 남은 카드 결제에도 "결제가 완료되었습니다"가 나간다.
- **방식**
  - `NotificationCommandService`는 클래스 단위 `@Transactional`이다 (`domain/notification/service/command/NotificationCommandService.java:27`). 알림을 DB에 저장하고 (`:53`), 실시간 전송을 시도한다 (`:57`).
  - 실시간 전송(WebSocket `/queue/notifications`)은 Redis에 `WebSocket:User:{email}` 키가 있을 때만 보낸다 (`:303-321`). 없으면 저장만 된다.
  - 실시간 전송은 커밋 전에 일어나며, DB 트랜잭션이 나중에 롤백되어도 되돌릴 수 없다. 예를 들어 `OrderBid` 저장(`OrderBidCommandService.java:206`)이 실패하면 알림은 이미 나간 상태가 된다.
  - 알림 실패는 로그만 남기고 삼킨다 (`PaymentCommandService.java:421-425`, `:457-461`).
- 이 경로에서 Kafka `notification-topic`은 쓰이지 않는다 (`notificationKafkaTemplate`은 `OrderEventConsumer`에만 있다).

## 5. 처리 완료 후 주문의 최종 상태, 창고 보관 선택 시 변화

- **주문 상태**: 성공해도 `Order.status`는 `PENDING_PAYMENT`로 남는다. 생성 시 설정되고 (`OrderCommandService.java:244`), 이후 즉시 구매 경로에서 갱신되지 않는다. 주문 상태가 `PAYMENT_COMPLETED` 이상으로 올라가지 않는다.
- **`OrderBid` 상태**: `MATCHED`, `isInstantPurchase = true`.
- **창고 보관 선택 (`warehouseStorage = true`)**
  - 요청 값은 컨트롤러에서 서비스까지 넘어간다 (`OrderBidCommandController.java:105` → `OrderBidCommandService.java:137` → `OrderCommandService.java:221`).
  - **그런데 `OrderCommandService.createInstantOrder`는 `isWarehouseStorage` 인자를 쓰지 않는다.** 실제 판단은 판매 쪽 플래그 `sale.isWarehouseStorage()`로 한다 (`OrderCommandService.java:292`). 이 값은 판매자가 판매를 만들 때 정한다 (`domain/sale/service/command/SaleCommandService.java:107`).
  - 판매 쪽 플래그가 참이면: `WarehouseStorage` 상태를 `ASSOCIATED_WITH_ORDER`로 바꾼다 (`OrderCommandService.java:293`). 창고 정보가 없으면 `WarehouseStorageNotFoundException`이 나고 (`domain/warehouseStorage/service/command/WarehouseStorageCommandService.java:30-33`에서 조회 실패), 상태가 `ON_AUCTION`이면 전이가 허용되지 않아 실패한다 (`WarehouseStorageCommandService.java:249-252`). 두 경우 모두 구매 전체가 롤백된다.
  - 구매자가 창고 보관을 골랐는데 판매 쪽 플래그가 거짓이면: 창고 관련 처리가 전혀 없고, 일반 배송 정보가 만들어진다 (`OrderCommandService.java:264-271`).
  - 어느 경우든 `Order.warehouseStorage`는 연결되지 않고 (일반 경로에서만 `assignWarehouseStorage`가 호출된다, `:171`), `Order.status`도 바뀌지 않는다. 일반 경로에서 창고 보관이면 `COMPLETED`까지 가지만(`:163-172`), 즉시 구매에는 이 흐름이 없다.

## 주석/메서드 이름과 실제 동작의 차이

1. **응답 ID**: 컨트롤러 주석 `:83`은 "생성된 주문 ID"라고 하지만, 실제로 반환하는 것은 `OrderBid` ID다 (`OrderBidCommandController.java:107`).
2. **판매 입찰 없음 예외**: 주석 `OrderBidCommandService.java:115`와 컨트롤러 `:86`은 `SaleBidNotFoundException`을 말하지만, `SaleBidQueryService.findById`는 `IllegalArgumentException`을 던진다 (`domain/sale/service/query/SaleBidQueryService.java:21-24`). 이 예외는 `OrderBidCreationFailedException`으로 감싸진다 (`OrderBidCommandService.java:212-217`). 그래서 `:173-176`의 null 검사는 실행되지 않는다.
3. **창고 보관 요청 값**: `InstantOrderRequestDto.warehouseStorage`와 `createInstantOrder`의 `isWarehouseStorage` 인자는 실제 동작에 쓰이지 않는다 (5번 참고).
4. **성공 메시지**: "즉시 구매가 성공적으로 처리되었습니다"(`OrderBidCommandController.java:109`)는 계좌 `PENDING` 결제나 `PENDING` 카드 결제에서도 나간다.
5. **카드 성공 판정**: 코드는 PortOne 응답 `code == 0`(`PortOneApiClient.java:270`)으로 요청 성공을 보고, 결제 상태 `PAID`는 `status == "success"`(`PaymentCommandService.java:203`)로 정한다. 두 조건이 어긋나면 결제는 `PENDING`인데 주문은 성공으로 끝난다. 실제 PortOne이 어떤 값을 보내는지는 이 저장소만으로는 확인할 수 없다.

## 기타 확인된 위험 (질문 범위 밖이지만 답에 영향)

- **금액 검증 없음**: 카드는 클라이언트 금액으로 승인하고 (`PaymentCommandService.java:179`), 일반 결제는 클라이언트 금액을 그대로 저장한다 (`:308`). 주문 금액(`totalAmount`, `OrderCommandService.java:243`)과 비교하지 않는다.
- **`@Min(100)` 미적용**: `PaymentRequestDto.paidAmount`의 `@Min(100)`(`PaymentRequestDto.java:50-51`)은 `InstantOrderRequestDto.paymentRequest`에 `@Valid`가 없어 검사되지 않는다 (`InstantOrderRequestDto.java:28-29`).
- **중복 구매 가드 없음**: 상태 검사가 없고 (`OrderBidCommandService.java:172-184`), `OrderBid.sale`은 `@OneToOne`이다 (`domain/order/entity/OrderBid.java:45-47`). 스키마가 생성되는 환경(`application-prod.yml`, `application-test.yml`의 `ddl-auto: create`)에서는 unique 제약이 생길 것으로 보인다. 그러면 두 번째 요청은 `OrderBid` 저장 단계에서 실패하지만, 그 전에 PortOne 결제는 이미 실행된 뒤다. 이 부분은 실행으로 확인하지 않았다.
