# 구매자 배송: 운송장 등록부터 배송 완료까지

경로 약칭: `shipment/` = `src/main/java/com/fream/back/domain/shipment/`, `order/`·`sale/`·`payment/`·`notification/` 도 같은 방식으로 `src/main/java/com/fream/back/domain/` 아래.

## 결론 요약

- 운송장 등록(`PATCH /shipments/order/{id}/status`)은 (a) 일반 구매 입찰 주문, (b) 즉시 구매 주문 모두 **실패한다.** 주문 상태가 `IN_TRANSIT`으로 전이할 수 없기 때문이며, 응답은 404 `S001`이고 아무것도 저장되지 않는다.
- 그래서 정상 흐름으로는 배치가 조회할 `IN_TRANSIT`/`OUT_FOR_DELIVERY` 배송이 만들어지지 않는다. 배치 대상이 되는 상태는 수동 조회 API(`check-status`)로만 만들어질 수 있다.
- 배송 완료 처리(배치 `ShipmentItemProcessor`)에서 (a)는 `Order` `PREPARING → COMPLETED` 전이 불가로 실패한다. (b)는 성공하며 구매자 알림 2건, 판매자 알림 0건, 입찰 상태는 `MATCHED`로 남는다.

## 1. 운송장 등록 요청

**진입점**
- `shipment/controller/command/OrderShipmentCommandController.java:20` 클래스 매핑 `/shipments/order`
- `shipment/controller/command/OrderShipmentCommandController.java:33-46` `@PatchMapping("/{shipmentId}/status")` → `orderShipmentCommandService.updateTrackingInfo(...)`

**서비스 `updateTrackingInfo` (설계상 순서)** — `shipment/service/command/OrderShipmentCommandService.java:238-303`
1. 택배사·운송장 빈값 검사 (`:243-246`)
2. `OrderShipment`: 택배사·운송장 설정 + `status = IN_TRANSIT` (`shipment/entity/OrderShipment.java:41-45`). 현재 상태를 검사하지 않고 직접 쓴다. `ShipmentStatus` 전이표에도 `PENDING → IN_TRANSIT`은 없다 (`shipment/entity/ShipmentStatus.java:4-9`).
3. `Order`: `order.updateStatus(OrderStatus.IN_TRANSIT)` (`:260`)
4. 구매자 알림 "상품이 출발하였습니다" (`:264-271`)
5. `updateSaleStatusToSold` (`:276`), 창고 상태 갱신 (`:279-286`), `OrderBid`/`SaleBid` → `COMPLETED` (`:289`, 본체는 `:413-440`)
6. 예외는 `ShipmentException(SHIPMENT_NOT_FOUND)`로 감싸 다시 던진다 (`:293-301`)

**설계상 엔티티 상태 순서**: `OrderShipment` PENDING→IN_TRANSIT → `Order`→IN_TRANSIT → `Sale`→SOLD 시도 → `OrderBid`/`SaleBid`→COMPLETED. 알림은 구매자 "출발" 1건.

**실제 동작 (a), (b) 공통 실패 지점 `:260`**
- 주문 상태: (a)는 `PREPARING`, (b)는 `PENDING_PAYMENT`.
  - (a): `order/service/kafka/OrderEventConsumer.java:216-217`, `order/service/command/OrderCommandService.java:175-176`에서 `PAYMENT_COMPLETED → PREPARING`.
  - (b): `OrderCommandService.java:241-245`에서 `PENDING_PAYMENT`로 생성. 이후 `processPayment`(`:304-305`)는 결제만 처리하고 주문 상태를 바꾸지 않는다 (`payment/` 어디에도 `order.updateStatus` 없음).
- `Order.updateStatus` (`order/entity/Order.java:113-121`)는 `OrderStatus.canTransitionTo`를 검사한다. `IN_TRANSIT`으로 들어가는 간선은 `SHIPMENT_STARTED`에서만 있다 (`order/entity/OrderStatus.java:24-29`, `PREPARING`은 `IN_WAREHOUSE`/`SHIPMENT_STARTED`만 허용, `PENDING_PAYMENT`는 `PAYMENT_COMPLETED`/`COMPLETED`/`IN_WAREHOUSE`만 허용). `SHIPMENT_STARTED`는 코드 어디서도 설정되지 않는다 (grep 확인).
- 결과: `InvalidOrderStatusException` → `:293-301`에서 `ShipmentException`으로 감싸짐 → `@Transactional` 롤백. **운송장·`IN_TRANSIT` 저장 안 됨, 알림 안 감** (`:264`은 `:260` 이후라 도달하지 않음).
- 응답: 컨트롤러에 try/catch가 없어 `global/exception/GlobalExceptionHandler.java:459-473`의 `handleShipmentException`이 처리 → **HTTP 404**, 본문 `ErrorResponse`의 code `S001`, message는 enum 기본 문구 "배송 정보를 찾을 수 없습니다." (`shipment/exception/ShipmentErrorCode.java:12`). 실제 원인 메시지는 로그에만 남는다.

**참고 (설령 `:260`을 통과하더라도)**: `:276` → `:116`의 `saleBidQueryService.findByOrderId`는 SaleBid가 없으면 `null`이 아니라 `IllegalArgumentException`을 던진다 (`sale/service/query/SaleBidQueryService.java:26-29`). (a)는 SaleBid가 없으므로 여기서도 막힌다. `:117`의 `if (saleBid != null)` 분기는 실제로 도달하지 않는다.

## 2. 배송 완료 감지

**누가·언제·어떻게**: 시스템 배치가 감지한다. 운영자가 바로 확인하려면 수동 API `POST /shipments/order/{id}/check-status`를 쓸 수 있다.

**주기**: `global/config/ShipmentBatchScheduler.java:34-44`, `@Scheduled(cron = "0 0 */6 * * *")` → 매일 00·06·12·18시 (서버 기본 타임존). 매 실행마다 `timestamp` 파라미터로 새 JobInstance를 만든다. 추가로 `application-prod.yml`에는 `spring.batch.job.enabled` 설정이 없어 Spring Boot 기본값(true)이 적용되므로 **기동 시에도 한 번 실행될 가능성이 높다** (런타임 확인 필요, 이 저장소에서는 확인하지 않음).

**대상 조회**: `shipment/config/UpdateShipmentStatusesJobConfig.java:87-97` `JpaPagingItemReader`, `pageSize 50`, `status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND trackingNumber IS NOT NULL` (`:95`). `ORDER BY`가 없다.

**실제로 실행되는 처리 코드**
- Step은 `new ShipmentItemProcessor(...)`를 쓴다 (`UpdateShipmentStatusesJobConfig.java:69-72`) → `shipment/config/ShipmentItemProcessor.java:57-157`.
- 이 processor는 Playwright 브라우저로 `https://trace.cjlogistics.com/next/tracking.html?wblNo=...`를 열고 `tbody#statusDetail tr`을 30초까지 기다린 뒤 (`:28-30`, `:81-87`), 마지막 행의 5번째 `td`를 읽는다 (`:181`).
- 비슷하지만 **실행되지 않는** 코드:
  - `UpdateShipmentStatusesJobConfig.java:104-` `shipmentItemProcessor()` 빈 (Jsoup/`CjTrackingPlaywright` 기반, step에 연결되지 않음). 그 안의 주석 "Order 상태 완료 처리"도 실행되지 않는다.
  - `UpdateShipmentStatusesJobConfig.java:186` `parseCjLogisticsStatus` (호출처 없음).
  - `shipment/service/command/OrderShipmentCommandService.java:308-391` `updateShipmentStatuses()` (호출처 없음, grep 확인).

**택배사 상태 → 내부 상태** (`ShipmentItemProcessor.java:220-226`)
- `"배송완료"` → `DELIVERED`
- `"배송출발"` → `OUT_FOR_DELIVERY`
- 그 외 전부 → `IN_TRANSIT`

처리 분기 (`ShipmentItemProcessor.java:101-125`): 현재 상태와 같으면 그대로 반환(`:101-105`). `DELIVERED`면 완료 처리(`:108-117`). `OUT_FOR_DELIVERY`면 상태만 변경(`:119-121`). 그 외는 `updateStatus(IN_TRANSIT)`(`:123-125`). `OUT_FOR_DELIVERY`에서 "그 외"로 바뀌면 전이 불가 → 예외 → skip.

**수동 경로 `check-status`**: `OrderShipmentCommandController.java:58-` → `OrderShipmentCommandService.updateAndCheckShipmentStatus` (`:451-516`). 송장을 먼저 `IN_TRANSIT`으로 쓰고 (`:473`) CJ를 조회한다 (`:477`, `CjTrackingPlaywright`). 그 다음 `DELIVERED`면 `completeOrder` (`:483-489`), 그 외는 `updateStatus`. 그런데 기본 분기 `:497`은 `IN_TRANSIT → IN_TRANSIT` 전이라 `canTransitionTo`가 거짓이고 `IllegalStateException`이 나온다 → `EXTERNAL_TRACKING_SERVICE_ERROR`(503)로 롤백. 즉 "배송 중" 텍스트에서는 이 경로가 실패한다.

## 3. 배송 완료 판정 이후 (배치 경로)

`ShipmentItemProcessor.java:108-117`의 DELIVERED 분기 순서:

1. `OrderShipment`: `IN_TRANSIT` 또는 `OUT_FOR_DELIVERY` → `DELIVERED` (전이 허용, `ShipmentStatus.java:16-34`). DB 반영은 청크 커밋 때 `JpaItemWriter`가 한다.
2. `orderService.completeOrder(orderId)` — `OrderShipmentCommandService.java:190-229`
   - `OrderBid` 조회 (`:196-197`). 없으면 `IllegalArgumentException` → `:221-228`에서 `ShipmentException(ORDER_NOT_FOUND_FOR_SHIPMENT)`.
   - `Order` → `COMPLETED` (`:204`). 전이 조건은 4번 참고.
   - `updateSaleStatusToSold` (`:208`): `Sale`은 이미 `SOLD`다. 결제 시점에 `payment/service/command/PaymentCommandService.java:83`의 `notifyUsersAndUpdateSaleStatus`(`:383-426`, `sale.updateStatus(SOLD)`는 `:404`·`:419`)에서 설정되기 때문이다. `SaleStatus.canTransitionTo(SOLD)`가 거짓이라 아무것도 하지 않는다 (`OrderShipmentCommandService.java:119`, `:156`). 판매자 알림도 없다.
   - 구매자 알림 "[completeOrder] 주문이 완료 처리되었습니다" (`:211-217`).
3. `notificationService.notifyShipmentCompleted(order)` (`ShipmentItemProcessor.java:117`, 본체 `notification/service/command/NotificationCommandService.java:219-234`) → 구매자 알림 "[배송 완료] ..." 1건.

**알림**: 구매자 2건(`BID` 카테고리, `SHOPPING`), 판매자 0건. 각 `createNotification`(`NotificationCommandService.java:44-67`)은 DB 저장 후 `/queue/notifications`로 실시간 푸시한다.

**입찰 상태**: `OrderBid`와 `SaleBid`는 `MATCHED`로 남는다. `completeOrder`는 입찰을 건드리지 않는다. `COMPLETED`로 바꾸는 `updateOrderAndSaleBidStatusToCompleted`(`:413-440`)는 컨트롤러 경로 `updateTrackingInfo`(`:289`)에서만 호출된다. 그 경로는 1번에서 실패한다.

## 4. 주문 종류별 차이

**(a) 실배송 일반 구매 입찰 주문** (`Order` `PREPARING`, `OrderBid`와 `Sale`이 있음, `SaleBid`는 없음)
- 3번이 끝까지 가지 못한다. 2번 `completeOrder`의 `order.updateStatus(COMPLETED)`에서 막힌다. `PREPARING`의 허용 전이는 `IN_WAREHOUSE`/`SHIPMENT_STARTED`뿐이다 (`order/entity/OrderStatus.java:26`). `InvalidOrderStatusException` → `completeOrder`의 catch (`:221-228`) → `ShipmentException(S102)` → processor가 재던짐 → skip.
- 저장: 청크 롤백 여부는 5번 참고. 구매자 알림 0건, 판매자 알림 0건, 입찰 `MATCHED`.
- 전이를 통과하더라도 `:208` → `:116`에서 SaleBid 없음으로 `IllegalArgumentException`이 나와 실패한다.
- 결과: 주문은 `PREPARING`에 머문다. 배송 행은 실패 시 `IN_TRANSIT`(또는 롤백 여부에 따라 `DELIVERED`)로 남고, 다음 주기에 같은 실패를 반복한다.

**(b) 즉시 구매 주문** (`OrderBidCommandService.java:119-149`로 생성, `OrderBid`는 `MATCHED`에 `isInstantPurchase`로 생성 (`:189-207`), `SaleBid`↔`Order` 연결은 `OrderCommandService.java:279`, `Order`는 `PENDING_PAYMENT`)
- 3번이 끝까지 진행된다. `PENDING_PAYMENT → COMPLETED`는 허용된다 (`OrderStatus.java:24`). `OrderBid`·`SaleBid` 조회도 성공하고, `Sale`은 이미 `SOLD`라 판매 분기는 건너뛴다.
- 저장: `OrderShipment` `DELIVERED`, `Order` `COMPLETED`. `Sale`은 `SOLD`(결제 시점 값 그대로). `OrderBid`·`SaleBid`는 `MATCHED`.
- 알림: 구매자 2건, 판매자 0건. 판매자는 결제 시점에 "구매자가 결제를 완료하였습니다"를 이미 받았다 (`PaymentCommandService.java:434-461`).
- 도달 경로: 운송장 등록 PATCH는 실패하므로 (b)도 `check-status`로만 도달한다.
  - 배송출발 응답 → `OUT_FOR_DELIVERY` 저장 → 배치가 나중에 처리 → 위와 같이 완료.
  - 배송완료 응답 → `updateAndCheckShipmentStatus`에서 `completeOrder`를 바로 호출해 성공. 이 경우 구매자 알림은 `completeOrder`의 1건뿐이고 `notifyShipmentCompleted`는 호출되지 않는다 (`:483-489`).

## 5. 실패 처리 (주기 실행 중 한 건 실패 시)

설정: `shipment/config/UpdateShipmentStatusesJobConfig.java:62-82`. `chunk(50)`, `faultTolerant()`, `skip(Exception.class)`, `skipLimit(50)`, 리스너는 `shipmentSkipListener`(`:251-`, 로그만 남김).

- **실패한 건**: processor가 던진 예외(CJ 조회 실패·30초 타임아웃·파싱 실패, 전이 불가, `completeOrder` 실패 등)는 skip된다. writer로 가지 않으므로 그 건의 상태 변경은 저장되지 않는다. 그 건의 `IN_TRANSIT`/`OUT_FOR_DELIVERY` 상태는 그대로이므로 **다음 6시간 실행에서 다시 시도된다.** 영구적으로 실패하는 건 (a) 같은 경우는 매 주기 반복 실패한다.
- **같은 청크의 나머지 건**: 예외 뒤에 Spring Batch가 청크를 재처리해 나머지 건을 계속 처리한다고 보는 것이 일반적인 동작이다. 이 저장소만으로는 확정하지 못했다 (Spring Batch 5.2.3 내부 확인 필요).
- **실패 건의 메모리상 `DELIVERED` 변경**: `completeOrder`는 `@Transactional`로 청크 트랜잭션에 참여하고 `RuntimeException`을 던진다. 그래서 공유 트랜잭션이 rollback-only가 되어 청크 롤백이 일어날 것으로 보인다. 다만 재처리 세부는 검증하지 않았다. 롤백이 일어나지 않으면 `DELIVERED`가 DB에 남을 수 있다 (미확인).
- **skip 한도 초과**: 한 실행에서 skip이 50건을 넘으면 step이 실패하고 나머지 건은 다음 주기까지 처리되지 않는다.
- **페이징 문제 (코드 추론)**: `ORDER BY` 없는 offset 페이징인데, 처리된 건이 필터(`IN_TRANSIT`/`OUT_FOR_DELIVERY`) 밖으로 빠지면 다음 페이지의 offset이 밀려 일부 건이 이번 실행에서 건너뛰어질 수 있다. 다음 주기에 다시 잡힌다.
- **미확인 사항**: 쿼리가 `@Enumerated(STRING)` enum 필드를 문자열 리터럴과 비교하는데, 사용 중인 Hibernate 버전에서 이것이 허용되는지는 확인하지 않았다.

## 주석·이름과 실제 동작이 다른 곳

- `OrderShipmentCommandService.java:115-117`: `if (saleBid != null)`로 없음을 가정하지만, `SaleBidQueryService.findByOrderId`는 `null`이 아니라 예외를 던진다 (`sale/service/query/SaleBidQueryService.java:26-29`).
- `OrderShipmentCommandService.java:258-260`: "주문 상태도 업데이트"라고 하지만 `IN_TRANSIT` 전이는 허용되지 않아 항상 실패한다.
- `UpdateShipmentStatusesJobConfig.java:146-149`: 주석은 "Order 상태 완료 처리"를 말하지만 이 빈은 실행되지 않는다. 실제 완료 처리는 `ShipmentItemProcessor`가 한다.
- `OrderShipmentCommandService.java:190-206`: `completeOrder`는 "후속 작업"으로 판매 완료를 처리하는 것처럼 보이지만, 판매 SOLD 전환은 결제 시점에 이미 끝나 있다.
- `OrderShipmentCommandService.java:412-413`: `updateOrderAndSaleBidStatusToCompleted`는 `private`인데 `@Transactional`이 붙어 있다 (프록시가 적용되지 않음). 내부 예외는 삼킨다 (`:436-439`).
- `OrderShipmentCommandService.java:477-498` check-status 경로는 "현재 상태 확인"을 하지만, 기본 분기는 `IN_TRANSIT → IN_TRANSIT` 전이 예외로 실패한다.
