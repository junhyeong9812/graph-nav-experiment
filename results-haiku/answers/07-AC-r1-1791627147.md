# 즉시 구매는 어떻게 처리되나

요약: 즉시 구매는 `POST /order-bids/instant` 한 번의 **동기** 요청이다. 주문 생성, 판매 입찰 매칭, 결제 호출, 판매 상태 변경, 주문 입찰 생성이 하나의 DB 트랜잭션 안에서 실행된다. 응답의 ID는 **OrderBid(주문 입찰)의 ID**이며 Order의 ID가 아니다. 결제 수단과 무관하게 주문은 끝까지 `PENDING_PAYMENT` 상태로 남는다. 아래 답 중 코드와 주석/메서드명이 어긋나는 부분은 실제 동작 기준으로 적었다.

경로 약어: `O` = `src/main/java/com/fream/back/domain/order`, `P` = `src/main/java/com/fream/back/domain/payment`, `S` = `src/main/java/com/fream/back/domain/sale`, `N` = `src/main/java/com/fream/back/domain/notification`, `W` = `src/main/java/com/fream/back/domain/warehouseStorage`, `G` = `src/main/java/com/fream/back/global`

---

## 1. 진입 API, 처리 단계, 동기/비동기, 응답 ID

- 진입점: `POST /order-bids/instant` (`O/controller/command/OrderBidCommandController.java:22` 클래스 매핑, `:89-90` 메서드).
- 요청 DTO: `saleBidId`, `addressId`, `warehouseStorage`(boolean), `paymentRequest` 필드, 각각 `@NotNull` (`O/dto/InstantOrderRequestDto.java:18-29`).
- 처리 순서:
  1. 이메일을 인증 정보에서 꺼냄 (`OrderBidCommandController.java:92`).
  2. 결제 요청에 `userEmail`을 인증 사용자 이메일로 덮어쓰고 `orderId`는 null로 초기화 (`:98`, `:119-123`). 주문 ID는 나중에 서버가 채운다.
  3. `OrderBidCommandService.createInstantOrderBid` 호출 (`:101-107`). 아래 2번 단계가 여기서 실행된다.
- 처리 방식은 **동기**다. 이 경로에서는 Kafka를 쓰지 않는다. Kafka 소비자(`OrderEventConsumer`, `PaymentEventConsumer`)는 다른 주문 경로(`/orders`)용이다.
  - 주의: 외부 PortOne HTTP 호출이 DB 트랜잭션 안에서 이루어진다 (`P/service/command/PaymentCommandService.java:179`). 호출 동안 트랜잭션이 열려 있다.
- 응답: `ResponseDto.success(orderId, ...)` 이고, `orderId`는 `createInstantOrderBid(...).getId()`의 결과이므로 **OrderBid ID**다 (`OrderBidCommandController.java:101-109`). 메서드 주석(`:83`)의 "생성된 주문 ID"와 다르다. Order ID는 응답에 없다.
- 입력 검증: 서비스에서 null만 확인한다 (`O/service/command/OrderBidCommandService.java:154-167`). 결제 DTO 내부 필드는 `@Valid` 연쇄 검증이 없다 (`OrderBidCommandController.java:90`).
- 예외 흐름: 서비스의 `catch`가 `OrderException`은 그대로 다시 던지고, 그 외는 `OrderBidCreationFailedException`으로 감싼다 (`OrderBidCommandService.java:145-147`, `:212-218`). `GlobalException`은 `RuntimeException`이므로 `@Transactional`이 롤백한다 (`G/exception/GlobalException.java:10`).

## 2. 생성되는 엔티티와 상태 변화 순서

모두 한 트랜잭션 안에서 일어난다. `OrderBidCommandService.createInstantOrderBid`(`:118-119`) → `OrderCommandService.createInstantOrder`(`O/service/command/OrderCommandService.java:219-220`) → `PaymentCommandService`(클래스 단위 `@Transactional`, `P/service/command/PaymentCommandService.java:37`) 순서다. 전파 방식은 기본값(REQUIRED)이다.

| 순서 | 단계 (근거) | 직후 상태 |
|---|---|---|
| a | 판매 입찰 조회 + Sale 존재 확인. `SaleBid`를 찾고 `sale != null`만 본다 (`OrderBidCommandService.java:172-184`, `S/service/query/SaleBidQueryService.java:21-24`) | 변화 없음. **판매 입찰 상태(`PENDING` 등)를 검사하지 않는다** |
| b | 주소 조회 후 `Order` 생성, `totalAmount = saleBid.bidPrice` (`OrderCommandService.java:238-247`) | `Order.status = PENDING_PAYMENT`, `totalAmount = bidPrice` |
| c | `OrderItem` 생성, `quantity=1`, `price=bidPrice`, `order`에 추가 (`OrderCommandService.java:255-256`, `O/service/command/OrderItemCommandService.java:34-49`) | `OrderItem` 1개 |
| d | `OrderShipment` 생성, 수령인 정보는 주소에서 복사, `status=PENDING`, `order`에 연결 (`OrderCommandService.java:264-271`, `shipment/service/command/OrderShipmentCommandService.java:56-75`) | `OrderShipment.status = PENDING` |
| e | `saleBid.assignOrder(order)` → 판매 입찰 `status=MATCHED`, `updateStatus(MATCHED)`, `entityManager.flush()` (`OrderCommandService.java:279-283`, `S/entity/SaleBid.java:58-61`) | `SaleBid.status = MATCHED`, `SaleBid.order = order` |
| f | `Sale.isWarehouseStorage`가 참이면 창고 보관 상태를 `ASSOCIATED_WITH_ORDER`로 변경 (`OrderCommandService.java:290-301`) | 조건부, 3절 참고 |
| g | 결제 처리 (`OrderCommandService.java:305`) → 결제 행 생성, 3절 참고 | `Payment` 1개 (`order_id` 연결) |
| h | 알림 전송 + 판매 `SOLD` (`PaymentCommandService.java:83`, `:383-426`), 4절 참고 | `Sale.status = SOLD` (`S/entity/Sale.java:73-75`) |
| i | `Order` 상태 변경 **없음** (`OrderCommandService.java:312-317` 전까지 `updateStatus` 호출 없음) | `Order.status = PENDING_PAYMENT` 유지 |
| j | `OrderBid` 생성: `status=MATCHED`, `order`, `sale`, `bidPrice=saleBid.bidPrice`; `assignOrder`로 양방향 연결; `markAsInstantPurchase()`로 `isInstantPurchase=true`; `save` (`OrderBidCommandService.java:189-207`, `O/entity/OrderBid.java:49-52`, `:60-82`, `:97-99`) | `OrderBid.status = MATCHED`, `isInstantPurchase = true`, `Order.orderBid` 설정 |
| k | 커밋 (`OrderBidCommandService.java:118`) | 모든 변경 확정 |

참고: 단계 h에서 `order.getOrderBid()`가 `null`이라 `SaleBid`를 `findByOrderId`로 찾는 분기를 탄다 (`PaymentCommandService.java:388-391`, `S/service/query/SaleBidQueryService.java:26-28`). OrderBid는 아직 만들어지기 전이므로 이 분기가 항상 쓰인다. `e`에서 flush를 해 두었기 때문에 조회가 된다.

## 3. 결제 수단별 결과, 카드 실패 시 동작

결제 공통: `validatePaymentRequest`는 주문 ID 일치, 이메일 일치, `paidAmount > 0`만 확인한다 (`PaymentCommandService.java:117-146`). **결제 금액을 판매 입찰 가격(`bidPrice`)과 비교하지 않는다.** 그런데 카드 결제는 클라이언트가 보낸 `paidAmount`를 그대로 PortOne에 보낸다 (`:179`). 따라서 구매자가 임의 금액으로 결제 요청을 할 수 있다. 주문과 OrderBid 금액은 `bidPrice`를 쓰므로 둘이 어긋날 수 있다.

**카드 (`CARD`)** (`PaymentCommandService.java:157-225`)
- 성공 케이스: PortOne `processCardPayment` 호출 (`P/portone/PortOneApiClient.java:229`). 응답의 `code == 0`이면 성공으로 보고 `CardPayment`를 만든다 (`PortOneApiClient.java:270-285`).
- `CardPayment.status`는 `response.status`가 문자열 `"success"`일 때만 `PAID`가 되고, 기본값은 `PENDING`이다 (`PaymentCommandService.java:203-206`, `P/entity/Payment.java:39`, `:44`). 로컬 코드베이스에 PortOne 응답의 실제 상태 값을 확인할 근거는 없다. PortOne v1 문서에서 성공 상태는 `"paid"`로 알려져 있으므로, 실제 성공 결제도 `PENDING`/`isSuccess=false`로 저장될 가능성이 있다. 이는 저장소 밖의 사실이라 확인이 필요하다.
- 실패 케이스(대행사가 실패 응답): HTTP가 200이 아니거나 `code != 0`이면 `PaymentProcessingException`을 던진다 (`PortOneApiClient.java:270-275`). 호출자 체인:
  1. `createCardPayment`는 `PaymentException`을 그대로 다시 던진다 (`PaymentCommandService.java:218-219`).
  2. `processPayment`도 그대로 전파한다 (`:89-94`).
  3. `OrderCommandService.createInstantOrder`가 `OrderPaymentProcessingFailedException`(코드 `ORD005`, HTTP 500)으로 감싼다 (`OrderCommandService.java:304-309`, `O/exception/OrderErrorCode.java:44`).
  4. 서비스가 다시 던지고 (`OrderBidCommandService.java:145-147`), 트랜잭션이 롤백된다.
- 결과: 주문, 주문 항목, 배송, `SaleBid`의 `MATCHED` 변경, 창고 상태 변경, `Payment` 행이 모두 롤백된다. 알림은 이 시점에 아직 보내지 않았으므로 나가지 않는다. 구매자는 500 응답(`ORD005`)을 받는다. `OrderBid`도 생성되지 않는다.
- 주의: 아래 "PortOne은 성공 후 DB가 롤백되는 경우"를 참고.

**계좌이체 (`ACCOUNT`)** (`PaymentCommandService.java:236-279`)
- 은행명 검증 후 `AccountPayment`를 `PENDING`으로 저장한다 (`:260-262`). 외부 호출은 없다.
- 그 다음 알림과 `SOLD`가 **그대로 실행된다** (`:83`). 결제는 `PENDING`인데 판매는 `SOLD`, 알림은 "결제가 완료되었습니다"다.
- `PENDING → PAID`로 바꾸는 `updatePaymentStatus`(`:498`)는 저장소 어디에서도 호출되지 않는다. 계좌이체 입금 확인 경로는 이 코드에 없다.

**일반 결제 (`GENERAL`)** (`PaymentCommandService.java:290-333`)
- 클라이언트가 보낸 `impUid`가 비어 있지 않은지만 확인한다 (`:297-300`). PortOne에 조회하지 않는다.
- `isSuccess=true`, `status=PAID`로 저장한다 (`:313-316`). 클라이언트가 보낸 `paidAmount`와 `impUid`를 그대로 믿는 구조다. 위조된 `impUid`와 금액으로도 `PAID`가 된다.
- 알림과 `SOLD`는 계좌이체와 같이 실행된다.

**즉시 구매가 끝까지 성공하는가**
- 예외 없이 끝나는 경우에만 OrderBid가 생성되고 응답이 나간다. 세 결제 수단 모두 예외 없이 끝나면 HTTP 200과 OrderBid ID를 돌려준다.
- 그러나 "성공"이 **주문의 결제 완료**를 뜻하지는 않는다. 주문 상태는 어떤 경우에도 `PENDING_PAYMENT`다 (5절).

**카드 응답 특수 케이스**: `code == 0`인데 `status != "success"`이면 예외가 없다. 그러면 결제 행은 `PENDING`으로 저장되고, 알림과 `SOLD`가 실행되며, 주문은 `PENDING_PAYMENT`, OrderBid는 `MATCHED`로 남는 모순된 상태가 된다 (`PaymentCommandService.java:203-206`, `:83`).

**PortOne은 성공했는데 DB가 롤백되는 경우**
- 카드 결제는 `createInstantOrder` 안의 `processPayment`에서 PortOne을 먼저 호출한다. 그 뒤 `createInstantOrderBid`의 `orderBidRepository.save`(`OrderBidCommandService.java:206`)나 커밋 단계에서 실패하면 DB는 롤백되는데 카드는 이미 결제된 상태다.
- 환불 함수 `handleRefundIfNecessary`(`PaymentCommandService.java:341-375`)가 정의만 되어 있고 호출하는 곳이 없다. 보상 환불이 없다.

**금액과 중복 구매 (코드 관찰, 질문 외 중요 사항)**
- `SaleBid`의 상태를 확인하지 않고 락도 없다 (`OrderBidCommandService.java:172-184`, `OrderCommandService.java:220-249`, 락/`@Version` 없음). 같은 판매 입찰로 즉시 구매를 두 번 요청하면 두 번째 주문이 생성되고 `SaleBid.order`를 덮어쓴다 (`S/entity/SaleBid.java:58-61`). DB 제약은 확인하지 않았다.

## 4. 알림 수신자, 시점, 방식

- 수신자: 구매자(`order.getUser()`)와 판매자(`sale.getSeller()`) (`PaymentCommandService.java:434-456`).
- 내용:
  - 구매자: "결제가 완료되었습니다. 주문 ID: {orderId}" (`:438-443`)
  - 판매자: "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}" (`:449-454`)
  - 둘 다 카테고리 `SHOPPING`, 타입 `BID`.
- 시점: `processPayment` 안, 결제 행을 만든 **직후**, 주문 트랜잭션 **커밋 전**이다 (`PaymentCommandService.java:83`, `:403`, `:416`).
- 방식:
  1. `NotificationCommandService.createNotification`이 알림 행을 DB에 저장한다 (`N/service/command/NotificationCommandService.java:44-59`).
  2. 이어서 `sendRealTimeNotification`이 Redis 키(사용자 이메일 기반)가 있을 때만 WebSocket으로 `convertAndSendToUser`를 보낸다 (`:57`, `:303-318`). 즉 접속 중인 사용자에게만 실시간으로 간다. 이메일이나 푸시는 이 경로에 없다.
- 주의: WebSocket 전송은 커밋 전에 일어난다. 그 뒤에 롤백되면 DB의 알림 행은 사라지지만 이미 보낸 실시간 메시지는 회수되지 않는다. 알림 실패는 `sendNotifications`와 `notifyUsersAndUpdateSaleStatus`에서 모두 삼켜지므로 주문 처리를 막지 않는다 (`PaymentCommandService.java:421-425`, `:457-461`).

## 5. 처리 완료 후 최종 상태, 창고 보관 선택 시 차이

처리가 성공해 커밋되었을 때의 최종 상태 (결제 수단은 3절):

| 엔티티 | 최종 상태 |
|---|---|
| `Order` | `status = PENDING_PAYMENT`. 이 경로에서는 `PAYMENT_COMPLETED`/`PREPARING` 등으로 바뀌지 않는다 (`O/entity/OrderStatus.java:8-17`, `O/entity/Order.java:113-118`) |
| `OrderItem` | 1개, `price = bidPrice` |
| `OrderShipment` | `status = PENDING`, 주소 정보 복사 |
| `Payment` | 카드: `PAID` 또는 `PENDING`(3절 참고). 계좌: `PENDING`. 일반: `PAID` |
| `OrderBid` | `status = MATCHED`, `isInstantPurchase = true`, `sale` 연결 |
| `SaleBid` | `status = MATCHED`, `order` 연결 |
| `Sale` | `status = SOLD` |

**구매자가 "창고 보관"을 선택했을 때**
- 요청의 `warehouseStorage` 값은 **아무 데도 쓰이지 않는다.** 컨트롤러가 값을 서비스에 넘기지만 (`OrderBidCommandController.java:105`), `createInstantOrder`의 `isWarehouseStorage` 매개변수는 본문에서 사용되지 않는다 (`OrderCommandService.java:221`, 본문 `:222-318`).
- 실제 분기는 판매자가 판매를 등록할 때 정한 `Sale.isWarehouseStorage`로만 결정된다 (`OrderCommandService.java:291-292`, `S/service/command/SaleCommandService.java:107`).
  - 값이 참이면 `WarehouseStorage`의 상태가 `IN_STORAGE` → `ASSOCIATED_WITH_ORDER`로 바뀐다 (`:293`, `W/service/command/WarehouseStorageCommandService.java:117-135`, 전이 규칙 `:232-260`, `W/entity/WarehouseStorage.java:66-67`). 해당 `WarehouseStorage`가 없으면 `WarehouseStorageNotFoundException`이 나고 주문 전체가 롤백된다 (`W/service/query/WarehouseStorageQueryService.java:30-33`).
  - 값이 거짓이면 창고 상태는 바뀌지 않는다.
- 어느 경우든 `Order.warehouseStorage` 연결은 만들어지지 않는다. `assignWarehouseStorage`가 이 경로에서 호출되지 않는다 (`O/entity/Order.java:99-104`).
- 배송 정보(`OrderShipment`)는 창고 보관 여부와 무관하게 입력한 주소로 만들어진다 (`OrderCommandService.java:264-271`).
- 결과적으로 구매자가 창고 보관을 선택해도 주문 상태나 배송 생성에 차이가 없다. 판매자가 창고 보관으로 등록한 판매라면 창고 상태만 바뀐다.
