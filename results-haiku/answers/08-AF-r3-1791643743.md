# 답: 구매자 배송은 운송장 등록부터 배송 완료까지 어떻게 처리되나

코드는 읽기만 했다(수정 없음, 실행·DB 검증 없음). 경로는 저장소 루트 기준이고, 이하 `src/main/java/com/fream/back/`는 `BASE/`로 줄여 쓴다.

---

## 1. 운송장 등록 요청

**진입점**
- `PATCH /shipments/order/{shipmentId}/status` — `BASE/domain/shipment/controller/command/OrderShipmentCommandController.java:33-34`. 본문의 `courier`, `trackingNumber`를 `OrderShipmentCommandService.updateTrackingInfo`로 넘기고(`:41-45`), 성공 시 본문 없는 200을 준다(`:48`).
- 같은 배송에 운송장을 붙이는 다른 경로: `POST /shipments/order/{id}/check-status`(`:58`) 및 `check-status-string`(`:103`) → `updateAndCheckShipmentStatus`(`BASE/domain/shipment/service/command/OrderShipmentCommandService.java:452`). 이 경로는 운송장을 쓰고 CJ를 조회한다. 아래 "우회 경로"에서 다룬다.

**설계된 처리 순서** (`OrderShipmentCommandService.java:239`, `@Transactional`)
1. 택배사·운송장 공백 검사 (`:243-246`)
2. 배송 조회 (`:249-253`)
3. `OrderShipment.updateTrackingInfo` → courier, trackingNumber 저장, `status = IN_TRANSIT` (`BASE/domain/shipment/entity/OrderShipment.java:41-45`). `canTransitionTo`를 검사하지 않는다. `PENDING`의 허용 전이는 `SHIPPED`·`CANCELED`뿐이라(`BASE/domain/shipment/entity/ShipmentStatus.java:4-9`), 상태 머신을 우회한다.
4. 주문 → `IN_TRANSIT` (`OrderShipmentCommandService.java:260`)
5. 구매자 알림 "상품이 출발하였습니다" (`:266-271`)
6. `updateSaleStatusToSold(orderId)` (`:276`): Sale이 SOLD로 전이 가능할 때만 SOLD(`:119-123`), 창고 보관이면 창고 상태 변경(`:126-129`), 판매자 알림(`:133-138`)
7. 주문 입찰·판매 입찰 → `COMPLETED` (`:289`, 본체 `:413-440`). 이 단계의 실패는 로그만 남기고 삼킨다(`:436-439`).

**알림**: 구매자 1건(출발). 판매자 알림은 6단계에서 Sale이 실제로 SOLD로 바뀔 때만 나간다. 그런데 Sale은 결제 시점에 이미 SOLD가 되고 구매자·판매자에게 알림이 나가므로(`BASE/domain/payment/service/command/PaymentCommandService.java:83`, `:404`, `:419`, `sendNotifications` `:434`), 보통 등록 시점에 판매자에게 새 알림은 없다.

**(a) 실배송 일반 구매 입찰 주문 — 끝까지 성공하지 않는다**
- 결제·배송 처리: `POST /orders/{orderId}/process-payment-shipment`(`BASE/domain/order/controller/command/OrderCommandController.java:54`)는 Kafka 이벤트만 발행한다. 실제 처리는 `OrderEventConsumer.processCompleteOrder`(`BASE/domain/order/service/kafka/OrderEventConsumer.java:166`)가 한다. 결제 → 배송 생성 → `PAYMENT_COMPLETED`(`:192-195`) → 실배송이면 `PREPARING`(`:216-217`). 주문은 `PREPARING`으로 저장된다.
- (참고: 동기식 `OrderCommandService.processPaymentAndShipment`도 `PREPARING`을 설정하지만, 호출부가 `OrderCommandController.java:101`에서 주석 처리되어 실행되지 않는다.)
- 운송장 등록: `:260` `order.updateStatus(IN_TRANSIT)` → `BASE/domain/order/entity/Order.java:113`이 전이를 거부한다. `PREPARING`의 허용 전이는 `IN_WAREHOUSE`, `SHIPMENT_STARTED`뿐이다(`BASE/domain/order/entity/OrderStatus.java:26`). `SHIPMENT_STARTED`를 설정하는 코드는 저장소에 없다. → `InvalidOrderStatusException` (`OrderException` → `GlobalException` → `RuntimeException`, `BASE/global/exception/GlobalException.java:10`).
- 서비스의 catch-all(`OrderShipmentCommandService.java:295-301`)이 이것을 `ShipmentException(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생…")`으로 감싸 던진다 → 트랜잭션 롤백.
- **저장되는 것: 없음.** 운송장, 배송 IN_TRANSIT, 주문 상태, 알림, Sale, 입찰 상태 모두 롤백된다. 배송은 PENDING, 주문은 PREPARING 그대로다.
- **응답**: HTTP 404, `code: S001`, message "배송 정보를 찾을 수 없습니다.", path (`BASE/global/exception/GlobalExceptionHandler.java:459-471`, `BASE/domain/shipment/exception/ShipmentErrorCode.java:12`). 실제 원인(주문 상태 전이 오류)은 로그에만 남고 응답에는 없다. 에러 코드가 원인을 잘못 가리킨다.

**(b) 즉시 구매 — 등록에서 실패하지만 원인이 다르다**
- 생성 흐름: `POST` 즉시 구매(`BASE/domain/order/controller/command/OrderBidCommandController.java:101-107`) → `OrderBidCommandService.createInstantOrderBid`(`BASE/domain/order/service/command/OrderBidCommandService.java:119`) → `OrderCommandService.createInstantOrder`(`BASE/domain/order/service/command/OrderCommandService.java:220`).
  - 주문 `PENDING_PAYMENT` (`:244`), 배송 생성 (`:264`), SaleBid에 주문 연결 + MATCHED (`:279-280`), **결제는 여기서 동기로 처리** (`:305`).
  - 이어서 OrderBid를 MATCHED, 주문·판매와 연결해 생성 (`OrderBidCommandService.java:189-206`, `isInstantPurchase` 플래그).
- 이 흐름은 주문을 `PAYMENT_COMPLETED`로 바꾸지 않는다. `PAYMENT_COMPLETED` 설정은 `OrderEventConsumer.java:195`에만 있다. 그래서 주문은 `PENDING_PAYMENT`에 머문다.
- 운송장 등록: `PENDING_PAYMENT → IN_TRANSIT`은 허용되지 않는다(`OrderStatus.java:24`). → (a)와 같은 롤백, 같은 404 S001.
- 주의 (데이터 정합성): 즉시 구매 응답의 `orderId`는 실제로 `OrderBid.getId()`다(`OrderBidCommandController.java:101-107`). 클라이언트가 이 값으로 `process-payment-shipment`를 호출하면 엉뚱한 주문을 처리하거나, 주문이 `PENDING_PAYMENT`라 중복 검사(`OrderEventConsumer.java:244`)를 통과해 결제가 두 번 실행될 수 있다. 확인한 범위(`PaymentCommandService.java:117-127`)에는 중복 결제 방지 검사가 없었다.

**요약**: 두 종류 모두 PATCH 등록은 끝까지 성공하지 못한다. (a)는 `PREPARING`에서, (b)는 `PENDING_PAYMENT`에서 `IN_TRANSIT` 전이에 막힌다. 두 경우 모두 `OrderShipmentCommandService.java:260`에서 실패한다.

**우회 경로 (check-status, `OrderShipmentCommandService.java:452-516`)**: 운송장을 `IN_TRANSIT`으로 먼저 쓰고(`:473`) CJ를 조회한다. 주문 상태는 건드리지 않는다. 결과는 CJ 문구에 따라 갈린다.
- CJ "배송출발" → `OUT_FOR_DELIVERY`(`:491-493`) 저장. 주문은 그대로. 이후 배치 대상이 된다.
- CJ "배송완료" → `DELIVERED` → `completeOrder`(`:483-489`). (a)는 PREPARING→COMPLETED 불가로 실패 → 404 S102(`ShipmentErrorCode.java:20`) 및 롤백. (b)는 성공(아래 3, 4).
- CJ 그 밖의 문구(예: 배송 중) → `else` 분기(`:495-497`)가 `IN_TRANSIT → IN_TRANSIT`을 시도한다. `IN_TRANSIT`은 `IN_TRANSIT`으로 전이할 수 없으므로(`ShipmentStatus.java:16-22`) `IllegalStateException` → `EXTERNAL_TRACKING_SERVICE_ERROR`(503, `ShipmentErrorCode.java:30`) → 롤백. 저장되는 것이 없다.

## 2. 배송 완료 감지

- **주체**: 서버의 주기 배치가 CJ 추적 페이지를 조회한다. 택배사 웹훅은 없다.
- **주기**: `@Scheduled(cron = "0 0 */6 * * *")` → 6시간마다 정각(0·6·12·18시, 서버 로컬 시각). `BASE/global/config/ShipmentBatchScheduler.java:34`. `jobLauncher.run`은 `:40`, 예외는 `printStackTrace`만 한다(`:41-43`). 배치 인프라는 `BASE/global/config/BatchInfraConfig.java:15`의 `@EnableBatchProcessing`.
- **대상**: `status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND trackingNumber IS NOT NULL` (`BASE/domain/shipment/config/UpdateShipmentStatusesJobConfig.java:89-96`, 쿼리 `:95`). 정렬 조건이 없다.
- **실제 실행되는 처리 코드**: `BASE/domain/shipment/config/ShipmentItemProcessor.java:57` `process()`.
  - 스텝이 `new ShipmentItemProcessor(...)`를 직접 만들어 쓴다(`UpdateShipmentStatusesJobConfig.java:69-73`).
  - 헤드리스 Playwright로 CJ 추적 페이지를 연다(`:72` `browserManager.newPage()`, `:83` navigate). `tbody#statusDetail tr`을 기다리고(`:87`, 타임아웃 30초 `:78`), 마지막 행의 5번째 칸 텍스트를 읽는다(`:181`). 빈 값이면 예외(`:183-189`).
  - 브라우저는 스텝 시작 때 열리고 끝날 때 닫힌다(`BASE/domain/shipment/config/BrowserManageStepListener.java:15-25`, `BASE/global/utils/PlaywrightBrowserManager.java:35,73,111`).
- **실행되지 않는 비슷한 코드 (헷갈리기 쉬움)**:
  - `UpdateShipmentStatusesJobConfig.shipmentItemProcessor()` 빈(`:104-177`): 스텝에 연결되지 않는다. `CjTrackingPlaywright`를 쓰고, 주석(`:101-102`)은 "Order 상태도 완료"라고 말하지만 실행되지 않는다.

  - `OrderShipmentCommandService.updateShipmentStatuses()`(`BASE/domain/shipment/service/command/OrderShipmentCommandService.java:309-391`): 호출처 없음.
  - `CjTrackingPlaywright.getCurrentTrackingStatus`(`BASE/global/utils/CjTrackingPlaywright.java:33`): 배치에서는 쓰이지 않고, check-status 엔드포인트(`OrderShipmentCommandService.java:477`)만 쓴다.
- **택배사 문구 → 내부 상태** (`ShipmentItemProcessor.java:220-226`)

## 4. 주문 종류별 차이

3의 완료 처리는 주문이 `COMPLETED`로 전이 가능한 상태여야 진행된다. 두 주문의 결제 후 상태가 달라 결과가 갈린다.

| 항목 | (a) 일반 구매 입찰 | (b) 즉시 구매 |
|---|---|---|
| 결제 후 주문 상태 | `PREPARING` (`OrderEventConsumer.java:216-217`) | `PENDING_PAYMENT` (`OrderCommandService.java:244`, 결제 후에도 변경 없음) |
| 운송장 PATCH | 실패: `PREPARING → IN_TRANSIT` 불가 (`OrderShipmentCommandService.java:260`) | 실패: `PENDING_PAYMENT → IN_TRANSIT` 불가 (`:260`) |
| check-status로 "배송출발" 저장 후 배치 진입 | 가능 (주문 상태 불변) | 가능 (주문 상태 불변) |
| 배송 완료 처리 시 주문 → COMPLETED (`:204`) | **실패**: `PREPARING → COMPLETED` 불가 (`OrderStatus.java:26`) → 처리기 예외 → 건너뜀 | 통과: `PENDING_PAYMENT → COMPLETED` 허용 (`OrderStatus.java:24`) |
| 판매 완료 처리의 SaleBid 조회 (`:116`) | 주문에 연결된 SaleBid가 없어 `IllegalArgumentException` → 롤백 | 연결됨 (`OrderCommandService.java:279-280`) |
| 최종 결과 | 주문 PREPARING, 배송 IN_TRANSIT/OUT_FOR_DELIVERY 유지. 6시간마다 재시도·건너뜀 | 주문 COMPLETED, 배송 DELIVERED. 구매자 알림 2건(배치) 또는 1건(check-status). 입찰은 MATCHED 유지 |

근거:
- SaleBid에 주문을 연결하는 곳은 즉시 구매(`OrderCommandService.java:279`)와 즉시 판매(`BASE/domain/sale/service/command/SaleBidCommandService.java:83`)뿐이다. 일반 판매 입찰 매칭은 주문을 연결하지 않는다. 그래서 (a)는 `:116`에서 항상 실패한다. 그리고 `:116`은 주문 상태 전이(`:204`) 뒤에 있으므로, (a)의 주문 상태가 COMPLETED 가능했더라도 막힌다.
- (b)의 판매 완료 처리는 결제 시점에 이미 SOLD가 되어 있어 no-op이다. 판매 완료 처리 자체에서는 예외가 나지 않는다.
- 다만 (b)가 "끝까지 간다"는 것은 결제 완료 전환이 빠진 상태(`PENDING_PAYMENT`)에서 우연히 통과하는 것이다. 위 1번의 중복 결제·orderId 문제가 함께 있다.

## 5. 실패 처리

- **스텝 설정** (`UpdateShipmentStatusesJobConfig.java`): 청크 50(`:67`), `faultTolerant().skip(Exception.class)`(`:75-76`), `skipLimit(50)`(`:77`), skip 리스너 로그(`:78`, `:252-287`).
- **한 건 실패** (예: CJ 조회 실패, 상태 전이 예외): `ShipmentItemProcessor`의 catch(`:133-145`)가 감싸서 다시 던진다 → 그 건은 쓰지 않고 건너뛴다. 그 건의 배송 상태는 바뀌지 않으므로(IN_TRANSIT/OUT_FOR_DELIVERY 그대로) 6시간 뒤 다음 실행에서 다시 선택된다.
- **같은 청크의 나머지 건**: 처리기가 청크 트랜잭션 안에서 실행되므로 예외가 나면 청크가 롤백된다. Spring Batch의 기본 동작은 청크 항목을 1건씩 다시 처리하는 것이다(프레임워크 동작에 근거한 설명, 실행으로 확인하지는 않았다). 그래서 실패 건 앞의 정상 건들은 CJ 조회를 다시 하고 각자 커밋된다. 실패 건이 같은 트랜잭션에서 만든 DB 변경(예: `:113`의 DELIVERED 설정)도 롤백된다.
- **외부 부작용은 롤백되지 않는다**: 알림은 저장 직후 WebSocket으로 실시간 전송된다(`NotificationCommandService.java:303-315`). 청크가 나중에 롤백되면, 저장되지 않은 알림이 실시간으로만 전달될 수 있다.
- **실패 누적과 스텝 중단**: 한 실행에서 건너뛰기가 50건을 넘으면 `SkipLimitExceededException`으로 스텝이 실패하고, 그 실행의 남은 건은 처리되지 않는다. 영구적으로 실패하는 건(예: 위 4번 (a))은 매 실행마다 건너뛰기 카운트를 채운다. 실패 건이 51개 이상 쌓이면 정상 건도 매 주기 처리되지 못한다. 이를 알리는 장치는 없다(`ShipmentBatchScheduler.java:41-43`은 `printStackTrace`만 한다).
- **추가 관찰 1 (추정, 실행 확인 안 함)**: 정렬 없는 오프셋 페이징(`UpdateShipmentStatusesJobConfig.java:89-96`)에서 청크를 커밋할 때마다 DELIVERED 건이 IN_TRANSIT 집합에서 빠진다. 그러면 다음 페이지의 오프셋이 밀려 일부 건을 건너뛸 수 있다.
- **추가 관찰 2**: OUT_FOR_DELIVERY 건의 CJ 최신 문구가 "배송출발"·"배송완료"가 아닌 것으로 바뀌면 `IN_TRANSIT`으로 매핑된다. 그런데 `OUT_FOR_DELIVERY → IN_TRANSIT`은 허용되지 않아(`ShipmentStatus.java:23-28`, `OrderShipment.java:47-55`의 `IllegalStateException`) 그 건은 매 실행 건너뛰기된다(`ShipmentItemProcessor.java:123-126`).

## 의도와 실제 동작이 다른 곳

- `updateTrackingInfo`는 "운송장 등록"인데, 주문 IN_TRANSIT, 판매 SOLD, 입찰 COMPLETED까지 한 번에 처리한다(`OrderShipmentCommandService.java:260`, `:276`, `:289`). 입찰 완료가 배송 완료가 아니라 등록 시점에 일어나도록 짜여 있다. 실제로는 (a)·(b) 모두 여기서 실패하므로 이 경로로 COMPLETED가 된 입찰은 없다.
- `updateTrackingInfo`의 catch-all은 모든 오류를 `SHIPMENT_NOT_FOUND`(404)로 바꾼다(`:297-301`). 응답이 실제 원인을 가린다.
- `updateOrderAndSaleBidStatusToCompleted`는 `private`인데 `@Transactional`이 붙어 있고(`:412-413`), 실패를 삼킨다(`:436-439`).
- `UpdateShipmentStatusesJobConfig`의 주석과 미사용 빈(`:101-102`, `:104-177`)은 Jsoup·`CjTrackingPlaywright` 기반 처리를 설명하지만, 실제로 실행되는 것은 Playwright 기반 `ShipmentItemProcessor`다.
- 결제·배송 처리의 동기 버전 `OrderCommandService.processPaymentAndShipment`는 호출되지 않는다(`OrderCommandController.java:101` 주석).

## 확인하지 못한 것
- 실행과 DB 검증은 하지 않았다. 청크 재처리와 오프셋 건너뛰기는 프레임워크 동작에 근거한 설명이다.
- 서버 타임존, 클라이언트가 즉시 구매 뒤 `process-payment-shipment`를 실제로 호출하는지는 저장소 밖이라 확인할 수 없다.
