# 구매자 배송: 운송장 등록부터 배송 완료까지

근거 경로는 모두 `src/main/java/com/fream/back/` 기준이다. 코드는 읽기만 했고 실행하지 않았다. 결론은 코드 읽기에 근거한다.

## 요약

- 운송장 등록(`PATCH /shipments/order/{id}/status`)은 **실배송 일반 구매 입찰 주문(a)과 즉시 구매 주문(b) 모두에서 실패**한다. 주문 상태가 `IN_TRANSIT`으로 전이할 수 없는 구조이기 때문이다. 실패하면 404 응답이고 아무것도 저장되지 않는다.
- 배송 완료 감지는 6시간마다 도는 Spring Batch 잡이 CJ대한통운 페이지를 스크래핑해서 한다. 실제 처리 코드는 `ShipmentItemProcessor`다.
- 완료 처리는 (b)에서만 끝까지 간다. 운송장 등록 없이 `check-status` API로 "배송출발"을 먼저 기록해 둔 경우에 한한다. (a)는 주문 상태가 `PREPARING`이라 `COMPLETED`로 전이하지 못해 완료되지 않는다.
- 완료 처리 후 입찰(`OrderBid`, `SaleBid`)은 `MATCHED`에 머문다. 문서가 말하는 `COMPLETED` 전환은 실행되지 않는다.

## 1. 운송장 등록 요청

**API**
- `PATCH /shipments/order/{shipmentId}/status` — `domain/shipment/controller/command/OrderShipmentCommandController.java:20, 33-46`
- 본문은 `courier`, `trackingNumber`다 (`domain/shipment/dto/OrderShipmentRequestDto.java`, 검증 어노테이션 없음). 빈 값이면 서비스가 `TRACKING_INFO_REQUIRED`(400)로 거부한다 (`domain/shipment/service/command/OrderShipmentCommandService.java:243-246`).

**코드가 의도한 처리 순서** (`OrderShipmentCommandService.updateTrackingInfo`, `:238-303`)
1. OrderShipment의 courier·trackingNumber를 쓰고 status를 `IN_TRANSIT`으로 직접 대입한다. 전이표 검사를 거치지 않는다 (`domain/shipment/entity/OrderShipment.java:41-45`). 전이표상 `PENDING`에서는 `SHIPPED`·`CANCELED`만 허용된다 (`domain/shipment/entity/ShipmentStatus.java:60-65`).
2. Order를 `IN_TRANSIT`으로 바꾼다 (`OrderShipmentCommandService.java:260`).
3. 구매자에게 "상품이 출발하였습니다" 알림 1건을 보낸다 (`:266-271`).
4. `updateSaleStatusToSold`를 호출한다 (`:276`). Sale을 `SOLD`로 바꾸고 판매자에게 알림을 보내도록 되어 있다 (`:112-138`).
5. 창고 보관 상태 갱신 (`:279-286`), OrderBid·SaleBid를 `COMPLETED`로 바꾼다 (`:289`, 실제 구현 `:413-440`).

**실제 동작: 2번에서 실패한다**
- `Order.updateStatus`는 `OrderStatus.canTransitionTo`로 검사한다 (`domain/order/entity/Order.java:113-121`).
- `IN_TRANSIT`으로 들어가는 전이는 `SHIPMENT_STARTED → IN_TRANSIT` 하나뿐이다 (`domain/order/entity/OrderStatus.java:28-29`).
- 그런데 `SHIPMENT_STARTED`는 어디에서도 설정되지 않는다. 소스 전체에서 나오는 곳은 화면 표시용 문자열뿐이다 (`domain/order/controller/query/OrderQueryController.java:207`). 따라서 `IN_TRANSIT`에 도달할 경로가 없다.
- 현재 주문 상태로도 막힌다. `PREPARING`은 `IN_WAREHOUSE`·`SHIPMENT_STARTED`만 허용하고 (`OrderStatus.java:26`), `PENDING_PAYMENT`는 `PAYMENT_COMPLETED`·`COMPLETED`·`IN_WAREHOUSE`만 허용한다 (`OrderStatus.java:24`).
- `Order.java:117`이 던진 `InvalidOrderStatusException`은 `catch (Exception e)`에서 `ShipmentException(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")`로 감싸져 던져진다 (`OrderShipmentCommandService.java:295-301`). `@Transactional` 때문에 전체가 롤백된다.

**저장되는 것: 없음.** 1번의 courier·trackingNumber·`IN_TRANSIT`도 롤백된다. 알림, Sale 변경, 입찰 변경은 그 이전에 실패하므로 실행되지 않는다.

**응답: HTTP 404, 본문 `{code: "S001", message: "배송 정보를 찾을 수 없습니다.", status: 404, path}`**
- `GlobalExceptionHandler`는 ErrorCode의 고정 메시지를 내보낸다 (`global/exception/GlobalExceptionHandler.java:49-63`). 그래서 상세 메시지는 응답에 나가지 않는다. `ShipmentErrorCode.java:12`.
- 원인("상태 전환이 허용되지 않습니다: PREPARING -> IN_TRANSIT" 형태)은 로그에만 남는다 (`OrderShipmentCommandService.java:297` 앞 catch 경로, `Order.java:117`).

**(a)·(b) 주문이 이 시점에 놓이는 상태**
- **(a) 실배송 일반 구매 입찰.** `POST /orders/{orderId}/process-payment-shipment` (`domain/order/controller/command/OrderCommandController.java:42`)은 Kafka로 발행한다 (`:54`). 동기 처리 메서드 `processPaymentAndShipment`는 컨트롤러에서 호출이 주석 처리되어 있다 (`:101`). 실제 처리는 `OrderEventConsumer.processCompleteOrder`다 (`domain/order/service/kafka/OrderEventConsumer.java:166`).
  - 결제 → OrderShipment 생성(`PENDING`, `OrderShipmentCommandService.java:67`) → Order `PENDING_PAYMENT`→`PAYMENT_COMPLETED` (`OrderEventConsumer.java:192-195`) → `PREPARING` (`:216-217`).
  - 결제 중에 `PaymentCommandService.notifyUsersAndUpdateSaleStatus`가 Sale을 이미 `SOLD`로 바꾸고, 구매자·판매자에게 결제 알림을 보낸다 (`domain/payment/service/command/PaymentCommandService.java:83`, `:383-420`, `:434-455`).
- **(b) 즉시 구매.** `OrderCommandService.createInstantOrder`가 Order를 `PENDING_PAYMENT`로 만들고 (`domain/order/service/command/OrderCommandService.java:244`), OrderShipment를 만들고 (`:264`), 결제한다 (`:305`). 결제 후 Order 상태를 바꾸는 코드가 없어서 `PENDING_PAYMENT`에 머문다. OrderBid는 `MATCHED`로 만들어진다 (`domain/order/service/command/OrderBidCommandService.java:142, 196`). Sale은 결제 중에 `SOLD`가 된다.

**(a)·(b) 결과: 둘 다 운송장 등록 실패.** (a)는 `PREPARING`→`IN_TRANSIT`, (b)는 `PENDING_PAYMENT`→`IN_TRANSIT`이 막힌다.

## 2. 배송 완료 감지

**누가·언제·어떻게**
- 스케줄러가 자동으로 실행한다. `global/config/ShipmentBatchScheduler.java:34-44`.
- `cron = "0 0 */6 * * *"`이므로 하루 4회, 00:00·06:00·12:00·18:00(서버 기본 타임존)이다. 매 실행마다 timestamp 파라미터가 달라서 새 Job 인스턴스가 된다 (`:37-40`). `@EnableScheduling`은 다른 설정 클래스에서 켜져 있어 전역에 적용된다 (`domain/event/scheduler/EventStatusScheduler.java:22`).
- 대상: `status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND trackingNumber IS NOT NULL`, 50건 단위, 정렬 없음 (`domain/shipment/config/UpdateShipmentStatusesJobConfig.java:169-179`, 쿼리 `:177`).
- Step은 chunk 50, `skip(Exception.class)`, `skipLimit(50)`이다 (`UpdateShipmentStatusesJobConfig.java:144-164`, 특히 `:157-159`).

**실제로 실행되는 처리 코드**
- Step은 `new ShipmentItemProcessor(...)`를 쓴다 (`UpdateShipmentStatusesJobConfig.java:151-155`). 실제 처리는 `ShipmentItemProcessor.process` (`domain/shipment/config/ShipmentItemProcessor.java:57-157`)다.
- 실행되지 않는 비슷한 코드:
  - `UpdateShipmentStatusesJobConfig.shipmentItemProcessor()` @Bean (`:186-259`). 어떤 Step에도 연결되지 않는다.
  - `UpdateShipmentStatusesJobConfig.parseCjLogisticsStatus` (`:268-302`). 호출자가 없다.
  - `OrderShipmentCommandService.updateShipmentStatuses()` (`OrderShipmentCommandService.java:309-391`). 호출자가 없다 (소스 전체 검색).
- 조회 방식
  - Step 시작 시 브라우저를 한 번 연다 (`domain/shipment/config/BrowserManageStepListener.java:240-251`, `global/utils/PlaywrightBrowserManager.java:35-68`).
  - 건마다 `newPage()` (`ShipmentItemProcessor.java:72`), `https://trace.cjlogistics.com/next/tracking.html?wblNo=…`로 이동 (`:81-83`), `tbody#statusDetail tr` 대기 (`:87`, 타임아웃 30초 `:78`).
  - 마지막 행의 다섯 번째 `td` 텍스트를 읽는다 (`:181`, 파싱 `:167-212`).
- `CjTrackingPlaywright.getCurrentTrackingStatus`(`global/utils/CjTrackingPlaywright.java:33`)는 배치에서 쓰지 않는다. check-status API에서만 쓴다 (`OrderShipmentCommandService.java:477`).

**택배사 상태 문자열 → 내부 상태** (`ShipmentItemProcessor.java:220-226`)
- `"배송완료"` → `DELIVERED`
- `"배송출발"` → `OUT_FOR_DELIVERY`
- 그 외 모든 문자열 → `IN_TRANSIT`
- 빈 문자열은 파싱 단계에서 예외가 난다 (`:183-189`).
- 현재 상태와 같으면 아무 일도 하지 않는다 (`:101-105`).

**주기 한계**: 폴링이라 배송 완료 반영이 최대 6시간 늦어진다.

## 3. 배송 완료 판정 이후 (배치 경로, `ShipmentItemProcessor.java:108-118`)

처리 순서:
1. OrderShipment → `DELIVERED` (`ShipmentItemProcessor.java:113`, `OrderShipment.java:47-55`, 허용 `ShipmentStatus.java:79-84`, `:72-78`).
2. `orderService.completeOrder(orderId)` (`:116`, `OrderShipmentCommandService.java:191-229`)
   - OrderBid 조회 (`:196`). 없으면 예외다.
   - Order → `COMPLETED` (`:204`).
   - `updateSaleStatusToSold` (`:208`). Sale은 이미 `SOLD`라서 `canTransitionTo(SOLD)`가 거짓이다 (`:119`, `:156`). 아무 일도 없다. 판매자 알림도 없다.
   - 구매자 알림 "[completeOrder] 주문이 완료 처리되었습니다…" (`:211-217`).
3. `notifyShipmentCompleted(order)` (`ShipmentItemProcessor.java:117` → `domain/notification/service/command/NotificationCommandService.java:219-233`). 구매자 알림 "[배송 완료] …" 1건.
4. 청크 커밋 시 OrderShipment 저장 (`UpdateShipmentStatusesJobConfig.java:321-328`).

**알림**: 구매자 **2건**, 판매자 **0건**.

**입찰 상태**: OrderBid·SaleBid 모두 **`MATCHED` 그대로**다. `completeOrder`에는 입찰 상태를 바꾸는 코드가 없다. `COMPLETED`로 바꾸는 `updateOrderAndSaleBidStatusToCompleted`(`OrderShipmentCommandService.java:413-440`)는 `updateTrackingInfo`(`:289`)와 죽은 코드인 `updateShipmentStatuses`(`:424`, `:431`)에서만 호출된다. `updateTrackingInfo`는 1번에서 항상 실패한다. SHIPMENT_README의 "입찰 COMPLETED" 설명은 실제 동작과 다르다.

**check-status 경로도 같은 완료 로직을 쓴다.** `updateAndCheckShipmentStatus`의 DELIVERED 분기는 `shipment.updateStatus(DELIVERED)`(`:486`) 후 `completeOrder`를 호출한다(`:489`). 다만 `notifyShipmentCompleted`는 없어서 구매자 알림은 1건이다.

## 4. 주문 종류별 차이

### (a) 실배송 일반 구매 입찰 (Order `PREPARING`, 입찰 `MATCHED`, Sale `SOLD`는 결제 시점)
- 운송장 PATCH: 실패. 404, 저장 없음 (1번 참고).
- 배치가 이 건을 잡으려면 shipment가 `IN_TRANSIT`/`OUT_FOR_DELIVERY`여야 하는데, PATCH가 실패하므로 이 상태가 되지 않는다.
  - 예외 경로: check-status에서 CJ가 "배송출발"을 주면 OrderShipment는 `OUT_FOR_DELIVERY`로 저장되고 200을 반환한다 (`OrderShipmentCommandService.java:491-493`). 주문은 건드리지 않아 `PREPARING`에 머문다.
- 이후 CJ가 "배송완료"를 주면 `completeOrder`에서 `PREPARING→COMPLETED`가 막힌다 (`OrderStatus.java:26`). `ShipmentException(ORDER_NOT_FOUND_FOR_SHIPMENT)`(`OrderShipmentCommandService.java:221-227`)가 나고, check-status는 404로 롤백한다 (`:489`, controller `:80-86`). 배치는 그 건을 skip한다 (`ShipmentItemProcessor.java:116` → `:133-145`).
- check-status에서 "배송완료"가 바로 나오면 DELIVERED도 같은 이유로 롤백되어 404가 된다.
- **최종 상태**: 배송 완료 안 됨. Order `PREPARING`, shipment `OUT_FOR_DELIVERY`, 입찰 `MATCHED`, 완료 알림 없음.

### (b) 즉시 구매 (Order `PENDING_PAYMENT`, Sale `SOLD`는 결제 시점, OrderBid `MATCHED`)
- 운송장 PATCH: 실패. 404, 저장 없음.
- check-status (`OrderShipmentCommandService.updateAndCheckShipmentStatus`, `:452-516`):
  - **"배송중" 등 기본값(IN_TRANSIT)**: `:497`에서 `IN_TRANSIT`→`IN_TRANSIT`을 시도한다. `ShipmentStatus.IN_TRANSIT`은 `IN_TRANSIT`으로 갈 수 없다 (`ShipmentStatus.java:72-78`). `OrderShipment.java:51`에서 `IllegalStateException`이 나고, `EXTERNAL_TRACKING_SERVICE_ERROR`(503)로 감싸져 롤백된다 (`OrderShipmentCommandService.java:507-514`). `/check-status`는 503을 빈 본문으로, `/check-status-string`은 `"Error: …"` 본문으로 돌려준다 (`OrderShipmentCommandController.java:80-86, 124-130`). 즉 가장 흔한 "배송 중" 조회가 항상 실패한다. 운송장 번호도 저장되지 않는다.
  - **"배송출발"**: OrderShipment `OUT_FOR_DELIVERY` 저장, 200. 주문은 건드리지 않는다.
  - **"배송완료"**: `DELIVERED`(`:486`) → `completeOrder`에서 `PENDING_PAYMENT→COMPLETED`가 허용된다 (`OrderStatus.java:24`). Order `COMPLETED`, 구매자 알림 1건, 입찰 `MATCHED` 유지, 200 `DELIVERED`. **이 경로로 (b)는 끝까지 완료된다.**
- 배치: `OUT_FOR_DELIVERY` 건이 "배송완료"가 되면 Order `COMPLETED`, 구매자 알림 **2건**(completeOrder 1 + notifyShipmentCompleted 1), 판매자 0건, 입찰 `MATCHED` 유지.
- **최종 상태**: 운송장 PATCH 없이 check-status로만 진행되며, "배송완료"를 거치면 Order `COMPLETED`가 된다. 입찰은 `MATCHED`로 남는다.

## 5. 실패 처리 (배치)

- 처리 중 예외가 나면 `skip(Exception.class)`로 그 건을 건너뛴다 (`UpdateShipmentStatusesJobConfig.java:157-158`). `SkipListener`가 로그를 남긴다 (`:333-348`).
- 같은 청크의 나머지 건은 Spring Batch의 fault-tolerant 기본 동작에 따라 다시 처리되어 정상 건은 저장된다. 이 부분은 프레임워크 동작에 근거한 판단이다. 실행해 확인하지는 않았다.
- 실패한 건의 변경(주문, Sale, 알림 포함)은 청크 트랜잭션과 함께 롤백된다. 그 건의 DB 상태는 `IN_TRANSIT`/`OUT_FOR_DELIVERY` 그대로이고, 다음 주기(6시간 뒤)에 다시 대상이 된다.
- **skip 한도**: step 전체 skip이 50을 넘으면 step이 실패하고 job도 실패한다. 그 실행의 나머지 건은 처리되지 않는다.
- **영구 실패 건의 누적**: 매 실행마다 같은 건이 skip을 소모한다. 대표 예는 두 가지다.
  - (a) 형 건: 주문이 `PREPARING`인데 shipment가 `OUT_FOR_DELIVERY`인 경우 (위 4-(a)).
  - `OUT_FOR_DELIVERY` 건을 CJ가 "배송중"으로 주는 경우. 기본 매핑이 `IN_TRANSIT`이라서 `ShipmentItemProcessor.java:119-126`에서 `OUT_FOR_DELIVERY→IN_TRANSIT`을 시도하고, 전이표가 막아 예외가 난다 (`:125`, 래핑 `:133-145`).
  - 이런 건이 50을 넘으면 매 실행마다 한도가 소진되어 뒤쪽 정상 건이 기아 상태가 된다.
- **페이징 주의**: `JpaPagingItemReader`는 offset 페이징인데, 조회 조건(status)이 처리 중에 바뀐다. `DELIVERED`가 된 건이 목록에서 빠지면 다음 페이지 offset이 밀려서 일부 건이 같은 실행에서 건너뛰어질 수 있다. 구조로부터의 추론이며 실행해서 확인하지는 않았다.

## 기타 발견 (질문 외)

- `OrderShipment.updateTrackingInfo`(`OrderShipment.java:41-45`)는 전이표를 거치지 않고 `IN_TRANSIT`을 직접 쓴다. 메서드 이름과 문서는 "전이"처럼 읽히지만 실제로는 검사를 우회한다.
- `updateSaleStatusToSold`의 SaleBid 조회(`OrderShipmentCommandService.java:116`)는 없으면 `IllegalArgumentException`을 던지고, 이 호출은 try로 감싸져 있지 않다 (`domain/sale/service/query/SaleBidQueryService.java:26-29`). SaleBid가 없는 주문은 `completeOrder`에서 실패한다.
- `OrderShipmentCommandService.updateTrackingInfo`가 정상 경로였다면 Sale을 결제 시점에 이미 `SOLD`로 바꾼 뒤이므로 판매자 "판매 완료" 알림도 나가지 않았을 것이다 (`:119`, `PaymentCommandService.java:404/419`).

## 검증 한계

- 실행하지 않았다. DB, Kafka, Playwright, CJ 사이트 접근이 없어서 모든 결론은 코드 읽기에 근거한다.
