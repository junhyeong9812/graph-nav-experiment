# 답: 구매자 배송의 운송장 등록 → 배송 완료 처리

## 요약

- **운송장 등록은 현재 코드로 성공하지 않는다.** 등록 시 `Order`를 `IN_TRANSIT`으로 바꾸는데, 실배송 일반 구매 입찰 주문은 `PREPARING`, 즉시 구매 주문은 `PENDING_PAYMENT` 상태라서 전이가 막힌다. 이 실패로 저장되는 것은 없고 응답은 404이다.
- 그래서 `IN_TRANSIT` 배송이 생기는 경로는 `check-status` 엔드포인트뿐이다. 이 경로로 배송이 `IN_TRANSIT`이 되면 6시간 주기 배치가 그 배송을 조회한다.
- 배치 완료 처리는 주문 종류에 따라 갈린다. (a) 실배송 일반 구매는 `PREPARING → COMPLETED` 전이가 막혀 건별 실패·롤백된다. (b) 즉시 구매는 주문 완료까지 진행되지만 판매 상태·판매자 알림·입찰 상태는 바뀌지 않는다.

## 1. 운송장 등록 요청

**1-1. 진입 API**

- `PATCH /shipments/order/{shipmentId}/status`, 본문 `OrderShipmentRequestDto`(택배사, 운송장 번호). `src/main/java/com/fream/back/domain/shipment/controller/command/OrderShipmentCommandController.java:33-49`
- 같은 운송장 정보를 등록하는 경로가 하나 더 있다. `POST /shipments/order/{id}/check-status`(`...OrderShipmentCommandController.java:58-94`)는 `updateAndCheckShipmentStatus`를 호출하며, 그 안에서 `shipment.updateTrackingInfo`로 `IN_TRANSIT`을 세운다. `src/main/java/com/fream/back/domain/shipment/service/command/OrderShipmentCommandService.java:473`
- 권한: `SecurityConfig`에 `/shipments` 관련 규칙은 보이지 않는다(`src/main/java/com/fream/back/global/config/security/SecurityConfig.java:51`의 화이트리스트 외 명시 규칙 없음). "운영 측"이라는 제한은 코드에서 확인되지 않았다.

**1-2. 설계된 상태 변화와 알림 (`updateTrackingInfo`, `OrderShipmentCommandService.java:239-303`)**

순서대로 다음이 일어나도록 짜여 있다.

1. `OrderShipment`: `PENDING` → `IN_TRANSIT`. `OrderShipment.updateTrackingInfo`는 전이 검사 없이 `IN_TRANSIT`을 직접 대입한다 (`src/main/java/com/fream/back/domain/shipment/entity/OrderShipment.java:41-45`). 이는 `ShipmentStatus`의 규칙(`PENDING → SHIPPED → IN_TRANSIT`, `ShipmentStatus.java:60-72`)과도 맞지 않는다.
2. `Order`: `SHIPMENT_STARTED → IN_TRANSIT`을 의도 (`OrderShipmentCommandService.java:260`).
3. 구매자 알림 1건: "상품이 출발하였습니다" (`OrderShipmentCommandService.java:265-271`).
4. `updateSaleStatusToSold` 호출 (`:276`). 판매가 `SOLD`로 바뀔 수 있을 때만 판매자 알림 1건 (`:116-141`).
5. 창고 보관 상품이면 창고 상태 갱신 (`:279-286`).
6. `OrderBid`·`SaleBid`를 `COMPLETED`로 변경 (`:289`, 구현은 `:413-440`). 배송 전인데 입찰이 완료되는 의도다.

응답은 성공 시 200 빈 본문이다 (`OrderShipmentCommandController.java:48`).

**1-3. 실배송 일반 구매 입찰 주문과 즉시 구매 주문에서 실제 동작**

**(a) 실배송 일반 구매 입찰 주문 — 실패**

- 주문 상태: 결제·배송 처리 후 `PAYMENT_COMPLETED → PREPARING`으로 끝난다 (`src/main/java/com/fream/back/domain/order/service/command/OrderCommandService.java:175-176`, 같은 결과가 `src/main/java/com/fream/back/domain/order/service/kafka/OrderEventConsumer.java:216-218`).
- `OrderBid`는 `MATCHED` (`src/main/java/com/fream/back/domain/order/entity/OrderBid.java:60-75`). 연결된 `SaleBid`는 없다. `Sale`은 `PENDING_SHIPMENT` (`src/main/java/com/fream/back/domain/sale/service/command/SaleCommandService.java:62`).
- **실패 지점: `OrderShipmentCommandService.java:260`.** `Order.updateStatus`는 `PREPARING → IN_TRANSIT`을 허용하지 않는다. 허용 목록은 `PREPARING → {IN_WAREHOUSE, SHIPMENT_STARTED}`이다 (`src/main/java/com/fream/back/domain/order/entity/OrderStatus.java:26`, 검사는 `src/main/java/com/fream/back/domain/order/entity/Order.java:113-121`). 여기서 `InvalidOrderStatusException`이 난다.
- 예외는 `OrderShipmentCommandService.java:295-301`에서 `ShipmentException(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: ...")`로 감싸져 다시 던져지고, `@Transactional`에 의해 롤백된다.
- **저장되는 것: 없음.** 배송의 택배사·운송장 번호·상태 변경은 롤백된다. 주문은 `PREPARING`에 머문다. 알림과 입찰 상태 변경은 모두 260행 뒤에 있으므로 실행되지 않는다.
- **응답: HTTP 404**, 본문 `ErrorResponse`, 코드 `S001`("배송 정보를 찾을 수 없습니다.") (`src/main/java/com/fream/back/domain/shipment/exception/ShipmentErrorCode.java:12`, `src/main/java/com/fream/back/global/exception/GlobalExceptionHandler.java:49-60`). 컨트롤러에는 try/catch가 없다 (`OrderShipmentCommandController.java:34-49`).
- 설령 260행을 통과해도 `:276` 호출에서 실패한다. `updateSaleStatusToSold`의 `:116`이 `saleBidQueryService.findByOrderId`를 호출하는데, 이 메서드는 `SaleBid`가 없으면 `IllegalArgumentException`을 던진다 (`src/main/java/com/fream/back/domain/sale/service/query/SaleBidQueryService.java:26-28`). `:116`은 try 블록(`:150`) 밖이라 그대로 전파된다. (a) 주문에는 `SaleBid`가 연결되지 않는다.

**(b) 즉시 구매 주문 — 역시 실패**

- 주문 생성: `createInstantOrder`가 `Order`를 `PENDING_PAYMENT`로 만든다 (`src/main/java/com/fream/back/domain/order/service/command/OrderCommandService.java:244`). 이후 결제 코드는 주문 상태를 바꾸지 않는다.
- 연결: `OrderBid`는 `MATCHED`에 즉시 구매 플래그가 붙는다 (`src/main/java/com/fream/back/domain/order/service/command/OrderBidCommandService.java:189-207`). `SaleBid`도 이 주문에 연결된다 (`OrderCommandService.java:279`).
- **실패 지점: 동일하게 `OrderShipmentCommandService.java:260`.** `PENDING_PAYMENT`는 `{PAYMENT_COMPLETED, COMPLETED, IN_WAREHOUSE}`만 허용하므로 `IN_TRANSIT`이 막힌다 (`OrderStatus.java:24`). 저장 없음, 404 `S001`.
- 따라서 (a)와 (b) 모두 운송장 등록으로는 `IN_TRANSIT`이 되지 않는다.

## 2. 배송 완료 감지

**2-1. 누가·언제·어떻게**

- 누가: 스케줄러가 Spring Batch 잡을 실행한다 (`src/main/java/com/fream/back/global/config/ShipmentBatchScheduler.java:34-44`).
- 언제: `@Scheduled(cron = "0 0 */6 * * *")`. 매 6시간 정각(0시·6시·12시·18시, 서버 시간대 기준)이다.
- 어떻게: 택배사 추적 페이지를 Playwright로 열고 `tbody#statusDetail tr`의 마지막 행 5번째 칸 텍스트를 읽는다 (`src/main/java/com/fream/back/domain/shipment/config/ShipmentItemProcessor.java:72-94`, `:181`). 페이지 타임아웃은 30초다 (`:30`).
- 대상 선정: `status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND trackingNumber IS NOT NULL`, 페이지 크기 50 (`src/main/java/com/fream/back/domain/shipment/config/UpdateShipmentStatusesJobConfig.java:87-97`). 정렬(ORDER BY)은 없다.

**2-2. 실제로 실행되는 처리 코드**

- 실행되는 것은 `ShipmentItemProcessor.process` (`src/main/java/com/fream/back/domain/shipment/config/ShipmentItemProcessor.java:57-157`)다. 스텝이 `UpdateShipmentStatusesJobConfig.java:69-73`에서 `new ShipmentItemProcessor(...)`를 직접 연결한다.
- 실행되지 않는 비슷한 코드:
  - `UpdateShipmentStatusesJobConfig.shipmentItemProcessor()` `@Bean` (`UpdateShipmentStatusesJobConfig.java:104-177`)은 스텝에 연결되지 않았다. 같은 파일의 `parseCjLogisticsStatus`(Jsoup, `:186-220`)도 호출되지 않는다.
  - `OrderShipmentCommandService.updateShipmentStatuses()` (`OrderShipmentCommandService.java:309-391`)는 호출하는 곳이 없다 (전체 검색 확인).
  - `CjTrackingPlaywright.getCurrentTrackingStatus`는 `check-status` 엔드포인트에서만 쓰인다.

**2-3. 택배사 상태 문자열 → 내부 상태**

매핑은 `ShipmentItemProcessor.java:220-226`에 있다.

- `"배송완료"` → `DELIVERED`
- `"배송출발"` → `OUT_FOR_DELIVERY`
- 그 밖의 모든 문자열 → `IN_TRANSIT`

정확히 일치하는 문자열만 인식한다. 현재 상태와 같으면 아무것도 하지 않는다 (`:101-105`). 주의할 점이 있다. `OUT_FOR_DELIVERY` 상태에서 조회값이 "배송완료"가 아니고 기타 문자열이면 `IN_TRANSIT`으로 바꾸려 하는데, `OUT_FOR_DELIVERY`에서 `IN_TRANSIT`으로는 전이할 수 없다 (`src/main/java/com/fream/back/domain/shipment/entity/ShipmentStatus.java:79-84`). 그러면 `OrderShipment.updateStatus`가 `IllegalStateException`을 던지고 (`OrderShipment.java:47-55`), 그 건은 스킵된다.

## 3. 배송 완료 판정 이후

**3-1. 엔티티 상태 변화 순서** (`ShipmentItemProcessor.java:108-117` → `OrderShipmentCommandService.java:191-229`)

1. `OrderShipment`: `IN_TRANSIT`(또는 `OUT_FOR_DELIVERY`) → `DELIVERED` (`ShipmentItemProcessor.java:113`, 허용은 `ShipmentStatus.java:72-78`).
2. `completeOrder(orderId)`:
   - `OrderBid` 조회, 없으면 예외 (`OrderShipmentCommandService.java:196-197`).
   - `Order` → `COMPLETED` (`:204`). 여기서 `Order.updateStatus` 검사가 걸린다.
   - `updateSaleStatusToSold` (`:208`).
   - 구매자 알림 1건 (`:211-217`).
3. 청크가 끝나면 `JpaItemWriter`가 커밋한다 (`UpdateShipmentStatusesJobConfig.java:239-246`).

**3-2. 알림**

- 구매자: 2건.
  - `"[completeOrder] 주문이 완료 처리되었습니다..."` (`OrderShipmentCommandService.java:212-217`). 메시지에 디버그성 접두어가 붙어 있다.
  - `"[배송 완료] 상품이 배송 완료되었습니다..."` (`ShipmentItemProcessor.java:117` → `src/main/java/com/fream/back/domain/notification/service/command/NotificationCommandService.java:219-234`).
- 판매자: 0건.
  - 판매자 알림은 `updateSaleStatusToSold` 안에서만 나오며, `Sale.updateStatus(SOLD)`가 성공할 때만 발생한다 (`OrderShipmentCommandService.java:119-141`, `:154-175`).
  - 이 프로젝트의 판매는 모두 `PENDING_SHIPMENT`로 생성된다 (`SaleCommandService.java:62`, `:108`). `SaleStatus`에서 `PENDING_SHIPMENT → IN_TRANSIT`, `IN_TRANSIT → IN_INSPECTION`만 허용되므로 `SOLD`로 갈 수 없다 (`src/main/java/com/fream/back/domain/sale/entity/SaleStatus.java:17-18`).

**3-3. 입찰 상태**

- `OrderBid`와 `SaleBid`는 배송 완료 경로에서 바뀌지 않는다. `MATCHED`로 남는다.
- `updateOrderAndSaleBidStatusToCompleted`(`OrderShipmentCommandService.java:413-440`)는 운송장 등록 메서드(`:289`)에서만 호출된다. 배송 완료 경로에는 호출이 없다.
- 참고: 그 메서드의 `@Transactional`은 private 메서드라 적용되지 않으며, 예외를 모두 삼킨다 (`:436-439`).

## 4. 주문 종류별 차이

| 항목 | (a) 실배송 일반 구매 입찰 | (b) 즉시 구매 |
|---|---|---|
| 등록 직전 주문 상태 | `PREPARING` (`OrderCommandService.java:175-176`) | `PENDING_PAYMENT` (`OrderCommandService.java:244`) |
| 운송장 등록 (`:260`) | 실패, 404 | 실패, 404 |

| 판매 상태 → SOLD | 해당 없음 (완료 전 실패) | 시도하지만 `PENDING_SHIPMENT`라 전이 안 됨 (`SaleStatus.java:17`) |
| 판매자 알림 | 0건 | 0건 |
| 구매자 알림 | 0건 | 2건 |
| 입찰 상태 | `MATCHED` 유지 | `MATCHED` 유지 |
| 배송 상태 | `IN_TRANSIT` 유지 (롤백) | `DELIVERED`로 커밋 |

(a) 상세: `ShipmentItemProcessor.java:116` → `completeOrder`의 `:204`에서 `Order.java:117`의 `InvalidOrderStatusException`. `OrderShipmentCommandService.java:221-227`이 `ShipmentException(ORDER_NOT_FOUND_FOR_SHIPMENT)`로 감싸고, `ShipmentItemProcessor.java:138-145`가 다시 던진다. 결과: 그 건 롤백, 스킵.

(b) 상세: `completeOrder`가 끝까지 진행된다. 판매 상태 블록 두 곳(`OrderShipmentCommandService.java:119`, `:156`)은 `canTransitionTo(SOLD)`가 거짓이라 아무것도 하지 않는다. 구매자 알림은 2건이다. 배송 상태는 `DELIVERED`로 커밋된다. 판매·입찰 상태는 정리되지 않은 채 남는다.

## 5. 실패 처리

- 한 건에서 예외가 나면 `ShipmentItemProcessor.java:133-145`가 `ShipmentException`으로 감싸 던지고, 스텝은 `.faultTolerant().skip(Exception.class).skipLimit(50)`로 설정돼 있다 (`UpdateShipmentStatusesJobConfig.java:75-77`). 스킵 리스너는 로그만 남긴다 (`:252-287`).
- **그 건**: 청크가 롤백되므로 DB에는 변경이 없다. `IN_TRANSIT`/`OUT_FOR_DELIVERY`로 남아 다음 주기(6시간 후)에 다시 시도된다. 결정적으로 실패하는 건(예: (a))은 매 주기 같은 실패를 반복한다.
- **나머지 건**: Spring Batch의 fault-tolerant 동작으로 실패한 청크는 한 건씩 다시 처리되며, 정상 건은 각자 커밋된다. (코드 읽기로 판단했으며 실행으로 검증하지는 않았다.)
- **스킵 한도**: `skipLimit(50)`은 스텝 실행 한 번당 한도다. 초과하면 스텝이 실패하고 그 실행의 남은 건은 처리되지 않는다. 정렬이 없어 어떤 건이 먼저 처리될지 보장되지 않는다.
- **의심 지점 (코드만으로 판단, 미검증)**: 롤백 후 재처리될 때 같은 청크의 앞선 건은 메모리 객체에 이미 바뀐 상태(`DELIVERED`, 주문 `COMPLETED`)가 남아 있을 수 있다. 그러면 `ShipmentItemProcessor.java:101`의 중복 방지 검사에서 바로 빠져나와 배송 상태만 `DELIVERED`로 저장되고, 주문 완료와 구매자 알림은 빠질 수 있다. 실행으로 확인하지 않았다.

## 부가 발견: 주석·이름과 실제 동작이 다른 곳

- `OrderCommandService.java:188`: 결제·배송 처리 후 `orderBidQueryService.findById(orderId)`로 `OrderBid`를 찾는다. 인자는 주문 ID인데 `OrderBid`의 PK로 조회한다. 엉뚱한 입찰을 `MATCHED`로 바꿀 수 있다.
- `OrderShipmentCommandService.java:112` `updateSaleStatusToSold` 주석은 판매를 `SOLD`로 바꾼다고 하지만, 이 프로젝트의 판매는 `PENDING_SHIPMENT`/`IN_TRANSIT`에서 `SOLD`로 갈 수 없어 실제로는 아무 일도 하지 않는다.
- `OrderShipmentCommandService.java:239` `updateTrackingInfo` 주석은 "관련 상태를 변경"한다고 하지만, 위 이유로 항상 실패한다.
- `OrderShipmentCommandService.java:221-227`: `completeOrder`가 모든 예외를 `ORDER_NOT_FOUND_FOR_SHIPMENT`로 감싼다. 실제 원인은 상태 전이 실패인데 "주문 없음"으로 보인다.
- `OrderShipment.updateTrackingInfo`(`OrderShipment.java:41-45`)는 `PENDING`에서 `IN_TRANSIT`으로 전이 검사 없이 점프한다. `ShipmentStatus`의 규칙과 맞지 않는다.
- 운송장 등록 시 입찰을 `COMPLETED`로 바꾸는 것(`:289`)은 배송 전에 완료 처리되므로 의도와 맞지 않는다. 배송 완료 경로는 입찰을 바꾸지 않는다.

## 확인하지 못한 점

- Spring Boot의 `spring.batch.job.enabled`는 설정 파일에서 찾지 못했다. 기본값(활성)이라면 앱 시작 시 잡이 한 번 실행될 수 있다.
- JPQL의 `'IN_TRANSIT'` 문자열 리터럴과 enum 필드 비교가 현재 Hibernate 버전에서 허용되는지는 실행하지 않아 확인하지 못했다.
- 택배사 페이지의 실제 상태 문자열(`"배송완료"` 등)은 코드의 가정만 확인했다.
