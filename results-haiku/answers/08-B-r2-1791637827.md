# 구매자 배송: 운송장 등록부터 배송 완료까지

> 방법: 정적 코드 읽기만 수행했다. 실행·테스트는 하지 않았고, CJ대한통운 실제 응답도 확인하지 않았다. 경로는 저장소 루트 기준이며, `src/main/java/com/fream/back/`은 `B/`로 줄여 쓴다. 예: `B/domain/shipment/...`는 `src/main/java/com/fream/back/domain/shipment/...`이다.

## 1. 운송장 등록 요청

**API**: `PATCH /shipments/order/{shipmentId}/status`, 본문 `{courier, trackingNumber}`. `shipmentId`는 `OrderShipment`의 ID이다 (주문 ID가 아님).
- `B/domain/shipment/controller/command/OrderShipmentCommandController.java:20` (기본 경로), `:33-47` (핸들러, 서비스 호출)
- DTO: `B/domain/shipment/dto/OrderShipmentRequestDto.java` (검증 애노테이션 없음, 빈 값 검사는 서비스에서 수행)
- 서비스: `B/domain/shipment/service/command/OrderShipmentCommandService.java:238-303` (`@Transactional`)

**의도된 흐름 (코드 순서)**

| 순서 | 처리 | 근거 |
|---|---|---|
| 1 | 택배사·운송장 빈 값 검사 → `TRACKING_INFO_REQUIRED` | `OrderShipmentCommandService.java:243-246` |
| 2 | `OrderShipment` 조회 (없으면 `SHIPMENT_NOT_FOUND`) | `OrderShipmentCommandService.java:249-253` |
| 3 | `OrderShipment`: courier, trackingNumber 설정, status `PENDING → IN_TRANSIT` (전이 규칙 우회) | `B/domain/shipment/entity/OrderShipment.java:188-192` |
| 4 | `Order`: `PREPARING → IN_TRANSIT` | `OrderShipmentCommandService.java:259-260` |
| 5 | 구매자 알림 1건: "상품이 출발하였습니다" | `OrderShipmentCommandService.java:265-273` |
| 6 | `updateSaleStatusToSold(orderId)`: Sale → `SOLD` (전이 가능할 때만), 판매자 알림 (전이가 일어난 경우에만) | `OrderShipmentCommandService.java:276`, `:111-139` |
| 7 | 창고 보관 상품이면 창고 상태 `SOLD` | `OrderShipmentCommandService.java:279-286` |
| 8 | `OrderBid`·`SaleBid`: `MATCHED → COMPLETED` (예외는 로그만 남김) | `OrderShipmentCommandService.java:289`, `:413-440` |

설계상 알림은 구매자 1건, 판매자 0~1건이다. 판매자 알림은 Sale이 `SOLD`로 바뀔 때만 나간다.

**실제 실행: 실배송 일반 구매 입찰 주문(a)은 끝까지 성공하지 않는다.**

실패 지점은 4단계(`:260`)이다.
- 결제·배송 처리 후 Order 상태는 `PREPARING`이다. 근거: Kafka 소비자가 `PAYMENT_COMPLETED`를 거쳐 `PREPARING`으로 바꾼다 (`B/domain/order/service/kafka/OrderEventConsumer.java:192-195`, `:216-218`).
- `PREPARING`에서 허용되는 다음 상태는 `IN_WAREHOUSE`, `SHIPMENT_STARTED`뿐이다 (`B/domain/order/entity/OrderStatus.java:26`).
- `IN_TRANSIT`으로 가는 전이는 `SHIPMENT_STARTED → IN_TRANSIT`뿐이다 (`OrderStatus.java:28`). 그런데 `SHIPMENT_STARTED`를 설정하는 코드가 없다 (저장소 전체 검색 결과). 따라서 정상 흐름으로는 `IN_TRANSIT`에 도달할 수 없다.
- `Order.updateStatus`가 `InvalidOrderStatusException("상태 전환이 허용되지 않습니다: PREPARING -> IN_TRANSIT")`을 던진다 (`B/domain/order/entity/Order.java:113-121`).
- `:295-301`의 catch가 이를 `ShipmentException(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: ...")`로 감싸 다시 던진다.

**저장되는 것**: 이 요청으로 저장되는 것은 없다. `ShipmentException`은 `RuntimeException`이므로 `@Transactional`이 롤백한다 (`B/global/exception/GlobalException.java:10`). 운송장 번호, 택배사, `IN_TRANSIT`, 주문 상태, 알림이 모두 버려진다. 이전 단계에서 저장된 상태는 그대로 남는다: Order `PREPARING`, OrderShipment `PENDING`(택배사·운송장 없음), 결제 시점에 생긴 알림과 Sale 상태.

**응답**: HTTP 404, 본문 `ErrorResponse`(code `S001`, 메시지 "배송 정보를 찾을 수 없습니다.", status 404, path)
- `B/global/exception/GlobalExceptionHandler.java:459-471`
- `B/domain/shipment/exception/ShipmentErrorCode.java:12` (`SHIPMENT_NOT_FOUND`, 404)
- 응답 메시지는 실제 원인을 담지 않는다. 원인은 서버 로그에만 남는다.

**숨은 두 번째 실패 지점 (일반 입찰 주문, SaleBid 없음)**: 4단계를 통과하더라도 6단계에서 실패한다.
- `updateSaleStatusToSold`의 `:116`에서 `saleBidQueryService.findByOrderId(orderId)`를 호출한다. 이 메서드는 없으면 `null`이 아니라 `IllegalArgumentException`을 던진다 (`B/domain/sale/service/query/SaleBidQueryService.java:26-29`).
- 이 호출은 `:150`의 try 블록 바깥에 있으므로 잡히지 않고 등록 전체가 롤백된다.
- 결과적으로 `:150-180`의 OrderBid 분기는 SaleBid가 없는 일반 입찰 주문에서는 도달할 수 없다. 같은 문제가 `:279`에도 있다.
- SaleBid가 생기는 경우는 판매자 즉시 판매뿐이다 (`B/domain/sale/service/command/SaleBidCommandService.java:72-87`). 이 경우에는 `:116`을 통과하지만 4단계에서 여전히 막힌다.

**(b) 즉시 구매 주문도 같은 지점(`:260`)에서 실패한다.**
- 즉시 구매 주문은 `PENDING_PAYMENT`로 생성되고 (`B/domain/order/service/command/OrderCommandService.java:244`), 결제 후에도 Order 상태가 바뀌지 않는다. 결제 모듈에는 Order 상태를 바꾸는 코드가 없다.
- `PENDING_PAYMENT`에서 허용되는 전이는 `PAYMENT_COMPLETED`, `COMPLETED`, `IN_WAREHOUSE`뿐이다 (`OrderStatus.java:24`). `IN_TRANSIT`은 없다.
- 실패 메시지는 `PENDING_PAYMENT -> IN_TRANSIT`이다. 저장·응답은 (a)와 같다.

## 2. 배송 완료 감지

**누가·언제·어떻게**: 사람이 아니라 시스템이 6시간마다 배치로 감지한다.
- 실행: `B/global/config/ShipmentBatchScheduler.java:34-40`, `@Scheduled(cron = "0 0 */6 * * *")`. 매일 00·06·12·18시 정각이다 (서버 시간대 기준).
- 실행 대상 Job: `updateShipmentStatusesJob` (`B/domain/shipment/config/UpdateShipmentStatusesJobConfig.java:54-60`). chunk 크기 50, skip 한도 50 (`:51-52`, `:75-77`).

**대상 배송**: `OrderShipment` 중 `status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND trackingNumber IS NOT NULL`
- `UpdateShipmentStatusesJobConfig.java:87-97` (리더, JPQL은 `:95`)
- 주의: 정렬(`ORDER BY`)이 없다 (5번 참고).

**실제로 실행되는 처리 코드**: `ShipmentItemProcessor.process()` (`B/domain/shipment/config/ShipmentItemProcessor.java:57-157`)
- 실제 step은 `new ShipmentItemProcessor(...)`를 직접 생성해 쓴다 (`UpdateShipmentStatusesJobConfig.java:69-73`).
- 헤드리스 Playwright 페이지로 `https://trace.cjlogistics.com/next/tracking.html?wblNo={운송장}`을 열고, `tbody#statusDetail tr`이 나타날 때까지 기다린다 (`ShipmentItemProcessor.java:81-87`, 타임아웃 30초).
- 마지막 행의 5번째 `td` 텍스트를 상태로 쓴다 (`:181`). 텍스트가 비면 `TRACKING_HTML_PARSE_ERROR`로 실패한다 (`:183-189`).
- 브라우저는 step 시작 시 열고 끝날 때 닫는다 (`B/domain/shipment/config/BrowserManageStepListener.java:15-25`).

**실행되지 않는 비슷한 코드 (무시할 것)**
- `UpdateShipmentStatusesJobConfig.java:104-177`의 `shipmentItemProcessor()` @Bean: step에 연결되지 않는다.
- `UpdateShipmentStatusesJobConfig.java:186-220`의 `parseCjLogisticsStatus()`(Jsoup): 호출되지 않는다.
- `B/domain/shipment/service/command/OrderShipmentCommandService.java:309-391`의 `updateShipmentStatuses()`: 호출하는 곳이 없다 (`grep` 결과).

**택배사 상태 → 내부 상태 매핑** (`ShipmentItemProcessor.java:220-226`, 같은 매핑이 `OrderShipmentCommandService.java:399-405`에도 있다)

| CJ 상태 텍스트 (정확 일치, trim 후) | 내부 상태 |
|---|---|
| `배송완료` | `DELIVERED` |
| `배송출발` | `OUT_FOR_DELIVERY` |
| 그 밖의 모든 값 | `IN_TRANSIT` |

- 띄어쓰기나 표기가 다르면 (예: `배송 완료`) 완료로 인식되지 않고 `IN_TRANSIT`으로 남는다.

**보조 경로 (수동 조회)**: `POST /shipments/order/{id}/check-status` (`OrderShipmentCommandController.java:58-98`) → `updateAndCheckShipmentStatus` (`OrderShipmentCommandService.java:451-516`)
- 이 경로는 운송장을 덮어쓰고 `IN_TRANSIT`으로 저장한 뒤 CJ를 조회한다 (`:473`, `:477`).
- 배송완료면 `completeOrder`를 호출한다 (`:486-489`). 그 밖의 경우에는 **Order 상태를 바꾸지 않는다** (`:497`).
- 따라서 Order가 `PREPARING`인 주문에 이 경로를 쓰면 `IN_TRANSIT` 배송과 `PREPARING` 주문이 공존하는 불일치 상태가 생긴다. 이후 배치가 이 배송을 집어서 완료 처리 때마다 실패한다.

## 3. 배송 완료 판정 이후

판정 이후 처리는 `ShipmentItemProcessor.java:108-117`과 `OrderShipmentCommandService.completeOrder` (`:191-229`)에서 이뤄진다. 아래 흐름은 배송이 `IN_TRANSIT`이라고 가정한 코드 흐름이다. 정상 등록 경로로는 이 상태에 도달할 수 없다 (1번 참고).

**엔티티 상태 변화 순서**
1. `OrderShipment`: `IN_TRANSIT`(또는 `OUT_FOR_DELIVERY`) → `DELIVERED` (`ShipmentItemProcessor.java:113`). `OUT_FOR_DELIVERY`에서 `DELIVERED`로 가는 전이는 허용된다 (`B/domain/shipment/entity/ShipmentStatus.java:277-282`).
2. `Order`: `IN_TRANSIT` → `COMPLETED` (`OrderShipmentCommandService.java:204`). `COMPLETED`는 `IN_TRANSIT`, `PENDING_PAYMENT`, `IN_WAREHOUSE`에서 허용된다. `PREPARING`에서는 허용되지 않는다 (`OrderStatus.java:24-29`).
3. `Sale`: `updateSaleStatusToSold`가 호출되지만 이미 `SOLD`면 변화가 없다 (`OrderShipmentCommandService.java:208`, `:119`).
4. `OrderShipment`는 Writer (`JpaItemWriter`)가 저장한다 (`UpdateShipmentStatusesJobConfig.java:241-246`).

**알림**
- 구매자 2건: `completeOrder`의 "[completeOrder] 주문이 완료 처리되었습니다" (`OrderShipmentCommandService.java:212-217`), 그리고 프로세서의 `notifyShipmentCompleted` "[배송 완료] ..." (`ShipmentItemProcessor.java:117` → `B/domain/notification/service/command/NotificationCommandService.java:219-234`). 같은 사건에 두 번 알리는 중복이다.
- 판매자: Sale이 아직 `SOLD`가 아니면 1건, 이미 `SOLD`면 0건 (`OrderShipmentCommandService.java:131-138`). 정상 흐름에서는 등록 시점에 이미 `SOLD`가 되므로 보통 0건이다.

**주문 입찰·판매 입찰**
- 이 경로에서는 바뀌지 않는다. `OrderBid`·`SaleBid`는 `MATCHED`로 남는다.
- `COMPLETED`로 바꾸는 코드(`updateOrderAndSaleBidStatusToCompleted`, `:413-440`)는 등록 메서드(`:289`)에서만 호출된다. 배송 완료 경로에서는 호출되지 않는다.
- `:413-440`은 `private`에 `@Transactional`이 붙어 있어 프록시가 적용되지 않는다. 그리고 내부 예외는 잡아서 로그만 남긴다 (`:436-439`).

## 4. 주문 종류별 차이

| 항목 | (a) 실배송 일반 구매 입찰 | (b) 즉시 구매 |
|---|---|---|
| 생성 | `createOrderBid` → Order `PENDING_PAYMENT`, OrderBid `PENDING` (`OrderBidCommandService.java:47-63`, `:95`) | `createInstantOrder` → Order `PENDING_PAYMENT`, SaleBid·OrderBid `MATCHED` (`OrderCommandService.java:220-319`, `:279-280`, `OrderBidCommandService.java:189-200`) |
| 결제 시 Sale | Sale이 OrderBid에 매칭되어 있을 때만 결제 시 `SOLD` + 알림 (`PaymentCommandService.java:409-419`, 매칭은 `SaleCommandService.java:79-80`) | SaleBid 분기로 결제 시 `SOLD` + 알림 (`PaymentCommandService.java:391-404`) |
| 결제 후 Order 상태 | `PREPARING` (Kafka 소비자, `OrderEventConsumer.java:216-218`) | `PENDING_PAYMENT` 그대로 |
| 운송장 등록 (1번) | **실패**: `PREPARING → IN_TRANSIT` 불가 (`:260`). SaleBid 없으면 `:116`에서도 실패 | **실패**: `PENDING_PAYMENT → IN_TRANSIT` 불가 (`:260`) |
| 배송 완료 처리 (3번) | 배치 대상이 아님 (`trackingNumber`가 없음). 도달하더라도 `PREPARING → COMPLETED` 불가로 실패 | `check-status` 우회 시 Order `COMPLETED`까지 성공. SaleBid 분기는 Sale이 이미 `SOLD`라 스킵되고, 구매자 알림 2건 |
| 입찰 상태 | `OrderBid` `PENDING` 그대로 (Kafka 경로는 `MATCHED`로 바꾸지 않음), `COMPLETED` 불가 | `OrderBid`·`SaleBid` `MATCHED` 그대로 (`COMPLETED`로 안 바뀜) |

결론
- (a)는 등록 단계에서 막힌다. 막힌 뒤에는 어떤 처리도 일어나지 않는다.
- (b)는 등록 단계에서 같은 방식으로 막힌다. 다만 등록 우회 경로(`check-status`)로 배송 완료까지 가면 Order 완료 처리는 성공한다. 그래도 입찰 상태는 `COMPLETED`로 바뀌지 않는다.

## 5. 실패 처리 (주기 처리 중 한 건 실패)

- Step은 `faultTolerant().skip(Exception.class).skipLimit(50)`이다 (`UpdateShipmentStatusesJobConfig.java:75-77`).
- **실패한 건**: 같은 chunk 트랜잭션 안에서 롤백된다. 그 건의 `OrderShipment` 상태, `completeOrder`의 Order 변경, 알림 DB 저장이 모두 취소된다. 배송 상태는 이전 값(`IN_TRANSIT`/`OUT_FOR_DELIVERY`)으로 남아, 다음 6시간 주기에 다시 시도된다. 스킵 로그는 `SkipListener.onSkipInProcess`가 남긴다 (`UpdateShipmentStatusesJobConfig.java:252-266`).
- **나머지 건**: 청크가 롤백된 뒤 정상 건은 개별 처리되어 커밋된다 (Spring Batch fault-tolerant 동작). 실패 건만 스킵된다.
- **롤백되지 않는 것**: `createNotification`은 저장 후 실시간 전송을 바로 호출한다 (`NotificationCommandService.java:52-57`). 청크가 롤백돼도 이미 나간 실시간 알림은 취소되지 않는다. 이것은 코드 읽기에서 확인한 것이다.
- **skip 한도 초과**: 한 step 실행에서 스킵이 50건을 넘으면 step이 FAILED로 끝나고, 남은 건은 이번 실행에서 처리되지 않는다. `ShipmentBatchScheduler`는 `jobLauncher.run` 예외만 잡는다 (`ShipmentBatchScheduler.java:41-43`). FAILED 상태는 예외로 올라오지 않으므로 알림 없이 로그만 남는다.

## 추가로 확인된 문제

1. **OUT_FOR_DELIVERY → IN_TRANSIT 실패가 매 주기 반복됨.** `OUT_FOR_DELIVERY`에서 허용되는 전이는 `DELIVERED`, `FAILED_DELIVERY`, `CANCELED`뿐이다 (`ShipmentStatus.java:277-282`). CJ 상태가 `배송출발`에서 다른 텍스트(예: 지점 도착 등)로 바뀌면 매핑이 `IN_TRANSIT`이 되고, `OrderShipment.updateStatus`가 `IllegalStateException`을 던진다 (`B/domain/shipment/entity/OrderShipment.java:194-202`, `ShipmentItemProcessor.java:123-126`). 그 건은 매 주기 스킵되고 skip 한도를 소진한다.
2. **페이지 읽기 중 상태가 바뀜 (코드상 추정, 실행 검증 안 함).** `JpaPagingItemReader`는 offset 기반이고 `ORDER BY`가 없다. Writer가 `IN_TRANSIT`을 `DELIVERED`로 바꾸면 WHERE 결과가 줄어들어 다음 페이지의 offset이 밀린다. 그 결과 일부 건이 이번 주기에 읽히지 않을 수 있다. 다음 주기에 다시 읽히므로 영구 유실은 아니지만 지연된다.
3. **`check-status` 우회로 생기는 불일치** (2번 참고): 운송장은 `IN_TRANSIT`인데 Order는 `PREPARING`인 상태가 만들어진다. 그 뒤 배치가 이 건을 계속 집어서 완료 시 실패한다.
4. **죽은 코드**: `shipmentItemProcessor()` @Bean, `parseCjLogisticsStatus()`, `OrderShipmentCommandService.updateShipmentStatuses()`는 호출되지 않는다. 같은 이름의 로직이 여러 곳에 있어 헷갈린다. 실제 실행은 `ShipmentItemProcessor`다.
5. **메시지와 실제 동작이 다름**: 등록 실패 응답 코드가 `SHIPMENT_NOT_FOUND`인데 실제 원인은 주문 상태 전이 실패다. `updateSaleStatusToSold`의 OrderBid 분기 주석("OrderBid가 없는 경우 예외로 중단하지 않고 진행")도 실제로는 SaleBid 조회 `IllegalArgumentException`이 먼저 나서 그 분기에 도달하지 못한다 (`OrderShipmentCommandService.java:179`, `:116`).
