# 즉시 구매는 어떻게 처리되나

요약: 즉시 구매는 HTTP 요청 안에서 동기로 끝까지 처리된다. 주문, 배송, 판매 입찰, 결제, 판매 상태, 알림 생성, 주문 입찰 생성이 한 DB 트랜잭션에 묶여 있다. 카드 결제는 같은 트랜잭션 안에서 PG를 호출한다. 응답 ID는 Order가 아니라 **OrderBid**의 ID다. 결제 수단과 무관하게 Order는 끝까지 `PENDING_PAYMENT`로 남는다. 아래 번호는 질문 번호와 같다.

경로 약칭: `P` = `src/main/java/com/fream/back/domain/`, `G` = `src/main/java/com/fream/back/global/`

---

## 1. 요청 진입점, 처리 단계, 동기/비동기, 응답 ID

- 진입점: `POST /order-bids/instant`. 클래스 base path는 `/order-bids` (`P/order/controller/command/OrderBidCommandController.java:22`, 메서드 매핑 `:89-90`).
- 요청 DTO: `saleBidId`, `addressId`, `warehouseStorage`, `paymentRequest`. `paymentRequest`에는 `@Valid`가 없어 결제 DTO의 제약(`paidAmount` `@Min(100)`, `paymentType` `@NotBlank`)은 검사되지 않는다 (`P/order/dto/InstantOrderRequestDto.java:20-29`, `P/payment/dto/PaymentRequestDto.java:36-52`).
- 컨트롤러 처리: 이메일은 SecurityContext에서 꺼내고 (`OrderBidCommandController.java:92`), `enrichPaymentRequest`가 `userEmail`을 채우고 `orderId`를 null로 둔다 (`:98`, `:119-122`). 그 다음 서비스를 호출한다 (`:101-107`).
- 서비스 `OrderBidCommandService.createInstantOrderBid` (`P/order/service/command/OrderBidCommandService.java:118-149`) 순서:
  1. 입력 검증 (`:123`, `:154-167`)
  2. 구매자 조회 (`:126`)
  3. 판매 입찰 조회와 검증 (`:129`, `:172-184`)
  4. `OrderCommandService.createInstantOrder` 호출 (`:133-139`). Order, 주소, 배송, 판매 입찰 매칭, 창고 상태, 결제가 여기서 일어난다.
  5. `OrderBid` 생성 및 저장 (`:142`, `:189-207`)
- 동기/비동기: **동기**다. 컨트롤러가 서비스를 직접 호출하고 결과를 기다려 응답한다. 이 경로에는 Kafka 발행이 없다. Kafka를 쓰는 `/orders` 명령 컨트롤러 (`P/order/controller/command/OrderCommandController.java:23-24`)는 이 경로를 타지 않는다. PG 호출도 동기 HTTP이며 DB 트랜잭션 안에서 실행된다 (`P/payment/portone/PortOneApiClient.java:266`).
- 응답 ID: 응답의 `orderId` 변수에 담기는 값은 `createInstantOrderBid(...).getId()`, 즉 **OrderBid의 ID**다 (`OrderBidCommandController.java:101-107`, 응답 `:109`). Order ID가 아니다. 응답 메시지는 결제가 `PENDING`이어도 "즉시 구매가 성공적으로 처리되었습니다."이다.

## 2. 생성되는 엔티티와 상태 변화 순서

모두 `OrderCommandService.createInstantOrder` (`P/order/service/command/OrderCommandService.java:220-319`)와 `OrderBidCommandService.createInstantOrderBid` 안에서 하나의 트랜잭션으로 실행된다. 두 메서드 모두 `@Transactional`이고, 예외는 `GlobalException`(RuntimeException) 계열이라 롤백된다 (`G/exception/GlobalException.java:10`).

| 순서 | 대상 | 동작 | 직후 상태 | 근거 |
|---|---|---|---|---|
| a | `Order` (신규) | 생성, 저장. `totalAmount` = `saleBid.bidPrice` | `status = PENDING_PAYMENT` | `OrderCommandService.java:241-247`; 결제 요청에 orderId 설정 `:250` |
| b | `OrderItem` (신규) | 수량 1, 가격 = bidPrice, 저장 | 해당 없음 | `:255-256`; `P/order/service/command/OrderItemCommandService.java:45-51` |
| c | `OrderShipment` (신규) | 주소 정보 복사, 저장 | `status = PENDING` | `OrderCommandService.java:264-271`; `P/shipment/service/command/OrderShipmentCommandService.java:61-70` |
| d | `SaleBid` (기존) | `order` 연결, `status = MATCHED`, `flush` | `MATCHED` | `OrderCommandService.java:279-283`; `P/sale/entity/SaleBid.java:58-61` |
| e | `WarehouseStorage` (기존, 조건부) | `sale.isWarehouseStorage()`가 true일 때만 상태 변경 | `ASSOCIATED_WITH_ORDER` | `OrderCommandService.java:292-294`; `P/warehouseStorage/service/command/WarehouseStorageCommandService.java:117-133` |
| f | `Payment` (신규) | 결제 수단별 생성, 저장 (3번 참고) | 카드 `PENDING` 또는 `PAID`, 계좌 `PENDING`, 일반 `PAID` | `P/payment/service/command/PaymentCommandService.java:57-80`, `:187-208`, `:250-262`, `:302-316` |
| g | `Sale` (기존) | 결제 처리 후 `SOLD`로 설정 | `SOLD` | `PaymentCommandService.java:383-420` (`:404`, `:419`) |
| h | `Notification` (신규) | 구매자, 판매자 각 1건 저장 | 알림 `isRead=false` | 4번 참고 |
| i | `OrderBid` (신규) | `status = MATCHED`, `sale` 연결, `order` 연결, `isInstantPurchase = true`, 저장 | `MATCHED`, `isInstantPurchase = true` | `OrderBidCommandService.java:189-207` (`:196`, `:205-206`); `P/order/entity/OrderBid.java:45-52` |

- 단계 f와 g 사이에 `Order.payment` 필드는 설정되지 않는다. `processPayment`의 반환값을 버리고 있다 (`OrderCommandService.java:305`). Payment 행에는 `order_id`가 저장된다 (`PaymentCommandService.java:200`, `P/payment/entity/Payment.java:47-50`).
- `OrderBid`는 결제 처리 뒤에 만들어진다. 그래서 `PaymentCommandService`의 알림/판매 상태 처리 시점에는 `order.getOrderBid()`가 null이고, 판매 입찰을 `findByOrderId`로 찾는 대체 경로를 탄다 (`PaymentCommandService.java:387-395`).

**최종 상태 (성공 경로 기준)**
- `Order.status` = **`PENDING_PAYMENT`** (변경되지 않는다, 5번 참고)
- `SaleBid.status` = `MATCHED`
- `OrderBid.status` = `MATCHED`, `isInstantPurchase` = true
- `Sale.status` = `SOLD`
- `Payment.status`: 카드 `PENDING`(조건부, 3번), 계좌 `PENDING`, 일반 `PAID`

## 3. 결제 수단별 결과, 최종 성공 여부, 카드 실패 응답

**공통**
- 결제 금액은 클라이언트가 보낸 `paidAmount`를 그대로 쓴다. 검증은 `> 0`뿐이고 판매 입찰 가격과 비교하지 않는다 (`PaymentCommandService.java:141-145`). 카드 결제는 이 금액을 PG에 그대로 요청한다 (`:179`, `P/payment/portone/PortOneApiClient.java:250`).
- `Payment`의 생성자는 `setPaidAmount`를 호출하고, 이 메서드는 `isSuccess = paidAmount > 0`으로 설정한다. 그래서 `CardPayment`, `AccountPayment`, `GeneralPayment`는 `status`가 `PENDING`이어도 `isSuccess`가 true가 된다 (`P/payment/entity/Payment.java:60-63`, `P/payment/entity/CardPayment.java:139`, `P/payment/entity/AccountPayment.java:28`, `P/payment/entity/GeneralPayment.java:30`).

**카드 (CARD)**
- 결제 정보 엔티티를 조회한 뒤 PortOne `processCardPayment`를 호출한다 (`PaymentCommandService.java:163-184`, `P/payment/portone/PortOneApiClient.java:229`).
- 성공 판단: `"success".equals(response.get("status"))`일 때만 `PAID`로 바꾼다 (`PaymentCommandService.java:203-206`). 그 외에는 `PENDING`으로 저장되고 예외 없이 진행된다 (`:208`).
- 이 `"success"` 문자열은 저장소 전체에서 이 한 곳에만 나온다 (grep 결과). PortOne의 실제 status 값은 외부 API 스펙 기준으로 `paid`, `ready`, `failed`, `cancelled`로 알고 있으나, 저장소에서는 확인할 수 없다. 그렇다면 실제 성공 응답도 `PENDING`으로 저장된다.
- **카드 실패 응답 (PG가 실패를 반환)**
  - `processCardPayment`는 HTTP가 200이 아니거나 `code != 0`이면 `PaymentProcessingException`을 던진다 (`PortOneApiClient.java:270-275`).
  - `@Retryable`은 `PaymentApiException`만 재시도한다 (`:224-228`). 이 예외는 재시도 대상이 아니다. 저장소에는 `@EnableRetry`도 없어서 `@Retryable`은 동작하지 않는다 (grep 결과).
  - 예외는 `createCardPayment`, `processPayment`를 거쳐 그대로 전파된다 (`PaymentCommandService.java:180-181`, `:218-219`, `:89-94`).
  - `createInstantOrder`가 `OrderPaymentProcessingFailedException`으로 감싸고 (`OrderCommandService.java:304-309`), `OrderException`이면 그대로 다시 던진다 (`:312-315`). `createInstantOrderBid`도 그대로 전파한다 (`OrderBidCommandService.java:145-147`, `:212-215`).
  - 컨트롤러 예외 처리는 `OrderException`의 `ErrorCode` 상태 코드로 응답한다 (`G/exception/GlobalExceptionHandler.java:325-332`).
  - **결과**: 같은 트랜잭션의 모든 쓰기가 롤백된다. Order, OrderItem, OrderShipment, SaleBid의 `MATCHED`, 창고 상태 변경이 모두 되돌아간다. Payment 행, 알림, `Sale.SOLD`도 생기지 않는다.
- **카드 실패의 예외 경로 두 가지**
  - (a) PG 네트워크 오류 (`RestClientException`): `PaymentApiException`으로 바뀐다 (`PortOneApiClient.java:288-290`). 위와 같이 롤백된다. 재시도는 되지 않는다.
  - (b) PG가 `code == 0`으로 응답하고 `status`가 `"success"`가 아닌 경우: **예외가 없다.** `CardPayment`가 `PENDING`으로 저장되고 즉시 구매는 성공으로 끝난다. 구매자에게 "결제가 완료되었습니다" 알림이 가고, `Sale`은 `SOLD`, `OrderBid`는 `MATCHED`가 된다 (`PaymentCommandService.java:203-208`, `:416-420`).
- **보상 처리 없음**: PG 승인은 DB 트랜잭션 안에서 일어난다. PG 승인 뒤에 DB 쓰기가 실패하면 트랜잭션은 롤백되지만 카드 승인은 취소되지 않는다. 예를 들어 `paymentRepository.save`나 `OrderBid` 저장(`OrderBidCommandService.java:206`)이 실패하는 경우다. 환불 메서드 `handleRefundIfNecessary`는 `private`이고 호출되는 곳이 없다 (`PaymentCommandService.java:341`).

**계좌이체 (ACCOUNT)**
- 은행명 검증만 한다 (`PaymentCommandService.java:242-248`). 입금 확인이나 PG 호출은 없다.
- `AccountPayment`를 `PENDING`으로 저장한다 (`:250-262`).
- 예외 없이 끝나므로 즉시 구매는 성공으로 응답한다. 입금 전인데도 `Sale`은 `SOLD`, 알림은 "결제가 완료되었습니다"로 간다 (`:83`, `:404`, `:419`).

**일반 결제 (GENERAL)**
- `impUid`가 비어 있지 않은지만 확인한다 (`PaymentCommandService.java:296-300`). PortOne 조회나 금액 검증은 하지 않는다. 클라이언트가 보낸 값을 그대로 믿는다.
- `GeneralPayment`를 `PAID`, `isSuccess = true`로 저장한다 (`:302-316`).
- 예외 없이 끝나므로 즉시 구매는 성공으로 응답한다.

**즉시 구매가 "끝까지 성공"하는가**
- 세 경로 모두 예외 없이 진행되면 HTTP 200과 OrderBid ID를 반환한다. 세 경우 모두 `Order`는 `PENDING_PAYMENT`로 남는다.
- 카드가 **명시적 실패**로 응답하면 전체가 롤백되고 오류를 반환한다.
- 카드가 `code == 0`인데 `status != "success"`이면 오류 없이 성공처럼 끝난다. 결제는 `PENDING`이다.

**컨트롤러 검증 누락**: `paymentRequest`에 `@Valid`가 없어 결제 DTO의 `@Min(100)`과 `@NotBlank`가 적용되지 않는다 (`InstantOrderRequestDto.java:28-29`).

## 4. 알림 수신자, 시점, 방식

- 수신자와 내용 (`P/payment/service/command/PaymentCommandService.java:434-456`):
  - 구매자: `SHOPPING` / `BID` 카테고리, "결제가 완료되었습니다. 주문 ID: {orderId}" (`:438-443`).
  - 판매자: 같은 카테고리와 타입, "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}" (`:449-454`).
- 시점: `processPayment` 안에서 동기로 보낸다 (`:83`, `:383-420`). 결제 수단과 무관하게, `PENDING` 카드나 계좌이체에도 보낸다. 메시지는 그래도 "완료"라고 말한다. 주문 입찰 저장과 커밋 전에 보내므로, 이후 단계가 실패하면 실시간 푸시는 이미 나갔는데 DB 알림 행은 롤백되는 상황이 생긴다.
- 방식:
  - `NotificationCommandService.createNotification`이 `Notification` 행을 저장한다 (`P/notification/service/command/NotificationCommandService.java:44-59`).
  - 실시간 전송은 Redis에 해당 사용자의 연결 키가 있을 때만 `convertAndSendToUser`로 WebSocket에 보낸다 (`:303-317`).
  - 비동기 처리(`@Async`)는 저장소에 없다 (grep 결과).
  - 알림 실패는 로그만 남기고 삼킨다 (`PaymentCommandService.java:457-461`). 알림 실패가 주문을 실패시키지 않는다.
- 주문이 실패하면 누구도 알림을 받지 않는다. 롤백 시점이 알림 저장보다 뒤이기 때문이다. 단 4번 시점 문제 때문에 실시간 푸시는 예외다.

## 5. 처리 완료 후 주문의 최종 상태, 창고 보관을 선택했을 때의 차이

**최종 주문 상태**
- `Order.status`는 `PENDING_PAYMENT`로 끝난다. 즉시 구매 경로에서 `Order.updateStatus`는 호출되지 않는다 (`P/order/entity/Order.java:113`). Order 상태를 바꾸는 호출은 `processPaymentAndShipment`(`OrderCommandService.java:163-177`)와 Kafka 소비자 `OrderEventConsumer`(`P/order/service/kafka/OrderEventConsumer.java:192-216`)뿐이다. 즉시 구매는 두 경로 모두 타지 않는다. 즉시 구매 경로에서 Kafka 발행도 없으므로 소비자가 이 주문을 건드리지도 않는다.
- 상태 전이표상 `PENDING_PAYMENT`에서 `PAYMENT_COMPLETED`, `COMPLETED`, `IN_WAREHOUSE`로 갈 수 있지만 (`P/order/entity/OrderStatus.java:24`) 즉시 구매는 이 전이를 하지 않는다.
- 따라서 결제가 `PAID`인 일반 결제도 Order는 `PENDING_PAYMENT`다.

**창고 보관 선택 (`warehouseStorage = true`)**
- 요청의 `warehouseStorage` 값은 컨트롤러 로그에만 쓰이고 (`OrderBidCommandController.java:94-95`), 서비스에서 `createInstantOrder`로 전달된다 (`OrderBidCommandService.java:133-139`).
- `OrderCommandService.createInstantOrder`의 `isWarehouseStorage` 파라미터(`OrderCommandService.java:221`)는 메서드 본문에서 **한 번도 읽히지 않는다**.
- 실제 동작은 판매자 쪽 플래그 `sale.isWarehouseStorage()`로만 결정된다 (`OrderCommandService.java:291-294`, `P/sale/entity/Sale.java:43`). 구매자 선택은 무시된다.
  - 판매가 창고 보관이면 `WarehouseStorage` 상태가 `ASSOCIATED_WITH_ORDER`로 바뀐다 (`:293`). 이 상태 변경은 기존 `WarehouseStorage`가 있어야 가능하다. 없으면 `WarehouseStorageNotFoundException`이 나고 `OrderWarehouseStorageProcessingFailedException`으로 바뀌어 **구매 전체가 실패한다** (`P/warehouseStorage/service/query/WarehouseStorageQueryService.java:30-33`, `OrderCommandService.java:295-297`).
  - 구매자가 창고 보관을 골랐는데 판매가 창고 보관이 아니면 아무 변화가 없다.
- 창고 보관 경로에서도 `Order.warehouseStorage`에 연결하지 않는다. `createOrderStorage`, `assignWarehouseStorage`, `IN_WAREHOUSE`, `COMPLETED` 전이는 모두 `processPaymentAndShipment`의 창고 분기에만 있다 (`OrderCommandService.java:163-172`). 즉시 구매는 이 분기를 타지 않는다.
- `OrderShipment`는 창고 선택과 무관하게 주소로 생성된다 (`OrderCommandService.java:264-271`).

## 질문과 코드의 불일치 (주석/메서드 이름 vs 실제 동작)

1. **`@throws SaleBidNotFoundException`** (`OrderBidCommandService.java:115`): 판매 입찰이 없으면 `SaleBidQueryService.findById`가 `IllegalArgumentException`을 던진다 (`P/sale/service/query/SaleBidQueryService.java:21-24`). 그 뒤 null 체크(`OrderBidCommandService.java:174-176`)는 실행되지 않는다. 결과는 `OrderBidCreationFailedException`이다.
2. **"즉시 구매는 바로 매칭 상태"** (`OrderBidCommandService.java:196`): 판매 입찰이 이미 매칭되었는지 확인하지 않는다. `getSaleBidAndValidate`는 null 체크만 한다 (`:172-184`). 같은 판매 입찰로 두 번째 구매를 하면 새 Order와 OrderBid가 만들어지고 `saleBid.assignOrder`로 기존 주문 연결이 덮어써진다 (`OrderCommandService.java:279`). 중복을 막는 것은 `OrderBid.sale`의 `@OneToOne` 제약뿐이고 (`P/order/entity/OrderBid.java:45-47`), 이 제약이 DB에 있는지는 저장소만으로 확정할 수 없다.
3. **`Sale.updateStatus`는 전이 검사를 하지 않는다** (`P/sale/entity/Sale.java:73-75`). `SaleStatus.canTransitionTo`가 있는데도 (`P/sale/entity/SaleStatus.java`) `SOLD`로 바로 설정된다. 예를 들어 `IN_STORAGE` 상태의 판매도 `SOLD`가 된다.
4. **`Order.updateStatus`가 있는 `processPaymentAndShipment`와 즉시 구매의 상태 흐름이 다르다.** 즉시 구매는 결제가 끝나도 Order를 `PAYMENT_COMPLETED`로 바꾸지 않는다 (5번).
5. **카드 `"success"` 판정과 실제 PG 응답**: 저장소 안에서는 `"success"` 한 곳만 확인된다. 실제 PortOne 응답의 status 값과 맞는지는 외부 스펙 확인이 필요하다. 맞지 않으면 정상 승인도 `PENDING`으로 남는다.
6. **결제 금액 무검증**: 카드, 계좌, 일반 모두 클라이언트가 보낸 `paidAmount`를 판매 입찰 가격과 비교하지 않는다 (`PaymentCommandService.java:141-145`). 카드는 그 금액으로 PG 승인을 요청한다 (`:179`).

## 확인하지 못한 것

- PG(PortOne)의 실제 응답 형식과 status 값: 외부 서비스라 저장소로 검증할 수 없다.
- DB 제약(unique, FK)과 실제 스키마: `application-test.yml`(`create-drop`)과 `application-prod.yml`(`create`)에 DDL 설정만 있다. 실제 스키마는 확인하지 못했다.
- 실시간 알림이 실제로 도달하는지: Redis 연결 키와 WebSocket 설정이 런타임 상태에 달려 있다.
