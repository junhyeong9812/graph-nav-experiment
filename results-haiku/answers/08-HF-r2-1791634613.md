# 답: 구매자 배송은 운송장 등록부터 배송 완료까지 어떻게 처리되나

정적 코드 분석 결과다. 실행하거나 테스트하지 않았다. 경로는 저장소 루트 기준이며, 공통 접두어 `src/main/java/com/fream/back/`은 `domain/...`, `global/...`로 줄여 쓴다.

**요약**
- 운송장 등록(`PATCH /shipments/order/{id}/status`)은 (a) 실배송 일반 구매 입찰 주문, (b) 즉시 구매 주문 모두 끝까지 성공하지 못한다. 주문 상태가 `PREPARING`인데 `IN_TRANSIT`으로 바꾸려다 실패하고 트랜잭션이 롤백된다.
- 배송 완료 감지는 6시간마다 도는 Spring Batch 잡(`ShipmentItemProcessor`)이 실제로 수행한다.
- 배송 완료 판정 후 `completeOrder`도 주문이 `PREPARING`이면 `COMPLETED`로 바꾸지 못해 실패한다. 따라서 (a), (b) 모두 "배송 완료 → 주문 완료"까지 진행되지 않는다.

---

## 1. 운송장 등록 요청

### 1-1. 진입 API
- `PATCH /shipments/order/{shipmentId}/status`: `domain/shipment/controller/command/OrderShipmentCommandController.java:33-49`. 요청 본문은 `courier`, `trackingNumber`이다.
- 같은 등록 로직을 타는 `POST /shipments/order/{id}/check-status`(`:58`), `POST .../check-status-string`(`:103`)도 있다. 이 둘은 CJ 조회까지 같이 한다(아래 1-5, 4 참고).

### 1-2. 상태가 바뀌는 순서 (등록 PATCH 기준, 코드 의도대로 읽었을 때)
1. 주문 생성 시 구매자 배송은 `PENDING`으로 만들어진다: `domain/shipment/service/command/OrderShipmentCommandService.java:67`.
2. 운송장 등록 시 `OrderShipment.updateTrackingInfo`가 `courier`, `trackingNumber`를 쓰고 `status`를 `IN_TRANSIT`으로 직접 설정한다: `domain/shipment/entity/OrderShipment.java:41-45`. `ShipmentStatus`의 전이 규칙을 거치지 않는다(`PENDING → IN_TRANSIT`이 허용 목록에 없음: `ShipmentStatus.java:60-65`).
3. 주문 `Order`를 `IN_TRANSIT`으로 바꾼다: `OrderShipmentCommandService.java:260`.
4. 주문 입찰·판매 입찰을 `COMPLETED`로 바꾼다: `OrderShipmentCommandService.java:289`, `:413-440`. 배송 완료 시점이 아니라 등록 시점에 바뀐다.
5. 판매 `Sale`을 `SOLD`로 바꾼다: `OrderShipmentCommandService.java:276`, `:112-123`. `SOLD`는 `ON_AUCTION` 또는 `SELLING`에서만 가능하다(`domain/sale/entity/SaleStatus.java:36-37`).

알림(코드상 의도):
- 구매자: "상품이 출발하였습니다" 1건 (`OrderShipmentCommandService.java:266-271`).
- 판매자: Sale이 `SOLD`로 바뀐 경우에만 "판매 완료" 1건 (`:133-138`, `:164-169`).

### 1-3. (a) 실배송 일반 구매 입찰 주문: 실패
선행 흐름(정상 처리):
- 일반 구매 입찰 생성 시 주문은 `PENDING_PAYMENT`: `domain/order/service/command/OrderCommandService.java:81`.
- 결제·배송 요청은 Kafka로 넘어간다: `domain/order/controller/command/OrderCommandController.java:54`.
- 컨슈머 `OrderEventConsumer.processCompleteOrder`가 `PENDING_PAYMENT → PAYMENT_COMPLETED`(`domain/order/service/kafka/OrderEventConsumer.java:195`) → `PREPARING`(`:216-218`)을 거쳐 저장한다(`:223`). 실배송이므로 창고 분기(`:197-211`)는 타지 않는다.
- 결과: 주문 `PREPARING`, 배송 `PENDING`, 입찰 `MATCHED`.

등록 PATCH에서 일어나는 일:
- `:249` 배송 조회는 성공한다. `:256`에서 배송 엔티티에 운송장과 `IN_TRANSIT`을 설정한다(메모리상).
- `:260` `order.updateStatus(IN_TRANSIT)`에서 실패한다. `OrderStatus`의 전이 표는 `PREPARING → {IN_WAREHOUSE, SHIPMENT_STARTED}`만 허용한다(`domain/order/entity/OrderStatus.java:26`). `SHIPMENT_STARTED`를 설정하는 코드는 저장소에 없다. `Order.updateStatus`가 `InvalidOrderStatusException`을 던진다(`domain/order/entity/Order.java:166-173`).
- `:295-301`의 `catch (Exception)`이 이를 `ShipmentException(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: ...")`로 감싼다. `ShipmentException`은 `RuntimeException`이므로 `@Transactional`이 롤백한다.

무엇이 저장되는가: 아무것도 저장되지 않는다.
- 배송: `courier`, `trackingNumber` 모두 null, `status` = `PENDING` 그대로.
- 주문: `PREPARING` 그대로.
- 알림: 0건. `:266`에 도달하지 못한다.

응답:
- `GlobalExceptionHandler`가 `ShipmentException`을 처리한다: `global/exception/GlobalExceptionHandler.java:49-62`. HTTP 상태는 `SHIPMENT_NOT_FOUND`의 404(`domain/shipment/exception/ShipmentErrorCode.java:12`)다.
- 응답 본문 메시지는 에러코드 기본 문구인 "배송 정보를 찾을 수 없습니다."이다. 실제 원인("PREPARING -> IN_TRANSIT")은 서버 로그에만 남는다.
- 즉 응답은 404이며, "배송 정보가 없다"는 잘못된 원인을 알려준다.

### 1-4. (b) 즉시 구매 주문: 같은 지점에서 실패
- 즉시 구매는 `OrderBidCommandService.createInstantOrderBid`(`domain/order/service/command/OrderBidCommandService.java:119-149`)에서 만든다. `OrderBid`는 `MATCHED`로 생성되고 `sale`이 연결되며, 즉시 구매 플래그가 켜진다(`:189-207`, 특히 `:196`, `:205`).
- 주문은 `PENDING_PAYMENT`(`OrderCommandService.java:244`), 판매 입찰(`SaleBid`)은 `assignOrder` 후 `MATCHED`가 된다(`OrderCommandService.java:279-280`).
- 이후 결제·배송 처리는 (a)와 같은 Kafka 경로를 타서 주문이 `PREPARING`이 된다.
- 등록 PATCH는 `:260`에서 (a)와 똑같이 실패한다. 404, 롤백, 저장 없음.
- 참고: `isInstantPurchase` 플래그는 설정만 되고 읽는 곳이 없다(`OrderBid.java:52`, `:97-99`). 배송 로직에 즉시 구매 분기는 없다.

### 1-5. 조회 API로 등록하는 경로 (check-status)
- `updateAndCheckShipmentStatus`(`OrderShipmentCommandService.java:452-516`)는 `:473`에서 배송을 `IN_TRANSIT`으로 만들되 주문은 건드리지 않는다.
- CJ 결과가 `배송출발`이면 `:491-493`에서 `OUT_FOR_DELIVERY`로 저장된다(`IN_TRANSIT → OUT_FOR_DELIVERY`는 허용). 주문은 `PREPARING`에 남는다. 이 경로로 운송장이 들어가면 배치 대상이 된다.
- CJ 결과가 `배송완료`이면 `:486`에서 `DELIVERED`로 바꾼 뒤 `completeOrder`를 호출하고, `PREPARING → COMPLETED`가 막혀 실패한다(4 참고). 롤백된다.
- CJ 결과가 그 밖의 값(`배송중` 등)이면 `:473`에서 이미 `IN_TRANSIT`인 배송을 `:497`에서 다시 `IN_TRANSIT`으로 전이한다. `IN_TRANSIT`은 자기 자신으로 전이할 수 없으므로(`ShipmentStatus.java:72-78`) `OrderShipment.updateStatus`가 `IllegalStateException`을 던진다(`OrderShipment.java:47-55`). `:507-514`에서 `EXTERNAL_TRACKING_SERVICE_ERROR`(503)로 감싸져 롤백된다. 즉 "배송출발"/"배송완료"가 아닌 중간 상태에서는 항상 실패한다.

## 2. 배송 완료 감지

### 2-1. 누가, 언제, 어떻게
- 자동 감지: `global/config/ShipmentBatchScheduler.java:34-44`. `@Scheduled(cron = "0 0 */6 * * *")`이므로 매일 00시, 06시, 12시, 18시(서버 타임존)에 `updateShipmentStatusesJob`을 실행한다. 실행마다 `timestamp` 파라미터를 넣어 새 JobInstance를 만든다. 예외는 `printStackTrace()`만 하고 삼킨다(`:41-43`).
- 잡 구성: `domain/shipment/config/UpdateShipmentStatusesJobConfig.java:55-82`. 청크 크기 50(`:51`), skip 한도 50(`:52`, `:75-77`).
- 대상 조회(Reader): `:89-97`. JPQL은 `:95`의 `status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND trackingNumber IS NOT NULL`이다.
- 실제 처리: `ShipmentItemProcessor.process`(`domain/shipment/config/ShipmentItemProcessor.java:57-157`).
  - Playwright로 `https://trace.cjlogistics.com/next/tracking.html?wblNo={운송장}`을 연다(`:28`, `:81-83`).
  - `tbody#statusDetail tr`이 나타날 때까지 기다린다(`:87`).
  - HTML을 Jsoup으로 파싱해 마지막 행의 5번째 `td`를 상태 문자열로 쓴다(`:167-212`, 특히 `:181`).
- 브라우저: 스텝 시작 시 열고 종료 시 닫는다(`domain/shipment/config/BrowserManageStepListener.java:15-25`).

### 2-2. 실제로 실행되는 코드 vs 죽은 코드
실행되는 쪽: `ShipmentItemProcessor`. `UpdateShipmentStatusesJobConfig.java:69-73`에서 `new ShipmentItemProcessor(...)`로 연결된다.

죽은 코드(같은 일을 하는 것처럼 보이지만 호출되지 않음):
- `UpdateShipmentStatusesJobConfig.shipmentItemProcessor()` 빈(`:104-177`): 스텝에 연결되지 않는다.
- `UpdateShipmentStatusesJobConfig.parseCjLogisticsStatus`(Jsoup 방식, `:186-220`)와 private `mapToShipmentStatus`(`:228-234`): 호출자가 없다.
- `OrderShipmentCommandService.updateShipmentStatuses()`(`OrderShipmentCommandService.java:309-391`): 호출자가 없다. 이 메서드는 `CjTrackingPlaywright`를 쓰는 또 다른 버전이다.
- `OrderCommandService.processPaymentAndShipment`(`:112`): 호출자가 없다(컨트롤러는 Kafka만 사용). 참고로 이 메서드는 주문 ID를 `OrderBid`의 PK로 조회한다(`:188`), 사용하지 않으므로 실해는 없다.

수동 조회 경로: `updateAndCheckShipmentStatus` → `CjTrackingPlaywright.getCurrentTrackingStatus`(`global/utils/CjTrackingPlaywright.java:33`, 호출 `OrderShipmentCommandService.java:477`).

### 2-3. 택배사 상태 문자열 → 내부 상태
- `ShipmentItemProcessor.mapToShipmentStatus`(`:220-226`), 그리고 같은 매핑이 `OrderShipmentCommandService.java:399-405`에도 있다:
  - `"배송완료"` → `DELIVERED`
  - `"배송출발"` → `OUT_FOR_DELIVERY`
  - 그 밖의 모든 문자열 → `IN_TRANSIT` (`default`)
- 비교는 `trim()` 후 정확히 일치하는 문자열로 한다(`:181`).
- 처리 분기(`ShipmentItemProcessor.java`):
  - `:101-105` 현재 상태와 같으면 아무것도 하지 않는다.
  - `:108-117` `DELIVERED`이면 배송 완료 처리(3 참고).
  - `:119-121` `OUT_FOR_DELIVERY`이면 상태만 바꾼다.
  - `:123-126` 그 밖이면 `IN_TRANSIT`으로 바꾼다.
- 주의: `OUT_FOR_DELIVERY` 상태에서 CJ 마지막 행이 "배송출발"도 "배송완료"도 아닌 텍스트로 바뀌면, `default`에 걸려 `IN_TRANSIT`을 시도한다. `OUT_FOR_DELIVERY`는 `IN_TRANSIT`으로 갈 수 없으므로(`ShipmentStatus.java:79-84`) `IllegalStateException`이 나고, 처리기가 이를 감싸 건너뛴다(`ShipmentItemProcessor.java:133-145`). 다음 회차에도 같은 일이 반복된다. 실제 CJ 텍스트 변화는 확인하지 못했다.

## 3. 배송 완료 판정 이후 (배치 경로)

`ShipmentItemProcessor.java:108-117`에서 다음 순서로 처리된다.

1. 배송 엔티티 `updateStatus(DELIVERED)`: `IN_TRANSIT`, `OUT_FOR_DELIVERY` 모두에서 허용된다(`ShipmentStatus.java:75-76`, `:82`).
2. `orderService.completeOrder(orderId)` 호출 (`domain/shipment/service/command/OrderShipmentCommandService.java:191-229`):
   - 주문을 `COMPLETED`로 바꾼다(`:204`). `COMPLETED`로 가는 전이는 `IN_TRANSIT`과 `IN_WAREHOUSE`에서만 허용된다(`domain/order/entity/OrderStatus.java:27`, `:29`).
   - `updateSaleStatusToSold(orderId)`를 호출한다(`:208`). 판매 입찰의 `Sale`이 `ON_AUCTION` 또는 `SELLING`이면 `SOLD`로 바꾸고 판매자에게 알림 1건을 보낸다(`:116-138`). 주문 입찰 쪽 경로(`:151-176`)는 Sale이 이미 `SOLD`라 추가 알림이 없다.
   - 구매자에게 "[completeOrder] 주문이 완료 처리되었습니다" 알림 1건(`:212-217`).
3. `notificationService.notifyShipmentCompleted(order)` 호출 (`ShipmentItemProcessor.java:117`, 구현은 `domain/notification/service/command/NotificationCommandService.java:219-234`): 구매자에게 "[배송 완료] ..." 알림 1건.

알림 집계(성공 경로 기준): 구매자 2건(내용이 비슷한 두 건), 판매자 0건 또는 1건(Sale 상태에 따라).

입찰 상태: `completeOrder`는 입찰 상태를 건드리지 않는다. 주문 입찰·판매 입찰의 `COMPLETED` 전환은 등록 시점의 `updateOrderAndSaleBidStatusToCompleted`(`OrderShipmentCommandService.java:289`, `:413-440`)에서만 일어난다. 즉 배송 완료 시점에는 바뀌지 않고, 등록 시점에 먼저 `COMPLETED`가 된다.

저장: 청크 트랜잭션이 커밋될 때 배송, 주문, 판매, 알림이 함께 저장된다. 처리 도중 예외가 나면 이 전부가 롤백된다.

주의: `completeOrder`의 `catch (Exception)`(`:221-227`)은 모든 실패를 `ORDER_NOT_FOUND_FOR_SHIPMENT`로 바꿔 원인을 가린다.

## 4. 주문 종류별 차이

**두 주문 모두 끝까지 진행되지 않는다.** 실패 지점은 같다.

- 등록 PATCH: (a), (b) 모두 `OrderShipmentCommandService.java:260`에서 실패한다(1-3, 1-4).
- 배치 경로: 배치 대상이 되려면 배송이 `IN_TRANSIT` 또는 `OUT_FOR_DELIVERY`여야 하는데, 이는 1-5의 check-status "배송출발" 경로로만 생긴다. 이때 주문은 여전히 `PREPARING`이다. 이후 배치가 `DELIVERED`를 판정하면 `completeOrder`의 `Order.updateStatus(COMPLETED)`가 `PREPARING → COMPLETED` 전이 불가로 실패한다(`OrderStatus.java:25-26`에는 `COMPLETED`로 가는 전이가 없다). 그 건은 건너뛰어진다(5 참고).

두 주문이 같은 데이터 구조를 갖는 점도 확인했다. 둘 다 `OrderBid`(주문 연결 있음)와 `SaleBid`(주문 연결 있음)를 가진다. 일반 구매 입찰은 판매자가 `POST /sale-bids/instant`로 매칭할 때 `SaleBid`가 생기고(`domain/sale/service/command/SaleBidCommandService.java:72-83`, 컨트롤러 `SaleBidCommandController.java:43-47`), 즉시 구매는 `OrderCommandService.java:279-280`에서 생긴다.

결과가 달라지는 지점은 주문 상태 전이를 통과한다고 가정했을 때만 드러난다(실제로는 `:260`, `:204`에서 막힘).
- (a) 일반 구매 입찰: 판매 `Sale`은 `createInstantSale`에서 `PENDING_SHIPMENT`로 만들어진다(`domain/sale/service/command/SaleCommandService.java:62`). `PENDING_SHIPMENT`에서는 `SOLD`로 갈 수 없다(`SaleStatus.java:32`). 따라서 `updateSaleStatusToSold`는 판매 상태를 바꾸지 않고 판매자 알림도 보내지 않는다(`OrderShipmentCommandService.java:119` 분기가 false, `:142-144`에서 debug 로그만). 주문은 완료되는 것처럼 보이지만 판매 쪽은 `SOLD`가 되지 않는다.
- (b) 즉시 구매: 판매 `Sale`은 기존 판매 입찰에서 온 것이다. `SOLD`는 그 시점 Sale 상태가 `ON_AUCTION` 또는 `SELLING`일 때만 된다. 그 경우 판매자 알림 1건과 `SOLD`가 기록되고, 아니면 (a)와 같다. 실제 Sale 상태는 데이터에 따라 다르며 확인하지 못했다.

## 5. 실패 처리 (주기 처리 중 한 건 실패 시)

- 실패한 건:
  - `ShipmentItemProcessor`가 예외를 던지면(`:133-145`) 스텝의 `.faultTolerant().skip(Exception.class)`(`UpdateShipmentStatusesJobConfig.java:75-77`)가 그 건을 건너뛴다. skip 리스너가 로그를 남긴다(`:252-266`).
  - 그 건의 DB 변경은 롤백된다. 배송 `DELIVERED`, 주문 `COMPLETED`, 알림은 같은 트랜잭션이라 모두 저장되지 않는다. 배송은 기존 `IN_TRANSIT` 또는 `OUT_FOR_DELIVERY` 그대로이고, 다음 회차(6시간 뒤)에 다시 대상이 된다.
  - 매 회차 같은 건이 실패하면 skip 횟수가 누적된다.
- 나머지 건:
  - 실패가 나면 Spring Batch의 fault-tolerant 청크는 청크를 롤백하고 건을 하나씩 다시 처리해 정상 건은 커밋한다. 이는 프레임워크 동작에 따른 것으로, 이 저장소 코드만으로는 검증하지 못했다.
- skip 한도 초과: 스텝 전체 skip 누적이 `SKIP_LIMIT`(50)을 넘으면 스텝이 실패하고, 그 회차의 나머지 건은 처리되지 않는다.
- 참고(추정, 실행하여 검증하지 않음): Reader는 `ORDER BY` 없이 페이지 오프셋으로 읽는다(`:95`). 처리 도중 상태가 바뀌어 결과 집합이 줄어들므로, 대상이 50건을 넘으면 페이지 경계에서 일부 건이 그 회차에 건너뛰어질 수 있다. 다음 회차에 처리된다.
- 등록 PATCH와 check-status 경로의 실패는 각각 1-3, 1-5에서 설명한 대로 롤백되고 응답 코드(404 또는 503)를 돌려준다.
