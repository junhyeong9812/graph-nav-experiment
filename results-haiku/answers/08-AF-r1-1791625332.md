# 답: 구매자 배송은 운송장 등록부터 배송 완료까지 어떻게 처리되나

결론부터 말하면, 코드상 설계된 흐름은 끝까지 이어지지만 **실배송 일반 구매 입찰 주문(a)은 운송장 등록부터 배송 완료까지 어느 단계에서도 성공하지 못합니다.** 주문 상태 전이 규칙이 설계된 흐름과 맞지 않기 때문입니다. 즉시 구매 주문(b)은 운송장 등록(PATCH)은 실패하지만, 택배사 조회 API(`check-status`)로 배송 완료를 처리하면 주문이 `COMPLETED`까지 갑니다.

이 답은 정적 코드 읽기 결과입니다. DB, 택배사 페이지, Kafka, Playwright는 실행하지 않았습니다. 실행으로 확인하지 않은 부분은 마지막 "검증 한계" 절에 따로 적었습니다.

## 1. 운송장 등록 요청

**API**
- `PATCH /shipments/order/{shipmentId}/status`, 본문은 `courier`, `trackingNumber`.
  - `src/main/java/com/fream/back/domain/shipment/controller/command/OrderShipmentCommandController.java:20` (base path), `:33-34` (PATCH), `:41` (서비스 호출)
  - 본문 DTO: `src/main/java/com/fream/back/domain/shipment/dto/OrderShipmentRequestDto.java:10-12`
- 처리 메서드: `OrderShipmentCommandService#updateTrackingInfo` (`src/main/java/com/fream/back/domain/shipment/service/command/OrderShipmentCommandService.java:238-303`).

**설계된 상태 변화 순서** (코드가 의도한 흐름)
1. `OrderShipment`: 운송장 정보 저장과 동시에 `IN_TRANSIT`. `OrderShipment.updateTrackingInfo`가 전이 규칙을 거치지 않고 status를 직접 `IN_TRANSIT`으로 씁니다. (`src/main/java/com/fream/back/domain/shipment/entity/OrderShipment.java:41-45`, 서비스 `:256`)
2. `Order`: `IN_TRANSIT`으로 변경 (`OrderShipmentCommandService.java:260`).
3. 구매자 알림 "상품이 출발하였습니다" 1건 (`:266-271`).
4. `updateSaleStatusToSold` 호출 (`:276`): Sale을 `SOLD`로, 창고 보관이면 창고 상태 `SOLD`, 판매자 알림 "판매 완료" (`:111-148`).
5. `OrderBid`와 `SaleBid`: `MATCHED` → `COMPLETED` (`:289`, 본체 `:413-440`). 이 메서드는 예외를 삼킵니다 (`:436-439`).

**설계된 알림**: 구매자 1건(출발), 판매자 1건(판매 완료, Sale 전이가 가능할 때만).

**(a) 실배송 일반 구매 입찰 주문: 끝까지 성공하지 않습니다.**

주문의 실제 상태는 다음과 같이 만들어집니다.
- 주문 생성: `Order`가 `PENDING_PAYMENT` (`src/main/java/com/fream/back/domain/order/service/command/OrderCommandService.java:81`). 입찰 `OrderBid`는 `assignOrder`에서 `MATCHED`가 됩니다 (`src/main/java/com/fream/back/domain/order/entity/OrderBid.java:74-75`, `src/main/java/com/fream/back/domain/order/service/command/OrderBidCommandService.java:90-103`).
- 결제·배송 처리: 컨트롤러는 직접 처리하지 않고 Kafka에 이벤트를 보냅니다 (`src/main/java/com/fream/back/domain/order/controller/command/OrderCommandController.java:54`). 컨슈머 `OrderEventConsumer#processCompleteOrder`가 `PAYMENT_COMPLETED` (`src/main/java/com/fream/back/domain/order/service/kafka/OrderEventConsumer.java:195`) → `PREPARING` (`:216-218`) → 저장 (`:223`)을 수행합니다. 따라서 (a)의 주문 상태는 `PREPARING`입니다.

운송장 등록은 다음 지점에서 실패합니다.
- `OrderShipmentCommandService.java:260`의 `order.updateStatus(OrderStatus.IN_TRANSIT)`.
- `Order.updateStatus`는 `canTransitionTo`가 false면 `InvalidOrderStatusException`을 던집니다 (`src/main/java/com/fream/back/domain/order/entity/Order.java:113-120`).
- `OrderStatus.PREPARING`의 허용 전이는 `IN_WAREHOUSE`, `SHIPMENT_STARTED`뿐입니다 (`src/main/java/com/fream/back/domain/order/entity/OrderStatus.java:26`). `IN_TRANSIT`은 없습니다.
- 예외는 `RuntimeException` 계열입니다 (`src/main/java/com/fream/back/domain/order/exception/InvalidOrderStatusException.java:6`, `OrderException.java:10`, `src/main/java/com/fream/back/global/exception/GlobalException.java:10`).
- 서비스의 `catch (Exception e)`가 이를 잡아 `ShipmentException(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: ...")`로 감쌉니다 (`OrderShipmentCommandService.java:295-301`). 트랜잭션은 롤백됩니다.

**저장되는 것**: 아무것도 저장되지 않습니다.
- 배송 엔티티는 `PENDING` 그대로 남고, 택배사와 운송장 번호도 저장되지 않습니다. 메모리 변경은 롤백됩니다.
- 주문은 `PREPARING` 그대로입니다.
- 구매자 알림은 생성되지 않습니다. 알림 코드가 `:260` 뒤에 있기 때문입니다.

**응답**: HTTP 404, 본문은 `ErrorResponse`(코드 `S001`, 메시지 "배송 정보를 찾을 수 없습니다.")입니다.
- `src/main/java/com/fream/back/global/exception/GlobalExceptionHandler.java:459-471`이 `errorCode.getMessage()`만 본문에 넣습니다.
- `src/main/java/com/fream/back/domain/shipment/exception/ShipmentErrorCode.java:12`의 `S001`, 상태 404.
- 실제 원인("PREPARING -> IN_TRANSIT 불가")은 서버 로그에만 남고 응답에는 나오지 않습니다.

**참고 (잠재 실패)**: 만약 `:260`을 통과하더라도 `:276`의 `updateSaleStatusToSold` → `:116`의 `saleBidQueryService.findByOrderId`에서 실패합니다. 이 메서드는 SaleBid가 없으면 `null`이 아니라 `IllegalArgumentException`을 던지고 (`src/main/java/com/fream/back/domain/sale/service/query/SaleBidQueryService.java:26-29`), 일반 입찰 주문에는 SaleBid가 없기 때문입니다.

**(b) 즉시 구매 주문: 같은 지점에서 실패합니다.**
- 즉시 구매는 `createInstantOrder`에서 `Order`를 `PENDING_PAYMENT`로 만들고 (`OrderCommandService.java:244`), 결제 후에도 주문 상태를 바꾸지 않습니다 (같은 메서드 `:220-319`, 결제 쪽 `PaymentCommandService`에도 `Order` 상태 변경 없음).
- `PENDING_PAYMENT`의 허용 전이는 `PAYMENT_COMPLETED`, `COMPLETED`, `IN_WAREHOUSE`뿐입니다 (`OrderStatus.java:24`). `IN_TRANSIT`은 없으므로 `:260`에서 같은 방식으로 실패하고 롤백됩니다.

## 2. 배송 완료 감지

**누가, 언제, 어떻게**: 택배사가 알려주지 않습니다. 서버가 주기적으로 택배사 추적 페이지를 조회합니다.
- 주기 실행: `src/main/java/com/fream/back/global/config/ShipmentBatchScheduler.java:34` `@Scheduled(cron = "0 0 */6 * * *")`. 6시간마다, 매일 00:00·06:00·12:00·18:00(서버 시간대)에 실행됩니다. `:40`에서 `jobLauncher.run`으로 `updateShipmentStatusesJob`을 실행합니다.
- 잡·스텝 정의: `src/main/java/com/fream/back/domain/shipment/config/UpdateShipmentStatusesJobConfig.java:55-82`.
- 수동 조회 엔드포인트도 있습니다. `POST /shipments/order/{id}/check-status`, `.../check-status-string` (`OrderShipmentCommandController.java:58-94`, `:103-138`). 같은 서비스의 `updateAndCheckShipmentStatus`를 씁니다.

**대상 조회** (reader): `UpdateShipmentStatusesJobConfig.java:87-97`, 쿼리는 `:95`.
- `SELECT s FROM OrderShipment s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL`
- 페이지 크기 50 (`:51`, `:94`). 정렬 절(ORDER BY)이 없습니다.

**실제로 실행되는 처리 코드**
- 스텝은 `UpdateShipmentStatusesJobConfig.java:69-73`에서 `new ShipmentItemProcessor(...)`를 직접 만듭니다.
- 따라서 실행되는 처리는 `src/main/java/com/fream/back/domain/shipment/config/ShipmentItemProcessor.java:57-157`의 `process`입니다. 이 쪽은 Playwright로 페이지를 열고 (`:72`, `:83`, `:87`), 마지막 행의 5번째 `td`를 읽습니다 (`parseStatusFromHtml`, `:94`, `:181`).
- 실행되지 않는 비슷한 코드:
  - `UpdateShipmentStatusesJobConfig`의 `@Bean shipmentItemProcessor()` (`:104-177`). 스텝에서 참조하지 않습니다. 같은 클래스의 Jsoup 파서 `parseCjLogisticsStatus` (`:186-220`)도 호출되지 않습니다.
  - `OrderShipmentCommandService#updateShipmentStatuses` (`OrderShipmentCommandService.java:309-391`). 호출하는 곳이 없습니다 (저장소 전체 grep).
  - `CjTrackingPlaywright#getCurrentTrackingStatus` (`src/main/java/com/fream/back/global/utils/CjTrackingPlaywright.java:33-115`)는 `check-status` 경로에서만 쓰입니다. 배치는 쓰지 않습니다.

**택배사 상태 문자열 → 내부 상태** (`ShipmentItemProcessor.java:220-226`)
- `"배송완료"` → `DELIVERED`
- `"배송출발"` → `OUT_FOR_DELIVERY`
- 그 밖의 모든 문자열 → `IN_TRANSIT` (알 수 없는 문구도 포함)
- 처리 흐름 (`ShipmentItemProcessor.java:101-126`):
  - 현재 상태와 같으면 아무것도 하지 않습니다 (`:101-105`).
  - `DELIVERED`면 `updateStatus(DELIVERED)` 후 `completeOrder`, 그 다음 `notifyShipmentCompleted` (`:113-117`).
  - `OUT_FOR_DELIVERY`면 `updateStatus(OUT_FOR_DELIVERY)` (`:121`).
  - 그 밖이면 `updateStatus(IN_TRANSIT)` (`:125`). `OUT_FOR_DELIVERY`에서 `IN_TRANSIT`으로 가는 것은 허용되지 않으므로 예외가 납니다 (`src/main/java/com/fream/back/domain/shipment/entity/ShipmentStatus.java:23-28`).

## 3. 배송 완료 판정 이후

**배송 완료가 판정되면 (배치 경로)**
1. `OrderShipment`: `DELIVERED` (`ShipmentItemProcessor.java:113`, 허용 전이 `ShipmentStatus.java:16-22`, `:23-28`).
2. `OrderShipmentCommandService#completeOrder` (`OrderShipmentCommandService.java:190-229`).
   - `OrderBid` 조회 (`:196`).
   - `Order`: `COMPLETED` (`:204`).
   - `updateSaleStatusToSold` (`:208`).
   - 구매자 알림 "[completeOrder] 주문이 완료 처리되었습니다" (`:212-217`).
3. `NotificationCommandService#notifyShipmentCompleted` (`src/main/java/com/fream/back/domain/notification/service/command/NotificationCommandService.java:219-234`). 구매자 알림 "[배송 완료]" (`createNotification`은 `:53`에서 저장).
4. 청크 writer가 변경을 저장합니다 (`UpdateShipmentStatusesJobConfig.java:239-246`).

**누가 몇 건 받나**: 배치 경로에서 구매자는 2건(`completeOrder`의 "[completeOrder]"와 `notifyShipmentCompleted`의 "[배송 완료]"). 판매자는 이 시점에 받지 않습니다. `check-status` 경로에서 `DELIVERED`가 되면 구매자는 1건입니다 (`OrderShipmentCommandService.java:483-489` → `completeOrder`).

**주문 입찰·판매 입찰 상태**: 이 경로에서는 바뀌지 않습니다. `MATCHED` 그대로입니다.
- `MATCHED` → `COMPLETED` 전환 코드(`:413-440`)는 `updateTrackingInfo`의 `:289`에서만 호출되는데, 그 경로는 1번 항목에서 설명한 대로 항상 실패합니다. 따라서 어떤 주문에서도 도달하지 않습니다.

**판매 상태**: 판매자 알림과 Sale `SOLD` 전이는 `updateSaleStatusToSold`가 맡습니다 (`OrderShipmentCommandService.java:111-183`). 하지만 즉시 구매 주문에서는 결제 시점에 이미 `SOLD`입니다 (4번 항목 참고).

## 4. 주문 종류별 차이

**(a) 실배송 일반 구매 입찰 주문: 끝까지 진행되지 않습니다.**

배치 경로 (`DELIVERED` 판정 후):
- `completeOrder`의 `order.updateStatus(COMPLETED)` (`OrderShipmentCommandService.java:204`)는 `PREPARING`에서 허용되지 않습니다 (`OrderStatus.java:24-32`에서 `COMPLETED` 전이는 `PENDING_PAYMENT`, `IN_WAREHOUSE`, `IN_TRANSIT`에서만 가능).
- `InvalidOrderStatusException` → `completeOrder`의 `catch`가 `ShipmentException(ORDER_NOT_FOUND_FOR_SHIPMENT)`로 감쌉니다 (`:221-227`).
- 프로세서가 이를 다시 던지고 (`ShipmentItemProcessor.java:133-145`) 그 건은 스킵됩니다. 배송 상태도 저장되지 않습니다 (청크 롤백).
- 설령 `:204`를 통과해도 `:208` → `:116`에서 SaleBid가 없어 `IllegalArgumentException`이 납니다.

`check-status` 경로 (`DELIVERED` 판정 후):
- 같은 이유로 `updateAndCheckShipmentStatus` (`OrderShipmentCommandService.java:483-489`)가 롤백되고, 응답은 404 본문 없음입니다. `OrderShipmentCommandController.java:80-86`은 상태 코드만 돌려줍니다.

결과: 주문은 `PREPARING`에 머뭅니다. 배송 상태는 `OUT_FOR_DELIVERY` 등 이전 상태 그대로입니다. 알림은 없습니다. 입찰은 `MATCHED`입니다. 배치는 같은 건을 6시간마다 다시 시도하고 계속 스킵합니다.

**(b) 즉시 구매로 만들어진 주문: `check-status`로는 끝까지 갑니다. PATCH와 배치 경로는 전제가 다릅니다.**

PATCH (운송장 등록): `:260`에서 실패합니다 (1번 항목 참고).

`check-status`의 `DELIVERED`:
- `completeOrder` `:204`: `PENDING_PAYMENT` → `COMPLETED`는 허용됩니다 (`OrderStatus.java:24`). 성공.
- `updateSaleStatusToSold` `:116`: SaleBid가 있습니다 (`createInstantOrder`에서 `saleBid.assignOrder(order)`, `OrderCommandService.java:279`).
- 판매 상태는 이미 `SOLD`입니다. 결제 처리 `PaymentCommandService.processPayment`(`PaymentCommandService.java:57`, `:83`) → `notifyUsersAndUpdateSaleStatus`(`:383-425`)가 `sale.updateStatus(SOLD)`를 호출합니다 (`:404`). 이 메서드는 결제 시점에 구매자·판매자 알림도 보냅니다 (`sendNotifications`, `:434-456`).
- 따라서 `canTransitionTo(SOLD)`가 false가 되어 (`src/main/java/com/fream/back/domain/sale/entity/SaleStatus.java:23`) 판매자 알림과 창고 `SOLD` 갱신은 건너뜁니다 (`OrderShipmentCommandService.java:119-129`).
- 구매자 알림 1건. 주문 `COMPLETED`, 배송 `DELIVERED`. 입찰 `MATCHED` 그대로.
- 창고 보관 주문이라면 창고 상태는 결제 시점의 `ASSOCIATED_WITH_ORDER` (`OrderCommandService.java:293`)에 머무릅니다. 코드 읽기 기준입니다.

배치 경로의 `DELIVERED`:
- 위와 같이 성공합니다. 다만 구매자 알림이 2건입니다 (`completeOrder`와 `notifyShipmentCompleted`).

**도달 가능성 참고**: 코드에서 배송 상태가 `IN_TRANSIT`으로 커밋되는 경로는 없습니다.
- PATCH는 실패하고 롤백됩니다.
- `check-status`의 "배송 중" 처리는 항상 실패합니다. `updateAndCheckShipmentStatus`는 먼저 `shipment.updateTrackingInfo`로 `IN_TRANSIT`을 설정하고 (`OrderShipmentCommandService.java:473`), 기본 분기에서 `shipment.updateStatus(IN_TRANSIT)`을 호출합니다 (`:495-497`). `IN_TRANSIT.canTransitionTo(IN_TRANSIT)`은 false라서 `IllegalStateException`이 나고, `EXTERNAL_TRACKING_SERVICE_ERROR`(`ShipmentErrorCode.java:30`, HTTP 503)로 감싸져 롤백됩니다 (`:507-514`).
- 그래서 배치가 실제로 처리하는 건은 `OUT_FOR_DELIVERY`(`check-status`에서 "배송출발"일 때 커밋됨, `:491-493`)인 것만 현실적으로 남습니다. (단, DataInitializer 시드 데이터에 `IN_TRANSIT`이 있는지는 확인하지 않았습니다.)

## 5. 실패 처리 (주기 처리 중 한 건 실패)

- 설정: `faultTolerant().skip(Exception.class).skipLimit(50)` (`UpdateShipmentStatusesJobConfig.java:75-77`, 상수 `:52`). 재시도(retry)는 설정되어 있지 않습니다.
- 한 건이 예외를 던지면 (예: (a)의 `completeOrder` 실패, 파싱 실패, 상태 전이 예외):
  - 그 건은 DB에 저장되지 않습니다. 프로세서에서 메모리에 바꾼 상태(예: `DELIVERED`)도 청크 롤백으로 버려집니다.
  - `shipmentSkipListener`가 로그를 남깁니다 (`:251-287`, 등록 `:78`).
  - 그 건은 스킵 카운트를 1 올립니다. 상태는 그대로이므로 다음 6시간 실행 때 다시 대상이 됩니다.
- 나머지 건: 스프링 배치의 내결함성 청크 처리에서는 청크 롤백 후 항목을 하나씩 다시 처리해 나머지 건을 개별 트랜잭션으로 커밋합니다. 이 동작은 스프링 배치의 표준 동작에 근거한 판단이며, 실행해서 확인하지는 않았습니다.
- 스킵 한도: 스킵이 50건을 넘으면 스텝이 실패하고 잡이 FAILED로 끝납니다. 그 뒤 남은 건은 이번 실행에서 처리되지 않습니다. 다음 실행(최대 6시간 뒤)에서 다시 처리됩니다.
- 참고 (추정, 실행 미확인): 리더 쿼리에 `ORDER BY`가 없고 오프셋 기반 페이징을 씁니다 (`:87-97`). 청크 안에서 `DELIVERED`로 바뀐 행은 대상 목록에서 빠지므로, 뒤쪽 페이지의 행이 한 칸씩 밀려 이번 실행에서 건너뛰어질 수 있습니다. 다음 실행에서 처리됩니다.
- 참고: `OrderShipmentCommandService#updateShipmentStatuses`에도 건별 `catch`가 있지만 호출되지 않습니다 (`OrderShipmentCommandService.java:383-387`).

## 검증 한계

- 정적 읽기로만 답했습니다. DB, Kafka, Playwright, 실제 택배사 페이지, 테스트는 실행하지 않았습니다.
- 확정하지 못한 부분:
  - 리더 JPQL에서 enum 필드를 문자열 리터럴(`'IN_TRANSIT'`)과 비교하는 것이 현재 Hibernate 버전에서 실행되는지.
  - 스프링 배치가 청크 롤백 뒤 항목을 개별 재처리하는지의 세부 동작(표준 동작으로 판단).
  - 오프셋 페이징의 행 밀림이 실제로 발생하는지.
  - 택배사 페이지의 상태 문구 `"배송완료"`, `"배송출발"`이 실제 페이지와 일치하는지.
- 주석과 실제 동작이 다른 부분 (실제 동작을 답에 썼습니다):
  - `OrderShipmentCommandService#updateShipmentStatuses`와 `UpdateShipmentStatusesJobConfig`의 Jsoup 파서는 실제 배치에서 쓰이지 않습니다.
  - `OrderCommandService#processPaymentAndShipment`는 HTTP에서 호출되지 않는 죽은 경로입니다 (`OrderCommandController.java:54`이 Kafka만 발행). 그 안의 `orderBidQueryService.findById(orderId)` (`OrderCommandService.java:188`)는 주문 ID를 입찰 ID로 쓰므로 잘못된 대상을 갱신할 수 있습니다.
