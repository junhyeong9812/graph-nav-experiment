# 즉시 구매는 어떻게 처리되나

경로 표기: 아래 `파일경로:줄`의 경로는 저장소 루트 기준이다. 표의 `src/main/java/com/fream/back/domain/`는 `D/`로 줄여 쓴다.

요약: 즉시 구매는 `POST /order-bids/instant` 한 번의 동기 HTTP 요청 안에서 하나의 DB 트랜잭션으로 처리된다. 결제 대행사(PortOne) 호출도 그 트랜잭션 안에서 일어난다. 응답 ID는 `Order`가 아니라 `OrderBid`의 ID다. 주문의 최종 상태는 `PENDING_PAYMENT`에 머문다. 결제 금액은 서버가 주문 금액과 대조하지 않으며, 계좌이체와 일반 결제는 결제 확인 없이 성공 처리된다.

---

## 1. 요청 진입점, 처리 단계, 동기/비동기, 응답 ID

- **API**: `POST /order-bids/instant`. 클래스 매핑은 `/order-bids`이고 메서드는 `D/order/controller/command/OrderBidCommandController.java:89-90`에 있다.
- **요청 DTO**: `saleBidId`(판매 입찰 ID), `addressId`(배송지 ID), `warehouseStorage`(창고 보관 여부), `paymentRequest`(결제 정보). `D/order/dto/InstantOrderRequestDto.java:20-29`.
- **처리 단계**:
  1. 이메일 추출 및 검증: `OrderBidCommandController.java:92`
  2. 결제 요청에 구매자 이메일을 넣고 `orderId`를 null로 초기화: `OrderBidCommandController.java:98`, `:119-123`
  3. `OrderBidCommandService.createInstantOrderBid` 호출: `OrderBidCommandController.java:101-107`
  4. 서비스 내부 순서 (`D/order/service/command/OrderBidCommandService.java:118-149`):
     - 입력 검증: `:123`, `:154-167`
     - 구매자 조회: `:126`
     - 판매 입찰(`SaleBid`)과 판매(`Sale`) 조회: `:129`, `:172-184`
     - `OrderCommandService.createInstantOrder` 호출 (주문, 주문 항목, 배송, 판매 입찰 매칭, 결제까지 수행): `:133-139`
     - `OrderBid` 생성 및 저장: `:142`, `:189-207`
- **동기/비동기**: 동기다. 모든 단계가 요청 스레드에서 같은 `@Transactional` 흐름으로 실행된다 (`OrderBidCommandService.java:118`, `OrderCommandService.java:219`). 이 경로에는 Kafka 발행이 없다. Kafka 발행은 `D/order/controller/command/OrderCommandController.java:54`처럼 다른 경로에만 있다.
- **응답 ID**: `OrderBid`의 ID다. `OrderBidCommandController.java:101-107`에서 서비스가 돌려준 `OrderBid`에 `.getId()`를 호출하고 그 값을 `orderId`라는 변수에 담아 응답한다 (`:109`). 메서드 주석 `:83`의 "생성된 주문 ID"와 응답 메시지 `:109`의 "즉시 구매가 성공적으로 처리되었습니다"는 실제 값과 다르다. `Order`의 ID가 아니다.

## 2. 생성되는 엔티티와 상태 변화 순서

한 트랜잭션 안에서 다음 순서로 진행된다. 각 단계 직후의 상태를 적었다.

| 순서 | 동작 | 위치 | 직후 상태 |
|---|---|---|---|
| a | `Order` 생성 및 저장. `totalAmount`는 판매 입찰의 `bidPrice`로 설정 | `D/order/service/command/OrderCommandService.java:241-247` | `Order.status = PENDING_PAYMENT` (`:244`) |
| b | `OrderItem` 생성 및 `Order`에 추가 | `OrderCommandService.java:255-256` | (주문 항목 생성) |
| c | `OrderShipment` 생성 (배송지 정보는 `addressQueryService.getAddress(buyer.getEmail(), addressId)`로 조회) | `OrderCommandService.java:238`, `:264-271` | 배송 엔티티 생성. 배송 상태 값은 이 경로에서 설정하지 않는다 |
| d | `SaleBid`에 `Order`를 연결하고 `SaleBid.status = MATCHED`, `flush()` | `OrderCommandService.java:279-283`, `D/sale/entity/SaleBid.java:58-61` | `SaleBid.status = MATCHED` |
| e | `Sale.isWarehouseStorage`가 true이면 창고 보관 상태 갱신 | `OrderCommandService.java:291-294` | `WarehouseStorage` → `ASSOCIATED_WITH_ORDER` |
| f | 결제 처리 (`processPayment`) 후 판매 상태 갱신과 알림 | `OrderCommandService.java:305`, `D/payment/service/command/PaymentCommandService.java:83`, `:383-424` | `Payment` 생성 (3번 참고), `Sale.status = SOLD` (`:404`, `:419`) |
| g | `OrderBid` 생성: `status = MATCHED`, `sale`은 판매 입찰의 판매, `isInstantPurchase = true`, `order`에 연결 | `D/order/service/command/OrderBidCommandService.java:189-207`, `D/order/entity/OrderBid.java:50-52`, `:60-82` | `OrderBid.status = MATCHED` |
| h | 커밋 | 트랜잭션 경계 `OrderBidCommandService.java:118` | `Order.status`는 여전히 `PENDING_PAYMENT` |

- `Order`의 상태는 이 경로 어디에서도 바뀌지 않는다. `createInstantOrder`와 `createInstantOrderBid` 모두 `Order.updateStatus`를 호출하지 않는다 (`OrderCommandService.java:219-319`에서 `updateStatus`는 없음). 따라서 최종 상태는 `PENDING_PAYMENT`다.
- `OrderBid`가 `Order`에 연결될 때 `OrderBid.assignOrder`가 `status`를 `MATCHED`로 한 번 더 설정한다 (`OrderBid.java:74-75`, 호출은 `OrderBidCommandService.java:202`).
- `OrderCommandService.java:305`의 `processPayment` 반환값(`Payment`)은 버려진다. 일반 주문 경로(`OrderCommandService.java:139-140`)처럼 `order.assignPayment(...)`로 연결하지 않는다.

## 3. 결제 수단별 결과, 성공 종료 여부, 카드 실패 시 동작

결제 유형은 `PaymentRequestDto.getResolvedPaymentType()` 값으로 `CARD`, `ACCOUNT`, `GENERAL` 중 하나로 분기한다 (`D/payment/service/command/PaymentCommandService.java:57-80`).

**공통 검증** (`PaymentCommandService.java:117-146`)
- 주문 ID 일치 (`:130-134`), 사용자 이메일 일치 (`:135-139`).
- 결제 금액은 **0보다 큰지만** 본다 (`:142-145`). 주문 금액(`Order.totalAmount`, 즉 판매 입찰 가격)과 비교하지 않는다. 카드 결제는 이 클라이언트 입력값을 그대로 PortOne에 청구한다 (`:179`).

**카드 (CARD)** (`PaymentCommandService.java:157-225`)
- PortOne 카드 결제를 동기 호출한다 (`:179`, 구현은 `D/payment/portone/PortOneApiClient.java:229`).
- 응답 `code`가 0이 아니거나 HTTP 상태가 200이 아니면 `PaymentProcessingException`을 던진다 (`PortOneApiClient.java:270-274`).
- 결제 상태는 응답의 `status` 값이 문자열 `"success"`일 때만 `PAID`가 된다 (`PaymentCommandService.java:203-206`). 그 외에는 `Payment`의 기본값 `PENDING`이 남는다 (`D/payment/entity/Payment.java:44`). 저장소 안에서는 PortOne이 실제로 보내는 `status` 값을 확인할 수 없다. 실제 값이 `"success"`가 아니면 결제 성공 응답이어도 `PENDING`으로 저장되고 주문은 그대로 진행된다.
- 카드 결제가 성공하면 `Payment` 저장 (`:208`) 후 판매 상태 갱신과 알림 (`:83`)을 거쳐 즉시 구매가 끝까지 성공한다.

**카드 결제 실패 시 (PortOne이 실패 응답)**
- 예외가 전파되는 경로:
  1. `PortOneApiClient.java:270-274`에서 `PaymentProcessingException`
  2. `PaymentCommandService.java:180-181`, `:218-219`, `:94`에서 그대로 재던짐 (`PaymentException` 하위 클래스)
  3. `OrderCommandService.java:305-308`에서 `OrderPaymentProcessingFailedException`으로 감싸짐
  4. `OrderCommandService.java:312-314`에서 `OrderException`이므로 그대로 던짐
  5. `OrderBidCommandService.java:145-147`, `:212-215`에서 다시 그대로 던짐
- 예외 클래스는 모두 `RuntimeException`의 하위다 (`D/global/exception/GlobalException.java:10`). 따라서 `@Transactional`이 롤백한다.
- 롤백되는 항목: `Order`, `OrderItem`, `OrderShipment`, `SaleBid`의 매칭(`MATCHED`), 창고 보관 상태 변경, `OrderBid`. `Payment` 행은 저장되지 않는다 (`:208`에 도달하지 못함). `Sale.SOLD`와 알림도 `processPayment` 안의 `:83` 이후이므로 실행되지 않는다.
- 결과적으로 즉시 구매는 실패로 끝나고 아무 데이터도 남지 않는다. 다만 HTTP 응답으로 어떤 코드가 나가는지는 `GlobalExceptionHandler`를 확인하지 않아 검증하지 못했다.

**계좌이체 (ACCOUNT)** (`PaymentCommandService.java:236-277`)
- 은행명만 검증한다 (`:243-250`). 실제 입금 확인은 하지 않는다.
- `Payment.status = PENDING`으로 저장한다 (`:260`).
- `processPayment`는 결제 상태와 무관하게 알림 전송과 `Sale.SOLD` 처리를 실행한다 (`:83`, `:383-424`). 따라서 입금 전인데도 즉시 구매가 성공으로 끝난다. 주문 상태는 `PENDING_PAYMENT`로 남는다.

**일반 결제 (GENERAL)** (`PaymentCommandService.java:290-331`)
- `impUid` 존재 여부만 확인한다 (`:297-300`). PortOne을 다시 호출해 검증하지 않는다. 클라이언트가 보낸 `impUid`, `paidAmount`를 그대로 저장하고 `PAID`로 바꾼다 (`:313-314`).
- 결제 상태와 무관하게 즉시 구매는 성공으로 끝난다.

**즉시 구매가 끝까지 성공하는 경우**
- 카드: PortOne 응답의 `code`가 0이면 성공 (`PortOneApiClient.java:270`).
- 계좌이체, 일반 결제: 검증 통과 시 항상 성공.
- 어느 경우든 주문 상태는 `PENDING_PAYMENT`다.

**추가로 확인된 문제**
- 같은 판매 입찰을 두 번 구매하는 것을 막는 검사가 이 경로에 없다. `getSaleBidAndValidate`는 판매 입찰의 존재와 판매 연결만 본다 (`OrderBidCommandService.java:172-184`). `SaleBid.status`를 확인하지 않는다. 락도 찾지 못했다. 두 번째 호출은 `SaleBid.assignOrder`로 기존 주문 연결을 덮어쓰고 새 `Order`를 만든다 (`SaleBid.java:58-61`). 엔티티 매핑에 따른 DB 제약은 확인하지 못했다.
- PortOne 호출은 DB 트랜잭션 안에서 일어난다. 카드 결제가 PortOne에서 성공한 뒤 뒤쪽 단계(예: `OrderBid` 저장, 커밋)가 실패하면 DB는 롤백되지만 PortOne 결제는 취소되지 않는다. 환불 보상 로직 `handleRefundIfNecessary`(`PaymentCommandService.java:341`)는 정의만 되어 있고 호출하는 곳이 없다.

## 4. 누가 어떤 알림을 받나, 언제, 어떤 방식으로 전달되나

알림은 `PaymentCommandService.sendNotifications`에서 만든다 (`PaymentCommandService.java:434-461`).

- **구매자**: `NotificationCategory.SHOPPING`, `NotificationType.BID`, 메시지 "결제가 완료되었습니다. 주문 ID: {orderId}" (`PaymentCommandService.java:438-446`).
- **판매자**: `sale.getSeller()`에게 같은 카테고리와 타입, 메시지 "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}" (`PaymentCommandService.java:449-457`).

**시점과 방식**
- 알림은 `processPayment` 안에서, 즉 `Payment` 처리 직후이면서 트랜잭션이 커밋되기 전에 생성된다 (`PaymentCommandService.java:83`).
- `NotificationCommandService`는 클래스 전체가 `@Transactional`이다 (`D/notification/service/command/NotificationCommandService.java:27`). 알림 행은 주문과 같은 트랜잭션에 들어간다 (`:44-61`).
- 실시간 전송(WebSocket, `messagingTemplate.convertAndSendToUser`)은 같은 메서드 안에서 커밋 전에 실행된다 (`NotificationCommandService.java:56-57`, `:303-315`). 사용자가 Redis에 연결되어 있을 때만 보낸다 (`:306-307`). 따라서 나중에 커밋이 실패해 롤백되면 사용자는 롤백된 알림을 실시간으로 받은 것이 된다.
- 알림 생성 실패는 `PaymentCommandService.java:457-461`에서 로그만 남기고 삼킨다. 결제 자체는 성공으로 진행된다.
- 결제 상태 확인 없이 보낸다. 계좌이체처럼 입금 전인 결제에도 "결제가 완료되었습니다"가 나간다.

## 5. 처리 완료 후 주문의 최종 상태와 창고 보관 선택 시 차이

**최종 상태 (창고 보관 여부와 무관하게 같음)**

| 엔티티 | 최종 상태 | 근거 |
|---|---|---|
| `Order` | `PENDING_PAYMENT` | `OrderCommandService.java:244`, 이후 변경 없음 |
| `OrderItem`, `OrderShipment` | 생성됨 | `OrderCommandService.java:255-271` |
| `SaleBid` | `MATCHED` | `OrderCommandService.java:280` |
| `OrderBid` | `MATCHED`, `isInstantPurchase = true`, `sale` 연결 | `OrderBidCommandService.java:196-205`, `OrderBid.java:50-52` |
| `Sale` | `SOLD` | `PaymentCommandService.java:404`, `:419` |
| `Payment` | 카드 `PAID` 또는 `PENDING`, 계좌이체 `PENDING`, 일반 `PAID` | 3번 항목 참고 |

- `nav/ORDER_README.md:233`은 "결제가 즉시 처리되어 주문 상태가 `PAYMENT_COMPLETED`로 업데이트됩니다"라고 적는다. 코드와 다르다. 코드에서 주문 상태는 `PENDING_PAYMENT`에 머문다.

**창고 보관 옵션 (`warehouseStorage = true`)**
- 구매자가 보낸 `warehouseStorage` 값은 컨트롤러의 로그에만 쓰이고 (`OrderBidCommandController.java:94-95`, `:105`), 서비스와 `OrderCommandService.createInstantOrder`에 전달된다 (`OrderBidCommandService.java:119-120`, `OrderCommandService.java:221`). 하지만 `createInstantOrder` 본문에서는 이 매개변수를 한 번도 읽지 않는다. 구매자의 선택은 결과에 영향을 주지 않는다.
- 창고 보관은 판매자가 등록한 `Sale.isWarehouseStorage` 값으로만 결정된다 (`OrderCommandService.java:291-294`, `D/sale/entity/Sale.java:43`). 판매가 창고 보관 판매이면 `WarehouseStorage`가 `ASSOCIATED_WITH_ORDER`로 바뀐다 (`OrderCommandService.java:293`). 구매자가 창고 보관을 골라도 달라지는 것은 없다.
- 창고 보관 판매라도 `Order`는 `IN_WAREHOUSE`나 `COMPLETED`로 바뀌지 않고 `PENDING_PAYMENT`로 남는다. `Order.assignWarehouseStorage`도 호출되지 않는다. 이는 `processPaymentAndShipment`의 창고 분기(`OrderCommandService.java:163-172`)와 다르다.
- 배송 엔티티는 구매자가 창고 보관을 골라도 만들어진다 (`OrderCommandService.java:264-271`).
- `nav/ORDER_README.md:238-240`은 "창고 보관을 선택한 경우 주문 상태가 `IN_WAREHOUSE`로 업데이트"된다고 적는다. 코드와 다르다.
