# 질문: 구매자 배송은 운송장 등록부터 배송 완료까지 어떻게 처리되나

> 정적 코드 읽기로만 확인했다(실행·테스트 없음). 경로는 저장소 루트 기준이며, `C` 는 `src/main/java/com/fream/back` 을 뜻한다. 코드는 수정하지 않았다.

**요약**
- 운송장 등록 API(`PATCH /shipments/order/{id}/status`)는 **(a) 일반 구매 입찰 주문, (b) 즉시 구매 주문 모두 실패한다.** 주문 상태가 `IN_TRANSIT` 으로 바뀌지 못해서이며, 실패 시 아무것도 저장되지 않고 404 가 응답된다.
- 그래서 정상 흐름의 배송 완료 처리는 실제로는 시작되지 않는다. 우회 경로인 `check-status` 가 배송 상태를 `OUT_FOR_DELIVERY` 로 만들면 6시간 주기 배치가 이를 집어 가는데, 이때 **(a)는 완료 처리가 실패하고 (b)만 끝까지 간다.**
- 입찰 상태(`OrderBid`/`SaleBid`)는 배송 완료 경로(`completeOrder`)에서 `COMPLETED` 로 바뀌지 않는다. `COMPLETED` 로 바꾸는 코드는 운송장 등록 경로에만 있는데, 그 경로도 실패한다.

## 1. 운송장 등록 요청

**1-1. 진입 API**
- `PATCH /shipments/order/{shipmentId}/status`, body 는 `courier`, `trackingNumber` (`C/domain/shipment/controller/command/OrderShipmentCommandController.java:20`, `:33-34`, `:41-45`). 성공 시 본문 없는 200 (`:48`).
- 같은 컨트롤러에 `POST /{shipmentId}/check-status`(`:58-59`)와 `check-status-string`(`:103-104`)이 있어 CJ 를 즉시 조회하면서 송장을 저장하는 우회 경로도 있다.
- 이 컨트롤러와 `C/domain/shipment` 아래에는 권한 어노테이션이 없다. 보안 설정에서 `/shipments` 규칙도 찾지 못했다(검색 범위 내). "운영 측"만 호출한다는 보장은 코드에서 확인되지 않는다.

**1-2. 의도된 상태 변화 순서** (`C/domain/shipment/service/command/OrderShipmentCommandService.java:238-303`)
1. 송장 필드 저장 + 배송 상태 `IN_TRANSIT`: `OrderShipment.updateTrackingInfo` (`C/domain/shipment/entity/OrderShipment.java:41-45`). 전이 규칙 검사 없이 대입한다. `ShipmentStatus` 의 PENDING 전이 규칙(`ShipmentStatus.java:4-9`, PENDING→SHIPPED/CANCELED만 허용)을 우회한다.
2. 주문 상태 `IN_TRANSIT`: `:259-260`.
3. 구매자 알림 1건 "상품이 출발하였습니다": `:265-271`.
4. 판매 상태 `SOLD` 및 판매자 알림: `updateSaleStatusToSold` (`:276`, 구현 `:112-183`). 즉, 출발 시점에 판매가 SOLD 가 된다.
5. 창고 보관 상태 갱신: `:279-286`.
6. 입찰 `OrderBid`/`SaleBid` 를 `COMPLETED` 로: `:289`, 구현 `:412-440`. 실패 시 로그만 남긴다.

**1-3. (a)·(b) 실제 결과: 둘 다 2단계(주문 상태 전이)에서 실패한다**
- 실패 지점: `OrderShipmentCommandService.java:260` `order.updateStatus(OrderStatus.IN_TRANSIT)` → `C/domain/order/entity/Order.java:113-121`에서 `InvalidOrderStatusException` 을 던진다.
- 이유: `OrderStatus` 전이 맵에서 `IN_TRANSIT` 으로 들어가는 경로는 `SHIPMENT_STARTED` 뿐이다 (`C/domain/order/entity/OrderStatus.java:28`). 코드 어디에서도 `SHIPMENT_STARTED` 를 설정하지 않는다.
  - **(a) 일반 구매 입찰 주문**: 결제·배송 처리 후 상태는 `PREPARING` (`C/domain/order/service/command/OrderCommandService.java:112`, `:176`; Kafka 경로 `C/domain/order/service/kafka/OrderEventConsumer.java:166`, `:216-217`). `PREPARING` 의 허용 대상은 `IN_WAREHOUSE`, `SHIPMENT_STARTED` 뿐이다 (`OrderStatus.java:26`). `IN_TRANSIT` 불가.
  - **(b) 즉시 구매 주문**: `createInstantOrder` 가 `PENDING_PAYMENT` 로 만들고 (`C/domain/order/service/command/OrderCommandService.java:220`, `:244`), 결제를 처리한 뒤에도 주문 상태를 바꾸지 않는다(같은 메서드 안에 `Order.updateStatus` 호출이 없다). `PENDING_PAYMENT` 의 허용 대상은 `PAYMENT_COMPLETED`, `COMPLETED`, `IN_WAREHOUSE` 뿐이다 (`OrderStatus.java:24`). `IN_TRANSIT` 불가.
- 저장되는 것: 없다. `updateTrackingInfo` 는 `@Transactional` (`:238`)이고, `:295-301` 에서 잡힌 예외를 `ShipmentException` 으로 감싸 다시 던지므로 롤백된다. 송장 번호·택배사·`IN_TRANSIT` 변경이 모두 사라진다. 배송 행은 `PENDING`(`OrderCommandService` 가 만든 그대로)이고 송장 번호는 null, 주문 상태는 (a) `PREPARING`, (b) `PENDING_PAYMENT` 그대로. 결제 기록은 주문 서비스의 별도 흐름에서 이미 저장되어 있다.
- 응답: `ShipmentException` 은 `GlobalExceptionHandler` 에서 처리된다 (`C/global/exception/GlobalExceptionHandler.java:459-473`). 상태 코드는 `S001` 의 404 (`C/domain/shipment/exception/ShipmentErrorCode.java:12`), 본문 메시지는 에러 코드의 고정 문구 "배송 정보를 찾을 수 없습니다."이다. 실제 원인("운송장 정보 업데이트 중 오류 발생: ...")은 본문이 아니라 로그에만 남는다. 배송 정보가 없어서 실패한 것이 아니므로 응답이 원인을 잘못 가리킨다.
- 참고: 2단계를 통과했다고 가정해도 (a)는 `OrderShipmentCommandService.java:276` 의 `updateSaleStatusToSold` → `:116` `saleBidQueryService.findByOrderId` 에서 실패한다. (a)에는 연결된 `SaleBid` 가 없고, `C/domain/sale/service/query/SaleBidQueryService.java:26-29` 가 `IllegalArgumentException` 을 던진다. 그래서 `:117` 의 null 검사는 도달하지 못한다. (b)는 `SaleBid.order` 가 연결되어 있어 (`C/domain/order/service/command/OrderCommandService.java:279`) 이 지점은 통과한다.
- 참고(확인 필요): (a)의 `processPaymentAndShipment` 는 `orderBidQueryService.findById(orderId)` (`OrderCommandService.java:188`)로 `OrderBid` 를 찾는다. 파라미터가 주문 ID 인데 `findById` 는 입찰 ID 를 찾으므로, 두 ID 가 다르면 (a)의 `OrderBid` 는 `MATCHED` 가 되지 않는다. 예외는 삼켜진다.

**1-4. `check-status` 경로(같은 송장 저장을 공유)**
`updateAndCheckShipmentStatus` (`OrderShipmentCommandService.java:452-516`)는 주문 상태 검사 없이 송장을 `IN_TRANSIT` 으로 저장한 뒤 CJ 를 조회한다.
- CJ 상태 "배송중"(기본값): 473행에서 `IN_TRANSIT` 으로 저장한 뒤 497행 `shipment.updateStatus(IN_TRANSIT)` 을 호출한다. `IN_TRANSIT→IN_TRANSIT` 은 전이 규칙에 없으므로 `IllegalStateException` (`C/domain/shipment/entity/OrderShipment.java:47-55`) → 507-515행에서 `S302`(503) 로 감싸져 롤백. 즉 "배송중" 조회는 항상 실패한다.
- CJ 상태 "배송출발": `OUT_FOR_DELIVERY` 로 바뀌어 저장되고 200 으로 응답한다. **주문 상태는 건드리지 않는다.** 이것이 주문이 `PREPARING`/`PENDING_PAYMENT` 인 채로 배치 대상에 들어가는 유일한 경로다.
- CJ 상태 "배송완료": `DELIVERED` 로 바꾼 뒤 `completeOrder` (`:489`)를 호출한다. (a)는 `PREPARING→COMPLETED` 불가로 실패해 롤백, (b)는 성공 (아래 3·4 참고).

## 2. 배송 완료 감지

**2-1. 누가, 언제, 어떻게**
- 주기 실행: `@Scheduled(cron = "0 0 */6 * * *")` (`C/global/config/ShipmentBatchScheduler.java:34`). 매일 00:00, 06:00, 12:00, 18:00 에 `updateShipmentStatusesJob` 을 실행한다. 배치 인프라는 `@EnableBatchProcessing` (`C/global/config/BatchInfraConfig.java:15`). 실행 예외는 `printStackTrace` 만 한다 (`ShipmentBatchScheduler.java:41-43`).
- 대상(reader): `status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND trackingNumber IS NOT NULL`, 페이지 크기 50 (`C/domain/shipment/config/UpdateShipmentStatusesJobConfig.java:95`, `:55-58`, `:63-77`). `ORDER BY` 가 없다.
- 실제 실행되는 처리 코드: `ShipmentItemProcessor.process` (`C/domain/shipment/config/ShipmentItemProcessor.java:57`). 스텝에서 `new ShipmentItemProcessor(...)` 로 직접 생성해 쓴다 (`UpdateShipmentStatusesJobConfig.java:69-72`).
  - 사용되지 않는 비슷한 코드: `UpdateShipmentStatusesJobConfig.shipmentItemProcessor()` 빈 (`:106`, 그 안의 람다는 어디에도 연결되지 않음), 그 안의 Jsoup 파서 `parseCjLogisticsStatus` (`:186`, 호출자 없음), `OrderShipmentCommandService.updateShipmentStatuses()` (`OrderShipmentCommandService.java:309-391`, 호출자 없음).
  - Playwright 조회 유틸 `CjTrackingPlaywright.getCurrentTrackingStatus` (`C/global/utils/CjTrackingPlaywright.java:33`)는 `updateAndCheckShipmentStatus` (`OrderShipmentCommandService.java:477`)에서만 쓰인다.
- 조회 방식: 스텝 시작 시 브라우저를 연다 (`C/domain/shipment/config/BrowserManageStepListener.java:15-17`). 처리 건마다 페이지를 열고 `https://trace.cjlogistics.com/next/tracking.html?wblNo=…` 로 이동, `tbody#statusDetail tr` 을 최대 30초 기다린 뒤 마지막 행의 5번째 `td` 를 읽는다 (`ShipmentItemProcessor.java:72`, `:181`).

**2-2. 택배사 상태 → 내부 상태** (`ShipmentItemProcessor.java:220-226`)
- `"배송완료"` → `DELIVERED`
- `"배송출발"` → `OUT_FOR_DELIVERY`
- 그 외 전부 → `IN_TRANSIT` (기본값). 반품·지연 등이 모두 `IN_TRANSIT` 으로 들어간다.
- 현재 상태와 같으면 아무 것도 하지 않는다 (`ShipmentItemProcessor.java:101-104`).
- `OUT_FOR_DELIVERY` 인 건이 CJ 에서 "배송중"으로 돌아오면 `else` 분기 (`:125`)가 `OUT_FOR_DELIVERY→IN_TRANSIT` 을 시도하는데, 전이 규칙에 없어 `IllegalStateException` → 건너뜀(skip).

## 3. 배송 완료 판정 이후

처리 위치: `ShipmentItemProcessor.java:113-117`(DELIVERED 분기), 그리고 `OrderShipmentCommandService.completeOrder` (`C/domain/shipment/service/command/OrderShipmentCommandService.java:191-229`).

1. 배송 행: `IN_TRANSIT`/`OUT_FOR_DELIVERY` → `DELIVERED` (`ShipmentItemProcessor.java:113`; 전이 허용은 `ShipmentStatus.java:16-28`).
2. 주문: `completeOrder` 가 `OrderBid` 를 먼저 찾는다(없으면 `IllegalArgumentException` → S102). 그다음 주문을 `COMPLETED` 로 바꾼다 (`OrderShipmentCommandService.java:204`). 허용 전이는 `IN_TRANSIT`, `PENDING_PAYMENT`, `IN_WAREHOUSE` → `COMPLETED` 이고, `PREPARING` 은 불가 (`OrderStatus.java:24-29`).
3. 판매: `updateSaleStatusToSold` (`:208`, 구현 `:112-183`). `SaleBid` 가 있으면 `Sale.canTransitionTo(SOLD)` 일 때만 `SOLD` 로 바꾼다 (`:116-123`; 전이 규칙은 `SaleStatus.java:15-24`에서 `ON_AUCTION`, `SELLING` 만 `SOLD` 로 간다). 창고 보관이면 창고 상태 갱신 (`:126-129`). 이어서 `OrderBid` 쪽의 `Sale` 에 대해 같은 처리를 한다 (`:151-176`). 1단계에서 이미 `SOLD` 가 되었다면 두 번째 블록은 알림을 보내지 않는다.
4. 입찰: `completeOrder` 는 `OrderBid`/`SaleBid` 를 `COMPLETED` 로 **바꾸지 않는다**. `updateOrderAndSaleBidStatusToCompleted` 는 운송장 등록 경로(`:289`)에서만 호출된다. 따라서 배송 완료 경로에서는 입찰이 `MATCHED` 로 남는다.
5. 알림:
   - 구매자 1건: "[completeOrder] 주문이 완료 처리되었습니다" (`OrderShipmentCommandService.java:212-217`).
   - 구매자 1건: "[배송 완료] 상품이 배송 완료되었습니다" (`ShipmentItemProcessor.java:117` → `C/domain/notification/service/command/NotificationCommandService.java:219`). 이 메서드는 예외를 삼킨다.
   - 판매자 0~1건: "상품이 성공적으로 판매 완료되었습니다" (`OrderShipmentCommandService.java:131-138`). `Sale` 이 `SOLD` 로 전이될 때만.
   - 즉 구매자는 **2건**, 판매자는 **최대 1건**.

## 4. 주문 종류별 차이

**(a) 결제·배송 처리를 마친 일반 구매 입찰 주문**
- 운송장 등록(1-3): 실패 (주문 `PREPARING` → `IN_TRANSIT` 불가).
- `check-status` 의 "배송출발"로 배치 대상에 들어간 경우(1-4, 2): 배치가 "배송완료"를 보면 `completeOrder` 의 `Order.updateStatus(COMPLETED)` (`OrderShipmentCommandService.java:204`)에서 `PREPARING` 때문에 실패 → 예외 → `ShipmentItemProcessor` 가 감싸 던짐 → 건너뜀. 행 상태 DELIVERED 는 롤백, 알림 0건, 입찰 상태 변화 없음.
- 2단계를 통과했다고 가정해도 `updateSaleStatusToSold` 의 `SaleBid` 조회에서 실패한다 (1-3 참고).
- **결론: 끝까지 성공하지 않는다.** 배송 행은 `OUT_FOR_DELIVERY` 에 머물고 6시간마다 같은 실패를 반복한다.

**(b) 즉시 구매로 만들어진 주문**
- 운송장 등록(1-3): 실패 (주문 `PENDING_PAYMENT` → `IN_TRANSIT` 불가). 응답 404, 저장 없음.
- `check-status` "배송출발"로 배치 대상에 들어간 경우: 배치의 `completeOrder` 에서 `PENDING_PAYMENT → COMPLETED` 는 허용되므로 (`OrderStatus.java:24`) 주문 완료가 된다. `SaleBid`(`OrderCommandService.java:279`)와 `OrderBid`(`OrderBidCommandService.java:189-205`)가 모두 연결되어 있어 판매 상태 전이와 판매자 알림 (`Sale` 이 `ON_AUCTION`/`SELLING` 이면 1건)이 진행된다. 구매자에게 2건, 행은 `DELIVERED`.
- **결론: 이 경로에서는 끝까지 간다.** 다만 주문이 결제 완료 상태를 한 번도 거치지 않은 채 `COMPLETED` 가 되며, 입찰은 `MATCHED` 로 남는다.

**차이 요약**: 두 주문 모두 정상 운송장 등록은 막혀 있다. 배치까지 도달했을 때는 (a)는 주문 `PREPARING` 때문에 `COMPLETED` 전이에서 막히고, (b)는 `PENDING_PAYMENT` 가 `COMPLETED` 로 직접 갈 수 있어 완료된다.

## 5. 실패 처리 (주기 처리 중 한 건 실패)

설정: 청크 50, `faultTolerant().skip(Exception.class).skipLimit(50)` (`UpdateShipmentStatusesJobConfig.java:67-77`), 스킵 리스너 로그 (`:252-290` 근처 `shipmentSkipListener`).

- 실패한 건: `ShipmentItemProcessor` 가 예외를 던지면 (파싱 실패, CJ 조회 실패, `completeOrder` 실패, 상태 전이 실패 등) 그 청크 트랜잭션이 롤백되고, Spring Batch 가 청크를 한 건씩 다시 처리하며 실패 건만 건너뛴다. 건너뛴 건은 DB 변경이 없고, 상태는 `IN_TRANSIT`/`OUT_FOR_DELIVERY` 그대로 남아 다음 주기(최대 6시간 뒤)에 다시 조회된다. 실패 원인은 로그에만 남는다. 보관되는 "실패" 표시는 없다.
- 같은 청크의 나머지 건: 롤백 후 한 건씩 다시 처리되므로 정상 건은 그대로 반영된다. 다만 앞쪽 건은 CJ 조회를 두 번 하게 된다. (근거는 Spring Batch 의 청크 재처리 동작에 기반한 추론이며 실행해 보지는 않았다.)
- 스킵 한도: 한 스텝 실행에서 50건을 넘게 건너뛰면 스텝이 실패하고 잡이 실패한다. 나머지 건은 그 실행에서 처리되지 않으며, 다음 주기에 다시 시도된다. 스케줄러는 잡 결과를 확인하지 않는다 (`ShipmentBatchScheduler.java:40`).
- 한 가지 위험(코드 근거): reader 는 `ORDER BY` 없이 오프셋 페이지를 쓰는데 (`UpdateShipmentStatusesJobConfig.java:95`), 처리 중 `DELIVERED` 건이 집합에서 빠진다. 다음 페이지가 밀린 위치에서 읽혀 같은 실행에서 건너뛰는 건이 생길 수 있다. 실행하여 확인하지는 않았다.
- 확인하지 못한 것: 쿼리의 문자열 리터럴 `'IN_TRANSIT'` 을 `@Enumerated(STRING)` enum 필드와 비교하는 JPQL 이 현재 Hibernate 버전에서 동작하는지는 실행 없이 판단할 수 없다.
