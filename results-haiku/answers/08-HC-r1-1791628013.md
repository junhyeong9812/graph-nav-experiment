# 답: 구매자 배송은 운송장 등록부터 배송 완료까지 어떻게 처리되나

근거의 파일 경로는 모두 `src/main/java/com/fream/back/` 아래 기준이다. 코드는 수정하지 않았고 실행·테스트도 하지 않았다. 정적으로 읽은 결과다.

---

## 1. 운송장 등록 요청

**진입점.** `PATCH /shipments/order/{shipmentId}/status`, 본문 `OrderShipmentRequestDto`(courier, trackingNumber).
`domain/shipment/controller/command/OrderShipmentCommandController.java:20, 33-49`.
컨트롤러와 서비스 어디에도 호출자 권한 검사가 없다(`@PreAuthorize` 없음). "운영 측만 호출한다"는 것은 코드로 보장되지 않는다.

**성공했을 때 의도된 상태 변경 순서** (`domain/shipment/service/command/OrderShipmentCommandService.java:238-303`)

1. `OrderShipment` 상태를 IN_TRANSIT으로, 택배사·운송장 번호를 저장한다 (`:256`). 엔티티가 `ShipmentStatus` 전이표를 거치지 않고 `IN_TRANSIT`을 직접 대입한다 (`domain/shipment/entity/OrderShipment.java:41-45`).
2. `Order` 상태를 IN_TRANSIT으로 바꾼다 (`:260`).
3. 구매자에게 "상품이 출발하였습니다" 알림 1건을 만든다 (`:266-271`).
4. `updateSaleStatusToSold` 호출 → Sale을 SOLD로 바꾸고 판매자에게 알림 (`:276`, `:111-183`).
5. 창고 보관 상품이면 창고 상태를 갱신한다 (`:279-286`).
6. `OrderBid`·`SaleBid`를 COMPLETED로 바꾼다 (`:289`, `:412-440`).

설계와 실제 의미가 어긋나는 부분이 있다. 배송 **시작** 시점에 Sale을 SOLD로, 입찰을 COMPLETED로 바꾼다. 배송 완료 전에 거래가 끝난 것처럼 처리된다.

**실제 결과: 결제·배송을 마친 일반 구매 입찰 주문은 여기서 실패한다.**

- 결제·배송 처리 후 Order 상태는 PREPARING이다. 실제로 쓰이는 경로는 `POST /orders/{orderId}/process-payment-shipment` → Kafka → `OrderEventConsumer.handleOrderProcessingEvent`(`domain/order/service/kafka/OrderEventConsumer.java:55-61`) → `processCompleteOrder`(`:166-233`)다. 실배송 분기는 `:216-217`에서 PREPARING으로 바꾼다. 배송 정보는 `:181`에서 만든다.
  - 동기 메서드 `OrderCommandService.processPaymentAndShipment`(`domain/order/service/command/OrderCommandService.java:165-176`)도 PREPARING까지 가지만 호출처가 없다. 컨트롤러 호출은 주석 처리돼 있다(`domain/order/controller/command/OrderCommandController.java:91-101`).
- `Order.updateStatus`는 전이표를 검사한다(`domain/order/entity/Order.java:113-121`). PREPARING의 전이 대상은 IN_WAREHOUSE, SHIPMENT_STARTED뿐이다(`domain/order/entity/OrderStatus.java:26`). PREPARING→IN_TRANSIT은 거부된다.
- IN_TRANSIT으로 가는 전이는 SHIPMENT_STARTED에서만 가능하다(`OrderStatus.java:28`). 그런데 SHIPMENT_STARTED를 대입하는 코드가 저장소 어디에도 없다(`OrderStatus.java:13`의 선언과 `OrderQueryController.java:207`의 표시 문자열 외에는 없음). 따라서 이 경로로는 어떤 주문도 IN_TRANSIT에 도달하지 못한다.
- 거부되면 `InvalidOrderStatusException`이 던져진다. `updateTrackingInfo`의 `catch (Exception e)`가 이를 `ShipmentException(SHIPMENT_NOT_FOUND)`로 감싼다(`OrderShipmentCommandService.java:293-301`). `GlobalException`은 `RuntimeException`이므로(`global/exception/GlobalException.java:10`) `@Transactional`이 롤백된다.
- **저장되는 것: 없음.** shipment의 메모리 변경도 롤백된다. 알림은 `:266` 이후라서 만들어지지 않는다.
- **응답: HTTP 404, 코드 `S001`.** 본문 메시지는 ErrorCode의 고정 문구 "배송 정보를 찾을 수 없습니다."다(`domain/shipment/exception/ShipmentErrorCode.java:12`, `global/exception/GlobalExceptionHandler.java:49-63`). 실제 사유 `PREPARING -> IN_TRANSIT`은 로그(`OrderShipmentCommandService.java:296-297`)에만 남는다.
- 즉시 구매 주문(b)도 같은 지점에서 실패한다. 즉시 구매 주문은 PENDING_PAYMENT로 생성되고(`OrderCommandService.java:244`), 이후 Order 상태를 바꾸는 코드가 없다. PENDING_PAYMENT→IN_TRANSIT도 거부된다. 실패 메시지만 `PENDING_PAYMENT -> IN_TRANSIT`으로 다르다.

**참고: 같은 운송장을 등록하는 다른 경로 `POST /shipments/order/{shipmentId}/check-status`.** 컨트롤러 `OrderShipmentCommandController.java:58-`, 서비스 `OrderShipmentCommandService.java:451-516`.
- Order를 건드리지 않고 shipment를 IN_TRANSIT으로 만든 뒤(`:473`) CJ를 직접 조회한다.
- 조회 결과가 배송출발·배송완료가 아니면 `:497`에서 `IN_TRANSIT→IN_TRANSIT` 전이를 시도한다. 전이표에 없으므로 `IllegalStateException`이 나고, `EXTERNAL_TRACKING_SERVICE_ERROR`로 감싸져 롤백된다(`:505-514`).
- 배송출발이면 OUT_FOR_DELIVERY로 저장되고 200을 돌려준다(`:491-493`).
- 배송완료이면 `completeOrder`를 호출한다(`:483-489`). 이 경우의 결과는 4번에서 본다.

## 2. 배송 완료 감지

- **누가, 언제:** 스케줄러가 한다. `global/config/ShipmentBatchScheduler.java:34` `@Scheduled(cron = "0 0 */6 * * *")`. 6시간마다 00·06·12·18시 정각에 `updateShipmentStatusesJob`을 `jobLauncher.run`으로 실행한다(`:35-43`). 배치 인프라는 `global/config/BatchInfraConfig.java:15`의 `@EnableBatchProcessing`이다.
- **주기:** 6시간.
- **대상:** `domain/shipment/config/UpdateShipmentStatusesJobConfig.java:88-96`의 reader 쿼리. `status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND trackingNumber IS NOT NULL`, 페이지·청크 크기 50(`:51-52`).
- **실제로 실행되는 처리 코드:** `UpdateShipmentStatusesJobConfig.java:69-73`에서 `new ShipmentItemProcessor(...)`를 스텝에 넣는다. 처리 본체는 `domain/shipment/config/ShipmentItemProcessor.java:56-157`이다.
  - 헤드리스 Playwright 페이지를 열고(`:72`), 추적 URL로 이동하고(`:81-83`), `tbody#statusDetail tr`을 기다린다(`:87`).
  - 마지막 행의 5번째 `td` 텍스트를 읽는다(`:167-212`, 특히 `:181`).
- **실행되지 않는 비슷한 코드 (무시할 것):**
  - `OrderShipmentCommandService.updateShipmentStatuses()`(`:308-391`). 호출처가 없고 `CjTrackingPlaywright`를 쓴다(`:335`).
  - `UpdateShipmentStatusesJobConfig.shipmentItemProcessor()` @Bean(`:104-177`). 스텝에 연결되지 않았다.
  - `UpdateShipmentStatusesJobConfig.parseCjLogisticsStatus()`(`:186-220`). Jsoup 기반 private 메서드이고 호출처가 없다.
- **상태 문자열 → 내부 상태** (`ShipmentItemProcessor.java:220-226`)
  - "배송완료" → DELIVERED
  - "배송출발" → OUT_FOR_DELIVERY
  - 그 밖의 모든 문자열 → IN_TRANSIT
  - 파싱 결과는 trim 후 정확 일치로 비교한다(`:181`).
- **분기** (`:101-126`): 현재 상태와 같으면 아무것도 하지 않는다. 같지 않으면 DELIVERED면 3번, OUT_FOR_DELIVERY면 전이, 그 밖이면 IN_TRANSIT 전이다. 전이표에 없는 전이는 예외가 난다. 예를 들어 OUT_FOR_DELIVERY→IN_TRANSIT은 불가능하다(`domain/shipment/entity/ShipmentStatus.java:23-28`). 배송출발 뒤 "배송 중" 류 문구가 나오면 그 건은 매 주기 실패한다.

## 3. 배송 완료 판정 이후

DELIVERED 분기(`ShipmentItemProcessor.java:108-117`)의 순서다.

1. `OrderShipment`를 DELIVERED로 바꾼다(`:113`). IN_TRANSIT→DELIVERED는 허용된다(`ShipmentStatus.java:16-22`).
2. `orderService.completeOrder(orderId)`(`OrderShipmentCommandService.java:190-229`)를 호출한다.
   - OrderBid를 조회한다(`:196`).
   - Order를 COMPLETED로 바꾼다(`:204`). 허용 여부는 주문 상태에 달렸다.
   - `updateSaleStatusToSold`를 부른다(`:208`). Sale이 SELLING 또는 ON_AUCTION일 때만 SOLD로 바뀌고 판매자에게 알림이 간다(`:119`, `domain/sale/entity/SaleStatus.java:15-24`). 그 밖의 상태에서는 아무 변화 없이 debug 로그만 남긴다(`:143`).
   - 구매자에게 "[completeOrder] 주문이 완료 처리되었습니다" 알림(`:212-217`).
3. `notificationService.notifyShipmentCompleted(order)`(`ShipmentItemProcessor.java:117`, 정의 `domain/notification/service/command/NotificationCommandService.java:219-232`). 구매자에게 "[배송 완료] ..." 알림을 보낸다.
4. 청크 커밋 시 `JpaItemWriter`가 shipment를 저장한다(`UpdateShipmentStatusesJobConfig.java:241-246`).

**알림 건수.** 구매자 2건(`[completeOrder]`, `[배송 완료]`). 판매자는 Sale이 SELLING·ON_AUCTION일 때만 1건이고, 그 밖에는 0건이다.

**입찰 상태.** OrderBid와 SaleBid는 MATCHED 그대로 남는다. 배송 완료 경로에는 입찰을 COMPLETED로 바꾸는 코드가 없다. `updateOrderAndSaleBidStatusToCompleted`(`OrderShipmentCommandService.java:412-440`)는 `updateTrackingInfo`의 `:289`에서만 호출된다. 즉 입찰 COMPLETED는 배송 **등록** 시점에 설정되도록 짜였고, 배송 완료 시점에는 설정되지 않는다. 이 메서드는 private이고 모든 예외를 삼키므로(`:436-439`) 실패해도 드러나지 않는다.

## 4. 주문 종류별 차이

**전제.** 1번에서 보았듯이 현재 코드로는 (a)·(b) 모두 IN_TRANSIT에 도달하지 못한다. 아래는 "shipment가 IN_TRANSIT이고 택배사가 배송완료를 반환한다"고 가정한 조건부 분석이다.

**(a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문 → 끝까지 가지 못한다.**
- Order는 PREPARING이다(`OrderEventConsumer.java:216-217`).
- `completeOrder`의 `order.updateStatus(COMPLETED)`(`OrderShipmentCommandService.java:204`)가 거부된다. PREPARING의 전이 대상에 COMPLETED가 없다(`OrderStatus.java:26`).
- `InvalidOrderStatusException`이 `completeOrder`의 `catch`(`:221-227`)에서 `ShipmentException`으로 바뀌고, 처리기가 그대로 다시 던진다(`ShipmentItemProcessor.java:133-145`).
- 결과: 트랜잭션 롤백, shipment는 DELIVERED로 저장되지 않음, 알림 0건, 입찰·Sale 변화 0. 그 건은 스킵되고 다음 주기에 다시 시도된다.
- 실패 지점은 이 Order 전이 하나다. (a)는 SaleBid가 order와 연결돼 있으므로(`SaleBidCommandService.java:65, 82-83`) 뒤따르는 `updateSaleStatusToSold`의 조회는 통과한다.

**(b) 즉시 구매로 만들어진 주문 → 끝까지 진행된다.**
- Order는 PENDING_PAYMENT이다(`OrderCommandService.java:244`). PENDING_PAYMENT→COMPLETED는 전이표에 있으므로 허용된다(`OrderStatus.java:24`).
- SaleBid가 order와 연결돼 있으므로(`OrderCommandService.java:279`) `updateSaleStatusToSold`의 조회도 성공한다.
- Sale이 SELLING·ON_AUCTION이 아니면(즉시 판매로 만들어진 Sale은 PENDING_SHIPMENT로 시작한다. `domain/sale/service/command/SaleCommandService.java:62`) SOLD 변경과 판매자 알림은 일어나지 않는다. 에러는 없다.
- 결과: shipment DELIVERED, Order COMPLETED가 저장된다. 구매자 알림 2건이 간다. OrderBid·SaleBid는 MATCHED로 남는다.

**차이 요약.** (a)는 Order 전이에서 막혀 아무것도 저장되지 않는다. (b)는 Order 전이를 통과해 완료 처리된다. 다만 (b)의 Order가 결제 완료 없이 PENDING_PAYMENT에서 COMPLETED로 넘어간다는 점이 문제다. 결제 상태를 확인하는 코드가 이 경로에 없다. 코드상 즉시 구매 결제 후에도 Order 상태가 바뀌지 않는다.

## 5. 실패 처리

- **실패한 건:** `UpdateShipmentStatusesJobConfig.java:75-77`의 `faultTolerant().skip(Exception.class).skipLimit(50)`에 따라 스킵된다. 처리기 예외(파싱 실패, 페이지 로드 실패, 30초 타임아웃 `ShipmentItemProcessor.java:30, 78`, DELIVERED 분기 예외 등)가 나면 그 건은 쓰이지 않는다. shipment 상태는 이전 값 그대로(IN_TRANSIT 또는 OUT_FOR_DELIVERY) 남고, 6시간 뒤 다음 실행에서 다시 조회된다. 스킵 로그는 `UpdateShipmentStatusesJobConfig.java:252-267`에 남는다.
- **같은 청크의 나머지 건:** Spring Batch의 기본 fault-tolerant 동작에 따르면 예외가 난 청크 트랜잭션은 롤백되고, 그 청크를 1건씩 다시 처리한다. 실패 건만 스킵되고 나머지는 각각 커밋된다. 이 과정에서 같은 페이지를 다시 조회하므로 CJ 조회가 한 번 더 일어난다. 이 동작은 프레임워크 기본 동작을 근거로 한 것이며 실행으로 확인하지 않았다.
- **스킵 한도:** 한 번의 실행에서 스킵이 50건을 넘으면 스텝이 실패한다. 남은 건은 다음 주기까지 처리되지 않는다.
- **부수 효과:** 롤백된 알림은 DB에서 사라지지만, 실시간 전송은 `NotificationCommandService.java:57`에서 이미 나갔다. 사용자는 DB에 없는 알림을 받은 것처럼 보일 수 있다.
- **추가 위험(추정, 실행으로 검증하지 않음):** reader 쿼리에는 ORDER BY가 없고(`UpdateShipmentStatusesJobConfig.java:95`), 처리 중에 상태가 바뀌어 필터에서 빠진다. 그런데 JPA 페이지를 오프셋으로 읽는다. 그래서 일부 건이 그 실행에서 건너뛰어질 수 있다. 다음 주기에는 잡히므로 영구 누락은 아니고 지연으로 봐야 한다.

## 확인하지 못한 것

- CJ 추적 페이지의 실제 HTML 구조(마지막 행의 5번째 `td`가 상태인지)는 확인하지 못했다.
- 실제 DB의 상태 분포와 Sale 상태는 확인하지 못했다.
- 코드를 실행하거나 테스트하지 않았다. 위 판단은 정적 읽기에 근거한다.
