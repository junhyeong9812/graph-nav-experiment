# 즉시 구매는 어떻게 처리되나

요청 진입점: `POST /order-bids/instant` (`src/main/java/com/fream/back/domain/order/controller/command/OrderBidCommandController.java:89-90`).
요청 본문 `InstantOrderRequestDto` 는 `saleBidId`, `addressId`, `warehouseStorage`, `paymentRequest` 를 가진다 (`src/main/java/com/fream/back/domain/order/dto/InstantOrderRequestDto.java:20-29`).

---

## 1. 요청 경로와 처리 방식

**API 와 처리 단계**

1. 컨트롤러가 인증 이메일을 꺼낸다 (`.../order/controller/command/OrderBidCommandController.java:92`).
2. `enrichPaymentRequest` 가 결제 요청에 `userEmail` 을 넣고 `orderId` 를 `null` 로 만든다 (`.../OrderBidCommandController.java:98`, `:119-122`).
3. `OrderBidCommandService.createInstantOrderBid` 를 호출한다 (`.../OrderBidCommandController.java:101-107`). 이 메서드는 `@Transactional` 이다 (`src/main/java/com/fream/back/domain/order/service/command/OrderBidCommandService.java:118-119`).
4. 서비스 내부 순서 (`.../OrderBidCommandService.java:121-149`)
   - 입력값 검증 (`:123`, 구현 `:154-167`)
   - 구매자 조회 `userQueryService.findByEmail` (`:126`)
   - `SaleBid` 와 `Sale` 조회 (`:129`, 구현 `:172-184`)
   - `OrderCommandService.createInstantOrder` 로 주문 생성 (`:133-139`, 구현 `src/main/java/com/fream/back/domain/order/service/command/OrderCommandService.java:219-319`)
   - `OrderBid` 생성과 저장 (`:142`, 구현 `:189-207`)

**동기인가 비동기인가**: 동기다. 모든 단계가 HTTP 요청 스레드에서 한 트랜잭션으로 실행된다. 즉시 구매 호출 체인에는 Kafka 발행이 없다. 결제 대행사(PortOne) 호출도 동기 HTTP 호출이다 (`src/main/java/com/fream/back/domain/payment/portone/PortOneApiClient.java:229`, `:266`).

**응답 ID**: 응답의 `orderId` 는 **Order 의 ID 가 아니라 방금 만든 `OrderBid`(입찰)의 ID** 다. 서비스가 `OrderBid` 를 반환하고 컨트롤러가 `.getId()` 를 쓴다 (`.../OrderBidCommandController.java:101-107`). 성공 응답 메시지는 `"즉시 구매가 성공적으로 처리되었습니다."` 다 (`:109`). 변수명과 응답 필드명이 Order 를 가리키는 것처럼 보여서 혼동하기 쉽다. 구매자는 응답만으로 Order ID 를 알 수 없다.

## 3. 결제 수단별 결과와 결제 대행사 실패 시

**공통 검증** (`src/main/java/com/fream/back/domain/payment/service/command/PaymentCommandService.java:117-146`)
- 주문 ID 와 이메일이 일치하는지만 확인한다 (`:131`, `:136`).
- 금액은 `paidAmount > 0` 만 확인한다 (`:142`). **주문 금액(`saleBid.bidPrice`)과 비교하지 않는다.** 카드 결제는 클라이언트가 보낸 `paidAmount` 로 승인을 요청한다 (`:179`). 따라서 결제 금액과 주문 금액이 다를 수 있다.

**결제 유형 판별**: `paymentType` 으로 DTO 서브클래스가 정해진다 (`src/main/java/com/fream/back/domain/payment/dto/PaymentRequestDto.java:20-24`). `processPayment` 는 `CARD`, `ACCOUNT`, `GENERAL` 외 값을 받으면 예외를 던진다 (`PaymentCommandService.java:67-80`).

**카드 (`CARD`)** (`PaymentCommandService.java:157-225`)
- 저장된 카드 정보를 `paymentInfoId` 로 조회한다 (`:166`).
- PortOne 에 승인 요청을 보낸다 (`:179`).
- 응답의 `status` 가 문자열 `"success"` 일 때만 `PAID`, `isSuccess = true` 로 바꾼다 (`:203-206`). 그 밖의 경우 `Payment` 기본값인 `PENDING` 과 `isSuccess = false` 가 남는다 (`src/main/java/com/fream/back/domain/payment/entity/Payment.java:44`, `:64-68`). 실제 PortOne 응답에서 이 값이 무엇인지는 코드만으로 확인할 수 없다.
- 예외 없이 저장되면 뒤의 알림과 `Sale.SOLD` 변경까지 실행된다 (`PaymentCommandService.java:83`). 즉 **결제가 `PENDING` 이어도 주문과 판매는 확정된다.**

**대행사가 카드 결제를 실패로 응답했을 때** (`src/main/java/com/fream/back/domain/payment/portone/PortOneApiClient.java:270-274`)
1. PortOne 응답의 `code` 가 0 이 아니면 `PaymentProcessingException` 을 던진다 (`PortOneApiClient.java:270-274`).
2. `createCardPayment` 가 `PaymentException` 을 그대로 다시 던진다 (`PaymentCommandService.java:180-181`).
3. `processPayment` 가 다시 던진다 (`:89-94`). 알림과 판매 상태 변경에는 도달하지 않는다.
4. `createInstantOrder` 가 이를 `OrderPaymentProcessingFailedException` 으로 감싼다 (`OrderCommandService.java:306-308`). 이 예외는 `OrderException` 이므로 그대로 전파된다 (`:312-314`).
5. `createInstantOrderBid` 의 catch 가 `OrderException` 을 그대로 다시 던진다 (`OrderBidCommandService.java:145-148`, `:212-214`).
6. `GlobalException` 은 `RuntimeException` 이고 (`src/main/java/com/fream/back/global/exception/GlobalException.java:10`), `@Transactional` 에 `rollbackFor` 나 `noRollbackFor` 가 없으므로 **전체가 롤백된다.** 롤백되는 대상은 `Order`, `OrderItem`, `OrderShipment`, `SaleBid` 변경, `WarehouseStorage` 변경이다.
7. 응답은 `GlobalExceptionHandler` 가 에러 응답으로 바꾼다 (`src/main/java/com/fream/back/global/exception/GlobalExceptionHandler.java:49`).

PG 가 승인한 뒤에 트랜잭션이 롤백되더라도 환불을 호출하는 코드는 없다. `handleRefundIfNecessary` (`PaymentCommandService.java:341`) 와 `updatePaymentStatus` (`:498`) 는 정의만 있고 호출처가 없다.

**계좌이체 (`ACCOUNT`)** (`PaymentCommandService.java:236-279`)
- 은행 코드만 검증한다 (`:244`). PG 호출은 없다.
- `Payment` 를 `PENDING` 으로 저장한다 (`:260`).
- 예외 없이 끝나므로 주문과 판매가 확정되고, 구매자 알림은 "결제가 완료되었습니다" 라고 나간다 (`:438-443`). 실제 결제는 `PENDING` 이다.
- `PENDING` 에서 `PAID` 로 바꾸는 코드는 호출처가 없다 (`:498` 의 `updatePaymentStatus` 참고).

**일반 결제 (`GENERAL`)** (`PaymentCommandService.java:290-335`)
- `impUid` 가 비어 있지 않은지만 확인한다 (`:297-300`). PG 에 조회하거나 검증하지 않는다.
- 클라이언트가 보낸 값으로 바로 `PAID` 처리한다 (`:313-314`).

**즉시 구매가 끝까지 성공하는가**
- 카드: PG 가 `code == 0` 이고 `status == "success"` 이면 끝까지 성공한다 (`:203-206`). `code != 0` 이면 전체가 롤백된다. `code == 0` 이지만 `status` 가 다르면 응답은 성공하지만 결제는 `PENDING` 으로 남는다.
- 계좌이체: 응답은 성공하지만 결제는 `PENDING` 에서 끝나고 완료시키는 경로가 코드에 없다.
- 일반: 응답은 성공하고 결제는 `PAID` 가 된다. 단, 클라이언트 값 외에는 검증하지 않는다.

## 4. 알림 대상, 시점, 방식

발송 함수는 `PaymentCommandService.sendNotifications` 다 (`PaymentCommandService.java:434-462`). `processPayment` 안에서 동기로 실행된다 (`:83`).

- **구매자**: 카테고리 `SHOPPING`, 타입 `BID`, 내용 `"결제가 완료되었습니다. 주문 ID: {orderId}"` (`:438-443`).
- **판매자**: 같은 카테고리와 타입, 내용 `"구매자가 결제를 완료하였습니다. 판매 ID: {saleId}"` (`:449-454`).

**방식**: `NotificationCommandService.createNotification` 이 알림을 DB 에 저장하고 (`src/main/java/com/fream/back/domain/notification/service/command/NotificationCommandService.java:52-53`), 이어서 실시간 전송을 시도한다 (`:57`). 실시간 전송은 Redis 에 사용자 키가 있을 때만 WebSocket 으로 보낸다 (`:303-315`). 이메일이나 Kafka 는 쓰지 않는다.

**시점과 실패 처리**
- 알림은 트랜잭션 커밋 전에 DB 저장되고 WebSocket 으로도 나간다. WebSocket 전송은 롤백되지 않는다.
- 알림 실패는 로그만 남기고 삼킨다 (`PaymentCommandService.java:457-461`).
- 계좌이체는 결제가 `PENDING` 이어도 "결제가 완료되었습니다" 알림이 나간다 (위 3번).

## 5. 처리 후 주문의 최종 상태와 창고 보관 선택의 효과

**성공 시 최종 상태** (커밋 후)

| 엔티티 | 최종 상태 | 근거 |
|---|---|---|
| `Order` | `PENDING_PAYMENT` (바뀌지 않음) | `OrderCommandService.java:244`. 즉시 구매 경로에는 `Order.updateStatus` 호출이 없다. `updateStatus` 호출은 `processPaymentAndShipment` (`:165-176`), Kafka 소비자 (`src/main/java/com/fream/back/domain/order/service/kafka/OrderEventConsumer.java:195-217`), 배송 흐름 (`src/main/java/com/fream/back/domain/shipment/service/command/OrderShipmentCommandService.java:204`, `:260`) 에만 있다. |
| `OrderBid` | `MATCHED`, `isInstantPurchase = true` | `.../OrderBidCommandService.java:196`, `:205` |
| `SaleBid` | `MATCHED` | `OrderCommandService.java:280`. `COMPLETED` 은 배송 흐름에서만 설정된다 (`OrderShipmentCommandService.java:431`). |
| `Sale` | `SOLD` | `PaymentCommandService.java:404`, `:419` |
| `Payment` | 카드·일반 `PAID`, 카드 비정상 응답·계좌이체 `PENDING` | 3번 참고 |
| `OrderShipment` | `PENDING` | `OrderShipmentCommandService.java:67` |

주의: `PENDING_PAYMENT` 에서 허용되는 다음 상태는 `PAYMENT_COMPLETED`, `COMPLETED`, `IN_WAREHOUSE` 뿐이다 (`src/main/java/com/fream/back/domain/order/entity/OrderStatus.java:24`). 배송 쪽 `IN_TRANSIT` 전이(`OrderShipmentCommandService.java:260`)는 이 규칙에 막힌다. 배송 흐름 전체를 따라가 확인하지는 않았다.

**창고 보관 선택 (`warehouseStorage` 플래그)**

- 컨트롤러가 플래그를 서비스에 넘긴다 (`OrderBidCommandController.java:105`). 서비스도 `OrderCommandService.createInstantOrder` 에 넘긴다 (`OrderBidCommandService.java:137`).
- 그런데 `createInstantOrder` 본문은 `isWarehouseStorage` 파라미터를 읽지 않는다 (`OrderCommandService.java:219-319`). 메서드 Javadoc 과 달리 **요청 플래그는 아무 효과가 없다.**
- 실제 판단 기준은 **판매 엔티티의 `isWarehouseStorage`** 다 (`OrderCommandService.java:289-292`). 이 값은 판매를 올릴 때 정해진다 (`src/main/java/com/fream/back/domain/sale/entity/Sale.java:43`, `src/main/java/com/fream/back/domain/sale/service/command/SaleCommandService.java:107`).
  - 판매가 창고 보관이면: 구매자 플래그와 무관하게 `WarehouseStorage` 상태를 `ASSOCIATED_WITH_ORDER` 로 바꾼다 (`OrderCommandService.java:293`). 연결된 `WarehouseStorage` 가 없으면 `WarehouseStorageNotFoundException` 이 나고 (`src/main/java/com/fream/back/domain/warehouseStorage/service/query/WarehouseStorageQueryService.java:30-33`), 이는 `WarehouseStorageException` 이므로 `OrderWarehouseStorageProcessingFailedException` 으로 감싸져 전체가 롤백된다 (`OrderCommandService.java:295-297`).
  - 판매가 창고 보관이 아니면: 구매자가 플래그를 켜도 아무 변화가 없다.
- 두 경우 모두 `Order` 상태는 바뀌지 않는다. 배송 정보는 항상 생성된다 (`OrderCommandService.java:264-271`). 즉시 구매 경로에서는 `order.assignWarehouseStorage` 도 호출되지 않는다 (`OrderCommandService.java:171` 은 다른 흐름이다).

## 참고: 코드에서 확인한 빈틈 (질문 밖이지만 실제 동작에 영향)

- **이미 매칭된 판매 입찰을 막는 검사가 없다.** `getSaleBidAndValidate` 는 존재 여부와 `Sale` 연결만 본다 (`OrderBidCommandService.java:172-184`). `SaleBid.status` 는 확인하지 않는다. 같은 판매 입찰로 즉시 구매가 두 번 들어오면 두 번째 주문이 만들어지고, `SaleBid.order` 가 새 주문으로 덮인다 (`OrderCommandService.java:279`). DB 제약은 이 코드만으로 확인되지 않는다.
- **구매자와 판매자가 같은지 검사하지 않는다** (이 경로 안에서 확인 범위).
- **카드 결제 금액 검증 누락** (3번 참고).
- **환불 자동 호출 없음** (3번 참고).
