# 구매자 배송: 운송장 등록 → 배송 완료

경로 약어: `D` = `src/main/java/com/fream/back/domain`, `G` = `src/main/java/com/fream/back/global`.

## 0. 전제 (결제·배송 처리 직후의 상태)

1. 구매자 배송 정보는 `OrderShipment`(status `PENDING`)로 생성된다. `D/shipment/service/command/OrderShipmentCommandService.java:56-75`
2. 일반 구매 입찰 주문은 `PENDING_PAYMENT`로 생성된다. `D/order/service/command/OrderCommandService.java:81`
3. 결제·배송 처리의 실사용 경로는 Kafka 컨슈머 `OrderEventConsumer`다. 컨트롤러가 `orderEventProducer.sendOrderProcessingEvent`를 호출한다. `D/order/controller/command/OrderCommandController.java:54`
4. 컨슈머가 결제 → 배송 생성 → `PAYMENT_COMPLETED` → (실배송이면) `PREPARING`까지만 올린다. `D/order/service/kafka/OrderEventConsumer.java:192-195, 215-218`
   - 동일 로직의 `OrderCommandService#processPaymentAndShipment`도 실배송이면 `PAYMENT_COMPLETED` → `PREPARING`에서 끝난다. `D/order/service/command/OrderCommandService.java:175-176`
5. 따라서 (a) 실배송 일반 구매 입찰 주문은 결제·배송 처리 후 Order=`PREPARING`, OrderShipment=`PENDING`이다.
6. `OrderStatus.SHIPMENT_STARTED`로 전이시키는 코드는 어디에도 없다. enum 정의와 화면 라벨만 있다.
   - 정의: `D/order/entity/OrderStatus.java:13`, 라벨: `D/order/controller/query/OrderQueryController.java:207`
   - 전이표: `PREPARING`은 `IN_WAREHOUSE`·`SHIPMENT_STARTED`로만, `IN_TRANSIT`은 `SHIPMENT_STARTED`에서만 갈 수 있다. `D/order/entity/OrderStatus.java:26-28`

## 1. 운송장 등록 요청

### 1-1. 진입 API

- `PATCH /shipments/order/{shipmentId}/status` (`OrderShipmentRequestDto`: courier, trackingNumber)
  - `D/shipment/controller/command/OrderShipmentCommandController.java:20, 33-45`
  - 컨트롤러는 `OrderShipmentCommandService#updateTrackingInfo`를 호출한다.
- 운영용 복제 컨트롤러가 같은 서비스를 호출한다. 경로는 `/admin/shipments/order/...`, `/partner/...`, `/internal/...`, `/legacy/...`, `/settlement/...`다.
  - 예: `D/adminshipment/controller/command/AdminOrderShipmentCommandController.java:20, 33`
  - 모두 `com.fream.back.domain.shipment.service.command.OrderShipmentCommandService`를 주입받는다. `D/adminshipment/controller/command/AdminOrderShipmentCommandController.java:8, 24`
- 별도의 `POST /shipments/order/{id}/check-status`(및 `check-status-string`)도 있다. 이 경로는 1-3·4에서 다시 다룬다. `D/shipment/controller/command/OrderShipmentCommandController.java:58-94`

### 1-2. 코드가 의도한 순서 (`OrderShipmentCommandService#updateTrackingInfo`, `:238-303`)

1. courier·trackingNumber가 비어 있으면 `TRACKING_INFO_REQUIRED`. `:243-246`
2. `OrderShipment` 조회. `:249-253`
3. `OrderShipment.updateTrackingInfo`가 courier·trackingNumber를 저장하고 status를 `IN_TRANSIT`으로 직접 대입한다. 전이 검증은 없다. `D/shipment/entity/OrderShipment.java:41-45`
4. `order.updateStatus(OrderStatus.IN_TRANSIT)`. `:259-260`
5. 구매자에게 알림 1건: "상품이 출발하였습니다. 주문 ID: …" (`SHOPPING`/`BID`). `:265-271`
6. `updateSaleStatusToSold(orderId)`. `:276`
   - SaleBid 경유 Sale → `SOLD`, 창고 보관이면 창고 상태 갱신, 판매자에게 알림 "상품이 성공적으로 판매 완료되었습니다". `:112-147`
   - OrderBid 경유 Sale → `SOLD`와 판매자 알림도 시도한다. `:150-180`
7. 창고 보관 Sale이면 `updateWarehouseStatusToSold`. `:279-286`
8. `updateOrderAndSaleBidStatusToCompleted`: OrderBid·SaleBid가 `MATCHED`이면 `COMPLETED`로 바꾼다. `:289, 413-440`

### 1-3. 실배송 일반 구매 입찰 주문 (Order=`PREPARING`)은 끝까지 성공하지 않는다

- **실패 지점:** 4단계 `order.updateStatus(IN_TRANSIT)`에서 실패한다.
  - `Order#updateStatus`는 `PREPARING → IN_TRANSIT`이 전이표에 없으므로 `InvalidOrderStatusException`을 던진다. `D/order/entity/Order.java:113-120`, `D/order/entity/OrderStatus.java:26`
  - 이 예외는 `ShipmentException`이 아니므로 `catch (Exception e)`에 걸린다. `:295-302`
  - 이어서 `ShipmentException(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")`로 감싸 던진다. 실제 원인은 "상태 전환 불가"인데 코드는 SHIPMENT_NOT_FOUND(S001)로 보고한다. `:297-301`
- **저장되는 것:** 없다.
  - `@Transactional` 메서드가 RuntimeException으로 빠져나가므로 롤백된다. `:238`
  - 3단계의 courier/trackingNumber/`IN_TRANSIT` 변경도 되돌려지고 shipment는 `PENDING`에 남는다.
  - 5~8단계는 실행되지 않으므로 알림, Sale SOLD, 입찰 COMPLETED도 없다.
  - Order는 `PREPARING` 그대로다.
- **응답:** `GlobalExceptionHandler`가 `ErrorResponse`를 반환한다. `D/shipment/controller/command/OrderShipmentCommandController.java:41`에는 try/catch가 없다.
  - HTTP 404, code `S001`, message "배송 정보를 찾을 수 없습니다."(ErrorCode 기본 메시지. 커스텀 메시지는 응답에 쓰이지 않음), path = 요청 URI.
  - 근거: `G/exception/GlobalExceptionHandler.java:49-63`, `D/shipment/exception/ShipmentErrorCode.java:12`, `G/response/ErrorResponse.java:20-40`
- **요약:** 운송장 등록 API는 `PREPARING` 주문에는 항상 실패한다. 이 API로는 shipment가 `IN_TRANSIT`이 될 수 없다.
- **같은 이유로 즉시 구매 주문도 실패한다.** 즉시 구매 Order는 `PENDING_PAYMENT`에 머문다(§4). `PENDING_PAYMENT`의 허용 전이는 `PAYMENT_COMPLETED`, `COMPLETED`, `IN_WAREHOUSE`뿐이라 `IN_TRANSIT`은 거부된다. `D/order/entity/OrderStatus.java:24`

### 1-4. shipment를 `IN_TRANSIT`으로 만들 수 있는 유일한 우회로

- `check-status` 계열이 호출하는 `updateAndCheckShipmentStatus`는 `shipment.updateTrackingInfo`(→ `IN_TRANSIT`)를 먼저 호출한다. `D/shipment/service/command/OrderShipmentCommandService.java:473`
- 그 다음 CJ 조회 결과로 `IN_TRANSIT`/`OUT_FOR_DELIVERY`를 설정한다. `:491-498`
- 이 경로는 Order 상태를 건드리지 않는다. Order는 `PREPARING`(또는 `PENDING_PAYMENT`) 그대로이고, 알림도 없다.
- 이후 §2의 배치가 이 shipment를 집어 간다.

### 2-1. 누가, 언제

- `ShipmentBatchScheduler#scheduleShipmentStatusJob`이 `@Scheduled(cron = "0 0 */6 * * *")`로 실행한다. 서버 시간대 기준 매일 00:00, 06:00, 12:00, 18:00(6시간 주기)이다. `G/config/ShipmentBatchScheduler.java:34-44`

### 2-2. 대상 조회

### 2-3. 실제로 실행되는 처리 코드

- Step은 `new ShipmentItemProcessor(playwrightBrowserManager(), notificationService, orderService)`를 processor로 쓴다. `D/shipment/config/UpdateShipmentStatusesJobConfig.java:69-73`
  - 구현은 `D/shipment/config/ShipmentItemProcessor.java:57-147`이다. Playwright로 `https://trace.cjlogistics.com/next/tracking.html?wblNo=`를 열고 `tbody#statusDetail tr`의 마지막 행 5번째 td를 읽는다. `:33-35, 72-95, 181`

### 2-4. 택배사 상태 문자열 → 내부 상태 (`ShipmentItemProcessor#mapToShipmentStatus`)

|---|---|
| `"배송완료"` | `DELIVERED` |
| `"배송출발"` | `OUT_FOR_DELIVERY` |

## 4. 주문 종류별 차이

### (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문 → 끝까지 진행되지 않는다

- 상태는 Order=`PREPARING`이다. `D/order/service/kafka/OrderEventConsumer.java:215-218`
- 운송장 API(1-3)가 실패하므로 정상적으로는 shipment가 `IN_TRANSIT`이 되지 못해 배치 대상에 오르지 않는다.
- `check-status` 우회로(1-4)로 shipment가 `IN_TRANSIT`이 되어 배치가 "배송완료"를 읽는 경우를 따져 본다.
  - shipment를 `DELIVERED`로 바꾼 뒤 `completeOrder`가 `order.updateStatus(COMPLETED)`를 호출한다. `D/shipment/service/command/OrderShipmentCommandService.java:204`
  - `PREPARING → COMPLETED`는 전이표에 없어 `InvalidOrderStatusException`이 난다. `D/order/entity/OrderStatus.java:26`
  - `completeOrder`의 catch가 `ShipmentException(ORDER_NOT_FOUND_FOR_SHIPMENT)`로 감싸 던진다. `:221-228`
  - 프로세서가 이를 그대로 재던지고(`D/shipment/config/ShipmentItemProcessor.java:133-145`) 해당 건은 skip된다(§5).
- 결과: shipment=`IN_TRANSIT` 유지, Order=`PREPARING` 유지. 알림 0건이고 Sale·입찰 변경도 없다. 이 건은 매 배치마다 조회·실패를 반복한다.
- `check-status` API 자체의 `DELIVERED` 분기도 같은 `completeOrder`를 쓴다. `:489` 예외는 `ShipmentException`이므로 응답은 `ORDER_NOT_FOUND_FOR_SHIPMENT`의 404이고 본문은 없다. `D/shipment/controller/command/OrderShipmentCommandController.java:80-86`, `D/shipment/exception/ShipmentErrorCode.java:20`

### (b) 즉시 구매로 만들어진 주문 → 끝까지 진행된다 (단, 입찰 상태는 `MATCHED`)

- 생성: `createInstantOrder`가 Order를 `PENDING_PAYMENT`로 만들고 `OrderShipment`(`PENDING`)를 생성한다. 이 과정에서 Order를 `PAYMENT_COMPLETED`/`PREPARING`으로 올리지 않는다. `D/order/service/command/OrderCommandService.java:244, 264-272`
- SaleBid를 `assignOrder` + `MATCHED`로 만든다. `:279-280`
- OrderBid는 별도로 `MATCHED`, `order`/`sale` 연결, 즉시 구매 플래그와 함께 저장된다. `D/order/service/command/OrderBidCommandService.java:190-205`
- 이 주문의 shipment가 `IN_TRANSIT`이 되는 길은 `check-status` 우회로(1-4)뿐이다. 운송장 API는 `PENDING_PAYMENT → IN_TRANSIT`이 막혀 실패한다(1-3).
- 배치가 "배송완료"를 읽으면 다음 순서로 진행된다.
  1. shipment → `DELIVERED`
  2. `completeOrder`: OrderBid 존재(즉시 구매도 OrderBid를 가짐). `D/order/service/command/OrderBidCommandService.java:190-205`
  3. `PENDING_PAYMENT → COMPLETED`는 전이가 허용된다. `D/order/entity/OrderStatus.java:24`
  4. `updateSaleStatusToSold`: SaleBid는 `findByOrderId`로 조회된다(`assignOrder` 덕). Sale은 결제 시 이미 `SOLD`라 변경과 판매자 알림은 없다.
  5. 구매자 알림 2건
- 결과: shipment=`DELIVERED`, Order=`COMPLETED`, OrderBid·SaleBid는 `MATCHED` 유지, 판매자 알림 0건.

### (a)와 (b)의 차이

| | (a) 실배송 일반 구매 입찰 | (b) 즉시 구매 |
|---|---|---|
| 배송완료 판정 시 Order | `PREPARING` | `PENDING_PAYMENT` |
| `→ COMPLETED` 전이 | 불가 → 예외 → skip | 허용 |
| shipment | `IN_TRANSIT` 유지 | `DELIVERED` |
| 알림 | 0건 | 구매자 2건 |
| 입찰 | 변경 없음 | `MATCHED` 유지 |

- (a)가 실패하는 근본 원인은 어떤 코드도 `SHIPMENT_STARTED`를 거치지 않아 `PREPARING`에서 `COMPLETED`/`IN_TRANSIT`으로 갈 수 없기 때문이다.
- (b)는 `PENDING_PAYMENT → COMPLETED` 전이 규칙이 허용되어서 우연히 통과한다.
- 두 주문 모두 `MATCHED → COMPLETED` 입찰 전환 코드(`updateOrderAndSaleBidStatusToCompleted`)는 실행되지 않는다.

## 5. 실패 처리 (주기 처리 중 한 건 실패)

- Step은 `faultTolerant().skip(Exception.class).skipLimit(50)`이다. `D/shipment/config/UpdateShipmentStatusesJobConfig.java:75-77`
