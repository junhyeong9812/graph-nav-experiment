# 즉시 구매 처리 흐름

경로 접두사 `D` = `src/main/java/com/fream/back/domain/`.
대상은 `order` 도메인이다. `legacy*`, `partner*` 등은 별도 도메인이며 이 흐름에 쓰이지 않는다.

## 1. 진입 API / 처리 단계 / 동기 여부 / 응답 ID

- 진입점은 `POST /order-bids/instant`이다. 컨트롤러는 `OrderBidCommandController#createInstantOrderBid`이다.
  - 근거: `D order/controller/command/OrderBidCommandController.java:22` (`@RequestMapping("/order-bids")`), `:89-90` (`@PostMapping("/instant")`)
- 처리 단계:
  1. SecurityUtils로 이메일을 추출한다.
     - 근거: `OrderBidCommandController.java:92`
  2. `enrichPaymentRequest`가 결제 DTO에 `userEmail`을 넣고 `orderId=null`로 둔다.
     - 근거: `OrderBidCommandController.java:98`, `:119-122`
  3. `OrderBidCommandService#createInstantOrderBid`(`@Transactional`)를 호출한다.
     - 근거: `OrderBidCommandController.java:101-107`, `D order/service/command/OrderBidCommandService.java:118-119`
  4. 서비스 내부 순서:
     1. 입력 검증
        - 근거: `OrderBidCommandService.java:123`, `:154-167`
     2. 구매자 조회
        - 근거: `OrderBidCommandService.java:126`
     3. SaleBid 조회. 존재 여부와 sale 연결만 확인하고 SaleBid 상태(이미 MATCHED인지)는 검증하지 않는다.
        - 근거: `OrderBidCommandService.java:129`, `:172-184`; `D sale/service/query/SaleBidQueryService.java:25-28`
     4. `OrderCommandService#createInstantOrder`로 Order 생성, 배송정보 생성, SaleBid 매칭, 창고 상태 갱신, 결제를 처리한다.
        - 근거: `OrderBidCommandService.java:133-139`; `D order/service/command/OrderCommandService.java:219-319`
     5. 그다음 OrderBid를 만들어 저장한다.
        - 근거: `OrderBidCommandService.java:142`, `:189-207`
- **동기 처리**다. Kafka를 쓰지 않고 하나의 `@Transactional` 안에서 PortOne 호출까지 끝낸 뒤 200 OK를 반환한다.
  - 근거: `OrderBidCommandController.java:109`, `OrderCommandService.java:219`
  - 비동기(Kafka, 202 Accepted)는 `/orders/{orderId}/process-payment-shipment`뿐이다. 즉시 구매는 이 경로를 타지 않는다.
    - 근거: `D order/controller/command/OrderCommandController.java:42-69`
- **응답 ID는 Order ID가 아니라 OrderBid ID다.**
  - 컨트롤러가 `Long orderId = orderBidCommandService.createInstantOrderBid(...).getId()`로 받는데, 서비스는 `OrderBid`를 반환한다. 그래서 `.getId()`는 OrderBid의 PK다.
    - 근거: `OrderBidCommandController.java:101-107`, `OrderBidCommandService.java:119`, `:142-144`
  - 변수명과 메시지("즉시 구매가 성공적으로 처리되었습니다.")는 주문 ID처럼 보이지만 실제 값은 OrderBid ID다.
    - 근거: `OrderBidCommandController.java:109`

## 2. 생성되는 엔티티와 상태 변화 순서

`createInstantOrder` 내부 순서와 각 단계 직후 상태는 다음과 같다.

| 순서 | 동작 | 직후 상태 | 근거 |
|---|---|---|---|
| a | 주소 조회(`addressQueryService.getAddress(email, addressId)`) | 엔티티 생성 없음 | `OrderCommandService.java:238` |
| b | **Order 생성·저장** (totalAmount=saleBid.bidPrice) | `Order.status = PENDING_PAYMENT` | `OrderCommandService.java:241-247` |
| c | `paymentRequest.orderId = order.id` 설정 | - | `OrderCommandService.java:250` |
| d | **OrderItem 생성**(quantity=1, price=bidPrice) 후 order에 추가 | Order는 PENDING_PAYMENT 그대로 | `OrderCommandService.java:255-256`; `D order/service/command/OrderItemCommandService.java:45-52` |
| e | **OrderShipment 생성**(주소 DTO 값 사용) 후 order에 연결 | `ShipmentStatus.PENDING` | `OrderCommandService.java:264-271`; `D shipment/service/command/OrderShipmentCommandService.java:61-70` |
| f | **SaleBid 매칭**: `saleBid.assignOrder(order)`로 `SaleBid.status = MATCHED`, `updateStatus(MATCHED)` 후 `entityManager.flush()` | `SaleBid.status = MATCHED`, `order` 연결 | `OrderCommandService.java:279-283`; `D sale/entity/SaleBid.java:58-60`, `:66-68` |
| g | `sale.isWarehouseStorage()`(**판매자 Sale**의 플래그)가 true면 창고 상태를 `ASSOCIATED_WITH_ORDER`로 변경 | `WarehouseStorage.status = ASSOCIATED_WITH_ORDER`. Sale의 창고 레코드를 못 찾으면 예외로 전체 롤백 | `OrderCommandService.java:291-293`; `D warehouseStorage/service/command/WarehouseStorageCommandService.java:117-133`; `D warehouseStorage/service/query/WarehouseStorageQueryService.java:30-32` |
| h | **Payment 생성**(`paymentCommandService.processPayment`). 결제수단별 결과는 3번 참조 | 카드 성공/일반 `PAID`, 계좌이체/카드 비성공 응답 `PENDING` | `OrderCommandService.java:305` |
| i | (결제 내부) **Sale 상태를 `SOLD`로 변경**. `sale.updateStatus`는 전이 검증이 없다. | `Sale.status = SOLD` | `D payment/service/command/PaymentCommandService.java:83`, `:388-405`; `D sale/entity/Sale.java:73-75` |
| j | **OrderBid 생성·저장**: `status=MATCHED`, `isInstantPurchase=true`, user=구매자, sale=Sale | `OrderBid.status = MATCHED` | `OrderBidCommandService.java:192-206`; `D order/entity/OrderBid.java:60-82`, `:97-99` |

- 새로 만들어지는 엔티티는 Order, OrderItem, OrderShipment, Payment(Card/Account/General 중 하나), OrderBid, Notification(구매자·판매자 각 1건)이다.
  - Notification 근거: `PaymentCommandService.java:438-455`
- 기존 엔티티의 상태 변화 순서는 `SaleBid: PENDING→MATCHED`, `(선택) WarehouseStorage: →ASSOCIATED_WITH_ORDER`, `Sale: →SOLD`다.
  - 근거: `SaleBid.java:37`, `OrderCommandService.java:279-293`, `PaymentCommandService.java:419`
- **Order 상태는 이 흐름에서 전혀 전이되지 않는다.**
  - `createInstantOrder`는 `order.updateStatus(...)`를 호출하지 않고, `PAYMENT_COMPLETED`로 바꾸는 코드는 Kafka 컨슈머와 `processPaymentAndShipment`에만 있다.
    - 근거: `OrderCommandService.java:219-319`, `D order/service/kafka/OrderEventConsumer.java:195`, `OrderCommandService.java:165`
- `order.assignPayment(payment)`도 호출되지 않는다. `Payment.assignOrder`는 Payment 쪽 FK만 채운다.
  - 근거: `OrderCommandService.java:305`, `D payment/entity/Payment.java:47-50`
- 상태 전이 규칙은 `D order/entity/OrderStatus.java:22-33`, `D order/entity/Order.java:113-121`에 있다.

## 3. 결제 수단별 결과 / 끝까지 성공 여부 / 카드 실패 시

결제 유형은 JSON의 `paymentType`(CARD/ACCOUNT/GENERAL)으로 하위 DTO가 결정되고 `processPayment`가 switch 한다.
- 근거: `D payment/dto/PaymentRequestDto.java:20-25`, `:74-81`; `PaymentCommandService.java:67-80`

공통 검증은 orderId 일치, 이메일 일치, `paidAmount > 0`뿐이다. **결제 금액이 `bidPrice`/`totalAmount`와 같은지는 검증하지 않는다.**
- 근거: `PaymentCommandService.java:131-145`

| 수단 | 처리 | 결과 Payment | 근거 |
|---|---|---|---|
| CARD | 저장된 PaymentInfo로 PortOne `processCardPayment` 호출 | 응답 `status=="success"`이면 `PAID`+`isSuccess=true`. **그 외 응답이면 PENDING·isSuccess=false로 저장되고 예외 없음** | `PaymentCommandService.java:166-208`; `Payment.java:39`, `:44` |
| ACCOUNT | 은행명 검증 후 PG 호출 없이 저장 | `PENDING`, `isSuccess=false` (입금 확인 로직 없음) | `PaymentCommandService.java:244-262` |
| GENERAL | `impUid`만 있으면 PG 재검증 없이 저장 | 즉시 `PAID`, `isSuccess=true`, paymentDate 기록 | `PaymentCommandService.java:297-314` |

- **즉시 구매의 끝까지 성공 여부**:
  - 어떤 수단이든 예외가 없으면 `createInstantOrder`가 order를 반환하고 OrderBid가 만들어져 HTTP 200 "성공"이 나간다.
    - 근거: `OrderCommandService.java:311`, `OrderBidCommandController.java:109`
  - 하지만 이 흐름은 `payment.isSuccess()`를 검사하지 않는다. Kafka 컨슈머 경로는 검사한다.
    - 근거: `OrderEventConsumer.java:174-176` (대조)
  - 계좌이체(PENDING)나 카드 비성공 응답(PENDING)이어도 Sale은 `SOLD`가 되고 알림도 나간다.
    - 근거: `PaymentCommandService.java:83`, `:416-419`
  - Order는 항상 `PENDING_PAYMENT`로 남는다(2번 참조).
- **PG(PortOne)가 카드 결제를 실패로 응답할 때**는 응답 형태에 따라 둘로 갈린다.
  1. **HTTP 비정상 또는 응답 `code != 0`**일 때:
     - `PaymentProcessingException`이 발생한다.
       - 근거: `D payment/portone/PortOneApiClient.java:270-275`
     - `createCardPayment`와 `processPayment`가 이를 전파한다.
       - 근거: `PaymentCommandService.java:179-184`, `:218-219`, `:89-94`
     - `createInstantOrder`가 `OrderPaymentProcessingFailedException`으로 감싼다.
       - 근거: `OrderCommandService.java:305-309`
     - `OrderBidCommandService`가 이를 그대로 던진다.
       - 근거: `OrderBidCommandService.java:145-146`, `:212-214`
     - `@Transactional` 롤백으로 Order, OrderItem, Shipment, SaleBid 매칭, 창고 상태, Sale 변경이 모두 취소된다. OrderBid는 생성되지 않고 클라이언트는 오류 응답을 받는다.
       - 근거: `OrderCommandService.java:219`, `OrderBidCommandService.java:118`
     - 통신 오류(`RestClientException`)는 `PaymentApiException`이 되며 `@Retryable`로 최대 3회 재시도 대상이다.
       - 근거: `PortOneApiClient.java:288-290`, `:69` 이하의 `@Retryable` 설정(카드 결제 메서드는 `:226-228`)
  2. **`code == 0`이지만 `response.status`가 "success"가 아닌**(예: failed) 경우:
     - 예외가 나지 않는다. 성공으로 보고 CardPayment를 `PENDING`/`isSuccess=false`로 저장한다.
       - 근거: `PaymentCommandService.java:203-208`
     - 이후 판매자·구매자 알림 발송과 `Sale=SOLD` 처리까지 진행되어 **HTTP 200 "즉시 구매 성공"으로 응답**한다.
       - 근거: `PaymentCommandService.java:83`, `:403-405`, `:416-419`, `OrderBidCommandController.java:109`

## 4. 알림 대상 / 시점 / 방식

- 알림 수신자는 결제 처리 중(`processPayment`→`notifyUsersAndUpdateSaleStatus`→`sendNotifications`) 두 명이다.
  - **구매자**: "결제가 완료되었습니다. 주문 ID: {orderId}"
    - 근거: `PaymentCommandService.java:436-443`
  - **판매자**(`sale.getSeller()`): "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}"
    - 근거: `PaymentCommandService.java:447-454`
  - 둘 다 `NotificationCategory.SHOPPING`, `NotificationType.BID`이다.
    - 근거: `PaymentCommandService.java:440-441`
- **시점**: 결제 Payment가 저장된 직후, OrderBid 생성보다 앞이며 같은 트랜잭션 안에서 동기적으로 보낸다.
  - 이 시점에 `order.getOrderBid()`는 null이라 `saleBidQueryService.findByOrderId`로 SaleBid→Sale을 찾아 보낸다.
    - 근거: `PaymentCommandService.java:388-403`, `OrderCommandService.java:305` vs `OrderBidCommandService.java:142`
  - 결제 성공 여부와 무관하게 발송된다. 카드 비성공 응답이나 계좌이체 PENDING에서도 "결제가 완료되었습니다" 알림이 나간다.
- **방식**:
  - `NotificationCommandService#createNotification`이 DB에 `Notification`을 저장한다.
    - 근거: `D notification/service/command/NotificationCommandService.java:44-54`
  - 그다음 Redis 키 `WebSocket:User:{email}`가 있을 때만 WebSocket `/user/queue/notifications`로 실시간 푸시한다. 연결이 없으면 저장만 된다.
    - 근거: `NotificationCommandService.java:37-38`, `:57`, `:303-322`
  - Kafka나 이메일 발송은 즉시 구매 경로에 없다. `OrderEventConsumer`의 WebSocket/Kafka 알림은 비동기 `process-payment-shipment` 경로 전용이다.
    - 근거: `OrderEventConsumer.java:96`, `:287-324`
- 알림 전송 실패는 로그만 남기고 삼킨다.
  - 근거: `PaymentCommandService.java:457-461`, `:421-425`

## 5. 최종 주문 상태 / 창고 보관 선택 시 차이

- **최종 주문 상태는 `PENDING_PAYMENT`(결제 대기)다.**
  - 이름과 로그는 "즉시 구매 완료"를 말하지만, 이 경로에서 Order 상태는 `PENDING_PAYMENT`로 만들어진 뒤 변경되지 않는다.
    - 근거: `OrderCommandService.java:244`
  - `PAYMENT_COMPLETED`/`PREPARING`/`COMPLETED` 전환은 없다.
    - 근거: `OrderCommandService.java:219-319`
  - 같이 만들어지는 상태는 `OrderShipment=PENDING`, `OrderBid=MATCHED`, `SaleBid=MATCHED`, `Sale=SOLD`, Payment는 수단/응답에 따라 `PAID` 또는 `PENDING`이다.
- **구매자의 "창고 보관"(`warehouseStorage`) 선택은 즉시 구매에서 아무 효과가 없다.**
  - 컨트롤러가 `requestDto.isWarehouseStorage()`를 `isWarehouseStorage` 인자로 넘긴다.
    - 근거: `OrderBidCommandController.java:105`, `OrderBidCommandService.java:137`, `OrderCommandService.java:221`
  - `createInstantOrder`는 이 인자를 본문에서 전혀 사용하지 않는다. `IN_WAREHOUSE`나 `createOrderStorage`는 호출되지 않는다.
    - 근거: `OrderCommandService.java:222-318`
  - 창고 관련 분기는 **판매자 Sale의 `isWarehouseStorage`** 플래그뿐이다. 이 경우 구매자 선택과 무관하게 기존 판매자 창고 레코드가 `ASSOCIATED_WITH_ORDER`로 바뀐다.
    - 근거: `OrderCommandService.java:291-293`, `D sale/entity/Sale.java:43`
  - 구매자용 `WarehouseStorage` 신규 생성, Order `IN_WAREHOUSE` 전이, `COMPLETED` 처리는 즉시 구매가 아니라 `processPaymentAndShipment`/Kafka 컨슈머 경로에만 있다.
    - 근거: `OrderCommandService.java:163-172`, `OrderEventConsumer.java:197-211`, `D warehouseStorage/service/command/WarehouseStorageCommandService.java:33-57`
  - 따라서 창고 보관을 선택하든 안 하든 즉시 구매의 결과 Order 상태는 같다(`PENDING_PAYMENT`).
