# 구매자 배송: 운송장 등록 → 배송 완료

경로 약어: `D` = `src/main/java/com/fream/back/domain`, `G` = `src/main/java/com/fream/back/global`.
구매자 배송 엔티티는 `OrderShipment`(`D/shipment/entity/OrderShipment.java:16`)이다. 아래는 모두 기본 `shipment` 도메인 기준이다. `admin*/internal*/legacy*/partner*/settlement*` 쪽은 같은 코드를 복제한 것이다.

## 사전: 결제·배송 처리 후 상태

- `OrderCommandService#processPaymentAndShipment`가 `OrderShipment`를 `PENDING`으로 만든다 (`D/shipment/service/command/OrderShipmentCommandService.java:56-60`, 호출 `D/order/service/command/OrderCommandService.java:148`).
- 실배송(창고 보관이 아닌 경우)이면 주문은 `PAYMENT_COMPLETED → PREPARING`에서 멈춘다 (`D/order/service/command/OrderCommandService.java:174-176`). `SHIPMENT_STARTED`나 `IN_TRANSIT`으로 가는 코드는 어디에도 없다.
- 즉시 구매(`createInstantOrder`)는 주문을 `PENDING_PAYMENT`로 만들고 (`OrderCommandService.java:~244`) 결제 후에도 상태를 바꾸지 않는다. 결제 서비스에는 `Order.updateStatus` 호출이 없다.

## 1. 운송장 등록 요청

### 1-1. API
- `PATCH /shipments/order/{shipmentId}/status`, 본문 `{courier, trackingNumber}` (`D/shipment/controller/command/OrderShipmentCommandController.java:21,29-45`, DTO `D/shipment/dto/OrderShipmentRequestDto.java`).
- 컨트롤러가 `OrderShipmentCommandService#updateTrackingInfo`를 호출한다 (`OrderShipmentCommandController.java:41`).
- 참고로 `POST /shipments/order/{id}/check-status`와 `/check-status-string`은 등록과 동시에 CJ 조회까지 하는 별도 API다 (`OrderShipmentCommandController.java:68,112`).

### 1-2. 의도된 상태 변경 순서와 알림
순서는 `D/shipment/service/command/OrderShipmentCommandService.java:241-300`이다.
1. courier나 trackingNumber가 비면 `TRACKING_INFO_REQUIRED` (`:244-247`).
2. `OrderShipment`를 조회해 `updateTrackingInfo`로 택배사·운송장을 저장하고 shipment 상태를 `IN_TRANSIT`으로 바꾼다 (`:256`, 엔티티 `OrderShipment.java:41-45`).
3. `Order.updateStatus(IN_TRANSIT)` (`:260`).
4. 구매자(`order.getUser()`)에게 알림 1건 "상품이 출발하였습니다. 주문 ID: …" (`:265-270`).
5. `updateSaleStatusToSold(orderId)` (`:276`). 이 안에서 `Sale`을 `SOLD`로 바꾸고 창고 보관이면 창고 상태도 바꾼다 (`:116-125`). 판매자에게 알림 "상품이 성공적으로 판매 완료되었습니다" (`:133-138`). OrderBid 쪽 Sale에 대해서도 같은 알림을 낸다 (`:164-169`).
6. 창고 보관 상품이면 창고 상태를 `SOLD`로 갱신한다 (`:279-285`).
7. `updateOrderAndSaleBidStatusToCompleted`로 OrderBid·SaleBid를 `MATCHED → COMPLETED`로 바꾼다 (`:289`, `:413-432`). 내부 예외는 삼키고 로그만 남긴다 (`:436-438`).

즉 운송장 등록 시점에 이미 "출발" 알림과 "판매 완료" 처리, 입찰 `COMPLETED`까지 앞당겨 하도록 짜여 있다. 배송 완료 시점이 아니다.

### 1-3. 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문: 성공하지 못한다
- **실패 지점**: 3단계 `order.updateStatus(OrderStatus.IN_TRANSIT)` (`OrderShipmentCommandService.java:260`).
  - 주문은 `PREPARING`이다. `PREPARING`에서 허용되는 다음 상태는 `{IN_WAREHOUSE, SHIPMENT_STARTED}`뿐이다 (`D/order/entity/OrderStatus.java:26`).
  - `IN_TRANSIT`은 `SHIPMENT_STARTED`에서만 갈 수 있다 (`OrderStatus.java:28`).
  - 따라서 `Order.updateStatus`가 `InvalidOrderStatusException`을 던진다 (`D/order/entity/Order.java:113-121`).
- **예외 변환**: `catch (Exception e)`가 이를 `ShipmentException(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")`으로 감싼다 (`OrderShipmentCommandService.java:295-301`).
- **저장되는 것**: 없다. `ShipmentException`은 `RuntimeException`(`G/exception/GlobalException.java:10`)이고 메서드가 `@Transactional`(`:240`)이므로 전체 롤백된다.
  - 2단계에서 메모리상 바꾼 courier/trackingNumber/`IN_TRANSIT`도 DB에 남지 않는다.
  - 구매자·판매자 알림도 아직 생성되기 전이다(4단계 이전).
  - shipment는 `PENDING`, 주문은 `PREPARING` 그대로다.
- **설령 `Order.updateStatus`를 통과해도** 5단계에서 막힌다. 일반 입찰 주문에는 `SaleBid.order`가 연결되지 않는다. `SaleBid.assignOrder`는 즉시 구매에서만 호출된다 (`OrderCommandService.java:279`). `SaleBidQueryService#findByOrderId`는 없으면 null이 아니라 `IllegalArgumentException`을 던진다 (`D/sale/service/query/SaleBidQueryService.java:26-29`). `updateSaleStatusToSold`의 첫 줄(`:116`)이 try 밖이므로 그대로 위로 전파된다.
- **응답**: `GlobalExceptionHandler#handleShipmentException`이 `ErrorResponse(code="S001", message=ErrorCode 고정 메시지 "배송 정보를 찾을 수 없습니다.", status=404, path)`로 응답한다 (`G/exception/GlobalExceptionHandler.java:459-472`, `D/shipment/exception/ShipmentErrorCode.java:12`). HTTP 404이고, 상세 메시지(`e.getMessage()`)는 본문에 쓰지 않는다.

### 1-3b. 참고: 즉시 구매 주문도 같은 API로는 실패한다
- `PENDING_PAYMENT`에서 `IN_TRANSIT`은 허용되지 않는다 (`OrderStatus.java:24`). 같은 404 / S001로 롤백된다.

## 2. 배송 완료 감지

### 2-1. 누가·언제·어떻게
- 주체는 `ShipmentBatchScheduler`다 (`G/config/ShipmentBatchScheduler.java:13-45`).
- `@Scheduled(cron = "0 0 */6 * * *")`로 6시간마다(00/06/12/18시 정각) `updateShipmentStatusesJob`을 `JobLauncher.run`으로 실행한다 (`:34-40`).
- 예외는 `printStackTrace`만 한다 (`:41-43`).
- 사용자가 배송 완료를 직접 알리는 경로는 없다. 단건 즉시 조회 API(`check-status`)는 운영자 수동 호출이다.

### 2-2. 주기·대상·실제 실행 코드
- **주기**: 6시간 (위 cron).
- **대상**: 리더 쿼리 `SELECT s FROM OrderShipment s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL`. 페이지 크기·청크 크기는 50이다 (`D/shipment/config/UpdateShipmentStatusesJobConfig.java:51,87-97`).
- **실제 실행 코드** (비슷한 코드가 여러 곳에 있다):
  - 실제로 쓰이는 것: `ShipmentItemProcessor.process` (`D/shipment/config/ShipmentItemProcessor.java:57-157`).
    - 스텝이 `.processor(new ShipmentItemProcessor(...))`로 직접 연결한다 (`UpdateShipmentStatusesJobConfig.java:69-73`).
    - Playwright로 CJ 페이지(`https://trace.cjlogistics.com/next/tracking.html?wblNo=`)를 열고 `tbody#statusDetail tr`의 마지막 행 5번째 `td` 텍스트를 읽는다 (`ShipmentItemProcessor.java:28-29,72-94,167-191`).
  - 실행되지 않는 것 1: `UpdateShipmentStatusesJobConfig#shipmentItemProcessor()`의 람다 빈 (`:104-177`). `.processor(...)`에 연결되지 않았다. 안의 `parseCjLogisticsStatus`(`:186`)도 미사용이다.
  - 실행되지 않는 것 2: `OrderShipmentCommandService#updateShipmentStatuses()` (`:309-394`). 호출처가 없다 (`@Scheduled`도 없다). 이름은 "주기적으로 업데이트"지만 실제로는 죽은 코드다.
  - 실행되지 않는 것 3: `admin*/internal*/legacy*/partner*/settlement*shipment`의 JobConfig·Processor 복제본. 스케줄러는 `@Qualifier("updateShipmentStatusesJob")` Job 빈만 받는다 (`ShipmentBatchScheduler.java:19-21`).
    - 이 복제본들도 같은 이름의 `updateShipmentStatusesJob()` `@Bean`을 정의한다 (예: `D/adminshipment/config/AdminUpdateShipmentStatusesJobConfig.java:55-57`). `application*.yml`에 `allow-bean-definition-overriding` 설정이 없다. Spring Boot 3.4.1 기본값이면 빈 이름 충돌이 날 수 있으나, 코드만으로는 실제 기동 결과를 단정하지 않는다.
    - 여기서는 도메인 `shipment`의 구현을 실행되는 것으로 본다.
- 조회 결과가 "배송완료"가 아닌 건 상태를 되돌리지 않는다. 같은 상태면 그대로 반환한다 (`ShipmentItemProcessor.java:101-105`).

### 2-3. 택배사 상태 문자열 → 내부 상태
`ShipmentItemProcessor#mapToShipmentStatus` (`ShipmentItemProcessor.java:220-226`):

| 택배사 문자열 | 내부 `ShipmentStatus` |
| --- | --- |
| `"배송완료"` | `DELIVERED` |
| `"배송출발"` | `OUT_FOR_DELIVERY` |
| 그 외 모든 값 (집화처리, 간선상차, 배송중 등) | `IN_TRANSIT` |

- 전이 규칙은 `ShipmentStatus#canTransitionTo`가 강제한다 (`D/shipment/entity/ShipmentStatus.java:16-27`). `IN_TRANSIT`에서는 `DELIVERED`로, `OUT_FOR_DELIVERY`에서는 `DELIVERED`로 갈 수 있다. `DELIVERED`는 종단이다 (`:29-34`).
- `OrderShipment#updateStatus`는 규칙을 어기면 `IllegalStateException`을 던진다 (`OrderShipment.java:47-55`).
- `OUT_FOR_DELIVERY` 상태에서 "그 외" 문자열이 오면 `IN_TRANSIT`으로 되돌리려 해서 전이 불가 예외가 난다 (`ShipmentItemProcessor.java:123-126`, 전이표 `ShipmentStatus.java:23-27`).

## 3. 배송 완료 판정 이후 (`newStatus == DELIVERED`)

### 3-1. 엔티티 상태 변경 순서 (`ShipmentItemProcessor.java:108-117`, 이후 writer)
1. `OrderShipment.updateStatus(DELIVERED)` (`:113`).
2. `OrderShipmentCommandService#completeOrder(orderId)` (`:116`, 본문 `OrderShipmentCommandService.java:190-226`):
   - `OrderBid`를 `findByOrderId`로 조회한다. 없으면 예외 (`:196-197`).
   - `Order.updateStatus(COMPLETED)` (`:204`). `IN_TRANSIT`, `IN_WAREHOUSE`, `PENDING_PAYMENT`에서만 허용된다 (`OrderStatus.java:24,27,29`).
   - `updateSaleStatusToSold(orderId)` (`:208`). `Sale`이 `canTransitionTo(SOLD)`이면 `SOLD`로 바꾸고 판매자에게 알림을 낸다 (`:116-138`).
   - 구매자에게 알림 "[completeOrder] 주문이 완료 처리되었습니다. 주문 ID: …" (`:211-217`).
3. `NotificationCommandService#notifyShipmentCompleted(order)` (`ShipmentItemProcessor.java:117`): 구매자에게 "[배송 완료] 상품이 배송 완료되었습니다. 주문 ID: …" (`D/notification/service/command/NotificationCommandService.java:219-233`). 내부 예외는 삼킨다.
4. `JpaItemWriter`가 shipment를 저장한다 (`UpdateShipmentStatusesJobConfig.java:74,239-246`).

### 3-2. 알림 건수
- 구매자: 2건 ("[completeOrder] …" + "[배송 완료] …").
- 판매자: `Sale`이 `SOLD`로 전이 가능할 때만 1건. 단, 결제 시점에 이미 `SOLD`가 되어 있으면 0건이다 (아래 3-3).
- 배치 경로에는 `OrderShipmentCommandService.java:359`의 "상품이 배송 완료되었습니다" 알림이 쓰이지 않는다. 그건 죽은 `updateShipmentStatuses()` 안에 있다.

### 3-3. 주문 입찰·판매 입찰 상태
- **`OrderBid`·`SaleBid`는 배송 완료 판정에서 바뀌지 않는다.**
  - `completeOrder`는 `OrderBid`를 조회만 하고 상태를 바꾸지 않는다 (`OrderShipmentCommandService.java:196-208`).
  - `COMPLETED`로 바꾸는 `updateOrderAndSaleBidStatusToCompleted`는 운송장 등록 경로(`:289`)에서만 호출된다.
  - 따라서 배치로 완료돼도 입찰은 `MATCHED`로 남는다. 메서드 이름·구조가 암시하는 "배송 완료 시 입찰 COMPLETED"와 다르다.
- `Sale`은 `canTransitionTo(SOLD)`가 참일 때만 `SOLD`로 바뀐다. 허용 출발 상태는 `ON_AUCTION`, `SELLING`이다 (`D/sale/entity/SaleStatus.java:97-98`). `SOLD`는 전이 불가다 (`:99`).
- 결제 단계에서 이미 `Sale`을 `SOLD`로 바꾼다. 즉시 구매는 `SaleBid → sale.updateStatus(SOLD)`이고 (`D/payment/service/command/PaymentCommandService.java:~395-405`), 일반 입찰은 `orderBid.getSale()`이 있으면 `SOLD`로 바꾼다 (`:~410-420`). 호출은 `processPayment`의 `notifyUsersAndUpdateSaleStatus` (`:83`)다.
  - 그래서 배송 완료 시점에는 `canTransitionTo(SOLD)`가 거짓이 되어 `Sale`은 그대로이고 판매자 알림도 가지 않는 것이 보통이다.

## 4. 주문 종류별 차이

### (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문: 끝까지 진행되지 않는다
- 주문 상태가 `PREPARING`이다 (사전 항목 참조).
- 1-3에서 본 대로 운송장 등록이 롤백되므로 shipment가 `IN_TRANSIT`에 도달하지 못하고 배치 대상(`IN_TRANSIT/OUT_FOR_DELIVERY` + 운송장 있음)에 들어가지 않는다.
- 설령 shipment만 `IN_TRANSIT`/`DELIVERED`인 상태로 3의 처리에 들어가도 (예: DB를 직접 수정한 경우):
  - `completeOrder`의 `Order.updateStatus(COMPLETED)`가 `PREPARING → COMPLETED` 불가로 `InvalidOrderStatusException`을 던진다 (`OrderStatus.java:26`).
  - 이를 `ShipmentException(ORDER_NOT_FOUND_FOR_SHIPMENT)`으로 감싼다 (`OrderShipmentCommandService.java:221-226`).
  - 주문이 `IN_TRANSIT`이었다 해도 `updateSaleStatusToSold`의 `SaleBid` 조회에서 `IllegalArgumentException`이 나서 같은 래핑으로 실패한다 (`SaleBidQueryService.java:26-29`, `OrderShipmentCommandService.java:116`).
- 결과: shipment `DELIVERED` 설정, 주문 `COMPLETED`, 구매자 알림 모두 청크 롤백으로 반영되지 않는다. 해당 건은 스킵 처리된다 (5 참조).

### (b) 즉시 구매로 만든 주문: 3의 처리가 끝까지 진행된다 (단, 도달 조건 필요)
- 즉시 구매는 `OrderBid`(`isInstantPurchase`, `MATCHED`, order·sale 연결, `OrderBidCommandService.java:189-206`)와 `SaleBid.order` 연결(`OrderCommandService.java:279`)을 모두 만든다. 그래서 `findByOrderId` 두 조회가 모두 성공한다.
- 주문은 `PENDING_PAYMENT`이고, `PENDING_PAYMENT → COMPLETED`는 허용된다 (`OrderStatus.java:24`). 그래서 `completeOrder`가 통과한다.
- 결과:
  - shipment `DELIVERED`, 주문 `COMPLETED`.
  - 구매자 알림 2건.
  - `Sale`은 결제 시점에 이미 `SOLD`라 판매자 알림 없음.
  - `OrderBid`·`SaleBid`는 `MATCHED` 유지.
- 도달 조건: 배치 대상이 되려면 shipment가 `IN_TRANSIT`이고 운송장이 있어야 한다. 등록 API는 주문 상태가 `PENDING_PAYMENT`라서 `IN_TRANSIT` 전이에서 막힌다 (1-3b). 그래서 정상 API 흐름만으로는 (b)도 배치 대상이 되지 못한다.
- 정리하면 (a)는 3의 처리에서 실패하고, (b)는 처리 자체는 성공한다. 둘 다 운송장 등록 단계에서 먼저 막히므로 실서비스 경로로는 배송 완료에 이르지 못한다.

## 5. 실패 처리 (주기 처리 중 한 건이 실패할 때)

- 스텝은 `faultTolerant().skip(Exception.class).skipLimit(50)`이다 (`UpdateShipmentStatusesJobConfig.java:75-77`, 상수 `:52`).
- 처리 중 예외는 `ShipmentItemProcessor`에서 `ShipmentException`으로 통일해 던지고 (`ShipmentItemProcessor.java:133-145`), 스킵 리스너가 로그만 남긴다 (`UpdateShipmentStatusesJobConfig.java:251-287`).
- **그 건**: 스킵된다. 해당 청크는 롤백된 뒤 항목 단위로 재처리되어 실패 건만 제외되고, 실패 건의 변경(shipment `DELIVERED`, order `COMPLETED`, 알림)은 DB에 반영되지 않는다.
  - `completeOrder`가 같은 트랜잭션에서 `ShipmentException`을 던지면 chunk 트랜잭션이 rollback-only가 된다.
  - 상태가 그대로이므로 6시간 뒤 같은 건이 다시 조회·실패한다.
- **나머지 건**: 계속 처리되어 정상 건은 반영된다.
- **한계**: 스킵이 50건을 넘으면 `SkipLimitExceededException`으로 스텝(잡)이 실패하고 남은 건은 처리되지 않는다.
- 외부 조회는 건마다 새 Playwright 페이지를 만들며 `TIMEOUT_MS = 30000`이다 (`ShipmentItemProcessor.java:30,72-78`). 실패(타임아웃·파싱 오류·행 없음)는 `TRACKING_HTML_PARSE_ERROR`/`EXTERNAL_TRACKING_SERVICE_ERROR`로 위와 같이 스킵된다.
- 스케줄러 쪽은 `jobLauncher.run` 예외를 `printStackTrace`로만 처리하고 재시도는 없다 (`ShipmentBatchScheduler.java:41-43`).
