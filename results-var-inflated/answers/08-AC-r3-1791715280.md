# 구매자 배송: 운송장 등록 → 배송 완료

경로 약어: `S` = `src/main/java/com/fream/back/domain/shipment`, `O` = `.../domain/order`, `N` = `.../domain/notification`, `P` = `.../domain/payment`, `G` = `src/main/java/com/fream/back/global`.
(`legacy*/internal*/partner*/settlement*/admin*` 도메인은 거의 복사본이다. 아래는 공용 엔티티·서비스를 실제로 쓰는 `shipment` 도메인 기준이다.)

## 사전 사실 (결제·배송 처리 직후의 상태)

- 결제 후 `OrderShipment`는 `PENDING`으로 생성된다. — `S/service/command/OrderShipmentCommandService.java:61-68`
- 일반 구매 입찰 주문의 실배송(`isWarehouseStorage=false`) 처리는 `PENDING_PAYMENT → PAYMENT_COMPLETED → PREPARING` 에서 끝난다. — `O/service/command/OrderCommandService.java:174-176` (Kafka 경로도 동일: `O/service/kafka/OrderEventConsumer.java:195,215-217`)
  - `SHIPMENT_STARTED`는 코드 어디에서도 설정하지 않는다 (`OrderStatus.SHIPMENT_STARTED` 대입 grep 결과 없음; 표시 문자열만 `O/controller/query/OrderQueryController.java:207`).
- 이 경로에서 `OrderBid`는 `MATCHED`로 올라간다. — `O/service/command/OrderCommandService.java:187-190`
- 즉시 구매 주문은 `createInstantOrder`에서 `PENDING_PAYMENT`로 만들어진 뒤 상태가 한 번도 바뀌지 않는다 (배송정보 생성·SaleBid 매칭·결제만 수행). — `O/service/command/OrderCommandService.java:220-311`
  - `OrderBid`는 `MATCHED` + `isInstantPurchase=true`로 생성한다. — `O/service/command/OrderBidCommandService.java:187-206`
  - 결제 시점에는 `order.getOrderBid()`가 아직 null이라 SaleBid 경로를 타고 `Sale`이 곧바로 `SOLD`가 된다. — `P/service/command/PaymentCommandService.java:83, 388-405` (OrderBid는 결제 이후 생성: `OrderBidCommandService.java:132-142`)
- 상태 전이 규칙
  - 주문: `PREPARING → {IN_WAREHOUSE, SHIPMENT_STARTED}`, `PENDING_PAYMENT → {PAYMENT_COMPLETED, COMPLETED, IN_WAREHOUSE}`, `IN_TRANSIT → {COMPLETED}`. — `O/entity/OrderStatus.java:24-31`
  - 위반 시 `InvalidOrderStatusException`. — `O/entity/Order.java:113-121`
  - 배송: `IN_TRANSIT → {OUT_FOR_DELIVERY, DELAYED, CANCELED, DELIVERED}` (자기 자신으로는 불가), `OUT_FOR_DELIVERY → {DELIVERED, FAILED_DELIVERY, CANCELED}`. — `S/entity/ShipmentStatus.java:16-28`

## 1. 운송장 등록 요청

### 1-1. 어느 API
- `PATCH /shipments/order/{shipmentId}/status` (body `OrderShipmentRequestDto{courier, trackingNumber}`) → `OrderShipmentCommandService#updateTrackingInfo`. — `S/controller/command/OrderShipmentCommandController.java:20,33` (`@RequestMapping("/shipments/order")`, `@PatchMapping("/{shipmentId}/status")`)
- 운영용 복사본 `PATCH /admin/shipments/order/{shipmentId}/status`도 같은 `shipment` 서비스를 호출한다. — `src/main/java/com/fream/back/domain/adminshipment/controller/command/AdminOrderShipmentCommandController.java:8,18-19,32-45`
- 보조 API: `POST .../{shipmentId}/check-status`, `.../check-status-string`는 택배사 조회를 즉시 수행하는 `updateAndCheckShipmentStatus` 호출. — `S/controller/command/OrderShipmentCommandController.java:58,103`, `S/service/command/OrderShipmentCommandService.java:452-516`
- 보안 설정에 해당 경로의 permitAll은 없고 `anyRequest().authenticated()`만 적용된다. — `G/config/security/SecurityConfig.java:51-52`

### 1-2. 코드가 의도한 상태 변경 순서와 알림 (`updateTrackingInfo`, `OrderShipmentCommandService.java:238-303`)
1. 택배사/운송장 공백 검사 → 실패 시 `TRACKING_INFO_REQUIRED`. (:243-246)
2. `OrderShipment` 조회 후 `shipment.updateTrackingInfo(courier, trackingNumber)`: 택배사·운송장 저장, 배송 상태를 무조건 `IN_TRANSIT`으로 설정. (:249-256; `S/entity/OrderShipment.java:41-45`)
3. `order.updateStatus(OrderStatus.IN_TRANSIT)`. (:259-260)
4. 구매자에게 알림 "상품이 출발하였습니다. 주문 ID: …" (SHOPPING/BID). (:265-271)
5. `updateSaleStatusToSold(orderId)`: `Sale`을 `SOLD`로, 창고 상품이면 창고 상태 갱신, 판매자에게 알림 "상품이 성공적으로 판매 완료되었습니다…". (:276; 본문 :112-183)
6. 창고 보관 `Sale`이면 창고 상태를 한 번 더 갱신. (:279-286)
7. `updateOrderAndSaleBidStatusToCompleted`: `OrderBid`·`SaleBid`가 `MATCHED`이면 `COMPLETED`. (:289; 본문 :413-440)

즉 의도상 "운송장 등록 시점에 이미 주문 IN_TRANSIT + 판매 SOLD + 입찰 COMPLETED"까지 한꺼번에 처리하는 구조이며, 배송 완료 이전에 판매 완료 처리와 판매자 알림이 나간다.

### 1-3. 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문은 끝까지 성공하나? → 아니오
- 실패 지점: 3단계 `order.updateStatus(OrderStatus.IN_TRANSIT)` (`OrderShipmentCommandService.java:260`).
  - 주문은 `PREPARING`이고 `PREPARING`에서는 `IN_WAREHOUSE`/`SHIPMENT_STARTED`로만 갈 수 있다 (`OrderStatus.java:26`). 따라서 `Order.updateStatus`가 `InvalidOrderStatusException("상태 전환이 허용되지 않습니다: PREPARING -> IN_TRANSIT")`을 던진다 (`Order.java:113-121`).
  - 이 코드를 우회하는 경로가 없다: `SHIPMENT_STARTED`를 세팅하는 코드가 없다.
- 예외 처리: `catch (Exception e)`가 받아 `ShipmentException(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")`로 감싸 다시 던진다. (:293-302) — 실제 원인은 "배송 없음"이 아니라 주문 상태 전이 위반인데 에러코드가 `SHIPMENT_NOT_FOUND`로 잘못 붙는다.
- 저장되는 것: 없음. 서비스 메서드가 `@Transactional`(:238)이고 `ShipmentException`은 `RuntimeException`(`G/exception/GlobalException.java:10`)이므로 롤백된다. 2단계에서 메모리상으로 바꾼 택배사·운송장·`IN_TRANSIT`도 DB에 남지 않는다 (배송은 `PENDING` 유지, 주문은 `PREPARING` 유지). 알림은 4단계 이전에 실패하므로 구매자·판매자 모두 0건이다.
- 응답: `updateTrackingInfo` 컨트롤러는 try/catch가 없어 `GlobalExceptionHandler#handleGlobalException`이 처리하며, `ErrorResponse(code="S001", message="배송 정보를 찾을 수 없습니다.", status=404, path)`가 HTTP 404로 나간다. — `S/exception/ShipmentErrorCode.java:12`, `G/exception/GlobalExceptionHandler.java:49-63`
- 참고(같은 이유로 실패): 즉시 구매 주문(`PENDING_PAYMENT`)도 `PENDING_PAYMENT → IN_TRANSIT`은 허용되지 않아(`OrderStatus.java:24`) 같은 404로 실패한다.
- 참고(만약 3단계를 통과해도 막히는 곳): 일반 입찰 주문엔 `SaleBid`가 없어 5단계의 `saleBidQueryService.findByOrderId`가 null이 아니라 `IllegalArgumentException`을 던진다 (`SaleBidQueryService.java:26-28`; 호출은 `OrderShipmentCommandService.java:116`, 널 체크 :117은 의미 없음). 같은 catch로 같은 404가 된다.
- 참고(`check-status` 보조 API의 부작용): 이 API는 주문 상태를 건드리지 않으므로 택배사·운송장 저장 및 `IN_TRANSIT` 후 `OUT_FOR_DELIVERY`(배송출발 문자열)일 때는 커밋된다. 그 외 문자열이면 `IN_TRANSIT → IN_TRANSIT` 전이 불가(`ShipmentStatus.java:16-21`)로 `EXTERNAL_TRACKING_SERVICE_ERROR`가 되어 롤백된다 (`OrderShipmentCommandService.java:473, 491-498, 505-515`). 따라서 정상적으로 `IN_TRANSIT`이 DB에 남는 경로는 사실상 없다.

## 2. 배송 완료 감지

### 2-1. 누가·언제·어떻게
- 주체: `ShipmentBatchScheduler`(`@Component`)가 스프링 배치 잡 `updateShipmentStatusesJob`을 `jobLauncher.run`으로 실행한다. — `G/config/ShipmentBatchScheduler.java:13-44`
- 주기: `@Scheduled(cron = "0 0 */6 * * *")` = 6시간마다 정각(00·06·12·18시, 서버 타임존). — `G/config/ShipmentBatchScheduler.java:34`
  - 스케줄링 활성화: `@EnableScheduling` 선언 예 `domain/event/scheduler/EventStatusScheduler.java:22`.
  - 예외는 `printStackTrace()`로만 삼킨다. (:41-43)
- 즉시 확인 경로(수동): 위 `check-status` API.

### 2-2. 조회 대상
- Reader: `SELECT s FROM OrderShipment s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL`, 페이지 크기 50. — `S/config/UpdateShipmentStatusesJobConfig.java:87-97` (`CHUNK_SIZE=50` :51)

### 2-3. 실제 실행되는 처리 코드
- 같은 이름의 `@Bean Job updateShipmentStatusesJob()`이 `shipment`, `adminshipment`, `internalshipment`, `legacyshipment`, `partnershipment`, `settlementshipment` 6곳에 있다 (`*UpdateShipmentStatusesJobConfig.java:55`). 스케줄러는 `@Qualifier("updateShipmentStatusesJob")`로 이름만 지정한다. — `G/config/ShipmentBatchScheduler.java:19-21`
  - 설정에 `allow-bean-definition-overriding`이 없다(리소스 yml 및 java 전체 grep 무결과). 스프링 부트 기본값에서는 동일 빈 이름 충돌로 기동이 실패할 수 있다. 기동이 된다고 가정하면 기준 구현은 `shipment` 도메인의 것이다(공용 `OrderShipmentCommandService`·`NotificationCommandService`를 직접 사용하는 쪽). 나머지 5곳은 알림 서비스와 리포지토리 클래스만 다른 복제본이다 (예: `adminshipment/config/AdminShipmentItemProcessor.java:3,25`).
- 이 잡의 Step의 processor는 `shipmentItemProcessor()` 빈이 아니라 `new ShipmentItemProcessor(playwrightBrowserManager(), notificationService, orderService)`이다. — `S/config/UpdateShipmentStatusesJobConfig.java:69-73`
  - `shipmentItemProcessor()` 빈(:104-177)과 `parseCjLogisticsStatus`(:186)는 Step에 연결되지 않은 죽은 코드다.
  - `OrderShipmentCommandService#updateShipmentStatuses`(:309-391)도 호출하는 곳이 없는 죽은 코드다 (grep 결과 정의만 존재).
- 실제 실행 코드: `S/config/ShipmentItemProcessor.java:56-146` (파일 전체 약 210줄) (`process`). 흐름: Playwright 페이지 생성(:72) → CJ 대한통운 `trace.cjlogistics.com/next/tracking.html?wblNo=…` 이동·`tbody#statusDetail tr` 대기 → HTML 파싱(:94, 상태 텍스트는 마지막 행 5번째 `td`, :181) → 매핑.
- Step 구성: chunk 50, `faultTolerant().skip(Exception.class).skipLimit(50)`, writer는 `JpaItemWriter`, 리스너로 브라우저 열기/닫기. — `S/config/UpdateShipmentStatusesJobConfig.java:66-81`

## 3. 배송 완료 판정 이후 (`newStatus == DELIVERED`, `ShipmentItemProcessor.java:108-118`)

0. 현재 상태와 매핑 결과가 같으면 아무 것도 하지 않고 반환 (:101-104).
1. `orderShipment.updateStatus(DELIVERED)` — 메모리 변경, writer가 flush. (:113)
2. `orderService.completeOrder(orderId)` (:116; 본문 `OrderShipmentCommandService.java:190-229`)
   1. `OrderBid` 조회 (:196).
   2. `order.updateStatus(OrderStatus.COMPLETED)` (:204).
   3. `updateSaleStatusToSold(orderId)` (:208):
      - `SaleBid`(주문에 연결된) 조회 → `Sale`이 `SOLD`로 전이 가능하면 `SOLD` + 판매자 알림 1건 (:116-141).
      - `OrderBid` 기반 `Sale`도 전이 가능하면 `SOLD` + 판매자 알림 1건 (:150-172).
   4. 구매자에게 알림 "[completeOrder] 주문이 완료 처리되었습니다. 주문 ID: …" (:211-217).
3. `notificationService.notifyShipmentCompleted(order)` → 구매자에게 "[배송 완료] 상품이 배송 완료되었습니다. 주문 ID: …" (:117; `N/service/command/NotificationCommandService.java:219-234`).

### 알림 건수 (판정 시점에 배치가 만드는 것)
- 구매자: 2건 ("[completeOrder] …" + "[배송 완료] …").
- 판매자: `Sale`이 아직 `SOLD`가 아니고 전이 가능할 때만 최대 1~2건 (SaleBid 경로 + OrderBid 경로가 각각 따로 판단). 이미 `SOLD`이면 0건 (4-(b) 참고).

### 입찰 상태
- 배치(`completeOrder`)는 `OrderBid`·`SaleBid`의 상태를 바꾸지 않는다. `COMPLETED`로 바꾸는 `updateOrderAndSaleBidStatusToCompleted`는 `updateTrackingInfo`에서만 호출된다 (:289, private :413). 따라서 입찰들은 `MATCHED`로 남는다.

## 4. 주문 종류별 차이

### (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문 → 끝까지 진행되지 않음
- 주문이 `PREPARING`이라 `completeOrder`의 `order.updateStatus(COMPLETED)`(:204)가 `InvalidOrderStatusException`을 던진다 (`PREPARING`의 허용 전이에 `COMPLETED` 없음: `OrderStatus.java:26`).
- `completeOrder`의 `catch (Exception)`이 `ShipmentException(ORDER_NOT_FOUND_FOR_SHIPMENT, "주문 완료 처리 중 오류 발생…")`으로 감싸 던진다 (:221-227). 에러코드가 "주문 없음"이지만 실제 원인은 상태 전이 위반.
- 결과: 프로세서에서 예외 → Step의 skip 대상. 배송 `DELIVERED`·주문 `COMPLETED`·판매 `SOLD`·알림 전부 반영되지 않고 롤백. 배송은 `IN_TRANSIT`/`OUT_FOR_DELIVERY`로 남아 6시간마다 재조회되며 매번 같은 실패가 반복된다. `notifyShipmentCompleted`는 `completeOrder` 뒤라 호출되지 않는다.
- 단, 현재 코드상 이런 배송이 `IN_TRANSIT`으로 DB에 들어가는 길 자체가 1-3에서 막혀 있다(운송장 등록 롤백). `check-status`로 `OUT_FOR_DELIVERY`를 저장한 경우에만 배치 대상이 된다.

### (b) 즉시 구매로 만들어진 주문 → 끝까지 진행됨 (조건: 배송이 배치 대상 상태에 있을 때)
- 주문이 `PENDING_PAYMENT`이고 `PENDING_PAYMENT → COMPLETED`는 허용된다 (`OrderStatus.java:24`). 중간 상태(`PREPARING`/`IN_TRANSIT`)를 건너뛰고 바로 `COMPLETED`가 된다.
- 판매: `Sale`은 결제 때 이미 `SOLD`(`PaymentCommandService.java:404`)이므로 `SOLD → SOLD` 전이 불가(`SaleStatus.java:38`) → 판매 상태 변경 없음, 판매자 알림 없음 (SaleBid 경로 :119 / OrderBid 경로 :156 모두 스킵).
- 구매자 알림 2건은 (a)와 달리 정상 발송. 입찰: `OrderBid`·`SaleBid`는 `MATCHED` 유지.
- 요약: (a)는 실패(전부 롤백, 반복 재시도), (b)는 배송 `DELIVERED` + 주문 `COMPLETED` + 구매자 알림 2건으로 완료. 단, (b)도 운송장 등록 API로는 `IN_TRANSIT`에 오를 수 없다(1-3 참고 사항).

## 5. 실패 처리 (주기 처리 중 한 건이 실패)
- 프로세서가 던진 예외는 `ShipmentException`으로 감싸져 전파 (`ShipmentItemProcessor.java:133-147`), Step이 `skip(Exception.class)`, `skipLimit(50)`로 처리한다 (`UpdateShipmentStatusesJobConfig.java:75-77`).
- 해당 건: 건너뛰기(skip). 청크 트랜잭션이 롤백되어 그 건의 `DELIVERED`·주문 `COMPLETED`·알림이 DB에 남지 않고, `SkipListener`가 로그만 남긴다 (`UpdateShipmentStatusesJobConfig.java:252-286`). DB 상태는 그대로이므로 다음 실행(6시간 뒤)에 다시 조회된다.
- 나머지 건: 계속 처리·저장된다. 청크(50건) 롤백 후 Spring Batch가 항목 단위로 재처리하며 실패한 항목만 제외하고 커밋한다 (재처리 시 프로세서가 다시 CJ를 조회).
- 한계: 스킵이 50건을 넘으면 `SkipLimitExceededException`으로 Step이 실패하고 남은 건은 그 회차에서 처리되지 않는다. 실패는 `ShipmentBatchScheduler`의 `catch`에서 `printStackTrace()`만 한다 (:41-43).
- 참고: 죽은 코드인 `updateShipmentStatuses`(:309-391)는 건별 try/catch로 계속 진행하는 설계였으나 호출되지 않는다.
