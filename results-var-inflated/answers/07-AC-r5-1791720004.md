# 즉시 구매 처리 흐름 (실제 코드 동작 기준)

경로 약어: `D` = `src/main/java/com/fream/back/domain`

## 1. 진입 API, 처리 단계, 동기/비동기, 응답 ID

**API**: `POST /order-bids/instant` (`D/order/controller/command/OrderBidCommandController.java:22` base `/order-bids`, `:89` `@PostMapping("/instant")`).
요청 DTO는 `InstantOrderRequestDto` — saleBidId, addressId, warehouseStorage, paymentRequest (`D/order/dto/InstantOrderRequestDto.java:20-29`).

**처리 단계 (전부 한 요청 스레드, 하나의 `@Transactional`)**
1. 컨트롤러가 JWT에서 이메일을 꺼내고(`OrderBidCommandController.java:92`) 결제 요청에 userEmail 주입, orderId는 null로 초기화 (`:119-122`).
2. `OrderBidCommandService#createInstantOrderBid` (`D/order/service/command/OrderBidCommandService.java:118-149`): 입력 검증(`:123`) → 구매자 조회(`:126`) → SaleBid/Sale 조회(`:129-130`) → `OrderCommandService#createInstantOrder` 호출(`:133`) → OrderBid 생성·저장(`:142`).
3. `OrderCommandService#createInstantOrder` (`D/order/service/command/OrderCommandService.java:219-319`): 주소 조회(`:238`) → Order 생성·저장(`:241-247`) → `paymentRequest.setOrderId(order.getId())`(`:250`) → OrderItem 생성(`:255`) → OrderShipment 생성(`:264`) → SaleBid 매칭(`:279-283`) → (판매자 창고 보관이면) 창고 상태 변경(`:291-293`) → 결제(`:305`).
4. 결제 후 알림 전송과 Sale 상태 변경은 `PaymentCommandService#processPayment` 안에서 일어난다 (`D/payment/service/command/PaymentCommandService.java:83`).

**동기 처리다.** Kafka를 쓰지 않는다. 컨트롤러가 서비스를 직접 호출하고(`OrderBidCommandController.java:101-107`) 완료 후 `200 OK`와 "즉시 구매가 성공적으로 처리되었습니다."를 반환한다(`:109`).
Kafka 비동기 경로(`POST /orders/{orderId}/process-payment-shipment`, 202 Accepted, `D/order/controller/command/OrderCommandController.java:42-69`, `D/order/service/kafka/OrderEventConsumer.java:55-110`)는 이미 만들어진 주문의 결제·배송 단계용 별개 API이며 즉시 구매 흐름에서는 호출되지 않는다.

**응답 ID는 Order ID가 아니라 OrderBid ID다.** 변수 이름은 `orderId`지만(`OrderBidCommandController.java:101`) `createInstantOrderBid(...)`가 반환한 `OrderBid`에 `.getId()`를 호출한 값이다(`:107`; 반환 타입 `OrderBid`: `OrderBidCommandService.java:119`, 반환 `:144`).

## 2. 새로 만들어지는 엔티티와 상태 변화 순서

생성 순서와 직후 상태 값:

| 순서 | 동작 | 근거 | 직후 상태 |
|---|---|---|---|
| 1 | `Order` 생성·저장 | `OrderCommandService.java:241-247` | Order.status = `PENDING_PAYMENT`, totalAmount = saleBid.bidPrice (`:243-244`) |
| 2 | `OrderItem` 생성 | `OrderCommandService.java:255-256` | — |
| 3 | `OrderShipment` 생성 | `OrderCommandService.java:264-271`, 상태 `D/shipment/service/command/OrderShipmentCommandService.java:67` | ShipmentStatus = `PENDING` |
| 4 | 기존 `SaleBid` 매칭: `assignOrder(order)` + `updateStatus(MATCHED)` + flush | `OrderCommandService.java:279-283`, `D/sale/entity/SaleBid.java:58-61, 66-68` | SaleBid.status = `MATCHED`, saleBid.order = 새 Order |
| 5 | (Sale.isWarehouseStorage가 true일 때만) 판매자 창고 보관 상태 변경 | `OrderCommandService.java:291-293`, `D/warehouseStorage/service/command/WarehouseStorageCommandService.java:117-140` | WarehouseStorage.status = `ASSOCIATED_WITH_ORDER` (`D/warehouseStorage/entity/WarehouseStatus.java`) |
| 6 | `Payment`(Card/Account/General) 생성·저장 | `PaymentCommandService.java:67-80` | 결제 수단별로 다름 (3번 참고). 기본값은 status=`PENDING`, isSuccess=false (`D/payment/entity/Payment.java:39, 44`) |
| 7 | 알림 전송 후 `Sale.status = SOLD` | `PaymentCommandService.java:391-404` | Sale.status = `SOLD` |
| 8 | `OrderBid` 생성·저장 (instantPurchase 플래그) | `OrderBidCommandService.java:192-206` | OrderBid.status = `MATCHED` (`:196`) |

- 7번에서 `order.getOrderBid()`는 아직 null이다(OrderBid가 8번에서 만들어짐). 그래서 `saleBidQueryService.findByOrderId`로 SaleBid를 찾아 그 Sale을 쓰는 분기를 탄다(`PaymentCommandService.java:388-406`).
- `Sale.updateStatus`는 전이 검증 없이 값을 대입한다(`D/sale/entity/Sale.java:73-75`). 그래서 SaleStatus와 무관하게 `SOLD`로 바뀐다.
- 구매자의 Order 상태는 `PENDING_PAYMENT`에서 바뀌지 않는다. 이 흐름에서 `order.updateStatus(...)`를 호출하는 곳이 없다(`OrderCommandService.java:219-319`).

## 3. 결제 수단별 결과, 끝까지 성공하는가, 카드 실패 응답

분기: `PaymentCommandService.java:67-80`. 모든 수단에서 결제 요청의 orderId·이메일 일치와 금액 > 0 검증을 거친다(`:117-146`). 금액이 SaleBid 가격과 같은지는 검증하지 않는다.

- **카드(CARD)**: PortOne 호출 `portOneApiClient.processCardPayment` (`PaymentCommandService.java:179`).
  - 응답 `status`가 `"success"`일 때만 `PAID` + `isSuccess=true` (`:203-206`). 이어서 저장(`:208`).
  - PortOne 응답이 HTTP 200이 아니거나 `code != 0`이면 `PaymentProcessingException`이 던져진다(`D/payment/portone/PortOneApiClient.java:270-275`).
  - 통신 오류는 `PaymentApiException`이고 `@Retryable` 3회 시도(`PortOneApiClient.java:224-228, 288-290`).
- **계좌이체(ACCOUNT)**: PortOne을 호출하지 않는다. 은행명만 검증(`:243-248`) 후 `AccountPayment`를 만들고 `updateStatus(PaymentStatus.PENDING)`을 호출한다(`:260`). 그런데 `Payment.updateStatus`는 `canTransitionTo`가 false면 `IllegalStateException`을 던지고(`Payment.java:70-76`), `PENDING`에서 갈 수 있는 상태는 `PAID`뿐이다(`D/payment/entity/PaymentStatus.java:12-13`). 생성자가 만든 초기 상태가 이미 `PENDING`이므로(`Payment.java:44`) 이 호출은 항상 예외다. 예외는 `PaymentProcessingException`으로 바뀌어 전파된다(`PaymentCommandService.java:274-277`). 따라서 **계좌이체 즉시 구매는 항상 실패**한다.
- **일반 결제(GENERAL)**: 클라이언트가 보낸 impUid가 비어 있지 않으면 PG 검증 없이 `isSuccess=true`, `PAID`로 저장(`:297-314`). 항상 성공한다.

**끝까지 성공하는가**: 카드(PG가 성공 응답)와 일반 결제는 응답 200까지 간다. 단, 성공해도 Order는 `PENDING_PAYMENT`에 머문다(2번). 결제 상태는 `order.assignPayment`로 Order에 연결되지도 않는다(`createInstantOrder`에서 `assignPayment` 미호출, `OrderCommandService.java:305`).

**PG가 카드 결제를 "실패"로 응답할 때** (HTTP 200, `code == 0`이지만 `response.status != "success"`인 경우):
1. 예외가 없다. `CardPayment`가 그대로 저장되고 status는 `PENDING`, isSuccess는 `false`다(`PaymentCommandService.java:203-208`, `Payment.java:39, 44`).
2. `processPayment`의 반환값을 `createInstantOrder`가 검사하지 않는다(`OrderCommandService.java:305`). Kafka 경로의 `payment.isSuccess()` 검사(`OrderEventConsumer.java:174-176`)와 달리 여기에는 없다.
3. `notifyUsersAndUpdateSaleStatus`가 결제 성공 여부와 무관하게 실행되어 구매자·판매자에게 "결제가 완료되었습니다" 알림을 보내고 Sale을 `SOLD`로 바꾼다(`PaymentCommandService.java:83, 404, 438-454`).
4. OrderBid가 `MATCHED`로 저장되고 컨트롤러는 200 + "즉시 구매가 성공적으로 처리되었습니다."를 응답한다(`OrderBidCommandService.java:196`, `OrderBidCommandController.java:109`).
5. 결과: 결제 실패인데 SaleBid `MATCHED`, Sale `SOLD`, OrderBid `MATCHED`, Order `PENDING_PAYMENT`, Payment `PENDING`/isSuccess=false로 남는다. 롤백되지 않는다.

반대로 PG가 `code != 0`이거나 HTTP 오류를 내면 예외가 `OrderPaymentProcessingFailedException`(`OrderCommandService.java:306-308`, 코드 `ORD005`, HTTP 500: `D/order/exception/OrderErrorCode.java:44`)으로 전파되어 트랜잭션 전체가 롤백된다(Order, SaleBid 매칭 등 모두 취소).

## 4. 알림 대상과 전달 방식

- **구매자**: "결제가 완료되었습니다. 주문 ID: {orderId}" — `NotificationCategory.SHOPPING`, `NotificationType.BID` (`PaymentCommandService.java:438-443`).
- **판매자**(`sale.getSeller()`): "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}" — 같은 카테고리·타입 (`:447-454`).
- 순서: 구매자 알림 → 판매자 알림 → 그 다음 `sale.updateStatus(SOLD)` (`:403-404`).

**전달 방식**: 동기 호출이며 결제 처리와 같은 트랜잭션 안에서 실행된다. `NotificationCommandService#createNotification`이 DB에 알림을 저장하고(`D/notification/service/command/NotificationCommandService.java:52-54`), 이어서 실시간 전송을 시도한다(`:57`). 실시간 전송은 Redis 키 `WebSocket:User:{email}`가 있을 때(WebSocket 접속 중인 사용자)만 STOMP `convertAndSendToUser(email, "/queue/notifications", dto)`로 보낸다(`:303-313`). 접속 중이 아니면 저장만 하고 끝난다(`:320-322`). 알림 생성 실패는 로그만 남기고 삼킨다(`PaymentCommandService.java:457-461`). Kafka 알림 이벤트나 주문 완료 WebSocket 알림(`OrderEventConsumer#sendSuccessNotification`)은 이 경로에서 발행되지 않는다. 그 코드는 Kafka 경로 전용이다.

카드 결제 실패(PG가 failed 응답)여도 알림은 나간다(3번).

## 5. 최종 주문 상태와 창고 보관 선택 시 차이

**최종 주문 상태는 `PENDING_PAYMENT`다.** `Order`는 `PENDING_PAYMENT`로 만들어지고(`OrderCommandService.java:244`) 이후 상태 변경이 없다. `PAYMENT_COMPLETED`, `PREPARING`, `COMPLETED`로 바뀌는 코드는 `OrderCommandService#processPaymentAndShipment`(`:165-177`)와 Kafka `OrderEventConsumer`(`:195-217`)에만 있고 즉시 구매 흐름은 둘 다 호출하지 않는다. 메서드 이름·응답 메시지가 "처리되었습니다"라고 말해도 실제 주문 상태는 결제 대기다.

**구매자가 `warehouseStorage=true`를 선택해도 달라지는 것이 없다.**
- `isWarehouseStorage` 파라미터는 `createInstantOrder` 시그니처에만 있고(`OrderCommandService.java:221`) 본문에서 한 번도 쓰이지 않는다.
- 구매자 창고 보관 엔티티를 만드는 `createOrderStorage`(`WarehouseStorageCommandService.java:33`)와 IN_WAREHOUSE 전이는 즉시 구매 흐름에서 호출되지 않는다.
- 창고 관련 동작은 구매자 요청이 아니라 **판매자 쪽 `Sale.isWarehouseStorage`** 로 결정된다: true이면 기존 창고 보관 기록의 상태만 `ASSOCIATED_WITH_ORDER`로 바뀐다(`OrderCommandService.java:291-293`). 이 기록이 없으면 `findBySale`이 예외를 던지는 구조라 주문 전체가 실패(롤백)할 수 있다(`WarehouseStorageCommandService.java:127`, `OrderCommandService.java:295-301`).
- 구매자 창고 보관 선택이 상태 전이(`PAYMENT_COMPLETED → PREPARING → IN_WAREHOUSE → COMPLETED`)로 이어지는 것은 `process-payment-shipment` 경로에서만이다(`OrderCommandService.java:163-172`, `OrderEventConsumer.java:197-213`). 즉시 구매 API에서는 `warehouseStorage` 값이 컨트롤러에서 서비스로 전달만 되고 무시된다(`OrderBidCommandController.java:105`).
