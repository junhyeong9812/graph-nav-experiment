# 즉시 구매 처리 흐름 분석

경로 접두사: `src/main/java/com/fream/back/domain` (이하 `D/`로 표기). 주 흐름은 order / payment / sale / notification 도메인이다.

## 요약 (핵심 결론)
- 동기 처리다. HTTP 요청 하나가 한 트랜잭션 안에서 결제·알림·상태 변경까지 끝낸다. Kafka를 쓰지 않는다.
- 응답으로 돌려주는 ID는 컨트롤러 변수명(`orderId`)과 달리 **OrderBid의 ID**다. Order ID가 아니다.
- 즉시 구매가 끝난 뒤 주문(Order) 상태는 **PENDING_PAYMENT 그대로**다. 창고 보관(`warehouseStorage`) 플래그는 주문 처리에 쓰이지 않는다.

---

## 1. 진입 API · 처리 단계 · 동기/비동기 · 응답 ID

1. `POST /order-bids/instant` 로 들어온다. 클래스 매핑 `@RequestMapping("/order-bids")` (`D/order/controller/command/OrderBidCommandController.java:22`), 메서드 `@PostMapping("/instant")` (같은 파일 :89).
2. 컨트롤러 단계 (`OrderBidCommandController.java:90-109`)
   - 인증 사용자 이메일 추출·검증 (:92, `global/utils/SecurityUtils.java:85`).
   - 결제 요청 DTO에 이메일 설정, `orderId=null` 로 초기화 (:98, :119-122).
   - `orderBidCommandService.createInstantOrderBid(...)` 직접 호출 (:101-107).
3. 서비스 단계 `OrderBidCommandService.createInstantOrderBid` (`D/order/service/command/OrderBidCommandService.java:118-149`, `@Transactional`)
   1. 입력 검증 (:123, :154-167) → 구매자 조회 (:126) → SaleBid/Sale 조회 (:129-130, :172-184).
   2. `orderCommandService.createInstantOrder(...)` 호출 (:133).
   3. 반환된 Order로 OrderBid 생성·저장 (:142, :189-207).
4. `OrderCommandService.createInstantOrder` (`D/order/service/command/OrderCommandService.java:219-319`): 주소 조회(:238) → Order 저장(:241-247) → OrderItem(:255) → OrderShipment(:264) → SaleBid 매칭 + flush(:279-283) → 창고 상태 갱신(:291-293) → 결제(:305).
5. **동기**: 컨트롤러가 `.getId()` 를 바로 받아 `ResponseEntity.ok` 로 응답한다 (:101-109). `OrderBidCommandController` 는 `OrderEventProducer` 를 쓰지 않는다. 반면 `/orders/{orderId}/process-payment-shipment` 는 Kafka producer로 비동기 처리한다 (`D/order/controller/command/OrderCommandController.java:30, 42, 54`) — 즉시 구매 경로가 아니다.
6. **응답 ID**: `createInstantOrderBid` 의 반환 타입은 `OrderBid` 이고 (`OrderBidCommandService.java:119`), 컨트롤러는 `.getId()` 를 `orderId` 변수에 담아 반환한다 (`OrderBidCommandController.java:101-107`). 따라서 응답 ID = **OrderBid.id**. 응답 메시지는 "즉시 구매가 성공적으로 처리되었습니다." (:109).

## 2. 새로 생기는 엔티티와 상태 변화 순서

새로 생성되는 엔티티: **Order, OrderItem, OrderShipment, Payment(Card/Account/General 중 하나), Notification(최대 2건), OrderBid**. (SaleBid/Sale/Warehouse는 기존 엔티티의 상태 변경)

| 순서 | 동작 | 직후 상태 | 근거 |
|---|---|---|---|
| 1 | Order 저장 | Order.status = `PENDING_PAYMENT`, totalAmount = saleBid.bidPrice | `OrderCommandService.java:241-247` |
| 2 | OrderItem 생성 (수량 1, 가격 bidPrice) | — | `OrderCommandService.java:255-256`, `OrderItemCommandService.java` createOrderItem |
| 3 | OrderShipment 생성 | ShipmentStatus = `PENDING` | `OrderCommandService.java:264-271`, `D/shipment/service/command/OrderShipmentCommandService.java:67` |
| 4 | SaleBid 매칭 (`assignOrder` + `updateStatus(MATCHED)`) 후 flush | SaleBid.status = `MATCHED`, SaleBid.order = Order | `OrderCommandService.java:279-283`, `D/sale/entity/SaleBid.java:49-52` |
| 5 | Sale.isWarehouseStorage == true 이면 창고 상태 갱신 | WarehouseStorage.status = `ASSOCIATED_WITH_ORDER` | `OrderCommandService.java:291-293`, `D/warehouseStorage/service/command/WarehouseStorageCommandService.java:117-133` |
| 6 | Payment 생성 (수단별, 3번 항목 참조) | Payment.status 기본 `PENDING` → 수단/응답에 따라 `PAID` 또는 `PENDING` | `OrderCommandService.java:305`, `D/payment/entity/Payment.java:44` |
| 7 | 알림 발송 + Sale 상태 변경 | Sale.status = `SOLD` | `D/payment/service/command/PaymentCommandService.java:83, 391-404` |
| 8 | OrderBid 생성 | OrderBid.status = `MATCHED` (빌더에서 지정 + `assignOrder` 에서도 MATCHED), isInstantPurchase = true | `OrderBidCommandService.java:192-206`, `D/order/entity/OrderBid.java:73-76, 97-99` |

참고
- 7번에서 `order.getOrderBid()` 는 아직 null이다(OrderBid는 8번에서 만든다). 그래서 `saleBidQueryService.findByOrderId` 로 SaleBid를 찾아 그 Sale을 쓴다 (`PaymentCommandService.java:388-407`; `D/sale/service/query/SaleBidQueryService.java:26-29`). 4번의 flush 덕분에 조회가 가능하다.
- Order에는 `assignPayment` 가 호출되지 않는다(`createInstantOrder` 는 결제 반환값을 버린다, :305). Payment 쪽에서만 order를 참조한다 (`PaymentCommandService.java:200, 258, 311`).
- 선택한 SaleBid가 이미 MATCHED/취소 상태인지 확인하는 코드는 없다 (`OrderBidCommandService.java:172-184`는 null 검사만 한다).

## 3. 결제 수단별 결과 / 결제 대행사 실패

결제 분기: `PaymentCommandService.processPayment` 의 switch (`PaymentCommandService.java:67-80`). 결제 전 검증: 주문 ID·이메일 일치, 금액 > 0 (:117-146).

| 수단 | 동작 | Payment 결과 | 근거 |
|---|---|---|---|
| 카드 (CARD) | PortOne API 호출(`portOneApiClient.processCardPayment`) 후 CardPayment 저장 | 응답 `status` 가 문자열 `"success"` 이면 `PAID` + isSuccess=true. 그 외 값이면 **PENDING, isSuccess=false 로 저장되고 예외 없이 계속 진행** | `PaymentCommandService.java:179, 203-208` |
| 계좌이체 (ACCOUNT) | 은행명 검증 후 PortOne 호출 없이 저장 | 항상 `PENDING`, isSuccess=false | `PaymentCommandService.java:243-262` |
| 일반 (GENERAL) | impUid 필수 검증 후 저장, PortOne 호출 없음 | 항상 `PAID`, isSuccess=true | `PaymentCommandService.java:297-314` |

- 세 수단 모두 결제 이후 흐름(알림 → Sale SOLD → OrderBid 생성)은 동일하다. 즉 계좌이체(PENDING)와 카드의 비-"success" 응답도 요청은 **성공(200)** 으로 끝나고, 구매자·판매자 알림이 가고 Sale이 SOLD가 된다. 결제 완료 여부를 확인하는 분기가 없다 (`PaymentCommandService.java:83, 383-426`).
- 따라서 "즉시 구매가 끝까지 성공하는가"에 대해: 예외가 없으면 어떤 수단이든 끝까지 진행된다. 다만 계좌이체는 입금 확인 전인 PENDING 결제로 확정된다.
- **카드 결제를 PortOne이 실패로 응답할 때**: `processCardPayment` 는 HTTP가 200이 아니거나 `code != 0` 이면 `PaymentProcessingException` 을 던진다 (`D/payment/portone/PortOneApiClient.java:270-275`); 통신 오류는 `PaymentApiException` (:121-123). 이 예외는 `createCardPayment` (:180-184, 218-219) → `processPayment` (:89-94) → `OrderCommandService.createInstantOrder` 의 catch 에서 `OrderPaymentProcessingFailedException` 으로 감싸져 (:306-309) → `OrderBidCommandService` 의 catch 에서 `OrderException` 이므로 그대로 던져진다 (:145-148, :212-217). `@Transactional` 이므로 Order, OrderItem, OrderShipment, SaleBid MATCHED, 창고 상태 변경이 모두 롤백되고 OrderBid/Notification은 만들어지지 않는다. 클라이언트에는 오류 응답이 간다.
- 반대로 `code == 0` 인데 `response.status` 가 "success" 가 아니면 위 표처럼 실패로 처리되지 않고 PENDING 결제로 성공 응답이 나간다 (:203-206). 실패 시 Payment를 `FAILED` 로 만드는 코드는 없다.

## 4. 알림: 누가, 언제, 어떻게

- 시점: 결제 처리 직후 같은 요청·같은 트랜잭션 안에서 동기 실행. `processPayment` 가 Payment를 만든 뒤 `notifyUsersAndUpdateSaleStatus` 를 호출한다 (`PaymentCommandService.java:83`), 그 안에서 `sendNotifications` (:403 / :416).
- 수신자와 내용 (`PaymentCommandService.java:434-462`), 둘 다 `NotificationCategory.SHOPPING`, `NotificationType.BID`:
  - 구매자: "결제가 완료되었습니다. 주문 ID: {orderId}" (:438-443)
  - 판매자(`sale.getSeller()`): "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}" (:447-454)
- 전달 방식 (`D/notification/service/command/NotificationCommandService.java:44-67, 303-323`):
  1. DB에 Notification 저장 (:52-53).
  2. 사용자가 Redis 키 `WebSocket:User:{email}` 로 연결 중인 경우에만 `/queue/notifications` 로 WebSocket(STOMP) 푸시 (:37-38, 303 이후). 연결이 없으면 저장만 되고 푸시는 생략된다.
- 알림 실패는 로그만 남기고 삼킨다 (`PaymentCommandService.java:457-461`, 상위 :421-425). 알림 발송 예외가 요청을 직접 실패시키지 않으며, `sendNotifications` 가 예외를 삼키므로 이후 Sale SOLD 변경은 계속 진행된다 (:416-419).
- 결제 실패(3번의 예외 경로)에서는 알림이 발송되지 않는다 — 알림 코드가 결제 생성 이후에 있기 때문 (:83).
- 알림 문구는 "결제가 완료되었습니다"지만 계좌이체(PENDING)·카드 비-success 응답에서도 동일하게 발송된다.

## 5. 최종 주문 상태 / 창고 보관 선택 시

- **최종 Order.status = `PENDING_PAYMENT`**. `createInstantOrder` 에서 한 번 설정(`OrderCommandService.java:244`)된 뒤 이 경로에서 `order.updateStatus` 가 호출되지 않는다 (`updateStatus` 호출은 `OrderCommandService.java:165-176` 의 `processPaymentAndShipment` 와 Kafka consumer `D/order/service/kafka/OrderEventConsumer.java:195, 204, 217` 에만 있고 즉시 구매 경로에서는 호출되지 않는다). 카드·일반 결제가 PAID 여도 주문은 결제 완료로 바뀌지 않는다. 같은 요청에서 만들어진 OrderBid만 MATCHED이다 (`OrderBidCommandService.java:196`).
- 컨트롤러 메서드 주석은 "즉시 구매 입찰을 생성합니다"이지만(`OrderBidCommandController.java:80`), 실제 응답 ID는 OrderBid ID다 (위 1번).
- **창고 보관(`warehouseStorage`) 선택 시**: 구매자가 보낸 `warehouseStorage` 값은 컨트롤러에서 로그(:94-95)와 서비스 인자(:105)로 전달되고 `createInstantOrder` 의 파라미터 `isWarehouseStorage` 로 들어가지만 (`OrderCommandService.java:221`), 메서드 본문에서 **한 번도 사용되지 않는다**. 사용되는 값은 판매자가 등록한 `Sale.isWarehouseStorage()` 뿐이다 (:292). 그 결과:
  - 구매자의 창고 보관 선택은 Order 상태, WarehouseStorage 생성(`warehouseStorageCommandService.createOrderStorage` 호출 없음), IN_WAREHOUSE/COMPLETED 전이 어디에도 반영되지 않는다. 선택 여부와 상관없이 결과(Order = PENDING_PAYMENT, OrderShipment 생성)가 같다.
  - `processPaymentAndShipment` 에는 창고 보관 시 IN_WAREHOUSE → COMPLETED 로 가는 분기가 있지만 (`OrderCommandService.java:163-172`) 즉시 구매 경로에서는 호출되지 않는다.
  - 창고에 영향을 주는 것은 판매자 쪽 `Sale.isWarehouseStorage == true` 인 경우의 `WarehouseStatus.ASSOCIATED_WITH_ORDER` 변경뿐이다 (:291-293). 해당 Sale에 창고 레코드가 없으면 `WarehouseStorageNotFoundException` → `OrderWarehouseStorageProcessingFailedException` 으로 전체 롤백된다 (`WarehouseStorageQueryService.java:30-33`, `OrderCommandService.java:295-301`).
