# 구매자 배송: 운송장 등록 → 배송 완료 (코드 조사 결과)

경로 약칭: `D` = `src/main/java/com/fream/back/domain`, `G` = `src/main/java/com/fream/back/global`

> 전제: `shipment`(기본) 외에 `adminshipment`, `partnershipment`, `internalshipment`, `settlementshipment`, `legacyshipment` 에
> 거의 같은 복사본(컨트롤러·배치 구성·프로세서)이 있다. 여기서는 기본 `shipment` 패키지를 기준으로 쓰고, 복사본과의 관계는 2-4에 적는다.

## 0. 배송 정보가 만들어지는 시점 (전제)

- 결제·배송 처리 `OrderCommandService.processPaymentAndShipment` 가 결제 후 `OrderShipment` 를 `PENDING` 상태로 만들어 붙인다.
  - 배송 생성 호출: `D/order/service/command/OrderCommandService.java:148`
  - `PENDING` 초기 상태: `D/shipment/service/command/OrderShipmentCommandService.java:67`
- 실배송(창고 보관 아님)이면 주문은 `PAYMENT_COMPLETED` → `PREPARING` 에서 멈춘다. `OrderCommandService.java:175-176`
- 창고 보관이면 `PAYMENT_COMPLETED → PREPARING → IN_WAREHOUSE → COMPLETED` 로 간다. `OrderCommandService.java:165-172`
- 즉시 구매 `createInstantOrder` 는 주문을 `PENDING_PAYMENT` 로 만든다(`OrderCommandService.java:244`). 이후 어디에서도 주문 상태를 바꾸지 않는다(`:247-311`에 `updateStatus` 없음).
  - 즉시 구매의 결제 처리는 `PaymentCommandService`(`D/payment/service/command/PaymentCommandService.java`)가 하는데, 여기에도 `OrderStatus` 변경은 없다.
  - 따라서 즉시 구매 주문은 배송 정보까지 만든 뒤에도 `PENDING_PAYMENT` 상태다.

## 1. 운송장 등록 요청

### 1-1. 진입 API
- `PATCH /shipments/order/{shipmentId}/status`, 본문은 `OrderShipmentRequestDto`(courier, trackingNumber).
  - 매핑: `D/shipment/controller/command/OrderShipmentCommandController.java:20`(`/shipments/order`), `:33`(`@PatchMapping("/{shipmentId}/status")`)
  - 서비스 호출: `OrderShipmentCommandController.java:41-45` → `OrderShipmentCommandService.updateTrackingInfo` (`OrderShipmentCommandService.java:238-239`)
- 참고로 같은 컨트롤러의 `POST /{shipmentId}/check-status`(`:58`)는 운송장을 넣고 즉시 CJ 조회까지 하는 별도 경로이다(`updateAndCheckShipmentStatus`, 서비스 `:451-516`).
- (복사본: `/admin/shipments/order/{id}/status` 등, `D/adminshipment/controller/command/AdminOrderShipmentCommandController.java:20,33`)

### 1-2. 코드가 의도한 상태 변경 순서와 알림 (`updateTrackingInfo`, `OrderShipmentCommandService.java:238-303`)
1. courier/trackingNumber 공백 검증 → `TRACKING_INFO_REQUIRED`. `:243-246`
2. `OrderShipment` 조회 후 `updateTrackingInfo` → 택배사·운송장 저장, 배송 상태를 `IN_TRANSIT` 으로 직접 세팅(전이 검사 없음). `:249-256`, `D/shipment/entity/OrderShipment.java:41-45`
3. 주문 상태를 `IN_TRANSIT` 으로 변경. `:259-260`
4. 구매자에게 알림 1건 "상품이 출발하였습니다. 주문 ID: …". `:265-271`
5. `updateSaleStatusToSold(orderId)` : Sale 을 `SOLD` 로 바꾸고(창고 보관이면 창고 상태도 변경) 판매자에게 알림 "상품이 성공적으로 판매 완료되었습니다…". `:276`, `:111-183`
6. SaleBid 로 Sale 을 다시 찾아 창고 보관이면 창고 상태 `SOLD` 갱신. `:279-286`
7. `updateOrderAndSaleBidStatusToCompleted` : OrderBid, SaleBid 가 `MATCHED` 이면 `COMPLETED` 로 변경(예외는 삼킴). `:289`, `:412-440`
   - 즉 "배송 중" 등록 시점에 이미 Sale `SOLD`, OrderBid/SaleBid `COMPLETED` 가 된다. 배송 완료까지 기다리지 않는다.

### 1-3. 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문(즉시 구매 아님): 끝까지 성공하지 못한다
- 이 주문은 `PREPARING` 상태이다(0절, `OrderCommandService.java:175-176`).
- `OrderStatus` 전이표에서 `PREPARING` 의 다음 상태는 `{IN_WAREHOUSE, SHIPMENT_STARTED}` 뿐이고 `IN_TRANSIT` 은 없다. `D/order/entity/OrderStatus.java:26`
  - `IN_TRANSIT` 은 `SHIPMENT_STARTED` 에서만 갈 수 있다(`OrderStatus.java:28`).
  - `SHIPMENT_STARTED` 로 바꾸는 코드는 어디에도 없다.
- 실패 지점은 서비스 `:260` 의 `order.updateStatus(OrderStatus.IN_TRANSIT)` 이다.
  - `Order.updateStatus` 가 `InvalidOrderStatusException("상태 전환이 허용되지 않습니다: PREPARING -> IN_TRANSIT")` 를 던진다. `D/order/entity/Order.java:113-120`
- 이 예외는 `catch (Exception e)` 에 잡혀 `ShipmentException(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")` 로 바뀌어 다시 던져진다. `OrderShipmentCommandService.java:295-301`
  - 에러 코드가 `SHIPMENT_NOT_FOUND`(S001, 404) 로 잘못 붙는 점에 주의.
- 무엇이 저장되나: **아무것도 저장되지 않는다.**
  - `ShipmentException` 은 `RuntimeException` 이다(`G/exception/GlobalException.java:10`).
  - `@Transactional`(`:238`) 이므로 롤백된다. 2단계에서 메모리상 바뀐 `courier`/`trackingNumber`/`IN_TRANSIT` 도 DB에 반영되지 않는다.
  - 배송은 `PENDING`, 운송장 `null` 로 남는다.
  - 알림(4단계)은 실패 지점(3단계) 뒤에 있어 생성되지 않는다.
- 응답: `GlobalExceptionHandler.handleShipmentException` 이 **HTTP 404**, 본문 `ErrorResponse(code="S001", message="배송 정보를 찾을 수 없습니다.", status=404, path=요청 URI)` 를 만든다. `G/exception/GlobalExceptionHandler.java:459-471`, `D/shipment/exception/ShipmentErrorCode.java:61`
  - 핸들러는 `errorCode.getMessage()` 를 쓰므로 상세 메시지("PREPARING -> IN_TRANSIT")는 응답에 나가지 않고 로그에만 남는다.
  - 이 엔드포인트의 컨트롤러는 try/catch 가 없다(`OrderShipmentCommandController.java:34-49`).
- 결과: 일반 구매 입찰 주문은 운송장 등록 API로는 배송이 시작되지 않는다. 즉시 구매 주문도 `PENDING_PAYMENT → IN_TRANSIT` 이 전이표에 없어 똑같이 실패한다(`OrderStatus.java:24`).

## 2. 배송 완료 감지

### 2-1. 누가·언제·어떻게
- 사람이 아니라 Spring `@Scheduled` 가 Spring Batch Job 을 띄워 감지한다.
  - `ShipmentBatchScheduler.scheduleShipmentStatusJob` 이 `updateShipmentStatusesJob` 을 `jobLauncher.run` 한다. `G/config/ShipmentBatchScheduler.java:34-44`
  - JobParameters 에 `timestamp` 를 넣어 매번 새 실행이 된다. `:37-40`
- 배송 완료는 CJ대한통운 운송장 조회 화면(`https://trace.cjlogistics.com/next/tracking.html?wblNo=`)을 Playwright 로 열어 파싱해 알아낸다.
  - URL: `D/shipment/config/ShipmentItemProcessor.java:28`, 파싱: `:166-190`

### 2-2. 주기
- `@Scheduled(cron = "0 0 */6 * * *")` → 6시간마다(0, 6, 12, 18시 정각). `G/config/ShipmentBatchScheduler.java:34`

### 2-3. 대상 배송
- `JpaPagingItemReader` 쿼리: `SELECT s FROM OrderShipment s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL`. `D/shipment/config/UpdateShipmentStatusesJobConfig.java:95`
- 청크 50, 스킵 한도 50. `UpdateShipmentStatusesJobConfig.java:51-52`, `:67`

### 2-4. 실제로 실행되는 처리 코드
- Step 은 `new ShipmentItemProcessor(...)` 를 직접 만들어 쓴다. `UpdateShipmentStatusesJobConfig.java:69`
  - 실행되는 것: `D/shipment/config/ShipmentItemProcessor.java:57` `process()`
- 같은 클래스에 `@Bean @StepScope shipmentItemProcessor()` 람다(`UpdateShipmentStatusesJobConfig.java:106`)와 `parseCjLogisticsStatus`(Jsoup)가 있지만 Step 에 연결되지 않은 죽은 코드이다.
- `OrderShipmentCommandService.updateShipmentStatuses()`(`OrderShipmentCommandService.java:309-391`) 도 호출하는 곳이 없다(스케줄러는 이 메서드를 쓰지 않는다). 이 메서드는 배송 완료 시 Order 를 `COMPLETED` 로 바꾸고 알림을 만드는 별개 구현이라, 실제 경로와 동작이 다르다.
- 복사본 주의: `admin/partner/settlement/internal/legacy` 의 `*UpdateShipmentStatusesJobConfig` 도 같은 이름의 `updateShipmentStatusesJob` 빈을 만든다.
  - 예: `D/adminshipment/config/AdminUpdateShipmentStatusesJobConfig.java:55-57`
  - `application*.yml` 에서 빈 오버라이딩 허용 설정은 찾지 못했다. 스케줄러는 `@Qualifier("updateShipmentStatusesJob")` 하나(`ShipmentBatchScheduler.java:19-21`)만 쓴다.
  - 어느 복사본이 쓰이든 프로세서의 완료 처리 로직은 같다(`AdminShipmentItemProcessor.java:108-117`도 `OrderShipmentCommandService.completeOrder` 호출). 알림 서비스 클래스만 다르다.
  - 위 이름 충돌이 실제로 기동 시 문제를 일으키는지는 코드만으로 확정하지 않았다. 이 답은 기본 `shipment` 패키지 기준이다.

### 2-5. 택배사 상태 문자열 → 내부 상태
`ShipmentItemProcessor.mapToShipmentStatus` (`D/shipment/config/ShipmentItemProcessor.java:220-225`)

- 파싱 대상은 `tbody#statusDetail tr` 의 마지막 행, 5번째 `td` 텍스트(`trim`). 정확히 일치해야 매핑된다. `ShipmentItemProcessor.java:166-190`
- 현재 상태와 같으면 변경 없이 반환. `:101-104`

## 3. 배송 완료 판정 이후 (`newStatus == DELIVERED`)

`ShipmentItemProcessor.process` `D/shipment/config/ShipmentItemProcessor.java:108-117`

상태 변경 순서
1. `OrderShipment` → `DELIVERED` (`orderShipment.updateStatus`, `:113`). 전이는 `IN_TRANSIT`/`OUT_FOR_DELIVERY` → `DELIVERED` 만 허용. `D/shipment/entity/ShipmentStatus.java:16-22,23-28`
2. `orderService.completeOrder(orderId)` (`:116`) → `OrderShipmentCommandService.completeOrder` (`:190-229`)
   1. OrderBid 를 `findByOrderId` 로 조회, 없으면 예외. `:196-197`
   2. `Order` → `COMPLETED`. `:204`
   3. `updateSaleStatusToSold` 호출 : Sale → `SOLD`(가능할 때), 판매자 알림. `:208`, `:111-183`
   4. 구매자 알림 "[completeOrder] 주문이 완료 처리되었습니다. 주문 ID: …". `:210-217`
3. `notificationService.notifyShipmentCompleted(order)` : 구매자 알림 "[배송 완료] 상품이 배송 완료되었습니다. 주문 ID: …". `ShipmentItemProcessor.java:117`, `D/notification/service/command/NotificationCommandService.java:219-234`
4. Writer(`JpaItemWriter`)가 `OrderShipment` 를 저장. `UpdateShipmentStatusesJobConfig.java:74`

알림 건수
- 구매자: **2건** (completeOrder 의 "[completeOrder]…" 1건 + notifyShipmentCompleted 의 "[배송 완료]…" 1건).
- 판매자: **0~1건**. `updateSaleStatusToSold` 에서 Sale 이 `SOLD` 로 **전이 가능할 때만** 1건(`:119`, `:156`).
  - Sale 은 SaleBid 쪽 분기에서 먼저 `SOLD` 가 되므로 OrderBid 쪽 분기에서 중복 알림은 생기지 않는다(`Sale.updateStatus` 가 즉시 상태를 바꿈, `SaleStatus.canTransitionTo` 는 `SOLD` 에서 false). `D/sale/entity/SaleStatus.java:23`
  - 결제 시점에 이미 Sale 이 `SOLD` 가 되었거나 운송장 등록(1-2의 5단계)에서 `SOLD` 가 되었다면 판매자 알림은 0건이다.

주문 입찰·판매 입찰 상태
- `completeOrder` 경로는 OrderBid/SaleBid 상태를 **바꾸지 않는다.** `updateOrderAndSaleBidStatusToCompleted` 는 `updateTrackingInfo`(`:289`)에서만 호출된다.
  - `OrderBid.updateStatus` 는 `MATCHED → COMPLETED` 를 운송장 등록 단계에서 처리할 의도이지만, 1-3 때문에 일반 입찰 주문은 그 단계에 도달하지 못한다.
  - 배송 완료 시점에는 OrderBid/SaleBid 가 그대로(`MATCHED` 등) 남는다.

## 4. 주문 종류별 차이

배송 완료 처리(3)가 배치 대상이 되려면 먼저 배송이 `IN_TRANSIT`/`OUT_FOR_DELIVERY` + 운송장 보유 상태여야 한다(2-3). 그런데 1-3 때문에 두 주문 모두 정상 운송장 등록 API로는 거기까지 가지 못한다. 아래는 완료 판정 코드 자체가 두 주문에서 어떻게 다르게 동작하는지이다.

### (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문 → 끝까지 진행되지 않는다
- 주문은 `PREPARING` (`OrderCommandService.java:175-176`). `PREPARING → COMPLETED` 는 전이표에 없다. `OrderStatus.java:26`
  - `completeOrder` 의 `order.updateStatus(COMPLETED)`(`OrderShipmentCommandService.java:204`)가 `InvalidOrderStatusException` 을 던진다.
- 설령 주문 상태가 통과해도 일반 입찰 주문에는 SaleBid 가 없다. `SaleBidQueryService.findByOrderId` 는 null 을 돌려주지 않고 `IllegalArgumentException` 을 던진다(`D/sale/service/query/SaleBidQueryService.java:25-29`).
  - 그래서 `updateSaleStatusToSold` 의 `if (saleBid != null)`(`OrderShipmentCommandService.java:117`) 은 사실상 죽은 분기이고, 예외가 그대로 `completeOrder` 의 catch 로 간다.
- 어느 쪽이든 `completeOrder` 의 catch 가 `ShipmentException(ORDER_NOT_FOUND_FOR_SHIPMENT)` 로 다시 던진다. `OrderShipmentCommandService.java:221-228`
- 결과: 프로세서가 예외를 던져 해당 건은 스킵되고(5절), 배송·주문·알림 모두 반영되지 않는다. 배송은 계속 `IN_TRANSIT`/`OUT_FOR_DELIVERY` 로 남아 6시간마다 재조회·재실패한다.
  - 이 주문이 배치 대상이 되는 경로는 `check-status` API 로 `OUT_FOR_DELIVERY` 가 저장된 경우 정도다(`updateAndCheckShipmentStatus`, `:473`, `:491-493`).

### (b) 즉시 구매로 만들어진 주문 → 완료 처리 자체는 끝까지 진행된다
- 주문은 `PENDING_PAYMENT`(`OrderCommandService.java:244`). `PENDING_PAYMENT → COMPLETED` 는 전이표에 있다. `OrderStatus.java:24`
- OrderBid 가 있다. `createInstantOrderBid` 가 `order` 와 연결해 저장. `D/order/service/command/OrderBidCommandService.java:189-207`, `:133-143`
- SaleBid 도 주문과 연결된다. `saleBid.assignOrder(order)`. `OrderCommandService.java:279-280`
  - 따라서 `findByOrderId` 들이 모두 성공하고 `completeOrder` 가 끝까지 간다.
- 결제 때 이미 Sale 이 `SOLD` 가 된다(`PaymentCommandService.java:83` → 즉시 구매 시점에는 `order.getOrderBid()` 가 없어 SaleBid 분기, `:383-405`).
  - 그래서 배송 완료 시 `canTransitionTo(SOLD)` 가 false 이고, 판매자 알림은 없고 구매자 알림만 2건이다.
- 결과: Shipment `DELIVERED`, Order `COMPLETED`, 구매자 알림 2건. OrderBid/SaleBid 는 `MATCHED` 그대로.
- 단, 이 주문도 운송장 등록 API 는 1-3 과 같은 이유로 실패하므로(`PENDING_PAYMENT → IN_TRANSIT` 불가) 배송이 `IN_TRANSIT` 이 되려면 `check-status` 경로 등을 거쳐야 한다.

요약

| 항목 | (a) 실배송 일반 입찰 | (b) 즉시 구매 |
|---|---|---|
| 주문 상태 | `PREPARING` | `PENDING_PAYMENT` |
| 운송장 등록 API | 실패(404 S001, 롤백) | 실패(404 S001, 롤백) |
| `completeOrder` 의 `COMPLETED` 전이 | 불가 | 가능 |
| SaleBid 조회 | 없음 → `IllegalArgumentException` | 있음 |
| 완료 처리 | 실패, 전부 롤백, 스킵 | 성공 |
| 구매자/판매자 알림 | 없음 | 구매자 2 / 판매자 0 |

- 실패한 건
  - 스킵 처리되어 `SkipListener.onSkipInProcess` 가 에러 로그만 남긴다. `UpdateShipmentStatusesJobConfig.java:252-263`
  - 그 건의 변경은 저장되지 않는다. `completeOrder` 가 `@Transactional` 메서드로서 청크 트랜잭션에 참여하다 `RuntimeException` 을 던지므로, 그 청크 트랜잭션은 롤백 대상이 된다.
  - 상태가 안 바뀐 채 `IN_TRANSIT`/`OUT_FOR_DELIVERY` 로 남아 다음 6시간 주기에 다시 대상이 된다.
- 나머지 건
  - Spring Batch fault-tolerant 스텝은 스킵 대상 예외가 나면 해당 청크를 롤백하고, 스킵된 건을 빼고 청크 내 나머지 아이템을 다시 처리해 쓴다.
  - 따라서 나머지 건은 계속 처리되고 성공 건은 반영된다. 이 재처리 동작은 코드가 아니라 Spring Batch 의 일반 동작을 근거로 한 설명이다.
- 스킵이 50건을 넘으면 `SkipLimitExceededException` 으로 Step(Job)이 실패한다. 이때 남은 건은 처리되지 않고 다음 주기를 기다린다. `UpdateShipmentStatusesJobConfig.java:77`
- 스케줄러 자체는 `jobLauncher.run` 예외를 `printStackTrace` 만 하고 삼킨다(재시도·알림 없음). `ShipmentBatchScheduler.java:41-43`
- 운송장 번호가 없는 건은 프로세서에서 `TRACKING_NUMBER_INVALID` 로 예외를 던져 같은 방식으로 스킵된다. `ShipmentItemProcessor.java:61-64` (reader 쿼리가 `trackingNumber IS NOT NULL` 이라 보통 해당되지 않는다)
- 한 건의 알림 실패는 따로 `notifyShipmentCompleted` 내부에서 삼켜 로그만 남긴다. `NotificationCommandService.java:230-233`
  - 반면 `completeOrder` 안의 `createNotification` 실패는 `NotificationException` 으로 전파되어 `completeOrder` 의 catch 로 간다.

## 보충: 주석/이름과 실제 동작이 다른 곳
- `updateTrackingInfo` 의 "OrderBid 상태를 COMPLETED로 변경"과 Sale `SOLD` 처리는 이름상 배송 완료 후처리처럼 보이지만 실제로는 운송장 등록 시점에 실행된다(`OrderShipmentCommandService.java:276-289`).
- `updateTrackingInfo` 의 실패는 `SHIPMENT_NOT_FOUND` 로 보고된다. 실제 원인은 주문 상태 전이 불가이다(`:295-301`).
- `updateShipmentStatuses()` 와 `shipmentItemProcessor()` 빈, `parseCjLogisticsStatus` 는 이름과 달리 실제 배치 경로에서 쓰이지 않는다(2-4).
- `processPaymentAndShipment` 의 "OrderBid 상태 업데이트"는 `orderBidQueryService.findById(orderId)` 로 주문 ID 를 OrderBid ID 로 써서 조회하므로(`OrderCommandService.java:188`) 엉뚱한 입찰을 건드리거나 아무것도 못 찾는다.
