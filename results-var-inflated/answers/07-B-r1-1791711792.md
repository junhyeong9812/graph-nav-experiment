# 즉시 구매 처리 흐름

경로 접두사 `D` = `src/main/java/com/fream/back/domain`

## 1. 진입 API, 처리 단계, 동기/비동기, 응답 ID

- 진입점은 `POST /order-bids/instant` 이다 (`D/order/controller/command/OrderBidCommandController.java:89`, 클래스 매핑 `/order-bids` 는 `:25`).
  본문은 `InstantOrderRequestDto` (saleBidId, addressId, warehouseStorage, paymentRequest) (`D/order/dto/InstantOrderRequestDto.java:20-29`).
- 처리 단계 (모두 한 요청 스레드, 한 `@Transactional` 안):
  1. 컨트롤러가 이메일을 꺼내고(`OrderBidCommandController.java:92`) 결제 요청의 `userEmail` 을 덮어쓰고 `orderId` 를 null 로 둔다 (`:98`, `:119-121`).
  2. `OrderBidCommandService.createInstantOrderBid` (`D/order/service/command/OrderBidCommandService.java:118-149`): 입력 검증(`:123`, `:154-167`) → 구매자 조회(`:126`) → SaleBid/Sale 조회(`:129`, `:172-184`).
  3. `OrderCommandService.createInstantOrder` (`D/order/service/command/OrderCommandService.java:219-319`): 주소 조회(`:238`) → Order 저장(`:241-247`) → `paymentRequest.setOrderId` (`:250`) → OrderItem(`:255`) → OrderShipment(`:264-271`) → SaleBid 매칭 + flush(`:279-283`) → 판매자 창고 상태 변경(`:291-293`) → 결제 처리(`:305`).
  4. `PaymentCommandService.processPayment` (`D/payment/service/command/PaymentCommandService.java:57-107`): 결제 수단별 Payment 생성 → `notifyUsersAndUpdateSaleStatus` (`:83`).
  5. 다시 `OrderBidCommandService.createInstantOrderBid(order, saleBid, sale)` 로 OrderBid 생성·저장 (`OrderBidCommandService.java:142`, `:189-207`).
- **동기 처리**다. 즉시 구매 경로에는 Kafka 이벤트가 없다. Kafka(`OrderEventProducer`)는 별도 API `POST /orders/{orderId}/process-payment-shipment` 에서만 쓰인다 (`D/order/controller/command/OrderCommandController.java:42-54`). 즉시 구매 서비스 어디에도 producer 호출이 없다.
- **응답의 ID 는 OrderBid 의 ID 다. Order ID 가 아니다.** 서비스가 `OrderBid` 를 반환하고(`OrderBidCommandService.java:144`) 컨트롤러가 그 `.getId()` 를 `orderId` 변수에 담아 그대로 내려준다 (`OrderBidCommandController.java:101-107`, `:109`). Javadoc("생성된 주문 ID")과 변수명이 말하는 것과 실제 값이 다르다. OrderBid 의 PK 는 `D/order/entity/OrderBid.java:156-158`.

## 2. 생성되는 엔티티와 상태 변화 순서

생성 순서와 직후 상태:

| 순서 | 동작 | 직후 상태 | 근거 |
|---|---|---|---|
| 1 | `Order` 생성 | `OrderStatus.PENDING_PAYMENT`, totalAmount = saleBid.bidPrice | `OrderCommandService.java:241-247` |
| 2 | `OrderItem` 생성 (수량 1, 가격 = 판매 입찰가) | — | `OrderCommandService.java:255`, `D/order/service/command/OrderItemCommandService.java:45-52` |
| 3 | `OrderShipment` 생성 (주소 조회 결과 사용) | `ShipmentStatus.PENDING` | `OrderCommandService.java:264-271`, `D/shipment/service/command/OrderShipmentCommandService.java:61-68` |
| 4 | 기존 `SaleBid` 에 order 연결 | `sale.BidStatus.MATCHED` | `OrderCommandService.java:279-280`, `D/sale/entity/SaleBid.java:58-61`, flush `:283` |
| 5 | (판매자가 창고 보관 판매일 때만) 판매자 `WarehouseStorage` | `WarehouseStatus.ASSOCIATED_WITH_ORDER` | `OrderCommandService.java:291-293`, `D/warehouseStorage/service/command/WarehouseStorageCommandService.java:117-133` |
| 6 | `Payment` (Card/Account/General) 생성 | 수단별로 다름(3번 참고) | `PaymentCommandService.java:157-333` |
| 7 | 결제 후 `Sale` 상태 변경 | `SaleStatus.SOLD` | `PaymentCommandService.java:391-406` |
| 8 | `OrderBid` 생성 | `BidStatus.MATCHED`, `isInstantPurchase=true`, sale 연결 | `OrderBidCommandService.java:192-206`, `D/order/entity/OrderBid.java:207-209`, `:230-232` |

- 7번에서 Order 의 `orderBid` 는 아직 만들어지기 전(8번이 나중)이므로 `order.getOrderBid()==null` 이다. 그래서 코드는 `saleBidQueryService.findByOrderId` 분기를 타서 Sale 을 찾는다 (`PaymentCommandService.java:388-406`).
- 결제 후 `Order.status` 를 바꾸는 코드는 즉시 구매 경로에 **없다** (5번 참고).

## 3. 결제 수단별 결과, 성공 여부, 카드 실패 시

공통: `processPayment` 는 orderId 일치, 이메일 일치, 금액 > 0 만 검증한다 (`PaymentCommandService.java:117-146`). 요청 금액과 SaleBid 가격(`bidPrice`)이 같은지는 **검증하지 않는다** (DTO 상 최소 100원 `D/payment/dto/PaymentRequestDto.java:50-52`, 그리고 그 제약은 `InstantOrderRequestDto.paymentRequest` 에 `@Valid` 가 없어 중첩 검증되지도 않는다 `InstantOrderRequestDto.java:28-29`).

수단별 동작 (`PaymentCommandService.java:67-80`):

- **CARD**: `PortOneApiClient.processCardPayment` 를 호출해 PortOne(`https://api.iamport.kr`) 으로 실제 결제를 요청한다 (`PaymentCommandService.java:179`, `D/payment/portone/PortOneApiClient.java:229-295`). 응답의 `status` 가 `"success"` 이면 Payment 를 `PAID` 로, 성공 플래그 true 로 둔다 (`PaymentCommandService.java:203-206`).
- **ACCOUNT**: 은행명만 enum 검증하고(`:244`, `:470-488`) 외부 호출 없이 `PaymentStatus.PENDING` 으로 저장한다 (`:250-262`). 즉시 구매에서 입금 확인 단계는 없다.
- **GENERAL**: `impUid` 만 확인하고 PG 재검증 없이 바로 `PAID` 로 저장한다 (`:297-316`).

즉시 구매가 "끝까지 성공"하는가:
- 카드(응답 success)와 일반 결제는 `PAID` 까지 가고, 이후 Sale 이 `SOLD` 가 된다. 하지만 **Order 는 끝까지 `PENDING_PAYMENT` 에 머문다** (5번).
- 계좌이체는 Payment 가 `PENDING` 인 채로 Sale 이 `SOLD`, SaleBid/OrderBid 가 `MATCHED` 가 된다. 요청은 성공 응답을 받는다. 입금 완료로 전환하는 경로는 이 흐름에 없다 (`PaymentStatus` 전이는 `D/payment/entity/PaymentStatus.java:89-100`, 상태 갱신 호출자는 환불/수동 변경 `PaymentCommandService.java:497-516`).
- 또한 `Payment` 의 `setPaidAmount` 가 금액 > 0 이면 `isSuccess=true` 로 만들기 때문에 (`D/payment/entity/Payment.java:60-63`, 생성자 호출 `CardPayment.java:38`, `AccountPayment.java:14`) PENDING 계좌이체도 `isSuccess=true` 로 저장된다 (`paymentDate` 만 null).

**결제 대행사가 카드 결제를 실패로 응답하면**:
- PortOne HTTP 상태가 200 이 아니거나 응답 `code != 0` 이면 `PaymentProcessingException` 을 던진다 (`PortOneApiClient.java:270-275`). 통신 오류(`RestClientException`)는 `PaymentApiException` (`:288-290`). 둘 다 `PaymentException` 이므로 `processPayment` 가 그대로 전파(`PaymentCommandService.java:89-94`) → `OrderCommandService` 가 `OrderPaymentProcessingFailedException` 으로 감싸 던진다 (`OrderCommandService.java:305-309`) → `OrderBidCommandService` 가 `OrderException` 을 그대로 다시 던진다 (`OrderBidCommandService.java:145-147`, `:212-218`).
- 예외가 `RuntimeException`(`src/main/java/com/fream/back/global/exception/GlobalException.java:10`)이고 같은 `@Transactional`(`OrderBidCommandService.java:118`) 안이므로 Order/OrderItem/OrderShipment/SaleBid MATCHED/창고 상태 변경이 **모두 롤백**된다. OrderBid 는 만들어지지 않고 알림도 안 나간다(알림은 결제 성공 뒤에 나가기 때문). 클라이언트는 오류 응답을 받는다.
- 예외: PortOne 이 `code==0` 으로 응답했지만 `response.status` 가 `"success"` 가 아니면(예: 결제 미완료) 예외 없이 `PENDING` Payment 가 저장되고 흐름이 계속되어 Sale 이 `SOLD` 가 된다 (`PaymentCommandService.java:203-208`, `:83`). 이 경우 카드 실패가 성공 처리처럼 흘러간다.
- `@Retryable` 이 `PortOneApiClient` 메서드에 붙어 있으나 (`PortOneApiClient.java:224-229`) 코드베이스에서 `@EnableRetry` 를 찾을 수 없어 재시도가 적용된다고 볼 수 없다.

## 4. 알림 수신자, 시점, 전달 방식

- 시점: 결제 처리 성공 직후, `processPayment` 안에서 호출된다 (`PaymentCommandService.java:83`, `:416` / 입찰 연결 없는 경로 `:403`). 즉시 구매에서는 OrderBid 가 아직 없으므로 `:391-403` 경로가 쓰인다. 알림 후에 Sale 을 SOLD 로 바꾼다 (`:403-404`).
- 수신자(2명, `PaymentCommandService.java:434-456`):
  - 구매자: "결제가 완료되었습니다. 주문 ID: {order.id}" (`:438-443`)
  - 판매자(`sale.getSeller()`): "구매자가 결제를 완료하였습니다. 판매 ID: {sale.id}" (`:447-454`)
  - 카테고리 `SHOPPING`, 타입 `BID`.
- 방식: **동기, 같은 트랜잭션**에서 DB 에 알림 행을 저장하고 (`D/notification/service/command/NotificationCommandService.java:44-54`), 이어서 WebSocket 실시간 전송을 시도한다. Redis 키 `WebSocket:User:{email}` 가 있을 때만 `/queue/notifications` 로 `convertAndSendToUser` 하고, 없으면 저장만 한다 (`NotificationCommandService.java:37-38`, `:303-322`). Kafka/비동기 처리는 쓰지 않는다.
- 알림 전송 예외는 삼킨다 (`PaymentCommandService.java:457-461`, 상위 `:421-425`). 알림 내용은 결제 상태와 무관하다: 계좌이체 PENDING 이어도 "결제가 완료되었습니다" 가 나간다.

## 5. 최종 상태와 창고 보관 선택

- 처리 종료 시 주문(`Order`)의 최종 상태는 **`PENDING_PAYMENT`** 다. 즉시 구매 경로는 Order 를 `PENDING_PAYMENT` 로 만든 뒤(`OrderCommandService.java:244`) 한 번도 `updateStatus` 를 호출하지 않는다 (`createInstantOrder` 전체 `:219-319`, `createInstantOrderBid` `OrderBidCommandService.java:118-149`). `PAYMENT_COMPLETED`/`PREPARING`/`IN_WAREHOUSE`/`COMPLETED` 로의 전이는 `processPaymentAndShipment`(`OrderCommandService.java:111-202`)와 Kafka 컨슈머(`D/order/service/kafka/OrderEventConsumer.java:192-217`) 에만 있고 이는 `/orders/{id}/process-payment-shipment` 를 따로 호출해야 일어난다. 따라서 "결제 완료"처럼 보이는 메시지와 달리 주문 상태는 결제 대기다.
- 함께 남는 상태: SaleBid `MATCHED`, OrderBid `MATCHED`(즉시구매 플래그 true), Sale `SOLD`, OrderShipment `PENDING`, Payment 는 카드(success)/일반 `PAID`, 계좌이체 `PENDING`.
- **구매자의 "창고 보관" 선택은 즉시 구매에서 아무 효과가 없다.** 컨트롤러가 로그에만 쓰고 서비스로 넘기지만(`OrderBidCommandController.java:94-95`, `:101-106`), `OrderCommandService.createInstantOrder` 는 `isWarehouseStorage` 인자를 본문에서 전혀 읽지 않는다 (`:219-319`, 인자 선언 `:221`). 그래서:
  - 구매자용 `WarehouseStorage` 가 생성되지 않는다 (생성 코드 `warehouseStorageCommandService.createOrderStorage` 는 `processPaymentAndShipment` 안에만 있다 `OrderCommandService.java:170`).
  - `IN_WAREHOUSE`/`COMPLETED` 전이가 일어나지 않는다 (`:163-172` 는 다른 메서드).
  - 배송지(OrderShipment)는 선택과 상관없이 항상 생성된다 (`:264-271`).
- 창고와 관련해 실제로 동작하는 것은 판매자 쪽 `sale.isWarehouseStorage()` 뿐이다. 그 경우 판매자의 창고 보관 상태만 `ASSOCIATED_WITH_ORDER` 로 바뀐다 (`OrderCommandService.java:291-293`). 이때 창고 레코드가 없으면 예외로 전체가 롤백된다 (`:295-301`).
