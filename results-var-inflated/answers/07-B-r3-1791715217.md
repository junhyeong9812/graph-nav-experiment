# 즉시 구매 처리 흐름 (domain/order 기준)

기준 경로 약칭: `O` = `src/main/java/com/fream/back/domain/order`, `P` = `src/main/java/com/fream/back/domain/payment`.
(`internalorder`, `legacyorder`, `settlementorder` 등은 같은 구조의 복제본이며, 아래는 일반 사용자용 `order` 도메인 기준이다.)

## 1. 진입 API, 처리 단계, 동기/비동기, 응답 ID

- 진입점: `POST /order-bids/instant` — `O/controller/command/OrderBidCommandController.java:22` (`@RequestMapping("/order-bids")`), `:89-90`.
- 요청 DTO `InstantOrderRequestDto`: saleBidId, addressId, warehouseStorage, paymentRequest — `O/dto/InstantOrderRequestDto.java:20-28`.
- 처리 단계:
  1. 컨트롤러가 이메일 추출 후 `paymentRequest.userEmail`을 세팅하고 `orderId=null`로 초기화 — `OrderBidCommandController.java:92,98,119-122`.
  2. `OrderBidCommandService.createInstantOrderBid` (`@Transactional`) 호출 — `O/service/command/OrderBidCommandService.java:118-149`.
     입력 검증(`:123,154-167`) → 구매자 조회(`:126`) → SaleBid/Sale 조회·검증(`:129,172-184`) → `OrderCommandService.createInstantOrder`(`:133`) → OrderBid 생성·저장(`:142,189-207`).
  3. `OrderCommandService.createInstantOrder` (`@Transactional`) — `O/service/command/OrderCommandService.java:219-319`.
     주소 조회(`:238`) → Order 저장(`:241-247`) → OrderItem(`:255`) → OrderShipment(`:264-271`) → SaleBid 매칭+flush(`:279-283`) → (조건부) 창고 상태 변경(`:291-293`) → 결제(`:305`).
- 동기 처리: 컨트롤러가 서비스를 직접 호출하고 결과를 기다려 `ResponseEntity.ok`로 응답한다 (`OrderBidCommandController.java:101-109`). Kafka/비동기 없음. 결제 대행사(PortOne) 호출도 같은 요청 스레드·같은 트랜잭션 안에서 이뤄진다 (`P/service/command/PaymentCommandService.java:179`).
  - 같은 도메인의 Kafka 비동기 경로(`POST /orders/{orderId}/process-payment-shipment`, 202 응답)는 즉시 구매 흐름에서 호출되지 않는 별도 API다 — `O/controller/command/OrderCommandController.java:20,43-68`.
- 응답으로 돌려주는 ID: **OrderBid의 ID**이다. 컨트롤러 변수명은 `orderId`이고 Javadoc도 "생성된 주문 ID"라고 하지만, 실제로는 `createInstantOrderBid(...)`가 반환한 `OrderBid`의 `.getId()`를 돌려준다 — `OrderBidCommandController.java:101-107,109` (반환 타입 `OrderBid`: `OrderBidCommandService.java:119`). Order의 ID가 아니다.

## 2. 새로 생성되는 엔티티와 상태 변화 순서

한 트랜잭션 안에서 순서대로 일어난다 (`OrderCommandService.createInstantOrder`, `OrderBidCommandService.createInstantOrderBid`).

| 순서 | 동작 | 직후 상태 | 근거 |
|---|---|---|---|
| 1 | `Order` 생성·저장 (totalAmount = saleBid.bidPrice) | Order = `PENDING_PAYMENT` | `OrderCommandService.java:241-247` |
| 2 | `paymentRequest.orderId = order.id` 세팅 | - | `:250` |
| 3 | `OrderItem` 생성 (수량 1, 가격 = bidPrice) | - | `:255-256`, `O/service/command/OrderItemCommandService.java:45-52` |
| 4 | `OrderShipment` 생성 (주소는 addressId로 조회한 값) | Shipment = `PENDING` | `:264-271`, `shipment/service/command/OrderShipmentCommandService.java:61-68` |
| 5 | `saleBid.assignOrder(order)` + `updateStatus(MATCHED)` 후 `flush` | SaleBid = `MATCHED` (Order 연결) | `:279-283`, `sale/entity/SaleBid.java:58-61,66-68` |
| 6 | (판매 건이 창고 보관 판매일 때만) 판매자 창고 상태 변경 | WarehouseStorage = `ASSOCIATED_WITH_ORDER` | `:291-293`, `warehouseStorage/service/command/WarehouseStorageCommandService.java:117-140` |
| 7 | 결제 처리 → `Payment` 생성 (유형별 상태는 3번 참고) | Payment = `PAID` 또는 `PENDING` | `:305`, `PaymentCommandService.java:57-81` |
| 8 | 결제 후 알림 전송 + `Sale.updateStatus(SOLD)` | Sale = `SOLD` | `PaymentCommandService.java:83,383-420` |
| 9 | `OrderBid` 생성: status `MATCHED`, `sale` 연결, `isInstantPurchase=true`로 저장 | OrderBid = `MATCHED` | `OrderBidCommandService.java:192-206`, `O/entity/OrderBid.java:60-80,97-99` |

- 새로 생성되는 엔티티: Order, OrderItem, OrderShipment, Payment(Card/Account/General 중 하나), OrderBid, 알림(Notification, 구매자·판매자 각 1건). 창고 보관 판매이면 기존 WarehouseStorage의 상태만 바뀐다(새로 만들지 않음).
- 8단계 세부: 이 시점에는 `order.getOrderBid()`가 아직 null이므로(OrderBid는 9단계에서 생성) SaleBid 쪽 경로를 탄다. `saleBidQueryService.findByOrderId`로 SaleBid를 찾아 그 `sale`을 `SOLD`로 바꾼다 — `PaymentCommandService.java:388-406`, `sale/service/query/SaleBidQueryService.java:26-29`. `Sale.updateStatus`는 전이 검증 없이 값을 대입한다 — `sale/entity/Sale.java:73-75`.
- 입력 검증이 느슨한 점: SaleBid가 이미 `MATCHED`인지, 본인 입찰인지는 검사하지 않는다 (`OrderBidCommandService.java:172-184`). 클라이언트가 보낸 `paidAmount`를 SaleBid 가격과 비교하지도 않는다 (`PaymentCommandService.java:117-146`은 주문 ID·이메일·0 이상 금액만 검사).

## 3. 결제 수단별 결과

결제 유형 분기: `PaymentCommandService.java:67-80` (CARD / ACCOUNT / GENERAL, 그 외는 `PAYMENT_VALIDATION_FAILED`).

| 결제 수단 | 동작 | Payment 상태 | 근거 |
|---|---|---|---|
| 카드 (CARD) | 저장된 PaymentInfo 조회 → PortOne 즉시 결제 API 동기 호출 → CardPayment 저장 | 응답 `status`가 문자열 `"success"`일 때만 `PAID`+isSuccess=true. 아니면 기본값 `PENDING`, isSuccess=false | `PaymentCommandService.java:166,179,187-208`, 기본값 `P/entity/Payment.java:39,44` |
| 계좌이체 (ACCOUNT) | 은행명만 enum 검증, 외부 호출 없음 | 항상 `PENDING` (이 흐름에서 `PAID`로 바꾸는 곳 없음) | `PaymentCommandService.java:244,250-262` |
| 일반 결제 (GENERAL) | impUid 존재만 확인, PG 검증 호출 없음 | 즉시 `PAID`, isSuccess=true | `PaymentCommandService.java:297-316` |

- **즉시 구매가 끝까지 성공하는지**: 수단과 무관하게 예외만 안 나면 요청은 "성공"으로 끝난다. 계좌이체(PENDING)와 카드 응답이 `"success"`가 아닌 경우에도 아래가 그대로 진행되어 `200 OK "즉시 구매가 성공적으로 처리되었습니다."`가 나간다 (`OrderBidCommandController.java:109`).
  - 알림 발송 (`PaymentCommandService.java:83,416`), Sale `SOLD` (`:419`), SaleBid `MATCHED`, OrderBid `MATCHED`.
  - 결제 성공 여부(`Payment.status`)를 `createInstantOrder`가 확인하지 않는다. 반환된 Payment도 버려지고 `order.assignPayment`도 호출하지 않는다 — `OrderCommandService.java:305` (반환값 미사용), 대조: 별도 흐름 `:139-140`.
- **카드가 실패 응답을 줄 때**: 실패의 형태에 따라 다르다.
  1. PortOne HTTP 상태가 200이 아니거나 응답 `code != 0`: `PaymentProcessingException` 발생 — `P/portone/PortOneApiClient.java:270-275`. 이는 `OrderPaymentProcessingFailedException`으로 감싸져(`OrderCommandService.java:306-309`) `createInstantOrderBid`의 `@Transactional`이 롤백된다. Order·OrderItem·OrderShipment·SaleBid 매칭·창고 상태 변경이 전부 취소되고 OrderBid도 만들어지지 않는다. 클라이언트는 오류 응답을 받는다 (`OrderBidCommandService.java:145-147,212-218`). 통신 오류(`PaymentApiException`)는 `@Retryable`로 최대 3회 재시도 대상이다 (`PortOneApiClient.java:224-228,288-290`).
  2. PortOne이 `code == 0`으로 응답하면서 결제 `status`가 `"success"`가 아닌 경우(예: 카드사 승인 실패 `failed`): 예외가 없다. CardPayment가 `PENDING`/isSuccess=false로 저장되고(`PaymentCommandService.java:203-208`) 위 "끝까지 성공" 경로로 흘러간다. 즉, 구매자·판매자에게 "결제 완료" 알림이 가고 Sale이 `SOLD`가 된다.
  3. 반대로 코드는 성공 상태를 `"success"` 문자열 비교로만 인정한다 (`:203`). PortOne의 `response.status`가 다른 값(예: 승인 성공 시의 `paid`)이면 승인된 결제도 `PENDING`으로 남는다.

## 4. 알림 대상과 전달 방식

- 발송 위치: `PaymentCommandService.notifyUsersAndUpdateSaleStatus` → `sendNotifications` — `PaymentCommandService.java:383-462`. 결제 처리(`processPayment`) 끝에서 호출된다 (`:83`).
- 수신자와 내용 (카테고리 `SHOPPING`, 타입 `BID`):
  - 구매자: "결제가 완료되었습니다. 주문 ID: {orderId}" — `:437-443`.
  - 판매자(`sale.getSeller()`): "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}" — `:447-454`.
  - 다른 수신자는 없다. 계좌이체 PENDING, 카드 PENDING에도 같은 "결제 완료" 문구가 간다(결제 상태를 확인하지 않음).
- 전달 방식: **동기 호출**이며 같은 요청·같은 트랜잭션 안이다. `NotificationCommandService.createNotification`이 DB에 Notification을 저장하고(`notification/service/command/NotificationCommandService.java:44-54`), 이어서 실시간 전송을 시도한다(`:57`).
  - 실시간 전송은 Redis 키 `WebSocket:User:{email}`가 있는(= WebSocket 연결된) 사용자에게만 STOMP `/queue/notifications`로 `convertAndSendToUser` 한다 — `:37-38,303-313`. 연결이 없으면 DB 저장만 한다 (`:320-322`).
  - Kafka 이벤트가 아니다. 알림 실패는 로그만 남기고 삼킨다 (`PaymentCommandService.java:457-461`, 바깥 `:421-425`).
  - 알림은 결제 직후(Sale `SOLD` 변경 직전, `:416-419`)에 보내지고, 이후 OrderBid 저장 단계(`OrderBidCommandService.java:142`)가 실패해 롤백되면 DB의 알림 저장분은 롤백되지만 이미 나간 WebSocket 푸시는 되돌릴 수 없다.

## 5. 최종 주문 상태와 창고 보관 선택 시

- 최종 `Order.status`: **`PENDING_PAYMENT` (결제 대기)** 이다. `createInstantOrder`는 Order를 `PENDING_PAYMENT`로 만들고(`OrderCommandService.java:244`) 이후 `order.updateStatus(...)`를 한 번도 호출하지 않는다 (`:219-319` 전체에 없음). 결제가 `PAID`여도, 즉시 구매 응답이 "성공"이어도 마찬가지다. `PAYMENT_COMPLETED`/`PREPARING` 등으로 바꾸는 코드는 별도 API(`/orders/{orderId}/process-payment-shipment`)의 `processPaymentAndShipment`(`OrderCommandService.java:162-177`)와 Kafka 컨슈머(`O/service/kafka/OrderEventConsumer.java:192-195`)에만 있고, 즉시 구매 흐름은 이를 호출하지 않는다.
  - 함께 남는 최종 상태: OrderBid `MATCHED`(`isInstantPurchase=true`), SaleBid `MATCHED`, Sale `SOLD`, Shipment `PENDING`, Payment는 결제 수단에 따라 `PAID` 또는 `PENDING`. `Order.payment` 필드는 연결되지 않는다 (`assignPayment` 미호출).
- 구매자가 "창고 보관"(`warehouseStorage=true`)을 선택한 경우: **아무것도 달라지지 않는다.**
  - 컨트롤러는 값을 전달하고(`OrderBidCommandController.java:105`), `OrderBidCommandService`도 넘기지만(`:137`), `createInstantOrder`의 `isWarehouseStorage` 파라미터는 메서드 본문에서 한 번도 읽히지 않는다 (`OrderCommandService.java:220-319`).
  - 구매자용 창고 보관 레코드 생성(`warehouseStorageCommandService.createOrderStorage`, 상태 `IN_STORAGE`/`IN_WAREHOUSE`/`COMPLETED`로 이어지는 코드)은 `processPaymentAndShipment`에만 있으며(`OrderCommandService.java:163-172`, `WarehouseStorageCommandService.java:33-55`) 즉시 구매 경로에서는 실행되지 않는다. 따라서 `WarehouseStorage`가 새로 만들어지지 않고 주문 상태도 `IN_WAREHOUSE`나 `COMPLETED`가 되지 않는다.
  - 창고 관련 코드가 실제로 도는 조건은 구매자 선택이 아니라 **판매 건(Sale)의 `isWarehouseStorage`** 이다 (`OrderCommandService.java:291-293`, `sale/entity/Sale.java:43`). 이 경우 판매자의 기존 창고 레코드가 `ASSOCIATED_WITH_ORDER`로 바뀐다. 해당 레코드가 없으면 `WarehouseStorageNotFoundException`이 나 `OrderWarehouseStorageProcessingFailedException`으로 감싸져 전체 즉시 구매가 롤백된다 (`WarehouseStorageQueryService.java:30-33`, `OrderCommandService.java:295-300`).
  - 배송지는 구매자 선택과 무관하게 항상 addressId로 조회해 `OrderShipment`가 생성된다 (`OrderCommandService.java:238,264-271`).
