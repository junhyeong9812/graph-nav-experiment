# 즉시 구매 처리 흐름 분석

대상: 일반 구매자용 `order` 도메인 (`/order-bids/instant`).
같은 구조의 복제본(`legacyorder`, `internalorder`, `settlementorder`, `partnerorder`)이 있으나 URL 접두어만 다르다(`/legacy/…`, `/internal/…`, `/settlement/…`, `/partner/…`).
경로는 `src/main/java/com/fream/back/domain/` 기준으로 쓴다.

## 1. 진입 API, 처리 단계, 동기/비동기, 응답 ID

**API**: `POST /order-bids/instant`
- 클래스 매핑 `@RequestMapping("/order-bids")`: `order/controller/command/OrderBidCommandController.java:22`
- 메서드 매핑 `@PostMapping("/instant")`: `OrderBidCommandController.java:89-90`
- 요청 본문 `InstantOrderRequestDto`는 `saleBidId`, `addressId`, `warehouseStorage`, `paymentRequest`를 가진다: `order/dto/InstantOrderRequestDto.java:20-29`

**처리 단계**
1. 컨트롤러가 인증 이메일을 추출한다(`OrderBidCommandController.java:92`).
2. `enrichPaymentRequest`가 `userEmail`을 로그인 사용자 이메일로 덮어쓰고 `orderId`를 null로 둔다(`OrderBidCommandController.java:98`, `:119-123`).
3. `OrderBidCommandService.createInstantOrderBid`를 호출한다(`OrderBidCommandController.java:101-107`). 이 메서드는 `@Transactional` 하나로 아래를 모두 묶는다(`order/service/command/OrderBidCommandService.java:118-149`).
   1. 입력 null 검증(`:123`, `:154-167`).
   2. 구매자 조회(`:126`).
   3. SaleBid 조회 및 `Sale` 존재 검증(`:129-130`, `:172-184`). SaleBid의 상태(이미 매칭되었는지)는 검증하지 않는다.
   4. `OrderCommandService.createInstantOrder` 호출(`:133-139`). 안에서 순서대로 다음을 한다(`order/service/command/OrderCommandService.java:220-319`).
      - 주소 조회(`:238`)
      - Order 생성(`:241-247`)
      - OrderItem 생성(`:255-256`)
      - OrderShipment 생성(`:264-271`)
      - SaleBid 매칭 및 flush(`:279-283`)
      - 판매자 창고 상태 변경(`:291-293`)
      - 결제 처리(`:305`)
   5. OrderBid 생성·저장(`OrderBidCommandService.java:142`, `:189-207`).

**동기/비동기**: **완전 동기**이다.
- 주문, 결제(PortOne HTTP 호출 포함), 알림 저장이 모두 요청 스레드에서 하나의 트랜잭션으로 끝난다.
- Kafka를 쓰지 않는다. Kafka 비동기 경로(`OrderEventProducer`)는 이미 존재하는 주문을 처리하는 별도 API `POST /orders/{orderId}/process-payment-shipment`(202 Accepted)에만 있고, 즉시 구매 경로에서는 호출되지 않는다: `order/controller/command/OrderCommandController.java:42-54`, `:68`.

**응답**: HTTP 200, `ResponseDto<Long>`, 메시지 "즉시 구매가 성공적으로 처리되었습니다."(`OrderBidCommandController.java:109`).
- 변수명은 `orderId`이지만 `createInstantOrderBid(...).getId()`는 반환된 **OrderBid의 ID**이다(`OrderBidCommandController.java:101-107`, 서비스 반환 타입 `OrderBid`: `OrderBidCommandService.java:119`).
- 주문(Order) ID가 아니다.

## 2. 생성되는 엔티티와 상태 변화 순서

한 트랜잭션 안에서 아래 순서로 일어난다.

| 단계 | 동작 | 직후 상태 | 근거 |
|---|---|---|---|
| 0 | (사전) SaleBid | `PENDING`(빌더 기본값). 검증 없이 사용됨 | `sale/entity/SaleBid.java:35-37`, `OrderBidCommandService.java:172-184` |
| 1 | **Order** 신규 생성·저장 | `Order.status = PENDING_PAYMENT`, `totalAmount = saleBid.bidPrice` | `OrderCommandService.java:241-247` |
| 2 | **OrderItem** 신규 생성(수량 1, 가격=입찰가) | 상태 필드 없음. Order에 연결 | `OrderCommandService.java:255-256`, `order/service/command/OrderItemCommandService.java:45-52` |
| 3 | **OrderShipment** 신규 생성, `order.assignOrderShipment` | `ShipmentStatus.PENDING` | `OrderCommandService.java:264-271`, `shipment/service/command/OrderShipmentCommandService.java:61-68` |
| 4 | **SaleBid** 갱신: `assignOrder(order)` 후 `updateStatus(MATCHED)`, `entityManager.flush()` | `SaleBid.status = MATCHED` | `OrderCommandService.java:279-283`, `SaleBid.java:58-61`, `:66-68` |
| 5 | (판매 `Sale.isWarehouseStorage == true`인 경우만) 판매자의 **WarehouseStorage** 갱신 | `WarehouseStatus.ASSOCIATED_WITH_ORDER` | `OrderCommandService.java:291-293`, `warehouseStorage/service/command/WarehouseStorageCommandService.java:117-133` |
| 6 | **Payment**(Card/Account/General) 신규 생성 | 결제 수단별로 다름(→ 3번) | `OrderCommandService.java:305`, `payment/service/command/PaymentCommandService.java:67-80` |
| 7 | 결제 직후 **Sale** 갱신 | `Sale.status = SOLD` | `PaymentCommandService.java:83`, `:388-405`, `sale/entity/Sale.java:73-74` |
| 8 | **OrderBid** 신규 생성, `assignOrder`, `markAsInstantPurchase` | `OrderBid.status = MATCHED`, `isInstantPurchase = true`, `sale` 연결 | `OrderBidCommandService.java:192-206`, `order/entity/OrderBid.java:60-82`, `:97-99` |

**Order.status는 단계 1 이후 바뀌지 않는다.**
- `createInstantOrder`에는 `order.updateStatus(...)` 호출이 없다(`OrderCommandService.java:220-319`).
- `PAYMENT_COMPLETED`, `PREPARING` 등으로의 전이 코드는 `processPaymentAndShipment`(`:111-202`)와 Kafka 소비자(`order/service/kafka/OrderEventConsumer.java:192-217`)에만 있다. 이들은 즉시 구매에서 호출되지 않는다.
- `Payment`는 `payment.assignOrder(order)`로 Payment 쪽에서만 연결되고, `order.assignPayment(...)`는 호출되지 않는다(`PaymentCommandService.java:200`, `:258`, `:311` 대비 `OrderCommandService.java:305`).

**Sale이 SOLD가 되는 경로**
- 결제 시점에 `order.getOrderBid()`는 아직 null이다. OrderBid는 결제 이후(단계 8)에 만들어진다.
- 그래서 `PaymentCommandService`는 `orderBid == null` 분기(`:388-407`)를 탄다.
- 이 분기는 `saleBidQueryService.findByOrderId`(`:391`, `sale/service/query/SaleBidQueryService.java:26-29`)로 단계 4에서 연결한 SaleBid를 찾아 `Sale`을 얻고 알림 후 `SOLD`로 바꾼다(`:403-405`).
- 이 갱신은 결제가 PAID인지와 무관하게 실행된다(3번 참고).

## 3. 결제 수단별 결과, 성공 여부, 카드 실패 시 동작

분기: `PaymentCommandService.java:67-80` (`getResolvedPaymentType`: `payment/dto/PaymentRequestDto.java:74-87`).

| 수단 | 처리 | Payment 상태 | isSuccess / paymentDate | 근거 |
|---|---|---|---|---|
| CARD | 저장된 PaymentInfo 조회 후 `portOneApiClient.processCardPayment` 호출(동기 HTTP) | 응답 `status == "success"`이면 `PAID`, 아니면 기본값 `PENDING` | success일 때만 true + 결제일시 기록 | `PaymentCommandService.java:166`, `:179`, `:203-208` |
| ACCOUNT | 은행명(`Bank` enum)만 검증하고 PG 호출 없이 저장 | `PENDING` | false(기본값), paymentDate 없음 | `PaymentCommandService.java:244`, `:250-262`, `payment/entity/Payment.java:39`, `:44` |
| GENERAL | `impUid`가 비어 있지 않은지만 검증. PG 재검증 없이 클라이언트가 준 값을 신뢰 | 즉시 `PAID` | true | `PaymentCommandService.java:297-314` |

**즉시 구매는 끝까지 성공한다(예외가 나지 않으면).**
- 계좌이체의 `PENDING`이나 카드의 `PENDING`(성공이 아닌 응답)이어도 예외 없이 `processPayment`가 반환된다.
- 이어서 `notifyUsersAndUpdateSaleStatus`가 실행되어 "결제가 완료되었습니다" 알림이 발송되고 Sale이 `SOLD`가 된다(`PaymentCommandService.java:83`, `:442`).
- `Order`는 `PENDING_PAYMENT`로 남은 채 응답은 성공이다.
- 결제 금액이 SaleBid 가격과 일치하는지는 검증하지 않고 0 초과만 확인한다(`PaymentCommandService.java:141-145`).

**결제 대행사(PortOne)가 카드 결제를 실패로 응답할 때**
- (a) **HTTP 비정상 또는 응답 `code != 0`**
  - `PaymentProcessingException`을 던진다(`payment/portone/PortOneApiClient.java:270-275`).
  - 이 예외는 재시도 대상이 아니다. `@Retryable`은 `PaymentApiException`만 대상이다(`:224-228`).
  - `createCardPayment`가 이를 전파한다(`PaymentCommandService.java:218-219`, `:220-223`).
  - `OrderCommandService`가 `OrderPaymentProcessingFailedException`으로 감싼다(`OrderCommandService.java:306-309`).
  - 이후 `OrderBidCommandService.handleOrderBidCreationException`이 다시 던진다(`OrderBidCommandService.java:145-147`, `:212-218`).
  - `GlobalException`은 `RuntimeException`이므로(`global/exception/GlobalException.java:10`) `@Transactional`이 **전체 롤백**한다. 롤백되는 대상은 Order, OrderItem, OrderShipment, SaleBid 매칭, 창고 상태, Payment이다.
  - 이 경우 알림은 보내지지 않는다(알림은 결제 성공 반환 이후 단계).
- (b) **HTTP 200, `code == 0`인데 `response.status`가 "success"가 아닌 경우**
  - 예외가 나지 않는다.
  - `CardPayment`는 상태 `PENDING`, `isSuccess=false`로 저장된다(`PaymentCommandService.java:203-208`).
  - 이후 흐름은 위의 계좌이체와 동일하다. 구매자·판매자 알림이 발송되고 Sale이 `SOLD`가 되며 OrderBid가 `MATCHED`로 생성된다. 성공 응답이 나간다.
  - 코드에는 `PaymentStatus.FAILED` 설정이나 `else` 처리가 없다(`PaymentStatus`에는 `FAILED`가 정의만 되어 있다: `payment/entity/PaymentStatus.java:8`).
  - 즉 (b)는 "결제 실패인데 구매가 성립"하는 실제 동작이다.

## 4. 알림 수신자, 시점, 전달 방식

**수신자 (두 명)**: `PaymentCommandService.sendNotifications` (`:434-462`)
- **구매자** `order.getUser()`: "결제가 완료되었습니다. 주문 ID: {orderId}" (`:436-443`)
- **판매자** `sale.getSeller()`: "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}" (`:447-454`)
- 두 알림 모두 `NotificationCategory.SHOPPING`, `NotificationType.BID`이다.

**시점**
- 요청 처리 중 `Payment` 저장 직후, `Sale.updateStatus(SOLD)` 직전, 같은 요청·같은 트랜잭션 안이다(`PaymentCommandService.java:83`, `:403-405`).
- 메시지 문구와 달리 계좌이체나 카드 비성공 응답(`PENDING`)이어도 발송된다.
- 알림 전송과 상태 갱신의 예외는 삼키고 로그만 남긴다(`:421-425`, `:457-461`).

**방식** (`notification/service/command/NotificationCommandService.java`)
1. DB에 `Notification` 저장(`:52-53`).
2. 실시간 전송 `sendRealTimeNotification`(`:303-324`).
   - Redis 키 `WebSocket:User:{email}`가 있을 때만(`:307`) WebSocket `/queue/notifications`로 `convertAndSendToUser`를 보낸다(`:310-314`, 상수 `:37-38`).
   - 연결이 없으면 DB에만 저장된다(`:321-323`).
   - 푸시 실패는 예외 없이 경고 로그만 남긴다.
- 이메일, SMS, Kafka 발행은 없다.

## 5. 최종 주문 상태와 창고 보관 선택 시 차이

**최종 상태**
- `Order.status = PENDING_PAYMENT` (결제 대기)이다. 즉시 구매가 끝난 뒤에도 갱신되지 않는다(2번 근거: `OrderCommandService.java:241-245`, 이후 `updateStatus` 없음).
- 결제 수단과 무관하게 `PAYMENT_COMPLETED`가 아니다. 카드 `PAID`나 일반 결제 `PAID`여도 마찬가지이다.
- 함께 남는 상태는 다음과 같다. Payment는 `PAID`(카드 성공, 일반) 또는 `PENDING`(계좌이체, 카드 비성공 응답), SaleBid `MATCHED`, OrderBid `MATCHED`(즉시 구매 플래그 true), Sale `SOLD`, OrderShipment `PENDING`.

**구매자가 "창고 보관"(`warehouseStorage=true`)을 선택한 경우: 사실상 차이가 없다.**
- 값은 컨트롤러에서 서비스로 전달된다(`OrderBidCommandController.java:105`, `OrderBidCommandService.java:137`, `OrderCommandService.java:221`).
- 그러나 `createInstantOrder` 본문에서 `isWarehouseStorage` 인자를 읽는 곳이 없다(`OrderCommandService.java:222-318`).
- 따라서 다음이 모두 일어나지 않는다.
  - 구매자용 `WarehouseStorage` 생성(`createOrderStorage` 호출 없음)
  - `IN_WAREHOUSE`, `COMPLETED`로의 상태 전이
  - `OrderShipment` 생성 생략(배송지로 항상 생성됨: `:264-271`)
- 같은 `createOrderStorage`와 `IN_WAREHOUSE → COMPLETED` 전이는 `processPaymentAndShipment`(`OrderCommandService.java:163-172`)와 Kafka 소비자(`OrderEventConsumer.java:199-210`)에만 구현되어 있다. 즉시 구매 경로에서는 쓰이지 않는다.
- 창고와 관련해 실제로 동작하는 것은 **판매자 쪽** 플래그 `Sale.isWarehouseStorage`뿐이다. 이것이 true이면 그 판매의 `WarehouseStorage`가 `ASSOCIATED_WITH_ORDER`로 바뀐다(`OrderCommandService.java:291-293`, `sale/entity/Sale.java:43`).
- 구매자의 선택은 응답과 저장 결과 어디에도 반영되지 않는다.

## 주석/이름과 실제 동작이 다른 곳 요약

- 응답의 `orderId`는 OrderBid ID이다(`OrderBidCommandController.java:101-109`).
- "결제가 완료되었습니다" 알림은 결제 성공 여부와 무관하게 발송된다(`PaymentCommandService.java:83`, `:442`).
- 카드 비성공 응답이 `code=0`이면 예외가 아니라 `PENDING`으로 저장되고 구매는 성립한다(`PaymentCommandService.java:203-208`, `PortOneApiClient.java:270`).
- 메서드명·Javadoc의 `isWarehouseStorage` 인자는 사용되지 않는다(`OrderCommandService.java:220-221`).
- `createInstantOrder`는 즉시 구매 "주문 생성"이라 하지만 주문 상태를 `PENDING_PAYMENT`에서 올리지 않는다(`OrderCommandService.java:244`).
