# 구매자 배송: 운송장 등록 → 배송 완료

경로 약어: `S` = `src/main/java/com/fream/back/domain/shipment/`, `O` = `src/main/java/com/fream/back/domain/order/`, `G` = `src/main/java/com/fream/back/global/`, `SALE` = `src/main/java/com/fream/back/domain/sale/`, `N` = `src/main/java/com/fream/back/domain/notification/`.

## 0. 전제: 결제 후 배송 정보와 주문 상태

- 결제·배송 처리 API(`OrderCommandController#processPaymentAndShipment`)는 동기 처리가 아니라 Kafka 이벤트만 발행하고 202를 돌려준다. `O controller/command/OrderCommandController.java:54`, `:68`
- 실제 처리는 `OrderEventConsumer#processCompleteOrder`. 결제 → `createOrderShipment`(배송 정보, 상태 PENDING) → 주문 PAYMENT_COMPLETED. 실배송이면 PREPARING에서 멈춘다. `O service/kafka/OrderEventConsumer.java:181`, `:195`, `:216-217`
- 같은 로직의 동기 버전(`OrderCommandService#processPaymentAndShipment`)도 실배송이면 PAYMENT_COMPLETED → PREPARING까지만 간다. `O service/command/OrderCommandService.java:175-176`
- 배송 정보 생성 시 상태는 `ShipmentStatus.PENDING`. `S service/command/OrderShipmentCommandService.java:67`
- 즉시 구매(`createInstantOrder`)는 주문을 PENDING_PAYMENT로 만들고 배송 정보(PENDING)를 만든 뒤 `SaleBid.assignOrder(order)`로 SaleBid에 주문을 연결한다. 결제(`processPayment`)는 주문 상태를 바꾸지 않는다. 즉시 구매 주문은 PENDING_PAYMENT로 남는다. `O service/command/OrderCommandService.java:244`, `:264`, `:279`, 결제 도메인에는 OrderStatus 변경이 없음(`domain/payment` 전체 grep 결과 없음)
- OrderBid는 즉시 구매에서만 `markAsInstantPurchase()`와 `sale` 연결이 생기고, 일반 입찰은 `Order`만 연결된다(SaleBid는 `order`에 연결되지 않음). `O service/command/OrderBidCommandService.java:198`, `:205`(즉시 구매), 일반 입찰은 `:100`

## 1. 운송장 등록 요청

### 1-1. 어느 API로 들어오나
- `PATCH /shipments/order/{shipmentId}/status` → `OrderShipmentCommandController#updateTrackingInfo` → `OrderShipmentCommandService#updateTrackingInfo(shipmentId, courier, trackingNumber)`. `S controller/command/OrderShipmentCommandController.java:20`, `:33-48`
- 같은 컨트롤러에 `POST .../check-status`, `.../check-status-string`이 있다. 이쪽은 운송장을 넣고 CJ 조회까지 즉시 수행하는 별도 경로(`updateAndCheckShipmentStatus`)다. `S controller/command/OrderShipmentCommandController.java:58`, `:103`

### 1-2. 의도된 엔티티 상태 변경 순서와 알림 (`updateTrackingInfo`)
1. courier/trackingNumber가 비어 있으면 `TRACKING_INFO_REQUIRED`. `S service/command/OrderShipmentCommandService.java:243-246`
2. `OrderShipment` 조회 후 `updateTrackingInfo` → courier, trackingNumber 저장, 상태를 전이 검사 없이 IN_TRANSIT으로 직접 대입. `S service/command/OrderShipmentCommandService.java:256`, `S entity/OrderShipment.java:41-45`
3. `Order.updateStatus(IN_TRANSIT)`. `OrderStatus` 전이 규칙 검사를 받는다. `S service/command/OrderShipmentCommandService.java:259-260`, `O entity/Order.java:113-121`
4. 구매자에게 알림 "상품이 출발하였습니다. 주문 ID: …" 1건. `S service/command/OrderShipmentCommandService.java:265-271`
5. `updateSaleStatusToSold(orderId)` — Sale을 SOLD로 바꾸고 판매자에게 "상품이 성공적으로 판매 완료…" 알림(SaleBid 경로, 이어서 OrderBid 경로). 배송 출발 시점에 이미 판매 완료 처리하도록 짜여 있다. `S service/command/OrderShipmentCommandService.java:276`, `:111-183`
6. 창고 보관 Sale이면 창고 상태 SOLD 갱신. `S service/command/OrderShipmentCommandService.java:279-286`
7. `updateOrderAndSaleBidStatusToCompleted` — OrderBid와 SaleBid가 MATCHED면 COMPLETED. 예외는 삼키고 로그만 남김. `S service/command/OrderShipmentCommandService.java:289`, `:413-440`
   - 즉 운송장 등록만으로 Order IN_TRANSIT, 입찰 COMPLETED, Sale SOLD까지 가는 설계다. 택배사 조회 결과와 무관하다.

### 1-3. 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문(즉시 구매 아님) — 끝까지 성공하나? **실패한다**
- 이 주문의 Order 상태는 PREPARING(0절). `OrderStatus` 전이표에서 PREPARING → {IN_WAREHOUSE, SHIPMENT_STARTED}뿐이라 IN_TRANSIT은 허용되지 않는다. `O entity/OrderStatus.java:26`
- 실패 지점: `S service/command/OrderShipmentCommandService.java:260` `order.updateStatus(OrderStatus.IN_TRANSIT)` → `InvalidOrderStatusException`("상태 전환이 허용되지 않습니다: PREPARING -> IN_TRANSIT"). `O entity/Order.java:117-119`
- 이 예외는 `ShipmentException`이 아니므로 `catch (Exception e)`에 잡혀 `ShipmentException(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")`로 바뀌어 던져진다(원인 오류와 코드가 맞지 않음). `S service/command/OrderShipmentCommandService.java:295-301`
- 저장되는 것: 없음. 메서드가 `@Transactional`이고 런타임 예외가 밖으로 나가므로 전체 롤백. 메모리에서만 바뀐 courier/trackingNumber/IN_TRANSIT은 저장되지 않고 shipment는 PENDING·운송장 없음, 주문은 PREPARING 그대로. 알림(4단계)에 도달하기 전에 실패하므로 알림도 0건. `S service/command/OrderShipmentCommandService.java:238`
- 설령 주문 상태 검사를 통과해도, 일반 입찰엔 SaleBid가 주문에 연결되어 있지 않다. `SaleBidQueryService#findByOrderId`는 없을 때 null이 아니라 `IllegalArgumentException`을 던지므로 `updateSaleStatusToSold`의 `saleBid != null` 분기는 의미가 없고 같은 곳에서 실패한다. `SALE service/query/SaleBidQueryService.java:26-29`, `S service/command/OrderShipmentCommandService.java:116-117`
- 응답: 예외 핸들러가 `ShipmentException`을 `ErrorCode`의 상태로 변환 → **HTTP 404**, 본문 `ErrorResponse`(code `S001`, message "배송 정보를 찾을 수 없습니다."). `G exception/GlobalExceptionHandler.java:459-473`, `S exception/ShipmentErrorCode.java:12`
- 참고: `check-status` 경로도 같은 주문에선 실패한다. 운송장 저장 후 DELIVERED면 `completeOrder`가 PREPARING → COMPLETED(비허용)에서 예외가 난다. 이 경로는 컨트롤러가 직접 catch해 상태코드만 있는 빈 응답을 돌려준다(ORDER_NOT_FOUND_FOR_SHIPMENT → 404). `S service/command/OrderShipmentCommandService.java:489`, `:204`, `S controller/command/OrderShipmentCommandController.java:80-86`
- 결론: 일반 구매 입찰 주문은 이 API로는 운송장이 등록되지 않고 IN_TRANSIT 상태의 배송이 만들어지지 않는다. 따라서 아래 배치 대상(IN_TRANSIT/OUT_FOR_DELIVERY + 운송장 있음)에 들어오지 못한다.

## 2. 배송 완료 감지

### 2-1. 누가·언제·어떻게
- 주체: Spring Batch Job `updateShipmentStatusesJob`을 스케줄러가 실행한다. 사람이 호출하는 API가 아니다(수동 확인은 1-1의 check-status API). `G config/ShipmentBatchScheduler.java:34-41`, `S config/UpdateShipmentStatusesJobConfig.java:55-60`
- 주기: `@Scheduled(cron = "0 0 */6 * * *")` → **6시간마다**(00·06·12·18시 정각). 실행 시마다 timestamp 파라미터로 새 JobInstance를 만든다. `G config/ShipmentBatchScheduler.java:34-38`
- 대상: `status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND trackingNumber IS NOT NULL`인 `OrderShipment`을 페이지 50건 단위로 읽는다. `S config/UpdateShipmentStatusesJobConfig.java:95`, `:51`
- 방식: 택배사 조회 페이지(CJ대한통운 `trace.cjlogistics.com`)를 Playwright로 열어 `tbody#statusDetail tr` 마지막 행의 5번째 `td` 텍스트를 읽는다. `S config/ShipmentItemProcessor.java:81-94`, `:167-191`, `:28-29`

### 2-3. 택배사 상태 문자열 → 내부 상태
`ShipmentItemProcessor#mapToShipmentStatus` (`S config/ShipmentItemProcessor.java:220-226`)
- `"배송완료"` → `DELIVERED`
- `"배송출발"` → `OUT_FOR_DELIVERY`
- 그 외 모든 문자열(집화처리, 간선상차 등) → `IN_TRANSIT`
- 이후 처리: 현재 상태와 같으면 변경 없이 반환(`:101-105`), DELIVERED면 완료 처리(`:108-117`), OUT_FOR_DELIVERY면 상태만 변경(`:119-122`), 그 외 IN_TRANSIT(`:123-126`). 파싱 결과가 비어 있거나 표가 없으면 `TRACKING_HTML_PARSE_ERROR`. `:167-191`
- `OrderShipment#updateStatus`는 `ShipmentStatus` 전이표를 검사하고(IN_TRANSIT → DELIVERED/OUT_FOR_DELIVERY 허용, OUT_FOR_DELIVERY → IN_TRANSIT 불허) 위반 시 `IllegalStateException`. `S entity/OrderShipment.java:47-55`, `S entity/ShipmentStatus.java:16-28`

## 3. 배송 완료 판정 이후 (`ShipmentItemProcessor#process`의 DELIVERED 분기)

### 3-1. 엔티티 상태 변경 순서
1. `OrderShipment` → DELIVERED (`updateStatus`). `S config/ShipmentItemProcessor.java:113`
2. `OrderShipmentCommandService#completeOrder(orderId)` 호출. `S config/ShipmentItemProcessor.java:116`, `S service/command/OrderShipmentCommandService.java:190-229`
   1. `OrderBid` 조회(없으면 예외). `:196-197`
   2. `Order` → COMPLETED (`updateStatus`, 전이 규칙 적용). `:204`
   3. `updateSaleStatusToSold(orderId)`: SaleBid 조회 → Sale이 SOLD로 전이 가능하면 SOLD(창고 보관이면 창고 상태 SOLD 갱신) → OrderBid의 Sale을 다시 조회하나 이미 SOLD라 전이 불가로 건너뜀. `:208`, `:112-183`
   4. 구매자 알림 생성. `:211-217`
3. `NotificationCommandService#notifyShipmentCompleted(order)` — 구매자 알림. `S config/ShipmentItemProcessor.java:117`, `N service/command/NotificationCommandService.java:219-234`
4. Step Writer(`JpaItemWriter`)가 `OrderShipment`을 저장(merge). `S config/UpdateShipmentStatusesJobConfig.java:74`, `:239-246`

### 3-2. 알림 (성공 시 총 3건)
- 구매자 2건: "[completeOrder] 주문이 완료 처리되었습니다. 주문 ID: …"(`S service/command/OrderShipmentCommandService.java:212-217`) + "[배송 완료] 상품이 배송 완료되었습니다. 주문 ID: …"(`N service/command/NotificationCommandService.java:224-229`)
- 판매자 1건: "상품이 성공적으로 판매 완료되었습니다. 판매 ID: …"(`S service/command/OrderShipmentCommandService.java:133-138`). OrderBid 경로의 동일 알림은 Sale이 이미 SOLD라 발송되지 않는다(`:156`)

### 3-3. 입찰 상태
- 배치 경로는 `completeOrder`만 호출하고 `updateOrderAndSaleBidStatusToCompleted`를 호출하지 않는다. 따라서 OrderBid·SaleBid의 상태는 **변하지 않고 MATCHED 그대로**다. `completeOrder`/`updateSaleStatusToSold` 어디에도 입찰 상태 변경이 없다. `S service/command/OrderShipmentCommandService.java:190-229`, `:112-183`
- 입찰이 COMPLETED가 되는 곳은 1-2의 운송장 등록 API(`updateOrderAndSaleBidStatusToCompleted`, `:289`, `:413-440`)뿐이다. 이 경로는 위의 이유로 정상 상황에서 성공하지 못한다.

## 4. 주문 종류별 차이

### (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문 — 끝까지 진행되지 않는다
- 앞서 1-3에서 본 대로 운송장 등록 API가 실패하므로 배송은 PENDING·운송장 없음으로 남아 배치 조회 조건을 만족하지 못한다. `S config/UpdateShipmentStatusesJobConfig.java:95`
- 어떻게든 DELIVERED 판정이 나더라도 `completeOrder`가 `order.updateStatus(COMPLETED)`에서 PREPARING → COMPLETED 불가로 `InvalidOrderStatusException`을 던진다. `S service/command/OrderShipmentCommandService.java:204`, `O entity/OrderStatus.java:26`
- 주문이 IN_TRANSIT까지 갔다고 가정해도 SaleBid가 없어서 `updateSaleStatusToSold`가 `IllegalArgumentException`으로 실패한다. `S service/command/OrderShipmentCommandService.java:116`, `SALE service/query/SaleBidQueryService.java:26-29`
- 어느 경우든 `completeOrder`의 `catch (Exception)`이 `ShipmentException(ORDER_NOT_FOUND_FOR_SHIPMENT)`로 바꿔 던진다. `S service/command/OrderShipmentCommandService.java:221-227`. 결과: Order·Sale·입찰 모두 변화 없음, 알림 없음.

### (b) 즉시 구매로 만들어진 주문 — 3의 처리가 끝까지 진행된다(배송이 배치 대상이 된 경우)
- 즉시 구매 주문은 PENDING_PAYMENT(0절)이고 이 상태는 COMPLETED로 직접 전이가 허용된다. `O entity/OrderStatus.java:24`
- SaleBid가 주문에 연결돼 있어 `findByOrderId`가 성공하고 Sale이 SOLD로 전이된다. `SALE entity/SaleBid.java:58-61`, `S service/command/OrderShipmentCommandService.java:116-123`
- OrderBid는 `order`가 연결되어 조회된다. `O service/command/OrderBidCommandService.java:189-205`
- 결과: 배송 DELIVERED, Order COMPLETED, Sale SOLD(+창고 상태), 구매자 알림 2건, 판매자 알림 1건. OrderBid·SaleBid는 MATCHED로 남는다(3-3).
- 단, 이 주문의 배송이 배치 대상(IN_TRANSIT/OUT_FOR_DELIVERY)이 되려면 운송장 등록 API(`updateTrackingInfo`)가 아니라 `check-status` 경로가 필요하다. `updateTrackingInfo`는 PENDING_PAYMENT → IN_TRANSIT이 불가해 같은 이유로 실패한다(`O entity/OrderStatus.java:24`, `S service/command/OrderShipmentCommandService.java:260`). `check-status`는 주문 상태를 건드리지 않고 shipment만 IN_TRANSIT/OUT_FOR_DELIVERY로 바꾼 뒤 DELIVERED면 `completeOrder`를 즉시 호출한다. `S service/command/OrderShipmentCommandService.java:473-498`

## 5. 실패 처리 (주기 처리 중 한 건이 실패할 때)

- 대상 코드: Step이 `faultTolerant().skip(Exception.class).skipLimit(50)`, 청크 크기 50. `S config/UpdateShipmentStatusesJobConfig.java:67`, `:75-77`, `:51-52`
- Processor는 모든 예외를 `ShipmentException`으로(비 Shipment 예외는 `EXTERNAL_TRACKING_SERVICE_ERROR`로 래핑) 다시 던진다. `S config/ShipmentItemProcessor.java:133-145`
- 한 건이 예외를 던지면: 그 청크의 트랜잭션이 롤백되고(`completeOrder`가 청크 트랜잭션에 참여하며 변경·알림 DB 저장도 되돌려짐) 스킵 가능 예외이므로 Spring Batch가 청크를 항목별로 다시 처리한다. 실패한 건만 스킵되고 `onSkipInProcess`로 로그만 남으며 나머지 건은 정상 처리·저장된다. `S config/UpdateShipmentStatusesJobConfig.java:252-266`
- 스킵된 건은 DB 상태가 바뀌지 않아 여전히 IN_TRANSIT/OUT_FOR_DELIVERY이므로 6시간 뒤 다음 실행에서 다시 조회된다. `S config/UpdateShipmentStatusesJobConfig.java:95`
- 스킵이 50건을 넘으면 Step 자체가 실패한다(`skipLimit`). 스케줄러는 Job 실행 예외를 `printStackTrace()`로만 처리하고 다음 주기를 기다린다. `G config/ShipmentBatchScheduler.java:42-44`
- 참고로 사용되지 않는 `updateShipmentStatuses()`는 건별 try/catch로 계속 진행하는 구조지만 실행되지 않는다. `S service/command/OrderShipmentCommandService.java:322-387`
- 주의: 알림 서비스의 실시간 전송(WebSocket)은 DB 롤백과 무관하므로, 롤백된 청크의 알림은 DB에는 없고 이미 전송되었을 수 있다. (코드상 `createNotification` 안에서 `sendRealTimeNotification` 호출, `N service/command/NotificationCommandService.java:44-57`)
