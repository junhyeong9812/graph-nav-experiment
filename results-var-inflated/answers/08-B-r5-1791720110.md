# 구매자 배송: 운송장 등록 ~ 배송 완료 처리 분석

경로 약어: `S` = `src/main/java/com/fream/back`
(배송 코드는 `domain/shipment`, `adminshipment`, `partnershipment`, `settlementshipment`, `internalshipment`, `legacyshipment` 6벌로 복제돼 있다. 복제본들은 컨트롤러·잡 설정이 거의 동일하며, 아래에서는 실제로 쓰이는 쪽을 가려 적었다.)

## 사전: 결제·배송 처리 직후의 상태

- 결제·배송 처리는 `POST /orders/{orderId}/process-payment-shipment` → Kafka 이벤트 발행 → 컨슈머가 처리한다. (`S/domain/order/controller/command/OrderCommandController.java:42`, `:54`)
- 컨슈머 `processCompleteOrder`에서 결제 후 `OrderShipment`를 `PENDING`으로 생성한다. (`S/domain/shipment/service/command/OrderShipmentCommandService.java:62-69`)
  - 실배송이면 `Order`는 `PAYMENT_COMPLETED` → `PREPARING`에서 멈춘다. (`S/domain/order/service/kafka/OrderEventConsumer.java:195`, `:215-217`)
  - 동기 경로 `OrderCommandService.processPaymentAndShipment`도 결과가 같다. (`S/domain/order/service/command/OrderCommandService.java:175-176`) 이 경로는 컨트롤러가 주석 처리해서 쓰이지 않는다. (`OrderCommandController.java:90-101`)
- 일반 구매 입찰의 `OrderBid`는 `assignOrder`로 `MATCHED`가 된다. (`S/domain/order/entity/OrderBid.java:73-76`; 생성: `OrderBidCommandService.java:100`)
  - 일반 구매 입찰은 이 시점에 `SaleBid`와 연결되지 않는다. `SaleBid.order`는 즉시 판매/즉시 구매 때만 세팅된다. (`S/domain/sale/service/command/SaleBidCommandService.java:83`, `OrderCommandService.java:279`)
- `Order` 상태 전이표: `PREPARING`은 `IN_WAREHOUSE`/`SHIPMENT_STARTED`로만, `PENDING_PAYMENT`는 `PAYMENT_COMPLETED`/`COMPLETED`/`IN_WAREHOUSE`로만 갈 수 있다. `IN_TRANSIT`은 `COMPLETED`로만 갈 수 있다. (`S/domain/order/entity/OrderStatus.java:141-146`)
  - 허용되지 않는 전이는 `InvalidOrderStatusException`을 던진다. (`S/domain/order/entity/Order.java:113-120`)

## 1. 운송장 등록 요청

### 1-1. 어느 API로 들어오나

- `PATCH /shipments/order/{shipmentId}/status`, body는 `OrderShipmentRequestDto`(courier, trackingNumber). (`S/domain/shipment/controller/command/OrderShipmentCommandController.java:20`, `:33`, `:41`)
- 같은 서비스를 호출하는 복제 컨트롤러가 접두어만 바꿔 존재한다. (예: `/admin/shipments/order/{id}/status`, `S/domain/adminshipment/controller/command/AdminOrderShipmentCommandController.java:20`, `:30-47`)
  - `/partner`, `/settlement`, `/internal`, `/legacy`도 마찬가지다. 전부 `domain.shipment.service.command.OrderShipmentCommandService.updateTrackingInfo`로 간다.
- 인증은 SecurityConfig의 `anyRequest().authenticated()`뿐이다. 경로별 역할 제한은 없다. (`S/global/config/security/SecurityConfig.java:50-52`)
- 별도로 `POST /shipments/order/{id}/check-status`도 있다 (`OrderShipmentCommandController.java:58`). 이 API는 서비스의 `updateAndCheckShipmentStatus`(`OrderShipmentCommandService.java:455-505`)를 호출하며 운송장 등록과는 다른 경로다.

### 1-2. 상태가 바뀌는 순서와 알림 (코드가 의도한 순서)

`OrderShipmentCommandService.updateTrackingInfo` (`:239-305`)의 순서:

1. courier/trackingNumber가 비어 있으면 `TRACKING_INFO_REQUIRED`. (`:243-246`)
2. `OrderShipment.updateTrackingInfo`: courier·trackingNumber를 저장하고 `status`를 **검증 없이 `IN_TRANSIT`으로 직접 대입**한다. (`:256`, `S/domain/shipment/entity/OrderShipment.java:41-45`)
3. `Order.updateStatus(IN_TRANSIT)`. (`:259-260`)
4. 구매자에게 알림 "상품이 출발하였습니다. 주문 ID: …". (`:265-271`)
5. `updateSaleStatusToSold(orderId)`: `Sale`을 `SOLD`로 바꾸고 판매자에게 "판매 완료" 알림. (`:276`, `:112-148`)
6. 창고 보관이면 창고 상태를 sold로. (`:279-286`)
7. `updateOrderAndSaleBidStatusToCompleted`: `OrderBid`/`SaleBid`가 `MATCHED`이면 `COMPLETED`. (`:289`, `:413-440`)

즉 의도는 운송장 등록 시점에 이미 판매 완료와 입찰 COMPLETED까지 처리하는 것이다. 배송 완료 시점이 아니라 출발 시점이라서 이름·의도와 어긋나 있다.

### 1-3. 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문에서 끝까지 성공하나 → 실패한다

- **어디서 / 왜**
  - 위 3단계 `order.updateStatus(OrderStatus.IN_TRANSIT)`(`OrderShipmentCommandService.java:260`)에서 실패한다.
  - 이 주문은 `PREPARING` 상태다. `PREPARING → IN_TRANSIT`은 전이표에 없다. (`OrderStatus.java:143`, `Order.java:114-119`)
  - `InvalidOrderStatusException`이 발생한다.
- **어떻게 변환되나**
  - 메서드 안의 `catch (Exception e)`가 `ShipmentException(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")`으로 감싼다. (`:292-299`)
  - 원인은 상태 전이 오류인데 에러코드는 `SHIPMENT_NOT_FOUND`다. (`S/domain/shipment/exception/ShipmentErrorCode.java:12`)
- **무엇이 저장되나: 아무것도 저장되지 않는다**
  - `ShipmentException`은 `GlobalException extends RuntimeException`이다. (`S/global/exception/GlobalException.java:10`)
  - `@Transactional`(`:238`)이 롤백되므로 2단계에서 메모리에서만 바뀐 courier/trackingNumber/`IN_TRANSIT`은 DB에 반영되지 않는다.
  - 알림(4단계)과 판매 처리(5단계)는 실패 지점 뒤라 실행되지 않는다.
  - 결과: 배송은 `PENDING`, 운송장 없음, 주문은 `PREPARING` 그대로다.
- **응답**
  - `GlobalExceptionHandler.handleGlobalException`이 `ErrorResponse(code="S001", message="배송 정보를 찾을 수 없습니다.", status=404, path)`을 **HTTP 404**로 내려보낸다. (`S/global/exception/GlobalExceptionHandler.java:49-63`)
- **참고(메서드 이름과 실제 동작 차이)**: 운송장 등록 요청 한 건으로는 배송을 `IN_TRANSIT`으로 만들 수 없다. `OrderShipment`에는 `PENDING → IN_TRANSIT`을 열어 주는 다른 경로가 없고, `updateTrackingInfo`가 직접 대입하는 것이 유일하다.

## 2. 배송 완료 감지

### 2-1. 누가 / 언제 / 어떻게

- 스프링 배치 잡 `updateShipmentStatusesJob`을 `ShipmentBatchScheduler`가 `@Scheduled`로 실행한다. (`S/global/config/ShipmentBatchScheduler.java:30-31`)
  - **주기: `cron = "0 0 */6 * * *"` → 매일 00·06·12·18시 정각, 6시간마다.** (`:30`)
  - `timestamp` 파라미터로 매번 새 JobInstance를 만든다. (`:33-36`)
- 사용자 API가 즉시 조회하는 경로도 별도로 있다 (`/check-status`, 1-1 참고). 자동 감지는 위 스케줄러뿐이다.
- 서비스의 `OrderShipmentCommandService.updateShipmentStatuses()`(`:309`)는 CJ 조회 후 완료 처리까지 하는 비슷한 코드지만, **호출하는 곳이 없다**(저장소 전체 검색에서 정의만 존재). 실행되지 않는다.

### 2-2. 어떤 배송을 조회하나

- 리더 쿼리: `SELECT s FROM OrderShipment s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL`. (`S/domain/shipment/config/UpdateShipmentStatusesJobConfig.java:95`)
- 페이지 크기 50, 청크 50. (`:51`, `:94`)

### 2-3. 실제로 실행되는 처리 코드

- 같은 빈 이름 `updateShipmentStatusesJob`이 6개의 `@Configuration`에 중복 정의되어 있다. (`UpdateShipmentStatusesJobConfig.java:55`, `S/domain/adminshipment/config/AdminUpdateShipmentStatusesJobConfig.java:55`, `partnershipment/…:55`, `settlementshipment/…:55`, `internalshipment/…:55`, `legacyshipment/…:55`)
  - 스케줄러는 `@Qualifier("updateShipmentStatusesJob")`으로 주입받는다. (`ShipmentBatchScheduler.java:19-21`)
  - 복제본들은 알림 서비스·레포지토리 타입만 다르고 로직이 같다.
  - `application*.yml`에 `allow-bean-definition-overriding` 설정이 없어 기본값(false)이면 기동 시 같은 이름 빈 충돌이 날 수 있다. 이 점은 코드만으로 확정하지 못했다.
  - 실제 사용되는 것은 기본(`domain.shipment`) 설정으로 보고 답한다. 스케줄러가 이 도메인의 서비스·알림을 쓰고, 기본 도메인이 컴포넌트 스캔 순서상 마지막이다.
- **Step의 processor는 `shipmentItemProcessor()` 빈(`:104-177`)이 아니라 `new ShipmentItemProcessor(...)`다.** (`UpdateShipmentStatusesJobConfig.java:69-73`)
  - 같은 설정 안의 `shipmentItemProcessor()` 빈, `parseCjLogisticsStatus`(`:186`), `mapToShipmentStatus`(`:228`)는 step에 연결되지 않은 죽은 코드다. (`CjTrackingPlaywright`/Jsoup 직접 조회 버전)
  - 실제 실행 코드는 `S/domain/shipment/config/ShipmentItemProcessor.java:57-157`이다.
- 처리 흐름은 Playwright(브라우저)로 `https://trace.cjlogistics.com/next/tracking.html?wblNo=<운송장>`을 연다. (`ShipmentItemProcessor.java:28`, `:72-90`)
  - `tbody#statusDetail tr`의 **마지막 행 5번째 td** 텍스트를 상태 문자열로 쓴다. (`:181`)
  - 브라우저는 `BrowserManageStepListener`가 step 시작·종료 때 열고 닫는다. (`S/domain/shipment/config/BrowserManageStepListener.java:15-25`)
  - 택배사는 courier 값과 무관하게 항상 CJ대한통운 URL로 조회한다.

### 2-4. 택배사 상태 문자열 → 내부 상태

`ShipmentItemProcessor.mapToShipmentStatus` (`:220-226`):

| 문자열 | 내부 상태 |
|---|---|
| `"배송완료"` | `DELIVERED` |
| `"배송출발"` | `OUT_FOR_DELIVERY` |
| 그 외 전부 | `IN_TRANSIT` |

- 공백은 trim 하지만 정확한 문자열 일치(`switch`)다. 다른 표현("배달완료" 등)은 모두 `IN_TRANSIT`이 된다.
- 현재 상태와 같으면 변경 없이 반환한다. (`:101-105`)

## 3. 배송 완료 판정 이후

`ShipmentItemProcessor.process`의 `DELIVERED` 분기 (`:108-117`) 순서:

1. `OrderShipment.updateStatus(DELIVERED)`: 메모리상 변경. `IN_TRANSIT`/`OUT_FOR_DELIVERY`에서만 허용된다. (`:113`, `ShipmentStatus.java:72-84`)
2. `OrderShipmentCommandService.completeOrder(orderId)` (`:116`, `:191-226`)
   1. `OrderBid`를 `findByOrderId`로 조회한다. 없으면 `IllegalArgumentException`. (`:196-197`)
   2. `Order.updateStatus(COMPLETED)`. (`:204`)
   3. `updateSaleStatusToSold`: `SaleBid`→`Sale`을 `SOLD`로, 창고 보관이면 창고 상태 변경, 판매자 알림. (`:208`, `:112-148`)
   4. 구매자 알림 "[completeOrder] 주문이 완료 처리되었습니다". (`:211-217`)
   5. 어떤 예외든 `ShipmentException(ORDER_NOT_FOUND_FOR_SHIPMENT)`으로 감싼다. (`:219-225`)
3. `NotificationCommandService.notifyShipmentCompleted(order)`: 구매자 알림 "[배송 완료] …". (`:117`, `S/domain/notification/service/command/NotificationCommandService.java:219-234`)
4. Writer `JpaItemWriter`가 `OrderShipment`를 저장한다. (`UpdateShipmentStatusesJobConfig.java:239-246`)

### 알림: 총 3건

- 구매자 2건
  - "[completeOrder] 주문이 완료 처리되었습니다"
  - "[배송 완료] 상품이 배송 완료되었습니다"
- 판매자 1건: "상품이 성공적으로 판매 완료되었습니다. 판매 ID"
  - `Sale`이 `SOLD`로 전이 가능할 때만(`SELLING`/`ON_AUCTION`) 발송한다. (`SaleStatus.java`)
  - `SaleBid` 경로에서 `SOLD`가 되면 뒤의 `OrderBid` 경로는 `SOLD→SOLD`가 불가라 중복 발송되지 않는다. (`OrderShipmentCommandService.java:150-173`)

### 입찰 상태

- 배치의 배송 완료 경로에서는 `OrderBid`/`SaleBid` 상태를 **바꾸지 않는다.** `COMPLETED`로 바꾸는 `updateOrderAndSaleBidStatusToCompleted`(`:413`)는 `updateTrackingInfo`에서만 호출된다. (`:289`)
  - 따라서 둘 다 `MATCHED`로 남는다.
  - 단 `Order`는 `COMPLETED`, `Sale`은 `SOLD`가 된다.
- `/check-status`로 완료되는 경로(`updateAndCheckShipmentStatus`)도 `completeOrder`만 호출하므로 같다. (`:489`) 이 경로에는 `notifyShipmentCompleted`가 없어 구매자 알림은 1건뿐이다 (총 2건).

## 4. 주문 종류별 차이

### (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문 → 끝까지 진행되지 않는다

- 주문은 `PREPARING`이고 배송은 `PENDING`이다. 운송장 등록이 1-3처럼 롤백되므로 배송에 운송장이 없고 상태가 `PENDING`이라 배치 리더(`IN_TRANSIT`/`OUT_FOR_DELIVERY` + 운송장 있음)의 대상이 아니다.
- 운송장 등록 없이 `/check-status`가 carrier의 "배송출발"로 `OUT_FOR_DELIVERY`를 저장했다고 가정하더라도 다음에서 막힌다.
  - `completeOrder` 안의 `order.updateStatus(COMPLETED)`: `PREPARING → COMPLETED`는 전이표에 없다. (`OrderStatus.java:143`)
  - 일반 입찰에는 `SaleBid`가 연결되지 않아 `saleBidQueryService.findByOrderId`가 `null`이 아니라 `IllegalArgumentException`을 던진다. (`S/domain/sale/service/query/SaleBidQueryService.java:26-28`)
- 결과: `completeOrder`가 `ShipmentException(ORDER_NOT_FOUND_FOR_SHIPMENT)`을 던지고 청크가 롤백된다. 배송 `DELIVERED`, 주문 `COMPLETED`, `Sale SOLD`, 알림 모두 반영되지 않는다.

### (b) 즉시 구매로 만들어진 주문 → 배송 완료 처리 자체는 끝까지 진행된다

- 즉시 구매는 `createInstantOrder`에서 `Order`를 `PENDING_PAYMENT`로 만들고 배송을 `PENDING`으로 만든다. (`OrderCommandService.java:241-245`, `:264-271`)
  - 이 경로의 코드에는 주문 상태를 바꾸는 호출이 없어 `PENDING_PAYMENT`로 남는다.
  - `saleBid.assignOrder(order)`로 `SaleBid`가 연결되고 `MATCHED`가 된다. (`:279-280`)
  - `OrderBid`는 `MATCHED`, `isInstantPurchase=true`로 저장된다. (`OrderBidCommandService.java:189-207`)
- 배송 완료가 판정되는 시점에는 `completeOrder`가 전부 성공한다.
  - `OrderBid` 있음(`:196`), `PENDING_PAYMENT → COMPLETED` 허용(`OrderStatus.java:141`), `SaleBid` 있음(`:116`).
  - 결과: `Shipment=DELIVERED`, `Order=COMPLETED`, `Sale=SOLD`, 알림 3건(구매자 2·판매자 1). `OrderBid`/`SaleBid`는 `MATCHED` 유지.
- 단 운송장 등록 API(`PATCH …/status`)는 (b)에서도 `PENDING_PAYMENT → IN_TRANSIT`이 불가해 1-3과 같은 이유로 실패한다. 배송이 `IN_TRANSIT`/`OUT_FOR_DELIVERY`가 되려면 `/check-status`가 carrier 상태로 `OUT_FOR_DELIVERY`를 저장하는 경로가 필요하다.
  - 이 경로에서 carrier 상태가 "배송출발/배송완료" 이외이면 `updateTrackingInfo`가 이미 `IN_TRANSIT`을 대입한 뒤 `updateStatus(IN_TRANSIT)`을 호출한다. `IN_TRANSIT→IN_TRANSIT`이 불가해 `IllegalStateException`이 나고 롤백된다. (`:473`, `:497`, `ShipmentStatus.java:72-77`)

## 5. 실패 처리 (주기 배치 중 한 건이 실패할 때)

- Step은 fault-tolerant이며 `skip(Exception.class)`, `skipLimit(50)`이다. (`UpdateShipmentStatusesJobConfig.java:51-52`, `:75-77`)
- 처리 중 예외(운송장 없음, 조회 실패, 파싱 실패, `completeOrder` 실패 등)는 `ShipmentException`으로 감싸져 던져진다. (`ShipmentItemProcessor.java:133-145`)
  - 그 건은 skip되고 `SkipListener`가 로그만 남긴다. (`UpdateShipmentStatusesJobConfig.java:251-286`)
  - 해당 건의 DB 변경(배송 `DELIVERED`, 주문·판매 변경, 알림)은 롤백되고 상태가 그대로라 **다음 실행(6시간 뒤)에 다시 조회 대상**이 된다.
  - `completeOrder`의 `@Transactional`은 청크 트랜잭션에 참여하므로 그 안의 실패도 같이 롤백된다.
- 나머지 건
  - 청크(50건) 단위 트랜잭션이므로, 실패한 건 때문에 청크가 롤백된 뒤 Spring Batch가 청크를 건별로 다시 처리한다. 실패한 건만 제외하고 나머지는 커밋된다. 이때 외부 조회와 알림이 재실행된다.
  - skip이 50건을 넘으면 `SkipLimitExceededException`으로 step이 실패하고 남은 건은 그 실행에서 처리되지 않는다. 다음 주기에 다시 시도한다.
- 스케줄러는 `jobLauncher.run` 예외를 `printStackTrace()`로만 처리하고 삼킨다. (`ShipmentBatchScheduler.java:38-40`)
