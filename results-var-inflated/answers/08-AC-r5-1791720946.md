# 구매자 배송: 운송장 등록 → 배송 완료

경로 약어: `S` = `src/main/java/com/fream/back/domain/shipment`, `O` = `src/main/java/com/fream/back/domain/order`, `Sa` = `src/main/java/com/fream/back/domain/sale`, `G` = `src/main/java/com/fream/back/global`.
`S/service/command/OrderShipmentCommandService.java`는 `SVC`로 줄여 쓴다.

## 0. 전제: 결제·배송 처리 직후의 상태

- 배송 정보 `OrderShipment`는 결제 처리 중에 `status=PENDING`으로 만들어진다. `SVC createOrderShipment`는 `S/service/command/OrderShipmentCommandService.java:55-75`, PENDING 지정은 `:67`이다.
- 일반 구매 입찰 주문의 실배송 경로(`processPaymentAndShipment`)는 주문을 `PAYMENT_COMPLETED → PREPARING`까지만 올린다. 근거는 `O/service/command/OrderCommandService.java:174-177`이다.
- Kafka 경로(`OrderEventConsumer`)도 같다. 실배송이면 `PREPARING`에서 멈춘다. 근거는 `O/service/kafka/OrderEventConsumer.java:215-218`이다.
- 코드 어디에도 `OrderStatus.SHIPMENT_STARTED`로 바꾸는 호출이 없다. `grep`으로 확인했고 정의와 전이표, 화면 라벨뿐이다. 정의는 `O/entity/OrderStatus.java:13`, 전이표는 `:26-28`이다.
- 즉시 구매 주문(`createInstantOrder`)은 `PENDING_PAYMENT`로 만들어지고(`O/service/command/OrderCommandService.java:241-245`) 이후 주문 상태를 올리는 코드가 없다. 배송은 `:264-271`에서 PENDING으로 생성된다.

## 1. 운송장 등록 요청

### 1-1. 어느 API로 들어오나

- `PATCH /shipments/order/{shipmentId}/status`, 핸들러 `OrderShipmentCommandController#updateTrackingInfo`다. 근거는 `S/controller/command/OrderShipmentCommandController.java:20,33-49`이다.
- 요청 바디 `OrderShipmentRequestDto`에서 `courier`, `trackingNumber`를 꺼내 `OrderShipmentCommandService#updateTrackingInfo`를 호출한다(`:41-45`).
- 운영 측이 쓰는 보조 API도 있다.
  - `POST /shipments/order/{shipmentId}/check-status`(`:58-94`)
  - `POST /shipments/order/{shipmentId}/check-status-string`(`:103-138`)
  - 둘 다 `updateAndCheckShipmentStatus`로 간다. 운송장을 저장하고 곧바로 택배사를 조회한다.

### 1-2. 코드가 의도한 상태 변경 순서와 알림 (`SVC updateTrackingInfo`, `:238-303`)

1. `courier`나 `trackingNumber`가 비어 있으면 `TRACKING_INFO_REQUIRED`(`:243-246`).
2. `OrderShipment`를 조회한다(`:249-253`).
3. 배송 정보를 갱신한다. `shipment.updateTrackingInfo(courier, trackingNumber)`(`:256`)는 택배사와 운송장을 넣고 `status=IN_TRANSIT`으로 직접 대입한다(`S/entity/OrderShipment.java:41-45`). 전이 검증(`canTransitionTo`)을 거치지 않는다.
4. `order.updateStatus(OrderStatus.IN_TRANSIT)`(`:259-260`). 이 메서드는 전이표 검사를 한다(`O/entity/Order.java:113-121`).
5. 구매자에게 알림 1건: "상품이 출발하였습니다. 주문 ID: …"(`:264-271`).
6. `updateSaleStatusToSold(orderId)`(`:276`)로 판매 상태를 SOLD로 바꾼다. 이어서 창고 보관이면 창고 상태를 SOLD로 바꾸고 판매자에게 알림 1건을 보낸다(`:111-183`, 판매자 알림 `:133-138`).
7. 창고 보관 판매이면 `updateWarehouseStatusToSold`를 한 번 더 호출한다(`:278-286`).
8. `updateOrderAndSaleBidStatusToCompleted`로 OrderBid와 SaleBid가 MATCHED이면 COMPLETED로 바꾼다(`:289`, 본문 `:412-440`).
   - 배송 완료 전에 입찰이 COMPLETED가 되는 순서다.
   - 이 메서드 안의 예외는 로그만 남기고 삼킨다(`:436-439`).

### 1-3. 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문(즉시 구매 아님)에서의 결과: 끝까지 성공하지 못한다

- **실패 지점**: `SVC:260`의 `order.updateStatus(OrderStatus.IN_TRANSIT)`이다.
- **이유**:
  - 이 주문의 상태는 `PREPARING`이다(0절).
  - `PREPARING`에서 갈 수 있는 상태는 `IN_WAREHOUSE`, `SHIPMENT_STARTED`뿐이다(`O/entity/OrderStatus.java:26`). `IN_TRANSIT`은 허용되지 않는다.
  - `canTransitionTo`가 false이므로 `InvalidOrderStatusException`("상태 전환이 허용되지 않습니다: PREPARING -> IN_TRANSIT")이 던져진다(`O/entity/Order.java:114-119`).
  - `IN_TRANSIT`으로 가려면 `SHIPMENT_STARTED`를 거쳐야 하는데(`O/entity/OrderStatus.java:28`) 그 상태로 바꾸는 코드가 없다.
- **예외 처리**:
  - 이 예외는 `ShipmentException`이 아니므로 `catch (ShipmentException)`을 지나친다(`SVC:293-294`).
  - 일반 `catch (Exception)`에서 `ShipmentException(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")`로 감싸 다시 던진다(`SVC:295-301`).
- **무엇이 저장되나: 아무것도 저장되지 않는다.**
  - `updateTrackingInfo`는 `@Transactional`이고(`SVC:238`) 런타임 예외가 밖으로 나가므로 전체가 롤백된다.
  - 3번의 courier, trackingNumber, `IN_TRANSIT` 대입도 DB에는 남지 않는다. 배송은 PENDING이고 운송장은 null인 채로 있다.
  - 5번 이후(구매자 알림, 판매자 알림, 입찰 COMPLETED)는 실행되지 않는다. 4번에서 이미 던져졌기 때문이다.
- **응답**:
  - 이 컨트롤러는 예외를 잡지 않는다(`S/controller/.../OrderShipmentCommandController.java:33-49`). 그래서 `GlobalExceptionHandler#handleGlobalException`으로 간다(`G/exception/GlobalExceptionHandler.java:49-62`).
  - 응답은 **HTTP 404**이고, `ErrorResponse`는 code=`S001`, message=`"배송 정보를 찾을 수 없습니다."`이다.
  - 핸들러가 `errorCode.getMessage()`를 쓰므로 사용자 지정 메시지는 응답에 실리지 않는다. 근거는 `S/exception/ShipmentErrorCode.java:12`와 `GlobalExceptionHandler.java:55-61`이다.
  - 실제 원인은 주문 상태 전이 위반인데 응답은 "배송 정보 없음"이다. 오류 코드가 잘못 매핑되어 있다.
- 참고: 이 주문에 판매자(SaleBid)가 붙어 있어도 `:260`에서 먼저 실패한다. 같은 실패다.
- 참고(즉시 구매 주문): 상태가 `PENDING_PAYMENT`다. 이 상태의 전이 허용 집합은 `{PAYMENT_COMPLETED, COMPLETED, IN_WAREHOUSE}`뿐이므로 `IN_TRANSIT`이 거부된다(`O/entity/OrderStatus.java:24`). 같은 지점에서 같은 응답으로 실패한다.

## 2. 배송 완료 감지

### 2-1. 누가, 언제, 어떻게

- **누가**: 스케줄러 `ShipmentBatchScheduler#scheduleShipmentStatusJob`이 Spring Batch 잡 `updateShipmentStatusesJob`을 `JobLauncher`로 실행한다(`G/config/ShipmentBatchScheduler.java:34-44`).
  - 잡 파라미터는 `timestamp`(현재 시각)이다(`:37-40`).
  - 예외는 `printStackTrace`만 한다(`:41-43`).
- **주기**: `@Scheduled(cron = "0 0 */6 * * *")`, 즉 6시간마다 정각(00, 06, 12, 18시)이다(`:34`).
- **대상**: 리더 `shipmentItemReader`의 JPQL이다.
  - `SELECT s FROM OrderShipment s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL`
  - 페이지 크기는 50이다.
  - 근거는 `S/config/UpdateShipmentStatusesJobConfig.java:89-96`이다.
- **조회 방식**: 택배사(CJ대한통운) 조회 페이지를 Playwright로 열어 렌더링된 HTML을 Jsoup으로 파싱한다.
  - URL은 `https://trace.cjlogistics.com/next/tracking.html?wblNo={운송장}`이다(`S/config/ShipmentItemProcessor.java:28`, 이동 `:82-87`).
  - `tbody#statusDetail tr`의 마지막 행에서 5번째 `td` 텍스트를 상태로 쓴다(`:181`).
  - 브라우저는 스텝 시작과 종료 시 `BrowserManageStepListener`가 열고 닫는다(`S/config/BrowserManageStepListener.java:15-23`, 등록 `UpdateShipmentStatusesJobConfig.java:80`).

### 2-2. 실제로 실행되는 처리 코드

- 스텝 구성이 `new ShipmentItemProcessor(playwrightBrowserManager(), notificationService, orderService)`를 processor로 직접 쓴다(`UpdateShipmentStatusesJobConfig.java:67-72`). 그러므로 실제 실행되는 것은 `S/config/ShipmentItemProcessor.java#process`(`:57`, 본문 `:57-157`)다.
- 같은 설정 클래스의 `@Bean shipmentItemProcessor()`(`UpdateShipmentStatusesJobConfig.java:106-168`)는 `CjTrackingPlaywright`를 쓰는 람다인데, 스텝에 연결되지 않아 실행되지 않는다. 스텝은 `.processor(new ShipmentItemProcessor(...))`만 쓴다(`:69`).
- `OrderShipmentCommandService#updateShipmentStatuses`(`SVC:308-391`)는 호출하는 곳이 없다(`grep` 결과 정의뿐). 이 안의 로직(DELIVERED 시 알림 1건, `order.updateStatus(COMPLETED)`)은 실행되지 않는다.
- `UpdateShipmentStatusesJobConfig#parseCjLogisticsStatus`(`:186`)도 어디서도 호출되지 않는다.
- 참고: `adminshipment`, `partnershipment`, `legacyshipment`, `internalshipment`, `settlementshipment`에도 같은 이름(`updateShipmentStatusesJob`)의 설정 클래스가 있다(예: `src/main/java/com/fream/back/domain/adminshipment/config/AdminUpdateShipmentStatusesJobConfig.java:54-55`).
  - 스케줄러는 `@Qualifier("updateShipmentStatusesJob")` 이름으로 주입받는다(`G/config/ShipmentBatchScheduler.java:19-21`).
  - 이 질문의 기준은 `domain/shipment`의 설정이다. 빈 이름이 겹치지만 `allow-bean-definition-overriding` 설정은 `src/main/resources`에서 찾지 못했다. 겹치는 빈을 기동 시 Spring이 어떻게 처리하는지는 실행해 보지 않아 확인하지 못했다.

### 2-3. 택배사 상태 문자열 → 내부 상태 (`ShipmentItemProcessor#mapToShipmentStatus`, `S/config/ShipmentItemProcessor.java:220-226`)

| 택배사 문자열 | 내부 `ShipmentStatus` |
|---|---|
| `"배송완료"` | `DELIVERED` |
| `"배송출발"` | `OUT_FOR_DELIVERY` |
| 그 외 모든 문자열 | `IN_TRANSIT` |

- 정확한 문자열 일치(`switch`)다. 공백이나 변형 문구는 모두 `IN_TRANSIT`이 된다.
- `DELAYED`, `FAILED_DELIVERY` 등은 매핑되지 않는다.

## 3. 배송 완료 판정 이후

`ShipmentItemProcessor#process`의 DELIVERED 분기(`:108-117`)다.

### 3-1. 상태 변경 순서

1. 새 상태가 현재 상태와 같으면 변경 없이 반환한다(`:101-105`).
2. `orderShipment.updateStatus(DELIVERED)`. `OrderShipment`가 `IN_TRANSIT` 또는 `OUT_FOR_DELIVERY`에서 `DELIVERED`로 가는 전이는 허용된다(`S/entity/ShipmentStatus.java:16-28`, 검사 `S/entity/OrderShipment.java:47-55`). 아직 메모리 객체만 바뀐다(`S/config/ShipmentItemProcessor.java:113`).
3. `orderService.completeOrder(orderId)`(`:116`, 본문 `SVC:190-229`)가 실행된다.
   1. `OrderBid`를 `orderId`로 조회한다(`SVC:196`).
   2. `order.updateStatus(OrderStatus.COMPLETED)`(`:204`).
   3. `updateSaleStatusToSold`(`:208`)를 호출한다.
      - SaleBid 조회(`:116`). 연결된 SaleBid가 없으면 `null`이 아니라 `IllegalArgumentException`이 던져진다(`Sa/service/query/SaleBidQueryService.java:26-29`).
      - Sale이 `SOLD`로 갈 수 있으면 `SOLD`로 바꾼다(`:119-123`).
      - 창고 보관이면 창고 상태도 `SOLD`로 바꾼다(`:126-129`).
      - 판매자에게 알림 1건을 보낸다(`:133-138`).
      - 이어서 `OrderBid.getSale()` 기준으로 같은 처리를 한 번 더 한다(`:150-171`). 이미 `SOLD`면 건너뛴다.
   4. 구매자에게 알림 1건: "[completeOrder] 주문이 완료 처리되었습니다. 주문 ID: …"(`:211-217`).
4. `notificationService.notifyShipmentCompleted(order)`(`ShipmentItemProcessor.java:117`)로 구매자에게 알림 1건: "[배송 완료] 상품이 배송 완료되었습니다. …"(`S/../NotificationCommandService`: `src/main/java/com/fream/back/domain/notification/service/command/NotificationCommandService.java:219-234`). 이 메서드는 실패해도 로그만 남긴다(`:230-233`).
5. 스텝의 writer `JpaItemWriter`가 청크 끝에서 `OrderShipment`(DELIVERED)를 저장한다(`UpdateShipmentStatusesJobConfig.java:74`, `:241-246`).

정리하면 `OrderShipment`가 `DELIVERED`가 되고(메모리에서 먼저, DB는 마지막), `Order`는 `COMPLETED`, `Sale`은 `SOLD`(가능한 경우)로 바뀐다.

### 3-2. 알림 건수 (판매자 1 + 구매자 2가 이론상 최대)

- 구매자: 2건. `completeOrder`의 "[completeOrder] …"(`SVC:212-217`)와 `notifyShipmentCompleted`의 "[배송 완료] …"(`NotificationCommandService.java:224-229`).
- 판매자: Sale이 `SOLD`로 전이 가능했을 때만 1건(`SVC:133-138`). 두 번째 블록은 이미 `SOLD`이므로 중복 발송되지 않는다(`SVC:156`).
- 실시간 알림은 `createNotification` 안에서 WebSocket으로 즉시 보낸다(`NotificationCommandService.java:44-59`).

### 3-3. 주문 입찰·판매 입찰 상태

- 변하지 않는다. 배치 경로(`completeOrder`)에는 입찰 상태를 바꾸는 코드가 없다.
- 입찰을 COMPLETED로 바꾸는 `updateOrderAndSaleBidStatusToCompleted`는 `updateTrackingInfo`(`SVC:289`)에서만 호출된다. 그런데 1-3에서 본 대로 `updateTrackingInfo`는 `:260`에서 실패하므로 사실상 실행되지 않는다.
- 결과적으로 `OrderBid`와 `SaleBid`는 배송 완료 후에도 `MATCHED`로 남는다. `OrderBid`는 `assignOrder`에서 MATCHED가 되고(`O/entity/OrderBid.java:75`), `SaleBid`는 `assignOrder`/`assignSale`에서 MATCHED가 된다(`Sa/entity/SaleBid.java:53-61`).

## 4. 주문 종류별 차이

### (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문: 끝까지 진행되지 않는다

- 우선 이 주문은 배치 대상 자체가 되기 어렵다.
  - 운송장 등록 `PATCH`가 `SVC:260`에서 실패해 `IN_TRANSIT`/운송장이 저장되지 않는다(1-3). 배송은 `PENDING`, 운송장 null이라 리더 조건에서 빠진다(`UpdateShipmentStatusesJobConfig.java:95`).
  - `check-status` API는 `shipment.updateTrackingInfo`로 `IN_TRANSIT`을 만들 수 있다(`SVC:473`, `S/entity/OrderShipment.java:41-45`). 이때 택배사가 "배송완료"라고 하면 곧바로 `completeOrder`가 호출된다(`SVC:483-489`).
- 어떤 경로로든 `completeOrder`에 도달하면 **`SVC:204`의 `order.updateStatus(COMPLETED)`에서 실패**한다.
  - 주문 상태가 `PREPARING`이고 `PREPARING → COMPLETED`는 허용되지 않기 때문이다(`O/entity/OrderStatus.java:26`).
  - `InvalidOrderStatusException`이 `completeOrder`의 `catch (Exception)`에서 `ShipmentException(ORDER_NOT_FOUND_FOR_SHIPMENT)`로 감싸진다(`SVC:221-228`).
  - 이 호출은 `updateSaleStatusToSold` 앞이므로 판매 상태 변경과 알림은 일어나지 않는다.
  - 판매자(SaleBid)가 붙지 않은 주문이었다면 `:208`에서도 `IllegalArgumentException`이 났을 것이다(`SaleBidQueryService.java:28`). 하지만 그 전에 `:204`에서 이미 막힌다.
- 결과: 배송은 `DELIVERED`로 저장되지 않고, 주문은 `PREPARING`으로 남으며, 알림은 없다. 입찰도 `MATCHED` 그대로다. 롤백 근거는 5절이다.

### (b) 즉시 구매로 만들어진 주문: 3의 처리가 끝까지 진행된다 (단, 운송장 등록 경로는 `check-status` API다)

- 이 주문은 `PENDING_PAYMENT` 상태다(`O/service/command/OrderCommandService.java:244`). 이 상태에서는 `COMPLETED`로의 전이가 허용된다(`O/entity/OrderStatus.java:24`). 그래서 `completeOrder`의 `SVC:204`가 통과한다.
- `PATCH` 운송장 등록은 이 주문에서도 실패하므로(1-3 참고) 배송이 `IN_TRANSIT`이 되려면 `check-status` API를 거쳐야 한다(`SVC:473`). 그 뒤에는 배치가 대상으로 잡는다.
- 필요한 연결이 있다.
  - `SaleBid.order`는 즉시 구매 때 `saleBid.assignOrder(order)`로 연결된다(`O/service/command/OrderCommandService.java:279`).
  - `OrderBid.order`와 `OrderBid.sale`도 즉시 구매 때 채워진다(`O/service/command/OrderBidCommandService.java:189-207`, 상태 MATCHED `:196`, 즉시 구매 플래그 `:205`).
  - 따라서 `SaleBidQueryService#findByOrderId`와 `OrderBidQueryService#findByOrderId`가 모두 값을 반환한다.
- 결과:
  - `OrderShipment` → `DELIVERED`, `Order` → `COMPLETED`.
  - 구매자 알림 2건.
  - 판매자 알림은 0건이다. 결제 시점에 이미 Sale이 `SOLD`가 되어 있기 때문이다.
    - 결제 처리 `processPayment`가 `notifyUsersAndUpdateSaleStatus`를 호출한다(`src/main/java/com/fream/back/domain/payment/service/command/PaymentCommandService.java:83`).
    - 즉시 구매에서는 이 시점에 `order.getOrderBid()`가 아직 null이라(OrderBid는 `createInstantOrder` 이후에 만들어진다, `O/service/command/OrderBidCommandService.java:133-142`) SaleBid 경로를 타서 `sale.updateStatus(SOLD)`를 한다(`PaymentCommandService.java:388-404`).
    - 배송 완료 시 `updateSaleStatusToSold`에서 `SOLD.canTransitionTo(SOLD)`가 false여서(`Sa/entity/SaleStatus.java:23`) 판매 상태 변경, 창고 변경, 판매자 알림이 모두 건너뛰어진다(`SVC:119,142-144,156,173-175`).
  - 입찰 상태는 `OrderBid`, `SaleBid` 모두 `MATCHED`로 남는다(3-3).
- (b)의 Sale `SOLD` 선행은 결제 시점의 `order.getOrderBid()` null 가정에 기대는 추론이다. 실행해서 확인한 것은 아니다.

## 5. 실패 처리 (주기 처리 중 한 건이 실패할 때)

- 스텝은 `faultTolerant().skip(Exception.class).skipLimit(50)`이다. 청크 크기는 50이다(`UpdateShipmentStatusesJobConfig.java:51-52,67,75-77`).
- 처리 중 예외는 `ShipmentItemProcessor`에서 `ShipmentException`으로 감싸 다시 던진다(`S/config/ShipmentItemProcessor.java:133-145`).
  - 예: 운송장이 비어 있음(`:61-64`), HTML 파싱 실패(`:181`, 파싱 예외 처리 `:193-211`), 허용되지 않는 전이로 `IllegalStateException`(`S/entity/OrderShipment.java:47-55`), `completeOrder` 실패(3절).
- 그 건:
  - 스킵 대상이다. `shipmentSkipListener#onSkipInProcess`가 로그만 남긴다(`UpdateShipmentStatusesJobConfig.java:255-262`).
  - 해당 청크의 트랜잭션은 롤백된다. `completeOrder`는 청크 트랜잭션에 참여하므로 그 건이 이미 바꾼 주문, 판매 상태와 알림 저장도 DB에서는 롤백된다(`SVC:190`의 `@Transactional`).
  - `OrderShipment`는 저장되지 않고 원래 상태(`IN_TRANSIT`/`OUT_FOR_DELIVERY`)로 남아, 다음 주기(6시간 뒤)에 다시 대상이 된다.
- 나머지 건:
  - Spring Batch의 fault tolerant 청크 동작에 따라 실패한 청크가 롤백된 뒤 항목별로 다시 처리되고, 실패한 항목만 건너뛴다. 나머지 건은 정상적으로 처리되어 저장된다.
  - 다른 청크는 영향받지 않는다.
  - 코드에서 직접 확인할 수 있는 부분은 스킵 설정까지다. 항목별 재처리는 Spring Batch의 표준 동작에 의존한다.
- 한도: 스킵이 50건을 넘으면 `SkipLimitExceededException`으로 잡이 실패하고 남은 건은 그 실행에서 처리되지 않는다(`:77`).
- 스케줄러 자체의 예외는 `printStackTrace`만 하고 삼킨다(`G/config/ShipmentBatchScheduler.java:41-43`).
- 알려진 부수 효과:
  - 롤백 시 이미 WebSocket으로 나간 실시간 알림은 취소되지 않는다. 항목별 재처리 때 같은 알림이 다시 나갈 수 있다(`NotificationCommandService.java:56-57`).
  - `OUT_FOR_DELIVERY` 배송에 택배사가 다른 문구(→ `IN_TRANSIT`)를 반환하면 `OUT_FOR_DELIVERY.canTransitionTo(IN_TRANSIT)`가 false여서 `IllegalStateException`이 나고 스킵된다(`S/entity/ShipmentStatus.java:23-28`, `S/config/ShipmentItemProcessor.java:123-125`).
  - 리더는 페이징(offset)인데 처리 결과로 상태가 바뀌어 `DELIVERED` 건이 조회 조건에서 빠진다. 다음 페이지에서 일부 건이 건너뛰어질 수 있다. 다음 주기에 다시 대상이 된다(`UpdateShipmentStatusesJobConfig.java:89-96`). 이 항목은 코드 구조에서의 추론이며 실행해서 확인하지는 않았다.
