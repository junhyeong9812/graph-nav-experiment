# 즉시 구매 처리 흐름 (domain/order 기준)

경로 약어: `OBC` = `src/main/java/com/fream/back/domain/order/controller/command/OrderBidCommandController.java`,
`OBS` = `src/main/java/com/fream/back/domain/order/service/command/OrderBidCommandService.java`,
`OCS` = `src/main/java/com/fream/back/domain/order/service/command/OrderCommandService.java`,
`PCS` = `src/main/java/com/fream/back/domain/payment/service/command/PaymentCommandService.java`.
(`legacy*`/`partner*`/`settlement*`/`internal*`/`admin*` 도메인은 같은 구조의 복제본이며, 일반 구매자 API는 `order` 도메인이다.)

## 1. 진입 API, 처리 단계, 동기/비동기, 응답 ID

- 진입: `POST /order-bids/instant` (`OBC:22` 클래스 `@RequestMapping("/order-bids")`, `OBC:89` `@PostMapping("/instant")`). 본문은 `InstantOrderRequestDto`(saleBidId, addressId, warehouseStorage, paymentRequest) — `src/main/java/com/fream/back/domain/order/dto/InstantOrderRequestDto.java:20-29`.
- 컨트롤러 단계:
  1. 로그인 이메일 추출 (`OBC:91`).
  2. `enrichPaymentRequest`로 paymentRequest에 userEmail 설정, orderId는 null로 초기화 (`OBC:98`, `OBC:119-122`).
  3. `orderBidCommandService.createInstantOrderBid(...)` 호출 (`OBC:101-107`).
- 서비스 단계 (`OBS:118-149`, `@Transactional`):
  1. 입력 검증 (`OBS:123`, `OBS:154-167`)
  2. 구매자 조회 (`OBS:126`)
  3. SaleBid/Sale 조회·검증 (`OBS:129-130`, `OBS:172-184`)
  4. `OrderCommandService#createInstantOrder` 호출 (`OBS:133-139`)
  5. `OrderBid` 생성·저장 (`OBS:142`, `OBS:189-207`)
- `createInstantOrder` (`OCS:219-319`) 내부 순서:
  1. 배송지 조회 (`OCS:238`)
  2. Order 저장 (`OCS:241-247`)
  3. paymentRequest에 orderId 주입 (`OCS:250`)
  4. OrderItem 생성 (`OCS:255-256`)
  5. OrderShipment 생성 (`OCS:264-271`)
  6. SaleBid 매칭 + flush (`OCS:279-283`)
  7. 판매자 창고 상태 갱신 (`OCS:291-294`)
  8. 결제 처리 (`OCS:305`)
- **동기 처리**다. 이 경로에서는 Kafka 이벤트를 발행하지 않는다. `OrderEventProducer#sendOrderProcessingEvent`는 별도 엔드포인트인 `OrderCommandController`(`.../order/controller/command/OrderCommandController.java:54`)에서만 호출된다. HTTP 요청 스레드 안에서 결제(PortOne HTTP 호출 포함)·알림까지 한 트랜잭션으로 끝나고 응답한다.
- **응답 ID는 주문(Order) ID가 아니라 새로 만든 `OrderBid`의 ID**다. 컨트롤러가 `createInstantOrderBid(...).getId()`로 OrderBid의 ID를 꺼내 `orderId`라는 변수명으로 반환한다 (`OBC:101-107`, `OBC:109`). 서비스가 `OrderBid`를 반환하기 때문이다 (`OBS:144`, `OBS:119`). Javadoc의 "생성된 주문 ID"(`OBC:76`)와 실제 값이 다르다.

## 2. 새로 만들어지는 엔티티와 상태 변화 순서

생성 순서와 직후 상태:

| 순서 | 대상 | 동작 | 직후 상태 | 근거 |
|---|---|---|---|---|
| 1 | `Order` | 신규 저장 | `PENDING_PAYMENT` (totalAmount = saleBid.bidPrice) | `OCS:241-247` |
| 2 | `OrderItem` | 신규 (수량 1, 가격 = bidPrice) | - | `OCS:255`, `src/main/java/com/fream/back/domain/order/service/command/OrderItemCommandService.java:45-52` |
| 3 | `OrderShipment` | 신규 (주소는 addressId로 조회한 값) | `ShipmentStatus.PENDING` | `OCS:264-271`, `src/main/java/com/fream/back/domain/shipment/service/command/OrderShipmentCommandService.java:61-68` |
| 4 | `SaleBid`(기존) | `assignOrder` → 상태 MATCHED, 이어서 `updateStatus(MATCHED)`, flush | sale `BidStatus.MATCHED`, order 연결 | `OCS:279-283`, `src/main/java/com/fream/back/domain/sale/entity/SaleBid.java:58-61` |
| 5 | `WarehouseStorage`(기존, 판매자 쪽) | `sale.isWarehouseStorage()`일 때만 `ASSOCIATED_WITH_ORDER`로 | `ASSOCIATED_WITH_ORDER` | `OCS:291-294`; 전이 검증 `src/main/java/com/fream/back/domain/warehouseStorage/service/command/WarehouseStorageCommandService.java:127-132, 232-` |
| 6 | `Payment`(Card/Account/General) | 신규 저장 | 아래 3번 표 | `OCS:305`, `PCS:57-107` |
| 7 | `Notification`(구매자·판매자) | 결제 처리 마지막에 신규 저장 | `isRead=false` | `PCS:83`, `PCS:434-455` |
| 8 | `Sale`(기존) | `updateStatus(SOLD)` (무조건 대입, 전이 검증 없음) | `SaleStatus.SOLD` | `PCS:404`/`PCS:419`, `src/main/java/com/fream/back/domain/sale/entity/Sale.java:73-75` |
| 9 | `OrderBid` | 신규 저장 | `order.BidStatus.MATCHED`, `isInstantPurchase=true`, order·sale 연결 | `OBS:192-206` |

- 8번은 `notifyUsersAndUpdateSaleStatus`에서 일어난다. 이 시점 `order.getOrderBid()`는 아직 null이다(OrderBid가 이후에 생성됨, `OBS:142`)이므로, `saleBidQueryService.findByOrderId`로 SaleBid → Sale을 찾는 분기를 탄다 (`PCS:388-406`). 4번에서 flush 했기 때문에 이 조회가 성공한다.
- `Order.status`는 이 흐름에서 **한 번도 `updateStatus`되지 않는다**(OCS 219-319에 호출 없음).
- `order.assignPayment`도 호출되지 않는다. Payment가 `order_id`를 가진 소유측이라 DB 연결은 된다 (`PCS:200`).

## 3. 결제 수단별 결과

결제 유형은 `requestDto.getResolvedPaymentType()`으로 분기한다 (`PCS:67-80`). 유효하지 않은 유형은 `PaymentException`.

| 수단 | 동작 | 저장 직후 Payment 상태 / isSuccess | 근거 |
|---|---|---|---|
| CARD | PaymentInfo 조회 후 PortOne 카드 결제 API 호출. 응답 `status == "success"`면 `PAID` + `isSuccess=true` | 성공 응답: `PAID`, true | `PCS:157-208` |
| ACCOUNT | 은행명 `Bank` enum 검증만 하고 외부 호출 없이 저장 | `PENDING` (PAID로 바뀌지 않음) | `PCS:236-262` |
| GENERAL | `impUid`만 있으면 검증 없이 저장, 즉시 성공 처리 | `PAID`, true | `PCS:290-316` |

- `Payment.status` 기본값은 `PENDING` (`src/main/java/com/fream/back/domain/payment/entity/Payment.java:44`).
- 모든 하위 Payment의 빌더가 `setPaidAmount`를 호출하고, 여기서 `isSuccess = paidAmount > 0`이 된다 (`Payment.java:60-63`, `src/main/java/com/fream/back/domain/payment/entity/CardPayment.java:60`). 따라서 **계좌이체는 상태 `PENDING`인데 `isSuccess=true`**다.
- **즉시 구매가 끝까지 성공하는가**: 수단과 무관하게 `createInstantOrder`는 `processPayment`의 반환값(Payment)과 `isSuccess`/`status`를 확인하지 않고 그대로 `order`를 반환한다 (`OCS:305-311`). 예외가 없으면 성공 응답 "즉시 구매가 성공적으로 처리되었습니다."(`OBC:109`)가 나간다. 계좌이체는 입금 확인 없이도 성공 응답과 함께 Sale이 SOLD가 된다.
- **결제 대행사가 카드 결제를 실패로 응답하면** 두 경우로 나뉜다.
  - (a) PortOne HTTP 응답이 200이 아니거나 `code != 0`이면 `PaymentProcessingException`을 던진다 (`src/main/java/com/fream/back/domain/payment/portone/PortOneApiClient.java:270-275`). `PCS:218-219`로 재전파되고 `OCS:306-308`에서 `OrderPaymentProcessingFailedException`으로 감싸져 전체 `@Transactional`이 롤백된다. Order·OrderItem·Shipment·SaleBid 매칭이 모두 취소되고 클라이언트는 오류 응답을 받는다. (통신 오류 `PaymentApiException`은 `@Retryable` 3회, `PortOneApiClient.java:224-228`.)
  - (b) `code == 0`이지만 내부 `response.status`가 `"success"`가 아니면(결제 거절 등) 예외 없이 진행한다. `PAID` 설정을 건너뛰어 CardPayment가 `status=PENDING`으로 저장된다. 그런데 `isSuccess`는 빌더의 `setPaidAmount` 때문에 `true`로 남는다 (`PCS:203-208`, `Payment.java:60-63`). 이어서 알림이 발송되고 Sale이 `SOLD`가 되며, OrderBid·SaleBid가 `MATCHED`로 남는다. 클라이언트에는 성공 응답이 나간다. 즉 거절된 카드 결제도 즉시 구매가 "성공"으로 처리된다.
  - (비동기 경로 `OrderEventConsumer`에는 `!payment.isSuccess()` 검사가 있으나 `.../order/service/kafka/OrderEventConsumer.java:174`, 즉시 구매 경로는 이를 거치지 않는다.)

## 4. 알림

- 받는 사람과 시점: 결제 레코드 저장 직후, 같은 요청 스레드·같은 트랜잭션 안에서 `sendNotifications` 호출 (`PCS:83`, `PCS:416`/`PCS:403`).
  - 구매자: "결제가 완료되었습니다. 주문 ID: {order.id}" (`PCS:438-443`)
  - 판매자(`sale.getSeller()`): "구매자가 결제를 완료하였습니다. 판매 ID: {sale.id}" (`PCS:447-454`)
  - 둘 다 `NotificationCategory.SHOPPING`, `NotificationType.BID`.
- 전달 방식: ① DB `Notification` 저장(`isRead=false`, `NotificationCommandService.java:52-53`, `:241-248` — `src/main/java/com/fream/back/domain/notification/service/command/NotificationCommandService.java`), ② Redis에 `WebSocket:User:{email}` 키가 있는 접속 사용자에게만 STOMP `/user/{email}/queue/notifications`로 실시간 푸시 (`NotificationCommandService.java:303-313`). 접속 중이 아니면 저장만 된다 (`:320-322`).
- 알림 실패(예외)는 삼켜지고 결제/주문 흐름은 계속된다 (`PCS:457-461`, `PCS:421-425`).
- 알림은 **결제 성공 여부와 무관하게** 나간다. 카드 거절(3-(b)) 또는 계좌이체 `PENDING`이어도 "결제가 완료되었습니다" 알림이 간다.
- 즉시 구매 경로에서는 Kafka 알림이나 `ORDER_COMPLETED` WebSocket 메시지(`OrderEventConsumer.java:287-329`)가 발송되지 않는다. 그건 `/orders` 비동기 경로 전용이다.

## 5. 최종 주문 상태와 창고 보관

- **최종 `Order.status`는 `PENDING_PAYMENT`**다. 결제 수단·성공 여부와 무관하다. `OCS:241-247`에서 설정한 뒤 `createInstantOrder`가 `PAYMENT_COMPLETED`, `PREPARING` 등으로 바꾸지 않는다 (`OCS:219-319` 전체에 `order.updateStatus` 없음). 반면 SaleBid·OrderBid는 `MATCHED`, Sale은 `SOLD`, Shipment는 `PENDING`으로 서로 일관되지 않는 상태가 된다.
  - 참고: 비동기 `/orders` 경로(`processCompleteOrder`)나 `processPaymentAndShipment`는 `PAYMENT_COMPLETED → PREPARING`(배송) 또는 `... → IN_WAREHOUSE → COMPLETED`(창고)로 바꾸지만 (`OCS:163-177`, `OrderEventConsumer.java:192-220`), 즉시 구매는 이 메서드들을 호출하지 않는다.
- **구매자가 "창고 보관"을 선택한 경우**: `warehouseStorage` 값은 컨트롤러가 `createInstantOrderBid`에 넘기고 (`OBC:105`) `createInstantOrder`의 `isWarehouseStorage` 인자로 전달되지만 (`OBS:137`, `OCS:221`), 메서드 본문에서 **전혀 사용되지 않는다**. 따라서 `WarehouseStorage` 생성(`createOrderStorage`)도, `IN_WAREHOUSE`/`COMPLETED` 전이도 없으며 주문 결과는 보관 여부와 동일하다(구매자 배송지로 `OrderShipment`가 만들어진다). 창고 관련으로 일어나는 일은 구매자 선택이 아니라 **판매 쪽 `sale.isWarehouseStorage()`**가 참일 때 판매자 창고 보관물의 상태가 `ASSOCIATED_WITH_ORDER`로 바뀌는 것뿐이다 (`OCS:291-294`).
