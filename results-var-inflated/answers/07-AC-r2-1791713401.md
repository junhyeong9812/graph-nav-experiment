# 즉시 구매 처리 흐름 (코드 기준 실제 동작)

경로 약어: `D` = `src/main/java/com/fream/back/domain`, `G` = `src/main/java/com/fream/back/global`.
(`legacy*/partner*/internal*/settlement*/admin*` 도메인은 같은 구조의 복제본이며, 기본 도메인은 `order`/`payment`/`sale` 이다.)

## 1. 어느 API로, 어떤 단계로, 동기/비동기, 응답 ID

- **API**: `POST /order-bids/instant` — `D/order/controller/command/OrderBidCommandController.java:22,89-90`. 본문은 `InstantOrderRequestDto`(saleBidId, addressId, warehouseStorage, paymentRequest) — `D/order/dto/InstantOrderRequestDto.java:25-34`.
- **동기 처리다.** 컨트롤러가 서비스를 직접 호출하고(`OrderBidCommandController.java:101-107`) 같은 요청 스레드에서 DB 저장, 포트원 결제 호출, 알림 저장까지 끝낸 뒤 `200 OK`로 응답한다(`:109`). 이 경로에는 Kafka를 쓰지 않는다.
  - Kafka 비동기 처리(`OrderEventProducer` → `order-processing-topic` → `OrderEventConsumer`)는 **다른 API** `POST /orders/{orderId}/process-payment-shipment` 용이다(`D/order/controller/command/OrderCommandController.java:42-54`, `D/order/service/kafka/OrderEventConsumer.java:55-61`). 즉시 구매는 이 경로를 타지 않는다.
- **처리 단계** (모두 `OrderBidCommandService#createInstantOrderBid`의 한 `@Transactional` 안 — `D/order/service/command/OrderBidCommandService.java:118-119`):
  1. 컨트롤러: 이메일 추출, `paymentRequest.userEmail=email`, `orderId=null` 세팅 (`OrderBidCommandController.java:92-98,119-123`).
  2. 입력 검증 (`OrderBidCommandService.java:123,154-167`) → 구매자 조회 (`:126`) → SaleBid 조회(`:129,172-183`; 없으면 `SaleBidQueryService#findById`가 `IllegalArgumentException` — `D/sale/service/query/SaleBidQueryService.java:21-23`).
  3. `OrderCommandService#createInstantOrder` 호출 (`OrderBidCommandService.java:133-139`): 주소 조회 → Order 저장 → OrderItem → OrderShipment → SaleBid 매칭 → (판매자 쪽) 창고 상태 → 결제 (`D/order/service/command/OrderCommandService.java:238-305`).
  4. `OrderBid` 생성·저장 (`OrderBidCommandService.java:142,189-206`).
- **응답으로 돌려주는 ID는 `OrderBid`의 ID이다. `Order` ID가 아니다.** 컨트롤러가 `...createInstantOrderBid(...).getId()`(반환형 `OrderBid`)를 `orderId` 변수에 담아 내보낸다 (`OrderBidCommandController.java:101-107,109`; 반환 타입 `OrderBidCommandService.java:119`). 변수명/Javadoc("생성된 주문 ID", `:82-83`)과 실제 값이 다르다.

## 2. 새로 생기는 엔티티와 상태 변화 순서 (`OrderCommandService#createInstantOrder`)

| 순서 | 동작 | 근거 | 직후 상태 |
|---|---|---|---|
| 0 | (기존) SaleBid는 `PENDING` 입찰 중 | `D/sale/entity/SaleBid.java:35-37` | SaleBid `PENDING` |
| 1 | `Order` 생성·저장 (totalAmount = 판매 입찰가) | `OrderCommandService.java:241-247` | Order `PENDING_PAYMENT` |
| 2 | `paymentRequest.orderId = order.id` | `:250` | — |
| 3 | `OrderItem` 생성, order에 추가 | `:255-256` | — |
| 4 | `OrderShipment` 생성(주소는 addressId로 조회한 값) | `:264-271`; 초기 상태 `D/shipment/service/command/OrderShipmentCommandService.java:61-68` | Shipment `PENDING` |
| 5 | 기존 `SaleBid`에 order 연결 + 상태 변경 + flush | `:279-283`, `D/sale/entity/SaleBid.java:58-61,66-68` | SaleBid `MATCHED` |
| 6 | 판매자 Sale이 `isWarehouseStorage`면 해당 창고 보관 항목 상태 변경 | `:290-293`, `D/warehouseStorage/service/command/WarehouseStorageCommandService.java:117-133` | WarehouseStorage(판매자 보관분) `ASSOCIATED_WITH_ORDER` |
| 7 | 결제 처리: `Payment` 서브타입(Card/Account/General) 생성·저장 | `:305`, `D/payment/service/command/PaymentCommandService.java:57-83` | 결제 수단별로 아래 3번 |
| 8 | 결제 직후 알림 + Sale 상태 변경 | `PaymentCommandService.java:83,383-420` | Sale `SOLD` |
| 9 | `OrderBid` 생성(생성 시 이미 매칭) + `isInstantPurchase=true` 저장 | `OrderBidCommandService.java:192-206`, `D/order/entity/OrderBid.java:60-82,97-99` | OrderBid `MATCHED` |

새로 만들어지는 엔티티: Order, OrderItem, OrderShipment, Payment(Card/Account/General 중 하나), OrderBid, Notification(구매자·판매자 각 1건). 창고 보관 엔티티(WarehouseStorage)는 **새로 만들어지지 않는다**(아래 5번).

주의할 실제 동작:
- 단계 8: 이 시점에 `order.getOrderBid()`는 아직 null(OrderBid는 단계 9에서 생성)이므로 `saleBidQueryService.findByOrderId`로 SaleBid → Sale을 찾는 분기를 탄다 (`PaymentCommandService.java:388-406`; 단계 5의 flush 덕에 조회됨).
- `Sale.updateStatus`는 전이 검증이 없다 (`D/sale/entity/Sale.java:73-75`). 결제 성공 여부와 무관하게 `SOLD`가 된다(아래 3번).
- **Order의 상태를 바꾸는 코드가 이 경로에 없다.** `order.updateStatus(...)`/`assignPayment`는 호출되지 않는다 (`OrderCommandService.java:238-311`에 없음; `processPayment` 반환값도 버려짐 `:305`). → 5번.
- Sale 상태/창고 상태는 결제보다 먼저(6) 또는 결제 안에서(8) 바뀌며, Sale이 `SOLD`가 되어도 판매자 창고 항목은 `ASSOCIATED_WITH_ORDER`로 남는다(SOLD로 바꾸는 `updateWarehouseStatusToSold`는 호출되지 않음).

## 3. 결제 수단별 결과

`PaymentCommandService#processPayment`가 `resolvedPaymentType`으로 분기한다 (`PaymentCommandService.java:67-80`). 사전 검증: 요청 orderId == 주문 ID, 이메일 일치, 금액 > 0 (`:117-146`).

| 수단 | 동작 | 결제 상태 / isSuccess | 근거 |
|---|---|---|---|
| **CARD** | 저장된 PaymentInfo 조회 → 포트원(`api.iamport.kr`) 즉시 호출 → CardPayment 저장 | 응답 `status`가 문자열 `"success"`일 때만 `PAID`+success=true. 그 외는 기본값 **`PENDING`, success=false** | `PaymentCommandService.java:166,179,187-208`; 기본값 `D/payment/entity/Payment.java:39,44` |
| **ACCOUNT** | 은행명만 검증, 외부 호출 없음 | 항상 **`PENDING`**, success=false (입금 확인 로직 없음) | `PaymentCommandService.java:243-262` |
| **GENERAL** | impUid 필수 검증만, 외부 검증 없이 클라이언트 값 신뢰 | 즉시 **`PAID`**, success=true | `PaymentCommandService.java:297-316` |

- **즉시 구매는 "끝까지 성공"한다고 보기 어렵다**: 위 세 경우 모두 결제가 `PENDING`이어도 예외가 아니므로 트랜잭션이 커밋되고, 구매자는 `200 "즉시 구매가 성공적으로 처리되었습니다."`를 받는다 (`OrderBidCommandController.java:109`). 그러나 Order는 `PENDING_PAYMENT`에 머문다(5번). `processPayment`는 반환된 Payment의 `isSuccess`를 확인하지 않는다 (`OrderCommandService.java:305`; 비교: Kafka 경로는 `!payment.isSuccess()`면 실패 처리 — `OrderEventConsumer.java:174-176`).
- 포트원 카드 응답의 `status`는 `PAID`가 아닌 포트원 값("paid" 등)이므로 `"success".equals(...)` 비교는 정상 결제에서도 거짓일 가능성이 높다. 이 비교는 코드상 확인(`PaymentCommandService.java:203`)이며, 포트원 실제 응답 값은 코드로 확인되지 않는다.
- **결제 대행사가 카드 결제를 실패로 응답하면**: HTTP 200이어도 `code != 0`이면 `PaymentProcessingException`을 던진다 (`D/payment/portone/PortOneApiClient.java:270-275`). 이는 `createCardPayment`에서 그대로 전파(`PaymentCommandService.java:180-181,218-219`) → `processPayment`가 재던짐(`:89-94`) → `createInstantOrder`가 `OrderPaymentProcessingFailedException`으로 감싸 던짐 (`OrderCommandService.java:305-308`, `:313-316`) → `OrderBidCommandService`가 `OrderException`을 그대로 전파 (`:145-146,212-214`). `@Transactional`(RuntimeException 기반, `G/exception/GlobalException.java:10`)이므로 **전체 롤백**: Order·OrderItem·OrderShipment·SaleBid 매칭·Sale `SOLD`·알림 모두 취소되고 OrderBid도 생성되지 않는다. `GlobalExceptionHandler#handleOrderException`이 에러 응답을 준다 (`G/exception/GlobalExceptionHandler.java:325-339`). (통신 오류는 `PaymentApiException`이며 `@Retryable` 3회 재시도 후 동일하게 롤백 — `PortOneApiClient.java:223-228,288-290`.) 단, 이미 포트원에서 승인된 건에 대한 보상(취소) 호출은 이 경로에 없다.
  - 반대로 응답이 HTTP 200 + `code==0`이지만 결제 자체 상태가 실패(`failed` 등)인 경우는 예외 없이 위 `PENDING` 케이스로 처리된다.

## 4. 알림: 누가, 언제, 어떻게

- 알림은 결제 처리 직후(`processPayment` 안, 단계 8)에 동기적으로 만든다 (`PaymentCommandService.java:83,434-456`). 결제가 `PENDING`(계좌이체, 카드 비-success)이어도 똑같이 "결제가 완료되었습니다" 알림이 나간다(수단/성공 여부 검사 없음).
- **구매자**: `"결제가 완료되었습니다. 주문 ID: {orderId}"` — 카테고리 SHOPPING, 타입 BID (`:438-443`).
- **판매자**(`sale.getSeller()`): `"구매자가 결제를 완료하였습니다. 판매 ID: {saleId}"` — 같은 카테고리/타입 (`:447-453`).
- **전달 방식**: `NotificationCommandService#createNotification`이 Notification을 DB에 저장하고(`D/notification/service/command/NotificationCommandService.java:52-54`), 사용자가 WebSocket 연결 중일 때만(Redis 키 `WebSocket:User:{email}` 존재) `/user/queue/notifications`로 실시간 푸시한다 (`:57,303-322`). 연결이 없으면 저장만 되고 푸시는 없다. Kafka/이메일은 이 경로에 없다.
- 알림 생성 실패는 로그만 남기고 삼킨다 (`PaymentCommandService.java:457-461,421-425`). 알림은 같은 트랜잭션이라 이후 단계(예: 카드 실패 아님이지만 OrderBid 생성 중 예외)에서 롤백되면 알림 행도 롤백된다(이미 나간 WebSocket 푸시는 회수되지 않음).
- 결제 실패(카드 오류) 시에는 알림이 없다: 예외로 `notifyUsersAndUpdateSaleStatus`에 도달하지 못한다 (`PaymentCommandService.java:179-184` → `:83`).
- `OrderEventConsumer`의 WebSocket `/topic/order/{id}` 및 `notification-topic` 알림(`OrderEventConsumer.java:287-329`)은 즉시 구매와 무관하다(다른 API).

## 5. 처리 종료 시 주문의 최종 상태 / 창고 보관 선택 시

- **주문(Order)의 최종 상태는 `PENDING_PAYMENT`(결제 대기)이다.** 생성 시 `PENDING_PAYMENT`로 저장되고 (`OrderCommandService.java:241-245`) 이후 즉시 구매 경로에서 상태를 바꾸지 않는다 (`order.updateStatus` 호출 없음: `OrderCommandService.java:238-311`, `PaymentCommandService.java:57-107`, `OrderBidCommandService.java:119-148`). 결제가 `PAID`여도(GENERAL, 성공한 CARD) Order는 `PAYMENT_COMPLETED/PREPARING`으로 가지 않는다. `order.assignPayment`도 호출하지 않아 `Payment.order` 쪽 FK로만 연결된다 (`Payment.java:47-50`).
  - 비교: `PAYMENT_COMPLETED → PREPARING (→ IN_WAREHOUSE → COMPLETED)` 전이는 **다른 API**(`processPaymentAndShipment` 및 Kafka 컨슈머)에만 있다 (`OrderCommandService.java:163-173`, `OrderEventConsumer.java:192-220`).
  - 함께 남는 상태: OrderShipment `PENDING`, SaleBid `MATCHED`, OrderBid `MATCHED`(isInstantPurchase), Sale `SOLD`, Payment는 수단별로 `PAID` 또는 `PENDING`.
- **구매자가 "창고 보관"(`warehouseStorage=true`)을 선택해도 아무 일도 일어나지 않는다.** 컨트롤러는 값을 서비스로 넘기지만 (`OrderBidCommandController.java:104`, `OrderBidCommandService.java:133-139`), `createInstantOrder`는 `isWarehouseStorage` 파라미터를 본문에서 전혀 사용하지 않는다 (파라미터 선언 `OrderCommandService.java:221`, 본문 `:238-311`에 참조 없음). 따라서 구매자 몫의 `WarehouseStorage`(`createOrderStorage`, `D/warehouseStorage/service/command/WarehouseStorageCommandService.java:33-57`)는 만들어지지 않고, 주문이 `IN_WAREHOUSE`/`COMPLETED`로 가지도 않으며, 배송 정보(OrderShipment)가 그대로 생성된다.
  - 실제로 창고 관련 분기를 결정하는 것은 **판매자가 올린 Sale의 `isWarehouseStorage`** 이다 (`OrderCommandService.java:290-293`, `D/sale/entity/Sale.java:43`): 그 경우 판매자 보관 항목이 `ASSOCIATED_WITH_ORDER`가 된다. 이때 해당 창고 항목이 없으면 `WarehouseStorageNotFoundException` → `OrderWarehouseStorageProcessingFailedException`으로 전체 롤백된다 (`WarehouseStorageQueryService.java:30-33`, `OrderCommandService.java:294-300`).
  - 구매자의 창고 보관 선택이 실제로 반영되는 경로는 `POST /orders/{orderId}/process-payment-shipment`의 `requestDto.isWarehouseStorage()`(`OrderEventConsumer.java:197-212`, 최종 `COMPLETED`)뿐이다.

## 요약 (실제 동작 vs 이름/주석)

1. "응답 orderId" = 실제로는 **OrderBid ID** (`OrderBidCommandController.java:101-109`).
2. "즉시 구매가 성공적으로 처리되었습니다" 응답이어도 Order는 **`PENDING_PAYMENT`**, 결제 수단에 따라 Payment `PENDING` 가능, Sale은 이미 `SOLD`.
3. 창고 보관 플래그는 구매자 입력으로는 **무시**된다.
4. 카드 실패(응답 code≠0)는 예외 → 전체 롤백(Sale SOLD·알림 포함 취소), 알림 없음.
5. 알림은 구매자·판매자 각 1건, DB 저장 + (접속 중이면) WebSocket 푸시, 동기 생성.
