# 구매자 배송: 운송장 등록 → 배송 완료

경로 약어: `S` = `src/main/java/com/fream/back/domain/shipment`, `O` = `src/main/java/com/fream/back/domain/order`.
주석·메서드명이 말하는 의도와 실제 동작이 다른 곳은 "실제"로 따로 적었다.

## 0. 전제: 결제·배송 처리 후 상태

- 일반 구매 입찰 주문은 `OrderBid(PENDING)` + `Order(PENDING_PAYMENT)` 로 만들어진다. (`O/service/command/OrderCommandService.java:81`, `O/service/command/OrderBidCommandService.java:91-97`)
- 결제·배송 처리(`processPaymentAndShipment`)에서 `OrderShipment` 가 `PENDING` 으로 생성되어 주문에 붙는다. (`S/service/command/OrderShipmentCommandService.java:56-70`, `O/service/command/OrderCommandService.java:148-155`)
- 실배송(`isWarehouseStorage=false`)이면 주문 상태는 `PAYMENT_COMPLETED → PREPARING` 에서 멈춘다. (`O/service/command/OrderCommandService.java:174-177`)
- 같은 메서드의 5단계는 `orderBidQueryService.findById(orderId)` 로, 주문 ID를 OrderBid ID 로 쓴다. 그래서 해당 주문의 OrderBid 가 MATCHED 가 된다는 보장이 없다. (`O/service/command/OrderCommandService.java:188-190`)
- 즉시 구매(`createInstantOrder`)는 `Order(PENDING_PAYMENT)`, `OrderShipment(PENDING)`, `SaleBid.assignOrder` (MATCHED) 를 만든다. (`O/service/command/OrderCommandService.java:241-247, 264-271, 279-280`)
- 즉시 구매에서 `PaymentCommandService.processPayment` 는 주문 상태를 바꾸지 않는다. 대신 `notifyUsersAndUpdateSaleStatus` 로 Sale 을 이미 `SOLD` 로 바꾼다. 이 시점에는 OrderBid 가 아직 없어 SaleBid 경로를 탄다. (`src/main/java/com/fream/back/domain/payment/service/command/PaymentCommandService.java:83, 388-406`)
- 즉시 구매의 OrderBid 는 이후에 `MATCHED` + `isInstantPurchase` 로 생성된다. (`O/service/command/OrderBidCommandService.java:189-206`)

## 1. 운송장 등록 요청

### 1-1. 어느 API 인가
- `PATCH /shipments/order/{shipmentId}/status`, 본문은 `OrderShipmentRequestDto`(courier, trackingNumber). (`S/controller/command/OrderShipmentCommandController.java:20, 33, 41`)
- `OrderShipmentCommandService.updateTrackingInfo(shipmentId, courier, trackingNumber)` 를 호출하고, 성공 시 `200 OK` 빈 본문을 반환한다. (`S/controller/command/OrderShipmentCommandController.java:41-48`)
- 보안 설정에 이 경로 전용 규칙은 없다. `anyRequest().authenticated()` 만 적용되어, 운영자 전용 권한 체크는 코드에 없다. (`src/main/java/com/fream/back/global/config/security/SecurityConfig.java:52`)

### 1-2. 의도된 상태 변경 순서와 알림 (`updateTrackingInfo`, `OrderShipmentCommandService.java:238-303`)
1. 택배사·운송장 공백 검사. 실패하면 `TRACKING_INFO_REQUIRED`. (`:243-246`)
2. `OrderShipment` 조회 후 `shipment.updateTrackingInfo` → courier/trackingNumber 저장, 배송 상태 `IN_TRANSIT`. (`:249-256`, `S/entity/OrderShipment.java:41-45`)
3. `Order.updateStatus(IN_TRANSIT)`. (`:259-260`)
4. 구매자에게 알림 1건: "상품이 출발하였습니다. 주문 ID". (`:265-271`)
5. `updateSaleStatusToSold(orderId)`. (`:276`, 본체 `:112-183`)
   - SaleBid 경로로 Sale → `SOLD`, 창고 보관이면 창고 상태 갱신, 판매자에게 알림 "판매 완료". (`:116-143`)
   - OrderBid 경로로 같은 Sale 이 이미 SOLD 이면 중복 전이는 건너뛴다. (`:150-176`)
6. SaleBid 의 Sale 이 창고 보관이면 창고 상태를 갱신한다. (`:279-286`)
7. `updateOrderAndSaleBidStatusToCompleted`. OrderBid 와 SaleBid 가 `MATCHED` 이면 `COMPLETED` 로 바꾼다. (`:289`, `:413-440`)

즉 의도는 "운송장 등록 시점에 이미 판매 완료·입찰 COMPLETED 까지 처리"이다. 메서드명·주석("배송 출발")과 달리 판매/입찰 완료까지 앞당겨 처리하는 구조다.

### 1-3. 실배송 일반 구매 입찰 주문(즉시 구매 아님)에서 끝까지 성공하나 → **아니오, 실패한다**
- **실패 지점**: 3단계 `order.updateStatus(OrderStatus.IN_TRANSIT)`. (`OrderShipmentCommandService.java:260`)
  - 주문은 `PREPARING` 이다. (`O/service/command/OrderCommandService.java:176`)
  - `PREPARING` 의 허용 전이는 `IN_WAREHOUSE`, `SHIPMENT_STARTED` 뿐이다. `IN_TRANSIT` 으로는 갈 수 없다. (`O/entity/OrderStatus.java:26`, `Order.java:113-121`)
  - 따라서 `InvalidOrderStatusException`("상태 전환이 허용되지 않습니다: PREPARING -> IN_TRANSIT")이 발생한다. (`O/entity/Order.java:113-120`)
- **예외 변환**: 이 예외는 `ShipmentException` 이 아니라서 `catch (Exception e)` 에 걸린다. `ShipmentErrorCode.SHIPMENT_NOT_FOUND` 로 감싸 다시 던진다. (`OrderShipmentCommandService.java:293-301`)
  - 메시지는 "운송장 정보 업데이트 중 오류 발생: ..." 이다.
  - 코드는 `SHIPMENT_NOT_FOUND`("S001", 404)로, 실제 원인(주문 상태 전이 불가)과 맞지 않는 오해 소지가 있는 코드다. (`S/exception/ShipmentErrorCode.java:12`)
- **무엇이 저장되나**: 아무것도 저장되지 않는다.
  - `@Transactional` 메서드에서 RuntimeException(`GlobalException` 계열)이 밖으로 나가 전체가 롤백된다. (`OrderShipmentCommandService.java:238`, `global/exception/GlobalException.java:10`)
  - 2단계에서 메모리상 바뀐 courier/trackingNumber/`IN_TRANSIT` 도 반영되지 않는다. DB 의 OrderShipment 는 `PENDING`, 운송장 null 그대로다.
  - 4단계 알림 생성 전에 실패하므로 알림도 0건이다.
- **응답**: `GlobalExceptionHandler.handleShipmentException` 이 `ErrorResponse(code="S001", message="배송 정보를 찾을 수 없습니다.", status=404, path=/shipments/order/{id}/status)` 를 반환한다. (`src/main/java/com/fream/back/global/exception/GlobalExceptionHandler.java:459-472`)
- **추가 실패 요인**: 전이 문제가 없어도 5단계에서 SaleBid 가 없으면 실패한다.
  - `SaleBidQueryService.findByOrderId` 는 이름과 달리 null 이 아니라 `IllegalArgumentException` 을 던진다. (`src/main/java/com/fream/back/domain/sale/service/query/SaleBidQueryService.java:26-28`)
  - 이를 호출하는 `updateSaleStatusToSold` 의 SaleBid 조회(`OrderShipmentCommandService.java:116`)에는 try/catch 가 없다. 그래서 `if (saleBid != null)` 분기(`:117`)와 `:276`, `:279` 도 사실상 도달 불가다.
- **즉시 구매 주문**도 `PENDING_PAYMENT → IN_TRANSIT` 이 허용되지 않아(`OrderStatus.java:24`) 같은 이유로 이 API 로는 실패한다.

### 1-4. (참고) 다른 API: `POST /shipments/order/{id}/check-status`
- `updateAndCheckShipmentStatus` 는 운송장을 저장한 뒤 `IN_TRANSIT` 으로 둔다. 주문 상태는 건드리지 않는다. (`OrderShipmentCommandService.java:452-473`, `S/controller/command/OrderShipmentCommandController.java:58`)
- CJ 상태가 "배송완료" 이면 `completeOrder` 까지 간다. (`:483-489`)
- 그 외 상태(기본 `IN_TRANSIT`)에서는 `IN_TRANSIT → IN_TRANSIT` 전이가 허용되지 않아 `IllegalStateException` 이 나고, 503(`EXTERNAL_TRACKING_SERVICE_ERROR`)으로 롤백된다. (`:497`, `S/entity/ShipmentStatus.java` IN_TRANSIT 의 허용 전이, `OrderShipmentCommandService.java:507-514`)
- 이 경로가 성공하면 주문은 `PREPARING` 인데 배송은 `IN_TRANSIT` 인 상태가 만들어진다.

## 2. 배송 완료 감지

### 2-1. 누가·언제·어떻게
- 주체는 `ShipmentBatchScheduler`(Spring `@Scheduled`)이다. 크론은 `0 0 */6 * * *` 으로 매일 00·06·12·18시 정각, 6시간 주기다.
  - 매번 `timestamp` 파라미터로 `JobLauncher.run(updateShipmentStatusesJob)` 을 호출한다.
  - 예외는 `printStackTrace()` 만 한다. (`src/main/java/com/fream/back/global/config/ShipmentBatchScheduler.java:34-45`)
- 스케줄링은 다른 클래스의 `@EnableScheduling` 으로 활성화된다. (`src/main/java/com/fream/back/domain/event/scheduler/EventStatusScheduler.java:22`)
- 푸시나 웹훅이 아니라 **폴링**이다. CJ대한통운 추적 페이지를 Playwright(headless Chromium)로 열어 렌더링한 뒤 Jsoup 으로 파싱한다.

### 2-2. 대상, 실제 실행 코드
- **대상**: `OrderShipment` 중 `status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND trackingNumber IS NOT NULL` 이다. (`S/config/UpdateShipmentStatusesJobConfig.java:95`)
  - `JpaPagingItemReader`, 페이지 크기 50. 청크 50, 스킵 한도 50. (`:51-52`)
- **실제로 실행되는 처리 코드**: `S/config/ShipmentItemProcessor.java` (Playwright 기반)이다.
  - 근거: Step 이 `new ShipmentItemProcessor(playwrightBrowserManager(), notificationService, orderService)` 를 직접 생성해 `.processor(...)` 에 넣는다. (`S/config/UpdateShipmentStatusesJobConfig.java:69-73`)
  - 같은 Step 에 `BrowserManageStepListener` 가 브라우저 오픈·종료를 맡는다. (`:80`, `S/config/BrowserManageStepListener.java`)
  - 처리 핵심은 `process()` 에서 `page.navigate → waitForSelector("tbody#statusDetail tr") → 마지막 tr 의 5번째 td 텍스트` 이다. (`S/config/ShipmentItemProcessor.java:29, 87, 170-181`)
- **실행되지 않는 유사 코드**:
  - `UpdateShipmentStatusesJobConfig.shipmentItemProcessor()` (`:106`, 내부에 `cjTrackingPlaywright` 사용)는 `@Bean` 이지만 Step 에서 참조되지 않는다. 호출처가 없다.
  - 같은 파일의 `parseCjLogisticsStatus` (Jsoup 직접 접속)도 미사용이다. (`UpdateShipmentStatusesJobConfig.java`, 호출처 없음)
  - `OrderShipmentCommandService.updateShipmentStatuses()` (`:309-391`)는 호출하는 곳이 없다. (전체 소스 grep 으로 확인) 이 메서드는 `notifyShipmentCompleted` 대신 `createNotification` 을 쓰고 `completeOrder` 를 호출하지 않는다.
  - `adminshipment`, `partnershipment`, `settlementshipment`, `legacyshipment`, `internalshipment` 의 `*UpdateShipmentStatusesJobConfig`/`*ShipmentItemProcessor` 는 `shipment` 패키지 코드의 복사본이다. 알림 서비스 클래스만 다르고 공유하는 `OrderShipmentCommandService.completeOrder` 를 쓴다. 예: `src/main/java/com/fream/back/domain/adminshipment/config/AdminShipmentItemProcessor.java`.
  - 스케줄러는 Job 을 `@Qualifier("updateShipmentStatusesJob")` 이름으로 주입한다. 복사본 설정들도 같은 빈 이름(`updateShipmentStatusesJob`, `shipmentItemReader` 등)을 선언한다. Spring Boot 3.4 의 기본 설정(빈 오버라이드 금지)에서는 충돌 가능성이 있으나, 설정 파일에서 오버라이드 허용 옵션은 찾지 못했다. 실제 기동은 실행해 확인하지 못했다. 어느 복사본이 선택되든 완료 처리 본체(`completeOrder`)는 동일하다.

### 2-3. 택배사 상태 문자열 → 내부 상태
`mapToShipmentStatus` (`S/config/ShipmentItemProcessor.java:220-225`):

| CJ 텍스트 | 내부 `ShipmentStatus` |
|---|---|
| `"배송완료"` | `DELIVERED` |
| `"배송출발"` | `OUT_FOR_DELIVERY` |
| 그 외 모든 문자열(집화처리, 간선상차 등) | `IN_TRANSIT` |

- 완전 일치(`switch`)만 매칭한다. 앞뒤 공백은 `trim()` 으로 제거한다. (`:181`)
- 빈 문자열이거나 행이 없으면 `TRACKING_HTML_PARSE_ERROR` 이다. (`:170-189`)
- 기존 상태와 같으면 변경 없이 반환한다. (`:101-105`)
- `OUT_FOR_DELIVERY` 상태인 건에 CJ 가 다시 "그 외"를 주면 `OUT_FOR_DELIVERY → IN_TRANSIT` 전이가 불가해 `IllegalStateException` → `EXTERNAL_TRACKING_SERVICE_ERROR` 로 그 건이 스킵된다. (`:125`, `S/entity/ShipmentStatus.java`)

## 3. 배송 완료 판정 이후 (`DELIVERED`)

`ShipmentItemProcessor.process` (`S/config/ShipmentItemProcessor.java:110-118`):
1. `orderShipment.updateStatus(DELIVERED)`. 메모리상이며 Writer 에서 flush 된다. (`:113`, writer: `UpdateShipmentStatusesJobConfig.java:74`)
2. `orderService.completeOrder(orderId)`. (`:116`, 본체 `OrderShipmentCommandService.java:191-229`)
   - 2-a. OrderBid 조회, 없으면 예외. (`:196-197`)
   - 2-b. `Order.updateStatus(COMPLETED)`. (`:204`)
   - 2-c. `updateSaleStatusToSold`. (`:208`) Sale 이 `SOLD` 로 전이 가능할 때만 SOLD 로 바꾸고 판매자 알림을 만든다. (`:116-143`)
   - 2-d. 구매자 알림: "[completeOrder] 주문이 완료 처리되었습니다. 주문 ID". (`:211-217`)
   - 2-e. 어떤 예외든 `ShipmentException(ORDER_NOT_FOUND_FOR_SHIPMENT)` 로 래핑해 던진다. (`:221-228`)
3. `notificationService.notifyShipmentCompleted(order)`. 구매자 알림 "[배송 완료] 상품이 배송 완료되었습니다. 주문 ID". (`:117`, `src/main/java/com/fream/back/domain/notification/service/command/NotificationCommandService.java:219-229`)

**상태 변경 순서**: OrderShipment `IN_TRANSIT/OUT_FOR_DELIVERY → DELIVERED` → Order `→ COMPLETED` → Sale `→ SOLD`(전이 가능하면).

**알림**:
- 구매자 2건: "[completeOrder]…", "[배송 완료]…".
- 판매자 0~1건: Sale 이 아직 SOLD 가 아니고 전이 가능할 때만 "판매 완료" 1건.
- 판매자 알림이 같은 Sale 로 두 번 생기지 않는다. 같은 엔티티가 이미 SOLD 가 되어 OrderBid 경로의 `canTransitionTo(SOLD)` 가 false 이기 때문이다. (`SaleStatus.java:23`)

**입찰 상태**:
- 배치 경로(`completeOrder`)는 OrderBid/SaleBid 를 `COMPLETED` 로 바꾸지 않는다. 그 로직(`updateOrderAndSaleBidStatusToCompleted`)은 `updateTrackingInfo`(운송장 등록)에서만 호출된다. (`OrderShipmentCommandService.java:289`)
- 따라서 배송 완료 판정 후에도 입찰은 이전 상태(MATCHED 이면 MATCHED, PENDING 이면 PENDING)로 남는다.
- 운송장 등록 API 가 1-3 처럼 실패하므로 정상 흐름에서는 COMPLETED 가 되는 경로가 사실상 없다.

## 4. 주문 종류별 차이

배치 대상이 되려면 OrderShipment 가 `IN_TRANSIT/OUT_FOR_DELIVERY` + 운송장 번호 보유 상태여야 한다.
- 정상 API(1번)로는 두 주문 모두 실패해 `PENDING` 에 머문다.
- 1-4 의 `check-status` 로만 `IN_TRANSIT` 이 만들어질 수 있다. (`OrderShipmentCommandService.java:473`)
- 아래는 배송이 `IN_TRANSIT` 이고 CJ 가 "배송완료"라고 가정한 결과다.

### (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문 → **끝까지 진행되지 않음**
- 주문 상태가 `PREPARING` 이다. (`O/service/command/OrderCommandService.java:176`)
- `completeOrder` 의 `order.updateStatus(COMPLETED)` 에서 `PREPARING → COMPLETED` 가 허용되지 않아 `InvalidOrderStatusException` 이 난다. (`OrderShipmentCommandService.java:204`, `OrderStatus.java:26`)
- `ShipmentException(ORDER_NOT_FOUND_FOR_SHIPMENT)` 로 래핑되어 던져진다. (`:221-228`)
- 결과:
  - Processor 가 예외를 다시 던진다. (`ShipmentItemProcessor.java:133-145`)
  - 청크가 롤백되고 해당 건은 스킵된다. (`UpdateShipmentStatusesJobConfig.java:75-77`)
  - DB 상태는 shipment `IN_TRANSIT`, order `PREPARING`, Sale/입찰 불변, 알림 0건이다.
  - 6시간마다 같은 실패를 반복하고, 매번 스킵 한도 50 을 소모한다.

### (b) 즉시 구매로 만들어진 주문 → **끝까지 진행됨**
- 주문 상태가 `PENDING_PAYMENT` 라서 `PENDING_PAYMENT → COMPLETED` 가 허용된다. (`OrderStatus.java:24`)
- OrderBid 가 즉시 구매로 생성되어 있어 `completeOrder` 의 조회가 성공한다. (`OrderBidCommandService.java:189-206`)
- SaleBid 도 `assignOrder` 로 연결되어 있어 SaleBid 조회가 성공한다. (`OrderCommandService.java:279`)
- Sale 은 결제 시점에 이미 SOLD 이다. (`PaymentCommandService.java:388-406`)
  - 그래서 `canTransitionTo(SOLD)` 가 false 이고, Sale 전이와 판매자 알림은 건너뛴다. (`OrderShipmentCommandService.java:119, 156`, `SaleStatus.java:23`)
- 결과:
  - Shipment `DELIVERED`, Order `COMPLETED`.
  - 구매자 알림 2건, 판매자 알림 0건.
  - OrderBid·SaleBid 는 `MATCHED` 그대로 유지된다. (배치 경로에서는 COMPLETED 로 안 바뀐다.)

| | (a) 실배송 일반 입찰 | (b) 즉시 구매 |
|---|---|---|
| Order 전이 | `PREPARING→COMPLETED` 불가, 실패 | `PENDING_PAYMENT→COMPLETED` 성공 |
| Shipment | `IN_TRANSIT` 유지(스킵) | `DELIVERED` |
| 알림 | 0건 | 구매자 2건 |

## 5. 실패 처리 (주기 처리 중 한 건 실패)

- Step 은 `faultTolerant().skip(Exception.class).skipLimit(50)` 이다. (`UpdateShipmentStatusesJobConfig.java:75-77`)
- Processor 에서 예외가 나면 그 청크가 롤백된다. 이후 Spring Batch 가 청크 안의 항목을 하나씩 다시 처리해 정상 항목은 커밋하고 실패 건만 스킵한다.
  - 실패 건: 처리·완료 알림 없이 이전 상태 그대로다. Order 변경과 알림이 롤백되고 shipment 는 flush 되지 않는다. 다음 주기(6시간 후)에 다시 대상이 된다.
  - 나머지 건: 정상 처리·커밋된다. 한 건 때문에 배치 전체가 중단되지 않는다.
- 스킵마다 `SkipListener` 가 로그만 남긴다. (`UpdateShipmentStatusesJobConfig.java:78, 252`)
- 스킵이 50건을 넘으면 `SkipLimitExceededException` 으로 Step 이 실패하고 남은 건은 처리되지 않는다. 스케줄러는 예외를 `printStackTrace` 만 한다. (`ShipmentBatchScheduler.java:42-44`)
- 실패 유형별 예외는 다음과 같다.
  - 운송장 공백: `TRACKING_NUMBER_INVALID` (`ShipmentItemProcessor.java:61-63`)
  - 조회·파싱 오류: `TRACKING_HTML_PARSE_ERROR`, `EXTERNAL_TRACKING_SERVICE_ERROR`
  - 상태 전이 불가: `IllegalStateException` → `EXTERNAL_TRACKING_SERVICE_ERROR` 로 래핑
- 참고: Reader 는 `IN_TRANSIT` 등으로 필터링하는 JPA 페이징이다. 처리하면서 DELIVERED 로 바뀐 행이 결과 집합에서 빠지므로, 다음 페이지 offset 이 밀려 일부 건이 이번 회차에서 건너뛰어질 수 있다. (`UpdateShipmentStatusesJobConfig.java:89-96`) 건너뛴 건은 다음 주기에 처리된다.
