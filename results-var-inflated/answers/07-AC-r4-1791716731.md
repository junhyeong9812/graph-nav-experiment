# 즉시 구매 처리 흐름

경로 접두어: `D = src/main/java/com/fream/back/domain`.
`internalorder`, `settlementorder` 등에 복제된 클래스가 있으나, 실제 서비스 본류는 `order` 도메인이다.

## 1. 진입 API와 처리 단계

- **API**: `POST /order-bids/instant`. 클래스 `@RequestMapping("/order-bids")` (`D/order/controller/command/OrderBidCommandController.java:22`), 메서드 `@PostMapping("/instant")` (`:89`).
  요청 본문은 `InstantOrderRequestDto`다. 필드는 `saleBidId`, `addressId`, `warehouseStorage`, `paymentRequest`다 (`D/order/dto/InstantOrderRequestDto.java:20-29`).
- **동기 처리**다.
  - 컨트롤러가 서비스를 직접 호출하고 반환값을 기다린다 (`OrderBidCommandController.java:101-107`).
  - Kafka 발행이나 `@Async`가 없다.
  - Kafka 기반 비동기 경로(`POST /orders/{orderId}/process-payment-shipment`, 202 Accepted)는 기존 주문의 결제·배송 처리용이다 (`D/order/controller/command/OrderCommandController.java:42-69`). 즉시 구매는 이 경로를 타지 않는다.
  - 즉시 구매 경로에는 Kafka 발행 호출이 없다. `OrderEventConsumer`/`PaymentEventConsumer`의 `@KafkaListener`는 즉시 구매 경로에서 호출되지 않는다 (`D/order/service/kafka/OrderEventConsumer.java:55,115`).
- **처리 단계** (한 트랜잭션):
  1. 컨트롤러가 이메일을 추출하고 (`OrderBidCommandController.java:92`), `enrichPaymentRequest`로 `userEmail`을 설정하고 `orderId=null`로 둔다 (`:98`, `:119-123`).
  2. `OrderBidCommandService#createInstantOrderBid` (`D/order/service/command/OrderBidCommandService.java:118-149`, `@Transactional`).
     - 입력 검증 (`:123`, `:154-167`)
     - 구매자 조회 (`:126`)
     - SaleBid 조회·검증 (`:129`, `:172-184`)
     - `OrderCommandService#createInstantOrder` 호출 (`:133`)
     - OrderBid 생성·저장 (`:142`)
  3. `OrderCommandService#createInstantOrder` (`D/order/service/command/OrderCommandService.java:219-319`, `@Transactional`).
     - 주소 조회 (`:238`)
     - Order 저장 (`:241-247`)
     - `paymentRequest.setOrderId` (`:250`)
     - OrderItem 생성 (`:255`)
     - OrderShipment 생성 (`:264-271`)
     - SaleBid 매칭 + flush (`:279-283`)
     - 창고 상태 갱신 (`:289-301`)
     - 결제 처리 (`:305`)
- **응답으로 돌려주는 ID는 `OrderBid`의 ID다. Order ID가 아니다.**
  - 서비스는 `OrderBid`를 반환한다 (`OrderBidCommandService.java:119,144`).
  - 컨트롤러는 `.getId()`를 `orderId`라는 변수에 담아 반환한다 (`OrderBidCommandController.java:101-107`).
  - 응답 메시지는 "즉시 구매가 성공적으로 처리되었습니다."이고 HTTP 200이다 (`:109`).
  - 변수명과 Javadoc("생성된 주문 ID", `:83`)은 Order ID를 말하지만 실제 값은 `OrderBid.id`다.

## 2. 생성되는 엔티티와 상태 변화 (순서)

새로 생성되는 엔티티:
Order → OrderItem → OrderShipment → Payment(카드/계좌/일반 중 하나) → OrderBid. 필요 시 Notification 행도 생성된다.

기존 엔티티 변경: SaleBid, Sale, WarehouseStorage(조건부).

| 순서 | 동작 | 직후 상태 | 근거 |
|---|---|---|---|
| 1 | Order 생성 | `Order.status = PENDING_PAYMENT`, `totalAmount = saleBid.bidPrice` | `OrderCommandService.java:241-247` |
| 2 | OrderItem 생성 (수량 1, 가격 = bidPrice) | OrderItem 저장 | `D/order/service/command/OrderItemCommandService.java:45-52`, `OrderCommandService.java:255-256` |
| 3 | OrderShipment 생성 (주소 DB 값 사용) | `ShipmentStatus.PENDING` | `D/shipment/service/command/OrderShipmentCommandService.java:61-70`, `OrderCommandService.java:264-271` |
| 4 | SaleBid 매칭: `assignOrder` + `updateStatus(MATCHED)` | `SaleBid.status = MATCHED`, `SaleBid.order = order` | `D/sale/entity/SaleBid.java:58-61,66-68`, `OrderCommandService.java:279-283` |
| 5 | 판매자가 창고 보관한 Sale이면 `updateWarehouseStatus(sale, ASSOCIATED_WITH_ORDER)` | `WarehouseStorage.status = ASSOCIATED_WITH_ORDER` | `OrderCommandService.java:291-293`, `D/warehouseStorage/service/command/WarehouseStorageCommandService.java:117-133` |
| 6 | 결제 생성 | 3절 참고 | `OrderCommandService.java:305` |
| 7 | 결제 후처리: 알림 전송, `sale.updateStatus(SOLD)` | `Sale.status = SOLD` | `D/payment/service/command/PaymentCommandService.java:383-420` |
| 8 | OrderBid 생성: `status = MATCHED`, `markAsInstantPurchase()` (`isInstantPurchase = true`) | `OrderBid.status = MATCHED` | `OrderBidCommandService.java:189-206`, `D/order/entity/OrderBid.java:97-99` |

- 5단계의 `WarehouseStorage` 변경은 `sale.isWarehouseStorage()`일 때만 일어난다 (`OrderCommandService.java:292`).
- 7단계의 `Sale` 변경은 상태 전이 검증이 없다 (`D/sale/entity/Sale.java:73-75`).
- 요청의 `warehouseStorage`가 쓰이는 곳은 없다 (5절 참고).
- **Order 상태는 `PENDING_PAYMENT`에서 바뀌지 않는다.**
  - `createInstantOrder`와 `processPayment` 어디에도 `order.updateStatus(...)`/`assignPayment` 호출이 없다.
  - `PAYMENT_COMPLETED`, `PREPARING`로 가는 코드는 별도 경로인 `processPaymentAndShipment`에만 있다 (`OrderCommandService.java:163-177`).
- SaleBid가 이미 `MATCHED`인지, 다른 구매자가 사 갔는지 검증하는 코드가 없다.
  - `getSaleBidAndValidate`는 null/Sale 연결 여부만 확인한다 (`OrderBidCommandService.java:172-184`).
  - `createInstantOrder`도 상태를 확인하지 않는다.

## 3. 결제 수단별 결과

분기는 `PaymentCommandService#processPayment`의 `switch (getResolvedPaymentType())`다 (`D/payment/service/command/PaymentCommandService.java:67-80`).
공통 검증 (`:117-146`):
- `order.id == requestDto.orderId`
- 이메일 일치
- `paidAmount > 0`

`Payment` 기본값은 `status = PENDING`, `isSuccess = false`다 (`D/payment/entity/Payment.java:39,44`).

| 결제 수단 | 동작 | 결과 상태 | 근거 |
|---|---|---|---|
| 카드 (`CARD`) | PaymentInfo 조회 → PortOne API 호출 → CardPayment 저장 | 응답 `status == "success"`이면 `PAID` + `isSuccess = true`. 아니면 상태 변경 없이 `PENDING`/`isSuccess=false`로 저장 | `PaymentCommandService.java:157-217` (특히 `:179`, `:203-206`) |
| 계좌이체 (`ACCOUNT`) | 은행명 검증 후 AccountPayment 저장. 외부 API 호출 없음 | 항상 `PENDING` | `PaymentCommandService.java:236-262` (특히 `:260`) |
| 일반 (`GENERAL`) | `impUid` 필수 검증 후 GeneralPayment 저장. 외부 API 호출 없음 | 즉시 `PAID` + `isSuccess = true` | `PaymentCommandService.java:290-316` (특히 `:313-314`) |

- **즉시 구매의 성공은 결제 성공을 뜻하지 않는다.**
  - 결제 상태와 무관하게 `processPayment`가 정상 반환하면 Order/OrderBid/SaleBid가 확정된다.
  - 계좌이체는 입금 전(`PENDING`)이어도 성공 응답이 나가고, Sale은 `SOLD`가 된다.
  - 이 서비스 어디에서도 `PENDING` 계좌이체 결제를 `PAID`로 바꾸는 후속 처리는 즉시 구매 경로에 연결돼 있지 않다.
- **카드 결제 실패 시** 두 경우로 갈린다.
  - **PortOne이 오류로 응답하는 경우** (HTTP 비 200, 본문 `code != 0`, 통신 예외, 토큰 발급 실패):
    - `PortOneApiClient#processCardPayment`가 `PaymentProcessingException`/`PaymentApiException`을 던진다 (`D/payment/portone/PortOneApiClient.java:270-275,288-293`).
    - `PaymentCommandService`는 이를 전파한다 (`:180-184`, `:218-219`).
    - `createInstantOrder`가 `OrderPaymentProcessingFailedException`으로 감싸 던지고 (`OrderCommandService.java:306-309`), `OrderBidCommandService`가 그대로 재전파한다 (`:145-147`, `:212-217`).
    - 클래스 전체가 하나의 `@Transactional`이므로 Order, OrderItem, OrderShipment, SaleBid 매칭, 창고 상태 변경이 롤백된다. OrderBid는 아직 생성되지 않았다.
    - 클라이언트는 오류 응답을 받는다.
  - **PortOne이 `code == 0`으로 응답하면서 내부 `status`가 `"success"`가 아닌 경우** (예: 결제 거절 `failed`):
    - 예외가 나지 않는다 (`PortOneApiClient.java:270`은 `code`만 검사한다).
    - `status != "success"`이면 `PAID`로 바꾸지 않고 `PENDING`/`isSuccess=false`인 CardPayment가 그대로 저장된다 (`PaymentCommandService.java:203-208`).
    - `FAILED` 상태로 기록되지 않는다.
    - 이후 알림 전송과 `Sale = SOLD`까지 진행된다 (`:83`, `:383-420`).
    - 결과적으로 주문(OrderBid, SaleBid)은 확정된 채 응답은 성공(200)이다.

## 4. 알림 (누가, 언제, 어떻게)

- **수신자**는 구매자와 판매자 각각 1건씩이다 (`PaymentCommandService.java:434-456`).
  - 구매자: "결제가 완료되었습니다. 주문 ID: {orderId}"
  - 판매자(`sale.getSeller()`): "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}"
  - 카테고리는 `SHOPPING`, 타입은 `BID`다.
- **시점**: 결제 레코드 저장 직후, 같은 요청·같은 트랜잭션 안이며 동기다 (`:83`).
  - 이 시점에는 OrderBid가 아직 만들어지지 않았다. `order.getOrderBid()`가 null이어서 `saleBidQueryService.findByOrderId`로 SaleBid → Sale을 찾는다 (`:388-406`, `D/sale/service/query/SaleBidQueryService.java:26-28`).
  - 알림 전송 후 `Sale = SOLD`로 바꾼다 (`:403-404`).
  - 결제 결과(`PENDING`, 미성공 카드 포함)와 무관하게 "결제가 완료되었습니다" 알림이 나간다.
- **방식**:
  - `NotificationCommandService#createNotification`이 DB에 Notification을 저장한다 (`D/notification/service/command/NotificationCommandService.java:44-54`).
  - 사용자가 WebSocket에 접속해 Redis 키 `WebSocket:User:{email}`가 있을 때만 `/queue/notifications`로 `convertAndSendToUser` 푸시한다 (`:303-313`).
  - 미접속이면 저장만 한다 (`:320-322`).
  - Kafka/이메일 발송은 없다.
  - 알림 실패는 `sendNotifications`/`notifyUsersAndUpdateSaleStatus`의 catch에서 삼켜 즉시 구매는 실패하지 않는다 (`PaymentCommandService.java:421-425,457-461`).
  - 단, 알림 서비스가 `@Transactional` 클래스라 내부 예외는 공유 트랜잭션을 rollback-only로 표시할 수 있다 (`NotificationCommandService.java:27`). 이 경우 커밋 시점에 `UnexpectedRollbackException`이 날 수 있는 잠재 위험이 있다.

## 5. 최종 상태와 창고 보관 선택

- **Order 최종 상태는 `PENDING_PAYMENT`다.** 처리가 끝나도 `PAYMENT_COMPLETED`/`COMPLETED`로 바뀌지 않는다 (`OrderCommandService.java:244`; 이후 `updateStatus` 호출 없음 — 2절 참고).
  - 같은 요청에서 SaleBid는 `MATCHED`, OrderBid는 `MATCHED`(+즉시구매 플래그), Sale은 `SOLD`, Shipment는 `PENDING`이다.
  - 결제는 수단에 따라 `PAID` 또는 `PENDING`이다.
  - `Order.payment`에 `assignPayment`를 호출하지 않으므로, 이 트랜잭션 내 `Order` 객체의 `payment` 필드는 null이다. DB의 `payment.order_id` FK는 설정된다 (`Payment.java:24-26`, `:47-50`).
- **구매자가 "창고 보관"(`warehouseStorage=true`)을 선택해도 달라지는 것이 없다.**
  - 컨트롤러는 `requestDto.isWarehouseStorage()`를 서비스로 넘긴다 (`OrderBidCommandController.java:105`).
  - `createInstantOrderBid`, `createInstantOrder`에서 이 파라미터는 선언만 되고 본문에서 참조되지 않는다 (`OrderBidCommandService.java:120,137`, `OrderCommandService.java:221`).
  - 결과적으로 구매자 요청의 창고 보관 여부와 무관하게 다음이 적용된다.
    - `IN_WAREHOUSE`/`COMPLETED`로의 상태 전이 없음
    - `createOrderStorage`로 새 WarehouseStorage 생성 없음
    - 배송지 정보는 동일하게 생성
  - 창고 보관 관련 로직(`PAYMENT_COMPLETED → PREPARING → IN_WAREHOUSE → createOrderStorage → COMPLETED`)은 즉시 구매가 아니라 `processPaymentAndShipment`에만 있다 (`OrderCommandService.java:163-172`).
  - 창고 관련 변화는 판매자의 Sale이 창고 보관 상품(`sale.isWarehouseStorage()`)일 때 그 WarehouseStorage가 `ASSOCIATED_WITH_ORDER`가 되는 것뿐이다 (`OrderCommandService.java:291-293`).
