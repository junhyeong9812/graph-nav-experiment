# 구매자 배송: 운송장 등록 → 배송 완료 처리 분석

경로 약어: `S` = `src/main/java/com/fream/back/domain/shipment`, `O` = `src/main/java/com/fream/back/domain/order`, `G` = `src/main/java/com/fream/back/global`.
(코드는 수정하지 않았고, 정적 분석만 했다. 실행/빌드는 하지 않았다.)

## 사전 정리: 중복 코드와 공통 흐름

- 구매자 배송 엔티티는 `OrderShipment` 하나뿐이다 (`S/entity/OrderShipment.java:11-34`). 주문과 1:1 (`:22-24`), 주문 쪽은 `Order.orderShipment` (`O/entity/Order.java:40-41`).
- 결제 후 배송 정보는 `OrderCommandService.processPaymentAndShipment`에서 `PENDING` 상태로 생성된다 (`O/service/command/OrderCommandService.java:148-155`, 생성은 `S/service/command/OrderShipmentCommandService.java:61-70`).
- 배송 컨트롤러·배치 설정이 `shipment`, `adminshipment`, `internalshipment`, `legacyshipment`, `partnershipment`, `settlementshipment` 6곳에 복제돼 있다. 복제본은 알림 서비스 타입·클래스명만 다르고 모두 **동일한 `OrderShipmentCommandService`(shipment 패키지)** 로 위임한다
  (예: `adminshipment/controller/command/AdminOrderShipmentCommandController.java:3-8,24,41`, `adminshipment/config/AdminUpdateShipmentStatusesJobConfig.java`). 따라서 아래 분석은 `shipment` 패키지 기준이며 복제본에도 그대로 적용된다.

## 1. 운송장 등록 요청

### 1-1. 어느 API인가
- 운영 측(관리자): `PATCH /admin/shipments/order/{shipmentId}/status` — `adminshipment/controller/command/AdminOrderShipmentCommandController.java:20,33-34` (body: `OrderShipmentRequestDto`의 courier, trackingNumber).
- 같은 로직의 복제 엔드포인트: `/shipments/order/{id}/status` (`S/controller/command/OrderShipmentCommandController.java:20,33`), `/internal|/legacy|/partner|/settlement/shipments/order/{id}/status`.
- 모두 `OrderShipmentCommandService.updateTrackingInfo(shipmentId, courier, trackingNumber)` 호출 (`OrderShipmentCommandController.java:41`, 서비스 `S/service/command/OrderShipmentCommandService.java:238-239`).
- 인증은 `anyRequest().authenticated()`뿐이며 `/admin/**` 역할 제한은 없다 (`G/config/security/SecurityConfig.java:50-52`).

### 1-2. 의도된 상태 변경 순서와 알림 (`updateTrackingInfo`, `OrderShipmentCommandService.java:238-303`)
1. courier/trackingNumber 공백 검사 → 없으면 `TRACKING_INFO_REQUIRED` (`:243-246`).
2. `OrderShipment` 조회 후 `shipment.updateTrackingInfo` — 택배사·운송장 저장, 배송 상태를 `IN_TRANSIT`으로 직접 설정 (`:249-256`, `S/entity/OrderShipment.java:41-45`; 전이 검증 없음).
3. `Order.updateStatus(IN_TRANSIT)` (`:259-260`).
4. 구매자에게 알림 "상품이 출발하였습니다" 1건 (`:265-271`).
5. `updateSaleStatusToSold(orderId)` (`:276`): SaleBid의 Sale을 `SOLD`로 + 판매자 알림 (`:111-147`), OrderBid의 Sale도 `SOLD` 시도 + 판매자 알림 (`:149-180`). 창고 상태 갱신 (`:278-286`).
6. `updateOrderAndSaleBidStatusToCompleted` — OrderBid·SaleBid가 `MATCHED`면 `COMPLETED` (`:289`, `:412-438`). 이 메서드 안의 예외는 로그만 남기고 삼킨다 (`:435-438`).
   - 의도와 다르게 "운송장 등록 시점"에 Sale이 SOLD, 입찰이 COMPLETED가 되도록 짜여 있다 (배송 완료 시점이 아님).

### 1-3. 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문에서 성공하나? → **실패한다**
- 이 주문의 상태: `processPaymentAndShipment`에서 실배송이면 `PAYMENT_COMPLETED` → `PREPARING`까지만 진행 (`O/service/command/OrderCommandService.java:173-177`). 창고 보관이 아니므로 `SHIPMENT_STARTED`로 가지 않는다.
- 실패 지점: `OrderShipmentCommandService.java:260` `order.updateStatus(OrderStatus.IN_TRANSIT)`.
  - `PREPARING`의 허용 전이는 `{IN_WAREHOUSE, SHIPMENT_STARTED}`뿐 (`O/entity/OrderStatus.java:26`), `IN_TRANSIT`은 `SHIPMENT_STARTED`에서만 허용 (`:28`). 따라서 `Order.updateStatus`가 `InvalidOrderStatusException`을 던진다 (`O/entity/Order.java:113-120`).
  - 이 예외는 `catch (Exception e)`(`OrderShipmentCommandService.java:295`)에서 `ShipmentException(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: ...")`로 감싸져 재던져진다 (`:297-301`). (`ShipmentException`은 `catch (ShipmentException)`으로 먼저 걸러지는 경우만 그대로 전파, `:293-294`.)
- 무엇이 저장되나: **아무것도 저장되지 않는다.** 메서드가 `@Transactional`(`:238`)이고 RuntimeException(`GlobalException extends RuntimeException`, `global/exception/GlobalException.java:10`)이 밖으로 나가므로 롤백된다. 2단계의 운송장·`IN_TRANSIT` 변경은 메모리에서만 일어났고, 4단계 이후(알림·Sale·입찰)는 실행되지도 않는다. 배송은 `PENDING`, 주문은 `PREPARING` 그대로.
- 응답: 컨트롤러는 예외를 잡지 않고 (`OrderShipmentCommandController.java:41`) `GlobalExceptionHandler.handleShipmentException`이 처리한다 (`G/exception/GlobalExceptionHandler.java:459-472`). → **HTTP 404**, body `ErrorResponse(code "S001", message "배송 정보를 찾을 수 없습니다.", status 404, path)` (`S/exception/ShipmentErrorCode.java:12`). 실제 원인 메시지는 body에 담기지 않고 로그에만 남는다. 즉 "배송 정보 없음"이라는 오해를 부르는 응답이다.
- 참고: 설령 `Order`가 `SHIPMENT_STARTED`였다 해도 다음 단계에서 `SaleBid`가 없는 일반 입찰은 `SaleBidQueryService.findByOrderId`가 `null`이 아니라 `IllegalArgumentException`을 던져 (`sale/service/query/SaleBidQueryService.java:26-29`) `updateSaleStatusToSold`(`:116`)에서 같은 방식으로 실패한다 (이 호출은 try 밖).

## 2. 배송 완료 감지

### 2-1. 누가/언제/어떻게
- **스케줄러**가 Spring Batch Job을 실행한다: `ShipmentBatchScheduler.scheduleShipmentStatusJob` (`G/config/ShipmentBatchScheduler.java:34-43`). 사용자 요청으로 감지되는 것이 아니다.
- 주기: `@Scheduled(cron = "0 0 */6 * * *")` (`:34`) → 매 6시간 정각(00·06·12·18시). 스케줄링 활성화는 다른 클래스의 `@EnableScheduling`에 의존한다 (이 클래스에는 없음; 예 `adminweather/config/AdminWeatherDataScheduler.java:16`).
- 실행 Job: `@Qualifier("updateShipmentStatusesJob")` (`:19-21`) — 빈 이름은 `updateShipmentStatusesJob`.
- (보조) 즉시 조회 API `POST .../{shipmentId}/check-status`는 사람이 부르는 단건 경로이며 주기 감지가 아니다 (`OrderShipmentCommandController.java:58`, 서비스 `:456-514`).

### 2-2. 조회 대상
- Reader 쿼리: `SELECT s FROM OrderShipment s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL` — 페이지 50건, 청크 50 (`S/config/UpdateShipmentStatusesJobConfig.java:51,87-96`).
- 주의(Spring Batch `JpaPagingItemReader` 동작에 기반한 추정): 처리 중 상태가 `DELIVERED`로 바뀌면 조건에서 빠지므로 offset 페이징이 일부 건을 건너뛸 수 있다. 다음 주기에 다시 잡힌다.

### 2-3. 실제 실행되는 처리 코드
- Step이 사용하는 프로세서는 **`new ShipmentItemProcessor(playwrightBrowserManager(), notificationService, orderService)`** (`UpdateShipmentStatusesJobConfig.java:69-73`) → `S/config/ShipmentItemProcessor.java:56-157`. Playwright로 CJ 대한통운 페이지(`https://trace.cjlogistics.com/next/tracking.html?wblNo=` `:28`)를 열고 `tbody#statusDetail tr` 마지막 행의 5번째 td를 상태로 읽는다 (`:72-94`, `:167-181`).
- **실행되지 않는 유사 코드**:
  - 같은 설정 클래스의 `shipmentItemProcessor()` 람다 빈 (`UpdateShipmentStatusesJobConfig.java:104-177`)과 `parseCjLogisticsStatus` (`:186`) — Step에 연결되어 있지 않음 (Step은 `:69`에서 `new`로 만든 클래스를 씀).
  - `OrderShipmentCommandService.updateShipmentStatuses()` (`:308-391`) — 호출하는 곳이 없음(스케줄러·컨트롤러 모두 미사용).
  - 복제 패키지(`adminshipment` 등)의 JobConfig/Processor 5벌 — 로직 동일.
- 복제 설정 주의: 6개 `@Configuration`이 모두 같은 이름의 `@Bean updateShipmentStatusesJob`/`updateShipmentStatusesStep`/`shipmentItemReader` 등을 정의한다 (각 `*UpdateShipmentStatusesJobConfig.java:54-62,87,104,239,251,292`). `allow-bean-definition-overriding` 설정은 저장소에서 찾지 못했고 Boot 3.4.1(`build.gradle:3`) 기본값은 금지라서, 정적으로는 기동 시 `BeanDefinitionOverrideException`이 날 위험이 있다 (실행 확인은 못 함). 어느 복제본이 선택되든 위 로직은 동일하다.

### 2-4. 택배사 상태 문자열 → 내부 상태 (`ShipmentItemProcessor.java:220-226`)
| 택배사 문자열 | 내부 상태 |
|---|---|
| `"배송완료"` | `DELIVERED` |
| `"배송출발"` | `OUT_FOR_DELIVERY` |
| 그 외 모든 문자열 | `IN_TRANSIT` |

정확 일치(`trim` 후, `:181`)만 인정한다. 빈 문자열/표 없음은 `TRACKING_HTML_PARSE_ERROR`로 예외 (`:172-189`).
`ShipmentStatus` 전이상 `OUT_FOR_DELIVERY → IN_TRANSIT`은 허용되지 않아 (`S/entity/ShipmentStatus.java:23-27`) 출발 후 택배사가 다른 문구를 주면 `updateStatus`가 `IllegalStateException`(`OrderShipment.java:47-55`)을 던지고 `EXTERNAL_TRACKING_SERVICE_ERROR`로 감싸져 (`ShipmentItemProcessor.java:138-144`) 그 건은 스킵된다.

## 3. 배송 완료 판정 이후 (`ShipmentItemProcessor.java:107-117`)

### 3-1. 엔티티 상태 변경 순서 (모두 성공하는 경우)
1. `OrderShipment.status` → `DELIVERED` (`:113`; `IN_TRANSIT/OUT_FOR_DELIVERY → DELIVERED`는 허용, `ShipmentStatus.java:16-27`).
2. `orderService.completeOrder(orderId)` (`:116`, `OrderShipmentCommandService.java:190-229`):
   - `OrderBid` 조회 (없으면 예외, `:196-197`) →
   - `Order.status` → `COMPLETED` (`:204`) →
   - `updateSaleStatusToSold` (`:208`): SaleBid의 `Sale` → `SOLD` (가능할 때만, `:116-123`; Sale 전이는 `ON_AUCTION`/`SELLING`에서만 SOLD 허용, `sale/entity/SaleStatus.java:21-22`), 창고 상품이면 창고 상태 갱신 (`:126-129`), OrderBid의 Sale도 `SOLD` 시도 (`:154-160`; 이미 SOLD면 전이 불가라 중복 변경 없음).
3. `notificationService.notifyShipmentCompleted(order)` (`:117`).
4. 프로세서가 배송 엔티티를 반환 → `JpaItemWriter`가 저장 (`UpdateShipmentStatusesJobConfig.java:74,239-246`).

### 3-2. 알림 (성공 시)
- 구매자 **2건**: ① `"[completeOrder] 주문이 완료 처리되었습니다. 주문 ID: ..."` (`OrderShipmentCommandService.java:211-217`), ② `"[배송 완료] 상품이 배송 완료되었습니다. 주문 ID: ..."` (`notification/service/command/NotificationCommandService.java:219-229`).
- 판매자 **최대 1건**: `"상품이 성공적으로 판매 완료되었습니다. 판매 ID: ..."` — Sale이 SOLD로 전이 가능할 때만 (`:131-138`). OrderBid 경로(`:162-169`)는 같은 Sale이 이미 SOLD라 중복 발송되지 않는다. Sale이 전이 불가면 판매자 알림은 0건.
- 즉 합계는 구매자 2 + (조건부) 판매자 1.

### 3-3. 입찰 상태
- **주문 입찰(OrderBid)·판매 입찰(SaleBid) 상태는 배치 경로에서 바뀌지 않는다.** `completeOrder`/`updateSaleStatusToSold` 어디에도 입찰 `COMPLETED` 전환이 없다. `COMPLETED`로 바꾸는 `updateOrderAndSaleBidStatusToCompleted`는 `updateTrackingInfo`(운송장 등록)에서만 호출된다 (`:289`). 따라서 배송 완료 후에도 입찰은 `MATCHED`로 남는다 (즉시 구매 OrderBid는 생성 시 `MATCHED`, `O/service/command/OrderBidCommandService.java:196`; SaleBid는 `OrderCommandService.java:280`).
- 참고: 일반 입찰의 `MATCHED` 전환(`OrderCommandService.java:188-190`)은 `orderBidQueryService.findById(orderId)`로 **주문 ID를 입찰 ID처럼** 조회한다 → 다른 입찰이 MATCHED되거나 못 찾으면 그냥 넘어간다 (예외는 `:191-194`에서 삼킴).

## 4. 주문 종류별 차이

배치가 이 주문들을 잡으려면 배송이 `IN_TRANSIT/OUT_FOR_DELIVERY`여야 한다. 1번 API는 위처럼 두 경우 모두 롤백되므로, 이 상태는 즉시 조회 API(`updateAndCheckShipmentStatus`: 운송장 설정과 함께 배송을 `IN_TRANSIT`으로 만들고 주문은 건드리지 않음, `OrderShipmentCommandService.java:473`)나 데이터 직접 수정 등으로만 만들어진다. 아래는 배송이 그 상태이고 택배사가 "배송완료"를 준 경우의 결과다.

### (a) 실배송 일반 구매 입찰 주문 → 끝까지 **진행되지 않음**
- 주문은 `PREPARING` (`OrderCommandService.java:175-177`), OrderBid는 있음, SaleBid는 없음.
- `completeOrder`에서 OrderBid는 찾지만 (`OrderShipmentCommandService.java:196`) `order.updateStatus(COMPLETED)`(`:204`)가 `PREPARING → COMPLETED` 불허(`OrderStatus.java:26`)로 `InvalidOrderStatusException` → `ShipmentException(ORDER_NOT_FOUND_FOR_SHIPMENT)`로 감싸짐 (`:221-227`).
- 결과: 주문 `PREPARING` 유지, 판매자·구매자 알림 없음, 프로세서 예외 → 해당 건 스킵(5번 참고). 배송 `DELIVERED` 변경도 롤백/미저장되어 배송은 `IN_TRANSIT`으로 남고 6시간마다 재시도·재실패한다.

### (b) 즉시 구매로 만든 주문 → 끝까지 **진행됨** (판매 상태는 조건부)
- 즉시 구매는 `createInstantOrder`로 주문·배송·SaleBid 매칭·결제를 만들고 (`OrderCommandService.java:219-311`), 이어서 `MATCHED` OrderBid를 만든다 (`OrderBidCommandService.java:133-142,189-205`). 주문 상태는 `PENDING_PAYMENT`에서 올라가지 않는다 (`OrderCommandService.java:241-245`, 이후 상태 변경 없음; 결제 서비스도 주문 상태를 바꾸지 않음).
- `PENDING_PAYMENT → COMPLETED`는 허용 전이라 (`OrderStatus.java:24`) `completeOrder`가 통과한다. OrderBid·SaleBid가 둘 다 있어 조회 예외도 없다.
- 결과: 배송 `DELIVERED`, 주문 `COMPLETED`, 구매자 알림 2건, Sale이 `ON_AUCTION`/`SELLING`이면 `SOLD` + 판매자 1건(아니면 Sale 변경·판매자 알림 없음, 예외도 없음). OrderBid·SaleBid는 `MATCHED` 유지.
- 대비: 운송장 등록 API(1번)는 (b)도 `PENDING_PAYMENT → IN_TRANSIT` 불허로 똑같이 실패한다.

## 5. 실패 처리 (주기 처리 중 한 건 실패)

- Step이 `faultTolerant().skip(Exception.class).skipLimit(50)`으로 설정돼 있다 (`UpdateShipmentStatusesJobConfig.java:75-77`, `SKIP_LIMIT=50` `:52`).
- 프로세서 예외(조회 실패, 파싱 실패, 상태 전이 불가, `completeOrder` 실패 등)는 `ShipmentException`으로 변환돼 던져진다 (`ShipmentItemProcessor.java:133-145`).
- 해당 건: 스킵 처리되어 writer로 가지 않으므로 저장되지 않는다. `completeOrder`는 `@Transactional`이라 청크 트랜잭션에 참여하며 예외로 롤백된다. 스킵 로그만 남는다 (`shipmentSkipListener`, `:251-287`). 배송은 `IN_TRANSIT/OUT_FOR_DELIVERY`로 남아 다음 6시간 주기에 다시 조회된다 (영구 재시도).
- 나머지 건: 중단되지 않는다. fault-tolerant 청크는 실패 시 해당 청크를 롤백하고 건별로 다시 처리하는 Spring Batch 표준 동작에 따라, 실패한 건만 제외하고 나머지는 처리·저장된다 (이 재처리는 외부 CJ 조회도 반복 발생).
- 한계: 스킵이 50건을 넘으면 `SkipLimitExceededException`으로 Step/Job이 실패하고 남은 건은 그 회차에서 처리되지 않는다. 이 예외는 스케줄러가 `catch (Exception e) { e.printStackTrace(); }`로 삼키고 끝난다 (`ShipmentBatchScheduler.java:41-43`).
