# 구매자 배송: 운송장 등록 → 배송 완료 처리 분석

경로 약어: `D` = `src/main/java/com/fream/back/domain`, `G` = `src/main/java/com/fream/back/global`

핵심 요약
- 운송장 등록 API(`PATCH .../{shipmentId}/status`)는 **실배송 일반 구매 입찰 주문에서는 항상 실패**한다 (주문이 `PREPARING`이라 `IN_TRANSIT`으로 갈 수 없음). 응답은 `404 / S001`, 저장되는 것은 없다.
- 배송 완료 감지는 `ShipmentBatchScheduler`가 **6시간마다** Spring Batch Job을 돌려 CJ대한통운 페이지를 Playwright로 읽어 판정한다. 실제 처리 코드는 `ShipmentItemProcessor`.
- 배송 완료 후처리(`completeOrder`)는 (a) 실배송 일반 입찰 주문은 끝까지 못 가고(주문 상태 전이 거부, 그 뒤에도 SaleBid 조회 예외), (b) 즉시 구매 주문은 끝까지 간다. 단 (b)에서도 OrderBid/SaleBid는 `COMPLETED`가 되지 않고 `MATCHED`로 남는다.

## 1. 운송장 등록 요청

### 1-1. 어느 API로 들어오나
1. 일반(표준) 경로: `PATCH /shipments/order/{shipmentId}/status`, body는 `OrderShipmentRequestDto`(courier, trackingNumber). 근거: `D/shipment/controller/command/OrderShipmentCommandController.java:20`(`@RequestMapping("/shipments/order")`), `:33`(`@PatchMapping("/{shipmentId}/status")`), `:41-45`(서비스 호출).
2. 운영(admin) 측 경로: `PATCH /admin/shipments/order/{shipmentId}/status`. 근거: `D/adminshipment/controller/command/AdminOrderShipmentCommandController.java:20,33,41-45`. 같은 서비스 메서드 `OrderShipmentCommandService.updateTrackingInfo`를 호출한다.
3. partner/settlement/internal/legacy 컨트롤러도 같은 서비스를 호출하는 복사본이다 (`D/partnershipment/controller/command/PartnerOrderShipmentCommandController.java:20,33`, `D/settlementshipment/controller/command/SettlementOrderShipmentCommandController.java:20,33`, 그 외 internal/legacy도 `OrderShipmentCommandService` 사용).
4. 참고: `POST .../{shipmentId}/check-status`도 운송장을 등록하지만 `updateAndCheckShipmentStatus`를 탄다 (`OrderShipmentCommandController.java:58-72`). 아래 4번에서 다룬다.

### 1-2. 코드가 의도한 상태 변경 순서와 알림 (`OrderShipmentCommandService.updateTrackingInfo`, `D/shipment/service/command/OrderShipmentCommandService.java:238-303`)
1. 택배사/운송장 공백 검사 → `TRACKING_INFO_REQUIRED` (`:243-246`).
2. `OrderShipment` 조회 후 `shipment.updateTrackingInfo(courier, trackingNumber)` → courier, trackingNumber 저장 + 배송 상태를 **무조건 `IN_TRANSIT`** 으로 (`:249-256`, `D/shipment/entity/OrderShipment.java:41-45`).
3. `Order.updateStatus(IN_TRANSIT)` (`:259-260`).
4. **구매자**에게 알림 "상품이 출발하였습니다. 주문 ID: …" (`:265-271`).
5. `updateSaleStatusToSold(orderId)` (`:276`, 본문 `:112-183`):
   - SaleBid 경로: Sale을 `SOLD`로(`:116-123`), 창고 보관이면 창고 상태 SOLD(`:126-129`), **판매자**에게 "상품이 성공적으로 판매 완료되었습니다" 알림(`:131-138`).
   - OrderBid 경로: `orderBid.getSale()`을 `SOLD`로, **판매자**에게 같은 문구 알림(`:150-172`).
6. 창고 보관 Sale이면 창고 상태 SOLD 갱신 (`:278-286`).
7. `updateOrderAndSaleBidStatusToCompleted` : OrderBid/SaleBid가 `MATCHED`이면 `COMPLETED`로 (`:289`, `:412-440`). 이 단계 실패는 로그만 남기고 삼킨다(`:436-439`).
8. 즉 의도된 순서는 OrderShipment(IN_TRANSIT) → Order(IN_TRANSIT) → Sale(SOLD)/창고 → OrderBid·SaleBid(COMPLETED)이며, 구매자 1건 + 판매자 알림(경로에 따라 최대 2건)이다. 배송 완료 전인데 판매·입찰이 이미 완료 처리되도록 짜여 있다.

### 1-3. 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문에서 끝까지 성공하나 → **아니오, 항상 실패**
1. 일반 구매 입찰은 `PENDING_PAYMENT` 주문으로 만들어진다 (`D/order/service/command/OrderCommandService.java:59,81`).
2. `processPaymentAndShipment`가 실배송(`isWarehouseStorage=false`)이면 `PAYMENT_COMPLETED` → `PREPARING`까지만 올린다 (`OrderCommandService.java:174-176`, 창고 보관 분기는 `:164-172`). 배송 정보는 `PENDING`으로 생성 (`D/shipment/service/command/OrderShipmentCommandService.java:67`, 호출 `OrderCommandService.java:148`).
3. `OrderStatus`에서 `PREPARING`이 갈 수 있는 곳은 `IN_WAREHOUSE`, `SHIPMENT_STARTED`뿐이고 `IN_TRANSIT`은 `SHIPMENT_STARTED`에서만 갈 수 있다 (`D/order/entity/OrderStatus.java:26,28`). 그런데 `SHIPMENT_STARTED`로 바꾸는 코드는 어디에도 없다 (참조는 조회 컨트롤러의 라벨 매핑뿐, 예: `D/order/controller/query/OrderQueryController.java:207`).
4. 따라서 `updateTrackingInfo`의 `order.updateStatus(IN_TRANSIT)`(`OrderShipmentCommandService.java:260`)에서 `Order.updateStatus`가 `InvalidOrderStatusException`("상태 전환이 허용되지 않습니다: PREPARING -> IN_TRANSIT")을 던진다 (`D/order/entity/Order.java:113-120`).
5. 이 예외는 `catch (Exception e)`(`OrderShipmentCommandService.java:295`)에 잡혀 `ShipmentException(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")`로 바뀌어 던져진다 (`:296-301`). `ShipmentException`은 `GlobalException extends RuntimeException`(`G/exception/GlobalException.java:10`)이라 `@Transactional`(`:238`)이 롤백된다.
6. 무엇이 저장되나: **아무것도 저장되지 않는다.** 2번 단계의 courier/trackingNumber/`IN_TRANSIT` 변경은 영속 컨텍스트 안에서만 일어났고 롤백된다. 구매자 알림(4단계)도 그 뒤 코드라 생성되지 않는다. OrderShipment는 `PENDING`·운송장 없음, Order는 `PREPARING` 그대로.
7. 응답: `GlobalExceptionHandler.handleShipmentException`이 `errorCode.getStatus()`/`getCode()`/`getMessage()`를 쓴다 (`G/exception/GlobalExceptionHandler.java:459-472`). `SHIPMENT_NOT_FOUND`는 `("S001", "배송 정보를 찾을 수 없습니다.", 404)` (`D/shipment/exception/ShipmentErrorCode.java:12`). 즉 **HTTP 404, code `S001`, message "배송 정보를 찾을 수 없습니다."**(본문에 실제 원인 메시지는 들어가지 않고, 사실은 배송이 없는 게 아니라 주문 상태 전이 거부 때문이다).
8. 설령 4번을 통과해도 다음에서 또 실패한다: `updateSaleStatusToSold`가 `saleBidQueryService.findByOrderId`를 부르는데(`:116`) 이 메서드는 SaleBid가 없으면 null이 아니라 `IllegalArgumentException`을 던진다 (`D/sale/service/query/SaleBidQueryService.java:26-28`). 일반 입찰 주문에는 SaleBid가 연결되지 않는다(`saleBid.assignOrder`는 즉시 구매 생성에서만 호출: `OrderCommandService.java:279`; 일반 입찰은 `orderBid.assignSale`로 Sale에만 연결: `D/sale/service/command/SaleCommandService.java:79`). `:117`의 null 검사는 죽은 코드이고, `:150`의 try/catch는 `:116`을 감싸지 않는다.

## 2. 배송 완료 감지

### 2-1. 누가, 언제, 어떻게
1. **누가**: `ShipmentBatchScheduler` (`G/config/ShipmentBatchScheduler.java:13-15`)가 `updateShipmentStatusesJob`(`@Qualifier`로 주입, `:19-21`)을 `JobLauncher`로 실행한다 (`:34-42`).
2. **주기**: `@Scheduled(cron = "0 0 */6 * * *")` (`:34`) = 매일 00:00, 06:00, 12:00, 18:00 (6시간마다 정각). 실패는 `e.printStackTrace()`만 하고 끝난다 (`:42-44`). 스케줄링 활성화는 다른 설정 클래스의 `@EnableScheduling`에 의존한다(예: `D/accessLog/config/AccessLogAopConfiguration.java:37`).
3. **어떻게**: Job → Step(청크 50, `faultTolerant`) → Reader → Processor → Writer (`D/shipment/config/UpdateShipmentStatusesJobConfig.java:54-82`).

### 2-2. 조회 대상
- Reader: `SELECT s FROM OrderShipment s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL`, pageSize 50 (`UpdateShipmentStatusesJobConfig.java:87-97`). 즉 운송장이 등록되어 `IN_TRANSIT`/`OUT_FOR_DELIVERY`인 배송만. `PENDING` 배송(운송장 미등록)은 대상이 아니다.

### 2-3. 실제로 실행되는 처리 코드
비슷한 코드가 여러 곳에 있지만 실제로 도는 것은 **`D/shipment/config/ShipmentItemProcessor.java`** 의 `process()`다.
- Step이 `new ShipmentItemProcessor(playwrightBrowserManager(), notificationService, orderService)`를 processor로 직접 등록한다 (`UpdateShipmentStatusesJobConfig.java:69-73`).
- 같은 파일의 `@Bean shipmentItemProcessor()` 람다(`:104-177`)와 `parseCjLogisticsStatus`(`:186-220`), `mapToShipmentStatus`(`:228-234`)는 Step에서 참조되지 않는 **죽은 코드**다 (`.processor(...)`에는 위 `new`만 들어감, `:69`).
- `OrderShipmentCommandService.updateShipmentStatuses()`(`D/shipment/service/command/OrderShipmentCommandService.java:308-391`)도 어디서도 호출되지 않는다 (`grep` 결과 정의뿐, 스케줄러는 Job만 실행: `ShipmentBatchScheduler.java:34-42`). 주석과 달리 "주기적 업데이트"는 이 메서드가 아니다.
- 처리 순서(`ShipmentItemProcessor.java:57-157`): 운송장 공백 검사(`:61-64`) → `browserManager.newPage()` (`:72`) → CJ 추적 URL 이동(`:81-83`, `TRACKING_URL_PREFIX` `:28`) → `tbody#statusDetail tr` 대기(`:87`) → HTML 파싱, **마지막 행의 5번째 td 텍스트**(`:167-191`, `:181`) → 상태 매핑(`:95`) → 현재 상태와 같으면 그대로 반환(`:101-105`) → 상태별 처리(`:108-126`).
- 사용 알림 서비스는 `D/notification/service/command/NotificationCommandService`(일반). admin/partner/settlement/internal/legacy 쪽 `*UpdateShipmentStatusesJobConfig`도 같은 이름의 Job 빈(`"updateShipmentStatusesJob"`)을 정의하는 복사본이다 (`D/adminshipment/config/AdminUpdateShipmentStatusesJobConfig.java:54-60`, `D/partnershipment/config/PartnerUpdateShipmentStatusesJobConfig.java:54-60` 등). 스케줄러는 이름으로 주입하므로 이름 충돌 시 어느 쪽이 쓰이는지는 빈 등록 결과에 달려 있다. 이 저장소에 `allow-bean-definition-overriding` 설정은 없다(`src/main/resources/application*.yml`). 일반 `shipment` 패키지 구현이 의도된 실행 대상이다.

### 2-4. 택배사 상태 문자열 → 내부 상태 (`ShipmentItemProcessor.java:220-226`)
| CJ 문자열 (정확히 일치) | 내부 `ShipmentStatus` |
|---|---|
| `"배송완료"` | `DELIVERED` |
| `"배송출발"` | `OUT_FOR_DELIVERY` |
| 그 외 모든 문자열 | `IN_TRANSIT` |

- 파싱 단계에서 `trim()`은 하지만(`:181`) 부분 일치는 없다. 빈 문자열/테이블 없음은 `TRACKING_HTML_PARSE_ERROR`(`:172-189`).
- 주의: `OUT_FOR_DELIVERY` 상태인 배송에 "집하" 같은 기타 문자열이 오면 `IN_TRANSIT`으로 매핑되는데 `OUT_FOR_DELIVERY → IN_TRANSIT`은 허용되지 않아(`D/shipment/entity/ShipmentStatus.java`의 `OUT_FOR_DELIVERY` 규칙, 허용: DELIVERED/FAILED_DELIVERY/CANCELED) `IllegalStateException`(`OrderShipment.java:47-54`) → `ShipmentException`으로 감싸져(`ShipmentItemProcessor.java:138-144`) 스킵된다.

## 3. 배송 완료 판정 이후 (`ShipmentItemProcessor.java:108-117`)

### 3-1. 엔티티 상태 변경 순서
1. `orderShipment.updateStatus(DELIVERED)` (`:113`) — `IN_TRANSIT`/`OUT_FOR_DELIVERY`에서 전이 가능 (`ShipmentStatus.java` IN_TRANSIT 규칙에 DELIVERED 포함).
2. `orderService.completeOrder(orderId)` (`:116`) → `OrderShipmentCommandService.completeOrder` (`D/shipment/service/command/OrderShipmentCommandService.java:190-229`):
   1. `OrderBid` 조회 — 없으면 `IllegalArgumentException` (`:195-197`)
   2. `order.updateStatus(COMPLETED)` (`:204`)
   3. `updateSaleStatusToSold(orderId)` (`:208`)
   4. 구매자 알림 생성 (`:211-217`)
   5. 어떤 예외든 `ShipmentException(ORDER_NOT_FOUND_FOR_SHIPMENT)`로 감싸 던짐 (`:221-228`)
3. `notificationService.notifyShipmentCompleted(order)` (`ShipmentItemProcessor.java:117`).
4. Writer(`JpaItemWriter`)가 `OrderShipment`를 DB에 반영 (`UpdateShipmentStatusesJobConfig.java:239-246`).

### 3-2. 알림 (정상 진행 시)
- **구매자**: ① `"[completeOrder] 주문이 완료 처리되었습니다. 주문 ID: …"` (`OrderShipmentCommandService.java:211-217`), ② `"[배송 완료] 상품이 배송 완료되었습니다. 주문 ID: …"` (`D/notification/service/command/NotificationCommandService.java:219-228`). 총 **2건**. `notifyShipmentCompleted`는 예외를 삼킨다(`:230-233`).
- **판매자**: `updateSaleStatusToSold`에서 Sale이 `SOLD`로 **전이 가능한 경우에만** 알림(`OrderShipmentCommandService.java:119-138`, `:156-169`). Sale이 이미 `SOLD`면 `SOLD → *` 불가(`D/sale/entity/SaleStatus.java`의 `case SOLD ... -> false`)라 0건. 두 경로 모두 가능하면 최대 2건.

### 3-3. 주문 입찰·판매 입찰 상태
- 배치 경로에서는 **OrderBid, SaleBid 상태를 바꾸지 않는다.** `completeOrder`는 `updateOrderAndSaleBidStatusToCompleted`를 호출하지 않는다 (이 메서드 호출은 `updateTrackingInfo`의 `:289` 하나뿐, `completeOrder` 본문 `:190-229`에 없음). 따라서 OrderBid/SaleBid는 기존 `MATCHED` 그대로 남고 `COMPLETED`가 되지 않는다.
- Sale만 가능한 경우 `SOLD`로 바뀐다 (`:123`, `:160`).

## 4. 주문 종류별 차이

운송장이 `IN_TRANSIT`으로 등록되어 있어야 배치 대상이 된다. 1번의 `PATCH` 경로는 두 종류 모두 실패하므로(아래), 배치 대상이 되는 길은 `check-status` 경로뿐이다 (`updateAndCheckShipmentStatus`가 courier/운송장/`IN_TRANSIT`을 Shipment에만 적용하고 Order는 건드리지 않음: `OrderShipmentCommandService.java:472-473`, 반환 시 `@Transactional`로 커밋 `:451`). 이 경우 Order 상태는 등록 시점 그대로다.

### (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문 → **끝까지 진행되지 않음**
1. 상태: Order `PREPARING`, OrderBid `MATCHED`(`OrderBid.assignOrder`, `D/order/entity/OrderBid.java:75`), Sale은 `PENDING_SHIPMENT`(`SaleCommandService.java:58-62`)이며 SaleBid 없음.
2. 배송 완료 판정 → `completeOrder` → OrderBid는 조회됨 → `order.updateStatus(COMPLETED)` (`OrderShipmentCommandService.java:204`)에서 `PREPARING → COMPLETED`가 `OrderStatus`상 불가(`OrderStatus.java:26`)라 `InvalidOrderStatusException`.
3. `completeOrder`가 `ShipmentException(ORDER_NOT_FOUND_FOR_SHIPMENT)`로 감싸 던짐 (`:221-228`) → 프로세서 catch가 그대로 다시 던짐 (`ShipmentItemProcessor.java:133-145`) → 해당 청크 롤백, 그 건은 스킵.
4. 결과: OrderShipment는 DB에서 `IN_TRANSIT` 그대로(DELIVERED 변경 롤백), Order `PREPARING`, OrderBid `MATCHED`, Sale 변화 없음, 알림 0건. 다음 주기(6시간 뒤)에 다시 조회·실패를 반복한다.
5. 가정상 Order 상태가 통과해도 `updateSaleStatusToSold`의 `SaleBidQueryService.findByOrderId`가 예외를 던져 같은 방식으로 실패한다 (`SaleBidQueryService.java:26-28`, 호출 `OrderShipmentCommandService.java:116`).

### (b) 즉시 구매로 만들어진 주문 → **끝까지 진행됨**
1. 상태 준비: `createInstantOrder`는 Order를 `PENDING_PAYMENT`로 만들고(`OrderCommandService.java:244`) 상태를 올리지 않는다. `saleBid.assignOrder(order)`로 SaleBid가 `MATCHED`(`:279`, `D/sale/entity/SaleBid.java:58-61`), 결제 처리(`:305`) 중 `notifyUsersAndUpdateSaleStatus`가 SaleBid 경로로 Sale을 이미 `SOLD`로 바꾸고 구매자·판매자에게 결제 알림을 보낸다 (`D/payment/service/command/PaymentCommandService.java:392-406`, `sendNotifications` `:434-456`). OrderBid는 이후 `MATCHED`로 생성되고 즉시 구매 플래그가 붙는다 (`OrderBidCommandService.java:142`, `:189-206`).
2. 배송 완료 판정 → `completeOrder`: OrderBid 있음 → `order.updateStatus(COMPLETED)`: `PENDING_PAYMENT → COMPLETED`는 허용 (`OrderStatus.java:24`) → `updateSaleStatusToSold`: SaleBid는 있으나 Sale이 이미 `SOLD`라 전이 불가 → Sale 변경·판매자 알림 없음, OrderBid 경로도 전이 불가로 건너뜀 (`OrderShipmentCommandService.java:119,156`) → 구매자 알림 ① 생성.
3. 이후 프로세서가 구매자 알림 ②(`[배송 완료]`) 생성, Writer가 OrderShipment `DELIVERED` 저장.
4. 결과: OrderShipment `DELIVERED`, Order `COMPLETED`, Sale `SOLD`(이미), **OrderBid·SaleBid는 `MATCHED` 유지**, 구매자 알림 2건, 판매자 알림 0건.

### 참고: 등록 API(1번)는 (b)에서도 실패
- `updateTrackingInfo`의 `order.updateStatus(IN_TRANSIT)`가 `PENDING_PAYMENT → IN_TRANSIT` 불가(`OrderStatus.java:24`)라 (a)와 같은 404/S001로 실패한다.

## 5. 실패 처리

1. Step은 `faultTolerant().skip(Exception.class).skipLimit(50)` (`UpdateShipmentStatusesJobConfig.java:75-77`, `SKIP_LIMIT` `:52`). Processor 안의 모든 예외는 `ShipmentException`으로 통일되어(`ShipmentItemProcessor.java:133-145`) 스킵 대상이다.
2. 실패한 건: 처리 중 일어난 변경(예: `DELIVERED` 세팅, `completeOrder`의 Order/Sale 변경, 알림 insert)은 청크 트랜잭션 롤백으로 DB에 남지 않는다 (`completeOrder`의 `@Transactional`은 청크 트랜잭션에 참여, `OrderShipmentCommandService.java:190`). 해당 배송은 상태가 그대로(`IN_TRANSIT`/`OUT_FOR_DELIVERY`)라 다음 6시간 주기에 다시 대상이 된다. 스킵 사실은 `SkipListener.onSkipInProcess`가 로그로만 남긴다 (`UpdateShipmentStatusesJobConfig.java:251-266`).
3. 나머지 건: 스킵으로 Step 전체는 중단되지 않고 계속 진행된다. Spring Batch의 fault-tolerant 청크는 실패 시 그 청크를 롤백하고 항목을 하나씩 다시 처리해 실패 항목만 건너뛰므로, 같은 청크의 성공 건은 재처리 후 커밋된다 (이 동작은 Spring Batch 기본 동작에 대한 설명이며 코드에 직접 명시되지는 않음).
4. 한계: 실패(스킵) 건이 50건을 넘으면 `SkipLimitExceededException`으로 Step이 실패하고 남은 건은 그 회차에서 처리되지 않는다. Job 실행 예외는 스케줄러에서 `printStackTrace`만 한다 (`ShipmentBatchScheduler.java:42-44`).
5. 부수 관찰(코드 근거): Reader가 `status IN (...)` 조건의 페이징 쿼리(`JpaPagingItemReader`, pageSize=청크=50, `:87-97`)이므로 처리 중 `DELIVERED`로 바뀌는 건이 있으면 이후 페이지 오프셋이 어긋나 일부 건이 해당 회차에 누락될 수 있다 (다음 회차에 다시 처리됨).
6. 참고: 이 저장소는 admin/partner/settlement/internal/legacy에 같은 이름의 `updateShipmentStatusesJob` 빈을 가진 복사본 설정이 있고, `spring.batch.job.enabled` 설정이 없어 기본값(true)이면 기동 시에도 Job이 한 번 실행될 수 있다 (`src/main/resources/application*.yml`에 해당 키 없음).
