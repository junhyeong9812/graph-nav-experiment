# 즉시 구매 처리 흐름 분석

경로 약어: `D` = `src/main/java/com/fream/back/domain`

> 참고: `internalorder`, `legacyorder`, `settlementorder`, `partnerorder` 도메인은 `/internal/order-bids`, `/legacy/order-bids`, `/settlement/order-bids` 같은 접두사만 다른 동일 코드 사본이다(클래스명 접두사를 제거하면 `OrderCommandService`와 diff가 없음). 이하는 기준 도메인 `order`(`/order-bids/instant`)를 기준으로 쓴다.

## 1. 진입 API, 처리 단계, 동기/비동기, 응답 ID

**진입 API**: `POST /order-bids/instant`
- `D/order/controller/command/OrderBidCommandController.java:23` (`@RequestMapping("/order-bids")`), `:83` (`@PostMapping("/instant")` `createInstantOrderBid`)
- 요청 바디는 `InstantOrderRequestDto`: saleBidId, addressId, warehouseStorage, paymentRequest — `D/order/dto/InstantOrderRequestDto.java:21-29`

**처리 단계** (모두 한 요청 스레드에서 순차 실행):
1. 컨트롤러가 로그인 이메일을 추출하고(`OrderBidCommandController.java:86`), `enrichPaymentRequest`로 결제 요청의 `userEmail`을 채우고 `orderId`를 null로 둔다(`:92`, `:116-120`).
2. `OrderBidCommandService.createInstantOrderBid` (`D/order/service/command/OrderBidCommandService.java:118-149`, `@Transactional`)
   - 입력 검증 `:123`, 구매자 조회 `:126`, SaleBid/Sale 조회·검증 `:129-130`(`:172-184`)
3. `OrderCommandService.createInstantOrder` 호출 (`OrderBidCommandService.java:133`; 구현 `D/order/service/command/OrderCommandService.java:219-319`, `@Transactional`)
   - 주소 조회 `:238` → Order 저장 `:241-247` → `paymentRequest.setOrderId` `:250` → OrderItem 생성 `:255-256` → OrderShipment 생성 `:264-271` → SaleBid 매칭 및 `entityManager.flush()` `:279-283` → (판매 건이 창고 보관이면) 창고 상태 변경 `:291-294` → 결제 처리 `:305`
4. `PaymentCommandService.processPayment` (`D/payment/service/command/PaymentCommandService.java:57-107`): 결제 수단별 Payment 생성 → `notifyUsersAndUpdateSaleStatus`(`:83`) 에서 알림 전송 + Sale을 SOLD로 변경.
5. 다시 `OrderBidCommandService`에서 OrderBid를 `MATCHED` + 즉시구매 플래그로 생성·저장 (`OrderBidCommandService.java:142`, `:189-207`).
6. 컨트롤러가 ID를 응답.

**동기 처리다.** Kafka를 쓰지 않는다. Kafka 비동기 처리(`order-processing-topic`)는 별개 API `POST /orders/{orderId}/process-payment-shipment`(`D/order/controller/command/OrderCommandController.java:42`, `:54`)에만 쓰이며, 즉시 구매 경로(`OrderBidCommandController` → `OrderBidCommandService` → `OrderCommandService`)에는 Producer/Consumer 호출이 없다. 결제 대행사(PortOne) 호출도 RestTemplate 동기 호출이다(`D/payment/portone/PortOneApiClient.java:266`). 전체가 하나의 DB 트랜잭션이다.

**응답으로 돌려주는 ID는 `OrderBid`의 ID다 (Order ID가 아님).**
- `OrderBidCommandController.java:96-102`: `Long orderId = orderBidCommandService.createInstantOrderBid(...).getId();` — 서비스가 반환하는 것은 `OrderBid`(`OrderBidCommandService.java:119`, 반환 `:144`)이므로 `.getId()`는 OrderBid의 PK다. 변수명 `orderId`, javadoc "생성된 주문 ID"(`:75`), 응답 메시지와 달리 실제 값은 입찰(OrderBid) ID다. Order의 ID는 응답에 포함되지 않는다.

## 2. 생성되는 엔티티와 상태 변화 순서

새로 생성되는 엔티티: **Order, OrderItem, OrderShipment, Payment(Card/Account/General 중 하나), OrderBid**, 그리고 알림 `Notification`(구매자·판매자). 기존 엔티티 변경: **SaleBid, Sale, (조건부) WarehouseStorage**.

| 순서 | 동작 | 직후 상태 | 근거 |
|---|---|---|---|
| 1 | Order 저장 | Order.status = `PENDING_PAYMENT`, totalAmount = saleBid.bidPrice | `OrderCommandService.java:241-247` |
| 2 | OrderItem 생성 (수량 1, 가격 = 입찰가) | — | `OrderCommandService.java:255-256`, `D/order/service/command/OrderItemCommandService.java:45-52` |
| 3 | OrderShipment 생성 (주소 조회 결과 사용) | ShipmentStatus = `PENDING` | `OrderCommandService.java:264-271`, `D/shipment/service/command/OrderShipmentCommandService.java:67` |
| 4 | `saleBid.assignOrder(order)` + `updateStatus(MATCHED)` + flush | SaleBid.status = `MATCHED`, SaleBid.order = 주문 | `OrderCommandService.java:279-283`, `D/sale/entity/SaleBid.java:58-61` |
| 5 | (Sale.isWarehouseStorage == true일 때만) 창고 보관 상태 변경 | WarehouseStorage.status = `ASSOCIATED_WITH_ORDER` | `OrderCommandService.java:291-294`, `D/warehouseStorage/service/command/WarehouseStorageCommandService.java:117-133` |
| 6 | 결제 생성 | Payment 상태는 수단별로 다름(3번 참조). `order.assignPayment`는 호출하지 않음 — 반환값을 버림 | `OrderCommandService.java:305` |
| 7 | 알림 전송 후 `sale.updateStatus(SOLD)` | Sale.status = `SOLD` | `PaymentCommandService.java:391-405` |
| 8 | OrderBid 생성 | OrderBid.status = `MATCHED`, isInstantPurchase = true, sale 연결 | `OrderBidCommandService.java:192-206`, `D/order/entity/OrderBid.java:60-82, 97-99` |

단계 7에 대한 보충: 이 시점에는 OrderBid가 아직 없어 `order.getOrderBid()`가 null이므로 `saleBidQueryService.findByOrderId`로 SaleBid를 찾아 그 Sale을 사용하는 분기로 들어간다(`PaymentCommandService.java:388-406`; 조회 `D/sale/service/query/SaleBidQueryService.java:26-29`). 4번에서 `assignOrder`와 flush가 먼저 되어 있어 조회가 성립한다.

주의: Order의 상태는 1단계 이후 **한 번도 바뀌지 않는다**(5번 항목 참조).

## 3. 결제 수단별 결과

분기: `PaymentCommandService.java:67-80` (`getResolvedPaymentType`, `D/payment/dto/PaymentRequestDto.java:74-87`).

| 수단 | 생성 엔티티 / 상태 | 외부 호출 | 근거 |
|---|---|---|---|
| 카드 `CARD` | `CardPayment`. 응답 `status == "success"`이면 `PAID` + isSuccess=true. 그렇지 않으면 기본값 `PENDING`, isSuccess=false 그대로 저장 | PortOne 카드 결제 API 호출 | `PaymentCommandService.java:157-208`; 기본값 `D/payment/entity/Payment.java:39, 44` |
| 계좌이체 `ACCOUNT` | `AccountPayment`, 상태 `PENDING`, isSuccess=false. 은행명만 검증하고 외부 호출 없음 | 없음 | `PaymentCommandService.java:236-262` |
| 일반 `GENERAL` | `GeneralPayment`, 즉시 `PAID` + isSuccess=true. impUid가 비어 있지 않은지만 검사하고 PG에 검증 요청을 하지 않음 | 없음 | `PaymentCommandService.java:290-316` |

**즉시 구매가 끝까지 성공하는가:** 수단과 무관하게, 예외가 없으면 요청은 "성공"으로 끝난다(HTTP 200, "즉시 구매가 성공적으로 처리되었습니다" — `OrderBidCommandController.java:102`). 그러나 결제 완료를 의미하지는 않는다.
- 계좌이체는 Payment가 `PENDING`(미입금)인데도 5단계(Sale SOLD, "결제가 완료되었습니다" 알림, SaleBid MATCHED, OrderBid MATCHED)가 그대로 진행된다. 결제 상태를 확인하는 분기가 없다(`notifyUsersAndUpdateSaleStatus`는 payment 인자를 쓰지 않음, `PaymentCommandService.java:383-426`).
- 결제 금액은 `paidAmount`(요청값, 100 이상 `@Min`)만 검증하며 SaleBid 가격과 비교하지 않는다(`PaymentCommandService.java:141-145`, `PaymentRequestDto.java:50-52`).

**결제 대행사가 카드 결제를 실패로 응답하면** — 실패 형태에 따라 결과가 갈린다.
1. **HTTP 비정상 / 응답 `code != 0` / 통신 오류 / 토큰 발급 실패**: `PortOneApiClient`가 예외를 던진다(`PortOneApiClient.java:270-275`, `:288-293`). → `createCardPayment`가 전파(`PaymentCommandService.java:180-184, 218-219`) → `OrderCommandService.java:306-309`에서 `OrderPaymentProcessingFailedException`으로 변환 → `OrderBidCommandService.handleOrderBidCreationException`(`:145-147`, `:212-218`)이 그대로 재던짐 → 트랜잭션 전체 롤백(Order, OrderItem, OrderShipment, SaleBid MATCHED, 창고 상태 모두 취소). OrderBid는 생성되지 않으며 클라이언트는 오류 응답을 받는다.
2. **HTTP 200 + `code == 0`이지만 `response.status`가 "success"가 아닌 경우(예: "failed")**: 예외가 없다. `PaymentCommandService.java:203-206`의 `if`가 거짓이라 상태/성공 플래그를 바꾸지 않고, `CardPayment`가 `PENDING`, isSuccess=false로 저장된다(`:208`). 이후 알림 전송과 Sale `SOLD`, SaleBid/OrderBid `MATCHED`가 모두 진행되어 응답은 성공이 된다. 즉 **카드 결제 실패 응답이 구매 실패로 이어지지 않는다.** (`PortOneApiClient.processCardPayment`는 `response.status`를 검사하지 않고 `response` 맵만 돌려줌 — `:277-285`)
3. 참고: 1번 경우 롤백은 DB 트랜잭션에 한정된다. 이미 대행사에서 결제가 승인된 뒤 이후 단계(예: 알림)에서 롤백이 일어나도 대행사 결제 취소(`cancelPayment`) 호출은 이 경로에 없다(`handleRefundIfNecessary`는 호출처가 없는 private 메서드, `PaymentCommandService.java:341`).

## 4. 알림: 수신자, 시점, 전달 방식

- **수신자 (2명)**: 구매자 — "결제가 완료되었습니다. 주문 ID: {orderId}", 판매자(`sale.getSeller()`) — "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}". 둘 다 카테고리 `SHOPPING`, 타입 `BID` — `PaymentCommandService.java:434-456`.
- **시점**: 결제(Payment) 저장 직후, 같은 요청·같은 트랜잭션 안에서 Sale을 `SOLD`로 바꾸기 **전**에 전송한다(`PaymentCommandService.java:403-404`). OrderBid 생성보다도 앞선다. 결제 성공 여부와 무관하게 전송되므로 계좌이체(`PENDING`)나 위 2번 케이스(카드 실패 응답)에도 "결제가 완료되었습니다"가 나간다.
- **방식**: `NotificationCommandService.createNotification`(`D/notification/service/command/NotificationCommandService.java:44-67`)이 (a) 알림을 DB에 저장하고 (b) `sendRealTimeNotification`(`:303-323`)으로, Redis에 `WebSocket:User:{email}` 키가 있는 사용자(웹소켓 연결 중)에게만 `/queue/notifications`로 WebSocket push(`convertAndSendToUser`, `:309`). 연결이 없으면 저장만 되고 push는 생략된다. Kafka를 쓰지 않고 동기 호출이다.
- **실패 처리**: 알림 전송 예외는 `sendNotifications`에서 삼키고(`PaymentCommandService.java:457-461`), 상위 `notifyUsersAndUpdateSaleStatus`도 예외를 로그만 남기고 삼킨다(`:421-425`). 따라서 알림이 실패해도 구매는 성공 처리된다. (다만 `NotificationCommandService`는 별도 빈의 클래스 단위 `@Transactional`이라 그 안에서 예외가 나면 공유 트랜잭션이 rollback-only로 표시될 수 있다 — 코드상 가능한 부수 효과이며 실행으로 확인하지는 않았다.)
- 이 경로에서 `OrderEventConsumer`의 성공/실패 알림(`D/order/service/kafka/OrderEventConsumer.java:96`)은 호출되지 않는다.

## 5. 최종 주문 상태와 창고 보관 선택 시 차이

**최종 Order 상태는 `PENDING_PAYMENT`(결제 대기)다.**
- 즉시 구매 경로에서 `Order.updateStatus`를 호출하는 곳이 없다. Order는 `PENDING_PAYMENT`로 저장된 뒤(`OrderCommandService.java:244`) 끝까지 그대로다.
- `PAYMENT_COMPLETED → PREPARING`(또는 창고 보관 시 `IN_WAREHOUSE → COMPLETED`)로 바꾸는 코드는 `processPaymentAndShipment`(`OrderCommandService.java:162-177`)와 Kafka 컨슈머(`OrderEventConsumer.java:192-210`)에만 있고, 이는 `/orders/{orderId}/process-payment-shipment` 경로다. 즉시 구매는 그 경로를 타지 않는다.
- 따라서 카드 결제가 `PAID`로 성공해도 Order는 `PENDING_PAYMENT`이며, 함께 만들어진 것은 SaleBid `MATCHED`, Sale `SOLD`, OrderBid `MATCHED`, OrderShipment `PENDING`이다.

**구매자가 "창고 보관"(`warehouseStorage=true`)을 선택해도 아무것도 달라지지 않는다.**
- 컨트롤러는 값을 서비스로 넘기고(`OrderBidCommandController.java:98-103`) `OrderBidCommandService.createInstantOrderBid`도 `OrderCommandService.createInstantOrder`로 그대로 전달하지만(`OrderBidCommandService.java:133-139`), `createInstantOrder` 본문(`OrderCommandService.java:222-318`)에서 `isWarehouseStorage` 파라미터는 **한 번도 읽히지 않는다**(javadoc과 시그니처에만 존재, `:210`, `:221`).
- 구매자용 `WarehouseStorage`를 만드는 `warehouseStorageCommandService.createOrderStorage`는 `processPaymentAndShipment`에서만 호출된다(`OrderCommandService.java:170`). 즉시 구매에서는 `order.assignWarehouseStorage`, `IN_WAREHOUSE`, `COMPLETED` 전이가 모두 일어나지 않는다.
- 배송 정보는 항상 만들어진다(`OrderCommandService.java:264-271`). 창고 보관 여부와 상관없이 구매자 주소로 OrderShipment(`PENDING`)가 생성된다.
- 창고 관련 분기가 하나 있지만 이는 **판매자의 Sale.isWarehouseStorage** 값에 의한 것이다(`OrderCommandService.java:291-294`, 필드 `D/sale/entity/Sale.java:43`). 그 경우 판매자의 기존 WarehouseStorage가 `ASSOCIATED_WITH_ORDER`로 바뀐다. 이 값은 구매자가 보낸 `warehouseStorage` 플래그와 무관하다. 해당 창고 레코드가 없으면 `WarehouseStorageNotFoundException`(`D/warehouseStorage/service/query/WarehouseStorageQueryService.java:30-33`)이 나서 `OrderWarehouseStorageProcessingFailedException`(`OrderCommandService.java:295-301`)으로 전체 롤백된다.
