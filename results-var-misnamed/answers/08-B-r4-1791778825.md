# 구매자 배송: 운송장 등록 → 배송 완료

> 클래스 이름이 실제 도메인과 어긋나 있다. 구매자 배송 = `FaqAddress`(테이블 `order_shipment`), 주문 = `Faq`(테이블 `orders`),
> 주문 입찰 = `FaqBid`, 판매 입찰 = `StyleBid`, 판매 = `Style`, 알림 = `payment` 도메인의 `Payment`/`PaymentCommandService`.
> `shipment` 패키지의 `Shipment` 는 주소록이라 이 흐름과 무관하다.
> 경로 접두사 `D` = `src/main/java/com/fream/back/domain`

## 0. 사전 상태 (결제·배송 처리를 마친 실배송 일반 구매 입찰 주문)

- 입찰 시 주문은 `PENDING_PAYMENT` 로 생성된다. — `D/faq/service/command/FaqCommandService.java:81`
- 결제·배송 정보 처리에서 배송정보(`FaqAddress`)가 `PENDING` 으로 만들어진다. — `D/address/service/command/FaqAddressCommandService.java:61-68`, 호출 `D/faq/service/command/FaqCommandService.java:148`
- 창고보관이 아닌 실배송이면 주문은 `PAYMENT_COMPLETED` → `PREPARING` 에서 멈춘다. — `D/faq/service/command/FaqCommandService.java:175-176` (Kafka 경로도 동일: `D/faq/service/kafka/FaqEventConsumer.java:195,216-217`)
- 즉 운송장 등록 시점의 주문 상태는 **PREPARING**, 배송 상태는 **PENDING** 이다.

## 1. 운송장 등록 요청

### 1-1. API
- `PATCH /shipments/order/{shipmentId}/status`, 바디 `FaqAddressRequestDto{courier, trackingNumber}` — `D/address/controller/command/FaqAddressCommandController.java:20,33-45`
- 서비스 `FaqAddressCommandService.updateTrackingInfo` (`@Transactional`) — `D/address/service/command/FaqAddressCommandService.java:238-239`
- 경로는 `SecurityConfig` 화이트리스트에 없어 인증만 요구되고(`anyRequest().authenticated()`), 운영자 권한 검사는 코드에 없다. — `src/main/java/com/fream/back/global/config/security/SecurityConfig.java:51-52`

### 1-2. 의도된 상태 변경 순서와 알림 (코드에 짜인 순서)
1. 택배사·운송장 입력 검증(비면 `TRACKING_INFO_REQUIRED`) — `FaqAddressCommandService.java:243-246`
2. 배송 조회 후 `shipment.updateTrackingInfo()` : 택배사/운송장 저장 + 배송 상태를 **IN_TRANSIT** 으로 직접 세팅(전이 검사 없음) — `FaqAddressCommandService.java:256`, `D/address/entity/FaqAddress.java:41-45`
3. 주문 `order.updateStatus(IN_TRANSIT)` — `FaqAddressCommandService.java:259-260`
4. 구매자에게 알림 1건 "상품이 출발하였습니다. 주문 ID" — `FaqAddressCommandService.java:265-271`
5. `updateSaleStatusToSold(orderId)` : 판매(Style)를 **SOLD** 로, 판매자에게 알림 "상품이 성공적으로 판매 완료…" — `FaqAddressCommandService.java:276`, `:111-183`
6. 창고보관 판매면 창고 상태 갱신 — `FaqAddressCommandService.java:279-286`
7. `updateOrderAndSaleBidStatusToCompleted` : FaqBid·StyleBid 가 `MATCHED` 면 `COMPLETED` — `FaqAddressCommandService.java:289`, `:413-440`

즉 의도상 판매 SOLD·입찰 COMPLETED 는 "운송장 등록 시점"에 일어나게 되어 있고 배송 완료와는 무관하다.

### 1-3. 실제로 끝까지 성공하나? → **아니오, 3단계에서 실패한다**
- 실패 지점: `order.updateStatus(FaqStatus.IN_TRANSIT)` — `FaqAddressCommandService.java:260`, `D/faq/entity/Faq.java:113-121`
- 이유: `FaqStatus` 전이표에서 `IN_TRANSIT` 으로 갈 수 있는 상태는 `SHIPMENT_STARTED` 뿐인데(`D/faq/entity/FaqStatus.java:161-162`), 현재 주문은 `PREPARING`(허용: `IN_WAREHOUSE`, `SHIPMENT_STARTED` — `FaqStatus.java:159`)이다. 게다가 코드 어디에서도 `SHIPMENT_STARTED` 로 바꾸지 않는다(저장소 전체에서 enum 정의 외 사용처 없음). → `InvalidFaqStatusException`("상태 전환이 허용되지 않습니다: PREPARING -> IN_TRANSIT") 발생.
- 예외 처리: `AddressException` 이 아니므로 `catch (Exception e)` 에서 `AddressException(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")` 로 감싸 던진다. — `FaqAddressCommandService.java:293-302`
- 저장되는 것: **없다.** 예외가 `@Transactional` 메서드 밖으로 전파되어 롤백되므로, 2단계에서 영속성 컨텍스트에 반영한 택배사/운송장/`IN_TRANSIT` 변경도 버려진다(배송은 `PENDING`, 운송장 null 유지). 4~7단계(알림·SOLD·입찰 COMPLETED)는 실행되지 않아 알림도 0건이다.
- 응답: `GlobalExceptionHandler.handleShipmentException` 이 `errorCode` 기준으로 응답 → **HTTP 404**, `ErrorResponse{code:"S001", message:"배송 정보를 찾을 수 없습니다.", status:404, path}`. 상세 메시지(상태 전환 불가)는 본문에 안 나오고 오류 코드는 실제 원인과 무관한 "배송 정보 없음"이다. — `src/main/java/com/fream/back/global/exception/GlobalExceptionHandler.java:459-473`, `D/address/exception/AddressErrorCode.java:12`
- 참고: 같은 이유로 즉시 구매 주문도 (상태가 `PENDING_PAYMENT`, 허용: `PAYMENT_COMPLETED/COMPLETED/IN_WAREHOUSE` — `FaqStatus.java:157`) 이 API 로는 실패한다.

## 2. 배송 완료 감지

### 2-1. 누가·언제·어떻게
- 주체: 스케줄러 `AddressBatchScheduler.scheduleShipmentStatusJob()` 가 Spring Batch 잡 `updateShipmentStatusesJob` 을 `JobLauncher` 로 실행(파라미터 `timestamp`). — `src/main/java/com/fream/back/global/config/AddressBatchScheduler.java:34-41`
- 주기: `@Scheduled(cron = "0 0 */6 * * *")` = 6시간마다 정각(0/6/12/18시, 서버 타임존). — `AddressBatchScheduler.java:34` (`@EnableScheduling` 은 다른 설정 클래스에 선언: `D/event/scheduler/EventStatusScheduler.java:22`)
- 수동 경로가 하나 더 있다: `POST /shipments/order/{id}/check-status`, `/check-status-string` → `updateAndCheckShipmentStatus` (요청 시 즉시 조회). — `FaqAddressCommandController.java:58-137`, `FaqAddressCommandService.java:451-516`

### 2-2. 대상 배송
- Reader 쿼리: `SELECT s FROM FaqAddress s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL` , 페이지/청크 50. — `D/address/config/UpdateAddressStatusesJobConfig.java:51,87-96`
- 따라서 `PENDING` 배송(운송장 등록이 1-3에서 실패한 건)은 대상이 아니다.

### 2-3. 실제 실행되는 처리 코드
- Step 의 processor 는 `new AddressItemProcessor(...)` (Playwright 로 CJ 대한통운 페이지를 열어 조회). — `UpdateAddressStatusesJobConfig.java:66-73`, `D/address/config/AddressItemProcessor.java:57-130`
- 실행되지 않는 유사 코드(죽은 코드):
  - `UpdateAddressStatusesJobConfig.shipmentItemProcessor()` 빈과 `parseCjLogisticsStatus()` — Step 에 연결되지 않음 (`UpdateAddressStatusesJobConfig.java:104-177, 186-220`; 사용처 없음)
  - `FaqAddressCommandService.updateShipmentStatuses()` — 호출처 없음 (`FaqAddressCommandService.java:308-391`)
  - 그 외 `updateShipmentStatus`(`:83`)도 호출처 없음
- 이 중 `AddressItemProcessor` 만이 `completeOrder` + `notifyShipmentCompleted` 를 실제로 호출한다(`AddressItemProcessor.java:113-117`). 죽은 코드(`updateShipmentStatuses`)는 주문 COMPLETED 와 알림만 하고 판매/입찰은 건드리지 않아 동작이 다르다.

### 2-4. 택배사 문자열 → 내부 상태
- 조회 페이지 `https://trace.cjlogistics.com/next/tracking.html?wblNo={운송장}` 의 `tbody#statusDetail tr` 마지막 행의 5번째 `td` 텍스트(trim)를 상태 문자열로 사용. 행이 없거나 비면 `TRACKING_HTML_PARSE_ERROR`. — `AddressItemProcessor.java:28-29,81-83,176-190`
- 매핑(정확히 일치): `"배송완료"` → `DELIVERED`, `"배송출발"` → `OUT_FOR_DELIVERY`, 그 외 모두 → `IN_TRANSIT`. — `AddressItemProcessor.java:220-226`
- 현재 상태와 매핑 결과가 같으면 아무것도 안 하고 반환. — `AddressItemProcessor.java:101-104`
- 전이 검사: `OUT_FOR_DELIVERY` 인 배송에 "그 외" 문자열이 오면 `IN_TRANSIT` 로 되돌리려 하지만 `OUT_FOR_DELIVERY` 는 `DELIVERED/FAILED_DELIVERY/CANCELED` 로만 갈 수 있어 `IllegalStateException` → 해당 건 스킵. — `AddressItemProcessor.java:123-125`, `D/address/entity/FaqAddress.java:47-55`, `D/address/entity/AddressStatus.java:79-84`

## 3. 배송 완료 판정 이후 (`AddressItemProcessor`, 상태 문자열이 "배송완료")

상태 변경 순서:
1. 배송 `DELIVERED` (메모리 상 변경, 청크 writer `JpaItemWriter` 가 저장) — `AddressItemProcessor.java:113`, `UpdateAddressStatusesJobConfig.java:239-246`
2. `completeOrder(orderId)` — `AddressItemProcessor.java:116`, `FaqAddressCommandService.java:190-229`
   1. `FaqBid` 조회(없으면 IAE→AddressException) — `:196-197`
   2. 주문 `COMPLETED` — `:204`
   3. `updateSaleStatusToSold` — `:208`: `StyleBid` 조회(없으면 IAE, 이 첫 블록은 try 밖이라 `completeOrder` 의 catch 로 전파) `:116`; 판매가 `canTransitionTo(SOLD)`(= `SELLING`/`ON_AUCTION` 일 때만, `D/style/entity/StyleStatus.java:97-98`)면 `SOLD` + 창고 보관 시 창고 상태 갱신 + 판매자 알림 1건 — `:117-141`. 이어서 `FaqBid.getSale()` 로 같은 판매를 다시 검사하나 이미 `SOLD` 라 전이 불가(중복 알림 없음) — `:150-176`
   4. 구매자 알림 "[completeOrder] 주문이 완료 처리되었습니다. 주문 ID" — `:211-217`
3. `notificationService.notifyShipmentCompleted(order)` → 구매자 알림 "[배송 완료] 상품이 배송 완료되었습니다. 주문 ID" (내부 예외는 삼킴) — `AddressItemProcessor.java:117`, `D/payment/service/command/PaymentCommandService.java:219-234`

알림 수:
- 구매자 **2건** ("[completeOrder]…", "[배송 완료]…"). 
- 판매자 **0 또는 1건** — 판매가 아직 `SELLING`/`ON_AUCTION` 이어서 이 단계에서 `SOLD` 로 바뀐 경우만 1건. 이미 `SOLD` 면 0건(아래 4-(b) 참고).

주문 입찰·판매 입찰 상태:
- **변경되지 않는다.** 입찰을 `COMPLETED` 로 바꾸는 `updateOrderAndSaleBidStatusToCompleted` 는 운송장 등록 메서드(`updateTrackingInfo`)에서만 호출된다(`FaqAddressCommandService.java:289`; 1-3 처럼 실패). 배치 경로(`completeOrder`/`AddressItemProcessor`)에는 입찰 상태 변경이 없어 `MATCHED` 그대로 남는다. (참고: 이 private 메서드의 `@Transactional` 은 자기호출/private 이라 효력도 없다. `:412-413`)

## 4. 주문 종류별 차이

전제: 배치는 배송이 `IN_TRANSIT/OUT_FOR_DELIVERY` + 운송장 보유여야 대상이다. 정상 등록 API(1-3)는 두 주문 모두 실패하므로, 대상이 되려면 `check-status` 계열 API 가 `updateTrackingInfo` 로 배송만 `IN_TRANSIT` 으로 바꿔둔 경우(주문 상태는 안 건드림 — `FaqAddressCommandService.java:473`)뿐이다.

### (a) 실배송 일반 구매 입찰 주문 → 끝까지 진행되지 않는다
- 주문 상태가 `PREPARING`(0절)인데 `completeOrder` 의 `order.updateStatus(COMPLETED)` 는 `PREPARING → COMPLETED` 를 허용하지 않아(`FaqStatus.java:159`) `InvalidFaqStatusException` — `FaqAddressCommandService.java:204`
- `completeOrder` 의 catch 가 `AddressException(ORDER_NOT_FOUND_FOR_SHIPMENT)` 로 감싸 던짐 → processor 예외 → 스킵. — `FaqAddressCommandService.java:221-228`
- 결과: 배송·주문·판매·입찰 어느 것도 저장되지 않고(청크 롤백), 알림 0건. 배송은 `IN_TRANSIT` 그대로라 6시간마다 같은 실패를 반복한다. (그 앞에서 `StyleBid` 가 아직 없으면 `findByOrderId` 가 IAE 를 던져 같은 방식으로 실패 — `StyleBidQueryService.java:26-29`)

### (b) 즉시 구매로 만들어진 주문 → 끝까지 진행된다
- 즉시 구매 주문은 `PENDING_PAYMENT` 로 생성되고(`FaqCommandService.java:244`), 결제 처리에서도 주문 상태를 바꾸지 않는다. `PENDING_PAYMENT → COMPLETED` 는 허용된다(`FaqStatus.java:157`).
- `FaqBid`(`order`·`sale` 연결, `isInstantPurchase=true`)와 `StyleBid.order` 가 모두 만들어져 있어 두 조회가 성공한다. — `D/faq/service/command/FaqBidCommandService.java:189-206`, `FaqCommandService.java:279`
- 판매(Style)는 결제 시점에 이미 `SOLD` 로 바뀌고 구매자·판매자에게 결제 알림이 갔다(주문에 `orderBid` 가 아직 없어 `StyleBid` 경로 사용). — `D/notification/service/command/NotificationCommandService.java:388-407`
- 따라서 배송 완료 시: 배송 `DELIVERED`, 주문 `COMPLETED`, 판매는 이미 `SOLD` 라 `canTransitionTo(SOLD)` 가 false → 판매자 알림 0건, 구매자 알림 2건. 입찰은 `MATCHED` 유지.

## 5. 실패 처리 (주기 처리 중 한 건이 실패할 때)

- Step 은 `faultTolerant().skip(Exception.class).skipLimit(50)` 이고 청크 크기 50. — `UpdateAddressStatusesJobConfig.java:51-52,67,75-78`
- processor 가 예외를 던지면(`AddressException` 또는 래핑된 `EXTERNAL_TRACKING_SERVICE_ERROR`; `AddressItemProcessor.java:81-91`) 그 건은 **스킵**되어 `shipmentSkipListener` 가 로그만 남기고 저장되지 않는다. 같은 청크 안의 다른 건은 Spring Batch 의 청크 롤백 후 건별 재처리로 정상 처리·저장된다. 나머지 청크도 계속 진행된다. — `UpdateAddressStatusesJobConfig.java:251-287`
- 스킵된 건은 상태가 그대로(`IN_TRANSIT/OUT_FOR_DELIVERY`)라 다음 6시간 주기에 다시 조회된다. 별도 재시도 횟수·실패 표시는 없다.
- 스킵이 50건을 넘으면 `SkipLimitExceededException` 으로 Step/Job 이 실패하고 남은 건은 그 회차에서 처리되지 않는다(스킵 한도는 Step 실행 단위).
- 브라우저는 Step 시작 시 열고 종료 시 닫는다. 페이지는 건별 `finally` 에서 닫는다. — `D/address/config/BrowserManageStepListener.java:15-25`, `AddressItemProcessor.java:92-101`
- 스케줄러 쪽 `jobLauncher.run` 예외는 `printStackTrace()` 만 한다. — `AddressBatchScheduler.java:41-43`
- (참고) 알림 DB 저장은 청크 트랜잭션과 함께 롤백되지만, `createNotification` 이 보내는 실시간 푸시(`sendRealTimeNotification`)는 롤백 대상이 아니다. — `PaymentCommandService.java:44-60` (추론; 실제 중복 푸시 여부는 실행해 보지 않음)
