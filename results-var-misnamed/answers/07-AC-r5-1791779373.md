# 즉시 구매 처리 흐름 (ANSWER)

용어: 이 코드베이스에서 `faq` 도메인 = 주문(Order, 테이블 `orders`), `FaqBid` = 구매 입찰(`order_bid`), `style` 도메인 = 판매(Sale), `StyleBid` = 판매 입찰(`sale_bid`), `Style` = 판매 건, `notification` 도메인의 `Notification` = 결제(Payment, 테이블 `payment`), `payment` 도메인의 `Payment` = 사용자 알림(in-app).
경로 접두어 `P` = `src/main/java/com/fream/back/domain`.

## 1. 진입 API · 처리 단계 · 동기/비동기 · 응답 ID

**API**: `POST /order-bids/instant` — `P/faq/controller/command/FaqBidCommandController.java:22,89-90` (`createInstantOrderBid`). 요청 DTO는 `saleBidId`, `addressId`, `warehouseStorage`, `paymentRequest` (`P/faq/dto/InstantFaqRequestDto.java:20-29`).

**처리 단계 (모두 한 요청 스레드·한 트랜잭션 안에서 동기 실행)**
1. 컨트롤러가 로그인 이메일을 꺼내고(`FaqBidCommandController.java:92`), 결제 요청에 `userEmail=이메일`, `orderId=null`을 덮어쓴다(`FaqBidCommandController.java:98, 119-123`).
2. `FaqBidCommandService#createInstantOrderBid` (`@Transactional`, `P/faq/service/command/FaqBidCommandService.java:118-149`): 입력 검증(`:154-167`) → 구매자 조회(`:126`) → 판매 입찰 조회·검증(`:129`, `:172-184`) → `FaqCommandService#createInstantOrder` 호출(`:133`) → 구매 입찰(`FaqBid`) 생성(`:142`, `:189-207`).
3. `FaqCommandService#createInstantOrder` (`@Transactional`, `P/faq/service/command/FaqCommandService.java:219-319`) 내부 순서:
   1. 배송지 조회 `addressQueryService.getAddress(email, addressId)` (`:238`)
   2. `Faq` 주문 생성·저장, 상태 `PENDING_PAYMENT`, 금액 = 판매 입찰가 (`:241-247`)
   3. `paymentRequest.setOrderId(order.getId())` (`:250`)
   4. 주문 항목 `FaqItem` 생성 (`:255-256`; `P/faq/service/command/FaqItemCommandService.java:45-52`)
   5. 배송 정보 `FaqAddress` 생성, 상태 `PENDING` (`:264-271`; `P/address/service/command/FaqAddressCommandService.java:61-70`)
   6. 판매 입찰 매칭: `saleBid.assignOrder(order)` + `updateStatus(MATCHED)` + `entityManager.flush()` (`:279-283`)
   7. 판매 건이 창고 보관이면 창고 상태를 `ASSOCIATED_WITH_ORDER`로 변경 (`:291-294`)
   8. 결제 처리 `paymentCommandService.processPayment(...)` (`:305`)
4. 결제 처리 후 `NotificationCommandService#notifyUsersAndUpdateSaleStatus`에서 알림 발송 및 판매 건 `SOLD` 처리 (`P/notification/service/command/NotificationCommandService.java:83, 383-420`).

**동기/비동기**: 동기다. 이 경로에는 Kafka 발행이나 `@Async`가 없다. Kafka 이벤트(`FaqEventProducer#sendOrderProcessingEvent`)는 별도 엔드포인트 `POST /orders/{orderId}/process-payment-shipment`에서만 쓰인다(`P/faq/controller/command/FaqCommandController.java:42-54`, 202 ACCEPTED 반환 `:68`). 즉시 구매는 PG 호출까지 요청 안에서 끝내고 `200 OK`로 응답한다(`FaqBidCommandController.java:109`).

**응답 ID**: 성공 메시지와 변수명은 `orderId`지만(`FaqBidCommandController.java:101,109`) 실제 반환값은 `createInstantOrderBid(...)`가 돌려준 **`FaqBid`(구매 입찰)의 ID**다(`FaqBidCommandController.java:107` `.getId()`, 서비스 반환 `FaqBidCommandService.java:142-144`). 주문(`Faq`) ID도, 판매 입찰 ID도 아니다. 주문 ID는 응답에 들어 있지 않다.

주의할 실제 동작:
- 판매 건이 `SOLD`가 되는 시점은 판매 입찰 매칭(4번) 이후, 결제 생성(6번) 직후다. 이때 `Faq.orderBid`는 아직 `null`이라(구매 입찰은 결제 이후에 만들어진다) `NotificationCommandService.java:388-406`의 "orderBid == null" 분기로 들어가 `saleBidQueryService.findByOrderId`로 판매 입찰을 찾아 `saleBid.getSale()`을 SOLD 처리한다.
- `StyleStatus.canTransitionTo`는 전환 규칙을 갖고 있지만 `Style#updateStatus`는 이를 검사하지 않고 값을 그대로 덮어쓴다(`P/style/entity/StyleStatus.java:15-25`, `Style.java:73-75`). 판매 건의 현재 상태와 무관하게 SOLD가 된다.
- 주문 상태는 이 경로에서 `PENDING_PAYMENT`로 만들어진 뒤 **한 번도 바뀌지 않는다**(5번 항목 참조).

## 3. 결제 수단별 결과, 성공 여부, 카드 실패 시

결제 수단 분기: `NotificationCommandService.java:67-80`. 공통 검증(주문 ID 일치, 이메일 일치, `paidAmount > 0`)은 `:117-146`. 결제 금액은 클라이언트가 보낸 `paidAmount`이며 판매 입찰가와 대조하지 않는다(`:142-145`; DTO는 최소 100원만 검증 `P/notification/dto/NotificationRequestDto.java:50-52`).

| 결제 수단 | 동작 | 결제 엔티티 상태 | 근거 |
|---|---|---|---|
| 카드 `CARD` | 저장된 결제 정보(`NotificationInfo`)를 조회해 PortOne API 호출. 응답 `status == "success"`일 때만 `PAID` + `isSuccess=true` | 성공 응답: `PAID`. 그 외 응답(예: code 0이지만 status가 failed 등)이면 **기본값 `PENDING` 그대로 저장되고 예외 없음** | `NotificationCommandService.java:164-208`; `P/notification/entity/Notification.java:43-44` |
| 계좌이체 `ACCOUNT` | PG 호출 없음. 은행명 검증 후 저장 | `PENDING` (입금 확인 로직 없음) | `NotificationCommandService.java:243-262` |
| 일반 `GENERAL` | PG 호출·검증 없음. 클라이언트가 보낸 `impUid`가 있으면 그대로 신뢰 | 즉시 `PAID`, `isSuccess=true` | `NotificationCommandService.java:297-316` |

**즉시 구매가 끝까지 성공하는가**: 결제 수단과 상관없이 `processPayment`가 예외 없이 끝나면 요청은 성공(200)한다. 계좌이체는 결제가 `PENDING`인 채로, 카드도 PG가 `status != success`로 응답하면 `PENDING`인 채로 아래 후속 처리(알림·SOLD·구매 입찰 MATCHED)가 그대로 진행된다. 결제 완료 여부로 후속 처리를 가르는 코드는 없다(`NotificationCommandService.java:83` 호출은 결제 상태를 보지 않음). 메시지도 무조건 "즉시 구매가 성공적으로 처리되었습니다"(`FaqBidCommandController.java:109`)이며, 알림 문구도 "결제가 완료되었습니다"(`NotificationCommandService.java:442`)로 나간다.

**PG(PortOne)가 카드 결제를 실패로 응답하는 경우**
- HTTP 상태가 200이 아니거나 `code != 0`이면 `NotificationProcessingException`을 던진다(`P/notification/portone/PortOneApiClient.java:270-274`). 통신 오류(`RestClientException`)는 `NotificationApiException`(`:289-290`). 이들은 `createCardPayment`→`processPayment`에서 그대로 전파되고(`NotificationCommandService.java:180-184, 218-219, 89-94`), `createInstantOrder`가 `FaqNotificationProcessingFailedException`으로 감싸 던진다(`FaqCommandService.java:304-309`) → `createInstantOrderBid`에서 그대로 재던짐(`FaqBidCommandService.java:145-146, 212-217`).
- 두 서비스 메서드가 모두 `@Transactional`이고 예외가 밖으로 전파되므로 **주문·주문 항목·배송 정보·판매 입찰 `MATCHED`·창고 상태 변경이 모두 롤백**된다. 구매 입찰은 아직 만들어지지 않았다. 알림도 만들어지기 전이라 아무도 알림을 받지 않는다. 컨트롤러에 try/catch가 없어 `GlobalExceptionHandler`(`src/main/java/com/fream/back/global/exception/GlobalExceptionHandler.java:12`, `FaqException` 처리)가 오류 응답으로 바꾼다.
- `processCardPayment`에 `@Retryable(NotificationApiException, 3회)`가 붙어 있으나(`PortOneApiClient.java:224-228`) 프로젝트에 `@EnableRetry`가 없어(`grep EnableRetry` 결과 없음) 실제로는 재시도되지 않는다. 또 `NotificationProcessingException`은 재시도 대상도 아니다.
- 실패 이력을 남기는 코드는 없다. 롤백되어 `FAILED` 결제 레코드도 남지 않는다(`NotificationStatus.FAILED`는 이 경로에서 설정되지 않음).

## 4. 알림 수신자·시점·방식

- **누가**: 결제 처리 성공 직후 구매자와 판매자 각각 1건. 구매자는 "결제가 완료되었습니다. 주문 ID: {orderId}", 판매자(`sale.getSeller()`)는 "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}" (`NotificationCommandService.java:436-456`). 둘 다 `PaymentCategory.SHOPPING`, `PaymentType.BID`.
- **언제**: `processPayment` 안에서 결제 엔티티 저장 직후(`:83`), 판매 건을 SOLD로 바꾸기 직전(`:403-404`, `:416-419`) — 즉 요청 처리 중 동기로, 구매 입찰 생성보다 앞서 발송된다. 위 3번에서 본 대로 결제가 `PENDING`이어도 발송된다.
- **어떻게**: `PaymentCommandService#createNotification`이 `Payment` 레코드를 DB에 저장하고(`P/payment/service/command/PaymentCommandService.java:52-53`), 수신자의 Redis 키 `WebSocket:Product:{email}`가 있을 때만 WebSocket `/queue/notifications`로 실시간 푸시한다(`:37-38, 303-313`). 연결이 없으면 저장만 되고 나중에 조회로 읽는다(`:320-322`). Kafka·이메일·푸시 발송은 없다.
- **실패 처리**: 알림 생성 오류는 `sendNotifications`/`notifyUsersAndUpdateSaleStatus`에서 잡혀 로그만 남고 결제·주문은 롤백되지 않는다(`NotificationCommandService.java:421-425, 457-461`). 다만 `PaymentCommandService`와 `NotificationCommandService`가 모두 클래스 단위 `@Transactional`(`PaymentCommandService.java:27`, `NotificationCommandService.java:37`)이라 같은 트랜잭션에 참여하므로, 알림 생성 중 예외가 던져졌다면 내부에서 잡아도 트랜잭션이 rollback-only로 표시될 수 있다(추정; 코드상 확인한 사실은 예외를 삼키는 try/catch까지). 단, 판매자 알림 전송 중 예외가 나면 이어지는 `SOLD` 처리는 `sendNotifications` 안의 try/catch 때문에 그대로 진행된다.
- 판매자 알림이 구매자 알림 뒤라서, 구매자 알림 생성이 예외를 던지면(내부 catch로 삼켜짐) 판매자 알림도 건너뛴다(`:436-461` 한 try 블록).
- `notification-topic` 등 Kafka 기반 알림은 이 경로에서 쓰이지 않는다.

## 5. 최종 주문 상태 · 창고 보관 선택 시 차이

**최종 주문 상태**: `PENDING_PAYMENT`. 이 경로에서는 `Faq#updateStatus`가 한 번도 호출되지 않는다(`FaqCommandService.java:219-319` 전체에 호출 없음, 생성 시 `:244`에서 지정). `PAYMENT_COMPLETED`, `PREPARING` 등으로의 전환은 별도 엔드포인트 `processPaymentAndShipment`(`FaqCommandService.java:111-202`, 일반 주문용 `POST /orders/{orderId}/process-payment-shipment`)에만 있다. 결제 엔티티가 `PAID`여도 주문은 `PENDING_PAYMENT`이고, `Faq.payment` 필드에도 `assignPayment`를 호출하지 않아(`createInstantOrder`에는 없음, 비교: `:140`) 메모리상 연결이 안 되어 있다(DB에는 `Notification.order`로 연결됨, `Notification.java:47-50`). 구매 입찰은 `MATCHED`, 판매 입찰은 `MATCHED`, 판매 건은 `SOLD`로 끝난다. 즉 "판매 건 SOLD / 주문 PENDING_PAYMENT"라는 불일치 상태다. 호출자 주석(`FaqCommandService.java` Javadoc류)이나 메시지가 말하는 "처리 완료"와 달리 주문 상태는 완료되지 않는다.

**"창고 보관" 선택(`warehouseStorage=true`)의 효과**: 사실상 없다. 요청의 `isWarehouseStorage`는 컨트롤러(`FaqBidCommandController.java:104`)에서 서비스로 전달되지만(`FaqBidCommandService.java:135-137`), `createInstantOrder` 본문에서 한 번도 읽히지 않는다(`FaqCommandService.java:219-319`, 매개변수 선언 `:221`만 있음).
- 구매자의 창고 보관용 `Notice`는 생성되지 않는다(`warehouseStorageCommandService.createOrderStorage`는 `processPaymentAndShipment`에서만 호출, `:170`). 주문 상태 `IN_WAREHOUSE`/`COMPLETED` 전환도 없다(`:163-172`는 다른 메서드).
- 창고 관련 분기는 구매자의 선택이 아니라 **판매자 쪽 `Style#isWarehouseStorage`** 값으로 결정된다(`FaqCommandService.java:291-292`). 판매 건이 창고 보관이면 기존 창고 `Notice`의 상태를 `ASSOCIATED_WITH_ORDER`로 바꾼다(`:293`; 허용 전환 검증 `NoticeCommandService.java:232-260`). 해당 판매에 창고 `Notice`가 없으면 `NoticeNotFoundException`(`P/notice/service/query/NoticeQueryService.java:30-33`) → `FaqNoticeProcessingFailedException`(`FaqCommandService.java:295-300`)이 되어 전체가 롤백된다.
- 따라서 구매자가 `warehouseStorage=false`로 보내도 판매 건이 창고 보관이면 창고 상태가 바뀌고, `true`로 보내도 판매 건이 일반 배송이면 아무 일도 일어나지 않는다. 배송 정보(`FaqAddress`)는 어느 쪽이든 항상 생성된다(`:264-271`).
- 구매 입찰·판매 입찰·알림·SOLD 처리는 창고 선택과 무관하게 동일하다.
