# 즉시 구매 처리 흐름

> 이 코드베이스는 클래스 이름이 도메인 의미와 어긋나 있다. 코드상 이름 → 실제 의미:
> `Faq`=주문(Order, 테이블 `orders`), `FaqBid`=구매 입찰(OrderBid), `Style`=판매(Sale), `StyleBid`=판매 입찰(SaleBid),
> `Notification`=결제(Payment, 테이블 `payment`), `Payment`(payment 패키지)=사용자 알림(알림 엔티티), `Product`=사용자(User), `Notice`=창고 보관(WarehouseStorage), `FaqAddress`=주문 배송지.
> 근거: `src/main/java/com/fream/back/domain/faq/entity/Faq.java:26`, `.../notification/entity/Notification.java:13`, `.../faq/entity/FaqBid.java:149`, `.../style/entity/Style.java:83`, `.../style/entity/StyleBid.java:14`

## 1. 진입 API, 처리 단계, 동기/비동기, 응답 ID

1. 진입점: `POST /order-bids/instant` — `FaqBidCommandController.createInstantOrderBid`
   (`src/main/java/com/fream/back/domain/faq/controller/command/FaqBidCommandController.java:28-29`(RequestMapping), `:89-90`). 요청 본문은 `InstantFaqRequestDto`(saleBidId, addressId, warehouseStorage, paymentRequest) (`.../faq/dto/InstantFaqRequestDto.java`).
2. 컨트롤러: 이메일 추출(`FaqBidCommandController.java:92`) → `paymentRequest.userEmail=email`, `orderId=null`로 덮어씀(`:98`, `:119-123`) → `FaqBidCommandService.createInstantOrderBid` 호출(`:101-107`).
3. `FaqBidCommandService.createInstantOrderBid`(`.../faq/service/command/FaqBidCommandService.java:118-147`, `@Transactional` `:118`):
   입력 검증(`:124`, `:150-161`) → 구매자 조회(`:126`) → 판매 입찰 조회·검증(`:129`, `:172-185`) → `FaqCommandService.createInstantOrder` 호출(`:133-139`) → 주문 입찰(FaqBid) 생성·저장(`:142`, `:189-207`).
4. `FaqCommandService.createInstantOrder`(`.../faq/service/command/FaqCommandService.java:219-319`) 내부 단계:
   배송지 조회(`:238`) → 주문 저장(`:241-247`) → `paymentRequest.setOrderId`(`:250`) → 주문 항목 생성(`:255-256`) → 주문 배송지 생성(`:264-271`) → 판매 입찰 매칭 + flush(`:279-283`) → 판매자 창고 보관 상태 갱신(`:291-293`) → 결제 처리(`:305`).
5. 결제 처리 `NotificationCommandService.processPayment`(`.../notification/service/command/NotificationCommandService.java:57-107`) 후 알림 + 판매 SOLD 처리 `notifyUsersAndUpdateSaleStatus`(`:83`, `:383-426`).
6. 동기 처리다. 컨트롤러 스레드에서 위 전 과정이 하나의 `@Transactional` 안에서 끝난 뒤 응답한다. Kafka 프로듀서/컨슈머, `@Async` 모두 이 경로에 없다(`FaqEventProducer`는 `FaqCommandController`/`FaqEventConsumer`에서만 주입, grep 결과). 외부 PortOne 호출도 동기 REST(`PortOneApiClient.java:266`).
7. 응답으로 돌려주는 ID: **주문(Order) ID가 아니라 주문 입찰(FaqBid, `order_bid` 테이블) ID**다. 컨트롤러가 `createInstantOrderBid(...).getId()`로 서비스가 반환한 `FaqBid`의 id를 꺼내 `orderId` 변수에 담는다(`FaqBidCommandController.java:101-107`). 서비스 반환값은 `FaqBid`다(`FaqBidCommandService.java:119`, `:142-144`). 변수명(`orderId`)과 메시지 "즉시 구매가 성공적으로 처리되었습니다"(`:109`)는 오해 소지가 있다.

## 2. 새로 생기는 엔티티와 상태 변화 순서

새로 생성되는 엔티티(모두 한 트랜잭션):

| 순서 | 엔티티 | 근거 |
|---|---|---|
| 1 | 주문 `Faq` | `FaqCommandService.java:241-247` |
| 2 | 주문 항목 `FaqItem` (수량 1, 가격=판매 입찰가) | `:255` → `.../faq/service/command/FaqItemCommandService.java:34-52` |
| 3 | 주문 배송지 `FaqAddress` (`AddressStatus.PENDING`) | `FaqCommandService.java:264` → `.../address/service/command/FaqAddressCommandService.java:56-70` |
| 4 | 결제 `Notification`(Card/Account/General) | `NotificationCommandService.java:187/250/302` |
| 5 | 사용자 알림 `Payment` 2건(구매자·판매자) | `.../payment/service/command/PaymentCommandService.java:44-57` |
| 6 | 주문 입찰 `FaqBid` | `FaqBidCommandService.java:189-207` |

상태 전이 순서와 각 단계 직후 값:

1. 주문 생성 직후: `Faq.status = PENDING_PAYMENT`, totalAmount=판매 입찰가 (`FaqCommandService.java:241-245`).
2. 판매 입찰 매칭: `StyleBid.assignOrder(order)` → `StyleBid.status = MATCHED`, `order` 연결(`FaqCommandService.java:279`, `.../style/entity/StyleBid.java:58-61`); 이어서 `updateStatus(MATCHED)` 한 번 더(`FaqCommandService.java:280`), 즉시 `flush`(`:283`).
   - 판매 입찰이 이미 MATCHED/CANCELLED인지 검사하지 않는다(`FaqBidCommandService.java:172-185`는 존재·sale 연결만 확인).
3. 창고 보관 판매였다면(`Style.isWarehouseStorage`가 true) `Notice.status = ASSOCIATED_WITH_ORDER`(`FaqCommandService.java:291-293`, `.../notice/service/command/NoticeCommandService.java:117-133`).
4. 결제 엔티티 생성: 상태는 결제 수단별로 다름(3번 항목). 기본값은 `NotificationStatus.PENDING`(`Notification.java:43-44`).
5. 판매 `Style.status = SOLD` (`NotificationCommandService.java:404`; 이전 상태 검증 없음 `Style.java:142-144`). 판매 입찰을 `findByOrderId`로 다시 찾아 그 `sale`을 갱신한다(`:391-404`) — 이 시점에 `order.getOrderBid()`는 아직 null(주문 입찰은 이후 생성)이라 이 분기가 사용된다(`:388-389`).
6. 주문 입찰 `FaqBid` 저장: `status = MATCHED`(`FaqBidCommandService.java:196`, `FaqBid.assignOrder`에서도 MATCHED `FaqBid.java:208`), `isInstantPurchase = true`(`FaqBidCommandService.java:205`, `FaqBid.java:230-232`), `sale` 연결(`:197`).
7. 주문(`Faq.status`)은 이 흐름에서 **한 번도 바뀌지 않는다** → 5번 참조.

## 3. 결제 수단별 결과, 성공 여부, 카드 실패 시

공통: `validatePaymentRequest`가 주문 ID 일치(`:131`), 이메일 일치(`:136`), `paidAmount > 0`(`:142`)만 검사한다. 결제 금액과 판매 입찰가의 일치는 검사하지 않는다.
수단은 DTO 클래스로 분기(`NotificationCommandService.java:67-80`, `.../notification/dto/NotificationRequestDto.java:74-86`).

| 수단 | 처리 | 결제 상태 |
|---|---|---|
| 카드 `CARD` | 저장된 카드 정보 조회(`:166`) → PortOne 호출(`:179`) → `response.status == "success"`일 때만 `PAID`+`isSuccess=true`(`:203-206`) | 성공 시 `PAID`, 그 외(코드 0이지만 status≠success)는 **`PENDING` 그대로 저장**(`Notification.java:44`) |
| 계좌이체 `ACCOUNT` | 은행명 검증(`:244`, `:470-488`) 후 외부 호출 없이 저장, 명시적으로 `PENDING`(`:260`) | `PENDING` (입금 확인 로직 없음) |
| 일반 `GENERAL` | `impUid` 비어 있지 않은지만 확인(`:297`), PortOne 검증 없이 `PAID`+성공 처리(`:313-314`) | `PAID` |

- 즉시 구매가 "끝까지 성공"하는가: 결제 단계에서 예외가 안 나면 HTTP 200으로 끝나고, 결제가 `PENDING`(계좌이체, 또는 status≠success 카드)이어도 구매는 완료로 취급된다. 판매 입찰 MATCHED, 판매 SOLD, 알림 전송이 결제 상태와 무관하게 실행된다(`:83`, `:383-426`에 결제 상태 검사 없음). 다만 주문 상태는 PENDING_PAYMENT에 머문다(5번).
- 카드 결제 실패(대행사가 HTTP≠200 또는 `code≠0`으로 응답): `PortOneApiClient.processCardPayment`가 `NotificationProcessingException`을 던진다(`PortOneApiClient.java:270-275`) → `createCardPayment`가 그대로 전파(`NotificationCommandService.java:218-219`) → `processPayment`가 로그 후 재던짐(`:89-94`) → `FaqCommandService`가 `FaqNotificationProcessingFailedException`으로 감싸 던짐(`FaqCommandService.java:304-309`) → `FaqException`으로 그대로 전파(`:312-315`) → `FaqBidCommandService`도 재던짐(`:146`, `:211-218`). `GlobalException`은 `RuntimeException`(`global/exception/GlobalException.java:10`)이고 `@Transactional` 경계가 `FaqBidCommandService.createInstantOrderBid`이므로 **전체 롤백**: 주문·주문 항목·배송지·결제·판매 입찰 MATCHED·창고 상태·주문 입찰 모두 취소되고 판매는 SOLD가 되지 않으며 알림도 저장되지 않는다. 클라이언트는 `GlobalExceptionHandler`가 변환한 오류 응답을 받는다. PortOne 통신 오류(`RestClientException`)는 `NotificationApiException`으로 변환되며(`PortOneApiClient.java:288-290`) 같은 롤백 경로를 탄다. `@Retryable`(3회)이 붙어 있으나(`PortOneApiClient.java:224-229`) 프로젝트에서 `@EnableRetry`를 찾지 못해 실제 재시도 여부는 확인되지 않았다.
- 카드 정보가 없거나(`:166-173`) 계좌의 은행이 미지원이어도(`:243-248`) 같은 롤백 경로.

## 4. 알림 수신자, 시점, 전달 방식

1. 수신자: 구매자(`order.getUser()`)에게 "결제가 완료되었습니다. 주문 ID: …", 판매자(`sale.getSeller()`)에게 "구매자가 결제를 완료하였습니다. 판매 ID: …" — 각각 `PaymentCategory.SHOPPING`, `PaymentType.BID`(`NotificationCommandService.java:434-456`). 두 명뿐이다.
2. 시점: 결제 엔티티 저장 직후, 같은 요청·같은 트랜잭션 안에서 판매자 알림까지(`:83` → `:403`/`:416`) — 주문 입찰 저장(`FaqBidCommandService.java:142`)보다 앞선다. 판매 상태 SOLD 변경은 알림 전송 직후(`:404`).
3. 방식: `PaymentCommandService.createNotification`이 DB에 `Payment`(알림) 행을 저장하고(`PaymentCommandService.java:52-53`), Redis에 `WebSocket:Product:<email>` 키가 있으면(접속 중) STOMP `convertAndSendToUser(email, "/queue/notifications", dto)`로 즉시 푸시한다(`:303-318`, `:37-38`). 키가 없으면 저장만 되고 푸시는 없다(`:320-322`). Kafka/이메일/푸시 알림은 이 경로에 없다.
4. 실패 허용: 알림 전송 예외는 삼켜서 경고만 남긴다(`NotificationCommandService.java:457-461`), 알림/판매 SOLD 처리 전체도 try-catch로 삼킨다(`:421-425`). 따라서 이 단계가 실패해도 결제와 주문은 롤백되지 않으며 판매 SOLD가 안 될 수 있다(예: `findByOrderId`가 `IllegalArgumentException`, `StyleBidQueryService.java:26-29`).

## 5. 최종 주문 상태, 창고 보관 선택 시 차이

1. 주문 최종 상태는 **`PENDING_PAYMENT`** 다. `createInstantOrder`는 주문을 `PENDING_PAYMENT`로 저장(`FaqCommandService.java:244`)한 뒤 `Faq.updateStatus`를 한 번도 호출하지 않고 반환한다(`:219-319` 전체). `PAYMENT_COMPLETED`/`PREPARING`/`IN_WAREHOUSE`/`COMPLETED`로 바꾸는 코드는 별도 메서드 `processPaymentAndShipment`(`:111-202`)에만 있고 즉시 구매 경로에서는 호출되지 않는다. 결제 성공(PAID)이어도 주문 상태는 그대로이며, 결제 상태·판매 상태(SOLD)·주문 입찰(MATCHED)과 어긋난다.
2. 구매자의 "창고 보관"(`warehouseStorage`) 선택은 사실상 무시된다: 컨트롤러는 로그에만 사용하고(`FaqBidCommandController.java:94-95`), `createInstantOrder`에 `isWarehouseStorage` 인자로 전달되지만(`:101-107`, `FaqCommandService.java:220-221`) 메서드 본문에서 한 번도 읽지 않는다. 대신 `sale.isWarehouseStorage()`(판매자가 올린 판매의 보관 여부)로 분기해 `Notice` 상태를 `ASSOCIATED_WITH_ORDER`로 갱신할 뿐이다(`:291-293`).
   - 따라서 구매자가 true를 보내도 `IN_WAREHOUSE` 전이, 창고 보관(`Notice`) 신규 생성(`createOrderStorage`, `:170`)은 일어나지 않고 주문 상태도 동일하게 `PENDING_PAYMENT`다.
   - 창고 보관 전용 단계(`PAYMENT_COMPLETED → PREPARING → IN_WAREHOUSE → COMPLETED`, `FaqCommandService.java:163-172`)는 `processPaymentAndShipment`에만 있다.
   - 참고: 판매자 쪽 판매가 창고 보관 판매이고 해당 `Notice`가 없으면 `NoticeNotFoundException`(`.../notice/service/query/...findBySale`, `NoticeQueryService.java:30-33`)이 전체 롤백을 유발한다(`FaqCommandService.java:295-301`).
