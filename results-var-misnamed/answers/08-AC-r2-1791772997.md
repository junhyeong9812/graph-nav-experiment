# 구매자 배송: 운송장 등록 ~ 배송 완료 처리 분석

경로 약어: `B` = `src/main/java/com/fream/back`.
핵심 클래스는 `FaqAddress`(구매자 배송, 테이블 order_shipment), `Faq`(주문), `FaqBid`(구매 입찰), `StyleBid`(판매 입찰), `Style`(판매)이다.

## 요약

- 운송장 등록 API는 일반 구매 입찰 주문(a)·즉시 구매 주문(b) 모두에서 실패한다. 결제·배송 처리를 마친 주문은 `PREPARING`(a) 또는 `PENDING_PAYMENT`(b)인데, 둘 다 `IN_TRANSIT`으로 전환하는 것이 허용되지 않는다.
- 응답은 HTTP 404, 코드 `S001`이다. 모든 변경이 롤백되어 아무것도 저장되지 않고 알림도 가지 않는다.
- 배송 완료 감지는 6시간마다 도는 Spring Batch Job이 한다. 실제로 실행되는 처리 코드는 `AddressItemProcessor`이다.
- 배송 완료 처리 자체는 (a)에서는 실패하고, (b)에서만 끝까지 진행된다.
- (b)는 구매자 알림 2건, 판매자 알림 0건이며 입찰은 `MATCHED`로 남는다.

## 1. 운송장 등록 요청

### 1-1. 어느 API로 들어오나

1. `PATCH /shipments/order/{shipmentId}/status`, 본문은 `{courier, trackingNumber}`이다.
   - 컨트롤러 `B/domain/address/controller/command/FaqAddressCommandController.java:20`(base path), `:33-49`(핸들러)
   - `FaqAddressRequestDto`: `B/domain/address/dto/FaqAddressRequestDto.java:11-12`
2. 핸들러는 `FaqAddressCommandService#updateTrackingInfo(shipmentId, courier, trackingNumber)`를 호출한다. `B/domain/address/service/command/FaqAddressCommandService.java:239`
3. 컨트롤러에는 역할 검사가 없다. SecurityConfig는 whitelist 외 `anyRequest().authenticated()`만 건다. `B/global/config/security/SecurityConfig.java:52`
4. 같은 컨트롤러의 `POST /{id}/check-status`, `/check-status-string`은 운송장 등록과 즉시 조회를 한 번에 하는 별도 경로이다(§4 참고). `FaqAddressCommandController.java:58, 103`

### 1-2. 엔티티 상태 변경 순서와 알림 (코드가 의도한 순서)

`FaqAddressCommandService#updateTrackingInfo`는 `@Transactional`이다(`:238-239`).

1. courier/trackingNumber가 비었으면 `TRACKING_INFO_REQUIRED`를 던진다. `:243-246`
2. `FaqAddress`를 `findById`로 조회한다. 없으면 `SHIPMENT_NOT_FOUND`. `:249-253`
3. **FaqAddress**: `shipment.updateTrackingInfo(courier, trackingNumber)`가 courier, trackingNumber를 세팅하고 상태를 곧바로 `IN_TRANSIT`으로 둔다. 전이 검사는 없다. `:256`, `B/domain/address/entity/FaqAddress.java:41-45`
4. **Faq(주문)**: `order.updateStatus(FaqStatus.IN_TRANSIT)`. `:259-260`
5. 구매자에게 알림 1건 "상품이 출발하였습니다. 주문 ID: …"(`PaymentCategory.SHOPPING`/`PaymentType.BID`)을 `PaymentCommandService#createNotification`으로 생성한다. `:265-271`
6. `updateSaleStatusToSold(order.getId())`가 `StyleBid`와 `FaqBid`로 `Style`을 조회한다. `Style`이 SOLD로 전이 가능하면 SOLD로 바꾸고 판매자에게 "상품이 성공적으로 판매 완료되었습니다" 알림을 보낸다. 창고 보관 상품이면 창고 상태도 바꾼다. `:276`, `:111-183`
7. 창고 보관 상품이면 `updateWarehouseStatusToSold`를 다시 호출한다. `:279-286`
8. `updateOrderAndSaleBidStatusToCompleted`가 `FaqBid`와 `StyleBid`가 `MATCHED`일 때 `COMPLETED`로 바꾼다. `:289`, `:412-440`

의도한 순서는 FaqAddress IN_TRANSIT → Faq IN_TRANSIT → 구매자 알림 → Style SOLD(+판매자 알림) → FaqBid/StyleBid COMPLETED이다.
메서드 이름·주석과 달리, 운송장 등록 시점에 이미 판매 SOLD와 입찰 COMPLETED까지 처리하려는 코드이다.

### 1-3. 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문에서 끝까지 성공하나

**실패한다.**

**실패 지점: 4단계 `order.updateStatus(IN_TRANSIT)`**

- 결제·배송 처리를 마친 실배송(창고 보관 아님) 일반 주문의 상태는 `PREPARING`이다.
  - 동기 경로 `FaqCommandService#processPaymentAndShipment`: `B/domain/faq/service/command/FaqCommandService.java:165-177`의 else 분기에서 `PAYMENT_COMPLETED` → `PREPARING`
  - Kafka 경로 `FaqEventConsumer`: `B/domain/faq/service/kafka/FaqEventConsumer.java:195`, `:216-217`
- `FaqStatus` 전이표에서 `PREPARING`은 `{IN_WAREHOUSE, SHIPMENT_STARTED}`만 허용하고, `IN_TRANSIT`은 `SHIPMENT_STARTED`에서만 갈 수 있다. `B/domain/faq/entity/FaqStatus.java:26,28`
- 코드베이스 어디에도 `FaqStatus.SHIPMENT_STARTED`로 바꾸는 호출이 없다(`FaqStatus.` 사용처 전수 확인). 따라서 일반 주문은 `IN_TRANSIT`에 도달할 수 없다.
- `Faq#updateStatus`는 전이가 불가하면 `InvalidFaqStatusException`을 던진다. `B/domain/faq/entity/Faq.java:113-119`

**예외 변환과 응답**

- `updateTrackingInfo`의 catch가 `AddressException`이 아닌 예외를 `AddressException(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: 상태 전환이 허용되지 않습니다: PREPARING -> IN_TRANSIT", cause)`로 바꿔 던진다. `FaqAddressCommandService.java:295-301`
  - 이름은 SHIPMENT_NOT_FOUND이지만 실제 원인은 주문 상태 전이 거부이다.
- `GlobalExceptionHandler`가 이를 받아 `ErrorResponse(code="S001", message="배송 정보를 찾을 수 없습니다.", status=404, path)`를 **HTTP 404**로 응답한다. 예외 메시지는 응답 본문에 담기지 않는다.
  - `B/global/exception/GlobalExceptionHandler.java:49-63`
  - `B/domain/address/exception/AddressErrorCode.java:12`

**저장되는 것**

- 아무것도 저장되지 않는다.
  - `AddressException`은 `RuntimeException`(`GlobalException`)이라 `@Transactional` 메서드가 롤백된다. `B/global/exception/GlobalException.java:10`
  - 3단계에서 바뀐 FaqAddress의 courier, trackingNumber, `IN_TRANSIT`은 flush되기 전에 롤백된다. 배송은 `PENDING`에 운송장 없음으로 남는다.
  - 구매자 알림(5단계)은 4단계 뒤에 있어 실행되지 않는다. 판매자 알림, SOLD, 입찰 COMPLETED도 모두 실행되지 않는다.
- 즉시 구매 주문(b)도 `PENDING_PAYMENT`이고 이 상태에서는 `IN_TRANSIT`으로 갈 수 없어, 같은 지점에서 같은 응답으로 실패한다. (`FaqStatus.java:24`, §4 참고)

## 2. 배송 완료 감지

### 2-1. 누가, 언제, 어떻게

- **누가**: `AddressBatchScheduler#scheduleShipmentStatusJob`이 Spring Batch Job `updateShipmentStatusesJob`을 실행한다.
  - `B/global/config/AddressBatchScheduler.java:19-21`, `:34-40`
  - 스케줄링은 `@EnableScheduling`(예: `B/domain/event/scheduler/EventStatusScheduler.java:22`)과 `@EnableBatchProcessing`(`B/global/config/BatchInfraConfig.java:15`)에 의존한다.
- **주기**: `@Scheduled(cron = "0 0 */6 * * *")`이다. 매일 00·06·12·18시 정각, 즉 6시간마다이다. `AddressBatchScheduler.java:34`
  - 실행마다 `timestamp` 파라미터를 달리 주므로 매번 새 JobInstance가 된다. `:37-39`
  - 예외는 `printStackTrace()`로만 처리된다. `:41-43`
- **어떻게**: Job은 Step 하나이다. `UpdateAddressStatusesJobConfig#updateShipmentStatusesJob`/`#updateShipmentStatusesStep`, `B/domain/address/config/UpdateAddressStatusesJobConfig.java:55-82`

### 2-2. 조회 대상

`shipmentItemReader`(JpaPagingItemReader, pageSize 50)가 다음 JPQL로 읽는다. `UpdateAddressStatusesJobConfig.java:89-97`

```
SELECT s FROM FaqAddress s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL
```

즉 운송장이 있고 상태가 `IN_TRANSIT` 또는 `OUT_FOR_DELIVERY`인 `FaqAddress`가 대상이다.

### 2-3. 실제로 실행되는 처리 코드

같은 일을 하는 코드가 세 곳에 있다.

| 후보 | 위치 | 실제 사용 여부 |
|---|---|---|
| `AddressItemProcessor` | `B/domain/address/config/AddressItemProcessor.java:57` | **실제 실행됨**. Step에 `.processor(new AddressItemProcessor(playwrightBrowserManager(), notificationService, orderService))`로 연결된다. `UpdateAddressStatusesJobConfig.java:67-73` |
| `shipmentItemProcessor` @Bean 람다 | `UpdateAddressStatusesJobConfig.java:106-` | Step이 참조하지 않는다. 빈으로만 존재하고 실행되지 않는다. |
| `FaqAddressCommandService#updateShipmentStatuses` | `FaqAddressCommandService.java:308-391` | 저장소 전체에서 호출하는 곳이 없다. 실행되지 않는다. |

- 실제 실행되는 `AddressItemProcessor#process`(`AddressItemProcessor.java:57-131`)는 다음과 같이 동작한다.
  - 운송장이 없으면 `TRACKING_NUMBER_INVALID`를 던진다. `:63`
  - `PlaywrightBrowserManager`로 새 페이지를 열고 `https://trace.cjlogistics.com/next/tracking.html?wblNo=<운송장>`으로 이동한다(`:28`, `:72-83`).
  - `tbody#statusDetail tr`을 기다린 뒤 HTML을 Jsoup으로 파싱해 **마지막 행의 5번째 `td`**(`get(4)`) 텍스트를 상태 문자열로 쓴다. `:87`, `:181`
  - 브라우저는 `BrowserManageStepListener`가 스텝 전후로 열고 닫는다. `B/domain/address/config/BrowserManageStepListener.java:15-23`, `UpdateAddressStatusesJobConfig.java:70-72`
- `FaqAddressCommandService`의 `cjTrackingPlaywright` 호출은 `updateShipmentStatuses`(`:335`)와 수동 조회 `updateAndCheckShipmentStatus`(`:477`)에서만 쓰인다. 배치 경로에서는 쓰이지 않는다.

### 2-4. 택배사 상태 문자열 → 내부 상태

`AddressItemProcessor#mapToShipmentStatus`: `AddressItemProcessor.java:220-226`

| 문자열(정확히 일치) | 내부 `AddressStatus` |

| `"배송완료"` | `DELIVERED` |

- 현재 상태와 같으면 변경 없이 반환한다. `:101-104`
- 빈 테이블/빈 텍스트는 `TRACKING_HTML_PARSE_ERROR`를 던진다. `:172-176`, `:183-188`

## 3. 배송 완료 판정 이후 (`AddressItemProcessor.java:108-117`)

`newStatus == DELIVERED`일 때 (`DELIVERED`가 아닌 `OUT_FOR_DELIVERY`/`IN_TRANSIT` 분기는 `:119-127`에서 FaqAddress 상태만 바꾼다):

### 3-1. 엔티티 상태 변경 순서

1. **FaqAddress**: `updateStatus(DELIVERED)`. `:113`
   - `IN_TRANSIT`/`OUT_FOR_DELIVERY` → `DELIVERED`는 허용된다. `B/domain/address/entity/AddressStatus.java:16-27`
2. `orderService.completeOrder(orderId)`를 호출한다. `:116`, `FaqAddressCommandService.java:190-229`
   1. `FaqBidQueryService#findByOrderId`로 FaqBid를 조회한다. 없으면 `IllegalArgumentException`. `:196-197`
   2. **Faq(주문)**: `order.updateStatus(COMPLETED)`. `:204`
   3. `updateSaleStatusToSold(orderId)`. `:208`
      - StyleBid를 조회한다. `StyleBidQueryService#findByOrderId`는 없으면 null이 아니라 `IllegalArgumentException`을 던진다. `B/domain/style/service/query/StyleBidQueryService.java:26-28`
      - 따라서 `if (saleBid != null)`(`:117`)은 사실상 항상 참이다.
      - `sale.getStatus().canTransitionTo(SOLD)`가 참일 때만 **Style → SOLD**로 바꾸고 판매자 알림 1건을 만든다. `:119-141`
      - 이어서 FaqBid 쪽 `Style`도 같은 조건으로 처리하며 판매자 알림을 한 번 더 만들 수 있다. `:150-176`
      - `StyleStatus.canTransitionTo(SOLD)`는 `ON_AUCTION`/`SELLING`에서만 true이고 `SOLD`는 false이다. `B/domain/style/entity/StyleStatus.java:14-24`
   4. 구매자에게 알림 "[completeOrder] 주문이 완료 처리되었습니다. 주문 ID: …" 1건. `:211-217`
3. `notificationService.notifyShipmentCompleted(order)`로 구매자에게 알림 "[배송 완료] 상품이 배송 완료되었습니다. 주문 ID: …" 1건. `AddressItemProcessor.java:117`, `B/domain/payment/service/command/PaymentCommandService.java:219-233`
   - 내부 예외는 로그만 남기고 삼킨다.
4. Step의 `JpaItemWriter`가 변경된 FaqAddress를 저장한다. `UpdateAddressStatusesJobConfig.java:74`, `:241-246`

### 3-2. 알림 건수 (모든 단계가 성공하는 경우)

- **구매자**: 2건
  - "[completeOrder] 주문이 완료 처리되었습니다"
  - "[배송 완료] 상품이 배송 완료되었습니다"
- **판매자**: `updateSaleStatusToSold`에서 `Style`이 SOLD로 전이 가능할 때만 1건씩(StyleBid 경로와 FaqBid 경로, 최대 2건). 그렇지 않으면 0건이다.

### 3-3. 입찰 상태

- **FaqBid/StyleBid는 COMPLETED로 바뀌지 않는다.**
  - 입찰을 `COMPLETED`로 바꾸는 `updateOrderAndSaleBidStatusToCompleted`는 운송장 등록 `updateTrackingInfo`에서만 호출된다(`FaqAddressCommandService.java:289`). 그 호출은 §1에서 보듯 도달하지 못한다.
  - `completeOrder`와 배치 경로에는 입찰 상태 변경 코드가 없다.
  - 따라서 배송 완료 후에도 입찰은 `MATCHED` 그대로이다. 호출 지점은 `updateTrackingInfo`뿐이다.

## 4. 주문 종류별 차이

배치는 `IN_TRANSIT`/`OUT_FOR_DELIVERY` + 운송장 있는 배송만 읽는다. 두 주문 모두 §1의 PATCH로는 그 상태에 이르지 못한다.
`POST /shipments/order/{id}/check-status`(`updateAndCheckShipmentStatus`)는 `FaqAddress#updateTrackingInfo`로 배송을 곧바로 `IN_TRANSIT`으로 만든다(`FaqAddressCommandService.java:473`, `FaqAddress.java:41-45`). 이 경로를 거친 배송이 있다고 가정하고 §3 처리를 두 주문에 적용하면 다음과 같다. DELIVERED 판정 시 `completeOrder`는 `:489`에서 같은 방식으로 호출된다.

### (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문 — 끝까지 진행되지 않는다

- 주문 상태는 `PREPARING`이다. FaqBid는 존재한다. (`FaqBidCommandService.java:189-205` 같은 즉시 구매용 생성이 아니라 일반 입찰로 만들어진 FaqBid이다. `FaqBidCommandService.java:100`)
- `completeOrder`의 `order.updateStatus(COMPLETED)`(`FaqAddressCommandService.java:204`)가 `PREPARING → COMPLETED`라서 `InvalidFaqStatusException`을 던진다. `FaqStatus.java:26`, `Faq.java:113-119`
  - `completeOrder`는 이를 `AddressException(ORDER_NOT_FOUND_FOR_SHIPMENT)`로 감싸 던진다. `FaqAddressCommandService.java:221-228`
- 결과(배치): 그 건의 Faq, FaqAddress, 알림이 모두 롤백되거나 반영되지 않는다. 구매자 알림 0건이고 Style/입찰도 변경되지 않는다. 배송은 `IN_TRANSIT`에 남아 6시간마다 재조회·재실패한다.
- 결과(`check-status`): 컨트롤러가 `AddressException`을 상태 코드만 있는 응답으로 돌려준다(404). `FaqAddressCommandController.java:80-86`

### (b) 즉시 구매로 만들어진 주문 — 끝까지 진행된다 (단, 판매자 쪽 변경 없음)

- 주문은 `FaqCommandService#createInstantOrder`에서 `PENDING_PAYMENT`로 만들어지고(`FaqCommandService.java:244`) 이후 상태 변경이 없다(`PAYMENT_COMPLETED`/`PREPARING` 전환 코드가 이 경로에 없다. 아래 목록 참고). 같은 서비스 안에서 StyleBid가 주문에 붙고 `MATCHED`가 된다(`:279-280`). 이어 `FaqBid`도 `MATCHED`+즉시 구매로 생성된다(`FaqBidCommandService.java:189-205`).
- 결제 처리 시 `NotificationCommandService#notifyUsersAndUpdateSaleStatus`가 이미 `Style`을 `SOLD`로 바꾼다. 이때는 FaqBid가 아직 없어 StyleBid 경로로 처리되며, `Style.updateStatus`에는 전이 검사가 없다.
  - `B/domain/notification/service/command/NotificationCommandService.java:389-404`
  - `B/domain/style/entity/Style.java:73-75`
  - 호출은 `FaqCommandService.java:305`
- 배송 완료 시:
  1. `PENDING_PAYMENT → COMPLETED`는 허용된다. `FaqStatus.java:24`, `Faq#updateStatus`
  2. FaqBid와 StyleBid 둘 다 존재하므로 `findByOrderId`가 성공한다.
  3. `Style`이 이미 `SOLD`라 `canTransitionTo(SOLD)`가 false이고, 판매 상태 변경과 판매자 알림이 모두 건너뛰어진다. `FaqAddressCommandService.java:119`, `:156`
  4. 구매자 알림 2건이 만들어진다(§3-2).
  5. FaqAddress `DELIVERED`, Faq `COMPLETED`가 저장된다.
- 결과: 구매자 2건, 판매자 0건, FaqBid/StyleBid는 `MATCHED`로 남는다(§3-3).

(a)는 배송 완료 판정 처리가 예외로 중단되어 어떤 상태·알림도 남지 않고, (b)는 주문 `COMPLETED`+배송 `DELIVERED`+구매자 알림 2건으로 마무리되지만 판매자 알림과 입찰 `COMPLETED`는 일어나지 않는다.

## 5. 실패 처리 (주기 처리 중 한 건 실패 시)

- Step은 `faultTolerant().skip(Exception.class).skipLimit(50)`이고 청크 크기는 50이다. `UpdateAddressStatusesJobConfig.java:51-52`, `:63-82`
  - 처리 중(process) 예외는 청크 단위 롤백 후, 청크 안의 항목을 하나씩 다시 처리하는 방식으로 실패한 항목만 건너뛴다.
  - 실패한 건: 변경은 롤백된다. 해당 FaqAddress는 이전 상태(`IN_TRANSIT`/`OUT_FOR_DELIVERY`)로 남아 다음 6시간 주기에 다시 조회된다. `shipmentSkipListener#onSkipInProcess`가 오류 로그를 남긴다. `:252-267`
  - 나머지 건: 정상 처리·저장된다. 건너뛴 항목만 제외하고 나머지는 유지된다.
- `AddressItemProcessor`의 모든 예외는 `AddressException`으로 변환되어 전파된다(`EXTERNAL_TRACKING_SERVICE_ERROR` 등). `AddressItemProcessor.java:133-146`
  - 같은 건이 반복해서 실패하는 경우(예: (a))에는 매 주기 skip이 누적된다.
- 한 실행에서 skip이 50건을 넘으면 Step이 실패하고 남은 항목은 처리되지 않는다(skipLimit=50).
- 읽기/쓰기 오류도 skip 대상이며 각각 `onSkipInRead`, `onSkipInWrite`로 로깅된다. `UpdateAddressStatusesJobConfig.java:269-285`
- 스케줄러는 Job 실행 예외를 `printStackTrace()`로만 남기고 재시도하지 않는다. 다음 주기(6시간 뒤)에 다시 실행된다. `AddressBatchScheduler.java:41-43`
- (참고) 실행되지 않는 `FaqAddressCommandService#updateShipmentStatuses`는 건별 try/catch로 실패한 건만 `errorCount++` 하고 나머지를 계속하는 구조이지만 호출되지 않는다. `FaqAddressCommandService.java:322-388`
