# 구매자 배송: 운송장 등록 ~ 배송 완료 처리

> 이름 매핑(코드 내 리네이밍): `Faq`=주문(order, 테이블 `orders`), `FaqBid`=구매(주문) 입찰, `StyleBid`=판매 입찰, `Style`=판매(sale),
> `FaqAddress`=구매자 배송(`order_shipment`), `Payment`(payment 도메인)=사용자 알림 엔티티, `PaymentCommandService`=알림 서비스.
> (`/addresses` 의 `Shipment*` 클래스는 사용자 주소록이라 이 흐름과 무관하다.)

경로 접두사: `B = src/main/java/com/fream/back`

## 1. 운송장 등록 요청

### 1-1. 어느 API로 들어오나
- `PATCH /shipments/order/{shipmentId}/status`, 바디 `{courier, trackingNumber}` — `B/domain/address/controller/command/FaqAddressCommandController.java:20,33-45`
  → `FaqAddressCommandService.updateTrackingInfo(shipmentId, courier, trackingNumber)` (`B/domain/address/service/command/FaqAddressCommandService.java:238-239`)
- 컨트롤러는 try/catch 가 없어 예외는 `GlobalExceptionHandler` 로 간다 (`B/global/exception/GlobalExceptionHandler.java:49-63`).
- (참고) 별도로 `POST /shipments/order/{id}/check-status`, `/check-status-string` 이 있다 — 운송장을 넣고 즉시 CJ 조회까지 한다 (`FaqAddressCommandController.java:58-94,103-138`, 서비스 `FaqAddressCommandService.java:451-516`). 4번에서 다시 언급.

### 1-2. 코드가 의도한 상태 변경 순서와 알림 (`updateTrackingInfo`, `FaqAddressCommandService.java:238-303`)
1. courier/trackingNumber 공백 검사 → `TRACKING_INFO_REQUIRED` (243-246)
2. `FaqAddress` 조회 (249-253), `shipment.updateTrackingInfo()` → courier·trackingNumber 저장 + 배송 상태를 곧바로 `IN_TRANSIT` 으로 세팅 (256; `B/domain/address/entity/FaqAddress.java:41-45`, 전이 검증 없음)
3. 주문 `Faq.updateStatus(IN_TRANSIT)` (259-262)
4. 구매자에게 알림 "상품이 출발하였습니다. 주문 ID: …" 1건 (265-271)
5. `updateSaleStatusToSold(orderId)` (276): 판매(`Style`)를 `SOLD` 로 바꾸고(111-183, 특히 116-123) 판매자에게 "상품이 성공적으로 판매 완료되었습니다" 알림 (132-138). 창고 보관 상품이면 창고 상태도 SOLD (126-129)
6. 창고 보관 판매면 창고 상태 갱신 (279-286)
7. `updateOrderAndSaleBidStatusToCompleted` (289, 412-440): 구매 입찰(`FaqBid`) MATCHED→COMPLETED, 판매 입찰(`StyleBid`) MATCHED→COMPLETED. 이 메서드는 내부에서 예외를 삼킨다(436-439).

즉 의도는 "배송 시작 시점에 판매 SOLD·입찰 COMPLETED 까지 처리"이지만, 아래처럼 3단계에서 막힌다.

### 1-3. 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문 — 끝까지 성공하나? **아니오, 3단계에서 실패**
- 결제·배송 처리(`FaqCommandService.processPaymentAndShipment`) 후 실배송(비창고) 주문의 상태는 `PAYMENT_COMPLETED → PREPARING` 에서 멈춘다 (`B/domain/faq/service/command/FaqCommandService.java:174-177`; 이벤트 경로도 동일 `B/domain/faq/service/kafka/FaqEventConsumer.java:195,216-218`). 배송 엔티티는 `PENDING` 으로 생성 (`FaqAddressCommandService.java:67`).
- `FaqStatus` 전이표에서 `PREPARING` 의 허용 다음 상태는 `IN_WAREHOUSE`, `SHIPMENT_STARTED` 뿐, `IN_TRANSIT` 은 `SHIPMENT_STARTED` 에서만 가능 (`B/domain/faq/entity/FaqStatus.java:26,28`). 코드 어디에서도 `SHIPMENT_STARTED` 로 바꾸지 않는다(`FaqStatus.` 사용처 전수 확인: FaqCommandService / FaqEventConsumer / FaqAddressCommandService / DataInitializer 뿐).
- 따라서 `FaqAddressCommandService.java:260` `order.updateStatus(IN_TRANSIT)` 에서 `InvalidFaqStatusException("상태 전환이 허용되지 않습니다: PREPARING -> IN_TRANSIT")` 발생 (`B/domain/faq/entity/Faq.java:113-120`).
- 이 예외는 `AddressException` 이 아니므로 `catch (Exception e)` (295-302)에 걸려 `AddressException(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")` 로 포장되어 던져진다.
- **무엇이 저장되나: 아무것도 저장되지 않는다.** 메서드가 `@Transactional` (238) 이고 런타임 예외가 밖으로 나가므로 롤백된다. 2단계의 courier/trackingNumber/`IN_TRANSIT` 세팅은 메모리에서만 일어났고 DB에 반영되지 않아 배송은 `PENDING`·운송장 null 그대로, 주문은 `PREPARING` 그대로다. 4~7단계(구매자 알림, 판매 SOLD, 판매자 알림, 입찰 COMPLETED)에는 도달하지 못하므로 알림도 0건.
- **응답**: HTTP 404, `ErrorResponse` 코드 `S001`, 메시지 "배송 정보를 찾을 수 없습니다." (`B/domain/address/exception/AddressErrorCode.java:12`, `GlobalExceptionHandler.java:55-62` — 응답 바디는 에러코드의 기본 메시지를 쓰고 상세 메시지는 쓰지 않음). 즉 실제 원인은 "배송 없음"이 아니라 주문 상태 전이 불가인데 SHIPMENT_NOT_FOUND 로 나간다.
- (참고) 이 주문에는 판매 입찰이 연결되지 않은 경우가 많은데, 그 경우 `StyleBidQueryService.findByOrderId` 가 null 이 아니라 `IllegalArgumentException` 을 던진다 (`B/domain/style/service/query/StyleBidQueryService.java:26-28`). 그래서 `updateSaleStatusToSold` 의 `if (saleBid != null)` 분기(117)는 의미 없고, 3단계를 통과했더라도 116행에서 터진다.

## 2. 배송 완료 감지

### 2-1. 누가·언제·어떻게
- 사람이 아니라 스케줄러가 감지한다: `AddressBatchScheduler.scheduleShipmentStatusJob()` — `@Scheduled(cron = "0 0 */6 * * *")` = **6시간마다 정각(0·6·12·18시)** (`B/global/config/AddressBatchScheduler.java:34-40`). `updateShipmentStatusesJob` 스프링 배치 잡을 실행한다.
- Job → Step `updateShipmentStatusesStep`: chunk 50 (`B/domain/address/config/UpdateAddressStatusesJobConfig.java:51,67`), reader → processor → `JpaItemWriter`.
- **대상**: `SELECT s FROM FaqAddress s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL` (같은 파일 95). PENDING 배송은 조회되지 않는다.
- **실제 실행되는 처리 코드**: `Step` 이 `new AddressItemProcessor(...)` 를 processor 로 직접 등록한다 (`UpdateAddressStatusesJobConfig.java:69-73`, 클래스 `B/domain/address/config/AddressItemProcessor.java:22,56-157`). 아래는 **실행되지 않는 유사 코드**다.
  - 같은 Config 의 `@Bean shipmentItemProcessor()` (104-177) 와 `parseCjLogisticsStatus` (Jsoup, 186-220): 어디에서도 step 에 연결되지 않음.
  - `FaqAddressCommandService.updateShipmentStatuses()` (308-391): 호출하는 곳이 없음(스케줄러도 이 메서드가 아니라 Job 을 호출). 이 메서드는 order 를 COMPLETED 로 바꾸고 알림 1건만 보내는 다른 로직이라 실제 동작과 다르다.
  - `check-status` API 경로 (`updateAndCheckShipmentStatus`)는 수동 호출용.
- 조회 방식: Playwright 로 `https://trace.cjlogistics.com/next/tracking.html?wblNo={운송장}` 을 열어 `tbody#statusDetail tr` 의 **마지막 행의 5번째 `td`(index 4)** 텍스트를 읽는다 (`AddressItemProcessor.java:28-29,81-94,167-191`). 같은 상태 표시 문자열을 읽는 `CjTrackingPlaywright` 는 `check-status` 쪽에서 사용 (`B/global/utils/CjTrackingPlaywright.java:79-161,185`).
  - 택배사 구분은 하지 않는다. `courier` 값과 무관하게 항상 CJ 대한통운 URL 로 조회한다.

### 2-2. 택배사 상태 문자열 → 내부 상태 (`AddressItemProcessor.java:220-226`)
| CJ 문자열 | 내부 `AddressStatus` |
|---|---|
| `"배송완료"` | `DELIVERED` |
| `"배송출발"` | `OUT_FOR_DELIVERY` |
| 그 외 모두(집화, 간선 상차 등) | `IN_TRANSIT` |

- 현재 상태와 같으면 변경 없이 리턴 (101-105). 완전 일치 비교라 공백이 다르면 `IN_TRANSIT` 로 처리됨.

## 3. 배송 완료 판정 이후 (실제 실행: `AddressItemProcessor.java:108-117`)

`newStatus == DELIVERED` 일 때 순서:
1. `FaqAddress.updateStatus(DELIVERED)` — `IN_TRANSIT/OUT_FOR_DELIVERY → DELIVERED` 허용 (113; `B/domain/address/entity/AddressStatus.java` 의 IN_TRANSIT·OUT_FOR_DELIVERY 전이 정의, 엔티티 `FaqAddress.java:47-55`)
2. `orderService.completeOrder(orderId)` (116; `FaqAddressCommandService.java:190-229`)
   1. `FaqBid` 를 `findByOrderId` 로 조회, 없으면 `IllegalArgumentException` (196-197)
   2. 주문 `Faq.updateStatus(COMPLETED)` (204)
   3. `updateSaleStatusToSold(orderId)` (208): 판매 입찰로 찾은 `Style` 이 `SOLD` 로 전이 가능하면(`SELLING`/`ON_AUCTION` 일 때만, `B/domain/style/entity/StyleStatus.java:20-22`) `SOLD`, 판매자 알림 1건 (116-138). 이어서 `FaqBid.getSale()` 로 같은 판매를 한 번 더 확인하지만 이미 SOLD 라 전이 불가 → 알림 중복 없음 (150-176)
   4. 구매자 알림 "[completeOrder] 주문이 완료 처리되었습니다. 주문 ID: …" (211-217)
3. `notificationService.notifyShipmentCompleted(order)` (117): 구매자 알림 "[배송 완료] 상품이 배송 완료되었습니다. 주문 ID: …" (`B/domain/payment/service/command/PaymentCommandService.java:219-229`; 실패해도 예외를 삼킴, 230-233)
4. 마지막에 `JpaItemWriter` 가 배송 엔티티를 저장 (`UpdateAddressStatusesJobConfig.java:241-246`)

- **알림 건수**: 구매자 **2건**(`[completeOrder]`, `[배송 완료]`), 판매자 **1건**(판매가 SOLD 로 전이됐을 때; 판매가 SELLING/ON_AUCTION 이 아니면 0건). 
- **입찰 상태**: 이 경로에서는 구매 입찰·판매 입찰 상태를 바꾸지 않는다. `COMPLETED` 로 바꾸는 `updateOrderAndSaleBidStatusToCompleted` 는 운송장 등록(1-2 의 7단계)에서만 호출된다 (`FaqAddressCommandService.java:289`). 즉 배치 경로에서는 두 입찰 모두 `MATCHED` 로 남는다 (`FaqBid.assignOrder` 와 `StyleBid.assignOrder` 가 MATCHED 로 세팅: `B/domain/faq/entity/FaqBid.java:74-76`, `B/domain/style/entity/StyleBid.java:58-61`).
- 이미 같은 상태면 건너뛰므로 DELIVERED 이후 재조회돼도 중복 처리는 없다. 또 DELIVERED 는 reader 대상(IN_TRANSIT/OUT_FOR_DELIVERY)에서 빠진다.

## 4. 주문 종류별 차이

| | (a) 결제·배송 처리 후 실배송 일반 구매 입찰 주문 | (b) 즉시 구매 주문 |
|---|---|---|
| 주문 상태 | `PREPARING` (`FaqCommandService.java:175-176`) | `PENDING_PAYMENT` 그대로 — `createInstantOrder` 는 상태를 바꾸지 않고(`FaqCommandService.java:241-311`), 결제 서비스도 주문 상태를 바꾸지 않는다 (`B/domain/notification/service/command/NotificationCommandService.java` 에 주문 `updateStatus` 없음) |
| 입찰 | `FaqBid` 있음(order 연결), 판매 입찰은 없을 수 있음 | `FaqBid`(`isInstantPurchase`, order·sale 연결, `FaqBidCommandService.java:189-206`) + `StyleBid.assignOrder(order)` (`FaqCommandService.java:279-280`) 모두 연결 |

### (a) 3의 처리가 끝까지 진행되지 않는다
- 먼저 1-3 에서 운송장 등록이 롤백되므로 배송이 `PENDING` 에 남아 배치 reader 대상(IN_TRANSIT/OUT_FOR_DELIVERY, `UpdateAddressStatusesJobConfig.java:95`)이 되지 않는다. 즉 DELIVERED 판정에 아예 도달하지 않는다.
- 가정으로 배송이 IN_TRANSIT 이고 CJ 가 "배송완료"를 반환해도, `completeOrder` 의 `Faq.updateStatus(COMPLETED)` (204)에서 `PREPARING → COMPLETED` 가 허용되지 않아(`FaqStatus.java:26`) `InvalidFaqStatusException` → `AddressException(ORDER_NOT_FOUND_FOR_SHIPMENT)` (221-227) 가 되어 notifyShipmentCompleted 도 호출되지 않는다. 결과: 주문 `PREPARING`, 판매 SOLD 아님, 알림 0건, 입찰 MATCHED.

### (b) 3의 처리는 끝까지 진행된다 (단, 배송이 IN_TRANSIT 이 될 수 있는 경우)
- 주문 `PENDING_PAYMENT → COMPLETED` 는 전이표에서 허용 (`FaqStatus.java:24`) 이고, `FaqBid`·`StyleBid` 가 모두 order 로 조회되므로 `completeOrder` 가 성공한다 → 3번 결과 그대로: 배송 DELIVERED, 주문 COMPLETED, 판매 SOLD(SELLING/ON_AUCTION 인 경우), 구매자 알림 2건 + 판매자 알림 1건, 입찰은 MATCHED 유지.
- 단 (b) 도 `PATCH .../status` 운송장 등록은 `PENDING_PAYMENT → IN_TRANSIT` 불가로 (a)와 똑같이 1-3 처럼 실패한다 (`FaqStatus.java:24`). 배송이 IN_TRANSIT 이 되는 길은 `POST /shipments/order/{id}/check-status` 뿐이다: 이 API 는 운송장을 넣어 배송을 IN_TRANSIT 으로 만든 뒤 주문 상태 전이 없이 CJ 를 조회하고, DELIVERED 면 `completeOrder` 를 호출한다 (`FaqAddressCommandService.java:473-489`). 이 경로의 DELIVERED 에서는 `notifyShipmentCompleted` 를 호출하지 않아 구매자 알림은 1건(`[completeOrder]`)이다. 이 API 로 운송장이 들어간 배송은 이후 6시간 배치의 대상이 되어 위 3번 처리를 따른다.
- 따라서 차이를 요약하면: (a) 는 주문이 PREPARING 이라 COMPLETED 전이가 막혀 완료 처리 불가, (b) 는 PENDING_PAYMENT 라 COMPLETED 전이가 허용되어 끝까지 진행된다. 둘 다 정상 운영 흐름(PATCH 등록)으로는 DELIVERED 에 도달하지 못한다.

## 5. 실패 처리 (주기 처리 중 한 건 실패)
- Step 은 `faultTolerant().skip(Exception.class).skipLimit(50)` + SkipListener (`UpdateAddressStatusesJobConfig.java:75-78`, SKIP_LIMIT=50 at 52). 한 건에서 예외(운송장 없음, CJ 페이지 없음/파싱 실패/타임아웃 → `AddressException`, `completeOrder` 실패 등; `AddressItemProcessor.java:61-64,133-145`)가 나면 그 건만 skip 되어 로그만 남고(`shipmentSkipListener`, 같은 파일 252-286 부근), 해당 건은 DB 에 저장되지 않아 상태는 그대로(다음 6시간 뒤 주기에 다시 대상이 됨).
- 나머지 건은 계속 처리된다. 청크(50건) 단위 트랜잭션이므로 실패 시 해당 청크가 롤백된 뒤 아이템을 하나씩 다시 처리(scan)하며 실패 건만 제외하고 커밋한다. `completeOrder` 가 청크 트랜잭션에 참여하므로 실패 건의 주문/알림 변경은 함께 롤백된다.
- skip 한도(50) 를 넘으면 스텝이 실패하고 잡이 종료된다. 스케줄러 쪽은 `jobLauncher.run` 예외를 `printStackTrace` 만 하고 삼킨다 (`AddressBatchScheduler.java:41-43`).
- 한 가지 주의(추론): 리더가 읽은 엔티티는 재처리 때도 같은 객체라, 실패한 건 이전에 이미 처리된 항목의 메모리 상태(예: DELIVERED)는 유지된다. 재처리 시 "같은 상태" 분기(101-105)로 빠져 `completeOrder`/알림이 건너뛰어질 수 있으므로, 스킵이 발생한 청크에서는 배송은 DELIVERED 로 저장되었으나 주문/알림이 롤백된 상태가 생길 여지가 있다. 이 부분은 코드 정적 분석에 의한 추론이며 실행으로 확인하지 않았다.
- (참고) 사용되지 않는 `updateShipmentStatuses()` 는 건별 try/catch 로 실패를 세고 다음 건으로 넘어가는 방식이지만 실제로 호출되지 않는다 (`FaqAddressCommandService.java:308-391`).
