# 즉시 구매 처리 흐름 (POST /order-bids/instant)

경로 약어: `D` = `src/main/java/com/fream/back/domain`

## 1. 진입 API, 처리 단계, 동기/비동기, 응답 ID

- 진입점: `POST /order-bids/instant` → `FaqBidCommandController#createInstantOrderBid` (`D/faq/controller/command/FaqBidCommandController.java:22,89-110`). 클래스 base path 는 `/order-bids` (:22).
- 요청 DTO `InstantFaqRequestDto`: `saleBidId`, `addressId`, `warehouseStorage`, `paymentRequest` (`D/faq/dto/InstantFaqRequestDto.java:20-29`).
- 처리 단계:
  1. 컨트롤러가 이메일을 추출하고(:92) 결제 요청에 `userEmail=이메일`, `orderId=null` 을 덮어쓴다(`enrichPaymentRequest`, :119-123).
  2. `FaqBidCommandService#createInstantOrderBid` (`D/faq/service/command/FaqBidCommandService.java:118-149`, `@Transactional`)
     - 입력 검증(:123, :154-167)
     - 구매자 조회(:126)
     - 판매 입찰 조회 `StyleBidQueryService#findById` 및 `sale` 존재 검증(:129, :172-184). 입찰이 없으면 `IllegalArgumentException`(`D/style/service/query/StyleBidQueryService.java:21-24`)이 나고, 이는 `FaqBidCreationFailedException` 으로 감싸진다(:212-218).
     - `FaqCommandService#createInstantOrder` 호출(:133)
     - `FaqBid` 생성·저장(:142, :189-207)
  3. `FaqCommandService#createInstantOrder` (`D/faq/service/command/FaqCommandService.java:219-319`, `@Transactional`). 순서는 다음과 같다.
     - (a) 배송지 조회 `ShipmentQueryService#getAddress`(:238)
     - (b) `Faq` 주문 저장(:241-247)
     - (c) `paymentRequest.orderId = order.id` 설정(:250)
     - (d) `FaqItem` 생성(:255-256)
     - (e) `FaqAddress`(주문 배송정보) 생성(:264-271)
     - (f) 판매 입찰 매칭 + flush(:279-283)
     - (g) 판매자 창고 상태 갱신(:290-301)
     - (h) 결제 처리 `NotificationCommandService#processPayment`(:305)
- 동기/비동기: **전부 동기, 하나의 트랜잭션**이다. 즉시 구매 경로에서는 Kafka 이벤트를 쓰지 않는다. Kafka 를 쓰는 `FaqEventProducer`/`FaqEventConsumer` 는 별도 엔드포인트 `/orders/{orderId}/process-payment-shipment` 용이다. 즉시 구매 서비스 체인(`FaqBidCommandService`, `FaqCommandService#createInstantOrder`)에는 Kafka 호출이 없다. PortOne 호출도 `RestTemplate.exchange` 동기 호출이다(`D/notification/portone/PortOneApiClient.java:266`).
- 응답 ID: `createInstantOrderBid(...).getId()` 라서 **`FaqBid`(주문 입찰, 테이블 `order_bid`)의 ID**이다. 변수 이름은 `orderId` 이지만(`FaqBidCommandController.java:101-109`) 실제 `Faq` 주문 ID(`orders` 테이블)가 아니다. 메시지는 "즉시 구매가 성공적으로 처리되었습니다."(:109)이다.

## 2. 새로 생성되는 엔티티와 상태 전이 순서

생성 순서와 각 단계 직후의 상태는 다음과 같다.

| # | 단계 | 근거 | 직후 상태 |
|---|---|---|---|
| 1 | `Faq`(orders) 생성·저장 | `FaqCommandService.java:241-247` | `Faq.status = PENDING_PAYMENT`, `totalAmount = saleBid.bidPrice`. `discountAmount`/`usedPoints` 는 0(int 기본값) |
| 2 | `FaqItem` 생성(수량 1, 가격 = 입찰가) | `FaqItemCommandService.java:45-52`, `FaqCommandService.java:255` | — |
| 3 | `FaqAddress` 생성 | `D/address/service/command/FaqAddressCommandService.java:61-70`, `FaqCommandService.java:264-271` | `AddressStatus.PENDING` |
| 4 | 판매 입찰 `StyleBid` 매칭 | `FaqCommandService.java:279-280`, `D/style/entity/StyleBid.java:58-61` | `StyleBid.order = 주문`, `StyleBid.status = MATCHED`(`assignOrder` 와 `updateStatus` 모두 MATCHED) |
| 5 | (판매자가 창고 보관한 판매일 때만) `Notice` 창고 상태 갱신 | `FaqCommandService.java:291-294` | `WarehouseStatus.ASSOCIATED_WITH_ORDER` |
| 6 | 결제 엔티티 `Notification` 생성(카드/계좌/일반) | `NotificationCommandService.java:67-80` | 아래 3번 참조 |
| 7 | 결제 직후 알림·판매 상태 | `NotificationCommandService.java:83, 383-426` | `Style.status = SOLD`(알림 `Payment` 2건 생성) |
| 8 | `FaqBid`(order_bid) 생성·저장 | `FaqBidCommandService.java:192-206` | `status = MATCHED`, `isInstantPurchase = true`, `order`=주문, `sale`=판매 |

- 7번에서 판매 조회가 가능한 이유: 이 시점에 `order.getOrderBid()` 는 아직 null 이다. `FaqBid` 는 8번에서 만들어진다. 그래서 `notifyUsersAndUpdateSaleStatus` 가 else 분기인 `saleBidQueryService.findByOrderId`(`NotificationCommandService.java:388-407`)로 간다. 4번에서 `assignOrder` 와 flush 를 이미 했기 때문에 이 조회가 성공한다. 조회가 없으면 `IllegalArgumentException` 이지만(`StyleBidQueryService.java:26-29`) 바깥 `try/catch(Exception)` 이 삼킨다(`NotificationCommandService.java:421-425`).
- `Style` 의 상태 전이는 `StyleStatus.canTransitionTo` 로 검사하지 않는다. `Style#updateStatus` 는 값을 그대로 대입한다(`D/style/entity/Style.java:73-75`).
- 결제 엔티티 `assignOrder`: `Notification#assignOrder` 는 `order` 를 설정하고 `sale=null` 로 만든다(`D/notification/entity/Notification.java:47-50`).
- 판매 입찰 상태 검증이 없다: `getSaleBidAndValidate` 는 존재와 `sale != null` 만 확인한다(`FaqBidCommandService.java:172-184`). 이미 `MATCHED` 이거나 이미 `SOLD` 인 입찰도 막지 않는다.
- 결제 금액 검증이 없다: `paidAmount`(클라이언트 입력)가 입찰가와 같은지 검사하지 않는다. `validatePaymentRequest` 는 `orderId`, 이메일, `paidAmount > 0` 만 본다(`NotificationCommandService.java:117-146`).

## 3. 결제 수단별 결과, 성공 여부, 카드 결제 실패 시

결제 수단 분기는 `switch (getResolvedPaymentType())` 이다(`NotificationCommandService.java:67-80`).

| 수단 | 처리 | 결제 엔티티 상태 | 근거 |
|---|---|---|---|
| CARD | `PortOneApiClient.processCardPayment` 로 PG 동기 호출. 응답 `status` 가 `"success"` 일 때만 `PAID` + `isSuccess=true` | `PAID` 또는(그 외) 기본값 `PENDING` | `NotificationCommandService.java:157-217` (특히 :179, :203-206), `Notification.java:43-44` |
| ACCOUNT | PG 호출 없음. 은행명 enum 검증 후 `PENDING` 저장. 입금 확인은 하지 않는다 | `PENDING` | `NotificationCommandService.java:236-262` (:260) |
| GENERAL | `impUid` 비어있지 않은지만 확인. PG 검증 없이 클라이언트 값 그대로 `PAID` + `isSuccess=true` | `PAID` | `NotificationCommandService.java:290-316` (:297-300, :313-314) |

- 즉시 구매가 끝까지 성공하는지:
  - 세 수단 모두 `processPayment` 가 예외 없이 끝나면 `Faq`/`FaqBid` 가 저장되고 HTTP 200 으로 응답한다.
  - 계좌이체는 결제가 `PENDING` 인 채로도 판매가 `SOLD` 가 되고 알림이 나간다. 입금 완료 여부와 무관하게 "성공"으로 처리된다.
  - 어느 수단에서도 주문 상태가 `PAYMENT_COMPLETED` 로 올라가지 않는다(5번 참조).
- 카드 결제 실패 시 (두 가지 경로가 있다):
  1. **PG 응답 HTTP 가 200 이 아니거나 `code != 0` 인 경우**
     - `NotificationProcessingException` 이 발생한다(`PortOneApiClient.java:270-275`).
     - `NotificationException` 하위라서 `catch (NotificationException e) { throw e; }` 로 그대로 전파된다(:286-287, `NotificationCommandService.java:218-219`).
     - `@Retryable` 은 `NotificationApiException` 만 재시도하므로(:224-228) 재시도 대상이 아니다. 단, `NotificationApiException` 은 통신 오류(`RestClientException`)일 때만 던져지며(:288-290), 이 경우에만 최대 3회 재시도된다.
     - `FaqCommandService#createInstantOrder` 에서 `FaqNotificationProcessingFailedException` 으로 감싸져(:305-309) 전파된다. 트랜잭션이 롤백되어 `Faq`, `FaqItem`, `FaqAddress`, 판매 입찰 매칭, 창고 상태 변경이 모두 취소된다. 컨트롤러는 에러 응답을 반환한다.
  2. **PG 응답이 `code == 0` 이지만 `response.status` 가 `"success"` 가 아닌 경우**(`PortOneApiClient` 는 `code` 만 검사하고 `status` 는 검사하지 않는다. :270)
     - 예외가 나지 않는다. `CardNotification` 이 `PENDING`, `isSuccess=false` 로 저장된다(`NotificationCommandService.java:203-208`).
     - 이어서 `notifyUsersAndUpdateSaleStatus` 가 결제 성공 여부를 확인하지 않고 알림 2건과 `Style=SOLD` 를 수행한다(:83, :403-404).
     - 즉시 구매는 성공 응답(HTTP 200, 입찰 ID)으로 끝나는데, 주문은 `PENDING_PAYMENT`, 결제는 `PENDING`(미결제) 이고 판매는 `SOLD` 이며 입찰은 `MATCHED` 인 불일치 상태가 남는다.

## 4. 알림 대상, 시점, 전달 방식

- 시점: 결제 엔티티 저장 직후, `processPayment` 안에서 동기로 발생한다(`NotificationCommandService.java:83` → :434-462). 같은 트랜잭션 안이다.
- 대상과 내용(`sendNotifications`, `NotificationCommandService.java:434-462`):
  - 구매자(`order.getUser()`): `PaymentCategory.SHOPPING`, `PaymentType.BID`, "결제가 완료되었습니다. 주문 ID: {orderId}" (:438-443)
  - 판매자(`sale.getSeller()`): `SHOPPING`, `BID`, "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}" (:447-455)
  - 문구는 "결제가 완료되었습니다" 이지만 카드 `status != success`(PENDING) 또는 계좌이체(PENDING)여도 그대로 발송된다.
- 전달 방식(`D/payment/service/command/PaymentCommandService.java:44-59`, :303-322):
  - DB 에 `Payment`(알림, `isRead=false`)로 저장(:52-53)
  - 구매자/판매자의 Redis 키 `WebSocket:Product:{email}` 가 있으면(WebSocket 연결 중) STOMP `/queue/notifications` 로 `convertAndSendToUser` 실시간 푸시(:307-313). 연결이 없으면 저장만 된다(:320-322).
  - Kafka `notification-topic` 은 즉시 구매 경로에서 사용되지 않는다. 이 토픽은 `FaqEventConsumer` 의 비동기 경로에서만 발행된다(`D/faq/service/kafka/FaqEventConsumer.java`).
- 알림 실패는 삼켜진다: `sendNotifications` 가 예외를 `log.warn` 으로만 처리한다(:457-461). 알림 실패가 즉시 구매를 실패시키지 않는다.

## 5. 처리 종료 시 주문 최종 상태와 창고 보관 선택 시 차이

- 주문(`Faq`) 최종 상태: **`PENDING_PAYMENT`**. 즉시 구매 경로(`createInstantOrder`)는 주문을 `PENDING_PAYMENT` 로 만든 뒤(`FaqCommandService.java:244`) `updateStatus` 를 한 번도 호출하지 않는다. 결제가 `PAID` 인 카드·일반 결제여도 마찬가지다. 따라서 응답은 "성공"이지만 주문 상태는 `PAYMENT_COMPLETED`/`PREPARING` 으로 진행되지 않는다. `PAYMENT_COMPLETED` → `PREPARING` → (`IN_WAREHOUSE` → `COMPLETED`) 전이는 별도 엔드포인트의 `processPaymentAndShipment` 에만 있다(`FaqCommandService.java:163-177`, Kafka 경로는 `FaqEventConsumer.java:192-217`). 즉시 구매 코드에는 그 전이가 없다.
- 함께 남는 상태값: `FaqBid=MATCHED`(`FaqBidCommandService.java:196`), `StyleBid=MATCHED`(`FaqCommandService.java:280`), `Style=SOLD`(`NotificationCommandService.java:404`), `FaqAddress=PENDING`, 결제는 수단별로 `PAID`/`PENDING`.
- 구매자가 "창고 보관(`warehouseStorage=true`)"을 선택한 경우:
  - **구매자의 `isWarehouseStorage` 값은 실제로 사용되지 않는다.** 컨트롤러가 값을 넘기고(`FaqBidCommandController.java:105`) 서비스가 `createInstantOrder` 시그니처로 받지만(`FaqBidCommandService.java:137`, `FaqCommandService.java:221`), 메서드 본문에서 읽는 곳이 없다. 본문의 `isWarehouseStorage` 호출은 `sale.isWarehouseStorage()`(판매자가 올린 판매의 보관 여부)뿐이다(:292).
  - 구매자 창고 보관의 효과가 만들어졌어야 할 `createOrderStorage`(`Notice` 생성), `IN_WAREHOUSE`/`COMPLETED` 전이는 즉시 구매 경로에서 호출되지 않는다. `createOrderStorage` 는 `processPaymentAndShipment`(:170)와 Kafka 소비자 경로에서만 호출된다.
  - 따라서 `true` 든 `false` 든 즉시 구매 결과(주문 `PENDING_PAYMENT`, 배송정보 생성, 알림, `Style=SOLD`)는 동일하다. 달라지는 것은 판매자 쪽 판매가 창고 보관(`sale.isWarehouseStorage()==true`)이었을 때뿐이다. 이 경우 그 판매의 `Notice` 상태가 `ASSOCIATED_WITH_ORDER` 로 바뀐다(:291-294).
    - `Notice` 를 찾지 못하면 `NoticeNotFoundException` 이 `FaqNoticeProcessingFailedException` 으로 감싸져 전체가 롤백된다(`NoticeQueryService.java:30-33`, `FaqCommandService.java:295-300`).
    - `SOLD`/`REMOVED_FROM_STORAGE` 에서는 상태 전환이 막혀 마찬가지로 실패한다(`NoticeCommandService.java:255-257`).
