# 즉시 구매 처리 흐름 분석

경로 표기: `D/` = `src/main/java/com/fream/back/domain/`

도메인 클래스 이름이 실제 의미와 다르다. 읽을 때 아래처럼 대응시켜야 한다.

| 코드 이름 | 실제 의미 |
|---|---|
| `Faq` (테이블 `orders`) | 주문 (`D/faq/entity/Faq.java:26`) |
| `FaqBid` (테이블 `order_bid`) | 구매 입찰 (`D/faq/entity/FaqBid.java:149`) |
| `StyleBid` | 판매 입찰 (`D/style/entity/StyleBid.java:19`) |
| `Style` | 판매 건 (`D/style/entity/Style.java`) |
| `Notification` / `CardNotification` / `AccountNotification` / `GeneralNotification` | 결제 (`D/notification/entity/Notification.java:18`) |
| `Payment` / `PaymentCommandService` (payment 도메인) | 사용자 알림 (`D/payment/service/command/PaymentCommandService.java:30`) |
| `Notice` | 창고 보관 (`D/notice/...`) |
| `FaqAddress` | 주문 배송 정보 |

## 1. 진입 API, 처리 단계, 동기/비동기, 응답 ID

### 진입 API
- `POST /order-bids/instant`. 클래스 매핑 `@RequestMapping("/order-bids")` 는 `D/faq/controller/command/FaqBidCommandController.java:22`, 메서드는 `FaqBidCommandController.java:89-90` 이다.
- 요청 DTO `InstantFaqRequestDto` 는 `saleBidId`, `addressId`, `warehouseStorage`, `paymentRequest` 를 받는다 (`D/faq/dto/InstantFaqRequestDto.java:20-29`).

### 처리 단계 (모두 한 요청 스레드 안에서 순차 실행)
1. **컨트롤러**
   - 로그인 이메일을 추출한다 (`FaqBidCommandController.java:92`).
   - 결제 요청 DTO에 `userEmail = 로그인 이메일`, `orderId = null` 을 덮어쓴다 (`FaqBidCommandController.java:98`, `119-123`).
   - `createInstantOrderBid(...)` 를 호출한다 (`FaqBidCommandController.java:101-107`).
2. **`FaqBidCommandService.createInstantOrderBid`** (`D/faq/service/command/FaqBidCommandService.java:118-149`, `@Transactional`)
   - 입력 null 검증 (`FaqBidCommandService.java:123`, `154-167`).
   - 구매자 조회 (`FaqBidCommandService.java:126`).
   - 판매 입찰 조회와 null 검증 (`FaqBidCommandService.java:129`, `172-184`). 판매 입찰이 이미 매칭됐는지, 즉 `status` 는 검증하지 않는다.
   - `FaqCommandService.createInstantOrder` 호출 (`FaqBidCommandService.java:133`).
   - 구매 입찰(`FaqBid`) 생성 (`FaqBidCommandService.java:142`, `189-207`).
3. **`FaqCommandService.createInstantOrder`** (`D/faq/service/command/FaqCommandService.java:219-319`)
   1. 배송지 조회: `addressQueryService.getAddress(email, addressId)` (`FaqCommandService.java:238`)
   2. 주문 생성·저장: `PENDING_PAYMENT`, `totalAmount = 판매입찰가` (`FaqCommandService.java:241-247`)
   3. 결제 DTO에 `orderId` 세팅 (`FaqCommandService.java:250`)
   4. 주문 항목 생성 (`FaqCommandService.java:254-260`)
   5. 배송 정보 생성 (`FaqCommandService.java:263-275`)
   6. 판매 입찰 매칭 후 flush (`FaqCommandService.java:277-287`)
   7. 판매자 창고 보관 상태 갱신 (`FaqCommandService.java:290-301`)
   8. 결제 처리 (`FaqCommandService.java:304-309`)
4. **`NotificationCommandService.processPayment`** (`D/notification/service/command/NotificationCommandService.java:57-107`)
   - 결제 유형별 분기 (`NotificationCommandService.java:67-80`).
   - 이어서 `notifyUsersAndUpdateSaleStatus` 로 알림과 판매 상태 갱신 (`NotificationCommandService.java:83`, `383-426`).
5. **구매 입찰 `FaqBid` 저장** 후 컨트롤러가 ID를 응답한다.

### 동기인가 비동기인가
- **전부 동기, 단일 트랜잭션이다.** `@Async`, `@EventListener`, Kafka 호출이 이 경로에 없다.
  - `FaqEventProducer`/`NotificationEventProducer` 는 `FaqCommandController`/`FaqEventConsumer`/`NotificationEventConsumer` 에서만 쓰인다. 이 경로의 서비스들은 사용하지 않는다.
  - 외부 호출은 PortOne REST 를 `RestTemplate.exchange` 로 블로킹 호출한다 (`D/notification/portone/PortOneApiClient.java:266`).
- 바깥 트랜잭션은 `FaqBidCommandService.createInstantOrderBid` 의 `@Transactional` (`FaqBidCommandService.java:118`). 안쪽 `@Transactional` 들은 여기에 합류한다.
- 중간에 `FaqException`/`NotificationException`(둘 다 `GlobalException` → `RuntimeException`, `src/main/java/com/fream/back/global/exception/GlobalException.java:10`)이 나면 전체가 롤백된다.

### 응답으로 돌려주는 ID
- **주문(`Faq`)의 ID가 아니라 구매 입찰(`FaqBid`, `order_bid` 테이블)의 ID 이다.**
  - 컨트롤러는 `createInstantOrderBid(...)` 가 돌려준 `FaqBid` 에서 `.getId()` 를 꺼낸다 (`FaqBidCommandController.java:101-107`).
  - 그 값을 `orderId` 라는 변수명으로 응답한다 (`FaqBidCommandController.java:109`).
  - 서비스가 반환하는 것은 `orderBidRepository.save(orderBid)` 결과인 `FaqBid` 이다 (`FaqBidCommandService.java:206`).
  - 변수명과 응답 메시지는 "주문 ID"처럼 보이지만 실제 값은 `order_bid.id` 이다.

### 단계 d의 "SOLD" 에 대한 주의
- 판매 상태 갱신은 `notifyUsersAndUpdateSaleStatus` 안에서 일어난다.
  - 구매 입찰이 아직 만들어지기 전(`order.getOrderBid() == null`)이므로 `saleBidQueryService.findByOrderId(order.getId())` 경로를 탄다 (`NotificationCommandService.java:388-391`).
  - 이 조회는 a 단계에서 `StyleBid.order` 를 세팅하고 flush 했기 때문에 성공한다.
  - 판매 입찰에서 `Style` 을 꺼내 알림을 보내고(`NotificationCommandService.java:397-403`) SOLD 로 바꾼다 (`NotificationCommandService.java:404`).
- 이 메서드 전체가 `try { ... } catch (Exception e) { log.error(...) }` 로 감싸져 있어 알림/SOLD 갱신이 실패해도 예외가 전파되지 않는다 (`NotificationCommandService.java:421-425`).

### 주문(`Faq`) 상태는 이 경로에서 바뀌지 않는다
- `createInstantOrder` 어디에도 `order.updateStatus(...)` 호출이 없다 (`FaqCommandService.java:219-319`).
- `FaqStatus` 전이 호출은 별도 메서드 `processPaymentAndShipment` 에만 있고 즉시 구매 경로에서는 호출되지 않는다 (`FaqCommandService.java:165-177`).
- 결제 객체를 주문에 연결하는 `order.assignPayment(...)` 도 호출되지 않는다. `processPayment` 반환값은 버려진다 (`FaqCommandService.java:305`).

## 3. 결제 수단별 결과

분기는 `getResolvedPaymentType()` 값으로 한다 (`NotificationCommandService.java:67-80`). 이 값은 DTO 하위 클래스 타입(`CardNotificationRequestDto` 등)에서 결정된다 (`D/notification/dto/NotificationRequestDto.java:74-87`).

공통 검증 (`NotificationCommandService.java:117-146`):
- `requestDto.orderId` 가 주문 ID와 같아야 한다 (`:131`). 서비스가 방금 만든 주문 ID를 넣으므로 항상 일치한다 (`FaqCommandService.java:250`).
- `userEmail` 이 구매자 이메일과 같아야 한다 (`:136`). 컨트롤러가 로그인 이메일을 넣었다 (`FaqBidCommandController.java:120`).
- `paidAmount > 0` 만 확인한다 (`:142`). **판매 입찰가와의 일치 여부는 검증하지 않는다.** 클라이언트가 보낸 금액이 그대로 결제 금액으로 쓰인다.

| 수단 | 처리 | 결제 상태 | `isSuccess` | 근거 |
|---|---|---|---|---|
| 카드 (`CARD`) | 저장된 카드 정보를 조회해 PortOne 에 즉시 결제 요청 | PortOne 응답 `status == "success"` 이면 `PAID`, 아니면 기본값 `PENDING` | 아래 참고 | `NotificationCommandService.java:157-225` |
| 계좌이체 (`ACCOUNT`) | 은행명만 검증하고 PG 호출 없이 레코드만 저장 | `PENDING` | 아래 참고 | `NotificationCommandService.java:236-279` |
| 일반 (`GENERAL`) | `impUid` 필수만 확인하고 PG 재검증 없이 저장 | `PAID` | `true` | `NotificationCommandService.java:290-333` |

### 카드
- 카드 정보 조회 (`:166`) 후 `portOneApiClient.processCardPayment` 호출 (`:179`).
- PortOne 응답에서 `card_name`, `imp_uid`, `receipt_url`, `pg_provider`, `pg_tid` 를 꺼내 저장한다 (`:187-198`).
- `response.get("status")` 가 `"success"` 일 때만 `PAID` 와 `updateSuccessStatus(true)` 를 호출한다 (`:203-206`).

### 계좌이체
- `validateBank` 는 `Bank` enum 에 있는 은행명인지만 본다 (`:244`, `470-488`).
- `AccountNotification` 은 생성자에서 `setPaidAmount` 를 호출한다 (`D/notification/entity/AccountNotification.java:28`). 이 때문에 `isSuccess` 가 `paidAmount > 0` 으로 `true` 가 된다 (`D/notification/entity/Notification.java:60-63`).
- 이후 `updateStatus(PENDING)` 은 사실상 기본값 재지정이다 (`NotificationCommandService.java:260`).
- 입금 확인 로직이 이 경로에 없으므로 **결제 상태는 `PENDING` 인 채로 즉시 구매 처리는 계속 진행된다.**

### 일반 결제
- `impUid` 가 비어 있지 않으면 되고, 서버가 PG 에 조회해 확인하지 않는다 (`:297-300`).
- `updateSuccessStatus(true)`, `updateStatus(PAID)` (`:313-314`).

### 즉시 구매가 끝까지 성공하는가
- **결제 수단과 상관없이 결제 단계에서 예외가 없으면 끝까지 진행해 `FaqBid` 까지 만들고 성공 응답을 준다.**
- 계좌이체(`PENDING`) 와 카드 `status != "success"` 인 경우도 마찬가지로 이후 단계(알림 발송, 판매 건 `SOLD` 갱신, 구매 입찰 생성)가 그대로 진행된다.
  - `notifyUsersAndUpdateSaleStatus` 는 결제 상태를 확인하지 않는다 (`NotificationCommandService.java:383-426`).
  - 입금 전인 계좌이체도 "결제가 완료되었습니다" 알림이 나가고 판매 건이 `SOLD` 가 된다.
- 응답 메시지는 항상 "즉시 구매가 성공적으로 처리되었습니다." 이다 (`FaqBidCommandController.java:109`).

### 결제 대행사가 카드 결제를 실패로 응답하면
실패 형태에 따라 두 갈래로 갈린다.

1. **PortOne 응답이 HTTP 200 이 아니거나 `code != 0` 인 경우**
   - `NotificationProcessingException("카드 결제 요청 실패: ...")` 을 던진다 (`PortOneApiClient.java:270-275`).
   - 이 예외는 `NotificationApiException` 이 아니므로 `@Retryable` 재시도 대상이 아니다 (`PortOneApiClient.java:224-228` 의 `value = NotificationApiException.class`).
   - `NotificationException` 계열이라 그대로 위로 전파된다 (`PortOneApiClient.java:286-287`, `NotificationCommandService.java:180-181`, `218-219`, `89-94`).
   - `FaqCommandService` 가 `FaqNotificationProcessingFailedException` 으로 감싸 던진다 (`FaqCommandService.java:305-309`).
   - `FaqBidCommandService` 가 `FaqException` 이므로 그대로 다시 던진다 (`FaqBidCommandService.java:268-269`, `335-338`).
   - **결과: 트랜잭션 전체 롤백.** 주문, 주문 항목, 배송 정보, 판매 입찰 매칭 상태, 알림 모두 취소되고 API 는 오류를 응답한다.
2. **PortOne 이 HTTP 200 + `code == 0` 으로 응답하지만 `response.status` 가 `"success"` 가 아닌 경우** (결제 자체는 실패 상태)
   - 예외가 나지 않는다.
   - `CardNotification` 이 `status = PENDING` 으로 저장된다 (`Notification.java:44`, `NotificationCommandService.java:203-208`).
   - 생성자의 `setPaidAmount` 때문에 `isSuccess = true` 가 되어 있다 (`D/notification/entity/CardNotification.java:38`, `Notification.java:60-63`).
   - `FAILED` 상태로 바꾸는 코드가 없다.
   - 이후 흐름은 정상 성공과 똑같이 진행되고 구매자/판매자에게 "결제 완료" 알림이 나간다. 판매 건은 `SOLD`, 판매 입찰은 `MATCHED`, 주문은 `PENDING_PAYMENT`, 응답은 성공이다.

PortOne 호출 중 통신 오류(`RestClientException`)는 `NotificationApiException` 으로 바뀌어 최대 3회, 1초 간격으로 재시도되고 (`PortOneApiClient.java:224-228`, `288-290`), 최종 실패하면 갈래 1처럼 롤백된다.

## 4. 누가 어떤 알림을 받나, 언제 어떻게 전달되나

### 수신자와 내용
`sendNotifications` (`NotificationCommandService.java:434-462`):

| 수신자 | 카테고리/타입 | 메시지 | 근거 |
|---|---|---|---|
| 구매자 (`order.getUser()`) | `SHOPPING` / `BID` | "결제가 완료되었습니다. 주문 ID: {주문ID}" | `NotificationCommandService.java:436-444` |
| 판매자 (`sale.getSeller()`) | `SHOPPING` / `BID` | "구매자가 결제를 완료하였습니다. 판매 ID: {판매ID}" | `NotificationCommandService.java:447-455` |

- 즉시 구매 성공 시에 이 두 건만 만들어진다. 환불 알림(`sendRefundNotification`, `:603-658`)은 환불 요청 시에만 쓰인다 (`:543-572`).
- 구매자 메시지에 들어가는 "주문 ID" 는 진짜 주문 ID 이다. 응답으로 돌려주는 값(구매 입찰 ID)과 다르다.

### 시점
- 결제 레코드를 저장한 직후, `processPayment` 안에서 호출된다 (`NotificationCommandService.java:83`).
- **구매 입찰(`FaqBid`) 생성보다 앞이고, 판매 건 `SOLD` 변경(`:404`)보다도 앞이다** (`sendNotifications` 호출 `:403` → `updateStatus(SOLD)` `:404`).
- 알림 생성은 같은 트랜잭션 안이라, 이후 단계가 예외를 던지면 DB 알림 레코드는 롤백된다. 이미 전송된 WebSocket 메시지는 회수되지 않는다.

### 전달 방식
- `PaymentCommandService.createNotification` (`PaymentCommandService.java:44-59`):
  1. 알림 레코드를 DB 에 저장한다 (`:52-53`).
  2. `sendRealTimeNotification` 으로 실시간 전송을 시도한다 (`:57`).
- `sendRealTimeNotification` (`PaymentCommandService.java:303-323` 범위, 메서드 본문의 Redis 키 확인 `:307`, 전송 `:309`, 연결 없음 `:320`):
  - Redis 키 `WebSocket:Product:{email}` 가 있으면(접속 중이면) STOMP `convertAndSendToUser(email, "/queue/notifications", dto)` 로 푸시한다 (`PaymentCommandService.java:37-38`).
  - 키가 없으면 푸시하지 않고 DB 에만 남는다.
- 따라서 **동기 호출이며, 접속 중인 사용자는 WebSocket 으로 즉시, 미접속 사용자는 DB 저장만** 이루어지고 나중에 조회로 확인한다. Kafka 를 통한 비동기 전달은 이 경로에 없다.
- 알림 발송 실패는 `warn` 로그만 남기고 삼킨다 (`NotificationCommandService.java:457-461`). 즉시 구매 자체는 실패하지 않는다.

## 5. 최종 상태, 창고 보관 선택 시 차이

### 처리 완료 시점 상태
| 대상 | 최종 값 | 근거 |
|---|---|---|
| 주문 `Faq.status` | **`PENDING_PAYMENT`** (결제 수단, 결제 성공 여부와 무관하게 변하지 않음) | 생성 `FaqCommandService.java:244`, 이후 갱신 없음 |
| 구매 입찰 `FaqBid.status` | `MATCHED`, `isInstantPurchase = true` | `FaqBidCommandService.java:196`, `205` |
| 판매 입찰 `StyleBid.status` | `MATCHED` | `FaqCommandService.java:279-280` |
| 판매 건 `Style.status` | `SOLD` | `NotificationCommandService.java:404` |
| 결제 | 카드 성공/일반: `PAID`, 계좌이체/카드 비성공: `PENDING` | 3번 참조 |
| 배송 정보 `FaqAddress.status` | `PENDING` | `FaqAddressCommandService.java:67` |

- 즉시 구매 완료 후에도 주문이 "결제 완료"(`PAYMENT_COMPLETED`)나 "준비 중"(`PREPARING`)이 되지 않고 `PENDING_PAYMENT` 에 머문다.
  - 결제를 `PAID` 로 처리한 카드/일반 결제도 마찬가지다.
  - 주문 상태를 `PAYMENT_COMPLETED` → `PREPARING` 으로 올리는 로직은 즉시 구매와 다른 `processPaymentAndShipment` 에만 있다 (`FaqCommandService.java:111-202`).
  - 이 경로의 호출자는 "구매자가 배송 정보를 따로 보내는 일반 주문 결제"이다.

### 구매자가 "창고 보관"(`warehouseStorage = true`)을 선택한 경우
**아무것도 달라지지 않는다. 이 값은 사용되지 않고 버려진다.**
- 컨트롤러는 요청의 `isWarehouseStorage()` 를 로그에만 쓰고 서비스에 넘긴다 (`FaqBidCommandController.java:94-95`, `101-105`).
- `FaqBidCommandService` 는 이를 `createInstantOrder` 로 전달만 한다 (`FaqBidCommandService.java:133-139`).
- `FaqCommandService.createInstantOrder` 는 파라미터 `isWarehouseStorage` 를 선언하지만 (`FaqCommandService.java:221`) 메서드 본문에서 한 번도 읽지 않는다. 같은 파일에서 `isWarehouseStorage` 가 나오는 곳은 `:163`(다른 메서드, `requestDto.isWarehouseStorage()`), `:221`(파라미터 선언), `:292`(`sale.isWarehouseStorage()`, 판매자 쪽) 뿐이다.
- 따라서 구매자 창고 보관용 `Notice` 를 만드는 `warehouseStorageCommandService.createOrderStorage(...)` 와 주문 상태 `IN_WAREHOUSE`, `COMPLETED` 전이는 즉시 구매 경로에서 실행되지 않는다. 그 코드는 `processPaymentAndShipment` 에만 있다 (`FaqCommandService.java:163-172`).
- 즉 구매자가 창고 보관을 선택해도 `Faq.warehouseStorage` 는 `null` 이고 주문은 `PENDING_PAYMENT` 이며 배송 정보(`FaqAddress`)는 그대로 생성된다.
- 창고 보관과 관련된 유일한 분기는 **판매자 쪽** 이다. 판매 건이 창고 보관 상품이면 판매자 쪽 보관 `Notice` 상태가 `ASSOCIATED_WITH_ORDER` 로 바뀐다 (`FaqCommandService.java:290-293`). 이 값은 구매자의 선택과 무관하다.

## 요약 (실제 동작 vs 이름/주석이 시사하는 의도)

- 응답 ID: 이름은 `orderId` / "주문 ID" 이지만 실제는 구매 입찰(`FaqBid`) ID.
- 처리: 이름과 주석은 "결제까지 한 번에"처럼 보이지만 PG 응답이 실패 상태여도(`status != "success"`) 예외 없이 계속 진행한다.
- 계좌이체: 입금 확인 없이 `PENDING` 상태로 저장하고도 "결제 완료" 알림 발송과 판매 건 `SOLD` 처리까지 진행한다.
- 주문 최종 상태: `PENDING_PAYMENT` 에서 바뀌지 않는다.
- 창고 보관 플래그: 입력은 받지만 어떤 로직에도 쓰이지 않는다.
- 알림: DB 저장은 항상, WebSocket 푸시는 접속 중인 경우에만. 판매 건 `SOLD` 보다 먼저 전송된다.
- 결제 금액: 판매 입찰가와 비교하지 않고 클라이언트 값(`paidAmount`)을 신뢰한다.
