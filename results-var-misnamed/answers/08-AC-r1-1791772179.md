# 구매자 배송: 운송장 등록 → 배송 완료

경로 약어: `ADDR` = `src/main/java/com/fream/back/domain/address`, `FAQ` = `src/main/java/com/fream/back/domain/faq`, `G` = `src/main/java/com/fream/back/global`, `STYLE` = `src/main/java/com/fream/back/domain/style`, `PAY` = `src/main/java/com/fream/back/domain/payment`.
(엔티티 이름 매핑: `Faq` = 주문(테이블 orders), `FaqAddress` = 구매자 배송(order_shipment), `FaqBid` = 주문(구매) 입찰, `StyleBid` = 판매 입찰, `Style` = 판매 상품, `Product` = 사용자, `Payment` = 알림.)

## 결론 요약

- 운송장 등록 API(`PATCH /shipments/order/{shipmentId}/status`)는 의도상 "배송 IN_TRANSIT → 주문 IN_TRANSIT → 구매자 알림 → 판매 SOLD/판매자 알림 → 입찰 COMPLETED" 순으로 짜여 있다.
- 실제로는 **결제·배송 처리를 마친 일반 구매 입찰 주문(PREPARING)에서 주문 상태 전이가 막혀 항상 실패**한다. 404 `S001`을 응답하고 전부 롤백된다.
- 즉시 구매 주문도 같은 이유로 이 API는 실패한다. `SHIPMENT_STARTED`는 코드 어디에서도 세팅되지 않는다.
- 배송 완료 감지는 `AddressBatchScheduler`가 6시간마다 띄우는 Spring Batch Job `updateShipmentStatusesJob`이며, 실제 처리 코드는 `AddressItemProcessor`다.
- 배송 완료 후처리(`completeOrder`)는 즉시 구매 주문만 끝까지 간다. 일반 구매 입찰 주문은 끝까지 가지 못한다.

## 1. 운송장 등록 요청

### 1-1. 진입 API

1. `PATCH /shipments/order/{shipmentId}/status`, 바디는 `FaqAddressRequestDto`(courier, trackingNumber). 컨트롤러 베이스 경로는 `ADDR/controller/command/FaqAddressCommandController.java:20`, 메서드는 `:33-49`이다.
2. 컨트롤러는 `FaqAddressCommandService#updateTrackingInfo(shipmentId, courier, trackingNumber)`를 그대로 호출한다 (`FaqAddressCommandController.java:41-45`). try/catch가 없어 예외는 `GlobalExceptionHandler`로 간다.
3. 역할(ADMIN) 검사는 코드에 없고, `anyRequest().authenticated()`뿐이다 (`G/config/security/SecurityConfig.java:51-52`). "운영 측"만 호출하도록 강제하는 코드는 이 경로에 없다.
4. 같은 컨트롤러의 `POST .../check-status`(`FaqAddressCommandController.java:~60-94`)와 `POST .../{shipmentId}/check-status-string`(`:103-138`)은 `updateAndCheckShipmentStatus`(`ADDR/service/command/FaqAddressCommandService.java:452`)를 호출한다. 이 경로는 운송장을 등록한 뒤 택배사를 즉시 조회하는 별도 API다.

### 1-2. 의도된 상태 변경 순서와 알림 (`FaqAddressCommandService#updateTrackingInfo`, `ADDR/service/command/FaqAddressCommandService.java:238-303`)

1. courier/trackingNumber가 비어 있으면 `TRACKING_INFO_REQUIRED`(400)를 던진다 (`:243-246`).
2. `FaqAddress`를 조회한다. 없으면 `SHIPMENT_NOT_FOUND` (`:249-253`).
3. `shipment.updateTrackingInfo(courier, trackingNumber)` (`:256`)가 택배사와 운송장을 저장하고 배송 상태를 곧바로 `IN_TRANSIT`으로 바꾼다 (`ADDR/entity/FaqAddress.java:41-45`). `PENDING`에서 `SHIPPED`를 거치지 않으며 전이 검증도 없다.
4. 주문 `order.updateStatus(FaqStatus.IN_TRANSIT)` (`:259-260`).
5. 구매자에게 알림 1건: "상품이 출발하였습니다. 주문 ID: …" (`:265-271`, `PaymentCommandService#createNotification` → `PAY/service/command/PaymentCommandService.java:44-67`). DB 저장과 WebSocket 푸시를 한다.
6. `updateSaleStatusToSold(orderId)` (`:276`)가 판매 `Style`을 `SOLD`로 바꾼다 (`:123`). 창고 보관이면 창고 상태를 갱신하고 (`:126-129`), 판매자에게 알림 1건 "상품이 성공적으로 판매 완료되었습니다…"을 보낸다 (`:132-138`). 이어서 `FaqBid` 쪽 sale도 같은 방식으로 처리하지만, 이미 SOLD면 `canTransitionTo`가 false라 알림이 중복되지 않는다 (`:150-176`, `StyleStatus.java:23`).
7. 창고 보관 상품이면 `updateWarehouseStatusToSold`를 한 번 더 호출한다 (`:279-286`).
8. `updateOrderAndSaleBidStatusToCompleted` (`:289`)가 `FaqBid`와 `StyleBid`가 MATCHED이면 COMPLETED로 바꾼다 (`:412-440`).
   - 이 메서드는 private + `@Transactional` self-invocation이고 예외를 삼킨다.
   - 즉 의도는 "배송 출발 시점에 입찰 COMPLETED"다.

요약하면, 배송 IN_TRANSIT → 주문 IN_TRANSIT → (구매자 알림) → 판매 SOLD(+판매자 알림) → 입찰 COMPLETED 순이다. 구매자 알림은 "출발"이고, 판매자 알림은 이 시점에 나간다.

### 1-3. 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문(즉시 구매 아님) — 끝까지 성공하지 못한다

선행 상태:

1. 입찰로 주문을 만들 때 `Faq`는 `PENDING_PAYMENT` (`FAQ/service/command/FaqCommandService.java:76-88`), `FaqBid`는 `PENDING` (`FAQ/service/command/FaqBidCommandService.java:92-102`)이다. 이 입찰에는 `StyleBid`가 연결되지 않는다.
2. 결제·배송 처리 후 실배송(창고 보관 아님)이면 주문은 `PAYMENT_COMPLETED → PREPARING`에서 멈춘다. 동기 경로는 `FaqCommandService.java:175-176`, 실제 컨트롤러가 쓰는 Kafka 경로는 `FaqEventConsumer.java:195, 216-217` (`FaqCommandController.java:54`가 이벤트 발행)이다.
3. 배송은 `FaqAddressCommandService#createOrderShipment`에서 `PENDING`으로 생성된다 (`FaqAddressCommandService.java:56-70`).

실패 지점:

1. `shipment.updateTrackingInfo(...)`(`:256`) 이후 `order.updateStatus(FaqStatus.IN_TRANSIT)`(`:260`)에서 `Faq.updateStatus`가 전이 검증을 한다 (`FAQ/entity/Faq.java:113-120`).
2. `PREPARING`의 허용 다음 상태는 `IN_WAREHOUSE`, `SHIPMENT_STARTED`뿐이다 (`FAQ/entity/FaqStatus.java:26`). `IN_TRANSIT`은 `SHIPMENT_STARTED`에서만 갈 수 있다 (`:28`). 따라서 `InvalidFaqStatusException("상태 전환이 허용되지 않습니다: PREPARING -> IN_TRANSIT")`이 발생한다 (`Faq.java:117-119`).
3. 이 예외는 `AddressException`이 아니므로 `catch (Exception e)` (`FaqAddressCommandService.java:295-302`)에서 `AddressException(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")`로 감싸져 던져진다. 에러코드가 실제 원인과 맞지 않는다.

저장되는 것:

1. **아무것도 저장되지 않는다.** `@Transactional` 메서드에서 RuntimeException이 밖으로 나가므로 롤백된다.
2. 3번 단계에서 메모리상으로 바꾼 택배사·운송장·IN_TRANSIT도 DB에 남지 않는다. 배송은 `PENDING`, 주문은 `PREPARING`, 입찰은 `MATCHED` 그대로다.
3. 구매자 "출발" 알림(`:265`)과 판매자 알림은 실패 지점 뒤에 있어 생성되지 않는다.

응답:

1. `GlobalExceptionHandler.handleShipmentException` (`G/exception/GlobalExceptionHandler.java:455-469`)이 `ErrorResponse{code:"S001", message:"배송 정보를 찾을 수 없습니다.", status:404, path}`를 내려보낸다. 코드값은 `ADDR/exception/AddressErrorCode.java:12`이다.
2. 커스텀 메시지(`"운송장 정보 업데이트 중 오류 발생 …"`)는 응답 바디에 쓰이지 않고 `errorCode.getMessage()`만 쓰인다.

보충: 이 주문이 실패 지점을 넘는다 해도, 일반 구매 입찰에는 주문에 연결된 `StyleBid`가 없다. `StyleBidQueryService#findByOrderId`는 없으면 null이 아니라 `IllegalArgumentException`을 던지므로 (`STYLE/service/query/StyleBidQueryService.java:26-29`) `updateSaleStatusToSold`의 `:116`에서 또 실패한다. `if (saleBid != null)` 분기(`:117`)는 사실상 죽은 코드다.

## 2. 배송 완료 감지

### 2-1. 누가·언제·어떻게

1. 사람이나 택배사 콜백이 아니라 서버의 스케줄러가 폴링한다. `AddressBatchScheduler#scheduleShipmentStatusJob`이 `@Scheduled(cron = "0 0 */6 * * *")`로 `updateShipmentStatusesJob`을 실행한다 (`G/config/AddressBatchScheduler.java:34-44`). 6시간마다(매일 00·06·12·18시 정각, 서버 타임존 기준)이며 `timestamp` 파라미터로 매번 새 JobInstance를 만든다. 예외는 `printStackTrace`만 한다 (`:41-43`).
2. 스케줄링 활성화는 `@EnableScheduling`(예: `domain/event/scheduler/EventStatusScheduler.java:22`)에 의존한다.
3. Job 구성: `ADDR/config/UpdateAddressStatusesJobConfig.java:54-82`. chunk 50 (`:51`), `faultTolerant().skip(Exception.class).skipLimit(50)` (`:75-77`).

### 2-2. 조회 대상

`JpaPagingItemReader`의 쿼리는 `SELECT s FROM FaqAddress s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL` (`UpdateAddressStatusesJobConfig.java:89-96`)이다. 즉 상태가 IN_TRANSIT·OUT_FOR_DELIVERY이고 운송장이 있는 배송이다. `PENDING`(운송장 미등록) 배송은 대상이 아니다.

### 2-3. 실제로 실행되는 처리 코드

`updateShipmentStatusesStep`은 `.processor(new AddressItemProcessor(playwrightBrowserManager(), notificationService, orderService))`를 쓴다 (`UpdateAddressStatusesJobConfig.java:69-73`). 따라서 실제 코드는 **`ADDR/config/AddressItemProcessor.java#process` (`:56-157`)** 이다.

실행되지 않는 유사 코드:

1. 같은 설정 클래스의 `shipmentItemProcessor()` `@Bean` (`UpdateAddressStatusesJobConfig.java:104-177`)과 private `parseCjLogisticsStatus` (`:186`). 스텝에 연결되어 있지 않다.
2. `FaqAddressCommandService#updateShipmentStatuses` (`FaqAddressCommandService.java:308-391`). 호출하는 곳이 없다.
3. `updateAndCheckShipmentStatus` (`:452`)는 API 요청 시에만 동작하며 주기 실행이 아니다.

조회 방식:

1. `BrowserManageStepListener`가 스텝 시작과 종료에 Playwright 브라우저를 열고 닫는다 (`ADDR/config/BrowserManageStepListener.java:14-24`).
2. 프로세서가 `https://trace.cjlogistics.com/next/tracking.html?wblNo=<운송장>`으로 이동한다 (`AddressItemProcessor.java:28, 81-83`).
3. `tbody#statusDetail tr`을 기다리고 (`:87`) 마지막 행의 5번째 `td` 텍스트를 상태 문자열로 쓴다 (`:167-181`). 행이 없거나 텍스트가 비면 `TRACKING_HTML_PARSE_ERROR`다.
4. 운송장이 비어 있으면 `TRACKING_NUMBER_INVALID`다 (`:61-64`).

### 2-4. 택배사 문자열 → 내부 상태 (`AddressItemProcessor.java:220-226`)

| 택배사 문자열 | 내부 `AddressStatus` |
|---|---|
| `"배송완료"` | `DELIVERED` |
| `"배송출발"` | `OUT_FOR_DELIVERY` |
| 그 외 모두 | `IN_TRANSIT` |

- 현재 상태와 같으면 변경 없이 그대로 반환한다 (`:101-105`).
- 상태 전이는 `FaqAddress.updateStatus`가 `AddressStatus.canTransitionTo`로 검증한다 (`ADDR/entity/FaqAddress.java:47-55`, `ADDR/entity/AddressStatus.java`).
- 예: `OUT_FOR_DELIVERY` 배송에 "배송중" 같은 기타 문자열이 오면 `IN_TRANSIT`으로 매핑되는데 `OUT_FOR_DELIVERY → IN_TRANSIT`은 불허라 `IllegalStateException`이 나고 (`AddressStatus.java:25-27`), `EXTERNAL_TRACKING_SERVICE_ERROR`로 감싸져 skip 된다 (`AddressItemProcessor.java:133-146`).

## 3. 배송 완료 판정 이후 (`AddressItemProcessor.java:108-117`, `FaqAddressCommandService#completeOrder` `:190-229`)

`DELIVERED`로 매핑되면 순서는 다음과 같다.

1. `orderShipment.updateStatus(DELIVERED)` — 배송 `IN_TRANSIT`/`OUT_FOR_DELIVERY` → `DELIVERED` (`AddressItemProcessor.java:113`).
2. `orderService.completeOrder(orderId)` (`:116`):
   1. `FaqBid`를 `findByOrderId`로 조회한다. 없으면 `IllegalArgumentException` (`FaqAddressCommandService.java:196-197`).
   2. 주문 `Faq` → `COMPLETED` (`:204`). `FaqStatus`상 `IN_TRANSIT`, `PENDING_PAYMENT`, `IN_WAREHOUSE`에서만 가능하다 (`FaqStatus.java:24, 27, 29`).
   3. `updateSaleStatusToSold(orderId)` (`:208`):
      - 판매 `Style` → `SOLD` (`StyleStatus`가 `ON_AUCTION`/`SELLING`일 때만, `:119-123`; `StyleStatus.java:21-22`).
      - 창고 보관이면 창고 상태를 갱신한다 (`:126-129`).
      - 판매자 알림 1건 (`:132-138`).
      - `FaqBid` 쪽은 같은 sale이 이미 SOLD라 변경과 알림이 없다 (`:155-156`).
   4. 구매자에게 "[completeOrder] 주문이 완료 처리되었습니다…" 알림 1건 (`:211-217`).
   5. 어떤 예외든 `AddressException(ORDER_NOT_FOUND_FOR_SHIPMENT)`로 감싸 던진다 (`:221-228`).
3. `notificationService.notifyShipmentCompleted(order)` (`AddressItemProcessor.java:117`): 구매자에게 "[배송 완료] 상품이 배송 완료되었습니다. 주문 ID: …" 알림 1건 (`PAY/service/command/PaymentCommandService.java:219-229`). 내부에서 예외를 삼킨다.
4. `JpaItemWriter`가 배송 엔티티를 저장하고 (`UpdateAddressStatusesJobConfig.java:239-246`), 주문과 판매 변경은 같은 청크 트랜잭션의 dirty checking으로 반영된다.

알림 건수: 구매자 2건(`[completeOrder]`, `[배송 완료]`), 판매자 1건(sale이 SOLD로 전이될 수 있을 때). 합계 최대 3건이다. 이 경로에서는 "출발" 알림이 나가지 않는다.

입찰 상태:

1. **주문 입찰(`FaqBid`)과 판매 입찰(`StyleBid`) 모두 변경되지 않는다.** 둘 다 `MATCHED` 그대로다.
2. `COMPLETED`로 바꾸는 `updateOrderAndSaleBidStatusToCompleted`는 `updateTrackingInfo`(`:289`)에서만 호출된다. 그런데 그 경로는 1-3처럼 실패한다.
3. 따라서 배치 경로에서는 입찰이 COMPLETED로 가지 않는다.

## 4. 주문 종류별 차이

공통 전제: 배치가 집으려면 배송이 `IN_TRANSIT`/`OUT_FOR_DELIVERY` + 운송장 보유여야 한다. 그런데 운송장 등록 API는 1-3처럼 두 주문 모두 실패한다. 배송 상태를 바꾸는 다른 코드는 `updateAndCheckShipmentStatus`(`:473`, `:497`)뿐이다. 이 API로 배송이 IN_TRANSIT이 되고 주문은 건드리지 않은 경우만 배치 대상이 된다.

### (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문 — 끝까지 가지 않는다

1. 주문은 `PREPARING`이다 (`FaqEventConsumer.java:216-217`).
2. 배송이 어떻게든 DELIVERED로 판정돼도 `completeOrder`의 `order.updateStatus(COMPLETED)`에서 `PREPARING → COMPLETED`가 불허다 (`FaqStatus.java:26`, `Faq.java:117`; `FaqAddressCommandService.java:204`).
3. `catch (Exception)`이 `AddressException(ORDER_NOT_FOUND_FOR_SHIPMENT, S102, 404)`로 감싼다 (`:221-228`). 배치에서는 skip 되어 롤백되고, 판매자·구매자 알림이 없으며 입찰 상태도 변하지 않는다.
4. 주문이 `COMPLETED`까지 갈 수 있다고 가정해도, 연결된 `StyleBid`가 없어 `saleBidQueryService.findByOrderId`가 `IllegalArgumentException`을 던진다 (`StyleBidQueryService.java:26-28`, `FaqAddressCommandService.java:116`). 어느 쪽이든 끝까지 가지 못한다.
5. `/check-status` API에서 DELIVERED면 같은 이유로 `completeOrder`(`:489`)가 실패한다. `AddressException`이 그대로 재던져져(`:505-506`) 트랜잭션 전체가 롤백되고 배송 DELIVERED도 저장되지 않는다.

### (b) 즉시 구매로 만들어진 주문 — 끝까지 진행된다 (배송이 배치 대상일 때)

1. `createInstantOrder`가 주문을 `PENDING_PAYMENT`로 만들고 (`FaqCommandService.java:241-247`), `saleBid.assignOrder(order)`와 `MATCHED`를 설정한다 (`:279-280`). 이후 `FaqBid`는 `MATCHED` + `sale` 연결 + `isInstantPurchase=true`로 만들어진다 (`FaqBidCommandService.java:189-206`). 주문 상태는 `PAYMENT_COMPLETED`/`PREPARING`으로 가지 않고 `PENDING_PAYMENT`로 남는다.
2. 운송장 등록 API는 `PENDING_PAYMENT → IN_TRANSIT`이 불허라 (`FaqStatus.java:24`) (a)와 똑같이 S001 404로 실패하고 롤백된다.
3. 배치로 DELIVERED가 판정되면 `completeOrder`가 `PENDING_PAYMENT → COMPLETED`를 허용한다 (`FaqStatus.java:24`). 이어서 `StyleBid`가 존재하므로 `findByOrderId`가 성공한다.
4. 결과:
   - 판매 `Style` → `SOLD` (sale이 `ON_AUCTION`/`SELLING`일 때; 그 외 상태면 SOLD·판매자 알림 없이 조용히 넘어간다 — `FaqAddressCommandService.java:119, 142-143`).
   - 판매자 알림 1건.
   - 구매자 알림 2건.
   - 배송 `DELIVERED`.
   - 주문 `COMPLETED`.
   - 입찰은 여전히 `MATCHED`.

### 차이 한 줄

(a)는 주문이 PREPARING이고 StyleBid가 없어 완료 처리에서 실패해 롤백·skip 된다. (b)는 주문이 PENDING_PAYMENT여서 COMPLETED 전이가 허용되고 StyleBid가 있어 완료·판매·알림까지 간다. 다만 입찰 COMPLETED 처리는 두 경우 모두 없다.

## 5. 실패 처리 (주기 처리 중 한 건이 실패할 때)

1. 프로세서에서 예외가 나면 `AddressException`이 아닌 것은 `EXTERNAL_TRACKING_SERVICE_ERROR`(503)로 감싸고 `AddressException`은 그대로 재던진다 (`AddressItemProcessor.java:133-146`).
2. 스텝이 `faultTolerant().skip(Exception.class).skipLimit(50)`이다 (`UpdateAddressStatusesJobConfig.java:75-77`). 실패 건은 skip 처리되고 `SkipListener`가 에러 로그를 남긴다 (`:251-287`).
3. 실패한 건의 변경은 청크 트랜잭션 롤백으로 저장되지 않는다.
   - 배송과 주문 상태, 그리고 `completeOrder` 안에서 만든 알림 행도 마찬가지다.
   - 상태가 그대로 IN_TRANSIT/OUT_FOR_DELIVERY이므로 다음 6시간 주기에 다시 조회 대상이 된다.
4. 나머지 건은 중단되지 않는다. Spring Batch가 청크를 롤백하고 skip 대상을 제외해 항목을 다시 처리한다. 성공 건은 정상 커밋된다.
   - 이 재처리 때문에 롤백된 청크의 앞쪽 성공 건에서 외부 부수효과(WebSocket 실시간 푸시, `PaymentCommandService.java:303-316`)가 두 번 나갈 수 있다. DB 행은 롤백 후 재생성된다.
5. skip이 50건을 넘으면 스텝이 실패한다. 스케줄러 쪽에서는 `printStackTrace`로만 처리한다 (`AddressBatchScheduler.java:41-43`).
6. 참고로 `notifyShipmentCompleted`는 알림 실패를 삼켜 전체를 실패시키지 않는다 (`PaymentCommandService.java:230-233`).
7. `FaqAddressCommandService#updateShipmentStatuses`에는 건별 try/catch로 계속 진행하는 로직이 있지만 (`:322-388`) 호출되지 않아 실제 동작과 무관하다.
