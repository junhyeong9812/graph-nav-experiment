# 즉시 구매 처리 흐름 (POST /order-bids/instant)

> 클래스 이름이 도메인 이름과 어긋나 있다(코드 내 이름 → 실제 의미): `Faq`=주문(Order, 테이블 `orders`), `FaqBid`=구매 입찰(order_bid), `StyleBid`=판매 입찰(sale_bid), `Style`=판매(sale), `Notification`=결제(payment), `Notice`=창고 보관(warehouse storage), `FaqAddress`=주문 배송 정보, `Product`=사용자, `payment.Payment`=앱 내 알림.
> 경로 약어: `D` = `src/main/java/com/fream/back/domain`

## 1. 진입 API, 처리 단계, 동기/비동기, 응답 ID

1. 진입점: `POST /order-bids/instant` (`D/faq/controller/command/FaqBidCommandController.java:24` 클래스 매핑 `/order-bids`, `:89` `@PostMapping("/instant")`). 요청 본문은 `saleBidId`, `addressId`, `warehouseStorage`, `paymentRequest` (`D/faq/dto/InstantFaqRequestDto.java`).
2. 컨트롤러: 로그인 이메일 추출(`FaqBidCommandController.java:92`) → 결제 요청에 `userEmail`을 채우고 `orderId`를 `null`로 비움(`:119-121`) → `FaqBidCommandService.createInstantOrderBid` 호출(`:101-110`).
3. `FaqBidCommandService.createInstantOrderBid` (`D/faq/service/command/FaqBidCommandService.java:119-146`, `@Transactional`):
   1. 입력 검증(`:123`, 검증 본문 `:150-162`)
   2. 구매자 조회(`:126`)
   3. 판매 입찰 조회 및 검증(`:129`, `:172-186`)
   4. `FaqCommandService.createInstantOrder` 호출(`:133-139`)
   5. 구매 입찰(FaqBid) 생성(`:142`, `:189-206`)
4. `FaqCommandService.createInstantOrder` (`D/faq/service/command/FaqCommandService.java:219-319`):
   1. 배송지 조회(`:238`)
   2. 주문 저장(`:241-247`)
   3. 결제 요청에 주문 ID 세팅(`:250`)
   4. 주문 항목 생성(`:255-256`)
   5. 배송 정보 생성(`:264-271`)
   6. 판매 입찰 매칭 및 flush(`:279-283`)
   7. 판매자 창고 상태 갱신(`:291-293`)
   8. 결제 처리(`:305`)
5. 결제 처리 `NotificationCommandService.processPayment` (`D/notification/service/command/NotificationCommandService.java:57-107`): 검증(`:117-146`) → 결제 유형별 분기(`:67-80`) → `notifyUsersAndUpdateSaleStatus`(`:83`, `:383-426`) → 알림 전송(`:434-462`).
6. **동기 처리**이다. 위 모든 단계가 한 HTTP 요청 스레드, 하나의 DB 트랜잭션 안에서 순차 실행된다(전파되는 `@Transactional`: `FaqBidCommandService.java:119`, `FaqCommandService.java:219`, `NotificationCommandService.java:37`). 즉시 구매 경로에는 Kafka 발행이 없다. Kafka를 쓰는 것은 별도 API `POST /orders/{orderId}/process-payment-shipment`(`D/faq/controller/command/FaqCommandController.java:41-54`, `FaqEventProducer`/`FaqEventConsumer`)뿐이다.
7. **응답 ID는 주문(Order) ID가 아니라 구매 입찰(FaqBid, order_bid) ID**이다. 컨트롤러 변수명은 `orderId`이지만 `createInstantOrderBid(...)`가 반환한 `FaqBid`에서 `.getId()`를 꺼낸다(`FaqBidCommandController.java:101-110`, 서비스 반환 타입 `FaqBidCommandService.java:119`). 응답 메시지는 "즉시 구매가 성공적으로 처리되었습니다."(`:112`).

## 2. 새로 만들어지는 엔티티와 상태 변화 순서

| 2 | 주문 항목(`FaqItem`) 생성, 수량 1, 가격 = 입찰가 | `FaqCommandService.java:255-256`, `D/faq/service/command/FaqItemCommandService.java:45-52` | 주문 `PENDING_PAYMENT` |

| 4 | 판매 입찰(`StyleBid`)에 주문 연결, 상태 `MATCHED`로 변경 후 flush | `FaqCommandService.java:279-283`, `D/style/entity/StyleBid.java:58-61` | 판매 입찰 `PENDING`→`MATCHED`. 주문은 그대로 |
| 5 | 판매(`Style`)가 `isWarehouseStorage`(판매자가 창고 보관으로 올린 건)이면 창고 보관(`Notice`) 상태를 `ASSOCIATED_WITH_ORDER`로 변경 | `FaqCommandService.java:291-293`, `D/notice/service/command/NoticeCommandService.java:117-133` | 창고 상태 `ASSOCIATED_WITH_ORDER`(해당 시) |
| 6 | 결제(`Notification`) 생성(결제 유형별, 아래 3번) | `NotificationCommandService.java:67-80` | 결제 `PAID` 또는 `PENDING`(아래 3번) |
| 7 | 판매(`Style`) 상태를 `SOLD`로 변경 | `NotificationCommandService.java:404` 또는 `:419`, `D/style/entity/Style.java:142-144` | 판매 `SOLD` |
| 8 | 구매 입찰(`FaqBid`) 생성·저장: `MATCHED`, `isInstantPurchase=true`, `order`·`sale` 연결 | `FaqBidCommandService.java:189-206`, `D/faq/entity/FaqBid.java:60-82`, `:97-99` | 구매 입찰 `MATCHED` |

- 새로 생기는 엔티티: 주문, 주문 항목, 배송 정보, 결제, 구매 입찰(FaqBid), 알림 2건(구매자·판매자; 알림 엔티티는 `D/payment/entity/Payment`).
- 7번 `SOLD` 변경은 결제가 PAID인지와 무관하게 실행된다(3번 참고).
- 주문의 상태는 `PENDING_PAYMENT`에서 바뀌지 않는다(5번 참고).
- 5번의 `NoticeException`은 `FaqNoticeProcessingFailedException`으로 바뀌어 전체 롤백된다(`FaqCommandService.java:295-301`).
- `entityManager.flush()`(`:283`)가 4번 직후 실행되므로 이후 `findByOrderId`가 판매 입찰을 찾을 수 있다.

## 3. 결제 수단별 결과, 최종 성공 여부, 카드 실패 시

공통: 결제 금액은 0보다 커야 하고, 요청의 orderId와 이메일이 일치해야 한다(`NotificationCommandService.java:131-145`). 요청 금액이 주문 총액(`totalAmount`)과 같은지는 비교하지 않는다.

| 결제 수단 | 동작 | 결제 상태 | 근거 |
|---|---|---|---|
| 카드(CARD) | 저장된 결제 수단 정보로 PortOne(아임포트) 일회성 결제 호출 | PG 응답 `status == "success"`면 `PAID`, `isSuccess=true`. 그 외 응답이면 기본값 `PENDING`, `isSuccess=false` | `NotificationCommandService.java:157-217`, 특히 `:179`, `:203-206`; 기본값 `D/notification/entity/Notification.java:39`, `:44` |
| 계좌이체(ACCOUNT) | 은행명 검증 후 결제 레코드만 생성, 외부 호출 없음 | 항상 `PENDING`(입금 확인 로직 없음) | `NotificationCommandService.java:236-265`, 특히 `:244`, `:260` |
| 일반 결제(GENERAL) | `impUid` 필수. 외부 검증 없이 클라이언트가 보낸 값으로 레코드 생성 | 즉시 `PAID`, `isSuccess=true` | `NotificationCommandService.java:290-318`, 특히 `:297-300`, `:313-314` |
| 그 외 | 예외 | - | `NotificationCommandService.java:77-79` |

**즉시 구매가 끝까지 성공하는가:** 결제 수단과 상관없이, 예외가 없으면 API는 성공(HTTP 200)으로 끝난다. 결제가 `PAID`가 아니어도 즉시 구매 흐름은 막히지 않는다. 계좌이체는 `PENDING` 상태로 입금 확인 없이, 카드는 PG가 200/code 0이면서 `status`가 `"success"`가 아닌 경우 `PENDING`/`isSuccess=false`로 저장된 채, 같은 요청 안에서 판매 입찰 `MATCHED`, 판매 `SOLD`, "결제가 완료되었습니다" 알림 전송까지 진행된다(`NotificationCommandService.java:83`, `:404`, `:419`, `:438-443`). 결제 상태(`isSuccess`/`status`)는 이 흐름에서 한 번도 검사하지 않는다.

**PG가 카드 결제를 실패로 응답하면:**
1. HTTP 상태가 200이 아니거나 응답 `code`가 0이 아니면 `NotificationProcessingException`을 던진다(`D/notification/portone/PortOneApiClient.java:270-274`). 통신 오류(`RestClientException`)는 `NotificationApiException`으로 바뀌고(`:288`), `@Retryable`로 최대 3회 시도한다(`:224-228`).
2. 예외는 `createCardPayment`에서 그대로 전파된다(`NotificationCommandService.java:218-219`, 카드 결제 호출 `:179-184`) → `processPayment`(`:89-100`) → `createInstantOrder`에서 `FaqNotificationProcessingFailedException`으로 포장된다(`FaqCommandService.java:304-309`) → `FaqBidCommandService`가 `FaqException`을 그대로 재던진다(`FaqBidCommandService.java:144-145`, `:212-218`).
3. 하나의 트랜잭션이므로 **전체 롤백**된다. 주문, 항목, 배송 정보, 판매 입찰 `MATCHED`, 창고 상태 변경이 모두 취소되고 구매 입찰은 만들어지지 않는다. 클라이언트는 오류 응답을 받는다.
4. 반면 PG가 HTTP 200/code 0을 주고 내부 `status`만 `"success"`가 아닌 경우(예: `failed`)에는 예외가 없다. 위의 "성공 처리되지만 결제는 `PENDING`" 경로가 된다(`NotificationCommandService.java:203-206`). 이 경우 환불 로직 호출도 없다(`handleRefundIfNecessary`는 정의만 있고 이 경로에서 호출되지 않는다: `:341`).

## 4. 알림 수신자, 시점, 전달 방식

1. **수신자와 문구**(`NotificationCommandService.java:434-462`):
   - 구매자: "결제가 완료되었습니다. 주문 ID: {orderId}" (`:438-443`)
   - 판매자(`sale.getSeller()`): "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}" (`:447-454`)
   - 둘 다 카테고리 `SHOPPING`, 타입 `BID`.
2. **시점:** 결제 레코드 저장 직후, 같은 요청 안에서 `notifyUsersAndUpdateSaleStatus`가 호출될 때(`:83`) 구매자 → 판매자 순으로 보낸다. 판매 상태 `SOLD` 변경 직전이다(`:403-404`, `:416-419`).
3. **주문 입찰 조회 경로:** 이 시점에는 FaqBid가 아직 만들어지지 않았으므로 `order.getOrderBid()`는 `null`이다(구매 입찰 생성은 `FaqBidCommandService.java:142`로 결제 이후). 따라서 `findByOrderId`로 판매 입찰을 찾아 그 `sale`을 사용한다(`NotificationCommandService.java:388-406`, `D/style/service/query/StyleBidQueryService.java:26-29`).
4. **전달 방식:** 동기 처리, Kafka 아님. `PaymentCommandService.createNotification`이 알림을 DB에 저장하고(`D/payment/service/command/PaymentCommandService.java:44-53`) WebSocket으로 푸시한다. 푸시는 Redis에 `WebSocket:Product:{email}` 키가 있을 때만(접속 중일 때만) `/queue/notifications`로 `convertAndSendToUser`한다(`:57`, `:303-322`, 상수 `:37-38`). 접속 중이 아니면 DB 저장만 되고 전송은 건너뛴다(`:321-322`).
5. **오류 처리 주의:** 알림·판매 상태 갱신 중 예외는 `catch`로 삼켜 로그만 남긴다(`NotificationCommandService.java:421-425`, `:457-461`). 따라서 알림이 실패해도 즉시 구매는 실패하지 않는다. 다만 `createNotification`은 자체가 `@Transactional`이라 내부 예외 시 공유 트랜잭션이 rollback-only로 표시될 수 있고, 이 경우 최종 커밋에서 오류가 날 수 있다(`PaymentCommandService.java:27`).

## 5. 최종 주문 상태와 창고 보관 선택 시 차이

1. **주문 최종 상태는 `PENDING_PAYMENT`이다.** 즉시 구매 경로에서는 주문 상태를 바꾸는 코드가 없다. `createInstantOrder`는 `PENDING_PAYMENT`로 생성만 하고(`FaqCommandService.java:241-245`) 이후 `updateStatus` 호출이 없다. 결제가 `PAID`여도 `PAYMENT_COMPLETED`로 전환되지 않는다. 결제 서비스도 주문 상태를 건드리지 않는다(`NotificationCommandService.java:57-107`, `:383-426`는 판매 상태만 `SOLD`로 바꾼다). 주문을 `PAYMENT_COMPLETED → PREPARING`(또는 `IN_WAREHOUSE → COMPLETED`)로 옮기는 코드는 다른 API의 `processPaymentAndShipment`(`FaqCommandService.java:163-177`)와 Kafka 컨슈머(`D/faq/service/kafka/FaqEventConsumer.java:192-200`)에만 있고 즉시 구매에서는 실행되지 않는다. 결제 상태는 3번 표와 같이 `PAID` 또는 `PENDING`이다.
   - 같이 바뀌는 다른 엔티티의 최종 값은 구매 입찰 `MATCHED`(`isInstantPurchase=true`), 판매 입찰 `MATCHED`, 판매 `SOLD`, 배송 `PENDING`이다.
2. **구매자가 "창고 보관(warehouseStorage)"을 선택해도 달라지는 것이 없다.**
   - 값은 DTO(`InstantFaqRequestDto.java:26`)에서 컨트롤러 로그(`FaqBidCommandController.java:94-95`)와 서비스 호출 인자(`:106`, `FaqBidCommandService.java:119`, `:133-139`)를 거쳐 `createInstantOrder(…, boolean isWarehouseStorage, …)`까지 전달되지만(`FaqCommandService.java:220-221`), 메서드 본문 어디에서도 사용되지 않는다(`:222-318`). 창고 보관(`Notice`) 레코드가 만들어지지 않고(`createOrderStorage` 호출 없음), 주문이 `IN_WAREHOUSE`/`COMPLETED`로 가지도 않는다.
   - 창고 보관 처리(`createOrderStorage`, `IN_WAREHOUSE`→`COMPLETED`)는 `processPaymentAndShipment`에만 있다(`FaqCommandService.java:163-172`).
   - 창고 관련으로 실제 반영되는 것은 구매자 선택이 아니라 **판매자의 판매 건**(`sale.isWarehouseStorage()`)뿐이다. 이 경우 판매자 창고 보관 상태가 `ASSOCIATED_WITH_ORDER`로 바뀐다(`FaqCommandService.java:291-293`). 해당 `Notice`가 없으면 `NoticeNotFoundException`(`D/notice/service/query/NoticeQueryService.java:30-33`) → 전체 롤백된다.
