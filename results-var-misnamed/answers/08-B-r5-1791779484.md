# 구매자 배송: 운송장 등록 → 배송 완료

경로 약어: `ADDR` = `src/main/java/com/fream/back/domain/address`, `FAQ` = `src/main/java/com/fream/back/domain/faq`,
`NOTI` = `src/main/java/com/fream/back/domain/notification`, `PAY` = `src/main/java/com/fream/back/domain/payment`, `GLOBAL` = `src/main/java/com/fream/back/global`.

용어(이름이 난독화되어 있음): `Faq` = 주문(테이블 `orders`), `FaqAddress` = 구매자 배송(테이블 `order_shipment`), `FaqBid` = 구매 입찰, `StyleBid` = 판매 입찰, `Style` = 판매(Sale), `Product` = 사용자, `PaymentCommandService.createNotification` = 사용자 알림 생성.

## 0. 선행: 결제·배송 처리 후 상태

- 주문은 `PENDING_PAYMENT`로 생성된다. `FAQ/service/command/FaqCommandService.java:81`
- 결제·배송 처리(`processPaymentAndShipment`)는 배송 정보(`FaqAddress`, `PENDING`)를 만들고 주문을 `PAYMENT_COMPLETED` → `PREPARING`까지만 올린다(창고 보관이 아닌 실배송). `FAQ/service/command/FaqCommandService.java:112`, `:155`, `:175-176`
- 배송 정보 초기 상태는 `PENDING`. `ADDR/service/command/FaqAddressCommandService.java:62-70` (`createOrderShipment`)
- 그러므로 "결제·배송 처리를 마친 실배송 일반 구매 입찰 주문"의 주문 상태는 `PREPARING`, 배송 상태는 `PENDING`이다.
- 주문 상태 전이표: `PREPARING`은 `IN_WAREHOUSE`/`SHIPMENT_STARTED`로만, `IN_TRANSIT`은 `COMPLETED`로만, `PENDING_PAYMENT`는 `PAYMENT_COMPLETED`/`COMPLETED`/`IN_WAREHOUSE`로만 갈 수 있다. `FAQ/entity/FaqStatus.java:24-29`
- 허용되지 않는 전이는 `InvalidFaqStatusException`(`FaqException` 계열, `AddressException` 아님)을 던진다. `FAQ/entity/Faq.java:112-121`

## 1. 운송장 등록 요청

### 1-1. 어느 API인가
- `PATCH /shipments/order/{shipmentId}/status`, 본문 `FaqAddressRequestDto`(courier, trackingNumber). `ADDR/controller/command/FaqAddressCommandController.java:20`, `:33-47`
- 컨트롤러는 `FaqAddressCommandService.updateTrackingInfo(shipmentId, courier, trackingNumber)`를 호출한다. `ADDR/controller/command/FaqAddressCommandController.java:41-45`
- (참고) `POST /shipments/order/{id}/check-status`, `/check-status-string`은 운송장 등록 + CJ 즉시 조회를 하는 별도 API다. `ADDR/controller/command/FaqAddressCommandController.java:58`, `:103`

### 1-2. 코드가 의도한 순서 (`updateTrackingInfo`, `@Transactional`)
1. courier/trackingNumber 공백이면 `TRACKING_INFO_REQUIRED`. `ADDR/service/command/FaqAddressCommandService.java:241-246`
2. 배송(`FaqAddress`) 조회 후 `shipment.updateTrackingInfo` → 택배사·운송장 세팅 + 배송 상태를 곧바로 `IN_TRANSIT`으로 세팅(전이 검증 없음). `ADDR/service/command/FaqAddressCommandService.java:256`, `ADDR/entity/FaqAddress.java:41-45`
3. 주문 상태 `order.updateStatus(IN_TRANSIT)`. `ADDR/service/command/FaqAddressCommandService.java:259-260`
4. 구매자에게 알림 "상품이 출발하였습니다. 주문 ID: …" 1건. `ADDR/service/command/FaqAddressCommandService.java:264-270`
5. `updateSaleStatusToSold(orderId)`: 판매(Style)를 `SOLD`로, 판매자에게 "상품이 성공적으로 판매 완료되었습니다" 알림(최대 2경로: SaleBid 경로, OrderBid 경로), 창고 보관이면 창고 상태 SOLD. `ADDR/service/command/FaqAddressCommandService.java:276`, `:111-186`
6. 창고 보관 판매면 창고 상태를 한 번 더 SOLD로. `ADDR/service/command/FaqAddressCommandService.java:279-286`
7. `updateOrderAndSaleBidStatusToCompleted`: 구매 입찰·판매 입찰이 `MATCHED`이면 `COMPLETED`로. `ADDR/service/command/FaqAddressCommandService.java:289`, `:412-437`

즉 의도상 "운송장 등록"에서 이미 판매 SOLD·입찰 COMPLETED·판매자 알림까지 처리하도록 짜여 있다(배송 완료 이전에).

### 1-3. 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문(즉시 구매 아님)에서 끝까지 성공하나 → **아니오, 실패한다**
- 실패 지점: 3단계 `order.updateStatus(FaqStatus.IN_TRANSIT)`. 주문이 `PREPARING`인데 `PREPARING → IN_TRANSIT`은 전이표에 없다(`PREPARING`은 `IN_WAREHOUSE`, `SHIPMENT_STARTED`만 허용). `FAQ/entity/FaqStatus.java:26`, `FAQ/entity/Faq.java:112-121`, 호출 `ADDR/service/command/FaqAddressCommandService.java:260`
  - `SHIPMENT_STARTED`로 올리는 코드는 어디에도 없다(전이표 정의 외에 `FaqStatus.SHIPMENT_STARTED`를 세팅하는 곳이 없음: 결제 처리는 `FAQ/service/command/FaqCommandService.java:165-176`, `FAQ/service/kafka/FaqEventConsumer.java:195-217`에서 PREPARING/IN_WAREHOUSE/COMPLETED까지만).
- 예외 흐름: `InvalidFaqStatusException`이 `catch (AddressException)`에 걸리지 않고 `catch (Exception e)`로 가서 `AddressException(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")`으로 감싸 던진다. `ADDR/service/command/FaqAddressCommandService.java:293-302`
- 무엇이 저장되나: **아무것도 저장되지 않는다.** 예외가 `@Transactional` 메서드(`ADDR/service/command/FaqAddressCommandService.java:238`) 밖으로 나가 롤백되므로 2단계에서 바꾼 courier/trackingNumber/`IN_TRANSIT`도 DB에 남지 않는다. 구매자 알림(4단계)은 실패 지점 뒤라서 생성되지 않고, 판매자 알림·입찰 변경도 실행되지 않는다. 결과: 배송 `PENDING`(운송장 없음), 주문 `PREPARING` 그대로.
- 응답: `GlobalException`이 `GlobalExceptionHandler`에서 `errorCode.getStatus()`로 변환된다. `SHIPMENT_NOT_FOUND`의 상태값은 404, 코드 "S001", 메시지 "배송 정보를 찾을 수 없습니다.". 따라서 **HTTP 404 + ErrorResponse(code S001)**. `GLOBAL/exception/GlobalExceptionHandler.java:49-61`, `ADDR/exception/AddressErrorCode.java:12`
- 부가: 롤백되므로 이후 배치 조회 대상(상태 `IN_TRANSIT` + 운송장 있음)에도 영원히 들어오지 않는다. `ADDR/config/UpdateAddressStatusesJobConfig.java:95`
- 참고(참고용 우회 경로): `check-status` API(`updateAndCheckShipmentStatus`)는 주문 상태를 건드리지 않고 배송만 `IN_TRANSIT`으로 만든다. `ADDR/service/command/FaqAddressCommandService.java:473`, `:497`. 이 경로로만 주문 `PREPARING` + 배송 `IN_TRANSIT` 조합이 만들어질 수 있다(2~4번 질문 참조).

## 2. 배송 완료 감지

### 2-1. 누가·언제·어떻게
- 사람이 아니라 **스케줄러**가 감지한다. `AddressBatchScheduler.scheduleShipmentStatusJob()`가 `@Scheduled(cron = "0 0 */6 * * *")`로 Spring Batch Job `updateShipmentStatusesJob`을 실행한다. `GLOBAL/config/AddressBatchScheduler.java:34-44`
- 주기: **6시간마다** (매일 00:00, 06:00, 12:00, 18:00, 서버 타임존 기준). `GLOBAL/config/AddressBatchScheduler.java:34`
- 수동 감지 경로도 있다: `POST /shipments/order/{id}/check-status` → `updateAndCheckShipmentStatus`. `ADDR/controller/command/FaqAddressCommandController.java:58`, `ADDR/service/command/FaqAddressCommandService.java:451-`

### 2-2. 조회 대상
- Job의 reader 쿼리: `SELECT s FROM FaqAddress s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL`. 페이지/청크 50. `ADDR/config/UpdateAddressStatusesJobConfig.java:50-52`, `:90-97`

### 2-3. 실제로 실행되는 처리 코드
비슷한 코드가 4곳 있다.

- Writer는 `JpaItemWriter`로 배송 엔티티를 저장한다. `ADDR/config/UpdateAddressStatusesJobConfig.java:72`, `:236-244`

### 2-4. 택배사 상태 문자열 → 내부 상태

(정확한 문자열 일치(`switch`)이며 `trim()`만 적용. 공백/빈 문자열은 `parseStatusFromHtml`에서 `TRACKING_HTML_PARSE_ERROR`. `ADDR/config/AddressItemProcessor.java:181-189`)

## 3. 배송 완료 판정 이후 (`AddressItemProcessor`, 상태 DELIVERED일 때)

### 3-1. 엔티티 상태 변경 순서
1. 새 상태가 현재 상태와 같으면 변경 없이 반환. `ADDR/config/AddressItemProcessor.java:100-105`
2. 배송 `orderShipment.updateStatus(DELIVERED)` (`IN_TRANSIT`/`OUT_FOR_DELIVERY` → `DELIVERED`는 허용). `ADDR/config/AddressItemProcessor.java:113`, `ADDR/entity/AddressStatus.java:15-26`
3. `orderService.completeOrder(orderId)`:
   1. 구매 입찰 조회(없으면 `IllegalArgumentException`). `ADDR/service/command/FaqAddressCommandService.java:196-197`
   2. 주문 `COMPLETED`. `ADDR/service/command/FaqAddressCommandService.java:204`
   3. `updateSaleStatusToSold(orderId)`: 판매(Style) `SOLD`(전이 가능 시)·창고 상태 SOLD. `ADDR/service/command/FaqAddressCommandService.java:208`, `:111-186`
   4. 구매자 알림. `ADDR/service/command/FaqAddressCommandService.java:211-217`
4. `notificationService.notifyShipmentCompleted(order)`: 구매자 배송 완료 알림. `ADDR/config/AddressItemProcessor.java:117`, `PAY/service/command/PaymentCommandService.java:219-232`
5. Writer가 배송 엔티티 저장(청크 트랜잭션).

### 3-2. 알림 (정상 진행 시)
- **구매자 2건**: ① "[completeOrder] 주문이 완료 처리되었습니다. 주문 ID: …" `ADDR/service/command/FaqAddressCommandService.java:211-217` ② "[배송 완료] 상품이 배송 완료되었습니다. 주문 ID: …" `PAY/service/command/PaymentCommandService.java:224-229` (중복 알림. `updateShipmentStatuses`의 "상품이 배송 완료되었습니다"는 미사용 코드).
- **판매자**: 판매(Style)가 아직 `SOLD`가 아니고 `SOLD`로 전이 가능한 경우에만 "상품이 성공적으로 판매 완료되었습니다. 판매 ID: …" 최대 1건(SaleBid 경로에서 SOLD가 되면 OrderBid 경로는 이미 SOLD라 건너뜀). `ADDR/service/command/FaqAddressCommandService.java:119-139`, `:151-171`. 단 결제 시점에 이미 판매가 SOLD(`NOTI/service/command/NotificationCommandService.java:404`, `:419`)가 되고 `StyleStatus.SOLD`는 더 이상 전이 불가(`style/entity/StyleStatus.java`의 `case SOLD … -> false`)이므로, 결제가 정상 처리된 주문이면 판매자 완료 알림은 0건이다.
- 총 구매자 2건 / 판매자 0~1건(정상 흐름에서는 0건).

### 3-3. 입찰 상태
- 배치 경로(`completeOrder`)는 **구매 입찰·판매 입찰 상태를 바꾸지 않는다.** `COMPLETED`로 바꾸는 `updateOrderAndSaleBidStatusToCompleted`는 운송장 등록(`updateTrackingInfo`)에서만 호출되고(`ADDR/service/command/FaqAddressCommandService.java:289`) 그 단계는 1-3대로 항상 실패한다. 따라서 배송 완료 후에도 입찰은 `MATCHED`에 머문다(`FaqBid`는 결제 시 `MATCHED`: `FAQ/service/command/FaqCommandService.java:187-189`).
- 판매(Style) 쪽 상태는 `SOLD`(`updateSaleStatusToSold`), 구매 입찰·판매 입찰 엔티티 자체는 변하지 않는다.

## 4. 주문 종류별 차이

공통 전제: 배치 대상이 되려면 배송이 `IN_TRANSIT`/`OUT_FOR_DELIVERY` + 운송장 보유여야 하는데, 정상 API(운송장 등록)로는 두 주문 모두 그 상태가 만들어지지 않는다(1-3, 아래 (b)). 아래는 배송이 `DELIVERED`로 판정되는 시점(예: `check-status`로 배송만 `IN_TRANSIT`이 된 경우 또는 운영 DB 수정)의 코드상 결과다.

### (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문 → **끝까지 진행되지 않는다**
- 주문 상태가 `PREPARING`이므로 `completeOrder`의 `order.updateStatus(COMPLETED)`에서 `PREPARING → COMPLETED` 불가로 예외. `FAQ/entity/FaqStatus.java:26`, `ADDR/service/command/FaqAddressCommandService.java:204`
- `completeOrder`가 `catch (Exception)`으로 `AddressException(ORDER_NOT_FOUND_FOR_SHIPMENT)`로 감싸 던짐. `ADDR/service/command/FaqAddressCommandService.java:221-227`
- 결과: 주문 `PREPARING` 유지, 판매 `SOLD` 변경·알림(구매자 2건, 판매자) 없음, 입찰 변경 없음, 배송 `DELIVERED` 변경도 롤백(청크 롤백·스킵). 다음 6시간 주기에 같은 건이 다시 시도되어 매번 실패.
- 추가로, 이 주문에 `StyleBid`가 연결돼 있지 않으면(일반 구매 입찰 + 판매자 `createSale` 경로는 `StyleBid.order`를 만들지 않음: `style/service/command/StyleCommandService.java:79-80`) `StyleBidQueryService.findByOrderId`가 null이 아니라 `IllegalArgumentException`을 던지므로(`style/service/query/StyleBidQueryService.java:26-28`), 상태 전이 문제를 피했더라도 `updateSaleStatusToSold`의 첫 줄(`ADDR/service/command/FaqAddressCommandService.java:116`)에서 다시 실패한다(이 호출은 try 밖).

### (b) 즉시 구매로 만들어진 주문
- 운송장 등록 단계: 즉시 구매 주문은 `PENDING_PAYMENT`로 생성되고(`FAQ/service/command/FaqCommandService.java:244`) 결제 처리(`:305`)가 주문 상태를 바꾸지 않으며(결제 서비스에 `order.updateStatus` 없음, `NOTI/service/command/NotificationCommandService.java`), 그래서 `PENDING_PAYMENT → IN_TRANSIT`도 전이표에 없어 운송장 등록 역시 404로 실패한다. `FAQ/entity/FaqStatus.java:24`
- 배송 완료 처리: 즉시 구매는 주문 생성 후 `createInstantOrderBid`로 구매 입찰(`MATCHED`, `isInstantPurchase`)을 만든다. `FAQ/service/command/FaqBidCommandService.java:140-142`, `:189-206`. 따라서 `completeOrder`의 입찰 조회는 성공하고, `PENDING_PAYMENT → COMPLETED`는 전이표에 허용되어 있어(`FAQ/entity/FaqStatus.java:24`) 주문이 `COMPLETED`가 된다.
- `updateSaleStatusToSold`: `StyleBid`가 주문에 연결되어 있고(`FAQ/service/command/FaqCommandService.java:279`) 판매는 결제 시 이미 `SOLD`(`NOTI/service/command/NotificationCommandService.java:391-405`)이므로 `canTransitionTo(SOLD)`가 false → 판매자 알림·상태 변경 없음.
- 결과: **끝까지 진행된다.** 주문 `COMPLETED`, 배송 `DELIVERED`, 구매자 알림 2건, 판매자 알림 0건, 입찰(`FaqBid`·`StyleBid`)은 `MATCHED` 유지.
- 정리: (a)는 `PREPARING`이라 완료 단계에서 실패하고, (b)는 `PENDING_PAYMENT → COMPLETED` 전이가 허용되어 (a)와 달리 완료까지 진행된다. 다만 (b)도 운송장 등록 API로는 배치 대상 상태가 되지 못한다.

## 5. 실패 처리 (주기 처리 중 한 건 실패)
- Step이 `faultTolerant().skip(Exception.class).skipLimit(50)`로 구성되어 있어, 처리 중 예외가 난 건은 **스킵**되고 나머지 건은 계속 처리된다. `ADDR/config/UpdateAddressStatusesJobConfig.java:74-78`
