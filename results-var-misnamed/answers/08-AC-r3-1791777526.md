# 구매자 배송: 운송장 등록 → 배송 완료

경로는 모두 `src/main/java/com/fream/back/` 기준이다. 약어는 다음과 같다.
- `FAS` = `domain/address/service/command/FaqAddressCommandService.java`
- `FaqAddress` = 구매자 배송 엔티티 (`domain/address/entity/FaqAddress.java`)
- `Faq` = 주문 엔티티 (`domain/faq/entity/Faq.java`)

## 요약

- 운송장 등록 API(`PATCH /shipments/order/{shipmentId}/status`)는 의도한 흐름대로라면 배송 → 주문 → 알림 → 판매/입찰 순으로 갱신한다. 그러나 결제·배송 처리를 마친 주문은 `PREPARING` 상태라서 `PREPARING → IN_TRANSIT` 전환이 막힌다. 실제로는 항상 실패하고 트랜잭션이 롤백되어 아무것도 저장되지 않는다.
- 배송 완료는 6시간마다 도는 Spring Batch 잡이 감지한다. 실제 실행되는 코드는 `AddressItemProcessor`다.
- 배송 완료 처리(`completeOrder`)는 일반 구매 입찰 주문(a)에서는 `Faq.updateStatus(COMPLETED)`에서 막힌다. 즉시 구매 주문(b)에서만 끝까지 간다.
- (b)도 입찰 상태(`FaqBid`/`StyleBid`)는 `COMPLETED`가 되지 않는다. 판매자 알림도 가지 않는다.

## 1. 운송장 등록 요청

### 1-1. 진입 API
1. `PATCH /shipments/order/{shipmentId}/status`, 본문은 `{courier, trackingNumber}`다.
   - 클래스 매핑은 `domain/address/controller/command/FaqAddressCommandController.java:20`이다.
   - 메서드는 `FaqAddressCommandController.java:33-34`이고, 서비스 호출은 `:41-45`이다.
   - 요청 DTO는 `domain/address/dto/FaqAddressRequestDto.java`의 `courier`, `trackingNumber`다.
2. 컨트롤러는 별도 try/catch 없이 `FAS#updateTrackingInfo`를 호출하고, 성공하면 `200 OK`(본문 없음)를 반환한다 (`FaqAddressCommandController.java:48`).
3. 보조 API로 `POST /shipments/order/{shipmentId}/check-status`(`FaqAddressCommandController.java:58`)가 있다.
   - `FAS#updateAndCheckShipmentStatus`(`FAS:452`)를 호출한다.
   - 운송장을 등록하고 즉시 택배사를 조회한다.

### 1-2. 코드가 의도한 상태 변경 순서 (`FAS#updateTrackingInfo`, `FAS:238-303`)
1. 택배사·운송장 번호가 비어 있으면 `TRACKING_INFO_REQUIRED`를 던진다 (`FAS:243-246`).
2. `FaqAddress`를 조회한다 (`FAS:249`).
3. **`FaqAddress`** 에 `updateTrackingInfo`를 호출한다 (`FAS:256`).
   - 택배사와 운송장 번호를 넣고 상태를 `IN_TRANSIT`으로 직접 대입한다. 상태 전이 검증은 없다 (`FaqAddress.java:41-45`).
4. **`Faq`(주문)** 를 `IN_TRANSIT`으로 바꾼다 (`FAS:259-260`).
   - `Faq#updateStatus`가 `FaqStatus.canTransitionTo`로 전이를 검증한다 (`Faq.java:166-174`).
5. **구매자**에게 알림 "상품이 출발하였습니다. 주문 ID: …"를 생성한다 (`FAS:265-271`).
6. `updateSaleStatusToSold`를 호출한다 (`FAS:276`).
   - 판매(`Style`)를 `SOLD`로 바꾼다 (`FAS:123`, `FAS:160`).
   - **판매자**에게 "상품이 성공적으로 판매 완료되었습니다" 알림을 보낸다 (`FAS:133-138`, `FAS:164-169`).
   - 창고 보관 상품이면 창고 상태도 `SOLD`로 바꾼다 (`FAS:126-129`).
7. 창고 보관 판매이면 창고 상태를 다시 한 번 갱신한다 (`FAS:279-286`).
8. `updateOrderAndSaleBidStatusToCompleted`(`FAS:289`, 본체 `FAS:413-440`)를 호출한다.
   - `FaqBid`가 `MATCHED`이면 `COMPLETED`로 바꾼다 (`FAS:422-425`).
   - `StyleBid`가 `MATCHED`이면 `COMPLETED`로 바꾼다 (`FAS:428-432`).

### 1-3. 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문은 끝까지 성공하지 못한다
**실패 지점은 `FAS:260`의 `order.updateStatus(FaqStatus.IN_TRANSIT)`이다.**

1. 주문의 상태는 `processPaymentAndShipment`의 비창고(실배송) 분기 때문에 `PAYMENT_COMPLETED → PREPARING`에서 멈춘다 (`domain/faq/service/command/FaqCommandService.java:115-118`).
2. `FaqStatus`는 `PREPARING`에서 `{IN_WAREHOUSE, SHIPMENT_STARTED}`로만 전이를 허용한다 (`domain/faq/entity/FaqStatus.java:26`).
   - `IN_TRANSIT`으로 가려면 `SHIPMENT_STARTED`를 거쳐야 한다 (`FaqStatus.java:28`).
   - 그런데 `SHIPMENT_STARTED`를 세팅하는 코드는 저장소 어디에도 없다. `FaqStatus.SHIPMENT_STARTED`를 참조하는 호출이 없다.
3. 따라서 `Faq#updateStatus`가 `InvalidFaqStatusException`을 던진다 (`Faq.java:170-172`).
4. 이 예외는 `FAS:293`의 `catch (AddressException)`에 걸리지 않는다. `FaqException`이므로 `FAS:295`의 `catch (Exception)`에서 잡힌다.
5. 거기서 `AddressException(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")`으로 바뀌어 던져진다 (`FAS:296-301`).
   - 이름이 말하는 의도(배송 정보 없음)와 실제 원인(주문 상태 전이 불가)이 다르다.

**무엇이 저장되는가: 아무것도 저장되지 않는다.**
- `updateTrackingInfo`는 `@Transactional`(`FAS:238`)이고 `AddressException`은 `GlobalException extends RuntimeException`이다 (`global/exception/GlobalException.java:10`). 그래서 롤백된다.
- 3단계에서 `FaqAddress`에 넣은 택배사·운송장·`IN_TRANSIT`은 메모리 변경일 뿐이며 커밋되지 않는다.
- 5단계의 구매자 알림(`FAS:266`)은 4단계 이전에 예외가 나서 실행되지 않는다.
- 결과는 `FaqAddress`가 `PENDING`에 운송장 없음, `Faq`가 `PREPARING`인 채로 유지되는 것이다.

**응답은 404이다.**
- `GlobalExceptionHandler#handleGlobalException`이 처리한다 (`global/exception/GlobalExceptionHandler.java:49-63`).
- `ErrorResponse`의 코드는 `S001`, 메시지는 "배송 정보를 찾을 수 없습니다.", status는 404다 (`domain/address/exception/AddressErrorCode.java:12`).
- 상세 메시지가 아니라 에러코드의 고정 메시지가 응답 본문에 들어간다.

**참고: 창고 보관 주문도 실패한다.**
- 창고 보관 주문은 이미 `COMPLETED`다 (`FaqCommandService.java:104-113`).
- `COMPLETED`는 전이 가능한 상태가 없다 (`FaqStatus.java:31`).

## 2. 배송 완료 감지

### 2-1. 누가·언제·어떻게
- 주체는 Spring `@Scheduled` 스케줄러가 띄우는 Spring Batch 잡이다.
- 주기는 `@Scheduled(cron = "0 0 */6 * * *")`, 즉 **6시간마다**(00·06·12·18시 정각)다 (`global/config/AddressBatchScheduler.java:34`).
  - 실행할 때마다 `timestamp` 파라미터를 넣어 `updateShipmentStatusesJob`을 `jobLauncher.run`으로 실행한다 (`AddressBatchScheduler.java:36-40`).
  - 예외는 `printStackTrace`로만 처리한다 (`AddressBatchScheduler.java:41-43`).
- 그 외에 사용자가 `POST /shipments/order/{id}/check-status`를 호출하면 즉시 조회·갱신된다 (`FAS:452-516`).

### 2-2. 조회 대상
- 잡의 Reader는 `JpaPagingItemReader`다 (`domain/address/config/UpdateAddressStatusesJobConfig.java:339-349`).
- 쿼리는 다음과 같다 (`UpdateAddressStatusesJobConfig.java:347`).
  ```
  SELECT s FROM FaqAddress s
  WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL
  ```
- 즉 상태가 `IN_TRANSIT` 또는 `OUT_FOR_DELIVERY`이고 운송장 번호가 있는 **구매자 배송**만 대상이다.
- chunk=50, skipLimit=50이다 (`UpdateAddressStatusesJobConfig.java:303-304`).
- 이 상태에 도달하는 경로는 두 가지다.
  - `updateTrackingInfo`: 1-3에서 본 대로 항상 롤백되므로 실제로는 도달하지 못한다.
  - `check-status` API: 운송장을 넣고 `IN_TRANSIT`(또는 `OUT_FOR_DELIVERY`)으로 커밋한다 (`FAS:473`, `FAS:491-498`).
  - 따라서 실제 배치 대상은 사실상 `check-status`로 운송장이 들어간 배송이다.

### 2-3. 실제로 실행되는 처리 코드
실행되는 것은 **`domain/address/config/AddressItemProcessor.java#process`** 다.

- 스텝이 `.processor(new AddressItemProcessor(playwrightBrowserManager(), notificationService, orderService))`로 연결한다 (`UpdateAddressStatusesJobConfig.java:321-325`).
- 이 프로세서의 동작은 다음과 같다.
  - Playwright로 CJ 페이지를 열고 `tbody#statusDetail tr`을 기다린다 (`AddressItemProcessor.java:72-87`).
  - 마지막 행의 5번째 `td` 텍스트를 상태 문자열로 쓴다 (`AddressItemProcessor.java:181`).

실행되지 않는 유사 코드는 다음과 같다.
- `UpdateAddressStatusesJobConfig#shipmentItemProcessor`(`:358-429`)는 `@Bean`이지만 스텝에 연결되지 않는다 (`:321`은 `new AddressItemProcessor`).
- `UpdateAddressStatusesJobConfig#parseCjLogisticsStatus`(`:438`)는 어디서도 호출되지 않는다.
- `FAS#updateShipmentStatuses`(`FAS:308-391`)는 정의만 있고 호출하는 곳이 없다. 이 메서드는 `@Scheduled`도 아니다.
- `FAS#updateAndCheckShipmentStatus`는 `check-status` API에서만 호출된다.

### 2-4. 택배사 상태 문자열 → 내부 상태
`AddressItemProcessor#mapToShipmentStatus` (`AddressItemProcessor.java:220-226`):

| 택배사 문자열 | 내부 상태 |
|---|---|
| `"배송완료"` | `DELIVERED` |
| `"배송출발"` | `OUT_FOR_DELIVERY` |
| 그 외 모든 문자열 | `IN_TRANSIT` |

- 완전 일치 비교다. `"배송출발"` 외의 진행 표현은 모두 `IN_TRANSIT`이 된다.
- 같은 매핑이 `FAS:399-405`와 `UpdateAddressStatusesJobConfig.java:480-486`에도 복제되어 있다.

## 3. 배송 완료 판정 이후 (`AddressItemProcessor#process`, `:108-117`)

`DELIVERED`로 판정된 경우(현재 상태와 다를 때)의 순서는 다음과 같다.

1. **`FaqAddress`**: `updateStatus(DELIVERED)` (`AddressItemProcessor.java:113`).
   - `IN_TRANSIT`/`OUT_FOR_DELIVERY → DELIVERED`는 허용된다 (`domain/address/entity/AddressStatus.java:72-84`).
2. `orderService.completeOrder(orderId)` (`AddressItemProcessor.java:116`, 본체 `FAS:190-229`)를 호출한다.
   1. `FaqBid`를 `findByOrderId`로 조회한다. 없으면 예외다 (`FAS:196-197`).
   2. **`Faq`**: `updateStatus(COMPLETED)` (`FAS:204`).
   3. `updateSaleStatusToSold(orderId)`를 호출한다 (`FAS:208`).
      - `StyleBid`를 조회한다.
      - 판매(`Style`)가 `SOLD`로 전이 가능하면 `SOLD`로 바꾸고 판매자에게 알림을 보낸다 (`FAS:116-141`).
      - `FaqBid`가 가리키는 판매에 대해서도 같은 처리를 한다 (`FAS:150-180`).
   4. **구매자**에게 "[completeOrder] 주문이 완료 처리되었습니다. 주문 ID: …" 알림을 보낸다 (`FAS:211-217`).
3. `notificationService.notifyShipmentCompleted(order)` (`AddressItemProcessor.java:117`).
   - **구매자**에게 "[배송 완료] 상품이 배송 완료되었습니다. 주문 ID: …" 알림을 보낸다 (`domain/payment/service/command/PaymentCommandService.java:219-232`).
4. 스텝 Writer(`JpaItemWriter`, `UpdateAddressStatusesJobConfig.java:491-498`)가 `FaqAddress`를 저장한다.

### 알림 건수
- 구매자는 **2건**을 받는다. `completeOrder`의 "[completeOrder]…"(`FAS:212-217`)와 `notifyShipmentCompleted`의 "[배송 완료]…"(`PaymentCommandService.java:226-229`)다.
- 판매자는 원래 설계상 1건이다 (`FAS:133-138`). 그러나 **실제로는 0건**이다.
  - 결제 시점에 이미 판매가 `SOLD`로 바뀐다. `NotificationCommandService#notifyUsersAndUpdateSaleStatus`가 `sale.updateStatus(SOLD)`를 호출한다 (`domain/notification/service/command/NotificationCommandService.java:404`, `:419`).
  - `StyleStatus.SOLD`는 전이 가능한 상태가 없다 (`domain/style/entity/StyleStatus.java:23`).
  - 그래서 `canTransitionTo(SOLD)`가 거짓이 되어 판매자 알림 분기에 들어가지 못한다 (`FAS:119`, `FAS:156`).

### 입찰 상태
- **이 경로에서는 `FaqBid`와 `StyleBid`가 `COMPLETED`로 바뀌지 않는다.**
  - 입찰을 `COMPLETED`로 바꾸는 `updateOrderAndSaleBidStatusToCompleted`는 `updateTrackingInfo`(`FAS:289`)에서만 호출된다.
  - 그런데 `updateTrackingInfo`는 1-3에서 본 대로 항상 실패한다.
  - 배치 경로(`completeOrder`)와 `check-status` 경로에는 입찰 상태 변경이 없다.
- 입찰은 `MATCHED`로 남는다.
  - `FaqBid`는 주문이 붙는 순간 `MATCHED`가 된다 (`domain/faq/entity/FaqBid.java:260-261`).
  - `StyleBid`도 주문이 붙는 순간 `MATCHED`가 된다 (`domain/style/entity/StyleBid.java:58-60`).

## 4. 주문 종류별 차이

배송이 `IN_TRANSIT`이고 택배사가 "배송완료"를 반환했다고 가정한다. 그 상태가 되는 경로는 `check-status`다.

### (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문: 끝까지 진행되지 않는다
1. 주문은 `PREPARING`이다 (`FaqCommandService.java:115-118`).
2. `completeOrder`의 `order.updateStatus(COMPLETED)`(`FAS:204`)가 막힌다.
   - `PREPARING → COMPLETED`는 허용되지 않는다 (`FaqStatus.java:26`).
   - `InvalidFaqStatusException`이 발생한다 (`Faq.java:170`).
3. `completeOrder`의 `catch (Exception)`이 `AddressException(ORDER_NOT_FOUND_FOR_SHIPMENT)`으로 감싸 던진다 (`FAS:221-227`).
   - 에러코드 이름은 "주문 없음"이지만 실제 원인은 상태 전이 불가다.
4. 그 이후의 `updateSaleStatusToSold`, 구매자 알림 2건, 판매자 알림은 실행되지 않는다.
5. 배치에서는 다음과 같이 처리된다.
   - `AddressItemProcessor#process`의 `catch`가 예외를 다시 던진다 (`AddressItemProcessor.java:133-145`).
   - 스텝의 `skip(Exception.class)`로 해당 항목이 스킵된다 (`UpdateAddressStatusesJobConfig.java:327-330`).
   - `FaqAddress`의 `DELIVERED` 변경은 저장되지 않는다. `completeOrder`가 같은 트랜잭션에 참여하므로 롤백된다.
   - 배송은 `IN_TRANSIT`에 머물고, 6시간마다 다시 대상이 되어 같은 이유로 계속 스킵된다.
6. `check-status` API에서 호출한 경우에는 `AddressException`이 `catch (AddressException)`으로 다시 던져져 롤백된다 (`FAS:505-506`). 컨트롤러는 에러코드의 status(404)로 빈 본문을 응답한다 (`FaqAddressCommandController.java:80-86`).

### (b) 즉시 구매로 만들어진 주문: 끝까지 진행된다 (단, 입찰 상태·판매자 알림 제외)
1. 즉시 구매 주문은 `createInstantOrder`가 `PENDING_PAYMENT`로 만들고 상태를 더 진행시키지 않는다 (`FaqCommandService.java:182-186`).
   - 결제 후에도 주문 상태 변경 코드가 없다 (`FaqCommandService.java:305`는 `processPayment`만 호출).
   - `StyleBid.assignOrder(order)`로 판매 입찰은 이미 주문에 붙어 있다 (`FaqCommandService.java:279`).
   - `FaqBid`는 결제 후 만들어지고 `isInstantPurchase=true`가 설정된다 (`domain/faq/service/command/FaqBidCommandService.java:205`).
2. `PENDING_PAYMENT → COMPLETED`는 허용된다 (`FaqStatus.java:24`).
   - `completeOrder`의 `order.updateStatus(COMPLETED)`가 성공한다 (`FAS:204`).
3. 결과는 다음과 같다.
   - `FaqAddress`는 `DELIVERED`, `Faq`는 `COMPLETED`가 된다.
   - 구매자 알림은 2건 간다 ("[completeOrder]…"와 "[배송 완료]…").
   - 판매자 알림은 없다. 결제 시점에 이미 `SOLD`다 (`NotificationCommandService.java:391-404`).
     - 즉시 구매는 결제 시점에 `order.getOrderBid()==null`이어서 `StyleBid`로 판매를 찾아 `SOLD`로 바꾼다.
   - `FaqBid`/`StyleBid`는 `MATCHED`로 남는다 (3장 참조).
4. 즉시 구매 주문에서 `updateTrackingInfo`(PATCH)를 쓰면 `PENDING_PAYMENT → IN_TRANSIT`이 허용되지 않아 (a)와 같은 이유로 실패한다 (`FaqStatus.java:24`, `FAS:260`).

### 차이 요약
| | (a) 일반 구매 입찰 + 실배송 | (b) 즉시 구매 |
|---|---|---|
| 배송 완료 판정 시 주문 상태 | `PREPARING` → `COMPLETED` 불가 | `PENDING_PAYMENT` → `COMPLETED` 가능 |
| 3의 처리 | `completeOrder`에서 예외, 전체 롤백·스킵 | 성공 |
| 구매자 알림 | 0건 | 2건 |

## 5. 실패 처리 (주기 처리 중 한 건이 실패할 때)

- 프로세서가 예외를 던지면 `AddressException`으로 래핑해 재던진다 (`AddressItemProcessor.java:133-145`).
- 스텝은 `faultTolerant().skip(Exception.class).skipLimit(50)`이다 (`UpdateAddressStatusesJobConfig.java:327-329`).
  - 실패한 건은 **스킵**된다. `SkipListener`가 에러 로그만 남긴다 (`UpdateAddressStatusesJobConfig.java:503-539`).
  - 스킵된 건은 쓰이지 않아 DB 상태가 변하지 않고, 다음 주기(6시간 뒤)에 같은 조건으로 다시 조회된다.
  - 나머지 건은 계속 처리되어 정상 건은 `JpaItemWriter`로 저장된다.
- 스킵 한도는 50건이다. 한 번의 실행에서 50건을 넘게 스킵되면 스텝이 실패한다. 그러면 잡이 실패하고 이후 항목은 처리되지 않는다.
- 같은 청크 안에서 `completeOrder`가 같은 트랜잭션을 롤백 마킹하면 청크가 롤백되고 재처리될 수 있다.
  - 이 부분은 Spring Batch의 fault-tolerant 동작에 따른 추론이며, 코드에서 직접 확인한 것은 skip 설정까지다.
  - 한 건의 실패가 같은 청크의 정상 건을 영구히 막지는 않는다.
- 운송장 번호가 비었거나 CJ 조회·HTML 파싱이 실패한 건도 같은 방식으로 스킵된다 (`AddressItemProcessor.java:61-64`, `:172-189`).
- 스케줄러 자체는 `jobLauncher.run` 예외를 `printStackTrace`로만 처리한다 (`AddressBatchScheduler.java:41-43`).
- 참고: 상태가 바뀌는 항목이 조회 조건에서 빠지는데 Reader는 페이지 오프셋 방식이다 (`UpdateAddressStatusesJobConfig.java:346`). 대상이 50건을 넘으면 뒤쪽 페이지의 항목이 한 번의 실행에서 건너뛰어질 수 있다. 이 부분도 코드 구조에서 추론한 것이다.
