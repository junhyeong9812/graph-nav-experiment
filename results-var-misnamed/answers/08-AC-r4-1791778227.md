# 구매자 배송: 운송장 등록 → 배송 완료

약칭: `A` = `src/main/java/com/fream/back/domain/address`, `F` = `src/main/java/com/fream/back/domain/faq`, `S` = `.../domain/style`, `G` = `src/main/java/com/fream/back/global`.
구매자 배송 엔티티는 `FaqAddress`(테이블 `order_shipment`), 주문은 `Faq`(테이블 `orders`), 구매 입찰은 `FaqBid`, 판매 입찰은 `StyleBid`, 판매는 `Style`이다. `domain/shipment`의 `Shipment`는 사용자 주소록이라 이 흐름과 무관하다.

## 0. 전제: 결제·배송 처리 후 상태

- `POST /orders/{orderId}/process-payment-shipment`는 Kafka 이벤트를 발행한다(`F/controller/command/FaqCommandController.java:42,54`).
- 소비 측은 `FaqEventConsumer#processCompleteOrder`다. 결제 → `FaqAddress` 생성(상태 `PENDING`, `A/service/command/FaqAddressCommandService.java:61-68`) → 주문 `PAYMENT_COMPLETED`(`F/service/kafka/FaqEventConsumer.java:195`) → 비창고 주문은 `PREPARING`(`FaqEventConsumer.java:216-217`) 순이다.
- 동기 경로 `FaqCommandService#processPaymentAndShipment`도 같다. 비창고 주문은 `PAYMENT_COMPLETED` → `PREPARING`(`F/service/command/FaqCommandService.java:175-176`)이고, 창고 보관이면 `COMPLETED`까지 간다(`FaqCommandService.java:165-172`).
- 즉 실배송 일반 주문은 결제·배송 처리 후 `PREPARING`에서 멈춘다. 이 상태 값이 아래 1번 이후의 실패 원인이다.
- 주문 상태 허용 전이는 `PREPARING → {IN_WAREHOUSE, SHIPMENT_STARTED}`, `IN_TRANSIT → {COMPLETED}`, `PENDING_PAYMENT → {PAYMENT_COMPLETED, COMPLETED, IN_WAREHOUSE}`다(`F/entity/FaqStatus.java:24-31`). 전이 검증은 `Faq#updateStatus`(`F/entity/Faq.java:166-174`)가 하며, 불허 시 `InvalidFaqStatusException`을 던진다.
- 코드 전체에서 주문을 `SHIPMENT_STARTED`로 바꾸는 곳은 없다(`FaqStatus.SHIPMENT_STARTED`는 `FaqQueryController`의 표시용 switch에만 등장). `PREPARING → IN_TRANSIT` 경로도 없다.

## 1. 운송장 등록 요청

### 1-1. 어느 API로 들어오나

- `PATCH /shipments/order/{shipmentId}/status`, body는 `{courier, trackingNumber}`(`A/controller/command/FaqAddressCommandController.java:20,33-45`, `A/dto/FaqAddressRequestDto.java`).
- 컨트롤러는 `FaqAddressCommandService#updateTrackingInfo(shipmentId, courier, trackingNumber)`를 바로 호출한다. try/catch가 없어 예외는 `GlobalExceptionHandler`로 간다.
- `SecurityConfig`에는 이 경로에 대한 role 제한이 없다(`G/config/security/SecurityConfig.java:51-52`: 화이트리스트 외에는 `authenticated()`만). "운영 측만 호출"은 코드로 강제되지 않는다.
- 같은 서비스에 즉시 조회형 `POST /shipments/order/{id}/check-status`(`FaqAddressCommandController.java:58`)와 `.../check-status-string`(`:103`)도 있다. 운송장을 세팅하고 택배사를 바로 조회한다(`FaqAddressCommandService.java:452-516`).

### 1-2. 상태가 바뀌도록 짜인 순서와 알림 (`FaqAddressCommandService#updateTrackingInfo`, 239-303행)

1. courier·trackingNumber가 null이거나 blank면 `TRACKING_INFO_REQUIRED`(243-246).
2. `FaqAddress` 조회. 없으면 `SHIPMENT_NOT_FOUND`(249-253).
3. `shipment.updateTrackingInfo`가 택배사·운송장을 저장하고 상태를 `IN_TRANSIT`으로 강제 세팅한다(256행, `A/entity/FaqAddress.java:41-45`). 이 메서드는 `canTransitionTo` 검증을 하지 않는다.
4. 주문 `order.updateStatus(IN_TRANSIT)`(260).
5. 구매자에게 알림 1건 "상품이 출발하였습니다. 주문 ID: …"(265-271).
6. `updateSaleStatusToSold(orderId)`(276)로 판매자 쪽 처리. `StyleBid`의 `Style`이 `SOLD`로 전이 가능하면 `SOLD`로 바꾸고, 창고 보관 상품이면 창고 상태를 `SOLD`로 바꾸고, 판매자에게 "상품이 성공적으로 판매 완료되었습니다" 알림을 보낸다(112-183).
7. 창고 보관 `Style`이면 `updateWarehouseStatusToSold` 한 번 더(279-286).
8. `updateOrderAndSaleBidStatusToCompleted`(289)로 `FaqBid`와 `StyleBid`가 `MATCHED`이면 `COMPLETED`로 바꾼다(413-440).

주의: 이 메서드는 운송장 등록 시점에 주문 `COMPLETED`, 판매 `SOLD`, 입찰 `COMPLETED`까지 한 번에 처리하도록 짜여 있다. 메서드 이름·단계 구성상 "출발" 처리지만 실제로는 "배송 완료 상태 처리"까지 포함한다. 단 4번에서 막힌다(1-3).

### 1-3. 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문: 끝까지 성공하지 않는다

- **실패 지점**: 4번 `order.updateStatus(FaqStatus.IN_TRANSIT)`(`FaqAddressCommandService.java:260`).
- **이유**: 주문이 `PREPARING`이고(0절), `PREPARING`의 허용 다음 상태에 `IN_TRANSIT`이 없다(`FaqStatus.java:26`). `Faq#updateStatus`가 `InvalidFaqStatusException`을 던진다(`Faq.java:170-172`).
- **예외 변환**: 이 예외는 `AddressException`이 아니므로 `catch (Exception e)`(295행)에 잡혀 `AddressException(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")`로 바뀌어 던져진다(297-301). 원인은 상태 전이 오류인데 코드는 "배송 정보를 찾을 수 없음"이 된다.
- **저장되는 것**: 없다. `updateTrackingInfo`는 `@Transactional`(238행)이고 예외가 메서드 밖으로 나가므로 롤백된다. 3번에서 세팅한 courier·trackingNumber·`IN_TRANSIT`은 영속화되지 않는다. 5번 알림도 실행 전이라 없다. 실패 시 저장되는 구매자·판매자 알림이나 상태 변경은 없다.
- **응답**: `GlobalExceptionHandler#handleShipmentException`(`G/exception/GlobalExceptionHandler.java:459-473`)이 `AddressErrorCode.SHIPMENT_NOT_FOUND`의 코드 `S001`, 메시지 "배송 정보를 찾을 수 없습니다.", HTTP 404로 응답한다(`A/exception/AddressErrorCode.java:12`). 상세 원인 메시지는 body에 노출되지 않는다.
- **성공하더라도 막히는 뒷단**: 4번을 통과하는 주문(상태가 맞는 예외적 경우)이어도 6번에서 `StyleBidQueryService#findByOrderId`는 연결된 `StyleBid`가 없으면 null이 아니라 `IllegalArgumentException`을 던진다(`S/service/query/StyleBidQueryService.java:26-28`). `updateSaleStatusToSold`의 try/catch는 `FaqBid` 부분만 감싸므로(150-180행) 이 예외는 그대로 위로 올라가 같은 404가 된다. 일반 구매 입찰은 판매자가 `createInstantSaleBid`로 매칭해야만 `StyleBid.order`가 생긴다(`S/service/command/StyleBidCommandService.java:72-84`).

## 2. 배송 완료 감지

### 2-1. 누가, 언제, 어떻게

- **주체**: 스케줄러 `AddressBatchScheduler#scheduleShipmentStatusJob`(`G/config/AddressBatchScheduler.java:34-44`)이 Spring Batch Job `updateShipmentStatusesJob`을 실행한다.
- **주기**: `@Scheduled(cron = "0 0 */6 * * *")`(34행)이므로 매일 0·6·12·18시 정각, 서버 타임존 기준 6시간마다다. 실행 파라미터는 현재 시각 timestamp다(36-38행). 예외는 `printStackTrace()`로만 처리한다(41-43).
- **수동 경로**: 운영 호출 `POST .../check-status`가 단건을 즉시 조회한다(`FaqAddressCommandService.java:452-516`).

### 2-2. 조회 대상 배송

- 리더 `shipmentItemReader`의 JPQL: `SELECT s FROM FaqAddress s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL`(`A/config/UpdateAddressStatusesJobConfig.java:95`). 페이지 크기 50(94행).

### 2-3. 실제 실행되는 처리 코드

비슷한 코드가 4곳 있다. 실제로 실행되는 것은 1번 하나다.

| 후보 | 실제 실행 여부 | 근거 |
|---|---|---|
| `AddressItemProcessor#process` (Playwright로 CJ 조회) | **실행됨** | Step에서 `.processor(new AddressItemProcessor(...))`로 연결(`UpdateAddressStatusesJobConfig.java:69-73`), 본체는 `A/config/AddressItemProcessor.java:352-453` 부근(`process`) |
| `UpdateAddressStatusesJobConfig#shipmentItemProcessor` (같은 클래스 106행의 `@Bean`) | 실행 안 됨 | Step 정의에서 참조하지 않음(69행은 `new AddressItemProcessor`) |
| `FaqAddressCommandService#updateShipmentStatuses` (309-391행) | 실행 안 됨 | `src` 전체에서 호출처 없음(`@Scheduled`는 위 스케줄러 하나뿐이고 이 메서드를 부르지 않음) |
| `UpdateAddressStatusesJobConfig#parseCjLogisticsStatus` (Jsoup, 186행) | 실행 안 됨 | private이며 호출처 없음 |

- 실행 프로세서의 조회 방식: Playwright 새 페이지로 `https://trace.cjlogistics.com/next/tracking.html?wblNo={운송장}`를 열고 `tbody#statusDetail tr`을 기다린다. 렌더링된 HTML을 Jsoup으로 파싱해 **마지막 행의 5번째 `td`**(`get(4)`) 텍스트를 trim해 상태 문자열로 쓴다(`AddressItemProcessor.java:72-95`, 파싱 `:181`). 행이 없거나 빈 문자열이면 `TRACKING_HTML_PARSE_ERROR`다.
- 브라우저는 `BrowserManageStepListener`가 Step 시작에 열고 종료에 닫는다(`BrowserManageStepListener.java:15-24`).

### 2-4. 택배사 문자열 → 내부 상태

`AddressItemProcessor#mapToShipmentStatus`(`AddressItemProcessor.java:220-226`):

- `"배송완료"` → `DELIVERED`
- `"배송출발"` → `OUT_FOR_DELIVERY`
- 그 외 모든 문자열(예: "집화처리", "간선상차", "배달중" 등) → `IN_TRANSIT`

정확 일치 비교다. 부분 문자열이나 공백 차이는 `IN_TRANSIT`으로 처리된다. 현재 상태와 같으면 변경 없이 그대로 반환한다(101행).

## 3. 배송 완료 판정 이후

`AddressItemProcessor#process` `DELIVERED` 분기(`AddressItemProcessor.java:109-118`)의 순서:

1. `orderShipment.updateStatus(DELIVERED)`(113). `IN_TRANSIT`/`OUT_FOR_DELIVERY` → `DELIVERED`는 허용된다(`A/entity/AddressStatus.java:38-50`).
2. `FaqAddressCommandService#completeOrder(orderId)`(116 → `FaqAddressCommandService.java:191-229`):
   1. `FaqBid`를 `orderId`로 조회. 없으면 `IllegalArgumentException`(196-197).
   2. `order.updateStatus(COMPLETED)`(204). `IN_TRANSIT`·`PENDING_PAYMENT`·`IN_WAREHOUSE`에서만 허용된다.
   3. `updateSaleStatusToSold(orderId)`(208): `StyleBid.sale`을 `SOLD`로(`StyleStatus`가 `ON_AUCTION`/`SELLING`일 때만 전이 가능, `S/entity/StyleStatus.java:321-323`), 창고 보관이면 창고 `SOLD`, 판매자 알림 1건.
   4. 구매자 알림 1건 "[completeOrder] 주문이 완료 처리되었습니다"(211-217).
   5. 어떤 예외든 `AddressException(ORDER_NOT_FOUND_FOR_SHIPMENT)`로 변환(221-227).
3. `PaymentCommandService#notifyShipmentCompleted(order)`(117 → `payment/service/command/PaymentCommandService.java:219-234`): 구매자에게 "[배송 완료] …" 알림 1건. 자체 try/catch로 실패는 로그만 남기고 삼킨다.
4. 처리기가 반환한 `FaqAddress`를 `JpaItemWriter`가 저장한다(`UpdateAddressStatusesJobConfig.java:74,241-246`).

### 상태 변화 순서

`FaqAddress`: `DELIVERED` → `Faq`: `COMPLETED` → `Style`: `SOLD`(조건 충족 시) → 창고 `Notice`: `SOLD`(창고 보관 상품일 때).

### 알림

- 구매자: 2건. `[completeOrder]` 1건과 `[배송 완료]` 1건이다.
- 판매자: 0~1건. `Style` 상태가 `SELLING`/`ON_AUCTION`이라 `SOLD`로 전이 가능할 때만 1건이다.
  - 코드에서 `StyleStatus`를 `PENDING_SHIPMENT`와 `SOLD` 외로 세팅하는 곳은 없다.
  - 결제 시점에 이미 판매를 무조건 `SOLD`로 바꾸므로(`notification/service/command/NotificationCommandService.java:383-420`, `S/entity/Style.java:73-75`), 실제로는 이미 `SOLD`인 경우가 많고 그 경우 판매자 알림은 0건이다.
- 총 구매자 2 + 판매자 0~1건이다.

### 입찰 상태

- `completeOrder` 경로에서는 `FaqBid`(주문 입찰)와 `StyleBid`(판매 입찰)의 status를 바꾸지 않는다. 둘 다 `MATCHED`로 남는다.
- `COMPLETED`로 바꾸는 코드는 `updateOrderAndSaleBidStatusToCompleted`(413-440행)뿐이다. 이 private 메서드는 `updateTrackingInfo` 안에서만 호출되고(289행), 1-3에서 본 대로 그 경로는 도달하지 못한다. 배치 경로와 `check-status` 경로는 호출하지 않는다.

## 4. 주문 종류별 차이

### (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문: 끝까지 진행되지 않는다

- 주문은 `PREPARING`(0절)이다.
- 이 주문의 배송은 `updateTrackingInfo`가 롤백되므로(1-3) `IN_TRANSIT`이 되지 않는다. 대상 쿼리(2-2)에 걸릴 수 있는 경로는 `check-status`뿐이다. 거기서 택배사가 "배송완료"가 아니면 `shipment.updateTrackingInfo`가 세팅한 `IN_TRANSIT`이 커밋되기 때문이다(`FaqAddressCommandService.java:473,495-498`).
- 이후 배치가 "배송완료"를 감지하면 3절 2-ii에서 `PREPARING → COMPLETED`가 막힌다(`FaqStatus.java:26`). 설령 통과해도 `StyleBid`가 없으면 `IllegalArgumentException`이다(`StyleBidQueryService.java:26-28`).
- 결과: `completeOrder`가 `AddressException(ORDER_NOT_FOUND_FOR_SHIPMENT)`을 던진다(221-227). 배치는 해당 건을 skip하고 롤백한다. 배송은 `IN_TRANSIT`, 주문은 `PREPARING`, 입찰은 `MATCHED`로 그대로 남고 알림도 생기지 않는다. 6시간마다 같은 실패가 반복된다.
- `check-status` 컨트롤러 경로에서 "배송완료"가 오면 같은 이유로 예외가 나고 컨트롤러가 `AddressException`의 status(여기서는 404, `ORDER_NOT_FOUND_FOR_SHIPMENT`)로 빈 응답을 돌려준다(`FaqAddressCommandController.java:76-83`). 트랜잭션은 롤백된다.

### (b) 즉시 구매로 만들어진 주문: 3의 처리가 끝까지 진행된다

- 즉시 구매는 `createInstantOrder`가 주문을 `PENDING_PAYMENT`로 만들고(`F/service/command/FaqCommandService.java:241-245`), 배송(`PENDING`)을 만들고(264-271), `StyleBid.assignOrder(order)`로 판매 입찰을 주문에 연결한다(279). 주문 입찰은 `MATCHED` + `isInstantPurchase=true`로 생성된다(`F/service/command/FaqBidCommandService.java:189-206`). 이후 주문은 `PREPARING`을 거치지 않고 `PENDING_PAYMENT`에 남는다.
- `PENDING_PAYMENT → COMPLETED`는 허용 전이다(`FaqStatus.java:24`). `FaqBid`와 `StyleBid` 둘 다 `findByOrderId`로 조회되므로 `completeOrder`가 성공한다.
- 도달 조건: 배송이 `IN_TRANSIT`이어야 한다. `PATCH .../status`는 주문이 `IN_TRANSIT`으로 못 가므로(`PENDING_PAYMENT`에서 `IN_TRANSIT` 불허) 실패하고, `check-status`로 운송장을 먼저 세팅해 `IN_TRANSIT`을 커밋시켜야 배치 대상이 된다.
- 결제 시점에 판매가 이미 `SOLD`로 바뀌어 있어서(`NotificationCommandService.java:395-407`) `updateSaleStatusToSold`의 `canTransitionTo(SOLD)`가 false다(`StyleStatus.java:324`). 판매자 알림과 창고 상태 변경은 건너뛴다.
- 결과: `FaqAddress` `DELIVERED`, `Faq` `COMPLETED`, 구매자 알림 2건, 판매자 알림 0건. `FaqBid`와 `StyleBid`는 `MATCHED`로 남는다.

### 차이 요약

| | (a) 일반 구매 입찰 | (b) 즉시 구매 |
|---|---|---|
| 배송완료 판정 시 주문 상태 | `PREPARING` | `PENDING_PAYMENT` |
| `→ COMPLETED` | 불허(실패) | 허용 |
| `StyleBid` 연결 | 판매자 매칭 시에만 | 항상 |
| 결과 | 예외, skip, 롤백, 반복 | 주문 `COMPLETED`, 구매자 알림 2 |

## 5. 실패 처리 (주기 처리 중 한 건 실패)

- Step 설정: `chunk(50)` + `faultTolerant().skip(Exception.class).skipLimit(50)`(`UpdateAddressStatusesJobConfig.java:67,75-77`).
- 한 건이 처리 중 예외를 던지면 그 건만 skip된다. `SkipListener.onSkipInProcess`가 로그만 남긴다(`:251-266`). 예외는 `AddressException`으로 통일된다(`AddressItemProcessor.java:133-145`).
- 해당 청크의 트랜잭션은 롤백된다. `completeOrder`와 `createNotification`은 같은 트랜잭션에 참여하므로 실패 건의 부분 변경과 알림도 함께 롤백된다. 나머지 건은 skip된 건을 제외하고 다시 처리되어 정상 커밋된다. 실패 건은 상태가 그대로이므로 다음 6시간 주기에 다시 대상이 된다.
- 운송장 번호가 null이면 `TRACKING_NUMBER_INVALID`로 skip(`AddressItemProcessor.java:56-60` 부근). 단 쿼리가 이미 `trackingNumber IS NOT NULL`로 걸러서 blank 문자열일 때만 해당한다.
- skip이 50건을 넘으면 `SkipLimitExceededException`으로 Step이 실패하고 남은 건은 처리되지 않는다. 스케줄러는 예외를 `printStackTrace()`로만 처리한다(`AddressBatchScheduler.java:41-43`).
- `OUT_FOR_DELIVERY` 상태 배송에 택배사가 "배송완료"·"배송출발" 이외를 반환하면 `IN_TRANSIT`으로 매핑되는데, `OUT_FOR_DELIVERY → IN_TRANSIT`은 불허라(`AddressStatus.java:45-50`) `IllegalStateException`이 나고 `EXTERNAL_TRACKING_SERVICE_ERROR`로 변환되어 skip된다.
- `JpaPagingItemReader`가 페이징으로 읽는 도중 처리된 건의 status가 바뀌면 조회 결과에서 빠져 이후 페이지의 건이 건너뛰어질 수 있다. 이는 코드 구조에서 추론한 것이고 실행으로 확인하지는 않았다.
- (참고) 실제로 쓰이지 않는 `FaqAddressCommandService#updateShipmentStatuses`는 건별 `try/catch`로 실패 건을 세고 계속 진행하도록 짜여 있다(383-387행). 하지만 호출되지 않으므로 실제 동작이 아니다.
