# 구매자 배송: 운송장 등록 → 배송 완료

> 경로 접두어 `B/` = `src/main/java/com/fream/back/`.
> 클래스 이름이 도메인과 어긋나 있다. `Faq`=주문(Order, 테이블 `orders`), `FaqAddress`=구매자 배송(OrderShipment, 테이블 `order_shipment`), `FaqBid`=구매 입찰(OrderBid), `StyleBid`=판매 입찰(SaleBid), `Style`=판매(Sale), `Product`=사용자, `Payment`=알림 엔티티, `Notification`=결제 엔티티.
> `FaqAddressCommandService`의 필드 `notificationCommandService`의 실제 타입은 `PaymentCommandService`이며 알림 생성기다 (`B/domain/address/service/command/FaqAddressCommandService.java:39`).

## 0. 사전: 결제·배송 처리 후 상태

- 배송 정보는 `PENDING`으로 생성된다 (`B/domain/address/service/command/FaqAddressCommandService.java:55-76`, builder의 `.status(AddressStatus.PENDING)`).
- 일반 구매 입찰 주문은 `PENDING_PAYMENT`로 생성된다 (`B/domain/faq/service/command/FaqCommandService.java:76-82`, `createOrderFromBid`).
- 입찰은 `FaqBid`가 `PENDING`으로 생성된다 (`B/domain/faq/service/command/FaqBidCommandService.java:90-97`).
- 결제·배송 처리 `processPaymentAndShipment`(`B/domain/faq/service/command/FaqCommandService.java:111-202`)는 실배송(창고보관 아님)일 때 주문을 `PAYMENT_COMPLETED` → `PREPARING`까지만 올린다 (`FaqCommandService.java:174-177`). 따라서 **(a) 주문의 최종 상태는 `PREPARING`** 이다.
  - 같은 처리에서 입찰 `MATCHED` 처리는 `orderBidQueryService.findById(orderId)` 이다 (`FaqCommandService.java:188-190`). 주문 ID로 입찰을 PK 조회하므로 ID가 우연히 같을 때만 맞는다. 그리고 `findById`는 `orderBidRepository.findById(id)` 이다 (`B/domain/faq/service/query/FaqBidQueryService.java:37-42`).
  - 이 입찰은 `order.getSale()`이 없다 (판매 연결 없음).
- Kafka 경로(`FaqEventConsumer.processCompleteOrder`)도 실배송이면 `PAYMENT_COMPLETED` → `PREPARING`에서 끝난다 (`B/domain/faq/service/kafka/FaqEventConsumer.java:192-195, 214-219`).
- `FaqStatus.SHIPMENT_STARTED`를 세팅하는 코드는 코드베이스에 없다. enum 정의와 전이표 뿐이다 (`B/domain/faq/entity/FaqStatus.java:13, 26-28`).
- 즉시 구매 주문(b)은 `PENDING_PAYMENT`로 생성된 뒤 **상태가 전혀 바뀌지 않는다** (`FaqCommandService.java:241-245`, 이후 결제 `:305`에서도 주문 상태 변경 없음). `FaqBid`는 `MATCHED` + `markAsInstantPurchase()`로 생성된다 (`FaqBidCommandService.java:189-206`, `B/domain/faq/entity/FaqBid.java:97-99`).

## 1. 운송장 등록 요청

### 1-1. 진입 API
- `PATCH /shipments/order/{shipmentId}/status`, 바디 `FaqAddressRequestDto{courier, trackingNumber}` (`B/domain/address/controller/command/FaqAddressCommandController.java:20, 33-37`).
- 컨트롤러는 `FaqAddressCommandService.updateTrackingInfo(shipmentId, courier, trackingNumber)`를 호출하고 성공 시 `200 OK` 빈 본문을 준다 (`FaqAddressCommandController.java:41-48`).
- 이 경로엔 별도 권한 제한이 없고 `anyRequest().authenticated()`뿐이다 (`B/global/config/security/SecurityConfig.java:50-52`).
- 참고로 `POST /shipments/order/{id}/check-status`, `/check-status-string`은 운송장을 등록하고 곧바로 택배사를 조회해 상태를 갱신하는 별도 API다 (`FaqAddressCommandController.java:58-94, 103-138`, 서비스 `FaqAddressCommandService.java:451-513`).

### 1-2. 코드가 의도한 순서 (`FaqAddressCommandService.updateTrackingInfo`, `:238-297`)
1. 택배사/운송장 공백 검증 → 없으면 `TRACKING_INFO_REQUIRED` (`:242-246`).
2. 배송 조회 (`:249-253`), 없으면 `SHIPMENT_NOT_FOUND`.
3. **배송(`FaqAddress`)**: `updateTrackingInfo`가 courier/trackingNumber 저장 + 상태를 `IN_TRANSIT`으로 **전이 검증 없이 직접 대입** (`:256`, `B/domain/address/entity/FaqAddress.java:41-45`).
4. **주문(`Faq`)**: `order.updateStatus(IN_TRANSIT)` (`FaqAddressCommandService.java:259-260`).
5. **알림**: 구매자(`order.getUser()`)에게 "상품이 출발하였습니다. 주문 ID: …" 1건 (`:263-270`).
6. `updateSaleStatusToSold(orderId)` (`:276`): 판매(`Style`)를 `SOLD`로 바꾸고 판매자에게 "판매 완료" 알림, 창고보관이면 창고 상태도 변경 (`:111-181`).
7. 창고보관 판매면 창고 상태를 한 번 더 `SOLD`로 (`:279-286`).
8. `updateOrderAndSaleBidStatusToCompleted(orderId)` (`:289`): `FaqBid` / `StyleBid`가 `MATCHED`면 `COMPLETED`로 (`:413-440`).

즉 의도는 "운송장 등록 시점에 이미 판매 SOLD, 입찰 COMPLETED"까지 처리하는 것으로 보인다. 메서드/주석(출발 알림)과 실제 효과(판매·입찰 완료)가 어긋난다.

### 1-3. (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문 → **성공하지 못한다**
- 주문 상태가 `PREPARING`이라 `PREPARING → IN_TRANSIT`은 허용 전이가 아니다. `PREPARING`의 허용 집합은 `{IN_WAREHOUSE, SHIPMENT_STARTED}` (`B/domain/faq/entity/FaqStatus.java:26`), `IN_TRANSIT`은 `SHIPMENT_STARTED`에서만 갈 수 있다 (`:28`).
- 실패 위치: `FaqAddressCommandService.java:260` `order.updateStatus(FaqStatus.IN_TRANSIT)` → `Faq.updateStatus`가 `InvalidFaqStatusException("상태 전환이 허용되지 않습니다: PREPARING -> IN_TRANSIT")`을 던진다 (`B/domain/faq/entity/Faq.java:113-121`).
- 이 예외는 `AddressException`이 아니므로 `catch (Exception e)`에 잡혀 `AddressException(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")`로 포장되어 다시 던져진다 (`FaqAddressCommandService.java:293-300`). 에러코드 이름은 "배송 없음"이지만 실제 원인은 주문 상태 전이 불가다.
- **저장되는 것: 없음.** `updateTrackingInfo`는 `@Transactional`이고(`:238`) `AddressException`은 `RuntimeException`(`B/global/exception/GlobalException.java:10`)이라 트랜잭션이 롤백된다.
  - 3단계에서 메모리상 바꾼 배송의 courier/trackingNumber/`IN_TRANSIT`도 DB에 반영되지 않는다.
  - 5단계 알림은 4단계에서 이미 터졌기 때문에 생성되지 않는다.
- **응답:** `GlobalExceptionHandler.handleGlobalException`이 `AddressErrorCode.SHIPMENT_NOT_FOUND`의 HTTP **404**, 코드 `S001`, 메시지 "배송 정보를 찾을 수 없습니다."의 `ErrorResponse`를 반환한다 (`B/global/exception/GlobalExceptionHandler.java:49-62`, `B/domain/address/exception/AddressErrorCode.java:61`). 상세 메시지(`상태 전환이 허용되지 않습니다…`)는 응답 본문이 아니라 로그에만 남는다 (핸들러가 `errorCode.getMessage()`를 쓴다).
- 일반화: 주문 상태가 `SHIPMENT_STARTED`가 아닌 이상 이 API는 항상 실패한다. `SHIPMENT_STARTED`로 보내는 코드가 없으므로 사실상 `status == null`이 아니면 성공 경로가 없다.

## 2. 배송 완료 감지

### 2-1. 누가, 언제
- 주체는 Spring `@Scheduled` + Spring Batch Job이다. `AddressBatchScheduler.scheduleShipmentStatusJob()`이 `updateShipmentStatusesJob`을 `jobLauncher.run`으로 실행한다 (`B/global/config/AddressBatchScheduler.java:34-40`).
- **주기: `cron = "0 0 */6 * * *"`, 6시간마다 (00/06/12/18시 정각)** (`AddressBatchScheduler.java:34`). 실행마다 `timestamp` 잡 파라미터를 넣어 새 JobInstance로 돈다 (`:37-39`).
- 사용자 호출 경로로는 `POST …/check-status`가 단건 즉시 조회를 한다 (1-1 참고). 그 외 호출자는 없다.

### 2-2. 대상 배송
- Reader: `JpaPagingItemReader`, JPQL `SELECT s FROM FaqAddress s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL`, pageSize 50 (`B/domain/address/config/UpdateAddressStatusesJobConfig.java:87-97`, `CHUNK_SIZE = 50` `:51`).
- 정렬이 없고 페이징 중에 대상 상태가 바뀌므로(완료되면 조건에서 빠짐) 뒤쪽 페이지 건이 건너뛰어질 수 있다. 이는 코드 구조에서 추론한 것이다.

### 2-3. 실제 실행되는 처리 코드
- Step은 `.processor(new AddressItemProcessor(playwrightBrowserManager(), notificationService, orderService))`를 쓴다 (`UpdateAddressStatusesJobConfig.java:66-73`). **실제로 실행되는 것은 `B/domain/address/config/AddressItemProcessor.java:57`의 `process()`** 이다.
- 같은 설정 클래스의 `shipmentItemProcessor()` 빈(`:104-177`)과 `parseCjLogisticsStatus`(`:186-220`, Jsoup 방식)는 Step에 연결되어 있지 않아 실행되지 않는다. 사실상 사본 코드다.
- `FaqAddressCommandService.updateShipmentStatuses()` (`FaqAddressCommandService.java:308-396`)는 호출하는 곳이 없다 (`@Scheduled`도 없고 Job에서도 부르지 않음). 이 메서드는 주문을 `COMPLETED`로 만들고 알림 1건만 보내는 다른 로직이지만 **실행되지 않는다**.
- `AddressItemProcessor.process`는 Playwright로 CJ 대한통운 페이지(`https://trace.cjlogistics.com/next/tracking.html?wblNo=<운송장>`)를 열고(`AddressItemProcessor.java:28, 81-83`), `tbody#statusDetail tr`을 기다린 뒤(`:87`) 마지막 행의 5번째 `td` 텍스트를 상태 문자열로 읽는다 (`:181`).
- 택배사와 무관하게 운송장 번호를 항상 CJ 대한통운에서 조회한다 (`courier` 값은 조회에 쓰이지 않는다).

### 2-4. 택배사 문자열 → 내부 상태 (`AddressItemProcessor.mapToShipmentStatus`, `:220-226`)
| 택배사 문자열 | 내부 `AddressStatus` |
|---|---|
| `"배송완료"` (정확히 일치) | `DELIVERED` |
| `"배송출발"` (정확히 일치) | `OUT_FOR_DELIVERY` |
| 그 외 전부 | `IN_TRANSIT` |

공백 trim만 한 뒤(`:181`) 완전 일치로 비교하므로 표기가 조금만 달라도(예: "배송 완료") `IN_TRANSIT`으로 떨어진다.

## 3. 배송 완료 판정 이후 (`AddressItemProcessor.process`, `:101-126`)

현재 상태와 같으면 변경 없음(`:101-106`). `DELIVERED`일 때의 순서:
1. **배송** `FaqAddress.updateStatus(DELIVERED)` (`:113`). `IN_TRANSIT`/`OUT_FOR_DELIVERY`에서만 가능 (`B/domain/address/entity/AddressStatus.java:72-84`, `FaqAddress.java:47-55`).
2. `FaqAddressCommandService.completeOrder(orderId)` (`:116`, 본체 `FaqAddressCommandService.java:190-224`):
   1. `FaqBid`를 `findByOrderId`로 조회, 없으면 `IllegalArgumentException` (`:196-197`).
   2. **주문** `order.updateStatus(COMPLETED)` (`:204`). 허용 전이는 `IN_TRANSIT`, `IN_WAREHOUSE`, `PENDING_PAYMENT`에서만 (`FaqStatus.java:24, 27, 29`).
   3. `updateSaleStatusToSold(orderId)` (`:208`): 판매 `Style`을 `SOLD`로(`Style.updateStatus`는 검증 없이 대입, `B/domain/style/entity/Style.java:73-75`) + 판매자에게 알림 + 창고보관 상태 변경. 단 `canTransitionTo(SOLD)`가 참인 경우에만 (`:111-181`).
   4. 구매자에게 "[completeOrder] 주문이 완료 처리되었습니다. 주문 ID: …" 알림 (`:211-217`).
3. `PaymentCommandService.notifyShipmentCompleted(order)` (`:117`): 구매자에게 "[배송 완료] 상품이 배송 완료되었습니다. 주문 ID: …" (`B/domain/payment/service/command/PaymentCommandService.java:219-234`, 내부 예외는 삼킴).
4. Step 쓰기: `JpaItemWriter`가 배송 엔티티를 저장 (`UpdateAddressStatusesJobConfig.java:239-246`).

### 알림 건수 (정상적으로 끝까지 가는 경우)
- **구매자: 2건** ("[completeOrder] 주문이 완료 처리되었습니다" + "[배송 완료] 상품이 배송 완료되었습니다").
- **판매자: 조건부 0~1건** ("상품이 성공적으로 판매 완료되었습니다. 판매 ID: …"). 판매가 아직 `SOLD`가 아니고 `SOLD`로 전이 가능할 때만 간다. `canTransitionTo(SOLD)`는 `ON_AUCTION`, `SELLING`에서만 true (`B/domain/style/entity/StyleStatus.java:221-223`).
- `updateSaleStatusToSold`의 두 번째 블록(`FaqBid` 기반, `:150-178`)은 같은 `Style`을 보고 이미 `SOLD`가 되었으므로 중복 알림을 만들지 않는다.

### 입찰 상태
- `completeOrder`는 `FaqBid`/`StyleBid` 상태를 바꾸지 않는다 (`FaqAddressCommandService.java:190-224`). `COMPLETED`로 바꾸는 `updateOrderAndSaleBidStatusToCompleted`는 `updateTrackingInfo`(`:289`)에서만 호출된다.
- 따라서 배송 완료 판정 이후에도 **주문 입찰(`FaqBid`)과 판매 입찰(`StyleBid`)은 `MATCHED` 그대로**이고 `COMPLETED`가 되지 않는다. 이 메서드는 운송장 등록 단계에서만 호출되는데, 그 단계는 1-3대로 실패한다.
- 참고: 그 메서드는 `private` + `@Transactional`이라 프록시를 타지 않고 내부 `catch (Exception)`이 모든 오류를 삼킨다 (`:412-440`).

## 4. 주문 종류별 차이

배송 완료 감지 대상이 되려면 배송이 `IN_TRANSIT`/`OUT_FOR_DELIVERY`여야 한다. 그런데 PATCH 등록은 (a)·(b) 모두 막힌다(주문이 `PREPARING` / `PENDING_PAYMENT`라서 `IN_TRANSIT` 전이 불가). 배송을 이 상태로 만드는 경로는 `check-status`뿐이다. `shipment.updateTrackingInfo`가 `IN_TRANSIT`을 세팅하고(`FaqAddressCommandService.java:473`), 택배사가 "배송출발"이면 `OUT_FOR_DELIVERY`로 커밋된다 (`:492-494`). 아래는 배송이 이미 `IN_TRANSIT`/`OUT_FOR_DELIVERY`로 잡혀 있고 택배사가 "배송완료"를 준다고 가정한 코드 동작이다.

### (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문 → **끝까지 진행되지 않는다**
- `FaqBid`는 있으므로 `completeOrder`는 `order.updateStatus(COMPLETED)`까지 도달하지만, 주문이 `PREPARING`이라 `PREPARING → COMPLETED`가 불허 → `InvalidFaqStatusException` (`FaqStatus.java:26`, `Faq.java:113-121`).
- `completeOrder`의 `catch (Exception)`이 `AddressException(ORDER_NOT_FOUND_FOR_SHIPMENT)`로 포장해 던진다 (`FaqAddressCommandService.java:221-224`).
- 결과: 구매자·판매자 알림 0건, 주문 `PREPARING` 유지, 입찰 `MATCHED` 유지, 배송 `DELIVERED` 변경도 롤백되어 `IN_TRANSIT`/`OUT_FOR_DELIVERY` 유지. 6시간마다 동일하게 재시도하고 매번 실패해 skip된다 (5번 참고).
- 추가로, `StyleBid`가 주문에 연결되지 않은(판매자가 매칭하지 않은) 일반 입찰이면 `updateSaleStatusToSold`의 `saleBidQueryService.findByOrderId`가 null이 아니라 `IllegalArgumentException`을 던진다 (`B/domain/style/service/query/StyleBidQueryService.java:25-29`). 이 경우에도 `FaqAddressCommandService.java:116`에서 실패한다. `if (saleBid != null)` 분기(`:117`)는 사실상 죽은 코드다.
- `check-status` API로 호출해도 동일하게 `completeOrder`가 예외를 던져 롤백된다 (`FaqAddressCommandService.java:489, 505-507`).

### (b) 즉시 구매로 만들어진 주문 → **끝까지 진행된다**
- `FaqBid`가 있고(`FaqBidCommandService.java:189-206`) `StyleBid`에 주문이 연결돼 있으며(`FaqCommandService.java:279`), 주문이 `PENDING_PAYMENT`라서 `PENDING_PAYMENT → COMPLETED`가 허용된다 (`FaqStatus.java:24`).
- 판매는 결제 시점에 이미 `SOLD`로 바뀌어 있다. 즉시 구매 결제 중 `processPayment` → `notifyUsersAndUpdateSaleStatus`가 `sale.updateStatus(SOLD)`를 실행한다 (`B/domain/notification/service/command/NotificationCommandService.java:83, 388-407, 419`; 호출 시점은 `FaqCommandService.java:305`). 그래서 `updateSaleStatusToSold`의 `canTransitionTo(SOLD)`가 거짓이라 판매 상태 변경과 판매자 알림은 **생략**된다.
- 결과:
  - 배송 `DELIVERED`, 주문 `PENDING_PAYMENT → COMPLETED` (주문이 `IN_TRANSIT`을 거치지 않고 바로 `COMPLETED`).
  - 구매자 알림 2건. 판매자 완료 알림 0건 (판매자는 결제 시점에 "구매자가 결제를 완료하였습니다"를 이미 받았다, `NotificationCommandService.java:447-455`).
  - 주문 입찰·판매 입찰 `MATCHED` 유지 (`COMPLETED` 안 됨).
- 같은 이유로 PATCH 운송장 등록은 (b)에서도 `PENDING_PAYMENT → IN_TRANSIT` 불허로 실패한다 (`FaqStatus.java:24`, 허용 집합에 `IN_TRANSIT` 없음).

### 차이 요약
| 구분 | 주문 상태 | `FaqBid` | 배송 완료 판정 처리 |
|---|---|---|---|
| (a) 일반 구매 입찰 실배송 | `PREPARING` | 있음, 판매 연결 없음 | `PREPARING→COMPLETED` 불허로 실패, 전부 롤백 |
| (b) 즉시 구매 | `PENDING_PAYMENT` | 있음, `MATCHED`, 즉시구매 플래그 | `COMPLETED`로 성공, 구매자 2건 |

## 5. 실패 처리 (주기 처리 중 한 건 실패)

- Step이 `.faultTolerant().skip(Exception.class).skipLimit(50)`이다 (`UpdateAddressStatusesJobConfig.java:75-77`, `SKIP_LIMIT = 50` `:52`). 청크 크기는 50 (`:67`).
- 프로세서에서 예외가 나면 (`AddressItemProcessor`가 `AddressException`으로 포장해 던짐, `:129-141`) 그 건은 **skip**되고 `shipmentSkipListener`가 에러 로그만 남긴다 (`UpdateAddressStatusesJobConfig.java:251-266`).
- 청크는 하나의 트랜잭션이므로 실패 시 해당 청크가 롤백된 뒤 항목별로 다시 처리된다. 실패한 건의 변경(배송 `DELIVERED`, 주문 `COMPLETED`, 같은 트랜잭션에서 저장한 알림 행)은 반영되지 않는다. 나머지 건은 성공하면 정상 저장된다. 이는 Spring Batch fault-tolerant chunk 의 일반 동작이며 코드에 별도 재시도·보상 로직은 없다.
- 실패한 건은 DB 상태가 그대로(`IN_TRANSIT`/`OUT_FOR_DELIVERY`)라 다음 6시간 주기에 다시 조회된다.
- 실시간 WebSocket 전송(`sendRealTimeNotification`, `PaymentCommandService.java:57`)은 DB 롤백과 무관하게 이미 나갔을 수 있다 (추론).
- skip 건수가 50을 넘으면 `SkipLimitExceededException`으로 Step/Job이 실패하고 남은 건은 처리되지 않는다. (a)처럼 매번 실패하는 건이 50건 이상 쌓이면 정상 건도 막힌다.
- 스케줄러는 `jobLauncher.run` 예외를 `printStackTrace()`로만 처리하며 재시도는 없다 (`AddressBatchScheduler.java:41-43`).
- (미사용 코드) 서비스의 `updateShipmentStatuses()`는 건별 `try/catch`로 실패 건만 `errorCount++`하고 계속 진행하는 구조지만 호출되지 않는다 (`FaqAddressCommandService.java:308-396`, 특히 `:383-386`).
