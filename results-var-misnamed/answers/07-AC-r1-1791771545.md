# 즉시 구매(POST /order-bids/instant) 처리 흐름

> 용어: 클래스명은 `Faq`=주문(Order, 테이블 `orders`), `FaqBid`=구매 입찰, `StyleBid`=판매 입찰(`sale_bid`), `Style`=판매 상품, `Notification`=결제(테이블 `payment`), `Payment`=사용자 알림.

## 1. 진입 API, 처리 단계, 동기/비동기, 응답 ID

1. 진입점: `POST /order-bids/instant` (클래스 `@RequestMapping("/order-bids")` + `@PostMapping("/instant")`).
   - 근거: `src/main/java/com/fream/back/domain/faq/controller/command/FaqBidCommandController.java:22`, `:89-90`
   - 요청 바디 `InstantFaqRequestDto`: saleBidId, addressId, warehouseStorage, paymentRequest — `src/main/java/com/fream/back/domain/faq/dto/InstantFaqRequestDto.java:20-29`
2. 컨트롤러 단계
   - 이메일 추출 `FaqBidCommandController.java:92`
   - `enrichPaymentRequest`로 paymentRequest의 userEmail=로그인 이메일, orderId=null 세팅 `:98`, `:119-123`
   - `createInstantOrderBid(...)` 호출 `:101-107`
3. `FaqBidCommandService#createInstantOrderBid` (`@Transactional`, `FaqBidCommandService.java:118-149`)
   1. 입력 검증 `:123`, `:154-167`
   2. 구매자 조회 `:126`
   3. 판매 입찰 조회 + sale 존재 검증 `:129`, `:172-184` (판매 입찰의 status는 검증하지 않는다. 이미 MATCHED인 입찰도 통과)
   4. `FaqCommandService#createInstantOrder` 호출 `:133-139`
   5. 반환된 주문으로 `FaqBid` 생성·저장 `:142`, `:189-207`
4. `FaqCommandService#createInstantOrder` (`@Transactional`, `src/main/java/com/fream/back/domain/faq/service/command/FaqCommandService.java:219-319`): 배송지 조회 `:238` → 주문 저장 `:241-247` → 결제 요청에 orderId 세팅 `:250` → 주문 항목 `:255-256` → 배송 정보 `:264-271` → 판매 입찰 매칭 `:279-283` → 창고 상태 `:291-294` → 결제 `:305`.
5. **동기 처리**다. Kafka 발행 없이 한 HTTP 요청·한 트랜잭션 안에서 DB 저장, PortOne 호출, 알림 생성까지 끝내고 `200 OK`를 돌려준다 (`FaqBidCommandController.java:109`). 비동기(Kafka, 202 ACCEPTED)는 별도 경로 `POST /orders/{orderId}/process-payment-shipment`(`src/main/java/com/fream/back/domain/faq/controller/command/FaqCommandController.java:42-69`)이며 즉시 구매는 이 경로를 쓰지 않는다. `createInstantOrder`의 유일한 호출처는 `FaqBidCommandService.java:133`이다. (`processPayment`는 Kafka consumer `FaqEventConsumer.java:171`, `NotificationEventConsumer.java:86`에서도 호출되지만 이는 비동기 경로다.)
6. **응답 ID**: 변수명은 `orderId`지만 `createInstantOrderBid(...).getId()`, 즉 **새로 만든 `FaqBid`(구매 입찰)의 ID**이다. 주문(`Faq`) ID가 아니다 (`FaqBidCommandController.java:101-109`, 반환 타입 `FaqBid` `FaqBidCommandService.java:119`, `:142-144`). 응답 메시지는 "즉시 구매가 성공적으로 처리되었습니다."이다.

## 2. 새로 생기는 엔티티와 상태 변화 순서

| 순서 | 동작 | 직후 상태 | 근거 |

| 3 | `FaqAddress`(주문 배송정보) 생성. 저장된 배송지 ID로 조회한 수령인·전화·우편번호·주소 사용 | (상태 필드 없음) | `:238`, `:264-271` |
| 4 | `StyleBid.assignOrder(order)` 후 `updateStatus(MATCHED)`, flush | StyleBid.status = `MATCHED`, order 연결 | `:279-283`, `src/main/java/com/fream/back/domain/style/entity/StyleBid.java:259-262` |
| 5 | `sale.isWarehouseStorage()`(판매자 쪽 플래그)가 true면 창고 Notice 상태 변경 | Notice.status = `ASSOCIATED_WITH_ORDER` | `FaqCommandService.java:291-294`, `src/main/java/com/fream/back/domain/notice/service/command/NoticeCommandService.java:117-133` |

- 7번에서 `Style`은 `StyleStatus.SOLD`로 바뀐다. `Style#updateStatus`는 전이 검증 없이 대입한다 (`src/main/java/com/fream/back/domain/style/entity/Style.java:73-74`).
- `FaqBid`는 마지막에 만들어지므로, 7번 시점에는 `order.getOrderBid()`가 null이다. 그래서 `saleBidQueryService.findByOrderId`로 판매 입찰을 찾아 sale을 얻는다 (`NotificationCommandService.java:388-401`). 4번 flush 덕분에 조회된다.
- 이 흐름에서는 `order.updateStatus(...)`가 한 번도 호출되지 않는다 (5절).

## 3. 결제 수단별 결과, 성공 여부, 카드 실패 시

`NotificationCommandService#processPayment`가 `getResolvedPaymentType()`으로 분기한다 (`NotificationCommandService.java:67-80`). 공통 검증은 orderId 일치, 이메일 일치, paidAmount>0뿐이다 (`:117-146`). 결제액이 판매 입찰가와 같은지는 검증하지 않는다 (`totalAmount`는 입찰가, 결제액은 요청값).

| 수단 | 처리 | 결제 상태 | 근거 |
|---|---|---|---|
| CARD | 저장된 카드정보 조회 → PortOne `processCardPayment` 실제 호출 | 응답 `status`=="success"면 `PAID`+isSuccess=true, 그 외에는 기본값 `PENDING`, isSuccess=false 그대로 저장 | `:164-208`, 기본값 `src/main/java/com/fream/back/domain/notification/entity/Notification.java:38-44` |
| ACCOUNT | 은행명(`Bank` enum)만 검증, PG 호출 없음 | 항상 `PENDING`, 입금 확인 로직 없음 | `:243-262` |
| GENERAL | impUid 필수, PG 재검증 없이 요청값 신뢰 | 즉시 `PAID`, isSuccess=true | `:297-316` |

**끝까지 성공하는가**: 위 분기들에서 예외가 없으면 3수단 모두 같은 HTTP 200 / 같은 후속 처리(판매 입찰 MATCHED, sale SOLD, 알림 발송)로 끝난다. 계좌이체는 입금 전(PENDING)인데도 sale이 SOLD 되고 "결제가 완료되었습니다" 알림이 나간다. 결제 상태가 PENDING에서 PAID로 바뀌는 코드는 이 흐름에 없다.

**카드 결제 실패 시** (두 경우로 갈린다):
1. PortOne HTTP가 200이 아니거나 JSON `code`가 0이 아니면 `NotificationProcessingException`을 던진다 (`PortOneApiClient.java:270-275`). 이는 `NotificationException`이므로 `createCardPayment`·`processPayment`가 그대로 다시 던진다 (`NotificationCommandService.java:180-181`, `:218-219`, `:89-94`). `FaqCommandService`가 `FaqNotificationProcessingFailedException`으로 감싸고 (`:304-309`), `FaqBidCommandService`가 `FaqException`이라 그대로 다시 던진다 (`:145-147`, `:212-214`). `GlobalException`은 RuntimeException이므로 (`src/main/java/com/fream/back/global/exception/GlobalException.java:10-12`) 트랜잭션 전체가 롤백된다. 주문, 항목, 배송정보, 판매 입찰 MATCHED, 창고 상태 변경이 모두 취소되고 에러 응답이 나간다. `RestClientException`은 `NotificationApiException`이 되어 `@Retryable`(3회, `PortOneApiClient.java:224-228`) 대상이다.
2. **PortOne이 `code=0`으로 응답하고 결제 `status`만 `success`가 아닌 경우**(승인 실패를 status로 알리는 응답): 예외가 없다. 카드 결제는 `PENDING`/isSuccess=false로 저장되고 (`NotificationCommandService.java:203-208`) 그대로 진행한다. 판매 입찰은 MATCHED, sale은 `SOLD`가 되고 구매자·판매자에게 "결제가 완료되었습니다" 알림이 나가며 HTTP 200으로 응답한다 (`:83`, `:383-420`). 실패한 결제가 성공으로 처리되는, 코드상 실제 동작이다. `NotificationStatus.FAILED`로 저장하는 코드는 없다.

## 4. 알림 수신자, 시점, 전달 방식

1. 수신자와 문구 (`NotificationCommandService#sendNotifications`, `:434-461`)
   - 구매자(`order.getUser()`): "결제가 완료되었습니다. 주문 ID: {orderId}" `:436-443`
   - 판매자(`sale.getSeller()`): "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}" `:447-454`
   - 둘 다 카테고리 SHOPPING, 타입 BID.
2. 시점: 결제 엔티티 저장 직후, 같은 요청·같은 트랜잭션 안에서 동기로 만든다 (`:83`, `:403`/`:416`). 이후 sale을 SOLD로 바꾼다 (`:404`, `:419`). 즉 요청 응답 이전이다.
3. 전달 방식 (`src/main/java/com/fream/back/domain/payment/service/command/PaymentCommandService.java:44-59`, `:303-322`)
   - `Payment` 엔티티로 DB 저장 (`:52-53`)
   - 사용자의 Redis 키 `WebSocket:Product:{email}`가 있을 때만 WebSocket `/user/queue/notifications`로 실시간 push (`:37-38`, `:307-313`). 연결이 없으면 저장만 되고 push는 없다 (`:320-321`).
   - Kafka, 이메일은 쓰지 않는다.
4. 알림 생성 실패는 로그만 남기고 삼킨다 (`NotificationCommandService.java:457-460`, `:421-425`). 알림이 실패해도 주문은 성공으로 끝난다. 이 알림은 트랜잭션 안에서 저장되므로 이후 롤백되면 같이 사라진다.

## 5. 최종 주문 상태와 창고 보관

1. **주문(`Faq`)의 최종 상태는 `PENDING_PAYMENT`**이다. 즉시 구매 경로(`createInstantOrder`, `createInstantOrderBid`, `processPayment`)에는 `Faq#updateStatus` 호출이 없고, 상태를 올리는 호출은 다른 경로(`FaqCommandService.java:165-177` = `process-payment-shipment` 경로, `FaqEventConsumer.java:195-217`)에만 있다. 결제가 PAID여도 주문은 PAYMENT_COMPLETED가 되지 않는다. 함께 확인할 최종 값: StyleBid=MATCHED, FaqBid=MATCHED(즉시구매 플래그 true), Style=SOLD, 결제=PAID/PENDING(수단별).
2. **구매자의 `warehouseStorage` 선택은 이 흐름에서 쓰이지 않는다.** 컨트롤러는 값을 넘기지만 (`FaqBidCommandController.java:105`) `createInstantOrder`는 `isWarehouseStorage` 파라미터를 본문에서 한 번도 읽지 않는다 (`FaqCommandService.java:220-318`). 창고 Notice를 새로 만들거나(`createOrderStorage`) 주문을 IN_WAREHOUSE/COMPLETED로 보내는 코드(`:163-172`)는 `processPaymentAndShipment` 경로에만 있다.
3. 대신 영향을 주는 것은 **판매자 쪽 플래그** `sale.isWarehouseStorage()`이다. 이 값이 true이면 해당 sale의 창고 Notice를 `ASSOCIATED_WITH_ORDER`로 바꾼다 (`FaqCommandService.java:291-294`). 창고 정보가 없으면 `NoticeNotFoundException`이 나고 (`src/main/java/com/fream/back/domain/notice/service/query/NoticeQueryService.java:30-32`) `FaqNoticeProcessingFailedException`으로 감싸져 (`FaqCommandService.java:295-300`) 전체 롤백된다. 플래그가 false이면 창고 처리는 없다.
4. 따라서 구매자가 창고 보관을 선택해도 선택 안 해도 주문 최종 상태·배송정보 생성은 동일하다 (`PENDING_PAYMENT`, 배송지 ID로 조회한 `FaqAddress` 생성 `:264-271`).
