# 즉시 구매 처리 흐름

> 클래스 이름이 실제 도메인과 어긋나 있다. 코드 기준 대응은 다음과 같다.
> `Faq`=주문(테이블 `orders`), `FaqBid`=구매 입찰(`order_bid`), `Style`=판매(상품), `StyleBid`=판매 입찰(`sale_bid`),
> `Notification`=결제(테이블 `payment`), `Payment`=사용자 알림, `Notice`=창고 보관, `FaqAddress`=주문 배송지.
> (`src/main/java/com/fream/back/domain/` 아래. 아래 경로는 이 디렉터리 기준으로 줄여 쓴다.)

기준 경로 접두어: `src/main/java/com/fream/back/domain/`

## 1. 진입 API, 처리 단계, 동기/비동기, 응답 ID

**API**: `POST /order-bids/instant`
- `faq/controller/command/FaqBidCommandController.java:22` (`@RequestMapping("/order-bids")`), `:89` (`@PostMapping("/instant")`), `:90` (`createInstantOrderBid`)
- 요청 본문 `InstantFaqRequestDto`: `saleBidId`, `addressId`, `warehouseStorage`, `paymentRequest` — `faq/dto/InstantFaqRequestDto.java` (필드 선언부)

**처리 단계 (모두 한 요청 스레드, 한 트랜잭션 안에서 순차 실행)**
1. 컨트롤러가 이메일을 뽑고(`FaqBidCommandController.java:92`), 결제 요청의 `userEmail`을 채우고 `orderId`를 `null`로 비운다 (`:98`, `:119-123`).
2. `FaqBidCommandService.createInstantOrderBid` (`faq/service/command/FaqBidCommandService.java:118-149`, `@Transactional`)
   - 입력 검증 (`:123`, `:154-167`) → 구매자 조회 (`:126`) → 판매 입찰 조회·검증 (`:129`, `:172-184`)
3. `FaqCommandService.createInstantOrder` (`faq/service/command/FaqCommandService.java:219-319`, `@Transactional`)
   1. 배송지 조회 `addressQueryService.getAddress(...)` (`:238`)
   2. 주문 저장, 상태 `PENDING_PAYMENT`, 금액=판매 입찰가 (`:241-247`)
   3. 결제 요청에 주문 ID 설정 (`:250`)
   4. 주문 항목 생성 (`:255-256`)
   5. 주문 배송지(`FaqAddress`) 생성 (`:264-271`)
   6. 판매 입찰에 주문 연결 + `MATCHED` + `flush` (`:279-283`)
   7. 판매자가 창고 보관 상품이면 창고 상태를 `ASSOCIATED_WITH_ORDER`로 (`:291-294`)
   8. 결제 처리 `paymentCommandService.processPayment` (`:305`) → 내부에서 결제 엔티티 저장, 알림 전송, 판매 `SOLD` 변경 (`notification/service/command/NotificationCommandService.java:57-83`)
4. 다시 `FaqBidCommandService`로 돌아와 구매 입찰(`FaqBid`) 생성·저장 (`:142`, `:189-206`)

**동기/비동기**: **동기**다. 이 경로에는 Kafka 발행/소비가 없다. `FaqBidCommandController`는 `FaqEventProducer`를 쓰지 않고 `FaqBidCommandService`를 직접 호출한다 (`FaqBidCommandController.java:28`, `:101`). Kafka 프로듀서는 별도 컨트롤러 `faq/controller/command/FaqCommandController.java:30`에서만 주입된다. 결제 대행사(PortOne) 호출도 `RestTemplate` 동기 호출이다 (`notification/portone/PortOneApiClient.java:36`, `:270`).

**응답 ID**: 응답 `data`는 **구매 입찰(`FaqBid`, `order_bid`)의 ID**이다. 주문(`Faq`) ID가 아니다.
- 컨트롤러는 변수명을 `orderId`로 두지만 `createInstantOrderBid(...).getId()`는 `FaqBid`의 ID다 (`FaqBidCommandController.java:101-107`). 서비스의 반환 타입이 `FaqBid`이고 (`FaqBidCommandService.java:119`, `:144`) 반환값은 `orderBidRepository.save(orderBid)` 결과다 (`:206`).
- 메시지는 "즉시 구매가 성공적으로 처리되었습니다."이다 (`:109`).

## 3. 결제 수단별 결과, 성공 여부, 카드 실패 시

`processPayment`가 `getResolvedPaymentType()`으로 분기한다 (`NotificationCommandService.java:67-80`, `notification/dto/NotificationRequestDto.java:74-87`). 사전 검증으로 주문 ID 일치, 이메일 일치, `paidAmount > 0`을 확인한다 (`:117-146`). `paidAmount`는 클라이언트가 보낸 값이며 주문 금액(`totalAmount`)과 비교하지 않는다.

| 수단 | PortOne 호출 | 결제 엔티티 상태 | 근거 |
|---|---|---|---|
| CARD | 호출함. 응답 `status=="success"`이면 `PAID`, `isSuccess=true` | `PAID` (그 외 응답이면 기본값 `PENDING` 유지, 예외 없음) | `NotificationCommandService.java:179`, `:203-206` |
| ACCOUNT(계좌이체) | 호출 안 함. 은행명만 검증 | `PENDING`, 성공 플래그 false | `:243-247`, `:260` |
| GENERAL(일반) | 호출 안 함. `impUid`만 있으면 됨 | 즉시 `PAID`, `isSuccess=true` | `:297-314` |

**즉시 구매가 끝까지 성공하는가**: 위 세 수단 모두 예외가 없으면 같은 후속 단계를 탄다. 결제 엔티티 상태와 무관하게 판매 `SOLD` 변경과 알림 전송이 이어지고(`NotificationCommandService.java:83`, `:383-420`), HTTP 응답은 성공이다. 따라서 **계좌이체는 `PENDING`(미입금) 상태인데도 판매는 `SOLD`로 바뀌고, 구매자에게 "결제가 완료되었습니다." 알림이 간다.** 카드 응답이 코드 0이지만 `status`가 `success`가 아닌 경우도 결제는 `PENDING`으로 저장된 채 같은 방식으로 진행된다.
- 단, 주문 자체는 `PENDING_PAYMENT`로 남는다(5번).

**결제 대행사가 카드 결제를 실패로 응답할 때**
1. HTTP가 200이 아니거나 응답 `code`가 0이 아니면 `NotificationProcessingException`을 던진다 (`PortOneApiClient.java:270-274`). 이 예외는 `@Retryable` 대상(`NotificationApiException`)이 아니라서 재시도하지 않는다 (`:224-228`, `notification/exception/NotificationProcessingException.java:6`). 반면 통신 오류(`RestClientException`)는 `NotificationApiException`으로 바뀌어 최대 3회 재시도된다 (`:44-46`, `:224-228`).
2. 예외가 `createCardPayment` → `processPayment`에서 그대로 재던져지고 (`NotificationCommandService.java:218-219`, `:89-94`), `createInstantOrder`가 `FaqNotificationProcessingFailedException`으로 바꿔 던진다 (`FaqCommandService.java:304-309`, `:312-315`).
3. `FaqBidCommandService`가 `FaqException`을 그대로 재던진다 (`FaqBidCommandService.java:145-146`, `:212-215`). 예외는 `GlobalException`의 하위 타입이며 전체가 하나의 `@Transactional`이라, **주문·항목·배송지 생성과 판매 입찰 `MATCHED`가 전부 롤백**된다. 구매 입찰은 아직 만들어지기 전이므로 생성되지 않는다. 판매는 `SOLD`로 바뀌기 전이다. 클라이언트는 에러 응답을 받는다.

## 4. 알림: 누가, 언제, 어떤 방식으로

**수신자**: 구매자와 판매자 각 1건.
- 구매자: `"결제가 완료되었습니다. 주문 ID: {orderId}"` (`NotificationCommandService.java:436-443`)
- 판매자(`sale.getSeller()`): `"구매자가 결제를 완료하였습니다. 판매 ID: {saleId}"` (`:447-454`)
- 둘 다 카테고리 `SHOPPING`, 타입 `BID` (`:440-441`, `:451-452`)

**시점**: 결제 엔티티 저장 직후, 판매를 `SOLD`로 바꾸기 직전이다 (`notifyUsersAndUpdateSaleStatus`, `:83`, `:403-404`, `:416-419`). 요청 처리 중에 동기로 실행된다(트랜잭션 커밋 전).

**방식**
1. DB에 알림 레코드 저장 (`PaymentCommandService.java:52-53`)
2. 수신자가 WebSocket 접속 중일 때만(Redis 키 `WebSocket:Product:{email}` 존재) `convertAndSendToUser(email, "/queue/notifications", dto)`로 실시간 푸시한다. 접속이 없으면 저장만 한다 (`:303-322`, `:37-38`).
3. 알림 전송 실패는 삼켜서 경고 로그만 남기고 구매 흐름은 계속된다 (`NotificationCommandService.java:457-461`, `:421-425`, `PaymentCommandService.java:315-319`).

그 외: Kafka 기반 알림은 이 경로에서 쓰지 않는다(1번). 환불 알림은 환불 경로(`refundPayment`)에만 있고 즉시 구매에는 없다 (`NotificationCommandService.java:564-572`, `:603-659`).

## 5. 최종 주문 상태와 "창고 보관" 선택의 영향

**주문(`Faq`)의 최종 상태는 `PENDING_PAYMENT`이다.**
- 즉시 구매 경로(`createInstantOrder`)는 주문을 `PENDING_PAYMENT`로 저장한 뒤 `order.updateStatus(...)`를 한 번도 호출하지 않는다 (`FaqCommandService.java:241-247`, 전체 `:219-319`에 호출 없음). 결제 완료 후 `PAYMENT_COMPLETED`/`PREPARING`/`IN_WAREHOUSE`/`COMPLETED`로 바꾸는 코드는 `processPaymentAndShipment`(`:111-202`)에만 있고, 즉시 구매 경로는 이 메서드를 호출하지 않는다 (`FaqBidCommandService.java:119-149`).
- 따라서 카드·일반 결제가 `PAID`여도, 계좌이체가 `PENDING`이어도 주문 상태는 같다.
- 메서드/메시지("즉시 구매가 성공적으로 처리되었습니다")는 완료를 말하지만, 실제로 주문 상태는 결제 대기로 남는다.

**"창고 보관" 선택(`warehouseStorage`)의 영향: 사실상 없다.**
- 컨트롤러는 값을 서비스까지 넘긴다 (`FaqBidCommandController.java:94-105`, `FaqBidCommandService.java:119-139`, `FaqCommandService.java:219-221`). 그러나 `createInstantOrder` 안에서 `isWarehouseStorage` 인자는 읽히지 않는다 (`:219-319`에 사용 없음).
- 창고 관련 분기는 **판매 쪽 플래그** `sale.isWarehouseStorage()`(판매자가 창고 보관으로 올린 상품)만 본다. 이때 기존 창고 보관 `Notice`의 상태만 `ASSOCIATED_WITH_ORDER`로 바꾼다 (`FaqCommandService.java:291-294`, `style/entity/Style.java:43`). 구매자가 true를 보내도 `IN_WAREHOUSE`/`COMPLETED` 전이나 `createOrderStorage`(창고 보관 `Notice` 신규 생성)는 일어나지 않는다. 그 코드는 `processPaymentAndShipment`의 `requestDto.isWarehouseStorage()` 분기에만 있다 (`FaqCommandService.java:163-173`, `notice/service/command/NoticeCommandService.java:33-57`).
- 참고로 판매자 상품이 창고 보관인데 해당 `Notice`가 없으면 `findBySale`이 예외를 던져 전체가 롤백된다 (`NoticeCommandService.java:127`, `notice/service/query/NoticeQueryService.java:30-33`, `FaqCommandService.java:295-301`).
