# 즉시 구매 처리 분석

용어: 코드에서 `Faq` = 주문(테이블 `orders`), `FaqBid` = 구매(주문) 입찰, `Style` = 판매, `StyleBid` = 판매 입찰, `Notification` = 결제(카드/계좌/일반), `Payment` = 사용자 알림, `Notice` = 창고 보관.

경로 약어: `F` = `src/main/java/com/fream/back/domain/faq`, `N` = `.../domain/notification`, `S` = `.../domain/style`, `P` = `.../domain/payment`, `NT` = `.../domain/notice`.

## 1. 진입 API, 처리 단계, 동기/비동기, 응답 ID

- 진입: `POST /order-bids/instant`. 클래스 매핑 `/order-bids` (`F/controller/command/FaqBidCommandController.java:22`), 메서드 `@PostMapping("/instant")` (`F/controller/command/FaqBidCommandController.java:89`). 이름은 `createInstantOrderBid`.
- 단계:
  1. 컨트롤러가 JWT에서 이메일을 꺼낸다 (`FaqBidCommandController.java:92`).
  2. `enrichPaymentRequest`가 결제 요청의 `userEmail`을 로그인 이메일로 덮어쓰고 `orderId`를 null로 비운다 (`FaqBidCommandController.java:98`, `:119-122`).
  3. `FaqBidCommandService#createInstantOrderBid` 호출 (`FaqBidCommandController.java:101-107`). 입력 검증 → 구매자 조회 → 판매 입찰 조회·검증(`:123-130`, `:154-184`).
  4. `FaqCommandService#createInstantOrder` 호출 (`F/service/command/FaqBidCommandService.java:133`). 배송지 조회 → 주문 저장 → 주문 항목 → 배송 정보 → 판매 입찰 매칭 → 창고 상태 → 결제 처리 순서 (`F/service/command/FaqCommandService.java:238-309`).
  5. 돌아와서 `FaqBid`(구매 입찰)를 만들어 저장한다 (`FaqBidCommandService.java:142`, `:189-207`).
- 동기/비동기: **전부 동기**, 단일 `@Transactional` 안에서 처리된다 (`FaqBidCommandService.java:118`, `FaqCommandService.java:219`). 이 경로에는 Kafka 발행, `@Async`가 없다. 결제는 PortOne REST를 요청 스레드에서 블로킹 호출한다 (`N/portone/PortOneApiClient.java:266`).
- 응답 ID: **구매 입찰(`FaqBid`)의 ID**. 컨트롤러 변수명은 `orderId`이지만 (`FaqBidCommandController.java:101`) 서비스가 반환하는 것은 `FaqBid`이고 (`FaqBidCommandService.java:119`, `:142-144`) 그 `.getId()`를 응답 data로 쓴다 (`:107`, `:109`). 주문(`Faq`) ID가 아니다. 주문 ID와 같다고 가정하면 안 된다.

## 2. 새로 만들어지는 엔티티와 상태 변화 순서

각 단계 직후 상태 (모두 같은 트랜잭션, 커밋 전):

| 순서 | 동작 | 근거 | 직후 상태 |
|---|---|---|---|
| 1 | `Faq`(주문) 생성·저장 | `FaqCommandService.java:241-247` | `FaqStatus.PENDING_PAYMENT`, totalAmount = 판매 입찰가 |
| 2 | `FaqItem`(주문 항목) 생성 | `FaqCommandService.java:255-256` | 주문에 연결 |
| 3 | `FaqAddress`(주문 배송 정보) 생성 | `FaqCommandService.java:264-271` | 배송지 ID로 조회한 수령인/전화/우편번호/주소 복사 |
| 4 | 판매 입찰 `StyleBid` 매칭 | `FaqCommandService.java:279-283` | `assignOrder`(`S/entity/StyleBid.java:58-61`)가 order 연결 + `BidStatus.MATCHED`, 이어 `updateStatus(MATCHED)`, `flush` |
| 5 | (판매가 창고 보관일 때만) 창고 `Notice` 상태 변경 | `FaqCommandService.java:291-294` | `WarehouseStatus.ASSOCIATED_WITH_ORDER` |
| 6 | 결제 `Notification` 생성 | `N/service/command/NotificationCommandService.java:67-80` | 카드: 응답 `status`가 `"success"`면 `PAID`, 아니면 기본값 `PENDING`. 계좌: `PENDING`. 일반: `PAID` (3번 참조) |
| 7 | 판매 `Style` 상태 변경 | `NotificationCommandService.java:83`, `:391-405` | `StyleStatus.SOLD` (결제 상태와 무관, 아래 3번) |
| 8 | 구매 입찰 `FaqBid` 생성·저장 | `FaqBidCommandService.java:192-206` | `BidStatus.MATCHED`, `isInstantPurchase = true`, order·sale 연결 |

- 7번에서 `orderBid`는 이 시점에 아직 없으므로(`order.getOrderBid() == null`, 8번에서 생성됨) `findByOrderId`로 판매 입찰을 찾고 거기서 `Style`을 얻어 SOLD로 바꾼다 (`NotificationCommandService.java:388-406`). `findByOrderId`는 4번의 `flush` 덕분에 조회된다 (`S/service/query/StyleBidQueryService.java:26-29`, `FaqCommandService.java:283`).
- `Style.updateStatus`는 전이 검증이 없다 (`S/entity/Style.java:73-75`), 그래서 `PENDING_SHIPMENT` 등 어떤 상태에서도 곧바로 SOLD가 된다 (`StyleStatus.canTransitionTo`는 호출되지 않음).
- 즉시 구매 경로에서는 **`Faq.updateStatus`가 한 번도 호출되지 않는다.** 주문은 `PENDING_PAYMENT`로 남는다 (아래 5번).
- 판매 입찰이 이미 MATCHED인지 검사하는 코드는 없다 (`FaqBidCommandService.java:172-184`는 null만 검사). 중복 매칭이 가능하다.

## 3. 결제 수단별 결과, 끝까지 성공하는가, 카드 실패 응답

분기: `getResolvedPaymentType()` 값 "CARD"/"ACCOUNT"/"GENERAL" (`NotificationCommandService.java:67-80`, `N/dto/NotificationRequestDto.java:74-87`). 공통 검증: orderId·이메일 일치, `paidAmount > 0` (`NotificationCommandService.java:117-146`). 요청 금액과 판매 입찰가가 같은지는 **검증하지 않는다**.

- **카드**: 저장된 결제수단 조회 후 PortOne `/subscribe/payments/onetime` 동기 호출 (`NotificationCommandService.java:166-179`, `PortOneApiClient.java:229-266`). 응답 `status`가 `"success"`일 때만 `PAID` + 성공 플래그 (`NotificationCommandService.java:203-206`). 그 외는 아무 상태 변경 없이 저장되어 `PENDING`, `isSuccess=false`로 남는다 (`N/entity/Notification.java:39,44`).
- **계좌이체**: 은행명만 검증하고 (`NotificationCommandService.java:243-248`, `:470-488`) `PENDING`으로 저장. 실제 입금 확인이나 PG 호출이 없다 (`:260-262`).
- **일반 결제**: `impUid` 필수 확인 후 곧바로 `isSuccess=true`, `PAID`로 저장 (`:297-314`). 클라이언트가 보낸 값을 PG 재검증 없이 신뢰한다.
- **즉시 구매는 결제 성공 여부와 관계없이 끝까지 진행된다.** 결제 처리 뒤 `notifyUsersAndUpdateSaleStatus`는 `payment.getStatus()`를 보지 않고 알림 전송과 SOLD 처리를 한다 (`NotificationCommandService.java:83`, `:404`, `:419`). 따라서 계좌이체(PENDING)와 PENDING으로 남은 카드도 판매 입찰 MATCHED, 판매 SOLD, 구매 입찰 MATCHED까지 간다. 어디서도 PAID가 될 때까지 기다리지 않는다.
- **PG가 카드 결제를 실패로 응답할 때** (두 갈래):
  1. HTTP 비정상이거나 `code != 0`인 경우: `PortOneApiClient`가 `NotificationProcessingException`을 던진다 (`PortOneApiClient.java:270-275`). 이 예외는 `createCardPayment`(`NotificationCommandService.java:218-219`) → `processPayment`(`:89-94`)로 전파되고, `FaqCommandService`에서 `FaqNotificationProcessingFailedException`으로 감싸 (`FaqCommandService.java:305-308`) 던진다. `FaqException`이라 그대로 다시 던져지며 (`:313-315`, `FaqBidCommandService.java:145-146`, `:213-214`) `@Transactional`이 롤백한다. 주문, 항목, 배송, 판매 입찰 MATCHED, 결제가 모두 취소된다. 구매 입찰도 만들어지지 않는다. 사용자는 오류 응답을 받는다.
  2. HTTP 200 + `code == 0`인데 `response.status`가 `"success"`가 아닌 경우(예: 카드사 거절로 `failed`): 예외가 없다. 결제는 `PENDING`/`isSuccess=false`로 저장되고 (`NotificationCommandService.java:203-208`), 그대로 판매가 SOLD가 되고 "결제가 완료되었습니다" 알림이 나가며 `FaqBid`가 만들어진다. 응답은 성공 메시지 "즉시 구매가 성공적으로 처리되었습니다."다 (`FaqBidCommandController.java:109`). 결제 실패가 주문 성공으로 처리되는 **실제 동작상 결함**이다.
- 환불 코드(`handleRefundIfNecessary`, `NotificationCommandService.java:341-375`)는 `processPayment` 흐름에서 호출되지 않는다.

## 4. 알림 대상, 시점, 전달 방식

- 대상 2명: **구매자**("결제가 완료되었습니다. 주문 ID: …")와 **판매자**("구매자가 결제를 완료하였습니다. 판매 ID: …") (`NotificationCommandService.java:436-456`). 카테고리 `SHOPPING`, 타입 `BID`.
- 시점: 결제 레코드 저장 직후, 같은 트랜잭션·같은 요청 안 (`NotificationCommandService.java:83`, `:403/416`). SOLD 처리보다 먼저 보낸다 (`:416-419`). 결제 성공(PAID) 여부와 무관하다. 계좌이체 PENDING이어도 "결제가 완료되었습니다"가 나간다.
- 방식:
  1. DB에 `Payment`(알림) 행 저장 (`P/service/command/PaymentCommandService.java:52-53`, `buildNotification` `:241-249`).
  2. 수신자의 Redis 키 `WebSocket:Product:<email>`이 있으면(웹소켓 접속 중) STOMP `/queue/notifications`로 `convertAndSendToUser` 푸시 (`PaymentCommandService.java:37-38`, `:57`, `:303-313`). 접속 중이 아니면 저장만 하고 푸시는 없다 (`:320-322`). 푸시 실패는 경고 로그만 남긴다 (`:315-319`).
  3. Kafka/이메일/SMS는 없다.
- 알림 실패는 삼킨다 (`NotificationCommandService.java:457-461`, 바깥 `:421-425`), 구매 자체는 실패하지 않는다. 관련 notification Kafka 컨슈머(`N/service/kafka/NotificationEventConsumer.java`)는 이 경로와 연결되어 있지 않다.

## 5. 최종 주문 상태, 창고 보관 선택 시 차이

- 주문(`Faq`)의 최종 상태: **`PENDING_PAYMENT` 그대로**다. 즉시 구매 경로(`createInstantOrder`)에는 `order.updateStatus(...)` 호출이 없고 초기 상태만 설정한다 (`FaqCommandService.java:241-245`). `PAYMENT_COMPLETED`/`PREPARING`/`COMPLETED`로 바꾸는 코드는 별도 일반 주문 경로 `processPaymentAndShipment`에만 있다 (`FaqCommandService.java:163-177`). 이 경로는 즉시 구매에서 호출되지 않는다.
- 같이 정리되는 최종 값: 판매 입찰 `StyleBid` = MATCHED, 판매 `Style` = SOLD, 구매 입찰 `FaqBid` = MATCHED (isInstantPurchase=true), 결제 = PAID(카드 success·일반) 또는 PENDING(계좌·카드 비성공).
- **구매자의 "창고 보관" 선택은 사실상 무시된다.**
  - 컨트롤러는 `requestDto.isWarehouseStorage()`를 서비스에 넘기고 (`FaqBidCommandController.java:105`), 서비스도 `createInstantOrder`에 전달한다 (`FaqBidCommandService.java:137`). 그러나 `createInstantOrder` 본문에서는 `isWarehouseStorage` 파라미터를 읽지 않는다 (`FaqCommandService.java:220-319` 어디에도 사용 없음).
  - 창고 관련 분기는 **판매자의 판매(`sale.isWarehouseStorage()`)** 값만 본다 (`FaqCommandService.java:291-293`). 이때만 기존 창고 `Notice`를 `ASSOCIATED_WITH_ORDER`로 바꾼다 (`NT/service/command/NoticeCommandService.java:117-133`).
  - 구매자 선택에 따른 창고 `Notice` 신규 생성(`createOrderStorage`)이나 `IN_WAREHOUSE` 상태 전이는 즉시 구매 경로에서 일어나지 않는다. 그 코드는 일반 경로 `processPaymentAndShipment`에만 있다 (`FaqCommandService.java:163-173`).
  - 따라서 구매자가 true를 보내든 false를 보내든 주문 상태, 생성 엔티티, 알림이 동일하다.
