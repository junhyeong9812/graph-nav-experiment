# 즉시 구매 처리 흐름

경로 접두어: `S = src/main/java/com/fream/back/domain`.

이 코드베이스는 도메인 이름이 치환되어 있다. 아래 대응 관계로 읽는다.

| 코드 이름 | 의미 |
|---|---|
| `Faq` (테이블 `orders`) | 주문(Order) |
| `FaqBid` | 구매 입찰(OrderBid) |
| `Style` | 판매(Sale) |
| `StyleBid` | 판매 입찰(SaleBid) |
| `Notification` (테이블 `payment`) | 결제(Payment) |
| `Payment` (`domain/payment`) | 사용자 알림 |
| `Notice` | 창고 보관(WarehouseStorage) |
| `Product` | 사용자(User) |

## 1. 진입 API, 처리 단계, 동기/비동기, 응답 ID

**진입 API**
- `POST /order-bids/instant` 로 들어온다. 클래스 매핑은 `S/faq/controller/command/FaqBidCommandController.java:22`, 메서드는 `:89-110` 이다.
- 요청 DTO는 `InstantFaqRequestDto` 이다. 필드는 `saleBidId`, `addressId`, `warehouseStorage`, `paymentRequest` 이다 (`S/faq/dto/InstantFaqRequestDto.java:20-29`).

**처리 단계**
1. 컨트롤러가 SecurityContext에서 이메일을 꺼낸다 (`FaqBidCommandController.java:92`).
2. 결제 요청 DTO에 이메일을 넣고 `orderId` 를 null 로 둔다 (`:98`, `:119-123`).
3. `FaqBidCommandService.createInstantOrderBid` (`S/faq/service/command/FaqBidCommandService.java:118-149`, `@Transactional`)를 호출한다. 이 안에서 다음을 순서대로 한다.
   - 입력 검증 (`:123`, `:154-167`).
   - 구매자 조회 (`:126`).
   - 판매 입찰 조회와 검증 (`:129`, `:172-184`).
   - `FaqCommandService.createInstantOrder` 호출 (`:133`).
   - `FaqBid` 생성 (`:142`, `:189-207`).
4. `FaqCommandService.createInstantOrder` (`S/faq/service/command/FaqCommandService.java:219-319`, `@Transactional`)는 다음 순서로 동작한다.
   1. 배송지 조회 `addressQueryService.getAddress(...)` (`:238`).
   2. 주문 저장, `PENDING_PAYMENT` (`:241-247`).
   3. 결제 요청에 `orderId` 설정 (`:250`).
   4. 주문 항목 생성 (`:255-256`).
   5. 배송 정보 생성 (`:264-271`).
   6. 판매 입찰에 주문 연결과 `MATCHED` 지정, flush (`:279-283`).
   7. 판매의 창고 보관 상태 갱신 (`:291-293`).
   8. 결제 처리 `paymentCommandService.processPayment` (`:305`).
5. `NotificationCommandService.processPayment` (`S/notification/service/command/NotificationCommandService.java:57-107`)는 결제 유형별로 결제를 만들고, 이어서 알림 발송과 판매 상태 갱신(`notifyUsersAndUpdateSaleStatus`, `:83`)을 한다.

**동기/비동기**
- 전부 **동기**이고, 하나의 DB 트랜잭션 안에서 요청 스레드가 처리한다. 클래스/메서드가 모두 `@Transactional` 이다 (`FaqBidCommandService.java:118`, `FaqCommandService.java:219`, `NotificationCommandService.java:37`).
- 즉시 구매 경로에는 Kafka 발행이 없다. `FaqEventProducer` 는 `FaqCommandController` 와 `FaqEventConsumer` 에서만 쓰이고(grep 확인), `FaqBidCommandController` 에서는 쓰이지 않는다.
- PortOne(카드사) 호출도 동기 HTTP(`RestTemplate`)이다 (`S/notification/portone/PortOneApiClient.java:266`).

**응답 ID**
- 컨트롤러 변수 이름은 `orderId` 이고 메시지도 "즉시 구매"라서 주문 ID처럼 보인다.
- 실제로는 `createInstantOrderBid(...).getId()` 이고 (`FaqBidCommandController.java:101-107`), 반환 타입이 `FaqBid` (`FaqBidCommandService.java:119`)이므로 **새로 만든 구매 입찰(`FaqBid`) ID** 이다. 주문(`Faq`) ID가 아니다.

## 2. 생성되는 엔티티와 상태 변화 순서

**새로 만들어지는 엔티티**

| 엔티티 | 위치 | 생성 시 상태 |
|---|---|---|
| `Faq` 주문 | `FaqCommandService.java:241-247` | `PENDING_PAYMENT`, `totalAmount` = 판매 입찰가 |
| `FaqItem` 주문 항목 | `FaqCommandService.java:255`, `S/faq/service/command/FaqItemCommandService.java:34-52` | 수량 1, 가격 = 입찰가 |
| `FaqAddress` 배송 | `FaqCommandService.java:264`, `S/address/service/command/FaqAddressCommandService.java:56-70` | `AddressStatus.PENDING` |
| `Notification` 결제 | `NotificationCommandService.java:187-208`(카드), `:250-262`(계좌), `:302-316`(일반) | 유형별로 다름. 3번 참고 |
| `Payment` 사용자 알림 (구매자 1건, 판매자 1건) | `S/payment/service/command/PaymentCommandService.java:241-249` | `isRead=false` |
| `FaqBid` 구매 입찰 | `FaqBidCommandService.java:189-207` | `MATCHED`, `isInstantPurchase=true`, `sale` 연결 |

`FaqBid` 는 builder 에서 `.status(MATCHED)` 를 주고 (`:196`), `assignOrder` 도 `MATCHED` 로 설정하며 (`S/faq/entity/FaqBid.java:75`), `markAsInstantPurchase()` 를 호출한다 (`FaqBidCommandService.java:205`).

**기존 엔티티 상태 변화 순서**

| # | 대상 | 변화 | 근거 |
|---|---|---|---|
| 1 | 판매 입찰 `StyleBid` | `PENDING` → `MATCHED`, `order` 연결 | `FaqCommandService.java:279-280`, `S/style/entity/StyleBid.java:58-61` |
| 2 | 창고 `Notice` (판매자가 창고 보관을 선택한 판매일 때만) | `IN_STORAGE` → `ASSOCIATED_WITH_ORDER` | `FaqCommandService.java:291-293`, `S/notice/service/command/NoticeCommandService.java:117-133`, `WarehouseStatus.java` |
| 3 | 결제 `Notification` | 생성 시 `PENDING`(기본값). 유형·결과에 따라 `PAID` 로 바뀜 | `S/notification/entity/Notification.java:43-44` |
| 4 | 판매 `Style` | 결제 처리 후 `SOLD` | `NotificationCommandService.java:404`, `Style.java:73-75` |
| 5 | 구매 입찰 `FaqBid` | 생성 시점부터 `MATCHED` | 위 참고 |

- 주문 `Faq` 상태는 `PENDING_PAYMENT` 에서 **변하지 않는다**. 5번 참고.
- 상태 전환 순서 요약: `StyleBid=MATCHED`(2-6단계) → `Notice=ASSOCIATED_WITH_ORDER`(2-7단계) → `Notification=PENDING/PAID`(2-8단계) → `Style=SOLD`(2-8단계 끝) → `FaqBid=MATCHED` 저장(3단계).
- 판매 상태 갱신(4번)은 `notifyUsersAndUpdateSaleStatus` 안에서 한다 (`:383-426`). 이 시점에는 `order.getOrderBid()` 가 아직 null 이다. `FaqBid` 는 `createInstantOrder` 반환 뒤에 만들어지기 때문이다. 그래서 `saleBidQueryService.findByOrderId` 분기로 판매를 찾는다 (`:388-406`). 이 분기가 동작하는 것은 `:283` 의 flush 덕분이다.

## 3. 결제 수단별 결과, 성공 여부, 카드 실패 시 동작

분기는 `processPayment` 의 switch 이다 (`NotificationCommandService.java:67-80`).

| 수단 | 처리 | 결과 상태 | 근거 |
|---|---|---|---|
| 카드 `CARD` | 저장된 결제정보 조회 → PortOne 카드 결제 호출(`portOneApiClient.processCardPayment`) | 응답 `status == "success"` 일 때만 `PAID` + `isSuccess=true` + `paymentDate`. 아니면 기본값 `PENDING` 으로 저장 | `NotificationCommandService.java:157-217` (`:203-206`) |
| 계좌이체 `ACCOUNT` | 은행명만 검증하고 PG 호출 없이 저장 | 항상 `PENDING` (`isSuccess=false`) | `:236-279` (`:260`) |
| 일반 `GENERAL` | `impUid` 필수 검사 후 PG 호출 없이 저장 | 곧바로 `PAID` + `isSuccess=true` | `:290-333` (`:313-314`) |

**즉시 구매가 끝까지 성공하는가**
- 예외가 없으면 수단과 무관하게 컨트롤러는 "즉시 구매가 성공적으로 처리되었습니다."(HTTP 200)를 반환한다 (`FaqBidCommandController.java:109`).
- 결제 결과가 `PENDING` 이어도 판매 상태 `SOLD` 갱신과 구매자/판매자 알림은 그대로 진행된다. 결제 상태를 확인하는 분기가 없다 (`NotificationCommandService.java:83`, `:383-426`).
- 따라서 계좌이체는 입금 전인데도 판매가 `SOLD` 가 되고 "결제가 완료되었습니다" 알림이 간다.
- 즉시 구매는 어느 수단에서도 **결제를 확정하고 주문을 진행시키는 단계까지 가지 못한다.** 주문 상태는 `PENDING_PAYMENT` 에 머문다 (5번).

**결제 대행사가 카드 결제를 실패로 응답하면**

실패 응답의 형태에 따라 두 갈래가 있다.
- **(a) HTTP 비-200 이거나 응답 `code != 0`**
  - `PortOneApiClient.processCardPayment` 가 `NotificationProcessingException` 을 던진다 (`PortOneApiClient.java:270-275`).
  - 이 예외는 `createCardPayment` → `processPayment` 를 거쳐 전파된다 (`NotificationCommandService.java:180-182`, `:89-94`).
  - `FaqCommandService.createInstantOrder` 가 `FaqNotificationProcessingFailedException` 으로 감싸 던지고 (`FaqCommandService.java:305-309`), `FaqBidCommandService` 가 그대로 다시 던진다 (`FaqBidCommandService.java:145-147`, `:212-218`).
  - 예외는 `RuntimeException` (`GlobalException.java:10`) 이므로 `@Transactional` 이 롤백된다. 주문, 항목, 배송, 판매 입찰 `MATCHED`, 창고 상태 변경이 모두 취소되고 `FaqBid` 도 생성되지 않는다. 클라이언트는 에러 응답을 받는다.
- **(b) HTTP 200 이고 `code == 0` 인데 `response.status` 가 `"success"` 가 아닌 경우** (예: `failed`)
  - 예외가 나지 않는다. 결제 레코드는 `PENDING` 으로 저장되고(`:203-208`), 흐름은 그대로 이어진다.
  - `StyleBid=MATCHED`, `Style=SOLD`, 알림 발송, `FaqBid=MATCHED` 가 모두 커밋되고 응답은 성공이다.
  - 결제는 실패했는데 즉시 구매는 "성공"으로 끝나는 결함이다.

PortOne 호출 후 뒤 단계가 실패하는 경우는 카드 결제가 이미 승인된 상태에서 DB 만 롤백된다. 자동 환불 호출은 즉시 구매 경로에 없다. `handleRefundIfNecessary` 는 정의만 있고 호출처가 없다 (`NotificationCommandService.java:341`).

## 4. 알림 수신자, 시점, 전달 방식

**수신자와 내용** (`NotificationCommandService.sendNotifications`, `:434-462`)
- **구매자**: `"결제가 완료되었습니다. 주문 ID: {orderId}"` (`:438-443`).
- **판매자** (`sale.getSeller()`): `"구매자가 결제를 완료하였습니다. 판매 ID: {saleId}"` (`:447-454`).
- 둘 다 카테고리 `SHOPPING`, 타입 `BID` 이다.

**시점**
- `processPayment` 안에서 결제 저장 직후, 판매를 `SOLD` 로 바꾸기 직전에 동기로 발송된다 (`:83`, `:403`, `:416` → `:404`, `:419`).
- 결제가 `PENDING`(계좌이체, 카드 `status != success`)이어도 발송된다. 위 3번 참고.
- 알림 발송 예외는 삼켜지므로(`:457-461`) 알림 실패가 즉시 구매를 막지 않는다.

**전달 방식** (`PaymentCommandService.createNotification`, `:44-67`)
1. DB 에 `Payment` 알림 레코드를 저장한다 (`:52-53`). 요청 트랜잭션에 참여한다 (`PaymentCommandService.java:27`).
2. 구매자/판매자가 WebSocket 연결 중이면 실시간 푸시한다 (`sendRealTimeNotification`, `:303-323`). 조건은 Redis 키 `WebSocket:Product:{email}` 존재이다 (`:37`, `:307`). 전송은 STOMP `convertAndSendToUser(email, "/queue/notifications", dto)` 이다 (`:38`, `:309-313`).
3. 연결이 없으면 저장만 되고 푸시는 생략된다 (`:320-322`). 전송 실패도 경고 로그만 남긴다 (`:315-319`).

Kafka 나 별도 비동기 큐는 쓰지 않는다. 푸시는 요청 스레드에서 직접 보낸다.

## 5. 최종 주문 상태와 창고 보관 선택 시 차이

**최종 상태**
- 즉시 구매 처리가 끝났을 때 주문(`Faq`)의 최종 상태는 **`PENDING_PAYMENT`** 이다.
  - 주문 생성 시 `PENDING_PAYMENT` 로 저장된다 (`FaqCommandService.java:244`).
  - `createInstantOrder` 와 `processPayment` 안에는 `order.updateStatus(...)` 호출이 없다 (`FaqCommandService.java:219-319`, `NotificationCommandService.java:57-107`).
  - `PAYMENT_COMPLETED`, `PREPARING`, `IN_WAREHOUSE`, `COMPLETED` 로 바꾸는 코드는 `processPaymentAndShipment` 에만 있다 (`FaqCommandService.java:163-177`). 이 메서드는 즉시 구매 경로에서 호출되지 않는다. 입찰 방식 주문에 대한 별도의 결제·배송 API용이다.
- 함께 만들어지는 `FaqBid` 는 `MATCHED` 이다 (`FaqBidCommandService.java:196`).
- 판매 입찰과 판매는 각각 `MATCHED`, `SOLD` 이다.
- 주석("즉시 구매가 성공적으로 처리되었습니다.")이나 메서드 이름과 달리 주문은 결제 완료·준비 중으로 진행되지 않는다.

**구매자가 "창고 보관"을 선택한 경우**
- **차이가 없다.** 요청의 `warehouseStorage` 는 컨트롤러에서 서비스까지 전달되지만 (`FaqBidCommandController.java:104`, `FaqBidCommandService.java:137`), `createInstantOrder` 의 `isWarehouseStorage` 파라미터는 본문에서 한 번도 쓰이지 않는다 (`FaqCommandService.java:220-319`).
- 그 값으로 만들어지는 `Notice`(창고 보관), `IN_WAREHOUSE` 전환, `COMPLETED` 전환은 일어나지 않는다. 이런 처리는 `processPaymentAndShipment` 의 `requestDto.isWarehouseStorage()` 분기에만 있다 (`FaqCommandService.java:163-172`).
- 창고 관련으로 일어나는 유일한 변화는 **판매자** 가 올린 판매(`Style.isWarehouseStorage`, `Style.java:43`)가 창고 보관 판매일 때 해당 창고 레코드를 `ASSOCIATED_WITH_ORDER` 로 바꾸는 것이다 (`FaqCommandService.java:291-293`). 이는 구매자 선택과 무관하다.
- 구매자의 창고 보관 선택 여부와 관계없이 주문은 `PENDING_PAYMENT` 로 남는다.
- 판매가 창고 보관인데 `Notice` 가 없으면 `NoticeNotFoundException` 이 `FaqNoticeProcessingFailedException` 으로 감싸져(`:295-301`) 전체가 롤백된다.
