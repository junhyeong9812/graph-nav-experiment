# 구매자 배송: 운송장 등록 → 배송 완료

## 용어 (이름이 난독화되어 있음)

- `FaqAddress` (테이블 `order_shipment`) = 구매자에게 가는 주문 배송. `Faq` = 주문(Order, 테이블 `orders`), `FaqBid` = 구매 입찰(OrderBid), `Style` = 판매(Sale), `StyleBid` = 판매 입찰(SaleBid), `Payment` = 알림 엔티티(`PaymentCommandService#createNotification`이 저장), `Product` = 사용자.
  - 근거: `src/main/java/com/fream/back/domain/address/entity/FaqAddress.java:11`, `src/main/java/com/fream/back/domain/faq/entity/Faq.java:26`, `src/main/java/com/fream/back/domain/faq/entity/FaqBid.java:202`
- 주문 상태: `PENDING_PAYMENT → PAYMENT_COMPLETED → PREPARING → IN_WAREHOUSE/SHIPMENT_STARTED → IN_TRANSIT → COMPLETED`. 허용 전이표는 `src/main/java/com/fream/back/domain/faq/entity/FaqStatus.java:24-32`.
  - `PREPARING`에서는 `IN_WAREHOUSE`, `SHIPMENT_STARTED`만 갈 수 있다 (`FaqStatus.java:26`).
  - `IN_TRANSIT`은 `SHIPMENT_STARTED`에서만 갈 수 있다 (`FaqStatus.java:28`).
  - `SHIPMENT_STARTED`로 바꾸는 코드는 소스 전체에 없다 (grep 결과 `FaqStatus.SHIPMENT_STARTED`를 세팅하는 곳 없음). 따라서 `IN_TRANSIT`은 정상 경로로 도달할 수 없다.
- 배송 상태 전이표: `src/main/java/com/fream/back/domain/address/entity/AddressStatus.java:16-34` (`IN_TRANSIT → OUT_FOR_DELIVERY/DELAYED/CANCELED/DELIVERED`, `DELIVERED`는 종단).

## 1. 운송장 등록 요청

### 1-1. 진입 API

- `PATCH /shipments/order/{shipmentId}/status`, 바디 `FaqAddressRequestDto{courier, trackingNumber}`.
  - 근거: `src/main/java/com/fream/back/domain/address/controller/command/FaqAddressCommandController.java:21` (base path `/shipments/order`), `:32-46` (`updateTrackingInfo` → `FaqAddressCommandService#updateTrackingInfo`).
- 인증/권한 체크는 이 컨트롤러에 없다. 운영 측이 호출한다는 전제일 뿐이다.
- 참고: 같은 컨트롤러의 `POST /{shipmentId}/check-status`, `/check-status-string`은 운송장을 넣고 택배사 조회까지 즉시 수행한다 (`FaqAddressCommandController.java:62-95`, 서비스 `FaqAddressCommandService.java:451-516`).

### 1-2. 코드가 의도한 순서 (`FaqAddressCommandService#updateTrackingInfo`, `FaqAddressCommandService.java:238-303`)

1. courier/trackingNumber가 비면 `TRACKING_INFO_REQUIRED` (`:243-246`).
2. 배송 조회 후 `shipment.updateTrackingInfo` → courier·trackingNumber 저장, 배송 상태를 전이 검사 없이 `IN_TRANSIT`으로 직접 세팅 (`:256`, `FaqAddress.java:41-45`).
3. `order.updateStatus(FaqStatus.IN_TRANSIT)` (`:259-260`). 전이 검사가 `Faq.java:113-121`에 있고, 불가하면 `InvalidFaqStatusException`.
4. 구매자에게 알림 1건 "상품이 출발하였습니다. 주문 ID: …" (`:265-271`).
5. `updateSaleStatusToSold(orderId)` (`:276`, 본문 `:111-183`).
   - 판매 입찰 조회 후 판매 `SOLD`로 변경.
   - 창고 보관이면 창고 상태 SOLD.
   - 판매자에게 알림 "상품이 성공적으로 판매 완료되었습니다".
   - 구매 입찰 기준 경로로 한 번 더 시도하지만 이미 SOLD라 전이 불가로 건너뛴다 (`StyleStatus.java:23`, `SOLD -> false`).
6. 판매 입찰이 있고 창고 보관이면 창고 상태 SOLD를 한 번 더 호출 (`:279-286`). 5단계에서 이미 SOLD가 되어 있어 `InvalidStatusTransitionException`("이미 판매 완료 상태")이 날 수 있다 (`NoticeCommandService.java:150-185`의 `updateWarehouseStatusToSold`).
7. `updateOrderAndSaleBidStatusToCompleted` (`:289`, 본문 `:412-440`)
   - `FaqBid`가 `MATCHED`이면 `COMPLETED`.
   - `StyleBid`가 `MATCHED`이면 `COMPLETED`.
   - 즉 입찰 COMPLETED는 배송 완료가 아니라 **운송장 등록 시점**에 일어나도록 짜여 있다. 이 private 메서드의 호출처는 이 한 곳뿐이다.

판매 입찰이 없는 주문이면 5단계 `StyleBidQueryService#findByOrderId`가 null이 아니라 `IllegalArgumentException`을 던진다 (`src/main/java/com/fream/back/domain/style/service/query/StyleBidQueryService.java:26-29`). 서비스의 `if (saleBid != null)` 분기(`FaqAddressCommandService.java:117`)는 실제로는 실행되지 않는다.

### 1-3. 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문에서의 결과: **끝까지 성공하지 못한다**

- 주문 상태 확인
  - 일반 구매 입찰은 `createOrderBid` → `createOrderFromBid`로 `PENDING_PAYMENT` 주문을 만들고 입찰에 연결한다 (`FaqBidCommandService.java:46-70, 90-103`, `FaqCommandService.java:58-96`).
  - 결제·배송 처리는 컨트롤러가 Kafka로 보내고 (`src/main/java/com/fream/back/domain/faq/controller/command/FaqCommandController.java:42-60`) `FaqEventConsumer#processCompleteOrder`가 실행한다.
  - 창고 보관이 아니면 `PAYMENT_COMPLETED` → `PREPARING`에서 끝난다 (`src/main/java/com/fream/back/domain/faq/service/kafka/FaqEventConsumer.java:192-196, 215-218`). 동기 버전도 동일하다 (`FaqCommandService.java:174-177`).
  - 따라서 이 주문은 `PREPARING` 상태다.
- 실패 지점
  - `FaqAddressCommandService.java:260`의 `order.updateStatus(IN_TRANSIT)`에서 실패한다. `PREPARING → IN_TRANSIT`은 `FaqStatus.java:26`에 없으므로 `InvalidFaqStatusException`("상태 전환이 허용되지 않습니다: PREPARING -> IN_TRANSIT")이 난다 (`Faq.java:113-120`).
  - 창고 보관 주문은 `COMPLETED`(`FaqStatus.java:31`, 빈 집합)라 마찬가지로 실패한다.
- 예외 변환
  - `AddressException`이 아니므로 `catch (Exception e)` (`FaqAddressCommandService.java:295-302`)에서 `AddressException(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")`으로 바뀐다.
  - 실제 원인은 주문 상태 전이 불가인데 코드는 "배송 정보를 찾을 수 없음"으로 보고한다.
- 저장되는 것
  - 아무것도 저장되지 않는다.
  - `@Transactional` 메서드(`:238`)에서 `RuntimeException`(`GlobalException`, `src/main/java/com/fream/back/global/exception/GlobalException.java:9`)이 나가므로 롤백된다.
  - 영속성 컨텍스트에서만 바뀐 courier/trackingNumber/`IN_TRANSIT`은 버려진다. 주문은 `PREPARING`, 배송은 `PENDING` 그대로다.
  - 알림은 `order.updateStatus` 뒤에 만들어지므로(`:265`) 생성되지 않는다.
- 응답
  - 컨트롤러는 예외를 잡지 않는다 (`FaqAddressCommandController.java:32-46`).
  - `GlobalExceptionHandler#handleShipmentException`이 `AddressException`을 받아 ErrorCode의 값으로 응답한다 (`src/main/java/com/fream/back/global/exception/GlobalExceptionHandler.java:459-471`).
  - HTTP 404, 코드 `S001`, 메시지 "배송 정보를 찾을 수 없습니다." (`src/main/java/com/fream/back/domain/address/exception/AddressErrorCode.java:12`). 상세 메시지(`"운송장 정보 업데이트 중 오류 발생…"`)는 응답 바디에 실리지 않는다.
- 즉시 구매 주문(`PENDING_PAYMENT`)도 `PENDING_PAYMENT → IN_TRANSIT`이 `FaqStatus.java:24`에 없어 같은 이유로 실패한다.

## 2. 배송 완료 감지

### 2-1. 누가·언제·어떻게

- 스케줄러 `AddressBatchScheduler#scheduleShipmentStatusJob`이 Spring Batch Job `updateShipmentStatusesJob`을 실행한다 (`src/main/java/com/fream/back/global/config/AddressBatchScheduler.java:34-44`).
- 주기: `@Scheduled(cron = "0 0 */6 * * *")` — 6시간마다 정각(00·06·12·18시) (`AddressBatchScheduler.java:34`).
- `@EnableScheduling`은 다른 설정 클래스에 있다 (`src/main/java/com/fream/back/domain/event/scheduler/EventStatusScheduler.java:22`).
- Job 구성은 `src/main/java/com/fream/back/domain/address/config/UpdateAddressStatusesJobConfig.java:54-82` (청크 50, skipLimit 50, `skip(Exception.class)`).
- 대상 조회 (`UpdateAddressStatusesJobConfig.java:95`): `SELECT s FROM FaqAddress s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL`.
- 조회 방식: Playwright로 CJ대한통운 추적 페이지(`https://trace.cjlogistics.com/next/tracking.html?wblNo=`)를 열고 `tbody#statusDetail tr`의 마지막 행 5번째 `td` 텍스트를 읽는다 (`src/main/java/com/fream/back/domain/address/config/AddressItemProcessor.java:28-29, 72-94, 167-191`).

### 2-2. 실제로 실행되는 처리 코드

비슷한 코드가 4곳에 있다.

| 후보 | 실행 여부 | 근거 |
|---|---|---|
| `AddressItemProcessor#process` | **실행됨**. Step의 processor로 `new AddressItemProcessor(...)`를 연결한다. | `UpdateAddressStatusesJobConfig.java:69-73`, `AddressItemProcessor.java:57` |
| `UpdateAddressStatusesJobConfig#shipmentItemProcessor` (빈) | 미사용. Step에 연결되지 않고 호출처도 없다. | 정의 `:104-177`, Step `:66-81` |
| `UpdateAddressStatusesJobConfig#parseCjLogisticsStatus` | 미사용. private, 호출처 없음. | `:186-220` |
| `FaqAddressCommandService#updateShipmentStatuses` | 미사용. 호출처가 없다 (`updateShipmentStatuses`를 호출하는 곳이 정의뿐). | `FaqAddressCommandService.java:308-391` |

- 따라서 실제 처리 코드는 `AddressItemProcessor#process`다. 같은 일을 하는 `FaqAddressCommandService#updateAndCheckShipmentStatus`는 `POST /shipments/order/{id}/check-status`로 수동 호출될 때만 돈다.

### 2-3. 택배사 상태 문자열 → 내부 상태 (`AddressItemProcessor#mapToShipmentStatus`, `AddressItemProcessor.java:220-226`)

- `"배송완료"` → `AddressStatus.DELIVERED`
- `"배송출발"` → `AddressStatus.OUT_FOR_DELIVERY`
- 그 외 모든 문자열 → `AddressStatus.IN_TRANSIT`

정확히 일치(equals)만 인식하고, 공백은 `trim`한다 (`:181`). 조회 결과가 현재 상태와 같으면 변경 없이 반환한다 (`:101-105`).

## 3. 배송 완료 판정 이후 (`AddressItemProcessor.java:108-117`)

`newStatus == DELIVERED`일 때 실행되는 순서:

1. `orderShipment.updateStatus(DELIVERED)` — 배송 `IN_TRANSIT`/`OUT_FOR_DELIVERY` → `DELIVERED` (`:113`, 전이 검사 `FaqAddress.java:47-55`, `AddressStatus.java:16-34`).
2. `FaqAddressCommandService#completeOrder(orderId)` (`:116`, 본문 `FaqAddressCommandService.java:190-229`)
   1. `FaqBid` 조회 (`:196-197`, 없으면 `IllegalArgumentException`).
   2. 주문 `COMPLETED` (`:204`).
   3. `updateSaleStatusToSold` (`:208`) — 판매 `SOLD`, 창고 보관이면 창고 SOLD, **판매자 알림 1건** "상품이 성공적으로 판매 완료되었습니다" (`:111-183`).
   4. **구매자 알림 1건** "[completeOrder] 주문이 완료 처리되었습니다" (`:211-217`).
   5. 예외는 모두 `AddressException(ORDER_NOT_FOUND_FOR_SHIPMENT)`으로 감싸 던진다 (`:221-228`).
3. `PaymentCommandService#notifyShipmentCompleted(order)` — **구매자 알림 1건** "[배송 완료] 상품이 배송 완료되었습니다" (`:117`, `src/main/java/com/fream/back/domain/payment/service/command/PaymentCommandService.java:219-234`). 실패해도 예외를 삼킨다 (`:230-233`).
4. 청크 writer(`JpaItemWriter`)가 배송을 저장한다 (`UpdateAddressStatusesJobConfig.java:74, 239-246`).

### 알림 건수 (판매·구매 모두 정상 진행될 때)

- 구매자: 2건 — `[completeOrder]`, `[배송 완료]`.
- 판매자: 최대 1건 — "판매 완료" 알림. 판매가 아직 `SOLD`가 아니고 `SELLING`/`ON_AUCTION`일 때만 발생한다 (`FaqAddressCommandService.java:119`, `StyleStatus.java:21-22`).

### 입찰 상태

- 배치 경로(`completeOrder`)는 `FaqBid`/`StyleBid` 상태를 바꾸지 않는다.
- 입찰 `COMPLETED` 변경은 `updateOrderAndSaleBidStatusToCompleted`뿐이고, 이 메서드는 운송장 등록(`updateTrackingInfo`)에서만 호출된다 (`FaqAddressCommandService.java:289, 412-440`). 1-3에서 그 경로가 항상 실패하므로, 배송 완료 뒤에도 구매 입찰·판매 입찰은 `MATCHED`로 남는다.
  - 메서드 이름과 "COMPLETED"라는 주석이 말하는 의도와 달리, 어떤 실행 경로에서도 입찰이 `COMPLETED`가 되지 않는다.

## 4. 주문 종류별 차이

배치 대상이 되려면 배송이 `IN_TRANSIT`/`OUT_FOR_DELIVERY`이면서 운송장 번호가 있어야 한다. 정상 API(1번)는 위 이유로 실패하므로 이 상태는 `POST /{shipmentId}/check-status`(`FaqAddressCommandService.java:451-516`)가 배송만 `IN_TRANSIT`으로 만들 때 생긴다. 그 메서드는 주문 상태를 건드리지 않는다. 아래는 그 배송이 배치 대상이 된 이후의 결과다.

### (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문: **끝까지 진행되지 않는다**

- 주문은 `PREPARING` (1-3 참조).
- 배치에서 `DELIVERED` 판정 → 배송을 메모리에서 `DELIVERED`로 바꾼 뒤 `completeOrder`가 `order.updateStatus(COMPLETED)`를 호출한다 (`FaqAddressCommandService.java:204`).
- `PREPARING → COMPLETED`는 `FaqStatus.java:26`에 없어 `InvalidFaqStatusException`이 발생한다. `completeOrder`의 `catch (Exception)`이 `AddressException(ORDER_NOT_FOUND_FOR_SHIPMENT)`로 감싼다 (`:221-228`).
- 알림·판매 상태 변경·입찰 변경은 하나도 일어나지 않는다.
  - `completeOrder`는 `@Transactional`이고 청크 트랜잭션에 참여하므로(`:190`) 롤백된다.
  - `AddressItemProcessor`는 이 예외를 다시 던진다 (`AddressItemProcessor.java:133-146`).
  - 해당 건은 skip 처리되고 writer에 가지 않는다.
- 결과: 배송은 `IN_TRANSIT`/`OUT_FOR_DELIVERY` 그대로이고 주문은 `PREPARING` 그대로다. 6시간마다 같은 건이 다시 조회되고 다시 실패하며 skip을 소모한다.

### (b) 즉시 구매로 만들어진 주문: **끝까지 진행된다 (단, 판매 상태·판매자 알림은 변하지 않는다)**

- 즉시 구매는 `createInstantOrder`로 주문을 `PENDING_PAYMENT`로 만들고 결제까지 같은 흐름에서 처리한다 (`FaqCommandService.java:219-319`). 이후 주문 상태를 올리는 코드가 없어 `PENDING_PAYMENT`로 남는다 (`:241-245` 외에 `updateStatus` 없음).
  - `isWarehouseStorage` 파라미터는 사용되지 않는다.
- `completeOrder`
  - `PENDING_PAYMENT → COMPLETED`는 허용된다 (`FaqStatus.java:24`). 주문이 `COMPLETED`가 된다.
  - 판매 입찰과 구매 입찰이 모두 존재한다 (`saleBid.assignOrder(order)` `FaqCommandService.java:279`; 즉시 주문 입찰 생성 `FaqBidCommandService.java:189-207`).
- 판매는 이미 결제 시점에 `SOLD`가 된다.
  - `processPayment` → `notifyUsersAndUpdateSaleStatus`가 `sale.updateStatus(SOLD)`를 전이 검사 없이 호출한다 (`src/main/java/com/fream/back/domain/notification/service/command/NotificationCommandService.java:83, 383-420`).
  - 따라서 배송 완료 시 `canTransitionTo(SOLD)`가 false여서 판매 상태 변경, 창고 상태 변경, 판매자 알림이 모두 건너뛰어진다 (`FaqAddressCommandService.java:119, 156`).
- 알림: 구매자 2건(`[completeOrder]`, `[배송 완료]`), 판매자 0건.
- 입찰: `FaqBid`·`StyleBid` 모두 `MATCHED` 그대로 (3번 참조).
- 구매 입찰은 `MATCHED`로 생성되고, 판매 입찰은 `assignOrder`로 `MATCHED`가 된다 (`StyleBid.java:58-61`).

### 비교

| | (a) 일반 구매 입찰 | (b) 즉시 구매 |
|---|---|---|
| 주문 상태 | `PREPARING` | `PENDING_PAYMENT` |
| `→ COMPLETED` | 불가 → 예외, 롤백 | 가능 |
| 배송 `DELIVERED` 저장 | 안 됨 | 됨 |
| 구매자 알림 | 0건 | 2건 |
| 판매자 알림 | 0건 | 0건 (이미 SOLD) |
| 입찰 상태 | 변화 없음 (`MATCHED`) | 변화 없음 (`MATCHED`) |

## 5. 실패 처리 (주기 처리 중 한 건이 실패할 때)

- Step은 `faultTolerant().skip(Exception.class).skipLimit(50)`이다 (`UpdateAddressStatusesJobConfig.java:75-78`). 청크는 50건 단위, 트랜잭션은 청크 단위다 (`:67`).
- 실패한 건
  - processor 예외는 `AddressException`으로 변환되어 던져진다 (`AddressItemProcessor.java:133-146`).
  - 스킵 리스너가 로그를 남긴다 (`UpdateAddressStatusesJobConfig.java:251-287`).
