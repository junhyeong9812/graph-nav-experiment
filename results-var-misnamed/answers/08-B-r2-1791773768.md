# 구매자 배송: 운송장 등록 → 배송 완료

경로 약어: `ADDR` = `src/main/java/com/fream/back/domain/address`, `FAQ` = `src/main/java/com/fream/back/domain/faq`, `STYLE` = `src/main/java/com/fream/back/domain/style`, `G` = `src/main/java/com/fream/back/global`
(클래스명이 Faq*/Style*/Product 등으로 되어 있으나 실제 역할은 `Faq`=주문(Order, 테이블 `orders`), `FaqAddress`=구매자 배송(테이블 `order_shipment`), `FaqBid`=구매 입찰, `StyleBid`=판매 입찰, `Style`=판매(Sale), `Product`=사용자, `Payment`=알림(Notification)이다.)

---

## 0. 전제: 결제 후 구매자 배송 정보와 주문 상태

- 결제·배송 처리(`processPaymentAndShipment`)에서 `FaqAddress`가 `PENDING` 상태로 생성된다 (`ADDR/service/command/FaqAddressCommandService.java:56-70`, 호출 `FAQ/service/command/FaqCommandService.java:148`).
- 창고보관이 아닌 실배송이면 주문(`Faq`)은 `PENDING_PAYMENT → PAYMENT_COMPLETED → PREPARING`까지만 간다 (`FAQ/service/command/FaqCommandService.java:175-176`). Kafka 경로도 동일하게 `PREPARING`에서 멈춘다 (`FAQ/service/kafka/FaqEventConsumer.java:216-217`).
- 일반 구매 입찰(`createOrderBid`)은 주문을 만들고(`FAQ/service/command/FaqBidCommandService.java:60`) `orderBid.assignOrder(order)`로 입찰↔주문을 연결하며 이때 입찰 상태가 `MATCHED`가 된다 (`FAQ/service/command/FaqBidCommandService.java:100`, `FAQ/entity/FaqBid.java:74-76`). 즉시구매 플래그는 `false`(기본, `FaqBid.java:50-52`).
- 즉시 구매(`createInstantOrderBid`)는 `createInstantOrder`로 주문을 만들고 주문 상태를 **`PENDING_PAYMENT` 그대로** 둔다 (`FAQ/service/command/FaqCommandService.java:244`; 이후 상태 변경 코드 없음 — 주문 상태를 바꾸는 곳은 `FaqStatus.` 검색 결과상 위에 적은 곳과 아래 주소 서비스뿐). 판매 입찰에 주문을 연결하고 `MATCHED`로 바꾸며(`FaqCommandService.java:279-280`), 구매 입찰은 `MATCHED + isInstantPurchase=true`로 저장된다 (`FAQ/service/command/FaqBidCommandService.java:189-205`).
- 상태 전이표
  - 주문: `PENDING_PAYMENT→{PAYMENT_COMPLETED, COMPLETED, IN_WAREHOUSE}`, `PREPARING→{IN_WAREHOUSE, SHIPMENT_STARTED}`, `SHIPMENT_STARTED→{IN_TRANSIT}`, `IN_TRANSIT→{COMPLETED}` (`FAQ/entity/FaqStatus.java:24-31`). 검증은 `Faq.updateStatus`가 하고 위반 시 `InvalidFaqStatusException` (`FAQ/entity/Faq.java:113-121`).
  - 배송: `IN_TRANSIT→{OUT_FOR_DELIVERY, DELAYED, CANCELED, DELIVERED}`, `OUT_FOR_DELIVERY→{DELIVERED, FAILED_DELIVERY, CANCELED}`, `DELIVERED→없음` (`ADDR/entity/AddressStatus.java:16-33`). 위반 시 `IllegalStateException` (`ADDR/entity/FaqAddress.java:47-55`).

## 1. 운송장 등록 요청

### 1-1. 진입 API
- `PATCH /shipments/order/{shipmentId}/status`, body `{courier, trackingNumber}` (`ADDR/controller/command/FaqAddressCommandController.java:20,33-45`, DTO `ADDR/dto/FaqAddressRequestDto.java`). 이름은 `/status`지만 실제로는 택배사·운송장 등록이다. 컨트롤러는 `FaqAddressCommandService.updateTrackingInfo`를 호출한다 (`FaqAddressCommandController.java:41`).
- 경로 전용 권한 설정은 없고 `anyRequest().authenticated()`만 적용된다 (`G/config/security/SecurityConfig.java:50-52`). 즉 "운영 측"만 호출하도록 막는 코드는 보이지 않는다.
- (참고) 같은 컨트롤러에 `POST /{shipmentId}/check-status`, `/check-status-string`이 있어 `updateAndCheckShipmentStatus`(운송장 저장 + 즉시 조회)를 호출한다 (`FaqAddressCommandController.java:58-68,103-112`).

### 1-2. 코드가 의도한 상태 변경 순서와 알림 (`FaqAddressCommandService.updateTrackingInfo`, `ADDR/service/command/FaqAddressCommandService.java:238-303`)
1. courier/trackingNumber가 비면 `TRACKING_INFO_REQUIRED`(400) (`:243-246`, 코드 `ADDR/exception/AddressErrorCode.java:15`).
2. 배송 조회 → `shipment.updateTrackingInfo` : 택배사·운송장 저장 + 배송 상태를 곧바로 `IN_TRANSIT`으로 세팅 (`:249-256`, `ADDR/entity/FaqAddress.java:41-45`).
3. 주문 `order.updateStatus(IN_TRANSIT)` (`:259-260`).
4. 구매자에게 알림 "상품이 출발하였습니다. 주문 ID: …" (`:265-271`, `PaymentCommandService.createNotification` `domain/payment/service/command/PaymentCommandService.java:44-67`, 실시간 전송 `:57`).
5. `updateSaleStatusToSold(orderId)` (`:276`): 판매 입찰(`StyleBid`)의 판매(`Style`)가 SOLD로 전이 가능하면 `SOLD`로 바꾸고, 창고보관 상품이면 창고 상태도 SOLD로, **판매자에게** "상품이 성공적으로 판매 완료되었습니다. 판매 ID: …" 알림 (`:111-147`, 알림 `:133-138`). 이어서 구매 입찰(`FaqBid`) 쪽 판매도 같은 식으로 처리(`:150-180`).
6. 창고보관 판매면 창고 상태 SOLD 업데이트 (`:279-286`).
7. `updateOrderAndSaleBidStatusToCompleted`: 구매 입찰이 `MATCHED`면 `COMPLETED`, 판매 입찰이 `MATCHED`면 `COMPLETED` (`:289`, `:412-440`). 이 메서드 안의 예외는 삼켜진다(`:436-439`).

### 1-3. 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문(즉시구매 아님)에서 끝까지 성공하나? → **실패한다**
- 실패 지점: 위 3단계 `order.updateStatus(FaqStatus.IN_TRANSIT)` (`ADDR/service/command/FaqAddressCommandService.java:260`).
- 이유: 이 주문은 `PREPARING` 상태(0절)이고, `PREPARING`에서 갈 수 있는 곳은 `IN_WAREHOUSE`, `SHIPMENT_STARTED`뿐이다 (`FAQ/entity/FaqStatus.java:26`). `IN_TRANSIT`은 `SHIPMENT_STARTED`에서만 갈 수 있는데(`:28`) 코드 어디에서도 `SHIPMENT_STARTED`로 바꾸는 곳이 없다 (`FaqStatus.SHIPMENT_STARTED` 쓰임은 enum 정의와 화면 라벨 `FAQ/controller/query/FaqQueryController.java:207`뿐). 따라서 `Faq.updateStatus`가 `InvalidFaqStatusException("상태 전환이 허용되지 않습니다: PREPARING -> IN_TRANSIT")`을 던진다 (`FAQ/entity/Faq.java:113-119`).
- 예외 변환: `InvalidFaqStatusException`은 `FaqException`(→`GlobalException`)이지 `AddressException`이 아니므로 `catch (AddressException)`(`:293`)을 지나 `catch (Exception)`(`:295-302`)에서 `AddressException(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")`로 바뀌어 던져진다 (원인이 "배송 정보 없음"이 아닌데도 이 코드가 쓰인다).
- 저장되는 것: **없음.** 메서드는 `@Transactional`(`:238`)이고 `AddressException → GlobalException → RuntimeException`(`G/exception/GlobalException.java:10`)이라 롤백된다. 2단계의 배송 `courier/trackingNumber/IN_TRANSIT` 변경은 메모리에서만 일어났으므로 DB에 남지 않는다. 구매자 알림(4단계)·판매자 알림·SOLD·입찰 COMPLETED는 3단계 뒤라 실행조차 되지 않는다. 배송은 `PENDING` 그대로, 주문은 `PREPARING` 그대로.
- 응답: `GlobalExceptionHandler`가 `errorCode`의 값으로 응답한다 → **HTTP 404, 에러 코드 `S001`, 메시지 "배송 정보를 찾을 수 없습니다."**, 경로=요청 URI (`G/exception/GlobalExceptionHandler.java:49-63`, `ADDR/exception/AddressErrorCode.java:12`). 내부 예외 메시지(상태 전환 불가)는 응답 본문에 나오지 않는다. 컨트롤러의 "업데이트 완료" 로그와 200 응답(`FaqAddressCommandController.java:47-48`)에는 도달하지 못한다.
- 부수적으로, 3단계를 통과하더라도 5단계의 `StyleBidQueryService.findByOrderId`는 연결된 판매 입찰이 없으면 `null`이 아니라 `IllegalArgumentException`을 던진다 (`STYLE/service/query/StyleBidQueryService.java:25-29`). 판매 입찰↔주문 연결은 즉시구매(`FaqCommandService.java:279`)나 즉시판매(`STYLE/service/command/StyleBidCommandService.java:82-83`)에서만 생기므로, 일반 구매 입찰 주문은 판매자가 매칭하기 전엔 여기서도 막힌다 (`updateSaleStatusToSold` 안에 이 호출을 감싼 try/catch 없음 → `:295` catch로 같은 404).

## 2. 배송 완료 감지

### 2-1. 누가/언제/어떻게
- 주체: 스프링 스케줄러 `AddressBatchScheduler.scheduleShipmentStatusJob` 이 Spring Batch Job `updateShipmentStatusesJob`을 실행한다 (`G/config/AddressBatchScheduler.java:19-21,34-40`). 요청 시 즉시 확인하는 수동 경로(1-1 참고 `check-status`)도 있으나 자동 감지는 이 배치다.
- 주기: `@Scheduled(cron = "0 0 */6 * * *")` → **6시간마다**(0·6·12·18시 정각) (`AddressBatchScheduler.java:34`). 매번 `timestamp` 파라미터로 새 JobInstance (`:37-40`). 예외는 `printStackTrace`로만 처리 (`:41-43`).
- (주의) `spring.batch.job.enabled`를 끄는 설정이 yml에 없다(`application-prod.yml:77-79`에는 `initialize-schema`뿐). 따라서 Boot 기본값에 따라 Job 빈이 기동 시 한 번 더 실행될 수 있다(설정 부재 기반 추정).

### 2-2. 조회 대상
- `JpaPagingItemReader`: `SELECT s FROM FaqAddress s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL` (`ADDR/config/UpdateAddressStatusesJobConfig.java:95`). 페이지 크기 = 청크 크기 50 (`:51`).
- 정렬 없이 offset 페이징이고 처리 중 `DELIVERED`가 되면 결과 집합에서 빠지므로, 같은 실행에서 일부 건이 건너뛰어질 수 있다(다음 실행에서 다시 대상이 됨).

### 2-3. 실제로 실행되는 처리 코드
- Step은 **`new AddressItemProcessor(playwrightBrowserManager(), notificationService, orderService)`** 를 쓴다 (`UpdateAddressStatusesJobConfig.java:69`). 따라서 실제 실행 코드는 `ADDR/config/AddressItemProcessor.java:57-157`이다.
- 같은 로직의 사본이 3개 더 있으나 **실행되지 않는다**:
  - `UpdateAddressStatusesJobConfig.shipmentItemProcessor()` 람다 (`:106` 이하): `@Bean`으로 정의만 되고 Step에 연결되지 않음(Step은 `:69`의 new 인스턴스 사용).
  - `UpdateAddressStatusesJobConfig.parseCjLogisticsStatus` (Jsoup): 어디서도 호출되지 않음.
  - `FaqAddressCommandService.updateShipmentStatuses()` (`ADDR/service/command/FaqAddressCommandService.java:308-391`): `@Scheduled`도 호출처도 없음(검색 결과 정의뿐). 이쪽은 알림 문구/상태 변경 방식이 달라(주문을 바로 `COMPLETED`, 구매자 알림 1건) 실제 동작과 혼동하면 안 된다.
- 조회 방식: `AddressItemProcessor`가 `PlaywrightBrowserManager`의 브라우저로 `https://trace.cjlogistics.com/next/tracking.html?wblNo=<운송장>`을 열고 `tbody#statusDetail tr` 대기(타임아웃 30초) 후 HTML 파싱 → **마지막 행의 5번째 `td`(index 4) 텍스트**를 상태 문자열로 사용 (`AddressItemProcessor.java:28-30,72-94,167-191`). 브라우저는 스텝 시작/종료 리스너가 열고 닫는다 (`ADDR/config/BrowserManageStepListener.java:17,23`, 등록 `UpdateAddressStatusesJobConfig.java:80`). 운송장 없음/빈 테이블/파싱 실패는 `AddressException`으로 던진다 (`AddressItemProcessor.java:61-64,172-190`).

### 2-4. 택배사 상태 문자열 → 내부 상태 (`AddressItemProcessor.java:220-226`)
| 택배사 문자열(정확히 일치) | 내부 상태 |
|---|---|
| `"배송완료"` | `DELIVERED` |
| `"배송출발"` | `OUT_FOR_DELIVERY` |
| 그 외 모든 문자열 | `IN_TRANSIT` |

- 현재 상태와 같으면 아무것도 안 하고 반환 (`:101-105`).
- 주의: 그 외 문자열은 전부 `IN_TRANSIT`이므로 `OUT_FOR_DELIVERY` 상태 배송이 "집하" 등 다른 문자열로 조회되면 `OUT_FOR_DELIVERY→IN_TRANSIT`을 시도하고 이는 전이표에 없어(`AddressStatus.java:23-27`) `IllegalStateException` → `AddressException(EXTERNAL_TRACKING_SERVICE_ERROR)`로 감싸져(`AddressItemProcessor.java:133-145`) 그 건이 스킵된다.

## 3. 배송 완료 판정 이후 (`AddressItemProcessor.java:108-117`)

### 3-1. 상태 변경 순서
1. 배송 `FaqAddress.updateStatus(DELIVERED)` (`:113`) — 메모리 상 변경, 쓰기는 청크 writer(`JpaItemWriter`, `UpdateAddressStatusesJobConfig.java:74,138` 부근 빈)에서 커밋.
2. `FaqAddressCommandService.completeOrder(orderId)` (`:116` → `ADDR/service/command/FaqAddressCommandService.java:190-229`):
   1. `FaqBidQueryService.findByOrderId`로 구매 입찰 조회, 없으면 예외 (`:196-197`, `FAQ/service/query/FaqBidQueryService.java:51-56`).
   2. 주문 `updateStatus(COMPLETED)` (`:204`).
   3. `updateSaleStatusToSold(orderId)` (`:208`): 판매 입찰의 판매 `SOLD` (+창고 상품이면 창고 SOLD), 판매자 알림 (`:111-147`); 이어 구매 입찰의 판매도 전이 가능할 때만 SOLD (`:150-176`).
   4. 구매자 알림 "[completeOrder] 주문이 완료 처리되었습니다. 주문 ID: …" (`:211-217`).
   5. 어떤 예외든 `AddressException(ORDER_NOT_FOUND_FOR_SHIPMENT)`로 변환 (`:221-228`).
3. `PaymentCommandService.notifyShipmentCompleted(order)` (`:117`): 구매자에게 "[배송 완료] 상품이 배송 완료되었습니다. 주문 ID: …" (`PaymentCommandService.java:219-234`; 이 메서드 내부 예외는 삼켜짐).

### 3-2. 알림 (정상 완료 시)
- **구매자 2건**: "[completeOrder] 주문이 완료 처리되었습니다…"(`FaqAddressCommandService.java:212-217`) + "[배송 완료] 상품이 배송 완료되었습니다…"(`PaymentCommandService.java:224-229`).
- **판매자 1건**: "상품이 성공적으로 판매 완료되었습니다. 판매 ID: …"(`FaqAddressCommandService.java:133-138`). 구매 입찰 쪽 두 번째 SOLD 블록(`:156-172`)은 이미 `SOLD`가 된 같은 판매에 대해 `canTransitionTo(SOLD)`가 `false`(`STYLE/entity/StyleStatus.java:23`)라 알림이 중복되지 않는다.
- 총 3건. 판매 상태가 `SELLING`/`ON_AUCTION`이 아니면(예: `IN_STORAGE`) SOLD 전이·판매자 알림은 조용히 생략된다 (`StyleStatus.java:20-22`, `FaqAddressCommandService.java:119,142-143`).

### 3-3. 주문 입찰·판매 입찰 상태
- **변하지 않는다.** 구매 입찰(`FaqBid`)과 판매 입찰(`StyleBid`)을 `COMPLETED`로 바꾸는 코드는 `updateOrderAndSaleBidStatusToCompleted`(`FaqAddressCommandService.java:412-440`)뿐이고, 이 메서드는 `updateTrackingInfo`(`:289`)에서만 호출된다. 배치 경로(`AddressItemProcessor` → `completeOrder`)는 호출하지 않으므로 두 입찰은 `MATCHED`로 남는다. 바뀌는 건 주문(`COMPLETED`), 판매(`Style.SOLD`), 배송(`DELIVERED`)이다.

## 4. 주문 종류별 차이

| | (a) 실배송 일반 구매 입찰 주문 | (b) 즉시 구매 주문 |
|---|---|---|
| 주문 상태(사전) | `PREPARING` (`FaqCommandService.java:176`) | `PENDING_PAYMENT` (`FaqCommandService.java:244`) |
| 3-1의 `order.updateStatus(COMPLETED)` | **불가**: `PREPARING→COMPLETED` 전이 없음 (`FaqStatus.java:26`) → `InvalidFaqStatusException` | **가능**: `PENDING_PAYMENT→COMPLETED` 허용 (`FaqStatus.java:24`) |
| 구매 입찰 조회 | 있음(`FaqBidCommandService.java:100`) | 있음(`FaqBidCommandService.java:189-205`) |
| 판매 입찰(`StyleBid`) 연결 | 판매자가 즉시판매로 매칭하기 전엔 없음 → `findByOrder_Id`가 `IllegalArgumentException` (`StyleBidQueryService.java:26-28`) | 있음 (`FaqCommandService.java:279`) |

### (a) 끝까지 진행되지 **않는다**
- `completeOrder`가 `order.updateStatus(COMPLETED)`(`FaqAddressCommandService.java:204`)에서 예외 → `AddressException(ORDER_NOT_FOUND_FOR_SHIPMENT)` (`:221-228`). 판매자·구매자 알림, SOLD, 입찰 변경 모두 일어나지 않고 `notifyShipmentCompleted`(`AddressItemProcessor.java:117`)도 실행되지 않는다.
- 호출이 같은 청크 트랜잭션에 참여하므로 `DELIVERED`로 바꿨던 배송도 롤백되어 `IN_TRANSIT`/`OUT_FOR_DELIVERY`로 남고, 해당 건은 스킵 처리된다(5절). 다음 6시간 주기에 같은 이유로 계속 실패한다.
- 사실 (a)는 1-3 때문에 운송장 등록 자체가 실패해 배송이 `PENDING`에 머물러 배치 조회 대상(`IN_TRANSIT`/`OUT_FOR_DELIVERY`+운송장)에도 들어오지 못한다. 위 내용은 배송이 어떤 경로로든 `IN_TRANSIT`+운송장 상태가 됐다고 가정했을 때의 결과다.

### (b) 3의 처리는 끝까지 진행된다 (단, 배송이 조회 대상 상태일 때)
- 배송 `DELIVERED`, 주문 `COMPLETED`, 판매 `SOLD`(판매가 SELLING/ON_AUCTION일 때), 구매자 알림 2건 + 판매자 알림 1건, 입찰 두 개는 `MATCHED` 유지 (3절과 동일).
- 단, (b)도 운송장 등록 API(1절)는 주문이 `PENDING_PAYMENT`라 `IN_TRANSIT` 전이가 막혀(`FaqStatus.java:24`) 마찬가지로 실패한다. 즉 (b)가 배치 대상이 되려면 `check-status` 경로(`updateAndCheckShipmentStatus`, `FaqAddressCommandService.java:452-516`)처럼 주문 상태를 건드리지 않고 배송에만 운송장을 넣는 경로(`:473`)나 DB 직접 수정이 필요하다.
- (참고) `updateAndCheckShipmentStatus`는 `completeOrder`만 호출하고 `notifyShipmentCompleted`는 호출하지 않아 구매자 알림은 1건 + 판매자 1건이다 (`:483-489`).

## 5. 실패 처리 (주기 처리 중 한 건 실패)

- 스텝 설정: 청크 50, `faultTolerant().skip(Exception.class).skipLimit(50)` (`UpdateAddressStatusesJobConfig.java:51-52,75-77`). 프로세서 예외는 모두 `Exception`이므로 스킵 대상이다.
- 해당 건: 청크 트랜잭션이 롤백되고 청크가 항목 단위로 재처리되며 실패 항목은 스킵 → writer로 가지 않아 저장되지 않는다. 이 건에서 이미 만든 알림·상태 변경도 같은 트랜잭션이라 롤백된다(`completeOrder`는 `@Transactional`로 합류, `PaymentCommandService`는 클래스에 `@Transactional` `:27`). 상태는 `IN_TRANSIT`/`OUT_FOR_DELIVERY` 그대로여서 다음 실행에서 다시 조회된다. (단, 실시간 웹소켓 전송 `PaymentCommandService.java:57`은 DB 롤백과 무관하게 이미 나갔을 수 있다.)
- 나머지 건: 정상 처리되어 커밋된다.
- 로그: 스킵 리스너가 처리/읽기/쓰기 스킵을 `log.error`로 남긴다 (`UpdateAddressStatusesJobConfig.java`의 `shipmentSkipListener`, 등록 `:78`). 프로세서도 자체 로그를 남기고 `AddressException`으로 감싸 던진다 (`AddressItemProcessor.java:133-145`).
- 스킵이 50건을 넘으면 `SkipLimitExceededException`으로 스텝(잡)이 실패한다. 이 예외는 스케줄러의 `catch`에서 `printStackTrace`로만 처리된다 (`AddressBatchScheduler.java:41-43`).
- 참고: 사용되지 않는 `updateShipmentStatuses()`(`FaqAddressCommandService.java:322-387`)는 건별 try/catch로 계속 진행하는 구조이지만 실행되지 않는다.
