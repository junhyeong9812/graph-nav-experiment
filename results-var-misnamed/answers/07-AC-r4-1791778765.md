# 즉시 구매 처리 흐름

경로 약어: `D` = `src/main/java/com/fream/back/domain`

## 1. 진입 API와 처리 단계 (동기 처리, 응답 ID = 주문 입찰 FaqBid ID)

1. `POST /order-bids/instant` — `D/faq/controller/command/FaqBidCommandController.java:22,89-90` (`@RequestMapping("/order-bids")`, `createInstantOrderBid`).
   - 요청 DTO는 `saleBidId`, `addressId`, `warehouseStorage`, `paymentRequest` 이다. `D/faq/dto/InstantFaqRequestDto.java:20-29`
2. 컨트롤러가 로그인 이메일을 꺼내고(`FaqBidCommandController.java:92`), `enrichPaymentRequest`로 `paymentRequest.userEmail=이메일`, `orderId=null`을 채운다(`:98`, `:119-123`).
3. `FaqBidCommandService#createInstantOrderBid` (`D/faq/service/command/FaqBidCommandService.java:118-149`, `@Transactional`)
   - 입력 검증 (`:123`, `:154-167`)
   - 구매자 조회 `findByEmail` (`:126`)
   - 판매 입찰 조회·검증 `getSaleBidAndValidate` (`:129`, `:172-184`)
   - `FaqCommandService#createInstantOrder` 호출 (`:133-139`)
   - `FaqBid`(주문 입찰) 생성·저장 (`:142`, `:189-207`)
4. `FaqCommandService#createInstantOrder` (`D/faq/service/command/FaqCommandService.java:219-319`, `@Transactional`)의 순서:
   1. 배송지 조회 `addressQueryService.getAddress(buyerEmail, addressId)` (`:238`)
   2. 주문 `Faq` 생성·저장, 상태 `PENDING_PAYMENT`, `totalAmount = saleBid.bidPrice` (`:241-247`)
   3. `paymentRequest.setOrderId(order.getId())` (`:250`)
   4. 주문 항목 `FaqItem` 생성 (`:255-256`)
   5. 배송 정보 `FaqAddress` 생성·연결 (`:264-271`)
   6. 판매 입찰에 주문 연결 + `MATCHED` + `flush` (`:279-283`)
   7. 판매 상품이 창고 보관이면 창고 상태 갱신 (`:291-294`)
   8. 결제 처리 `paymentCommandService.processPayment` (`:305`)
5. 결제 처리와 판매 상태 변경은 `NotificationCommandService#processPayment` (`D/notification/service/command/NotificationCommandService.java:57-83`) 안에서 한다.
6. 동기 처리다. 컨트롤러 → 서비스 → 결제 대행사 호출 → 알림 저장까지 한 요청 스레드, 하나의 `@Transactional`에서 끝난다.
   - Kafka 발행이나 `@Async`가 없다. 이 경로(`faq/service/command`, `faq/controller/command`, `notification/service/command`)에서 `@Async`, `KafkaTemplate`, `@EventListener` grep 결과가 없다.
   - Kafka를 쓰는 `/orders/{id}/process-payment-shipment` 경로(`FaqCommandController`)와는 별개 경로다.
7. 응답으로 돌려주는 ID는 주문(`Faq`)이 아니라 주문 입찰 `FaqBid`의 ID다.
   - `createInstantOrderBid`가 `FaqBid`를 반환하고, 컨트롤러는 그 `.getId()`를 `orderId`라는 변수에 담아 반환한다. `FaqBidCommandController.java:101-107`
   - 변수 이름이 `orderId`라 주문 ID처럼 보이지만 실제 값은 `FaqBid` 엔티티의 PK다. `D/faq/entity/FaqBid.java:23-25`
   - 메시지는 "즉시 구매가 성공적으로 처리되었습니다."이다 (`:109`).

## 2. 새로 만들어지는 엔티티와 상태 변화 순서

| 순서 | 동작 | 엔티티/상태 | 근거 |
|---|---|---|---|
| 1 | 주문 생성 | `Faq` 신규, `status = PENDING_PAYMENT`, `discountAmount`·`usedPoints`는 기본값 0 | `FaqCommandService.java:241-247` |
| 2 | 주문 항목 | `FaqItem` 신규, 주문에 `addOrderItem` | `:255-256` |
| 3 | 배송 정보 | `FaqAddress` 신규, `status = AddressStatus.PENDING`, `order.assignOrderShipment` | `D/address/service/command/FaqAddressCommandService.java:61-68`, `FaqCommandService.java:264-271` |
| 4 | 판매 입찰 매칭 | 기존 `StyleBid`: `order` 연결, `status = MATCHED` (`assignOrder`와 `updateStatus(MATCHED)` 모두 MATCHED) | `FaqCommandService.java:279-280`, `D/style/entity/StyleBid.java:58-61,66-68` |
| 5 | 창고 상태 (조건부) | 기존 `Style#isWarehouseStorage()`가 true일 때만 `Notice` 상태 → `ASSOCIATED_WITH_ORDER` | `FaqCommandService.java:291-294`, `D/notice/service/command/NoticeCommandService.java:117-133` |
| 6 | 결제 레코드 | `Notification`(Card/Account/General) 신규, `order` 연결 (결제 수단별 상태는 3번 참조) | `NotificationCommandService.java:187-208,250-262,302-316` |
| 7 | 판매 상품 상태 | 기존 `Style`: `status = SOLD` (결제 상태와 무관) | `NotificationCommandService.java:383-421` (`:404`, `:419`) |
| 8 | 알림 | `Payment`(알림 엔티티) 신규 2건: 구매자·판매자 | `NotificationCommandService.java:434-455`, `D/payment/service/command/PaymentCommandService.java:44-57,241-249` |
| 9 | 주문 입찰 | `FaqBid` 신규, `status = MATCHED`, `isInstantPurchase = true`, `sale`·`order` 연결 | `FaqBidCommandService.java:189-206`, `D/faq/entity/FaqBid.java:60-82,97-99` |

- 순서 요약: `Faq`(PENDING_PAYMENT) → `StyleBid`(MATCHED) → (창고 `Notice` ASSOCIATED_WITH_ORDER) → `Notification`(결제) → `Style`(SOLD) → `Payment`(알림) → `FaqBid`(MATCHED).
- `FaqBid`는 결제 처리가 **끝난 뒤** 마지막에 만든다 (`FaqBidCommandService.java:133-142`).
  - 그래서 `processPayment` 시점의 `order.getOrderBid()`는 null이다.
  - 이 때문에 `saleBidQueryService.findByOrderId`로 판매 입찰을 다시 찾는다 (`NotificationCommandService.java:389-391`).
  - 이는 앞서 `StyleBid.order`를 flush 해 둔 덕분에 가능하다 (`FaqCommandService.java:279-283`).
- 즉시 구매 경로에서 주문 `Faq`의 상태를 바꾸는 코드는 없다. `updateStatus(FaqStatus...)` 호출은 `processPaymentAndShipment`(`FaqCommandService.java:165-177`)에만 있고 이 경로에서는 호출하지 않는다. `Faq.payment`도 `assignPayment`로 연결하지 않는다 (`createInstantOrder`에 호출 없음).

## 3. 결제 수단별 결과, 성공 여부, 카드 실패 시 동작

결제 수단은 `paymentType`(`CARD`/`ACCOUNT`/`GENERAL`)으로 분기한다 (`NotificationRequestDto.java:20-25`, `NotificationCommandService.java:68-74`).

공통 사전 검증은 `validatePaymentRequest`이다 (`NotificationCommandService.java:125-146`).
- 주문 ID 일치 (`:131`)
- 이메일 일치
- `paidAmount > 0` (`:142`)

| 수단 | 처리 | 결제 레코드 상태 | 근거 |
|---|---|---|---|
| CARD | 저장된 카드정보 조회 → PortOne 호출 `processCardPayment` → 응답의 `status`가 `"success"`이면 `PAID` + `isSuccess=true` | 성공: `PAID`. 응답 status가 `"success"`가 아니면 기본값 `PENDING`, `isSuccess=false` 그대로 저장 | `NotificationCommandService.java:179,187-208`, `D/notification/entity/Notification.java:39,44` |
| ACCOUNT | 은행명만 검증(`Bank` enum). 실제 이체 확인/외부 호출 없음 | 항상 `PENDING` | `NotificationCommandService.java:236-262` |
| GENERAL | `impUid` 필수 확인 후 그대로 신뢰, PortOne 호출 없음 | 항상 `PAID`, `isSuccess=true` | `NotificationCommandService.java:290-316` |

- **즉시 구매는 어떤 수단에서도 "끝까지" 성공으로 처리된다.** 결제 대행사 실패 응답으로도 주문·판매 입찰·판매 상품 상태가 되돌려지지 않는다.
  - `notifyUsersAndUpdateSaleStatus`는 `payment` 상태를 보지 않고 항상 `sale.updateStatus(SOLD)`를 한다 (`NotificationCommandService.java:83,404,419`).
  - `createInstantOrder`는 결제 처리 후 `Faq` 상태를 바꾸지 않아 주문은 계속 `PENDING_PAYMENT`다 (`FaqCommandService.java:305-311`).
  - 그 결과 ACCOUNT 결제는 `PENDING` 상태인데도 판매 상품은 `SOLD`가 되고 "결제가 완료되었습니다." 알림이 나간다.
- **카드 결제를 대행사가 실패로 응답할 때** (실제 동작):
  - HTTP 비-200이거나 응답 `code != 0`이면 `PortOneApiClient`가 예외를 던진다 (`D/notification/portone/PortOneApiClient.java:270-275`).
    - `NotificationProcessingException` → `NotificationCommandService`가 재던짐 → `createInstantOrder`의 `catch`(`FaqCommandService.java:306-309`)가 `FaqNotificationProcessingFailedException`으로 변환 → 트랜잭션 전체 롤백. 주문·배송지·판매 입찰 매칭·결제 레코드가 모두 저장되지 않는다.
    - 이때만 사용자에게 오류가 나가고 `FaqBid`는 만들어지지 않는다 (`FaqBidCommandService.java:145-147`).
  - 반면 대행사 응답이 `code == 0`인데 `response.status`가 `"success"`가 아닌 경우(예: 카드 승인 거절 `failed`)에는 예외가 없다.
    - 결제 레코드는 `PENDING`/`isSuccess=false`로 저장되고 (`:187-208`), 흐름이 계속된다.
    - 판매 상품이 `SOLD`가 되고 주문 입찰이 `MATCHED`로 저장되며, 구매자·판매자에게 "결제 완료" 알림이 나가고, 응답은 성공이다.
    - `FaqStatus`도 `PENDING_PAYMENT`로 남는다. 실패를 감지해 환불/롤백하는 코드가 없다. `handleRefundIfNecessary`는 있으나 즉시 구매 경로에서 호출하지 않는다 (`NotificationCommandService.java:343-361` 정의만).
- 결제 후 알림/판매상태 갱신(`notifyUsersAndUpdateSaleStatus`)은 전체가 `try/catch(Exception)`으로 감싸져 있어 실패해도 로그만 남기고 삼킨다 (`:383-424`). 알림 전송도 마찬가지다 (`:434-466`, `log.warn`).

## 4. 알림 수신자와 전달 방식

- 수신자 (`NotificationCommandService#sendNotifications`, `:434-455`)
  - 구매자(`order.getUser()`): "결제가 완료되었습니다. 주문 ID: {orderId}" (`:442`)
  - 판매자(`sale.getSeller()`): "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}" (`:453`)
  - 카테고리 `PaymentCategory.SHOPPING`, 타입 `PaymentType.BID` (`:438-455`)
- 시점: 결제 레코드 저장 직후, `processPayment` 내부(`:83`)에서 같은 트랜잭션 안에서 동기적으로 생성된다. 결제 성공/실패/대기와 무관하게 발송된다.
  - 판매 입찰·판매 정보가 없으면 알림 없이 return 한다 (`:391-401`).
- 방식 (`PaymentCommandService#createNotification`, `D/payment/service/command/PaymentCommandService.java:44-67`)
  1. `Payment` 알림 엔티티를 DB에 저장한다 (`isRead=false`, `:241-249`, `:53`).
  2. 이어서 `sendRealTimeNotification`으로 WebSocket 전송을 시도한다 (`:57`).
     - Redis 키 `WebSocket:Product:{email}`가 있을 때(접속 중일 때)만 `/queue/notifications`로 `convertAndSendToUser` 한다 (`:37-38`, `:303-313`).
     - 접속 중이 아니면 DB에만 남는다 (`:320-322`).
- 이메일/푸시/Kafka 알림은 없다. 즉시 구매 경로의 Kafka 토픽 사용은 없다 (`FaqCommandService.java:219-319`).
- 알림 저장은 트랜잭션 안이므로, WebSocket 전송은 커밋 전에 일어난다.

## 5. 최종 주문 상태와 창고 보관 선택 시 차이

- 처리 완료 후 주문(`Faq`)의 최종 상태는 **`PENDING_PAYMENT`** 이다.
  - 생성 시 `PENDING_PAYMENT` (`FaqCommandService.java:244`)이고, 이후 즉시 구매 경로에서 상태를 바꾸는 호출이 없다 (`:219-319` 전체, `FaqBidCommandService.java:118-207` 전체).
  - `PAYMENT_COMPLETED`·`PREPARING`·`COMPLETED`로 가지 않는다. 이름/응답 메시지("즉시 구매가 성공적으로 처리되었습니다.")와 달리 결제 완료 상태가 아니다.
- 함께 남는 상태: `StyleBid=MATCHED`, `FaqBid=MATCHED(isInstantPurchase=true)`, `Style=SOLD`, 결제(`Notification`)는 CARD 성공/GENERAL이면 `PAID`, ACCOUNT이면 `PENDING`.
- **구매자가 "창고 보관"을 선택해도 처리에 아무 차이가 없다.**
  - `warehouseStorage` 플래그는 컨트롤러 로그(`FaqBidCommandController.java:94-95`)와 파라미터 전달(`:104`, `FaqBidCommandService.java:136`)에만 쓰이고, `createInstantOrder`의 `isWarehouseStorage` 파라미터(`FaqCommandService.java:221`)는 본문에서 한 번도 읽지 않는다.
  - 구매자 창고 보관용 `Notice` 생성(`createOrderStorage`)과 `IN_WAREHOUSE`/`COMPLETED` 전환은 `processPaymentAndShipment`(`FaqCommandService.java:163-172`) 경로에만 있고 즉시 구매에서는 호출하지 않는다.
  - 창고 관련 동작은 요청 플래그가 아니라 **판매 상품**의 `sale.isWarehouseStorage()`로 결정된다. 이 값이 true일 때만 기존 창고 `Notice` 상태를 `ASSOCIATED_WITH_ORDER`로 바꾼다 (`FaqCommandService.java:291-294`).
    - 이 경우 판매 상품에 연결된 `Notice`가 없으면 `NoticeNotFoundException`(`NoticeCommandService.java:127`, `NoticeQueryService.java:30-32`)이 `FaqNoticeProcessingFailedException`으로 변환되어(`FaqCommandService.java:295-301`) 즉시 구매 전체가 롤백된다.
