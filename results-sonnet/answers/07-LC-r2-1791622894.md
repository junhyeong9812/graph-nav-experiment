# 즉시 구매 처리 흐름 (POST /order-bids/instant)

경로는 `src/main/java/com/fream/back/domain/` 기준이며, 같은 파일 내 반복 인용은 파일명만 적었다.

## 1. API / 처리 단계 / 동기·비동기 / 응답 ID

- 진입: `POST /order-bids/instant` → `src/main/java/com/fream/back/domain/order/controller/command/OrderBidCommandController.java:89-110` (`@RequestMapping("/order-bids")` 22행). 본문은 `InstantOrderRequestDto`(saleBidId, addressId, warehouseStorage, paymentRequest) — `src/main/java/com/fream/back/domain/order/dto/InstantOrderRequestDto.java:20-29`.
- 단계:
  1. 컨트롤러가 이메일을 꺼내고 `paymentRequest.userEmail`=구매자, `orderId`=null 로 보강 — `OrderBidCommandController.java:98, 119-123`.
  2. `OrderBidCommandService#createInstantOrderBid`(`@Transactional`) — `src/main/java/com/fream/back/domain/order/service/command/OrderBidCommandService.java:118-149`: 입력 검증(154-167) → 구매자 조회(126) → SaleBid/Sale 조회·검증(129-130, 172-184).
  3. `OrderCommandService#createInstantOrder` — `src/main/java/com/fream/back/domain/order/service/command/OrderCommandService.java:219-319`: 주소 조회(238) → Order 저장(241-247) → OrderItem(255) → OrderShipment(264) → SaleBid 매칭 + flush(279-283) → 판매자 창고 상태 변경(289-301) → **결제 처리(305)**.
  4. 결제 직후 `PaymentCommandService#notifyUsersAndUpdateSaleStatus`에서 알림 + Sale→SOLD — `src/main/java/com/fream/back/domain/payment/service/command/PaymentCommandService.java:83, 383-426`.
  5. 마지막으로 OrderBid(MATCHED, 즉시구매 플래그, sale 연결) 저장 — `OrderBidCommandService.java:142, 189-207`.
- **동기 처리**다. Kafka 프로듀서 호출이 이 경로 어디에도 없고, 결제(PortOne HTTP 호출 `PortOneApiClient.java:266`)·알림·상태 변경이 모두 한 요청/한 트랜잭션 안에서 끝난다. (비동기 `order-processing-topic` 경로는 `/orders/{id}/process-payment-shipment` 쪽이며 즉시 구매와 무관.)
- 응답 ID: **OrderBid의 ID**. `createInstantOrderBid(...).getId()`를 `orderId`라는 변수에 담아 `ResponseDto.success(orderId, ...)` 로 반환한다 — `OrderBidCommandController.java:101-109`. 변수명/문구와 달리 Order ID가 아니다(Order ID는 `OrderBid.getOrder().getId()`, 응답에 없음).

## 2. 생성되는 엔티티와 상태 변화 순서

| 순서 | 동작 | 직후 상태 | 근거 |
|---|---|---|---|

| 2 | OrderItem 생성 | (주문 항목, Order에 추가) | `OrderCommandService.java:255-256` |
| 3 | OrderShipment 생성 | OrderShipment = `PENDING` (주소록의 수령인/전화/우편번호/주소 복사) | `src/main/java/com/fream/back/domain/shipment/service/command/OrderShipmentCommandService.java:56-75`(67행) |
| 4 | `SaleBid.assignOrder(order)` + `updateStatus(MATCHED)` + flush | SaleBid = `MATCHED` | `OrderCommandService.java:279-283`, `src/main/java/com/fream/back/domain/sale/entity/SaleBid.java:58-61, 66-68` |
| 5 | Sale.isWarehouseStorage 이면 판매자 창고 보관 항목 `updateWarehouseStatus(sale, ASSOCIATED_WITH_ORDER)` | WarehouseStorage = `ASSOCIATED_WITH_ORDER` | `OrderCommandService.java:291-294`, `src/main/java/com/fream/back/domain/warehouseStorage/service/command/WarehouseStorageCommandService.java:117-133` |
| 6 | Payment 생성(카드/계좌/일반) | 결제수단별로 아래 3번 | `PaymentCommandService.java:67-80` |
| 7 | Sale → SOLD (알림 전송 직후) | Sale = `SOLD` | `PaymentCommandService.java:404` (SaleBid 경로; `order.getOrderBid()`가 아직 null이라 `findByOrderId`로 SaleBid를 찾음 388-391) |
| 8 | OrderBid 생성·저장 | OrderBid = `MATCHED`, isInstantPurchase=true, sale 연결 | `OrderBidCommandService.java:192-206`; `OrderBid.assignOrder`가 MATCHED로 세팅 `src/main/java/com/fream/back/domain/order/entity/OrderBid.java:60-82` |

- Order 상태는 3번 이후 **어디서도 바뀌지 않는다**(`PENDING_PAYMENT` 유지). 아래 5번 참고.
- 세 단계(결제 알림/Sale SOLD)가 OrderBid 저장보다 먼저라 `order.getOrderBid()`는 항상 null이다(Order 생성 직후라서) — 그래서 `PaymentCommandService.java:388-407` 의 SaleBid 분기만 실행된다.

## 3. 결제 수단별 결과

핵심: 전체가 하나의 `@Transactional`(`OrderBidCommandService.java:118`, `PaymentCommandService.java:37`)이고, 결제 예외는 `OrderPaymentProcessingFailedException`으로 감싸져(`OrderCommandService.java:306-309`) `OrderException`이라 그대로 다시 던져진다(`OrderBidCommandService.java:145-147, 212-218`). 예외가 나면 Order·OrderItem·OrderShipment·SaleBid 매칭·창고 상태·Payment가 모두 롤백된다. 응답은 오류 응답.

- **GENERAL(일반 결제)**: impUid 필수, 클라이언트가 보낸 값을 그대로 신뢰해 `isSuccess=true`, `PAID` 저장 — `PaymentCommandService.java:290-318`. PortOne 서버 검증 없음. 끝까지 성공(Sale SOLD, 알림, OrderBid 저장).
- **CARD(카드)**: 저장된 PaymentInfo로 `portOneApiClient.processCardPayment` 호출(179). 응답 `status == "success"` 이면 `PAID`+`isSuccess=true`(203-206). 끝까지 성공.
- **ACCOUNT(계좌이체)**: **항상 실패**한다. `Payment.status` 기본값이 `PENDING`(`src/main/java/com/fream/back/domain/payment/entity/Payment.java:44`)인데 `accountPayment.updateStatus(PaymentStatus.PENDING)`(`PaymentCommandService.java:260`)을 호출하고, `PENDING.canTransitionTo(PENDING)`은 false(`src/main/java/com/fream/back/domain/payment/entity/PaymentStatus.java:12-13`)라 `IllegalStateException`(`Payment.java:70-76`). 이는 `catch (Exception)`(274-278)에서 `PaymentProcessingException`으로 바뀌어 전파 → 전체 롤백. 즉 계좌이체로는 즉시 구매가 성사되지 않는다(의도는 "PENDING 대기"로 보이나 실제는 예외).
- 따라서 **끝까지 성공하는 경우는 CARD(성공 응답)와 GENERAL뿐**이다. 그리고 "성공"이어도 Order는 `PENDING_PAYMENT`로 끝난다(5번).
- **PortOne이 카드 결제를 실패로 응답하면**:
  - HTTP≠200 이거나 응답 `code != 0`: `PaymentProcessingException("카드 결제 요청 실패: …")` — `PortOneApiClient.java:270-275` → 위와 같이 전체 롤백, 오류 응답. Sale은 SOLD가 되지 않고 알림도 롤백(같은 트랜잭션)된다.
  - HTTP 4xx/5xx 등으로 `RestClientException`: `PaymentApiException` — `PortOneApiClient.java:288-290`. `@Retryable(PaymentApiException, 3회, 1초)`(224-228) 대상이지만 같은 클래스 내부 호출이 아니라 외부 빈 호출이므로 재시도 후 실패하면 마찬가지로 롤백.
  - **code==0 이지만 `response.status`가 "success"가 아닌 경우**(예: 승인 거절 "failed"): 예외가 없다. `status`=`PENDING`, `isSuccess=false`인 CardPayment가 그대로 저장되고(`PaymentCommandService.java:187-208`, 기본값 `Payment.java:39,44`) 흐름이 계속되어 구매자/판매자에게 "결제가 완료되었습니다" 알림이 가고 Sale이 SOLD로 바뀐다(`83, 404, 438-454`). 결제 성공 여부(`isSuccess`)는 어디서도 확인하지 않는다. 즉 이 경우 결제는 실패인데 거래는 성립한 것처럼 처리된다.
- 금액 검증은 `paidAmount > 0` 뿐이며(`PaymentCommandService.java:142-145`) saleBid 가격과 비교하지 않는다. 주문 ID/이메일 일치만 확인(131-139).

## 4. 알림 (누가, 언제, 어떻게)

- 수신자 2명, **결제 처리 직후 같은 요청/트랜잭션 안에서 동기적으로** 생성: `PaymentCommandService.java:83 → 416(또는 403) sendNotifications`, `434-462`.
  - 구매자: "결제가 완료되었습니다. 주문 ID: {orderId}" (카테고리 SHOPPING, 타입 BID) — `PaymentCommandService.java:436-443`.
  - 판매자(`sale.getSeller()`): "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}" — `447-454`.
- 전달 방식: `NotificationCommandService#createNotification`이 DB에 Notification 저장 후 `sendRealTimeNotification` 호출 — `src/main/java/com/fream/back/domain/notification/service/command/NotificationCommandService.java:44-57`. Redis 키 `WebSocket:User:{email}`가 있는(=접속 중) 사용자에게만 STOMP `/user/{email}/queue/notifications`로 푸시(303-313); 미접속이면 저장만 한다(320-322). Kafka `notification-topic`은 이 경로에서 쓰이지 않는다.
- 알림 실패는 삼켜진다(`PaymentCommandService.java:457-461`, 421-425) — 단, 알림 저장/전송은 호출 순서상 결제 후이므로 이후 예외가 나면 같은 트랜잭션 롤백으로 알림 행도 사라진다. 이 경로에서 이후 예외 가능성은 OrderBid 저장 단계(142)뿐이다.
- 판매 입찰 시 SaleBid 쪽 별도 알림(판매자에게 "매칭됨" 등)은 즉시 구매 경로에 없다. 배송 관련 알림도 없다.

## 5. 최종 주문 상태 / 창고 보관 선택 시

- **Order 최종 상태 = `PENDING_PAYMENT`**. 생성 시 `PENDING_PAYMENT`(`OrderCommandService.java:244`) 이후 결제 성공 여부와 무관하게 `PAYMENT_COMPLETED`/`PREPARING`으로 바꾸는 코드가 즉시 구매 경로에 없다(그 전이는 Kafka 소비자 `OrderEventConsumer`에만 있음). 결제 완료 알림과 Sale=SOLD, Payment=PAID가 되었어도 Order는 결제 대기 상태로 남는다. 반면 SaleBid·OrderBid는 MATCHED, Sale은 SOLD, OrderShipment는 PENDING.
- **"창고 보관" 요청 플래그는 사실상 무시된다.** `isWarehouseStorage` 파라미터는 `createInstantOrder` 시그니처(219-221)에 있으나 본문에서 한 번도 참조되지 않는다. 구매자용 창고 보관(`createOrderStorage`, IN_WAREHOUSE→COMPLETED 등)은 즉시 구매 경로에서 호출되지 않는다. 달라지는 것은 **판매 쪽 Sale의 `isWarehouseStorage`** 뿐이다:
  - Sale이 창고 보관(판매자가 센터에 맡기는 방식)이면 `updateWarehouseStatus(sale, ASSOCIATED_WITH_ORDER)` 실행(`OrderCommandService.java:291-294`). 창고 레코드가 없으면(판매자가 아직 발송 전이라 `createSellerStorage`가 안 불린 경우) `WarehouseStorageNotFoundException`(`WarehouseStorageQueryService.findBySale` 30-33행)이 나 `OrderWarehouseStorageProcessingFailedException`(296-297)으로 즉시 구매 전체가 실패/롤백된다.
  - 상태 전이 규칙은 `WarehouseStorageCommandService.java:232-257`(IN_STORAGE→ASSOCIATED_WITH_ORDER 허용, SOLD에서는 불가).
  - 이후 구매자 송장 등록 시 창고가 SOLD가 되는 흐름은 별개(`nav/flow-trade.md` §6).
- 요약: 구매자가 `warehouseStorage=true`로 보내도 구매자 측 동작(주문 상태, 구매 보관 생성)은 `false`일 때와 동일하다.
