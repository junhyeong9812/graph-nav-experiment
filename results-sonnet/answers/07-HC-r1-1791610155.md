# 즉시 구매 처리 흐름 분석

경로 약어: `D` = `src/main/java/com/fream/back/domain`

## 1. 진입 API / 처리 단계 / 동기 여부 / 응답 ID

**API**: `POST /order-bids/instant` (`D/order/controller/command/OrderBidCommandController.java:22,89-90`). 요청 본문은 `InstantOrderRequestDto`(saleBidId, addressId, warehouseStorage, paymentRequest) (`D/order/dto/InstantOrderRequestDto.java:20-29`).

**처리 단계 (모두 한 요청 스레드, 한 트랜잭션 안에서 동기 처리)**
1. 컨트롤러가 이메일을 추출하고, `paymentRequest`에 userEmail을 넣고 orderId는 null로 둔다 (`OrderBidCommandController.java:92,98,119-122`).
2. `OrderBidCommandService.createInstantOrderBid` (`@Transactional`, `D/order/service/command/OrderBidCommandService.java:118-149`)
   - 입력 검증 → 구매자 조회 → SaleBid·Sale 조회 (`:123-130`, `:172-184`)
   - `orderCommandService.createInstantOrder(...)` 호출 (`:133`)
3. `OrderCommandService.createInstantOrder` (`@Transactional`, `D/order/service/command/OrderCommandService.java:219-319`)
   - 주소 조회 (`:238`) → Order 저장 (`:241-247`) → paymentRequest.orderId 설정 (`:250`) → OrderItem (`:255-256`) → OrderShipment (`:264-271`) → SaleBid 매칭 + flush (`:279-283`) → 창고 상태 갱신 (`:291-293`) → 결제 (`:305`)
4. 그 뒤 OrderBid를 만들어 저장한다 (`OrderBidCommandService.java:142`, `:189-207`).

**동기/비동기**: 동기다. 이 경로에는 Kafka가 없다. Kafka를 쓰는 것은 별도 API `POST /orders/{orderId}/process-payment-shipment`(`D/order/controller/command/OrderCommandController.java:42-69`, `OrderEventConsumer.java:55-110`)이며 즉시 구매 흐름에서는 호출되지 않는다. 컨트롤러 Javadoc/응답 문구의 "즉시 구매가 성공적으로 처리되었습니다"와 달리, 결제가 실패해도 정상 응답이 나갈 수 있다(3번 참조).

**응답 ID**: Order ID가 아니라 **OrderBid의 ID**다. 컨트롤러가 `orderBidCommandService.createInstantOrderBid(...).getId()`를 `orderId` 변수에 담아 돌려준다 (`OrderBidCommandController.java:101-109`). 서비스가 반환하는 객체가 `OrderBid`이기 때문이다 (`OrderBidCommandService.java:119,142-144`). 변수 이름은 `orderId`지만 실제 값은 `OrderBid.id`다 (`D/order/entity/OrderBid.java:23-25`).

## 2. 새로 생기는 엔티티와 상태 변화 순서

| 순서 | 동작 | 직후 상태 | 근거 |
|---|---|---|---|
| 1 | **Order** 생성·저장 | `OrderStatus.PENDING_PAYMENT`, totalAmount = saleBid.bidPrice | `OrderCommandService.java:241-247` |
| 2 | **OrderItem** 생성 (수량 1, 가격 = bidPrice) | 상태 필드 없음 | `OrderCommandService.java:255-256`, `D/order/service/command/OrderItemCommandService.java:45-52` |
| 3 | **OrderShipment** 생성 (저장된 주소 사용) | `ShipmentStatus.PENDING` | `OrderCommandService.java:264-271`, `D/shipment/service/command/OrderShipmentCommandService.java:56-70` |
| 4 | 기존 **SaleBid**: order 연결, 상태 갱신 후 flush | `sale.BidStatus.MATCHED` (초기값 PENDING) | `OrderCommandService.java:279-283`, `D/sale/entity/SaleBid.java:35-37,58-64` |
| 5 | 기존 **WarehouseStorage**(판매자 물건): `Sale.isWarehouseStorage`가 true일 때만 | `WarehouseStatus.ASSOCIATED_WITH_ORDER` | `OrderCommandService.java:291-293`, `D/warehouseStorage/service/command/WarehouseStorageCommandService.java:117-133` |
| 6 | **Payment** 생성 (결제 수단별, 3번 참조) | 카드 성공 `PAID`, 계좌이체 `PENDING`, 일반 `PAID` | `PaymentCommandService.java:187-208,250-262,302-316` |
| 7 | 기존 **Sale** 상태 갱신 (결제 직후 `notifyUsersAndUpdateSaleStatus`) | `SaleStatus.SOLD` | `D/payment/service/command/PaymentCommandService.java:83,388-407` |
| 8 | **OrderBid** 생성·저장 | `order.BidStatus.MATCHED`, `isInstantPurchase = true` | `OrderBidCommandService.java:192-206`, `OrderBid.java:97-99` |

- 7번 시점에 `order.getOrderBid()`는 아직 null이다(OrderBid가 8번에서 만들어진다). 그래서 `saleBidQueryService.findByOrderId`로 SaleBid를 찾아 그 Sale을 쓴다 (`PaymentCommandService.java:388-406`). 4번에서 flush해 둔 덕분에 조회된다 (`D/sale/repository/SaleBidRepository.java:10`).
- 상태 갱신은 Payment 외에는 전이 규칙 검증이 없다. SaleBid/Sale/OrderBid의 `updateStatus`가 값을 그냥 대입한다.
- 이 경로는 `Order.updateStatus`를 호출하지 않는다. 따라서 Order 상태는 위 모든 단계 동안 `PENDING_PAYMENT`다.
- `createInstantOrder`는 `processPayment`가 반환한 `Payment`를 버린다 (`OrderCommandService.java:305`). `order.assignPayment`도 `payment.isSuccess()` 검사도 하지 않는다. 반면 Kafka 경로는 둘 다 한다 (`OrderEventConsumer.java:171-176`).

## 3. 결제 수단별 결과

`switch (resolvedPaymentType)`로 분기한다 (`PaymentCommandService.java:67-80`).

| 수단 | 동작 | Payment 상태 / isSuccess | 근거 |
|---|---|---|---|
| CARD | 저장된 PaymentInfo로 PortOne API를 호출하고 응답을 저장한다 | 응답 `status`가 `"success"`면 `PAID`/true, 아니면 기본값 `PENDING`/false | `PaymentCommandService.java:166-208`, `D/payment/entity/Payment.java:38-44` |
| ACCOUNT | 은행명만 검증하고 외부 호출 없이 저장 | `PENDING` / false (이후 갱신 없음) | `PaymentCommandService.java:244,250-262` |
| GENERAL | impUid 필수 확인 후 외부 호출 없이 클라이언트가 준 값을 신뢰 | `PAID` / true | `PaymentCommandService.java:297-316` |

**끝까지 성공하는가**: 예외가 없으면 수단에 상관없이 끝까지 "성공"으로 끝난다. 이유는 다음과 같다.
- `notifyUsersAndUpdateSaleStatus`는 payment 상태를 확인하지 않는다. 계좌이체(PENDING)이든 카드 실패이든 구매자·판매자 알림을 보내고 Sale을 `SOLD`로 바꾼다 (`PaymentCommandService.java:83,403-404,416-419`). 알림 문구도 "결제가 완료되었습니다"다 (`:438-443`). 결제가 미완료여도 Sale은 `SOLD`가 된다.
- `createInstantOrder`가 payment 결과를 검사하지 않고 Order를 반환하므로 (`OrderCommandService.java:305-311`), 컨트롤러는 200과 "즉시 구매가 성공적으로 처리되었습니다"를 돌려준다 (`OrderBidCommandController.java:109`).

**PortOne이 카드 결제를 실패로 응답하면** 응답 형태에 따라 두 갈래다.
1. HTTP 200이 아니거나 최상위 `code != 0`이면 `PaymentProcessingException`이 던져진다 (`D/payment/portone/PortOneApiClient.java:270-275`). 통신 오류는 `PaymentApiException`이 되고 `@Retryable`로 최대 3회 재시도한다 (`PortOneApiClient.java:224-229`, `:288-290`). 예외는 `processPayment`에서 `OrderPaymentProcessingFailedException`으로 감싸져 (`OrderCommandService.java:306-309`) 트랜잭션 전체가 롤백된다. Order, OrderItem, Shipment, SaleBid 매칭, OrderBid가 모두 취소되고 클라이언트는 오류 응답을 받는다.
2. `code == 0`이지만 `response.status`가 `"success"`가 아닌 경우(예: failed)는 예외가 없다. `PENDING`/`isSuccess=false`인 CardPayment가 저장되고 (`PaymentCommandService.java:203-208`), 이후는 위 "끝까지 성공" 경로를 그대로 탄다. 즉 Sale `SOLD`, 구매자·판매자 "결제 완료" 알림, SaleBid/OrderBid `MATCHED`, 컨트롤러 200 성공이 모두 일어난다. 주문은 결제 없이 `PENDING_PAYMENT`로 남는다. 이것이 의도와 실제 동작의 불일치다.
   - 참고: 성공 판정이 `"success".equals(response.get("status"))`라서, 응답이 다른 성공 문자열을 쓰면 정상 결제도 PENDING으로 저장된다(코드 기준 사실은 문자열 비교뿐이다).

## 4. 알림

- **받는 사람**: 구매자(`order.getUser()`)와 판매자(`sale.getSeller()`) 두 명이다 (`PaymentCommandService.java:436-456`).
  - 구매자 메시지: "결제가 완료되었습니다. 주문 ID: {orderId}" (`:438-443`)
  - 판매자 메시지: "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}" (`:449-454`)
  - 둘 다 카테고리 `SHOPPING`, 타입 `BID`다.
- **시점**: `processPayment` 안에서 Payment 저장 직후, 같은 요청 스레드·같은 트랜잭션 안이다 (`PaymentCommandService.java:83`, `OrderCommandService.java:305`). OrderBid 생성 전이고 커밋 전이다.
- **방식**: `NotificationCommandService.createNotification`이 Notification 엔티티를 DB에 저장하고 (`D/notification/service/command/NotificationCommandService.java:44-54`), 이어서 WebSocket 실시간 전송을 시도한다 (`:57`). 전송은 Redis 키 `WebSocket:User:{email}`이 있는, 즉 접속 중인 사용자에게만 `convertAndSendToUser(email, "/queue/notifications", ...)`로 한다 (`:303-313`). 접속 중이 아니면 저장만 된다 (`:320-322`). Kafka는 쓰지 않는다.
- **실패 처리**: `sendNotifications`는 예외를 삼키고 경고 로그만 남긴다 (`PaymentCommandService.java:457-461`). 그래서 알림 실패가 주문을 막지 않는다.
- **Kafka 경로와 구분**: `OrderEventConsumer`의 `ORDER_COMPLETED` WebSocket 알림과 `notification-topic` 발행 (`OrderEventConsumer.java:287-324`)은 `/orders/{id}/process-payment-shipment` 경로에서만 나가며, 즉시 구매 API에서는 나가지 않는다. 즉시 구매 API는 위 두 건의 알림만 보낸다.

## 5. 최종 주문 상태 / 창고 보관

**주문의 최종 상태**: `OrderStatus.PENDING_PAYMENT`이다. 요청이 끝났을 때 `PAYMENT_COMPLETED`, `PREPARING`, `COMPLETED` 어느 것으로도 바뀌지 않는다. `createInstantOrder`에는 `updateStatus` 호출이 없고 (`OrderCommandService.java:219-319`), Order는 `PENDING_PAYMENT`로 생성되어 (`:244`) 그대로 반환된다. 결제가 성공(카드 `PAID`, 일반 `PAID`)해도 Order 상태는 변하지 않는다. 같은 트랜잭션에서 바뀌는 것은 SaleBid `MATCHED`, Sale `SOLD`, OrderBid `MATCHED`이고, Order만 결제 대기에 머문다. 이름이 말하는 "즉시 구매 완료"와 다르다. `PAYMENT_COMPLETED` 이후 전이는 별도 API(`/orders/{id}/process-payment-shipment`)가 호출되어야 일어난다 (`OrderEventConsumer.java:192-220`).

**구매자가 "창고 보관"을 선택한 경우**: 아무것도 달라지지 않는다.
- `isWarehouseStorage` 인자는 `createInstantOrder` 시그니처에만 있고 본문에서 한 번도 쓰이지 않는다 (`OrderCommandService.java:220-221`, 본문 `:222-318` 전체). `OrderBidCommandService`는 인자를 그대로 넘기기만 한다 (`OrderBidCommandService.java:133-139`).
- 그래서 구매자용 `WarehouseStorage`(`createOrderStorage`, `IN_STORAGE`)도 만들어지지 않고 (`WarehouseStorageCommandService.java:33-57`는 이 흐름에서 호출되지 않는다), `IN_WAREHOUSE`/`COMPLETED` 전이도 일어나지 않는다. 배송정보(OrderShipment)는 `isWarehouseStorage` 값과 무관하게 항상 만들어진다 (`OrderCommandService.java:264-271`).
- 창고와 관련된 유일한 분기는 **판매자 쪽** `Sale.isWarehouseStorage`다 (`D/sale/entity/Sale.java:43`). 이 값이 true이면 판매자가 맡긴 WarehouseStorage가 `ASSOCIATED_WITH_ORDER`로 바뀐다 (`OrderCommandService.java:291-293`). 해당 보관 정보가 없으면 예외가 나 전체가 롤백된다 (`WarehouseStorageCommandService.java:127-130,134-138`, `OrderCommandService.java:295-300`).
- `OrderEventConsumer`/`processPaymentAndShipment`의 창고 보관 분기(`PAYMENT_COMPLETED → PREPARING → IN_WAREHOUSE → COMPLETED`)는 `OrderCommandService.java:163-172`, `OrderEventConsumer.java:197-212`에 있지만, 즉시 구매 요청 자체가 타는 코드가 아니다.
