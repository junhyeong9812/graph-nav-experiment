# 구매자 배송: 운송장 등록 → 배송 완료 (실제 코드 동작 기준)

경로 약어: `S` = `src/main/java/com/fream/back/domain/shipment`, `O` = `src/main/java/com/fream/back/domain/order`, `G` = `src/main/java/com/fream/back/global`.

## 1. 운송장 등록 요청

### 1-1. 진입 API
1. `PATCH /shipments/order/{shipmentId}/status` (body: courier, trackingNumber) → `OrderShipmentCommandController#updateTrackingInfo` (`S/controller/command/OrderShipmentCommandController.java:33-49`) → `OrderShipmentCommandService#updateTrackingInfo` (`S/service/command/OrderShipmentCommandService.java:239`).
2. 소유자·권한 검증은 없다(인증만 필요). 컨트롤러는 예외를 잡지 않으므로 `GlobalExceptionHandler`가 처리한다.
3. 대체 경로: `POST /shipments/order/{id}/check-status` → `updateAndCheckShipmentStatus` (`OrderShipmentCommandService.java:452`, 컨트롤러 `OrderShipmentCommandController.java:58-94`). 이 경로는 송장 갱신 직후 CJ를 즉시 조회한다.

### 1-2. 의도된 상태 변경 순서와 알림 (`OrderShipmentCommandService.java:239-303`)
1. 입력 검증: courier/trackingNumber가 비면 `TRACKING_INFO_REQUIRED` (`:243-246`).
2. OrderShipment: `updateTrackingInfo`가 검증 없이 courier/trackingNumber 저장 + status=`IN_TRANSIT` (`:256`, `S/entity/OrderShipment.java:41-45`).
3. Order: `order.updateStatus(OrderStatus.IN_TRANSIT)` (`:260`).
4. 알림 ① 구매자에게 "상품이 출발하였습니다. 주문 ID: …" 1건 (`:265-271`).
5. `updateSaleStatusToSold(orderId)` (`:276`, 본문 `:112-183`): SaleBid 경로·OrderBid 경로에서 Sale이 SOLD로 전이 가능하면 Sale→SOLD, 창고 보관이면 창고 SOLD, 알림 ② 판매자에게 "상품이 성공적으로 판매 완료되었습니다" (`:116-147`, `:150-180`).
6. SaleBid의 Sale이 창고 보관이면 `updateWarehouseStatusToSold` (`:279-286`).
7. `updateOrderAndSaleBidStatusToCompleted` (`:289`, 본문 `:413-440`): OrderBid MATCHED→COMPLETED, SaleBid MATCHED→COMPLETED. 실패해도 로그만 남긴다(`:436-439`). 이 메서드는 `@Transactional private`이라 프록시 트랜잭션이 적용되지 않는다(`:412-413`).
- 즉 의도상 "운송장 등록 시점"에 Sale/입찰이 이미 SOLD/COMPLETED가 된다(배송 완료 시점이 아님).

### 1-3. 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문은 끝까지 성공하나? → **아니오, 항상 실패**
- 이 주문의 상태: 결제 후 `OrderEventConsumer`가 PENDING_PAYMENT→PAYMENT_COMPLETED→**PREPARING**으로 만든다 (`O/service/kafka/OrderEventConsumer.java:195`, `:215-217`; 창고 보관이 아닌 "실제 배송" 분기).
- 실패 지점: `OrderShipmentCommandService.java:260`의 `order.updateStatus(IN_TRANSIT)`. `Order#updateStatus`는 허용 전이가 아니면 `InvalidOrderStatusException`을 던진다 (`O/entity/Order.java:113-121`). PREPARING에서 허용되는 다음 상태는 `IN_WAREHOUSE`, `SHIPMENT_STARTED`뿐이고 (`O/entity/OrderStatus.java:26`), IN_TRANSIT는 SHIPMENT_STARTED에서만 가능하다 (`:28`). SHIPMENT_STARTED를 설정하는 코드는 없다.
- 예외 래핑: `InvalidOrderStatusException`은 `OrderException`→`GlobalException`이지 `ShipmentException`이 아니므로 (`O/exception/InvalidOrderStatusException.java:6`, `OrderException.java:10`) `catch (ShipmentException)`(`:293`)을 지나 `catch (Exception)`(`:295-302`)에 걸려 `ShipmentException(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")`로 바뀐다.
- 저장되는 것: 없음. 메서드가 `@Transactional`(`:238`)이고 런타임 예외로 빠져나가므로 2단계의 shipment 변경(IN_TRANSIT, 송장번호)과 Order 변경 모두 롤백된다. 알림(4~5단계)·Sale/입찰 변경은 이 지점 이전에 도달하지 않는다(알림은 `:266` 이후라 생성되지 않음). OrderShipment는 PENDING, 송장번호 null 그대로.
- 응답: 컨트롤러가 잡지 않으므로 `GlobalExceptionHandler#handleGlobalException` (`G/exception/GlobalExceptionHandler.java:49-60`)이 **HTTP 404**, 코드 `S001`, 메시지는 enum 기본 문구 "배송 정보를 찾을 수 없습니다."의 `ErrorResponse`를 반환한다 (`S/exception/ShipmentErrorCode.java:12`; 상세 메시지는 응답에 쓰이지 않고 `errorCode.getMessage()`만 사용 `:57-60`).
- 별개로, 이 주문에 SaleBid가 연결되지 않은 경우 `SaleBidQueryService#findByOrderId`가 `IllegalArgumentException`을 던지므로(`O` 아닌 `sale/service/query/SaleBidQueryService.java:26-29`) 설령 4단계를 통과해도 `updateSaleStatusToSold`의 `:116`에서 같은 식으로 실패한다.

## 2. 배송 완료 감지

### 2-1. 누가/언제/어떻게
1. **스케줄러(자동)**: `ShipmentBatchScheduler#scheduleShipmentStatusJob` `@Scheduled(cron = "0 0 */6 * * *")` — **6시간마다**(00/06/12/18시 정각) (`G/config/ShipmentBatchScheduler.java:34-44`). `JobLauncher.run(updateShipmentStatusesJob, timestamp)`.
2. **수동**: `POST /shipments/order/{id}/check-status(-string)` (위 1-1의 3번).
3. 대상 조회: Reader JPQL `SELECT s FROM OrderShipment s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL`, 페이지 50 (`S/config/UpdateShipmentStatusesJobConfig.java:87-97`).
4. 스텝 구성: chunk 50, faultTolerant, `skip(Exception.class)`, skipLimit 50 (`:51-52`, `:66-81`). Writer는 `JpaItemWriter` (`:239-246`).

### 2-2. 실제로 실행되는 처리 코드
- 스텝에 연결된 것은 `new ShipmentItemProcessor(playwrightBrowserManager(), notificationService, orderService)` (`UpdateShipmentStatusesJobConfig.java:69-73`) → **`S/config/ShipmentItemProcessor.java#process` (`:57-157`)** 가 실제 실행 코드다. 공유 Playwright 브라우저로 `https://trace.cjlogistics.com/next/tracking.html?wblNo=<운송장>`을 열고 `tbody#statusDetail tr` 마지막 행의 5번째 td 텍스트를 Jsoup으로 파싱한다 (`:28-29`, `:72-94`, `:167-191`). 브라우저는 `BrowserManageStepListener`가 스텝 전후로 열고 닫는다 (`UpdateShipmentStatusesJobConfig.java:80`).
- 실행되지 않는 유사 코드(사용 금지 대상): `UpdateShipmentStatusesJobConfig#shipmentItemProcessor()` 빈 (`:104-177`, 스텝에서 참조 안 함)과 `parseCjLogisticsStatus` (`:186`), 서비스의 `OrderShipmentCommandService#updateShipmentStatuses` (`:309-391`, 호출처 없음 — Order만 COMPLETED로 바꾸고 판매/입찰은 건드리지 않는 구버전).
- 수동 API용은 `CjTrackingPlaywright#getCurrentTrackingStatus`(매 호출 새 Playwright)이며 배치 경로가 아니다 (`OrderShipmentCommandService.java:477`).

### 2-3. 택배사 문자열 → 내부 상태 (`ShipmentItemProcessor.java:220-226`)
- `"배송완료"` → `DELIVERED`, `"배송출발"` → `OUT_FOR_DELIVERY`, 그 외 모든 문자열 → `IN_TRANSIT` (정확히 일치 비교).
- 처리 분기 (`:100-126`): 현재 상태와 같으면 변경 없이 반환(`:101-105`); DELIVERED면 완료 처리; OUT_FOR_DELIVERY면 `updateStatus(OUT_FOR_DELIVERY)`; 그 외 `updateStatus(IN_TRANSIT)`. 단 IN_TRANSIT→IN_TRANSIT는 위 "같으면 반환"으로 걸러지고, OUT_FOR_DELIVERY 상태에서 "그 외" 문자열이 오면 OUT_FOR_DELIVERY→IN_TRANSIT는 전이표에 없어 `IllegalStateException`이 난다 (`S/entity/ShipmentStatus.java:23-28`, `OrderShipment.java:47-55`) → `EXTERNAL_TRACKING_SERVICE_ERROR(S302)`로 래핑 (`:138-144`).

## 3. 배송 완료 판정 이후 (배치 `ShipmentItemProcessor` 기준)

### 3-1. 상태 변경 순서 (`ShipmentItemProcessor.java:108-117`, `OrderShipmentCommandService.java:191-229`)
1. OrderShipment: `updateStatus(DELIVERED)` (IN_TRANSIT/OUT_FOR_DELIVERY→DELIVERED 허용, `ShipmentStatus.java:19-21,26`) — 메모리에서 변경, Writer가 저장.
2. `OrderShipmentCommandService#completeOrder(orderId)`:
   1. `OrderBidQueryService#findByOrderId`로 OrderBid 조회, 없으면 `IllegalArgumentException` (`:196-197`).
   2. **Order: `updateStatus(COMPLETED)`** (`:204`).
   3. `updateSaleStatusToSold(orderId)` (`:208`): SaleBid의 Sale / OrderBid의 Sale이 `canTransitionTo(SOLD)`일 때만 Sale→SOLD(+창고 SOLD, 판매자 알림). `SaleStatus`상 SOLD로 갈 수 있는 것은 ON_AUCTION, SELLING뿐이다 (`sale/entity/SaleStatus.java:21-22`).
   4. 구매자 알림 "[completeOrder] 주문이 완료 처리되었습니다. 주문 ID" (`:211-217`).
3. `NotificationCommandService#notifyShipmentCompleted(order)` — 구매자 알림 "[배송 완료] 상품이 배송 완료되었습니다. 주문 ID" (`ShipmentItemProcessor.java:117`, `notification/service/command/NotificationCommandService.java:219-234`).
4. Writer(`JpaItemWriter`)가 OrderShipment 저장.

### 3-2. 알림 (정상 완료 시)
- 구매자: **2건** ("[completeOrder] …" + "[배송 완료] …").
- 판매자: Sale이 이 시점에 SOLD로 전이 가능했을 때만 "판매 완료" 1건(경로가 SaleBid/OrderBid 둘 다 해당하면 최대 2건이나, 첫 전이 후 SOLD가 되어 두 번째는 불가 → 실질 최대 1건). 이미 SOLD면 0건.

### 3-3. 입찰 상태
- `completeOrder` 경로는 OrderBid/SaleBid 상태를 **전혀 바꾸지 않는다**. MATCHED→COMPLETED 변경은 `updateOrderAndSaleBidStatusToCompleted`뿐이고 이는 `updateTrackingInfo`(운송장 등록)에서만 호출된다 (`:289`, 정의 `:413`). 따라서 배송 완료 판정만 거친 주문의 OrderBid·SaleBid는 MATCHED로 남는다(운송장 등록이 성공했던 경우에만 COMPLETED).

## 4. 주문 종류별 차이

### (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문 — **끝까지 진행되지 않음**
- Order 상태는 PREPARING (`OrderEventConsumer.java:215-217`). `completeOrder`의 `order.updateStatus(COMPLETED)`(`OrderShipmentCommandService.java:204`)에서 `InvalidOrderStatusException`: PREPARING의 허용 전이는 IN_WAREHOUSE/SHIPMENT_STARTED뿐 (`OrderStatus.java:26`). `catch (Exception)`이 `ShipmentException(ORDER_NOT_FOUND_FOR_SHIPMENT, S102)`로 감싸 던진다 (`:221-228`).
- 결과: Order는 PREPARING 유지, Sale·입찰·창고 변경 없음, 알림 0건(`completeOrder`의 알림은 `:208` 이후라 미도달, `notifyShipmentCompleted`도 `:117`에서 예외로 미도달). 메모리상의 OrderShipment DELIVERED 변경은 스킵된 아이템이라 저장되지 않아 shipment는 IN_TRANSIT/OUT_FOR_DELIVERY로 남고, 6시간마다 재조회·재실패한다.
- 참고: 이 주문의 shipment는 1-3 때문에 운송장 API로는 IN_TRANSIT가 되지 못한다. 배치 대상이 되려면 `check-status`(송장 갱신 시 `OrderShipment#updateTrackingInfo`가 IN_TRANSIT 설정, Order는 건드리지 않음)가 커밋돼야 하는데, CJ 결과가 OUT_FOR_DELIVERY일 때만 커밋된다 (`:473`, `:491-493`; CJ 결과가 그 외면 IN_TRANSIT→IN_TRANSIT `IllegalStateException`→S302로 롤백, `:497`). DELIVERED면 위와 같은 `completeOrder` 실패로 롤백.

### (b) 즉시 구매로 만들어진 주문 — **완료 처리 진행됨**
- 즉시 구매 Order는 PENDING_PAYMENT로 만들어지고 이후 바뀌지 않는다 (`O/service/command/OrderCommandService.java:241-245`; 결제 후 상태 전이 코드 없음). `PENDING_PAYMENT`→`COMPLETED`는 허용된다 (`OrderStatus.java:24`). OrderBid(MATCHED, 즉시구매, order·sale 연결)와 SaleBid(order 연결)가 존재해 조회가 성공한다 (`O/service/command/OrderBidCommandService.java:189-206`, `OrderCommandService.java:279-280`).
- 결과: Order→COMPLETED, OrderShipment→DELIVERED. Sale은 결제 시점에 이미 SOLD이므로 `canTransitionTo(SOLD)`가 false(`SaleStatus.java:23`) → Sale/창고/판매자 알림 변경 없음(`OrderShipmentCommandService.java:119`, `:156`). 구매자 알림 2건. OrderBid/SaleBid는 MATCHED 유지(3-3).
- 주의: (b)의 운송장 API 등록 자체도 `order.updateStatus(IN_TRANSIT)`(PENDING_PAYMENT→IN_TRANSIT 불허)로 실패하므로, 배치 대상이 되는 경로는 위 (a)와 같이 `check-status`뿐이다.

## 5. 실패 처리 (주기 처리 중 한 건 실패)
- Step이 `faultTolerant().skip(Exception.class).skipLimit(50)` (`UpdateShipmentStatusesJobConfig.java:75-77`)이므로 Processor 예외(S102/S302/S303, 파싱 오류 `TRACKING_HTML_PARSE_ERROR` 등 — `ShipmentItemProcessor.java:133-145`)는 그 건만 skip되고 `shipmentSkipListener`가 에러 로그를 남긴다 (`:251-287`). 해당 건은 DB에 변경 없이 같은 상태로 남아 다음 6시간 주기에 다시 대상이 된다.
- 나머지 건은 계속 처리된다. 청크(50건) 트랜잭션은 롤백 후 아이템 단위로 재처리되며, 실패 건만 건너뛰고 성공 건은 커밋된다(Spring Batch fault-tolerant 기본 동작).
- skip 한도 50을 넘기면 Step이 실패해 Job이 중단되고, 스케줄러는 예외를 `printStackTrace`만 하고 삼킨다 (`ShipmentBatchScheduler.java:41-43`). 한 건의 CJ 조회 실패가 재시도 없이 다음 주기까지 대기한다.
- 한 건 안에서의 부분 반영: `completeOrder`는 `@Transactional`로 청크 트랜잭션에 참여하며 예외 시 청크가 롤백된다. 알림(`createNotification`)은 같은 트랜잭션이라 함께 롤백되지만, `notifyShipmentCompleted`는 내부에서 예외를 삼키므로(`NotificationCommandService.java:230-233`) 알림 실패가 배송 완료 처리를 막지는 않는다.
