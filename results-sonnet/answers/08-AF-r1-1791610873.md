# 구매자 배송: 운송장 등록 → 배송 완료

경로 약어: `S` = `src/main/java/com/fream/back/domain/shipment`, `O` = `.../domain/order`, `SA` = `.../domain/sale`, `G` = `.../global`.
(모두 `src/main/java/com/fream/back/` 아래)

## 0. 전제: 배송 정보는 언제 생기나

- 결제·배송 처리 시 `OrderShipment` 가 `PENDING` 으로 생성된다: `S/service/command/OrderShipmentCommandService.java:55-75` (status = PENDING, :67).
- 실배송 일반 주문은 Kafka 컨슈머 `processCompleteOrder` 에서 결제 → 배송 생성 → 주문 상태 `PAYMENT_COMPLETED` → `PREPARING` 으로 끝난다: `O/service/kafka/OrderEventConsumer.java:171-189, 192-195, 215-218`. (동기 경로 `OrderCommandService.java:148-177` 도 같은 결과.) 컨트롤러는 Kafka 이벤트만 발행한다: `O/controller/command/OrderCommandController.java:54`.
- 따라서 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문의 `Order.status` 는 **PREPARING** 이다.
- 즉시 구매 주문은 `createInstantOrder` 에서 `Order` 를 `PENDING_PAYMENT` 로 만들고 (`O/service/command/OrderCommandService.java:244`) 이후 주문 상태를 바꾸는 코드가 없다. 즉시 구매 시 `SaleBid.assignOrder(order)` 로 SaleBid 가 주문에 연결된다 (`OrderCommandService.java:279`). OrderBid 는 `MATCHED`, `isInstantPurchase=true`, `sale` 세팅 (`O/service/command/OrderBidCommandService.java:189-206`).

## 1. 운송장 등록 요청

### 1-1. 진입 API
- `PATCH /shipments/order/{shipmentId}/status`, body `{courier, trackingNumber}`: `S/controller/command/OrderShipmentCommandController.java:20, 33-45` → `OrderShipmentCommandService#updateTrackingInfo` (`OrderShipmentCommandService.java:238-303`).
- (보조) `POST /shipments/order/{id}/check-status`, `/check-status-string` 도 courier/운송장을 받아 저장하고 CJ 를 즉시 조회한다: `OrderShipmentCommandController.java:58-138`, `OrderShipmentCommandService.java:451-500`.

### 1-2. 의도된 상태 변경 순서와 알림 (코드 작성 순서)
`updateTrackingInfo` (`OrderShipmentCommandService.java:238-303`):
1. courier/운송장 공백 검증 → `TRACKING_INFO_REQUIRED` (:243-246).
2. `OrderShipment` 조회 (:249-253), `shipment.updateTrackingInfo(courier, trackingNumber)` → 택배사·운송장 저장 + shipment 상태를 전환 규칙 검사 없이 `IN_TRANSIT` 으로 세팅 (:256, `S/entity/OrderShipment.java:41-45`).
3. `order.updateStatus(OrderStatus.IN_TRANSIT)` (:259-260).
4. **구매자**에게 알림 "상품이 출발하였습니다. 주문 ID: …" (:265-271).
5. `updateSaleStatusToSold(orderId)` (:276, 본체 :111-183): SaleBid 의 Sale 을 `SOLD` 로, 창고 보관이면 창고 상태 SOLD, **판매자**에게 "상품이 성공적으로 판매 완료되었습니다" 알림; 이어 OrderBid 기반 Sale 도 `SOLD` + 판매자 알림.
6. 창고 상태 갱신 재시도 (:279-286).
7. `updateOrderAndSaleBidStatusToCompleted` (:289, 본체 :412-440): OrderBid 와 SaleBid 가 `MATCHED` 이면 `COMPLETED` 로 (실패는 로그만, :436-439).

### 1-3. 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문은 끝까지 성공하나? → **아니오, 실패한다**
- 실패 지점: `OrderShipmentCommandService.java:260` `order.updateStatus(OrderStatus.IN_TRANSIT)`.
- 이유: 주문은 `PREPARING` 인데 `OrderStatus` 전이표상 `PREPARING → {IN_WAREHOUSE, SHIPMENT_STARTED}` 만 허용 (`O/entity/OrderStatus.java:26`). `IN_TRANSIT` 은 `SHIPMENT_STARTED` 에서만 갈 수 있다 (:28). `Order.updateStatus` 가 `InvalidOrderStatusException` 을 던진다 (`O/entity/Order.java:113-120`). 그리고 `SHIPMENT_STARTED` 로 바꾸는 코드는 코드베이스 어디에도 없다 (OrderStatus 사용처 grep 결과: 결제/배송 처리·DataInitializer 뿐).
- 예외는 `catch (ShipmentException)` 이 아니라 `catch (Exception e)` (:295) 로 잡혀 `ShipmentException(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")` 로 재포장된다 (:296-301).
- **무엇이 저장되나: 아무것도 저장되지 않는다.** 메서드가 `@Transactional` 이고 RuntimeException(`GlobalException`) 이 밖으로 나가므로 롤백된다. :256 에서 메모리상 바뀐 택배사/운송장/`IN_TRANSIT` 은 DB 에 남지 않아 shipment 는 `PENDING`·운송장 null 그대로다. 4번 이후(구매자 알림, Sale SOLD, 입찰 COMPLETED)는 :260 에서 이미 중단되어 실행되지 않는다.
- **응답:** `GlobalExceptionHandler#handleGlobalException` 이 `errorCode` 기준으로 응답을 만든다 (`G/exception/GlobalExceptionHandler.java:49-63`): HTTP **404**, code `S001`, message "배송 정보를 찾을 수 없습니다." (`S/exception/ShipmentErrorCode.java:12`). 코드·메시지는 ErrorCode 의 것이고 상세 메시지(원인)는 응답 본문에 쓰이지 않는다.
- 참고: 즉시 구매 주문(`PENDING_PAYMENT`)도 `PENDING_PAYMENT → IN_TRANSIT` 이 허용되지 않아 (`OrderStatus.java:24`) 같은 지점에서 실패한다. 즉 이 API 로는 정상 주문이 성공하는 경우가 사실상 없다.
- (참고) 설령 :260 을 통과해도 `SaleBidQueryService#findByOrderId` 는 SaleBid 가 없으면 null 이 아니라 `IllegalArgumentException` 을 던져 (`SA/service/query/SaleBidQueryService.java:160-163`) `updateSaleStatusToSold` 의 `saleBid != null` 분기 (:117) 는 의미가 없고 다시 :295 로 빠진다.

## 2. 배송 완료 감지

### 2-1. 누가·언제·어떻게
- **스케줄러** `ShipmentBatchScheduler#scheduleShipmentStatusJob` 가 Spring Batch 잡 `updateShipmentStatusesJob` 을 실행 (`G/config/ShipmentBatchScheduler.java:34-43`; 파라미터는 현재 시각 timestamp).
- **주기:** `@Scheduled(cron = "0 0 */6 * * *")` = 6시간마다 (00·06·12·18시 정각) (`ShipmentBatchScheduler.java:34`).
- 잡 구성: `S/config/UpdateShipmentStatusesJobConfig.java:54-85` — chunk 50 (:51, :67), skip 허용 `Exception.class`, skipLimit 50 (:75-77), 스텝 시작/종료 시 Playwright 브라우저 open/close (`BrowserManageStepListener`, :80).

### 2-2. 조회 대상
- Reader JPQL: `SELECT s FROM OrderShipment s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL` (`UpdateShipmentStatusesJobConfig.java:95`). PENDING·DELIVERED 등은 대상이 아니다. (1-3 처럼 운송장 등록이 롤백되면 shipment 는 PENDING+운송장 null 이라 배치 대상이 되지 못한다.)

### 2-3. 실제로 실행되는 처리 코드
비슷한 구현이 여러 곳에 있다:

| 위치 | 실행되나 |
|---|---|
| `S/config/ShipmentItemProcessor#process` (`ShipmentItemProcessor.java:57-150`) | **실행됨** — 스텝이 `new ShipmentItemProcessor(...)` 를 processor 로 등록 (`UpdateShipmentStatusesJobConfig.java:69-73`) |
| `UpdateShipmentStatusesJobConfig#shipmentItemProcessor` (@Bean 람다, :104-) | 빈으로만 있고 스텝은 쓰지 않음 (스텝은 :69 에서 직접 new). 실행되지 않음 |
| `UpdateShipmentStatusesJobConfig#parseCjLogisticsStatus` (:~190, Jsoup) | 어디서도 호출되지 않는 private 메서드 |
| `OrderShipmentCommandService#updateShipmentStatuses` (`:308-391`) | 호출하는 곳이 없음(스케줄러·컨트롤러 모두 미사용). 실행되지 않음 |
| `OrderShipmentCommandService#updateAndCheckShipmentStatus` (:451-) | 배치가 아니라 `check-status` API 로 수동 호출될 때만 |

실행되는 `ShipmentItemProcessor#process` 동작:
1. 운송장 null/공백 → `TRACKING_NUMBER_INVALID` (:60-63).
2. Playwright 페이지로 `https://trace.cjlogistics.com/next/tracking.html?wblNo={운송장}` 이동 (:28, :81), `tbody#statusDetail tr` 로딩 대기 (:~85), 타임아웃 30초 (:30).
3. `parseStatusFromHtml`: 마지막 `tr` 의 5번째 `td`(index 4) 텍스트를 trim 해서 사용; 행이 없거나 빈 문자열이면 `TRACKING_HTML_PARSE_ERROR` (:170-190, 특히 :181).
4. `mapToShipmentStatus` 로 내부 상태 변환.
5. 현재 상태와 같으면 변경 없이 반환 (:101).

### 2-4. 택배사 상태 문자열 → 내부 상태 (`ShipmentItemProcessor.java:221-225`)
- `"배송완료"` → `DELIVERED`
- `"배송출발"` → `OUT_FOR_DELIVERY`
- 그 외 모든 문자열(공백 변형·"집하처리"·"간선상차" 등 포함) → `IN_TRANSIT` (exact-match switch).
- 주의: `OUT_FOR_DELIVERY` 였던 건에 "그 외" 문자열이 오면 `IN_TRANSIT` 으로 매핑되어 `OrderShipment.updateStatus` 가 `OUT_FOR_DELIVERY → IN_TRANSIT` 을 거부(`ShipmentStatus.java:23-27`, `OrderShipment.java:47-55`)하고 `IllegalStateException` → `ShipmentException(EXTERNAL_TRACKING_SERVICE_ERROR)` 로 포장되어 (`ShipmentItemProcessor.java:~136-145`) skip 된다.

## 3. 배송 완료 판정 이후 (`ShipmentItemProcessor.java:108-118`)

### 3-1. 상태 변경 순서
1. `OrderShipment.updateStatus(DELIVERED)` (:113; `IN_TRANSIT`/`OUT_FOR_DELIVERY` → `DELIVERED` 허용: `ShipmentStatus.java:19-26`) — 메모리상 변경, 실제 DB 반영은 청크 Writer(`JpaItemWriter`, `UpdateShipmentStatusesJobConfig.java:~239-248`).
2. `OrderShipmentCommandService#completeOrder(orderId)` (:116 → `OrderShipmentCommandService.java:190-229`):
   1. `OrderBid` 조회 (:196-197, 없으면 IllegalArgumentException).
   2. `order.updateStatus(COMPLETED)` (:204).
   3. `updateSaleStatusToSold(orderId)` (:208): Sale 이 `SOLD` 로 전이 가능한 상태(`ON_AUCTION`/`SELLING`, `SA/entity/SaleStatus.java:14-24`)일 때만 `SOLD` + 판매자 알림 + 창고 SOLD.
   4. **구매자** 알림 "[completeOrder] 주문이 완료 처리되었습니다. 주문 ID: …" (:211-217).
3. `NotificationCommandService#notifyShipmentCompleted(order)` (`ShipmentItemProcessor.java:117`) → **구매자** 알림 "[배송 완료] 상품이 배송 완료되었습니다. 주문 ID: …" (`domain/notification/service/command/NotificationCommandService.java:219-234`; 실패는 로그만 남기고 삼킴, :230-233).

(`OUT_FOR_DELIVERY` 로 바뀐 건은 shipment 상태만 바뀌고 알림 없음: :119-122.)

### 3-2. 알림 건수
- 구매자: 항상 **2건** ("[completeOrder] …" + "[배송 완료] …").
- 판매자: Sale 이 아직 `SOLD` 가 아니고 `SOLD` 전이가 가능할 때만 1건 (:119-141 / :156-172; 두 블록이 같은 Sale 을 가리키면 첫 블록에서 `SOLD` 가 되어 두 번째 블록은 전이 불가 → 합쳐 최대 1건). 결제 시점에 이미 Sale 이 `SOLD` 로 바뀌어 있으면 0건 (아래 4-b).
- 배치 경로의 총합: 구매자 2건 + 판매자 0~1건.

### 3-3. 주문 입찰·판매 입찰 상태
- **배치 경로에서는 `OrderBid`/`SaleBid` 상태를 바꾸지 않는다.** `COMPLETED` 로 바꾸는 `updateOrderAndSaleBidStatusToCompleted` 는 `updateTrackingInfo` 에서만 호출되고 (`OrderShipmentCommandService.java:289`), `completeOrder`/배치에서는 호출되지 않는다. 따라서 둘 다 `MATCHED` 로 남는다 (OrderBid: `O/entity/OrderBid.java:60-78` 의 `assignOrder`, SaleBid: `SA/entity/SaleBid.java:58-61`).
- 바뀌는 것은 Order(`COMPLETED`), OrderShipment(`DELIVERED`), 조건부로 Sale(`SOLD`), 창고(`SOLD`).

## 4. 주문 종류별 차이

### (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문 → **끝까지 진행되지 않는다**
- 주문은 `PREPARING` (0절). 배치(또는 check-status)에서 `DELIVERED` 판정 시 `completeOrder` 의 `order.updateStatus(COMPLETED)` (`OrderShipmentCommandService.java:204`) 가 `PREPARING → COMPLETED` 불허 (`OrderStatus.java:26`) 로 `InvalidOrderStatusException` → :221 에서 잡혀 `ShipmentException(ORDER_NOT_FOUND_FOR_SHIPMENT)` 로 재던짐 (:223-227).
- 결과: Order 는 `PREPARING` 유지, 판매 상태·창고·구매자/판매자 알림·`notifyShipmentCompleted` 전부 실행되지 않는다 (예외가 :116 에서 나가 :117 에 도달하지 않음). OrderBid/SaleBid 도 `MATCHED` 그대로. 배치는 이 건을 skip 한다 (5절). 배송 상태도 DB 에는 `DELIVERED` 로 저장되지 않는다.
- 즉 1-3 의 이유(주문이 `SHIPMENT_STARTED`/`IN_TRANSIT` 으로 갈 방법이 없음)와 같은 전이표 문제 때문에 실배송 일반 주문은 등록에서도, 완료에서도 막힌다.

### (b) 즉시 구매로 만들어진 주문 → **끝까지 진행된다**
- 주문 상태가 `PENDING_PAYMENT` 로 남아 있어 (`OrderCommandService.java:244`) `PENDING_PAYMENT → COMPLETED` 가 허용된다 (`OrderStatus.java:24`). OrderBid 도 `order` 와 연결되어 있어 조회 성공 (`OrderBidCommandService.java:189-202`).
- `completeOrder` 결과: Order `COMPLETED`; `updateSaleStatusToSold` 는 SaleBid (`saleBid.assignOrder`, `OrderCommandService.java:279`) 를 찾지만 Sale 이 이미 결제 시점에 `SOLD` 로 바뀌어 있어 (`PaymentCommandService.java:83, 391-404` — 결제 처리 중 `order.getOrderBid()` 가 아직 null 이라 SaleBid 경로로 `sale.updateStatus(SOLD)`) `canTransitionTo(SOLD)` 가 false (`SaleStatus.java:24`) → 판매자 알림·창고 갱신 없음.
- 알림은 구매자 2건 (completeOrder 1 + 배송 완료 1), 판매자 0건. Shipment `DELIVERED`.
- OrderBid/SaleBid 는 배치 경로에서는 `MATCHED` 로 유지 (3-3).
- 차이 요약: (a) 는 `order.updateStatus(COMPLETED)` 에서 실패해 아무 것도 완료되지 않고, (b) 는 Order·Shipment 가 완료되지만 판매 쪽 후속(Sale SOLD 전이·판매자 알림)은 이미 결제 때 처리되어 발생하지 않는다.
- 단, (b) 도 운송장 등록 API 는 1-3 참고대로 `PENDING_PAYMENT → IN_TRANSIT` 불허로 실패하므로, 배치 대상이 되려면 `IN_TRANSIT` + 운송장이 다른 경로(예: `check-status` 의 `updateTrackingInfo` 호출, `OrderShipmentCommandService.java:473`)로 먼저 채워져야 한다.

## 5. 실패 처리 (주기 처리 중 한 건 실패)
- 스텝은 `faultTolerant().skip(Exception.class).skipLimit(50)` (`UpdateShipmentStatusesJobConfig.java:75-77`). processor 가 예외(운송장 무효, 브라우저 오류, 파싱 오류, `completeOrder` 실패 등; `ShipmentItemProcessor.java:~136-148` 에서 `ShipmentException` 으로 통일)를 던지면 **그 건만 skip** 된다.
- 청크(50건)는 하나의 트랜잭션이므로 그 건이 건드린 변경(메모리상 `DELIVERED`, Order `COMPLETED` 등)은 롤백되고, Spring Batch 가 skip 된 건을 제외하고 청크의 나머지 건을 재처리·커밋한다. 나머지 건은 정상적으로 계속 처리되고 Writer 로 저장된다.
- skip 시 `SkipListener#onSkipInProcess` 가 에러 로그만 남긴다 (`UpdateShipmentStatusesJobConfig.java:~251-270`). 별도 보상·알림·상태 표시는 없으므로 해당 건은 `IN_TRANSIT`/`OUT_FOR_DELIVERY` 로 남아 다음 실행(6시간 후)에 다시 조회된다 — (a) 같은 건은 매번 같은 이유로 반복 실패한다.
- skip 이 50건을 넘으면 `SkipLimitExceededException` 으로 스텝이 FAILED 되고 남은 건은 처리되지 않는다. 스케줄러는 `jobLauncher.run` 예외를 `printStackTrace()` 로만 처리한다 (`ShipmentBatchScheduler.java:~40-42`).
- 참고(실행되지 않는 코드): 서비스의 `updateShipmentStatuses` 는 건별 try/catch 로 계속 진행하지만 (`OrderShipmentCommandService.java:322-388`) 호출처가 없다.
