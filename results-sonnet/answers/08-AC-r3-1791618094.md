# 구매자 배송: 운송장 등록 → 배송 완료

경로 약어: `S` = `src/main/java/com/fream/back/domain/shipment`, `O` = `src/main/java/com/fream/back/domain/order`, `P` = `src/main/java/com/fream/back/domain/payment`, `G` = `src/main/java/com/fream/back/global`

## 사전: 결제·배송 처리를 마친 뒤의 상태

- 일반 구매 입찰 주문(실배송)은 `OrderCommandService#processPaymentAndShipment`에서 배송 레코드가 `PENDING`으로 생성된다 (`S/service/command/OrderShipmentCommandService.java:67`, 호출 `O/service/command/OrderCommandService.java:148`).
- 이어서 Order는 `PENDING_PAYMENT → PAYMENT_COMPLETED → PREPARING`까지만 간다 (`O/service/command/OrderCommandService.java:175-176`). 창고 보관이면 `IN_WAREHOUSE → COMPLETED`까지 간다 (`:165-172`).
- 주문 상태 전이표: `PREPARING → {IN_WAREHOUSE, SHIPMENT_STARTED}`만 허용된다 (`O/entity/OrderStatus.java:26`). `IN_TRANSIT`은 `SHIPMENT_STARTED`에서만, `COMPLETED`는 `PENDING_PAYMENT`·`IN_WAREHOUSE`·`IN_TRANSIT`에서만 도달한다 (`:24, :27-29`).
- 코드 어디에서도 `SHIPMENT_STARTED`로 전이시키지 않는다 (`updateStatus(OrderStatus.SHIPMENT_STARTED)` 호출 없음, `grep` 확인). 따라서 실배송 주문은 `PREPARING`에서 더 나아갈 수 없다.
- `Order#updateStatus`는 허용되지 않은 전이에 `InvalidOrderStatusException`을 던진다 (`O/entity/Order.java:113-121`). 이 예외는 `OrderException → GlobalException → RuntimeException` 계열이다 (`G/exception/GlobalException.java:10`).

## 1. 운송장 등록 요청

### 1-1. 진입 API
- `PATCH /shipments/order/{shipmentId}/status`, 본문 `OrderShipmentRequestDto{courier, trackingNumber}`. 핸들러는 `OrderShipmentCommandController#updateTrackingInfo` (`S/controller/command/OrderShipmentCommandController.java:20, 33-45`)이고 `OrderShipmentCommandService#updateTrackingInfo`를 호출한다.
- 별도로 `POST /shipments/order/{id}/check-status`와 `/check-status-string`이 있다. 이쪽은 운송장 저장과 즉시 조회를 함께 하는 API다 (`:58, :103`).
- 인증만 요구하고 역할 제한은 없다 (`G/config/security/SecurityConfig.java:51-52`, `/shipments`는 화이트리스트에 없고 `anyRequest().authenticated()`).

### 1-2. 코드가 의도한 상태 변경 순서와 알림 (`OrderShipmentCommandService#updateTrackingInfo`, `S/service/command/OrderShipmentCommandService.java:239-303`)
1. courier·trackingNumber가 비면 `TRACKING_INFO_REQUIRED` (`:243-246`).
2. `OrderShipment`를 조회한다 (`:249`).
3. `OrderShipment#updateTrackingInfo`로 택배사·운송장을 넣고 **배송 상태를 곧바로 `IN_TRANSIT`**으로 세팅한다 (`:256`, `S/entity/OrderShipment.java:41-45`). `ShipmentStatus` 전이 검증을 거치지 않는다.
4. `Order`를 `IN_TRANSIT`으로 변경한다 (`:259-260`).
5. 구매자에게 알림 1건: "상품이 출발하였습니다. 주문 ID: …" (`:265-271`).
6. `updateSaleStatusToSold(orderId)` (`:276`). Sale을 `SOLD`로 바꾸고, 창고 보관이면 창고 상태를 SOLD로 바꾸며, 판매자에게 "판매 완료" 알림을 보낸다 (`:112-183`). 배송 출발 시점에 판매 완료로 처리하는 구조다.
7. SaleBid의 Sale이 창고 보관이면 창고 상태를 다시 SOLD로 변경한다 (`:279-286`).
8. `updateOrderAndSaleBidStatusToCompleted`: OrderBid가 `MATCHED`면 `COMPLETED`, SaleBid가 `MATCHED`면 `COMPLETED`로 바꾼다 (`:289`, `:413-440`). 배송 완료 전에 입찰이 완료 처리되는 구조다. 이 메서드는 `private`에 `@Transactional`이 붙어 있어 프록시가 적용되지 않는다 (`:412-413`).

### 1-3. 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문에서 끝까지 성공하나? → **실패한다**
- **실패 지점**: 위 4단계 `order.updateStatus(OrderStatus.IN_TRANSIT)` (`S/service/command/OrderShipmentCommandService.java:260`). 주문이 `PREPARING`인데 `PREPARING → IN_TRANSIT`은 허용되지 않아 `InvalidOrderStatusException("상태 전환이 허용되지 않습니다: PREPARING -> IN_TRANSIT")`이 발생한다 (`O/entity/OrderStatus.java:26`, `O/entity/Order.java:113-121`).
- **예외 변환**: 이 예외는 `ShipmentException`이 아니므로 `catch (ShipmentException)`(`:293`)을 지나 `catch (Exception)`(`:295-302`)에 걸린다. 여기서 `ShipmentException(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")`으로 감싸 던진다. 코드 이름이 실제 원인과 맞지 않는다.
- **저장되는 것**: 없다. `@Transactional` 메서드에서 RuntimeException이 밖으로 나가므로 롤백된다. 3단계에서 메모리상 바뀐 택배사·운송장·`IN_TRANSIT`도 반영되지 않아 DB에는 `PENDING` 그대로 남는다. 5번 이후(알림, Sale SOLD, 입찰 COMPLETED)는 실행되지도 않는다. 구매자·판매자 알림은 0건이다.
- **응답**: `GlobalExceptionHandler#handleShipmentException`이 `ErrorCode`의 고정 값을 쓴다 (`G/exception/GlobalExceptionHandler.java:459-471`). 따라서 **HTTP 404**, 본문 `ErrorResponse{code:"S001", message:"배송 정보를 찾을 수 없습니다.", status:404, path}`이다 (`S/exception/ShipmentErrorCode.java:12`). 내부 메시지(상태 전환 불가)는 응답에 나가지 않는다.
- 참고: 즉시 구매 주문도 `PENDING_PAYMENT → IN_TRANSIT`이 허용되지 않아(`O/entity/OrderStatus.java:24`) 같은 이유로 이 API에서 실패한다.
- 참고: SaleBid 조회 `findByOrderId`는 없으면 null이 아니라 `IllegalArgumentException`을 던진다 (`src/main/java/com/fream/back/domain/sale/service/query/SaleBidQueryService.java:26-29`). 일반 구매 입찰 주문에는 SaleBid가 연결되지 않으므로, 4단계를 통과하더라도 6단계(`:116`)에서 같은 방식으로 실패한다.

## 2. 배송 완료 감지

### 2-1. 누가·언제·어떻게
- 주체는 스프링 스케줄러 `ShipmentBatchScheduler#scheduleShipmentStatusJob`이다. `jobLauncher.run(updateShipmentStatusesJob, timestamp 파라미터)`로 Spring Batch Job을 실행한다 (`G/config/ShipmentBatchScheduler.java:34-40`).
- **주기**: `@Scheduled(cron = "0 0 */6 * * *")`, 즉 **6시간마다**(매일 00·06·12·18시 정각, 서버 타임존 기준) (`G/config/ShipmentBatchScheduler.java:34`). 스케줄링 활성화는 다른 `@EnableScheduling` 클래스가 담당한다 (`src/main/java/com/fream/back/domain/event/scheduler/EventStatusScheduler.java:22`).
- 예외는 `catch (Exception e) { e.printStackTrace(); }`로 삼킨다 (`:41-43`).

### 2-2. 조회 대상
- Reader는 `JpaPagingItemReader`이고 쿼리는 `SELECT s FROM OrderShipment s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL`이다 (`S/config/UpdateShipmentStatusesJobConfig.java:95`). `PENDING` 배송은 대상이 아니다. 청크·페이지 크기는 50이다 (`:51, :67`).

### 2-3. 실제로 실행되는 처리 코드
- 비슷한 코드가 세 곳에 있다.
  - (A) `ShipmentItemProcessor` 클래스: `Step`에서 `new ShipmentItemProcessor(...)`로 직접 생성해 연결한다 (`S/config/UpdateShipmentStatusesJobConfig.java:69-73`). **실제 실행되는 쪽이다.**
  - (B) `UpdateShipmentStatusesJobConfig#shipmentItemProcessor` `@Bean`(`:106-176`): 정의만 있고 Step에 연결되지 않는다. 같은 클래스에서 `shipmentItemProcessor()`를 호출하는 곳이 없다.
  - (C) `OrderShipmentCommandService#updateShipmentStatuses` (`S/service/command/OrderShipmentCommandService.java:309-391`): 호출하는 곳이 없다 (`grep` 결과 정의뿐). 스케줄러·컨트롤러 어디에도 연결되어 있지 않다.
- (A)의 흐름은 다음과 같다 (`S/config/ShipmentItemProcessor.java`).
  - `PlaywrightBrowserManager#newPage`로 페이지를 만든다 (`:72`).
  - `https://trace.cjlogistics.com/next/tracking.html?wblNo=<운송장>`으로 이동한다 (`:81-83`).
  - `tbody#statusDetail tr`을 기다린 뒤 HTML을 가져온다 (`:87-90`).
  - Jsoup으로 **마지막 행의 5번째 td**를 상태 문자열로 쓴다 (`:167-181`).
  - `CjTrackingPlaywright`는 이 경로에서 쓰이지 않는다.

### 2-4. 택배사 상태 문자열 → 내부 상태 (`S/config/ShipmentItemProcessor.java:220-226`)
| 택배사 문자열 | 내부 상태 |
|---|---|
| `"배송완료"` | `ShipmentStatus.DELIVERED` |
| `"배송출발"` | `ShipmentStatus.OUT_FOR_DELIVERY` |
| 그 외 모든 문자열 | `ShipmentStatus.IN_TRANSIT` |

- 정확한 문자열 일치만 허용한다. 공백은 `trim`한다 (`:181`).
- 그 외 모든 문자열은 `IN_TRANSIT`으로 취급한다.
- 현재 상태와 매핑 결과가 같으면 아무것도 하지 않고 item을 그대로 반환한다 (`:101-104`).

## 3. 배송 완료 판정 이후 (`ShipmentItemProcessor#process`, DELIVERED 분기 `S/config/ShipmentItemProcessor.java:108-117`)

### 상태 변경 순서
1. `OrderShipment.status → DELIVERED` (`:113`). `IN_TRANSIT → DELIVERED`와 `OUT_FOR_DELIVERY → DELIVERED`는 허용된다 (`S/entity/ShipmentStatus.java:16-22, :23-28`). 이 값은 아직 메모리상이다.
2. `OrderShipmentCommandService#completeOrder(orderId)` 호출 (`:116`, 정의 `S/service/command/OrderShipmentCommandService.java:190-229`).
   1. `OrderBid`를 `findByOrderId`로 조회하고 없으면 `IllegalArgumentException` (`:196-197`).
   2. `Order.status → COMPLETED` (`:204`).
   3. `updateSaleStatusToSold(orderId)` (`:208`). SaleBid를 조회하고, Sale이 `SOLD`로 전이 가능하면 `SOLD`로 바꾸고 판매자에게 알림을 보낸다 (`:116-141`). OrderBid 쪽 Sale도 같은 방식으로 처리한다 (`:150-176`).
   4. 구매자에게 알림 "[completeOrder] 주문이 완료 처리되었습니다. 주문 ID: …" (`:211-217`).
   5. 이 블록 전체가 `catch (Exception)`으로 `ShipmentException(ORDER_NOT_FOUND_FOR_SHIPMENT)`으로 감싸져 재던져진다 (`:221-227`).
3. `NotificationCommandService#notifyShipmentCompleted(order)`: 구매자에게 "[배송 완료] 상품이 배송 완료되었습니다." (`S/config/ShipmentItemProcessor.java:117`, 정의 `src/main/java/com/fream/back/domain/notification/service/command/NotificationCommandService.java:219-234`). 이 메서드는 예외를 삼킨다.
4. Writer(`JpaItemWriter`)가 `OrderShipment`를 저장한다 (`S/config/UpdateShipmentStatusesJobConfig.java:241-247`, `:74`).

### 알림 수 (정상 진행 시, 즉시 구매 주문 기준)
- **구매자 2건**: completeOrder의 "주문이 완료 처리되었습니다"와 notifyShipmentCompleted의 "배송 완료".
- **판매자 0건**: 결제 시점에 이미 Sale이 `SOLD`로 바뀌어 있어 `canTransitionTo(SOLD)`가 false다 (`P/service/command/PaymentCommandService.java:404, :419`; `src/main/java/com/fream/back/domain/sale/entity/SaleStatus.java:15-24`, `SOLD → false`). 그래서 `updateSaleStatusToSold`의 알림 분기에 들어가지 않는다 (`:119, :156`).
- 만약 Sale이 SOLD가 아닌 상태로 남아 있었다면 판매자 알림이 SaleBid 경로에서 1건 생긴다. OrderBid 경로는 이미 SOLD가 되어 중복 알림이 생기지 않는다.
- 실행 없이 확인하지 못한 점: 리더가 페이지를 읽은 뒤 영속성 컨텍스트를 비우기 때문에 `orderShipment.getOrder()` lazy 프록시 초기화가 실패할 수 있다. 이 경우 `notifyShipmentCompleted`가 예외를 삼켜 배송 완료 알림 1건이 누락될 수 있다.

### 주문 입찰·판매 입찰의 상태
- 배송 완료 경로(`completeOrder`)는 **OrderBid·SaleBid 상태를 바꾸지 않는다.** 입찰을 `COMPLETED`로 바꾸는 `updateOrderAndSaleBidStatusToCompleted`는 `updateTrackingInfo`에서만 호출된다 (`S/service/command/OrderShipmentCommandService.java:289`; `completeOrder`는 `:208`에서 `updateSaleStatusToSold`만 호출).
- 따라서 즉시 구매 주문의 OrderBid는 생성 시 `MATCHED`(`O/service/command/OrderBidCommandService.java:196`), SaleBid는 `assignOrder`로 `MATCHED`(`O/service/command/OrderCommandService.java:279-280`)이고, 배송 완료 후에도 **`MATCHED`로 남는다.**
- 입찰이 `COMPLETED`가 되는 유일한 경로는 1번의 운송장 등록 API다. 이 경로는 배송 완료 전에 실행되며, 1-3에서 본 대로 실패한다.

## 4. 주문 종류별 차이

두 경우 모두 배송이 `IN_TRANSIT`/`OUT_FOR_DELIVERY` + 운송장 보유 상태가 되어야 배치 대상이 된다. 1번 API가 두 경우 모두 실패하므로(`PATCH …/status`), 현재 코드에서 배치 대상으로 만드는 경로는 `check-status`뿐이다.

- `check-status`는 `updateTrackingInfo`를 거쳐 배송을 `IN_TRANSIT`으로 세팅한다 (`S/service/command/OrderShipmentCommandService.java:473`).
- 이 경로에서 택배사가 "배송출발"이면 `OUT_FOR_DELIVERY`로 저장된다 (`:491-493`). 그 외 문자열이면 `IN_TRANSIT → IN_TRANSIT`이 허용되지 않아 예외가 나 롤백된다 (`:497`, `S/entity/ShipmentStatus.java:16-22`).
- "배송완료"이면 `completeOrder`가 호출되어 아래 (a)와 같은 이유로 실패, 롤백된다 (`:483-489`).
- 즉 배송 상태를 배치 대상으로 만들 수 있는 입력은 "배송출발"뿐이다.

### (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문 → **끝까지 진행되지 않는다**
- Order가 `PREPARING`이다. `completeOrder`의 `order.updateStatus(COMPLETED)` (`S/service/command/OrderShipmentCommandService.java:204`)가 `PREPARING → COMPLETED` 불허로 `InvalidOrderStatusException`을 던진다 (`O/entity/OrderStatus.java:26`).
- `completeOrder`의 catch가 이를 `ShipmentException(ORDER_NOT_FOUND_FOR_SHIPMENT)`로 감싼다 (`:221-227`). `ShipmentItemProcessor`는 `ShipmentException`이면 그대로 재던진다 (`S/config/ShipmentItemProcessor.java:133-145`).
- Step이 `skip(Exception.class)`라서 이 건은 스킵된다 (`S/config/UpdateShipmentStatusesJobConfig.java:75-77`). 청크 트랜잭션이 롤백되어 `OrderShipment`의 `DELIVERED`도 저장되지 않는다. 배송은 `OUT_FOR_DELIVERY`로 남고, Order는 `PREPARING`, OrderBid는 `MATCHED`이며 알림은 0건이다.
- 6시간 뒤에도 같은 조건으로 다시 조회되어 같은 이유로 계속 스킵된다.
- 상태와 무관하게 SaleBid가 없다는 점도 막는다. `updateSaleStatusToSold`의 `saleBidQueryService.findByOrderId`가 `IllegalArgumentException`을 던진다 (`src/main/java/com/fream/back/domain/sale/service/query/SaleBidQueryService.java:26-29`, 호출 `S/service/command/OrderShipmentCommandService.java:116`).

### (b) 즉시 구매로 만들어진 주문 → **끝까지 진행된다**
- `createInstantOrder`는 Order를 `PENDING_PAYMENT`로 만들고(`O/service/command/OrderCommandService.java:244`), 이후 주문 상태를 바꾸는 코드가 없다. 결제 쪽도 Order 상태를 바꾸지 않는다 (`P/service/command/PaymentCommandService.java:383-426`).
- `PENDING_PAYMENT → COMPLETED`는 허용된다 (`O/entity/OrderStatus.java:24`). `order.updateStatus(COMPLETED)`가 성공한다 (`S/service/command/OrderShipmentCommandService.java:204`).
- OrderBid가 존재한다 (`O/service/command/OrderBidCommandService.java:189-206`, `order` 연결). SaleBid도 `assignOrder`로 연결되어 있다 (`O/service/command/OrderCommandService.java:279`). `findByOrderId` 조회가 모두 성공한다.
- 최종 결과는 다음과 같다.
  - OrderShipment: `DELIVERED`
  - Order: `COMPLETED`
  - Sale: 결제 시점에 이미 `SOLD`
  - OrderBid·SaleBid: `MATCHED` 유지
  - 알림: 구매자 2건, 판매자 0건

## 5. 실패 처리 (주기 배치)

- Step은 `faultTolerant().skip(Exception.class).skipLimit(50)` (`S/config/UpdateShipmentStatusesJobConfig.java:75-77`). 청크 크기는 50이다 (`:67`).
- 한 건의 처리에서 예외(운송장 번호 없음, 파싱 실패, 브라우저 오류, `completeOrder` 실패 등)가 나면 `ShipmentItemProcessor`가 `ShipmentException`으로 변환해 던진다 (`S/config/ShipmentItemProcessor.java:133-145`).
- 그 건은 스킵된다. 스킵 사유는 `SkipListener`가 `log.error`로 남긴다 (`S/config/UpdateShipmentStatusesJobConfig.java:255-289`).
- 해당 청크의 트랜잭션은 롤백되고, Spring Batch가 스킵된 건을 제외하고 나머지 건을 다시 처리해 정상 건은 정상적으로 반영된다. 스킵된 건의 DB 상태는 변하지 않는다. 즉 DB 상태가 그대로이므로 다음 6시간 주기에 다시 조회된다. 별도의 실패 마킹·재시도 횟수 기록은 없다.
- 스킵 건수가 50을 넘으면 `SkipLimitExceededException`으로 Step이 실패한다. 남은 건은 그 실행에서 처리되지 않는다 (`:52, :77`).
- 한 건씩 독립된 트랜잭션이 아니라 청크 단위 트랜잭션이다. `completeOrder`는 외부 청크 트랜잭션에 참여한다.
- 실패 건이 있어도 Job 전체는 실행을 이어간다. 스케줄러는 Job 실행에서 나온 예외를 `printStackTrace`로만 처리한다 (`G/config/ShipmentBatchScheduler.java:41-43`).
- 참고(추론): `JpaPagingItemReader`가 페이지를 offset 방식으로 읽는데, 처리된 건이 조회 조건(`IN_TRANSIT`/`OUT_FOR_DELIVERY`)에서 빠지면서 뒷 페이지가 앞당겨진다. 따라서 한 실행에서 일부 건이 건너뛰어질 수 있고, 그 건은 다음 주기에 처리된다.
