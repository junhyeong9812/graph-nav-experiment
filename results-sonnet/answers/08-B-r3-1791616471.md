# 구매자 배송: 운송장 등록 → 배송 완료 처리 분석

경로 약어: `S` = `src/main/java/com/fream/back`

## 0. 전제: 결제·배송 처리 후 상태
- 구매자 배송은 `OrderShipment`(PENDING)로 생성된다. `S/domain/shipment/service/command/OrderShipmentCommandService.java:61-70`
- 일반 구매 입찰(실배송) 주문은 결제·배송 처리 후 `Order.status = PREPARING` 이 된다 (PAYMENT_COMPLETED → PREPARING).
  `S/domain/order/service/command/OrderCommandService.java:174-177`, Kafka 경로도 동일 `S/domain/order/service/kafka/OrderEventConsumer.java:214-218`
  (REST 직접 호출 `processPaymentAndShipment`는 컨트롤러에서 주석 처리: `S/domain/order/controller/command/OrderCommandController.java:90-104`)
- 이 주문에는 `SaleBid`가 연결되어 있지 않다. 일반 구매 입찰 주문은 `OrderBid`만 만들고(`OrderBidCommandService.java:90-102`) `SaleBid.order` 는 즉시 구매(`OrderCommandService.java:279`)나 즉시 판매(`SaleBidCommandService.java:83`)에서만 설정된다.
- 즉시 구매 주문은 `Order.status = PENDING_PAYMENT` 로 남는다 (`OrderCommandService.java:241-245`, 이후 상태 변경 없음).

## 1. 운송장 등록 요청

### 1-1. API
- `PATCH /shipments/order/{shipmentId}/status`, 바디 `OrderShipmentRequestDto`(courier, trackingNumber)
  `S/domain/shipment/controller/command/OrderShipmentCommandController.java:20,33-46`
  → `OrderShipmentCommandService.updateTrackingInfo` (`OrderShipmentCommandService.java:238-303`)
- (참고) 같은 컨트롤러 `POST /{shipmentId}/check-status` (`OrderShipmentCommandController.java:58`)는 운송장 저장 + CJ 즉시 조회 (`OrderShipmentCommandService.java:451-516`).

### 1-2. 코드가 의도한 순서 (`updateTrackingInfo`)
1. courier/trackingNumber 공백 검사 → `TRACKING_INFO_REQUIRED` (`:243-246`)
2. `OrderShipment` 조회, 없으면 `SHIPMENT_NOT_FOUND` (`:249-253`)
3. `shipment.updateTrackingInfo` → 택배사/운송장 세팅 + `ShipmentStatus = IN_TRANSIT` (전이 검사 없이 직접 대입) `S/domain/shipment/entity/OrderShipment.java:41-45`
4. `order.updateStatus(OrderStatus.IN_TRANSIT)` (`:260`)
5. 구매자에게 알림 1건 "상품이 출발하였습니다. 주문 ID: …" (`:265-271`)
6. `updateSaleStatusToSold(orderId)` : Sale → SOLD, 창고 상태, 판매자에게 알림 "상품이 성공적으로 판매 완료되었습니다…" (`:276`, 본문 `:111-183`)
7. 창고 보관 Sale 이면 창고 상태 SOLD (`:279-286`)
8. `updateOrderAndSaleBidStatusToCompleted` : OrderBid/SaleBid MATCHED → COMPLETED (`:289`, 본문 `:412-440`)

즉, 의도상 알림은 구매자 1건(출발) + 판매자 1건(판매 완료)이다.

### 1-3. 실배송 일반 구매 입찰 주문(PREPARING)에서의 실제 결과: **끝까지 성공하지 못함**
- 실패 지점: `OrderShipmentCommandService.java:260` `order.updateStatus(IN_TRANSIT)`.
  `PREPARING` 에서 허용되는 다음 상태는 `IN_WAREHOUSE, SHIPMENT_STARTED` 뿐이다 (`S/domain/order/entity/OrderStatus.java:26`). IN_TRANSIT 은 SHIPMENT_STARTED 이후에만 가능(`:28`).
  `Order.updateStatus` 가 `InvalidOrderStatusException` 을 던진다 (`S/domain/order/entity/Order.java:113-120`).
- 그 예외는 `catch (Exception e)` (`OrderShipmentCommandService.java:295-302`)에서 `ShipmentException(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")` 로 바뀐다. 이름과 달리 실제 원인은 "배송 없음"이 아니라 주문 상태 전이 불가다.
- 저장되는 것: 없음. `GlobalException` 은 RuntimeException (`S/global/exception/GlobalException.java:10`)이고 메서드는 `@Transactional` 이므로 롤백된다. 3단계에서 바꾼 courier/trackingNumber/IN_TRANSIT 도 DB에 남지 않는다 (shipment 는 PENDING 유지).
- 알림: 5·6단계에 도달하지 못하므로 0건. (참고: 상태 검사를 통과했더라도 6단계의 `saleBidQueryService.findByOrderId` 가 SaleBid 없음으로 `IllegalArgumentException` 을 던진다. `S/domain/sale/service/query/SaleBidQueryService.java:26-29`, 호출 `OrderShipmentCommandService.java:116`. 이 값은 null 이 아니라 예외다.)
- 응답: `GlobalExceptionHandler` 가 `ErrorResponse(code="S001", message="배송 정보를 찾을 수 없습니다.", status=404, path)` 로 응답 (`S/global/exception/GlobalExceptionHandler.java:49-62`, `S/domain/shipment/exception/ShipmentErrorCode.java:12`). 컨트롤러에는 별도 try/catch 가 없다 (`OrderShipmentCommandController.java:41-46`). 상세 메시지는 응답에 쓰이지 않고 errorCode 의 고정 메시지가 사용된다.
- 즉시 구매 주문(PENDING_PAYMENT)도 PENDING_PAYMENT → IN_TRANSIT 이 허용되지 않아(`OrderStatus.java:24`) 같은 이유로 이 API 는 실패한다. 따라서 IN_TRANSIT 배송은 사실상 `check-status` API(주문 상태를 건드리지 않음, `:473`)나 데이터 초기화(`S/global/config/DataInitializer.java:481`) 같은 경로에서만 생긴다.

## 2. 배송 완료 감지

### 2-1. 누가/언제/어떻게
- 스프링 스케줄러 `ShipmentBatchScheduler.scheduleShipmentStatusJob` 이 `@Scheduled(cron = "0 0 */6 * * *")` 로 Spring Batch Job `updateShipmentStatusesJob` 을 실행한다. `S/global/config/ShipmentBatchScheduler.java:34-41`
  - 주기: 6시간마다 정각 (00:00, 06:00, 12:00, 18:00). 스케줄링 활성화는 `@EnableScheduling` (`S/domain/event/scheduler/EventStatusScheduler.java:22`).
  - 실행마다 `timestamp` JobParameter 로 새 JobInstance 를 만든다 (`:37-40`). 예외는 `printStackTrace` 만 한다 (`:41-43`).
- 대상: Reader 쿼리 `SELECT s FROM OrderShipment s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL` , pageSize 50. `S/domain/shipment/config/UpdateShipmentStatusesJobConfig.java:93-96`
- 조회: Playwright 로 `https://trace.cjlogistics.com/next/tracking.html?wblNo=<운송장>` 을 열어 `tbody#statusDetail tr` 의 마지막 행 5번째 td 텍스트(trim)를 읽는다. `S/domain/shipment/config/ShipmentItemProcessor.java:28-29,80-94,181`
- 수동 조회 경로는 별도로 있다: `POST /shipments/order/{id}/check-status` (`OrderShipmentCommandController.java:58`).

### 2-2. 실제로 실행되는 처리 코드
- Step 의 processor 는 `new ShipmentItemProcessor(...)` 이다 (`UpdateShipmentStatusesJobConfig.java:67-72`). 실제 실행 코드는 `S/domain/shipment/config/ShipmentItemProcessor.java` 의 `process` 이다.
- 실행되지 않는 유사 코드 (호출/연결 없음):
  - `UpdateShipmentStatusesJobConfig.shipmentItemProcessor()` 빈 (`:106`)과 `parseCjLogisticsStatus` : Step 에 연결되지 않음. 주석은 "DELIVERY 완료 시 알림…"이라고 하나 사용되지 않는다.
  - `OrderShipmentCommandService.updateShipmentStatuses()` (`:308-391`): 호출하는 곳이 없다 (전체 검색 결과 정의부만 존재). 이 코드는 `completeOrder` 대신 주문을 직접 COMPLETED 로 바꾸고 알림 문구도 다르지만 실행되지 않는다.

### 2-3. 택배사 상태 문자열 → 내부 상태 (`ShipmentItemProcessor.java:219-226`)
- "배송완료" → `DELIVERED`
- "배송출발" → `OUT_FOR_DELIVERY`
- 그 외 모든 문자열 → `IN_TRANSIT` (default). 정확 일치 비교이며 "배송 완료" 등 변형은 IN_TRANSIT 으로 처리된다.
- 현재 상태와 같으면 변경 없이 그대로 반환한다 (`:101-107`).
- 주의: 현재 OUT_FOR_DELIVERY 인데 CJ 가 그 외 문자열이면 `updateStatus(IN_TRANSIT)` (`:125`)가 `OUT_FOR_DELIVERY.canTransitionTo(IN_TRANSIT)=false` (`S/domain/shipment/entity/ShipmentStatus.java:23-27`) 라서 `IllegalStateException`(`OrderShipment.java:47-54`) → `EXTERNAL_TRACKING_SERVICE_ERROR` 로 감싸져 해당 건이 skip 된다 (`ShipmentItemProcessor.java:133-146`).

## 3. 배송 완료 판정 이후 (`ShipmentItemProcessor.process`, `:111-119`)
의도한(성공 시) 순서:
1. `OrderShipment.status = DELIVERED` (IN_TRANSIT/OUT_FOR_DELIVERY → DELIVERED 허용, `ShipmentStatus.java:16-28`) — `:113`
2. `orderService.completeOrder(orderId)` — `:116`, 본문 `OrderShipmentCommandService.java:190-229`
   - `OrderBid` 를 orderId 로 조회, 없으면 예외 (`:196-197`)
   - `Order.status = COMPLETED` (`:204`)
   - `updateSaleStatusToSold` (`:208`): SaleBid 조회(`:116`, 없으면 IAE), Sale 이 SOLD 로 전이 가능할 때만 Sale SOLD + 판매자 알림 (`:119-141`); 이어서 OrderBid 의 Sale 에 대해 같은 처리 (`:150-176`)
   - 구매자 알림 "[completeOrder] 주문이 완료 처리되었습니다. 주문 ID: …" (`:211-217`)
3. `notificationService.notifyShipmentCompleted(order)` → 구매자에게 "[배송 완료] 상품이 배송 완료되었습니다. 주문 ID: …" (`ShipmentItemProcessor.java:117`, `S/domain/notification/service/command/NotificationCommandService.java:219-228`)
4. Writer(`JpaItemWriter`)가 shipment 저장 (`UpdateShipmentStatusesJobConfig.java:74,241-247`)

알림: 구매자 2건 ("[completeOrder] …", "[배송 완료] …"). 판매자 알림은 Sale 이 아직 SOLD 로 전이 가능할 때만 1건 (`:131-138`, `:162-169`).

주문 입찰·판매 입찰 상태: **바뀌지 않는다.** `completeOrder` 는 `updateOrderAndSaleBidStatusToCompleted` 를 호출하지 않는다. 그 메서드는 `updateTrackingInfo` (`:289`)에서만 호출되며, 거기서도 실패 경로라 도달하지 못한다. 따라서 OrderBid·SaleBid 는 MATCHED 로 남고 COMPLETED 가 되지 않는다. (`Sale` 만 조건부로 SOLD 가 된다.)

## 4. 주문 종류별 차이 (배송이 IN_TRANSIT/OUT_FOR_DELIVERY + 운송장 보유 상태라고 가정)

### (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문 → **끝까지 진행되지 않음**
- 주문 상태 PREPARING (0절). `completeOrder` 의 `order.updateStatus(COMPLETED)` (`OrderShipmentCommandService.java:204`)에서 `PREPARING → COMPLETED` 불허 (`OrderStatus.java:26`) → `InvalidOrderStatusException` (`Order.java:113-120`).
- `completeOrder` 의 catch (`:221-228`)가 `ShipmentException(ORDER_NOT_FOUND_FOR_SHIPMENT, S102)` 로 변환해 던진다 → `process` 의 catch 가 그대로 재던짐 (`ShipmentItemProcessor.java:133-145`) → Step 의 skip 대상 (`UpdateShipmentStatusesJobConfig.java:75-77`).
- 결과: 구매자/판매자 알림 0건 (`:117` 에 도달하지 못함), Order 는 PREPARING 유지, OrderBid/SaleBid 변화 없음, 판매 상태 변화 없음.
- 부수 효과(추정, 실행 검증은 하지 않음): `:113` 에서 이미 메모리 상의 shipment 를 DELIVERED 로 바꾼 뒤 예외가 난다. 롤백 후 Spring Batch 가 항목을 하나씩 재처리할 때 같은 객체의 상태가 DELIVERED 이므로 `:101` 의 "상태 변경 없음" 분기로 반환되어 Writer 가 shipment 만 DELIVERED 로 저장할 수 있다. 이 경우 배송은 DELIVERED, 주문은 PREPARING 인 불일치가 생긴다.

### (b) 즉시 구매로 만들어진 주문 → **진행됨**
- 주문 상태 PENDING_PAYMENT 이므로 `PENDING_PAYMENT → COMPLETED` 가 허용된다 (`OrderStatus.java:24`). `completeOrder` 가 통과한다 (OrderBid 도 존재: `OrderBidCommandService.java:189-206`, SaleBid 도 연결: `OrderCommandService.java:279`).
- 결제 시점에 이미 Sale 이 SOLD 로 바뀌어 있다. `processPayment` 안에서 `notifyUsersAndUpdateSaleStatus` 가 호출되고(`S/domain/payment/service/command/PaymentCommandService.java:83`), 이 시점에 OrderBid 가 아직 없어(`OrderBidCommandService.java:133-142` 순서) SaleBid 경로로 `sale.updateStatus(SOLD)` 된다 (`PaymentCommandService.java:388-406`). 따라서 배송 완료 시 `SOLD.canTransitionTo(SOLD)=false` (`S/domain/sale/entity/SaleStatus.java:23`) → 판매자 알림·창고 갱신은 건너뛴다 (`OrderShipmentCommandService.java:119,156`).
- 결과: Shipment DELIVERED, Order COMPLETED, 구매자 알림 2건 ("[completeOrder]…", "[배송 완료]…"), 판매자 알림 0건(배송 완료 시점). OrderBid·SaleBid 는 MATCHED 유지(COMPLETED 아님).
- 결제 시점 알림(구매자 "결제가 완료되었습니다", 판매자 "구매자가 결제를 완료하였습니다")은 배송 완료와 별개다 (`PaymentCommandService.java:434-456`).

요약: (a) 실패(skip, 알림 0, 주문 PREPARING 유지) vs (b) 성공(Order COMPLETED, 구매자 알림 2건, 입찰 상태는 둘 다 MATCHED 유지).

## 5. 실패 처리 (주기 처리 중 한 건 실패)
- Step 은 fault-tolerant, chunk=50, `skip(Exception.class)`, `skipLimit=50` (`UpdateShipmentStatusesJobConfig.java:51-52,67,74-77`).
- processor 예외(조회 실패, 파싱 실패, 상태 전이 불가, `completeOrder` 실패 등)는 모두 `ShipmentException` 으로 감싸져(`ShipmentItemProcessor.java:133-146`) skip 대상이 된다.
- 해당 chunk 트랜잭션은 롤백되고 항목별 재처리가 일어나며, 실패한 한 건만 skip 되고 `SkipListener` 가 로그를 남긴다 (`UpdateShipmentStatusesJobConfig.java:78,252-`). 같은 chunk 의 나머지 건은 정상 처리·저장된다. 다음 chunk 도 계속 진행한다.
- skip 된 건은 DB 상태가 IN_TRANSIT/OUT_FOR_DELIVERY 로 남아 다음 주기(6시간 후)에 다시 조회 대상이 된다 (예: 운송장 번호 공백/없음도 `TRACKING_NUMBER_INVALID` 로 skip, `ShipmentItemProcessor.java:63` — 단 Reader 쿼리가 이미 `trackingNumber IS NOT NULL` 이다).
- skip 이 50건을 넘으면 Step 이 실패한다(스프링 배치 skipLimit 동작). 스케줄러는 예외를 `printStackTrace` 만 하고 삼킨다 (`ShipmentBatchScheduler.java:41-43`).
- 브라우저는 Step 시작/종료 때 열고 닫는다 (`S/domain/shipment/config/BrowserManageStepListener.java:17,23`).
- 주의(추정): `JpaPagingItemReader` 는 offset 페이징인데 처리된 건이 DELIVERED 로 바뀌어 쿼리 결과에서 빠지므로, 한 실행에서 일부 건이 다음 페이지로 밀려 건너뛰어질 수 있다. 건너뛴 건은 다음 주기에 처리된다.
