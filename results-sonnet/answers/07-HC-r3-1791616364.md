# 즉시 구매 처리 흐름 분석

경로 약어: `D` = `src/main/java/com/fream/back/domain`

## 1. 진입 API, 처리 단계, 동기/비동기, 응답 ID

**API**: `POST /order-bids/instant` (`@RequestMapping("/order-bids")` + `@PostMapping("/instant")`)
- `D/order/controller/command/OrderBidCommandController.java:22`, `:89-90`

**처리 단계 (모두 한 요청 스레드 안에서 동기 처리)**
1. 컨트롤러가 로그인 이메일을 꺼내고(`:92`), 결제 요청 DTO에 `userEmail` 을 넣고 `orderId=null` 로 둔다 (`:98`, `:119-123`).
2. `OrderBidCommandService.createInstantOrderBid` (`@Transactional`) 호출 (`:101`, 서비스 `D/order/service/command/OrderBidCommandService.java:118-120`).
   - 입력 검증 (`:123`, `:154-167`) → 구매자 조회 (`:126`) → SaleBid/Sale 조회·검증 (`:129-130`, `:172-184`).
3. `OrderCommandService.createInstantOrder` 호출 (`OrderBidCommandService.java:133`; 본체 `D/order/service/command/OrderCommandService.java:219-319`).
   - 주소 조회 `:238` → Order 저장 `:241-247` → `paymentRequest.setOrderId(order.getId())` `:250` → OrderItem `:255-256` → OrderShipment `:264-271` → SaleBid 매칭 + `flush` `:279-283` → (Sale이 창고 보관이면) 창고 상태 변경 `:291-293` → 결제 `:305`.
4. 결제(`PaymentCommandService.processPayment`, `D/payment/service/command/PaymentCommandService.java:57-107`) 안에서 알림 전송 + Sale `SOLD` 처리 (`:83`, `:383-426`).
5. 마지막으로 `OrderBid` 를 만들어 저장한다 (`OrderBidCommandService.java:142`, `:189-207`).

**동기/비동기**: 동기다. 컨트롤러는 Kafka 를 쓰지 않고 서비스를 직접 호출한다 (`OrderBidCommandController.java:28`, `:101`). 즉시 구매 경로에는 Kafka Producer 가 없다. 비동기(Kafka, 202 Accepted)로 처리되는 것은 다른 API `POST /orders/{orderId}/process-payment-shipment` 이며 즉시 구매와 무관하다 (`D/order/controller/command/OrderCommandController.java:42-69`). 즉시 구매가 이 API를 거치지 않으므로 `OrderEventConsumer` 의 상태 전이(`D/order/service/kafka/OrderEventConsumer.java:192-217`)도 실행되지 않는다.

**응답 ID**: 응답은 `200 OK` + `ResponseDto<Long>` 이고 값은 **`OrderBid` 의 ID** 다. 변수 이름은 `orderId` 이고 메시지도 "즉시 구매가 성공적으로 처리되었습니다" 이지만, 서비스가 `OrderBid` 를 반환하고 컨트롤러가 그 `.getId()` 를 담는다 (`OrderBidCommandController.java:101-109`; 반환 타입 `OrderBidCommandService.java:119`, `:142-144`). `Order` ID 가 아니다.

## 2. 새로 생성되는 엔티티와 상태 변화 순서

한 트랜잭션 안에서 아래 순서로 일어난다 (실패 시 전체 롤백, 3번 참고).

| # | 동작 | 엔티티 / 상태 | 근거 |
|---|------|--------------|------|
| 1 | Order 생성·저장 | `Order.status = PENDING_PAYMENT`, `totalAmount = saleBid.bidPrice` | `OrderCommandService.java:241-247` |
| 2 | OrderItem 생성 (수량 1, 가격 = 입찰가) | 신규 `OrderItem` | `:255-256`; `D/order/service/command/OrderItemCommandService.java:45-52` |
| 3 | OrderShipment 생성 | `ShipmentStatus.PENDING` | `OrderCommandService.java:264-271`; `D/shipment/service/command/OrderShipmentCommandService.java:61-68` |
| 4 | SaleBid ↔ Order 연결 + 상태 변경 | `SaleBid.order = order`, `SaleBid.status = MATCHED` (`assignOrder` 도 MATCHED 로 세팅, 이어서 `updateStatus(MATCHED)`) → `flush` | `OrderCommandService.java:279-283`; `D/sale/entity/SaleBid.java:58-61` |
| 5 | (판매자의 Sale 이 창고 보관 Sale 일 때만) 창고 보관 상태 변경 | `WarehouseStorage.status = ASSOCIATED_WITH_ORDER` | `OrderCommandService.java:291-293`; `D/warehouseStorage/service/command/WarehouseStorageCommandService.java:117-133` |
| 6 | Payment 생성 | 결제 수단별로 다름 (3번 참고). 기본값 `PENDING`, `isSuccess=false` | `Payment.java:39`, `:44` |
| 7 | 알림 전송 + Sale 상태 변경 | `Sale.status = SOLD` | `PaymentCommandService.java:404`/`:419`; `D/sale/entity/Sale.java:73-75` (전이 검증 없음) |
| 8 | OrderBid 생성·저장 | `OrderBid.status = MATCHED`, 즉시구매 플래그 true, `order`/`sale` 연결 | `OrderBidCommandService.java:192-206`; `D/order/entity/OrderBid.java:97-99` |

- 6번 시점에 `order.getOrderBid()` 는 아직 `null` 이다. 그래서 `notifyUsersAndUpdateSaleStatus` 는 `saleBidQueryService.findByOrderId` 경로로 Sale 을 찾는다 (`PaymentCommandService.java:388-406`). 4번에서 `flush` 해 두었기 때문에 조회가 된다.
- `Order.status` 는 위 어디서도 `PENDING_PAYMENT` 에서 바뀌지 않는다 (5번 항목 참고).
- `Order.payment` 는 즉시 구매 경로에서 `assignPayment` 되지 않는다. `createInstantOrder` 는 `processPayment` 의 반환값을 버린다 (`OrderCommandService.java:305`). Payment 쪽의 `order_id` FK 로만 연결된다 (`assignOrder`, `PaymentCommandService.java:200`, `:258`, `:311`).

## 3. 결제 수단별 결과

분기: `requestDto.getResolvedPaymentType()` 의 `switch` (`PaymentCommandService.java:67-80`). 공통 검증: 주문 ID·이메일 일치, 금액 > 0 (`:117-146`). 요청 금액(`paidAmount`)이 `saleBid.bidPrice` 와 같은지는 어디서도 검증하지 않는다.

| 수단 | 처리 | Payment 상태 | 근거 |
|------|------|--------------|------|
| CARD | 저장된 `PaymentInfo` 로 PortOne(아임포트) 카드 결제 호출 | 응답 `status == "success"` 일 때만 `PAID` + `isSuccess=true`. 그 외에는 `PENDING`, `isSuccess=false` 로 저장 | `PaymentCommandService.java:166`, `:179`, `:203-208` |
| ACCOUNT | PG 호출 없음. 은행명만 검증하고 저장 | 항상 `PENDING` (`isSuccess=false`) | `:244`, `:250-262` |
| GENERAL | PG 호출 없음. 클라이언트가 보낸 `impUid` 를 그대로 신뢰 | 항상 `PAID` + `isSuccess=true` | `:297-316` |

**끝까지 성공하는가**: 즉시 구매는 결제 완료 여부와 상관없이 "끝까지" 간다. 서비스는 `Payment` 의 성공 여부를 확인하지 않는다 (`OrderCommandService.java:305` 는 호출만 하고 `isSuccess` 를 검사하지 않음). 그래서 ACCOUNT(미입금 `PENDING`) 도, 카드 응답이 `success` 가 아닌 경우도 성공 응답(200)이 나가고 Order·SaleBid·OrderBid·Sale 이 모두 갱신된다 (`PaymentCommandService.java:83`, `:383-426` 도 payment 상태를 보지 않는다). `OrderEventConsumer` 가 하는 `if (!payment.isSuccess()) throw` 같은 검사(`OrderEventConsumer.java:174-176`)가 이 경로에는 없다.

**카드 결제를 PortOne 이 실패로 응답하는 경우** — 실패 응답 형태에 따라 두 가지다.
1. **PortOne 응답의 최상위 `code != 0` 또는 HTTP 200 이 아닌 경우**: `PortOneApiClient.processCardPayment` 가 `PaymentProcessingException` 을 던진다 (`D/payment/portone/PortOneApiClient.java:270-275`) → `PaymentCommandService` 가 그대로 전파 (`:89-94`, `:180-183`) → `OrderCommandService` 가 `OrderPaymentProcessingFailedException` 으로 감싼다 (`OrderCommandService.java:306-309`) → `OrderBidCommandService` 가 그대로 던진다 (`OrderBidCommandService.java:145-146`, `:212-214`). `@Transactional` 이 롤백하므로 Order, OrderItem, OrderShipment, SaleBid 매칭, 창고 상태가 모두 되돌려진다. 클라이언트는 오류 응답을 받고 OrderBid 는 만들어지지 않는다.
2. **`code == 0` 이지만 `response.status` 가 `"success"` 가 아닌 경우** (카드사 승인 실패 등; `PaymentCommandService.java:203` 이 이 경우를 가정한 분기): 예외가 없다. `CardPayment` 가 `PENDING`, `isSuccess=false` 로 저장되고 (`:187-208`, 기본값 `Payment.java:39`, `:44`) 흐름이 계속된다. 결과적으로 `SaleBid=MATCHED`, `OrderBid=MATCHED`, `Sale=SOLD`, 알림 전송, 200 응답이 나가고 `Order` 는 `PENDING_PAYMENT` 로 남는다. 결제가 안 됐는데 판매가 `SOLD` 로 처리되는 불일치가 생긴다. 이 `PENDING` 은 이후 `PENDING → PAID` 로만 전이할 수 있다 (`D/payment/entity/PaymentStatus.java` `canTransitionTo`).

## 4. 알림 수신자, 시점, 전달 방식

- **구매자**: "결제가 완료되었습니다. 주문 ID: {orderId}" (`PaymentCommandService.java:436-445`)
- **판매자(`sale.getSeller()`)**: "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}" (`:447-455`)
- 둘 다 `NotificationCategory.SHOPPING`, `NotificationType.BID`.

**시점**: `processPayment` 안에서 Payment 저장 직후, `Sale` 을 `SOLD` 로 바꾸기 직전이다 (`:83`, `:403`, `:416`). OrderBid 생성보다 앞이다. 결제 수단·결제 성공 여부와 무관하게, 즉 ACCOUNT `PENDING` 이나 카드 `PENDING`(3번의 2)이어도 전송된다. 결제 성공을 확인하는 분기가 없다.

**방식**: 동기 호출이고 Kafka 를 쓰지 않는다. `NotificationCommandService.createNotification` 이 (1) DB 에 `Notification` 을 저장하고 (`D/notification/service/command/NotificationCommandService.java:52-53`), (2) 수신자의 Redis 키 `WebSocket:User:{email}` 이 있을 때만 WebSocket `/user/queue/notifications` 로 푸시한다 (`:303-318`, 상수 `:37-38`). 접속 중이 아니면 저장만 하고 푸시는 생략한다 (`:320-322`). 알림 전송 실패는 `catch` 로 삼켜서 구매 흐름을 막지 않는다 (`PaymentCommandService.java:457-461`, `:421-425`).

## 5. 최종 주문 상태와 창고 보관 선택 시 차이

**최종 `Order.status` = `PENDING_PAYMENT`**.
- 즉시 구매 경로에서 `Order.updateStatus(...)` 를 호출하는 곳이 없다. `createInstantOrder` 는 `PENDING_PAYMENT` 로 만든 뒤 상태를 건드리지 않는다 (`OrderCommandService.java:241-245`, 메서드 전체 `:219-319`).
- `PAYMENT_COMPLETED`/`PREPARING`/`IN_WAREHOUSE`/`COMPLETED` 로 올리는 코드는 `processPaymentAndShipment` (`OrderCommandService.java:163-177`) 와 Kafka `OrderEventConsumer` (`:192-217`) 뿐이고, 둘 다 `/orders/{id}/process-payment-shipment` 경로다. 즉시 구매 응답 메시지("성공적으로 처리")와 달리 주문은 결제 완료 상태가 아니다. 결제가 `PAID` 인 CARD/GENERAL 이어도 마찬가지다.
- 같은 흐름에서 SaleBid 는 `MATCHED`, OrderBid 는 `MATCHED`, Sale 은 `SOLD`, OrderShipment 는 `PENDING` 이다 (2번 표).

**구매자가 "창고 보관"(`warehouseStorage=true`)을 선택한 경우**: 아무것도 달라지지 않는다.
- 컨트롤러는 값을 로그에 찍고(`OrderBidCommandController.java:94-95`) 서비스로 넘긴다 (`:105`). `OrderBidCommandService` 도 그대로 `createInstantOrder` 에 전달한다 (`:137`).
- 그러나 `createInstantOrder` 의 `isWarehouseStorage` 파라미터는 본문에서 한 번도 읽히지 않는다 (선언 `OrderCommandService.java:221`, 이후 사용처 없음; 검증 `:223-235` 에도 없음). `createOrderStorage` 호출도 없으므로 구매자용 `WarehouseStorage` 는 생성되지 않고 `Order.warehouseStorage` 는 `null` 이다. 상태도 `IN_WAREHOUSE`/`COMPLETED` 로 가지 않는다. 배송지 `OrderShipment` 는 창고 보관 여부와 상관없이 항상 생성된다 (`:264-271`).
- 창고 관련해서 실제로 실행되는 코드는 **판매자 쪽** `Sale.isWarehouseStorage()` 가 true 일 때 판매자 창고 보관 건(`WarehouseStorage`)을 `ASSOCIATED_WITH_ORDER` 로 바꾸는 것뿐이다 (`:291-293`). 구매자의 선택값과는 무관하다. 이때 해당 Sale 의 `WarehouseStorage` 가 없거나 상태 전이가 불가하면 예외가 나 전체가 롤백된다 (`:295-301`, `WarehouseStorageCommandService.java:127-130`).
- 창고 보관 처리가 실제로 구현된 곳은 비동기 경로(`OrderEventConsumer.java:197-221`)와 `processPaymentAndShipment` (`OrderCommandService.java:163-172`) 뿐이다.
