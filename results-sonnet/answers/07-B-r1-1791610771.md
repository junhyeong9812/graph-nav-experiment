# 즉시 구매 처리 흐름

경로 접두어: `src/main/java/com/fream/back/domain/` (이하 `D/`로 줄여 씀)

## 1. 진입 API, 처리 단계, 동기/비동기, 응답 ID

**진입 API**: `POST /order-bids/instant` (`D/order/controller/command/OrderBidCommandController.java:22,89-90`). 요청 본문은 `InstantOrderRequestDto`(saleBidId, addressId, warehouseStorage, paymentRequest) (`D/order/dto/InstantOrderRequestDto.java:20-29`).

**처리 단계 (모두 한 요청 스레드 안, 하나의 `@Transactional` 안에서 순차 실행)**
1. 컨트롤러가 로그인 이메일을 추출한다 (`OrderBidCommandController.java:92`).
2. `enrichPaymentRequest`가 결제 요청에 `userEmail`을 넣고 `orderId`를 null로 둔다 (`OrderBidCommandController.java:98,119-122`).
3. `OrderBidCommandService.createInstantOrderBid` (`D/order/service/command/OrderBidCommandService.java:118-149`)
   - 입력 검증 (`:123`, `:154-167`)
   - 구매자 조회 (`:126`)
   - SaleBid·Sale 조회/검증 (`:129-130`, `:172-183`)
   - `orderCommandService.createInstantOrder(...)` 호출 (`:133`)
   - 그 뒤 OrderBid 생성·저장 (`:142`, `:189-207`)
4. `OrderCommandService.createInstantOrder` (`D/order/service/command/OrderCommandService.java:219-319`) 내부 순서
   - 주소 조회 (`:238`)
   - Order 생성·저장 (`:241-247`)
   - 결제 요청에 orderId 주입 (`:250`)
   - OrderItem 생성 (`:255-256`)
   - OrderShipment 생성 (`:264-271`)
   - SaleBid 매칭 + flush (`:279-283`)
   - 판매자 창고 상태 갱신 (`:289-301`)
   - 결제 처리 (`:305`)

**동기/비동기**: **동기**다. 이 경로에는 Kafka 발행이나 `@Async`가 없다. 컨트롤러는 서비스 반환값을 바로 받아 `200 OK`로 응답한다 (`OrderBidCommandController.java:101-109`). 카드사 호출(PortOne)도 같은 스레드에서 블로킹 호출이다 (`D/payment/portone/PortOneApiClient.java:266`).
> 참고: Kafka 비동기 처리(202 Accepted)는 즉시 구매가 아니라 별도 API `POST /orders/{orderId}/process-payment-shipment`에만 있다 (`D/order/controller/command/OrderCommandController.java:42-69`). 즉시 구매는 이 경로를 타지 않는다.

**응답으로 돌려주는 ID**: **OrderBid의 ID**다. Order의 ID가 아니다.
- 서비스가 `OrderBid`를 반환하고 (`OrderBidCommandService.java:142-144`), 컨트롤러가 `.getId()`를 호출한다 (`OrderBidCommandController.java:101-107`).
- 변수명은 `orderId`이고 javadoc은 "생성된 주문 ID"(`:83`)라고 하지만 실제 값은 OrderBid PK다.
- 응답 메시지는 "즉시 구매가 성공적으로 처리되었습니다."이다 (`:109`).

## 2. 새로 생기는 엔티티와 상태 변화 순서

| 순서 | 동작 | 근거 | 직후 상태 |
|---|---|---|---|
| 1 | **Order** 생성 | `OrderCommandService.java:241-247` | `Order.status = PENDING_PAYMENT`, totalAmount = saleBid.bidPrice |
| 2 | **OrderItem** 생성 (수량 1, 가격 = saleBid.bidPrice) | `OrderCommandService.java:255`, `D/order/service/command/OrderItemCommandService.java:45-52` | 상태 필드 없음 |
| 3 | **OrderShipment** 생성 | `OrderCommandService.java:264`, `D/shipment/service/command/OrderShipmentCommandService.java:61-68` | `ShipmentStatus.PENDING` |
| 4 | 기존 **SaleBid** 매칭 | `OrderCommandService.java:279-280`, `D/sale/entity/SaleBid.java:58-61,66-68` | `SaleBid.status = MATCHED`, `order` 연결 |
| 5 | 기존 **WarehouseStorage**(판매자 `Sale`의 창고 레코드): `sale.isWarehouseStorage()`가 true일 때만 | `OrderCommandService.java:291-294`, `D/warehouseStorage/service/command/WarehouseStorageCommandService.java:117-133` | `WarehouseStatus.ASSOCIATED_WITH_ORDER` |
| 6 | **Payment** 생성 (카드/계좌/일반) | `OrderCommandService.java:305`, `D/payment/service/command/PaymentCommandService.java:57-80` | 결제 수단별 상태는 3번 참고 |
| 7 | 결제 직후 알림 + 기존 **Sale** 상태 변경 | `PaymentCommandService.java:83,383-420` | `Sale.status = SOLD` |
| 8 | **OrderBid** 생성·저장 | `OrderBidCommandService.java:192-206` | `BidStatus.MATCHED`, `isInstantPurchase = true`, order/sale 연결 |

세부 사항
- 5단계는 판매자 쪽 `Sale`의 창고 보관 플래그만 본다. 구매자 요청의 `warehouseStorage` 값은 사용하지 않는다 (5번 참고).
- 7단계: 즉시 구매에서는 이 시점에 `order.getOrderBid()`가 null이다. OrderBid가 아직 만들어지지 않았기 때문이다. 그래서 `saleBidQueryService.findByOrderId`로 SaleBid를 찾는 분기로 간다 (`PaymentCommandService.java:389-406`, `D/sale/service/query/SaleBidQueryService.java:26-28`). 4단계에서 flush했으므로 조회된다 (`OrderCommandService.java:283`).
- 7단계: `Sale.updateStatus`는 전이 검증 없이 값을 대입한다 (`D/sale/entity/Sale.java:73-75`). 결제 수단과 결과(PENDING 포함)에 관계없이 SOLD가 된다.
- 8단계: `OrderBid.assignOrder`도 상태를 MATCHED로 바꾼다 (`D/order/entity/OrderBid.java:73-75`).
- **Order 자체의 상태는 `PENDING_PAYMENT`에서 바뀌지 않는다.** `createInstantOrder`에는 `order.updateStatus(...)` 호출이 없다 (`OrderCommandService.java:219-319`). 5번 참고.

## 3. 결제 수단별 결과

결제 분기: `PaymentCommandService.java:67-80`. `Payment.status` 기본값은 PENDING (`D/payment/entity/Payment.java:41-42`). 허용 전이는 PENDING→PAID뿐이다 (`D/payment/entity/PaymentStatus.java:12-13`).

| 결제 수단 | 코드 동작 | 결과 |
|---|---|---|
| **CARD** | PortOne `processCardPayment` 호출 (`PaymentCommandService.java:179`). 응답 `status`가 `"success"`이면 `PAID` + `isSuccess=true` (`:203-206`) | 성공 시 `PAID` |
| **ACCOUNT** (계좌이체) | 은행명 검증 후 `AccountPayment` 생성 (`:243-256`). 이어서 `updateStatus(PaymentStatus.PENDING)` 호출 (`:260`) | **항상 실패한다.** 이미 PENDING인데 `PENDING.canTransitionTo(PENDING)`은 false라서 `IllegalStateException`이 난다 (`Payment.java:70-76`, `PaymentStatus.java:12-13`). 이 예외는 `PaymentProcessingException`으로 변환된다 (`:274-277`). |
| **GENERAL** (일반 결제) | `impUid` 필수. `GeneralPayment` 생성 후 `success=true`, `PAID` (`:297-314`). PG 호출 없이 클라이언트가 보낸 impUid를 그대로 신뢰한다 | 성공 시 `PAID` |

**즉시 구매가 끝까지 성공하는가**
- 카드, 일반 결제: 아래 조건에서 성공한다. 이때 Order는 `PENDING_PAYMENT`로 남는다.
- 계좌이체: **끝까지 성공하지 못한다.** 계좌이체 Payment 생성에서 예외가 나므로 즉시 구매 전체가 실패한다.
  - `OrderPaymentProcessingFailedException`으로 감싸진다 (`OrderCommandService.java:306-309`).
  - `createInstantOrder`와 `createInstantOrderBid`가 모두 `@Transactional`이다 (`OrderCommandService.java:219`, `OrderBidCommandService.java:118`). `OrderException`은 RuntimeException 계열이다 (`D/global/exception/GlobalException.java:10`). 그래서 Order/OrderItem/Shipment/SaleBid 매칭이 전부 롤백된다.
  - 클라이언트는 오류 응답을 받는다.
  - (`PaymentCommandService`도 클래스 레벨 `@Transactional`이라 같은 트랜잭션에 참여한다. `:37`)

**결제 대행사가 카드 결제를 실패로 응답하면**
- 응답이 **`code != 0` 또는 HTTP 비-200**인 경우
  - `PaymentProcessingException("카드 결제 요청 실패: ...")`이 발생한다 (`PortOneApiClient.java:270-275`).
  - `PaymentCommandService`는 이를 그대로 전파한다 (`:180-181, 218-219`).
  - `OrderPaymentProcessingFailedException`으로 감싸져 (`OrderCommandService.java:306-309`) 전체 트랜잭션이 롤백된다.
  - Order, OrderItem, Shipment, SaleBid 매칭, 창고 상태 변경이 모두 취소되고 OrderBid도 생기지 않는다.
  - Payment 레코드도 저장되지 않는다.
  - 알림은 결제 이후 단계라서 발송되지 않는다.
  - 통신 오류(`RestClientException`)는 `PaymentApiException`이 되고, `@Retryable`로 최대 3회 재시도된다 (`PortOneApiClient.java:221-227,288-290`).
- 응답이 **`code == 0`인데 `response.status`가 `"success"`가 아닌** 경우 (예: 실패 status)
  - `PortOneApiClient`는 `code==0`만 보고 예외 없이 응답을 반환한다 (`:270-285`).
  - `PaymentCommandService`는 `"success"`일 때만 PAID로 바꾼다 (`:203-206`). `else` 분기도, 예외도 없다.
  - 결과적으로 `CardPayment`가 **`status=PENDING`, `isSuccess=false`**로 그대로 저장된다 (`:208`). (`Payment.java:41-42`)
  - 호출한 쪽은 이를 실패로 보지 않는다. 즉시 구매 흐름이 정상 종료되고 알림이 발송되며 Sale이 SOLD가 된다 (`PaymentCommandService.java:83`, `OrderCommandService.java:305-311`, `OrderBidCommandService.java:142`).
  - 컨트롤러는 "즉시 구매가 성공적으로 처리되었습니다."로 응답한다 (`OrderBidCommandController.java:109`).

## 4. 알림 수신자, 시점, 방식

**누가 무엇을 받는가** (`PaymentCommandService.java:434-456`)
- **구매자**: "결제가 완료되었습니다. 주문 ID: {orderId}" (`:438-443`)
- **판매자** (`sale.getSeller()`): "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}" (`:447-454`)
- 둘 다 `NotificationCategory.SHOPPING`, `NotificationType.BID` 타입이다.

**언제**
- 결제(Payment 저장) 직후, 같은 요청·같은 트랜잭션 안에서 **동기로** 보낸다. 근거는 `processPayment`의 `notifyUsersAndUpdateSaleStatus` 호출이다 (`:83`).
- 알림 발송 → 그 다음 `Sale.status = SOLD` 순서다 (`:403-404`).
- Kafka나 비동기 큐는 쓰지 않는다.
- 결제 수단과 무관하게 결제 서비스가 예외 없이 반환되면 발송된다. 카드 `PENDING` 케이스도 포함된다.
- 구매자 알림 문구의 "주문 ID"는 Order의 ID이고, 응답 ID(OrderBid)와는 다르다.

**어떤 방식으로**
1. DB에 `Notification` 저장 (`D/notification/service/command/NotificationCommandService.java:52-54`).
2. 실시간 WebSocket 푸시: `/queue/notifications`로 사용자 이메일 대상 전송 (`:57`, `:309-313`, `:38`).
   - Redis에 `WebSocket:User:{email}` 키가 있는 연결된 사용자에게만 보낸다 (`:305-307`, `:37`).
   - 연결이 없으면 푸시하지 않고 DB 저장만 남는다 (`:320-321`).
- 알림 실패는 로그만 남기고 삼킨다 (`PaymentCommandService.java:457-460`, `:421-425`).
- (주의) `createNotification`은 자체가 `@Transactional`(클래스 레벨, `NotificationCommandService.java:27`)이다. 내부 예외가 프록시를 통과하면 외부 트랜잭션이 rollback-only로 표시될 수 있다. 이 부분은 코드에서 확인한 정황이고 실제 실행으로 검증하지는 않았다.

## 5. 최종 주문 상태와 창고 보관 선택 시의 차이

**최종 주문 상태**: `Order.status = PENDING_PAYMENT` (결제 대기)
- 즉시 구매 경로에는 `PAYMENT_COMPLETED`, `PREPARING` 등으로 바꾸는 호출이 없다 (`OrderCommandService.java:219-319`).
- 카드/일반 결제가 `PAID`여도 `Order`에는 반영되지 않는다 (`PaymentCommandService.java:57-107`는 order 상태를 건드리지 않는다).
- 응답 메시지는 "성공적으로 처리되었습니다"라고 하지만 주문은 결제 대기로 남는다.
- `PAYMENT_COMPLETED→PREPARING` 및 창고/완료 전이는 별도 API(`processPaymentAndShipment`, Kafka 경로)에만 있다 (`OrderCommandService.java:111-202`, 특히 `:163-177`). 즉시 구매는 이 메서드를 호출하지 않는다.
- 같이 남는 상태: `SaleBid=MATCHED`, `OrderBid=MATCHED(isInstantPurchase)`, `Sale=SOLD`, `OrderShipment=PENDING`, Payment는 `PAID`(카드/일반) 또는 `PENDING`(카드 이상 응답).

**구매자가 "창고 보관"을 선택하면**: **아무것도 달라지지 않는다.**
- `isWarehouseStorage` 파라미터는 `createInstantOrder`의 시그니처와 javadoc에만 있다 (`OrderCommandService.java:210,221`). 본문에서는 한 번도 읽히지 않는다 (`:222-318`).
- 컨트롤러는 값을 전달할 뿐이다 (`OrderBidCommandController.java:105`, `OrderBidCommandService.java:137`).
- 구매자용 `WarehouseStorage`는 생성되지 않는다 (`warehouseStorageCommandService.createOrderStorage`는 이 경로에서 호출되지 않는다. 호출처는 `processPaymentAndShipment`의 `:170`뿐이다).
- Order는 `IN_WAREHOUSE`나 `COMPLETED`로 가지 않는다.
- 배송 정보(OrderShipment)는 창고 보관 여부와 상관없이 항상 만들어진다 (`OrderCommandService.java:264-271`).
- 창고 관련 코드가 동작하는 유일한 지점은 **판매자 쪽** `sale.isWarehouseStorage()`이다. 이 값이 true이면 판매자의 창고 레코드가 `ASSOCIATED_WITH_ORDER`로 바뀐다 (`:291-294`). 그 레코드가 없으면 `WarehouseStorageNotFoundException`이 나서 즉시 구매가 실패한다 (`D/warehouseStorage/service/query/WarehouseStorageQueryService.java:30-33`, `OrderCommandService.java:295-301`).
  - 이 동작은 구매자의 선택과 무관하다.
