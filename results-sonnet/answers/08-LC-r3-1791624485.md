# 구매자 배송: 운송장 등록 → 배송 완료

경로 약어: `S` = `src/main/java/com/fream/back/domain/shipment`, `O` = `.../domain/order`, `G` = `.../global`.
줄 번호는 현재 소스 기준이며, 주석·메서드명이 아니라 실제 코드 동작을 기준으로 적었다.

## 0. 전제: 결제·배송 처리 후 주문의 상태
- 일반 구매 입찰 주문(a)의 결제·배송 처리는 컨트롤러가 Kafka로 던지고(`O/controller/command/OrderCommandController.java:54`), `OrderEventConsumer.processCompleteOrder`(`O/service/kafka/OrderEventConsumer.java:166`)가 처리한다. (동기 `OrderCommandService.processPaymentAndShipment`는 컨트롤러에서 주석 처리됨: `OrderCommandController.java:91-101`.)
- 순서: 결제(`:170`) → `OrderShipment` 생성, status=PENDING(`:181`, `S/service/command/OrderShipmentCommandService.java:67`) → `PAYMENT_COMPLETED`(`:195`) → 실배송이면 `PREPARING`(`:216-217`)에서 멈춘다. 즉 주문 상태는 **PREPARING**.
- `OrderStatus` 전이표: PREPARING → {IN_WAREHOUSE, SHIPMENT_STARTED}만 허용(`O/entity/OrderStatus.java:26`), SHIPMENT_STARTED → IN_TRANSIT(`:28`). 코드 어디에서도 SHIPMENT_STARTED로 바꾸지 않는다(`grep OrderStatus` 결과 전이는 `OrderCommandService`/`OrderEventConsumer`의 PAYMENT_COMPLETED/PREPARING/IN_WAREHOUSE/COMPLETED뿐).
- 즉시 구매(b)는 `OrderCommandService.createInstantOrder`(`O/service/command/OrderCommandService.java:220`)에서 Order를 `PENDING_PAYMENT`로 만들고(`:244`) 이후 상태를 바꾸지 않는다. 그래서 **PENDING_PAYMENT** 그대로다. 그 뒤 `OrderBidCommandService.createInstantOrderBid`가 OrderBid(MATCHED, 즉시구매 플래그)를 만든다(`O/service/command/OrderBidCommandService.java:192-205`). SaleBid는 주문과 연결되어 MATCHED(`OrderCommandService.java:279-280`).

## 1. 운송장 등록 요청

### 1-1. 어느 API
- `PATCH /shipments/order/{shipmentId}/status`, body `OrderShipmentRequestDto(courier, trackingNumber)` — `S/controller/command/OrderShipmentCommandController.java:33-45` → `OrderShipmentCommandService.updateTrackingInfo`(`S/service/command/OrderShipmentCommandService.java:239`). (prod nginx가 `/api`를 떼므로 매핑에는 `/api` 없음. 인증만 필요하고 관리자 확인·소유자 검증은 없음.)
- 참고: `POST /shipments/order/{id}/check-status`(`OrderShipmentCommandController.java:58`)는 운송장 갱신 + 즉시 CJ 조회를 하는 별도 수동 API다. 질문의 "운송장 등록"은 위 PATCH다.

### 1-2. 짜여 있는 상태 변경 순서와 알림 (의도된 흐름)
`updateTrackingInfo`(`OrderShipmentCommandService.java:239-303`) — 하나의 `@Transactional`:
1. courier/trackingNumber 비어 있으면 `TRACKING_INFO_REQUIRED`(`:243-246`).
2. `OrderShipment` 조회 후 `shipment.updateTrackingInfo` → **검증 없이 status=IN_TRANSIT**(`:256`, `S/entity/OrderShipment.java:41-45`).
3. `order.updateStatus(OrderStatus.IN_TRANSIT)`(`:259-260`).
4. **구매자**에게 알림 "상품이 출발하였습니다. 주문 ID: …"(`:265-271`).
5. `updateSaleStatusToSold(orderId)`(`:276`): SaleBid 경로(`:116-143`)와 OrderBid 경로(`:150-180`)에서 Sale을 SOLD로 바꾸고, 각각 **판매자**에게 "판매 완료" 알림(`:133-138`, `:164-169`). 창고 보관이면 창고 상태 SOLD(`:126-129`).
6. SaleBid의 Sale이 창고보관이면 `updateWarehouseStatusToSold` 한 번 더(`:279-286`).
7. `updateOrderAndSaleBidStatusToCompleted`(`:289`, 정의 ~`:415-441`): OrderBid·SaleBid가 MATCHED면 COMPLETED. 예외는 삼키고 로그만(`:437-440`).
→ 즉 의도상 "운송장 등록 시점"에 이미 주문 IN_TRANSIT, Sale SOLD, 입찰 COMPLETED까지 가도록 되어 있다(배송 완료 전).

### 1-3. (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문에 대해 끝까지 성공하나? — **실패한다**
- 실패 지점: 단계 3, `order.updateStatus(IN_TRANSIT)`(`OrderShipmentCommandService.java:260`). 주문은 PREPARING인데 PREPARING → IN_TRANSIT은 전이표에 없으므로(`OrderStatus.java:26`) `Order.updateStatus`가 `InvalidOrderStatusException`을 던진다(`O/entity/Order.java:166-173`).
- 이 예외는 `ShipmentException`이 아니므로 `catch (Exception e)`(`OrderShipmentCommandService.java:295`)에 걸려 `ShipmentException(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")`로 래핑되어 재던져진다(`:297-301`). (에러코드가 엉뚱하게 "배송 정보를 찾을 수 없습니다"가 됨.)
- 저장되는 것: **아무것도 없다.** 메서드 전체가 하나의 트랜잭션이고 런타임 예외가 밖으로 나가므로 롤백된다. 2단계에서 메모리상 바꾼 shipment의 IN_TRANSIT/courier/trackingNumber도 반영되지 않아 `OrderShipment`는 PENDING·운송장 null 그대로, 주문은 PREPARING 그대로다. 알림(4단계)은 실패 지점 뒤라 한 건도 생성되지 않고, Sale/입찰/창고 상태도 안 바뀐다.
- 응답: `GlobalExceptionHandler.handleShipmentException`(`G/exception/GlobalExceptionHandler.java:459-472`)이 `ErrorResponse`를 반환 — HTTP **404**, code **S001**, message는 항상 enum 기본 문구 "배송 정보를 찾을 수 없습니다."(`S/exception/ShipmentErrorCode.java:12`; 래핑 시 넣은 사용자 메시지는 응답에 안 나감, `GlobalExceptionHandler.java:62-67`).
- 설령 순서를 바꿔 통과해도 다음 줄에서 또 실패한다: 일반 입찰 주문엔 SaleBid가 연결되지 않았고 `SaleBidQueryService.findByOrderId`는 null이 아니라 `IllegalArgumentException`을 던진다(`sale/service/query/SaleBidQueryService.java:26-29`, 호출 `OrderShipmentCommandService.java:116` — try/catch 밖).
- (참고) 즉시 구매(b) 주문도 이 API로는 PENDING_PAYMENT → IN_TRANSIT이 불가해 동일하게 실패한다(`OrderStatus.java:24`).

## 2. 배송 완료 감지

### 2-1. 누가·언제·어떻게
- 시스템이 자동으로 감지한다. `ShipmentBatchScheduler.scheduleShipmentStatusJob`이 `@Scheduled(cron = "0 0 */6 * * *")` — **6시간마다**(0·6·12·18시 정각), `updateShipmentStatusesJob`을 timestamp 파라미터로 실행(`G/config/ShipmentBatchScheduler.java:34-40`). 예외는 `printStackTrace`만(`:41-43`).
- 수동 보조 경로: `check-status` API(`OrderShipmentCommandService.updateAndCheckShipmentStatus`, `:~452`)는 같은 매핑으로 즉시 처리하지만 주기 실행은 아니다.

### 2-2. 대상·실제 실행 코드
- Job `updateShipmentStatusesJob` → Step `updateShipmentStatusesStep`: chunk 50, `faultTolerant().skip(Exception.class).skipLimit(50)`(`S/config/UpdateShipmentStatusesJobConfig.java:55-82`).
- 대상(Reader): `SELECT s FROM OrderShipment s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL`, page 50(`:95`).
- **실제 실행되는 Processor**는 `new ShipmentItemProcessor(...)`(`:69-73`) = `S/config/ShipmentItemProcessor.java:57-157`. 공유 Playwright 브라우저로 `https://trace.cjlogistics.com/next/tracking.html?wblNo=`+운송장을 열어(`:72-83`) `tbody#statusDetail tr` 마지막 행의 5번째 td(`:181`)를 읽는다.
- 같은 파일의 `shipmentItemProcessor()` 빈(`JobConfig.java:104-177`)과 `parseCjLogisticsStatus`(`:186`), `OrderShipmentCommandService.updateShipmentStatuses()`(`:309`, 호출처 없음), `CjTrackingPlaywright` 사용 코드는 이 Step에서 쓰이지 않는 사본이다(Step은 `:69`에서 새 인스턴스를 직접 생성).
- Writer는 `JpaItemWriter`(`:239-246`), 브라우저는 `BrowserManageStepListener`가 Step 전후로 열고 닫는다(`:80`).

### 2-3. 택배사 문자열 → 내부 상태
`ShipmentItemProcessor.mapToShipmentStatus`(`:220-226`): `"배송완료"`→`DELIVERED`, `"배송출발"`→`OUT_FOR_DELIVERY`, **그 외 전부**→`IN_TRANSIT`("집화처리", "간선상차" 등). 완전 일치(trim만 됨, `:181`).
- 현재 상태와 같으면 아무것도 안 하고 반환(`:101-105`).
- 주의: 조회 결과가 OUT_FOR_DELIVERY인 배송에 CJ가 "배송출발"이 아닌 다른 문구(→IN_TRANSIT)를 주면 `OUT_FOR_DELIVERY→IN_TRANSIT`은 전이 불가(`S/entity/ShipmentStatus`)라 `IllegalStateException`→`ShipmentException`으로 실패·skip된다(`:125`, `OrderShipment.java:47-55`, `:138-145`).

## 3. 배송 완료 판정 이후 (처리 코드 기준)
Processor `:108-117`:
1. `orderShipment.updateStatus(DELIVERED)`(`:113`) — IN_TRANSIT/OUT_FOR_DELIVERY에서 허용.
2. `OrderShipmentCommandService.completeOrder(orderId)`(`:116` → `:191-229`):
   - OrderBid 조회, 없으면 예외(`:196-197`) → `order.updateStatus(COMPLETED)`(`:204`) → `updateSaleStatusToSold`(`:208`) → 구매자 알림 "[completeOrder] 주문이 완료 처리되었습니다"(`:211-217`). 예외는 모두 `ShipmentException(ORDER_NOT_FOUND_FOR_SHIPMENT)`로 래핑(`:221-227`).
3. `NotificationCommandService.notifyShipmentCompleted(order)`(`:117`) → 구매자 알림 "[배송 완료] …"(`notification/service/command/NotificationCommandService.java:219-229`).
4. Writer가 shipment 저장.

알림(정상 진행 시): **구매자 2건**(completeOrder 1 + 배송 완료 1). 판매자 알림은 `updateSaleStatusToSold`에서 Sale이 아직 SOLD로 전이 가능한 때만 1건(`:119`, `:133`; OrderBid 경로는 같은 Sale이 이미 SOLD가 되어 중복 발송되지 않음 `:156`).

입찰 상태: 배치 경로는 `updateOrderAndSaleBidStatusToCompleted`를 **호출하지 않는다**(호출처는 `updateTrackingInfo:289`뿐). 따라서 OrderBid/SaleBid는 배송 완료 뒤에도 MATCHED 그대로이고 COMPLETED가 되지 않는다.

## 4. 주문 종류별 차이

### (a) 실배송 일반 구매 입찰 주문 — 끝까지 진행되지 않음
- 주문이 PREPARING이라 `completeOrder`의 `order.updateStatus(COMPLETED)`(`OrderShipmentCommandService.java:204`)에서 `InvalidOrderStatusException`(PREPARING→COMPLETED 불가, `OrderStatus.java:26`) → `ShipmentException(ORDER_NOT_FOUND_FOR_SHIPMENT)`(`:221-227`). Sale/알림 단계(`:208`, `:211`)는 실행되지 않는다.
- 결과: 주문 COMPLETED 안 됨, 구매자·판매자 알림 0건, 입찰 상태 불변. Processor는 예외를 `ShipmentException`으로 그대로 던져(`ShipmentItemProcessor.java:133-145`) 해당 건은 skip 처리된다(5번 참조).
- 애초에 1번에서 보듯 이 주문은 PATCH API로 IN_TRANSIT 운송장 등록이 불가능하다. 이 배치의 대상이 되려면 `check-status` API(주문 상태 검증 없이 shipment만 IN_TRANSIT으로 바꿈, `:~490-505`)로 shipment만 IN_TRANSIT이 된 경우뿐이다.

### (b) 즉시 구매 주문 — 판매 쪽 후속 처리는 건너뛰고 주문/알림은 진행
- 이 주문은 OrderBid가 있고(`OrderBidCommandService.java:192-205`) 주문 상태가 PENDING_PAYMENT라서 `PENDING_PAYMENT→COMPLETED`가 허용된다(`OrderStatus.java:24`). 따라서 `completeOrder`의 order COMPLETED(`:204`)와 구매자 알림(`:211-217`) 및 `notifyShipmentCompleted`(`:117`)가 진행된다 → shipment DELIVERED, Order COMPLETED, 구매자 알림 2건.
- 판매 쪽: 결제 시점에 이미 Sale이 SOLD로 바뀌어 있다. `createInstantOrder` 안의 `processPayment`(`OrderCommandService.java:305`) → `notifyUsersAndUpdateSaleStatus`(`payment/service/command/PaymentCommandService.java:83`)가, 이때 order.getOrderBid()==null이라 SaleBid 경로(`:388-406`)로 `sale.updateStatus(SOLD)`(`:404`, `Sale.updateStatus`는 검증 없음 `sale/entity/Sale.java:73-75`)를 한다. 그래서 배송 완료 시 `canTransitionTo(SOLD)`가 false(`SaleStatus.java:23`)여서 판매자 알림·창고 상태 변경은 일어나지 않는다(`OrderShipmentCommandService.java:119`, `:156`). → 판매자 알림 0건.
- OrderBid/SaleBid는 MATCHED로 남는다(위 3번과 동일).

요약: (a)는 completeOrder에서 예외로 중단(주문 PREPARING 유지, 알림 0, 배송 상태 쪽만 아래 5의 주의 참조), (b)는 주문 COMPLETED + 구매자 알림 2건까지 진행하되 입찰은 COMPLETED가 되지 않고 판매자 알림은 없다.

## 5. 실패 처리 (주기 처리 중 한 건 실패)
- Processor 안의 모든 예외는 `ShipmentException`(`EXTERNAL_TRACKING_SERVICE_ERROR` 등)으로 던져진다(`ShipmentItemProcessor.java:133-145`). Step이 `.skip(Exception.class).skipLimit(50)`이므로(`UpdateShipmentStatusesJobConfig.java:76-77`) 그 건은 skip되고 `shipmentSkipListener`가 로그만 남긴다(`:252-266`). Job은 중단되지 않고 나머지 건은 계속 처리된다. skip이 50건을 넘으면 Step이 실패한다.
- `completeOrder`는 청크 트랜잭션에 합류한 `@Transactional` 호출이라(`OrderShipmentCommandService.java:190`) 실패 시 같은 청크 트랜잭션이 롤백 대상이 된다. 청크(50건) 단위 트랜잭션이므로 Spring Batch의 fault-tolerant 동작으로 청크가 롤백된 뒤 항목 단위로 다시 처리되며, 실패 건만 skip되고 나머지는 정상 처리·저장된다.
- 주의(코드상 사실): Processor는 `completeOrder` 호출 **전에** 메모리의 shipment를 DELIVERED로 바꾼다(`:113`). 실패한 건이 청크 재처리에서 같은 객체로 다시 들어오면 "상태 동일" 가드(`:101-105`)에 걸려 completeOrder 없이 반환될 수 있고, 그러면 Writer가 shipment만 DELIVERED로 저장하고 주문은 완료되지 않는 불일치가 생길 수 있다. 이 부분은 Spring Batch 재처리 동작에 의존하며 코드만으로 확정하지 못했다(실행 미검증).
- 스케줄러 레벨 실패는 `printStackTrace`만 하고 다음 6시간 주기에 다시 실행된다(`ShipmentBatchScheduler.java:41-43`). 실패한 shipment는 상태가 DELIVERED로 바뀌지 않았다면 IN_TRANSIT/OUT_FOR_DELIVERY로 남아 다음 주기에 다시 조회 대상이 된다.
