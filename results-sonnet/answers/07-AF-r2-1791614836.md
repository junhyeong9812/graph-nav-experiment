# 즉시 구매 처리 흐름 (POST /order-bids/instant)

경로 약어: `D` = `src/main/java/com/fream/back/domain/`

## 1. 진입 API · 처리 단계 · 동기/비동기 · 응답 ID

**진입점**: `POST /order-bids/instant` → `OrderBidCommandController#createInstantOrderBid`
(`D order/controller/command/OrderBidCommandController.java:22,89-90`).
`/sale-bids/instant`(`SaleBidCommandController`)는 판매자가 구매 입찰을 골라 즉시 판매하는 반대 방향 API이며 이 질문의 흐름이 아니다.

**처리 단계 (모두 한 요청 스레드, 한 트랜잭션 안에서 순차 실행)**

1. 컨트롤러가 이메일을 추출하고 `paymentRequest.userEmail=이메일`, `orderId=null`로 보강한다 (`OrderBidCommandController.java:92,98,119-122`).
2. `OrderBidCommandService#createInstantOrderBid` (`@Transactional`, `D order/service/command/OrderBidCommandService.java:118-149`)
   - 입력 검증: 이메일·saleBidId·addressId·paymentRequest null 체크 (`:154-167`)
   - 구매자 조회 (`:126`), SaleBid 조회와 Sale 연결 여부만 검증 (`:129,172-184`). SaleBid 상태(이미 MATCHED인지)나 구매자=판매자 여부는 검증하지 않는다.
3. `OrderCommandService#createInstantOrder` (`D order/service/command/OrderCommandService.java:219-319`)
   1. 배송지 조회 `addressQueryService.getAddress` (`:238`)
   2. `Order` 저장, 상태 `PENDING_PAYMENT`, 금액은 `saleBid.getBidPrice()` (`:241-247`)
   3. `paymentRequest.orderId = order.id` 설정 (`:250`)
   4. `OrderItem` 생성 (수량 1, 가격은 입찰가) (`:255-256`, `OrderItemCommandService.java:45-52`)
   5. `OrderShipment` 생성, 상태 `PENDING` (`:264-271`, `D shipment/service/command/OrderShipmentCommandService.java:61-68`)
   6. `saleBid.assignOrder(order)` + `saleBid.updateStatus(MATCHED)` 후 `entityManager.flush()` (`:279-283`)
   7. 판매 측 `Sale.isWarehouseStorage()`가 true면 창고 상태를 `ASSOCIATED_WITH_ORDER`로 변경 (`:291-294`)
   8. `paymentCommandService.processPayment(...)` 호출 (`:305`)
4. 결제 후 `OrderBid`를 생성한다 (`OrderBidCommandService.java:142`, 구현 `:189-207`). 상태는 `MATCHED`, `isInstantPurchase=true`, `order`·`sale` 연결, `bidPrice`는 판매 입찰가.

**동기/비동기**: 동기다. Kafka나 `@Async`를 쓰지 않고 한 `@Transactional` 안에서 결제 대행사(PortOne) HTTP 호출까지 끝낸 뒤 응답한다. 비동기(Kafka)는 별개 엔드포인트인 `OrderCommandController`의 결제·배송 처리에만 쓰인다 (`D order/controller/command/OrderCommandController.java:30,54`).

**응답으로 돌려주는 ID**: 컨트롤러 변수명과 응답 메시지는 "orderId"·"즉시 구매"라고 하지만, 실제 값은 **`OrderBid`의 ID**다. `createInstantOrderBid(...)`가 `OrderBid`를 반환하고 컨트롤러가 `.getId()`를 꺼낸다 (`OrderBidCommandController.java:101-107,109`; 반환 타입 `OrderBidCommandService.java:119,142-144`). 이 ID는 `Order`의 ID와 다를 수 있다.

## 2. 새로 생성되는 엔티티와 상태 전이 (순서대로)

| 순서 | 동작 | 직후 상태 | 근거 |
|---|---|---|---|
| a | `Order` 생성 | `Order.status = PENDING_PAYMENT` | `OrderCommandService.java:241-245` |
| b | `OrderItem` 생성 | 수량 1, 가격 = 입찰가 | `OrderItemCommandService.java:45-52` |
| c | `OrderShipment` 생성 | `ShipmentStatus.PENDING` | `OrderShipmentCommandService.java:67` |
| d | 기존 `SaleBid`에 주문 연결 | `SaleBid.status = MATCHED` (`assignOrder` 자체도 MATCHED로 바꾼다) | `OrderCommandService.java:279-280`, `D sale/entity/SaleBid.java:58-61,66-68` |
| e | (판매 Sale이 창고 보관인 경우) 기존 `WarehouseStorage` 상태 변경 | `ASSOCIATED_WITH_ORDER` | `OrderCommandService.java:291-294`, `D warehouseStorage/service/command/WarehouseStorageCommandService.java:117-133` |
| f | `Payment`(Card/Account/General) 생성 | 결제 수단별로 다름 (3번 참조) | `PaymentCommandService.java:57-80` |
| g | 결제 후처리: `Sale.status = SOLD` | `Sale.status = SOLD` (등록 시 초기값은 `PENDING_SHIPMENT`) | `PaymentCommandService.java:383-406`, `SaleCommandService.java:62,108`, `D sale/entity/Sale.java:73-75` |
| h | `OrderBid` 생성 | `OrderBid.status = MATCHED`, `isInstantPurchase = true` | `OrderBidCommandService.java:192-205` |

- `Sale.updateStatus`는 전이 규칙 검사(`SaleStatus.canTransitionTo`) 없이 값을 그냥 대입한다 (`Sale.java:73-75`). 그래서 `PENDING_SHIPMENT → SOLD`가 막히지 않는다.
- 결제 후처리(g)의 호출 시점에는 `OrderBid`가 아직 없다(h는 결제 뒤). 그래서 `order.getOrderBid()==null` 분기로 들어가 `saleBidQueryService.findByOrderId(order.getId())`로 SaleBid → Sale을 찾아 `SOLD`로 바꾼다 (`PaymentCommandService.java:388-406`). d 단계의 `flush`가 이 조회를 가능하게 한다.
- Order의 `PAYMENT_COMPLETED`·`PREPARING` 등으로의 전이는 이 경로에서 일어나지 않는다 (5번 참조).

## 3. 결제 수단별 결과 · 성공 여부 · 카드 실패 시

`PaymentCommandService#processPayment`가 `resolvedPaymentType`으로 분기한다 (`PaymentCommandService.java:67-80`). 공통 사전 검증은 order·user·요청 null, `requestDto.orderId == order.id`, 이메일 일치, `paidAmount > 0`이다 (`:117-146`). 결제 금액과 주문 금액(입찰가)이 같은지는 검증하지 않는다.

`Payment` 기본값은 `status=PENDING`, `isSuccess=false` (`D payment/entity/Payment.java:39,44`). `PENDING → PAID`만 허용된다 (`D payment/entity/PaymentStatus.java:12-13`).

| 수단 | 처리 | 결과 상태 | 근거 |
|---|---|---|---|
| CARD | 저장된 `PaymentInfo` 조회 → PortOne `processCardPayment` 동기 호출 → 응답 `status`가 `"success"`일 때만 `PAID` + `isSuccess=true` | 성공 응답: `PAID`. 그 외 응답: `PENDING`, `isSuccess=false` | `PaymentCommandService.java:166,179,203-208` |
| ACCOUNT | 은행명 검증(`Bank` enum)만 하고 외부 호출 없이 저장 | 항상 `PENDING` (입금 확인 로직 없음) | `:243-262`, `:470-481` |
| GENERAL | `impUid`만 필수. 클라이언트가 보낸 값을 그대로 신뢰해 저장 (PG 서버 검증 없음) | 즉시 `PAID`, `isSuccess=true` | `:297-316` |

**즉시 구매가 끝까지 성공하는지**: 예외가 없으면 수단과 무관하게 `OrderBid` ID를 반환하며 "성공" 응답을 준다. 하지만 ACCOUNT는 `Payment=PENDING`인 채로 `Sale=SOLD`, 구매·판매자 알림까지 진행된다. 입금이 확인되기 전에 판매 완료로 처리되는 셈이다. 어느 수단이든 `Payment`가 `PAID`로 바뀌지 않은 상태에서 흐름이 계속될 수 있다.

**PortOne이 카드 결제를 실패로 응답하면**: 실패 응답 형태에 따라 두 갈래다.

- **HTTP 비 200이거나 응답 `code != 0`**: `PaymentProcessingException`이 발생한다 (`D payment/portone/PortOneApiClient.java:270-274`). `PaymentApiException`(통신 오류)만 최대 3회 재시도한다 (`:223-227,288-290`). 예외는 `OrderPaymentProcessingFailedException`으로 감싸져 전파된다 (`OrderCommandService.java:305-309`). 같은 트랜잭션이 롤백되므로 Order·OrderItem·OrderShipment·SaleBid 매칭이 모두 되돌려지고 OrderBid는 생성되지 않는다. 컨트롤러는 에러 응답을 준다.
- **HTTP 200 + `code == 0`이지만 `response.status`가 `success`가 아님** (예: PG 승인 거절 `failed`): 클라이언트는 예외를 던지지 않고 `response`를 그대로 반환한다 (`PortOneApiClient.java:277-285`). `PaymentCommandService`는 `"success"`일 때만 `PAID`로 올리고, 아니면 `CardPayment`를 `PENDING`/`isSuccess=false`로 저장한다 (`:203-208`). 이후 흐름은 예외 없이 이어진다. 즉 `Sale=SOLD`로 바뀌고 "결제가 완료되었습니다" 알림이 구매자·판매자에게 나가며(`:403-404,438-453`), `OrderBid=MATCHED`가 만들어지고 성공 응답이 간다. 코드는 결제 실패를 감지해 되돌리지 않는다. 이름이나 메시지와 달리 "결제 완료"가 사실이 아닐 수 있다.

## 4. 알림 대상 · 시점 · 방식

- **누가**: 구매자와 판매자 각각 1건씩, `NotificationCategory.SHOPPING` / `NotificationType.BID` (`PaymentCommandService.java:438-455`).
  - 구매자(`order.getUser()`): "결제가 완료되었습니다. 주문 ID: {orderId}"
  - 판매자(`sale.getSeller()`): "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}"
- **언제**: `processPayment` 안에서, Payment 저장 직후이고 `Sale=SOLD`로 바꾸기 직전이다 (`:83`, `:403-404`). 요청 처리 중 동기로 발생하며 트랜잭션 커밋 전이다. 알림 코드에서 발생한 예외는 삼키므로 흐름은 막지 않는다 (`:421-425,457-461`).
- **어떻게**: `NotificationCommandService#createNotification`이 DB에 `Notification`을 저장하고(`D notification/service/command/NotificationCommandService.java:44-57`), Redis에 `WebSocket:User:{email}` 키가 있을 때만 STOMP `convertAndSendToUser(email, "/queue/notifications", dto)`로 실시간 전송한다 (`:37-38,300-313`). 접속하지 않았으면 저장만 되고 푸시는 없다 (`:320-322`). Kafka·이메일·푸시 알림은 쓰지 않는다. `notification-topic`은 발행만 있고 구독이 없다(NAV 기준).
- 카드 결제가 실패 응답(`PENDING`)이어도 위 알림은 그대로 나간다 (3번 참조).
- 판매자 입찰 등록 시점의 알림(`SaleCommandService#createSale`)은 이 흐름과 별개다.

## 5. 최종 주문 상태 · 창고 보관 선택 시 차이

**최종 주문 상태**: `Order.status`는 **`PENDING_PAYMENT`**에서 바뀌지 않는다.
- `createInstantOrder`는 상태를 `PENDING_PAYMENT`로 만든 뒤 `updateStatus`를 한 번도 호출하지 않는다 (`OrderCommandService.java:241-245,305-311`).
- `PaymentCommandService`도 `Order`의 상태를 건드리지 않고 `Payment`·`Sale`만 바꾼다 (`:383-426`).
- 즉시 구매 경로는 `Order.assignPayment`도 호출하지 않는다 (`OrderCommandService.java:305` 반환값 무시).
- `PAYMENT_COMPLETED → PREPARING → (IN_WAREHOUSE → COMPLETED)` 전이는 `processPaymentAndShipment`(별도 Kafka 기반 `/orders/...` 경로)에만 있다 (`:161-177`).

결과적으로 즉시 구매 직후의 최종 상태는 다음과 같다.

| 대상 | 상태 |
|---|---|
| Order | `PENDING_PAYMENT` |
| OrderBid | `MATCHED` |
| SaleBid | `MATCHED` |
| Sale | `SOLD` |
| OrderShipment | `PENDING` |
| Payment | CARD 성공/GENERAL = `PAID`, ACCOUNT·CARD 실패 응답 = `PENDING` |

**"창고 보관"을 선택한 경우**: 요청의 `warehouseStorage` 플래그는 즉시 구매 경로에서 **사실상 무시된다**.
- 컨트롤러는 `requestDto.isWarehouseStorage()`를 서비스에 넘기고(`OrderBidCommandController.java:105`), `createInstantOrder`의 파라미터 `isWarehouseStorage`로 전달된다(`OrderCommandService.java:221`). 하지만 메서드 본문에서 이 변수를 읽는 곳이 없다(`:222-319`). 로그(`OrderBidCommandController.java:94-95`) 외에는 쓰이지 않는다.
- 창고 관련 분기는 **판매자 쪽 `Sale.isWarehouseStorage()`**만 본다 (`OrderCommandService.java:291-294`). 이 값이 true일 때만 기존 `WarehouseStorage`가 `ASSOCIATED_WITH_ORDER`로 바뀐다.
- 구매자가 창고 보관을 선택해도 `WarehouseStorage`를 새로 만들지 않고, Order를 `IN_WAREHOUSE`/`COMPLETED`로 바꾸지 않으며, 배송지 기반 `OrderShipment`도 그대로 만든다 (`:262-275`). 구매자 창고 보관 처리(`createOrderStorage`, `IN_WAREHOUSE`)는 `processPaymentAndShipment` 쪽에만 있다 (`:163-172`).
- 주의: 판매자의 `Sale`이 창고 보관인데 `WarehouseStorage`를 찾지 못하는 등 예외가 나면 `OrderWarehouseStorageProcessingFailedException`으로 전체가 롤백된다 (`:295-301`).
