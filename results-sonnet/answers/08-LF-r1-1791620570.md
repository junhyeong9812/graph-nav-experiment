# 구매자 배송: 운송장 등록 ~ 배송 완료 (실제 코드 동작 기준)

경로 약어: `B` = `src/main/java/com/fream/back/`

## 1. 운송장 등록 요청

### 1-1. 진입 API
- `PATCH /shipments/order/{shipmentId}/status`, body `OrderShipmentRequestDto(courier, trackingNumber)` — `B domain/shipment/controller/command/OrderShipmentCommandController.java:20,33-45`. 서비스는 `OrderShipmentCommandService#updateTrackingInfo` (`B domain/shipment/service/command/OrderShipmentCommandService.java:239`).
- 소유자/관리자 검증 없음(인증만 필요). courier/trackingNumber가 비면 `TRACKING_INFO_REQUIRED` (`...CommandService.java:243-246`).
- 별도로 `POST /shipments/order/{id}/check-status`(`Controller:58`)도 송장을 등록하며 택배사를 즉시 조회한다(`Service:452`). 질문의 "운송장 등록"은 위 PATCH.

### 1-2. 의도된 상태 변경 순서와 알림 (`Service:239-303`)
1. `OrderShipment` → IN_TRANSIT (`shipment.updateTrackingInfo`, 검증 없이 설정. `B domain/shipment/entity/OrderShipment.java:41-45`) — `Service:256`
2. `Order` → IN_TRANSIT (`order.updateStatus`) — `Service:259-260`
3. 구매자 알림: "상품이 출발하였습니다. 주문 ID: …" — `Service:265-271`
4. `updateSaleStatusToSold(orderId)` — `Service:276`, 본체 `Service:112-183`
   - SaleBid 경로: Sale이 SOLD로 전이 가능하면 Sale→SOLD, 창고보관이면 창고 SOLD, 판매자 알림 "상품이 성공적으로 판매 완료되었습니다…" (`Service:116-143`)
   - OrderBid 경로: 같은 조건이면 Sale→SOLD + 판매자 알림 (`Service:150-176`)
5. 창고보관 Sale이면 `updateWarehouseStatusToSold` 재호출 — `Service:279-286`
6. OrderBid·SaleBid가 MATCHED면 → COMPLETED — `Service:289`, 본체 `Service:412-440` (실패해도 로그만 남김)
- 즉 "출발" 시점에 Sale SOLD / 입찰 COMPLETED까지 처리하도록 짜여 있고, 알림은 구매자 1건 + 판매자(최대 1~2건).

### 1-3. 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문에서의 결과: **끝까지 성공하지 못함**
- 주문 상태: 결제 후 실배송이면 PAYMENT_COMPLETED → PREPARING에서 멈춘다 (`B domain/order/service/kafka/OrderEventConsumer.java:195,214-218`). 창고보관이 아니므로 IN_WAREHOUSE/COMPLETED로 가지 않는다.
- 전이표: PREPARING은 {IN_WAREHOUSE, SHIPMENT_STARTED}만 허용, IN_TRANSIT은 SHIPMENT_STARTED에서만 도달 가능 (`B domain/order/entity/OrderStatus.java:26,28`). SHIPMENT_STARTED를 세팅하는 코드는 없다.
- 실패 지점: `Service:260` `order.updateStatus(IN_TRANSIT)` → `Order.updateStatus`가 `InvalidOrderStatusException` 발생 (`B domain/order/entity/Order.java:113-120`).
- 이 예외는 `catch (ShipmentException)`에 안 걸리고 `catch (Exception)`에 걸려 `ShipmentException(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")`로 재포장됨 (`Service:295-301`). 에러코드 S001/404 (`B domain/shipment/exception/ShipmentErrorCode.java:12`).
- 저장되는 것: **없음**. `@Transactional`(`Service:238`) 메서드에서 RuntimeException이 밖으로 나가므로 롤백. 1단계에서 메모리상 바꾼 courier/trackingNumber/IN_TRANSIT도 DB에 남지 않아 OrderShipment는 PENDING·운송장 null 그대로, Order는 PREPARING 그대로. 3단계 이후(알림, Sale, 입찰)는 실행도 안 됨 → 알림 0건.
- 응답: 컨트롤러는 예외를 잡지 않음(`Controller:33-49`) → `GlobalExceptionHandler#handleShipmentException`(`B global/exception/GlobalExceptionHandler.java:459-473`) → **HTTP 404**, body `ErrorResponse{code:"S001", message:"배송 정보를 찾을 수 없습니다."(enum 기본 문구), status:404, path}`. 상세 원인 메시지는 body에 노출되지 않는다.
- (참고) 설령 5단계까지 갔어도, 일반 입찰 주문은 SaleBid가 없으면 `SaleBidQueryService#findByOrderId`가 IllegalArgumentException을 던진다 (`B domain/sale/service/query/SaleBidQueryService.java:26-29`, 호출 `Service:116`).

## 2. 배송 완료 감지

### 2-1. 누가/언제/어떻게
- 사람이 `check-status` API를 호출하는 수동 경로(`Service:452`)와, 스케줄러 배치 경로가 있다. 상시 감지는 배치.
- 스케줄러: `ShipmentBatchScheduler#scheduleShipmentStatusJob`, `@Scheduled(cron = "0 0 */6 * * *")` → **6시간마다**(00/06/12/18시) `updateShipmentStatusesJob` 실행 — `B global/config/ShipmentBatchScheduler.java:34-44`. 예외는 `printStackTrace`만.

### 2-2. 조회 대상
- Reader JPQL: `status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND trackingNumber IS NOT NULL`, pageSize 50 — `B domain/shipment/config/UpdateShipmentStatusesJobConfig.java:87-97`. 즉 운송장이 등록돼 IN_TRANSIT/OUT_FOR_DELIVERY인 구매자 배송(OrderShipment)만. (PENDING은 대상 아님.)
- chunk 50, `faultTolerant().skip(Exception.class).skipLimit(50)` — `JobConfig:66-81`.

### 2-3. 실제 실행되는 처리 코드
- Step이 쓰는 것은 `new ShipmentItemProcessor(playwrightBrowserManager(), notificationService, orderService)` (`JobConfig:69-73`) → `B domain/shipment/config/ShipmentItemProcessor.java:57`. 공유 Playwright 브라우저로 `https://trace.cjlogistics.com/next/tracking.html?wblNo=` 접속, `tbody#statusDetail tr` 마지막 행 5번째 td를 Jsoup 파싱 (`ItemProcessor:28-29,72-94,167-191`).
- 실행되지 않는 유사 코드: `JobConfig#shipmentItemProcessor()` @Bean(`JobConfig:104-177`, Step에 연결 안 됨), `JobConfig#parseCjLogisticsStatus`(`:186`, 미사용), `OrderShipmentCommandService#updateShipmentStatuses`(`Service:309`, 호출처 없음 — grep 결과 정의뿐), `CjTrackingPlaywright` 호출 방식은 수동 API(`Service:477`)에서만.

### 2-4. 택배사 문자열 → 내부 상태
- `"배송완료"` → DELIVERED, `"배송출발"` → OUT_FOR_DELIVERY, 그 외 모든 문자열 → IN_TRANSIT (`ItemProcessor:220-226`; 같은 매핑 `Service:399-405`). 완전일치(equals) switch.
- 현재 상태와 같으면 변경 없이 그대로 반환 (`ItemProcessor:101-105`). 그 외에는 `OrderShipment.updateStatus` 전이 검증을 받는다(`OrderShipment.java:47-55`). 전이표상 IN_TRANSIT→DELIVERED / OUT_FOR_DELIVERY→DELIVERED는 허용 (`B domain/shipment/entity/ShipmentStatus.java:16-28`).

## 3. 배송 완료 판정 이후 (DELIVERED, `ItemProcessor:108-117`)

상태 변경 순서:
1. `OrderShipment` → DELIVERED (`ItemProcessor:113`)
2. `OrderShipmentCommandService#completeOrder(orderId)` (`ItemProcessor:116`, 본체 `Service:191-229`):
   1. OrderBid 조회 (없으면 예외 → S102로 재포장) — `Service:196-197`
   2. `Order` → COMPLETED — `Service:204`
   3. `updateSaleStatusToSold` — `Service:208` (Sale이 SOLD 전이 가능할 때만 Sale→SOLD + 판매자 알림)
   4. 구매자 알림 "[completeOrder] 주문이 완료 처리되었습니다. 주문 ID: …" — `Service:211-217`
3. `NotificationCommandService#notifyShipmentCompleted` → 구매자 알림 "[배송 완료] 상품이 배송 완료되었습니다…" (`ItemProcessor:117`, `B domain/notification/service/command/NotificationCommandService.java:219-234`; 예외는 삼킴)
4. Writer `JpaItemWriter`가 OrderShipment 반영.

알림: 구매자는 **2건**("[completeOrder]" + "[배송 완료]"). 판매자는 Sale이 SOLD가 아닌 전이 가능 상태일 때만 SaleBid 경로/OrderBid 경로 각 1건(최대 2건) — 아래 4번에서 보듯 실제로는 대부분 0건.

입찰 상태: 배치/`completeOrder`는 OrderBid·SaleBid 상태를 **건드리지 않는다**. COMPLETED 변경은 `updateOrderAndSaleBidStatusToCompleted`(`Service:412`)뿐이며 이는 운송장 등록(`updateTrackingInfo`, `Service:289`)에서만 호출된다. 따라서 배송 완료 시점의 입찰은 그 전 상태(MATCHED) 그대로.

## 4. 주문 종류별 차이

### (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문 → **끝까지 진행되지 않음**
- Order는 PREPARING (`OrderEventConsumer.java:214-218`). `completeOrder`의 `order.updateStatus(COMPLETED)`(`Service:204`)에서 PREPARING→COMPLETED 불허 (`OrderStatus.java:26`) → `InvalidOrderStatusException` → `catch (Exception)`에서 `ShipmentException(ORDER_NOT_FOUND_FOR_SHIPMENT, S102)`로 재포장 (`Service:221-228`).
- 결과: Sale→SOLD 처리·구매자 알림 2건·판매자 알림 모두 실행되지 않음. 예외가 processor 밖으로 나가 skip 처리되고 chunk 트랜잭션이 롤백되므로 OrderShipment는 DELIVERED로 저장되지 않고 IN_TRANSIT/OUT_FOR_DELIVERY 그대로 → 6시간마다 재조회·재실패(skip 한도 소모).
- 보충: 이런 주문은 1번에서 PATCH가 실패하므로 애초에 batch 대상(IN_TRANSIT+운송장)이 되려면 `check-status` API를 거쳐야 한다. 그 경로에서 CJ가 "배송완료"를 주면 `Service:486-489`의 `completeOrder`가 같은 이유로 실패하고 전체 롤백, "배송출발"이면 OUT_FOR_DELIVERY로 저장, 그 외 문자열이면 IN_TRANSIT→IN_TRANSIT 전이 불허 `IllegalStateException`(`OrderShipment.java:47-55`)이 S302(503)로 재포장 (`Service:497,507-514`).

### (b) 즉시 구매로 만들어진 주문 → **끝까지 진행되나, 판매 측 후처리는 사실상 없음**
- 즉시 구매 시 Order는 PENDING_PAYMENT로 만들어지고 이후 바뀌지 않는다 (`B domain/order/service/command/OrderCommandService.java:241-245`, 결제 `:305`; 상태 변경 코드 없음). PENDING_PAYMENT→COMPLETED는 허용 (`OrderStatus.java:24`) → `completeOrder`의 Order COMPLETED 성공.
- OrderBid는 결제 이후 생성되어 order와 연결됨(MATCHED, `B domain/order/service/command/OrderBidCommandService.java:189-206`), 따라서 `completeOrder`의 OrderBid 조회(`Service:196`) 성공.
- Sale은 결제 단계에서 이미 SOLD (`B domain/payment/service/command/PaymentCommandService.java:391-405`, `Sale.updateStatus`는 무검증 `Sale.java:73-75`). `SOLD.canTransitionTo(SOLD)`는 false (`B domain/sale/entity/SaleStatus.java:23`) → `updateSaleStatusToSold`의 두 경로 모두 else(로그만) → **판매자 알림 0건**, 창고 SOLD 갱신도 이 경로에선 안 일어남.
- 결과: OrderShipment DELIVERED, Order COMPLETED, 구매자 알림 2건. OrderBid·SaleBid는 MATCHED로 남음(COMPLETED 안 됨).
- 주의: 즉시 구매 주문의 송장 등록 PATCH는 Order가 PENDING_PAYMENT라 `IN_TRANSIT` 전이 불허(`OrderStatus.java:24`)로 1-3과 같은 이유로 실패한다. IN_TRANSIT+운송장 상태가 되려면 `check-status` 경로가 필요.

## 5. 실패 처리 (배치)
- Processor가 예외를 던지면(운송장 무효, 브라우저 없음, 파싱 실패, 전이 불허, `completeOrder` 실패 등; 비-ShipmentException은 S302로 래핑 — `ItemProcessor:133-145`) Step은 `skip(Exception.class)`라서 Job을 중단하지 않고 해당 건만 skip (`JobConfig:75-78`, SkipListener는 로그).
- 해당 건: DB 변경이 롤백되어 상태 그대로(IN_TRANSIT/OUT_FOR_DELIVERY 유지) → 다음 6시간 주기에 다시 대상이 된다. 같은 chunk의 다른 건: faultTolerant 스텝은 chunk 트랜잭션을 롤백한 뒤 항목을 하나씩 재처리하므로 성공 건은 정상 반영된다(다만 CJ 조회가 중복 실행됨). `completeOrder`는 같은 트랜잭션에 참여하므로 그 내부 실패는 chunk를 rollback-only로 만들어 이 재처리 경로를 탄다.
- skip 누적이 50(`SKIP_LIMIT`)을 넘으면 Step이 실패하여 남은 건은 그 주기에 처리되지 않는다. 실패 건 수는 알림/재시도 큐 없이 로그만 남는다.
- (참고) 사용되지 않는 구 버전 `updateShipmentStatuses`(`Service:322-388`)는 건별 try/catch로 계속 진행하지만 호출처가 없다.
- (참고) Reader가 페이징 쿼리이고 처리하면서 상태가 DELIVERED로 바뀌어 조건에서 빠지므로, 50건을 넘는 경우 다음 페이지(offset 50)에서 일부 건이 건너뛰어질 수 있다 — 코드상 추정, 실행 확인은 하지 않음 (`JobConfig:91-96`).
