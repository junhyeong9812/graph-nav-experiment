# 즉시 구매(Instant Purchase) 처리 흐름

경로 접두사 `src/main/java/com/fream/back/domain/` 는 `D/` 로 줄여 쓴다. 줄 번호는 현재 소스 기준.

## 1. 진입 API / 처리 단계 / 동기·비동기 / 응답 ID

**API**: `POST /order-bids/instant` (prod nginx가 `/api`를 떼므로 코드에는 `/order-bids` 만 있음)
- `D/order/controller/command/OrderBidCommandController.java:22` (`@RequestMapping("/order-bids")`), `:89-110` (`createInstantOrderBid`)

**단계**
1. 컨트롤러: 이메일 추출(`:92`) → `enrichPaymentRequest`로 `paymentRequest.userEmail=email`, `orderId=null` 세팅(`:98`, `:119-123`) → 서비스 호출(`:101-107`).
2. `OrderBidCommandService#createInstantOrderBid` (`@Transactional`, `D/order/service/command/OrderBidCommandService.java:118-149`):
   입력 검증(`:123`, `:154-167`) → 구매자 조회(`:126`) → `SaleBid` 조회(`:129`, `:172-184`; 판매 입찰이 없거나 sale이 없으면만 실패. **SaleBid 상태/Sale 상태 검증은 없음**) → `OrderCommandService#createInstantOrder`(`:133`) → `OrderBid` 생성·저장(`:142`, `:189-207`).
3. `OrderCommandService#createInstantOrder` (`@Transactional`, `D/order/service/command/OrderCommandService.java:219-319`):
   배송지 조회(`:238`) → Order 저장(`:241-247`) → `paymentRequest.setOrderId`(`:250`) → OrderItem(`:255-256`) → OrderShipment(`:264-271`) → SaleBid 매칭 + `flush`(`:279-283`) → 판매자 창고 보관 연결(`:291-293`) → 결제(`:305`) → Order 반환(`:311`).

**동기/비동기**: 전부 **동기, 단일 DB 트랜잭션**이다. Kafka 호출/`@Async`가 없다. 결제도 요청 스레드 안에서 PortOne REST를 직접 호출한다(`D/payment/service/command/PaymentCommandService.java:57-83`, `D/payment/portone/PortOneApiClient.java:229-295`). (비동기 Kafka 경로 `order-processing-topic`은 *입찰 후 결제* 흐름 `POST /orders/{id}/process-payment-shipment` 용이며 즉시 구매에서는 쓰이지 않음.)

**응답 ID**: `OrderBid`의 ID. 서비스가 반환한 `OrderBid`에서 `.getId()`를 꺼내(`OrderBidCommandController.java:101-107`) 변수명 `orderId`로 `ResponseDto.success`에 담는다(`:109`). 변수명·Javadoc("생성된 주문 ID", `:82`)과 달리 **Order ID가 아니라 OrderBid ID**다(반환 타입 `OrderBid`, `OrderBidCommandService.java:119`, `:206`).

## 2. 새로 생기는 엔티티와 상태 변화 순서

| 순서 | 동작 | 직후 상태 | 근거 |
|---|---|---|---|
| ① | `Order` 신규 저장 (totalAmount = SaleBid.bidPrice) | `Order.status = PENDING_PAYMENT` | `OrderCommandService.java:241-247` |
| ② | `OrderItem` 신규 (productSize = SaleBid의 사이즈) | — | `:255-256` |
| ③ | `OrderShipment` 신규 (주소록의 수령인·전화·우편번호·주소) | `ShipmentStatus.PENDING` | `:264-271`, `D/shipment/service/command/OrderShipmentCommandService.java:56-70` (`:67`) |
| ④ | 기존 `SaleBid`에 `assignOrder(order)` + `updateStatus(MATCHED)`, flush | `SaleBid.status = MATCHED` (order 연결) | `:279-283`, `D/sale/entity/SaleBid.java:166-169` |
| ⑤ | 판매자가 창고 보관(`sale.isWarehouseStorage()`)이면 판매자 보관물 상태 변경 | `WarehouseStatus.ASSOCIATED_WITH_ORDER` | `:291-293`, `D/warehouseStorage/service/command/WarehouseStorageCommandService.java:117-133` |
| ⑥ | `Payment`(Card/Account/General) 신규 저장 | 카드 성공 `PAID`+isSuccess=true / 일반 `PAID`+isSuccess=true / 계좌 → 3번 참조 | `PaymentCommandService.java:203-208`, `:314` |
| ⑦ | 결제 직후 `notifyUsersAndUpdateSaleStatus`: 이 시점 `order.getOrderBid()`는 null → `SaleBid.findByOrderId`로 Sale 획득 → 알림 → `Sale.updateStatus(SOLD)` | `Sale.status = SOLD` (전이 검증 없음, 보통 PENDING_SHIPMENT에서 곧바로 SOLD) | `PaymentCommandService.java:383-404`, `D/sale/service/query/SaleBidQueryService.java:26-29`, `D/sale/entity/Sale.java:73-75`, Sale 초기값 `D/sale/service/command/SaleCommandService.java:62` |
| ⑧ | `OrderBid` 신규 저장 (user=구매자, sale 연결, `isInstantPurchase=true`) | `OrderBid.status = MATCHED` | `OrderBidCommandService.java:192-206`, `D/order/entity/OrderBid.java:60-82` |

- 즉 `Sale = SOLD`가 구매자 송장 등록/배송 완료보다 훨씬 먼저, 결제 직후에 설정된다.
- Payment가 Order에 `assignPayment`로 연결되지는 않는다(`createInstantOrder`는 반환값을 버림, `OrderCommandService.java:305`; 연결은 `Payment.assignOrder`쪽만, `PaymentCommandService.java:~200`). Order의 상태 전이 호출(`PAYMENT_COMPLETED` 등)은 이 경로에 없다.

## 3. 결제 수단별 결과

분기: `PaymentCommandService.java:67-80` (`getResolvedPaymentType`, `D/payment/dto/PaymentRequestDto.java:74-87`). 선검증: orderId·이메일 일치, 금액 > 0 (`:117-...`, `:131`, `:136`).

| 수단 | 동작 | 결과 |
|---|---|---|
| **GENERAL** | 클라이언트가 준 `impUid`를 그대로 신뢰, PG 호출 없음 (`:290-320`) | `updateSuccessStatus(true)` + `PAID` (`:313-314`) → **즉시 구매 성공** |
| **CARD** | 저장된 PaymentInfo로 PortOne `/subscribe/payments/onetime` 호출 (`:157-208`, `PortOneApiClient.java:229-295`) | 응답 `status=="success"`이면 `PAID`+성공(`:203-206`) → 성공 |
| **ACCOUNT** | `AccountPayment` 생성 후 `updateStatus(PENDING)` 호출(`:260`). 초기값이 이미 PENDING이고 `PENDING→PENDING`은 `canTransitionTo` 불허(`D/payment/entity/PaymentStatus.java:89-93`) → `Payment.updateStatus`가 `IllegalStateException`(`D/payment/entity/Payment.java:70-76`) → `PaymentProcessingException`(`:236-240` 부근 catch) → `OrderPaymentProcessingFailedException`(`OrderCommandService.java:306-309`) | **항상 실패**, 트랜잭션 롤백 → Order/OrderItem/Shipment/Payment/SaleBid 변경·Sale 변경 전부 취소. **계좌이체로는 즉시 구매가 끝까지 성공하지 못한다.** |

(롤백은 예외가 `OrderException`으로 다시 던져지고 `@Transactional` 메서드 밖으로 나가기 때문: `OrderBidCommandService.java:145-147`, `:212-218`.)

**카드 결제 대행사 실패 응답**
- PortOne 응답이 HTTP≠200 이거나 `code != 0`이면 `PaymentProcessingException` → 위와 같이 전체 롤백, 구매자는 오류 응답 (`PortOneApiClient.java:270-275`). 통신 오류는 `PaymentApiException`(`:288-290`).
- **하지만 `code == 0`이면서 `response.status`가 `"success"`가 아닌 경우(예: 결제 `failed`)에는 예외가 없다.** 코드는 `if ("success".equals(status))`일 때만 `PAID`로 바꿀 뿐(`PaymentCommandService.java:203-206`), 아니면 그대로 저장한다. 그런데 `CardPayment` 생성자가 `setPaidAmount(paidAmount)`를 호출하고(`D/payment/entity/CardPayment.java:38`) 이것이 `isSuccess = paidAmount > 0`을 true로 만든다(`D/payment/entity/Payment.java:60-63`). 결과: Payment는 `status=PENDING`이지만 `isSuccess=true`로 저장되고, 이후 `notifyUsersAndUpdateSaleStatus`가 돌아 "결제가 완료되었습니다" 알림이 가고 **Sale이 SOLD**가 되며 OrderBid가 MATCHED로 저장되고 HTTP 200 "즉시 구매가 성공적으로 처리되었습니다"가 나간다(`PaymentCommandService.java:83`, `OrderBidCommandController.java:109`). 즉 "PG가 실패라고 알려줘도 구매가 성공 처리될 수 있다". 이후 Order는 `PENDING_PAYMENT` 그대로다.

## 4. 알림

- **받는 사람**: 구매자 1명, 판매자(`sale.getSeller()`) 1명. `PaymentCommandService.java:434-460` 부근 `sendNotifications`:
  - 구매자: "결제가 완료되었습니다. 주문 ID: {orderId}" (`SHOPPING`/`BID`)
  - 판매자: "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}" (`SHOPPING`/`BID`)
- **시점**: 결제 생성 직후, 같은 트랜잭션 안(커밋 전), Sale을 SOLD로 바꾸기 직전 (`:383-404`, `:83`). 결제 처리가 성공 경로를 탔을 때(카드 실패응답 포함)만 발송되고, 계좌이체/PG 오류는 롤백이라 알림도 롤백된다.
- **방식**: `NotificationCommandService#createNotification`(`D/notification/service/command/NotificationCommandService.java:44-57`)이 DB 저장 후 즉시 `sendRealTimeNotification`(`:303-323`) 호출 → Redis 키 `WebSocket:User:{email}`가 있는(=WebSocket 접속 중인) 사용자에게만 `convertAndSendToUser(email, "/queue/notifications")`(`:37-38`, `:307-313`)으로 STOMP 푸시. 접속 중이 아니면 DB에만 남는다. Kafka(`notification-topic`)는 쓰지 않는다. 알림 실패는 삼켜진다(`PaymentCommandService.java:417-421`대 catch, `:381-385`대 catch).
- 판매 입찰 쪽(`SaleBid`) 판매자 외에 별도 "배송/검수" 알림은 이 흐름에 없다.

## 5. 최종 상태 / 창고 보관 선택 시

**성공 시 최종 상태 (응답 시점)**
- `Order.status = PENDING_PAYMENT` — 결제 성공 후에도 **PAYMENT_COMPLETED/PREPARING으로 바뀌지 않는다**. `createInstantOrder`에 `Order.updateStatus` 호출이 없고(`OrderCommandService.java:219-319` 전체), `assignPayment`도 호출하지 않는다.
- `OrderShipment = PENDING`, `SaleBid = MATCHED`, `OrderBid = MATCHED(isInstantPurchase=true)`, `Sale = SOLD`, (판매자 보관이면) 판매자 `WarehouseStorage = ASSOCIATED_WITH_ORDER`, `Payment = PAID`(카드/일반 정상 시).
- 이후 상태는 구매자 송장 등록·배송 완료 단계에서 별도 API/배치가 바꾼다(여기서는 범위 밖).

**구매자가 "창고 보관(`warehouseStorage=true`)"을 선택한 경우**: **아무것도 달라지지 않는다.** 값은 컨트롤러가 읽어 서비스로 넘기지만(`OrderBidCommandController.java:94-95`, `:104`; `OrderBidCommandService.java:119-139`), `OrderCommandService#createInstantOrder`는 파라미터 `isWarehouseStorage`를 본문에서 전혀 사용하지 않는다(`:220-319`에 참조 없음). 그래서 구매자용 `WarehouseStorage`가 생성되지 않고(`createOrderStorage` 호출 없음), Order가 `IN_WAREHOUSE→COMPLETED`로 가지도 않으며, 배송(`OrderShipment`)이 그대로 만들어진다. (입찰 후 결제 경로인 `OrderCommandService#processPaymentAndShipment`/Kafka 소비자에서만 `isWarehouseStorage`로 `PAYMENT_COMPLETED→PREPARING→IN_WAREHOUSE→COMPLETED`가 적용됨: `:163-172`.) 창고 관련 분기는 오직 *판매자*의 `sale.isWarehouseStorage()` 여부(`:292-293`)뿐이다.
