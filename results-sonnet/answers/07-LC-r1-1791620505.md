# 즉시 구매 처리 흐름 (`POST /order-bids/instant`)

경로 접두사 `D = src/main/java/com/fream/back/domain/`.

## 1. 진입 API, 처리 단계, 동기/비동기, 응답 ID

**API**: `POST /order-bids/instant` (prod nginx가 `/api`를 떼므로 `/api` 없음)
- `D order/controller/command/OrderBidCommandController.java:22` (`@RequestMapping("/order-bids")`), `:89-110` (`createInstantOrderBid`)

**단계**
1. 컨트롤러: 로그인 이메일 추출 → `paymentRequest.userEmail=email`, `paymentRequest.orderId=null` 세팅 → 서비스 호출. `OrderBidCommandController.java:92,98,119-123`
2. `OrderBidCommandService#createInstantOrderBid`(`@Transactional`): 입력 검증 → 구매자 조회 → `SaleBidQueryService#findById`(없으면 IllegalArgumentException) → `OrderCommandService#createInstantOrder` → `OrderBid` 생성/저장. `D order/service/command/OrderBidCommandService.java:118-149`, `:154-167`, `:172-184`
3. `OrderCommandService#createInstantOrder`(`@Transactional`) 내부 순서 — `D order/service/command/OrderCommandService.java:219-319`
   1. 배송지 조회 `addressQueryService.getAddress(email, addressId)` `:238`
   2. `Order` 저장(`PENDING_PAYMENT`, totalAmount=SaleBid.bidPrice) `:241-247`, `paymentRequest.setOrderId(order.getId())` `:250`
   3. `OrderItem` 생성(수량 1, 가격=bidPrice) `:255-256`
   4. `OrderShipment` 생성(주소록의 수령인/전화/우편번호/주소) + `order.assignOrderShipment` `:264-271`
   5. `saleBid.assignOrder(order)` + `updateStatus(MATCHED)` + `entityManager.flush()` `:279-283`
   6. Sale이 창고보관(`sale.isWarehouseStorage()`)이면 `updateWarehouseStatus(sale, ASSOCIATED_WITH_ORDER)` `:291-294`
   7. `paymentCommandService.processPayment(order, buyer, paymentRequest)` `:305` (반환 Payment는 버림)
4. `PaymentCommandService#processPayment` → 결제 유형별 Payment 저장 → `notifyUsersAndUpdateSaleStatus` (알림 + Sale→SOLD). `D payment/service/command/PaymentCommandService.java:57-83`
5. `createInstantOrderBid(order, saleBid, sale)`로 `OrderBid`(MATCHED, `isInstantPurchase`, sale 연결) 저장. `OrderBidCommandService.java:189-207`

**동기/비동기**: 전부 **동기**, 한 요청 스레드의 단일 트랜잭션이다. 이 경로에는 Kafka(`OrderEventProducer`)·`@Async`가 없다. 결제(PortOne HTTP 호출 포함), 배송정보 생성, 알림이 모두 응답 전에 끝난다. (Kafka 비동기 경로는 별개 API `POST /orders/{id}/process-payment-shipment`이며 즉시 구매는 쓰지 않는다. `OrderCommandService#createInstantOrder`에 Kafka 호출 없음 `:219-319`)

**응답 ID**: `orderBidCommandService.createInstantOrderBid(...).getId()` — **OrderBid의 ID**이다. 변수명은 `orderId`이고 Javadoc도 "생성된 주문 ID"라고 하지만 실제로는 주문(Order) ID가 아니다. `OrderBidCommandController.java:101-107`, `:81-83`. 응답 메시지는 "즉시 구매가 성공적으로 처리되었습니다."(`:109`)

## 2. 새로 생기는 엔티티와 상태 변화 순서

**새로 생성**: `Order`, `OrderItem`, `OrderShipment`, `Payment`(CardPayment/AccountPayment/GeneralPayment 중 하나), `OrderBid`, 알림(`Notification`) 2건. (SaleBid/Sale은 기존 것을 재사용)

| 순서 | 시점 | 대상 | 상태 값 | 근거 |
|---|---|---|---|---|
| 0 | 요청 전 | SaleBid | `MATCHED` (판매 입찰은 생성 즉시 MATCHED) | `D sale/service/command/SaleBidCommandService.java:82`, `D sale/entity/SaleBid.java:53-56` |
| 0 | 요청 전 | Sale | `PENDING_SHIPMENT` | `D sale/service/command/SaleCommandService.java:62,108` |
| 1 | Order 저장 직후 | Order | `PENDING_PAYMENT` | `OrderCommandService.java:244` |
| 2 | 배송 생성 직후 | OrderShipment | `PENDING` | `D shipment/service/command/OrderShipmentCommandService.java:67` |
| 3 | `saleBid.assignOrder` 직후 | SaleBid | `MATCHED` (이미 MATCHED였고 `order` 연결만 추가됨. 사전 상태 검증 없음) | `OrderCommandService.java:279-280`, `SaleBid.java:58-61` |
| 4 | 창고 보관 Sale일 때 | WarehouseStorage(판매자측) | `ASSOCIATED_WITH_ORDER` | `OrderCommandService.java:293` |
| 5 | 결제 직후 | Payment | CARD 성공: `PAID`(isSuccess=true) / GENERAL: `PAID`(isSuccess=true) / ACCOUNT: 예외(아래 3번) | `PaymentCommandService.java:203-206`, `:313-314` |
| 6 | 결제 후 알림 | Sale | `SOLD` (검증 없이 `updateStatus`) | `PaymentCommandService.java:404`, `D sale/entity/Sale.java:73-75` |
| 7 | 마지막 | OrderBid | `MATCHED` (`isInstantPurchase=true`) | `OrderBidCommandService.java:196,205` |

- 6번에서 Sale을 찾는 방법: 이 시점 `order.getOrderBid()`는 아직 null(OrderBid는 5단계 이후에 저장)이므로 `saleBidQueryService.findByOrderId`로 SaleBid → Sale을 찾는다. `PaymentCommandService.java:388-404` (`D sale/service/query/SaleBidQueryService.java:26-29`)
- **Order 상태는 한 번도 바뀌지 않는다.** `createInstantOrder`에는 `order.updateStatus(...)`·`order.assignPayment(...)` 호출이 없다(`OrderCommandService.java:219-319`; `assignPayment` 호출처는 `OrderCommandService.java:140`(미사용 경로)·`D order/service/kafka/OrderEventConsumer.java:172`뿐).

## 3. 결제 수단별 결과

분기: `PaymentCommandService.java:67-80` (`getResolvedPaymentType`: `D payment/dto/PaymentRequestDto.java:74-87`). 사전 검증: orderId·이메일 일치, 금액>0 `PaymentCommandService.java:110-137`범위(`validatePaymentRequest`). 결제금액이 SaleBid 가격과 같은지는 검증하지 않는다.

| 수단 | 동작 | 결과 |
|---|---|---|
| **CARD** | 저장된 PaymentInfo 조회 → `PortOneApiClient#processCardPayment` 동기 호출 → CardPayment 저장. 응답 `status=="success"`일 때만 `PAID`+`isSuccess=true` | `PaymentCommandService.java:157-215`, `:179`, `:203-206` |
| **ACCOUNT(계좌이체)** | Payment는 기본 `PENDING`인데 `updateStatus(PENDING)`을 호출 → `PENDING.canTransitionTo(PENDING)`은 false(PENDING은 PAID로만 전이) → `IllegalStateException` → `PaymentProcessingException`으로 감싸짐 → **항상 실패** | `PaymentCommandService.java:260`, `D payment/entity/Payment.java:44,70-76`, `D payment/entity/PaymentStatus.java:12-13`, `PaymentCommandService.java:274-277` |
| **GENERAL** | `impUid`만 비어있지 않으면 PortOne 검증 없이 `PAID`+`isSuccess=true` (클라이언트 값 신뢰) | `PaymentCommandService.java:290-322` |

**즉시 구매가 끝까지 성공하는가**: 위 코드 기준으로 CARD(PortOne 성공)와 GENERAL만 끝까지 성공한다. ACCOUNT는 예외가 `OrderCommandService:306-309`에서 `OrderPaymentProcessingFailedException`으로 변환되고 `OrderBidCommandService:145-148`에서 그대로 재던져져(OrderException) 트랜잭션 전체가 롤백된다 → Order/OrderItem/OrderShipment/Payment/SaleBid 연결/Sale 변경이 모두 취소되고 OrderBid는 만들어지지 않는다. 계좌이체는 이 API로 구매를 완료할 수 없다.

**PortOne이 카드 결제를 실패로 응답하면** — 실패 표현 방식에 따라 다르다.
- (a) HTTP 비-200 또는 응답 body의 `code`가 0이 아님 → `PaymentProcessingException` 발생(`D payment/portone/PortOneApiClient.java:270-275`) → 위와 같이 전체 롤백, 구매자는 오류 응답. (통신 오류 `RestClientException`도 `PaymentApiException`으로 같은 결과 `:288-290`)
- (b) HTTP 200 + `code==0`이지만 `response.status`가 `success`가 아님(예: `failed`) → **예외가 나지 않는다.** CardPayment는 `PENDING`/`isSuccess=false`로 저장되고(`PaymentCommandService.java:203-206`은 success일 때만 PAID 처리) `processPayment`는 이를 실패로 확인하지 않고 곧바로 `notifyUsersAndUpdateSaleStatus`를 호출한다(`:83`). 호출자 `createInstantOrder`도 반환값을 무시한다(`OrderCommandService.java:305`). 결과적으로 결제가 안 됐는데도 구매자·판매자에게 "결제가 완료되었습니다" 알림이 가고 Sale이 `SOLD`가 되며 OrderBid가 MATCHED로 저장되고 200 성공 응답이 나간다. Order는 `PENDING_PAYMENT` 그대로다.

## 4. 알림

- 시점: `processPayment` 안에서 Payment 저장 직후, **동기**로, 같은 트랜잭션에서 2건. `PaymentCommandService.java:83` → `:383-421`, `sendNotifications` 호출 `:403,418`
- 수신자와 내용 (둘 다 `NotificationCategory.SHOPPING`, `NotificationType.BID`):
  - **구매자**(`order.getUser()`): "결제가 완료되었습니다. 주문 ID: {orderId}" `PaymentCommandService.java:437-443` 근처(`createNotification` 호출 `:438`)
  - **판매자**(`sale.getSeller()`): "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}" (`createNotification` 호출 `:449`)
- 전달 방식: `NotificationCommandService#createNotification`이 DB에 알림을 저장(`D notification/service/command/NotificationCommandService.java:52-53`)하고, Redis 키 `WebSocket:User:{email}`가 있을 때(= 접속 중)만 STOMP `/user/{email}/queue/notifications`로 푸시한다. 접속 중이 아니면 DB 저장만 되고 푸시는 생략된다. `NotificationCommandService.java:37-38,57,303-323`
- 이 경로에서 Kafka `notification-topic` 발행이나 `/topic/order/{id}` 브로드캐스트는 없다(그건 `OrderEventConsumer` 전용).
- 알림/Sale 상태 갱신 예외는 `catch`로 삼켜 로그만 남긴다. `PaymentCommandService.java:421-424`, `:457-460`. (참고: `NotificationCommandService`가 클래스 레벨 `@Transactional`이라 내부 예외 시 트랜잭션이 rollback-only로 표시될 수 있고, 그러면 커밋 시점에 `UnexpectedRollbackException`이 날 수 있다 — 코드 기반 추정이며 실행 검증은 하지 않았다.)
- 입찰 생성 알림 등 다른 알림은 이 흐름에서 보내지 않는다.

## 5. 최종 상태, 창고 보관 선택 시

**처리 후 최종 상태(성공 시, CARD success 또는 GENERAL 기준)**
- **Order: `PENDING_PAYMENT`** — `PAYMENT_COMPLETED`/`PREPARING`으로 가지 않는다. `OrderCommandService.java:244` 이후 상태 변경 호출 없음. 알림 문구("결제 완료")와 Payment=`PAID`는 실제 Order 상태와 다르다.
- Payment: `PAID`, Sale: `SOLD`, SaleBid: `MATCHED`(order 연결), OrderBid: `MATCHED`(instant), OrderShipment: `PENDING`.
- 이후 Order를 진행시키는 코드는 이 흐름 밖(구매자 송장 등록 `OrderShipmentCommandService#updateTrackingInfo` 등)이며, `PENDING_PAYMENT → IN_TRANSIT` 전이는 `OrderStatus` 규칙상 허용되지 않는다(`D order/entity/OrderStatus.java:24`: PENDING_PAYMENT는 PAYMENT_COMPLETED/COMPLETED/IN_WAREHOUSE만 가능).

**"창고 보관"(`warehouseStorage=true`)을 선택한 경우: 아무것도 달라지지 않는다.**
- 컨트롤러는 `requestDto.isWarehouseStorage()`를 서비스에 넘기지만(`OrderBidCommandController.java:105`), `OrderBidCommandService`는 이를 `createInstantOrder`에 그대로 전달하기만 하고(`OrderBidCommandService.java:133-139`), `createInstantOrder` 본문은 `isWarehouseStorage` 파라미터를 전혀 읽지 않는다(`OrderCommandService.java:220-319` — 사용처 없음). 따라서 구매자 창고 보관 엔티티(`createOrderStorage`)가 생성되지 않고, Order도 `IN_WAREHOUSE`/`COMPLETED`로 가지 않는다. 일반 배송 선택과 결과가 동일하다. 배송지(`OrderShipment`)도 창고 여부와 무관하게 항상 생성된다(`:264-271`).
- 창고 관련 분기는 **판매자 쪽** `sale.isWarehouseStorage()`(판매자가 창고 보관으로 올린 판매)뿐이며, 이때만 판매자 보관 건이 `ASSOCIATED_WITH_ORDER`로 바뀐다(`OrderCommandService.java:291-294`). 구매자의 선택과 무관하다.
- 참고로 구매자 창고 보관(`createOrderStorage` → Order IN_WAREHOUSE → COMPLETED)이 실제로 구현된 곳은 Kafka 경로 `OrderEventConsumer`와 미사용 `OrderCommandService#processPaymentAndShipment`(`OrderCommandService.java:163-172`)이며, 즉시 구매는 이를 타지 않는다.

## 요약(주석/이름과 실제 동작의 차이)
- 응답 `orderId`는 실제로 **OrderBid ID**.
- "즉시 구매가 성공적으로 처리"되어도 **Order는 PENDING_PAYMENT**.
- `warehouseStorage` 파라미터는 **무시**됨.
- ACCOUNT 결제는 **항상 실패**(롤백), 카드 결제가 PortOne에서 `code=0`·status≠success로 오면 **실패를 감지하지 못하고 성공 처리**.
