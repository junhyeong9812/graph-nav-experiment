# 즉시 구매(`POST /order-bids/instant`) 처리 분석

경로 약어: `D` = `src/main/java/com/fream/back/domain`. (prod nginx가 `/api`를 떼므로 매핑은 `/order-bids/instant`.)

## 1. 진입 API, 처리 단계, 동기/비동기, 응답 ID

**API**: `POST /order-bids/instant` — `D/order/controller/command/OrderBidCommandController.java:89` (`createInstantOrderBid`). 인증 필요(이메일은 SecurityContext에서 추출, `:92`).

**처리 단계 (전부 한 요청 스레드, 한 DB 트랜잭션)**
1. 컨트롤러가 이메일을 결제 요청에 주입하고 `orderId=null`로 초기화 — `OrderBidCommandController.java:98`, `:119-123`.
2. `OrderBidCommandService#createInstantOrderBid` (`@Transactional`, `D/order/service/command/OrderBidCommandService.java:118-119`): 입력 검증(`:123`, `:154-167`) → 구매자 조회(`:126`) → SaleBid/Sale 조회(`:129`, `:172-183`) → `OrderCommandService#createInstantOrder`(`:133`) → OrderBid 생성·저장(`:142`, `:189-207`).
3. `OrderCommandService#createInstantOrder` (`D/order/service/command/OrderCommandService.java:219-221`) 안에서 순서대로:
   1. 배송지 조회 `addressQueryService.getAddress` (`:238`)
   2. Order 생성·저장, PENDING_PAYMENT (`:241-247`), `paymentRequest.setOrderId` (`:250`)
   3. OrderItem 생성 (`:255-256`)
   4. OrderShipment 생성 (`:264-271`, 구현은 `D/shipment/service/command/OrderShipmentCommandService.java:56-75`)
   5. SaleBid에 Order 연결 + MATCHED, `flush` (`:279-283`)
   6. Sale이 창고 보관이면 창고 상태 ASSOCIATED_WITH_ORDER (`:291-294`)
   7. 결제 `paymentCommandService.processPayment` (`:305`)
4. `PaymentCommandService#processPayment` (`D/payment/service/command/PaymentCommandService.java:57`): 검증(`:117-146`) → 결제 유형별 처리(`:67-80`) → `notifyUsersAndUpdateSaleStatus`(`:83`)로 알림 + Sale→SOLD.
5. 서비스 복귀 후 OrderBid(MATCHED, 즉시구매 플래그) 저장 (`OrderBidCommandService.java:189-207`).

**동기/비동기**: **동기**다. Kafka를 쓰지 않는다. 일반 구매(`/orders/{id}/process-payment-shipment`)만 Kafka 비동기이고 즉시 구매 경로에는 Kafka 호출이 없다. PortOne 호출(`PortOneApiClient.java:266`)도 요청 스레드에서 블로킹으로 수행된다.

**응답 ID**: **OrderBid의 ID**다. `orderBidCommandService.createInstantOrderBid(...).getId()`가 반환값(`OrderBidCommandController.java:101-107`)이고, 서비스가 반환하는 것이 OrderBid(`OrderBidCommandService.java:142-144`)이다. 변수명은 `orderId`지만 Order ID가 아니다. 응답 메시지는 "즉시 구매가 성공적으로 처리되었습니다."(`:109`).

## 2. 새로 생기는 엔티티와 상태 변화 순서

| 순서 | 동작 | 엔티티 / 상태 | 근거 |
|---|---|---|---|
| 1 | Order 생성 | **Order** `status=PENDING_PAYMENT`, `totalAmount=saleBid.bidPrice` | `OrderCommandService.java:241-247` |
| 2 | OrderItem 생성 | **OrderItem** (수량 1, 가격=bidPrice) | `OrderCommandService.java:255-256` |
| 3 | 배송 생성 | **OrderShipment** `status=PENDING` (주소록 값 복사) | `OrderShipmentCommandService.java:61-70` |
| 4 | SaleBid 매칭 | 기존 **SaleBid**: `order=Order`, `status=MATCHED` (`assignOrder`가 MATCHED 설정 후 `updateStatus(MATCHED)` 재설정). SaleBid는 판매 입찰 생성 시 `Sale.assignSaleBid`→`SaleBid.assignSale`로 이미 MATCHED였으므로 값 변화는 없고 order 연결만 생긴다 | `OrderCommandService.java:279-283`, `D/sale/entity/SaleBid.java:53-61,66-68`, `D/sale/entity/Sale.java:59-62`, `D/sale/service/command/SaleBidCommandService.java:45,53` |
| 5 | 창고 | (판매자가 창고 보관 건일 때만) 기존 **WarehouseStorage** → `ASSOCIATED_WITH_ORDER` | `OrderCommandService.java:291-294`, `D/warehouseStorage/service/command/WarehouseStorageCommandService.java:117-140` |
| 6 | 결제 | **Payment**(Card/Account/General) 생성·저장. 유형별 상태는 3번 참조 | `PaymentCommandService.java:187-208, 250-262, 302-316` |
| 7 | 알림 + Sale | 알림 2건 저장, 기존 **Sale** `status=SOLD` (검증 없는 대입) | `PaymentCommandService.java:391-405, 434-455`; `D/sale/entity/Sale.java:73-75` |
| 8 | OrderBid 생성 | **OrderBid** `status=MATCHED`, `isInstantPurchase=true`, `sale`/`order` 연결 | `OrderBidCommandService.java:192-206`, `D/order/entity/OrderBid.java:60-82, 97-99` |

- 7번 시점에 `order.getOrderBid()`는 아직 null이다. OrderBid는 8번에 만들어지기 때문이다. 그래서 `saleBidQueryService.findByOrderId`로 SaleBid→Sale을 찾는 분기(`PaymentCommandService.java:388-407`)가 실제로 사용된다.
- `Order.assignPayment`는 호출되지 않는다(`createInstantOrder`에 호출 없음, `OrderCommandService.java:303-311`). Payment 쪽에서만 `assignOrder(order)`한다(`PaymentCommandService.java:200`).
- 주문 금액은 `saleBid.bidPrice`지만, 결제 금액 `paidAmount`는 클라이언트 값이며 0 초과인지만 검사한다(`PaymentCommandService.java:142-145`). bidPrice와 비교하지 않는다.
- SaleBid가 이미 매칭됐거나 Sale이 이미 SOLD인지 검사하는 코드는 없다(`OrderBidCommandService.java:172-183`은 null 검사만).

## 3. 결제 수단별 결과, 끝까지 성공하는가, 카드 실패 시

공통: 결제 분기는 `PaymentCommandService.java:67-80`, 요청 유형은 DTO 클래스로 결정(`D/payment/dto/PaymentRequestDto.java:74-87`).

| 수단 | 동작 | 결과 |
|---|---|---|
| **CARD** | 저장된 PaymentInfo 조회(`:166`) → PortOne `processCardPayment` 호출(`:179`) → 응답의 `status`가 문자열 `"success"`일 때만 `PAID` + `isSuccess=true`(`:203-206`) → 저장(`:208`) | 성공 시 PAID. 그 외 응답은 아래 "카드 실패" 참조 |
| **ACCOUNT** (계좌이체) | `AccountPayment` 생성 후 `updateStatus(PENDING)`(`:260`). `Payment.status` 기본값이 이미 PENDING(`D/payment/entity/Payment.java:44`)이고 `PENDING.canTransitionTo(PENDING)`은 false(`D/payment/entity/PaymentStatus.java:11-14`)이므로 `IllegalStateException`(`Payment.java:70-76`) → `:274`에서 `PaymentProcessingException`으로 래핑 | **항상 실패**. 즉시 구매 전체가 롤백된다(아래 참조) |
| **GENERAL** (일반) | `impUid`가 비어 있지 않은지만 검증(`:297-300`). PortOne 검증 호출 없이 클라이언트 값을 신뢰해 `isSuccess=true`, `PAID`(`:313-314`) | 항상 성공(금액·impUid 서버 검증 없음) |

**즉시 구매가 끝까지 성공하는 경우**: CARD(응답 status가 "success")와 GENERAL이다. ACCOUNT는 설계상 지원되는 것처럼 보이지만 실제로는 항상 예외로 실패한다. 주석이 말하는 "계좌이체 결제 대기(PENDING)"와 달리 PENDING→PENDING 전이가 막혀 있기 때문이다.

**실패 시 처리(공통)**: 예외는 `PaymentCommandService.java:89-100` → `OrderCommandService.java:306-308`(`OrderPaymentProcessingFailedException`) → `:312-314` 재전파 → `OrderBidCommandService.java:145-148, 212-218` 재전파 순으로 올라가고, 최상위 `@Transactional`(`OrderBidCommandService.java:118`)이 롤백한다. Order·OrderItem·OrderShipment·Payment·SaleBid 연결·창고 상태 변경이 모두 원복되고 OrderBid는 만들어지지 않는다. 알림 저장도 같은 트랜잭션이라 취소된다. Kafka 재시도 경로도 없다. 클라이언트는 에러 응답을 받는다.

**결제 대행사가 카드 결제를 실패로 응답하면**: 응답 형태에 따라 결과가 갈린다.
- **HTTP 비정상이거나 body의 `code != 0`**: `PortOneApiClient.java:270-275`에서 `PaymentProcessingException` 발생 → 위의 전체 롤백. `PaymentApiException`은 `@Retryable`로 최대 3회 재시도(`:224-228`). HTTP 4xx/5xx 등 `RestClientException`은 `PaymentApiException`으로 바뀌므로(`:288-290`) 재시도 대상이다.
- **`code == 0`인데 `response.status`가 `"success"`가 아닌 경우(예: failed)**: 예외가 없다. `CardPayment`는 `status=PENDING`, `isSuccess=false`로 저장된다(`PaymentCommandService.java:203-208`). 그런데 `processPayment`는 `isSuccess`를 검사하지 않고 곧바로 `notifyUsersAndUpdateSaleStatus`를 호출한다(`:83`). 즉시 구매 경로에서는 `isSuccess` 확인 코드가 없어서(`OrderCommandService.java:303-311`) **결제가 실패했어도 구매자·판매자 알림이 나가고 Sale이 SOLD가 되며 요청은 성공(OrderBid ID 반환)으로 끝난다**. 일반 구매 경로는 `OrderEventConsumer`가 `isSuccess`를 검사하지만 이 경로에는 그 검사가 없다.
- 참고: 성공 판정이 리터럴 `"success"`뿐이다(`PaymentCommandService.java:203`). 대행사가 성공을 다른 문자열로 내려주면 성공 응답도 같은 "PENDING, isSuccess=false, 그래도 진행" 경로를 탄다.

## 4. 누가 어떤 알림을 받나, 언제 어떻게 전달되나

- **누가/무엇을**: `PaymentCommandService#sendNotifications`(`:434-462`)
  - 구매자(`order.getUser()`): "결제가 완료되었습니다. 주문 ID: {orderId}" (`:438-443`)
  - 판매자(`sale.getSeller()`): "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}" (`:449-454`)
  - 둘 다 카테고리 `SHOPPING`, 타입 `BID`.
- **언제**: 결제 서비스 처리 직후, 같은 요청·같은 트랜잭션 안에서 동기로 발송된다(`PaymentCommandService.java:83`). Sale을 SOLD로 바꾸기 직전(`:403-404`). 결제 성공 여부와 무관하게(3번 참조) 호출된다. OrderBid 저장보다 먼저다.
- **방식**:
  1. DB에 `Notification` 저장 (`D/notification/service/command/NotificationCommandService.java:52-53`).
  2. 실시간: Redis 키 `WebSocket:User:{email}`가 존재할 때(= WebSocket 연결 중)만 STOMP `convertAndSendToUser(email, "/queue/notifications", dto)`로 푸시한다(`:303-313`, 상수 `:37-38`). 연결이 없으면 저장만 되고 푸시는 생략된다(`:320-322`).
  3. 알림 생성·전송 실패는 로그만 남기고 삼킨다(`PaymentCommandService.java:457-461`, `:421-425`).
- Kafka `notification-topic`은 쓰이지 않는다. 이 경로는 `OrderEventConsumer`를 거치지 않는다. 같은 이유로 `/topic/order/{id}` 푸시도 없다.
- 배송 단계 알림은 이 요청 범위 밖이다(`OrderShipmentCommandService`, 이후 송장 등록·배송 완료 시).

## 5. 최종 상태, 창고 보관 선택 시 차이

**처리 종료 시 주문 최종 상태**: Order는 **`PENDING_PAYMENT`로 남는다**. 즉시 구매 경로에는 `PAYMENT_COMPLETED`·`PREPARING` 등으로 바꾸는 코드가 없다.
- `createInstantOrder`는 PENDING_PAYMENT로 생성만 하고(`OrderCommandService.java:241-245`) 이후 `order.updateStatus`/`assignPayment`를 호출하지 않는다(`:247-311`).
- 상태를 `PAYMENT_COMPLETED`/`PREPARING`/`IN_WAREHOUSE`로 바꾸는 곳은 Kafka 컨슈머의 `processCompleteOrder`뿐이고(`D/order/service/kafka/OrderEventConsumer.java`), 즉시 구매는 이를 호출하지 않는다.
- 그 외 최종 상태 값은 다음과 같다. SaleBid=MATCHED(주문 연결), OrderBid=MATCHED(`OrderBidCommandService.java:196`), OrderShipment=PENDING(`OrderShipmentCommandService.java:67`), Sale=SOLD(`PaymentCommandService.java:404`), Payment=PAID(CARD "success"/GENERAL) 또는 CARD 비-success 응답이면 PENDING(`:203-208`).
- 이후 구매자가 송장을 등록하면(`updateTrackingInfo`) Order가 PENDING_PAYMENT에서 IN_TRANSIT으로 전이가 불허되어 실패할 소지가 있다. 이는 `nav/flow-trade.md:41`에 기술된 후속 이슈이며 이 질문 범위 밖이다.

**구매자가 "창고 보관"(`warehouseStorage=true`)을 선택한 경우**: **차이가 없다. 구매자의 선택은 사실상 무시된다.**
- 컨트롤러는 값을 로그와 서비스 인자로 전달하지만(`OrderBidCommandController.java:94-95, 105`), `createInstantOrder`의 파라미터 `isWarehouseStorage`(`OrderCommandService.java:221`)는 메서드 본문에서 한 번도 참조되지 않는다. 파일 내 `isWarehouseStorage` 참조는 `:163`(미사용 `processPaymentAndShipment`), 주석 `:210`, 시그니처 `:221`, `sale.isWarehouseStorage()` `:292`뿐이다.
- 구매자용 창고 보관 `WarehouseStorage`는 생성되지 않고(`createOrderStorage`는 `OrderEventConsumer` 경로에서만 호출), Order의 `IN_WAREHOUSE`·`COMPLETED` 전이도 일어나지 않는다.
- 창고 관련 분기는 **판매자(Sale)의 `isWarehouseStorage`** 만 본다(`OrderCommandService.java:291-294`; 필드 `D/sale/entity/Sale.java:43`). 이 경우 판매자가 맡긴 기존 `WarehouseStorage`가 `ASSOCIATED_WITH_ORDER`로 바뀐다(`WarehouseStorageCommandService.java:127-133`). `IN_STORAGE`에서는 어떤 전이도 허용된다(`:240-242`).
- 주의: 판매자 창고 보관 건의 `WarehouseStorage`는 판매자가 발송할 때 비로소 생성된다(`D/shipment/service/command/SellerShipmentCommandService.java:79`). 발송 전에 즉시 구매하면 `findBySale`이 `WarehouseStorageNotFoundException`을 던지고(`D/warehouseStorage/service/query/WarehouseStorageQueryService.java:30-33`), 이는 `OrderWarehouseStorageProcessingFailedException`으로 바뀌어(`OrderCommandService.java:295-300`) 즉시 구매 전체가 롤백된다.
