# 구매자 배송: 운송장 등록 → 배송 완료 (코드 기준 실제 동작)

경로 약칭: `S` = `src/main/java/com/fream/back/domain/shipment`, `O` = `src/main/java/com/fream/back/domain/order`, `G` = `src/main/java/com/fream/back/global`, `P` = `src/main/java/com/fream/back/domain/payment`.

## 요약

- 운송장 등록 API(`PATCH /shipments/order/{id}/status`)는 코드 의도상 shipment→IN_TRANSIT, order→IN_TRANSIT, 구매자/판매자 알림, 입찰 COMPLETED 순이다. 그러나 **결제·배송 처리를 마친 실배송 일반 구매 입찰 주문(Order=PREPARING)은 `order.updateStatus(IN_TRANSIT)`에서 예외가 나서 실패하고 전부 롤백**된다.
- 배송 완료 감지는 6시간마다 도는 Spring Batch 잡이며, 실제 실행되는 처리 코드는 `ShipmentItemProcessor` 클래스다 (JobConfig 안의 람다 빈, `OrderShipmentCommandService.updateShipmentStatuses()`는 실행되지 않는다).
- 배송 완료 판정 후 `completeOrder`는 (a) 실배송 일반 구매 입찰 주문(PREPARING)에서는 실패(스킵), (b) 즉시 구매 주문에서는 끝까지 성공하되 입찰(Bid) 상태는 바뀌지 않는다.

## 1. 운송장 등록 요청

### 1-1. 진입 API
1. `PATCH /shipments/order/{shipmentId}/status` — 컨트롤러 `OrderShipmentCommandController.updateTrackingInfo`. 근거: `S/controller/command/OrderShipmentCommandController.java:20` (`@RequestMapping("/shipments/order")`), `:33-45` (`@PatchMapping("/{shipmentId}/status")`, 서비스 `updateTrackingInfo` 호출), `:48` (`ResponseEntity.ok().build()`).
2. 이 컨트롤러 메서드는 try/catch가 없어 예외는 `GlobalExceptionHandler`로 간다 (`:33-48`).
3. (참고) 같은 컨트롤러의 `POST /{shipmentId}/check-status` 도 택배사/운송장을 넣는다(`:62-`, 서비스 `updateAndCheckShipmentStatus` `S/service/command/OrderShipmentCommandService.java:452`). 질문의 "운송장 등록"은 위 PATCH다.

### 1-2. 의도된 상태 변경 순서 (`OrderShipmentCommandService.updateTrackingInfo`, `S/service/command/OrderShipmentCommandService.java:238-303`)
1. courier/trackingNumber 공백 검증 → `TRACKING_INFO_REQUIRED` (`:243-246`).
2. `OrderShipment` 조회 (`:249-253`).
3. **OrderShipment** → `IN_TRANSIT` + courier/trackingNumber 세팅 (`:256`; 엔티티 `S/entity/OrderShipment.java:41-45`, 전이검증 없이 직접 `this.status = IN_TRANSIT`).
4. **Order** → `IN_TRANSIT` (`:259-260`, `Order.updateStatus` = `O/entity/Order.java:113-121`, 전이표 검증).
5. **구매자 알림** "상품이 출발하였습니다. 주문 ID: …" (`:265-271`).
6. `updateSaleStatusToSold(order.getId())` (`:276`, 본문 `:111-183`): SaleBid 경유 Sale → `SOLD` (`:116-123`), 창고보관이면 창고 상태 SOLD (`:126-129`), **판매자 알림** "상품이 성공적으로 판매 완료되었습니다…" (`:131-138`); OrderBid 경유 Sale → SOLD + 판매자 알림 (`:149-176`, 이미 SOLD면 `canTransitionTo`가 false라 건너뜀 — `G`가 아닌 `domain/sale/entity/SaleStatus.java:23`).
7. SaleBid의 Sale이 창고보관이면 창고 상태 SOLD 다시 호출 (`:278-286`).
8. `updateOrderAndSaleBidStatusToCompleted` → OrderBid/SaleBid가 `MATCHED`이면 `COMPLETED` (`:289`, 본문 `:412-440`).
9. 응답은 `200 OK` 빈 본문 (`OrderShipmentCommandController.java:48`).

알림 대상: 구매자 1건(출발), 판매자(Sale 소유자) 1건(SOLD 전환 시). 알림은 `NotificationCommandService.createNotification`으로 DB 저장 + 실시간 전송 (`domain/notification/service/command/NotificationCommandService.java:44-57`).

### 1-3. 실배송 일반 구매 입찰 주문(즉시 구매 아님)에서는 끝까지 성공하지 않는다
1. 주문 생성: `createOrderFromBid`가 Order를 `PENDING_PAYMENT`로 만든다 (`O/service/command/OrderCommandService.java:76-82`).
2. 결제·배송 처리 `processPaymentAndShipment`: 배송 정보를 만들 때 shipment 상태는 `PENDING` (`S/service/command/OrderShipmentCommandService.java:61-68`), 실배송(비창고)이면 Order를 `PAYMENT_COMPLETED` → `PREPARING`까지만 올린다 (`O/service/command/OrderCommandService.java:173-177`). 즉 결제·배송 처리를 마친 시점 Order 상태 = **PREPARING**.
3. `OrderStatus` 전이표에서 `PREPARING`의 다음 상태는 `IN_WAREHOUSE`, `SHIPMENT_STARTED` 뿐이다 (`O/entity/OrderStatus.java:26`). `IN_TRANSIT`은 `SHIPMENT_STARTED`에서만 갈 수 있다 (`:28`). `SHIPMENT_STARTED`로 올리는 코드는 어디에도 없다 (`OrderStatus.SHIPMENT_STARTED` 설정 호출 없음 — 전체 `updateStatus(OrderStatus.…)` 호출은 `OrderCommandService` 165-176, `OrderEventConsumer` 195-217, `OrderShipmentCommandService` 204/260/355 뿐).
4. 따라서 `S/service/command/OrderShipmentCommandService.java:260` `order.updateStatus(OrderStatus.IN_TRANSIT)` 에서 `InvalidOrderStatusException("상태 전환이 허용되지 않습니다: PREPARING -> IN_TRANSIT")` 발생 (`O/entity/Order.java:113-121`).
5. 이 예외는 `ShipmentException`이 아니므로 `catch (Exception e)`(`:295-302`)에 잡혀 `ShipmentException(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")`로 바뀌어 다시 던져진다.
6. **무엇이 저장되나:** 아무것도 저장되지 않는다. 메서드가 `@Transactional`(`:238`)이고 `ShipmentException`은 `RuntimeException`(`G/exception/GlobalException.java:10`)이라 전체 롤백된다. 3번에서 바꾼 shipment의 `IN_TRANSIT`/택배사/운송장도 롤백 → shipment는 `PENDING`, 운송장 없음, Order는 `PREPARING` 그대로. 구매자 알림은 `:260` 이후 코드(`:265`)라 만들어지지도 않는다.
7. **응답:** `GlobalExceptionHandler.handleGlobalException`이 `ErrorCode` 기준으로 응답한다 (`G/exception/GlobalExceptionHandler.java:49-62`). 코드 `SHIPMENT_NOT_FOUND`(`S001`, "배송 정보를 찾을 수 없습니다.", HTTP **404**) (`S/exception/ShipmentErrorCode.java:12`). 실제 원인 메시지(상태 전환 불가)는 응답 본문에 안 나가고 `errorCode.getMessage()`만 나간다.
8. 추가 문제(상태 전환이 맞았더라도): `SaleBidQueryService.findByOrderId`는 없으면 null이 아니라 `IllegalArgumentException`을 던진다 (`domain/sale/service/query/SaleBidQueryService.java:26-28`). 그래서 SaleBid가 없는 일반 구매 입찰 주문은 `:116`에서도 같은 `SHIPMENT_NOT_FOUND`로 실패한다 (호출부의 `if (saleBid != null)` 체크는 의미 없음).

## 2. 배송 완료 감지

### 2-1. 누가/언제/어떻게
1. 주체: 스케줄러 `ShipmentBatchScheduler.scheduleShipmentStatusJob` (`G/config/ShipmentBatchScheduler.java:34-44`)가 Spring Batch `updateShipmentStatusesJob`을 `JobLauncher`로 실행한다 (`:37-40`). 사용자 요청이 아니라 서버 내부 주기 실행.
2. **주기: `@Scheduled(cron = "0 0 */6 * * *")` = 6시간마다(매 0·6·12·18시 정각)** (`ShipmentBatchScheduler.java:34`). 스케줄링 활성화는 다른 클래스의 `@EnableScheduling`로 이미 켜져 있다 (예: `domain/weather/config/WeatherDataScheduler.java:16`). 잡 실패 예외는 `printStackTrace`만 한다 (`:41-43`).
3. 대상: Reader가 `status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND trackingNumber IS NOT NULL` 인 `OrderShipment`를 50건씩 페이징 조회 (`S/config/UpdateShipmentStatusesJobConfig.java:89-96`, chunk/page 50: `:34-35,57,92`). `PENDING` 상태 shipment는 대상이 아니다.
4. 택배사 조회: Playwright로 CJ대한통운 `https://trace.cjlogistics.com/next/tracking.html?wblNo=`+운송장 페이지를 열고 `tbody#statusDetail tr`의 마지막 행 5번째 `td` 텍스트를 상태 문자열로 쓴다 (`S/config/ShipmentItemProcessor.java:28-29,81-94,181`).

### 2-2. 실제로 실행되는 처리 코드
비슷한 구현이 4곳 있다.

| 후보 | 위치 | 실행 여부 |
|---|---|---|
| `ShipmentItemProcessor.process` | `S/config/ShipmentItemProcessor.java:57-157` | **실행됨**. Step이 `new ShipmentItemProcessor(...)`를 `.processor(...)`로 등록 (`S/config/UpdateShipmentStatusesJobConfig.java:69-73`) |
| `shipmentItemProcessor()` @Bean 람다 | `UpdateShipmentStatusesJobConfig.java:106-` | **미사용** — Step에 연결되지 않음(`:68-73`은 `new ShipmentItemProcessor`) |
| `parseCjLogisticsStatus` (Jsoup) | `UpdateShipmentStatusesJobConfig.java:186` | **미사용** — 호출처 없음 |
| `OrderShipmentCommandService.updateShipmentStatuses()` | `S/service/command/OrderShipmentCommandService.java:308-391` | **미사용** — 호출처 없음(정의만 존재; 스케줄러는 Batch Job만 호출) |

Step 구성: `chunk(50)`, `faultTolerant().skip(Exception.class).skipLimit(50)`, `BrowserManageStepListener`로 Step 시작/끝에 브라우저 open/close (`UpdateShipmentStatusesJobConfig.java:66-81`, `S/config/BrowserManageStepListener.java`). Writer는 `JpaItemWriter` (`:241-247`).

### 2-3. 택배사 상태 문자열 → 내부 상태 (`ShipmentItemProcessor.mapToShipmentStatus`, `S/config/ShipmentItemProcessor.java:220-226`)
- `"배송완료"` → `DELIVERED` (`:222`)
- `"배송출발"` → `OUT_FOR_DELIVERY` (`:223`)
- 그 외 모든 문자열 → `IN_TRANSIT` (`:224`) (정확히 일치(equals)만 인정; 공백/다른 표기면 IN_TRANSIT)
- 현재 상태와 같으면 변경 없이 반환 (`:101-105`). 처리 분기는 `:108-126`.
- 주의: OUT_FOR_DELIVERY 상태에서 그 외 문자열이 오면 `IN_TRANSIT`로 매핑되어 `ShipmentStatus.OUT_FOR_DELIVERY → IN_TRANSIT`이 허용되지 않으므로(`S/entity/ShipmentStatus.java:23-27`) `IllegalStateException`(`S/entity/OrderShipment.java:47-55`) → 해당 건 스킵.

## 3. 배송 완료 판정 이후 (`ShipmentItemProcessor.process`, `:108-117` → `completeOrder`)

순서:
1. **OrderShipment** → `DELIVERED` (`ShipmentItemProcessor.java:113`; `IN_TRANSIT/OUT_FOR_DELIVERY → DELIVERED`는 허용 `ShipmentStatus.java:19-20,26`). 영속화는 Writer가 한다.
2. `orderService.completeOrder(orderId)` 호출 (`:116`, 본문 `S/service/command/OrderShipmentCommandService.java:190-229`):
   1. `OrderBid`를 orderId로 조회, 없으면 `IllegalArgumentException` (`:196-197`).
   2. **Order** → `COMPLETED` (`:204`, 전이표 검증).
   3. `updateSaleStatusToSold(orderId)` (`:208`): Sale이 SOLD로 전이 가능할 때만 Sale→SOLD, 창고 SOLD, 판매자 알림 (`:116-141,151-172`).
   4. **구매자 알림** "[completeOrder] 주문이 완료 처리되었습니다. 주문 ID: …" (`:211-217`).
   5. 어떤 예외든 `catch (Exception)`에서 `ShipmentException(ORDER_NOT_FOUND_FOR_SHIPMENT)`로 다시 던짐 (`:221-228`).
3. `notificationService.notifyShipmentCompleted(order)` (`:117`): **구매자 알림** "[배송 완료] 상품이 배송 완료되었습니다. 주문 ID: …" (`NotificationCommandService.java:219-234`; 실패해도 로그만).

알림 건수: 정상 진행 시 구매자 **2건**(`[completeOrder] …` + `[배송 완료] …`), 판매자는 `updateSaleStatusToSold`에서 Sale이 아직 SOLD가 아닐 때만 최대 1건(이미 SOLD면 0건; 둘 다 같은 Sale이면 두 번째 경로는 `canTransitionTo`가 false라 중복 안 됨 — `SaleStatus.java:23`).

입찰 상태: 배치 경로(`completeOrder`)는 `updateOrderAndSaleBidStatusToCompleted`를 호출하지 않는다. 이 메서드는 `updateTrackingInfo`(`OrderShipmentCommandService.java:289`)에서만 불린다. 따라서 **OrderBid/SaleBid의 상태는 배송 완료 후에도 바뀌지 않고 `MATCHED` 그대로**다. (nav 문서의 "입찰 COMPLETED로 변경"은 배송 완료 경로에는 적용되지 않는다.) Sale은 SOLD(이미 SOLD였거나 3-2-3에서 전이), Order는 COMPLETED.

## 4. 주문 종류별 차이

### (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문 → 끝까지 진행되지 않음
1. 이 주문의 Order는 `PREPARING` (`O/service/command/OrderCommandService.java:175-176`); 운송장 등록(1-3)도 실패해 Order는 계속 PREPARING.
2. shipment가 `IN_TRANSIT`이 되는 길은 `check-status` API (`OrderShipmentCommandService.java:473`의 `updateTrackingInfo`는 Order를 건드리지 않고 shipment만 IN_TRANSIT으로 만듦) 정도이며, 그렇게 배치 대상이 된 건이 DELIVERED로 판정되면:
3. `completeOrder`의 `order.updateStatus(COMPLETED)` (`:204`)에서 `PREPARING → COMPLETED`는 전이표에 없어 (`O/entity/OrderStatus.java:26`) `InvalidOrderStatusException` → `ShipmentException(ORDER_NOT_FOUND_FOR_SHIPMENT)` (`:221-228`).
4. 이 예외가 Processor 밖으로 나가 (`ShipmentItemProcessor.java:133-145`) 그 건은 스킵 되고 `shipment.updateStatus(DELIVERED)`(`:113`)·Order·알림 모두 롤백. 결과: shipment `IN_TRANSIT` 유지, Order `PREPARING`, 알림 0건, OrderBid/SaleBid `MATCHED`. 6시간마다 같은 건이 반복해서 스킵된다.
5. 즉시 `check-status` API에서 완료 판정이 나도 동일하게 `completeOrder`가 실패하고 (`:489`), 트랜잭션 롤백 후 컨트롤러가 `ShipmentException`의 HTTP status(404)를 빈 본문으로 반환한다 (`OrderShipmentCommandController.java:80-86`).

### (b) 즉시 구매로 만들어진 주문 → 끝까지 진행됨
1. 즉시 구매 주문은 Order `PENDING_PAYMENT`로 생성되고 이후 `PAYMENT_COMPLETED/PREPARING` 처리가 없다 (`OrderCommandService.java:241-245`; `createInstantOrder`에 상태 변경 없음, `PaymentCommandService`에도 `OrderStatus` 변경 없음). OrderBid는 `MATCHED`, `order`/`sale` 연결, 즉시구매 플래그로 생성된다 (`O/service/command/OrderBidCommandService.java:189-207`). SaleBid는 `assignOrder`로 `MATCHED` + order 연결 (`OrderCommandService.java:279-280`).
2. 결제 시점에 Sale이 이미 `SOLD`가 된다: `processPayment`→`notifyUsersAndUpdateSaleStatus` (`P/service/command/PaymentCommandService.java:83,391-405`; 이때 Order의 OrderBid는 아직 없어 SaleBid 경로, `:384-405`).
3. 배송 완료 시 `PENDING_PAYMENT → COMPLETED`는 전이표에 존재 (`OrderStatus.java:24`) → `order.updateStatus(COMPLETED)` 성공 (`OrderShipmentCommandService.java:204`).
4. `updateSaleStatusToSold`: Sale이 이미 SOLD라 `canTransitionTo(SOLD)`=false (`SaleStatus.java:23`) → Sale 변경·창고 변경·판매자 알림 없음 (`:119,156`).
5. 구매자 알림 2건(`[completeOrder]`, `[배송 완료]`)이 생성된다 (`:211-217`, `ShipmentItemProcessor.java:117`).
6. 결과: shipment `DELIVERED`, Order `COMPLETED`, Sale `SOLD`(결제 시점에 이미), OrderBid/SaleBid `MATCHED`(변경 없음), 판매자 알림 0건, 구매자 알림 2건.
7. (참고) 이 (b) 주문의 shipment가 `IN_TRANSIT`이 되려면 `PATCH .../status`는 사용할 수 없다: Order가 `PENDING_PAYMENT`라 `IN_TRANSIT` 전이가 불가(`OrderStatus.java:24`) → 1-3과 같은 실패. `check-status`(`:473`)로 shipment를 IN_TRANSIT으로 만든 건만 배치에서 완료까지 간다.

## 5. 실패 처리 (주기 처리 중 한 건 실패)

1. Processor 안에서 모든 예외는 `ShipmentException`으로 감싸 다시 던진다 (`ShipmentItemProcessor.java:133-145`; 운송장 없음 `:61-64`, 브라우저 null `:73-75`, 파싱 실패 `:167-211`, 전이 불가 `IllegalStateException` 포함).
2. Step이 `faultTolerant().skip(Exception.class).skipLimit(50)`이므로 (`UpdateShipmentStatusesJobConfig.java:75-77`) 실패한 건만 **스킵**된다. 스킵 시 `shipmentSkipListener.onSkipInProcess`가 에러 로그만 남긴다 (`:252-`).
3. 스킵된 건은 변경이 반영되지 않는다: 청크 트랜잭션이 롤백되고(그 안에서 이미 바뀐 shipment DELIVERED·Order COMPLETED·알림 포함), Spring Batch fault-tolerant 동작상 청크가 건별로 재처리되며 스킵된 건만 제외되고 나머지 건은 정상 처리·커밋된다. 스킵된 shipment는 여전히 `IN_TRANSIT/OUT_FOR_DELIVERY`라 다음 6시간 주기에 다시 대상이 된다 (Reader 조건 `:95`).
4. 스킵이 50건을 초과하면 Step이 실패(스킵 한도 초과)하여 그 실행의 나머지는 처리되지 않고, 스케줄러는 예외를 `printStackTrace`만 하고 다음 주기를 기다린다 (`ShipmentBatchScheduler.java:41-43`).
5. (실행되지 않는 `updateShipmentStatuses()`는 건별 try/catch로 계속 진행하도록 짜여 있으나 `:383-387`, 호출처가 없어 실제 동작과 무관하다.)
