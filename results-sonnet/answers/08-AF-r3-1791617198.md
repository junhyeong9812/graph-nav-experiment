# 구매자 배송: 운송장 등록 ~ 배송 완료 처리 분석

경로 약어: `S` = `src/main/java/com/fream/back/domain/shipment`, `O` = `src/main/java/com/fream/back/domain/order`, `G` = `src/main/java/com/fream/back/global`.
(핵심 서비스: `S/service/command/OrderShipmentCommandService.java` = `OSCS`)

## 0. 선행 상태 (결제·배송 처리 직후)

- 실배송 일반 구매 입찰 주문: `processPaymentAndShipment`가 배송 정보를 `PENDING`으로 만들고(`OSCS:67`, `O/service/command/OrderCommandService.java:148`), 주문을 `PAYMENT_COMPLETED → PREPARING`으로 올린다 (`O/service/command/OrderCommandService.java:175-176`). Kafka 경로도 결과가 같다 (`O/service/kafka/OrderEventConsumer.java:195,216-217`). 즉 주문은 **PREPARING**에서 멈춘다.
- 이후 `OrderStatus.SHIPMENT_STARTED`로 보내는 코드는 어디에도 없다 (enum 정의 `O/entity/OrderStatus.java:13`, 전이표 `:26-28` 외 사용처 없음).
- 즉시 구매 주문(`createInstantOrder`): 주문 `PENDING_PAYMENT`로 생성(`O/service/command/OrderCommandService.java:244`), 배송 `PENDING` 생성(`:264`), 이후 주문 상태를 바꾸는 코드가 없다 → 주문은 **PENDING_PAYMENT** 그대로. 결제 시점에 이미 Sale을 `SOLD`로 바꾼다 (아래 4-b).

## 1. 운송장 등록 요청

### 1-1. 진입 API
- `PATCH /shipments/order/{shipmentId}/status`, body `OrderShipmentRequestDto`(courier, trackingNumber) → `OrderShipmentCommandController#updateTrackingInfo` (`S/controller/command/OrderShipmentCommandController.java:33-45`) → `OSCS#updateTrackingInfo` (`OSCS:238-303`).
- 부가로 `POST /shipments/order/{id}/check-status`, `/check-status-string` (`...Controller.java:58,103`)도 운송장을 등록하며 즉시 CJ 조회를 한다 (`OSCS#updateAndCheckShipmentStatus`, `OSCS:451-516`). 질문의 "운송장 등록"에 해당하는 것은 `/status` PATCH.

### 1-2. 코드가 의도한 상태 변경 순서와 알림 (`OSCS#updateTrackingInfo`)
1. courier/trackingNumber 공백 검사 → `TRACKING_INFO_REQUIRED` (`OSCS:243-246`).
2. `OrderShipment` 조회 후 `updateTrackingInfo` → 택배사·송장 저장하며 배송 상태를 곧바로 `IN_TRANSIT`으로 세팅 (전이 검사 없이 대입, `S/entity/OrderShipment.java:41-45`).
3. `Order.updateStatus(IN_TRANSIT)` (`OSCS:259-260`).
4. **구매자**에게 알림 1건 "상품이 출발하였습니다. 주문 ID: …" (`OSCS:265-271`).
5. `updateSaleStatusToSold(orderId)` (`OSCS:276`): SaleBid → Sale을 `SOLD`로, 창고 보관이면 창고 상태 SOLD, **판매자**에게 "상품이 성공적으로 판매 완료되었습니다" 알림 (`OSCS:116-141`); OrderBid 쪽 Sale도 같은 처리 + 판매자 알림 (`OSCS:150-176`).
6. SaleBid 재조회 후 창고 상태 SOLD 갱신 (`OSCS:279-286`).
7. `updateOrderAndSaleBidStatusToCompleted` : OrderBid·SaleBid가 `MATCHED`이면 `COMPLETED` (`OSCS:289`, `:412-440`).
   - 주의: 이 단계는 "배송 완료"가 아니라 **출발 시점**에 판매 SOLD / 입찰 COMPLETED까지 앞당겨 처리하도록 짜여 있다(의도와 이름 불일치).

### 1-3. 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문에서 끝까지 성공하나? → **실패한다**
- 실패 지점: `OSCS:260` `order.updateStatus(OrderStatus.IN_TRANSIT)`. 주문이 `PREPARING`이고 `PREPARING`에서 갈 수 있는 상태는 `{IN_WAREHOUSE, SHIPMENT_STARTED}`뿐이라 `IN_TRANSIT`은 불허 (`O/entity/OrderStatus.java:26`, 검사 `O/entity/Order.java:113-121`) → `InvalidOrderStatusException`.
  - IN_TRANSIT으로 갈 수 있는 유일한 출발 상태는 `SHIPMENT_STARTED`인데(`OrderStatus.java:28`) 이를 세팅하는 코드가 없다.
- 예외 전파: `catch (ShipmentException)`에 안 걸리고 `catch (Exception)`에서 `ShipmentException(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")`로 감싸 던진다 (`OSCS:295-301`).
- **저장되는 것: 없음.** 메서드가 `@Transactional`(`OSCS:238`)이고 예외가 밖으로 나가므로 롤백된다. 2단계에서 바꾼 택배사·송장번호·`IN_TRANSIT`도 반영되지 않아 배송은 `PENDING`, 송장 null, 주문은 `PREPARING` 그대로. 4·5단계 이전에 터지므로 구매자·판매자 알림도 0건.
- 응답: `ShipmentException`은 `GlobalExceptionHandler#handleShipmentException`이 처리 (`G/exception/GlobalExceptionHandler.java:459-472`). **HTTP 404**, body `ErrorResponse`(code `S001`, message "배송 정보를 찾을 수 없습니다." — 에러코드의 기본 메시지를 쓰며 상세 사유 문자열은 body에 안 실림, `S/exception/ShipmentErrorCode.java:12`). 즉 실제 원인은 "주문 상태 전이 불가"인데 클라이언트는 "배송 정보 없음" 404를 받는다.
- 즉시 구매 주문도 마찬가지: `PENDING_PAYMENT`의 허용 전이는 `{PAYMENT_COMPLETED, COMPLETED, IN_WAREHOUSE}`(`OrderStatus.java:24`)라 `IN_TRANSIT` 불가 → 동일하게 404.
- 참고: `check-status` 엔드포인트는 주문 상태를 건드리지 않고 배송만 갱신한다 (`OSCS:473`, `:483-498`). 그래서 이쪽으로만 배송이 `IN_TRANSIT`/`OUT_FOR_DELIVERY`로 영속화될 수 있고, 그런 배송이 아래 배치 대상이 된다. 단 이 경로에서도 CJ 상태가 "배송완료"이면 `completeOrder`에서 실패해 롤백되고(아래 3), 기타 상태는 `IN_TRANSIT→IN_TRANSIT` 전이 불허(`ShipmentStatus.java:19-20`)로 `IllegalStateException`→503 `S302`, "배송출발"만 `OUT_FOR_DELIVERY`로 저장된다 (`OSCS:491-493`, `:505-514`).

## 2. 배송 완료 감지

### 2-1. 누가·언제·어떻게
- 스프링 스케줄러 `ShipmentBatchScheduler#scheduleShipmentStatusJob`이 `@Scheduled(cron = "0 0 */6 * * *")` → **6시간마다 정각(00·06·12·18시)** 에 Spring Batch Job `updateShipmentStatusesJob`을 실행 (`G/config/ShipmentBatchScheduler.java:34-44`, 매 실행 timestamp 파라미터). 예외는 `printStackTrace`만 한다 (`:41-43`).
- 스케줄링 활성화는 다른 빈의 `@EnableScheduling`이 담당 (`domain/event/scheduler/EventStatusScheduler.java:22`), 배치 인프라는 `G/config/BatchInfraConfig.java:15`.

### 2-2. 조회 대상
- `JpaPagingItemReader`: `SELECT s FROM OrderShipment s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL`, pageSize 50 (`S/config/UpdateShipmentStatusesJobConfig.java:87-96`). chunk 50, skipLimit 50 (`:51-52`).

### 2-3. 실제 실행되는 처리 코드
- Step은 `new ShipmentItemProcessor(playwrightBrowserManager(), notificationService, orderService)`를 직접 생성해 쓴다 (`UpdateShipmentStatusesJobConfig.java:66-73`). 따라서 **실제 실행 = `S/config/ShipmentItemProcessor.java#process` (`:57-157`)**: Playwright 페이지(`PlaywrightBrowserManager#newPage`)로 CJ 추적 페이지 로드 → `tbody#statusDetail tr` 마지막 행 5번째 td 텍스트 파싱 (`:72-94`, `:167-191`) → 매핑 (`:220-226`).
- 실행되지 **않는** 유사 코드 (죽은 코드):
  - `UpdateShipmentStatusesJobConfig#shipmentItemProcessor` 빈 (`:104-177`)과 `parseCjLogisticsStatus`(Jsoup, `:186-220`) — step에 연결되지 않음 (step은 `:69`에서 `new`로 생성).
  - `OSCS#updateShipmentStatuses` (`OSCS:308-391`) — 호출처 없음(스케줄러는 Job만 호출).
  - `CjTrackingPlaywright#getCurrentTrackingStatus`는 위 빈/`check-status` 경로에서만 쓰임.

### 2-4. 택배사 상태 문자열 → 내부 상태
- `ShipmentItemProcessor#mapToShipmentStatus` (`ShipmentItemProcessor.java:220-226`): `"배송완료"→DELIVERED`, `"배송출발"→OUT_FOR_DELIVERY`, **그 외 모든 문자열 → IN_TRANSIT** (다른 클래스의 복제본도 동일: `OSCS:399-405`, `JobConfig:228-234`).
- 현재 상태와 같으면 변경 없이 반환 (`:101-105`). 그 외는 `ShipmentStatus#canTransitionTo` 검사를 통과해야 한다. 예) `OUT_FOR_DELIVERY→IN_TRANSIT`은 불허라 `IllegalStateException`→`ShipmentException`으로 감싸져 skip (`ShipmentStatus.java:26`, `OrderShipment.java:47-55`, `ShipmentItemProcessor.java:133-145`).

## 3. 배송 완료 판정 이후 (배치, `ShipmentItemProcessor:108-117`)

의도된 순서:
1. `OrderShipment.updateStatus(DELIVERED)` (`:113`; `IN_TRANSIT/OUT_FOR_DELIVERY→DELIVERED`는 허용, `ShipmentStatus.java:19-26`) — 메모리 상 변경.
2. `OSCS#completeOrder(orderId)` (`:116`, `OSCS:190-229`):
   1. OrderBid 조회(없으면 IllegalArgumentException, `:196-197`)
   2. `Order.updateStatus(COMPLETED)` (`:204`)
   3. `updateSaleStatusToSold` (`:208`) — Sale `SOLD`(+창고 SOLD), 판매자 알림 (`OSCS:112-183`)
   4. 구매자에게 "[completeOrder] 주문이 완료 처리되었습니다. 주문 ID: …" 알림 (`:211-217`)
3. `NotificationCommandService#notifyShipmentCompleted(order)` → 구매자에게 "[배송 완료] 상품이 배송 완료되었습니다. 주문 ID: …" (`ShipmentItemProcessor.java:117`, `domain/notification/service/command/NotificationCommandService.java:219-229`).
4. Writer `JpaItemWriter`가 배송을 저장 (`JobConfig:239-246`).

알림 건수(정상 완주 시): **구매자 2건**(completeOrder 1 + 배송완료 1) + **판매자 최대 1건**(Sale이 아직 SOLD 전이 가능한 경우에만, 같은 Sale이 SaleBid·OrderBid 양쪽에서 잡히면 첫 번째에서 SOLD가 되어 두 번째는 `canTransitionTo` 불가로 건너뜀, `OSCS:119,156`, `SaleStatus.java:15-23`).
- `check-status` 경로는 `completeOrder`만 호출하므로 구매자 알림은 1건 ("[completeOrder] …")뿐 (`OSCS:489`).

주문 입찰·판매 입찰 상태:
- `completeOrder`/배치는 OrderBid·SaleBid를 **건드리지 않는다**. `COMPLETED`로 바꾸는 `updateOrderAndSaleBidStatusToCompleted`는 `updateTrackingInfo`(`OSCS:289`)에서만 호출되고 그 경로는 1-3에서 항상 실패한다. 따라서 배송 완료 후에도 OrderBid/SaleBid는 `MATCHED`로 남는다 (`OSCS:422-432`는 MATCHED일 때만 COMPLETED로 바꾸고, 호출되지 않음).
- 즉 "입찰 COMPLETED" 처리는 의도상 출발 시점에 있지만 실제로는 어느 경로에서도 도달하지 못한다.

## 4. 주문 종류별 차이

배치/`check-status`에 도달하는 배송은 §1-3 마지막 단락의 경로(check-status로 `OUT_FOR_DELIVERY` 영속화)로만 생긴다. 그런 배송이 CJ에서 "배송완료"가 된다고 가정했을 때:

### (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문 → **끝까지 진행되지 않음**
- 주문은 `PREPARING`. `completeOrder`의 `order.updateStatus(COMPLETED)` (`OSCS:204`)가 `PREPARING`의 허용 전이 `{IN_WAREHOUSE, SHIPMENT_STARTED}`에 없어 `InvalidOrderStatusException` (`OrderStatus.java:26`, `Order.java:113-121`).
- `completeOrder`의 `catch (Exception)`이 `ShipmentException(ORDER_NOT_FOUND_FOR_SHIPMENT)`로 감싸 던짐 (`OSCS:221-228`). 판매 SOLD 처리·구매자 알림(`:208-217`)·`notifyShipmentCompleted` 모두 실행 안 됨 → 알림 0건.
- 설령 주문 전이가 통과해도, 일반 입찰에는 SaleBid가 없을 수 있고 `SaleBidQueryService#findByOrderId`는 null이 아니라 `IllegalArgumentException`을 던진다 (`domain/sale/service/query/SaleBidQueryService.java:26-29`). `OSCS:116-117`의 `!= null` 검사는 무의미하고 이 예외는 `OSCS:150-180`의 try 바깥이라 `completeOrder`가 다시 실패한다.
- 결과: 배송은 DELIVERED 변경이 롤백/skip되어 `OUT_FOR_DELIVERY`/`IN_TRANSIT` 그대로, 주문 `PREPARING`, 입찰·Sale 변화 없음. 다음 6시간 주기에 다시 같은 실패 반복.

### (b) 즉시 구매로 만들어진 주문 → **배치 처리는 끝까지 진행됨** (단, 운송장 등록 단계 자체는 1-3처럼 실패)
- 주문은 `PENDING_PAYMENT`이며 `PENDING_PAYMENT→COMPLETED`는 허용 (`OrderStatus.java:24`) → `order.updateStatus(COMPLETED)` 성공 (`OSCS:204`).
- OrderBid가 즉시구매용으로 생성되어 있어 `findByOrderId` 성공 (`O/service/command/OrderBidCommandService.java:189-206`, `OSCS:196-197`).
- Sale은 이미 결제 시점에 `SOLD`로 바뀌고 구매자·판매자 알림("결제가 완료되었습니다"/"구매자가 결제를 완료하였습니다")이 나갔다 (`domain/payment/service/command/PaymentCommandService.java:83`, `:386-407`, `:433-446`; 이 시점 `order.getOrderBid()`가 null이라 SaleBid 분기를 탐 — OrderBid는 결제 뒤에 생성됨 `OrderBidCommandService.java:133-142`). 그래서 `updateSaleStatusToSold`에서 `SOLD.canTransitionTo(SOLD)`가 false(`SaleStatus.java:23`) → 판매자 알림·창고 갱신 없음 (`OSCS:119,142-144,156,173-175`).
- 결과: 배송 `DELIVERED`, 주문 `COMPLETED`, 구매자 알림 2건(배치 경로; `check-status` 경로는 1건), 판매자 알림 0건. OrderBid·SaleBid는 `MATCHED` 유지(`COMPLETED`로 안 바뀜, §3).

### 차이 요약
| | (a) 일반 입찰, 실배송 | (b) 즉시 구매 |
|---|---|---|
| 배송 판정 시 주문 상태 | PREPARING | PENDING_PAYMENT |
| `completeOrder` | `PREPARING→COMPLETED` 불허로 실패 | 성공 |
| 배송/주문 최종 | 배송·주문 변경 없음(롤백/skip) | DELIVERED / COMPLETED |
| 알림 | 0건 | 구매자 2건, 판매자 0건 |

## 5. 실패 처리 (배치)

- Step은 `faultTolerant().skip(Exception.class).skipLimit(50)` (`UpdateShipmentStatusesJobConfig.java:75-78`), chunk 50 (`:67`).
- 한 건에서 처리 예외(조회 실패, 파싱 실패, 전이 불허, `completeOrder` 실패 등)가 나면 `ShipmentItemProcessor`가 `ShipmentException`으로 감싸 던지고 (`:133-145`) 그 건은 skip, `SkipListener`가 로그만 남긴다 (`JobConfig:251-287`). Spring Batch 방식상 해당 chunk 트랜잭션이 롤백되고 chunk 내 항목이 개별 트랜잭션으로 재처리되며 실패 건만 제외된다. **실패 건**: DB 상태 변경 없음(`IN_TRANSIT`/`OUT_FOR_DELIVERY` 유지, 알림·주문 변경 롤백)이라 다음 실행(6시간 뒤)에 다시 조회 대상. **나머지 건**: 정상 처리·커밋된다.
- skip이 50건을 넘으면 Step이 실패하고 남은 건은 처리되지 않는다 (`:77`). Job 실행 예외는 스케줄러에서 `printStackTrace`로만 처리 (`ShipmentBatchScheduler.java:41-43`).
- 부수 관찰: 알림 생성 시 실시간(WebSocket) 전송이 트랜잭션 안에서 즉시 나가므로 (`NotificationCommandService.java:57`) chunk 롤백·재처리 때 DB에는 없는 알림이 이미 푸시되었거나 중복 푸시될 수 있다. 또 reader가 status 조건 + 페이지 offset 방식이라 처리 중 DELIVERED로 바뀐 항목이 조건에서 빠지면 다음 페이지 일부가 건너뛰어질 수 있다 (`JobConfig:87-96`) — 코드 구조에서 추정한 것이며 실행으로 확인하지 않았다.
- (참고) 죽은 코드인 `OSCS#updateShipmentStatuses`는 건별 try/catch로 계속 진행하는 설계지만 호출되지 않는다 (`OSCS:322-388`).
