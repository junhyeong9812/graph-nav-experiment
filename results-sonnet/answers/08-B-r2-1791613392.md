# 구매자 배송: 운송장 등록 → 배송 완료

경로 약어: `S` = `src/main/java/com/fream/back`

- `OSCS` = `S/domain/shipment/service/command/OrderShipmentCommandService.java`
- `JOB`  = `S/domain/shipment/config/UpdateShipmentStatusesJobConfig.java`
- `PROC` = `S/domain/shipment/config/ShipmentItemProcessor.java`
- `OCS`  = `S/domain/order/service/command/OrderCommandService.java`

## 사전 정보: 결제·배송 처리 직후 상태

- 결제 후 주문에는 `OrderShipment`(PENDING)가 붙는다: `OCS:148-155`, `OSCS:61-70`(`status(PENDING)` 67행).
- 일반 입찰 주문은 `PENDING_PAYMENT`로 만들어진다: `OCS:76-82`.
- 실배송(`isWarehouseStorage=false`)이면 `PAYMENT_COMPLETED → PREPARING`에서 멈춘다: `OCS:173-177`. **주문 상태는 PREPARING**.
- 일반 입찰의 `OrderBid`는 생성 시 `assignOrder`로 이미 MATCHED다: `S/domain/order/service/command/OrderBidCommandService.java:100`, `S/domain/order/entity/OrderBid.java:74-76`.
- 결제 처리(`processPayment`)는 주문 상태를 바꾸지 않는다(`S/domain/payment/service/command/PaymentCommandService.java:57-85`에 Order 상태 변경 없음).
- 즉시 구매 주문은 `createInstantOrder`에서 `PENDING_PAYMENT`로 만들어진 뒤(`OCS:241-245`) 상태 변경이 없다. 결제 후에도 **PENDING_PAYMENT** 그대로다(`OCS:303-311`).

## 1. 운송장 등록 요청

### 1-1. API
- `PATCH /shipments/order/{shipmentId}/status`, body `{courier, trackingNumber}`: `S/domain/shipment/controller/command/OrderShipmentCommandController.java:20,33-45`.
- 컨트롤러는 `OrderShipmentCommandService.updateTrackingInfo(shipmentId, courier, trackingNumber)`를 호출하고 성공하면 `200 OK`(빈 body)를 반환한다: `OrderShipmentCommandController.java:41-47`.

### 1-2. 의도된 순서 (`OSCS:238-303`, `@Transactional`)
1. courier/trackingNumber가 비면 `TRACKING_INFO_REQUIRED`: `OSCS:243-246`.
2. `OrderShipment` 조회, 없으면 `SHIPMENT_NOT_FOUND`: `OSCS:249-253`.
3. **OrderShipment**: `updateTrackingInfo`로 택배사/송장 저장 + 상태를 `IN_TRANSIT`으로 직접 대입한다(전이 검증 없음): `OSCS:256`, `S/domain/shipment/entity/OrderShipment.java:41-45`.
4. **Order**: `order.updateStatus(IN_TRANSIT)`: `OSCS:259-260`. 전이 규칙은 `Order.java:113-121`.
5. **구매자 알림**: "상품이 출발하였습니다. 주문 ID: …": `OSCS:265-271`.
6. `updateSaleStatusToSold(orderId)`: SaleBid→Sale SOLD, 창고 상태, 판매자 알림 "상품이 성공적으로 판매 완료되었습니다": `OSCS:276`, `OSCS:111-183`.
7. 창고 보관 Sale이면 창고 상태를 SOLD로 갱신한다: `OSCS:279-286`.
8. `updateOrderAndSaleBidStatusToCompleted`: MATCHED인 OrderBid·SaleBid를 COMPLETED로 변경: `OSCS:289`, `OSCS:412-440`.

의도 요약: Shipment IN_TRANSIT → Order IN_TRANSIT → 구매자 알림 → Sale SOLD(+판매자 알림) → OrderBid/SaleBid COMPLETED. 이름은 "운송장 등록"이지만 판매 완료·입찰 완료까지 한꺼번에 처리하도록 짜여 있다.

### 1-3. 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문: 성공하지 못한다
- **실패 지점**: `OSCS:260` `order.updateStatus(OrderStatus.IN_TRANSIT)`.
  - 주문은 PREPARING 상태다(사전 정보 참조).
  - `PREPARING`에서 허용되는 다음 상태는 `{IN_WAREHOUSE, SHIPMENT_STARTED}`뿐이라 IN_TRANSIT은 불가: `S/domain/order/entity/OrderStatus.java:26`. `IN_TRANSIT`으로는 `SHIPMENT_STARTED`에서만 갈 수 있다(`OrderStatus.java:28`).
  - `Order.updateStatus`가 `InvalidOrderStatusException`을 던진다: `Order.java:113-120`.
- **예외 변환**: `catch (ShipmentException)`에 안 걸리고 `catch (Exception)`에 걸려 `ShipmentException(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")`로 감싸 던진다: `OSCS:293-302`.
- **저장되는 것: 없음.**
  - 예외는 `@Transactional`(`OSCS:238`) 경계를 RuntimeException(`GlobalException extends RuntimeException`, `S/global/exception/GlobalException.java:10`)으로 넘어가므로 전체 롤백된다.
  - 3단계에서 대입한 shipment 의 courier/trackingNumber/IN_TRANSIT 은 DB에 남지 않는다.
  - 구매자 알림(5단계)은 4단계 이전에 도달하지 못해 생성되지 않는다.
  - 결과적으로 shipment는 PENDING, order는 PREPARING 그대로다.
- **응답**: `ShipmentException` 핸들러가 `ErrorResponse(code="S001", message="배송 정보를 찾을 수 없습니다.", status=404, path)`를 반환한다. 본문 message는 에러코드 기본 메시지이고 custom message(원인)는 응답에 안 나간다: `S/global/exception/GlobalExceptionHandler.java:459-472`, `S/domain/shipment/exception/ShipmentErrorCode.java:12`.
  - 즉 "상태 전이 불가"가 **404 "배송 정보를 찾을 수 없습니다"**로 둔갑한다.
- 부차적으로 이 흐름이 성공했더라도 막혔을 지점이 있다. `saleBidQueryService.findByOrderId`는 SaleBid가 없으면 null이 아니라 `IllegalArgumentException`을 던진다(`S/domain/sale/service/query/SaleBidQueryService.java:26-29`). 일반 입찰 주문에는 SaleBid가 연결되지 않는다(`saleBid.assignOrder`는 즉시구매 `OCS:279`에서만 호출). 그래서 `OSCS:116`(`updateSaleStatusToSold`)과 `OSCS:279`에서도 예외가 난다. `OSCS:116`은 try 밖이다(try는 150행부터).
- 참고(즉시 구매): 동일 API는 PENDING_PAYMENT → IN_TRANSIT도 `OrderStatus.java:24`에서 허용하지 않아 마찬가지로 실패한다.

## 2. 배송 완료 감지

### 2-1. 누가·언제·어떻게
- 사람이 호출하는 API가 아니라 **Spring `@Scheduled` 스케줄러가 Spring Batch Job을 실행**해서 감지한다: `S/global/config/ShipmentBatchScheduler.java:34-41`.
- 스케줄링 활성화는 `@EnableScheduling`(다른 클래스에 선언, 앱 전역): `S/domain/event/scheduler/EventStatusScheduler.java:22`. 배치 인프라는 `S/global/config/BatchInfraConfig.java:15`.
- **주기**: `cron = "0 0 */6 * * *"`, 즉 매일 0·6·12·18시 정각(6시간마다): `ShipmentBatchScheduler.java:34`. 실행마다 timestamp 파라미터로 새 JobInstance를 만든다(`ShipmentBatchScheduler.java:37-40`).
- 스케줄러에서 예외가 나면 `printStackTrace`만 한다: `ShipmentBatchScheduler.java:41-43`.
- 상태 변화를 외부(CJ대한통운)에 조회하는 pull 방식이다. CJ 추적 페이지 `https://trace.cjlogistics.com/next/tracking.html?wblNo=<운송장>`를 Playwright로 열어 `tbody#statusDetail tr`의 **마지막 행 5번째 td**를 읽는다: `PROC:28-29,80-96,167-198`.

### 2-2. 대상 배송
- Reader 쿼리: `SELECT s FROM OrderShipment s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL`, pageSize 50: `JOB:91-96`.
- 청크 크기 50, 스킵 한도 50: `JOB:51-52`.

### 2-3. 실제로 실행되는 처리 코드
비슷한 코드가 세 곳에 있다.

| 후보 | 위치 | 실제 사용 여부 |
|---|---|---|
| **`ShipmentItemProcessor.process`** | `PROC:57-157` | **실제 실행됨.** Step이 `new ShipmentItemProcessor(...)`를 `.processor(...)`로 등록한다: `JOB:67-72` |
| `shipmentItemProcessor()` @Bean 람다 | `JOB:104-177` | Step에 연결되지 않아 사용 안 됨(`.processor`는 위 `new` 인스턴스, `JOB:69`) |
| `OrderShipmentCommandService.updateShipmentStatuses()` | `OSCS:308-391` | 호출하는 코드가 없다(grep으로 호출처 없음). 스케줄러·배치에서 안 쓰임 |

- `JOB:484-518`의 `parseCjLogisticsStatus`(Jsoup)도 호출되지 않는다.
- 실행 경로: `ShipmentBatchScheduler:40` → `updateShipmentStatusesJob`(`JOB:54-60`) → Step(`JOB:63-82`) → `ShipmentItemProcessor.process`. 브라우저는 Step 전후로 열고 닫는다(`BrowserManageStepListener.java:16-24`, 등록은 `JOB:80`).
- 이 경로는 `CjTrackingPlaywright`가 아니라 자체 `PlaywrightBrowserManager`로 조회한다: `PROC:24-26`.
- Writer는 `JpaItemWriter`로 변경된 `OrderShipment`를 저장한다: `JOB:74,239-245`.

### 2-4. 택배사 상태 문자열 → 내부 상태
`PROC:219-226`(`mapToShipmentStatus`, 완전 일치 `switch`):

| 택배사 문자열 | 내부 상태 |
|---|---|
| `"배송완료"` | `DELIVERED` |
| `"배송출발"` | `OUT_FOR_DELIVERY` |
| 그 외 모두(집화, 이동중 등) | `IN_TRANSIT` |

- 매핑 결과가 현재 상태와 같으면 변경 없이 반환한다: `PROC:101-106`.
- 분기: DELIVERED(`PROC:107-119`), OUT_FOR_DELIVERY(`PROC:119-122`), 그 외는 IN_TRANSIT(`PROC:123-126`).
- `ShipmentStatus` 전이 규칙은 `S/domain/shipment/entity/ShipmentStatus.java`. IN_TRANSIT/OUT_FOR_DELIVERY → DELIVERED는 허용된다(`:19-20, :26`). `OrderShipment.updateStatus`는 불허 전이에서 `IllegalStateException`을 던진다: `OrderShipment.java:47-55`.
  - 예: 현재 OUT_FOR_DELIVERY인데 택배사 문자열이 "배송완료/배송출발"이 아니면 매핑값 IN_TRANSIT이므로 `OUT_FOR_DELIVERY → IN_TRANSIT` 불허로 예외 → 해당 건 skip.

## 3. 배송 완료 판정 이후 (`PROC:107-119`)

### 3-1. 엔티티 상태 변경 순서
1. **OrderShipment**: `updateStatus(DELIVERED)`: `PROC:113`(Writer가 나중에 저장).
2. `orderService.completeOrder(orderId)` (`OSCS:190-229`, `@Transactional`): `PROC:116`
   1. OrderBid를 `findByOrderId`로 조회, 없으면 예외: `OSCS:196-197`.
   2. **Order**: `updateStatus(COMPLETED)`: `OSCS:204`.
   3. `updateSaleStatusToSold(orderId)`: `OSCS:208`
      - **SaleBid**를 `findByOrderId`로 조회(없으면 예외, `OSCS:116`).
      - **Sale**이 `canTransitionTo(SOLD)`이면 SOLD로 변경(`OSCS:119-123`), 창고 보관이면 창고 상태 SOLD(`OSCS:126-129`), 판매자 알림(`OSCS:131-138`).
      - **OrderBid.getSale()**로도 한 번 더 같은 확인·SOLD·판매자 알림을 한다(`OSCS:150-176`).
   4. 구매자 알림 "[completeOrder] 주문이 완료 처리되었습니다": `OSCS:210-217`.
3. `notificationService.notifyShipmentCompleted(order)`: 구매자에게 "[배송 완료] 상품이 배송 완료되었습니다": `PROC:117`, `S/domain/notification/service/command/NotificationCommandService.java:219-234`.

### 3-2. 알림 (정상 완료 시)
- 구매자 **2건**: "[completeOrder] 주문이 완료 처리되었습니다"(`OSCS:212-217`), "[배송 완료] …"(`NotificationCommandService.java:228-233`).
- 판매자: Sale이 아직 SOLD로 전이 가능한 상태일 때만 1건씩(`OSCS:131-138`, `OSCS:162-169`). 단 Sale이 첫 블록에서 SOLD가 되면 OrderBid 블록에서는 `SOLD → SOLD` 불가라 중복 알림은 안 간다(`SaleStatus.java:23`). 따라서 **판매자 최대 1건**.
- 합계: 구매자 2건 + 판매자 0~1건.

### 3-3. 주문 입찰·판매 입찰의 상태
- **변하지 않는다.** `completeOrder`는 `updateOrderAndSaleBidStatusToCompleted`를 호출하지 않는다(`OSCS:190-229`에 호출 없음). 이 함수는 운송장 등록 흐름(`OSCS:289`)에서만 호출된다.
- OrderBid와 SaleBid는 MATCHED로 남고 COMPLETED가 되지 않는다. 바뀌는 것은 Order(COMPLETED)와 Sale(SOLD, 조건부)뿐이다.
- 운송장 등록 단계의 COMPLETED 처리는 1-3의 이유로 실제로는 실행되지 않는다. 그래서 배송 완료 후에도 입찰은 MATCHED 상태다.

## 4. 주문 종류별 차이

두 경우 모두 운송장 등록(1)이 실패해 shipment가 PENDING에 머물므로, 2-2의 Reader 조건(IN_TRANSIT/OUT_FOR_DELIVERY)에 걸리지 않는다. 즉 현재 코드 경로만으로는 스케줄러가 이 주문들을 집어 들 일이 없다. 아래는 shipment가 어떤 경로로든 IN_TRANSIT 이고 택배사가 "배송완료"를 반환한다고 가정한 3의 처리 결과다.

### (a) 실배송 일반 구매 입찰 주문 (Order=PREPARING, SaleBid 없음): 끝까지 가지 못함
1. `orderShipment.updateStatus(DELIVERED)`는 메모리에서 수행된다: `PROC:113`.
2. `completeOrder`에서 `order.updateStatus(COMPLETED)`가 `PREPARING → COMPLETED` 불허(`OrderStatus.java:26`)로 `InvalidOrderStatusException`: `OSCS:204`.
3. `catch (Exception)`이 `ShipmentException(ORDER_NOT_FOUND_FOR_SHIPMENT)`로 감싸 던진다: `OSCS:221-227`.
4. 프로세서 catch에서 ShipmentException 그대로 재던짐: `PROC:133-146`. Step의 skip 대상이 된다(`JOB:76`).
5. 결과: shipment·order 변경 롤백, **알림 0건**, 입찰 상태 불변(MATCHED), 완료 판정 없음. 설령 2번을 통과해도 SaleBid 조회에서 `IllegalArgumentException`이 난다(`SaleBidQueryService.java:26-29`, `OSCS:116`).

### (b) 즉시 구매로 만들어진 주문 (Order=PENDING_PAYMENT, SaleBid·OrderBid 둘 다 연결): 끝까지 진행됨
1. Shipment DELIVERED: `PROC:113`.
2. `completeOrder`
   - OrderBid가 있다(`OrderBidCommandService.java:189-207`).
   - `PENDING_PAYMENT → COMPLETED`는 허용된다(`OrderStatus.java:24`).
   - SaleBid가 있다(`OCS:279`).
3. Sale은 이미 결제 시점에 SOLD가 되었다. 결제 시점엔 `order.getOrderBid()`가 null이어서 SaleBid 경로를 타고 `sale.updateStatus(SOLD)`를 실행한다: `PaymentCommandService.java:383-405`(호출은 `:83`).
   - 따라서 `OSCS:119`/`OSCS:156`의 `canTransitionTo(SOLD)`가 false(`SaleStatus.java:23`)이다. Sale 변경·판매자 알림이 모두 생략된다.
4. 알림: 구매자 2건(`[completeOrder]` + `[배송 완료]`), 판매자 0건.
5. 결과: Shipment=DELIVERED, Order=COMPLETED, OrderBid·SaleBid=MATCHED 유지.

### 차이 요약
| | (a) 일반 입찰 (PREPARING) | (b) 즉시 구매 (PENDING_PAYMENT) |
|---|---|---|
| Order → COMPLETED | 불허, 예외 | 허용 |
| SaleBid 조회 | 없음 → 예외 | 있음 |
| 완료 처리 | 실패, skip, 롤백 | 성공 |
| 구매자 알림 | 0건 | 2건 |
| 판매자 알림 | 0건 | 0건(Sale 이미 SOLD) |
| 입찰 상태 | MATCHED 유지 | MATCHED 유지 |

## 5. 실패 처리 (주기 처리 중 한 건 실패)
- Step이 `faultTolerant().skip(Exception.class).skipLimit(50)`이다: `JOB:75-77`. 프로세서에서 나온 모든 예외가 skip 대상이다.
- 프로세서는 운송장 없음(`PROC:61-64`), 브라우저 오류, 조회/파싱 실패(`PROC:167-218`), 상태 전이 불가, `completeOrder` 실패를 모두 `ShipmentException`으로 던진다: `PROC:133-146`.
- **실패한 건**: skip 되어 `SkipListener.onSkipInProcess`가 로그를 남긴다(`JOB:251-266`). 해당 청크 트랜잭션은 롤백되고, 그 건의 shipment 상태는 DB에서 바뀌지 않는다(IN_TRANSIT/OUT_FOR_DELIVERY 그대로). 재시도 큐 없이 **다음 6시간 주기에 Reader 조건으로 다시 조회**된다. `completeOrder` 의 알림·상태 변경도 같은 트랜잭션이므로 롤백된다.
- **나머지 건**: 청크(50건)가 롤백된 뒤 Spring Batch가 skip된 건을 제외하고 청크 내 항목을 다시 처리해 커밋하므로 정상 건은 계속 진행되어 저장된다. 이때 정상 건도 CJ 조회를 다시 수행한다.
- **한도 초과**: 스킵이 50건을 넘으면 `SkipLimitExceededException`으로 Step이 실패하고 남은 건은 처리되지 않는다. 스케줄러 쪽에서는 예외를 로그만 남기고 다음 주기를 기다린다(`ShipmentBatchScheduler.java:41-43`).
- 참고: `OrderShipmentCommandService.updateShipmentStatuses`(`OSCS:322-388`)는 건별 try/catch로 계속 진행하지만 호출되지 않으므로 실제 동작과 무관하다.
