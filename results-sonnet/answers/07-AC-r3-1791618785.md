# 즉시 구매 처리 흐름

경로 접두사: `D = src/main/java/com/fream/back/domain`

## 요약
- 즉시 구매는 `POST /order-bids/instant` 한 번의 **동기** 요청이며, 하나의 트랜잭션 안에서 주문 생성 → 판매입찰 매칭 → 결제 → 알림 → OrderBid 생성까지 끝낸다. Kafka를 쓰지 않는다.
- 응답 ID는 이름(`orderId`)과 달리 **OrderBid의 ID**다.
- 주문(Order) 상태는 끝까지 `PENDING_PAYMENT`로 남는다. 구매자의 `warehouseStorage` 플래그는 사실상 쓰이지 않는다.

## 1. 진입 API, 처리 단계, 동기/비동기, 응답 ID

1. 진입: `POST /order-bids/instant` (`@RequestMapping("/order-bids")` + `@PostMapping("/instant")`).
   - 근거: `D/order/controller/command/OrderBidCommandController.java:19`, `:89`
   - 본문은 `InstantOrderRequestDto` (saleBidId, addressId, warehouseStorage, paymentRequest). 근거: `D/order/dto/InstantOrderRequestDto.java:20-29`
2. 컨트롤러가 이메일을 추출하고, `paymentRequest`에 `userEmail`을 넣고 `orderId=null`로 보강한 뒤 서비스 호출.
   - 근거: `OrderBidCommandController.java:92`, `:97`, `:101-107`, `:118-122`
3. `OrderBidCommandService#createInstantOrderBid` (`@Transactional`) 단계:
   - 입력 검증 (`:123`, `:154-167`)
   - 구매자 조회 (`:126`)
   - SaleBid/Sale 조회 및 검증 (`:129-130`, `:172-184`)
   - `orderCommandService.createInstantOrder(...)` 호출 (`:133-139`)
   - OrderBid 생성·저장 (`:142`, `:189-207`)
   - 근거 파일: `D/order/service/command/OrderBidCommandService.java`
4. `OrderCommandService#createInstantOrder` 내부 단계 (`D/order/service/command/OrderCommandService.java`):
   1. 배송지 조회 `addressQueryService.getAddress(email, addressId)` (`:238`)
   2. Order 저장, 상태 `PENDING_PAYMENT`, 금액 = `saleBid.getBidPrice()` (`:241-247`)
   3. `paymentRequest.setOrderId(order.getId())` (`:250`)
   4. OrderItem 생성 (`:255-256`)
   5. OrderShipment 생성 (`:264-271`)
   6. SaleBid 매칭 (`:279-283`)
   7. 판매자 창고 상태 변경 (`:291-293`)
   8. 결제 처리 `paymentCommandService.processPayment` (`:305`)
5. **동기 처리**다.
   - 응답 `ResponseEntity.ok(...)` 이 서비스 호출 직후 반환된다 (`OrderBidCommandController.java:109`).
   - Kafka/@Async는 이 경로에 없다. Kafka 비동기 처리는 별도 API `POST /orders/{orderId}/process-payment-shipment`뿐이다 (`D/order/controller/command/OrderCommandController.java:47-76`, 202 Accepted). 즉시 구매는 이 API를 거치지 않는다.
6. **응답 ID = OrderBid의 ID**.
   - 서비스가 `OrderBid`를 반환하고 (`OrderBidCommandService.java:119`, `:144`), 컨트롤러가 `.getId()`를 `orderId` 변수에 담아 `ResponseDto.success(orderId, ...)`로 돌려준다 (`OrderBidCommandController.java:101-109`).
   - 변수명·Javadoc("생성된 주문 ID", `:83`)과 달리 Order ID가 아니다. Order ID와 값이 같다는 보장도 없다.

## 2. 새로 생기는 엔티티와 상태 변화 순서

한 트랜잭션 안의 순서다. 각 단계 직후 값:

| 순서 | 동작 | 직후 상태 | 근거 |
|---|---|---|---|
| 1 | **Order 생성** | `Order.status = PENDING_PAYMENT` | `OrderCommandService.java:241-247` |
| 2 | **OrderItem 생성**, Order에 추가 | (상태 필드 없음) | `:255-256` |
| 3 | **OrderShipment 생성** | `ShipmentStatus.PENDING` | `:264-271`, `D/shipment/service/command/OrderShipmentCommandService.java:61-68` |
| 4 | **기존 SaleBid** 매칭 (`assignOrder` + `updateStatus`) | `SaleBid.status = MATCHED`, `SaleBid.order = 새 Order` | `OrderCommandService.java:279-280`, `D/sale/entity/SaleBid.java:58-61` |
| 5 | 판매자가 창고 보관(`sale.isWarehouseStorage()`)이면 **기존 WarehouseStorage** 상태 변경 | `WarehouseStatus.ASSOCIATED_WITH_ORDER` | `OrderCommandService.java:291-293`, `D/warehouseStorage/service/command/WarehouseStorageCommandService.java:117-133` |
| 6 | **Payment 생성** (종류별 상세는 3번) | CARD: `PENDING`(성공 응답 문자열이 `"success"`일 때만 `PAID`) / ACCOUNT: `PENDING` / GENERAL: `PAID` | `D/payment/service/command/PaymentCommandService.java:203-206`, `:260`, `:313-314` |
| 7 | 결제 직후 **Sale 상태** → `SOLD` | `Sale.status = SOLD` | `PaymentCommandService.java:83`, `:404`, `:419` |
| 8 | **OrderBid 생성** (구매자, 입찰가=판매입찰가, sale 연결) | `OrderBid.status = MATCHED`, `isInstantPurchase = true` | `OrderBidCommandService.java:192-206`, `D/order/entity/OrderBid.java:60-82`, `:97-99` |

- 보충 (6→7): `notifyUsersAndUpdateSaleStatus`는 이 시점에 `order.getOrderBid()`가 아직 null이므로 `saleBidQueryService.findByOrderId`로 SaleBid → Sale을 찾아 처리한다 (`PaymentCommandService.java:388-406`). 4단계에서 `entityManager.flush()`로 order 연결을 반영해 둔 덕분에 조회된다 (`OrderCommandService.java:283`).
- 보충 (7): `Sale.updateStatus`는 전이 검증이 없다 (`D/sale/entity/Sale.java:73-75`).
- **Order 상태는 이후 바뀌지 않는다.** 즉시 구매 경로에서 `Order.updateStatus`를 호출하는 곳이 없다. `PAYMENT_COMPLETED/PREPARING/IN_WAREHOUSE/COMPLETED`로 바꾸는 코드는 `processPaymentAndShipment`(`OrderCommandService.java:165-176`)와 Kafka 소비자(`D/order/service/kafka/OrderEventConsumer.java:195-217`)에만 있고, 즉시 구매는 둘 다 거치지 않는다.

## 3. 결제 수단별 결과

분기: `requestDto.getResolvedPaymentType()`의 `CARD`/`ACCOUNT`/`GENERAL` (`PaymentCommandService.java:67-80`). 공통 검증은 `:117-146`이다 (orderId 일치, 이메일 일치, 금액 > 0).

| 수단 | 처리 | Payment 상태 | 근거 |
|---|---|---|---|
| CARD | 저장된 `PaymentInfo`로 PortOne 카드 결제 API 호출 후 `CardPayment` 저장 | 응답 `status`가 문자열 `"success"`이면 `PAID` + isSuccess=true, 아니면 기본값 `PENDING`, isSuccess=false | `PaymentCommandService.java:157-208`, `D/payment/entity/Payment.java:39`, `:44` |
| ACCOUNT | 은행명 검증 후 `AccountPayment`를 PG 호출 없이 저장 | 항상 `PENDING` (입금 확인 로직 없음) | `PaymentCommandService.java:236-262` |
| GENERAL | `impUid`만 확인하고 외부 검증 없이 저장 | 즉시 `PAID`, isSuccess=true | `PaymentCommandService.java:290-314` |

- **끝까지 성공하는가**: 예외가 없으면 수단과 무관하게 트랜잭션이 커밋되고 HTTP 200 "즉시 구매가 성공적으로 처리되었습니다."가 나간다 (`OrderBidCommandController.java:109`). 응답 성공이 결제 완료(`PAID`)를 뜻하지는 않는다.
  - ACCOUNT는 `PENDING`인 채로 SaleBid `MATCHED`, Sale `SOLD`, 완료 알림까지 진행된다.
  - Order는 모든 수단에서 `PENDING_PAYMENT`로 남는다 (2번 참고).
- **카드 결제를 PG사가 실패로 응답하면** 두 경우로 갈린다.
  1. **PortOne 응답의 `code`가 0이 아니거나 HTTP 200이 아님**: `PaymentProcessingException`이 발생한다 (`D/payment/portone/PortOneApiClient.java:270-275`).
     - `PaymentCommandService`는 이를 그대로 전파한다 (`:180-181`, `:218-219`, `:89-94`).
     - `OrderCommandService`가 `OrderPaymentProcessingFailedException`으로 감싸 던진다 (`:304-309`).
     - `OrderBidCommandService`가 OrderException을 그대로 다시 던진다 (`:212-214`).
     - 전체 `@Transactional`이 롤백된다 (Order, OrderItem, OrderShipment, SaleBid 매칭, Warehouse 상태 변경 모두 취소). 이때 응답은 오류다.
     - 통신 오류(RestClientException)도 `PaymentApiException`으로 같은 경로를 탄다 (`PortOneApiClient.java:288-290`).
     - 예외는 `GlobalException extends RuntimeException` 계열이라 롤백된다 (`src/main/java/com/fream/back/global/exception/GlobalException.java:10`, `D/order/exception/OrderException.java:10`).
  2. **HTTP 200 + `code == 0`이지만 `response.status`가 `"success"`가 아닌 경우** (예: `failed`): 예외가 없다.
     - `CardPayment`가 `PENDING`/isSuccess=false로 저장되고 (`PaymentCommandService.java:203-208`) 흐름이 계속된다.
     - Sale이 `SOLD`로 바뀌고, "결제가 완료되었습니다." 알림이 구매자·판매자에게 나가며, 응답은 200 성공이다 (`:83`, `:404`, `:438-454`).
     - PortOne이 실제로 쓰는 성공 값은 보통 `"paid"`인데 코드는 `"success"`만 `PAID`로 인정한다. 그래서 카드 결제는 PG가 성공을 돌려줘도 `PENDING`으로 저장될 가능성이 크다. 이 부분은 코드 비교 문자열에 근거한 추정이다.
- 참고: 카드 결제 실패 시 환불 로직 `handleRefundIfNecessary`는 정의만 있고 호출되지 않는다 (`PaymentCommandService.java:341`).

## 4. 알림 수신자, 시점, 방식

- 호출 위치: 결제 저장 직후 `notifyUsersAndUpdateSaleStatus` → `sendNotifications` (`PaymentCommandService.java:83`, `:403`, `:434-462`).
- **구매자**: `NotificationCategory.SHOPPING` / `NotificationType.BID`, 메시지 "결제가 완료되었습니다. 주문 ID: {orderId}" (`:438-443`).
- **판매자**(`sale.getSeller()`): 같은 SHOPPING / BID, 메시지 "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}" (`:447-453`).
- **시점**: 결제 처리 직후, 같은 요청·같은 트랜잭션 안에서 동기적으로 호출된다. 알림은 결제 수단과 무관하게 나간다. 카드가 `PENDING`이어도, 계좌이체가 입금 전이어도 "결제가 완료되었습니다."가 간다.
  - 알림 생성 중 예외는 `catch`로 삼켜져 결제·주문 흐름을 막지 않는다 (`:457-461`).
  - SaleBid/Sale을 못 찾는 경우에는 알림 자체가 생략된다 (`:392-401`).
- **방식**:
  1. DB에 `Notification` 저장 (`D/notification/service/command/NotificationCommandService.java:52-53`).
  2. 수신자가 접속 중이면(Redis 키 `WebSocket:User:{email}` 존재) WebSocket `/queue/notifications`로 사용자별 전송 (`:303-313`, `:37-38`).
  3. 접속 중이 아니면 저장만 하고 푸시하지 않는다 (`:320-322`).
  - Kafka의 `notification-topic`은 이 경로와 무관하다.

## 5. 최종 주문 상태와 창고 보관 선택 시 차이

- **최종 Order 상태 = `PENDING_PAYMENT`**.
  - 생성 시 설정되고 (`OrderCommandService.java:244`) 이후 즉시 구매 경로에서 변경되지 않는다 (2번의 보충 참고).
  - 결제가 `PAID`(GENERAL)여도 Order는 `PAYMENT_COMPLETED`가 되지 않는다.
  - 결제 `PAID`, SaleBid `MATCHED`, OrderBid `MATCHED`, Sale `SOLD`인데 Order만 `PENDING_PAYMENT`다. 상태가 서로 어긋난다.
- **구매자의 `warehouseStorage=true`를 선택해도 달라지는 것이 없다**.
  - `isWarehouseStorage` 인자는 `createInstantOrder` 시그니처에만 있고 본문에서 한 번도 참조되지 않는다 (`OrderCommandService.java:220-318`). 컨트롤러·서비스는 이 값을 로그와 인자 전달에만 쓴다 (`OrderBidCommandController.java:94-95`, `:105`, `OrderBidCommandService.java:137`).
  - 구매자용 `WarehouseStorage`를 만드는 `createOrderStorage`는 일반 결제·배송 처리 경로(`processPaymentAndShipment`, `OrderCommandService.java:163-172`)에만 호출된다. 이 API에서는 호출되지 않는다.
  - 따라서 `Order.status`가 `IN_WAREHOUSE`나 `COMPLETED`가 되지 않고, 구매자용 WarehouseStorage도 생기지 않는다.
- 창고와 관련해 실제로 일어나는 것은 **판매자 쪽 플래그**(`Sale.isWarehouseStorage`)뿐이다. 이 값이 true면 기존 WarehouseStorage가 `ASSOCIATED_WITH_ORDER`로 바뀐다 (`OrderCommandService.java:291-293`). 해당 Sale의 창고 정보가 없으면 `WarehouseStorageNotFoundException` → `OrderWarehouseStorageProcessingFailedException`으로 전체가 롤백된다 (`D/warehouseStorage/service/query/WarehouseStorageQueryService.java:30-33`, `OrderCommandService.java:295-300`).
