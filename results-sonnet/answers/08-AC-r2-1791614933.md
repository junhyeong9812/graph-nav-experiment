# 구매자 배송: 운송장 등록 → 배송 완료

경로 약어: `S` = `src/main/java/com/fream/back/domain/shipment`, `O` = `.../domain/order`, `P` = `.../domain/payment`, `SA` = `.../domain/sale`, `N` = `.../domain/notification`, `G` = `.../global` (모두 `src/main/java/com/fream/back/` 아래).

## 1. 운송장 등록 요청

### 1-1. 진입 API
- `PATCH /shipments/order/{shipmentId}/status`, 바디 `{courier, trackingNumber}` — `S/controller/command/OrderShipmentCommandController.java:20`(base path), `:33-45`.
- 컨트롤러는 `OrderShipmentCommandService#updateTrackingInfo`를 호출하고 성공 시 `200 OK` 빈 본문을 돌려준다 — `OrderShipmentCommandController.java:41-48`.
- 같은 서비스를 거치는 대체 진입점 `POST /shipments/order/{id}/check-status`, `/check-status-string`은 운송장 등록과 즉시 조회를 한 번에 한다(`:58`, `:103`). 이 경로는 2·4절에서 다시 다룬다.
- 결제 직후의 배송 엔티티는 `OrderShipment.status = PENDING`으로 만들어진다 — `S/service/command/OrderShipmentCommandService.java:61-68`.

### 1-2. 코드가 의도한 상태 변경 순서와 알림 (`OrderShipmentCommandService#updateTrackingInfo`, `:238-303`)
1. `courier`/`trackingNumber`가 비어 있으면 `TRACKING_INFO_REQUIRED` — `:243-246`.
2. `OrderShipment` 조회 후 `updateTrackingInfo(courier, trackingNumber)`. 택배사·운송장을 저장하고 상태를 곧바로 `IN_TRANSIT`으로 바꾼다(전이 검사 없음) — `:249-256`, `S/entity/OrderShipment.java:41-45`.
3. `Order.updateStatus(OrderStatus.IN_TRANSIT)` — `:259-260`. `Order.updateStatus`는 전이 규칙을 강제한다 — `O/entity/Order.java:113-121`.
4. **구매자**에게 알림 1건: "상품이 출발하였습니다. 주문 ID: …" — `:265-271`.
5. `updateSaleStatusToSold(orderId)` — `:276`. 내부 동작은 다음과 같다(`:111-183`).
   - `SaleBid`를 조회해 `Sale`을 `SOLD`로 바꾼다 — `:116-123`.
   - 창고 보관 건이면 창고 상태를 `SOLD`로 바꾼다 — `:126-129`.
   - **판매자**에게 알림 1건: "상품이 성공적으로 판매 완료되었습니다" — `:132-138`.
   - 이어서 `OrderBid.getSale()` 기준으로 같은 처리를 다시 한다 — `:150-176`.
6. `SaleBid.sale`이 창고 보관이면 창고 상태를 다시 `SOLD`로 바꾼다 — `:279-286`.
7. `updateOrderAndSaleBidStatusToCompleted(orderId)`로 `OrderBid`와 `SaleBid`가 `MATCHED`일 때 `COMPLETED`로 바꾼다 — `:289`, `:412-440`.

의도한 순서는 `OrderShipment`(IN_TRANSIT) → `Order`(IN_TRANSIT) → 구매자 알림 → `Sale`(SOLD) → 창고 → 판매자 알림 → `OrderBid`/`SaleBid`(COMPLETED)다.
메서드 이름·주석은 "출발"인데 판매 완료(SOLD)와 입찰 COMPLETED까지 운송장 등록 시점에 처리한다. 실제 동작도 그렇다(배송 완료 전에 판매·입찰이 완료된다).

### 1-3. 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문은 끝까지 성공하는가 → **실패한다**
- 이 주문의 상태는 `PREPARING`이다. 실배송이면 `PAYMENT_COMPLETED → PREPARING`까지만 간다 — `O/service/command/OrderCommandService.java:174-177`. Kafka 경로도 `PREPARING`에서 멈춘다 — `O/service/kafka/OrderEventConsumer.java:215-218`.
- `PREPARING`에서 허용되는 다음 상태는 `IN_WAREHOUSE`, `SHIPMENT_STARTED`뿐이다 — `O/entity/OrderStatus.java:26`. `IN_TRANSIT`은 `SHIPMENT_STARTED`에서만 갈 수 있다(`:28`).
- `SHIPMENT_STARTED`로 보내는 코드는 어디에도 없다(`OrderStatus` 정의와 조회 컨트롤러의 라벨 외에 사용처 없음). 그래서 `:260`의 `order.updateStatus(IN_TRANSIT)`이 `InvalidOrderStatusException`("상태 전환이 허용되지 않습니다: PREPARING -> IN_TRANSIT")을 던진다 — `O/entity/Order.java:113-121`.
- 이 예외는 `ShipmentException`이 아니므로 `catch (Exception e)`에서 잡혀 `ShipmentException(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")`로 감싸져 다시 던져진다 — `OrderShipmentCommandService.java:295-302`.
- 설령 이 단계를 통과해도 다음 줄에서 또 실패한다. 일반 입찰 주문에는 `SaleBid`가 연결되어 있지 않다. `SaleBid.order`는 즉시 구매(`OrderCommandService.java:279`)나 즉시 판매(`SA/service/command/SaleBidCommandService.java:83`)에서만 세팅된다. `SaleBidQueryService#findByOrderId`는 없으면 `null`이 아니라 `IllegalArgumentException`을 던진다 — `SA/service/query/SaleBidQueryService.java:27-30`. 호출 위치는 `OrderShipmentCommandService.java:116`이다.
- **무엇이 저장되나:** 아무것도 저장되지 않는다. `@Transactional` 메서드에서 `RuntimeException`이 밖으로 나가므로 롤백된다(`:238`).
  - 3단계 전에 메모리에서 바꾼 `courier`/`trackingNumber`/`IN_TRANSIT`도 DB에 반영되지 않는다. 배송은 `PENDING`, 택배사·운송장은 `null`로 남는다.
  - 알림도 만들어지지 않는다(알림 생성은 `:260` 이후다).
- **응답:** `GlobalExceptionHandler`가 `ShipmentException`을 처리한다 — `G/exception/GlobalExceptionHandler.java:459-473`. 에러 코드 `S001`, HTTP **404**, 메시지는 "배송 정보를 찾을 수 없습니다." 고정 문구다 — `S/exception/ShipmentErrorCode.java:12`. 원인은 상태 전이 오류인데 응답은 "배송 정보 없음 404"로 나와 오해를 부른다.

## 2. 배송 완료 감지

### 2-1. 누가·언제·어떻게
- **주체:** 스프링 스케줄러 `ShipmentBatchScheduler#scheduleShipmentStatusJob`이 Spring Batch 잡 `updateShipmentStatusesJob`을 실행한다 — `G/config/ShipmentBatchScheduler.java:34-41`. `@EnableScheduling`은 다른 설정 클래스에 선언되어 있어 같은 컨텍스트에서 동작한다(`domain/event/scheduler/EventStatusScheduler.java:22`).
- **주기:** `cron = "0 0 */6 * * *"`, 즉 매일 0·6·12·18시 정각(6시간마다) — `ShipmentBatchScheduler.java:34`. 매 실행마다 `timestamp` 파라미터를 달리해 새 JobInstance로 실행한다(`:37-40`).
- **대상:** `status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND trackingNumber IS NOT NULL`인 `OrderShipment`를 페이지 50건씩 읽는다 — `S/config/UpdateShipmentStatusesJobConfig.java:93-96`.
- **조회:** 각 건에 대해 CJ대한통운 추적 페이지(`trace.cjlogistics.com/next/tracking.html?wblNo=`)를 Playwright로 열고 `tbody#statusDetail tr`의 마지막 행 5번째 `td`를 상태 문자열로 읽는다 — `S/config/ShipmentItemProcessor.java:69-90`, `:167-191`.

### 2-2. 실제로 실행되는 처리 코드

## 3. 배송 완료 판정 이후 (`ShipmentItemProcessor#process`, `:108-118`)

### 3-1. 엔티티 상태 변경 순서
1. `OrderShipment.updateStatus(DELIVERED)` — `:113`. `IN_TRANSIT`/`OUT_FOR_DELIVERY` → `DELIVERED`는 허용된다 — `S/entity/ShipmentStatus.java:16-28`.
2. `OrderShipmentCommandService#completeOrder(orderId)` — `:116`.
   - `OrderBid`를 `findByOrderId`로 조회하고 없으면 예외 — `OrderShipmentCommandService.java:196-197`.
   - `Order.updateStatus(COMPLETED)` — `:204`.
   - `updateSaleStatusToSold` — `:208`. `Sale.status`가 `canTransitionTo(SOLD)`일 때만 `SOLD`로 바꾸고, 창고 보관 건이면 창고 상태를 갱신한다 — `:112-183`.
   - 구매자 알림 — `:211-217`.
3. `Sale` 변경은 `Sale.updateStatus`가 검증 없이 대입한다(`SA/entity/Sale.java:73-75`). `completeOrder`는 `OrderBid`/`SaleBid`의 `COMPLETED` 변경(`updateOrderAndSaleBidStatusToCompleted`)을 호출하지 **않는다**. 이 메서드는 운송장 등록 경로(`:289`)에서만 호출된다.
4. `JpaItemWriter`가 `OrderShipment`를 저장한다(청크 커밋).

### 3-2. 알림 (정상 진행 시)
- **구매자:** 2건.
  - "[completeOrder] 주문이 완료 처리되었습니다. 주문 ID: …" — `OrderShipmentCommandService.java:211-217`.
  - "[배송 완료] 상품이 배송 완료되었습니다. 주문 ID: …" — `N/service/command/NotificationCommandService.java:224-229`. `ShipmentItemProcessor.java:117`에서 호출한다.
- **판매자:** `Sale`이 아직 `SOLD`가 아니고 전이 가능할 때만 "판매 완료" 알림이 최대 1건(`SaleBid` 경로) 가거나 `OrderBid` 경로로 추가로 갈 수 있다(`:132-138`, `:163-169`). 두 경로가 같은 `Sale`을 가리키면 첫 경로에서 이미 `SOLD`가 되어 두 번째는 건너뛴다. 최대 1건이다. 이미 `SOLD`이면 0건이다.

### 3-3. 입찰 상태
- 배치 경로(`completeOrder`)는 `OrderBid`와 `SaleBid`를 **건드리지 않는다.** 두 입찰은 `MATCHED`로 남는다. `COMPLETED`로 바꾸는 코드는 `updateOrderAndSaleBidStatusToCompleted`뿐이고(`:412-440`), 이는 운송장 등록 경로에서만 호출되는데 1-3절대로 일반 주문에서는 실패한다. 즉시 구매 주문에서도 같은 이유로 등록 경로가 실패하므로(4절 참고) 실질적으로 이 메서드는 도달하지 못한다.
- 또한 이 메서드는 `private` 메서드에 `@Transactional`이 붙어 있어 프록시가 무시한다(`:412-413`). 내부에서 모든 예외를 삼키므로 실패해도 로그만 남는다(`:436-439`).

## 4. 주문 종류별 차이

배송 완료 처리 자체에 이르는 경로를 먼저 짚는다. 운송장 등록 API(`PATCH …/status`)는 위에서 본 대로 두 주문 모두 `Order.updateStatus(IN_TRANSIT)` 단계에서 실패한다.
- (a)는 `PREPARING → IN_TRANSIT`이 불가하다 — `OrderStatus.java:26`.
- (b)는 `PENDING_PAYMENT → IN_TRANSIT`이 불가하다 — `OrderStatus.java:24`. `createInstantOrder`는 주문 상태를 `PENDING_PAYMENT`에서 바꾸지 않는다(`OrderCommandService.java:241-311`).

따라서 배송이 `IN_TRANSIT`이 되어 배치 대상이 되는 현실적인 경로는 `check-status` 계열 API(`updateAndCheckShipmentStatus`, `OrderShipmentCommandService.java:451-516`)다. 이 경로는 `shipment.updateTrackingInfo`만 호출하고 `Order` 상태는 건드리지 않는다(`:473`). 아래는 배송이 `IN_TRANSIT`이고 택배사가 "배송완료"를 반환한 상태를 가정한 비교다.

### (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문 — **끝까지 진행되지 않는다**
- `completeOrder`의 `order.updateStatus(COMPLETED)`(`:204`)는 현재 `PREPARING`에서 `COMPLETED`로 갈 수 없어 `InvalidOrderStatusException`이 난다 — `OrderStatus.java:26`.
- `completeOrder`의 catch가 이를 `ShipmentException(ORDER_NOT_FOUND_FOR_SHIPMENT)`로 감싸 던진다 — `OrderShipmentCommandService.java:221-228`.
- 배치에서는 처리기의 catch가 그대로 다시 던지고(`ShipmentItemProcessor.java:133-146`) skip 대상이 된다. 같은 트랜잭션에서 `completeOrder`가 롤백 표시를 하므로, `OrderShipment`의 `DELIVERED` 변경(`:113`)도 저장되지 않는다. 배송은 `IN_TRANSIT`에 머물고, 주문은 `PREPARING`, 입찰은 `MATCHED`이며 알림은 0건이다. 이후 6시간마다 같은 건을 다시 조회하고 같은 이유로 실패한다.
- `check-status` 경로에서도 `completeOrder`가 같은 예외를 내므로(`:489`) 컨트롤러가 404를 반환한다. 이때 같은 트랜잭션이 롤백되어 앞서 세팅한 택배사·운송장도 저장되지 않는다(`OrderShipmentCommandController.java:80-86`).

### (b) 즉시 구매로 만들어진 주문 — **끝까지 진행되지만 판매측 처리는 이미 끝나 있다**
- 주문은 `PENDING_PAYMENT`다. `PENDING_PAYMENT → COMPLETED`가 허용 목록에 있으므로 `order.updateStatus(COMPLETED)`가 성공한다 — `OrderStatus.java:24`. 중간 상태를 건너뛴 채 완료된다.
- 즉시 구매에서는 결제 시점에 이미 `Sale`이 `SOLD`로 바뀌고 알림도 나갔다. `createInstantOrder`에서 `saleBid.assignOrder(order)`를 한 뒤(`OrderCommandService.java:279`) 결제를 처리하고(`:305`), 결제가 `notifyUsersAndUpdateSaleStatus`를 호출한다(`P/service/command/PaymentCommandService.java:83`). 이때 `OrderBid`는 아직 없어 `SaleBid` 경로로 `sendNotifications`(구매자 "결제 완료", 판매자 "결제 완료") 후 `Sale`을 `SOLD`로 바꾼다 — `:391-405`, `:425-449`.
- 따라서 `updateSaleStatusToSold`에서 `SOLD → SOLD`는 `canTransitionTo`가 false라(`SA/entity/SaleStatus.java:23`) 건너뛴다. 판매자 "판매 완료" 알림과 창고 갱신은 일어나지 않는다 — `OrderShipmentCommandService.java:119`, `:156`.
- 결과: `OrderShipment` DELIVERED, `Order` COMPLETED, 구매자 알림 2건, 판매자 알림 0건, `OrderBid`/`SaleBid`는 `MATCHED`로 남는다(배치 경로는 `COMPLETED`로 바꾸지 않는다).
- 단, 배송 대기 상태의 배송이 `IN_TRANSIT`이 되는 경로가 `check-status`뿐이라는 전제가 붙는다.

| (b) 즉시 구매(PENDING_PAYMENT) | 성공 | `COMPLETED` | 2 | 0 (결제 시 이미 처리) | `MATCHED` |

## 5. 실패 처리 (주기 배치)
- 한 건이 예외를 던지면 `faultTolerant().skip(Exception.class).skipLimit(50)` 때문에 그 건만 skip된다 — `UpdateShipmentStatusesJobConfig.java:75-78`. `SkipListener#onSkipInProcess`가 로그만 남긴다(`:251-`, 로그 `ERROR`). 별도의 상태 표시나 재시도·알림은 없다.
- 처리기 안에서 모든 예외를 `ShipmentException`(`EXTERNAL_TRACKING_SERVICE_ERROR` 등)으로 바꿔 던진다 — `ShipmentItemProcessor.java:133-146`. 운송장 번호가 비어 있는 경우도 마찬가지다(`:61-64`).
- 청크(50건) 단위 트랜잭션이므로, 처리기 예외가 나면 청크가 롤백된 뒤 항목별로 재처리해 실패 항목만 건너뛰고 나머지는 정상 처리·저장된다(Spring Batch fault-tolerant step의 기본 scan 동작). 실패한 건은 DB에 변경이 반영되지 않고 상태가 그대로라 다음 6시간 주기에 다시 대상이 된다.
- skip이 50건을 넘으면 스텝이 실패한다(`SKIP_LIMIT=50`, `UpdateShipmentStatusesJobConfig.java:52`). 스케줄러는 예외를 `printStackTrace`로만 처리한다 — `ShipmentBatchScheduler.java:41-43`.
