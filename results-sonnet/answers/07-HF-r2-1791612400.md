# 즉시 구매 처리 흐름

경로 접두어 `B` = `src/main/java/com/fream/back/domain`

## 1. API / 처리 단계 / 동기·비동기 / 응답 ID

- 진입점: `POST /order-bids/instant` (`B/order/controller/command/OrderBidCommandController.java:22,89-90`). 본문은 `InstantOrderRequestDto`(saleBidId, addressId, warehouseStorage, paymentRequest) (`B/order/dto/InstantOrderRequestDto.java:21-29`).
- 단계:
  1. 컨트롤러가 SecurityContext에서 이메일 추출 (`OrderBidCommandController.java:92`), `paymentRequest.userEmail=이메일`, `orderId=null`로 보강 (`:98,119-122`).
  2. `OrderBidCommandService.createInstantOrderBid` (`B/order/service/command/OrderBidCommandService.java:118-149`): 입력 검증(`:123,154-167`) → 구매자 조회(`:126`) → SaleBid/Sale 조회·검증(`:129-130,172-184`).
  3. `OrderCommandService.createInstantOrder` (`B/order/service/command/OrderCommandService.java:219-319`): 주소 조회(`:238`) → Order 저장(`:241-247`) → `paymentRequest.setOrderId(order.getId())`(`:250`) → OrderItem(`:255`) → OrderShipment(`:264-271`) → SaleBid 매칭 + `entityManager.flush()`(`:279-283`) → 판매자가 창고보관 판매면 창고 상태 변경(`:291-293`) → 결제 `paymentCommandService.processPayment`(`:305`).
  4. 결제 성공 후 `PaymentCommandService.notifyUsersAndUpdateSaleStatus`로 알림 + Sale `SOLD` (`B/payment/service/command/PaymentCommandService.java:83,383-420`).
  5. 마지막으로 `OrderBid` 생성·저장 (`OrderBidCommandService.java:142,189-207`).
- **동기 처리**다. 컨트롤러가 서비스 반환값을 그대로 받아 응답한다(`OrderBidCommandController.java:101-109`). 전부 `@Transactional` 하나(`OrderBidCommandService.java:118`)로 묶인 단일 트랜잭션이다. 이 경로에는 Kafka Producer/Consumer 호출이 없다(Kafka는 `OrderCommandController` 등 다른 엔드포인트용: `B/order/controller/command/OrderCommandController.java:30`). 알림 WebSocket 전송도 같은 스레드에서 직접 호출한다.
- 응답으로 돌려주는 ID는 **OrderBid의 ID**다. 컨트롤러 변수명은 `orderId`지만 `createInstantOrderBid(...).getId()`는 `OrderBid.getId()`다(`OrderBidCommandController.java:101-107`, 반환 타입 `OrderBid` `OrderBidCommandService.java:119`). 주문(Order) ID가 아니다.

## 2. 생성되는 엔티티와 상태 변화 순서

| 순서 | 동작 | 직후 상태 | 근거 |
|---|---|---|---|
| 1 | Order 생성·저장 | Order=`PENDING_PAYMENT` (totalAmount=SaleBid 가격) | `OrderCommandService.java:241-247` |
| 2 | OrderItem 생성 (quantity 1) | — | `OrderCommandService.java:255`, `B/order/service/command/OrderItemCommandService.java:46-52` |
| 3 | OrderShipment 생성 (주소는 addressId로 조회한 값) | Shipment=`PENDING` | `OrderCommandService.java:264-271`, `B/shipment/service/command/OrderShipmentCommandService.java:61-67` |
| 4 | `saleBid.assignOrder(order)` + `updateStatus(MATCHED)` + flush | SaleBid=`MATCHED` | `OrderCommandService.java:279-283`, `B/sale/entity/SaleBid.java:58-68` |
| 5 | (Sale이 창고보관 판매인 경우) 창고 상태 변경 | WarehouseStorage=`ASSOCIATED_WITH_ORDER` | `OrderCommandService.java:291-293`, `B/warehouseStorage/service/command/WarehouseStorageCommandService.java:117-133` |
| 6 | Payment 생성 (카드/계좌/일반) | 3번 항목 참조 | `PaymentCommandService.java:67-80` |
| 7 | 결제 후 Sale 상태 변경 | Sale=`SOLD` (전이 검증 없이 대입) | `PaymentCommandService.java:391-406`, `B/sale/entity/Sale.java:73-75` |
| 8 | OrderBid 생성 (user=구매자, bidPrice=SaleBid 가격, sale 연결) | OrderBid=`MATCHED`, `isInstantPurchase=true` | `OrderBidCommandService.java:192-206`, `B/order/entity/OrderBid.java:60-82,97-99` |

- Order 상태는 1번 이후 **한 번도 바뀌지 않는다** (5번 질문 참조).
- 7번 참고: 결제 시점에 `order.getOrderBid()`는 아직 null(OrderBid가 나중에 생성됨)이므로, `saleBidQueryService.findByOrderId`로 SaleBid→Sale을 찾는 분기(`PaymentCommandService.java:388-406`)를 탄다. 4번에서 flush했기 때문에 조회된다.
- 이 단계에서 `Order.assignPayment`는 호출되지 않는다 (`OrderCommandService.java:305`는 반환값을 버림). Payment는 `payment.assignOrder(order)`만 되어 있다(`PaymentCommandService.java:200,258,311`).

## 3. 결제 수단별 결과

- 공통 검증: orderId·이메일 일치, 금액 > 0 (`PaymentCommandService.java:117-146`). 유형은 JSON `paymentType`으로 분기 (`B/payment/dto/PaymentRequestDto.java:20-25`).
- **카드(CARD)**: PaymentInfo 조회 → PortOne 호출(`PaymentCommandService.java:166,179`). 응답 `status`가 `"success"`면 `PAID` + `isSuccess=true`(`:203-206`). 아니면 PENDING 기본값으로 저장된다(`B/payment/entity/Payment.java:44`) — 다만 PortOne 클라이언트는 `code != 0`이면 예외를 던지므로(`B/payment/portone/PortOneApiClient.java:270-275`) 실제로는 거의 `PAID`로만 저장된다.
- **계좌이체(ACCOUNT)**: 은행명 검증 후 `PENDING`으로 저장, 외부 호출 없음 (`PaymentCommandService.java:244,250-262`). 결제 완료 처리가 이 경로에 없어 `PENDING`으로 남는다.
- **일반(GENERAL)**: impUid 필수 확인 후 곧바로 `PAID`, `isSuccess=true` (`PaymentCommandService.java:297-314`). 외부 검증 없음.
- **즉시 구매 자체는 끝까지 성공한다**: 어느 결제 수단이든 예외만 안 나면 Order/OrderItem/Shipment/Payment/OrderBid가 저장되고 응답 `200 "즉시 구매가 성공적으로 처리되었습니다"` (`OrderBidCommandController.java:109`). 계좌이체는 결제가 `PENDING`인데도 SaleBid는 `MATCHED`, Sale은 `SOLD`로 바뀌고 알림도 나간다 (결제 상태를 확인하지 않음: `PaymentCommandService.java:83`).
- **카드 결제를 PG가 실패로 응답하면**: `PortOneApiClient`가 `PaymentProcessingException`을 던짐(`PortOneApiClient.java:270-274`) → `createCardPayment`가 재전파(`PaymentCommandService.java:180-181,218-219`) → `processPayment`가 재전파(`:89-94`) → `createInstantOrder`가 `OrderPaymentProcessingFailedException`으로 감쌈(`OrderCommandService.java:306-309`) → `OrderException`이므로 그대로 전파(`:312-314`, `OrderBidCommandService.java:145-146,213-214`). 모두 RuntimeException(`src/main/java/com/fream/back/global/exception/GlobalException.java:10`)이고 같은 트랜잭션이므로 **전체 롤백**: Order, OrderItem, OrderShipment, SaleBid의 `MATCHED`, 창고 상태 변경이 모두 취소되고 Payment/OrderBid도 생성되지 않는다. 구매자에게는 에러 응답이 간다. (HTTP 통신 오류도 `PaymentApiException`으로 같은 결과: `PortOneApiClient.java:288-290`.)

## 4. 알림

- 수신자 2명, 모두 앱 내 알림 (`NotificationCategory.SHOPPING`, `NotificationType.BID`): (`PaymentCommandService.java:415-437`)
  - 구매자: "결제가 완료되었습니다. 주문 ID: {orderId}"
  - 판매자(`sale.getSeller()`): "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}"
- 시점: 결제 Payment 저장 직후, 같은 요청/트랜잭션 안에서 동기 전송(`PaymentCommandService.java:83`). 즉 OrderBid 생성보다 앞이다.
- 방식: `NotificationCommandService.createNotification`이 DB에 저장하고(`B/notification/service/command/NotificationCommandService.java:52-54`) 이어서 Redis 키 `WebSocket:User:{email}`가 있는 사용자(=접속 중)에게만 `/queue/notifications`로 WebSocket 푸시한다(`:303-314`). 접속 중이 아니면 저장만 된다(`:320-322`).
- 알림 실패는 삼키고 로그만 남긴다(`PaymentCommandService.java:438-442`, 알림 전체 블록은 `:384-385,411-414`의 try/catch). 알림이 실패해도 즉시 구매는 롤백되지 않는다.
- Kafka, 이메일 알림은 이 경로에 없다.

## 5. 최종 주문 상태 / 창고 보관

- **주문(Order)의 최종 상태는 `PENDING_PAYMENT`**다. 결제가 `PAID`여도 마찬가지다. `createInstantOrder`는 Order를 `PENDING_PAYMENT`로 만든 뒤(`OrderCommandService.java:244`) `updateStatus`를 한 번도 호출하지 않고, 결제 서비스도 Order 상태를 건드리지 않는다(`PaymentCommandService.java:57-107,383-420`). `PAYMENT_COMPLETED`/`PREPARING`/`IN_WAREHOUSE`/`COMPLETED`로 전이하는 코드는 `processPaymentAndShipment`(`OrderCommandService.java:163-177`)와 Kafka Consumer(`B/order/service/kafka/OrderEventConsumer.java:192-217`)에만 있고, 즉시 구매 경로에서는 호출되지 않는다. (메서드명·javadoc의 "주문 완료"와 달리 실제로는 결제 대기 상태.) 반면 OrderBid=`MATCHED`, SaleBid=`MATCHED`, Sale=`SOLD`이다.
- **창고 보관(`warehouseStorage=true`) 선택 시**: 요청 값은 서비스에 `isWarehouseStorage`로 전달되지만(`OrderBidCommandController.java:105`, `OrderBidCommandService.java:137`) `createInstantOrder` 안에서 **한 번도 읽히지 않는다**(`OrderCommandService.java:220-319` 어디에도 사용 없음). 따라서 구매자가 보관을 선택해도 `createOrderStorage`, `IN_WAREHOUSE` 전이, 주문 완료 처리가 일어나지 않고 `false`와 결과가 동일하다. 배송 정보(OrderShipment, PENDING)는 보관 여부와 관계없이 항상 만들어진다(`OrderCommandService.java:264-271`).
- 창고 관련으로 실제 일어나는 일은 구매자 선택이 아니라 **판매 쪽 플래그**다: `sale.isWarehouseStorage()`가 true면 판매자의 WarehouseStorage를 `ASSOCIATED_WITH_ORDER`로 바꾼다(`OrderCommandService.java:291-293`). 해당 보관 정보가 없거나 전환이 불가하면 `OrderWarehouseStorageProcessingFailedException`으로 전체 롤백된다(`:295-301`).
