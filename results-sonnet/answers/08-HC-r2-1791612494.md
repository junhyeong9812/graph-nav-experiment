# 구매자 배송: 운송장 등록 → 배송 완료

경로 약어: `S` = `src/main/java/com/fream/back/domain/shipment`, `O` = `src/main/java/com/fream/back/domain/order`, `SALE` = `src/main/java/com/fream/back/domain/sale`, `G` = `src/main/java/com/fream/back/global`

## 1. 운송장 등록 요청

### 1-1. 진입 API
- `PATCH /shipments/order/{shipmentId}/status`, body `{courier, trackingNumber}` — `S/controller/command/OrderShipmentCommandController.java:20,33-45`.
- 컨트롤러는 `OrderShipmentCommandService.updateTrackingInfo(shipmentId, courier, trackingNumber)`를 그대로 호출하고 성공하면 200 빈 본문을 준다 (`OrderShipmentCommandController.java:41-48`).
- 비슷한 `POST /{id}/check-status` (`:58`)는 `updateAndCheckShipmentStatus`를 호출하는 별개 API다.

### 1-2. 코드가 의도한 순서 (`S/service/command/OrderShipmentCommandService.java:238-303`)
1. courier/trackingNumber 공백 검사 → 실패 시 `TRACKING_INFO_REQUIRED` (`:243-246`).
2. `OrderShipment` 조회 (`:249-253`).
3. **OrderShipment** `updateTrackingInfo` → courier/trackingNumber 저장, 상태 `IN_TRANSIT` (`:256`, `S/entity/OrderShipment.java:41-45`). PENDING→IN_TRANSIT 전이 검사 없이 바로 대입한다.
4. **Order** → `IN_TRANSIT` (`:259-260`).
5. 구매자 알림 1건 "상품이 출발하였습니다. 주문 ID: …" (`:265-271`).
6. `updateSaleStatusToSold(orderId)` (`:276`): **Sale** → `SOLD`, 판매자 알림 "상품이 성공적으로 판매 완료되었습니다…" (`:111-183`, 알림 `:133-138`, `:164-169`).
7. 창고 보관 Sale이면 창고 상태 갱신 (`:279-286`).
8. `updateOrderAndSaleBidStatusToCompleted` (`:289`): **OrderBid** MATCHED→`COMPLETED`, **SaleBid** MATCHED→`COMPLETED` (`:412-440`).

즉 설계상 구매자 1건 + 판매자 1건 알림이고, "배송 완료"가 아니라 운송장 등록 시점에 Sale이 SOLD, 입찰이 COMPLETED가 된다. 이 메서드는 `@Transactional private`이라 어노테이션은 무의미하고, 안의 예외는 로그만 남기고 삼킨다 (`:436-439`).

### 1-3. 실배송 일반 구매 입찰 주문에서 끝까지 성공하나 → **아니오, 4단계에서 실패**
**실패 직전 상태**
- 일반 입찰은 `Order=PENDING_PAYMENT`로 생성된다 (`O/service/command/OrderCommandService.java:78-82`).
- 결제·배송 처리를 마치면 실배송은 `PAYMENT_COMPLETED → PREPARING`까지만 간다 (`OrderCommandService.java:174-177`).
- 배송정보는 `PENDING`으로 만들어진다 (`S/service/command/OrderShipmentCommandService.java:61-68`).

**실패 지점과 이유**
- 단계 4의 `order.updateStatus(IN_TRANSIT)` (`OrderShipmentCommandService.java:260`)에서 실패한다.
- `PREPARING`의 허용 전이는 `IN_WAREHOUSE, SHIPMENT_STARTED`뿐이다 (`O/entity/OrderStatus.java:26`).
- 그래서 `Order.updateStatus`가 `InvalidOrderStatusException`을 던진다 (`O/entity/Order.java:166-173`). 이 예외는 `OrderException` 계열이다 (`O/exception/InvalidOrderStatusException.java:6`).
- `catch (ShipmentException)`에 걸리지 않고 `catch (Exception)`에 걸려 `ShipmentException(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")`로 래핑된다 (`OrderShipmentCommandService.java:293-301`).
- 설령 4단계를 통과해도 6단계 `updateSaleStatusToSold`의 `saleBidQueryService.findByOrderId`(`:116`)가 SaleBid 없음으로 `IllegalArgumentException`을 던진다. 이 메서드는 null을 반환하지 않고 예외를 던진다 (`SALE/service/query/SaleBidQueryService.java:26-28`). 이 호출은 try 밖이라 그대로 `:295` catch로 가서 같은 래핑 예외가 된다. 일반 입찰 주문은 SaleBid(order 연결)가 없으므로 이쪽도 실패한다.

**무엇이 저장되나 → 아무것도 저장되지 않음**
- 예외는 `GlobalException extends RuntimeException`이다 (`G/exception/GlobalException.java:12`).
- `@Transactional` 메서드 밖으로 나가므로 롤백된다.
- 3단계의 `IN_TRANSIT`/courier/trackingNumber는 메모리에서만 바뀐 상태였고 DB에는 반영되지 않는다. 배송은 `PENDING`, 운송장 `null`로 남는다.
- 알림(5단계)은 4단계 뒤라서 만들어지지 않는다. 입찰/Sale 변경도 없다.

**응답**
- `GlobalExceptionHandler.handleShipmentException`이 `errorCode.getStatus()/getCode()/getMessage()`로 응답을 만든다 (`G/exception/GlobalExceptionHandler.java:459-472`). 커스텀 메시지는 응답에 쓰이지 않는다.
- 결과: **HTTP 404, code `S001`, message "배송 정보를 찾을 수 없습니다."** (`S/exception/ShipmentErrorCode.java:12`). 배송이 실제로 존재해도 이 응답이 나온다.

## 2. 배송 완료 감지

### 2-1. 누가 / 언제
- 사람이 호출하는 게 아니라 스케줄러가 한다. `ShipmentBatchScheduler.scheduleShipmentStatusJob` (`G/config/ShipmentBatchScheduler.java:34-44`).
- 주기: `@Scheduled(cron = "0 0 */6 * * *")` = **6시간마다(00/06/12/18시 정각, 서버 타임존)** (`:34`).
- `timestamp` 파라미터를 매번 바꿔 Spring Batch `updateShipmentStatusesJob`을 `jobLauncher.run`으로 실행한다 (`:37-40`). 예외는 `printStackTrace`만 하고 삼킨다 (`:41-43`).

### 2-2. 조회 대상
- reader가 `SELECT s FROM OrderShipment s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL`를 페이지 50건씩 읽는다 (`S/config/UpdateShipmentStatusesJobConfig.java:87-96`).
- chunk 50 / skipLimit 50 (`:51-52`, `:67`, `:76-77`).

### 2-3. 실제로 실행되는 처리 코드
- 실제 사용되는 것은 **`new ShipmentItemProcessor(playwrightBrowserManager(), notificationService, orderService)`** 이다 (`UpdateShipmentStatusesJobConfig.java:69-73`). 클래스는 `S/config/ShipmentItemProcessor.java:57` (`process`)이다.
- 같은 파일의 `@Bean shipmentItemProcessor()` 람다 (`:104-177`)와 `parseCjLogisticsStatus` (`:186`)는 Step에 연결되어 있지 않아 실행되지 않는다. `OrderShipmentCommandService.updateShipmentStatuses()` (`:309`)도 호출하는 곳이 없다 (`grep` 결과 정의만 존재).
- `ShipmentItemProcessor`는 Playwright 페이지로 `https://trace.cjlogistics.com/next/tracking.html?wblNo=<운송장>`을 열고 `tbody#statusDetail tr`을 기다린 뒤 (`ShipmentItemProcessor.java:56-90`), **마지막 행의 5번째 td**(`get(4)`)를 `trim`해서 상태 문자열로 쓴다 (`:167-181`).
- 브라우저는 Step 시작/종료 때 열고 닫는다 (`S/config/BrowserManageStepListener.java:15-23`).

### 2-4. 택배사 문자열 → 내부 상태 (`ShipmentItemProcessor.java:220-226`)
| 택배사 문자열 | 내부 상태 |
|---|---|
| `"배송완료"` | `DELIVERED` |
| `"배송출발"` | `OUT_FOR_DELIVERY` |
| 그 외 전부 | `IN_TRANSIT` |

- 정확한 문자열 일치이며, 알 수 없는 문자열은 조용히 IN_TRANSIT이 된다.
- 현재 상태와 매핑 결과가 같으면 아무것도 안 하고 반환한다 (`:96-101`).
- `OUT_FOR_DELIVERY`인 배송이 "그 외"로 나오면 IN_TRANSIT 전이가 허용되지 않아 (`S/entity/ShipmentStatus.java`: OUT_FOR_DELIVERY는 DELIVERED/FAILED_DELIVERY/CANCELED만 허용) `IllegalStateException` → `EXTERNAL_TRACKING_SERVICE_ERROR`로 래핑되어 skip된다 (`ShipmentItemProcessor.java:129-141`).

## 3. 배송 완료 판정 이후 (`ShipmentItemProcessor.java:108-117`)

### 상태 변경 순서
1. **OrderShipment** → `DELIVERED` (`:113`). IN_TRANSIT/OUT_FOR_DELIVERY에서 모두 허용된다.
2. `orderService.completeOrder(orderId)` (`:116`, `S/service/command/OrderShipmentCommandService.java:190-229`):
   - **Order** → `COMPLETED` (`:204`).
   - `updateSaleStatusToSold` (`:208`): SaleBid의 Sale이 전이 가능하면 **Sale → SOLD** (`:116-123`, 창고 보관이면 창고 상태 `:126-129`). OrderBid의 Sale도 같은 방식 (`:149-176`).
   - 구매자 알림 "[completeOrder] 주문이 완료 처리되었습니다. 주문 ID: …" (`:210-217`).
3. `notificationService.notifyShipmentCompleted(order)` → 구매자 알림 "[배송 완료] 상품이 배송 완료되었습니다. 주문 ID: …" (`:117`, `S/../notification/service/command/NotificationCommandService.java:219-229`; 경로: `src/main/java/com/fream/back/domain/notification/service/command/NotificationCommandService.java`).
4. Writer `JpaItemWriter`가 OrderShipment를 저장한다 (`UpdateShipmentStatusesJobConfig.java:74,239-246`).

### 알림 수
- **구매자 2건**: `[completeOrder]` 1건 + `[배송 완료]` 1건.
- **판매자 최대 1건**: Sale이 SOLD로 전이될 때만 "상품이 성공적으로 판매 완료되었습니다…" (`OrderShipmentCommandService.java:133-138`). 이미 SOLD면 `SaleStatus.canTransitionTo(SOLD)`가 false여서 (`SALE/entity/SaleStatus.java:209`) 0건이다. SaleBid 경로와 OrderBid 경로가 같은 Sale을 가리켜도 첫 경로가 SOLD로 만든 뒤라 두 번째는 건너뛴다.

### 주문 입찰·판매 입찰 상태
- 배치 완료 경로(`completeOrder`)에는 **OrderBid/SaleBid 상태를 바꾸는 코드가 없다.** `updateOrderAndSaleBidStatusToCompleted`는 운송장 등록 경로에서만 호출된다 (`OrderShipmentCommandService.java:289`).
- 따라서 배송 완료 후에도 둘 다 `MATCHED`로 남는다. OrderBid는 생성 시 `assignOrder`에서 MATCHED가 된다 (`O/entity/OrderBid.java:73-76`).
- `COMPLETED`가 되는 것은 1-2의 운송장 등록 성공 경로뿐이다.

## 4. 주문 종류별 차이

### (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문 → **끝까지 진행되지 않음**
- 이 주문은 1-3에서 본 대로 운송장 등록이 롤백되어 배송이 PENDING/운송장 null이다. 배치 reader 조건(IN_TRANSIT & 운송장 not null)에 걸리지 않아 **애초에 대상이 아니다.**
- `POST /check-status`로 배송만 IN_TRANSIT이 된 경우를 가정해도 `completeOrder`에서 실패한다.
  - Order가 PREPARING이라 `COMPLETED` 전이가 불가하다 (`OrderStatus.java:26`).
  - SaleBid가 없어 `findByOrderId`가 예외를 던진다 (`SaleBidQueryService.java:26-28`).
  - `completeOrder`가 이를 `ShipmentException(ORDER_NOT_FOUND_FOR_SHIPMENT)`로 래핑한다 (`OrderShipmentCommandService.java:221-228`).
- 결과: 그 건은 Step에서 skip 처리되고 (5번), 롤백되어 Order/배송/입찰 상태 변화·알림이 모두 없다.

### (b) 즉시 구매로 만들어진 주문 → **3의 처리가 끝까지 진행됨** (배치가 대상으로 잡는다는 전제)
- 상태:
  - Order는 `PENDING_PAYMENT`로 생성되고 (`OrderCommandService.java:241-245`) 결제·즉시구매 흐름에서 상태가 바뀌지 않는다 (`PaymentCommandService`에 `OrderStatus` 변경 없음).
  - `PENDING_PAYMENT → COMPLETED`는 허용된다 (`OrderStatus.java:24`).
  - SaleBid가 `assignOrder`로 order에 연결되어 있고 (`OrderCommandService.java:279`), OrderBid도 order/sale 연결 상태로 생성된다 (`O/service/command/OrderBidCommandService.java:189-206`).
- 결제 시점에 Sale은 이미 SOLD이다. `notifyUsersAndUpdateSaleStatus`가 SaleBid 경로로 `sale.updateStatus(SOLD)`를 한다 (`PaymentCommandService.java:388-406`, 호출 `:83`).
- 배송 완료 시: OrderShipment DELIVERED, Order COMPLETED, 구매자 알림 2건. Sale은 이미 SOLD라 전이 불가여서 Sale 변경과 판매자 알림은 0건이다 (`SaleStatus.java:209`). OrderBid/SaleBid는 MATCHED 유지.
- 주의: 즉시 구매 주문도 `PATCH .../status` 운송장 등록은 `PENDING_PAYMENT → IN_TRANSIT` 불가 (`OrderStatus.java:24`)로 1-3과 똑같이 실패한다. 배치 대상이 되려면 `check-status`(`OrderShipmentCommandService.java:451-516`)처럼 Order 상태를 건드리지 않고 배송만 IN_TRANSIT으로 만드는 경로가 필요하다.

### 차이 요약
| | (a) 일반 입찰 | (b) 즉시 구매 |
|---|---|---|
| Order 상태(완료 직전) | PREPARING | PENDING_PAYMENT |
| COMPLETED 전이 | 불가 | 가능 |
| SaleBid 존재 | 없음 → 예외 | 있음 |
| 배송 완료 처리 | 실패·롤백·skip | 성공 |
| 알림 | 0건 | 구매자 2건, 판매자 0건 |

## 5. 실패 처리 (주기 처리 중 한 건 실패)
- Step이 `faultTolerant().skip(Exception.class).skipLimit(50)` 이다 (`UpdateShipmentStatusesJobConfig.java:75-77`).
- processor가 던진 예외(`ShipmentException`, 래핑된 `IllegalStateException` 등)는 그 건만 skip된다. `SkipListener`가 에러 로그만 남긴다 (`:251-287`).
- 실패한 건: `completeOrder`/알림이 청크 트랜잭션에 참여하므로 그 건의 DB 변경은 롤백된다. 상태는 IN_TRANSIT/OUT_FOR_DELIVERY 그대로 남고, **다음 6시간 주기에 다시 조회**된다. 재시도·보상 로직은 없다.
- 나머지 건: Spring Batch가 실패한 청크를 롤백한 뒤 건별로 다시 처리·커밋한다 (fault-tolerant 기본 동작). 정상 건은 반영된다.
- skip이 50건을 넘으면 Step이 실패하고 남은 건은 그 회차에서 처리되지 않는다. 스케줄러는 예외를 `printStackTrace`만 하고 끝낸다 (`ShipmentBatchScheduler.java:41-43`).
- 참고(코드 추정, 실행 검증은 하지 않음): 대상이 50건을 넘으면 reader가 offset 페이징이고 처리된 건이 조회 조건에서 빠져, 일부가 이번 회차에서 건너뛰어질 수 있다 (`UpdateShipmentStatusesJobConfig.java:91-96`).
