# 구매자 배송: 운송장 등록 → 배송 완료 처리 (코드 기준 실제 동작)

경로 약어: `S` = `src/main/java/com/fream/back/`

핵심 요약
- 운송장 등록 API(`PATCH /shipments/order/{id}/status`)는 **결제·배송 처리를 마친 실배송 일반 입찰 주문(PREPARING)** 에서 항상 실패한다. 응답은 404 / `S001`, DB에는 아무것도 남지 않는다.
- 배송 완료 판정은 6시간 주기 Spring Batch가 한다. 이 처리는 (a) 실배송 일반 입찰 주문에서는 끝까지 못 가고, (b) 즉시 구매 주문에서는 끝까지 간다.

---

## 1. 운송장 등록 요청

### 1-1. 진입 API
1. `PATCH /shipments/order/{shipmentId}/status`, body `OrderShipmentRequestDto(courier, trackingNumber)` → `OrderShipmentCommandController#updateTrackingInfo` → `OrderShipmentCommandService#updateTrackingInfo`.
   - `S/domain/shipment/controller/command/OrderShipmentCommandController.java:20,33-45`
   - `S/domain/shipment/service/command/OrderShipmentCommandService.java:238-239`
2. 관리자 확인이나 소유자 확인은 없다(인증만 필요). 컨트롤러는 예외를 잡지 않는다(`:41-45`). 전역 핸들러가 처리한다.
3. 같은 컨트롤러에 `POST /{id}/check-status`, `/check-status-string`이 따로 있다. 이쪽은 운송장 갱신 후 CJ를 즉시 조회한다(`OrderShipmentCommandController.java:58-94,103-138`, 서비스 `:451-516`). 위 PATCH와는 다른 경로다.

### 1-2. 코드가 의도한 상태 전이와 알림 (`OrderShipmentCommandService.java:238-303`)
순서는 다음과 같다.
1. courier / trackingNumber 공백 검증, 위반 시 `TRACKING_INFO_REQUIRED` (`:243-246`).
2. `OrderShipment` 조회 후 `shipment.updateTrackingInfo(courier, no)` 호출. 전이 검증 없이 **status = IN_TRANSIT** 으로 바뀐다 (`:249-256`, `S/domain/shipment/entity/OrderShipment.java:41-45`).
3. **Order** `order.updateStatus(OrderStatus.IN_TRANSIT)` (`:259-260`).
4. **알림 ①** 구매자에게 "상품이 출발하였습니다. 주문 ID: …" (`:265-271`).
5. `updateSaleStatusToSold(orderId)` (`:276`, 본체 `:111-183`).
   - SaleBid 경로: Sale이 SOLD로 전이 가능하면 SOLD로 바꾸고 창고보관이면 창고 SOLD 처리. **알림 ②** 판매자에게 "상품이 성공적으로 판매 완료되었습니다" (`:116-147`).
   - OrderBid 경로: Sale을 SOLD로 바꾸고 **알림 ③** 판매자 알림 (`:150-180`).
6. SaleBid의 Sale이 창고보관이면 `updateWarehouseStatusToSold` (`:279-286`).
7. `updateOrderAndSaleBidStatusToCompleted` : OrderBid MATCHED→COMPLETED, SaleBid MATCHED→COMPLETED (`:289`, `:412-440`). 예외는 삼키고 로그만 남긴다(`:436-439`).

의도된 순서는 OrderShipment=IN_TRANSIT → Order=IN_TRANSIT → (Sale=SOLD, 창고 SOLD) → OrderBid/SaleBid=COMPLETED 다. 알림 대상은 구매자 1건과 판매자 1건 이상이다.
메서드 주석("배송 정보에 운송장 정보를 업데이트")과 달리 이 시점에 이미 판매 SOLD / 입찰 COMPLETED 처리가 일어나는 구조다. 배송 완료 시점이 아니다.

### 1-3. 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문에서 성공하나? → **실패한다**
1. 이 주문의 상태는 **PREPARING** 이다.
   - 입찰 주문은 `PENDING_PAYMENT`로 생성된다 (`S/domain/order/service/command/OrderCommandService.java:81`).
   - Kafka 경로: 결제 후 `PAYMENT_COMPLETED` → 실배송이면 `PREPARING` (`S/domain/order/service/kafka/OrderEventConsumer.java:195,215-218`).
   - 동기 경로도 동일하다 (`OrderCommandService.java:175-176`).
   - `SHIPMENT_STARTED`를 설정하는 코드는 없다.
2. 상태 전이표에서 `PREPARING`은 `IN_WAREHOUSE`, `SHIPMENT_STARTED`로만 갈 수 있고, `IN_TRANSIT`은 `SHIPMENT_STARTED`에서만 갈 수 있다 (`S/domain/order/entity/OrderStatus.java:26,28`). 따라서 `PREPARING → IN_TRANSIT`은 불허다.
3. 실패 지점은 `OrderShipmentCommandService.java:260`의 `order.updateStatus(IN_TRANSIT)` 이다. `Order#updateStatus`가 `InvalidOrderStatusException`("상태 전환이 허용되지 않습니다: PREPARING -> IN_TRANSIT")을 던진다 (`S/domain/order/entity/Order.java:113-120`).
4. 이 예외는 `ShipmentException`이 아니라서 `catch (Exception e)` 로 들어가 `ShipmentException(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")` 으로 포장된다 (`OrderShipmentCommandService.java:293-301`).
5. 무엇이 저장되나: **아무것도 저장되지 않는다.**
   - `@Transactional` 메서드에서 RuntimeException(`GlobalException extends RuntimeException`, `S/global/exception/GlobalException.java:11`)이 밖으로 나가므로 롤백된다.
   - 3번 이전에 메모리에서 바뀐 `shipment`의 courier / trackingNumber / IN_TRANSIT 은 DB에 반영되지 않는다. 배송은 PENDING, 송장번호는 null 그대로다.
   - 알림은 5단계 이후에 만들어지므로 생성되지 않는다.
6. 응답은 HTTP **404**, 바디는 `ErrorResponse(code="S001", message="배송 정보를 찾을 수 없습니다.", status=404, path=…)` 이다.
   - `ShipmentErrorCode.SHIPMENT_NOT_FOUND("S001", "배송 정보를 찾을 수 없습니다.", 404)` (`S/domain/shipment/exception/ShipmentErrorCode.java:12`).
   - `GlobalExceptionHandler#handleShipmentException`은 포장 시 넣은 상세 메시지가 아니라 enum 기본 문구를 쓴다 (`S/global/exception/GlobalExceptionHandler.java:459-472`).
   - 실제 원인은 "배송 정보 없음"이 아니라 주문 상태 전이 불가인데, 오해를 부르는 코드로 내려간다.
7. 부가로, 설령 상태 전이가 통과해도 일반 입찰 주문에는 SaleBid가 없다. `SaleBidQueryService#findByOrderId`가 없으면 `IllegalArgumentException`을 던지므로(`S/domain/sale/service/query/SaleBidQueryService.java:25-29`) `updateSaleStatusToSold`의 `:116`에서 다시 실패한다. 이중으로 막혀 있다.

참고: 즉시 구매 주문(PENDING_PAYMENT)도 `PENDING_PAYMENT → IN_TRANSIT`이 표에 없어(`OrderStatus.java:24`) 같은 PATCH가 같은 방식으로 실패한다.

## 2. 배송 완료 감지

### 2-1. 누가 / 언제 / 어떻게
1. 감지 주체는 서버 내부 스케줄러 `ShipmentBatchScheduler#scheduleShipmentStatusJob` 이다. 시각 파라미터를 붙여 `updateShipmentStatusesJob`을 `JobLauncher`로 실행한다 (`S/global/config/ShipmentBatchScheduler.java:34-44`).
2. **주기**는 `@Scheduled(cron = "0 0 */6 * * *")`, 즉 매일 0·6·12·18시 정각(6시간)이다 (`ShipmentBatchScheduler.java:34`).
3. Job 구성: Step 하나, chunk 50, `faultTolerant().skip(Exception.class).skipLimit(50)` (`S/domain/shipment/config/UpdateShipmentStatusesJobConfig.java:51-52,54-82`).
4. 대상 조회(Reader): `SELECT s FROM OrderShipment s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL`, page 50 (`UpdateShipmentStatusesJobConfig.java:95`). PENDING / DELIVERED 등은 대상이 아니다.
5. 결과적으로 운송장이 성공적으로 등록되지 못한 배송(PENDING)은 영영 조회 대상이 되지 않는다.

### 2-2. 실제로 실행되는 처리 코드
비슷한 코드가 여러 곳에 있지만 배치에서 실제 실행되는 것은 **`ShipmentItemProcessor#process`** 하나다.
- Step이 `new ShipmentItemProcessor(playwrightBrowserManager(), notificationService, orderService)`를 직접 등록한다 (`UpdateShipmentStatusesJobConfig.java:69-73`).
- 실행 내용: 공유 Playwright 브라우저로 `https://trace.cjlogistics.com/next/tracking.html?wblNo=<운송장>`에 접속해 `tbody#statusDetail tr`을 기다린다. 마지막 행의 5번째 td를 Jsoup으로 읽는다 (`S/domain/shipment/config/ShipmentItemProcessor.java:28-29,57-94,167-191`).
- 실행되지 않는 유사 코드:
  - `UpdateShipmentStatusesJobConfig#shipmentItemProcessor()` @Bean (`:104-177`). Step에서 쓰지 않는다. `parseCjLogisticsStatus` (`:186-220`)도 마찬가지다.
  - `OrderShipmentCommandService#updateShipmentStatuses()` (`:308-391`). 호출처가 없다(전체 검색 결과 정의만 존재). `@Scheduled`도 없다.
  - `CjTrackingPlaywright#getCurrentTrackingStatus` 는 배치가 아니라 수동 `check-status` API와 위 미사용 코드에서만 쓰인다.

### 2-3. 택배사 상태 문자열 → 내부 상태
`ShipmentItemProcessor#mapToShipmentStatus` (`ShipmentItemProcessor.java:220-226`). 문자열은 trim 후 **정확히 일치**할 때만 매핑한다.

| CJ 문자열 | 내부 ShipmentStatus |
|---|---|
| `배송완료` | DELIVERED |
| `배송출발` | OUT_FOR_DELIVERY |
| 그 외 전부(집화처리, 간선상차 등) | IN_TRANSIT |

처리 분기 (`ShipmentItemProcessor.java:100-126`):
- 현재 상태와 같으면 변경 없이 반환.
- DELIVERED면 배송완료 처리.
- OUT_FOR_DELIVERY / IN_TRANSIT이면 해당 상태로 `updateStatus`.

주의: `OUT_FOR_DELIVERY` 상태인 건에 대해 CJ가 "배송출발"·"배송완료" 외의 문자열을 주면 IN_TRANSIT으로 매핑된다. `OUT_FOR_DELIVERY → IN_TRANSIT`은 `ShipmentStatus`에서 불허이므로(`S/domain/shipment/entity/ShipmentStatus.java:17-22`) `IllegalStateException`이 나고(`OrderShipment.java:47-55`), `ShipmentException(S302)`으로 포장되어(`ShipmentItemProcessor.java:138-144`) 스킵된다.

## 3. 배송 완료 판정 이후 (배치, `ShipmentItemProcessor.java:108-117`)

### 3-1. 상태 변경 순서
1. `orderShipment.updateStatus(DELIVERED)` (메모리, `:113`). `IN_TRANSIT`/`OUT_FOR_DELIVERY` → `DELIVERED`는 허용이다 (`ShipmentStatus.java:17-28`).
2. `orderService.completeOrder(orderId)` (`:116`, 본체 `OrderShipmentCommandService.java:190-229`):
   1. `OrderBid` 조회, 없으면 `IllegalArgumentException` (`:196-197`).
   2. **Order → COMPLETED** (`:204`).
   3. `updateSaleStatusToSold` (`:208`). Sale이 `canTransitionTo(SOLD)`일 때만 SOLD (`SaleStatus.java`에서 SOLD는 전이 불가).
   4. 구매자 알림 (`:211-217`).
   5. 어떤 예외든 `ShipmentException(ORDER_NOT_FOUND_FOR_SHIPMENT, S102)`로 포장 (`:221-228`).
3. `notificationService.notifyShipmentCompleted(order)` (`:117`).
4. Writer(`JpaItemWriter`)가 chunk 커밋 시 `OrderShipment`를 DB에 반영한다 (`UpdateShipmentStatusesJobConfig.java:241-246`).

순서 요약: OrderShipment=DELIVERED → Order=COMPLETED → Sale=SOLD (필요 시) → 알림 → 저장.

### 3-2. 알림
- 구매자: 2건.
  - "[completeOrder] 주문이 완료 처리되었습니다. 주문 ID: …" (`OrderShipmentCommandService.java:212-217`)
  - "[배송 완료] 상품이 배송 완료되었습니다. 주문 ID: …" (`S/domain/notification/service/command/NotificationCommandService.java:219-229`)
- 판매자: Sale이 아직 SOLD가 아닐 때만 "상품이 성공적으로 판매 완료되었습니다. 판매 ID: …" 1건 (`OrderShipmentCommandService.java:133-138`).
  - SaleBid 경로(`:116-147`)와 OrderBid 경로(`:150-180`)가 같은 Sale을 가리키면 첫 경로에서 SOLD가 되고 두 번째는 전이 불가라 중복 알림은 없다.
  - 그러나 결제 단계에서 이미 Sale이 SOLD로 바뀌므로(`S/domain/payment/service/command/PaymentCommandService.java:82-83,404,419`) 실제로는 보통 0건이다.
- 알림 생성은 `createNotification` → DB 저장 + STOMP 푸시 (`NotificationCommandService.java:44-57`).

### 3-3. 주문 입찰 / 판매 입찰 상태
- 배송 완료 처리 경로(`completeOrder`, `ShipmentItemProcessor`)는 **OrderBid·SaleBid의 상태를 건드리지 않는다.** `updateOrderAndSaleBidStatusToCompleted`는 운송장 등록 메서드(`:289`)에서만 호출된다.
- 따라서 두 입찰은 배송 완료 후에도 MATCHED 로 남는다 (즉시 구매는 생성 즉시 MATCHED: `S/domain/order/service/command/OrderBidCommandService.java:196`, `S/domain/order/service/command/OrderCommandService.java:279-280`).
- 운송장 등록 성공 시 COMPLETED로 바뀌게 되어 있지만(1-2의 7), 1-3에서 본 대로 그 경로는 성공하지 못한다. 결국 COMPLETED로 가는 실제 경로가 사실상 없다.

## 4. 주문 종류별 차이

### (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문: **끝까지 진행되지 않는다**
1. 주문 상태가 PREPARING이다 (`OrderEventConsumer.java:215-218`).
2. 먼저 배송을 IN_TRANSIT으로 만드는 것 자체가 막힌다. 운송장 PATCH는 1-3에서 본 대로 실패하므로 배치 대상(`IN_TRANSIT`/`OUT_FOR_DELIVERY`)이 되지 못한다.
3. 가정적으로 `check-status` API 등으로 배송이 IN_TRANSIT이 되어 배치가 DELIVERED를 판정해도 다음에서 실패한다.
   - `completeOrder`의 `order.updateStatus(COMPLETED)` (`OrderShipmentCommandService.java:204`)에서 `PREPARING → COMPLETED` 불허 (`OrderStatus.java:26`) → `InvalidOrderStatusException`.
   - `ShipmentException(S102)`로 포장 (`:221-228`).
4. 결과:
   - Order는 PREPARING, Sale·입찰 상태는 변경 없음.
   - 구매자·판매자 알림 0건. `notifyShipmentCompleted`(`:117`)에 도달하지 않는다.
   - 배송 DELIVERED 변경도 롤백되어 유지되지 않는다. 항목은 스킵되고 다음 실행(6시간 뒤)에서 다시 같은 실패를 반복한다.
5. 수동 `check-status`로 "배송완료"를 받아도 같은 `completeOrder`에서 실패하며 응답은 `S102`의 HTTP 404(바디 없음)다 (`OrderShipmentCommandController.java:80-86`, `OrderShipmentCommandService.java:489,505-506`).

### (b) 즉시 구매로 만들어진 주문: **끝까지 진행된다 (단, 입찰 상태는 그대로)**
1. 생성 경로: 즉시 구매는 `Order(PENDING_PAYMENT)`를 만들고 결제까지 처리하며(`OrderCommandService.java:244,305`), 이후 `OrderBid(MATCHED, isInstantPurchase)`를 만든다(`OrderBidCommandService.java:133,189-206`). Order 상태는 결제 후에도 PENDING_PAYMENT로 남는다. 즉시 구매 경로에서 Order를 `PAYMENT_COMPLETED` 등으로 바꾸는 코드는 없다(`OrderCommandService.java`에서 `updateStatus(OrderStatus…)`는 `:165-176`의 `processPaymentAndShipment`에만 있다).
2. 판매 입찰(SaleBid)은 이 주문에 연결되고 MATCHED이다 (`OrderCommandService.java:279-280`).
3. DELIVERED 판정 시(배송이 어떤 경로로든 IN_TRANSIT/OUT_FOR_DELIVERY일 때):
   - `completeOrder`: OrderBid가 존재 → `PENDING_PAYMENT → COMPLETED` 는 표에서 허용 (`OrderStatus.java:24`) → 성공.
   - `updateSaleStatusToSold`: SaleBid가 존재하므로 `:116`에서 예외 없음. Sale은 결제 시 이미 SOLD(`PaymentCommandService.java:404`)라 `canTransitionTo(SOLD)`가 false → 판매자 알림·창고 처리 없음.
4. 결과:
   - OrderShipment=DELIVERED, Order=COMPLETED, Sale=SOLD (이미).
   - OrderBid/SaleBid는 MATCHED 유지(COMPLETED 아님).
   - 알림: 구매자 2건, 판매자 0건.
   - 참고: 이 주문의 운송장은 PATCH API로 등록할 수 없다(`PENDING_PAYMENT → IN_TRANSIT` 불허, 1-3 참고). 배치 대상이 되려면 `check-status` API가 "배송출발"을 받아 OUT_FOR_DELIVERY가 되는 식의 우회가 필요하다. 이 API에서 CJ가 IN_TRANSIT 계열을 주면 `IN_TRANSIT→IN_TRANSIT` 불허로 `IllegalStateException` → S302 → 롤백된다 (`OrderShipmentCommandService.java:495-498`).
   - `check-status` API에서 바로 "배송완료"를 받으면 `completeOrder`만 실행되어 구매자 알림은 1건이다. `notifyShipmentCompleted`는 호출되지 않는다 (`:483-489`).

차이 요약
| | (a) 실배송 일반 입찰 | (b) 즉시 구매 |
|---|---|---|
| Order 상태 | PREPARING | PENDING_PAYMENT |
| COMPLETED 전이 | 불허 → 예외 S102 | 허용 → 성공 |
| 운송장 PATCH | 실패(S001/404) | 실패(S001/404) |
| 배치 완료 처리 | 매번 스킵·롤백 | 성공 |
| 알림 | 0건 | 구매자 2 / 판매자 0 |
| OrderBid/SaleBid | MATCHED 유지 | MATCHED 유지 |

## 5. 실패 처리 (배치)
1. 한 건 처리 중 예외가 나면 `ShipmentItemProcessor`가 `ShipmentException`으로 포장해 던진다 (`ShipmentItemProcessor.java:133-145`).
2. Step이 `faultTolerant().skip(Exception.class).skipLimit(50)`이라 해당 건만 스킵되고, 스킵 리스너가 로그를 남긴다 (`UpdateShipmentStatusesJobConfig.java:75-78,251-287`).
3. 해당 건: DB 변경 없이 상태가 그대로(IN_TRANSIT / OUT_FOR_DELIVERY)라 다음 6시간 주기에 다시 조회 대상이 된다. 같은 원인이면 같은 실패를 반복한다.
   - `completeOrder`는 chunk 트랜잭션에 참여하고 RuntimeException으로 빠져나가므로 해당 트랜잭션이 롤백 대상이 된다.
   - 스킵된 항목은 Writer로 넘어가지 않는다.
4. 나머지 건: 계속 처리되어 정상 반영된다. 스킵 시 Spring Batch가 chunk를 롤백한 뒤 항목 단위로 재처리하므로, 성공 건들은 다시 처리되어 커밋된다. Spring Batch의 fault-tolerant 기본 동작에 대한 설명이며, 이 저장소 코드에는 별도의 재처리 로직이 없다.
5. 한도: 스킵이 50건을 넘으면 `SkipLimitExceededException`으로 Step이 실패하고 남은 건은 그 실행에서 처리되지 않는다.
6. 스케줄러는 `jobLauncher.run` 예외를 `printStackTrace()`만 하고 삼킨다 (`ShipmentBatchScheduler.java:41-43`). 재시도나 알림은 없다.
7. 브라우저는 Step 시작 시 열고 끝나면 닫는다 (`S/domain/shipment/config/BrowserManageStepListener.java`). 페이지는 건마다 `finally`에서 닫는다 (`ShipmentItemProcessor.java:146-156`).
8. 참고(미사용 코드): `OrderShipmentCommandService#updateShipmentStatuses`는 건별 try/catch로 실패 건을 세고 계속 진행하는 구조이나(`:322-387`) 호출처가 없어 실행되지 않는다.
