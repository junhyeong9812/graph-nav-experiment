# 즉시 구매 처리 흐름 (POST /order-bids/instant)

경로 약어: `D` = `src/main/java/com/fream/back/domain`

## 1. 진입 API / 처리 단계 / 동기·비동기 / 응답 ID

- 진입: `POST /order-bids/instant` → `OrderBidCommandController#createInstantOrderBid` (`D/order/controller/command/OrderBidCommandController.java:22,89-110`). 클래스 매핑은 `/order-bids`(:22). prod nginx가 `/api`를 떼므로 `/api` 없음.
- 단계:
  1. 컨트롤러: 로그인 이메일 추출(`:92`), `enrichPaymentRequest`로 `userEmail` 설정·`orderId=null`(`:98`, `:119-122`).
  2. `OrderBidCommandService#createInstantOrderBid` (`D/order/service/command/OrderBidCommandService.java:118-149`, `@Transactional` :118): 입력 검증(:123) → 구매자 조회(:126) → `SaleBid`/`Sale` 조회(:129-130) → `OrderCommandService#createInstantOrder`(:133) → `OrderBid` 생성·저장(:142, 구현 :189-207).
  3. `OrderCommandService#createInstantOrder` (`D/order/service/command/OrderCommandService.java:219-319`): 배송지 조회(:238) → Order 저장(:241-247) → paymentRequest.orderId 설정(:250) → OrderItem(:255) → OrderShipment(:264-271) → SaleBid 매칭 + flush(:279-283) → 판매자 창고 상태 변경(:289-301) → **결제 동기 호출**(:305).
- **완전 동기**. Kafka를 쓰지 않는다. (Kafka 경유 결제는 `/orders/{id}/process-payment-shipment` 쪽 흐름이며 즉시 구매와 무관.) 결제·알림·상태변경이 모두 요청 스레드·하나의 트랜잭션 안에서 끝난 뒤 응답한다.
- 응답: `ResponseDto<Long>`의 값. 변수명은 `orderId`지만(`OrderBidCommandController.java:101`) 실제로는 `createInstantOrderBid(...).getId()`(`:107`), 즉 **새로 만든 OrderBid의 ID**이지 Order ID가 아니다.

## 2. 생성되는 엔티티와 상태 변화 순서

| 순서 | 동작 | 직후 상태 | 근거 |
|---|---|---|---|
| 1 | Order 생성 | `OrderStatus.PENDING_PAYMENT` | `OrderCommandService.java:241-247` |
| 2 | OrderItem 생성 | (상태 없음, Order에 추가) | `:255-256` |
| 3 | OrderShipment 생성 | `ShipmentStatus.PENDING` | `D/shipment/service/command/OrderShipmentCommandService.java:56-75`(:67), 호출 `OrderCommandService.java:264` |
| 4 | 기존 SaleBid에 Order 연결 | SaleBid `BidStatus.MATCHED` | `D/sale/entity/SaleBid.java:58-61`, `OrderCommandService.java:279-280`, flush :283 |
| 5 | (판매자가 창고 보관인 Sale일 때만) 판매자 WarehouseStorage | `ASSOCIATED_WITH_ORDER` (IN_STORAGE→전환 허용) | `OrderCommandService.java:291-294`, `D/warehouseStorage/service/command/WarehouseStorageCommandService.java:117-133,232-` |
| 6 | Payment 생성 (결제수단별, 아래 3번) | CARD: 원칙상 PAID / GENERAL: PAID / ACCOUNT: 예외 | `PaymentCommandService.java:57-83` |
| 7 | Sale 상태 변경 | `SaleStatus.SOLD` (결제 성공 여부와 무관, 검증 없음) | `D/payment/service/command/PaymentCommandService.java:383-411` (:391 findByOrderId, :404 `sale.updateStatus(SOLD)`) |
| 8 | OrderBid 생성·저장 | `BidStatus.MATCHED`, `isInstantPurchase=true`, order·sale 연결 | `OrderBidCommandService.java:189-206`, `D/order/entity/OrderBid.java:60-82,97-99` |

- 새로 생기는 엔티티: Order, OrderItem, OrderShipment, Payment(Card/Account/General 중 하나), Notification(구매자·판매자 각 1건), OrderBid. SaleBid·Sale은 기존 엔티티.
- 6~7번 주의: 7번 시점에 `order.getOrderBid()`는 아직 null(OrderBid는 8번에서 생성)이라 `SaleBid` 경로로 Sale을 찾는다(`PaymentCommandService.java:388-411`).
- **Order 상태는 PENDING_PAYMENT에서 바뀌지 않는다.** 즉시 구매 경로에는 `PAYMENT_COMPLETED` 등으로 바꾸는 코드가 없다(그 전환은 Kafka 소비자 `OrderEventConsumer#processCompleteOrder`에만 있음; `nav/flow-trade.md` 8번 표 참고).
- 구매 쪽 `OrderBid.assignOrder`가 `order.assignOrderBid`를 통해 Order↔OrderBid 양방향 연결을 만든다(`OrderBid.java:78-80`).

## 3. 결제 수단별 결과 / 끝까지 성공하는가 / 카드 실패 시

분기: `PaymentCommandService#processPayment` switch (`PaymentCommandService.java:67-80`), DTO 타입으로 결정(`D/payment/dto/PaymentRequestDto.java:74-86`).

- **GENERAL(일반 결제)**: 클라이언트가 준 `impUid`만 검사하고(:297-300) PG 호출 없이 `PAID` + 성공 처리(:313-314, 저장 :316). 끝까지 성공한다.
- **CARD(카드)**: 저장된 PaymentInfo 조회(:166) → `PortOneApiClient#processCardPayment`(:179) 동기 호출(`D/payment/portone/PortOneApiClient.java:229-`). 응답을 CardPayment로 저장(:187-208). `status`가 문자열 `"success"`일 때만 `PAID`+성공(:203-206). 그렇지 않으면 Payment는 기본값 `PENDING`(`D/payment/entity/Payment.java:44`)·isSuccess=false로 저장된다. PortOne 실제 응답의 status는 보통 `"paid"`이므로(외부 지식, 코드 상 비교 대상은 `"success"`) 정상 결제도 PENDING으로 남을 가능성이 높다. 이 경우에도 예외가 아니므로 아래 7번처럼 Sale은 SOLD가 되고 흐름은 성공으로 끝난다.
- **ACCOUNT(계좌이체)**: Payment를 만들고 `updateStatus(PENDING)`을 호출하는데(`:260`) 이미 PENDING이라 `canTransitionTo(PENDING)`이 false(`D/payment/entity/PaymentStatus.java` PENDING 분기는 PAID만 허용, `Payment.java:70-76`) → `IllegalStateException` → `catch (Exception)`(:274-277)에서 `PaymentProcessingException`으로 변환 → `createInstantOrder`가 `OrderPaymentProcessingFailedException`으로 변환(`OrderCommandService.java:305-309`). **계좌이체 즉시 구매는 항상 실패**하고 전체 트랜잭션이 롤백된다. (은행명 검증 `validateBank`는 앞에서 통과해야 하며 `Bank` enum에 없으면 :244-248에서 먼저 실패.)
- **결제 대행사가 카드 결제를 실패로 응답**: HTTP≠200이거나 `code`≠0이면 `PaymentProcessingException`을 던진다(`PortOneApiClient.java:267-273`). `@Retryable`은 `PaymentApiException`만 대상이라(:224-228) 이 예외는 재시도되지 않는다(통신 오류 `RestClientException`만 `PaymentApiException`으로 변환되어 최대 3회 재시도, :290-292 부근). 예외는 `processPayment`(:89-94)·`createInstantOrder`(:305-309)를 거쳐 `OrderPaymentProcessingFailedException` → `OrderBidCommandService#handleOrderBidCreationException`(:145-147, :212-218)로 전파된다. `@Transactional` 메서드가 RuntimeException으로 종료되므로 **Order·OrderItem·OrderShipment·SaleBid 매칭·창고 상태 변경이 모두 롤백**되고, OrderBid는 생성되지 않으며 Sale도 SOLD가 되지 않는다. 클라이언트는 에러 응답을 받는다(성공 응답 없음).
- 요약: 끝까지 성공하는 경우는 GENERAL, CARD(PG 응답 code=0)뿐이며 ACCOUNT는 항상 실패. 성공해도 Order는 PENDING_PAYMENT로 남는다.

## 4. 알림

- 발송 위치: `PaymentCommandService#notifyUsersAndUpdateSaleStatus` → `sendNotifications` (`PaymentCommandService.java:383-423`, 알림 본문 :433-465 부근), 결제 처리 직후 같은 트랜잭션에서 동기 호출(`:83`). 예외는 삼켜 로그만 남긴다(:416-420 및 sendNotifications의 catch).
- 구매자: "결제가 완료되었습니다. 주문 ID: {orderId}" (category SHOPPING, type BID).
- 판매자(`sale.getSeller()`): "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}" (SHOPPING, BID).
- 전달 방식: `NotificationCommandService#createNotification`(`D/notification/service/command/NotificationCommandService.java:44-67`)가 DB에 먼저 저장하고, 수신자가 Redis에 접속 키가 있을 때만(`:303-306` `hasKey`) STOMP `convertAndSendToUser(email, WEBSOCKET_DESTINATION, ...)`(:309-313)로 푸시한다(`/user/{email}/queue/notifications`). 접속 중이 아니면 저장만 되고 추후 조회로 확인한다.
- 알림은 결제 성공 여부와 무관하게(카드가 PENDING으로 남아도) 보내진다. 단 결제가 예외로 실패하면 알림 코드에 도달하지 않거나, 도달했더라도 트랜잭션 롤백으로 DB 알림도 사라진다(이미 전송된 WebSocket 메시지는 취소되지 않음).
- Kafka `notification-topic`·`OrderEventConsumer`의 알림은 즉시 구매 경로에서 쓰이지 않는다.

## 5. 최종 주문 상태 / 창고 보관 선택 시

- 최종 Order 상태: **`PENDING_PAYMENT`** (`OrderCommandService.java:244`, 이후 변경 코드 없음). 결제가 성공했어도 `PAYMENT_COMPLETED`/`PREPARING`으로 바뀌지 않는다. 함께 바뀌는 것은 SaleBid=MATCHED, OrderBid=MATCHED, Sale=SOLD, OrderShipment=PENDING, Payment(GENERAL=PAID / CARD=조건부 PAID 또는 PENDING)이다.
- 구매자가 "창고 보관"을 선택한 경우: **아무 차이도 없다.** 컨트롤러가 `requestDto.isWarehouseStorage()`를 서비스로 넘기지만(`OrderBidCommandController.java:101-106`, `OrderBidCommandService.java:133-139`) `createInstantOrder` 본문에서 `isWarehouseStorage` 파라미터는 한 번도 사용되지 않는다(파라미터 선언 `OrderCommandService.java:221` 외 참조는 `sale.isWarehouseStorage()` 하나뿐, :292). 즉 구매자용 `WarehouseStorage`(`createOrderStorage`)가 생성되지 않고 Order에도 창고 보관 정보가 연결되지 않으며 Order→`IN_WAREHOUSE`/`COMPLETED` 전환도 없다. (그런 처리는 Kafka 경로 `OrderEventConsumer#processCompleteOrder`에만 있음.)
- 창고 관련으로 실제 달라지는 것은 **판매자 쪽 Sale이 창고 보관(`sale.isWarehouseStorage()`)인 경우**뿐이며 그 판매자의 WarehouseStorage 상태가 `ASSOCIATED_WITH_ORDER`로 바뀐다(`OrderCommandService.java:289-294`). 이후 구매자 송장 등록 시 `SOLD`로 바뀐다(`D/warehouseStorage/.../WarehouseStorageCommandService.java:150-`).

## 부가 관찰 (의도 vs 실제)
- 응답 메시지 "즉시 구매가 성공적으로 처리되었습니다."(`OrderBidCommandController.java:109`)와 달리 주문은 결제 대기 상태로 남는다.
- SaleBid가 이미 MATCHED인지/중복 구매인지 확인하는 검증이 없다(`getSaleBidAndValidate` 는 null 검사만, `OrderBidCommandService.java:172-184`).
