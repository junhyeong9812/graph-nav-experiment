# 즉시 구매 처리 흐름 (POST /order-bids/instant)

경로 약어: `OBC` = `src/main/java/com/fream/back/domain/order/controller/command/OrderBidCommandController.java`,
`OBS` = `.../domain/order/service/command/OrderBidCommandService.java`,
`OCS` = `.../domain/order/service/command/OrderCommandService.java`,
`PCS` = `.../domain/payment/service/command/PaymentCommandService.java`,
`PORT` = `.../domain/payment/portone/PortOneApiClient.java`.

## 1. API, 처리 단계, 동기/비동기, 응답 ID

- 진입점: `POST /order-bids/instant` (`@RequestMapping("/order-bids")` `OBC:22`, `@PostMapping("/instant")` `OBC:89`). 본문은 `InstantOrderRequestDto`(saleBidId, addressId, warehouseStorage, paymentRequest) — `src/main/java/com/fream/back/domain/order/dto/InstantOrderRequestDto.java`.
- 처리 단계 (모두 한 요청 스레드, 한 `@Transactional` 안):
  1. 컨트롤러가 이메일을 추출하고 `paymentRequest`에 `userEmail`을 넣고 `orderId=null`로 초기화 (`OBC:92`, `OBC:98`, `OBC:119-123`).
  2. `OrderBidCommandService#createInstantOrderBid` (`OBS:118-149`): 입력 검증(`OBS:154-167`) → 구매자 조회(`OBS:126`) → SaleBid·Sale 조회/검증(`OBS:129`, `OBS:172-184`; SaleBid 상태가 PENDING인지는 검사하지 않음) → `OrderCommandService#createInstantOrder` 호출(`OBS:133`) → `OrderBid` 생성·저장(`OBS:142`, `OBS:189-207`).
  3. `OrderCommandService#createInstantOrder` (`OCS:219-319`): 주소 조회(`OCS:238`) → Order 생성·저장(`OCS:241-247`) → `paymentRequest.setOrderId`(`OCS:250`) → OrderItem 생성(`OCS:255-256`) → OrderShipment 생성(`OCS:264-271`) → SaleBid에 order 연결 + MATCHED + `flush`(`OCS:279-283`) → 판매자가 창고 보관 건이면 창고 상태 변경(`OCS:291-294`) → 결제 처리(`OCS:305`).
  4. 결제 처리 내부: `PaymentCommandService#processPayment`(`PCS:57-107`)가 결제 수단별 Payment를 만들고(`PCS:67-80`) 알림 발송 + Sale을 SOLD로 변경(`PCS:83`, `PCS:383-426`).
- 동기 처리다. 이 경로에서는 Kafka 이벤트를 발행하지 않는다. (Kafka 비동기는 별도 경로인 `POST /orders/{orderId}/process-payment-shipment`가 `orderEventProducer.sendOrderProcessingEvent`를 쓰는 것뿐 — `src/main/java/com/fream/back/domain/order/controller/command/OrderCommandController.java:42-54`.) 결제 대행사(PortOne) 호출도 같은 스레드에서 동기 호출한다(`PCS:179`, `PORT:266`).
- 응답 ID: **OrderBid의 ID**다. 서비스가 반환한 `OrderBid`에서 `.getId()`를 꺼낸다(`OBC:101-107`). 변수명이 `orderId`, javadoc이 "생성된 주문 ID"(`OBC:82`)라고 하지만 실제 값은 `OrderBid.id`이며 `Order.id`가 아니다.

## 2. 새로 만들어지는 엔티티와 상태 변화 순서

생성 순서와 직후 상태:

| 순서 | 동작 | 직후 상태 | 근거 |
|---|---|---|---|
| 1 | `Order` 저장 | `Order.status = PENDING_PAYMENT`, totalAmount = SaleBid.bidPrice | `OCS:241-247` |
| 2 | `OrderItem` 저장 (수량 1, 가격 = bidPrice) | — | `OCS:255-256`, `src/main/java/com/fream/back/domain/order/service/command/OrderItemCommandService.java` `createOrderItem` |
| 3 | `OrderShipment` 저장 (주소는 addressId로 조회한 값) | `ShipmentStatus.PENDING` | `OCS:264-271`, `src/main/java/com/fream/back/domain/shipment/service/command/OrderShipmentCommandService.java` `createOrderShipment` |
| 4 | 기존 `SaleBid`에 order 연결 | `SaleBid.status = MATCHED` (`assignOrder`가 MATCHED 세팅, 이어서 `updateStatus(MATCHED)`) | `OCS:279-280`, `src/main/java/com/fream/back/domain/sale/entity/SaleBid.java:159-162` |
| 5 | (판매자가 창고 보관으로 올린 Sale일 때만) 기존 `WarehouseStorage` | `ASSOCIATED_WITH_ORDER` | `OCS:291-294`, `src/main/java/com/fream/back/domain/warehouseStorage/service/command/WarehouseStorageCommandService.java:117-134` |
| 6 | `Payment`(Card/Account/General) 저장 | 결제 수단별로 아래 3번 | `PCS:157-333` |
| 7 | 기존 `Sale` 상태 변경 | `Sale.status = SOLD` (생성 시 `PENDING_SHIPMENT`였음 — `src/main/java/com/fream/back/domain/sale/service/command/SaleCommandService.java:108`) | `PCS:404`/`PCS:419`, `src/main/java/com/fream/back/domain/sale/entity/Sale.java:73-75` |
| 8 | `OrderBid` 저장 (구매자, 가격 = SaleBid 가격, sale 연결, `isInstantPurchase=true`) | `OrderBid.status = MATCHED` | `OBS:192-206` |
| 9 | `Notification` 2건 저장 | — | 4번 항목 |

주의할 실제 동작:
- 7번의 Sale SOLD 변경은 `Sale#updateStatus`가 전이 규칙(`SaleStatus#canTransitionTo`)을 검사하지 않고 그냥 대입하므로(`Sale.java:73-75`) `PENDING_SHIPMENT → SOLD`가 막히지 않는다. 규칙상으로는 `PENDING_SHIPMENT`에서 `IN_TRANSIT`만 가능하다(`src/main/java/com/fream/back/domain/sale/entity/SaleStatus.java:93`).
- 알림·Sale 변경 시점(`PCS:83`)에는 아직 `OrderBid`가 없어(`OBS:142`가 더 뒤) `order.getOrderBid()`가 null이므로, `saleBidQueryService.findByOrderId`로 SaleBid → Sale을 찾는다(`PCS:388-406`). 이는 4번에서 `saleBid.assignOrder(order)`+flush를 먼저 해 두었기 때문에 동작한다.
- `OrderStatus`는 이 경로에서 `PENDING_PAYMENT`에서 바뀌지 않는다(5번 참고).
- 요청의 결제 금액(`paidAmount`)이 SaleBid 가격과 같은지는 검증하지 않는다. 검증은 0보다 큰지·orderId·이메일 일치뿐이다(`PCS:117-146`).

## 3. 결제 수단별 결과, 성공 여부, 카드 실패 시

`PaymentRequestDto`는 `paymentType` 속성(CARD/ACCOUNT/GENERAL)으로 하위 DTO가 결정된다(`src/main/java/com/fream/back/domain/payment/dto/PaymentRequestDto.java:20-24`). `Payment` 기본값은 `status=PENDING`, `isSuccess=false`(`src/main/java/com/fream/back/domain/payment/entity/Payment.java:39`, `:44`).

| 수단 | 동작 | Payment 결과 | 근거 |
|---|---|---|---|
| CARD | 저장된 PaymentInfo로 PortOne 카드 결제 API를 동기 호출. 응답 `status`가 `"success"`일 때만 PAID | 성공: `status=PAID`, `isSuccess=true`, paymentDate 기록. 응답 `status`가 `"success"`가 아니면(예외 없이) `PENDING`/`isSuccess=false` 상태로 저장되고 계속 진행 | `PCS:166-208` |
| ACCOUNT | 은행명만 enum으로 검증(`Bank.valueOf`). 외부 호출 없음 | `status=PENDING`, `isSuccess=false`로 저장. 이 경로에서는 PAID로 바뀌지 않음 | `PCS:236-262`, `PCS:470-488` |
| GENERAL | `impUid`가 비어있지 않은지만 확인. PortOne에 검증 호출 없음 | 즉시 `PAID`, `isSuccess=true` | `PCS:290-316` |

- 끝까지 성공하는가: 예외가 없으면 수단과 무관하게 끝까지 진행되어 HTTP 200 "즉시 구매가 성공적으로 처리되었습니다."가 반환된다(`OBC:109`). 하지만 "결제 완료"까지 간 것은 CARD(성공 응답)와 GENERAL뿐이고, ACCOUNT는 Payment가 PENDING인 채로 Sale이 SOLD가 되고 "결제가 완료되었습니다" 알림이 나간다(`PCS:83`, `PCS:438-443`). Order는 어떤 수단이든 `PENDING_PAYMENT`로 남는다(5번).
- 결제 대행사가 카드 결제를 실패로 응답하면:
  - PortOne 응답 HTTP 상태가 200이 아니거나 최상위 `code != 0`이면 `PaymentProcessingException`을 던진다(`PORT:270-275`). 이는 `PCS:179-184`(PaymentException은 그대로 전파)와 `processPayment`의 catch(`PCS:89-94`)를 거쳐 `OCS:305-309`에서 `OrderPaymentProcessingFailedException`으로 감싸지고 `OCS:312-314`에서 그대로 재던져진다. `OBS:145-146`도 `OrderException`이므로 그대로 던진다. 전체가 한 `@Transactional`(`OBS:118`, `OCS:219`, `PCS:37`)이므로 RuntimeException(`GlobalException` 계열)으로 롤백되어 Order, OrderItem, OrderShipment, SaleBid 매칭, 창고 상태 변경, CardPayment가 모두 취소된다. 즉 Order·OrderBid는 남지 않고 Sale도 SOLD가 되지 않으며 알림도 저장되지 않는다. 클라이언트에는 오류 응답이 간다.
  - 반대로 `code == 0`인데 내부 `response.status`가 `"success"`가 아닌 경우(예: 카드사 거절이 `status=failed`로 오는 경우)는 예외가 아니라 `PENDING` 상태의 CardPayment가 저장되고, 이후 단계(알림·Sale SOLD·OrderBid MATCHED)가 그대로 진행되어 성공 응답이 반환된다(`PCS:203-208`, `PCS:83`). 이때는 `PaymentStatus.FAILED`로 기록되지도 않는다.

## 4. 알림 수신자, 시점, 방식

- 수신자 2명 (`PCS:434-456`):
  - 구매자(`order.getUser()`): "결제가 완료되었습니다. 주문 ID: {orderId}" (`PCS:438-443`)
  - 판매자(`sale.getSeller()`): "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}" (`PCS:449-454`)
  - 둘 다 `NotificationCategory.SHOPPING`, `NotificationType.BID`.
- 시점: 결제 처리 직후, 같은 요청·트랜잭션 안에서 Payment 생성 후 Sale을 SOLD로 바꾸기 직전에 호출한다(`PCS:83`, `PCS:403`/`PCS:416`). 별도 비동기 처리 없음.
- 방식: `NotificationCommandService#createNotification`(`src/main/java/com/fream/back/domain/notification/service/command/NotificationCommandService.java:44-67`)이 DB(Notification 테이블)에 저장하고, 수신자가 WebSocket에 연결돼 있을 때만(Redis 키 `WebSocket:User:{email}`가 존재할 때) STOMP `/queue/notifications`로 실시간 푸시한다(`:303-321`, `:37-38`). 연결이 없으면 저장만 되고 푸시는 생략된다. 알림 생성이나 전송 실패는 `sendNotifications`/`notifyUsersAndUpdateSaleStatus`가 예외를 삼키므로(`PCS:457-461`, `PCS:421-425`) 구매 처리를 막지 않는다. 단, 알림 단계에서 예외가 나면 그 뒤의 `sale.updateStatus(SOLD)`가 실행되지 않고 조용히 지나갈 수 있다(`PCS:403-404`).
- 이 경로에서는 판매 입찰 등록 시의 알림("판매 입찰이 등록되었습니다.")은 이미 별도로 나갔고(`SaleCommandService.java:125-130`), 즉시 구매 시점에 추가 알림은 위 2건뿐이다.

## 5. 최종 주문 상태와 창고 보관 선택 시 차이

- 최종 주문 상태: `Order.status = PENDING_PAYMENT`. 즉시 구매 경로(`OBS:118-149`, `OCS:219-319`, `PCS:57-107`)에서는 어디서도 `Order.updateStatus`를 호출하지 않는다. `PAYMENT_COMPLETED`/`PREPARING`/`IN_WAREHOUSE`/`COMPLETED`로 바꾸는 코드는 `processPaymentAndShipment`(`OCS:162-177`)와 Kafka 소비자(`src/main/java/com/fream/back/domain/order/service/kafka/OrderEventConsumer.java:192-217`)에만 있고, 이는 `/orders/{id}/process-payment-shipment` 경로다. 따라서 응답 메시지는 "성공"이지만 결제가 PAID인 카드/일반 결제여도 Order는 결제 대기로 남는다. 다른 객체의 최종 상태: SaleBid `MATCHED`, OrderBid `MATCHED`(isInstantPurchase=true), Sale `SOLD`, OrderShipment `PENDING`, Payment는 3번 표 참고.
- 구매자가 "창고 보관"(`warehouseStorage=true`)을 선택한 경우: **아무것도 달라지지 않는다.** 요청의 `isWarehouseStorage`는 컨트롤러 로그(`OBC:94-95`)와 서비스 인자로 전달되지만(`OBC:105`, `OBS:137`) `createInstantOrder` 본문에서는 사용되지 않는다(`OCS:220-319`에 참조 없음). 창고 관련 분기는 구매자의 플래그가 아니라 **판매자의 `Sale.isWarehouseStorage`**를 본다(`OCS:291-294`). 그 경우에만 기존 `WarehouseStorage`가 `ASSOCIATED_WITH_ORDER`로 바뀌고, 해당 WarehouseStorage가 없으면 예외로 전체가 롤백된다(`WarehouseStorageCommandService.java:127`, `WarehouseStorageQueryService.java:30-31`). 구매자의 선택으로 `WarehouseStorage`를 만들고 `IN_WAREHOUSE`→`COMPLETED`로 바꾸는 로직은 `processPaymentAndShipment`(`OCS:163-172`)에만 있으며 즉시 구매에서는 실행되지 않는다. 배송 정보(OrderShipment)는 창고 보관 여부와 상관없이 항상 생성된다(`OCS:264-271`).
