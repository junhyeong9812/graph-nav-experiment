# 구매자 배송: 운송장 등록 → 배송 완료

경로 약어: `S` = `src/main/java/com/fream/back`

## 1. 운송장 등록 요청

### 1-1. 진입 API
- `PATCH /shipments/order/{shipmentId}/status`, body `OrderShipmentRequestDto`(courier, trackingNumber). 클래스 매핑 `S/domain/shipment/controller/command/OrderShipmentCommandController.java:20`, 메서드 `:33-45`. 컨트롤러는 `OrderShipmentCommandService.updateTrackingInfo(shipmentId, courier, trackingNumber)`를 호출하고 성공이면 `200 OK`(body 없음)를 돌려준다(`:45-48`).
- 참고: 같은 컨트롤러의 `POST /shipments/order/{shipmentId}/check-status`(`OrderShipmentCommandController.java:58` 부근)는 별도 경로다. 운송장 등록 후 CJ 조회까지 한 번에 하며 서비스 `updateAndCheckShipmentStatus`(`S/domain/shipment/service/command/OrderShipmentCommandService.java:451-519`)를 쓴다.

### 1-2. 의도된 상태 변경 순서와 알림 (`OrderShipmentCommandService.updateTrackingInfo`, `:238-303`)
1. courier/trackingNumber가 비어 있으면 `TRACKING_INFO_REQUIRED` (`:243-246`).
2. `OrderShipment` 조회 후 `shipment.updateTrackingInfo(courier, trackingNumber)` (`:249-256`). 택배사·운송장 번호를 넣고 배송 상태를 곧바로 `IN_TRANSIT`으로 세팅한다(`S/domain/shipment/entity/OrderShipment.java:41-45`). 상태 전이 검증은 없다.
3. `order.updateStatus(OrderStatus.IN_TRANSIT)` (`:259-260`). 주문 상태를 바꾼다.
4. 구매자에게 알림 1건 "상품이 출발하였습니다. 주문 ID: …" (`:265-271`).
5. `updateSaleStatusToSold(orderId)` (`:276`). Sale을 `SOLD`로 바꾸고 판매자에게 "상품이 성공적으로 판매 완료되었습니다" 알림을 보낸다(`:111-183`). 창고 보관 상품이면 창고 상태도 바꾼다(`:126-129`, `:279-286`).
6. `updateOrderAndSaleBidStatusToCompleted` (`:289`, 본체 `:412-440`). OrderBid와 SaleBid가 `MATCHED`이면 `COMPLETED`로 바꾼다. 이 단계는 예외를 삼킨다(`:436-439`).
- 즉 의도는 `OrderShipment: IN_TRANSIT → Order: IN_TRANSIT → (Sale: SOLD, 창고) → OrderBid/SaleBid: COMPLETED` 순서이고, 알림은 구매자 1건(출발)과 판매자 1건(판매 완료)이다. 주문 입찰·판매 입찰·Sale이 "배송 완료"가 아니라 "운송장 등록" 시점에 완료 처리되도록 짜여 있다.

### 1-3. 실배송 일반 구매 입찰 주문에서 끝까지 성공하나? → 실패한다
- 결제·배송 처리 후 주문 상태는 `PREPARING`이다. 구매 입찰 주문의 결제·배송 처리 API(`S/domain/order/controller/command/OrderCommandController.java:43-54`)는 Kafka로 이벤트를 발행하고, 컨슈머 `OrderEventConsumer.processCompleteOrder`가 처리한다. 실제 배송(창고 보관 아님)이면 `PAYMENT_COMPLETED → PREPARING`까지만 간다(`S/domain/order/service/kafka/OrderEventConsumer.java:195`, `:215-218`). 동기 버전 `OrderCommandService.processPaymentAndShipment`도 같다(`S/domain/order/service/command/OrderCommandService.java:174-177`).
- `OrderStatus`의 허용 전이는 `PREPARING → {IN_WAREHOUSE, SHIPMENT_STARTED}`뿐이고 `IN_TRANSIT`은 `SHIPMENT_STARTED`에서만 갈 수 있다(`S/domain/order/entity/OrderStatus.java:87-90`). 그런데 코드는 `SHIPMENT_STARTED`를 거치지 않고 `PREPARING → IN_TRANSIT`을 시도한다.
- 실패 지점: `updateTrackingInfo`의 `order.updateStatus(OrderStatus.IN_TRANSIT)` (`OrderShipmentCommandService.java:260`). `Order.updateStatus`가 `InvalidOrderStatusException`("상태 전환이 허용되지 않습니다: PREPARING -> IN_TRANSIT")을 던진다(`S/domain/order/entity/Order.java:113-121`).
- 이 예외는 `ShipmentException`이 아니므로 `catch (Exception e)`(`OrderShipmentCommandService.java:295-302`)에 걸려 `ShipmentException(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생…")`로 감싸져 던져진다.
- 저장되는 것: 없음. 메서드는 `@Transactional`(`:238`)이고 RuntimeException이 밖으로 나가므로 롤백된다. 2번 단계에서 메모리상 바꾼 shipment의 courier/trackingNumber/`IN_TRANSIT`도 DB에 남지 않는다. shipment는 `PENDING`, 운송장 null 그대로다. 4번 알림은 3번에서 이미 예외가 나 생성되지 않는다.
- 응답: `GlobalExceptionHandler.handleShipmentException`이 `errorCode`의 상태/메시지로 응답한다(`S/global/exception/GlobalExceptionHandler.java:459-472`). `SHIPMENT_NOT_FOUND`는 코드 `S001`, 메시지 "배송 정보를 찾을 수 없습니다.", HTTP 404이다(`S/domain/shipment/exception/ShipmentErrorCode.java:12`). 응답 본문에는 예외 메시지(상태 전환 오류)가 아니라 에러코드의 고정 메시지가 들어간다. 즉 404인데 실제 원인은 주문 상태 전이 위반이다.
- 가려진 두 번째 결함: 설령 order 전이를 통과해도 5번 `updateSaleStatusToSold`에서 `saleBidQueryService.findByOrderId`는 SaleBid가 없으면 null이 아니라 `IllegalArgumentException`을 던진다(`S/domain/sale/service/query/SaleBidQueryService.java:26-29`). 판매자가 아직 붙지 않은 일반 구매 입찰 주문은 SaleBid가 없으므로, `:117`의 null 체크는 도달하지 못하고 같은 `catch (Exception)`으로 빠져 실패한다.

## 2. 배송 완료 감지

### 2-1. 누가·언제·어떻게
- 사용자 요청이 아니라 스케줄러가 감지한다. `ShipmentBatchScheduler.scheduleShipmentStatusJob`이 `@Scheduled(cron = "0 0 */6 * * *")`로 6시간마다(매일 00·06·12·18시 정각) Spring Batch Job `updateShipmentStatusesJob`을 timestamp 파라미터로 실행한다(`S/global/config/ShipmentBatchScheduler.java:34-40`). 예외는 `printStackTrace()`로만 처리한다(`:41-43`).
- Job은 `S/domain/shipment/config/UpdateShipmentStatusesJobConfig.java:353-358`, Step은 `:361-380`이다. chunk 50(`:349`), `faultTolerant().skip(Exception.class).skipLimit(50)`(`:373-375`)이다.
- 대상 조회(Reader): `SELECT s FROM OrderShipment s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL` (`:393`). `PENDING`, `DELIVERED` 및 운송장 없는 배송은 읽지 않는다.
- 실제로 실행되는 처리 코드: Step이 `new ShipmentItemProcessor(playwrightBrowserManager(), notificationService, orderService)`를 processor로 등록한다(`UpdateShipmentStatusesJobConfig.java:367-371`). 그러므로 실행되는 쪽은 `S/domain/shipment/config/ShipmentItemProcessor.java:128-229`다.
  - 같은 파일 `:404-475`의 `shipmentItemProcessor()` @Bean은 Step에서 쓰이지 않는다(참조 없음). `:484-518`의 `parseCjLogisticsStatus`도 호출처가 없다.
  - `OrderShipmentCommandService.updateShipmentStatuses()`(`S/domain/shipment/service/command/OrderShipmentCommandService.java:309-391`)도 호출하는 곳이 없어 실행되지 않는다. 이 메서드는 `completeOrder`가 아닌 직접 `order.updateStatus(COMPLETED)`를 하는 별개 구현이다.
  - 조회 방식: `PlaywrightBrowserManager`로 페이지를 열어 `https://trace.cjlogistics.com/next/tracking.html?wblNo=<운송장>`로 이동하고(`ShipmentItemProcessor.java:100`, `:144-155`), `tbody#statusDetail tr`을 기다려(`:159`) 마지막 행 5번째 `td` 텍스트를 상태 문자열로 쓴다(`:239-263`). Step 시작/종료 시 브라우저를 열고 닫는다(`S/domain/shipment/config/BrowserManageStepListener.java:60-70`).

### 2-2. 택배사 상태 문자열 → 내부 상태 (`ShipmentItemProcessor.java:292-298`)
- `"배송완료"` → `DELIVERED`, `"배송출발"` → `OUT_FOR_DELIVERY`, 그 외 모든 문자열(집화, 간선상차 등 포함) → `IN_TRANSIT`.
- 매핑 결과가 현재 상태와 같으면 아무것도 하지 않고 반환한다(`:173-177`).

## 3. 배송 완료 판정 이후 (`ShipmentItemProcessor.java:180-189`, 성공 가정)
1. `orderShipment.updateStatus(DELIVERED)` (`:185`). `IN_TRANSIT → DELIVERED`, `OUT_FOR_DELIVERY → DELIVERED`는 허용된다(`S/domain/shipment/entity/ShipmentStatus.java:16-28`). 엔티티 변경은 Step writer `JpaItemWriter`가 chunk 커밋 시 반영한다(`UpdateShipmentStatusesJobConfig.java:372`, `:537-544`).
2. `orderService.completeOrder(orderId)` (`ShipmentItemProcessor.java:188` → `OrderShipmentCommandService.java:190-229`).
   - `OrderBid` 조회(`:196-197`) → `order.updateStatus(COMPLETED)` (`:204`) → `updateSaleStatusToSold` (`:208`) → 구매자 알림 "[completeOrder] 주문이 완료 처리되었습니다. 주문 ID: …" 1건 (`:211-217`).
   - `updateSaleStatusToSold`(`:111-183`)는 SaleBid의 Sale(또는 OrderBid의 Sale)이 `SOLD`로 전이 가능할 때만 `SOLD`로 바꾸고 판매자에게 알림 1건을 보낸다(`:119-141`, `:156-172`). 창고 보관이면 창고 상태 갱신(`:126-129`).
3. `notificationService.notifyShipmentCompleted(order)` (`ShipmentItemProcessor.java:189`). 구매자에게 "[배송 완료] 상품이 배송 완료되었습니다. 주문 ID: …" 1건(`S/domain/notification/service/command/NotificationCommandService.java:219-234`).
- 알림 건수: 구매자 2건(completeOrder 알림 + 배송 완료 알림). 판매자는 Sale이 아직 `SOLD`가 아닐 때만 1건(`OrderShipmentCommandService.java:131-138`)이고, 이미 `SOLD`이면 0건이다.
- 주문 입찰·판매 입찰 상태: 배치 경로(`completeOrder`)는 OrderBid/SaleBid 상태를 바꾸지 않는다. `updateOrderAndSaleBidStatusToCompleted`는 운송장 등록 경로(`:289`)에서만 호출된다. 따라서 배송 완료 후에도 둘 다 `MATCHED` 그대로다. 바뀌는 것은 Order(`COMPLETED`), OrderShipment(`DELIVERED`), 조건부로 Sale(`SOLD`)이다.
- `OUT_FOR_DELIVERY`로 판정되면 shipment만 `OUT_FOR_DELIVERY`로 바꾸고 알림은 없다(`ShipmentItemProcessor.java:191-194`). 기타 문자열은 `IN_TRANSIT`으로 바꾼다(`:195-198`).

## 4. 주문 종류별 차이
공통 전제: 배치 대상이 되려면 shipment가 `IN_TRANSIT`/`OUT_FOR_DELIVERY`여야 한다. 일반 운송장 등록 API는 두 주문 모두 1-3처럼 주문 전이에서 막히므로, 실제로는 `check-status` 경로(`OrderShipmentCommandService.java:473`은 주문 상태를 건드리지 않고 shipment만 `IN_TRANSIT`으로 세팅)로만 배치 대상이 될 수 있다.

### (a) 실배송 일반 구매 입찰 주문: 끝까지 진행되지 않는다
- 주문 상태는 `PREPARING`(위 1-3). `completeOrder`의 `order.updateStatus(COMPLETED)`(`OrderShipmentCommandService.java:204`)는 `PREPARING → COMPLETED`가 허용되지 않아(`OrderStatus.java:87`) `InvalidOrderStatusException`이 난다.
- `completeOrder`의 `catch (Exception)`(`:221-228`)이 `ShipmentException(ORDER_NOT_FOUND_FOR_SHIPMENT)`로 감싸 던지고, `ShipmentItemProcessor`가 그대로 다시 던진다(`:205-217`).
- 결과: 배송 완료 알림(`:189`)은 실행되지 않아 알림 0건, Order는 `PREPARING` 유지, OrderBid/SaleBid 변경 없음. chunk 트랜잭션이 롤백되어 shipment의 `DELIVERED` 변경도 저장되지 않고 `IN_TRANSIT`으로 남는다. 다음 6시간 주기에 다시 조회되고 같은 실패가 반복된다.
- 설령 주문이 `IN_TRANSIT`이어도 SaleBid가 없으면 `updateSaleStatusToSold`가 `IllegalArgumentException`을 던져 같은 방식으로 실패한다(`SaleBidQueryService.java:26-29`, `OrderShipmentCommandService.java:116`).

### (b) 즉시 구매로 만들어진 주문: 끝까지 진행된다
- 즉시 구매 주문은 `PENDING_PAYMENT`로 생성되고(`S/domain/order/service/command/OrderCommandService.java:244`), 이후 결제 처리(`PaymentCommandService`)는 주문 상태를 바꾸지 않는다(`PaymentCommandService.java` 내 `OrderStatus` 변경 없음). 따라서 `PENDING_PAYMENT`가 유지된다. 이 상태는 `COMPLETED`로 전이가 허용된다(`OrderStatus.java:85`).
- 즉시 구매 생성 시 `saleBid.assignOrder(order)`(`OrderCommandService.java:279`)와 OrderBid 생성(`S/domain/order/service/command/OrderBidCommandService.java:189-207`, 상태 `MATCHED`, order 연결)으로 SaleBid/OrderBid 조회가 성공한다.
- 결제 시 `notifyUsersAndUpdateSaleStatus`가 이미 Sale을 `SOLD`로 바꿨다(`PaymentCommandService.java:383-425`, 특히 `:419`). `Sale.updateStatus`는 전이 검증이 없다(`S/domain/sale/entity/Sale.java:73-75`). 그래서 `updateSaleStatusToSold`에서 `SOLD.canTransitionTo(SOLD)`는 false라 Sale 변경·판매자 알림·창고 갱신을 건너뛴다(`SaleStatus.java:271`, `OrderShipmentCommandService.java:119`, `:156`).
- 결과: OrderShipment `DELIVERED`, Order `COMPLETED`, 구매자 알림 2건([completeOrder] + [배송 완료]), 판매자 추가 알림 0건(결제 시점에 이미 받음). OrderBid/SaleBid는 `MATCHED` 그대로다.
- 단, 이 주문이 배치 대상이 되려면 shipment가 `IN_TRANSIT`이어야 한다. PATCH 운송장 등록은 `PENDING_PAYMENT → IN_TRANSIT`이 허용되지 않아(`OrderStatus.java:85`) 1-3과 같은 방식으로 실패한다. 즉시 구매 주문의 shipment도 `check-status` 경로로만 `IN_TRANSIT`이 된다.

## 5. 실패 처리
- 처리 중 예외는 `ShipmentItemProcessor`에서 `ShipmentException`(비 Shipment 예외는 `EXTERNAL_TRACKING_SERVICE_ERROR`로 래핑)으로 다시 던져진다(`ShipmentItemProcessor.java:205-217`). 운송장 null/빈 값도 `TRACKING_NUMBER_INVALID`를 던진다(`:133-136`).
- Step은 `faultTolerant().skip(Exception.class).skipLimit(50)`이다(`UpdateShipmentStatusesJobConfig.java:373-375`). 실패한 건은 skip되고 `shipmentSkipListener.onSkipInProcess`가 에러 로그만 남긴다(`:549-565`).
- 해당 chunk 트랜잭션은 롤백되어, 실패한 건의 변경(메모리상 `DELIVERED`)과 같은 트랜잭션에서 이미 처리한 `completeOrder`(주문 변경·알림 insert)가 취소된다. 실패 건은 DB에서 `IN_TRANSIT`/`OUT_FOR_DELIVERY` 그대로이고 다음 6시간 주기에 다시 조회된다.
- 나머지 건: Spring Batch 내결함성 Step이 chunk를 개별 항목 단위로 다시 처리해 실패 항목만 제외하고 정상 항목은 커밋한다. 이 재처리 과정에서 정상 항목의 CJ 조회가 한 번 더 실행될 수 있다. 한 건이 실패해도 Job 전체가 중단되지 않는다.
- skip이 50건을 넘으면 Step이 실패한다(`:350`, `:375`). 이때 스케줄러는 예외를 `printStackTrace()`만 하고 삼킨다(`ShipmentBatchScheduler.java:41-43`).
- 주의: Reader가 오프셋 기반 `JpaPagingItemReader`(`:387-395`)인데 처리하면 상태가 조회 조건에서 빠져나가므로, 많은 건이 한 번에 완료되면 이후 페이지의 일부가 해당 실행에서 건너뛰어질 수 있다(다음 주기에 잡힌다).
