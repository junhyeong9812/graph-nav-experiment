# 즉시 구매 처리 흐름 (ANSWER)

경로 약칭: `D` = `src/main/java/com/fream/back/domain`, `G` = `src/main/java/com/fream/back/global`.

## 1. 진입 API, 처리 단계, 동기/비동기, 응답 ID

**API**: `POST /order-bids/instant` (prod nginx가 `/api`를 떼므로 매핑에 `/api` 없음)
- 클래스 매핑 `@RequestMapping("/order-bids")`: `D/order/controller/command/OrderBidCommandController.java:22`
- 메서드 `createInstantOrderBid`, 본문 `InstantOrderRequestDto`(saleBidId, addressId, warehouseStorage, paymentRequest): `OrderBidCommandController.java:89-90`, `D/order/dto/InstantOrderRequestDto.java:20-29`

**처리 단계 (모두 한 요청 스레드, 하나의 `@Transactional` 안에서 동기 실행)**
1. 컨트롤러가 현재 사용자 email 추출 → `paymentRequest.userEmail=email`, `orderId=null` 로 보강: `OrderBidCommandController.java:92`, `:98`, `:119-123`
2. `OrderBidCommandService#createInstantOrderBid` (`@Transactional`): `D/order/service/command/OrderBidCommandService.java:118-120`
   - 입력 검증(email/saleBidId/addressId/paymentRequest null 검사): `OrderBidCommandService.java:123`, `:154-167`
   - 구매자 조회(`userQueryService.findByEmail`): `:126`
   - SaleBid·Sale 조회 및 null 검증: `:129-130`, `:172-184`
3. `OrderCommandService#createInstantOrder` (`@Transactional`): `D/order/service/command/OrderCommandService.java:219-221`
   1. 배송지 조회 `addressQueryService.getAddress`: `OrderCommandService.java:237`
   2. Order 저장 (totalAmount = saleBid.bidPrice, `PENDING_PAYMENT`): `:240-247`
   3. `paymentRequest.setOrderId(order.getId())`: `:250`
   4. OrderItem 생성: `:255-256`
   5. OrderShipment 생성(주소록의 수령인/연락처/우편번호/주소): `:264-271`
   6. SaleBid에 order 연결 + `MATCHED` + `entityManager.flush()`: `:279-283`
   7. Sale이 판매자 창고보관이면 창고 상태 `ASSOCIATED_WITH_ORDER`: `:291-293`
   8. 결제 `paymentCommandService.processPayment(order, buyer, paymentRequest)`: `:305`
4. 결제 후 `notifyUsersAndUpdateSaleStatus`에서 구매자/판매자 알림 + Sale→SOLD: `D/payment/service/command/PaymentCommandService.java:83`, `:383-426`
5. `OrderBid` 생성(`MATCHED`, order·sale 연결, `markAsInstantPurchase`) 후 저장: `OrderBidCommandService.java:142`, `:189-207`
6. 컨트롤러가 200 OK 와 ID를 반환: `OrderBidCommandController.java:101-109`

**동기/비동기**: 완전 동기이다. 이 경로에는 Kafka 발행이 없다. `OrderEventProducer`(order-processing-topic)를 쓰는 것은 `/orders/{id}/process-payment-shipment` 경로이며 즉시 구매와 무관하다. 결제도 요청 스레드에서 PortOne REST를 직접 호출한다(`D/payment/portone/PortOneApiClient.java:229-266`). 응답은 202가 아니라 200 이다.

**응답 ID**: **OrderBid(구매 입찰)의 ID**이다. 변수명은 `orderId`지만 `createInstantOrderBid(...)`가 반환한 `OrderBid`의 `.getId()`를 담는다(`OrderBidCommandController.java:101-107`). 반환된 객체는 `orderBidRepository.save(orderBid)` 결과이다(`OrderBidCommandService.java:206`). Order의 ID가 아니다. 메시지는 "즉시 구매가 성공적으로 처리되었습니다."(`:109`).

## 3. 결제 수단별 결과, 성공 여부, 카드 결제 실패 응답

공통: `processPayment`가 `resolvedPaymentType`으로 분기하고(`PaymentCommandService.java:67-80`), 요청의 orderId/email 일치 및 금액>0 을 검증한다(`:117-146`). 요청 DTO 는 `paymentType` 속성으로 CARD/ACCOUNT/GENERAL 서브타입 역직렬화한다(`D/payment/dto/PaymentRequestDto.java:20-24`).

| 수단 | 동작 | 결과 | 근거 |
|---|---|---|---|
| CARD | 저장된 PaymentInfo 조회 → PortOne `/subscribe/payments/onetime` 호출 → 응답 `status=="success"`이면 `PAID`+isSuccess | 성공 시 알림·Sale SOLD 진행 | `PaymentCommandService.java:166`, `:179`, `:203-208`, `PortOneApiClient.java:229-285` |
| ACCOUNT (계좌이체) | 은행 검증 후 Payment 저장 전에 `updateStatus(PENDING)` 호출. 기본 상태가 이미 `PENDING`이고 `PENDING→PENDING` 전이는 불허라 `IllegalStateException` 발생 → `PaymentProcessingException` 으로 변환되어 **항상 실패** | 즉시 구매 전체 롤백 | `PaymentCommandService.java:243-260`, `:274-277`, `D/payment/entity/PaymentStatus.java:10-21`, `D/payment/entity/Payment.java:66`, `:92-98` |
| GENERAL (일반 결제) | 클라이언트가 준 impUid 가 비어있지 않으면 PG 검증 없이 `PAID`+isSuccess 로 저장 | 성공 | `PaymentCommandService.java:297-316` |

**끝까지 성공하는가**: CARD(PG 성공 응답)와 GENERAL 만 끝까지 성공한다. ACCOUNT 는 구조적으로 항상 실패한다(코드상 `PENDING→PENDING` 전이 금지). 성공하더라도 주문(Order)은 `PENDING_PAYMENT`로 남고 배송은 `PENDING`에 머문다(5번).

**결제 대행사가 카드 결제를 실패로 응답하면** (두 경우가 다르다):
1. **PortOne 응답이 HTTP≠200 이거나 `code != 0`인 경우**: `PaymentProcessingException("카드 결제 요청 실패: ...")` 발생(`PortOneApiClient.java:270-275`) → `createCardPayment`에서 그대로 전파(`PaymentCommandService.java:180-181`, `:218-219`) → `processPayment`가 재던짐(`:89-94`) → `createInstantOrder`가 `OrderPaymentProcessingFailedException`으로 감싸 던짐(`OrderCommandService.java:305-310`) → `OrderBidCommandService`가 `OrderException`이면 그대로 재던짐(`:145-147`, `:212-218`). 하나의 트랜잭션이므로 Order·OrderItem·OrderShipment·SaleBid MATCHED·창고 상태·알림 저장이 모두 롤백된다. OrderBid 는 만들어지지 않는다. 클라이언트는 에러 응답을 받는다(`G/exception/GlobalExceptionHandler.java:348-361`, 단 `OrderException` 계열은 해당 핸들러가 별도로 처리). 이 경우 판매자·구매자에게 가는 알림은 없다.
2. **PortOne 이 `code==0`, HTTP 200 이지만 `response.status`가 "success"가 아닌 경우(예: "failed")**: 코드는 예외를 던지지 않는다. CardPayment 는 기본값(`PENDING`, isSuccess=false)으로 저장되고(`PaymentCommandService.java:203-208`, `Payment.java:61`, `:66`), 이후 흐름이 그대로 진행되어 "결제가 완료되었습니다" 알림 발송 + Sale→SOLD + OrderBid 생성 후 200 OK 를 반환한다(`:83`, `:438-443`, `:404`). 즉 실패 응답이 성공처럼 처리된다. 메서드 이름/주석이 말하는 의도("결제 완료 알림")와 실제 동작이 다른 부분이다.

## 4. 알림 대상, 시점, 전달 방식

- **수신자 2명**
  - 구매자: "결제가 완료되었습니다. 주문 ID: {orderId}" — `PaymentCommandService.java:436-443`
  - 판매자(`sale.getSeller()`): "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}" — `PaymentCommandService.java:447-454`
  - 둘 다 `NotificationCategory.SHOPPING`, `NotificationType.BID`.
- **시점**: 결제 저장 직후, `processPayment` 내부에서 동기 실행(`:83`). Sale→SOLD 변경 직전이다(`:403-404`, `:416-419`). OrderBid 저장(`OrderBidCommandService.java:142`)보다 먼저다.
- **방식**
  1. DB 저장: `notificationRepository.save`(`NotificationCommandService.java:52-53`). 요청 트랜잭션에 참여한다.
  2. 실시간 전송: Redis 키 `WebSocket:User:{email}` 가 있을 때(WebSocket 연결 중)만 STOMP `convertAndSendToUser(email, "/queue/notifications", dto)` → 클라이언트 구독 경로 `/user/{email}/queue/notifications` (`NotificationCommandService.java:37-38`, `:57`, `:303-313`). 연결이 없으면 DB 에만 남는다(`:320-322`). 푸시 실패는 로그만 남긴다(`:315-319`).
  3. Kafka `notification-topic` 은 이 경로에서 사용하지 않는다.
- 알림/Sale 상태 변경 중 예외는 `catch`로 삼켜 로그만 남기고 결제는 성공 처리된다(`PaymentCommandService.java:421-425`, `:457-461`). 예를 들어 `findByOrderId`가 `IllegalArgumentException`을 던지면 알림도 SOLD 변경도 일어나지 않지만 요청은 성공한다.
- 알림은 DB 저장이 트랜잭션에 묶여 있어, 이후 단계가 실패해 롤백되면 DB 알림은 사라진다. 이미 나간 STOMP 푸시는 회수되지 않는다.

## 5. 최종 주문 상태와 창고 보관 선택 시 차이

**최종 상태 (결제까지 성공한 경우)**
- **Order: `PENDING_PAYMENT` 그대로**. `createInstantOrder`에는 Order 상태를 바꾸는 코드가 없다(`OrderCommandService.java:219-311`). `Order#updateStatus`는 호출되지 않는다. `PAYMENT_COMPLETED`/`PREPARING` 으로 바꾸는 코드는 Kafka 경로(`OrderEventConsumer`)에만 있다. 따라서 결제가 `PAID`여도 주문은 결제대기로 남는다.
- OrderShipment `PENDING`, SaleBid `MATCHED`, OrderBid `MATCHED`(`isInstantPurchase=true`), Sale `SOLD`, Payment `PAID`(CARD 성공/GENERAL).

**구매자가 "창고 보관"을 선택한 경우**
- 컨트롤러는 로그에만 `requestDto.isWarehouseStorage()`를 쓰고(`OrderBidCommandController.java:94-95`) 서비스로 전달한다(`:104-105`). `createInstantOrder` 시그니처에 `isWarehouseStorage`가 있으나(`OrderCommandService.java:220-221`) **메서드 본문에서 전혀 사용하지 않는다**. 검증하지 않고 저장도 하지 않는다. 구매자용 WarehouseStorage 를 만드는 `createOrderStorage` 호출은 일반 입찰 경로 `OrderCommandService.java:163-171`에만 있다. 즉시 구매 경로에는 없다.
- 따라서 구매자 선택 여부와 무관하게 결과가 동일하다. Order 상태에 `IN_WAREHOUSE`/`COMPLETED` 전이가 일어나지 않고 구매자 창고 보관 엔티티도 생기지 않는다.
- 실제로 창고 관련 동작을 바꾸는 것은 **판매자 쪽 Sale 의 `isWarehouseStorage`** 이다. 이 경우 해당 Sale 의 WarehouseStorage 상태가 `ASSOCIATED_WITH_ORDER`로 바뀐다(`OrderCommandService.java:291-293`, `WarehouseStorageCommandService.java:117-133`). 상태 전이가 허용되지 않으면 `OrderWarehouseStorageProcessingFailedException`으로 전체가 롤백된다(`OrderCommandService.java:295-301`).
