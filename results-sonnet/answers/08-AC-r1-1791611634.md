# 구매자 배송: 운송장 등록 → 배송 완료 처리 분석

경로 약어: `S` = `src/main/java/com/fream/back/domain/shipment/service/command/OrderShipmentCommandService.java`,
`C` = `src/main/java/com/fream/back/domain/shipment/controller/command/OrderShipmentCommandController.java`,
`P` = `src/main/java/com/fream/back/domain/shipment/config/ShipmentItemProcessor.java`,
`J` = `src/main/java/com/fream/back/domain/shipment/config/UpdateShipmentStatusesJobConfig.java`,
`OS` = `src/main/java/com/fream/back/domain/order/entity/OrderStatus.java`,
`OCS` = `src/main/java/com/fream/back/domain/order/service/command/OrderCommandService.java`.

## 요약

- 운송장 등록 API(`PATCH /shipments/order/{id}/status`)는 주문 상태를 `IN_TRANSIT`으로 바꾸려 하는데, 결제·배송 처리를 마친 주문은 `PREPARING`이고 `PREPARING → IN_TRANSIT` 전이는 허용되지 않는다. 일반 구매 입찰 주문(a)은 등록 단계에서 항상 실패한다.
- 즉시 구매 주문(b)도 `PENDING_PAYMENT → IN_TRANSIT`이 막혀 있어 등록 단계에서 실패한다.
- 실제로 실행되는 주기 처리는 `ShipmentItemProcessor`(Spring Batch, 6시간마다)다. `OrderShipmentCommandService#updateShipmentStatuses`는 호출하는 곳이 없다.

## 1. 운송장 등록 요청

### 1-1. 어느 API로 들어오나

1. `PATCH /shipments/order/{shipmentId}/status`, 본문은 `OrderShipmentRequestDto{courier, trackingNumber}`. 클래스 base path `C:20`, 메서드 `C:33-49`.
2. 컨트롤러는 `OrderShipmentCommandService#updateTrackingInfo(shipmentId, courier, trackingNumber)`를 그대로 호출한다 (`C:41-45`). try/catch가 없어 예외는 `GlobalExceptionHandler`로 간다.

### 1-2. 엔티티 상태 변경 순서와 알림 (코드가 의도한 순서)

`S:238-303` `updateTrackingInfo` (`@Transactional`):

1. courier/trackingNumber가 비어 있으면 `TRACKING_INFO_REQUIRED` 예외 (`S:243-246`).
2. `OrderShipment` 조회, 없으면 `SHIPMENT_NOT_FOUND` (`S:249-253`).
3. **OrderShipment**: `shipment.updateTrackingInfo(courier, trackingNumber)` (`S:256`). 택배사·송장번호를 넣고 상태를 전이 검사 없이 곧바로 `IN_TRANSIT`으로 세팅한다 (`OrderShipment.java:41-45`, `src/main/java/com/fream/back/domain/shipment/entity/OrderShipment.java`).
4. **Order**: `order.updateStatus(OrderStatus.IN_TRANSIT)` (`S:259-260`). 전이 규칙을 검사한다 (`src/main/java/com/fream/back/domain/order/entity/Order.java:113-121`).
5. **알림 1 (구매자)**: "상품이 출발하였습니다. 주문 ID: …" (`S:265-271`).
6. `updateSaleStatusToSold(orderId)` (`S:276`, 본문 `S:111-183`):
   - SaleBid가 있고 Sale이 `SOLD`로 전이 가능하면 `Sale → SOLD` (`S:119-123`).
   - 창고 보관이면 창고 상태를 sold로 바꾼다 (`S:126-129`).
   - **알림 2 (판매자)**: "상품이 성공적으로 판매 완료되었습니다" (`S:132-138`).
   - 이어서 OrderBid 기반 Sale에 대해 같은 처리를 반복한다 (`S:150-180`).
7. SaleBid의 Sale이 창고 보관이면 창고 상태를 한 번 더 갱신한다 (`S:279-286`).
8. `updateOrderAndSaleBidStatusToCompleted(orderId)` (`S:289`, 본문 `S:412-440`): OrderBid가 `MATCHED`이면 `COMPLETED`, SaleBid가 `MATCHED`이면 `COMPLETED`.

즉 코드가 의도한 순서는 OrderShipment(IN_TRANSIT) → Order(IN_TRANSIT) → Sale(SOLD) → OrderBid/SaleBid(COMPLETED)다.

- 알림은 구매자 "출발" 1건, 판매자 "판매 완료" 0~1건이다.
- 이름과 달리 "배송 완료" 시점이 아니라 **운송장 등록 시점**에 Sale이 SOLD, 입찰이 COMPLETED가 되도록 짜여 있다.
- `updateOrderAndSaleBidStatusToCompleted`는 `private`인데 `@Transactional`이 붙어 있어 프록시가 적용되지 않는다. 호출자(`updateTrackingInfo`)의 트랜잭션 안에서 실행된다.

### 1-3. 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문은 끝까지 성공하나 → **실패한다**

**주문 상태가 무엇인가**

- 일반 구매 입찰 주문은 `OrderBidCommandService`에서 `Order`를 만들고 OrderBid를 `assignOrder`한다 (`src/main/java/com/fream/back/domain/order/service/command/OrderBidCommandService.java:60-63, 90-102`).
- 결제·배송 정보 처리는 `OCS:112-202` `processPaymentAndShipment`이다. 실제 배송(`isWarehouseStorage=false`)이면 `PAYMENT_COMPLETED → PREPARING`까지만 간다 (`OCS:174-177`).
- Kafka 경로(`OrderEventConsumer#processCompleteOrder`)도 동일하게 `PREPARING`에서 멈춘다 (`src/main/java/com/fream/back/domain/order/service/kafka/OrderEventConsumer.java:207-218`).
- 이 흐름에는 `SHIPMENT_STARTED`로 보내는 코드가 없다. `updateStatus(OrderStatus` 호출 위치는 `OCS`, `OrderEventConsumer`, 배송 서비스뿐이고 `SHIPMENT_STARTED`를 세팅하는 곳은 없다.

**어디서 왜 실패하나**

1. `S:260` `order.updateStatus(IN_TRANSIT)`가 호출된다.
2. `OS:26`에서 `PREPARING`이 갈 수 있는 곳은 `{IN_WAREHOUSE, SHIPMENT_STARTED}`뿐이다 (`OS:26`, 판정 `OS:41-44`).
3. `Order.updateStatus`가 `InvalidOrderStatusException`을 던진다 (`Order.java:113-121`). 이 예외는 `OrderException → GlobalException → RuntimeException`이다.
4. `S:293-301`: `ShipmentException`이 아니므로 `catch (Exception e)`에 걸려 `ShipmentException(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")`으로 감싸 다시 던진다.

**무엇이 저장되나**

- 예외가 `@Transactional` 메서드 밖으로 나가므로 트랜잭션 전체가 롤백된다.
- `shipment.updateTrackingInfo`로 바꾼 courier/trackingNumber/IN_TRANSIT도 롤백되어 **아무것도 저장되지 않는다**. OrderShipment는 `PENDING`, Order는 `PREPARING`, 송장 번호는 `null`로 남는다.
- 알림은 `S:266`에서 만드는데 실패 지점(`S:260`) 뒤라서 생성되지 않는다.
- 결과적으로 이 배송은 `IN_TRANSIT`이 되지 않아 6시간 배치의 조회 대상(2번 참조)에도 영영 들어오지 않는다.

**응답**

- `GlobalExceptionHandler#handleShipmentException`이 `errorCode.getStatus()`와 `ErrorResponse.of(code, message, status, uri)`를 만든다 (`src/main/java/com/fream/back/global/exception/GlobalExceptionHandler.java:458-470`).
- `SHIPMENT_NOT_FOUND`는 `S001`, "배송 정보를 찾을 수 없습니다.", HTTP **404**다 (`src/main/java/com/fream/back/domain/shipment/exception/ShipmentErrorCode.java:12`).
- 실제 원인은 주문 상태 전이 오류인데 응답은 "배송 정보를 찾을 수 없음 404"다. 에러 코드가 원인과 어긋난다.

## 2. 배송 완료 감지

### 2-1. 누가, 언제, 어떻게

- **누가**: Spring Batch Job `updateShipmentStatusesJob`을 `ShipmentBatchScheduler`가 실행한다 (`src/main/java/com/fream/back/global/config/ShipmentBatchScheduler.java:34-44`).
- **주기**: `@Scheduled(cron = "0 0 */6 * * *")` (`ShipmentBatchScheduler.java:34`). 서버 시간대 기준 매일 00:00, 06:00, 12:00, 18:00 정각, 즉 **6시간마다**다. 실행마다 `timestamp` JobParameter를 새로 만든다 (`ShipmentBatchScheduler.java:37-40`). 스케줄링은 다른 클래스의 `@EnableScheduling`으로 켜진다.
- **조회 대상**: `JpaPagingItemReader`가 `SELECT s FROM OrderShipment s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL`을 읽는다 (`J:87-97`). 페이지·청크 크기는 50이다 (`J:51, 67, 94`).
- **방식**: 각 건에 대해 CJ대한통운 조회 페이지(`https://trace.cjlogistics.com/next/tracking.html?wblNo=<송장번호>`)를 Playwright로 열고 `tbody#statusDetail tr`의 마지막 행 5번째 `td` 텍스트를 읽는다 (`P:28-29, 72-94, 167-191`). 페이지 타임아웃은 30초다 (`P:30, 78`).

### 2-2. 실제로 실행되는 처리 코드

비슷한 코드가 4곳에 있다.

| 후보 | 위치 | 실제 실행 여부 |
|---|---|---|
| `ShipmentItemProcessor#process` | `P:57-157` | **실행됨**. 스텝이 `new ShipmentItemProcessor(playwrightBrowserManager(), notificationService, orderService)`를 직접 등록한다 (`J:69-73`) |
| `UpdateShipmentStatusesJobConfig#shipmentItemProcessor` (`@Bean`) | `J:104-177` | 스텝에 연결되지 않아 사용되지 않음 (스텝은 `.processor(new ShipmentItemProcessor(...))`, `J:69`) |
| `UpdateShipmentStatusesJobConfig#parseCjLogisticsStatus` | `J:186-220` | 어디서도 호출하지 않음 |
| `OrderShipmentCommandService#updateShipmentStatuses` | `S:308-391` | 호출하는 곳이 없음 (스케줄러·배치가 부르지 않는다) |

- 또 `S:451-516` `updateAndCheckShipmentStatus`는 수동 API(`POST /shipments/order/{id}/check-status`, `C:58`)용이다. `CjTrackingPlaywright` 기반이며 주기 처리가 아니다.
- 따라서 주기 실행의 실체는 `ShipmentItemProcessor#process`이고, 저장은 `JpaItemWriter`다 (`J:239-246`).
- 브라우저는 스텝 시작 시 열고 종료 시 닫는다 (`BrowserManageStepListener`, `J:80`).

### 2-3. 택배사 상태 문자열 → 내부 상태

`P:220-226` `mapToShipmentStatus` (정확히 일치하는 문자열 비교):

- `"배송완료"` → `DELIVERED`
- `"배송출발"` → `OUT_FOR_DELIVERY`
- 그 외 모든 문자열 → `IN_TRANSIT`

현재 상태와 매핑 결과가 같으면 아무것도 하지 않고 반환한다 (`P:100-105`).

주의: 배송 상태가 `OUT_FOR_DELIVERY`인데 택배사가 다른 문자열(예: "배송 중")을 주면 `IN_TRANSIT`으로 매핑된다. `OUT_FOR_DELIVERY → IN_TRANSIT`은 `ShipmentStatus`가 허용하지 않아 (`src/main/java/com/fream/back/domain/shipment/entity/ShipmentStatus.java:79-83`) `IllegalStateException`이 나고, 이는 `EXTERNAL_TRACKING_SERVICE_ERROR`로 감싸져 건너뜀 처리된다 (`P:133-145`).

## 3. 배송 완료 판정 이후 (배치 `ShipmentItemProcessor`)

`P:108-117`에서 `DELIVERED`로 판정되면 순서는 다음과 같다.

1. **OrderShipment**: `orderShipment.updateStatus(DELIVERED)` (`P:113`). `IN_TRANSIT/OUT_FOR_DELIVERY → DELIVERED`는 허용된다 (`ShipmentStatus.java:72-84`).
2. `orderService.completeOrder(orderId)` 호출 (`P:116`, 본문 `S:190-229`):
   1. OrderBid 조회, 없으면 예외 (`S:196-197`).
   2. **Order**: `order.updateStatus(COMPLETED)` (`S:204`).
   3. `updateSaleStatusToSold(orderId)` (`S:208`): Sale → `SOLD`(가능할 때만), 창고 상태 갱신, 판매자 알림.
   4. **알림 (구매자)**: "[completeOrder] 주문이 완료 처리되었습니다. 주문 ID: …" (`S:211-217`).
3. `notificationService.notifyShipmentCompleted(order)` (`P:117`): **알림 (구매자)** "[배송 완료] 상품이 배송 완료되었습니다. 주문 ID: …" (`src/main/java/com/fream/back/domain/notification/service/command/NotificationCommandService.java:219-234`).
4. 청크 끝에서 `JpaItemWriter`가 OrderShipment를 저장한다 (`J:74, 239-246`).

### 알림 건수

- **구매자: 2건** (`S:212-217`의 "[completeOrder]" 1건 + `P:117`의 "[배송 완료]" 1건). 같은 사건에 대해 중복 알림이 간다.
- **판매자: 코드상 0~1건**. `S:132-138`에서 Sale이 아직 `SOLD`가 아니어서 `canTransitionTo(SOLD)`가 참일 때만 1건이다.
  - `SaleStatus`에서 `SOLD`는 어디로도 전이하지 않는다 (`src/main/java/com/fream/back/domain/sale/entity/SaleStatus.java:91`).
  - 운송장 등록(1번)에서 이미 `SOLD`가 되어 있거나(`S:276`), 결제 시점에 이미 `SOLD`이면(`src/main/java/com/fream/back/domain/payment/service/command/PaymentCommandService.java:404, 419`) 0건이다. 배송 완료 시점에 판매자 알림이 가는 경우는 사실상 드물다.

### 주문 입찰·판매 입찰 상태

- 배치 경로의 `completeOrder`와 `updateSaleStatusToSold`는 **OrderBid/SaleBid의 status를 건드리지 않는다**. `BidStatus` 갱신은 `updateOrderAndSaleBidStatusToCompleted`(`S:412-440`) 한 곳이고, 호출자는 운송장 등록 `updateTrackingInfo`(`S:289`)뿐이다.
- 따라서 배송 완료 판정 시점에는 OrderBid/SaleBid가 그대로 `MATCHED`로 남는다. 운송장 등록이 성공했다면 그때 이미 `COMPLETED`가 되었을 것이다.
- 주석("OrderBid와 SaleBid의 상태를 COMPLETED로 업데이트")과 달리 "배송 완료"와는 무관한 시점에 일어난다.
- 판매 입찰 SaleBid는 `findByOrderId`가 없을 때 `null`이 아니라 `IllegalArgumentException`을 던진다 (`src/main/java/com/fream/back/domain/sale/service/query/SaleBidQueryService.java:25-29`). 그래서 `S:117`의 `saleBid != null` 분기와 `S:145-147`의 else는 사실상 도달하지 않는다.

## 4. 주문 종류별 차이

### (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문 → 끝까지 진행되지 않는다

- 선행 단계에서 막힌다. 1-3에서 본 대로 운송장 등록이 롤백되므로 OrderShipment가 `IN_TRANSIT`이 되지 않고 배치 대상이 아니다.
- 가정으로 OrderShipment가 `IN_TRANSIT`이고 택배사가 "배송완료"를 준다고 해도 `completeOrder`의 `S:204` `order.updateStatus(COMPLETED)`에서 막힌다. `PREPARING → COMPLETED`는 `OS:26` 규칙에 없어 `InvalidOrderStatusException`이 발생한다.
- 그 예외는 `S:221-228`에서 `ShipmentException(ORDER_NOT_FOUND_FOR_SHIPMENT)`으로 감싸진다.
- 전이가 허용됐더라도 일반 입찰 주문에는 SaleBid가 없어(SaleBid가 order에 붙는 곳은 즉시 구매 `OCS:279`와 판매자 즉시 판매 `SaleBidCommandService.java:72-83`뿐) `S:116`의 `saleBidQueryService.findByOrderId`가 `IllegalArgumentException`을 던져 같은 방식으로 실패한다.
- 결과: 배치에서는 건너뜀(5번 참조). 구매자·판매자 알림은 0건이고, OrderShipment는 `IN_TRANSIT`, Order는 `PREPARING`, 입찰은 그대로다. 배송 완료로 바뀌지 않는다.

### (b) 즉시 구매로 만들어진 주문

- 주문은 `createInstantOrder`에서 `PENDING_PAYMENT`로 만들어지고 (`OCS:241-245`) 결제 처리 후에도 주문 상태는 바뀌지 않는다 (`OCS:303-309`; 결제 서비스에도 `Order` 상태 변경이 없음). OrderBid는 `isInstantPurchase=true`, 상태 `MATCHED`로 만들어진다 (`OrderBidCommandService.java:189-206`).
- **운송장 등록 API는 (b)도 실패한다.** `PENDING_PAYMENT → IN_TRANSIT`은 `OS:24` 규칙에 없다. 즉 (b)도 정상 흐름으로는 배치 대상이 되지 않는다.
- 배송이 `IN_TRANSIT`이 되어 배치가 돌았다고 가정하면 3번 처리가 끝까지 진행된다.
  - 이유 1: `PENDING_PAYMENT → COMPLETED`가 허용된다 (`OS:24`).
  - 이유 2: OrderBid(`OrderBidCommandService.java:189-206`)와 SaleBid(`OCS:279`)가 모두 존재한다.
- 결과:
  - OrderShipment=`DELIVERED`, Order=`COMPLETED`.
  - 구매자 알림 2건.
  - Sale은 결제 시점에 이미 `SOLD`(`PaymentCommandService.java:404`)여서 `canTransitionTo(SOLD)`가 거짓이라 판매자 알림 0건, 창고 갱신도 없다.
  - OrderBid/SaleBid는 `MATCHED` 그대로다.
- 수동 API `POST /shipments/order/{id}/check-status`(`S:451-516`)는 먼저 `shipment.updateTrackingInfo`로 `IN_TRANSIT`을 세팅한 뒤 조회하므로(`S:473`) (b)는 이 경로로는 완료된다. 이 경로에서는 `completeOrder`만 호출해 `notifyShipmentCompleted`는 호출하지 않으므로 구매자 알림이 1건이다 (`S:489`). 같은 경로에서 (a)는 `S:204`에서 실패한다.

### 차이 정리

| 항목 | (a) 일반 입찰 + 실배송 | (b) 즉시 구매 |
|---|---|---|
| 결제·배송 처리 후 Order | `PREPARING` | `PENDING_PAYMENT` |
| 운송장 등록 API | 실패 (404 S001, 롤백) | 실패 (같은 이유) |
| `completeOrder` | `S:204`에서 전이 불가 + SaleBid 없음으로 실패 | 성공 (`COMPLETED`) |
| 배송 완료 후 결과 | 변화 없음 (건너뜀) | Shipment `DELIVERED`, Order `COMPLETED`, 구매자 알림 2건 |
| OrderBid/SaleBid | 변화 없음 | `MATCHED` 유지 |

## 5. 실패 처리 (주기 배치)

- 스텝은 `faultTolerant().skip(Exception.class).skipLimit(50)`이고 청크 크기는 50이다 (`J:66-77`).
- 한 건에서 처리 중 예외가 나면(`P:133-145`에서 `ShipmentException`으로 감싸 던짐):
  - 그 건은 **건너뜀**이다. `SkipListener#onSkipInProcess`가 shipmentId, 송장번호, 상태, 사유를 로그로 남긴다 (`J:252-266`).
  - 그 건은 Writer로 가지 않으므로 DB 변경이 없다. 프로세서에서 메모리상 바꾼 `DELIVERED`도 저장되지 않는다. `completeOrder`가 청크 트랜잭션에 참여하다 던진 예외로 청크 트랜잭션은 롤백 대상이 된다.
  - 나머지 건은 Spring Batch의 skip 처리에 따라 청크가 롤백된 뒤 문제 건을 제외하고 다시 처리되어 정상 건은 계속 처리·저장된다 (Spring Batch fault-tolerant 동작).
  - 건너뛴 건은 상태가 `IN_TRANSIT/OUT_FOR_DELIVERY`로 남아 6시간 뒤 다음 실행에서 다시 조회된다. 그 건이 계속 같은 이유로 실패하면 매번 실패한다 (예: 위 (a)).
- 건너뜀이 50건을 넘으면 스텝이 실패하고 Job이 중단된다. 그 뒤 건은 이번 실행에서 처리되지 않는다. 스케줄러는 예외를 `printStackTrace`로만 처리하고 (`ShipmentBatchScheduler.java:41-43`) 다음 주기를 기다린다.
- 참고: "건별 try/catch 후 계속 진행"하는 구조는 호출되지 않는 `S:322-388` `updateShipmentStatuses`에만 있고 실제 배치와는 무관하다.
