# 구매자 배송: 운송장 등록 → 배송 완료 처리 (실제 코드 동작 기준)

경로 약어: `S` = `src/main/java/com/fream/back/domain/shipment`, `O` = `.../domain/order`, `P` = `.../domain/payment`, `SA` = `.../domain/sale`, `G` = `.../global`.
(`nav/domain/shipment/README.md` 의 설명은 실제 코드와 다른 부분이 많아 코드를 기준으로 답한다.)

## 0. 전제: 결제 직후 주문/배송 상태

- 일반 구매 입찰 주문은 `Order(PENDING_PAYMENT)` 로 생성된다 — `O/service/command/OrderCommandService.java:76-82`. 입찰 시 `OrderBid` 도 같이 만들어지고 `assignOrder` 가 즉시 `MATCHED` 로 바꾼다 — `O/entity/OrderBid.java:246-268` (261행).
- 결제·배송 처리(`processPaymentAndShipment`)에서 배송 정보는 `OrderShipment(PENDING)` 로 생성되고 (`S/service/command/OrderShipmentCommandService.java:55-75`, 호출 `OrderCommandService.java:148-155`), 실배송(창고 보관 아님)이면 주문은 `PAYMENT_COMPLETED → PREPARING` 에서 멈춘다 — `OrderCommandService.java:174-176`.
- 허용 전이 표: `PREPARING → {IN_WAREHOUSE, SHIPMENT_STARTED}`, `PENDING_PAYMENT → {PAYMENT_COMPLETED, COMPLETED, IN_WAREHOUSE}`, `IN_TRANSIT → {COMPLETED}` — `O/entity/OrderStatus.java:24-32`. 위반 시 `InvalidOrderStatusException` — `O/entity/Order.java:166-174`.
- 코드 어디에도 `SHIPMENT_STARTED` 로 바꾸는 곳이 없고, `OrderStatus.IN_TRANSIT` 으로 바꾸는 곳은 `OrderShipmentCommandService.java:260` 하나뿐이다 (grep 결과).

## 1. 운송장 등록 요청

### 1-1. 진입 API
- `PATCH /shipments/order/{shipmentId}/status` — `S/controller/command/OrderShipmentCommandController.java:20,33-48` → `OrderShipmentCommandService.updateTrackingInfo(shipmentId, courier, trackingNumber)` (`:41`). 성공 시 `200 OK`(본문 없음) (`:47`).
- (별도) `POST /shipments/order/{shipmentId}/check-status` 도 운송장을 등록하지만 즉시 택배사 조회까지 한다 — `OrderShipmentCommandController.java:55-` / `OrderShipmentCommandService.java:452-516`. 아래 2·4 에서 다시 나온다.

### 1-2. 의도된 상태 변경 순서와 알림 (`OrderShipmentCommandService.java:238-303`)
1. courier/trackingNumber 공백 검사 → 없으면 `TRACKING_INFO_REQUIRED` (`:243-246`).
2. `OrderShipment` 조회 후 `shipment.updateTrackingInfo` — 택배사·송장번호 저장 + 배송 상태를 **무조건 `IN_TRANSIT`** 으로 세팅 (`:256`, `S/entity/OrderShipment.java:41-45`; 전이 검증 없음).
3. `Order` 를 `IN_TRANSIT` 으로 변경 (`:259-260`).
4. 구매자에게 알림 1건 "상품이 출발하였습니다. 주문 ID: …" (`:264-271`).
5. `updateSaleStatusToSold(orderId)` (`:276`, 본체 `:111-183`): `Sale` 을 `SOLD` 로 바꾸고(전이 가능할 때만), 창고 보관이면 창고 상태 갱신, 판매자에게 알림 "상품이 성공적으로 판매 완료되었습니다" (`:116-180`). — 즉 **배송 완료 전에 운송장 등록 시점에 판매가 SOLD 로 처리되도록** 짜여 있다.
6. 창고 보관 `Sale` 이면 창고 상태 재갱신 (`:279-286`).
7. `OrderBid`/`SaleBid` 가 `MATCHED` 이면 `COMPLETED` 로 변경 (`:289`, 본체 `:412-440`).

요약: Shipment(IN_TRANSIT) → Order(IN_TRANSIT) → Sale(SOLD) → OrderBid/SaleBid(COMPLETED). 알림은 구매자 1건 + 판매자(조건부) 1건.

### 1-3. 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문에서 끝까지 성공하나? → **아니오, 실패한다**
- 실패 지점: 3단계 `order.updateStatus(OrderStatus.IN_TRANSIT)` — `OrderShipmentCommandService.java:260` → `Order.java:166-174`. 현재 주문 상태는 `PREPARING`(0절) 이고 `PREPARING → IN_TRANSIT` 은 허용되지 않아 `InvalidOrderStatusException`("상태 전환이 허용되지 않습니다: PREPARING -> IN_TRANSIT") 발생. (`SHIPMENT_STARTED` 를 거치는 코드가 없어 정상 경로로는 항상 막힌다.)
- 이 예외는 `ShipmentException` 이 아니라서 `catch (Exception e)` 로 빠지고 (`:295-302`), `ShipmentErrorCode.SHIPMENT_NOT_FOUND` 로 **잘못 포장되어** 다시 던져진다.
- 무엇이 저장되나: 아무것도 저장되지 않는다. 예외가 `@Transactional`(`:238`) 메서드 밖으로 나가는 `RuntimeException`(`G/exception/GlobalException.java:10`) 이므로 롤백된다. 2단계에서 메모리상 `IN_TRANSIT`/택배사/송장번호로 바꾼 것도 반영되지 않아 `OrderShipment` 는 `PENDING`·송장번호 null, `Order` 는 `PREPARING` 그대로다. 알림은 4단계 이전에 예외가 나므로 생성되지 않는다.
- 응답: `GlobalExceptionHandler.handleShipmentException` (`G/exception/GlobalExceptionHandler.java:459-473`) 이 `ErrorResponse(code="S001", message="배송 정보를 찾을 수 없습니다.", status=404)` 를 반환한다 (`S/exception/ShipmentErrorCode.java:61`). 즉 **HTTP 404 / S001** (실제 원인은 주문 상태 전이 불가).

## 2. 배송 완료 감지

### 2-1. 누가·언제·어떻게
- **스케줄러**: `G/config/ShipmentBatchScheduler.java:34` `@Scheduled(cron = "0 0 */6 * * *")` → **6시간마다 정각(00·06·12·18시)** 에 `updateShipmentStatusesJob` 을 `jobLauncher.run` 으로 실행 (`:35-43`). 예외는 `printStackTrace` 만 한다. `@EnableScheduling` 은 `domain/event/scheduler/EventStatusScheduler.java:22` (`@Component` `:19`) 에 선언돼 활성화된다.
- Job/Step: `S/config/UpdateShipmentStatusesJobConfig.java:55-80` (chunk 50, faultTolerant, skip(Exception) 한도 50).
- **조회 대상**: `status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND trackingNumber IS NOT NULL` 인 `OrderShipment` — `UpdateShipmentStatusesJobConfig.java:95` (JpaPagingItemReader, pageSize 50).
- 수동 경로: `POST /shipments/order/{id}/check-status(-string)` 로 단건 즉시 조회 (`OrderShipmentCommandService.java:452-516`).

## 3. 배송 완료 판정 이후 (`ShipmentItemProcessor.java:101-117` → `completeOrder`)

판정이 `DELIVERED` 이고 현재 상태와 다를 때:
1. `orderShipment.updateStatus(DELIVERED)` — `IN_TRANSIT`/`OUT_FOR_DELIVERY` 에서는 허용 (`S/entity/ShipmentStatus.java:72-84`).
2. `orderService.completeOrder(orderId)` (`OrderShipmentCommandService.java:190-229`):
   1. `OrderBid` 조회 — 없으면 `IllegalArgumentException` (`:196-197`).
   2. `order.updateStatus(COMPLETED)` (`:204`).
   3. `updateSaleStatusToSold(orderId)` (`:208`): `SaleBid` 조회(`SA/service/query/SaleBidQueryService.java:26-29` — **없으면 null 이 아니라 예외**) → `Sale` 이 `SOLD` 로 전이 가능할 때만 SOLD + 판매자 알림 1건(+창고 갱신); 이어 `OrderBid.getSale()` 쪽도 같은 방식(같은 Sale 이라 이미 SOLD 이면 건너뜀).
   4. 구매자 알림 "[completeOrder] 주문이 완료 처리되었습니다" (`:210-217`).
3. `notificationService.notifyShipmentCompleted(order)` — 구매자 알림 "[배송 완료] 상품이 배송 완료되었습니다" (`src/main/java/com/fream/back/domain/notification/service/command/NotificationCommandService.java:219-234`, 예외는 삼킴).
4. Writer `JpaItemWriter` 가 `OrderShipment` 저장 (`UpdateShipmentStatusesJobConfig.java:108-115`).

상태 변경 순서: `OrderShipment(DELIVERED)` → `Order(COMPLETED)` → `Sale(SOLD, 조건부)`.

알림(성공 시): 구매자 **2건**(`[completeOrder]`, `[배송 완료]`), 판매자 **0~1건**(Sale 이 아직 SOLD 가 아니고 전이 가능할 때만 1건). 판매자 알림이 중복으로 2건 가는 경로는 없다(둘 다 같은 Sale).

입찰 상태: **배치 경로는 `OrderBid`/`SaleBid` 를 건드리지 않는다.** `COMPLETED` 로 바꾸는 `updateOrderAndSaleBidStatusToCompleted` 는 `updateTrackingInfo` 에서만 호출된다 (`:289`; `completeOrder` 에는 없음). 따라서 배송 완료 후에도 둘 다 `MATCHED` 로 남는다 (README 의 "입찰 COMPLETED" 설명은 실제 동작과 다름).

## 4. 주문 종류별 차이

### (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문 → **끝까지 진행되지 않는다**
- 주문은 `PREPARING` (0절). 배송이 배치 대상이 되려면 `IN_TRANSIT`+송장번호가 있어야 하는데, `PATCH …/status` 는 1-3 처럼 롤백되므로 `POST …/check-status` 로만 가능하다 (이 경로는 shipment 만 `IN_TRANSIT` 으로 저장하고 Order 는 안 건드림 — `:473`, `:497`).
- 그 상태에서 `DELIVERED` 가 감지되면 `shipment.updateStatus(DELIVERED)` 후 `completeOrder` 의 `order.updateStatus(COMPLETED)` (`:204`) 에서 `PREPARING → COMPLETED` 불허로 `InvalidOrderStatusException` → `catch (Exception)` 이 `ShipmentException(ORDER_NOT_FOUND_FOR_SHIPMENT, S102, 404)` 로 변환 (`:221-228`). 이후 단계(Sale SOLD, 알림 2건, `notifyShipmentCompleted`)는 실행되지 않는다.
- 설령 주문 상태 문제가 없더라도, 매칭된 판매 입찰(`SaleBid`)이 없으면 `SaleBidQueryService.findByOrderId` 가 예외를 던져 같은 방식으로 실패한다 (`:26-29`).
- 결과: 트랜잭션 롤백 → `OrderShipment` 는 `IN_TRANSIT` 유지, `Order` `PREPARING`, 알림·입찰 변화 없음. 배치에서는 skip 처리되어 6시간마다 같은 실패가 반복된다. (`check-status` 호출 시에는 컨트롤러가 `ShipmentException` 상태코드만 담아 본문 없이 응답 — `OrderShipmentCommandController.java:~80-86`.)

### (b) 즉시 구매로 만들어진 주문 → **끝까지 진행된다** (배치에서 shipment 가 `IN_TRANSIT` 이 된 경우)
- `createInstantOrder`: Order `PENDING_PAYMENT` 로 생성(`OrderCommandService.java:241-245`), 배송 `PENDING` 생성(`:264-271`), `SaleBid` 와 매칭 `saleBid.assignOrder` (`:279`), 결제 처리 (`:305`). 즉시 구매 흐름에서 주문 상태를 바꾸는 코드는 없어 주문은 `PENDING_PAYMENT` 로 남는다. `OrderBid` 는 `MATCHED`, `sale` 연결, `isInstantPurchase=true` 로 생성된다 (`O/service/command/OrderBidCommandService.java:189-205`).
- 결제 시점에 `PaymentCommandService.notifyUsersAndUpdateSaleStatus` 가 `SaleBid` → `Sale` 을 찾아 구매자·판매자 알림을 보내고 `Sale` 을 **이미 `SOLD`** 로 만든다 (`P/service/command/PaymentCommandService.java:383-420`, 404행).
- 운송장 등록 `PATCH …/status` 는 (a)와 똑같이 `PENDING_PAYMENT → IN_TRANSIT` 불허로 실패한다. `check-status` 로 shipment 가 `IN_TRANSIT` 이 되면 배치 대상이 된다.
- 배송 완료 감지 시: `Order PENDING_PAYMENT → COMPLETED` 는 허용 (`OrderStatus.java:24`) → `completeOrder` 성공. 그러나 `Sale` 이 이미 `SOLD` 라 `canTransitionTo(SOLD)` 가 false → 판매자 알림·창고 갱신 없음 (`:119`, `:156`).
- 결과(배치 경로): `OrderShipment DELIVERED`, `Order COMPLETED`, 구매자 알림 2건, 판매자 알림 0건, `OrderBid`/`SaleBid` 는 `MATCHED` 유지. (`POST check-status` 로 완료 감지된 경우는 `notifyShipmentCompleted` 가 없어 구매자 알림 1건 — `:483-489`.)

## 5. 실패 처리 (배치)

- 한 건 처리 중 예외(운송장 없음, 파싱 실패, Playwright 오류, `completeOrder` 실패, 불가능한 상태 전이 등) → 처리기가 `ShipmentException` 으로 감싸 던진다 (`ShipmentItemProcessor.java:~128-146`).
- Step 은 `faultTolerant().skip(Exception.class).skipLimit(50)` (`UpdateShipmentStatusesJobConfig.java:75-77`): 실패한 건은 **skip** 되고 `SkipListener` 가 로그만 남긴다 (`:~125-150`). 해당 chunk(50건) 트랜잭션은 롤백된 뒤, 실패 건을 제외하고 다시 처리되어 나머지 건은 정상 커밋된다. 실패한 건은 DB 에서 DELIVERED/COMPLETED 로 바뀌지 않고(롤백) `IN_TRANSIT` 으로 남아 다음 주기(6시간 뒤)에 다시 조회된다 — 재시도/보정 로직은 없다.
- 누적 skip 이 50건을 넘으면 `SkipLimitExceededException` 으로 Step 이 실패하고 그 이후 건은 해당 실행에서 처리되지 않는다. 스케줄러는 예외를 `printStackTrace` 만 하고 넘어간다 (`ShipmentBatchScheduler.java:~41-43`).
- 참고(미사용 코드): `OrderShipmentCommandService.updateShipmentStatuses()` 는 건별 try/catch 로 실패 건만 건너뛰는 구조지만 호출되지 않는다.
- 추가 관찰(위험): reader 가 offset 기반 페이징(`JpaPagingItemReader`)이라 chunk 처리 중 상태가 `DELIVERED` 로 바뀌어 조건에서 빠지면 다음 페이지 offset 이 밀려 일부 건이 해당 회차에서 누락될 수 있다.
