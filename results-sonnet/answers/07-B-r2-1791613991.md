# 즉시 구매 처리 흐름 (ANSWER)

경로 접두어: `D = src/main/java/com/fream/back/domain`

## 1. 진입 API, 처리 단계, 동기/비동기, 응답 ID

- 진입점: `POST /order-bids/instant` (`D/order/controller/command/OrderBidCommandController.java:22`, `:89-90`). 바디는 `InstantOrderRequestDto`(saleBidId, addressId, warehouseStorage, paymentRequest — `D/order/dto/InstantOrderRequestDto.java:20-29`).
- 단계
  1. 컨트롤러가 이메일 추출 후 `enrichPaymentRequest`로 `userEmail`을 채우고 `orderId=null`로 둔다 (`OrderBidCommandController.java:92`, `:98`, `:119-123`).
  2. `OrderBidCommandService.createInstantOrderBid` (`D/order/service/command/OrderBidCommandService.java:118-149`, `@Transactional`): 입력 검증(`:123`) → 구매자 조회(`:126`) → SaleBid/Sale 조회·검증(`:129-130`, `:172-184`) → `OrderCommandService.createInstantOrder`(`:133`) → `OrderBid` 생성·저장(`:142`, `:189-207`).
  3. `OrderCommandService.createInstantOrder` (`D/order/service/command/OrderCommandService.java:219-319`, `@Transactional`): 주소 조회(`:238`) → Order 저장(`:241-247`) → OrderItem(`:255-256`) → OrderShipment(`:264-271`) → SaleBid 매칭 + flush(`:279-283`) → 판매 측 창고 상태 변경(`:291-293`) → 결제(`:305`).
  4. 결제 `PaymentCommandService.processPayment` (`D/payment/service/command/PaymentCommandService.java:57-107`) → 알림 및 Sale 상태 변경 (`:83`, `:383-426`).
- **동기 처리**다. Kafka/@Async/이벤트 리스너를 쓰지 않고(이 경로에서 `OrderEventProducer` 호출 없음; 컨트롤러는 서비스만 의존 `OrderBidCommandController.java:28`), 하나의 HTTP 요청·하나의 트랜잭션 안에서 PortOne 호출까지 끝낸다. (`/orders/{orderId}/process-payment-shipment`만 Kafka 비동기 202 응답이며 즉시 구매 경로가 아니다: `D/order/controller/command/OrderCommandController.java:42-69`.)
- 응답: `ResponseEntity.ok(ResponseDto.success(orderId, "즉시 구매가 성공적으로 처리되었습니다."))` (`OrderBidCommandController.java:101-109`). 변수 이름과 메시지는 orderId지만, 서비스가 반환한 **OrderBid**의 `.getId()` 이다 (`:101-107`, 서비스 반환 타입 `OrderBid` `OrderBidCommandService.java:119`, `:142-144`). 즉 응답 ID는 **Order ID가 아니라 새로 만든 OrderBid의 ID**이다(컨트롤러 Javadoc "생성된 주문 ID" `:82-83`은 사실과 다름).

## 2. 생성되는 엔티티와 상태 변화 순서

| 순서 | 동작 | 직후 상태 | 근거 |
|---|---|---|---|
| 1 | `Order` 생성·저장 (totalAmount = saleBid.bidPrice) | Order.status = `PENDING_PAYMENT` | `OrderCommandService.java:241-247` |
| 2 | `OrderItem` 생성(quantity 1, 가격 = 입찰가) 후 Order에 추가 | (Order 상태 변화 없음) | `:255-256`, `D/order/service/command/OrderItemCommandService.java:45-52` |
| 3 | `OrderShipment` 생성(주소 DTO의 수령인/전화/우편번호/주소) 후 연결 | Shipment.status = `PENDING` | `:264-271`, `D/shipment/service/command/OrderShipmentCommandService.java:61-70` |
| 4 | 판매 입찰에 주문 연결 + 매칭, flush | SaleBid.status = `MATCHED` (`assignOrder`가 MATCHED 세팅, 이어서 `updateStatus(MATCHED)`) | `:279-283`, `D/sale/entity/SaleBid.java:58-61` |
| 5 | Sale이 창고 보관 판매(`sale.isWarehouseStorage()`)면 창고 상태 변경 | WarehouseStorage.status = `ASSOCIATED_WITH_ORDER` | `:291-293`, `D/warehouseStorage/service/command/WarehouseStorageCommandService.java:117-133`, `:232-` |
| 6 | `Payment` 생성(타입별, 3번 참조) 후 저장 | CARD 성공 시 `PAID`, ACCOUNT `PENDING`, GENERAL `PAID` | `PaymentCommandService.java:203-208`, `:260`, `:313-314` |
| 7 | 알림 발송 후 판매 상태 변경 | Sale.status = `SOLD` (PENDING_SHIPMENT 등 이전 값에서 전이 검증 없이 대입) | `PaymentCommandService.java:403-404`, `D/sale/entity/Sale.java:73-75` |
| 8 | `OrderBid` 생성·저장 (즉시 구매 플래그) | OrderBid.status = `MATCHED`, isInstantPurchase = true | `OrderBidCommandService.java:192-206`, `D/order/entity/OrderBid.java:60-82`, `:97-99` |

- 새로 만들어지는 엔티티: Order, OrderItem, OrderShipment, Payment(CardPayment/AccountPayment/GeneralPayment), Notification(구매자·판매자 각 1건), OrderBid.
- 기존 엔티티가 바뀌는 순서: SaleBid(PENDING→MATCHED, order 연결) → (창고 판매면) WarehouseStorage(→ASSOCIATED_WITH_ORDER) → Sale(→SOLD).
- 주의: 결제 시점에 `order.getOrderBid()`는 아직 null이다(OrderBid는 결제 이후 생성, `OrderBidCommandService.java:133-142`). 그래서 `notifyUsersAndUpdateSaleStatus`는 `OrderBid` 분기 대신 `saleBidQueryService.findByOrderId`로 SaleBid를 찾아 그 Sale을 쓴다 (`PaymentCommandService.java:388-406`, `D/sale/service/query/SaleBidQueryService.java:26-28`).
- 주의: 두 `BidStatus` enum(order/sale)이 별개 타입이다 (`OrderCommandService.java:280`은 sale 쪽을 풀네임으로 사용).

## 3. 결제 수단별 결과, 성공 여부, 카드 실패 시

- 분기: `switch (requestDto.getResolvedPaymentType())` (`PaymentCommandService.java:67-80`). 검증으로 orderId·이메일 일치, 금액>0을 확인한다 (`:117-146`). orderId는 컨트롤러에서 null이었다가 `OrderCommandService.java:250`에서 채워 통과한다.
- **CARD** (`:157-225`): 저장된 PaymentInfo 조회(`:166`) → PortOne 호출 `processCardPayment`(`:179`) → CardPayment 저장. 응답 `status`가 `"success"`일 때만 `PAID` + isSuccess=true (`:203-206`). 그렇지 않으면 상태는 기본값 `PENDING`, isSuccess=false로 그대로 저장된다 (`D/payment/entity/Payment.java:39`, `:44`).
- **ACCOUNT** (`:236-279`): 은행명 검증(`:244`)만 하고 외부 호출 없이 AccountPayment를 `PENDING`으로 저장 (`:260-262`). 입금 확인 로직은 없다. 
- **GENERAL** (`:290-333`): impUid 필수만 확인하고 외부 검증 없이 곧바로 `PAID`, isSuccess=true (`:297-300`, `:313-314`).
- 즉시 구매는 요청 안에서 **끝까지 진행되어 성공 응답**을 준다(CARD 성공/ACCOUNT/GENERAL 모두). 단 ACCOUNT는 결제가 `PENDING`인 채로 Order·Sale이 이미 확정(SOLD)된다.
- **카드 결제 실패**
  - PortOne이 HTTP≠200 이거나 `code != 0`이면 `PaymentProcessingException` 발생 (`D/payment/portone/PortOneApiClient.java:270-275`) → `processPayment`가 전파(`PaymentCommandService.java:89-94`) → `OrderCommandService`가 `OrderPaymentProcessingFailedException`으로 감싸 던짐 (`OrderCommandService.java:304-309`) → 최종 `OrderException`이므로 그대로 전파(`:312-314`) → `OrderBidCommandService.handleOrderBidCreationException`이 재던짐(`:212-215`). 같은 `@Transactional` 안이므로 **Order/OrderItem/Shipment/SaleBid 매칭/창고 상태가 모두 롤백**되고 OrderBid는 만들어지지 않는다. 구매자는 오류 응답을 받는다.
  - 네트워크 오류는 `PaymentApiException`(재시도 3회 `@Retryable`, `PortOneApiClient.java:223-228`, `:288-290`) 후 동일하게 롤백.
  - 예외: PortOne이 `code==0`인데 `response.status`가 `"success"`가 아니면(예: `failed`) 예외 없이 **PENDING·isSuccess=false 결제가 저장**되고, 이후 알림·Sale SOLD·OrderBid MATCHED까지 그대로 진행된다 (`PaymentCommandService.java:203-208`, `:83`). 실패 응답이 성공 응답으로 처리되는 셈이다.

## 4. 알림 수신자, 시점, 전달 방식

- 수신자 (`PaymentCommandService.java:434-455`)
  - 구매자: "결제가 완료되었습니다. 주문 ID: {orderId}"
  - 판매자(`sale.getSeller()`): "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}"
  - 둘 다 `NotificationCategory.SHOPPING`, `NotificationType.BID`.
- 시점: `processPayment` 안에서 Payment 저장 직후, Sale을 SOLD로 바꾸기 직전 (`:83`, `:403-404`). 결제 PENDING(계좌이체)이든 성공이든 동일하게 "결제가 완료되었습니다"가 나간다. 알림은 트랜잭션 커밋 이전에 발송된다.
- 방식: **동기**. `NotificationCommandService.createNotification`이 DB에 Notification을 저장하고(`D/notification/service/command/NotificationCommandService.java:52-54`), 그 사용자의 Redis 키 `WebSocket:User:{email}`가 있을 때만 WebSocket `/queue/notifications`로 `convertAndSendToUser` 한다 (`:303-313`, 상수 `:37-38`). 연결이 없으면 저장만 되고 푸시는 없다 (`:320-322`). 별도 Kafka·이메일·푸시는 이 경로에 없다.
- 알림 실패는 로그만 남기고 삼킨다 (`PaymentCommandService.java:457-461`, `:421-425`).

## 5. 최종 주문 상태와 창고 보관 선택 시 차이

- 최종 Order.status = **`PENDING_PAYMENT`**. 즉시 구매 경로에서 Order의 상태는 생성 시 한 번 세팅되고(`OrderCommandService.java:244`) 이후 `order.updateStatus`가 호출되지 않는다. `PAYMENT_COMPLETED`/`PREPARING`/`IN_WAREHOUSE`/`COMPLETED`로 바꾸는 코드는 `processPaymentAndShipment`(`:163-176`)와 Kafka 소비자(`D/order/service/kafka/OrderEventConsumer.java:195`, `:210`) 쪽이며 즉시 구매는 거치지 않는다. 결제가 성공해도 주문은 "결제 대기"로 남는다(메서드 이름·응답 메시지 "처리되었습니다"와 다른 실제 동작). 파생 상태: Payment `PAID`(카드/일반) 또는 `PENDING`(계좌), SaleBid `MATCHED`, Sale `SOLD`, OrderBid `MATCHED`.
- 창고 보관 선택(`warehouseStorage=true`)의 효과: **없다**. 요청 DTO의 `warehouseStorage`는 컨트롤러에서 서비스로 전달되지만(`OrderBidCommandController.java:105`, `OrderBidCommandService.java:137`) `createInstantOrder` 본문에서 `isWarehouseStorage` 파라미터를 읽는 곳이 없다(선언 `OrderCommandService.java:221` 이후 사용처 없음). 창고 관련 분기는 구매자의 선택이 아니라 **판매자 Sale의 `isWarehouseStorage`** 만 본다 (`:291-293`) — 이 경우 판매 창고 보관 상태만 `ASSOCIATED_WITH_ORDER`로 바뀐다.
  - 구매자용 창고 처리(`createOrderStorage`, 상태 `IN_WAREHOUSE`→`COMPLETED`)는 `processPaymentAndShipment`에만 있다 (`:163-172`). 즉시 구매에서는 일어나지 않아 WarehouseStorage가 구매자 주문에 생성·연결되지 않고, 배송 정보도 항상 요청한 `addressId`의 주소로 만들어진다(`:264-270`).
