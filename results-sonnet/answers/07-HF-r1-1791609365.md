# 즉시 구매 처리 흐름 (ANSWER)

경로 접두어: `D = src/main/java/com/fream/back/domain`

## 1. 진입 API, 처리 단계, 동기/비동기, 응답 ID

**API**: `POST /order-bids/instant` (`D/order/controller/command/OrderBidCommandController.java:22,89-90`). 본문은 `InstantOrderRequestDto`(saleBidId, addressId, warehouseStorage, paymentRequest).

**처리 단계 (전부 한 요청 스레드 안에서 동기 처리)**
1. 컨트롤러가 SecurityContext 에서 이메일을 꺼내고(`OrderBidCommandController.java:92`), 결제 요청에 `userEmail` 을 넣고 `orderId=null` 로 초기화한다(`:98`, `:119-122`).
2. `OrderBidCommandService.createInstantOrderBid` (`@Transactional`, `D/order/service/command/OrderBidCommandService.java:118-149`)
   - 입력 검증 (`:123`, `:154-167`) → 구매자 조회 (`:126`) → SaleBid/Sale 조회·검증 (`:129`, `:172-184`)
3. `OrderCommandService.createInstantOrder` (`D/order/service/command/OrderCommandService.java:219-319`)
   - 주소 조회 (`:238`) → Order 저장 (`:241-247`) → `paymentRequest.setOrderId` (`:250`)
   - OrderItem 생성 (`:255-256`) → OrderShipment 생성 (`:264-271`)
   - SaleBid 매칭 + `flush` (`:279-283`)
   - 판매자가 창고 보관 상품이면 WarehouseStorage 상태 변경 (`:291-293`)
   - 결제 처리 `paymentCommandService.processPayment` (`:305`)
4. `PaymentCommandService.processPayment` (`D/payment/service/command/PaymentCommandService.java:57-107`) → 결제 유형별 Payment 생성 → `notifyUsersAndUpdateSaleStatus` (`:83`, `:383-426`)에서 알림 + Sale 상태 변경.
5. 복귀 후 OrderBid 생성·저장 (`OrderBidCommandService.java:142`, `:189-207`).

**동기/비동기**: 전부 동기, 단일 DB 트랜잭션이다. 이 경로에는 Kafka/`@Async`/`runAsync` 가 없다. Kafka 프로듀서(`OrderEventProducer`)는 `OrderCommandController` 의 별도 결제·배송 경로에서만 쓰인다(`D/order/controller/command/OrderCommandController.java:30`). 즉시 구매 경로(`OrderBidCommandService`→`OrderCommandService.createInstantOrder`)는 이 프로듀서를 호출하지 않는다. 외부 호출(PortOne 카드 결제 HTTP)도 요청 스레드에서 블로킹으로 실행된다(`D/payment/portone/PortOneApiClient.java:266`).

**응답 ID**: 응답 `data` 는 **OrderBid 의 ID** 다. 컨트롤러는 `createInstantOrderBid(...).getId()` 를 `orderId` 변수에 담아 돌려주지만(`OrderBidCommandController.java:101-109`), 서비스 반환값이 `OrderBid` 이므로(`OrderBidCommandService.java:119,144`) Order ID 가 아니다. Javadoc 의 "생성된 주문 ID"(`:83`)와 변수명 `orderId` 는 실제 동작과 다르다.

## 2. 새로 만들어지는 엔티티와 상태 변화 순서

생성 순서와 직후 상태(모두 동일 트랜잭션; 커밋 전 중간 상태 포함):

| 순서 | 동작 | 직후 상태 | 근거 |
|---|---|---|---|
| 1 | **Order** 저장 | `OrderStatus.PENDING_PAYMENT` (`totalAmount = saleBid.bidPrice`) | `OrderCommandService.java:241-247` |
| 2 | **OrderItem** 생성, Order 에 추가 | (상태 없음, 가격 = saleBid 입찰가) | `:255-256` |
| 3 | **OrderShipment** 생성 | `ShipmentStatus.PENDING` | `D/shipment/service/command/OrderShipmentCommandService.java:61-68`, `OrderCommandService.java:264-271` |
| 4 | **기존 SaleBid** 에 order 연결, 상태 변경 | `sale.BidStatus.MATCHED` (`assignOrder` 자체가 MATCHED 로 세팅, 이어서 `updateStatus(MATCHED)` 한 번 더) | `OrderCommandService.java:279-280`, `D/sale/entity/SaleBid.java:58-61,66-68` |
| 5 | (Sale 이 창고 보관 상품이면) **기존 WarehouseStorage** 상태 변경 | `ASSOCIATED_WITH_ORDER` | `OrderCommandService.java:291-293`, `D/warehouseStorage/service/command/WarehouseStorageCommandService.java:117-133` |
| 6 | **Payment**(Card/Account/General) 저장 | 유형별(3번 문항 참조) | `PaymentCommandService.java:157-333` |
| 7 | 알림 생성 + **기존 Sale** 상태 변경 | `SaleStatus.SOLD` | `PaymentCommandService.java:403-405` |
| 8 | **OrderBid** 생성·저장 | `order.BidStatus.MATCHED`, `isInstantPurchase=true`, sale 연결 | `OrderBidCommandService.java:192-206`, `D/order/entity/OrderBid.java:73-76,97-99` |

요약: 신규 엔티티는 Order, OrderItem, OrderShipment, Payment, Notification(2건), OrderBid 이며, 기존 SaleBid(→MATCHED), (조건부)WarehouseStorage(→ASSOCIATED_WITH_ORDER), Sale(→SOLD)의 상태가 바뀐다.

**주의(실제 동작)**
- Order 의 상태는 이 경로에서 `PENDING_PAYMENT` 이후 **한 번도 갱신되지 않는다**. `updateStatus`/`PAYMENT_COMPLETED` 호출이 `createInstantOrder` 에도 `createInstantOrderBid` 에도 없다(`OrderCommandService.java:219-319` 전체, `OrderBidCommandService.java:118-207` 전체). `docs`(nav/domain/order README)가 말하는 "결제 즉시 처리 → PAYMENT_COMPLETED" 와 다르다. `Payment` 도 `order.assignPayment` 로 Order 에 연결되지 않는다(반환값을 버림, `OrderCommandService.java:305`) — Payment 쪽에서만 `assignOrder` 로 Order 를 가리킨다(`PaymentCommandService.java:200,258,311`).
- `PaymentCommandService.notifyUsersAndUpdateSaleStatus` 는 시점상 `order.getOrderBid()==null`(OrderBid 가 아직 안 만들어짐, `:388-389`) 이므로 `saleBidQueryService.findByOrderId` 분기(`:391-406`)를 탄다. 이는 4단계에서 `saleBid.assignOrder(order)` + flush 가 선행되었기 때문에 동작한다.
- SaleBid 가 이미 MATCHED 인지 같은 중복 구매 검사가 없다(`getSaleBidAndValidate`, `OrderBidCommandService.java:172-184`는 null 만 검사).

## 3. 결제 수단별 결과, 성공 여부, 카드 실패 시

결제 유형은 요청 DTO 클래스로 결정된다(`D/payment/dto/PaymentRequestDto.java:74-86`), 분기는 `PaymentCommandService.java:67-80`. 공통 검증: Order ID/이메일 일치, 금액 > 0 (`:117-146`).

| 수단 | 처리 | 저장되는 Payment 상태 | 근거 |
|---|---|---|---|
| **CARD** | 저장된 PaymentInfo 로 PortOne 카드 결제 API 동기 호출 | 응답 `status` 가 문자열 `"success"` 일 때만 `PAID` + `isSuccess=true`. 그 외엔 기본값 **`PENDING`, isSuccess=false** 로 저장하고 예외 없이 진행 | `PaymentCommandService.java:166,179,203-208`, `D/payment/entity/Payment.java:39,44` |
| **ACCOUNT** | 은행명 enum 검증만, 외부 호출 없음 | 항상 **`PENDING`** (입금 확인 로직 없음) | `PaymentCommandService.java:244,258-262` |
| **GENERAL** | `impUid` 필수 검사만 하고(PortOne 서버 검증 없음) 클라이언트가 준 값으로 생성 | 즉시 **`PAID`**, `isSuccess=true` | `PaymentCommandService.java:297-314` |

**즉시 구매가 끝까지 성공하는가**: 결제 상태와 무관하게 구매 흐름은 끝까지 진행된다. 결제 유형이 무엇이든 `processPayment` 가 예외 없이 반환하면 → 알림 발송, Sale=SOLD, SaleBid=MATCHED, OrderBid=MATCHED 가 모두 확정된다(`PaymentCommandService.java:83`, `:403-420`). 즉 ACCOUNT(PENDING)이나, `status` 가 "success" 가 아닌 CARD(PENDING)도 판매 완료/알림이 나간다. 알림 메시지도 "결제가 완료되었습니다"(`:442`)로 나간다. 또 카드의 `status` 비교값이 `"success"` 라서 PortOne 이 일반적으로 쓰는 `"paid"` 같은 값이면 PAID 로 가지 않을 수 있다(코드상 실제 비교는 `"success"` 만, `:203`).

**카드사/PG 가 실패로 응답할 때**: 두 갈래다.
- PortOne 응답 HTTP≠200 이거나 `code != 0` 이면 `PaymentProcessingException` 을 던진다(`PortOneApiClient.java:270-275`). 이 예외는 `createCardPayment`(`PaymentCommandService.java:180-184,218-219`) → `processPayment`(`:89-94`) → `OrderCommandService` 가 `OrderPaymentProcessingFailedException` 으로 감싸(`OrderCommandService.java:306-309`) → `OrderBidCommandService.handleOrderBidCreationException` 이 `OrderException` 이므로 그대로 재던짐(`:212-215`). `@Transactional` 이 걸려 있어 **Order/OrderItem/OrderShipment/SaleBid 매칭/창고 상태 변경이 전부 롤백**된다. 호출자는 에러 응답을 받고 OrderBid 도 만들어지지 않는다. 토큰 발급 실패/통신 오류도 같다(`PortOneApiClient.java:240-244, 288-290`).
- `code == 0` 인데 응답 `status` 가 "success" 가 아닌 경우(예: 결제 건 자체는 생성되었으나 실패 상태)는 예외가 없다. Payment 가 `PENDING`/`isSuccess=false` 로 저장되고(`PaymentCommandService.java:203-208`) 그대로 위 "끝까지 성공" 경로를 탄다. Payment 를 `FAILED` 로 두는 코드는 없다.

## 4. 알림 대상, 시점, 전달 방식

- **누가**: 구매자와 판매자 각 1건 (`PaymentCommandService.java:434-456`).
  - 구매자: "결제가 완료되었습니다. 주문 ID: {orderId}" (`:438-443`)
  - 판매자(`sale.getSeller()`): "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}" (`:447-454`)
  - 둘 다 `NotificationCategory.SHOPPING`, `NotificationType.BID`.
- **언제**: `processPayment` 안에서 Payment 저장 직후, 즉 OrderBid 저장 이전이며 Sale 을 SOLD 로 바꾸기 직전(`:83`, `:403`→`:404`). 결제 성공 여부는 확인하지 않는다(위 3번).
- **어떻게**: 동기 호출 + DB 저장 + WebSocket 실시간 푸시.
  - `NotificationCommandService.createNotification` 이 Notification 을 DB 에 저장(`D/notification/service/command/NotificationCommandService.java:52-54`)하고 `sendRealTimeNotification` 호출(`:57`).
  - Redis 에 `WebSocket:User:{email}` 키가 있을 때(접속 중일 때)만 `/queue/notifications` 로 STOMP 전송, 접속 중이 아니면 저장만 한다(`:303-322`).
  - 알림 예외는 삼켜지므로 알림 실패가 구매를 막지 않는다(`PaymentCommandService.java:457-461`, `:421-425`). Kafka 경유가 아니다.
- 부가: 알림 저장은 동일 트랜잭션이라, 이후 단계에서 예외로 롤백되면 알림 행도 롤백되나 이미 푸시된 WebSocket 메시지는 취소되지 않는다(푸시는 트랜잭션과 무관, `:309-313`).

## 5. 최종 주문 상태, 창고 보관 선택 시 차이

**최종 주문 상태**: **`PENDING_PAYMENT`** (`OrderCommandService.java:244`, 이후 변경 없음 — 2번 "주의" 참조). 결제가 PAID 여도 마찬가지다. 함께 남는 상태: SaleBid=MATCHED, OrderBid=MATCHED(isInstantPurchase), Sale=SOLD, OrderShipment=PENDING, Payment=유형/응답에 따라 PAID 또는 PENDING.

**구매자가 "창고 보관"을 선택한 경우**: 사실상 **아무것도 달라지지 않는다**.
- 컨트롤러가 `requestDto.isWarehouseStorage()` 를 서비스에 넘기고(`OrderBidCommandController.java:104-105`), `OrderBidCommandService` 가 `createInstantOrder` 로 전달하지만(`OrderBidCommandService.java:137`), `createInstantOrder` 안에서 `isWarehouseStorage` 파라미터는 **어디서도 읽히지 않는다**(`OrderCommandService.java:219-319`; 파일 내 `isWarehouseStorage` 사용처는 `:163`(다른 메서드의 `requestDto`)과 `:292`(`sale.isWarehouseStorage()`, 판매자 쪽)뿐).
- 일반 결제·배송 경로(`processPaymentAndShipment`)에서는 창고 보관 시 `IN_WAREHOUSE` → WarehouseStorage 생성 → `COMPLETED` 로 가지만(`OrderCommandService.java:163-172`), 즉시 구매 경로에서는 이 로직을 타지 않는다. 구매자의 창고 보관 선택으로 OrderShipment 도 여전히 생성되고(`:264-271`), 구매자용 WarehouseStorage 는 만들어지지 않는다.
- 창고 관련 변화는 구매자의 선택이 아니라 **판매자의 `sale.isWarehouseStorage()`** 에 의해서만 생긴다: 판매자 보관 상품이면 해당 WarehouseStorage 가 `ASSOCIATED_WITH_ORDER` 로 바뀐다(`OrderCommandService.java:291-293`). 상태 전이는 `IN_STORAGE` 에서 허용되며, 이미 SOLD 이면 `InvalidStatusTransitionException` → `OrderWarehouseStorageProcessingFailedException` 으로 전체 롤백된다(`WarehouseStorageCommandService.java:232-256`, `OrderCommandService.java:295-300`).
