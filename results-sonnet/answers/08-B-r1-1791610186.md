경로 약어: `S` = `src/main/java/com/fream/back`

## 0. 선행 사실 (결제·배송 처리 이후 상태)

- 결제+배송 정보 생성은 `POST` 요청 → Kafka producer(`S/domain/order/controller/command/OrderCommandController.java:54`) → consumer `processCompleteOrder`에서 처리된다.
  - `OrderShipment`를 `PENDING`으로 생성: `S/domain/shipment/service/command/OrderShipmentCommandService.java:61-68`
  - 실배송이면 주문은 `PENDING_PAYMENT → PAYMENT_COMPLETED → PREPARING`에서 끝난다: `S/domain/order/service/kafka/OrderEventConsumer.java:195,216-217`
  - 동기 경로도 같다: `S/domain/order/service/command/OrderCommandService.java:175-176`
- 일반 구매 입찰은 `OrderBid`(PENDING)를 만들고 `assignOrder`로 MATCHED가 된다: `S/domain/order/service/command/OrderBidCommandService.java:100`, `S/domain/order/entity/OrderBid.java:128`
- 즉시 구매는 `createInstantOrder`가 주문을 `PENDING_PAYMENT`로 만든 뒤 상태를 바꾸지 않는다. `SaleBid`에 주문을 연결(MATCHED)하고 `OrderBid`(MATCHED, `isInstantPurchase=true`)를 만든다.
  - `S/domain/order/service/command/OrderCommandService.java:241-245,279-280,305`
  - `S/domain/order/service/command/OrderBidCommandService.java:196-205`
- 주문 상태 전이표: `PENDING_PAYMENT→{PAYMENT_COMPLETED, COMPLETED, IN_WAREHOUSE}`, `PREPARING→{IN_WAREHOUSE, SHIPMENT_STARTED}`, `IN_TRANSIT→{COMPLETED}`
  - `S/domain/order/entity/OrderStatus.java:24-29`
  - `Order.updateStatus`는 불허 전이에서 `InvalidOrderStatusException`을 던진다: `S/domain/order/entity/Order.java:113-120`

### 1-2. 의도된 상태 변경 순서와 알림 (코드가 짜인 순서)

2. `OrderShipment`를 조회해 `updateTrackingInfo`를 호출한다. 택배사·운송장을 넣고 상태를 `IN_TRANSIT`으로 직접 세팅하며 전이 검증은 없다: `OrderShipmentCommandService.java:249-256`, `S/domain/shipment/entity/OrderShipment.java:41-45`
3. `Order`를 `IN_TRANSIT`으로 변경한다: `OrderShipmentCommandService.java:259-260`

   - `SaleBid` 조회. 연결된 `Sale`이 SOLD로 전이 가능하면 SOLD로 바꾸고 창고 상태를 갱신하며 판매자에게 알림 "판매 완료"를 보낸다: `OrderShipmentCommandService.java:116-141`
   - 이어서 `OrderBid` 쪽 `Sale`도 같은 처리를 한다: `OrderShipmentCommandService.java:150-176`

   - 이 메서드는 `private`이라 `@Transactional`이 의미 없고, 내부 예외를 삼킨다: `:436-439`
- 즉 이름·주석은 "운송장 등록 = 출발"인데, 실제 코드는 등록 시점에 Sale SOLD와 입찰 COMPLETED까지 앞당겨 처리하려고 한다.

### 1-3. 실배송 일반 구매 입찰 주문에서 끝까지 성공하는가 → 실패한다
- **실패 지점**: `OrderShipmentCommandService.java:260`의 `order.updateStatus(OrderStatus.IN_TRANSIT)`.
  - 주문이 `PREPARING`이라(0항) `PREPARING→IN_TRANSIT`이 전이표에 없다: `OrderStatus.java:26`
  - 그래서 `InvalidOrderStatusException`이 발생한다: `Order.java:117-119`
- **잠재 실패 지점**: 이 지점을 통과하더라도 `updateSaleStatusToSold`의 `saleBidQueryService.findByOrderId`가 SaleBid가 없으면 null이 아니라 `IllegalArgumentException`을 던진다.
  - `S/domain/sale/service/query/SaleBidQueryService.java:26-29`
  - 호출부의 `if (saleBid != null)`(`OrderShipmentCommandService.java:117`)는 의미가 없다.
  - 이 예외는 `:150`의 try 밖이라 전파된다.
- **예외 변환**: 일반 `catch (Exception)`에서 `ShipmentException(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")`로 감싸 던진다: `OrderShipmentCommandService.java:295-301`
- **저장되는 것**: 없다.
  - `@Transactional` 메서드에서 RuntimeException이 나가므로 롤백된다: `:238`
  - 배송의 택배사·운송장·`IN_TRANSIT` 변경은 메모리에서만 일어났고 저장되지 않는다. 배송은 PENDING, 주문은 PREPARING 그대로다.
  - 구매자 알림(`:265`)은 실패 지점(`:260`) 뒤에 있어 생성되지 않는다.
- **응답**: 404와 `ErrorResponse{code:"S001", message:"배송 정보를 찾을 수 없습니다.", status:404, path}`.
  - 핸들러는 예외의 상세 메시지가 아니라 `errorCode.getMessage()`를 쓴다.
  - `S/global/exception/GlobalExceptionHandler.java:459-473`
  - `S/domain/shipment/exception/ShipmentErrorCode.java:12`
  - 실제 원인(`INVALID_ORDER_STATUS`)은 로그에만 남는다.
- 즉시 구매 주문(`PENDING_PAYMENT`)도 `PENDING_PAYMENT→IN_TRANSIT`이 불허라(`OrderStatus.java:24`) 똑같이 같은 지점에서 실패한다.
- 참고: 배송을 `IN_TRANSIT`으로 영속화할 수 있는 경로는 `POST /shipments/order/{id}/check-status`(`OrderShipmentCommandController.java:58`)뿐이다.
  - 이 경로는 `updateTrackingInfo`로 `IN_TRANSIT`을 세팅하고 택배사 조회 결과가 배송완료가 아니면 `IN_TRANSIT`/`OUT_FOR_DELIVERY`만 저장한다. 주문은 건드리지 않는다.
  - `OrderShipmentCommandService.java:472-474,491-498`
  - 그래서 주문은 PREPARING/PENDING_PAYMENT인 채 배송만 IN_TRANSIT인 상태가 만들어질 수 있다.

## 2. 배송 완료 감지

### 2-1. 누가·언제·어떻게
- **스케줄러**: `ShipmentBatchScheduler.scheduleShipmentStatusJob`이 `@Scheduled(cron = "0 0 */6 * * *")`로 6시간마다(00/06/12/18시 정각) Spring Batch Job `updateShipmentStatusesJob`을 실행한다. 파라미터는 timestamp이다.
  - `S/global/config/ShipmentBatchScheduler.java:34-40`
  - 예외는 `printStackTrace`만 한다: `:41-43`
- **Job 구성**: `S/domain/shipment/config/UpdateShipmentStatusesJobConfig.java:55-82`
  - chunk 50, faultTolerant, skip(Exception), skipLimit 50: `:51-52,67,75-77`
- **대상**: JPQL `status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND trackingNumber IS NOT NULL`, 페이지 크기 50: `UpdateShipmentStatusesJobConfig.java:91-96`
- **실제 실행되는 처리 코드**: `ShipmentItemProcessor` (`S/domain/shipment/config/ShipmentItemProcessor.java:57-157`)
  - Step에서 `new ShipmentItemProcessor(...)`로 직접 붙인다: `UpdateShipmentStatusesJobConfig.java:69-73`

### 2-2. 택배사 문자열 → 내부 상태
- `ShipmentItemProcessor.mapToShipmentStatus`: `"배송완료"→DELIVERED`, `"배송출발"→OUT_FOR_DELIVERY`, 그 외 모두 → `IN_TRANSIT`: `ShipmentItemProcessor.java:220-226`
- 같은 매핑이 다른 곳에도 중복 구현돼 있다: `OrderShipmentCommandService.java:399-405`, `UpdateShipmentStatusesJobConfig.java:228-234`
- 현재 상태와 같으면 변경 없이 그대로 반환한다: `ShipmentItemProcessor.java:101-105`
- 부작용: 배송이 `OUT_FOR_DELIVERY`인데 조회 결과가 "배송출발"/"배송완료" 이외의 문자열이면 `IN_TRANSIT`으로 매핑된다.
  - `OUT_FOR_DELIVERY→IN_TRANSIT`은 전이 불가라 `IllegalStateException`이 나고, `ShipmentException`으로 감싸져 skip된다: `S/domain/shipment/entity/ShipmentStatus.java:23-28`, `OrderShipment.java:47-55`, `ShipmentItemProcessor.java:123-125,138-145`

## 3. 배송 완료 판정 이후 (`ShipmentItemProcessor` DELIVERED 분기, `:108-117`)

상태 변경 순서와 알림:
1. `OrderShipment`: `IN_TRANSIT/OUT_FOR_DELIVERY → DELIVERED` (`:113`, 전이 허용 `ShipmentStatus.java:19-20,26`)
2. `orderService.completeOrder(orderId)` (`:116`, `OrderShipmentCommandService.java:190-229`)
   1. `OrderBid`를 조회한다. 없으면 `IllegalArgumentException`: `:196-197`
   2. `Order` → `COMPLETED` (`:204`)
   3. `updateSaleStatusToSold` (`:208`, 본문 `:111-183`): `SaleBid`의 `Sale`이 SOLD 전이 가능하면 SOLD로 바꾸고 판매자에게 알림 1건. 이어서 OrderBid의 `Sale`도 처리하지만 이미 SOLD면 전이가 불가해 건너뛴다(`SaleStatus.java:23`).
   4. 구매자 알림 "[completeOrder] 주문이 완료 처리되었습니다": `:211-217`
   5. 내부 예외는 모두 `ShipmentException(ORDER_NOT_FOUND_FOR_SHIPMENT)`로 감싸 다시 던진다: `:221-228`
3. `notificationService.notifyShipmentCompleted(order)`: 구매자에게 "[배송 완료] 상품이 배송 완료되었습니다" 알림 (`:117`, `S/domain/notification/service/command/NotificationCommandService.java:219-234`). 실패는 로그만 남긴다.
4. Writer `JpaItemWriter`가 배송을 저장한다: `UpdateShipmentStatusesJobConfig.java:74,241-246`

알림 건수:
- 구매자: 2건 ("[completeOrder] …"와 "[배송 완료] …")
- 판매자: Sale이 SOLD로 전이 가능한 경우에만 1건 (4항 참고)

입찰 상태:
- `completeOrder`는 `updateOrderAndSaleBidStatusToCompleted`를 호출하지 않는다. 이 메서드는 `updateTrackingInfo`에서만 호출된다: `OrderShipmentCommandService.java:289`
- 따라서 스케줄러의 배송 완료 처리 후에도 `OrderBid`와 `SaleBid`는 COMPLETED가 되지 않고 MATCHED로 남는다.
- 일반 입찰의 OrderBid 상태는 MATCHED다: `OrderBid.java:128`

## 4. 주문 종류별 차이

### (a) 실배송 일반 구매 입찰 주문 → 끝까지 진행되지 않는다
- 주문은 PREPARING이다(0항).
- 배송이 IN_TRANSIT이라고 가정하면(1-3의 check-status 경로로만 가능) 2항의 `ShipmentItemProcessor`가 배송을 DELIVERED로 세팅한 뒤 `completeOrder`에서 `order.updateStatus(COMPLETED)`를 호출한다: `OrderShipmentCommandService.java:204`
  - `PREPARING→COMPLETED`는 불허라 `InvalidOrderStatusException`이 난다: `OrderStatus.java:26`, `Order.java:117`
  - catch에서 `ShipmentException(S102 ORDER_NOT_FOUND_FOR_SHIPMENT)`로 변환된다: `OrderShipmentCommandService.java:221-228`
  - 프로세서는 이를 그대로 다시 던진다: `ShipmentItemProcessor.java:145`
- 결과:
  - 배송은 DB에서 IN_TRANSIT 그대로(메모리의 DELIVERED는 청크 롤백으로 폐기)
  - 주문은 PREPARING 그대로
  - 알림 0건, `Sale`/`OrderBid`/`SaleBid` 변경 없음
  - 이 건은 skip 처리되고 6시간 뒤 같은 이유로 다시 실패한다.
- 온디맨드 `check-status`에서 DELIVERED면 같은 `completeOrder`가 실패하고 `ShipmentException`이 나가 컨트롤러가 빈 본문의 `ResponseEntity.status(404)`를 반환한다: `OrderShipmentCommandController.java:80-86`, `ShipmentErrorCode.java:19`

### (b) 즉시 구매로 만들어진 주문 → 진행되며 주문은 COMPLETED가 된다
- 주문은 PENDING_PAYMENT이고 `PENDING_PAYMENT→COMPLETED`가 허용돼 있다: `OrderStatus.java:24`
- 배송 IN_TRANSIT 전제는 (a)와 같이 check-status 경로뿐이다. 운송장 PATCH는 1-3대로 실패한다.
- 처리 결과:
  - `OrderShipment`: DELIVERED
  - `Order`: COMPLETED
  - 구매자 알림 2건(`:216`, `NotificationCommandService.java:224`)
  - `SaleBid`는 `findByOrderId`로 조회되지만(`SaleBid.assignOrder`로 연결됨, `OrderCommandService.java:279`), `Sale`의 상태가 `PENDING_SHIPMENT`/`IN_TRANSIT`/`IN_STORAGE`이면 SOLD 전이가 불가해 `Sale`은 바뀌지 않는다.
    - 코드상 `Sale`을 `SELLING`/`ON_AUCTION`으로 만드는 곳이 없다. SOLD 전이가 가능한 상태는 둘뿐인데 어디서도 그 상태로 만들지 않는다: `SaleStatus.java:17-22`, `SellerShipmentCommandService.java:82`(IN_STORAGE까지만)
    - 따라서 판매자 알림과 창고 SOLD 갱신은 일어나지 않는다. 판매자가 알림을 받으려면 DB에서 Sale이 ON_AUCTION/SELLING이어야 한다.
  - `OrderBid`(즉시 구매 플래그)와 `SaleBid`는 MATCHED로 남는다(COMPLETED 아님). `OrderShipmentCommandService.java:289`는 이 경로에서 호출되지 않는다.

차이 요약: (a)는 주문 상태 전이가 막혀 어떤 변경도 저장되지 않고, (b)는 주문이 COMPLETED로 바뀌고 구매자가 알림 2건을 받으나 입찰 두 개는 모두 MATCHED로 남는다.

## 5. 실패 처리 (주기 처리 중 한 건 실패)

- Step이 `faultTolerant().skip(Exception.class).skipLimit(50)`이다: `UpdateShipmentStatusesJobConfig.java:75-77`
- 한 건에서 예외(`ShipmentException`, 조회 실패, 파싱 실패, 상태 전이 불가 등)가 나면:
  - 그 건은 skip되고 `shipmentSkipListener`가 `[Skip]` 로그를 남긴다: `:78,251-266`
  - 처리 도중 `completeOrder`가 바꾼 변경(주문 COMPLETED, 알림 등)은 청크 트랜잭션 롤백으로 폐기된다. 같은 트랜잭션에 참여하는 `@Transactional` 호출이기 때문이다.
  - 같은 청크(50건)의 나머지 건은 롤백 뒤 건별로 다시 처리되어 정상 건은 커밋되고, 해당 건만 건너뛴다. 이 재처리 때 Playwright 조회가 다시 실행된다.
  - 실패한 배송은 DB 상태가 그대로라 다음 주기(6시간 뒤)에 다시 대상이 된다.
- skip이 50건을 넘으면 Step이 실패하고 남은 건은 처리되지 않는다. `jobLauncher.run`은 예외를 던지지 않고 스케줄러에도 별도 처리가 없다: `ShipmentBatchScheduler.java:36-43`
- 참고: 위의 "한 건 실패 시 나머지 진행"은 실제 실행되는 배치 경로의 동작이다. 호출되지 않는 `updateShipmentStatuses()`에는 건별 try/catch가 있지만 실행되지 않는다: `OrderShipmentCommandService.java:322-388`
