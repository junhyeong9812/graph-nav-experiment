# 구매자 배송: 운송장 등록 → 배송 완료 (코드 기준 실제 동작)

경로 약어: `P` = `src/main/java/com/fream/back`

**한 줄 결론:** 의도된 흐름은 "운송장 등록 → Order IN_TRANSIT → Bid COMPLETED → (6시간 배치가 CJ 조회) → DELIVERED → Order COMPLETED"다. 그러나 실제로는 ① 일반(실배송) 주문에서 운송장 등록이 항상 실패하고(Order가 PREPARING), ② 배송 완료 처리(`completeOrder`)도 PREPARING→COMPLETED가 막혀 실패하며, ③ 즉시 구매 주문만 `completeOrder`가 통과한다.

---

## 1. 운송장 등록 요청

### 1-1. 진입 API
- `PATCH /shipments/order/{shipmentId}/status`, body `OrderShipmentRequestDto(courier, trackingNumber)` → `OrderShipmentCommandService#updateTrackingInfo`
  - `P/domain/shipment/controller/command/OrderShipmentCommandController.java:20,33-49`
- (참고) 수동 조회용 `POST /shipments/order/{shipmentId}/check-status`도 송장을 갱신한다: `OrderShipmentCommandController.java:58-72` → `OrderShipmentCommandService.java:452,473`
- 인증은 필요하나 소유자/관리자 검증 코드는 없다(컨트롤러·서비스에 없음).

### 1-2. 의도된 상태 변경 순서 / 알림 (`OrderShipmentCommandService.java:239-303`)
1. courier/trackingNumber 공백 검증 → `TRACKING_INFO_REQUIRED` (:243-246)
2. `OrderShipment.updateTrackingInfo` → 전이 검증 없이 `status=IN_TRANSIT` (:256, `P/domain/shipment/entity/OrderShipment.java:41-45`)
3. `order.updateStatus(OrderStatus.IN_TRANSIT)` (:259-260)
4. **구매자**에게 "상품이 출발하였습니다. 주문 ID" 알림 1건 (:264-271)
5. `updateSaleStatusToSold(orderId)` (:276, 정의 :112-183): SaleBid 경로/OrderBid 경로의 Sale이 `canTransitionTo(SOLD)`이면 SOLD + 창고보관이면 창고 SOLD + **판매자** 알림 (:116-138, :150-172)
6. SaleBid의 Sale이 창고보관이면 창고 SOLD (:279-286)
7. `updateOrderAndSaleBidStatusToCompleted` → OrderBid·SaleBid가 MATCHED면 COMPLETED (:289, 정의 :413-)
   (`@Transactional private`이라 프록시 트랜잭션은 적용되지 않고, 내부 예외는 로그만 남기고 삼킴 :412-413)

### 1-3. 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문 — 끝까지 성공하지 못한다
- 결제 후 Kafka 처리에서 실배송 주문은 `PAYMENT_COMPLETED → PREPARING`에서 멈춘다 (`P/domain/order/service/kafka/OrderEventConsumer.java:195,214-218`). 이때 OrderShipment는 PENDING(`OrderShipmentCommandService.java:67`).
- 전이표: `PREPARING`은 `IN_WAREHOUSE, SHIPMENT_STARTED`만 허용, `IN_TRANSIT`은 `SHIPMENT_STARTED`에서만 가능 (`P/domain/order/entity/OrderStatus.java:26,28`). `SHIPMENT_STARTED`를 설정하는 코드는 없다.
- **실패 지점:** 3단계 `order.updateStatus(IN_TRANSIT)` (`OrderShipmentCommandService.java:260`)에서 `Order.updateStatus`가 `InvalidOrderStatusException`을 던진다 (`P/domain/order/entity/Order.java:113-121`).
- 이 예외는 `OrderException`(GlobalException)이지 `ShipmentException`이 아니므로 `catch (Exception)`에 걸려 `ShipmentException(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: ...")`로 래핑된다 (:295-302).
- **저장되는 것:** 없음. 4단계 알림 이전에 예외가 나므로 알림 0건이고, `@Transactional`(:238)이 롤백되어 3·2단계의 메모리 변경(shipment IN_TRANSIT+송장번호)도 DB에 반영되지 않는다. OrderShipment는 PENDING·송장 없음, Order는 PREPARING 그대로.
- **응답:** `GlobalExceptionHandler#handleShipmentException` (`P/global/exception/GlobalExceptionHandler.java:459-473`) → **HTTP 404, code `S001`, message "배송 정보를 찾을 수 없습니다."** (`ShipmentErrorCode.java:SHIPMENT_NOT_FOUND`). enum 기본 문구가 나가고 커스텀 메시지는 응답 body에 안 들어간다. 실제 원인(상태 전환 불가)은 로그에만 남는다.
- 창고 보관 주문도 `COMPLETED`(IN_WAREHOUSE→COMPLETED, `OrderEventConsumer.java:206-211`)라 `COMPLETED→IN_TRANSIT`이 막혀 동일하게 실패한다. 즉시 구매 주문은 PENDING_PAYMENT라 `PENDING_PAYMENT→IN_TRANSIT`이 허용되지 않아 역시 실패한다 (`OrderStatus.java:24`).
- 그 외 SaleBid가 없는 주문이면 5단계 `saleBidQueryService.findByOrderId`가 null이 아닌 `IllegalArgumentException`을 던진다 (`P/domain/sale/service/query/SaleBidQueryService.java:26-29`) — 이미 3단계에서 먼저 실패하지만 설계상 별도 결함.

## 2. 배송 완료 감지

### 2-1. 누가/언제/어떻게
- **스케줄러 `ShipmentBatchScheduler#scheduleShipmentStatusJob`** — `@Scheduled(cron = "0 0 */6 * * *")` = **6시간마다 정각(0,6,12,18시)**, `jobLauncher.run(updateShipmentStatusesJob, timestamp)` (`P/global/config/ShipmentBatchScheduler.java:34-44`). 예외는 `printStackTrace`만.
- 사람이 `POST /shipments/order/{id}/check-status`로 즉시 조회하는 경로도 있음(1-1). 자동 감지는 배치뿐이다.

### 2-2. 조회 대상
- Reader: `SELECT s FROM OrderShipment s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL`, page 50 (`P/domain/shipment/config/UpdateShipmentStatusesJobConfig.java:87-97`).
- Step: chunk 50, `faultTolerant().skip(Exception.class).skipLimit(50)` (:63-81).
- 주의: 1-3에 따라 운송장 등록(PATCH)이 실패하므로 일반 주문의 shipment는 PENDING에 머물러 **배치 대상에 들어오지 못한다.** 대상이 되는 건 `check-status` API가 shipment를 IN_TRANSIT/OUT_FOR_DELIVERY로 저장한 건뿐이다.

### 2-3. 실제 실행되는 처리 코드 (비슷한 코드 구분)
| 후보 | 실제 실행 여부 |
|---|---|
| **`ShipmentItemProcessor#process`** | **실행됨.** Step이 `new ShipmentItemProcessor(playwrightBrowserManager(), notificationService, orderService)`를 processor로 등록 (`UpdateShipmentStatusesJobConfig.java:69-73`). 공유 Playwright 브라우저로 CJ 페이지 로드 → Jsoup으로 `tbody#statusDetail tr` 마지막 행 5번째 td 파싱 (`P/domain/shipment/config/ShipmentItemProcessor.java:57-95,167-191`) |
| `UpdateShipmentStatusesJobConfig#shipmentItemProcessor()` 빈 + `parseCjLogisticsStatus` | Step이 참조하지 않음(미사용) (:104-177, :186-220) |
| `OrderShipmentCommandService#updateShipmentStatuses` | 호출처 없음(미사용). 게다가 `completeOrder`가 아니라 `order.updateStatus(COMPLETED)`를 직접 호출 (:309-, :355) |
| `CjTrackingPlaywright#getCurrentTrackingStatus` | 배치가 아니라 수동 `check-status` API에서만 사용 (`OrderShipmentCommandService.java:476`) |

### 2-4. 택배사 상태 문자열 → 내부 상태
`ShipmentItemProcessor#mapToShipmentStatus` (`ShipmentItemProcessor.java:220-226`):
- `"배송완료"` → `DELIVERED`
- `"배송출발"` → `OUT_FOR_DELIVERY`
- 그 외 모든 문자열 → `IN_TRANSIT` (완전 일치 `switch`, 부분일치/공백 변형은 IN_TRANSIT)
- 현재 shipment 상태와 매핑 결과가 같으면 아무것도 안 하고 반환 (:101-105).

## 3. 배송 완료 판정 이후 (`ShipmentItemProcessor.java:108-117`, 의도된 순서)
1. `orderShipment.updateStatus(DELIVERED)` — IN_TRANSIT/OUT_FOR_DELIVERY→DELIVERED 허용 (`P/domain/shipment/entity/ShipmentStatus.java:16-26`), 메모리 변경 후 Writer(JpaItemWriter, `UpdateShipmentStatusesJobConfig.java:239-246`)가 저장
2. `OrderShipmentCommandService#completeOrder(orderId)` (`OrderShipmentCommandService.java:191-229`):
   1. `OrderBidQueryService#findByOrderId` (없으면 IllegalArgumentException, :196-197; 쿼리 `P/domain/order/service/query/OrderBidQueryService.java:51-56`)
   2. **Order → COMPLETED** (`order.updateStatus(COMPLETED)`, :204). 허용 출발 상태: PENDING_PAYMENT, IN_WAREHOUSE, IN_TRANSIT (`OrderStatus.java:24,27,29`)
   3. `updateSaleStatusToSold(orderId)` (:208): Sale이 SOLD로 전이 가능할 때만 Sale→SOLD + **판매자 알림 1건** (+창고보관이면 창고 SOLD)
   4. **구매자** 알림 "[completeOrder] 주문이 완료 처리되었습니다" 1건 (:210-217)
   5. 모든 예외는 `ShipmentException(ORDER_NOT_FOUND_FOR_SHIPMENT S102)`로 래핑 (:221-228)
3. `NotificationCommandService#notifyShipmentCompleted(order)` → **구매자** "[배송 완료] 상품이 배송 완료되었습니다" 1건 (`ShipmentItemProcessor.java:117`, `P/domain/notification/service/command/NotificationCommandService.java:219-234`; 이 메서드는 내부 예외를 삼킴)

**알림 건수(성공 시):** 구매자 2건(`[completeOrder]` + `[배송 완료]`) + 판매자 최대 1건(Sale이 아직 SOLD 가능 상태일 때만). 사전 운송장 등록 단계의 알림(구매자 "출발", 판매자 "판매 완료")은 1-2의 경로로 이미 갔을 수 있으나 1-3 때문에 일반 주문에선 가지 않는다.

**입찰 상태:** `completeOrder`/배치는 OrderBid·SaleBid 상태를 **건드리지 않는다.** `COMPLETED`로 바꾸는 코드는 `updateOrderAndSaleBidStatusToCompleted`(운송장 등록 `updateTrackingInfo`에서만 호출, :289)뿐이다. 따라서 배송 완료 시점의 OrderBid/SaleBid는 `MATCHED` 그대로다 (`OrderBid.java:60-82`, `SaleBid.java:53-61`에서 MATCHED가 설정됨).

## 4. 주문 종류별 차이

### (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문 — 끝까지 진행 안 됨
- Order는 PREPARING (`OrderEventConsumer.java:214-218`). 3-2-2의 `order.updateStatus(COMPLETED)`에서 `PREPARING→COMPLETED`는 허용되지 않아(`OrderStatus.java:26`) `InvalidOrderStatusException` → `ShipmentException(S102)` (`OrderShipmentCommandService.java:204,221-228`).
- 이 때문에 `updateSaleStatusToSold`(판매자 알림), 구매자 `[completeOrder]` 알림, `notifyShipmentCompleted`는 모두 실행되지 않는다. Order는 PREPARING, 입찰은 MATCHED 유지, shipment DELIVERED 변경도 롤백(5 참고). 배송 완료는 영원히 반영되지 않는다.
- 추가로 1-3에 의해 애초에 배치 대상(IN_TRANSIT)이 되려면 `check-status`를 거쳐야 하고, `check-status`에서 CJ가 "배송완료"를 주면 `completeOrder`(:489)에서 같은 이유로 실패, 응답은 `ShipmentException`의 status만 있는 빈 body (`OrderShipmentCommandController.java:80-86`, S102 → 404).

### (b) 즉시 구매로 만들어진 주문 — `completeOrder`는 끝까지 진행됨
- 생성 상태: Order=PENDING_PAYMENT 유지 (`P/domain/order/service/command/OrderCommandService.java:241-245`, 결제 후에도 변경 코드 없음), OrderShipment=PENDING (:264-271), SaleBid.order=order·MATCHED (:279-280), OrderBid는 `order` 연결·MATCHED·즉시구매 플래그 (`P/domain/order/service/command/OrderBidCommandService.java:189-206`), Sale은 결제 직후 이미 **SOLD**이고 구매자/판매자 알림도 그때 발송 (`P/domain/payment/service/command/PaymentCommandService.java:383-420`).
- 운송장 등록 `PATCH`는 `PENDING_PAYMENT→IN_TRANSIT` 불가로 (a)와 같이 실패(404 S001). 배송 완료까지 가려면 `check-status`로 shipment를 IN_TRANSIT/OUT_FOR_DELIVERY로 만들어야 한다 (`OrderShipmentCommandService.java:473-497`; CJ가 "배송완료"면 즉시 DELIVERED + `completeOrder`, :486-489).
- `completeOrder` 진행: OrderBid 조회 성공 → `PENDING_PAYMENT→COMPLETED` **허용**(`OrderStatus.java:24`) → Order=COMPLETED. `updateSaleStatusToSold`에서 Sale은 이미 SOLD라 `canTransitionTo(SOLD)`가 false(`P/domain/sale/entity/SaleStatus.java:23`) → Sale 변경·판매자 알림·창고 SOLD 모두 생략 (:119,156). 구매자 `[completeOrder]` 1건. 배치 경로면 `[배송 완료]` 1건 추가(총 구매자 2건).
- 결과: Order COMPLETED, Shipment DELIVERED, **판매자 신규 알림 0건**, OrderBid/SaleBid는 MATCHED 그대로(COMPLETED로 바뀌지 않음), 창고보관 Sale이어도 창고 상태 SOLD 처리는 이 경로에선 안 됨.
- 참고: `check-status`에서 CJ 결과가 IN_TRANSIT이면 `updateTrackingInfo`가 이미 IN_TRANSIT으로 만든 뒤 `updateStatus(IN_TRANSIT)`(IN_TRANSIT→IN_TRANSIT 불허)가 `IllegalStateException` → S302로 롤백되므로 shipment가 저장되지 않는다 (:497, `ShipmentStatus.java:19-20`).

## 5. 실패 처리 (주기 배치)
- Step이 `faultTolerant().skip(Exception.class).skipLimit(50)`이라 처리(process) 중 예외는 **그 건만 skip**된다. 건별 예외(S003 번호 없음, S301 파싱 실패, S302 조회 오류, S102 completeOrder 실패 등)는 `process`의 catch에서 `ShipmentException`으로 통일돼 던져진다 (`ShipmentItemProcessor.java:133-145`), SkipListener가 에러 로그만 남긴다 (`UpdateShipmentStatusesJobConfig.java:251-286`).
- skip된 건은 Writer로 넘어가지 않아 저장되지 않고 DB 상태는 그대로(IN_TRANSIT/OUT_FOR_DELIVERY)이므로 **다음 6시간 주기에 다시 대상**이 된다.
- 나머지 건은 계속 처리된다. `completeOrder`는 `@Transactional`이라 청크 트랜잭션에 참여하며 예외가 나면 청크 트랜잭션이 롤백 마킹된다 → Spring Batch가 그 청크를 건별로 다시 처리하며 실패 건만 건너뛴다(롤백된 청크의 다른 건은 재처리되어 반영).
- 한도: skip이 **50건을 넘으면** `SkipLimitExceededException`으로 Step/Job이 실패하고 남은 건은 그 회차에 처리되지 않는다. 스케줄러는 예외를 `printStackTrace`만 한다 (`ShipmentBatchScheduler.java:41-43`).
- 브라우저는 Step 시작 시 열고 종료 시 닫는다(`BrowserManageStepListener`, `UpdateShipmentStatusesJobConfig.java:80`). 한 건의 페이지는 `finally`에서 닫힌다 (`ShipmentItemProcessor.java:146-156`).
- (추론, 프레임워크 동작) 롤백된 청크를 다시 처리할 때 processor가 같은 메모리 객체에 이미 `DELIVERED`를 넣어 둔 상태라 "상태 동일 → 변경 없음" 분기(`ShipmentItemProcessor.java:101-105`)로 빠질 수 있다. 이 경우 롤백된 앞쪽 건은 `completeOrder` 재실행 없이 shipment만 DELIVERED로 저장될 위험이 있다. 이는 코드 리딩에 기반한 추론이며 실행으로 검증하지 않았다.
