# 구매자 배송: 운송장 등록 → 배송 완료 처리 분석

경로 약어 (모두 `src/main/java/com/fream/back/` 아래):
- `SVC` = `domain/shipment/service/command/OrderShipmentCommandService.java`
- `JOB` = `domain/shipment/config/UpdateShipmentStatusesJobConfig.java`
- `PROC` = `domain/shipment/config/ShipmentItemProcessor.java`
- `CTRL` = `domain/shipment/controller/command/OrderShipmentCommandController.java`
- `OCS` = `domain/order/service/command/OrderCommandService.java`

## 사전: 주문·배송이 결제 후 어떤 상태가 되는가

- 일반 구매 입찰 주문은 `PENDING_PAYMENT` 로 생성된다 (`OCS:81`). 결제·배송 정보 처리(`processPaymentAndShipment`)에서 `OrderShipment` 가 `PENDING` 으로 생성되고(`SVC:61-68`, 호출 `OCS:148`), 실배송이면 주문 상태는 `PAYMENT_COMPLETED → PREPARING` 에서 멈춘다 (`OCS:174-176`; Kafka 경로도 동일 `domain/order/service/kafka/OrderEventConsumer.java:216-217`).
- 주문 상태 전이표: `PAYMENT_COMPLETED→{PREPARING,REFUND_REQUESTED,IN_WAREHOUSE}`, `PREPARING→{IN_WAREHOUSE,SHIPMENT_STARTED}`, `SHIPMENT_STARTED→{IN_TRANSIT}`, `IN_TRANSIT→{COMPLETED}`, `PENDING_PAYMENT→{PAYMENT_COMPLETED,COMPLETED,IN_WAREHOUSE}` (`domain/order/entity/OrderStatus.java:24-31`). 위반하면 `InvalidOrderStatusException` (`domain/order/entity/Order.java:113-121`).
- `SHIPMENT_STARTED` 로 바꾸는 코드는 코드베이스 어디에도 없다 (`OrderStatus.` 사용처 grep: 위 결제 경로와 `SVC:204,260,355` 뿐). 즉 실배송 주문은 `PREPARING` 에서 `IN_TRANSIT` 으로 갈 방법이 없다.

## 1. 운송장 등록 요청

### 1-1. 진입 API
- `PATCH /shipments/order/{shipmentId}/status`, 바디 `OrderShipmentRequestDto`(courier, trackingNumber) → `OrderShipmentCommandController#updateTrackingInfo` (`CTRL:27-50` 부근, `@RequestMapping("/shipments/order")` `CTRL:20`) → `OrderShipmentCommandService#updateTrackingInfo` (`SVC:238-303`). 성공 시 `200 OK` 본문 없음.
- (보조) `POST /shipments/order/{id}/check-status`, `/check-status-string` 도 운송장을 받아 `updateAndCheckShipmentStatus` 로 즉시 조회·갱신한다 (`CTRL:39-119`, `SVC:451-516`). 아래 4·5 에서 다시 언급.

### 1-2. 의도된 상태 변경 순서와 알림 (`SVC:238-303`)
1. courier/trackingNumber 공백 검사 → `TRACKING_INFO_REQUIRED`(400) (`SVC:243-246`).
2. `OrderShipment` 조회 후 `updateTrackingInfo` : 택배사·운송장 저장 + 배송 상태를 **무조건 `IN_TRANSIT`** 으로 설정(전이 검증 없음) (`SVC:256`, `domain/shipment/entity/OrderShipment.java:41-45`).
3. `Order` → `IN_TRANSIT` (`SVC:259-260`).
4. 구매자에게 알림 1건 "상품이 출발하였습니다. 주문 ID: …" (`SVC:265-271`).
5. `updateSaleStatusToSold(orderId)` (`SVC:276`, 본체 `SVC:111-183`): SaleBid→Sale 이 `SOLD` 로 전이 가능하면 `Sale` → `SOLD`, 창고 보관이면 창고 상태 SOLD, **판매자에게 알림 1건** "상품이 성공적으로 판매 완료되었습니다…" (`SVC:116-147`). 이어 OrderBid 쪽 Sale 도 같은 처리(전이가 이미 불가능하면 건너뜀, `SVC:150-180`).
6. 창고 보관 Sale 이면 창고 상태 SOLD 재호출 (`SVC:279-286`).
7. `updateOrderAndSaleBidStatusToCompleted` : `OrderBid(MATCHED)` → `COMPLETED`, `SaleBid(MATCHED)` → `COMPLETED` (`SVC:289`, `SVC:412-440`). 즉 입찰 COMPLETED 는 **배송 완료가 아니라 운송장 등록 시점**에 일어나도록 짜여 있다. (`@Transactional private` 은 자기호출·private 이라 무의미, 내부 예외는 try/catch 로 삼킨다 `SVC:436-439`.)

요약: 알림은 구매자 1건(출발) + 판매자 1건(판매 완료, Sale 이 SOLD 가능할 때만).

### 1-3. 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문 — 끝까지 성공하지 않는다
- 실패 지점: `SVC:260` `order.updateStatus(OrderStatus.IN_TRANSIT)`. 주문은 `PREPARING` 인데 `PREPARING→IN_TRANSIT` 은 허용되지 않아(`OrderStatus.java:26`) `InvalidOrderStatusException` 발생 (`Order.java:117`).
- 이 예외는 `ShipmentException` 이 아니므로 `catch (Exception e)` (`SVC:295-302`) 에서 `ShipmentException(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: 상태 전환이 허용되지 않습니다: PREPARING -> IN_TRANSIT")` 로 감싸 던진다 (`SVC:297-301`).
- 저장되는 것: **없음**. 메서드가 `@Transactional`(`SVC:238`) 이고 런타임 예외가 밖으로 나가므로 롤백된다. 2단계에서 바꾼 `OrderShipment` 의 courier/trackingNumber/`IN_TRANSIT` 도 DB 에 남지 않고(배송은 `PENDING` 유지), 알림(4단계)·Sale/입찰 변경(5~7단계)은 도달하지도 않는다.
- 응답: 이 엔드포인트는 try/catch 가 없어 `GlobalExceptionHandler#handleShipmentException` 이 처리 → HTTP **404**, `ErrorResponse(code="S001", message="배송 정보를 찾을 수 없습니다.", status=404, path)` (`global/exception/GlobalExceptionHandler.java:459-473`, `domain/shipment/exception/ShipmentErrorCode.java:12`). 응답 본문 message 는 ErrorCode 의 고정 문구라 상세 사유는 로그에만 남는다.
- 추가로, 설령 주문이 `IN_TRANSIT` 이어도 연결된 SaleBid 가 없으면 `SaleBidQueryService#findByOrderId` 가 null 이 아니라 `IllegalArgumentException` 을 던진다 (`domain/sale/service/query/SaleBidQueryService.java:26-29`). `updateSaleStatusToSold` 의 `if (saleBid != null)` 는 이 경우 무의미하며 `SVC:116` 에서 예외가 전파되어 같은 404 로 실패한다. 일반 구매 입찰은 판매자가 매칭(`createInstantSaleBid`, `domain/sale/service/command/SaleBidCommandService.java:~60-90`)되기 전에는 SaleBid 가 없다.

## 2. 배송 완료 감지

### 2-1. 누가·언제·어떻게
- 감지 주체는 스프링 배치 잡 `updateShipmentStatusesJob` 이며, `ShipmentBatchScheduler#scheduleShipmentStatusJob` 가 `@Scheduled(cron = "0 0 */6 * * *")` 로 **6시간마다(서버 시간 00·06·12·18시 정각)** 실행한다 (`global/config/ShipmentBatchScheduler.java:34-44`, 매번 timestamp 파라미터로 새 JobInstance). 스케줄링은 다른 클래스의 `@EnableScheduling` 으로 활성(`domain/event/scheduler/EventStatusScheduler.java:22`).
- 잡 구성: 청크 50, `faultTolerant().skip(Exception.class).skipLimit(50)` (`JOB:51-52,66-81`).
- Reader: `SELECT s FROM OrderShipment s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL` (`JOB:95`). 즉 운송장이 있고 IN_TRANSIT / OUT_FOR_DELIVERY 인 배송만 조회한다.
- 수동 경로: `POST …/check-status` 로 운영자가 단건을 즉시 조회할 수 있다 (`SVC:451-516`).

### 2-2. 실제로 실행되는 처리 코드 (비슷한 코드가 여럿)
| 후보 | 실제 실행 여부 | 근거 |
|---|---|---|
| `ShipmentItemProcessor#process` (Playwright 페이지 직접 조작, `PlaywrightBrowserManager` 사용) | **실행됨** | 스텝이 `new ShipmentItemProcessor(playwrightBrowserManager(), notificationService, orderService)` 로 직접 생성해 `.processor(...)` 에 등록 (`JOB:69-73`), 본체 `PROC:57-157` |
| `JOB#shipmentItemProcessor` @Bean (람다, `CjTrackingPlaywright` 사용) | 미사용 — 빈은 있으나 스텝에서 참조 안 함 | `JOB:104-177`, 스텝은 `JOB:69` 에서 위 클래스를 new |
| `JOB#parseCjLogisticsStatus` (Jsoup) | 미사용 private 메서드 | `JOB:186-220` |
| `OrderShipmentCommandService#updateShipmentStatuses` | 미사용 — 호출하는 스케줄러/코드가 없음 (전체 grep 정의 1건) | `SVC:305-391` |

→ 실행되는 쪽은 **`ShipmentItemProcessor#process`**. 이후 3·4·5 의 "배치 경로"는 이 클래스 기준이다.

### 2-3. 택배사 상태 문자열 → 내부 상태
- CJ대한통운 페이지(`https://trace.cjlogistics.com/next/tracking.html?wblNo=`)의 `tbody#statusDetail tr` 마지막 행 5번째 `td` 텍스트(trim)를 상태 문자열로 사용 (`PROC:28-29,167-191`). 행이 없거나 빈 문자열이면 `TRACKING_HTML_PARSE_ERROR`.
- 매핑 (`PROC:220-226`, 다른 복제본도 동일 `JOB:228-234`, `SVC:399-405`): `"배송완료"` → `DELIVERED`, `"배송출발"` → `OUT_FOR_DELIVERY`, **그 외 모든 문자열**(집화, 이동중 등 포함) → `IN_TRANSIT`. 정확히 일치(equals)할 때만 앞의 두 값이 된다.
- 현재 상태와 같은 값이면 아무것도 하지 않고 반환 (`PROC:101-105`).

## 3. 배송 완료 판정 이후 (실행되는 배치 경로 `PROC:107-117`)

상태가 바뀌는 순서:
1. `OrderShipment` → `DELIVERED` (`PROC:113`, 전이 검증: IN_TRANSIT/OUT_FOR_DELIVERY→DELIVERED 허용 `domain/shipment/entity/ShipmentStatus.java:16-28`).
2. `OrderShipmentCommandService#completeOrder(orderId)` (`PROC:116`, `SVC:190-229`):
   1. `OrderBid` 조회 (`SVC:196-197`)
   2. `Order` → `COMPLETED` (`SVC:204`)
   3. `updateSaleStatusToSold` (`SVC:208`): Sale 이 아직 SOLD 가 아니고 전이 가능할 때만 `Sale→SOLD`(+창고) 및 판매자 알림
   4. 구매자 알림 "[completeOrder] 주문이 완료 처리되었습니다. 주문 ID: …" (`SVC:211-217`)
3. `NotificationCommandService#notifyShipmentCompleted` : 구매자에게 "[배송 완료] 상품이 배송 완료되었습니다. 주문 ID: …" (`PROC:117`, `domain/notification/service/command/NotificationCommandService.java:219-229`, 내부 예외는 삼킴 `:230-233`).
4. Writer(`JpaItemWriter`)가 `OrderShipment` 를 저장 (`JOB:239-246`).

알림 건수:
- 구매자: **2건** ("[completeOrder] …" + "[배송 완료] …").
- 판매자: **보통 0건**. 판매자 알림은 `Sale` 이 `SOLD` 로 전이 가능할 때(= ON_AUCTION/SELLING)만 나가는데(`SaleStatus.java:75-85`, `SVC:119`), 결제 시점에 이미 Sale 을 SOLD 로 바꾸기 때문에(`domain/payment/service/command/PaymentCommandService.java:404,419`) 이미 SOLD 이면 `canTransitionTo` 가 false 라 건너뛴다(`SVC:142-144`). 운송장 등록(1-2의 5단계)에서 SOLD 가 됐어도 동일. 전이가 가능한 상태로 남아 있던 예외 경우에만 판매자 1건.
- (수동 `check-status` 경로는 `completeOrder` 만 호출하고 `notifyShipmentCompleted` 는 호출하지 않아 구매자 1건 — `SVC:483-489`.)

주문 입찰·판매 입찰 상태: **이 배송 완료 경로는 `OrderBid`/`SaleBid` 상태를 바꾸지 않는다.** `completeOrder` 에는 입찰 상태 변경이 없고 (`SVC:190-229`), COMPLETED 변경은 운송장 등록 메서드의 `updateOrderAndSaleBidStatusToCompleted` 에만 있다 (`SVC:289,412-440`). 따라서 배송 완료 시점의 입찰은 매칭된 `MATCHED` 그대로 남는다 (운송장 등록이 성공해 이미 COMPLETED 가 된 경우만 COMPLETED).

## 4. 주문 종류별 차이

### (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문 — 끝까지 진행되지 않는다
- 주문 상태는 `PREPARING` (사전 참고). 운송장 등록 API 가 1-3 처럼 실패해 배송이 `IN_TRANSIT`+운송장 상태가 되지 못하므로 배치 Reader 대상(`JOB:95`)에도 들어오지 않는다.
- 우회로(`check-status`)로 배송이 `OUT_FOR_DELIVERY`/`IN_TRANSIT` 이 됐다 하더라도(`SVC:473,491-493`; 운송장 갱신 시 `IN_TRANSIT` 이 된 상태에서 `IN_TRANSIT→IN_TRANSIT` 은 불허라 "그 외" 분기는 `IllegalStateException`→`EXTERNAL_TRACKING_SERVICE_ERROR` 503, `SVC:495-498`, `ShipmentStatus.java:19-21`, `OrderShipment.java:47-55`), `DELIVERED` 판정 후 `completeOrder` 의 `order.updateStatus(COMPLETED)` 에서 `PREPARING→COMPLETED` 불허로 실패한다 (`SVC:204`, `OrderStatus.java:26`). `completeOrder` 의 `catch (Exception)` 이 `ShipmentException(ORDER_NOT_FOUND_FOR_SHIPMENT)` 로 감싸 던진다 (`SVC:221-228`).
- 설령 주문이 IN_TRANSIT 이어서 통과해도 SaleBid 가 없으면 `updateSaleStatusToSold` 의 `findByOrderId` 가 `IllegalArgumentException` 을 던져 같은 방식으로 실패 (`SVC:116`, `SaleBidQueryService.java:26-29`).
- 결과: Order 는 `PREPARING` 유지, 배송은 DELIVERED 로 저장되지 않음(롤백/스킵), 알림 0건, Sale/입찰 변경 없음.

### (b) 즉시 구매로 만든 주문 — 3의 처리가 끝까지 진행된다 (단, 운송장 등록 API 로는 배송 상태 진입 불가)
- 즉시 구매 주문은 `PENDING_PAYMENT` 로 만들어지고 `OrderShipment(PENDING)` 이 생성되며(`OCS:244,264`), SaleBid 에 `assignOrder` 로 order 가 연결되고 `MATCHED`(`OCS:279-280`, `domain/sale/entity/SaleBid.java:58-61`), OrderBid 는 `MATCHED` + sale + order + 즉시구매 플래그로 생성된다 (`domain/order/service/command/OrderBidCommandService.java:192-205`). 결제 처리 후에도 주문 상태는 `PENDING_PAYMENT` 로 남는다 (`OCS:305`, 결제 서비스에 OrderStatus 변경 없음), Sale 은 결제 시 `SOLD` (`PaymentCommandService.java:404,419`).
- 운송장 등록 API 는 (a) 와 같은 이유로 실패한다: `PENDING_PAYMENT→IN_TRANSIT` 불허 (`OrderStatus.java:24`, `SVC:260`) → 404 S001, 롤백.
- 그러나 `check-status` 로 운송장이 붙어 `IN_TRANSIT`/`OUT_FOR_DELIVERY` 가 되면(`SVC:473`) 배송 완료 시 `completeOrder` 가 통과한다: OrderBid 있음, `PENDING_PAYMENT→COMPLETED` 허용(`OrderStatus.java:24`), SaleBid 있음(`findByOrderId` 정상), Sale 은 이미 SOLD 라 변경·판매자 알림 없음.
- 결과: Order `COMPLETED`, 배송 `DELIVERED`, 구매자 알림 2건(배치) 또는 1건(check-status), 판매자 알림 0건, OrderBid/SaleBid 는 `MATCHED` 유지(COMPLETED 로 안 바뀜).
- 차이 요약: (a) 는 `PREPARING→COMPLETED` 불허 + SaleBid 부재로 실패, (b) 는 `PENDING_PAYMENT→COMPLETED` 가 전이표에 허용되어 완료된다.

## 5. 실패 처리 (주기 배치)

- 한 건의 `process` 가 예외를 던지면(`PROC:133-145`; `ShipmentException` 아니면 `EXTERNAL_TRACKING_SERVICE_ERROR` 로 래핑) `faultTolerant().skip(Exception.class)` 로 해당 건만 **스킵**된다 (`JOB:75-77`). 청크 트랜잭션은 롤백되고 Spring Batch 가 청크의 아이템을 개별 재처리하여, 실패 건만 제외하고 나머지는 정상 처리·저장된다. `completeOrder` 가 같은 트랜잭션에 참여하므로 실패 건의 Order/Sale/알림 변경도 함께 롤백된다.
- 스킵된 건은 `shipmentSkipListener` 가 로그만 남기고(`JOB:251-286`) 상태 변경은 없다 → DB 상태가 그대로(IN_TRANSIT/OUT_FOR_DELIVERY)라 **다음 실행(6시간 뒤)에 다시 조회 대상**이 된다 (`JOB:95`).
- 스킵 한도 50 (`JOB:52,77`): 한 번의 실행에서 실패가 50건을 넘으면 스텝이 실패하고 잡이 중단되어 남은 건은 다음 주기까지 처리되지 않는다.
- 스케줄러는 `jobLauncher.run` 예외를 `printStackTrace` 만 하고 삼킨다 (`global/config/ShipmentBatchScheduler.java:41-43`).
- (실행되지 않는 `SVC#updateShipmentStatuses` 는 건별 try/catch 로 errorCount++ 후 계속 진행하지만 `SVC:383-387`, 호출되지 않아 실제 동작과 무관하다.)
