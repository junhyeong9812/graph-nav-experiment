# 즉시 구매 처리 흐름 (코드 기준 실제 동작)

경로 약어: `D` = `src/main/java/com/fream/back/domain`

## 1. 진입 API, 처리 단계, 동기/비동기, 응답 ID

- 진입점은 `POST /order-bids/instant`이다. 클래스 `@RequestMapping("/order-bids")` + `@PostMapping("/instant")`. 요청 바디는 `InstantOrderRequestDto`(saleBidId, addressId, warehouseStorage, paymentRequest). 근거: `D/order/controller/command/OrderBidCommandController.java:89-90`, `D/order/dto/InstantOrderRequestDto.java:18-29`
  - (`/orders/{orderId}/process-payment-shipment` 는 Kafka 비동기 경로이지만 즉시 구매와 무관하다. 즉시 구매는 이 경로를 쓰지 않는다. `D/order/controller/command/OrderCommandController.java:42-54`)
- 처리 단계 (모두 한 요청 스레드 안, 하나의 `@Transactional`):
  1. 컨트롤러가 이메일을 꺼내고 `enrichPaymentRequest`로 `userEmail`을 채우고 `orderId=null`로 둔다. `OrderBidCommandController.java:92-98, 119-122`
  2. `OrderBidCommandService#createInstantOrderBid` (`@Transactional`): 입력 검증 → 구매자 조회 → SaleBid 조회(+Sale 존재 검증) → `OrderCommandService#createInstantOrder` → OrderBid 생성. `D/order/service/command/OrderBidCommandService.java:118-143`
  3. `OrderCommandService#createInstantOrder` (`@Transactional`): 주소 조회 → Order 저장 → 결제요청에 orderId 주입 → OrderItem → OrderShipment → SaleBid 매칭(+flush) → 창고 상태 → 결제. `D/order/service/command/OrderCommandService.java:219-311`
  4. 결제 `PaymentCommandService#processPayment` 안에서 알림 생성 + Sale 상태 변경. `D/payment/service/command/PaymentCommandService.java:57-83`
  5. 마지막에 OrderBid 생성/저장. `OrderBidCommandService.java:189-207`
- **동기 처리**다. Kafka 발행/구독이 전혀 없다(이 경로에서 `OrderEventProducer`/`KafkaTemplate` 호출 없음). 컨트롤러는 서비스가 끝날 때까지 기다려 `200 OK`를 반환한다. `OrderBidCommandController.java:101-109` (HTTP 202가 아니라 200 + "즉시 구매가 성공적으로 처리되었습니다.")
- 응답 data의 `Long`은 변수명·메시지("생성된 주문 ID")와 달리 **OrderBid의 ID**이다. 서비스 `createInstantOrderBid`의 반환 타입이 `OrderBid`이고(`OrderBidCommandService.java:119, 142-144`), 컨트롤러는 그 `.getId()`를 `orderId` 변수에 담아 반환한다(`OrderBidCommandController.java:101-107`). Order의 PK(`order.getId()`)와는 다른 값일 수 있다.

## 2. 새로 생성되는 엔티티와 상태 변화 순서

생성 순서와 각 단계 직후 상태:

| 순서 | 동작 | 직후 상태 | 근거 |
|---|---|---|---|
| 1 | `Order` 생성·저장 (totalAmount = SaleBid.bidPrice) | Order = `PENDING_PAYMENT` | `OrderCommandService.java:241-247` |
| 2 | `OrderItem` 생성 (quantity 1, price = bidPrice) | Order 상태 그대로 `PENDING_PAYMENT` | `OrderCommandService.java:255-256`, `D/order/service/command/OrderItemCommandService.java:45-52` |
| 3 | `OrderShipment` 생성 (주소는 addressId로 조회한 값) | Shipment = `PENDING` | `OrderCommandService.java:238, 264-271`, `D/shipment/service/command/OrderShipmentCommandService.java:61-68` |
| 4 | `saleBid.assignOrder(order)` + `updateStatus(MATCHED)` + `flush` | SaleBid = `MATCHED`, `saleBid.order`=Order | `OrderCommandService.java:279-283`, `D/sale/entity/SaleBid.java:83-93` |
| 5 | (판매 건이 창고 보관이면) 창고 상태 변경 | WarehouseStorage = `ASSOCIATED_WITH_ORDER` | `OrderCommandService.java:289-301` |
| 6 | `Payment` 생성 (Card/Account/General) | 결제수단별로 다름 (3번 참조) | `PaymentCommandService.java:67-80` |
| 7 | 알림 2건(구매자·판매자) 생성 후 `Sale` → `SOLD` | Sale = `SOLD` (생성 시 `PENDING_SHIPMENT`였음) | `PaymentCommandService.java:391-405`, `D/sale/service/command/SaleCommandService.java:108` |
| 8 | `OrderBid` 생성 (status `MATCHED`, `isInstantPurchase=true`, order·sale 연결) | OrderBid = `MATCHED` | `OrderBidCommandService.java:192-206`, `D/order/entity/OrderBid.java:49-52, 60-82` |

세부:
- 7번에서 `orderBid`는 아직 만들어지기 전이라 `order.getOrderBid()`가 null이다. 그래서 `saleBidQueryService.findByOrderId`로 SaleBid를 찾아(4번에서 flush되어 조회됨) Sale을 얻는 분기를 탄다. `PaymentCommandService.java:388-406`, `D/sale/service/query/SaleBidQueryService.java:26-29`
- `Sale.updateStatus`는 `SaleStatus.canTransitionTo` 검사를 하지 않으므로 `PENDING_SHIPMENT → SOLD`가 그대로 들어간다. (전이표상 `PENDING_SHIPMENT`는 `IN_TRANSIT`으로만 가능) `D/sale/entity/Sale.java:73-75`, `D/sale/entity/SaleStatus.java:15-25`
- 판매 입찰의 현재 상태(이미 MATCHED인지)는 검증하지 않는다. `OrderBidCommandService.java:172-184` — 이미 매칭된 SaleBid에도 다시 즉시 구매가 가능하다.
- Order 상태는 어디서도 `PAYMENT_COMPLETED` 등으로 바뀌지 않는다 (5번 참조).

## 3. 결제 수단별 결과, 성공 여부, 카드 결제 실패 시

공통 사전 검증: orderId 일치, 이메일 일치, 금액>0. `PaymentCommandService.java:117-145`. 결제 유형 분기: `PaymentCommandService.java:67-80`. 금액이 SaleBid 가격과 같은지는 검사하지 않는다(요청의 `paidAmount`를 그대로 사용).

| 수단 | 동작 | 생성된 Payment 상태 | 근거 |
|---|---|---|---|
| CARD | PaymentInfo 조회 → PortOne API로 실제 카드 결제 요청 → CardPayment 저장. 응답 `status`가 `"success"`면 `PAID`로 변경 | 성공 시 `PAID`+success=true. `"success"`가 아니면 `PENDING` 그대로 | `PaymentCommandService.java:166-208` |
| ACCOUNT | 은행명 검증 후 외부 호출 없이 AccountPayment 저장 | 항상 `PENDING` | `PaymentCommandService.java:244-262` |
| GENERAL | impUid 비어있지 않으면 외부 검증 없이 저장 | 항상 `PAID`, success=true | `PaymentCommandService.java:297-316` |

- **즉시 구매는 결제 성공 여부와 무관하게 "끝까지 성공"한다.** `OrderCommandService#createInstantOrder`는 `processPayment`의 반환값을 사용하지도 않고(`payment.isSuccess()`/상태 확인 없음), `order.assignPayment`나 Order 상태 변경도 하지 않는다. `OrderCommandService.java:303-311`. 반면 Kafka 경로(`OrderEventConsumer`)는 `!payment.isSuccess()`면 예외를 던지는데(`D/order/service/kafka/OrderEventConsumer.java:171-176`) 즉시 구매 경로에는 그 검사가 없다.
- 계좌이체(`PENDING`)여도 Sale은 `SOLD`가 되고 구매자·판매자에게 "결제가 완료되었습니다" 알림이 나간다. `PaymentCommandService.java:83, 403-405, 434-456`. 입금 확인 같은 후속 처리 코드는 이 경로에 없다.
- 주의: `Payment.isSuccess`는 `Card/Account/GeneralPayment` 생성자가 `setPaidAmount`를 호출하면서 `paidAmount>0`이면 true가 된다. `D/payment/entity/Payment.java:60-63`, `CardPayment.java:38`, `AccountPayment.java:28`, `GeneralPayment.java:30`. 따라서 ACCOUNT(`PENDING`)도 `isSuccess=true`이고, 카드 `"success"`가 아닌 경우도 `isSuccess=true`+`PENDING`일 수 있다 (`isSuccess`와 `status`가 불일치).
- **PortOne이 카드 결제를 실패로 응답하면** 응답 형태에 따라 둘로 갈린다:
  1. HTTP 비200이거나 body의 `code != 0` → `PaymentProcessingException`을 던진다. `D/payment/portone/PortOneApiClient.java:270-275`. 이 예외가 `PaymentCommandService`(`:89-94, 218-219`)를 거쳐 `OrderCommandService`에서 `OrderPaymentProcessingFailedException`으로 감싸져(`OrderCommandService.java:306-309`) 던져지고 `OrderBidCommandService`가 그대로 재던진다(`:145-146, 212-218`). 하나의 트랜잭션이므로 **Order, OrderItem, OrderShipment, SaleBid 매칭이 전부 롤백**되고 에러 응답이 반환된다. 알림·Sale SOLD도 만들어지지 않는다(예외가 그 전에 발생). 통신 오류(`RestClientException`)도 `PaymentApiException`으로 같은 결과. `PortOneApiClient.java:288-290`
  2. HTTP 200 + `code == 0` 이지만 `response.status`가 `"success"`가 아닌 경우(`failed` 등) → 예외 없이 `CardPayment`가 `PENDING`(isSuccess는 위 이유로 true)으로 저장된다. `PaymentCommandService.java:203-208`. 이후 구매자·판매자 알림이 나가고 Sale이 `SOLD`가 되고 OrderBid `MATCHED`가 만들어져 **200 OK "즉시 구매가 성공적으로 처리되었습니다"로 끝난다.** 실패가 걸러지지 않는 결함성 동작이다.
- 그 밖에 롤백되는 경우: 주소 조회 실패, 창고 상태 변경 실패(`OrderCommandService.java:295-301`), SaleBid 없음 등.

## 4. 알림 수신자, 시점, 방식

- 수신자는 **구매자와 판매자 각 1명**이다. `PaymentCommandService#sendNotifications`:
  - 구매자(`order.getUser()`): "결제가 완료되었습니다. 주문 ID: {orderId}"
  - 판매자(`sale.getSeller()`): "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}"
  - 둘 다 `NotificationCategory.SHOPPING`, `NotificationType.BID`. `PaymentCommandService.java:434-456`
- 시점: 요청 처리 중, 결제 Payment 저장 직후이자 Sale을 `SOLD`로 바꾸기 직전(같은 트랜잭션 안, 동기). `PaymentCommandService.java:83, 403-405`. 응답이 나가기 전이다. 알림이 실패해도 예외를 삼키므로(`PaymentCommandService.java:421-425, 457-461`) 구매는 계속 진행된다.
- 방식: `NotificationCommandService#createNotification`이 (1) DB에 `Notification` 저장 후 (2) Redis에 `WebSocket:User:{email}` 키가 있는 사용자에게만 STOMP `convertAndSendToUser(email, "/queue/notifications", dto)`로 실시간 전송한다. 연결이 없으면 저장만 되고 조회로 확인한다. `D/notification/service/command/NotificationCommandService.java:44-59, 37-39, 297-323`
- Kafka `notification-topic`/WebSocket `/topic/order/{id}` 알림(`OrderEventConsumer#sendSuccessNotification`)은 즉시 구매 경로에서는 발생하지 않는다 — 그 컨슈머는 `order-processing-topic` 이벤트에서만 호출된다. `OrderEventConsumer.java:55-96`. (참고: `notification-topic` 구독자도 소스에 없음.)
- 판매 건 생성 시의 알림(`SaleCommandService#createSale`)은 판매 등록 시점의 것으로, 즉시 구매 시점의 알림이 아니다. `SaleCommandService.java:125`

## 5. 최종 주문 상태와 "창고 보관" 선택 시 차이

- **주문의 최종 상태는 `PENDING_PAYMENT` (결제 대기)이다.** `createInstantOrder`는 Order를 `PENDING_PAYMENT`로 만들고(`OrderCommandService.java:241-245`) 이후 `updateStatus`를 한 번도 호출하지 않는다(`OrderCommandService.java:219-319`). 결제가 `PAID`여도, 응답이 "성공"이어도 Order는 결제 완료/준비중/완료로 가지 않는다. `PAYMENT_COMPLETED`, `PREPARING`, `COMPLETED` 등으로 바꾸는 코드는 `processPaymentAndShipment`(`OrderCommandService.java:163-177`)와 Kafka 컨슈머(`OrderEventConsumer.java:195-220`)에만 있고 즉시 구매 경로는 호출하지 않는다. 또한 `Order.payment` 필드도 설정하지 않는다(반환 값 미사용, `:305`; 단 `payment.order`는 `assignOrder`로 설정됨, `PaymentCommandService.java:200, 258, 311`).
  - 한편 같은 요청으로 SaleBid=`MATCHED`, OrderBid=`MATCHED`, Sale=`SOLD`로 바뀌므로 주문 상태와 불일치한다.
- **구매자의 "창고 보관" 선택(`warehouseStorage`)은 즉시 구매에서 실제로 무시된다.** 값은 컨트롤러 → `createInstantOrderBid(..., isWarehouseStorage, ...)` → `createInstantOrder(..., isWarehouseStorage, ...)`로 전달되지만(`OrderBidCommandController.java:105`, `OrderBidCommandService.java:137`) `createInstantOrder` 본문에서 이 파라미터를 읽는 곳이 없다(`OrderCommandService.java:219-319`; `isWarehouseStorage` 사용 위치는 주석/시그니처뿐, 코드상 `:292`의 `sale.isWarehouseStorage()`는 **판매자 Sale**의 필드).
  - 그 결과 `createOrderStorage`(구매자용 WarehouseStorage 생성, `IN_STORAGE`)나 `IN_WAREHOUSE`/`COMPLETED` 상태 전이는 일어나지 않는다. 창고 보관 여부에 관계없이 Order는 `PENDING_PAYMENT`, 배송정보(OrderShipment `PENDING`)도 동일하게 만들어진다.
  - 창고와 관련해 실제로 달라지는 것은 **판매자가 창고 보관으로 올린 Sale인 경우**뿐이다: 그 Sale의 WarehouseStorage가 `ASSOCIATED_WITH_ORDER`로 바뀐다(`OrderCommandService.java:291-294`, `D/warehouseStorage/service/command/WarehouseStorageCommandService.java:117-133`). 해당 보관 정보가 없으면 `WarehouseStorageNotFoundException`(`D/warehouseStorage/service/query/WarehouseStorageQueryService.java:30-33`)으로 전체가 롤백된다.
- 비교: 별도 경로 `process-payment-shipment`(Kafka)에서는 창고 보관 선택 시 `createOrderStorage` 후 `PREPARING → IN_WAREHOUSE → COMPLETED`까지 가고(`OrderEventConsumer.java:197-212`), 일반 배송이면 `PREPARING`에서 끝난다(`:214-219`). 즉시 구매는 이 로직을 타지 않는다.
