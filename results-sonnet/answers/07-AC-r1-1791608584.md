# 즉시 구매 처리 흐름 (POST /order-bids/instant)

경로 약칭: `OBC` = `src/main/java/com/fream/back/domain/order/controller/command/OrderBidCommandController.java`,
`OBS` = `.../domain/order/service/command/OrderBidCommandService.java`,
`OCS` = `.../domain/order/service/command/OrderCommandService.java`,
`PCS` = `.../domain/payment/service/command/PaymentCommandService.java`,
`PORT` = `.../domain/payment/portone/PortOneApiClient.java`,
`NCS` = `.../domain/notification/service/command/NotificationCommandService.java`
(모두 `src/main/java/com/fream/back/` 아래).

## 1. 진입 API, 처리 단계, 동기/비동기, 응답 ID

- 진입점: `POST /order-bids/instant` → `OrderBidCommandController#createInstantOrderBid`
  (`domain/order/controller/command/OrderBidCommandController.java:22,89-90`).
  요청 DTO는 `saleBidId`, `addressId`, `warehouseStorage`, `paymentRequest`
  (`domain/order/dto/InstantOrderRequestDto.java:20-29`).
- 처리 단계 (전부 한 요청 스레드, 한 트랜잭션 안에서 순차 실행):
  1. 컨트롤러가 이메일을 추출하고 `paymentRequest.userEmail = email`, `orderId = null`로 보강 (`OBC:92,98,119-123`).
  2. `OrderBidCommandService#createInstantOrderBid` (`@Transactional`, `OBS:118-149`):
     입력 검증(`OBS:154-167`) → 구매자 조회(`OBS:126`) → SaleBid/Sale 조회(`OBS:129-130,172-184`).
     SaleBid가 이미 MATCHED인지, 구매자가 판매자 본인인지는 검사하지 않는다(`OBS:172-184`에 해당 검사 없음).
  3. `OrderCommandService#createInstantOrder` (`@Transactional`, `OCS:219-319`):
     주소 조회(`OCS:238`) → Order 저장(`OCS:241-247`) → `paymentRequest.orderId` 설정(`OCS:250`)
     → OrderItem(`OCS:255-256`) → OrderShipment(`OCS:264-271`) → SaleBid 매칭 + `flush`(`OCS:279-283`)
     → 판매자 창고 상태 갱신(`OCS:289-301`) → 결제 처리(`OCS:305`).
  4. 결제 처리 `PaymentCommandService#processPayment` (`PCS:57-107`): 검증(`PCS:117-146`) →
     결제수단별 생성(`PCS:67-80`) → 알림 및 Sale 상태 갱신(`PCS:83`, `PCS:383-426`).
  5. 다시 `OBS`로 돌아와 OrderBid를 만들어 저장(`OBS:142`, `OBS:189-207`).
- 동기 처리다. Kafka/이벤트 발행이 이 경로에 없다. `OrderEventProducer`는 별도 엔드포인트
  `/orders/{orderId}/process-payment-shipment`에서만 쓰인다(`nav/order.md` 호출 사슬; 즉시구매 경로의 `OBS`/`OCS`/`PCS`에 producer 호출 없음).
  PG(PortOne) 호출도 요청 스레드에서 동기 HTTP(`PORT:266`, `restTemplate.exchange`)다.
- **응답의 ID는 Order ID가 아니라 OrderBid ID다.** `createInstantOrderBid(...)`가 반환한 `OrderBid`에
  `.getId()`를 호출해 `orderId`라는 이름의 변수에 담고 "즉시 구매가 성공적으로 처리되었습니다."와 함께 내려준다
  (`OBC:101-109`; 반환값은 `OBS:142-144`의 OrderBid). 변수명·Javadoc("생성된 주문 ID", `OBC:83`)과 실제 동작이 다르다.

## 2. 새로 생기는 엔티티와 상태 변화 순서

생성 순서와 직후 상태:

| # | 동작 | 근거 | 직후 상태 |
|---|---|---|---|
| 1 | `Order` 생성·저장 | `OCS:241-247` | `Order.status = PENDING_PAYMENT`, totalAmount = SaleBid.bidPrice |
| 2 | `OrderItem` 생성 | `OCS:255-256` | (상태 없음) |
| 3 | `OrderShipment` 생성 | `OCS:264-271`, `domain/shipment/service/command/OrderShipmentCommandService.java:61-70` | `ShipmentStatus.PENDING` (`:67`) |
| 4 | 기존 `SaleBid` 갱신: `order` 연결 + 상태 변경 | `OCS:279-280`, `domain/sale/entity/SaleBid.java:83-86,91-93` | `SaleBid.status = MATCHED` (`sale.entity.BidStatus`), 그 후 `flush`(`OCS:283`) |
| 5 | (판매자가 창고 보관을 택한 Sale이면) 기존 `WarehouseStorage` 갱신 | `OCS:291-294`, `domain/warehouseStorage/service/command/WarehouseStorageCommandService.java:117-133` | `WarehouseStatus.ASSOCIATED_WITH_ORDER` (IN_STORAGE에서는 전환 허용, `:239-242`) |
| 6 | `Payment`(Card/Account/General) 생성·저장 | `PCS:187-208`, `PCS:250-262`, `PCS:302-316` | 수단별로 다름 (3번 참조) |
| 7 | 기존 `Sale` 상태 변경 | `PCS:391-405` | `Sale.status = SOLD` (생성 시 `PENDING_SHIPMENT`, `domain/sale/service/command/SaleCommandService.java:108`) |
| 8 | `Notification` 2건 생성 | `PCS:438-454` | 4번 참조 |
| 9 | `OrderBid` 생성·저장 | `OBS:192-206` | `OrderBid.status = MATCHED`, `isInstantPurchase = true`, `sale` 연결 |

특이점:
- 7번은 결제 성공 여부와 무관하게 실행된다. `Sale.updateStatus`는 전환 규칙을 검사하지 않으므로
  (`domain/sale/entity/Sale.java:73-75`) `PENDING_SHIPMENT → SOLD`가 그대로 들어간다
  (`SaleStatus.canTransitionTo`는 이 경로에서 호출되지 않음, `SaleStatus.java:15-24`).
- 결제 시점(6~7번)에는 `OrderBid`가 아직 없으므로 `order.getOrderBid()`가 null이고, `PCS:388-407`의 "SaleBid 탐색" 분기로
  들어가 `saleBidQueryService.findByOrderId`(`PCS:391`)로 4번에서 연결된 SaleBid를 찾아 Sale을 얻는다
  (그래서 4번의 `flush`가 필요하다).
- OrderBid는 맨 마지막(9번)에 만들어진다. 즉 "OrderBid PENDING → MATCHED" 같은 중간 상태는 없고 처음부터 MATCHED다(`OBS:196`).
- `Order.status`는 이 경로에서 한 번도 바뀌지 않는다(5번 질문 참조).

## 3. 결제 수단별 결과, 성공 여부, 카드 실패 시

공통: 결제 금액은 0보다 큰지, 주문 ID·이메일이 일치하는지만 검증한다(`PCS:131-145`). 금액이 SaleBid 가격과 같은지는 비교하지 않는다
(Order.totalAmount는 입찰가 `OCS:243`, 결제 금액은 요청의 `paidAmount`). 결제수단은 `paymentType`의 JSON 다형성으로 결정(`PaymentRequestDto.java:20-25`).

| 수단 | 처리 | 결제 상태 | 근거 |
|---|---|---|---|
| CARD | PortOne `processCardPayment` 호출 후 CardPayment 저장. 응답 `status`가 `"success"`일 때만 PAID + `isSuccess=true` | 성공: `PAID`; 응답 status가 success가 아니면 기본값 `PENDING`, `isSuccess=false` | `PCS:179,187-208`, 기본값 `domain/payment/entity/Payment.java:39,44` |
| ACCOUNT | 은행명만 검증(`Bank` enum), PG 호출 없음, 즉시 저장 | `PENDING`(입금 대기), `isSuccess=false` | `PCS:244,250-262,470-488` |
| GENERAL | 요청의 `impUid`만 있으면 PG 확인 없이 성공 처리 | `PAID`, `isSuccess=true` | `PCS:297-300,313-314` |

- **핵심: 결제 상태와 상관없이 후속 단계(알림, Sale SOLD, OrderBid MATCHED)가 진행된다.** `processPayment`는 수단별 생성 후 곧바로
  `notifyUsersAndUpdateSaleStatus`를 호출하고(`PCS:83`), 이 안에서 결제 상태를 확인하지 않는다(`PCS:383-426`).
  따라서 계좌이체(PENDING)도, 카드 응답이 success가 아닌 경우도 구매자에게 "결제가 완료되었습니다" 알림이 가고 Sale은 SOLD가 된다.
- 즉시 구매가 "끝까지 성공"하는가: HTTP 응답은 성공(200)으로 나가지만, 완결된 주문은 아니다. 결제가 PAID인 경우(카드 success, 일반 결제)에도
  Order는 `PENDING_PAYMENT`에서 움직이지 않고, `order.assignPayment`도 호출되지 않으며(`OCS:305`는 반환값을 버림), 배송/창고 처리 단계가 없다.
  계좌이체는 결제 자체가 PENDING이다. (5번 참조)
- **카드 결제를 PG가 실패로 응답하는 경우** (두 갈래):
  1. HTTP 비정상이거나 최상위 `code != 0`이면 `PaymentProcessingException`을 던진다 (`PORT:270-274`: `!response.getBody().get("code").equals(0)`).
     이 예외는 `createCardPayment`(`PCS:218-224`) → `processPayment`(`PCS:89-94`) → `OCS:306-309`에서
     `OrderPaymentProcessingFailedException`으로 감싸져 → `OBS:145-147`이 그대로 재던진다. 모두 하나의 트랜잭션이므로
     Order, OrderItem, OrderShipment, SaleBid MATCHED 변경이 전부 롤백되고 OrderBid/Payment/알림은 만들어지지 않으며 Sale도 SOLD가 되지 않는다. 클라이언트는 에러 응답을 받는다.
     통신 오류(`RestClientException`)는 `PaymentApiException`으로 바뀌어 `@Retryable`로 최대 3회 재시도(`PORT:224-228,288-290`) 후 같은 경로로 실패한다.
  2. 최상위 `code == 0`이지만 `response.status`가 `"success"`가 아닌 경우(예: PG 응답 status `failed`) — 예외 없이
     CardPayment가 `PENDING`/`isSuccess=false`로 저장되고(`PCS:203-208`), 이후 단계는 그대로 진행되어 구매자·판매자 알림,
     Sale `SOLD`, OrderBid `MATCHED`가 확정된다. 실패한 결제인데 주문 흐름은 성공으로 끝나는 코드상 결함이다.

## 4. 알림 대상, 시점, 전달 방식

- 받는 사람은 두 명이다(`PCS:434-456`, `sendNotifications`):
  - 구매자: "결제가 완료되었습니다. 주문 ID: {order.id}" (`PCS:438-443`)
  - 판매자(`sale.getSeller()`): "구매자가 결제를 완료하였습니다. 판매 ID: {sale.id}" (`PCS:447-454`)
  - 둘 다 카테고리 `SHOPPING`, 타입 `BID`.
- 시점: 결제 수단 생성 직후, Sale을 SOLD로 바꾸기 직전이다(`PCS:83`, `PCS:403-404`). 요청 트랜잭션 안에서 동기 실행되며,
  카드 PG 실패 예외(3-1)가 나면 이 단계에 도달하지 못해 알림이 없다. 결제 상태 PENDING이어도 위 문구로 발송된다(3번).
- 전달 방식(`NCS:44-67,303-323`): DB에 `Notification`으로 저장한 뒤, Redis에 `WebSocket:User:{email}` 키가 있을 때만
  STOMP `convertAndSendToUser(email, "/queue/notifications", dto)`로 실시간 푸시한다. 접속 중이 아니면 저장만 되고, 푸시 실패는 로그만 남긴다
  (`NCS:315-319`). Kafka를 쓰지 않는다. (`OrderEventConsumer`가 쓰는 `notification-topic`은 이 경로와 무관하고, 소스 내 구독자도 없다 — `CLAUDE.md` msg 항목.)
- 알림 전송 실패는 `sendNotifications`/`notifyUsersAndUpdateSaleStatus`에서 삼켜진다(`PCS:457-461,421-425`).
  다만 `NotificationCommandService`는 클래스 레벨 `@Transactional`(`NCS:27`)이고 같은 트랜잭션에 참여하므로,
  내부에서 예외가 던져졌다면 트랜잭션이 rollback-only로 표시되어 커밋 시점에 실패할 수 있다(코드 구조에서 추정, 실행 확인은 안 함).

## 5. 최종 주문 상태와 창고 보관 선택 시

- **Order의 최종 상태는 `PENDING_PAYMENT`다.** 즉시 구매 경로(`OBC` → `OBS#createInstantOrderBid` → `OCS#createInstantOrder` →
  `PCS#processPayment`)에서 `Order.updateStatus`를 호출하는 곳이 없다. 생성 시 `PENDING_PAYMENT`(`OCS:244`)로 저장된 뒤 그대로 남는다.
  `PAYMENT_COMPLETED → PREPARING → (IN_WAREHOUSE → COMPLETED)`로 바꾸는 코드는 `processPaymentAndShipment`(`OCS:162-177`)와
  Kafka 소비자(`domain/order/service/kafka/OrderEventConsumer.java:192-217`)에만 있으며, 즉시 구매는 이를 호출하지 않는다.
  "결제 완료" 알림 문구나 응답 메시지("성공적으로 처리")와 달리 주문은 결제 대기 상태다.
  함께 확정되는 값: SaleBid `MATCHED`, OrderBid `MATCHED`(+`isInstantPurchase`), Sale `SOLD`, OrderShipment `PENDING`, Payment는 수단별(`PAID` 또는 `PENDING`).
- **구매자의 "창고 보관" 선택(`warehouseStorage`)은 사실상 무시된다.**
  요청 값은 `OBC:95,105` → `OBS:119-120,133-139` → `OCS:220-221`까지 전달되지만 `createInstantOrder` 본문에서 한 번도 읽히지 않는다
  (`OCS:222-318`에 `isWarehouseStorage` 사용 없음). 그래서 true여도:
  - 구매자용 `WarehouseStorage`가 생성되지 않고(`createOrderStorage` 호출 없음; 호출은 `OCS:170`의 별도 경로뿐),
  - Order가 `IN_WAREHOUSE`/`COMPLETED`가 되지 않으며,
  - 배송 정보(`OrderShipment`)는 창고 여부와 무관하게 항상 생성된다(`OCS:264-271`).
  - 창고와 관련해 실제로 일어나는 것은 **판매자 쪽** Sale의 `isWarehouseStorage`가 true일 때 그 Sale의 기존 `WarehouseStorage`를
    `ASSOCIATED_WITH_ORDER`로 바꾸는 것뿐이다(`OCS:291-294`). 해당 창고 레코드가 없으면 `WarehouseStorageNotFoundException`
    (`domain/warehouseStorage/service/query/WarehouseStorageQueryService.java:31-32`)이 `OCS:295-301`에서 감싸져 전체가 롤백된다.
- 비교: 일반 경로 `processPaymentAndShipment`는 `warehouseStorage=true`면 `PAYMENT_COMPLETED → PREPARING → IN_WAREHOUSE`, 구매자용
  `WarehouseStorage`(IN_STORAGE, 1개월) 생성 후 `COMPLETED`로 만든다(`OCS:163-172`, `WarehouseStorageCommandService.java:48-55`).
  즉시 구매 경로는 이 동작을 하지 않는다.
