# 즉시 구매 처리 흐름

경로 약어: `D` = `src/main/java/com/fream/back/domain`

## 1. 진입 API · 처리 단계 · 동기/비동기 · 응답 ID

**API**: `POST /order-bids/instant` → `OrderBidCommandController#createInstantOrderBid`
(`D/order/controller/command/OrderBidCommandController.java:22,89-110`). 판매 쪽 `/sale-bids/instant`(판매자가 구매 입찰에 즉시 판매)와는 다른 경로다.

**단계 (모두 한 요청 스레드, 한 `@Transactional` 안에서 순차 실행)**
1. 컨트롤러가 이메일을 추출하고, `paymentRequest.userEmail=email`, `orderId=null`로 보강한다 (`OrderBidCommandController.java:92,98,119-123`).
2. `OrderBidCommandService#createInstantOrderBid` (`D/order/service/command/OrderBidCommandService.java:118-149`): 입력 검증(154-167) → 구매자 조회(126) → `SaleBid` 조회·`Sale` 존재 검증(129,172-184) → `OrderCommandService#createInstantOrder` 호출(133) → `OrderBid` 생성·저장(142,189-207).
3. `OrderCommandService#createInstantOrder` (`D/order/service/command/OrderCommandService.java:219-319`), 순서:
   1. 주소 조회 `addressQueryService.getAddress` (238)
   2. `Order` 저장, `paymentRequest.orderId = order.id` (241-250)
   3. `OrderItem` 생성 (255)
   4. `OrderShipment` 생성 (264-271)
   5. `saleBid.assignOrder(order)` + `saleBid.updateStatus(MATCHED)` + `entityManager.flush()` (279-283)
   6. 판매자 `Sale.isWarehouseStorage`이면 창고 상태 `ASSOCIATED_WITH_ORDER`로 변경 (291-294)
   7. `paymentCommandService.processPayment` (305)
4. `PaymentCommandService#processPayment` (`D/payment/service/command/PaymentCommandService.java:57-107`): 검증(60) → 결제 유형별 생성(67-80) → 알림·`Sale` 상태 변경(83).

**동기/비동기**: 전부 동기다. 이 경로에는 Kafka 발행이 없다. `OrderEventProducer`/`OrderEventConsumer`는 `POST /orders/{orderId}/process-payment-shipment`(별도 API)에서만 쓰인다 (`D/order/controller/command/OrderCommandController.java`, `D/order/service/kafka/OrderEventConsumer.java:192-217`). PG 호출(`PortOneApiClient#processCardPayment`)도 요청 안에서 블로킹으로 실행된다. 알림만 DB 저장 + WebSocket 즉시 푸시다(4번).

**응답 ID**: 메서드 주석은 "생성된 주문 ID"라고 하지만(`OrderBidCommandController.java:83`), 실제 반환값은 `orderBidCommandService.createInstantOrderBid(...).getId()`, 즉 **새로 만든 `OrderBid`의 ID**다 (`OrderBidCommandController.java:101-109`). `Order` ID가 아니다. 응답 변수명이 `orderId`일 뿐이다.

## 2. 생성되는 엔티티와 상태 변화 순서 (각 단계 직후 상태)

| 순서 | 동작 | 대상 | 상태 값 | 근거 |
|---|---|---|---|---|
| 1 | 생성 | `Order` | `PENDING_PAYMENT` (totalAmount = saleBid.bidPrice) | `OrderCommandService.java:241-247` |
| 2 | 생성 | `OrderItem` (SaleBid의 ProductSize, 입찰가) | — | `OrderCommandService.java:255-256` |
| 3 | 생성 | `OrderShipment` | `ShipmentStatus.PENDING` | `D/shipment/service/command/OrderShipmentCommandService.java:56-75` (67) |
| 4 | 변경 | `SaleBid` | `assignOrder`가 `MATCHED`로 세팅(`D/sale/entity/SaleBid.java:58-61`), 이어서 `updateStatus(MATCHED)` (`OrderCommandService.java:279-280`) + flush. 이전 상태가 PENDING인지는 검사하지 않는다. | |
| 5 | (조건부) 변경 | `WarehouseStorage` | `ASSOCIATED_WITH_ORDER` (판매자 Sale이 창고 보관일 때만) | `OrderCommandService.java:291-294`, `D/warehouseStorage/service/command/WarehouseStorageCommandService.java:117-133` |
| 6 | 생성 | `Payment` (Card/Account/General) | 3번 참고 | `PaymentCommandService.java:157-333` |
| 7 | 변경 | `Sale` | `SOLD` (`updateStatus`는 전이 검사 없이 대입; 생성 직후 상태는 `PENDING_SHIPMENT`여도 SOLD로 바뀜) | `PaymentCommandService.java:404`, `D/sale/entity/Sale.java:73-75`, `D/sale/service/command/SaleCommandService.java:108` |
| 8 | 생성 | `OrderBid` | `MATCHED`, `isInstantPurchase=true`, `order`·`sale` 연결, bidPrice = saleBid.bidPrice | `OrderBidCommandService.java:192-206` |

보충:
- 7번에서 `order.getOrderBid()`는 아직 null이다(`OrderBid`는 8번에서 생성). 그래서 `notifyUsersAndUpdateSaleStatus`는 `saleBidQueryService.findByOrderId`(4번에서 flush됨)로 `SaleBid → Sale`을 찾는 분기를 탄다 (`PaymentCommandService.java:388-406`).
- **`Order.status`는 이 흐름에서 `PENDING_PAYMENT`에서 바뀌지 않는다.** `createInstantOrder`·`processPayment` 어디에서도 `order.updateStatus`를 호출하지 않는다. 상태를 `PAYMENT_COMPLETED` 등으로 바꾸는 코드는 `processPaymentAndShipment`(`OrderCommandService.java:165-176`), Kafka 컨슈머(`OrderEventConsumer.java:195-217`), 배송 서비스(`OrderShipmentCommandService.java:204,260,355`)뿐이다.
- `Order.orderBid`/`Payment`는 `order.assignPayment`를 호출하지 않는다 (즉시 구매 경로는 `processPayment`의 반환값을 버린다, `OrderCommandService.java:305`). `Payment.order`로만 연결된다.

## 3. 결제 수단별 결과

`paymentType` JSON 값으로 DTO 하위 타입이 정해진다 (`D/payment/dto/PaymentRequestDto.java:20-25,74-87`). 금액 `paidAmount`는 0 초과여야 하고, `orderId`/`userEmail`은 서버가 채운 값과 대조한다 (`PaymentCommandService.java:117-146`).

핵심 함정: 세 `Payment` 서브클래스 생성자가 모두 `setPaidAmount()`를 호출하고, 이 메서드는 `isSuccess = paidAmount > 0`으로 만든다 (`D/payment/entity/Payment.java:60-63`, `D/payment/entity/CardPayment.java:38`, `D/payment/entity/AccountPayment.java:28`). 따라서 **생성 직후 `isSuccess`는 금액만 양수면 이미 true**이고, `status` 기본값은 `PENDING`이다 (`Payment.java:39,44`).

| 수단 | 처리 | 저장 결과 | 근거 |
|---|---|---|---|
| CARD | 저장된 `PaymentInfo` 복호화 조회 → PortOne 카드 결제 호출 → 응답 `status`가 문자열 `"success"`일 때만 `PAID` + `updateSuccessStatus(true)`(paymentDate 기록) | 성공: `status=PAID`, `isSuccess=true`, impUid/receiptUrl 등 저장 | `PaymentCommandService.java:166,179,187-208` |
| ACCOUNT | PG 호출 없음. 은행명 검증 후 저장만 한다 | `status=PENDING`, `isSuccess=true`(생성자 효과), impUid 없음, paymentDate 없음 | `PaymentCommandService.java:236-262`, `AccountPayment.java:21-29` |
| GENERAL | 클라이언트가 이미 PG 결제한 `impUid`를 받아 저장만 한다. 서버는 PG에 검증하지 않는다. `impUid` 공백이면 예외 | `status=PAID`, `isSuccess=true` | `PaymentCommandService.java:290-316` |

**즉시 구매가 끝까지 성공하는가**: 위 세 경우 모두 예외 없이 끝나면 HTTP 200 "즉시 구매가 성공적으로 처리되었습니다."가 나간다 (`OrderBidCommandController.java:109`). 단 계좌이체는 입금 확인 없이 `PENDING`으로 저장되는데도 이후 단계(Sale `SOLD`, 알림, OrderBid `MATCHED`)가 똑같이 실행된다.

예외로 실패하는 경우: PG 통신/토큰/`code != 0` 응답(`PortOneApiClient.java:270-275`, 289-293), `PaymentInfo` 없음, 금액·주문ID·이메일 불일치, 은행 검증 실패, 주소 없음, 창고 보관 Sale인데 `WarehouseStorage` 행이 없는 경우(`findBySale`이 `WarehouseStorageNotFoundException`, `WarehouseStorageQueryService.java:30-33`). 이 경우 `OrderException`으로 감싸져 올라가고(`OrderCommandService.java:305-309`) 전체 트랜잭션이 롤백된다 (Order/OrderItem/Shipment/SaleBid 변경 포함; PG에서 이미 승인된 결제를 취소하는 보상 로직은 없다).

**PG가 카드 결제를 실패로 응답하면**:
- PortOne HTTP 응답이 `code != 0`이거나 non-200이면 예외 → 위와 같이 전체 롤백, 구매 실패.
- 응답이 `code == 0`이지만 `response.status`가 `"success"`가 아닌 경우(예: 결제 거절을 담은 응답)에는 **예외가 없다.** `CardPayment`는 `PENDING`/`isSuccess=true`(생성자 효과, paymentDate 없음)로 저장된다 (`PaymentCommandService.java:203-208`). 그 뒤 `notifyUsersAndUpdateSaleStatus`는 결제 상태를 보지 않고 알림 전송과 `Sale=SOLD`를 수행한다 (`PaymentCommandService.java:83,383-420`). `handleRefundIfNecessary`는 있으나 어디서도 호출되지 않는다. 결과적으로 **결제 실패인데도 주문 입찰은 `MATCHED`, SaleBid `MATCHED`, Sale `SOLD`, 응답 200**이 된다. 반대로 코드는 `"success"`만 `PAID`로 인정하므로 PG가 다른 성공 문자열을 쓰면 정상 결제도 `PENDING`이 된다(응답 값 의미는 PortOne 문서 확인 필요; 코드 근거는 위 줄).

## 4. 알림 수신자 · 시점 · 전달 방식

- **구매자**: "결제가 완료되었습니다. 주문 ID: {orderId}" (`PaymentCommandService.java:438-443`)
- **판매자**(`sale.getSeller()`): "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}" (`PaymentCommandService.java:447-454`)
- 두 알림 모두 카테고리 `SHOPPING`, 타입 `BID` (`D/notification/entity/NotificationType.java:7`).
- **시점**: `processPayment` 안에서, `Payment`를 저장한 직후이며 `Sale.updateStatus(SOLD)` 직전이다 (`PaymentCommandService.java:83,403-404`). 즉 결제 성공 여부와 무관하게 `Payment` 생성이 끝나면 나간다. `OrderBid` 생성 전이다. 알림 전송·상태 업데이트 오류는 try/catch로 삼켜 구매를 막지 않는다 (`PaymentCommandService.java:421-425,457-`).
- **방식**: 동기 호출. `NotificationCommandService#createNotification`이 `Notification`을 DB에 저장하고(`D/notification/service/command/NotificationCommandService.java:52-54`), 이어서 Redis 키 `WebSocket:User:{email}`가 있는(=WebSocket 접속 중인) 사용자에게만 STOMP `/queue/notifications`로 `convertAndSendToUser` 푸시한다 (`NotificationCommandService.java:37-39,57,303-322`). 접속 중이 아니면 DB 저장만 되고 나중에 조회한다. 이 경로에서 Kafka `notification-topic`은 쓰이지 않는다. 그 토픽은 `OrderEventConsumer`의 Kafka 처리 경로에서만 쓰인다.
- 주의: `NotificationCommandService`는 클래스 단위 `@Transactional`이라, 알림 생성 중 예외가 나면 호출부가 예외를 삼켜도 같은 트랜잭션이 rollback-only로 표시될 수 있다.

## 5. 최종 주문 상태 · 창고 보관 선택 시 차이

**최종 주문 상태**: 요청이 정상 종료되면 `Order.status = PENDING_PAYMENT`("결제 대기") 그대로다 (2번 참고; `OrderCommandService.java:244` 이후 변경 없음). 결제가 `PAID`여도, 계좌이체여도 같다. 같은 시점의 다른 값은 `OrderBid=MATCHED`, `SaleBid=MATCHED`, `Sale=SOLD`, `OrderShipment=PENDING`, `Payment`는 수단별로 `PAID`/`PENDING`이다. "즉시 구매 성공"이라는 응답과 달리 주문은 결제 완료 상태로 승격되지 않는다.

**구매자가 "창고 보관"을 선택한 경우**: 달라지는 것이 없다. 컨트롤러가 `requestDto.isWarehouseStorage()`를 서비스에 넘기고(`OrderBidCommandController.java:104`), `OrderBidCommandService#createInstantOrderBid`가 `createInstantOrder`에 그대로 전달하지만(`OrderBidCommandService.java:133-139`), `createInstantOrder` 본문에서는 `isWarehouseStorage` 파라미터를 한 번도 읽지 않는다 (`OrderCommandService.java:219-319`; 사용처는 `sale.isWarehouseStorage()`뿐이다). 그 결과 구매자용 `WarehouseStorage`(`createOrderStorage`)는 생성되지 않고, `IN_WAREHOUSE`/`COMPLETED` 전이도 일어나지 않으며, 배송지 주소로 `OrderShipment`가 그대로 만들어진다. 창고 보관 분기(PAYMENT_COMPLETED → PREPARING → IN_WAREHOUSE → 보관 생성 → COMPLETED)는 별도의 `processPaymentAndShipment`에만 있고(`OrderCommandService.java:163-172`) 즉시 구매 경로에서는 호출되지 않는다.

창고와 관련해 즉시 구매에 실제로 영향을 주는 것은 **판매자 쪽** `Sale.isWarehouseStorage`뿐이다: true면 해당 `WarehouseStorage`를 `ASSOCIATED_WITH_ORDER`로 바꾼다 (`OrderCommandService.java:291-294`). 그 `WarehouseStorage`는 판매자 발송 처리 시 만들어지므로(`D/shipment/service/command/SellerShipmentCommandService.java:79`), 발송 전 상태의 판매 입찰을 즉시 구매하면 창고 레코드 부재로 요청이 실패한다.
