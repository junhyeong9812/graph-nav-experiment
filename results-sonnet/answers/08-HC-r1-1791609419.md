# 구매자 배송: 운송장 등록 → 배송 완료

경로 약어: `S` = `src/main/java/com/fream/back/`

## 1. 운송장 등록 요청

### 1-1. 진입 API
- `PATCH /shipments/order/{shipmentId}/status`, body `OrderShipmentRequestDto`(courier, trackingNumber) — `S domain/shipment/controller/command/OrderShipmentCommandController.java:20,33-41`
- 컨트롤러는 try/catch 없이 `OrderShipmentCommandService.updateTrackingInfo(...)` 를 호출하고 성공 시 `200 OK` 빈 body 를 반환한다 (`:41-47`).

### 1-2. 코드가 의도한 순서 (`S domain/shipment/service/command/OrderShipmentCommandService.java:238-303`)
1. courier/trackingNumber 공백 검사 → `TRACKING_INFO_REQUIRED` (`:243-246`)
2. `OrderShipment` 조회, 없으면 `SHIPMENT_NOT_FOUND` (`:249-253`)
3. `shipment.updateTrackingInfo` : courier·운송장 세팅 + 상태를 **전환 검증 없이** `IN_TRANSIT` 으로 직접 대입 (`:256`, `S domain/shipment/entity/OrderShipment.java:41-45`)
4. `order.updateStatus(OrderStatus.IN_TRANSIT)` (`:260`)
5. 구매자(주문자)에게 "상품이 출발하였습니다" 알림 1건 (`:265-271`)
6. `updateSaleStatusToSold(orderId)` : Sale → SOLD, (창고 보관이면 창고 상태 SOLD), 판매자에게 "판매 완료" 알림 (`:276`, `:112-183`)
7. 창고 보관 Sale 이면 창고 상태 SOLD 갱신 (`:279-286`)
8. OrderBid/SaleBid 가 MATCHED 이면 COMPLETED (`:289`, `:413-440`; 이 메서드는 예외를 삼킨다 `:436-439`)

의도된 알림: 구매자 1건("출발"), 판매자 1건(Sale 이 SOLD 로 전환될 때). 즉 코드 의도는 "운송장 등록 = 배송 출발 + 판매 SOLD + 입찰 COMPLETED" 이다.

### 1-3. 실배송 일반 구매 입찰 주문(즉시 구매 아님)에서는 끝까지 성공하지 못한다
- 이 주문의 Order 상태: 결제·배송 처리(Kafka 컨슈머 `processCompleteOrder`)에서 `PENDING_PAYMENT → PAYMENT_COMPLETED → PREPARING` 까지만 간다. 실배송이면 `PREPARING` 에서 멈춘다 (`S domain/order/service/kafka/OrderEventConsumer.java:195,214-218`; 동기 버전도 동일 `S domain/order/service/command/OrderCommandService.java:174-177`). API 는 Kafka 로 이벤트만 발행하는 202 응답 (`S domain/order/controller/command/OrderCommandController.java:54`).
- `OrderStatus` 전이표에서 `PREPARING` 의 다음 상태는 `IN_WAREHOUSE`, `SHIPMENT_STARTED` 뿐이다 (`S domain/order/entity/OrderStatus.java:26`). `IN_TRANSIT` 은 `SHIPMENT_STARTED` 에서만 갈 수 있다 (`:27`).
- 따라서 **실패 지점**은 `OrderShipmentCommandService.java:260` `order.updateStatus(IN_TRANSIT)` 이다. `Order.updateStatus` 가 전이 불가이면 `InvalidOrderStatusException` 을 던진다 (`S domain/order/entity/Order.java:113-120`).
- 이 예외(RuntimeException 계열, `S global/exception/GlobalException.java:10`)는 바깥 `catch (Exception e)` (`:295`)에 잡혀 `ShipmentException(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: ...")` 로 재포장되어 던져진다 (`:296-301`). 에러코드가 실제 원인과 무관한 `SHIPMENT_NOT_FOUND` 로 둔갑한다.
- **저장되는 것: 없음.** `@Transactional` (`:238`) 메서드에서 RuntimeException 이 나가므로 3번의 courier/trackingNumber/IN_TRANSIT 변경도 롤백된다. 배송은 `PENDING` 그대로, courier·trackingNumber 는 null. 알림 생성(`:266`)은 실패 지점 뒤라 1건도 만들어지지 않는다. Sale/OrderBid/SaleBid 도 변경 없음.
- **응답:** `GlobalExceptionHandler.handleShipmentException` (`S global/exception/GlobalExceptionHandler.java:459-472`)이 에러코드의 상태·메시지를 쓴다 → **HTTP 404, code `S001`, message "배송 정보를 찾을 수 없습니다."** (`S domain/shipment/exception/ShipmentErrorCode.java:12`). 사용자 정의 메시지(원인)는 응답 body 에 안 나간다.
- 설령 4번을 통과해도 6번에서 또 실패한다: `SaleBidQueryService.findByOrderId` 는 SaleBid 가 없으면 `IllegalArgumentException` 을 던지고 (`S domain/sale/service/query/SaleBidQueryService.java:26-28`), `updateSaleStatusToSold` 의 첫 호출(`:116`)은 try 밖이라 잡히지 않는다. 일반 구매 입찰 주문엔 SaleBid 가 없다.
- (참고) 즉시 구매 주문도 Order 가 `PENDING_PAYMENT` 라(`S domain/order/service/command/OrderCommandService.java:244`, 결제 서비스는 OrderStatus 를 건드리지 않음) `PENDING_PAYMENT → IN_TRANSIT` 이 불가(`OrderStatus.java:24`)하여 같은 이유로 이 API 는 실패한다.
- 결과적으로 이 API 로는 배송이 `IN_TRANSIT` 으로 가지 못한다. 배송을 `IN_TRANSIT` 으로 만드는 다른 경로는 `POST /shipments/order/{id}/check-status` (`OrderShipmentCommandController.java:58`) → `updateAndCheckShipmentStatus` 의 `shipment.updateTrackingInfo` (`OrderShipmentCommandService.java:473`) 뿐이며, 여기서는 Order 상태를 건드리지 않는다.

## 2. 배송 완료 감지

### 2-1. 누가/언제/어떻게
- 스프링 `@Scheduled` 가 Spring Batch Job `updateShipmentStatusesJob` 을 기동한다 (`S global/config/ShipmentBatchScheduler.java:34-40`).
- **주기:** cron `0 0 */6 * * *` = 6시간마다 정각(00·06·12·18시, 서버 타임존) (`:34`).
- **대상:** JPQL `status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND trackingNumber IS NOT NULL` 인 `OrderShipment` (`S domain/shipment/config/UpdateShipmentStatusesJobConfig.java:95`). chunk 50, skipLimit 50 (`:51-52,67,76-77`).
- 이 밖에 수동 호출 API(`check-status`)가 있다 (`OrderShipmentCommandController.java:58`).

### 2-2. 실제로 실행되는 처리 코드
비슷한 구현이 3벌 있다.
| 후보 | 실행 여부 |
|---|---|
| `ShipmentItemProcessor` (Playwright + Jsoup) | **실행됨** — Step 이 `.processor(new ShipmentItemProcessor(...))` 로 직접 생성해 사용 (`UpdateShipmentStatusesJobConfig.java:69-73`) |
| `UpdateShipmentStatusesJobConfig.shipmentItemProcessor()` @Bean 람다 (`:106`) | 미사용 — Step 에 연결되지 않음 (`:69` 가 new 로 만든 것을 씀) |
| `OrderShipmentCommandService.updateShipmentStatuses()` (`:309-391`) | 미사용 — 호출하는 곳이 저장소에 없음 (스케줄러는 Job 만 호출) |
| `parseCjLogisticsStatus` (Jsoup, `UpdateShipmentStatusesJobConfig.java`) | 어디서도 호출되지 않는 private 메서드 |

따라서 실제 처리는 `S domain/shipment/config/ShipmentItemProcessor.java:57-` `process()` 이다: CJ대한통운 추적 페이지(`trace.cjlogistics.com`)를 Playwright 로 열고 `tbody#statusDetail tr` 의 **마지막 행 5번째 td** 텍스트를 상태로 쓴다 (`:29`, `:181`).

### 2-3. 상태 문자열 → 내부 상태 (`ShipmentItemProcessor.java:221-225`)
- `"배송완료"` → `DELIVERED`
- `"배송출발"` → `OUT_FOR_DELIVERY`
- 그 외 모든 문자열(빈 값 제외, 파싱 실패는 예외) → `IN_TRANSIT`
- 정확 일치(equals) 비교다. 현재 상태와 같으면 아무것도 하지 않고 반환 (`:101`).

## 3. 배송 완료 판정 이후 (`ShipmentItemProcessor.java:112-117`)
1. `OrderShipment`: `IN_TRANSIT/OUT_FOR_DELIVERY → DELIVERED` (`:113`; 전이 허용 `S domain/shipment/entity/ShipmentStatus.java:16-22,23-28`)
2. `orderService.completeOrder(orderId)` (`:116`, `OrderShipmentCommandService.java:191-229`):
   1. OrderBid 조회 (없으면 예외) (`:196`)
   2. **Order → COMPLETED** (`:204`)
   3. `updateSaleStatusToSold` (`:208`): SaleBid 의 Sale(전이 가능하면) → SOLD + (창고 보관이면 창고 SOLD) + **판매자 알림**, 이어 OrderBid 의 Sale 도 같은 방식 (`:116-180`). Sale 이 이미 SOLD 이면 전이 불가라 건너뜀(`SaleStatus.java:23`).
   4. **구매자 알림 "[completeOrder] 주문이 완료 처리되었습니다"** (`:211-217`)
3. `notificationService.notifyShipmentCompleted(order)` → **구매자 알림 "[배송 완료] ..."** (`:117`, `S domain/notification/service/command/NotificationCommandService.java:219-229`)
4. Writer(`JpaItemWriter`)가 shipment 저장 (`UpdateShipmentStatusesJobConfig.java`의 `shipmentJpaItemWriter`).

### 알림 수 (정상 경로)
- 구매자 2건: "[completeOrder] 주문이 완료 처리되었습니다" + "[배송 완료] 상품이 배송 완료되었습니다" (같은 사건에 대해 중복 알림)
- 판매자 0~1건: Sale 이 아직 SOLD 가 아니고 SOLD 로 전이될 때만 1건 (`:133-138`/`:164-169`; 두 분기는 같은 Sale 이면 한 번만 발송됨)

### 입찰 상태
- `completeOrder` 는 **OrderBid/SaleBid 상태를 바꾸지 않는다.** 배치 경로에서 둘은 `MATCHED` 로 남는다. `COMPLETED` 로 바꾸는 `updateOrderAndSaleBidStatusToCompleted` 는 `updateTrackingInfo` (`:289`)에서만 호출되는데, 1-3 에서 보듯 그 경로는 성공하지 못한다. (주석/이름은 "COMPLETED" 라고 하지만 배송 완료 시점에는 호출되지 않는다.)
- 참고: `OrderBid.assignOrder` 가 MATCHED 로 바꾸므로 일반 구매 입찰도 생성 즉시 MATCHED 다 (`S domain/order/entity/OrderBid.java:75`, 호출 `S domain/order/service/command/OrderBidCommandService.java:100`). `SaleBid.assignOrder` 도 MATCHED (`S domain/sale/entity/SaleBid.java:58-61`).

## 4. 주문 종류별 차이

### (a) 실배송 일반 구매 입찰 주문 — 끝까지 진행되지 않는다
- Order 가 `PREPARING` 이다 (1-3). `Order → COMPLETED` 는 `PREPARING` 에서 불가 (`OrderStatus.java:26`) → `completeOrder` 의 `order.updateStatus(COMPLETED)` (`OrderShipmentCommandService.java:204`)에서 `InvalidOrderStatusException`.
- `completeOrder` 의 `catch (Exception)` 이 `ShipmentException(ORDER_NOT_FOUND_FOR_SHIPMENT)` 로 재포장 (`:221-228`). 뒤의 Sale SOLD 처리·구매자 알림(`:208-217`)은 실행되지 않고, 그 뒤의 `notifyShipmentCompleted`(`ShipmentItemProcessor.java:117`)도 안 불린다. 알림 0건.
- 트랜잭션이 롤백되므로 Order 는 PREPARING, 입찰은 MATCHED 그대로. 해당 건은 skip 처리된다(5번).
- 더구나 이 주문의 배송은 1-3 때문에 `PENDING` 에 머물러 애초에 배치 대상(IN_TRANSIT/OUT_FOR_DELIVERY)이 되지 않는다. 이 처리에 도달하려면 `check-status` API 로 배송을 `IN_TRANSIT` 으로 만든 뒤여야 하고, 그래도 위처럼 실패한다.

### (b) 즉시 구매로 만든 주문 — 3의 처리가 끝까지 진행된다 (배송이 IN_TRANSIT 이 되었다는 전제)
- 즉시 구매 Order 는 `PENDING_PAYMENT` 에서 시작해 결제 후에도 그대로다 (`OrderCommandService.java:241-245,305`; 결제 서비스에 OrderStatus 변경 없음). `PENDING_PAYMENT → COMPLETED` 는 전이표가 허용한다 (`OrderStatus.java:24`) → `completeOrder` 의 `order.updateStatus(COMPLETED)` 성공.
- OrderBid 는 즉시 구매 시 sale 을 가진 채 MATCHED 로 만들어져 있어 `findByOrderId` 성공 (`OrderBidCommandService.java:196-202`).
- Sale 은 결제 단계에서 이미 SOLD 로 바뀐다: `order.getOrderBid()` 가 아직 null 이라 SaleBid 경로를 타서 `sale.updateStatus(SOLD)` (`S domain/payment/service/command/PaymentCommandService.java:388-404`; SaleBid 는 `saleBid.assignOrder(order)` + flush 로 order 와 연결됨 `OrderCommandService.java:279-283`). 따라서 `updateSaleStatusToSold` 에서는 SOLD→SOLD 불가(`SaleStatus.java:23`)로 **Sale 변경·판매자 알림이 발생하지 않는다**.
- 결과: Shipment DELIVERED, Order COMPLETED, 구매자 알림 2건, 판매자 알림 0건, OrderBid/SaleBid 는 MATCHED 유지(COMPLETED 아님).
- 단 (b) 도 운송장 등록 API(1번)는 `PENDING_PAYMENT → IN_TRANSIT` 불가로 실패하므로, 현실적으로 배송이 IN_TRANSIT 이 되는 길은 `check-status` API 뿐이다.

| | (a) 실배송 일반 구매 입찰 | (b) 즉시 구매 |
|---|---|---|
| 완료 직전 Order | PREPARING | PENDING_PAYMENT |
| Order → COMPLETED | 불가 → 예외, 롤백 | 가능 |
| 알림 | 0건 | 구매자 2건, 판매자 0건 |
| 입찰 | MATCHED 유지 | MATCHED 유지 |

## 5. 실패 처리 (배치 주기 처리)
- Step 이 `faultTolerant().skip(Exception.class).skipLimit(50)` (`UpdateShipmentStatusesJobConfig.java:75-77`)이므로, 한 건의 처리 중 예외(운송장 없음, 파싱 실패, 브라우저 오류, `completeOrder` 예외 등)가 나면 그 건만 skip 되고 `SkipListener` 가 shipmentId·사유를 에러 로그로 남긴다 (`shipmentSkipListener`). 그 건의 변경은 롤백되어 상태는 이전(IN_TRANSIT 등) 그대로이므로 **다음 6시간 주기에 다시 조회 대상**이 된다.
- 나머지 건은 계속 처리되고 저장된다. skip 이 50건을 넘으면 Step 이 실패한다.
- `ShipmentItemProcessor` 는 비-ShipmentException 을 `EXTERNAL_TRACKING_SERVICE_ERROR` 로 감싸 다시 던진다 (`:128-` 의 catch 블록).
- 스케줄러 자체는 Job 기동 예외를 `printStackTrace()` 만 하고 삼킨다 (`ShipmentBatchScheduler.java:41-43`).
- 관찰(추정): 청크가 롤백되어 항목별 재처리(scan)가 일어나면 processor 가 같은 객체로 다시 호출되는데, 앞서 메모리상 DELIVERED 로 바뀐 객체는 `상태 동일` 조기 반환(`ShipmentItemProcessor.java:101`)에 걸릴 수 있어 주문 완료/알림이 재실행되지 않고 shipment 만 저장될 여지가 있다. 또한 `JpaPagingItemReader` 가 상태 조건 쿼리를 offset 페이징하므로 50건 초과 시 일부가 한 주기 건너뛰어질 수 있다. 코드로 실행 확인한 것은 아니다.
