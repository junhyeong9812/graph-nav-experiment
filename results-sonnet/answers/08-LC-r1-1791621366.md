# 구매자 배송: 운송장 등록 → 배송 완료 (코드 기준 실제 동작)

경로 약어: `S` = `src/main/java/com/fream/back/domain/shipment`, `O` = `.../domain/order`, `P` = `.../domain/payment`, `G` = `.../global`

## 1. 운송장 등록 요청

### 1-1. 진입 API
- `PATCH /shipments/order/{shipmentId}/status`, body `OrderShipmentRequestDto(courier, trackingNumber)` — `S/controller/command/OrderShipmentCommandController.java:20,33-45` → `OrderShipmentCommandService#updateTrackingInfo` (`S/service/command/OrderShipmentCommandService.java:238-239`). (prod nginx가 `/api`를 떼므로 매핑에 `/api` 없음)
- 관리자 권한 체크 없음. 컨트롤러는 인증만 요구하고 예외를 잡지 않아 `GlobalExceptionHandler`로 간다.
- 별도 수동 API `POST /shipments/order/{id}/check-status`(`Controller:58`)는 송장 등록 + CJ 즉시 조회(1-3 참고).

### 1-2. 코드가 의도한 상태 변경 순서와 알림 (`OrderShipmentCommandService.java:238-303`)
1. 택배사·송장번호가 비어 있으면 `TRACKING_INFO_REQUIRED` (:243-246).
2. `OrderShipment` 조회 후 `shipment.updateTrackingInfo` → 검증 없이 택배사/송장 저장 + status=`IN_TRANSIT` (:256, `S/entity/OrderShipment.java:41-45`). PENDING→IN_TRANSIT 전이표는 우회된다.
3. `Order.updateStatus(IN_TRANSIT)` (:259-260).
4. **구매자**에게 알림 "상품이 출발하였습니다. 주문 ID: …" (:264-271).
5. `updateSaleStatusToSold(orderId)` (:276, 본문 :111-183): SaleBid의 Sale이 SOLD로 전이 가능하면 Sale→SOLD, 창고보관이면 창고 SOLD, **판매자**에게 알림 "상품이 성공적으로 판매 완료되었습니다…" (:119-138). OrderBid 경로도 같은 방식(:150-176).
6. SaleBid의 Sale이 창고보관이면 창고 상태 SOLD 재호출 (:278-286).
7. `updateOrderAndSaleBidStatusToCompleted` → OrderBid·SaleBid MATCHED→COMPLETED (:289, 본문 :412-440). 이 메서드는 `private` + `@Transactional`이라 프록시 트랜잭션이 적용되지 않고(내부 호출), 예외는 로그만 남기고 삼킨다(:436-439).
- 즉 의도상 송장 등록 시점에 Sale SOLD와 Bid COMPLETED까지 처리하려는 구조다(배송 완료 시점 아님).

### 1-3. 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문 → **끝까지 성공하지 못한다**
- 이 주문의 상태는 `PREPARING`이다. Kafka 경로: PENDING_PAYMENT→PAYMENT_COMPLETED→PREPARING (`O/service/kafka/OrderEventConsumer.java:195,214-218`), 동기 경로도 동일 (`O/service/command/OrderCommandService.java:174-176`).
- `OrderStatus` 전이표에서 `PREPARING → {IN_WAREHOUSE, SHIPMENT_STARTED}`만 허용 (`O/entity/OrderStatus.java:26`), `IN_TRANSIT`은 `SHIPMENT_STARTED`에서만 갈 수 있다 (:28). `SHIPMENT_STARTED`를 설정하는 코드는 전체 소스에 없다(`OrderQueryController.java:207`의 표시 문자열뿐).
- 실패 지점: `OrderShipmentCommandService.java:260` `order.updateStatus(IN_TRANSIT)` → `Order.java:113-120`에서 `InvalidOrderStatusException("상태 전환이 허용되지 않습니다: PREPARING -> IN_TRANSIT")`.
- 이 예외는 `ShipmentException`이 아니므로 `catch (Exception e)` (:295-302)에서 `ShipmentException(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")`로 래핑되어 `@Transactional` 메서드 밖으로 나가 **롤백**된다.
- 저장되는 것: **없음**. 2단계의 shipment 변경(택배사/송장번호/IN_TRANSIT)은 flush 전에 롤백되어 shipment는 PENDING·송장 null 그대로, 구매자/판매자 알림도 4단계 전에 터졌으므로 0건, Sale·Bid 불변.
- 응답: 컨트롤러가 예외를 잡지 않으므로 `GlobalExceptionHandler#handleGlobalException`(`G/exception/GlobalExceptionHandler.java:49-63`)이 `ErrorResponse` 반환. 코드 `S001`, status **404**, message는 항상 enum 기본 문구 "배송 정보를 찾을 수 없습니다." (`S/exception/ShipmentErrorCode.java:12`). 실제 원인 문구는 응답에 안 나오고 로그에만 남는다. 즉 원인은 상태 전이 오류인데 "배송 없음"처럼 보인다.
- 부가: 순서를 통과했더라도 SaleBid가 없는 일반 입찰 주문이면 `saleBidQueryService.findByOrderId`가 null이 아니라 `IllegalArgumentException`을 던져(`SaleBidQueryService.java:26-28`) `updateSaleStatusToSold` 첫 줄(:116)에서 또 실패한다(OrderBid 쪽만 try/catch :150-180). SaleBid는 즉시판매 경로(`SaleBidCommandService.java:63-83`)에서만 order에 연결된다.
- 즉시 구매 주문(`Order=PENDING_PAYMENT`)도 PATCH는 같은 이유로 실패한다(`OrderStatus.java:24`에 IN_TRANSIT 없음).

## 2. 배송 완료 감지

### 2-1. 누가/언제/어떻게
- **스케줄러**가 감지한다: `G/config/ShipmentBatchScheduler.java:34-44` `@Scheduled(cron = "0 0 */6 * * *")` → `jobLauncher.run(updateShipmentStatusesJob, timestamp)`. **주기: 6시간마다**(0·6·12·18시 정각, 서버 타임존). 예외는 `printStackTrace`만 (:41-43).
- 보조: 운영자가 호출하는 수동 API `check-status`(`Controller:58-94,103-138`)가 `updateAndCheckShipmentStatus`(`Service:451-516`)로 같은 판정을 한다. 단 이쪽은 송장을 다시 `IN_TRANSIT`으로 덮고 `Order`를 건드리지 않는다.

### 2-2. 조회 대상
- Reader: `SELECT s FROM OrderShipment s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL`, pageSize 50 (`S/config/UpdateShipmentStatusesJobConfig.java:87-97`).
- Step: chunk 50, faultTolerant, skip(Exception) limit 50 (:66-81, :51-52).

### 2-3. 실제 실행되는 처리 코드
- Step이 사용하는 것은 `new ShipmentItemProcessor(playwrightBrowserManager(), notificationService, orderService)` (`JobConfig:69-73`) 즉 **`S/config/ShipmentItemProcessor.java#process` (:57-157)**. 공유 Playwright 브라우저로 `https://trace.cjlogistics.com/next/tracking.html?wblNo=<번호>`에 접속(:72-83), `tbody#statusDetail tr` 마지막 행의 5번째 `td` 텍스트를 Jsoup으로 파싱 (:167-181).
- 실행되지 않는 유사 코드: `JobConfig#shipmentItemProcessor()` 빈(:104-177, Step에 연결 안 됨), `JobConfig#parseCjLogisticsStatus`(:186), `OrderShipmentCommandService#updateShipmentStatuses`(:308-391, 호출처 없음), `CjTrackingPlaywright`(수동 API 전용).

### 2-4. 택배사 문자열 → 내부 상태 (`ShipmentItemProcessor.java:219-225`)
- 정확히 `"배송완료"` → `DELIVERED`, `"배송출발"` → `OUT_FOR_DELIVERY`, **그 외 전부** → `IN_TRANSIT` (완전 일치, 공백/다른 표기는 IN_TRANSIT).
- 현재 상태와 같으면 변경 없이 반환 (:100-105). `OUT_FOR_DELIVERY` 상태에서 "그 외" 문자열이 오면 `IN_TRANSIT` 전이가 표에 없어 `IllegalStateException` → 래핑되어 skip된다 (`ShipmentStatus.java:26`, `OrderShipment.java:47-55`).

## 3. 배송 완료 판정 이후 (`ShipmentItemProcessor.java:108-117`)
엔티티 상태 변경 순서:
1. `OrderShipment` → `DELIVERED` (:113; IN_TRANSIT/OUT_FOR_DELIVERY에서만 허용).
2. `orderService.completeOrder(orderId)` (:116, `Service:190-229`): OrderBid 조회(없으면 IAE→래핑) → **`Order` → `COMPLETED`** (:204) → `updateSaleStatusToSold` (:208) → 구매자 알림.
3. `Sale` → `SOLD`는 `canTransitionTo(SOLD)`(SELLING/ON_AUCTION에서만 true, `SaleStatus.java`)일 때만. 그런데 Sale은 이미 **결제 시점**에 SOLD로 바뀐다(`P/service/command/PaymentCommandService.java:83,383-420`, 무검증 `Sale.updateStatus`) → 배송 완료 시점에는 SOLD→SOLD 불가라 건너뛴다(:119, :156). 창고 SOLD 갱신도 그 분기 안이라 실행되지 않는다(:126-129).
4. `notifyShipmentCompleted` (:117).
5. 이후 Writer(`JpaItemWriter`)가 shipment 저장.

알림(성공 시, 즉시 구매 기준):
- **구매자 2건**: ① "[completeOrder] 주문이 완료 처리되었습니다. 주문 ID: …" (`Service:210-217`) ② "[배송 완료] 상품이 배송 완료되었습니다. 주문 ID: …" (`src/main/java/com/fream/back/domain/notification/service/command/NotificationCommandService.java:219-229`).
- **판매자 0건**: Sale이 이미 SOLD라 판매자 알림 분기에 안 들어간다(Sale이 SOLD가 아닌 예외적 상태면 최대 1건: SaleBid 경로 :133-138, 이어지는 OrderBid 경로는 SOLD라 불가).

입찰 상태: 배치/배송완료 경로는 `updateOrderAndSaleBidStatusToCompleted`를 호출하지 않는다(그 호출은 `updateTrackingInfo` :289뿐이고 1-3에서 도달 불가). 따라서 **OrderBid·SaleBid는 MATCHED 그대로**, COMPLETED로 바뀌지 않는다. (이름이 `completeOrder`여도 Bid는 완료 처리 안 됨.)

## 4. 주문 종류별 차이

### (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문 — **끝까지 진행되지 않음**
- Order는 `PREPARING` (1-3). `completeOrder`의 `order.updateStatus(COMPLETED)` (`Service:204`)는 `PREPARING → COMPLETED` 불가(`OrderStatus.java:26`) → `InvalidOrderStatusException` → `catch (Exception)` (:221-228)에서 `ShipmentException(ORDER_NOT_FOUND_FOR_SHIPMENT, S102)`로 래핑 → Processor가 rethrow (`ShipmentItemProcessor.java:133-145`) → skip.
- 결과: Order/Shipment/Sale/Bid/알림 모두 롤백(shipment `DELIVERED` 변경도 반영 안 됨), 배송은 IN_TRANSIT/OUT_FOR_DELIVERY로 남아 6시간마다 같은 실패를 반복한다. 수동 `check-status`로 DELIVERED가 오면 같은 이유로 롤백되고 컨트롤러는 body 없이 404를 반환한다(`Controller:80-86`).
- 참고: 이런 주문의 송장은 PATCH로 등록 불가(1-3)라, 배치 대상 상태가 되는 길은 사실상 수동 `check-status`가 "배송출발"을 받아 OUT_FOR_DELIVERY로 커밋하는 경우뿐이다(`Service:491-494`).

### (b) 즉시 구매로 만들어진 주문 — **끝까지 진행됨**
- `createInstantOrder`는 Order를 `PENDING_PAYMENT`로 만들고(`OrderCommandService.java:241-245`) 결제 후에도 Order 상태를 올리지 않는다(:303-309; 결제 서비스도 Order 상태 미변경). `OrderBid`는 MATCHED + `isInstantPurchase`로 저장(`OrderBidCommandService.java:192-206`), SaleBid는 `assignOrder` + MATCHED (`OrderCommandService.java:279-280`). Sale은 결제 시점 SOLD (SaleBid 경로 `PaymentCommandService.java:404`).
- 배송 완료 판정 시 `PENDING_PAYMENT → COMPLETED`는 전이표상 허용(`OrderStatus.java:24`)이라 `completeOrder`가 성공한다. 결과: Shipment DELIVERED, Order COMPLETED, Sale은 이미 SOLD, 구매자 알림 2건, 판매자 알림 0건, OrderBid/SaleBid는 MATCHED 유지. (배치 대상이 되려면 shipment가 수동 `check-status` 등으로 IN_TRANSIT/OUT_FOR_DELIVERY가 되어 있어야 하며, 수동 `check-status`가 DELIVERED를 받으면 같은 결과를 즉시 만든다 `Service:483-490`.)
- 차이 요약: (a)는 Order가 PREPARING이라 COMPLETED 전이 불가로 전체 롤백·skip, (b)는 Order가 PENDING_PAYMENT로 남아 있어 우연히 COMPLETED 전이가 가능해 정상 완료.

## 5. 실패 처리 (주기 배치)
- Processor에서 예외가 나면(`ShipmentException`은 그대로, 그 외는 `EXTERNAL_TRACKING_SERVICE_ERROR(S302)`로 래핑, `ShipmentItemProcessor.java:133-145`) Step이 `faultTolerant().skip(Exception.class).skipLimit(50)` (`JobConfig:75-77`)이므로 **해당 건만 skip**된다. 청크(50건) 트랜잭션은 롤백되고 아이템을 하나씩 다시 처리하며 실패한 건만 건너뛰고 나머지는 정상 커밋된다. `SkipListener`가 로그만 남긴다(`JobConfig:251-266`).
- 실패한 건: DB 변경 없음(`completeOrder`의 변경도 롤백), 상태가 IN_TRANSIT/OUT_FOR_DELIVERY 그대로라 다음 6시간 주기에 다시 조회된다 (재시도 상한·실패 표시 없음).
- skip이 50건을 넘으면 Step이 `SkipLimitExceededException`으로 실패해 남은 건이 그 회차에 처리되지 않는다. Job 실패는 스케줄러에서 `printStackTrace`만 한다(`ShipmentBatchScheduler.java:41-43`).
- 브라우저는 Step 시작/종료 시 열고 닫는다(`BrowserManageStepListener`); 페이지는 건별 `finally`에서 닫는다(`ShipmentItemProcessor.java:146-155`).
- (추정, 미검증) `JpaPagingItemReader`가 상태 조건 쿼리를 offset 페이징하므로 앞 청크에서 상태가 바뀐 건이 빠지면 다음 페이지에서 일부 건이 한 회차 건너뛰어질 수 있다.
