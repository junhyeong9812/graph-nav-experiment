## 1. API 진입점, 처리 단계, 동기/비동기, 응답 ID

**API**: `POST /order-bids/instant` (`OBC:22`, `OBC:89`) — `OrderBidCommandController.createInstantOrderBid(@RequestBody @Valid InstantOrderRequestDto)`
(`domain/order/controller/command/OrderBidCommandController.java:89-90`). 요청 DTO는 `saleBidId`, `addressId`, `warehouseStorage`, `paymentRequest`
(`domain/order/dto/InstantOrderRequestDto.java:20-29`).

**처리 단계 (모두 한 요청 스레드, 한 트랜잭션 안)**

1. 컨트롤러가 SecurityContext에서 이메일을 꺼내고(`OBC:92`), 결제 요청에 `userEmail`을 넣고 `orderId=null`로 초기화한다(`OBC:98`, `OBC:119-122`).
2. `OrderBidCommandService.createInstantOrderBid` (`@Transactional`, `OBS:118-120`) 호출 (`OBC:101-107`).
   - 입력 검증(`OBS:123`, `OBS:154-167`), 구매자 조회(`OBS:126`), SaleBid 조회·검증(`OBS:129`, `OBS:172-184`). 검증은 SaleBid가 이미 매칭됐는지는 보지 않는다(Sale 존재 여부만 확인).
3. `OrderCommandService.createInstantOrder` 호출(`OBS:133-139`, `OCS:219-221`, `@Transactional`)
   - 주소 조회(`OCS:238`) → Order 저장(`OCS:241-247`) → `paymentRequest.setOrderId`(`OCS:250`) → OrderItem 생성(`OCS:255-256`) → OrderShipment 생성(`OCS:264-271`) → SaleBid 매칭 및 flush(`OCS:279-283`) → (판매자가 창고 보관이면) 창고 상태 변경(`OCS:291-293`) → 결제 처리(`OCS:305`) → Order 반환(`OCS:311`).
4. 결제 처리 `PaymentCommandService.processPayment` (`PCS:57`, 클래스 `@Transactional` `PCS:37`)
   - 결제 수단별 Payment 생성(`PCS:67-80`) → `notifyUsersAndUpdateSaleStatus`(`PCS:83`) 에서 알림 + Sale 상태 SOLD(`PCS:383-426`).
5. 다시 `OBS`로 돌아와 OrderBid 생성·저장(`OBS:142`, `OBS:189-207`), 컨트롤러가 200 OK 응답(`OBC:109`).

**동기/비동기**: **동기**이다. 이 경로에는 Kafka/`@Async`가 없다. `OrderEventProducer`/`OrderEventConsumer`를 쓰는 비동기 경로(202 Accepted)는 별개의 API `POST /orders/{orderId}/process-payment-shipment`(`domain/order/controller/command/OrderCommandController.java:42-69`)이며 즉시 구매 흐름에서는 호출되지 않는다(즉시 구매는 `OrderCommandService.createInstantOrder`를 직접 호출). 결제 대행사 호출(PortOne REST)도 요청 스레드 안에서 동기로 실행된다(`PCS:179`, `PORT:266`).

**응답으로 돌려주는 ID**: 이름은 `orderId`이고 메시지는 "즉시 구매가 … 처리되었습니다"이지만, 실제 값은 **OrderBid(주문 입찰)의 ID**이다.
`createInstantOrderBid(...)`가 `OrderBid`를 반환하고(`OBS:119`, `OBS:144`) 컨트롤러가 그 `.getId()`를 `orderId` 변수에 담아 응답한다(`OBC:101-107`, `OBC:109`). 주석(`OBC:83` "생성된 주문 ID")과 달리 Order의 ID가 아니다. (Order 자체의 ID는 응답에 없다.)

## 2. 생성되는 엔티티와 상태 변화 순서 (각 단계 직후 값)

| 순서 | 동작 | 직후 상태 | 근거 |
|---|---|---|---|
| 1 | **Order** 생성·저장 (`totalAmount = saleBid.bidPrice`) | `Order.status = PENDING_PAYMENT` | `OCS:241-247` |
| 2 | **OrderItem** 생성 (수량 1, 가격 = 입찰가), Order에 추가 | (상태 필드 없음; 수량 1) | `OCS:255-256`, `domain/order/service/command/OrderItemCommandService.java:45-52` |
| 3 | **OrderShipment** 생성 (주소 DTO의 수령인·연락처·우편번호·주소) | `ShipmentStatus.PENDING` | `OCS:264-271`, `domain/shipment/service/command/OrderShipmentCommandService.java:61-70` |
| 4 | **SaleBid**에 Order 연결 + 상태 변경 | `SaleBid.status = MATCHED` (`assignOrder`가 MATCHED 세팅, 이어서 `updateStatus(MATCHED)` 한 번 더) → `flush` | `OCS:279-283`, `domain/sale/entity/SaleBid.java:58-61, 66-68` |
| 5 | (판매자의 `Sale.isWarehouseStorage == true`일 때만) **WarehouseStorage**(기존 엔티티) 상태 변경 | `WarehouseStatus.ASSOCIATED_WITH_ORDER` | `OCS:291-293`, `domain/warehouseStorage/service/command/WarehouseStorageCommandService.java:117-133` |
| 6 | **Payment**(CardPayment/AccountPayment/GeneralPayment) 생성·저장 | 결제 수단별로 다름 → 3번 항목 참조 | `PCS:67-80` |
| 7 | **Sale** 상태 변경 (알림 전송 직후) | `Sale.status = SOLD` (전이 규칙 검사 없이 대입) | `PCS:403-405`, `domain/sale/entity/Sale.java:73-75` |
| 8 | **OrderBid** 생성·저장 (구매자, 입찰가, Sale 연결, 즉시구매 플래그) | `OrderBid.status = MATCHED` | `OBS:192-206` |

세부 사항:

- 6번 시점에 `order.getOrderBid()`는 아직 `null`(OrderBid는 8번에서 생성)이라, `PCS:388-407`의 "OrderBid가 없으면 SaleBid로 Sale 탐색" 분기가 항상 실행된다. 이때 4번에서 연결·flush된 SaleBid를 `findByOrderId`로 찾는다(`PCS:391`, `domain/sale/service/query/SaleBidQueryService.java:26-29`).
- Order 상태는 위 1번 이후 **한 번도 바뀌지 않는다**. `createInstantOrder`에는 `order.updateStatus(...)`나 `assignPayment` 호출이 없다(`OCS:219-319` 전체). 반환값 Payment도 버려진다(`OCS:305`).
- `isWarehouseStorage`(구매자의 창고 보관 선택) 파라미터는 `createInstantOrder` 본문에서 사용되지 않는다(선언 `OCS:221`, 본문 `OCS:222-318`에 참조 없음). 5번은 구매자 선택이 아니라 **판매자의 Sale 설정**(`OCS:292`)에 의존한다.

## 3. 결제 수단별 결과와 성공 여부

결제 유형은 JSON `paymentType`(CARD/ACCOUNT/GENERAL)으로 결정된다(`domain/payment/dto/PaymentRequestDto.java:20-25`, `PCS:67-80`). 사전 검증: 주문 ID·이메일 일치, 금액 > 0(`PCS:117-146`).

| 수단 | Payment 결과 | 즉시 구매 성공? | 근거 |
|---|---|---|---|
| **GENERAL(일반 결제)** | `impUid` 필수. `isSuccess=true`, `status=PAID`, `paymentDate` 세팅. PG 호출 없음(클라이언트가 보낸 impUid를 신뢰) | **성공** | `PCS:297-300, 311-316` |
| **CARD(카드)** | PortOne 카드 결제 호출(`PCS:179`). 응답 `status`가 문자열 `"success"`이면 `PAID` + `isSuccess=true`. 아니면 상태 변경 없음 → `PENDING` 유지 | 호출이 예외 없이 끝나면 **성공 처리됨** (아래 상세) | `PCS:179, 203-208` |
| **ACCOUNT(계좌이체)** | 항상 **예외** 발생 → 즉시 구매 전체 실패 | **항상 실패(롤백)** | `PCS:260`, `PAY:70-76`, `PaymentStatus.java:12-13` |

**계좌이체가 항상 실패하는 이유**: `createAccountPayment`는 `accountPayment.updateStatus(PaymentStatus.PENDING)`를 호출하는데(`PCS:260`), `Payment.status`의 기본값이 이미 `PENDING`이고(`PAY:44`), `Payment.updateStatus`는 `PENDING.canTransitionTo(PENDING)`이 false여서 `IllegalStateException("결제 상태 전환이 허용되지 않습니다…")`을 던진다(`PAY:70-76`; 전이표 `PENDING → PAID`만 허용, `PaymentStatus.java:12-13`). 이 예외는 `PCS:274-277`에서 `PaymentProcessingException`으로 바뀌고, `OCS:306-308`에서 `OrderPaymentProcessingFailedException`으로 한 번 더 감싸져 전파된다. 모든 단계가 RuntimeException(`GlobalException extends RuntimeException`, `global/exception/GlobalException.java:10`)이므로 외부 `@Transactional`(`OBS:118`)이 **롤백**한다 → Order/OrderItem/Shipment/SaleBid 매칭/창고 상태/알림 DB 저장 모두 취소된다. 의도(계좌이체는 PENDING으로 대기)와 실제 동작이 다르다.

**카드 결제 대행사가 실패로 응답하면** — 두 경우가 갈린다:

1. **PortOne이 HTTP 비-200이거나 `code != 0`으로 응답**: `PortOneApiClient`가 `PaymentProcessingException("카드 결제 요청 실패: …")`을 던짐(`PORT:270-275`) → 통신 오류도 `PaymentApiException`(`PORT:288-290`) → `PCS:180-184`에서 전파 → `OCS:306-308`에서 `OrderPaymentProcessingFailedException` → **전체 롤백, 즉시 구매 실패**.
2. **`code == 0`이지만 `response.status`가 `"success"`가 아님**(예: failed 등): 예외가 **발생하지 않는다**. `PCS:203-206`의 if를 건너뛰어 CardPayment는 `status=PENDING`으로 저장되고(`PCS:208`), `processPayment`는 정상 반환한다(`PCS:88`). 게다가 `CardPayment` 생성자가 `setPaidAmount(paidAmount)`를 호출해 `isSuccess = paidAmount > 0`을 **true**로 만들어 두므로(`CardPayment.java:38`, `PAY:60-63`), 결제가 실패했어도 `isSuccess=true`, `paymentDate=null`, `status=PENDING`인 모순된 Payment가 남는다. 이후 흐름은 그대로 진행되어 SaleBid MATCHED·Sale SOLD(`PCS:404`)·알림 전송(`PCS:403`)이 일어나고 OrderBid가 생성되며 200 "즉시 구매가 성공적으로 처리되었습니다"가 응답된다. 이 경로에서 `isSuccess`를 검사해 막는 코드는 없다(비동기 경로 `OrderEventConsumer:174-176`에만 `payment.isSuccess()` 검사가 있고 즉시 구매 경로에는 없음).

즉, 즉시 구매는 **일반 결제와 카드 결제(PG 호출이 예외 없이 끝난 경우)에서만 끝까지 진행**되고, 계좌이체는 항상 실패한다. 단, 끝까지 성공해도 Order 상태는 `PENDING_PAYMENT`로 남는다(5번 참조).

## 4. 알림 수신자, 시점, 전달 방식

**누가 무엇을 받나** (`PCS:434-462`, `sendNotifications`):

- **구매자**(`order.getUser()`): 카테고리 `SHOPPING`, 타입 `BID`, 메시지 `"결제가 완료되었습니다. 주문 ID: {orderId}"` (`PCS:436-443`)
- **판매자**(`sale.getSeller()`): 카테고리 `SHOPPING`, 타입 `BID`, 메시지 `"구매자가 결제를 완료하였습니다. 판매 ID: {saleId}"` (`PCS:447-454`)
- 그 외 수신자는 없다(관리자·Kafka 알림 토픽 없음).

**언제**: 결제 Payment를 저장한 직후, 같은 요청·같은 트랜잭션 안에서(`PCS:83` → `PCS:403`), 그리고 `Sale`을 `SOLD`로 바꾸기 **직전**(`PCS:403-404`)이다. 이후 OrderBid 생성(`OBS:142`)이 남아 있으므로 알림은 커밋 이전에 나간다.

**어떻게**: `NotificationCommandService.createNotification` 호출(`PCS:438, 449`) →
1. DB에 `Notification` 저장(동기)(`NCS:46-53`),
2. 실시간 전송 시도: Redis에 `WebSocket:User:{email}` 키가 있을 때만(= WebSocket 연결 중) `convertAndSendToUser(email, "/queue/notifications", dto)`로 STOMP 푸시(`NCS:303-313`). 연결이 없으면 DB 저장만 되고 푸시는 하지 않는다(`NCS:320-322`).
- 알림 생성/전송 실패는 로그만 남기고 삼킨다(`PCS:457-461`, `PCS:421-425`) → 알림 때문에 결제 흐름이 실패하지 않는다.
- 이 경로에서는 `OrderEventConsumer`의 Kafka `notification-topic`/`/topic/order/{id}` 알림은 쓰이지 않는다(비동기 경로 전용, `OrderEventConsumer.java:287-324`).
- 참고: 알림 처리 중 `findByOrderId`가 SaleBid를 못 찾으면 `IllegalArgumentException`이 나지만 `PCS:421`에서 잡혀 알림이 생략된다(`SaleBidQueryService.java:26-29`).
- 참고: 알림이 DB에 저장되고 WebSocket으로 나간 뒤 `OBS:142`에서 예외가 나면 DB는 롤백되지만 이미 보낸 WebSocket 푸시는 취소되지 않는다(전송이 트랜잭션 커밋 전에 일어나기 때문).

## 5. 처리 종료 시 주문의 최종 상태, 창고 보관 선택 시 차이

**최종 상태**: `Order.status = PENDING_PAYMENT` (결제 대기) 그대로이다.
- 생성 시 `PENDING_PAYMENT`(`OCS:244`), 이후 `createInstantOrder`/`createInstantOrderBid`/`processPayment` 어디에서도 Order 상태를 `PAYMENT_COMPLETED` 등으로 바꾸지 않는다(`OCS:219-319`, `OBS:119-149`, `PCS:57-107`). Payment 쪽 `PAID`는 Order 상태에 반영되지 않는다.
- 같이 남는 값: SaleBid `MATCHED`, Sale `SOLD`, OrderBid `MATCHED`, OrderShipment `PENDING`, Payment는 수단/응답에 따라 `PAID` 또는 `PENDING`.
- 같은 이름의 비동기 경로(`OrderEventConsumer.processCompleteOrder`)는 `PAYMENT_COMPLETED → PREPARING`(또는 창고 보관 시 `→ IN_WAREHOUSE → COMPLETED`)로 바꾸지만(`OrderEventConsumer.java:195-220`), 즉시 구매는 그 경로를 타지 않으므로 해당 없음.
- 또한 `OrderBidCommandService`의 메서드 주석·응답 문구("성공적으로 처리")와 달리 주문은 결제 완료 상태가 아니다.

**구매자가 "창고 보관"을 선택한 경우**: **아무것도 달라지지 않는다.**
- 컨트롤러는 값을 로그에 찍고(`OBC:94-95`) 서비스로 넘기지만(`OBC:105`, `OBS:137`, `OCS:221`), `createInstantOrder` 안에서 사용하지 않는다. 구매자용 `WarehouseStorage` 생성(`warehouseStorageCommandService.createOrderStorage`)도, `IN_WAREHOUSE`/`COMPLETED` 전이도 즉시 구매 경로에는 없다(해당 호출은 비동기 경로 `OrderEventConsumer.java:197-211`와 `OCS:163-172`의 별도 메서드에만 있음).
- 창고 관련 상태 변경은 구매자 선택과 무관하게 **판매자 Sale의 `isWarehouseStorage`가 true일 때** 그 Sale의 창고 레코드를 `ASSOCIATED_WITH_ORDER`로 바꾸는 것뿐이다(`OCS:291-293`). 해당 창고 레코드가 없으면 `WarehouseStorageNotFoundException`(`WarehouseStorageQueryService.java:30-33`)이 `OrderWarehouseStorageProcessingFailedException`으로 바뀌어(`OCS:295-300`) 즉시 구매 전체가 롤백된다.
- 배송지 정보(OrderShipment)는 창고 보관 여부와 상관없이 항상 생성된다(`OCS:264-271`).
