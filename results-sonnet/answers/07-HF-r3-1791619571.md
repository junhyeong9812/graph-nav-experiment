# 즉시 구매 처리 흐름 (POST /order-bids/instant)

경로 약어: `D` = `src/main/java/com/fream/back/domain`

## 1. 진입 API, 처리 단계, 동기/비동기, 응답 ID

- 진입: `POST /order-bids/instant` → `OrderBidCommandController.createInstantOrderBid`
  (`D/order/controller/command/OrderBidCommandController.java:22,89-110`).
- 단계 (모두 한 요청 스레드, 한 `@Transactional` 안):
  1. 컨트롤러가 인증 이메일을 추출하고 결제 DTO에 `userEmail` 설정, `orderId=null` 설정 (`...Controller.java:92,98,119-122`).
  2. `OrderBidCommandService.createInstantOrderBid` (`D/order/service/command/OrderBidCommandService.java:118-149`):
     입력 검증(:154-167) → 구매자 조회(:126) → SaleBid/Sale 조회·null 검증(:129-130,172-184) → Order 생성 위임(:133) → OrderBid 생성(:142,189-207).
  3. `OrderCommandService.createInstantOrder` (`D/order/service/command/OrderCommandService.java:219-319`):
     주소 조회(:238) → Order 저장(:241-247) → `paymentRequest.setOrderId(order.getId())`(:250) → OrderItem(:255) → OrderShipment(:264) → SaleBid 매칭 + flush(:279-283) → (판매자가 창고 보관 건이면) 창고 상태 변경(:291-294) → 결제(:305).
  4. `PaymentCommandService.processPayment` (`D/payment/service/command/PaymentCommandService.java:57-107`): 결제 유형별 Payment 생성 → `notifyUsersAndUpdateSaleStatus`(:83).
- 동기 처리다. Kafka/`@Async`를 쓰지 않는다. 결제·알림까지 요청 안에서 끝난다.
  Kafka(`OrderEventProducer`)를 쓰는 것은 별개 API `POST /orders/{id}/process-payment-shipment`뿐이다 (`D/order/controller/command/OrderCommandController.java:54`).
  즉시 구매 경로는 이를 호출하지 않는다.
- 응답 ID: 컨트롤러 Javadoc(`:82-83`)과 메시지는 "주문 ID"라 하지만 실제로는 **OrderBid의 ID**다.
  서비스가 `OrderBid`를 반환하고(`OrderBidCommandService.java:144`) 컨트롤러가 `.getId()`를 그대로 반환한다(`OrderBidCommandController.java:101-109`). Order ID가 아니다.

## 2. 생성되는 엔티티와 상태 변화 순서

처음부터 끝까지 한 트랜잭션(`OrderBidCommandService.java:118`, `OrderCommandService.java:219`, `PaymentCommandService.java:37`의 클래스 레벨 `@Transactional`)이다.

| 순서 | 동작 | 직후 상태 | 근거 |
|---|---|---|---|
| 1 | **Order** 생성·저장 | `Order.status = PENDING_PAYMENT`, `totalAmount = saleBid.bidPrice` | `OrderCommandService.java:241-247` |
| 2 | **OrderItem** 생성 (SaleBid의 ProductSize, 입찰가) | — | `OrderCommandService.java:255-256` |
| 3 | **OrderShipment** 생성 (주소 조회 값으로) | `ShipmentStatus.PENDING` | `OrderCommandService.java:264-271`, `D/shipment/service/command/OrderShipmentCommandService.java:61-68` |
| 4 | **SaleBid** 상태 변경 (`assignOrder`) | `SaleBid.status: PENDING → MATCHED`, order 연결 | `OrderCommandService.java:279-280`, `D/sale/entity/SaleBid.java:58-61` |
| 5 | (판매자 Sale이 창고 보관 건일 때만) WarehouseStorage 상태 변경 | `ASSOCIATED_WITH_ORDER` | `OrderCommandService.java:291-294`, `D/warehouseStorage/service/command/WarehouseStorageCommandService.java:117-133` |
| 6 | **Payment** 생성 (유형별) | 3번 항목 참고 | `PaymentCommandService.java:67-80` |
| 7 | **Sale** 상태 변경 | `Sale.status = SOLD` (Payment가 PENDING이어도 변경) | `PaymentCommandService.java:391-405` |
| 8 | **OrderBid** 생성·저장 | `OrderBid.status = MATCHED`, `isInstantPurchase = true`, order·sale 연결 | `OrderBidCommandService.java:189-206`, `D/order/entity/OrderBid.java:60-82,97-99` |

- 7번 설명: 결제 시점에는 OrderBid가 아직 없어 `order.getOrderBid()`가 null이다. 그래서 `saleBidQueryService.findByOrderId`로 SaleBid를 찾는 분기를 탄다 (`PaymentCommandService.java:388-406`, `D/sale/service/query/SaleBidQueryService.java:26-29`).
  4번에서 이미 flush했으므로 조회된다.
- Order에는 `assignPayment`를 호출하지 않는다. `Payment.order`만 설정된다 (`PaymentCommandService.java:200`). 즉시 구매 경로에는 `OrderCommandService.java:139-140`에 해당하는 코드가 없다.
- 참고: SaleBid가 이미 MATCHED인지, 구매자=판매자인지는 검증하지 않는다 (`OrderBidCommandService.java:172-184`).

## 3. 결제 수단별 결과, 끝까지 성공하는가, 카드 실패 시

공통: `validatePaymentRequest`가 주문 ID·이메일 일치, 금액 > 0을 검사한다 (`PaymentCommandService.java:117-146`).

- **CARD** (`PaymentCommandService.java:157-225`):
  - 저장된 PaymentInfo를 조회하고(:166) PortOne을 실제 호출한다(`portOneApiClient.processCardPayment`, :179 → `D/payment/portone/PortOneApiClient.java:229-295`).
  - 응답 `status`가 문자열 `"success"`일 때만 `PAID` + `isSuccess=true`로 바꾼다 (`:203-206`).
  - 그 외 응답이면 예외 없이 Payment 기본값인 **`PENDING`, `isSuccess=false`** 로 저장된다 (`D/payment/entity/Payment.java:39,44`).
  - 코드상 `"success"`만 PAID로 인정한다. PortOne이 성공을 다른 문자열(예: `"paid"`)로 주는 경우의 실제 응답 값은 코드로 확인할 수 없다.
- **ACCOUNT (계좌이체)** (`:236-279`): 은행명만 검증하고 PG를 호출하지 않는다. Payment를 **`PENDING`** 으로 저장한다 (`:260`). `isSuccess`는 false 그대로다.
- **GENERAL (일반 결제)** (`:290-333`): `impUid`만 있으면 PG 검증 없이 `isSuccess=true`, **`PAID`** 로 저장한다 (`:313-314`).
- **카드 실패 시** — 경우가 둘로 갈린다:
  1. PG가 HTTP 비정상이거나 응답 `code != 0`이면 `PaymentProcessingException`(`PortOneApiClient.java:270-275`) → `OrderPaymentProcessingFailedException`으로 래핑(`OrderCommandService.java:306-309`) → `OrderBidCommandService`가 그대로 던진다(:212-214).
     같은 트랜잭션이므로 **Order, OrderItem, OrderShipment, SaleBid MATCHED, 창고 상태 변경이 모두 롤백**된다. OrderBid는 생성되지 않고 클라이언트는 오류 응답을 받는다.
     통신 오류(`PaymentApiException`)는 `@Retryable` 대상이라 최대 3회 재시도 후 같은 결과다 (`PortOneApiClient.java:224-228,288-290`).
  2. `code == 0`인데 `status != "success"`이면 예외가 없다. Payment는 PENDING으로 저장되고 판매가 SOLD, OrderBid MATCHED로 진행되어 **정상 응답(HTTP 200, "즉시 구매가 성공적으로 처리되었습니다")** 이 나간다.
     결제가 실패해도 매칭이 유지되는 경우다.
- **끝까지 성공하는가**: 아니다. 어느 결제 수단이든 즉시 구매 경로에서는 Order가 `PENDING_PAYMENT`를 벗어나지 않는다 (5번 참고).
  Order를 `PAYMENT_COMPLETED`로 바꾸는 코드는 `processPaymentAndShipment`(`OrderCommandService.java:165,175`)와 Kafka 컨슈머(`D/order/service/kafka/OrderEventConsumer.java:195`)뿐이며 즉시 구매는 둘 다 호출하지 않는다.
  또한 계좌이체 및 PG 응답이 `"success"`가 아닌 카드는 결제 자체가 PENDING인데도 판매는 이미 SOLD가 되고 "결제 완료" 알림이 나간다.

## 4. 알림: 수신자, 시점, 전달 방식

- 수신자 (`PaymentCommandService.java:434-456`):
  - **구매자**: "결제가 완료되었습니다. 주문 ID: {orderId}"
  - **판매자** (`sale.getSeller()`): "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}"
  - 두 알림 모두 `NotificationCategory.SHOPPING`, `NotificationType.BID`.
- 시점: `processPayment` 안에서 Payment 저장 직후, Sale을 SOLD로 바꾸기 직전이다 (`:83,403-404`).
  알림은 SOLD 변경보다 먼저 보낸다. Payment가 PENDING(계좌이체 등)이어도 "결제 완료" 문구로 나간다.
- 방식: 동기 호출이다 (Kafka 아님). `NotificationCommandService.createNotification` (`D/notification/service/command/NotificationCommandService.java:44-59`)이
  Notification을 **DB에 저장**하고, Redis 키 `WebSocket:User:{email}`가 있는 연결된 사용자에게만 **WebSocket**(`/queue/notifications`, `convertAndSendToUser`)으로 푸시한다 (`:302-323`).
  연결이 없으면 저장만 되고 조회 시 읽는다.
- 알림 실패는 로그만 남기고 삼킨다 (`PaymentCommandService.java:457-461,421-425`).
  단, `createNotification`이 `@Transactional`이라 내부 예외 시 공유 트랜잭션이 rollback-only로 표시되어 커밋 시점에 문제가 될 수 있다 (코드 읽기에 근거한 추론).

## 5. 최종 주문 상태와 "창고 보관" 선택 시 차이

- **최종 Order 상태: `PENDING_PAYMENT`**. 즉시 구매 경로에서 Order 상태를 바꾸는 코드가 없다 (`OrderCommandService.java:241-245` 이후 `updateStatus` 호출 없음).
  `PAYMENT_COMPLETED`, `PREPARING`, `COMPLETED`로 가지 않는다. 메시지는 "성공"이지만 주문 상태로는 결제 대기다.
  함께 남는 상태: SaleBid `MATCHED`, Sale `SOLD`, OrderBid `MATCHED`, Shipment `PENDING`, Payment는 3번 항목 참고.
- **구매자가 `warehouseStorage=true`를 선택한 경우: 아무 차이가 없다.**
  요청 값은 컨트롤러(`OrderBidCommandController.java:105`)와 서비스(`OrderBidCommandService.java:137`)를 거쳐 `createInstantOrder`의 `isWarehouseStorage` 파라미터로 들어오지만(`OrderCommandService.java:221`)
  메서드 본문(:222-318)에서 **한 번도 읽지 않는다**.
  - 구매자용 WarehouseStorage는 생성되지 않는다 (`createOrderStorage`는 `processPaymentAndShipment`(:170)에서만 호출).
  - Order는 `IN_WAREHOUSE`/`COMPLETED`로 바뀌지 않는다.
  - 배송 정보(OrderShipment)는 `false`일 때와 동일하게 생성된다 (:264-271).
  - 창고 관련 분기는 요청 값이 아니라 **판매자 Sale의 `isWarehouseStorage`** 이다 (`OrderCommandService.java:291-293`).
    이 경우에만 판매자 창고 보관 건이 `ASSOCIATED_WITH_ORDER`로 바뀐다.
    해당 창고 보관 정보가 없으면 예외로 전체가 롤백된다 (:295-301).
- 비교: 일반 경로(`processPaymentAndShipment`)는 `warehouseStorage=true`일 때 `PAYMENT_COMPLETED → PREPARING → IN_WAREHOUSE → COMPLETED`로 바꾸고 WarehouseStorage를 만든다 (`OrderCommandService.java:163-172`).
  즉시 구매 경로에는 이 처리가 없다.
