# 즉시 구매 처리 흐름 분석

경로 표기: `B` = `src/main/java/com/fream/back/domain/`

## 1. 진입 API / 처리 단계 / 동기·비동기 / 응답 ID

- 진입 API: `POST /order-bids/instant` — `B order/controller/command/OrderBidCommandController.java:22,89-90` (`@RequestMapping("/order-bids")` + `@PostMapping("/instant")`).
  요청 바디는 `InstantOrderRequestDto`(saleBidId, addressId, warehouseStorage, paymentRequest) — `B order/dto/InstantOrderRequestDto.java:25-34`.
- 단계:
  1. 컨트롤러가 이메일을 추출하고(`OrderBidCommandController.java:92`), `enrichPaymentRequest`로 paymentRequest에 userEmail을 넣고 orderId를 null로 둔다 — `:98`, `:119-122`.
  2. `OrderBidCommandService.createInstantOrderBid` 호출 (`@Transactional`) — `B order/service/command/OrderBidCommandService.java:118-119`, 컨트롤러 `:101-107`.
     - 입력 검증 `:123`, 구매자 조회 `:126`, SaleBid/Sale 조회·검증 `:129`, `:172-184`.
  3. `OrderCommandService.createInstantOrder` 호출(`@Transactional`, 같은 트랜잭션에 합류) — `OrderBidCommandService.java:133-139`, `B order/service/command/OrderCommandService.java:219-221`.
     주소 조회 `:238` → Order 저장 `:241-247` → OrderItem `:255` → OrderShipment `:264-271` → SaleBid 매칭+flush `:279-283` → (판매자 창고 보관이면) 창고 상태 변경 `:289-293` → 결제 `:305`.
  4. 결제는 `PaymentCommandService.processPayment` — `B payment/service/command/PaymentCommandService.java:57-107`. 결제 종류별 분기 `:67-80`, 이후 알림 + Sale 상태 변경 `:83` (`notifyUsersAndUpdateSaleStatus`, `:383-426`).
  5. 마지막으로 OrderBid 생성·저장 — `OrderBidCommandService.java:142`, `:189-207`.
- 동기/비동기: **동기**. Kafka 를 쓰지 않고 컨트롤러 → 서비스가 한 트랜잭션에서 모두 처리한 뒤 `ResponseEntity.ok`(HTTP 200)를 돌려준다 — `OrderBidCommandController.java:101-109`.
  (Kafka 비동기인 것은 `POST /orders/{orderId}/process-payment-shipment` 쪽이며 즉시 구매 경로가 아니다 — `B order/controller/command/OrderCommandController.java:42-69`.) 즉시 구매 경로에서는 `OrderEventProducer`/`OrderEventConsumer` 가 호출되지 않는다.
- 응답으로 돌려주는 ID: 변수명·메시지는 `orderId`("즉시 구매가 성공적으로 처리되었습니다.")지만 실제 값은 **OrderBid 의 ID** 이다.
  서비스가 `OrderBid` 를 반환하고(`OrderBidCommandService.java:119,144`) 컨트롤러가 그 `.getId()` 를 `orderId` 로 담아 반환한다 — `OrderBidCommandController.java:101-107,109`. Order 의 ID 가 아니다.

## 2. 새로 생성되는 엔티티와 상태 변화 순서 (단계 직후 상태)

단일 트랜잭션 안의 순서 (`OrderCommandService.createInstantOrder`, 아래 줄 번호는 이 파일):

| # | 동작 | 직후 상태 | 근거 |
|---|------|-----------|------|
| 1 | `Order` 생성·저장 (totalAmount = SaleBid 의 bidPrice) | Order.status = `PENDING_PAYMENT` | `OrderCommandService.java:241-247` |
| 2 | `OrderItem` 생성 (quantity 1, price = bidPrice) | — | `OrderCommandService.java:255`, `B order/service/command/OrderItemCommandService.java:45-52` |
| 3 | `OrderShipment` 생성 (주소 조회 값으로) | Shipment.status = `PENDING` | `OrderCommandService.java:264-271`, `B shipment/service/command/OrderShipmentCommandService.java:61-70` |
| 4 | 기존 `SaleBid` 에 order 연결, 상태 변경 후 flush | SaleBid.status = `MATCHED` (sale 패키지의 BidStatus) | `OrderCommandService.java:279-283`, `B sale/entity/SaleBid.java:58-61` |
| 5 | (Sale.isWarehouseStorage == true 일 때만) 창고 보관 엔티티 상태 변경 | WarehouseStorage.status = `ASSOCIATED_WITH_ORDER` | `OrderCommandService.java:289-293`, `B warehouseStorage/service/command/WarehouseStorageCommandService.java:116-133` |
| 6 | `Payment`(Card/Account/General) 생성 | 3절 참고 (`PAID` 또는 `PENDING`) | `PaymentCommandService.java:187-208,250-262,302-316` |
| 7 | 결제 후 알림 생성 + `Sale` 상태 변경 | Sale.status = `SOLD` | `PaymentCommandService.java:83,404` |
| 8 | `OrderBid` 생성·저장 (즉시 구매 플래그 true) | OrderBid.status = `MATCHED`, isInstantPurchase = true | `OrderBidCommandService.java:192-206`, `B order/entity/OrderBid.java:60-82,97-99` |

- 새로 만들어지는 엔티티: Order, OrderItem, OrderShipment, Payment(하위 타입), Notification(구매자·판매자 각 1건), OrderBid.
- 기존 엔티티 상태 변경: SaleBid(→MATCHED), Sale(→SOLD), (조건부) WarehouseStorage(→ASSOCIATED_WITH_ORDER).
- Sale 이 SOLD 가 되는 시점 상세: 결제 시점에는 아직 OrderBid 가 없어 `order.getOrderBid()` 가 null 이므로 `saleBidQueryService.findByOrderId` 경로(위 4번에서 flush 한 SaleBid)로 Sale 을 찾아 SOLD 로 바꾼다 — `PaymentCommandService.java:388-406`, `B sale/service/query/SaleBidQueryService.java:26-29`. `Sale.updateStatus` 는 전이 검증이 없어 그대로 대입된다 — `B sale/entity/Sale.java:73-75`.
- `Order` 의 `payment` 필드는 `order.assignPayment` 가 호출되지 않아 즉시 구매 경로에서는 설정되지 않는다(Payment 쪽에서만 order 를 가리킴) — `OrderCommandService.java:305` (반환값 미사용), `B order/entity/Order.java:75-80`.

## 3. 결제 수단별 결과

분기: `getResolvedPaymentType()` 의 타입(CARD/ACCOUNT/GENERAL) — `B payment/dto/PaymentRequestDto.java:74-87`, `PaymentCommandService.java:67-80`.
공통: 결제 요청의 orderId·userEmail·금액(>0) 검증 — `PaymentCommandService.java:117-146`.

| 수단 | 동작 | Payment 상태 | 근거 |
|------|------|--------------|------|
| 카드 | PaymentInfo 조회 → PortOne `processCardPayment` 호출 → CardPayment 저장. 응답 `status` 가 `"success"` 일 때만 PAID/성공 처리 | 성공: `PAID`, isSuccess=true. 그 외: 기본값 `PENDING`, isSuccess=false | `PaymentCommandService.java:157-208`, `B payment/entity/Payment.java:39,44` |
| 계좌이체 | 은행명 검증 후 외부 호출 없이 AccountPayment 저장 | 항상 `PENDING` (입금 확인 단계 없음) | `PaymentCommandService.java:236-262` |
| 일반 결제 | impUid 필수 여부만 확인(PortOne 검증 호출 없음), GeneralPayment 저장 | 즉시 `PAID`, isSuccess=true | `PaymentCommandService.java:290-316` |

- **즉시 구매는 끝까지 성공한다**(예외가 없으면): 결제 수단과 상관없이 결제 후 단계(`notifyUsersAndUpdateSaleStatus`)가 항상 실행되어 Sale 이 SOLD, 알림 2건이 생성되고 OrderBid 가 만들어지며 HTTP 200 이 반환된다 — `PaymentCommandService.java:83`, `OrderBidCommandService.java:142`.
  계좌이체(PENDING)여도 "결제가 완료되었습니다" 알림이 나가고 Sale 이 SOLD 가 된다. 즉 결제 상태(PAID 여부)는 이후 단계의 조건이 아니다.
- **결제 대행사가 카드 결제를 실패로 응답할 때** — 응답 형태에 따라 두 갈래:
  1. HTTP 비정상 또는 응답 `code != 0`: `PaymentProcessingException` 발생 — `B payment/portone/PortOneApiClient.java:270-275`. (RestClientException 이면 `PaymentApiException` — `:288-290`.) 예외는 `PaymentCommandService.java:89-94`에서 재전파 → `OrderCommandService.java:305-309` 에서 `OrderPaymentProcessingFailedException` 으로 감싸 던짐 → `:312-317`(바깥 catch)에서 OrderException 이므로 그대로 전파 → `OrderBidCommandService.java:145-147,212-218` 에서 재전파. `createInstantOrderBid`/`createInstantOrder` 가 `@Transactional` 이고 런타임 예외이므로 **Order·OrderItem·Shipment·SaleBid 매칭 등 전부 롤백**되고 OrderBid 도 만들어지지 않으며 오류 응답이 나간다.
  2. 응답 `code == 0` 이지만 `response.status` 가 `"success"` 가 아닌 경우(예: failed): 예외가 없다. `PaymentCommandService.java:203-206` 의 if 에 걸리지 않아 CardPayment 는 `PENDING`/isSuccess=false 로 저장되고, **그대로 진행**되어 알림 발송·Sale=SOLD·OrderBid=MATCHED 가 되며 HTTP 200 "성공" 이 나간다. 실패 결제를 감지·롤백하는 코드는 없다.

## 4. 알림 수신자 / 시점 / 방식

- 수신자 2명 (`PaymentCommandService.sendNotifications`, `:434-456`):
  - 구매자(`order.getUser()`): "결제가 완료되었습니다. 주문 ID: {orderId}" — `:438-443`.
  - 판매자(`sale.getSeller()`): "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}" — `:449-454`.
  - 둘 다 카테고리 `SHOPPING`, 타입 `BID`.
- 시점: 결제 처리 직후, 같은 요청·같은 트랜잭션 안에서 동기로 — `PaymentCommandService.java:83`, `:403`/`:416`(알림 → 이후 `:404`/`:419`에서 Sale SOLD). 결제 성공/PENDING 여부와 무관하게 발송된다(3절).
- 방식: `NotificationCommandService.createNotification` — DB 에 Notification 저장(`B notification/service/command/NotificationCommandService.java:53`) 후, Redis 키 `WebSocket:User:{email}` 가 있는(접속 중) 사용자에게만 WebSocket(`convertAndSendToUser(email, "/queue/notifications", dto)`)으로 실시간 전송 — `:37-38,57,164-175`. 접속 중이 아니면 저장만 되고 실시간 전송은 없다 — `:181-183`. Kafka 는 쓰지 않는다.
- 알림/Sale 상태 갱신 실패는 로깅만 하고 예외를 삼킨다 — `PaymentCommandService.java:421-425,457-`.

## 5. 최종 주문 상태와 창고 보관 선택 시

- **Order 의 최종 상태는 `PENDING_PAYMENT` 이다.** 즉시 구매 경로(`OrderCommandService.createInstantOrder`)에는 `order.updateStatus(...)` 호출이 한 번도 없다 — 상태는 생성 시 `PENDING_PAYMENT`(`OrderCommandService.java:244`)로 정해진 뒤 `:311` 에서 반환될 때까지 그대로다. 결제가 PAID 여도 Order 는 `PAYMENT_COMPLETED` 로 가지 않는다. (`PAYMENT_COMPLETED→PREPARING…→COMPLETED` 로 바꾸는 코드는 별도 API 의 `processPaymentAndShipment` — `OrderCommandService.java:163-176` / Kafka 컨슈머 `B order/service/kafka/OrderEventConsumer.java:192-217` — 에만 있다.) 메서드 이름·응답 메시지("처리되었습니다")와 달리 주문은 결제 대기 상태로 남는다.
  - 함께 남는 값: SaleBid=`MATCHED`, OrderBid=`MATCHED`(즉시 구매), Sale=`SOLD`, Shipment=`PENDING`, Payment=`PAID`(카드 성공·일반) 또는 `PENDING`(계좌/카드 비성공).
- **구매자가 "창고 보관"(`warehouseStorage=true`)을 선택한 경우: 사실상 아무것도 달라지지 않는다.**
  - 컨트롤러는 값을 서비스까지 넘기지만(`OrderBidCommandController.java:105`, `OrderBidCommandService.java:137`), `createInstantOrder` 는 파라미터 `isWarehouseStorage`(`OrderCommandService.java:221`)를 본문에서 전혀 사용하지 않는다. 즉 구매자 요청의 창고 보관 값은 무시된다.
  - 창고 관련 분기는 **판매자의 Sale 의 `isWarehouseStorage`** 만 본다(`OrderCommandService.java:291-294`, `B sale/entity/Sale.java:43`). 이 경우에도 변경은 기존 WarehouseStorage 의 상태를 `ASSOCIATED_WITH_ORDER` 로 바꾸는 것뿐이다(`WarehouseStorageCommandService.java:116-133`). 구매자의 선택과는 무관하다.
  - 반대로 구매자 보관용 `WarehouseStorage` 를 새로 만드는 `createOrderStorage`, Order 를 `IN_WAREHOUSE`/`COMPLETED` 로 바꾸는 로직은 다른 API(`processPaymentAndShipment`, `OrderCommandService.java:163-173`)에만 있고 즉시 구매 경로에서는 실행되지 않는다. 배송지(OrderShipment)도 창고 선택과 무관하게 항상 생성된다(`OrderCommandService.java:264-271`).
