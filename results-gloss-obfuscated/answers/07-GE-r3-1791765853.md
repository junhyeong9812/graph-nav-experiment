# 즉시 구매 처리 분석

경로 약어: `D = src/main/java/com/fream/back/domain`

이름 대응: Xzj27=OrderBid, Xdg64=Order, Xzz58=SaleBid, Xgg74=Sale, Xbf54=Payment, Xhx14=OrderShipment, Xnn94=WarehouseStorage, Xhm58=OrderItem, Xkh73=Notification.

## 1. 진입 API와 처리 단계 (동기, 응답 ID = 주문 ID)

1. 진입점은 `POST /order-bids/instant` 이다. (`D/m16/controller/command/Xzj27CommandController.java:22`, `:89-90`)
   - 요청 DTO는 `saleBidId`, `addressId`, `warehouseStorage`, `paymentRequest` 이다. (`D/m16/dto/Xpj49RequestDto.java`: 필드 `saleBidId`, `addressId`, `warehouseStorage`, `paymentRequest`)
2. 컨트롤러가 인증 이메일을 꺼내고(`Xzj27CommandController.java:92`), 결제 요청에 `userEmail` 을 넣고 `orderId=null` 로 만든다. (`:98`, `:119-122`)
3. 이어서 `Xzj27CommandService.createInstantOrderBid` 를 호출한다. (`Xzj27CommandController.java:101-107`)
4. `Xzj27CommandService.createInstantOrderBid` 는 `@Transactional` 이다. (`D/m16/service/command/Xzj27CommandService.java:118-149`)
   - 입력 검증: `:123`, `:154-167`
   - 구매자 조회: `:126`
   - 판매 입찰(Xzz58) 조회 및 sale 존재 확인: `:129`, `:172-184`. 판매 입찰의 상태(PENDING 여부)는 확인하지 않는다.
   - `orderCommandService.createInstantOrder` 호출: `:133-139`
   - `Xzj27`(OrderBid) 생성·저장: `:142`, `:189-207`
5. `Xdg64CommandService.createInstantOrder` 의 내부 순서는 다음과 같다. (`D/m16/service/command/Xdg64CommandService.java:219-319`)
   1. 배송지 조회: `:238`
   2. Order 저장: `:241-247`
   3. 결제 요청에 orderId 설정: `:250`
   4. OrderItem 생성: `:255-256`
   5. OrderShipment 생성: `:264-271`
   6. 판매 입찰 매칭 후 `flush`: `:279-283`
   7. 판매자 창고 상태 갱신: `:290-301`
   8. 결제 처리: `:305`
6. **동기 처리다.** 이 경로에는 Kafka 이벤트 발행이 없고, 한 HTTP 요청과 한 트랜잭션 안에서 모두 처리된다. 응답은 `200 OK` 이다. (`Xzj27CommandController.java:109`)
   - 비동기(Kafka) 처리는 별도 API `POST /{orderId}/process-payment-shipment` 에만 있다. 이 API 는 이벤트를 발행하고 `202 ACCEPTED` 로 응답한다. (`D/m16/controller/command/Xdg64CommandController.java:43`, `:54`, 응답 코드 `:57-70` 부근)
   - `Xdg64EventConsumer` 는 즉시 구매 경로에서 호출되지 않는다. (`D/m16/service/kafka/Xdg64EventConsumer.java:55-61`)
7. **응답으로 돌려주는 ID 는 주문 입찰(OrderBid, Xzj27)의 ID 다. 주문(Order) ID 가 아니다.**
   - 컨트롤러는 변수명과 응답 메시지가 `orderId` 이지만 `createInstantOrderBid(...).getId()` 를 담는다. (`Xzj27CommandController.java:101-107`)
   - `createInstantOrderBid` 의 반환 타입이 `Xzj27` 이고 마지막에 저장된 OrderBid 를 돌려준다. (`Xzj27CommandService.java:119`, `:142-144`, `:206`)
   - 주문(Order) ID 는 응답에 포함되지 않는다.

## 2. 새로 만들어지는 엔티티와 상태 변화 순서

처리 순서와 각 단계 직후 상태는 다음과 같다. 모두 `Xdg64CommandService.createInstantOrder` 와 그 호출부 기준이다.

| 순서 | 동작 | 엔티티 | 직후 상태 | 근거 |
|---|---|---|---|---|
| 1 | Order 생성·저장 | Order(Xdg64) 신규 | `PENDING_PAYMENT`, totalAmount=판매입찰가 | `Xdg64CommandService.java:241-247` |
| 2 | OrderItem 생성 (수량 1, 가격=입찰가) | OrderItem(Xhm58) 신규 | - | `Xdg64CommandService.java:255-256`, `D/m16/service/command/Xhm58CommandService.java:45-52` |
| 3 | OrderShipment 생성 | OrderShipment(Xhx14) 신규 | `PENDING` (Xpb98Status) | `Xdg64CommandService.java:264-271`, `D/m12/service/command/Xhx14CommandService.java:61-70` |
| 4 | 판매 입찰에 주문 연결 후 상태 변경 | SaleBid(Xzz58) 기존 | `MATCHED` (`assignOrder` 와 `updateStatus` 가 모두 MATCHED) | `Xdg64CommandService.java:279-280`, `D/m10/entity/Xzz58.java:58-61` |
| 5 | (판매가 창고 보관 판매일 때만) 판매자 창고 보관 갱신 | WarehouseStorage(Xnn94) 기존 | `ASSOCIATED_WITH_ORDER` | `Xdg64CommandService.java:291-294`, `D/m07/service/command/Xnn94CommandService.java:117-133` |
| 6 | 결제 생성 (결제 수단별로 다름, 3번 참고) | Payment(Xbf54) 신규 | `PAID` 또는 `PENDING` | `D/m06/service/command/Xbf54CommandService.java:57-83` |
| 7 | 결제 후처리: 판매자·구매자 알림 생성, 판매 상태 변경 | Sale(Xgg74) 기존 | `SOLD` | `Xbf54CommandService.java:83`, `:383-426` |
| 8 | OrderBid 생성·연결 | OrderBid(Xzj27) 신규 | `MATCHED`, `isInstantPurchase=true` | `Xzj27CommandService.java:192-206`, `D/m16/entity/Xzj27.java:60-99` |

보충 설명:

- **7단계(Sale → SOLD):**
  - 결제 시점에 Order 에는 아직 OrderBid 가 없다. OrderBid 는 8단계에서 만들어진다.
  - 그래서 `order.getOrderBid()` 는 null 이고 코드는 `saleBidQueryService.findByOrderId` 쪽 분기로 간다. (`Xbf54CommandService.java:388-407`)
  - 이 분기는 4단계 `flush` 덕분에 SaleBid 를 찾아 알림을 보내고 `sale.updateStatus(SOLD)` 를 호출한다. (`:391-405`, `D/m10/service/query/Xzz58QueryService.java:26`)
  - `Xgg74.updateStatus` 는 `canTransitionTo` 검사 없이 값을 그대로 넣는다. (`D/m10/entity/Xgg74.java:73-75`)
  - 이 후처리는 결제 성공 여부와 상관없이 실행된다. (`Xbf54CommandService.java:83`)
- **Order 상태는 그대로다.** 즉시 구매 경로 어디에서도 `Order.updateStatus` 를 호출하지 않는다.
  - `PAYMENT_COMPLETED`, `PREPARING`, `IN_WAREHOUSE`, `COMPLETED` 로의 전환은 `Xdg64CommandService.processPaymentAndShipment`(`:165-176`)와 `Xdg64EventConsumer.processCompleteOrder`(`:195-211`)에만 있다.
  - 이 두 곳은 즉시 구매 경로에서 호출되지 않는다.
- **OrderBid 상태:** `Builder` 에 `MATCHED` 를 주고(`Xzj27CommandService.java:196`), `assignOrder` 도 `MATCHED` 로 만든다. (`Xzj27.java:75`)
- Sale 이 `SOLD` 가 되어도 창고 보관 쪽 `SOLD` 전환(`updateWarehouseStatusToSold`)은 이 경로에서 호출되지 않는다. (`D/m07/service/command/Xnn94CommandService.java:150`)

## 3. 결제 수단별 결과, 성공 여부, 카드 결제 실패 시

공통: `processPayment` 는 `getResolvedPaymentType()` 으로 분기한다. (`Xbf54CommandService.java:67-80`, `D/m06/dto/Xbf54RequestDto.java:74-87`)
공통 검증은 orderId 일치, 이메일 일치, 금액 > 0 이다. (`Xbf54CommandService.java:117-146`)
결제 금액과 판매 입찰가(`totalAmount`)가 같은지는 확인하지 않는다.

| 수단 | 동작 | 결제 상태 / isSuccess | 근거 |
|---|---|---|---|
| 카드(CARD) | 저장된 카드정보로 PortOne 에 결제 요청 후 응답 `status` 가 `"success"` 일 때만 성공 처리 | 성공: `PAID`, `isSuccess=true`. 그 외: 기본값 `PENDING`, `isSuccess` 는 `paidAmount>0` 이라 생성자의 `setPaidAmount` 때문에 `true` | `Xbf54CommandService.java:157-208`, `D/m06/entity/Xqg94.java:38`, `D/m06/entity/Xbf54.java:60-63` |
| 계좌이체(ACCOUNT) | PG 호출 없음. 은행명 검증 후 저장 | `PENDING` (`isSuccess` 는 `setPaidAmount` 때문에 `true`) | `Xbf54CommandService.java:236-262`, `Xbf54.java:60-63` |
| 일반 결제(GENERAL) | `impUid` 필수. PG 호출·검증 없이 그대로 저장 | `PAID`, `isSuccess=true` | `Xbf54CommandService.java:290-316` |

**즉시 구매가 끝까지 성공하는가:**

- **카드·일반 결제:** 예외가 없으면 응답 200 으로 완료된다.
- **계좌이체:** 결제는 `PENDING` 인 채로 응답이 200 으로 끝난다. 입금 확인 단계는 이 경로에 없다.
  - 그런데도 Sale 은 `SOLD`, SaleBid 는 `MATCHED`, 알림 발송까지 이미 진행된다. (`Xbf54CommandService.java:83`, `:403-405`)
  - 즉 결제 확정 여부와 무관하게 판매 완료로 처리된다.
- **어느 수단이든 Order 는 `PENDING_PAYMENT` 에 머문다.** (2번 참고) "끝까지 성공"이라 해도 주문 상태가 결제완료·준비중으로 바뀌지는 않는다.

**결제 대행사가 카드 결제를 실패로 응답하면:**

- 실패 응답은 두 가지로 나뉜다.
  - **(a) HTTP 비 200 이거나 응답 `code != 0` 인 경우:** `Xxv33ApiClient.processCardPayment` 가 `Xdf64Exception` 을 던진다. (`D/m06/p05/Xxv33ApiClient.java:270-275`)
    - 예외 전파 경로: `createCardPayment` 가 그대로 재던짐(`Xbf54CommandService.java:180-181`, `:218-219`) → `processPayment` 가 그대로 재던짐(`:89-94`) → `createInstantOrder` 가 `Xqj91Exception` 으로 감쌈(`Xdg64CommandService.java:304-309`) → `Xdg64Exception` 이라 그대로 전파됨(`:312-315`, `Xzj27CommandService.java:212-215`).
    - 호출이 `@Transactional` 한 트랜잭션이라 Order, OrderItem, OrderShipment, SaleBid 매칭 등이 롤백되고 클라이언트는 오류 응답을 받는다.
    - 통신 오류(`RestClientException`)도 `Xbf54ApiException` 으로 같은 경로를 탄다. (`Xxv33ApiClient.java:288-290`)
  - **(b) 응답은 정상(`code == 0`)인데 내부 `status` 가 `"success"` 가 아닌 경우:** 예외가 없다.
    - `Xbf54CommandService.java:203-206` 의 `if` 를 건너뛰고 결제는 `PENDING` 으로 저장된다. (`:208`)
    - 이후 7단계 후처리가 그대로 실행되고(알림, `Sale=SOLD`), 즉시 구매는 성공 응답으로 끝난다.
    - 즉 "결제 실패"를 감지해 막는 코드가 이 경로에는 없다.
- 참고: Kafka 소비자(`processCompleteOrder`)에는 `!payment.isSuccess()` 검사가 있다. (`Xdg64EventConsumer.java:174-176`) 즉시 구매 경로에는 이런 검사가 없다.

## 4. 알림: 누가, 언제, 어떻게

- **누가·무엇을:** 결제 후처리에서 아래 두 알림이 만들어진다. (`Xbf54CommandService.java:434-456`)
  - 구매자: "결제가 완료되었습니다. 주문 ID: {orderId}"
  - 판매자(`sale.getSeller()`): "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}"
  - 카테고리는 둘 다 `SHOPPING`, 타입은 `BID` 다.
- **언제:** 결제 저장 직후, 같은 요청·같은 트랜잭션 안에서 동기로 만든다. (`Xbf54CommandService.java:83` → `:403`)
  - OrderBid 생성(8단계)보다 먼저다.
  - 결제 성공 여부와 무관하다. 계좌이체 `PENDING`, 카드 `status != success` 에도 발송된다.
- **방식:** `Xkh73CommandService.createNotification` 이 DB 에 알림을 저장한다. (`D/m15/service/command/Xkh73CommandService.java:44-54`)
  - 이어서 `sendRealTimeNotification` 이 Redis 키 `WebSocket:Xrd81:{email}` 의 존재를 확인하고, 있을 때만 WebSocket(`/user/{email}/queue/notifications`)으로 전송한다. (`:57`, `:303-322`, 상수 `:37-38`)
  - 키가 없으면(접속 중이 아니면) DB 에만 저장된다.
- **알림 실패는 무시된다.** 알림 생성·전송 예외는 잡아서 경고 로그만 남기고, 결제나 주문은 계속 진행된다. (`Xbf54CommandService.java:457-461`, 외곽 `:421-425`)
  - 구매자 알림이 먼저 실패하면 같은 `try` 안이라 판매자 알림도 건너뛴다. (`:434-456`)
- **이 경로에서는 보내지 않는 알림:** Kafka 경로의 "ORDER_COMPLETED" WebSocket 알림과 `notification-topic` 이벤트는 `Xdg64EventConsumer` 에만 있어 즉시 구매에서는 나가지 않는다. (`Xdg64EventConsumer.java:96`, `:287-329`)

## 5. 최종 주문 상태와 창고 보관 선택 시 차이

- **주문의 최종 상태는 `PENDING_PAYMENT` 다.**
  - 주문 저장 시 이 값으로 만든 뒤(`Xdg64CommandService.java:244`) 즉시 구매 경로에서 한 번도 바꾸지 않는다. (2번 설명 참고)
  - 같이 만들어진 다른 엔티티의 최종 상태: SaleBid `MATCHED`, OrderBid `MATCHED`(즉시 구매 표시), Sale `SOLD`, Payment 는 수단에 따라 `PAID`/`PENDING`, Shipment `PENDING`.
  - 메서드 이름·응답 메시지("즉시 구매가 성공적으로 처리되었습니다.", `Xzj27CommandController.java:109`)는 완료처럼 보이지만 실제 주문 상태는 결제 대기 그대로다.
- **구매자의 "창고 보관" 선택(`warehouseStorage`)은 아무 영향이 없다.**
  - 값은 로그에만 쓰이고(`Xzj27CommandController.java:94-95`) 서비스로 전달된다. (`:105`, `Xzj27CommandService.java:119-120`, `:133-139`)
  - 그러나 `createInstantOrder` 는 그 파라미터 `isWarehouseStorage` 를 본문에서 전혀 사용하지 않는다. (`Xdg64CommandService.java:220-319`)
  - 그래서 구매자 창고 보관용 `Xnn94` 는 만들어지지 않고(`createOrderStorage` 호출 없음), `IN_WAREHOUSE`/`COMPLETED` 로의 전환도 일어나지 않는다.
  - 창고 보관 시의 상태 전환 로직(`PAYMENT_COMPLETED → PREPARING → IN_WAREHOUSE → COMPLETED`, 창고 보관 정보 생성)은 Kafka 소비자와 `processPaymentAndShipment` 에만 있다. (`Xdg64EventConsumer.java:197-213`, `Xdg64CommandService.java:163-172`)
- **창고와 관련해 실제로 달라지는 것은 판매자 쪽이다.** 판매(Sale) 자체가 창고 보관 판매(`sale.isWarehouseStorage()`)이면 5단계에서 그 판매의 창고 보관 상태가 `ASSOCIATED_WITH_ORDER` 가 된다. (`Xdg64CommandService.java:291-294`, `D/m10/entity/Xgg74.java:43`)
  - 해당 창고 정보가 없으면 `findBySale` 이 예외를 던지고(`D/m07/service/query/Xnn94QueryService.java:30-33`) 전체가 롤백된다. (`Xdg64CommandService.java:295-301`)
