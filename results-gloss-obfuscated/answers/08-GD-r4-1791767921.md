# 구매자 배송: 운송장 등록 ~ 배송 완료 처리 분석

(이름 대응표: m12=shipment, m16=order, m10=sale, m15=notification. Xhx14=주문 배송(order_shipment), Xdg64=주문, Xzj27=주문 입찰(OrderBid), Xzz58=판매 입찰(SaleBid), Xgg74=판매(Sale), Xpb98Status=배송 상태 enum.)

## 결론 요약

- 운송장 등록 API(`PATCH /shipments/order/{shipmentId}/status`)는 의도상 "배송 IN_TRANSIT → 주문 IN_TRANSIT → 구매자 알림 → 판매 SOLD → 입찰 COMPLETED" 순서로 짜여 있다. 그러나 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문(상태 PREPARING)은 `PREPARING → IN_TRANSIT` 전환이 허용되지 않아 **끝까지 성공하지 못하고** 404 `S001`로 실패하며 전부 롤백된다.
- 배송 완료 감지는 `Xpb98BatchScheduler`(6시간마다) → Spring Batch `updateShipmentStatusesJob` → 실제 처리기 **`Xth19Processor`**(Playwright로 CJ대한통운 페이지 조회)가 한다.
- 배송 완료 판정 후 처리(`completeOrder`)는 (a) 일반 구매 입찰 주문에서는 실패(스킵)하고, (b) 즉시 구매 주문에서는 끝까지 성공한다.

## 2. 배송 완료 감지

### 2-1. 누가·언제·어떻게
1. 감지 주체는 스케줄러 `Xpb98BatchScheduler.scheduleShipmentStatusJob`이다. cron `0 0 */6 * * *` = **6시간마다 정각**(00,06,12,18시). 매번 timestamp 파라미터로 `updateShipmentStatusesJob`을 동기 실행한다. 예외는 `printStackTrace`만 하고 삼킨다. 근거: src/main/java/com/fream/back/global/config/Xpb98BatchScheduler.java:34-44
2. Job은 `updateShipmentStatusesStep` 하나이고 청크 크기 50, 스킵 한도 50이다. 근거: src/main/java/com/fream/back/domain/m12/config/Xqv91JobConfig.java:51-52, src/main/java/com/fream/back/domain/m12/config/Xqv91JobConfig.java:55-62, src/main/java/com/fream/back/domain/m12/config/Xqv91JobConfig.java:63-81
3. **조회 대상:** 상태가 `IN_TRANSIT` 또는 `OUT_FOR_DELIVERY`이고 `trackingNumber IS NOT NULL`인 주문 배송(Xhx14). JPA 페이징 리더. 근거: src/main/java/com/fream/back/domain/m12/config/Xqv91JobConfig.java:89-97
