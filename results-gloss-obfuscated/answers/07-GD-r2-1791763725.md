## 1. API, 처리 단계, 동기/비동기, 응답 ID

**API**: `POST /order-bids/instant` (`D/m16/controller/command/Xzj27CommandController.java:22`, `:89-90`). 인증된 이메일을 꺼내고(`:92`), `paymentRequest` 에 `userEmail` 을 넣고 `orderId=null` 로 비운다(`:98`, `:119-123`).

**동기 처리다.** Kafka 를 쓰지 않는다. Kafka 를 쓰는 곳은 별도 API `POST /{orderId}/process-payment-shipment` (`D/m16/controller/command/Xdg64CommandController.java:42`, `:54` 의 `sendOrderProcessingEvent`) 뿐이다. 즉시 구매는 HTTP 요청 스레드 안에서 `Xzj27CommandService.createInstantOrderBid` (`@Transactional`, `D/m16/service/command/Xzj27CommandService.java:118-119`) → `Xdg64CommandService.createInstantOrder` (`D/m16/service/command/Xdg64CommandService.java:219-220`) 순으로 전부 실행되고, 결제 대행사 HTTP 호출(`D/m06/p05/Xxv33ApiClient.java:266`)까지 같은 요청 안에서 끝난다.

처리 단계:
1. 입력 검증: 구매자 이메일, saleBidId, addressId, paymentRequest null 검사 (`Xzj27CommandService.java:123`, 검증 메서드는 `:154` 부근).
2. 구매자 조회, 판매 입찰(SaleBid) 조회 및 연결된 Sale 존재 확인 (`Xzj27CommandService.java:126-130`, `:172-183`).
3. `createInstantOrder` 호출 (`Xzj27CommandService.java:133`). 내부 순서:
   1. 배송지 조회 `addressQueryService.getAddress(email, addressId)` (`Xdg64CommandService.java:238`)
   2. Order 생성·저장, 상태 `PENDING_PAYMENT`, `totalAmount = saleBid.bidPrice` (`:241-247`), `paymentRequest.setOrderId(order.getId())` (`:250`)
   3. OrderItem 생성 (`:255-256`)
   4. OrderShipment 생성 (조회한 배송지 값으로, 상태 `PENDING`) (`:264-271`, `D/m12/service/command/Xhx14CommandService.java:56-70`)
   5. SaleBid 에 Order 연결 + `MATCHED` + `flush` (`:279-283`)
   6. 판매 쪽 창고 보관이면 창고 상태를 `ASSOCIATED_WITH_ORDER` 로 변경 (`:290-294`)
   7. 결제 처리 `paymentCommandService.processPayment` (`:305`)
4. OrderBid 를 `MATCHED` 로 만들어 저장, 즉시구매 플래그 설정 (`Xzj27CommandService.java:142`, `:189-206`).

**응답 ID 는 Order ID 가 아니라 OrderBid(주문 입찰, Xzj27) ID 다.** 컨트롤러 변수 이름은 `orderId` 지만(`Xzj27CommandController.java:101`) `createInstantOrderBid(...)` 가 돌려주는 `Xzj27` 의 `.getId()` 를 담는다(`:101-107`). 서비스가 반환하는 것은 `orderBidRepository.save(orderBid)` (`Xzj27CommandService.java:206`, 반환 `:144`). 응답 메시지는 "즉시 구매가 성공적으로 처리되었습니다."(`:109`).

## 3. 결제 수단별 결과, 성공 여부, 카드 실패 응답 시

`processPayment` 는 요청 DTO 의 실제 클래스(Card/Account/General)로 분기한다 (`Xbf54CommandService.java:67-76`, `D/m06/dto/Xbf54RequestDto.java:74-87`). 선행 검증: orderId 일치, userEmail 일치, `paidAmount > 0` (`:117-146`). 요청 금액이 입찰가와 같은지는 검사하지 않는다(`totalAmount` 는 입찰가, 결제 금액은 요청의 `paidAmount`).

| 수단 | 처리 | Payment 상태 / `isSuccess` | 근거 |
|---|---|---|---|
| 카드 (CARD) | 저장된 카드정보 조회 → PortOne(아임포트) 일회성 결제 호출 → 응답의 `status` 가 `"success"` 일 때만 `PAID` | 성공: `PAID` | `Xbf54CommandService.java:157-208` |
| 계좌이체 (ACCOUNT) | 은행명 검증만 하고 외부 호출 없음 | `PENDING` (입금 확인 전) | `:236-262` |
| 일반 (GENERAL) | `impUid` 필수. 외부 호출 없이 클라이언트가 준 결제 결과를 신뢰 | 즉시 `PAID`, `isSuccess=true` | `:290-316` |

**즉시 구매가 끝까지 성공하는가?** 요청이 예외 없이 끝나면 세 수단 모두 HTTP 200 으로 성공 처리되고, Order 는 `PENDING_PAYMENT`, SaleBid·OrderBid 는 `MATCHED`, Sale 은 `SOLD` 가 된다. 그러나 이 경로에서 Order 가 결제 완료 단계로 가지 않으므로 "끝까지" 간다는 말은 맞지 않다. 계좌이체는 결제가 `PENDING` 인 채로 판매가 `SOLD` 가 된다.

**결제 대행사가 카드 결제를 실패로 응답하면?** 두 갈래다.
1. **HTTP 오류이거나 응답 `code != 0`**: `Xdf64Exception("카드 결제 요청 실패: ...")` 이 던져진다 (`Xxv33ApiClient.java:270-274`). `processPayment` 가 다시 던지고(`Xbf54CommandService.java:89-94`), `createInstantOrder` 가 `Xqj91Exception` 으로 감싸 던진다(`Xdg64CommandService.java:304-309`, `:312-314`). `Xzj27CommandService` 의 `@Transactional` 이 롤백되어 Order, OrderItem, OrderShipment, SaleBid MATCHED, 창고 상태 변경이 모두 되돌려진다 (`Xzj27CommandService.java:118`, `:146-148`). 요청은 오류 응답이다.
2. **HTTP 200 + `code == 0` 이지만 `response.status` 가 `"success"` 가 아닌 경우(결제 거절)**: 예외가 없다. 상태를 `PAID` 로 올리지 않지만 Payment 는 저장되고 그대로 진행한다 (`Xbf54CommandService.java:203-208`). 이때 Payment 는 `status=PENDING` 인데 `isSuccess=true` 다. 카드 엔티티 생성자가 `setPaidAmount` 를 호출하고 이 메서드가 `isSuccess = paidAmount > 0` 으로 설정하기 때문이다 (`D/m06/entity/Xqg94.java:38`, `D/m06/entity/Xbf54.java:60-63`). 그 뒤 `notifyUsersAndUpdateSaleStatus` 가 그대로 실행되어 구매자·판매자 알림이 나가고 Sale 이 `SOLD` 가 되며 (`Xbf54CommandService.java:83`, `:403-404`), 결제 성공 여부를 다시 검사하는 코드가 즉시 구매 경로에 없다. 결과적으로 **응답은 "즉시 구매가 성공적으로 처리되었습니다"** 가 된다. (Kafka 소비자에는 `isSuccess` 검사가 있지만 `Xdg64EventConsumer.java:174-176`, 즉시 구매 경로는 거치지 않는다.)

## 4. 알림 수신자, 시점, 방식

알림은 `Xbf54CommandService.sendNotifications` 에서 만든다 (`Xbf54CommandService.java:434-462`), 호출은 `:403`/`:416`, 결제 저장 직후 `processPayment` 안이다 (`:83`).

| 수신자 | 내용 | 근거 |
|---|---|---|
| 구매자 (`order.getUser()`) | "결제가 완료되었습니다. 주문 ID: {orderId}" | `:436-443` |
| 판매자 (`sale.getSeller()`) | "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}" | `:447-454` |

두 알림 모두 카테고리 `SHOPPING`, 타입 `BID` (`:440-441`, `:451-452`).

- **시점**: 결제 레코드 저장 직후, 같은 HTTP 요청·같은 트랜잭션 안에서 동기적으로 (비동기·Kafka 아님). 계좌이체(결제 `PENDING`)나 카드 거절(위 3번 2갈래)이어도 보낸다. 결제 성공 여부로 분기하지 않는다.
- **방식**: `Xkh73CommandService.createNotification` 이 알림을 DB 에 저장하고 (`D/m15/service/command/Xkh73CommandService.java:44-54`), 사용자의 Redis 키 `WebSocket:Xrd81:{email}` 가 있을 때만 WebSocket(`/user/{email}/queue/notifications`)으로 실시간 전송한다 (`:57`, `:303-322`). 연결이 없으면 저장만 하고 푸시는 없다.
- 알림 생성 예외는 삼켜서 로그만 남기고 구매는 계속된다 (`Xbf54CommandService.java:457-461`, `:421-425`).
- 즉시 구매 경로에서는 `Xdg64EventConsumer` 의 "주문 완료/실패" WebSocket·Kafka 알림(`Xdg64EventConsumer.java:287-374`)이 **발송되지 않는다**. 그 소비자는 `order-processing-topic` 이벤트로만 동작한다.

## 5. 최종 상태와 창고 보관 선택 시 차이

**Order 의 최종 상태는 `PENDING_PAYMENT` 다.** `createInstantOrder` 는 Order 를 `PENDING_PAYMENT` 로 만들고 (`Xdg64CommandService.java:244`) 이후 `updateStatus` 나 `assignPayment` 를 호출하지 않는다 (`:219-319`). `PAYMENT_COMPLETED`/`PREPARING` 등으로 가는 코드는 별도 API `process-payment-shipment` 경로(`:111-202`, `Xdg64EventConsumer.java:166-229`)에만 있다. 결제가 성공(`PAID`)해도 Order 상태는 바뀌지 않는다. 그 외 최종 상태: SaleBid `MATCHED`, OrderBid `MATCHED`, Sale `SOLD`, OrderShipment `PENDING`, Payment 는 수단별(3번).

**구매자가 "창고 보관"을 선택하면?** 아무것도 달라지지 않는다. 컨트롤러가 `isWarehouseStorage()` 를 서비스에 넘기지만 (`Xzj27CommandController.java:104`, `Xzj27CommandService.java:119-120`, `:133-139`), `createInstantOrder` 는 이 값을 받기만 하고 본문에서 사용하지 않는다 (파라미터 선언 `Xdg64CommandService.java:221`, 본문 `:219-319` 에 참조 없음). 그래서 구매자 창고 보관용 Xnn94 생성(`createOrderStorage`), `IN_WAREHOUSE`/`COMPLETED` 전이는 일어나지 않는다. 그런 처리는 `process-payment-shipment` 경로에만 있다 (`Xdg64CommandService.java:163-172`, `Xdg64EventConsumer.java:197-211`).

혼동하기 쉬운 부분: 즉시 구매 경로에서 창고와 관련된 유일한 처리는 **판매자 쪽** `sale.isWarehouseStorage()` 가 true 일 때 기존 창고 보관 건의 상태를 `ASSOCIATED_WITH_ORDER` 로 바꾸는 것이다 (`Xdg64CommandService.java:290-294`). 이는 구매자의 선택과 무관하다.
