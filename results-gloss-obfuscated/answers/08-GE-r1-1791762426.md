# 구매자 배송: 운송장 등록 → 배송 완료

경로 약어: `B` = `src/main/java/com/fream/back`.
핵심 파일: `B/domain/m12/service/command/Xhx14CommandService.java`(OrderShipment 서비스), `B/domain/m12/config/Xqv91JobConfig.java`(배치 잡), `B/domain/m12/config/Xth19Processor.java`(배치 프로세서).

용어: Xhx14=OrderShipment, Xdg64=Order, Xzj27=OrderBid, Xzz58=SaleBid, Xgg74=Sale, Xpb98Status=배송 상태, Xdg64Status=주문 상태.

## 먼저: 결제·배송 처리 직후의 상태 (1·4번의 전제)

- 결제·배송 정보 처리(`processPaymentAndShipment`)에서 배송 엔티티(Xhx14)가 `PENDING`으로 생성되어 주문에 붙는다. (`B/domain/m12/service/command/Xhx14CommandService.java:55-75`, 호출 `B/domain/m16/service/command/Xdg64CommandService.java:148-156`)
- 창고 보관이 아닌 실배송 주문은 주문 상태가 `PAYMENT_COMPLETED → PREPARING`에서 멈춘다. (`B/domain/m16/service/command/Xdg64CommandService.java:175-176`; Kafka 경로도 동일하게 `PREPARING`까지만 `B/domain/m16/service/kafka/Xdg64EventConsumer.java:216-217`)
- `SHIPMENT_STARTED`로 보내는 코드는 코드베이스 어디에도 없다. `Xdg64Status.SHIPMENT_STARTED`는 정의(`B/domain/m16/entity/Xdg64Status.java:13`)와 전이표(`:26-28`)에만 나온다.
- 주문 상태 전이표: `PREPARING → {IN_WAREHOUSE, SHIPMENT_STARTED}`, `IN_TRANSIT → {COMPLETED}`, `PENDING_PAYMENT → {PAYMENT_COMPLETED, COMPLETED, IN_WAREHOUSE}`, `COMPLETED → {}`. (`B/domain/m16/entity/Xdg64Status.java:24-33`) 불허 전이는 `Xxc76StatusException`(`B/domain/m16/entity/Xdg64.java:113-121`).

## 1. 운송장 등록 요청

### 1-1. 진입 API

- `PATCH /shipments/order/{shipmentId}/status`, body는 `Xhx14RequestDto`(courier, trackingNumber). (`B/domain/m12/controller/command/Xhx14CommandController.java:20,33-49`)
- 컨트롤러는 `Xhx14CommandService.updateTrackingInfo(shipmentId, courier, trackingNumber)`를 호출한다. (`...Xhx14CommandController.java:41`)
- 참고: 같은 컨트롤러의 `POST /shipments/order/{id}/check-status`, `/check-status-string`은 별개 경로다. 택배사를 즉시 조회하고 운송장도 같이 저장한다. (`...Xhx14CommandController.java:58-100,103-135`, 서비스 `Xhx14CommandService.java:451-516`)

### 1-2. 코드가 의도한 처리 순서 (`Xhx14CommandService.updateTrackingInfo`, `:238-303`)

1. courier/trackingNumber 공백 검사 → `TRACKING_INFO_REQUIRED`. (`:243-246`)
2. 배송 조회 후 `shipment.updateTrackingInfo(courier, trackingNumber)`. 배송 상태를 전이표 검사 없이 곧바로 `IN_TRANSIT`으로 세팅한다. (`:249-256`, `B/domain/m12/entity/Xhx14.java:41-45`)
3. 주문 상태를 `IN_TRANSIT`으로 변경. (`:259-262`)
4. 구매자에게 알림 "상품이 출발하였습니다. 주문 ID: …" 1건. (`:265-273`)
5. `updateSaleStatusToSold(orderId)`: SaleBid→Sale이 `SOLD`로 갈 수 있으면 변경, 창고 보관이면 창고 상태 SOLD, 판매자에게 "상품이 성공적으로 판매 완료되었습니다" 알림. 이어서 OrderBid 기반으로 같은 처리를 한 번 더 한다. (`:276`, 본체 `:111-183`)
6. 창고 보관 상품이면 `updateWarehouseStatusToSold`를 한 번 더 호출. (`:279-286`)
7. `updateOrderAndSaleBidStatusToCompleted`: OrderBid·SaleBid가 `MATCHED`이면 `COMPLETED`로 변경. (`:289`, 본체 `:412-440`)

알림 의도: 구매자 1건(출발) + 판매자 최대 1건(판매 완료).

### 1-3. 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문: 끝까지 성공하지 못한다

- 실패 지점은 단계 3, `order.updateStatus(Xdg64Status.IN_TRANSIT)` (`Xhx14CommandService.java:260`)이다.
- 이유: 주문이 `PREPARING`인데 `PREPARING → IN_TRANSIT`은 허용되지 않는다(`B/domain/m16/entity/Xdg64Status.java:26`). `IN_TRANSIT`은 `SHIPMENT_STARTED`에서만 갈 수 있고(`:28`) `SHIPMENT_STARTED`는 아무도 세팅하지 않는다. 그래서 `Xdg64.updateStatus`가 `Xxc76StatusException`을 던진다. (`B/domain/m16/entity/Xdg64.java:113-121`)
- 예외 처리: `catch (Xpb98Exception)`에는 안 걸리고 `catch (Exception e)`(`Xhx14CommandService.java:295-302`)에서 `Xpb98Exception(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")`로 다시 감싸 던진다. 에러코드가 실제 원인과 무관한 `SHIPMENT_NOT_FOUND`로 바뀐다.
- 무엇이 저장되나: 아무것도 저장되지 않는다. 메서드가 `@Transactional`(`:238`)이고 런타임 예외가 밖으로 나가므로 롤백된다.
  - 2단계에서 바꾼 courier/trackingNumber/`IN_TRANSIT` 배송 상태도 롤백되어 DB의 배송은 `PENDING`, 운송장 없음 상태로 남는다.
  - 알림은 단계 4(주문 상태 변경 이후)에서 만들어지므로 한 건도 생성되지 않는다.
- 응답: 전역 핸들러 `Xks43ExceptionHandler.handleGlobalException`이 `Xks43Exception` 계열을 받아 `errorCode.getStatus()`로 응답한다. (`B/global/exception/Xks43ExceptionHandler.java:49-63`)
  - HTTP 404, body는 `ErrorResponse`(code `S001`, message "배송 정보를 찾을 수 없습니다.", path). (`B/domain/m12/exception/Xpb98ErrorCode.java:12`)
  - 예외에 담긴 상세 메시지는 응답 body에 쓰이지 않는다. 핸들러가 `errorCode.getMessage()`만 쓴다.
  - 컨트롤러의 "업데이트 완료" 로그와 `200 OK`(`...Xhx14CommandController.java:47-48`)에는 도달하지 못한다.
- 이 상태가 되면 `PATCH`로는 배송이 `IN_TRANSIT`에 들어가지 못하므로, 아래 2번 배치 대상이 되려면 `check-status` 계열 API로 운송장을 저장하는 길뿐이다(2-4 참고).
- 주문이 이미 `COMPLETED`인 창고 보관 주문, `PENDING_PAYMENT`인 즉시 구매 주문(`B/domain/m16/service/command/Xdg64CommandService.java:244`)도 `→ IN_TRANSIT`이 불허되어 똑같이 실패한다. (`Xdg64Status.java:24,31`)
- 추가 결함(가정적으로 3단계를 통과해도): `Xzz58QueryService.findByOrderId`는 SaleBid가 없으면 `null`이 아니라 `IllegalArgumentException`을 던진다. (`B/domain/m10/service/query/Xzz58QueryService.java:26-29`) 그래서 `updateSaleStatusToSold`의 `saleBid != null` 분기(`Xhx14CommandService.java:117`)는 의미가 없고, 판매자 매칭 전 주문은 5단계에서 예외가 난다. 창고 보관 판매는 5단계에서 이미 SOLD로 만든 창고 상태를 6단계에서 다시 SOLD로 바꾸려 해 `Xfw62Exception("이미 판매 완료 상태…")`이 난다. (`B/domain/m07/service/command/Xnn94CommandService.java:150-161`)

## 2. 배송 완료 감지

### 2-1. 누가, 언제, 어떻게

- 스케줄러 `Xpb98BatchScheduler.scheduleShipmentStatusJob()`가 `@Scheduled(cron = "0 0 */6 * * *")`로 스프링 배치 잡 `updateShipmentStatusesJob`을 기동한다. 매번 `timestamp` 잡 파라미터를 넣어 새 인스턴스로 실행한다. (`B/global/config/Xpb98BatchScheduler.java:34-44`)
- 주기: 6시간마다 정각(00:00, 06:00, 12:00, 18:00). Spring 6필드 cron(초 분 시 …)이다.
- 잡 정의: 스텝 1개, chunk 50, skip 한도 50. (`B/domain/m12/config/Xqv91JobConfig.java:51-52,55-60,62-82`)
- 조회 방식: Playwright(헤드리스 브라우저)로 `https://trace.cjlogistics.com/next/tracking.html?wblNo=<운송장>`(CJ대한통운)에 접속하고 `tbody#statusDetail tr`을 기다린다. 마지막 행의 5번째 `td`(index 4) 텍스트를 상태 문자열로 쓴다. (`B/domain/m12/config/Xth19Processor.java:72-90,181`)

### 2-2. 조회 대상

- JPQL: `SELECT s FROM Xhx14 s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL`, 페이지 크기 50. (`B/domain/m12/config/Xqv91JobConfig.java:93-96`)
- `PENDING`·`DELIVERED` 등은 대상이 아니다.

### 2-3. 실제로 실행되는 처리 코드 (비슷한 코드 중 선택)

- 실제 실행: `Xth19Processor` (`B/domain/m12/config/Xth19Processor.java:57-`). 스텝이 `new Xth19Processor(playwrightBrowserManager(), notificationService, orderService)`로 직접 연결한다. (`B/domain/m12/config/Xqv91JobConfig.java:69-73`)
- 실행되지 않는 유사 코드:
  - `Xqv91JobConfig.shipmentItemProcessor()` (`:106-177`)는 `@Bean`이지만 스텝에 연결되지 않는다(`:69`). `.processor(...)`는 `Xth19Processor`만 쓴다.
  - `Xqv91JobConfig.parseCjLogisticsStatus` (`:186`)는 호출처가 없다.
  - `Xhx14CommandService.updateShipmentStatuses()` (`B/domain/m12/service/command/Xhx14CommandService.java:308-391`)는 `@Scheduled`도 없고 호출처도 없다. `grep`으로 정의 외 참조가 없음을 확인했다.
  - `Xxx20.getCurrentTrackingStatus` (`B/global/utils/Xxx20.java:33-115`)는 `check-status` API용 단건 조회에서만 쓰인다(`Xhx14CommandService.java:477`).

### 2-4. 택배사 문자열 → 내부 상태

`Xth19Processor.mapToShipmentStatus` (`B/domain/m12/config/Xth19Processor.java:220-225`)는 정확히 일치하는 문자열만 본다.

| 택배사 문자열 | 내부 상태 |
|---|---|
| `"배송완료"` | `DELIVERED` |
| `"배송출발"` | `OUT_FOR_DELIVERY` |
| 그 외 전부 (집화처리, 간선상차 등) | `IN_TRANSIT` |

- 공백은 `trim()` 후 비교하고, 부분 일치는 하지 않는다. (`...Xth19Processor.java:181`)
- 대상 배송이 존재하려면 운송장이 저장된 `IN_TRANSIT`/`OUT_FOR_DELIVERY`여야 한다. `PATCH` 경로는 1-3대로 실배송 주문에서 롤백되므로, 실제로는 `check-status` API가 배송을 `IN_TRANSIT` 등으로 저장해야 배치 대상이 된다. (`Xhx14CommandService.java:473-498`)
- 같은 상태(`newStatus == 현재 상태`)면 변경 없이 반환한다. (`...Xth19Processor.java:101-105`)
- 배송이 `OUT_FOR_DELIVERY`인데 택배사가 그 외 문자열을 주면 `IN_TRANSIT`으로 매핑되고, `OUT_FOR_DELIVERY → IN_TRANSIT`은 전이표에 없어(`B/domain/m12/entity/Xpb98Status.java:23-28`) `IllegalStateException`이 난다. 이 예외는 `Xpb98Exception(EXTERNAL_TRACKING_SERVICE_ERROR)`으로 감싸져 해당 건이 skip된다. (`...Xth19Processor.java:133-146`)

## 3. 배송 완료 판정 이후 (`DELIVERED` 판정 시)

### 3-1. 상태 변경 순서 (`Xth19Processor.process`, `:108-118`; `completeOrder`, `Xhx14CommandService.java:190-229`)

1. 배송: `orderShipment.updateStatus(DELIVERED)`. `IN_TRANSIT`/`OUT_FOR_DELIVERY → DELIVERED`는 허용된다. (`B/domain/m12/entity/Xpb98Status.java:16-27`)
2. `orderService.completeOrder(orderId)` 호출. (`...Xth19Processor.java:116`)
   1. OrderBid를 `order_id`로 조회, 없으면 `IllegalArgumentException`. (`Xhx14CommandService.java:196-197`)
   2. 주문 `COMPLETED`로 변경. (`:204`)
   3. `updateSaleStatusToSold(orderId)`. (`:208`, 본체 `:111-183`)
      - SaleBid 조회 → `sale.status.canTransitionTo(SOLD)`면 Sale `SOLD`로 변경, 창고 보관이면 창고 `SOLD`, 판매자 알림. (`:116-147`)
      - 이어서 OrderBid의 Sale에 대해서도 `canTransitionTo(SOLD)`면 `SOLD` + 판매자 알림. (`:150-180`)
   4. 구매자 알림 "[completeOrder] 주문이 완료 처리되었습니다. 주문 ID: …". (`:211-219`)
3. `notificationService.notifyShipmentCompleted(order)`: 구매자 알림 "[배송 완료] 상품이 배송 완료되었습니다. 주문 ID: …". (`...Xth19Processor.java:117`, `B/domain/m15/service/command/Xkh73CommandService.java:219-234`)
4. 프로세서가 반환한 Xhx14를 `JpaItemWriter`가 저장한다. (`B/domain/m12/config/Xqv91JobConfig.java:74,241-246`)

### 3-2. 알림 건수

- 구매자: 최대 2건. "[completeOrder] 주문이 완료 처리…"와 "[배송 완료] …".
- 판매자: Sale이 `SOLD`로 전이될 때만 1건. 두 번째 블록은 이미 `SOLD`라 `SOLD → SOLD`가 불허되므로 중복 알림이 없다. (`B/domain/m10/entity/Xgg74Status.java:91`)
- 단, 아래 4번대로 실제 데이터에서는 판매자 알림이 가지 않는다.

### 3-3. 주문 입찰·판매 입찰

- 이 경로(배치·`check-status`)에서는 OrderBid·SaleBid의 상태를 바꾸지 않는다. 둘 다 `MATCHED`로 남는다.
  - `COMPLETED`로 바꾸는 `updateOrderAndSaleBidStatusToCompleted`는 `private`이고 호출처가 `updateTrackingInfo`(`Xhx14CommandService.java:289`) 하나뿐이다. 그 경로는 1-3대로 실패한다.
  - `completeOrder`·`Xth19Processor`·`updateAndCheckShipmentStatus` 어디에서도 이 메서드나 `bid.updateStatus(COMPLETED)`를 부르지 않는다. (`Xhx14CommandService.java:190-229,451-516`)
- Sale 상태는 `canTransitionTo(SOLD)`가 참인 `SELLING`/`ON_AUCTION`에서만 `SOLD`가 될 수 있다. (`B/domain/m10/entity/Xgg74Status.java:88-90`) 그런데 코드에서 Sale이 `SELLING`/`ON_AUCTION`이 되는 곳은 없다. `PENDING_SHIPMENT`(`B/domain/m10/service/command/Xgg74CommandService.java:62,108`), `IN_TRANSIT`(`:142`), `IN_STORAGE`(`B/domain/m12/service/command/Xxn30CommandService.java:82`)만 있다. 따라서 배송 완료 시점의 `updateSaleStatusToSold`는 대부분 "변경 불가" 분기로 가서 아무 것도 하지 않는다. 결제 시점에 Sale이 이미 `SOLD`가 되는 경우는 4번 참조.

## 4. 주문 종류별 차이

| | (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문 | (b) 즉시 구매 주문 |
|---|---|---|
| 주문 상태 | `PREPARING` | `PENDING_PAYMENT` (즉시 구매 생성·결제 어디서도 `updateStatus` 안 함, `Xdg64CommandService.java:220-310`) |
| `completeOrder`의 `→ COMPLETED` | 불허: `PREPARING`에는 `COMPLETED`가 없음 (`Xdg64Status.java:26`) | 허용: `PENDING_PAYMENT → COMPLETED` (`Xdg64Status.java:24`) |
| 3의 처리가 끝까지 진행되나 | 아니오. 주문 변경 시점에서 예외 | 예, 예외 없이 끝까지 진행 |

### (a) 결과: 3의 처리가 끝나지 않고 실패한다

- `completeOrder`에서 `order.updateStatus(COMPLETED)`가 `Xxc76StatusException`을 던진다. (`Xhx14CommandService.java:204`)
- `catch (Exception)`이 `Xpb98Exception(ORDER_NOT_FOUND_FOR_SHIPMENT, "주문 완료 처리 중 오류 발생: …")`로 감싸 던진다. 실제 원인은 "주문을 못 찾음"이 아니라 상태 전이 불가다. (`:221-228`)
- 구매자·판매자 알림이 0건이다. 알림은 주문 상태 변경 이후에 만들어지기 때문이다. 알림 서비스도 `notifyShipmentCompleted`까지 가지 못한다.
- 배치에서의 처리:
  - `completeOrder`는 프록시를 거치는 `@Transactional`이라 청크 트랜잭션에 참여하고, 예외가 나가면 롤백 대상이 된다.
  - 예외는 프로세서에서 `Xpb98Exception`으로 다시 던져진다(`Xth19Processor.java:133-146`). `skip(Exception.class)`에 걸려 해당 건이 skip된다. (`Xqv91JobConfig.java:76-77`)
  - 배송 완료 반영분은 저장되지 않으므로 배송은 계속 `IN_TRANSIT`/`OUT_FOR_DELIVERY`로 남는다. 6시간 뒤 배치가 같은 건을 다시 조회하고 같은 이유로 또 실패한다.
- `check-status` 경로(`updateAndCheckShipmentStatus`)도 같다. `completeOrder`가 예외를 던지면 바깥 `@Transactional`이 롤백되고 `Xpb98Exception`이 그대로 전파된다. (`Xhx14CommandService.java:483-489,505-506`) 컨트롤러가 HTTP 404(`S102`)를 돌려주며 body는 없다(`...Xhx14CommandController.java:76-81`).
  - 이때 같은 호출에서 저장했던 운송장·`IN_TRANSIT` 변경도 함께 롤백된다.

### (b) 결과: 배치로 끝까지 진행되지만 판매자 알림과 입찰 상태 변경은 일어나지 않는다

- 주문 `PENDING_PAYMENT → COMPLETED` 성공. (`Xdg64Status.java:24`)

## 5. 실패 처리 (주기 처리 중 한 건이 실패할 때)

실제로 실행되는 쪽은 Spring Batch 스텝이다 (`Xqv91JobConfig.java:62-82`).

- 한 건이 예외를 던지면(운송장 없음, 조회 실패, HTML 파싱 실패, 상태 전이 불가, `completeOrder` 실패 등) `faultTolerant().skip(Exception.class).skipLimit(50)`에 의해 skip된다. (`:75-77`)
  - 그 청크의 트랜잭션이 롤백되고, 스프링 배치가 청크 내 아이템을 개별로 다시 처리한다. 실패한 건만 제외되고 나머지는 정상 처리·저장된다. 따라서 성공한 건은 다시 조회(Playwright 호출)된다.
  - skip된 건은 `SkipListener`가 에러 로그만 남기며 DB에는 아무 변경이 없다. (`:252-`, `shipmentSkipListener`)
  - 상태가 바뀌지 않은 채라 다음 6시간 주기에 다시 대상이 된다. 별도 재시도 횟수·실패 표시는 없다.
- skip이 50건을 넘으면 `SkipLimitExceededException`으로 스텝과 잡이 실패하고 남은 건은 처리되지 않는다. 이 예외는 `jobLauncher.run`이 던지는 것이 아니라 실행 결과(`JobExecution`)에 남으므로 스케줄러의 `catch`(`Xpb98BatchScheduler.java:41-43`)에는 대개 걸리지 않는다. 실패해도 알림·예외가 밖으로 나가지 않는다.
- 주의: 리더가 `status IN (...)` 조건의 페이징 쿼리를 쓰는데 처리 중 상태가 바뀌는 항목(DELIVERED 반영분)이 있어 오프셋 페이징에서 일부 건을 건너뛸 수 있다. (`Xqv91JobConfig.java:89-96`) 50건을 초과하는 대상이 있을 때만 해당하며 이 항목은 코드 구조에 근거한 추정이다.
- 프로세서 안에서 Playwright `Page`는 `finally`에서 닫는다. 스텝 전후 리스너가 브라우저를 열고 닫는다. (`Xth19Processor.java:146-157`, `B/domain/m12/config/Xmb36Listener.java:15-25`)
- 참고: 사용되지 않는 `Xhx14CommandService.updateShipmentStatuses()`는 건별 `try/catch`로 실패를 세고 계속 진행하는 방식(`:322-388`)이지만 호출되지 않는다.
