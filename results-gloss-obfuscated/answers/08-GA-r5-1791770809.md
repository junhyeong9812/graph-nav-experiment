# 구매자 배송: 운송장 등록 → 배송 완료

경로 약어 (모두 `src/main/java/com/fream/back/` 아래):
- `D` = `domain/`
- 배송 = m12, 주문 = m16 (Xdg64), 구매입찰 = Xzj27, 판매입찰 = Xzz58, 판매 = Xgg74(m10), 알림 = m15

핵심 요약
- 운송장 등록 API(1번)는 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문에서 **항상 실패**한다. 주문이 `PREPARING`에서 멈추고, `PREPARING → IN_TRANSIT` 전이가 허용되지 않는다. 롤백되어 아무것도 저장되지 않고, 응답은 404 / `S001`이다.
- 주기 배치는 6시간마다 돈다. 실제 실행되는 처리 코드는 `Xth19Processor`이다.
- 배송 완료 판정 후 `completeOrder`는 (a) 일반 구매 입찰 주문(`PREPARING`)에서는 `COMPLETED` 전이가 막혀 실패한다. (b) 즉시 구매 주문(`PENDING_PAYMENT`)에서는 성공한다.
- 배치 경로에서는 구매입찰·판매입찰이 `COMPLETED`로 바뀌지 않는다. `MATCHED` 그대로다.

## 1. 운송장 등록 요청

### 1-1. 진입 API
1. `PATCH /shipments/order/{shipmentId}/status`, body는 `Xhx14RequestDto`(courier, trackingNumber)이다.
   - 컨트롤러 클래스 매핑: `D/m12/controller/command/Xhx14CommandController.java:20`
   - 메서드: `Xhx14CommandController.java:33-49`
   - 서비스 호출: `Xhx14CommandController.java:41` → `Xhx14CommandService.updateTrackingInfo` (`D/m12/service/command/Xhx14CommandService.java:239`)
2. 같은 컨트롤러에 즉시 조회용 `POST /{shipmentId}/check-status`(`Xhx14CommandController.java:58-94`)와 `check-status-string`(`:103-138`)도 있다. 이 둘은 `updateAndCheckShipmentStatus`를 호출한다(`Xhx14CommandService.java:452`). 내용은 1-4에서 다룬다.

### 1-2. 코드가 의도한 상태 변경 순서 (`updateTrackingInfo`, `Xhx14CommandService.java:239-303`)
1. 택배사·운송장 번호가 비어 있으면 `TRACKING_INFO_REQUIRED`(400)를 던진다. (`:243-246`, 코드 `Xpb98ErrorCode.java:15`)
2. 배송(Xhx14)을 조회한다. 없으면 `SHIPMENT_NOT_FOUND`다. (`:249-253`)
3. 배송: `shipment.updateTrackingInfo`가 courier·trackingNumber를 저장하고 상태를 `IN_TRANSIT`으로 직접 대입한다. 전이 검사는 없다. (`:256`, `D/m12/entity/Xhx14.java:41-45`)
4. 주문: `order.updateStatus(Xdg64Status.IN_TRANSIT)` (`:259-260`)
5. 구매자 알림 1건: "상품이 출발하였습니다. 주문 ID: …" (SHOPPING / BID) (`:265-271`)
6. `updateSaleStatusToSold(orderId)` (`:276`, 본문 `:111-183`)
   - SaleBid가 있으면 판매(Xgg74)를 `SOLD`로 바꾼다 (`:116-123`).
   - 창고 보관 판매면 창고 상태를 SOLD로 바꾼다 (`:126-129`).
   - 판매자 알림 1건: "상품이 성공적으로 판매 완료되었습니다…" (`:132-138`)
   - 이어서 OrderBid 쪽 sale도 SOLD로 바꾸고 판매자 알림을 한 번 더 보낸다 (`:150-176`).
7. 창고 보관 판매면 창고 상태를 다시 한 번 갱신한다. (`:279-286`)
8. `updateOrderAndSaleBidStatusToCompleted`: OrderBid·SaleBid가 `MATCHED`이면 `COMPLETED`로 바꾼다. (`:289`, 본문 `:412-440`)
   - 이 메서드는 `updateTrackingInfo`에서만 호출된다.

즉 의도는 배송 IN_TRANSIT → 주문 IN_TRANSIT → 구매자 알림 → 판매 SOLD(+판매자 알림) → 입찰 COMPLETED 순서다.

### 1-3. 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문에서는 끝까지 성공하지 못한다
1. 일반 구매 입찰 주문은 `createOrderFromBid`에서 `PENDING_PAYMENT`로 만들어진다. (`D/m16/service/command/Xdg64CommandService.java:76-82`)
2. 결제·배송 처리(`processPaymentAndShipment`)에서 실배송(창고 보관 아님)이면 `PAYMENT_COMPLETED` → `PREPARING`까지만 간다. (`Xdg64CommandService.java:173-177`)
   - Kafka 소비자 경로도 `PREPARING`에서 끝난다. (`D/m16/service/kafka/Xdg64EventConsumer.java:214-219`)
   - 코드 어디에서도 `SHIPMENT_STARTED`로 바꾸지 않는다. `Xdg64Status.SHIPMENT_STARTED`는 정의(`D/m16/entity/Xdg64Status.java:144`)와 허용 전이표(`:159, :161`)에만 나온다.
3. 허용 전이표는 `PREPARING → {IN_WAREHOUSE, SHIPMENT_STARTED}`뿐이고, `IN_TRANSIT`은 `SHIPMENT_STARTED`에서만 갈 수 있다. (`Xdg64Status.java:159, :161`)
4. 따라서 `updateTrackingInfo`의 `order.updateStatus(IN_TRANSIT)`(`Xhx14CommandService.java:260`)에서 실패한다.
   - `Xdg64.updateStatus`가 `Xxc76StatusException("상태 전환이 허용되지 않습니다: PREPARING -> IN_TRANSIT")`를 던진다. (`D/m16/entity/Xdg64.java:113-121`)
   - 이 예외는 `Xdg64Exception` 계열이라 `catch (Xpb98Exception)`(`Xhx14CommandService.java:293`)에 걸리지 않는다. 일반 `catch (Exception)`(`:295-302`)이 이를 `Xpb98Exception(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")`로 바꿔 던진다.
5. 무엇이 저장되나: **아무것도 저장되지 않는다.**
   - `@Transactional`(`:238`) 메서드에서 RuntimeException(`Xks43Exception extends RuntimeException`, `global/exception/Xks43Exception.java:10`)이 밖으로 나가므로 롤백된다.
   - 3단계에서 엔티티에 대입한 courier·trackingNumber·`IN_TRANSIT`은 DB에 반영되지 않는다.
   - 4단계에서 실패하므로 구매자 알림(5단계), 판매 SOLD, 입찰 COMPLETED는 실행조차 되지 않는다.
   - 배송은 `PENDING`, 주문은 `PREPARING`으로 남는다.
6. 응답: 전역 핸들러가 `Xpb98Exception`을 받아 **HTTP 404**, 바디 `ErrorResponse(code="S001", message="배송 정보를 찾을 수 없습니다.", status=404, path)`를 돌려준다. (`global/exception/Xks43ExceptionHandler.java:459-473`, `Xpb98ErrorCode.java:12`)
   - 원인은 실제로는 주문 상태 전이 거부인데 응답은 "배송 정보 없음"이다. 상세 메시지는 응답 바디에 노출되지 않는다.
   - 만약 주문 상태가 허용되어 통과한다 해도 `Xzz58QueryService.findByOrderId`는 SaleBid가 없으면 `IllegalArgumentException`을 던진다 (`D/m10/service/query/Xzz58QueryService.java:26-29`). `updateSaleStatusToSold`의 `saleBid != null` 분기(`Xhx14CommandService.java:117`)는 의도와 달리 동작한다. 이 경우에도 같은 일반 `catch`로 같은 404가 된다.

### 1-4. 참고: 즉시 조회 API (`check-status`)
- `updateAndCheckShipmentStatus`는 `shipment.updateTrackingInfo`로 배송을 바로 `IN_TRANSIT`으로 만든다 (`Xhx14CommandService.java:473`). 주문 상태는 건드리지 않으므로 위 전이 문제를 우회한다.
- 이어서 CJ 조회 결과로 분기한다 (`:477-498`).
  - 배송완료이면 `completeOrder`를 호출한다 (`:489`).
  - 배송출발이면 `OUT_FOR_DELIVERY`로 바꾼다 (`:491-493`).
  - 그 외에는 `shipment.updateStatus(IN_TRANSIT)`를 호출하는데, `IN_TRANSIT → IN_TRANSIT`은 전이표에 없어 `IllegalStateException`이 난다 (`:497`, `D/m12/entity/Xpb98Status.java:16-21`, `Xhx14.java:47-55`).
  - 이 예외는 `EXTERNAL_TRACKING_SERVICE_ERROR`(503)로 감싸지며 롤백된다 (`:507-514`). 컨트롤러는 503을 상태코드로만 돌려준다 (`Xhx14CommandController.java:80-86`).

## 2. 배송 완료 감지

### 2-1. 누가·언제·어떻게
1. 주체는 스프링 스케줄러 `Xpb98BatchScheduler`다.
   - `@Scheduled(cron = "0 0 */6 * * *")`이므로 **6시간마다**(00·06·12·18시 정각) 실행된다. (`global/config/Xpb98BatchScheduler.java:34`)
   - `updateShipmentStatusesJob`을 `JobLauncher`로 실행한다. 파라미터는 timestamp이고, 예외는 `printStackTrace`로만 처리한다. (`:36-43`)
2. Job은 `updateShipmentStatusesStep` 하나다. (`D/m12/config/Xqv91JobConfig.java:54-60`)
   - chunk 50 (`:51, :67`), reader→processor→writer 구성이다.
   - 스텝 시작 시 `Xmb36Listener.beforeStep`에서 Playwright 브라우저를 열고, 종료 시 닫는다. (`:80`, `D/m12/config/Xmb36Listener.java:15-24`)
3. 조회 대상(reader): JPQL `SELECT s FROM Xhx14 s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL`. 즉 운송장이 등록된 배송 중·배송 출발 건이다. (`Xqv91JobConfig.java:87-97`)
   - `JpaPagingItemReader`이고 pageSize는 50이다. 처리하면서 상태가 DELIVERED로 바뀌어 조회 조건에서 빠지는 행이 있으면 다음 페이지에서 일부가 건너뛰어질 수 있다. 다음 주기에 다시 조회되므로 영구 누락은 아니다.
4. CJ대한통운 조회 페이지를 Playwright로 연다.
   - URL: `https://trace.cjlogistics.com/next/tracking.html?wblNo={운송장}` (`D/m12/config/Xth19Processor.java:24`)
   - `tbody#statusDetail tr`의 마지막 행 5번째 `td` 텍스트를 상태로 쓴다. (`Xth19Processor.java:25, :181`)

### 2-2. 실제로 실행되는 처리 코드 (비슷한 코드 구분)
| 후보 | 실제 실행 여부 | 근거 |
|---|---|---|
| `Xth19Processor.process` | **실행됨** | 스텝이 `new Xth19Processor(...)`를 processor로 등록 (`Xqv91JobConfig.java:69-73`). |
| `Xqv91JobConfig.shipmentItemProcessor()` 빈 | 미사용 | `@Bean`으로 정의만 있고(`:104-177`) 스텝에서 참조하지 않는다. |
| `Xqv91JobConfig.parseCjLogisticsStatus` | 미사용 | private이고 호출처가 없다 (`:186`). |
| `Xhx14CommandService.updateShipmentStatuses()` | 미사용 | 정의만 있고(`:308-391`) 호출처가 없다. 배치와 다른 로직이다. |
| `Xxx20.getCurrentTrackingStatus` | 배치에서는 미사용 | check-status API에서만 쓴다 (`Xhx14CommandService.java:477`). |

따라서 배치에서 실제 실행되는 것은 `Xth19Processor.process`(`Xth19Processor.java:57-146`)이고, 완료 처리는 `Xhx14CommandService.completeOrder`(`:191`) + `Xkh73CommandService.notifyShipmentCompleted`(`D/m15/service/command/Xkh73CommandService.java:219`)를 호출한다. (`Xth19Processor.java:116-117`)

### 2-3. 택배사 상태 문자열 → 내부 상태
`Xth19Processor.mapToShipmentStatus` (`Xth19Processor.java:220-225`)
- `"배송완료"` → `DELIVERED`
- `"배송출발"` → `OUT_FOR_DELIVERY`
- 그 외 모든 문자열 → `IN_TRANSIT`
- 텍스트는 `trim()` 후 정확히 일치해야 한다 (`:181`). 비어 있으면 `TRACKING_HTML_PARSE_ERROR` (`:183-188`).
- 현재 상태와 매핑 결과가 같으면 변경 없이 반환한다. (`:101-105`)
- 그 외 상태 전이는 `Xhx14.updateStatus`의 전이표를 따른다. (`Xhx14.java:47-55`, `Xpb98Status.java:16-33`)
  - 예: 현재 `OUT_FOR_DELIVERY`인데 CJ 문자열이 "배송완료"·"배송출발" 외 값이면 `IN_TRANSIT`으로 매핑된다. `OUT_FOR_DELIVERY → IN_TRANSIT`은 전이표에 없어 예외가 나고(`Xpb98Status.java:24-28`), `EXTERNAL_TRACKING_SERVICE_ERROR`로 감싸져 해당 건은 skip된다 (`Xth19Processor.java:133-145`).

## 3. 배송 완료 판정 이후 (배치 `Xth19Processor`)

### 3-1. 상태 변경 순서
1. 배송: `orderShipment.updateStatus(DELIVERED)`. `IN_TRANSIT → DELIVERED`, `OUT_FOR_DELIVERY → DELIVERED`가 모두 허용된다. (`Xth19Processor.java:113`, `Xpb98Status.java:16-33`)
2. `orderService.completeOrder(orderId)` (`Xth19Processor.java:116`, 본문 `Xhx14CommandService.java:191-229`):
   1. OrderBid를 `findByOrderId`로 조회한다. 없으면 IAE → 최종적으로 `ORDER_NOT_FOUND_FOR_SHIPMENT`로 감싸진다. (`:196-197`, `:221-228`)
   2. 주문: `order.updateStatus(COMPLETED)` (`:204`)
   3. `updateSaleStatusToSold(orderId)` (`:208`)
      - SaleBid가 있으면 판매 `SOLD`로 바꾼다. 창고 보관이면 창고 상태 SOLD로 바꾼다. 판매자 알림 1건 (`:116-138`)
      - OrderBid.sale 쪽은 이미 SOLD라 `canTransitionTo(SOLD)`가 false여서 건너뛴다 (`:156`, `D/m10/entity/Xgg74Status.java:15-24`). 같은 판매자 알림이 두 번 가지 않는다.
   4. 구매자 알림 1건: "[completeOrder] 주문이 완료 처리되었습니다. 주문 ID: …" (`:211-217`)
3. `notifyShipmentCompleted(order)`: 구매자 알림 1건 "[배송 완료] 상품이 배송 완료되었습니다. 주문 ID: …" (`Xkh73CommandService.java:219-229`)
   - 예외는 내부에서 삼킨다 (`:230-233`).
4. 처리 후 `JpaItemWriter`가 배송을 저장한다. (`Xqv91JobConfig.java:74, :239-246`)

### 3-2. 알림 (성공 시)
- 구매자: **2건**. `[completeOrder] …`와 `[배송 완료] …`, 둘 다 SHOPPING/BID 타입이다.
- 판매자: **1건**. "상품이 성공적으로 판매 완료되었습니다. 판매 ID: …" (SaleBid가 있고 판매 상태가 SOLD로 전이 가능할 때)

### 3-3. 주문 입찰·판매 입찰 상태
- **변하지 않는다.** OrderBid·SaleBid를 `COMPLETED`로 바꾸는 `updateOrderAndSaleBidStatusToCompleted`는 `updateTrackingInfo`에서만 호출된다 (`Xhx14CommandService.java:289`). `completeOrder`와 배치 경로에는 없다.
- 즉시 구매 주문은 생성 시 둘 다 `MATCHED`이고 (`D/m16/service/command/Xzj27CommandService.java:192-196`, `D/m16/service/command/Xdg64CommandService.java:279-280`) 배송 완료 후에도 `MATCHED`로 남는다.
- 바뀌는 것은 주문 `COMPLETED`, 배송 `DELIVERED`, 판매(Xgg74) `SOLD`(가능한 경우)와 창고 상태다.

## 4. 주문 종류별 차이

### (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문 → 끝까지 진행되지 않는다
- 주문 상태는 `PREPARING`이다. (`Xdg64CommandService.java:175-177`)
- 배송이 이미 `IN_TRANSIT`+운송장이 있다고 가정해도(예: check-status API 경유, 1-4 참고) 다음에서 막힌다.
  1. 배치가 배송을 `DELIVERED`로 바꾼다 (`Xth19Processor.java:113`).
  2. `completeOrder`의 `order.updateStatus(COMPLETED)` (`Xhx14CommandService.java:204`)에서 `PREPARING → COMPLETED`가 허용되지 않아 `Xxc76StatusException`이 난다 (`Xdg64Status.java:159`, `Xdg64.java:113-121`).
  3. `completeOrder`가 이를 `Xpb98Exception(ORDER_NOT_FOUND_FOR_SHIPMENT)`로 바꿔 던진다 (`Xhx14CommandService.java:221-228`).
  4. 프로세서 예외 → skip 대상이 된다. 구매자·판매자 알림은 0건이고 입찰·판매 상태 변경도 없다. 배송은 `IN_TRANSIT`으로 남아 6시간 뒤 다시 조회·실패한다. (5번 참고)
- 이 주문에는 SaleBid가 없는 경우도 많다. SaleBid는 판매자가 즉시 판매(`createInstantSaleBid`)로 응했을 때만 order와 연결된다 (`D/m10/service/command/Xzz58CommandService.java:72-84`). 그 경우에도 위 `COMPLETED` 전이 단계에서 이미 실패한다.

### (b) 즉시 구매로 만들어진 주문 → 배치의 완료 처리가 끝까지 진행된다
- 생성: `createInstantOrder`는 주문을 `PENDING_PAYMENT`로 만들고 상태를 더 바꾸지 않는다. (`Xdg64CommandService.java:241-245`, 메서드 `:220-319`)
  - 배송은 `PENDING`으로 생성된다. (`Xhx14CommandService.java:67`)
  - SaleBid는 order에 연결되어 `MATCHED`가 된다 (`Xdg64CommandService.java:279-280`). OrderBid는 `MATCHED`이고 `sale`과 `order`가 모두 연결된다 (`Xzj27CommandService.java:189-206`).
- 전이표상 `PENDING_PAYMENT → COMPLETED`가 허용된다. (`Xdg64Status.java:157`)
- 따라서 배송이 IN_TRANSIT/OUT_FOR_DELIVERY이고 운송장이 있다면 `completeOrder`의 각 단계가 모두 통과한다 (SaleBid 있음, OrderBid 있음). 결과는 3-1~3-3과 같다.
  - 주문 `COMPLETED`, 판매 `SOLD`(판매 상태가 `ON_AUCTION`/`SELLING`일 때만, `Xgg74Status.java:20-21`)
  - 구매자 알림 2건, 판매자 알림 1건
  - OrderBid·SaleBid는 `MATCHED` 그대로
- 단, 판매가 `SELLING`/`ON_AUCTION`이 아니면 SOLD 전이와 판매자 알림은 조용히 건너뛴다 (`:119, :142-144`).
- 창고 보관 판매이고 창고 상태 전이가 막히면 `completeOrder`가 실패해 전체가 롤백된다. (`D/m07/service/command/Xnn94CommandService.java:150-176`)
- (b)가 운송장 등록 단계에 도달하는 경로는 제한적이다.
  - `PATCH …/status`는 `PENDING_PAYMENT → IN_TRANSIT`이 허용되지 않아 1-3과 같이 404/S001로 실패한다.
  - 운송장 등록과 IN_TRANSIT 전이는 `check-status` API(1-4)로만 가능하다.

## 5. 실패 처리 (주기 처리 중 한 건 실패)
1. 실패 건 처리
   - `Xth19Processor.process`의 모든 예외는 `Xpb98Exception`으로 통일되어 던져진다. (`Xth19Processor.java:133-145`)
   - 스텝은 `faultTolerant().skip(Exception.class).skipLimit(50)`이므로 해당 건은 **skip**된다. (`Xqv91JobConfig.java:75-77`)
   - `SkipListener.onSkipInProcess`가 shipmentId·운송장·상태·사유를 error 로그로 남긴다. (`:252-266`)
   - skip된 건은 writer에 가지 않는다. 그 건의 DB 변경(배송 `DELIVERED` 대입, 주문 변경 등)은 청크 롤백으로 사라진다.
   - 상태는 `IN_TRANSIT`/`OUT_FOR_DELIVERY`로 남아 다음 6시간 주기에 다시 대상이 된다. 운송장 번호가 비어 있는 건은 reader 조건상 애초에 제외된다 (`:95`).
2. 나머지 건
   - 프로세서에서 예외가 나면 Spring Batch가 해당 청크 트랜잭션을 롤백하고, 청크 내 항목을 하나씩 다시 처리한다. 성공한 항목은 각각 커밋되고 실패 항목만 skip된다. 다른 건은 영향을 받지 않고 계속 진행된다.
   - 다시 처리하는 동안 같은 운송장을 Playwright로 한 번 더 조회한다.
   - `completeOrder`·`notifyShipmentCompleted` 안의 알림은 같은 트랜잭션이라 롤백된다. 다만 `createNotification`이 롤백 전에 WebSocket으로 실시간 푸시를 이미 보냈을 수 있다 (`Xkh73CommandService.java:57`). 푸시는 롤백되지 않는다.
3. 한도 초과
   - skip이 50건을 넘으면 `SkipLimitExceededException`으로 스텝이 실패하고 남은 건은 그 주기에 처리되지 않는다.
   - 스케줄러는 예외를 `printStackTrace`로만 처리한다 (`Xpb98BatchScheduler.java:41-43`).
4. 알림 생성 실패
   - `notifyShipmentCompleted`만 예외를 내부에서 삼키므로 건 실패로 번지지 않는다 (`Xkh73CommandService.java:230-233`).
   - 반면 `completeOrder` 안의 `createNotification` 예외는 `completeOrder`의 `catch (Exception)`에서 `Xpb98Exception`으로 바뀌어 건 실패가 된다 (`Xhx14CommandService.java:221-228`).
5. (참고) 사용되지 않는 `updateShipmentStatuses()`는 건별 try/catch로 계속 진행하는 구조지만 (`Xhx14CommandService.java:322-388`) 어디서도 호출되지 않는다.
