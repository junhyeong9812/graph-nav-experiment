# 구매자 배송: 운송장 등록 → 배송 완료

경로 약어: `D` = `src/main/java/com/fream/back/domain`, `G` = `src/main/java/com/fream/back/global`.
이름은 CLAUDE.md 대응표를 따른다 (m12=shipment, m16=order, m10=sale, m15=notification).
클래스: Xhx14=구매자 배송(OrderShipment), Xdg64=주문, Xzj27=주문 입찰, Xzz58=판매 입찰, Xgg74=판매, Xpb98Status=배송 상태.

**결론 요약**
- 운송장 등록 API는 일반 구매 입찰 주문(실배송, 결제·배송 처리 후 주문 상태 `PREPARING`)에서 항상 실패한다. 주문을 `IN_TRANSIT`으로 바꾸는 순간 예외가 나고, 트랜잭션이 롤백되어 아무것도 저장되지 않는다.
- 배송 완료 감지는 Spring Batch 잡이 6시간마다 돈다. 실제 처리 코드는 `Xth19Processor`다.
- 완료 처리 코드(`completeOrder`)는 (a) 일반 주문에서는 `PREPARING → COMPLETED` 전환 불가로 실패하고, (b) 즉시 구매 주문에서는 `PENDING_PAYMENT → COMPLETED`가 허용되어 끝까지 진행된다.
- 다만 (b)는 운송장 등록 API가 `PENDING_PAYMENT → IN_TRANSIT` 전환 불가로 막혀, 배치 대상(`IN_TRANSIT`/`OUT_FOR_DELIVERY`)에 들어갈 길이 코드상 없다.

## 1. 운송장 등록 요청

### 1-1. 진입 API
1. `PATCH /shipments/order/{shipmentId}/status`, 본문 `{courier, trackingNumber}`.
   - 근거: `D/m12/controller/command/Xhx14CommandController.java:20` (`@RequestMapping("/shipments/order")`), `:33-49` (`@PatchMapping("/{shipmentId}/status")` → `updateTrackingInfo`).
   - 요청 DTO: `D/m12/dto/Xhx14RequestDto.java:11-12`.
2. 컨트롤러는 `Xhx14CommandService.updateTrackingInfo(shipmentId, courier, trackingNumber)`를 호출한다 (`Xhx14CommandController.java:41-45`).
   - 메서드 이름은 "tracking info 업데이트"지만 실제로는 주문·판매·입찰·알림까지 처리한다.

### 1-2. 코드가 의도한 상태 변경 순서와 알림
`D/m12/service/command/Xhx14CommandService.java:238-303` (`@Transactional`).

1. courier/trackingNumber가 null이거나 blank면 `TRACKING_INFO_REQUIRED`(400)를 던진다 (`:243-246`).
2. 배송 조회: `findById`, 없으면 `SHIPMENT_NOT_FOUND` (`:249-254`).
3. **배송(Xhx14)**: `shipment.updateTrackingInfo(...)`가 courier, trackingNumber를 세팅하고 상태를 `IN_TRANSIT`으로 직접 대입한다 (`:256`, `D/m12/entity/Xhx14.java:41-45`).
   - `updateStatus()`의 전이 검사를 거치지 않는다. enum상 `PENDING → IN_TRANSIT`은 불가능하다 (`D/m12/entity/Xpb98Status.java:4-9`).
4. **주문(Xdg64)**: `order.updateStatus(Xdg64Status.IN_TRANSIT)` (`:259-260`).
5. **구매자 알림 1**: "상품이 출발하였습니다. 주문 ID: …" (`:265-271`).
6. `updateSaleStatusToSold(orderId)` (`:276`, 정의 `:111-183`):
   - 판매 입찰(Xzz58) 기준으로 판매(Xgg74)를 `SOLD`로 바꾸고, 창고 보관이면 창고 상태도 바꾼다 (`:116-130`).
   - **판매자 알림**: "상품이 성공적으로 판매 완료되었습니다. 판매 ID: …" (`:132-138`).
   - 주문 입찰(Xzj27) 기준으로 한 번 더 `SOLD` 시도와 판매자 알림 (`:150-176`).
7. 창고 보관이면 `updateWarehouseStatusToSold`를 한 번 더 호출한다 (`:279-286`).
8. `updateOrderAndSaleBidStatusToCompleted(orderId)`: `MATCHED`인 주문 입찰과 판매 입찰을 `COMPLETED`로 바꾼다 (`:289`, 정의 `:412-440`).
   - 이 메서드는 `private`인데 `@Transactional`이 붙어 있어 프록시 기준으로는 의미가 없다. 예외는 내부에서 삼킨다 (`:436-438`).

즉 의도는 "배송 `IN_TRANSIT` → 주문 `IN_TRANSIT` → 판매 `SOLD` → 입찰 `COMPLETED`"이고, 알림은 구매자에게 1건, 판매자에게 최대 2건이다.
운송장 등록만으로 판매·입찰을 완료 처리한다는 점이 이름/의도와 어긋난다. 이 코드가 실행되는 배송 완료 시점은 아니다.

### 1-3. 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문에서는 끝까지 성공하는가? → 실패한다
**(a) 주문이 이 시점에 `PREPARING` 상태다.**
- 일반 구매 입찰 주문은 `Xdg64CommandService.createOrderFromBid`에서 `PENDING_PAYMENT`로 만들어진다 (`D/m16/service/command/Xdg64CommandService.java:76-82`).
- `processPaymentAndShipment`가 배송 정보를 만들고 (`:148`) 창고 보관이 아닌 실배송이면 `PAYMENT_COMPLETED → PREPARING`까지만 올린다 (`:174-177`).
- 창고 보관이면 `IN_WAREHOUSE → COMPLETED`다 (`:163-172`).
- Kafka 경로도 동일하게 실배송이면 `PREPARING`에서 멈춘다 (`D/m16/service/kafka/Xdg64EventConsumer.java:195-219`).
- 이 흐름 어디에도 `SHIPMENT_STARTED`로 올리는 코드가 없다 (`grep Xdg64Status.SHIPMENT_STARTED`는 enum 정의뿐).

**(b) `PREPARING → IN_TRANSIT`은 허용되지 않는다.**
- `PREPARING`의 허용 다음 상태는 `IN_WAREHOUSE`, `SHIPMENT_STARTED`뿐이다 (`D/m16/entity/Xdg64Status.java:26`).
- `IN_TRANSIT`은 `SHIPMENT_STARTED`에서만 갈 수 있다 (`Xdg64Status.java:28`).
- `Xdg64.updateStatus`는 불가능한 전이에 `Xxc76StatusException`을 던진다 (`D/m16/entity/Xdg64.java:113-120`).

**(c) 실패 지점과 응답**
- 실패 지점: `Xhx14CommandService.java:260` (`order.updateStatus(IN_TRANSIT)`).
- 이 예외는 `Xpb98Exception`이 아니므로 `catch (Exception e)`(`:295`)에 걸린다. 여기서 `Xpb98Exception(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")`로 감싸 던진다 (`:297-301`).
- 응답: `Xks43ExceptionHandler`가 `errorCode`의 코드/메시지/상태로 응답한다 (`G/exception/Xks43ExceptionHandler.java:49-62`).
  - HTTP **404**, 코드 `S001`, 메시지 "배송 정보를 찾을 수 없습니다." (`D/m12/exception/Xpb98ErrorCode.java:12`).
  - 실제 원인(상태 전환 불가)은 응답 본문에 나오지 않고 로그에만 남는다.
- **저장되는 것: 없다.**
  - 3단계의 courier/trackingNumber/`IN_TRANSIT` 변경은 영속 엔티티에 대한 메모리상 변경일 뿐이다.
  - `RuntimeException`이 `@Transactional` 경계를 넘어가므로 롤백된다.
  - 알림(5단계)과 판매/입찰 변경(6~8단계)은 4단계에서 터졌기 때문에 실행되지 않는다.
  - 결과적으로 배송은 `PENDING`이고 운송장 번호도 비어 있다.
- 따라서 이 API로는 배치 대상 상태(`IN_TRANSIT`)인 배송이 생기지 않는다.

## 2. 배송 완료 감지

### 2-1. 누가, 언제, 어떻게
- **주체**: 스케줄러 `Xpb98BatchScheduler`가 Spring Batch 잡 `updateShipmentStatusesJob`을 실행한다.
  - `@Scheduled(cron = "0 0 */6 * * *")` → **6시간마다** (00, 06, 12, 18시 정각), `G/config/Xpb98BatchScheduler.java:34-40`.
  - 매번 `timestamp` 잡 파라미터를 달리해 실행한다 (`:37-40`). 예외는 `printStackTrace()`로만 처리한다 (`:41-43`).
- **잡 구성**: `D/m12/config/Xqv91JobConfig.java:54-60` (잡), `:62-82` (스텝).
  - 청크 크기 50, 스킵 한도 50 (`:51-52`).
  - reader → processor → `JpaItemWriter` (`:68-74`).
  - `faultTolerant().skip(Exception.class).skipLimit(50)` (`:75-77`).
  - 스텝 시작/종료 시 `Xmb36Listener`가 Playwright 브라우저를 열고 닫는다 (`:80`, `D/m12/config/Xmb36Listener.java:15-24`).

### 2-2. 조회 대상
- reader JPQL: `SELECT s FROM Xhx14 s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL` (`Xqv91JobConfig.java:95`). 페이지 크기는 50 (`:94`).
- 즉 **구매자 배송(Xhx14)만** 대상이다. `PENDING`, `SHIPPED`, `DELAYED` 등은 제외된다.
- 판매자 배송(Xxn30)은 대상이 아니다.

### 2-3. 실제로 실행되는 처리 코드
비슷한 코드가 네 곳에 있다.

| 후보 | 위치 | 실제 실행 여부 |
|---|---|---|
| `Xth19Processor.process` | `D/m12/config/Xth19Processor.java:56-157` | **실행됨**. `.processor(new Xth19Processor(...))` (`Xqv91JobConfig.java:69-73`) |
| `shipmentItemProcessor` 빈 | `Xqv91JobConfig.java:104-177` | 빈으로만 있고 스텝에 연결되지 않아 실행되지 않음 |
| `Xhx14CommandService.updateShipmentStatuses` | `Xhx14CommandService.java:308-391` | 호출하는 곳이 없음 (스케줄·컨트롤러 어디에서도 안 부름) |
| `updateAndCheckShipmentStatus` | `Xhx14CommandService.java:451-516` | 서비스에는 있으나 구매자 배송 컨트롤러에서 호출하지 않음 |

- `Xth19Processor`는 `Xqv91JobConfig`의 `shipmentItemProcessor`와 `updateShipmentStatuses`가 쓰는 `Xxx20` 대신 자기 브라우저 매니저(`Xrk74`)와 Jsoup 파싱을 쓴다 (`Xth19Processor.java:72-95`).
- 처리 순서(`Xth19Processor.java:101-126`):
  1. 새 상태가 현재 상태와 같으면 변경 없이 반환한다 (`:101-105`).
  2. `DELIVERED`: `orderShipment.updateStatus(DELIVERED)` → `orderService.completeOrder(orderId)` → `notificationService.notifyShipmentCompleted(order)` (`:108-117`).
  3. `OUT_FOR_DELIVERY`: `updateStatus(OUT_FOR_DELIVERY)` (`:119-121`).
  4. 그 외: `updateStatus(IN_TRANSIT)` (`:123-126`).
- 처리된 `Xhx14`는 `JpaItemWriter`가 저장한다 (`Xqv91JobConfig.java:241-245`).

### 2-4. 택배사 상태 문자열 → 내부 상태
- 조회: CJ대한통운 `https://trace.cjlogistics.com/next/tracking.html?wblNo=<운송장>`, 마지막 `tbody#statusDetail tr` 행의 5번째 `td` 텍스트를 쓴다 (`Xth19Processor.java:28-29, 81-87, 167-181`).
- 매핑 `mapToShipmentStatus` (`Xth19Processor.java:220-226`):
  - `"배송완료"` → `DELIVERED`
  - `"배송출발"` → `OUT_FOR_DELIVERY`
  - 그 외 모든 문자열 → `IN_TRANSIT`
- 주의: 공백 제거(`trim`)만 하고 완전 일치로 비교한다. "집화처리", "배송 완료" 같은 문자열은 모두 `IN_TRANSIT`이 된다.
- 택배사는 `courier` 값과 상관없이 항상 CJ로 조회한다 (URL이 고정).

## 3. 배송 완료 판정 이후

`Xth19Processor.java:108-117`에서 `DELIVERED`로 판정된 경우다.

### 3-1. 상태 변경 순서
1. **배송 Xhx14**: `IN_TRANSIT`/`OUT_FOR_DELIVERY` → `DELIVERED` (`Xth19Processor.java:113`; 전이 허용은 `Xpb98Status.java:16-21, 23-27`).
2. `Xhx14CommandService.completeOrder(orderId)` (`Xhx14CommandService.java:190-229`, `@Transactional`):
   1. `orderBidQueryService.findByOrderId`로 주문 입찰 조회, 없으면 `IllegalArgumentException` (`:196-197`).
   2. **주문 Xdg64**: `order.updateStatus(COMPLETED)` (`:204`).
   3. `updateSaleStatusToSold(orderId)` (`:208`):
      - 판매 입찰을 `findByOrderId`로 조회한다. 이 메서드는 없으면 null이 아니라 `IllegalArgumentException`을 던진다 (`D/m10/service/query/Xzz58QueryService.java:26-29`).
      - 판매 Xgg74가 `SELLING`/`ON_AUCTION`이면 `SOLD`로 바꾼다 (`Xhx14CommandService.java:116-123`; 허용 전이 `D/m10/entity/Xgg74Status.java:19-21`).
      - 창고 보관 판매면 창고 상태를 `SOLD`로 바꾼다 (`:126-129`).
      - 이후 주문 입찰 기준의 두 번째 블록(`:150-176`)은 이미 `SOLD`라 전이가 불가(`Xgg74Status.java:22`)해 건너뛴다.
3. `notifyShipmentCompleted(order)` (`Xth19Processor.java:117`; 구현 `D/m15/service/command/Xkh73CommandService.java:219-234`). 실패해도 예외를 삼킨다 (`:230-233`).

### 3-2. 알림 (정상 진행 시)
| # | 수신자 | 내용 | 근거 |
|---|---|---|---|
| 1 | 판매자 | "상품이 성공적으로 판매 완료되었습니다. 판매 ID: …" | `Xhx14CommandService.java:132-138` |
| 2 | 구매자 | "[completeOrder] 주문이 완료 처리되었습니다. 주문 ID: …" | `Xhx14CommandService.java:211-217` |
| 3 | 구매자 | "[배송 완료] 상품이 배송 완료되었습니다. 주문 ID: …" | `Xkh73CommandService.java:224-229` |

- 총 **3건**: 구매자 2건, 판매자 1건.
- 판매자 알림은 판매가 `SELLING`/`ON_AUCTION`이어서 `SOLD` 전이가 가능한 경우에만 생긴다 (`Xhx14CommandService.java:119`).
- 구매자에게 "완료"에 가까운 알림이 두 번 가는 점은 의도치 않은 중복이다.

### 3-3. 주문 입찰·판매 입찰 상태
- 배송 완료 경로(`completeOrder`)는 주문 입찰(Xzj27)과 판매 입찰(Xzz58)의 상태를 **바꾸지 않는다**. `MATCHED` 그대로다.
  - 입찰을 `COMPLETED`로 바꾸는 코드(`updateOrderAndSaleBidStatusToCompleted`, `Xhx14CommandService.java:412-440`)는 `updateTrackingInfo`(`:289`)에서만 호출된다.
  - 그런데 `updateTrackingInfo`는 1-3에서 본 대로 일반 주문에서 실패하고 즉시 구매 주문도 막힌다 (4번 참고). 사실상 실행되지 않는 경로다.
- 판매(Xgg74)는 `SOLD`가 된다.

## 4. 주문 종류별 차이

### (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문 → 끝까지 진행되지 않는다
- 주문 상태는 `PREPARING`이다 (`Xdg64CommandService.java:174-177`).
- `completeOrder`의 `order.updateStatus(COMPLETED)`가 `PREPARING → COMPLETED` 불가로 `Xxc76StatusException`을 던진다 (`Xhx14CommandService.java:204`; `Xdg64Status.java:26`; `Xdg64.java:113-120`).
- `completeOrder`의 `catch (Exception e)`가 `Xpb98Exception(ORDER_NOT_FOUND_FOR_SHIPMENT)`로 감싸 던진다 (`:221-228`).
- 프로세서가 그대로 다시 던진다 (`Xth19Processor.java:138-145`).
- 결과:
  - 배치가 이 건을 skip 처리한다 (`Xqv91JobConfig.java:76-78`, 로그 `:255-265`).
  - 주문은 `COMPLETED`가 되지 않는다.
  - 판매 `SOLD` 처리, 판매자 알림, 구매자 알림이 모두 나가지 않는다.
  - 배송의 `DELIVERED` 변경은 같은 청크 트랜잭션이 롤백되어 저장되지 않는다. 배송은 `IN_TRANSIT`으로 남고, 6시간 뒤 다시 조회되어 같은 실패를 반복한다.
- 실제로는 1-3에서 본 대로 이런 배송이 `IN_TRANSIT`에 들어갈 수 없다 (운송장 등록 API가 실패). 이 결과는 어떤 경로로든 `IN_TRANSIT` 배송이 있다고 가정했을 때다.

### (b) 즉시 구매로 만들어진 주문 → 처리 코드는 끝까지 진행된다
- 주문 상태는 `PENDING_PAYMENT`다. `createInstantOrder`는 주문을 `PENDING_PAYMENT`로 만들고 (`Xdg64CommandService.java:241-245`), 결제 처리(`:305`)나 이후 코드에서 주문 상태를 올리지 않는다. 결제 서비스에도 `order.updateStatus` 호출이 없다.
- 배송 정보는 `PENDING`으로 생성된다 (`:264`, `Xhx14CommandService.java:67`).
- 주문 입찰은 `createInstantOrderBid`에서 `MATCHED`, `sale` 연결, `isInstantPurchase=true`로 만들어진다 (`D/m16/service/command/Xzj27CommandService.java:189-206`).
- 판매 입찰도 `saleBid.assignOrder(order)` 후 `MATCHED`다 (`Xdg64CommandService.java:279-280`).
- 따라서 `completeOrder` 안에서:
  - `PENDING_PAYMENT → COMPLETED`가 허용된다 (`Xdg64Status.java:24`).
  - 판매 입찰이 존재해 `findByOrderId`가 성공한다.
  - 판매가 `SELLING`/`ON_AUCTION`이면 `SOLD`가 되고 판매자 알림이 간다.
  - 구매자 알림 2건이 간다.
  - 알림 총 3건이다.
- 입찰 상태는 `MATCHED` 그대로다 (3-3).
- 단, 판매 상태가 `SELLING`/`ON_AUCTION`이 아니면(예: `IN_STORAGE`) 판매는 `SOLD`가 되지 않고 판매자 알림도 없다 (`Xgg74Status.java:19-21`).
- 도달 가능성: 이 배송을 `IN_TRANSIT`으로 만드는 수단이 코드에 없다.
  - 운송장 등록 API는 `order.updateStatus(IN_TRANSIT)`에서 `PENDING_PAYMENT → IN_TRANSIT` 불가로 실패한다 (`Xhx14CommandService.java:260`; `Xdg64Status.java:24`).
  - 배송이 `PENDING`이면 reader 조건에 맞지 않아 배치가 건드리지 않는다.
  - 즉 (b)의 3번 처리는 "코드 자체는 끝까지 간다"이지만 정상 흐름에서는 호출되지 않는다.

## 5. 실패 처리 (주기 처리 중 한 건 실패)

실제로 실행되는 경로는 Spring Batch 스텝이다 (`Xqv91JobConfig.java:66-81`).
- 프로세서에서 예외가 나면 `Xth19Processor`가 `Xpb98Exception`으로 통일해 던진다 (`Xth19Processor.java:133-145`).
  - 운송장이 비면 `TRACKING_NUMBER_INVALID` (`:61-64`).
  - 브라우저 페이지 생성 실패는 `BROWSER_INITIALIZATION_ERROR` (`:72-75`).
  - 조회 실패나 파싱 실패는 `TRACKING_HTML_PARSE_ERROR` 또는 `EXTERNAL_TRACKING_SERVICE_ERROR`.
- `faultTolerant().skip(Exception.class).skipLimit(50)`이므로 그 건은 **skip**되고 나머지 건은 계속 처리된다 (`Xqv91JobConfig.java:75-77`).
  - skip 시 `shipmentSkipListener.onSkipInProcess`가 에러 로그를 남긴다 (`:251-266`).
  - Spring Batch의 fault-tolerant 청크는 실패 시 청크 전체를 롤백한다. 그 뒤 아이템을 하나씩 다시 처리하며 문제 건만 건너뛴다.
  - 같은 청크의 다른 건은 재처리 후 정상 저장된다.
- 실패한 건의 변경분(배송 `DELIVERED`, 주문 `COMPLETED`)은 롤백되어 저장되지 않고, 상태가 `IN_TRANSIT`/`OUT_FOR_DELIVERY`로 남아 다음 주기(6시간 뒤)에 다시 대상이 된다.
- **한도**: skip이 50건을 넘으면 스텝이 실패한다 (`:77`). 그러면 남은 건은 그 주기에서 처리되지 않는다. 스케줄러는 예외를 `printStackTrace()`로만 처리한다 (`Xpb98BatchScheduler.java:41-43`).
- (참고) 실행되지 않는 `updateShipmentStatuses`는 건별 try/catch로 로그만 남기고 계속 진행하는 구조다 (`Xhx14CommandService.java:322-387`). 다만 호출처가 없다.
