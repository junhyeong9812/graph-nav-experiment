# 즉시 구매 처리 흐름 분석

경로 약어: `D` = `src/main/java/com/fream/back/domain`

## 핵심 요약

- 즉시 구매는 **전부 동기 처리**이며 Kafka 비동기 주문 처리 파이프라인(`order-processing-topic`)을 타지 않는다.
- 응답 ID는 **주문(Order, Xdg64)의 ID**다. 주문 입찰(OrderBid) ID가 아니다.
- 주문은 끝까지 **PENDING_PAYMENT** 상태로 남는다. "결제 완료/준비중/창고 입고/완료"로 바뀌는 코드는 즉시 구매 경로에 없다.
- 결제 대행사가 카드 결제를 "실패"로 응답해도(HTTP 200, code 0, status≠success) 예외가 없어서 즉시 구매가 **성공 응답**으로 끝난다.

5. **동기/비동기**
   - 즉시 구매 경로에서 Kafka 프로듀서(`Xdg64EventProducer`)를 호출하는 곳은 없다. 프로듀서는 `D/m16/controller/command/Xdg64CommandController.java:54`(일반 `process-payment-shipment`, 202 Accepted)에서만 쓰인다.
   - 즉시 구매는 요청 스레드에서 DB 저장, PortOne 호출, 알림까지 모두 끝낸 뒤 200 OK로 응답한다.
   - 즉시 구매 경로는 Kafka 컨슈머(`D/m16/service/kafka/Xdg64EventConsumer.java:55-110`)와 상태 전환 로직(`:166-230`)을 거치지 않는다.
6. **응답 ID**
   - 컨트롤러 변수명이 `orderId`다: `Xzj27CommandController.java:101`.
   - 서비스가 반환하는 객체는 `Xzj27`(OrderBid)이고(`Xzj27CommandService.java:119`, `:142`), 컨트롤러는 그 객체의 `getId()`를 `orderId` 변수에 담는다(`Xzj27CommandController.java:101-107`). 주문의 `getOrder().getId()`가 아니다.
   - 따라서 **응답으로 돌려주는 ID의 실제 값은 주문 입찰(OrderBid, Xzj27)의 ID**다. 변수명과 응답 메시지는 주문 ID처럼 보이지만 실제 동작은 OrderBid ID다.

## 3. 결제 수단별 결과

결제 분기: `Xbf54CommandService.java:67-80`(`getResolvedPaymentType()`으로 CARD/ACCOUNT/GENERAL 분기, 판정은 `D/m06/dto/Xbf54RequestDto.java:74-87`). 결제 상태 기본값은 `PENDING`, `isSuccess` 기본값은 false(`D/m06/entity/Xbf54.java:39`, `:44`).

| 수단 | 처리 | 결제 직후 Payment 상태 | 근거 |
|---|---|---|---|
| 카드 | 저장된 결제 정보로 PortOne API 호출(`processCardPayment`). 응답의 `status`가 `"success"`일 때만 PAID로 변경 | 성공 응답: `PAID`, isSuccess=true. 그 외: `PENDING`, isSuccess=false | `Xbf54CommandService.java:157-225`, 호출 `:179`, 분기 `:203-206`, 저장 `:208` |
| 계좌이체 | 은행명 검증 후 저장. 외부 호출 없음 | 항상 `PENDING` (입금 확인 로직 없음) | `Xbf54CommandService.java:236-262`, `:260` |
| 일반 결제 | impUid만 확인하고 저장. PortOne 재검증 없음 | 항상 `PAID`, isSuccess=true | `Xbf54CommandService.java:290-316`, `:297-300`, `:313-314` |

### 즉시 구매가 끝까지 성공하는가

- 결제 수단과 관계없이 `processPayment`가 예외를 던지지 않으면 이후 단계(판매 SOLD, 알림, OrderBid MATCHED)가 그대로 진행되고 200 응답이 나간다.
- `createInstantOrder`는 `processPayment`의 반환값(`isSuccess`)을 검사하지 않는다(`Xdg64CommandService.java:305`는 반환값을 버린다).
- 즉 계좌이체(PENDING)와 카드 실패 응답(PENDING)도 "즉시 구매가 성공적으로 처리되었습니다."로 응답된다(`Xzj27CommandController.java:109`).
- 어느 경우에도 주문은 `PENDING_PAYMENT`로 남고, 판매·판매입찰·주문입찰은 이미 SOLD/MATCHED로 바뀐다. "끝까지 성공"은 상태가 완료로 이어진다는 뜻이 아니라 예외 없이 응답이 나간다는 뜻이다.

### 결제 대행사가 카드 결제를 실패로 응답하면

실패 응답 형태에 따라 두 갈래다.

1. **PortOne이 결제 API 자체의 실패 코드를 응답(HTTP≠200 또는 body.code≠0)**
   - `Xdf64Exception` 발생: `D/m06/p05/Xxv33ApiClient.java:270-275`.
   - `Xbf54Exception` 하위 클래스라 그대로 재던져진다(`Xxv33ApiClient.java:286-287`, `Xbf54CommandService.java:180-181`, `:218-219`, `:89-94`).
   - `createInstantOrder`가 `Xqj91Exception`으로 감싸고(`Xdg64CommandService.java:306-309`) `Xdg64Exception`이므로 그대로 위로 전파된다(`:313-315`, `Xzj27CommandService.java:146`, `:151-156`).
   - `@Transactional` 안의 RuntimeException이므로 주문·주문 항목·배송·판매 입찰 매칭 변경이 모두 롤백되고, 클라이언트는 오류 응답을 받는다.
2. **PortOne이 code=0으로 응답하되 결제 내용 status가 "success"가 아님(카드 승인 거절 등)**
   - 예외가 없다. `"success".equals(response.get("status"))` 조건만 거짓이므로 결제 상태 변경을 건너뛴다(`Xbf54CommandService.java:203-206`).
   - Payment는 `PENDING`/isSuccess=false로 저장된다(`:187-208`, 기본값 `Xbf54.java:39`, `:44`).
   - 이어서 알림과 판매 `SOLD` 처리가 실행된다(`Xbf54CommandService.java:83`, `:404`).
   - 응답은 성공이다. 주문은 `PENDING_PAYMENT`, 결제는 `PENDING`, 판매는 `SOLD`, 판매 입찰·주문 입찰은 `MATCHED`가 되어 상태가 서로 어긋난다.
   - 자동 환불·롤백 코드는 이 경로에 없다. `handleRefundIfNecessary`(`Xbf54CommandService.java:341`)는 `processPayment`에서 호출되지 않는다.

## 4. 알림 수신자·시점·방식

- **수신자 (두 명)**
  - 구매자: "결제가 완료되었습니다. 주문 ID: …" — `Xbf54CommandService.java:437-443`
  - 판매자: "구매자가 결제를 완료하였습니다. 판매 ID: …" — `Xbf54CommandService.java:447-454`
  - 카테고리 `SHOPPING`, 타입 `BID`로 동일하다.
- **시점**
  - 결제 저장 직후, 같은 요청·같은 트랜잭션 안에서 동기적으로 보낸다. 호출 위치는 `Xbf54CommandService.java:83`(`notifyUsersAndUpdateSaleStatus`) → `:403`/`:416`(`sendNotifications`) → `:434-462`.
  - 결제 성공 여부와 무관하다. 결제가 `PENDING`이어도 "결제가 완료되었습니다" 알림이 나간다(`Xbf54CommandService.java:83`은 성공 여부를 검사하지 않음).
  - 알림 실패는 삼키고 경고 로그만 남긴다(`:457-461`, 상위 `:421-425`).
- **방식**
  1. DB 저장: `Xkh73CommandService.java:52-53`.
  2. 실시간 WebSocket 전송: `convertAndSendToUser(email, "/queue/notifications", dto)` — `Xkh73CommandService.java:307-313`.
     - Redis에 `WebSocket:Xrd81:{email}` 키가 있을 때(연결 중일 때)만 전송한다. 없으면 저장만 한다(`:304`, `:307`, `:320-322`).
  3. Kafka `notification-topic`이나 `/topic/order/{id}` 알림은 **즉시 구매 경로에서 발행되지 않는다**. 그 알림은 비동기 주문 컨슈머 경로(`Xdg64EventConsumer.java:287-329`)에만 있다.

## 5. 최종 주문 상태와 창고 보관 선택 시 차이

### 최종 주문 상태

- **`PENDING_PAYMENT`**. 즉시 구매 경로에서 주문 상태를 바꾸는 코드가 없다(2번 8항 참조). 시작값은 `Xdg64CommandService.java:244`이다.
- 결제가 `PAID`로 끝난 카드·일반 결제여도 주문 상태는 `PENDING_PAYMENT`다. `PAYMENT_COMPLETED`, `PREPARING`, `IN_WAREHOUSE`, `COMPLETED`로의 전환 호출이 없다.
- 주석과 응답 메시지("즉시 구매가 성공적으로 처리되었습니다")가 완료를 암시하지만 실제 주문 상태는 결제 대기다.

### 구매자가 "창고 보관"을 선택한 경우

- **아무것도 달라지지 않는다.** 요청의 `warehouseStorage`는 컨트롤러가 서비스로 넘긴다(`Xzj27CommandController.java:104`, `Xzj27CommandService.java:119-120`, `:133-139`).
- `Xdg64CommandService.createInstantOrder`는 이 값을 파라미터로 받지만(`:220-221`) 메서드 본문에서 한 번도 사용하지 않는다.
- 창고 보관 주문 처리(`createOrderStorage` → PREPARING → IN_WAREHOUSE → COMPLETED)는 Kafka 컨슈머(`Xdg64EventConsumer.java:197-213`)와 `processPaymentAndShipment`(`Xdg64CommandService.java:163-172`)에만 있고, 즉시 구매는 두 경로를 쓰지 않는다.
- 창고 관련으로 실제 동작하는 것은 구매자의 선택이 아니라 **판매자 쪽 판매 물품의 `sale.isWarehouseStorage()`** 값이다. 이 값이 true이면 기존 창고 보관 건의 상태를 `ASSOCIATED_WITH_ORDER`로 바꾼다(`Xdg64CommandService.java:291-293`).
- 따라서 구매자가 창고 보관을 선택해도 주문 상태는 여전히 `PENDING_PAYMENT`이고, 구매자용 새 창고 보관(Xnn94)도 생성되지 않는다.
