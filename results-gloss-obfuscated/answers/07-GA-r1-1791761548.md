# 즉시 구매 처리 흐름

경로 접두어 `D` = `src/main/java/com/fream/back/domain`. 클래스 이름은 CLAUDE.md 코드 이름 그대로 쓴다.
(Xzj27 = OrderBid, Xzz58 = SaleBid, Xgg74 = Sale, Xdg64 = Order, Xbf54 = Payment, Xnn94 = WarehouseStorage, Xkh73 = Notification)

## 1. 진입 API, 처리 단계, 동기/비동기, 응답 ID

**API**: `POST /order-bids/instant`
- `D/m16/controller/command/Xzj27CommandController.java:22` (`@RequestMapping("/order-bids")`), `:89` (`@PostMapping("/instant")`), `:90` (`createInstantOrderBid`)
- 요청 본문은 `Xpj49RequestDto`: `saleBidId`, `addressId`, `warehouseStorage`, `paymentRequest` (`D/m16/dto/Xpj49RequestDto.java:143-152`)

**처리 단계** (모두 한 요청 스레드, 한 트랜잭션 안에서 순차 실행)
1. 컨트롤러가 로그인 이메일을 꺼내고(`Xzj27CommandController.java:92`), 결제 요청에 `userEmail=email`, `orderId=null`을 채운다(`:98`, `:119-123`).
2. `Xzj27CommandService.createInstantOrderBid`(`D/m16/service/command/Xzj27CommandService.java:118-149`, `@Transactional`)가 입력 검증(`:123`, `:154-167`) 후 구매자(`:126`)와 판매 입찰(`:129`, `:172-184`)을 조회한다.
3. `Xdg64CommandService.createInstantOrder`(`D/m16/service/command/Xdg64CommandService.java:219-319`)를 호출한다(`Xzj27CommandService.java:133`). 이 안에서 순서대로 다음을 한다.
   1. 배송지 조회: `addressQueryService.getAddress(buyer.getEmail(), addressId)` (`Xdg64CommandService.java:238`)
   2. Order 생성·저장, 상태 `PENDING_PAYMENT` (`:241-247`)
   3. 결제 요청에 `orderId` 세팅 (`:250`)
   4. OrderItem 생성 (`:255-256`)
   5. OrderShipment 생성 (`:264-271`)
   6. SaleBid를 Order에 연결하고 MATCHED 처리 후 flush (`:279-283`)
   7. 판매자가 창고 보관으로 올린 Sale이면 창고 상태를 `ASSOCIATED_WITH_ORDER`로 변경 (`:291-293`)
   8. 결제 처리 `paymentCommandService.processPayment` (`:305`) — 카드이면 PortOne 호출, 결제 후 알림 발송과 Sale `SOLD` 처리까지 포함 (아래 3, 4번 참고)
4. 돌아와서 OrderBid(Xzj27)를 생성한다 (`Xzj27CommandService.java:142`, `:189-207`). 상태는 `MATCHED`, 즉시구매 플래그는 `markAsInstantPurchase()`로 true가 된다 (`:196`, `:205`).

**동기/비동기**: 완전 동기다. 즉시 구매 경로에는 Kafka 발행이 없다. Kafka 프로듀서 `Xdg64EventProducer.sendOrderProcessingEvent`는 별도 일반 주문 컨트롤러에서만 호출된다 (`D/m16/controller/command/Xdg64CommandController.java:54`). `Xdg64EventConsumer`의 Kafka 처리(`D/m16/service/kafka/Xdg64EventConsumer.java:55-110`)와 `processPaymentAndShipment`(`Xdg64CommandService.java:111`)는 즉시 구매에서 호출되지 않는다. PortOne 카드 결제도 요청 스레드에서 `RestTemplate`으로 직접 호출한다 (`D/m06/p05/Xxv33ApiClient.java:266`).

**응답 ID**: 응답의 `Long`은 이름이 `orderId`지만 **OrderBid(Xzj27)의 ID**다. 서비스가 반환한 OrderBid에서 `.getId()`를 꺼내 `orderId` 변수에 담아 응답한다 (`Xzj27CommandController.java:101-109`; 서비스 반환형은 `Xzj27`, `Xzj27CommandService.java:119`). Order(Xdg64)의 ID가 아니다.

## 2. 새로 생기는 엔티티와 상태 변화 순서

새로 생기는 엔티티는 Order, OrderItem, OrderShipment, Payment(카드/계좌/일반 중 하나), OrderBid, Notification(구매자·판매자)이다. WarehouseStorage와 SaleBid는 새로 생기지 않는다.

| 순서 | 동작 | 직후 상태 | 근거 |
|---|---|---|---|
| 1 | Order 생성 | Order = `PENDING_PAYMENT` | `Xdg64CommandService.java:241-247` |
| 2 | OrderItem 생성 후 Order에 추가 | 상태 값 변화 없음 | `:255-256` |
| 3 | OrderShipment 생성 | Shipment = `PENDING` | `D/m12/service/command/Xhx14CommandService.java:61-68` |
| 4 | `saleBid.assignOrder(order)` 후 `updateStatus(MATCHED)` | SaleBid = `MATCHED` (`assignOrder` 안에서도 MATCHED가 됨) | `Xdg64CommandService.java:279-280`, `D/m10/entity/Xzz58.java:58-61`, `:66-68` |
| 5 | (판매자가 창고 보관인 경우) 창고 상태 변경 | WarehouseStorage = `ASSOCIATED_WITH_ORDER` | `Xdg64CommandService.java:291-293`, `D/m07/service/command/Xnn94CommandService.java:117-133` |
| 6 | 결제 생성 | 카드 성공 = `PAID`(isSuccess true), 계좌이체 = `PENDING`, 일반 = `PAID` (3번 참고) | `D/m06/service/command/Xbf54CommandService.java:203-206`, `:260`, `:313-314` |
| 7 | 결제 후 알림과 Sale 상태 변경 | Sale = `SOLD` | `Xbf54CommandService.java:383-420` (`:404`, `:419`) |
| 8 | OrderBid 생성 | OrderBid = `MATCHED` | `Xzj27CommandService.java:196`; `assignOrder`도 MATCHED로 만든다 (`D/m16/entity/Xzj27.java:60-82`, `:75`) |

**Order 상태는 1번 이후 바뀌지 않는다.** 즉시 구매 경로에서는 `PAYMENT_COMPLETED`나 `PREPARING`으로 전환하는 코드가 호출되지 않는다. 그런 전환은 `processPaymentAndShipment`(`Xdg64CommandService.java:165-176`)와 Kafka 컨슈머(`Xdg64EventConsumer.java:195-217`)에만 있고, 둘 다 즉시 구매 경로에서 쓰이지 않는다.
- 결제 객체는 `order.assignPayment`로 Order에 연결되지 않는다. 결제 쪽에서만 `assignOrder`를 한다 (`Xbf54CommandService.java:200`, `:258`, `:311`; `Xdg64CommandService.java:305`는 반환값을 버린다).

## 3. 결제 수단별 결과, 성공 여부, 카드 결제 실패

수단은 요청 DTO 타입으로 결정된다 (`D/m06/dto/Xbf54RequestDto.java:74-87`). 분기는 `Xbf54CommandService.java:67-80`이다.

| 수단 | 처리 | 결제 상태 | 근거 |
|---|---|---|---|
| 카드 (CARD) | 저장된 결제정보 조회 후 PortOne(`api.iamport.kr`) 단건결제 호출. 응답 `status == "success"`일 때만 PAID로 바꾼다 | 성공 `PAID` | `Xbf54CommandService.java:157-208`, `D/m06/p05/Xxv33ApiClient.java:229-285` |
| 계좌이체 (ACCOUNT) | 은행명만 검증하고 PG 호출 없이 저장. 입금 확인 로직 없음 | `PENDING`, isSuccess는 setPaidAmount 때문에 true | `Xbf54CommandService.java:236-262`, `D/m06/entity/Xbf54.java:60-63` |
| 일반 (GENERAL) | impUid 필수 확인 외에는 PG 검증 없이 무조건 성공 처리 | `PAID`, isSuccess true | `Xbf54CommandService.java:290-316` |

**끝까지 성공하나**: 세 수단 모두 PG 응답이나 결제 상태와 관계없이 예외가 나지 않으면 `processPayment` 안에서 알림 발송과 Sale `SOLD`가 이어진다 (`Xbf54CommandService.java:83`). 따라서 계좌이체(`PENDING`)여도 Sale은 `SOLD`가 되고 구매자·판매자에게 "결제 완료" 알림이 간다. 컨트롤러는 "즉시 구매가 성공적으로 처리되었습니다."를 반환한다 (`Xzj27CommandController.java:109`). 단, Order는 `PENDING_PAYMENT`로 남는다 (2번 참고).

**카드 결제를 PG가 실패로 응답하는 경우**는 두 가지다.
1. **HTTP가 200이 아니거나 `code != 0`인 경우**: `Xdf64Exception`이 던져진다 (`Xxv33ApiClient.java:270-274`). 이 예외는 `Xbf54ApiException`이 아니라서 `@Retryable` 대상도 아니다 (`:224-228`). 예외는 `createCardPayment`(`Xbf54CommandService.java:218-219`)와 `processPayment`(`:89-94`)를 거쳐 `createInstantOrder`에서 `Xqj91Exception`으로 감싸 던져진다 (`Xdg64CommandService.java:306-308`, `:312-314`). `Xzj27CommandService`가 이를 그대로 재던진다 (`:212-215`). 이 예외들은 `RuntimeException` 계열(`global/exception/Xks43Exception.java:10`)이고 서비스에 `@Transactional`이 걸려 있어 Order, OrderItem, OrderShipment, SaleBid MATCHED, 창고 상태 변경이 롤백된다. OrderBid는 만들어지지 않고 응답은 오류다. 코드에서는 이 롤백과 결제 상태가 결제 전체 트랜잭션에 묶여 있다는 점이 확인된다.
2. **`code == 0`이지만 응답 `status`가 `"success"`가 아닌 경우** (아임포트의 카드 거절이 이 형태일 수 있다): 예외가 나지 않는다. `if ("success".equals(...))` 안에서만 PAID로 바뀌므로 (`Xbf54CommandService.java:203-206`) 결제는 `PENDING`으로 저장된다. 또 빌더가 `setPaidAmount`를 호출해 `isSuccess=true`가 이미 되어 있다 (`D/m06/entity/Xqg94.java:38`, `D/m06/entity/Xbf54.java:60-63`). 이후 알림 발송과 Sale `SOLD`, OrderBid `MATCHED`가 그대로 진행되고 즉시 구매는 "성공"으로 응답된다. 실패한 카드 결제인데 성공으로 처리되는 셈이다. 같은 실패를 막는 `payment.isSuccess()` 검사는 Kafka 경로에만 있고(`Xdg64EventConsumer.java:174-176`) 즉시 구매 경로에는 없다.

## 4. 알림 대상, 시점, 전달 방식

**누가 무엇을 받나** (`Xbf54CommandService.sendNotifications`, `:434-462`; 카테고리 `SHOPPING`, 유형 `BID`)
- 구매자(order.getUser): "결제가 완료되었습니다. 주문 ID: {orderId}" (`:437-443`)
- 판매자(sale.getSeller): "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}" (`:447-454`)
- 즉시 구매 경로에서는 다른 알림이 없다. Kafka `Xdg64EventConsumer`의 성공/실패 알림(`:287-374`)이나 환불 알림(`:603-659`)은 호출되지 않는다.

**언제**: `processPayment` 안에서 결제 객체가 저장된 직후, 요청 처리 중에 발송된다 (`Xbf54CommandService.java:83` → `:383-420`). 알림 발송이 Sale을 `SOLD`로 바꾸기 직전이다 (`:416` → `:419`).
- 이 시점에 OrderBid는 아직 만들어지지 않았으므로 `order.getOrderBid()`가 null이고, 판매 입찰 조회 경로로 Sale을 찾는다 (`:388-406`; `saleBidQueryService.findByOrderId`는 `D/m10/service/query/Xzz58QueryService.java:26-28`). 이 조회는 못 찾으면 null이 아니라 `IllegalArgumentException`을 던지고, 바깥 `catch`가 삼킨다(`:421-425`).
- 알림 오류도 삼켜서(`:457-461`) 결제나 주문을 되돌리지 않는다.

**어떤 방식으로**: `Xkh73CommandService.createNotification` (`D/m15/service/command/Xkh73CommandService.java:44-59`)이 호출 스레드에서 동기로
1. 알림을 DB에 저장하고 (`:52-53`),
2. 사용자의 Redis 키 `WebSocket:Xrd81:{email}`가 있을 때만 STOMP `/user/queue/notifications`로 푸시한다 (`:303-322`, 상수 `:37-38`). 접속 중이 아니면 DB에만 저장된다 (`:320-321`).

Kafka나 비동기 큐는 쓰지 않는다. 알림 생성이 요청 트랜잭션 안(`Xbf54CommandService`는 클래스 `@Transactional`, `:37`)에서 일어나므로, 이후 단계에서 예외가 나 롤백되면 DB의 알림 행도 롤백된다. 이미 나간 WebSocket 푸시는 되돌릴 수 없다.

## 5. 최종 주문 상태와 "창고 보관" 선택의 영향

**최종 상태**
- **Order**: `PENDING_PAYMENT`. 즉시 구매 경로에서 생성 시점의 값(`Xdg64CommandService.java:244`) 이후로 바꾸는 코드가 없다. 결제 완료로 바뀌지 않으며, 응답 ID가 Order의 ID가 아니라는 점과 함께 코드명과 동작이 다른 부분이다.
- OrderBid = `MATCHED` (`Xzj27CommandService.java:196`), SaleBid = `MATCHED` (`Xdg64CommandService.java:280`), Sale = `SOLD` (`Xbf54CommandService.java:419`), Shipment = `PENDING` (`Xhx14CommandService.java:67`).
- Payment는 3번 표의 상태다.

**구매자가 "창고 보관"(`warehouseStorage=true`)을 선택하면**: 아무것도 달라지지 않는다.
- 값은 컨트롤러에서 서비스로 전달된다 (`Xzj27CommandController.java:104`, `Xzj27CommandService.java:119`, `:137`, `Xdg64CommandService.java:220-221`). 그러나 `createInstantOrder` 본문에서 `isWarehouseStorage` 파라미터는 한 번도 읽지 않는다 (`Xdg64CommandService.java:219-319`).
- 구매자용 WarehouseStorage는 만들어지지 않는다. `warehouseStorageCommandService.createOrderStorage`와 `IN_WAREHOUSE`·`COMPLETED` 전환은 `processPaymentAndShipment`(`:163-172`)와 Kafka 컨슈머(`Xdg64EventConsumer.java:197-210`)에만 있다.
- 창고 관련 코드는 구매자의 선택이 아니라 판매자의 선택(`sale.isWarehouseStorage()`)을 본다. Sale이 창고 보관이면 기존 창고 보관 레코드가 `ASSOCIATED_WITH_ORDER`로 바뀐다 (`Xdg64CommandService.java:291-293`; 필드는 `D/m10/entity/Xgg74.java:43`). 구매자 플래그 여부와 상관없이 같다.
- 따라서 `true`/`false` 모두 최종 Order 상태는 `PENDING_PAYMENT`이고 구매자 쪽 창고 보관 엔티티는 생기지 않는다. 일반 주문 경로(`processPaymentAndShipment`)에서는 이 선택이 `IN_WAREHOUSE` → `COMPLETED`로 이어지지만, 즉시 구매에는 적용되지 않는다.
