코드 이름 ↔ 업무 용어: Xzj27 = 주문 입찰(OrderBid), Xdg64 = 주문(Order), Xzz58 = 판매 입찰(SaleBid), Xgg74 = 판매(Sale), Xbf54 = 결제(Payment), Xkh73 = 알림(Notification), Xnn94 = 창고 보관(WarehouseStorage), Xhx14 = 배송(OrderShipment).

   5. 배송 정보(Xhx14) 생성 (`:264-271`)

   (Kafka 컨슈머 `m16/service/kafka/Xdg64EventConsumer.java:61-110`, `m06/service/kafka/Xbf54EventConsumer.java:51-109`는 이 흐름과 무관하다.)
6. **응답 ID**: 변수명은 `orderId`이고 성공 메시지도 "즉시 구매"지만, 실제 값은 **주문 입찰(Xzj27 OrderBid) 엔티티의 ID** 이다. 서비스가 반환한 `Xzj27`에서 `.getId()`를 꺼내 응답한다 (`m16/controller/command/Xzj27CommandController.java:101-109`, 반환값 `m16/service/command/Xzj27CommandService.java:142-146`, `:189-207`). 주문(Xdg64)의 ID가 아니다.

기존 엔티티의 상태 변화 순서:

1. **판매 입찰 Xzz58**: `assignOrder(order)`가 order를 연결하면서 상태를 `MATCHED`로 바꾸고 (`m10/entity/Xzz58.java:58-61`), 이어서 `updateStatus(MATCHED)` 한 번 더 호출 (`Xdg64CommandService.java:279-280`), 즉시 `entityManager.flush()` (`:283`). → 판매 입찰 `PENDING → MATCHED`. 이 시점에 판매 입찰이 이미 MATCHED인지는 검사하지 않는다 (`Xzj27CommandService.java:172-184`에 상태 검사 없음).
2. **창고 보관(Xnn94)**: 판매(Xgg74)의 `isWarehouseStorage()`가 true(**판매자가 창고 보관으로 올린 판매**)이면 보관 상태를 `ASSOCIATED_WITH_ORDER`로 변경 (`Xdg64CommandService.java:291-294`, `m07/service/command/Xnn94CommandService.java:117-133`). 구매자가 보낸 `isWarehouseStorage`는 여기서 쓰이지 않는다 (5번 참조).
3. **결제 처리** (`Xbf54CommandService.java:57-88`): 결제 엔티티 생성 → `notifyUsersAndUpdateSaleStatus` (`:83`)
   - 주문에 연결된 주문 입찰이 아직 없으므로(`order.getOrderBid()==null`, 주문 입찰은 결제 이후에 생성됨) `saleBidQueryService.findByOrderId`로 판매 입찰 → 판매를 찾는다 (`:388-401`, `m10/service/query/Xzz58QueryService.java:26-29`).
   - 알림 전송 후 **판매(Xgg74) 상태를 `SOLD`로** 변경 (`:403-405`). `updateStatus`는 전이 검증 없이 대입만 한다 (`m10/entity/Xgg74.java:73-75`).
4. **주문 입찰 Xzj27 생성**: `status=MATCHED`, `assignOrder`로 주문과 양방향 연결(이때도 MATCHED, `m16/entity/Xzj27.java:60-75`), `markAsInstantPurchase()` (`Xzj27CommandService.java:189-207`).

요약 순서: 주문 `PENDING_PAYMENT` 생성 → 판매 입찰 `MATCHED` → (판매자 창고 보관이면) 창고 `ASSOCIATED_WITH_ORDER` → 결제 생성(수단별) → 판매 `SOLD` → 주문 입찰 `MATCHED`로 생성.
**주문(Xdg64)의 상태는 이 흐름에서 한 번도 바뀌지 않는다** (5번 참조).

## 3. 결제 수단별 결과 / 성공 여부 / 카드 실패 응답

공통: 결제 유형은 요청의 `paymentType`(CARD/ACCOUNT/GENERAL)으로 분기 (`m06/dto/Xbf54RequestDto.java:20-25`, `Xbf54CommandService.java:67-80`). 결제 금액은 클라이언트가 보낸 `paidAmount`이며(100 이상 검증, `Xbf54RequestDto.java:50-52`, `Xbf54CommandService.java:142-145`) 판매 입찰가와 비교하지 않는다.

| 결제 수단 | 결제 상태 / isSuccess | 근거 |
|---|---|---|
| CARD | PortOne 응답 `status`가 문자열 `"success"`일 때만 `PAID` + `isSuccess=true`. 그 외(응답 status가 다른 값이면)는 기본값 `PENDING`, `isSuccess=false` 로 저장되고 **예외 없이 계속 진행** | `Xbf54CommandService.java:203-208`, 기본값 `m06/entity/Xbf54.java:39,44` |
| ACCOUNT(계좌이체) | 은행명만 검증, 외부 호출 없음. `PENDING`, `isSuccess=false` 로 저장 | `Xbf54CommandService.java:243-262`, 기본값 `m06/entity/Xbf54.java:39,44` |
| GENERAL(일반) | impUid가 비어 있지 않으면 외부 검증 없이 바로 `PAID` + `isSuccess=true` | `Xbf54CommandService.java:297-316` |

**즉시 구매가 끝까지 성공하는가**: 카드·계좌이체·일반 모두 즉시 구매 흐름 자체는 성공(HTTP 200, "즉시 구매가 성공적으로 처리되었습니다.")한다. 이 흐름은 결제의 `isSuccess`/`PAID` 여부를 검사하지 않는다 (`Xdg64CommandService.java:304-311` 은 반환값을 버리고 `return order`). 따라서 **계좌이체는 입금 전(`PENDING`)이어도, 카드 응답이 `"success"`가 아니어도** 판매 입찰 `MATCHED`, 판매 `SOLD`, 주문 입찰 `MATCHED`, 구매자·판매자 알림("결제가 완료되었습니다")이 모두 진행된다 (`Xbf54CommandService.java:83`, `:403-405`, `:438-454`). 결제 완료가 아닌데 완료 알림이 나가고 판매가 SOLD가 되는 것이 실제 동작이다.
- 참고: PortOne의 정상 응답 status 값이 `"success"`가 아니라 `"paid"` 같은 값이면 정상 결제도 `PENDING`/`isSuccess=false`로 남는다. 코드가 비교하는 값은 `"success"`뿐이다 (`:203`).

**결제 대행사가 카드 결제를 실패로 응답하면**
- PortOne이 HTTP 200이 아니거나 `code != 0`이면 `Xdf64Exception("카드 결제 요청 실패: ...")` (`m06/p05/Xxv33ApiClient.java:270-274`). `Xdf64Exception`은 `Xbf54Exception`의 하위 클래스이므로 `createCardPayment`가 그대로 재던지고 (`Xbf54CommandService.java:180-181`, `:218-219`), 결제 엔티티는 저장되지 않는다.
- `processPayment`도 재던지고 (`:89-94`), `createInstantOrder`가 `Xqj91Exception("결제 처리 중 오류가 발생했습니다")`로 감싸 던진다 (`Xdg64CommandService.java:305-309`). `Xdg64Exception` 하위라서 바깥 catch가 그대로 전달 (`:312-315`), `Xzj27CommandService.createInstantOrderBid`도 `Xdg64Exception`이면 그대로 던진다 (`:145-148`, `:212-214`). 응답은 에러이며 응답 ID 없음.
- `@Transactional`이므로 같은 트랜잭션에서 한 일(주문, 주문 항목, 배송, 판매 입찰 MATCHED, 창고 `ASSOCIATED_WITH_ORDER`)이 모두 롤백된다 (`Xdg64CommandService.java:219`, `Xzj27CommandService.java:118`). 판매 입찰은 `PENDING`으로 돌아가고 판매는 SOLD가 되지 않는다. 결제 실패 알림은 이 경로에 없고, 실패 시 알림도 가지 않는다 (알림은 결제 성공 반환 후에만 호출, `Xbf54CommandService.java:83`).
- 단, 대행사가 HTTP 200 + `code==0`이면서 `response.status`가 `"success"`가 아닌 "실패"를 돌려주는 경우는 위의 "그 외" 경로로, 예외 없이 `PENDING`, `isSuccess=false` 결제가 저장되고 흐름은 성공으로 끝난다 (`Xbf54CommandService.java:203-208`).
- 통신 오류(RestClientException)는 `Xbf54ApiException` (`Xxv33ApiClient.java:288-290`)이며 같은 방식으로 롤백된다.

## 4. 알림 대상 / 시점 / 방식

1. **누가**: 결제 처리 성공 직후 `sendNotifications` (`Xbf54CommandService.java:434-455`)
   - 구매자: "결제가 완료되었습니다. 주문 ID: {orderId}" — `Xzv64.SHOPPING`, `Xkh73Type.BID` (`:437-443`)
   - 판매자(`sale.getSeller()`): "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}" — `Xzv64.SHOPPING`, `Xkh73Type.BID` (`:447-454`)
   - 구매 요청자·판매자 외에 다른 사람은 받지 않는다. 판매자 쪽 알림 유형도 `BID`다.
2. **언제**: 같은 요청·트랜잭션 안에서, 결제 엔티티 저장 직후, 판매를 `SOLD`로 바꾸기 직전 (`:83` → `:403-405`). 주문 입찰 Xzj27 생성보다 **앞**이다. 결제 수단·결제 상태와 무관하게(`PENDING`이어도) 보낸다.
3. **어떻게**: `Xkh73CommandService.createNotification` (`m15/service/command/Xkh73CommandService.java:44-59`)가 DB에 알림을 저장하고, 이어서 `sendRealTimeNotification` (`:303-322`)으로 Redis에 `WebSocket:Xrd81:{email}` 키(접속 표시)가 있을 때만 STOMP `/user/{email}/queue/notifications` 로 푸시한다. 키가 없으면 푸시 없이 "알림은 저장됨"(DB 저장만). Kafka 알림은 이 경로에서 쓰지 않는다. 알림 전송 실패는 `catch`로 삼켜져 즉시 구매 결과에 영향이 없다 (`Xbf54CommandService.java:457-461`; 바깥 `notifyUsersAndUpdateSaleStatus`도 모든 예외를 로그만 남김 `:421-425`).
4. 주문 완료 WebSocket/Kafka 알림("주문 완료" `sendSuccessNotification`, `m16/service/kafka/Xdg64EventConsumer.java:287-329`)은 Kafka 주문 처리 컨슈머에서만 호출되므로 즉시 구매에서는 발송되지 않는다.

## 5. 최종 주문 상태 / 창고 보관 선택 시 차이

- **주문(Xdg64)의 최종 상태는 `PENDING_PAYMENT`** 이다. `createInstantOrder`는 주문을 `PENDING_PAYMENT`로 만들고 (`Xdg64CommandService.java:244`) 이후 `updateStatus`를 호출하는 곳이 없다 (`:219-319` 전체). 결제 성공(`PAID`)이어도 주문 상태는 `PAYMENT_COMPLETED`/`PREPARING`으로 넘어가지 않는다. `PAYMENT_COMPLETED → PREPARING` 전이는 `processPaymentAndShipment`(`:111-202`)와 Kafka 컨슈머(`Xdg64EventConsumer.java:192-220`)에만 있는데 즉시 구매 경로는 호출하지 않는다.
  - 코드에는 `주문 완료`·`즉시 구매가 성공적으로 처리되었습니다`(컨트롤러 `:109`) 같은 메시지가 있지만 실제 주문 상태는 결제 대기 상태로 남는다.
- 주문 입찰(Xzj27)은 `MATCHED` (`Xzj27CommandService.java:196`), 판매 입찰(Xzz58)은 `MATCHED`, 판매(Xgg74)는 `SOLD`.
- **구매자가 "창고 보관"(`warehouseStorage=true`)을 선택한 경우**: 아무것도 달라지지 않는다.
  - 컨트롤러는 `requestDto.isWarehouseStorage()`를 서비스에 넘기고 (`Xzj27CommandController.java:104`), 서비스는 `createInstantOrder(buyer, saleBid, addressId, isWarehouseStorage, paymentRequest)`로 전달하지만 (`Xzj27CommandService.java:133-139`), `createInstantOrder` 본문은 이 파라미터를 전혀 사용하지 않는다 (`Xdg64CommandService.java:219-319`에 `isWarehouseStorage` 참조 자체가 없음).
  - 창고 관련 처리는 **판매자 쪽** `sale.isWarehouseStorage()`일 때 보관 상태를 `ASSOCIATED_WITH_ORDER`로 바꾸는 것뿐이다 (`:291-294`).
  - 구매자용 창고 보관 엔티티 생성(`createOrderStorage`)과 `IN_WAREHOUSE`/`COMPLETED` 전이는 `processPaymentAndShipment`(`:163-172`)와 Kafka 컨슈머(`Xdg64EventConsumer.java:197-211`)에만 있고 즉시 구매에서는 실행되지 않는다. 따라서 주문의 창고 보관(`warehouseStorage`) 엔티티는 생성되지 않고 주문 상태도 `PENDING_PAYMENT` 그대로이다.
