# 즉시 구매 처리 흐름 (POST /order-bids/instant)

경로 약어: `D` = `src/main/java/com/fream/back/domain`

## 1. 진입 API, 처리 단계, 동기/비동기, 응답 ID

**진입 API**: `POST /order-bids/instant` (`D/m16/controller/command/Xzj27CommandController.java:22`, `:89-90`). 본문은 `Xpj49RequestDto`(saleBidId, addressId, warehouseStorage, paymentRequest) (`D/m16/dto/Xpj49RequestDto.java:20-29`).

**단계**
1. 컨트롤러가 로그인 사용자 이메일을 꺼낸다 (`Xzj27CommandController.java:92`).
2. `enrichPaymentRequest`가 결제 요청에 userEmail을 넣고 orderId를 null로 만든다 (`Xzj27CommandController.java:98`, `:119-123`).
3. `Xzj27CommandService.createInstantOrderBid`(`@Transactional`)를 호출한다 (`D/m16/service/command/Xzj27CommandService.java:118`, `:119`).
   - 입력 검증: 이메일, saleBidId, addressId, paymentRequest (`Xzj27CommandService.java:123`, `:154-167`).
   - 구매자와 판매 입찰을 조회하고 판매 입찰에 연결된 Sale이 있는지 확인한다 (`Xzj27CommandService.java:126-130`, `:172-184`).
4. `Xdg64CommandService.createInstantOrder`를 호출한다 (`Xzj27CommandService.java:133`; `D/m16/service/command/Xdg64CommandService.java:219-221`). 이 안에서 순서대로 실행한다.
   - 배송지 조회 (`Xdg64CommandService.java:238`)
   - 주문 저장 (`:241-247`)
   - 결제 요청에 orderId 설정 (`:250`)
   - 주문 항목 생성 (`:255-256`)
   - 주문 배송 생성 (`:264-271`)
   - 판매 입찰 매칭 (`:279-283`)
   - 판매자 창고 보관 상태 갱신 (`:291-293`)
   - 결제 처리 (`:305`)
5. 결제까지 끝난 뒤에야 주문 입찰(`Xzj27`)을 만든다. `MATCHED`로 만들고 `markAsInstantPurchase()`를 호출한 뒤 저장한다 (`Xzj27CommandService.java:189-207`).

**동기/비동기**: 전부 **동기**이고 한 트랜잭션이다. 결제 대행사(PortOne) HTTP 호출도 요청 스레드에서 블로킹으로 실행된다 (`D/m06/p05/Xxv33ApiClient.java:266`). 알림도 같은 스레드에서 처리한다 (4번 참고). 이 경로에는 Kafka 발행이 없다.

비동기(Kafka) 경로는 별개의 `POST /orders/{orderId}/process-payment-shipment`뿐이다 (`D/m16/controller/command/Xdg64CommandController.java:37-54`, 202 ACCEPTED 응답). 즉시 구매는 이 경로를 쓰지 않는다.

**응답 ID**: 응답 `data`는 **주문 입찰(OrderBid, `Xzj27`, order_bid 테이블)의 ID**이다. 컨트롤러 변수명은 `orderId`이지만 `createInstantOrderBid(...)`가 반환한 `Xzj27`에 `.getId()`를 호출한 값이다 (`Xzj27CommandController.java:101-107`). 서비스가 돌려주는 객체가 `Xzj27`이다 (`Xzj27CommandService.java:119`, `:189`, `:206`). 주문(Order) ID가 아니다. 주문 ID는 응답에 담기지 않는다.

## 2. 새로 만들어지는 엔티티와 상태 전이 (순서, 직후 상태)

| 순서 | 동작 | 대상 | 직후 상태 | 근거 |
|---|---|---|---|---|
| 1 | 주문 생성 | `Xdg64` Order | `PENDING_PAYMENT` (totalAmount = 판매 입찰가) | `Xdg64CommandService.java:241-247` |
| 2 | 주문 항목 생성 | `Xhm58` OrderItem (수량 1, 가격 = 입찰가) | 상태 필드 없음 | `Xdg64CommandService.java:255-256`; `D/m16/service/command/Xhm58CommandService.java:45-52` |
| 3 | 주문 배송 생성 | `Xhx14` OrderShipment | `PENDING` (Xpb98Status) | `Xdg64CommandService.java:264-271`; `D/m12/service/command/Xhx14CommandService.java:61-70` |
| 4 | 판매 입찰 매칭 | `Xzz58` SaleBid에 order 연결 | `PENDING` → `MATCHED` (`assignOrder`가 MATCHED로 세팅, 이어서 `updateStatus(MATCHED)`) | `Xdg64CommandService.java:279-280`; `D/m10/entity/Xzz58.java:58-60` |
| 5 | 판매자 창고 보관 상태 갱신 (Sale이 창고 보관인 경우만) | `Xnn94` WarehouseStorage | `ASSOCIATED_WITH_ORDER` | `Xdg64CommandService.java:291-293`; `D/m07/service/command/Xnn94CommandService.java:117-133` |
| 6 | 결제 생성 | `Xbf54` Payment (Xqg94, Xkg34, Xjt86 중 하나) | 결제 수단별로 다름 (3번 참고) | `Xdg64CommandService.java:305`; `D/m06/service/command/Xbf54CommandService.java:57-81` |
| 7 | 알림 생성 후 판매 상태 변경 | `Xkh73` Notification 2건, `Xgg74` Sale | Sale → `SOLD` | `Xbf54CommandService.java:83`, `:383-419`, `:434-454` |
| 8 | 주문 입찰 생성 | `Xzj27` OrderBid (`isInstantPurchase=true`, sale 연결) | `MATCHED` | `Xzj27CommandService.java:189-207`; `D/m16/entity/Xzj27.java:75`, `:97-98` |

- 7번에서 Sale을 `SOLD`로 바꿀 때 상태 전이 검증이 없다. `updateStatus`는 값을 그대로 대입한다 (`D/m10/entity/Xgg74.java:73-75`).
- 주문 입찰이 7번 시점에는 아직 없다. `order.getOrderBid()`가 null이므로 `saleBidQueryService.findByOrderId`로 판매 입찰을 거쳐 Sale을 찾는다 (`Xbf54CommandService.java:388-404`). 4단계에서 연결해 둔 order_id가 이 조회를 가능하게 한다.
- **Order 상태는 위 어느 단계에서도 바뀌지 않는다** (5번 참고).

## 3. 결제 수단별 결과, 끝까지 성공 여부, 카드 실패 시

`processPayment`는 결제 DTO의 실제 타입으로 분기한다 (`Xbf54CommandService.java:67-80`). 시작 전 검증은 다음과 같다 (`:117-146`).
- orderId 일치 (`:131`)
- 이메일 일치 (`:136`)
- 금액 > 0 (`:142`)

| 수단 | 처리 | Payment 상태 | 근거 |
|---|---|---|---|
| 카드 (Xqg94) | 저장된 결제정보를 조회하고 PortOne 카드 결제를 동기 호출한다. 응답 `status == "success"`이면 상태를 `PAID`로, 성공 플래그를 true로 바꾼다. | `PAID` | `Xbf54CommandService.java:166`, `:179`, `:187-208` |
| 계좌이체 (Xkg34) | 은행명만 검증한다. 외부 호출과 입금 확인이 없다. | `PENDING`으로 저장 | `Xbf54CommandService.java:244`, `:250-262` |
| 일반 결제 (Xjt86) | impUid 존재만 검사한다. PortOne 검증 호출 없이 클라이언트가 준 값을 신뢰해 바로 성공 처리한다. | `PAID` | `Xbf54CommandService.java:297-316` |

**끝까지 성공하는가**
- 카드, 일반 결제: 예외가 없으면 알림, Sale `SOLD`, 주문 입찰 `MATCHED` 저장까지 모두 이어진다.
- 계좌이체: 요청 자체는 "성공"으로 끝난다. 하지만 Payment는 `PENDING`이고 입금 확인 로직이 이 경로에 없다. 그런데 `notifyUsersAndUpdateSaleStatus`는 결제 상태를 보지 않고 실행된다 (`Xbf54CommandService.java:83`, `:383-419`). 그래서 입금 전에도 구매자와 판매자에게 "결제 완료" 알림이 가고 Sale이 `SOLD`가 된다.
- 카드 응답이 HTTP 200이고 `code == 0`인데 `status != "success"`이면 Payment가 `PENDING`/미성공으로 저장된다 (`Xbf54CommandService.java:203-208`). 이때도 알림과 `SOLD`가 실행된다.
- 판매자 알림과 판매 상태 갱신 블록은 예외를 삼킨다 (`:421-425`, `:457-461`). 이 단계의 실패는 구매를 롤백시키지 않는다.

**카드 결제를 대행사가 실패로 응답하면** (HTTP 비 200 또는 `code != 0`)
1. `processCardPayment`가 `Xdf64Exception`을 던진다 (`Xxv33ApiClient.java:270-275`). 이 예외는 `Xbf54Exception`의 하위 클래스이다 (`D/m06/exception/Xdf64Exception.java:6`).
   - `@Retryable`은 `Xbf54ApiException`만 대상이므로 재시도되지 않는다 (`Xxv33ApiClient.java:224-228`).
   - 같은 클래스 안의 `catch (Xbf54Exception e) { throw e; }`로 그대로 전파된다 (`:286-287`).
2. 이 예외는 `createCardPayment`와 `processPayment`를 거쳐 그대로 던져진다 (`Xbf54CommandService.java:180-182`, `:218-219`, `:89-94`). 그 결과 Payment 행은 저장되지 않는다 (`:208`에 도달하지 않음).
3. `createInstantOrder`가 이를 `Xqj91Exception`("결제 처리 중 오류가 발생했습니다")으로 감싸 던진다 (`Xdg64CommandService.java:305-309`). `Xdg64Exception` 계열이므로 바깥 catch에서 그대로 재던진다 (`:312-315`). `Xzj27CommandService.handleOrderBidCreationException`도 `Xdg64Exception`은 그대로 재던진다 (`Xzj27CommandService.java:212-218`).
4. `Xks43Exception`은 RuntimeException이다 (`D/global/exception/Xks43Exception.java:10`). `@Transactional`에서 전체가 롤백된다.
   - 롤백 대상: 주문, 주문 항목, 배송, 판매 입찰 `MATCHED`, 창고 `ASSOCIATED_WITH_ORDER`
   - 주문 입찰은 아직 만들어지지 않았다.
5. 알림은 만들어지지 않는다. 결제 실패는 알림 생성 이전에 던져지기 때문이다 (`Xbf54CommandService.java:179` → `:83`).
6. 응답은 오류이고, 판매 입찰은 `PENDING`으로 남아 다른 구매자가 다시 살 수 있다.

## 4. 알림 수신자와 전달 방식

수신자는 두 명이다 (`Xbf54CommandService.java:434-454`).
- **구매자**: "결제가 완료되었습니다. 주문 ID: {orderId}" (`:438-443`)
- **판매자** (`sale.getSeller()`): "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}" (`:447-454`)
- 둘 다 카테고리 `SHOPPING`, 타입 `BID`이다.

**시점**: 결제 처리 직후, 같은 요청과 같은 트랜잭션 안에서 동기로 만든다 (`Xbf54CommandService.java:83`). 결제 상태와 무관하다 (3번 참고).

**전달 방식**: `Xkh73CommandService.createNotification` (`D/m15/service/command/Xkh73CommandService.java:44-67`)이 두 가지를 한다.
1. 알림을 DB에 저장한다 (`:53`).
2. 수신자가 접속 중이면 WebSocket으로 실시간 푸시한다 (`:57`, `:303-323`).
   - 접속 여부는 Redis 키 `WebSocket:Xrd81:{email}`의 존재로 판단한다 (`:37`, `:307`).
   - 키가 있으면 `convertAndSendToUser(email, "/queue/notifications", dto)`로 보낸다 (`:309-313`).
   - 접속 중이 아니면 DB 저장만 하고 나중에 조회로 확인한다 (`:320-322`).

푸시 실패는 경고 로그만 남고 구매에는 영향이 없다 (`:315-319`; `Xbf54CommandService.java:457-461`). 별도 큐나 Kafka는 쓰지 않는다.

## 5. 최종 주문 상태와 "창고 보관" 선택

**주문 최종 상태: `PENDING_PAYMENT`**
- 즉시 구매 경로는 주문을 `PENDING_PAYMENT`로 만들고 (`Xdg64CommandService.java:244`) 끝까지 `updateStatus`를 호출하지 않는다 (`:219-319`).
- 카드와 일반 결제가 `PAID`여도 주문은 `PAYMENT_COMPLETED`나 `PREPARING`이 되지 않는다. 주문을 전이시키는 코드는 비동기 Kafka 경로 (`D/m16/service/kafka/Xdg64EventConsumer.java:195-217`)와 `processPaymentAndShipment` (`Xdg64CommandService.java:165-177`) 뿐이다. 즉시 구매는 둘 다 거치지 않는다.
- "즉시 구매가 성공적으로 처리되었습니다" 메시지 (`Xzj27CommandController.java:109`)와 달리 주문 상태만 보면 결제 대기로 남는다. 그 외 상태는 다음과 같다.
  - 주문 입찰 `MATCHED`
  - 판매 입찰 `MATCHED`
  - Sale `SOLD`
  - 배송 `PENDING`
  - Payment 는 수단에 따라 `PAID` 또는 `PENDING`

**구매자가 "창고 보관"(`warehouseStorage=true`)을 선택하면: 달라지는 것이 없다.**
- 컨트롤러는 값을 서비스에 넘긴다 (`Xzj27CommandController.java:105`). 서비스도 `createInstantOrder`에 그대로 넘긴다 (`Xzj27CommandService.java:133-139`).
- 그러나 `createInstantOrder`의 `isWarehouseStorage` 파라미터는 본문에서 한 번도 읽지 않는다 (`Xdg64CommandService.java:220-319`에서 파라미터 선언 외 사용 없음).
- 구매자용 창고 보관 엔티티(`createOrderStorage`)도 만들지 않는다. 주문을 `IN_WAREHOUSE`/`COMPLETED`로 바꾸는 분기는 `processPaymentAndShipment`에만 있다 (`Xdg64CommandService.java:163-173`). 즉시 구매는 이 메서드를 호출하지 않는다.
- 창고 관련 처리는 **판매자 쪽** `sale.isWarehouseStorage()`일 때만 일어난다. 이때 기존 판매자 창고 보관 건을 `ASSOCIATED_WITH_ORDER`로 바꾼다 (`Xdg64CommandService.java:291-293`, `D/m10/entity/Xgg74.java:43`).
- 구매자가 창고 보관을 선택해도 결과는 선택하지 않은 경우와 동일하다. 응답의 ID, 주문 상태, 엔티티 구성이 모두 같다.
