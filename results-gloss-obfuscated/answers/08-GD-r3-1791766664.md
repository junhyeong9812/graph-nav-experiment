# 구매자 배송: 운송장 등록 → 배송 완료

경로 약칭: `B` = `src/main/java/com/fream/back`
엔티티 이름: Xhx14 = 주문 배송(order_shipment), Xdg64 = 주문(Order), Xzj27 = 주문 입찰(OrderBid), Xzz58 = 판매 입찰(SaleBid), Xgg74 = 판매(Sale), Xpb98Status = 배송 상태, Xdg64Status = 주문 상태, Xtz73Status = 입찰 상태.

## 0. 전제: 결제·배송 처리 직후의 상태

- 주문은 `PENDING_PAYMENT`로 생성된다. `B/domain/m16/service/command/Xdg64CommandService.java:81`
- `processPaymentAndShipment`가 결제와 배송 정보(Xhx14)를 만든다. `Xdg64CommandService.java:139`, `:148`
  - 배송 정보는 `PENDING` 상태로 생성된다. `B/domain/m12/service/command/Xhx14CommandService.java:67`
- 창고 보관이 아닌 실배송이면 주문은 `PAYMENT_COMPLETED` → `PREPARING`에서 멈춘다. `Xdg64CommandService.java:175-176`
  - `SHIPMENT_STARTED`로는 가지 않는다.
- 결제 서비스는 주문 상태를 바꾸지 않는다. `Xbf54CommandService`에는 `order.updateStatus` 호출이 없다.
- 따라서 (a) 일반 구매 입찰 실배송 주문은 주문 `PREPARING` / 배송 `PENDING`이다.
- (b) 즉시 구매 주문은 `createInstantOrder`에서 `PENDING_PAYMENT`로 생성된다. `Xdg64CommandService.java:244`
  - 이후 주문 상태를 바꾸는 코드는 없어 `PENDING_PAYMENT`로 남는다. 배송은 `PENDING`이다. `Xdg64CommandService.java:264`

## 1. 운송장 등록 요청

### 1-1. 진입 API
- `PATCH /shipments/order/{shipmentId}/status`, 바디는 `{courier, trackingNumber}`이다.
  - `B/domain/m12/controller/command/Xhx14CommandController.java:20`, `:33-45`
  - 컨트롤러가 `Xhx14CommandService.updateTrackingInfo`를 호출한다.
- 같은 컨트롤러의 `POST .../check-status`, `.../check-status-string`은 별도 경로다. `Xhx14CommandController.java:58`, `:103`
  - 이쪽은 `updateAndCheckShipmentStatus`를 호출한다(아래 1-4 참고).

### 1-2. 코드가 의도한 순서 (`Xhx14CommandService.updateTrackingInfo`, `:238-303`)
1. 택배사·운송장이 비어 있으면 `TRACKING_INFO_REQUIRED`(400)를 던진다. `:243-246`
2. 배송을 조회하고 `shipment.updateTrackingInfo`를 호출한다. `:249`, `:256`
   - 엔티티가 상태를 무조건 `IN_TRANSIT`으로 세팅한다. 전이 검사가 없다. `B/domain/m12/entity/Xhx14.java:41-45`
3. `order.updateStatus(IN_TRANSIT)`을 호출한다. `Xhx14CommandService.java:259-260`
4. 구매자에게 알림을 보낸다: "상품이 출발하였습니다. 주문 ID: …". `:265-270`
5. `updateSaleStatusToSold(orderId)`를 호출한다. `:276`
   - 판매 입찰(SaleBid)에서 판매(Sale)를 `SOLD`로 바꾼다. `:116-123`
   - 판매자에게 "상품이 성공적으로 판매 완료되었습니다" 알림을 보낸다. `:132-138`
   - 창고 보관이면 창고 상태도 `SOLD`로 바꾼다. `:126-129`
   - 주문 입찰(OrderBid) 기준 Sale도 `SOLD`로 바꾸고 판매자에게 같은 알림을 보낸다. `:150-172`
6. 창고 보관이면 창고 상태를 `SOLD`로 바꾼다. `:279-286`
7. `updateOrderAndSaleBidStatusToCompleted`를 호출한다. `:289`
   - 주문 입찰이 `MATCHED`이면 `COMPLETED`로 바꾼다. `:422-425`
   - 판매 입찰이 `MATCHED`이면 `COMPLETED`로 바꾼다. `:428-432`
   - 이 메서드는 private인데 `@Transactional`이 붙어 있다(`:412`). 프록시를 타지 않으므로 효과가 없다.
   - 내부에서 예외를 삼키므로 실패해도 전파되지 않는다. `:436-439`

의도된 순서를 요약하면 다음과 같다.
- 배송: `IN_TRANSIT`
- 주문: `IN_TRANSIT`
- 판매: `SOLD`
- 입찰: 둘 다 `COMPLETED`
- 알림: 구매자 1건(출발) + 판매자 알림

### 1-3. 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문(즉시 구매 아님)에서의 결과: 성공하지 못한다
- 실패 지점은 `:260`의 `order.updateStatus(IN_TRANSIT)`이다.
  - 주문 상태가 `PREPARING`이다(0절).
  - 허용 전이는 `PREPARING → {IN_WAREHOUSE, SHIPMENT_STARTED}`뿐이다. `B/domain/m16/entity/Xdg64Status.java:26`
  - `IN_TRANSIT`은 `SHIPMENT_STARTED`에서만 갈 수 있다(`Xdg64Status.java:28`). 그 경로는 어디서도 거치지 않는다.
  - 따라서 `Xdg64.updateStatus`가 `Xxc76StatusException`을 던진다. `B/domain/m16/entity/Xdg64.java:113-120`
- 예외가 `catch (Exception e)`에 잡혀 `Xpb98Exception(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")`로 바뀐다. `Xhx14CommandService.java:295-301`
- 저장되는 것은 없다.
  - 메서드 전체가 하나의 `@Transactional`(`:238`)이고 `RuntimeException`이 밖으로 나가므로 전체가 롤백된다.
  - 2단계에서 바꾼 배송 `IN_TRANSIT`과 택배사·운송장 번호도 롤백되어 배송은 `PENDING`, 운송장은 비어 있다.
  - 주문은 `PREPARING`으로 유지된다.
  - 구매자 알림(4단계)과 판매 상태 변경(5단계)은 3단계 이후라서 실행조차 되지 않는다.
- 응답은 HTTP 404이다. 바디는 `ErrorResponse(code="S001", message="배송 정보를 찾을 수 없습니다.", status=404, path)`이다.
  - 근거: `Xks43ExceptionHandler.handleShipmentException`, `B/global/exception/Xks43ExceptionHandler.java:459-473`
  - 코드 `SHIPMENT_NOT_FOUND`는 `B/domain/m12/exception/Xpb98ErrorCode.java:12`에 정의되어 있다.
  - 이 컨트롤러 메서드(`:33-49`)는 try/catch가 없어 예외가 그대로 전역 핸들러로 간다.
  - 실제 원인은 "배송 없음"이 아니라 주문 상태 전이 불가이므로, 코드와 메시지가 오해를 부른다.
- (b) 즉시 구매 주문도 같은 이유로 실패한다. 주문이 `PENDING_PAYMENT`이고 허용 전이가 `{PAYMENT_COMPLETED, COMPLETED, IN_WAREHOUSE}`이기 때문이다. `Xdg64Status.java:24`
- 결과적으로 PATCH API로는 `PENDING`에서 `IN_TRANSIT`으로 갈 수 없다.

### 1-4. 우회 경로: `POST /shipments/order/{id}/check-status`
- `updateAndCheckShipmentStatus`(`Xhx14CommandService.java:451-516`)는 `shipment.updateTrackingInfo`로 배송을 `IN_TRANSIT`으로 만든다(`:473`).
  - 이후 CJ 조회 결과(`:477`)로 상태를 정한다.
  - 이 경로는 주문 상태를 바꾸지 않고, 알림도 보내지 않는다.
- 조회 결과가 `DELIVERED`가 아니면 `IN_TRANSIT` 또는 `OUT_FOR_DELIVERY`로 남아, 아래 2절의 주기 처리 대상이 된다.

## 2. 배송 완료 감지

### 2-1. 누가, 언제, 어떻게
- `Xpb98BatchScheduler.scheduleShipmentStatusJob`이 감지한다. 스프링 스케줄러가 호출한다.
  - 주기는 `@Scheduled(cron = "0 0 */6 * * *")`로 6시간마다(00/06/12/18시 정각)이다. `B/global/config/Xpb98BatchScheduler.java:34`
  - 이 메서드가 `updateShipmentStatusesJob`을 실행한다(`:36-40`). 예외는 `printStackTrace`로만 처리한다(`:41-43`).
- 스케줄링은 다른 클래스의 `@EnableScheduling`으로 활성화된다. 예: `B/domain/m05/config/Xwv44Scheduler.java:16`

### 2-2. 조회 대상
- Job의 reader는 JPQL `SELECT s FROM Xhx14 s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL`이다. `B/domain/m12/config/Xqv91JobConfig.java:95`
- 이 쿼리는 `PENDING` 배송을 읽지 않는다. 운송장이 등록돼 `IN_TRANSIT`/`OUT_FOR_DELIVERY`가 된 배송만 대상이다.
- 청크 크기와 스킵 한도는 모두 50이다. `Xqv91JobConfig.java:51-52`

### 2-3. 실제로 실행되는 처리 코드
- 실제로 실행되는 것은 **`Xth19Processor`**(`B/domain/m12/config/Xth19Processor.java:56-157`)이다.
  - `Xqv91JobConfig.java:69-73`에서 `new Xth19Processor(...)`를 step의 processor로 붙인다.
  - Playwright 브라우저로 CJ 페이지를 조회한다(`Xth19Processor.java:72-90`). 브라우저는 `Xmb36Listener`가 step 전후에 열고 닫는다. `Xmb36Listener.java:15-24`
- 실행되지 않는 유사 코드는 다음과 같다.
  - `Xqv91JobConfig.shipmentItemProcessor`(`:104-177`)는 `@Bean`이지만 step에 연결되지 않는다.
    - 구성 클래스 안의 `parseCjLogisticsStatus`(`:186`)와 `mapToShipmentStatus`(`:228`)도 마찬가지다.
  - `Xhx14CommandService.updateShipmentStatuses`(`:308-391`)는 호출하는 곳이 없다. 스케줄러·배치 어디서도 참조하지 않는다.
  - 이 코드가 같은 일을 하는 것처럼 보이지만, 같은 상태에서 `COMPLETED` 처리만 하고 입찰·판매 처리가 없다는 점이 다르다.

### 2-4. 택배사 상태 문자열 → 내부 상태 (`Xth19Processor.mapToShipmentStatus`, `:220-226`)
| 택배사 문자열 | 내부 상태 |
|---|---|
| `"배송완료"` | `DELIVERED` |
| `"배송출발"` | `OUT_FOR_DELIVERY` |
| 그 외 모든 문자열 | `IN_TRANSIT` |

- 상태 텍스트는 마지막 행의 5번째 `td`이다. `Xth19Processor.java:181`
- 비교는 완전 일치(`switch`)이다. 그래서 "배송 완료"처럼 공백이 다르면 `IN_TRANSIT`이 된다.
- 현재 상태와 같으면 변경 없이 반환한다. `Xth19Processor.java:101-105`

## 3. 배송 완료 판정 이후 (`Xth19Processor.process:108-118` → `completeOrder`)

순서는 다음과 같다.
1. 배송 `IN_TRANSIT`/`OUT_FOR_DELIVERY` → `DELIVERED`. `Xth19Processor.java:113`
   - 엔티티 전이는 `IN_TRANSIT → DELIVERED`와 `OUT_FOR_DELIVERY → DELIVERED`를 허용한다. `B/domain/m12/entity/Xpb98Status.java:16-28`
2. `orderService.completeOrder(orderId)`를 호출한다. `Xth19Processor.java:116`
   - `Xhx14CommandService.java:190-229`에서 먼저 OrderBid를 조회한다. 없으면 `IllegalArgumentException`이 된다. `:196-197`
   - 주문을 `COMPLETED`로 바꾼다. `:204`
   - `updateSaleStatusToSold`를 호출한다(`:208`). 그 내용은 1-2의 5단계와 같다(Sale `SOLD`, 창고 `SOLD`, 판매자 알림).
   - 구매자에게 "[completeOrder] 주문이 완료되었습니다" 알림을 보낸다. `:211-217`
3. `notificationService.notifyShipmentCompleted(order)`를 호출한다. `Xth19Processor.java:117`
   - 구매자에게 "[배송 완료] 상품이 배송 완료되었습니다" 알림을 보낸다. `B/domain/m15/service/command/Xkh73CommandService.java:219-229`
4. `JpaItemWriter`가 배송을 저장한다. `Xqv91JobConfig.java:239-246`

### 알림
- 구매자에게 2건이 간다.
  - "[completeOrder] …" (`Xhx14CommandService.java:212-217`)
  - "[배송 완료] …" (`Xkh73CommandService.java:224-229`)
- 판매자에게는 Sale 상태를 `SOLD`로 바꿀 수 있을 때만 알림이 간다.
  - `updateSaleStatusToSold`의 SaleBid 쪽(`:133-138`)과 OrderBid 쪽(`:164-169`)에서 각각 최대 1건이다.
  - 다만 Sale이 이미 `SOLD`면 `canTransitionTo(SOLD)`가 거짓이라 보내지 않는다. `Xgg74Status.java:23`

### 입찰 상태
- 배치 경로는 `completeOrder`만 호출하고 `updateOrderAndSaleBidStatusToCompleted`는 호출하지 않는다.
  - 따라서 OrderBid·SaleBid는 `COMPLETED`로 바뀌지 않고 `MATCHED`로 남는다.
  - 그 메서드는 `updateTrackingInfo`(`:289`)에서만 호출된다.
- 판매(Sale)는 전이 가능할 때만 `SOLD`로 바뀐다.

## 4. 주문 종류별 차이 (3의 처리가 끝까지 진행되나)

전제: 두 경우 모두 배치 대상이 되려면 배송이 `IN_TRANSIT`이어야 한다. 1-3에서 보았듯 PATCH API는 두 경우 모두 롤백되므로, 이 상태는 `check-status` API(1-4)로만 만들 수 있다.

### (a) 일반 구매 입찰 주문, 실배송: 끝까지 진행되지 않는다
- 주문이 `PREPARING`이다. 허용 전이는 `{IN_WAREHOUSE, SHIPMENT_STARTED}`뿐이라 `COMPLETED`가 불가하다. `Xdg64Status.java:26`
- `completeOrder`의 `order.updateStatus(COMPLETED)`(`Xhx14CommandService.java:204`)에서 `Xxc76StatusException`이 난다.
  - catch되어 `Xpb98Exception(ORDER_NOT_FOUND_FOR_SHIPMENT)`로 바뀐다. `:221-227`
  - 프로세서도 `Xpb98Exception`을 그대로 다시 던진다. `Xth19Processor.java:138-145`
- 결과는 다음과 같다.
  - 청크가 롤백되고 해당 건은 skip된다.
  - 주문은 `PREPARING`으로 남고, 배송은 DB에서 `IN_TRANSIT` 그대로이다. 입찰과 판매는 바뀌지 않는다.
  - 알림은 전혀 가지 않는다. 상태 변경이 알림보다 앞이라서다.
  - 6시간마다 같은 건이 다시 실패한다.

### (b) 즉시 구매로 만들어진 주문: 끝까지 진행된다
- 주문이 `PENDING_PAYMENT`이고 `PENDING_PAYMENT → COMPLETED`가 허용된다. `Xdg64Status.java:24`
- 즉시 구매는 OrderBid도 함께 생성한다(`B/domain/m16/service/command/Xzj27CommandService.java:189-206`). 그래서 `completeOrder`의 OrderBid 조회(`Xhx14CommandService.java:196`)가 성공한다.
- 결과는 다음과 같다.
  - 배송 `DELIVERED`, 주문 `COMPLETED`.
  - Sale은 이미 결제 시점에 `SOLD`가 된 상태이므로 판매자 알림은 없다.
    - 즉시 구매 결제 때 `notifyUsersAndUpdateSaleStatus`가 SaleBid 경로로 Sale을 `SOLD`로 만든다. `B/domain/m06/service/command/Xbf54CommandService.java:383-407`
    - 이때 OrderBid는 아직 없다. `Xzj27CommandService.java:133-142`에서 주문 생성 후에 만들어진다.
  - 구매자 알림은 2건이다.
  - OrderBid·SaleBid는 `MATCHED` 그대로이다(3절 참고).
- 주문이 실제로 `COMPLETED`까지 가는 것은 즉시 구매뿐이다.

### 정리
| 항목 | (a) 일반 구매 입찰 | (b) 즉시 구매 |
|---|---|---|
| 주문 상태 | `PREPARING` 유지 (실패) | `COMPLETED` |
| 배송 상태 | DB에는 `IN_TRANSIT` 유지 | `DELIVERED` |
| 알림 | 0건 | 구매자 2건 |
| 입찰 | 변화 없음 | `MATCHED` 유지 |

## 5. 실패 처리

- step이 `faultTolerant().skip(Exception.class).skipLimit(50)`으로 설정되어 있다. `B/domain/m12/config/Xqv91JobConfig.java:75-77`
  - 프로세서에서 예외가 나면 그 건만 skip된다.
  - 롤백은 해당 청크 단위로 일어나고, 나머지 건은 계속 처리된다.
  - 이 과정은 skip 한도 안에서만 유효하다. 실패가 50건을 넘으면 step이 실패한다.
- skip 사유는 `SkipListener`가 로그로 남긴다. `Xqv91JobConfig.java:251-286`
- 프로세서는 실패를 `Xpb98Exception`으로 감싼다.
  - 운송장 없음이면 `TRACKING_NUMBER_INVALID`다. `Xth19Processor.java:61-64`
  - 그 외 조회·파싱 오류는 `EXTERNAL_TRACKING_SERVICE_ERROR`다. `Xth19Processor.java:138-144`
- skip된 건은 DB에서 상태가 그대로이므로 다음 6시간 주기에 다시 조회 대상이 된다.
- 스케줄러의 `try/catch`는 Job 실행 자체의 예외만 `printStackTrace`로 처리한다. `Xpb98BatchScheduler.java:41-43`
- 참고로, 호출되지 않는 `updateShipmentStatuses`(`Xhx14CommandService.java:308-391`)는 건별 try/catch로 계속 진행하지만 실제로는 실행되지 않는다.
