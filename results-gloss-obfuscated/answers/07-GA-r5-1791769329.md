# 즉시 구매 처리 흐름 (ANSWER)

경로 접두사: `src/main/java/com/fream/back/domain/` (이하 `D/`로 줄임).
이름 대응: Xzj27=OrderBid, Xdg64=Order, Xzz58=SaleBid, Xgg74=Sale, Xbf54=Payment, Xnn94=WarehouseStorage, Xhx14=OrderShipment, Xhm58=OrderItem, Xkh73=Notification.

## 1. 진입 API, 처리 단계, 동기/비동기, 응답 ID

**진입 API**: `POST /order-bids/instant`
- 클래스 매핑 `@RequestMapping("/order-bids")` — `D/m16/controller/command/Xzj27CommandController.java:22`
- 메서드 `@PostMapping("/instant")` `createInstantOrderBid` — `Xzj27CommandController.java:89-90`
- 요청 본문 `Xpj49RequestDto`: `saleBidId`, `addressId`, `warehouseStorage`, `paymentRequest` — `D/m16/dto/Xpj49RequestDto.java`

**처리 단계** (모두 한 호출 스택, 한 트랜잭션)
1. 컨트롤러: 인증 이메일 추출 → 결제 요청에 `userEmail` 주입, `orderId=null` 로 초기화 — `Xzj27CommandController.java:92, 98, 119-122`
2. 컨트롤러가 `Xzj27CommandService.createInstantOrderBid(...)` 호출 — `Xzj27CommandController.java:101-107`
3. 서비스(`@Transactional`): 입력 검증 → 구매자 조회 → 판매 입찰 조회·검증 — `D/m16/service/command/Xzj27CommandService.java:118-129, 154-184`
4. `Xdg64CommandService.createInstantOrder(...)` 호출 — `Xzj27CommandService.java:133-139`
   - 주소 조회 `D/m16/service/command/Xdg64CommandService.java:238`
   - 주문 생성·저장 `:241-247`
   - 주문 항목 생성 `:254-260`
   - 배송 정보 생성 `:263-275`
   - 판매 입찰 매칭 후 flush `:277-283`
   - 판매자 창고 보관 상태 갱신(조건부) `:290-301`
   - 결제 처리 `:304-309`
5. 서비스가 `Xzj27`(주문 입찰)을 만들어 저장 — `Xzj27CommandService.java:142, 189-207`
6. 컨트롤러가 `ResponseDto.success(orderId, "즉시 구매가 성공적으로 처리되었습니다.")` 반환 — `Xzj27CommandController.java:109`

**동기 처리다.** 이 경로에는 Kafka 발행, `@Async`, 이벤트 리스너가 없다. 결제 대행사(PortOne) HTTP 호출도 요청 스레드에서 블로킹으로 실행된다 (`D/m06/p05/Xxv33ApiClient.java:229-285`, `D/m06/service/command/Xbf54CommandService.java:179`). Kafka 로 비동기 처리하는 쪽은 별도 API `POST /orders/{orderId}/process-payment-shipment` 이다 (`D/m16/controller/command/Xdg64CommandController.java:42, 54`). 즉시 구매는 그쪽을 타지 않는다.

**응답으로 돌려주는 ID**: 변수 이름은 `orderId` 이지만 실제 값은 **주문 입찰(`Xzj27`, order_bid) ID** 이다. `createInstantOrderBid(...)` 가 돌려준 `Xzj27` 에 `.getId()` 를 호출한다 (`Xzj27CommandController.java:101-107`). 주문(`Xdg64`)의 ID 가 아니다. 주문 ID 와 값이 같다는 보장은 없다.

세부 사항
- 단계 7 의 경로: 결제 시점에는 `order.getOrderBid()` 가 아직 `null` 이다. 주문 입찰은 결제 이후(단계 8)에 만들어지기 때문이다. 그래서 `saleBidQueryService.findByOrderId` 폴백 경로를 탄다 (`Xbf54CommandService.java:388-406`). 단계 4 에서 이미 flush 했으므로 판매 입찰이 조회된다. 이 경로에서 알림 전송 후 `sale.updateStatus(SOLD)` 가 실행된다.
- `Xzz58.isInstantSale` 은 이 흐름에서 true 가 되지 않는다. 즉시 구매에서 true 로 바뀌는 것은 `Xzj27.isInstantPurchase` 뿐이다.
- 주문 상태는 단계 1 이후 이 흐름에서 한 번도 바뀌지 않는다 (5번 참조).

## 3. 결제 수단별 결과, 성공 여부, 카드 결제 실패 시

결제 유형은 요청 DTO 의 하위 타입으로 결정된다: `CARD` / `ACCOUNT` / `GENERAL` — `Xbf54CommandService.java:67-80`; `D/m06/dto/Xbf54RequestDto.java:74-80`.

| 수단 | 처리 | 결제 상태 | `isSuccess` | 근거 |
|---|---|---|---|---|
| 카드 | 저장된 결제 정보 조회 → PortOne 카드 결제 API 호출 | 응답 `status == "success"` 일 때만 `PAID`, 아니면 기본값 `PENDING` | 성공 시만 `true` | `Xbf54CommandService.java:166, 179, 203-206` |
| 계좌이체 | 은행명만 검증하고 외부 호출 없음 | `PENDING` | `false` (기본값) | `Xbf54CommandService.java:244, 250-262`; `D/m06/entity/Xbf54.java:38-44` |
| 일반 결제 | `impUid` 필수 확인 외에 서버 측 검증·대행사 확인 없음 | 즉시 `PAID` | `true` | `Xbf54CommandService.java:297-316` |

**즉시 구매는 끝까지 성공한다.** 결제 수단과 상관없이 예외가 나지 않으면 위 단계가 모두 실행되고 `Xzj27` 이 저장된다. 계좌이체(`PENDING`)와, 카드 응답이 성공이 아닌 경우(`PENDING`)에도 후속 단계가 그대로 진행된다. 결제 완료를 기다리지 않는다.
- 결제 수단과 무관하게 `notifyUsersAndUpdateSaleStatus` 가 항상 실행된다. 결제가 `PENDING` 이어도 알림이 나가고 판매는 `SOLD` 가 된다 (`Xbf54CommandService.java:83`).
- 결제 금액은 클라이언트가 보낸 `paidAmount`(100원 이상) 가 쓰인다. 판매 입찰가와 대조하는 코드는 없다 (`Xbf54CommandService.java:142`, `Xbf54RequestDto.java:51-52`).

**결제 대행사가 카드 결제를 실패로 응답하면** 실패 형태에 따라 두 가지다.
- (a) HTTP 가 200 이 아니거나 응답 `code != 0` 인 경우: `Xdf64Exception("카드 결제 요청 실패: ...")` 이 발생한다 (`Xxv33ApiClient.java:270-275`). 이 예외가 아래 순서로 전파된다.
  1. `createCardPayment` 가 그대로 재던짐 (`Xbf54CommandService.java:218-219`)
  2. `processPayment` 가 재던짐 (`:89-94`)
  3. `createInstantOrder` 가 `Xqj91Exception`(결제 처리 실패)으로 감쌈 (`Xdg64CommandService.java:306-308`)
  4. `Xdg64Exception` 은 그대로 재던짐 (`Xdg64CommandService.java:312-314`; `Xzj27CommandService.java:213-214`)

  `RuntimeException` 이므로 `@Transactional`(`Xzj27CommandService.java:118`) 이 롤백된다. 주문, 주문 항목, 배송, 판매 입찰 MATCHED, 창고 상태, 결제, 주문 입찰이 모두 취소된다. 알림도 결제 이후에 생성되므로 생성되지 않는다. 클라이언트는 오류 응답을 받는다. 통신 오류(`RestClientException`)는 `Xbf54ApiException` 이 되어 `@Retryable` 로 3회까지 재시도된다 (`Xxv33ApiClient.java:224-228, 288-289`).
- (b) HTTP 200, `code == 0` 이지만 `response.status` 가 `"success"` 가 아닌 경우: 예외 없이 `PENDING`, `isSuccess=false` 인 결제가 저장되고 흐름이 계속된다. 이 경우 구매자·판매자 알림이 나가고 판매는 `SOLD` 가 된다 (`Xbf54CommandService.java:203-208`). 주석·메서드 이름은 "결제 처리"이지만 실제로는 실패 응답이 통과한다.

## 4. 알림 수신자와 전달 방식

수신자는 두 명이다 (`Xbf54CommandService.java:434-456`). 카테고리 `SHOPPING`, 타입 `BID` 이다.
- 구매자: "결제가 완료되었습니다. 주문 ID: {orderId}" — `Xbf54CommandService.java:436-444`
- 판매자(`sale.getSeller()`): "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}" — `Xbf54CommandService.java:447-455`

**시점**: 결제 저장 직후, `processPayment` 내부에서 `notifyUsersAndUpdateSaleStatus` → `sendNotifications` 가 호출될 때다 (`Xbf54CommandService.java:83, 403, 416`). 즉시 구매 요청 처리 중이며, 주문 입찰(`Xzj27`) 생성보다 앞선다.

**방식**: 동기 호출이다.
1. 알림 엔티티를 DB 에 저장한다 — `D/m15/service/command/Xkh73CommandService.java:44-54`
2. 수신자의 WebSocket 연결을 나타내는 Redis 키가 있을 때만 `convertAndSendToUser(email, "/queue/notifications", dto)` 로 실시간 푸시한다. 키가 없으면 저장만 한다 — `Xkh73CommandService.java:38, 305-322`

별도 큐/비동기는 없다. 알림 전송 예외는 삼키고 경고 로그만 남긴다 (`Xbf54CommandService.java:457-461`; 바깥쪽 `:421-425`).

## 5. 최종 주문 상태와 "창고 보관" 선택의 영향

**주문(`Xdg64`)의 최종 상태는 `PENDING_PAYMENT`** 이다. `createInstantOrder` 는 주문을 `PENDING_PAYMENT` 로 만든 뒤(`Xdg64CommandService.java:244`) 상태를 바꾸지 않는다 (`:219-319` 에 `order.updateStatus` 호출이 없다). 결제 서비스도 주문 상태를 건드리지 않는다. `PAYMENT_COMPLETED`/`PREPARING`/`COMPLETED` 로 올리는 코드는 `processPaymentAndShipment`(`:162-177`)와 Kafka 소비자(`D/m16/service/kafka/Xdg64EventConsumer.java:192-217`)에 있으나, 즉시 구매 경로에서는 호출되지 않는다.

그래서 결제가 `PAID` 이든 `PENDING` 이든 주문은 `PENDING_PAYMENT` 로 남는다. 반면 판매 입찰은 `MATCHED`, 판매는 `SOLD`, 주문 입찰은 `MATCHED` 이다. 메서드 이름이나 응답 메시지("즉시 구매가 성공적으로 처리되었습니다")와 달리 주문이 결제 완료 상태로 넘어가지 않는다.

**구매자가 "창고 보관"을 선택한 경우**: 달라지는 것이 없다.
- 플래그는 컨트롤러(`Xzj27CommandController.java:105`)와 서비스(`Xzj27CommandService.java:137`)를 거쳐 `createInstantOrder(…, boolean isWarehouseStorage, …)` 의 파라미터(`Xdg64CommandService.java:221`)까지 전달된다. 그러나 메서드 본문에서 읽히지 않는다 (`:222-318`).
- 구매자용 창고 보관(`Xnn94` 생성, `IN_WAREHOUSE`, `COMPLETED`)은 `processPaymentAndShipment` 에만 있고 즉시 구매에서는 실행되지 않는다 (`Xdg64CommandService.java:163-172`).
- 창고 관련 코드가 도는 조건은 구매자 선택이 아니라 **판매자가 올린 판매의 `sale.isWarehouseStorage()`** 이다. 이 경우 그 판매의 기존 창고 보관 레코드가 `ASSOCIATED_WITH_ORDER` 로 바뀐다 (`Xdg64CommandService.java:291-294`). 이 판매에 보관 레코드가 없으면 예외로 전체가 롤백된다 (`Xnn94CommandService.java:127-138`, `Xdg64CommandService.java:295-300`).
