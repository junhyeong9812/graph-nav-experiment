## 1. 진입 API, 처리 단계, 동기/비동기, 응답 ID

**진입 API**: `POST /order-bids/instant`
- 클래스 매핑 `@RequestMapping("/order-bids")`: `D/m16/controller/command/Xzj27CommandController.java:22`
- 메서드 매핑 `@PostMapping("/instant")`, `createInstantOrderBid`: `Xzj27CommandController.java:89-90`
- 요청 DTO(`Xpj49RequestDto`)는 saleBidId, addressId, warehouseStorage, paymentRequest를 받는다: `D/m16/dto/Xpj49RequestDto.java:20-29`

**처리 단계 (모두 한 요청 스레드 안에서 순차 실행)**
1. 컨트롤러가 인증된 이메일을 꺼낸다: `Xzj27CommandController.java:92`
2. `enrichPaymentRequest`가 결제 요청에 userEmail을 넣고 orderId를 null로 만든다: `Xzj27CommandController.java:98`, `:119-123`
3. `Xzj27CommandService.createInstantOrderBid`(`@Transactional`)를 호출한다: `Xzj27CommandController.java:101-107`, `D/m16/service/command/Xzj27CommandService.java:241-243` (파일 줄 기준 118-120)
   - 입력 검증(이메일/판매입찰ID/배송지ID/결제정보 null 체크): `Xzj27CommandService.java:246` → `:277-290`
   - 구매자 조회 `userQueryService.findByEmail`: `Xzj27CommandService.java:249`
   - 판매 입찰 조회와 검증(sale 존재): `Xzj27CommandService.java:252` → `:295-307`
4. `Xdg64CommandService.createInstantOrder`(`@Transactional`)를 호출한다: `Xzj27CommandService.java:256-262`, `D/m16/service/command/Xdg64CommandService.java:219-221`
   1. 배송지 조회: `Xdg64CommandService.java:238`
   2. 주문(order) 저장: `:241-247`
   3. `paymentRequest.setOrderId(order.getId())`: `:250`
   4. 주문 항목 생성: `:255-256`
   5. 배송 정보(shipment) 생성: `:264-271`
   6. 판매 입찰 매칭: `:279-283`
   7. 판매자의 창고 보관 상태 갱신: `:290-294`
   8. 결제 처리 `paymentCommandService.processPayment`: `:305`
5. 주문 입찰(order bid) 생성/저장: `Xzj27CommandService.java:265` → `:312-330`
6. 응답을 돌려준다: `Xzj27CommandController.java:109`

**동기 처리다.** 즉시 구매 경로에는 Kafka 발행이나 `@Async`가 없다. 결제 대행사(PortOne) 호출도 `RestTemplate.exchange`로 블로킹 호출한다: `D/m06/p05/Xxv33ApiClient.java:266`.
Kafka 비동기 경로(`order-processing-topic`)는 별도의 일반 주문 컨트롤러(`D/m16/controller/command/Xdg64CommandController.java:54`)에서만 발행하며, 즉시 구매에서는 쓰이지 않는다. 컨슈머: `D/m16/service/kafka/Xdg64EventConsumer.java:55-61`.

**응답으로 돌려주는 ID는 주문(order)의 ID가 아니라 "주문 입찰(OrderBid, Xzj27)"의 ID다.**
- 서비스가 반환하는 것은 `Xzj27`이다 (`Xzj27CommandService.java:242`).
- 컨트롤러가 그 `.getId()`를 `orderId`라는 변수명에 담아 응답한다: `Xzj27CommandController.java:101-107`, `:109`.
- 변수명과 메시지는 "orderId/즉시 구매가 성공적으로 처리되었습니다"이지만, 실제 값은 order_bid 테이블의 PK다.

## 3. 결제 수단별 결과, 성공 여부, 카드 결제 실패 시

`Xbf54CommandService.processPayment`가 결제 유형으로 분기한다: `Xbf54CommandService.java:67-80` (유형 결정: `D/m06/dto/Xbf54RequestDto.java:74-87`).
검증: orderId 일치, 이메일 일치, 금액>0만 확인한다 (`Xbf54CommandService.java:131-145`). 금액이 판매 입찰가와 같은지는 검사하지 않는다 (판매 입찰가는 `totalAmount`에만 쓰임: `Xdg64CommandService.java:243`).

| 결제 수단 | 동작 | 결제 상태 / isSuccess | 근거 |
|---|---|---|---|
| 카드 (`CARD`) | 저장된 카드정보 조회 후 PortOne 카드 결제 API를 동기 호출. 응답의 `status`가 `"success"`일 때만 PAID로 바꾼다 | 성공: `PAID`/true + paymentDate. 그 외: 기본값 `PENDING`/false 로 저장 | `Xbf54CommandService.java:166`, `:179`, `:203-206`, `:208` |
| 계좌이체 (`ACCOUNT`) | 외부 호출 없음. 은행 이름만 enum으로 검증 | `PENDING`/false | `Xbf54CommandService.java:243-244`, `:260`, `:262`; 은행 검증 `:470-481` |
| 일반 결제 (`GENERAL`) | impUid 필수 여부만 확인. PortOne에 검증 호출 없음 | 바로 `PAID`/true | `Xbf54CommandService.java:297-300`, `:313-314` |

**즉시 구매는 끝까지 성공하는가?**
- 예외가 나지 않는 한 어느 결제 수단이든 요청은 끝까지 진행되어 200 응답("즉시 구매가 성공적으로 처리되었습니다")을 돌려준다: `Xzj27CommandController.java:109`.
- 호출 측은 `processPayment`의 반환값(결제 성공 여부)을 확인하지 않는다: `Xdg64CommandService.java:305`에서 결과를 버린다. 기존 비동기 경로가 `payment.isSuccess()`를 확인해 실패 시 예외를 던지는 것(`D/m16/service/kafka/Xdg64EventConsumer.java:174-176`)과 다르다.
- 따라서 **계좌이체(PENDING)도 판매 입찰 MATCHED, 판매 SOLD, 주문 입찰 MATCHED, "결제가 완료되었습니다" 알림까지 그대로 진행된다.** 입금 확인을 기다리지 않는다 (`Xbf54CommandService.java:83`, `:404`, `:438-443`).

**결제 대행사가 카드 결제를 실패로 응답하면?** 실패 응답 형태에 따라 두 가지다.
1. **HTTP 비정상 또는 응답 `code != 0`**: PortOne 클라이언트가 `Xdf64Exception("카드 결제 요청 실패: ...")`을 던진다 (`Xxv33ApiClient.java:270-275`). 이 예외가 `Xbf54CommandService.java:180-185` → `:218-219`로 전파되고, `Xdg64CommandService.java:306-309`에서 `Xqj91Exception`으로 감싸진다. 이어 `Xzj27CommandService.java:268-270`을 거쳐 `createInstantOrderBid` 트랜잭션 전체가 롤백된다. 주문/배송/주문 입찰/판매입찰 MATCHED/결제 레코드가 남지 않고 에러 응답이 나간다. (`@Retryable`은 `Xbf54ApiException`일 때만 재시도: `Xxv33ApiClient.java:224-228`)
2. **HTTP 200 + `code == 0`이지만 `response.status`가 `"success"`가 아닌 경우** (코드상 허용되는 경로): 예외가 발생하지 않는다. 결제 엔티티는 기본값 `PENDING`/`isSuccess=false`로 저장된다 (`Xbf54CommandService.java:203-208`, 기본값 `Xbf54.java:39`, `:44`). `FAILED` 상태로 바꾸는 코드는 없다. 이후 흐름은 그대로 진행되어 판매 SOLD, 알림, 주문 입찰 MATCHED, 성공 응답까지 간다. 즉 **카드가 실패했는데 즉시 구매는 성공으로 처리된다.**

## 4. 알림 수신자, 시점, 전달 방식

**수신자 (결제 처리 안에서 2명)**
- 구매자(`order.getUser()`): "결제가 완료되었습니다. 주문 ID: {orderId}": `Xbf54CommandService.java:436-443`
- 판매자(`sale.getSeller()`): "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}": `Xbf54CommandService.java:447-454`
- 카테고리 `SHOPPING`, 타입 `BID`로 동일하다.

**시점**: `processPayment`에서 결제 엔티티를 저장한 직후, 같은 요청/같은 트랜잭션 안에서 동기로 실행된다. 호출 위치는 `Xbf54CommandService.java:83`, 구현은 `:383-426`이다. 결제 성공 여부와 무관하게 나가며 (계좌이체 PENDING, 카드 `status != success`일 때도 발송), 판매 상태 SOLD 변경(`:404`)과 같은 곳에서 일어난다.

**전달 방식**
1. DB에 알림 엔티티(`Xkh73`, `isRead=false`)를 저장: `Xkh73CommandService.java:52-53`, `:241-248`
2. 수신자가 실시간 접속 중이면 WebSocket(STOMP)으로 `/user/{email}/queue/notifications`에 전송. "접속 중" 판정은 Redis 키 `WebSocket:Xrd81:{email}` 존재 여부다: `Xkh73CommandService.java:37-38`, `:303-313`. 키가 없으면 DB 저장만 하고 끝난다 (`:320-322`). 전송 실패는 warn 로그만 남긴다 (`:315-318`).
3. 알림 전송 오류는 삼켜진다. `sendNotifications`와 `notifyUsersAndUpdateSaleStatus`의 try/catch가 로그만 남기고 결제 처리를 계속한다: `Xbf54CommandService.java:457-461`, `:421-425`.

**참고 (즉시 구매에서는 오지 않는 알림)**: `Xdg64EventConsumer`의 `ORDER_COMPLETED` WebSocket(`/queue/notifications`, `/topic/order/{id}`)과 Kafka `notification-topic` 알림은 `order-processing-topic` 이벤트를 소비하는 비동기 경로에서만 나간다 (`Xdg64EventConsumer.java:96`, `:287-329`). 즉시 구매는 이 이벤트를 발행하지 않으므로 해당 알림이 없다. 배송 완료 알림(`notifyShipmentCompleted`, `Xkh73CommandService.java:219-229`)도 이 시점이 아니라 이후 배송 단계의 일이다.

## 5. 처리 종료 시 주문 최종 상태와 창고 보관 선택의 영향

**최종 상태: 주문(Xdg64)은 `PENDING_PAYMENT`로 남는다.**
- 주문은 `PENDING_PAYMENT`로 생성되고 (`Xdg64CommandService.java:241-245`), `createInstantOrder` 안에서 `order.updateStatus(...)`가 호출되지 않는다 (`Xdg64CommandService.java:219-319`).
- 이후 단계도 주문 상태를 바꾸지 않는다. 결제 서비스는 payment/sale/알림만 다루고 (`Xbf54CommandService.java:57-107`, `:383-426`), 주문 입찰 생성은 Xzj27 자신의 상태만 설정한다 (`Xzj27CommandService.java:312-330`).
- 결제가 `PAID`여도 주문은 `PAYMENT_COMPLETED`로 전환되지 않는다. 일반 주문 경로 `processPaymentAndShipment`가 `PAYMENT_COMPLETED`→`PREPARING`(→창고면 `IN_WAREHOUSE`→`COMPLETED`)으로 올리는 코드 (`Xdg64CommandService.java:163-177`)와 달리, 즉시 구매는 그 메서드를 호출하지 않는다.
- 최종 상태 정리:

| 엔티티 | 최종 상태 |
|---|---|
| 주문 `Xdg64` | `PENDING_PAYMENT` |
| 주문 입찰 `Xzj27` | `MATCHED` (`isInstantPurchase=true`) |
| 판매 입찰 `Xzz58` | `MATCHED` |
| 판매 `Xgg74` | `SOLD` |
| 결제 `Xbf54` | 카드 성공/일반 `PAID`, 계좌이체/카드 비성공 응답 `PENDING` |
| 배송 `Xhx14` | `PENDING` |

**구매자가 "창고 보관"을 선택하면?** **실질적으로 아무것도 달라지지 않는다.** 요청의 `warehouseStorage` 값은 사실상 무시된다.
- 컨트롤러는 로그에만 찍는다 (`Xzj27CommandController.java:94-95`), 서비스까지 `isWarehouseStorage`로 전달된다 (`Xzj27CommandController.java:104`, `Xzj27CommandService.java:243`, `:259`).
- `createInstantOrder`는 파라미터로 받지만(`Xdg64CommandService.java:221`) 본문 어디에서도 읽지 않는다 (`:219-319`).
- 그 결과 구매자용 창고 보관(`warehouseStorageCommandService.createOrderStorage`, `order.assignWarehouseStorage`)이 호출되지 않는다. 일반 경로에서는 `Xdg64CommandService.java:163-172`와 `Xdg64EventConsumer.java:197-200`에서 호출된다. 주문 상태도 `IN_WAREHOUSE`/`COMPLETED`로 가지 않는다.
- 창고 관련 로직이 하나 실행되지만 이는 구매자의 선택이 아니라 **판매자 쪽 `sale.isWarehouseStorage()`** 에 의존한다. 판매자가 창고 보관 판매였다면 그 판매의 창고 보관을 `ASSOCIATED_WITH_ORDER`로 바꾼다 (`Xdg64CommandService.java:291-293`).
- 따라서 `warehouseStorage=true`든 `false`든 응답, 주문 상태, 생성 엔티티가 동일하다.

## 요약 (의도와 실제 동작의 차이)
- 응답의 `orderId`는 실제로는 **주문 입찰(order_bid) ID**다 (`Xzj27CommandController.java:101-109`).
- 처리는 전부 **동기**이며 Kafka 이벤트 경로를 타지 않는다.
- 결제 결과(성공 여부)를 확인하지 않아 계좌이체 PENDING이나 카드 비성공 응답도 판매 SOLD, 알림, 성공 응답으로 이어진다 (`Xdg64CommandService.java:305`, `Xbf54CommandService.java:83`).
- 주문은 `PENDING_PAYMENT`에서 전환되지 않고, 구매자의 `warehouseStorage` 입력은 쓰이지 않는다.
