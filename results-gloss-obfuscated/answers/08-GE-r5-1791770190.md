# 구매자 배송: 운송장 등록 ~ 배송 완료 (코드 조사 결과)

경로 접두어: `B` = `src/main/java/com/fream/back`.
타입 이름은 CLAUDE.md 대응표 기준이다 (Xhx14=OrderShipment, Xdg64=Order, Xzj27=OrderBid, Xzz58=SaleBid, Xgg74=Sale, Xpb98=Shipment, Xkh73=Notification).

## 결론 요약

- 운송장 등록 API는 일반 구매 입찰 주문(실배송)에 대해 **끝까지 성공하지 못한다.** 주문 상태 `PREPARING → IN_TRANSIT` 전환이 허용되지 않아 `Xxc76StatusException`이 나고, 트랜잭션이 롤백되며 **404 / S001** 로 응답한다.
- 배송 완료 감지는 6시간마다 도는 Spring Batch 잡이며, 실제로 실행되는 처리 코드는 `Xth19Processor`이다 (`Xqv91JobConfig.shipmentItemProcessor`, `Xhx14CommandService.updateShipmentStatuses` 는 죽은 코드).
- 배송 완료 처리(`completeOrder`)는 즉시 구매 주문(`PENDING_PAYMENT`)에서는 주문이 `COMPLETED`까지 가지만, 일반 구매 입찰 주문(`PREPARING`)에서는 예외로 실패한다.
- 판매(Sale)는 어느 쪽에서도 `SOLD`가 되지 않고, 주문 입찰·판매 입찰 상태는 이 경로에서 `COMPLETED`로 바뀌지 않는다.

## 1. 운송장 등록 요청

### 1-1. 진입 API

- `PATCH /shipments/order/{shipmentId}/status`, 본문 `{courier, trackingNumber}`
  - 컨트롤러 매핑: `B/domain/m12/controller/command/Xhx14CommandController.java:20` (`@RequestMapping("/shipments/order")`), `:33-49` (`updateTrackingInfo`).
  - 본문 DTO: `B/domain/m12/dto/Xhx14RequestDto.java:11-12`.
  - 서비스 호출: `Xhx14CommandService.updateTrackingInfo` (`B/domain/m12/service/command/Xhx14CommandService.java:238-303`).
- 같은 컨트롤러에 `POST /shipments/order/{shipmentId}/check-status` (`:58-94`)와 `check-status-string` (`:103-138`)이 있다. 이 둘은 운송장을 넣고 택배사를 즉시 조회하는 별도 경로이며, "등록 후 알림" 경로는 아니다.

### 1-2. 코드가 의도한 엔티티 상태 변경 순서와 알림 (`Xhx14CommandService.updateTrackingInfo`)

1. 택배사 또는 운송장이 비어 있으면 `TRACKING_INFO_REQUIRED` 예외 (`Xhx14CommandService.java:243-246`).
2. 배송 조회: `orderShipmentRepository.findById` (`:249-253`).
3. **Shipment(OrderShipment)**: `shipment.updateTrackingInfo(courier, trackingNumber)` (`:256`). 엔티티 구현은 택배사·운송장을 넣고 상태를 전환 검증 없이 곧바로 `IN_TRANSIT`으로 세팅한다 (`B/domain/m12/entity/Xhx14.java:41-45`).
4. **Order**: `order.updateStatus(Xdg64Status.IN_TRANSIT)` (`Xhx14CommandService.java:259-260`). 상태 전환 검증이 있다 (`B/domain/m16/entity/Xdg64.java:113-121`).
5. **알림 1 — 구매자**: "상품이 출발하였습니다. 주문 ID: …" (`Xhx14CommandService.java:265-271`).
6. `updateSaleStatusToSold(orderId)` (`:276`, 본체 `:111-183`)
   - 판매 입찰(SaleBid)을 `orderId`로 찾는다 (`:116`).
   - Sale 상태가 SOLD로 전환 가능하면 `SOLD` (`:119-123`), 창고 보관이면 창고 상태 갱신 (`:126-129`).
   - **알림 2 — 판매자**: "상품이 성공적으로 판매 완료되었습니다…" (`:132-138`).
   - 이어서 OrderBid 경로로 한 번 더 Sale을 SOLD로 바꾸려 시도하고 판매자 알림을 보낸다 (`:151-176`). 같은 Sale이면 이미 SOLD라 전환이 안 되어 중복 알림은 안 간다.
7. 창고 보관 Sale이면 `updateWarehouseStatusToSold` (`:279-286`).
8. `updateOrderAndSaleBidStatusToCompleted` (`:289`, 본체 `:412-440`): OrderBid가 `MATCHED`이면 `COMPLETED` (`:422-425`), SaleBid가 `MATCHED`이면 `COMPLETED` (`:428-432`). 이 메서드 안의 예외는 삼킨다 (`:436-439`).

즉 의도된 순서는 Shipment `IN_TRANSIT` → Order `IN_TRANSIT` → (구매자 알림) → Sale `SOLD`(+판매자 알림) → OrderBid/SaleBid `COMPLETED`이다.
메서드 이름·주석은 "운송장 등록"이지만 판매 완료·입찰 완료까지 한꺼번에 처리하도록 짜여 있다.

### 1-3. 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문에서 끝까지 성공하나? — **아니오**

선행 상태 추적:

- 일반 구매 입찰 주문은 `PENDING_PAYMENT`로 생성된다 (`B/domain/m16/service/command/Xdg64CommandService.java:76-82`). OrderBid는 이 주문에 `assignOrder`로 묶인다 (`B/domain/m16/service/command/Xzj27CommandService.java:90-102`).
- 결제·배송 처리 `processPaymentAndShipment` (`Xdg64CommandService.java:112`)는 배송(Shipment)을 `PENDING`으로 만든다 (`:148-155`, `Xhx14CommandService.java:67`).
- 창고 보관이 아닌 실배송이면 주문을 `PAYMENT_COMPLETED` → `PREPARING`까지만 올린다 (`Xdg64CommandService.java:173-177`). 카프카 경로도 동일하게 `PREPARING`에서 멈춘다 (`B/domain/m16/service/kafka/Xdg64EventConsumer.java:195, 214-218`).
- 주문 상태 전환표에서 `PREPARING`은 `IN_WAREHOUSE`, `SHIPMENT_STARTED`로만 갈 수 있고 `IN_TRANSIT`은 허용되지 않는다 (`B/domain/m16/entity/Xdg64Status.java:26`). `SHIPMENT_STARTED → IN_TRANSIT`만 허용되는데 (`:28`), `SHIPMENT_STARTED`로 바꾸는 코드는 코드베이스 어디에도 없다 (`Xdg64Status.SHIPMENT_STARTED` 대입 검색 결과 없음).

실패 지점·원인:

- `Xhx14CommandService.java:260` `order.updateStatus(IN_TRANSIT)`에서 `PREPARING → IN_TRANSIT` 전환이 거부되어 `Xxc76StatusException`("상태 전환이 허용되지 않습니다: PREPARING -> IN_TRANSIT")이 던져진다 (`Xdg64.java:113-121`).
- `updateTrackingInfo`의 `catch (Exception e)`가 이를 `Xpb98Exception(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")`로 감싸 다시 던진다 (`Xhx14CommandService.java:293-302`). 오류 코드 이름과 실제 원인(주문 상태 전환 불가)이 다르다.
- 그 뒤 단계(알림, Sale SOLD, 입찰 COMPLETED)에는 도달하지 못한다. 설령 통과해도 `saleBidQueryService.findByOrderId`는 SaleBid가 없으면 null이 아니라 `IllegalArgumentException`을 던지므로 (`B/domain/m10/service/query/Xzz58QueryService.java:26-29`), 매칭된 판매 입찰이 없는 일반 입찰 주문은 `:116`에서도 막힌다 (추가 장애물).

저장되는 것:

- **아무것도 저장되지 않는다.** `updateTrackingInfo`는 `@Transactional`(`:238`)이고 `RuntimeException`이 메서드 밖으로 나가므로 롤백된다. `shipment.updateTrackingInfo`의 변경(택배사·운송장·`IN_TRANSIT`)은 영속 컨텍스트 메모리에서만 이뤄졌고 flush·commit 되지 않는다.
- Shipment는 `PENDING`, 운송장 `null` 그대로이고 Order는 `PREPARING`이다. 구매자·판매자 알림도 생성되지 않는다 (알림 생성은 `:260` 이후).

응답:

- 예외는 컨트롤러에서 잡히지 않고 전역 핸들러로 간다. `Xks43ExceptionHandler`(`B/global/exception/Xks43ExceptionHandler.java:49-61`)가 에러코드의 상태를 쓰므로 **HTTP 404**, 본문 코드 `S001`, 메시지 "배송 정보를 찾을 수 없습니다." (`B/domain/m12/exception/Xpb98ErrorCode.java:12`).

## 2. 배송 완료 감지

### 2-1. 누가·언제·어떻게

- **누가**: `Xpb98BatchScheduler.scheduleShipmentStatusJob` (`B/global/config/Xpb98BatchScheduler.java:34-44`)가 `updateShipmentStatusesJob`을 `JobLauncher`로 실행한다. 잡 파라미터는 매번 `timestamp`를 바꿔 넣는다 (`:37-40`). 잡 실행 중 예외는 `e.printStackTrace()`로만 처리한다 (`:41-43`).
- **주기**: `@Scheduled(cron = "0 0 */6 * * *")` (`Xpb98BatchScheduler.java:34`) → 매 6시간 정각(00·06·12·18시)마다 실행.
- **대상**: JPQL `SELECT s FROM Xhx14 s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL` (`B/domain/m12/config/Xqv91JobConfig.java:95`). `JpaPagingItemReader`, 페이지 크기 50 (`:89-96`). 즉 `PENDING`, 이미 `DELIVERED`인 배송은 조회하지 않는다.
- **방식**: Playwright 브라우저로 CJ대한통운 조회 페이지 `https://trace.cjlogistics.com/next/tracking.html?wblNo=<운송장>`을 열고 (`B/domain/m12/config/Xth19Processor.java:83` 부근 `page.navigate`, URL 상수는 클래스 상단), `tbody#statusDetail tr`을 기다린 뒤 마지막 행의 5번째 `td` 텍스트를 상태 문자열로 읽는다 (`Xth19Processor.java:181`).

### 2-2. 실제 실행되는 처리 코드

비슷한 코드가 세 곳에 있으나 실제 실행되는 것은 **`Xth19Processor`** 하나이다.

| 위치 | 실제 사용 여부 |
|---|---|
| `B/domain/m12/config/Xth19Processor.java:57` `process()` | **사용됨.** 스텝이 `new Xth19Processor(...)`를 processor로 등록 (`Xqv91JobConfig.java:69-73`) |
| `B/domain/m12/config/Xqv91JobConfig.java:106` `shipmentItemProcessor()` (`@Bean`, Jsoup `parseCjLogisticsStatus`) | 스텝에 연결되지 않은 빈. 실행 경로 없음 (스텝은 `:68-73`에서 직접 생성한 `Xth19Processor`만 사용) |
| `B/domain/m12/service/command/Xhx14CommandService.java:308-391` `updateShipmentStatuses()` | 호출하는 곳이 없음 (전체 소스에서 정의만 존재). 만약 호출되면 주문만 `COMPLETED`로 바꾸는 별개 로직이라 동작이 다르다 |

잡 구성: `updateShipmentStatusesJob` (`Xqv91JobConfig.java:54-60`) → 스텝 `updateShipmentStatusesStep` (`:63-80`): chunk 50, `faultTolerant().skip(Exception.class).skipLimit(50)`, 스텝 리스너가 시작 시 브라우저를 열고 종료 시 닫는다 (`B/domain/m12/config/Xmb36Listener.java:60-70`). writer는 `JpaItemWriter` (`Xqv91JobConfig.java:~140-146`).

### 2-3. 택배사 상태 문자열 → 내부 상태

`Xth19Processor.mapToShipmentStatus` (`Xth19Processor.java:220-226`):

- `"배송완료"` → `DELIVERED`
- `"배송출발"` → `OUT_FOR_DELIVERY`
- 그 외 모든 문자열(집하·간선상차·배송준비 등) → `IN_TRANSIT`

문자열은 `trim()` 후 정확히 일치 비교한다 (`Xth19Processor.java:181`). 상태 행이 없거나 텍스트가 비면 `TRACKING_HTML_PARSE_ERROR`가 던져진다.

처리 분기: 조회 상태가 현재 상태와 같으면 변경 없이 반환하고, `DELIVERED`이면 아래 3번 처리, `OUT_FOR_DELIVERY`이면 상태만 갱신, 그 외는 `IN_TRANSIT`으로 갱신한다 (`Xth19Processor.java:~100-127`). 배송 상태 전환표상 `IN_TRANSIT → DELIVERED`, `OUT_FOR_DELIVERY → DELIVERED`는 허용된다 (`B/domain/m12/entity/Xpb98Status.java:16-28`).

## 3. 배송 완료 판정 이후 (`Xth19Processor` DELIVERED 분기)

엔티티 상태 변경 순서 (`Xth19Processor.java:113-117`):

1. **Shipment** `updateStatus(DELIVERED)` (`:113`). 아직 메모리 값이며 writer가 청크 끝에 저장한다.
2. `orderService.completeOrder(orderId)` (`:116`, 본체 `Xhx14CommandService.java:190-229`)
   - OrderBid를 `orderId`로 조회, 없으면 예외 (`:196-197`, `B/domain/m16/service/query/Xzj27QueryService.java:51-55`).
   - **Order** → `COMPLETED` (`:204`).
   - `updateSaleStatusToSold(orderId)` (`:208`) — 1-2의 6번과 같은 로직: Sale이 `SOLD` 전환 가능할 때만 `SOLD`로 바꾸고 판매자 알림.
   - **구매자 알림 A**: "[completeOrder] 주문이 완료 처리되었습니다. 주문 ID: …" (`:211-217`).
   - 어떤 예외든 `Xpb98Exception(ORDER_NOT_FOUND_FOR_SHIPMENT)`로 감싸 던진다 (`:221-228`).
3. `notificationService.notifyShipmentCompleted(order)` (`Xth19Processor.java:117`) → **구매자 알림 B**: "[배송 완료] 상품이 배송 완료되었습니다. 주문 ID: …" (`B/domain/m15/service/command/Xkh73CommandService.java:219-229`). 이 메서드는 내부 예외를 삼킨다 (`:230-233`).

알림 건수 (성공 시):

- 구매자: **2건** (`[completeOrder]` + `[배송 완료]`).
- 판매자: Sale이 `SOLD`로 전환 가능할 때만 1건, 아니면 0건. 아래 이유로 이 코드베이스에서는 실질적으로 **0건**이다.
  - Sale은 `PENDING_SHIPMENT`로 생성되고 (`B/domain/m10/service/command/Xgg74CommandService.java:62, 108`), 검수 통과 시 `IN_STORAGE`까지만 올라간다 (`B/domain/m12/service/command/Xxn30CommandService.java:82`).
  - `SOLD`로 갈 수 있는 상태는 `ON_AUCTION`, `SELLING` 뿐이다 (`B/domain/m10/entity/Xgg74Status.java:21-22`). `IN_STORAGE`에서는 `SOLD` 불가 (`:20`). `SELLING`/`ON_AUCTION`으로 바꾸는 코드는 없다.
  - 따라서 `canTransitionTo(SOLD)`가 false여서 Sale 상태 변경과 판매자 알림이 건너뛰어진다 (`Xhx14CommandService.java:119, 156`).

주문 입찰·판매 입찰 상태:

- 이 배송 완료 경로에서는 **OrderBid·SaleBid 상태를 바꾸지 않는다.** `completeOrder`와 `Xth19Processor` 어디에도 `Xtz73Status.COMPLETED` 대입이 없다.
- `COMPLETED`로 바꾸는 코드는 운송장 등록 메서드의 `updateOrderAndSaleBidStatusToCompleted` (`Xhx14CommandService.java:289, 412-440`) 뿐이고, 1-3에서 본 대로 그쪽은 앞단에서 실패한다.
- 따라서 두 입찰은 결제 시점의 `MATCHED`로 남는다 (OrderBid: `Xdg64CommandService.java:187-190`·`Xzj27.java:60-79`, SaleBid: `Xzz58.java` `assignOrder`).

## 4. 주문 종류별 차이

배송 완료 판정 후 `completeOrder`의 `order.updateStatus(COMPLETED)` (`Xhx14CommandService.java:204`)가 갈림길이다.

### (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문 — 끝까지 진행되지 않음

- 주문 상태가 `PREPARING` (1-3 참조). `PREPARING → COMPLETED`는 전환표에 없다 (`Xdg64Status.java:26`) → `Xxc76StatusException`.
- `completeOrder`의 catch가 `Xpb98Exception(ORDER_NOT_FOUND_FOR_SHIPMENT)`로 감싼다 (`Xhx14CommandService.java:221-228`).
- 결과: Order는 `PREPARING` 그대로, Sale/입찰 변경 없음, 구매자 알림 A·B 모두 없음. `Xth19Processor`는 `Xpb98Exception`을 다시 던져 (`Xth19Processor.java:~140-150`) 해당 아이템이 skip 처리된다. Shipment `DELIVERED`로의 변경은 writer까지 가지 못해 저장되지 않는다.
- 참고: 이런 배송이 배치 대상(`IN_TRANSIT`/`OUT_FOR_DELIVERY`)이 되려면 1번 운송장 등록 API가 성공해야 하는데 위에서 보듯 실패한다. 따라서 (a)는 정상 경로로는 배치 대상 자체가 되지 못한다. 대상이 되는 경우는 `check-status` API(`updateAndCheckShipmentStatus`, `Xhx14CommandService.java:452-516`)로 Shipment만 `IN_TRANSIT`이 된 경우 정도이고, 그때도 `completeOrder`에서 같은 이유로 실패한다.

### (b) 즉시 구매로 만들어진 주문 — 끝까지 진행되지만 Sale은 SOLD가 되지 않음

- `createInstantOrder`는 주문을 `PENDING_PAYMENT`로 만들고 (`Xdg64CommandService.java:241-245`), Shipment 생성 (`:264-271`), `saleBid.assignOrder(order)` + SaleBid `MATCHED` (`:279-280`), 결제 처리 (`:305`)를 하지만 주문 상태를 더 올리지 않는다. OrderBid는 `order`와 `sale`이 모두 붙은 `MATCHED`이며 `isInstantPurchase=true` (`Xzj27CommandService.java:189-207`).
- 전환표상 `PENDING_PAYMENT → COMPLETED`가 허용되어 (`Xdg64Status.java:24`) `completeOrder`의 `order.updateStatus(COMPLETED)`가 통과한다.
- 결과: Order `COMPLETED`, 구매자 알림 2건. Sale은 `IN_STORAGE` 등 `SOLD` 전환 불가 상태라 변경 없음, 판매자 알림 0건 (3번 참조). OrderBid·SaleBid는 `MATCHED` 유지.
- 참고: 이 주문에 대해 운송장 등록 API(`PATCH …/status`)를 호출하면 `PENDING_PAYMENT → IN_TRANSIT`이 거부되어 역시 1-3과 같은 404가 난다 (`Xdg64Status.java:24`). 이 주문이 `DELIVERED`가 되려면 `check-status` API로 Shipment를 `IN_TRANSIT`으로 만드는 경로를 거쳐야 한다. 그 경로는 `completeOrder`만 호출하고 `notifyShipmentCompleted`는 호출하지 않아 구매자 알림이 1건(`[completeOrder]`)이다 (`Xhx14CommandService.java:483-489`).

차이 요약: 같은 `completeOrder`가 (a)에서는 상태 전환 불가로 예외, (b)에서는 `PENDING_PAYMENT → COMPLETED`가 허용되어 주문 완료까지 진행된다. 둘 다 Sale `SOLD`, OrderBid/SaleBid `COMPLETED`는 일어나지 않는다.

## 5. 실패 처리 (주기 처리 중 한 건 실패)

- 스텝은 `faultTolerant().skip(Exception.class).skipLimit(50)` (`Xqv91JobConfig.java:75-77`)이므로 처리 중 발생한 모든 예외가 skip 대상이다. `Xth19Processor`도 예외를 `Xpb98Exception`으로 감싸 다시 던지고 (`Xth19Processor.java:~140-150`) 아이템 내부에서는 삼키지 않는다.
- **실패한 그 건**: skip 되어 writer에 가지 않으므로 저장되지 않고 이전 상태(`IN_TRANSIT`/`OUT_FOR_DELIVERY`) 그대로 남는다. 스킵 리스너가 에러 로그만 남긴다 (`Xqv91JobConfig.java:~165-200` `shipmentSkipListener`: `onSkipInProcess`, `onSkipInRead`, `onSkipInWrite`). 다음 6시간 주기에 다시 조회 대상이 된다.
- **나머지 건**: 청크(50건)가 롤백된 뒤 아이템 단위로 재처리되어 정상 건은 계속 처리·저장된다. 즉 한 건 때문에 전체가 멈추지 않는다.
  - 단, `completeOrder`는 `@Transactional`이라 청크 트랜잭션에 참여하고, 내부에서 예외가 터지면 해당 트랜잭션이 rollback-only가 되어 그 청크는 어차피 롤백되고 스캔(재시도) 방식으로 다시 처리된다.
- **skip 한도**: 한 번의 잡 실행에서 skip이 50건을 넘으면 스텝이 실패하고 남은 건은 그 회차에서 처리되지 않는다 (`:77`). 잡 실패는 스케줄러가 `printStackTrace`만 하고 넘어간다 (`Xpb98BatchScheduler.java:41-43`).
- 보조 주의: 읽기 조건이 상태(`IN_TRANSIT`/`OUT_FOR_DELIVERY`)인데 처리하면서 상태가 `DELIVERED`로 바뀌어 결과 집합에서 빠지므로, 페이징 reader(페이지 50)가 뒤쪽 페이지를 건너뛸 수 있다. 건너뛴 건은 다음 주기에 처리된다 (코드상 reader `Xqv91JobConfig.java:89-96`, 쿼리 `:95`).
