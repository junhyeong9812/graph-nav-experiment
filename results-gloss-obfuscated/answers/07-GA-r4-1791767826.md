# 즉시 구매 처리 흐름

경로 약어: `D` = `src/main/java/com/fream/back/domain`

## 1. 진입 API, 처리 단계, 동기/비동기, 응답 ID

**API**: `POST /order-bids/instant` (`D/m16/controller/command/Xzj27CommandController.java:22`, `:89-90`). 요청 본문은 `Xpj49RequestDto` = saleBidId, addressId, warehouseStorage, paymentRequest (`D/m16/dto/Xpj49RequestDto.java:20-29`).

**처리 단계 (모두 한 요청 스레드에서 호출 체인으로 진행)**
1. 컨트롤러가 로그인 이메일을 꺼내고 `paymentRequest.userEmail=email`, `orderId=null`로 채운다 (`Xzj27CommandController.java:92`, `:98`, `:119-122`).
2. `Xzj27CommandService.createInstantOrderBid` (`@Transactional`, `D/m16/service/command/Xzj27CommandService.java:118-149`)
   - 입력 검증 (`:123`, `:154-167`)
   - 구매자 조회 (`:126`)
   - 판매 입찰 조회·검증 (`:129`, `:172-184`)
3. `Xdg64CommandService.createInstantOrder` (`@Transactional`, `D/m16/service/command/Xdg64CommandService.java:219-319`)
   - 배송지 조회 (`:238`)
   - 주문 저장 (`:241-247`)
   - 주문 항목 생성 (`:255-256`)
   - 배송 정보 생성 (`:264-271`)
   - 판매 입찰 매칭 + flush (`:279-283`)
   - 창고 상태 갱신 (`:290-301`)
   - 결제 (`:305`)
4. 결제 후 `Xbf54CommandService.notifyUsersAndUpdateSaleStatus`가 알림을 만들고 판매를 SOLD로 바꾼다 (`D/m06/service/command/Xbf54CommandService.java:83`, `:383-426`).
5. 마지막으로 주문 입찰(OrderBid)을 만든다 (`Xzj27CommandService.java:142`, `:189-207`).

**동기/비동기**: 동기다. `@Async`, 큐 발행, 이벤트 발행 없이 한 트랜잭션 안에서 서비스 메서드를 차례로 호출하고, 끝난 뒤에 응답을 반환한다 (`Xzj27CommandController.java:101-109`). PortOne 결제 호출(RestTemplate)도 같은 스레드에서 블로킹으로 실행된다 (`D/m06/p05/Xxv33ApiClient.java:266`). 결제용 Kafka 프로듀서/컨슈머(`D/m06/service/kafka`)는 이 경로에서 호출되지 않는다.

**응답 ID**: OrderBid(주문 입찰, `order_bid`)의 ID다. 주문(Order)의 ID가 아니다. 컨트롤러가 `createInstantOrderBid(...)`가 반환한 `Xzj27`(OrderBid)의 `.getId()`를 `orderId`라는 변수에 담아 반환한다 (`Xzj27CommandController.java:101-107`, `:109`). 변수명과 메시지가 주문 ID처럼 보이지만 실제 값은 OrderBid ID다.

- 6~7단계에서 주문은 아직 OrderBid와 연결되기 전이라 `order.getOrderBid()`가 null이다. 그래서 `saleBidQueryService.findByOrderId`로 판매 입찰을 찾아 Sale을 얻는다 (`Xbf54CommandService.java:388-407`). 이 조회가 가능한 것은 4단계에서 SaleBid에 order를 연결하고 flush했기 때문이다.

- `Xdg64Status` 전이표상 `PENDING_PAYMENT`에서 갈 수 있는 값은 `PAYMENT_COMPLETED`/`COMPLETED`/`IN_WAREHOUSE`다 (`D/m16/entity/Xdg64Status.java:24`).

## 3. 결제 수단별 결과, 성공 여부, 카드 실패 시

결제 유형은 요청 DTO의 `paymentType`(CARD/ACCOUNT/GENERAL) 다형성으로 결정된다 (`D/m06/dto/Xbf54RequestDto.java:20-25`, `:74-87`). 분기는 `Xbf54CommandService.java:67-80`이다.

| 수단 | 처리 | 저장 직후 결제 상태 / isSuccess | 근거 |
|------|------|---------------------------------|------|
| CARD | 저장된 카드정보 조회 후 PortOne 단건결제 API 호출. 응답 `status`가 문자열 `"success"`일 때만 PAID로 변경 | 응답 `status=="success"`면 `PAID`, `isSuccess=true`. 그 외(code 0이지만 status가 다른 값)는 기본값 `PENDING`, `isSuccess=false`로 저장하고 예외 없이 계속 진행 | `Xbf54CommandService.java:164-179`, `:187-208`, 기본값 `D/m06/entity/Xbf54.java:39`, `:44` |
| ACCOUNT (계좌이체) | 은행명 검증(`Xpt57` enum)만 하고 외부 호출 없이 저장 | 항상 `PENDING`, `isSuccess=false`. 입금 확인 로직은 없다 | `Xbf54CommandService.java:243-262` |
| GENERAL (일반) | `impUid`가 비어 있지 않은지만 검사하고 외부 검증 없이 저장 | 즉시 `PAID`, `isSuccess=true` (PortOne에 조회·검증하지 않고 클라이언트가 보낸 값을 신뢰) | `Xbf54CommandService.java:297-316` |

**즉시 구매가 끝까지 성공하는가**: 수단과 무관하게, 예외만 나지 않으면 끝까지 진행한다. 결제 상태가 `PENDING`인 계좌이체나 `"success"`가 아닌 카드 응답도 이후 단계(알림, Sale `SOLD`, SaleBid `MATCHED`, OrderBid `MATCHED` 생성, 정상 응답)를 모두 거친다. `processPayment`와 `notifyUsersAndUpdateSaleStatus`는 결제 상태가 PAID인지 확인하지 않는다 (`Xbf54CommandService.java:83`, `:383-426`). 따라서 계좌이체는 입금 확인 전인데도 Sale이 `SOLD`가 되고 알림이 "결제가 완료되었습니다"로 나간다 (`:442`). 그 사이 Order는 `PENDING_PAYMENT`로 남는다.

**결제 대행사가 카드 결제를 실패로 응답하면**: HTTP 상태가 200이 아니거나 응답 `code`가 0이 아니면 `Xdf64Exception("카드 결제 요청 실패: ...")`을 던진다 (`Xxv33ApiClient.java:270-275`). 이 예외는 다음과 같이 전파된다.
- `createCardPayment`가 `Xbf54Exception`을 그대로 다시 던진다 (`Xbf54CommandService.java:180-181`, `:218-219`).
- `processPayment`도 그대로 다시 던진다 (`:89-94`).
- `createInstantOrder`가 `Xqj91Exception`(결제 처리 실패)으로 감싼다 (`Xdg64CommandService.java:304-309`).
- 바깥 catch가 `Xdg64Exception` 하위이므로 그대로 다시 던진다 (`:312-315`, 상속은 `D/m16/exception/Xqj91Exception.java:6`, `Xdg64Exception.java:10`).
- `Xzj27CommandService`도 그대로 다시 던진다 (`Xzj27CommandService.java:145-146`, `:212-215`).
- 결과: 예외가 `@Transactional` 경계 밖으로 나가 롤백된다 (`Xzj27CommandService.java:118`). 주문·주문 항목·배송·결제·SaleBid `MATCHED`·창고 `ASSOCIATED_WITH_ORDER`가 모두 취소되고, OrderBid는 만들어지지 않으며 알림도 나가지 않는다. 알림은 결제 성공 뒤에 만들기 때문이다 (`Xbf54CommandService.java:83`).
- 통신 오류(`RestClientException`)는 `Xbf54ApiException`이 된다 (`Xxv33ApiClient.java:288-290`). 마찬가지로 전체가 롤백된다.
- 반대로 PortOne이 `code=0`이면서 `status`가 `"success"`가 아닌 값으로 응답하는 경우는 실패로 취급되지 않는다 (위 CARD 행 참조).

## 4. 알림 수신자, 시점, 전달 방식

**누가 무엇을 받나**: 결제 처리 성공 직후 알림이 2건 생성된다 (`Xbf54CommandService.java:434-455`).
- 구매자: "결제가 완료되었습니다. 주문 ID: {orderId}" (`:438-443`)
- 판매자(`sale.getSeller()`): "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}" (`:447-454`)
- 둘 다 카테고리 `SHOPPING`, 타입 `BID`다.
- 다른 알림은 없다. 배송이나 창고 관련 알림, 즉시 구매 시작 알림, 매칭 알림은 이 경로에 없다.

**언제**: 결제 레코드 저장 직후, 같은 요청·같은 트랜잭션 안에서 동기적으로 만들어진다 (`Xbf54CommandService.java:83`). 이 시점은 판매 상태를 SOLD로 바꾸기 직전이고 OrderBid 생성보다 앞이다 (`:416-419`).

**어떻게**: `Xkh73CommandService.createNotification` (`D/m15/service/command/Xkh73CommandService.java:44-67`)
1. 알림을 DB에 저장한다 (`:52-54`).
2. 수신자가 WebSocket에 연결돼 있으면(Redis 키 `WebSocket:Xrd81:{email}` 존재, `:304-307`) STOMP로 `/queue/notifications`에 사용자 대상 푸시한다 (`:309-313`, 상수 `:37-38`).
3. 연결이 없으면 푸시 없이 DB 저장만 하고 끝난다. 이후 조회로 확인해야 한다 (`:320-322`).
- 푸시 실패는 로그만 남기고 무시한다 (`:315-319`).
- 알림 생성 자체가 실패해도 `sendNotifications`와 `notifyUsersAndUpdateSaleStatus`가 예외를 삼켜 구매 흐름은 계속 진행된다 (`Xbf54CommandService.java:457-461`, `:421-425`).
- 알림 저장은 구매 트랜잭션에 포함된다(`Xkh73CommandService`는 클래스 레벨 `@Transactional`, `:27`). 이후 구매 트랜잭션이 롤백되면 저장된 알림도 같이 롤백되지만, 이미 나간 WebSocket 푸시는 되돌릴 수 없다.

## 5. 최종 주문 상태와 창고 보관 선택 시 차이

**최종 주문 상태**: 모든 수단에서 `PENDING_PAYMENT`다. 결제가 PAID인 카드와 일반 결제에서도 마찬가지다 (근거는 2번의 `createInstantOrder`에 `order.updateStatus`가 없다는 점, `Xdg64CommandService.java:219-319`). 같이 변하는 값은 다음과 같다.
- SaleBid `MATCHED` (`:280`)
- Sale `SOLD` (`Xbf54CommandService.java:419`)
- OrderBid `MATCHED` (`Xzj27CommandService.java:196`)
- Payment: 카드는 `PAID` 또는 `PENDING`, 계좌이체는 `PENDING`, 일반은 `PAID`

메서드 이름과 메시지("즉시 구매가 성공적으로 처리되었습니다", `Xzj27CommandController.java:109`)와 달리 주문이 결제 완료나 준비 중 상태로 넘어가지 않는다. `PAYMENT_COMPLETED`→`PREPARING` 전이는 이 경로에서 일어나지 않는다.

**구매자가 "창고 보관"을 선택하면**: 달라지는 것이 없다. 요청의 `warehouseStorage` 값은 컨트롤러에서 서비스로 전달되어 `createInstantOrder`의 `isWarehouseStorage` 인자로 들어가지만 (`Xzj27CommandController.java:104`, `Xzj27CommandService.java:133-139`, `Xdg64CommandService.java:220-221`), 본문에서 한 번도 읽히지 않는다 (`:219-319`).
- 구매자용 창고 보관 엔티티(`createOrderStorage`)는 만들어지지 않는다. 이 호출은 `processPaymentAndShipment` 안에만 있다 (`Xdg64CommandService.java:163-172`).
- `IN_WAREHOUSE`/`COMPLETED`로의 상태 전이도 일어나지 않는다. 그 전이 역시 `processPaymentAndShipment`에만 있다 (`:165-172`).
- 창고와 관련해 실제로 일어나는 일은 구매자 선택이 아니라 판매 쪽 속성이다. 판매(Sale)가 `isWarehouseStorage`이면 판매자 쪽 기존 창고 보관 건이 `ASSOCIATED_WITH_ORDER`로 바뀐다 (`Xdg64CommandService.java:291-293`, `D/m10/entity/Xgg74.java:43`).
- 구매자의 `warehouseStorage` 값은 로그에만 찍힌다 (`Xzj27CommandController.java:94-95`).
