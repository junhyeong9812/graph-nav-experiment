# 구매자 배송: 운송장 등록 → 배송 완료

경로 약어: `B` = `src/main/java/com/fream/back`
(코드 이름: Xhx14 = OrderShipment, Xdg64 = Order, Xzj27 = OrderBid, Xzz58 = SaleBid, Xgg74 = Sale, Xpb98 = Shipment, Xkh73 = Notification)

## 요약

- 운송장 등록 API(`PATCH /shipments/order/{id}/status`)는 PREPARING 상태인 일반 주문과 PENDING_PAYMENT 상태인 즉시 구매 주문 모두에서 실패한다. 주문 상태 전이 `→ IN_TRANSIT`이 허용되지 않기 때문이다. 응답은 404 / `S001`이고 DB에는 아무것도 남지 않는다.
- 배송 완료 감지는 Spring Batch 잡이 6시간마다 수행한다. 일반 구매 입찰 주문(a)은 끝까지 가지 못하고 해당 건이 skip된다. 즉시 구매 주문(b)은 끝까지 진행된다.
- 주문 입찰과 판매 입찰을 COMPLETED로 바꾸는 코드는 운송장 등록 경로(실패하는 경로)에만 있다. 배송 완료 판정 경로는 입찰 상태를 건드리지 않는다.

## 1. 운송장 등록 요청

### 1-1. 어느 API로 들어오나
1. `PATCH /shipments/order/{shipmentId}/status`, 바디는 `{courier, trackingNumber}`.
   - 근거: `B/domain/m12/controller/command/Xhx14CommandController.java:20` (`@RequestMapping("/shipments/order")`), `:33` (`@PatchMapping("/{shipmentId}/status")`), `:41` (서비스 `updateTrackingInfo` 호출). 바디 DTO는 `B/domain/m12/dto/Xhx14RequestDto.java:11-12`.
2. 같은 컨트롤러에 즉시 조회용 `POST /{shipmentId}/check-status`(`:58`)와 `/check-status-string`(`:103`)도 있다. 이들은 서비스 `updateAndCheckShipmentStatus`(`B/domain/m12/service/command/Xhx14CommandService.java:452`)를 호출한다.

### 1-2. 코드가 의도한 상태 변경 순서와 알림
`Xhx14CommandService.updateTrackingInfo` (`Xhx14CommandService.java:238-303`, `@Transactional`)의 순서는 다음과 같다.
1. courier/trackingNumber가 비어 있으면 `TRACKING_INFO_REQUIRED`(400)를 던진다. (`:243-246`, 코드 `B/domain/m12/exception/Xpb98ErrorCode.java:15`)
2. 배송(Xhx14)을 조회하고 `shipment.updateTrackingInfo(courier, trackingNumber)`를 호출한다. (`:249-256`)
   - 이 메서드는 courier와 trackingNumber를 넣고 배송 상태를 곧바로 `IN_TRANSIT`으로 대입한다. (`B/domain/m12/entity/Xhx14.java:41-45`)
   - 전이 검사(`canTransitionTo`)를 거치지 않는다. PENDING은 원래 SHIPPED/CANCELED로만 갈 수 있다. (`B/domain/m12/entity/Xpb98Status.java:4-8`)
3. 주문 상태를 `order.updateStatus(Xdg64Status.IN_TRANSIT)`으로 바꾼다. (`:259-260`)
4. 구매자에게 알림 "상품이 출발하였습니다. 주문 ID: …"를 만든다. SHOPPING/BID, `createNotification`. (`:265-271`)
5. `updateSaleStatusToSold(orderId)`를 호출한다. (`:276`, 본문 `:111-183`)
   - SaleBid의 Sale이 SOLD로 전이 가능하면 Sale을 SOLD로 바꾼다. (`:119-123`)
   - 창고 보관 상품이면 창고 상태도 SOLD로 바꾼다. (`:126-129`)
   - **판매자에게** "상품이 성공적으로 판매 완료되었습니다" 알림을 보낸다. (`:132-138`)
   - OrderBid 쪽 Sale도 같은 방식으로 SOLD로 바꾸고 판매자에게 알림을 보낸다. (`:151-172`)
6. 창고 보관 Sale이면 창고 상태를 한 번 더 SOLD로 바꾼다. (`:279-286`)
7. `updateOrderAndSaleBidStatusToCompleted`로 OrderBid와 SaleBid의 MATCHED를 COMPLETED로 바꾼다. (`:289`, 본문 `:412-440`)

정리하면 의도된 순서는 `shipment IN_TRANSIT → order IN_TRANSIT → (Sale SOLD, 창고 SOLD) → OrderBid/SaleBid COMPLETED`이고, 알림은 구매자 1건(출발)과 판매자 1~2건(판매 완료)이다.

### 1-3. 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문에서 끝까지 성공하나 → 아니오, 실패한다
**어디서·왜 실패하나**
1. 결제·배송 처리를 마친 일반 주문의 상태는 `PREPARING`이다.
   - 생성 시 `PENDING_PAYMENT`. (`B/domain/m16/service/command/Xdg64CommandService.java:81`)
   - `processPaymentAndShipment`의 비창고 분기에서 `PAYMENT_COMPLETED → PREPARING`까지만 진행한다. (`:175-176`)
   - Kafka 소비자 경로도 `PREPARING`에서 멈춘다. (`B/domain/m16/service/kafka/Xdg64EventConsumer.java:195`, `:216-217`)
   - 이 외에 주문 상태를 바꾸는 곳은 없다. `Xdg64Status`를 쓰는 파일은 위 두 서비스, 엔티티, `Xhx14CommandService`뿐이다.
2. 주문 상태 전이표에서 `PREPARING`은 `{IN_WAREHOUSE, SHIPMENT_STARTED}`만 허용한다. (`B/domain/m16/entity/Xdg64Status.java:26`) `IN_TRANSIT`은 `SHIPMENT_STARTED`에서만 갈 수 있다. (`:28`)
3. 따라서 `order.updateStatus(IN_TRANSIT)`(`Xhx14CommandService.java:260`)에서 `Xxc76StatusException("상태 전환이 허용되지 않습니다: PREPARING -> IN_TRANSIT")`이 발생한다. (`B/domain/m16/entity/Xdg64.java:113-121`)
4. 이 예외는 `Xpb98Exception`이 아니므로 `catch (Exception e)`(`Xhx14CommandService.java:295-302`)에서 `Xpb98Exception(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")`으로 감싸져 다시 던져진다.
   - 에러코드 이름은 "배송 정보 없음"이지만 실제 원인은 주문 상태 전이 위반이다.

**무엇이 저장되나 → 아무것도 저장되지 않는다**
- `Xpb98Exception`은 `Xks43Exception extends RuntimeException`이다. (`B/global/exception/Xks43Exception.java:10`) `@Transactional` 메서드에서 던져지므로 트랜잭션이 롤백된다.
- 2단계에서 메모리상으로 바꾼 shipment의 courier, trackingNumber, IN_TRANSIT은 DB에 반영되지 않는다. 배송은 PENDING, 주문은 PREPARING 그대로다.
- 구매자 알림(`:266`)과 이후 단계는 예외 지점(`:260`) 뒤에 있어 실행되지 않는다. 알림은 0건이고, Sale SOLD와 입찰 COMPLETED도 일어나지 않는다.

**응답**
- `Xks43ExceptionHandler.handleShipmentException`이 `ErrorResponse(code="S001", message="배송 정보를 찾을 수 없습니다.", status=404, path)`를 **HTTP 404**로 응답한다. (`B/global/exception/Xks43ExceptionHandler.java:459-473`, 코드 `Xpb98ErrorCode.java:12`)
- 예외 상세 메시지(상태 전이 위반)는 응답 본문에 들어가지 않는다. 핸들러가 `errorCode.getMessage()`만 쓴다. (`:468`)

## 2. 배송 완료 감지

### 2-1. 누가·언제·어떻게
- **누가**: 스케줄러 `Xpb98BatchScheduler.scheduleShipmentStatusJob`이 Spring Batch 잡 `updateShipmentStatusesJob`을 실행한다. (`B/global/config/Xpb98BatchScheduler.java:34-41`)
- **언제**: `@Scheduled(cron = "0 0 */6 * * *")`, 즉 **6시간마다**(00:00, 06:00, 12:00, 18:00 정각). (`:34`)
  - 실행마다 `timestamp` 잡 파라미터를 넣어 새 JobInstance로 돌린다. (`:37-40`)
  - 예외는 `printStackTrace`로만 처리한다. (`:41-43`)
  - 스케줄링 활성화는 다른 설정 클래스의 `@EnableScheduling`에 기대고 있다. (`B/domain/m18/config/Xvq73Configuration.java:37`)
- **어떻게**: 잡이 대상 배송을 읽어 택배사(CJ대한통운) 조회 페이지를 Playwright로 열고 HTML의 마지막 상태 행을 파싱한다.

### 2-2. 조회 대상
- `JpaPagingItemReader`의 쿼리는 `SELECT s FROM Xhx14 s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL`이고, 페이지 크기는 50이다. (`B/domain/m12/config/Xqv91JobConfig.java:91-96`, `:51`)
- 청크 크기는 50, skip 한도는 50이다. (`:51-52`, `:67`, `:75-77`)

### 2-3. 실제로 실행되는 처리 코드
같은 로직이 세 곳에 있다. 실제로 실행되는 것은 **`Xth19Processor.process`** 뿐이다.

| 후보 | 위치 | 실행 여부 |
|---|---|---|
| `Xth19Processor.process` | `B/domain/m12/config/Xth19Processor.java:57` | **실행됨**. 스텝이 `.processor(new Xth19Processor(...))`로 직접 생성해 연결한다. (`Xqv91JobConfig.java:69-73`) |
| `Xqv91JobConfig.shipmentItemProcessor()` 빈 | `Xqv91JobConfig.java:106-177` | 미사용. 스텝에 연결되지 않았다. (`:66-81`) 안의 `parseCjLogisticsStatus`(`:186`)도 어디서도 호출되지 않는다. |
| `Xhx14CommandService.updateShipmentStatuses()` | `Xhx14CommandService.java:309-391` | 미사용. 정의 외 호출처가 없다(전체 소스 grep). |

`Xth19Processor`의 동작은 다음과 같다.
1. Playwright 페이지를 열고 `https://trace.cjlogistics.com/next/tracking.html?wblNo=<운송장>`으로 이동한다. 이어서 `tbody#statusDetail tr`을 대기한다. (`Xth19Processor.java:72`, `:83`, `:87`)
2. 마지막 `tr`의 5번째 `td`(index 4) 텍스트를 상태 문자열로 쓴다. (`:181`)
3. 상태 문자열을 매핑한다. (`:95`, `:220-226`)
4. 매핑 결과가 현재 배송 상태와 같으면 변경 없이 반환한다. (`:101-104`)
5. 결과가 DELIVERED면 배송을 DELIVERED로 바꾸고 `orderService.completeOrder`를 호출한 뒤 `notifyShipmentCompleted`를 호출한다. (`:108-117`)
6. 결과가 OUT_FOR_DELIVERY면 배송 상태만 바꾼다. 그 외는 IN_TRANSIT으로 둔다. (`:118-126` 부근)

### 2-4. 택배사 상태 문자열 → 내부 상태
`mapToShipmentStatus` (`Xth19Processor.java:220-226`):
- `"배송완료"` → `DELIVERED`
- `"배송출발"` → `OUT_FOR_DELIVERY`
- 그 외 전부(예: "집화처리", "간선상차" 등) → `IN_TRANSIT`

문자열 완전 일치(switch)이다. 앞뒤 공백은 `trim()`으로 제거한다. (`:181`) 빈 문자열이거나 행이 없으면 `TRACKING_HTML_PARSE_ERROR`를 던진다. (`:170-189` 부근)

## 3. 배송 완료 판정 이후

`Xth19Processor`(`:108-117`)가 `completeOrder`와 `notifyShipmentCompleted`를 호출한다. 순서는 다음과 같다.

1. **배송(Xhx14)**: `IN_TRANSIT`/`OUT_FOR_DELIVERY` → `DELIVERED`. (`Xth19Processor.java:113`) 전이는 `Xhx14.updateStatus`가 검사하며 `IN_TRANSIT`/`OUT_FOR_DELIVERY` 모두 DELIVERED를 허용한다. (`Xhx14.java:47-55`, `Xpb98Status.java:16-21`, `:23-27`)
2. **주문(Xdg64)**: `completeOrder`가 OrderBid를 `findByOrderId`로 조회한 뒤 `order.updateStatus(COMPLETED)`를 호출한다. (`Xhx14CommandService.java:191-205`)
3. **판매(Xgg74)**: `updateSaleStatusToSold`를 호출한다. (`:208`)
   - SaleBid의 Sale이 SOLD로 전이 가능할 때만 SOLD로 바꾼다. (`:119-123`)
   - OrderBid의 Sale에도 같은 조건을 적용한다. (`:156-160`)
   - `Xgg74Status.canTransitionTo`는 SOLD 상태에서 아무 곳으로도 갈 수 없다. (`B/domain/m10/entity/Xgg74Status.java:38`) 따라서 이미 SOLD면 건너뛴다.

**알림**
- 구매자에게 `completeOrder`가 "[completeOrder] 주문이 완료 처리되었습니다. 주문 ID: …" 1건을 보낸다. (`Xhx14CommandService.java:211-217`)
- 구매자에게 `notifyShipmentCompleted`가 "[배송 완료] 상품이 배송 완료되었습니다. 주문 ID: …" 1건을 보낸다. (`B/domain/m15/service/command/Xkh73CommandService.java:219-234`, 호출 `Xth19Processor.java:117`)
- 판매자는 Sale을 SOLD로 바꾸는 분기에 들어갔을 때만 1건(SaleBid 쪽) 또는 2건(OrderBid 쪽 추가)을 받는다. (`Xhx14CommandService.java:132-138`, `:163-169`)
- 판매자 알림은 위 분기에서만 나온다. 결제 시점에 Sale이 이미 SOLD가 됐다면(4(b) 참조) 판매자는 이 단계에서 알림을 받지 못한다.
- 구매자 합계는 **2건**이다.

**입찰(OrderBid·SaleBid) 상태**
- 이 경로에서는 바뀌지 않는다. OrderBid와 SaleBid를 COMPLETED로 바꾸는 `updateOrderAndSaleBidStatusToCompleted`는 `updateTrackingInfo`(`:289`)에서만 호출되고, `completeOrder`와 `Xth19Processor`는 호출하지 않는다.
- 배송 완료 후에도 두 입찰은 `MATCHED`로 남는다. 메서드 이름과 달리 "배송 완료 시 입찰 COMPLETED"는 실행되지 않는다.
- 참고: `updateAndCheckShipmentStatus`도 DELIVERED 시 `completeOrder`만 호출한다. (`:489`)

## 4. 주문 종류별 차이

두 경우 모두 배송이 `IN_TRANSIT`/`OUT_FOR_DELIVERY`이고 운송장이 있어야 배치 대상이 된다. 1-3에서 봤듯이 운송장 등록 API(PATCH)로는 어느 쪽도 그 상태가 되지 않는다. 배송이 IN_TRANSIT이 되는 길은 `check-status` API(`:452-516`)가 택배사 결과가 "배송완료"가 아닐 때 `shipment.updateTrackingInfo`만 반영하고 커밋하는 경우뿐이다. 이 경로는 주문 상태를 건드리지 않는다. 아래는 배송이 그렇게 IN_TRANSIT이 되어 배치에 잡혔다고 가정한 결과다.

### (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문 → 끝까지 진행되지 않는다
1. 주문 상태는 `PREPARING`이다. (1-3 참조)
2. 프로세서가 DELIVERED로 판정하면 `shipment.updateStatus(DELIVERED)`는 통과한다. (`Xth19Processor.java:113`)
3. `completeOrder`에서 `order.updateStatus(COMPLETED)`가 `PREPARING → COMPLETED`를 시도한다. 이 전이는 허용되지 않아 `Xxc76StatusException`이 발생한다. (`Xdg64Status.java:26`, `Xdg64.java:117`, 호출 `Xhx14CommandService.java:204`)
4. 설령 상태 전이를 통과해도 다음에서 막힌다. 일반 구매 입찰에는 `order_id`가 걸린 SaleBid가 없다. `saleBidQueryService.findByOrderId`는 null을 반환하지 않고 `IllegalArgumentException`을 던진다. (`B/domain/m10/service/query/Xzz58QueryService.java:26-28`) 이 호출은 `if (saleBid != null)` 앞의 try 밖에서 실행된다. (`Xhx14CommandService.java:116`)
   - SaleBid에 order가 걸리는 곳은 즉시 구매(`Xdg64CommandService.java:279`)와 즉시 판매(`B/domain/m10/service/command/Xzz58CommandService.java:83`) 두 곳뿐이다.
5. `completeOrder`의 `catch (Exception)`이 `Xpb98Exception(ORDER_NOT_FOUND_FOR_SHIPMENT)`로 감싸 던진다. (`Xhx14CommandService.java:221-227`)
6. 결과: 해당 배송 건은 skip되고 롤백된다. 배송 DELIVERED는 저장되지 않고 IN_TRANSIT, 주문은 PREPARING, 입찰은 MATCHED로 남는다. 알림은 0건이다. 다음 6시간 주기에 같은 이유로 또 실패한다.

### (b) 즉시 구매로 만들어진 주문 → 끝까지 진행된다
1. 주문 상태는 `PENDING_PAYMENT`다. `createInstantOrder`는 PENDING_PAYMENT로 만들고(`Xdg64CommandService.java:241-245`), 결제 처리(`processPayment`)는 주문 상태를 바꾸지 않는다. 이후 주문 상태를 바꾸는 코드도 없다.
   - 배송(Xhx14)은 `PENDING`으로 생성된다. (`Xdg64CommandService.java:264`)
2. `PENDING_PAYMENT → COMPLETED`가 허용 전이다. (`Xdg64Status.java:24`) 따라서 `completeOrder`의 `order.updateStatus(COMPLETED)`가 통과한다.
3. OrderBid는 존재한다. 즉시 구매 시 `createInstantOrderBid`가 `order`를 연결해 만든다. (`B/domain/m16/service/command/Xzj27CommandService.java:189-206`) 따라서 `findByOrderId`가 성공한다. (`Xzj27QueryService.java:51-55`)
4. SaleBid도 order에 연결돼 있다. (`Xdg64CommandService.java:279`)
5. Sale은 결제 시점에 이미 SOLD가 되어 있다. `processPayment` → `notifyUsersAndUpdateSaleStatus`가 SaleBid로 Sale을 찾아 `sale.updateStatus(SOLD)`를 무전이검사로 호출한다. (`B/domain/m06/service/command/Xbf54CommandService.java:83`, `:383-405`) SOLD는 더 전이할 수 없으므로 `updateSaleStatusToSold`의 두 분기는 모두 건너뛴다. (`Xhx14CommandService.java:119`, `:156`)
6. 결과:
   - 배송 DELIVERED, 주문 COMPLETED.
   - 구매자 알림 2건("[completeOrder] …", "[배송 완료] …").
   - 이 단계의 판매자 알림은 0건. 판매자는 결제 시점에 "구매자가 결제를 완료하였습니다"를 이미 받았다. (`Xbf54CommandService.java:447-455`)
   - OrderBid와 SaleBid는 MATCHED로 남는다.

### 차이 요약
| | (a) 일반 구매 입찰 (PREPARING) | (b) 즉시 구매 (PENDING_PAYMENT) |
|---|---|---|

## 5. 실패 처리 (주기 처리 중 한 건 실패)

1. 프로세서는 예외를 모두 `Xpb98Exception`으로 바꿔 던진다. (`Xth19Processor.java:133-146`)
2. 스텝은 fault-tolerant이고 `.skip(Exception.class).skipLimit(50)`이다. (`Xqv91JobConfig.java:75-77`) 한 건이 실패해도 잡 전체는 중단되지 않고 그 건만 skip된다.
3. skip된 건은 `onSkipInProcess`가 ERROR 로그만 남긴다. (`Xqv91JobConfig.java:255-266`)
   - 처리 중 변경분은 청크 트랜잭션에서 롤백된다. `completeOrder`는 `@Transactional`이라 청크 트랜잭션에 참여하며, 예외로 롤백 대상이 된다.
   - 실패한 건은 DB상 IN_TRANSIT/OUT_FOR_DELIVERY 그대로여서 다음 주기(6시간 뒤)에 같은 조회 대상으로 다시 잡힌다.
4. 나머지 건은 정상 처리된다. Spring Batch 기본 동작상 skip 가능한 예외가 나면 청크를 롤백하고 항목별로 재처리하며, 실패 항목만 건너뛰고 writer(`JpaItemWriter`, `:241-246`)가 성공 건을 저장한다.
5. skip이 50건을 넘으면 스텝이 실패해 남은 건은 그 회차에서 처리되지 않는다. (`:77`)
6. 읽기 쪽은 상태 조건을 거는 페이징 쿼리이고 정렬이 없다. 처리 중 상태가 바뀌면 페이지 오프셋이 어긋나 일부가 그 회차에서 빠질 수 있다. 다음 회차에 다시 잡힌다. (`:91-96`)
7. 건별 try/catch로 "실패 건만 건너뛰는" 구조를 가진 코드는 미사용인 `Xhx14CommandService.updateShipmentStatuses`(`:322-388`)이고, 실제 경로는 위 Batch skip 방식이다.
