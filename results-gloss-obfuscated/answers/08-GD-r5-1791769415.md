# 구매자 배송: 운송장 등록 → 배송 완료 (코드 조사 결과)

경로 접두어: `B = src/main/java/com/fream/back`. 타입 이름은 코드 이름 그대로 쓴다. Xhx14 = 구매자 배송(OrderShipment), Xdg64 = 주문(Order), Xzj27 = 구매 입찰(OrderBid), Xzz58 = 판매 입찰(SaleBid), Xgg74 = 판매(Sale).

## 결론 요약
- 운송장 등록 API(`PATCH /shipments/order/{id}/status`)는 의도대로라면 배송→주문→알림→판매→입찰 순으로 바꾸지만, **결제·배송 처리를 마친 실배송 일반 구매 입찰 주문(PREPARING)에서는 주문 상태 전환 단계에서 반드시 실패**한다. 저장되는 것은 없고(롤백), 응답은 404 / `S001`이다.
- 배송 완료 감지는 `Xpb98BatchScheduler`의 6시간 주기 Spring Batch 잡이며, 실제 실행 코드는 `Xth19Processor`(Playwright)이다.
- 완료 판정(`completeOrder`)은 즉시 구매 주문(b)에서는 끝까지 진행되지만, 실배송 일반 구매 입찰 주문(a)은 주문이 PREPARING이라 COMPLETED 전환이 막혀 실패한다. 이때 그 건은 skip되고 나머지 건은 정상 처리된다.

## 1. 운송장 등록 요청

### 1-1. 진입 API
1. `PATCH /shipments/order/{shipmentId}/status`, 본문은 `Xhx14RequestDto`(courier, trackingNumber). 근거: `B/domain/m12/controller/command/Xhx14CommandController.java:20`, `:33-45`.
2. 컨트롤러는 `Xhx14CommandService.updateTrackingInfo`를 호출하고 성공하면 200 빈 본문을 반환한다. 근거: `Xhx14CommandController.java:41-48`. 컨트롤러에 try/catch가 없어 예외는 전역 핸들러로 간다.
3. 비슷한 진입점으로 `POST /shipments/order/{id}/check-status`와 `/check-status-string`(운송장 등록 + CJ 즉시 조회)이 있다. 근거: `Xhx14CommandController.java:58`, `:103`. 이 경로는 주문 상태를 IN_TRANSIT으로 바꾸지 않고 배송 상태만 바꾼다(`Xhx14CommandService.java:473-497`).

### 1-2. 상태가 바뀌도록 짜인 순서와 알림 (`Xhx14CommandService.updateTrackingInfo`, `B/domain/m12/service/command/Xhx14CommandService.java:238-300`)
1. 택배사·운송장이 비어 있으면 `TRACKING_INFO_REQUIRED`로 거절한다 (`:244-246`).
2. 배송 조회 후 `shipment.updateTrackingInfo(courier, trackingNumber)`. 엔티티 안에서 택배사·운송장을 넣고 **배송 상태를 곧바로 IN_TRANSIT으로 세팅**한다 (`:256`, `B/domain/m12/entity/Xhx14.java:41-45`). 이 메서드는 전환 검증을 하지 않는다.
3. `order.updateStatus(Xdg64Status.IN_TRANSIT)`: 주문 상태 IN_TRANSIT (`:259-260`).
4. **구매자**에게 알림 "상품이 출발하였습니다. 주문 ID: …" (`:266-271`, 카테고리 SHOPPING, 타입 BID).
5. `updateSaleStatusToSold(orderId)` (`:274`, 본체 `:111-180`).
   - 판매 입찰(Xzz58)이 연결돼 있고 판매가 SOLD로 전환 가능하면 Xgg74를 SOLD로 바꾸고 (`:121-123`), 창고 보관이면 창고 상태를 갱신하며 (`:126-129`), **판매자**에게 "상품이 성공적으로 판매 완료되었습니다. 판매 ID: …" 알림을 보낸다 (`:133-138`).
   - 이어서 구매 입찰(Xzj27)의 판매(Xgg74)가 SOLD로 전환 가능하면 같은 SOLD 변경과 판매자 알림을 한 번 더 수행한다 (`:151-170`).
6. 판매 입찰의 판매가 창고 보관이면 창고 상태를 한 번 더 갱신한다 (`:279-285`).
7. `updateOrderAndSaleBidStatusToCompleted`: 구매 입찰·판매 입찰이 MATCHED이면 COMPLETED로 바꾼다 (`:289`, `:412-437`). 이 메서드는 `private`이라 `@Transactional`이 적용되지 않고(self-invocation), 내부 예외는 로그만 남기고 삼킨다 (`:436-438`).
8. 메서드 이름·로그는 "배송 중 처리"처럼 보이지만 실제로는 운송장 등록 시점에 판매를 SOLD로, 입찰을 COMPLETED로까지 바꾸려는 코드다.

### 1-3. (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문 → 끝까지 성공하지 못한다
1. 이 주문의 상태는 PREPARING이다.
   - 입찰에서 주문이 만들어질 때는 PENDING_PAYMENT (`B/domain/m16/service/command/Xdg64CommandService.java:81`).
   - `processPaymentAndShipment`는 결제·배송지 처리 후 실배송(창고 보관 아님)이면 PAYMENT_COMPLETED → PREPARING까지만 올린다 (`Xdg64CommandService.java:174-176`). Kafka 경로도 PREPARING에서 멈춘다 (`B/domain/m16/service/kafka/Xdg64EventConsumer.java:195-219`).
   - 결제 서비스는 주문 상태를 바꾸지 않는다 (`B/domain/m06/service/command/Xbf54CommandService.java`에 `Xdg64Status` 사용이 없음).
2. 허용 전이표에서 `PREPARING → {IN_WAREHOUSE, SHIPMENT_STARTED}`만 가능하다 (`B/domain/m16/entity/Xdg64Status.java:26`). IN_TRANSIT은 SHIPMENT_STARTED에서만 갈 수 있다 (`:28`). SHIPMENT_STARTED로 올리는 코드는 어디에도 없다.
3. 실패 지점: `order.updateStatus(Xdg64Status.IN_TRANSIT)` (`Xhx14CommandService.java:260`). `Xdg64.updateStatus`가 허용되지 않은 전환이라 `Xxc76StatusException`을 던진다 (`B/domain/m16/entity/Xdg64.java:113-120`).
4. 이 예외는 `updateTrackingInfo`의 `catch (Exception e)`에 잡혀 `Xpb98Exception(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")`로 바뀌어 다시 던져진다 (`Xhx14CommandService.java:295-301`).
5. 저장되는 것은 **없다**.
   - `Xpb98Exception`은 `RuntimeException`이고 (`B/global/exception/Xks43Exception.java:10`), `updateTrackingInfo`가 `@Transactional`이므로 전체가 롤백된다 (`:238`).
   - 2단계에서 메모리상 바꾼 배송의 courier·trackingNumber·IN_TRANSIT은 DB에 남지 않는다. 배송은 PENDING, 주문은 PREPARING 그대로이다.
   - 4번 구매자 알림 이후 코드에 도달하지 못하므로 알림도 없다. 실패가 알림보다 앞이다 (`:260` < `:266`).
6. 응답은 **HTTP 404**, 본문은 `ErrorResponse(code="S001", message="배송 정보를 찾을 수 없습니다.", status=404, path)`이다.
   - 오류 코드: `B/domain/m12/exception/Xpb98ErrorCode.java:12`.
   - 전역 핸들러가 `e.getMessage()`가 아니라 코드 기본 메시지를 쓴다 (`B/global/exception/Xks43ExceptionHandler.java:49-63`).
   - 실제 원인은 "배송을 못 찾음"이 아니라 주문 상태 전환 불가인데, 에러 코드가 잘못 붙어 있다.
7. 참고(잠재적 두 번째 실패 지점): 주문에 판매 입찰(Xzz58)이 연결돼 있지 않으면 `saleBidQueryService.findByOrderId`가 null이 아니라 `IllegalArgumentException`을 던진다 (`B/domain/m10/service/query/Xzz58QueryService.java:26-28`). 이 호출은 `updateSaleStatusToSold`에서 try 밖이다 (`Xhx14CommandService.java:116`). 그래서 `if (saleBid != null)` 체크는 의미가 없다.

## 2. 배송 완료 감지

### 2-1. 누가·언제·어떻게
1. 주체는 스케줄러 `Xpb98BatchScheduler.scheduleShipmentStatusJob`이다. 사람이나 택배사 콜백이 아니라 서버가 CJ대한통운 조회 화면을 주기적으로 긁어(polling) 감지한다. 근거: `B/global/config/Xpb98BatchScheduler.java:34-44`.
2. 주기: `@Scheduled(cron = "0 0 */6 * * *")`, 즉 **6시간마다 정각(00·06·12·18시, 서버 시간대)** (`:34`). `jobParameters`에 timestamp를 넣어 매번 새 잡으로 실행한다 (`:37-40`). 스케줄링은 `@EnableScheduling`이 다른 설정 클래스들에 선언돼 앱 전역으로 켜지며, 배치는 `@EnableBatchProcessing` (`B/global/config/Xct70Config.java:15`).
3. 잡 구성: `updateShipmentStatusesJob` → `updateShipmentStatusesStep`, chunk 50, faultTolerant, `skip(Exception.class)`, skipLimit 50 (`B/domain/m12/config/Xqv91JobConfig.java:55-82`, `:67`, `:75-77`).

### 2-2. 조회 대상
- `SELECT s FROM Xhx14 s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL`, JpaPagingItemReader, pageSize 50 (`Xqv91JobConfig.java:89-96`). PENDING이나 운송장이 없는 배송, 이미 DELIVERED인 배송은 조회하지 않는다.

### 2-3. 실제로 실행되는 처리 코드
비슷한 코드가 세 곳 있다.

| 위치 | 실제 사용 여부 |
|---|---|
| `Xth19Processor.process` (`B/domain/m12/config/Xth19Processor.java:57-146`) | **사용됨.** 스텝이 `new Xth19Processor(...)`를 processor로 등록한다 (`Xqv91JobConfig.java:69-73`). |
| `Xqv91JobConfig.shipmentItemProcessor()` 빈 (`:106-177`) 및 `parseCjLogisticsStatus` (`:186`) | 스텝에 연결되지 않아 **사용되지 않음**. |
| `Xhx14CommandService.updateShipmentStatuses()` (`Xhx14CommandService.java:308-396`) | 호출처가 없다 (전체 검색 결과). **사용되지 않음.** |

실제 실행 흐름(`Xth19Processor.process`):
1. 운송장이 없으면 `TRACKING_NUMBER_INVALID` (`:61-64`).
2. `browserManager.newPage()`로 Playwright 페이지를 열고 (`:72`) `https://trace.cjlogistics.com/next/tracking.html?wblNo=<운송장>`으로 이동해 `tbody#statusDetail tr`이 뜰 때까지 기다린다 (`:36-37`, `:80-87`). 브라우저는 스텝 시작·종료 때 `Xmb36Listener`가 열고 닫는다 (`B/domain/m12/config/Xmb36Listener.java:13-24`, `Xqv91JobConfig.java:80`).
3. 마지막 행의 5번째 `td` 텍스트를 상태 문자열로 쓴다 (`Xth19Processor.java:181`).
4. 매핑 후, 같은 상태면 그대로 반환한다 (`:101-105`).
5. DELIVERED이면 배송 상태 DELIVERED로 바꾸고 → `orderService.completeOrder(orderId)` → `notificationService.notifyShipmentCompleted(order)` 순으로 실행한다 (`:108-118`).
6. OUT_FOR_DELIVERY이면 배송 상태 OUT_FOR_DELIVERY, 그 밖이면 IN_TRANSIT으로 바꾼다 (`:119-126`).
7. 결과는 `JpaItemWriter`로 저장한다 (`Xqv91JobConfig.java:141-146`).

### 2-4. 택배사 상태 문자열 → 내부 상태 (`Xth19Processor.mapToShipmentStatus`, `:220-225`)
- `"배송완료"` → `DELIVERED`
- `"배송출발"` → `OUT_FOR_DELIVERY`
- **그 외 모든 문자열**(집하, 간선상차, 배송중 등) → `IN_TRANSIT`
- 정확히 일치(equals)하는 문자열만 인식한다. 앞뒤 공백만 trim한다 (`:181`).
- 이후 `Xhx14.updateStatus`가 전환표(`B/domain/m12/entity/Xpb98Status.java:16-34`)로 검증한다. 예를 들어 OUT_FOR_DELIVERY에서 IN_TRANSIT으로 되돌아가는 전환은 허용되지 않아 `IllegalStateException`이 나고, 그 건은 오류(skip)로 처리된다 (`Xhx14.java:47-55`).

## 3. 배송 완료 판정 이후

`Xth19Processor.java:108-118` → `Xhx14CommandService.completeOrder` (`:190-227`)
1. 배송(Xhx14): 상태 DELIVERED (`Xth19Processor.java:113`). 전환표상 IN_TRANSIT·OUT_FOR_DELIVERY에서 DELIVERED로 갈 수 있다 (`Xpb98Status.java:16-22`, `:23-28`).
2. `completeOrder`: 구매 입찰 `findByOrderId`가 없으면 `IllegalArgumentException` (`Xhx14CommandService.java:196-197`).
3. 주문(Xdg64): `order.updateStatus(COMPLETED)` (`:204`). 허용 전이는 IN_TRANSIT·IN_WAREHOUSE·PENDING_PAYMENT에서만 가능하다 (`Xdg64Status.java:24`, `:27`, `:29`).
4. `updateSaleStatusToSold(orderId)` (`:206`): 판매(Xgg74)를 SOLD로 바꾸려 시도하고, 전환 가능할 때만 판매자에게 "상품이 성공적으로 판매 완료되었습니다" 알림을 보낸다 (`:111-180`).
5. **구매자**에게 "[completeOrder] 주문이 완료 처리되었습니다. 주문 ID: …" 알림 (`:211-217`).
6. 메서드를 빠져나온 뒤 프로세서가 `notifyShipmentCompleted`로 **구매자**에게 "[배송 완료] 상품이 배송 완료되었습니다. 주문 ID: …"를 보낸다 (`B/domain/m15/service/command/Xkh73CommandService.java:219-234`). 이 메서드는 예외를 삼킨다 (`:230-233`).
7. 알림 건수: 구매자 2건(completeOrder 1건 + [배송 완료] 1건). 판매자는 4번 조건을 만족할 때만 최대 1~2건(판매 입찰 경로와 구매 입찰 경로 각각)이다. 아래 4(b)에서 보듯 즉시 구매 주문은 결제 때 판매가 이미 SOLD라 판매자 알림이 0건이다.
8. 주문 입찰(Xzj27)·판매 입찰(Xzz58)의 상태: **`completeOrder`와 배치 경로는 두 입찰의 상태를 건드리지 않는다.**
   - 입찰을 COMPLETED로 바꾸는 `updateOrderAndSaleBidStatusToCompleted`는 운송장 등록 경로(`updateTrackingInfo`, `Xhx14CommandService.java:289`)에서만 호출된다.
   - 따라서 배송 완료 후에도 입찰은 MATCHED로 남는다. (운송장 등록이 정상이라면 이미 COMPLETED였겠지만, 1-3에서 본 것처럼 그 경로는 막혀 있다.)

## 4. 주문 종류별 차이

### (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문 → **끝까지 진행되지 않음**
1. 주문 상태 PREPARING (1-3의 근거 `Xdg64CommandService.java:174-176`).
2. 배송이 IN_TRANSIT/OUT_FOR_DELIVERY가 되려면 운송장 등록 API(1-3에서 실패해 롤백)가 아니라 `check-status` 계열을 통해야 한다. 이 경로는 주문 상태를 건드리지 않고 배송에 운송장·IN_TRANSIT을 저장한다 (`Xhx14CommandService.java:473-497`).
3. 이후 배치가 DELIVERED를 감지하면 `Xth19Processor`가 배송을 DELIVERED로 바꾸고(메모리) `completeOrder`를 호출한다 (`:113-116`).
4. `completeOrder`의 `order.updateStatus(COMPLETED)`에서 PREPARING → COMPLETED가 허용되지 않아 `Xxc76StatusException`이 난다 (`Xdg64Status.java:26`, `Xdg64.java:113-120`, `Xhx14CommandService.java:204`).
5. `completeOrder`는 이를 `Xpb98Exception(ORDER_NOT_FOUND_FOR_SHIPMENT)`로 감싸 던진다 (`:221-227`).
6. 결과:
   - 배송은 DELIVERED로 저장되지 않아 IN_TRANSIT에 남고,
   - 주문은 PREPARING이며,
   - 알림은 없고(`completeOrder` 알림도 `:211` 이후라 미도달, `notifyShipmentCompleted`도 미실행),
   - 입찰·판매 상태 변경도 없다.
   - 그 배송은 다음 6시간 주기에도 다시 조회돼 같은 이유로 계속 실패한다.

### (b) 즉시 구매로 만들어진 주문 → **끝까지 진행됨**
1. `createInstantOrder`는 주문을 PENDING_PAYMENT로 만들고 (`Xdg64CommandService.java:244`), 배송을 만들고 (`:264`), 판매 입찰을 주문에 매칭하고 (`:279-283`), 결제를 처리한다 (`:305`).
   - 주문 상태는 PENDING_PAYMENT에서 올라가지 않는다. 결제 서비스도 주문 상태를 바꾸지 않는다.
   - 이어서 `Xzj27CommandService.createInstantOrderBid`가 구매 입찰(Xzj27)을 MATCHED·즉시구매로 만든다 (`B/domain/m16/service/command/Xzj27CommandService.java:133-142`, `:189-206`).
2. 결제 처리 중 `notifyUsersAndUpdateSaleStatus`가 판매 입찰 경로(구매 입찰이 아직 없으므로)로 판매를 **이미 SOLD**로 바꾸고 구매자·판매자에게 "결제가 완료되었습니다 / 구매자가 결제를 완료하였습니다" 알림을 보낸다 (`B/domain/m06/service/command/Xbf54CommandService.java:83`, `:388-406`, `:434-465`).
3. 배송 완료 판정 시 `completeOrder`가 구매 입찰을 찾고 (구매 입찰이 있으므로 성공) 주문을 PENDING_PAYMENT → COMPLETED로 바꾼다. 이 전환은 허용돼 있다 (`Xdg64Status.java:24`).
4. 판매가 이미 SOLD라 `canTransitionTo(SOLD)`가 false이므로 판매 변경과 판매자 알림은 건너뛴다 (`Xgg74Status.java:38`, `Xhx14CommandService.java:120`, `:158`).
5. 결과: 배송 DELIVERED, 주문 COMPLETED, **구매자 알림 2건**(completeOrder + [배송 완료]), 판매자 알림 0건. 구매 입찰·판매 입찰은 MATCHED 그대로이다(3의 8번).

## 5. 실패 처리 (주기 처리 중 한 건이 실패할 때)
1. 프로세서는 모든 예외를 `Xpb98Exception`으로 감싸 다시 던진다 (`Xth19Processor.java:133-145`). 스텝은 `faultTolerant().skip(Exception.class).skipLimit(50)`이다 (`Xqv91JobConfig.java:75-77`).
2. 실패한 건: skip 대상이 된다. 현재 청크 트랜잭션이 롤백되고 같은 청크를 건별로 다시 처리하면서 실패한 건만 제외한다. 이 과정에서 건별 재처리 때 CJ 조회가 다시 일어난다.
   - 실패한 건의 변경(배송 DELIVERED 등)은 저장되지 않아 이전 상태 그대로이다. 다음 주기(6시간 뒤)에 다시 조회된다.
   - `completeOrder`는 청크 트랜잭션에 참여해 실행되므로 그 예외가 트랜잭션을 롤백 전용으로 만든다.
   - `SkipListener`가 건별 로그만 남긴다 (`Xqv91JobConfig.java:252-286`).
3. 나머지 건: 영향 없이 정상 처리되어 커밋된다.
4. 한도: 한 번의 잡 실행에서 skip이 50건을 넘으면 스텝이 실패하고 남은 건은 처리되지 않는다 (`Xqv91JobConfig.java:77`).
5. 스케줄러 쪽: `jobLauncher.run` 예외는 `printStackTrace`만 하고 삼킨다 (`Xpb98BatchScheduler.java:41-43`).
6. 부가 주의: `JpaPagingItemReader`는 오프셋 기반 페이징인데 처리 중 대상(IN_TRANSIT 등)이 DELIVERED로 빠지면 다음 페이지 오프셋이 어긋나 일부 건이 이번 실행에서 건너뛰어질 수 있다 (`Xqv91JobConfig.java:89-96`). 다음 주기에 다시 조회된다.
