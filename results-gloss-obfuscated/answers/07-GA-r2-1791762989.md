# 즉시 구매 처리 흐름

경로 약어: `D` = `src/main/java/com/fream/back/domain`

- Xzj27 = OrderBid(주문 입찰), Xdg64 = Order(주문), Xzz58 = SaleBid(판매 입찰), Xgg74 = Sale(판매), Xbf54 = Payment(결제)
- Xnn94 = WarehouseStorage(창고 보관), Xhx14 = OrderShipment(주문 배송), Xhm58 = OrderItem(주문 항목)

## 1. 진입 API와 처리 단계

**API**: `POST /order-bids/instant`
- 클래스 매핑 `@RequestMapping("/order-bids")`: `D/m16/controller/command/Xzj27CommandController.java:22`
- 메서드 매핑 `@PostMapping("/instant")`, 메서드 `createInstantOrderBid`: `Xzj27CommandController.java:89-90`
- 요청 DTO(`Xpj49RequestDto` = InstantOrderRequestDto)는 `saleBidId`, `addressId`, `warehouseStorage`, `paymentRequest`를 가진다: `D/m16/dto/Xpj49RequestDto.java:20-29`

**처리 단계 (모두 동기, 하나의 트랜잭션)**
1. 컨트롤러가 JWT에서 이메일을 꺼낸다(`Xzj27CommandController.java:92`). `paymentRequest`에 `userEmail=이메일`, `orderId=null`을 채운다(`Xzj27CommandController.java:98`, `:119-123`).
2. `Xzj27CommandService.createInstantOrderBid`(`@Transactional`, `D/m16/service/command/Xzj27CommandService.java:118-149`)가 호출된다.
   - 입력 검증: `Xzj27CommandService.java:123`, `:154-167`
   - 구매자 조회: `Xzj27CommandService.java:126`
   - 판매 입찰 조회 및 검증: `Xzj27CommandService.java:129`, `:172-184`. 판매 입찰의 상태(PENDING 여부)는 검증하지 않는다.
3. `Xdg64CommandService.createInstantOrder`(`@Transactional`, `D/m16/service/command/Xdg64CommandService.java:219-319`)가 아래를 순서대로 수행한다.
   1. 배송지 조회: `Xdg64CommandService.java:238`
   2. 주문 저장(`PENDING_PAYMENT`, 금액=판매 입찰가): `Xdg64CommandService.java:241-247`
   3. 결제 요청에 orderId 주입: `Xdg64CommandService.java:250`
   4. 주문 항목 생성: `Xdg64CommandService.java:255-256`
   5. 주문 배송 생성: `Xdg64CommandService.java:264-271`
   6. 판매 입찰에 주문 연결 및 `MATCHED`, 그리고 flush: `Xdg64CommandService.java:279-283`
   7. 판매의 창고 보관 상태 갱신: `Xdg64CommandService.java:290-294`
   8. 결제 처리: `Xdg64CommandService.java:305`
4. 결제 단계(`Xbf54CommandService.processPayment`, `D/m06/service/command/Xbf54CommandService.java:57-107`)는 결제 유형별 생성 후 `notifyUsersAndUpdateSaleStatus`(`Xbf54CommandService.java:83`)를 부른다. 이 메서드가 알림 전송과 판매 `SOLD` 처리를 한다(`:383-426`).
5. 다시 `Xzj27CommandService`로 돌아와 주문 입찰(OrderBid)을 `MATCHED` / `isInstantPurchase=true`로 만들어 저장한다: `Xzj27CommandService.java:142`, `:189-206`.

**동기/비동기**: 동기 처리다.
- 응답 전에 모든 DB 작업과 PortOne HTTP 호출(`RestTemplate.exchange`)이 끝난다: `D/m06/p05/Xxv33ApiClient.java:266`.
- `@Async`, `@EventListener`, 메시지 큐는 없다. 알림도 같은 호출 스택에서 직접 저장·전송한다(4번 참고).

**응답 ID**: **주문 입찰(Xzj27 = OrderBid)의 ID**다. 주문(Xdg64) ID가 아니다.
- `createInstantOrderBid(...)`가 반환한 `Xzj27`에 `.getId()`를 호출한다: `Xzj27CommandController.java:101-107`.
- 변수명이 `orderId`지만 실제 값은 OrderBid ID다. 응답은 `ResponseDto<Long>` 형태로, 메시지는 "즉시 구매가 성공적으로 처리되었습니다."다: `Xzj27CommandController.java:109`.

세부 사항:
- 4번 판매 입찰은 `assignOrder`와 `updateStatus(MATCHED)`를 모두 호출하며, 결과는 `MATCHED`다. 판매 입찰 enum은 `PENDING/MATCHED/CANCELLED/COMPLETED`다(`D/m10/entity/Xtz73Status.java`).
- 5번은 `sale.isWarehouseStorage()`가 true일 때만 실행된다. 이 값은 **판매자의 판매**에 붙은 플래그다(`D/m10/entity/Xgg74.java:43`).
- 7번에서 주문 입찰(OrderBid)은 아직 만들어지기 전이다(주문 입찰은 `Xzj27CommandService.java:142`에서 생성). 그래서 `order.getOrderBid()`는 null이고, `saleBidQueryService.findByOrderId`로 판매 입찰을 찾아 판매를 얻는다(`Xbf54CommandService.java:388-407`). 판매 입찰에 주문이 이미 연결·flush되어 있어서 조회가 가능하다(`Xdg64CommandService.java:279-283`).
- 7번 `Xgg74.updateStatus`는 전이 검증이 없다(`D/m10/entity/Xgg74.java:73-75`). 판매의 현재 상태와 무관하게 `SOLD`가 된다.
- 9번 주문 입찰은 `assignOrder` 안에서 `MATCHED`가 되고, 주문 쪽 `orderBid`도 연결된다(`Xzj27.java:74-81`).

**주문 상태는 즉시 구매 경로에서 한 번도 바뀌지 않는다.** `PENDING_PAYMENT`로 저장된 뒤 `createInstantOrder` 안에서 `order.updateStatus(...)` 호출이 없다(`Xdg64CommandService.java:219-319`). `processPaymentAndShipment`(`:111-202`)는 다른 경로(Xrt49 = PayAndShipment)에서만 쓰인다.

## 3. 결제 수단별 결과

분기: `requestDto.getResolvedPaymentType()`의 switch, `Xbf54CommandService.java:67-80`. DTO는 `paymentType` 프로퍼티로 다형 역직렬화된다(`D/m06/dto/Xbf54RequestDto.java:20-25`).

| 수단 | 처리 | 결제 상태 / isSuccess | 근거 |
|------|------|----------------------|------|
| CARD | 저장된 결제 수단 정보 조회 후 PortOne API로 카드 결제 | 응답 `status`가 `"success"`일 때만 `PAID` / true. 그 외는 `PENDING` / false | `Xbf54CommandService.java:166-208` |
| ACCOUNT | 은행명 검증만 하고 외부 호출 없음. 계좌 결제 저장 | 항상 `PENDING` | `Xbf54CommandService.java:244-262` |
| GENERAL | 클라이언트가 보낸 `impUid`를 그대로 신뢰해 저장 (외부 검증 없음) | 즉시 `PAID` / true | `Xbf54CommandService.java:297-316` |

**즉시 구매는 끝까지 성공하는가?** 세 수단 모두, 예외가 없으면 같은 경로를 끝까지 간다. 그 후 판매 `SOLD`, 알림 2건, 주문 입찰 `MATCHED`까지 진행하고 HTTP 200을 돌려준다. 결제 상태와 무관하다.
- 계좌이체는 `PENDING`인데도 알림("결제가 완료되었습니다")과 판매 `SOLD`가 실행된다. `notifyUsersAndUpdateSaleStatus`가 결제 상태를 확인하지 않는다(`Xbf54CommandService.java:83`, `:383-426`).
- 카드도 응답 `status`가 `"success"`가 아니면(PortOne 실제 응답값은 보통 `"paid"`) 결제는 `PENDING`/미성공으로 저장되고, 위와 같이 끝까지 진행한다(`Xbf54CommandService.java:203-206`).
- 요청의 `paidAmount`가 판매 입찰가와 같은지는 검증하지 않는다. `paidAmount > 0`만 확인한다(`Xbf54CommandService.java:142-145`). DTO에는 `@Min(100)`이 있다(`Xbf54RequestDto.java:50-52`).
- 주문 상태는 어느 경우에도 `PENDING_PAYMENT`로 남는다(2번 참고).

**PortOne이 카드 결제를 실패로 응답하면**
1. HTTP 상태가 200이 아니거나 `code != 0`이면 `Xdf64Exception("카드 결제 요청 실패: ...")`을 던진다(`Xxv33ApiClient.java:270-275`).
2. 이 예외는 `Xbf54Exception` 하위 클래스(`D/m06/exception/Xdf64Exception.java:6`)이므로 그대로 재던져진다(`Xxv33ApiClient.java:286-287`, `Xbf54CommandService.java:180-181`, `:218-219`, `:89-94`).
3. `@Retryable`은 `Xbf54ApiException`만 대상이므로 재시도하지 않는다(`Xxv33ApiClient.java:224-228`). 통신 오류(`RestClientException`)는 `Xbf54ApiException`이 되어 최대 3회 재시도된다(`:288-290`).
4. 호출 측에서 `Xqj91Exception`(OrderPaymentProcessingFailed)으로 감싸 던진다(`Xdg64CommandService.java:305-309`). 이 예외는 바깥 catch에서 그대로 재던져지고(`:312-314`), `Xzj27CommandService`의 `handleOrderBidCreationException`도 그대로 재던진다(`Xzj27CommandService.java:212-215`).
5. 결과: 외부 트랜잭션이 롤백된다. 주문, 주문 항목, 배송, 판매 입찰 `MATCHED`, 창고 상태 변경이 모두 취소된다. 주문 입찰은 아직 생성 전이다. 알림도 저장되지 않는다. 클라이언트는 오류 응답을 받는다.
6. 카드 응답이 성공 코드(`code==0`)인데 `status`가 `"success"`가 아니면 위 경로가 아니다. 예외 없이 `PENDING` 결제로 저장되고 끝까지 진행된다(위 설명).

## 4. 알림

- **구매자**: "결제가 완료되었습니다. 주문 ID: {orderId}"
- **판매자**(`sale.getSeller()`): "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}"
- 둘 다 카테고리 `SHOPPING`, 타입 `BID`: `Xbf54CommandService.java:438-454`
- 즉시 구매 요청 한 건당 구매자 1건, 판매자 1건이다.
- 결제가 `PENDING`(계좌이체 등)이어도 전송된다(3번 참고).

**언제**: 결제 레코드 저장 직후, 같은 요청 스레드·같은 트랜잭션 안에서다. 판매 `SOLD` 갱신 직전에 보낸다(`Xbf54CommandService.java:83`, `:403-404`, `:416-419`).

**어떤 방식**: `Xkh73CommandService.createNotification`(`D/m15/service/command/Xkh73CommandService.java:44-67`)이 처리한다.
1. DB에 알림 엔티티를 저장한다(`:52-53`).
2. 실시간 전송 `sendRealTimeNotification`(`:57`, `:104-124`)을 호출한다. Redis 키 `WebSocket:Xrd81:{email}`가 있을 때만(접속 중일 때만) `messagingTemplate.convertAndSendToUser(email, "/queue/notifications", dto)`로 WebSocket(STOMP) 전송한다. 키가 없으면 DB 저장만 하고 건너뛴다(`:108-123`).
3. 푸시, 이메일, 메시지 큐는 없다. 전송 실패는 로그만 남기고 삼킨다(`Xkh73CommandService.java:116-120`, `Xbf54CommandService.java:457-461`).
4. 알림 전송 단계 전체가 try/catch로 감싸져 있어 예외가 나도 결제는 실패하지 않는다(`Xbf54CommandService.java:421-425`). `sendNotifications`에도 자체 catch가 있어서(`:457-461`) 알림 오류가 나도 이어지는 `sale.updateStatus(SOLD)`는 실행된다.

## 5. 최종 상태와 창고 보관

**처리 종료 시 주문(Xdg64)의 최종 상태는 `PENDING_PAYMENT`다.**
- 즉시 구매 경로 어디에서도 주문 상태를 올리지 않는다(`Xdg64CommandService.java:219-319`, `Xbf54CommandService.java:57-107`, `Xzj27CommandService.java:118-207`).
- 메서드명(`createInstantOrder`)이나 알림 문구("결제가 완료되었습니다")와 달리, `PAYMENT_COMPLETED`나 `PREPARING`, `COMPLETED`로 가지 않는다.
- 다른 엔티티의 최종 상태는 다음과 같다. 주문 입찰 `MATCHED`, 판매 입찰 `MATCHED`, 판매 `SOLD`, 배송 `PENDING`, 결제는 수단별(카드 `PAID` 또는 `PENDING`, 계좌 `PENDING`, 일반 `PAID`).

**구매자가 "창고 보관"을 선택한 경우**
- 요청의 `warehouseStorage` 값은 컨트롤러 로그와 서비스 인자 전달에만 쓰이고(`Xzj27CommandController.java:94-95`, `:101-106`), `createInstantOrder` 안에서는 사용되지 않는다(`Xdg64CommandService.java:220-319`에 해당 변수 참조 없음). 따라서 **구매자의 선택은 아무것도 바꾸지 않는다.**
- 구매자 창고 보관 용도인 `Xnn94CommandService.createOrderStorage`, 주문 상태 `IN_WAREHOUSE`·`COMPLETED` 전이는 `processPaymentAndShipment`(`Xdg64CommandService.java:163-172`)에만 있다. 즉시 구매 경로에서는 호출되지 않는다. 결과적으로 주문에는 `warehouseStorage`가 연결되지 않고 새 창고 보관 레코드도 만들어지지 않는다.
- 창고 관련 동작은 구매자 선택이 아니라 **판매 쪽 플래그** `sale.isWarehouseStorage()`로만 결정된다. 판매자가 창고 보관을 선택했다면 기존 창고 보관 레코드를 `ASSOCIATED_WITH_ORDER`로 바꾼다(`Xdg64CommandService.java:290-294`). 구매자가 어떤 값을 보내든 주문에는 일반 배송 정보(`PENDING`)가 생성된다.
