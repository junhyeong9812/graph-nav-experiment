# 즉시 구매 처리 흐름

경로 약어: `D` = `src/main/java/com/fream/back/domain`

## 1. API, 처리 단계, 동기/비동기, 응답 ID

**API**: `POST /order-bids/instant` (`D/m16/controller/command/Xzj27CommandController.java:22`, `:89`). 요청 본문은 `Xpj49RequestDto`(saleBidId, addressId, warehouseStorage, paymentRequest) (`D/m16/dto/Xpj49RequestDto.java:20-29`).

**처리 단계 (모두 한 요청 스레드, 한 트랜잭션 안에서 순차 실행)**

1. 컨트롤러가 로그인 이메일을 꺼내고(`Xzj27CommandController.java:92`), 결제 요청에 구매자 이메일을 넣고 `orderId`를 null로 비운다(`:98`, `:119-123`).
2. `Xzj27CommandService.createInstantOrderBid`(`D/m16/service/command/Xzj27CommandService.java:241-243`, 파일 내 줄 번호 기준 `@Transactional`은 241, 메서드는 242)가 입력을 검증하고(`:246`, `:277-290`), 구매자와 판매 입찰을 조회한다(`:249`, `:252`, `:295-307`).
3. `Xdg64CommandService.createInstantOrder`(`D/m16/service/command/Xdg64CommandService.java:219-221`)를 호출한다. 내부 순서:
   1. 배송지 조회(`:238`)
   2. 주문 생성·저장(`:241-247`)
   3. 결제 요청에 주문 ID 세팅(`:250`)
   4. 주문 항목 생성(`:255-256`)
   5. 주문 배송 생성(`:264-271`)
   6. 판매 입찰 매칭(`:279-283`)
   7. 판매자 창고 상태 변경(`:291-294`)
   8. 결제 처리(`:305`)
4. 서비스가 `Xzj27`(주문 입찰)을 새로 만들어 저장한다(`Xzj27CommandService.java:265`, `:312-330`).
5. 컨트롤러가 응답한다(`Xzj27CommandController.java:101-109`).

**동기/비동기**: 완전히 동기다. Kafka 이벤트를 발행하지 않고 결제 대행사(PortOne) 호출도 같은 스레드에서 실행한다(`D/m06/p05/Xxv33ApiClient.java:229-285`).
Kafka(`order-processing-topic`)를 쓰는 비동기 경로는 별도 컨트롤러 `Xdg64CommandController`(`D/m16/controller/command/Xdg64CommandController.java:54`)에서만 발행된다. 즉시 구매는 이 경로를 타지 않는다.

**응답 ID**: 응답 값은 `orderId`라는 변수명이지만 실제로는 **주문 입찰(Xzj27)의 ID**다. `createInstantOrderBid(...)`가 `Xzj27`을 반환하고 컨트롤러가 그 `.getId()`를 쓴다(`Xzj27CommandController.java:101-107`). 주문(Xdg64)의 ID가 아니다. 메시지는 "즉시 구매가 성공적으로 처리되었습니다."(`:109`)다.

| 4 | 판매 입찰 `Xzz58`에 주문 연결, 상태 변경 후 flush | 판매 입찰 `MATCHED` | `Xdg64CommandService.java:279-283`, `D/m10/entity/Xzz58.java:58-61` |

- 주문 상태는 1번 이후 **한 번도 바뀌지 않는다**. `createInstantOrder`에는 `updateStatus` 호출이 없고(`Xdg64CommandService.java:219-319`), 결제 서비스도 주문 상태를 건드리지 않는다.
- 6번에서 sale은 `Xgg74Status.SOLD`가 된다(`Xbf54CommandService.java:404`, `:419`). `updateStatus`는 전환 검증 없이 값을 덮어쓴다(`D/m10/entity/Xgg74.java:73-75`).

- 7번의 주문 입찰 상태는 빌더에서 `MATCHED`로 주고(`Xzj27CommandService.java:319`), `assignOrder`에서도 `MATCHED`로 세팅된다(`Xzj27.java:75`).

## 3. 결제 수단별 결과, 성공 여부, 카드 실패 시

결제 수단은 DTO의 `paymentType`(CARD/ACCOUNT/GENERAL)으로 분기한다(`D/m06/dto/Xbf54RequestDto.java:20-25`, `:74-86`; `Xbf54CommandService.java:67-80`). 금액 검증은 `paidAmount > 0`뿐이며(`:142-145`) 판매 입찰가와 비교하지 않는다.

| 수단 | 처리 | 결제 상태 / isSuccess | 근거 |
|---|---|---|---|
| 카드 | 저장된 결제정보 조회 후 PortOne 호출 | 응답 `status`가 문자열 `"success"`일 때만 `PAID` + `isSuccess=true`. 그 외에는 `PENDING`, `false`인 채로 저장 | `Xbf54CommandService.java:164-208` |
| 계좌이체 | 은행명만 검증, 외부 호출 없음 | `PENDING`, `isSuccess=false` | `:236-262`, `:470-488` |
| 일반 결제 | `impUid`만 확인하고 그대로 신뢰 | 즉시 `PAID`, `isSuccess=true` | `:290-316` |

**즉시 구매가 끝까지 성공하는가**: 요청 자체는 예외 없이 끝나면 HTTP 200으로 성공한다. 그러나 이후 단계를 거치므로 "결제 완료까지 간다"는 뜻은 아니다.
- 결제 결과(성공 여부)를 확인하는 코드가 없다. `createInstantOrder`는 `processPayment`의 반환값을 버린다(`Xdg64CommandService.java:305`). 반면 Kafka 경로는 `payment.isSuccess()`를 확인한다(`D/m16/service/kafka/Xdg64EventConsumer.java:171-176`).
- 계좌이체는 `PENDING`인 채로, 주문은 `PENDING_PAYMENT`인 채로 성공 응답이 나가고 sale은 `SOLD`가 된다(`Xbf54CommandService.java:404`, `:419`).
- 카드도 응답 `status`가 `"success"`가 아니면 같은 상태가 된다. 즉 PortOne 응답이 코드 0이면서 `status`가 다른 값(예: 실제 PortOne의 `paid`)이면 결제는 `PENDING`으로 남는다(`:203-206`).

**결제 대행사가 카드 결제를 실패로 응답하면**: HTTP 상태가 200이 아니거나 `code != 0`이면 `Xdf64Exception("카드 결제 요청 실패: ...")`을 던진다(`Xxv33ApiClient.java:270-274`).
- 이 예외는 `createCardPayment`와 `processPayment`에서 그대로 전파된다(`Xbf54CommandService.java:89-94`, `:218-219`). `Xdf64Exception`은 `Xbf54Exception`의 하위 클래스다(`D/m06/exception/Xdf64Exception.java:6`).
- `createInstantOrder`가 이를 `Xqj91Exception`으로 감싸 던진다(`Xdg64CommandService.java:305-309`). `Xqj91Exception`은 `Xdg64Exception`이므로 그대로 통과한다(`:312-314`, `Xzj27CommandService.java:335-337`).
- 전체가 `RuntimeException`이어서 트랜잭션이 롤백된다. 주문, 항목, 배송, 판매 입찰 `MATCHED`, 창고 상태, 알림 DB 행이 모두 되돌아가고 주문 입찰은 만들어지지 않는다. 결제를 `FAILED`로 저장하는 코드는 없다(`Xbf54Status.FAILED`는 이 경로에서 세팅되지 않는다).
- 클라이언트는 성공 ID 대신 오류 응답을 받는다.
- 재시도(`@Retryable`)는 `Xbf54ApiException`(통신 오류)에만 적용된다(`Xxv33ApiClient.java:224-228`). 코드 0이 아닌 결제 거절(`Xdf64Exception`)은 재시도하지 않는다.

## 4. 알림

- **시점**: 결제 엔티티 저장 직후, `processPayment` 안에서 즉시 만든다(`Xbf54CommandService.java:83`, `:383-426`). 주문 입찰 생성보다 앞이고 트랜잭션 커밋보다도 앞이다. 결제 상태가 `PENDING`이어도 보낸다.
- **수신자**:
  - 구매자: "결제가 완료되었습니다. 주문 ID: …" (`:438-443`)
  - 판매자(`sale.getSeller()`): "구매자가 결제를 완료하였습니다. 판매 ID: …" (`:447-454`)
  - 둘 다 카테고리 `SHOPPING`, 타입 `BID`다.
- **방식**:
  - `Xkh73CommandService.createNotification`이 DB에 알림을 저장한다(`D/m15/service/command/Xkh73CommandService.java:44-54`). 이어서 `sendRealTimeNotification`이 Redis에 `WebSocket:Xrd81:<email>` 키가 있을 때만 STOMP `/user/queue/notifications`로 보낸다(`:57`, `:303-313`). 연결이 없으면 저장만 된다(`:320-322`).
  - 같은 요청 스레드에서 동기로 실행되고 Kafka를 쓰지 않는다. 즉시 구매 경로에서는 `Xdg64EventConsumer`의 성공/실패 알림(WebSocket+Kafka `notification-topic`)이 쓰이지 않는다.
  - 알림 생성 오류는 삼켜진다(`Xbf54CommandService.java:457-461`, `:421-425`). 알림이 실패해도 구매는 계속 진행된다.
- **롤백 시 주의**: WebSocket 전송은 트랜잭션과 무관하게 이미 나가므로, 이후 단계가 실패해 롤백돼도 푸시는 이미 전송된 상태일 수 있다.

## 5. 최종 주문 상태와 창고 보관 선택 시 차이

**최종 상태**: 주문은 **`PENDING_PAYMENT`** 로 끝난다. 일반 결제처럼 결제가 즉시 `PAID`여도 `PAYMENT_COMPLETED`/`PREPARING` 등으로 전이시키는 코드가 이 경로에 없다(`Xdg64CommandService.java:219-319`). 결제 서비스도 주문 상태를 바꾸지 않는다(`Xbf54CommandService.java:57-107`). 상태 전이 코드는 `processPaymentAndShipment`(`Xdg64CommandService.java:161-177`)나 Kafka 컨슈머(`Xdg64EventConsumer.java:192-220`)에만 있고 즉시 구매 경로에서는 호출되지 않는다.

그 외 최종 상태: 판매 입찰 `MATCHED`, 주문 입찰 `MATCHED`(즉시구매 플래그 true), 배송 `PENDING`, sale `SOLD`, 결제는 3번 표와 같다.

**창고 보관(`warehouseStorage`)을 선택한 경우**: 달라지는 것이 없다. 요청의 `isWarehouseStorage` 값은 컨트롤러에서 서비스(`Xzj27CommandController.java:104`)로, 다시 `createInstantOrder`(`Xzj27CommandService.java:256-262`)로 전달되지만 `createInstantOrder` 본문에서 한 번도 읽지 않는다(`Xdg64CommandService.java:219-319`).
- 구매자용 창고 보관 `Xnn94`는 생성되지 않는다(`createOrderStorage` 호출 없음). 주문의 상태 `IN_WAREHOUSE`/`COMPLETED`로의 전환도 없다.
- 창고 관련으로 실제 일어나는 일은 **판매자 sale**의 `isWarehouseStorage`가 true일 때 기존 창고 레코드를 `ASSOCIATED_WITH_ORDER`로 바꾸는 것뿐이다(`:291-294`). 이는 구매자의 선택이 아니라 판매 입찰의 속성에 따른 것이다. 창고 레코드가 없으면 `Xnx94Exception`으로 전체가 롤백된다(`D/m07/service/query/Xnn94QueryService.java:30-33`).
- 창고 보관 시 `IN_WAREHOUSE` 후 `COMPLETED`로 만드는 로직은 비동기 Kafka 경로와 `processPaymentAndShipment`에만 있다(`Xdg64CommandService.java:163-172`, `Xdg64EventConsumer.java:197-211`).
