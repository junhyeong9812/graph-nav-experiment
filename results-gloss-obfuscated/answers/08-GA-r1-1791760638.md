# 구매자 배송: 운송장 등록 → 배송 완료

경로 약어: `M12`=`src/main/java/com/fream/back/domain/m12`, `M16`=`.../domain/m16`, `M06`=`.../domain/m06`, `M10`=`.../domain/m10`, `M15`=`.../domain/m15`, `G`=`src/main/java/com/fream/back/global`.
(타입명은 CLAUDE.md 대응표: Xhx14=OrderShipment, Xdg64=Order, Xzj27=OrderBid, Xzz58=SaleBid, Xgg74=Sale, Xpb98=Shipment)

## 사전: 결제·배송 처리를 마친 일반 구매 입찰 주문의 상태

- 일반 구매 입찰: 주문은 `PENDING_PAYMENT`로 생성되고(`M16/service/command/Xdg64CommandService.java:81`), 입찰은 `assignOrder` 때 `MATCHED`가 된다(`M16/entity/Xzj27.java` `assignOrder`; 호출 `M16/service/command/Xzj27CommandService.java:100`). 이때 연결된 판매 입찰(SaleBid)과 Sale은 없다(`orderBid.sale == null`).
- 결제·배송 처리 API `POST /orders/{orderId}/process-payment-shipment`는 Kafka 이벤트만 발행한다(`M16/controller/command/Xdg64CommandController.java:42,54`). 실제 처리는 컨슈머 `processCompleteOrder`(`M16/service/kafka/Xdg64EventConsumer.java:166`)다: 결제 → 배송(Xhx14, 상태 `PENDING`: `M12/service/command/Xhx14CommandService.java:67`) 생성 → 주문 `PAYMENT_COMPLETED`(`:195`) → 창고보관이 아니면 `PREPARING`(`:215-218`)에서 멈춘다.
- 결과: 주문 `PREPARING`, 배송 `PENDING`, 입찰 `MATCHED`. 이 상태가 아래 1·4(a)의 전제다.
- 주문 상태 전이표: `PREPARING → {IN_WAREHOUSE, SHIPMENT_STARTED}`만 허용(`M16/entity/Xdg64Status.java:26`), `IN_TRANSIT → {COMPLETED}`(`:29`), `PENDING_PAYMENT → {PAYMENT_COMPLETED, COMPLETED, IN_WAREHOUSE}`(`:24`). `PREPARING → IN_TRANSIT`, `PREPARING → COMPLETED`는 허용되지 않는다.

## 1. 운송장 등록 요청

### 1-1. 진입 API
- `PATCH /shipments/order/{shipmentId}/status`, 본문 `{courier, trackingNumber}` (`M12/controller/command/Xhx14CommandController.java:20,33-45`, DTO `M12/dto/Xhx14RequestDto.java`) → `Xhx14CommandService.updateTrackingInfo` (`M12/service/command/Xhx14CommandService.java:239`).
- (참고) 별도로 `POST /shipments/order/{shipmentId}/check-status`(`Xhx14CommandController.java:58`)는 운송장 저장과 택배사 즉시조회를 한 번에 한다(`Xhx14CommandService.java:452`). 질문의 "등록" 경로는 PATCH 쪽이다.

### 1-2. 코드가 의도한 상태 변경 순서 / 알림 (`updateTrackingInfo`, `@Transactional`)
1. 택배사·운송장 공백 검사 → `TRACKING_INFO_REQUIRED`(400) (`:243-246`).
2. 배송 조회 (`:249-253`), `shipment.updateTrackingInfo` → 배송 상태를 곧바로 `IN_TRANSIT`으로 세팅(전이 검사 없음) (`:256`, `M12/entity/Xhx14.java:41-45`).
3. 주문 `order.updateStatus(IN_TRANSIT)` (`:259-260`).
4. 구매자에게 알림 1건 "상품이 출발하였습니다. 주문 ID: …" (`:265-271`).
5. `updateSaleStatusToSold(orderId)` (`:276`): 판매 입찰이 있으면 Sale을 `SOLD`로, 창고보관이면 창고 상태 SOLD, 판매자에게 "판매 완료" 알림(`:116-147`). 이어서 OrderBid 쪽 Sale도 SOLD 시도 + 판매자 알림(`:150-180`).
6. 창고보관 Sale이면 창고 상태 SOLD 재호출 (`:279-286`).
7. `updateOrderAndSaleBidStatusToCompleted`: OrderBid·SaleBid가 `MATCHED`이면 `COMPLETED` (`:289`, `:413-440`).
→ 의도: 배송 `IN_TRANSIT`, 주문 `IN_TRANSIT`, 구매자 알림 1건, (판매 입찰 있을 때) Sale `SOLD` + 판매자 알림, 입찰들 `COMPLETED`.

### 1-3. 실배송 일반 구매 입찰 주문(PREPARING)에서의 실제 결과: **끝까지 성공하지 못한다**
1. 3단계 `order.updateStatus(IN_TRANSIT)`에서 현재 `PREPARING → IN_TRANSIT`이 전이표에 없으므로(`Xdg64Status.java:26`) `Xxc76StatusException`(`INVALID_ORDER_STATUS`, `M16/entity/Xdg64.java:113-121`)이 던져진다. 앞서 `shipment.updateTrackingInfo`가 메모리상 상태를 바꿔 놓았지만 아직 flush 전이다.
2. 이 예외는 `Xpb98Exception`이 아니므로 `catch (Exception e)`(`Xhx14CommandService.java:295-302`)에서 `Xpb98Exception(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")`로 감싸져 다시 던져진다(오류 코드 이름이 실제 원인과 무관하게 "배송 정보를 찾을 수 없습니다").
3. `@Transactional`이 RuntimeException으로 롤백한다. **저장되는 것은 없다**: 배송은 `PENDING` 그대로, 택배사·운송장 번호도 저장되지 않음, 주문 `PREPARING` 유지, 알림 0건(알림 생성 `:266`은 예외 지점 `:260` 뒤라 도달 안 함), 입찰 상태 변화 없음.
4. 응답: 전역 핸들러가 `ErrorResponse(code="S001", message="배송 정보를 찾을 수 없습니다.", status=404, path)`로 응답 → **HTTP 404, 코드 S001** (`M12/exception/Xpb98ErrorCode.java:61`, `G/exception/Xks43ExceptionHandler.java` `handleGlobalException`). 컨트롤러의 성공 로그·`200 OK`는 나오지 않는다(`Xhx14CommandController.java:41-48`).
- 부가: 설령 주문 상태 전이를 통과해도 5단계 `saleBidQueryService.findByOrderId`는 SaleBid가 없으면 null이 아니라 `IllegalArgumentException`을 던진다(`M10/service/query/Xzz58QueryService.java:26-29`). 즉 판매 입찰이 없는 일반 구매 입찰은 어차피 `:276`에서 같은 SHIPMENT_NOT_FOUND로 실패하며, 코드의 `saleBid != null` 분기(`Xhx14CommandService.java:117,280`)는 사실상 죽은 코드다.

## 2. 배송 완료 감지

### 2-1. 누가·언제·어떻게
- 스케줄러 `Xpb98BatchScheduler.scheduleShipmentStatusJob()`이 `@Scheduled(cron = "0 0 */6 * * *")`로 **6시간마다(0·6·12·18시 정각)** `updateShipmentStatusesJob` Spring Batch 잡을 `timestamp` 파라미터로 실행한다 (`G/config/Xpb98BatchScheduler.java:34-40`).
- 잡 정의: `M12/config/Xqv91JobConfig.java:55-82` (청크 50, skip 한도 50, `Exception` 전부 skip; `:51-52,67,75-77`).
- 대상: reader JPQL `SELECT s FROM Xhx14 s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL` (`Xqv91JobConfig.java:95`), 페이지 크기 50의 `JpaPagingItemReader`(`:89-96`). PENDING 배송은 조회되지 않는다.

### 2-2. 실제로 실행되는 처리 코드
- 비슷한 코드가 3곳 있다.
  1. `Xqv91JobConfig.shipmentItemProcessor()` (`Xqv91JobConfig.java:104-177`) — `@Bean`이지만 스텝에 연결되지 않아 **실행되지 않는다**(스텝은 `new Xth19Processor(...)`를 쓴다, `:69-73`).
  2. `Xhx14CommandService.updateShipmentStatuses()` (`Xhx14CommandService.java:308-391`) — 코드베이스 어디서도 호출되지 않는다(호출처 grep 결과 없음).
  3. **`M12/config/Xth19Processor.process()`** (`M12/config/Xth19Processor.java:52-150`) — 스텝에 실제로 연결된 프로세서(`Xqv91JobConfig.java:69-73`). 이것이 실제 실행 코드다.
- 동작: Playwright 브라우저(`Xrk74`)로 CJ대한통운 `https://trace.cjlogistics.com/next/tracking.html?wblNo=<운송장>`을 열어(`Xth19Processor.java:24,72-85`) `tbody#statusDetail tr` 로딩을 대기하고(`:87`), 마지막 행의 5번째 `td`(index 4) 텍스트를 상태 문자열로 쓴다(`:181`). 스텝 시작/종료 시 브라우저 open/close는 `Xmb36Listener`(`M12/config/Xmb36Listener.java:15-25`).
- 택배사(`courier`) 값은 무시되고 항상 CJ 조회다.

### 2-3. 택배사 문자열 → 내부 상태 (`Xth19Processor.mapToShipmentStatus`, `:~195-200`)
- `"배송완료"` → `DELIVERED`, `"배송출발"` → `OUT_FOR_DELIVERY`, 그 밖의 모든 문자열 → `IN_TRANSIT` (default).
- 현재 상태와 같으면 변경 없이 반환(`:101-105`). 표에 행이 없거나 텍스트가 비면 `TRACKING_HTML_PARSE_ERROR`(`:~166-175`).
- 주의: `OUT_FOR_DELIVERY`인 배송이 조회 결과 "그 밖의 문자열"이면 `IN_TRANSIT`으로 되돌리려 하지만, 전이표에 `OUT_FOR_DELIVERY → IN_TRANSIT`이 없어(`M12/entity/Xpb98Status.java:23-28`) `IllegalStateException`(`Xhx14.java:47-55`)이 되고 → `EXTERNAL_TRACKING_SERVICE_ERROR`로 감싸져 그 건은 skip된다.

## 3. 배송 완료 판정 이후 (`Xth19Processor.java:108-117`)

### 3-1. 상태 변경 순서
1. 배송 `orderShipment.updateStatus(DELIVERED)` (`IN_TRANSIT`/`OUT_FOR_DELIVERY → DELIVERED` 허용, `Xpb98Status.java:16-28`) — 메모리 변경 (`:113`).
2. `orderService.completeOrder(orderId)` (`:116` → `Xhx14CommandService.java:190-229`):
   - OrderBid를 `findByOrderId`로 조회(없으면 `IllegalArgumentException`) (`:196-197`).
   - 주문 `COMPLETED`로 변경 (`:204`; 현재 상태에 따라 전이 예외 가능, 아래 4 참조).
   - `updateSaleStatusToSold(orderId)` (`:208`).
   - 구매자 알림 "[completeOrder] 주문이 완료 처리되었습니다. 주문 ID: …" (`:211-217`).
   - 어떤 예외든 `Xpb98Exception(ORDER_NOT_FOUND_FOR_SHIPMENT)`로 감싸 던짐 (`:221-228`).
3. `notificationService.notifyShipmentCompleted(order)` — 구매자에게 "[배송 완료] 상품이 배송 완료되었습니다. 주문 ID: …" (`M15/service/command/Xkh73CommandService.java:219-234`; 내부 예외는 삼킴).
4. 위 상태는 chunk 종료 시 `JpaItemWriter`가 저장(`Xqv91JobConfig.java:74,239-246`).

### 3-2. 알림 건수
- 구매자: 2건(`completeOrder`의 "[completeOrder] …" 1건 + `notifyShipmentCompleted`의 "[배송 완료] …" 1건).
- 판매자: `updateSaleStatusToSold`에서 Sale이 `SOLD`로 전이 가능할 때만 1건 "상품이 성공적으로 판매 완료되었습니다. 판매 ID: …" (`Xhx14CommandService.java:132-138`). SaleBid 쪽에서 SOLD가 된 뒤에는 OrderBid 쪽(`:150-180`)은 같은 Sale이라 `SOLD → SOLD`가 불가해 두 번째 알림은 없다. Sale이 `canTransitionTo(SOLD)`를 만족하지 않으면(`M10/entity/Xgg74Status.java:30-40`; `IN_STORAGE`·`PENDING_SHIPMENT`는 불가) 판매자 알림 0건.

### 3-3. 주문 입찰·판매 입찰 상태
- 배치 경로(`completeOrder`)는 `OrderBid`/`SaleBid` 상태를 **바꾸지 않는다**. `MATCHED → COMPLETED` 변경은 `updateOrderAndSaleBidStatusToCompleted`(`Xhx14CommandService.java:413-440`)에만 있고, 이는 운송장 등록 API(`:289`)에서만 호출된다(그것도 1-3에서 보듯 일반 주문에선 도달하지 못함). 따라서 배송 완료 후에도 OrderBid·SaleBid는 `MATCHED`로 남는다. 바뀌는 것은 Sale(`SOLD`, 가능할 때)뿐이다.

## 4. 주문 종류별 차이

### (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문 — 끝까지 진행되지 않음
- 주문 `PREPARING`(사전 참조). 3-1의 2단계 `order.updateStatus(COMPLETED)`에서 `PREPARING → COMPLETED`가 불가(`Xdg64Status.java:26`)하여 `Xxc76StatusException` → `completeOrder`의 catch → `Xpb98Exception(ORDER_NOT_FOUND_FOR_SHIPMENT, …)` (`Xhx14CommandService.java:204,221-228`).
- 따라서 `notifyShipmentCompleted`(`Xth19Processor.java:117`)는 실행되지 않고, 알림 0건(구매자 완료 알림은 `:212`로 예외 뒤), Sale 변화 없음, OrderBid/SaleBid `MATCHED` 유지. 예외는 chunk 트랜잭션을 롤백시키고 skip 대상이 되므로 배송은 `DELIVERED`로 저장되지 않고 `IN_TRANSIT` 그대로 남는다 → 6시간마다 계속 재시도·재실패.
- (이 배송이 배치 대상이 되려면 `IN_TRANSIT` + 운송장이 필요한데, 1-3에 의해 PATCH API로는 만들어지지 않는다. `check-status` API는 배송만 `IN_TRANSIT`으로 저장하고 주문은 `PREPARING` 그대로 둘 수 있어(`Xhx14CommandService.java:473-498`) 이 경우가 해당한다. 또한 이 API에서 DELIVERED가 조회되면 같은 이유로 `completeOrder`에서 실패해 전체가 롤백된다.)

### (b) 즉시 구매로 만들어진 주문 — 끝까지 진행됨 (단, 판매자 알림 없음)
- 즉시 구매는 `createInstantOrder`(`M16/service/command/Xdg64CommandService.java:220`)가 주문을 `PENDING_PAYMENT`로 만들고(`:244`) 상태 전이 없이 끝난다. SaleBid를 주문에 `assignOrder`(`:279`)하고 `MATCHED`로 만든다. OrderBid는 `MATCHED`·`isInstantPurchase=true`로 생성(`M16/service/command/Xzj27CommandService.java:189-206`)되어 `order`와 연결되므로 `findByOrderId`가 성공한다.
- 결제 시점(`processPayment` → `notifyUsersAndUpdateSaleStatus`, `M06/service/command/Xbf54CommandService.java:83,383-421`)에 OrderBid가 아직 생성 전이라 `order.getOrderBid()==null` 분기(`:392-407`)로 가서 Sale을 **이미 `SOLD`로** 바꾸고(`:404`) 구매자·판매자에게 결제 완료 알림을 보낸다(`:434-451`).
- 배송 완료 처리: 주문 `PENDING_PAYMENT → COMPLETED`는 허용(`Xdg64Status.java:24`)이라 `completeOrder`가 성공한다. `updateSaleStatusToSold`에서는 Sale이 이미 `SOLD`여서 `canTransitionTo(SOLD)`가 false(`Xgg74Status.java:38`) → Sale 변경·창고 갱신·판매자 알림 없음(`:142-144,173-175`).
- 결과: 배송 `DELIVERED`, 주문 `COMPLETED`, 구매자 알림 2건, 판매자 알림 0건(배송 완료 시점), OrderBid/SaleBid는 `MATCHED` 유지.
- (이 배송을 배치 대상으로 만들려면 `IN_TRANSIT` + 운송장이 필요한데, PATCH API는 `PENDING_PAYMENT → IN_TRANSIT` 불가로 실패한다(`:260`, 전이표 `Xdg64Status.java:24`). 즉 `check-status` API로 운송장을 넣었을 때만 배치 대상이 된다.)

### 차이 요약
| | (a) 일반 구매 입찰(PREPARING) | (b) 즉시 구매(PENDING_PAYMENT) |
|---|---|---|
| 주문 → COMPLETED | 불가(`Xxc76StatusException`) | 가능 |
| 배송 DELIVERED 저장 | 롤백·skip, `IN_TRANSIT` 유지 | 저장됨 |
| 구매자 알림 | 0건 | 2건 |
| 판매자 알림 | 0건 | 0건(Sale이 이미 SOLD) |
| OrderBid/SaleBid | `MATCHED` | `MATCHED` |

## 5. 실패 처리 (주기 배치)
- 프로세서에서 예외 발생 시: 비 `Xpb98Exception`은 `EXTERNAL_TRACKING_SERVICE_ERROR`로 감싸 던지고(`Xth19Processor.java:~134-145`), 페이지는 `finally`에서 닫는다(`:147-156`).
- 스텝은 `faultTolerant().skip(Exception.class).skipLimit(50)` (`Xqv91JobConfig.java:75-77`)이므로 실패한 건은 skip되고 `shipmentSkipListener`가 로그만 남긴다(`:251-287`). 스킵 건은 `DELIVERED` 등으로 저장되지 않아(롤백) 상태가 바뀌지 않고, 다음 실행(6시간 후)에 다시 조회 대상이 된다.
- 나머지 건: chunk(50건) 안에서 한 건이 프로세서 예외를 내면 chunk 트랜잭션이 롤백되고, Spring Batch fault-tolerant 스텝이 그 chunk를 아이템 단위로 다시 처리하여 실패 건만 건너뛰고 나머지는 정상 처리·커밋한다. 실패 건 처리 중 `completeOrder`가 던진 예외는 공유 트랜잭션을 rollback-only로 표시하므로 chunk 전체가 한 번 롤백된다.
- 롤백 시 이미 보낸 실시간(웹소켓) 알림은 취소되지 않을 수 있다(`createNotification`이 저장 후 `sendRealTimeNotification` 호출, `M15/service/command/Xkh73CommandService.java:52-57`).
- skip이 50건을 넘으면 스텝이 `SkipLimitExceeded`로 실패하여 이후 건은 해당 실행에서 처리되지 않는다.
- 부가 주의: reader가 `ORDER BY` 없는 `JpaPagingItemReader`이고 처리 중 대상 조건(`IN_TRANSIT/OUT_FOR_DELIVERY`)에서 빠지는 행이 생기므로(`DELIVERED`로 변경), 페이지 오프셋이 밀려 대상이 50건을 넘을 때 일부가 해당 실행에서 건너뛰어질 수 있다(`Xqv91JobConfig.java:89-96`). 스케줄러 자체의 예외는 `printStackTrace()`로만 처리된다(`Xpb98BatchScheduler.java:41-43`).
