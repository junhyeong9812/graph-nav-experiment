# 구매자 배송: 운송장 등록 ~ 배송 완료

경로는 `src/main/java/com/fream/back/` 기준이다 (아래에서는 `…/`로 줄여 쓴다).
타입 이름은 CLAUDE.md 대응표를 따른다. Xhx14 = OrderShipment, Xdg64 = Order, Xzj27 = OrderBid, Xzz58 = SaleBid, Xgg74 = Sale, Xpb98 = Shipment 계열.

## 요약

- 운송장 등록 API(`PATCH /shipments/order/{id}/status`)는 의도(주문 IN_TRANSIT → 구매자 알림 → 판매 SOLD → 입찰 COMPLETED)와 달리, 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문에서는 항상 실패한다.
  - 주문이 PREPARING 상태인데 `PREPARING → IN_TRANSIT` 전환이 허용되지 않기 때문이다.
  - 예외가 `SHIPMENT_NOT_FOUND`(404)로 바뀌어 전체가 롤백된다.
- 배송 완료 감지는 6시간마다 도는 Spring Batch 잡이 한다. 실제 처리 코드는 `Xth19Processor`이다.
  - `Xqv91JobConfig.shipmentItemProcessor`와 `Xhx14CommandService.updateShipmentStatuses`는 실행되지 않는 사본이다.
- 배송 완료 이후 처리는 즉시 구매 주문(b)에서는 끝까지 진행되고, 일반 구매 입찰 주문(a)에서는 `order.updateStatus(COMPLETED)`에서 실패한다.

## 1. 운송장 등록 요청

### 1-1. 진입 API

- `PATCH /shipments/order/{shipmentId}/status`, 본문은 `{courier, trackingNumber}`이다.
  - `…/domain/m12/controller/command/Xhx14CommandController.java:20` (`@RequestMapping("/shipments/order")`)
  - `…/domain/m12/controller/command/Xhx14CommandController.java:33` (`@PatchMapping("/{shipmentId}/status")`)
  - `…/domain/m12/dto/Xhx14RequestDto.java:10-13` (본문 DTO)
- 컨트롤러는 `Xhx14CommandService.updateTrackingInfo`를 호출한다 (`Xhx14CommandController.java:41`, 서비스 정의 `…/domain/m12/service/command/Xhx14CommandService.java:239`).
- 메서드 이름이 `status`인 이 PATCH 말고도, 같은 컨트롤러에 `POST /{shipmentId}/check-status`(`Xhx14CommandController.java:58`)가 있다.
  - 이 API는 운송장을 저장하고 곧바로 택배사 조회까지 한다 (`Xhx14CommandService.java:452-503`).
  - 이 경로는 주문 상태를 IN_TRANSIT으로 바꾸지 않는다. 6절 참고.

### 1-2. 코드가 의도한 상태 변경 순서와 알림

`Xhx14CommandService.updateTrackingInfo` (`…/Xhx14CommandService.java:239-303`) 기준이다.

1. courier·trackingNumber가 비어 있으면 `TRACKING_INFO_REQUIRED`(400)를 던진다 (`:243-246`).
2. 배송(Xhx14)을 조회한다 (`:249-253`).
3. `shipment.updateTrackingInfo(courier, trackingNumber)` (`:256`)
   - 택배사와 운송장 번호를 넣고 상태를 곧바로 `IN_TRANSIT`으로 세팅한다 (`…/domain/m12/entity/Xhx14.java:41-45`).
   - `updateStatus`의 전이 검사를 거치지 않는다. 검사했다면 PENDING → IN_TRANSIT은 허용되지 않는다 (`…/domain/m12/entity/Xpb98Status.java:4-8`, PENDING은 SHIPPED·CANCELED만 허용).
4. `order.updateStatus(Xdg64Status.IN_TRANSIT)` (`:259-260`)
5. 구매자에게 알림 1건: "상품이 출발하였습니다. 주문 ID: …" (`:265-271`)
6. `updateSaleStatusToSold(orderId)` (`:276`, 본체 `:111-183`)
   - SaleBid의 Sale이 SOLD로 갈 수 있으면 SOLD로 바꾼다 (`:116-123`).
   - 창고 보관 건이면 창고 상태도 바꾼다 (`:126-129`).
   - 판매자에게 알림 1건: "상품이 성공적으로 판매 완료되었습니다" (`:132-138`).
   - OrderBid 쪽 Sale도 같은 방식으로 처리한다 (`:150-176`).
7. 창고 보관 판매면 창고 상태를 한 번 더 갱신한다 (`:279-286`).
8. `updateOrderAndSaleBidStatusToCompleted` (`:289`, 본체 `:413-440`)
   - MATCHED인 OrderBid를 COMPLETED로 바꾼다 (`:422-425`).
   - MATCHED인 SaleBid를 COMPLETED로 바꾼다 (`:428-432`).

의도된 알림은 구매자 1건과 판매자 1건이다. 배송 완료 알림은 이 단계에 없다.

### 1-3. 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문은 끝까지 성공하는가 → 아니오, 4번 단계에서 실패한다

**주문 상태가 PREPARING이다.**

- `Xdg64CommandService.processPaymentAndShipment`가 결제를 처리하고 배송(PENDING)을 만든다 (`…/domain/m16/service/command/Xdg64CommandService.java:139-155`).
- 창고 보관이 아닌 경우(실배송)에는 `PAYMENT_COMPLETED → PREPARING`까지만 진행한다 (`Xdg64CommandService.java:174-177`).
- 창고 보관은 `IN_WAREHOUSE → COMPLETED`까지 간다 (`Xdg64CommandService.java:165-172`).
- 이 흐름은 Kafka 경로(`…/domain/m16/service/kafka/Xdg64EventConsumer.java:216-217`)에서도 동일하게 PREPARING에서 멈춘다.

**PREPARING → IN_TRANSIT 전이가 허용되지 않는다.**

- 허용 전이 표: `PREPARING → {IN_WAREHOUSE, SHIPMENT_STARTED}` (`…/domain/m16/entity/Xdg64Status.java:26`).
- IN_TRANSIT은 `SHIPMENT_STARTED → IN_TRANSIT`으로만 갈 수 있다 (`Xdg64Status.java:28`).
- 코드베이스 어디에도 주문을 SHIPMENT_STARTED로 올리는 `updateStatus` 호출이 없다 (`grep Xdg64Status.SHIPMENT_STARTED` 결과는 enum 정의뿐이다).

**실패 지점은 `Xhx14CommandService.java:260`이다.**

- `Xdg64.updateStatus`가 `Xxc76StatusException`("상태 전환이 허용되지 않습니다: PREPARING -> IN_TRANSIT")을 던진다 (`…/domain/m16/entity/Xdg64.java:113-120`).
- 이 예외는 `Xdg64Exception → Xks43Exception → RuntimeException` 계열이다 (`…/domain/m16/exception/Xxc76StatusException.java:55`, `…/global/exception/Xks43Exception.java:10`).
- `Xpb98Exception`이 아니므로 `catch (Xpb98Exception e)`(`:293`)를 지나쳐 `catch (Exception e)`(`:295`)에 잡힌다.
- 여기서 `Xpb98Exception(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")`으로 바뀌어 던져진다 (`:296-301`).
- 메서드가 `@Transactional`이고(`:238`) 런타임 예외가 밖으로 나가므로 전체가 롤백된다.

**저장되는 것은 없다.**

- 배송의 courier·trackingNumber·IN_TRANSIT 변경은 롤백된다. 배송은 PENDING에 운송장 없음 상태로 남는다.
- 주문은 PREPARING 그대로다.
- 구매자 알림(5단계)과 판매자 알림(6단계), 입찰 COMPLETED 변경은 이 지점 뒤라서 실행조차 되지 않는다.
- 결과적으로 이 배송은 배치 대상(`status IN (IN_TRANSIT, OUT_FOR_DELIVERY) AND trackingNumber IS NOT NULL`, `…/domain/m12/config/Xqv91JobConfig.java:95`)에 영영 들어가지 못한다.

**응답은 HTTP 404, 본문 `ErrorResponse`(code `S001`)이다.**

- 이 엔드포인트의 컨트롤러는 try/catch가 없다 (`Xhx14CommandController.java:33-49`).
- `Xks43ExceptionHandler`가 `Xks43Exception`을 받아 `errorCode.getStatus()`로 응답한다 (`…/global/exception/Xks43ExceptionHandler.java:49-63`).
- `SHIPMENT_NOT_FOUND`는 `("S001", "배송 정보를 찾을 수 없습니다.", 404)`이다 (`…/domain/m12/exception/Xpb98ErrorCode.java:12`).
- 응답 본문에는 예외에 담은 상세 메시지(PREPARING → IN_TRANSIT)가 아니라 에러코드의 고정 메시지가 들어간다 (`Xks43ExceptionHandler.java:57-62`).
- 사실은 "배송이 없다"가 아니라 "주문 상태 전이 불가"인데도 `SHIPMENT_NOT_FOUND`/404로 보인다.

**참고: 같은 메서드에는 두 번째 잠복 실패가 있다.**

- `saleBidQueryService.findByOrderId`는 SaleBid가 없으면 `null`이 아니라 `IllegalArgumentException`을 던진다 (`…/domain/m10/service/query/Xzz58QueryService.java:26-28`).
- 그런데 `updateSaleStatusToSold`(`Xhx14CommandService.java:116-117`)와 `:279-280`은 `null` 반환을 가정한 코드다.
- 일반 구매 입찰 주문은 SaleBid.order가 연결돼 있지 않으므로, 4단계 전이 실패가 없었더라도 6단계에서 어차피 실패한다.

## 2. 배송 완료 감지

### 2-1. 누가, 언제, 어떻게

- 스케줄러 `Xpb98BatchScheduler`가 `@Scheduled(cron = "0 0 */6 * * *")`로 Spring Batch 잡 `updateShipmentStatusesJob`을 띄운다.
  - `…/global/config/Xpb98BatchScheduler.java:34-40`
  - 주기는 6시간마다 정각이다. 매일 00:00, 06:00, 12:00, 18:00(서버 시간대)에 실행된다.
  - 실행할 때마다 `timestamp` 파라미터를 새로 넣는다 (`:37-39`).
  - 예외는 `printStackTrace()`만 하고 삼킨다 (`:41-43`).
- 스케줄링은 프로젝트 내 다른 설정 클래스의 `@EnableScheduling`으로 켜져 있다 (예: `…/domain/m18/config/Xvq73Configuration.java:37`).
- 배치는 `@EnableBatchProcessing`(`…/global/config/Xct70Config.java:15`) 위에서 `Xqv91JobConfig`가 구성한다 (잡 `:55-60`, 스텝 `:62-82`).
- 감지 방식은 Playwright 헤드리스 브라우저로 CJ대한통운 추적 페이지를 열어 HTML을 파싱하는 것이다.
  - URL은 `https://trace.cjlogistics.com/next/tracking.html?wblNo=` + 운송장 번호다 (`…/domain/m12/config/Xth19Processor.java:28`, `:75-83` 부근의 이동·대기).
  - `tbody#statusDetail tr`의 **마지막 행, 5번째 `td`**(`get(4)`) 텍스트를 상태 문자열로 쓴다 (`Xth19Processor.java:29`, `:181`).
  - 택배사 값(`courier`)은 조회에 쓰지 않는다. 항상 CJ 대한통운 URL이다.
- 스텝 시작 때 브라우저를 열고(`Xmb36Listener.beforeStep` → `openBrowser()`), 끝나면 닫는다 (`…/domain/m12/config/Xmb36Listener.java:14-25`, 리스너 등록 `Xqv91JobConfig.java:80`).

### 2-2. 조회 대상

- 읽기: `JpaPagingItemReader`, pageSize 50 (`Xqv91JobConfig.java:90-96`).
- 쿼리: `SELECT s FROM Xhx14 s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL` (`Xqv91JobConfig.java:95`).
  - PENDING, DELIVERED 등은 대상이 아니다.
- 스텝은 chunk 50, 오류 허용 스킵 한도 50이다 (`Xqv91JobConfig.java:51-52`, `:64`, `:75-77`).

### 2-3. 실제로 실행되는 처리 코드

- 스텝은 `new Xth19Processor(playwrightBrowserManager(), notificationService, orderService)`를 프로세서로 쓴다 (`Xqv91JobConfig.java:69-73`). 실제 실행되는 것은 `Xth19Processor.process` (`Xth19Processor.java:57-148`)이다.
- 같은 파일의 다음 두 코드는 실행되지 않는다.
  - `Xqv91JobConfig.shipmentItemProcessor()`(`Xqv91JobConfig.java:104-106` 부근)는 `@Bean`으로 등록돼 있지만 스텝에 연결되지 않았다. 스텝은 `.processor(new Xth19Processor(...))`만 쓴다 (`:69`).
  - 같은 파일의 `parseCjLogisticsStatus`는 어디서도 호출되지 않는다.
- `Xhx14CommandService.updateShipmentStatuses()`(`:309-391`)는 배치 외에 아무 데서도 호출되지 않는다 (`@Scheduled`도 없고, `grep` 결과 정의뿐이다). 이 메서드는 `Xxx20.getCurrentTrackingStatus`를 쓰고 주문을 `completeOrder` 없이 직접 COMPLETED로 바꾸는 다른 로직이다. 이 메서드는 실행되지 않는다.

### 2-4. 택배사 상태 문자열 → 내부 상태 (`Xth19Processor.mapToShipmentStatus`, `:220-226`)

| 택배사 문자열 | 내부 상태 |
|---|---|
| `"배송완료"` | `Xpb98Status.DELIVERED` |
| `"배송출발"` | `Xpb98Status.OUT_FOR_DELIVERY` |
| 그 외 모든 문자열(집화처리, 간선상차 등) | `Xpb98Status.IN_TRANSIT` |

- 문자열은 `trim()` 후 정확히 일치해야 한다 (`:181`, `switch`는 `:221` 부근).
- 빈 문자열이거나 행·칸이 없으면 `TRACKING_HTML_PARSE_ERROR`를 던진다 (`:166-197`).
- 현재 상태와 같으면 변경 없이 반환한다 (`:101-104`).
- 매핑에는 `DELAYED`·`FAILED_DELIVERY` 같은 상태가 없다.

## 3. 배송 완료 판정 이후 (`Xth19Processor.process`, `:109-118`)

상태가 `DELIVERED`로 매핑되면 다음 순서로 진행한다.

1. `orderShipment.updateStatus(DELIVERED)` (`Xth19Processor.java:113`)
   - IN_TRANSIT → DELIVERED, OUT_FOR_DELIVERY → DELIVERED는 허용된다 (`Xpb98Status.java:16-21`, `:23-28`).
2. `orderService.completeOrder(orderId)` (`Xth19Processor.java:116`, 본체 `Xhx14CommandService.java:191-229`)
   - OrderBid를 `findByOrderId`로 조회한다. 없으면 `IllegalArgumentException`이 나서 `catch (Exception)`을 거쳐 `Xpb98Exception(ORDER_NOT_FOUND_FOR_SHIPMENT)`이 된다 (`:196-197`, `:221-227`).
   - `order.updateStatus(COMPLETED)` (`:204`)
   - `updateSaleStatusToSold(orderId)` (`:208`): SaleBid의 Sale이 SOLD로 갈 수 있으면 SOLD로 바꾸고 판매자 알림 1건을 보낸다 (`:116-138`). OrderBid 쪽 Sale도 같은 방식이다 (`:150-176`).
   - 구매자 알림 1건: "[completeOrder] 주문이 완료 처리되었습니다. 주문 ID: …" (`:211-217`)
3. `notificationService.notifyShipmentCompleted(order)` (`Xth19Processor.java:117`)
   - 구매자에게 "[배송 완료] 상품이 배송 완료되었습니다. 주문 ID: …" 알림 1건 (`…/domain/m15/service/command/Xkh73CommandService.java:219-229`).
   - 이 메서드 안에서 예외를 삼키므로 실패해도 전체 흐름은 이어진다 (`:230-233`).
4. 프로세서가 반환한 배송을 `JpaItemWriter`가 저장한다 (`Xqv91JobConfig.java:74`, `:241-246`).
   - 배송 DELIVERED 저장, 주문 COMPLETED는 `completeOrder` 트랜잭션에 포함된다.

**상태 변경 순서: 배송 DELIVERED → 주문 COMPLETED → (Sale SOLD) → 알림.**

### 알림 건수

- 구매자: 2건 (`[completeOrder] 주문이 완료 처리되었습니다`와 `[배송 완료] …`).
- 판매자: Sale을 이때 SOLD로 바꾸는 경우에 한해 1건 (`Xhx14CommandService.java:132-138`). 이미 SOLD였다면 0건이다. 4절 참고.
- 상태 문구가 서로 다른 구매자 알림이 중복으로 2건 가는 것이 이 흐름의 특징이다.

### 주문 입찰·판매 입찰 상태

- 배송 완료 처리(`completeOrder`)는 **OrderBid·SaleBid의 상태를 COMPLETED로 바꾸지 않는다.**
  - 입찰 COMPLETED 변경은 `updateOrderAndSaleBidStatusToCompleted`(`Xhx14CommandService.java:413-440`)에 있고, 이 메서드는 운송장 등록(`updateTrackingInfo`, `:289`)에서만 호출된다.
  - 그런데 운송장 등록 API는 1-3절처럼 일반 구매 입찰 주문에서 실패한다.
- 결과적으로 배송 완료 후에도 두 입찰은 `MATCHED`에 머문다.
  - 즉시 구매에서는 OrderBid가 `MATCHED`로 만들어진다 (`…/domain/m16/service/command/Xzj27CommandService.java:192-199`).
  - SaleBid는 주문 연결 때 `MATCHED`가 된다 (`Xdg64CommandService.java:279-280`).
- Sale(판매)은 `SOLD`로 바뀐다. 위 2단계 `updateSaleStatusToSold`가 하고, 결제 시점에도 이미 SOLD로 바꿔 놓는다 (`…/domain/m06/service/command/Xbf54CommandService.java:383-420`).

## 4. 주문 종류별 차이

두 경우 모두 "운송장 등록은 끝나 있고 배송이 IN_TRANSIT이며 택배사가 배송완료를 돌려준다"고 가정한 비교다. 1-3절 때문에 (a)·(b) 모두 PATCH API로는 그 상태에 이르지 못하고, `POST /check-status`(`Xhx14CommandService.java:473`, 주문 상태는 건드리지 않고 배송만 IN_TRANSIT으로 만듦)로만 도달할 수 있다.

### (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문 → 끝까지 진행되지 않는다

- 주문은 PREPARING이다 (`Xdg64CommandService.java:175-177`).
- `process`의 순서는 다음과 같다.
  1. `shipment.updateStatus(DELIVERED)`가 성공한다. 메모리 상의 변경일 뿐이다.
  2. `completeOrder`가 OrderBid를 찾는다. 일반 구매 입찰은 OrderBid가 있으므로 `:196-197`은 통과한다.
  3. `order.updateStatus(COMPLETED)`(`Xhx14CommandService.java:204`)에서 `PREPARING → COMPLETED`가 허용되지 않아 `Xxc76StatusException`이 난다 (전이 표 `Xdg64Status.java:26`, 예외 `Xdg64.java:113-120`).
  4. `catch (Exception)`이 `Xpb98Exception(ORDER_NOT_FOUND_FOR_SHIPMENT)`으로 감싸서 던진다 (`:221-227`).
- 결과는 다음과 같다.
  - `Xth19Processor`가 그 예외를 다시 던진다 (`:133-145`). 스텝의 `.skip(Exception.class)`로 해당 건은 스킵된다 (`Xqv91JobConfig.java:76`).
  - 배송 DELIVERED도, 주문 COMPLETED도, 구매자·판매자 알림도 저장되지 않는다. `notifyShipmentCompleted`는 실행되지 않는다.
  - 배송은 IN_TRANSIT에 남아, 다음 6시간 주기마다 같은 건이 다시 조회·실패한다.
- 추가로, 상태 전이를 통과했더라도 `updateSaleStatusToSold`의 `saleBidQueryService.findByOrderId`가 SaleBid 없음으로 `IllegalArgumentException`을 던져(`Xzz58QueryService.java:26-28`) 같은 방식으로 실패한다.

### (b) 즉시 구매로 만들어진 주문 → 끝까지 진행된다

- 즉시 구매 주문은 `createInstantOrder`에서 PENDING_PAYMENT로 만들어지고 이후 상태를 올리는 코드가 없다 (`Xdg64CommandService.java:241-245`; 결제 서비스는 주문 상태를 건드리지 않는다).
- 즉시 구매 흐름에서 OrderBid가 새로 만들어진다 (`Xzj27CommandService.java:142`, `:189-207`). 따라서 `completeOrder`의 OrderBid 조회가 성공한다.
- `PENDING_PAYMENT → COMPLETED`는 전이 표에 허용돼 있다 (`Xdg64Status.java:24`). 그래서 `order.updateStatus(COMPLETED)`가 성공한다.
- 주문 COMPLETED, 구매자 알림 2건이 저장되고 배송은 DELIVERED로 저장된다.
- 판매자 알림은 **0건**이다.
  - 결제 시점에 이미 Sale이 SOLD가 되었다. 즉시 구매에서는 SaleBid가 주문에 연결된 뒤 `processPayment`가 불리고(`Xdg64CommandService.java:279-280`, `:305`), 그 안에서 `sale.updateStatus(SOLD)`와 구매자·판매자 알림이 나간다 (`Xbf54CommandService.java:83`, `:391-405`, `:434-456`).
  - 그래서 `updateSaleStatusToSold`의 `canTransitionTo(SOLD)`가 false(SOLD → SOLD 불가, `Xgg74Status.java` 의 `case SOLD … -> false`)라 판매자 알림이 가지 않는다 (`Xhx14CommandService.java:119`, `:156`).
- 입찰은 MATCHED로 남는다 (3절).

## 5. 실패 처리 (주기 처리 중 한 건이 실패하면)

- 스텝은 `faultTolerant().skip(Exception.class).skipLimit(50)`이다 (`Xqv91JobConfig.java:75-77`).
- 프로세서에서 예외가 나면 그 건만 스킵한다. 청크는 롤백된 뒤 해당 건을 뺀 나머지 아이템을 다시 처리한다. 나머지 건은 정상 처리된다.
  - 프로세서는 모든 예외를 `Xpb98Exception`으로 바꿔 던진다 (`Xth19Processor.java:133-145`; 파싱 예외는 `:166-206`).
  - 실패한 건은 쓰기 대상에서 빠지므로 DB에는 변경 없이(배송 IN_TRANSIT 그대로) 남는다. 다음 주기(6시간 뒤)에 다시 대상이 된다.
- 스킵은 `SkipListener`가 에러 로그만 남긴다 (`Xqv91JobConfig.java:253-281` 부근의 `shipmentSkipListener`). 별도 재시도·알림·보상 처리는 없다.
- 스킵이 50건을 넘으면 스텝이 스킵 한도 초과로 실패해 그 실행의 나머지 건은 처리되지 않는다 (`:52`, `:77`). 그 경우 잡은 FAILED이고, 스케줄러는 예외를 `printStackTrace`로만 처리한다 (`Xpb98BatchScheduler.java:41-43`).
- 아이템 단위로 보면 `completeOrder` 내부에서 이미 바뀐 주문·Sale 변경은 같은 트랜잭션이라 함께 롤백된다.
  - 단 `notifyShipmentCompleted`는 내부 try/catch로 예외를 삼키므로 알림 실패만으로는 건이 실패하지 않는다 (`Xkh73CommandService.java:230-233`).

## 6. 참고: 주석·이름과 실제 동작이 다른 곳

- `PATCH …/status`는 이름과 달리 "상태"를 직접 받지 않고 운송장을 등록한다. 등록과 동시에 주문 IN_TRANSIT·판매 SOLD·입찰 COMPLETED까지 시도하지만 일반 구매 입찰 주문에서는 실패한다 (1-3).
- `Xhx14.updateTrackingInfo`는 상태 전이 검사 없이 IN_TRANSIT으로 바꾼다 (`Xhx14.java:41-45`). 검사를 거치는 `updateStatus`와 규칙이 다르다.
- `completeOrder`의 이름과 달리 입찰은 COMPLETED로 바꾸지 않는다 (3절).
- `updateAndCheckShipmentStatus`(`POST /check-status`)는 택배사 응답이 DELIVERED면 `completeOrder`까지 호출하지만(`Xhx14CommandService.java:483-489`), 구매자 `notifyShipmentCompleted`는 호출하지 않는다. 이 경우 구매자 알림은 `completeOrder`의 1건뿐이다.
- 배치 잡 설정 클래스 안의 `shipmentItemProcessor`, `parseCjLogisticsStatus`와 `updateShipmentStatuses()`는 이름은 그럴듯하지만 실행되지 않는다 (2-3).
- 택배사 조회에 `courier` 값은 쓰이지 않는다. 항상 CJ대한통운 추적 URL이다 (2-1).
