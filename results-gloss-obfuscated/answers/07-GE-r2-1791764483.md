# 즉시 구매 처리 흐름 (POST /order-bids/instant)

경로 약칭 (모두 `src/main/java/com/fream/back/domain/` 아래):
- 컨트롤러 = `m16/controller/command/Xzj27CommandController.java`
- OrderBid 서비스 = `m16/service/command/Xzj27CommandService.java`
- Order 서비스 = `m16/service/command/Xdg64CommandService.java`
- 결제 서비스 = `m06/service/command/Xbf54CommandService.java`
- PG 클라이언트 = `m06/p05/Xxv33ApiClient.java`

핵심 요약: 즉시 구매는 **동기 처리**다. 한 트랜잭션 안에서 주문·배송·결제·알림까지 모두 끝낸다. Kafka 경로(`Xdg64EventProducer`/`Xdg64EventConsumer`)는 타지 않는다. 응답 ID는 **OrderBid(주문 입찰) ID**이고, 주문(Order)의 최종 상태는 **PENDING_PAYMENT**다.

## 1. 진입 API, 처리 단계, 동기/비동기, 응답 ID

### 진입
- `POST /order-bids/instant` (클래스 `@RequestMapping("/order-bids")` + `@PostMapping("/instant")`).
  - 근거: `Xzj27CommandController.java:22`, `Xzj27CommandController.java:89-90`
- 요청 본문은 `Xpj49RequestDto`: `saleBidId`, `addressId`, `warehouseStorage`, `paymentRequest`.
  - 근거: `m16/dto/Xpj49RequestDto.java:20-29`

### 단계
1. 컨트롤러가 인증 이메일을 꺼낸다. `Xzj27CommandController.java:92`
2. `enrichPaymentRequest`가 결제 요청에 `userEmail`을 넣고 `orderId`를 null로 비운다. `Xzj27CommandController.java:98`, `Xzj27CommandController.java:119-123`
3. `Xzj27CommandService.createInstantOrderBid`(`@Transactional`)를 호출한다. `Xzj27CommandController.java:101-107`, `Xzj27CommandService.java:118-119`(서비스 파일 기준 줄)
   - 입력 검증(이메일, saleBidId, addressId, paymentRequest null 여부): `Xzj27CommandService.java:154-167`
   - 구매자 조회, 판매 입찰 조회·검증(`sale` 연결 필수): `Xzj27CommandService.java:126-130`, `Xzj27CommandService.java:172-184`
4. `Xdg64CommandService.createInstantOrder`(`@Transactional`)가 주문을 만들고 결제까지 처리한다. `Xdg64CommandService.java:219-319`
   1. 배송지 조회 `addressQueryService.getAddress(email, addressId)` — `Xdg64CommandService.java:238`
   2. Order 저장(`PENDING_PAYMENT`, totalAmount = 판매 입찰가) — `Xdg64CommandService.java:241-247`
   3. `paymentRequest.setOrderId(order.getId())` — `Xdg64CommandService.java:250`
   4. OrderItem 생성(수량 1, 가격 = 입찰가) — `Xdg64CommandService.java:255-256`, `m16/service/command/Xhm58CommandService.java:45-52`
   5. OrderShipment 생성(`PENDING`), 배송지 정보는 조회한 주소에서 복사 — `Xdg64CommandService.java:264-271`, `m12/service/command/Xhx14CommandService.java:61-70`
   6. SaleBid 매칭: `saleBid.assignOrder(order)` + `updateStatus(MATCHED)` 후 `flush` — `Xdg64CommandService.java:279-283`
   7. 판매자 창고 보관 상태 갱신(판매 건이 창고 보관일 때만) — `Xdg64CommandService.java:290-301`
   8. 결제 처리 `paymentCommandService.processPayment` — `Xdg64CommandService.java:305`
5. 다시 `Xzj27CommandService`에서 OrderBid를 생성·저장한다(상태 `MATCHED`, 즉시구매 플래그 true, order·sale 연결). `Xzj27CommandService.java:189-207`
6. 컨트롤러가 결과를 200 OK로 반환한다. `Xzj27CommandController.java:109`

### 동기/비동기
- 동기다. 컨트롤러는 서비스 반환값을 그대로 받아 응답한다. 이벤트 발행·큐잉이 없다. `Xzj27CommandController.java:101-109`
- 비동기(Kafka)는 별도 API인 `POST /{orderId}/process-payment-shipment`에서만 쓴다(`sendOrderProcessingEvent` 후 202 ACCEPTED). 즉시 구매는 이 경로가 아니다. `m16/controller/command/Xdg64CommandController.java:54`
  - `sendOrderProcessingEvent`의 호출처는 이 컨트롤러뿐이다.

### 응답 ID는 무엇의 ID인가
- **OrderBid(주문 입찰, `Xzj27`)의 ID**다. 변수 이름은 `orderId`지만 `createInstantOrderBid(...)`가 돌려주는 `Xzj27`에 `.getId()`를 호출한다. 주문(`Xdg64`)의 ID가 아니다.
  - 근거: `Xzj27CommandController.java:101-107`(반환 타입 `Xzj27`, `.getId()`), `Xzj27CommandService.java:118-119`(서비스 시그니처 반환 `Xzj27`)
- 응답 메시지: "즉시 구매가 성공적으로 처리되었습니다." (`Xzj27CommandController.java:109`)

## 3. 결제 수단별 결과와 성공 여부, 카드 결제 실패 시

결제 수단은 `paymentType`(CARD/ACCOUNT/GENERAL)로 분기한다. `Xbf54CommandService.java:67-80`, `m06/dto/Xbf54RequestDto.java:49-54`, `:102-116`

| 수단 | 처리 | 결제 상태 | `isSuccess` | 근거 |
|---|---|---|---|---|
| 카드(CARD) | PortOne(iamport) 일회성 결제 API 호출. 응답 `status == "success"`일 때만 `PAID` | 성공 시 `PAID`, 그 외 `PENDING` | 성공 시 `true`+결제일 기록. 그 외에도 `true`(아래 참고) | `Xbf54CommandService.java:179`, `:203-206`; `Xqg94.java:26-39` |
| 계좌이체(ACCOUNT) | 은행명만 검증(`Xpt57` enum). PG 호출 없음 | `PENDING` (입금 확인 단계 없음) | `true` (금액 > 0이므로) | `Xbf54CommandService.java:243-248`, `:258-262`; `Xbf54.java:60-63` |
| 일반 결제(GENERAL) | `impUid`가 비어 있지 않은지만 확인. PG 검증 호출 없음, 요청값을 그대로 신뢰 | 즉시 `PAID` | `true`+결제일 기록 | `Xbf54CommandService.java:297-300`, `:313-314` |

`isSuccess`가 `true`가 되는 이유: 결제 엔티티 생성자에서 `setPaidAmount(paidAmount)`를 부르는데, 이 메서드가 `isSuccess = paidAmount > 0`으로 정한다. 즉 실제 결제 성공 여부와 무관하다. `Xqg94.java:38`, `Xbf54.java:60-63`

### 즉시 구매는 끝까지 성공하는가
- 세 수단 모두 예외만 나지 않으면 **끝까지 진행되어 성공 응답(200)을 돌려준다.** 즉시 구매 경로는 `processPayment`가 돌려준 `Xbf54`의 상태·`isSuccess`를 **확인하지 않는다**(반환값을 버림). 계좌이체(`PENDING`)여도 SaleBid 매칭, Sale `SOLD`, "결제가 완료되었습니다" 알림, OrderBid 생성이 그대로 일어난다. `Xdg64CommandService.java:305`
- 대비: 비동기 경로(`Xdg64EventConsumer`)는 `payment.isSuccess()`를 확인하지만(`Xdg64EventConsumer.java:174-176`) 즉시 구매는 이 검증이 없다.
- 결제 금액(`paidAmount`)과 입찰가(`totalAmount`)를 서로 비교하는 코드도 없다. `validatePaymentRequest`는 금액 > 0만 확인한다. `Xbf54CommandService.java:142-145`, `Xdg64CommandService.java:243`

### 카드 결제를 PG가 실패로 응답하면 (두 경우가 다르다)
1. **PG가 HTTP 비-200이거나 응답 `code != 0`인 경우 → 예외 → 전체 롤백.**
   - `processCardPayment`가 `Xdf64Exception("카드 결제 요청 실패: ...")`을 던진다. `Xxv33ApiClient.java:270-275`
   - `createCardPayment`는 `Xbf54Exception`을 그대로 다시 던지고(`Xbf54CommandService.java:218-219`), `processPayment`도 다시 던진다(`:89-94`). `Xdf64Exception`은 `Xbf54Exception`의 하위 클래스다(`m06/exception/Xdf64Exception.java:7`).
   - `createInstantOrder`가 `Xqj91Exception("결제 처리 중 오류가 발생했습니다...")`로 감싼다. `Xdg64CommandService.java:306-309` → `Xdg64Exception`이라 그대로 통과한다(`:312-315`) → `Xzj27CommandService.handleOrderBidCreationException`도 그대로 던진다(`Xzj27CommandService.java:212-214`).
   - `RuntimeException`(`Xks43Exception extends RuntimeException`)이므로 `@Transactional`이 롤백된다. Order, OrderItem, OrderShipment, SaleBid 매칭, 창고 상태 변경이 모두 취소된다. OrderBid는 만들어지지 않는다. 구매자·판매자에게 알림도 가지 않는다(결제 성공 후에만 호출).
   - `@Retryable`이 붙어 있지만 프로젝트에 `@EnableRetry`가 없어 재시도는 동작하지 않는다(`Xxv33ApiClient.java:224-228`; 저장소 전체에서 `EnableRetry` 검색 결과 없음).
2. **PG가 `code == 0`(HTTP 200)이지만 응답 `status`가 `"success"`가 아닌 경우(예: failed) → 예외 없이 성공으로 흘러간다.**
   - 카드 결제 엔티티가 만들어지고, `status`는 기본값 `PENDING`으로 남으며 `isSuccess`는 위 이유로 `true`다. `Xbf54CommandService.java:187-208`, `Xbf54.java:44`, `Xqg94.java:38`
   - `FAILED` 상태로 바꾸는 코드가 없다. 이후 `notifyUsersAndUpdateSaleStatus`가 그대로 돌아 알림 발송과 Sale `SOLD` 처리가 되고(`Xbf54CommandService.java:83`, `:391-406`), OrderBid가 `MATCHED`로 생성되어 200 성공이 나간다.
   - 결과적으로 **결제가 안 된 채 판매 완료·매칭이 확정된다.**

## 4. 알림: 누가, 무엇을, 언제, 어떤 방식으로

### 누가 무엇을
`Xbf54CommandService.sendNotifications`가 결제 직후 두 명에게 만든다. 카테고리 `SHOPPING`, 타입 `BID`.
- **구매자**: "결제가 완료되었습니다. 주문 ID: {orderId}" — `Xbf54CommandService.java:436-445`
- **판매자**(`sale.getSeller()`): "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}" — `Xbf54CommandService.java:447-456`

### 언제
- `processPayment` 안에서, 결제 엔티티를 저장한 **직후** 같은 트랜잭션에서 호출된다(`notifyUsersAndUpdateSaleStatus`). `Xbf54CommandService.java:83`
- Sale을 `SOLD`로 바꾸기 직전에 보낸다(`sendNotifications` → `sale.updateStatus(SOLD)`). `Xbf54CommandService.java:416-419`
- 커밋 이후(after-commit)에 보내는 것이 아니다. 같은 트랜잭션 안이다.

### 어떤 방식으로
- DB에 알림 레코드를 저장하고(`notificationRepository.save`), 이어서 `sendRealTimeNotification`으로 **WebSocket(STOMP) `/user/queue/notifications`**에 push한다. `Xkh73CommandService.java:52-57`, `:303-318`
- push는 Redis 키 `WebSocket:Xrd81:{email}`가 있을 때(= 접속 중)만 한다. 없으면 저장만 하고 끝난다. `Xkh73CommandService.java:37`, `:306-307`, `:318-320`
- **Kafka 알림이나 `/topic/order/{id}` 브로드캐스트는 즉시 구매에서 쓰이지 않는다.** 그것들은 비동기 경로인 `Xdg64EventConsumer.sendSuccessNotification`에만 있다(`Xdg64EventConsumer.java:287-319`). 즉시 구매는 이 컨슈머를 거치지 않는다.
- 알림 전송 예외는 `sendNotifications`/`notifyUsersAndUpdateSaleStatus`에서 잡아 삼킨다(결제는 유지). `Xbf54CommandService.java:457-461`, `:421-425`
  - 단, 알림 생성 서비스가 `@Transactional`이라 그 안에서 예외가 나면 바깥 트랜잭션이 rollback-only로 표시될 수 있다(클래스 `@Transactional`: `Xkh73CommandService.java:27`). 이 경우 마지막 커밋에서 예외가 날 수 있다.

## 5. 최종 주문 상태, 창고 보관을 선택한 경우

### 최종 상태
- Order의 최종 상태는 **`PENDING_PAYMENT`**다. 즉시 구매 경로에는 Order 상태를 `PAYMENT_COMPLETED`/`PREPARING` 등으로 바꾸는 코드가 없다.
  - 근거: 생성 시 `PENDING_PAYMENT`(`Xdg64CommandService.java:244`) 이후 `Xdg64.updateStatus`를 부르는 곳이 없다(`Xdg64CommandService.java:219-319`, `Xzj27CommandService.java:118-149`, `Xbf54CommandService.java:57-107`).
  - 이름·메시지는 "결제 완료"처럼 보이지만(`Xbf54CommandService.java:442`), 실제 Order 상태는 그대로다. 결제 상태 전환(`PAYMENT_COMPLETED` → `PREPARING`)은 비동기 경로(`Xdg64EventConsumer.java:192-195`, `:216-218`)나 `processPaymentAndShipment`(`Xdg64CommandService.java:165-177`)에만 있고 즉시 구매는 호출하지 않는다.
- 다른 엔티티의 최종 상태: SaleBid `MATCHED`, OrderBid `MATCHED`(즉시구매), Sale `SOLD`, OrderShipment `PENDING`, Payment는 수단별(카드 `PAID`/계좌이체 `PENDING`/일반 `PAID`).
- 참고로 `PENDING_PAYMENT`는 비동기 처리 중복 방지 기준이기도 하다(`Xdg64EventConsumer.java:243-244`).

### 구매자가 "창고 보관"을 선택하면 달라지는 것
- **실질적으로 달라지는 것이 없다.** `warehouseStorage` 값은 컨트롤러 로그와 파라미터 전달에만 쓰이고(`Xzj27CommandController.java:94-95`, `:104`), `createInstantOrder`는 `isWarehouseStorage` 인자를 받기만 하고 본문에서 한 번도 사용하지 않는다(`Xdg64CommandService.java:220-221`, 본문 `:222-318`).
- 따라서 구매자 창고 보관(`Xnn94` 생성, `order.assignWarehouseStorage`, `IN_WAREHOUSE`/`COMPLETED` 전환)은 일어나지 않는다. 그 로직은 다른 경로에만 있다(`Xdg64CommandService.java:163-172`, `Xdg64EventConsumer.java:197-212`).
- 창고와 관련된 동작은 구매자 선택이 아니라 **판매 건(Sale)의 설정**으로만 결정된다: `sale.isWarehouseStorage()`가 true면 판매자 보관 건을 `ASSOCIATED_WITH_ORDER`로 바꾼다(`Xdg64CommandService.java:291-293`, `m10/entity/Xgg74.java:43`). 이 경우 보관 정보가 없으면 `findBySale`이 예외를 던져(`m07/service/query/Xnn94QueryService.java:30-33`) `Xdx92Exception`으로 바뀌고 전체가 롤백된다(`Xdg64CommandService.java:295-300`).
- 구매자 선택 여부와 무관하게 OrderShipment(`PENDING`)는 항상 만들어지고, Order는 `PENDING_PAYMENT`로 남는다.
