# 즉시 구매 처리 흐름 (POST /order-bids/instant)

경로 약칭 (모두 `src/main/java/com/fream/back/domain/` 아래):
- 컨트롤러 = `m16/controller/command/Xzj27CommandController.java` (OrderBid 컨트롤러)
- 주문입찰 서비스 = `m16/service/command/Xzj27CommandService.java`
- 주문 서비스 = `m16/service/command/Xdg64CommandService.java`
- 결제 서비스 = `m06/service/command/Xbf54CommandService.java`
- PortOne 클라이언트 = `m06/p05/Xxv33ApiClient.java`

## 1. 진입 API, 처리 단계, 동기/비동기, 응답 ID

1. `POST /order-bids/instant` 로 들어온다. 클래스에 `@RequestMapping("/order-bids")`(`Xzj27CommandController.java:22`), 메서드에 `@PostMapping("/instant")`(`Xzj27CommandController.java:89`)가 붙어 있다. 본문은 `Xpj49RequestDto`(InstantOrderRequestDto)이고 `saleBidId`, `addressId`, `warehouseStorage`, `paymentRequest`를 담는다(`m16/dto/Xpj49RequestDto.java:20-29`).
2. 컨트롤러가 JWT에서 이메일을 꺼내고(`Xzj27CommandController.java:92`), 결제 요청에 `userEmail`을 넣고 `orderId=null`로 초기화한다(`Xzj27CommandController.java:118-120`, `enrichPaymentRequest`).
3. `orderBidCommandService.createInstantOrderBid(...)` 호출(`Xzj27CommandController.java:101-107`)
   - `@Transactional` 메서드(`Xzj27CommandService.java:118-120`)
   - 입력 검증(`Xzj27CommandService.java:123`, 154-167)
   - 구매자 조회(`Xzj27CommandService.java:126`)
   - 판매 입찰(SaleBid) 조회·검증(`Xzj27CommandService.java:129`, 172-184)
4. `orderCommandService.createInstantOrder(...)`(`Xzj27CommandService.java:133-139`, 구현 `Xdg64CommandService.java:219-319`)이 아래 순서로 실행된다.
   1. 배송지 조회: `addressQueryService.getAddress(email, addressId)` (`Xdg64CommandService.java:238`)
   2. Order 저장 (`Xdg64CommandService.java:241-247`)
   3. OrderItem 생성 (`Xdg64CommandService.java:255-256`)
   4. OrderShipment 생성 (`Xdg64CommandService.java:264-271`)
   5. SaleBid 매칭 및 `flush` (`Xdg64CommandService.java:279-283`)
   6. 판매자 창고 보관 상태 갱신 (`Xdg64CommandService.java:290-301`)
   7. 결제 `processPayment` (`Xdg64CommandService.java:304-309`)
5. 이어서 `createInstantOrderBid(order, saleBid, sale)`로 OrderBid를 만들어 저장한다(`Xzj27CommandService.java:142`, 189-207).
6. 컨트롤러가 `ResponseEntity.ok(ResponseDto.success(orderId, "즉시 구매가 성공적으로 처리되었습니다."))`를 반환한다(`Xzj27CommandController.java:109`).

- **동기 처리**다.
  - 요청 스레드 하나, 트랜잭션 하나(`@Transactional`이 전파되어 합류)에서 결제 대행사 호출, 알림 저장, 상태 변경까지 끝난 뒤 응답한다.
  - 이 경로에서는 Kafka 프로듀서를 호출하지 않는다. `Xdg64EventProducer`는 `Xdg64CommandController`에서만 쓰이고(`m16/controller/command/Xdg64CommandController.java:30`), 결제 쪽 `Xbf54EventProducer`는 컨슈머 재시도에서만 쓰인다(`m06/service/kafka/Xbf54EventConsumer.java:191`).
- **응답 ID의 정체**: 변수명은 `orderId`지만 실제 값은 **OrderBid(주문 입찰)의 ID**다.
  - `createInstantOrderBid(...)`가 `Xzj27`(OrderBid)을 반환하고 컨트롤러가 그 `.getId()`를 쓴다(`Xzj27CommandController.java:101-108`).
  - 반환값은 `orderBidRepository.save(orderBid)`의 결과이다(`Xzj27CommandService.java:206`).
  - 따라서 Order(`orders` 테이블)의 ID가 아니다.

## 2. 새로 만들어지는 엔티티와 상태 변화 순서

새로 생기는 엔티티는 **Order, OrderItem, OrderShipment, Payment(카드/계좌/일반 중 하나), OrderBid** 5종이다. 창고 보관(WarehouseStorage) 엔티티는 새로 만들지 않는다(5번 참고).

| 순서 | 동작 | 직후 상태 | 근거 |
|---|---|---|---|
| 1 | Order 생성·저장 | Order = `PENDING_PAYMENT`, `totalAmount = saleBid.bidPrice` | `Xdg64CommandService.java:241-247` |
| 2 | `paymentRequest.setOrderId(order.getId())` | (결제 요청에 주문 ID 주입) | `Xdg64CommandService.java:250` |
| 3 | OrderItem 생성 (수량 1, 가격 = 입찰가) | 상태 값 없음 | `Xdg64CommandService.java:255-256`, `m16/service/command/Xhm58CommandService.java:45-52` |
| 4 | OrderShipment 생성 | Shipment = `PENDING` | `m12/service/command/Xhx14CommandService.java:61-70` |
| 5 | `saleBid.assignOrder(order)` 후 `updateStatus(MATCHED)` | SaleBid = `MATCHED` (`assignOrder`가 이미 `MATCHED`를 세팅하고, 이후 `entityManager.flush()`) | `Xdg64CommandService.java:279-283`, `m10/entity/Xzz58.java:58-60, 66-68` |
| 6 | 판매자가 창고 보관 매물이면(`sale.isWarehouseStorage()`) 창고 상태 갱신 | WarehouseStorage = `ASSOCIATED_WITH_ORDER` | `Xdg64CommandService.java:290-294` |
| 7 | `processPayment` → Payment 생성·저장 | 아래 3번 참고 (카드·일반 = `PAID`, 계좌 = `PENDING`) | `Xdg64CommandService.java:305` |
| 8 | 결제 후 알림 전송, `sale.updateStatus(SOLD)` | Sale = `SOLD` | `Xbf54CommandService.java:383-420` |
| 9 | OrderBid 생성 (`status(MATCHED)`, `markAsInstantPurchase()`) | OrderBid = `MATCHED`, `isInstantPurchase = true` | `Xzj27CommandService.java:192-206` |

- 5번의 SaleBid 상태 enum은 `m10/entity/Xtz73Status`(PENDING/MATCHED/CANCELLED/COMPLETED)이다(`Xdg64CommandService.java:280`).
- 6번의 창고 상태 전이는 `validateStatusTransition`을 거친다(`m07/service/command/Xnn94CommandService.java:130, 232-257`).
  - 창고 레코드가 없으면 `Xnx94Exception`이 나서 `Xdx92Exception`으로 감싸져 전체가 롤백된다(`m07/service/query/Xnn94QueryService.java:30-33`, `Xdg64CommandService.java:295-301`).
- 8번에서 Order·OrderBid가 아직 연결되기 전이라 `order.getOrderBid()`는 `null`이다.
  - 그래서 `saleBidQueryService.findByOrderId(order.getId())`로 SaleBid → Sale을 찾는다(`Xbf54CommandService.java:388-404`).
  - 이 조회가 가능한 이유는 5번에서 `flush`했기 때문이다(`Xdg64CommandService.java:283`).
- 9번 OrderBid 생성이 Payment보다 **뒤**다. 결제 시점에는 OrderBid가 아직 없다.
- Order의 상태는 이 흐름에서 한 번도 갱신되지 않는다(5번 참고).

## 3. 결제 수단별 결과, 성공 여부, 카드 실패 시 동작

공통: `processPayment`는 `order.getId()`와 `requestDto.getOrderId()`, 사용자 이메일, `paidAmount > 0`을 검증한다(`Xbf54CommandService.java:117-146`). 결제 유형은 DTO 클래스(`Xqg94RequestDto` 등)로 결정되고 `switch`로 분기한다(`Xbf54CommandService.java:67-80`, `m06/dto/Xbf54RequestDto.java:74-87`).

| 수단 | 처리 | Payment 상태 | 근거 |
|---|---|---|---|
| 카드(CARD) | 저장된 결제 정보 조회 후 PortOne 호출 | 응답 `status == "success"`이면 `PAID`, 그 외는 `PENDING` | `Xbf54CommandService.java:157-217` |
| 계좌이체(ACCOUNT) | 은행명만 검증, 외부 호출 없음 | `PENDING` | `Xbf54CommandService.java:236-262` |
| 일반(GENERAL) | `impUid` 필수. 외부 검증 호출 없이 클라이언트 값 그대로 신뢰 | `PAID` | `Xbf54CommandService.java:290-316` |

- **카드**
  - `portOneApiClient.processCardPayment`를 호출하고(`Xbf54CommandService.java:179`), 응답 `status == "success"`일 때만 `PAID`로 올린다(`Xbf54CommandService.java:203-206`).
- **계좌이체**
  - 입금 확인 단계가 없다. 상태는 `PENDING`으로 저장만 된다(`Xbf54CommandService.java:260`).
- **일반 결제**
  - 호출된 시점에 즉시 `PAID`로 세팅한다(`Xbf54CommandService.java:313-314`).
- **세 수단 모두 즉시 구매가 끝까지 진행된다.**
  - 계좌이체의 `PENDING`도 예외 없이 지나가므로, 아래 후속 처리(알림, 판매 `SOLD`, OrderBid 생성, 성공 응답)가 실행된다.
  - 결제가 확정되지 않았는데도 `sale.updateStatus(SOLD)`와 구매자 "결제가 완료되었습니다" 알림이 나간다(`Xbf54CommandService.java:83, 383-420, 438-443`).
  - 후속 처리는 결제 상태를 확인하지 않는다.
  - 즉 `PENDING` 계좌이체도 사실상 성공 처리된다.
- `isSuccess`(성공 플래그)는 세 서브타입 모두 생성자에서 `setPaidAmount(paidAmount)`를 호출해 `paidAmount > 0`이면 이미 `true`가 된다(`m06/entity/Xbf54.java:62-63`, `Xqg94.java:38`, `Xkg34.java:28`, `Xjt86.java:30`). 즉 이 플래그는 결제 성공 여부를 반영하지 않는다.

### 결제 대행사가 카드 결제를 실패로 응답하면

두 경우가 다르다.

1. **PortOne이 HTTP 비정상이거나 `code != 0`으로 응답**
   - `Xxv33ApiClient.processCardPayment`가 `Xdf64Exception`("카드 결제 요청 실패: ...")을 던진다(`Xxv33ApiClient.java:270-275`).
   - 이 예외는 `Xbf54Exception`의 하위 클래스다(`m06/exception/Xdf64Exception.java:6`). `Xbf54ApiException`이 아니므로 `@Retryable`(`Xxv33ApiClient.java:224-228`)의 재시도 대상이 아니다.
   - 예외는 `createCardPayment`(`Xbf54CommandService.java:180-181`), `processPayment`(`Xbf54CommandService.java:89-94`)를 거쳐 `Xqj91Exception`(OrderPaymentProcessingFailed)으로 감싸진다(`Xdg64CommandService.java:306-309`).
   - `Xdg64Exception` 하위이므로 그대로 재던져지고(`Xdg64CommandService.java:312-314`, `Xzj27CommandService.java:213-215`), 하나의 트랜잭션이므로 **전부 롤백**된다.
   - 롤백 대상: Order, OrderItem, OrderShipment, SaleBid 매칭, 창고 상태 변경. 이 시점에는 Payment와 OrderBid는 만들어지지 않았다.
   - 클라이언트는 성공 응답을 받지 못하고 오류를 받는다.
2. **HTTP 200, `code == 0`인데 응답 본문 `status`가 `"success"`가 아닌 경우** (예: `failed`)
   - 예외가 없다. Payment는 `PENDING`으로 저장되고(`Xbf54CommandService.java:203-208`, `isSuccess`는 위 이유로 `true`), 흐름은 계속된다.
   - 결과적으로 계좌이체와 같이 알림, `SOLD`, OrderBid `MATCHED`, 성공 응답으로 끝난다.
   - 실제 환불·실패 처리 로직은 없다. `handleRefundIfNecessary`가 정의돼 있지만 어디서도 호출되지 않는다(`Xbf54CommandService.java:341`). `Xbf54Status.FAILED`도 세팅되는 곳이 없다.

## 4. 알림: 누가, 언제, 어떻게

- **알림 주체와 시점**
  - `processPayment`가 결제 저장에 성공한 직후 `notifyUsersAndUpdateSaleStatus`를 호출한다(`Xbf54CommandService.java:83`).
  - 즉 `createInstantOrder` 안, OrderBid 생성보다 앞이다.
  - 실제 알림은 `sendNotifications`에서 보낸다(`Xbf54CommandService.java:403, 434-461`).
- **구매자**: `Xzv64.SHOPPING`, `Xkh73Type.BID`, 메시지 "결제가 완료되었습니다. 주문 ID: {orderId}" (`Xbf54CommandService.java:438-443`).
- **판매자**: `sale.getSeller()`에게 `SHOPPING`, `BID`, "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}" (`Xbf54CommandService.java:447-454`).
- **전달 방식**
  - `Xkh73CommandService.createNotification`이 DB에 알림을 **저장**한다(`m15/service/command/Xkh73CommandService.java:52-54`).
  - 이어서 `sendRealTimeNotification`으로 WebSocket(STOMP) `/queue/notifications`에 푸시한다(`Xkh73CommandService.java:38, 57, 309-313`).
  - 사용자의 WebSocket 연결을 나타내는 Redis 키가 있을 때만 푸시하고, 없으면 저장만 한다(`Xkh73CommandService.java:307, 320-322`).
  - 푸시 실패는 경고 로그만 남기고 무시한다(`Xkh73CommandService.java:315-318`).
  - 알림 저장과 푸시가 요청 스레드에서 같은 트랜잭션 안에서 **동기적으로** 일어난다. Kafka나 비동기 처리는 쓰지 않는다.
- **알림 실패는 무시된다.** `sendNotifications`와 `notifyUsersAndUpdateSaleStatus` 모두 예외를 삼키므로(`Xbf54CommandService.java:457-461, 421-425`), 알림이 실패해도 즉시 구매는 성공한다. 이때 `sale.updateStatus(SOLD)`는 알림 이후 줄에 있어서, 알림 단계에서 예외가 터지면 `sendNotifications`가 삼킨 뒤 계속 진행한다. 반면 `findByOrderId`가 `IllegalArgumentException`을 던지는 경우(`Xzz58QueryService.java:26-29`)는 `SOLD` 갱신 전에 바깥 `catch`로 빠진다(`Xbf54CommandService.java:391, 421-425`).
- 결제 환불 알림(`REFUND`)은 별도의 환불 API 경로에서만 나가며 즉시 구매 흐름에서는 나가지 않는다(`Xbf54CommandService.java:603-659`).

## 5. 주문의 최종 상태와 "창고 보관" 선택의 효과

- **최종 Order 상태는 `PENDING_PAYMENT`다.**
  - `createInstantOrder`는 Order를 `PENDING_PAYMENT`로 만든 뒤(`Xdg64CommandService.java:244`) 어디서도 `order.updateStatus(...)`를 호출하지 않는다(`Xdg64CommandService.java:219-319`). `Xzj27CommandService.createInstantOrderBid`도 Order 상태를 바꾸지 않는다(`Xzj27CommandService.java:189-207`).
  - 결제가 성공(`PAID`)해도 Order는 `PAYMENT_COMPLETED`/`PREPARING`으로 올라가지 않는다. 해당 전이는 다른 메서드 `processPaymentAndShipment`에만 있다(`Xdg64CommandService.java:165-176`). 이 메서드는 즉시 구매 경로에서 호출되지 않는다.
  - 메서드 이름·메시지("즉시 구매가 성공적으로 처리되었습니다")와 달리 주문 자체는 결제 대기 상태로 남는다.
- **같이 확정되는 다른 엔티티의 최종 상태**
  - SaleBid = `MATCHED` (`Xdg64CommandService.java:279-280`)
  - Sale = `SOLD` (`Xbf54CommandService.java:419`)
  - OrderBid = `MATCHED`, 즉시구매 플래그 `true` (`Xzj27CommandService.java:196, 205`)
  - OrderShipment = `PENDING` (`Xhx14CommandService.java:67`)
  - Payment = 카드 성공·일반 `PAID`, 계좌이체 `PENDING` (3번)
- **구매자가 `warehouseStorage = true`를 보내도 달라지는 것이 없다.**
  - 값은 DTO(`Xpj49RequestDto.java:26`) → 컨트롤러(`Xzj27CommandController.java:104`) → `Xzj27CommandService.createInstantOrderBid`(`Xzj27CommandService.java:136`) → `Xdg64CommandService.createInstantOrder`의 파라미터 `isWarehouseStorage`(`Xdg64CommandService.java:221`)까지 전달된다.
  - 그러나 `createInstantOrder` 본문에서 이 파라미터를 읽는 곳이 없다.
  - 창고 분기는 판매자의 `sale.isWarehouseStorage()`만 본다(`Xdg64CommandService.java:292`).
  - 따라서 구매자 창고 보관 요청으로는 `createOrderStorage` 호출, `Xnn94`(WarehouseStorage) 새로 생성, `IN_WAREHOUSE`/`COMPLETED` 전이가 일어나지 않는다. 이 로직은 `processPaymentAndShipment`에만 있고(`Xdg64CommandService.java:163-172`), 즉시 구매 경로에서는 쓰이지 않는다.
  - 구매자의 `true`/`false`와 관계없이 결과는 동일하며, 달라지는 것은 판매자 매물이 창고 보관형인 경우 기존 창고 레코드가 `ASSOCIATED_WITH_ORDER`로 바뀌는 것(2번 6행)뿐이다.
