# 즉시 구매 처리 흐름 분석

경로 약어 (모두 `src/main/java/com/fream/back/domain/` 아래):

- **m16** = order 도메인: `Xzj27` = 주문 입찰(orderBid), `Xdg64` = 주문(order), `Xhm58` = 주문 항목
- **m10** = sale 도메인: `Xzz58` = 판매 입찰(saleBid), `Xgg74` = 판매(sale)
- **m06** = payment 도메인: `Xbf54` = 결제(payment)
- **m15** = notification 도메인: `Xkh73` = 알림(notification)
- **m07** = warehouseStorage 도메인: `Xnn94` = 창고 보관(warehouse storage)

## 1. 진입 API, 처리 단계, 동기/비동기, 응답 ID

**진입 API**: `POST /order-bids/instant`

- 클래스 매핑 `@RequestMapping("/order-bids")`: `m16/controller/command/Xzj27CommandController.java:22`
- 메서드 매핑: `Xzj27CommandController.java:89` (`createInstantOrderBid`)
- 요청 DTO `Xpj49RequestDto`(판매 입찰 ID, 배송지 ID, 창고 보관 여부, 결제 정보): `m16/dto/Xpj49RequestDto.java:20-29`

**처리 단계 (전부 한 호출 스택에서 동기 처리)**

1. 컨트롤러가 인증 사용자 이메일을 추출하고(`Xzj27CommandController.java:92`), 결제 요청에 이메일을 넣고 `orderId=null`로 초기화한다(`:98`, `:119-123`).
2. `Xzj27CommandService.createInstantOrderBid`가 `@Transactional`로 시작한다(`m16/service/command/Xzj27CommandService.java:118-119`).
   - 입력 검증(`:123`, `:154-167`)
   - 구매자 조회(`:126`)
   - 판매 입찰 조회와 검증(`:129`, `:172-184`). 판매 입찰의 상태(이미 MATCHED인지)는 검증하지 않는다.
3. `Xdg64CommandService.createInstantOrder`를 호출한다(`Xzj27CommandService.java:133`; 본체는 `m16/service/command/Xdg64CommandService.java:219-319`).
   - 배송지 조회(`:238`)
   - 주문 저장(`:241-247`)
   - 주문 항목 생성(`:255-256`)
   - 배송 정보 생성(`:264-271`)
   - 판매 입찰 매칭(`:279-283`)
   - 창고 상태 갱신(`:290-301`)
   - 결제 처리(`:305`)
4. 결제 서비스 `Xbf54CommandService.processPayment`가 유형별로 결제를 만든다(`m06/service/command/Xbf54CommandService.java:57-80`). 이어서 알림을 보내고 판매를 SOLD로 바꾼다(`:83`, `:383-426`).
5. 주문 입찰을 `MATCHED`로 만들어 저장한다(`Xzj27CommandService.java:142`, `:189-207`).
6. 컨트롤러가 주문 ID를 응답한다(`Xzj27CommandController.java:101-109`).

**동기/비동기**

- 이 경로에는 Kafka 발행이 없다. HTTP 스레드 안에서 결제 대행사(PortOne) REST 호출까지 끝낸 뒤 응답한다.
- Kafka를 쓰는 곳은 별도 API `POST /{orderId}/process-payment-shipment`다. 이 API는 `sendOrderProcessingEvent`로 발행하고 202 ACCEPTED를 반환한다(`m16/controller/command/Xdg64CommandController.java:54`, `:63-70`).
- 즉시 구매는 그 경로를 타지 않는다. 즉시 구매에서는 `Xdg64EventProducer`나 `Xbf54EventConsumer`가 호출되지 않는다.

**응답 ID**

- 응답 본문의 `Long`은 **새로 만들어진 주문 입찰(Xzj27)의 ID**다. 주문(Xdg64) ID가 아니다.
- 컨트롤러 변수명은 `orderId`지만, 서비스가 반환하는 것은 `Xzj27`이고 그 `getId()`를 꺼낸다(`Xzj27CommandController.java:101-107`, `Xzj27CommandService.java:119`, `:142-144`).
- 주문(Xdg64)은 `orderBid.getOrder()`로만 닿을 수 있고 응답에는 담기지 않는다. 변수명 `orderId`와 성공 메시지가 오해를 부른다.
- 응답 메시지는 "즉시 구매가 성공적으로 처리되었습니다."이며 HTTP 200이다(`:109`).

## 2. 새로 만들어지는 엔티티와 상태 변화 순서

모두 하나의 `@Transactional` 안에서 일어난다(`Xzj27CommandService.java:118`). `Xdg64CommandService.createInstantOrder`, `Xbf54CommandService`(클래스 `@Transactional`, `:37`)는 같은 트랜잭션에 참여한다.

| 순서 | 동작 | 직후 상태 | 근거 |
|---|---|---|---|
| 1 | 주문(Xdg64) 신규 저장 | 주문 `PENDING_PAYMENT`, 금액 = 판매 입찰 가격 | `Xdg64CommandService.java:241-247` |
| 2 | 주문 항목(Xhm58) 신규 | 주문에 연결 | `:255-256` |
| 3 | 배송 정보(Xhx14) 신규. 배송지 ID로 조회한 수령인 정보 사용 | 배송 `PENDING` | `:238`, `:264-271`; 상태는 `m12/service/command/Xhx14CommandService.java:67` |
| 4 | 판매 입찰(Xzz58)에 주문 연결 후 flush | 판매 입찰 `MATCHED` | `:279-283`; `m10/entity/Xzz58.java:58-61` |
| 5 | 판매(Xgg74)가 창고 보관 판매(`sale.isWarehouseStorage()`)면 창고 보관(Xnn94) 상태 변경 | 창고 보관 `ASSOCIATED_WITH_ORDER` | `:291-294`; `m07/service/command/Xnn94CommandService.java:117-133` |
| 6 | 결제(Xbf54) 신규 저장 | 결제 유형별로 다름(3번 참고) | `Xbf54CommandService.java:67-80` |
| 7 | 판매(Xgg74) 상태 변경 | 판매 `SOLD` | `:404` (아래 주의 참고) |
| 8 | 주문 입찰(Xzj27) 신규 저장 | 주문 입찰 `MATCHED`, 즉시 구매 플래그 true | `Xzj27CommandService.java:189-206`; `m16/entity/Xzj27.java:97-99` |

**주의**

- 7번은 `notifyUsersAndUpdateSaleStatus`에서 일어난다.
  - 호출 시점에는 주문 입찰이 아직 없다(8번이 이후). 그래서 `order.getOrderBid()`가 null이다(`Xbf54CommandService.java:388-389`).
  - 코드는 `saleBidQueryService.findByOrderId`로 판매 입찰을 찾고(`:391`), 거기서 판매를 얻어 SOLD로 바꾼다(`:397-405`).
  - 판매 입찰이 4번에서 이미 주문과 연결되어 있으므로 이 경로로 동작한다.
- 주문(Xdg64)의 상태는 `PENDING_PAYMENT`에서 바뀌지 않는다(5번 참고).
- 주문 입찰은 `Xdg64CommandService.processPaymentAndShipment`에서 `MATCHED`로 바뀌는 로직이 있다(`:187-190`). 그러나 즉시 구매는 이 메서드를 호출하지 않는다.

## 3. 결제 수단별 결과와 카드 결제 실패

수단 분기: `Xbf54CommandService.java:67-80`. 모든 수단에서 결제 금액 > 0 등만 검증한다(`:117-146`). 요청의 `paidAmount`와 판매 입찰 가격이 같은지는 검증하지 않는다.

| 수단 | 결제(Xbf54) 결과 | 근거 |
|---|---|---|
| 카드 `CARD` | 결제 대행사 응답의 `status`가 `"success"`이면 `PAID` + `isSuccess=true`. 아니면 기본값 `PENDING` + `isSuccess=false`로 **그대로 저장** | `:203-208`; 기본값 `m06/entity/Xbf54.java:39`, `:44` |
| 계좌이체 `ACCOUNT` | 은행명 검증 후 항상 `PENDING`(입금 대기)으로 저장. 외부 호출 없음 | `:243-262` |
| 일반 `GENERAL` | `impUid`만 있으면 외부 검증 없이 `PAID` + `isSuccess=true` | `:297-316` |

**즉시 구매가 끝까지 성공하는가**

- 결제가 `PAID`든 `PENDING`이든 예외만 안 나면 즉시 구매 자체는 끝까지 진행된다.
- 계좌이체는 결제 `PENDING`(미입금)인데도 판매는 `SOLD`가 되고, 구매자와 판매자에게 "결제가 완료되었습니다" 알림이 간다. 결제 성공 여부를 따지지 않는다(`:83`, `:403-405`, `:438-454`).
- 카드도 대행사가 `status`를 `success`가 아닌 값으로 주면 같은 결과다. 결제는 `PENDING`/`isSuccess=false`로 저장되고 흐름은 계속된다.

**결제 대행사가 카드 결제를 실패로 응답하면**

- 대행사 응답의 `code != 0`이거나 HTTP 200이 아니면 `Xdf64Exception("카드 결제 요청 실패: ...")`이 던져진다(`m06/p05/Xxv33ApiClient.java:270-275`).
- 이 예외는 `Xbf54Exception` 계열이라 그대로 전파된다(`Xxv33ApiClient.java:286-287`; `Xbf54CommandService.java:180-181`, `:218-219`, `:89-94`).
- `createInstantOrder`가 `Xqj91Exception`으로 감싸고(`Xdg64CommandService.java:306-308`), `Xdg64Exception`이므로 그대로 다시 던진다(`:312-314`). `Xzj27CommandService.java:145-146`, `:335-337`도 마찬가지다.
- 같은 `@Transactional` 안이므로 **전체가 롤백된다.** 주문, 주문 항목, 배송, 판매 입찰 매칭, 창고 상태, 결제는 저장되지 않는다. 판매는 SOLD가 되지 않고 알림도 만들어지지 않는다. 예외 핸들러가 에러 응답을 반환한다(`global/exception/Xks43ExceptionHandler.java:325-337`).
- 반대로 대행사가 **`code=0`이면서 `status`가 `success`가 아닌** 값을 주면 예외가 나지 않는다. 앞의 "끝까지 성공" 경우다.
- 네트워크 오류(`RestClientException`)는 `Xbf54ApiException`으로 바뀌고 `@Retryable`로 최대 3회 재시도된다(`Xxv33ApiClient.java:224-228`, `:288-290`). `code != 0`인 `Xdf64Exception`은 재시도 대상이 아니다.

## 4. 알림 수신자, 시점, 전달 방식

**수신자와 내용** (`Xbf54CommandService.sendNotifications`, `:434-462`)

- **구매자**: "결제가 완료되었습니다. 주문 ID: {orderId}" (`:437-443`)
- **판매자**: `sale.getSeller()`에게 "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}" (`:447-454`)
- 둘 다 카테고리 `Xzv64.SHOPPING`, 타입 `Xkh73Type.BID`다.

**시점**

- 결제 저장 직후, 판매를 SOLD로 바꾸기 직전, 같은 요청·같은 트랜잭션 안에서 보낸다(`:83`, `:403-404`).
- 주문 입찰 저장보다 앞이다.
- 알림은 결제 상태와 무관하게 보낸다. 3번에서 말한 `PENDING`도 마찬가지다.

**전달 방식** (`m15/service/command/Xkh73CommandService.java:44-59`, `:303-323`)

1. 알림을 DB에 저장한다(`:52-53`).
2. 수신자의 Redis 키(`WebSocket:Xrd81:{email}`)가 있으면(WebSocket 접속 중) STOMP로 `/queue/notifications`에 사용자별 푸시한다(`:307-313`).
3. 접속 중이 아니면 DB 저장만 하고 푸시는 하지 않는다(`:320-322`).
4. 알림 생성·전송 오류는 로그만 남기고 삼킨다. 알림이 실패해도 결제와 주문은 롤백되지 않는다(`Xbf54CommandService.java:457-461`, `:421-425`).
   - 알림 저장 자체가 DB 예외를 일으켜 트랜잭션이 rollback-only로 마킹되는 경우는 별개다. 코드상 이 경로에서 별도 처리는 없다.
5. 구매자와 판매자 외에 다른 알림은 이 흐름에서 만들지 않는다. 배송 완료 알림 등은 별도 흐름이다.

## 5. 주문의 최종 상태와 "창고 보관" 선택의 영향

**주문의 최종 상태: `PENDING_PAYMENT`**

- `createInstantOrder`는 주문을 `PENDING_PAYMENT`로 만든다(`Xdg64CommandService.java:241-245`).
- 이후 `updateStatus`를 한 번도 호출하지 않는다(`:219-319` 전체).
- `PAYMENT_COMPLETED`, `PREPARING`, `IN_WAREHOUSE`, `COMPLETED`로 바꾸는 코드는 `processPaymentAndShipment`(`:165-177`)에만 있다. 즉시 구매는 이를 호출하지 않으므로 결제가 `PAID`여도 주문은 `PENDING_PAYMENT`로 남는다.
- 성공 메시지("즉시 구매가 성공적으로 처리되었습니다")와 달리 주문 상태는 결제 완료로 갱신되지 않는다. 실제 동작 기준으로 답한다.

**각 엔티티의 최종 상태**

| 엔티티 | 최종 상태 |
|---|---|
| 주문(Xdg64) | `PENDING_PAYMENT` |
| 판매 입찰(Xzz58) | `MATCHED` |
| 주문 입찰(Xzj27) | `MATCHED` |
| 판매(Xgg74) | `SOLD` |
| 배송 정보(Xhx14) | `PENDING` |
| 결제(Xbf54) | 카드 성공 `PAID` / 카드 비성공 `PENDING` / 계좌이체 `PENDING` / 일반 `PAID` |

**구매자가 "창고 보관"을 선택한 경우: 실제로 아무것도 달라지지 않는다.**

- 컨트롤러는 `requestDto.isWarehouseStorage()`를 서비스로 넘긴다(`Xzj27CommandController.java:105`). 서비스도 `createInstantOrder`로 그대로 전달한다(`Xzj27CommandService.java:133-139`).
- 그러나 `createInstantOrder` 본문은 구매자 쪽 `isWarehouseStorage` 인자를 읽지 않는다. 파라미터는 `:221`에 선언만 되어 있다.
- 창고 관련 분기는 **판매자 쪽** `sale.isWarehouseStorage()`만 본다(`:291-294`). 이 값이 true일 때 기존 창고 보관 건을 `ASSOCIATED_WITH_ORDER`로 바꿀 뿐이다.
- 구매자 창고 보관 플래그에 따른 처리는 `processPaymentAndShipment`에만 있다(`:163-172`). 즉시 구매 경로에서는 다음이 일어나지 않는다.
  - 새 창고 보관(Xnn94) 생성(`createOrderStorage`)
  - 주문 상태 `IN_WAREHOUSE` 전이
  - 주문 `COMPLETED` 전이
- 즉시 구매 경로에서 구매자 창고 선택은 로그에만 찍힌다(`Xzj27CommandController.java:94-95`).
- 판매자가 창고 보관 판매인데 연결된 창고 정보가 없으면 `findBySale`이 예외를 던져 `Xdx92Exception`으로 바뀌고 전체가 롤백된다(`m07/service/query/Xnn94QueryService.java:30-32`; `Xdg64CommandService.java:295-300`).
