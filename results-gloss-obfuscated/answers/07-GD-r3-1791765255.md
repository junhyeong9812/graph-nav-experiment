# 즉시 구매 처리 흐름 분석

경로 약어: `D` = `src/main/java/com/fream/back/domain`

코드 이름 대응: Xzj27 = 주문 입찰(OrderBid), Xdg64 = 주문(Order), Xzz58 = 판매 입찰(SaleBid), Xgg74 = 판매(Sale), Xbf54 = 결제(Payment), Xnn94 = 창고 보관(WarehouseStorage), Xhx14 = 주문 배송(OrderShipment), Xhm58 = 주문 항목(OrderItem), Xkh73 = 알림(Notification).

## 1. 진입 API, 처리 단계, 동기/비동기, 응답 ID

1. **진입 API**: `POST /order-bids/instant` (`D/m16/controller/command/Xzj27CommandController.java:22`, `:89-90`). 본문은 `Xpj49RequestDto`(saleBidId, addressId, warehouseStorage, paymentRequest) (`D/m16/dto/Xpj49RequestDto.java`).
2. **컨트롤러 단계**
   - 로그인 이메일을 추출한다 (`Xzj27CommandController.java:92`).
   - 결제 요청에 `userEmail`을 넣고 `orderId`를 `null`로 비운다 (`:98`, `:119-123`).
   - `orderBidCommandService.createInstantOrderBid(...)`를 호출한다 (`:101-107`).
3. **서비스 단계 1 - 주문 입찰 서비스** (`D/m16/service/command/Xzj27CommandService.java:119-149`, `@Transactional`)
   - 입력값을 검증한다 (`:124`, `:154-168`).
   - 구매자를 조회한다 (`:127`).
   - 판매 입찰과 그 판매(sale)를 조회·검증한다 (`:129-130`, `:172-186`).
   - `orderCommandService.createInstantOrder(...)`를 호출한다 (`:133-139`).
   - 그 뒤 주문 입찰 Xzj27을 만들어 저장한다 (`:142`, `:189-207`).
4. **서비스 단계 2 - 주문 서비스** `Xdg64CommandService.createInstantOrder` (`D/m16/service/command/Xdg64CommandService.java:219-319`, `@Transactional`). 순서는 다음과 같다.
   1. 배송지 조회 (`:238`)
   2. 주문 생성·저장 (`:241-247`)
   3. 결제 요청에 orderId 주입 (`:250`)
   4. 주문 항목 생성 (`:255-256`)
   5. 배송 정보 생성 (`:264-271`)
   6. 판매 입찰 매칭 + flush (`:279-283`)
   7. 판매자 창고 보관 상태 갱신 (`:290-301`)
   8. 결제 처리 `paymentCommandService.processPayment` (`:305`)
5. **결제 서비스** `Xbf54CommandService.processPayment`
   - 결제 유형별로 분기한다 (`D/m06/service/command/Xbf54CommandService.java:67-80`).
   - 이어서 `notifyUsersAndUpdateSaleStatus`를 호출한다 (`:83`).
6. **동기 처리다.**
   - Kafka 발행이나 `@Async`가 없다. 컨트롤러 → 서비스 → 결제 API 호출 → 알림 저장까지 한 요청 스레드, 한 트랜잭션에서 끝난다 (`Xzj27CommandService.java:119` `@Transactional`; 이 서비스와 `Xbf54CommandService`에는 Kafka/Async 사용이 없다).
   - `order-processing-topic` Kafka 소비자(`D/m16/service/kafka/Xdg64EventConsumer.java:55-61`)는 일반 주문 경로용이다. 즉시 구매는 이를 거치지 않는다.
   - 외부 결제 대행사(PortOne) 호출도 이 요청 안에서 동기로 수행된다 (`D/m06/p05/Xxv33ApiClient.java:229`, `:270`).
7. **응답으로 돌려주는 ID는 주문(Order) ID가 아니라 "주문 입찰(OrderBid, Xzj27)의 ID"다.**
   - 서비스가 반환하는 것은 Xzj27이고 (`Xzj27CommandService.java:142-144`), 컨트롤러는 그 `.getId()`를 받아 변수명만 `orderId`로 쓴다 (`Xzj27CommandController.java:101-107`).
   - 메시지는 "즉시 구매가 성공적으로 처리되었습니다."이다 (`:109`).
   - 주문 ID(Xdg64.id)는 응답에 담기지 않는다.

## 2. 새로 만들어지는 엔티티와 상태 변화 순서

즉시 구매에서 새로 생기는 것은 Order, OrderItem, OrderShipment, Payment, OrderBid 5종이다.

| 순서 | 동작 | 근거 | 직후 상태 |
|---|---|---|---|
| 1 | **주문 Xdg64 생성** | `Xdg64CommandService.java:241-247` | `PENDING_PAYMENT`, totalAmount = 판매 입찰가 |
| 2 | 주문 항목 Xhm58 생성 (수량 1, 가격 = 입찰가) | `Xdg64CommandService.java:255-256`, `D/m16/service/command/Xhm58CommandService.java:34-52` | - |
| 3 | **주문 배송 Xhx14 생성** (주소는 addressId로 조회한 값) | `Xdg64CommandService.java:264-271`, `D/m12/service/command/Xhx14CommandService.java:56-75` | 배송 `Xpb98Status.PENDING` |
| 4 | **판매 입찰 Xzz58 갱신**: `assignOrder`(주문 연결) + `updateStatus(MATCHED)`, 이어서 flush | `Xdg64CommandService.java:279-283`, `D/m10/entity/Xzz58.java:58-61`, `:66` | 판매 입찰 `MATCHED` (기존 `PENDING`, `Xzz58.java:37`) |
| 5 | 판매자가 창고 보관 판매(`sale.isWarehouseStorage()`)면 창고 보관 상태를 `ASSOCIATED_WITH_ORDER`로 변경 | `Xdg64CommandService.java:290-293`, `D/m07/service/command/Xnn94CommandService.java:116-140` | 창고 보관 `ASSOCIATED_WITH_ORDER` |
| 6 | **결제 Xbf54 생성·저장** (유형별은 3번 참고). 결제 상태 기본값은 `PENDING` | `Xbf54CommandService.java:157-333`, `D/m06/entity/Xbf54.java:44` | 결제 `PAID` 또는 `PENDING` (3번 참고) |
| 7 | 결제 직후 `notifyUsersAndUpdateSaleStatus`: 구매자·판매자 알림 후 **판매 Xgg74 `SOLD`** | `Xbf54CommandService.java:383-407`, `:404` | 판매 `SOLD` |
| 8 | **주문 입찰 Xzj27 생성·저장** (`status=MATCHED`, `assignOrder`도 MATCHED로 설정, `markAsInstantPurchase`) | `Xzj27CommandService.java:189-206`, `:205`, `D/m16/entity/Xzj27.java:60-75`, `:97` | 주문 입찰 `MATCHED`, `isInstantPurchase=true` |

주의할 점은 다음과 같다.

- 주문 상태는 1번 이후 즉시 구매 경로에서 한 번도 바뀌지 않는다. `createInstantOrder` 안에는 `order.updateStatus(...)` 호출이 없다 (`Xdg64CommandService.java:219-319`).
- `PAYMENT_COMPLETED`/`PREPARING` 등으로 바꾸는 코드는 `processPaymentAndShipment`(`:111-202`)와 Kafka 소비자(`Xdg64EventConsumer.java:192-220`)에만 있고, 즉시 구매는 호출하지 않는다.
- 결제 직후에는 `order.getOrderBid()`가 `null`이다. 주문 입찰이 결제 이후에 만들어지기 때문이다 (`Xbf54CommandService.java:388-391`).
- 그래서 결제 서비스는 `saleBidQueryService.findByOrderId`로 판매 입찰을 찾아 그 판매를 SOLD 처리한다 (`:391-404`). 4번에서 flush 했기 때문에 조회된다.
- 주문 입찰의 `sale`은 판매 입찰의 sale이다 (`Xzj27CommandService.java:130`, `:196-197`).

## 3. 결제 수단별 결과, 성공 여부, 카드 실패 시 동작

결제 수단은 `getResolvedPaymentType()` 값(CARD / ACCOUNT / GENERAL)으로 분기한다 (`Xbf54CommandService.java:67-80`). 공통 검증은 다음과 같다.

- 요청의 orderId·userEmail이 실제 주문·사용자와 같아야 한다 (`:131-139`).
- 금액이 0보다 커야 한다 (`:142-145`).
- 결제 금액이 입찰가와 같은지는 검증하지 않는다.

| 수단 | 처리 | 결제 상태 | isSuccess | 근거 |
|---|---|---|---|---|
| CARD | 저장된 결제 수단 조회 → PortOne 카드 결제 API 호출 → 응답의 `status`가 `"success"`일 때만 PAID | `PAID` (그 외에는 기본값 `PENDING`) | PAID일 때만 true | `Xbf54CommandService.java:157-217`, 특히 `:179`, `:203-206` |
| ACCOUNT(계좌이체) | 은행명만 검증하고 외부 호출 없이 저장 | 항상 `PENDING` | false | `:236-271`, `:260` |
| GENERAL(일반 결제) | `impUid` 필수. 클라이언트가 준 값을 그대로 저장하고 PortOne 검증은 없음 | 즉시 `PAID` | true | `:290-325`, `:297-314` |

**즉시 구매가 끝까지 성공하는가**

- 계좌이체는 결제가 `PENDING`인 채로 예외 없이 끝난다. 이후 흐름은 결제 성공 여부를 확인하지 않는다.
- `processPayment`는 성공 여부와 무관하게 알림과 `sale.SOLD`를 수행한다 (`Xbf54CommandService.java:83`, `:383-420`).
- 주문 입찰 생성도 이어서 수행하며, 컨트롤러는 "즉시 구매가 성공적으로 처리되었습니다."를 응답한다 (`Xzj27CommandController.java:109`).
- 반환값 `payment`는 버려지고 주문에 `assignPayment`도 호출하지 않는다 (`Xdg64CommandService.java:305`).
- 결과적으로 계좌이체(PENDING 결제)도 요청은 성공한 것처럼 끝나고, 판매는 `SOLD`, 판매 입찰·주문 입찰은 `MATCHED`가 된다.
- 즉 "결제 완료 → 구매 확정"이 아니라 "결제 시도 → 즉시 매칭·판매 완료 처리"로 동작한다.
- 이에 비해 일반 주문 경로는 `payment.isSuccess()`가 아니면 예외를 던진다 (`Xdg64EventConsumer.java:174-176`). 즉시 구매에는 이 검사가 없다.

**결제 대행사가 카드 결제를 실패로 응답하면**

- HTTP 상태가 200이 아니거나 응답 body의 `code`가 0이 아니면 `Xdf64Exception("카드 결제 요청 실패: ...")`을 던진다 (`D/m06/p05/Xxv33ApiClient.java:270-275`).
- 이 예외는 `createCardPayment`·`processPayment`에서 `Xbf54Exception`으로 그대로 재전파된다 (`Xbf54CommandService.java:89-94`, `:218-219`).
- `createInstantOrder`는 이를 `Xqj91Exception`(주문 도메인의 결제 처리 실패)으로 감싸 던지고 (`Xdg64CommandService.java:305-309`), 바깥 `catch`에서 `Xdg64Exception`이므로 그대로 재던진다 (`:312-315`).
- `Xzj27CommandService`는 `Xdg64Exception`을 그대로 재던진다 (`:145-147`, `:212-218`의 `handleOrderBidCreationException`).
- `Xks43Exception`은 `RuntimeException`이다 (`D/global/exception/Xks43Exception.java:10`).
- 따라서 `@Transactional`이 롤백되어 주문, 주문 항목, 배송, 판매 입찰 MATCHED, 창고 상태 변경이 모두 되돌려진다. 주문 입찰은 아직 만들어지기 전이고, 알림도 보내지지 않는다.
- 판매 Xgg74는 `SOLD`로 바뀌지 않는다. 클라이언트는 `Xks43ExceptionHandler`가 변환한 에러 응답을 받는다.
- 단, 대행사가 `code=0`으로 응답하되 `response.status`가 `"success"`가 아닌 경우는 예외 없이 `PENDING` 결제로 저장된다 (`:203-208`).
- 이때는 위 "끝까지 성공" 설명대로 계속 진행되어 알림·`SOLD`·주문 입찰 `MATCHED`가 일어난다.
- 카드 결제 호출은 `@Retryable`이 붙어 있지만 재시도 대상은 `Xbf54ApiException`(통신 오류)뿐이다 (`Xxv33ApiClient.java:224-228`). 결제 거절(`Xdf64Exception`)은 재시도하지 않는다.

## 4. 누가 어떤 알림을 받나, 언제·어떤 방식으로 전달되나

1. **발송 시점**
   - 결제 처리가 끝난 직후, 같은 요청·같은 트랜잭션 안에서 발송한다 (`Xbf54CommandService.java:83`, `:383-420`).
   - 주문 입찰이 생성되기 전이며, 결제가 PENDING이어도 발송한다.
2. **받는 사람과 내용** (`Xbf54CommandService.java:434-456`)
   - 구매자(`order.getUser()`): `Xzv64.SHOPPING` / `Xkh73Type.BID`, "결제가 완료되었습니다. 주문 ID: {orderId}".
   - 판매자(`sale.getSeller()`): `SHOPPING` / `BID`, "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}".
3. **전달 방식** (`D/m15/service/command/Xkh73CommandService.java:44-67`)
   - DB에 알림 엔티티를 저장한다 (`:52-53`).
   - 사용자의 Redis 키(`WebSocket:Xrd81:{email}`)가 있을 때만 STOMP 개인 큐 `/queue/notifications`로 푸시한다 (`:303-323`, `:37-38`).
   - WebSocket 연결이 없으면 저장만 되고 푸시는 없다.
   - Kafka를 통한 알림은 이 경로에서는 쓰이지 않는다. `Xdg64EventConsumer`의 `notification-topic` 발행은 일반 주문 경로에만 있다.
4. **실패 처리**
   - `sendNotifications`와 `notifyUsersAndUpdateSaleStatus`는 예외를 삼키고 로그만 남긴다 (`Xbf54CommandService.java:457-461`, `:421-425`).
   - 알림 실패로 주문 처리가 실패하지는 않는다.
5. 즉시 구매 경로에서 `Xdg64EventConsumer`의 `ORDER_COMPLETED` WebSocket/Kafka 알림(`:287-329`)은 발송되지 않는다.

## 5. 최종 주문 상태와 "창고 보관" 선택의 영향

1. **주문(Xdg64)의 최종 상태는 `PENDING_PAYMENT`다.**
   - 주문은 `PENDING_PAYMENT`로 생성된다 (`Xdg64CommandService.java:241-245`).
   - 이후 즉시 구매 경로에서 `updateStatus`가 호출되지 않는다 (`:219-319`).
   - 결제가 `PAID`든 `PENDING`이든 마찬가지다.
   - 메서드 이름·응답 메시지("즉시 구매가 성공적으로 처리")가 암시하는 `PAYMENT_COMPLETED`/`PREPARING` 등으로는 가지 않는다.
2. **함께 남는 상태**
   - 판매 입찰 `MATCHED`.
   - 주문 입찰 `MATCHED`, `isInstantPurchase=true`.
   - 판매 `SOLD`.
   - 결제는 카드·일반이 `PAID`, 계좌이체(또는 카드 `status`가 success가 아닐 때)는 `PENDING`.
   - 배송은 `PENDING`.
3. **구매자가 "창고 보관"을 선택하면 달라지는 것이 사실상 없다.**
   - 컨트롤러가 `isWarehouseStorage`를 서비스로 전달하고 (`Xzj27CommandController.java:104`), `Xzj27CommandService`도 `createInstantOrder`로 넘기지만 (`:133-139`), `createInstantOrder` 본문에서는 이 매개변수를 읽지 않는다 (`Xdg64CommandService.java:219-319`; 본문의 `isWarehouseStorage` 참조는 `sale.isWarehouseStorage()`, `:292` 하나뿐이다).
   - 이는 구매자 선택이 아니라 "판매자가 창고 보관으로 올린 판매인지"를 보는 값이다.
   - 따라서 구매자용 창고 보관 엔티티(`createOrderStorage`)는 만들어지지 않는다. 호출은 `processPaymentAndShipment`(`Xdg64CommandService.java:163-173`)와 Kafka 소비자(`Xdg64EventConsumer.java:197-200`)에만 있다.
   - `IN_WAREHOUSE`/`COMPLETED`로의 주문 상태 전이도 일어나지 않는다.
   - 창고 보관 여부와 관계없이 주문은 `PENDING_PAYMENT`로 남는다.
   - 창고 관련으로 일어나는 변경은 판매자 쪽뿐이다. 판매(sale)가 창고 보관 판매이면 해당 창고 보관 건이 `ASSOCIATED_WITH_ORDER`로 바뀐다 (`:290-293`).
