# 구매자 배송: 운송장 등록 → 배송 완료

경로 약어: `B` = `src/main/java/com/fream/back`
엔티티 코드명: Xhx14=주문 배송(OrderShipment), Xdg64=주문(Order), Xzj27=주문 입찰(OrderBid), Xzz58=판매 입찰(SaleBid), Xgg74=판매(Sale), Xkh73=알림.

**결론 요약**
- 운송장 등록 API는 일반 구매 입찰 주문(결제·배송 처리 후 `PREPARING`)에서 항상 실패한다. 주문 상태 `IN_TRANSIT` 전환이 막히기 때문이다.
- 즉시 구매 주문은 `PENDING_PAYMENT`로 남아 있어 같은 이유로 등록이 실패한다. 다만 배송 완료 처리 코드(`completeOrder`) 자체는 즉시 구매 주문에서만 끝까지 진행된다.

## 1. 운송장 등록 요청

### 1-1. 진입 API
1. `PATCH /shipments/order/{shipmentId}/status`, 바디는 `Xhx14RequestDto`(courier, trackingNumber).
   - 클래스 매핑: `B/domain/m12/controller/command/Xhx14CommandController.java:20`
   - 메서드 매핑: `Xhx14CommandController.java:33`
2. 컨트롤러가 `Xhx14CommandService.updateTrackingInfo(shipmentId, courier, trackingNumber)`를 호출한다: `Xhx14CommandController.java:41`
3. 참고로 `POST /shipments/order/{shipmentId}/check-status`(`Xhx14CommandController.java:58`)는 운송장 등록과 즉시 조회를 겸하는 별도 경로다. 이는 `updateAndCheckShipmentStatus`(`B/domain/m12/service/command/Xhx14CommandService.java:452`)를 호출한다.

### 1-2. 코드가 의도한 상태 변경·알림 순서 (`Xhx14CommandService.updateTrackingInfo`, `Xhx14CommandService.java:238-300`)
1. 입력 검증: courier·trackingNumber가 비어 있으면 `TRACKING_INFO_REQUIRED`(S004, 400)를 던진다. (`Xhx14CommandService.java:239-245`)
2. 배송(Xhx14) 조회 후 `shipment.updateTrackingInfo`(`:256`)를 호출한다.
   - courier와 trackingNumber를 저장하고, 상태를 `canTransitionTo` 검사 없이 곧바로 `IN_TRANSIT`으로 세팅한다. (`B/domain/m12/entity/Xhx14.java:32-36`)
   - 배송 생성 시 초기 상태는 `PENDING`이다. (`Xhx14CommandService.java:55-80`의 createOrderShipment, `Xpb98Status.PENDING`)
3. 주문(Xdg64)을 `IN_TRANSIT`으로 변경한다. (`Xhx14CommandService.java:260`)
4. 구매자에게 알림 "상품이 출발하였습니다. 주문 ID: …"을 보낸다. (`Xhx14CommandService.java:266`)
5. `updateSaleStatusToSold(orderId)`를 호출한다. (`:276`, 본문 `:111-188`)
   - 판매 입찰(Xzz58) 조회: `Xzz58QueryService.findByOrderId`는 없으면 `null`이 아니라 IllegalArgumentException을 던진다. (`B/domain/m10/service/query/Xzz58QueryService.java:26-29`)
   - 판매(Xgg74)가 `SOLD`로 전환 가능하면 `SOLD`로 바꾸고 판매자에게 알림 "상품이 성공적으로 판매 완료되었습니다."를 보낸다. (`Xhx14CommandService.java:119-133`)
   - 이어서 Xzj27 쪽 sale도 같은 방식으로 처리한다. (`:151-164`)
6. 창고 보관 상품이면 창고 상태를 갱신한다. (`:279-287`)
7. `updateOrderAndSaleBidStatusToCompleted`를 호출한다. (`:289`, 본문 `:412-440`)
   - 주문 입찰(Xzj27)과 판매 입찰(Xzz58)이 `MATCHED`이면 `COMPLETED`로 바꾼다.
   - 즉 운송장 등록 시점에 이미 입찰이 COMPLETED, 판매가 SOLD가 되도록 짜여 있다. 메서드 이름과 달리 "배송 완료"와는 무관하다.

### 1-3. 결제·배송 처리를 마친 일반 구매 입찰 주문(즉시 구매 아님)에서는 끝까지 성공하지 않는다
- **실패 지점**: 3단계 `order.updateStatus(Xdg64Status.IN_TRANSIT)` (`Xhx14CommandService.java:260`).
- **이유**
  1. 결제·배송 처리(`processPaymentAndShipment`)가 끝난 비창고 일반 주문의 상태는 `PAYMENT_COMPLETED → PREPARING`에서 멈춘다. (`B/domain/m16/service/command/Xdg64CommandService.java:175-176`)
     - Kafka 소비 경로도 마찬가지로 `PREPARING`에서 끝난다. (`B/domain/m16/service/kafka/Xdg64EventConsumer.java:216-218`)
  2. 상태 전이표에서 `PREPARING`이 갈 수 있는 곳은 `IN_WAREHOUSE`, `SHIPMENT_STARTED`뿐이다. `IN_TRANSIT`은 `SHIPMENT_STARTED`에서만 갈 수 있다. (`B/domain/m16/entity/Xdg64Status.java:26,28`)
  3. `Xdg64.updateStatus`는 허용되지 않는 전환이면 `Xxc76StatusException`을 던진다. (`B/domain/m16/entity/Xdg64.java:113-120`)
  4. 이 예외는 `Xdg64Exception` 계열이라 `catch (Xpb98Exception)`에 걸리지 않는다. 그래서 일반 `catch (Exception)`에서 `Xpb98Exception(SHIPMENT_NOT_FOUND)`로 감싸져 다시 던져진다. (`Xhx14CommandService.java:295-300`)
  5. `SHIPMENT_STARTED`로 바꾸는 코드는 이 흐름 어디에도 없다.
- **저장되는 것**
  - 없다. 예외가 `@Transactional` 메서드 밖으로 전파되므로 전체가 롤백된다. 운송장·택배사·`IN_TRANSIT`은 메모리에서만 바뀌었고 DB에 남지 않는다.
  - 구매자·판매자 알림도 생성되지 않는다. 4단계 알림 생성(`:266`)보다 앞에서 실패한다.
  - 배송은 `PENDING`, 주문은 `PREPARING`, 입찰은 `MATCHED` 그대로다.
- **응답**
  - `Xks43ExceptionHandler`가 `ErrorCode`의 상태를 그대로 쓴다. (`B/global/exception/Xks43ExceptionHandler.java:459-473`)
  - HTTP **404**, 바디 `ErrorResponse`는 코드 `S001`, 메시지 "배송 정보를 찾을 수 없습니다."이다. (`B/domain/m12/exception/Xpb98ErrorCode.java:12`)
  - 실제 원인("상태 전환이 허용되지 않습니다: PREPARING -> IN_TRANSIT")은 예외 메시지에만 있고 응답 바디에는 나가지 않는다. 에러코드가 "배송 없음"이라 오해를 부른다.
- 같은 이유로 `POST /check-status`도 (조회 결과가 DELIVERED여도) 순서상 `completeOrder`에서 실패한다. 4절 참고.

## 2. 배송 완료 감지

### 2-1. 누가·언제·어떻게
- **누가**: 서버 내부 스프링 스케줄러 `Xpb98BatchScheduler`(`@Component`). (`B/global/config/Xpb98BatchScheduler.java:13-15`)
- **언제**: `@Scheduled(cron = "0 0 */6 * * *")`, 즉 **6시간마다**(매일 00:00·06:00·12:00·18:00, 서버 시간대). (`Xpb98BatchScheduler.java:34`)
- **어떻게**
  - 매번 `timestamp` 잡 파라미터로 `jobLauncher.run(updateShipmentStatusesJob, …)`를 실행한다. (`Xpb98BatchScheduler.java:36-40`)
  - 실행 중 예외는 `printStackTrace`만 하고 삼킨다. (`Xpb98BatchScheduler.java:41-43`)
  - 스프링 배치가 켜져 있다. (`B/global/config/Xct70Config.java:15` `@EnableBatchProcessing`)

### 2-2. 조회 대상
- 잡 `updateShipmentStatusesJob`의 reader 쿼리: `SELECT s FROM Xhx14 s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL`. (`B/domain/m12/config/Xqv91JobConfig.java:95`)
- 페이지 크기·청크 크기는 50이다. (`Xqv91JobConfig.java:51,94`)

### 2-3. 실제로 실행되는 처리 코드
- **실제 실행**: `Xth19Processor` (Playwright 기반)
  - 스텝이 `new Xth19Processor(playwrightBrowserManager(), notificationService, orderService)`를 processor로 쓴다. (`Xqv91JobConfig.java:69-73`)
  - 처리 본문: `B/domain/m12/config/Xth19Processor.java:56-157`
  - 브라우저는 `Xmb36Listener`가 스텝 전후로 열고 닫는다. (`Xqv91JobConfig.java:80`, `B/domain/m12/config/Xmb36Listener.java:14-25`)
- **실행되지 않는 유사 코드**
  - `Xqv91JobConfig.shipmentItemProcessor()` 빈(`:104-177`)은 스텝에 연결되지 않은 죽은 빈이다. 같은 파일의 `parseCjLogisticsStatus`(`:186`, Jsoup 직접 호출)도 미사용이다.
  - `Xhx14CommandService.updateShipmentStatuses()`(`Xhx14CommandService.java:308-309`)는 호출하는 곳이 없다(스케줄러도 없음). 이 메서드는 `Xxx20.getCurrentTrackingStatus`를 쓰며, 안에서 직접 주문을 COMPLETED로 바꾸는 구현이 따로 있다. (`:355`)
  - `Xxx20`(`B/global/utils/Xxx20.java:33`)은 수동 `check-status` API 경로(`Xhx14CommandService.java:477`)에서만 쓰인다.

### 2-4. 택배사 상태 문자열 → 내부 상태
CJ대한통운 조회 페이지(`https://trace.cjlogistics.com/next/tracking.html?wblNo=`)에서 `tbody#statusDetail tr`의 마지막 행, 5번째 `td` 텍스트를 읽는다. (`Xth19Processor.java:28-29,181`)

매핑은 `Xth19Processor.java:220-226`이다.

| 택배사 문자열 | 내부 상태 `Xpb98Status` |
|---|---|
| `"배송완료"` | `DELIVERED` |
| `"배송출발"` | `OUT_FOR_DELIVERY` |
| 그 외 모든 값(`"집화처리"` 등) | `IN_TRANSIT` |

- 행이 없거나 텍스트가 비어 있으면 `TRACKING_HTML_PARSE_ERROR`(S301)로 실패한다. (`Xth19Processor.java:172-189`)
- 현재 상태와 같으면 변경 없이 반환한다. (`:101-105`)

## 3. 배송 완료 판정 이후 (`Xth19Processor.java:108-118`)

### 3-1. 상태 변경 순서
1. 배송(Xhx14): `IN_TRANSIT/OUT_FOR_DELIVERY → DELIVERED` (`Xth19Processor.java:113`). `Xpb98Status.IN_TRANSIT`과 `OUT_FOR_DELIVERY` 모두 `DELIVERED`로 갈 수 있다. (`B/domain/m12/entity/Xpb98Status.java:16-28`)
2. `orderService.completeOrder(orderId)` 호출. (`Xth19Processor.java:116`, 본문 `Xhx14CommandService.java:190-226`)
   1. Xzj27을 `findByOrderId`로 조회한다. 없으면 IllegalArgumentException이 되고, 이는 `ORDER_NOT_FOUND_FOR_SHIPMENT`(S102)로 감싸진다. (`:196-198,221-226`)
   2. 주문(Xdg64)을 `COMPLETED`로 변경한다. (`:204`)
   3. `updateSaleStatusToSold`를 호출한다. (`:208`)
      - 판매(Xgg74)가 `SOLD`로 전환 가능하면 `SOLD`로 바꾸고 판매자에게 알림을 보낸다. (`:119-133`)
      - 이어서 Xzj27 쪽 sale도 같은 방식으로 처리한다. (`:151-164`)
   4. 구매자에게 알림을 보낸다. 메시지는 "[completeOrder] 주문이 완료 처리되었습니다. 주문 ID: …". (`:212`)
3. `notificationService.notifyShipmentCompleted(order)`를 호출한다. 구매자에게 "[배송 완료] 상품이 배송 완료되었습니다. 주문 ID: …" 알림이 간다. (`Xth19Processor.java:117`, `B/domain/m15/service/command/Xkh73CommandService.java:219-229`)
4. 스텝의 `JpaItemWriter`가 배송(Xhx14)을 저장한다. (`Xqv91JobConfig.java:74,239-245`)

### 3-2. 알림 건수
- **구매자**: 정상 진행 시 **2건**("[completeOrder] …" + "[배송 완료] …").
- **판매자**: 판매(Xgg74)가 아직 `SOLD`로 전환 가능한 상태일 때만 **최대 1건**. Xzz58 경로와 Xzj27 경로가 같은 sale을 가리키면 첫 경로에서 `SOLD`가 되므로 두 번째 경로는 건너뛰어 중복되지 않는다. (`Xhx14CommandService.java:119,156`)
- 이는 정상 케이스(예: 판매가 아직 `SOLD`가 아닌 상태)의 설계 동작이다. 실제 주문 종류별 결과는 4절을 본다.

### 3-3. 주문 입찰·판매 입찰 상태
- 배치 경로에서는 **바뀌지 않는다**. 입찰을 `COMPLETED`로 바꾸는 `updateOrderAndSaleBidStatusToCompleted`는 운송장 등록 경로(`updateTrackingInfo:289`)에서만 호출된다. `completeOrder`와 `Xth19Processor`는 호출하지 않는다.
- 따라서 배송 완료 후에도 Xzj27·Xzz58은 `MATCHED`로 남는다. 입찰 상태 값은 `PENDING/MATCHED/CANCELLED/COMPLETED`이다. (`B/domain/m16/entity/Xtz73Status.java:3-8`)
- 판매(Xgg74)의 `SOLD`만 `completeOrder` 안에서 처리된다.

## 4. 주문 종류별 차이

### (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문 → 끝까지 진행되지 않음
- 주문 상태는 `PREPARING`이다. (`Xdg64CommandService.java:175-176`)
- `completeOrder`의 `order.updateStatus(COMPLETED)`(`Xhx14CommandService.java:204`)에서 막힌다. `PREPARING`의 허용 전이는 `IN_WAREHOUSE`·`SHIPMENT_STARTED`뿐이다. (`Xdg64Status.java:26`)
- `Xxc76StatusException`이 `ORDER_NOT_FOUND_FOR_SHIPMENT`(S102)로 감싸져 던져진다. (`Xhx14CommandService.java:221-226`)
- 추가로, 일반 주문에는 `order_id`가 연결된 판매 입찰이 없다. `updateSaleStatusToSold`의 `saleBidQueryService.findByOrderId`는 없으면 예외를 던지므로(`Xzz58QueryService.java:26-28`), 상태 전환이 통과하더라도 `:116`에서 또 실패한다.
- 결과
  - 주문은 `PREPARING`을 유지한다.
  - 알림은 없다.
  - 배치에서는 해당 건이 롤백·skip된다(5절).
- 사실 이 주문은 1절에서 운송장 등록부터 실패해 배송이 `PENDING`에 머문다. 배치 대상(`IN_TRANSIT`/`OUT_FOR_DELIVERY`)에 아예 들어오지 않는다.

### (b) 즉시 구매로 만들어진 주문 → 3의 처리가 끝까지 진행됨
- 구성
  - `createInstantOrder`는 주문을 `PENDING_PAYMENT`로 만든다. (`Xdg64CommandService.java:241-245`)
  - 이후 상태 변경이 없다(결제 서비스도 주문 상태를 바꾸지 않음). 판매 입찰에는 `assignOrder`로 order_id가 연결된다. (`:279-280`)
  - 주문 입찰도 만들어진다: `isInstantPurchase=true`, `MATCHED`, order·sale 연결. (`B/domain/m16/service/command/Xzj27CommandService.java:142,189-206`)
- `completeOrder` 진행
  1. Xzj27이 있다. (`Xhx14CommandService.java:196`)
  2. `PENDING_PAYMENT → COMPLETED`는 허용된다. (`Xdg64Status.java:24`)
  3. 판매 입찰도 `order_id`로 조회된다. (`:116`)
- 결과
  - 배송 `DELIVERED`, 주문 `COMPLETED`.
  - 판매(Xgg74)는 이미 결제 처리에서 `SOLD`가 된 상태다. 결제 서비스가 Xzj27 생성 전에 판매 입찰로 sale을 `SOLD` 처리하고 구매자·판매자 알림을 보낸다. (`B/domain/m06/service/command/Xbf54CommandService.java:83,388-405,434-452`)
  - 따라서 `SOLD → SOLD` 전환은 불가로 판정되어(`B/domain/m10/entity/Xgg74Status.java:23`) 판매자 알림과 상태 변경은 건너뛴다.
  - 구매자는 완료 알림 **2건**("[completeOrder] …", "[배송 완료] …")을 받는다. 판매자 배송 완료 알림은 0건이다.
  - 입찰 상태는 `MATCHED` 그대로다.
- 단, (b)도 API 운송장 등록(1절)은 주문이 `PENDING_PAYMENT`라 `IN_TRANSIT` 전환이 불가해 실패한다. 즉 정상 API 경로로는 배송이 `IN_TRANSIT`에 도달하지 못한다. 위 결과는 3의 처리 코드 자체가 (b)에서만 끝까지 가는 것을 뜻한다.

## 5. 실패 처리 (주기 처리 중 한 건 실패)

- processor 내부에서 오류가 나면 `Xpb98Exception`으로 감싸 다시 던진다. (`Xth19Processor.java:133-146`) 건별로 삼키지 않는다.
- 스텝은 fault-tolerant이다.
  - `.faultTolerant().skip(Exception.class).skipLimit(50)` (`Xqv91JobConfig.java:75-77`)
  - 한 건이 예외를 내면 그 건만 skip되고, 청크는 롤백된 뒤 항목 단위로 재처리된다. 나머지 건은 계속 처리·저장된다.
  - `completeOrder`는 청크 트랜잭션에 참여해 실패 시 같은 트랜잭션이 롤백 대상이 되므로, 실패 건의 주문·판매·알림 변경은 저장되지 않는다. 실패 건은 `IN_TRANSIT`으로 남아 6시간 뒤 다시 조회된다.
  - `SkipListener`가 로그만 남긴다. (`Xqv91JobConfig.java:252-286`)
- skip이 50건을 넘으면 스텝 자체가 실패한다. 이후 건은 처리되지 않으며 스케줄러는 예외를 `printStackTrace`로 삼킨다. (`Xpb98BatchScheduler.java:41-43`)
- 실패 사례
  - 일반 주문(a)처럼 상태 전환 불가 → S102.
  - 택배사 조회 실패 → S302, 파싱 실패 → S301.
