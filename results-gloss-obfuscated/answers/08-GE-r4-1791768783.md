# 구매자 배송: 운송장 등록 ~ 배송 완료

경로 약어: `P` = `src/main/java/com/fream/back`, `M12` = `P/domain/m12`, `M16` = `P/domain/m16`.
엔티티 약어: 구매자 배송 = `Xhx14`(OrderShipment), 주문 = `Xdg64`, 주문 입찰 = `Xzj27`(OrderBid), 판매 입찰 = `Xzz58`(SaleBid), 판매 = `Xgg74`(Sale).

## 결론 요약

- 운송장 등록 API(`PATCH /shipments/order/{id}/status`)는 의도상 "배송 IN_TRANSIT → 주문 IN_TRANSIT → 구매자 알림 → 판매 SOLD/판매자 알림 → 입찰 COMPLETED" 순서다.
- 그러나 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문은 `PREPARING` 상태라서 `PREPARING → IN_TRANSIT` 전환이 막힌다. 따라서 **끝까지 성공하지 못하고 전부 롤백**되며, 응답은 404 `S001`이다.
- 배송 완료 감지는 6시간마다 도는 Spring Batch 잡이 하고, 실제로 쓰이는 처리 코드는 `Xth19Processor`다. 같은 `PREPARING` 주문은 여기서도 `PREPARING → COMPLETED`가 막혀 배송 완료 처리가 실패하고 skip 된다.
- 즉시 구매 주문은 `PENDING_PAYMENT` 상태로 남아 있어서 `PENDING_PAYMENT → COMPLETED`는 허용된다. 배송 완료 처리가 끝까지 진행되지만 입찰 상태는 COMPLETED로 바뀌지 않는다.

## 1. 운송장 등록 요청

### 1-1. 어느 API로 들어오나

1. `PATCH /shipments/order/{shipmentId}/status`, 본문은 `Xhx14RequestDto`(courier, trackingNumber)이다.
   - 컨트롤러 매핑: `M12/controller/command/Xhx14CommandController.java:19`(클래스 `@RequestMapping("/shipments/order")`), `:31-33`(`@PatchMapping("/{shipmentId}/status")`).
   - 호출 서비스: `M12/controller/command/Xhx14CommandController.java:40` → `Xhx14CommandService.updateTrackingInfo` (`M12/service/command/Xhx14CommandService.java:238-239`).
2. 비슷한 입구가 둘 더 있다. `POST /shipments/order/{id}/check-status`와 `/check-status-string`은 `updateAndCheckShipmentStatus`를 호출한다(`M12/controller/command/Xhx14CommandController.java:59-64`, `M12/service/command/Xhx14CommandService.java:452`). 이 입구는 운송장을 저장하고 택배사 조회를 즉시 실행하며, 주문 상태를 IN_TRANSIT으로 바꾸지 않는다. 질문의 "운송장 등록"은 PATCH 쪽이다.

### 1-2. 코드가 의도한 상태 변경 순서와 알림

`Xhx14CommandService.updateTrackingInfo`(`@Transactional`, `M12/service/command/Xhx14CommandService.java:238-239`):

1. courier·trackingNumber가 비어 있으면 `TRACKING_INFO_REQUIRED`(`:242-245`).
2. 배송 조회 후 `shipment.updateTrackingInfo(...)`(`:256`)가 **배송(Xhx14)** 상태를 `IN_TRANSIT`으로 바꾼다. 이 엔티티 메서드는 전환 검증 없이 대입한다(`M12/entity/Xhx14.java:41-45`).
3. **주문(Xdg64)** 상태를 `IN_TRANSIT`으로 변경한다(`:259-260`). 주문 상태 머신 검증이 걸린다(`M16/entity/Xdg64.java:113-121`).
4. **구매자**에게 알림 1건 "상품이 출발하였습니다. 주문 ID: …"(`:265-270`, SHOPPING/BID).
5. `updateSaleStatusToSold(orderId)`(`:276`, 본체 `:111-181`):
   - `SaleBid`가 있고 판매가 SOLD로 전환 가능하면 **판매(Xgg74)** 를 SOLD로 바꾸고(`:127-131`) 창고 보관이면 창고 상태도 바꾼다(`:133-136`). **판매자**에게 알림 "상품이 성공적으로 판매 완료되었습니다"(`:138-146`).
   - 이어서 `OrderBid` 경로로 같은 판매에 대해 한 번 더 SOLD 시도와 판매자 알림(`:149-177`). 이미 SOLD면 전환 불가라 건너뛴다.
6. 판매가 창고 보관이면 창고 상태를 다시 한 번 갱신한다(`:279-287`).
7. `updateOrderAndSaleBidStatusToCompleted`(`:289`, 본체 `:412-441`): **OrderBid** MATCHED → COMPLETED(`:421-425`), **SaleBid** MATCHED → COMPLETED(`:428-432`). 이 메서드 안의 예외는 삼켜진다(`:436-439`).

즉 의도된 순서는 `Xhx14 IN_TRANSIT → Xdg64 IN_TRANSIT → (구매자 알림) → Xgg74 SOLD(+판매자 알림) → Xzj27/Xzz58 COMPLETED`이다.
알림은 구매자 1건, 판매자 최대 1~2건이다. 입찰을 COMPLETED로 바꾸는 시점이 배송 완료가 아니라 **운송장 등록 시점**이라는 점이 메서드 이름·주석 의도와 다르다.

### 1-3. 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문은 끝까지 성공하나 → **실패한다**

1. 일반 구매 입찰 주문은 `PENDING_PAYMENT`로 만들어진다(`M16/service/command/Xdg64CommandService.java:81`).
2. 결제·배송 처리(`processPaymentAndShipment`)는 비창고 보관이면 `PAYMENT_COMPLETED → PREPARING`에서 멈춘다(`M16/service/command/Xdg64CommandService.java:174-176`).
   - 실제 HTTP 경로는 Kafka를 거친다(`M16/controller/command/Xdg64CommandController.java:54`). 컨슈머도 비창고 보관이면 `PAYMENT_COMPLETED → PREPARING`까지만 보낸다(`M16/service/kafka/Xdg64EventConsumer.java:195`, `:215-218`). 결과는 같다.
   - 창고 보관(`isWarehouseStorage`)이면 `COMPLETED`까지 가므로(`M16/service/command/Xdg64CommandService.java:165-172`) 실배송이 아니다.
3. 주문 상태 머신은 `PREPARING → {IN_WAREHOUSE, SHIPMENT_STARTED}`만 허용하고(`M16/entity/Xdg64Status.java:26`), `IN_TRANSIT`은 `SHIPMENT_STARTED`에서만 갈 수 있다(`M16/entity/Xdg64Status.java:28`). 코드 어디서도 `SHIPMENT_STARTED`로 바꾸지 않는다(`SHIPMENT_STARTED`는 `Xdg64Status`와 표시용 `M16/controller/query/Xdg64QueryController.java:207`에만 나온다).
4. 따라서 `updateTrackingInfo`의 `order.updateStatus(IN_TRANSIT)`(`M12/service/command/Xhx14CommandService.java:260`)에서 `Xxc76StatusException`("상태 전환이 허용되지 않습니다: PREPARING -> IN_TRANSIT")이 발생한다(`M16/entity/Xdg64.java:113-120`).

**어디서·왜 실패하나**: 위 `:260`이다. `PREPARING → IN_TRANSIT` 전환이 상태 머신에 없다.

**무엇이 저장되나: 아무것도 저장되지 않는다.**
- 예외는 `catch (Exception e)`(`M12/service/command/Xhx14CommandService.java:295`)에서 `Xpb98Exception(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")`으로 감싸 다시 던진다(`:297-301`). `@Transactional` 메서드를 예외로 빠져나가므로 전체가 롤백된다.
- 배송에 대입한 courier·trackingNumber·IN_TRANSIT(`:256`)도 롤백되어 배송은 PENDING에 운송장 없음 그대로다.
- 구매자 알림(`:265`)과 판매·입찰 변경(`:276`, `:289`)은 `:260`보다 뒤라 실행되지 않는다. 알림 0건.
- 따라서 이후 배치의 조회 대상(`IN_TRANSIT`/`OUT_FOR_DELIVERY`이면서 운송장 있음)에도 들어가지 못한다(`M12/config/Xqv91JobConfig.java:95`).

**응답**: 전역 핸들러가 `Xpb98Exception`을 받아 `errorCode`의 코드·메시지·상태로 응답한다(`P/global/exception/Xks43ExceptionHandler.java:459-473`). 응답은 **HTTP 404, code `S001`, message "배송 정보를 찾을 수 없습니다."** 이다(`M12/exception/Xpb98ErrorCode.java:12`). 실제 원인은 주문 상태 전환 불가인데 "배송 정보 없음"으로 보인다. 상세 메시지는 응답 본문에 노출되지 않는다.

## 2. 배송 완료 감지

### 2-1. 누가·언제·어떻게

- 감지 주체는 스케줄러 `Xpb98BatchScheduler.scheduleShipmentStatusJob`이고, 이 메서드가 Spring Batch 잡 `updateShipmentStatusesJob`을 실행한다(`P/global/config/Xpb98BatchScheduler.java:34-41`).
- 요청 주체는 사람이 아니라 서버 스케줄러이며, 택배사 화면을 직접 조회해서 판단한다(웹훅·콜백 없음).

### 2-2. 주기, 대상, 실제 실행 코드

- **주기**: `@Scheduled(cron = "0 0 */6 * * *")`, 즉 매일 00·06·12·18시 정각, 6시간마다이다(`P/global/config/Xpb98BatchScheduler.java:34`). 실행 때마다 `timestamp` 파라미터를 달리 넣는다(`:37`).
- **대상**: 상태가 `IN_TRANSIT` 또는 `OUT_FOR_DELIVERY`이고 `trackingNumber`가 NULL이 아닌 배송(`M12/config/Xqv91JobConfig.java:95`). chunk 50, skip 한도 50(`:49-50`, `:67`, `:76-77`).
- **실제로 실행되는 처리 코드**: `Xth19Processor`이다. 스텝이 `new Xth19Processor(...)`를 `.processor(...)`에 넣는다(`M12/config/Xqv91JobConfig.java:69-73`). `Xmb36Listener`가 스텝 전후로 Playwright 브라우저를 연다/닫는다(`:80`, `M12/config/Xmb36Listener.java:15-24`).
  - 처리 흐름(`M12/config/Xth19Processor.java:57-146`): Playwright로 `https://trace.cjlogistics.com/next/tracking.html?wblNo=…`에 접속(`:78-86`) → 상태 테이블 마지막 행의 5번째 td 텍스트를 읽음(`:182`) → 내부 상태로 매핑(`:95`) → DELIVERED이면 `updateStatus(DELIVERED)`, `orderService.completeOrder`, `notifyShipmentCompleted`(`:108-117`).
- **실행되지 않는 유사 코드(죽은 코드)**:
  - `Xqv91JobConfig.shipmentItemProcessor`(`M12/config/Xqv91JobConfig.java:112-175`)는 `@Bean`이지만 스텝에서 쓰이지 않는다(스텝은 `:69`에서 `Xth19Processor`를 직접 생성).
  - `Xqv91JobConfig.parseCjLogisticsStatus`(`:187`)는 호출처가 없다.
  - `Xhx14CommandService.updateShipmentStatuses`(`M12/service/command/Xhx14CommandService.java:309`)는 호출처가 없다(전체 소스에서 `updateShipmentStatuses(`의 호출은 정의뿐).
  - 이 세 곳은 배송 완료 시 구매자 알림이나 완료 처리가 다르다(예: 서비스 쪽 `:350-362`는 `completeOrder` 대신 주문을 직접 COMPLETED로 바꾸고 알림 1건). 실제 동작을 결정하는 쪽은 `Xth19Processor`다.
  - `@EnableScheduling`은 같은 앱의 다른 설정(`P/domain/m04/scheduler/EventStatusScheduler.java:22` 등)에서 켜져 있어 스케줄러가 동작한다.

### 2-3. 택배사 상태 문자열 → 내부 상태

`Xth19Processor.mapToShipmentStatus`(`M12/config/Xth19Processor.java:220-226`):

| 택배사 문자열 | 내부 상태(`Xpb98Status`) |
|---|---|
| `"배송완료"` | `DELIVERED` |
| `"배송출발"` | `OUT_FOR_DELIVERY` |
| 그 외 전부 | `IN_TRANSIT` |

- 정확한 문자열 일치(`switch`)이며 공백은 파싱 시 `trim()`된다(`:182`). 빈 문자열이면 `TRACKING_HTML_PARSE_ERROR`(`:184-190`).
- 같은 상태이면 변경 없이 반환한다(`:101-105`).
- 배송 상태 머신: `IN_TRANSIT → {OUT_FOR_DELIVERY, DELAYED, CANCELED, DELIVERED}`, `OUT_FOR_DELIVERY → {DELIVERED, FAILED_DELIVERY, CANCELED}`(`M12/entity/Xpb98Status.java:14-26`). 그 밖의 전환은 `IllegalStateException`이다(`M12/entity/Xhx14.java:47-55`).
  - 예: 배송이 `OUT_FOR_DELIVERY`인데 조회 결과가 "배송중"(→ `IN_TRANSIT`)이면 `OUT_FOR_DELIVERY → IN_TRANSIT`이 불가해 예외가 나고 skip 된다.

## 3. 배송 완료 판정 이후 (`Xth19Processor` → `completeOrder`)

**주문 상태가 허용 전환일 때(아래 4-(b)처럼 끝까지 가는 경우)의 순서**:

1. **배송(Xhx14)**: `DELIVERED`로 변경(`M12/config/Xth19Processor.java:113`). `IN_TRANSIT`/`OUT_FOR_DELIVERY` → `DELIVERED`는 허용(`M12/entity/Xpb98Status.java:14-26`). 저장은 청크 writer `JpaItemWriter`가 한다(`M12/config/Xqv91JobConfig.java:71`, `:201-206`).
2. `orderService.completeOrder(orderId)`(`M12/config/Xth19Processor.java:116`, 본체 `M12/service/command/Xhx14CommandService.java:190-230`):
   1. `OrderBid`를 `orderId`로 조회, 없으면 예외(`:195-196`).
   2. **주문(Xdg64)** → `COMPLETED`(`:204`).
   3. `updateSaleStatusToSold`(`:208`): 판매가 SOLD로 전환 가능할 때만 SOLD와 판매자 알림(`:111-181`).
   4. **구매자**에게 알림 "[completeOrder] 주문이 완료 처리되었습니다. 주문 ID: …"(`:211-217`).
3. `notificationService.notifyShipmentCompleted(order)`(`M12/config/Xth19Processor.java:117`)가 **구매자**에게 알림 "[배송 완료] 상품이 배송 완료되었습니다. 주문 ID: …"(`P/domain/m15/service/command/Xkh73CommandService.java:219-229`).

**알림 건수**:
- 구매자: **2건**(`[completeOrder]` 1건 + `[배송 완료]` 1건). 두 문구가 사실상 같은 사건에 대한 중복 알림이다.
- 판매자: 판매가 아직 SOLD가 아닐 때만 최대 1~2건이다. 결제 단계에서 이미 SOLD가 되므로(`P/domain/m06/service/command/Xbf54CommandService.java:404`, `:419`) 실제로는 **0건**이 된다(4-(b) 참고).
- `notifyShipmentCompleted`는 예외를 삼킨다(`:230-233`).

**주문 입찰·판매 입찰 상태**: 배송 완료 경로(`completeOrder`)는 `Xzj27`, `Xzz58`의 상태를 바꾸지 않는다. 입찰 COMPLETED 처리는 `updateOrderAndSaleBidStatusToCompleted`뿐이고(`M12/service/command/Xhx14CommandService.java:412-441`) 이것은 운송장 등록 메서드에서만 호출된다(`:289`). 이 호출은 1-3에서 본 대로 도달 전에 실패한다. 결과적으로 **배송 완료 후에도 OrderBid·SaleBid는 `MATCHED`로 남는다**.
- 판매(Xgg74)만 SOLD(결제 시점에 이미 SOLD)이다.

## 4. 주문 종류별 차이

### (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문 → 끝까지 진행되지 않음

주문 상태는 `PREPARING`이다(1-3 참고). 배송이 어떻게든 IN_TRANSIT/OUT_FOR_DELIVERY + 운송장 상태가 되어 배치 대상이 되고(예: `check-status` API로 운송장이 저장된 경우, `M12/service/command/Xhx14CommandService.java:473`) 택배사가 "배송완료"를 주면:

1. 프로세서가 배송을 메모리에서 `DELIVERED`로 바꾼다(`M12/config/Xth19Processor.java:113`).
2. `completeOrder`가 `order.updateStatus(COMPLETED)`를 호출한다(`M12/service/command/Xhx14CommandService.java:204`). `PREPARING → COMPLETED`는 상태 머신에 없어(`M16/entity/Xdg64Status.java:26`) `Xxc76StatusException`이 발생한다(`M16/entity/Xdg64.java:113-120`).
3. `completeOrder`의 catch가 `Xpb98Exception(ORDER_NOT_FOUND_FOR_SHIPMENT)`로 감싸 던진다(`:221-228`). 트랜잭션은 롤백 상태가 된다.
4. 프로세서는 `Xpb98Exception`을 그대로 던지고(`M12/config/Xth19Processor.java:130-141`), 스텝이 skip 처리한다(`M12/config/Xqv91JobConfig.java:75-77`).

결과: 배송은 `DELIVERED`로 저장되지 않고 `IN_TRANSIT`/`OUT_FOR_DELIVERY`로 남는다. 주문은 `PREPARING` 그대로이며 알림 0건, 입찰·판매 변경 없음이다. 다음 6시간 주기에 다시 조회되어 같은 실패를 반복한다.

### (b) 즉시 구매로 만들어진 주문 → 끝까지 진행됨

1. 즉시 구매 주문은 `createInstantOrder`에서 `PENDING_PAYMENT`로 만들어지고(`M16/service/command/Xdg64CommandService.java:241-245`), 이후 결제 처리는 `processPayment`만 호출한다(`:305`). 주문 상태를 올리는 코드가 없어 `PENDING_PAYMENT`로 남는다. `SaleBid`는 주문에 연결되고 MATCHED가 된다(`:279-280`).
2. 즉시 구매용 `OrderBid`는 이후 `createInstantOrderBid`로 만들어지며 MATCHED, 주문과 판매에 연결, `isInstantPurchase=true`이다(`M16/service/command/Xzj27CommandService.java:189-206`, 호출 `:142`).
3. 결제 시 판매는 이미 SOLD가 된다. 이 시점에 주문에 OrderBid가 아직 없으므로 SaleBid 경로(`P/domain/m06/service/command/Xbf54CommandService.java:388-404`)로 처리된다.
4. 배송이 배치 대상이 되어 "배송완료"가 오면, `completeOrder`에서 `PENDING_PAYMENT → COMPLETED`가 허용되므로(`M16/entity/Xdg64Status.java:24`) 통과한다.
   - 배송: `DELIVERED`(저장됨).
   - 주문: `COMPLETED`(`M12/service/command/Xhx14CommandService.java:204`).
   - 판매: 이미 SOLD이므로 `canTransitionTo(SOLD)`가 false여서 변경·판매자 알림 없음(`M10/entity/Xgg74Status.java`의 SOLD 분기, `:119-132`, `:154-170`의 조건). 판매자 알림 **0건**.
   - 구매자 알림 **2건**(3장).
   - OrderBid·SaleBid는 `MATCHED` 그대로(3장).

단, (b)도 운송장 **등록 API**는 `PENDING_PAYMENT → IN_TRANSIT`이 막혀(`M16/entity/Xdg64Status.java:24`) 똑같이 404 `S001`로 실패한다. 배치 대상으로 들어가려면 `check-status` API로 운송장·상태를 저장하는 우회 경로가 필요하다.

## 5. 실패 처리 (주기 처리 중 한 건 실패)

1. 스텝은 `faultTolerant().skip(Exception.class).skipLimit(50)`이다(`M12/config/Xqv91JobConfig.java:75-77`). 프로세서에서 예외가 나면 해당 항목만 skip 된다.
2. 프로세서는 모든 예외를 `Xpb98Exception`으로 바꿔 던진다(`M12/config/Xth19Processor.java:130-141`). 스킵된 건은 `onSkipInProcess`가 로그만 남긴다(`M12/config/Xqv91JobConfig.java:213-226`). 알림이나 재시도는 없다.
3. skip 된 건: 청크 트랜잭션이 롤백되므로 그 건의 변경(DELIVERED 대입, 주문 변경)은 저장되지 않는다. 상태가 그대로라 다음 주기(6시간 후)에 다시 대상이 된다.
4. 나머지 건: 스프링 배치의 fault-tolerant 동작에 따라 실패한 청크를 건별로 다시 처리하며, skip 된 건을 제외한 나머지는 정상 처리·저장된다.
5. skip이 50건을 넘으면 스텝이 실패하고 남은 건은 그 실행에서 처리되지 않는다. 이 예외는 스케줄러에서 `printStackTrace`만 한다(`P/global/config/Xpb98BatchScheduler.java:42-44`).
6. 한 건에서 구매자 알림만 실패하는 경우는 다르다. `notifyShipmentCompleted`는 예외를 삼키므로(`P/domain/m15/service/command/Xkh73CommandService.java:230-233`) 배송·주문 변경은 그대로 저장된다.
7. 참고(죽은 코드): `Xhx14CommandService.updateShipmentStatuses`는 건별 try/catch로 계속 진행하지만(`M12/service/command/Xhx14CommandService.java:383-387`), 호출처가 없어 실제 실패 처리에 해당하지 않는다.
