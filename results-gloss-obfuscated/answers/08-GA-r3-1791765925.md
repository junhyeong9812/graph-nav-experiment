# 구매자 배송: 운송장 등록 → 배송 완료

경로 접두어: `src/main/java/com/fream/back/` 는 `B/` 로 줄여 쓴다. (코드 이름: Xhx14=OrderShipment, Xdg64=Order, Xzj27=OrderBid, Xzz58=SaleBid, Xgg74=Sale, Xpb98=Shipment, Xkh73=Notification, Xth19=ShipmentItem)

## 1. 운송장 등록 요청

### 1-1. 진입 API
- `PATCH /shipments/order/{shipmentId}/status`, body `{courier, trackingNumber}` — `B/domain/m12/controller/command/Xhx14CommandController.java:20,33-49`
  - 컨트롤러는 `Xhx14CommandService.updateTrackingInfo` 를 호출하고 200 빈 본문을 돌려준다. (`:41-48`)
- 같은 컨트롤러에 `POST /{shipmentId}/check-status`, `/check-status-string` 도 있다 (`:58`, `:103`). 이쪽은 택배사를 즉시 조회하는 별도 경로이고, "운송장 등록" 본 경로는 PATCH 이다.

### 1-2. 코드가 의도한 상태 변경 순서와 알림 (`B/domain/m12/service/command/Xhx14CommandService.java:238-303`)
1. courier·trackingNumber 가 비면 `TRACKING_INFO_REQUIRED` (`:243-246`).
2. shipment 조회, 없으면 `SHIPMENT_NOT_FOUND` (`:249-253`).
3. 배송(Xhx14) 상태 → `IN_TRANSIT`. `updateTrackingInfo` 가 전이 검사 없이 직접 대입한다. (`:256`, `B/domain/m12/entity/Xhx14.java:41-45`)
4. 주문(Xdg64) 상태 → `IN_TRANSIT` (`:259-260`). 이 전이는 `Xdg64.updateStatus` 가 허용표로 검사한다. (`B/domain/m16/entity/Xdg64.java:113-121`)
5. 구매자에게 알림 1건: "상품이 출발하였습니다. 주문 ID: …" (`:265-271`)
6. `updateSaleStatusToSold(orderId)` (`:276`, 본체 `:111-183`)
   - SaleBid 의 Sale 이 SOLD 로 전이 가능하면 Sale → `SOLD`, 창고 보관이면 창고 상태도 변경, 판매자에게 알림 1건 "상품이 성공적으로 판매 완료되었습니다…" (`:116-141`)
   - OrderBid 쪽 Sale 도 같은 방식으로 SOLD + 판매자 알림 (`:151-172`)
7. SaleBid 의 Sale 이 창고 보관이면 창고 상태를 한 번 더 갱신 (`:279-286`)
8. `updateOrderAndSaleBidStatusToCompleted` : OrderBid 가 MATCHED 면 COMPLETED, SaleBid 가 MATCHED 면 COMPLETED (`:289`, `:412-440`). 이 메서드는 예외를 삼킨다 (`:436-439`).

즉 설계상 "운송장 등록" 시점에 주문 IN_TRANSIT, 판매 SOLD, 입찰 COMPLETED 까지 한꺼번에 처리하려 한다. 알림 대상은 구매자 1건 + 판매자(최대 1~2건).

### 1-3. 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문은 끝까지 성공하나? — **성공하지 않는다**
- 그 시점 주문 상태는 `PREPARING` 이다.
  - 일반 입찰 주문은 `PENDING_PAYMENT` 로 만들어지고 (`B/domain/m16/service/command/Xdg64CommandService.java:76-82`),
  - `processPaymentAndShipment` 의 비창고(실배송) 분기에서 `PAYMENT_COMPLETED → PREPARING` 까지만 간다. (`:174-177`)
  - Kafka 소비자 경로도 동일하게 PREPARING 에서 멈춘다. (`B/domain/m16/service/kafka/Xdg64EventConsumer.java:206-207` 근처의 비창고 분기)
  - 이후 주문을 `SHIPMENT_STARTED` 로 올리는 코드는 어디에도 없다. (`Xdg64Status.SHIPMENT_STARTED` 를 대입하는 곳이 없음; IN_WAREHOUSE 로만 `Xdg64CommandService.java:167`, `Xdg64EventConsumer.java:207`, `global/config/Xnp67.java:553`)
- 허용 전이표에서 `PREPARING → {IN_WAREHOUSE, SHIPMENT_STARTED}` 뿐이다. `IN_TRANSIT` 은 없다. (`B/domain/m16/entity/Xdg64Status.java:26`)
- 따라서 `Xhx14CommandService.java:260` 의 `order.updateStatus(IN_TRANSIT)` 가 `Xxc76StatusException`("상태 전환이 허용되지 않습니다: PREPARING -> IN_TRANSIT", `Xdg64.java:117-119`) 을 던진다.
- 실패 지점과 이후 흐름
  - 이 예외는 `catch (Xpb98Exception)` 에 안 걸리고 `catch (Exception)` 에 걸려 `Xpb98Exception(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")` 로 포장되어 다시 던져진다. (`:293-302`)
  - 실패는 `:260` 이므로 5번(구매자 알림) 이후 단계는 실행되지 않는다. 알림은 0건.
- 저장되는 것: **없음.** `@Transactional`(`:238`) 에서 RuntimeException 이 나가므로 롤백된다. 3번의 메모리상 변경(courier, trackingNumber, IN_TRANSIT)은 DB에 반영되지 않는다. 배송은 `PENDING`·운송장 없음, 주문은 `PREPARING` 그대로.
- 응답: PATCH 컨트롤러는 예외를 잡지 않으므로 (`Xhx14CommandController.java:33-49`) 전역 핸들러가 처리한다. (`B/global/exception/Xks43ExceptionHandler.java:49-63`)
  - HTTP **404**, body `ErrorResponse(code="S001", message="배송 정보를 찾을 수 없습니다.", status=404, path=요청 URI)`. (`B/domain/m12/exception/Xpb98ErrorCode.java:12`)
  - 핸들러는 `errorCode.getMessage()` 를 쓰므로 "상태 전환이 허용되지 않습니다" 같은 상세 메시지는 응답에 나가지 않는다 (서버 로그에만 남음). 실제 원인은 "배송 없음"이 아니라 주문 상태 전환 불가인데 오류 코드가 오도된다.
- (참고) 즉시 구매 주문도 `PENDING_PAYMENT` 에서 `IN_TRANSIT` 이 허용표에 없어서 (`Xdg64Status.java:24`) 같은 방식으로 실패한다.

## 2. 배송 완료 감지

### 2-1. 누가·언제·어떻게
- 사람의 호출이 아니라 **스케줄러가 Spring Batch Job 을 띄워 감지**한다.
  - `Xpb98BatchScheduler.scheduleShipmentStatusJob` 에 `@Scheduled(cron = "0 0 */6 * * *")` — **6시간마다**(매일 0·6·12·18시 정각, 서버 타임존 기준). (`B/global/config/Xpb98BatchScheduler.java:34-44`)
  - 호출마다 `timestamp` 파라미터로 새 JobInstance 를 만들어 `updateShipmentStatusesJob` 을 실행한다. (`:37-40`) 예외는 `printStackTrace` 만 한다. (`:41-43`)
- Job 구성: `B/domain/m12/config/Xqv91JobConfig.java:54-60`(Job), `:62-82`(Step)
  - chunk 50 (`:51,67`), faultTolerant + `skip(Exception.class)` + skipLimit 50 (`:52,75-77`).
- 조회 대상: reader JPQL `SELECT s FROM Xhx14 s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL` (`:95`). 페이지 크기 50, 정렬 조건 없음.

### 2-2. 실제로 실행되는 처리 코드
- Step 의 processor 는 `new Xth19Processor(playwrightBrowserManager(), notificationService, orderService)` (`Xqv91JobConfig.java:69-73`, `.writer` `:74`). 즉 **`B/domain/m12/config/Xth19Processor.java` 의 `process` (`:57-157`)** 가 실제로 실행된다.
  - 흐름: 운송장 공백 검사(`:61-65`) → Playwright 페이지로 `https://trace.cjlogistics.com/next/tracking.html?wblNo=` 접속(`:26,81-83`) → `tbody#statusDetail tr` 대기 → 마지막 행의 5번째 td(`get(4)`) 텍스트를 상태로 사용(`:167-181`) → 상태 매핑(`:95`) → 배송/주문 처리.
- 실행되지 **않는** 유사 코드 (혼동 주의)
  - `Xqv91JobConfig.shipmentItemProcessor` 빈 (`:106-177`) 과 `parseCjLogisticsStatus` (`:186`): Step 에 연결되지 않는다 (step 은 `new Xth19Processor` 를 사용, `:69`).
  - `Xhx14CommandService.updateShipmentStatuses` (`:308-391`): 호출하는 곳이 없다 (`@Scheduled`·Job 에서 참조 없음). 이 메서드는 주문만 COMPLETED 로 바꾸고 판매/입찰은 건드리지 않아 의도가 다르다. 실행되지 않는다.
  - `Xxx20.getCurrentTrackingStatus` (`B/global/utils/Xxx20.java:33`) 는 `check-status` API 와 위 미사용 코드가 쓴다. 배치 Step 은 `Xrk74` 브라우저 매니저 + `Xth19Processor` 를 쓴다.

### 2-3. 택배사 상태 문자열 → 내부 상태 (`Xth19Processor.java:220-226`)
| 택배사 텍스트 | 내부 상태 |
|---|---|
| `"배송완료"` (정확히 일치) | `DELIVERED` |
| `"배송출발"` (정확히 일치) | `OUT_FOR_DELIVERY` |
| 그 외 모든 문자열 | `IN_TRANSIT` |

- 파싱 단계에서는 `trim()` 하지만(`:181`), 매핑 `switch` 는 정확 일치다. 표 비어 있음·td 부족·빈 문자열은 `TRACKING_HTML_PARSE_ERROR` (`:167-211`).
- 현재 상태와 매핑 결과가 같으면 아무것도 하지 않고 반환 (`:101-105`).
- 부수 주의: 현재 `OUT_FOR_DELIVERY` 인데 매핑이 `IN_TRANSIT` 이면 `updateStatus(IN_TRANSIT)` (`:123-125`)이 허용표(`Xpb98Status.java:23-28`)에 없어 `IllegalStateException` → 포장되어 해당 건이 skip 된다.

## 3. 배송 완료 판정 이후 (`Xth19Processor.java:108-118` → `Xhx14CommandService.completeOrder`)

상태 변경 순서
1. 배송(Xhx14) `DELIVERED` — `orderShipment.updateStatus(DELIVERED)` (`Xth19Processor.java:113`). IN_TRANSIT/OUT_FOR_DELIVERY 에서만 허용 (`Xpb98Status.java:16-28`).
2. `orderService.completeOrder(orderId)` (`:116`, 본체 `Xhx14CommandService.java:190-229`)
   - OrderBid 를 orderId 로 조회, 없으면 예외 (`:196-197`)
   - 주문(Xdg64) → `COMPLETED` (`:204`) — 전이 검사 있음.
   - `updateSaleStatusToSold(orderId)` (`:208`): SaleBid 조회(`:116`) → Sale 이 SOLD 로 전이 가능하면 Sale→`SOLD`(+창고 보관이면 창고 상태), 판매자 알림 (`:119-141`); OrderBid 쪽 Sale 도 동일 (`:151-172`).
   - 구매자 알림 (`:211-217`)
3. `notificationService.notifyShipmentCompleted(order)` (`Xth19Processor.java:117`, `B/domain/m15/service/command/Xkh73CommandService.java:219-234`) — 구매자에게 "[배송 완료] 상품이 배송 완료되었습니다. 주문 ID: …". 이 메서드는 예외를 삼킨다. (`:230-233`)
4. 이후 chunk writer(`JpaItemWriter`) 가 배송을 저장한다 (`Xqv91JobConfig.java:74` `.writer(shipmentJpaItemWriter())`, 빈 정의 `:241`).

알림 건수 (판매 상태 전이가 일어나는 경우 기준)
- **구매자 2건**: "[completeOrder] 주문이 완료 처리되었습니다…"(`Xhx14CommandService.java:212-217`) + "[배송 완료] …"(`Xkh73CommandService.java:224-229`).
- **판매자 최대 1건**: "상품이 성공적으로 판매 완료되었습니다…" (`:133-138`). Sale 이 이미 SOLD 이거나 SOLD 로 전이 불가면 0건이다. 두 블록(SaleBid 기반 `:116-141`, OrderBid 기반 `:151-172`) 이 같은 Sale 을 보므로 첫 블록에서 SOLD 가 되면 두 번째 블록은 전이 불가로 건너뛰어 중복 알림은 없다.

주문 입찰·판매 입찰 상태
- **변경되지 않는다.** 배송 완료 경로(`completeOrder`/`updateSaleStatusToSold`)에는 OrderBid·SaleBid 의 `updateStatus(COMPLETED)` 가 없다. 입찰을 COMPLETED 로 바꾸는 코드는 private `updateOrderAndSaleBidStatusToCompleted` (`Xhx14CommandService.java:412-440`) 하나이며 `updateTrackingInfo`(운송장 등록, `:289`)에서만 호출된다. 따라서 배치로 배송 완료를 처리한 입찰은 `MATCHED` 로 남는다.
- (추가) `updateOrderAndSaleBidStatusToCompleted` 는 `@Transactional private` + 같은 클래스 내부 호출이라 트랜잭션 어드바이스가 적용되지 않고, 예외도 삼킨다.

## 4. 주문 종류별 차이

### (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문 — **끝까지 진행되지 않는다**
- 주문 상태가 `PREPARING` (`Xdg64CommandService.java:174-177`). `completeOrder` 의 `order.updateStatus(COMPLETED)` (`Xhx14CommandService.java:204`)는 허용표 `PREPARING → {IN_WAREHOUSE, SHIPMENT_STARTED}` (`Xdg64Status.java:26`)에 COMPLETED 가 없어 `Xxc76StatusException`.
- `completeOrder` 의 catch 가 `Xpb98Exception(ORDER_NOT_FOUND_FOR_SHIPMENT)` 로 포장해 던진다 (`:221-227`). `Xth19Processor` 의 catch 도 그대로 다시 던진다 (`:133-146`).
- 결과: 해당 건은 skip, chunk 트랜잭션 롤백(→ 배송 DELIVERED 도 저장 안 됨, DB 에는 IN_TRANSIT 유지), 주문 COMPLETED 안 됨, 알림 없음 (실패가 `:204` 라 `:212` 구매자 알림·`notifyShipmentCompleted` 이전). 다음 6시간 주기에 같은 사유로 반복 실패한다.
- 설령 주문 상태 문제가 없어도, 이 주문에 SaleBid 가 연결돼 있지 않으면 `Xzz58QueryService.findByOrderId` 는 null 이 아니라 `IllegalArgumentException` 을 던져 (`B/domain/m10/service/query/Xzz58QueryService.java:26-29`) `updateSaleStatusToSold` 의 `if (saleBid != null)` 방어(`Xhx14CommandService.java:117`)가 무의미하며 같은 방식으로 실패한다.
- 일반 입찰 주문은 결제 시점에 Sale 이 SOLD 로 바뀌지도 않는다 (OrderBid 에 sale 이 없으면 `return`, `Xbf54CommandService.java:388-418`).

### (b) 즉시 구매로 만들어진 주문 — **끝까지 진행된다** (배송이 IN_TRANSIT/OUT_FOR_DELIVERY + 운송장 있음으로 이미 조회 대상일 때)
- `createInstantOrder` 는 주문을 `PENDING_PAYMENT` 로 만들고 (`Xdg64CommandService.java:241-245`) 상태를 더 올리지 않는다 (`:219-319`에 `updateStatus` 호출 없음). 결제 서비스도 주문 상태를 바꾸지 않는다 (`m06` 에 `Xdg64Status` 사용 없음).
- `PENDING_PAYMENT → COMPLETED` 는 허용된다 (`Xdg64Status.java:24`). 그래서 `completeOrder` 의 `:204` 가 통과한다.
- OrderBid 가 존재한다: `MATCHED` 로 생성되고 order·sale 이 연결되며 `isInstantPurchase=true` (`B/domain/m16/service/command/Xzj27CommandService.java:189-206`). SaleBid 도 `assignOrder(order)` 로 order 가 연결된다 (`Xdg64CommandService.java:279-280`). 따라서 `findByOrderId` 들이 모두 성공한다.
- 판매 상태: 즉시 구매는 결제 시점에 `notifyUsersAndUpdateSaleStatus` 가 Sale 을 이미 `SOLD` 로 바꾸고 판매자·구매자에게 결제 알림을 보낸다 (SaleBid 경로 `Xbf54CommandService.java:391-404`; 결제 호출 `Xdg64CommandService.java:305`). 그래서 배송 완료 시점의 `canTransitionTo(SOLD)` 는 SOLD→SOLD 로 false (`Xgg74Status.java:15-25`)이고 판매자 알림·창고 갱신은 일어나지 않는다.
- 결과: 배송 `DELIVERED`, 주문 `COMPLETED`, 구매자 알림 2건, 판매자 알림 0건(Sale 은 결제 때 이미 SOLD), OrderBid·SaleBid 는 `MATCHED` 유지.

### 차이 요약
| | (a) 일반 입찰, 실배송 | (b) 즉시 구매 |
|---|---|---|
| 배송 완료 시 주문 상태 | PREPARING → COMPLETED 불가 → 실패 | PENDING_PAYMENT → COMPLETED 가능 |
| 배송 상태 저장 | 롤백(IN_TRANSIT 유지) | DELIVERED 저장 |
| 알림 | 없음 | 구매자 2건 |
| 입찰 상태 | 변화 없음 | MATCHED 유지(변화 없음) |

(주의: 두 경우 모두 1-3 의 PATCH 운송장 등록은 주문 IN_TRANSIT 전이 때문에 실패하므로, 배송이 IN_TRANSIT 이 되려면 `check-status` API 같은 다른 경로가 필요하다. 그 경로도 택배사 상태가 "배송중"류이면 `updateTrackingInfo`(IN_TRANSIT) 직후 `updateStatus(IN_TRANSIT)`(`Xhx14CommandService.java:473,497`)가 IN_TRANSIT→IN_TRANSIT 불가로 예외가 나 롤백된다. "배송출발"/"배송완료" 문자열일 때만 성공한다.)

## 5. 실패 처리 (주기 처리 중 한 건 실패)
- Step 은 `faultTolerant().skip(Exception.class).skipLimit(50)` (`Xqv91JobConfig.java:75-77`). 처리 중 예외가 난 건은 **skip** 되고 `shipmentSkipListener` 가 로그만 남긴다 (`:252-255` `onSkipInProcess`, 등록 `:78`).
  - 실패한 건의 변경(배송 DELIVERED 등)과 같은 chunk 트랜잭션에서 한 변경은 롤백된다. `completeOrder` 의 `@Transactional` 이 chunk 트랜잭션에 참여한 채 RuntimeException 을 던지기 때문이다.
  - 롤백 후 Spring Batch 가 chunk 의 나머지 건을 다시 처리해 성공한 건은 커밋한다. 나머지 건과 이후 chunk 는 계속 진행된다.
  - 실패 건은 DB 에서 IN_TRANSIT/OUT_FOR_DELIVERY 로 남아 다음 실행(6시간 뒤)에서 다시 조회·재시도된다.
