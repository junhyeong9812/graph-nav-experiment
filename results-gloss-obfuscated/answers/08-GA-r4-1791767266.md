# 구매자 배송: 운송장 등록 → 배송 완료

경로 약어: `S` = `src/main/java/com/fream/back/domain/m12/service/command/Xhx14CommandService.java`, `C` = `.../domain/m12/controller/command/Xhx14CommandController.java`, `J` = `.../domain/m12/config/Xqv91JobConfig.java`, `P` = `.../domain/m12/config/Xth19Processor.java`, `O` = `.../domain/m16/entity/Xdg64.java`, `OS` = `.../domain/m16/entity/Xdg64Status.java`, `CS` = `.../domain/m16/service/command/Xdg64CommandService.java` (모두 `src/main/java/com/fream/back/` 아래).

## 결론 요약
- 운송장 등록 API(`PATCH /shipments/order/{id}/status`)는 주문을 `IN_TRANSIT`으로 바꾸려 하지만, 결제·배송 처리를 마친 일반 구매 입찰 주문은 `PREPARING` 상태라 전이가 막혀 **끝까지 성공하지 못한다**. 전부 롤백되고 404 `S001`이 응답된다.
- 실제 주기 실행은 `Xqv91JobConfig` 배치 잡 + `Xth19Processor`(6시간마다)이며, `Xhx14CommandService.updateShipmentStatuses()`와 `Xqv91JobConfig.shipmentItemProcessor()`는 호출되지 않는 죽은 코드다.
- 배송 완료 처리(`completeOrder`)는 (a) 일반 구매 입찰 주문(`PREPARING`)에서는 실패하고, (b) 즉시 구매 주문(`PENDING_PAYMENT`)에서만 끝까지 진행된다.

## 1. 운송장 등록 요청

### 1-1. 진입 API
1. `PATCH /shipments/order/{shipmentId}/status`, 바디 `Xhx14RequestDto`(courier, trackingNumber). 컨트롤러 메서드 `updateTrackingInfo` → `S.updateTrackingInfo(...)` 호출. 근거: `C:20`(`@RequestMapping("/shipments/order")`), `C:33-45`.
2. 비슷한 API로 `POST /shipments/order/{id}/check-status`, `/check-status-string`이 있다. 이쪽은 운송장 등록과 동시에 택배사를 즉시 조회하는 `S.updateAndCheckShipmentStatus`를 호출한다(`C:58-89`, `C:103-`, `S:452`). 운송장 "등록" 본체는 위 PATCH다.

### 1-2. 의도된 처리 순서 (`S.updateTrackingInfo`, `S:238-303`)
1. courier/trackingNumber가 비어 있으면 `TRACKING_INFO_REQUIRED`(400). `S:243-246`
2. 배송(`Xhx14`) 조회 후 `shipment.updateTrackingInfo` → 택배사·운송장 저장 + 상태를 `IN_TRANSIT`으로 직접 세팅(전이 검사 없음). `S:249-256`, `domain/m12/entity/Xhx14.java:41-45`
3. 주문 `order.updateStatus(IN_TRANSIT)`. `S:259-260`
4. 구매자에게 알림 "상품이 출발하였습니다. 주문 ID: …" (SHOPPING/BID). `S:265-271`
5. `updateSaleStatusToSold(orderId)`: 판매(Xgg74)를 `SOLD`로, 창고 보관이면 창고 상태 SOLD, 판매자에게 "상품이 성공적으로 판매 완료되었습니다" 알림. 이어 `orderBid.getSale()`에 대해서도 같은 처리. `S:276`, `S:111-183`
6. 판매가 창고 보관이면 창고 상태 SOLD 재호출. `S:279-286`
7. `updateOrderAndSaleBidStatusToCompleted`: 주문 입찰·판매 입찰이 `MATCHED`이면 `COMPLETED`로. 예외는 삼킨다. `S:289`, `S:412-440`

즉 "출발" 시점에 판매를 SOLD로 만들고 입찰도 COMPLETED로 만드는 설계다. 알림은 구매자 1건(출발) + 판매자(판매 완료)이다.

### 1-3. 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문(즉시 구매 아님): 실패한다
1. 이 주문은 `createOrderFromBid`로 `PENDING_PAYMENT`로 생성되고(`CS:76-82`), 결제·배송 처리(`POST /orders/{id}/process-payment-shipment` → Kafka 이벤트 → 컨슈머 `processCompleteOrder`)에서 `PAYMENT_COMPLETED` → `PREPARING`까지만 간다(창고 보관이 아닌 실배송). 근거: `domain/m16/service/kafka/Xdg64EventConsumer.java:192-195`, `:215-218`(동일 로직의 직접 서비스 경로는 `CS:174-177`). 주문 입찰은 `assignOrder`로 `MATCHED`, `sale`은 비어 있고 판매 입찰(Xzz58)도 없다(`domain/m16/entity/Xzj27.java:60-80`, `CS:76-88`). 배송은 `PENDING`(`S:67`).
2. 허용 전이표에서 `PREPARING`의 다음 상태는 `IN_WAREHOUSE`, `SHIPMENT_STARTED`뿐이다. `IN_TRANSIT`은 불가. 근거: `OS:26`(`PREPARING → {IN_WAREHOUSE, SHIPMENT_STARTED}`), `OS:28-29`(`IN_TRANSIT`은 `SHIPMENT_STARTED` 다음에만 가능).
3. 따라서 `S:260`의 `order.updateStatus(IN_TRANSIT)`에서 `Xxc76StatusException("상태 전환이 허용되지 않습니다: PREPARING -> IN_TRANSIT")`이 던져진다. 근거: `O:113-121`.
4. 이 예외는 `Xpb98Exception`이 아니므로 `S:295`의 `catch (Exception)`에 잡혀 `Xpb98Exception(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")`로 바뀌어 던져진다. `S:293-302`
5. **무엇이 저장되나: 아무것도 저장되지 않는다.** `updateTrackingInfo`는 `@Transactional`(`S:238`)이고 `Xpb98Exception`은 `RuntimeException`(`global/exception/Xks43Exception.java:10`)이라 롤백된다. 2단계에서 메모리상 바꾼 택배사·운송장·배송 `IN_TRANSIT`도 DB에 반영되지 않는다. 구매자 알림(4단계)은 3단계 뒤라 생성되지 않는다. 배송은 `PENDING`, 주문은 `PREPARING`, 운송장은 null 그대로다.
6. **응답:** `Xks43ExceptionHandler.handleShipmentException`이 `ErrorResponse`(code `S001`, message "배송 정보를 찾을 수 없습니다.", status 404, 요청 URI)를 404로 반환한다. 근거: `global/exception/Xks43ExceptionHandler.java:459-473`, `domain/m12/exception/Xpb98ErrorCode.java:61`(`SHIPMENT_NOT_FOUND("S001", …, 404)`). 실제 원인(주문 상태 전이 불가)은 응답에 나타나지 않고 오해를 부르는 "배송 정보 없음"으로 나온다.
7. 참고(추가 결함): 설령 주문 전이를 통과해도 `S:116`의 `saleBidQueryService.findByOrderId`는 SaleBid가 없으면 `null`이 아니라 `IllegalArgumentException`을 던진다(`domain/m10/service/query/Xzz58QueryService.java:26-29`). `S:117`의 `if (saleBid != null)` 분기는 의미가 없고, 일반 구매 입찰 주문은 여기서도 같은 `S001` 404가 된다.

### 1-4. 즉시 구매 주문도 이 API로는 성공하지 못한다
- `createInstantOrder`는 주문을 `PENDING_PAYMENT`로 만들고(`CS:241-245`) 이후 어디서도 주문 상태를 바꾸지 않는다(`processPayment`는 주문 상태를 건드리지 않음: `domain/m06/service/command/Xbf54CommandService.java:57-90`). `PENDING_PAYMENT`의 허용 전이는 `PAYMENT_COMPLETED, COMPLETED, IN_WAREHOUSE`라 `IN_TRANSIT`이 불가하다(`OS:24`). 같은 지점(`S:260`)에서 실패해 같은 404 `S001`이 나온다.
- 즉 운송장 PATCH는 주문 상태 기준으로 `SHIPMENT_STARTED` 상태인 주문에서만 성공할 수 있는데, 그 상태로 만드는 코드는 이 코드베이스에 없다(`Xdg64Status.SHIPMENT_STARTED`는 `OS:28`의 표 외에 세팅하는 곳이 없음).

## 2. 배송 완료 감지

1. **누가/언제:** 스케줄러 `Xpb98BatchScheduler.scheduleShipmentStatusJob`이 `@Scheduled(cron = "0 0 */6 * * *")` — 매일 0·6·12·18시 정각, **6시간마다** — Spring Batch 잡 `updateShipmentStatusesJob`을 실행한다(타임스탬프 파라미터로 매번 새 인스턴스). 근거: `global/config/Xpb98BatchScheduler.java:19-21`, `:34-44`. 스케줄링 활성화는 `domain/m05/config/Xwv44Scheduler.java:16` 등 `@EnableScheduling`, 배치는 `global/config/Xct70Config.java:15`.
2. **대상:** `JpaPagingItemReader`가 `SELECT s FROM Xhx14 s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL`를 읽는다(페이지 크기·청크 50). 근거: `J:51`, `J:93-96`.
3. **실제 실행 처리 코드:** 스텝은 `new Xth19Processor(...)`를 프로세서로 쓴다(`J:67-74`). 즉 `Xth19Processor.process`(`P:57-`)가 실제 실행된다. 죽은 코드: 같은 파일의 `shipmentItemProcessor()` 빈(`J:106-`, Jsoup `parseCjLogisticsStatus` `J:186-`)은 스텝에 연결되지 않고(`shipmentItemProcessor` 호출처 없음), `Xhx14CommandService.updateShipmentStatuses()`(`S:308-391`)도 호출처가 없다.
4. **조회 방식:** `Xth19Processor`는 Playwright 브라우저(`Xmb36Listener`가 스텝 전후 open/close, `J:80`)로 `https://trace.cjlogistics.com/next/tracking.html?wblNo={운송장}`을 열고 `tbody#statusDetail tr`을 기다려(`P:72-`) HTML을 Jsoup으로 파싱, 마지막 행의 5번째 `td` 텍스트를 상태 문자열로 쓴다(`P:181`). 행이 없거나 텍스트가 비면 `TRACKING_HTML_PARSE_ERROR`.
5. **상태 매핑:** `P:220-225` — `"배송완료"` → `DELIVERED`, `"배송출발"` → `OUT_FOR_DELIVERY`, 그 외 모든 문자열 → `IN_TRANSIT`(기본값). 같은 매핑이 `S:399-405`, `J:228-233`에도 복제되어 있다.
6. 택배사는 사실상 CJ대한통운만 조회한다(저장된 `courier` 값은 조회에 쓰이지 않는다).
7. 운송장 등록 시점에 즉시 감지하는 별도 경로는 `POST /shipments/order/{id}/check-status`(`S:452-516`)이다.

## 3. 배송 완료 판정 이후 (`Xth19Processor`, `P:57-130`)

1. 현재 상태와 매핑 결과가 같으면 그대로 반환(변경 없음). `P:101-105`
2. `DELIVERED`이면 순서대로:
   1. 배송 `updateStatus(DELIVERED)` (`IN_TRANSIT/OUT_FOR_DELIVERY → DELIVERED` 허용, `domain/m12/entity/Xpb98Status.java`). `P:113`
   2. `orderService.completeOrder(orderId)` (`P:116`, 구현 `S:190-229`): 주문 입찰 조회 → 주문 `COMPLETED`(`S:204`) → `updateSaleStatusToSold`(`S:208`, 판매 `SOLD` + 창고 SOLD + 판매자 알림, 단 판매가 이미 SOLD면 전이 불가로 건너뜀 `S:119`, `S:156`) → 구매자 알림 "[completeOrder] 주문이 완료 처리되었습니다"(`S:211-217`)
   3. `notificationService.notifyShipmentCompleted(order)` → 구매자 알림 "[배송 완료] 상품이 배송 완료되었습니다"(`P:117`, `domain/m15/service/command/Xkh73CommandService.java:219-234`)
3. 배송 완료 후 `JpaItemWriter`가 배송을 저장한다(`J:74`).
4. `OUT_FOR_DELIVERY`면 배송만 `OUT_FOR_DELIVERY`로, 그 외는 `IN_TRANSIT`으로 갱신. `P:119-126`
5. **알림 건수:** 이 경로에서 구매자 **2건**(completeOrder 1건 + 배송 완료 1건). 판매자 알림은 판매가 아직 SOLD가 아닐 때만 `completeOrder` 안에서 1건 생성된다(아래 4 참고; 결제 시점에 판매가 이미 SOLD가 되는 즉시 구매에서는 0건).
6. **입찰 상태:** `completeOrder`/`Xth19Processor`는 주문 입찰·판매 입찰 상태를 `COMPLETED`로 바꾸지 않는다. `updateOrderAndSaleBidStatusToCompleted`는 운송장 등록 경로(`S:289`)에서만 호출되고 그 경로는 1-3·1-4처럼 실패하므로, 배송 완료 후에도 주문 입찰·판매 입찰은 `MATCHED`로 남는다. 판매(Xgg74)만 상황에 따라 `SOLD`.

## 4. 주문 종류별 차이

### (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문 — 끝까지 진행되지 않는다
- 주문은 `PREPARING`(1-3), 판매 입찰 없음, 주문 입찰 `MATCHED`이며 판매(sale)도 없다.
- 운송장 PATCH는 1-3처럼 실패하므로 배송은 `PENDING`/운송장 null이어서 배치 대상(`IN_TRANSIT/OUT_FOR_DELIVERY` + 운송장 있음)에 오르지 않는다. `check-status` API로 운송장을 넣어 배송이 `IN_TRANSIT`이 되면(주문은 그대로 `PREPARING`, `S:473`, `S:497`) 배치 대상이 된다.
- 택배사가 "배송완료"를 주면 `completeOrder`의 `order.updateStatus(COMPLETED)`가 `PREPARING → COMPLETED` 불가(`OS:26`)로 `Xxc76StatusException`을 던지고, 이는 `S:221-228`에서 `Xpb98Exception(ORDER_NOT_FOUND_FOR_SHIPMENT)`로 바뀐다. 따라서 주문 `COMPLETED`, 판매자·구매자 알림, `notifyShipmentCompleted`(`P:117`) 모두 실행되지 않는다. 입찰·판매 상태도 그대로(`MATCHED`/없음).
- 결과: 배송 `DELIVERED` 변경은 저장되지 않고(스킵되어 writer에 가지 않음) 매 6시간 같은 오류가 반복된다. `check-status` 경로에서는 같은 예외가 404(본문 없음)로 응답된다(`C:58-93`, 트랜잭션 롤백).

### (b) 즉시 구매로 만들어진 주문 — 끝까지 진행된다
- 주문은 `PENDING_PAYMENT`이고(`CS:241-245`), 판매 입찰 `MATCHED`·주문 입찰 `MATCHED`(`isInstantPurchase`)가 있다(`CS:279-280`, `domain/m16/service/command/Xzj27CommandService.java:189-205`). 배송은 `createOrderShipment`로 `PENDING`(`CS:264-271`).
- 배송이 배치 대상이 되려면 `check-status`로 운송장을 넣어 `IN_TRANSIT`이 되어야 한다(PATCH 경로는 1-4처럼 실패).
- 배송 완료 시 `completeOrder`: `PENDING_PAYMENT → COMPLETED`는 허용(`OS:24`)되어 주문이 `COMPLETED`가 된다. 결제 처리 때 이미 판매가 `SOLD`로 바뀌어 있어(`Xbf54CommandService.java:83`, `:383-415`, SaleBid 경로·구매자/판매자 "결제 완료" 알림 포함) `canTransitionTo(SOLD)`가 false(`domain/m10/entity/Xgg74Status.java:144-153`)라 판매 상태 변경과 판매자 알림은 건너뛴다. 구매자 알림 "[completeOrder]…" 1건(`S:211-217`) + 배치의 "[배송 완료]…" 1건(`P:117`) = 구매자 2건, 판매자 0건. `check-status` 경로는 `notifyShipmentCompleted`가 없어 구매자 1건.
- 배송 `DELIVERED`, 주문 `COMPLETED`는 저장되지만 주문 입찰·판매 입찰은 `MATCHED` 그대로다(3-6).

| | (a) 일반 구매 입찰 | (b) 즉시 구매 |
|---|---|---|
| 운송장 PATCH | 404 S001, 전부 롤백 | 404 S001, 전부 롤백 |
| 주문 상태(완료 직전) | `PREPARING` | `PENDING_PAYMENT` |
| `completeOrder` | `PREPARING→COMPLETED` 불가로 실패 | 성공(`COMPLETED`) |
| 구매자 알림 | 0건 | 2건(배치) |
| 판매자 알림 | 0건 | 0건(이미 SOLD) |
| 입찰 상태 | 변화 없음 | `MATCHED` 유지 |

## 5. 실패 처리 (주기 처리 중 한 건 실패)
1. `Xth19Processor.process`는 모든 예외를 잡아 `Xpb98Exception`(`EXTERNAL_TRACKING_SERVICE_ERROR` 등)으로 다시 던진다. `P:133-145`의 catch 블록, 페이지는 `P:146-`의 finally에서 닫는다.
2. 스텝은 `faultTolerant().skip(Exception.class).skipLimit(50)`이다(`J:75-77`). 실패한 건은 스킵되어 `shipmentSkipListener`가 오류 로그만 남긴다(`J:78`, 구현 `J:252-`). 해당 건은 변경이 writer로 가지 않아 DB는 이전 상태(`IN_TRANSIT` 등) 그대로이고 다음 주기(6시간 후)에 다시 조회된다.
3. 나머지 건은 계속 처리·저장된다. 청크(50) 단위 트랜잭션이므로 실패 시 해당 청크가 롤백되었다가 실패 항목만 빼고 재처리된다. 스킵이 50건을 넘으면 잡이 실패한다.
4. 스케줄러는 잡 실행 예외를 `printStackTrace()`로만 처리한다(`global/config/Xpb98BatchScheduler.java:41-43`).
5. 참고: 사용되지 않는 `S.updateShipmentStatuses()`는 건별 try/catch로 계속 진행하고 카운트만 남기는 방식이지만(`S:383-387`) 호출되지 않는다.
