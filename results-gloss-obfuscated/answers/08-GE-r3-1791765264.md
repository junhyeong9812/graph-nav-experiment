# 구매자 배송: 운송장 등록 → 배송 완료

경로 약어: `M12` = `src/main/java/com/fream/back/domain/m12`, `M16` = `.../domain/m16`, `M06` = `.../domain/m06`, `M10` = `.../domain/m10`, `M15` = `.../domain/m15`, `G` = `.../global`.
이름 대응: Xhx14 = OrderShipment, Xdg64 = Order, Xzj27 = OrderBid, Xzz58 = SaleBid, Xgg74 = Sale, Xpb98Status = Shipment 상태, Xkh73 = Notification.

## 요약

- 운송장 등록 API(`PATCH /shipments/order/{id}/status`)는 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문에서 **항상 실패**한다. 그 주문의 상태는 `PREPARING`인데, 주문 상태 머신은 `PREPARING → IN_TRANSIT`을 허용하지 않기 때문이다. 트랜잭션이 롤백되어 아무것도 저장되지 않고, 응답은 404 `S001 "배송 정보를 찾을 수 없습니다."`이다.
- 배송 완료 감지는 6시간마다 도는 Spring Batch Job이다. 실제로 쓰이는 프로세서는 `Xth19Processor`이다.
- 배송 완료 후 처리(`completeOrder`)는 (a) 실배송 일반 구매 입찰 주문에서는 끝까지 못 간다(`PREPARING → COMPLETED` 불가). (b) 즉시 구매 주문에서는 끝까지 간다(`PENDING_PAYMENT → COMPLETED` 허용). 단 입찰 상태는 어느 쪽도 `COMPLETED`가 되지 않는다.

## 1. 운송장 등록 요청

### 1-1. 진입 API

1. `PATCH /shipments/order/{shipmentId}/status`, body는 `Xhx14RequestDto`(courier, trackingNumber). — `M12/controller/command/Xhx14CommandController.java:20,33-49`
2. 컨트롤러는 `Xhx14CommandService.updateTrackingInfo(shipmentId, courier, trackingNumber)`를 호출하고 성공하면 200을 돌려준다. — `Xhx14CommandController.java:41-48`
3. 같은 컨트롤러의 `POST /{shipmentId}/check-status`(`Xhx14CommandController.java:58`)와 `/check-status-string`(`:103`)은 별도의 "즉시 조회" 경로이다. 3-1 이후에서 다룬다.

### 1-2. 의도된 상태 변경 순서 (`updateTrackingInfo`, `M12/service/command/Xhx14CommandService.java:238-303`)

1. 입력 검증: courier·trackingNumber가 비어 있으면 `TRACKING_INFO_REQUIRED`. — `Xhx14CommandService.java:243-246`
2. 배송(Xhx14) 조회 후 `shipment.updateTrackingInfo(courier, trackingNumber)` 호출. 엔티티는 택배사·운송장을 넣고 상태를 **전환 검사 없이** `IN_TRANSIT`으로 직접 세팅한다(PENDING에서 IN_TRANSIT은 상태 머신상 불가이지만 우회). — `Xhx14CommandService.java:249-256`, `M12/entity/Xhx14.java:41-45`
3. 주문(Xdg64) 상태를 `IN_TRANSIT`으로 변경. — `Xhx14CommandService.java:259-262`
4. 알림: **구매자**에게 "상품이 출발하였습니다. 주문 ID: …" 1건. — `Xhx14CommandService.java:265-273`
5. `updateSaleStatusToSold(orderId)`로 판매(Xgg74)를 `SOLD`로 바꾸고 **판매자**에게 "상품이 성공적으로 판매 완료되었습니다" 알림. 창고 보관 상품이면 창고 상태도 SOLD로 바꾼다. — `Xhx14CommandService.java:276`, 본문 `:111-183`
6. 창고 보관 판매이면 `updateWarehouseStatusToSold`를 다시 한 번 호출. — `Xhx14CommandService.java:279-286`
7. `updateOrderAndSaleBidStatusToCompleted`로 OrderBid(Xzj27)·SaleBid(Xzz58)를 `MATCHED → COMPLETED`로 변경. — `Xhx14CommandService.java:289`, 본문 `:412-440`

즉, 설계상 순서는 배송 `IN_TRANSIT` → 주문 `IN_TRANSIT` → (구매자 알림) → 판매 `SOLD`(+판매자 알림) → 입찰들 `COMPLETED`이다.

### 1-3. 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문에서 끝까지 성공하나? — **아니오**

**전제: 주문 상태가 PREPARING이다.**

1. 결제·배송 처리 API `POST /{orderId}/process-payment-shipment`는 Kafka 이벤트를 보내고, 컨슈머가 처리한다. — `M16/controller/command/Xdg64CommandController.java:41-60`, `M16/service/kafka/Xdg64EventConsumer.java:166-220`
2. 일반(비창고) 주문은 `PENDING_PAYMENT → PAYMENT_COMPLETED → PREPARING`에서 멈춘다. — 컨슈머 `Xdg64EventConsumer.java:192-195, 215-217`. 동기 경로 `Xdg64CommandService.processPaymentAndShipment`도 동일하다. — `M16/service/command/Xdg64CommandService.java:174-177`
3. 창고 보관 주문은 `COMPLETED`까지 간다. — `Xdg64CommandService.java:163-172`. "실배송"이 아니므로 대상이 아니다.
4. 이 단계에서 배송(Xhx14)은 `PENDING`으로 생성된다. — `Xhx14CommandService.java:56-70`

**실패 지점: `Xhx14CommandService.java:260`, `order.updateStatus(Xdg64Status.IN_TRANSIT)`**

1. 주문 상태 머신: `PREPARING`은 `{IN_WAREHOUSE, SHIPMENT_STARTED}`만 허용한다. `IN_TRANSIT`은 `SHIPMENT_STARTED`에서만 갈 수 있다. — `M16/entity/Xdg64Status.java:26,28,29`
2. `Xdg64.updateStatus`가 `Xxc76StatusException`("상태 전환이 허용되지 않습니다: PREPARING -> IN_TRANSIT")을 던진다. — `M16/entity/Xdg64.java:112-120`(파일 기준 `updateStatus`), 예외 정의 `M16/exception/Xxc76StatusException.java`
3. `SHIPMENT_STARTED`로 바꾸는 코드는 코드베이스에 없다. `Xdg64Status.SHIPMENT_STARTED`는 enum 정의 외에 쓰이는 곳이 없다(전체 `Xdg64Status.*` 사용처에서 확인).
4. 이 예외는 `Xpb98Exception`이 아니므로 `catch (Exception e)`에 걸려 `Xpb98Exception(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")`로 포장되어 다시 던져진다. — `Xhx14CommandService.java:293-302`

**무엇이 저장되나: 아무것도 저장되지 않는다.**

1. `updateTrackingInfo`는 `@Transactional`이고(`Xhx14CommandService.java:238`), `Xpb98Exception`은 `RuntimeException` 계열이다(`G/exception/Xks43Exception.java:10`). 그래서 트랜잭션 전체가 롤백된다.
2. 2단계에서 엔티티에 반영한 택배사·운송장·`IN_TRANSIT`은 flush 전에 롤백되어 DB에 남지 않는다.
3. 주문 상태 변경 뒤에 있는 구매자 알림(`:266`)과 판매·입찰 처리(`:276`, `:289`)는 아예 실행되지 않는다.

**응답: HTTP 404**

1. `Xks43ExceptionHandler`가 `ErrorResponse(code="S001", message="배송 정보를 찾을 수 없습니다.", status=404, path)`를 돌려준다. — `G/exception/Xks43ExceptionHandler.java:49-62`, `M12/exception/Xpb98ErrorCode.java:12`
2. 상세 원인("PREPARING -> IN_TRANSIT")은 응답 본문이 아니라 로그에만 남는다. 에러 코드명도 실제 원인(주문 상태 전환 불가)과 달리 "배송 없음"이라 오해를 부른다.

(참고: 정상 흐름이라면 SaleBid가 없는 일반 주문에서는 5단계 `saleBidQueryService.findByOrderId`가 null이 아니라 `IllegalArgumentException`을 던지는 구조이다. — `M10/service/query/Xzz58QueryService.java:26-28`. 그래서 `if (saleBid != null)` 분기(`Xhx14CommandService.java:117`)는 사실상 도달 불가이고, 어차피 이 지점까지 가지도 못한다.)

## 2. 배송 완료 감지

### 2-1. 누가·언제·어떻게

1. 주체: Spring `@Scheduled` 스케줄러 `Xpb98BatchScheduler.scheduleShipmentStatusJob()`가 Spring Batch Job `updateShipmentStatusesJob`을 `JobLauncher`로 실행한다. — `G/config/Xpb98BatchScheduler.java:34-41`
2. 주기: `cron = "0 0 */6 * * *"` → 매일 00:00, 06:00, 12:00, 18:00(서버 시간대)에 6시간 간격으로 실행. — `Xpb98BatchScheduler.java:34`
3. 실행마다 `timestamp` 파라미터로 새 JobInstance를 만든다. 예외는 `printStackTrace`로만 처리한다. — `Xpb98BatchScheduler.java:37-43`

### 2-2. 대상 배송

JPQL: `SELECT s FROM Xhx14 s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL`. 페이지 크기 50의 `JpaPagingItemReader`. — `M12/config/Xqv91JobConfig.java:93-96,51`

### 2-3. 실제로 실행되는 처리 코드

실제로 실행되는 쪽은 **`Xth19Processor.process`**(`M12/config/Xth19Processor.java:57-146`)이다.

1. 스텝은 `new Xth19Processor(playwrightBrowserManager(), notificationService, orderService)`를 프로세서로 쓴다. — `Xqv91JobConfig.java:69-73`
2. `Xmb36Listener`가 스텝 시작 전에 Playwright 브라우저를 열고 종료 후 닫는다. — `Xqv91JobConfig.java:80`, `M12/config/Xmb36Listener.java`
3. 프로세서 동작: Playwright 페이지로 `https://trace.cjlogistics.com/next/tracking.html?wblNo={운송장}`에 접속 → `tbody#statusDetail tr`의 마지막 행 5번째 `td` 텍스트를 읽어 상태로 사용. — `Xth19Processor.java:70-95, 170-190`

**실행되지 않는 유사 코드**

1. `Xqv91JobConfig.shipmentItemProcessor()` 빈과 `parseCjLogisticsStatus`(Jsoup)는 스텝에 연결되지 않는다. — 연결 확인 `Xqv91JobConfig.java:69`, 정의 `:106`
2. `Xhx14CommandService.updateShipmentStatuses()`(`:308-391`)는 호출하는 곳이 없다. `@Scheduled`도 없다. 이 메서드는 주문만 `COMPLETED`로 바꾸고 `completeOrder`를 쓰지 않는다.
3. `Xhx14CommandService.updateAndCheckShipmentStatus`(`:451`)는 `POST check-status` 컨트롤러에서만 호출된다.

### 2-4. 택배사 상태 문자열 → 내부 상태

`Xth19Processor.mapToShipmentStatus` (`Xth19Processor.java:220-225`)

| 택배사 문자열 | 내부 상태 |
|---|---|
| `"배송완료"` | `DELIVERED` |
| `"배송출발"` | `OUT_FOR_DELIVERY` |
| 그 외 모두 | `IN_TRANSIT` |

주의: 문자열 완전 일치이고 `trim` 후 비교한다(`:187`). "그 외 모두 IN_TRANSIT" 규칙 때문에, 현재 상태가 `OUT_FOR_DELIVERY`인 배송에 택배사가 다른 문자열을 주면 `IN_TRANSIT`으로 매핑된다. `OUT_FOR_DELIVERY`는 `IN_TRANSIT`으로 갈 수 없으므로(`M12/entity/Xpb98Status.java:23-28`), `updateStatus`가 `IllegalStateException`을 던지고(`Xhx14.java:47-55`), 이는 `EXTERNAL_TRACKING_SERVICE_ERROR`로 포장되어 그 건이 skip된다(`Xth19Processor.java:133-145`).

## 3. 배송 완료 판정 이후

`Xth19Processor.process`의 `newStatus == DELIVERED` 분기 (`Xth19Processor.java:108-117`)

### 3-1. 엔티티 상태 변경 순서

1. 현재 상태와 같으면 변경 없이 반환. — `Xth19Processor.java:101-105`
2. 배송(Xhx14) `IN_TRANSIT`(또는 `OUT_FOR_DELIVERY`) → `DELIVERED`. — `Xth19Processor.java:113`
3. `orderService.completeOrder(orderId)` (`Xhx14CommandService.java:190-229`) 실행:
   1. OrderBid 조회. 없으면 `IllegalArgumentException`. — `:196-197`
   2. 주문(Xdg64) → `COMPLETED`. — `:204`
   3. `updateSaleStatusToSold(orderId)`: SaleBid의 Sale을 `SOLD`로 바꾸고(창고 보관이면 창고 상태도 SOLD), 판매자 알림 생성. 이어서 OrderBid의 Sale도 `SOLD` 시도. — `:208`, 본문 `:111-183`. 두 분기 모두 `canTransitionTo(SOLD)`가 참일 때만 동작한다. — `:119, :156`
   4. 구매자 알림. — `:211-217`
   5. 어느 단계에서든 예외가 나면 `Xpb98Exception(ORDER_NOT_FOUND_FOR_SHIPMENT)`로 포장해 다시 던진다. — `:221-228`
4. `notificationService.notifyShipmentCompleted(order)`. — `Xth19Processor.java:117`
5. 스텝 writer(`JpaItemWriter`)가 배송을 저장(merge)한다. — `Xqv91JobConfig.java:76, 118-124`

### 3-2. 알림 수

정상적으로 끝까지 가면:

- **구매자 2건**:
  1. `"[completeOrder] 주문이 완료 처리되었습니다. 주문 ID: …"` — `Xhx14CommandService.java:212-217`
  2. `"[배송 완료] 상품이 배송 완료되었습니다. 주문 ID: …"` — `M15/service/command/Xkh73CommandService.java:219-228`
- **판매자 최대 1건**: `"상품이 성공적으로 판매 완료되었습니다. 판매 ID: …"`. Sale이 `SOLD`로 전환 가능할 때만 생성되며, 두 분기 중 먼저 전환된 한 번만 나간다(두 번째는 `SOLD → SOLD`가 불가). — `Xhx14CommandService.java:133-138, 164-169`. 실제로 몇 건이 되는지는 4번에서 설명한다.

### 3-3. 주문 입찰·판매 입찰 상태

1. 배송 완료 경로(`completeOrder`)는 OrderBid·SaleBid의 상태를 **바꾸지 않는다.** 두 입찰을 `COMPLETED`로 바꾸는 `updateOrderAndSaleBidStatusToCompleted`는 `updateTrackingInfo`에서만 호출된다(`Xhx14CommandService.java:289`). 다른 호출처는 없다.
2. 따라서 배송 완료 시점에도 OrderBid·SaleBid는 `MATCHED`로 남는다(생성/매칭 시 `MATCHED`: `M16/entity/Xzj27.java` `assignOrder`, `M10/entity/Xzz58.java:58-61`).
3. 바뀌는 것은 Sale(`SOLD`), 주문(`COMPLETED`), 배송(`DELIVERED`)뿐이다.
4. 그 위에, 운송장 등록 경로는 1-3에서 본 대로 실패하므로 입찰을 `COMPLETED`로 바꾸는 유일한 코드는 일반 주문에서 실제로는 도달하지 못한다.

## 4. 주문 종류별 차이

배치가 이 배송을 읽으려면 배송이 `IN_TRANSIT`/`OUT_FOR_DELIVERY`이면서 운송장이 있어야 한다. 운송장 PATCH는 두 주문 모두에서 막히므로(아래), 배송을 `IN_TRANSIT`으로 만드는 현실적인 경로는 `POST /{id}/check-status`이다. 이 경로는 배송에 운송장·`IN_TRANSIT`만 저장하고 주문 상태는 건드리지 않는다. — `Xhx14CommandService.java:473, 497`, `Xhx14.java:41-45`

### (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문 — **끝까지 진행되지 않는다**

1. 주문 상태가 `PREPARING`이다(1-3 참고).
2. 배송이 `DELIVERED`로 판정되면 `completeOrder`의 `order.updateStatus(COMPLETED)`에서 막힌다. `PREPARING`은 `{IN_WAREHOUSE, SHIPMENT_STARTED}`만 허용한다. — `Xhx14CommandService.java:204`, `Xdg64Status.java:26`
3. `Xxc76StatusException` → `Xpb98Exception(ORDER_NOT_FOUND_FOR_SHIPMENT)`로 포장. — `Xhx14CommandService.java:221-228`
4. 트랜잭션이 롤백되므로 주문·판매·알림 변경은 DB에 남지 않는다. 배송은 `IN_TRANSIT`/`OUT_FOR_DELIVERY` 그대로이다. 프로세서는 예외를 다시 던진다(`Xth19Processor.java:133-145`). 스텝이 skip 처리하고 6시간 뒤에 다시 같은 오류가 반복된다.
5. 결과: 구매자·판매자 알림 0건, 주문 `PREPARING` 유지, Sale 상태 변경 없음, 입찰 상태 변경 없음.
6. `POST check-status`로 즉시 조회해 `배송완료`가 나와도 같은 `completeOrder` 호출(`Xhx14CommandService.java:489`)에서 같은 실패가 난다. 이 경우 컨트롤러는 빈 본문 404를 돌려준다. — `Xhx14CommandController.java:75-82`(`catch (Xpb98Exception)`)
7. (참고) 일반 구매 입찰 주문은 결제 시점에 Sale이 없다(OrderBid에 `sale`을 넣지 않음: `M16/service/command/Xzj27CommandService.java:91-98`, 결제 알림 쪽 `M06/service/command/Xbf54CommandService.java:388-417`에서 sale이 null이면 경고 후 반환). 즉 이 주문은 매칭 전이면 구조적으로도 판매 쪽 처리가 비어 있다.

### (b) 즉시 구매로 만들어진 주문 — **끝까지 진행된다**

1. 즉시 구매 주문은 `PENDING_PAYMENT` 상태로 생성되고, 이후 주문 상태를 바꾸는 코드가 없다. `createInstantOrder`는 상태를 건드리지 않는다. — `Xdg64CommandService.java:241-245, 219-319`
2. `PENDING_PAYMENT → COMPLETED`는 허용된다. — `Xdg64Status.java:24`. 그래서 `completeOrder`의 `order.updateStatus(COMPLETED)`가 통과한다. — `Xhx14CommandService.java:204`
3. OrderBid가 존재한다. 즉시 구매는 주문 생성 후 OrderBid를 `MATCHED`·`isInstantPurchase=true`로 만든다. — `Xzj27CommandService.java:133, 142, 189-206`. 따라서 `completeOrder`의 OrderBid 조회가 성공한다(`:196`).
4. SaleBid가 주문에 연결되어 있다. — `Xdg64CommandService.java:279-283`. 그래서 `findByOrderId`가 예외 없이 반환한다.
5. **판매자 알림은 0건이다.** 결제 처리(`processPayment`, `Xdg64CommandService.java:305`)가 OrderBid 생성(`Xzj27CommandService.java:142`)보다 먼저 일어난다. 그래서 `order.getOrderBid()`가 null이고, 결제 서비스가 SaleBid 경로를 타서 Sale을 이미 `SOLD`로 바꿔 놓는다. — `Xbf54CommandService.java:83, 388-405`. `Xgg74.updateStatus`는 전환 검사가 없다(`M10/entity/Xgg74.java:73-75`). 배송 완료 시점에는 Sale이 이미 `SOLD`여서 `canTransitionTo(SOLD)`가 거짓이다. 따라서 판매자 알림과 창고 SOLD 갱신이 건너뛰어진다. — `Xgg74Status.java`(`SOLD → false`), `Xhx14CommandService.java:119, 156`
6. 결과: 배송 `DELIVERED`, 주문 `COMPLETED`, 구매자 알림 2건, 판매자 알림 0건, Sale은 이미 `SOLD`, OrderBid·SaleBid는 `MATCHED` 유지(`COMPLETED`로 안 바뀜).

### 비교

| | (a) 실배송 일반 구매 입찰 | (b) 즉시 구매 |
|---|---|---|
| 배송 완료 시 주문 상태 | `PREPARING`, `COMPLETED` 불가 | `PENDING_PAYMENT`, `COMPLETED` 가능 |

## 5. 실패 처리 (주기 처리 중 한 건이 실패할 때)

1. 스텝이 `faultTolerant().skip(Exception.class).skipLimit(50)`으로 설정되어 있다. 청크 크기는 50이다. — `Xqv91JobConfig.java:51-52, 75-77`
2. 한 건에서 예외가 나면(`Xpb98Exception` 등) 그 청크 트랜잭션이 롤백되고, 청크를 항목별로 다시 처리하면서 실패한 건만 skip된다. 실패한 건은 `onSkipInProcess`가 error 로그를 남긴다. — `Xqv91JobConfig.java:252-262`
3. 나머지 건은 정상 처리되어 저장된다. 실패한 건의 DB 변경(배송·주문·알림)은 롤백되어 남지 않는다. 그 건은 상태가 그대로여서 다음 실행(6시간 뒤)에 다시 조회된다.
4. skip이 50건을 넘으면 `SkipLimitExceededException`으로 스텝이 실패한다. 그 뒤 항목은 이번 실행에서 처리되지 않고 다음 실행을 기다린다. 스케줄러는 예외를 `printStackTrace`로만 삼킨다. — `Xpb98BatchScheduler.java:41-43`
5. `Xth19Processor`는 운송장이 비면 `TRACKING_NUMBER_INVALID`, 브라우저가 없으면 `BROWSER_INITIALIZATION_ERROR`, 표가 비거나 파싱이 안 되면 `TRACKING_HTML_PARSE_ERROR`를 던지고, 그 외 예외는 `EXTERNAL_TRACKING_SERVICE_ERROR`로 감싼다. 모두 skip 대상이다. — `Xth19Processor.java:60-64, 72-75, 133-145, 170-190`
6. 알림 생성 실패는 `notifyShipmentCompleted` 안에서 삼켜져(`Xkh73CommandService.java:230-233`) 배송 처리 자체를 실패시키지 않는다. 반면 `completeOrder` 안의 `createNotification` 실패는 `completeOrder`의 catch로 가서 그 건 전체를 실패시킨다(`Xhx14CommandService.java:221-228`).
7. (추정) 리더가 정렬 없는 페이징 쿼리이고 페이지마다 조건에 맞는 행이 `DELIVERED`로 빠진다. 그래서 같은 실행에서 일부 행이 다음 페이지 오프셋에 가려 건너뛰어질 수 있으며, 건너뛴 건은 다음 실행에 처리된다. — `Xqv91JobConfig.java:93-96`
