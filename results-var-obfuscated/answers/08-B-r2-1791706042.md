경로 약어: `M12 = src/main/java/com/fream/back/domain/m12`, `M16 = .../domain/m16`, `M10 = .../domain/m10`, `M06 = .../domain/m06`, `G = .../global`, `M15 = .../domain/m15`

## 사전: 결제·배송 처리 후의 상태 (질문 1·4의 전제)

- 결제·배송 처리: `M16/service/command/Xdg64CommandService.java:112` `processPaymentAndShipment`
  - 구매자 배송 `Xhx14`는 `PENDING`으로 생성 — `M12/service/command/Xhx14CommandService.java:61-68`
  - 실배송(창고 보관 아님)이면 주문 상태는 `PAYMENT_COMPLETED` → `PREPARING`에서 멈춘다 — `M16/service/command/Xdg64CommandService.java:174-177`. (창고 보관이면 `IN_WAREHOUSE` → `COMPLETED`까지 가므로 `:163-172` 배송 대상이 아니다.)
- 주문 상태 전이표: `PREPARING`은 `IN_WAREHOUSE`, `SHIPMENT_STARTED`로만 갈 수 있다 — `M16/entity/Xdg64Status.java:26`. `IN_TRANSIT`은 `SHIPMENT_STARTED`에서만(`:28`), `COMPLETED`는 `IN_TRANSIT`/`IN_WAREHOUSE`/`PENDING_PAYMENT`에서만 갈 수 있다(`:24, :27, :29`).
- 주문 상태 변경은 `Xdg64.updateStatus`가 전이표를 검사하고 위반 시 `Xxc76StatusException`을 던진다 — `M16/entity/Xdg64.java:113-120`.

## 1. 운송장 등록 요청

### 1-1. 진입 API
- `PATCH /shipments/order/{shipmentId}/status`, body `{courier, trackingNumber}` — `M12/controller/command/Xhx14CommandController.java:20, 33-49`
- 서비스 `Xhx14CommandService.updateTrackingInfo(shipmentId, courier, trackingNumber)` 호출 — `M12/service/command/Xhx14CommandService.java:238-246`
- 택배사/운송장이 null·blank이면 `TRACKING_INFO_REQUIRED`(400) — `:243-246`

### 1-2. 설계된 상태 변경 순서와 알림
`Xhx14CommandService.updateTrackingInfo`(`:238-303`)가 한 트랜잭션 안에서 아래 순서로 처리하도록 짜여 있다.
1. 배송 조회 `findById`, 없으면 `SHIPMENT_NOT_FOUND` — `:249-253`
2. 배송 엔티티: 택배사·운송장 저장 + 상태 `IN_TRANSIT`으로 직접 대입(전이 검증 없음) — `:256`, `M12/entity/Xhx14.java:41-45`
3. 주문 상태 → `IN_TRANSIT` — `:259-260`
4. 구매자(`order.getUser()`)에게 알림 "상품이 출발하였습니다. 주문 ID: …" 1건 — `:265-271`
5. `updateSaleStatusToSold(orderId)` — `:276`
   - 판매 입찰(SaleBid)의 판매(Sale)가 `SOLD`로 전이 가능하면 `SOLD`로 바꾸고, 창고 보관이면 창고 상태도 SOLD, 판매자에게 알림 "상품이 성공적으로 판매 완료되었습니다" — `:116-141`
   - 주문 입찰(OrderBid) 쪽 Sale도 같은 방식으로 처리 — `:150-176`
6. 창고 보관 상품이면 창고 상태 SOLD — `:279-286`
7. `updateOrderAndSaleBidStatusToCompleted` — 주문입찰/판매입찰이 `MATCHED`이면 `COMPLETED`로 — `:289`, `:412-440`

즉 설계 의도: 배송 `IN_TRANSIT` → 주문 `IN_TRANSIT` → (구매자 알림) → 판매 `SOLD`(판매자 알림) → 입찰들 `COMPLETED`.

### 1-3. 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문(즉시 구매 아님)은 끝까지 성공하는가 → **실패한다**
- 실패 지점: 3단계 `order.updateStatus(Xdg64Status.IN_TRANSIT)` — `M12/service/command/Xhx14CommandService.java:260`
- 이유: 이 주문은 `PREPARING`(위 사전 항목)인데 `PREPARING → IN_TRANSIT` 전이는 허용되지 않는다 — `M16/entity/Xdg64Status.java:26`. `Xdg64.updateStatus`가 `Xxc76StatusException("상태 전환이 허용되지 않습니다: PREPARING -> IN_TRANSIT")`을 던진다 — `M16/entity/Xdg64.java:113-120`
- 예외 처리: 바깥 `catch (Exception e)`가 받아 `Xpb98Exception(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")`로 감싸 던진다 — `:295-302`. (`Xpb98Exception`만 따로 재throw하는 `:293-294` 분기는 해당 없음 — `Xxc76StatusException`은 `Xdg64Exception` 계열이다 — `M16/exception/Xxc76StatusException.java:6`.)
- 저장되는 것: **없다.** `@Transactional`(`:238`) 메서드가 `RuntimeException`(`Xks43Exception extends RuntimeException`, `G/exception/Xks43Exception.java:10`)을 던지므로 롤백되어, 2단계에서 바꾼 택배사·운송장·`IN_TRANSIT`도 DB에 남지 않는다. 배송은 `PENDING` 그대로, 주문은 `PREPARING` 그대로. 구매자/판매자 알림은 4·5단계 이전에 중단되어 한 건도 생성되지 않는다(알림 생성 코드는 `:265` 이후).
- 응답: HTTP **404**, 본문 `ErrorResponse(code="S001", message="배송 정보를 찾을 수 없습니다.", status=404, path=요청 URI)`. 컨트롤러에 try/catch가 없고(`M12/controller/command/Xhx14CommandController.java:33-49`) `Xpb98Exception` 전용 핸들러가 `errorCode`의 코드·메시지·상태를 쓴다 — `G/exception/Xks43ExceptionHandler.java:459-472`; 코드값은 `M12/exception/Xpb98ErrorCode.java:102` (`SHIPMENT_NOT_FOUND("S001", …, 404)`). 실제 원인 문구는 응답 본문이 아니라 로그/예외 메시지에만 있다(핸들러가 `errorCode.getMessage()`를 쓰므로).
- 부가: 같은 `PREPARING` 주문이 이 API를 통과하려면 주문이 `SHIPMENT_STARTED`여야 하는데, 코드 어디서도 `SHIPMENT_STARTED`로 설정하는 곳이 없다(`grep Xdg64Status.SHIPMENT_STARTED`는 전이표 정의 `M16/entity/Xdg64Status.java:26-28`뿐). 따라서 이 PATCH는 일반 주문에서 구조적으로 성공 불가.

(`Xth19Processor`에는 save 호출이 없고 Writer가 저장한다.)

### 알림 건수
- 구매자: **2건** — "[completeOrder] 주문이 완료 처리되었습니다"(`Xhx14CommandService.java:212-217`) + "[배송 완료] 상품이 배송 완료되었습니다"(`Xkh73CommandService.java:224-229`). 같은 사건에 중복 알림이 간다.
- 판매자: Sale이 `ON_AUCTION`/`SELLING`일 때만 1건(`M10/entity/Xgg74Status.java:21-22`가 `SOLD` 전이를 허용하는 상태). 그 외(특히 이미 `SOLD`)면 0건 — `Xhx14CommandService.java:119, 156`.

### 입찰 상태
- 배송 완료 경로(`completeOrder`)는 주문입찰(`Xzj27`)·판매입찰(`Xzz58`)의 상태를 **바꾸지 않는다**. `COMPLETED`로 바꾸는 `updateOrderAndSaleBidStatusToCompleted`는 운송장 등록 메서드에서만 호출된다(`Xhx14CommandService.java:289`; `completeOrder` `:190-229`에는 호출 없음). 따라서 `MATCHED` 상태 그대로 남는다.
- 이름/주석이 말하는 의도("주문 완료 처리")와 달리 입찰은 COMPLETED가 되지 않는다.

## 4. 주문 종류별 차이

### (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문 → **끝까지 진행되지 않는다**
- 운송장 등록 PATCH가 1-3처럼 실패하므로 배송은 `PENDING`에 머물고 배치 대상(`IN_TRANSIT`/`OUT_FOR_DELIVERY`)에 들어가지 않는다 — `M12/config/Xqv91JobConfig.java:95`.
- (수동 `check-status`로 배송만 `IN_TRANSIT`/`OUT_FOR_DELIVERY`가 되어 배치에 잡힌다고 가정해도) `completeOrder`가 `order.updateStatus(COMPLETED)`에서 `PREPARING → COMPLETED` 불허로 `Xxc76StatusException` — `M12/service/command/Xhx14CommandService.java:204`, `M16/entity/Xdg64Status.java:26`. 설령 통과해도 `updateSaleStatusToSold`의 `saleBidQueryService.findByOrderId`가 판매입찰이 없으면 `null`이 아니라 `IllegalArgumentException`을 던진다 — `M10/service/query/Xzz58QueryService.java:26-29`(`Xhx14CommandService.java:116`의 `null` 검사는 사실상 죽은 코드). 일반 입찰 주문은 판매입찰이 없으므로 이쪽에서도 실패한다. 둘 다 `completeOrder`의 catch에서 `Xpb98Exception(ORDER_NOT_FOUND_FOR_SHIPMENT)`(`:221-228`).
- 결과: 주문은 `PREPARING`, 배송은 `DELIVERED` 반영 안 됨(롤백/스킵), 알림 0건, 입찰 상태 변화 없음.

### (b) 즉시 구매로 만들어진 주문 → **진행된다**(단, 알림·입찰 결과가 다름)
- 즉시 구매 주문은 `PENDING_PAYMENT`로 생성되고 결제 처리가 주문 상태를 바꾸지 않아 `PENDING_PAYMENT`로 남는다 — `M16/service/command/Xdg64CommandService.java:241-245, 304-309`(결제 서비스에 `Xdg64Status` 사용 없음 — `M06/service/command/Xbf54CommandService.java`). `PENDING_PAYMENT → COMPLETED`는 전이표에서 허용 — `M16/entity/Xdg64Status.java:24`. 따라서 `completeOrder`의 `:204`가 통과해 주문이 `COMPLETED`가 된다.
- 판매입찰은 `saleBid.assignOrder(order)`로 주문에 연결 — `M16/service/command/Xdg64CommandService.java:279`, 주문입찰도 order/sale과 함께 생성(`isInstantPurchase=true`) — `M16/service/command/Xzj27CommandService.java:189-206`. 그래서 `findByOrderId`들이 모두 값을 반환한다.
- 결제 시점에 이미 Sale을 `SOLD`로 직접 세팅한다 — `M06/service/command/Xbf54CommandService.java:83, 391-406`(`order.getOrderBid()`가 아직 null일 때 판매입찰 경로로 `sale.updateStatus(SOLD)`). 그래서 배송 완료 시 `SOLD.canTransitionTo(SOLD)`가 false(`M10/entity/Xgg74Status.java:23`) → 판매 상태 변경·창고 상태 변경·판매자 알림 모두 건너뜀 — `Xhx14CommandService.java:119, 142-144, 156, 173-175`.
- 결과: 배송 `DELIVERED`, 주문 `COMPLETED`, 구매자 알림 2건(위 3절), 판매자 알림 0건, 주문입찰·판매입찰은 `MATCHED` 유지(3절 근거).
- 단, 이 주문의 배송이 배치 대상이 되려면 `IN_TRANSIT`이어야 하는데 PATCH는 `PENDING_PAYMENT → IN_TRANSIT` 불허(`Xdg64Status.java:24`)로 실패하므로, 실제로는 수동 `POST .../check-status`(`updateAndCheckShipmentStatus`)로 배송 상태가 먼저 `IN_TRANSIT`/`OUT_FOR_DELIVERY`가 되어야 한다 — `Xhx14CommandService.java:473, 483-498`. 이 수동 경로에서 `DELIVERED`가 확인되면 같은 `completeOrder`가 즉시 실행된다(`:489`; 이때는 `notifyShipmentCompleted`가 없어 구매자 알림은 1건).

## 5. 실패 처리 (주기 배치 중 한 건 실패)

- Step이 `faultTolerant().skip(Exception.class).skipLimit(50)` — `M12/config/Xqv91JobConfig.java:75-77`. 청크 크기 50.
- 한 건에서 예외(조회 실패, 파싱 실패, 상태 전이 불허, `completeOrder` 실패 등)가 나면 `Xth19Processor`가 `Xpb98Exception`으로 감싸 던지고(`M12/config/Xth19Processor.java:133-146`), 해당 청크 트랜잭션은 롤백된 뒤 스킵 모드로 아이템을 하나씩 재처리한다. 실패한 건은 스킵되어(`SkipListener`가 ERROR 로그만 남김 — `M12/config/Xqv91JobConfig.java:251-286`) 그 건의 변경(배송 상태, 주문 상태, 알림)은 반영되지 않고 상태가 그대로 남아 **다음 6시간 주기에 다시 대상**이 된다(여전히 `IN_TRANSIT`/`OUT_FOR_DELIVERY`).
- 나머지 건은 중단 없이 계속 처리·커밋된다. 단 스킵 한도(50)를 넘으면 Step이 실패하고 잡이 종료된다 — `:77`.
- 스케줄러 자체는 잡 실행 예외를 `printStackTrace()`만 하고 삼킨다 — `G/config/Xpb98BatchScheduler.java:41-43`. 알림 전송 실패는 `notifyShipmentCompleted` 내부에서만 삼켜진다(`M15/service/command/Xkh73CommandService.java:230-233`); `completeOrder` 안의 알림 실패는 건 전체 실패로 이어진다(`Xhx14CommandService.java:221-228`).
- 참고: 사용되지 않는 `updateShipmentStatuses()`(`Xhx14CommandService.java:322-388`)는 건별 try/catch로 계속 진행하도록 짜여 있지만 호출되지 않아 실제 동작과 무관하다.
