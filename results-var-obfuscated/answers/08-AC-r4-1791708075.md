## 전제: 결제 후 주문·배송 상태

- 구매 입찰 주문은 `PENDING_PAYMENT`로 생성된다 (`OC:81`). 이때 주문 입찰(Xzj27)이 만들어지면서 `assignOrder`가 입찰 상태를 `MATCHED`로 바꾼다 (`domain/m16/service/command/Xzj27CommandService.java:60,100`, `domain/m16/entity/Xzj27.java:73-80`).
- 결제·배송 처리 `processPaymentAndShipment`가 배송(Xhx14)을 `PENDING`으로 만들어 주문에 붙인다 (`OC:148-155`, `S:61-70`).
- 실배송(창고 보관 아님)이면 주문은 `PAYMENT_COMPLETED → PREPARING`에서 멈춘다 (`OC:174-177`). Kafka 경로도 같다 (`domain/m16/service/kafka/Xdg64EventConsumer.java:195-218`).
- 즉시 구매 주문은 `createInstantOrder`에서 `PENDING_PAYMENT`로 만들어진 뒤 상태가 전혀 바뀌지 않는다. `PAYMENT_COMPLETED`, `PREPARING` 전환 코드가 없다 (`OC:244`, 배송 생성 `OC:264-271`, 판매 입찰 매칭 `OC:279-280`, 결제 `OC:305`).
- `SHIPMENT_STARTED`로 바꾸는 코드는 어디에도 없다 (grep 결과 `OS` enum 선언과 전이표뿐).

## 1. 운송장 등록 요청

### 1-1. 진입 API
- `PATCH /shipments/order/{shipmentId}/status`, body `{courier, trackingNumber}` (`C:20,33-49`) → `S#updateTrackingInfo` (`S:238-303`).
- 같은 컨트롤러에 `POST /shipments/order/{id}/check-status`와 `/check-status-string`도 있다 (`C:58,103`). 이 둘은 운송장을 저장하고 즉시 택배사를 조회하는 `S#updateAndCheckShipmentStatus`(`S:451-516`)를 호출한다. 주문 상태는 건드리지 않고 배송만 `IN_TRANSIT`으로 만든다.

### 1-2. 의도된 상태 변경 순서와 알림 (`S#updateTrackingInfo`)
1. courier·trackingNumber가 비어 있으면 `TRACKING_INFO_REQUIRED` (`S:243-246`).
2. 배송 조회. 없으면 `SHIPMENT_NOT_FOUND` (`S:249-253`).
3. **배송(Xhx14)**: `updateTrackingInfo`가 courier·trackingNumber를 쓰고 status를 `IN_TRANSIT`으로 바로 대입한다 (`S:256`, `SH:41-45`). 전이 검증은 없다.
4. **주문(Xdg64)** → `IN_TRANSIT` (`S:259-260`). `Xdg64.updateStatus`는 전이표를 검사하고 위반 시 `Xxc76StatusException`을 던진다 (`domain/m16/entity/Xdg64.java:113-120`).
5. **구매자 알림 1건**: "상품이 출발하였습니다. 주문 ID: …" (`S:265-271`).
6. `updateSaleStatusToSold(orderId)` (`S:276`, 본문 `S:111-183`):
   - 판매(Xgg74) → `SOLD`. `canTransitionTo(SOLD)`일 때만 바뀐다 (`S:119-123`).
   - 창고 보관 상품이면 창고 상태를 `SOLD`로 바꾼다 (`S:126-129`).
   - **판매자 알림**: "상품이 성공적으로 판매 완료되었습니다. 판매 ID: …" (`S:132-138`).
   - 주문 입찰 쪽 판매도 같은 방식으로 처리한다 (`S:150-180`).
7. 창고 보관 상품이면 창고 상태를 다시 `SOLD`로 바꾼다 (`S:279-286`).
8. `updateOrderAndSaleBidStatusToCompleted` (`S:289`, 본문 `S:412-440`): 주문 입찰(Xzj27)과 판매 입찰(Xzz58)이 `MATCHED`이면 `COMPLETED`로 바꾼다. 예외는 삼킨다 (`S:436-439`). 즉 입찰은 설계상 운송장 등록 시점에 이미 COMPLETED가 된다.

### 1-3. 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문: 끝까지 성공하지 않는다
- 이 시점의 주문 상태는 `PREPARING`이다. 허용 전이는 `IN_WAREHOUSE`, `SHIPMENT_STARTED`뿐이다 (`OS:26`).
- **실패 지점**: `S:260`의 `order.updateStatus(IN_TRANSIT)`. `Xdg64.updateStatus`(`domain/m16/entity/Xdg64.java:113-120`)가 `Xxc76StatusException`("상태 전환이 허용되지 않습니다: PREPARING -> IN_TRANSIT")을 던진다.
- 이 예외는 `Xpb98Exception`이 아니므로 `catch (Exception e)` (`S:295-301`)에 잡혀 `Xpb98Exception(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")`으로 감싸져 던져진다.
- **저장되는 것: 없음.**
  - 배송에 들어간 courier·trackingNumber·`IN_TRANSIT`은 메모리 변경뿐이다.
  - 예외가 `@Transactional`(`S:238`) 밖으로 RuntimeException으로 나가므로 롤백된다.
  - 구매자 알림(`S:265`)과 판매 처리(`S:276`)는 실패 지점 뒤라서 실행되지 않는다.
  - 결과적으로 배송은 `PENDING`, 운송장 없음, 주문은 `PREPARING` 그대로다.
- **응답**: 글로벌 핸들러가 `Xpb98Exception`을 받아 `ErrorCode`의 값으로 HTTP **404**, `ErrorResponse{code:"S001", message:"배송 정보를 찾을 수 없습니다.", status:404, path}`를 돌려준다 (`global/exception/Xks43ExceptionHandler.java:459-472`, 코드 정의 `domain/m12/exception/Xpb98ErrorCode.java:12`). 실제 원인(상태 전이 불가)과 다른 "배송 정보 없음" 응답이다.
- 이 주문에 판매 입찰(Xzz58)이 없다면 순서가 바뀌어도 실패한다. `Xzz58QueryService#findByOrderId`는 null을 반환하지 않고 `IllegalArgumentException`을 던지기 때문이다 (`domain/m10/service/query/Xzz58QueryService.java:26-28`). 그래서 `S:117`의 `if (saleBid != null)`은 의미가 없다.
- 즉시 구매 주문(`PENDING_PAYMENT`)에서도 `PENDING_PAYMENT → IN_TRANSIT`은 허용되지 않아 (`OS:24`) 같은 이유로 실패한다.

## 2. 배송 완료 감지

### 2-1. 누가·언제·어떻게
- **누가**: `Xpb98BatchScheduler#scheduleShipmentStatusJob`가 Spring Batch Job `updateShipmentStatusesJob`을 실행한다 (`global/config/Xpb98BatchScheduler.java:19-21,34-40`).
- **주기**: `@Scheduled(cron = "0 0 */6 * * *")`. 매일 00:00, 06:00, 12:00, 18:00 정각, 6시간마다이고 서버 타임존 기준이다 (`Xpb98BatchScheduler.java:34`). 실행마다 timestamp 파라미터로 새 JobInstance를 만든다 (`:37-39`). 예외는 `printStackTrace`만 한다 (`:41-43`).
- **사용자 요청이 아니다.** `/check-status*` API는 요청 시점에 단건만 조회한다.

### 2-2. 대상
- `JpaPagingItemReader`의 쿼리: `SELECT s FROM Xhx14 s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL` (`J:91-96`). 페이지 크기와 청크 크기는 50 (`J:51,94`).
- 상태가 `PENDING`, `SHIPPED`, `DELIVERED`인 배송은 조회되지 않는다. 운송장 등록 후 `IN_TRANSIT`이 된 배송만 대상이다.

### 2-3. 실제 실행되는 처리 코드
- Step은 `chunk(50)` + `faultTolerant().skip(Exception.class).skipLimit(50)`이다 (`J:66-81`).
- 프로세서는 `new Xth19Processor(playwrightBrowserManager(), notificationService, orderService)`이다 (`J:69-73`). **실제 실행되는 코드는 `P#process`(`P:57-141`)다.**
  - Playwright 브라우저(`Xrk74`)로 CJ대한통운 `https://trace.cjlogistics.com/next/tracking.html?wblNo=` 페이지를 연다 (`P:27,83`).
  - `tbody#statusDetail tr`을 기다린 뒤 (`P:87`) 마지막 행의 5번째 td 텍스트를 상태로 읽는다 (`P:181`).
  - `Xmb36Listener`가 Step 전후로 브라우저를 열고 닫는다 (`J:80`, `domain/m12/config/Xmb36Listener.java:15-25`).
- **실행되지 않는 유사 코드**:
  - `J#shipmentItemProcessor` 빈 (`J:104-177`): Step에 연결되지 않는다. `J:69`에서 프로세서를 직접 `new`로 만든다.
  - `J#parseCjLogisticsStatus` (`J:186`): 호출하는 곳이 없다.
  - `S#updateShipmentStatuses` (`S:308-391`): 호출하는 곳이 없다 (전체 소스 grep). 이 메서드는 배송 완료 시 `completeOrder`가 아니라 주문을 직접 `COMPLETED`로 바꾸는 별도 로직이다.
  - `Xxx20`(Playwright 매 호출 기동)은 `/check-status*` API 경로에서만 쓰인다 (`S:477`).

### 2-4. 택배사 상태 문자열 → 내부 상태 (`P:220-226`)
| 택배사 문자열 | 내부 상태 |
|---|---|
| `"배송완료"` (정확히 일치) | `DELIVERED` |
| `"배송출발"` (정확히 일치) | `OUT_FOR_DELIVERY` |
| 그 외 모든 문자열 | `IN_TRANSIT` |

- `"배송출발"`과 `"배송완료"` 정확 일치만 인식한다. 다른 표기는 모두 `IN_TRANSIT`이다.
- 현재 상태와 같으면 아무 것도 하지 않고 반환한다 (`P:101-105`).
- `OUT_FOR_DELIVERY`인 배송이 "그 외"로 판정되면 `IN_TRANSIT`으로 되돌리려 하지만, `OUT_FOR_DELIVERY → IN_TRANSIT` 전이가 없어 `IllegalStateException`이 난다 (`SS:34-40`, `SH:47-55`). 이는 5번 실패 처리로 간다.

## 3. 배송 완료 판정 이후 (`P:107-118`)

순서:
1. **배송(Xhx14)** `IN_TRANSIT/OUT_FOR_DELIVERY → DELIVERED` (`P:112`). 전이는 허용된다 (`SS:16-22,29-33`).
2. `S#completeOrder(orderId)` (`P:116`, 본문 `S:190-229`):
   - 주문 입찰 조회. 없으면 `IllegalArgumentException` (`S:196-197`).
   - **주문(Xdg64)** → `COMPLETED` (`S:204`).
   - `updateSaleStatusToSold` (`S:208`). 판매 입찰이 없으면 여기서 `IAE`가 나고, 판매가 이미 `SOLD`이면 변경 없이 넘어간다 (`S:116-123`, `domain/m10/service/query/Xzz58QueryService.java:26-28`).
   - **구매자 알림**: "[completeOrder] 주문이 완료 처리되었습니다. 주문 ID: …" (`S:211-217`).
   - 예외는 모두 `Xpb98Exception(ORDER_NOT_FOUND_FOR_SHIPMENT)`로 감싸 던진다 (`S:221-227`).
3. `notifyShipmentCompleted(order)` (`P:117`, `domain/m15/service/command/Xkh73CommandService.java:219-234`): **구매자 알림**: "[배송 완료] 상품이 배송 완료되었습니다. 주문 ID: …". 알림 생성 중 예외는 삼킨다.
4. 변경된 배송은 `JpaItemWriter`가 저장한다 (`J:241-246`).

알림 건수 (판매가 이 시점에 `SOLD`로 바뀌는 경우):
- 구매자 2건: `[completeOrder]` 1건 + `[배송 완료]` 1건.
- 판매자 1건: "판매 완료" (`S:132-138`).
- 합계 최대 3건. 판매가 이미 `SOLD`이면 판매자 알림 0건이고 합계 2건이다 (4-(b) 참조).

입찰 상태:
- 배송 완료 경로(`completeOrder`)는 주문 입찰(Xzj27)과 판매 입찰(Xzz58)의 상태를 바꾸지 않는다. 입찰을 `COMPLETED`로 바꾸는 `updateOrderAndSaleBidStatusToCompleted`는 `updateTrackingInfo`(`S:289`)에서만 호출된다.
- 따라서 이 경로의 입찰은 `MATCHED`로 남는다.
- `updateTrackingInfo`가 항상 실패하므로 (1-3) 입찰이 `COMPLETED`가 되는 경로는 사실상 없다. 즉 주문은 `COMPLETED`인데 입찰은 `MATCHED`로 남는다.

## 4. 주문 종류별 차이

배송이 `IN_TRANSIT`+운송장 상태가 되어야 배치 대상이 된다. 둘 다 PATCH 등록이 실패하므로 (1-3), 배치 대상이 되려면 `/check-status` 계열로 운송장을 저장해야 한다 (`S:473`, `SH:41-45`).

### (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문: 끝까지 진행되지 않는다
- 주문은 `PREPARING`이다. 배치에서 `DELIVERED`가 판정되면 `completeOrder`의 `order.updateStatus(COMPLETED)` (`S:204`)에서 `PREPARING → COMPLETED`가 전이표에 없어 (`OS:26`) `Xxc76StatusException`이 난다.
- `S:221-227`이 `Xpb98Exception(ORDER_NOT_FOUND_FOR_SHIPMENT)`로 감싸고 `P:133-141`이 그대로 던진다. Step이 이 건을 skip한다.
- 결과:
  - 주문은 `PREPARING`, 판매와 입찰은 변경 없음.
  - 알림 0건.
  - 배송은 `DELIVERED`가 저장되지 않아 `IN_TRANSIT`으로 남고, 다음 주기(6시간 후)에 같은 방식으로 다시 조회·실패한다.
- `/check-status`로 처리하면 같은 `completeOrder` 실패가 `updateAndCheckShipmentStatus`에서 잡혀 `Xpb98Exception`이 되고, 트랜잭션이 롤백되어 컨트롤러가 오류 상태 코드를 응답한다 (`S:505-515`, `C:80-93`).

### (b) 즉시 구매로 만들어진 주문: 끝까지 진행된다 (판매자 알림 없음)
- 즉시 구매 주문은 판매 입찰(Xzz58)이 주문에 붙고 (`OC:279-280`) 주문 입찰(Xzj27)도 `order`·`sale`과 함께 만들어진다 (`Xzj27CommandService.java:189-206`). 주문 상태는 `PENDING_PAYMENT`다.
- 배송 완료 시 `completeOrder`:
  - 주문 입찰 존재 (`S:196`).
  - `order.updateStatus(COMPLETED)`: `PENDING_PAYMENT → COMPLETED`는 전이표에 있어 성공한다 (`OS:24`).
  - 판매 입찰 조회 성공.
- 판매자 알림은 가지 않는다. 즉시 구매 결제 시점에 `processPayment`가 판매를 이미 `SOLD`로 바꾸고 판매자에게 "구매자가 결제를 완료하였습니다"를 보냈기 때문이다.
  - `OC:305`의 `processPayment`가 `notifyUsersAndUpdateSaleStatus`(`domain/m06/service/command/Xbf54CommandService.java:83,383-421`)를 호출한다.
  - 이때 주문 입찰이 아직 없어 판매 입찰 경로로 가서 판매를 `SOLD`로 만든다 (`:388-406`).
  - 배송 완료 시점에는 `SOLD.canTransitionTo(SOLD)`가 false여서 (`domain/m10/entity/Xgg74Status.java:23`) 판매 변경, 창고 상태 변경, 판매자 알림이 모두 건너뛰어진다 (`S:119`).
- 결과: 배송 `DELIVERED`, 주문 `COMPLETED`, 구매자 알림 2건(`[completeOrder]`, `[배송 완료]`), 판매자 알림 0건. 주문 입찰·판매 입찰은 `MATCHED` 그대로 (3 참조).

### 요약 차이
| | (a) 실배송 일반 구매 입찰 | (b) 즉시 구매 |
|---|---|---|

## 5. 실패 처리 (주기 처리)

- Step이 `faultTolerant().skip(Exception.class).skipLimit(50)`이다 (`J:75-77`). 처리 중 예외가 난 건은 skip되고 `SkipListener`가 로그만 남긴다 (`J:251-287`).
- 실패한 건은 `onSkipInProcess`에서 로그만 남고 write되지 않으므로 배송 상태는 DB에 저장되지 않는다.
  - 프로세서가 메모리에서 바꾼 `DELIVERED`도 버려진다.
  - `completeOrder`가 청크 트랜잭션에 참여했다면 그 변경도 롤백된다.
  - 다음 주기(6시간 후)에 같은 대상으로 다시 조회된다.
- 나머지 건은 계속 처리된다. 한 건이 터지면 청크가 롤백된 뒤, 같은 청크의 다른 아이템은 개별 재처리(스캔)로 이어진다. skip은 최대 50건이고, 이를 넘기면 Step이 실패하며 이후 건은 다음 주기까지 처리되지 않는다.
