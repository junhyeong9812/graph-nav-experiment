# 즉시 구매 처리 흐름 분석

경로 약어: `B` = `src/main/java/com/fream/back`

## 1. 진입 API, 처리 단계, 동기/비동기, 응답 ID

**API**: `POST /order-bids/instant` (구매자 인증 필요)
- 클래스 `@RequestMapping("/order-bids")` — `B/domain/m16/controller/command/Xzj27CommandController.java:22`, 메서드 `@PostMapping("/instant")` — `:89-90`.
- 요청 DTO는 `saleBidId`, `addressId`, `warehouseStorage`, `paymentRequest` — `B/domain/m16/dto/Xpj49RequestDto.java:20-29`.

**처리 단계 (모두 동기, 단일 트랜잭션)**
1. 컨트롤러: 이메일 추출 후 결제 요청의 `userEmail`을 덮어쓰고 `orderId=null`로 초기화 — `Xzj27CommandController.java:92,98,119-122`.
2. `Xzj27CommandService.createInstantOrderBid` (`@Transactional`, `:118-149`):
   - 입력 검증 — `:123`, `:154-167`
   - 구매자 조회 — `:126`
   - 판매 입찰 조회·검증 (`sale` 연결 필수) — `:129`, `:172-184`
   - 주문 생성 위임 — `:133-139`
   - `Xzj27`(주문 입찰) 생성·저장 — `:142`, `:189-207`
3. `Xdg64CommandService.createInstantOrder` (`@Transactional`, `B/domain/m16/service/command/Xdg64CommandService.java:219-319`) 내부 순서:
   1. 배송지 조회 `addressQueryService.getAddress` — `:238`
   2. 주문 `Xdg64` 저장 (`PENDING_PAYMENT`, totalAmount=입찰가) — `:241-247`
   3. `paymentRequest.setOrderId(order.getId())` — `:250`
   4. 주문 항목 생성 — `:255-256`
   5. 배송 정보 생성 (배송지 ID로 조회한 주소 사용) — `:264-271`
   6. 판매 입찰에 주문 연결 + 상태 `MATCHED` + `flush` — `:279-283`
   7. 판매자가 창고 보관인 경우 창고 보관 상태를 `ASSOCIATED_WITH_ORDER`로 변경 — `:291-294`
   8. 결제 처리 `paymentCommandService.processPayment` — `:305`
4. 결제 서비스 `Xbf54CommandService.processPayment` (`:57-107`, 클래스 `@Transactional` `:37`): 결제 유형별 결제 생성 → `notifyUsersAndUpdateSaleStatus`(알림 + 판매 SOLD) — `B/domain/m06/service/command/Xbf54CommandService.java:67-83`.

**동기/비동기**: 완전 동기이다. 즉시 구매 경로에는 Kafka 발행, `@Async`, 이벤트 리스너가 없다.
- Kafka 프로듀서(`Xdg64EventProducer`)는 `/orders/{orderId}/process-payment-shipment` 컨트롤러에서만 주입·사용된다 — `B/domain/m16/controller/command/Xdg64CommandController.java:6,30,42`. 즉시 구매 서비스들은 프로듀서를 쓰지 않는다 (`Xzj27CommandService.java:29-33`, `Xdg64CommandService.java:38-46`).
- 외부 호출(PortOne 카드 결제 REST)도 같은 스레드에서 동기 호출한다 — `B/domain/m06/p05/Xxv33ApiClient.java:266`.

**응답 ID**: 변수 이름은 `orderId`이고 응답 메시지도 주문처럼 보이지만, 실제 값은 **주문 입찰(`Xzj27`, order-bid)의 ID**이다. `createInstantOrderBid`는 `Xzj27`을 반환하고(`Xzj27CommandService.java:119,142-144`), 컨트롤러는 그 `.getId()`를 `orderId`에 담아 `ResponseDto.success(orderId, "즉시 구매가 성공적으로 처리되었습니다.")`로 돌려준다 — `Xzj27CommandController.java:101-109`. 주문(`Xdg64`)의 ID는 `order.getId()`로 별도이며 응답에 포함되지 않는다.

## 3. 결제 수단별 결과, 끝까지 성공하는가, 카드 실패 시

결제 유형 분기 — `Xbf54CommandService.java:67-80` (유형은 DTO 서브타입으로 결정, `B/domain/m06/dto/Xbf54RequestDto.java:20-25,74-87`).

| 수단 | 결제 엔티티 상태 | 근거 |
|---|---|---|
| 카드 (`CARD`) | PortOne 응답 `status == "success"`일 때만 `PAID` + `isSuccess=true`. 아니면 기본값 `PENDING` 유지 | `Xbf54CommandService.java:203-206`, 기본값 `B/domain/m06/entity/Xbf54.java:44` |
| 계좌이체 (`ACCOUNT`) | 은행명 검증 후 무조건 `PENDING` (입금 확인 로직 없음) | `Xbf54CommandService.java:244,260` |
| 일반 (`GENERAL`) | `impUid`만 있으면 서버 검증 없이 즉시 `PAID` + success | `Xbf54CommandService.java:297-314` |

**즉시 구매는 어떤 수단이든 "끝까지" 간다**: 결제 상태가 `PENDING`이어도 결제 후 단계(알림, 판매 `SOLD`, 주문 입찰 생성, 응답 "성공")가 그대로 진행된다. `notifyUsersAndUpdateSaleStatus`는 결제 상태를 확인하지 않는다 — `Xbf54CommandService.java:83,383-426`. 따라서 계좌이체는 입금 전인데도 구매자·판매자에게 "결제가 완료되었습니다" 알림이 가고 판매는 `SOLD`가 된다.

**카드 결제 실패 시** (두 경우가 다르다)
- (a) PortOne HTTP 응답이 200이 아니거나 응답 `code != 0`: `Xdf64Exception` 발생 — `Xxv33ApiClient.java:270-275`. (통신 오류 `RestClientException`은 `Xbf54ApiException`으로 바뀌어 `@Retryable` 3회 재시도 — `:69-72`/`:224-228`, `:288-290`.) 예외는 `processPayment`(`Xbf54CommandService.java:95-100`) → `createInstantOrder`의 `catch`에서 `Xqj91Exception`으로 감싸져 재던져진다(`Xdg64CommandService.java:304-309`) → `createInstantOrderBid`가 다시 던진다(`Xzj27CommandService.java:145-147,212-218`). 모두 한 트랜잭션이므로 **주문·주문 항목·배송·판매 입찰 `MATCHED`·창고 상태 변경이 전부 롤백**되고 클라이언트는 에러 응답을 받는다.
- (b) PortOne이 `code == 0`이면서 `response.status`가 `"success"`가 아닌 경우(예: `failed`): 위 (a)의 검사는 `code`만 보므로 예외가 나지 않는다. 카드 결제는 `PENDING`, `isSuccess=false`로 저장되고(`Xbf54CommandService.java:187-208`, `Xxv33ApiClient.java:270`), 이후 흐름은 정상 성공과 동일하게 진행되어 알림 발송, 판매 `SOLD`, 응답 "성공적으로 처리되었습니다"가 나간다. **결제가 실패했는데도 구매가 성공 처리되는 결함**이다.

## 4. 알림 대상, 시점, 방식

- **수신자**: 구매자(`order.getUser()`)에게 "결제가 완료되었습니다. 주문 ID: …", 판매자(`sale.getSeller()`)에게 "구매자가 결제를 완료하였습니다. 판매 ID: …" — `Xbf54CommandService.java:436-455`. 카테고리 `SHOPPING`, 타입 `BID`.
- **시점**: 결제 엔티티 저장 직후, `processPayment` 안에서, 판매 `SOLD` 변경 직전 — `Xbf54CommandService.java:83,403-404,416,419`. 즉 주문 입찰(`Xzj27`) 생성 이전이며 요청 트랜잭션이 커밋되기 전이다.
  - 즉시 구매에서는 `order.getOrderBid()`가 아직 `null`이므로(주문 입찰은 이후에 생성됨, `Xzj27CommandService.java:142`) `saleBidQueryService.findByOrderId`로 판매 입찰→판매를 찾는 분기를 탄다 — `Xbf54CommandService.java:388-407`. 이 값은 앞서 `flush`된 `saleBid.assignOrder`(`Xdg64CommandService.java:279-283`) 덕에 조회된다.
- **방식**: 비동기가 아니라 같은 요청 스레드·같은 트랜잭션 안에서 처리한다.
  1. `Xkh73` 알림을 DB에 저장 — `Xkh73CommandService.java:52-53`
  2. 수신자가 Redis에 `WebSocket:Xrd81:{email}` 키가 있을 때(웹소켓 접속 중)만 STOMP `/queue/notifications`(`convertAndSendToUser`)로 실시간 전송. 접속해 있지 않으면 저장만 한다 — `Xkh73CommandService.java:37-38,154-173`.
  - Kafka `notification-topic`은 `/process-payment-shipment` 경로의 컨슈머에서만 쓰이며(`B/domain/m16/service/kafka/Xdg64EventConsumer.java:318,364`) 즉시 구매 경로에서는 사용되지 않는다.
- 알림 오류는 삼켜진다: `sendNotifications`(`:457-461`)와 `notifyUsersAndUpdateSaleStatus`(`:421-425`)가 예외를 로그만 남기고 무시한다. 단, 알림 서비스가 `@Transactional`이라(`Xkh73CommandService.java:27`) 내부에서 예외가 나가면 트랜잭션이 rollback-only로 표시되어 커밋 시점에 실패할 수 있다.

## 5. 최종 주문 상태와 "창고 보관" 선택의 영향

**최종 주문 상태: `PENDING_PAYMENT`.**
- 즉시 구매 경로에서 주문 상태를 바꾸는 코드는 없다. 생성 시 `PENDING_PAYMENT`로 저장(`Xdg64CommandService.java:244`)된 뒤 `createInstantOrder`·`processPayment`·`createInstantOrderBid` 어디에서도 `order.updateStatus(...)`를 호출하지 않는다 (`Xdg64CommandService.java:219-319`, `Xbf54CommandService.java:57-107`, `Xzj27CommandService.java:119-207`).
- `PAYMENT_COMPLETED`/`PREPARING`/`IN_WAREHOUSE`/`COMPLETED`로의 전환은 별도 API `POST /orders/{orderId}/process-payment-shipment` 경로(`processPaymentAndShipment`, `Xdg64CommandService.java:111-202`)에만 있으며, 즉시 구매에서는 호출되지 않는다.
- 이름·응답 메시지("즉시 구매가 성공적으로 처리되었습니다")와 달리 주문은 결제 완료 상태가 아니다. 결제가 `PAID`인 경우에도 마찬가지이다. 주문의 결제 연결(`order.assignPayment`)도 호출되지 않는다. `createInstantOrder`는 `processPayment`의 반환값을 버린다 — `Xdg64CommandService.java:305`. 결제 쪽 FK(`payment.order_id`)로만 연결된다 — `Xbf54.java:47-50`.

**구매자가 "창고 보관(`warehouseStorage=true`)"을 선택한 경우: 아무것도 달라지지 않는다.**
- 컨트롤러는 값을 로그에만 사용하고(`Xzj27CommandController.java:94-95`) 서비스에 전달한다(`:105`). `createInstantOrderBid`도 `createInstantOrder`로 전달하지만(`Xzj27CommandService.java:119-120,133-139`), `createInstantOrder` 본문에서 `isWarehouseStorage` 파라미터는 **한 번도 읽히지 않는다** — `Xdg64CommandService.java:220-319`.
- 구매자용 창고 보관 엔티티 `Xnn94` 생성(`warehouseStorageCommandService.createOrderStorage`)과 주문 상태 `IN_WAREHOUSE`→`COMPLETED` 전환은 `processPaymentAndShipment`에만 있고 (`Xdg64CommandService.java:163-172`) 즉시 구매에는 없다.
- 즉시 구매에서 창고와 관련된 유일한 동작은 **판매자의** 판매가 창고 보관(`sale.isWarehouseStorage()`)일 때 기존 창고 보관 건을 `ASSOCIATED_WITH_ORDER`로 바꾸는 것이다 — `Xdg64CommandService.java:291-294`. 이는 구매자의 선택과 무관하다.
