# 즉시 구매 처리 흐름

경로 약어: `m16` = `src/main/java/com/fream/back/domain/m16`, `m06` = `.../domain/m06`, `m10` = `.../domain/m10`, `m15` = `.../domain/m15`, `m07` = `.../domain/m07`, `m12` = `.../domain/m12`

## 1. 진입 API · 처리 단계 · 동기/비동기 · 응답 ID

- 진입점은 `POST /order-bids/instant`이다. 클래스는 `@RequestMapping("/order-bids")` (`m16/controller/command/Xzj27CommandController.java:22`), 메서드는 `createInstantOrderBid` (`Xzj27CommandController.java:89-90`).
- 요청 DTO `Xpj49RequestDto`는 `saleBidId`, `addressId`, `warehouseStorage`, `paymentRequest`를 가진다 (`m16/dto/Xpj49RequestDto.java`). `paymentRequest`는 `paymentType`(CARD/ACCOUNT/GENERAL)으로 하위 DTO가 결정되는 다형 DTO다 (`m06/dto/Xbf54RequestDto.java:20-24`).
- 처리 단계 (모두 한 요청 스레드 안에서 순서대로 실행):
  1. 컨트롤러가 이메일을 꺼내고 (`Xzj27CommandController.java:92`), `enrichPaymentRequest`로 결제 요청의 `userEmail`을 로그인 사용자로 덮어쓰고 `orderId`를 null로 비운다 (`Xzj27CommandController.java:98`, `119-123`).
  2. `Xzj27CommandService#createInstantOrderBid` (`m16/service/command/Xzj27CommandService.java:118-149`)
     - 입력 검증 (`:123`, `154-167`)
     - 구매자 조회 (`:126`)
     - 판매 입찰 조회와 sale 연결 확인 (`:129`, `172-184`)
     - `Xdg64CommandService#createInstantOrder` 호출 (`:133`)
     - 주문 입찰 `Xzj27` 생성·저장 (`:142`, `189-207`)
  3. `Xdg64CommandService#createInstantOrder` (`m16/service/command/Xdg64CommandService.java:219-319`)
     - 배송지 조회 (`:238`)
     - 주문 저장 (`:241-247`)
     - 결제 요청에 orderId 세팅 (`:250`)
     - 주문 항목 생성 (`:255-256`)
     - 배송 정보 생성 (`:264-271`)
     - 판매 입찰 매칭 + flush (`:279-283`)
     - 창고 상태 갱신 (`:290-301`)
     - 결제 처리 (`:305`)
  4. `Xbf54CommandService#processPayment` (`m06/service/command/Xbf54CommandService.java:57-107`): 결제 수단별 결제 엔티티를 만들고, 이어서 알림과 sale 상태 갱신 (`:83`).
- 동기 처리다. `/order-bids/instant` 경로에는 Kafka 발행이나 `@Async`가 없다. 결제 대행사(PortOne) 호출도 동기 `RestTemplate.exchange`다 (`m06/p05/Xxv33ApiClient.java:266`). 서비스 메서드는 `@Transactional`이라 한 트랜잭션이다 (`Xzj27CommandService.java:118`, `Xdg64CommandService.java:219`).
- Kafka 비동기 처리는 별도 엔드포인트 `POST /orders/{orderId}/process-payment-shipment`의 경로이며 즉시 구매 경로가 아니다.
- 응답으로 돌려주는 ID는 **주문 입찰(Xzj27, order_bid)의 ID**다. 주문(Xdg64)의 ID가 아니다.
  - 컨트롤러는 변수 이름을 `orderId`로 두었지만, 실제 값은 `createInstantOrderBid(...).getId()`다 (`Xzj27CommandController.java:101-107`).
  - 그 서비스 메서드의 반환 타입이 `Xzj27`이고 (`Xzj27CommandService.java:119`), 반환값은 2번 단계 마지막(주문 입찰 저장)에서 저장한 주문 입찰이다 (`:142-144`, `206`).
  - 메시지는 "즉시 구매가 성공적으로 처리되었습니다."이다 (`Xzj27CommandController.java:109`).

## 2. 새로 만들어지는 엔티티와 상태 변화 순서

각 단계 직후의 상태 값은 다음과 같다. 모든 단계가 한 트랜잭션이다.

| 순서 | 동작 | 엔티티 / 상태 | 근거 |
|---|---|---|---|
| 0 | 요청 시점의 판매 입찰 `Xzz58` | status는 기본 `PENDING`, sale 연결됨 | `m10/entity/Xzz58.java:35-37` |
| 1 | 주문 `Xdg64` 생성·저장 | `totalAmount = saleBid.bidPrice`, status = `PENDING_PAYMENT` (discount/usedPoints는 0) | `Xdg64CommandService.java:241-247` |
| 2 | 주문 항목 `Xhm58` 생성, 주문에 추가 | 주문 항목 신규 | `Xdg64CommandService.java:255-256` |
| 3 | 배송 `Xhx14` 생성 (배송지 DTO 값 사용) | status = `Xpb98Status.PENDING`, 주문에 연결 | `m12/service/command/Xhx14CommandService.java:55-75`, `Xdg64CommandService.java:264-271` |
| 4 | 판매 입찰 매칭 | `saleBid.assignOrder(order)` → order 연결, status `MATCHED`. 이어서 `updateStatus(MATCHED)`로 한 번 더 MATCHED 지정 후 `flush` | `m10/entity/Xzz58.java:58-61`, `Xdg64CommandService.java:279-283` |
| 5 | 창고 보관 판매이면 창고 상태 갱신 | `sale.isWarehouseStorage()`가 true이면 `Xnn94`(창고 보관)의 상태를 `ASSOCIATED_WITH_ORDER`로 변경 | `Xdg64CommandService.java:291-294`, `m07/service/command/Xnn94CommandService.java:117-133` |
| 6 | 결제 `Xbf54` 하위 엔티티 생성 | 수단별 값은 3번 항목 참조 | `Xbf54CommandService.java:67-80` |
| 7 | 판매 `Xgg74` 상태 갱신 | status = `SOLD` (전이 검증 없이 대입) | `Xbf54CommandService.java:403-404`, `m10/entity/Xgg74.java:73-75` |
| 8 | 주문 입찰 `Xzj27` 생성·저장 | status = `MATCHED`, `isInstantPurchase = true`, order·sale 연결 | `Xzj27CommandService.java:192-206`, `m16/entity/Xzj27.java:60-82`, `97-99` |

- 7번의 결제 후처리 분기는 다음과 같다.
  - 이 시점 `order.getOrderBid()`는 null이다. 주문 입찰은 8번에서 만들어진다.
  - 그래서 `saleBidQueryService.findByOrderId`로 4번에서 연결한 판매 입찰을 찾아 그 sale을 쓴다 (`Xbf54CommandService.java:388-404`).
  - `findByOrderId`는 못 찾으면 null이 아니라 `IllegalArgumentException`을 던진다 (`m10/service/query/Xzz58QueryService.java:26-29`). 이 예외는 `notifyUsersAndUpdateSaleStatus`의 catch에서 삼켜진다 (`:421-425`).
- 주문 상태는 이 경로에서 `PENDING_PAYMENT` 이후로 바뀌지 않는다. 결제 완료 시점에도 `Xdg64.updateStatus`를 호출하지 않는다 (5번 참조).
- 결제 엔티티 `Xbf54`의 `assignOrder`는 `sale = null`로 비운다 (`m06/entity/Xbf54.java:47-50`).
- 결제 요청 DTO의 금액(`paidAmount`)은 클라이언트 값이다. 판매 입찰 가격과 대조하는 코드는 없다. `paidAmount <= 0`만 검사한다 (`Xbf54CommandService.java:142-145`).
- 판매 입찰이 이미 매칭되었는지(`MATCHED`) 확인하는 검증은 없다 (`Xzj27CommandService.java:172-184`).

## 3. 결제 수단별 결과 · 성공 여부 · 카드 실패 시

`processPayment`가 `getResolvedPaymentType()`으로 분기한다 (`Xbf54CommandService.java:67-80`, `m06/dto/Xbf54RequestDto.java:74-87`).

| 수단 | 처리 | 저장되는 결제 상태 | 근거 |
|---|---|---|---|
| CARD | 저장된 결제정보 조회 후 PortOne `/subscribe/payments/onetime` 동기 호출. 응답 `status`가 문자열 `"success"`이면 `PAID`와 `isSuccess=true`로 갱신 | `"success"`이면 `PAID`, 아니면 기본값 `PENDING` 그대로 저장 | `Xbf54CommandService.java:157-208`, `m06/p05/Xxv33ApiClient.java:229-285` |
| ACCOUNT (계좌이체) | 은행명만 검증하고 외부 호출 없음. 명시적으로 `PENDING` | `PENDING`. `isSuccess`는 기본값 false | `Xbf54CommandService.java:236-262`, `m06/entity/Xbf54.java:38-44` |
| GENERAL (일반 결제) | `impUid`가 비어 있지 않은지만 확인. 외부 검증·호출 없이 바로 성공 처리 | `PAID`, `isSuccess=true` | `Xbf54CommandService.java:290-316` |

- 즉시 구매가 끝까지 성공하는지:
  - 세 수단 모두 결제 엔티티를 저장하고 예외 없이 끝나면, 결제 상태가 `PENDING`이어도 후속 단계를 그대로 진행한다. 즉시 구매는 응답상 "성공"으로 끝난다.
  - 구체적으로 판매 `SOLD`, 알림 2건, 주문 입찰 `MATCHED`까지 모두 수행된다 (`Xbf54CommandService.java:83`, `Xzj27CommandService.java:142`).
  - 계좌이체는 입금 확인 단계가 코드에 없다. `PENDING` 상태로 저장된 채 판매는 즉시 `SOLD`가 된다.
  - 카드 결제도 응답 `status`가 `"success"`가 아니면(PortOne 정상 응답은 보통 `paid`) 결제는 `PENDING`/`isSuccess=false`로 남는다. 그런데도 같은 후속 단계(SOLD, 알림)가 진행된다. 결제 완료 여부를 판단하는 분기가 없다.
- 결제 대행사가 카드 결제를 실패로 응답하면:
  - HTTP 상태가 200이 아니거나 응답 `code`가 0이 아니면 `Xdf64Exception("카드 결제 요청 실패: ...")`을 던진다 (`Xxv33ApiClient.java:270-275`).
  - 이 예외는 `createCardPayment` → `processPayment`에서 그대로 또는 래핑되어 올라온다 (`Xbf54CommandService.java:89-100`, `218-224`).
  - `createInstantOrder`가 `Xqj91Exception("결제 처리 중 오류가 발생했습니다")`로 감싸 던진다 (`Xdg64CommandService.java:305-309`). `Xqj91Exception`은 `Xdg64Exception`의 하위 클래스라 바깥 catch에서 그대로 다시 던져진다 (`Xdg64CommandService.java:312-314`, `m16/exception/Xqj91Exception.java`). `Xzj27CommandService`도 그대로 재던진다 (`Xzj27CommandService.java:212-215`).
  - 결과적으로 요청 전체 트랜잭션이 롤백된다. 주문, 주문 항목, 배송, 판매 입찰 `MATCHED`, 창고 상태 변경, 결제 엔티티가 모두 저장되지 않는다. 주문 입찰도 만들어지지 않고 알림도 나가지 않는다. 알림은 결제 성공 이후 단계다.
  - 결제 대행사 통신 오류(`RestClientException`)는 `Xbf54ApiException`이 되어 `@Retryable`로 최대 3회 재시도된다. 이는 토큰 발급 메서드에 대한 설정이다 (`Xxv33ApiClient.java:69-73`, `288-290`).
  - 다만 대행사가 HTTP 200과 `code: 0`을 주면서 실제 결제 상태만 실패(`failed`)로 표시한 경우에는 위 예외 경로를 타지 않는다. 이 경우 `status != "success"`이므로 결제가 `PENDING`으로 저장되고 흐름이 계속된다. 위에서 말한 "성공처럼 끝남"에 해당한다.

## 4. 알림: 수신자 · 시점 · 전달 방식

- 수신자는 구매자와 판매자 두 명이다 (`m06/service/command/Xbf54CommandService.java:434-456`).
  - 구매자: "결제가 완료되었습니다. 주문 ID: {orderId}" (`:438-443`)
  - 판매자(`sale.getSeller()`): "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}" (`:447-455`)
  - 둘 다 카테고리 `Xzv64.SHOPPING`, 타입 `Xkh73Type.BID`.
- 시점: 결제 엔티티 저장 직후, 같은 요청 스레드·같은 트랜잭션 안에서 `sale.updateStatus(SOLD)` 직전에 보낸다 (`Xbf54CommandService.java:83`, `403-404`). 응답을 돌려주기 전에 전달된다.
- 방식:
  - `Xkh73CommandService#createNotification`이 알림 엔티티를 DB에 저장한다 (`m15/service/command/Xkh73CommandService.java:44-53`).
  - 이어서 `sendRealTimeNotification`이 Redis 키 `WebSocket:Xrd81:{email}`가 존재하면(웹소켓 접속 중이면) `messagingTemplate.convertAndSendToUser`로 `/queue/notifications`에 STOMP 푸시한다 (`Xkh73CommandService.java:37-39`, `303-313`). 접속 중이 아니면 DB 저장만 한다 (`:320-322`).
  - Kafka `notification-topic`은 이 경로에서 쓰이지 않는다. 그 토픽은 비동기 주문 처리 컨슈머에서만 발행된다.
- 알림 실패는 삼켜진다 (`Xbf54CommandService.java:457-461`, `421-425`). 알림이 실패해도 즉시 구매는 계속된다.
- 판매자 알림은 `Xgg74CommandService`의 판매 생성 알림과는 별개다.

## 5. 최종 주문 상태 · 창고 보관 선택 시 차이

- 처리 종료 시점의 주문 상태는 **`PENDING_PAYMENT`**다.
  - 주문은 `PENDING_PAYMENT`로 생성되고 (`Xdg64CommandService.java:244`), `createInstantOrder` 안에서 `updateStatus`를 호출하지 않는다 (`:219-319`).
  - 결제 서비스도 주문 상태를 바꾸지 않는다 (`Xbf54CommandService.java:57-107`, `383-426`).
  - `PAYMENT_COMPLETED`/`PREPARING`/`COMPLETED`로의 전환은 `processPaymentAndShipment`(`Xdg64CommandService.java:163-177`)와 Kafka 컨슈머(`m16/service/kafka/Xdg64EventConsumer.java:192-217`)에만 있고, 즉시 구매 경로에서는 호출되지 않는다.
  - 즉 "결제 완료"는 결제 엔티티 상태(카드 성공 시 `PAID`, 계좌이체는 `PENDING`)와 판매(`SOLD`), 판매 입찰·주문 입찰(`MATCHED`)에만 반영된다.
- 구매자가 `warehouseStorage=true`를 선택한 경우:
  - 컨트롤러가 이 값을 로그에 남기고 서비스에 넘기지만 (`Xzj27CommandController.java:94-95`, `104`), `createInstantOrder`는 `isWarehouseStorage` 인자를 읽지 않는다 (`Xdg64CommandService.java:220-221`, 이후 본문에서 참조 없음).
  - 창고 관련 분기는 **판매 쪽** `sale.isWarehouseStorage()`로만 결정된다 (`Xdg64CommandService.java:291-294`). 구매자 요청 값이 `true`든 `false`든 결과는 같다.
  - 구매자 측 창고 보관 엔티티(`createOrderStorage`, 주문 `IN_WAREHOUSE`/`COMPLETED` 전환)는 즉시 구매 경로에서 만들어지지 않는다. 그런 처리는 `processPaymentAndShipment`(`Xdg64CommandService.java:163-172`)에만 있다.
  - 따라서 창고 보관을 선택해도 주문 상태는 `PENDING_PAYMENT` 그대로이고, 변하는 것은 판매자가 창고 보관으로 올린 건에서 기존 `Xnn94` 상태가 `ASSOCIATED_WITH_ORDER`로 바뀌는 것뿐이다. 이는 구매자 선택과 무관하다.
