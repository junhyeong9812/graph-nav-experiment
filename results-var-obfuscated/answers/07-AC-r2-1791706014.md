# 즉시 구매 처리 분석

경로 약기: `D=src/main/java/com/fream/back/domain`

## 1. 진입 API, 처리 단계, 동기/비동기, 응답 ID

**진입점**: `POST /order-bids/instant` → `Xzj27CommandController#createInstantOrderBid`
(`D/m16/controller/command/Xzj27CommandController.java:22`(base path), `:89-110`). 요청 DTO는 `Xpj49RequestDto`(saleBidId, addressId, warehouseStorage, paymentRequest — `D/m16/dto/Xpj49RequestDto.java:20-29`).

처리 단계 (모두 한 요청 스레드, 한 `@Transactional` 안):
1. 컨트롤러가 SecurityContext에서 이메일을 꺼내고(`Xzj27CommandController.java:92`), 결제 요청에 `userEmail=이메일`, `orderId=null`을 채운다(`:98`, `:119-123`).
2. `Xzj27CommandService#createInstantOrderBid`(`D/m16/service/command/Xzj27CommandService.java:118-149`): 입력 검증(`:123`, `:154-167`) → 구매자 조회(`:126`) → 판매 입찰 `Xzz58` 조회·검증(`:129`, `:172-184`; 판매 입찰의 상태/이미 매칭 여부는 검사하지 않음).
3. `Xdg64CommandService#createInstantOrder`(`D/m16/service/command/Xdg64CommandService.java:219-319`): 배송지 조회(`:238`) → 주문 저장(`:241-247`) → 결제요청에 주문 ID 세팅(`:250`) → 주문 항목(`:255`) → 배송 정보(`:264-271`) → 판매 입찰 매칭(`:279-283`) → 창고 상태(`:291-293`) → 결제(`:305`).
4. 결제 안에서 알림 + 판매 SOLD 처리(`D/m06/service/command/Xbf54CommandService.java:83`, `:383-426`).
5. 마지막에 `Xzj27`(주문 입찰) 저장(`Xzj27CommandService.java:142`, `:189-207`).

**동기/비동기**: 완전 동기. 이 경로에는 Kafka 발행이 없다. Kafka(`Xdg64EventProducer`/`Xdg64EventConsumer`)는 `/orders/{orderId}/process-payment-shipment` 경로에서만 쓰이며(`nav/m16.md` 엔드포인트 표), 즉시 구매 호출 사슬(`Xzj27CommandService → Xdg64CommandService → Xbf54CommandService`)에는 등장하지 않는다. PG(PortOne) 호출도 `RestTemplate.exchange` 동기 호출(`D/m06/p05/Xxv33ApiClient.java:266`).

**응답 ID**: 컨트롤러 변수명은 `orderId`이지만 `createInstantOrderBid(...)`의 반환값은 `Xzj27`(주문 입찰)이므로 `.getId()`는 **주문 입찰(Xzj27)의 ID**이지 주문(Xdg64) ID가 아니다(`Xzj27CommandController.java:101-107`, 반환 타입 `Xzj27CommandService.java:119`). 메시지는 "즉시 구매가 성공적으로 처리되었습니다."(`:109`).

| 2 | `Xhm58` 주문 항목 생성 | — | `:255-256` |

| 4 | 판매 입찰 `Xzz58.assignOrder(order)` (내부에서 MATCHED), 이어서 `updateStatus(MATCHED)` + `flush` | 판매 입찰 `MATCHED` (기존 `PENDING`→`MATCHED`) | `Xdg64CommandService.java:279-283`, `D/m10/entity/Xzz58.java:58-61,66-68` |

## 3. 결제 수단별 결과, 끝까지 성공하는가, PG 카드 실패 시

분기는 `processPayment`의 `switch (getResolvedPaymentType())`(`Xbf54CommandService.java:67-80`). 공통 검증: 주문 ID·이메일 일치, 금액>0(`:117-146`).

| 수단 | 처리 | 결제 상태 | 근거 |
|---|---|---|---|
| CARD | 저장된 결제정보 조회 → PortOne 카드 결제 호출 → 응답의 `status`가 문자열 `"success"`일 때만 `PAID`+성공 처리, 아니면 기본값 유지 | `PAID` (조건 충족 시) / 아니면 `PENDING`(엔티티 기본값, `isSuccess=false`) | `Xbf54CommandService.java:157-208`, 기본값 `D/m06/entity/Xbf54.java:39,44` |
| ACCOUNT | 은행명 검증 후 PG 호출 없이 저장 | `PENDING` (이후 확정 로직은 이 경로에 없음) | `Xbf54CommandService.java:236-262` |
| GENERAL | `impUid`만 있으면 PG 검증 없이 성공 처리 | `PAID`, `isSuccess=true` | `Xbf54CommandService.java:290-316` |

- 카드의 `"success"` 비교는 코드상 그렇게 되어 있다(`:203`). PortOne 응답 `status`가 다른 값(예: `paid`)이면 PG 승인이 났어도 결제는 `PENDING`으로 남는다(PG 실응답 값은 코드에서 확인 불가, 코드가 비교하는 값만 확인).
- 결제 방식과 무관하게, 예외 없이 `processPayment`가 끝나면 `notifyUsersAndUpdateSaleStatus`가 실행되어(`:83`) 알림("결제가 완료되었습니다")과 판매 `SOLD`가 일어난다. 즉 **계좌이체(PENDING)이거나 카드가 PENDING이어도 "결제 완료" 알림과 SOLD가 나간다.**
- **끝까지 성공하는가**: 호출은 HTTP 200으로 끝나지만, 주문은 `PENDING_PAYMENT`에서 더 진행되지 않고, 배송 생성·창고 입고 등 후속 단계도 이 경로에서 일어나지 않는다(5번 답). "결제 완료→준비→..." 전이는 `processPaymentAndShipment`/Kafka 소비자 경로에만 있다(`Xdg64CommandService.java:165-177`, `D/m16/service/kafka/Xdg64EventConsumer.java:192-217`).
- **PG가 카드 결제를 실패로 응답하면**: `status != 200` 또는 `code != 0`이면 `Xdf64Exception("카드 결제 요청 실패: ...")`을 던진다(`Xxv33ApiClient.java:270-275`; `Xdf64Exception`은 `Xbf54Exception` 하위, `D/m06/exception/Xdf64Exception.java:6`). 이 예외는 `createCardPayment`에서 그대로 재전파(`Xbf54CommandService.java:180-181,218-219`) → `processPayment`에서 재전파(`:89-94`) → `createInstantOrder`가 `Xqj91Exception`("결제 처리 중 오류")으로 감싸 던진다(`Xdg64CommandService.java:304-309`, `Xqj91Exception.java:6,12`) → `Xdg64Exception`이므로 그대로 상위로(`:312-314`, `Xzj27CommandService.java:145-147,212-215`). 모두 RuntimeException(`D/../global/exception/Xks43Exception.java:10`)이라 바깥 `@Transactional`이 **전체 롤백**: 주문, 주문 항목, 배송, 판매 입찰 MATCHED, 창고 상태 변경, `Xzj27`이 저장되지 않는다. 이 시점은 결제 저장·알림·SOLD 이전이라 알림도 없다. 클라이언트는 `Xks43ExceptionHandler`에 의해 `ORD005 "주문 결제 처리에 실패했습니다."` HTTP 500을 받는다(`D/m16/exception/Xdg64ErrorCode.java:44`, `src/main/java/com/fream/back/global/exception/Xks43ExceptionHandler.java:49-61`). `@Retryable`이 `Xxv33ApiClient` 메서드에 붙어 있으나(`:224-228`) 대상이 `Xbf54ApiException`뿐이고(실패 응답은 `Xdf64Exception`), 코드베이스에 `@EnableRetry`가 없어 재시도는 일어나지 않는다.
- (참고) 통신 오류(RestClientException)는 `Xbf54ApiException`이 되어 같은 경로로 롤백된다(`Xxv33ApiClient.java:288-290`, `Xbf54CommandService.java:183`).

## 4. 알림 대상과 전달 방식

- 수신자: **구매자**("결제가 완료되었습니다. 주문 ID: …")와 **판매자**("구매자가 결제를 완료하였습니다. 판매 ID: …"). 카테고리 `SHOPPING`, 타입 `BID`(`Xbf54CommandService.java:434-456`). 판매자는 `sale.getSeller()`(`:447`).
- 시점: 결제 엔티티 저장 직후(결제 수단 분기 다음), 판매 SOLD 처리 직전, 같은 요청·같은 트랜잭션 안(`:83`, `:403-404`). 주문 입찰 저장보다 앞선다.
- 방식: `Xkh73CommandService#createNotification`이 DB에 알림을 저장하고(`D/m15/service/command/Xkh73CommandService.java:52-54`), 사용자의 Redis 키(`WebSocket:Xrd81:<email>`)가 있으면 WebSocket `/queue/notifications`로 사용자에게 즉시 푸시한다(`:37-38,57`, `:303-313`). 연결이 없으면 저장만 된다(`:320-322`). Kafka `notification-topic`이 아니다.
- 알림 전송/판매 상태 갱신 오류는 로그만 남기고 삼킨다(`Xbf54CommandService.java:457-461`, `:421-425`).
- 푸시는 커밋 전에 일어나므로, 이후 단계(`Xzj27` 저장 등)에서 실패해 롤백되어도 이미 보낸 WebSocket 알림은 취소되지 않는다(코드 순서에서 도출).

## 5. 주문 최종 상태와 창고 보관 선택 시 차이

- **주문 최종 상태: `PENDING_PAYMENT`.** `createInstantOrder`는 `PENDING_PAYMENT`로 생성(`Xdg64CommandService.java:244`)하고 이후 `order.updateStatus`를 호출하지 않는다(해당 메서드의 `updateStatus` 호출은 `processPaymentAndShipment`에만 있음, `:165-176`). 결제·알림·Xzj27 생성 어디에서도 주문 상태를 바꾸지 않는다(`Xbf54CommandService.java` 전체에 주문 상태 변경 없음, `Xzj27CommandService.java:189-207`). 결제가 `PAID`여도 주문은 `PENDING_PAYMENT`다. 주석/응답 메시지("즉시 구매가 성공적으로 처리")와 달리 실제 상태는 결제 완료로도 승격되지 않는다.
- 같이 남는 최종 상태: 판매 입찰 `MATCHED`, 판매 `SOLD`, 주문 입찰 `MATCHED`, 배송 `PENDING`, 결제 `PAID`/`PENDING`(3번 답).
- **구매자의 "창고 보관" 선택은 효과가 없다.** `warehouseStorage`는 컨트롤러 로그와 인자 전달에만 쓰이고(`Xzj27CommandController.java:94-95,104`), `createInstantOrder`의 `isWarehouseStorage` 파라미터는 메서드 본문에서 한 번도 참조되지 않는다(`Xdg64CommandService.java:220-319`). 창고 입고용 `createOrderStorage`/`IN_WAREHOUSE`/`COMPLETED` 전이는 `processPaymentAndShipment`에만 있다(`:163-172`).
- 창고와 관련해 실제로 달라지는 것은 구매자 선택이 아니라 **판매(Xgg74) 쪽 플래그**다: `sale.isWarehouseStorage()`가 true이면 기존 창고 보관 건을 `ASSOCIATED_WITH_ORDER`로 바꾼다(`Xdg64CommandService.java:291-293`). 이 경우 창고 보관 건이 없거나 전이가 불가하면 `Xdx92Exception`으로 전체 롤백(`:295-301`).
