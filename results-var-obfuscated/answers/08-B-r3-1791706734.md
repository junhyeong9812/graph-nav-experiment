# 구매자 배송: 운송장 등록 → 배송 완료

경로 약어: `B = src/main/java/com/fream/back`. 클래스명이 난독화되어 있다. 배송=`Xhx14`(order_shipment), 주문=`Xdg64`, 주문입찰=`Xzj27`, 판매입찰=`Xzz58`, 판매=`Xgg74`, 배송상태=`Xpb98Status`, 주문상태=`Xdg64Status`.

## 요약

- 운송장 등록 API(`PATCH /shipments/order/{id}/status`)는 주문을 `IN_TRANSIT`으로 바꾸려 한다. 그런데 `IN_TRANSIT`으로 갈 수 있는 유일한 선행 상태 `SHIPMENT_STARTED`를 세팅하는 코드가 어디에도 없다. 그래서 정상 주문에서는 항상 실패하고 전체가 롤백된다.
- 배송 완료 감지는 6시간마다 도는 Spring Batch 잡이다. 실제 처리 코드는 `Xth19Processor`다.
- 완료 판정 이후 주문 상태 전이는 주문 종류에 따라 갈린다.
  - (a) 일반 입찰 주문은 `PREPARING`에 머물러 있어 `COMPLETED` 전이가 거부되고 실패한다.
  - (b) 즉시 구매 주문은 `PENDING_PAYMENT`에 머물러 있어 `COMPLETED`로 전이된다.

## 1. 운송장 등록 요청

### 1-1. 진입 API

- `PATCH /shipments/order/{shipmentId}/status`, 바디는 `Xhx14RequestDto`(courier, trackingNumber).
  - 클래스 매핑 `B/domain/m12/controller/command/Xhx14CommandController.java:20`, 메서드 `:33-49`.
  - `Xhx14CommandService.updateTrackingInfo(shipmentId, courier, trackingNumber)`를 호출한다 (`:41`).
- 보조 API로 `POST /shipments/order/{shipmentId}/check-status`(`:58`)와 `/check-status-string`이 있다. 운송장을 저장하고 곧바로 택배사를 조회한다. 이 부분은 4번과 5번에서 다룬다.

### 1-2. 코드가 의도한 상태 변경 순서와 알림

모두 `B/domain/m12/service/command/Xhx14CommandService.java`의 `updateTrackingInfo` (`:238-303`, `@Transactional`)에 있다.

1. courier나 trackingNumber가 비어 있으면 `TRACKING_INFO_REQUIRED`를 던진다 (`:243-246`).
2. 배송(`Xhx14`)을 조회한다 (`:249`). 없으면 `SHIPMENT_NOT_FOUND`다.
3. `shipment.updateTrackingInfo()` (`:256`)가 택배사와 운송장을 세팅하고 **배송 상태를 `IN_TRANSIT`으로 직접 대입**한다. 전이 검사가 없다 (`B/domain/m12/entity/Xhx14.java:41-45`).
4. `order.updateStatus(Xdg64Status.IN_TRANSIT)` (`:259-260`). 주문 쪽은 전이 검사를 한다 (`B/domain/m16/entity/Xdg64.java:113-121`).
5. 구매자에게 알림 "상품이 출발하였습니다. 주문 ID: …"을 보낸다 (`:265-271`, `createNotification`).
6. `updateSaleStatusToSold(orderId)` (`:276`).
   - 판매입찰의 sale을 `SOLD`로 바꾸고, 창고 보관이면 창고 상태를 갱신하고, 판매자에게 "상품이 성공적으로 판매 완료…" 알림을 보낸다 (`:111-183`).
   - 주문입찰 쪽 sale에 대해서도 같은 처리를 한다 (`:150-180`).
7. 창고 보관 판매이면 `updateWarehouseStatusToSold`를 호출한다 (`:279-286`).
8. `updateOrderAndSaleBidStatusToCompleted` (`:289`)가 MATCHED인 주문입찰과 판매입찰을 `COMPLETED`로 바꾼다 (`:412-440`).

의도대로라면 운송장 등록 시점에 주문이 IN_TRANSIT이 되고, 판매가 SOLD 처리되고, 입찰이 COMPLETED가 되고, 구매자와 판매자에게 알림이 간다.

### 1-3. (a) 실배송 일반 구매 입찰 주문에서 끝까지 성공하나? → **아니오, 4단계에서 실패**

- 일반 입찰 주문의 결제·배송 처리 후 주문 상태:
  - 주문은 `PENDING_PAYMENT`로 생성된다 (`B/domain/m16/service/command/Xdg64CommandService.java:81`).
  - `processPaymentAndShipment`에서 `isWarehouseStorage()`가 false인 분기는 `PAYMENT_COMPLETED` → `PREPARING`까지만 간다 (`:175-176`). 상태는 **`PREPARING`**이다.
  - 배송은 `PENDING`으로 생성된다 (`Xhx14CommandService.java:67`).
- `Xdg64Status`의 허용 전이는 `PREPARING → {IN_WAREHOUSE, SHIPMENT_STARTED}`뿐이다 (`B/domain/m16/entity/Xdg64Status.java:26`). `IN_TRANSIT`으로 가는 유일한 전이는 `SHIPMENT_STARTED → IN_TRANSIT`이다 (`:28`).
- `SHIPMENT_STARTED`를 세팅하는 코드는 저장소 어디에도 없다. enum 정의와 라벨 매핑(`B/domain/m16/controller/query/Xdg64QueryController.java:207`)뿐이다.
- 실패 지점은 `Xhx14CommandService.java:260`의 `order.updateStatus(IN_TRANSIT)`이다.
  - `Xdg64.updateStatus`가 `Xxc76StatusException("상태 전환이 허용되지 않습니다: PREPARING -> IN_TRANSIT")`을 던진다 (`Xdg64.java:117-119`).
  - `updateTrackingInfo`의 `catch (Exception e)` (`:295`)가 이를 잡아 `Xpb98Exception(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")`로 감싸 던진다 (`:297-301`). 이 예외는 `Xpb98Exception`이 아니라 `Xxc76StatusException`이므로 `:293`의 rethrow 분기를 타지 않는다.
- **저장되는 것은 없다.**
  - `Xks43Exception`은 `RuntimeException`이다 (`B/global/exception/Xks43Exception.java:10`). `@Transactional` 메서드 밖으로 나가면서 롤백된다.
  - 3단계에서 대입한 courier, trackingNumber, `IN_TRANSIT`은 영속화되지 않는다. 배송은 `PENDING`에 운송장 없음 그대로다.
  - 5단계 이후는 실행되지 않았으므로 알림이나 sale 변경도 없다.
- **응답**: 컨트롤러에 try/catch가 없다 (`Xhx14CommandController.java:33-49`). `Xks43ExceptionHandler.handleGlobalException` (`B/global/exception/Xks43ExceptionHandler.java:49-62`)이 처리한다.
  - HTTP **404**, 바디 `ErrorResponse(code="S001", message="배송 정보를 찾을 수 없습니다.", status=404, path)`.
  - `S001`/404는 `Xpb98ErrorCode.java:12`에 정의돼 있다.
  - 핸들러는 `errorCode.getMessage()`를 쓰므로 상세 메시지(상태 전환 사유)는 응답에 노출되지 않는다.
  - 오류 코드는 "배송 없음"이지만 실제 원인은 주문 상태 전이 거부다.

## 2. 배송 완료 감지

### 2-1. 누가, 언제, 어떻게

- 주체는 스케줄러 `Xpb98BatchScheduler.scheduleShipmentStatusJob`이다.
  - `@Scheduled(cron = "0 0 */6 * * *")`, 즉 **6시간마다**(00, 06, 12, 18시 정각)다 (`B/global/config/Xpb98BatchScheduler.java:34`).
  - `updateShipmentStatusesJob`을 `timestamp` 파라미터로 실행한다 (`:36-40`). 예외는 `printStackTrace`만 한다 (`:41-43`).
- 잡 정의는 `B/domain/m12/config/Xqv91JobConfig.java:54-60`, 스텝은 `:62-81`이다.
  - 청크 50, `skip(Exception.class)`, `skipLimit 50` (`:51-52`, `:67`, `:75-77`).
  - reader는 `JpaPagingItemReader`, 페이지 50 (`:87-97`).
  - writer는 `JpaItemWriter` (`:239-246`).
- 수동 트리거로는 `POST /shipments/order/{id}/check-status`가 있다. 단건을 즉시 조회하며 완료 처리까지 한다 (`Xhx14CommandService.java:451-516`).

### 2-2. 조회 대상

- JPQL: `SELECT s FROM Xhx14 s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL` (`Xqv91JobConfig.java:95`).
- `PENDING` 배송은 조회되지 않는다. 운송장 등록이 1-3처럼 롤백되면 이 대상에 들어오지 않는다.

### 2-3. 실제로 실행되는 처리 코드

- 스텝은 `new Xth19Processor(...)`를 쓴다 (`Xqv91JobConfig.java:69-73`). **실행되는 코드는 `B/domain/m12/config/Xth19Processor.java:56-157`이다.**
  - Playwright로 `https://trace.cjlogistics.com/next/tracking.html?wblNo=…`를 열고 (`:28`, `:81-83`), `tbody#statusDetail tr`을 기다린 뒤 (`:87`), 마지막 행의 5번째 `td` 텍스트를 상태로 쓴다 (`:181`).
- 같은 작업을 하는 **죽은 코드**가 두 곳 있다.
  - `Xqv91JobConfig.shipmentItemProcessor` (`:104-177`)는 `@Bean`이지만 스텝에 연결되지 않는다 (`:69`에서 직접 new). 같은 클래스의 `parseCjLogisticsStatus` (`:186-220`, Jsoup)는 호출처가 없다.
  - `Xhx14CommandService.updateShipmentStatuses` (`:308-391`)는 `@Scheduled`도, 호출처도 없다 (저장소 grep 결과 정의 외 참조 없음). `cjTrackingPlaywright.getCurrentTrackingStatus`를 쓴다.
- 두 죽은 코드와 `Xth19Processor`의 차이:
  - `updateShipmentStatuses`는 `completeOrder`를 쓰지 않고 `order.updateStatus(COMPLETED)`를 직접 호출한다 (`:353-355`). 알림 문구도 다르다 ("상품이 배송 완료되었습니다").
  - `Xth19Processor`는 `orderService.completeOrder`를 호출한다 (`:116`).

### 2-4. 택배사 상태 문자열 → 내부 상태

`Xth19Processor.mapToShipmentStatus` (`:220-226`, 다른 두 곳도 동일). 정확한 문자열 일치(switch)다.

| 택배사 문자열 | 내부 상태 |
|---|---|
| `"배송완료"` | `DELIVERED` |
| `"배송출발"` | `OUT_FOR_DELIVERY` |
| 그 외 전부 | `IN_TRANSIT` |

- 파싱 실패나 빈 문자열은 `TRACKING_HTML_PARSE_ERROR` 예외다 (`:172-189`).
- 이전 상태와 같으면 변경 없이 반환한다 (`:101-105`).
- `OUT_FOR_DELIVERY`인 배송에 택배사가 "배송출발/배송완료" 외의 문자열을 주면 `IN_TRANSIT`으로 매핑된다. `OUT_FOR_DELIVERY → IN_TRANSIT` 전이는 허용되지 않아 (`B/domain/m12/entity/Xpb98Status.java:23-28`, `Xhx14.java:47-55`) `IllegalStateException`이 나고 해당 건은 스킵된다.

## 3. 배송 완료 판정 이후 (`Xth19Processor` 경로)

### 3-1. 상태 변경 순서

`Xth19Processor.java:108-117`

1. `orderShipment.updateStatus(DELIVERED)` (`:113`). `IN_TRANSIT`과 `OUT_FOR_DELIVERY` 모두 `DELIVERED`로 갈 수 있다 (`Xpb98Status.java:19-20`, `:26`).
2. `Xhx14CommandService.completeOrder(orderId)` (`:116`, 구현 `Xhx14CommandService.java:190-229`):
   1. `orderBid`를 `findByOrderId`로 조회한다 (`:196`). 없으면 `IllegalArgumentException`이다.
   2. `order.updateStatus(COMPLETED)` (`:204`).
   3. `updateSaleStatusToSold(orderId)` (`:208`)로 판매입찰과 주문입찰의 sale을 `SOLD`로 바꾼다 (`:111-183`).
   4. 구매자에게 "[completeOrder] 주문이 완료 처리되었습니다. 주문 ID: …" 알림을 보낸다 (`:211-217`).
   5. 어떤 예외든 `Xpb98Exception(ORDER_NOT_FOUND_FOR_SHIPMENT)`로 감싸 던진다 (`:221-228`).
3. `notificationService.notifyShipmentCompleted(order)` (`Xth19Processor.java:117`)가 구매자에게 "[배송 완료] 상품이 배송 완료되었습니다. 주문 ID: …"를 보낸다 (`B/domain/m15/service/command/Xkh73CommandService.java:219-229`). 이 메서드는 내부 예외를 삼킨다 (`:230-233`).
4. 처리된 배송은 `JpaItemWriter`로 저장된다.

### 3-2. 알림 건수 (정상 진행 시)

- **구매자 2건**: `[completeOrder] …` 1건과 `[배송 완료] …` 1건. 같은 사건에 중복 알림이 간다.
- **판매자**: `updateSaleStatusToSold`가 sale을 `SOLD`로 바꾸는 경우에만 1건 간다 (`:132-138`, `:163-169`).
  - sale이 이미 `SOLD`면 `canTransitionTo(SOLD)`가 false라 (`B/domain/m10/entity/Xgg74Status.java:38`) 판매자 알림이 없다.
  - 두 경로(판매입찰 기준, 주문입찰 기준)가 같은 sale을 가리키면 두 번째는 이미 `SOLD`이므로 알림은 최대 1건이다.

### 3-3. 입찰 상태

- 배치 경로(`completeOrder`)는 주문입찰과 판매입찰의 `status`를 건드리지 않는다. 둘 다 이전 값(`MATCHED`)으로 남고 `COMPLETED`가 되지 않는다.
- `COMPLETED`로 바꾸는 `updateOrderAndSaleBidStatusToCompleted` (`Xhx14CommandService.java:412-440`)는 `updateTrackingInfo`에서만 호출된다 (`:289`). 그런데 `updateTrackingInfo`는 1-3처럼 그 앞에서 실패한다. 그러므로 이 메서드는 사실상 실행되지 않는다.
- 이 메서드는 private인 데다 `@Transactional`이 붙어 있어 그 어노테이션은 효과가 없다.
- 바뀌는 것은 판매(`Xgg74`)의 `SOLD`뿐이다.

## 4. 주문 종류별 차이

배송이 배치 대상(`IN_TRANSIT`)이 되려면 택배사 조회 결과가 완료가 아닌 상태로 `check-status` 엔드포인트가 한 번 성공해야 한다. 이때 `updateTrackingInfo`와 달리 배송만 `IN_TRANSIT` 등으로 저장되고 주문은 건드리지 않는다 (`Xhx14CommandService.java:473-498`). 이후 배치가 배송 완료를 판정하는 상황을 가정한다.

### (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문 → **끝까지 진행되지 않음**

- 주문 상태는 `PREPARING`이다 (`Xdg64CommandService.java:175-176`).
- 배송을 `DELIVERED`로 바꾼 뒤 `completeOrder`의 `order.updateStatus(COMPLETED)` (`Xhx14CommandService.java:204`)에서 실패한다. `PREPARING`에서 `COMPLETED`로의 전이는 없다 (`Xdg64Status.java:26`). `Xxc76StatusException`이 나고 `Xpb98Exception(ORDER_NOT_FOUND_FOR_SHIPMENT)`로 감싸진다 (`:221-228`).
- 설사 이 검사를 통과해도 다음 단계에서 막힌다. 일반 입찰 주문은 `Xzz58.order`가 연결되지 않는다. `saleBidQueryService.findByOrderId`는 없으면 null이 아니라 `IllegalArgumentException`을 던진다 (`B/domain/m10/service/query/Xzz58QueryService.java:26-29`). 그런데 `updateSaleStatusToSold`에서 이 호출(`Xhx14CommandService.java:116`)은 try 밖에 있어 그대로 전파된다. 즉 `if (saleBid != null)` 분기는 사실상 도달 불가다.
- 결과:
  - 프로세서가 예외를 던져 해당 배송은 스킵된다 (5번 참고).
  - 배송과 주문 변경은 롤백된다. 배송은 `IN_TRANSIT`으로 남아 6시간마다 재조회되고 계속 실패한다.
  - 알림은 0건이다.

### (b) 즉시 구매로 만들어진 주문 → **끝까지 진행됨**

- 주문 상태는 `PENDING_PAYMENT`로 생성되고 (`Xdg64CommandService.java:244`), `createInstantOrder` 안에서 상태가 바뀌지 않는다. 결제 서비스도 주문 상태를 바꾸지 않는다 (`B/domain/m06/service/command/Xbf54CommandService.java`에 `order.updateStatus` 호출이 없음).
- `PENDING_PAYMENT → COMPLETED`는 허용 전이다 (`Xdg64Status.java:24`). 그래서 `completeOrder`의 `order.updateStatus(COMPLETED)`가 통과한다.
- 즉시 구매 주문은 판매입찰이 `assignOrder`로 연결된다 (`Xdg64CommandService.java:279`). 그래서 `findByOrderId`가 성공한다. 주문입찰도 `status=MATCHED`, `sale` 연결, `isInstantPurchase=true`로 만들어진다 (`B/domain/m16/service/command/Xzj27CommandService.java:189-206`).
- 결제 처리 시점에 이미 sale이 `SOLD`가 되고, 구매자와 판매자에게 알림이 나간다 (`Xbf54CommandService.java:83`, `:388-419`, `:434-456`). 이때 `order.getOrderBid()`가 아직 null이라 판매입찰 경로를 탄다 (`:388-407`).
- 따라서 배송 완료 시점에는 `updateSaleStatusToSold`가 `sale.getStatus().canTransitionTo(SOLD)`에서 false를 만나 변경도, 판매자 알림도 건너뛴다 (`Xhx14CommandService.java:119`, `:156`; `Xgg74Status.java:38`).
- 결과:
  - 배송 `DELIVERED`, 주문 `COMPLETED`.
  - 구매자 알림 2건 (`[completeOrder]`, `[배송 완료]`), 판매자 알림 0건.
  - 주문입찰과 판매입찰은 `MATCHED` 그대로다.

### 차이 요약

| 구분 | (a) 일반 입찰 | (b) 즉시 구매 |
|---|---|---|
| 주문 상태(배송 완료 시점) | `PREPARING` | `PENDING_PAYMENT` |
| `order → COMPLETED` | 거부 (`Xdg64Status.java:26`) | 허용 (`Xdg64Status.java:24`) |
| 판매입찰 연결 | 없음 (`findByOrderId`가 예외) | 있음 (`MATCHED`) |
| 결과 | 스킵(예외), 롤백, 알림 0건 | `DELIVERED`+`COMPLETED`, 구매자 알림 2건 |

## 5. 실패 처리 (주기 처리 중 한 건이 실패할 때)

- `Xth19Processor.process`는 어떤 예외든 `Xpb98Exception`으로 바꿔 던진다 (`Xth19Processor.java:133-146`). 브라우저 페이지는 `finally`에서 닫는다 (`:146-156`).
- 스텝이 `faultTolerant().skip(Exception.class).skipLimit(50)`이다 (`Xqv91JobConfig.java:75-77`).
  - 실패한 **그 건은 스킵**된다. 스킵 리스너가 로그만 남긴다 (`:251-287`). 그 건은 writer에 가지 않아 저장되지 않는다. 상태는 `IN_TRANSIT` 또는 `OUT_FOR_DELIVERY` 그대로이고, 6시간 뒤 다음 실행에서 다시 조회된다.
  - **나머지 건은 계속 처리**된다. Spring Batch의 fault-tolerant 스텝은 프로세서 예외 시 청크를 롤백하고 항목을 하나씩 다시 처리해, 성공한 건만 커밋한다 (프레임워크 일반 동작이며 이 저장소에 별도 구현은 없다).
  - 한 번의 잡 실행에서 스킵이 50건을 넘으면 스텝이 `SkipLimitExceededException`으로 실패하고 남은 건은 처리되지 않는다.
- 알림 생성 실패 중 `notifyShipmentCompleted`는 예외를 삼켜 배송 완료 처리를 막지 않는다 (`Xkh73CommandService.java:230-233`). `completeOrder` 안의 `createNotification` 실패는 전파되어 해당 건이 스킵된다.
- 스케줄러 자체가 던지는 예외(잡 실행 실패)는 `printStackTrace`로만 처리된다 (`Xpb98BatchScheduler.java:41-43`).
- 참고로 죽은 코드 `updateShipmentStatuses`에는 건별 try/catch로 `errorCount++` 후 계속하는 방식이 있지만 (`Xhx14CommandService.java:383-387`), 실행되지 않는다.
- 추정(코드 외 프레임워크 동작): reader 쿼리의 `status IN (…)` 조건 때문에 청크 커밋으로 `DELIVERED`가 된 건이 결과 집합에서 빠진다. 이때 `JpaPagingItemReader`의 페이지 오프셋이 밀려 일부 건이 해당 실행에서 누락될 수 있다. 누락된 건은 다음 실행에서 처리된다.
