# 구매자 배송: 운송장 등록 → 배송 완료

경로 약어: `B` = `src/main/java/com/fream/back`, `S` = `B/domain/m12/service/command/Xhx14CommandService.java`.

핵심 요약
- 운송장 등록 API(`PATCH /shipments/order/{id}/status`)는 주문이 `PREPARING`/`PENDING_PAYMENT`인 한 항상 실패한다(주문 상태 전이 규칙 위반). 롤백되어 아무것도 저장되지 않고 404 `S001`이 내려간다.
- 배송 완료 감지는 6시간 주기 Spring Batch 잡이며, 실제 실행 코드는 `Xth19Processor`다.
- (a) 실배송 일반 구매 입찰 주문은 배송 완료 처리가 끝까지 가지 못한다. (b) 즉시 구매 주문은 끝까지 진행된다.

## 1. 운송장 등록 요청

### 1-1. 어느 API로 들어오나
- `PATCH /shipments/order/{shipmentId}/status`, body는 `Xhx14RequestDto`(courier, trackingNumber). `B/domain/m12/controller/command/Xhx14CommandController.java:20`(base path), `:33`(PatchMapping), `:34-48`(서비스 호출).
- 서비스 `S:238` `updateTrackingInfo(shipmentId, courier, trackingNumber)`.
- 유사 API로 `POST /shipments/order/{id}/check-status`, `/check-status-string`이 있다(`Xhx14CommandController.java:58`, `:103`). 이 둘은 운송장 등록 + 택배사 즉시 조회를 하는 `S:451 updateAndCheckShipmentStatus`를 호출한다. 1번 질문의 "운송장 등록"은 PATCH 쪽이다.

### 1-2. 상태 변경 순서와 알림 (코드가 의도한 순서)
`S:238-303`:
1. 택배사/운송장 공백이면 `TRACKING_INFO_REQUIRED`(400) (`S:243-246`).
2. 배송 조회 후 `shipment.updateTrackingInfo(courier, trackingNumber)` → 배송(Xhx14) 상태를 전이 검사 없이 `IN_TRANSIT`으로 세팅 (`S:256`, `B/domain/m12/entity/Xhx14.java:41-45`).
3. `order.updateStatus(Xdg64Status.IN_TRANSIT)` → 주문(Xdg64) 상태 `IN_TRANSIT` (`S:259-260`).
4. 구매자에게 알림 "상품이 출발하였습니다. 주문 ID: …" 1건 (`S:265-271`).
5. `updateSaleStatusToSold(orderId)` (`S:276`): 판매(Xgg74)가 `SOLD`로 전이 가능하면 `SOLD`로 바꾸고 창고 보관이면 창고 상태 갱신, 판매자에게 "상품이 성공적으로 판매 완료…" 알림 (`S:111-183`; saleBid 경로 `:116-147`, orderBid 경로 `:150-180`).
6. 창고 보관 판매면 `updateWarehouseStatusToSold` 한 번 더 (`S:279-286`).
7. `updateOrderAndSaleBidStatusToCompleted` → 주문 입찰(Xzj27)·판매 입찰(Xzz58)이 `MATCHED`이면 `COMPLETED`로 (`S:289`, `S:412-440`). 즉 배송 출발 시점에 입찰을 완료 처리하도록 짜여 있다. 이 메서드는 `private`인 `@Transactional`이고 내부 예외를 삼킨다 (`S:436-439`).

### 1-3. 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문(즉시 구매 아님)에서 끝까지 성공하나 → **실패한다**
- 결제·배송 처리를 마친 실배송(창고 보관 아님) 주문의 상태는 `PREPARING`이다. 이 주문은 `PENDING_PAYMENT → PAYMENT_COMPLETED → PREPARING`까지만 간다.
  - 서비스 경로: `B/domain/m16/service/command/Xdg64CommandService.java:174-176` (창고 보관이 아닌 else 분기).
  - Kafka 경로(컨트롤러 `B/domain/m16/controller/command/Xdg64CommandController.java:54`가 이벤트를 발행): `B/domain/m16/service/kafka/Xdg64EventConsumer.java:195`, `:215-218`.
  - `SHIPMENT_STARTED`로 바꾸는 코드는 코드베이스 전체에 없다(`Xdg64Status.SHIPMENT_STARTED`를 `updateStatus`에 넘기는 곳 없음).
- 주문 상태 전이표: `PREPARING`은 `{IN_WAREHOUSE, SHIPMENT_STARTED}`만 허용 (`B/domain/m16/entity/Xdg64Status.java:26`). `IN_TRANSIT`은 `SHIPMENT_STARTED`에서만 갈 수 있다 (`:28`).
- 따라서 `S:260 order.updateStatus(IN_TRANSIT)`에서 `Xxc76StatusException`("상태 전환이 허용되지 않습니다: PREPARING -> IN_TRANSIT")이 발생한다 (`B/domain/m16/entity/Xdg64.java:113-120`).
- 이 예외는 `Xpb98Exception`이 아니라 `S:293`의 `catch (Xpb98Exception)`에 걸리지 않고, `S:295-302`의 일반 `catch (Exception)`에서 `Xpb98Exception(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")`로 감싸져 다시 던져진다. 에러 코드 이름이 실제 원인(상태 전이 불가)과 무관하게 "배송 정보를 찾을 수 없음"으로 나가는 점이 주석/이름과 실제 동작이 다른 부분이다.
- 저장되는 것: **없다.** `updateTrackingInfo`는 `@Transactional`이고 RuntimeException(`Xks43Exception extends RuntimeException`, `B/global/exception/Xks43Exception.java`)이 밖으로 나가므로 롤백된다. 배송은 `PENDING`에 courier/trackingNumber 없이 남고, 주문은 `PREPARING` 그대로이며, 알림은 4단계 이전에 실패해 생성되지 않는다(알림은 `S:266` 이후라서 생성조차 안 됨).
- 응답: `Xks43ExceptionHandler`가 `ErrorResponse`로 변환 (`B/global/exception/Xks43ExceptionHandler.java:49-61`). HTTP **404**, code `S001`, message "배송 정보를 찾을 수 없습니다." (`B/domain/m12/exception/Xpb98ErrorCode.java:12`). `Xpb98Exception`의 custom message는 응답 message에 쓰이지 않고 errorCode의 message가 쓰인다.
- 참고: 즉시 구매 주문도 `PENDING_PAYMENT`(`Xdg64CommandService.java:244`에서 만들어진 뒤 상태 전진 코드 없음)라서 `PENDING_PAYMENT → IN_TRANSIT`이 표에 없어(`Xdg64Status.java:24`) 똑같이 실패한다.
- 결론: PATCH로 운송장을 등록해 `IN_TRANSIT`으로 만드는 경로는 어떤 주문에서도 성공하지 못한다. 배송이 `IN_TRANSIT`이 되려면 `check-status` 계열(`S:473`)을 거쳐야 한다. 아래 2-1 참고.

## 2. 배송 완료 감지

### 2-1. 누가·언제·어떻게
- 주체: `Xpb98BatchScheduler.scheduleShipmentStatusJob()` (`B/global/config/Xpb98BatchScheduler.java:34-44`). `JobLauncher`로 `updateShipmentStatusesJob`을 timestamp 파라미터와 함께 실행 (`:37-40`).
- 주기: `@Scheduled(cron = "0 0 */6 * * *")` → 매 6시간 정각(00, 06, 12, 18시, 매일) (`:34`).
- 대상: 리더 JPQL `SELECT s FROM Xhx14 s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL` (`B/domain/m12/config/Xqv91JobConfig.java:95`), 페이지 크기 50 (`:51`, `:93`).
- 배송이 `IN_TRANSIT`이 되는 경로는 사실상 `check-status` 계열뿐이다: `updateAndCheckShipmentStatus`가 `shipment.updateTrackingInfo`로 `IN_TRANSIT` + 운송장을 세팅하고(`S:473`) 조회 결과가 배송 출발이면 `OUT_FOR_DELIVERY`로 커밋한다(`S:491-494`). 단, 조회 결과가 "배송완료/배송출발"이 아니면 `S:497`의 `IN_TRANSIT → IN_TRANSIT`이 `Xpb98Status.java:16-21`에서 거부되어 `IllegalStateException` → `EXTERNAL_TRACKING_SERVICE_ERROR`(503) + 롤백 (`S:507-514`). 즉 PATCH 경로(1)가 막혀 있어 운영상 조회 대상이 되려면 "배송출발"로 조회되는 건이 `check-status`로 먼저 들어가야 한다.

### 2-2. 실제 실행되는 처리 코드
비슷한 코드가 3곳 있다.
| 후보 | 실제 실행 여부 |
|---|---|
| `Xth19Processor#process` (`B/domain/m12/config/Xth19Processor.java:57`) | **실행됨.** `Xqv91JobConfig.java:69`에서 `new Xth19Processor(playwrightBrowserManager(), notificationService, orderService)`를 step의 processor로 등록. |
| `Xqv91JobConfig#shipmentItemProcessor` 빈 (`Xqv91JobConfig.java:106`) | step에 연결되지 않음(미사용). Jsoup `parseCjLogisticsStatus`(`:186`) 역시 미사용 private. |
| `Xhx14CommandService#updateShipmentStatuses` (`S:308`) | 호출하는 곳이 없음(스케줄러·컨트롤러 어디서도 호출 안 함). 미사용. |

- 실행 방식: Playwright 브라우저를 step 시작/종료 시 열고 닫음 (`Xmb36Listener.java:15-24`), 건별 `browserManager.newPage()`로 `https://trace.cjlogistics.com/next/tracking.html?wblNo={운송장}` 이동(`Xth19Processor.java:72-87`), `tbody#statusDetail tr`의 마지막 행 5번째 `td` 텍스트를 상태 문자열로 사용 (`:169-181`).
- chunk 50, `faultTolerant().skip(Exception.class).skipLimit(50)` (`Xqv91JobConfig.java:67-77`).

### 2-3. 택배사 상태 문자열 → 내부 상태
`Xth19Processor.java:220-225`:
- `"배송완료"` → `DELIVERED`
- `"배송출발"` → `OUT_FOR_DELIVERY`
- 그 외 모든 문자열(null이 아닌 이상) → `IN_TRANSIT` (집화처리, 간선상차 등 전부)
- 정확 일치(`switch`)이며 공백 트림 후 비교(`:181`). 빈 문자열이면 `TRACKING_HTML_PARSE_ERROR` (`:182-186`).

## 3. 배송 완료 판정 이후 (`Xth19Processor` 경로)

1. 현재 상태와 새 상태가 같으면 아무 것도 안 하고 반환 (`Xth19Processor.java:90-96`).
2. `DELIVERED`이면 (`:99-118`):
   1. 배송(Xhx14) `IN_TRANSIT`/`OUT_FOR_DELIVERY` → `DELIVERED` (메모리상, 이후 writer가 저장) (`:113`, 전이표 `Xpb98Status.java:16-29`).
   2. `orderService.completeOrder(orderId)` (`:116`, `S:190-229`):
      - 주문 입찰 조회 (`S:196`) → 주문(Xdg64) → `COMPLETED` (`S:204`)
      - `updateSaleStatusToSold` (`S:208`): 판매 입찰 조회(없으면 예외 — 아래 4), 판매(Xgg74)가 `SOLD`로 전이 가능하면 `SOLD` + 판매자 알림, 이어서 주문 입찰 쪽 판매도 같은 처리
      - 구매자 알림 "[completeOrder] 주문이 완료 처리되었습니다. 주문 ID: …" (`S:211-217`)
   3. `notificationService.notifyShipmentCompleted(order)` (`:117`) → 구매자에게 "[배송 완료] 상품이 배송 완료되었습니다. 주문 ID: …" (`B/domain/m15/service/command/Xkh73CommandService.java:219-230`, 예외는 삼킴).
   4. writer(`JpaItemWriter`)가 배송을 merge로 저장 (`Xqv91JobConfig.java:241-246` shipmentJpaItemWriter).
3. 알림 건수: 구매자 2건(completeOrder 1 + 배송 완료 1). 판매자 알림은 판매가 아직 `SOLD`가 아닐 때만 최대 2회 경로(saleBid 경로 + orderBid 경로)에서 생기는데, 같은 판매에 대해서는 첫 경로에서 `SOLD`가 되면 두 번째는 `canTransitionTo(SOLD)`가 false라 1건이다. 다만 아래 4(b)처럼 결제 시점에 이미 `SOLD`로 바뀌므로 실제로는 판매자 알림 0건이다. → **구매자 2건, 판매자 0건**(통상 경로).
4. 주문 입찰·판매 입찰 상태: **바뀌지 않는다.** `updateOrderAndSaleBidStatusToCompleted`는 PATCH 경로(`S:289`)에서만 호출되고 `completeOrder`/배치 경로에는 없다. 따라서 배송 완료 후에도 입찰은 `MATCHED`로 남고 `COMPLETED`가 되지 않는다. (`check-status` 경로 `S:489`도 `completeOrder`만 호출.)
5. `check-status` 경로(`S:483-489`)는 배송 `DELIVERED` + `completeOrder`까지이며 `notifyShipmentCompleted`는 호출하지 않아 구매자 알림 1건(completeOrder)만 간다.

## 4. 주문 종류별 차이

### (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문 → 끝까지 진행되지 **않는다**
- 주문 상태 `PREPARING` (1-3 참고). `completeOrder`의 `order.updateStatus(COMPLETED)` (`S:204`)에서 `PREPARING → COMPLETED`가 전이표에 없어(`Xdg64Status.java:26`) `Xxc76StatusException`.
- `completeOrder`의 `catch (Exception)`이 `Xpb98Exception(ORDER_NOT_FOUND_FOR_SHIPMENT)`로 감싸 다시 던짐 (`S:221-228`).
- 결과: 구매자 알림·`notifyShipmentCompleted`·판매 `SOLD` 모두 실행되지 않음(주문 완료 단계 이전에 실패). `Xth19Processor`는 예외를 그대로 던지고(`:455-467`) 해당 건은 skip. 배송의 `DELIVERED` 세팅은 writer에 도달하지 못해 저장되지 않으므로 배송은 `IN_TRANSIT`/`OUT_FOR_DELIVERY` 그대로 남아 6시간마다 다시 조회되고 다시 실패한다. 주문은 `PREPARING`, 입찰은 `MATCHED` 그대로.
- `check-status`로 호출하면 `completeOrder` 예외가 `S:505-506`에서 그대로 올라가고 컨트롤러는 HTTP 404(빈 body) 또는 `Error: …` 문자열(string 변형)을 반환한다 (`Xhx14CommandController.java:80-86`, `:124-131`; 코드 `Xpb98ErrorCode.java:20` 404). 전체가 롤백된다.
- 추가 이유: `updateSaleStatusToSold`의 `saleBidQueryService.findByOrderId`는 연결된 SaleBid가 없으면 null이 아니라 `IllegalArgumentException`을 던진다 (`B/domain/m10/service/query/Xzz58QueryService.java:26-29`). 일반 구매 입찰 주문에는 판매 입찰이 연결되지 않으므로 `S:116`의 `if (saleBid != null)` 방어 코드는 의미가 없고, 주문 상태 전이를 통과하더라도 이 지점에서 예외가 난다(그 예외는 `S:150`의 try 밖이라 삼켜지지 않는다).

### (b) 즉시 구매로 만들어진 주문 → 끝까지 진행된다
- 즉시 구매 주문은 `PENDING_PAYMENT`로 만들어지고 이후 상태가 전진하지 않는다 (`Xdg64CommandService.java:244`, 결제 `:305`; `createInstantOrder`에 상태 전이 코드 없음). 판매 입찰에 주문이 연결되고(`:279`) 주문 입찰은 `MATCHED`로 생성(`Xzj27CommandService.java:133-142`, `:196`, `:205`).
- `PENDING_PAYMENT → COMPLETED`는 전이표에 있다 (`Xdg64Status.java:24`). 그래서 `completeOrder`가 통과한다: 주문 `COMPLETED`, 구매자 알림 1건.
- `updateSaleStatusToSold`: 판매 입찰이 연결돼 있어 `findByOrderId`가 성공. 판매는 결제 처리(`notifyUsersAndUpdateSaleStatus`, `B/domain/m06/service/command/Xbf54CommandService.java:83`, `:388-428`)에서 이미 `SOLD`가 되어 있어 `canTransitionTo(SOLD)`가 false(`B/domain/m10/entity/Xgg74Status.java:23`) → 판매 상태 변경·판매자 알림 없음.
- 최종: 배송 `DELIVERED`, 주문 `COMPLETED`, 구매자 알림 2건(배치 경로; check-status 경로는 1건), 판매자 알림 0건, 판매 입찰·주문 입찰 `MATCHED` 유지.
- 단 (b)도 운송장 등록 PATCH는 1-3대로 실패하므로, 배송이 `IN_TRANSIT`이 되려면 `check-status`를 거쳐야 한다.

## 5. 실패 처리 (배치 중 한 건 실패)
- `faultTolerant().skip(Exception.class).skipLimit(50)` (`Xqv91JobConfig.java:75-77`): 처리 중 예외가 난 건은 skip 처리되고 나머지 건은 계속 진행된다. skip된 건은 writer로 가지 않아 저장되지 않는다(배송 상태 불변, 다음 6시간 주기에 재조회).
- skip 시 `shipmentSkipListener`가 `[Skip] 배송 상태 처리 스킵: shipmentId=…` 로그만 남긴다 (`Xqv91JobConfig.java:252-287`). 재시도·알림·보상 처리는 없다.
- `Xth19Processor`는 모든 예외를 `Xpb98Exception`(비-Xpb98은 `EXTERNAL_TRACKING_SERVICE_ERROR`)으로 감싸 던진다 (`:455-467`). 운송장 번호가 비면 `TRACKING_NUMBER_INVALID` (`:60-63`).
- skip 한도 50 초과 시 step이 실패한다(Spring Batch 동작; 해당 한도는 `SKIP_LIMIT = 50`, `Xqv91JobConfig.java:52`).
- 주의(추정): `completeOrder`는 프록시를 통한 `@Transactional` 호출이라 chunk 트랜잭션에 참여한다. 이 내부에서 예외가 나면 chunk 트랜잭션이 rollback-only로 표시되어, 같은 chunk(최대 50건)의 다른 건 처리 결과에도 영향을 줄 수 있다. 이 부분은 Spring Batch 런타임 동작에 대한 추정이며 코드만으로 확정하지 못했다.
- 스케줄러 자체는 잡 실행 예외를 `printStackTrace()`로만 처리한다 (`Xpb98BatchScheduler.java:41-43`).
