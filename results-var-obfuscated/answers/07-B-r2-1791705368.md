## 1. 진입 API, 처리 단계, 동기/비동기, 응답 ID

**API**: `POST /order-bids/instant` (클래스 `@RequestMapping("/order-bids")` — `D/m16/controller/command/Xzj27CommandController.java:22`, 메서드 `:89-110`).
요청 바디는 `Xpj49RequestDto`(saleBidId, addressId, warehouseStorage, paymentRequest — `D/m16/dto/Xpj49RequestDto.java:20-29`).

**처리 단계 (모두 한 요청 스레드, 한 `@Transactional` 안에서 진행)**

1. 컨트롤러: 이메일 추출 후 `enrichPaymentRequest`로 결제 요청에 `userEmail`을 넣고 `orderId`를 null로 설정 (`Xzj27CommandController.java:92-98`, `:119-123`).
2. `Xzj27CommandService.createInstantOrderBid` (`D/m16/service/command/Xzj27CommandService.java:118-149`, `@Transactional`):
   - 입력 검증(이메일/판매입찰ID/배송지ID/결제정보 null 체크) — `:154-167`
   - 구매자 조회, `getSaleBidAndValidate`로 판매 입찰 조회 + sale 존재 확인 — `:126-130`, `:172-184`. 판매 입찰의 상태(이미 MATCHED인지)나 본인 입찰 여부는 검증하지 않는다.
3. `Xdg64CommandService.createInstantOrder` (`D/m16/service/command/Xdg64CommandService.java:219-319`) 에서 순서대로:
   1. 배송지 조회 `addressQueryService.getAddress` — `:238`
   2. 주문(Xdg64) 저장, 상태 `PENDING_PAYMENT`, 금액 = 판매 입찰가 — `:241-247`
   3. 결제 요청에 주문 ID 세팅 — `:250`
   4. 주문 항목 생성 — `:255-256`
   5. 배송 정보 생성(배송지의 수령인/전화/우편번호/주소) — `:264-271`
   6. 판매 입찰에 주문 연결 + `MATCHED` + flush — `:279-283`
   7. 판매가 창고 보관이면 창고 상태 `ASSOCIATED_WITH_ORDER` — `:291-294`
   8. 결제 처리 `paymentCommandService.processPayment` — `:305`
4. 다시 `Xzj27CommandService`: 구매 입찰(Xzj27)을 `MATCHED`로 만들어 저장하고 `markAsInstantPurchase()` — `:142`, `:189-206`.
5. 컨트롤러가 `ResponseDto.success(...)` 반환 — `Xzj27CommandController.java:101-109`.

**동기 처리다.** 이 경로에서는 Kafka 이벤트를 발행하지 않는다. `Xdg64EventProducer.sendOrderProcessingEvent`는 일반 주문 컨트롤러(`D/m16/controller/command/Xdg64CommandController.java:54`)에서만 호출되고, 즉시 구매 경로(`Xzj27CommandController` → `Xzj27CommandService` → `Xdg64CommandService.createInstantOrder`)에는 없다. 결제도 PortOne API를 요청 스레드에서 동기 호출한다 (`D/m06/p05/Xxv33ApiClient.java:229-295`).

**응답으로 돌려주는 ID**: 변수 이름과 성공 메시지는 "orderId"이지만 실제 값은 **주문 입찰(Xzj27, order_bid) ID**다. `createInstantOrderBid(...)`가 `Xzj27`을 반환하고 그 `.getId()`를 `orderId` 변수에 담아 응답한다 (`Xzj27CommandController.java:101-107`; 반환 타입 `Xzj27CommandService.java:119`). 주문(Xdg64) ID가 아니다.

## 3. 결제 수단별 결과, 성공 여부, 카드 결제 실패 시

`Xbf54CommandService.processPayment`가 `getResolvedPaymentType()`으로 분기한다 (`:57-80`). 요청 바디 `paymentType`이 `CARD`/`ACCOUNT`/`GENERAL`이며 Jackson 서브타입으로 매핑된다 (`D/m06/dto/Xbf54RequestDto.java:20-25`). 공통 검증은 orderId·이메일 일치와 `paidAmount > 0`뿐이다(`:117-146`). 결제 금액이 주문 금액(`totalAmount`)과 같은지는 검사하지 않는다.

| 수단 | 처리 | 결제 상태 | isSuccess | 근거 |
|---|---|---|---|---|
| CARD | 저장된 결제 정보 조회 후 PortOne API 동기 호출 | 응답 `status == "success"`이면 `PAID`, 아니면 기본값 `PENDING` | 위 조건일 때만 true | `Xbf54CommandService.java:157-208`; 기본값 `D/m06/entity/Xbf54.java:39`, `:44` |
| ACCOUNT | 은행명 검증만 하고 외부 호출 없이 저장 | `PENDING` | false (기본값) | `Xbf54CommandService.java:236-262` |
| GENERAL | `impUid` 필수 확인 후 저장 (이미 결제된 건으로 간주, 외부 검증 없음) | `PAID` | true | `Xbf54CommandService.java:290-316` |

**즉시 구매는 끝까지 성공하는가**: 결제 수단과 상관없이 `processPayment`가 예외 없이 반환되면 흐름은 끝까지 간다. 계좌이체(`PENDING`)나 카드 응답이 `"success"`가 아닌 경우에도, 결제 성공 여부를 확인하지 않고 그대로 진행한다.
- `createInstantOrder`는 `processPayment`가 던진 예외만 처리하고 `payment.isSuccess()`를 보지 않는다 (`Xdg64CommandService.java:304-311`).
- `notifyUsersAndUpdateSaleStatus`도 결제 상태와 무관하게 판매를 `SOLD`로 바꾸고 알림을 보낸다 (`Xbf54CommandService.java:83`, `:383-420`).
- 따라서 계좌이체는 입금 전(`PENDING`)인데도 판매 `SOLD`, 판매 입찰 `MATCHED`, 구매 입찰 `MATCHED`가 되고 HTTP 200 + "즉시 구매가 성공적으로 처리되었습니다."가 반환된다 (`Xzj27CommandController.java:109`).
- 이 흐름에서 주문(Xdg64)은 `PENDING_PAYMENT`로 남는다.

**결제 대행사가 카드 결제를 실패로 응답하면** (두 가지로 나뉨)

1. **PortOne이 HTTP 비200 이거나 body의 `code != 0`**인 경우 (일반적인 승인 실패): `Xdf64Exception("카드 결제 요청 실패: ...")`를 던진다 (`Xxv33ApiClient.java:270-275`).
   - 이 예외는 `Xbf54Exception`이라 그대로 전파된다 (`Xxv33ApiClient.java:286-287`, `Xbf54CommandService.java:180-181`, `:218-219`, `:89-94`).
   - `createInstantOrder`가 `Xqj91Exception`("결제 처리 중 오류가 발생했습니다")으로 감싸 던진다 (`Xdg64CommandService.java:305-309`). 이 예외는 `Xdg64Exception`이라 바깥 catch에서 그대로 재던져지고 (`:312-315`), `Xzj27CommandService`도 그대로 재던진다 (`Xzj27CommandService.java:145-146`, `:212-215`).
   - 모두 `RuntimeException`(`D/../global/exception/Xks43Exception.java:10`)이며 `@Transactional`이므로 **전체 트랜잭션이 롤백**된다. 주문, 주문 항목, 배송, 판매 입찰 MATCHED, 창고 상태, 결제가 모두 취소된다. 구매 입찰은 아직 만들어지지 않았다.
   - 클라이언트는 `Xks43ExceptionHandler`의 `Xdg64Exception` 핸들러가 만든 오류 응답을 받는다 (`D/../global/exception/Xks43ExceptionHandler.java:325-340`). 알림은 발송되지 않는다. 알림 단계는 결제 성공 이후에 있기 때문이다.
   - 네트워크 오류(`RestClientException`)는 `Xbf54ApiException`이 되고 `@Retryable`(최대 3회)이 붙어 있다 (`Xxv33ApiClient.java:229` 위 어노테이션, `:288-290`).
2. **HTTP 200 + `code == 0`이지만 `status`가 `"success"`가 아닌 경우**: 예외가 없다. 카드 결제가 `PENDING`/isSuccess=false로 **저장되고** (`Xbf54CommandService.java:203-208`), 위 "끝까지 성공" 경로와 같이 진행된다. 즉 실패로 응답했어도 구매는 성공 처리되고 판매는 `SOLD`가 된다.

## 4. 알림 수신자, 시점, 전달 방식

**누가 무엇을 받나** (`Xbf54CommandService.sendNotifications`, `:434-462`)

| 수신자 | 메시지 | 근거 |
|---|---|---|
| 구매자 | "결제가 완료되었습니다. 주문 ID: {주문 ID}" | `Xbf54CommandService.java:438-443` |
| 판매자(`sale.getSeller()`) | "구매자가 결제를 완료하였습니다. 판매 ID: {판매 ID}" | `Xbf54CommandService.java:447-454` |

둘 다 카테고리 `SHOPPING`, 타입 `BID`. 다른 알림(구매 입찰 생성, 주문 완료 등)은 이 경로에서 발송되지 않는다. Kafka 컨슈머의 "ORDER_COMPLETED" WebSocket/Kafka 알림(`Xdg64EventConsumer.java:287-329`)은 이 경로에서 호출되지 않는다.

**언제**: `processPayment` 안에서 결제 객체 저장 직후, 판매를 `SOLD`로 바꾸기 직전이다 (`Xbf54CommandService.java:83`, `:416-419`). 요청 스레드·같은 트랜잭션 안에서 동기로 실행된다. 결제 성공 여부와 무관하다(3번 참고).

**어떤 방식으로**: `Xkh73CommandService.createNotification` (`D/m15/service/command/Xkh73CommandService.java:44-67`)
1. DB에 알림 레코드 저장 (`:52-53`).
2. 실시간 전송: Redis에 `WebSocket:Xrd81:{email}` 키가 있을 때만 STOMP `convertAndSendToUser(email, "/queue/notifications", dto)`로 푸시한다 (`:37-39`, `:303-323`). 연결이 없으면 DB에만 저장된다.
3. 알림 전송 중 예외는 `sendNotifications`/`notifyUsersAndUpdateSaleStatus`에서 로그만 남기고 삼킨다 (`Xbf54CommandService.java:421-425`, `:457-461`). 알림 실패가 구매를 실패시키지 않는다.

주의: 판매자에게 가는 "판매 입찰이 등록되었습니다." 알림은 입찰 등록 시(`Xgg74CommandService.java:125-130`)의 것이며 즉시 구매와 무관하다.

## 5. 최종 주문 상태와 창고 보관 선택 시 차이

**최종 주문(Xdg64) 상태: `PENDING_PAYMENT`** 이다.
- 생성 시 `PENDING_PAYMENT` (`Xdg64CommandService.java:244`).
- 이후 즉시 구매 경로에서 `order.updateStatus(...)`를 호출하는 곳이 없다 (2번 보충 참고). `Xbf54CommandService`도 주문 상태를 건드리지 않는다.
- 결제가 `PAID`여도 주문은 `PENDING_PAYMENT`로 남는다. 결제 완료/배송 준비 같은 상태로 진행하는 코드는 일반 주문 경로(`processPaymentAndShipment`, Kafka 컨슈머)에만 있다.
- "즉시 구매가 성공적으로 처리되었습니다."라는 응답 메시지와는 다르다 (`Xzj27CommandController.java:109`).
- 함께 변하는 값: 판매 입찰 `MATCHED`, 판매 `SOLD`, 구매 입찰 `MATCHED`, 배송 `PENDING`, 결제는 수단별(3번).

**구매자가 "창고 보관"을 선택한 경우**: 달라지는 것이 **없다**. 구매자가 보낸 `warehouseStorage` 값은
- 컨트롤러에서 로그에만 쓰이고 서비스로 전달되지만 (`Xzj27CommandController.java:94-95`, `:104`),
- `Xdg64CommandService.createInstantOrder`의 `isWarehouseStorage` 파라미터는 메서드 본문에서 한 번도 읽히지 않는다 (시그니처 `:220-221`, 본문 `:222-318`).
- 창고 관련 분기는 **판매자**가 판매 등록 때 정한 `sale.isWarehouseStorage()`만 본다 (`Xdg64CommandService.java:291-294`). 이 값이 true면 이미 있는 창고 보관 건(Xnn94)을 `ASSOCIATED_WITH_ORDER`로 바꾼다 (`Xnn94CommandService.java:117-133`, `D/m07/service/query/Xnn94QueryService.java:30-33`).
- 구매자 선택에 따른 새 창고 보관 건(`createOrderStorage`), `IN_WAREHOUSE`/`COMPLETED` 전이는 일반 주문 경로에만 있다 (`Xdg64CommandService.java:163-173`, `Xdg64EventConsumer.java:197-211`). 즉시 구매에서는 실행되지 않는다.
- 결과적으로 구매자가 창고 보관을 선택해도 주문은 `PENDING_PAYMENT`이고, 배송 정보(Xhx14)는 항상 생성된다 (`Xdg64CommandService.java:264-271`).
