# 즉시 구매 처리 흐름

경로 약어: `D` = `src/main/java/com/fream/back/domain`

## 1. 진입 API, 처리 단계, 동기/비동기, 응답 ID

**진입점**: `POST /order-bids/instant` (`D/m16/controller/command/Xzj27CommandController.java:22` base `/order-bids`, `:89` `@PostMapping("/instant")`, `:90` `createInstantOrderBid`). 바디는 `Xpj49RequestDto`(saleBidId, addressId, warehouseStorage, paymentRequest) (`D/m16/dto/Xpj49RequestDto.java:20-29`).

**처리 단계 (모두 한 요청 스레드, 한 `@Transactional` 안에서 순차 실행)**

1. 컨트롤러가 인증 이메일을 꺼내고(`Xzj27CommandController.java:92`), `enrichPaymentRequest`로 결제 요청에 `userEmail`을 넣고 `orderId=null`로 비운다 (`:98`, `:119-123`).
2. `Xzj27CommandService#createInstantOrderBid`가 입력(이메일·saleBidId·addressId·paymentRequest null 여부)을 검증하고 (`D/m16/service/command/Xzj27CommandService.java:123`, `:154-167`), 구매자 조회(`:126`), 판매 입찰 조회(`:129`, `:172-184`; `Xzz58QueryService#findById` 는 없으면 IllegalArgumentException, `D/m10/service/query/Xzz58QueryService.java:21-24`)를 한다. 판매 입찰이 이미 매칭됐는지 같은 상태 검증은 없다.
3. `Xdg64CommandService#createInstantOrder` 호출 (`Xzj27CommandService.java:133-139`), 내부 순서 (`D/m16/service/command/Xdg64CommandService.java`):
   1. 배송지 조회 `addressQueryService.getAddress` (`:238`)
   2. 주문 `Xdg64` 생성·저장 (`:241-247`)
   3. 결제 요청에 orderId 주입 (`:250`)
   4. 주문 항목 `Xhm58` 생성 (`:255-256`)
   5. 배송 `Xhx14` 생성 (`:264-271`)
   6. 판매 입찰에 주문 연결 + MATCHED + flush (`:279-283`)
   7. 판매자 창고 보관분이면 창고 상태 변경 (`:291-294`)
   8. 결제 처리 `processPayment` (`:305`)
4. 주문 입찰 `Xzj27`을 만들어 저장한다 (`Xzj27CommandService.java:142`, `:189-207`).

**동기 처리다.** Kafka 이벤트를 쓰지 않는다. 이 경로에는 `Xdg64EventProducer`가 없고 서비스 메서드 직접 호출뿐이다 (`Xdg64CommandService.java:305`). Kafka 비동기 처리는 별도 API `POST /orders/{orderId}/process-payment-shipment`(`Xdg64EventProducer#sendOrderProcessingEvent`)이며 즉시 구매와는 무관하다. 알림도 동기로 DB 저장한다 (4번 참조).

**응답으로 돌려주는 ID**: 변수명과 메시지는 `orderId`지만 실제로는 **주문 입찰(`Xzj27`, order bid)의 ID**다. 서비스가 `Xzj27`을 반환하고 (`Xzj27CommandService.java:142-144`) 컨트롤러가 그 `.getId()`를 `orderId`에 담아 응답한다 (`Xzj27CommandController.java:101-109`). 주문(`Xdg64`)의 ID가 아니다. 응답 메시지는 항상 "즉시 구매가 성공적으로 처리되었습니다."이다 (`:109`).

## 3. 결제 수단별 결과, 성공 여부, 카드 실패 응답

`processPayment`가 `getResolvedPaymentType()`으로 분기한다 (`Xbf54CommandService.java:67-80`). 검증: orderId·이메일 일치, 금액>0 (`:117-146`).

| 수단 | 동작 | 결제 상태 | 근거 |
|---|---|---|---|
| CARD | 저장된 결제정보 조회 후 PortOne(아임포트) 호출, 응답 `status=="success"`일 때만 PAID·성공 처리 | 성공 응답: `PAID`, isSuccess=true / 그 외 응답: `PENDING`, isSuccess=false | `:164-208` |
| ACCOUNT | 은행명 검증 후 외부 호출 없이 저장 | 항상 `PENDING` (입금 확인 단계 없음) | `:236-262` |
| GENERAL | impUid 필수, 외부 호출 없이 클라이언트가 보낸 값으로 저장 | 즉시 `PAID`, isSuccess=true | `:290-316` |

**끝까지 성공하는가**: 수단과 무관하게 결제가 예외 없이 저장되기만 하면 즉시 구매는 끝까지 진행되어 200 OK를 돌려주며, 이후 단계(알림, 판매 SOLD, 주문 입찰 MATCHED)도 결제 상태를 확인하지 않고 실행된다 (`Xbf54CommandService.java:83`, `:383-419`). 즉 ACCOUNT는 입금 전(PENDING)인데도 "결제가 완료되었습니다" 알림과 SOLD 처리가 일어난다.

**카드사/PG가 실패로 응답하는 경우**
- PortOne 응답의 HTTP 상태가 200이 아니거나 `code != 0`이면 `Xdf64Exception`을 던진다 (`D/m06/p05/Xxv33ApiClient.java:270-275`). 이 예외는 `Xdg64CommandService`에서 `Xqj91Exception`("결제 처리 중 오류")으로 감싸지고 (`:305-309`), `Xzj27CommandService`가 `Xdg64Exception`을 그대로 다시 던진다 (`Xzj27CommandService.java:145-147`, `:212-215`). 하나의 트랜잭션이므로 주문·항목·배송·판매 입찰 MATCHED·창고 상태가 모두 롤백된다. 요청은 에러 응답이 된다.
- `code == 0`이지만 `response.status`가 "success"가 아닌 경우(승인 거절 등 PG가 failed로 응답)에는 예외가 없다. 결제 엔티티가 `PENDING`/isSuccess=false로 저장되고 (`Xbf54CommandService.java:203-208`, `Xbf54.java:39`, `:44`), 이어서 알림과 SOLD 처리, 주문 입찰 MATCHED, 200 OK 성공 응답이 그대로 나간다. 결제 실패를 `FAILED`로 기록하는 코드도 없다.

## 4. 알림 수신자, 시점, 방식

- 시점: 결제 처리 직후 같은 요청·같은 트랜잭션 안에서 즉시 (`Xbf54CommandService.java:83` → `:383-416` → `sendNotifications` `:434-456`). Kafka `notification-topic`은 사용하지 않는다.
- 수신자와 내용 (카테고리 `SHOPPING`, 타입 `BID`):
  - 구매자: "결제가 완료되었습니다. 주문 ID: {orderId}" (`:438-443`)
  - 판매자(`sale.getSeller()`): "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}" (`:447-455`)
- 방식: `Xkh73CommandService#createNotification`이 알림을 DB에 저장하고 (`D/m15/service/command/Xkh73CommandService.java:52-54`), 해당 사용자의 Redis 키 `WebSocket:Xrd81:{email}`가 있을 때(웹소켓 접속 중)만 `/queue/notifications`로 WebSocket 푸시한다 (`:57`, `:303-323`). 접속 중이 아니면 저장만 된다.
- 실패 처리: `sendNotifications`와 `notifyUsersAndUpdateSaleStatus`는 예외를 로그만 남기고 삼킨다 (`Xbf54CommandService.java:457-461`, `:421-425`). 다만 알림 서비스가 클래스 레벨 `@Transactional`이라 (`Xkh73CommandService.java:27`) 거기서 예외가 나면 바깥 트랜잭션이 rollback-only가 될 수 있다(코드 상 추정).
- 알림이 가는 곳은 이 둘뿐이다. 즉시 구매 경로에서 판매 입찰 등록자 외 다른 사용자에게는 알림이 없다.

## 5. 최종 주문 상태와 창고 보관 선택 시 차이

**주문(`Xdg64`)의 최종 상태는 `PENDING_PAYMENT`이다.** 즉시 구매 경로에서 `Xdg64.updateStatus`를 호출하는 곳이 없다. 주문은 `PENDING_PAYMENT`로 만들어지고 (`Xdg64CommandService.java:244`) 이후 상태 변경이 없다. 결제가 PAID여도 마찬가지이며, `PAYMENT_COMPLETED`/`PREPARING` 전이는 `processPaymentAndShipment`(별도 API)에만 있다 (`:165-177`). 메서드 이름·응답 문구("즉시 구매가 성공적으로 처리")와 달리 주문은 결제 완료 상태로 넘어가지 않는다.

같은 요청이 만든 다른 엔티티의 최종 상태: 판매 입찰 `MATCHED`, 판매 `SOLD`, 주문 입찰 `MATCHED`, 배송 `PENDING`, 결제는 3번 표와 같다.

**구매자가 "창고 보관"(`warehouseStorage=true`)을 선택해도 달라지는 것이 없다.**
- 컨트롤러는 이 값을 로그에 찍고 서비스로 넘긴다 (`Xzj27CommandController.java:94-95`, `:104`). 서비스도 `createInstantOrder`에 넘기지만 (`Xzj27CommandService.java:133-139`), `createInstantOrder` 본문에서 `isWarehouseStorage` 파라미터는 한 번도 읽히지 않는다 (`Xdg64CommandService.java:220-319`).
- 따라서 구매자용 창고 보관 `Xnn94`는 생성되지 않고 (`warehouseStorageCommandService.createOrderStorage` 호출 없음; 그 호출은 `processPaymentAndShipment` `:170`에만 있다) 주문은 `IN_WAREHOUSE`/`COMPLETED`로 가지 않는다.
- 창고 관련으로 실제 일어나는 것은 판매자 쪽 플래그뿐이다. 판매(`Xgg74.isWarehouseStorage`)가 창고 보관 상품이면 그 보관 레코드가 `ASSOCIATED_WITH_ORDER`로 바뀐다 (`Xdg64CommandService.java:291-293`). 구매자의 선택값과는 무관하다.
