# 구매자 배송: 운송장 등록 → 배송 완료 처리 분석

경로 약어: `M12` = `src/main/java/com/fream/back/domain/m12`, `M16` = `.../domain/m16`, `M10` = `.../domain/m10`, `M06` = `.../domain/m06`, `M15` = `.../domain/m15`, `G` = `src/main/java/com/fream/back/global`.

## 사전 사실: 결제·배송 처리 직후의 상태

| 구분 | 주문(Xdg64) | 배송(Xhx14) | 비고 |
|---|---|---|---|
| (a) 일반 구매 입찰 주문, 실배송 | `PENDING_PAYMENT → PAYMENT_COMPLETED → PREPARING` | `PENDING` | `M16/service/command/Xdg64CommandService.java:175-176` (`isWarehouseStorage=false` 분기), 배송 생성 `:148-155`, `M12/service/command/Xhx14CommandService.java:61-68` |
| (b) 즉시 구매 주문 | `PENDING_PAYMENT` 그대로 | `PENDING` | `Xdg64CommandService.java:241-245`(생성), `:264-271`(배송), `:305`(결제). 결제 서비스는 주문 상태를 바꾸지 않음(`M06/service/command/Xbf54CommandService.java`에 `Xdg64Status` 사용 없음) |

- (a)에서 주문 입찰(Xzj27)에는 `order`가 걸려 있다(`M16/service/command/Xzj27CommandService.java:90-100`). 판매 입찰(Xzz58)은 주문과 연결되지 않는다. `saleBid.assignOrder(order)`는 즉시 구매 경로에만 있다(`Xdg64CommandService.java:279`).
- (b)에서는 판매 입찰(Xzz58)에 `order`가 걸리고(`Xdg64CommandService.java:279-280`, `M10/entity/Xzz58.java:58-61`), 주문 입찰(Xzj27)은 주문 생성 뒤 `MATCHED` + `isInstantPurchase=true`로 만들어진다(`Xzj27CommandService.java:189-206`).
- 결제 시점에 이미 판매(Xgg74)가 `SOLD`가 된다. 주문 입찰 경로는 `Xbf54CommandService.java:419`, 판매 입찰 경로는 `:404`이다. 구매자·판매자에게 "결제 완료" 알림이 가는 것도 이때다(`:434-456`). 판매 `SOLD`는 배송 완료보다 먼저 일어난다(아래 3·4번에 영향).
- 주문 상태 전이표: `M16/entity/Xdg64Status.java:24-32`. 전이 위반이면 `Xxc76StatusException`이 던져진다(`M16/entity/Xdg64.java:113-121`).
  - `PENDING_PAYMENT → {PAYMENT_COMPLETED, COMPLETED, IN_WAREHOUSE}`
  - `PREPARING → {IN_WAREHOUSE, SHIPMENT_STARTED}`
  - `IN_TRANSIT → {COMPLETED}`
  - `SHIPMENT_STARTED`로 보내는 코드는 코드베이스 어디에도 없다. `grep SHIPMENT_STARTED`는 전이표와 설명 문자열(`Xdg64QueryController.java:207`)뿐이다.

## 1. 운송장 등록 요청

### 1-1. 어느 API로 들어오나

- `PATCH /shipments/order/{shipmentId}/status`, body `{courier, trackingNumber}` → `Xhx14CommandController#updateTrackingInfo` (`M12/controller/command/Xhx14CommandController.java:20,33-49`) → `Xhx14CommandService#updateTrackingInfo` (`M12/service/command/Xhx14CommandService.java:238-303`).
- 인증만 필요하다(`G/config/security/SecurityConfig.java:50-52`: 화이트리스트 외 `anyRequest().authenticated()`). 운영 전용 권한 검사는 코드에 없다.
- 입력 검증은 서비스에서 courier·trackingNumber가 비어 있으면 `TRACKING_INFO_REQUIRED`(`Xhx14CommandService.java:243-246`). DTO에는 검증 어노테이션이 없다(`M12/dto/Xhx14RequestDto.java`).
- 같은 컨트롤러에 `POST .../check-status`, `POST .../check-status-string`도 있다. 이 둘은 운송장 등록과 동시에 택배사 조회를 즉시 수행하는 `updateAndCheckShipmentStatus`를 호출한다(`Xhx14CommandController.java:58-138`, 서비스 `:451-516`).

### 1-2. 의도된 상태 변경 순서와 알림 (`updateTrackingInfo`, `Xhx14CommandService.java:249-289`)

1. 배송 조회(`findById`) 후 `shipment.updateTrackingInfo(courier, trackingNumber)`. 택배사·운송장을 저장하고 **전이 검사 없이** 배송 상태를 `IN_TRANSIT`으로 직접 대입한다(`M12/entity/Xhx14.java:41-45`).
2. `order.updateStatus(IN_TRANSIT)`으로 주문 상태를 `IN_TRANSIT`으로 바꾼다(`:259-260`).
3. 구매자에게 알림 "상품이 출발하였습니다. 주문 ID: …"(`:265-271`, `Xkh73CommandService#createNotification` `M15/service/command/Xkh73CommandService.java:44-67`).
4. `updateSaleStatusToSold(orderId)`(`:276`, 본체 `:111-183`)
   - 판매 입찰로 판매를 찾는다. `Xzz58QueryService#findByOrderId`는 **null이 아니라 없으면 `IllegalArgumentException`을 던진다**(`M10/service/query/Xzz58QueryService.java:26-29`).
   - 판매가 `SOLD`로 전이 가능하면 `SOLD`로 바꾸고, 창고 보관이면 창고 상태를 `SOLD`로 바꾼 뒤 판매자에게 알림을 보낸다(`:116-141`).
   - 이어서 주문 입찰 기준으로 같은 처리를 한 번 더 시도하고, 판매자에게 알림을 보낸다(`:150-180`).
5. 판매 입찰이 있으면 창고 보관 상태를 한 번 더 `SOLD` 처리한다(`:279-286`).
6. `updateOrderAndSaleBidStatusToCompleted`로 주문 입찰·판매 입찰이 `MATCHED`이면 `COMPLETED`로 바꾼다(`:289`, 본체 `:412-440`, 내부에서 예외를 삼킴).

즉 의도는 "운송장 등록 = 출발" 시점에 주문 `IN_TRANSIT`, 판매 `SOLD`, 입찰 `COMPLETED`까지 한 번에 처리하는 것이다. 구매자 1건 + 판매자 알림(최대 2건)이 목표다.

### 1-3. (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문에서 끝까지 성공하나 → **실패한다**

- 실패 지점은 `Xhx14CommandService.java:260` (`order.updateStatus(Xdg64Status.IN_TRANSIT)`)이다.
  - (a)의 주문 상태는 `PREPARING`이다(`Xdg64CommandService.java:175-176`).
  - 전이표상 `PREPARING → IN_TRANSIT`은 허용되지 않는다(`Xdg64Status.java:26`). `IN_TRANSIT`은 `SHIPMENT_STARTED`에서만 갈 수 있고(`:28`), 그 상태로 만드는 코드가 없다.
  - 따라서 `Xxc76StatusException("상태 전환이 허용되지 않습니다: PREPARING -> IN_TRANSIT")`가 발생한다(`Xdg64.java:113-121`).
- 예외 처리 경로
  - `catch (Xpb98Exception)`은 이 예외에 해당하지 않아 `catch (Exception)`으로 간다(`Xhx14CommandService.java:293-302`).
  - 거기서 `Xpb98Exception(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")`로 감싸 던진다.
- **무엇이 저장되나: 아무것도 저장되지 않는다.**
  - `Xpb98Exception`은 `RuntimeException`(`G/exception/Xks43Exception.java:10`)이고 메서드가 `@Transactional`(`:238`)이라 전체가 롤백된다.
  - 1단계의 택배사·운송장·`IN_TRANSIT`도 롤백되고, 구매자 알림(3단계)·판매 처리·입찰 완료도 실행되지 않는다. 배송은 `PENDING`, 주문은 `PREPARING`에 남는다.
- **응답**
  - 전역 예외 핸들러(`G/exception/Xks43ExceptionHandler.java:49-63`)가 `ErrorResponse`를 반환한다.
  - HTTP **404**, 코드 `S001`, 메시지 "배송 정보를 찾을 수 없습니다."(`M12/exception/Xpb98ErrorCode.java:12`)이며, 상세 메시지(`Xxc76`)는 body에 담기지 않는다(`errorCode.getMessage()` 사용).
  - 실제 원인은 배송 미존재가 아니라 주문 상태 전이 위반이다.
- 설령 주문 상태 전이를 통과했더라도 4단계에서 (a)는 판매 입찰이 없으므로 `findByOrderId`가 `IllegalArgumentException`을 던져(`Xzz58QueryService.java:26-29`) 같은 방식으로 실패한다. 이중으로 막혀 있다.
- (참고) (b)도 주문이 `PENDING_PAYMENT`라 `IN_TRANSIT` 전이가 불가능하다(`Xdg64Status.java:24`)는 이유로 같은 지점에서 실패한다.

### 1-4. 참고: 운송장이 실제로 저장되는 경로

- `check-status` 계열(`updateAndCheckShipmentStatus`)은 주문 상태를 건드리지 않고 운송장을 저장한다(`Xhx14CommandService.java:473`).
- 택배사 조회 결과가 "배송출발"이면 `OUT_FOR_DELIVERY`로 커밋되어 배치 대상이 된다(`:491-494`).
- 결과가 "배송완료"이면 `completeOrder`를 호출한다(`:489`). (a)에서는 아래 3-1대로 실패해 롤백된다.
- 그 밖의 문자열이면 `updateStatus(IN_TRANSIT)`가 호출되는데, 직전에 `updateTrackingInfo`가 이미 `IN_TRANSIT`을 넣어 둔 상태라 `IN_TRANSIT → IN_TRANSIT`은 전이 불가(`M12/entity/Xpb98Status.java:16-22`)이므로 `IllegalStateException`이 난다(`Xhx14.java:47-55`). 이는 `EXTERNAL_TRACKING_SERVICE_ERROR`(503)로 감싸져 롤백된다(`Xhx14CommandService.java:495-498, 507-515`).

## 2. 배송 완료 감지

### 2-1. 누가·언제·어떻게

- **스프링 배치 잡 `updateShipmentStatusesJob`을 스케줄러가 주기 실행**한다.
  - 스케줄러: `G/config/Xpb98BatchScheduler.java:34-44`.
  - 잡/스텝 정의: `M12/config/Xqv91JobConfig.java:54-82`.
  - 실행 시 `timestamp` 잡 파라미터를 매번 새로 넣어 매번 새 JobInstance를 만든다(`Xpb98BatchScheduler.java:37-40`). 예외는 `printStackTrace`만 한다(`:41-43`).
- **주기**: `@Scheduled(cron = "0 0 */6 * * *")` → 매일 00:00, 06:00, 12:00, 18:00 (6시간마다 정각, 서버 타임존 기준)(`Xpb98BatchScheduler.java:34`).
- **대상**: JPQL `SELECT s FROM Xhx14 s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL`(`Xqv91JobConfig.java:95`). 페이지 크기·청크 크기는 50(`:51`)이다.
- **실제 실행되는 처리 코드**: `Xth19Processor#process`
  - 스텝이 `new Xth19Processor(...)`를 processor로 직접 연결한다(`Xqv91JobConfig.java:69-73`).
  - 같은 파일의 `shipmentItemProcessor()` 빈(`:104-177`, 스텝에서 사용 안 함)과 `Xhx14CommandService#updateShipmentStatuses`(`Xhx14CommandService.java:308-391`, 코드베이스 어디서도 호출되지 않음)는 **실행되지 않는 중복 코드**다.
  - 조회 방식: 스텝 리스너 `Xmb36Listener`가 스텝 시작 때 Playwright 브라우저를 열고 종료 때 닫는다(`M12/config/Xmb36Listener.java:15-23`).
  - 운송장마다 `Xrk74#newPage`로 CJ대한통운 추적 페이지를 열어 `tbody#statusDetail tr`을 기다린다.
  - 마지막 행의 5번째 `td`(index 4) 텍스트를 상태 문자열로 쓴다(`Xth19Processor.java:57-100, 167-185`).
  - `Xxx20#getCurrentTrackingStatus`(`G/utils/Xxx20.java:33-115`)는 배치가 아니라 서비스 경로(`check-status`)에서만 쓰인다.
- 푸시/웹훅은 없고, 배송 완료는 이 폴링으로만 감지된다(수동 경로는 `check-status` API).

### 2-2. 택배사 상태 문자열 → 내부 상태 (`Xth19Processor.java:220-226`)

| 택배사 문자열 | 내부 상태 |
|---|---|
| `"배송완료"` | `DELIVERED` |
| `"배송출발"` | `OUT_FOR_DELIVERY` |
| 그 외 모든 문자열(예: "배송중", "집화처리" 등) | `IN_TRANSIT` |

- 완전 일치 비교이다. 매핑 결과가 현재 배송 상태와 같으면 아무것도 하지 않고 그대로 반환한다(`Xth19Processor.java:97-101`).
- 현재가 `OUT_FOR_DELIVERY`인데 조회 결과가 "그 외"이면 `updateStatus(IN_TRANSIT)`가 전이 불가(`Xpb98Status.java:23-28`)라 `IllegalStateException`이 나고, 이는 `EXTERNAL_TRACKING_SERVICE_ERROR`로 감싸져 해당 건이 스킵된다(`Xth19Processor.java:119-121, 129-141`).

## 3. 배송 완료 판정 이후 (`Xth19Processor.java:108-117`)

배송 상태가 `DELIVERED`로 매핑되고 현재 상태와 다르면 다음 순서로 진행한다.

1. `orderShipment.updateStatus(DELIVERED)` : `IN_TRANSIT`/`OUT_FOR_DELIVERY → DELIVERED`는 허용된다(`Xpb98Status.java:16-28`). 이 값은 청크 writer(`JpaItemWriter`, `Xqv91JobConfig.java:239-246`)로 저장된다.
2. `orderService.completeOrder(orderId)` (`Xhx14CommandService.java:190-229`)
   1. 주문 입찰 조회(`Xzj27QueryService#findByOrderId`, `M16/service/query/Xzj27QueryService.java:51-56`). 없으면 `IllegalArgumentException`.
   2. `order.updateStatus(COMPLETED)`로 주문이 `COMPLETED`가 된다(`:204`). 전이가 안 되면 예외가 난다.
   3. `updateSaleStatusToSold(orderId)` 호출(`:208`).
      - 판매 입찰로 조회한다. 입찰이 없으면 `findByOrderId`가 예외를 던진다.
      - 판매가 `canTransitionTo(SOLD)`일 때만 `SOLD`, 창고 처리, 판매자 알림이 일어난다.
      - `Xgg74Status.canTransitionTo`는 `SOLD`에서 어디로도 못 가게 막혀 있어(`M10/entity/Xgg74Status.java:23`) 이미 `SOLD`면 건너뛴다.
   4. 구매자에게 알림 "[completeOrder] 주문이 완료 처리되었습니다. 주문 ID: …"(`:211-217`).
3. `notificationService.notifyShipmentCompleted(order)` : 구매자에게 알림 "[배송 완료] 상품이 배송 완료되었습니다. 주문 ID: …"(`Xth19Processor.java:117`, `M15/service/command/Xkh73CommandService.java:219-234`. 실패해도 예외를 삼킴).

### 3-1. 알림 건수

- **구매자: 2건** (`[completeOrder] …` 1건 + `[배송 완료] …` 1건).
- **판매자: 0건** (일반적인 경우). 결제 시점에 판매가 이미 `SOLD`가 되어 있어(`Xbf54CommandService.java:404,419`) `updateSaleStatusToSold`의 `SOLD` 전이 조건이 거짓이 되기 때문이다(`Xhx14CommandService.java:119, 156`).
  - 판매자 알림이 가는 경우는 판매가 `ON_AUCTION`/`SELLING`일 때뿐이다(`Xgg74Status.java:21-22`).
  - 코드 의도(`updateSaleStatusToSold`가 판매자 알림을 보냄)와 다르게 실제로는 판매자 알림이 생성되지 않는다.

### 3-2. 주문 입찰·판매 입찰 상태

- 배치/`completeOrder` 경로에서는 **주문 입찰(Xzj27)과 판매 입찰(Xzz58)의 상태를 바꾸지 않는다.** 둘 다 `MATCHED`로 남는다.
  - `COMPLETED`로 바꾸는 `updateOrderAndSaleBidStatusToCompleted`는 `updateTrackingInfo` 안에서만 호출된다(`Xhx14CommandService.java:289, 412-440`). 이 경로는 위 1-3에서 실패한다.
  - `completeOrder`와 프로세서에는 입찰 상태 변경 코드가 없다(`:190-229`, `Xth19Processor.java:108-117`).
- 변경되는 엔티티와 순서 요약: 배송 `→ DELIVERED` → 주문 `→ COMPLETED` → (판매 `SOLD`, 보통 이미 SOLD라 변화 없음) → 알림 2건.

## 4. 주문 종류별 차이

배치 입력은 배송이 `IN_TRANSIT`/`OUT_FOR_DELIVERY`이고 운송장이 있는 건이다. 이 상태는 1-4의 `check-status`("배송출발")로 만들어질 수 있다. 이 전제에서 3의 처리를 적용한다.

### (a) 실배송 일반 구매 입찰 주문 → **끝까지 진행되지 않는다 (실패·롤백)**

- 주문이 `PREPARING`이다(`Xdg64CommandService.java:175-176`).
- `completeOrder`의 `order.updateStatus(COMPLETED)`(`Xhx14CommandService.java:204`)가 `PREPARING → COMPLETED` 불가(`Xdg64Status.java:26`)로 `Xxc76StatusException`을 던진다.
- 그러면 `catch (Exception)`이 `Xpb98Exception(ORDER_NOT_FOUND_FOR_SHIPMENT, "주문 완료 처리 중 오류 발생: …")`로 감싸 던진다(`:221-228`).
- 이 예외로 프로세서가 실패하고(`Xth19Processor.java:119-141`), 스텝 트랜잭션이 롤백되어 3-1/3-2의 어떤 변경도 저장되지 않는다.
  - 배송 `DELIVERED` 대입도 롤백된다.
  - 알림은 `completeOrder`가 예외를 던진 시점 이전에는 만들지 않았으므로 0건이다.
  - 주문 입찰·판매 입찰·판매 상태도 그대로다.
- 배송은 `IN_TRANSIT`/`OUT_FOR_DELIVERY`로 남아 6시간 뒤 다시 같은 이유로 실패한다.
- (보조) 설령 주문 전이를 통과해도 판매 입찰이 없어 `updateSaleStatusToSold`의 `findByOrderId`가 `IllegalArgumentException`을 던진다(`Xzz58QueryService.java:26-29`). 이 경우는 `completeOrder`의 `catch (Exception)`으로 같은 래핑이 된다.

### (b) 즉시 구매 주문 → **끝까지 진행된다**

- 주문이 `PENDING_PAYMENT`다(`Xdg64CommandService.java:244`). `PENDING_PAYMENT → COMPLETED`는 허용된다(`Xdg64Status.java:24`). 주문 입찰도 있다(`Xzj27CommandService.java:189-206`)가 주문 입찰은 `order`가 걸려 있어 `findByOrderId`로 조회된다.
- 판매 입찰(Xzz58)이 주문에 연결돼 있어 `findByOrderId`가 예외 없이 반환한다(`Xdg64CommandService.java:279`).
- 결과: 배송 `DELIVERED`, 주문 `COMPLETED`, 구매자 알림 2건이 저장된다.
  - 판매는 결제 시점에 이미 `SOLD`(`Xbf54CommandService.java:404`)라 건너뛰므로 판매자 알림 0건, 창고 처리도 없다.
  - 주문 입찰·판매 입찰은 `MATCHED`로 남는다.

## 5. 주기 처리 중 한 건이 실패하면

- 스텝이 `faultTolerant().skip(Exception.class).skipLimit(50)`로 구성되어 있다(`Xqv91JobConfig.java:75-77`).
- 프로세서에서 예외가 나면 그 건은 `SkipListener#onSkipInProcess`로 에러 로그만 남기고 건너뛴다(`:251-266`).
- 한 건이 실패하면 현재 청크(최대 50건) 트랜잭션이 롤백된 뒤 같은 청크를 항목별로 다시 처리한다. 실패한 건만 제외되고 **나머지 건은 정상 처리·커밋된다.** 실패한 건은 변경이 반영되지 않아 상태 그대로 남고 다음 주기(6시간 뒤)에 다시 조회된다.
- 스킵이 50건을 넘으면 스텝이 실패한다(`SKIP_LIMIT = 50`, `:52`). 그 경우 남은 건은 그 회차에서 처리되지 않는다. 스케줄러는 예외를 `printStackTrace`로만 삼킨다(`Xpb98BatchScheduler.java:41-43`).
- 운송장이 비어 있는 건은 쿼리 조건(`trackingNumber IS NOT NULL`)에서 제외된다(`Xqv91JobConfig.java:95`). 프로세서에도 `TRACKING_NUMBER_INVALID` 가드가 있다(`Xth19Processor.java:60-63`).
- 한 건의 실패가 다른 건을 막지 않는다는 점은 쓰이지 않는 서비스 메서드 `updateShipmentStatuses`의 `try/catch + continue`(`Xhx14CommandService.java:322-387`)와 같은 의도다. 하지만 이 메서드는 호출되지 않는다.
