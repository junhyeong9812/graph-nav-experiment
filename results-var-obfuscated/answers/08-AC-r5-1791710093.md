# 구매자 배송: 운송장 등록 → 배송 완료 처리 분석

경로 약어: `M12` = `src/main/java/com/fream/back/domain/m12/`, `M16` = `src/main/java/com/fream/back/domain/m16/`, `M15` = `.../domain/m15/`, `M06` = `.../domain/m06/`, `M10` = `.../domain/m10/`, `G` = `src/main/java/com/fream/back/global/`.
엔티티 이름: 주문 배송 `Xhx14`(상태 enum `Xpb98Status`), 주문 `Xdg64`(`Xdg64Status`), 구매 입찰 `Xzj27`, 판매 입찰 `Xzz58`, 판매 `Xgg74`, 알림 서비스 `Xkh73CommandService`.

## 0. 선행 사실: 결제·배송 처리를 마친 직후의 상태

- `POST /orders/{orderId}/process-payment-shipment`는 Kafka 이벤트만 발행하고, 실제 처리는 `Xdg64EventConsumer#processCompleteOrder`가 한다. (`M16/service/kafka/Xdg64EventConsumer.java:166-224`)
  - 결제 → `Xhx14` 생성(`PENDING`, `M12/service/command/Xhx14CommandService.java:55-75`) → 주문 `PENDING_PAYMENT → PAYMENT_COMPLETED`(195행) → 실배송(비창고)이면 `PREPARING`(216-217행). 여기서 끝난다.
  - 동기 서비스 경로 `Xdg64CommandService#processPaymentAndShipment`도 같다: `PAYMENT_COMPLETED → PREPARING` (`M16/service/command/Xdg64CommandService.java:173-177`). 창고 보관이면 `COMPLETED`까지 간다(163-172행).
- 즉 실배송 일반 구매 입찰 주문(a)의 주문 상태는 `PREPARING`, 배송 상태는 `PENDING`이다.
- 주문 상태 전이표: `PENDING_PAYMENT→{PAYMENT_COMPLETED, COMPLETED, IN_WAREHOUSE}`, `PREPARING→{IN_WAREHOUSE, SHIPMENT_STARTED}`, `IN_TRANSIT→{COMPLETED}` (`M16/entity/Xdg64Status.java:24-31`). `Xdg64#updateStatus`는 불허 전이에서 `Xxc76StatusException`(RuntimeException 계열)을 던진다 (`M16/entity/Xdg64.java:113-121`, `M16/exception/Xxc76StatusException.java:6`).
- 결제 시점에 이미 판매(`Xgg74`)가 `SOLD`로 바뀐다: `Xbf54CommandService#processPayment` → `notifyUsersAndUpdateSaleStatus` → `sale.updateStatus(SOLD)` (`M06/service/command/Xbf54CommandService.java:83`, `:383-427`). 이때 구매자·판매자에게 "결제 완료" 알림도 간다(`:434-`). 이 사실이 3·4번 답에 영향을 준다.

## 1. 운송장 등록 요청

### 1-1. 진입 API
- `PATCH /shipments/order/{shipmentId}/status`, 본문 `Xhx14RequestDto`(courier, trackingNumber) → `Xhx14CommandController#updateTrackingInfo` → `Xhx14CommandService#updateTrackingInfo` (`M12/controller/command/Xhx14CommandController.java:20,33-49`).
- 보조 경로: `POST /shipments/order/{shipmentId}/check-status`, `/check-status-string`은 운송장을 갱신하면서 즉시 택배사 조회까지 한다(`Xhx14CommandController.java:58-94`, `:103-138` → `Xhx14CommandService.java:452-516`). 아래 1-3의 실패 경로와는 별개다.
- 보안 설정은 `anyRequest().authenticated()`뿐이라 URL에 "운영자 전용" 제한은 없다 (`G/config/security/SecurityConfig.java:52`).

### 1-2. 코드가 의도한 순서 (`Xhx14CommandService#updateTrackingInfo`, `M12/.../Xhx14CommandService.java:238-303`)
1. courier/trackingNumber 공백 검증, 위반 시 `TRACKING_INFO_REQUIRED` (243-246).
2. `Xhx14` 조회 후 `shipment.updateTrackingInfo(courier, trackingNumber)` → 택배사·운송장 저장, 배송 상태를 전이 검사 없이 `IN_TRANSIT`으로 직접 세팅 (256행, `M12/entity/Xhx14.java:41-45`).
3. 주문 `order.updateStatus(IN_TRANSIT)` (260행).
4. 구매자에게 알림 1건: "상품이 출발하였습니다. 주문 ID: …" (265-271행). 수신자는 구매자(`order.getUser()`)뿐이다.
5. `updateSaleStatusToSold(orderId)` (276행): 판매 입찰 → 판매 `SOLD` + (창고 보관이면 창고 상태 SOLD) + 판매자 알림 "상품이 성공적으로 판매 완료되었습니다" (111-183행). 구매 입찰 경유 판매에도 같은 처리(150-180행).
6. 창고 보관 상품이면 창고 상태 SOLD 갱신 (279-286행).
7. `updateOrderAndSaleBidStatusToCompleted` (289행): 구매 입찰 `MATCHED→COMPLETED`, 판매 입찰 `MATCHED→COMPLETED` (412-440행). 이 메서드는 내부에서 모든 예외를 삼킨다(436-439행).

의도된 상태 순서는 배송(IN_TRANSIT) → 주문(IN_TRANSIT) → 판매(SOLD) → 입찰(COMPLETED)이다. 이름은 "운송장 등록"인데 코드는 이 시점에 판매 SOLD·입찰 COMPLETED까지 앞당겨 처리하려 한다.

### 1-3. (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문에서는 끝까지 성공하지 않는다
- 실패 지점: 260행 `order.updateStatus(Xdg64Status.IN_TRANSIT)`.
  - 주문 상태가 `PREPARING`이고(0절) `PREPARING`의 허용 전이는 `IN_WAREHOUSE, SHIPMENT_STARTED`뿐이라(`Xdg64Status.java:26`) `Xxc76StatusException`이 발생한다 (`Xdg64.java:113-121`).
  - `Xpb98Exception`이 아니므로 293행 catch에 걸리지 않고, 295-302행의 `catch (Exception)`이 `Xpb98Exception(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")`으로 감싸 던진다.
- 무엇이 저장되나: 아무것도 저장되지 않는다.
  - `@Transactional`(238행) 메서드에서 RuntimeException이 전파되어 롤백된다. 256행의 운송장·택배사·`IN_TRANSIT` 세팅은 영속화되지 않고, 배송은 `PENDING`, 주문은 `PREPARING`으로 남는다.
  - 알림(265행 이후), 판매 SOLD, 입찰 COMPLETED는 실행 전이라 전혀 일어나지 않는다.
- 응답: `Xks43ExceptionHandler#handleShipmentException`이 `errorCode`의 status로 응답한다 (`G/exception/Xks43ExceptionHandler.java:459-473`). 코드는 `SHIPMENT_NOT_FOUND`("S001", "배송 정보를 찾을 수 없습니다.", **404**) (`M12/exception/Xpb98ErrorCode.java:12`). 실제 원인은 주문 상태 전이 불가인데 "배송 정보 없음 404"로 나간다. 본문은 `ErrorResponse`(코드 S001, 메시지 고정 문구).
- 참고: 같은 PATCH가 성공하려면 주문이 이미 `SHIPMENT_STARTED` 상태여야 하지만, 코드베이스에서 `SHIPMENT_STARTED`로 보내는 곳은 없다(전이표에만 존재, `Xdg64Status.java:26-29`).
- 추가 위험(260행을 통과했다고 가정해도 실패): 5단계 `updateSaleStatusToSold`의 `saleBidQueryService.findByOrderId`는 연결된 판매 입찰이 없으면 `null`이 아니라 `IllegalArgumentException`을 던진다 (`M10/service/query/Xzz58QueryService.java:26-29`). 116행의 `if (saleBid != null)` 분기는 사실상 도달 불가이고 이 예외가 try 밖에서 전파된다(150행 try는 그 뒤).

## 2. 배송 완료 감지

### 2-1. 누가·언제·어떻게
- 사람이 호출하는 API가 아니라 스케줄러가 감지한다. `Xpb98BatchScheduler#scheduleShipmentStatusJob`, `@Scheduled(cron = "0 0 */6 * * *")` → **6시간마다**(매일 00·06·12·18시 정각, 서버 타임존 기준) `updateShipmentStatusesJob`을 `JobLauncher`로 실행한다. 매번 timestamp 파라미터를 넣어 새 JobInstance가 된다 (`G/config/Xpb98BatchScheduler.java:34-44`). 예외는 `printStackTrace`만 한다(41-43행).
- 수동 보조: `POST .../check-status`(1-1)는 단건을 즉시 조회한다.

### 2-2. 조회 대상
- `shipmentItemReader`의 JPQL: `SELECT s FROM Xhx14 s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL` (`M12/config/Xqv91JobConfig.java:87-97`). 페이지·청크 크기 50 (51행).
- 따라서 `PENDING` 상태(운송장 미등록)나 이미 `DELIVERED`인 배송은 대상이 아니다.

### 2-3. 실제로 실행되는 처리 코드
- 실제 실행: **`Xth19Processor#process`** (`M12/config/Xth19Processor.java:57-137`).
  - 스텝이 `new Xth19Processor(playwrightBrowserManager(), notificationService, orderService)`를 프로세서로 등록한다 (`Xqv91JobConfig.java:69-73`). 이 프로세서는 `Xrk74`(Playwright 브라우저 매니저)로 `newPage()` → CJ대한통운 조회 URL 이동 → `tbody#statusDetail tr` 대기 → 마지막 행 5번째 `td`를 상태 문자열로 파싱한다 (`Xth19Processor.java:72-95`, `:167-192`). 브라우저는 `Xmb36Listener`가 스텝 전후로 열고 닫는다 (`Xqv91JobConfig.java:80`, `M12/config/Xmb36Listener.java:14-24`).
- 실행되지 않는 유사 코드(죽은 코드):
  - `Xqv91JobConfig#shipmentItemProcessor` (104-177행)는 `@Bean`이지만 스텝이 사용하지 않는다(스텝은 69행에서 `new Xth19Processor`). 다른 곳에서도 참조가 없다.
  - `Xqv91JobConfig#parseCjLogisticsStatus` (186-220행) private·미사용.
  - `Xhx14CommandService#updateShipmentStatuses` (308-391행)는 호출처가 없다. 이쪽은 `Xxx20`(요청마다 Playwright 기동)을 쓰고, DELIVERED 때 `completeOrder`도 호출하지 않는 다른 로직이라 실제 흐름과 다르다.

### 2-4. 택배사 상태 문자열 → 내부 상태
- `Xth19Processor#mapToShipmentStatus` (`Xth19Processor.java:220-226`): `"배송완료"` → `DELIVERED`, `"배송출발"` → `OUT_FOR_DELIVERY`, **그 외 모든 문자열**(집화처리·간선상차·공백 포함 "배송 완료" 등) → `IN_TRANSIT`. `.trim()` 후 정확히 일치해야 한다 (파싱 `:181`).
- 현재 상태와 같으면 변경 없이 반환(`:101-106` 부근, 동일 상태 스킵).
- 주의: 배송이 `OUT_FOR_DELIVERY`인데 택배사가 그 외 문자열을 주면 `IN_TRANSIT`으로 매핑되고, `OUT_FOR_DELIVERY→IN_TRANSIT`은 `Xpb98Status` 전이표에 없어 `IllegalStateException`이 난다 (`M12/entity/Xpb98Status.java:16-26`, `Xhx14.java:47-55`, 호출 `Xth19Processor.java:119-121`). 이 건은 5번 실패 처리로 간다.

## 3. 배송 완료 판정 이후 (`Xth19Processor#process`의 DELIVERED 분기, `:108-117`)

### 3-1. 상태 변경 순서
1. 배송 `Xhx14.updateStatus(DELIVERED)` — `IN_TRANSIT/OUT_FOR_DELIVERY → DELIVERED`는 허용 (`Xpb98Status.java:16-26`, `Xhx14.java:47-55`), 메모리상 변경 (`Xth19Processor.java:109`).
2. `orderService.completeOrder(orderId)` (112행 → `M12/.../Xhx14CommandService.java:190-229`):
   - 구매 입찰 `Xzj27`을 `findByOrderId`로 조회, 없으면 예외 (196-197행).
   - 주문 `Xdg64.updateStatus(COMPLETED)` (204행).
   - `updateSaleStatusToSold(orderId)` (208행): 판매 `Xgg74` → `SOLD`는 `canTransitionTo(SOLD)`일 때만 (`M10/entity/Xgg74Status.java:15-24`: `ON_AUCTION`/`SELLING`에서만 허용; 결제 때 이미 `SOLD`면 `SOLD→SOLD` 불가라 건너뜀).
   - 구매자 알림 (211-217행).
   - 모든 Exception은 `Xpb98Exception(ORDER_NOT_FOUND_FOR_SHIPMENT)`으로 감싸 재throw (221-228행).
3. `notificationService.notifyShipmentCompleted(order)` (113행, `M15/.../Xkh73CommandService.java:219-236`) — 구매자 알림, 자체 try/catch로 실패해도 삼킨다.
4. 배송 변경분은 `JpaItemWriter`가 청크 커밋 때 저장한다 (`Xqv91JobConfig.java:239-246`).
- 결과: **배송 DELIVERED → 주문 COMPLETED → (조건부) 판매 SOLD**.

### 3-2. 알림 (정상 완료 시)
- 구매자 2건(중복): ① `"[completeOrder] 주문이 완료 처리되었습니다. 주문 ID: …"` (`Xhx14CommandService.java:211-217`) ② `"[배송 완료] 상품이 배송 완료되었습니다. 주문 ID: …"` (`Xkh73CommandService.java:228`).
- 판매자 알림 "상품이 성공적으로 판매 완료되었습니다"(`Xhx14CommandService.java:132-138`, `:163-169`)는 판매가 이 시점에 `SOLD`로 전이될 때만 가는데, 결제 시점에 이미 `SOLD`가 된 판매(0절)에서는 `canTransitionTo(SOLD)`가 false라 **가지 않는다**. 그래서 실제로는 **구매자 2건, 판매자 0건**이다.

### 3-3. 주문 입찰·판매 입찰 상태
- 변하지 않는다. 배치 경로(`completeOrder`)는 `updateOrderAndSaleBidStatusToCompleted`를 호출하지 않는다 (그 메서드는 `updateTrackingInfo`의 289행에서만 호출).
- 구매 입찰 `Xzj27`, 판매 입찰 `Xzz58`은 주문 생성/매칭 때 세팅된 `MATCHED`로 남고 `COMPLETED`가 되지 않는다. (`Xzj27#assignOrder`가 `MATCHED`로 둠: `M16/entity/Xzj27.java:60-82`; 즉시 구매 시 `MATCHED`: `M16/service/command/Xzj27CommandService.java:189-206`; 판매 입찰도 `assignOrder`/`assignSale`에서 `MATCHED`: `M10/entity/Xzz58.java:53-61`.)

## 4. 주문 종류별 차이

배치가 `DELIVERED`를 잡으려면 배송이 `IN_TRANSIT/OUT_FOR_DELIVERY`+운송장 보유여야 한다. 그런데 PATCH 경로는 두 주문 모두에서 260행에서 실패하므로, 이 상태는 `POST .../check-status`(주문 상태는 건드리지 않고 `Xhx14#updateTrackingInfo`로 배송만 `IN_TRANSIT`으로 저장, `Xhx14CommandService.java:473`)로만 만들 수 있다.

### (a) 실배송 일반 구매 입찰 주문 — 끝까지 진행되지 않는다
- 주문 상태 `PREPARING`. `completeOrder`의 204행 `order.updateStatus(COMPLETED)`에서 `PREPARING→COMPLETED`가 전이표에 없어 `Xxc76StatusException` → `Xpb98Exception(ORDER_NOT_FOUND_FOR_SHIPMENT, "주문 완료 처리 중 오류 발생…")` (`Xhx14CommandService.java:204`, `:221-228`, `Xdg64Status.java:26`).
- 결과: 판매 SOLD 처리·구매자 알림·`notifyShipmentCompleted` 모두 실행 전. 배송 DELIVERED 변경은 청크 롤백으로 저장되지 않아 배송은 `IN_TRANSIT`에 남고 다음 주기(6시간 뒤)에 같은 건이 반복해서 실패한다.
- `check-status`로 직접 호출한 경우: 컨트롤러가 `Xpb98Exception`의 status(404)로 바디 없이 응답하고, 문자열 버전은 `"Error: …"` (`Xhx14CommandController.java:80-93`, `:124-137`). 트랜잭션은 롤백된다.

### (b) 즉시 구매로 만들어진 주문 — 끝까지 진행된다 (단, 판매자 알림·입찰 완료는 없음)
- `createInstantOrder`는 주문을 `PENDING_PAYMENT`로 만들고 그대로 둔다(`Xdg64CommandService.java:241-245`, 상태 변경 호출 없음). 판매 입찰에 `assignOrder(order)`+`MATCHED` (`:279-280`), 배송 생성(`:264-271`), 결제(`:305`).
- 구매 입찰은 `order`·`sale`을 모두 채워 생성(`Xzj27CommandService.java:189-206`)되므로 `completeOrder`의 `findByOrderId`(196행)가 성공한다.
- 주문 `PENDING_PAYMENT→COMPLETED`는 허용된다 (`Xdg64Status.java:24`).
- 판매는 결제 시점에 이미 `SOLD`(`Xbf54CommandService.java:403-405`, 판매 입찰이 `findByOrderId`로 조회됨)라 `updateSaleStatusToSold`에서는 전이도 판매자 알림도 없다.
- 결과: 배송 DELIVERED, 주문 COMPLETED, 구매자 알림 2건, 판매자 알림 0건(결제 알림은 결제 때 이미 발송). 구매 입찰·판매 입찰은 `MATCHED` 그대로.
- (b)에서도 PATCH 운송장 등록은 `PENDING_PAYMENT→IN_TRANSIT` 불허로 실패하므로 배송 `IN_TRANSIT`에 도달하는 길은 `check-status` 계열뿐이다.

| | (a) 실배송 일반 구매 입찰 | (b) 즉시 구매 |
|---|---|---|
| 주문 상태(운송 전) | PREPARING | PENDING_PAYMENT |
| `→COMPLETED` | 불허(예외) | 허용 |
| 배송 DELIVERED 저장 | 롤백, 미저장 | 저장 |
| 알림 | 없음 | 구매자 2 / 판매자 0 |
| 입찰 상태 | 불변 | 불변(MATCHED) |

## 5. 실패 처리 (주기 배치)

- 스텝은 `faultTolerant().skip(Exception.class).skipLimit(50)` + `SkipListener` (`M12/config/Xqv91JobConfig.java:75-78`, `:51-52`, `:251-287`).
- 한 건의 프로세서가 예외(조회 실패, 파싱 실패, 상태 전이 불가, `completeOrder` 실패 등)를 던지면 `Xpb98Exception`으로 감싸 재throw (`Xth19Processor.java:132-141`).
  - 그 건은 skip되어 `[Skip] 배송 상태 처리 스킵` 오류 로그만 남는다 (`Xqv91JobConfig.java:255-266`).
  - 청크 트랜잭션이 롤백되고 같은 청크의 나머지 건은 한 건씩 다시 처리되어 정상 건은 커밋된다. 롤백된 쪽은 DB에 반영되지 않는다. 실패 건은 상태가 그대로라 다음 6시간 주기에 다시 대상이 되고, 같은 이유면 계속 실패한다.
  - `completeOrder`/`notifyShipmentCompleted`가 만든 알림 행은 롤백되지만 WebSocket 실시간 전송(`Xkh73CommandService.java:57`)은 롤백되지 않는다.
  - 재처리 때 Playwright 조회가 다시 일어난다.
- skip이 50건을 넘으면 스텝이 실패하고 남은 배송은 처리되지 않는다. 예외는 스케줄러에서 `printStackTrace`로만 처리된다 (`Xpb98BatchScheduler.java:41-43`).
- 참고: `notifyShipmentCompleted` 내부 실패는 삼켜지므로(`Xkh73CommandService.java:229-235`) 그 건은 skip되지 않는다.
- 참고: 리더가 `JpaPagingItemReader`(페이지 50)인데 쓰기 단계에서 처리 대상의 상태가 `DELIVERED`로 바뀌어 조회 조건에서 빠지므로, 대상이 50건을 넘으면 다음 페이지 조회 때 일부가 건너뛰어질 수 있다. 다음 주기에 처리된다. (코드 구조상의 추론이며 실행해 확인하지는 않았다.)
