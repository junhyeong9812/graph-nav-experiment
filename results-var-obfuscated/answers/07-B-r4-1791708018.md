# 즉시 구매 처리 흐름

경로 표기: `D/` = `src/main/java/com/fream/back/domain/`. 클래스명은 소스 그대로(난독화된 이름)이고 역할을 괄호로 적는다.

- Xzj27 = 주문 입찰(OrderBid), Xdg64 = 주문(Order), Xzz58 = 판매 입찰(SaleBid), Xgg74 = 판매(Sale)
- Xbf54 = 결제(Payment), Xkh73 = 알림(Notification), Xnn94 = 창고 보관(WarehouseStorage), Xhx14 = 주문 배송(OrderShipment)

## 1. 진입 API, 처리 단계, 동기/비동기, 응답 ID

1. **진입점**: `POST /order-bids/instant`
   - 근거: `D/m16/controller/command/Xzj27CommandController.java:22` (`@RequestMapping("/order-bids")`), `:89-90` (`@PostMapping("/instant")`).
   - 요청 본문은 `Xpj49RequestDto`: `saleBidId`, `addressId`, `warehouseStorage`, `paymentRequest` (`D/m16/dto/Xpj49RequestDto.java:20-29`).
2. **컨트롤러**: 이메일을 추출하고(`Xzj27CommandController.java:92`), 결제 요청에 `userEmail`을 채우고 `orderId`를 null로 비운 뒤(`:98`, `:119-122`) `Xzj27CommandService.createInstantOrderBid`를 호출한다(`:101-107`).
3. **주문 입찰 서비스** `Xzj27CommandService.createInstantOrderBid` (`D/m16/service/command/Xzj27CommandService.java:118-149`, `@Transactional`):
   1. 입력 검증: 이메일, saleBidId, addressId, paymentRequest null 체크 (`:123`, `:154-167`).
   2. 구매자 조회 (`:126`), 판매 입찰 조회 (`:129`, `:172-184`).
      - 검증은 null 체크와 sale 연결 여부뿐이다. 판매 입찰이 이미 MATCHED인지, 구매자가 판매자 본인인지는 검사하지 않는다.
   3. `Xdg64CommandService.createInstantOrder` 호출 (`:133-139`).
   4. 반환된 주문으로 주문 입찰(Xzj27)을 만들어 저장 (`:142`, `:189-207`).
4. **주문 서비스** `Xdg64CommandService.createInstantOrder` (`D/m16/service/command/Xdg64CommandService.java:219-319`, `@Transactional`):
   주소 조회(`:238`) → 주문 저장(`:241-247`) → 결제 요청에 orderId 세팅(`:250`) → 주문 항목 생성(`:255-256`) → 배송 정보 생성(`:264-271`) → 판매 입찰 MATCHED 처리 + flush(`:279-283`) → (판매 쪽 창고 보관이면) 창고 상태 갱신(`:290-301`) → 결제 처리(`:305`).
5. **결제 서비스** `Xbf54CommandService.processPayment` (`D/m06/service/command/Xbf54CommandService.java:57-107`): 결제 유형별 결제 엔티티 생성(`:67-80`) → `notifyUsersAndUpdateSaleStatus`(`:83`)로 알림 + 판매 SOLD 처리.
6. **동기/비동기**: 전부 **동기**이며 하나의 요청 스레드, 하나의 트랜잭션(`@Transactional`)에서 끝난다.
   - Kafka는 이 경로에서 쓰이지 않는다. `Xdg64EventProducer`는 일반 결제/배송 처리 컨트롤러 `Xdg64CommandController.java:54`에서만 호출된다.
   - 알림도 같은 스레드에서 DB 저장 + WebSocket 직접 전송이다(4번 참고).
   - PortOne 결제 호출도 `RestTemplate`으로 동기 호출한다 (`D/m06/p05/Xxv33ApiClient.java` `processCardPayment`, 호출은 `Xbf54CommandService.java:179`).
7. **응답 ID**: 응답 `data`는 **주문 입찰(Xzj27, OrderBid)의 ID**이다. 주문(Order) ID가 아니다.
   - 근거: 컨트롤러가 `createInstantOrderBid(...)`의 반환값(`Xzj27`)에 `.getId()`를 호출한다 (`Xzj27CommandController.java:101-107`).
   - 변수명은 `orderId`이고 메시지도 "즉시 구매가 성공적으로 처리되었습니다"(`:109`)지만, 실제 값은 `orderBid.getId()`이다.
   - 실제 주문 ID는 응답에 포함되지 않는다.

- **9번 주문 입찰**: 결제가 끝난 뒤에 생성된다(`Xzj27CommandService.java:133-142`). 즉 결제와 알림 시점에 주문 입찰은 존재하지 않는다. `assignOrder`는 상태를 MATCHED로 만들고 `order.assignOrderBid(this)`를 호출한다(`Xzj27.java:60-80`).
- **주문 상태는 1번 이후 바뀌지 않는다**(5번 항목 참고).

## 3. 결제 수단별 결과

공통: 결제 유형은 `getResolvedPaymentType()`으로 결정된다 (`D/m06/dto/Xbf54RequestDto.java:73-80`, 서브타입 매핑 `:20-25`). 검증은 orderId 일치, 이메일 일치, `paidAmount > 0`이다(`Xbf54CommandService.java:117-146`). 결제 엔티티의 초기 상태는 `PENDING`(`D/m06/entity/Xbf54.java:43-44`)이고, 상태 전이는 `PENDING → PAID`만 허용한다(`D/m06/entity/Xbf54Status.java:10-14`).

| 결제 수단 | 동작 | 결제 상태 | 근거 |
|---|---|---|---|
| **CARD** | 저장된 결제 정보 조회 후 PortOne 카드 결제 API 호출. 응답 `status`가 `"success"`일 때만 `PAID`로 바꾸고 `isSuccess=true` | `"success"`면 `PAID`, 그렇지 않으면 **`PENDING` 그대로** | `Xbf54CommandService.java:157-225` (`:179`, `:203-206`) |
| **ACCOUNT** (계좌이체) | 은행명만 검증하고 PG 호출 없이 저장 | 항상 `PENDING`, `isSuccess=false` | `Xbf54CommandService.java:236-279` (`:244`, `:260`) |
| **GENERAL** (일반) | `impUid` 필수. 클라이언트가 준 값을 PG 재검증 없이 신뢰하고 즉시 `PAID` 처리 | `PAID`, `isSuccess=true` | `Xbf54CommandService.java:290-333` (`:297-299`, `:313-314`) |

**즉시 구매가 끝까지 성공하는가**: 그렇다. 결제 상태와 무관하게, 예외가 없으면 요청은 성공(HTTP 200)으로 끝난다.

- `notifyUsersAndUpdateSaleStatus`는 결제 상태를 확인하지 않고 무조건 알림 전송과 `sale → SOLD`를 수행한다 (`Xbf54CommandService.java:83`, `:383-426`). 호출은 결제 수단 분기 직후다.
- 따라서 계좌이체는 결제가 `PENDING`인데도 구매자에게 "결제가 완료되었습니다" 알림이 가고 판매는 SOLD가 된다.
- 같은 이유로 응답에 `PENDING` 결제 정보가 그대로 남아 있다. 이후 입금 확인으로 `PAID`로 바꾸는 코드는 이 경로에 없다.

**결제 대행사가 카드 결제를 실패로 응답하면**: 응답 형태에 따라 두 가지로 갈린다.

1. **PortOne 응답의 HTTP 상태가 200이 아니거나 `code != 0`인 경우**
   - 처리 위치: `Xxv33ApiClient.processCardPayment` (`D/m06/p05/Xxv33ApiClient.java`, `if (response.getStatusCode() != HttpStatus.OK || !...get("code").equals(0))` 분기). `Xdf64Exception`을 던진다.
   - 전파: `createCardPayment`에서 `Xbf54Exception`이므로 그대로 재던짐(`Xbf54CommandService.java:180-181`, `:218-219`) → `processPayment`에서 재던짐(`:89-94`) → `createInstantOrder`에서 `Xqj91Exception`(`Xdg64Exception` 하위)으로 감쌈(`Xdg64CommandService.java:305-309`) → 외부 catch에서 그대로 재던짐(`:312-314`) → `Xzj27CommandService`가 `Xdg64Exception`이면 그대로 던짐(`:212-215`).
   - 결과: 모두 `RuntimeException`(`D/global/exception/Xks43Exception.java`는 `RuntimeException` 상속, `Xdg64Exception`·`Xbf54Exception` 모두 그 하위)이다. `@Transactional`이 롤백되므로 **주문, 주문 항목, 배송, 판매 입찰 MATCHED, 결제, 알림 모두 저장되지 않는다.** 판매 입찰은 `PENDING`으로 남는다. 클라이언트는 에러 응답을 받는다.
   - 단, 통신 오류(`RestClientException`)는 `Xbf54ApiException`이 되어 `@Retryable`(3회)의 대상이다. `Xdf64Exception`은 대상이 아니다 (`Xxv33ApiClient.java:25-29`, `:89-91`).
2. **HTTP 200 + `code == 0`인데 응답 `status`가 `"success"`가 아닌 경우** (예: PG가 `failed`, 또는 실제 PortOne이 쓰는 `paid`)
   - 예외가 나지 않는다. 카드 결제 엔티티는 `PENDING`/`isSuccess=false`로 저장된다 (`Xbf54CommandService.java:203-208`).
   - 이어서 알림 전송과 `sale → SOLD`가 그대로 실행된다. 즉 **실패한 카드 결제인데도 즉시 구매는 성공으로 끝난다.**
   - 코드가 비교하는 값이 `"success"` 하나뿐이므로, PortOne이 성공을 `"paid"`로 돌려주는 경우에도 결제는 `PENDING`으로 남는다(코드 기준 사실).

## 4. 알림: 누가, 무엇을, 언제, 어떻게

**수신자와 내용** (`Xbf54CommandService.sendNotifications`, `:434-462`; 호출은 `:403` 또는 `:416`):

- **구매자**: "결제가 완료되었습니다. 주문 ID: {orderId}" (`:438-443`)
- **판매자**(`sale.getSeller()`): "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}" (`:447-455`)
- 두 알림 모두 카테고리 `Xzv64.SHOPPING`, 타입 `Xkh73Type.BID` (`D/m15/entity/Xzv64.java:5`, `D/m15/entity/Xkh73Type.java:7`).
- 별도 이메일/푸시/Kafka 알림은 없다. 이 경로에서 알림은 이 두 건뿐이다.

**시점**: 결제 엔티티 생성 직후, 같은 요청과 트랜잭션 안이다. 판매를 `SOLD`로 바꾸기 *전*이며(`:416-419`), 주문 입찰 생성 *전*이다. 즉 알림이 만들어진 시점에 `Xzj27`은 아직 없다.

**전달 방식** (`D/m15/service/command/Xkh73CommandService.java:44-67`, `:303-323`):

1. DB에 알림 엔티티를 저장한다 (`:52-53`). 읽지 않음 상태다.
2. 수신자의 Redis 키 `WebSocket:Xrd81:{email}`가 있을 때만(접속 중일 때) STOMP로 `convertAndSendToUser(email, "/queue/notifications", dto)`를 보낸다 (`:37-38`, `:307-313`).
3. 접속 중이 아니면 DB에만 남고 실시간 전송은 하지 않는다 (`:320-322`).

**실패 처리**: 알림 실패는 삼킨다(`Xbf54CommandService.java:457-461`, `:421-425`). 구매 자체는 실패하지 않는다. 다만 알림 서비스 쪽에서 `@Transactional` 프록시를 통해 예외가 던져졌다면 외부 트랜잭션이 rollback-only로 표시될 수 있다. 이 부분은 코드만으로는 확정하지 않았다.

## 5. 최종 주문 상태와 "창고 보관" 선택의 영향

**최종 주문 상태는 `PENDING_PAYMENT`이다.**

- 즉시 구매 경로에서 주문 상태는 생성 시 `PENDING_PAYMENT`로 정해지고(`Xdg64CommandService.java:244`), 이후 `order.updateStatus(...)`를 한 번도 호출하지 않는다 (`createInstantOrder` 전체 `:219-319`, `Xbf54CommandService` 전체에 `order.updateStatus` 호출 없음).
- 결제가 `PAID`여도(GENERAL, 성공한 CARD) 주문은 `PAYMENT_COMPLETED`/`PREPARING`으로 넘어가지 않는다. 그 전이를 하는 코드는 일반 결제·배송 처리 `processPaymentAndShipment`(`:111-202`)와 Kafka 컨슈머(`D/m16/service/kafka/Xdg64EventConsumer.java:192-195`)에만 있고, 즉시 구매는 거치지 않는다.
- 이름은 "즉시 구매 완료"지만 주문 상태가 `PENDING_PAYMENT`로 남는 것이 실제 동작이다. 판매 입찰은 `MATCHED`, 판매는 `SOLD`, 주문 입찰은 `MATCHED`이다.

**구매자가 "창고 보관"을 선택한 경우: 아무것도 달라지지 않는다.**

- `warehouseStorage` 값은 컨트롤러에서 로그로 쓰고(`Xzj27CommandController.java:94-95`) 서비스로 전달된다(`:104`, `Xzj27CommandService.java:135-137`). `createInstantOrder`의 파라미터 `isWarehouseStorage`(`Xdg64CommandService.java:221`)는 **본문 어디에서도 읽히지 않는다** (`:222-318`).
- 그 결과 구매자용 창고 보관 엔티티 생성(`createOrderStorage`), 주문 상태 `IN_WAREHOUSE`/`COMPLETED` 전이, `assignWarehouseStorage`는 일어나지 않는다. 이 동작은 일반 경로 `processPaymentAndShipment`(`:163-172`)에만 있다.
- 창고 보관 여부에 따라 달라지는 것은 **판매자 쪽** `sale.isWarehouseStorage()`뿐이다. 이 값이 true이면 판매자 창고 보관 건의 상태가 `ASSOCIATED_WITH_ORDER`가 된다 (`:290-294`).
- 배송 정보는 항상 만들어진다(`:264-271`). 창고 보관을 선택해도 배송 정보 생성은 건너뛰지 않는다.

## 요약: 문서/이름이 말하는 것과 실제 동작이 다른 지점

1. 응답의 `orderId`는 실제로는 **주문 입찰 ID**이다.
2. 구매자의 `warehouseStorage` 요청값은 **무시된다**.
3. 계좌이체는 결제 `PENDING`인 채로 "결제 완료" 알림 + 판매 `SOLD` + 요청 성공 처리된다.
4. 카드 PG 응답이 `code=0`이면서 `status != "success"`이면 결제는 `PENDING`인 채 성공 처리된다. `code != 0`일 때만 전체가 롤백된다.
5. 주문은 끝까지 `PENDING_PAYMENT`이다.
