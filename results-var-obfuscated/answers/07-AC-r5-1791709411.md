# 즉시 구매(POST /order-bids/instant) 처리 분석

경로 약어: `D` = `src/main/java/com/fream/back/domain`

## 1. 진입 API · 처리 단계 · 동기/비동기 · 응답 ID

1. 진입점: `POST /order-bids/instant` → `Xzj27CommandController#createInstantOrderBid`
   (`D/m16/controller/command/Xzj27CommandController.java:22`, `:89-110`). 클래스 base path `/order-bids`는 `:22`.
2. 컨트롤러 단계 (`Xzj27CommandController.java:92-107`)
   - 로그인 이메일 추출 `SecurityUtils.extractAndValidateEmailForOrderBid` (`:92`).
   - `enrichPaymentRequest`가 결제 요청의 `userEmail`을 로그인 이메일로 덮어쓰고 `orderId`를 null로 비운다 (`:119-123`).
   - `Xzj27CommandService#createInstantOrderBid(email, saleBidId, addressId, warehouseStorage, paymentRequest)` 호출 (`:101-107`).
3. 서비스 `Xzj27CommandService#createInstantOrderBid` (`D/m16/service/command/Xzj27CommandService.java:118-149`, `@Transactional` `:118`)
   - 입력 검증: 이메일, saleBidId, addressId, paymentRequest null 여부 (`:154-167`).
   - 구매자 조회 `userQueryService.findByEmail` (`:126`).
   - 판매 입찰 조회·검증 `getSaleBidAndValidate`: 존재 여부와 연결된 sale 존재 여부만 확인한다 (`:172-184`). 판매 입찰의 상태(PENDING 여부)는 검사하지 않는다.
   - `Xdg64CommandService#createInstantOrder` 호출 (`:133-139`).
   - 반환된 주문으로 주문 입찰(Xzj27)을 새로 만들어 저장 (`:142`, `:189-207`).
4. `Xdg64CommandService#createInstantOrder` (`D/m16/service/command/Xdg64CommandService.java:219-319`, `@Transactional` `:219`) 내부 순서
   1. 배송지 조회 `addressQueryService.getAddress(email, addressId)` (`:238`)
   2. 주문 저장 (`:241-247`)
   3. 결제 요청에 `orderId` 세팅 (`:250`)
   4. 주문 항목 생성 (`:255-256`)
   5. 주문 배송 정보 생성 (`:264-271`)
   6. 판매 입찰에 주문 연결 + MATCHED + flush (`:279-283`)
   7. 판매자가 창고 보관 판매였다면 창고 상태 갱신 (`:291-294`)
   8. 결제 처리 `paymentCommandService.processPayment` (`:305`)
5. **동기 처리**다. Kafka 이벤트나 `@Async`가 없고 하나의 DB 트랜잭션 안에서 결제 대행사(PortOne) 호출까지 끝낸다.
   - 결제 대행사 호출은 `RestTemplate.exchange`를 동기로 호출한다 (`D/m06/p05/Xxv33ApiClient.java:266`).
   - `Xdg64EventProducer`/`Xdg64EventConsumer`(Kafka)는 `/orders/{id}/process-payment-shipment` 경로 전용이며 이 경로에서 호출하지 않는다.
6. **응답 ID는 주문 입찰(Xzj27, order bid)의 ID이지 주문(Xdg64) ID가 아니다.**
   - 컨트롤러는 `createInstantOrderBid(...).getId()`의 반환값을 `orderId`라는 변수에 담아 돌려준다 (`Xzj27CommandController.java:101-109`).
   - 서비스가 반환하는 것은 `Xzj27`(주문 입찰) 엔티티다 (`Xzj27CommandService.java:142-144`, `:206`).
   - 변수명과 메시지는 "orderId"·"즉시 구매가 성공적으로 처리되었습니다"라고 하지만 실제 값은 order-bid ID다. 주문 ID는 응답에 없다.

   - 직후 `entityManager.flush()` (`Xdg64CommandService.java:283`).
2. **창고 보관 `Xnn94`**(판매자가 창고 보관으로 올린 판매인 경우만): `IN_STORAGE` → `ASSOCIATED_WITH_ORDER`
   - `sale.isWarehouseStorage()`가 true일 때만 `updateWarehouseStatus(sale, ASSOCIATED_WITH_ORDER)` (`Xdg64CommandService.java:291-294`, `D/m07/service/command/Xnn94CommandService.java:117-133`).
   - 판매에 연결된 창고 레코드가 없으면 `Xnx94Exception`이 나고(`D/m07/service/query/Xnn94QueryService.java:30-33`) `Xdx92Exception`으로 바뀌어 전체 롤백된다 (`Xdg64CommandService.java:295-300`).
3. **결제 `Xbf54`**: 생성 시 기본값 `PENDING` (`D/m06/entity/Xbf54.java:44`). 이후 상태는 3번 참조.
4. **판매 `Xgg74`**: (판매자가 올린 상태, 보통 `PENDING_SHIPMENT`) → `SOLD`
   - 결제 처리 끝에 `notifyUsersAndUpdateSaleStatus`가 실행된다 (`Xbf54CommandService.java:83`).
   - 이 시점에 `order.getOrderBid()`는 아직 null이다. 주문 입찰은 이후에 만들어진다 (`Xzj27CommandService.java:142`). 따라서 `saleBidQueryService.findByOrderId`로 판매 입찰을 찾는 분기로 간다 (`Xbf54CommandService.java:388-406`).
   - 알림 전송 후 `sale.updateStatus(SOLD)` (`Xbf54CommandService.java:403-404`).
   - `Xgg74#updateStatus`는 `canTransitionTo` 검증 없이 값을 바로 대입하므로 어떤 상태에서든 SOLD가 된다 (`D/m10/entity/Xgg74.java:73-75`). 판매 시작 상태가 `PENDING_SHIPMENT`면 `Xgg74Status#canTransitionTo`상 SOLD로 갈 수 없지만(`D/m10/entity/Xgg74Status.java:17`) 우회된다.
5. **주문 입찰 `Xzj27`**: 생성 시 builder에서 `MATCHED` (`Xzj27CommandService.java:196`). `assignOrder`도 MATCHED로 설정한다 (`D/m16/entity/Xzj27.java:60-82`, `:75`). 이후 `markAsInstantPurchase()` (`Xzj27CommandService.java:205`).
6. **주문 `Xdg64`**: 이 경로에서는 **상태를 바꾸지 않는다**. 생성 시 `PENDING_PAYMENT`가 그대로 남는다 (5번 참조).

(`Xbf54CommandService`의 결제 처리 외에 `notify...`는 try/catch로 예외를 삼키므로, 알림·SOLD 처리에서 오류가 나도 결제와 주문 생성은 롤백되지 않는다. `Xbf54CommandService.java:421-425`.)

## 3. 결제 수단별 결과 · 성공 여부 · 카드 실패 응답

분기는 `Xbf54CommandService#processPayment`의 switch다 (`Xbf54CommandService.java:67-80`). 판별은 DTO 하위 타입(`paymentType`: CARD/ACCOUNT/GENERAL)으로 한다 (`D/m06/dto/Xbf54RequestDto.java:25-38`).

| 수단 | 처리 | 결제 상태 | 근거 |
|---|---|---|---|
| CARD | 저장된 카드 정보 조회 → PortOne `processCardPayment` 호출 → 응답 `status=="success"`일 때만 `PAID` | 성공 시 `PAID`·`isSuccess=true`, 그 외 기본 `PENDING` | `Xbf54CommandService.java:166`, `:179`, `:203-206` |
| ACCOUNT (계좌이체) | 은행명만 검증하고 외부 호출 없이 저장 | 항상 `PENDING` | `Xbf54CommandService.java:244`, `:260`, `:262` |
| GENERAL (일반) | `impUid`가 있으면 외부 검증 없이 클라이언트 값 그대로 저장 | 즉시 `PAID`·`isSuccess=true` | `Xbf54CommandService.java:297-314` |

공통 사항
- 결제 금액은 `paidAmount > 0`만 검증한다. 판매 입찰가와의 일치 여부는 확인하지 않는다 (`Xbf54CommandService.java:142-145`). 주문 `totalAmount`는 판매 입찰가다 (`Xdg64CommandService.java:243`).
- 계좌이체가 `PENDING`이어도 `processPayment`는 정상 반환하고, 알림 전송과 판매 SOLD 처리를 그대로 진행한다 (`Xbf54CommandService.java:83`). 입금 확인을 기다리지 않는다.

**즉시 구매는 끝까지 성공하는가**
- 예외가 없으면 끝까지 진행된다. 계좌이체(`PENDING`)도, 카드 응답이 success가 아닌 경우도 마찬가지다. 그 결과 응답은 "성공" 메시지가 된다 (`Xzj27CommandController.java:109`).
- 결제가 실제로 완료되었는지(`PAID`)와 무관하게 판매 입찰 MATCHED, 판매 SOLD, 주문 입찰 MATCHED가 이루어진다.

**결제 대행사가 카드 결제를 실패로 응답하면**
- (a) HTTP 상태가 200이 아니거나 응답 `code`가 0이 아닌 경우
  - `Xdf64Exception("카드 결제 요청 실패: ...")` 발생 (`Xxv33ApiClient.java:270-274`).
  - 이 예외는 `Xbf54Exception` 하위라서 `createCardPayment`에서 그대로 재전파된다 (`Xbf54CommandService.java:218-219`). `processPayment`도 재전파한다 (`:89-94`).
  - `createInstantOrder`가 `Xqj91Exception`("결제 처리 중 오류")으로 감싼다 (`Xdg64CommandService.java:306-309`). 이는 `Xdg64Exception` 하위이므로 `Xzj27CommandService`가 그대로 던진다 (`Xzj27CommandService.java:212-215`).
  - 모두 RuntimeException(`Xks43Exception extends RuntimeException`, `D/../global/exception/Xks43Exception.java:10`)이고 같은 트랜잭션이라 **주문·배송·주문 항목·판매 입찰 MATCHED 변경이 전부 롤백**된다. 알림도 이 단계 전에는 생성되지 않는다 (알림은 결제 저장 이후, `Xbf54CommandService.java:83`).
  - 클라이언트는 에러 응답을 받는다.
- (b) HTTP 200이고 `code==0`이지만 응답의 `status`가 `"success"`가 아닌 경우 (예: 대행사가 `failed`를 본문에 담는 경우)
  - 예외가 나지 않는다. 카드 결제가 `PENDING`, `isSuccess=false`로 저장된다 (`Xbf54CommandService.java:187-208`, `Xbf54.java:39`, `:44`).
  - 이후 알림("결제가 완료되었습니다")과 판매 SOLD 처리까지 진행되고 응답은 성공이다. 즉 실패한 카드 결제가 성공으로 처리되는 코드 경로다.
  - 이 경로가 실제 PortOne 응답과 일치하는지는 외부 서비스 동작이라 코드만으로 확인할 수 없고, 코드상 가능하다는 점만 확인했다.

## 4. 알림 수신자 · 시점 · 전달 방식

1. 수신자와 내용 (`Xbf54CommandService#sendNotifications`, `Xbf54CommandService.java:434-462`)
   - 구매자 (`order.getUser()`): `"결제가 완료되었습니다. 주문 ID: {orderId}"` (`:438-443`)
   - 판매자 (`sale.getSeller()`): `"구매자가 결제를 완료하였습니다. 판매 ID: {saleId}"` (`:449-454`)
   - 둘 다 카테고리 `Xzv64.SHOPPING`, 타입 `Xkh73Type.BID`.
   - 그 외 수신자는 없다. 판매자 쪽은 `sale.getSeller()`가 null이면 건너뛴다 (`:447-448`).
2. 시점
   - 결제 객체를 저장한 직후, 판매를 `SOLD`로 바꾸기 직전이다 (`Xbf54CommandService.java:83`, `:403-404`).
   - 결제가 `PENDING`(계좌이체·카드 실패 응답)이어도 같은 메시지가 나간다.
   - 결제가 예외로 실패하면 알림은 나가지 않는다.
   - 즉시구매 경로에서 호출되는 `Xgg74CommandService#createInstantSale`의 판매자 알림은 이 흐름과 무관하다 (`/sale-bids/instant` 경로).
3. 방식 (`Xkh73CommandService#createNotification`, `D/m15/service/command/Xkh73CommandService.java:44-67`)
   - 동기 처리다. 알림 엔티티를 DB에 저장한다 (`:52-54`). 같은 트랜잭션이므로 이후 롤백되면 알림도 사라진다.
   - 이어서 `sendRealTimeNotification`이 Redis에 해당 사용자 WebSocket 연결 키가 있을 때만 STOMP `convertAndSendToUser`로 실시간 푸시한다 (`:57`, `:303-323`). 연결 키가 없으면 저장만 하고 푸시는 하지 않는다 (`:320-322`).
   - Kafka `notification-topic`은 사용하지 않는다. 그 토픽은 `Xdg64EventConsumer`(비동기 주문 처리 경로)에서만 쓰인다.
   - 알림 전송 실패는 warn 로그만 남기고 삼킨다 (`Xbf54CommandService.java:457-461`).

## 5. 주문의 최종 상태 · 창고 보관 선택 시 차이

1. **처리 완료 후 주문(Xdg64)의 최종 상태는 `PENDING_PAYMENT`다.**
   - 주문은 `PENDING_PAYMENT`로 생성되고 (`Xdg64CommandService.java:244`) 이 경로 어디에서도 `order.updateStatus(...)`를 호출하지 않는다.
   - `Xbf54CommandService#processPayment`와 `notifyUsersAndUpdateSaleStatus`도 주문 상태를 바꾸지 않는다 (`Xbf54CommandService.java:57-107`, `:383-426`).
   - 결제가 `PAID`인 일반 결제나 성공한 카드 결제여도 마찬가지다. 응답 메시지는 "성공적으로 처리"라고 하지만 주문은 결제 완료(`PAYMENT_COMPLETED`), `PREPARING`, `COMPLETED`로 가지 않는다.
   - 주문 상태를 `PAYMENT_COMPLETED` → `PREPARING` → (`IN_WAREHOUSE` → `COMPLETED`)로 올리는 코드는 `processPaymentAndShipment`뿐이다 (`Xdg64CommandService.java:163-177`). 이는 별도 엔드포인트 `/orders/{orderId}/process-payment-shipment`용이다.
2. 연관 상태 최종값
   - 판매 입찰: `MATCHED`
   - 판매: `SOLD`
   - 주문 입찰: `MATCHED`
   - 결제: 일반 `PAID` / 카드 성공 `PAID` / 계좌이체·카드 non-success `PENDING`
   - 배송(Xhx14): `PENDING`
3. **구매자가 `warehouseStorage=true`를 선택해도 달라지는 것이 없다.**
   - 컨트롤러가 로그만 찍고 값을 서비스로 전달한다 (`Xzj27CommandController.java:94-95`, `:104-105`).
   - `Xzj27CommandService`는 `isWarehouseStorage`를 `createInstantOrder`에 넘기지만 (`Xzj27CommandService.java:133-139`), `createInstantOrder` 본문에서 이 파라미터를 읽는 곳이 없다 (`Xdg64CommandService.java:220-319`).
   - 창고 관련 분기(`:292`)는 구매자의 선택이 아니라 판매자가 판매 등록 시 정한 `sale.isWarehouseStorage()`(`D/m10/entity/Xgg74.java:43`)로 결정된다.
   - 구매자용 창고 보관 `Xnn94`가 새로 만들어지지 않고, 주문 상태도 `IN_WAREHOUSE`/`COMPLETED`로 바뀌지 않는다. 배송 정보(Xhx14)는 창고 선택과 무관하게 항상 생성된다 (`Xdg64CommandService.java:264-271`).
   - 구매자가 창고 보관을 선택했을 때 창고 보관과 `IN_WAREHOUSE`가 반영되는 곳은 `processPaymentAndShipment`뿐이다 (`:163-172`).
