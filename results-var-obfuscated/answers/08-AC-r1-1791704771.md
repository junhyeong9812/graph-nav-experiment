## 사전: 결제 후 상태 (질문의 전제)

- 결제·배송 처리 API(`POST /orders/{orderId}/process-payment-shipment`)는 Kafka 이벤트만 발행하고 202를 돌려준다 (`src/main/java/com/fream/back/domain/m16/controller/command/Xdg64CommandController.java:43-55`). 실제 처리는 `Xdg64EventConsumer#processCompleteOrder`다.
- 배송 정보는 `createOrderShipment`이 `Xpb98Status.PENDING`으로 만든다 (`S:67`).
- 일반 구매 입찰, 실배송(창고 보관 아님): 주문은 `PENDING_PAYMENT → PAYMENT_COMPLETED → PREPARING`에서 멈춘다 (`src/main/java/com/fream/back/domain/m16/service/kafka/Xdg64EventConsumer.java:195`, `:216-217`). `PREPARING`이 최종 상태다.
  - 주문 입찰(Xzj27)은 `createAndSaveOrderBid`에서 `assignOrder`로 MATCHED가 된다 (`src/main/java/com/fream/back/domain/m16/entity/Xzj27.java:75`). `sale`은 null이다 (`src/main/java/com/fream/back/domain/m16/service/command/Xzj27CommandService.java:91-97`).
  - 이 주문에 연결된 판매 입찰(Xzz58)은 없다.
- 즉시 구매(`POST /order-bids/instant`): `createInstantOrder`가 주문을 `PENDING_PAYMENT`로 만들고 배송(PENDING)을 붙인다 (`src/main/java/com/fream/back/domain/m16/service/command/Xdg64CommandService.java:241-245`, `:264`).
  - 판매 입찰에 `assignOrder`를 하고, 결제를 호출한다 (`:279-280`, `:305`).
  - 이 경로에는 주문 상태를 바꾸는 코드가 없어, 주문은 `PENDING_PAYMENT`로 남는다.
  - 주문 입찰은 MATCHED이고 `order`와 `sale`이 채워지며 `isInstantPurchase=true`다 (`Xzj27CommandService.java:192-205`).

## 1. 운송장 등록 요청

### 1-1. 어느 API인가

- `PATCH /shipments/order/{shipmentId}/status` (`C:20`, `C:33-34`). 본문은 `Xhx14RequestDto`(courier, trackingNumber)이고 `Xhx14CommandService#updateTrackingInfo`를 호출한다 (`C:41`, `S:239`).
- 운송장 등록과 즉시 상태 조회를 겸하는 `POST /shipments/order/{id}/check-status`와 `/check-status-string`도 있다 (`C:58`, `C:103` → `S:452`).
- 운영(관리자) 전용을 강제하는 코드는 없다. `SecurityConfig`는 `anyRequest().authenticated()`뿐이다 (`src/main/java/com/fream/back/global/config/security/SecurityConfig.java:51-52`).

### 1-2. 의도된 상태 변경 순서와 알림 (`S:239-303`)

1. courier·trackingNumber가 비어 있으면 `TRACKING_INFO_REQUIRED` (`S:243-246`).
2. 배송(Xhx14) 조회 후 `shipment.updateTrackingInfo`. 택배사·운송장을 넣고 상태를 **전환 검사 없이 `IN_TRANSIT`으로 직접 대입**한다 (`S:256`, `H:41-45`).
3. 주문(Xdg64) → `IN_TRANSIT` (`S:260`).
4. 구매자에게 알림 1건: "상품이 출발하였습니다. 주문 ID" (`S:265-271`).
5. `updateSaleStatusToSold(orderId)` (`S:276`).
   - 판매 입찰의 판매(Xgg74)가 `SOLD`가 될 수 있으면 `SOLD`로 바꾼다 (`S:116-123`).
   - 창고 보관이면 창고 상태를 갱신한다 (`S:126-128`).
   - 판매자에게 알림: "판매 완료되었습니다" (`S:132-138`).
   - 주문 입찰 쪽 sale도 같은 방식으로 처리한다 (`S:151-170`).
6. 창고 보관이면 창고 상태를 한 번 더 `SOLD`로 갱신한다 (`S:279-286`).
7. `updateOrderAndSaleBidStatusToCompleted` (`S:289`). 주문 입찰과 판매 입찰이 MATCHED이면 **COMPLETED**로 바꾼다 (`S:422-432`).
   - 즉, 의도된 코드는 배송 완료가 아니라 **운송장 등록 시점**에 입찰을 COMPLETED로 만든다.
   - 이 메서드의 `@Transactional`은 private이라 효과가 없고, 예외는 삼킨다 (`S:412-413`, `S:436-439`).

### 1-3. 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문(즉시 구매 아님)은 끝까지 성공하나? → **실패한다**

- **어디서**: `S:260`의 `order.updateStatus(Xdg64Status.IN_TRANSIT)`.
- **왜**:
  - 주문은 `PREPARING`이다.
  - `PREPARING`에서 허용되는 전이는 `IN_WAREHOUSE`, `SHIPMENT_STARTED`뿐이다 (`OS:26`).
  - `IN_TRANSIT`은 `SHIPMENT_STARTED`에서만 갈 수 있다 (`OS:28`).
  - `Xdg64#updateStatus`가 `Xxc76StatusException`을 던진다 (`O:113-121`).
- **예외 변환**:
  - `Xxc76StatusException`은 `Xdg64Exception` 계열이라 `Xpb98Exception`이 아니다.
  - `S:293-302`의 `catch (Exception)`이 `Xpb98Exception(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")`으로 감싸 던진다.
- **저장되는 것**: 없다.
  - `@Transactional` 메서드(`S:238`)가 RuntimeException으로 끝나 전체가 롤백된다.
  - 배송의 courier·trackingNumber·IN_TRANSIT 대입(`S:256`)도 DB에 남지 않는다.
  - 구매자 알림(`S:266`)은 `S:260` 이후라 만들어지지 않았다. 입찰·판매 상태도 그대로다.
  - 배송은 `PENDING`, 운송장 없음, 주문은 `PREPARING`으로 남는다.
- **응답**:
  - 컨트롤러는 예외를 잡지 않는다 (`C:33-47`).
  - `Xks43ExceptionHandler#handleShipmentException`이 `ErrorResponse`를 돌려준다 (`src/main/java/com/fream/back/global/exception/Xks43ExceptionHandler.java:459-473`).
  - 코드는 `S001`, 메시지는 "배송 정보를 찾을 수 없습니다.", HTTP **404** (`src/main/java/com/fream/back/domain/m12/exception/Xpb98ErrorCode.java:12`).
  - 메시지가 "배송 없음"이라 실제 원인(주문 상태 전이 불가)은 응답에 드러나지 않고 로그에만 남는다.
- 즉시 구매 주문(`PENDING_PAYMENT`)도 같은 이유로 실패한다. `PENDING_PAYMENT`에서는 `PAYMENT_COMPLETED`, `COMPLETED`, `IN_WAREHOUSE`만 허용된다 (`OS:24`).
- 부가: `/check-status`는 주문을 `IN_TRANSIT`으로 바꾸지 않는다. 대신 아래 4항의 문제가 있다.

## 2. 배송 완료 감지

### 2-1. 누가·언제·어떻게

- 사람이 호출하는 `check-status` API는 요청 시점에 즉시 조회한다 (`C:58`, `C:103`).
- 자동 감지는 스케줄러 `Xpb98BatchScheduler#scheduleShipmentStatusJob`이 Spring Batch Job `updateShipmentStatusesJob`을 실행하는 것이다 (`src/main/java/com/fream/back/global/config/Xpb98BatchScheduler.java:34-40`).
  - `@Scheduled`는 `Xwv44Scheduler` 등 다른 클래스의 `@EnableScheduling`으로 활성화된다. `@EnableBatchProcessing`은 `Xct70Config`에 있다.
  - 예외는 `printStackTrace`로만 처리한다 (`Xpb98BatchScheduler.java:41-43`).

### 2-2. 주기·대상·실제 처리 코드

- **주기**: cron `0 0 */6 * * *`, 즉 **6시간마다** 정각(00, 06, 12, 18시) (`Xpb98BatchScheduler.java:34`).
- **대상**: `SELECT s FROM Xhx14 s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL` (`J:95`).
  - pageSize와 chunk는 50, skipLimit은 50이다 (`J:51-52`, `J:67`, `J:76-77`).
  - `PENDING`인 배송은 대상이 아니다.
- **실제로 실행되는 코드**: `Xth19Processor#process` (`P:57`).
  - Step이 `new Xth19Processor(playwrightBrowserManager(), notificationService, orderService)`를 processor로 쓴다 (`J:69-73`).
  - Playwright로 페이지를 열어 `tbody#statusDetail tr`의 마지막 행 5번째 td를 읽는다 (`P:72-94`, `P:167-191`).
- **같은 일을 하지만 실행되지 않는 코드**:
  - `Xqv91JobConfig#shipmentItemProcessor` (`J:106`). `@Bean`이지만 Step에 연결되지 않았다.
  - `Xhx14CommandService#updateShipmentStatuses` (`S:309`). 호출하는 곳이 없다.
  - `Xqv91JobConfig#parseCjLogisticsStatus`(Jsoup, `J` 내 private)는 호출되지 않는다.
  - `Xxx20#getCurrentTrackingStatus`는 `check-status` API 경로(`S:477`)에서만 쓰인다.

### 2-3. 택배사 상태 문자열 → 내부 상태

`mapToShipmentStatus` (`P:220-225`; 동일 코드가 `S:399-405`, `J:228-233`에도 있음).

| 문자열 (정확히 일치) | 내부 상태 |
|---|---|
| `"배송완료"` | `DELIVERED` |
| `"배송출발"` | `OUT_FOR_DELIVERY` |
| 그 외 전부 | `IN_TRANSIT` |

- 상태 전이 규칙은 `Xpb98Status`에 있다 (`src/main/java/com/fream/back/domain/m12/entity/Xpb98Status.java`).
  - `IN_TRANSIT`은 `OUT_FOR_DELIVERY`, `DELAYED`, `CANCELED`, `DELIVERED`로 갈 수 있다.
  - `OUT_FOR_DELIVERY`는 `DELIVERED`, `FAILED_DELIVERY`, `CANCELED`로 갈 수 있다.
  - `OUT_FOR_DELIVERY → IN_TRANSIT`은 불가다.
- 현재 상태와 매핑 결과가 같으면 아무것도 하지 않고 반환한다 (`P:101-105`).

## 3. 배송 완료 판정 이후 (Xth19Processor 기준)

실행 순서 (`P:108-118`):

1. 배송(Xhx14) `IN_TRANSIT/OUT_FOR_DELIVERY → DELIVERED` (`P:113`).
2. `orderService.completeOrder(orderId)` (`P:116` → `S:190-229`).
   1. 주문 입찰 조회, 없으면 예외 (`S:196-197`).
   2. 주문(Xdg64) → `COMPLETED` (`S:204`).
   3. `updateSaleStatusToSold` (`S:208`).
      - 판매 입찰 → sale `SOLD`, 창고 보관이면 창고 `SOLD` (`S:116-128`).
      - 판매자 알림 (`S:132-138`).
      - 주문 입찰 쪽 sale 처리 (`S:151-170`).
   4. 구매자 알림 "[completeOrder] 주문이 완료 처리되었습니다" (`S:211-217`).
3. `notificationService.notifyShipmentCompleted(order)`. 구매자 알림 "[배송 완료] …" (`P:117`, `src/main/java/com/fream/back/domain/m15/service/command/Xkh73CommandService.java:219-229`). 이 안의 예외는 삼킨다 (`:230-233`).
4. Writer(`JpaItemWriter`)가 배송을 저장한다 (`J:239-246`).

**알림 건수** (즉시 구매 주문 기준 정상 진행 시):

- 구매자 **2건**: "[completeOrder]" 1건과 "[배송 완료]" 1건.
- 판매자 **1건**: "판매 완료되었습니다".
  - 판매 입찰 경로에서 sale이 `SOLD`로 바뀌면, 주문 입찰 경로는 같은 sale이 `canTransitionTo(SOLD) == false`(`Xgg74Status`: `SOLD → false`)라 알림을 중복 생성하지 않는다 (`S:156`).
  - sale 상태가 `ON_AUCTION`/`SELLING`이 아니면 `SOLD` 전환이 일어나지 않으므로, 이 경우 판매자 알림은 0건이다 (`src/main/java/com/fream/back/domain/m10/entity/Xgg74Status.java`).
- `check-status` API 경로(`S:483-489`)는 `completeOrder`만 호출하므로 구매자 알림은 1건이다.

**입찰 상태**:

- 배송 완료 경로의 어디에도 주문 입찰(Xzj27)·판매 입찰(Xzz58)의 `COMPLETED` 변경이 없다.
- `completeOrder`와 `updateSaleStatusToSold`는 입찰 상태를 건드리지 않는다.
- 입찰을 COMPLETED로 바꾸는 코드(`S:412-432`)는 운송장 등록 경로(`S:289`)에서만 호출된다.
- 따라서 배송 완료 후에도 두 입찰은 `MATCHED` 그대로다. 변경되는 것은 판매(Xgg74)의 `SOLD`뿐이다.

## 4. 주문 종류별 차이

두 경우 모두 배송을 `IN_TRANSIT/OUT_FOR_DELIVERY` + 운송장 있음 상태로 만드는 것이 선행되어야 배치 대상이 된다. 그런데 1항의 `PATCH` 경로는 전 종류에서 롤백되어 배송이 `PENDING`에 머문다. 남는 진입로는 `check-status`뿐이다.

- `check-status`에서 택배사 응답이 "배송출발"이면 `OUT_FOR_DELIVERY`로 저장된다 (`S:491-494`). 이때만 배치 대상이 된다.
- 응답이 "배송완료"이면 같은 요청 안에서 `completeOrder`를 호출한다 (`S:483-489`).
- 응답이 그 외(IN_TRANSIT)면 문제가 있다. `updateTrackingInfo`가 이미 `IN_TRANSIT`을 넣었으므로 `updateStatus(IN_TRANSIT)`은 `IN_TRANSIT → IN_TRANSIT` 전이 불가로 `IllegalStateException`이 된다 (`S:473`, `S:497`, `H:47-54`, `Xpb98Status` IN_TRANSIT 항목). 이는 `EXTERNAL_TRACKING_SERVICE_ERROR`(503)로 감싸지고 롤백된다 (`S:507-514`).

### (a) 실배송 일반 구매 입찰 주문 (주문 `PREPARING`, 판매 입찰 없음): **끝까지 진행되지 않는다**

- `completeOrder` 안에서 `order.updateStatus(COMPLETED)`가 `PREPARING → COMPLETED` 불가로 `Xxc76StatusException`을 던진다 (`S:204`, `OS:26`).
  - `S:221-228`이 `Xpb98Exception(ORDER_NOT_FOUND_FOR_SHIPMENT)`로 변환하고, 같은 트랜잭션이 롤백된다.
- 설령 주문이 `IN_TRANSIT`이었더라도 다음 지점에서 실패한다.
  - `Xzz58QueryService#findByOrderId`는 없으면 null이 아니라 `IllegalArgumentException`을 던진다 (`src/main/java/com/fream/back/domain/m10/service/query/Xzz58QueryService.java:26-28`).
  - `updateSaleStatusToSold`의 이 호출은 try 밖이므로(`S:116`) `completeOrder`를 실패시킨다.
  - `S:117`의 `saleBid != null` 분기는 사실상 죽은 코드다.
  - 일반 입찰은 판매 입찰도 sale도 없어서 정상 경로가 없다.
- 결과:
  - 배치에서는 해당 건이 skip된다. 배송, 주문, 알림 모두 변화가 없고 다음 주기(6시간 뒤)에 같은 실패를 반복한다.
  - `check-status`는 DELIVERED 응답 시 `ORDER_NOT_FOUND_FOR_SHIPMENT`(S102, 404)를 돌려주고 롤백한다 (`C:63-72`, `Xpb98ErrorCode.java:20`). 코드는 `S:505-506`의 재던짐이고, `/check-status`는 본문 없는 404, `-string`은 "Error: …" 본문이다.

### (b) 즉시 구매 주문 (주문 `PENDING_PAYMENT`, 판매 입찰·sale 연결): **처리 코드는 끝까지 진행된다**

- 단, 배송이 `OUT_FOR_DELIVERY`/`IN_TRANSIT`+운송장 상태여야 하고, 그 상태가 되려면 `check-status`에서 "배송출발"을 받아야 한다 (위 참조).
- 진행 내용:
  - 배송 → `DELIVERED`.
  - 주문 `PENDING_PAYMENT → COMPLETED`는 허용된 전이다 (`OS:24`).
  - 판매 입찰(주문 ID로 조회됨, `S:116`)의 sale이 `ON_AUCTION`/`SELLING`이면 `SOLD`.
  - 구매자 알림 2건, 판매자 알림 1건.
- 입찰은 `MATCHED`인 채로 남는다 (3항).
- 주문이 `SHIPMENT_STARTED`/`IN_TRANSIT`을 거치지 않고 `PENDING_PAYMENT`에서 바로 `COMPLETED`가 된다. 이는 (a)와의 핵심 차이다.
- 단, sale이 이미 `SOLD`이거나 `IN_STORAGE` 등 `SOLD` 전이 불가 상태면 sale·판매자 알림은 생략되고 로그만 남는다 (`S:142-144`). 주문과 배송은 완료된다.

## 5. 실패 처리 (주기 처리 중 한 건 실패)

- Step이 `faultTolerant().skip(Exception.class).skipLimit(50)`이다 (`J:75-77`). 처리 중 예외(운송장 없음, 파싱 실패, 상태 전이 불가, `completeOrder` 실패 등)는 해당 아이템만 skip되고 Step은 계속된다.
- 프로세서는 예외를 `Xpb98Exception`으로 감싸 다시 던진다 (`P:133-146`).
- `SkipListener`가 `[Skip]` 에러 로그를 남긴다 (`J:251-287`).
- chunk 트랜잭션은 `completeOrder` 등 `@Transactional` 메서드가 같은 트랜잭션에 참여하므로, 실패 시 해당 chunk가 롤백된다.
  - 실패 건의 DB 변경(배송 상태, 주문, 알림)은 반영되지 않는다.
  - 나머지 건은 Spring Batch가 chunk를 아이템 단위로 다시 처리(scan)하여 정상 건은 커밋된다.
  - 단, WebSocket 실시간 전송은 이미 나갔을 수 있다.
