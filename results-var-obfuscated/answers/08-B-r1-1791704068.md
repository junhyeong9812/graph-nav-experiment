경로 표기: `B` = `src/main/java/com/fream/back`. 클래스명은 난독화되어 있다.
- `Xhx14` = 구매자 배송(OrderShipment, 테이블 `order_shipment`) — `B/domain/m12/entity/Xhx14.java:11`
- `Xpb98Status` = 배송 상태 enum

- `Xzj27` = 주문(구매) 입찰, `Xzz58` = 판매 입찰, `Xgg74` = 판매(Sale)

## 0. 전제: 결제 직후 상태

- 결제·배송 처리(`processPaymentAndShipment`)는 `Xhx14`를 `PENDING` 상태로 만든다. `B/domain/m12/service/command/Xhx14CommandService.java:61-68`, 호출 `B/domain/m16/service/command/Xdg64CommandService.java:148-155`.
- **(a) 실배송 일반 구매 입찰 주문:** 주문 상태가 `PENDING_PAYMENT → PAYMENT_COMPLETED → PREPARING`에서 멈춘다. `B/domain/m16/service/command/Xdg64CommandService.java:175-176`. 창고 보관(`isWarehouseStorage`)이면 `IN_WAREHOUSE → COMPLETED`까지 간다(165-172).
- **(b) 즉시 구매 주문:** `createInstantOrder`는 주문을 `PENDING_PAYMENT`로 만든 뒤 상태를 한 번도 바꾸지 않는다. `B/domain/m16/service/command/Xdg64CommandService.java:241-245`.
  - 결제(`processPayment`)도 주문 상태를 바꾸지 않는다. `B/domain/m06/service/command/Xbf54CommandService.java`에는 주문 `updateStatus` 호출이 없다.
  - 이 서비스에서 판매 입찰 상태를 바꾸는 곳은 `Xdg64CommandService.java:279-283`이다.
  - 즉시 구매 주문 입찰(`Xzj27`)은 `MATCHED` + `isInstantPurchase=true`로 만들어진다. `B/domain/m16/service/command/Xzj27CommandService.java:192-206`.
- 주문 상태 전이표: `B/domain/m16/entity/Xdg64Status.java:24-31`.
  - `PENDING_PAYMENT → {PAYMENT_COMPLETED, COMPLETED, IN_WAREHOUSE}`
  - `PREPARING → {IN_WAREHOUSE, SHIPMENT_STARTED}`
  - `SHIPMENT_STARTED → {IN_TRANSIT}`, `IN_TRANSIT → {COMPLETED}`
  - 전이가 막히면 `Xxc76StatusException`을 던진다. `B/domain/m16/entity/Xdg64.java:113-121`.
- `SHIPMENT_STARTED`로 바꾸는 코드는 코드베이스 어디에도 없다. enum 정의와 표시 문구(`B/domain/m16/controller/query/Xdg64QueryController.java:207`)뿐이다.

## 1. 운송장 등록 요청

### 1-1. 진입 API
- `PATCH /shipments/order/{shipmentId}/status`, body는 `{courier, trackingNumber}`. `B/domain/m12/controller/command/Xhx14CommandController.java:20,33-49`.
- 컨트롤러는 `Xhx14CommandService.updateTrackingInfo`를 그대로 호출하고 예외를 잡지 않는다(41-45).
- 참고: `/shipments/seller`(`B/domain/m12/controller/command/Xxn30CommandController.java:17`)는 판매자 배송용이라 구매자 배송과 무관하다.
- 참고: `POST /shipments/order/{id}/check-status`와 `/check-status-string`도 운송장을 갱신하며 즉시 조회한다(`Xhx14CommandController.java:58,103`). 이 경로는 아래 1-4에서 다룬다.

### 1-2. 코드가 의도한 상태 변경 순서 (`Xhx14CommandService.updateTrackingInfo`, `B/domain/m12/service/command/Xhx14CommandService.java:238-303`)
1. 택배사/운송장이 비어 있으면 `TRACKING_INFO_REQUIRED`(400)를 던진다(243-246).
2. 배송 `Xhx14`를 조회한다(249-253).
3. `shipment.updateTrackingInfo`로 courier·trackingNumber를 쓰고, 상태를 전이 검사 없이 `IN_TRANSIT`으로 강제 세팅한다(256). `B/domain/m12/entity/Xhx14.java:41-45`.
4. `order.updateStatus(Xdg64Status.IN_TRANSIT)`로 주문을 `IN_TRANSIT`으로 바꾼다(259-260).
5. 구매자에게 알림 "상품이 출발하였습니다. 주문 ID: …"을 보낸다(265-271).
6. `updateSaleStatusToSold(orderId)`(276), `Xhx14CommandService.java:111-183`:
   - 판매 입찰 `Xzz58` 쪽 판매(`Xgg74`)가 `SOLD`로 전이 가능하면 `SOLD`로 바꾸고 판매자에게 "판매 완료" 알림을 보낸다(116-143). 창고 보관이면 창고 상태도 갱신한다(126-129).
   - 주문 입찰 `Xzj27` 쪽 판매(`Xgg74`)도 같은 방식으로 `SOLD`로 바꾸고 판매자에게 알림을 보낸다(150-180).
7. 창고 보관 판매이면 `updateWarehouseStatusToSold`를 한 번 더 호출한다(279-286).
8. `updateOrderAndSaleBidStatusToCompleted`(289, 구현 412-440)가 주문 입찰·판매 입찰이 `MATCHED`일 때 `COMPLETED`로 바꾼다. 내부 예외는 로그만 남기고 삼킨다(436-439).
9. 이 메서드의 `@Transactional`은 `private` 메서드에 붙어 있어 실효가 없다(412). 바깥 트랜잭션에 참여할 뿐이다.

알림 요약: 구매자 1건("상품이 출발하였습니다"), 판매자 최대 2건(판매 입찰 경로 1건 + 주문 입찰 경로 1건). 두 경로가 같은 판매를 가리키면 첫 경로에서 이미 `SOLD`가 되어 둘째 경로의 `canTransitionTo(SOLD)`가 거짓이라 판매자 알림은 1건이다(156).

### 1-3. (a) 실배송 일반 구매 입찰 주문 — 끝까지 성공하지 못한다
- **실패 지점:** 4단계 `order.updateStatus(IN_TRANSIT)`, `B/domain/m12/service/command/Xhx14CommandService.java:260`.
- **이유:** 주문이 `PREPARING`이고, `PREPARING`의 허용 다음 상태는 `IN_WAREHOUSE`/`SHIPMENT_STARTED`뿐이다(`B/domain/m16/entity/Xdg64Status.java:26`). `IN_TRANSIT`은 `SHIPMENT_STARTED`에서만 갈 수 있는데 `SHIPMENT_STARTED`로 보내는 코드가 없다(0절). `Xdg64.updateStatus`가 `Xxc76StatusException`을 던진다(`B/domain/m16/entity/Xdg64.java:113-121`).
- **예외 변환:** 이 예외는 `Xpb98Exception`이 아니어서 `catch (Exception e)`에 걸린다(295). `Xpb98Exception(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")`로 감싸 다시 던진다(297-301).
- **저장되는 것: 아무것도 없다.**
  - `@Transactional`(238) 메서드가 `RuntimeException`(`B/global/exception/Xks43Exception.java`)을 던지므로 롤백된다.
  - 3단계에서 메모리상 바꾼 배송의 courier·trackingNumber·`IN_TRANSIT`도 반영되지 않는다. 배송은 `PENDING`, 운송장은 null 그대로다.
  - 4단계에서 실패하므로 구매자 알림(5단계)과 판매 처리(6~8단계)는 실행되지 않았다.
- **응답:** 컨트롤러에 try/catch가 없어 `Xks43ExceptionHandler`가 처리한다(`B/global/exception/Xks43ExceptionHandler.java:49-63`).
  - HTTP **404**, body는 `ErrorResponse(code="S001", message="배송 정보를 찾을 수 없습니다.", status=404, path)`.
  - 핸들러가 `errorCode.getMessage()`를 쓰므로 상세 메시지("…오류 발생: …")는 응답에 나가지 않는다. 에러코드는 `B/domain/m12/exception/Xpb98ErrorCode.java:12`.
  - 즉 "배송 정보를 찾을 수 없다"는 실제 원인과 무관한 오해를 부르는 응답이다.
- 창고 보관 주문(`COMPLETED`)도 `COMPLETED`는 빈 전이 집합이라 같은 이유로 실패한다(`Xdg64Status.java:31`).

### 1-4. 부가 경로 `check-status`
- `updateAndCheckShipmentStatus`(`Xhx14CommandService.java:451-516`)는 주문 상태를 `IN_TRANSIT`으로 바꾸지 않는다.
  - 택배사 조회 결과에 따라 배송만 `IN_TRANSIT`/`OUT_FOR_DELIVERY`/`DELIVERED`로 바꾼다(473-498).
  - 배송이 `DELIVERED`로 판정되면 `completeOrder`가 호출된다(489). 이 경우는 3·4절과 같다.
- 따라서 `PREPARING` 주문의 배송이 `IN_TRANSIT`이 되어 배치 대상에 들어갈 수 있는 사실상 유일한 길이 이 엔드포인트다(상태가 `DELIVERED`가 아닌 경우 커밋된다).
- (a)·(b) 주문의 배송을 배치가 집는 전제는 "`IN_TRANSIT`/`OUT_FOR_DELIVERY` + 운송장 있음"이다. 이 전제는 일반 운송장 API로는 충족되지 않는다.

## 2. 배송 완료 감지

### 2-1. 누가·언제·어떻게
- **누가:** Spring `@Scheduled` + Spring Batch. `B/global/config/Xpb98BatchScheduler.java:34-44`.
- **주기:** cron `0 0 */6 * * *`, 매일 00:00·06:00·12:00·18:00 정각(서버 시간대 기준). 6시간 주기이며 `@EnableScheduling`은 다른 설정 클래스에도 붙어 있어 활성화된다(`B/domain/m05/config/Xwv44Scheduler.java:16`).
- **실행:** `JobLauncher.run(updateShipmentStatusesJob, timestamp 파라미터)`(37-40). 예외는 `printStackTrace`만 하고 삼킨다(41-43).
- **Job/Step:** `B/domain/m12/config/Xqv91JobConfig.java:54-82`.
  - chunk 50, 오류 건 skip, skipLimit 50, faultTolerant(75-77).
  - 스텝 시작 시 Playwright 브라우저를 열고 종료 시 닫는다(`B/domain/m12/config/Xmb36Listener.java:60-70`, 설정은 `Xqv91JobConfig.java:80`).

### 2-2. 조회 대상
- `JpaPagingItemReader` 쿼리: `SELECT s FROM Xhx14 s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL`. `B/domain/m12/config/Xqv91JobConfig.java:95`.
- 즉 운송장이 있고 `IN_TRANSIT` 또는 `OUT_FOR_DELIVERY`인 구매자 배송만 대상이다. `PENDING`은 제외된다.

### 2-3. 실제 실행되는 처리 코드
- 스텝의 processor는 `new Xth19Processor(...)`다. `Xqv91JobConfig.java:69-73`.
- 따라서 실제 실행 코드는 `B/domain/m12/config/Xth19Processor.java:56-157`이다.
  - Playwright로 `https://trace.cjlogistics.com/next/tracking.html?wblNo=<운송장>`을 연다(28, 81-83).
  - `tbody#statusDetail tr`의 마지막 행 5번째 `td` 텍스트를 읽는다(167-191).
- **실행되지 않는 유사 코드:**
  - `Xqv91JobConfig.shipmentItemProcessor()`(`Xqv91JobConfig.java:104-177`) — `@Bean`이지만 스텝에 연결되지 않는다(69).
  - `Xqv91JobConfig.parseCjLogisticsStatus`(186-220) — private이고 호출처가 없다.
  - `Xhx14CommandService.updateShipmentStatuses()`(`Xhx14CommandService.java:308-391`) — 호출처가 없다(`grep` 결과 정의뿐).
  - 이 중 `shipmentItemProcessor`와 `updateShipmentStatuses`는 `Xth19Processor`와 처리 순서가 달라 혼동하기 쉽다.

### 2-4. 택배사 상태 문자열 → 내부 상태
- `Xth19Processor.mapToShipmentStatus`, `B/domain/m12/config/Xth19Processor.java:220-226`. 문자열 완전 일치 비교다(`trim` 후).

| 택배사 문자열 | 내부 상태 |
|---|---|
| `"배송완료"` | `DELIVERED` |
| `"배송출발"` | `OUT_FOR_DELIVERY` |
| 그 외 모든 값 | `IN_TRANSIT` |

- 현재 상태와 같으면 변경 없이 그대로 반환한다(101-105).
- `DELIVERED`가 아닌 상태는 `updateStatus`로 단순 갱신한다(119-126).
- 테이블이 비었거나 파싱 실패 시 `TRACKING_HTML_PARSE_ERROR`를 던진다(172-178, 193-210).

## 3. 배송 완료 판정 이후 (`Xth19Processor` 108-118)

### 3-1. 상태 변경 순서
1. `orderShipment.updateStatus(DELIVERED)`: `IN_TRANSIT`/`OUT_FOR_DELIVERY` → `DELIVERED`는 허용된다(113). 전이표는 `B/domain/m12/entity/Xpb98Status.java:16-26`.
2. `orderService.completeOrder(orderId)`(116), 구현 `B/domain/m12/service/command/Xhx14CommandService.java:190-229`.
   1. `Xzj27 orderBid = orderBidQueryService.findByOrderId(orderId)`를 조회하고, 없으면 `IllegalArgumentException`을 던진다(196-197).
   2. 주문 `COMPLETED` 변경: `order.updateStatus(COMPLETED)`(204).
   3. `updateSaleStatusToSold(orderId)`(208): 판매 `SOLD`, 판매자 알림 등(1-2절 6단계와 같다).
   4. 구매자에게 알림 "[completeOrder] 주문이 완료 처리되었습니다. 주문 ID: …"을 보낸다(211-217).
   5. 위 1~4 어디서든 예외가 나면 `Xpb98Exception(ORDER_NOT_FOUND_FOR_SHIPMENT)`로 감싼다(221-227).
3. `notificationService.notifyShipmentCompleted(order)`(117): 구매자에게 "[배송 완료] 상품이 배송 완료되었습니다. 주문 ID: …"을 보낸다. `B/domain/m15/service/command/Xkh73CommandService.java:219-234`. 이 메서드는 내부 예외를 삼킨다(230-233).
4. `JpaItemWriter`가 변경된 `Xhx14`를 저장한다(`Xqv91JobConfig.java:241-246`).

### 3-2. 알림 건수 (정상 완주 시)
- 구매자 **2건**: "[completeOrder] 주문이 완료 처리되었습니다"(`Xhx14CommandService.java:216`)와 "[배송 완료] …"(`Xkh73CommandService.java:228`).
- 판매자는 `updateSaleStatusToSold`에서 판매가 `SOLD`로 전이될 때만 알림을 받는다. 판매 입찰 경로와 주문 입찰 경로가 같은 판매면 최대 **1건**이다(`Xhx14CommandService.java:133-138, 164-169`).
- 판매가 이미 `SOLD`이면 전이 불가라 판매자 알림은 **0건**이다(119, 156). 이는 4절 (b)에서 발생한다.
- 구매자 쪽 "상품이 출발하였습니다" 알림은 운송장 등록 단계(1절)에서 나가며 이 단계에서는 나가지 않는다.

### 3-3. 주문 입찰·판매 입찰 상태
- 배송 완료 배치 경로(`completeOrder`)는 `Xzj27`(주문 입찰)과 `Xzz58`(판매 입찰)의 상태를 `COMPLETED`로 바꾸지 않는다.
  - `completeOrder` 안에는 입찰 `updateStatus` 호출이 없다(190-229).
  - `COMPLETED`로 바꾸는 `updateOrderAndSaleBidStatusToCompleted`는 `updateTrackingInfo`(289)에서만 호출된다. 그 경로는 1-3절처럼 실제 주문에서는 도달하지 못한다.
- 따라서 입찰들은 결제 시점의 `MATCHED`에 그대로 남는다.
  - 주문 입찰은 주문 연결 시 `MATCHED`가 된다. `B/domain/m16/entity/Xzj27.java:60-75`.
  - 판매 입찰은 `assignOrder`에서 `MATCHED`가 된다. `B/domain/m10/entity/Xzz58.java:58-61`.
- 변하는 것은 판매(`Xgg74`)의 `SOLD`뿐이다.
- 참고: 결제 단계에서 `processPaymentAndShipment`가 `orderBidQueryService.findById(orderId)`를 호출한다(`B/domain/m16/service/command/Xdg64CommandService.java:188`). 이는 주문 ID를 주문 입찰 ID로 잘못 쓰는 코드라, 다른 입찰을 `MATCHED`로 바꿀 수 있다.

## 4. 주문 종류별 차이

배치가 집으려면 배송이 `IN_TRANSIT`/`OUT_FOR_DELIVERY`여야 하고(2-2), 이는 `check-status`(1-4)로만 도달한다. 그 배송이 `DELIVERED`로 판정되었다고 가정하고 비교한다.

### (a) 실배송 일반 구매 입찰 주문 — 끝까지 진행되지 않는다
- 주문이 `PREPARING`이다(0절).
- `completeOrder`에서 주문 입찰은 존재하므로 조회는 통과한다(196). 이어 `order.updateStatus(COMPLETED)`(`Xhx14CommandService.java:204`)에서 막힌다.
  - `PREPARING`은 `COMPLETED`로 갈 수 없다(`B/domain/m16/entity/Xdg64Status.java:26`).
  - `Xxc76StatusException`이 나고 `Xpb98Exception(ORDER_NOT_FOUND_FOR_SHIPMENT)`로 감싸진다(221-227).
- 결과:
  - 판매 `SOLD` 처리, 구매자 알림 2건, 판매자 알림이 모두 실행되지 않는다.
  - 배송의 `DELIVERED` 변경(113)과 주문 상태는 청크 롤백으로 반영되지 않는다. 배송은 `IN_TRANSIT`/`OUT_FOR_DELIVERY`로 남는다.
  - 다음 6시간 주기에서 다시 조회·실패를 반복한다.
  - 입찰들의 상태 변화는 없다.

### (b) 즉시 구매로 만들어진 주문 — 끝까지 진행된다
- 주문이 `PENDING_PAYMENT`이고 `PENDING_PAYMENT → COMPLETED`가 허용된다(`Xdg64Status.java:24`). 그래서 `order.updateStatus(COMPLETED)`(`Xhx14CommandService.java:204`)가 통과한다.
- 즉시 구매는 `Xzj27`을 `createInstantOrderBid`로 만들어 주문에 연결한다(`B/domain/m16/service/command/Xzj27CommandService.java:142, 192-206`). 그래서 `completeOrder`의 주문 입찰 조회(196)도 통과한다.
- 판매는 결제 시점에 이미 `SOLD`가 된다. `B/domain/m06/service/command/Xbf54CommandService.java:383-404`.
  - 이 시점에는 주문 입찰이 아직 없어 `order.getOrderBid()`가 null이므로 판매 입찰 경로(391-404)를 탄다.
  - `sale.updateStatus(SOLD)`는 검사 없이 호출된다(404).
- 따라서 배송 완료 시 `updateSaleStatusToSold`의 `canTransitionTo(SOLD)`가 거짓이다(`SOLD`는 `false`, `B/domain/m10/entity/Xgg74Status.java:25`). 판매 변경과 판매자 알림, 창고 갱신을 건너뛴다(`Xhx14CommandService.java:119, 156`).
- 결과:
  - 배송 `DELIVERED`, 주문 `COMPLETED`.
  - 구매자 알림 2건.
  - 판매자 알림은 이 단계에서 0건(결제 시점에 이미 받음).
  - 주문 입찰·판매 입찰은 `MATCHED` 그대로.
  - 청크가 커밋되어 저장된다.

## 5. 실패 처리 (주기 처리 중 한 건 실패)

- 설정: `faultTolerant().skip(Exception.class).skipLimit(50)`. `B/domain/m12/config/Xqv91JobConfig.java:75-77`.
- 프로세서가 던지는 예외(`Xpb98Exception`, 조회 실패, 상태 전이 실패 등)는 모두 skip 대상이다.
  - 프로세서는 일반 예외를 `EXTERNAL_TRACKING_SERVICE_ERROR`로 감싸 다시 던진다(`Xth19Processor.java:133-145`).
  - 운송장이 없으면 `TRACKING_NUMBER_INVALID`를 던진다(61-64).
- **그 건:**
  - 청크 트랜잭션이 롤백되고 해당 건만 skip된다.
  - `onSkipInProcess`가 로그만 남긴다(`Xqv91JobConfig.java:255-266`).
  - 변경은 저장되지 않는다. `completeOrder`가 일으킨 주문·판매 변경과 알림도 같은 트랜잭션이라 함께 롤백된다.
  - 상태가 그대로이므로 다음 주기(6시간 후)에 다시 조회된다.
- **나머지 건:** 청크 전체가 롤백된 뒤 항목별로 재처리되어, 실패한 건을 제외한 나머지는 정상 커밋된다. 한 건의 실패가 나머지 처리를 막지 않는다.
- **한도:** skip이 50건을 넘으면 `SkipLimitExceededException`으로 스텝이 실패한다. 스케줄러는 예외를 `printStackTrace`로만 처리한다(`Xpb98BatchScheduler.java:41-43`).
- **주의 (reader 페이징):** 상태 필터 쿼리를 페이징(`pageSize=50`)으로 읽으면서 처리 중에 대상 행의 상태가 바뀐다(`DELIVERED`로 이동). 다음 페이지의 offset이 밀려 일부 대상이 이번 실행에서 누락될 수 있고, 다음 주기로 넘어간다. `Xqv91JobConfig.java:89-96`.
- `completeOrder`의 실패가 `Xhx14CommandService`의 `@Transactional` 프록시를 통과해 청크 트랜잭션을 rollback-only로 만든다. 예외를 프로세서가 밖으로 던지므로 위와 같이 처리된다.
