# 구매자 배송: 운송장 등록 ~ 배송 완료 처리

경로 약칭: `B` = `src/main/java/com/fream/back`
엔티티 이름은 난독화되어 있다. Xhx14 = 구매자 배송(order_shipment), Xdg64 = 주문(orders), Xzj27 = 주문 입찰, Xzz58 = 판매 입찰, Xgg74 = 판매, Xpb98Status = 배송 상태, Xdg64Status = 주문 상태.

## 요약

- 운송장 등록(PATCH)은 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문에서 **항상 실패**한다. 주문이 `PREPARING`인데 `PREPARING -> IN_TRANSIT` 전환이 허용되지 않기 때문이다. 응답은 404 / `S001`이고 DB에 남는 것은 없다.
- 배송 완료 감지는 6시간마다 도는 Spring Batch 잡이 한다. 실제로 쓰이는 처리 코드는 `Xth19Processor`이다.
- 같은 이유로 (a) 실배송 일반 구매 입찰 주문은 `COMPLETED` 전환에서 막혀 완료 처리가 실패한다. (b) 즉시 구매 주문은 끝까지 진행된다.

## 1. 운송장 등록 요청

### 1-1. 진입 API
1. `PATCH /shipments/order/{shipmentId}/status`, body는 `Xhx14RequestDto`(courier, trackingNumber)이다.
   - 근거: `B/domain/m12/controller/command/Xhx14CommandController.java:20` (`@RequestMapping("/shipments/order")`), `:33-49`.
2. 컨트롤러는 `Xhx14CommandService.updateTrackingInfo(shipmentId, courier, trackingNumber)`를 호출한다.
   - 근거: `Xhx14CommandController.java:41-45`.
3. 운송장 등록 + 즉시 상태 조회 API가 따로 있다. 엔티티의 `updateTrackingInfo`만 쓰고 주문 상태는 건드리지 않는다.
   - `POST /shipments/order/{shipmentId}/check-status` (`:58`)
   - `POST /shipments/order/{shipmentId}/check-status-string` (`:96` 부근)
   - 서비스: `B/domain/m12/service/command/Xhx14CommandService.java:452-516`

### 1-2. `updateTrackingInfo`가 의도한 엔티티 상태 순서와 알림
근거: `Xhx14CommandService.java:238-303`

1. courier/trackingNumber가 비었으면 `TRACKING_INFO_REQUIRED`(S004)를 던진다. (`:243-246`)
2. 배송(Xhx14)을 조회한다. 없으면 `SHIPMENT_NOT_FOUND`. (`:249-253`)
3. **배송**: `shipment.updateTrackingInfo(courier, trackingNumber)`를 호출한다. 택배사·운송장을 저장하고 상태를 곧바로 `IN_TRANSIT`으로 설정한다. 상태 머신 검증은 없고, `PENDING -> SHIPPED`를 거치지 않는다. (`:256`, `B/domain/m12/entity/Xhx14.java:41-45`)
4. **주문**: `order.updateStatus(Xdg64Status.IN_TRANSIT)`을 호출한다. (`Xhx14CommandService.java:259-260`)
   - 이 메서드는 `canTransitionTo`를 검사하고 불허이면 `Xxc76StatusException`을 던진다. (`B/domain/m16/entity/Xdg64.java:113-121`)
5. **알림**: 구매자에게 "상품이 출발하였습니다. 주문 ID: …" 알림을 1건 만든다. (`Xhx14CommandService.java:265-271`)
6. `updateSaleStatusToSold(orderId)`를 호출한다. (`:276`)
   - 판매 입찰의 판매(Xgg74)가 `canTransitionTo(SOLD)`이면 `SOLD`로 바꾼다. (`:116-123`)
   - 창고 보관 상품이면 창고 상태도 갱신한다. (`:126-129`)
   - 판매자에게 "상품이 성공적으로 판매 완료되었습니다" 알림을 1건 만든다. (`:132-138`)
   - 주문 입찰 쪽 판매도 같은 방식으로 처리한다. (`:150-180`)
7. 창고 보관 상품이면 창고 상태를 다시 `SOLD`로 갱신한다. (`:279-286`)
8. `updateOrderAndSaleBidStatusToCompleted`를 호출한다. 주문 입찰 `MATCHED -> COMPLETED`, 판매 입찰 `MATCHED -> COMPLETED`. (`:289`, `:412-440`)
   - 이 메서드의 예외는 삼킨다. (`:436-439`)

의도된 순서는 배송 `IN_TRANSIT`, 주문 `IN_TRANSIT`, 구매자 알림, 판매 `SOLD` + 판매자 알림, 입찰 `COMPLETED`이다.

### 1-3. 실배송 일반 구매 입찰 주문에서 끝까지 성공하나? → 아니오
**실패 지점: 4단계, `Xhx14CommandService.java:260`의 `order.updateStatus(IN_TRANSIT)`**

원인:
1. 일반 구매 입찰 주문은 `Xdg64CommandService.createOrderFromBid`에서 `PENDING_PAYMENT`로 만들어진다. (`B/domain/m16/service/command/Xdg64CommandService.java:76-82`)
2. 결제·배송 처리(`processPaymentAndShipment`)에서 실배송(`isWarehouseStorage()==false`)이면 `PAYMENT_COMPLETED -> PREPARING`까지만 간다. (`Xdg64CommandService.java:174-177`)
   - Kafka 소비자 경로도 동일하게 `PREPARING`에서 멈춘다. (`B/domain/m16/service/kafka/Xdg64EventConsumer.java:192-195`, `:215-218`)
3. 허용 전환표에서 `PREPARING`의 다음 상태는 `IN_WAREHOUSE`, `SHIPMENT_STARTED`뿐이다. `IN_TRANSIT`은 `SHIPMENT_STARTED`에서만 갈 수 있다. (`B/domain/m16/entity/Xdg64Status.java:26`, `:28`)
4. 코드 어디에서도 `Xdg64Status.SHIPMENT_STARTED`로 설정하는 곳이 없다. (전체 grep 결과 `Xdg64Status.SHIPMENT_STARTED`를 쓰는 setter 호출 없음)
5. 따라서 `Xxc76StatusException("상태 전환이 허용되지 않습니다: PREPARING -> IN_TRANSIT")`이 발생한다. (`Xdg64.java:117-119`)

예외 흐름:
- `catch (Xpb98Exception e) { throw e; }`에는 걸리지 않는다. `Xxc76StatusException`은 `Xdg64Exception` 계열이다.
- `catch (Exception e)`에서 `Xpb98Exception(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")`로 감싸 던진다. (`Xhx14CommandService.java:295-301`)
- 오류 코드 `SHIPMENT_NOT_FOUND`는 `S001`, 404이다. (`B/domain/m12/exception/Xpb98ErrorCode.java:12`)

무엇이 저장되나: **아무것도 저장되지 않는다.**
- `@Transactional` 메서드에서 `RuntimeException`(`Xks43Exception extends RuntimeException`, `B/global/exception/Xks43Exception.java:10`)이 나가므로 롤백된다.
- 3단계의 택배사·운송장·`IN_TRANSIT` 변경은 영속화되지 않는다. 배송은 `PENDING`에 운송장 null인 채로 남는다.
- 주문은 `PREPARING` 그대로이다.
- 알림 생성(5단계)과 판매 `SOLD`(6단계)에는 도달하지 못했으므로 알림도 없다.

응답:
- `Xks43ExceptionHandler.handleShipmentException`이 `ErrorResponse`를 만든다. HTTP **404**, code `S001`, message "배송 정보를 찾을 수 없습니다.", 요청 URI를 담는다. (`B/global/exception/Xks43ExceptionHandler.java:455-469`)
- 실제 원인 메시지는 응답 본문에 나가지 않고 errorCode의 고정 메시지만 나간다.

참고로 1-2의 6단계도 어차피 막혀 있다. `saleBidQueryService.findByOrderId`는 없으면 null이 아니라 `IllegalArgumentException`을 던지므로 `saleBid != null` 분기는 의미가 없다. (`B/domain/m10/service/query/Xzz58QueryService.java:25-29`)

## 2. 배송 완료 감지

### 2-1. 누가·언제·어떻게
1. **누가**: `Xpb98BatchScheduler.scheduleShipmentStatusJob()`이 `@Scheduled`로 Spring Batch 잡 `updateShipmentStatusesJob`을 실행한다.
   - 근거: `B/global/config/Xpb98BatchScheduler.java:34-44`
   - `@Qualifier("updateShipmentStatusesJob")`로 주입한다. (`:19-21`)
   - `timestamp` 잡 파라미터를 넣어 매번 새 인스턴스로 실행한다. (`:37-40`)
2. **주기**: `cron = "0 0 */6 * * *"`, 즉 **6시간마다**(00, 06, 12, 18시 정각)이다. (`Xpb98BatchScheduler.java:34`)
   - 다른 스케줄러(`m03 Xgp60`, `m04 EventStatusScheduler`, `m05 Xwv44Scheduler`, `m13 Xzb84Scheduler`, `m18 Xvq73Configuration`, `m19 Xzs57Aspect`)에는 배송 관련 코드가 없다.
3. **대상**: reader의 JPQL이 `status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND trackingNumber IS NOT NULL`인 Xhx14이다. 페이지 크기 50이다. (`B/domain/m12/config/Xqv91JobConfig.java:89-96`, `:51`)
4. **어떻게**:
   - 잡 구성은 `chunk(50) -> reader -> processor -> JpaItemWriter`이고, 스텝 전후로 `Xmb36Listener`가 Playwright 브라우저를 열고 닫는다. (`Xqv91JobConfig.java:55-82`, `B/domain/m12/config/Xmb36Listener.java:15-24`)
   - 처리 중 CJ대한통운 추적 페이지 `https://trace.cjlogistics.com/next/tracking.html?wblNo=<운송장>`을 Playwright로 열고 `tbody#statusDetail tr`을 기다린다. (`Xth19Processor.java:72-87`, 상수 `:28-30`)
   - 마지막 행의 5번째 `td`(index 4) 텍스트를 상태 문자열로 읽는다. 행이 없거나 텍스트가 비면 `TRACKING_HTML_PARSE_ERROR`이다. (`Xth19Processor.java:167-198`)

### 2-2. 실제 실행되는 처리 코드
- 실제 처리 코드는 **`B/domain/m12/config/Xth19Processor.java`의 `process()`** (`:56-137`)이다.
  - 스텝이 `.processor(new Xth19Processor(playwrightBrowserManager(), notificationService, orderService))`로 직접 생성해 쓴다. (`Xqv91JobConfig.java:69-73`)
- 같은 이름의 `shipmentItemProcessor()` `@Bean`(`Xqv91JobConfig.java:104-177`)은 스텝에 연결되지 않아 **실행되지 않는다**. 로직은 비슷하지만 Playwright 대신 `cjTrackingPlaywright`를 쓴다.
- `Xqv91JobConfig.parseCjLogisticsStatus`(`:186-220`)도 어디서도 호출되지 않는다.
- `Xhx14CommandService.updateShipmentStatuses()`(`:308-391`)도 호출처가 없다. 전체 저장소에서 정의 외에 참조가 없다. `@Scheduled`도 없다.
- 즉시 조회 API(`updateAndCheckShipmentStatus`, `:452-516`)는 주기 처리와 별개의 수동 경로이다.

### 2-3. 택배사 상태 문자열 → 내부 상태
`Xth19Processor.mapToShipmentStatus` (`Xth19Processor.java:220-226`)

| 택배사 문자열 | 내부 상태 |
|---|---|
| `"배송완료"` | `DELIVERED` |
| `"배송출발"` | `OUT_FOR_DELIVERY` |
| 그 외 모두 | `IN_TRANSIT` |

- 정확한 문자열 일치(`trim()` 후)이다. (`:181`)
- "배송출발"이 아닌 다른 문자열(예: "배달중", "집하")은 전부 `IN_TRANSIT`이 된다.
- 현재 상태가 `OUT_FOR_DELIVERY`인데 조회 결과가 그 외 문자열이면 `IN_TRANSIT`으로 매핑된다. `OUT_FOR_DELIVERY -> IN_TRANSIT`은 불허라서 `IllegalStateException`이 나고, `EXTERNAL_TRACKING_SERVICE_ERROR`로 감싸져 해당 건이 skip된다. (`B/domain/m12/entity/Xpb98Status.java:23-28`, `Xhx14.java:47-55`, `Xth19Processor.java:133-144`)
- 매핑 결과가 현재 상태와 같으면 아무것도 하지 않고 그대로 반환한다. (`Xth19Processor.java:101-105`)

| 수신자 | 내용 | 건수 |

### 3-3. 주문 입찰·판매 입찰 상태
- **주기 처리 경로에서는 주문 입찰도 판매 입찰도 `COMPLETED`로 바뀌지 않는다.**
- `completeOrder`가 호출하는 `updateSaleStatusToSold`는 판매(Xgg74)만 건드린다. 입찰 상태는 건드리지 않는다. (`Xhx14CommandService.java:112-183`)

- 따라서 주문 입찰(Xzj27)과 판매 입찰(Xzz58)은 `MATCHED`로 남는다. 바뀌는 것은 판매(Xgg74)의 `SOLD`뿐이다.
- 주문 입찰의 `updateStatus`는 검증 없이 대입만 한다. (`B/domain/m16/entity/Xzj27.java:106-108`)

## 4. 주문 종류별 차이

### (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문 → 끝까지 진행되지 않는다
- 주문 상태는 `PREPARING`이다. (`Xdg64CommandService.java:175-176`)
- 배송이 `IN_TRANSIT`+운송장이 되려면 `check-status` API를 거쳐야 한다. PATCH 경로는 1-3에서 실패한다. 이 경우 `Xhx14.updateTrackingInfo`는 주문 상태를 건드리지 않는다. (`Xhx14CommandService.java:473`)
- 그 뒤 주기 처리에서 "배송완료"가 감지되면 `completeOrder`의 `order.updateStatus(COMPLETED)`(`:204`)에서 막힌다. `PREPARING`의 다음 상태는 `IN_WAREHOUSE`, `SHIPMENT_STARTED`뿐이다. (`Xdg64Status.java:26`)
- `Xxc76StatusException`이 `completeOrder`의 `catch (Exception)`에 잡혀 `Xpb98Exception(ORDER_NOT_FOUND_FOR_SHIPMENT, "주문 완료 처리 중 오류 발생: …")`으로 다시 던져진다. (`:221-228`)
- 이 예외는 `Xth19Processor`의 catch를 거쳐 그대로 재던져지고 skip된다. (`Xth19Processor.java:133-144`)
- 결과:
  - 배송 `DELIVERED` 변경은 메모리에서만 일어나고 저장되지 않는다. DB에는 `IN_TRANSIT`/`OUT_FOR_DELIVERY`로 남는다.
  - 주문은 `PREPARING`, 판매 `SOLD` 전환 없음, 알림 0건이다.
  - 다음 6시간 주기에 같은 건이 다시 조회·실패하는 것을 반복한다.
- 별도 문제: `processPaymentAndShipment`가 주문 입찰을 `findById(orderId)`로 찾는다. 이는 주문 ID를 입찰 ID로 쓰는 것이라 대상이 어긋난다. (`Xdg64CommandService.java:188-190`)

### (b) 즉시 구매로 만들어진 주문 → 끝까지 진행된다
- 생성: `createInstantOrder`가 주문을 `PENDING_PAYMENT`로 만들고, 결제 후에도 상태를 올리지 않는다. 판매 입찰은 주문에 연결되고 `MATCHED`가 된다. (`Xdg64CommandService.java:241-245`, `:279-280`, `:305`)
- 주문 입찰은 `MATCHED` + `markAsInstantPurchase()`로 만들어지며 `order`와 `sale`이 채워진다. (`B/domain/m16/service/command/Xzj27CommandService.java:192-205`)
- 결제 단계에서 이미 판매가 `SOLD`가 된다. (`B/domain/m06/service/command/Xbf54CommandService.java:83`, `:390-404`, `Xgg74.java:73-75`는 검증 없는 대입)
- 배송 완료 판정 후:
  - `PENDING_PAYMENT -> COMPLETED`는 허용된다. (`Xdg64Status.java:24`) 따라서 `completeOrder`의 `order.updateStatus(COMPLETED)`가 성공한다.
  - `updateSaleStatusToSold`는 판매가 이미 `SOLD`라 `canTransitionTo(SOLD)`가 거짓이어서 변경과 판매자 알림이 모두 건너뛰어진다. (`Xgg74Status.java:25`, `Xhx14CommandService.java:119`, `:156`)
  - 구매자 알림 2건(`[completeOrder]`, `[배송 완료]`)이 생성된다. 판매자 알림은 0건이다.
  - 배송은 `DELIVERED`로 저장된다.
- 주문 입찰·판매 입찰은 `MATCHED`로 남는다. (3-3 참고)
- 주기 처리 대상이 되려면 배송이 `IN_TRANSIT`이어야 한다. PATCH 경로는 `PENDING_PAYMENT -> IN_TRANSIT`이 불허(`Xdg64Status.java:24`)라 실패하므로, `check-status` API로 운송장을 등록해야 한다.

### 차이 요약
| | (a) 실배송 일반 구매 입찰 | (b) 즉시 구매 |
|---|---|---|
| 배송 완료 시 주문 상태 | `PREPARING`, `COMPLETED` 전환 불허로 실패 | `PENDING_PAYMENT -> COMPLETED` 성공 |
| 배송 상태 | `DELIVERED` 저장 안 됨(skip) | `DELIVERED` 저장 |
| 구매자 알림 | 0건 | 2건 |
| 판매자 알림 | 0건 | 0건(판매가 이미 `SOLD`) |
| 입찰 상태 | 변화 없음 | `MATCHED` 유지 |

## 5. 실패 처리 (주기 처리 중 한 건 실패)

근거: `Xqv91JobConfig.java:66-81`, `Xth19Processor.java:133-144`
1. processor 안에서 모든 예외는 `Xpb98Exception`으로 통일되어 던져진다. 비-`Xpb98Exception`은 `EXTERNAL_TRACKING_SERVICE_ERROR`로 감싼다. (`Xth19Processor.java:133-144`)
2. 스텝은 `faultTolerant().skip(Exception.class).skipLimit(50)`이다. (`Xqv91JobConfig.java:75-77`, 상수 `:52`)
   - 실패한 건은 **skip**되고 잡 전체는 중단되지 않는다.
   - 해당 청크 트랜잭션은 롤백되고, 청크 안의 나머지 건은 한 건씩 다시 처리되어 정상 건만 커밋된다. (Spring Batch fault-tolerant 청크 기본 동작)
3. 실패한 건: 변경이 저장되지 않아 DB 상태(`IN_TRANSIT`/`OUT_FOR_DELIVERY`)가 그대로이다. 다음 6시간 주기에 같은 쿼리로 다시 대상이 된다. 로그는 `SkipListener.onSkipInProcess`로 남는다. (`Xqv91JobConfig.java:251-259`)
4. 나머지 건: 계속 처리되어 정상 저장된다.
5. skip이 50건을 넘으면 스텝이 실패하고 남은 건은 처리되지 않는다. 이는 Spring Batch의 skipLimit 동작이다.
6. 스케줄러는 잡 실행 예외를 `printStackTrace()`로만 처리한다. (`Xpb98BatchScheduler.java:41-43`)
7. 알림 생성은 `notifyShipmentCompleted` 내부에서 예외를 삼켜 로그만 남긴다. 따라서 알림 실패는 건 실패로 이어지지 않는다. (`Xkh73CommandService.java:230-233`)
8. 참고로 `Xhx14CommandService.updateShipmentStatuses()`(`:322-387`)는 건별 try/catch로 실패를 세고 계속 진행하는 로직이지만, 호출처가 없어 실행되지 않는다.
