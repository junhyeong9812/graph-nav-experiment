클래스명은 난독화되어 있다. 주요 매핑은 다음과 같다.

## 1. 진입 API, 처리 단계, 동기/비동기, 응답 ID

**진입 API**: `POST /order-bids/instant`
- 클래스 매핑 `@RequestMapping("/order-bids")`는 `D/m16/controller/command/Xzj27CommandController.java:22`, 메서드 매핑 `@PostMapping("/instant")`는 `:89`이다.
- 요청 DTO는 `saleBidId`, `addressId`, `warehouseStorage`, `paymentRequest`로 구성된다 (`D/m16/dto/Xpj49RequestDto.java`).

**처리 단계** (모두 하나의 요청 스레드 안에서 순서대로 실행)
1. 컨트롤러가 인증 이메일을 꺼낸다 (`Xzj27CommandController.java:92`).
2. `enrichPaymentRequest`가 결제 요청에 `userEmail`을 넣고 `orderId`를 null로 비운다 (`:98`, `:119-123`).
3. `Xzj27CommandService.createInstantOrderBid`를 호출한다 (`:101-107`).
4. 서비스가 입력을 검증한다 (`D/m16/service/command/Xzj27CommandService.java:123`, `:154-167`).
5. 구매자를 조회한다 (`:126`).
6. 판매 입찰을 조회하고 검증한다 (`:129`, `:172-184`).
   - 판매 입찰이 이미 `MATCHED`인지, 이미 다른 주문과 연결됐는지는 검사하지 않는다.
7. `Xdg64CommandService.createInstantOrder`로 주문을 만든다 (`:133-139`).
   1. 배송지를 조회한다 (`D/m16/service/command/Xdg64CommandService.java:238`).
   2. 주문을 저장한다 (`:241-247`).
   3. 주문 항목을 만든다 (`:255`).
   4. 배송 정보를 만든다 (`:264`).
   5. 판매 입찰을 매칭한다 (`:279-283`).
   6. 창고 상태를 갱신한다 (`:291-293`).
   7. 결제를 처리한다 (`:305`).
8. 구매 입찰(OrderBid)을 `MATCHED` 상태로 만들어 저장한다 (`Xzj27CommandService.java:142`, `:189-207`).

**동기 처리다.**
- 이 경로에는 Kafka 발행, `@Async`, 스케줄러가 없다. 결제 대행사(PortOne) 호출도 같은 스레드에서 REST로 블로킹 호출한다 (`D/m06/p05/Xxv33ApiClient.java:266`).
- Kafka(`order-processing-topic`)는 별도 엔드포인트 `POST /orders/{orderId}/process-payment-shipment`에서만 쓰인다 (`D/m16/service/kafka/Xdg64EventProducer.java:24`, `D/m16/controller/command/Xdg64CommandController.java:30`, `:42`). 즉시 구매는 이 경로를 타지 않는다.
- 전체는 `@Transactional` 한 트랜잭션이다 (`Xzj27CommandService.java:118`, `Xdg64CommandService.java:219`).

**응답 ID는 주문(Order) ID가 아니라 구매 입찰(OrderBid, `Xzj27`)의 ID다.**
- 컨트롤러는 `createInstantOrderBid(...)`가 돌려준 `Xzj27`에 `.getId()`를 호출한 값을 `orderId`라는 변수에 담아 응답한다 (`Xzj27CommandController.java:101-109`).
- 서비스의 반환 타입이 `Xzj27`이다 (`Xzj27CommandService.java:119`, `:144`).
- 변수명과 응답 메시지는 "주문 ID"처럼 보이지만 실제 값은 OrderBid ID다.

## 2. 생성되는 엔티티와 상태 변화 순서

### 새로 생성되는 엔티티 (생성 순서)

| 순서 | 엔티티 | 생성 직후 상태 | 근거 |
|---|---|---|---|
| ① | Order `Xdg64` | `PENDING_PAYMENT` | `Xdg64CommandService.java:241-247` (`orderRepository.save`) |
| ② | OrderItem `Xhm58` | 수량 1, 가격 = 입찰가 | `Xdg64CommandService.java:255`, `D/m16/service/command/Xhm58CommandService.java:45-52` |
| ③ | OrderShipment `Xhx14` | `Xpb98Status.PENDING` | `D/m12/service/command/Xhx14CommandService.java:61-70` |
| ④ | Payment `Xbf54` | 결제 수단에 따라 다름 (3번 참고) | `D/m06/service/command/Xbf54CommandService.java:157-333` |
| ⑤ | Notification `Xkh73` ×2 | `isRead=false` | `D/m15/service/command/Xkh73CommandService.java:52-53`, `:241-249` |
| ⑥ | OrderBid `Xzj27` | `MATCHED`, `isInstantPurchase=true` | `Xzj27CommandService.java:192-206` |

- 배송지는 `addressId`로 조회한 주소(수령인, 전화번호, 우편번호, 주소)를 그대로 사용한다 (`Xdg64CommandService.java:264-270`).
- Notification은 구매자용과 판매자용 2건이 만들어진다 (`Xbf54CommandService.java:438`, `:449`).

### 기존 엔티티의 상태 변경 순서

1. **SaleBid(`Xzz58`) → `MATCHED`**
   - `saleBid.assignOrder(order)`가 `status=MATCHED`를 세팅하고 (`D/m10/entity/Xzz58.java:58-61`), 이어서 `updateStatus(MATCHED)`를 호출한다 (`Xdg64CommandService.java:279-280`).
   - 직후 `entityManager.flush()`한다 (`:283`).
   - 이 시점부터 `findByOrder_Id(order.getId())`로 SaleBid를 찾을 수 있다 (`D/m10/service/query/Xzz58QueryService.java:26-28`).
2. **창고 보관 상태 (`Xnn94`) → `ASSOCIATED_WITH_ORDER`**
   - 조건은 판매자의 `Sale.isWarehouseStorage()`가 true인 경우뿐이다 (`Xdg64CommandService.java:291-293`).
   - 이 값은 판매자가 판매 입찰을 만들 때 선택한 값이다 (`Xzz58CommandService.java:95`). 구매자의 `warehouseStorage`와는 무관하다.
   - 상태 전환 규칙은 `D/m07/service/command/Xnn94CommandService.java:232-257`에 있다.
3. **Payment 생성** (`Xdg64CommandService.java:305`). 결제 수단별 상태는 3번에서 설명한다.
4. **Sale(`Xgg74`) → `SOLD`**
   - `Xbf54CommandService.notifyUsersAndUpdateSaleStatus`에서 처리한다 (`:383-426`).
   - 이 시점에 `order.getOrderBid()`는 아직 null이다. OrderBid는 결제 뒤에 만들어진다 (`Xzj27CommandService.java:133` → `:142`).
   - 그래서 SaleBid 경로(`:388-407`)를 타서 `findByOrderId`로 SaleBid를 찾고, `sendNotifications` 뒤에 `sale.updateStatus(SOLD)`를 호출한다 (`:403-404`).
   - 상태 전환 검증 없이 값을 그냥 덮어쓴다 (`D/m10/entity/Xgg74.java:73-75`).
5. **OrderBid `Xzj27`을 `MATCHED`로 생성** (`Xzj27CommandService.java:196`).
   - `assignOrder`도 상태를 `MATCHED`로 만든다 (`D/m16/entity/Xzj27.java:60-82`).

### 정리한 상태 흐름

| 단계 | 대상 | 상태 |
|---|---|---|
| 1 | Order | `PENDING_PAYMENT` |
| 2 | SaleBid | `PENDING` → `MATCHED` |
| 3 | Warehouse (판매자 창고 보관일 때만) | → `ASSOCIATED_WITH_ORDER` |
| 4 | Payment | `PAID` 또는 `PENDING` |
| 5 | Sale | → `SOLD` |
| 6 | OrderBid | 생성 시 `MATCHED` |

- Order는 이후에도 상태가 바뀌지 않는다 (5번 참고).

## 3. 결제 수단별 결과, 성공 여부, 카드 실패 시 동작

결제 분기는 `Xbf54CommandService.processPayment`의 `switch`에서 이루어진다 (`:67-80`). 공통 사전 검증은 `:117-146`이다.
- 주문 ID와 이메일이 일치하는지 확인한다.
- `paidAmount > 0`인지 확인한다.
- **`paidAmount`가 판매 입찰가(`saleBid.getBidPrice()`)와 같은지는 검증하지 않는다.** 클라이언트가 보낸 금액을 그대로 쓴다.

| 결제 수단 | 동작 | Payment 상태 | 근거 |
|---|---|---|---|
| **카드** (`CARD`) | PortOne `/subscribe/payments/onetime` 호출. 응답 `status`가 `"success"`일 때만 `PAID`, `isSuccess=true` | `PAID` 또는 `PENDING`(기본값) | `Xbf54CommandService.java:157-225`, 특히 `:179`, `:203-206`; 기본값 `D/m06/entity/Xbf54.java:44` |
| **계좌이체** (`ACCOUNT`) | 은행명만 검증하고 외부 호출 없이 저장 | `PENDING` (`isSuccess=false`) | `:236-279`, 특히 `:260` |
| **일반 결제** (`GENERAL`) | `impUid`만 있으면 즉시 성공 처리. 외부 검증 호출 없음 | `PAID`, `isSuccess=true` | `:290-333`, 특히 `:297-314` |

**즉시 구매는 어느 수단이든 "끝까지" 진행된다.**
- 계좌이체(`PENDING`)여도 결제 직후 `notifyUsersAndUpdateSaleStatus`가 무조건 실행된다 (`:83`). 따라서 Sale은 `SOLD`가 되고 알림이 나가며 OrderBid도 만들어진다.
- 결제 완료 여부와 상관없이 판매가 확정된다.
- 계좌이체의 입금 확인이나 후속 상태 전이는 이 경로에 없다.

**카드 결제 실패 시 동작은 실패가 어떤 모양으로 오느냐에 따라 둘로 갈린다.**

(a) **PortOne HTTP 오류, 또는 응답 `code != 0`인 경우** → 예외 발생, 전체 롤백
- `Xxv33ApiClient.processCardPayment`가 `Xdf64Exception`을 던진다 (`Xxv33ApiClient.java:270-275`).
- `createCardPayment`가 `Xbf54Exception` 계열을 그대로 다시 던진다 (`Xbf54CommandService.java:218-219`). `Xdf64Exception`은 `Xbf54Exception`의 하위 클래스다 (`D/m06/exception/Xdf64Exception.java:6`).
- `processPayment`도 그대로 다시 던진다 (`:89-94`).
- `Xdg64CommandService`가 `Xqj91Exception`으로 감싼다 (`:306-308`). 이 예외는 `Xdg64Exception`이므로 그대로 상위로 전파된다 (`:312-314`).
- `Xzj27CommandService`도 `Xdg64Exception`이면 그대로 다시 던진다 (`:213-215`).
- 모두 `RuntimeException`이다 (`G/exception/Xks43Exception.java:10`). 단일 `@Transactional`이 롤백되므로 Order, OrderItem, Shipment, SaleBid 매칭, Payment가 전부 취소된다. OrderBid는 생성되지 않는다.
- `@Retryable`이 붙어 있으나 (`Xxv33ApiClient.java:224-228`) 대상은 `Xbf54ApiException`뿐이고, 프로젝트에 `@EnableRetry`가 없어 사실상 재시도는 동작하지 않는다.

(b) **PortOne이 `code == 0`으로 응답하되 `status`가 `"success"`가 아닌 경우 (예: `failed`)** → 실패가 무시되고 성공처럼 진행됨
- `status`가 `"success"`일 때만 `PAID`로 바꾸므로 (`Xbf54CommandService.java:203-206`), 아니면 Payment는 기본값 `PENDING`, `isSuccess=false`로 저장된다 (`:208`; 기본값 `Xbf54.java:39`, `:44`).
- 예외를 던지지 않는다. 그 뒤 `notifyUsersAndUpdateSaleStatus`가 그대로 실행된다 (`:83`).
  - Sale은 `SOLD`가 된다.
  - 구매자에게 "결제가 완료되었습니다", 판매자에게 "구매자가 결제를 완료하였습니다" 알림이 간다.
  - SaleBid는 `MATCHED`, OrderBid는 `MATCHED`로 확정되고 HTTP 200 "즉시 구매가 성공적으로 처리되었습니다"가 응답된다 (`Xzj27CommandController.java:109`).
- 결제 실패 후 보상 처리(환불, 롤백)도 없다. `handleRefundIfNecessary`(`:341`)는 어디서도 호출되지 않는다.

## 4. 알림 수신자, 시점, 전달 방식

**수신자 (2명)** — `Xbf54CommandService.sendNotifications` (`:434-462`)
- 구매자: "결제가 완료되었습니다. 주문 ID: {orderId}" (`:438-443`)
- 판매자(`sale.getSeller()`): "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}" (`:447-455`)
- 두 알림 모두 카테고리 `SHOPPING`, 타입 `BID`다.
- 이 경로에서 다른 알림(주문 생성, 배송 등)은 없다.
- 환불 알림(`sendRefundNotification`, `:603`)은 이 경로에서 호출되지 않는다.

**시점**
- 결제 처리 직후, Sale을 `SOLD`로 바꾸기 직전이다 (`:403-404`).
- OrderBid 생성보다 앞서므로, 알림이 나간 시점에는 OrderBid가 아직 없다.
- 결제 수단과 결제 성공 여부에 관계없이 나간다 (3번 참고).

**방식 (동기, 영속 저장 + 선택적 실시간 푸시)**
1. `createNotification`이 DB에 알림을 저장한다 (`Xkh73CommandService.java:52-53`).
2. 이어서 `sendRealTimeNotification`을 호출한다 (`:57`).
   - Redis 키 `WebSocket:Xrd81:{email}`가 있으면(= 접속 중) `messagingTemplate.convertAndSendToUser`로 `/queue/notifications`에 WebSocket 푸시한다 (`:303-318`).
   - 키가 없으면 푸시 없이 저장만 한다 (`:320-322`).
3. 푸시 실패는 경고 로그만 남긴다 (`:315-319`).
4. 알림 생성 자체가 실패해도 `sendNotifications`가 예외를 삼킨다 (`Xbf54CommandService.java:457-461`). 또한 상위 `notifyUsersAndUpdateSaleStatus`도 삼킨다 (`:421-425`). 알림 실패는 구매 처리를 막지 않는다.
5. `@Async`나 Kafka를 쓰지 않는다. 요청 스레드에서 동기로, 같은 트랜잭션 안에서 실행된다 (`Xkh73CommandService.java:27`).
   - 트랜잭션 커밋 전에 WebSocket 푸시가 나갈 수 있다.
   - 이후 단계(예: OrderBid 저장)에서 롤백되어도 푸시는 되돌릴 수 없다.

## 5. 최종 주문 상태와 창고 보관 선택 시 차이

**주문(Order)의 최종 상태는 `PENDING_PAYMENT`다.**
- 주문 생성 시 `PENDING_PAYMENT`로 저장된다 (`Xdg64CommandService.java:244`).
- 즉시 구매 경로의 이후 어느 단계에서도 `order.updateStatus(...)`를 호출하지 않는다 (`:219-319`, `Xbf54CommandService.java` 전체, `Xzj27CommandService.java` 전체).
- `PAYMENT_COMPLETED`, `PREPARING` 등으로 바뀌는 곳은 다음 두 경로뿐이고, 즉시 구매에서는 호출되지 않는다.
  - `POST /orders/{id}/process-payment-shipment`: `Xdg64CommandService.java:165`, `:175`
  - Kafka 컨슈머: `D/m16/service/kafka/Xdg64EventConsumer.java:195`
- 결제가 `PAID`여도 주문은 `PENDING_PAYMENT`로 남는다. 서비스 메서드 이름이나 응답 메시지("성공적으로 처리")와 실제 상태가 다르다.
- 결제 성공 시에도 `order.assignPayment(payment)`를 호출하지 않는다 (`:305`의 반환값을 사용하지 않음). Payment 쪽 `order` FK로만 연결된다 (`Xbf54CommandService.java:200`, `:258`, `:311`).

**구매자가 "창고 보관"(`warehouseStorage=true`)을 선택해도 달라지는 것이 없다.**
- 값은 컨트롤러 로그에만 쓰이고 (`Xzj27CommandController.java:94-95`), 서비스까지 전달된다 (`:104`, `Xzj27CommandService.java:119`, `:133-139`).
- `createInstantOrder`의 파라미터 `isWarehouseStorage`는 메서드 본문에서 한 번도 사용되지 않는다 (`Xdg64CommandService.java:220-319`).
- 이 경로에서는 구매자용 창고 보관 `Xnn94`가 생성되지 않는다 (`createOrderStorage`는 `:170`의 별도 경로에만 있음).
- 주문은 `IN_WAREHOUSE`나 `COMPLETED`로 가지 않는다. 그 전이는 `process-payment-shipment` 경로에만 있다 (`:163-172`).
- 창고 관련 변경은 판매자가 판매 입찰에서 창고 보관을 선택한 경우의 창고 레코드 `ASSOCIATED_WITH_ORDER` 전환뿐이다 (`:291-293`). 이는 구매자의 선택과 무관하다.

**최종 상태 요약 (성공 경로)**

| 엔티티 | 최종 상태 |
|---|---|
| Order | `PENDING_PAYMENT` |
| SaleBid | `MATCHED` |
| Sale | `SOLD` |
| OrderBid | `MATCHED` (`isInstantPurchase=true`) |
| Payment | 카드/일반 `PAID`, 계좌이체 `PENDING` |
| OrderShipment | `PENDING` |
