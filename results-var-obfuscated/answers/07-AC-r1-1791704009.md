# 즉시 구매 처리 흐름 (POST /order-bids/instant)

경로 약어: `D` = `src/main/java/com/fream/back/domain`

## 1. 진입 API · 처리 단계 · 동기/비동기 · 응답 ID

- 진입: `POST /order-bids/instant` → `D/m16/controller/command/Xzj27CommandController.java:89-110` (`createInstantOrderBid`, 클래스 base path `/order-bids` 는 :22).
  - 요청 DTO `Xpj49RequestDto`(saleBidId, addressId, warehouseStorage, paymentRequest): `D/m16/dto/Xpj49RequestDto.java:20-29`.
  - 결제 DTO는 `paymentType` 값(CARD/ACCOUNT/GENERAL)으로 하위 DTO를 결정: `D/m06/dto/Xbf54RequestDto.java:20-24`.
- 단계:
  1. 컨트롤러가 JWT에서 이메일 추출(`Xzj27CommandController.java:92`) 후 `enrichPaymentRequest` 로 결제 요청에 userEmail 주입, orderId=null 로 초기화(`:98`, `:119-123`).
  2. `Xzj27CommandService#createInstantOrderBid`(`D/m16/service/command/Xzj27CommandService.java:118-149`, `@Transactional`): 입력 검증(`:154-167`) → 구매자 조회(`:126`) → 판매 입찰 조회·검증(`:129`, `:172-184`) → `Xdg64CommandService#createInstantOrder` 호출(`:133`) → 주문 입찰(Xzj27) 생성·저장(`:142`, `:189-207`).
  3. `Xdg64CommandService#createInstantOrder`(`D/m16/service/command/Xdg64CommandService.java:219-319`, `@Transactional`)에서 순서대로: 배송지 조회(`:238`) → 주문 저장(`:241-247`) → 결제요청에 orderId 세팅(`:250`) → 주문 항목 생성(`:255-256`) → 주문 배송(Xhx14) 생성(`:264-271`) → 판매 입찰 매칭(`:279-283`) → 판매자 창고 상태 갱신(`:290-301`) → 결제 처리(`:305`).
  4. 결제: `Xbf54CommandService#processPayment`(`D/m06/service/command/Xbf54CommandService.java:57-107`) → 결제수단별 생성 → `notifyUsersAndUpdateSaleStatus`(`:83`) 에서 알림 전송과 판매(Xgg74) SOLD 처리.
- 동기/비동기: **전부 동기, 단일 트랜잭션**이다. Kafka 이벤트 경로(`Xdg64EventProducer`, `/orders/{id}/process-payment-shipment`)는 이 흐름에서 호출되지 않는다. 호출 사슬 전체가 직접 서비스 호출이며(`Xzj27CommandService.java:133`, `Xdg64CommandService.java:305`), 결제 대행사(PortOne) 호출도 RestTemplate 동기 호출이다(`D/m06/p05/Xxv33ApiClient.java:266`). `@Retryable` 이 붙어 있으나 `@EnableRetry` 선언이 소스에 없어 재시도는 동작하지 않는다(`Xxv33ApiClient.java:224-228`).
- 응답 ID: 메시지·변수명은 "orderId"이지만(`Xzj27CommandController.java:101,109`), `createInstantOrderBid(...)` 의 반환값은 `Xzj27`(주문 입찰, order_bid 테이블) 이므로 `.getId()` 는 **주문 입찰(OrderBid) ID** 이다 (`Xzj27CommandService.java:119` 반환형 `Xzj27`, `:206` save). 주문(Xdg64, orders) ID가 아니다.

## 3. 결제 수단별 결과 · 카드 실패 시

`switch (getResolvedPaymentType())`: `Xbf54CommandService.java:67-80`.

| 수단 | 처리 | 결제 상태 | 근거 |
|---|---|---|---|
| CARD | 저장된 결제정보 조회 → PortOne `processCardPayment` 호출 → 응답 `status=="success"` 이면 PAID | 성공 `PAID`, 아니면 기본값 `PENDING` | `Xbf54CommandService.java:166,179,203-206`; 기본값 `D/m06/entity/Xbf54.java:34` |
| ACCOUNT | 은행명 검증 후 외부 호출 없이 저장 | **`PENDING`**(입금 확인 로직 없음) | `Xbf54CommandService.java:244,260-262` |
| GENERAL | impUid 필수, 외부 호출 없이 클라이언트가 보낸 값으로 저장 | 즉시 `PAID`, isSuccess=true | `Xbf54CommandService.java:297,313-314` |

- **즉시 구매는 어떤 수단이든 끝까지 "성공"(HTTP 200)한다.** 결제 후 `notifyUsersAndUpdateSaleStatus` 는 모든 예외를 삼키고(`:421-425`), 알림도 예외를 삼킨다(`:457-461`). 계좌이체(PENDING)·카드 응답이 success 가 아닌 경우에도 `sale=SOLD`, 알림 발송, 200 응답이 된다. 주문은 결제 완료로 바뀌지 않고 `PENDING_PAYMENT` 에 머문다(§2-5).
- **PortOne 이 카드 결제를 실패로 응답하면**(HTTP≠200 또는 `code≠0`): `Xdf64Exception` 을 던진다(`Xxv33ApiClient.java:270-275`, `Xdf64Exception extends Xbf54Exception` `D/m06/exception/Xdf64Exception.java:6`). `createCardPayment` 가 `Xbf54Exception` 을 그대로 재던지고(`Xbf54CommandService.java:218-219`) → `processPayment` 도 재던짐(`:89-94`) → `createInstantOrder` 가 `Xqj91Exception`(Xdg64Exception)으로 감싸 던지고(`Xdg64CommandService.java:306-309`) → `Xzj27CommandService` 는 Xdg64Exception 이라 그대로 던짐(`Xzj27CommandService.java:213-215`). 예외는 `RuntimeException`(`D/../global/exception/Xks43Exception.java:10`) 이므로 바깥 `@Transactional`(`Xzj27CommandService.java:118`)이 롤백된다. 따라서 주문·주문 항목·배송·결제 레코드, 판매 입찰 MATCHED, 창고 ASSOCIATED_WITH_ORDER 변경이 **모두 취소**되고 알림·SOLD 도 일어나지 않는다. 클라이언트는 에러 응답을 받는다. (단, 외부 PortOne 쪽에 이미 승인된 건이 있다면 보상 환불 호출은 이 경로에 없다.)
- 반대로 **응답은 code=0 인데 `response.status` 가 "success" 가 아닌 경우**는 예외가 아니어서 위 "성공" 경로로 흘러간다(`Xbf54CommandService.java:203-208`).

## 4. 알림 대상·시점·방식

- 누가: 결제 처리 성공 직후 `sendNotifications` 가 **구매자**(`"결제가 완료되었습니다. 주문 ID: …"`)와 **판매자**(`"구매자가 결제를 완료하였습니다. 판매 ID: …"`) 각 1건을 만든다. 카테고리 SHOPPING, 타입 BID (`Xbf54CommandService.java:434-456`). 판매자는 `sale.getSeller()` (`:447`).
- 언제: `processPayment` 안, 결제 저장 직후·sale SOLD 변경 직전이며(`:83`, `:403-404`), 같은 요청/트랜잭션 안에서 **동기**로 발생한다. Kafka `notification-topic` 은 이 경로에서 쓰이지 않는다(그건 `Xdg64EventConsumer` 경로).
- 어떻게: `Xkh73CommandService#createNotification`(`D/m15/service/command/Xkh73CommandService.java:44-59`) 이 DB에 알림을 저장하고 `sendRealTimeNotification`(`:303-323`) 이 Redis 키 `WebSocket:Xrd81:{email}` 가 있을 때만 WebSocket `/user/{email}/queue/notifications` 로 push 한다(`:37-38,307-313`). 접속 중이 아니면 저장만 되고 push 는 없다(`:320-321`). 알림 실패는 로그만 남기고 무시된다(`Xbf54CommandService.java:457-461`).
- 주의: 알림은 결제 수단과 무관하게(계좌이체 PENDING 이어도) 발송된다. 주문 입찰이 아직 없는 시점이라 `order.getOrderBid()==null` 이고 판매 입찰을 `findByOrderId` 로 찾는다(`:388-391`). 못 찾으면(`findByOrderId` 는 예외를 던진다 `D/m10/service/query/Xzz58QueryService.java:26-28`) 바깥 catch 에서 삼켜져 알림·SOLD 처리 둘 다 조용히 생략된다(`:421-425`).

## 5. 최종 상태 · 창고 보관

- 처리 종료 시점의 주문 `Xdg64.status` 는 **`PENDING_PAYMENT`** 이다. 결제가 PAID 여도 주문은 PAYMENT_COMPLETED/PREPARING/… 로 전이되지 않는다(`Xdg64CommandService.java:219-319`). 응답 메시지는 "즉시 구매가 성공적으로 처리되었습니다."(`Xzj27CommandController.java:109`)지만 상태는 그렇지 않다. 참고로 `PAYMENT_COMPLETED→PREPARING→(IN_WAREHOUSE→COMPLETED)` 전이는 별도 경로 `processPaymentAndShipment`(`Xdg64CommandService.java:111-202`)와 Kafka 컨슈머에만 있고, 즉시 구매 경로는 호출하지 않는다.
- 최종 상태 요약: 주문 `PENDING_PAYMENT` / 주문 입찰 `MATCHED` / 판매 입찰 `MATCHED` / 판매 `SOLD` / 결제 카드·일반 `PAID`, 계좌 `PENDING` / 주문 배송 `PENDING`.
- **구매자가 "창고 보관"을 선택한 경우**: 요청의 `warehouseStorage` 는 컨트롤러 로그에만 쓰이고(`Xzj27CommandController.java:94-95`), `Xzj27CommandService.createInstantOrderBid` 가 서비스로 넘기지만(`:133-139`) `createInstantOrder` 본문에서는 **한 번도 참조되지 않는다**(`Xdg64CommandService.java:220-319`). 따라서 구매자 선택은 아무 영향이 없다: 주문 창고 보관(Xnn94 order 연결) 생성 없음, `IN_WAREHOUSE`/`COMPLETED` 전이 없음(그 로직은 `processPaymentAndShipment` 에만 있음 `:163-172`), 주문 배송은 항상 생성되고 배송지로 보낸다(`:264-271`).
  - 창고 관련 분기는 **판매자 쪽 플래그** `sale.isWarehouseStorage()` 로만 결정된다: true 이면 판매자 창고 보관 레코드 상태를 `ASSOCIATED_WITH_ORDER` 로 변경(`:291-293`); 이때 해당 레코드가 없으면 `findBySale` 이 예외(`D/m07/service/query/Xnn94QueryService.java:30-33`)를 던져 `Xdx92Exception` 으로 감싸져 전체가 롤백된다(`Xdg64CommandService.java:295-301`). 판매자 창고 레코드는 판매자 배송 등록 시 생성된다(`D/m12/service/command/Xxn30CommandService.java:75-83`).
