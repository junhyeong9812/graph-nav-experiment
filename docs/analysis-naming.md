# 이름 후속 실험 분석 — 대응표는 지도를 대신하는가, 틀린 이름은 얼마나 해로운가

- 날짜: 2026-10-12
- 명세: `docs/plans/2026-10-12/naming-followup/requirement-spec.md`
- 앞 실험: `docs/analysis-size-structure.md`
  - 이름을 지우면 토큰은 그대로이고 정답률만 떨어졌다.
  - 지도의 URL 한 줄이 이름 손실을 메웠다.
- 원자료:
  - `results-gloss-obfuscated/`(GD·GE·GA)
  - `results-var-misnamed/`(B·AC)
  - 비교 기준: `results-var-obfuscated/`, `results-var-original/` + `results-sonnet/`
- 전체 표: `results-naming-analysis.md`(`python3 scripts/analyze_naming.py`로 다시 만든다)

## 한 줄 결론

**도메인 이름 19줄(539B)만 알려 줘도 자동 지도(6.3KB)만큼 정답률을 되찾았다. 틀린 이름은 의미 없는 이름보다 덜 해로웠고, 토큰도 늘리지 않았다.**

## 규모

| 항목 | 값 |
|---|---|
| 대응표 | obfuscated × GD·GE·GA × 8과제 × 5회 = 120회 |
| 틀린 이름 | misnamed × B·AC × 8과제 × 5회 = 80회 |
| 유효성 | 200회 모두 유효, 감사 위반 0, 회귀 판정 오류 0 |
| 실행 비용 | $74.81 (대응표 $44.70, 틀린 이름 $30.11) |
| 채점 비용 | Opus 50건, $8.26 |

## 실험 A: 대응표 vs 지도 (난독화 변형)

대응표는 `m15 = notification`, `Xkh73 = Notification` 형식으로 CLAUDE.md에 넣었다. nav 디렉터리는 두지 않았다.

| 조건 (CLAUDE.md 크기) | ÷B [95%] | 성공(/30) | 과제 05 성공 · 알림 enum 열람 | 질문(/8) |
|---|---|---|---|---|
| B 없음 | 1.00 | 21 | 0/5 · 0/5 | 7.70 |
| AC 자동 지도 (6,344B) | 1.07 [0.95–1.21] | 25 | 4/5 · 4/5 | 7.65 |
| **GD 도메인만 (539B)** | 1.07 [0.88–1.17] | 24 | **5/5 · 5/5** | 7.55 |
| GE 도메인 + 엔티티·enum 어간 (2,297B) | 1.08 [0.92–1.22] | 24 | 3/5 · 3/5 | 7.40 |
| GA 어간 전부 (10,342B) | 1.16 [1.01–1.34] | 24 | 4/5 · 3/5 | 7.45 |

- **정답률:** 가장 작은 대응표(GD)가 지도와 같은 수준으로 성공을 되찾았다. 과제 05에서는 가장 좋았다(5/5).
  - GD에는 `m15 = notification` 한 줄뿐이다. `Xkh73`이 알림이라는 정보는 없다.
  - 에이전트는 이 줄로 알림 도메인 폴더를 찾아 들어가 enum을 열었다.
- **더 자세하다고 낫지 않았다.**
  - GE(어간 78개)는 과제 05에서 3/5였다.
  - GA(어간 384개, 10KB)는 토큰이 1.16배로 늘었다. 구간 하한(1.01)이 1을 넘는다. 매 턴 문맥에 실리는 고정비 때문이다.
- **토큰:** 어떤 대응표도 B보다 싸지 않았다. 앞 실험처럼 효과는 비용이 아니라 정답률에서만 나타났다.
- **과제 04 예외:** GD에서 과제 04가 4/5였다. 다른 조건은 5/5다. 표본 1회 차이다.

## 실험 B: 틀린 이름 (도메인끼리 맞바꾸기)

도메인 18개(event 제외)를 9쌍으로 짝지어 타입 이름과 도메인 패키지에서 업무어를 서로 바꿨다. 메서드·필드·URL·문자열은 원래대로 두었다.

- 예: notification ↔ payment(`NotificationType` → `PaymentType`, `domain/notification` → `domain/payment`)
- 다른 짝: order ↔ faq, shipment ↔ address, product ↔ user, style ↔ sale

| 변형·조건 | ÷원본B | 성공(/30) | 과제 05 성공 · enum 열람 | 질문(/8) | AC÷B [95%] |
|---|---|---|---|---|---|
| original B | 1.00 | 25 | 4/5 · 4/5 | 7.60 | |
| original AC | 1.07 | 25 | 5/5 · 5/5 | 7.60 | 1.07 [0.92–1.21] |
| obfuscated B | 0.95 | 21 | 0/5 · 0/5 | 7.70 | |
| obfuscated AC | 1.02 | 25 | 4/5 · 4/5 | 7.65 | 1.07 [0.95–1.21] |
| **misnamed B** | 1.03 | 22 | 2/5 · 2/5 | 7.55 | |
| **misnamed AC** | 0.99 | 24 | 4/5 · 3/5 | 7.35 | 0.97 [0.85–1.05] |

- **토큰은 늘지 않았다(1.03).** 과제별 B 중앙값도 원본과 거의 같다(예: 01 274k vs 274k, 04 228k vs 229k).
- **정답률은 원본과 의미 없는 이름의 중간이다(22).** 차이는 이번에도 과제 05에 몰렸다.
  - 성공한 실행만 `BENEFIT`을 찾았다.
  - 실패한 실행은 배송 코드에 있던 `PaymentType.BID` 호출을 재사용했다.
  - 기전은 난독화와 같다. 알림 종류 enum을 열었는지가 성패와 일치한다.
- **에이전트가 이름의 모순을 거의 말하지 않았다.** 자기 서술에서 이름과 실제가 다르다고 언급한 실행은 80회 중 2회(과제 07, "실제로는 `FaqBid`의 ID")뿐이다.
  - 그래도 대부분 과제를 풀었다.
  - 메서드 이름·URL·문자열이 맞는 업무어를 유지하고 있어, 그쪽을 따라 탐색했다.
- **지도:** 틀린 이름에서도 지도는 05를 2/5에서 4/5로 올렸다. 지도에는 `payment … api: PaymentCommandController /notifications`처럼 모순이 그대로 드러난다.

### 왜 틀린 이름이 의미 없는 이름보다 덜 해로웠나 (해석)

- 바꾼 것은 타입·패키지 이름뿐이다. 진입점을 찾는 단서(메서드·문자열·URL)는 진실했다. 앞 실험에서 확인했듯 에이전트는 그쪽으로 grep한다.
- 의미 없는 이름(`Xkh73Type`)은 "열어 볼 이유"를 주지 않았다. 반면 `PaymentType`은 알림 호출 안에서 어색하게 보여 일부 실행이 열어 봤을 가능성이 있다. 이 부분은 추정이며 기록으로 확인하지 않았다.
- 실제 코드베이스의 "틀린 이름"은 보통 일부만 틀리고 나머지 단서는 맞다. 그래서 이 설정이 비현실적이지는 않다. 다만 메서드·문자열까지 일관되게 틀린 코드는 시험하지 않았다.

## 세 실험을 합친 결론

1. **탐색 비용은 아키텍처의 지엽성이 정한다.** 크기 4.3배, 이름 제거, 이름 뒤섞기, 어떤 지도나 대응표를 줘도 토큰은 원본 B의 0.95~1.36배 안에 머물렀다(최대는 부풀림+난독화+지도). grep으로 진입점을 찾고 도메인 폴더 안만 읽는 패턴이 모든 변형에서 유지됐다.
2. **정답률은 도메인 경계를 넘는 단서가 정한다.** 변형·조건 사이의 정답률 차이는 대부분 "다른 도메인의 기존 부품(알림 종류)을 골라야 하는" 지점에서 났다. 과제 03(패턴 4지점)은 모든 조건에서 거의 실패해 차이를 만들지 않았다. 단서는 셋 중 하나면 충분했다.
   - 맞는 타입 이름
   - 지도에 남은 URL
   - 도메인 이름 한 줄
3. **필요한 정보량은 작다.** 539B 대응표가 6.3KB 지도와 같았고, 10KB 대응표는 고정비만 늘렸다. 지도·문서의 가치는 크기가 아니라 "이 폴더가 무슨 업무인가"를 알려 주는 데 있다.
4. **실무 지침:**
   - 도메인 패키지 이름을 업무어로 짓는 것이 가장 싼 투자다.
   - 이름이 이미 망가진 코드베이스라면, CLAUDE.md에 도메인 대응표 몇 줄을 두는 것이 지도를 만드는 것보다 낫다.

## 타당성 위협

- **표본:** 조건당 5회다. 정답률 차이는 사실상 과제 05 하나(알림 종류 선택)에서 나온다. 기전은 기록으로 확인했지만, 경계를 넘는 과제가 하나뿐이라 일반화에 한계가 있다.
- **비교 기준의 시점:** obfuscated B·AC와 original은 2026-10-11에, 대응표·misnamed는 10-12에 실행했다. 시간대 효과는 분리할 수 없다.
- **틀린 이름의 범위:** 짝은 시드로 정했다. 짝에 따라 그럴듯함이 다르다(notification ↔ payment는 그럴듯하고, order ↔ faq는 명백히 어색하다). 짝마다 효과를 따로 재지는 않았다.
- **GD의 도메인 이름:** 대응표의 오른쪽은 원래 패키지 이름(`warehouseStorage`, `chatQuestion`)이다. 사람이 쓴 업무 설명이 아니다.
- **선행 연구:** 이름 제거·오도가 LLM 정답률을 떨어뜨린다는 보고는 이미 있다(arXiv 2510.03178, 2609.26388 등. 초록 수준 확인). 크기를 통제한 에이전트 비용 측정, 비용과 정답률의 분리, 짧은 대응표와 지도의 비교는 찾지 못했다.
