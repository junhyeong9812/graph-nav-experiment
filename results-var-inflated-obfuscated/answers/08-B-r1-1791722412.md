경로 약어: `D` = `src/main/java/com/fream/back/domain`, `G` = `src/main/java/com/fream/back/global`.

용어(난독화된 이름 → 의미)
- `Xfr60` = 구매자 배송(order_shipment), `Xhq12` = 주문(orders), `Xtw92` = 주문(구매) 입찰, `Xzt63` = 판매 입찰, `Xpj42` = 판매(sale), `Xrg51` = 판매자 배송.

## 1. 운송장 등록 요청

### 1-1. 진입 API
- `PATCH /shipments/order/{shipmentId}/status`, 바디 `{courier, trackingNumber}`
  - `D/m45/controller/command/Xfr60CommandController.java:20` (`@RequestMapping("/shipments/order")`), `:33` (`@PatchMapping("/{shipmentId}/status")`)
  - 컨트롤러는 `orderShipmentCommandService.updateTrackingInfo(...)`만 호출한다. `try/catch`가 없다. 근거: `Xfr60CommandController.java:41` 부근
- 같은 메서드를 부르는 복제 컨트롤러가 접두사만 다르게 존재한다. 모두 `Xfr60CommandService`를 주입받는다.
  - `/settlement/shipments/order` — `D/m81/controller/command/Xsd74CommandController.java:20,33`
  - `/internal/shipments/order` — `D/m38/controller/command/Xdn57CommandController.java:20,33`
  - `/admin/shipments/order` — `D/m09/controller/command/Xqh36CommandController.java:20,33`
  - `/partner/shipments/order` — `D/m31/controller/command/Xzm66CommandController.java:20,33`
  - `/legacy/shipments/order` — `D/m70/controller/command/Xcx47CommandController.java:20,33`
- 판매자 배송(`POST /sales/{saleId}/shipment`, `D/m85/controller/command/Xpj42CommandController.java:18`)은 `Xrg51`/`Xpj42`를 다루는 별개의 흐름이라 구매자 배송이 아니다.

### 1-2. 코드가 의도한 상태 변경 순서와 알림 (`Xfr60CommandService.updateTrackingInfo`, `D/m45/service/command/Xfr60CommandService.java:239-303`)
1. 택배사·운송장 공백 검사. 비면 `TRACKING_INFO_REQUIRED`(400) — `:243-246`
2. 배송 조회 후 `shipment.updateTrackingInfo(...)` — `:256`. 이 메서드는 전이 검사 없이 `status = IN_TRANSIT`을 바로 넣는다 — `D/m45/entity/Xfr60.java:41-45`
3. `order.updateStatus(Xhq12Status.IN_TRANSIT)` — `:259-260`
4. 구매자에게 알림 1건 "상품이 출발하였습니다. 주문 ID: …" — `:265-270`
5. `updateSaleStatusToSold(orderId)` — `:276`. 판매(`Xpj42`)를 SOLD로 바꾸고, 창고 보관이면 창고 상태를 SOLD로 바꾸고, 판매자에게 알림 "상품이 성공적으로 판매 완료되었습니다" — `:112-180`
6. 창고 보관 판매이면 창고 상태를 한 번 더 SOLD로 바꾼다 — `:279-286`
7. `updateOrderAndSaleBidStatusToCompleted(orderId)` — `:289`. 주문 입찰과 판매 입찰이 MATCHED이면 COMPLETED로 바꾼다 — `:413-437`

즉 설계상으로는 배송 완료가 아니라 운송장 등록 시점에 판매 SOLD·입찰 COMPLETED까지 처리한다. 메서드 이름이나 주석의 "출발"과 다르다.

### 1-3. 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문에서의 실제 결과: **끝까지 성공하지 못한다**
- 이 주문의 상태: `processPaymentAndShipment`가 일반 경로에서 `PAYMENT_COMPLETED → PREPARING`까지만 올린다 — `D/m99/service/command/Xhq12CommandService.java:174-177`. 배송 레코드는 `PENDING`으로 생성된다 — `Xfr60CommandService.java:56-75`.
- 실패 지점: `:260`의 `order.updateStatus(IN_TRANSIT)`.
  - `PREPARING`에서 허용되는 다음 상태는 `{IN_WAREHOUSE, SHIPMENT_STARTED}`뿐이다 — `D/m99/entity/Xhq12Status.java:26`. `IN_TRANSIT`은 `SHIPMENT_STARTED`에서만 갈 수 있다 — `Xhq12Status.java:28-29`.
  - 코드 전체에서 `SHIPMENT_STARTED`로 바꾸는 곳은 없다(조회 화면의 라벨 문자열만 있다. 예: `D/m27/controller/query/Xnt31QueryController.java:207`). 그래서 `PREPARING`인 주문은 `IN_TRANSIT`에 도달할 수 없다.
  - `Xhq12.updateStatus`가 `Xxm16StatusException`("상태 전환이 허용되지 않습니다: PREPARING -> IN_TRANSIT")을 던진다 — `D/m99/entity/Xhq12.java:113-121`.
- 예외 변환: 이 예외는 `Xzn53Exception`이 아니므로 `catch (Exception e)`에 잡힌다. 그러면 `Xzn53Exception(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")`로 바뀌어 던져진다 — `Xfr60CommandService.java:293-302`.
  - 메시지는 "배송을 못 찾음" 계열이지만 실제 원인은 주문 상태 전이 거부다. 코드 이름이 실제 원인과 다르다.
- 저장되는 것: **없다.**
  - `updateTrackingInfo`는 `@Transactional`(`:238`)이고 던져진 것은 RuntimeException이다(`D/../global/exception/Xkt44Exception.java:10`). 따라서 전체가 롤백된다.
  - 배송의 택배사·운송장·`IN_TRANSIT`(`:256`)은 롤백되어 `PENDING`에 운송장이 없는 상태로 남고, 주문은 `PREPARING`이다.
  - 알림은 `:265` 이후에 만들어지므로 한 건도 생기지 않는다.
- 설령 3단계를 통과해도 5단계의 `saleBidQueryService.findByOrderId`가 `null`이 아니라 `IllegalArgumentException`을 던진다. 일반 구매 입찰 주문에는 주문에 연결된 판매 입찰이 없기 때문이다 — `D/m85/service/query/Xzt63QueryService.java:26-29`. 이것도 `:116`에서 터지고 같은 `catch (Exception)`으로 `Xzn53Exception`이 된다.
- 응답: `Xkt44ExceptionHandler`가 `errorCode.getStatus()`와 `ErrorResponse(code, message=errorCode.getMessage())`를 돌려준다 — `G/exception/Xkt44ExceptionHandler.java:49-62`.
  - HTTP **404**, 코드 `S001`, 메시지 "배송 정보를 찾을 수 없습니다." — `D/m45/exception/Xzn53ErrorCode.java:15`.
  - 상세 메시지(`Cannot transition…`)는 응답 바디에 나가지 않는다. 생성자에 준 message는 로그에만 남는다.

## 2. 배송 완료 감지

### 2-1. 누가·언제·어떻게
- 주체: 스프링 스케줄러 `Xzn53BatchScheduler.scheduleShipmentStatusJob()`가 Spring Batch Job `updateShipmentStatusesJob`을 실행한다 — `G/config/Xzn53BatchScheduler.java:19-21,34-44`.
- 주기: `@Scheduled(cron = "0 0 */6 * * *")`, 즉 **6시간마다**(서버 타임존 기준 00:00, 06:00, 12:00, 18:00 정각) — `Xzn53BatchScheduler.java:34`.
  - 매 실행마다 `timestamp` 파라미터를 새로 넣어 JobInstance를 새로 만든다 — `:37-40`.
  - 예외는 `printStackTrace()`로만 처리한다 — `:41-43`.
- 스케줄링 활성화: 앱 내 `@EnableScheduling` 컴포넌트가 있다(예: `D/m66/config/Xtk92Scheduler.java:16`). 배치는 `G/config/Xff76Config.java:15`의 `@EnableBatchProcessing`.
- 수동 경로(주기 아님): `POST /shipments/order/{id}/check-status`, `.../check-status-string` — `Xfr60CommandController.java:58,103` → `Xfr60CommandService.updateAndCheckShipmentStatus` (`:452-516`).

### 2-2. 조회 대상
- Reader 쿼리: `SELECT s FROM Xfr60 s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL` — `D/m45/config/Xpc23JobConfig.java:91-96`. 페이지 크기와 청크 크기는 50 — `:51,94`.
- 결과: 운송장이 등록돼 `IN_TRANSIT`이거나 `OUT_FOR_DELIVERY`인 배송만 조회한다. `PENDING`(운송장 등록 전·롤백된 건)은 조회하지 않는다.

### 2-3. 실제로 실행되는 처리 코드 (유사 코드 중 선택)
- **실행되는 것**: Job → Step → `new Xcz52Processor(...)` (Playwright 크롬 브라우저로 CJ대한통운 조회 페이지를 열고 HTML을 파싱)
  - Step 구성에서 `.processor(new Xcz52Processor(playwrightBrowserManager(), notificationService, orderService))` — `D/m45/config/Xpc23JobConfig.java:66-81`
  - 처리 본문 — `D/m45/config/Xcz52Processor.java:56-131`. URL은 `https://trace.cjlogistics.com/next/tracking.html?wblNo=`, 선택자는 `tbody#statusDetail tr`이고 마지막 행의 5번째 `td` 텍스트를 상태 문자열로 쓴다 (`:477` 계열, 파싱 메서드 `parseStatusFromHtml`).
- **실행되지 않는 것**
  - `Xpc23JobConfig.shipmentItemProcessor()` 람다 빈(`Xpc23JobConfig.java:104-177`)과 `parseCjLogisticsStatus`(Jsoup, `:186-220`). Step이 이 빈을 참조하지 않는다. 사실상 죽은 코드다.
  - `Xfr60CommandService.updateShipmentStatuses()` (`:309-396`). 호출처가 없다(전체 검색 결과 정의 외 호출 없음). 이름과 달리 스케줄러가 부르지 않는다.
  - 이 메서드는 `COMPLETED`와 구매자 알림을 직접 처리하는 별도 구현이어서 실제 Job 경로와 동작도 다르다.
- **Job 설정 복제본**: `Xpc23JobConfig`(m45)와 내용이 같은 `@Configuration`이 `D/m09/config/Xxt33JobConfig.java`, `D/m31/config/Xkd78JobConfig.java`, `D/m38/config/Xrx68JobConfig.java`, `D/m70/config/Xkq49JobConfig.java`, `D/m81/config/Xfr70JobConfig.java`에 있다. 모두 `updateShipmentStatusesJob`이라는 같은 빈 이름과 같은 reader 쿼리, 같은 `Processor`를 쓴다.
  - 차이는 클래스명과 `notificationService` 주입 타입뿐이다. 주입된 알림 서비스들은 `notifyShipmentCompleted` 본문이 동일하다 — 예: `D/m52/service/command/Xbp24CommandService.java:219`, `D/m03/service/command/Xtc38CommandService.java:219`.
  - `application*.yml`에 `allow-bean-definition-overriding` 설정이 없다(정적 확인만 했다. 기동 시 동일 빈 이름 충돌이 어떻게 처리되는지는 실행해 보지 않았다). 어느 쪽이 등록되든 동작이 같으므로, 서비스와 같은 모듈이며 `Xfr60CommandService`와 같은 알림 서비스(`Xbp24CommandService`)를 쓰는 **m45의 `Xpc23JobConfig`/`Xcz52Processor`를 기준**으로 서술했다.

### 2-4. 택배사 상태 문자열 → 내부 상태
- 매핑 (`Xcz52Processor.mapToShipmentStatus`, 같은 내용이 `Xfr60CommandService.java:399-404`에도 있다)
  - `"배송완료"` → `DELIVERED`
  - `"배송출발"` → `OUT_FOR_DELIVERY`
  - 그 외 모든 문자열(예: 집화, 간선상차 등) → `IN_TRANSIT`
- 처리 분기 (`Xcz52Processor.java:101-126`)
  - 새 상태 == 현재 상태 → 변경 없이 그대로 반환(`:101-105`).
  - `DELIVERED` → 배송 `DELIVERED`로 변경, `completeOrder`, `notifyShipmentCompleted`.
  - `OUT_FOR_DELIVERY` → 배송 상태 변경만.
  - 그 외 → `IN_TRANSIT`으로 변경.
- 전이 검사: `Xfr60.updateStatus`는 `canTransitionTo`를 검사해 위반하면 `IllegalStateException`을 던진다 — `Xfr60.java:47-55`, `D/m45/entity/Xzn53Status.java`.
  - `IN_TRANSIT → DELIVERED`와 `OUT_FOR_DELIVERY → DELIVERED`는 허용된다 — `Xzn53Status.java:19-20,26`.
  - `OUT_FOR_DELIVERY` 배송에 대해 택배사가 "배송출발" 이외의 문자열(→ `IN_TRANSIT`)을 돌려주면 `OUT_FOR_DELIVERY → IN_TRANSIT`은 허용되지 않아 예외가 난다(`:26`). 이 건은 5번의 실패 처리로 간다.

## 3. 배송 완료 판정 이후 (`DELIVERED`를 받은 경우)

`Xcz52Processor.java:108-117`, `Xfr60CommandService.completeOrder` (`:191-228`) 기준.

### 3-1. 상태 변경 순서
1. 배송 `Xfr60`: `IN_TRANSIT`/`OUT_FOR_DELIVERY` → `DELIVERED` — `Xcz52Processor.java:113`
2. `completeOrder(orderId)` 진입 — `Xcz52Processor.java:116`

      - 주문 입찰 → 판매 경로: 같은 조건이면 `Xpj42` SOLD 후 판매자 알림 — `:150-171`

| 수신자 | 내용 | 건수 | 근거 |

### 3-3. 주문 입찰·판매 입찰 상태
- **배송 완료 판정 처리에서는 바뀌지 않는다.** 입찰을 COMPLETED로 바꾸는 `updateOrderAndSaleBidStatusToCompleted`는 `updateTrackingInfo`(운송장 등록 시점, `:289`)에서만 호출된다. `completeOrder`와 배치 프로세서에는 호출이 없다.
- 따라서 배송 완료 시점에 주문 입찰(`Xtw92`)과 판매 입찰(`Xzt63`)은 `MATCHED`로 남는다. 이름상 "완료 처리"인 `completeOrder`는 주문(`Xhq12`)과 판매(`Xpj42`)만 건드린다.
- 근거: 일반 구매 입찰은 생성 시점에 이미 MATCHED다 — `D/m99/entity/Xtw92.java:75`(`assignOrder`), `D/m99/service/command/Xtw92CommandService.java:97-98`. 즉시 구매 입찰도 MATCHED로 만든다 — `Xtw92CommandService.java:196`.

## 4. 주문 종류별 차이

두 경우 모두 "배송 레코드가 IN_TRANSIT/OUT_FOR_DELIVERY로 배치에 잡힌 상태"를 전제로 3의 처리를 비교한다. 운송장 등록 API로는 두 경우 모두 그 상태가 만들어지지 않는다(1-3 참고). `/check-status`(`updateAndCheckShipmentStatus`)가 주문 상태를 건드리지 않고 배송만 `IN_TRANSIT`으로 만드는 경로다 — `Xfr60CommandService.java:473`.

### (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문: **끝까지 진행되지 않는다**
- 주문 상태는 `PREPARING`이다 — `Xhq12CommandService.java:174-177`.
- 순서: 배송 `DELIVERED`(메모리) → `completeOrder` → 주문 입찰 조회는 성공 → `order.updateStatus(COMPLETED)`에서 거부된다. `PREPARING`의 허용 목록은 `{IN_WAREHOUSE, SHIPMENT_STARTED}`다 — `Xhq12Status.java:26`, `Xhq12.java:113-121`.
- `Xxm16StatusException`은 `completeOrder`의 `catch (Exception)`에서 `Xzn53Exception(ORDER_NOT_FOUND_FOR_SHIPMENT)`로 변환돼 던져진다 — `Xfr60CommandService.java:221-227`.
- 결과: 배치에서는 해당 건이 스킵되고 트랜잭션이 롤백된다. 배송 `DELIVERED`, 주문 `COMPLETED`, 알림, 판매 `SOLD`가 모두 반영되지 않는다. 배송은 `IN_TRANSIT` 그대로이므로 6시간마다 재조회되며 매번 같은 이유로 스킵된다.

### (b) 즉시 구매로 만들어진 주문: **끝까지 진행된다 (단, 판매자 알림·판매 전이는 이미 결제 시점에 끝나 있다)**
- 주문은 `PENDING_PAYMENT`로 만들어지고 결제 처리 후에도 주문 상태가 바뀌지 않는다 — `Xhq12CommandService.java:241-245, 305`. 즉시 구매 입찰은 `order`와 `sale`이 연결돼 생성된다 — `Xtw92CommandService.java:189-207`.
- `PENDING_PAYMENT → COMPLETED`는 허용된다 — `Xhq12Status.java:24`. 그래서 `completeOrder`의 `order.updateStatus(COMPLETED)`(`:204`)가 성공한다.
- 판매(`Xpj42`)는 결제 처리 중에 이미 SOLD가 되었다: `processPayment` 안의 `notifyUsersAndUpdateSaleStatus`가 주문 입찰이 없을 때 판매 입찰을 통해 `sale.updateStatus(SOLD)`를 호출한다 — `D/m64/service/command/Xjt45CommandService.java:83,388-404`. 이때 결제 완료 알림은 구매자와 판매자에게 이미 나갔다(`:434-456`).
- 따라서 `updateSaleStatusToSold`의 `canTransitionTo(SOLD)`가 false(`Xpj42Status.java:23`)여서 판매 상태 변경과 창고 상태 변경, 판매자 알림은 모두 건너뛴다 — `Xfr60CommandService.java:119, 156`.
- 결과(배치 경로): 배송 `DELIVERED`, 주문 `COMPLETED`, 구매자 알림 2건(`[completeOrder]`, `[배송 완료]`), 판매자 알림 0건, 주문 입찰·판매 입찰은 `MATCHED` 유지.
- 참고: 수동 `/check-status`로 `DELIVERED`가 되면 `completeOrder`만 호출하고 `notifyShipmentCompleted`는 호출하지 않아 구매자 알림은 1건이다 — `Xfr60CommandService.java:484-488`.

## 5. 실패 처리 (주기 처리 중 한 건이 실패할 때)

- 설정: 청크 50, `faultTolerant().skip(Exception.class).skipLimit(50)` + SkipListener — `D/m45/config/Xpc23JobConfig.java:51-52,66-81`.
- 프로세서 안의 모든 예외는 `Xzn53Exception`으로 통일되어 던져진다(`Xcz52Processor.java:133-146`). 예: 파싱 실패, 브라우저 초기화 실패, `completeOrder` 실패, 상태 전이 거부.
- 실패한 건
  - 스킵 대상이다. 그 청크의 트랜잭션은 롤백되고, 해당 아이템만 건너뛰어 처리된다. `completeOrder`가 바꾼 주문/판매/알림도 같은 트랜잭션이라 함께 되돌아간다(`@Transactional` REQUIRED가 청크 트랜잭션에 참여, `Xfr60CommandService.java:190`).
  - `onSkipInProcess`에서 `[Skip] ... shipmentId, trackingNumber, status, 사유` 로그만 남는다 — `Xpc23JobConfig.java:252-266`.
  - 배송 상태는 이전(`IN_TRANSIT`/`OUT_FOR_DELIVERY`) 그대로이므로 다음 실행(6시간 후)에 다시 대상이 된다. 별도의 재시도 상한이나 실패 표시는 없다.
- 나머지 건
  - 계속 처리된다. 스킵 후 청크의 나머지 아이템이 다시 처리되어 커밋된다. 성공 건의 `DELIVERED`와 알림은 저장된다.
  - 스킵이 50건을 넘으면 Step(및 Job)이 실패하고 남은 건은 처리되지 않는다. 스케줄러는 예외를 `printStackTrace()`만 하고 다음 주기를 기다린다 — `Xzn53BatchScheduler.java:41-43`.
- 비슷한 이름의 `updateShipmentStatuses()`(`Xfr60CommandService.java:309-396`)는 건별 `try/catch`로 에러 카운트만 올리는 방식이지만 호출되지 않으므로 실제 동작이 아니다.
- 참고(추론): reader가 페이징(`JpaPagingItemReader`)인데 처리 중에 조회 조건 컬럼(`status`)이 바뀌어 대상에서 빠지므로, 대상이 50건을 넘으면 다음 페이지 오프셋에서 일부가 한 회차 누락될 수 있다. 이 부분은 코드를 실행해 확인하지 않았다.
