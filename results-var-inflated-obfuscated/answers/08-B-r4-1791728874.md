### 1-2. 상태 변경 순서와 알림 (코드가 의도한 순서)

8. 구매입찰과 판매입찰이 `MATCHED` 이면 `COMPLETED` 로 바꾼다 (`:289`, 본체는 `:412-440`).

의도상 알림은 구매자 1건(출발)과 판매자 1건(판매 완료)이다.

### 1-3. 실배송 일반 구매 입찰 주문에서 끝까지 성공하나 → **아니오, 4단계에서 실패한다**

**주문 상태가 왜 `PREPARING` 인가**
- 일반 구매 입찰 주문은 `createOrderFromBid` 에서 `PENDING_PAYMENT` 로 생성된다 (`D/m99/service/command/Xhq12CommandService.java:81`).
- 결제·배송 처리를 마치면 비창고 주문은 `PAYMENT_COMPLETED` 를 거쳐 `PREPARING` 에서 멈춘다.
  - 직접 서비스: `D/m99/service/command/Xhq12CommandService.java:175-176`
  - 실제 API 인 `POST /orders/{orderId}/process-payment-shipment` 는 Kafka 이벤트로 발행한다 (`D/m99/controller/command/Xhq12CommandController.java:42-60`).
  - 컨슈머 쪽 처리도 같다 (`D/m99/service/kafka/Xhq12EventConsumer.java:195`, `:216-217`).
- 코드 어디에서도 주문을 `SHIPMENT_STARTED` 로 바꾸지 않는다. 주문을 `IN_TRANSIT` 으로 바꾸는 곳은 `updateTrackingInfo` 의 `:260` 뿐이다 (`rg SHIPMENT_STARTED` 결과는 enum 과 라벨 매핑뿐).

**어디서 왜 실패하나**
- `:260` `order.updateStatus(IN_TRANSIT)` 는 `Xhq12.updateStatus` (`D/m99/entity/Xhq12.java:113-121`) 를 호출한다.
- 전이표는 `PREPARING → {IN_WAREHOUSE, SHIPMENT_STARTED}` 만 허용한다 (`D/m99/entity/Xhq12Status.java:26`). `IN_TRANSIT` 으로의 전이는 `SHIPMENT_STARTED` 에서만 가능하다 (`:28`).
- 따라서 `Xxm16StatusException("상태 전환이 허용되지 않습니다: PREPARING -> IN_TRANSIT")` 이 발생한다 (`Xhq12.java:117-119`).
- 이 예외는 `updateTrackingInfo` 의 `catch (Exception e)` 에 잡힌다 (`Xfr60CommandService.java:295-302`). 여기서 `Xzn53Exception(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")` 으로 감싸 다시 던진다.

**무엇이 저장되나 → 아무것도 저장되지 않는다**
- 메서드가 `@Transactional` 이고 (`:238`) 런타임 예외가 밖으로 나가므로 롤백된다.
- 3번에서 메모리상 바꾼 배송의 courier·trackingNumber·`IN_TRANSIT` 은 DB 에 남지 않는다.
- 주문 상태는 `PREPARING` 그대로다.
- 5번 구매자 알림, 6번 판매자 알림, 8번 입찰 `COMPLETED` 는 실행되지 않는다.

**응답**
- `Xzn53Exception` 은 전역 핸들러 `handleShipmentException` 이 처리한다 (`B/global/exception/Xkt44ExceptionHandler.java:459-473`).
- 응답은 HTTP 404 이고 본문은 에러코드 `S001`, 메시지 "배송 정보를 찾을 수 없습니다." 이다 (`D/m45/exception/Xzn53ErrorCode.java:12`).
- 실제 원인은 주문 상태 전이 오류인데 "배송 정보 없음" 으로 보인다.

**부연: 즉시 구매 주문**
- 즉시 구매 주문(`createInstantOrder`)은 `PENDING_PAYMENT` 로 생성된다 (`D/m99/service/command/Xhq12CommandService.java:244`). 결제 처리(`:305`) 후에도 상태를 바꾸지 않는다.
- 이 상태에서도 `PENDING_PAYMENT → IN_TRANSIT` 은 허용되지 않는다 (`Xhq12Status.java:24`). 같은 지점에서 같은 방식으로 실패한다.

## 2. 배송 완료 감지

### 2-1. 누가, 언제, 어떻게
- 스프링 배치 잡 `updateShipmentStatusesJob` 을 스케줄러가 주기적으로 실행한다.

- 스케줄링 활성화는 `@EnableScheduling` 이 다른 설정 클래스에 선언돼 있어 전역으로 켜진다 (`D/m84/config/Xzh65Configuration.java:37`).

### 2-2. 주기

### 2-4. 실제 실행되는 처리 코드

  1. 운송장이 비어 있으면 예외를 던진다 (`:63`).

  3. `tbody#statusDetail tr` 를 기다린다 (`:87`).
  4. 마지막 행의 5번째 `td`(`get(4)`) 텍스트를 상태 문자열로 쓴다 (`:181`).
  5. 상태를 매핑한 뒤 아래 분기를 탄다 (`:94-125`).
- 같은 잡 설정 안의 `shipmentItemProcessor` 빈 (`Xpc23JobConfig.java:106-`) 은 스텝에 연결되지 않은 죽은 코드다. 스텝은 `new Xcz52Processor` 를 쓴다 (`:69`).

  - 6개 모두 같은 로직이라 어느 쪽이 선택되어도 결과가 같다. 빈 이름 충돌을 허용하는 설정은 찾지 못했다 (`application*.yml` 에 `allow-bean-definition-overriding` 없음).

## 4. 주문 종류별 차이

### (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문 → 끝까지 진행되지 않는다

**전제**
- 주문은 `PREPARING` 이다 (1-3 참고).
- 송장 등록 API(`PATCH …/status`)가 1-3 에서 실패하므로 배송은 `PENDING` 에 송장 없음으로 남는다. 이 상태에서는 배치 대상이 되지 않는다 (`status IN ('IN_TRANSIT','OUT_FOR_DELIVERY')` 필요, `Xpc23JobConfig.java:95`).
- `check-status` 엔드포인트로 배송을 `IN_TRANSIT` 으로 만든 경우(`Xfr60CommandService.java:473`)에만 배치 대상이 된다. 이 경로는 주문 상태를 바꾸지 않아 주문은 `PREPARING` 이다.

**배치가 `DELIVERED` 를 판정한 이후**
1. 배송을 `DELIVERED` 로 바꾼다 (`Xcz52Processor.java:113`). 아직 메모리상이다.
2. `completeOrder` 가 `order.updateStatus(COMPLETED)` 를 호출한다 (`Xfr60CommandService.java:204`).
3. 전이표 `PREPARING → {IN_WAREHOUSE, SHIPMENT_STARTED}` 때문에 `COMPLETED` 로 갈 수 없다 (`Xhq12Status.java:26`). `Xxm16StatusException` 이 난다 (`Xhq12.java:113-121`).
4. `completeOrder` 의 catch 가 `Xzn53Exception(ORDER_NOT_FOUND_FOR_SHIPMENT)` 로 감싸 던진다 (`Xfr60CommandService.java:221-227`).
5. 프로세서가 `Xzn53Exception` 을 그대로 다시 던지고 (`Xcz52Processor.java:145`) 스킵 처리된다 (5번 참고).

**결과**
- 배송 `DELIVERED` 변경은 롤백된다.
- 주문은 `PREPARING`, 구매입찰 `MATCHED`, 판매입찰 `MATCHED` 그대로다.
- 알림은 없다. `completeOrder` 의 구매자 알림(`:212`)은 실패 지점 뒤이고, `notifyShipmentCompleted` 도 도달하지 못한다.
- 배송은 `IN_TRANSIT` 으로 남아 6시간마다 같은 조회와 같은 실패를 반복한다.
- 주문 쪽 전이를 통과했다 해도, 구매 입찰 주문에는 `saleBid` 가 연결돼 있지 않으면 `updateSaleStatusToSold` 의 `findByOrderId` 가 `IllegalArgumentException` 을 던진다 (`Xzt63QueryService.java:26-29`, 호출 `Xfr60CommandService.java:116`). 이 경우도 `completeOrder` 의 catch 에서 같은 `ORDER_NOT_FOUND_FOR_SHIPMENT` 가 된다.

### (b) 즉시 구매로 만들어진 주문 → 3의 처리가 끝까지 진행된다

**전제**
- 즉시 구매 주문은 `PENDING_PAYMENT` 로 생성되고 (`D/m99/service/command/Xhq12CommandService.java:244`) 결제 후에도 주문 상태를 바꾸지 않는다.
- 즉시 구매는 구매입찰(`isInstantPurchase=true`, `MATCHED`, `order` 와 `sale` 연결)을 만든다 (`D/m99/service/command/Xtw92CommandService.java:189-206`).
- 판매입찰에도 주문을 연결한다: `saleBid.assignOrder(order)` (`Xhq12CommandService.java:279`).
- 따라서 `completeOrder` 가 쓰는 두 조회가 모두 성공한다.
  - 구매입찰 `findByOrderId` (`D/m99/service/query/Xtw92QueryService.java:51-55`)
  - 판매입찰 `findByOrderId` (`Xzt63QueryService.java:26-29`)

**3의 처리 결과**
1. 배송 `→ DELIVERED`.
2. 주문 `PENDING_PAYMENT → COMPLETED` 는 허용된다 (`Xhq12Status.java:24`). 주문이 `COMPLETED` 가 된다.
3. 판매 `→ SOLD`.
   - 판매가 `ON_AUCTION`/`SELLING` 일 때만 전이한다.
   - 이때 판매자 알림 1건이 나가고, 창고보관이면 창고 상태도 갱신한다.
4. 구매자 알림 2건.
5. 구매입찰·판매입찰은 `MATCHED` 그대로다 (3-3).

**진입 조건**
- 송장 등록 API(`PATCH …/status`)는 (b) 에서도 `PENDING_PAYMENT → IN_TRANSIT` 이 막혀 실패한다 (1-3 부연).
- 배치에 들어오려면 `check-status` 로 배송을 `IN_TRANSIT` 으로 만들어야 한다.
- `check-status` 로 `DELIVERED` 가 즉시 판정되면 `completeOrder` 만 호출하고 `notifyShipmentCompleted` 는 호출하지 않는다 (`Xfr60CommandService.java:483-489`). 이 경우 구매자 알림은 1건이다.

### 차이 요약
| | (a) 일반 구매 입찰, `PREPARING` | (b) 즉시 구매, `PENDING_PAYMENT` |
|---|---|---|
| 송장 등록 API | 실패 (`PREPARING → IN_TRANSIT` 불가) | 실패 (`PENDING_PAYMENT → IN_TRANSIT` 불가) |
| 배송 완료 후 `completeOrder` | 실패 (`PREPARING → COMPLETED` 불가) | 성공 |
| 주문 최종 상태 | `PREPARING` | `COMPLETED` |
| 알림 | 없음 | 구매자 2건 (+ 판매 `SOLD` 가능 시 판매자 1건) |
| 입찰 상태 | 변화 없음 | 변화 없음 (둘 다 `MATCHED`) |

## 5. 실패 처리 (주기 처리 중 한 건 실패)

**프로세서에서 던지는 예외**
- 모든 예외는 `Xzn53Exception` 이 된다. `Xzn53Exception` 이 아닌 예외는 `EXTERNAL_TRACKING_SERVICE_ERROR` 로 감싸 던지고, `Xzn53Exception` 이면 그대로 던진다 (`D/m45/config/Xcz52Processor.java:131-146`).
- Playwright 페이지는 `finally` 에서 닫는다 (`:148-157`).

**스텝 설정**
- `faultTolerant().skip(Exception.class).skipLimit(50)` 이다 (`D/m45/config/Xpc23JobConfig.java:75-77`).
- 따라서 한 건의 처리 예외는 잡 전체를 중단시키지 않고 그 건만 스킵된다.

**스킵된 건**
- 청크 트랜잭션이 롤백된다.
- 그 건의 `DELIVERED` 변경이나 주문·판매 변경은 DB 에 저장되지 않는다. 메모리상의 변경이 롤백된다. 청크 단위 롤백 후 스프링 배치가 아이템을 하나씩 다시 처리한다.
- 스킵 사실은 `SkipListener.onSkipInProcess` 가 에러 로그로만 남긴다 (`Xpc23JobConfig.java:252-262`).
- 상태가 그대로이므로 다음 실행(6시간 뒤)에 다시 대상이 된다.

**나머지 건**
- 같은 청크의 다른 건은 재처리되어 정상 건은 성공하고 저장된다.
- 청크 밖의 다른 건도 계속 처리된다.
- 한도(50건)를 넘기면 `SkipLimitExceededException` 으로 스텝이 실패하고 이후 건은 그 회차에 처리되지 않는다.
- 잡 실행 예외는 스케줄러가 `printStackTrace` 만 하고 삼킨다 (`B/global/config/Xzn53BatchScheduler.java:41-43`).
- 알림 발송 실패(`notifyShipmentCompleted`)는 메서드 안에서 예외를 삼키므로 배송 처리를 실패시키지 않는다 (`D/m52/service/command/Xbp24CommandService.java:230-233`).
- 외부 알림 서비스가 아닌 `createNotification` (`completeOrder` 내부) 의 예외는 `completeOrder` 의 catch 로 가 같은 스킵 경로를 탄다 (`Xfr60CommandService.java:221-227`).
