# 즉시 구매 처리 흐름

경로 표기: `D` = `src/main/java/com/fream/back/domain`. 기준 구현은 `/order-bids/instant`(m99)다. m10(`/internal/order-bids`), m27(`/legacy/order-bids`), m96(`/settlement/order-bids`)에 같은 로직의 복제본이 있고(`nav/m27.md:13`, `nav/m96.md:11`), 이 답은 m99 기준이다.
(`/sale-bids/instant`(m85)는 반대로 *판매자*가 구매 입찰을 골라 즉시 판매하는 API라서 해당 없음: `D/m85/controller/command/Xzt63CommandController.java:43-55`.)

## 1. 진입 API와 처리 단계 / 동기 여부 / 응답 ID

- **API**: `POST /order-bids/instant` — `D/m99/controller/command/Xtw92CommandController.java:22`(base path `/order-bids`), `:89-90`. 요청 DTO는 `saleBidId`, `addressId`, `warehouseStorage`, `paymentRequest` (`D/m99/dto/Xcr44RequestDto.java`).
- **처리 단계** (모두 한 호출 스택, 한 트랜잭션):
  1. 컨트롤러가 로그인 이메일을 추출한다 (`Xtw92CommandController.java:92`). `paymentRequest.userEmail`을 로그인 이메일로 덮어쓰고 `orderId`를 null로 둔다 (`:98`, `:119-122` `enrichPaymentRequest`).
  2. `Xtw92CommandService#createInstantOrderBid` (`D/m99/service/command/Xtw92CommandService.java:118-149`, `@Transactional`). 입력 검증 (`:154-167`), 구매자 조회 (`:126`), 판매 입찰 조회·검증 (`:129`, `:172-184`).
  3. `Xhq12CommandService#createInstantOrder` (`D/m99/service/command/Xhq12CommandService.java:219-319`):
     배송지 조회 (`:238`) → 주문 저장 (`:241-247`) → 주문 항목 생성 (`:255-256`) → 배송 정보 생성 (`:264-271`) → 판매 입찰 매칭 + flush (`:279-283`) → (판매자 창고 보관이면) 창고 상태 갱신 (`:290-301`) → 결제 처리 (`:305`).
  4. 결제 서비스 `Xjt45CommandService#processPayment` (`D/m64/service/command/Xjt45CommandService.java:57-107`)가 결제 유형별 결제를 만들고, 이어 `notifyUsersAndUpdateSaleStatus`로 알림 + 판매 SOLD 처리 (`:83`, `:383-426`).
  5. 마지막으로 구매 입찰(OrderBid)을 만든다 (`Xtw92CommandService.java:142`, `:189-207`).
- **동기/비동기**: 전부 동기다. 컨트롤러가 `createInstantOrderBid(...)`를 호출하고 반환값의 `.getId()`를 바로 응답한다 (`Xtw92CommandController.java:101-109`). 이 경로에는 Kafka 발행이 없다. 일반 주문의 `orderEventProducer.sendOrderProcessingEvent`는 다른 컨트롤러(`D/m99/controller/command/Xhq12CommandController.java:54`)에만 있다. `Xhq12CommandService`가 주입받은 클래스에도 이벤트 프로듀서는 없다 (`Xhq12CommandService.java:38-46`).
- **응답 ID**: 변수 이름은 `orderId`지만 (`Xtw92CommandController.java:101`, 메시지 "즉시 구매가 성공적으로 처리되었습니다." `:109`) 서비스가 반환하는 것은 `Xtw92`(OrderBid, 구매 입찰) 엔티티다 (`Xtw92CommandService.java:119`, `:142-144`). 따라서 `.getId()`는 **주문(Order, `Xhq12`)의 ID가 아니라 구매 입찰(OrderBid)의 ID**다. 주문 ID는 응답에 없다.

## 3. 결제 수단별 결과 / 끝까지 성공하는가 / 카드 실패 응답

`processPayment`는 `paymentType`(`CARD`/`ACCOUNT`/`GENERAL`)으로 분기한다 (`Xjt45CommandService.java:67-80`, DTO 다형성 `D/m64/dto/Xjt45RequestDto.java:20-25`).

- **카드(CARD)**: `Xjt45CommandService.java:157-225`. 저장된 결제 정보를 조회해 (`:166`) PortOne(아임포트) 호출 `portOneApiClient.processCardPayment` (`:179`)을 한다. 응답의 `status`가 `"success"`일 때만 `PAID` + `isSuccess=true` (`:203-206`). 아니면 상태는 엔티티 기본값 `PENDING` 그대로 저장된다 (`D/m64/entity/Xjt45.java:44`, `:208`).
- **계좌이체(ACCOUNT)**: `Xjt45CommandService.java:236-279`. 은행명만 검증하고 (`:244`, `:470-488`) 외부 호출 없이 `Xkg34`를 `PENDING`으로 저장한다 (`:260-262`). 이후에도 `PAID`로 바꾸는 단계가 없다.
- **일반 결제(GENERAL)**: `Xjt45CommandService.java:290-333`. `impUid`가 비어 있지 않은지만 보고 (`:297`), 외부 검증 없이 `isSuccess=true`, `PAID`로 저장한다 (`:313-314`).
- **세 방식 공통**: 결제 성공/실패와 무관하게 `processPayment`가 예외 없이 반환되면 알림 발송과 판매 SOLD 처리가 이어진다 (`:83`). 즉 계좌이체는 결제가 `PENDING`인데도 즉시 구매가 "성공"한다.
- **카드 실패 응답 — 두 경우**:
  1. PortOne HTTP가 200이 아니거나 body의 `code != 0`이면 `Xtc14Exception` (`D/m64/p02/Xhs91ApiClient.java:270-275`). `Xtc14Exception`은 `Xjt45Exception` 계열의 RuntimeException (`D/m64/exception/Xtc14Exception.java:6`, `D/global/exception/Xkt44Exception.java:10`)이라 `createCardPayment`에서 그대로 던져진다 (`Xjt45CommandService.java:218-219`). 이어 `Xwf42Exception`(`Xhq12Exception`)으로 감싸져 (`Xhq12CommandService.java:305-309`) `Xtw92CommandService#handleOrderBidCreationException`이 그대로 재던진다 (`:212-214`). `@Transactional` 안에서 RuntimeException이므로 주문·주문항목·배송·판매입찰 MATCHED 등이 전부 롤백되고, 클라이언트는 `Xkt44ExceptionHandler`의 `Xhq12Exception` 처리로 오류 응답을 받는다 (`D/global/exception/Xkt44ExceptionHandler.java:325`).
  2. PortOne이 `code == 0`으로 응답하되 `response.status`가 `"success"`가 아닌 경우(실패/미결제 등). 예외가 없으므로 `PENDING` 카드 결제가 저장되고 (`Xjt45CommandService.java:203-208`) 흐름이 계속된다. 판매 입찰 MATCHED, 구매자·판매자 "결제 완료" 알림, 판매 `SOLD`, OrderBid `MATCHED`가 모두 진행되어 **결제 실패인데도 즉시 구매가 성공 처리된다**. 응답도 200 + 성공 메시지다.
- **재시도**: `processCardPayment`에 `@Retryable`(3회)이 붙어 있지만 (`Xhs91ApiClient.java:224-228`) 저장소에 `@EnableRetry`가 없어 (`grep EnableRetry src` 결과 없음) 동작하지 않는다. 또 `code != 0` 실패는 재시도 대상 `Xjt45ApiException`이 아니라 `Xtc14Exception`이다.
- **결제 실패 시 환불 처리 없음**: `handleRefundIfNecessary`(`Xjt45CommandService.java:341`)는 정의만 있고 이 흐름에서 호출되지 않는다.

## 4. 알림 대상, 시점, 전달 방식

- **대상 2명**: 구매자(`order.getUser()`)와 판매자(`sale.getSeller()`) — `Xjt45CommandService#sendNotifications` (`:434-456`).
  - 구매자: "결제가 완료되었습니다. 주문 ID: {orderId}" (`:438-443`).
  - 판매자: "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}" (`:449-454`).
  - 카테고리 `SHOPPING`, 타입 `BID` (`:440-441`).
- **시점**: 결제 생성 직후, 같은 트랜잭션·같은 스레드에서 동기로 보낸다 (`:83` → `:383-426`). 즉시 구매 호출 안에서 OrderBid 생성(`Xtw92CommandService.java:142`) *이전*이다. 이때 주문의 `orderBid`는 아직 null이라 `saleBidQueryService.findByOrderId`로 판매 입찰→판매를 찾아 알림을 보낸다 (`Xjt45CommandService.java:388-406`; 4단계에서 flush했기 때문에 조회 가능 `Xhq12CommandService.java:283`).
- **방식**: `Xbp24CommandService#createNotification`(`D/m52/service/command/Xbp24CommandService.java:44-67`)이 (a) DB에 알림 행을 저장하고 (`:52-53`), (b) 실시간 전송을 시도한다 (`:57`). (b)는 Redis에 `WebSocket:Xjm45:{email}` 키가 있을 때만(접속 중일 때만) STOMP `/queue/notifications`로 `convertAndSendToUser`한다 (`:303-323`, `:37-38`). 미접속이면 저장만 되고 푸시는 없다 (`:320-321`). Kafka `notification-topic`은 이 경로에서 쓰지 않는다.
- **알림 실패는 삼켜진다**: `sendNotifications`는 자체 try/catch로 경고 로그만 남기고 (`Xjt45CommandService.java:457-461`), 상위 `notifyUsersAndUpdateSaleStatus`도 모든 예외를 로그만 남기고 삼킨다 (`:421-425`). 알림이 실패해도 구매는 성공하며 판매 `SOLD` 처리(`:404`)는 계속 진행된다.
- 구매자·판매자 외에 "판매 입찰이 매칭되었다"는 별도 알림은 없다.

## 5. 최종 주문 상태와 "창고 보관" 선택의 영향

- **주문의 최종 상태는 `PENDING_PAYMENT`** 다. 즉시 구매 경로는 주문 상태를 한 번도 갱신하지 않는다. 주문 생성 시 `PENDING_PAYMENT` (`Xhq12CommandService.java:244`)가 마지막 값이다. `PAYMENT_COMPLETED`/`PREPARING`/`COMPLETED` 전환은 일반 주문 경로 `processPaymentAndShipment` (`:111-202`) 안에만 있고, 즉시 구매는 이 메서드를 호출하지 않는다 (`Xtw92CommandService.java:119-149`). 결제가 `PAID`여도(카드 성공, 일반 결제) 주문은 `PENDING_PAYMENT`이고, 같이 바뀌는 것은 SaleBid `MATCHED`, Sale `SOLD`, OrderBid `MATCHED`뿐이다.
- 메서드 이름과 응답 메시지는 "즉시 구매 성공"이지만 실제 주문 상태는 결제 완료로 바뀌지 않는다. 또 `order.assignPayment(payment)`도 호출하지 않아 `Xhq12.payment` 필드는 설정되지 않는다 (`Xhq12CommandService.java:305`는 반환값을 버림, payment 쪽 `order` FK만 설정 `Xjt45CommandService.java:200`).
- **구매자가 "창고 보관"을 선택한 경우**: 컨트롤러가 `isWarehouseStorage`를 서비스로 넘기고 (`Xtw92CommandController.java:101-106`) `createInstantOrder`의 파라미터로도 받지만 (`Xhq12CommandService.java:220-221`), 메서드 본문에서 **한 번도 사용되지 않는다** (`:222-319` 어디에도 없음). `createOrderStorage`(창고 보관 레코드 생성, `D/m63/service/command/Xms75CommandService.java:33-57`)는 일반 주문 경로 `processPaymentAndShipment`에서만 호출된다 (`Xhq12CommandService.java:170`). 결과적으로 구매자가 창고 보관을 고르든 말든 즉시 구매 결과(주문 상태, 창고 레코드, 알림)는 **달라지지 않는다**. 창고 관련 동작은 판매자가 판매 입찰 시 고른 `sale.isWarehouseStorage()`로만 결정되고, 그 경우에도 판매자 쪽 기존 창고 레코드 상태가 `ASSOCIATED_WITH_ORDER`로 바뀌는 것이 전부다 (`Xhq12CommandService.java:290-294`).
