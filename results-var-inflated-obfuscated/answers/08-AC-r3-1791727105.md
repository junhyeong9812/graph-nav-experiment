# 구매자 배송: 운송장 등록 → 배송 완료

경로 약어: `D` = `src/main/java/com/fream/back/domain`, `G` = `src/main/java/com/fream/back/global`

핵심 요약
- 구매자 배송 엔티티 = `Xfr60`(테이블 `order_shipment`, `D/m45/entity/Xfr60.java:15-16`), 상태 enum = `Xzn53Status`.
- 서비스는 `D/m45/service/command/Xfr60CommandService.java` 하나뿐이고, 다른 도메인(m09/m31/m38/m70/m81)의 컨트롤러·잡 설정은 이 서비스·엔티티를 그대로 호출하는 복제본이다.
- 일반(실배송) 구매 입찰 주문은 운송장 등록 단계에서 **주문 상태 전이 규칙 위반으로 실패**한다. 코드상 주문 상태를 `SHIPMENT_STARTED`로 보내는 곳이 없어서 `IN_TRANSIT`으로 갈 수 없다.

## 0. 선행: 결제·배송 처리 후 상태 (질문 1-c, 4의 전제)

- 일반 입찰 주문 생성: 주문 `PENDING_PAYMENT` (`D/m27/service/command/Xnt31CommandService.java:76-82`).
- 결제·배송 처리 후(Kafka 컨슈머 `processCompleteOrder`, 실제 경로):
  - 결제 `processPayment` → `order.assignPayment` (`D/m27/service/kafka/Xnt31EventConsumer.java:171-172`).
  - 배송 `createOrderShipment`가 `Xfr60`을 `status=PENDING`으로 생성 (`D/m45/service/command/Xfr60CommandService.java:56-75`, 상태 지정 `:69`; 컨슈머 호출 `Xnt31EventConsumer.java:181-188`).
  - 주문 `PENDING_PAYMENT → PAYMENT_COMPLETED` (`Xnt31EventConsumer.java:192-195`).
  - 비창고(실배송)이면 `→ PREPARING`에서 끝 (`Xnt31EventConsumer.java:215-218`). 창고 보관이면 `IN_WAREHOUSE → COMPLETED`까지 간다 (`:203-211`).
  - 동기 경로 `Xnt31CommandService#processPaymentAndShipment`도 같은 결과(`PAYMENT_COMPLETED → PREPARING`, `Xnt31CommandService.java:175-176`).
- 결제 처리 중 `notifyUsersAndUpdateSaleStatus`가 구매자·판매자에게 "결제 완료" 알림을 보내고 **판매(`Xpj42`)를 즉시 `SOLD`로 바꾼다** (`D/m64/service/command/Xjt45CommandService.java:83`, `:383-419`, `SOLD` 설정 `:404`, `:419`; 알림 `sendNotifications` `:434-460`). 판매 상태 변경은 전이 검사 없는 setter다 (`D/m85/entity/Xpj42.java:73-75`).
- 주문 상태 전이표 (`D/m99/entity/Xhq12Status.java:24-32`):
  - `PENDING_PAYMENT → {PAYMENT_COMPLETED, COMPLETED, IN_WAREHOUSE}`
  - `PREPARING → {IN_WAREHOUSE, SHIPMENT_STARTED}`
  - `SHIPMENT_STARTED → {IN_TRANSIT}`
  - `IN_TRANSIT → {COMPLETED}`
  - 위반 시 `Xxm16StatusException` (`D/m99/entity/Xhq12.java` `updateStatus`, "상태 전환이 허용되지 않습니다").
- `SHIPMENT_STARTED`를 대입하는 코드는 enum 정의 외에 없다. 조회 컨트롤러 `switch`에서 라벨만 쓴다 (예: `D/m99/controller/query/Xhq12QueryController.java:207`).

4. 주문 `order.updateStatus(IN_TRANSIT)` (`:259-260`).
5. 알림 1건: 구매자에게 "상품이 출발하였습니다. 주문 ID: …" (`:265-270`).
6. `updateSaleStatusToSold(orderId)` (`:274`):
   - 판매(`Xpj42`) `SOLD` 전이 가능 시 `SOLD`로 바꾸고 판매자에게 "상품이 성공적으로 판매 완료…" 알림 (`:116-139`, orderBid 기반 `:151-170`).
   - 창고 보관 상품이면 창고 상태 `SOLD` (`:126-128`).
7. 창고 보관 판매 건이면 창고 상태 업데이트를 한 번 더 호출 (`:279-286`).
8. `updateOrderAndSaleBidStatusToCompleted(orderId)` (`:289`):
   - `Xtw92`(주문 입찰) `MATCHED → COMPLETED`, `Xzt63`(판매 입찰) `MATCHED → COMPLETED` (`:413-434`).
   - 이 메서드는 내부에서 예외를 삼킨다 (`:436-438`).
- 즉 코드 의도는 "운송장 등록 시점에 주문 `IN_TRANSIT`, 입찰까지 `COMPLETED`"이다. 이름·주석과 달리 배송 완료 이전에 입찰이 완료 처리된다.
- 알림 대상: 구매자 1건 + (판매 상태 전이가 가능할 때) 판매자 1건. `createNotification`은 DB 저장 + WebSocket 전송 (`D/m52/service/command/Xbp24CommandService.java:44-56`).

### 1-c. 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문 — 끝까지 성공하지 않는다

- 실패 지점: 4단계 `order.updateStatus(Xhq12Status.IN_TRANSIT)` (`Xfr60CommandService.java:260`).
  - 이유: 주문은 `PREPARING`(0절)이고, `PREPARING → IN_TRANSIT`은 전이표에 없다 (`Xhq12Status.java:26`). `SHIPMENT_STARTED`를 거치는 코드가 없다.
  - `Xhq12.updateStatus`가 `Xxm16StatusException`을 던진다 (`D/m99/entity/Xhq12.java`).
- 예외 변환:
  - `Xxm16StatusException`은 `Xzn53Exception`이 아니므로 `catch (Exception e)`로 들어가 `Xzn53Exception(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")`로 다시 던져진다 (`Xfr60CommandService.java:293-302`).
  - 이름은 `SHIPMENT_NOT_FOUND`지만 실제 원인은 주문 상태 전이 위반이다.
- 저장되는 것: 없음. 3단계에서 바꾼 courier/trackingNumber/`IN_TRANSIT`은 같은 `@Transactional`(`:238`)에서 RuntimeException이 전파되므로 롤백된다.
  - 구매자 알림(5단계)은 4단계 뒤라서 생성되지 않는다.
  - 결과적으로 배송은 `PENDING`, 주문은 `PREPARING`, 운송장 번호는 null로 남는다.
- 응답: `Xkt44ExceptionHandler`가 `ErrorResponse(code="S001", message="배송 정보를 찾을 수 없습니다.", status=404, path)`를 **HTTP 404**로 반환한다 (`G/exception/Xkt44ExceptionHandler.java:49-63`; `SHIPMENT_NOT_FOUND("S001", …, 404)` — `D/m45/exception/Xzn53ErrorCode.java:11`). `Xkt44Exception`은 RuntimeException (`G/exception/Xkt44Exception.java:10`).
- 즉시 구매 주문도 같은 이유로 실패한다. 즉시 구매 주문은 결제·배송 처리 후에도 `PENDING_PAYMENT`이고 `PENDING_PAYMENT → IN_TRANSIT`도 금지다 (`Xnt31CommandService.java:241-245`에서 생성 후 상태 변경 없음, `Xhq12Status.java:24`).
- 창고 보관(`IN_WAREHOUSE → COMPLETED`) 주문은 이미 `COMPLETED`라 `COMPLETED → IN_TRANSIT`이 금지되어 역시 실패한다 (`Xhq12Status.java:31`).

## 2. 배송 완료 감지

### 2-a. 누가·언제·어떻게

- 배치 스케줄러 `Xzn53BatchScheduler#scheduleShipmentStatusJob`이 감지한다 (`G/config/Xzn53BatchScheduler.java:34-44`).
  - `jobLauncher.run(updateShipmentStatusesJob, timestamp 파라미터)`로 Spring Batch 잡을 기동한다 (`:36-40`).
  - 예외는 `printStackTrace`만 한다 (`:42`).
- 주기: `@Scheduled(cron = "0 0 */6 * * *")` = 매일 0·6·12·18시 정각, 6시간마다 (`:34`).
- 운송장 등록 API는 감지를 직접 하지 않는다. 즉시 조회는 `check-status` API(1-a)에서만 수동으로 일어난다.

### 2-b. 대상·실제 실행되는 코드

- 잡 `updateShipmentStatusesJob` → 스텝 `updateShipmentStatusesStep` (`D/m45/config/Xpc23JobConfig.java:54-58`, `:61-82`).
  - 청크 50, 스킵 한도 50 (`:51-52`).
  - 쿼리 (`:95`): `SELECT s FROM Xfr60 s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL`.
  - 즉 `PENDING`/`SHIPPED`/`DELIVERED` 등은 대상이 아니다.
- 실제 실행 프로세서 = `Xcz52Processor` (`Xpc23JobConfig.java:69`에서 `new Xcz52Processor(...)`).
  - 흐름 (`D/m45/config/Xcz52Processor.java:49-139`):
    1. Playwright 페이지를 열고 `https://trace.cjlogistics.com/next/tracking.html?wblNo=` + 운송장 번호로 이동 (`:28`, `:81-83`).
    2. `tbody#statusDetail tr`의 **마지막 행 5번째 td** 텍스트를 상태로 읽는다 (`parseStatusFromHtml`, `:140-185`).
  - 브라우저는 스텝 시작 시 `Xhd56Listener#beforeStep`에서 열고(`D/m45/config/Xhd56Listener.java:15-17`), 종료 시 닫는다.
- 실행되지 않는 유사 코드:
  - `Xpc23JobConfig#shipmentItemProcessor` (`:106`) — 스텝에 연결되지 않은 `@Bean`이다. 스텝은 `new Xcz52Processor`를 쓴다 (`:69`). Jsoup 파싱 메서드 `parseCjLogisticsStatus`(`:176`대)도 미사용.

  - 다른 도메인의 `*JobConfig`/`*Processor`(m09 `Xxt33JobConfig`/`Xzd96Processor`, m31, m38, m70, m81)는 `Xfr60`·`Xfr60CommandService`를 쓰는 복제본이다. 같은 이름의 `updateShipmentStatusesJob` 빈이 6개라서 이 중 하나를 쓰지만, 로직은 m45판과 동일하고 알림 서비스 클래스만 다르다 (예: m09는 `Xrw60CommandService#notifyShipmentCompleted`). 스케줄러가 `@Qualifier("updateShipmentStatusesJob")`로 주입하는 대상 (`Xzn53BatchScheduler.java:19-21`)이다.

## 3. 배송 완료 판정 이후 (`Xcz52Processor.java:109-118`)

판정이 `DELIVERED`일 때의 순서:

1. 배송 `Xfr60.updateStatus(DELIVERED)` — `IN_TRANSIT`/`OUT_FOR_DELIVERY → DELIVERED`는 전이표상 허용 (`:113`; 전이표 `D/m45/entity/Xzn53Status.java`; 검사 `Xfr60.java:47-54`).
2. `orderService.completeOrder(orderId)` (`:116`; 구현 `Xfr60CommandService.java:191-228`):
   - `orderBid`를 `findByOrderId`로 조회, 없으면 `IllegalArgumentException` (`:196-197`).
   - 주문 `order.updateStatus(COMPLETED)` (`:204`).
   - `updateSaleStatusToSold(orderId)` (`:208`) — 판매 `Xpj42`를 `SOLD`로 바꾸고 판매자 알림 (`:112-182`). 단 `canTransitionTo(SOLD)`가 참일 때만이다 (`:119`, `:156`).
   - 구매자 알림 "[completeOrder] 주문이 완료 처리되었습니다. 주문 ID: …" (`:211-217`).
   - 모든 예외를 `Xzn53Exception(ORDER_NOT_FOUND_FOR_SHIPMENT)`로 감싸 던진다 (`:221-227`).
3. `notificationService.notifyShipmentCompleted(order)` (`:117`) — 구매자에게 "[배송 완료] 상품이 배송 완료되었습니다." (`D/m52/service/command/Xbp24CommandService.java:216-229`). 예외는 내부에서 삼킨다 (`:230-233`).
4. 상태가 `DELIVERED`로 바뀐 배송은 `JpaItemWriter`가 저장한다 (`Xpc23JobConfig.java:80`대 `shipmentJpaItemWriter`).

### 알림 건수
- 구매자: 2건 ("[completeOrder] 주문이 완료 처리…" + "[배송 완료] …").
- 판매자: 판매가 `SOLD`로 전이 가능했을 때만 1건. 단 0절에서 본 것처럼 결제 시점에 이미 `SOLD`로 바뀌어 있어(`Xjt45CommandService.java:404`, `:419`) `SOLD.canTransitionTo(SOLD)`가 false → 보통 0건이다.
- 합계: 일반적으로 구매자 2건, 판매자 0건.

### 입찰 상태
- 배치 경로는 `Xtw92`(주문 입찰), `Xzt63`(판매 입찰)의 상태를 바꾸지 않는다. `updateOrderAndSaleBidStatusToCompleted`는 `updateTrackingInfo`(1-b 8단계)에서만 호출된다 (`Xfr60CommandService.java:289`).
- 결제·배송 처리 후 입찰은 `MATCHED`다 (`Xnt31CommandService.java:189`; `Xtw92.assignOrder` `D/m99/entity/Xtw92.java:60-80`). 배치 완료 후에도 `MATCHED` 그대로, `COMPLETED`가 되지 않는다.
- 운송장 등록이 1-c에서 실패하므로 `COMPLETED` 처리가 일어날 수도 없다.

## 4. 주문 종류별 차이 (3의 처리)

전제: 배치 대상이 되려면 배송이 `IN_TRANSIT`/`OUT_FOR_DELIVERY`여야 한다. 일반 주문 API(`updateTrackingInfo`)는 1-c로 실패하므로, 배송을 `IN_TRANSIT`으로 만드는 경로는 `check-status`(`updateAndCheckShipmentStatus`, 운송장 저장 시 배송만 `IN_TRANSIT` — `Xfr60CommandService.java:473`, 주문은 건드리지 않음)뿐이다. 이 경로로 배송이 `IN_TRANSIT`이 된 상태를 가정해 배치 처리를 비교한다.

### (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문 — 끝까지 진행되지 않음
- 주문은 `PREPARING` (0절). `completeOrder`의 `order.updateStatus(COMPLETED)`에서 `PREPARING → COMPLETED`는 전이표에 없어 `Xxm16StatusException` (`Xfr60CommandService.java:204`; `Xhq12Status.java:26`).
- `completeOrder`가 `Xzn53Exception(ORDER_NOT_FOUND_FOR_SHIPMENT)`로 감싸 던지고 (`:221-227`), 프로세서는 이를 그대로 다시 던진다 (`Xcz52Processor.java:128-139`) → 아래 5절 스킵.
- 결과: 배송 `IN_TRANSIT` 유지(롤백), 주문 `PREPARING`, 판매·입찰 변화 없음, 구매자 알림 0건(`notifyShipmentCompleted` 호출 전 중단).
- `check-status`로 직접 호출한 경우도 같은 `completeOrder`가 실패해 같은 결과다 (`Xfr60CommandService.java:489`) → 컨트롤러가 404 반환 (`Xfr60CommandController.java:73-80`).

### (b) 즉시 구매로 만들어진 주문 — 끝까지 진행됨 (일반 주문과 대비)
- 즉시 구매 주문은 `createInstantOrder`에서 `PENDING_PAYMENT`로 만들고 상태를 바꾸지 않는다 (`Xnt31CommandService.java:241-245`, 배송 `PENDING` 생성 `:264-271`). 주문 입찰 `Xtw92`는 `MATCHED`·`isInstantPurchase`로 별도 생성된다 (`D/m27/service/command/Xnw92CommandService.java:189-208`).
- `completeOrder`: `orderBid` 존재 → `PENDING_PAYMENT → COMPLETED`는 전이표 허용 (`Xhq12Status.java:24`) → 성공.
- `updateSaleStatusToSold`: 판매가 결제 시점에 이미 `SOLD`(`Xjt45CommandService.java:404`)이므로 판매자 알림·전이 없음.
- 결과: 배송 `DELIVERED`, 주문 `COMPLETED`, 구매자 알림 2건, 판매자 알림 0건, 주문 입찰·판매 입찰은 `MATCHED` 유지.
- 단, (b)도 운송장 등록 API(`updateTrackingInfo`)는 1-c처럼 실패하므로 배송을 `IN_TRANSIT`으로 만드는 경로는 마찬가지로 `check-status`뿐이다.

차이 요약: (a)는 주문이 `PREPARING`이라 `COMPLETED` 전이가 막혀 배송 완료 후처리가 전부 롤백되고, (b)는 `PENDING_PAYMENT`가 `COMPLETED`로 직접 전이되는 규칙 덕에 완료된다.

## 5. 실패 처리 (주기 처리 중 한 건 실패)

- 스텝은 `faultTolerant().skip(Exception.class).skipLimit(50)` (`Xpc23JobConfig.java:74-77`), 스킵 리스너 `shipmentSkipListener`가 로그만 남긴다 (`:77` 등록, 구현 `:244-275`대).
- 프로세서 예외는 `Xzn53Exception`으로 통일되어 던져진다 (`Xcz52Processor.java:128-139`: 비-`Xzn53Exception`은 `EXTERNAL_TRACKING_SERVICE_ERROR`로 감쌈; 운송장 번호 공백은 `TRACKING_NUMBER_INVALID` `:57-60`; 파싱 실패 `TRACKING_HTML_PARSE_ERROR`).
- 그 건:
  - 스킵 처리. 청크 트랜잭션이 롤백되고, 실패한 건을 뺀 나머지를 한 건씩 다시 처리·커밋한다.
  - 그래서 `DELIVERED`로 바꿨던 인메모리 변경과 `completeOrder` 변경도 저장되지 않는다. DB에서는 `IN_TRANSIT` 그대로이고 다음 6시간 주기에 다시 조회된다 (2-a, 2-b).
- 나머지 건: 계속 처리되어 정상 커밋된다. 스킵이 50건을 넘으면 `SkipLimitExceededException`으로 스텝(잡)이 실패한다.
- 잡 실행 자체의 예외는 스케줄러가 `catch (Exception) → printStackTrace`만 한다 (`Xzn53BatchScheduler.java:41-43`).
- 참고(미사용 경로): `updateShipmentStatuses`는 건별 try/catch로 `errorCount++` 후 계속하는 구조지만 호출되지 않는다 (`Xfr60CommandService.java:309-396`).
