# 즉시 구매 처리 흐름 분석

경로 약어: `D` = `src/main/java/com/fream/back/domain`.
공개(사용자) 경로는 m99(`/order-bids`)이다. `/legacy`, `/internal`, `/admin`, `/partner`, `/settlement` 아래에도 구조가 같은 복제본 컨트롤러·서비스가 있다(예: `D/m10/controller/command/Xnt62CommandController.java:22,89`). 아래는 m99 기준이다.

## 1. 진입 API, 처리 단계, 동기/비동기, 응답 ID

1. **진입점**: `POST /order-bids/instant`. 바디는 `Xcr44RequestDto`(saleBidId, addressId, warehouseStorage, paymentRequest)이다.
   - 근거: `D/m99/controller/command/Xtw92CommandController.java:22`(base path), `:89-90`(매핑)
2. **컨트롤러 단계**:
   - 인증 사용자의 이메일을 추출한다(`:92`).
   - 결제 요청 DTO에 `userEmail`을 넣고 `orderId`는 null로 비운다(`:98`, `:119-121`).
   - `orderBidCommandService.createInstantOrderBid(email, saleBidId, addressId, warehouseStorage, paymentRequest)`를 호출한다(`:101-107`).
3. **OrderBid 서비스 단계** (`D/m99/service/command/Xtw92CommandService.java:118-149`):
   1. 입력 검증: 이메일, saleBidId, addressId, paymentRequest가 null이면 예외(`:154-167`).
   2. 구매자 조회(`:126`).
   3. 판매 입찰 조회, 판매(Sale) 연결 여부 검증(`:129`, `:172-184`).
   4. `orderCommandService.createInstantOrder(...)` 호출(`:133-139`).
   5. 주문 입찰(OrderBid)을 생성해 저장(`:142`, `:189-207`).
4. **Order 서비스 단계** (`D/m99/service/command/Xhq12CommandService.java:219-319`), 순서대로:
   1. 배송지 조회: `addressQueryService.getAddress(buyer.getEmail(), addressId)`(`:238`).
   2. Order 생성·저장: totalAmount = 판매 입찰가, status = `PENDING_PAYMENT`(`:241-247`).
   3. `paymentRequest.setOrderId(order.getId())`(`:250`).
   4. OrderItem 생성: 수량 1, 가격 = 입찰가(`:255-256`, `D/m99/service/command/Xnd96CommandService.java:45-52`).
   5. OrderShipment 생성: 배송지 DTO 값 복사, status = `PENDING`(`:264-271`, `D/m45/service/command/Xfr60CommandService.java:61-70`).
   6. SaleBid 상태를 MATCHED로 바꾸고 order를 연결한 뒤 flush(`:279-283`).
   7. 판매 쪽 창고 보관 상태 갱신(`:291-294`).
   8. 결제 처리 `paymentCommandService.processPayment(...)`(`:305`).
   9. 알림 전송과 Sale을 SOLD로 변경(`D/m64/service/command/Xjt45CommandService.java:83`, `:383-426`).
5. **동기/비동기**: 전부 동기이며 한 트랜잭션이다.
   - 컨트롤러가 응답을 만들기 전에 위 단계가 모두 끝난다.
   - `@Transactional` 서비스 호출 체인이고(`Xtw92CommandService.java:118`, `Xhq12CommandService.java:219`, `Xjt45CommandService.java:37`), 결제도 `RestTemplate`으로 PortOne을 동기 호출한다(`D/m64/p02/Xhs91ApiClient.java:266`).
   - 이 경로에서는 Kafka 이벤트를 발행하지 않는다. Kafka 프로듀서(`Xhq12EventProducer`)는 `process-payment-shipment` 경로에서만 쓰인다(`D/m99/controller/command/Xhq12CommandController.java:30`, `D/m99/service/kafka/Xhq12EventProducer.java:34`).
   - 실제 PortOne 결제 호출은 `getAccessToken` 후 `/subscribe/payments/onetime`을 호출한다(`Xhs91ApiClient.java:238-266`).
6. **응답 ID**: 응답 `data`는 **OrderBid(주문 입찰)의 ID**이다.
   - 컨트롤러 변수명은 `orderId`지만 실제 값은 `createInstantOrderBid(...).getId()`, 즉 `Xtw92`(OrderBid) 엔티티의 id이다(`Xtw92CommandController.java:101-109`).
   - 주문(Order) ID가 아니다.
   - 메시지는 "즉시 구매가 성공적으로 처리되었습니다."이다(`:109`).

## 2. 생성되는 엔티티와 상태 변화 순서

생성은 아래 순서이며, 괄호는 직후 상태이다.

| 순서 | 동작 | 상태 값 | 근거 |
|---|---|---|---|
| 1 | Order 생성 | `PENDING_PAYMENT` | `Xhq12CommandService.java:241-247` |
| 2 | OrderItem 생성 | (상태 필드 없음, qty 1, price = 입찰가) | `Xnd96CommandService.java:45-52` |
| 3 | OrderShipment 생성 | `PENDING` | `Xfr60CommandService.java:67` |
| 4 | SaleBid: `assignOrder` + `updateStatus(MATCHED)` | `MATCHED` (`assignOrder`가 이미 MATCHED로 바꿈) | `Xhq12CommandService.java:279-280`, `D/m85/entity/Xzt63.java:58-61` |
| 5 | 판매자 Sale이 창고 보관이면 창고 보관 엔티티(Xms75) 상태 변경 | `ASSOCIATED_WITH_ORDER` | `Xhq12CommandService.java:291-294`, `D/m63/service/command/Xms75CommandService.java:117-133` |
| 6 | Payment 생성 (결제 수단별로 아래 3번 참고) | 카드: `PAID` 또는 `PENDING` / 계좌: `PENDING` / 일반: `PAID` | `Xjt45CommandService.java:203-206`, `:260`, `:313-314` |
| 7 | Sale 상태 변경 | `SOLD` (전이 검증 없음) | `Xjt45CommandService.java:404`, `:419`, `D/m85/entity/Xpj42.java:73-75` |
| 8 | OrderBid 생성·저장 | `MATCHED`, `isInstantPurchase = true`, sale 연결 | `Xtw92CommandService.java:192-205`, `D/m99/entity/Xtw92.java:60-82`, `:97-99` |

세부 사항:
- **Order**: 이후 상태 전이가 없다. 즉시 구매 경로에서 `Xhq12.updateStatus(...)`를 호출하는 곳이 없다. `PAYMENT_COMPLETED` 전이는 `process-payment-shipment` 경로(`Xhq12CommandService.java:165,175`, `D/m99/service/kafka/Xhq12EventConsumer.java:195`)에만 있다.
- **SaleBid(4)**: 호출 순서는 `Xjt45CommandService.java:391`의 `findByOrderId`가 이 시점(6, flush 이후)에 연결을 찾을 수 있게 만든다.
- **Payment(6)**: 전체 흐름에서 `order.assignPayment(...)`를 부르지 않는다. 결제 엔티티 쪽에서만 `assignOrder(order)`로 연결된다(`Xjt45CommandService.java:200`, `:258`, `:311`).
- **Sale SOLD(7)**: `notifyUsersAndUpdateSaleStatus`는 `order.getOrderBid()`가 null이므로(OrderBid는 이 시점 뒤에 생성됨) `saleBidQueryService.findByOrderId`로 SaleBid를 찾고 거기서 Sale을 얻는다(`Xjt45CommandService.java:388-407`).
- **OrderBid(8)**: 빌더에 `MATCHED`를 지정하고 `assignOrder`가 다시 MATCHED로 둔다. 이 시점에는 이미 Order의 결제가 처리된 뒤이다.
- **OrderBid 생성 시점**: OrderBid는 `createInstantOrder`가 끝난 뒤에야 만들어진다(`Xtw92CommandService.java:133-142`).

## 3. 결제 수단별 결과, 성공 여부, 카드 결제 실패 시

공통: 결제 유형은 `getResolvedPaymentType()`으로 분기한다(`Xjt45CommandService.java:67-80`). 요청 DTO의 `paidAmount`가 0 이하이면 예외이다(`:142-145`). **`paidAmount`는 입찰가와 대조하지 않고 클라이언트 값을 그대로 쓴다**(`:142`, `:193`).

| 수단 | 처리 | 결제 상태 | 근거 |
|---|---|---|---|
| CARD | 저장된 결제 정보 조회 후 PortOne 카드 결제 호출 | 응답 `status`가 문자열 `"success"`일 때만 `PAID` + `isSuccess=true`. 아니면 기본값 `PENDING` | `Xjt45CommandService.java:166-179`, `:203-206`, `D/m64/entity/Xjt45.java:44` |
| ACCOUNT | PG 호출 없음. 은행명 검증 후 저장 | 항상 `PENDING` | `Xjt45CommandService.java:244`, `:250-262` |
| GENERAL | PG 호출 없음. 클라이언트가 보낸 `impUid`를 신뢰해 저장 (`impUid` 비어 있으면 예외) | 즉시 `PAID`, `isSuccess=true` | `Xjt45CommandService.java:297-314` |

- **즉시 구매 전체 결과**: 결제 상태와 무관하게 끝까지 성공 처리된다. 결제 후 단계가 결제 상태를 확인하지 않는다.
  - 계좌이체(`PENDING`)여도 Sale은 `SOLD`가 되고, 구매자 알림은 "결제가 완료되었습니다"로 나간다(`Xjt45CommandService.java:83`, `:404`, `:438-443`).
  - 응답은 성공(`ResponseDto.success`)이다.
- **`isSuccess` 불일치**: 결제 엔티티의 `isSuccess`는 빌더 단계에서 `setPaidAmount`가 `paidAmount > 0`이면 true로 둔다(`D/m64/entity/Xxf47.java:36`, `D/m64/entity/Xjt45.java:60-63`, `D/m64/entity/Xkg34.java:28`). 계좌이체 `PENDING`이나 카드 비성공이어도 `isSuccess`는 true일 수 있다.
- **카드: 결제 대행사가 실패로 응답하면** 두 경우로 갈린다.
  1. **HTTP 비정상이거나 응답 `code != 0`**: `Xhs91ApiClient.processCardPayment`가 `Xtc14Exception`을 던진다(`Xhs91ApiClient.java:270-275`).
     - 이 예외는 `Xjt45Exception` 계열이라 그대로 재전파된다(`Xjt45CommandService.java:180-181`, `:218-219`).
     - `Xhq12CommandService`가 `Xwf42Exception`으로 감싸 던지고(`:304-309`), 그 아래 `Xhq12Exception` 계열이므로 그대로 올라간다(`:312-314`).
     - `Xtw92CommandService`도 그대로 재던진다(`:145-148`, `:212-217`).
     - 결과: 트랜잭션 전체가 롤백된다. Order, OrderItem, OrderShipment, SaleBid MATCHED, 결제 모두 취소되고 OrderBid도 생기지 않는다. 클라이언트는 오류 응답을 받는다.
  2. **응답 `code == 0`인데 `response.status`가 `"success"`가 아닌 경우** (카드 거절이 이렇게 오는 경우):
     - 예외가 없다. 카드 결제는 `PENDING`으로 저장되고(`FAILED`로 바뀌지 않음, `Xjt45CommandService.java:203-208`), 흐름은 계속된다.
     - 이후 알림 전송과 Sale `SOLD`까지 그대로 진행되어 요청은 성공 응답을 반환한다(`:83`, `:404`).
     - 즉 카드 실패가 성공 구매로 처리된다. `"success"`라는 리터럴만 비교하며 다른 값("paid" 등)이면 항상 `PENDING`이다.
- 결제 후 알림·Sale 상태 갱신은 자체 try/catch로 예외를 삼키므로 이 단계 실패는 구매 실패로 이어지지 않는다(`Xjt45CommandService.java:421-425`). 단, 아래 4번 참고.

## 4. 알림 대상, 시점, 방식

- **수신자 2명**(`Xjt45CommandService.java:434-456`):
  - **구매자**: "결제가 완료되었습니다. 주문 ID: {orderId}" (`:438-443`)
  - **판매자**(`sale.getSeller()`): "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}" (`:447-454`)
  - 둘 다 카테고리 `SHOPPING`, 타입 `BID`(`:440-441`, `:451-452`).
- **시점**: 결제 엔티티 저장 직후, Sale을 `SOLD`로 바꾸기 직전이다(`:83`, `:403`/`:416` → `:404`/`:419`). 결제 수단·결제 상태와 무관하게(PENDING이어도) 보낸다.
- **방식**: 동기 호출이며 Kafka가 아니다.
  - `Xbp24CommandService.createNotification`이 같은 트랜잭션에서 알림 엔티티를 DB에 저장한다(`D/m52/service/command/Xbp24CommandService.java:44-53`).
  - 이어서 `sendRealTimeNotification`이 Redis에 `WebSocket:Xjm45:{email}` 키가 있는 경우에만 STOMP `/queue/notifications`로 `convertAndSendToUser`한다(`:57`, `:164-174`). 연결이 없으면 저장만 한다(`:181-183`).
  - 알림 오류는 `sendNotifications`에서 `log.warn`으로 삼킨다(`Xjt45CommandService.java:457-461`).
  - 주의: 알림 서비스가 클래스 수준 `@Transactional`(`Xbp24CommandService.java:27`)이라 알림 생성이 예외를 던지면 같은 트랜잭션이 rollback-only로 표시될 수 있다.
- 이 경로에서 별도 알림 Kafka 발행은 없다(`notification-topic` 전송은 `Xhq12EventConsumer`에만 있음: `D/m99/service/kafka/Xhq12EventConsumer.java:318`, `:364`).

## 5. 최종 주문 상태와 "창고 보관" 선택의 영향

- **주문(Order)의 최종 상태는 `PENDING_PAYMENT`이다.** 결제가 `PAID`여도 바뀌지 않는다.
  - Order 생성 시 `PENDING_PAYMENT`(`Xhq12CommandService.java:244`)이고, `createInstantOrder`·`createInstantOrderBid`·`processPayment` 어디에서도 Order의 `updateStatus`를 호출하지 않는다.
  - 이름("결제 완료"/"성공적으로 처리")과 달리 실제 상태 전이(`PAYMENT_COMPLETED`→`PREPARING`)는 일어나지 않는다. 다만 관련 엔티티는 SaleBid `MATCHED`, Sale `SOLD`, OrderBid `MATCHED`이다.
  - 결제가 `PENDING`인 경우(계좌이체, 카드 비성공)도 Order 상태는 같다.
- **구매자의 "창고 보관"(`warehouseStorage`) 선택은 이 경로에서 아무 영향이 없다.**
  - 컨트롤러는 로그에만 쓰고 서비스로 전달한다(`Xtw92CommandController.java:95-96`, `:104`).
  - `createInstantOrder`는 파라미터 `isWarehouseStorage`를 받지만 본문에서 읽지 않는다(`Xhq12CommandService.java:220-221`; 본문 참조는 `:292`의 `sale.isWarehouseStorage()`뿐이다).
  - 따라서 창고 보관 엔티티(Xms75) 생성, 주문 상태 `IN_WAREHOUSE`/`COMPLETED` 전이는 일어나지 않는다. 이 분기(`order.updateStatus(IN_WAREHOUSE)`, `createOrderStorage`, `COMPLETED`)는 `processPaymentAndShipment`에만 있다(`:163-172`).
- **달라지는 것은 판매자 쪽 Sale의 창고 보관 여부뿐이다.** `sale.isWarehouseStorage()`가 true면 해당 Sale의 창고 보관 엔티티 상태가 `ASSOCIATED_WITH_ORDER`로 바뀐다(`Xhq12CommandService.java:291-294`, `Xms75CommandService.java:117-133`).
