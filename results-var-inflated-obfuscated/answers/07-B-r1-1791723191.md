# 즉시 구매 처리 흐름

경로 약어: `D` = `src/main/java/com/fream/back/domain`

> 같은 코드가 모듈별로 복제되어 있다 (`/order-bids`=m99, `/legacy/order-bids`=m27, `/internal/order-bids`=m10, `/settlement/order-bids`=m96).
> 클래스 이름과 주입 의존성만 다르고 로직은 동일하다. 아래는 원본 도메인인 m99(`/order-bids/instant`) 기준이다.

## 1. 진입 API, 처리 단계, 동기/비동기, 응답 ID

6. 동기/비동기: **전부 동기, 단일 트랜잭션**이다.
   - 즉시 구매 경로에는 Kafka 발행이나 `@Async`가 없다. HTTP 요청 스레드 안에서 PortOne 호출까지 끝낸 뒤 응답한다.

7. 응답 ID: **주문 입찰(OrderBid, `Xtw92`, 테이블 `order_bid`)의 ID**이다.
   - 서비스가 `Xtw92`를 반환하고 컨트롤러가 `.getId()`를 호출한다 (`Xtw92CommandService.java:119,142-144`, `Xtw92CommandController.java:101-109`).

   - 엔티티 정의: `D/m99/entity/Xtw92.java:16-21`

- **4번 (SaleBid)**: 이 시점의 "변화"는 사실상 없다.
  - 일반 판매 입찰은 생성 직후 `sale.assignSaleBid(saleBid)`가 호출되고 (`D/m85/service/command/Xzt63CommandService.java:45-53`), 이 호출이 `saleBid.assignSale`을 통해 이미 `MATCHED`로 바꾼다 (`D/m85/entity/Xpj42.java:59-62`, `D/m85/entity/Xzt63.java:53-56`).
  - 구매 시 상태를 검사하지 않으므로, 이미 `MATCHED`인 입찰도 다시 구매된다 (`Xtw92CommandService.java:172-184`).
- **7번 (Sale)**: 판매 건의 초기 상태는 `PENDING_SHIPMENT`이다 (`D/m85/service/command/Xpj42CommandService.java:62`).
  - 즉시 구매에서는 `canTransitionTo` 검사 없이 `updateStatus(SOLD)`를 직접 호출한다 (`D/m85/entity/Xpj42.java:73-75`, `Xjt45CommandService.java:404,419`).
  - 호출 시점에 주문은 아직 `orderBid`가 없으므로 `saleBidQueryService.findByOrderId`로 판매 입찰을 거쳐 `sale`을 찾는다 (`Xjt45CommandService.java:388-404`, `D/m85/service/query/Xzt63QueryService.java:26`).
- **8번 (OrderBid)**: 빌더에서 `MATCHED`를 지정하고 (`Xtw92CommandService.java:196`), `assignOrder`도 `MATCHED`로 설정한다 (`Xtw92.java:75`).
  - 양방향 연결이 맺어지고 `isInstantPurchase=true`가 된다 (`Xtw92CommandService.java:202-205`).
  - 이 순서 때문에, 결제 처리 시점의 `order.getOrderBid()`는 항상 null이다.

## 3. 결제 수단별 결과, 성공 여부, 카드 실패 시 동작

분기: `getResolvedPaymentType()`의 값 `CARD` / `ACCOUNT` / `GENERAL` (`Xjt45CommandService.java:67-80`, `D/m64/dto/Xjt45RequestDto.java:20-25,74-80`).

| 수단 | 처리 | 결제 상태 | 근거 |
|---|---|---|---|
| CARD | 저장된 결제정보를 조회하고 PortOne 카드 결제를 동기 호출한다. 응답 `status=="success"`일 때만 `PAID` + `updateSuccessStatus(true)` | 성공: `PAID` / 그 외: `PENDING` | `Xjt45CommandService.java:157-208`, `D/m64/p02/Xhs91ApiClient.java:229-295` |
| ACCOUNT | 은행명만 검증한다 (`Xcn97` enum). **PG 호출이 없다.** | 항상 `PENDING` | `Xjt45CommandService.java:236-262,470-488` |
| GENERAL | 클라이언트가 보낸 `impUid`를 신뢰한다. PG 호출·검증 없이 `PAID`로 저장한다. `impUid`가 비면 예외 | `PAID` | `Xjt45CommandService.java:290-316` |

- **`isSuccess` 값**: 세 생성자 모두 `setPaidAmount`를 호출하고, 이것이 `isSuccess = paidAmount > 0`으로 만든다 (`D/m64/entity/Xjt45.java:60-63`; `Xxf47.java:38`, `Xkg34.java:28`, `Xgg74.java:30`).
  - 따라서 ACCOUNT(`PENDING`)나 카드 `status!="success"`인 건도 `isSuccess=true`로 저장된다. `paymentDate`는 `updateSuccessStatus(true)`가 불릴 때만 채워진다 (`Xjt45.java:64-69`).
- **즉시 구매가 끝까지 "결제 완료"로 성공하는가: 아니다.**
  - 어느 수단이든 `createInstantOrder`는 결제 결과의 상태를 확인하지 않는다. `processPayment`의 반환값을 버리고 (`Xhq12CommandService.java:305`), 예외가 없으면 그대로 진행한다.
  - 계좌이체는 입금 대기(`PENDING`)인 채로 즉시 구매가 "성공" 응답으로 끝나고, 판매는 `SOLD`가 된다.
  - 결제가 `PAID`가 되는 경우(카드 성공, GENERAL)에도 **주문 상태는 `PENDING_PAYMENT`에서 바뀌지 않는다** (5절).
- **카드 실패 시 두 경로가 갈린다.**
  1. **PortOne이 HTTP 오류이거나 `code != 0`을 반환하거나 통신 예외가 난 경우**
     - `processCardPayment`가 예외를 던진다: `Xtc14Exception` (`Xhs91ApiClient.java:270-275`), `Xjt45ApiException` (`:288-290`), `Xtc14Exception` (`:291-293`).
     - 예외 전파 순서:
       1. `processPayment`가 `Xjt45Exception`을 재던진다 (`Xjt45CommandService.java:89-94`).
       2. `createInstantOrder`가 `Xwf42Exception("결제 처리 중 오류...")`으로 감싼다 (`Xhq12CommandService.java:304-309`).
       3. `Xwf42Exception`은 `Xhq12Exception`의 하위 클래스라 그대로 재던져진다 (`D/m99/exception/Xwf42Exception.java:6`, `Xhq12CommandService.java:312-315`, `Xtw92CommandService.java:212-215`).
     - 같은 `@Transactional` 안이므로 **주문·주문 항목·배송·판매 입찰 `MATCHED`·결제 저장이 모두 롤백**되고 클라이언트는 오류 응답을 받는다.
     - 롤백 시 알림 행도 함께 롤백된다. 알림은 이 지점 이전에 발송되지 않는다 (알림은 결제 생성 이후 단계, `Xjt45CommandService.java:83`).
  2. **PortOne이 `code == 0`으로 응답하지만 `response.status`가 `"success"`가 아닌 경우** (예: `failed`)
     - 예외가 발생하지 않는다. 카드 결제는 `PENDING` 상태로 저장된다 (`Xjt45CommandService.java:203-208`).
     - 이후 알림 발송과 판매 `SOLD` 처리가 그대로 진행되고, 즉시 구매는 성공 응답을 반환한다.
     - 실패 응답이 성공처럼 처리되는 구멍이다. `FAILED` 상태로 두거나 예외를 던지는 코드가 없다 (`Xjt45Status.FAILED`는 어디서도 설정되지 않는다).
- 참고: 결제 요청의 `paidAmount`는 `> 0`만 검사하고 (`Xjt45CommandService.java:142-145`), 판매 입찰가(`totalAmount`)와 비교하지 않는다.

## 4. 알림 수신자, 시점, 전달 방식

- **누가 무엇을 받는가** (`Xjt45CommandService.java:434-462`, 카테고리 `SHOPPING`, 타입 `BID`)
  - 구매자: "결제가 완료되었습니다. 주문 ID: {orderId}" (`:438-443`)
  - 판매자(`sale.getSeller()`): "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}" (`:447-454`)
- **언제**
  - `processPayment` 안에서 결제 엔티티를 만든 직후 `notifyUsersAndUpdateSaleStatus` → `sendNotifications` 순서로 발송한다 (`Xjt45CommandService.java:83,403,416`).
  - 알림 직후 `sale.updateStatus(SOLD)`가 따라온다 (`:404,419`).
  - 결제 상태(`PENDING`/`PAID`)와 무관하게 발송된다. 계좌이체나 카드 `status!="success"`여도 "결제가 완료되었습니다" 알림이 간다.
- **어떻게** (`D/m52/service/command/Xbp24CommandService.java:44-67,298-322`)
  1. 알림을 DB에 저장한다 (`notificationRepository.save`, `:52-53`). **같은 트랜잭션**이다.
  2. 대상 사용자의 Redis 키 `WebSocket:Xjm45:{email}`이 있을 때만 WebSocket `/queue/notifications`로 푸시한다 (`:37-38,298-314`). 키가 없으면 저장만 되고 푸시는 없다 (`:320-322`).
  3. Kafka·이메일·푸시 등 다른 채널은 쓰지 않는다. 호출 전체가 동기식이다.
- **오류 처리**: 알림·판매 상태 갱신 실패는 로그만 남기고 삼킨다 (`Xjt45CommandService.java:421-425,457-461`).
  - 알림이나 `findByOrderId`가 던진 예외는 참여 중인 트랜잭션을 rollback-only로 표시할 수 있다 (`Xbp24CommandService`는 클래스 레벨 `@Transactional`, `D/m85/service/query/Xzt63QueryService.java:25-29`).
  - 그러면 삼켜도 최종 커밋이 실패할 수 있다. 이는 코드 구조상의 위험이며 실제 발생 여부는 실행하지 않아 확인하지 못했다.
- 이 외에 주문 입찰(OrderBid) 생성 시점의 알림은 없다.

## 5. 최종 주문 상태와 창고 보관 선택 시 차이

- **주문(`Xhq12`)의 최종 상태는 `PENDING_PAYMENT`이다.**
  - `createInstantOrder`는 주문을 `PENDING_PAYMENT`로 만든 뒤 `updateStatus`를 한 번도 호출하지 않는다 (`Xhq12CommandService.java:241-247`, 메서드 범위 `:219-319`).
  - `PAYMENT_COMPLETED` / `PREPARING` / `IN_WAREHOUSE` / `COMPLETED`로의 전환은 `processPaymentAndShipment`(별도 엔드포인트 `/orders/{id}/process-payment-shipment`)에만 있다 (`Xhq12CommandService.java:161-177`, 컨트롤러 `Xhq12CommandController.java:42`).
  - 즉시 구매 경로에서는 그 메서드가 호출되지 않는다.
  - "즉시 구매가 성공적으로 처리되었습니다" 메시지 (`Xtw92CommandController.java:109`)와 달리, 주문은 결제 완료 상태로 넘어가지 않는다.
  - 메서드명·메시지는 구매 완료를 암시하지만, 실제로 `MATCHED`가 되는 것은 주문 입찰·판매 입찰이고 판매 건은 `SOLD`가 된다.
- **연관 엔티티 최종 값**

  | 엔티티 | 최종 상태 | 근거 |
  |---|---|---|
  | 주문 `Xhq12` | `PENDING_PAYMENT` | `Xhq12CommandService.java:244` |
  | 주문 입찰 `Xtw92` | `MATCHED`, `isInstantPurchase=true` | `Xtw92CommandService.java:196,205` |
  | 판매 입찰 `Xzt63` | `MATCHED` | `Xhq12CommandService.java:280` |
  | 판매 `Xpj42` | `SOLD` | `Xjt45CommandService.java:404` |
  | 배송 `Xfr60` | `PENDING` | `Xfr60CommandService.java:67` |
  | 결제 `Xjt45` | CARD 성공·GENERAL: `PAID` / ACCOUNT·카드 비성공: `PENDING` | 3절 참조 |

  - 결제 객체의 `order` FK는 설정되지만 (`Xjt45.java:47-50`), 즉시 구매 경로에서는 `order.assignPayment(...)`가 호출되지 않는다 (`Xhq12CommandService.java:305`). 인메모리 `Xhq12.payment`도 채워지지 않는다.
- **구매자가 "창고 보관(`warehouseStorage=true`)"을 선택한 경우: 사실상 아무것도 달라지지 않는다.**
  - 값은 컨트롤러 → 서비스 → `createInstantOrder(..., isWarehouseStorage, ...)`까지 전달된다 (`Xtw92CommandController.java:105`, `Xtw92CommandService.java:136-137`, `Xhq12CommandService.java:220-221`).
  - 그러나 `createInstantOrder` 본문에서 이 파라미터를 읽는 곳이 없다 (`:219-319`).
  - 창고 관련 분기는 **판매자 쪽 `sale.isWarehouseStorage()`** 만 본다 (`:291-293`).
    - 이 경우 기존 창고 보관 건의 상태가 `ASSOCIATED_WITH_ORDER`로 바뀐다.
    - 이 값은 구매자가 정하는 값이 아니다.
  - 구매자 선택에 따른 `IN_WAREHOUSE` 상태 전환이나 구매자용 창고 보관(`Xms75`) 생성은 `processPaymentAndShipment`(`:163-172`)에만 있고, 즉시 구매에서는 실행되지 않는다.
  - 따라서 `warehouseStorage` 값에 관계없이 주문은 `PENDING_PAYMENT`이고, 창고 보관(`createOrderStorage`)은 생성되지 않는다.
