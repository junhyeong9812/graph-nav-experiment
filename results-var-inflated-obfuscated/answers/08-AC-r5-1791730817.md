# 구매자 배송: 운송장 등록 → 배송 완료

경로 약어: `D` = `src/main/java/com/fream/back/domain`, `G` = `src/main/java/com/fream/back/global`.
엔티티 이름은 난독화되어 있다: `Xfr60`=OrderShipment(배송), `Xhq12`=Order(주문), `Xtw92`=OrderBid(구매 입찰), `Xzt63`=SaleBid(판매 입찰), `Xpj42`=Sale(판매), `Xbp24`=Notification, `Xzn53Status`=배송 상태.

## 0. 먼저 알아둘 것 — 같은 코드가 여러 벌 있다

- 배송 서비스(`D/m45/service/command/Xfr60CommandService.java`)는 한 벌뿐이다. 이 서비스를 호출하는 컨트롤러가 6벌 있고 경로만 다르다.
  - `D/m45/.../Xfr60CommandController.java:20` `/shipments/order`
  - `D/m81/.../Xsd74CommandController.java:20` `/settlement/shipments/order`
  - `D/m38/.../Xdn57CommandController.java:20` `/internal/shipments/order`
  - `D/m09/.../Xqh36CommandController.java:20` `/admin/shipments/order`
  - `D/m31/.../Xzm66CommandController.java:20` `/partner/shipments/order`
  - `D/m70/.../Xcx47CommandController.java:20` `/legacy/shipments/order`
  - 여섯 컨트롤러는 diff 상 클래스명과 base path만 다르고 본문이 같다.
- 배치 Job 설정도 6벌이다(`D/m45/config/Xpc23JobConfig.java`, `m81/config/Xfr70JobConfig.java`, `m38/config/Xrx68JobConfig.java`, `m09/config/Xxt33JobConfig.java`, `m31/config/Xkd78JobConfig.java`, `m70/config/Xkq49JobConfig.java`). 여섯 개 모두 `updateShipmentStatusesJob` 빈을 만들고(각 파일 :55), 프로세서·알림 서비스 클래스만 다르다. 알림 서비스 6개(m52, m03, m79, m77, m102, m101)의 `notifyShipmentCompleted`는 같은 형태다.
- 이 보고서는 엔티티와 서비스 본체가 있는 m45 계열(`Xpc23JobConfig` + `Xcz52Processor` + `Xfr60CommandService`)을 기준으로 쓴다. 다른 5벌의 로직은 diff 상 동일하다. 단, 같은 이름의 빈이 6개 정의되어 있어 `spring.main.allow-bean-definition-overriding` 설정이 없으면 기동 시 충돌할 수 있다. 이 설정은 `application*.yml`에서 찾지 못했다.
- 같은 판정 로직이 세 곳에 있지만 실제 스케줄 실행 경로에서 쓰이는 것은 하나뿐이다. 자세한 것은 2번에 있다.
- 주문 도메인(`m99`)도 `m27/m10/m96/m74/m54`에 서비스 사본이 있다. 아래는 엔티티 소유 도메인 `m99` 기준이다.

## 1. 운송장 등록 요청

### 1-1. 어느 API로 들어오나

- `PATCH {base}/{shipmentId}/status`. 대표 경로는 `PATCH /shipments/order/{shipmentId}/status`이고, 위 6개 base path 모두 같은 동작이다. 근거: `D/m45/controller/command/Xfr60CommandController.java:20,33-45`.
- 요청 본문은 `{courier, trackingNumber}`이다(`D/m45/dto/Xfr60RequestDto.java:10-13`).
- 컨트롤러는 `Xfr60CommandService#updateTrackingInfo(shipmentId, courier, trackingNumber)`를 그대로 호출한다(`Xfr60CommandController.java:41`).
- `SecurityConfig`는 이 경로를 화이트리스트에 두지 않고 `anyRequest().authenticated()`만 적용한다(`G/config/security/SecurityConfig.java:48-51`). 즉 로그인만 되어 있으면 된다. 역할(ADMIN) 검사는 코드에서 찾지 못했다.
- 참고: 같은 컨트롤러에 `POST .../{shipmentId}/check-status`도 있다(`Xfr60CommandController.java:58`). 이 API는 `updateAndCheckShipmentStatus`를 호출한다. 송장을 저장하고 택배사를 즉시 조회한다(`Xfr60CommandService.java:452-516`).

### 1-2. 코드가 의도한 상태 변경 순서와 알림 (`Xfr60CommandService.java:238-303`)

1. `courier`·`trackingNumber`가 비어 있으면 `TRACKING_INFO_REQUIRED`(S004, 400)로 거절한다(:243-246).
2. 배송 조회. 없으면 `SHIPMENT_NOT_FOUND`(:249-253).
3. **배송(Xfr60)**: `updateTrackingInfo`로 택배사·운송장을 넣고 상태를 `IN_TRANSIT`으로 바로 대입한다(:256, 엔티티 `D/m45/entity/Xfr60.java:41-45`). 이 대입은 `canTransitionTo` 검사를 거치지 않는다. `PENDING`에서 `IN_TRANSIT`은 enum상 허용 전이가 아닌데도 통과한다(`Xzn53Status.java:60-65`).
4. **주문(Xhq12)**: `order.updateStatus(IN_TRANSIT)`(:259-260).
5. **알림 ① 구매자**: "상품이 출발하였습니다. 주문 ID: …"(:265-271).
6. `updateSaleStatusToSold(orderId)`(:276, 본문 :111-183):
   - 판매 입찰(Xzt63)이 연결된 판매(Xpj42)를 `SOLD`로 바꾼다(:123).
   - 창고 보관이면 창고 상태를 SOLD로 바꾼다(:126-129).
   - **알림 ② 판매자**: "상품이 성공적으로 판매 완료되었습니다. 판매 ID: …"(:133-138).
   - 주문 입찰(Xtw92) 쪽 판매가 아직 `SOLD`로 갈 수 있으면 같은 처리를 한 번 더 한다(:151-175).
7. 창고 보관 판매면 창고 상태를 갱신한다(:279-286).
8. `updateOrderAndSaleBidStatusToCompleted`(:289, 본문 :412-440): 주문 입찰(Xtw92)과 판매 입찰(Xzt63)이 `MATCHED`이면 `COMPLETED`로 바꾼다. 이 메서드는 내부 예외를 삼킨다(:436-439).

의도한 순서는 배송 `IN_TRANSIT` → 주문 `IN_TRANSIT` → 판매 `SOLD` → 입찰 `COMPLETED`이다. 알림은 구매자 1건과 판매자 1건이다.

### 1-3. 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문은 끝까지 성공하나 — **실패한다**

**이 주문의 상태**
- `processPaymentAndShipment`가 결제와 배송 정보(배송은 `PENDING`)를 만든다(`D/m99/service/command/Xhq12CommandService.java:139,148`).
- 실배송(창고 보관 아님) 분기는 주문을 `PAYMENT_COMPLETED` → `PREPARING`으로만 올린다(:175-176).
- 그 뒤 코드에서 `SHIPMENT_STARTED`로 올리는 곳은 없다. `Xhq12Status` 정의와 조회 컨트롤러의 라벨(`D/m99/controller/query/Xhq12QueryController.java:207`)만 있다.
- 일반 구매 입찰이라 판매 입찰(Xzt63)과 판매(Xpj42)가 아직 연결되어 있지 않다(`D/m99/service/command/Xtw92CommandService.java:90-103`에서 입찰은 sale 없이 만들어진다).

**어디서 왜 실패하나**
- 실패 지점은 `Xfr60CommandService.java:260` `order.updateStatus(Xhq12Status.IN_TRANSIT)`이다.
- 주문 허용 전이는 `PREPARING → {IN_WAREHOUSE, SHIPMENT_STARTED}`뿐이고 `IN_TRANSIT`은 `SHIPMENT_STARTED`에서만 갈 수 있다(`D/m99/entity/Xhq12Status.java:26-28`).
- `Xhq12.updateStatus`가 `Xxm16StatusException`("상태 전환이 허용되지 않습니다: PREPARING -> IN_TRANSIT")을 던진다(`D/m99/entity/Xhq12.java:113-121`).
- `updateTrackingInfo`의 `catch (Exception e)`가 이를 잡아 `SHIPMENT_NOT_FOUND`로 감싸 던진다(`Xfr60CommandService.java:295-302`). `Xxm16StatusException`은 `Xzn53Exception`이 아니라서 위쪽 `catch (Xzn53Exception)`(:293)을 지나친다.
- 원인이 배송을 못 찾은 것이 아닌데도 "배송 정보를 찾을 수 없습니다"로 보이는 오해성 에러 코드다.
- 설령 이 전이가 통과해도 다음 단계 `updateSaleStatusToSold`의 첫 줄 `saleBidQueryService.findByOrderId`가 `IllegalArgumentException`을 던진다(`D/m85/service/query/Xzt63QueryService.java:26-29`). 이 메서드는 `null`을 돌려주지 않고 던진다. 그래서 `Xfr60CommandService.java:117`의 `saleBid != null` 방어는 의미가 없다. 이 예외는 :150 try 블록 밖이라 잡히지 않는다. 즉 판매 입찰이 없는 주문은 어느 쪽으로든 실패한다.

**무엇이 저장되나 — 아무것도 저장되지 않는다**
- `updateTrackingInfo`는 `@Transactional`(:238)이고 `Xzn53Exception`은 `RuntimeException`(`G/exception/Xkt44Exception.java:10`)이라 전체가 롤백된다.
- 배송에 값을 넣은 것(:256)과 구매자 알림 전의 모든 변경은 커밋되지 않는다. 결과적으로 배송은 `PENDING`에 운송장 없음, 주문은 `PREPARING` 그대로다.
- 구매자 "출발" 알림(:265)은 실패 지점(:260) 뒤라서 아예 만들어지지 않는다. 판매자 알림도 없다.

**응답**
- 컨트롤러가 try/catch를 하지 않으므로 `Xkt44ExceptionHandler#handleShipmentException`으로 간다(`G/exception/Xkt44ExceptionHandler.java:459-473`).
- 응답은 HTTP 404, 본문 `ErrorResponse{code:"S001", message:"배송 정보를 찾을 수 없습니다.", status:404, path, timestamp}`이다(`D/m45/exception/Xzn53ErrorCode.java:12`, `G/response/ErrorResponse.java:51-59`). 상세 메시지는 응답에 실리지 않는다. 핸들러가 `errorCode.getMessage()`를 쓴다.

**참고 — 즉시 구매 주문(b)도 같은 API에서 실패한다.** 즉시 구매 주문은 `PENDING_PAYMENT`로 남아 있다(결제 서비스는 주문 상태를 바꾸지 않는다). `PENDING_PAYMENT → IN_TRANSIT`도 허용 전이에 없다(`Xhq12Status.java:24`). 그래서 같은 `S001` 404가 난다.

## 2. 배송 완료 감지

### 2-1. 누가·언제·어떻게

- **누가**: 스프링 스케줄러 `Xzn53BatchScheduler`가 스프링 배치 Job `updateShipmentStatusesJob`을 실행한다(`G/config/Xzn53BatchScheduler.java:19-21,40`).
- **언제**: `@Scheduled(cron = "0 0 */6 * * *")`, 즉 **6시간마다**(00·06·12·18시 정각, 서버 시간대 기준)다(`Xzn53BatchScheduler.java:34`). 실행 시마다 `timestamp` 파라미터를 넣어 새 JobInstance를 만든다(:37-39). 예외는 `printStackTrace`만 하고 삼킨다(:41-43).
- **어떻게**: 택배사(CJ대한통운) 추적 페이지를 Playwright로 열어 HTML을 파싱한다.
  - URL은 `https://trace.cjlogistics.com/next/tracking.html?wblNo={운송장}`이다(`D/m45/config/Xcz52Processor.java:28,81-83`).
  - `tbody#statusDetail tr`의 마지막 행에서 5번째 `td` 텍스트를 상태 문자열로 쓴다(:29,170-181).
- 한 건씩 조회하며 배송 완료를 사람이 알려주는 구조가 아니다. 택배사 웹페이지 폴링뿐이고 웹훅은 없다.

### 2-2. 대상 배송

`JpaPagingItemReader`의 쿼리는 다음과 같다(`D/m45/config/Xpc23JobConfig.java:95`).

```
SELECT s FROM Xfr60 s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL
```

- 청크 크기 50, 페이지 크기 50(:51,94).
- 읽는 도중 `DELIVERED`가 되면 결과 집합이 줄어든다. 이 reader는 offset 페이징이라 대상이 50건을 넘으면 일부가 이번 실행에서 건너뛰어질 수 있다. 다음 실행(6시간 뒤)에서 다시 잡힌다. 이는 코드 구조상의 추론이다.

### 2-3. 실제로 실행되는 처리 코드 — 비슷한 코드 3곳 중 어느 쪽인가

| 후보 | 실제 실행 여부 | 근거 |
|---|---|---|
| **`Xcz52Processor#process`** (`D/m45/config/Xcz52Processor.java:57-157`) | **실행됨** | Step이 `new Xcz52Processor(...)`를 `.processor(...)`로 지정한다(`Xpc23JobConfig.java:69-73`). |
| `Xpc23JobConfig#shipmentItemProcessor` 빈 안의 람다 (`:104-177`, 내부에 `parseCjLogisticsStatus` :186) | 실행 안 됨 | 이 빈은 Step에 연결되지 않는다(Step은 :69에서 `new`로 만든 프로세서를 쓴다). 옛 Jsoup 방식의 잔재다. |
| `Xfr60CommandService#updateShipmentStatuses` (`:308-391`) | 실행 안 됨 | 호출하는 곳이 없다(`grep updateShipmentStatuses()`에서 정의 외 호출 0건). |

- 실제 실행되는 `Xcz52Processor`는 배송 완료 시 `orderService.completeOrder` + `notificationService.notifyShipmentCompleted`를 호출한다(`Xcz52Processor.java:113-117`).
- 반면 실행되지 않는 `updateShipmentStatuses`는 주문 `COMPLETED`와 알림을 직접 처리한다(`Xfr60CommandService.java:353-364`). 이쪽은 `completeOrder`·판매 `SOLD` 처리가 없어 결과가 다르다. 이 사본을 기준으로 읽으면 틀린다.
- 위 6벌의 JobConfig 중 하나만 `Xzn53BatchScheduler`의 `@Qualifier("updateShipmentStatusesJob")`에 주입된다. 6벌의 프로세서는 알림 서비스 클래스만 다르고 같은 동작이다.

### 2-4. 택배사 상태 문자열 → 내부 상태

`mapToShipmentStatus`(`Xcz52Processor.java:220-226`):

| 택배사 문자열 | 내부 상태 |
|---|---|
| `"배송완료"` | `DELIVERED` |
| `"배송출발"` | `OUT_FOR_DELIVERY` |
| 그 외 모든 문자열(집하·간선상차 등 포함) | `IN_TRANSIT` |

- 정확히 일치(`switch` 문자열)이며 trim만 한다(:181). 비슷한 문구("배송 완료" 등)는 모두 `IN_TRANSIT`이 된다.
- 현재 상태와 매핑 결과가 같으면 아무것도 하지 않고 그대로 반환한다(:101-105).
- `OUT_FOR_DELIVERY`인 배송에 택배사가 다시 "그 외" 문자열을 주면 `IN_TRANSIT`으로 되돌리려다 `Xfr60.updateStatus`가 `IllegalStateException`을 던진다(`Xfr60.java:47-55`, `Xzn53Status.java:79-84`). 프로세서는 이를 `EXTERNAL_TRACKING_SERVICE_ERROR`로 감싸 던져 그 건이 skip된다(`Xcz52Processor.java:133-145`).

## 3. 배송 완료 판정 이후 (`Xcz52Processor.java:108-117` → `Xfr60CommandService#completeOrder` `:190-229`)

### 3-1. 엔티티 상태 변경 순서 (코드가 의도한 정상 경로)

1. **배송(Xfr60)** `IN_TRANSIT`/`OUT_FOR_DELIVERY` → `DELIVERED`(`Xcz52Processor.java:113`).
2. `completeOrder(orderId)`(:116):
   1. `orderBidQueryService.findByOrderId`로 주문 입찰을 조회하고 없으면 예외(`Xfr60CommandService.java:196-197`).
   2. **주문(Xhq12)** → `COMPLETED`(:204).
   3. `updateSaleStatusToSold`(:208): **판매(Xpj42)** → `SOLD`, 창고 보관이면 창고 상태 SOLD. 이미 `SOLD`거나 전이 불가면 건너뛴다(:119,156).
   4. 예외는 모두 `ORDER_NOT_FOUND_FOR_SHIPMENT`(S102, 404)로 감싼다(:221-228).
3. 배송 쓰기: `JpaItemWriter`가 청크 끝에서 배송을 저장한다(`Xpc23JobConfig.java:241-246`).

### 3-2. 알림 (정상 경로에서 몇 건·누구에게)

- 구매자: `completeOrder` 안에서 "[completeOrder] 주문이 완료 처리되었습니다. 주문 ID: …" 1건(`Xfr60CommandService.java:211-217`).
- 구매자: `notifyShipmentCompleted`가 "[배송 완료] 상품이 배송 완료되었습니다. 주문 ID: …" 1건(`D/m52/service/command/Xbp24CommandService.java:219-235`). 이 메서드는 내부 예외를 삼킨다.
- 판매자: `updateSaleStatusToSold`가 판매가 `SOLD`로 바뀌는 경우에만 "상품이 성공적으로 판매 완료되었습니다. 판매 ID: …" 1건(`Xfr60CommandService.java:133-138`).
- 합계: 구매자 2건, 판매 상태가 실제로 `SOLD`로 바뀌면 판매자 1건 추가(최대 3건).

### 3-3. 입찰 상태

- **주문 입찰(Xtw92)·판매 입찰(Xzt63)의 상태는 이 경로에서 바뀌지 않는다.** `completeOrder`와 프로세서는 입찰 상태를 쓰지 않는다. 입찰을 `COMPLETED`로 바꾸는 `updateOrderAndSaleBidStatusToCompleted`(:412-440)는 운송장 등록 `updateTrackingInfo`(:289)에서만 호출되고 이 경로에서는 실행되지 않는다(1-3에서 이미 실패한다).
- 따라서 배송 완료 후에도 입찰은 `MATCHED`로 남는다. 바뀌는 것은 판매(Xpj42) 상태뿐이다. 이 점은 메서드 이름이 주는 인상(배송 완료 → 입찰 완료)과 다르다.

## 4. 주문 종류별 차이

두 경우 모두 배치가 대상으로 잡으려면 배송이 `IN_TRANSIT`/`OUT_FOR_DELIVERY`여야 하는데, 1번의 `PATCH …/status`는 둘 다 실패해서 이 상태를 만들지 못한다. 이 상태를 만들 수 있는 것은 `POST …/check-status`뿐이다(`Xfr60CommandService.java:473`에서 송장 저장과 `IN_TRANSIT` 대입이 일어나고, 이 메서드는 주문 상태를 건드리지 않는다). 아래는 그 이후 배치가 DELIVERED를 판정했다고 가정한 결과다.

### (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문 — **끝까지 진행되지 않는다**

- 주문은 `PREPARING`이다(1-3). `completeOrder`의 `order.updateStatus(COMPLETED)`(:204)는 `PREPARING → COMPLETED`가 허용 전이에 없어(`Xhq12Status.java:26`) `Xxm16StatusException`이 난다.
- 이 예외는 :221에서 `ORDER_NOT_FOUND_FOR_SHIPMENT`로 감싸져 프로세서 밖으로 나간다(`Xcz52Processor.java:133-145`).
- 결과: 주문 `PREPARING` 유지, 판매 상태 변경 없음(:208까지 가지 못함), 알림 0건(`notifyShipmentCompleted`도 :117에서 실행되지 못함). 해당 건은 skip되어 배송은 DB에서 계속 `IN_TRANSIT`이다. 6시간마다 다시 잡혔다가 같은 이유로 매번 실패한다.
- 판매 입찰이 없다는 점도 별도로 문제가 된다. 설령 주문 상태가 통과하더라도 `Xzt63QueryService#findByOrderId`가 던지므로(`Xzt63QueryService.java:26-29`) `updateSaleStatusToSold`에서 막힌다.

### (b) 즉시 구매로 만들어진 주문 — **끝까지 진행된다. 단 의미가 다르다**

- 구성: 주문 `PENDING_PAYMENT` 유지(`Xhq12CommandService.java:244`; 이후 코드가 바꾸지 않음), 판매 입찰이 `MATCHED`로 주문에 붙음(:279-281), 주문 입찰이 `MATCHED` + 즉시구매 표시로 생성됨(`Xtw92CommandService.java:189-206`).
- 결제 시점에 이미 판매(Xpj42)가 `SOLD`가 된다. 즉시 구매는 주문 입찰이 아직 없는 시점에 `createInstantOrder`가 결제(:305)를 부르기 때문에, `Xjt45CommandService#notifyUsersAndUpdateSaleStatus`의 판매 입찰 분기를 탄다(`D/m64/service/command/Xjt45CommandService.java:388-407`, `sale.updateStatus(SOLD)` :404). 이때 구매자·판매자에게 "결제 완료" 알림도 나간다(:434-455).
- 배송 완료 처리 결과:
  - 배송 `DELIVERED`.
  - 주문 `PENDING_PAYMENT → COMPLETED`. 허용 전이다(`Xhq12Status.java:24`).
  - 판매는 이미 `SOLD`라 `canTransitionTo(SOLD)`가 false여서 건너뛴다(`Xpj42Status.java:23`, `Xfr60CommandService.java:119,156`). 따라서 판매자 알림은 없고 창고 상태 갱신도 이 경로에서는 일어나지 않는다.
  - 알림은 구매자 2건(`[completeOrder]` + `[배송 완료]`)뿐이다.
  - 입찰 상태는 `MATCHED` 그대로다.

### 차이 요약

| | (a) 일반 구매 입찰, 실배송 | (b) 즉시 구매 |
|---|---|---|
| 주문 상태(완료 직전) | `PREPARING` | `PENDING_PAYMENT` |
| `PREPARING/PENDING_PAYMENT → COMPLETED` | 불가 → 예외 | 가능 |
| 3의 처리 | 끝까지 안 감, 배송 `IN_TRANSIT` 유지 | 끝까지 감, 배송 `DELIVERED` |
| 주문 최종 | `PREPARING` | `COMPLETED` |
| 알림 | 0건 | 구매자 2건 |
| 입찰 | 변화 없음 | 변화 없음(`MATCHED`) |

## 5. 실패 처리 (주기 처리 중 한 건이 실패할 때)

- Step 설정: `faultTolerant().skip(Exception.class).skipLimit(50)` + `SkipListener`(`Xpc23JobConfig.java:75-78`). 청크 크기 50(:51).
- 그 건: 프로세서가 던진 `Xzn53Exception`(또는 감싼 예외)이 skip 대상이다. `SkipListener#onSkipInProcess`가 `[Skip] 배송 상태 처리 스킵: shipmentId=…` 로그를 남긴다(`Xpc23JobConfig.java:255-268`). 그 건은 저장되지 않아 DB상 이전 상태(`IN_TRANSIT`/`OUT_FOR_DELIVERY`)가 유지되고, 다음 실행(6시간 뒤)에 다시 대상이 된다. `completeOrder`와 같은 트랜잭션에서 일어난 변경은 청크 롤백으로 취소된다.
- 나머지 건: Job 전체는 멈추지 않는다. 같은 청크의 다른 건은 계속 처리되고 다음 청크도 진행된다.
  - 청크 트랜잭션이 롤백된 뒤 Spring Batch가 청크 입력을 다시 처리하며 실패 건만 건너뛴다(이 재처리 동작은 Spring Batch 일반 동작에 대한 추론이다).
  - 재처리 때 이미 메모리에서 `DELIVERED`가 된 같은 청크의 다른 건은 "상태 변경 없음"으로 판정되어(`Xcz52Processor.java:101-105`) `completeOrder`·알림을 다시 타지 않고 배송만 `DELIVERED`로 저장될 수 있다. 이는 코드 구조에서 추론한 위험이며 실행으로 확인하지는 않았다.
- skip이 50건을 넘으면 Step이 실패한다. 이 경우에도 `Xzn53BatchScheduler`가 예외를 `printStackTrace`로 삼키고(`Xzn53BatchScheduler.java:41-43`), 다음 크론 시각에 다시 실행한다.
- 브라우저 자원: 프로세서의 `finally`가 Playwright `page.close()`를 시도하고 실패해도 경고 로그만 남긴다(`Xcz52Processor.java:146-156`).
- 운송장 번호가 비어 있으면 `TRACKING_NUMBER_INVALID`(S003)를 던져 skip된다(:61-64). 다만 reader 쿼리가 `trackingNumber IS NOT NULL`로 걸러 null은 오지 않고 빈 문자열만 올 수 있다.
