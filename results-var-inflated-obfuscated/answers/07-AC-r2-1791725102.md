# 즉시 구매 처리 흐름

경로 접두어: `D = src/main/java/com/fream/back/domain`.
대상 엔드포인트는 접두어 없는 구매자용 `/order-bids/instant`(m99)이다. m10, m27, m54, m74, m96 등에 `/internal`, `/legacy`, `/admin`, `/partner`, `/settlement` 접두어가 붙은 같은 모양의 복제 컨트롤러가 있지만 대상이 아니다.
`/sale-bids/instant`(m85)는 반대로 **판매자**가 구매 입찰을 골라 파는 흐름이라 대상이 아니다.

## 1. 진입 API, 처리 단계, 동기/비동기, 응답 ID

1. `POST /order-bids/instant` → `Xtw92CommandController#createInstantOrderBid`
   - 근거: `D/m99/controller/command/Xtw92CommandController.java:89-90` (클래스 base path `/order-bids`는 `D/m99/controller/command/Xtw92CommandController.java:22`)
   - 요청 본문 `Xcr44RequestDto`는 `saleBidId`, `addressId`, `warehouseStorage`, `paymentRequest`다. 근거: `D/m99/dto/Xcr44RequestDto.java`
2. 컨트롤러는 인증 사용자 이메일을 꺼내고(`:92`), 결제 요청에 `userEmail=이메일`, `orderId=null`을 채운다(`:98`, `:119-121`).
3. `Xtw92CommandService#createInstantOrderBid`를 호출한다(`:101`). 이 메서드는 `@Transactional`이다.
   - 근거: `D/m99/service/command/Xtw92CommandService.java:118-149`
   - 입력 검증(이메일, saleBidId, addressId, paymentRequest): `:154-167`
   - 구매자 조회(`:126`)
   - 판매 입찰 조회와 연결된 Sale 존재 검증: `:129`, `:172-184`
4. `Xhq12CommandService#createInstantOrder` (`@Transactional`)가 주문을 만든다. 근거: `D/m99/service/command/Xhq12CommandService.java:219-319`
   - 배송지 조회 `addressQueryService.getAddress`: `:238`
   - 주문 저장: `:241-247`
   - `paymentRequest.setOrderId(order.getId())`: `:250`
   - 주문 항목 생성: `:255-256`
   - 배송 정보 생성: `:264-271`
   - 판매 입찰에 주문 연결과 MATCHED 처리 후 flush: `:279-283`
   - 판매자가 창고 보관한 Sale이면 창고 상태 갱신: `:291-294`
   - 결제 처리 `paymentCommandService.processPayment`: `:305`
5. `Xjt45CommandService#processPayment`가 결제 유형별로 분기한다(`D/m64/service/command/Xjt45CommandService.java:57-80`).
   결제 후 `notifyUsersAndUpdateSaleStatus`로 알림을 보내고 Sale을 SOLD로 바꾼다(`:83`, `:383-426`).
6. 마지막으로 `Xtw92` 주문 입찰 엔티티를 만들어 저장한다(`D/m99/service/command/Xtw92CommandService.java:142`, `:189-207`).

**동기/비동기:** 전부 동기이며 하나의 DB 트랜잭션 안에서 처리된다.
- 이 경로에는 Kafka 발행이 없다. `/orders/{id}/process-payment-shipment`가 쓰는 `Xhq12EventProducer`와 다르다.
- 결제 대행사(PortOne) 호출도 `restTemplate.exchange`로 요청 스레드에서 블로킹 호출한다. 근거: `D/m64/p02/Xhs91ApiClient.java:266`
- 컨트롤러는 서비스 반환값을 받아 바로 응답한다(`D/m99/controller/command/Xtw92CommandController.java:101-109`).

**응답 ID:** `ResponseDto.success(orderId, "즉시 구매가 성공적으로 처리되었습니다.")`의 `orderId`다. 근거: `D/m99/controller/command/Xtw92CommandController.java:101-109`
- 변수명은 `orderId`이고 값은 `createInstantOrderBid(...).getId()`다. 이름이 비슷하지만 이 `.getId()`는 방금 만든 `Xtw92`(주문 입찰, OrderBid) 엔티티의 ID다. 주문(`Xhq12`)의 ID가 아니다.
- 반환 객체는 `Xtw92`다(`D/m99/service/command/Xtw92CommandService.java:119`, `:206`).
- 따라서 응답으로 돌아가는 ID는 **OrderBid(Xtw92)의 ID**다.
- 주문 ID는 이 응답에 담기지 않는다.

기존 엔티티의 상태 변화 순서와 각 단계 직후의 값:

| 단계 | 대상 | 변화 후 값 | 근거 |
|---|---|---|---|
| a | 판매 입찰 `Xzt63` | `PENDING` → `MATCHED`, `order` 연결 | `D/m85/entity/Xzt63.java:58-61`, 호출 `D/m99/service/command/Xhq12CommandService.java:279-280`. 기본값 PENDING은 `D/m85/entity/Xzt63.java:37` |

| c | 결제 `Xjt45` | 카드 성공 `PAID`, 계좌이체 `PENDING`, 일반 `PAID` (3번 참조) | 위 결제 표 |
| d | 판매 `Xpj42` | `SOLD` (상태 전이 검증 없이 `updateStatus` 직접 대입) | `D/m64/service/command/Xjt45CommandService.java:404`; `D/m85/entity/Xpj42.java:73-75` |

**주문 `Xhq12.status`는 이 흐름에서 한 번도 갱신되지 않는다. `PENDING_PAYMENT`로 끝난다.** 근거:
- `createInstantOrder`에는 `updateStatus` 호출이 없다(`D/m99/service/command/Xhq12CommandService.java:219-319`).
- `processPayment`도 주문 상태를 바꾸지 않는다(`D/m64/service/command/Xjt45CommandService.java:57-107`).
- 상태를 `PAYMENT_COMPLETED`, `PREPARING`으로 올리는 코드는 별도 엔드포인트 `processPaymentAndShipment`(`D/m99/service/command/Xhq12CommandService.java:165-177`)뿐이며 즉시 구매 경로에서는 호출되지 않는다.

기타 동작:
- 알림 단계는 `order.getOrderBid()`가 null이어서(주문 입찰은 결제 이후에 만들어진다) `saleBidQueryService.findByOrderId`로 판매 입찰을 찾아 Sale에 접근한다. 근거: `D/m64/service/command/Xjt45CommandService.java:388-403`
- 결제 요청의 `paidAmount`와 입찰가의 일치 여부는 검증하지 않는다. 검증은 `paidAmount > 0`, 주문 ID와 이메일 일치뿐이다(`:117-146`).
- 경로에서 `Sale`이 `SELLING`인지 같은 상태 검사도 없다(`D/m99/service/command/Xtw92CommandService.java:172-184`).

## 3. 결제 수단별 결과, 성공 여부, 카드 실패 응답

| 결제 | 처리 | 결제 상태 | 결제 후 흐름 |
|---|---|---|---|
| CARD | 저장된 카드 정보 조회(`D/m64/service/command/Xjt45CommandService.java:166`) → PortOne `/subscribe/payments/onetime` 호출(`:179`) → 응답의 `status == "success"`일 때만 `PAID` + `success=true`(`:203-206`) | 기본값 `PENDING`(`D/m64/entity/Xjt45.java:44`), 성공 시 `PAID` | 계속 진행 |
| ACCOUNT | PortOne 호출 없음. 은행명만 검증(`:243-248`)하고 `PENDING`으로 저장(`:260-262`) | **`PENDING`** | 계속 진행 (실제 입금/확인 코드 없음) |
| GENERAL | 이미 승인된 `impUid`만 받아 저장, PortOne 재검증 없음. `success=true`, `PAID`(`:297-316`) | `PAID` | 계속 진행 |

- 결제 유형이 위 셋이 아니면 `PAYMENT_VALIDATION_FAILED`로 실패한다(`:77-79`).
- **즉시 구매는 어떤 결제 수단이든 성공 시 끝까지 성공 처리된다.**
  - 계좌이체는 결제가 `PENDING`인데도 이후 단계(Sale `SOLD`, 알림, 응답 성공)를 그대로 진행한다. `payment.getStatus()` 값을 분기에 쓰지 않는다(`D/m64/service/command/Xjt45CommandService.java:83`, `:383-426`).
  - 알림 문구도 "결제가 완료되었습니다"로 나간다(`:442`).

**결제 대행사가 카드 결제를 실패로 응답하면** 경우가 둘로 갈린다.
1. HTTP 상태가 OK가 아니거나 응답 `code != 0`인 경우(대행사가 명시적으로 실패를 응답한 경우): `Xtc14Exception`을 던진다(`D/m64/p02/Xhs91ApiClient.java:270-275`).
   - `Xtc14Exception`은 `Xjt45Exception`의 하위 클래스다. `Xjt45ApiException`의 하위가 아니므로 `@Retryable`(대상은 `Xjt45ApiException`)이 재시도하지 않는다.
   - 예외는 `createCardPayment`에서 그대로 전파되고(`D/m64/service/command/Xjt45CommandService.java:218-219`), `processPayment`에서 재전파된다(`:89-94`).
   - `createInstantOrder`가 `Xwf42Exception`(`Xhq12Exception`의 하위)으로 감싼다(`D/m99/service/command/Xhq12CommandService.java:306-309`).
   - 이 예외는 그대로 전파된다(`:312-315`, `D/m99/service/command/Xtw92CommandService.java:213-215`). `@Transactional`이 롤백되므로 주문, 항목, 배송, 판매 입찰 MATCHED, 결제가 모두 저장되지 않는다.
   - 응답 ID는 반환되지 않는다.
   - 예외 변환 구현이 `Xkt44Exception`(전역 예외 계열)에 의존하므로 HTTP 오류 형태는 전역 예외 처리에 따른다.
2. `code == 0`이지만 `response.status`가 `"success"`가 아닌 경우(예: `failed`): 예외가 없다. 카드 결제 엔티티는 기본 `PENDING` 상태로 저장되고(`:203-208`), 이후 단계가 정상 진행된다.
   - Sale은 `SOLD`가 되고 구매자와 판매자에게 "결제 완료" 알림이 나가며 응답은 성공이다.
   - 실제 동작이 결제 실패를 놓치는 구멍이다.

**다른 오류의 처리:** 결제 후 알림이나 Sale 상태 갱신에서 예외가 나면 `notifyUsersAndUpdateSaleStatus`가 삼킨다(`D/m64/service/command/Xjt45CommandService.java:421-425`).
- 이 경우 알림이 안 가고 Sale이 SOLD가 되지 않아도 요청은 성공한다.
- 알림 발송 실패도 별도로 삼킨다(`:457-461`).

## 4. 알림 대상, 시점, 전달 방식

- **구매자:** "결제가 완료되었습니다. 주문 ID: {orderId}". 근거: `D/m64/service/command/Xjt45CommandService.java:438-443`
- **판매자(`sale.getSeller()`):** "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}". 근거: `D/m64/service/command/Xjt45CommandService.java:447-454`
- 두 알림 모두 카테고리 `Xrv73.SHOPPING`, 타입 `Xbp24Type.BID`다.
- 이 경로에서 **알림은 결제 성공/실패와 무관하게** `processPayment`가 예외 없이 끝나면 나간다. 계좌이체 `PENDING`과 카드 `code=0 + status!=success`에서도 전송된다(위 3번).
- 시점: 결제 레코드 저장 직후, 같은 요청 스레드, 같은 트랜잭션 안(`:83`)에서 동기 전송한다. 이후 주문 입찰 저장(`D/m99/service/command/Xtw92CommandService.java:142`)보다 먼저다. Kafka를 쓰지 않는다. Kafka `notification-topic`을 쓰는 알림은 `Xhq12EventConsumer`의 별도 비동기 주문 처리 경로의 것이다(이 흐름 아님).
- 전달 방식:
  1. DB에 알림 엔티티 저장(`D/m52/service/command/Xbp24CommandService.java:52-53`).
  2. 실시간 전송: 수신자 이메일 기준 Redis 키 `WebSocket:Xjm45:{email}`가 있을 때만 STOMP `convertAndSendToUser(email, "/queue/notifications", dto)`로 푸시한다(`:303-312`, 상수 `:37-38`). 연결이 없으면 저장만 한다(`:320-322`).

## 5. 최종 주문 상태와 창고 보관 선택 시 차이

**최종 주문 상태: `PENDING_PAYMENT`.**
- 위 2번대로 즉시 구매 경로에서 `Xhq12.status`를 갱신하는 코드가 없다(`D/m99/service/command/Xhq12CommandService.java:241-247`에서 설정된 후 변경 없음).
- 주석이나 메서드 이름("즉시 구매가 성공적으로 처리되었습니다", `D/m99/controller/command/Xtw92CommandController.java:109`)은 완료를 말하지만, 코드상 주문은 결제 완료나 `COMPLETED`로 가지 않는다.
- 같이 남는 상태: 판매 입찰 `MATCHED`, 판매 `SOLD`, 주문 입찰 `MATCHED`, 결제는 수단에 따라 `PAID` 또는 `PENDING`이다.

**구매자가 "창고 보관"(`warehouseStorage=true`)을 선택한 경우: 아무것도 달라지지 않는다.**
- 컨트롤러는 `isWarehouseStorage()`를 서비스에 넘긴다(`D/m99/controller/command/Xtw92CommandController.java:94-95`, `:101-107`). 서비스도 `createInstantOrder`에 넘긴다(`D/m99/service/command/Xtw92CommandService.java:133-139`).
- 그러나 `createInstantOrder` 본문에서 `isWarehouseStorage` 인자는 한 번도 읽히지 않는다(`D/m99/service/command/Xhq12CommandService.java:219-319`). `createOrderStorage`도 호출되지 않고 `IN_WAREHOUSE`나 `COMPLETED`로의 전환도 없다.
- 창고 관련 코드는 `sale.isWarehouseStorage()`(**판매자**가 정한 값, `D/m85/entity/Xpj42.java:43`)가 true일 때 기존 창고 보관 레코드 상태를 `ASSOCIATED_WITH_ORDER`로 바꾸는 것뿐이다(`D/m99/service/command/Xhq12CommandService.java:291-293`).
- 구매자 창고 보관 선택(`createOrderStorage`, 상태 `IN_WAREHOUSE` → `COMPLETED`)은 별도 엔드포인트 `process-payment-shipment`의 `processPaymentAndShipment`에서만 처리된다(`D/m99/service/command/Xhq12CommandService.java:163-172`).
