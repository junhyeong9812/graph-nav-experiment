# 구매자 배송: 운송장 등록 → 배송 완료

경로 약어: `B` = `src/main/java/com/fream/back`
(엔티티 이름은 난독화되어 있다. 배송 `Xfr60`(order_shipment), 주문 `Xhq12`(orders), 구매 입찰 `Xtw92`(order_bid), 판매 입찰 `Xzt63`(sale_bid), 판매 `Xpj42`(sale), 판매자 배송 `Xrg51`.)

핵심 결론 (실제 동작 기준):
- 실배송 일반 구매 입찰 주문은 결제·배송 처리 후 주문 상태가 `PREPARING` 이다. 운송장 등록은 `Order PREPARING → IN_TRANSIT` 전이가 허용되지 않아 **실패(404 `S001`)하고 전부 롤백**된다.
- 같은 이유로 배송 완료 처리(`completeOrder`)도 `PREPARING → COMPLETED` 에서 실패한다. 즉시 구매 주문은 주문 상태가 `PENDING_PAYMENT` 라 `COMPLETED` 전이가 허용되어 끝까지 진행된다.

## 1. 운송장 등록 요청

### 1-1. 진입 API
- `PATCH /shipments/order/{shipmentId}/status`, 바디 `{courier, trackingNumber}`
  - `B/domain/m45/controller/command/Xfr60CommandController.java:20` (`@RequestMapping("/shipments/order")`), `:33-49` (`updateTrackingInfo`)
  - 바디 DTO: `B/domain/m45/dto/Xfr60RequestDto.java:10-13`
- 컨트롤러는 try/catch 없이 `Xfr60CommandService.updateTrackingInfo` 를 호출하고 200 을 돌려준다 (`:41-48`).
- 참고: `/internal`, `/admin`, `/partner`, `/settlement`, `/legacy` 접두어의 동일 복제 컨트롤러가 m09/m31/m38/m70/m81 에 있다. 모두 같은 `Xfr60`/`Xfr60CommandService`(m45) 를 쓰는 복제본이다 (예: `B/domain/m81/controller/command/Xsd74CommandController.java:8,20,24`).
- `POST /shipments/order/{id}/check-status` 도 운송장을 덮어쓰지만 별도 경로다 (`Xfr60CommandController.java:58`).

### 1-2. 코드가 의도한 상태 변경 순서 (`B/domain/m45/service/command/Xfr60CommandService.java:238-303`)
1. 택배사/운송장 공백 검사 → `TRACKING_INFO_REQUIRED` (`:243-246`)
2. 배송 `Xfr60` 조회 후 `updateTrackingInfo` → 택배사·운송장 저장, 배송 상태 `IN_TRANSIT` (`:249-256`; 엔티티 `B/domain/m45/entity/Xfr60.java:41-45`)
3. 주문 `Xhq12` 상태 `IN_TRANSIT` (`:259-262`)
4. **구매자**에게 알림 "상품이 출발하였습니다. 주문 ID: …" (`:265-273`)
5. `updateSaleStatusToSold(orderId)` (`:276`)
   - 판매 입찰 조회 (`:116`) → 판매 `Xpj42` 가 `SOLD` 로 전이 가능하면 `SOLD` (`:119-123`)
   - 창고 보관이면 창고 상태 갱신 (`:126-129`)
   - **판매자**에게 알림 "상품이 성공적으로 판매 완료되었습니다. 판매 ID: …" (`:132-138`)
   - 구매 입찰 쪽 경로로 같은 처리를 한 번 더 시도하나 이미 `SOLD` 면 `canTransitionTo(SOLD)` 가 false 라 건너뛴다 (`:151-176`; `B/domain/m85/entity/Xpj42Status.java:16-23`)
6. 창고 보관 판매면 창고 상태 재갱신 (`:279-286`)
7. `updateOrderAndSaleBidStatusToCompleted` → 구매 입찰 `MATCHED→COMPLETED`, 판매 입찰 `MATCHED→COMPLETED` (`:289`, `:412-440`)

요약: 의도상 등록 시점에 배송·주문이 `IN_TRANSIT` 이 되고, 구매자 알림 1건 + 판매자 알림 1건이 가며, 판매·입찰도 이 시점에 `SOLD`/`COMPLETED` 로 바뀐다. 메서드 이름과 달리 "운송장 등록" 이 판매 완료 처리까지 한다.

### 1-3. 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문: 성공하지 않는다
- 결제·배송 처리(`processPaymentAndShipment`) 후 실배송(`isWarehouseStorage=false`)의 주문 상태는 `PAYMENT_COMPLETED → PREPARING` 에서 멈춘다.
  - `B/domain/m99/service/command/Xhq12CommandService.java:175-176`
  - 실제 진입점인 Kafka 경로도 동일: `B/domain/m99/controller/command/Xhq12CommandController.java:42-60`(이벤트 발행), `B/domain/m99/service/kafka/Xhq12EventConsumer.java:195,215-218`
- 주문 상태 전이표에서 `PREPARING` 의 다음 상태는 `IN_WAREHOUSE`, `SHIPMENT_STARTED` 뿐이다 (`B/domain/m99/entity/Xhq12Status.java:25`). `IN_TRANSIT` 으로 가는 길은 `SHIPMENT_STARTED` 뿐이다 (`:27`).
- `SHIPMENT_STARTED` 로 바꾸는 코드는 저장소에 없다 (`updateStatus(Xhq12Status.*)` 호출은 PAYMENT_COMPLETED/PREPARING/IN_WAREHOUSE/COMPLETED/IN_TRANSIT 뿐; 시드 `B/global/config/Xdq35.java:541-554` 포함).
- 따라서 `Xfr60CommandService.java:260` `order.updateStatus(IN_TRANSIT)` 에서 `Xhq12.updateStatus` 가 `Xxm16StatusException("상태 전환이 허용되지 않습니다: PREPARING -> IN_TRANSIT")` 를 던진다 (`B/domain/m99/entity/Xhq12.java:113-121`).

실패 위치와 결과:
1. 실패 지점: `Xfr60CommandService.java:260`. 구매자·판매자 알림 코드(`:266`, `:276`)와 입찰 `COMPLETED` 처리(`:289`)에는 도달하지 못한다.
2. 이 예외는 `Xzn53Exception` 이 아니므로 `catch (Exception e)` (`:295-302`) 에서 `Xzn53Exception(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")` 로 다시 감싸져 던져진다.
3. **저장되는 것은 없다.** 서비스 메서드가 `@Transactional`(`:238`)이고 `RuntimeException` 계열(`B/global/exception/Xkt44Exception.java:10`)이라 롤백된다. 메모리상 배송 `IN_TRANSIT`/운송장 반영(`:256`)은 DB 에 남지 않고, 배송은 `PENDING`, 주문은 `PREPARING` 그대로이며 알림도 없다.
4. 응답: `Xkt44ExceptionHandler.handleShipmentException` 이 `404` 와 `ErrorResponse(code="S001", message="배송 정보를 찾을 수 없습니다.", status=404, path)` 를 돌려준다 (`B/global/exception/Xkt44ExceptionHandler.java:459-473`, `B/domain/m45/exception/Xzn53ErrorCode.java:12`). 실제 원인(상태 전이 불가)은 응답 코드에 드러나지 않고 로그에만 남는다.

## 2. 배송 완료 감지

### 2-1. 누가/언제
- **스프링 스케줄러**가 Spring Batch Job 을 띄운다: `Xzn53BatchScheduler.scheduleShipmentStatusJob`, `@Scheduled(cron = "0 0 */6 * * *")` → **6시간마다 정각(00·06·12·18시)** (`B/global/config/Xzn53BatchScheduler.java:34-44`). 매번 `timestamp` 파라미터를 달리해 `updateShipmentStatusesJob` 실행 (`:37-40`). 예외는 `printStackTrace` 로만 처리 (`:41-43`).
- 사용자·웹훅이 아니라 택배사(CJ대한통운) 페이지를 **폴링**하는 방식이다.

### 2-2. 대상 / 실제 실행되는 코드
- Job: `Xpc23JobConfig.updateShipmentStatusesJob` → Step `updateShipmentStatusesStep` (`B/domain/m45/config/Xpc23JobConfig.java:54-82`). chunk 50, skip 제한 50 (`:51-52`, `:67`, `:75-77`).
- 조회 대상(Reader): `SELECT s FROM Xfr60 s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL`, 페이지 크기 50 (`:87-97`).
- **실제로 쓰이는 처리기는 `Xcz52Processor`** 이다 (`Xpc23JobConfig.java:69-73` 에서 `new Xcz52Processor(...)`; 구현 `B/domain/m45/config/Xcz52Processor.java:56-157`). Playwright 브라우저를 Step 시작/종료 시 열고 닫는다 (`B/domain/m45/config/Xhd56Listener.java:14-25`, `Xpc23JobConfig.java:80`). 각 건은 `https://trace.cjlogistics.com/next/tracking.html?wblNo=<운송장>` 로 이동해 `tbody#statusDetail tr` 마지막 행의 5번째 `td` 텍스트를 읽는다 (`Xcz52Processor.java:28-29,81-94,167-191`).
- 비슷하지만 **실행되지 않는** 코드:
  - `Xpc23JobConfig.shipmentItemProcessor` (`:104-177`) 와 `parseCjLogisticsStatus` (`:186-220`): Step 에 연결되지 않은 `@StepScope` 빈/미사용 private 메서드.
  - `Xfr60CommandService.updateShipmentStatuses` (`B/domain/m45/service/command/Xfr60CommandService.java:308-391`): 호출하는 곳이 없다.
  - m09/m31/m38/m70/m81 의 `*JobConfig`/`*Processor` (예: `B/domain/m81/config/Xfr70JobConfig.java:55`, `Xcj35Processor.java`): m45 와 로직이 같은 복제본. 같은 빈 이름 `updateShipmentStatusesJob` 을 6곳이 정의하며 (`Xzn53BatchScheduler.java:19` 는 이름으로 주입), 오버라이딩 허용 설정은 저장소에서 찾지 못했다. 어느 쪽이 선택되든 대상 엔티티(`Xfr60`)·로직·알림 구현이 동일해 동작은 같다.
  - `Xfr60CommandService.updateAndCheckShipmentStatus` (`:452-516`, `POST …/check-status`): 수동 즉시 조회 경로. 주기 처리가 아니다.

### 2-3. 택배사 상태 문자열 → 내부 상태 (`Xcz52Processor.java:220-226`)

## 3. 배송 완료 판정 이후 (`newStatus == DELIVERED`)

`Xcz52Processor.java:108-117` → `Xfr60CommandService.completeOrder` (`:190-229`):

1. 배송 `Xfr60` 상태 `DELIVERED` (`Xcz52Processor.java:113`). `IN_TRANSIT`/`OUT_FOR_DELIVERY` → `DELIVERED` 는 허용 (`Xzn53Status.java`).
2. `completeOrder(orderId)` 호출 (`:116`)
   1. 구매 입찰 `Xtw92` 를 주문 ID 로 조회, 없으면 `IllegalArgumentException` (`Xfr60CommandService.java:196-197`)
   2. 주문 `Xhq12` 상태 `COMPLETED` (`:204`)
   3. `updateSaleStatusToSold` (`:208`): 판매 `Xpj42` → `SOLD`(전이 가능할 때, `:119-123`), 창고 보관이면 창고 상태 갱신(`:126-129`), 판매자 알림(`:132-138`)
   4. **구매자** 알림 "[completeOrder] 주문이 완료 처리되었습니다. 주문 ID: …" (`:211-217`)
3. 다시 처리기에서 `notifyShipmentCompleted(order)` → **구매자** 알림 "[배송 완료] 상품이 배송 완료되었습니다. 주문 ID: …" (`Xcz52Processor.java:117`, `B/domain/m52/service/command/Xbp24CommandService.java:219-234`)
4. Writer(`JpaItemWriter`)가 배송을 저장 (`Xpc23JobConfig.java:74,239-246`)

알림 건수:
- 구매자 2건 ("[completeOrder] …", "[배송 완료] …"). 같은 사건에 중복 알림이다.
- 판매자 최대 1건 ("상품이 성공적으로 판매 완료되었습니다…"). 판매 `Xpj42` 가 `SOLD` 로 전이 가능한 상태(`ON_AUCTION`/`SELLING`)일 때만 간다. 그렇지 않으면 조용히 건너뛰어 0건이다 (`Xfr60CommandService.java:119,142-144`; `Xpj42Status.java:21-22`).
- 알림 생성 자체는 `Xbp24CommandService.createNotification` (`:44-67`)이며 실시간 푸시도 보낸다 (`:57`).

입찰 상태:
- 이 경로에서는 **구매 입찰·판매 입찰 상태를 바꾸지 않는다**. `MATCHED` 그대로다. `COMPLETED` 로 바꾸는 `updateOrderAndSaleBidStatusToCompleted` (`:412-440`)는 운송장 등록 경로(`:289`)에서만 호출되고, `completeOrder`/처리기 경로에서는 호출되지 않는다.
- 판매 쪽은 판매 `Xpj42` 가 `SOLD` 로 바뀔 수 있을 뿐이다.

## 4. 주문 종류별 차이

### (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문 → 끝까지 진행되지 않는다
- 주문 상태 `PREPARING` (1-3 참조). `completeOrder` 의 `order.updateStatus(COMPLETED)` (`Xfr60CommandService.java:204`)가 `PREPARING → COMPLETED` 전이 불가로 `Xxm16StatusException` 을 던진다 (`Xhq12Status.java:25`, `Xhq12.java:113-121`).
- `completeOrder` 의 `catch (Exception)` 이 `Xzn53Exception(ORDER_NOT_FOUND_FOR_SHIPMENT, "주문 완료 처리 중 오류 발생: …")` 로 감싸 던진다 (`:221-228`). 판매 `SOLD` 처리(`:208`), 구매자 알림(`:212`), 처리기의 `notifyShipmentCompleted` (`Xcz52Processor.java:117`)는 실행되지 않는다.
- 결과: 주문 `PREPARING`, 배송 `IN_TRANSIT`/`OUT_FOR_DELIVERY` 유지(저장 안 됨), 알림 0건, 입찰 `MATCHED`. 이 건은 스킵되고 6시간마다 같은 이유로 반복 실패한다.
- 그 이전에 이 주문은 1-3 때문에 정상 경로(운송장 등록 API)로는 배송이 `IN_TRANSIT` 이 될 수도 없다. 대상이 되려면 `check-status` API 로 배송만 `IN_TRANSIT` 으로 바뀐 경우여야 한다 (`Xfr60CommandService.java:473,497`; 이 경로는 주문 상태를 건드리지 않음).

### (b) 즉시 구매로 만들어진 주문 → 3의 처리가 끝까지 진행된다
- 즉시 구매 주문은 `PENDING_PAYMENT` 로 만들어지고 이후 상태 변경이 없다 (`Xhq12CommandService.java:241-245`; 결제 서비스 `m64` 에는 주문 상태 변경 호출이 없다).
- 구매 입찰은 `MATCHED`, `isInstantPurchase=true` 로 생성되고 (`B/domain/m99/service/command/Xtw92CommandService.java:189-206`), 판매 입찰에 주문이 연결된다 (`Xhq12CommandService.java:279`) → `findByOrderId` 가 둘 다 성공한다 (`Xtw92QueryService.java:51-56`, `B/domain/m85/service/query/Xzt63QueryService.java:26-29`).
- `PENDING_PAYMENT → COMPLETED` 는 허용된다 (`Xhq12Status.java:23`). 따라서 `completeOrder` 가 끝까지 진행된다. 주문 `COMPLETED`, 판매 `SOLD`(전이 가능 시) + 판매자 알림, 구매자 알림 2건.
- 입찰 상태는 `MATCHED` 그대로(3과 동일).
- 단, (b) 도 운송장 등록 API 는 `PENDING_PAYMENT → IN_TRANSIT` 이 허용되지 않아 (`Xhq12Status.java:23`) 1-3 과 똑같이 404 로 실패한다. 배송이 `IN_TRANSIT` 이 되어 배치 대상이 되는 길은 `check-status` API 뿐이다.

### 차이 요약
| | (a) 실배송 일반 구매 입찰 | (b) 즉시 구매 |
|---|---|---|
| 주문 상태(처리 전) | `PREPARING` | `PENDING_PAYMENT` |
| `→ COMPLETED` | 불가 → 예외 | 가능 |
| 배송 완료 처리 | 실패, 롤백/스킵 | 성공 |
| 알림 | 0건 | 구매자 2건 + 판매자 0~1건 |
| 입찰 상태 | `MATCHED` | `MATCHED` |

## 5. 실패 처리 (주기 처리 중 한 건 실패)

- Step 이 `faultTolerant().skip(Exception.class).skipLimit(50)` 이다 (`Xpc23JobConfig.java:75-77`). 처리기에서 예외가 나면 해당 청크가 롤백되고 건별로 다시 처리되며, **실패한 그 건만 스킵**되고 **나머지는 정상 처리·커밋**된다. `completeOrder` 가 같은 트랜잭션에 참여한 `@Transactional` 이라 실패한 건의 변경(배송 `DELIVERED`, 주문 변경, 알림)은 함께 롤백된다.
- 스킵된 건은 `SkipListener` 가 `[Skip] 배송 상태 처리 스킵 …` 로 로그만 남긴다 (`Xpc23JobConfig.java:251-287`). 상태가 바뀌지 않으므로 여전히 대상 조회 조건에 해당해 다음 실행(6시간 뒤)에 다시 시도된다.
- 스킵이 50건을 넘으면 Step/Job 이 실패하고 남은 건은 그 회차에서 처리되지 않는다 (`:52,77`). 스케줄러는 `printStackTrace` 만 한다 (`Xzn53BatchScheduler.java:41-43`).
