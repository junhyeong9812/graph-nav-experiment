# 즉시 구매 처리 흐름 분석

대상 코드는 접두사 없는 구매자용 경로 `POST /order-bids/instant` (`domain/m99` 모듈)이다.
`/legacy/…`, `/internal/…`, `/admin/…`, `/partner/…`, `/settlement/…` 접두사가 붙은 m27·m10·m74·m54·m96 모듈은 같은 구조의 복제본이다.
`/sale-bids/instant`(m85)는 판매자가 구매 입찰을 골라 즉시 판매하는 반대 방향 API라 이 질문과 무관하다.

경로 약칭: `B = src/main/java/com/fream/back/domain`

## 1. 진입 API, 처리 단계, 동기/비동기, 응답 ID

**진입점**
- `POST /order-bids/instant`. 클래스 `@RequestMapping("/order-bids")` (`B/m99/controller/command/Xtw92CommandController.java:22`), 메서드 `@PostMapping("/instant")` (`:89`).
- 요청 본문은 `Xcr44RequestDto`다. 필드는 `saleBidId`, `addressId`, `warehouseStorage`, `paymentRequest`다 (`B/m99/dto/Xcr44RequestDto.java:21-29`).
- `paymentRequest`는 `paymentType`(CARD/ACCOUNT/GENERAL)에 따라 하위 타입으로 역직렬화된다 (`B/m64/dto/Xjt45RequestDto.java:22-24`).

**처리 단계**
1. 컨트롤러가 로그인 이메일을 추출한다 (`Xtw92CommandController.java:92`, `global/utils/SecurityUtils.java:85`).
2. `enrichPaymentRequest`가 결제 요청에 `userEmail=로그인 이메일`, `orderId=null`을 채운다 (`Xtw92CommandController.java:98`, `:119-123`).
3. `Xtw92CommandService.createInstantOrderBid`를 호출한다 (`Xtw92CommandController.java:101`). 이 메서드는 `@Transactional`이다 (`B/m99/service/command/Xtw92CommandService.java:118-119`).
   - 입력을 검증한다: 이메일, saleBidId, addressId, paymentRequest (`:123`, `:154-167`).
   - 구매자를 조회한다 (`:126`).
   - 판매 입찰을 조회하고 연결된 sale이 있는지 확인한다 (`:129`, `:172-184`).
   - `Xhq12CommandService.createInstantOrder`로 주문을 만든다 (`:133`). 이 안에서 주문 → 주문 항목 → 배송 → 판매입찰 매칭 → 창고 상태 → 결제 순으로 진행한다 (`B/m99/service/command/Xhq12CommandService.java:219-319`).
   - 주문 입찰(Xtw92)을 생성·저장한다 (`Xtw92CommandService.java:142`, `:189-207`).

**동기/비동기**
- **전부 동기, 단일 트랜잭션이다.**
  - Kafka 발행이나 `@Async`가 없다.
  - 결제 대행사 호출(`portOneApiClient.processCardPayment`)과 알림 생성도 같은 호출 스레드에서 수행한다 (`B/m64/service/command/Xjt45CommandService.java:179`, `:83`).
- Kafka 소비자 `Xhq12EventConsumer`(`order-processing-topic`)는 일반 주문 결제 경로가 쓴다. 발행 지점은 `B/m99/controller/command/Xhq12CommandController.java:54`이고, 즉시 구매 경로에는 연결되어 있지 않다.

**응답 ID**
- 응답 본문은 `ResponseDto.success(orderId, ...)`다 (`Xtw92CommandController.java:109`).
- 변수명은 `orderId`지만 값은 `orderBidCommandService.createInstantOrderBid(...).getId()`다 (`:101-107`).
- 그 메서드의 반환 타입은 주문 입찰 엔티티 `Xtw92`다 (`Xtw92CommandService.java:119`, `:142-144`).
- 따라서 **응답 ID는 주문(Xhq12) ID가 아니라 새로 생성된 주문 입찰(OrderBid, `order_bid` 테이블) ID**다.

**주문 상태가 더 이상 바뀌지 않는다.**
- `createInstantOrder` 안에는 `order.updateStatus(...)` 호출이 없다. 그 호출은 일반 주문 경로(`processPaymentAndShipment`, `Xhq12CommandService.java:165-177`)와 Kafka 소비자(`Xhq12EventConsumer.java:195-217`)에만 있다.
- 주문은 `PENDING_PAYMENT`로 생성된 뒤 이 요청 안에서 변경되지 않는다.
- `order.assignPayment`도 호출되지 않는다. 결제와 주문은 결제 쪽 FK(`assignOrder`, `Xjt45CommandService.java:200`)로만 연결된다.

**참고: 단계 ⑥과 ⑦의 순서**
- ⑥(알림·SOLD)은 주문 입찰(⑦)이 만들어지기 전에 실행된다.
- 그래서 `order.getOrderBid()`는 null이다 (`Xjt45CommandService.java:388-389`).
- 대신 ③에서 맺어 둔 판매입찰→주문 연결로 `saleBidQueryService.findByOrderId`가 sale을 찾는다 (`:391-404`, `B/m85/service/query/Xzt63QueryService.java:26-28`).

## 3. 결제 수단별 결과와 카드 결제 실패

**공통**
- `processPayment`는 `getResolvedPaymentType()`으로 분기한다 (`Xjt45CommandService.java:67-80`).
- 사전 검증: `orderId`가 주문 ID와 같아야 하고, `userEmail`이 같아야 하며, `paidAmount > 0`이어야 한다 (`:131-145`).
- 결제 금액과 주문 `totalAmount`(= 판매입찰 `bidPrice`)를 **비교하지 않는다**. DTO의 최소 100원 제약만 있다 (`Xjt45RequestDto.java:52`).

**수단별 결과**

| 수단 | 처리 | 결제 상태 | 근거 |
|---|---|---|---|
| 카드(CARD) | 저장된 결제정보를 조회해 PortOne `/subscribe/payments/onetime`을 호출하고, 응답의 `status`가 `"success"`일 때만 `PAID` | 성공 시 `PAID`(`isSuccess=true`, `paymentDate` 설정). 그 외 `PENDING`(`isSuccess=false`) | `Xjt45CommandService.java:166`, `:179`, `:203-208`; `B/m64/p02/Xhs91ApiClient.java:229-285` |
| 계좌이체(ACCOUNT) | 은행명을 `Xcn97` enum으로만 검증하고 외부 호출 없이 저장 | `PENDING`. 입금 확인 로직 없음 | `Xjt45CommandService.java:243-247`, `:260`, `:470-488` |
| 일반(GENERAL) | `impUid`가 비어 있지 않은지만 확인하고, PG 사후 검증 없이 성공으로 기록 | `PAID`, `isSuccess=true` | `Xjt45CommandService.java:297-300`, `:313-314` |

**즉시 구매가 끝까지 성공하는가**
- 세 수단 모두 예외가 나지 않으면 결제 상태와 무관하게 요청은 성공한다. 같은 흐름으로 이어진다: 판매 `SOLD`, 알림 전송, 주문 입찰 `MATCHED` 저장, 200 응답.
- 계좌이체는 결제가 `PENDING`인데도 `notifyUsersAndUpdateSaleStatus`가 결제 상태를 보지 않아 같은 후속 처리가 일어난다 (`:383-420`).
- 이 때문에 구매자와 판매자는 실제로는 미결제인 계좌이체에도 "결제가 완료되었습니다" 알림을 받고 판매는 `SOLD`가 된다 (`:438-454`).
- 주문 상태는 어떤 수단이든 `PENDING_PAYMENT`다 (2번 참조).
- 일반 주문 경로 소비자(`Xhq12EventConsumer.java:174-176`)와 달리 `payment.isSuccess()`를 검사하지 않는다.

**결제 대행사가 카드 결제를 실패로 응답할 때 — 두 경우로 갈린다**
- **(a) HTTP 비200 또는 응답 `code != 0`인 경우**
  - `Xtc14Exception`을 던진다 (`Xhs91ApiClient.java:270-275`).
  - 이 예외는 `createCardPayment`에서 재던져지고(`Xjt45CommandService.java:180-181`, `:218-219`), `processPayment`에서도 재던져진다 (`:89-94`).
  - `createInstantOrder`가 이를 `Xwf42Exception`으로 감싸고 (`Xhq12CommandService.java:304-309`), 바깥 catch가 `Xhq12Exception`을 그대로 재던진다 (`:312-315`). 이어서 `Xtw92CommandService.handleOrderBidCreationException`이 재던진다 (`:145-147`, `:212-215`).
  - 전체가 하나의 `@Transactional`이고 런타임 예외(`Xkt44Exception extends RuntimeException`, `global/exception/Xkt44Exception.java:10`)이므로 **주문, 주문 항목, 배송, 판매입찰 `MATCHED`가 롤백**된다.
  - `Xkt44ExceptionHandler`가 에러 응답으로 변환한다 (`global/exception/Xkt44ExceptionHandler.java:49-60`).
  - 알림·SOLD 처리는 결제 성공 이후 단계라 실행되지 않는다.
- **(b) HTTP 200·`code == 0`인데 `response.status != "success"`인 경우**
  - 예외가 없다. 결제는 `PENDING`, `isSuccess=false`로 저장된다 (`Xjt45CommandService.java:203-208`).
  - 이후는 성공 흐름과 같다 (`:83`). 주문 입찰은 `MATCHED`로 저장되고 판매는 `SOLD`가 되며, "결제가 완료되었습니다" 알림이 나가고 200이 반환된다.
  - 주문은 `PENDING_PAYMENT`다. 대행사가 "실패"라고 응답한 카드 결제를 서버가 성공으로 처리하는 지점이다.

## 4. 알림 수신자, 시점, 전달 방식

**수신자와 메시지**
- 결제 처리 직후 `sendNotifications(order, sale)`가 호출된다 (`Xjt45CommandService.java:403`, `:434-456`).
  - **구매자**: `"결제가 완료되었습니다. 주문 ID: {orderId}"` (`:438-443`).
  - **판매자**(`sale.getSeller()`): `"구매자가 결제를 완료하였습니다. 판매 ID: {saleId}"` (`:447-454`).
  - 카테고리는 `SHOPPING`, 타입은 `BID`다.
- 이 외 즉시 구매 경로의 알림은 없다. 환불 알림(`:603-659`)은 환불 시에만 나간다. `Xhq12EventConsumer`의 WebSocket/Kafka 알림(`:287-374`)은 Kafka 주문 처리 경로 전용이다.

**시점**
- 결제 저장 직후, 판매를 `SOLD`로 바꾸기 직전에 보낸다 (`Xjt45CommandService.java:83`, `:403-404`). 주문 입찰 저장(`Xtw92CommandService.java:142`)보다 앞이다.
- 동기 호출이며 같은 트랜잭션 안이다 (`Xbp24CommandService` 클래스 `@Transactional`, `B/m52/service/command/Xbp24CommandService.java:27`).

**전달 방식**
1. 알림을 DB에 저장한다 (`Xbp24CommandService.java:52-53`).
2. `sendRealTimeNotification`이 Redis 키 `WebSocket:Xjm45:{email}`가 있을 때만 STOMP `/queue/notifications`로 `convertAndSendToUser` 한다 (`:57`, `:303-322`). 연결 키가 없으면 DB에만 남는다 (`:320-321`).
- 알림 실패(예외)는 `sendNotifications`에서 `warn`으로 삼키므로 결제와 주문을 롤백하지 않는다 (`Xjt45CommandService.java:457-461`).
- `notifyUsersAndUpdateSaleStatus` 전체도 예외를 삼킨다 (`:421-425`). 판매입찰·sale 조회에 실패해 알림이 안 나가거나 SOLD 갱신이 실패해도 요청은 성공한다.

## 5. 최종 주문 상태와 창고 보관 선택 시 차이

**최종 상태 (요청 처리 종료 시점)**

| 대상 | 값 | 근거 |
|---|---|---|
| 주문 `Xhq12` | `PENDING_PAYMENT` | `Xhq12CommandService.java:244` (이후 `updateStatus` 없음) |
| 판매입찰 `Xzt63` | `MATCHED` | `:280` |
| 판매 `Xpj42` | `SOLD` | `Xjt45CommandService.java:404` |
| 주문입찰 `Xtw92` | `MATCHED`, `isInstantPurchase=true` | `Xtw92CommandService.java:196`, `:205` |
| 결제 | 카드 성공·일반 `PAID`, 계좌·카드 비성공 응답 `PENDING` | 3번 표 참조 |
| 배송 | `PENDING` | `Xfr60CommandService.java:67` |

- 즉시 구매가 "성공"해도 주문은 `PAYMENT_COMPLETED`/`PREPARING`/`COMPLETED`에 도달하지 않는다.
- 일반 주문 경로(`processPaymentAndShipment`)는 결제 후 `PAYMENT_COMPLETED → PREPARING`(또는 창고 보관이면 `IN_WAREHOUSE → COMPLETED`)로 올리지만, 즉시 구매는 이 단계를 타지 않는다 (`Xhq12CommandService.java:163-177`).

**구매자가 "창고 보관"을 선택한 경우**
- **실질적으로 달라지는 것이 없다.**
  - `warehouseStorage` 값은 컨트롤러 로그 출력 (`Xtw92CommandController.java:94-95`)과 서비스 인자 전달 (`:105`, `Xtw92CommandService.java:137`)에만 쓰인다.
  - `createInstantOrder`는 파라미터 `isWarehouseStorage`를 받지만 본문에서 읽지 않는다 (선언 `Xhq12CommandService.java:221`, 본문 `:224-318`에 사용처 없음).
  - 따라서 구매자의 창고 보관 선택에 따른 창고 보관 레코드(`createOrderStorage`) 생성이나 `IN_WAREHOUSE`/`COMPLETED` 전이는 일어나지 않는다. 이는 일반 주문 경로에만 있다 (`:163-172`, `Xhq12EventConsumer.java:197-213`).
- 창고 관련 처리는 **구매자 플래그가 아니라 판매자의 `sale.isWarehouseStorage()`**에만 반응한다.
  - 판매자가 창고 보관으로 올린 sale이면, 기존 창고 레코드 상태를 `ASSOCIATED_WITH_ORDER`로 바꾼다 (`Xhq12CommandService.java:291-293`).
  - 그 창고 레코드를 찾지 못하거나 상태 전이가 막히면 예외(`Xkd21Exception`)가 나 전체가 롤백된다 (`:295-301`, `B/m63/service/command/Xms75CommandService.java:127-130`).
  - 구매자의 창고 보관 선택 여부와 무관하게 동작한다.
