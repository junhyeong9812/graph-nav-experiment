# 즉시 구매 처리 흐름 (POST /partner/order-bids/instant)

경로 약어: `M54`=`src/main/java/com/fream/back/domain/m54`, `M64`=`src/main/java/com/fream/back/domain/m64`, `M99`=`src/main/java/com/fream/back/domain/m99`, `M85`=`src/main/java/com/fream/back/domain/m85`, `M52`=`src/main/java/com/fream/back/domain/m52`, `M63`=`src/main/java/com/fream/back/domain/m63`

## 1. 진입 API, 처리 단계, 동기/비동기, 응답 ID

1. 진입: `POST /partner/order-bids/instant` — `M54/controller/command/Xrx79CommandController.java:22,89-90` (클래스 base path `/partner/order-bids` + `@PostMapping("/instant")`). 바디는 `Xcr44RequestDto`(saleBidId, addressId, warehouseStorage, paymentRequest) — `M99/dto/Xcr44RequestDto.java:20-29`.
2. 컨트롤러: 인증 이메일 추출(`Xrx79CommandController.java:92`) → `enrichPaymentRequest`로 결제 요청의 userEmail을 로그인 이메일로 덮어쓰고 orderId를 null로 비움(`:98`, `:119-123`) → `Xrx79CommandService#createInstantOrderBid` 호출(`:101-107`).
3. `Xrx79CommandService#createInstantOrderBid`(`M54/service/command/Xrx79CommandService.java:119-149`, `@Transactional`):
   - 입력 검증(`:154-167`) → 구매자 조회(`:126`) → 판매 입찰 조회·검증(`:129`, `:172-184`; 존재와 sale 연결 여부만 확인하고 입찰 상태가 이미 MATCHED인지는 검사하지 않음)
   - `Xhx22CommandService#createInstantOrder` 호출(`:133-139`)
   - 이어서 OrderBid(`Xtw92`) 생성·저장(`:142`, `:189-207`)
4. `Xhx22CommandService#createInstantOrder`(`M54/service/command/Xhx22CommandService.java:219-319`, `@Transactional`)의 순서: 주소 조회(`:238`) → Order 저장(`:241-247`) → paymentRequest.orderId에 주문 ID 세팅(`:250`) → OrderItem 생성(`:255-256`) → 배송 정보 생성(`:264-271`) → 판매 입찰 MATCHED 처리 + flush(`:279-283`) → 창고 상태 갱신(`:290-294`) → 결제 처리(`:305`).
5. **동기 처리**다. Kafka 이벤트 발행·`@Async` 없이 한 HTTP 요청 / 한 트랜잭션 안에서 결제 대행사 호출까지 끝난다. (`/partner/orders/{id}/process-payment-shipment`가 쓰는 Kafka 경로 `Xhx22EventProducer`는 즉시 구매 흐름에서 호출되지 않는다.)
6. **응답 ID는 주문(Order, `Xhq12`)의 ID가 아니라 새로 만든 주문 입찰(OrderBid, `Xtw92`)의 ID**다. 컨트롤러가 `createInstantOrderBid(...).getId()`를 `orderId` 변수에 담지만(`Xrx79CommandController.java:101-107`) 반환 객체는 `Xtw92`(`Xrx79CommandService.java:119`, `:265-267`)이다. 응답 메시지는 "즉시 구매가 성공적으로 처리되었습니다."(`:109`).

## 2. 새로 생성되는 엔티티와 상태 변화 순서

새로 생성: Order(`Xhq12`), OrderItem(`Xnd96`), OrderShipment(`Xfr60`), Payment(`Xjt45` 하위: 카드 `Xxf47`/계좌 `Xkg34`/일반 `Xgg74`), 알림(`Xbp24`, 구매자·판매자 각 1건), OrderBid(`Xtw92`). 기존 엔티티(SaleBid `Xzt63`, Sale `Xpj42`, 창고 `Xms75`)는 상태만 변경된다.

| 순서 | 동작 | 직후 상태 | 근거 |
|---|---|---|---|
| 1 | Order 저장 | Order.status = `PENDING_PAYMENT` | `Xhx22CommandService.java:241-247` |
| 2 | OrderItem 생성(수량 1, 가격=판매 입찰가) | — | `:255-256`, `M54/service/command/Xqj87CommandService.java:45-52` |
| 3 | OrderShipment 생성 | Shipment.status = `PENDING` | `:264-271`, `M45/service/command/Xfr60CommandService.java:61-70` (M45=`src/main/java/com/fream/back/domain/m45`) |
| 4 | SaleBid에 order 연결 | SaleBid.status = `MATCHED` (`assignOrder`가 MATCHED 세팅, 이어서 명시적 MATCHED) | `:279-280`, `M85/entity/Xzt63.java:58-61,66-68` |
| 5 | Sale이 창고 보관 판매(`sale.isWarehouseStorage()`)일 때만 창고 레코드 상태 변경 | Xms75.status = `ASSOCIATED_WITH_ORDER` | `:291-294`, `M63/service/command/Xms75CommandService.java:117-133` |
| 6 | 결제 생성 (결제수단별 상태는 3번 참고) | 카드 성공/일반: `PAID`, 계좌: `PENDING` | `M64/service/command/Xjt45CommandService.java:67-76` |
| 7 | 결제 후처리: Sale 상태 변경 | Sale.status = `SOLD` | `Xjt45CommandService.java:383-405`, `M85/entity/Xpj42.java:73-75` |
| 8 | OrderBid 생성·저장 | OrderBid.status = `MATCHED`, isInstantPurchase = true, sale 연결 | `Xrx79CommandService.java:189-207`, `M99/entity/Xtw92.java:60-82,97-99` |

주의: 즉시 구매 경로(`createInstantOrder`)에는 Order 상태를 전이시키는 `order.updateStatus(...)` 호출이 없다. Order는 `PENDING_PAYMENT`에서 더 이상 바뀌지 않는다(5번 항목 참조). 또한 `order.assignPayment`도 호출하지 않으며 결제 엔티티가 `payment.assignOrder(order)`로 주문 FK만 가진다(`Xjt45CommandService.java:200,258,311`).

## 3. 결제 수단별 결과, 성공 여부, 카드 실패 시

공통: `processPayment`는 orderId·이메일 일치, 금액>0을 검증(`Xjt45CommandService.java:117-146`)한 뒤 `getResolvedPaymentType()`(`M64/dto/Xjt45RequestDto.java:74-87`)으로 분기(`:67-80`)하고, 이후 판매 상태/알림 처리(`:83`)를 한다.

| 수단 | 처리 | 결제 상태 | 근거 |
|---|---|---|---|
| CARD | 저장된 결제정보 조회 → PortOne(iamport) 일회성 결제 API 동기 호출 → 응답의 `status`가 `"success"`일 때만 PAID + success=true | 성공 시 `PAID`, 그렇지 않으면 엔티티 기본값 `PENDING` 그대로 저장 | `:157-217` (`:179`, `:203-206`), 기본값 `M64/entity/Xjt45.java:43-44` |
| ACCOUNT(계좌이체) | 은행명 enum 검증만 하고 외부 호출 없이 저장 | `PENDING` (입금/승인 대기) | `:236-262` (`:244`, `:260`), `:470-488` |
| GENERAL(일반) | `impUid` 필수 확인 후 외부 호출 없이 바로 성공 처리 | `PAID`, success=true | `:290-316` (`:297`, `:313-314`) |

- **끝까지 성공하는가**: 세 수단 모두 예외 없이 통과하면 API는 성공 응답을 낸다. 그러나 결제 수단과 무관하게 `notifyUsersAndUpdateSaleStatus`가 호출되어 판매자·구매자에게 "결제가 완료되었습니다" 알림이 가고 Sale이 `SOLD`가 된다(`:83`, `:404`, `:419`). 즉 계좌이체(`PENDING`)나 카드 응답 status가 success가 아닌 경우에도 결제 완료 알림·SOLD·OrderBid MATCHED·"즉시 구매 성공" 응답이 나간다. 최종적으로 Order는 `PENDING_PAYMENT`이다.
- **결제 대행사가 카드 결제를 실패로 응답할 때**는 두 갈래다.
  1. HTTP가 200이 아니거나 응답 `code != 0`: `Xtc14Exception`("카드 결제 요청 실패: ...") 발생(`M64/p02/Xhs91ApiClient.java:270-274`; `Xtc14Exception extends Xjt45Exception`: `M64/exception/Xtc14Exception.java:6`). `Xjt45CommandService`는 그대로 재던지고(`:218-219`, `:89-94`), `createInstantOrder`가 `Xwf42Exception`으로 감싸며(`Xhx22CommandService.java:304-309`), `Xrx79CommandService#handleOrderBidCreationException`이 `Xhq12Exception`이면 그대로, 아니면 `Xrd49Exception`으로 던진다(`:212-218`). 예외가 `@Transactional` 경계를 벗어나므로 Order/OrderItem/Shipment/SaleBid MATCHED/창고 상태 변경이 전부 롤백되고 OrderBid와 알림도 생기지 않아 에러 응답이 나간다. (통신 오류는 `Xjt45ApiException`이라 `@Retryable`로 최대 3회 재시도, `Xhs91ApiClient.java:224-228,288-290`.)
  2. HTTP 200 + `code == 0`이지만 `response.status`가 `"success"`가 아님(예: failed): 예외 없이 결제가 `PENDING`, success=false로 저장되고(`Xjt45CommandService.java:203-208`) 위 "성공 경로"로 계속 진행한다. 즉 실패가 성공으로 처리된다.
- 참고: 카드 결제 승인 후 뒤 단계에서 예외가 나면 DB는 롤백되지만 PortOne 결제 취소 호출은 없다(즉시 구매 경로에서 `cancelPayment` 미호출).

## 4. 알림 수신자, 시점, 전달 방식

- 시점: `processPayment` 안에서 결제 엔티티를 저장한 직후 동일 요청·동일 트랜잭션에서 **동기**로 생성된다(`Xjt45CommandService.java:83` → `:383-426`). Order에 아직 OrderBid가 없으므로(`order.getOrderBid()==null`) `saleBidQueryService.findByOrderId`로 판매 입찰→Sale을 찾아 보낸다(`:388-403`).
- 수신자 2명(`sendNotifications`, `:434-455`):
  - 구매자: "결제가 완료되었습니다. 주문 ID: {orderId}" (`:438-443`)
  - 판매자(`sale.getSeller()`): "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}" (`:449-454`)
  - 둘 다 카테고리 `SHOPPING`, 타입 `BID`.
- 전달 방식: `Xbp24CommandService#createNotification`이 DB에 알림 저장(`M52/service/command/Xbp24CommandService.java:44-54`) 후 `sendRealTimeNotification`(`:57`)에서 Redis 키 `WebSocket:Xjm45:{email}`가 있을 때만 WebSocket(STOMP `/queue/notifications`, `convertAndSendToUser`)으로 푸시한다(`:303-314`). 연결이 없으면 저장만 되고 푸시하지 않는다(`:320-322`). Kafka/이메일 아님.
- 알림·판매 상태 변경 오류는 try/catch로 삼켜지므로(`Xjt45CommandService.java:421-425`, `:457-461`) 알림이 실패해도 구매는 성공한다. 즉시 구매 경로에서는 실패 알림이 없다.

## 5. 최종 상태와 창고 보관 선택의 영향

- **주문(Order) 최종 상태: `PENDING_PAYMENT`.** `createInstantOrder`가 만든 상태(`Xhx22CommandService.java:244`)에서 즉시 구매 경로는 `updateStatus`를 호출하지 않는다(`:219-319`에 호출 없음). `PAYMENT_COMPLETED`/`PREPARING`/`COMPLETED`로 전이시키는 코드는 별도 경로 `processPaymentAndShipment`(`:111-202`)에만 있고, 즉시 구매는 이를 거치지 않는다. 그 사이 결제는 `PAID`(카드 성공/일반) 또는 `PENDING`(계좌/카드 비성공)이고, Sale=`SOLD`, SaleBid·OrderBid=`MATCHED`이다. 메서드 이름·응답 메시지("즉시 구매가 성공적으로 처리되었습니다")가 주는 인상과 달리 주문은 결제 완료로 표시되지 않는다.
- **구매자의 "창고 보관" 선택(`warehouseStorage`)은 사실상 무시된다.** 컨트롤러는 값을 로그에 남기고 서비스에 넘기지만(`Xrx79CommandController.java:94-95,104`, `Xrx79CommandService.java:119-120,137`), `createInstantOrder`의 `isWarehouseStorage` 파라미터(`Xhx22CommandService.java:220-221`)는 본문에서 한 번도 사용되지 않는다. 창고 분기는 `requestDto.isWarehouseStorage()`를 쓰는 `processPaymentAndShipment`(`:163-172`: IN_WAREHOUSE → 창고 보관 생성 → COMPLETED)에만 있고 즉시 구매에서는 실행되지 않는다. 구매자 선택에 따른 차이(창고 보관 레코드 생성, 주문 `IN_WAREHOUSE`/`COMPLETED` 전이)는 없다.
- 창고와 관련해 실제로 일어나는 일은 구매자 선택이 아니라 **판매 건의 속성**(`sale.isWarehouseStorage()`) 때문에 기존 창고 레코드가 `ASSOCIATED_WITH_ORDER`로 바뀌는 것뿐이다(`Xhx22CommandService.java:291-294`). 그 창고 레코드가 없으면 `Xzg57Exception`(`M63/service/query/Xms75QueryService.java:30-32`, 호출 `Xms75CommandService.java:127`)이 `Xkd21Exception`으로 감싸져 전체가 롤백된다(`Xhx22CommandService.java:295-301`).
