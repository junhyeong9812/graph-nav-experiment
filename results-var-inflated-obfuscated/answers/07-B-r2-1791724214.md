# 즉시 구매 처리 흐름 분석

경로 약어: `D` = `src/main/java/com/fream/back/domain`, `G` = `src/main/java/com/fream/back/global`.

> 참고: 같은 코드가 `m99`(`/order-bids`), `m27`(`/legacy/order-bids`), `m10`(`/internal/order-bids`), `m96`(`/settlement/order-bids`), `m74`(`/admin/order-bids`), `m54`(`/partner/order-bids`)에 클래스명만 바꿔 복제되어 있다
> (예: `D/m27/controller/command/Xnw92CommandController.java:22,89`, `D/m10/controller/command/Xnt62CommandController.java:22,89`).
> 복제본은 모두 동일한 `m99` 엔티티와 `m99`의 주문 서비스(`Xhq12CommandService`)를 쓰고 동작도 같다. 아래는 정본인 `m99`(`/order-bids`) 기준이다.

## 1. 진입 API, 처리 단계, 동기/비동기, 응답 ID

**진입 API**: `POST /order-bids/instant`
- 근거: `D/m99/controller/command/Xtw92CommandController.java:22`(`@RequestMapping("/order-bids")`), `:89`(`@PostMapping("/instant")`), `:90`(`createInstantOrderBid`).
- 요청 DTO(`Xcr44RequestDto`): `saleBidId`, `addressId`, `warehouseStorage`, `paymentRequest` (`D/m99/dto/Xcr44RequestDto.java:20-29`).
- `saleBidId`, `addressId`, `paymentRequest`는 `@NotNull`이다. `warehouseStorage`는 `boolean`이다.

**처리 단계**
1. 컨트롤러가 SecurityContext에서 이메일을 추출한다. 실패하면 예외를 던진다 (`Xtw92CommandController.java:92`, `G/utils/SecurityUtils.java:85-97`).
2. `enrichPaymentRequest`가 결제 요청에 `userEmail`을 채우고 `orderId`를 null로 지운다 (`Xtw92CommandController.java:98`, `:119-123`).
3. `Xtw92CommandService.createInstantOrderBid`(`@Transactional`)를 호출한다 (`D/m99/service/command/Xtw92CommandService.java:118-149`).
   1. 입력 검증: 이메일, saleBidId, addressId, paymentRequest null 체크 (`:123`, `:154-167`).
   2. 구매자 조회 (`:126`).
   3. 판매 입찰 조회: `findById`는 없으면 `IllegalArgumentException`을 던진다. 연결된 `sale`이 없으면 예외다 (`:129`, `:172-184`, `D/m85/service/query/Xzt63QueryService.java:21-24`).
      - 판매 입찰의 현재 상태(이미 MATCHED인지)나 본인 입찰 여부는 검증하지 않는다.
   4. 주문 생성 `Xhq12CommandService.createInstantOrder` 호출 (`:133-139`).
4. `createInstantOrder` 내부 (`D/m99/service/command/Xhq12CommandService.java:219-319`)
   1. 배송지 조회: `addressQueryService.getAddress(email, addressId)` (`:238`)
   2. `Order` 저장: `status=PENDING_PAYMENT`, `totalAmount=saleBid.bidPrice` (`:241-247`)
   3. `paymentRequest.setOrderId(order.getId())` (`:250`)
   4. `OrderItem` 생성 (`:255-256`)
   5. `OrderShipment` 생성 (`:264-271`)
   6. 판매 입찰 `assignOrder` + `MATCHED`, 그리고 `flush` (`:279-283`)
   7. 판매자 창고 보관 상태 갱신 (`:291-294`)
   8. 결제 처리 `paymentCommandService.processPayment` (`:305`)
5. 결제 후 처리: `Xjt45CommandService.notifyUsersAndUpdateSaleStatus`가 알림 전송과 `Sale=SOLD` 처리를 한다 (`D/m64/service/command/Xjt45CommandService.java:83`, `:383-420`).
6. 서비스로 돌아와 `OrderBid`를 만들고 저장한다 (`Xtw92CommandService.java:142`, `:189-207`).

**동기/비동기**
- 전부 동기다. 하나의 HTTP 요청 스레드에서 하나의 트랜잭션으로 처리된다.
  - `@Transactional`: `Xtw92CommandService.java:118`, `Xhq12CommandService.java:219`, 결제 서비스는 클래스 레벨 `Xjt45CommandService.java:37`.
  - 호출 체인에 `@Async`나 Kafka 발행이 없다.
  - 결제 서비스는 `Xjt45EventProducer`를 쓰지 않는다 (`Xjt45CommandService.java:41-45`의 의존성 목록에 없음).
- 결제 대행사(PortOne/아임포트) 호출도 `RestTemplate`으로 동기 호출한다 (`D/m64/p02/Xhs91ApiClient.java:266`).

**응답으로 돌려주는 ID**
- **주문 입찰(OrderBid, `order_bid` 테이블, `Xtw92`)의 ID**다. 주문(Order)이나 결제의 ID가 아니다.
- 근거: 서비스가 `Xtw92`(OrderBid)를 반환하고 (`Xtw92CommandService.java:119`, `:142-144`), 컨트롤러가 `.getId()`를 꺼내 `orderId`라는 변수에 담아 반환한다 (`Xtw92CommandController.java:101-109`).
- 변수명은 `orderId`지만 실제 값은 OrderBid ID다. 엔티티 `@Table(name = "order_bid")` (`D/m99/entity/Xtw92.java:16`).
- 응답 메시지는 "즉시 구매가 성공적으로 처리되었습니다." 이다 (`Xtw92CommandController.java:109`).

## 2. 새로 만들어지는 엔티티와 상태 변화 순서

각 항목은 `Xhq12CommandService.createInstantOrder` 안의 순서대로이며, 마지막만 서비스 계층이다.

| 순서 | 동작 | 직후 상태 | 근거 |
|---|---|---|---|
| 1 | `Order`(`orders`, `Xhq12`) 신규 저장 | `PENDING_PAYMENT` | `Xhq12CommandService.java:241-247` |
| 2 | `OrderItem`(`Xnd96`) 신규 (수량 1, 가격=입찰가) | (상태 없음) | `:255-256`, `D/m99/service/command/Xnd96CommandService.java` (`createOrderItem`) |
| 3 | `OrderShipment`(`Xfr60`) 신규 | `PENDING` (`Xzn53Status.PENDING`) | `:264-271`, `D/m45/service/command/Xfr60CommandService.java:61-68` |
| 4 | 판매 입찰(`Xzt63` SaleBid) 갱신: `order` 연결 + 상태 변경 | 판매 입찰 `PENDING → MATCHED` | `:279-280`, `D/m85/entity/Xzt63.java:58-61,66-68` |
| 5 | 판매자가 창고 보관을 선택한 Sale이면 창고 보관(`Xms75`) 상태 갱신 | `ASSOCIATED_WITH_ORDER` | `:291-293`, `D/m63/service/command/Xms75CommandService.java:117-133` |
| 6 | `Payment`(`Xjt45` 하위: 카드 `Xxf47`, 계좌 `Xkg34`, 일반 `Xgg74`) 신규 | 결제 수단별로 다름 (3번 참고) | `:305`, `Xjt45CommandService.java:57-88` |
| 7 | 결제 직후 `Sale`(`Xpj42`) 갱신 | `SOLD` | `Xjt45CommandService.java:404`/`:419`, `D/m85/entity/Xpj42.java:73-75` |
| 8 | `OrderBid`(`Xtw92`) 신규 저장 | `MATCHED`, `isInstantPurchase=true` | `Xtw92CommandService.java:192-206`, `D/m99/entity/Xtw92.java:60-82,97-99` |

세부 사항:
- 4번: `assignOrder`와 `updateStatus(MATCHED)`는 상태 전이 검증 없이 값을 대입한다 (`Xzt63.java:58-68`). 이어서 `entityManager.flush()`로 DB에 반영한다 (`Xhq12CommandService.java:283`).
- 5번: Sale이 창고 보관이 아니면(`sale.isWarehouseStorage()==false`) 건너뛴다. 창고 레코드가 없으면 `Xzg57Exception`이 난다 (`D/m63/service/query/Xms75QueryService.java:30-33`). 이 예외는 `Xkd21Exception`으로 감싸져 전체가 롤백된다 (`Xhq12CommandService.java:295-301`).
- 7번: `Sale.updateStatus`는 전이 검증이 없다 (`Xpj42.java:73-75`). 따라서 `Xpj42Status.canTransitionTo`를 거치지 않고 바로 `SOLD`가 된다.
- 7번: 이 시점에는 `OrderBid`가 아직 없어 `order.getOrderBid()==null`이다. 그래서 `saleBidQueryService.findByOrderId`로 판매 입찰을 찾아 Sale을 얻는다 (`Xjt45CommandService.java:388-405`). 4번에서 판매 입찰에 `order`를 연결·flush해 둔 덕분에 찾을 수 있다.
- 8번: `Xtw92.builder()`에서 `status(MATCHED)`를 주고, `assignOrder`가 다시 `MATCHED`로 설정하며, `markAsInstantPurchase()`로 플래그를 켠다 (`Xtw92CommandService.java:192-205`, `Xtw92.java:60-82,97-99`). 이 `OrderBid`가 응답으로 나가는 ID의 주인이다.
- `OrderBid`는 `Xhq12CommandService`가 아니라 `Xtw92CommandService`에서 마지막에 저장한다. 따라서 결제 처리 시점에는 존재하지 않는다.

**`Order`의 상태 변경은 이 흐름에서 일어나지 않는다.** `createInstantOrder` 안에서 `order.updateStatus(...)`를 부르는 곳은 없다. 상태 값은 `PENDING_PAYMENT`로 저장된 이후 그대로다 (5번 항목 참고).

## 3. 결제 수단별 결과

분기: `Xjt45CommandService.processPayment`의 `switch (getResolvedPaymentType())` (`Xjt45CommandService.java:67-80`).
공통 사전 검증: `order.getId() == requestDto.getOrderId()`, 이메일 일치, `paidAmount > 0` (`:117-145`). DTO는 `paidAmount`에 `@Min(100)` 제약도 있다 (`D/m64/dto/Xjt45RequestDto.java:50-52`).

| 수단 | 동작 | 결제 상태 | 근거 |
|---|---|---|---|
| CARD | 저장된 결제 정보(`Xjt45Info`) 조회 → PortOne 카드 결제 API 호출 → 응답 `status`가 문자열 `"success"`이면 `PAID`+성공 처리, 아니면 `PENDING` 그대로 저장 | `PAID` 또는 `PENDING` | `:157-217`, 특히 `:179`, `:203-206`, `:208` |
| ACCOUNT | 은행명 검증 후 즉시 `PENDING`으로 저장. 외부 호출 없음 | `PENDING` | `:236-262` (`:260`) |
| GENERAL | `impUid` 필수 확인 후 외부 호출 없이 즉시 `PAID`+성공 처리 | `PAID` | `:290-316` (`:313-314`) |

**즉시 구매가 끝까지 성공하는가**
- 세 수단 모두 `processPayment`가 예외 없이 반환하면 `createInstantOrder`가 `order`를 반환하고 OrderBid가 저장된다. HTTP 200과 "즉시 구매가 성공적으로 처리되었습니다."가 나간다 (`Xhq12CommandService.java:305-311`, `Xtw92CommandController.java:109`).
- 결제가 `PENDING`(계좌이체, 또는 응답 status가 `"success"`가 아닌 카드)이어도 응답은 성공이고, 판매자·구매자 알림이 나가며 Sale은 `SOLD`가 된다.
  - `notifyUsersAndUpdateSaleStatus`는 `payment`의 상태를 보지 않는다 (`Xjt45CommandService.java:383-420`).
  - 즉 계좌이체는 입금 확인 전인데도 "결제가 완료되었습니다" 알림이 나가고 Sale이 `SOLD`가 된다.
- 카드의 `"success"` 비교는 `:203`의 문자열 리터럴이다. PortOne 응답의 `status` 값이 이 문자열과 다르면 카드도 `PENDING`으로 남는다. 실제 PortOne이 어떤 값을 주는지는 코드에서 확인할 수 없다.
- 일반 결제(GENERAL)는 서버가 대행사에 확인하지 않고 클라이언트가 보낸 `impUid`를 믿고 `PAID`로 처리한다 (`:297-314`).

**결제 대행사가 카드 결제를 실패로 응답하면**
1. `processCardPayment`가 HTTP 상태가 200이 아니거나 `body.code != 0`이면 `Xtc14Exception("카드 결제 요청 실패: ...")`을 던진다 (`Xhs91ApiClient.java:270-275`).
   - `Xtc14Exception`은 `Xjt45Exception`의 하위이고 (`D/m64/exception/Xtc14Exception.java:6`), `Xkt44Exception`은 `RuntimeException`이다 (`G/exception/Xkt44Exception.java:10`).
2. `createCardPayment`가 이를 그대로 던진다. 결제 엔티티는 저장 전이라 만들어지지 않는다 (`Xjt45CommandService.java:178-185`, 저장은 `:208`).
3. `processPayment`가 로깅 후 재던진다 (`:89-94`). `notifyUsersAndUpdateSaleStatus`는 호출되지 않으므로 알림도 없다 (`:83`은 `switch` 뒤).
4. `createInstantOrder`의 `catch (Exception e)`가 `Xwf42Exception("결제 처리 중 오류가 발생했습니다")`으로 감싼다 (`Xhq12CommandService.java:304-309`). 바깥 `catch`는 `Xhq12Exception`이라 그대로 재던진다 (`:312-315`).
5. `Xtw92CommandService.handleOrderBidCreationException`이 `Xhq12Exception`을 그대로 던진다 (`Xtw92CommandService.java:145-147`, `:212-215`).
6. 런타임 예외가 `@Transactional` 경계를 넘으므로 전체가 롤백된다. 새로 만든 `Order`, `OrderItem`, `OrderShipment`, 판매 입찰의 `MATCHED` 변경, 창고 상태 변경이 모두 취소된다. `OrderBid`도 아직 만들어지지 않았다.
7. `Xkt44ExceptionHandler`가 `Xhq12Exception` 핸들러로 에러 응답을 만든다 (`G/exception/Xkt44ExceptionHandler.java:325-329`).
- 재시도: `@Retryable`이 `Xhs91ApiClient` 메서드에 붙어 있지만 (`:69-73`, `:224-228`) `@EnableRetry`가 프로젝트에 없어 실제로는 동작하지 않는다 (소스 전체 grep 결과 없음). 그래서 재시도 없이 즉시 실패한다.
- 결과적으로 결제 실패 시 주문이 남지 않으므로 "결제 실패 주문 + 상태 FAILED"는 이 경로에서 만들어지지 않는다. `Xjt45Status.FAILED`는 이 흐름에서 쓰이지 않는다.

## 4. 알림: 누가, 언제, 어떤 방식으로

**수신자와 내용** (`Xjt45CommandService.sendNotifications`, `:434-456`)
- 구매자 (`order.getUser()`): "결제가 완료되었습니다. 주문 ID: {orderId}" (`:436-443`)
- 판매자 (`sale.getSeller()`): "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}" (`:447-454`)
- 둘 다 카테고리 `SHOPPING`, 타입 `BID`다.
- 구매자 알림에 들어가는 "주문 ID"는 Order ID다. 응답으로 받는 OrderBid ID와는 다른 값이다.

**시점**
- 결제 처리 직후, 같은 요청·같은 트랜잭션 안에서 보낸다 (`Xjt45CommandService.java:83` → `:416`).
- `Sale`을 `SOLD`로 바꾸기 직전이다 (`:416-419`).
- 결제가 `PENDING`이어도 알림은 나간다 (3번 참고).
- 즉시 구매 경로에서 다른 알림은 없다.

**전달 방식** (`D/m52/service/command/Xbp24CommandService.java:44-59`, `:303-322`)
1. 먼저 DB에 알림 레코드를 저장한다 (`notificationRepository.save`, `:52-53`).
2. 그 다음 실시간 전송을 시도한다. Redis에 `WebSocket:Xjm45:{email}` 키가 있을 때, 즉 사용자가 WebSocket에 접속해 있을 때만 STOMP로 `/user/queue/notifications`에 푸시한다 (`:303-313`, `:37-38`, 브로커 설정 `G/config/websocket/WebSocketConfig.java:28-30`).
3. 접속 중이 아니면 저장만 하고 푸시는 없다 (`:320-322`). 전송 예외는 삼킨다 (`:315-319`).
- 동기 호출이며 별도 큐나 Kafka를 거치지 않는다.
- `sendNotifications`는 예외를 삼키고 `warn`만 남긴다 (`Xjt45CommandService.java:457-461`). 다만 `Xbp24CommandService`는 클래스 레벨 `@Transactional`이고 같은 트랜잭션에 참여한다 (`Xbp24CommandService.java:27`). 이 서비스가 런타임 예외를 던지면 바깥 트랜잭션이 rollback-only로 표시될 수 있다. 이 부분은 코드 구조에서 추론한 것이고 실행으로 확인하지 않았다.

## 5. 최종 상태와 창고 보관 선택 시 차이

**주문(Order)의 최종 상태: `PENDING_PAYMENT`**
- `createInstantOrder`는 `Order`를 `PENDING_PAYMENT`로 저장하고 (`Xhq12CommandService.java:241-245`), 이후 `Order.updateStatus`를 호출하지 않는다 (`:219-319` 전체).
- 결제 서비스도 `Order` 상태를 바꾸지 않는다. `payment.assignOrder(order)`만 한다 (`Xjt45CommandService.java:200`, `:258`, `:311`).
- 호출자(`Xtw92CommandService`, 컨트롤러)에도 `Order` 상태 변경이 없다 (`Xtw92CommandService.java:118-149`, `:189-207`).
- 따라서 카드 `PAID`, 일반 결제 `PAID`인 경우에도 주문은 `PAYMENT_COMPLETED`/`PREPARING`/`COMPLETED`로 가지 않고 `PENDING_PAYMENT`로 남는다.
- 상태 전이표상 `PENDING_PAYMENT → PAYMENT_COMPLETED`는 허용되지만 (`D/m99/entity/Xhq12Status.java:24`), 이 경로에서는 호출하지 않는다.
- 결과 상태 조합:
  - Order = `PENDING_PAYMENT`
  - OrderShipment = `PENDING`
  - SaleBid = `MATCHED`
  - OrderBid = `MATCHED` (`isInstantPurchase=true`)
  - Sale = `SOLD`
  - Payment = `PAID`(일반, 카드 성공 시) 또는 `PENDING`(계좌이체, 카드 응답이 `"success"`가 아닐 때)

**구매자가 "창고 보관"을 선택한 경우: 사실상 달라지는 것이 없다**
- 컨트롤러는 `requestDto.isWarehouseStorage()`를 서비스에 넘기고 (`Xtw92CommandController.java:105`), 서비스도 `createInstantOrder`에 그대로 전달한다 (`Xtw92CommandService.java:137`).
- 그러나 `createInstantOrder` 본문은 `isWarehouseStorage` 파라미터를 읽지 않는다 (`Xhq12CommandService.java:220-221`에 선언만 있고 본문에서 참조가 없다). 본문에서 쓰는 `sale.isWarehouseStorage()`는 **판매자 Sale 엔티티**의 값이다 (`:292`).
- 구매자 플래그가 true여도 `Xms75`(창고 보관) 레코드 생성(`createOrderStorage`)이나 `IN_WAREHOUSE`/`COMPLETED` 전이는 일어나지 않는다.
- 구매자 선택을 실제로 반영하는 코드는 즉시 구매가 아닌 다른 경로(`processPaymentAndShipment`)에만 있다 (`Xhq12CommandService.java:163-172`: `PAYMENT_COMPLETED → PREPARING → IN_WAREHOUSE`, 창고 생성, `COMPLETED`). 즉시 구매는 이 메서드를 호출하지 않는다.
- 판매자가 창고 보관 Sale을 올렸다면(`sale.isWarehouseStorage()==true`), 구매자 선택과 무관하게 창고 보관 상태가 `ASSOCIATED_WITH_ORDER`로 바뀐다 (`:291-293`).
- 이 때문에 컨트롤러 로그에 찍히는 "창고 보관 여부"(`Xtw92CommandController.java:94-95`)와 실제 처리는 일치하지 않는다.
