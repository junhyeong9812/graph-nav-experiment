# 구매자 배송: 운송장 등록 → 배송 완료

경로 약어: `B` = `src/main/java/com/fream/back`

핵심 엔티티: 구매자 배송 `Xfr60`(테이블 `order_shipment`, 배송 상태 `Xzn53Status`), 주문 `Xhq12`(`orders`, 주문 상태 `Xhq12Status`), 주문 입찰 `Xtw92`, 판매 입찰 `Xzt63`, 판매 `Xpj42`.
(`Xrg51`은 판매자 배송이라 이 흐름과 무관하다.)

## 사전: 결제·배송 처리가 끝난 주문과 배송의 상태

- 결제·배송 처리: `B/domain/m99/service/command/Xhq12CommandService.java:112` `processPaymentAndShipment`
- 배송 생성: `createOrderShipment`가 배송을 `PENDING` 상태로 만든다. (`B/domain/m45/service/command/Xfr60CommandService.java:56,67`, 호출은 `Xhq12CommandService.java:148`)
- 주문 상태: 창고 보관이 아니면 `PAYMENT_COMPLETED → PREPARING`에서 멈춘다. (`Xhq12CommandService.java:175-176`)
- 따라서 실배송 일반 구매 입찰 주문은 주문 `PREPARING`, 배송 `PENDING` 상태가 된다.
- 주문 상태 전이표 (`B/domain/m99/entity/Xhq12Status.java:157-165`)
  - `PENDING_PAYMENT → {PAYMENT_COMPLETED, COMPLETED, IN_WAREHOUSE}`
  - `PREPARING → {IN_WAREHOUSE, SHIPMENT_STARTED}`
  - `IN_TRANSIT → {COMPLETED}`
  - `Xhq12.updateStatus`가 허용되지 않는 전이를 `Xxm16StatusException`으로 던진다. (`B/domain/m99/entity/Xhq12.java:113-121`)
- 코드 어디에서도 `SHIPMENT_STARTED`로 보내지 않는다. `Xhq12Status.(IN_TRANSIT|SHIPMENT_STARTED)`를 세팅하는 곳은 `Xfr60CommandService`의 `updateTrackingInfo`(:260)뿐이다.

## 1. 운송장 등록 요청

### 1-1. 진입 API

- `PATCH /shipments/order/{shipmentId}/status`, body는 `Xfr60RequestDto`(courier, trackingNumber). (`B/domain/m45/controller/command/Xfr60CommandController.java:20,33-49`)
- 컨트롤러는 `Xfr60CommandService.updateTrackingInfo(shipmentId, courier, trackingNumber)`를 호출한다. (`:41`)
- 인증만 요구하고 별도 역할 제한은 없다. (`B/global/config/security/SecurityConfig.java:49-51`, `anyRequest().authenticated()`)
- 같은 컨트롤러를 복제한 경로가 5개 더 있고 모두 같은 서비스를 호출한다. (`/admin/shipments/order` m09, `/settlement/...` m81, `/internal/...` m38, `/partner/...` m31, `/legacy/...` m70)
  - 예: `B/domain/m09/controller/command/Xqh36CommandController.java:20,24,33`
- 별도로 `POST /shipments/order/{id}/check-status`는 운송장을 저장하고 즉시 조회한다. (`Xfr60CommandController.java:58`, 서비스 `Xfr60CommandService.java:452`)

### 1-2. 코드가 의도한 상태 변경 순서와 알림 (`Xfr60CommandService.java:239-299`)

1. courier/trackingNumber가 비어 있으면 `TRACKING_INFO_REQUIRED`. (:241-)
2. 배송을 조회한다. (:249-)
3. `shipment.updateTrackingInfo`로 배송을 `IN_TRANSIT`으로 바꾼다. (:256)
   - 엔티티는 전이 검사 없이 `status = IN_TRANSIT`을 대입한다. (`B/domain/m45/entity/Xfr60.java:41-45`)
4. `order.updateStatus(IN_TRANSIT)`로 주문을 `IN_TRANSIT`으로 바꾼다. (:260)
5. 구매자에게 알림 1건 "상품이 출발하였습니다. 주문 ID: …"을 보낸다. (:266)
6. `updateSaleStatusToSold(orderId)`로 판매를 `SOLD`로 바꾸고 판매자에게 알림을 보낸다. (:276, 본문 :112-168)
7. 창고 보관 상품이면 창고 상태를 갱신한다. (:279-286)
8. `updateOrderAndSaleBidStatusToCompleted`로 주문 입찰·판매 입찰 `MATCHED → COMPLETED`를 처리한다. (:289, 본문 :413-)

### 1-3. 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문(즉시 구매 아님)에서의 결과: 끝까지 성공하지 못한다

- 실패 지점: 4단계 `order.updateStatus(Xhq12Status.IN_TRANSIT)` (`Xfr60CommandService.java:260`)
  - 이유: 주문이 `PREPARING`인데 `PREPARING`에서는 `IN_TRANSIT`으로 갈 수 없다. (`Xhq12Status.java:159`)
  - `Xxm16StatusException`(`Xhq12Exception` 계열)이 발생한다. (`Xhq12.java:117-119`)
- 예외 변환: `catch (Xzn53Exception)`이 아니라 `catch (Exception e)` 쪽에서 `Xzn53Exception(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")`으로 감싸 던진다. (`Xfr60CommandService.java:293-300`)
  - 실제 원인은 주문 상태 전이 오류인데 "배송 정보를 찾을 수 없음" 코드로 나간다.
- 저장되는 것: 없다.
  - `Xkt44Exception`은 `RuntimeException`이다. (`B/global/exception/Xkt44Exception.java:10`)
  - 메서드가 `@Transactional`(:238)이므로 롤백된다. 3단계의 배송 `IN_TRANSIT`·courier·trackingNumber 변경은 DB에 남지 않고, 배송은 `PENDING`, 주문은 `PREPARING` 그대로다.
  - 5~8단계는 실행되지 않는다. 구매자·판매자 알림, 판매 `SOLD`, 입찰 `COMPLETED`도 모두 없다.
- 응답: HTTP 404, 본문은 `ErrorResponse`(code `S001`, message "배송 정보를 찾을 수 없습니다.", status 404, 요청 URI).
  - 핸들러: `B/global/exception/Xkt44ExceptionHandler.java:459-473`
  - 코드 정의: `B/domain/m45/exception/Xzn53ErrorCode.java:12`
- 설령 4단계를 통과해도 6단계에서 막힌다.
  - `Xzt63QueryService.findByOrderId`는 SaleBid가 없으면 null이 아니라 `IllegalArgumentException`을 던진다. (`B/domain/m85/service/query/Xzt63QueryService.java:26-28`)
  - `updateSaleStatusToSold`의 첫 호출(`Xfr60CommandService.java:116`)은 try 밖이므로 예외가 그대로 올라가 같은 방식으로 감싸져 실패한다.
  - 일반 입찰 주문에는 아직 SaleBid가 연결되어 있지 않다.

### 1-4. 참고: 우회 경로 `check-status`

- `updateAndCheckShipmentStatus`(`Xfr60CommandService.java:452-`)는 배송에 운송장을 넣고(:473) 택배사 조회 결과로 배송 상태만 바꾼다. 주문 상태는 건드리지 않는다.
- 조회 결과가 배송완료가 아니면 배송 `IN_TRANSIT`(또는 `OUT_FOR_DELIVERY`)이 저장되고 주문은 `PREPARING`으로 남는다.
- 배치 대상(IN_TRANSIT)이 만들어지는 실질 경로는 이것뿐이다.

## 2. 배송 완료 감지

### 2-1. 누가·언제·어떻게

- 주체: 스프링 스케줄러 `Xzn53BatchScheduler.scheduleShipmentStatusJob()`가 Spring Batch Job `updateShipmentStatusesJob`을 실행한다. (`B/global/config/Xzn53BatchScheduler.java:17-22,34-43`)
- 주기: `@Scheduled(cron = "0 0 */6 * * *")`, 매 6시간 정각(00·06·12·18시)이다. (`Xzn53BatchScheduler.java:34`)
- `@EnableScheduling`은 `B/domain/m84/config/Xzh65Configuration.java:37`에 있다.
- 방식: 배송마다 CJ대한통운 추적 페이지 `https://trace.cjlogistics.com/next/tracking.html?wblNo=<운송장>`를 Playwright(헤드리스 크롬)로 열고, `tbody#statusDetail tr`의 마지막 행 5번째 `td`(index 4) 텍스트를 상태 문자열로 읽는다.
  - 처리 코드: `B/domain/m45/config/Xcz52Processor.java:28-30,70-90,181`
  - 스텝 시작 시 브라우저를 열고 종료 시 닫는다. (`B/domain/m45/config/Xhd56Listener.java:15-24`)

### 2-2. 조회 대상

- 리더: `SELECT s FROM Xfr60 s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL`, 페이지 크기 50. (`B/domain/m45/config/Xpc23JobConfig.java:89-96`)
- 즉 운송장이 있고 배송 상태가 `IN_TRANSIT`·`OUT_FOR_DELIVERY`인 `order_shipment`만 대상이다. `PENDING`/`DELIVERED` 등은 제외된다.
- 청크 크기 50, 스킵 한도 50이다. (`Xpc23JobConfig.java:51-52,67,76-77`)

### 2-3. 실제 실행되는 처리 코드 (비슷한 코드 구분)

| 후보 | 실행 여부 | 근거 |
|---|---|---|
| `Xpc23JobConfig`의 스텝이 `new Xcz52Processor(...)`를 processor로 사용 | **실행됨** | `Xpc23JobConfig.java:67-73` |
| `Xpc23JobConfig.shipmentItemProcessor()` 빈 + `parseCjLogisticsStatus`(Jsoup) | 스텝에 연결되지 않아 사용되지 않음 | 스텝은 `.processor(new Xcz52Processor…)` 사용 (`:69`), `shipmentItemProcessor`를 참조하는 곳 없음 |
| `Xfr60CommandService.updateShipmentStatuses()` | 호출하는 곳이 없어 사용되지 않음 | 정의 `Xfr60CommandService.java:309` 외 호출 없음. `Xwg86` 단발 조회를 쓰는 별도 구현 |
| `Xfr60CommandService.updateAndCheckShipmentStatus` | 스케줄이 아니라 `check-status` API에서만 | `Xfr60CommandController.java:68,112` |

- 같은 구성이 m81·m38·m09·m31·m70에도 복제되어 있다.
  - JobConfig: `B/domain/m81/config/Xfr70JobConfig.java:55`, `m38/config/Xrx68JobConfig.java:55`, `m09/config/Xxt33JobConfig.java:55`, `m31/config/Xkd78JobConfig.java:55`, `m70/config/Xkq49JobConfig.java:55` 모두 `updateShipmentStatusesJob()` 빈.
  - 복제 프로세서: `Xcj35Processor`, `Xvh59Processor`, `Xzd96Processor`, `Xhx91Processor`, `Xqn22Processor`
- 복제본은 알림 서비스 클래스만 다르다 (`Xtc38`, `Xzm86`, `Xrw60`, `Xss87`, `Xbj82`). 로직·알림 문구는 `Xbp24CommandService`와 동일하다. (`notifyShipmentCompleted` 모두 `:219-228`)
- `completeOrder`는 전부 `Xfr60CommandService`(m45)를 쓴다. 어느 복제본이 선택되어도 동작은 같다.
- 주의: 같은 이름의 `updateShipmentStatusesJob` 빈이 6곳에 정의되어 있고 `allow-bean-definition-overriding` 설정은 없다. 기본 설정이면 기동 시 빈 이름 충돌이 날 수 있다.
  - 이 분석은 충돌이 없다고 가정하고, 코드 기준 정규 구현인 m45(`Xpc23JobConfig` + `Xcz52Processor`)를 기준으로 한다.
  - 스케줄러는 `@Qualifier("updateShipmentStatusesJob")`로 주입한다. (`Xzn53BatchScheduler.java:19-21`)

### 2-4. 택배사 상태 문자열 → 내부 상태 (`Xcz52Processor.java:220-226`)

- `"배송완료"` → `DELIVERED`
- `"배송출발"` → `OUT_FOR_DELIVERY`
- 그 외 모든 문자열(null이 아닌 값) → `IN_TRANSIT`
- 정확히 일치하는 문자열만 인식한다. `trim()`은 적용되지만(`:181`) 그 외 변형은 모두 `IN_TRANSIT`이다.
- 테이블이 비었거나 텍스트가 비면 `TRACKING_HTML_PARSE_ERROR`다. (`:171-186`)

## 3. 배송 완료 판정 이후 (`Xcz52Processor.process`, `:95-126`)

`newStatus == DELIVERED`이고 현재 상태와 다를 때의 순서는 다음과 같다. 현재 상태와 같으면 변경 없이 반환한다. (`:99-103`)

1. 배송 `IN_TRANSIT/OUT_FOR_DELIVERY → DELIVERED` (`:113`, 전이 허용: `B/domain/m45/entity/Xzn53Status.java:16-28`)
2. `Xfr60CommandService.completeOrder(orderId)` (`:116`, 본문 `Xfr60CommandService.java:191-228`)
   1. `Xtw92`를 `findByOrderId`로 조회한다. 없으면 `IllegalArgumentException`이다. (:196-197)
   2. 주문 `→ COMPLETED` (:204)
   3. `updateSaleStatusToSold(orderId)` (:208)
      - 판매 입찰 → 판매가 `SOLD`로 전이 가능하면(`SELLING`/`ON_AUCTION` 등) 판매를 `SOLD`로 바꾼다. (:116-123)
      - 창고 보관이면 창고 상태 `SOLD`로 바꾸고, 판매자에게 알림 "상품이 성공적으로 판매 완료되었습니다. 판매 ID: …"을 보낸다. (:133)
      - 주문 입찰 기준의 같은 처리가 한 번 더 있다. (:151-165)
   4. 구매자 알림 "[completeOrder] 주문이 완료 처리되었습니다. 주문 ID: …" (:212-)
3. `notificationService.notifyShipmentCompleted(order)`로 구매자 알림 "[배송 완료] 상품이 배송 완료되었습니다. 주문 ID: …" (`Xcz52Processor.java:117`, `B/domain/m52/service/command/Xbp24CommandService.java:219-234`)
   - 이 메서드는 내부 예외를 삼킨다. (:230-233)
4. 청크 writer `JpaItemWriter`가 배송을 저장한다. (`Xpc23JobConfig.java:74,241`)

### 알림 건수 (정상 완주 시)

- 구매자 2건: `[completeOrder]` 1건 + `[배송 완료]` 1건.
- 판매자: `completeOrder` 안에서 판매가 아직 `SOLD`가 아닐 때만 1건(두 조회 경로 모두 `SOLD`로 전이 가능한 경우 최대 2건까지 가능). 이미 `SOLD`이면 0건.

### 주문 입찰·판매 입찰 상태

- 배송 완료 경로 어디에서도 `Xtw92`/`Xzt63`의 상태를 바꾸지 않는다.
  - `updateOrderAndSaleBidStatusToCompleted`(`Xfr60CommandService.java:413-`)는 운송장 등록(`:289`)에서만 호출된다.
  - 그 등록 경로는 1-3에서 보듯 일반 주문에서 실패한다.
- 따라서 입찰은 결제 시 세팅된 `MATCHED`에 머문다. `COMPLETED`로 가지 않는다.
  - 판매 입찰은 즉시 구매 시 `MATCHED`다. (`Xhq12CommandService.java:280`)
  - 주문 입찰은 즉시 구매에서 `MATCHED`로 만들어진다. (`B/domain/m99/service/command/Xtw92CommandService.java:189-203`)
- 일반 입찰 주문 쪽 `MATCHED` 처리는 `orderBidQueryService.findById(orderId)`로, 주문 ID를 입찰 ID로 조회하는 버그가 있다. (`Xhq12CommandService.java:188`)

## 4. 주문 종류별 차이

두 경우 모두 배치가 배송을 읽으려면 배송이 `IN_TRANSIT`이어야 한다. 위 1-4의 `check-status` 경로가 그 상태를 만든다. 아래는 배송이 `IN_TRANSIT`이고 택배사가 "배송완료"를 돌려준 이후의 결과다.

### (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문: 끝까지 진행되지 않는다

- 주문은 `PREPARING`이다. (사전 항목)
- `completeOrder` 2-2 단계에서 `order.updateStatus(COMPLETED)`가 `PREPARING → COMPLETED` 불가로 `Xxm16StatusException`을 던진다. (`Xfr60CommandService.java:204`, 전이표 `Xhq12Status.java:159`)
- `catch (Exception)`이 `Xzn53Exception(ORDER_NOT_FOUND_FOR_SHIPMENT)`로 바꿔 던진다. (:221-227)
- 프로세서는 이를 다시 던진다. (`Xcz52Processor.java:133-148`)
- 결과
  - 배송은 `DELIVERED`로 저장되지 않고 `IN_TRANSIT`으로 남는다. (청크 롤백)
  - 주문은 `PREPARING`, 입찰은 `MATCHED`, 판매 변화 없음, 알림 0건이다.
  - 이 배송은 다음 주기(6시간 뒤)에 같은 이유로 또 실패한다. 영구 반복된다.

### (b) 즉시 구매로 만들어진 주문: `completeOrder`는 끝까지 진행된다

- 즉시 구매 주문은 `PENDING_PAYMENT` 상태이고 결제 처리가 주문 상태를 바꾸지 않는다. (`Xhq12CommandService.java:244,305`)
- 이 주문에는 주문 입찰 `Xtw92`(`MATCHED`, `isInstantPurchase`)가 생긴다. (`Xtw92CommandService.java:189-203`) → `findByOrderId` 성공.
- `PENDING_PAYMENT → COMPLETED`는 허용된다. (`Xhq12Status.java:157`) → 주문 `COMPLETED`.
- 판매는 이미 결제 시점에 `SOLD`로 바뀌어 있다. (`B/domain/m64/service/command/Xjt45CommandService.java:383-406`, `notifyUsersAndUpdateSaleStatus`)
  - 그래서 `completeOrder`의 `canTransitionTo(SOLD)`가 거짓이라 판매자 알림 0건이다. (`Xfr60CommandService.java:119,156`)
- 결과
  - 배송 `DELIVERED`
  - 주문 `COMPLETED`
  - 구매자 알림 2건
  - 판매자 알림 0건 (결제 시점에 이미 발송)
  - 주문 입찰·판매 입찰은 `MATCHED` 유지 (`COMPLETED`로 안 바뀜)

### 정리

- (a)는 주문 상태 전이 위반으로 완료 처리가 전부 실패하고 아무것도 바뀌지 않는다.
- (b)는 `PENDING_PAYMENT → COMPLETED` 전이가 허용되어 완료된다.
- (b)의 운송장 등록 `PATCH` API는 `PENDING_PAYMENT → IN_TRANSIT`이 허용되지 않아 (a)와 똑같이 실패한다. (`Xhq12Status.java:157`) 같은 이유로 `PATCH`로는 두 종류 모두 배송이 `IN_TRANSIT`이 되지 못한다.

## 5. 실패 처리 (주기 처리 중 한 건이 실패할 때)

- 프로세서는 모든 예외를 `Xzn53Exception`으로 통일해 던진다. (`Xcz52Processor.java:133-143`)
  - 운송장 없음: `TRACKING_NUMBER_INVALID` (`:50-53`)
  - 브라우저/조회 오류: `EXTERNAL_TRACKING_SERVICE_ERROR` 등
  - 파싱 오류: `TRACKING_HTML_PARSE_ERROR`
- 스텝은 `faultTolerant().skip(Exception.class).skipLimit(50)`이다. (`Xpc23JobConfig.java:75-77`)
  - 실패한 건은 스킵되고, 사유를 `SkipListener`가 로그로 남긴다. (`Xpc23JobConfig.java:252-290`)
  - 청크(50건) 트랜잭션이 롤백되고 같은 청크를 건별로 다시 처리한다. 실패 건만 스킵되고 나머지는 정상 커밋된다.
  - 실패한 건은 상태가 바뀌지 않아 다음 주기에 다시 대상이 된다.
- 스킵 한도(50건) 초과 시 스텝이 실패하고 남은 건 처리가 중단된다. 한 건 실패가 곧바로 전체 중단은 아니다.
- 상태 전이 위반(예: 현재 `OUT_FOR_DELIVERY`인데 택배사 문자열이 그 외라 `IN_TRANSIT`으로 매핑되는 경우)도 `IllegalStateException` → `Xzn53Exception`으로 스킵된다. (`Xfr60.java:47-55`, `Xzn53Status.java:23-28`, `Xcz52Processor.java:125`)
- 스케줄러는 `jobLauncher.run`의 예외를 잡아 `printStackTrace()`만 한다. (`Xzn53BatchScheduler.java:42-44`)
- 참고: 미사용 코드인 `Xfr60CommandService.updateShipmentStatuses()`는 건별 try/catch로 계속 진행하지만 실행되지 않는다. (`Xfr60CommandService.java:309`)
