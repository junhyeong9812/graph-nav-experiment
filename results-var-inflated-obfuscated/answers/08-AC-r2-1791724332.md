# 구매자 배송: 운송장 등록 → 배송 완료

경로 약어: `D45` = `src/main/java/com/fream/back/domain/m45`, `D99` = `src/main/java/com/fream/back/domain/m99`, `G` = `src/main/java/com/fream/back/global`.
클래스 이름은 난독화되어 있다. Xfr60 = 주문 배송(OrderShipment), Xhq12 = 주문(Order), Xtw92 = 주문 입찰(OrderBid), Xzt63 = 판매 입찰(SaleBid), Xpj42 = 판매(Sale), Xzn53Status = 배송 상태.

## 0. 선행 사실: 결제·배송 처리 직후 상태

- 결제·배송 처리(`processPaymentAndShipment`)는 Xfr60 을 `PENDING` 으로 만든다. `D45/service/command/Xfr60CommandService.java:61-68`, 호출은 `D99/service/command/Xhq12CommandService.java:148-155`.
- 창고 보관이 아닌 실배송이면 주문은 `PAYMENT_COMPLETED → PREPARING` 에서 멈춘다. `D99/service/command/Xhq12CommandService.java:175-176`.
- 주문 상태 전이표: `PREPARING` 에서는 `IN_WAREHOUSE`, `SHIPMENT_STARTED` 로만 갈 수 있다. `D99/entity/Xhq12Status.java:26`.
- `IN_TRANSIT` 으로 가는 전이는 `SHIPMENT_STARTED → IN_TRANSIT` 하나뿐이다. `D99/entity/Xhq12Status.java:28`.
- `SHIPMENT_STARTED` 로 바꾸는 코드는 어디에도 없다. 전이표 정의(`Xhq12Status.java:13,26-28`)와 화면 문구(`D99/controller/query/Xhq12QueryController.java:207`)에만 나온다.
- 즉시 구매 주문(`createInstantOrder`)은 `PENDING_PAYMENT` 로 만들어진 뒤 결제만 처리되고 상태가 바뀌지 않는다. `D99/service/command/Xhq12CommandService.java:241-245,305` (이 메서드에는 `order.updateStatus` 가 없다).

## 1. 운송장 등록 요청

### 1-1. 진입 API

- `PATCH /shipments/order/{shipmentId}/status`, body 는 `{courier, trackingNumber}`.
  - 컨트롤러: `D45/controller/command/Xfr60CommandController.java:20,33-45`.
  - 서비스: `Xfr60CommandService#updateTrackingInfo` (`D45/service/command/Xfr60CommandService.java:239`).
  - body DTO: `D45/dto/Xfr60RequestDto.java:11-12`.
- 같은 서비스를 호출하는 복제 컨트롤러가 접두사만 바꿔 존재한다. 로직은 동일하다.
  - `/admin/shipments/order/{id}/status` (m09), `/settlement/...` (m81), `/internal/...` (m38), `/partner/...` (m31), `/legacy/...` (m70).
  - 예: `src/main/java/com/fream/back/domain/m09/controller/command/Xqh36CommandController.java`.
- 별도의 역할 검사는 없다. 화이트리스트 밖은 인증만 요구한다. `G/config/security/SecurityConfig.java:48-50`.
- 보조 API: `POST /shipments/order/{id}/check-status` 와 `/check-status-string` 은 송장 등록과 동시에 택배사 조회까지 한다 (`Xfr60CommandController.java:58,103`, 서비스 `Xfr60CommandService.java:452`).

### 1-2. 설계된 상태 변경 순서 (`updateTrackingInfo`, `Xfr60CommandService.java:239-303`)

1. 택배사·운송장이 비어 있으면 `Xzn53Exception(TRACKING_INFO_REQUIRED)` 를 던진다 (243-246).
2. Xfr60 의 courier, trackingNumber 를 넣고 상태를 곧바로 `IN_TRANSIT` 으로 설정한다 (256). 전이 검사 없이 필드를 직접 대입한다. `D45/entity/Xfr60.java:337-341`.
3. 주문 Xhq12 를 `IN_TRANSIT` 으로 바꾼다 (260).
4. 구매자에게 알림 "상품이 출발하였습니다. 주문 ID: …" 를 만든다 (265-271).
5. `updateSaleStatusToSold(orderId)` (276, 본체 112-183).
   - SaleBid 경유 Xpj42 를 `SOLD` 로 바꾸고 (123), 창고 보관 상품이면 창고 상태를 갱신한다 (126-129).
   - 판매자에게 알림 "상품이 성공적으로 판매 완료되었습니다…" 를 만든다 (132-138).
   - OrderBid 경유 Xpj42 에 대해서도 같은 처리를 한다 (150-180).
6. SaleBid 의 판매가 창고 보관이면 창고 상태를 다시 갱신한다 (279-286).
7. `updateOrderAndSaleBidStatusToCompleted` (289, 본체 413-440).
   - OrderBid(Xtw92) 와 SaleBid(Xzt63) 가 `MATCHED` 이면 `COMPLETED` 로 바꾼다 (422-432).
   - 이 메서드는 `private` + `@Transactional` 이라 프록시를 타지 않는다. 내부 예외는 전부 삼키고 로그만 남긴다 (436-439).

알림 의도는 구매자 1건(출발) + 판매자 1건(판매 완료, 조건부) 이다.

### 1-3. 결제·배송을 마친 실배송 일반 구매 입찰 주문: 끝까지 실패한다

- 실패 위치는 `Xfr60CommandService.java:260` (`order.updateStatus(Xhq12Status.IN_TRANSIT)`) 이다.
- 이유: 주문이 `PREPARING` 인데 `Xhq12Status` 전이표에서 `PREPARING → IN_TRANSIT` 이 허용되지 않는다 (`D99/entity/Xhq12Status.java:26`).
- `Xhq12#updateStatus` 가 `Xxm16StatusException("상태 전환이 허용되지 않습니다: PREPARING -> IN_TRANSIT")` 를 던진다. `D99/entity/Xhq12.java:113-121`.
- 이 예외는 `Xzn53Exception` 이 아니므로 `catch (Xzn53Exception)` (293) 을 통과해 `catch (Exception)` (295-301) 에 걸린다. 여기서 `Xzn53Exception(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")` 로 감싸 다시 던진다.
- 무엇이 저장되나: 아무것도 저장되지 않는다.
  - `@Transactional` 메서드에서 `RuntimeException` 이 밖으로 나가므로 전체 롤백된다 (`Xfr60CommandService.java:238`).
  - Xfr60 의 courier/trackingNumber/`IN_TRANSIT` (256) 은 영속화 전에 롤백된다. DB 에서는 계속 `PENDING`, 송장 없음이다.
  - 주문은 `PREPARING` 그대로다.
  - 구매자 알림 생성 (266) 은 실패 지점(260) 뒤에 있어 실행되지 않는다. 판매 상태·입찰 상태 변경도 실행되지 않는다.
- 응답:
  - `Xkt44ExceptionHandler#handleGlobalException` 이 `ErrorResponse` 를 만든다 (`G/exception/Xkt44ExceptionHandler.java:44-58`).
  - HTTP 404, code `S001`, message "배송 정보를 찾을 수 없습니다.", path 는 요청 URI.
  - 코드·메시지·상태는 `D45/exception/Xzn53ErrorCode.java:12` 에서 온다. 상세 메시지(전이 불가 사유)는 응답 body 에 담기지 않고 로그에만 남는다.
  - 예외 클래스가 `RuntimeException` 을 상속한다는 점은 `G/exception/Xkt44Exception.java` 에서 확인했다.
- 이 실패를 우회하는 길이 있다.
  - `check-status` 계열은 주문 상태를 건드리지 않고 Xfr60 만 `IN_TRANSIT` 으로 만들어 커밋한다 (`Xfr60CommandService.java:473,477-498`).
  - 이때 조회 결과가 `IN_TRANSIT` 이면 `shipment.updateStatus(IN_TRANSIT)` 가 `IN_TRANSIT → IN_TRANSIT` 전이 불가(`D45/entity/Xzn53Status.java:21-24`)로 `IllegalStateException` 이 나, `EXTERNAL_TRACKING_SERVICE_ERROR` 로 감싸져 롤백된다 (495-497, 507-514).
  - 따라서 이 우회로는 `OUT_FOR_DELIVERY` 또는 `DELIVERED` 조회 결과에서만 의미가 있다.

## 2. 배송 완료 감지

### 2-1. 누가·언제·어떻게

- 스프링 `@Scheduled` + 스프링 배치 잡이다. `G/config/Xzn53BatchScheduler.java:34-44`.
  - 주기는 cron `0 0 */6 * * *`, 즉 매일 00·06·12·18시 정각, 6시간마다이다 (34).
  - `JobLauncher.run(updateShipmentStatusesJob, timestamp 파라미터)` 로 실행한다 (37-40). 예외는 `printStackTrace` 로만 처리한다 (41-43).
  - 스케줄링 활성화는 다른 도메인의 `@EnableScheduling` 설정에 의존한다. 예: `src/main/java/com/fream/back/domain/m84/config/Xzh65Configuration.java:37`.
- 잡은 이름 `"updateShipmentStatusesJob"` 로 주입된다 (`Xzn53BatchScheduler.java:19-21`).
  - `D45/config/Xpc23JobConfig.java:54-60`: Job 한 개에 Step 하나(`updateShipmentStatusesStep`)이다.

### 2-2. 대상 배송

- reader: `SELECT s FROM Xfr60 s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL`.
  - `D45/config/Xpc23JobConfig.java:87-97`. 페이지 크기·청크 크기 50 (51, 94).
- 구매자 배송(Xfr60, 테이블 `order_shipment`)만 대상이다. 판매자 배송 Xrg51 은 대상이 아니다.

### 2-3. 실제로 실행되는 처리 코드

- Step 은 `new Xcz52Processor(playwrightBrowserManager(), notificationService, orderService)` 를 processor 로 쓴다. `Xpc23JobConfig.java:66-81`.
  - 실제 처리 클래스는 `D45/config/Xcz52Processor.java:57-` 이다.
  - Playwright 브라우저(Xkh22)로 CJ대한통운 페이지(`https://trace.cjlogistics.com/next/tracking.html?wblNo=`, 28행)를 열고 (72-83), `tbody#statusDetail tr` 의 마지막 행 5번째 `td` 텍스트를 상태로 쓴다 (87,94,`parseStatusFromHtml` 의 64).
  - 브라우저는 `Xhd56Listener` 가 step 시작·종료 시 열고 닫는다 (`D45/config/Xhd56Listener.java:14-25`).
- 실행되지 않는 유사 코드:
  - `Xpc23JobConfig#shipmentItemProcessor` (104-177): `@Bean` 이지만 Step 에 연결되지 않는다. Step 은 위의 `new Xcz52Processor` 를 쓴다 (69).
  - `Xpc23JobConfig#parseCjLogisticsStatus` (186-220): private, 호출 없음.
  - `Xfr60CommandService#updateShipmentStatuses` (309-391): 호출하는 곳이 없다 (`grep` 결과 정의뿐). 이 메서드의 `DELIVERED` 처리 (350-367) 는 실행되지 않는다.
  - `Xfr60CommandService#updateAndCheckShipmentStatus` (452-516): `check-status` API 로 수동 호출될 때만 실행된다. `Xwg86` 의 Playwright 를 쓴다 (477).
  - 다른 도메인(m09, m31, m38, m70, m81)의 `*JobConfig`/`*Processor`/알림 서비스 복제본은 클래스명만 다르다. 정규화 diff 상 주입 클래스명만 다르고 로직은 동일하다.
    - 예: `src/main/java/com/fream/back/domain/m81/config/Xfr70JobConfig.java`.
    - 알림 서비스 복제본: m03 `Xtc38CommandService`, m77 `Xrw60CommandService` 등 (`notifyShipmentCompleted` 는 각각 219행).
  - 주의: 여섯 곳의 `@Bean updateShipmentStatusesJob` 은 이름이 같다. 스프링 부트 기본 설정(`allow-bean-definition-overriding` 설정 없음, `src/main/resources/*.yml`)이면 중복 정의 예외가 날 수 있다. 어느 쪽이 살아남든 동작은 같으므로 도메인 소유자인 m45 쪽(Xpc23JobConfig/Xcz52Processor)을 기준으로 답했다.

### 2-4. 택배사 상태 문자열 → 내부 상태

- `mapToShipmentStatus` (`Xcz52Processor.java:220-225`, 동일 코드가 `Xpc23JobConfig.java:228-234`, `Xfr60CommandService.java:399-405` 에도 있다).
  - `"배송완료"` → `DELIVERED`.
  - `"배송출발"` → `OUT_FOR_DELIVERY`.
  - 그 외 모든 문자열 → `IN_TRANSIT` (default).
- 텍스트가 비어 있거나 표 행이 없으면 `TRACKING_HTML_PARSE_ERROR` 예외를 던진다. `Xcz52Processor.java:166-190` 부근(`parseStatusFromHtml`).

## 3. 배송 완료 판정 이후 (`Xcz52Processor#process`, 108-117)

순서:
1. 조회 결과가 현재 상태와 같으면 아무 것도 하지 않고 반환한다 (101-105).
2. `DELIVERED` 이면 `orderShipment.updateStatus(DELIVERED)` (113). 이 변경은 청크 writer(`JpaItemWriter`)가 저장한다 (`Xpc23JobConfig.java:74,239-246`).
3. `orderService.completeOrder(orderId)` (116, 본체 `Xfr60CommandService.java:190-229`).
   - OrderBid 를 `findByOrderId` 로 찾는다 (196). 없으면 `IllegalArgumentException`.
   - 주문 Xhq12 를 `COMPLETED` 로 바꾼다 (204).
   - `updateSaleStatusToSold(orderId)` (208).
     - SaleBid 를 찾는다. 연결된 SaleBid 가 없으면 `Xzt63QueryService#findByOrderId` 가 `null` 이 아니라 `IllegalArgumentException` 을 던진다 (`src/main/java/com/fream/back/domain/m85/service/query/Xzt63QueryService.java:26-29`).
     - `sale.getStatus().canTransitionTo(SOLD)` 일 때만 Xpj42 를 `SOLD` 로 바꾸고 판매자 알림을 만든다 (119-138, 156-173).
     - 허용 상태는 `ON_AUCTION`, `SELLING` 뿐이다 (`m85/entity/Xpj42Status.java` 의 `canTransitionTo`).
   - 구매자에게 알림 "[completeOrder] 주문이 완료 처리되었습니다. 주문 ID: …" 를 만든다 (211-217).
4. `notificationService.notifyShipmentCompleted(order)` (117). 구매자에게 "[배송 완료] 상품이 배송 완료되었습니다. 주문 ID: …" 를 만든다. 내부 예외는 삼킨다. `src/main/java/com/fream/back/domain/m52/service/command/Xbp24CommandService.java:219-237`.
5. 반환 후 writer 가 Xfr60 을 저장한다.

알림 건수:
- 구매자: 2건 ("[completeOrder] 주문이 완료 처리되었습니다" + "[배송 완료]…"). 같은 사건에 중복 알림이다.
- 판매자: 이론상 1건이다 (Xpj42 가 `ON_AUCTION`/`SELLING` 일 때). 실제로는 보통 0건이다. 결제 때 이미 `SOLD` 로 바뀌기 때문이다 — `src/main/java/com/fream/back/domain/m64/service/command/Xjt45CommandService.java:404,419` 에서 `SOLD` 로 강제 대입, `Xpj42.updateStatus` 는 검사 없음 (`src/main/java/com/fream/back/domain/m85/entity/Xpj42.java:73-75`). 이미 `SOLD` 면 `SOLD → SOLD` 전이 불가로 건너뛴다.
- 합계: 구매자 2 + 판매자 0~1.

입찰 상태:
- 배치 경로(`completeOrder`)는 OrderBid(Xtw92), SaleBid(Xzt63) 의 status 를 건드리지 않는다. 둘 다 `MATCHED` 그대로다.
- `COMPLETED` 로 바꾸는 코드(`updateOrderAndSaleBidStatusToCompleted`)는 `updateTrackingInfo` 안에서만 호출된다 (`Xfr60CommandService.java:289`). 1-3 에서 보듯 이 호출은 실제로는 도달하지 못한다.
- `check-status` 경로(489 `completeOrder`)도 마찬가지로 입찰은 `MATCHED` 로 남는다.
- Xpj42 는 `SOLD` 로 바뀐다 (결제 단계에서 이미 `SOLD`).

## 4. 주문 종류별 차이

### (a) 결제·배송을 마친 실배송 일반 구매 입찰 주문: 끝까지 진행되지 않는다

- 주문 상태가 `PREPARING` 이다. `completeOrder` 의 204행 `order.updateStatus(COMPLETED)` 에서 `PREPARING → COMPLETED` 가 전이표에 없어 `Xxm16StatusException` 이 난다 (`D99/entity/Xhq12Status.java:26`).
- `completeOrder` 의 `catch (Exception)` 이 `Xzn53Exception(ORDER_NOT_FOUND_FOR_SHIPMENT)` 로 감싸 던진다 (221-228).
- 이 배송이 배치 대상이 되려면 먼저 `IN_TRANSIT` 이어야 한다. 그런데 `updateTrackingInfo` 는 1-3 대로 실패해 `IN_TRANSIT` 을 만들지 못한다. `check-status` 우회로만 가능하다.
- 우회로로 `IN_TRANSIT` 이 된 배송이 있다면 (주문은 `PREPARING`) 배치가 `DELIVERED` 를 감지해도 위 예외로 해당 건이 skip 된다.
- 결과: 배송 `IN_TRANSIT` 유지, 주문 `PREPARING` 유지, 입찰 `MATCHED` 유지, 알림 0건. 6시간마다 같은 실패가 반복된다.
- 추가로 연결된 SaleBid 가 없으면 `updateSaleStatusToSold` 에서도 `IllegalArgumentException` 이 난다 (`Xzt63QueryService.java:26-29`).

### (b) 즉시 구매로 만들어진 주문: 3의 처리가 끝까지 진행된다 (단, 송장 등록 경로는 다름)

- 생성 시 OrderBid(`MATCHED`, `isInstantPurchase`) 와 SaleBid(order 연결, `MATCHED`) 가 만들어진다. `D99/service/command/Xtw92CommandService.java:189-208` 부근(`createInstantOrderBid`), `Xhq12CommandService.java:279-280`.
- 주문 상태는 `PENDING_PAYMENT` 이다. `PENDING_PAYMENT → COMPLETED` 는 전이표에서 허용된다 (`D99/entity/Xhq12Status.java:24`).
- `updateTrackingInfo` 의 `IN_TRANSIT` 전이는 `PENDING_PAYMENT → IN_TRANSIT` 이라 허용되지 않아 (a) 와 똑같이 실패한다.
- `check-status` 로 Xfr60 이 `IN_TRANSIT` 이 된 뒤 배치가 `DELIVERED` 를 감지하면 `completeOrder` 가 성공한다.
  - 배송 `DELIVERED`, 주문 `COMPLETED`.
  - 구매자 알림 2건. 판매자 알림은 결제 시 이미 `SOLD` 라 0건.
  - 입찰 상태는 `MATCHED` 유지. Xpj42 는 `SOLD`.

### 차이 요약

| | (a) 일반 구매 입찰 (PREPARING) | (b) 즉시 구매 (PENDING_PAYMENT) |
|---|---|---|
| `completeOrder` 의 주문 `COMPLETED` 전이 | 불가, 예외 | 가능 |
| 결과 | skip, 배송 `IN_TRANSIT` 잔류 | 배송 `DELIVERED`, 주문 `COMPLETED`, 알림 2건 |
| 입찰 상태 | `MATCHED` 유지 | `MATCHED` 유지 |

## 5. 실패 처리 (주기 처리 중 한 건 실패)

- Step 은 fault-tolerant 이다. `skip(Exception.class)`, `skipLimit(50)`, `SkipListener` 등록. `Xpc23JobConfig.java:75-78` (SKIP_LIMIT 는 52행).
- 한 건의 processor 예외 (조회 실패, HTML 파싱 실패, 전이 불가, `completeOrder` 실패 등):
  - processor 가 예외를 `Xzn53Exception` 으로 감싸 다시 던진다 (`Xcz52Processor.java:133-148`).
  - 그 건은 skip 으로 기록된다. `shipmentSkipListener#onSkipInProcess` 가 shipmentId, 운송장, 상태, 사유를 `error` 로그로 남긴다 (`D45/config/Xpc23JobConfig.java:255-266`).
  - 스프링 배치 skip 의미상 청크 트랜잭션은 롤백된 뒤 나머지 건을 건별로 다시 처리한다. 이때 성공 건은 writer 가 저장하고, 실패 건은 저장되지 않는다. 롤백된 건의 알림·주문 상태 변경도 같은 트랜잭션이므로 함께 취소된다.
  - 나머지 건은 정상 처리된다. 실패 건은 상태가 `IN_TRANSIT`/`OUT_FOR_DELIVERY` 로 남아 다음 6시간 주기에 다시 대상이 된다 (reader 쿼리 95행).
- skip 이 50건을 넘으면 Step 이 실패하고 남은 건은 그 회차에 처리되지 않는다. Job 이 실패하면 스케줄러가 예외를 잡아 `printStackTrace` 만 한다 (`Xzn53BatchScheduler.java:41-43`).
- `notifyShipmentCompleted` 는 내부에서 예외를 삼키므로 알림 실패만으로 건이 실패하지는 않는다 (`Xbp24CommandService.java:230-236`).
- 참고: 같은 이름의 `Xfr60CommandService#updateShipmentStatuses` 는 건별 try/catch 로 실패 건을 세고 계속 진행하도록 짜여 있다 (322-388). 그러나 호출처가 없어 실제 주기 처리에는 쓰이지 않는다.
