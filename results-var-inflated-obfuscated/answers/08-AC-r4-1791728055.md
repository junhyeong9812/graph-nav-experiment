# 구매자 배송: 운송장 등록 → 배송 완료

표기: `F` = `src/main/java/com/fream/back/`, 클래스명은 난독화된 실제 이름이다.
- 주문 `Xhq12`(m99) · 구매자 배송 `Xfr60`(m45, 테이블 order_shipment) · 주문 입찰 `Xtw92`(m99) · 판매 입찰 `Xzt63`(m85) · 판매 `Xpj42`(m85)
- 구매자 배송 상태 `Xzn53Status`, 주문 상태 `Xhq12Status`, 입찰 상태 `Xkh73Status`(PENDING/MATCHED/CANCELLED/COMPLETED)

## 0. 전제: 결제·배송 처리 후 주문과 배송의 상태

1. `POST /orders/{orderId}/process-payment-shipment`는 Kafka 이벤트만 발행하고 202를 돌려준다. (`F domain/m99/controller/command/Xhq12CommandController.java:42,54,68`)
2. 실제 처리는 컨슈머 `Xhq12EventConsumer#processCompleteOrder`가 한다. (`F domain/m99/service/kafka/Xhq12EventConsumer.java:166-224`)
   - 결제 처리 (:171)
   - 배송 `Xfr60`을 `PENDING`으로 생성 (:181, 생성 지점 `F domain/m45/service/command/Xfr60CommandService.java:61-68`)
   - 주문 `PENDING_PAYMENT → PAYMENT_COMPLETED` (:195)
   - 창고 보관이 아니면 `PREPARING`에서 멈춘다 (:216-218).
3. 컨슈머는 주문 입찰 `Xtw92`를 MATCHED로 바꾸지 않는다. 일반 구매 입찰은 생성 시 `PENDING`(`F domain/m99/service/command/Xtw92CommandService.java:95`)이고 그대로 남는다. MATCHED로 바꾸는 코드는 `Xhq12CommandService#processPaymentAndShipment`(`F domain/m99/service/command/Xhq12CommandService.java:187-190`)에 있지만, 호출하는 곳이 없다. 컨트롤러는 이벤트 프로듀서만 쓴다.
4. 일반 주문 입찰에는 판매 `Xpj42`도, 판매 입찰 `Xzt63`도 연결되어 있지 않다.
5. 결과적으로 (a) 실배송 일반 구매 입찰 주문은 `Xhq12=PREPARING`, `Xfr60=PENDING`, `Xtw92=PENDING` 상태다.

## 1. 운송장 등록 요청

### 1-1. 어느 API로 들어오나

`PATCH /shipments/order/{shipmentId}/status` (바디 courier, trackingNumber) → `Xfr60CommandController#updateTrackingInfo` → `Xfr60CommandService#updateTrackingInfo`.
- 컨트롤러: `F domain/m45/controller/command/Xfr60CommandController.java:20,33-45`
- 서비스: `F domain/m45/service/command/Xfr60CommandService.java:238-303`

같은 서비스를 부르는 URL 별칭이 다른 도메인 컨트롤러에 복제되어 있다.
- 경로: `/admin/shipments/order`(m09 `Xqh36CommandController.java:20`), `/settlement/...`(m81 `Xsd74CommandController.java:20`), `/internal/...`(m38 `Xdn57CommandController.java:20`), `/partner/...`(m31 `Xzm66CommandController.java:20`), `/legacy/...`(m70 `Xcx47CommandController.java:20`)
- 모두 `Xfr60CommandService`를 호출하며 로직은 같다.

참고: `POST /shipments/order/{shipmentId}/check-status`(`Xfr60CommandController.java:58`)도 운송장을 등록한다. 이쪽은 주문 상태를 바꾸지 않는다(1-4, 4절 참고).

### 1-2. 코드가 의도한 상태 변경 순서 (`Xfr60CommandService#updateTrackingInfo`)

1. 택배사·운송장이 비어 있으면 `TRACKING_INFO_REQUIRED` 예외 (:243-246).
2. 배송 `Xfr60`: courier·trackingNumber 저장, 상태 `IN_TRANSIT`. 전이 검증 없이 대입한다. (:256, `F domain/m45/entity/Xfr60.java:41-45`)
3. 주문 `Xhq12`: `IN_TRANSIT`으로 변경 (:260).
4. 구매자에게 알림 1건: "상품이 출발하였습니다. 주문 ID: …" (:265-271).
5. `updateSaleStatusToSold(orderId)` (:276, 본문 :111-183)
   - 연결된 판매 `Xpj42`가 SOLD로 전이 가능하면 SOLD로 바꾼다.
   - 창고 보관 판매면 창고 상태도 SOLD로 바꾼다.
   - 판매자에게 알림 1건: "상품이 성공적으로 판매 완료되었습니다…"
6. 판매가 창고 보관이면 창고 상태를 다시 갱신 (:279-286).
7. `updateOrderAndSaleBidStatusToCompleted` (:289, 본문 :411-440)
   - 주문 입찰 `Xtw92`: MATCHED이면 COMPLETED.
   - 판매 입찰 `Xzt63`: MATCHED이면 COMPLETED.
   - 이 메서드는 내부 예외를 삼킨다.

즉 코드의 의도는 "운송장 등록 시점에 주문 IN_TRANSIT, 판매 SOLD, 입찰 COMPLETED"까지 한 번에 처리하는 것이다. 배송 완료 시점이 아니다. 알림 대상은 구매자 1건과 판매자 1건이다.

### 1-3. (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문: 끝까지 성공하지 못한다

- **실패 지점**: `Xfr60CommandService.java:260`의 `order.updateStatus(Xhq12Status.IN_TRANSIT)`.
  - `Xhq12#updateStatus`는 전이 불가면 `Xxm16StatusException("상태 전환이 허용되지 않습니다: PREPARING -> IN_TRANSIT")`을 던진다. (`F domain/m99/entity/Xhq12.java:113-120`)
- **이유**: 허용 전이표에서 `PREPARING → {IN_WAREHOUSE, SHIPMENT_STARTED}`뿐이고 `IN_TRANSIT`은 `SHIPMENT_STARTED`에서만 갈 수 있다. (`F domain/m99/entity/Xhq12Status.java:26,28`)
  - `SHIPMENT_STARTED`로 바꾸는 코드는 어디에도 없다. 열거형 정의와 라벨 문자열에만 나온다.
  - 그래서 정상 흐름의 주문은 이 API로 IN_TRANSIT이 될 수 없다.
- **예외 변환**: `Xxm16StatusException`은 `Xzn53Exception`이 아니므로 `catch (Exception e)`(:295)에 걸려 `Xzn53Exception(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")`으로 감싸져 던져진다. (:295-301)
- **저장되는 것**: 없다.
  - `@Transactional`(:238) 메서드가 RuntimeException으로 끝나므로 롤백된다.
  - 배송에 대입한 courier·tracking·IN_TRANSIT(:256)도 저장되지 않는다. 배송은 `PENDING`, 운송장 `null` 그대로다.
  - 알림(:266)과 판매·입찰 변경(:276 이후)은 실패 지점 뒤라 실행되지 않는다.
- **응답**: 글로벌 핸들러가 `Xkt44Exception`을 받아 `errorCode.getStatus()` 그대로 응답한다. (`F global/exception/Xkt44ExceptionHandler.java:49-62`)
  - **HTTP 404**, ErrorResponse 코드 `S001`, 메시지는 코드 기본 문구 "배송 정보를 찾을 수 없습니다." (`F domain/m45/exception/Xzn53ErrorCode.java:12`)
  - 실제 사유(상태 전환 불가)는 응답 메시지에 노출되지 않고 로그에만 남는다.
  - 오류 코드 이름(SHIPMENT_NOT_FOUND)과 실제 원인이 다르다.
- 이 경우 `updateSaleStatusToSold`에 도달하더라도 `Xzt63QueryService#findByOrderId`가 null이 아니라 `IllegalArgumentException`을 던진다. (`F domain/m85/service/query/Xzt63QueryService.java:26-29`) 일반 주문은 판매 입찰이 없으므로 이쪽으로도 성공하지 못한다.

### 1-4. (참고) check-status API (`updateAndCheckShipmentStatus`, `Xfr60CommandService.java:451-516`)

- 같은 요청에서 `shipment.updateTrackingInfo`(:473)로 운송장을 저장하고 `IN_TRANSIT`(`Xfr60.java:44`)으로 만든다. 이어서 Playwright로 택배사를 조회해 상태를 매핑한다 (:477-478).
- 주문 상태는 건드리지 않는다. 따라서 일반 주문도 여기서는 배송 `IN_TRANSIT`으로 저장된다.
- 이것이 아래 2절 배치의 조회 대상(IN_TRANSIT + 운송장 있음)이 생기는 실질적인 경로다.
- 조회 결과가 DELIVERED면 같은 트랜잭션에서 `completeOrder`를 호출한다 (:489). 이때 주문이 PREPARING이면 4절처럼 예외가 나고 전체가 롤백된다.

## 2. 배송 완료 감지

### 2-1. 누가, 언제, 어떻게

- **누가**: 스케줄러 `Xzn53BatchScheduler#scheduleShipmentStatusJob`이 Spring Batch 잡 `updateShipmentStatusesJob`을 실행한다. (`F global/config/Xzn53BatchScheduler.java:19-21,34-40`)
- **주기**: `@Scheduled(cron = "0 0 */6 * * *")`, 즉 6시간마다 매 정각(00·06·12·18시). (:34)
- **방식**: 잡은 청크 크기 50, 스킵 제한 50, fault-tolerant 스텝이다. 리더 → `Xcz52Processor` → `JpaItemWriter` 순이다. (`F domain/m45/config/Xpc23JobConfig.java:51-52,66-81`)
- **조회 대상**: 상태가 `IN_TRANSIT` 또는 `OUT_FOR_DELIVERY`이고 운송장 번호가 NULL이 아닌 `Xfr60`. (`Xpc23JobConfig.java:95`)
- **택배사 조회**: Playwright로 CJ대한통운 추적 페이지 `https://trace.cjlogistics.com/next/tracking.html?wblNo=<운송장>`를 열고, 상태 테이블 마지막 행의 5번째 `td` 텍스트를 trim해서 쓴다. (`F domain/m45/config/Xcz52Processor.java:57,181`)

### 2-2. 실제로 실행되는 처리 코드

- **배치 스텝의 프로세서는 `new Xcz52Processor(...)`다.** (`Xpc23JobConfig.java:69-73`, 클래스 `Xcz52Processor.java:57-117`)
- 같은 설정 클래스의 `shipmentItemProcessor()` 빈(:104-177)과 `Xfr60CommandService#updateShipmentStatuses`(:308-391)는 실행되지 않는다.
  - `shipmentItemProcessor()` 빈은 스텝에 연결되어 있지 않다.
  - `updateShipmentStatuses`는 호출하는 곳이 없다. 이 메서드는 배송을 DELIVERED로 바꾸고 `completeOrder` 없이 주문을 직접 COMPLETED로 만들며, 구매자 알림도 1건만 보내는 다른 로직이다.
- `Xpc23JobConfig#parseCjLogisticsStatus`(:186)도 미사용이다.
- **복제본**: 같은 이름 `updateShipmentStatusesJob` 빈이 m09 `Xxt33JobConfig`, m31 `Xkd78JobConfig`, m38 `Xrx68JobConfig`, m70 `Xkq49JobConfig`, m81 `Xfr70JobConfig`에도 있다. 이들의 프로세서도 로직이 동일하다. 알림 서비스만 m52 `Xbp24CommandService`의 복사본(m03, m77, m79, m101, m102)을 쓰고, 모두 `Xfr60CommandService#completeOrder`를 부른다.
  - 코드상 동작은 어느 쪽이 선택되어도 동일하다.
  - `application*.yml`·Java 어디에도 `allow-bean-definition-overriding` 설정이 없다. Boot 3.4.1 기본값에서는 같은 이름 빈 충돌로 기동이 실패할 수 있다. 이 부분은 실행해서 확인하지 못했다.
  - 이 답변은 m45 구현(`Xpc23JobConfig` + `Xcz52Processor`)을 실행되는 쪽으로 본다.

### 2-3. 택배사 상태 문자열 → 내부 상태

`Xcz52Processor#mapToShipmentStatus` (`Xcz52Processor.java:220-226`)

| 택배사 문자열 | 내부 상태 |
|---|---|
| `"배송완료"` | `DELIVERED` |
| `"배송출발"` | `OUT_FOR_DELIVERY` |
| 그 외 모든 문자열 | `IN_TRANSIT` |

- 정확히 일치(equals)만 인정한다. "배송완료" 외의 표기(예: "배달완료")는 모두 IN_TRANSIT이 된다.
- 현재 상태와 같으면 변경 없이 반환한다 (:99-103).
- 현재가 `OUT_FOR_DELIVERY`인데 기타 문자열이 와서 `IN_TRANSIT`으로 매핑되면, `Xzn53Status`에서 `OUT_FOR_DELIVERY → IN_TRANSIT`이 불가하다 (`F domain/m45/entity/Xzn53Status.java:23-28`). `Xfr60#updateStatus`가 `IllegalStateException`을 던져 그 건은 스킵된다 (`Xfr60.java:47-55`).

## 3. 배송 완료 판정 이후 (`Xcz52Processor` DELIVERED 분기)

### 3-1. 상태 변경 순서 (`Xcz52Processor.java:108-118`)

1. 배송 `Xfr60`: `IN_TRANSIT/OUT_FOR_DELIVERY → DELIVERED` (:113). 인메모리 변경이며 writer가 청크 커밋 때 저장한다.
2. `Xfr60CommandService#completeOrder(orderId)` (:116, 본문 `Xfr60CommandService.java:190-229`)
   1. 주문 입찰을 `findByOrderId`로 조회해 주문을 얻는다 (:196-199).
   2. 주문 `Xhq12`를 `COMPLETED`로 변경 (:204). 허용 전이는 PENDING_PAYMENT, IN_WAREHOUSE, IN_TRANSIT에서만 가능하다 (`Xhq12Status.java:24,27,29`).
   3. `updateSaleStatusToSold` (:208)
      - 판매 입찰 → 판매 `Xpj42`를 SOLD로 변경한다. 이미 SOLD면 전이 불가라 건너뛴다 (:116-147).
      - 이어서 주문 입찰의 `sale`도 같은 방식으로 SOLD로 변경한다 (:150-180).
      - 창고 보관이면 창고 상태를 갱신한다 (:126-129).
      - 전이될 때마다 판매자에게 알림 1건을 보낸다 (:133-138, :164-169).
   4. 구매자에게 알림 1건: "[completeOrder] 주문이 완료 처리되었습니다…" (:211-217).
3. `Xbp24CommandService#notifyShipmentCompleted(order)` (`Xcz52Processor.java:117`) → 구매자에게 알림 1건 "[배송 완료] 상품이 배송 완료되었습니다…" (`F domain/m52/service/command/Xbp24CommandService.java:219-234`). 이 메서드는 내부 예외를 삼킨다.

### 3-2. 알림

- **구매자**: 2건 — "[completeOrder] 주문이 완료 처리되었습니다"(`Xfr60CommandService.java:211-217`)와 "[배송 완료] …"(`Xbp24CommandService.java:219-234`).
- **판매자**: 판매(`Xpj42`)가 이번에 SOLD로 전이될 때만 1건. 이미 SOLD였으면 0건이다.
- 둘 다 `SHOPPING / BID` 유형으로 DB 저장과 WebSocket 전송이 이뤄진다.

### 3-3. 주문 입찰·판매 입찰 상태

- 배치 경로(`completeOrder`)는 입찰 상태를 COMPLETED로 바꾸지 않는다. 입찰 COMPLETED 처리는 `updateOrderAndSaleBidStatusToCompleted`(:411)에만 있고, 이 메서드는 `updateTrackingInfo`(:289)에서만 호출된다. 1-3에서 본 대로 정상 흐름에서는 그곳에 도달하지 못한다.
- 따라서 배송 완료 후에도 입찰 상태는 변하지 않는다. 즉시 구매 입찰은 `MATCHED` 그대로이고, 일반 입찰은 `PENDING` 그대로다.

## 4. 주문 종류별 차이

두 경우 모두 배송이 IN_TRANSIT이 되려면 check-status API(1-4)를 거쳐야 한다(`updateTrackingInfo`는 두 경우 모두 1-3과 같은 이유로 실패한다). 그 상태에서 배치가 DELIVERED를 감지한다고 가정한다.

### (a) 실배송 일반 구매 입찰 주문 → 끝까지 진행되지 않는다

- 주문이 `PREPARING`이므로 `completeOrder`의 `order.updateStatus(COMPLETED)`(`Xfr60CommandService.java:204`)에서 `Xxm16StatusException`이 난다. (`PREPARING`은 COMPLETED로 갈 수 없다. `Xhq12Status.java:26`)
- 설령 통과해도 `updateSaleStatusToSold`의 `saleBidQueryService.findByOrderId`(:116)가 `IllegalArgumentException`을 던진다. (일반 주문에는 판매 입찰이 없고 이 메서드는 null이 아닌 예외를 던진다. `Xzt63QueryService.java:26-29`)
- 예외는 `completeOrder`의 catch(:221-228)에서 `Xzn53Exception(ORDER_NOT_FOUND_FOR_SHIPMENT)`으로 바뀌어 던져지고, 프로세서에서도 그대로 다시 던져진다 (`Xcz52Processor.java:134-141`).
- **결과**: 배치에서는 그 건이 스킵된다 (아래 5절).
  - 주문은 `PREPARING`, 배송은 `IN_TRANSIT`, 입찰은 `PENDING` 그대로다.
  - 알림은 0건이다.
  - 다음 6시간 주기에 다시 조회하고 다시 같은 이유로 실패한다.
- check-status API로 DELIVERED가 확인된 경우에도 `completeOrder`에서 예외가 나서 요청 전체가 롤백된다. 응답은 `Xzn53Exception`의 상태 코드(`ORDER_NOT_FOUND_FOR_SHIPMENT`, 404) 그대로다. (`Xfr60CommandController.java:80-86`)

### (b) 즉시 구매로 만들어진 주문 → 끝까지 진행된다

- 즉시 구매 주문은 생성 시 `PENDING_PAYMENT`이고 배송 `Xfr60`은 `PENDING`이다. (`Xhq12CommandService.java:241-245,264-271`)
  - `Xzt63`이 주문과 연결되어 MATCHED (:279-280).
  - 주문 입찰 `Xtw92`는 MATCHED + `isInstantPurchase`, `sale` 연결 (`Xtw92CommandService.java:189-206`).
  - 결제 서비스는 주문 상태를 바꾸지 않는다.
- 결제 처리 중 `Xjt45CommandService#notifyUsersAndUpdateSaleStatus`가 이미 판매를 SOLD로 바꾼다. (`F domain/m64/service/command/Xjt45CommandService.java:83,383-405`)
  - 주문 입찰은 결제 시점에 아직 생성 전이라(`Xtw92CommandService.java:133` → `:142`) `order.getOrderBid()==null` 경로로 들어가 판매 입찰에서 판매를 찾아 `sale.updateStatus(SOLD)`를 호출한다 (:404). 이 `updateStatus`에는 전이 검증이 없다. (`F domain/m85/entity/Xpj42.java:73-75`)
  - 이때 구매자 "결제가 완료되었습니다", 판매자 "구매자가 결제를 완료하였습니다" 알림이 나간다 (배송 완료와 별개의 시점).
- 배송 완료 판정 후 `completeOrder`:
  - 주문 `PENDING_PAYMENT → COMPLETED`는 허용 전이다 (`Xhq12Status.java:24`). 주문 입찰도 판매 입찰도 존재한다.
  - 판매는 이미 SOLD라 `canTransitionTo(SOLD)`가 false → 두 블록 모두 건너뛰고 판매자 알림은 0건이다 (`Xfr60CommandService.java:119,156`).
  - 구매자 알림은 2건이다 (3-2).
  - 주문 입찰·판매 입찰은 `MATCHED` 그대로다 (3-3).
- 배송 `DELIVERED`, 주문 `COMPLETED`가 청크 커밋 때 저장된다.

## 5. 실패 처리 (주기 처리 중 한 건 실패)

- 프로세서는 모든 예외를 `Xzn53Exception`으로 바꿔 던진다. (`Xcz52Processor.java:134-141`)
- 스텝이 `.faultTolerant().skip(Exception.class).skipLimit(50)`이다. (`Xpc23JobConfig.java:75-77`)
  - 실패한 건은 스킵된다. 스킵 사실은 `SkipListener#onSkipInProcess`가 로그만 남기고 (:255-262) 별도 저장·알림은 없다.
  - 스킵한 건의 DB 변경(배송 DELIVERED, 주문 COMPLETED, 알림 등)은 청크 트랜잭션이 롤백되어 반영되지 않는다. 그 건은 IN_TRANSIT/OUT_FOR_DELIVERY 그대로 남아 다음 주기에 다시 조회된다.
  - 나머지 건은 중단되지 않는다. 스킵 처리 시 청크(최대 50건)가 롤백된 뒤 남은 항목이 건별로 다시 처리되고 정상 건은 커밋된다. (Spring Batch fault-tolerant 스텝의 표준 동작이며 코드에 별도 구현은 없다.)
  - 스킵이 50건을 넘으면 잡 자체가 실패한다.
- 스케줄러는 `jobLauncher.run`의 예외를 `printStackTrace`로만 처리한다. (`Xzn53BatchScheduler.java:41-43`) 재시도나 알림이 없고 다음 6시간 주기에 다시 실행된다.
- 운송장 번호가 없거나 비어 있으면 `TRACKING_NUMBER_INVALID`로 그 건만 스킵된다. 단, 리더 쿼리가 이미 `trackingNumber IS NOT NULL`로 거르므로 빈 문자열만 해당한다. (`Xcz52Processor.java:60-63`)
- (미사용 코드) `updateShipmentStatuses`는 건별 try/catch로 실패 건만 건너뛰고 다음으로 진행하는 구조(:322-388)지만 호출되지 않는다.
