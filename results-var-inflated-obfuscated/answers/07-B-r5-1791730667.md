# 즉시 구매 처리 흐름

경로 접두어: `D = src/main/java/com/fream/back/domain`.
엔티티 이름은 난독화되어 있다. 이 문서에서는 다음처럼 부른다.

| 코드 이름 | 문서에서의 이름 |
|---|---|
| `Xhq12` | 주문(Order) |
| `Xtw92` | 주문 입찰(OrderBid) |
| `Xzt63` | 판매 입찰(SaleBid) |
| `Xpj42` | 판매(Sale) |
| `Xjt45` | 결제(Payment) |
| `Xms75` | 창고 보관(WarehouseStorage) |
| `Xfr60` | 주문 배송(OrderShipment) |

실제 즉시 구매 API는 `/order-bids/instant` 하나다. `/legacy/*`, `/internal/*`, `/settlement/*` 등에 같은 모양의 복제본이 있으나 접두어 없는 `/order-bids` 컨트롤러가 기준이다.

## 1. 진입 API · 처리 단계 · 동기/비동기 · 응답 ID

- **API**: `POST /order-bids/instant`. 요청 본문은 `Xcr44RequestDto`이며 `saleBidId`, `addressId`, `warehouseStorage`, `paymentRequest`를 가진다.
  - 근거: `D/m99/controller/command/Xtw92CommandController.java:22`, `:89-90`, `D/m99/dto/Xcr44RequestDto.java`
- **처리 단계**
  1. 컨트롤러가 로그인 이메일을 추출하고 결제 요청에 `userEmail`을 넣고 `orderId=null`로 초기화한다.
     - 근거: `Xtw92CommandController.java:92`, `:98`, `:119-123`
  2. `Xtw92CommandService.createInstantOrderBid`가 입력을 검증하고, 구매자와 판매 입찰을 조회해 `sale`을 꺼낸다.
     - 근거: `D/m99/service/command/Xtw92CommandService.java:123-130`, `:172-184`
  3. `Xhq12CommandService.createInstantOrder`가 주문을 만든다.
     - 근거: `Xtw92CommandService.java:133-139`
     - 이 안에서 다음이 순서대로 일어난다.
       - 주소 조회: `D/m99/service/command/Xhq12CommandService.java:238`
       - 주문 저장: `:241-247`
       - 주문 항목 생성: `:255`
       - 배송 정보 생성: `:264-271`
       - 판매 입찰 매칭: `:279-283`
       - 판매자 창고 보관 상태 변경: `:291-293`
       - 결제 처리: `:305`
  4. 결제 처리 안에서 결제 엔티티 생성, 알림 발송, 판매 상태 변경이 이루어진다.
     - 근거: `D/m64/service/command/Xjt45CommandService.java:57-88`
  5. 마지막으로 주문 입찰(OrderBid)이 `MATCHED`로 새로 만들어져 저장된다.
     - 근거: `Xtw92CommandService.java:142`, `:189-207`
- **동기**: 전부 하나의 HTTP 요청 안에서 동기로 처리된다.
  - `createInstantOrderBid`는 `@Transactional`이며 하위 서비스도 같은 트랜잭션에 참여한다.
    - 근거: `Xtw92CommandService.java:118`, `Xhq12CommandService.java:219`, `Xjt45CommandService.java:37`
  - 카드 결제는 PortOne REST를 `RestTemplate`으로 동기 호출한다. 근거: `D/m64/p02/Xhs91ApiClient.java:266`
  - 이 경로에서는 Kafka 이벤트를 발행하지 않는다.
    - `Xhq12EventProducer`는 `/orders/{id}/process-payment-shipment` 컨트롤러와 이벤트 컨슈머에서만 쓰인다.
    - 근거: `D/m99/controller/command/Xhq12CommandController.java:30`, `:42`
- **응답 ID**: 주문 ID가 아니라 **새로 만들어진 주문 입찰(OrderBid)의 ID**다.
  - 컨트롤러 변수명은 `orderId`이고 메시지도 "즉시 구매가…"이지만, 값은 `createInstantOrderBid(...).getId()`다.
  - 이 메서드의 반환 타입은 `Xtw92`(주문 입찰)다.
  - 근거: `Xtw92CommandController.java:101-109`, `Xtw92CommandService.java:119`, `:142-144`

## 2. 새로 생기는 엔티티와 상태 변화 순서

각 단계 직후의 상태 값이다. 전부 같은 트랜잭션이며 중간 상태는 커밋되지 않는다.

| # | 단계 | 새 엔티티 / 변경 | 직후 상태 | 근거 |
|---|---|---|---|---|
| 1 | 주문 저장 | **주문** 생성. `totalAmount` = 판매 입찰 `bidPrice` | 주문 `PENDING_PAYMENT` | `Xhq12CommandService.java:241-247` |
| 2 | 주문 항목 | **주문 항목** 생성(수량 1, 가격 = `bidPrice`) | 변화 없음 | `Xhq12CommandService.java:255-256`, `D/m99/service/command/Xnd96CommandService.java:45-52` |
| 3 | 배송 정보 | **주문 배송** 생성. 배송지 ID로 조회한 주소 사용 | 배송 `PENDING` | `Xhq12CommandService.java:264-271`, `D/m45/service/command/Xfr60CommandService.java:61-68` |
| 4 | 판매 입찰 매칭 | 판매 입찰에 주문 연결. `assignOrder`가 이미 `MATCHED`로 바꾸고 `updateStatus(MATCHED)`를 한 번 더 호출한 뒤 flush | 판매 입찰 `PENDING`(기본값) → `MATCHED` | `Xhq12CommandService.java:279-283`, `D/m85/entity/Xzt63.java:35-37`, `:58-61` |
| 5 | 판매자 창고 | 판매가 `isWarehouseStorage`이면 판매자의 창고 보관 상태를 변경 | 창고 보관 `ASSOCIATED_WITH_ORDER` | `Xhq12CommandService.java:291-293`, `D/m63/service/command/Xms75CommandService.java:117-133` |
| 6 | 결제 | **결제** 생성 (결제 수단별 상태는 3번 참조) | 카드 `PENDING` 또는 `PAID`, 계좌 `PENDING`, 일반 `PAID`. 주문 상태는 그대로 `PENDING_PAYMENT` | `Xjt45CommandService.java:67-80` |
| 7 | 알림 + 판매 상태 | 알림 2건 생성, 판매 상태 변경 | 판매 `SOLD` (전이 검증 없이 직접 대입) | `Xjt45CommandService.java:403-406`, `D/m85/entity/Xpj42.java:73-75` |
| 8 | 주문 입찰 | **주문 입찰** 생성. 주문·판매 연결, `isInstantPurchase=true` | 주문 입찰 `MATCHED` | `Xtw92CommandService.java:192-206`, `D/m99/entity/Xtw92.java:60-82`, `:97-99` |

- 6번 시점에 `order.getOrderBid()`는 아직 `null`이다. 주문 입찰은 8번에서 생성되기 때문이다. 그래서 알림·판매 상태 변경은 `saleBidQueryService.findByOrderId(order.getId())` 경로를 탄다. 4번에서 flush했기 때문에 조회가 가능하다.
  - 근거: `Xjt45CommandService.java:388-407`, `Xhq12CommandService.java:283`
- 주문 상태를 `PAYMENT_COMPLETED`로 바꾸는 코드는 이 경로에 없다.
  - 그런 코드는 `/orders/{id}/process-payment-shipment`(`Xhq12CommandService.java:112-184`)와 Kafka 컨슈머(`D/m99/service/kafka/Xhq12EventConsumer.java:192-217`)에만 있다.
- 판매 입찰이 이미 `MATCHED`인지, 금액이 판매가와 일치하는지는 검사하지 않는다. 결제 금액도 클라이언트가 보낸 `paidAmount`를 그대로 쓰며 `> 0`만 확인한다.
  - 근거: `Xtw92CommandService.java:172-184`, `Xjt45CommandService.java:142-145`

## 3. 결제 수단별 결과

결제 수단은 `paymentType` 값(CARD/ACCOUNT/GENERAL)으로 하위 DTO가 결정된다. 근거: `D/m64/dto/Xjt45RequestDto.java:20-25`, `D/m64/service/command/Xjt45CommandService.java:67-80`.

| 수단 | 처리 | 결제 상태 | 근거 |
|---|---|---|---|
| **CARD** | 저장된 결제 정보로 PortOne 단건 결제를 동기 호출. 응답의 `status`가 문자열 `"success"`일 때만 `PAID`와 `isSuccess=true`로 바꾼다. 아니면 기본값 `PENDING`인 채로 저장하고 예외도 던지지 않는다. | `PAID` 또는 `PENDING` | `Xjt45CommandService.java:166-208`, `D/m64/entity/Xjt45.java:44` |
| **ACCOUNT** | 은행명만 검증한다. 외부 호출은 없다. 입금 확인 없이 `PENDING`으로 저장한다. | `PENDING` | `Xjt45CommandService.java:236-262`, `:470-488` |
| **GENERAL** | 클라이언트가 보낸 `impUid`가 비어 있지 않으면 검증 없이 즉시 `PAID`, `isSuccess=true`로 저장한다. PG 확인 호출은 없다. | `PAID` | `Xjt45CommandService.java:297-316` |

- **즉시 구매는 끝까지 성공한다.** 결제 상태가 `PENDING`이어도 위 2번의 7~8단계가 실행된다.
  - 계좌이체, 그리고 응답 `status != "success"`인 카드는 결제가 `PENDING`인 채로 판매가 `SOLD`가 되고 구매자와 판매자에게 알림이 간다.
  - 알림 문구도 "결제가 완료되었습니다"다.
  - `notifyUsersAndUpdateSaleStatus`는 결제 상태를 확인하지 않는다.
  - 근거: `Xjt45CommandService.java:83`, `:383-426`
- **카드 결제를 PortOne이 실패로 응답하면**
  1. HTTP 상태가 200이 아니거나 `code != 0`이면 `Xtc14Exception("카드 결제 요청 실패: …")`을 던진다.
     - 근거: `D/m64/p02/Xhs91ApiClient.java:270-274`
  2. 이 예외는 `Xjt45Exception` 계열이라 `createCardPayment`와 `processPayment`가 그대로 재던진다. 결제 레코드는 저장되지 않는다.
     - 근거: `D/m64/exception/Xtc14Exception.java:6`, `Xjt45CommandService.java:180-181`, `:218-219`, `:89-94`
  3. `createInstantOrder`가 이를 `Xwf42Exception`(`Xhq12Exception` 계열)으로 감싸 던진다.
     - 근거: `Xhq12CommandService.java:305-313`, `D/m99/exception/Xwf42Exception.java:6`
  4. `createInstantOrderBid`는 `Xhq12Exception`이므로 그대로 다시 던진다.
     - 근거: `Xtw92CommandService.java:145-147`, `:212-214`
  5. 컨트롤러에는 catch가 없어 전역 `@ExceptionHandler(Xkt44Exception.class)`가 오류 응답을 만든다.
     - 근거: `D/../global/exception/Xkt44ExceptionHandler.java:49`
  6. 트랜잭션이 롤백된다. 주문, 주문 항목, 배송, 판매 입찰 `MATCHED`, 창고 상태 변경이 모두 취소된다.
  7. 알림과 판매 `SOLD` 변경은 결제 이후 단계라 일어나지 않는다. 주문 입찰도 만들어지지 않는다.
- 결제 이후의 `notifyUsersAndUpdateSaleStatus`는 내부에서 모든 예외를 삼킨다. 그 단계의 오류는 요청을 실패시키지 않는다.
  - 근거: `Xjt45CommandService.java:421-425`, `:457-461`

## 4. 알림

- **수신자와 내용**: 구매자와 판매자 각 1건이다. 카테고리는 `SHOPPING`, 타입은 `BID`다.
  - 구매자(`order.getUser()`): "결제가 완료되었습니다. 주문 ID: {주문ID}"
  - 판매자(`sale.getSeller()`): "구매자가 결제를 완료하였습니다. 판매 ID: {판매ID}"
  - 근거: `Xjt45CommandService.java:434-456`
- **시점**: 결제 엔티티를 저장한 직후, 판매를 `SOLD`로 바꾸기 직전이다. 같은 요청과 같은 트랜잭션 안이며 커밋 전이다.
  - 근거: `Xjt45CommandService.java:83`, `:403-404`
- **방식**
  - 알림은 DB에 동기로 저장된다. 근거: `D/m52/service/command/Xbp24CommandService.java:44-54`
  - 이어서 실시간 푸시를 시도한다. Redis에 사용자의 WebSocket 연결 키(`WebSocket:Xjm45:{email}`)가 있을 때만 `/queue/notifications`로 STOMP 전송한다. 키가 없으면 저장만 한다.
    - 근거: `Xbp24CommandService.java:37-38`, `:57`, `:303-322`
  - Kafka나 비동기 큐는 쓰지 않는다.
  - 전송 실패는 경고 로그만 남기고 무시한다. 근거: `Xbp24CommandService.java:315-319`, `Xjt45CommandService.java:457-461`
- 결제 실패로 롤백되는 경우 알림은 생성되지 않는다(3번 참조).

## 5. 최종 주문 상태 · 창고 보관 선택

- **주문의 최종 상태는 `PENDING_PAYMENT`다.**
  - 주문은 `PENDING_PAYMENT`로 만들어진다(`Xhq12CommandService.java:241-245`).
  - 이후 이 경로에서 주문 상태를 바꾸는 코드는 없다.
  - 결제가 `PAID`여도 주문은 `PAYMENT_COMPLETED`로 넘어가지 않는다.
  - 응답 메시지는 "즉시 구매가 성공적으로 처리되었습니다"이지만 주문은 결제 대기 상태로 남는다.
  - 주문과 함께 만들어진 주문 입찰은 `MATCHED`, 판매 입찰은 `MATCHED`, 판매는 `SOLD`다.
  - 근거: `Xtw92CommandService.java:196`, `Xhq12CommandService.java:280`, `Xjt45CommandService.java:404`
- **구매자가 "창고 보관"을 선택해도 달라지는 것이 없다.**
  - `warehouseStorage` 값은 컨트롤러에서 로그에 찍히고 서비스로 전달된다.
    - 근거: `Xtw92CommandController.java:94-95`, `:105`, `Xtw92CommandService.java:136`
  - `createInstantOrder`는 `isWarehouseStorage` 파라미터를 받지만 본문 어디에서도 사용하지 않는다.
    - 근거: `Xhq12CommandService.java:220-319`
  - 따라서 구매자 창고 보관(`Xms75` 생성), 주문 `IN_WAREHOUSE`/`COMPLETED` 전이는 일어나지 않는다. 그런 처리는 `process-payment-shipment` 경로(`Xhq12CommandService.java:163-173`)에만 있다.
  - 창고 관련으로 이 경로에서 일어나는 것은 판매자 쪽 `sale.isWarehouseStorage()`가 true일 때 판매자 창고 보관 상태를 `ASSOCIATED_WITH_ORDER`로 바꾸는 것뿐이다. 구매자 선택과는 무관하다.
    - 근거: `Xhq12CommandService.java:291-293`
  - 이 상태 변경이 불가능한 전이(예: 이미 `SOLD`)에서 `Xzz46Exception`을 던지면 즉시 구매 전체가 실패하고 롤백된다.
    - 근거: `Xms75CommandService.java:243-256`, `Xhq12CommandService.java:295-301`
