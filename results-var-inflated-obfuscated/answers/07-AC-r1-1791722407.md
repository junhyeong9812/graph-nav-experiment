# 즉시 구매 처리 흐름 (판매 입찰 → 주문 입찰 `POST /order-bids/instant`)

> 경로 접두 `src/main/java/com/fream/back/domain/` 는 `D/` 로 줄여 쓴다.
> 진입점은 `m99` 의 `/order-bids/instant` 이다 (`D/m99/controller/command/Xtw92CommandController.java:22` base path `/order-bids`, `:89` `@PostMapping("/instant")`).
> `m27(/legacy/order-bids)`, `m10(/internal/…)`, `m96(/settlement/…)`, `m74(/admin/…)`, `m54(/partner/…)` 에도 같은 모양의 `/instant` 컨트롤러가 있으나(각 `…CommandController.java:22,89`), 실제 주문·결제·판매입찰 엔티티(m99/m64/m85)를 쓰는 본 경로는 `m99` 이다.
> 용어: `Xtw92`=주문 입찰(OrderBid), `Xhq12`=주문(Order), `Xzt63`=판매 입찰(SaleBid), `Xpj42`=판매(Sale), `Xjt45`=결제(Payment), `Xfr60`=배송, `Xms75`=창고 보관, `Xbp24`=알림.

## 1. API 와 처리 단계 / 동기·비동기 / 응답 ID

**API**: `POST /order-bids/instant`, body `Xcr44RequestDto` = `saleBidId`, `addressId`, `warehouseStorage`, `paymentRequest` (`D/m99/dto/Xcr44RequestDto.java:20-31`). 결제 요청은 `paymentType` 으로 CARD/ACCOUNT/GENERAL 하위 타입으로 역직렬화된다 (`D/m64/dto/Xjt45RequestDto.java:20-25`).

**단계**
1. 컨트롤러가 인증 이메일을 꺼내고(`Xtw92CommandController.java:92`), 결제 요청에 `userEmail` 을 넣고 `orderId=null` 로 둔 뒤(`:112-116` `enrichPaymentRequest`) `createInstantOrderBid(...)` 호출 (`:101-107`).
2. `Xtw92CommandService#createInstantOrderBid` (`@Transactional`, `D/m99/service/command/Xtw92CommandService.java:118-149`):
   - 입력 검증(이메일/판매입찰ID/배송지ID/결제정보 null 검사, `:154-167`)
   - 구매자 조회 `userQueryService.findByEmail` (`:126`)
   - 판매 입찰 조회·검증 (`:129`, `:172-184`; 존재와 sale 연결 여부만 검사하고 **판매 입찰이 이미 MATCHED 인지는 검사하지 않는다**)
   - `Xhq12CommandService#createInstantOrder` 호출 (`:133-139`)
   - 반환된 주문으로 주문 입찰 생성·저장 (`:142`, `:189-207`)
3. `Xhq12CommandService#createInstantOrder` (`@Transactional`, `D/m99/service/command/Xhq12CommandService.java:219-319`) 안에서 순서대로:
   배송지 조회(`:238`) → 주문 생성·저장(`:241-247`) → 주문 항목(`:255-256`) → 배송 정보(`:264-271`) → 판매 입찰 매칭 + `flush`(`:279-283`) → 판매자 창고 상태 갱신(조건부, `:291-294`) → 결제 처리(`:305`).
4. `Xjt45CommandService#processPayment` (`D/m64/service/command/Xjt45CommandService.java:57-107`): 검증(`:117-146`) → 결제 유형 switch(`:67-80`) → 알림 + 판매 상태 갱신 `notifyUsersAndUpdateSaleStatus`(`:83`).

**동기/비동기**: 전부 **동기**, 하나의 DB 트랜잭션이다. 이 경로에는 Kafka 발행이 없다. Kafka(`Xhq12EventProducer`)는 별도 엔드포인트 `/orders/{orderId}/process-payment-shipment` 에서만 쓰인다 (`D/m99/controller/command/Xhq12CommandController.java`, nav/m99.md §1). PortOne 결제 호출도 `restTemplate.exchange` 동기 호출이다 (`D/m64/p02/Xhs91ApiClient.java:266`).

**응답 ID**: `orderBidCommandService.createInstantOrderBid(...).getId()` (`Xtw92CommandController.java:101-107`) 이므로 **주문 입찰(Xtw92, OrderBid)의 ID** 이다. 변수명은 `orderId` 지만 주문(Xhq12) ID 가 아니다. 응답은 `ResponseDto.success(orderId, "즉시 구매가 성공적으로 처리되었습니다.")` (`:109`).

## 2. 새로 생성되는 엔티티와 상태 변화 순서

새로 생성: 주문 `Xhq12`, 주문 항목 `Xnd96`, 배송 `Xfr60`, 결제 `Xjt45`(하위 `Xxf47`/`Xkg34`/`Xgg74`), 알림 `Xbp24`(구매자·판매자 각 1), 주문 입찰 `Xtw92`. (창고 보관 `Xms75` 는 새로 만들지 않는다 — 5번 참고.)

| 순서 | 동작 | 직후 상태 | 근거 |
|---|---|---|---|
| 1 | 주문 `Xhq12` 생성·저장 | 주문 `PENDING_PAYMENT` | `Xhq12CommandService.java:241-247` |
| 2 | 주문 항목 생성 | 주문 항목 연결(상태 값 없음) | `:255-256` |
| 3 | 배송 `Xfr60` 생성 | 배송 `Xzn53Status.PENDING` | `D/m45/service/command/Xfr60CommandService.java:61-70`; 주문에 연결 `:271` |
| 4 | 판매 입찰 `saleBid.assignOrder(order)` + `updateStatus(MATCHED)` + flush | 판매 입찰 `PENDING → MATCHED` (주문 연결) | `Xhq12CommandService.java:279-283`; `D/m85/entity/Xzt63.java:58-61` |
| 5 | (판매가 창고 보관일 때만) 판매자 창고 보관 상태 변경 | 창고 보관 `ASSOCIATED_WITH_ORDER` | `Xhq12CommandService.java:291-294`; `D/m63/service/command/Xms75CommandService.java:117-133` |
| 6 | 결제 엔티티 생성·저장 | 결제 상태는 유형별(3번 표) | `Xjt45CommandService.java:157-333` |
| 7 | 판매 `sale.updateStatus(SOLD)` | 판매 `Xpj42Status.SOLD` | `Xjt45CommandService.java:391-405` (주문에 orderBid 가 아직 없어 `saleBidQueryService.findByOrderId` 경로를 탄다, `:388-391`) |
| 8 | 주문 입찰 `Xtw92` 생성 (builder 에서 `MATCHED`), `assignOrder`, `markAsInstantPurchase`, 저장 | 주문 입찰 `MATCHED`, `isInstantPurchase=true`, sale 연결 | `Xtw92CommandService.java:189-206`; `D/m99/entity/Xtw92.java:70-97` |

참고
- 주문(`Xhq12`)에 대해 `updateStatus` 가 즉시 구매 경로에서 **한 번도 호출되지 않는다** (`Xhq12CommandService.java:219-319` 전체에 `updateStatus` 없음, `Xjt45CommandService` 도 주문 상태를 건드리지 않음). 따라서 주문은 `PENDING_PAYMENT` 로 남는다.
- `Xhq12Status` 전이 규칙은 `PENDING_PAYMENT → PAYMENT_COMPLETED/COMPLETED/IN_WAREHOUSE` 등 (`D/m99/entity/Xhq12Status.java:15-24`) 이지만 호출되지 않아 쓰이지 않는다. `PAYMENT_COMPLETED → PREPARING → …` 로 바꾸는 코드는 별도 `processPaymentAndShipment`(`Xhq12CommandService.java:112-202`)에만 있다.
- 결제 금액 `paidAmount` 가 판매 입찰 가격(`saleBid.getBidPrice()`, 주문 `totalAmount`)과 같은지 검증하는 코드는 없다. `paidAmount > 0` 만 본다 (`Xjt45CommandService.java:142-145`).

## 3. 결제 수단별 결과 / 카드 결제 실패 시

| 유형 | 결제 엔티티 | 결제 상태 | 비고 / 근거 |
|---|---|---|---|
| CARD | `Xxf47` | PortOne 응답 `status == "success"` 이면 `PAID` + `isSuccess=true`, 아니면 `PENDING` 유지 | `Xjt45CommandService.java:157-208`; 기본값 `PENDING` `D/m64/entity/Xjt45.java:44` |
| ACCOUNT | `Xkg34` | 항상 `PENDING` (PG 호출·입금 확인 없음). 은행명만 enum 검증 | `Xjt45CommandService.java:236-262`, `:470-488` |
| GENERAL | `Xgg74` | 항상 `PAID`, `isSuccess=true` (`impUid` 비어있지 않은지만 검사, PG 검증 없음) | `Xjt45CommandService.java:290-316` |

**즉시 구매가 끝까지 성공하는가**: 결제 상태와 무관하게 **세 유형 모두 정상 반환**된다. 결제 후 처리(`notifyUsersAndUpdateSaleStatus`)는 결제 상태(`PAID`/`PENDING`)를 확인하지 않고 실행된다 (`Xjt45CommandService.java:83`, `:383-425`). 그래서 계좌이체(`PENDING`)여도 판매는 `SOLD`, 주문 입찰은 `MATCHED`, 알림이 나간다. 어느 유형이든 주문은 `PENDING_PAYMENT` 에 머문다 (2번).

**카드 결제를 PortOne 이 실패로 응답하면**
- 두 갈래다.
  1. **HTTP 상태≠200 이거나 응답 `code != 0`**: `Xtc14Exception` 발생 (`Xhs91ApiClient.java:270-275`). 통신 오류는 `Xjt45ApiException`(재시도 `@Retryable` 대상, `:224-228`) 또는 `Xtc14Exception`(`:288-293`). 예외는 `createInstantOrder` 에서 `Xwf42Exception`(결제 처리 오류)로 감싸져 (`Xhq12CommandService.java:306-309`) `Xhq12Exception` 이므로 그대로 재던져지고 (`:312-314`, `Xtw92CommandService.java:212-216`), `@Transactional` 이 RuntimeException 으로 **전체 롤백**된다. 주문·배송·판매 입찰 MATCHED·주문 입찰 모두 저장되지 않고, 에러 응답(`Xkt44ExceptionHandler#handleGlobalException`, `D/../global/exception/Xkt44ExceptionHandler.java:49`)이 나간다.
  2. **HTTP 200 + `code == 0` 이지만 결제 `status` 가 `success` 가 아님(예: failed)**: 예외가 없다. `PAID` 로 바꾸지 않고(`Xjt45CommandService.java:203-206`) `PENDING` 인 채로 저장한다. 게다가 `Xxf47` 생성자가 `setPaidAmount` 를 호출해 `isSuccess = paidAmount > 0 = true` 가 된다 (`D/m64/entity/Xxf47.java:38`, `D/m64/entity/Xjt45.java:60-63`). 이후 흐름이 계속되어 판매 `SOLD`, 알림 발송, 주문 입찰 `MATCHED` 가 되고 `200 OK` 와 "즉시 구매가 성공적으로 처리되었습니다." 가 응답된다. 즉 **실패 카드 결제가 성공처럼 처리된다.**

## 4. 알림: 누가, 언제, 어떻게

- **누가**: 구매자(`order.getUser()`)에게 `"결제가 완료되었습니다. 주문 ID: {orderId}"`, 판매자(`sale.getSeller()`)에게 `"구매자가 결제를 완료하였습니다. 판매 ID: {saleId}"`. 둘 다 카테고리 `Xrv73.SHOPPING`, 타입 `Xbp24Type.BID` (`Xjt45CommandService.java:434-456`). 알림에 들어가는 ID 는 주문(Xhq12) ID 와 판매(Xpj42) ID 이다.
- **언제**: 결제 엔티티 저장 직후, 판매 상태를 `SOLD` 로 바꾸기 직전(`:403-404`), 즉 같은 요청·같은 트랜잭션 안(`createInstantOrder` → `processPayment`)이다. 결제 성공 여부와 무관하게 3번처럼 `PENDING`/실패 응답이어도 발송된다.
- **어떻게**: `Xbp24CommandService#createNotification` 이 알림을 DB 에 저장(`D/m52/service/command/Xbp24CommandService.java:52-53`)하고 `sendRealTimeNotification` 으로 WebSocket(STOMP) 푸시한다. Redis 키 `WebSocket:Xjm45:{email}` 가 있을 때만 `/user/queue/notifications` 로 보내고(`:303-319`, 상수 `:37-38`), 접속이 없으면 저장만 한다(`:320-322`). Kafka 알림 토픽은 이 경로에서 쓰지 않는다.
- 알림·판매 상태 갱신의 예외는 try/catch 로 삼켜진다 (`Xjt45CommandService.java:421-425`, `:457-461`): 알림이 실패해도 구매는 계속 진행되고, 이 경우 판매는 `SOLD` 로 바뀌지 않을 수 있다. WebSocket 푸시는 커밋 전에 일어난다.

## 5. 최종 주문 상태 / 창고 보관 선택 시

**최종 상태 (정상 종료 시)**
- 주문 `Xhq12`: **`PENDING_PAYMENT`** (2번 참고; 결제 완료 후에도 바뀌지 않음).
- 주문 입찰 `Xtw92`: `MATCHED` (`isInstantPurchase=true`), 판매 입찰 `Xzt63`: `MATCHED`, 판매 `Xpj42`: `SOLD`, 배송 `Xfr60`: `PENDING`, 결제: CARD 성공/GENERAL `PAID`, ACCOUNT·카드 비성공 응답 `PENDING`.
- `COMPLETED` 나 `PAYMENT_COMPLETED` 같은 주문 상태는 이 경로에서 세팅되지 않는다.

**구매자가 "창고 보관"(`warehouseStorage=true`)을 선택한 경우**
- 컨트롤러는 값을 서비스에 전달하지만 (`Xtw92CommandController.java:101-107` → `Xtw92CommandService.java:119-139` → `Xhq12CommandService.java:220-221`), `createInstantOrder` 본문에서 `isWarehouseStorage` 파라미터를 **한 번도 사용하지 않는다** (`:219-319`). 그러므로 구매자의 선택은 **결과에 아무 영향이 없다.**
  - 구매자용 창고 보관 엔티티 `Xms75` 를 만드는 `createOrderStorage` 는 즉시 구매 경로에서 호출되지 않는다 (호출은 `processPaymentAndShipment` `:170` 뿐, 거기서만 `IN_WAREHOUSE`→`COMPLETED` 전이).
  - 주문 상태는 `warehouseStorage` 값과 관계없이 `PENDING_PAYMENT`.
- 창고 관련 분기는 **판매자 쪽** 속성 `sale.isWarehouseStorage()` 로만 결정된다 (`Xhq12CommandService.java:291-294`): 판매가 창고 보관 판매이면 판매자의 보관 정보 상태를 `ASSOCIATED_WITH_ORDER` 로 바꾸고, 보관 정보가 없으면 `Xzg57Exception`(`D/m63/service/query/…#findBySale`) 이 `Xkd21Exception` 으로 감싸져 전체 롤백된다 (`:295-301`).
- 창고 보관과 무관하게 배송 정보(`Xfr60`)는 항상 구매자 배송지로 생성된다 (`:264-271`).
