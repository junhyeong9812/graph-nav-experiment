# 구매자 배송: 운송장 등록 → 배송 완료

경로 약어: `D` = `src/main/java/com/fream/back/domain`, `G` = `src/main/java/com/fream/back/global`.
엔티티 약어(난독화 이름): 배송 `Xfr60`(order_shipment), 주문 `Xhq12`(orders), 주문 입찰 `Xtw92`, 판매 입찰 `Xzt63`, 판매 `Xpj42`, 배송 상태 enum `Xzn53Status`.

**먼저 알아둘 점 — 같은 코드가 여러 도메인에 복제돼 있다.**
- 운송장 등록 컨트롤러가 6벌 있다(`m45`, `m09`, `m31`, `m70`, `m81`, `m38`). 모두 같은 `Xfr60CommandService`(`D/m45/service/command/Xfr60CommandService.java`)를 호출한다.
- 배송 상태 배치 Job 설정도 6벌 있다(`m31`, `m09`, `m38`, `m45`, `m70`, `m81`). 모두 빈 이름이 `updateShipmentStatusesJob`이고 내용은 도메인/패키지/주입 서비스만 다르다.
- 아래에서는 `m31` 판을 대표로 인용한다. 처리 로직은 6벌이 동일하고, 모두 같은 `Xfr60CommandService#completeOrder`와 알림 서비스를 호출한다.
- 같은 빈 이름이 겹치므로 Spring 설정에 따라 기동 시 충돌할 수 있다. 그래도 어느 판이 선택되든 동작은 같다. (`application*.yml`에 bean overriding 설정은 없다.)

## 1. 운송장 등록 요청

### 1-1. 진입 API
- `PATCH /{prefix}/shipments/order/{shipmentId}/status`, body `{courier, trackingNumber}`.
  - 운영 측 경로는 `/admin/shipments/order/...` → `D/m09/controller/command/Xqh36CommandController.java:20,33-41`.
  - 같은 서비스를 부르는 다른 prefix 판: `/shipments/order`(`D/m45/controller/command/Xfr60CommandController.java:20,33`), `/partner/shipments/order`(`D/m31/controller/command/Xzm66CommandController.java:20,33`), `/legacy/...`(`D/m70/controller/command/Xcx47CommandController.java:20`), `/settlement/...`(`D/m81/controller/command/Xsd74CommandController.java:20`), `/internal/...`(`D/m38/controller/command/Xdn57CommandController.java:20`).
- 컨트롤러는 `Xfr60CommandService#updateTrackingInfo(shipmentId, courier, trackingNumber)`를 그대로 호출한다 (`D/m45/controller/command/Xfr60CommandController.java:41-45`, 서비스 `D/m45/service/command/Xfr60CommandService.java:239`).
- 요청 DTO는 단순 `String courier, trackingNumber`이고 검증 애노테이션이 없다 (`D/m45/dto/Xfr60RequestDto.java`). 빈 값 검사는 서비스에서 한다(`Xfr60CommandService.java:243-246`, `TRACKING_INFO_REQUIRED`/400).

### 1-2. 의도된 상태 변경 순서와 알림 (`Xfr60CommandService.java:249-289`)
1. 배송 조회: `orderShipmentRepository.findById` (249-253).
2. **배송 `Xfr60`**: `updateTrackingInfo(courier, trackingNumber)`로 택배사·운송장 저장 + 상태를 곧바로 `IN_TRANSIT`으로 세팅 (256). 엔티티 메서드는 전이 검사를 하지 않는다 (`D/m45/entity/Xfr60.java:41-45`).
3. **주문 `Xhq12`**: `order.updateStatus(IN_TRANSIT)` (259-260). 전이 검사는 `Xhq12Status.canTransitionTo` (`D/m99/entity/Xhq12.java:113-121`).
4. **알림 1건 → 구매자**: "상품이 출발하였습니다. 주문 ID: …" (265-271, `Xbp24CommandService#createNotification`).
5. `updateSaleStatusToSold(orderId)` (276): 판매자에게 "상품이 성공적으로 판매 완료되었습니다" 알림과 `Xpj42 → SOLD`를 시도 (111-183).
6. 창고 보관 판매이면 창고 상태를 sold로 갱신 (279-286).
7. `updateOrderAndSaleBidStatusToCompleted(orderId)` (289, 413-440): 주문 입찰 `MATCHED→COMPLETED`, 판매 입찰 `MATCHED→COMPLETED`. 이 메서드의 예외는 내부에서 삼킨다 (436-439).

### 1-3. 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문에서 끝까지 성공하나? → **아니오, 3단계에서 실패한다**
- 이 주문의 상태: `processPaymentAndShipment`의 비창고 분기에서 `PENDING_PAYMENT → PAYMENT_COMPLETED → PREPARING`까지만 간다 (`D/m10/service/command/Xkf46CommandService.java:174-177`, 같은 코드가 `D/m99`, `D/m96`, `D/m74` 등에도 있다). 창고 보관이면 `COMPLETED`까지 가서 마찬가지로 이후 전이가 없다 (165-172).
- 배송은 `createOrderShipment`에서 `PENDING`으로 만들어진다 (`Xfr60CommandService.java:67`).
- 허용 전이표: `PREPARING → {IN_WAREHOUSE, SHIPMENT_STARTED}`, `IN_TRANSIT`은 `SHIPMENT_STARTED`에서만 올 수 있다 (`D/m99/entity/Xhq12Status.java:26,28`). 즉 `PREPARING → IN_TRANSIT`은 불허다.
- 실패 지점: `Xfr60CommandService.java:260`의 `order.updateStatus(Xhq12Status.IN_TRANSIT)`가 `Xxm16StatusException("상태 전환이 허용되지 않습니다: PREPARING -> IN_TRANSIT")`을 던진다 (`D/m99/entity/Xhq12.java:117-119`).
- 이 예외는 `Xzn53Exception`이 아니라서 `catch (Exception e)` (295-302)에 걸려 `Xzn53Exception(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")`로 바뀌어 다시 던져진다. 이 코드는 `Xkt44Exception extends RuntimeException`이다 (`G/exception/Xkt44Exception.java:10`).
- 저장되는 것: **없음**. `@Transactional` 메서드(238)가 RuntimeException으로 끝나므로 롤백된다. 그 결과 배송은 여전히 `PENDING`에 택배사·운송장 null이고, 주문은 `PREPARING`이다. 구매자 알림(4번)은 3번 앞에서 중단되어 생성되지 않는다.
- 응답: `Xkt44ExceptionHandler#handleShipmentException` (`G/exception/Xkt44ExceptionHandler.java:459-473`)이 `ErrorCode`의 값으로 응답한다. HTTP **404**, body `ErrorResponse{code:"S001", message:"배송 정보를 찾을 수 없습니다.", status:404, path}`. 예외에 담은 상세 메시지는 응답에 나가지 않는다. 코드 정의는 `D/m45/exception/Xzn53ErrorCode.java:12`.
- 이름·의도와 실제 동작이 다르다: `SHIPMENT_NOT_FOUND`라는 코드지만 실제 원인은 주문 상태 전이 불허다.

(참고: 같은 서비스의 `updateAndCheckShipmentStatus`(`check-status` 엔드포인트, 452-516)는 주문 상태를 건드리지 않고 배송만 `IN_TRANSIT`으로 만든다 (473, 497). 이 경로로는 위 실패 없이 배송이 `IN_TRANSIT`이 될 수 있다.)

## 2. 배송 완료 감지

### 2-1. 누가·언제·어떻게
- **스케줄러**: `G/config/Xzn53BatchScheduler.java`의 `scheduleShipmentStatusJob()`.
- **주기**: `@Scheduled(cron = "0 0 */6 * * *")` → 6시간마다(00/06/12/18시 정각) (`Xzn53BatchScheduler.java:34`). 매 실행마다 `timestamp` 파라미터를 붙여 `jobLauncher.run(updateShipmentStatusesJob, …)` 한다 (36-40). 예외는 `printStackTrace`만 한다 (41-43).
- **Job → Step**: `updateShipmentStatusesJob` → `updateShipmentStatusesStep` (`D/m31/config/Xkd78JobConfig.java:54-82`). 청크 50, `faultTolerant().skip(Exception.class).skipLimit(50)` (51-52, 75-77).
- **대상 배송**: reader JPQL `SELECT s FROM Xfr60 s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL` (`Xkd78JobConfig.java:95`). `PENDING` 배송은 조회되지 않는다.
- **실제로 실행되는 처리 코드**: `Xkd78JobConfig.java:69-73`이 `new Xhx91Processor(playwrightBrowserManager(), notificationService, orderService)`를 processor로 넣는다. 따라서 실제 처리는 `D/m31/config/Xhx91Processor.java#process`이다.
  - 같은 설정 클래스 안의 `shipmentItemProcessor()` 빈(`Xkd78JobConfig.java:106-177`)은 step에 연결되지 않아 쓰이지 않는다. 그 안의 `parseCjLogisticsStatus`(Jsoup, 186-220)도 어디서도 호출되지 않는다.
  - `Xfr60CommandService#updateShipmentStatuses()`(309-391)도 호출처도 `@Scheduled`도 없어 실행되지 않는다. 이쪽은 알림 로직이 다르고 `completeOrder`를 쓰지 않는다. 배치는 이 메서드를 호출하지 않는다.
- **조회 방식**: `Xhx91Processor`가 Playwright 브라우저로 CJ대한통운 `https://trace.cjlogistics.com/next/tracking.html?wblNo=<운송장>` 페이지를 열어(`Xhx91Processor.java:72-87`) `tbody#statusDetail tr`의 **마지막 행 5번째 td 텍스트**를 상태 문자열로 쓴다 (`parseStatusFromHtml`, `.td.get(4).text().trim()`). 택배사 `courier` 값은 조회에 쓰이지 않고 항상 CJ로 조회한다. Step 시작/종료 시 `Xsn32Listener`가 브라우저를 열고 닫는다 (`D/m31/config/Xsn32Listener.java`, `Xkd78JobConfig.java:80`).

### 2-2. 택배사 상태 문자열 → 내부 상태 (`Xhx91Processor.java:221-226`)
| 택배사 문자열 | 내부 상태 |
|---|---|
| `"배송완료"` | `DELIVERED` |
| `"배송출발"` | `OUT_FOR_DELIVERY` |
| 그 외 모든 문자열(예: "집화처리", "배송 완료" 같은 표기 차이 포함) | `IN_TRANSIT` |

- 정확한 문자열 일치(`switch`)다.
- 조회한 값이 현재 상태와 같으면 변경 없이 반환한다 (`Xhx91Processor.java:101`).
- 현재 `OUT_FOR_DELIVERY`인데 문자열이 그 외로 매핑되면 `IN_TRANSIT`으로의 전이가 불허여서(`Xzn53Status.java:23-28`) `IllegalStateException` → `EXTERNAL_TRACKING_SERVICE_ERROR`로 감싸져 해당 건이 skip된다.

## 3. 배송 완료 판정 이후 (`Xhx91Processor.java:108-117`)

상태 변경 순서 (`DELIVERED`로 판정된 경우):
1. **배송 `Xfr60`**: `updateStatus(DELIVERED)` (`:113`). `IN_TRANSIT`/`OUT_FOR_DELIVERY`에서만 허용 (`D/m45/entity/Xzn53Status.java:16-28`).
2. `Xfr60CommandService#completeOrder(orderId)` (`:116`, 서비스 `:190-229`):
   1. 주문 입찰 조회 `orderBidQueryService.findByOrderId` — 없으면 `IllegalArgumentException` (196-197).
   2. **주문 `Xhq12`**: `updateStatus(COMPLETED)` (204). 허용 출발 상태는 `PENDING_PAYMENT`, `IN_WAREHOUSE`, `IN_TRANSIT` (`Xhq12Status.java:24,27,29`).
   3. `updateSaleStatusToSold(orderId)` (208): 판매 입찰 조회 후 `Xpj42 → SOLD`를 시도하고, 전이가 가능할 때만 판매자 알림을 만든다 (111-183). `SOLD`에서 `SOLD`로는 `canTransitionTo`가 false이므로(`D/m85/entity/Xpj42Status.java`의 `case SOLD … -> false`) 이미 `SOLD`이면 아무 일도 하지 않는다.
   4. 구매자 알림 1건: "[completeOrder] 주문이 완료 처리되었습니다. 주문 ID: …" (211-217).
   5. 어느 단계든 예외가 나면 `Xzn53Exception(ORDER_NOT_FOUND_FOR_SHIPMENT)`로 감싸 던진다 (221-228).
3. `Xss87CommandService#notifyShipmentCompleted(order)` (`:117`, 구현 `D/m102/service/command/Xss87CommandService.java:219-234`): 구매자 알림 1건 "[배송 완료] 상품이 배송 완료되었습니다. 주문 ID: …". 내부에서 예외를 삼킨다 (230-233).
4. 이후 writer(`JpaItemWriter`, `Xkd78JobConfig.java:239-246`)가 배송을 저장한다.

알림 수 (정상 완료 시):
- **구매자 2건** (`[completeOrder]` 1건 + `[배송 완료]` 1건). 두 알림 모두 `Xjm45 buyer = order.getUser()` 대상이다.
- **판매자 0~1건**: `updateSaleStatusToSold`가 판매 상태를 실제로 `SOLD`로 바꿀 때만 1건. 결제 단계에서 이미 `Xpj42 → SOLD`로 바뀌므로 (`D/m64/service/command/Xjt45CommandService.java:383-426`, 특히 404, 419) 보통은 0건이다.

주문 입찰·판매 입찰 상태:
- `completeOrder`는 **입찰 상태를 바꾸지 않는다.** 입찰을 `COMPLETED`로 바꾸는 `updateOrderAndSaleBidStatusToCompleted`는 `updateTrackingInfo`(운송장 등록, `:289`)에서만 호출되고 `completeOrder`/배치 경로에서는 호출되지 않는다. 그러므로 배송 완료 후에도 주문 입찰(`Xtw92`)과 판매 입찰(`Xzt63`)은 `MATCHED` 그대로다.
- 판매(`Xpj42`)는 결제 시점에 `SOLD`로 바뀌어 있다.
- 입찰 `updateStatus`에는 전이 검사가 없다 (`D/m99/entity/Xtw92.java:106-108`, `D/m85/entity/Xzt63.java:66-68`).

## 4. 주문 종류별 차이

### (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문 → **끝까지 진행되지 않는다. `completeOrder`에서 실패**
- 이 주문은 `Xtw92`는 있지만 판매 입찰 `Xzt63`의 `order`는 비어 있다. 일반 구매 입찰은 `createOrderFromBid` + `createAndSaveOrderBid`로 만들어지고 (`D/m99/service/command/Xtw92CommandService.java:60-63,90-104`) 판매 입찰에 주문이 연결되는 곳은 즉시 구매/즉시 판매뿐이다 (`D/m10/service/command/Xkf46CommandService.java:279`, `D/m85/service/command/Xzt63CommandService.java:83`).
- `updateSaleStatusToSold`의 `saleBidQueryService.findByOrderId`는 연결이 없으면 `null`이 아니라 `IllegalArgumentException`을 던진다 (`D/m85/service/query/Xzt63QueryService.java:26-29`). 호출 쪽의 `if (saleBid != null)` 분기(116-117)는 이 경우를 처리하지 못한다.
- 그 예외는 `completeOrder`의 `catch (Exception)` (221)에서 `Xzn53Exception(ORDER_NOT_FOUND_FOR_SHIPMENT)`로 바뀌어 나간다. `completeOrder` 204줄의 주문 `COMPLETED` 변경, 구매자 알림(211-217), 이후의 `notifyShipmentCompleted`(117)는 모두 롤백되거나 실행되지 않는다.
- 결과: 배송 `DELIVERED` 변경과 주문 `COMPLETED` 변경이 모두 저장되지 않고, 알림도 0건이다. 배송은 `IN_TRANSIT`(또는 `OUT_FOR_DELIVERY`)으로 남아 6시간마다 재조회되고 매번 같은 이유로 skip된다.
- 또한 이 주문은 1-3에서 본 대로 `updateTrackingInfo`로는 `IN_TRANSIT`이 될 수 없다. 이 배치 경로에 도달하려면 `check-status` 경로(위 참고)나 직접 DB 수정이 필요하다.

### (b) 즉시 구매로 만들어진 주문 → **3의 처리가 끝까지 진행된다**
- 즉시 구매는 `createInstantOrder`에서 `saleBid.assignOrder(order)`로 판매 입찰과 주문을 연결하고 `flush`한다 (`Xkf46CommandService.java:279-283`). 이어서 `createInstantOrderBid`가 `order`/`sale`이 연결된 주문 입찰을 `MATCHED`로 저장한다 (`Xtw92CommandService.java:142,189-206`). 그래서 `completeOrder`의 주문 입찰 조회와 판매 입찰 조회가 둘 다 성공한다.
- 주문은 `PENDING_PAYMENT`에서 멈춰 있고(`Xkf46CommandService.java:244`, 결제 서비스는 주문 상태를 바꾸지 않는다), `PENDING_PAYMENT → COMPLETED`는 허용이다 (`Xhq12Status.java:24`). 그래서 `order.updateStatus(COMPLETED)`가 성공한다.
- 판매는 결제 시점에 이미 `SOLD`이므로 판매자 알림 없이 통과한다. 결과는 배송 `DELIVERED`, 주문 `COMPLETED`, 구매자 알림 2건이고, 입찰은 `MATCHED` 그대로다.
- 단, (b)도 `updateTrackingInfo`로는 `PENDING_PAYMENT → IN_TRANSIT`이 불허여서 1번의 등록 API는 실패한다 (응답은 1-3과 같은 404/S001). 배송을 `IN_TRANSIT`으로 만드는 길은 `check-status` 경로뿐이다.

요약: 같은 `DELIVERED` 판정이라도 (a)는 판매 입찰이 주문에 연결돼 있지 않아 `completeOrder`가 예외로 끝나고 아무것도 저장되지 않으며, (b)는 연결돼 있어 성공한다.

## 5. 실패 처리 (주기 처리 중 한 건 실패)

- 처리 중 예외는 `Xhx91Processor`에서 `Xzn53Exception`으로 감싸 다시 던진다 (`Xhx91Processor.java:120-146`). 빈/null 운송장은 `TRACKING_NUMBER_INVALID`, 페이지 생성 실패는 `BROWSER_INITIALIZATION_ERROR`, 상태표가 비어 있거나 파싱이 실패하면 `TRACKING_HTML_PARSE_ERROR` 등이다.
- Step은 `faultTolerant().skip(Exception.class).skipLimit(50)` (`Xkd78JobConfig.java:75-77`)이므로 한 건의 예외는 **그 건만 skip**된다.
  - skip된 배송은 write되지 않아 상태가 그대로이고 다음 6시간 주기에 다시 대상이 된다.
  - 청크(50건)의 트랜잭션이 롤백된 뒤 항목을 하나씩 다시 처리하며, 성공한 건은 커밋된다. 롤백된 청크 안의 알림 INSERT도 함께 취소되고, 재처리 과정에서 외부 조회가 다시 실행될 수 있다.
  - 나머지 건은 그대로 처리된다.
- skip 시 `shipmentSkipListener`는 로그만 남긴다 (`Xkd78JobConfig.java:251-286`). 재시도나 알림은 없다.
- skip이 한 실행에서 50건을 넘으면 `SkipLimitExceededException`으로 Step/Job이 실패하고, 아직 읽지 않은 배송은 그 회차에 처리되지 않는다. 스케줄러는 예외를 `printStackTrace`로만 처리한다 (`Xzn53BatchScheduler.java:41-43`).
- `notifyShipmentCompleted` 안의 예외는 내부에서 삼켜져 배송 완료 처리를 실패시키지 않는다 (`Xss87CommandService.java:230-233`). 반면 `completeOrder` 안의 예외는 모두 `Xzn53Exception`으로 올라가 해당 건을 실패시킨다.
- 부가 주의: reader는 `JpaPagingItemReader`(offset 페이징)인데 처리 중 상태가 `DELIVERED`로 바뀌어 조회 조건에서 빠지므로, 대상이 한 페이지(50건)를 넘으면 일부 건이 그 회차에 건너뛰어질 수 있다 (`Xkd78JobConfig.java:87-97`). 다음 주기에 다시 잡힌다.
