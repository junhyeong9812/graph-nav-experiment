## 1. API 진입점, 처리 단계, 동기/비동기, 응답 ID

**API**: `POST /order-bids/instant`
- `D/m99/controller/command/Xtw92CommandController.java:22` (`@RequestMapping("/order-bids")`), `:89` (`@PostMapping("/instant")`)
- 요청 DTO: `saleBidId`, `addressId`, `warehouseStorage`, `paymentRequest` — `D/m99/dto/Xcr44RequestDto.java:20-29`

**처리 단계 (모두 한 요청 스레드, 하나의 `@Transactional` 안)**
1. 컨트롤러가 로그인 이메일을 추출하고(`Xtw92CommandController.java:92`), 결제 요청에 `userEmail`을 채우고 `orderId=null`로 초기화한다(`:98`, `:119-122`).
2. `Xtw92CommandService.createInstantOrderBid` (`D/m99/service/command/Xtw92CommandService.java:118-149`, `@Transactional`)
   - 입력 검증(이메일/판매입찰ID/배송지ID/결제정보) `:123`, `:154-167`
   - 구매자 조회 `:126`, 판매 입찰 조회 + sale 연결 확인 `:129`, `:172-184`
3. `Xhq12CommandService.createInstantOrder` (`D/m99/service/command/Xhq12CommandService.java:219-319`, `@Transactional`)
   1. 배송지 조회 `:238`
   2. 주문(Order) 저장 `:241-247`
   3. 결제 요청에 orderId 설정 `:250`
   4. 주문 항목 생성 `:255-256`
   5. 배송 정보 생성 `:264-271`
   6. 판매 입찰 매칭 `:279-283`
   7. 판매자 창고 상태 갱신(조건부) `:290-301`
   8. 결제 처리 `:305` → `Xjt45CommandService.processPayment` (`D/m64/service/command/Xjt45CommandService.java:57-107`)
      - 결제 생성 후 알림 발송 + 판매 SOLD 처리 `:83` (`notifyUsersAndUpdateSaleStatus`, `:383-426`)
4. 주문 입찰(OrderBid) 생성·저장 `Xtw92CommandService.java:142`, `:189-202`

**동기/비동기**: 완전한 **동기** 처리이다.
- 즉시 구매 경로에는 `@Async`, Kafka 발행, 이벤트 리스너가 없다. Kafka 프로듀서(`Xhq12EventProducer.sendOrderProcessingEvent`)는 일반 주문의 `/orders/{id}/process-payment-shipment` 경로에서만 쓰인다 (`D/m99/controller/command/Xhq12CommandController.java:54`). 즉시 구매는 그 경로를 타지 않는다.
- PG(아임포트/PortOne) 카드 결제 호출도 요청 스레드에서 `RestTemplate`으로 동기 호출한다 (`D/m64/p02/Xhs91ApiClient.java:229-295`, 내부에서 `@Retryable` 최대 3회, `:224-228`).
- 알림도 같은 스레드에서 DB 저장 + WebSocket 전송 (4번 항목).

**응답으로 돌려주는 ID**: 변수명은 `orderId`지만 실제 값은 **주문 입찰(OrderBid, `order_bid` 테이블)의 ID**이다.
- `orderBidCommandService.createInstantOrderBid(...).getId()` — 반환 타입이 `Xtw92`(OrderBid)이다. `Xtw92CommandController.java:101-107`
- `Xtw92`는 `@Table(name = "order_bid")` 엔티티 — `D/m99/entity/Xtw92.java:16`, `:23-25`
- 응답은 `ResponseDto.success(orderId, "즉시 구매가 성공적으로 처리되었습니다.")` — `Xtw92CommandController.java:109`
- 실제 Order(`orders`, `Xhq12`)의 ID와는 별개의 값이다 (`Xhq12.java:26`). 일치하는 것처럼 보이는 것은 두 테이블의 IDENTITY 값이 우연히 같을 때뿐이다.

### 기존 엔티티의 상태 변화 (시간 순서)
기존 엔티티는 판매 입찰(SaleBid `Xzt63`)과 그 판매(Sale `Xpj42`)이다. 판매 입찰 생성 시점의 초기값은 다음과 같다.
- SaleBid: `PENDING` — `D/m85/service/command/Xzt63CommandService.java:45`
- Sale: `PENDING_SHIPMENT` — `D/m85/service/command/Xpj42CommandService.java:108` (`createSale`)

즉시 구매가 일으키는 변화:

1. **주문 저장 직후** — Order = `PENDING_PAYMENT`. (`Xhq12CommandService.java:244-247`)
2. **판매 입찰 매칭** — `saleBid.assignOrder(order)` 후 `updateStatus(MATCHED)` + `flush`. SaleBid: `PENDING` → **`MATCHED`**, `saleBid.order = 방금 만든 주문`.
   - `Xhq12CommandService.java:279-283`, `D/m85/entity/Xzt63.java:58-61`, `:66-68`
   - 이 시점 이전에 SaleBid가 아직 `PENDING`인지 검사하는 코드는 없다(`Xtw92CommandService.java:172-184`는 null/sale 존재만 확인). 이미 `MATCHED`인 판매 입찰도 다시 구매할 수 있다.
3. **판매자 창고 상태**(조건부) — `sale.isWarehouseStorage()`(판매자가 올릴 때 선택한 값)가 true이면 판매자 창고 레코드를 `ASSOCIATED_WITH_ORDER`로 변경. 창고 레코드가 없으면 `Xzg57Exception` → 롤백.
   - `Xhq12CommandService.java:291-294`, `D/m63/service/command/Xms75CommandService.java:116-140`, `D/m63/service/query/Xms75QueryService.java:30-33`
4. **결제 생성** — 결제 상태는 수단별(3번 참조).
5. **판매 SOLD 처리** — `processPayment` 안에서 Sale: `PENDING_SHIPMENT`(등) → **`SOLD`**.
   - 이 시점에 Order의 orderBid는 아직 null이므로 `saleBidQueryService.findByOrderId(order.getId())`로 판매 입찰을 찾아 그 sale을 쓴다. `Xjt45CommandService.java:388-406`
   - `sale.updateStatus(SOLD)`는 전환 검증 없이 값을 그대로 대입한다(`D/m85/entity/Xpj42.java:73-75`). `Xpj42Status.canTransitionTo`(`Xpj42Status.java:14-25`)상 `PENDING_SHIPMENT → SOLD`는 불허인데도 통과한다.
6. **주문 입찰 생성** — OrderBid를 `MATCHED`로 저장. `Xtw92CommandService.java:192-202`

최종 상태 요약: SaleBid=`MATCHED`, Sale=`SOLD`, Order=`PENDING_PAYMENT`(5번 참조), OrderBid=`MATCHED`.

## 3. 결제 수단별 결과, 성공 여부, PG 실패 응답

수단 분기: `Xjt45CommandService.java:67-80` (`getResolvedPaymentType()`: `D/m64/dto/Xjt45RequestDto.java:73-87`). 공통 검증은 `:117-146` — orderId 일치, 이메일 일치, `paidAmount > 0`.
**청구 금액(`paidAmount`)은 클라이언트가 보낸 값이며 판매 입찰 `bidPrice`와 대조하지 않는다** (`:142-145`, 반면 주문 `totalAmount`는 `bidPrice`, `Xhq12CommandService.java:243`).

| 수단 | 처리 | 결제 상태 | isSuccess | 근거 |
|---|---|---|---|---|
| 카드 `CARD` | 저장된 결제정보 조회 → PortOne `/subscribe/payments/onetime` 호출. 응답 `status == "success"`일 때만 PAID | 성공 시 `PAID`, 그 외 `PENDING`(기본값) | `PAID`일 때만 true | `Xjt45CommandService.java:157-225`, 특히 `:179`, `:203-206`; 기본값 `D/m64/entity/Xjt45.java:44`, `:39` |
| 계좌이체 `ACCOUNT` | 은행명만 검증, PG 호출 없음 | 항상 `PENDING` | false | `Xjt45CommandService.java:236-279`, `:260` |
| 일반 `GENERAL` | `impUid` 존재 여부만 확인, PG 재검증 없음 | 즉시 `PAID` | true | `Xjt45CommandService.java:290-333`, `:313-314` |

**즉시 구매가 끝까지 성공하는가?** 수단과 무관하게 결제 서비스가 예외를 던지지 않으면 성공한다. 계좌이체는 결제가 `PENDING`인 채로, 카드는 PG가 승인하지 않아도, 아래 경우에는 "성공"으로 끝난다.
- 결제가 `PENDING`(계좌이체)이어도 이후 `notifyUsersAndUpdateSaleStatus`가 그대로 실행되어 알림("결제가 완료되었습니다")이 나가고 Sale이 `SOLD`가 된다 — `Xjt45CommandService.java:83`, `:416-419`, `:438-443`.
- 컨트롤러는 "즉시 구매가 성공적으로 처리되었습니다."라고 응답한다 — `Xtw92CommandController.java:109`.
- 주문은 `PENDING_PAYMENT`에서 더 진행되지 않는다(5번). 즉 "즉시 구매 성공"의 의미는 입금/승인 확정이 아니라 레코드 생성 및 매칭 완료이다.

**PG(결제 대행사)가 카드 결제를 실패로 응답하면** — 두 경우가 갈린다.
1. **HTTP 비정상 또는 응답 `code != 0`** (PG가 오류 코드로 응답): `Xhs91ApiClient.java:270-275`에서 `Xtc14Exception`(= `Xjt45Exception`)을 던진다.
   - `createCardPayment`가 그대로 재던짐(`Xjt45CommandService.java:180-181`, `:218-219`) → `processPayment`도 재던짐(`:89-94`)
   - `createInstantOrder`가 `Xwf42Exception`("결제 처리 중 오류가 발생했습니다")으로 감싸 던짐(`Xhq12CommandService.java:305-309`) → 외부 catch가 `Xhq12Exception`을 그대로 재던짐(`:312-315`) → `handleOrderBidCreationException`도 재던짐(`Xtw92CommandService.java:145-147`, `:211-216`대, `Xhq12Exception`이면 그대로 throw)
   - 모든 예외가 `RuntimeException`(`D/../global/exception/Xkt44Exception.java`)이고 `@Transactional` 경계가 하나이므로 **트랜잭션 전체 롤백**: 주문·항목·배송·결제·판매입찰 매칭·알림이 모두 취소되고, 판매 입찰은 `PENDING`으로 남는다. 클라이언트는 `Xkt44ExceptionHandler`가 만든 에러 응답을 받는다 (`global/exception/Xkt44ExceptionHandler.java:49-`).
   - 단 통신 오류(`RestClientException`)는 `Xjt45ApiException`이 되어 `@Retryable`로 최대 3회 재시도(1초 간격)한다 — `Xhs91ApiClient.java:224-228`, `:288-290`.
2. **HTTP 200 + `code == 0`이지만 응답 `status`가 `"success"`가 아닌 경우**(예: 승인 거절 `failed`): 예외가 발생하지 않는다. 결제는 `PENDING`/`isSuccess=false`로 저장되고(`Xjt45CommandService.java:203-208`) 흐름은 계속 진행되어 **구매가 성공으로 끝난다** — 구매자·판매자 알림이 나가고 Sale은 `SOLD`, SaleBid는 `MATCHED`가 된다. 실패를 걸러내는 코드가 없다.

## 4. 알림 대상, 시점, 전달 방식

**누가 무엇을 받나** — `Xjt45CommandService.sendNotifications` (`:434-462`):
- 구매자: "결제가 완료되었습니다. 주문 ID: {orderId}" — `:438-443`
- 판매자(`sale.getSeller()`): "구매자가 결제를 완료하였습니다. 판매 ID: {saleId}" — `:447-453`
- 둘 다 카테고리 `SHOPPING`, 타입 `BID`.

**시점**: 결제 레코드가 생성된 직후, 같은 요청/트랜잭션 안에서(`processPayment`의 `:83`). 결제 상태와 무관하게(카드 PG 거절·계좌이체 PENDING 포함) 발송된다. 순서는 구매자 → 판매자, 이후 Sale `SOLD` 처리(`:416-419`).

**전달 방식**:
- 알림을 DB에 저장한다 — `Xbp24CommandService.java:52-53`
- 수신자가 WebSocket에 연결돼 있으면(Redis 키 `WebSocket:Xjm45:{email}` 존재) STOMP `/queue/notifications`로 `convertAndSendToUser` 실시간 푸시 — `Xbp24CommandService.java:37-38`, `:303-323`
- 연결이 없으면 DB 저장만 되고 푸시는 생략("알림은 저장됨") — `:320-322`
- 이메일/SMS/FCM 등 다른 채널, 비동기 큐는 없다. 알림 전송 실패는 `catch`로 삼켜 경고 로그만 남긴다(`Xjt45CommandService.java:457-461`, `:421-425`).
- 트랜잭션 안에서 보내므로, 이후 단계(예: 주문 입찰 저장)에서 롤백되더라도 WebSocket 푸시는 이미 나갔을 수 있다(DB 알림 행만 롤백).

## 5. 최종 주문 상태와 "창고 보관" 선택의 효과

**주문(Order)의 최종 상태 = `PENDING_PAYMENT`**
- `createInstantOrder`는 주문을 `PENDING_PAYMENT`로 저장(`Xhq12CommandService.java:244`)한 뒤 `updateStatus`를 한 번도 호출하지 않는다(`:219-319` 전체에 없음).
- 결제 처리(`Xjt45CommandService`)도 주문 상태를 바꾸지 않고 Sale 상태만 바꾼다(`:404`, `:419`).
- `PAYMENT_COMPLETED → PREPARING → ...` 전환은 일반 주문의 `processPaymentAndShipment`(`Xhq12CommandService.java:163-177`)에만 있고, 즉시 구매 경로에서는 호출되지 않는다.
- 카드가 `PAID`이든, 계좌이체가 `PENDING`이든, PG가 거절했든 최종 주문 상태는 동일하게 `PENDING_PAYMENT`이다.
- 주문 입찰(OrderBid)은 `MATCHED`(`Xtw92CommandService.java:196`), 판매 입찰은 `MATCHED`, 판매는 `SOLD`.

**구매자가 "창고 보관"(`warehouseStorage=true`)을 선택하면 달라지는 것: 실제로는 아무것도 달라지지 않는다.**
- 컨트롤러가 값을 서비스로 넘기고(`Xtw92CommandController.java:104`) `createInstantOrder`의 파라미터 `isWarehouseStorage`로 전달되지만(`Xtw92CommandService.java:137`, `Xhq12CommandService.java:221`), 메서드 본문에서 **한 번도 읽지 않는다**(`:219-319`).
- 따라서 구매자용 창고 보관 레코드(`Xms75.createOrderStorage`, `D/m63/service/command/Xms75CommandService.java:33-64`)가 만들어지지 않고, 주문 상태도 `IN_WAREHOUSE`/`COMPLETED`로 가지 않는다.
- 창고 보관에 따른 상태 전환(`PAYMENT_COMPLETED → PREPARING → IN_WAREHOUSE → COMPLETED`, `Xms75` 생성)은 일반 주문 `processPaymentAndShipment`에만 구현돼 있다(`Xhq12CommandService.java:163-173`).
- 즉시 구매 경로에서 창고 관련 코드가 실행되는 유일한 곳은 **판매자**가 판매 등록 시 정한 `sale.isWarehouseStorage()` 기반의 `ASSOCIATED_WITH_ORDER` 갱신(`:291-294`)이며, 이는 구매자의 선택과 무관하다.
- 응답 메시지도 창고 선택과 무관하게 동일하다(`Xtw92CommandController.java:109`).
