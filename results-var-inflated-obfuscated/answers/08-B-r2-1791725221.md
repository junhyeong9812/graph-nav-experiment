## 0. 사전: 결제·배송 처리 직후 주문/배송 상태

- 결제·배송 처리 API는 `POST /orders/{orderId}/process-payment-shipment`. 이 API는 Kafka 이벤트만 발행한다 (`D/m99/controller/command/Xhq12CommandController.java:36-52`).
- 실제 처리는 컨슈머가 한다. 결제 후 `Xfr60`를 `PENDING`으로 만들고 (`D/m99/service/kafka/Xhq12EventConsumer.java:181-188`, `D/m45/service/command/Xfr60CommandService.java:55-75`), 주문을 `PAYMENT_COMPLETED`로 바꾼다 (`Xhq12EventConsumer.java:195`).
- 창고 보관이 아닌 실배송이면 `PREPARING`에서 멈춘다 (`Xhq12EventConsumer.java:215-218`). 동기 버전도 같다 (`D/m99/service/command/Xhq12CommandService.java:175-176`).
- 즉 "결제·배송 처리를 마친 실배송 일반 구매 입찰 주문"은 **주문 `PREPARING` / 배송 `PENDING`** 이다.
- 코드 어디에서도 주문을 `SHIPMENT_STARTED`로 바꾸지 않는다 (`updateStatus(Xhq12Status.…)` 호출 전수 검색 결과: `PAYMENT_COMPLETED`, `PREPARING`, `IN_WAREHOUSE`, `COMPLETED`, `IN_TRANSIT`만 사용). 이 점이 아래 1번 실패의 근본 원인이다.

## 1. 운송장 등록 요청

### 1-1. 어느 API로 들어오나

- `PATCH /shipments/order/{shipmentId}/status`, 바디 `{courier, trackingNumber}` (`D/m45/controller/command/Xfr60CommandController.java:20,33-49`, DTO `D/m45/dto/Xfr60RequestDto.java`).
- 컨트롤러는 `Xfr60CommandService.updateTrackingInfo(shipmentId, courier, trackingNumber)`만 호출한다 (`Xfr60CommandController.java:41-45`).
- 같은 서비스를 호출하는 복제 컨트롤러가 `/admin/shipments/order` (m09), `/partner/…` (m31), `/internal/…` (m38), `/legacy/…` (m70), `/settlement/…` (m81)에도 있다 (예: `D/m09/controller/command/Xqh36CommandController.java:20,24,33`). 동작은 동일하다.
- 같은 컨트롤러의 `POST …/check-status`, `POST …/check-status-string`(`Xfr60CommandController.java:58,103`)은 별도 흐름이다. 이 둘은 `updateAndCheckShipmentStatus`를 호출한다. 아래 4번에서 다시 언급한다.

### 1-2. 코드가 의도한 상태 변경 순서 / 알림 (`D/m45/service/command/Xfr60CommandService.java:238-303`)

1. 택배사·운송장 공백 검사. 공백이면 `TRACKING_INFO_REQUIRED(S004, 400)` (:243-246).
2. `Xfr60` 조회, 없으면 `SHIPMENT_NOT_FOUND` (:249-253).
3. **배송**: `shipment.updateTrackingInfo()`가 courier/trackingNumber를 넣고 상태를 **무조건 `IN_TRANSIT`** 으로 세팅한다 (:256, `D/m45/entity/Xfr60.java:41-45`). `canTransitionTo` 검사를 거치지 않는다.
4. **주문**: `order.updateStatus(Xhq12Status.IN_TRANSIT)` (:260). 이때만 전이 검사(`Xhq12.java:113-121`)가 걸린다.
5. **알림 1 (구매자)**: "상품이 출발하였습니다. 주문 ID: …" (:265-271).
6. `updateSaleStatusToSold(orderId)` (:276, 본문 :111-183). 판매 입찰의 판매(`Xpj42`)를 `SOLD`로 바꾸고, 창고 보관 상품이면 창고 상태를 갱신한다. 이때 **알림 2 (판매자)** "상품이 성공적으로 판매 완료되었습니다. 판매 ID: …" (:133-138). 주문 입찰 쪽 블록(:150-180)도 같은 판매를 다시 보지만, 이미 `SOLD`라 `canTransitionTo(SOLD)`가 false여서 알림이 중복되지는 않는다.
7. 창고 보관 상품이면 창고 상태 갱신을 한 번 더 호출 (:279-286).
8. `updateOrderAndSaleBidStatusToCompleted` (:289, 본문 :412-440). 주문 입찰·판매 입찰이 `MATCHED`면 `COMPLETED`로 바꾼다. 이 메서드는 try/catch로 예외를 삼킨다 (:436-439).

의도상으로는 이 한 번의 호출에서 배송 `IN_TRANSIT`, 주문 `IN_TRANSIT`, 판매 `SOLD`, 입찰 `COMPLETED`가 모두 처리된다. 즉 "출발" 시점에 판매 완료·입찰 완료까지 앞당겨 처리하도록 짜여 있다.

### 1-3. 실배송 일반 구매 입찰 주문(`PREPARING`)에서 끝까지 성공하나 → **실패한다**

- 실패 지점: 4단계 `order.updateStatus(IN_TRANSIT)` (`Xfr60CommandService.java:260`).
  - 주문 상태 전이표에서 `PREPARING`의 허용 대상은 `{IN_WAREHOUSE, SHIPMENT_STARTED}`뿐이다 (`D/m99/entity/Xhq12Status.java:26`). `IN_TRANSIT`은 `SHIPMENT_STARTED`에서만 갈 수 있다 (:28).
  - `Xhq12.updateStatus`가 `Xxm16StatusException("상태 전환이 허용되지 않습니다: PREPARING -> IN_TRANSIT")`을 던진다 (`D/m99/entity/Xhq12.java:113-121`).
- 예외 처리: 이 예외는 `Xzn53Exception`이 아니라서 `catch (Exception e)`로 들어가, `Xzn53Exception(SHIPMENT_NOT_FOUND, "운송장 정보 업데이트 중 오류 발생: …")`로 감싸져 던져진다 (:295-301).
- 무엇이 저장되나: **아무것도 저장되지 않는다.** `@Transactional`(:238) 메서드에서 `RuntimeException`이 밖으로 나가므로 롤백된다.
  - 배송은 `PENDING`에 courier/trackingNumber가 비어 있는 채로 남는다 (3단계의 메모리상 변경이 롤백).
  - 주문은 `PREPARING` 그대로.
  - 5단계 이전에 터지므로 알림 1도 생성되지 않는다.
  - 판매·입찰 상태도 변하지 않는다.
- 응답: `Xkt44ExceptionHandler`가 `errorCode`로 응답을 만든다 (`G/exception/Xkt44ExceptionHandler.java:49-63`). 결과는 **HTTP 404, 코드 `S001`, 메시지 "배송 정보를 찾을 수 없습니다."** (`D/m45/exception/Xzn53ErrorCode.java:12`)이고, 바디는 `ErrorResponse`(code/message/status/path)다. 실제 원인(주문 상태 전이 불가)은 응답 바디가 아니라 로그에만 남고, 응답 코드도 "배송 없음"으로 오해를 부른다.
- 부차 사실: 이 경로에서 배송을 `IN_TRANSIT`으로 만들 수 있는 정상 방법이 없으므로, 일반 구매 주문의 배송은 `PENDING`에 머문다. 배치가 대상으로 삼는 상태가 아니라서 이후 자동 완료도 일어나지 않는다.

## 2. 배송 완료 감지

### 2-1. 누가·언제·어떻게

- 주체: 스프링 스케줄러 `Xzn53BatchScheduler.scheduleShipmentStatusJob()`이 `updateShipmentStatusesJob` 배치를 `JobLauncher`로 실행한다 (`G/config/Xzn53BatchScheduler.java:34-44`). 매번 `timestamp` 파라미터를 붙여 새 JobInstance로 실행한다.
- 주기: `@Scheduled(cron = "0 0 */6 * * *")`, 즉 **6시간마다**(매일 0·6·12·18시 정각, 서버 타임존 기준) (`Xzn53BatchScheduler.java:34`).
- 감지 방식: 택배사(CJ대한통운) 조회 페이지 `https://trace.cjlogistics.com/next/tracking.html?wblNo=<운송장>`을 Playwright로 열어 `tbody#statusDetail tr`의 **마지막 행 5번째 `td`** 텍스트를 읽는다 (`D/m45/config/Xcz52Processor.java:28-29,81-94,170-190`). 웹훅/푸시가 아니라 폴링이다.

### 2-2. 조회 대상

- `SELECT s FROM Xfr60 s WHERE s.status IN ('IN_TRANSIT','OUT_FOR_DELIVERY') AND s.trackingNumber IS NOT NULL` (`D/m45/config/Xpc23JobConfig.java:87-97`). `JpaPagingItemReader`, 페이지 크기 50.
- 청크 크기 50, skipLimit 50 (:51-52).

### 2-3. 실제로 실행되는 처리 코드 (비슷한 코드가 여러 개)

실제 실행 경로는 **`Xpc23JobConfig`의 스텝 → `Xcz52Processor.process()`** 이다.

- 스텝이 `new Xcz52Processor(...)`를 processor로 연결한다 (`Xpc23JobConfig.java:66-81`, 특히 :69).
- 같은 파일의 `shipmentItemProcessor()` 빈(:104-177)은 스텝에 연결되지 않은 **죽은 코드**다. `parseCjLogisticsStatus`(:186-220)와 파일 내 `mapToShipmentStatus`(:228-234)도 호출처가 없다.
- `Xfr60CommandService.updateShipmentStatuses()` (`Xfr60CommandService.java:308-391`)는 스케줄러·배치·컨트롤러 어디서도 호출되지 않는다 (`updateShipmentStatuses()` 호출 검색 결과 정의부뿐). 이 메서드는 `completeOrder`를 쓰지 않고 구매자 알림만 직접 보내는 다른 로직이라, 실행되지 않는다.
- 복제본: m09/m31/m38/m70/m81에 같은 구조의 `…JobConfig`/`…Processor`가 있다 (`D/m09/config/Xxt33JobConfig.java`, `D/m31/config/Xkd78JobConfig.java`, `D/m38/config/Xrx68JobConfig.java`, `D/m70/config/Xkq49JobConfig.java`, `D/m81/config/Xfr70JobConfig.java`). 이름이 같은 `updateShipmentStatusesJob` 빈을 모두 정의하며(각 `:55-57`), 차이는 알림 서비스 복제 클래스와 리스너뿐이다. 알림 서비스의 `notifyShipmentCompleted` 본문은 동일하다 (`D/m52/service/command/Xbp24CommandService.java:219`, `D/m77/…/Xrw60CommandService.java:219` 등). 따라서 어느 복제본이 선택되어도 결과 동작은 같고, 기준 구현은 도메인 위치(`m45`, `Xfr60`/`Xfr60CommandService`와 같은 패키지)의 `Xpc23JobConfig` + `Xcz52Processor`다.
- 주의(검증 한계): 같은 빈 이름이 여섯 번 정의되어 있고 `allow-bean-definition-overriding` 설정은 어디에도 없다 (`application*.yml`, 예시 yml 검색 결과 없음). Spring Boot 3.4 기본값이면 기동 시 빈 중복 오류가 날 수 있다. 정적 분석만으로는 실제 기동 여부를 확인하지 못했다.

### 2-4. 택배사 상태 문자열 → 내부 상태 (`Xcz52Processor.java:220-226`)

| 택배사 텍스트 | 내부 `Xzn53Status` |
|---|---|
| `"배송완료"` | `DELIVERED` |
| `"배송출발"` | `OUT_FOR_DELIVERY` |
| 그 외 모든 문자열 | `IN_TRANSIT` |

- 정확히 일치 비교라 공백이 섞인 문자열("배송 완료" 등)은 `IN_TRANSIT`이 된다.
- 현재 상태와 같으면 변경 없이 반환한다 (:101-105).
- `OUT_FOR_DELIVERY`인 배송에 "그 외" 문자열이 오면 `IN_TRANSIT`으로 매핑되는데, `OUT_FOR_DELIVERY → IN_TRANSIT`은 `canTransitionTo`가 false라 (`Xzn53Status.java:23-27`) `IllegalStateException`이 나서 해당 건이 스킵된다.

## 3. 배송 완료 판정 이후 (`Xcz52Processor.java:108-117`)

`newStatus == DELIVERED`일 때 순서:

1. **배송**: `orderShipment.updateStatus(DELIVERED)` (:113). `IN_TRANSIT`/`OUT_FOR_DELIVERY`에서 허용된다 (`Xzn53Status.java:16-27`). 저장은 스텝 writer(`JpaItemWriter`)가 한다 (`Xpc23JobConfig.java:74,239-246`).
2. `orderService.completeOrder(orderId)` (:116, 본문 `Xfr60CommandService.java:190-229`):
   1. `orderBid = findByOrderId(orderId)` 조회. 없으면 예외 (:196-197).
   2. **주문**: `order.updateStatus(COMPLETED)` (:204). 전이 검사 대상이다. `IN_TRANSIT`, `PENDING_PAYMENT`, `IN_WAREHOUSE`에서만 허용된다 (`Xhq12Status.java:24,27,29`).
   3. `updateSaleStatusToSold(orderId)` (:208). 판매를 `SOLD`로 바꾸고 판매자에게 알림 (1-2의 6단계와 동일).
   4. **구매자 알림**: "[completeOrder] 주문이 완료 처리되었습니다. 주문 ID: …" (:211-217).
   5. 어떤 예외든 `Xzn53Exception(ORDER_NOT_FOUND_FOR_SHIPMENT)`로 감싸 던진다 (:221-228).
3. **구매자 알림**: `notificationService.notifyShipmentCompleted(order)` → "[배송 완료] 상품이 배송 완료되었습니다. 주문 ID: …" (`Xcz52Processor.java:117`, `Xbp24CommandService.java:219-235`). 이 메서드는 내부 예외를 삼킨다.

배송 완료 시 상태 순서 정리: 배송 `DELIVERED` → 주문 `COMPLETED` → 판매 `SOLD`(이미 `SOLD`가 아닐 때).

### 알림 수

- 구매자 2건: "[completeOrder] 주문이 완료 처리되었습니다", "[배송 완료] 상품이 배송 완료되었습니다".
- 판매자 최대 1건: "상품이 성공적으로 판매 완료되었습니다" (`Xfr60CommandService.java:133-138`). 판매가 `SOLD`로 전이 가능할 때만 간다. 이미 `SOLD`면 0건이다 (아래 4-b 참고).

### 주문 입찰·판매 입찰 상태

- 이 경로에서 **입찰 상태는 바뀌지 않는다.** `completeOrder`와 `Xcz52Processor` 어디에도 `Xtw92`/`Xzt63`의 `updateStatus(COMPLETED)` 호출이 없다. 입찰이 `COMPLETED`가 되는 곳은 `updateOrderAndSaleBidStatusToCompleted`(`Xfr60CommandService.java:412-440`) 하나뿐이고, 이는 운송장 등록(1번) 경로에서만 호출된다.
- 따라서 배송 완료 시점에 주문 입찰과 판매 입찰은 매칭 후 상태인 `MATCHED`로 남는다 (`Xtw92.java:73-76`, `Xzt63.java:58-61`: `assignOrder`가 `MATCHED`로 세팅). 판매(`Xpj42`)만 `SOLD`가 된다.

## 4. 주문 종류별 차이

배송을 `IN_TRANSIT`으로 만드는 두 경로가 다르다는 점이 먼저 중요하다.

- 운송장 등록 API(`updateTrackingInfo`)는 주문 상태도 `IN_TRANSIT`으로 바꿔야 하므로 두 주문 모두 막힌다.
- `POST …/check-status`(`updateAndCheckShipmentStatus`, `Xfr60CommandService.java:451-516`)는 `shipment.updateTrackingInfo`로 배송만 `IN_TRANSIT`으로 만들고 (:473) 주문은 건드리지 않는다. 이 경로로 `IN_TRANSIT` 배송을 만들 수 있고, 이후 배치가 이를 집어간다. 조회 결과가 `DELIVERED`면 즉시 `completeOrder`도 호출한다 (:483-489).

### (a) 결제·배송 처리를 마친 실배송 일반 구매 입찰 주문 → **끝까지 진행되지 않는다**

- 주문은 `PREPARING` (0절). 배송이 `IN_TRANSIT`이 되어 배치가 `DELIVERED`를 감지해도, `completeOrder`의 `order.updateStatus(COMPLETED)` (`Xfr60CommandService.java:204`)에서 `PREPARING → COMPLETED`가 허용되지 않아 (`Xhq12Status.java:26`) `Xxm16StatusException`이 난다.
- `completeOrder`가 이를 `Xzn53Exception(ORDER_NOT_FOUND_FOR_SHIPMENT, S102)`로 감싸 던진다 (:221-228). 프로세서가 그대로 전파하고 (`Xcz52Processor.java:131-146`) 배치는 해당 건을 스킵한다.
- 결과: 주문 `PREPARING` 유지, 구매자·판매자 알림 0건, 입찰 `MATCHED` 유지, 판매 상태 불변. 트랜잭션 롤백으로 `DELIVERED`로 바꾼 배송 상태도 저장되지 않는다. 배송은 다음 주기에도 다시 대상이 되고 같은 실패를 반복한다.
- 추가로, 주문에 연결된 판매 입찰이 없는 일반 입찰이라면 `Xzt63QueryService.findByOrderId`가 `null`이 아니라 `IllegalArgumentException`을 던진다 (`D/m85/service/query/Xzt63QueryService.java:26-29`). 그러면 `updateSaleStatusToSold` 첫 줄 (`Xfr60CommandService.java:116`)에서도 막힌다. `null` 체크 (:117)는 도달 불가능한 코드다.

### (b) 즉시 구매로 만들어진 주문 → **끝까지 진행된다 (check-status로 `IN_TRANSIT`이 된 경우)**

- 즉시 구매 주문은 `PENDING_PAYMENT` 상태로 만들어지고 이후 상태가 바뀌지 않는다 (`D/m99/service/command/Xhq12CommandService.java:241-245`; 결제 서비스 `D/m64/service/command/Xjt45CommandService.java`에는 주문 상태 변경이 없다). 주문 입찰은 `MATCHED`로 생성되고 `markAsInstantPurchase()`가 호출된다 (`D/m99/service/command/Xtw92CommandService.java:176-193`). 판매 입찰은 주문에 연결되고 `MATCHED`다 (`Xhq12CommandService.java:279-280`).
- 운송장 등록 API는 이 주문에서도 실패한다. `PENDING_PAYMENT → IN_TRANSIT`이 허용되지 않기 때문이다 (`Xhq12Status.java:24`). 하지만 `check-status` 경로로 배송이 `IN_TRANSIT`이 되면 배치가 처리할 수 있다.
- 배치에서 `DELIVERED` 판정 시: 주문 입찰 존재 → `order.updateStatus(COMPLETED)`는 `PENDING_PAYMENT → COMPLETED`가 허용되어 통과 (`Xhq12Status.java:24`) → 판매 입찰이 연결되어 있어 `findByOrderId` 성공. 배송 `DELIVERED`, 주문 `COMPLETED`까지 진행된다.
- 판매 상태: 결제 처리 시 `notifyUsersAndUpdateSaleStatus`가 이미 판매를 `SOLD`로 바꿔 놓는다 (`Xjt45CommandService.java:83, 383-432`, `sale.updateStatus(SOLD)` :404/:419). 따라서 `updateSaleStatusToSold`의 `canTransitionTo(SOLD)`가 false가 되어 (`D/m85/entity/Xpj42Status.java`: `SOLD → false`) 판매 상태 변경과 판매자 알림은 일어나지 않는다.
- 알림: 구매자 2건(`[completeOrder]`, `[배송 완료]`), 판매자 0건. 이는 이 시점에 판매자 알림이 없다는 뜻이다 (판매자는 결제 시점에 "구매자가 결제를 완료하였습니다" 알림을 이미 받았다, `Xjt45CommandService.java:456-463`).
- 입찰 상태: 주문 입찰·판매 입찰 모두 `MATCHED` 유지 (3절).

## 5. 실패 처리 (주기 처리 중 한 건 실패)

- 스텝은 `faultTolerant().skip(Exception.class).skipLimit(50)`이다 (`D/m45/config/Xpc23JobConfig.java:75-77`). 청크 크기는 50 (:51,67).
- 한 건의 `process()`가 예외를 던지면 그 건만 **스킵**된다. 프로세서가 `Xzn53Exception`을 그대로 던지거나, 그 외 예외는 `EXTERNAL_TRACKING_SERVICE_ERROR`로 감싸 던진다 (`Xcz52Processor.java:131-146`). 스킵 리스너가 로그만 남긴다 (`Xpc23JobConfig.java:251-287`).
- 청크 트랜잭션은 롤백되고, 스프링 배치가 청크를 항목 단위로 다시 처리해 실패 건을 제외한 나머지를 커밋한다. 따라서 나머지 건은 정상 반영된다. 이 과정에서 외부 조회(Playwright)가 한 번 더 실행될 수 있다.
- 실패한 건: 변경이 롤백되고 상태는 `IN_TRANSIT`/`OUT_FOR_DELIVERY` 그대로다. 다음 6시간 주기에 다시 대상이 되어 같은 이유로 반복 실패할 수 있다 (특히 4-a).
- 스킵이 50건을 넘으면 `SkipLimitExceededException`으로 스텝이 실패하고 남은 건은 그 실행에서 처리되지 않는다.
- 스케줄러 자체는 예외를 `printStackTrace()`로만 처리하고 삼킨다 (`Xzn53BatchScheduler.java:41-43`). 다음 주기에 다시 실행된다.
- 조회 대상 상태 쿼리가 페이징 중 상태를 갱신하므로 페이지 경계에서 일부 건이 누락될 가능성이 있다 (`Xpc23JobConfig.java:87-97`의 offset 기반 페이징; 코드 읽기에서 추론한 것이고 실행으로 확인하지 않음). 누락분은 다음 주기에 처리된다.
- 참고: 사용되지 않는 `updateShipmentStatuses()`는 건별 try/catch로 `errorCount`만 올리고 계속 진행하는 구조다 (`Xfr60CommandService.java:322-388`). 실제로 실행되지는 않는다.
